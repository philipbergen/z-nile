---
title: A sequestration check never takes its reference from a ref the author can move
when: both
tags: [sequestration, guards, review]
check: Can the branch's author make the reference commit (a local or pushed branch, a merge) that this check judges sequestered files against?
---
A check that compares sequestered files with "the newest prep commit merged into the branch" lets the author pass it: point a local branch of that name at HEAD, or push an edit to the prep branch and merge it, and the edited `check.sh` becomes its own reference.

**Why:** c0120 code review 004 F1. AC18 read `origin/prep-c0120` and `prep-c0120` to find c0120's own files' reference after Guess 17's decision reached the item folder by a prep merge. In a clone, `git branch -f prep-c0120 HEAD` turned a deleted AC18 line green. The user decided "Reviewer-pinned commit": the reference is a `Prep reference: <sha>` an approving review records, and a missing or foreign sha refuses.

**How to apply:** when a check needs a moving reference, take it from a file only a reviewer writes (an approved review's recorded sha), never from a branch name, and refuse when it is missing or not in the branch. Add the case that moves the ref and expects red.

**Walk both trees, by item identity.** c0120 code review 005 F1: once its reference was pinned, AC18 still walked only HEAD's files, so `git rm` of a sequestered spec, or of another item's `check.sh`, left it green, and a file added to an item's folder was never judged. A sequestration check keys each file by its item and its path inside the item folder (the folder moves between `active/` and `done/`, and roots move), requires every reference file at HEAD, and every HEAD file of a known item in the reference.

**Model each lifecycle event through the tracker's own reader.** c0120 code review 006 F1: the both-ways walk read `done`'s promotion (`acceptance/` moving to `<home>/tests/acceptance/<id>`) as a deletion, because its fixture moved a folder by hand where `done` moves its specs out; and the rewrite's folder map, computed against HEAD, shifted once a later merge finished an item. A sequestration check that follows files across events reads each place the way the tracker does (`projects.promotedDir`, `paths.rewrite`), pins what it derives from the move to the move commit itself, refuses a compaction, and its fixture produces each event with the tracker's own steps. Check: does a merge of origin/main that finishes an item, and c0114's own `done`, keep the check green? For reviewers: a Recommendation that prescribes how a check models an event names every effect of that event (review 005's "finished by a later merge" missed that `done` moves the specs out of the folder): read the code that performs it.

**Judge the branch's own diff against what it merged, never a snapshot.** c0120 code review 007 F1: after three rounds of teaching AC18 lifecycle events by hand, a merge of the whole of today's origin/main turned it red on 17 files the branch never touched: main's own reviewed preps and readies changed them, and a frozen reference can never match them again. A sequestration check judges the branch's own delta, three-way per file against `git merge-base HEAD origin/main` (main's text is the reference for what main changed since the branch's base), and refuses when both sides changed a file differently. Prove it with a real merge of all of origin/main, not the events you expect. Check: merged with the whole of today's origin/main, does the check stay green while the branch has changed nothing?

**Any reference a sequestration check reads comes from outside the author's control.** c0120 code review 008 F1: "the main it merged" was read from the local `refs/remotes/origin/main`, so an unpublished commit carrying a weakened `check.sh`, set as that ref and merged, passed as main's. Read the published tip (`git ls-remote origin refs/heads/main`), require it fetched, and refuse when it can't be read. And a key that ignores a file's place must judge the place: a spec moved back out of its promoted folder keeps its text and loses its gate (008 F2).

**A whole-main merge is proven by every gate.** c0120 code review 009 F1: the merge simulation ran AC18 and override-markers, both green, while z-nile's gate failed on specs main promoted for the old layout, which the move must override and AC18 forbade editing. After merging all of today's origin/main, run all gates *and* the sequestration check, and give the overrides a reviewed, pinned home (here `main-overrides.patch`). And **inputs a reference is derived from are references too** (009 F2): a world picked by `git log -1 -- <path>` let a commit the author makes, and later undoes, choose what a finished check.sh is expected to be; pin such inputs (group 4's tree by its subject, HEAD's), never per file.
