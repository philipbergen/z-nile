---
title: A guard derives what it protects only after it strips the overrides that redirect git
when: both
tags: [guards, git, fence, ordering]
check: Is each value this guard derives from git (the protected repository, the toplevel, a common dir) computed after every inherited override (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_CONFIG_PARAMETERS`, …) is stripped? Is there a case with an inherited `GIT_DIR` that is relative (a hook's `.git`) and one that points at a foreign repository? What does the guard do when the read finds nothing, and is there a case with an inherited ceiling at the checkout's root, entered from a project home? For each read moved into the clean environment, does its caller then act through git with its own environment?
---
A guard that asks git which repository it protects, while an inherited `GIT_DIR` is still set, protects whatever that variable names. A relative `GIT_DIR=.git`, which git sets for hooks in a main checkout, resolves against the guard's own folder. From a project home that resolves to no repository at all, so the guard records nothing and lets every ref update through. An absolute one, pointing at another repository, records that one instead.

**Why:** c0120 code review 001 F1: review 002's reorder of `pickman_fence_env` ("refuse before you change anything") moved the `unset GIT_DIR …` below the hooks refusal, and `real=$(git rev-parse --git-common-dir)` went above it. A run from `pickman/` with `GIT_DIR=.git` inherited left `PICKMAN_FENCE_REAL_GIT` empty, and `git update-ref` succeeded in the real repository. No spec caught it: the existing cases set `GIT_DIR` to the same repository, absolute.

**How to apply:** when a guard's steps are reordered, list every read it makes of the repository it protects, and put each one after the full strip. The strip is a change, so it still comes after the read-only refusals (architecture/guard-no-is-explicit). Add the two cases (relative `GIT_DIR` from a subfolder, foreign `GIT_DIR` from the root), each checking that the recorded repository is the checkout's and that the ref guard refuses there. Add a mutant that moves the read above the strip.

**Found nothing is not "nothing to protect".** An override can make the read fail as well as redirect it. `GIT_CEILING_DIRECTORIES` at the checkout's root hides the checkout from a project home, because git never searches up into a ceiling folder. And the ceiling can't simply be stripped from the shell: the fence accumulates it, and nested fences and specs need it. So do the read through a clean `env -u …` that also drops the ceiling, for that one read only, and make an empty answer refuse, in every mode. c0120 code review 002 F1: after review 001's fix, an inherited root ceiling still left `PICKMAN_FENCE_REAL_GIT` empty from `pickman/`. The ref guard then let `git update-ref` through, and the runner's tripwire read nothing.

**Check what each read is for before you clean it.** A guard that answers "is the repository I am about to change protected?" must read the way the changer's own git will, and the clean way too, and protect when either names a protected repository. c0120 code review 003 F1: review 002's fix moved `pickman_guarded` to the clean read only. A caller that set `GIT_DIR` to the protected repository itself then got `unguarded`, while its git would act there. Now both reads are made, and either failing or coming back empty is exit 1, which callers treat as guarded.
