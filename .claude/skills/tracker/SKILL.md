# Tracker

All work is tracked in project roots, which are committed. `z-nile/projects.toml` lists the projects, each with the root that holds its issues and rafts: pickman's is `tracker/` (until c0120 moves it to `pickman/.tracker/`) and z-nile's, the tooling's, is `z-nile/.tracker/`. A directory it does not list is not a project. One counter numbers every project, so a bare id is unique across the repository, and every command that takes an id (`find`, `members`, `status`, `capture`, …) searches every root. The engine, its templates (`z-nile/templates/`), the counter and the compaction map live in `z-nile/` and belong to no project. The command is `./zn` at the repository root (`scripts/tracker.sh` forwards to it until every raft whose sequestered `check.sh` names that path is done). The only way to change tracker state is `./zn`. Don't move tracker directories by hand. Inside a raft, commit with `./zn commit`; capture, prep and doc-only worktrees, which have no active raft, use plain `git add` and `git commit` (see Landing a change). Every change is made in a worktree (see Worktrees).

## Items
| kind | ID | example |
|---|---|---|
| feature issue | `f` + 4 digits | `f0010` |
| defect issue | `d` + 4 digits | `d0020` |
| chore issue | `c` + 4 digits | `c0030` (includes every CI/test/tooling fix, even bugs; see make-issue) |
| raft (epic) | `R` + 4 digits | `R0010` |

- **Numbering**: `f`, `d` and `c` share one number space; rafts have their own. `z-nile/next` holds the next number of each (`issue <n> <phrase>`, `raft <n> <phrase>`). The first publish after c0114 lands moves the counter there from the old counter file, in its own lease push, and leaves a tombstone in the old file, so an engine from before c0114 refuses to number; until then the old file is the counter. `new`, `new raft`, an emergent issue and `renumber` take the counter, counting by one, and push it raised, with a fresh phrase, in a lease push to `origin/main` (a lost race is retried on the new `main`); a number already in use is always passed. Offline (`PICKMAN_PUBLISH=0`) the local counter is read but never written. A tree without `z-nile/next` (a fixture) keeps the old rule: the next multiple of 10 above the highest number in use.
- **Compaction**: `./zn compact` renumbers every item from 0001, in a fresh worktree cut from `origin/main`, as one local commit to land by pull request; it refuses while another branch changes a project root (`tracker/`, `z-nile/.tracker/`) or `tests/acceptance/` (`--force` runs anyway), and writes the old-to-new map to `z-nile/compaction.txt`. Merge the compaction PR only while `origin/main` still equals the sha in `z-nile/compaction.txt`'s header; if `main` has moved, reset to `origin/main` and compact again (it is deterministic). On each branch that was in flight, run `./zn remap` before merging `origin/main`: it takes the new ids and then merges `origin/main` itself. Never merge it plainly first: nothing detects the mixed tree afterwards. A branch that did merge plainly undoes that merge with `git reset --hard ORIG_HEAD`, then remaps. Any other tree from before the compaction refuses to publish until it merges `origin/main`.
- **Duplicate ids**: `./zn audit` reports every problem in the tree (the gate runs it too). One id in two lifecycle folders blocks most commands: `./zn renumber <directory>` renumbers that copy only: renumber the copy not in `done/` (normally the fresh backlog stub, for example `renumber tracker/issues/c0510`), because a done copy's specs are promoted under its id; a `done/` directory is refused.
- **Legacy layout**: documents used to be named with their slug. `./zn migrate` renames any such document to `<ID>.md` and adds `slug:` to its frontmatter; run it, and commit, after merging a `main` that has the new layout.
- **Conflicts**: two branches that pick the same number now conflict in git, because both write `<ID>/<ID>.md`. Only a `CONFLICT (add/add)` on that path means two items share a number: run `git merge --abort`, `git fetch origin main`, then `./zn renumber <ID>` on your own branch, which gives the item the number one above the highest of its kind in **both** your tree and `origin/main` (`f`, `d` and `c` share one space, rafts have their own), and merge again. `renumber <old> <new>` sets a number by hand. `renumber` rewrites every reference. A content conflict on a document is two edits to one item: resolve it like any merge, and never renumber. A branch from before c0114 that added a file inside a tooling item's folder gets `CONFLICT (file location)` when it merges `origin/main`: git suggests the folder's new place under `z-nile/.tracker/`; accept it (`git add` that path) and never move the folder back.
- **References**: always refer to items by bare ID, never by path. Use `./zn find <id>` to get the current directory.
- **Projects**: `./zn new issue` files the issue in the first project of `z-nile/projects.toml` (pickman), or in the one `--project <name>` names (`--project z-nile` for tooling: the tracker, the gate, the guards, the skills); an emergent issue goes beside its raft. A raft lives in its members' project and never spans two. R0001, finished before c0114, is the one exception: its members stayed with their projects (c0001 in z-nile's, c0002 in pickman's), and `members R0001` still lists both. `.tracker/` is a hidden folder: `rg` and some search tools skip it unless told (`rg --hidden`), so find items with `./zn find` or `git grep`.

Each item is a directory named by its ID:
```
<ID>/<ID>.md            the document (frontmatter incl. slug + sections from z-nile/templates)
<ID>/check.sh           acceptance criteria as executable checks (see the testing skill)
<ID>/acceptance/        sequestered acceptance specs (issues); `done` moves them to tests/acceptance/<ID>/
<ID>/experiments/       spikes for unknowns (issues)
<ID>/design-review-NNN.md, design-refute-NNN.md   from ticket-prep, on the raft
<ID>/review-NNN.md, refute-NNN.md                 code review, on the raft
<ID>/spend.md           written by `./zn commit` and `./zn spend`; never edit by hand
```

- **Lessons**: `.claude/skills/<skill>/lessons/<slug>.md`, id `<skill>/<slug>`. Frontmatter `title`, `when` (`design`, `build` or `both`), `tags: [a, b]`, `check` (one question ending in `?`) and optional `from` (only for a source with no item folder to hold a note; each key once); the body says the rule, why, and how to apply it. **`harvest.md`**, in each reviewed item's folder, has one entry per review finding: `- design-review-001 F2: <lesson id>, <lesson id>` or `- review-001 F3: one-off: <reason>`, plus `- note <text>: <lesson ids>` for a source that is not a review finding (a subagent's candidate, a correction by the user, a failed step). A note covers no finding. A lesson's sources are the entries naming it, each once. See `./zn lessons`.

## Worktrees
Every change is made in its own git worktree under `<repo>/.worktree/` and lands by pull request (except tracker state, see Sync and claim). The main checkout stays on `main` and is never edited. Every job runs in a worktree under `<repo>/.worktree/`, never outside the repo directory: no sibling directory next to the repo, and not the harness's own `.claude/worktrees/`.

1. **The main checkout is read-only.** The complete list of commands that may run there:
   - `git fetch`, `./zn sync` (a fast-forward there, which also rebuilds the board), and read-only inspection (`git status|log|diff|show|worktree list`);
   - `git worktree add|remove|prune` and `git branch -D <merged branch>`;
   - `z-nile/setup.sh`, once, when bootstrapping a new machine (SETUP.md);
   - `./zn ready` and `stop`, which publish to `origin/main`, fast-forward it there; `ready` writes the ignored `<root>/rafts/active/<R-id>/prompt.md` beside the raft and `stop` removes it;
   - the read-only tracker commands `list`, `audit`, `find`, `members`, `metrics`, `workstreams`, `status` (without a target status), `prompt <R-id>` (it reads a readied raft's prompt and writes nothing), `lessons` and `capture <id>` (they only read), and the worktree commands `worktree` and `worktree-prune`. (`./zn check` runs an item's checks and, for a raft, the full gate, so it runs in a worktree.)
   The tracker enforces part of this: `new`, `renumber`, `migrate`, `start`, `status <id> <to>`, `compact` and `remap` refuse to run in the main checkout of a repo that has an `origin`; `ready` and `stop` refuse to run anywhere else.
2. **Every change starts with a worktree**: `cd "$(./zn worktree <target>)"`.

   | work | target | path and branch |
   |---|---|---|
   | executing a raft | `R0010` | `.worktree/R0010`, branch `R0010-<slug>` |
   | capturing an issue (make-issue) | `capture-<slug>` | `.worktree/capture-<slug>`, the same branch name; lands with `./zn land`, no PR |
   | prepping a raft (ticket-prep) | `prep-<slug>`, the raft's slug | `.worktree/prep-<slug>`, the same branch name |
   | a skill, doc or config edit | `<area>-<slug>`, for example `skills-worktree-rule` | `.worktree/<area>-<slug>`, the same branch name |

   A change to skills, docs or tooling is still tracked work: it has an issue and normally a raft, and is executed in the raft's worktree like any other. Names are lowercase, so a prep worktree is named by the raft's slug: its id isn't known until `new raft` has run inside it. Use `./zn worktree`, not the harness's own worktree feature: its directories aren't under `.worktree/`, and `worktree-prune` never sees them (it warns about any worktree outside `.worktree/` and leaves it). A worktree inside the repo also sees the main checkout's `.luaurc` as a parent configuration, so an alias a branch renames can still resolve locally: CI, which checks out the branch alone, is the final check.
3. **Starting execution**: the human starts a Claude session in the main checkout (which stays on `main`) and runs `/launch-raft <R-id>`. The skill reads the raft's prompt (`./zn prompt <R-id> --path`) and `cd`s into `$(./zn worktree <R-id>)`. The hooks follow the session's current directory, so from then on they act in the worktree; subagents get absolute worktree paths, because a subagent's shell resets its working directory on every call. Another agent gets the same text from `./zn prompt <R-id>`.
4. **Prep merges before execution.** A prep PR merges (Landing a change) before `ready-raft` runs, so the raft's own worktree branches from an `origin/main` that has the prepped items. `ready-raft` never creates a raft: a raftless issue goes back to ticket-prep.

## Lifecycle: the directory and the status
- **Paths**: `<root>/{issues,rafts}/<ID>` is backlog (`<root>` is the item's project root, `tracker` or `z-nile/.tracker`), `…/active/<ID>` is in progress, and `…/done/<ID>` is finished. On `main`, `active/` holds the rafts that `ready` has handed out (and their issues), not only the branch you are on: the current raft is the active raft whose branch is the current branch.
- **The design field**: frontmatter `design:` moves `draft` → `reviewed` → `ready`, and only `ticket-prep` sets it.
- **Everything worked is a raft.** A raft has exactly one type (feature, defect or chore), and every member issue must match it. A lone issue gets a `single: true` raft made by ticket-prep in its prep worktree; `./zn ready <issue>` refuses a raftless issue, and `prompt` takes only a raft id.
- **One raft = one branch (`R0010-<slug>`) = one PR.** In Phase 2B, temporary stream branches (`ws-<issue>`) feed the raft branch and are deleted.

| step | command | effect |
|---|---|---|
| ready | `./zn ready <R-id\|issue-id>` | main checkout only, on a clean `main`, with an origin (ready-raft skill). Checks the raft and every member are `design: ready` with a `check.sh` that has a check, and that every `depends_on` outside the raft is `done`. Claims the raft, publishes one tracker-only commit that moves it and its members to `active/` on `origin/main` (every `check.sh` item path rewritten), pulls the main checkout, and writes the ignored `tracker/rafts/active/<R-id>/prompt.md`. On an active raft it regenerates the prompt and makes no commit. |
| stop | `./zn stop <R-id>` | main checkout only, on a clean `main`, with an origin (stop-raft skill). It gives back exactly the issues that carry the raft's own claim stamp (`ready` and `start` stamp the raft and every issue they claim with one `active-…` value); an issue only listed in `issues:`, or one filed naming the raft after the claim, is never touched (the latter is named in a warning). Every claim stamp is new on `origin/main` (redrawn until no item carries it), and a raft with no `active-…` stamp is refused, to be given back by hand. Gives back a readied raft: publishes one tracker-only commit that moves it and its members from `active/` back to the backlog, stamped `prepared-…` (every `check.sh` item path rewritten back), removes `prompt.md`, pulls the main checkout, and names the raft's branch and PR, which it leaves as they are. A raft claimed by the legacy `start` (backlog, status `active`) gets a status-only publish and no move. A member in `done/` refuses. |
| start | `./zn start R0010` | clean tree required. A readied raft (in `active/` on `origin/main`): creates the branch, makes an empty `tracker: start` commit, pushes, and opens a **draft** PR; it claims and moves nothing. A backlog raft (legacy): checks members are `design: ready` and every `depends_on` of a member that isn't a member of the raft is `done` on `origin/main` (an unknown id is refused too); if `start` refuses, merge `origin/main` and retry, never edit `depends_on` or move items to get past it: stop and report. For a named worktree, `--from <ref>` cuts the new branch from that ref instead of `origin/main` (used for workstream streams: `./zn worktree ws-<issue> --from <raft branch>`). |

A raft's shown type comes from its issues (one type, or mix). A row with a next command has a copy button. ## Landing a change
One procedure for every change: a raft, a capture, a prep or an edit.
0. **Sync first.** `./zn sync` in the worktree (a fetch and a merge of `origin/main`).
   - If `main` brought the new document layout, run `./zn migrate` and commit.
   - A `CONFLICT (add/add)` on a tracker document means two items picked the same number: see Conflicts.
   - Then run `./zn list` (it fails on a duplicate id and warns when one number is shared by two prefixes; renumber yours if you can) and `z-nile/check.sh --full`.
1. **Commit in the worktree**: `./zn commit` inside a raft; plain `git add` and `git commit` elsewhere.
2. **Push and open the PR**: `git push -u origin <branch>`. A raft's PR is opened as a draft by `start`; any other PR is opened ready with `gh pr create`. A capture lands with `./zn land` instead (no PR): it merges `origin/main`, runs `z-nile/check.sh --full` locally, checks that only the sections, title and `depends_on` of draft backlog issue documents changed, pushes one commit to `main` (retrying a lost race) and prints the worktree-removal command.
3. **Merge** a PR only when the conditions under Merging hold, with `gh pr merge --squash`. A raft additionally needs `./zn done` and a resolved review. A prep the user didn't ask for is not merged without asking, and a capture they didn't ask for is not landed without asking. (A capture has no PR: `./zn land` in step 2 is its landing.)
4. **After the merge, one chained command, run last**: `"<root>/zn" sync; git -C <root> worktree remove <path> && git -C <root> branch -D <branch>; git -C <root> worktree prune`. `<root>` is the first path in `git worktree list`; `sync` fast-forwards the root and rebuilds its board. When the session works inside the worktree (with launch-raft it started in the main checkout and `cd`'d into the worktree), removing it removes the session's own directory, so every command after it must use `-C <root>` or absolute paths, and nothing should run after this command: post the final report first. The alternative is to leave removal to `./zn worktree-prune`, run later from the main checkout.

## Merging
The agent that delivered the change merges its own PR once the evidence is in. Don't wait for a human. Merge only when **all** of these hold:
1. **For a raft**, `./zn done` succeeded: the latest review round is resolved and the raft's `check.sh` passed. The PR is ready, not draft, and has no unresolved `BLOCKED:` comment. The results of the most recent review are already on the PR as a comment (execute-raft Phase 4). Only a *significant* finding in the final round's `review-NNN.md` (any high, or a failed Judged criterion) blocks the merge and engages the human; mediums and lows become follow-up issues (execute-raft Phase 4 step 7).
2. `z-nile/check.sh --full` passes on the final head, run by you.
3. CI is green on the PR's exact head sha. `done` marks the PR ready before its final push, so the push starts the `pull_request` run on the final head (the `ready_for_review` event also starts a run, on the previous head; the poll ignores it because it looks at the final sha). Poll `gh pr view <pr> --json headRefOid,statusCheckRollup` until `headRefOid` equals `git rev-parse HEAD` and the `gate` check is `COMPLETED` with conclusion `SUCCESS`. Any other state is **not** green: a missing `gate`, `IN_PROGRESS`, or `SKIPPED` on the final sha means that sha was pushed while the PR was still a draft, so no run will follow by itself: dispatch one with `z-nile/ci-verify.sh` (below); `FAILURE` is red. If no `gate` run for this sha appears within a few minutes of the push, dispatch one with `z-nile/ci-verify.sh` (it needs HEAD equal to `origin/<branch>`, so push first) and wait. If the dispatched run fails, treat it as red.
   **The `beta` job too.** A PR that is ready for review from this repo also runs `beta`, which publishes the version to Pickman (Beta) and runs the runtime tests, so a merge needs it:
   - A missing `beta` check for the head sha means keep waiting, exactly like a missing `gate`.
   - A `workflow_dispatch` run never satisfies `beta` (it skips it). If no `pull_request` run appears within about 5 minutes of the `ready_for_review` event, re-fire that event with `gh pr ready --undo <pr> && gh pr ready <pr>`; use `ci-verify.sh` only to diagnose `gate`.
   - `beta` must be `COMPLETED` with conclusion `SUCCESS`. Unconfigured publishing ends `SUCCESS` with a warning, which is fine.
   - A red `beta` whose log shows `opencloud: ... failed with HTTP 429` or `HTTP 5xx` (500-599), from publishing, creating the task or polling it, or a publish `HTTP 409` (Roblox busy), is a transient Roblox failure whose retries ran out: rerun that job with `gh run rerun <run-id> --job <job-id>`, at most 3 times, then `BLOCKED:`. Any other red `beta` (HTTP 401, 403, 404 or another 4xx besides publish's 409, or a `FAIL` line without such a status) is a real failure: never rerun it; fix the cause, or post `BLOCKED:` when it isn't in this PR.
   - For a `CANCELLED` `beta`, run `gh run view <run-id> --json jobs`: a `beta` job with no steps was superseded by a newer ready PR (it never started), so rerun it with `gh run rerun <run-id> --job <job-id>` as often as needed until it finishes, but stop with `BLOCKED:` once 60 minutes have passed since the PR became ready, counted from the first ready event (re-firing it does not restart the count). A `beta` job whose steps ran was timed out or cancelled by hand: red. Judge `beta` only by the PR's own `pull_request` runs for the head sha: a `beta` that a dispatched run reports as `SKIPPED` never counts, for or against.
4. `gh pr view <pr> --json mergeable,mergeStateStatus` shows `MERGEABLE` and `CLEAN` (`UNKNOWN` is GitHub still computing it right after `done`: re-poll for up to a minute before deciding); any other state (`BEHIND`, `BLOCKED`, `UNSTABLE`, `DIRTY`) is not mergeable. `done` is preceded by a merge of `origin/main` (execute-raft Phase 5), so this should hold. If `main` moved since, and the merge is a clean one, merge `origin/main` in with plain `git` (`./zn commit` needs an active raft, and `done` has moved it), rerun `check.sh --full`, push, and repeat step 3. If it conflicts, or it needs anything beyond renumbering colliding IDs (`renumber` per Conflicts), post `BLOCKED:` and stop: a finished PR gets no unreviewed code changes.
5. The human hasn't said to hold.

Then `gh pr merge <pr> --squash --subject "<raft>: <title> (#<pr>)" --body $'<summary>\n\n<the Co-Authored-By line from your commit instructions>'` (the `$'...'` form makes the newlines real, so the trailer is a trailer). Get the merge sha with `gh pr view <pr> --json mergeCommit -q .mergeCommit.oid`. Then follow Landing a change, step 4. This repo may have no branch protection, so these conditions are the only gate: you enforce them. Never use `--admin`, and never merge on red or missing CI, an unresolved review, or a stop condition. If any condition can't be met, leave the PR as it is, post a `BLOCKED:` comment saying which, and stop.

Observed criteria (human Studio playtests) do not block the merge. Put them in the final report and PR comment, and file any failure the human finds later as a defect issue.

## The PR is the visible record
The draft PR opened by `start` stays the live log of the raft. Every `./zn commit` pushes. In addition, comment on the PR (`gh pr comment`) when: a review starts (with the sha), a review file lands (verdict and findings by severity), a review is answered (the refute lines), an issue finishes, and on any `BLOCKED:` stop. Never sit on unpushed work, and never leave review files uncommitted. See execute-raft Phase 4.

## Spend (best effort, automatic)
Rows are only ever appended. A row has nine columns: when, commit, +lines, -lines, minutes, attribution, phase and tokens. The phase is one of `capture`, `prep`, `design-review`, `build`, `code-review` or `deliver`.
- `capture`: `./zn spend <issue> --phase capture` after `./zn land`, before the capture worktree is removed. No lines.
- `prep`: `./zn spend <R-id> --phase prep` once, when the prep PR is opened, before anyone readies the raft. Lines are that branch's own `check.sh`, `acceptance/` and `experiments/` files.
- `design-review`: `./zn spend <R-id> --phase design-review` for the reviewer's run and again for the answering time. No lines.
- `build`: `./zn commit` (the default phase). Lines are the staged diff.
- `code-review`: `./zn commit --phase code-review`, including the reviewer's tokens when the harness reports them. Lines are the staged diff.
- `deliver`: `./zn commit --phase deliver`, `done`'s own commit, and `./zn spend <R-id> --phase deliver` after the merge. Lines are the staged diff, or none after the merge.
- **Lines**: the staged diff, excluding every project root, except the `prep` phase above. On the `done` commit, the promoted `tests/acceptance/` specs are also excluded, because they're prep work. Later edits to them, for example a defect fix, do count.
- **Attribution**:
  1. `--issue` flags if given;
  2. otherwise the current focus;
  3. otherwise every issue in the raft.
  With several issues, each file's lines go to the issue whose **Touched modules** lists that path; files nobody claims are split evenly.
- **Minutes**:
  - `--time <minutes>` when you actually know how long you worked on it. Prefer this.
  - Otherwise the wall-clock time since the previous commit, capped at 45 minutes.
  - With several issues, minutes are split in proportion to lines added.
- **Commit often**, at least once per issue and once per review round. Smaller commits mean more accurate attribution.

## Emergent issues
- **Can't be postponed** (it blocks the raft's check.sh, or shipping without it would break something):
  1. `./zn new issue d <slug> --raft R0010`. It's created directly in `active/` with `emergent: true`, using the correct type even if that differs from the raft's.
  2. Fill in Problem, Solution and ACs, plus a `check.sh`.
  3. Fix it in the same PR.
  4. List it under the raft's "Addressed during execution".
  Its spend counts toward its own type, which is how rework is measured.
- **Can be postponed**: `./zn new issue <f|d|c> <slug>` into the backlog, mention it in the final report, and don't fix it now.

## Sync and claim
Tracker state is shared the moment it changes, not when a PR merges, so parallel terminals see each other's work.
- **Sync first.** Every skill that reads or changes tracker state starts with `./zn sync` (a merge of `origin/main` in a worktree, a fast-forward in the main checkout). Reviewers and stream agents never merge: they run `./zn sync --fetch`, which only updates `origin/main`, so the diff they judge does not move.
- **Statuses** (`status:` in an item's frontmatter): `new -> preparing -> prepared -> active -> done`. `design:` (draft, reviewed, ready) stays the design review's field. A missing `status:` is derived: `done/` is done, `active/` is active, `design: ready` is prepared, a draft item in a raft (or a draft raft) is preparing, anything else is new. `./zn status` lists them from `origin/main`; `status <id>` prints one; `status <id> <to>` moves one, checked against `origin/main`. `done` is only ever set by `./zn done`, and only `ready` (or the legacy `start` of a backlog raft) claims `active`, and `stop` gives a readied raft back.
- **Every write is stamped**: the stored value is `<state>-<three words>` (for example `preparing-quiet-copper-falcon`) and each write uses fresh words, so two terminals making the same move conflict in git instead of merging silently.
- **Published or carried.** These moves are pushed straight to `origin/main` as a tiny commit: `new issue` (the stub, `--desc "<line>"` is its Problem), `new raft` (claims its members), `status <id> preparing|new`, `status <id> prepared` back from `active`, and the claim made by `ready` (or by a legacy `start`). An emergent `new issue --raft <R-id>` and `renumber <id>` without `<new>` push a counter-only commit (the raised `z-nile/next`) and then work locally. The move to `prepared` is **carried by the prep PR**: it only edits the local documents.
- **The direct-push exception.** Everything else lands by pull request. A published change is a tracker-only commit: only `<root>/(issues|rafts)/<ID>/<ID>.md` and `check.sh`, under a root that `origin/main`'s `z-nile/projects.toml` lists (never the working tree's), a `check.sh` only when it is created, an existing document only in its `status:` line (what `status`, `new raft` and `start` publish), an issue's `spend.md`, rows appended only (`./zn spend`), and `z-nile/next`, whose counters may only go up. The one other kind is a whole-directory move by `ready` or `stop`: every file of an item directory moves between the backlog and `active/` of its own root (never `done/`, never to another root), byte for byte, except the document's `status:` line and the item paths in `check.sh`, which `paths.rewrite` changes to the new directory; publish recomputes both and refuses anything else. `./zn land` also pushes a capture's edits to draft backlog issue documents (their sections, `title` and `depends_on`; design stays draft, every other frontmatter line unchanged) after a local full gate. Designs, reviews, code and acceptance specs never ride it. A commit that skips CI for the many tiny pushes is intended: `check.yml` ignores `tracker/**`, `z-nile/.tracker/**` and `z-nile/next` on `push`, not on `pull_request`.
- **Claims.** Prep claims with `new raft` (issues must be `new`). An existing draft raft is claimed with `./zn status <R-id> preparing`, which stamps the raft and its members; an issue added to a raft during prep is claimed first with `status <id> preparing`; one dropped is released with `status <id> new`. `ready` (and a legacy `start`) refuses a raft unless it and its members are `prepared` on `origin/main`; the claim is made by `ready`, not `start`.
- **A failed start.** `start` runs every local check before it claims. If a step after the claim fails (branch push, `gh pr create`), the local state is consistent: finish by hand (`git push -u origin <branch>`, `gh pr create --draft`), or give **your own** claim back with `status <R-id> prepared` (a raft started the legacy way, still in the backlog; a readied raft is given back only by `./zn stop <R-id>`). The same terminal can re-run `start` if it died before moving anything (it remembers the claim in `.cache/tracker-claim-<R-id>`); another terminal is refused.
- **Offline.** `PICKMAN_PUBLISH=0` (or a repository without `origin`) keeps every command local, as it was before. Publishing and every other command that changes a repository first check that git's repository root is the checkout the tracker lives in; read-only commands do not.
- **Giving back a readied raft.** `status` refuses any item in `active/` on `origin/main` ("<id> is readied (in active/): use ./zn stop <R>"); `./zn stop <R-id>` is the way to give back a readied raft, and it also gives back a raft claimed by the legacy `start`.
- **Whose claim.** A claim is not enforced against other terminals' give-backs (`stop` included): `status <R-id> prepared` from `active` (a legacy claim; a readied raft only through `stop`), `status <id> new` and `status <id> preparing` are open to anyone, so use them only for a claim that is yours (the user's decision: ownership is documented, not checked). Never give back a claim you did not make; ask the user.
- **Cutover.** A prep that was open before this landed exists only on its branch, so nothing on `origin/main` knows its raft id or members. Land such preps first, and renumber on a clash (see Conflicts). Do not stamp their members with `status <id> preparing`: a stamped member of a raft that is not on `origin/main` cannot be moved to `prepared` and can never be started.

## Lessons
Before you start, read this skill's lessons: `./zn lessons --skill tracker --full`. Each is a mistake made before, with the question that catches it.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `.claude/skills/<the skill the lesson improves>/lessons/<slug>.md` (format: tracker skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (ticket-prep step 5.3, execute-raft Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (make-issue skill). The prep that takes the issue writes the file.
