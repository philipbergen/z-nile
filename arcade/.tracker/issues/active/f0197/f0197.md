# f0197: Hiscores with revives

## Problem
The user, 2026-10-31: "I want to branch out into multiple games, they will each have their own directory in the project: first person snake, first person asteroids. I also want a new project for a landing portal where you can scroll between the games and see the highscores for each, the same cost model remains but it shoudl show 5 robux for each game witha slash through showing it is currently on sale for 1 robux. highscores shoudl show how many revives were used. I want you to design a full fun playable game for both of those two new game ideas. I also want both snake and asteroids to be a two player game, snakes can even be n-player up to a high number just make the wold bigger. Snakes should have maps that once you have reached a certain length the game ends and we move to a new map, the first is empty, then one wall somewhere in the middle, then two, then three and so on. The walls can be vertical and horizontal but do not connect. for asteroids we could have a two player version where each player is attacking the aliens from opposing sides. You can shoot each other's barriers. the aliens would then come in from the side and and split into two groups that move toward either player". Then: "Add a third game first person asteroids." Decided with the user (2026-10-31): the 2-player aliens game is pure Space Invaders (`invaders`); Asteroids is its own game (`asteroids`); one Roblox experience with the portal as start place, replacing pickman's lobby; every board shows revives used; one free game per hour per game.

The approved design is `arcade/.tracker/architecture.md` (c0183). This issue owns these parts of it, as they are said there: **Technical skeleton**, "What moves into arcade", item 1 (Hiscores). The rest of it belongs to other issues (c0190's ownership table), listed under Non-goals.

What should happen:
- A shared Hiscores feature (pure Logic, from pickman's `Logic/Hiscores`) and one generic server `Boards` adapter, used by every place.
- Each game has its own stores (per-game store names); pickman keeps today's names, so its boards keep their rows.
- Every board row records and shows **revives used** (paid revives of that run); rows written before it show as no revives.
- Each game's progress figure is stored with the row (Pickman level, Snake map, Invaders wave, Asteroids wave).

## Non-goals
- Pickman switching to it: c0198 (Switch to arcade hiscores).
- The portal's board screens: f0206 (Boards per game).
- Each game's runs reaching its boards: f0215, f0219 and f0223.
- The rest of `arcade/.tracker/architecture.md`: c0198, f0199, c0200, f0201, c0202, f0203, c0204, f0206, f0209, c0210, f0212, f0218, f0222, and c0184 and c0185 (the library's layout, wiring, gate and paths).

## Solution
Copy pickman's `Logic/Hiscores` into the library as `arcade/src/shared/Logic/Hiscores` with three changes: a title's stores are named from a prefix (`Hiscores.names(prefix)`, where `""` gives pickman's names as they are today), every row, list entry and best carries `revives` (the paid revives the run used; a row stored without them reads as 0), and the progress figure keeps its stored name `level` for every title. Merge pickman's two store adapters (`src/server/HiscoreStore.luau`, which writes, and `src/lobby/server/Boards.luau`, which serves) into one generic server adapter, `arcade/src/server/Boards.luau`, opened per title with `Boards.open(prefix)`. List every title's prefix and the name of its progress figure in one config table, `arcade/src/shared/HiscoreGames.luau`. Nothing in pickman changes: c0198 switches pickman to the library, and the portal and the new games wire it in through their own issues.

### Modules
1. **`arcade/src/shared/Logic/Hiscores/init.luau`** (pure, a leaf: requires nothing). A copy of `pickman/src/shared/Logic/Hiscores/init.luau` at `origin/main`, every function and constant kept with its behaviour, and these changes only:
   - **Store names from a prefix.** `export type Names = { ordered: string, companion: string, top: string }`. `Hiscores.PREFIX_MAX = 20`. `Hiscores.names(prefix: string): Names` returns a frozen table `{ ordered = prefix .. "Hiscores", companion = prefix .. "HiscoreEntries", top = prefix .. "HiscoreTop" }`. A prefix is `""` or matches `^%u[%a%d]*$` with `#prefix <= PREFIX_MAX`; anything else (a lower-case start, a space or punctuation, too long, not a string) raises an error at level 2. The longest names (`HiscoreEntries` after 20 characters, 34, plus a `_week_2026_10_12` global suffix, 50) fit the engine's 50-character store names. The constants `ORDERED_STORE`, `COMPANION_STORE` and `TOP_STORE` are removed (`names("")` holds them); `TOP_SCOPE` and `TOP_KEY` stay.
   - `Hiscores.storeTarget(names: Names, kind: string, board: Board, useScope: boolean): (string, string)`: the base is `names.ordered` for `"ordered"` and `names.companion` otherwise; the rest is pickman's (scope or the global name).
   - **Revives.** `Attempt.revives: number?` (nil is none). `Hiscores.valid` also requires `revives` to be nil or a whole number from 0 to 2^53 - 1 (a negative, a fraction, an infinity, NaN, a string or a boolean makes the attempt invalid, so nothing is written, exactly as a bad score does). `Companion.revives: number?` (rows stored before f0197 have none). `Hiscores.commit` stores `revives = attempt.revives or 0`. `Hiscores.revivesOf(raw: any): number` is `raw` when it is a whole number from 0 to 2^53 - 1, else 0: the one reader of a stored figure. `Row.revives: number` is `revivesOf(companion.revives)` in `Hiscores.rows`. `TopRun.revives: number`: `topRun` takes `attempt.revives or 0`, the list's reader (`ordered`) keeps `revivesOf(e.revives)` (so an entry stored before f0197 reads 0), and `bestRun` takes `revivesOf(row.revives)`. `Best = { score, level, revives }`, with `revives = revivesOf(companion.revives)`. `StepEvent.revives: number?` and `Submission.revives: number`: `onStep` takes `event.revives`, 0 when the event names none (a bad value goes on to the submit, where `valid` refuses it). `qualifies`, `rows`' sort and the list's order (`before`) do not read `revives`. Every reader of a stored figure (`rows`, the list's reader `ordered`, both branches of `bestRun`, `best`) goes through `revivesOf`, so a junk value (`-2`, `1.5`, `"3"`, `2^53`) reads 0 everywhere.
   - **The leave window is each title's.** `Hiscores.leave(stepsWaited: number, sawOver: boolean, window: number): "drop" | "keep"` drops when `sawOver or stepsWaited >= window`, and `Hiscores.onStep(state, events, here, window: number)` passes its `window` on. `Hiscores.LEAVE_STEPS = 45` stays, documented as pickman's window (its dying pause: 45 of its 30-a-second steps), for c0198 to pass; each new title's run adapter passes its own window, in its own steps (f0215, f0219, f0223). The window is required, so no title gets pickman's by default.
   - **The GameOver contract** (in `onStep`'s comment, binding f0186, f0215, f0219 and f0223): a title's `GameOver` step event is the run's end. It comes once any revive offer has closed unbought; a bought revive continues the same run and emits no GameOver; the event carries the run's final score, progress figure and `revives`. `onStep` submits the first scored GameOver of a run once (pickman's `once`), so a title that emitted GameOver when its offer opened would record the run before its revives and then have its real end refused.
   - `Hiscores.lobbyRows` becomes `Hiscores.boardRows(rows: { Row }): { BoardRow }`, `export type BoardRow = { rank: number, name: string, score: number, level: number, revives: number }`: what a client is sent, with no user id. `Hiscores.topRows` also carries `revives`.
   - **The progress figure is `level`, for every title.** Pickman's stored rows, ordered integers (`pack`'s tie-break) and list entries call it `level`, and pickman's servers keep reading those rows until c0198 switches them, while servers of both builds run side by side during a deploy. A renamed field would make every row written by the library invisible to a pickman server (`rows` drops a companion without a whole `level`). So the field stays `level`, the doc comments say it is the title's progress figure, and `HiscoreGames` names what it counts. Adding `revives` is safe in both directions: today's build ignores the field, and the library reads a row without it as 0. (A list written by today's build drops `revives` from its entries; no run has revives before f0186, long after c0198, so nothing is lost.)
   - The module header and comments never use the word "game": the engine-word rule (`tests/meta/architecture.spec`) reads comments too (E2). They say "title".
2. **`arcade/src/server/Boards.luau`** (adapter, server only: `ServerStorage.Arcade.Boards`). It requires only `@game/ReplicatedStorage/Arcade/Logic/Hiscores`, and decides nothing that Hiscores decides.
   ```lua
   export type Listener = (userId: string, run: number, rank: number?, missed: number?) -> ()
   export type Game = {
   	names: Hiscores.Names,
   	submit: (userId: string, name: string, score: number, level: number, revives: number, run: number) -> (),
   	pending: () -> number,
   	listen: (fn: Listener) -> (),
   	serve: (remote: RemoteEvent) -> (),
   }
   function Boards.open(prefix: string): Game
   ```
   - `Boards.open(prefix)` calls `Hiscores.names(prefix)` (so a bad prefix errors here), and returns one handle per prefix: the same prefix is the same table, so every caller in a place shares its pending count, its listener and its cache. Each handle has its own `pending`, listener, board-key states and held bests; two titles never share any of them.
   - `submit` is pickman's `HiscoreStore.submit` with `revives` added and the stores named from the handle's names: it counts itself pending, spawns the write (`task.spawn` inside `pcall`), builds the attempt with `revives`, takes `Hiscores.topRun(attempt, os.time(), run, game.JobId)`, names the run on the attempt (`run`, `at`), runs `Hiscores.drive` and then `Hiscores.driveTop` with drive's rows, tells the listener when the place is known, warns on failure (`[arcade] hiscore write failed (<ordered name>)`), and is no longer pending when the write ends, failed or not. A run that `Hiscores.valid` refuses (a score below 0, a progress figure below 1, a bad revives count) writes nothing, as in pickman, and `submit` now also warns `[arcade] hiscore run refused (<ordered name>)`, so a title whose figures are out of range finds out. Its doc comment states the ranges: `score` a whole number from 0, `level` (the progress figure) one from 1, `revives` one from 0. Its `Io` and `TopIo` are pickman's, with `GetDataStore(names.top, TOP_SCOPE)` for the list and `storeTarget(names, ...)` for the boards. The engine's `game` stays visible in the module: no local is named `game`.
   - `pending` and `listen` are pickman's `HiscoreStore.pending` and `listen`, per handle.
   - `serve(remote)` is pickman's lobby `Boards.start` without the remote's creation (the place's own adapter makes the remote, names it and parents it, then passes it in): it connects `remote.OnServerEvent` and, once per handle, `Players.PlayerRemoving` (a leaving player's held best is dropped). Each request is a board id (`Hiscores.boardId`; anything else is ignored); the reply is `remote:FireClient(player, id, Hiscores.boardRows(rows), Hiscores.rankOf(rows, userId), failed, best)`, where `best` is the asker's held best (with revives) on the all-time board only. The read, the shared cache (`Hiscores.lookup` with `CACHE_TTL` and `READ_GAP`), the waiters, the failure wait, the sweep of old periods and the per-player best (`needsRead`, at most once per `CACHE_TTL`) are pickman's. The list's read is `Hiscores.topRows((topStore():GetAsync(TOP_KEY)))`: the parentheses keep `GetAsync`'s second result (its key info) out of `topRows` (E5). Writes and reads share one page reader (pickman's `HiscoreStore` one: the ordered store is opened inside each of its two tries, so a store that fails to open once is tried again at size 50, where pickman's lobby failed the read at the first open error; two failures fail the read, as `serve.spec` pins).
3. **`arcade/src/shared/HiscoreGames.luau`** (a config table, `ReplicatedStorage.Arcade.HiscoreGames`; a client may read it). `export type Game = { prefix: string, progress: string }`, and a frozen table of frozen entries: `pickman = { prefix = "", progress = "Level" }`, `snake = { prefix = "Snake", progress = "Map" }`, `invaders = { prefix = "Invaders", progress = "Wave" }`, `asteroids = { prefix = "Asteroids", progress = "Wave" }`. A title opens its boards with `Boards.open(HiscoreGames.<title>.prefix)`, and the portal (f0206) walks the table to read and label every title's boards. Every prefix is distinct and valid for `Hiscores.names`.
4. **`arcade/tests/unit/Hiscores/`**: pickman's three unit specs (`hiscores`, `read`, `run`), copied; a typed `Row` literal gains `revives = 0` (luau-lsp needs it). `./zn finish` writes their watch files.
5. **`arcade/.tracker/architecture.md`**: item 1 of What moves into arcade names the three modules and the prefix rule (done in this prep). No dependency edge: Hiscores requires no other feature, so the `deps` block stays as it is.

### The split and server authority
Everything that decides is in the pure module and unit-tested in Lune: the names, the revives rules, the replace rule, the order, the retries and budgets, the list, the shared read. `Boards` only opens stores, hands Hiscores its calls and fires replies. It lives under `src/server`, which never replicates, so no client can open a store. The server alone submits: `submit` is called by a title's server adapter with the run's own score, progress and revives (counted by its server, f0186/f0215/f0219/f0223), and a client's only message is a board id, which `Hiscores.boardId` bounds. The replies carry no user id.

### Data flow
A title's server (its own issue) calls `Boards.open(HiscoreGames.snake.prefix).submit(userId, name, score, map, revives, run)` at game over → the write runs on its own thread: `Hiscores.drive` (three per-player boards, each a companion row then the ordered integer) → `Hiscores.driveTop` (the title's list of runs, merged with drive's all-time rows) → the listener hears the run's place. A place that shows boards makes a `RemoteEvent` and calls `handle.serve(remote)`; a client fires a board id and hears `(id, rows, rank, failed, best)`, each row `{ rank, name, score, level, revives }`.

### Edge cases
- A row or list entry stored before f0197 (no `revives`), or one with a junk value: reads as 0, never dropped for it.
- An attempt with bad revives: refused whole, nothing written (as a bad score is).
- Equal score and level with different revives: neither replaces the other, and their order is pickman's tie-break (user id; on the list, the instant and then the id).
- A prefix that is not valid: `Hiscores.names` and so `Boards.open` raise at once, in the adapter that opened it, not at the first write.
- The same prefix opened twice in one place: one handle, so one pending count for `BindToClose` and one cache.
- A player who leaves: their held best is dropped; a read that ends after they left is dropped (pickman's).
- Two titles in one place (the portal): separate caches, bests and pending counts; a title's reply never carries another's rows.
- A failed read: answered once, `failed = true`, with the rows held before (pickman's). A list that cannot be read is a failed all-time answer, not the per-player board (pickman's).
- A title with no list yet (every new title until its first listed run, the portal's first read of Snake, Invaders or Asteroids): the all-time answer is its per-player all-time board (pickman's rule for rows stored before d0124).
- A run outside the figures' ranges: refused, nothing written, one warning.
- A departed player, in a title whose steps are not pickman's: dropped at that title's window, not at 45.

### Scalability
Per finished run, per title, the requests are pickman's today: per board one companion `UpdateAsync` and one ordered `UpdateAsync` (3 boards: 6 writes, each gated on the request budget), one all-time page read and up to 10 companion reads to rank it, and one list `UpdateAsync`, all on the server's own thread with pickman's retries. Per served board key, at most one read per `CACHE_TTL` (15 s): the all-time board is one `GetAsync` of the list (plus one companion read per asking player's best, at most once per 15 s each); a day or week board is one page and up to 10 companion reads. One title's three boards cost at most 23 reads per 15 s however many players ask. Two budgets bind, per server and per minute (Roblox's documented limits): `GetAsync` at 60 + 10 × players, and `GetSortedAsync` at 5 + 2 × players. Of one title's 23 reads per 15 s, 2 are sorted reads (the day and the week page), so 8 sorted reads a minute, already above 5 + 2 × 1 with one player in the place (covered from 2 players); the 21 standard reads are 84 a minute (covered from 3 players). On top of that, each asking player's best is one standard read per 15 s (4 a minute per player), within the 10 a minute each player adds. The portal serving four titles is 4 × the shared reads: 32 sorted reads a minute (covered from about 14 players) and 336 standard reads a minute (covered from about 28 players), plus the per-player bests. Settling that (a snapshot per board, the architecture's E3) is f0206's; this issue keeps each title's cost where pickman's lobby has it today. Nothing replicates except the replies: 10 rows of five small fields per answer.

### Maintainability
A new title adds one entry to `HiscoreGames` (a prefix and the name of its figure), calls `Boards.open(<its prefix>)` from its server adapter, and passes its own leave window to `Hiscores.onStep`: no change to Hiscores or Boards. Store names are derived by one function, so no title can type another's name by hand, and a prefix collision fails `games.spec`. The pure module stays a copy of pickman's with the listed changes, so c0198 can delete pickman's copy and point pickman's adapters here with `Boards.open("")`, keeping its rows.

### Usability
A title's adapter needs two calls: `local boards = Boards.open(HiscoreGames.snake.prefix)` once, then `boards.submit(...)` at game over (`boards.pending()` for `BindToClose`, `boards.listen(fn)` for the rank line), or `boards.serve(remote)` in a place that shows boards. The types are exported (`Boards.Game`, `Boards.Listener`, `Hiscores.Names`, `Hiscores.BoardRow`); a bad prefix fails at `open`, the names are frozen, and `revives` is a required argument of `submit`, so a title cannot forget it silently (its type checker flags the missing argument).
