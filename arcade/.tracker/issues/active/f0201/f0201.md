# f0201: Paid play and receipts

## Problem
The user, 2026-10-31: "I want to branch out into multiple games, they will each have their own directory in the project: first person snake, first person asteroids. I also want a new project for a landing portal where you can scroll between the games and see the highscores for each, the same cost model remains but it shoudl show 5 robux for each game witha slash through showing it is currently on sale for 1 robux. highscores shoudl show how many revives were used. I want you to design a full fun playable game for both of those two new game ideas. I also want both snake and asteroids to be a two player game, snakes can even be n-player up to a high number just make the wold bigger. Snakes should have maps that once you have reached a certain length the game ends and we move to a new map, the first is empty, then one wall somewhere in the middle, then two, then three and so on. The walls can be vertical and horizontal but do not connect. for asteroids we could have a two player version where each player is attacking the aliens from opposing sides. You can shoot each other's barriers. the aliens would then come in from the side and and split into two groups that move toward either player". Then: "Add a third game first person asteroids." Decided with the user (2026-10-31): the 2-player aliens game is pure Space Invaders (`invaders`); Asteroids is its own game (`asteroids`); one Roblox experience with the portal as start place, replacing pickman's lobby; every board shows revives used; one free game per hour per game.

The approved design is `arcade/.tracker/architecture.md` (c0183). This issue owns these parts of it, as they are said there: **Technical skeleton**, "What moves into arcade", item 3 (PaidPlay and Receipts), and **Unknowns**, E4. The rest of it belongs to other issues (c0190's ownership table), listed under Non-goals.

What should happen:
- The cost model, shared by every game: **one free game per hour per game** per player, then **1 Robux per game**, and a **revive** (3 new lives, keeping score and progress) for **1 Robux**.
- The price is shown as **5 R$ struck through, on sale for 1 R$** (the charge is 1 R$); the badge text sits in one config table.
- Purchases go through Developer Products; the server grants exactly once (an idempotent `ProcessReceipt` installed in every place, with a receipt ledger; E4 settles a receipt retried in another place); the client never decides a grant; TeleportData is never trusted for an entitlement.
- The free-hour claim is atomic per player and game.
- **Playtests never charge**: the purchase screens show and accept their controls exactly as live, and nothing is deducted (f0145).
- Each run counts its revives for the boards (f0197).

## Solution
The cost model becomes one pure leaf, `Logic/PaidPlay`, over a per-title record (`free`, `plays`, `revives`, the last 50 receipt ids), and three thin server adapters in `ServerStorage.Arcade`: `Catalog` (every title's stores and product attributes), `Wallet` (each decision one `UpdateAsync` of that record, whose last transform call decides; the portal's passes; the run's revive count; the guards that bound one client's cost) and `Receipts` (installed by every place: `ProcessReceipt` for every title's products, prompts, and the test screen's server side). Two shared modules: `Prices`, the badge text table, and `TestPurchase`, the test purchase screen each place's client boots. E4 is settled by **one play product and one revive product per title**: a receipt names its title by its product, so whichever place Roblox processes it in grants it into that title's record, by user id, in the same write that remembers its id.

### 1. `arcade/src/shared/Logic/PaidPlay/init.luau` (new, pure, a leaf)
The word `game` is refused in Logic (pickman-arch rule 2), so a title is a `name` and a play is a `"play"`.
```lua
export type Mode = "live" | "test" | "closed"
export type Kind = "play" | "revive"
export type Start = "free" | "credit" | "buy"
export type Verdict = "play" | "back"
export type Record = { free: number?, plays: number, revives: number, receipts: { string } } -- one player in one title (key: user id)
export type Stored = { free: number?, plays: number, continues: number, receipts: { string } } -- as stored: f0145's record
export type Status = { free: boolean, nextFree: number?, plays: number, revives: number }
export type Entry = { name: string, title: string, store: string, testStore: string, play: string, revive: string } -- a catalog entry
export type Ids = { play: number?, revive: number? }
export type Product = { name: string, kind: Kind }
export type Title = { entry: Entry, mode: Mode, ids: Ids }
export type Config = { titles: { [string]: Title }, products: { [number]: Product } }
export type Prices = { struck: string, price: string, sale: string }
PaidPlay.FREE_SECONDS = 3600; PaidPlay.PRICE = 1; PaidPlay.RECEIPTS_KEPT = 50; PaidPlay.LIVE = "live"
PaidPlay.TEST_NOTE = "TEST PURCHASE: NOTHING IS CHARGED"
PaidPlay.KIND_TEXT = { play = "1 GAME", revive = "REVIVE: 3 NEW LIVES" }
PaidPlay.TEST_KEYS = { confirm = { "Return", "KeypadEnter", "ButtonA" }, cancel = { "Backspace", "ButtonB" } }
function PaidPlay.mode(raw: any, ids: Ids): Mode            -- "live" only for exactly "live" with both ids; "live" with one missing is "closed"; else "test"
function PaidPlay.store(entry: Entry, mode: Mode): string    -- test mode's own store, else the live one (closed included)
function PaidPlay.configure(catalog: { Entry }, raw: any, read: (string) -> any): Config -- every title's ids (whole positive numbers) and mode; an id two products share belongs to neither; names are lowercase letters, once
function PaidPlay.record(raw: any): Record                   -- read defensively; nil or broken is a new player's; the revives are the stored `continues`
function PaidPlay.stored(r: Record): Stored                  -- what every write stores: exactly f0145's four fields, the revives as `continues`
function PaidPlay.freeDue(r: Record, now: number): boolean   -- none yet, or the latest a full FREE_SECONDS ago; a clock behind waits; a non-whole instant never grants
function PaidPlay.status(r: Record, now: number): Status     -- for the portal's badge and timer (f0207)
function PaidPlay.start(r: Record, now: number): (Start, Record) -- the claim: a free start due (recording now), else one held play, else "buy" (nothing changes)
function PaidPlay.grant(r: Record, kind: Kind, receiptId: string): (Record, boolean) -- once per receipt id; the oldest id dropped past RECEIPTS_KEPT
function PaidPlay.refund(r: Record, kind: Kind): Record      -- a credit given back, outside the receipts (nothing retries a refund)
function PaidPlay.useRevive(r: Record): (boolean, Record)    -- one held revive, once
function PaidPlay.arrive(start: Start?, passed: boolean): Verdict -- a charge or a failed claim (nil) plays; "buy" plays only with the portal's pass
function PaidPlay.testLines(title: string, kind: Kind, prices: Prices): { string } -- "<TITLE>: <KIND_TEXT>", "5 R$ 1 R$ SALE", TEST_NOTE
function PaidPlay.testKey(name: string): ("confirm" | "cancel")?
```
Nothing mutates the record it is given. The stored shape is f0145's record exactly (design review 001 F3): a Pickman server on f0145's build and one on this library read and write each other's records, so neither loses the other's credits, and nothing needs migrating.

### 4. `arcade/src/server/Wallet.luau` (new, server adapter)
```lua
Wallet.WAIT_SECONDS = 5    -- a claim, a pass read or a read not back by then counts as failed
Wallet.READ_SECONDS = 60   -- a read within this of the last record this server saw answers from it
Wallet.RETRY_SECONDS = 6   -- after a read that failed, reads answer "down" with no store call for this long
Wallet.USE_SECONDS = 6     -- at most one revive write per player and title in this span
Wallet.KEEP_SECONDS = 600  -- a departed player's run count is dropped this long after they left
Wallet.PASS_SECONDS = 300; Wallet.PASS_MAP = "PaidPlayPass"; Wallet.MODE_ATTRIBUTE = "PaidPlay"
function Wallet.config(): PaidPlay.Config                 -- read once: ServerScriptService's PaidPlay and every catalog entry's two id attributes
function Wallet.mode(name: string): PaidPlay.Mode          -- a title's mode on this server (the place shows "store unavailable" when closed)
function Wallet.read(player, name): (PaidPlay.Record?, ("busy" | "down")?)
function Wallet.arrive(player, name): (PaidPlay.Verdict, PaidPlay.Start?)
function Wallet.useRevive(player, name): boolean?          -- true used, false none held, nil cannot tell
function Wallet.refund(player, name, kind): boolean
function Wallet.revives(player, name): number              -- this run's revives, for the boards (f0197)
function Wallet.pass(player, name): boolean                -- the portal's pass, only after a read that answered "down"
function Wallet.grant(userId: number, name, kind, receiptId: string): (boolean, boolean) -- written, new: into the live store
function Wallet.testGrant(player, name, kind): boolean     -- test mode only: into the test store under "test:<guid>"
```
- **One write per decision.** `arrive`, `useRevive`, `refund`, `grant` and `testGrant` are each one `UpdateAsync` of `tostring(userId)` in the title's store (`PaidPlay.store(entry, mode)`; `grant` always the live one), whose transform runs `PaidPlay` on `PaidPlay.record(raw)`, stores `PaidPlay.stored(...)`, and returns nil (no write) when nothing changes; the answer is the transform's **last** call's, since `UpdateAsync` may call it again on a newer value (another server's write). So the free-hour claim is atomic per player and title, and a receipt's credit and its id are one write.
- **Slots** (design review 001 F2): the per-player state (`seen`, the in-flight flags, the retry span, the pass allowance, this join's arrival) is kept **per Player object and title**, so one title's read, use or arrival never answers, blocks or bounds another's. Slots are dropped on `PlayerRemoving`, so a result that comes back after a leave lands in a dropped slot and a rejoin starts fresh.
- **The record seen** is refreshed by every read and write this server makes for the player and title: `read`, `arrive`, `useRevive`, `refund`, `testGrant`, and `grant` for a buyer on this server (design review 001 F1), except a live grant on a server whose title is in test mode, whose record seen is the test one. So a revive or a play just bought is usable at once.
- **The arrival** (the title's place calls it once the player is in): the claim `PaidPlay.start` at `os.time()`; then the pass is taken whatever the start (a MemoryStore hash map entry `<name>/<user id>`): a map that cannot be read, or whose read is not back within `WAIT_SECONDS`, counts as a pass ("Let all of them play"), and a late answer still removes the entry it found (design review 001 F4); then the verdict `PaidPlay.arrive(start, passed)`. The arrival is bounded by 2 × `WAIT_SECONDS`. A claim that fails, or is not back within `WAIT_SECONDS`, is nil and plays (G10: a failure costs the player nothing; a late write then charges what it charges, once). Charged **once per join**: a later call answers the first's; a call during the first's write waits for it and gets the same answer (one write). The arrival begins the run's revive count at 0. What a teleport carries is never read.
- **Revives**: `useRevive` uses one held revive (counted for the run: `revives` goes up), answers false with no write when the record seen holds none, and nil with no write while a use is under way (however long it takes), within `USE_SECONDS` of the last use's write, or when the store fails. A **written** revive refund takes one off the run's count, never below 0; a failed refund or a play refund leaves it (design review 001 F9). The run's count is kept by user id and title after the player leaves (a departed run is submitted after `PlayerRemoving`) for `KEEP_SECONDS`, counted from that player's latest leave, and starts again at their next arrival (design review 001 F14).
- **Reads** (the portal's status, f0207): nil and `"busy"` while a read for that player and title is under way; the record seen when it is less than `READ_SECONDS` old; nil and `"down"` when the store fails or is not back within `WAIT_SECONDS` (a read still yielding keeps the player busy until it ends); and then nil and `"down"` with no store call for `RETRY_SECONDS` after the failed call ended (design review 001 F8).
- **The pass** (design review 001 F7): `pass` writes the entry (for `PASS_SECONDS`) only when this server's last read for that player and title answered `"down"` (a failure, a time limit, or the retry span), once per such answer; after a good read, a busy one, or a pass already written, it answers false and writes nothing. This is the user's rule, a pass for a player let in "because its read of their record failed", made hard to misuse.
- **A player who already left** (design review 001 F10): `arrive` answers `"back"` and nil, `useRevive` nil, `read` nil and `"down"`, `pass` false, each with no store call and no slot; `refund` still writes (the credit is theirs); grants by user id are unchanged.
- **Failures**: each DataStore is opened on first use inside a `pcall` and kept (lesson pickman-arch/open-stores-guarded); a store that cannot be opened is a failed call on every path, except a **test** store (design review 001 F5): in test mode, where the test store cannot be opened (a Studio playtest from a file, or with API access off), Wallet keeps a per-server stand-in for it with the same `UpdateAsync` and `GetAsync` contract, so arrivals, test purchases and revives go through in a playtest; its credits last as long as that server. A live store never has a stand-in: a real receipt still answers `NotProcessedYet` and a live arrival claims nothing. A title not in the catalog is an error (a typo must not read as a free start).
- **Engine surface** (design review 001 F11; what the specs' stub engine provides): time limits are `task.delay`; a wait is `coroutine.yield` resumed by `task.spawn`; handlers are `task.spawn`ed; a player is present while `Parent ~= nil`; a buyer is found with `Players:GetPlayerByUserId`; the clock for the bounds is `os.clock()` and for the free hour `os.time()`. The stub also serves `task.defer`, `task.wait` and `Players:GetPlayers`.

### 5. `arcade/src/server/Receipts.luau` (new, server adapter)
```lua
export type Handlers = {
	granted: ((player: Player, name: string, kind: PaidPlay.Kind) -> ())?,             -- a new grant for a player on this server
	closed: ((player: Player, name: string, kind: PaidPlay.Kind, bought: boolean) -> ())?, -- a purchase screen closed
}
Receipts.FOLDER = "ArcadePaidPlay"; Receipts.REMOTE = "TestPurchase"
function Receipts.start(handlers: Handlers?): boolean -- once per server; a second call does nothing and answers false
function Receipts.ask(player, name, kind): boolean     -- live: PromptProductPurchase of the title's id; test: the test screen; closed: nothing
```
- `start` makes `ReplicatedStorage.ArcadePaidPlay.TestPurchase` (a RemoteEvent) and sets `MarketplaceService.ProcessReceipt` (Roblox: "This can only be done once by one server-side script", E2).
- **ProcessReceipt**: the product id maps through `Wallet.config().products` to its title and kind; an unknown product, a purchase id that is not a non-empty string, or a player id that is not a number answers `NotProcessedYet`. Otherwise `Wallet.grant` by user id (the buyer need not be on this server); a failed write answers `NotProcessedYet`; else `PurchaseGranted`, and a **new** grant for a player on this server whose title is not in test mode is handed to `granted` (spawned, so the answer never waits on the place). A real receipt is kept in the live record even in test mode (real Robux were charged), and is not handed to a test-mode place, which reads the test record. A closed title's receipt is granted: it was charged.
- **Test mode**: `ask` opens the test screen (`FireClient(player, "open", PaidPlay.testLines(title, kind, Prices))`) and records it as the player's one open screen (a second `ask` while one is open answers false); the client's `"confirm"` for that open screen grants with `Wallet.testGrant` and then reports `closed(…, written)` and, when written, `granted`; `"cancel"` reports `closed(…, false)`; anything else, or any answer with no screen open (another player's, after a cancel, in live mode), does nothing. The open screen is forgotten on an answer or a leave.
- **Live mode**: `PromptProductPurchaseFinished` of a known product, for a player on this server, reports `closed(player, name, kind, bought)`; it never grants (Roblox: "Do not use the PromptProductPurchaseFinished event to process purchases").
- Handlers hear only players still on the server, and are `task.spawn`ed. The place's adapters hear one client message, the test screen's answer, on one `OnServerEvent` connection; nothing assigns an `OnServerInvoke` (pinned by spies, design review 001 F11).

### Authority and what a client could lie about
A client sends one thing: the test screen's `"confirm"` or `"cancel"`, honoured only for a screen this server opened for that player, in test mode, into the test store. It never names a product, a price, a title or a receipt. Every credit is a server write: a Roblox receipt (server-only `ProcessReceipt`), a test confirm, or a refund the place asks for. An arrival reads the store, never TeleportData, so a join that claims to have paid is a "buy"; the arrival's verdict is the server's. `src/server` is ServerStorage, which never replicates.

### Edge cases
- Two servers at once (a receipt processed while the arrival claims): both are `UpdateAsync` of one key; each transform sees the other's write, and the last call decides.
- A player who leaves during a write: the write completes (credits stay), the place hears nothing, the slot is dropped.
- The clock: whole seconds (`os.time()`); an instant behind the stored free start (another server's clock) waits.
- A title whose ids are misconfigured: closed, sells nothing, grants nothing free; free starts and credits still work. An id two products share: both closed.
- A receipt for a title whose place the player is not in: credited to that title, used at its next arrival or revive.
- A call made for a player who already left (a place that yields before `arrive`): nothing claimed, read, used or passed; a refund is still written.
- Two titles for one player at once (the portal's four cards): each title has its own slot, so neither's read, use, bound or arrival touches the other's.

### Scalability
Per player and title: the arrival one `UpdateAsync` and at most one MemoryStore `GetAsync` (+ one `RemoveAsync` when a pass is there); each purchase one `UpdateAsync`; each revive used one; a pass one `SetAsync`, only after a failed read. Reads: at most one `GetAsync` per `READ_SECONDS` (60) while the store answers, and at most one per `RETRY_SECONDS` (6) while it fails (a failed read holds "down" with no call for that span, design review 001 F8), so the portal's four cards cost at most 4 reads a minute per player when the store is up and 40 a minute when it is down, whatever the client asks. Revive writes: at most one per `USE_SECONDS` (6) and none while none is known held, so one client spamming its revive costs at most 10 writes a minute. A client asking every frame therefore stays near its own share of the server's budget (about 60 + 10 × players a minute per request type) in the common case; during an outage the read bound caps each player at 10 calls a minute per title. Nothing per frame, nothing per step. Replicated: one folder and one RemoteEvent per place, one message per test screen. Memory: a slot per player and title on the server (dropped on leave), one number per run's revive count (dropped `KEEP_SECONDS` after the player leaves), and in a test-mode server without DataStore access, its stand-in's test records.

### Maintainability
A new title is one `Catalog` entry and two Developer Products; no code changes, no branch on a name. The price words are `Prices`; the hour, the price and the receipts kept are `PaidPlay` constants; the adapters' bounds are `Wallet`'s. A new product kind (a pass, a boost) is one `Kind` value, one catalog attribute and one branch where it is used.

### Usability
- **Player**: a purchase is granted once and never lost (a credit kept when it cannot be used at once); a failing store never charges them for nothing; in test mode the screen shows exactly what is bought and its price, says nothing is charged, and takes the same choice by tap, keyboard and controller.
- **Developer** (a title's adapters): `Receipts.start(handlers)` once per place; `Wallet.arrive(player, name)` on arrival (act on "back"); `Receipts.ask(player, name, kind)` to buy; `Wallet.useRevive` and `Wallet.refund` for the revive; `Wallet.revives` at the game over; `Wallet.read` with `PaidPlay.status` for the portal's badge, and `Wallet.pass` when a read answered "down" (it refuses otherwise); `TestPurchase.start()` in each client and `TestPurchase.isOpen()` for a place's own key handlers. The name is the only per-title argument, and a wrong one is an error.

## Unknowns & experiments
- **E1 (architecture E4). Is a receipt retried in another place of the experience?** Doc check (2026-11-15, MarketplaceService and Developer products pages): the samples say a receipt not granted "tries again next time the user joins the game" and "is redelivered later or the next time they join a server"; neither says which place. The design holds either way: every place installs the same Receipts with the whole catalog, a receipt names its title by its product (one play and one revive product per title), and the grant is a credit in that title's record by user id, so a receipt processed in the portal, in another title's place or in a later session is granted once into the right record and used at the next arrival or revive. The pending-intent alternative is rejected: the intent and the credit would be two writes, and a lost or overwritten intent would grant the wrong title. Pinned: receipts :: every title's receipt is granted in any place…, a buyer not on this server…. Left for Beta (f0169's live publish): a real purchase retried after a teleport (OC1).
- **E2. ProcessReceipt's contract.** Doc: "This can only be done once by one server-side script"; "Do not use the PromptProductPurchaseFinished event to process purchases"; the sample grants "exactly once, even if the same receipt is delivered more than once" with a purchase history in an `UpdateAsync`. Roblox does not order the purchase screen's close and the receipt (f0145 E2), so `closed` and `granted` are separate handlers and a title's revive screen waits for the grant (f0215, f0219, f0223). `BindReceiptHandler` (with `Enum.ReceiptDecision`) is on the same page, its interaction with ProcessReceipt undocumented and ProcessReceipt not deprecated: not used; `process` maps one-to-one onto it if Roblox ever retires ProcessReceipt.
- **E3. UpdateAsync** may call the transform more than once, on a newer value, and a nil answer writes nothing (Roblox's DataStore docs; f0145 E2). The stub engine writes a competing value before the transform and can call it twice on the stale value first; a blind read-then-write fails those cases (W9 below).
- **E4. Prototype and specs** (scratch worktree `proto-f0201` from origin/main of 2026-11-15, `experiments/prototype.patch`, 1091 lines of `src` with a one-case unit spec; rerun after design review 001): the six acceptance specs pass on it, 109 cases; `./zn check f0201` there passes 7/7; `./zn promote-check f0201` there type-checks every spec clean; `arcade/check.sh --affected` passes format, lint, both type passes and the build, its only failure the new unit spec's missing watch file, which `./zn finish` writes. - **E5. Mutation check** (`experiments/mutants.py`, its output `experiments/mutants.out`): every row below was applied to the prototype one at a time and its spec run; all 115 fail on an assertion (none on a load error; the script reports a refused run as NO RUN, and none was). - **E6. Literal types across a require.** The Roblox type pass widens a literal-union return (`Verdict`, `testKey`'s) to `string` at the caller, so `Wallet` casts at the call (`:: PaidPlay.Verdict`) and `TestPurchase`'s `send` takes a string; the patch has both.
- **E8. Fallback taken: test mode's per-server stand-in (§4, Failures); live mode has none. Pinned by wallet :: in test mode a test store that cannot be opened has a stand-in…, and in live mode an unopenable store has no stand-in…. Not proven here: whether Studio with API access off throws at `GetDataStore` (the lesson says so, from f0148) or only at each request (Roblox's "Studio access to API services" error). Pass: the first Studio playtest of a place that boots the library (f0208's or c0202's Observed steps) buys a test revive with API access off. Fallback if it fails: in test mode only, a request error that names Studio API access also switches that test store to its stand-in (a follow-up defect against this feature, with its own case).

## Acceptance criteria

### Checked
- AC1: PaidPlay: one free start per rolling hour per title and player (recorded at the claim; a clock behind waits; a non-whole instant never grants), else one held play, else buy with nothing changed; a receipt id grants once and the last 50 are kept, oldest dropped first; a refund is its own credit outside the receipts; a held revive is used once; a stored record is read defensively and stored in f0145's shape (exactly free, plays, continues holding the revives, receipts); an arrival plays when charged or when its claim failed, and a buy only with the portal's pass; nothing mutates its input.
- AC2: the configuration: a title is live only for exactly "live" with both its product ids, closed for "live" with one missing or bad, else test; an id two products share belongs to neither; each mode has its store (closed keeps the live one); catalog names are lowercase letters, once; the shipped catalog holds Pickman (f0145's names), Snake, Invaders and Asteroids with distinct stores and attributes; the badge text is one frozen config table, "5 R$" struck, "1 R$", "SALE", naming the charge; the test screen prints the title and product, the badge and "TEST PURCHASE: NOTHING IS CHARGED", and takes Return, KeypadEnter, ButtonA to buy and Backspace, ButtonB to cancel.
- AC3: Wallet on a stub engine: per player and title, the arrival claims the free start due, else a held play, once per join, in one UpdateAsync of the mode's store whose transform's last call decides and which writes f0145's shape; a second arrival waits for the first; a failed or slow claim plays; the portal's pass is taken on every arrival within WAIT_SECONDS (a slow or unreadable map counts as a pass, a late answer still removes it) and is written only after a read that answered down, once per such answer; join data is never read; a revive is used once and counted for the run (less each written revive refund, never below 0; kept KEEP_SECONDS after the latest leave; reset at the next arrival), with one write at a time, none while none is known held and at most one per USE_SECONDS; reads are busy during a read, answered from the record seen within READ_SECONDS, down when failed or slow and then for RETRY_SECONDS with no store call, and keep nothing for a player who left; calls for a departed player claim, read, use and pass nothing, and a refund is still written; in test mode an unopenable test store has a stand-in, in live mode none; an unknown title is an error; the mode is read once.
- AC4: Receipts on a stub engine: a receipt of any title is granted once into its own live record by user id, wherever processed and whether or not the buyer is on the server, PurchaseGranted only after the write, NotProcessedYet for an unknown product, a bad purchase or player id, or a failed write; another server's grant counts once; a grant, a test grant and a refund refresh the record seen, so a purchase is usable and shown at once, except a real receipt on a test-mode server, which stays live and is not handed on; a closed title's receipt is granted; ask prompts Roblox in live mode, opens the test screen in test mode, nothing when closed; a test confirm grants into the test store under its own test id, only for the one screen this server opened for that player, reports the screen closed and then the grant; cancels, stray answers, other players' confirms and screens left behind by a leave grant nothing; Roblox's closed screen is reported, never granted; start runs once; the place hears one client message on one connection and never reads join data.
- AC5: the test purchase screen on a stub client: start returns at once; the server's text lines with BUY and CANCEL, centred in the middle half inside the safe insets, above the place's screens; a tap, Return, KeypadEnter or ButtonA sends confirm and Backspace, ButtonB or a tap on CANCEL sends cancel, on the press, and closes it; its keys are bound at priority 3000 only while it is open, and isOpen says whether it is; a second open replaces the first; a malformed open shows nothing; it starts once.
- AC6: in the built library place PaidPlay is a Logic leaf, Prices and TestPurchase are shared modules, Wallet, Receipts and Catalog are server-only modules; nothing in ReplicatedStorage.Arcade requires a server module; architecture.md declares the feature, installed by every place, with no dependency edge.
- AC7: PaidPlay and its unit specs exist; Logic stays engine-free, every dependency is declared, and every feature has unit specs.
