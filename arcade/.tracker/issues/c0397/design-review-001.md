### F1 [medium] narrow.py, the only judge of AC1, is outside the approval contract, so it can change after `./zn approve` without the approval going stale
Where: `acceptance/narrow.py` (the issue's acceptance holds no `*.spec.luau`); `z-nile/engine/approval.luau:20-50` (`walk` collects only names that match `%.spec%.luau$`, and with none found `collect` falls back to the promoted folder, which also has none); `z-nile/engine/readycheck.luau:240-256` (`readycheck.specs`, the same choice).
Evidence: for c0397 the contract's `specs` set is empty, so `approval.md`'s hash covers only the document's sections and `check.sh`. Suppose `narrow.py` is replaced after approval with a file that does `import sys; sys.exit(0)`, or its anchors are widened. Then `ready` and `done` (`approval.refusal`) still pass, AC1 goes green for any edit to the two specs, and the design's prose blob ids (4d20b213, 3e9e5007) are compared by nothing. z-raft's `grouped:` hash does cover `acceptance/` (`raftplan.luau:361-366`), but it is taken at rafting, after approval, so it records whatever narrow.py is by then. The code review's sequestration diff catches only edits made on the execution branch. c0386 and c0302 had a `.spec.luau` beside their `narrow.py`, so their contracts at least bound the spec. c0397's folder holds nothing else, and portal's c0392 is in the same position.
Critique: the human's approval is supposed to bind the acceptance the reviewer read (the chore checklist's "Guards … fail closed"). The tempting fix is "it's the engine's bug, leave it". The issue would then be approved on a contract that omits its entire AC1.
Consequences: if c0397's `check.sh` pins narrow.py's sha256, any later edit to narrow.py also needs an edit to check.sh, which the contract hashes, so the approval goes stale as it should. After `./zn done` the file moves byte for byte, so the digest still holds at the promoted path. A compaction that renumbers f0201 or c0397 would move the digest, but it moves the blob pins inside narrow.py too, which already stop for a re-prep. AC1 is meant to be red after the landing anyway. The engine-side fix (hash every file under `acceptance/`) changes the contract of every approved item that has a non-spec helper, so it needs its own migration and is not this chore's to make.
Recommendation: in check.sh, make AC1's command verify narrow.py's digest before running it, inside `check` and failing closed, for example `bash -c 'test "$(shasum -a 256 < "$A/narrow.py" | cut -d" " -f1)" = <sha256> && python3 -I "$A/narrow.py" "$ZN_ROOT"'` (export `A`, or inline the path). Add a row N13 to the Rules and mutants table, "narrow.py replaced by a stub that exits 0 → AC1 red", run through check.sh rather than narrow.py alone. The lead should also capture a z-nile defect: `approval.collect`/`readycheck.specs` leave every non-spec file under `acceptance/` out of the contract (c0392's narrow.py-only folder; the `.py` helpers of c0239, c0269, c0302 and c0386). Its fix needs a migration for existing approvals.
