### F1 [high] The generic `Boards` adapter's copied server behaviour is pinned by almost nothing: nine plausible wrong adapters pass every f0197 spec
Where: Design, Modules item 2 (`serve`: "The read, the shared cache …, the waiters, the failure wait, the sweep of old periods and the per-player best … are pickman's"); E4 ("Pickman's adapter specs (`f0024/adapter`, `f0026/adapters`, `d0124/adapters`) test pickman's two modules and its client views, so they are not copied"); Edge cases ("A failed read: answered once, `failed = true`, with the rows held before"; "a read that ends after they left is dropped"); Rules and mutants (M18 to M26 are the adapter's only rows); `acceptance/boards.spec.luau` (11 cases).
Evidence: each mutant applied to the prototype's `arcade/src/server/Boards.luau`, then all 17 spec files run: **every one SURVIVED with 141 passed, 0 failed**:
- X4: the all-time board with no list stored fails (`error("no list", 0)` after `topRows` gives nil) instead of answering the per-player board.
- Y1: the adapter's page read tries size 10 only (`for attempt = 1, 1`): no size-50 retry.
- Y2: a companion row that cannot be read is skipped (`lookup` returns `nil, nil` on error), so a short board is answered as healthy and cached. This is the defect c0128/R0011 fixed.
- Y3: a request that arrives while a read is in flight is never answered (it is not added to `waiters`).
- Y4: the failure wait is ignored (`nil` passed to `Hiscores.lookup` for `failure`), so every request during an outage reads again.
- Y5: the `get` budget is mapped to `OrderedRead`.
- Y6: a player who left (`Parent == nil`) is still sent an answer.
- Y7: `pending` is never released when a write throws, so `BindToClose` waits the full `CLOSE_WAIT`.
- Y8: a failed read answers `{}` instead of the rows held before. That is the design's own Edge case, and the same mutant as f0026's "window-empty-rows".

Most cases in the specs E4 calls pickman's are about server behaviour this merge copies, not about client views: `f0024/adapter.spec.luau:307` (each update preceded by its own store's budgets), `:334` (pending also when the drive fails), `:350` (size 10 rejected → once at 50), `:367`; `f0026/adapters.spec.luau:525`, `:578` (a request during a read, one answer each), `:605` (an outage costs three reads in ten seconds), `:630`, `:653` (an unreadable companion fails the read), `:680` (a waiter who left), `:747`, `:776`; `d0124/adapters.spec.luau:590`, `:601`, `:632` ("with no list stored, the all-time answer is the per-player board, as before"), `:704`, `:722`, `:736`, `:751`, `:763` (the held-best rules).
Critique: AC4 ("serves its boards on a given remote") passes with an adapter that breaks every one of these. Every place will use this adapter, and c0198 then deletes pickman's adapters and their promoted specs. After that, nothing in the repository pins these rules, even though R0011, c0128 and d0124 took several review rounds to settle them. X4 is not a corner case: every new title starts with no list, so the portal's first all-time read of Snake, Invaders or Asteroids takes that path. The tempting fix is two or three more cases for the mutants named here.
Consequences: porting the cases needs a stronger stub in `boards.spec`: a read that can be held (a `GetAsync`/`GetSortedAsync` that yields on a coroutine until released, the way `task.spawn` already can be held), a clock that can be set (it is fixed at `FRI` today), a companion `GetAsync` that fails for one key, a store that rejects size 10, a recorded budget request type per call, a player whose `Parent` is nil, and a submit whose drive throws. The cases must observe behaviour, not match source text (zz-test/source-pins-name-what-the-design-names). c0198's design will have to name pickman's three adapter specs as Overrides and point at these cases as their replacements.
Recommendation: in `boards.spec`, port every server-side case of `f0024/adapter`, `f0026/adapters` and `d0124/adapters` listed above to the generic adapter on the strengthened stub. Leave out only the client-view cases (lobby screen, FlowView, Ranks, place files), each named in E4 with the reason. Add the Edge case "a title with no list yet (every new title until its first listed run): the all-time board is its per-player board". Add one Rules and mutants row per ported rule, with X4 and Y1 to Y8 as their mutants, run them through the mutation runner (after F3's fix) and record the kills in E6.

### F2 [high] `bestRun`'s named-run branch can write `revives = 0` and pass AC2; the only case covers the branch that rows written since d0124 no longer take
Where: Design, Modules item 1 ("`bestRun` takes `revivesOf(row.revives)`"); Rules row M9; `revives.spec` "a per-player best merged into the list brings the row's revives" (its companion has no `run`).
Evidence: mutant X1 (in the `if type(row.run) == "string" …` branch of `Hiscores.bestRun`, `revives = 0`) SURVIVED, 141 passed. `top.spec`'s whole-object expectations all have `revives = 0`, so they cannot see it either. Every per-player row written since d0124 names its run (`commit` stores `run`/`at`), so the named branch is the one that runs in practice. Scenario: Ada's run uses 2 revives, and `drive` writes her rows naming the run. `driveTop` then fails its three tries (the budget is spent). Bea's next run merges the bests from `drive`'s read, and Ada's run reaches the list through the named branch. Under X1 the all-time board shows that run with 0 revives.
Critique: AC2 ("every row read shows them … list entries, bests") passes with a wrong implementation. The likely fix is a third assertion in the same case. But the case's companion has no `run`, so it can only reach the unnamed branch.
Consequences: none new. The rule that a stored copy wins over a best with the same id stays as designed (a list entry written by today's build keeps 0, and the design accepts that, since no run has revives before f0186).
Recommendation: in `revives.spec`, give the merged-best case a second companion that names its run (`run = "2:1:1:j", at = 1, revives = 4`), and expect the merged entry's `id` to be `"2:1:1:j"` with `revives = 4`. Add a Rules row for it (M9b: the named branch writes 0), run it, and record the kill.
Lesson: zz-test/seed-every-enumerated-case

### F3 [high] `experiments/mutants.py` writes its mutants into whichever checkout it runs in, and leaves one behind when its time limit stops it
Where: `experiments/mutants.py:5` (`P=os.path.abspath(os.environ.get('PROTO', '.'))`), and `:108`–`:120` (writes the source file, then restores it in `finally`); E6; Implementation step 7 ("`experiments/prototype.patch` is the prototype these steps were proven on").
Evidence: in my scratch clone, `env -u PROTO ./zn run --time 2 -- python3 arcade/.tracker/issues/f0197/experiments/mutants.py M28` printed `bounded: stopped at the wall-clock limit (--time 2 s): python3`, and afterwards `arcade/src/shared/Logic/Hiscores/init.luau:86` read `Hiscores.LEAVE_STEPS = 44`. The `finally` never ran, because SIGTERM ends Python without running it. Once f0197 is done, the main checkout and the executor's raft worktree both hold that file. Run there with no `PROTO`, or with `PROTO` naming them, the script edits real source, and an interrupted run leaves a mutant in it.
Critique: zz-review item 9: "Every command that changes anything must run in a fixture under `.cache/<unique name>` with its own repository". This script edits a checkout it is pointed at, and its default target is the current directory. The tempting fix is a guard on `PROTO` ("refuse unless it is a worktree"), but the real checkouts pass that test.
Consequences: a script that builds its own clone needs the acceptance specs from wherever they live: the item folder before `done`, `arcade/tests/acceptance/f0197` after it. Its mutant patterns are written against `prototype.patch`'s text, so they stay valid on a clone built from that patch.
Recommendation: rewrite the script so it takes no directory. It makes a `mktemp -d` outside any checkout, `git clone --shared`s the repository into it at the recorded base (3290615a), applies `prototype.patch`, and copies the item's `acceptance/` folder in. It runs each mutant there through `./zn run --time`, turns SIGTERM into `SystemExit` so cleanup always runs, and removes the directory by a validated path at the end. Re-run the 33 mutants (and F1's and F2's new ones) with it, and update E6.
Lesson: z-design/prep-experiments-run-in-standalone-clones

### F4 [medium] The library's run policy keeps pickman's session shape as constants: the 45-step leave window is pickman's dying pause in pickman's ticks, and the "revives are final at the first GameOver" contract is not stated
Where: Design, Modules item 1 ("every function and constant kept with its behaviour"; `onStep` takes `event.revives`); Maintainability ("A new title adds one entry … no change to Hiscores or Boards"); `acceptance/leave.spec.luau` (drops `Game.CLASSIC_CONFIG.dyingTicks` and pins a bare 45); arcade-arch rule 2.
Evidence: `pickman/src/shared/Logic/Game/init.luau:42` `dyingTicks = 45` and `pickman/src/shared/Logic/Session/init.luau:153` `TICK_RATE = 30`, so the window is 1.5 s of pickman's ticks. Snake steps at 4 tiles/s on map 1 and faster on later maps, waits 1.5 s on a death and holds a 10 s revive offer (`snake/.tracker/game-design.md:15`, `:34`–`:35`), so its window in its own steps is another number. A probe on the prototype (`.cache/review-f0197-1/probe.luau`, run from the prototype's `arcade/` through `./zn run`) printed: `first 30 0`, then `second (same run, after a revive) nil (refused)`, and `a departed player's run dropped after steps: 45`. So a title that emits GameOver when its revive offer opens records revives 0, and after a revive its run's real final score is refused by `once`.
Critique: rule 2 says per-game differences are parameters. This one is a library constant tuned to one game, and the Maintainability claim does not hold for a title whose step is not pickman's. The tempting fix is a comment saying "45 is pickman's". That leaves every other title's window wrong.
Consequences: `leave` and `onStep` gain an argument. The copied `leave`/`run` specs (sequestered, so edit them now in prep) call the new signature. c0198 passes pickman's `dyingTicks`, and f0215, f0219 and f0223 each name their own window. The GameOver contract then binds f0186 and each title's design.
Recommendation: take the window as a parameter: `Hiscores.leave(stepsWaited, sawOver, window)` and `Hiscores.onStep(state, events, here, window)`, with `LEAVE_STEPS = 45` kept and documented as pickman's value. State in the Design, and in `onStep`'s comment, that a title's `GameOver` event is the run's end after any revive offer has closed, that a revive continues the same run, and that the event's `revives` is the run's final count. Cases: `leave` honours a given window (44 keep and 45 drop with 45; 9 keep and 10 drop with 10), and `onStep` passes its window on. Add a Rules row for each, with a mutant that ignores the window.

In `boards.spec`, Snake and Asteroids each `listen`, and Asteroids' run is heard only by Asteroids' listener. Add a Rules row for each, record the kills, and give each Edge-case sentence its row (z-design/spec-design-correspondence).

### F6 [low] A refused run is silent, and the figure's floor is not stated to the titles
Where: Usability ("hard to misuse"); `HiscoreGames` (it names the figures but not their range); `Boards.submit`.
Evidence: the probe printed `level 0 valid? false`. A title whose progress figure starts at 0, or whose revives counter goes wrong, gets nothing written, no listener call and no warning (`drive` returns `wrote` all false and `topRun` returns nil). Today's game designs start at map 1 and wave 1, so this is latent.
Recommendation: state it in the Design and in `Boards.submit`'s doc: the progress figure is a whole number from 1 and revives a whole number from 0. Have `submit` warn once with `[arcade] hiscore run refused (<ordered name>)` when `Hiscores.valid` refuses the attempt, with a `boards.spec` case on the stub's existing `warnings` counter.

### F7 [low] Scalability compares the portal's reads only with the GetAsync budget, and "however many players ask" contradicts the per-player best reads in the same paragraph
Where: Design, Scalability.
Evidence: of the 92 reads per 15 s, 8 are `GetSortedAsync` (the day and week page of each of 4 titles), which is 32 a minute. Roblox's documented server budget for sorted reads is 5 + 2 × players a minute, so it is the tighter one: about 14 players before it covers 32. One title's 2 sorted reads per 15 s (8 a minute) already exceed it with one player. The same sentence says 23 reads "however many players ask", then adds a read per asking player's best.
Recommendation: E3 stays f0206's. State both budgets and the per-player term so f0206 starts from the right constraint.

## Candidate lessons (for the lead to harvest)
- z-design: when a design copies or merges a module, every case in that module's promoted specs that tests behaviour the new module keeps is ported to the new module's specs, or named with the reason it is dropped. "They test the old module" is not a reason. Why: f0197 dropped pickman's three adapter specs as a group, and nine wrong generic adapters passed (F1). Check: for each promoted spec of the copied module, which cases still describe the new module, and where is each one now?
- z-design: a constant copied into the library from one game (a window in that game's ticks, an event name) is a per-game parameter unless the design says why every game shares it. Why: f0197 kept pickman's 45 dying ticks as the leave window for every title (F4). Check: for each constant the copy keeps, is its unit or its value one game's?
