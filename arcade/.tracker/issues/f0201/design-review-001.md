### F1 [high] Nothing pins that a grant refreshes the record this server last saw: a Wallet that skips it refuses a revive the player has just bought, and passes all 88 cases
Where: f0201.md §4, Revives ("every read and write here refreshes it, a grant here included"); Rules and mutants (no row); wallet.spec and receipts.spec (no case)
Evidence: No case calls `useRevive` or `read` after a grant. receipts.spec never calls `arrive`, `read` or `useRevive`, and wallet.spec never processes a receipt. Every `useRevive` there runs on a record seeded straight into the store. Delete the prototype's two `seeGrant(...)` calls (in `Wallet.grant` and `Wallet.testGrant`) and every case still passes. Then, in live mode: seed Pickman's record `{ free = NOW - 7200 }` for user 7, call `arrive` (the record seen holds 0 revives), then `w.receipt(7, 102, "rv-1")`. The answer is PurchaseGranted, the store holds 1 revive, and `granted` is handed on. But `useRevive(p, "pickman")` answers `false` and writes nothing, because the record seen still says 0. Test mode does the same after an `ask` and a `"confirm"`. The opposite mistake also passes: refreshing the record seen with the live record in test mode, where the record seen is the test one (the prototype skips it when `t.mode == "test"`).
Critique: This is the main flow of every revive screen (f0215, f0219, f0223): none held, then `ask`, then `granted`, then `useRevive`. A player who has paid 1 R$ is told they hold no revive, and the run ends with the credit unused. The fix the author will reach for is one case for the live grant.
Consequences: The refresh has three writers (`grant` for a player on this server, `testGrant`, `refund`) and one exclusion (a live grant in test mode refreshes nothing). Each needs its own case, or the next one can be dropped the same way. The portal reads from the same cache (READ_SECONDS), so a play bought in the portal must show in a read straight away.
Recommendation: Add these cases. (a) Live: `arrive` with 0 revives, a receipt for the title's revive product, then `useRevive` answers true, with one more write and `revives(p) == 1`. (b) Test: `ask` a revive, `"confirm"`, then `useRevive` answers true. (c) After a use and a `refund`, the next `useRevive` past USE_SECONDS answers true. (d) The portal: a `read` (0 plays), a receipt for a play, a second `read` within READ_SECONDS shows 1 play with no new GetAsync. (e) Test mode: a live receipt arrives, and a `read` within READ_SECONDS still shows the test record. Add mutant rows: `grant` does not refresh, `testGrant` does not refresh, `refund` does not refresh, a live grant refreshes in test mode.

### F2 [high] Nothing pins that the per-player state is kept per title: a Wallet with one slot per player gives the portal's four cards one title's record
Where: §4, Slots ("the per-player state (`seen`, the in-flight flags, this join's arrival) is kept per Player object"), Reads; wallet.spec "each title keeps its own record: a free start in one leaves another's due"
Evidence: Every `read`, `useRevive` and `refund` in wallet.spec names `"pickman"`. The only other title is one `arrive(p, "snake")` (line 430) and one `pass(p, "snake")` (line 553). In "each title keeps its own record", the Pickman arrival after the Snake one is checked only by `h.results[2] == "free"`. An arrival cached per player alone returns Snake's cached `("play", "free")` without writing, and passes. The Slots bullet itself says "per Player object", not "per player and title". In such a Wallet the portal (f0208, f0207) reads Pickman `{ plays = 2 }`, then reads Snake within READ_SECONDS and gets Pickman's record back. Four card reads at once get three `"busy"` answers.
Critique: The portal's PLAY decides from `read` whether a free game is due or a play is held. A cache that ignores the title shows the wrong badge. It then prompts a 1 R$ purchase when that title's free game is due, or teleports a player who holds nothing there, only for them to be sent back.
Consequences: Keying by title also covers the in-flight read flag, the arrival cache and the revive guards (`using`, `usedAt`). The drop on `PlayerRemoving` has to clear every title's slot.
Recommendation: In §4 Slots, say "kept per Player object and title". Cases: (a) in "each title keeps its own record", also assert that the Pickman record was written (`rec(w, TEST, 7).free == NOW`, `w.writes == 2`); (b) seed Pickman `{ plays = 2 }` and Snake `{ free = NOW - 60 }`, then read both within READ_SECONDS: each answers its own record, and `reads == 2`; (c) while a Snake read is held, a Pickman read is not busy; (d) a Pickman revive use does not start Snake's USE_SECONDS. Add a mutant row: slots keyed by player only.

### F3 [medium] The f0145 carry-over works one way only: arcade writes `revives` without `continues`, so a Pickman server still on f0145 loses those credits and then drops arcade's
Where: §1 `PaidPlay.record`; §3 Catalog ("f0145's names, so a record ... carries over"); Order & dependencies, f0145
Evidence: f0145's stored record is `{ free: number?, plays: number, continues: number, receipts: { string } }`, and its `Pay.record` reads `continues` only (f0145.md §1 on `origin/prep-paid-play-and-continues`). f0201 writes `{ free, plays, revives, receipts }` into the same `PaidPlay` and `PaidPlayTest` stores. f0208, the portal that boots Receipts with Pickman's entry, depends on `[f0199, f0201, f0205]`, not on c0202. And a publish leaves old servers running. Scenario: a Pickman continue is bought in f0145's place, and its receipt is retried in the portal (E1). Arcade grants it as `revives = 1` with no `continues`. f0145's Pickman then reads 0 continues and offers a purchase, and its next write stores `continues` without `revives`. The paid credit is gone.
Critique: The design cites z-design/new-rules-migrate-existing-work but answers only its first half. That lesson's R0044 note covers exactly this: a migration is safe only when nothing keeps writing the old shape after it. The fix the author will reach for is ordering c0202 before the portal, but old f0145 servers outlive that publish too.
Consequences: Once both builds store the same shape, nothing needs migrating (nothing has written `revives` yet). The case "a record f0145 wrote keeps its continues as revives; revives win when both are there" and mutant Y14 change with it.
Recommendation: Store the revive credit under f0145's field name `continues` in every title's record. The Luau `Record` type can keep `revives`, but `PaidPlay.record` reads `continues` and every transform writes exactly f0145's four fields. Each build then reads the other's writes. Cases: a record Wallet writes has `continues` and no `revives`; f0145's shape round-trips unchanged; the stored table has exactly those four keys. Revise Y14.
Lesson: z-design/new-rules-migrate-existing-work

### F4 [medium] The arrival's pass read has no time limit, so a slow MemoryStore holds a player who has already arrived with no run started
Where: §4, The arrival ("then the pass is taken whatever the start"); `WAIT_SECONDS` bounds only "an arrival's claim or a read"
Evidence: On every arrival, the pass's `GetAsync` (and its `RemoveAsync`) runs after the claim with no bound. The prototype's `takePass` sits outside `within`. The stub can hold the pass read (`w.hold.pass`), but no case does (grep: no `hold.pass` in any spec). A held pass read leaves `arrive` unfinished indefinitely, so the title's place never starts the run.
Critique: The lesson asks for a time limit on every store call that stands before a player-visible step. The fix the author will reach for is wrapping it in `within` and treating a late read as a pass. But then the real entry stays in the map for up to 300 s and lets a later buy arrival play free as well.
Consequences: The design must say whether a pass read not back in time counts as unreadable. The user's "Let all of them play" covers a map that cannot be read, so say it does. Its late answer must still remove the entry it found. The arrival's total bound becomes claim plus pass, unless the two run side by side.
Recommendation: Bound the pass read by WAIT_SECONDS, or take it beside the claim so the whole arrival is bounded by WAIT_SECONDS. A pass read not back in time counts as a pass, and its late answer still removes the entry. Cases: hold the pass read and `elapse()`: a buy arrival plays; `release()`: the entry is gone; a buy arrival on the next join goes back. Add a mutant row: no limit on the pass read.
Lesson: pickman-arch/open-stores-guarded

### F5 [medium] A test purchase never succeeds where the test store can't be opened, so in a Studio playtest from a file every BUY closes not bought
Where: §4, Failures ("a store that cannot be opened is a failed call on every path"); §5, Test mode; Unknowns (not listed); OC1 ("the test-mode screens are first seen in Studio through those issues' own Observed steps")
Evidence: `GetDataStore` throws where a place cannot reach DataStores, "a local file, API access off" (lesson pickman-arch/open-stores-guarded). `testGrant` then fails, and the confirm is reported `closed(…, false)` (receipts :: "a test confirm whose write fails closes the screen not bought"). `useRevive` answers nil. f0145's G1 puts Studio inside test mode, and the capture says "the purchase screens show and accept their controls exactly as live". In a Studio playtest from a file the screen shows, but no purchase can ever be tried through.
Critique: The design assumes a playtest can reach DataStores, without saying so and without an experiment. Each consumer's Observed steps in Studio will fail at BUY.
Consequences: The fallback must be test mode only and open-failure only. Live and closed mode keep failing closed: a real receipt still answers NotProcessedYet. Test credits made this way last only on that server, and `arrive` and `useRevive` must see them too, or the confirm succeeds and the revive is still refused. The sequestered case "a DataStore that cannot be opened: the arrival plays, a read is down, nothing throws" runs in test mode (`world(nil)`), so it moves to live mode.
Recommendation: In test mode, when the test store cannot be opened, Wallet uses a per-server in-memory stand-in for that store with the same `UpdateAsync`/`GetAsync` contract; nothing above it changes. Record it as an Unknown, with the doc fact and this fallback. Cases (stub `fail.open`, test mode): `arrive` answers free; `ask` then `"confirm"` closes bought and is granted; `useRevive` answers true. With `fail.open` in live mode: a receipt answers NotProcessedYet and `arrive` plays with a nil start, as now. Add a mutant row: the stand-in used in live mode.

### F6 [medium] The test screen takes its keys "above the place's own" only against ContextActionService bindings: UserInputService handlers, such as pickman's, still get Return, ButtonA, ButtonB and the taps
Where: §6 ("sunk there, so outside it they reach the place's own bindings"); §7's architecture text; Usability, Developer
Evidence: "ContextActionService marks every key and button it binds as processed (`gameProcessedEvent` true)" (lesson pickman-arch/count-processed-input-when-tracking), so a sink at priority 3000 does not stop `UserInputService.InputBegan`. `pickman/src/client/Controls.luau:188` connects `InputBegan` and ignores the processed flag (`_: boolean`). The portal's design plays on "Enter or A" (portal/.tracker/game-design.md). Suppose that is a UIS handler. Return on an open test screen then sends `"confirm"` and also presses PLAY. The server takes the confirm and forgets the open screen. While `testGrant` yields, the PLAY press asks again and opens a second test screen.
Critique: Every consumer (f0208, c0202, f0215, f0219, f0223) will rely on the library's stated precedence and bind its keys however it likes. The double action only shows on a device.
Consequences: The rule constrains every place's input code. A tracker that only notes the device in use (Pads) is exempt, per that same lesson. A new "is it open" query is public API and needs its own case.
Recommendation: State the consumer rule in §6 and in §7's text: "a place's own handlers of Return, KeypadEnter, ButtonA, Backspace, ButtonB and taps act through ContextActionService bindings below 3000, or skip processed input; a device tracker is exempt". Name it for each consumer in Order & dependencies. Add `TestPurchase.isOpen(): boolean` for places that gate their own handlers, with a case: false before any open, true after one, false after each answer.

### F7 [medium] `Wallet.pass` grants a free game whenever it is called: nothing ties it to a failed read, and `read` answers nil for both "busy" and "down"
Where: §4 `Wallet.pass` ("the portal's pass after a failed read"); Usability, Developer
Evidence: The user's rule is that a player let in "because its read of their record failed … plays that one game free" (f0145, 2026-10-26). The prototype's `pass` sets the entry unconditionally. A portal (f0208) that treats `read`'s nil as a failure hands a pass to a client that double-presses PLAY. The second press gets `(nil, "busy")`, receives a pass and is teleported, and its buy arrival plays free. No case refuses a pass.
Critique: arcade-arch's checklist wants the developer API "hard to misuse". This hole is one `if not record then` away in every consumer.
Consequences: The rule becomes one pass per failed read. A read answered from the cache, or busy, allows none. With F8, a cached "down" still allows its one pass.
Recommendation: `Wallet.pass(player, name)` writes a pass only when this server's last read for that player and title answered "down", and only once per such read. Otherwise it answers false and writes nothing. Cases: after a good read → false, the map stays empty; after busy → false; after down → true; a second call → false. Add a mutant row: pass unconditional.

### F8 [medium] Reads have no rate bound once the store fails, so "at most one GetAsync per READ_SECONDS" is false during an outage
Where: §4, Reads; Scalability ("reads at most one GetAsync per READ_SECONDS (60) … cannot exhaust other players'")
Evidence: Only a successful read sets the record seen. After a "down" (an error, or WAIT_SECONDS), the next call reads again at once. A client asking every frame while GetAsync errors fast (a full throttle queue) makes one GetAsync per frame per title. The case "a read whose store fails is down" reads once and never checks a second call.
Critique: That is exactly the outage in which the budget is shared. One client keeps every player's GetAsync and UpdateAsync throttled (UpdateAsync spends the get budget too), which is the opposite of the Scalability claim. This is the back-to-back half of the lesson.
Consequences: The portal shows the store as down for that span, and with F7 it still allows one pass per down.
Recommendation: After a read that ends "down", answer `(nil, "down")` with no store call for `Wallet.RETRY_SECONDS` (for example 6), counted from when the read ends. Correct the Scalability numbers. Cases: `fail.get` → down with `reads == 1`; at +5.9 s down with `reads == 1`; at +6.1 s `reads == 2`; a read that timed out starts the span when it ends. Add a mutant row: no retry bound.
Lesson: zz-arch/client-triggered-reads-guarded

### F9 [medium] A refunded revive still counts for the run, so the boards show a revive the run never used
Where: §4, Revives, `Wallet.refund`, `Wallet.revives`; AC3; the captured outcome "Each run counts its revives for the boards"
Evidence: `useRevive` adds one to the run's count. `refund` gives back a revive that could not be applied (Usability: "`Wallet.useRevive` and `Wallet.refund` for the revive"; f0145 refunds when the player left, declined or the offer ended) and leaves the count unchanged. The only refund case (wallet.spec line 680) never reads `revives`. Scenario: the player leaves during the `useRevive` write, the place refunds, and the departed run, submitted after PlayerRemoving, shows `revives = 1`.
Critique: This is a wrong value in a captured outcome. The fix the author will reach for, decrementing on every refund call, double-counts when a place retries a refund whose write failed.
Consequences: Only a written revive refund decrements. A failed one leaves the count (the credit is lost and the place may retry). The count never goes below 0, and a play refund leaves it alone.
Recommendation: A written revive refund takes one off this run's count, never below 0. Cases: use (count 1), refund → count 0 and the record's revives back to 1; a refund whose write fails → count 1; a refund at count 0 → 0; a play refund → count unchanged. Add a mutant row.

### F10 [medium] An arrival called for a player who has already left still spends their free game or a held play, and leaks a slot
Where: §4, The arrival; Slots; Edge cases ("A player who leaves during a write")
Evidence: The design covers a leave during a write, but not a call made after the leave. A place that calls `arrive` after a yield (waiting for the character or a first Ready, as f0145 did) can make it for a departed player. The prototype then claims the free start that player never plays. Its `slotOf` also makes a slot that `PlayerRemoving`, which has already fired, never drops. The same goes for `read`, `useRevive` and `pass` after a leave. No case calls any of them on a departed Player (the only call after a `w.leave` uses a new player).
Critique: f0145's G10 says "a teleport that never arrives costs nothing". A join that leaves before its claim is that case.
Consequences: `refund` must still write for a departed player (the credit is theirs). Grants by user id are unchanged, and so is the departed run's revive count.
Recommendation: `arrive` for a player no longer in the game (`Parent == nil`) answers `("back", nil)` with no store call and no slot. `useRevive` answers nil, `read` answers `(nil, "down")` and `pass` answers false, each without a call or a slot. `refund` still writes. Add a case for each, calling after `w.leave(p)`, and a mutant row for each.

### F11 [medium] The sequestered specs require spellings and an engine surface the Design never states, so a correct implementation can fail AC3, AC4 or AC6 with no way for the executor to fix it
Where: acceptance/place.spec.luau, "the server adapters never read TeleportData, and hear one client message"; experiments/stub-server.luau (inside wallet.spec and receipts.spec)
Evidence: (a) place.spec requires the literal `remote.OnServerEvent:Connect(answer)`, and counts `OnServerEvent` and searches for `TeleportData`/`GetJoinData` in raw source, comments included. A Receipts that writes `remote.OnServerEvent:Connect(onAnswer)`, or has a header saying "never reads TeleportData", fails AC6. `player["GetJoin" .. "Data"]` passes it. (b) The stub's `task` has only `spawn` and `delay`, `os` has only `time` and `clock`, and `Players` has only `PlayerRemoving` and `GetPlayerByUserId`. Presence is `Parent`. A Wallet that times the claim with `task.wait` in a spawned thread, hands handlers on with `task.defer`, or finds the buyer with `Players:GetPlayers()` fails on a nil call. §4 and §5 say only "spawned" and "not back within WAIT_SECONDS".
Critique: The executor may not edit sequestered files, so each mismatch forces an escalation. The text pins also miss the evasions the lesson lists.
Consequences: Spies in the stub replace the text pins and see the behaviour itself, whatever the spelling.
Recommendation: (a) Replace the text pins with stub spies. Across every Wallet and Receipts case, `GetJoinData` is never called, the TestPurchase remote gets exactly one `OnServerEvent` connection, and nothing assigns `OnServerInvoke`. Keep place.spec's structural cases, and say in Rules and mutants what is left to code review. (b) State in §4–§6 the engine surface the stub provides: time limits are `task.delay`, handlers are `task.spawn`ed, the buyer is found with `GetPlayerByUserId`, presence is `Parent ~= nil`. Or widen the stub (`task.wait` and `task.defer` on its fake clock, `GetPlayers`).
Lesson: zz-test/source-text-pins-read-the-code

### F13 [low] `TestPurchase.start()` yields its caller until the remote exists, so every client boot after it waits on the server
Where: §6 ("waits for the remote"); prototype `ReplicatedStorage:WaitForChild("ArcadePaidPlay"):WaitForChild("TestPurchase")` in `start`
Evidence: client.spec's stub `WaitForChild` returns at once, so a blocking start is never seen. If the place's server is late with `Receipts.start`, or never calls it, the client's Main stops at this line.
Recommendation: `start()` returns at once and waits in its own thread. Case: a stub `WaitForChild` that yields; `start()` returns, and an open after the release shows the screen.

### F14 [low] The run's revive counts are kept for every player who ever arrived on the server
Where: §4, Revives ("kept … until their next arrival on this server"); Scalability, Memory
Evidence: One entry per user and title that is never dropped. On a long-lived server it grows with every visitor.
Recommendation: Drop a departed player's count once it has been read after the leave, or after a bound (for example 10 minutes after `PlayerRemoving`). Add a case for each.

## Lesson candidates (for the lead to file)
- When a Design says a cache is refreshed by "every read and write", does a case follow each writer (and each exclusion) with the read that depends on it? (F1: a grant's refresh survived 88 cases.)
- When per-player state is also keyed by a second value (a title, a board), does a case drive two values for one player and assert that nothing is shared? (F2.)
- When a shared screen sinks keys, does the Design say what it cannot stop (UserInputService listeners) and the rule its consumers follow? (F6.)

Verdict: changes
