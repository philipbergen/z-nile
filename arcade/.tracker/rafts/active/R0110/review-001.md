### F1 [high] A stale record overwrites a fresher one in `slot.seen`, and `useRevive` then refuses a revive the player just paid for, with no write, for the rest of the join
Where: arcade/src/server/Wallet.luau:105-108 (`see` keeps whatever arrives last), 336-349 (`arrive` applies its claim's record only after `takePass` has yielded), 259-261 (`read` applies a GetAsync begun before a write), 372-375 (`useRevive` answers false from `seen` with no age bound and no write).
Evidence: `see` orders records by when the Lua thread gets its answer back, not by when the store applied them. Two runs on a copy of the acceptance stub harness (live mode, Pickman, player 7):
- Arrival vs a receipt processed on join (Roblox redelivers an unprocessed receipt when the player joins, which is when the place calls `arrive`): seed `{ free = NOW-60, plays = 1, continues = 0 }`; `w.hold.pass = true`; run `arrive` (its UpdateAsync completes, claiming the play, `final.revives = 0`, then it yields in `takePass`); `w.receipt(7, 102, "r1")` answers PurchaseGranted, the live record holds `continues = 1`, and `seeGrant` sets `seen.revives = 1`; `w.release()`; `arrive` now runs `see(slot, final)` with `revives = 0`. `useRevive` answers **false with 0 writes**, and still false after `w.advance(30)`.
- Read vs a receipt: `w.hold.get = true` with a GetAsync that returns the value as it stood when the request was served (as a real read in flight does); run `read`; `w.receipt(7, 102, "r1")` (seen.revives = 1); release: the read's `see` puts back `revives = 0`. `useRevive` answers false with 0 writes; a `read` 59 s later answers `revives = 0` from the cache, and `useRevive` is still false.
The same happens between two writes whose answers come back out of commit order (a `useRevive` that committed 1→0, a grant that committed 0→1 and answered first). The record in the store is right; this server's `seen` is wrong, and nothing refreshes it: `useRevive`'s false path makes no write, and `read` answers from the stale `seen` for `READ_SECONDS` after it was (wrongly) refreshed.
Why no spec caught it: the acceptance stub's `GetAsync` reads `held[key]` after the hold is released (wallet.spec.luau:187-194), so a held read always returns the newest value; no case holds the pass read across a grant.
Critique: the Design promises "a revive or a play just bought is usable at once" (§4 The record seen) and "a purchase is granted once and never lost" (Usability). Here the revive screen (f0215/f0219/f0223) hears `granted`, calls `useRevive`, gets false ("none held") and offers to sell another one: the player is charged again for a revive they already hold. The tempting fix is to re-read the record before answering false, which spends a store read per revive press and reopens the bound the in-flight and USE_SECONDS guards exist for; or to order by `os.clock()` at the answer, which is exactly what is broken.
Consequences: any ordering rule must cover reads, writes and grants by user id (which find the slot through `GetPlayerByUserId`), keep test-mode servers' live grants out of the test record, and keep every client-triggered bound (one read per READ_SECONDS, one revive write per USE_SECONDS, none in flight).
Recommendation: make `seen` conservative under overlap. Per slot, count store calls in flight and a generation number bumped at every call's start and end; a call applies its result with `see` only when the generation is still the one it recorded at its own start (no other call on that slot started or ended meanwhile), and otherwise clears `seen` to nil. `grant` and `testGrant` take part through the buyer's slot when the buyer is on this server (a test-mode server's live grant does not touch the slot, as today). `arrive` applies its claim's record as soon as its UpdateAsync returns, inside the `within` closure, not after `takePass`. A cleared `seen` costs one store read at the next `read` and one write at the next `useRevive` (both still under their in-flight and time bounds), never a refusal. Spec cases (in a non-sequestered spec, e.g. `arcade/tests/unit/` or an adapter spec with its own stub, whose held GetAsync can answer the value from when it was served): (a) a read held across a revive receipt, then `useRevive` writes and answers true; (b) a revive receipt during the arrival's pass read, then `useRevive` answers true; (c) two writes answered out of commit order, then `useRevive` writes; (d) the existing "with none held known, no write is made" still holds when nothing overlapped. The acceptance specs need no change.
Lesson: zz-arch/client-triggered-reads-guarded

### F2 [medium] `pass` still writes after a busy answer or a cached good answer, against the Design's rule for the pass
Where: arcade/src/server/Wallet.luau:223-232 (the busy and cached returns leave `slot.mayPass` as it was), 274-277.
Evidence: Design §4 The pass: "after a good read, a busy one, or a pass already written, it answers false and writes nothing." Probes on the stub harness, test mode: (1) `read` fails ("down", mayPass true); `w.advance(7)`; `w.hold.get = true`; `read` (in flight); `read` answers "busy"; `pass` answers **true** and writes `pickman/7`. (2) `read` fails; `w.advance(7)`; `refund(p, "pickman", "play")` (sees a record); `read` answers the cached record (a good answer); `pass` answers **true** and writes. The acceptance case "a pass is written only after a read that answered down" holds a read only for a player with no earlier down answer (wallet.spec.luau:1027-1031), so it cannot see this.
Critique: the Design calls this guard "the user's rule ... made hard to misuse": a pass is for a player let in "because its read of their record failed". After a good cached answer, the portal knows the record and must not hand out a free entry; the code does. The tempting fix is to clear `mayPass` only in the cached branch, which still leaves the busy one.
Consequences: clearing on every non-down answer means a portal that reads, sees "busy", and then wants to pass must read again until it gets "down"; that is the Design's stated contract (f0208 reads before passing), so no new user decision.
Recommendation: set `slot.mayPass = false` on every answer of `read` that is not "down" (busy, cached and fresh good), keep it true only from the down answers. Add cases (outside the sequestered spec): down, then busy, then `pass` false and no SetAsync; down, then a cached good answer, then `pass` false and no SetAsync.

### F3 [medium] During an outage one client gets one MemoryStore write per PLAY press: the pass write is not bounded by anything the client cannot drive
Where: arcade/src/server/Wallet.luau:226-229 (every "down" answer in the retry span re-arms `mayPass`, with no store call), 268-285 (each armed `pass` is one `SetAsync`).
Evidence: probe, test mode, `w.fail.get = true`, 50 iterations of `read` then `pass` with no clock advance: **50 passes written, 1 store read**. The Design's Scalability says the guards hold "whatever the client asks" and counts "a pass one SetAsync, only after a failed read"; the read bound (one GetAsync per RETRY_SECONDS) holds, but the pass write rides on answers, not on store calls, so a client mashing PLAY on the portal (f0208: `read`, then `pass` on "down") spends one MemoryStore write per press for as long as the DataStore is down, from the experience-wide MemoryStore budget every server shares.
Critique: this is the outage case, the one moment the budgets are already stressed. The tempting fix is "one pass per RETRY_SECONDS span", but the sequestered case requires a second down answer in the same span to answer `pass` true (wallet.spec.luau:1038-1041).
Consequences: the answer must stay true (the spec and the user's rule "Let them play free"), only the write may be skipped; a pass this server wrote is still in the map until an arrival takes it or PASS_SECONDS passes, and an arrival takes it only in another place, after this player has left this server (their slot is dropped), so a skipped rewrite never leaves a player without a pass.
Recommendation: per slot, remember when this server last wrote the pass; a `pass` armed by a later down answer within RETRY_SECONDS of that write answers true with no SetAsync (or, more simply, within PASS_SECONDS, since the entry is still there); state the bound in the Scalability text you already have (at most one pass write per RETRY_SECONDS per player and title). Add a case counting SetAsync over many read/pass pairs in one span (one write) and after the span (one more).
