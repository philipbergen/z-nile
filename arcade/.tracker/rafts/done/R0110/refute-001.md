# Refute 001: R0110 (code mode)
Answers review-001 (layer 1 re-finished at 9cec1590d, layer 2 restacked on it at 8c77058a1).

- F1: fixed 9cec1590d: `Wallet.luau` orders the record seen by the store, not by when an answer comes back. Each slot keeps a count of store calls under way and a generation bumped at every call's start and end (`begin`, `ended`); a call's record becomes the record seen only when no other call on that slot started or ended while it ran, and otherwise the record seen is forgotten (a failed write forgets it too; a failed read leaves it). Reads, the arrival, revive uses, refunds, live grants (on a server whose title is not in test mode) and test grants take part, a grant through the buyer's slot when the buyer is on the server as the write starts (a buyer who joined during it has the record seen forgotten). The arrival applies its claim's record as its write returns, inside the time-limited call, not after the pass read. New spec `arcade/tests/place/wallet-order.spec.luau` (its stub's held GetAsync answers the value as served, and a write can be held after it was applied): a read served before a revive grant, a revive granted during the arrival's pass read, and two writes answered out of order each leave `useRevive` writing and answering true; with nothing overlapping, a revive none is known to hold still makes no write. The three overlap cases fail on the code before the fix (6 of 7 cases fail there, the guard case passes on both); consequences: a forgotten record costs one store read at the next `read` and one write at the next `useRevive`, each still under the in-flight flag, READ_SECONDS, RETRY_SECONDS and USE_SECONDS bounds, so a client cannot drive more calls than before; an arrival whose claim comes back after WAIT_SECONDS now sets the record seen when it ran alone (it is the store's own record of that write), and a late read still keeps nothing; a test-mode server's live grant still leaves the test record seen alone (acceptance "in test mode a real receipt leaves the record seen alone" passes). Checked: `./zn check f0201` 7/7 (130 acceptance cases), arcade's meta, place and unit specs 53 passed, `z-nile/check.sh --affected` green.
- F2: fixed 9cec1590d: `read` clears the pass allowance on every answer that is not "down": a busy answer and an answer from the record seen, as a fresh good read already did; only the down answers (a failure, a time limit, the retry span) allow one pass. Cases in `wallet-order.spec.luau`: down, then busy, then `pass` false with no SetAsync; down, then a good answer from the record seen, then `pass` false with no SetAsync; consequences: a portal that read "down", then "busy", must read again until it gets "down" before it may pass, which is the Design's contract (§4 The pass); the acceptance case "a pass is written only after a read that answered down, once per such answer" still passes.
- F3: fixed 9cec1590d: `pass` remembers when this server last wrote the player's pass for the title (`passedAt`, per slot); a pass allowed by a later down answer within RETRY_SECONDS of that write answers true with no SetAsync, so the writes are at most one per RETRY_SECONDS per player and title however often a client asks (10 a minute, the same bound as the reads during an outage). Case: 50 read-and-pass pairs in one span make 1 store read and 1 SetAsync; after RETRY_SECONDS one more of each; another title's pass is its own; consequences: the answer stays true, as the sequestered case requires; the skipped write leaves the entry this server wrote within the last 6 s, which lives PASS_SECONDS (300 s), and an arrival takes it only in a title's place, after the player has left this server (their slot, and `passedAt` with it, is dropped then), so a skipped write never leaves a player without the pass; a failed SetAsync records nothing, so the next allowed pass writes again.
