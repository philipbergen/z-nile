# c0128: Narrow hiscore adapter pins

## Problem
Two promoted hiscore adapter specs pin today's per-player-only boards, so d0124 (R0044) cannot land while they stand. d0124 keeps every per-player board as it is and adds an all-time top-10 list of runs in a new store, `HiscoreTop` (scope `all`, key `runs`): the game server writes it before the per-player boards, and the lobby's all-time answer reads it and also carries the asker's own best as a fifth value. User decision for d0124, 2026-10-21: "Keep player best and a global list of top-10, so the number of rows is (10+n_players) in total".

On a prototype of d0124 (R0044 prep, 2026-10-21) exactly seven promoted cases fail, and every other selected spec passes (309 of 316 cases):
- `tests/acceptance/f0024/adapter.spec.luau` :: "stores are the shared names scoped by period, budgets are the modern request types": the exact list of six stores gains `HiscoreTop|all`.
- `tests/acceptance/f0024/adapter.spec.luau` :: "each update is preceded by the read and write budgets of its own store": `expected 6, got 8` (the list's update, twice on a first write: once to find no list, once with the seed).
- `tests/acceptance/f0026/adapters.spec.luau` :: "a failed read still answers once, with failed = true and the rows it had, or none", "an error anywhere in the read, opening the store included, is a failed read and the board is not wedged" and "a companion row that cannot be read fails the read: no short board is answered as healthy or cached": a whole-answer `toEqual` of four values meets a fifth (the asker's best).
- `tests/acceptance/f0026/adapters.spec.luau` :: "Boards opens the ordered and the companion store under their own names and the board's scope": `expected "companion|HiscoreEntries|all", got "companion|HiscoreTop|all"`.
- `tests/acceptance/f0026/adapters.spec.luau` :: "a page of 50 after the size-10 fallback is cut to the top N before any companion is read": `gets <= N` counts the list read and the best read too.

**Outcome:** those seven cases are narrowed so they keep pinning what they pinned for the per-player boards and no longer forbid d0124's additions, and `main` stays green before and after d0124 lands. No other case changes, and no case is removed.

## Non-goals
- Any change to `src/`: d0124 (R0044) builds the list, the best line and the missed-rank line, and its own sequestered specs pin them.
- Any other promoted spec, and these files' other cases.

## Solution
- f0024 `adapter.spec` stores case: the six per-player stores are each opened, and any other store opened is `HiscoreTop|all` only.
- f0024 `adapter.spec` budgets case: every update is still preceded by both budgets of its own kind, and the updates to the `Hiscores` and `HiscoreEntries` stores are still exactly six; updates to `HiscoreTop` are not counted.
- f0026 `adapters.spec` three answer cases: compare the first four values of each Board answer (id, rows, highlight, failed), as every whole-answer `toEqual` in the file does after this change.
- f0026 `adapters.spec` opens case: a companion open is `companion|HiscoreEntries|all` or `companion|HiscoreTop|all`; ordered opens stay `ordered|Hiscores|all`.
- f0026 `adapters.spec` page-of-50 case: count only the `GetAsync` calls for the board's thirty row keys, which stay at most N.

Prep adds (2026-10-21, R0045):

The captured bullet is kept as it is.

## Design
### Files and changes
The exact change is `R0045/experiments/narrowing.patch`, against `origin/main` ae122db2 (it applies cleanly on fa9cc9bc and later too). Only `tests/acceptance/f0024/adapter.spec.luau` and `tests/acceptance/f0026/adapters.spec.luau` change, and only in the seven cases:
- **f0024 `adapter` "stores are the shared names …"**: the exact list of six stores becomes: each of the six (`HiscoreEntries|all`, `HiscoreEntries|day:2026-10-16`, `HiscoreEntries|week:2026-10-12`, `Hiscores|all`, `Hiscores|day:2026-10-16`, `Hiscores|week:2026-10-12`) is opened, every opened store is one of them or `HiscoreTop|all`, and there are exactly 6 opened stores, or 7 when `HiscoreTop|all` is one, so no store is opened under two kinds (design review 001 F4). The budget-kind loop stays.
- **f0024 `adapter` "each update is preceded …"**: the stub logs `update:<kind>:<name>` (was `update:<kind>`); the loop still requires both budgets of an update's own kind since the last update, for every update, and counts only the updates whose name is not `HiscoreTop`, which stay `toBe(6)`. The kind test becomes a prefix test (`string.sub(entry, 1, #"update:ordered") == "update:ordered"`).
- **f0026 `adapters`**: a local `four(answers)` returns each answer's first four values (id, rows, highlight, failed). In "a failed read still answers once …" (7 comparisons), "an error anywhere in the read …" (2) and "a companion row that cannot be read …" (2), every whole-answer `toEqual` compares `four(...)` against the same expected values.
- **f0026 `adapters` "Boards opens …"**: a companion open is `companion|HiscoreEntries|all` or `companion|HiscoreTop|all`; ordered opens stay `ordered|Hiscores|all`; at least one of each; and `companion|HiscoreEntries|all` is among the opens (design review 001 F2), so a Boards that reads its rows from the list store alone fails.
- **f0026 `adapters` "a page of 50 …"**: the stub records each companion `GetAsync` key (`w.keys`); the case counts the reads of the thirty row keys (`101`..`130`) and requires more than 0 and at most `Hiscores.N`. The page sizes `{10, 50}` and the answer checks stay.

### The c0128 specs
- `titles.spec`: the case titles of both files, in order.
- `guards.spec`: each narrowed case's guard, as text probes (the six store names and the 6-or-7 count, `toBe(6)` and both budget kinds, the number of four-value compares, the required `HiscoreEntries` open, the floor and cap on row reads).
- `golden.spec` (design review 001 F1): each whole file, normalised as c0103 normalises f0014's (whitespace collapsed, a trailing comma before `}` dropped, item ids masked; comments kept), must have the sha256 of the narrowing applied to `origin/main`: f0024 `747696e1…5737db`, f0026 `f5a74905…091394b` (full digests in the spec). This pins "No other case changes": any edit outside the narrowing, a deleted assertion or a changed comment included, fails it. Any later change to either file must update the digest. The digests are of the narrowing applied to the blobs `aa100297` (f0024) and `21647d7e` (f0026) on `origin/main`, so execution is tied to that base (Implementation step 1).
- Every path to a real item folder goes through `renamed.id` and is spelled in two parts (design review 001 F3), as c0063 and c0103 do, so a compaction cannot break them.

### Pure/adapter split and authority
No `src/` change. These are promoted specs, which a chore may edit in its own raft (z-design, Override check).

### Scalability
No runtime cost. The two spec files run in the same time (35 cases, about 0.1 s each).

### Maintainability
Each narrowing keeps the case's guard for the per-player boards and names the one addition it now allows (`HiscoreTop`), so a future store still fails these cases. The c0128 specs pin the case titles, the guards and each whole file (`golden.spec`), so a later edit cannot narrow by deleting; a later deliberate edit of either file updates the digest in `golden.spec`.

### Usability
Developer-facing only: the narrowed cases' own failures still name what broke (the store, the count, the compared values). A `golden.spec` failure prints only two digests: `titles.spec` and `guards.spec` then say which case or guard moved, and `git diff` against `R0045/experiments/narrowing.patch` shows the rest; `golden.spec`'s header says how to record a new digest.
