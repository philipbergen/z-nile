In the game: `frame.boon` is "the latest boon a finished pick granted, nil before any", `walls.opened` keeps its holes until a new level or run, `hopped` is "the tick the latest hop started, nil before any" (Session `Frame` type), and every classic-maze game frame carries `ghosts`. A probe settles the fix: in the clone I appended, before the case's assertion loop, a second pass of the same fourteen play states, each in a frame with a hole and two marks (`frame({ at(2, 2) }, { at(7, 2), at(25, 6) })`), `tick` 1000 + i, `hopped` and `hopTicks` set, a `boon`, `shots = 0`, a `shot`, and a `pick` under way while playing, plus one `ready` frame (lives 2), with the same expected calls. Critique: this is the third round on one mechanism. Round 1 added phases, round 2 the rest of `play`; review 002's Recommendation (a) asked the Design to say whether the frames are hand-built or taken from a real `Session`, and the refute answered with more `play` fields and no stated choice. A text pin refuses every guard, so "at least what the text pin kills" needs every field of the frame Main receives to take, in some frame, a value the game reaches; varying the slice the author thinks of leaves the next field for round 4. The tempting fix is to add `boon`, `opened`, `hopped` and `ghosts` to some frames, which closes these four and not the next one (`player`, `shot`, a field f0147 adds).
Consequences: a second pass changes which frames Main sees: holes and marks make Main call `MazeView.rewall` (a recorder; the edible and wallState counts are unaffected, as the probe shows); `maze` and `v` must stay as they are (a new `maze` rebuilds the model, and only one layout exists); a `pick` is only valid while playing (it lapses on leaving play), and holes, the boon and `hopped` persist over a death and into game over, so each phase's context must be what the producer allows there. The case grows to about 30 frames, so Scalability's count, walls.spec's digest, E2 and E3 change. A literal list of the fields the busy context must change, checked by the case against the plain frame, keeps the coverage honest; iterating `pairs` of the frame and requiring every key to differ would instead turn red whenever a later issue adds a Frame field (zz-test/promoted-specs-pin-rules-not-sets), so don't.
Recommendation: question the mechanism and state it in the Design: "the colour state is a function of `frame.play` alone, handed over every frame, whatever else the frame holds". Then:
(a) Push the whole step sequence twice, in one `mainWorld()` (counts continue): once on the plain `frame({}, {})` and once in a busy context where every non-`play` field of `Session.Frame` except `v` and `maze` holds a value the game reaches in that phase and differs from the plain frame: `ghosts` (take them from a `Session.frame` of a session with ghosts, or the harness's own ghost frames if f0126 has one), `player` (another tile and heading), `tick` increasing, `hopped`/`hopTicks`, `walls` with a hole and marks, `boon`, `shot`, `shots = 0`, and `pick` while playing. Use the types' own values (`Maze.Heading` is a compass letter, e.g. `"W"`). Put the busy pass after the plain one, so a stale-local mutant (K1) is seen on the busy frames' changes of edible.
(b) Add `ready` frames where the producer goes there: after the death with lives left and after the level clear (F2), each expecting one call with edible false.
(c) In the case, assert for a literal list of those field names that the busy frame's value differs from the plain frame's (so a later edit of the context can't quietly drop one).
(d) Add R1, K1, K1r, B1, W1, H1, GH and TK to `mutants.py` and the Rules table as `run` rows (the rule: "the colour state ignores every field but `play`, and is sent in every phase, ready included"); recompute the digest; re-record E2 and E3; update Scalability.
