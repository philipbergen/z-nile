### F4 [medium] The lobby's switch to the library's 60 s read rests on "nothing else writes a lobby player's record while they are in the lobby"; a receipt does, and a join read that returns after it hides the play for a minute and drops the grant's START
Where: §3, the "Two consequences" paragraph; lobby.spec; `experiments/stub.part` (`GetAsync`).
Evidence: a play receipt that Roblox retries when the player joins the lobby (or a purchase made at join) writes the record while the `PlayerAdded` read is in flight. On the prototype, `Wallet.read` stores the `GetAsync` result with `see(slot, r)` when it returns (`arcade/src/server/Wallet.luau`, `read`). That happens after `Wallet.grant`'s `seeGrant` has set the slot to plays 1, so the older value (plays 0) wins for `READ_SECONDS` (60 s). Meanwhile Paid's `granted` handler calls `Wallet.read`, which answers "busy" (no tell), and its press reaches `Paid.allow`, whose read answers "busy" and returns false: the bought play does not start. For the next minute every START press sees plays 0 and opens the play product again. In live mode that is a second real purchase of a play the player already holds, kept as a credit (G9). f0145 bounded the same window to `Paid.PRESS_SECONDS` (2 s). The stub cannot show it: its `GetAsync` reads `held[key]` only after the hold is released, so a held read returns the newer value.
Critique: it is tempting to call this the library's problem and leave it, or to shorten `READ_SECONDS`, which is a library constant every title uses.
Consequences: the root fix is in f0201's Wallet. A read that began before a write this server made must not replace that write's record, for example with a per-slot write counter checked in `read` before `see`. That is an arcade change (re-prep f0201, or a follow-up arcade defect) that c0202 would depend on, or a risk the user accepts. A c0202-only mitigation (the lobby's play grant presses again once the read ends) adds a delayed press that must not teleport twice. Starts' idle-travel guard should hold that, and a case must show it.
Recommendation: correct §3's premise. Report the stale-read race to f0201's owner through the lead, and name in Order & dependencies the item that fixes it. In c0202, when the read answers "busy", the lobby's play grant presses again once after `Wallet.WAIT_SECONDS`. Add a lobby case "a play receipt granted while the join read is under way starts the game once, and the line says 1 GAME YOU BOUGHT", with a Rules row and mutant (no retry). Change the stub's `GetAsync` to capture the stored value when called (before the hold), so the race is visible to that case.
Lesson: zz-arch/client-triggered-reads-guarded
