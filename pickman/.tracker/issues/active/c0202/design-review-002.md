### F3 [low] `useOne`'s tell can wait on a store read before it releases the hold or applies a decline
Where: c0202.md §2 "What the player holds" ("sent only when the read answered a record … The library answers from the record it saw with no store call, except when its ticket forgot that record … when the read is one `GetAsync` bounded by the library's own guards"); prototype `Continues.luau` `useOne` (`tell(player)` before `Session.hold(s, id, false)` and `Session.decline(s, id)`).
Evidence: a player declines during a revive's write; the write succeeds, so the revive is given back with `Wallet.refund`. If that refund's write fails, `ended(slot, ticket, nil, true)` forgets the record seen, and a failed write does not set `downUntil`; `tell` then calls `Wallet.read`, which makes a `GetAsync` and waits up to `Wallet.WAIT_SECONDS` (5 s) during the outage that failed the refund. Only after it returns does `useOne` release the flight's hold and apply the decline, so the player who chose END GAME watches a held CONTINUE? for up to 5 s more. Main's tell carried the record it had and never yielded. The same order puts a read before the offer's `Receipts.ask` after a "none" whose write overlapped another call.
Critique: the tell is information only, yet it sits in front of the run's state changes. Spawning it (`task.spawn(tell, player)`) would remove the wait but lets two tells arrive out of order, so a slow older read could overwrite a newer line.
Consequences: moving the tell below the hold and the decline keeps the messages in order and changes no message's content; `status.spec`'s give-back case still sees the tell after the write.
Recommendation: in `useOne`, tell after `Session.hold(s, id, false)` and `Session.decline(s, id)` (the continued path already tells after `Session.continue`); keep `heard`'s first tell, which runs while a screen or the receipt wait holds the countdown anyway. Add a case to `offer.spec` or `status.spec`: "a decline during a revive's write whose give-back fails ends the run at the next step, while the read the tell makes is still under way" (the refund's write failed through `w.onUpdate`, the stub's read held), with a row whose mutant is the current order.
