### F1 [low] The harvest records the repeat but doesn't sharpen the lesson's `check`, whose Logic-fallback clause only covers "an adapter every feature touches (Main)"
Where: `pickman/skills/pickman-test/lessons/stub-loaders-fall-back.md`, `check:` frontmatter; `harvest.md` line for design-review-006 F1.
Evidence: z-design step 3 says "A finding that repeats a lesson the pass should have caught sharpens that lesson's `check`." The re-prep added only a body paragraph. The check still asks (1) "which issues in flight add a require to that adapter". d0124's original prep answered "none": f0146 added `Logic/Pad` to FlowView later. It also asks (2) whether the harness is open, but only "for an adapter every feature touches (Main)". So a design pass that asks this check of a loader for FlowView, Ranks or HiscoreStore, with nothing in flight, still passes the closed table that broke R0044.
Critique: the next prep that writes a stub loader for a non-Main adapter repeats d0124's defect, because the check still lets it through. The body's How to apply already says "in a new stub loader, fall back to the real Logic module"; the check is narrower than that rule.
Consequences: widening the check doesn't open siblings and services for every loader. Those may still refuse, as this spec deliberately does (design-review-006 F1 Consequences). Only the Logic fallback becomes unconditional.
Recommendation: change the check to ask, for every spec that loads an adapter through a stub `require`: "Does it load every unstubbed `@game/ReplicatedStorage/Shared/Logic/<name>` as `@logic/<name>`, whatever is in flight now (a later issue can add one), and for an adapter every feature touches (Main), are siblings and services stand-ins too?"
