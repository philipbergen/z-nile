# d0412: Decline during revive write sells

## Problem
R0125 code review 001 F1 (2026-11-17): in the game place's continue offer (`pickman/src/server/Continues.luau`), a player who declines (END GAME, Backspace, ButtonB) while a revive's write is under way, when that write then finds no revive held (`Wallet.useRevive` answers false) or cannot tell (nil), is shown the revive's purchase screen (Roblox's prompt live, the library's test screen in test mode) and the countdown is held again: `useOne` applies the decline and answers "empty" or "unknown", and `ask` then opens the product, since a decline ends the offer only at the next step. The decline is not applied; a player who then buys is charged and continues a run they ended. f0145's rule "a decline during the write is applied after it" held only when the write used a revive. Main had the same gap (`useOne` answered "none" there); c0202 rewrote both functions in this raft, so the fix lands with it rather than after it.

## Non-goals
- c0202's sequestered specs and its contract: unchanged; this issue's spec is its own, outside `acceptance/`.
- A decline outside a write (it ends the offer at the next step, unchanged) and a decline during a write that used a revive (given back, unchanged).

## Solution
`useOne` answers "declined" when the player declined during the write and no revive was used (the decline is applied as before), and `ask` returns on it before opening any purchase screen, as it does for "refunded".

## Design
In `Continues.useOne`, after the give-back branch (`used == true` → "refunded"), `if flight.declined then return "declined" end`; `ask` adds "declined" to the answers that return at once. `heard` needs no change: in test mode "declined" is not one of the answers that release the countdown (the decline already released the flight's hold), and live it arms no retry (only "unknown" does), and it tells nothing (only "empty" tells). The hold, the decline and the give-back order are unchanged.

### Scalability
No store call or message added; one fewer prompt and screen in this case.
### Maintainability
One more answer of `useOne`, documented with the others in its comment.
### Usability
The player's END GAME during the write is honoured: no purchase screen, and the run ends at the next step.
