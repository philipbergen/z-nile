### F1 [medium] Two of the carry's stated rules have no row and their mutants survive: ½ on a new level or a new run, and kept across a change of kind (repeat of review-002 F3, in part)

- Y1: `Ghosts.power` sets `g.carry = 0.5` on every ghost it turns blue (a reset on a change of kind): `Y1: SURVIVED (ramp)`.
- Y4: a hunting (whole-unit) step sets `g.carry = 0.5` (the carry dropped whenever the ghost leaves the tunnel or stops being blue): `Y4: SURVIVED (ramp)`.
Critique: round 2 asked the author to state the kind-change rule so the executor need not guess; it is now stated, so it is a behavioural rule, and every behavioural rule needs a row (zz-review design mode, item 0). A tidy executor plausibly writes Y4 ("a whole speed needs no carry") or Y1 ("a fresh blue period starts clean"), and the issue's own case can't tell. No new state; Behaviour 2's sentence stands.
Recommendation: extend the ramp.spec case: after three frightened steps, `Ghosts.reset(set, "level", 2)` and, on another set, `Ghosts.reset(set, "run", 2)`; re-frighten; the first step is 13 for each. Add rows (Y2: kept over a new level or run; Y1/Y4: reset on a change of kind) with runner entries, and run them.

### F2 [medium] From level 2 on, the "longer jumps" boon is a dud on every roll: a consequence of the bonanza's carried long hops that the user was not told and the design does not record
Where: f0147.md Behaviour 6 ("Since every level ends with a bonanza, every level from level 2 on has long hops"), Edge cases (no row for a jumps roll while long hops are on); game-design.md Wall picks ("**Boons**, each with the same chance (1 in 6): **longer jumps** [...]") and the new section's bonanza bullet; prototype `Picks.roll` (`return BOONS[roll(p, #BOONS)]`, uniform) and Session's `if boon == "jumps"` branch
Evidence: on every level from 2 on, `member.longHops` is true from the level's READY (the bonanza) until its fresh maze. Rolled boons stay uniform over six, so one roll in six on those levels is "longer jumps", which sets `longHops = true` again and changes nothing. The player sees the banner "LONGER JUMPS" for 2 s and gets nothing. Over nine rolled picks a level, that is about 1.5 dead boons per level, on every level the player reaches after the first. On level 1 this only happens on a second jumps roll (f0126's behaviour); f0147 makes it the rule for every later level. Neither f0147.md nor game-design.md mentions it, and the user's "Carry into next level" answer (2026-10-31) was asked without it.
Critique: f0126's user rule is "even chance on each boon", and the user chose the bonanza's carried long jumps; together they make one boon worthless from level 2 on. That's a player-facing outcome of two user decisions, and only the user can trade them. An executor will build it as written, and the first playtest finds it.
Consequences: every fix changes a user rule. Re-rolling among the other five while long hops are on changes f0126's "even chance". Replacing jumps on later levels with something else adds a boon. Making a jumps roll on a long-hop level extend something (for example, the next level's hops too) adds state that a death or a new run must handle. Each choice needs a case (a seeded roll that lands on jumps while `longHops` is set) and a row.
Recommendation: escalate to the user: (a) keep it, recorded in game-design.md's bonanza bullet and the Edge cases ("from level 2 a rolled longer-jumps boon does nothing"), with a case pinning that it grants nothing and still shows its banner; (b) while long hops are on, roll among the other five boons (changes f0126's "1 in 6"), with a case on a seed that rolls jumps and a row for the re-roll; (c) another reward in its place, as the user names it. Keeping today's design costs nothing to build, but leaves the dead boon in the game.

### F3 [medium] hud.spec's clearance case names the touch controls one by one, so after d0149 (in prep) it silently skips the controls that replace them
Where: hud.spec "the counter is clear of every other HUD block, both radars, the touch buttons, the pick bar and banner" (`others = { ..., b.snap, b.fire, b.hop, b.pick, ... }` with `b = Touch.buttons(l) :: any`, then `for i, o in others`); the author's uncommitted "Pending for round 3" note in design-refute-002.md
Evidence: d0149's prototype (proto-d0149 06bf7a5c) has `export type Buttons = { steer: Circle, look: Circle, fire: Rect, pick: Rect }`. With it, `b.snap` and `b.hop` are nil, so the table constructor leaves holes, the generalized `for` skips them, and the steer and look circles are never compared with the counter. The case stays green and checks two controls fewer, with nothing saying so (zz-test/no-vacuous-pass). Measured today with a probe (d0149's `Touch.buttons` against `Hud.picksBox(Touch.blocks(l).score)` from the f0147 prototype, f0126's 15 screens × 5 insets, circles as their bounding squares): 300 comparisons, no overlap. So the gap is in what the case checks, not in the geometry. The author's pending note plans to walk every field `Touch.buttons` returns.
Critique: the planned walk is right, but it's still a plan, and the sequestered spec can't change once the issue is readied. Whichever of f0147 and d0149 lands second, the promoted case must still check every touch control.
Consequences: a walk over every field can still pass vacuously if `Touch.buttons` returns nothing or nothing it recognises. A `Circle`'s bounding square is conservative (it can fail where the drawn circle clears), which the 300-comparison probe shows is not a problem today. `Touch.snapRect` (a separate function, used by f0158's clear.spec) disappears with d0149's "no snap-look button", and hud.spec must not name it either.
Recommendation: as the note says, walk `Touch.buttons(l)` by `pairs`: a `Rect` as it is, a `{x, y, r}` as its bounding square, any other shape an error. Require at least two touch controls on every layout, so an empty or renamed result fails. Drop every named touch field from `others`. Record the d0149 probe as an experiment (the prototype's sha, 300 comparisons, no hit), and run hud.spec against a copy of the prototype with d0149's `Touch` swapped in, as I did. Add a row: a mutant that drops one field from the walk (for example, skipping circles) must die.
Lesson: zz-test/no-vacuous-pass
