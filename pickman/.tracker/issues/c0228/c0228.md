# c0228: Walls built once per maze

## Problem
Main builds every wall twice on a maze's first frame: MazeView.build draws the walls unmarked, then the frame's walls key (always three marks) triggers MazeView.rewall at once (R0053 code review 001 F5). Once per maze, so cheap; fix by letting MazeView.build take the marks (or the frame's maze and marks) so the first frame builds once, keeping f0126's views.spec 'rebuilds once per walls key' and f0109's wallColorOf pin green.

## Non-goals
- The pellets, the doors and the floor: MazeView.build draws them as it does now, and PelletView.build still gets the maze's layout (`Maze.layout(frame.maze)`) and the model.
- Main's walls key (View.wallsKey) and when Main calls MazeView.rewall: unchanged, once per change of the key, the maze's first frame included (f0126's views.spec pins it).
- Colours: View.wallColor, the flash and the edible green stay f0109's and f0126's, untouched.
- A new maze still builds a new model (Main destroys the old one); only one layout exists today ("classic").

## Solution
Captured idea (unchanged): let MazeView.build take the marks (or the frame's maze and marks) so the first frame builds once, keeping f0126's views.spec "rebuilds once per walls key" and f0109's wallColorOf pin green.

Added at prep: `MazeView.build(m, marked?)` draws the walls with the marks, and Main builds from the frame's maze (`View.frameMaze(frame)`, holes open) and the frame's marks. Main keeps calling `MazeView.rewall` on the first frame (views.spec counts it), so MazeView remembers the walls each model has drawn, as a key of their runs (`View.runsKey`, pure), and a rewall to walls already drawn makes and destroys nothing. The first frame then draws every wall once: the build draws them, and the rewall finds them drawn.

## Design
Decisions relied on (`pickman/.tracker/game-design.md`): "Marked walls: three interior walls ... at a time are gold; a finished pick marks the next at once" and "Marked walls stay gold while the walls are green (f0109 ...); the level-clear flash still lights them white" (f0126); "The maze walls ... are green (14, 64, 14) while the power timer runs ..., blue (33, 33, 222) otherwise, and white during the level-clear flash, which wins" (f0109). This chore changes none of them: the walls look exactly as before; they are drawn once instead of twice.

Why the skip lives in MazeView, not in Main: the obvious fix (Main sets `wallsKey = key` in its build branch, skipping the first rewall) turns f0126's promoted views.spec case "Main rebuilds the walls once per change of the holes or the marks, from the frame's maze" red, because it counts one `MazeView.rewall` call on the first frame (mutant M14 in the mutation check); the capture says that case stays green. So Main still calls rewall once per key change, and MazeView makes that call cost nothing when the walls are the ones it has drawn.

**Pure (Logic), `pickman/src/shared/Logic/View/init.luau`:**
```lua
-- A key that changes exactly when the runs do (c0228): each run's bounds and whether it is marked, in order.
function View.runsKey(rects: { Rect }): string
```
One `x0,y0,x1,y1,m` entry per run, `m` = `1` when `r.marked == true` else `0` (so `marked = false` and `nil` are the same, as MazeView draws only `marked == true` gold), joined by `;`. View.walls returns its runs row by row in a fixed order, so equal mazes and marks (any tables, the marks in any order) give equal keys, and runs that differ in any bound, in count or in the mark give different keys. The comparison that could be wrong (which walls are "the same") is in Logic, as pickman-arch rule 3 asks, and is unit-specified (runs.spec). Compared by value, never by table identity (lesson pickman-arch/source-changes-compare-values): View.frameMaze hands back a new maze table whenever the holes' key changes, and every frame carries new mark tables.

**Adapter, `pickman/src/client/MazeView.luau`:**
- `MazeView.build(m: Maze.Maze, marked: { Maze.Tile }?): Model`: as now, with the walls drawn by `walls(model, m, marked)`; `build(m)` with no marks draws what it draws today (f0109's place spec builds `MazeView.build(Maze.layout("classic"))` and paints it).
- `MazeView.rewall(model, m, marked)`: unchanged signature and body (`walls(model, m, marked)`).
- `walls(model, m, marked)` (local): `local runs = View.walls(m, nil, marked)`; `local key = View.runsKey(runs)`; if `drawn[model] == key`, return (no part made, none destroyed); else `drawn[model] = key`, destroy the `Wall` and `MarkedWall` parts and draw one per run, as now (`"Wall", wallColorOf(model)` and `"MarkedWall", wallColorOf(model, true)`, so f0109's text pin `"Wall", wallColorOf(` and f0126's adapters.spec pattern `View.walls(m, nil, marked)` still match).
- `local drawn: { [Model]: string } = setmetatable({}, { __mode = "k" }) :: any`: module state, keyed by the maze model, weak so a destroyed model (Main destroys it on a new maze) is collected with its entry. A key lost early (Roblox may collect an Instance key from a weak table when no Lua reference holds it; Main's `model` local holds it) would only make the next rewall draw again: never a wrong skip.
- Colours of skipped walls: the parts stay, and MazeView.flash and MazeView.edible repaint every wall part from the model's attributes as they change (`paint`), so walls a rewall skips have the colours a redraw would give them (walls.spec case "keeps their lit and edible colours"; f0126's "rebuilt while lit: lit").

**Adapter, `pickman/src/client/Main.client.luau`** (the frame handler):
```lua
	local marked = if frame.walls then frame.walls.marked else {}
	if built ~= frame.maze then
		...
		local m = Maze.layout(frame.maze)
		-- built with the frame's holes and marks, so the rewall below finds them drawn and the walls are built once (c0228);
		-- its floor is the layout's all the same, since picks open interior walls only (View.bounds' margins stay put)
		local walls = MazeView.build(View.frameMaze(frame), marked)
		model = walls
		pellets = PelletView.build(m, walls)
		lit = false -- new walls are built unlit
		wallsKey = nil
	end
	local key = View.wallsKey(frame)
	if model and key ~= wallsKey then
		wallsKey = key
		MazeView.rewall(model, View.frameMaze(frame), marked)
	end
```
`frame.walls.marked` and `MazeView.rewall(model, View.frameMaze(frame),` stay in the text (f0126 adapters.spec "Main rebuilds the walls from the frame's maze and marks when View.wallsKey changes"). No `return` is added to the handler, and the `MazeView.edible` and `DangerHud.wallState` lines are untouched (tests/place/main-walls.spec). View.frameMaze caches the last holes' maze, so the second call in the first frame returns the same table.

The floor (design review 001 F4): MazeView.build sizes the floor from `View.bounds(m)`, whose tunnel margins come from `wraps()` over the maze's first row and column, and build now gets the frame's maze rather than the layout. They agree because picks mark and open interior walls only (`pickman/src/shared/Logic/Picks/init.luau:44`; game-design.md "three interior walls (not on the maze's outer edge)"), so a hole never opens a tunnel. The comment at the build call says so, and walls.spec "Main builds every wall once …" checks that the floor's size and position with holes open equal `MazeView.build(classic)`'s. A later pick rule that allowed edge walls would turn that case red rather than silently move the floor.

**Server authority:** none involved. Everything here is client rendering of what the server's frame already says (its maze, holes and marks).

**No behaviour change for players** (chore checklist): the walls on screen are the same parts in the same places and colours on every frame; only the first frame of a maze makes about half the parts it made (240 runs on classic, so 240 parts instead of 480). walls.spec's `drawnAs` checks pin the walls' runs and colours after every step; f0126's views.spec and f0109's place spec stay green on the prototype (E2).

### Scalability
Per frame: nothing new while the walls key holds (Main does not call rewall). Per walls-key change after the first frame (a pick, a new level): `View.walls` is computed once, as now, plus `View.runsKey` over its runs (one short string per run: 240 on classic) and one string compare. On a maze's first frame `View.walls` and `View.runsKey` run twice each (once in build's draw, once in the rewall that finds the walls drawn), where main runs View.walls twice too (build and rewall) and also makes and destroys ~240 parts (design review 001 F4). On a maze's first frame the client now makes ~240 wall parts instead of ~480 and destroys none (R0053 code review 001 F5). Grows linearly with the maze's wall runs, as View.walls does. Nothing replicates: the maze model is the client's own.

### Maintainability
A new maze layout or a new kind of mark needs nothing here: the key is computed from View.walls' runs, so whatever changes the runs changes the key. A new field on View.Rect that changes how a run is drawn must be added to `View.runsKey` too; the function's comment says so, and runs.spec pins every field it has now. The skip is one place (MazeView's local `walls`), used by both build and rewall.

### Usability
Player: unchanged (the same walls; the busiest frame of a maze gets cheaper). Developer API: `MazeView.build(m, marked?)` gains one optional argument with the same meaning as rewall's third; `MazeView.rewall` may be called with the walls already drawn at no cost, so a caller need not track what it last drew; `View.runsKey(rects)` is a small typed pure function.
