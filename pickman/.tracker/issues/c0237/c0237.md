# c0237: Lobby tooling pattern

## Problem
f0061/lobby-tooling.spec line 55 uses %{ and %} in a Lua pattern; luau-lsp rejects it (FormatString: expected a magic character after %), so the type stage and the stop hook fail on main

## Non-goals
Changing what the spec asserts.

## Solution
Write the braces unescaped (`"%${p}"`); `{` and `}` are not magic in a Lua pattern. Chore, so a promoted spec is edited in its own raft (user, 2026-11-03: "Go ahead just fix main").

Decided with the user (2026-11-04): "Run a tiny raft". The fix itself already landed on `main` as a plain PR (#230, 51968dcc), which skipped the lifecycle (lesson zz-rules/a-tracked-fix-lands-through-its-raft); this raft is the issue's design, review and `done`, with no further code change.

## Design
The code change is already on `main` (PR #230, commit 51968dcc): `pickman/tests/acceptance/f0061/lobby-tooling.spec.luau` line 55 reads `'^%s*for f in "%${p}"%*%.project%.json; do'`. `{` and `}` are not magic in a Lua pattern, so the escape `%{` that luau-lsp rejected (FormatString) is gone. The raft's executable work is to verify that state and close the issue: no source or spec edit.

### Scalability
One line in one spec; nothing grows with the repository.
### Maintainability
The pattern is shorter and matches the same text. AC2 stops the escape returning.
### Usability
The pickman type stage and the stop hook pass on `main` again; the evidence is the full gate that merged #230 (type stage included) and, at `done`, this raft's `--full` gate.

**No behaviour change** for players: nothing in `pickman/src/` changes. The spec still asserts what it did, that lobby tooling loops over `"${p}"*.project.json` (AC1).
**Overrides**: `pickman/tests/acceptance/f0061/lobby-tooling.spec.luau`, already changed by #230. It still pins the lobby tooling's project loop; only the pattern's spelling changed. Nothing in this raft edits it again.
