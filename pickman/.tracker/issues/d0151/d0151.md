# d0151: Touch input reaches nothing

## Problem
The user, 2026-10-25, testing the Beta game on a phone: "Nothing responds": swipes don't turn, the right-half look drag doesn't look, and the snap button doesn't snap. So no touch input reaches the game's controls at all, although R0012 shipped them (f0027 swipe turns, f0028 the look drag, f0029 the snap button and the mobile HUD) and their headless specs pass.

What should happen: on a phone, today's touch controls work as f0027 to f0029 specify (a left-half swipe turns, a right-half drag looks, the snap button recentres the view), found and fixed at the cause.

Decided with the user (2026-10-25): this is split out of d0149's first step ("Prep finds why today's touch controls fail … before redesigning them") as its own defect, done first. f0110 (Touch fire and hop, R0051), the stopgap the user chose to land before d0149, depends on it: its FIRE and JUMP buttons use the same input path, so R0051 is not readied until this is done. d0149 keeps the circle redesign.

Scope decision (user, 2026-10-26): "Close d0151 (Recommended)", asked as: "There's no touch jump yet: f0110 adds the JUMP and FIRE buttons, but it's blocked until d0151 is done, and d0151 doesn't reproduce. Close d0151 so f0110 (your JUMP button) can go ahead?"

The finding behind it (the author's record, from the user's retest on 2026-10-26, Beta, a phone in landscape): the user wrote "The steering works but literally nothing shows on the screen except one inert little round ring", answered "Yes, view rotates" to a right-half drag and "Yes, it snaps back" to tapping the ring after looking away, and asked "Still don't know how to jump". Their screenshot shows the HUD f0029 specifies: the score (700) top-left, LEVEL 1 top-right, two lives bottom-left, the radar, and the snap ring bottom-right; so "nothing shows" means no on-screen controls (no way to jump or fire), which is f0110's buttons and d0149's circles, not a missing HUD (design review 001 F1). The defect does not reproduce, and the build did not change between the reports (E2).

## Non-goals
- d0149's circle controls (steer and look circles, tap to jump, shoot and pick buttons).
- f0110's FIRE and JUMP buttons (R0051).
- Gamepad controls (f0146).

## Solution
- Find where touch is lost on a real phone before changing anything: whether `Main.client.luau` reaches `Controls.start` on a touch device (an error in an earlier `start`), whether `UserInputService.InputBegan` delivers `UserInputType.Touch` there, whether a GUI or Roblox's own touch handling consumes the touches, and whether the session runs at all. The runtime tests (`tests/runtime/`, Open Cloud Luau Execution) and a device's developer console are the probes; the cause decides the fix.
- Pin the cause with a spec that fails on today's code (a headless one where the cause allows it), so it can't come back.

## Design
No code change. The finding: on a phone (2026-10-26), today's touch controls work as f0027 to f0029 specify: a left-half swipe turns, a right-half drag looks, and the snap control recentres the view. The first report ("Nothing responds", 2026-10-25) was not reproduced, and nothing in the touch path changed between the two tests, so no cause can be pinned. The snap ring looks inert while the view is already straight ahead, because snapping a centred view changes nothing.

The delivery is the record: this issue's `check.sh` reruns f0027's, f0028's and f0029's promoted touch specs, so the issue is done only while the headless touch path still passes, and the phone test is Observed (OC1).
