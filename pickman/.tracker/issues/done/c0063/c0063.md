# c0063: Narrow play again specs

## Problem
R0015's f0031 gave game over a PLAY AGAIN prompt, and its acceptance specs were promoted into `tests/acceptance/f0031/` when R0015 was done (2026-10-02). They pin that behaviour exactly: the `playAgain` field and the `PLAY AGAIN (Enter)` button of `Flow.overlay`, the `PlayAgain` remote and the server handler that calls `Session.playAgain`, `FlowView` firing that remote, and the whole-run flow ending in a new run. f0065 deliberately replaces it (results, then a tap, then a teleport to the lobby). Promoted specs are never edited during execution, so a chore has to narrow them first, or f0065 cannot land.

## Non-goals
- Any behaviour change: this chore only removes or narrows assertions.
- The new game-over flow itself (f0065).

## Solution
Narrow the four promoted specs of f0031 so they pin only what stays true after f0065 (designed in R0034): READY!, the dying fade, the level-clear flash, the GAME OVER results, a thin server that leaves the decision to Logic, the client wiring and the whole run on screen. Every assertion on the play-again surface that f0065 replaces goes: the `PlayAgain` remote and its handler, the `playAgain` overlay field, `Flow.PLAY_AGAIN_KEYS` and `Flow.isPlayAgainKey`, and the cursor wired to `.playAgain`. No spec file is deleted, so f0031's `check.sh` keeps every line; only the labels of its AC1, AC2 and AC4 are corrected, in this prep (a `check.sh` is sequestered during execution), and f0031's document gets a dated note saying what is no longer pinned. The exact edits are `experiments/narrowing.patch` (written and run in this prep).

## Design
### Which assertions f0065 turns red (from R0034's prototype)
f0065 (R0034) changes, in the game place: the `Flow.Overlay` field `playAgain` becomes `tap` (a tap asks for the lobby now), with new fields `prompt` and `cursor`; `Flow.PLAY_AGAIN_KEYS` and `Flow.isPlayAgainKey` become `Flow.CONTINUE_KEYS` and `Flow.isContinueKey`; the `PlayAgain` remote and its `Sessions` handler go, replaced by `ToLobby`/`LobbyStatus` and a new `Returns` adapter; Main calls `Camera.setCursor(overlay.cursor)`. Logic's `Session.playAgain`/`Game.playAgain` stay (f0016, f0017, f0018, f0023 and f0030 specs pin them). Against that, case by case:

| spec :: case | after f0065 | change here |

| every other case | unaffected | unchanged |

Each changed file gets a header line `Narrowed by c0063: …` saying what is no longer pinned and why. `narrowed.spec` reads f0031's specs as text, so only `--full` runs it; its header says any later change to them must update it (design review 001 F4).

**`tests/runtime/structure.luau` is not touched here** (the draft listed it): it is not a promoted spec, so f0065 may edit it freely, and on `main` the `PlayAgain` remote still exists until f0065 lands, so removing the Beta assertion now would only weaken it. The promoted assertion that ties it to `PlayAgain` (adapter's last case) is what blocks f0065, and that is deleted here. f0065 replaces `PlayAgain` with `ToLobby`, `LobbyStatus` and `LobbyPlaceId` there itself.

### Scalability
No runtime change. The specs stay in-process text and Logic checks (0.1 s each).

### Maintainability
The narrowed specs pin the presentation that is stable (phases, fade, flash, results) and leave the game-over action to whichever feature owns it (f0065 now). The header lines say so, so nobody restores the deleted cases.

### Usability
Developer: the specs keep their names where their meaning did not change; renamed cases say exactly what they still pin.
