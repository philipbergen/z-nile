### F1 [high] The narrowed key-map spec no longer pins which keys `View.KEYS` binds, so a map with none of the ten keys passes the whole suite
Where: experiments/narrowing.patch, the `keys.spec` hunk `for _ in View.KEYS do n += 1 end` (the removed `t.expect(want[key]).toBe(action)`); c0150.md Design table row 1 ("keep the `want` table and its loop through `View.action` (all ten bindings)")
Evidence: `Controls.luau:82` binds `for name in View.KEYS do`, and `View.action` reads a separate local `KEYS` (`View/init.luau:223`). In the clone, with the patch applied, I replaced line 67 with `View.KEYS = table.freeze({ F1 = "Fire", …, F10 = "Fire" })` and left `View.action` as it was. Narrowed `keys.spec`: `4 passed, 0 failed`. The whole pickman suite (`lune run tests/run`): `1404 passed, 0 failed, 206 spec files`. On main's `keys.spec` the same mutant fails `maps exactly the ten keys`. In the game, Controls would then bind F1 to F10 and none of W A S D, Space, E or the arrows. So the captured outcome "the ten f0104 bindings are still pinned" is met only through `View.action`, which is not what the client binds.
Critique: the old loop checked every entry of `View.KEYS` against `want`. Dropping it so that F can be an eleventh key also dropped the only check of `View.KEYS`'s own entries. The tempting fix, keeping `n >= 10`, is what lets ten junk keys through.
Consequences: a per-key check through `View.KEYS` turns this mutant red and still lets F = "Pick" pass. The digest must be re-taken, and Rules and mutants needs a row for it.
Recommendation: in the `want` loop assert both accessors: `t.expect(View.KEYS[key]).toBe(action)` and `t.expect(View.action(key)).toBe(action)`. Add mutant N9, "`View.KEYS` replaced by ten other keys while `View.action` still reads the real map", to Rules and mutants and E3, run it, re-take `KEYS_SHA`, and re-run E1 and E2.

### F2 [medium] Extra keys may now take the ten keys' actions, a second movement key included, which f0126 doesn't need and the case title still forbids
Where: narrowing.patch (`keys.spec`); c0150.md "What the narrowed specs still limit f0126 (and later keys) to" ("any further key may be bound to anything that is not a movement intent's key"); the case title "…only W A S D are movement intents"
Evidence: in the clone, with the patch applied, `local KEYS … = { Z = "Forward", X = "Back", G = "Jump", …` passes the narrowed `keys.spec` 4/4. Main's spec rejects it (`n == 10`, `want[key]`). The second case only tests `Movement.isIntent` on six named keys, so "only W A S D are movement intents" is no longer true of the file. The capture asks for each spec "narrowed to what it was written to protect". f0126 needs one new key bound to a new action (`F = "Pick"`), never a second Forward or Jump key. The Design's sentence is ambiguous: it reads as "a further key may not be bound to a movement intent", which no case checks.
Critique: this loosens more than f0126 needs. A later key binding (Z to Forward, an extra jump key) would land green and unreviewed against f0104's decision.
Consequences: constraining the extras keeps any key outside the ten free for a new action, so F = "Pick" passes, and keeps out duplicates of the ten actions. A later issue that wants a second movement key must narrow again, which is the intended friction. The extra-key rule doesn't depend on Pick, so c0150 still doesn't pin f0126's choice.
Recommendation: inside the counting loop, for `want[key] == nil`, assert that `action` is not one of `want`'s actions, which also covers `Movement.isIntent(action) == false`. Rewrite the Design sentence to say exactly that. Add mutant N10 ("an extra key bound to Forward" and "an extra key bound to Jump") and run it. Run E2 again: the prototype's F = "Pick" must pass.

### F3 [high] The digest's whitespace tolerance lets a later edit comment out the shown-tick check, or empty a needle, and still match `PLACE_SHA`
Where: acceptance/narrowed.spec.luau `normalised` (`string.gsub(text, "%s+", " ")`) and its header ("comments are pinned too, so no code can hide in one"); c0150.md Maintainability ("exactly three tolerances… so no code can hide in one"); E3
Evidence: two edits, both run in the clone with the patch applied.
(a) M1: in `place.spec`, join the comment line `-- that tick is View.shownTick … View.alpha` and the whole `local blend = string.match(…)` / `t.expect(blend ~= nil).toBe(true)` block into one comment line, so those statements become comment text. `narrowed.spec` plus `place.spec`: `8 passed, 0 failed`. `stylua --check` also passes the mutant. With the camera then changed to `local shown = snap.tick`, both still pass, while main's `place.spec` fails the eye case. Collapsing `\n` to a space erases the one character that ends a `--` comment, so a whitespace-only edit here is not harmless. `place.spec:52` is the only comment inside a case body in either file.
(b) M2: change `has(src, "Vector3.new(6, 7, 6)")` to `"Vector3.new(6,  7,  6)"` (two spaces). `narrowed.spec`: `3 passed, 0 failed`. The `toBe(false)` in GhostView's case can then never fail, because whitespace inside a string literal is collapsed too.
Critique: the claim "only whitespace is tolerated, so no code can hide in a comment" is false for this file. N8 tested only a `--[[ ]]` block comment. The fix the author will reach for is to drop the comment at line 52, but a later edit could add one back, and (b) is still open.
Consequences: a normaliser that keeps the newline after every line comment, and the whitespace inside every string, still tolerates a stylua reflow (stylua neither moves comments nor edits strings) and a compaction. It is stricter than c0103's normaliser, so the two copies diverge. c0103's copy can't be exploited this way today: f0014's `keys.spec` has comments only in its header, where joining the first `require` line makes the spec error, and no string literal contains whitespace. The zz-test lesson that tells authors to normalise "as c0103 does" needs a note (lesson candidate below).
Recommendation: before collapsing, (1) mark the end of each line comment, e.g. `text = string.gsub(text, "(%-%-[^\n]*)\n", "%1 \u{0} ")`, so joining a line into a comment changes the normalised text; and (2) escape whitespace inside every one-line quoted string, e.g. `string.gsub(text, '"[^"\n]*"', function(s) return (string.gsub(s, "%s", function(c) return string.format("\\%03d", string.byte(c)) end)) end)`. A quote mis-paired in a comment only makes that span stricter, so it fails closed. Then fix the header and Maintainability wording, add mutants M1 and M2 to Rules and mutants and E3 for both files, re-run N1 to N8 (and F1's and F2's new mutants), and re-take both digests.

Lesson candidates (for the prep's lead):
- zz-test/narrowing-pins-the-whole-file (note): whitespace collapse must keep the newline that ends a line comment and the whitespace inside string literals, or a whitespace-only edit comments out code or empties a needle. Check: can joining two lines, or changing the spaces inside a string, change what the pinned file asserts while its normalised text stays the same?
- zz-test (new): narrowing "exactly these N" to "at least N" keeps a per-member check on the accessor the code actually uses (here `View.KEYS`, which Controls binds), and constrains the extras to what the narrowing is for. Check: for each assertion the narrowing removes, which `src/` mutant did it alone kill, and does the narrowed file still kill it?
