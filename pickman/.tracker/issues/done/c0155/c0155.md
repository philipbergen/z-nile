# c0155: Narrow f0110's and f0146's button-table pins

## Problem
f0126 (risky wall picks) adds its pick to every input, by the user's rule (2026-10-25: "We support keyboard, cosole, and touch for every feature"): a touch PICK button beside f0110's FIRE and JUMP, and the controller's Y / triangle in f0146's button map. The user decided that f0126 lands after f0110 ("PICK button after f0110") and after f0146 ("f0126 after f0146"). Two of those issues' acceptance specs, promoted when they are done, compare their tables exactly, so f0126's additions would turn `main` red and an executor may not edit a promoted spec:
- f0110's `buttons.spec` case "Touch.buttons is the snap, fire and hop rectangles together" checks `Touch.buttons(box)` with `toEqual` against exactly the snap, fire and hop rectangles; f0126 adds `pick`.
- f0146's `pad.spec` case "the constants and the button map" checks `Pad.BUTTONS` exactly; f0126 adds `ButtonY = "Pick"`.

What should happen: each case is narrowed to pin its own entries one by one, so that added buttons (f0126's now, d0149's later) do not fail it, while every entry it pins today stays pinned. If f0110's or f0146's prep makes that change itself before landing (f0126's prep asked both on 2026-10-25), this chore checks that and has nothing left to narrow for that spec.

Scope decision (user, 2026-10-31): "Verify only (Recommended)": both cases were already narrowed entry by entry by f0110's and f0146's own preps, so this chore only checks that, with a spec that runs the two cases; it does not pin the two files whole by digest (the Solution's "pin the narrowed files whole (as c0150 does)"), so that d0149, which replaces f0110's buttons, needs no chore to undo a digest.

Scope decision (user, 2026-10-31): "Own action, like keys (Recommended)": a pad button added to `Pad.BUTTONS` beyond today's seven must have an action of its own (none of the seven's, no other added button's), as c0150 rules for the keys; f0146's narrowed case no longer checks that, so c0155's spec does, on the real map (design review 003 F2).

## Non-goals
- f0126's PICK button and Y binding themselves.
- Any other case of those specs.

## Solution
- After f0110 and f0146 are done: in each promoted spec, replace the whole-table comparison with one assertion per pinned entry, keep the case's name meaning, and pin the narrowed files whole (as c0150 does), with a header line saying what is no longer pinned and why.

## Design
Nothing is left to narrow. On `origin/main` (0db4aa6d), both promoted cases already pin entry by entry:
- `pickman/tests/acceptance/f0110/buttons.spec.luau` :: "Touch.buttons holds the snap, fire and hop rectangles (a later control may add a field)" checks `b.snap`, `b.fire` and `b.hop` one by one with `toEqual` against `Touch.snapRect`, `Touch.fireRect` and `Touch.hopRect`, for every sample screen. An added field (f0126's `pick`) is never read.
- `pickman/tests/acceptance/f0146/pad.spec.luau` :: "the constants and the button map" loops over its seven-entry `want` table with `t.expect(Pad.BUTTONS[key]).toBe(action)`. An added key (f0126's `ButtonY = "Pick"`, f0143's `ButtonL3`) is never read, and its other lines (`Pad.action("ButtonX")` is nil, no `Pad.BUTTONS` key is a `View` key) still hold for both.

f0126's own design says the same (its Regression guard: "both now pin entry by entry (E10, rerun at design review 009), so the chore c0155 captured for them has nothing to narrow and is no longer a dependency"), and f0126 no longer lists c0155 in `depends_on`.

So the chore adds one acceptance spec and changes nothing else. `acceptance/narrowed.spec.luau` checks the narrowing **by behaviour**, not by text:
- It requires both promoted spec modules (`@tests/acceptance/f0110/buttons.spec`, `@tests/acceptance/f0146/pad.spec`; a spec module only collects its cases when required, it runs none) and the same `@logic/Touch` and `@logic/Pad` tables they require (one module cache per spec file, so a field replaced here is the one the case reads).
- It finds each case by its exact name (exactly one match), and runs its function under `pcall`, counting only a failure whose message is one of `t`'s assertions as a fail: `t` raises at its caller's line, so the message starts `<file>:<line>: expected `, which Luau's own errors (`… (table expected, got nil)`) never do (design review 001 F2). Any other error fails this spec instead.
- f0110's case: it wraps `Touch.buttons` (`edit(real(box), n)`, `n` the call's number from 1), counts the calls and the distinct boxes they get (a box is told apart by `safeX`, `safeY`, `safeW`, `safeH` and `margin`; today's 13 sample screens give 13 distinct boxes), and puts the real one back after each run. The case must pass unchanged and with an extra `pick` rectangle. It must call `Touch.buttons` with at least 13 distinct boxes (a floor, so a later issue may add screens, lesson zz-test/promoted-specs-pin-rules-not-sets; distinct boxes, not calls, so a case that checks one screen 13 times fails, design review 002 F1), and for every call `k` on its own it must fail when `snap`, `fire` or `hop` has any one of `x`, `y`, `w`, `h` off by one pixel either way (+1 and −1, so a `<=` or `>=` compare fails too, design review 003 F1), or is missing (13 × 3 × 9 = 351 runs, about a second; design review 001 F1: moving every screen's `x` at once let a case that checked one screen, or only `x`, pass).
- f0146's case: it replaces `Pad.BUTTONS` with a frozen copy and puts the real table back after each run. The case must pass on today's map, and with `ButtonY = "Pick"` and `ButtonL3 = "Boost"` added, and must fail when any of the seven entries is swapped to another real action or removed. The spec holds its own copy of today's seven entries, and first checks that the case passes on exactly that copy, so each failure below is that one entry's.
- Added pad buttons (the user's scope decision above): every key of the real `Pad.BUTTONS` beyond today's seven must map to an action none of the seven has and no other added key has. The rule runs on the real map (the one `Controls` binds), and checks that `Pad.action(key)`, the accessor `Controls` resolves a press with, gives each key's map entry (design review 004 F1); and on planted maps: f0126's `ButtonY = "Pick"` with f0143's `ButtonL3 = "Boost"` pass; an added `ButtonB` reusing any of the seven actions fails, and so does a second button for `Pick`.
- It reaches the two cases through the tables they read today (`Touch.buttons`, `Pad.BUTTONS`). A rewrite of f0146's case to the same pins through `Pad.action` (the accessor `Controls` uses) would turn c0155 red with no defect, and would need a chore; the spec's header says so (design review 003 F3).
- A first case checks that the two cases still exist and that f0110's and f0146's `check.sh` files each have a check line (one starting `check "`, so not a commented-out one) that runs `"$A/buttons.spec.luau"` and `"$A/pad.spec.luau"` (design review 001 F3).
- Ids are written as full `tests/acceptance/<id>` paths (the two requires, `BUTTONS_DIR`, `PAD_DIR` and the header), which a compaction rewrites with the folders (`ids.rewritePaths`, E5); each item folder's id (`.tracker/issues/done/<id>/check.sh`) is taken from the last part of those paths, because a compaction does not rewrite a tracker path inside a `.luau` file. `renamed.id` is wrong here: `z-nile/compaction.txt` already maps an older `f0110` to `f0012`, so it would read f0012's file (E2; lesson zz-test/split-paths-still-need-renamed-id, its c0153 note).

No player behaviour changes: no file in `src/` changes, and AC2 runs f0110's and f0146's own acceptance checks unchanged.

None for players. For executors: a red `narrowed.spec` names the case and the variant (added button, moved or missing entry) that broke.
