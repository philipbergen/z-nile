# f0027: Touch turn controls

## Problem
On a phone there is no keyboard. The player turns with a swipe. Screen-left, screen-right, screen-down, and screen-up become the same four intents the keyboard already sends, and the server already checks.

Decided with the user (2026-10-21), from code review 001 F4:
- Merge on the gates. The Studio premise checks this executor could not run (E9's tap positions, E5's insets and 180° turn, E6's mouse delta during a touch, E7's band top, a fast left-half swipe that must not yaw, and backgrounding the app mid-swipe) are listed in the PR and the final report for the OC1 playtest; the user accepts that risk.

## Non-goals
- Applying look to the camera, and `Camera.holdMouse` (f0028). This issue's fold emits look deltas and snap-on-begin so the zone lock has one implementation; it does not read the mouse and it does not draw.
- `Hud.layout` insets, `Touch.snapRect`, `Touch.blocks`, and the Snap frame (f0029).
- A fifth intent, a swipe clock, gyro, or any gamepad binding. `Controls.luau` must not contain the word `Gamepad`.

## Solution
A pure feature `Touch` classifies a finger at begin and, on finger-up in the turn zone, emits at most one existing intent. `Controls` feeds it `UserInputService` touch events and fires the existing Intent remote.

## Design
Agree with `tracker/rafts/R0012/R0012.md`. The module map and the pinned rectangles live there. This issue creates the feature and the adapter path.

`src/shared/Logic/Touch/init.luau` is the only public API. It requires `./View` and nothing else (the place spec searches the file for the substring `./View`). `tracker/architecture.md` already declares `Touch -> View`. Do not edit that file again, and do not require Movement or Hud.

```lua
export type Zone = "turn" | "look" | "snap"
export type Rect = { x: number, y: number, w: number, h: number } -- half-open
export type Phase = "begin" | "move" | "end"
export type Event = { id: number, phase: Phase, x: number, y: number } -- no time field
export type Finger = { zone: Zone, x0: number, y0: number, x: number, y: number }
export type State = { fingers: { [number]: Finger } }
export type Effect =
	{ kind: "turn", intent: "Left" | "Right" | "Back" | "Forward" }
	| { kind: "look", dx: number, dy: number }
	| { kind: "snap" }
export type Context = { width: number, snap: Rect? }

Touch.MIN_SWIPE = 48
Touch.AXIS_DEGREES = 30

function Touch.empty(): State
function Touch.zone(width: number, x: number, y: number, snap: Rect?): Zone
function Touch.swipe(dx: number, dy: number): ("Left" | "Right" | "Back" | "Forward")?
function Touch.track(state: State, event: Event, ctx: Context): (State, { Effect })

-- Min/Max, as GuiService:GetInsetArea returns it; structural, no engine words.
export type Area = { Min: { X: number, Y: number }, Max: { X: number, Y: number } }
-- An input position (GUI-inset space) in screen pixels: x - none.Min.X, y - none.Min.Y.
-- none nil is the identity; a non-finite Min component counts as 0 on its axis.
function Touch.toScreen(none: Area?, x: number, y: number): (number, number)
-- The screen's size: none.Max - none.Min when both sides are positive and finite, else the fallback.
function Touch.screenSize(none: Area?, fallbackW: number, fallbackH: number): (number, number)
```

Coordinate space (design review 003 F1): every point and rect `Touch` sees is **screen pixels**, origin the top-left of the device screen (`ScreenInsets.None`), the space HudView draws the snap button in. Its size is `Touch.screenSize(GetInsetArea(None), ViewportSize.X, ViewportSize.Y)`: Roblox documents `Camera.ViewportSize` as the device safe area ("not equal to the fullscreen area size on displays with cutouts or notches"), so `ViewportSize` is only the fallback while the area is empty (design review 004 F1). On the documented phone the width is 851, not 733: screen x 400 is the left half (turn), which a 733 width would call look. `InputObject.Position` is not: Roblox documents that "the inset applied to GUI elements (such as from the top bar) is accounted for in the position", and `GetInsetArea` rects are relative to that same core-UI origin. So Controls converts every touch position with `Touch.toScreen(GuiService:GetInsetArea(Enum.ScreenInsets.None), input.Position.X, input.Position.Y)` before it builds the event. On Roblox's documented phone (None `(-59, -58)-(792, 334)`, a 851×392 screen) a finger on the drawn button at screen `(550, 320)` reports `(491, 262)`; unconverted it misses the button and lands on the other side of the half split. Swipes and look deltas are differences, so they do not change.

`Touch.swipe` has two parameters. A third parameter is a type error on the spec's two-argument calls, and a body that returns nil when a missing `dt` is nil fails AC1.

Zone: inside the snap rect (`x >= rect.x and y >= rect.y and x < rect.x + rect.w and y < rect.y + rect.h`) → `"snap"`, including on the right half and including when `width` is not a positive finite number. Else if `width` is finite, `> 0`, and `x < width/2` → `"turn"`. Else `"look"`. Width 0, negative, NaN, and infinite are look, unless the point is inside the snap rect.

Swipe: non-finite dx or dy → nil. Distance `< 48` → nil. `48` on an axis turns. Cone:

```lua
local angle = math.atan2(math.abs(dy), math.abs(dx))
local fromAxis = math.min(angle, math.pi / 2 - angle)
if fromAxis > math.rad(Touch.AXIS_DEGREES) + 1e-9 then
	return nil
end
```

`angle <= pi/4` is horizontal (`dx < 0` → `View.action("A")` which is `"Left"`, else `"D"` / `"Right"`). Otherwise vertical (`dy > 0` → `"S"` / `"Back"`, else `"W"` / `"Forward"`). Screen-down is Back. The epsilon is required so `80 * cos(rad(60)), 80 * sin(rad(60))` is `"Back"`; without it that vector is the dead zone. 31° of length 80 stays nil. `dy = dx * tan(rad(30))` is on the horizontal axis; one pixel past it is nil.

`track` returns a fresh state. A move and an end leave the input finger's `x`, `y`, and `zone` unchanged and return a different table. A begin on `Touch.empty()` still adds nothing to that empty table. Two separate tracks of one begin state to the same move both return that move's delta, so a module-level last point cannot make the second track a zero step. Threading only the returned state is what a pure fold needs for the zero step, and it is not enough by itself: an in-place write and a module-level cursor both pass a zero step taken on the returned state. One finger per zone. `begin` locks the zone and, for snap only, emits `{ kind = "snap" }`. A repeated begin of the same id emits nothing. A look `move` emits the step from the previous point on the **returned** state, including `{ dx = 0, dy = 0 }` when that point is repeated. A turn `move` emits nothing. A turn `end` swipes from `(x0, y0)` to the **end event** position, not along the path. Look and snap ends emit nothing. Unknown phase, unknown id: nothing. A turn finger and a look finger may be down together. A later `width` does not reclassify: begin at `x = 9` on a width of 20 is turn; end at `x = 100` on a width of 10 emits `{ kind = "turn", intent = "Right" }`.

`src/client/Controls.luau`:

```lua
function Controls.start(
	onSnap: () -> (),
	onLook: ((dx: number, dy: number) -> ())?,
	snapRect: (() -> Rect?)?,
	onTouch: ((held: boolean) -> ())?
)
```

`Controls.start(Camera.snap)` in `Main` stays valid. This issue does not edit `Main`. On start, set `GuiService.TouchControlsEnabled = false` (the source contains `TouchControlsEnabled = false`). Subscribe to `InputBegan`, `InputChanged`, and `InputEnded`. Handle only `UserInputType.Touch`. The identifier `gameProcessed` does not occur in `Controls.luau`. The callback's second parameter is `_`. A later text box that must swallow a gesture is a new issue, not a branch in this `Controls.start`. Assign a monotonic integer id per `InputObject` in the adapter; Logic never sees the instance. Per touch event, read the area inline in both calls, so it cannot be cached at start (the first frames can report an empty area, and rotation changes it; `(Enum :: any)` cast allowed): `local sx, sy = Touch.toScreen(GuiService:GetInsetArea(Enum.ScreenInsets.None), input.Position.X, input.Position.Y)` and `local sw = Touch.screenSize(GuiService:GetInsetArea(Enum.ScreenInsets.None), camera.ViewportSize.X, camera.ViewportSize.Y)` (any local names). Both locals are made in the same function as the single `Touch.track(` call (the input handler), with no helper between that returns the pair, and `toScreen` reads the event's own `input.Position.X, input.Position.Y`: a width computed once in `start`, or an origin cached as `Touch.toScreen(area, 0, 0)` and added later, is wrong (design review 005 F1). The single `Touch.track(` call gets `x = sx`, `y = sy` in its event and `width = sw` in its context, and its argument list mentions neither `Position` nor `ViewportSize`. Call `Touch.track` with that width and with `snapRect()` when `snapRect` was passed, otherwise nil. Apply effects: `turn` → the existing Intent `:FireServer`; `look` → `onLook` when passed; `snap` → `onSnap`. When the finger count goes from 0 to more than 0, call `onTouch(true)` if it was passed; when it returns to 0, call `onTouch(false)`. The source contains `Touch.track(`, `Touch.toScreen(` (before it), `GetInsetArea(Enum.ScreenInsets.None`, `UserInputType.Touch`, and `onTouch(`.

The keyboard path stays: `View.action(`, `BindActionAtPriority`, `:FireServer(`, `View.KEYS`, begin-only, Snap calls `onSnap`, any other action is fired. Do not add a gamepad branch.

Server: no change. `Session.submit` already rejects a non-intent with `"invalid intent"`. The fired value is one of `Movement.INTENTS` (`Back`, `Forward`, `Left`, `Right`).

### Scalability
A touch event walks the fingers already down, which is at most one per zone (three). No per-frame scan of the maze, no replication, no extra remote. The Intent remote stays the rate-limited queue `Session` already has.

### Maintainability
The next gesture is another `Effect` kind plus a branch in `track`, with a synthetic track in `acceptance/`. Thresholds are `Touch.MIN_SWIPE` and `Touch.AXIS_DEGREES`, not literals at the call site. The adapter does not decide the angle. f0029 adds `snapRect` and `blocks` to this same `init.luau`; leave the fold's rules in place when it does.

### Usability
A short or diagonal finger-up does nothing, so a tap in the turn zone is not a turn. The second finger cannot contradict the first. The keyboard still turns. `TouchControlsEnabled = false` keeps the platform thumbstick off the left half (vetoable; see the raft Theme).

The API is the six functions above. `swipe` cannot take a time. `track` cannot mutate its input. Ids are numbers the adapter chooses.
