### F1 [high] Nothing observes the session's ghosts moving: a call site that slows them twice (and slows the eyes) passes all seven cases
Where: `acceptance/speeds.spec.luau:71-83` (AC4), `:53-58` (AC3 eyes), `:20-37` (AC1); Rules and mutants rows "the session's ghosts get the config's factor", "eyes are never tuned".
Evidence: in the scratch clone, mutant MX1 changes one line of `Session.step`'s ghost input, `baseSpeed = s.config.movement.speed,` → `baseSpeed = s.config.movement.speed * (s.config.ghostTuning or 1),` with `Session.join` still passing `{ tuning = s.config.ghostTuning }`. `lune run tests/run -- tests/acceptance/f0125/speeds.spec.luau` → `7 passed, 0 failed`. Under MX1 the shipped ghosts get both factors (`Levels.ghostSpeed(30/1.1, level, kind, 1/1.1)`: by arithmetic about 23 units a tick on level 1 instead of 26, a gain far outside 1.07–1.13) and the eyes `round(2 × 30/1.1) = 55` instead of 60, which the Non-goals and AC3 forbid. The spec can't see it because every case reads only the pure `Session.speeds`, and AC4 re-derives the ghosts' speed with the spec's own `Levels.ghostSpeed(base, level, kind, set.tuning)`, using the spec's `base` rather than the `input.baseSpeed` the session actually hands `Ghosts.step` (`Session/init.luau:383-389`).
Critique: AC1 ("the player's speed over a hunting ghost's") and AC3 ("eyes keep twice level 1's speed") are claims about the game, but they're checked on an oracle that no game code reads for the ghosts. The tempting fix is one more assertion on `input.baseSpeed`, made by wrapping `Ghosts.step` in the spec. That pins an internal, and the next mis-wiring (a tuned `level`, a wrong `kind`) slips past again.
Consequences: a motion case needs ghosts that are active and moving straight (no mode reversal inside the measured window, no tunnel unless that's what it measures), and it needs a units count that survives tile boundaries (`tile` + `progress` along the rails, `Movement.UNITS = 120` per tile). The eyes case needs an eaten ghost (`Ghosts.eat` on an active one, as f0023's specs do). Levels above 1 need the member's `play.level` set, as f0023/f0104 already do by hand.
Recommendation: make AC4 a motion case. Step a `Session.GAME_CONFIG` session in play, and on level 1 and one later level (5) assert that an active hunting ghost covers exactly `Session.speeds(c, level).ghost` units in a step, a frightened one `…frightened` (after `Ghosts.power`), and eyes `…eyes`; add the tunnel if a fixture can place a ghost in the side tunnel cheaply. Add MX1 (input base speed scaled by the factor) and MX2 (eyes speed tuned through the input) as `run` rows, both killed by the motion case. Keep the pure cases: with the motion case, the band in AC1 is about the game rather than just the function.

### F2 [medium] "One function for the speeds" holds for the player only, and f0143's design writes the step line back to `Levels.playerSpeed`
Where: Design "One function for the speeds"; Rules and mutants row M7 (`reasoned`); f0143.md (prep-speed-boost-escape) Behaviour "Speed" and E1.
Evidence: `Session.speeds`' `ghost`, `tunnel`, `frightened` and `eyes` fields are read by no game code: the ghosts compute their own speeds in `Ghosts.speedOf` (`Ghosts/init.luau:373-382`) from `set.tuning`. So there are two computations of a ghost's speed, and the spec judges one against a copy of the other's formula (F1). For the player, M7 is an equivalent mutant (`Session.speeds(...).player` is `Levels.playerSpeed(...)` with the same arguments), so nothing will ever turn red if the call is reverted. And f0143's design writes exactly that line: "the step's speed is `Boost.speed(Levels.playerSpeed(base, level, frightened), Boost.active(member.boosted, s.tick), Movement.UNITS)`". Whichever of the two lands second, an executor following f0143's text undoes f0125's call, and no spec notices. f0143's E1 also measures "f0125's faster player (base 33)", which is route B. The user chose route A. f0125's own document names neither overlap: f0143 isn't mentioned, and f0126 appears only as a reader of `Ghosts.Set.tuning`. f0126's design has the matching note ("whichever lands second merges by hand and reruns the other's specs"); f0125's doesn't.
Critique: the Maintainability section claims "one function decides a config's speeds, used by the step and by the spec", and the lesson it cites (zz-test/one-rule-one-function) is met only for the player. The author will be tempted to keep M7 `reasoned` and rely on code review. That fails the moment f0143 merges.
Consequences: routing the ghosts through `Session.speeds` (for example, `Ghosts.Input` carrying the level's `Speeds`) would make the claim true, but it changes `Ghosts`' public `Input`, makes `set.tuning` redundant for speed while f0126 still reads it for the pick's length, and needs f0126's V6 to follow. Rewording the claim costs nothing, and F1's motion case then ties the oracle to the real ghosts.
Recommendation: say plainly that `Session.speeds` is the step's source for the player and the specs' oracle for the ghosts, tied to the real ghosts by F1's motion case. Mark M7 as an equivalent mutant (not a rule a spec can pin), and keep "the step calls `Session.speeds`" as a code-review item. Add a Regression guard bullet for each overlap. For f0143: the step line becomes `Boost.speed(Session.speeds(s.config, level, frightened).player, …)` whichever lands second, and its E1 premise (route B's base 33) no longer holds; under route A the player is unchanged and the ghosts are slower, so its margins only grow. For f0126: it reads `member.ghosts.tuning`, its picks become 47/42/38 steps at 1/1.1, and its V6 proves that. In both cases, whoever lands second reruns the other's specs. The lead should pass the f0143 note to f0143's prep.
Lesson: zz-test/one-rule-one-function

### F3 [medium] `ghostTuning` has no upper bound: a config whose ghosts cover two tiles a tick is accepted, and contacts miss
Where: Design "Config and validation"; `Session.new` in the prototype (`k ~= k or k <= 0 or k == math.huge`).
Evidence: probe in the scratch clone: `GAME_CONFIG` with `movement.speed = 96` (f0018 pins 96 as accepted) and `ghostTuning = 2` → `pcall(Session.new, …)` returns `true`, and `Session.speeds(c, 5)` gives a ghost 228, a tunnel 120 and a frightened 144 units a tick, all against `Movement.UNITS = 120`. `Ghosts.contacts` (`Ghosts/init.luau:581-600`) detects only a shared tile or a swap of tiles within the tick, so a ghost moving about two tiles a tick can pass through the player. The design places the check "next to `checkLevelSpeeds`", which refuses exactly this for the player.
Critique: the tempting fix is `k <= 1` ("slower ghosts" only). That's a product rule nobody asked for, and it still leaves base speeds where a k of 1 is near the limit.
Consequences: the bound must hold for every level and every tuned kind (normal, tunnel, frightened; eyes are untuned and run at 2 × base, the same today, out of scope). f0018's pins (base 96 accepted, 97 refused with no tuning) must stay green: at k = 1, base 96's fastest ghost is 114.
Recommendation: refuse, in `Session.new` beside `checkLevelSpeeds`, a `ghostTuning` for which any level's tuned ghost speed exceeds `Movement.UNITS` (`session: ghostTuning {k} is too fast: level {l} ghosts would be {v} > 120`). Add cases: base 96 with k = 1.1 is refused (level 5's ghost 125), base 96 with no tuning and `GAME_CONFIG` are accepted. Add a row to Rules and mutants (mutant: the bound dropped).

Consequences: none.
Recommendation: record the measured catch time (9.3 s against 12.3 s, floor 8 s) in the Regression guard, so whoever trips the floor knows it was close on the day f0125 landed.
