### F2 [high] The game place's client-triggered writes are not guarded during their yield: held continues are spent without a continue, a leave in the receipt's write loses the hiscore, and a burst of asks fills the server's write queue
Where: §5 the game place (`Continue "ask"`, a fresh grant uses it at once); prototype `Continues.luau` `useOne` (lines 72-88) and the `ask` handler (97-111); the stub `UpdateAsync` returns at once
Evidence: `useOne` checks `Session.offering` before `Purchases.update`. After that call yields, it calls `Session.continue` on the session it captured, ignores the result, and never gives the continue back. Probes (stub `onWrite` hook, firing the event inside the yielding write):
```
P1 two held continues, a second "ask" during the first ask's write:   continues left 0  lives 3  phase ready   (two spent, one continue)
P2 one held, "decline" (and a step) during the ask's write:            continues left 0  phase gameover        (spent, run over)
P3 bought; the player leaves (Sessions -> leave) during useOne's write after the receipt:
   receipt PurchaseGranted; continues left 0  phase ready  lives 3  offer 0;  game over within 45 steps: false
P5 20 "ask" during each other's writes:                                 writes 20  prompts 20
```
P3: the continue revives a parked run (offer off, three new lives), so it never reaches a `GameOver` within `Hiscores.LEAVE_STEPS` (45). The run is dropped with no submission, after the player paid for the continue. This is the F1 (review 001) hole reopened through the adapter. P5: the lobby got the in-flight guard (zz-arch/client-triggered-reads-guarded), but the game place's `ask` did not. A client firing `Continue "ask"` during its own offer (which it can hold open forever) starts one `UpdateAsync` per message, with nothing limiting it. That spends the server's write budget, and once Roblox's throttle queue is full, other players' writes fail. Another player's arrival whose write fails "plays" (G10), so the spam hands a free game to anyone (an alt or a friend) who joins that server.
Lesson: zz-arch/client-triggered-reads-guarded
Critique: the tempting fix is a per-player in-flight flag on `ask` alone. That stops P1 and P5, but not P2 (decline), not P3 (leave) and not a receipt's `useOne` racing an ask.
Consequences: every caller of `useOne` (ask, the test confirm, a fresh receipt grant) needs the same rule: spend a continue only if, after the write returns, the session is still this player's and still offering. Otherwise the continue goes back (a second write that adds it, which can itself fail, so it is better to decide inside one write). The decline and the leave also need a rule while a continue is in flight: either they wait for it, or it loses.
Recommendation: (1) keep one in-flight marker per player in Continues, set before the write and cleared after it. An `ask` while it is set is dropped. A decline while it is set is applied after the write. Clear it on PlayerRemoving. (2) After the write, call `Session.continue` only when `sessionOf(player)` is still the same session and it is still offering. When that fails, give the continue back with `Pay.grant`-style idempotence (a refund keyed by the use), or take the use and the refund in one transform keyed by an id. Add Rules and mutants rows and adapters cases on a stub whose `UpdateAsync` yields (an `onWrite` hook): a double ask with two held spends one; a decline during the write leaves the continue held; a leave during a receipt's continue write keeps the continue held and the run submits within LEAVE_STEPS (through runs.spec's real Sessions/Submits); 20 asks during a write make one write. Mutants: no in-flight guard, no re-check after the write.

### F3 [high] A "buy" arrival is sent back only by the client's teleport: when the teleport fails, the player plays the whole game unpaid
Where: §5 the game place ("otherwise sent back to the lobby (`TeleportService:TeleportAsync` …) with no offer"); Authority ("a 'buy' arrival without the lobby's pass is sent back"); prototype `Continues.luau:49-57` (TeleportAsync in `pcall`, `TeleportInitFailed` not handled, `LobbyPlaceId` unset → nothing)
Evidence: `Sessions` makes the session on `Ready` before Continues decides, and nothing on the server stops it. Probe P4 (a buy arrival, the stub's teleport recorded but the player still in the server): `teleports 1 phase gameover`, so the run was played through to its end (offer off). `TeleportAsync` errors are swallowed and `TeleportInitFailed` is not heard. A teleport also needs the client to cooperate. In every one of those cases, a direct join plays a full free game, and their score is submitted to the boards at its game over.
Critique: the case "a buy arrival goes back" asserts only that a teleport was asked for and the offer is off. A `Continues` that never sends anyone back but switches the offer off fails only on the teleport count.
Consequences: the server has to end the run itself when the teleport fails. The way to do that should not submit a hiscore for an unpaid run, and should not loop when the lobby keeps sending the player back (see F4).
Recommendation: on "back", stop the run on the server. Either kick the player with a message ("start a game from the lobby") when `TeleportAsync` errors, when `TeleportInitFailed` fires for them, or when they are still present after a bound (for example 10 s). Or freeze their session (no intents, no submission). Name the choice in §5. Add cases: TeleportAsync errors → kicked (or frozen) and nothing submitted; TeleportInitFailed → the same; `LobbyPlaceId` unset → the same. Add a mutant row: "back only asks for a teleport".

### F4 [medium] The lobby's pass outlives its game, and a MemoryStore failure breaks G10's "Let them play free"
Where: §5 Purchases `pass`/`takePass`, the game place ("a 'buy' plays only with the lobby's pass (taken once)"); G10 as decided; prototype `Continues.luau:48` (`takePass` only when `how == "buy"`), `Purchases.pass` (errors swallowed)
Evidence: P6: a pass left by a failed lobby read, then an arrival that was charged its free start → `pass left true`. A second arrival in the next 300 s (a direct join, a rejoin, a friend's server) with "buy" → `teleports 0 offer 150`: a free game with the continue offer, and no store failure needed at that point. P7: the lobby's read fails and the MemoryStore is down too → `lobby teleports 1 pass nil`. The arrival's write then succeeds with "buy" and the player is bounced, which contradicts G10 ("a store that cannot be read or written lets the player in"). A `takePass` read that fails on arrival bounces the player the same way.
Critique: the tempting fix of "take the pass on every arrival" closes P6 but adds a MemoryStore read to every arrival. It does nothing for P7.
Consequences: taking the pass on every arrival is one more MemoryStore call per arrival, far inside the budget. P7 is the user's decision to make: the pass is a second store, and its failure has no fallback that is both safe and free.
Recommendation: take (remove) the pass on every arrival, whatever the start, and add a case: pass + free arrival, then a buy arrival → back. Mutant: the pass taken only on buy. For P7, escalate to the user: (a) the lobby refuses START with a "try again" line when both its read and the pass write fail (no bounce, but no free game); (b) accept the bounce (a G10 exception, recorded); (c) the arrival lets a "buy" play when its own pass read fails (the bypass reopens whenever the MemoryStore is down). Pin the chosen one with a case.

### F5 [medium] A live publish with a bad product id silently runs the production game in test mode: every player's games and continues are free
Where: G1 (body amended for review 001 F8); `Pay.mode`; §5 `Purchases.ask`/`testGrant`
Evidence: `Pay.mode("live", { play = 1001, continue = nil })` → "test". The test screen then grants plays and continues on BUY (into `PaidPlayTest`), so a live experience with a typo in one attribute charges no one, and nothing says so except the "(TEST: NOTHING IS CHARGED)" line. Review 001 F8 asked for this fail-closed or fail-open choice to be put to the user. The decided G1 body now carries the review's fail-open text, with no user line for that change.
Critique: failing open avoids a hung offer but gives the product away free. Nothing tells the publisher (no warning, no runtime check), and f0169 (the publish) is where a bad id would come from.
Consequences: whichever the user picks, f0169's live publish should check the ids it sets.
Recommendation: escalate to the user: (a) fail open as now, plus a server `warn` when `PaidPlay == "live"` but an id is bad, and a check in f0169's publish that refuses a live publish without both ids; (b) fail closed (no test screens and no free plays when `PaidPlay == "live"` with a bad id; the lobby says the store is unavailable). Record the answer as a `Decided with the user` line in G1, and add a pay.spec or adapters case for the chosen behaviour.
