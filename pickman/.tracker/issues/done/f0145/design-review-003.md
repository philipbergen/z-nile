### F1 [high] Client-triggered store calls are bounded only while one is yielding: back-to-back asks and presses each cost a store call, without limit, in both places (repeat of review-002 F2's P5)
Where: §5 the game place ("a burst of asks makes one write"), the lobby ("One read per player at a time"); Authority ("A client firing `Continue` fast costs one write at a time"); Scalability ("one per START"); prototype `Continues.luau` ask handler and `useOne`, `Paid.allow`
Evidence: the in-flight guards drop a request only while that player's call yields. A request sent after the call returns starts a new one. A client that sends one request per round trip keeps one call running all the time. Probes on `r3`:
```
PROBE2  live, offer 50, none held, 20 "ask" one after another:   writes 20  prompts 20  held true
PROBE2t test mode, the same:                                      writes 20  screens 20
PROBE7  lobby, nothing due, 20 START presses one after another:   reads 20  prompts 20
```
In the game place the offer stays held for as long as the purchase screen is open, which the client controls. In test mode a cancel releases it and the next ask holds it again. So the loop has no end. Each `useOne` with none held is an `UpdateAsync` that changes nothing. The server's DataStore budget is shared (about 60 + 10 × players requests a minute per type), and once its throttle queue is full, other players' calls fail. By G10 a failed call costs the player nothing: a failed lobby read leaves a pass, and a failed arrival write plays. So one client spamming CONTINUE or START hands free games to everyone else on that server, or on the next server they reach. Review 002 F2 named this consequence (P5). The refute's case "twenty asks during a continue's write make one write" fires all twenty inside the write, so it passes while PROBE2 shows 20 writes.
Lesson: zz-arch/client-triggered-reads-guarded
Critique: the in-flight flag stops concurrent requests, not repeated ones. The tempting fix, "drop an ask while the countdown is held", still leaves test mode's cancel-then-ask loop and the lobby's press loop open.
Consequences: any limit has to keep a real player's second try working: START again after a closed purchase screen, CONTINUE again after a cancel. A limit kept per player in a server table resets when the player leaves the server, so the lobby's limit also has to survive rejoins, or be cheap enough not to matter.
Recommendation: question the mechanism, not just this hole. Bound the store calls a client can cause per unit of time, not per call in flight. (1) In the game place: no write for an ask while the player's countdown is held (a screen open or a receipt awaited). Skip the `useContinue` write when this server's last known record for the player holds no continue and no grant has reached this server since. Allow at most one continue write per player per `Continues.ASK_SECONDS` (for example 2 s). (2) In the lobby: at most one read per player per `Paid.PRESS_SECONDS`. A press inside that window answers from the record last read, or is dropped while a screen is open. Add each constant to Maintainability. Spec cases (adapters.spec, since they are rules the gate keeps): 20 asks one after another during one offer make at most one write, in live and in test mode, with a cancel between asks; 20 presses one after another make one read and one prompt; a second press after the window reads again. Mutants: no rate bound (ask); no rate bound (press); the write made while held. Correct the Authority and Scalability lines to state the bound.

### F2 [medium] A continue asked in time, with one held, is lost when the offer's countdown ends during its write
Where: §5 the game place ("Once the write is back, the run continues only if … still in the offer"); prototype `useOne` (the countdown is not held during the flight)
Evidence: PROBE1: `arena("live", 3)` with one continue held. The player asks, and the stub's `onWrite` steps the session 4 times, as the server's 15 steps a second would during a 270 ms write. Output: `gameover true offering false lives 0 continues 1`. The player asked during the offer and holds a continue, yet the run ends and is submitted. The continue comes back as a refund, but the run can't be continued. The window is the length of the write: an ask in the last few tenths of a second, or any ask while the DataStore is slow (its throttle queue, which F1 can fill), loses the run.
Critique: the re-check after the write was review 002's fix for a decline or a leave during the write. It also punishes the player for the store's latency, which is not a choice they made. The tempting fix is to call `Session.hold(s, id, true)` before the write and `false` after it.
Consequences: the hold flag is shared. A flight started by a receipt's `useOne` while a screen hold or `awaitReceipt` is active must not release that hold when it ends with "none" or "gone". A decline noted during the flight still ends the offer. A depart still ends it at the next step (`Game.decline` clears the hold). And the countdown must not stay held if the write never returns: `UpdateAsync` errors after its own timeout, and `useOne` must release the hold on the error path too.
Recommendation: hold the countdown for the length of the flight, and restore the hold state from before the flight when it ends without a continue (keep it in the `Flight` record). Add a Rules and mutants row "an ask in time is judged at the ask": adapters case, offer 3 steps, one held, the write lasts 4 steps, then the run continues with three lives and none held. Add a case that a receipt's flight during an `awaitReceipt` hold ends with the hold still on when it finds nothing. Mutants: no hold during the flight; the flight releases a hold it didn't set.

### F3 [medium] The "Let them play" decision is recorded narrower than what the design does, and the refute labels it with the option the user did not choose
Where: Problem, `Decided with the user (2026-10-26): "Let them play"`; G10; §5 `takePass` ("a pass map that cannot be read counts as a pass"); refute 002 ("'Let them play' (F4b)")
Evidence: the Problem's line reads: "when the lobby's read failed and the MemoryStore is down too, so no pass is seen, the player plays". The arrival can't know whether the lobby's read failed, so the design and the prototype let **every** "buy" arrival play while the pass map can't be read: direct joins and friends' servers, whose lobby read worked or who never went through the lobby. PROBE4 (a direct join with nothing due, no lobby involved, `failPassReads`): `teleports 0 over false`, a free game with the continue offer. That is review 002's option (c), whose cost ("the bypass reopens whenever the MemoryStore is down") the Problem's line does not state. The refute calls the decision "F4b", but review 002's (b) was "accept the bounce", the opposite answer.
Critique: the user's words fit (c), and (c) may be what they meant. But the recorded line describes a narrower rule than the one the design implements, and the next reader (an executor, or z-raft's coherence review) can't tell which the user agreed to.
Consequences: if the user meant only the narrow reading, no design can deliver it: the arrival can't tell a lobby player from a direct join while the MemoryStore is down. The choice is then (b) or (c).
Recommendation: escalate to the user: show them that the arrival can't tell a lobby player from a direct join while the MemoryStore is down, and ask them to confirm (c), "any 'buy' arrival plays while the pass map can't be read, direct joins included", or to choose (b), "the bounce". Record the answer word for word in the Problem and G10, with the cost line, and fix the refute's label in the harvest. PROBE4 as written is the case for (c), and the existing "pass map cannot be read" case already pins it.

### F4 [medium] The refund's key has no rule row: a constant key survives the whole suite
Where: Rules and mutants ("an unused continue is given back", P17); §5 ("`Pay.grant` keyed `refund:<guid>`, so it counts once"); prototype `useOne`
Evidence: mutant `"refund:" .. HttpService:GenerateGUID(false)` → `"refund"`, run on `r3`: adapters.spec + runs.spec `36 passed, 0 failed`. With that mutant, a player's second refund ever is answered "already granted" and the continue is lost. Every case refunds at most once per player. On the question asked: the guid is minted inside the transform, so `UpdateAsync`'s re-calls each mint a fresh one and only the last commits. PROBE3 (`twice`, a decline during the write) holds `continues 1`, `receipts refund:guid2`, so this is correct. But "so it counts once" protects nothing: no caller retries the refund. Refund ids also enter the 50-entry `receipts` list, where they push out real `PurchaseId`s that Roblox may still retry.
Recommendation: add a row "each refund is its own grant": an adapters case with two declines-during-write in two offers of one run, ending with two continues held. Mutant: a constant refund key. Either drop "so it counts once" from §5, or say what it guards. Do one of the following, and pin it with a pay.spec case: (a) refunds add the credit without entering `receipts`, since nothing retries them; (b) state why refunds evicting receipts is safe.

### F5 [low] A player who leaves during the arrival write and is then sent back stays in `sentBack`
Where: prototype `Continues.luau` Ready handler / `sendBack`
Evidence: `PlayerRemoving` clears `sentBack[player]` before the arrival's yielding write returns. `sendBack` then sets it again for a Player that has left, and nothing clears it (the delayed kick checks `player.Parent` and returns). The table then holds a Player object for the server's life, one per such player.
Recommendation: in the Ready handler, after the write, return when `player.Parent == nil`. Add an adapters case where the player leaves inside the arrival's `onWrite`, and nothing is sent back, teleported or kicked.
