### F1 [high] controls.spec claims "the D-pad's Up goes the way of W" and checks R2 only for a Sink, so a Controls whose D-pad doesn't turn and whose R2 doesn't fire passes check.sh

Evidence:

- Two mutants, run on the prototype, one at a time:

- place.spec's pattern `View%.action%([^)]*%)%s*or%s*Pad%.action%(` only shows that the lookup is shared, not that every branch after it treats a pad action as its key.
Critique: "R2 fires the blaster" is one of the four captured outcomes, and the D-pad is G4. The D-pad's Up going down W's path is also what the user's "a double tap of the D-pad's Up also boosts" rests on, since f0143 folds the double tap on that path. ### F2 [medium] "The most recently used controller drives everywhere" is checked for Sticks only: a Camera that always reads Gamepad1's right stick passes every spec
Where: §2 Camera ("it tracks the controller as Sticks does"); place.spec's Camera case (`has(src, "Pad.track(")`); Rules and mutants P21 (pad and Sticks only).
Evidence:
- Two mutants on the prototype's `Camera.luau`, run one at a time:
  - `local pad = Enum.UserInputType.Gamepad1` in place of the tracked pad. place.spec and controls.spec → `8 passed, 0 failed`. Every `tests/place` spec plus f0104 and f0031 → `85 passed, 0 failed, 14 spec files`.
  - The `LastInputTypeChanged` handler computing `Pad.track` and dropping the result, so the tracked pad never changes after start. place.spec → `5 passed, 0 failed`.
- The tracking is written twice, in Sticks and in Camera, each with its own `active` variable and `LastInputTypeChanged` connection. Only Sticks' copy is run. The disconnect rule ("the tracked one disconnected: nothing read") is run for Sticks and not for Camera.
Critique: the user's decision is "everywhere", and with one of the two copies unchecked, a second controller can drive while its right stick does nothing. The tempting fix is a third source pin, which a mutant can step around again. Running Camera on the stub means modelling `BindToRenderStep`, `View.interpolate` and the camera.
Consequences: one tracker owned by one adapter (for example Sticks keeps the tracked pad and exposes `Sticks.position(keyCodeName): (number, number)?`, nil when none is tracked or it's disconnected), with Camera reading it, removes the second copy. It adds one adapter-to-adapter edge (Camera → Sticks) that Main must boot in order, and Controls still never says Gamepad (f0027).
Recommendation: put the tracking in one place (as above, or a small `PadState` client module that both read), and run it in controls.spec. Thumbstick2 of the most recent pad is returned after a takeover, a key keeps it, and a disconnected pad gives nil. Pin Camera's use of that one function in place.spec. Add rows: the Gamepad1 mutant above (kill it) and "Camera reads its own copy of the tracking" (judged by reading). If you keep two copies instead, run Camera's on the stub with the same three steps.
Lesson: zz-test/one-rule-one-function; zz-test/pin-fail-safes-where-they-act

### F3 [medium] "Most recent controller" rests on an unproven Roblox behaviour: whether a thumbstick alone, and an idle pad's drift, change `LastInputType`
Where: §1 `Pad.track`, §2 Sticks and Camera (both follow only `GetLastInputType()`/`LastInputTypeChanged`); Unknowns & experiments (no entry); OC1 ("a second controller picked up drives").
Evidence:
- Sticks and Camera change the driving pad only on `LastInputTypeChanged`. Two engine questions decide whether that works, and neither is an experiment:
  - Does moving only Gamepad2's left stick (no button) make `GetLastInputType()` Gamepad2? If not, a player who picks up the second controller and pushes the stick gets nothing until a button is pressed.
  - Does a resting, connected Gamepad1 whose stick drifts a little below any dead zone fire `LastInputTypeChanged` back to Gamepad1? If so, the "most recent" pad flips while the active player is steering with Gamepad2, and Sticks and Camera read the idle pad.
- E3 covers only the lobby selection. OC1 tries the pickup, with no pass/fail on drift and no fallback.
Critique: the design's new rule (the user's decision) is only as good as the event it listens to. With no recorded fallback, a failure found on a device sends this back to design.
Consequences: a fallback that tracks from `InputBegan`/`InputChanged` (`input.UserInputType`, a stick counted only past a magnitude) changes `Pad.track`'s signature to take a magnitude, and that magnitude needs a constant (`STEER_OFF` or `LOOK_DEAD` would do) and cases.
Recommendation: add E8 with a pass/fail question per bullet above, run on a device in OC1's session ("with Gamepad1 connected and untouched, steer with Gamepad2's stick alone for 30 s: Gamepad2 drives throughout"). Name the fallback above as the design to switch to if it fails: `Pad.track(active, inputType, magnitude)`, which ignores a pad's stick below `STEER_OFF`, with its pad.spec cases and a Sticks running case. Or adopt the fallback now, which needs no device answer.
Lesson: zz-arch/guard-what-the-engine-sees
