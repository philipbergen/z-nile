### F1 [high] AC2 measures the ring and the HUD in one frame, but the game draws them in two, so a landscape phone under Roblox's 58 px top bar has ring dots on the score and level blocks while AC2 stays green
Where: f0158.md Design "Clearance"; acceptance/clear.spec.luau `hudBoxes` (`Hud.layout(w, h)` with no inset, `Hud.radarBox(..., 0)`, `Hud.jumpButtons(0, 0, w, h)`), SCREENS.
Evidence: HudView lays the HUD out on the whole screen with the core-UI inset (`Hud.layout(sw, sh, Hud.safeInset(none, core))`, `HudView.luau:51,157-160`). The ring screen is `ScreenInsets = DeviceSafeInsets`, so its dots sit in the device safe area. I ran the prototype's `Awareness.ring` with f0029's own sample "notched phone, landscape, under a 58 px top bar" (`tests/acceptance/f0029/jump.spec.luau:74-81`: 844×390, core inset top 58 / bottom 21 / left and right 59, device inset top 0 / bottom 21 / left and right 59). I offset the dots into screen pixels and tested them against `Touch.blocks(Hud.layout(844, 390, core))`. The output was `ring top y 73.96 score 68 67 345 18 level 431 67 345 18 hits: score,level`: the score and level blocks run from y 67 to 85, and the ring's top sector starts at y 74. A 667×375 screen with a 58 px bar also hits `score,level`. clear.spec never sees this because it lays the HUD out with zero insets and leaves out f0029's short sample screens (480×320, 320×568).
Critique: AC2 says "no ring dot overlaps the HUD blocks", and on a real phone layout that the repo already models, that is false. The spec passes because it checks the wrong coordinate space, so any ring size passes it on these screens. The tempting fix is to add insets to the spec and then shrink `share` until it passes. That cuts the user's "roughly 60%".
Consequences: the ring's frame becomes a design decision. In the device safe area, the ring overlaps the top text band when the top bar is tall. In the core-UI safe area (`ScreenInsets = CoreUISafeInsets`), it clears the bar, but its 60% is measured on a smaller side (on this phone, 0.6 × 311 = 187 px instead of 221) and its centre sits below the camera's centre. If the HUD's text draws over the ring, as G6 already allows for f0126's overlays, that needs the user's yes.
Recommendation: escalate to the user: (a) centre the ring in the core-UI safe area and keep 60% of that area's smaller side (smaller on phones with a top bar; centred about 18 px below the view centre); (b) keep the device safe area and 60%, and accept that the score and level blocks draw over the ring's top dots on short landscape screens (a G6-style decision, with AC2 rewritten to name the accepted overlap and pin it); (c) keep both, and measure clearance against the text's drawn extent instead of the half-screen label blocks (the cost: a text-extent model in Hud that doesn't exist today). Whichever is chosen, name each box's coordinate space in the Design. Then rewrite clear.spec to lay the HUD out as HudView does (`Hud.layout(w, h, core)`, `Hud.radarBox(..., bandTop)`, `Hud.jumpButtons` on the core frame) and place the ring in its own frame with the device offset. Run it on every f0029 sample (`jump.spec.luau`'s SAMPLES, including 480×320 and 320×568 under a 58 px bar, and both turns). Add a mutant row: "the ring in the wrong frame (no inset offset)".
Lesson: zz-arch/name-each-coordinate-space; pickman-test/new-controls-get-inset-and-turn-cases

### F2 [high] AC3's source pins pass an adapter that inverts the transparency, so the nearest ghost is the faintest and the idle ring is nearly opaque, and one that paints every dot red
Where: acceptance/place.spec.luau "a lit dot is the one warning colour at the lit opacity…"; Rules and mutants rows "unlit at idle opacity", "one warning colour".
Evidence: I ran the real place.spec on the combined R0056 + prototype fixture after `sed` edited DangerHud. First mutant: `f.BackgroundTransparency = alpha` (lit) and `f.BackgroundTransparency = Awareness.RING.idle` (unlit), so the nearest lit dot is 15% opaque and every idle dot 85% opaque. Result: `4 passed, 0 failed`. Second mutant: the unlit branch's `Color3.new(1, 1, 1)` replaced by `Color3.fromRGB(danger.r, danger.g, danger.b)`, so the whole ring is warning-coloured and no sector stands out by colour. Result: `4 passed, 0 failed`. The case only checks that the strings `Awareness.RING.lit.min`, `…lit.max`, `d.brightness` and `Awareness.RING.idle` appear somewhere. The opacity direction (closer is more opaque) and Roblox's transparency = 1 − opacity are never observed. Frame reuse (Scalability: "48 dots, one frame each, reused") is not pinned either: a `ringDot(edge)` call every step passes.
Critique: "translucent" and "more opaque the closer" are the user's G2 and G5. The likeliest real-world mistake, Roblox's inverted transparency, passes. The tempting fix is another needle such as `"1 - alpha"`, which pins a local's spelling and still misses `1 - (max - …)` inversions.
Consequences: a behaviour case needs DangerHud's real source running. f0158 already depends on f0109, whose `fake.module` (on R0056) runs DangerHud's real source, fires `renderStepped`, and serves Awareness, View and Hud. It passed with the prototype's ring in my fixture. So the case only works once f0109 has landed. Implementation step 1 already waits for that, but the spec must not run green against main before then. That is fine: sequestered specs only need to pass at execution.
Recommendation: replace the lit/unlit source case with a behavioural one on `fake.module(client("DangerHud").Source, "DangerHud")`, as f0109's radar case does. Push a snapshot with a dangerous ghost near and one far in other sectors, and fire one render step. Then, for every child of the `Ring` screen: the count is 8 × `RING.dots` and is unchanged after a second step (frames reused); each Position/Size equals `Awareness.ring`'s box; a lit dot is `DANGER_COLOR` with `BackgroundTransparency == 1 - (lit.min + (lit.max - lit.min) × brightness)`; an unlit dot is white with `1 - RING.idle`; the near sector is more opaque than the far one. Add mutant rows: inverted transparency, unlit dots in the warning colour, inverted opacity ramp, a new frame every step. Keep the no-geometry and no-glow source checks.
Lesson: zz-test/source-pins-name-what-the-design-names

### F3 [high] The user-decided numbers behind "translucent" (G3, G5, G7) are unpinned: idle 0.9, lit 0.05–0.10 and 3 dots per sector pass every f0158 spec
Where: acceptance/ring.spec.luau "the ring's numbers are the capture's" (checks only `share`, `SECTORS`, `dots >= 3`, `0 < dot < 0.1`); Rules and mutants has no row for the opacities.
Evidence: on the combined fixture I set `Awareness.RING` to `dots = 3, lit = { min = 0.05, max = 0.1 }, idle = 0.9`. ring 6/6, clear 2/2, place 4/4 and colors 3/3 all passed. The idle ring at 90% opacity is not "translucent indicators" (AC1's own word), and a lit sector at 5–10% is nearly invisible against it.
Critique: AC1 says "translucent dots", and the decided values (G3: 6 dots; G5: lit 35–85%, idle 15%; G7: dot 3.5%) are what make them translucent and readable. Nothing checks any of them, so an executor tuning by eye can undo the user's answers without a red spec.
Consequences: pinning exact values means a later retune is an override, which is right for numbers the user decided. If only bounds are wanted, the bounds need the user's own words.
Recommendation: in ring.spec, pin `RING.dots == 6`, `RING.dot == 0.035`, `RING.lit.min == 0.35`, `RING.lit.max == 0.85`, `RING.idle == 0.15`, citing G3/G5/G7. Also assert the rule: `idle < lit.min < lit.max < 1`, so unlit is fainter than any lit dot and every dot stays translucent. Add the row "decided opacities and counts" with mutants "idle 0.9" and "lit range inverted".

### F4 [medium] "A side that is not a positive finite number counts as 0" is tested for the width only; an unguarded height passes
Where: acceptance/ring.spec.luau "a screen side that is not a positive finite number…" (`Awareness.ring({}, bad, 720)` only); Rules row "bad sides count as 0 / R8".
Evidence: with the ring's guard edited to `local w, h = side(width), height`, ring.spec passed 6/6 on the combined fixture. In Luau `math.min(1280, 0/0)` returns `1280` (I ran it: `min(1280,nan) 1280`), so `Awareness.ring({}, 1280, NaN)` with that mutant draws a 768 px ring at y = NaN. That happens whenever the screen's `AbsoluteSize.Y` is read as 0 or NaN in the first frames.
Critique: this is half of a stated rule with no case. The case's title also says "at the centre" but asserts `x == 0`. That is only the centre because the bad side is the width.
Consequences: none beyond the case.
Recommendation: loop the bad values over both sides (`ring({}, bad, 720)` and `ring({}, 1280, bad)`), assert `w == 0` and that every coordinate is finite, and name the mutant "height unguarded" in the row.
