# f0110: Touch fire and hop

## Problem
On a touch screen there is no way to fire the ghost blaster (f0100) or to spy hop (f0101): shots pile up on the HUD unused. Touch needs a fire control (aimed like the desktop: the look's nearest heading) and a jump gesture or button, placed with R0012's touch layout (f0029).

Decided with the user (2026-10-25): "Land R0051 as a stopgap". The user captured d0149 (Touch circle controls: a left circle steers, a right circle looks, a tap on the right circle jumps, circle-buttons shoot and pick) and first folded f0110 into it; asked during R0051's design rounds 3 and 4, they settled the order **d0151, f0110, f0126, d0149**: d0151 (Touch input reaches nothing on a phone, captured 2026-10-25 from their report that on a phone "Nothing responds") is found and fixed first, because these buttons use the same input path; then this stopgap, so touch players can shoot and hop; d0149 replaces these buttons later and owns retiring or narrowing `tests/acceptance/f0110/` where its circles change what they pin. PR #127 (the fold) was closed unmerged; d0149 on main depends on d0151 and f0110.

## Non-goals
- d0149's circle controls (steer and look circles, a tap to jump, circle-buttons to shoot and pick). This issue is the stopgap the user chose until d0149 lands (see the decision above); it keeps today's swipe and drag zones.
- Finding and fixing why touch input reaches nothing on a phone: d0151, which must be in `done/` before R0051 is readied (`depends_on: [d0151]`).
- A touch PICK button (f0126's wall pick): f0126's, after this issue (the user, 2026-10-25: "PICK button after f0110"; chore c0155 narrows what f0110's promoted specs would otherwise refuse, and finds nothing left to do because this prep pinned `Touch.buttons` by field). `Touch.Buttons` may gain a `pick` field, and this issue's specs keep green when it does.
- A gamepad (f0146 captures it, and changes game-design.md's Platforms decision). Controls still never names `Gamepad` (f0027's place spec pins that).
- Moving the radar, Roblox's jump-corner rows (`Hud.JUMP`) or any other HUD block: the hop button takes the jump corner R0012 already keeps clear (f0029's c0106 fold-in) and FIRE sits beside it, so no promoted spec changes; where that layout is tight the accepted overlaps below say what touches what.
- A shot grace at junctions, or any other change to the blaster's or the hop's rules (f0100, f0101). The server decides both, as it does for the keys.
- Hiding or dimming the fire button with no shots held. The shot bars beside the lives already show the count, and a fire with none does nothing on the server (f0100).
- Turning Roblox's own touch controls (thumbstick, jump button) on: `GuiService.TouchControlsEnabled` stays false.

## Solution
Two on-screen buttons, drawn only on a touch screen and hit-tested in Touch's fold like the snap control (f0029): **FIRE** fires the blaster, aimed as on desktop through `Camera.aim` (the look's nearest heading; touch has no arrows), and **JUMP** sends the spy hop. The hop button sits exactly where Roblox draws its touch jump button (its legacy placement, the corner f0029 keeps clear of the radar, the power bar and the snap control), so a phone player's thumb finds jump where every Roblox game puts it. The fire button is the same size, one margin to its left, raised just enough to stay clear of the snap control. A finger that goes down on a button acts at once, once, and never looks or turns, whatever it does after.

## Design
### Touch (pure, `src/shared/Logic/Touch/init.luau`)
New types and fields:
```lua
export type Zone = "turn" | "look" | "snap" | "fire" | "hop"
export type Effect = { kind: "turn", intent: Turn } | { kind: "look", dx: number, dy: number }
	| { kind: "snap" } | { kind: "fire" } | { kind: "hop" }
export type Context = { width: number, snap: Rect?, fire: Rect?, hop: Rect? }
export type Buttons = { snap: Rect, fire: Rect, hop: Rect } -- the touch controls, as Touch.buttons places them
```
- `Touch.zone(width, x, y, snap: Rect?, fire: Rect?, hop: Rect?): Zone`: half-open rectangles, checked in the order snap, fire, hop, then the halves (left `turn`, right `look`, as before). With `fire` and `hop` nil it is today's function (f0027's and f0029's specs call it with four arguments).
- `Touch.track`: classifies a `begin` with `Touch.zone(ctx.width, x, y, ctx.snap, ctx.fire, ctx.hop)`. One finger per zone holds for the new zones as for every zone (the existing `taken` loop). A `begin` that takes the fire zone emits `{ kind = "fire" }`, the hop zone `{ kind = "hop" }`, in that same event. A fire or hop finger's `move` and `end` emit nothing: only a look finger looks and only a turn finger turns (the existing branches). Never mutates the given state.
- **Coordinate spaces**: every rectangle here is in screen pixels, origin the device screen's top-left, the space HudView draws in (its ScreenGui ignores every inset) and Controls hit-tests in (each touch converted by `Touch.toScreen` from `GetInsetArea(Enum.ScreenInsets.None)`, f0027). `box` is `Hud.layout(sw, sh, inset)` of that screen, so `safeX`…`safeH` is the core-UI safe rectangle in screen pixels, which is also the frame Roblox's touch GUI fills (f0029's jump spec measures `Hud.jumpButtons` there).
- `Touch.hopRect(box: Box): Rect`: the first row of `Hud.jumpButtons(box.safeX, box.safeY, box.safeW, box.safeH)` (Roblox's legacy touch jump button) as a fresh `Rect`. The safe rectangle is the touch GUI's frame, as f0029's jump spec measures it.
- `Touch.fireRect(box: Box): Rect`: `side = hop.w`; `x = hop.x - box.margin - side`; `y = math.min(hop.y, snap.y - box.margin - side)` with `snap = Touch.snapRect(box)`; `w = h = side`. Level with the hop button where that clears the snap control, otherwise its bottom is one margin above the snap control's top.
- `Touch.buttons(box: Box): Buttons`: `{ snap = Touch.snapRect(box), fire = Touch.fireRect(box), hop = Touch.hopRect(box) }`.
- The header comment names the new zones. New dependency edge **`Touch -> Hud`** (for `Hud.jumpButtons`), added to the architecture map's deps block in this prep. Hud requires Levels and Session, never Touch, so the graph stays acyclic.

FIRE also misses the snap control and the power bar everywhere. The hop button, being exactly Roblox's jump place, touches two things on some screens, both by one pixel and **accepted and pinned** (`buttons.spec`'s `touches`): on a 320 px wide portrait screen it shares column 225 (rows 517 to 547) with the snap control, where the snap control wins the zone; with a 500 px short side (500×900, 900×500) its bottom row lies on the power bar, which takes no input. ### Controls (adapter, `src/client/Controls.luau`)
- `Controls.start(onSnap, onLook, snapRect, onTouch, buttons: (() -> Touch.Buttons?)?)`: a fifth, optional hook. Every touch event reads it afresh (as it reads `snapRect()`), so a re-layout moves the hit areas with the drawing, and passes `{ width = sw, snap = rect, fire = placed and placed.fire, hop = placed and placed.hop }` to the one `Touch.track` call (f0027's place spec pins that there is one, with `width`, `x` and `y` as they are).
- One local `fire()` serves E and the fire effect: `keys and keys.aim()`, and when that is a heading, `intent:FireServer(Blaster.intent(h))`; nothing before the first snapshot or without `Controls.keys`. The hop effect sends `intent:FireServer(Hop.INTENT)`, as Space does. No new remote, no new wire string, no new require.
### HudView (adapter, `src/client/HudView.luau`)
- `HudView.start` makes two frames after the Snap frame, both children of the one `Hud` ScreenGui, through one local `button(name, caption, colour, parent)`: `Fire` (HudView's existing `CYAN` constant, the shot bars' colour, caption `FIRE`) and `Hop` (`WHITE`, caption `JUMP`, the word the keys use). Each is `Active = false`, `Visible = UserInputService.TouchEnabled`, `BackgroundTransparency = 0.6`, `BorderSizePixel = 0`, one `UICorner` of `UDim.new(0.5, 0)` (a disc, like the snap control), and holds one `TextLabel` (`label("Caption", Enum.TextXAlignment.Center, frame)`: white Arcade text, no background; full size `UDim2.fromScale(1, 1)`, `Active = false`) at the HUD's text size, with a full black outline (`TextStrokeColor3` `(0, 0, 0)`, `TextStrokeTransparency = 0`). The captions, not the colours, tell the buttons apart: game-design.md records that the user sees `(0, 255, 255)` as white (Inky's colour, f0109), so FIRE may look like JUMP's white to them.
- `button` returns `{ frame: Frame, caption: TextLabel }`, and HudView keeps that pair for each button, so `lay` sets the caption's `TextSize` without searching. Don't find the caption with `FindFirstChildOfClass`: `tests/place/hud-shots.spec.luau`'s stub instances have no such method, and the prototype turned that spec red that way (E2).
- `lay` computes `Touch.buttons(l)` once per layout, keeps it for `HudView.buttons()` and places both frames on its rectangles. `HudView.buttons(): Touch.Buttons?` is nil before the first layout. The frames take no input: a touch on them is a zone in Touch's fold.

### Scalability
Per touch event: three rectangle tests more in `Touch.zone`, and one `buttons()` call returning the table HudView already holds. Per layout (only when the screen size or inset changes): `Touch.buttons`, a handful of arithmetic. Nothing new per frame, per tick, or replicated; the intents are the existing ones at the existing rate limit.
### Maintainability
A further touch control is one more optional rectangle in `Context`, one more `Zone`, one more field in `Buttons`, and one more row in `Touch.zone`'s order. The placement is data from `Hud.jumpButtons` (f0029's `Hud.JUMP` table) plus one formula, so if Roblox's corner moves, the buttons move with it. The fire path is one function shared by E and the button.
### Usability
- Player: jump is where Roblox games put it; fire is one thumb-width left of it, both reachable with the right thumb that also looks. A tap acts on finger-down (no wait for the lift), once; a second finger on the same button is ignored, so a palm can't double-fire. The outlined captions say what each does. The shot bars still show what is held.
- **The finger-down trade-off (a prep choice, marked (prep) in game-design.md for the user's veto).** Finger-down fire is instant, which the blaster needs: f0100 already asks for a side shot to be pressed about half a tile before the junction's centre. Its cost: a look drag that starts on FIRE (the lower right, where the right thumb may rest) spends a shot (at most three held, a 50% drop) and does not look. Firing on the lift of a short tap would avoid that but delays every shot by the tap's length (typically 80 to 150 ms, more than one 67 ms step). The prep chose finger-down; a later issue can switch to the lift if Beta players waste shots.
- Developer: one optional argument each (`Touch.zone`, `Touch.track`'s context, `Controls.start`), all nil-safe, so every existing caller keeps its behaviour. `Touch.buttons` returns all three rectangles in one typed table, and HudView and Controls hit-test the same one.
