### F1 [high] AC3's source pins pass a Controls that boosts on every W press, and one that shares the keys' taps with touch
Where: acceptance/place.spec.luau, case "Controls folds W's Forward and a swipe up…"; E4; Implementation step 4.
Evidence: in the scratch clone of proto-f0143, Controls changed so that the W path calls `Boost.tap` and then fires `Boost.INTENT` unconditionally (M1: every W press asks for a boost, so the first W press after the cooldown boosts), and the touch path folds `Boost.tap(keyTaps, …)` instead of `touchTaps` (M2). `lune run tests/run -- .tracker/issues/f0143/acceptance/place.spec.luau` → `3 passed, 0 failed`. The pins count `Boost.taps()` (2), `Boost.tap(` (≥ 2), and look for `:FireServer(Boost.INTENT)`, `os.clock()` and `effect.intent == "Forward"`; none of them ties the send to the fold's result, the touch fold to its own Taps, or the fold to `Forward` only (a fold on every movement intent passes as well). The only running case is the one Implementation step 4 asks the executor to add to `tests/place/touch-adapters.spec.luau`, a file the executor writes and nothing sequesters.
E4's reason for not running Controls in a sequestered spec ("about 300 lines of prep") doesn't hold: `tests/place/touch-adapters.spec.luau`'s whole stub (services, enum proxy, recording remote, the loader) is lines 40–200, and f0126's sequestered `acceptance/controls.spec.luau` (raft-wall-picks) already runs Controls' real source on a stub of about 150 lines, with a fallback loader for Logic requires.
Critique: the double tap is the feature's whole keyboard and touch trigger, and the wrong implementations above are what a hurried executor writes (the `if pair then` dropped, one Taps reused). The tempting fix is more source needles (`if pair then`), which pass the same mutants with a renamed local.
Consequences: a sequestered running case needs an injectable clock: the stub's `os.clock` must be controlled by the case, because with Lune's real clock every two presses in a test are microseconds apart and always pair (so the existing touch-adapters stub's constant `os.clock = 0` pairs every two Forwards too). It must find the keyboard handler by the codes it was bound with, not "the last `BindActionAtPriority`", because f0146 adds a second list of codes (and may add a second binding), and its loader must fall back to the real `@logic/<name>` (f0110's and f0126's pattern) so f0146's `Pad` and f0126's changes don't turn it red. The D-pad's Up is `Forward` once f0146 lands (see F2), so the case must also say whether a D-pad Up press is folded.
Recommendation: add a running case to `acceptance/place.spec.luau` (or a new `controls.spec.luau`) that loads Controls' real source on a trimmed stub with a scripted clock and asserts the fired list: W, W at 0 and 0.2 → `Forward, Forward, Boost`; W, W at 0 and 0.31 → no `Boost`; W, W, W within the window → one `Boost`; swipe up then W within the window → no `Boost` (separate Taps); Left, Left → no `Boost`; two swipes up within the window → `Forward, Forward, Boost`. Keep the source pins only for what the stub can't see. Add rows (M1, M2, "fold on every movement intent") to Rules and mutants and run them.

### F2 [high] The controller trigger the user's every-feature rule requires has no design, no Touched path and no acceptance criterion in either issue
Where: Problem's "Decided with the user … the boost has a keyboard, a touch and a console trigger"; §3 Gamepad; G5; Touched modules; Acceptance criteria; f0146.md §2b and G6.
Evidence: §3 says L3 is "one row of f0146's `Pad.BUTTONS` mapped to the boost, added by whichever of f0143 and f0146 lands second". f0143's Touched modules have no `Logic/Pad`, its ACs and specs never mention L3 or `Pad` (`grep -n "L3\|Pad" acceptance/*.luau` → nothing), and f0146's design (§2b, G6) repeats the same "whichever lands second" with no AC either. `depends_on` is `[]` in both, so neither knows which is second. Nor does either design say how the row works: `Pad.BUTTONS` maps key codes to a `View.Action` that Controls dispatches (`Jump` → `Hop.INTENT`, …); there is no `"Boost"` action, and the L3 path must send `Boost.INTENT` directly (no double tap), which is a new branch in Controls' handler that no document specifies.
Critique: an outcome the user added by decision ("We support keyboard, console, and touch for every feature") has no acceptance criterion, so both issues can land green with no console boost (z-design's scope rule; this is **high**). The tempting fix, "the executor of the second adds it", is the instruction that has no check today.
Consequences: whichever owns the row needs the other's code: f0143 owning it means `depends_on: [f0146]`, its prototype rebased on f0146's, and its specs run with f0146's (z-design/run-the-other-rafts-specs). It also needs a `"Boost"` action (in `View.Action`, or a Pad-only action) and a decision whether the D-pad Up, which f0146 maps to `Forward` through the same `Movement.isIntent(action)` branch the proto folds in, also double-taps a boost (today it would, sharing `keyTaps` with W).
Recommendation: give the row one owner and an order: f0143 `depends_on: [f0146]` (f0146 is the input feature and is earlier in f0126's landing order), add `pickman/src/shared/Logic/Pad` to Touched, add the `"Boost"` action and its Controls branch to §3, and add an AC with a sequestered case: `Pad.BUTTONS.ButtonL3 == "Boost"` (entry by entry, as f0146 pins), and in the running Controls case (F1) a ButtonL3 press sends exactly `Boost.INTENT`, no `Forward`. Decide and pin whether D-pad Up double taps boost. Update f0146's §2b and G6 to point at f0143 as the owner.

### F3 [medium] f0126's pick stop and the boost's speed are combined in an order no spec pins, and "nothing semantic" in the merge is wrong
Where: §3b f0126; f0126.md Behaviour 3 ("the step's speed (whatever set it: … f0143's speed boost when it lands) is capped to land exactly on it").
Evidence: f0126 (in execution on raft-wall-picks) caps the step's speed to land on the pick's centre. Its V5 case exercises "whatever sets the step's speed" with the speeds that exist without Boost (frightened). Whichever of f0126 and f0143 lands second writes the line that combines `Boost.speed` and the pick cap; applying the boost after the cap (`Boost.speed(cappedSpeed, …)`) carries a boosted player 1.5 × the remaining distance past the marked wall's centre, and neither issue has a case with a boost and a pick request in one step. f0143 is not in f0126's recorded landing order (d0151; f0110, f0146, f0109; c0155; f0126; d0149).
Critique: the order of two speed modifiers is semantic, and the second lander's merge is unchecked.
Consequences: if f0143 lands after f0126 (likely: f0126 is executing), its specs can name `Picks`; if before, f0126's executor must add the case to its own work, which is sequestered already.
Recommendation: decide the order now (f0143 after f0126 is the natural one given f0126 is executing; add it to `depends_on`) and add a session case: a boosted step with a pending pick request beside a marked wall lands exactly on the centre and starts the pick, and the boost's remaining steps after the pick resume at the boosted speed. If the order is instead f0143 first, write the case into f0126's design through its lead.

### F5 [medium] The client draws the boost one step late: the view widens a step after the speed rises and stays wide a step after it falls, and the HUD says "cooling" for a frame when a boost would start
Where: §4 `Boost.fov`; §3 HUD (`Boost.status(frame.boosted, frame.tick)`).
Evidence: `Hop.airborne` documents the convention: step N moves the world from shown tick N − 1 to N. A boost started in step 100 makes steps 100–121 fast, shown over 99–121. In the scratch clone: `Boost.fov(100, 99.5)` → `0` (the middle of the first boosted step), `Boost.fov(100, 121.5)` → `2` (the middle of step 122, which is not boosted); and at the frame after step 211, `Boost.status(100, 211)` → `cooling` while `Boost.canStart(100, 212)` → `true`, so a boost asked during that frame starts.
Critique: the shown slice of time isn't the rule's slice (lesson below). The visible cost is small (67 ms at each end), but it's the defect the lesson exists for, and the fix is one subtraction.
Consequences: Camera and HUD read different conventions unless one pure function decides both.
Recommendation: specify `fov` over `u = t − (last − 1)` (or pass `shown + 1`), and the HUD's ready state as the state of the next step (`Boost.status(boosted, tick + 1)`, or a `Boost.shown(last, frameTick)` that says it); pin both with cases at the slice edges.
Lesson: zz-arch/shown-time-follows-the-rule

### F6 [medium] The HUD chevron's place is not Logic and not pinned, and the prototype puts it at the middle of the screen, not after the shot bars
Where: §3 HUD ("a chevron after the shot bars (`Hud.shotIcons`' row, the same icon size)"); proto HudView.boost.
Evidence: the prototype positions the icon at `shots.AbsolutePosition.X + shots.AbsoluteSize.X + 8`; `lay()` sets `shots.Size = lives.Size`, and the lives block is `w = math.max(0, w / 2 - m)` (Touch.layout), so the icon lands half a screen to the right of the lives, wherever the bars end. No spec or Logic function says where it goes; the design names no Hud function.
Critique: layout is Logic in this codebase (Hud/Touch layouts are pure and pinned by f0019's and f0029's layout specs; pickman-arch rule 3); a free-hand adapter computation drifted at once in the prototype, and on a phone the middle of the bottom edge is where f0110's buttons and the touch radar sit.
Consequences: a Hud function needs the lives and shots counts, and the re-lay on a count or screen change, like `shotIcons`.
Recommendation: add `Hud.boostIcon(l, lives, shots): Box` (one gap after the last bar, the bars' height, inside the safe area), placed by HudView in `lay()`, with unit cases (0 and 3 shots, a narrow phone) and a case that it clears f0110's FIRE and JUMP rectangles when those exist.
Lesson: zz-arch/name-each-coordinate-space

### F7 [medium] §5's claim is wrong: a client that sends `Boost` alone keeps its buffered turn, which a double tap cancels, and L3 would give console players the same
Where: §5; G5.
Evidence: both W presses are `Forward`, and W "cancels a buffered turn" (*Desktop keys*, f0104, quoted in the Design's decisions). A double tap is therefore `Forward, Forward, Boost`: the boost costs the player any turn they had buffered. A modified client sends `Boost` alone and keeps it; and F2's L3 press sends `Boost` alone by design, so the console boost has an advantage the keyboard's and touch's don't.
Critique: the asymmetry is small but real, and the design says there is none.
Consequences: none for the server (it can't see the tap); it is a fairness and parity question.
Recommendation: correct §5 to state the asymmetry, and escalate to the user: (a) accept it (L3 and a cheat keep the buffered turn); (b) the keyboard and touch folds send `Boost` *instead of* the second `Forward` (the first `Forward` still cancels, so only half fixes it); (c) the server treats `Boost` as also cancelling a buffered turn, so every input pays the same (a Session rule, with a case).

### F9 [low] The "two tiles on every level" proxy measures an empty corridor; with dots the gain is about 1.8 tiles on level 1 and 1.1 on level 21
Where: AC1's last case; Usability ("gains about 3 tiles"); E1.
Evidence: (arithmetic from game-design.md's eating rule: a dot stops the player half a tick at the step's speed) level 1 boosted, a dot every tile: 120/45 + 0.5 = 3.17 ticks a tile, 37.9 units a tick against the ghost's 28, × 22 = 218 units (1.8 tiles); level 21: 120/51 + 0.5 = 2.85 ticks, 42.1 against 36, × 22 = 134 units (1.1 tiles). A fleeing player is usually in a dotted corridor.
Critique: the outcome ("enough to pull away") holds in both, but the stated number doesn't, and the proxy can't see that the eating pause is owed at the boosted speed.
Recommendation: state the dotted-corridor numbers beside the empty ones in Usability and E1, or make the proxy a session run through a dotted corridor with `eatSlowdown`; leave the factor to the user (G2) if the dotted gain is thought too small.
