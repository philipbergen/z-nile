# f0143: Speed boost escape

## Problem
The user, 2026-10-25: "a speed boost that lasts a second or two to help get away from a ghost."

Today the player has no way to escape a ghost that is closing in except by out-turning it: the player's speed is fixed per level (game-design.md, Rules: 30 units a tick on level 1 against a hunting ghost's 28) and only rises while the ghosts are frightened. What should happen: the player can get a short burst of extra speed, lasting a second or two, that is enough to pull away from a chasing ghost.

Decided with the user (2026-10-25): "Trigger the speed boost with a double tap on the forward ('w') key"

Decided with the user (2026-10-25): "We support keyboard, console, and touch for every feature" (relayed by the coordinator): the boost has a keyboard, a touch and a console trigger (G5 picks the touch and console ones).

Decided with the user (2026-10-25): "Accept all (Recommended)" (G1 to G9: prep's recommended defaults).

Decided with the user (2026-10-26): "Yes, stick up boosts too": a quick double push of the left stick up boosts like W and the D-pad's Up. This issue owns every boost trigger on every device (f0146 lands first and can't reach `Logic/Boost`; design review 002 F1).

Decided with the user (2026-10-25): "Same as W; D-pad yes": a Boost sent alone (the controller's L3, or a modified client) also cancels the buffered turn, like a double tap of W (the server treats Boost as cancelling the turn), and a double tap of the D-pad's Up also boosts (design review 001 F2, F7).

## Non-goals
- The player's permanent speed relative to the ghosts: f0125 ("Player 10% faster than the ghosts").
- The frightened-time speed-up, which stays as game-design.md has it.
- The spy hop's jump over ghosts (f0101), a different escape.

## Solution
- Open for prep to put to the user: how the boost is triggered (a key or touch control, like the blaster's fire; or a pickup), whether it is limited (a cooldown, charges like the blaster's, or both), how much faster it is, and whether "a second or two" is real time or game time (the game runs at half speed: one real second is half a game second, 15 ticks).
  - Decided with the user (2026-10-25): "Trigger the speed boost with a double tap on the forward ('w') key"; touch and console by the every-feature rule (G5: two swipes up; the left stick's click); the D-pad's Up double-taps too ("Same as W; D-pad yes"). The window, the limit, the factor and the span are G1 to G4.
- The server decides it (the player's speed is server-side, as every catch is), and the speed per tick stays within `checkLevelSpeeds`' one-tile-per-tick limit.

## Design
A double tap on the forward key asks the server for a short burst of speed. The server decides: it starts a boost only in play and only once the last one has run and cooled down, and while it lasts the player's speed for the step is the level's speed times `Boost.FACTOR`, never more than one tile a step. Everything that decides is pure Logic in a new feature, `Logic/Boost`, beside `Hop` (the spy hop, the same shape: an intent, a span counted in steps, a cooldown). The client only recognises the double tap and draws the result.

The numbers below are the guesses at the end, **G1 to G9, each decided with the user (2026-10-25) as prep's default**; every one is a constant in `Boost`, so a decision changes one line and its spec.

Decisions this relies on (game-design.md): the server simulates every maze and clients send intents (*Authority*); W is `Forward`, the straight exit, and cancels a buffered turn (*Desktop keys*, f0104); a swipe up is `Forward` on touch (*Mobile*); all rules count 30 ticks a game second and the server steps 15 a real second, and a rule that decides catches is counted in steps with its real-time numbers following `GAME_SPEED`, as the spy hop is (*Game speed*); eating stops the player for distance owed at the speed of the tick that ate (*Eating slowdown*); keys pressed in a pause are ignored (*Run pauses*).

### 1. `Logic/Boost` (new, pure, no dependencies)
```lua
export type Status = "ready" | "boosting" | "cooling"
export type Taps = { last: number? } -- real seconds of the last unpaired forward press

Boost.INTENT = "Boost"   -- the wire string on the Intent remote
Boost.FACTOR = 1.5       -- G2: the boosted step covers round(speed * FACTOR) units
Boost.TICKS = 22         -- G3: steps a boost lasts (1.47 s of real time at Session.STEP_RATE 15)
Boost.COOLDOWN = 90      -- G4: steps after a boost ends before the next may start (6 s of real time)
Boost.WINDOW = 0.3       -- G1: real seconds from one forward press to the next that make a double tap
Boost.FOV = 8            -- G6: degrees the camera's field of view widens while boosting
Boost.RAMP = 2           -- G6: steps the widening takes at each end

function Boost.isIntent(raw: any): boolean                                  -- raw == INTENT, exactly
function Boost.canStart(last: number?, tick: number): boolean               -- tick >= last + TICKS + COOLDOWN; a nil or non-finite last never blocks; a non-finite tick never starts
function Boost.active(last: number?, tick: number): boolean                 -- last <= tick < last + TICKS (the starting step is boosted); false for nil or non-finite
function Boost.speed(speed: number, active: boolean, cap: number): number   -- active: math.min(round(speed * FACTOR), cap); else speed; round is floor(x + 0.5)
function Boost.status(last: number?, tick: number): Status                  -- at the frame of step `tick`: active(last, tick): "boosting"; else canStart(last, tick + 1): "ready"; else "cooling"
function Boost.taps(): Taps                                                 -- { last = nil }
function Boost.tap(t: Taps, now: number): (Taps, boolean)                   -- see below
function Boost.fov(last: number?, t: number): number                        -- degrees at shown tick t (fractional), step N shown from N - 1; see §4
```
`Boost.tap` folds forward presses (real seconds from the client's clock): a press within `WINDOW` of the remembered one is a double tap, returns true and forgets both (a third quick press starts a new pair, so a triple tap boosts once); a press after the window, or the first, is remembered. A press at a non-finite time, or earlier than the remembered one (a clock that went back), returns false and remembers nothing, so it can never pair.

### 2. The session (`Logic/Session`)
- **Intent**: `Session.submit` accepts `Boost.INTENT` beside the movement, fire and hop intents (`"invalid intent"` for every other spelling, as today). It is taken once a tick (a second in the same tick is `"rate limited"`), and it also queues a `Forward`, so it cancels a buffered turn exactly as W does whatever input sent it (decided with the user, 2026-10-25: "Same as W"; §5); that `Forward` is what counts it toward `maxIntentsPerTick`. `Member` gains `boost: boolean` (asked this tick) and `boosted: number?` (the tick the latest boost started).
- **Start**: in `Session.step`, in play, after the shot and the hop and before the move: `if boost and Boost.canStart(member.boosted, s.tick) then member.boosted = s.tick` and a `Boosted` event (`{ kind = "Boosted", player = id }`). A boost asked outside play does nothing and is not kept (`member.boost` is cleared at the start of every step, as `hop` is), and a boost asked while one runs or cools does nothing.
- **Speed**: the step's speed is `Boost.speed(<the level's player speed>, Boost.active(member.boosted, s.tick), Movement.UNITS)`, where the level's player speed is `Session.speeds(s.config, level, frightened).player` once f0125 has landed (its one function for the speeds) and `Levels.playerSpeed(base, level, frightened)` before; whichever of f0125 and f0143 lands second writes the line with `Session.speeds` (Order & dependencies). It stacks on the frightened speed (G8, with a case). f0126's pick stop then caps the boosted speed at the distance to the centre beside a marked wall: **the cap applies after the boost** (§3b, AC7). The eating pause is owed at that speed (`eat` receives it), so a pellet eaten while boosting costs the same time and more distance, as the existing rule says for any speed change. `checkLevelSpeeds` is unchanged: the cap keeps every boosted step within one tile, so a base speed `Session.new` accepts today still is (f0018's config spec pins 96 accepted, 97 refused).
- **Ends**: a boost runs `TICKS` steps and is not stopped by turning, stopping at a wall or a hop (the speed of a stopped player is spent on nothing). `teleport` (a death's respawn, a new level, a new run) clears `boost` and `boosted`, so a boost ends there and the next life starts with one ready (G7; a case each for a death, a new level and a new run, since a clear beside the death's own reset is the natural wrong place). A pause stops the session's steps for the player (`moving` false), and the boost's steps keep counting in ticks, as the hop's do.
- **Frame**: `Session.frame` gains `boosted: number?` (the tick the latest boost started, nil before any), beside `hopped`. The snapshot is unchanged (f0018 pins its keys).

### 3. The client
- **Controls** (`src/client/Controls.luau`): it keeps one `Boost.Taps` per input kind, keys and touch. When a key's or a pad button's `Forward` goes out (`Movement.isIntent(action)` and `action == "Forward"`: W, and f0146's D-pad Up, decided with the user: "D-pad yes"), it folds `Boost.tap(keyTaps, os.clock())` and on true also sends `intent:FireServer(Boost.INTENT)`; a touch `turn` effect whose intent is `Forward` (a swipe up) folds `touchTaps` the same way (G5). No other intent folds. Both presses still send `Forward` first: a double tap is the straight exit plus a boost. Every fold, and L3's send, happens on the press (`Begin`), never on the release, and a release adds nothing (design review 002 F2).
- **Sticks** (`src/client/Sticks.luau`, f0146's; the user, 2026-10-26: "Yes, stick up boosts too"): the stick keeps its own `Boost.Taps` (`stickTaps`; Sticks shares no state with Controls, so W followed by a push up never pairs). Every `Forward` that `Pad.steer` emits counts as a push, from rest or turned into up from a side; on it Sticks folds `Boost.tap(stickTaps, os.clock())` and on a pair also sends `Boost.INTENT`. A stick held up is one push (Pad.steer emits once a push), and a tilt that never reaches `STEER_ON` is none.
- **Gamepad** (this issue owns it; f0143 depends on f0146): required by the user's every-feature rule. The gamepad itself is f0146's, whose Non-goals leave the boost's controller trigger here (G5): the left stick's click, `Pad.BUTTONS.ButtonL3 = "Boost"`, with `"Boost"` a new `View.Action` that no key maps to; Controls' handler sends `intent:FireServer(Boost.INTENT)` for it on Begin, alone (no `Forward`, no double tap), and sinks it. The server's `Forward` (above) makes it cost the buffered turn as a double tap does. f0126 takes `ButtonY`, so L3 does not clash.
- **HUD** (`HudView.boost(status: Boost.Status)`, G6): a chevron after the shot bars: a `TextLabel` named `Boost` (text `>>`), created by `HudView.start` and hidden until the first `HudView.boost`; its `TextColor3` is `255, 255, 0` when ready (the lives' yellow), `255, 255, 255` while boosting and `90, 90, 90` while cooling; `HudView.show` and `HudView.shots` re-lay it at once, and a new screen size on the next render (design review 003 F2: hud.spec pins these). Its place is Logic (design review 001 F6): `Hud.boostIcon(l: Hud.Layout, lives: number, shots: number): Hud.Box`, in the lives block's space as `Hud.shotIcons`: one gap (`round(margin / 2)`) after the last shot bar, after the lives when there are none, a square of `iconSize`, inside the lives block on every layout. HudView places it in `lay()` at `blocks.lives` plus the box, so it re-lays with the lives and shots counts and the screen. `Main` calls `HudView.boost(Boost.status(frame.boosted, frame.tick))` on every frame: the frame's tick is the step being shown, so the chevron is white while that step is boosted and turns yellow on the frame before the step a boost may start in, when a boost asked now starts (design review 001 F5).
- **Camera** (`Camera.boosted(tick: number?)`, G6): while a boost runs the field of view widens by `Boost.fov(boosted, shown)` degrees on top of the base, at the shown tick the camera already uses for the hop, so it follows the server's boost and the game's clock.

### 4. `Boost.fov`
Step N moves the world from shown tick N − 1 to N (`Hop.airborne`'s convention), so a boost started in step `last` is fast over the shown ticks `last − 1` to `last + TICKS − 1`. For `u = t − (last − 1)` (steps, fractional): 0 when last is nil, either value is not finite, `u < 0` or `u >= TICKS`; else `FOV * min(1, u / RAMP, (TICKS - u) / RAMP)`. So the view widens from the start of the first boosted step and is back at 0 at the end of the last (design review 001 F5: measured from `last`, it lagged the speed by a step at each end).

### 5. What a client cannot lie about
A client that sends `Boost.INTENT` without a double tap gains nothing a fast double tap would not: the server enforces the cooldown and the cap, and a Boost also cancels the buffered turn, as the two `Forward`s of a double tap do (decided with the user, 2026-10-25: "Same as W"; design review 001 F7: before, a lone Boost, the console's L3 included, kept the turn a double tap loses). The double tap is a client gesture, like a swipe.

### Scalability
One comparison and one multiplication a step per player; no new replicated instance, one number (`boosted`) more in the frame. Independent of the maze size and the ghost count.

### Maintainability
The boost is data in `Boost` (factor, span, cooldown, window, FOV); a later speed power-up (f0126's boons, if one is added) calls `Boost.speed` or adds its own factor in the same step line. It mirrors `Hop` exactly, so the next timed ability copies the pattern.

### Usability
- **Player**: on level 1 a boost runs 45 units a step against a hunting ghost's 28, so in an empty corridor it gains about 3 tiles in its 22 steps (the Test plan's proxy pins at least 2 tiles on every level). In a dotted corridor the eating pause (half a tick a dot at the step's speed) cuts it: about 1.8 tiles on level 1 and 1.1 on level 21 (design review 001 F9: level 1, 120 / 45 + 0.5 = 3.17 ticks a tile, 37.9 units a tick against 28, × 22 = 218 units; level 21, 2.85 ticks, 42.1 against 36, 134 units). A fleeing player is usually in a dotted corridor; the factor stays the user's (G2); the HUD says when it is ready; the wider view says it is on. A triple tap does not waste a second boost.
- **Developer**: five functions over plain numbers; `Boost.speed` takes the cap, so no caller can exceed a tile a step.
