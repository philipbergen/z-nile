# Refute 003: f0145 (answers to design-review-003, changes)
The user clarified on 2026-10-31, recorded word for word in the Problem and in G10, in place of the narrower 2026-10-26 reading: Decided with the user (2026-10-31): "Let all of them play". While the MemoryStore's pass map cannot be read, every "buy" arrival plays free, direct joins included; outages are rare and short. That settles F3.

- F1 [high]: fixed. Client-triggered store calls are now bounded over time, not only while one is in flight.
  - Game place: an ask while the countdown is held (a screen open, a receipt awaited) is dropped. An ask writes nothing when this server last saw the player hold no continue; it learns that from every read and write of their record it makes, and forgets it on a grant it hears. An ask causes at most one write per `Continues.ASK_SECONDS` (2), which bounds the case where what the player holds is unknown (the store failing). Grants are never bounded.
  - Lobby: a press within `Paid.PRESS_SECONDS` (2) of the last read answers from that read; every grant the lobby hears updates the kept record.
  - New cases, each sending requests one after another: twenty asks with the screen closed between them (live and test) make no write; asks while a screen is open make one prompt and no write; with nothing known and the store failing, one write per window; twenty presses make one read, and a press after the window reads again.
  - Q1 to Q4 are killed. Scalability and Authority now state the bound.
  - Consequences: a real player's second try still works: CONTINUE after a cancel opens the screen again (screens cost no store call), and START after a closed screen answers from the kept record. Four existing cases had given the player a continue by editing the stub's record after the arrival, which cannot happen (a continue reaches the record only through a grant on the server the player is in, or is there when they arrive). They now set it before the arrival.
- F2 [medium]: fixed. The countdown is held for the write, so an ask made in time is judged at the ask. A flight that ends without a continue releases only a hold it set itself (`Flight.held`, from the new `Session.holding`), so a screen's hold or an awaited receipt stays as it was. A decline noted during the flight, or a depart, still ends the offer, because `Game.decline` clears the hold. Since `Purchases.update` is wrapped in `pcall`, a write that errors returns and the hold is released on that path too. Cases: the offer has 3 steps left and the write lasts 4, and the run continues; a receipt's flight that finds nothing leaves the awaited receipt held, with its wait still counting. Q5 and Q6 are killed. Consequence: P15 (no in-flight guard) is now equivalent, since an ask during a flight meets the flight's hold and is dropped by Q3's rule. The only remaining path to "busy" is a grant's call during a flight, and both orders end the same way. It is marked equivalent in the table, and the guard is kept as defence in depth.
- F3 [medium]: fixed by the user's decision above. The Problem, G10 and the case title now carry "Let all of them play" with its cost line. Refute 002's label is corrected: its decision is review 002's option (c), not (b), and is now superseded.
- F4 [medium]: fixed, with option (a). A refund is `Pay.refund`: one more continue, outside `receipts`. Nothing retries a refund, and a refund must not push a real purchase's id out of the 50 kept. §5 no longer says "so it counts once". New row "each refund is its own credit, outside the receipts", with a pay.spec case where two refunds give two continues and leave the receipts unchanged. Q7 (refunds under one constant key) and Q8 (a refund taking a receipt slot) are killed.
- F5 [low]: fixed. The arrival returns when the player left during its write. Case: a buy arrival whose player leaves inside the write is neither sent back, teleported nor kicked, and nothing is left delayed. Q9 is killed.
