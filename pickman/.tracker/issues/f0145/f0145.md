# f0145: Paid play and continues

## Problem
The user, 2026-10-25: "Unless in playtest (it will show the screen and accept controls, but not actually deduct) we want to allow a free game per hour but after that we charge 1 robux per game and also you can continue with three new lives for 1 robux, we should show in highscore how many lives were spent".

Today every game is free and a game ends when the last life is lost (game-design.md: 3 lives, one extra at 10,000 points). What should happen:
- **A free game per hour:** each player gets one free game per hour.
- **After that, 1 Robux per game:** starting another game within the hour costs 1 Robux.
- **Continue for 1 Robux:** when the last life is lost, the player can pay 1 Robux to continue the same game with three new lives.
- **Hiscores show lives spent:** a hiscore entry shows how many lives the run used, so a score bought with continues is visible as such.
- **Playtest never charges:** in a playtest the purchase screens show and accept their controls exactly as in a live game, but nothing is deducted.

Decided with the user (2026-10-26): accepted as recommended (G1 to G12: the open questions of the Solution, prep's recommendations).

## Non-goals
- The hiscore boards' own rules (all-time, daily, weekly, the top ten): d0124 / R0044; this issue only adds the lives-spent figure to their entries.
- Other purchases (passes, cosmetics, boosts).

## Solution
- Open for prep to put to the user: what "playtest" covers (Roblox Studio play only, or also the Beta place); whether the hour is a rolling hour from the last free game or a clock hour, and whether it is per player across servers (a DataStore) or per server; where the buy prompt appears (the lobby's START GAME, the game place, or both); whether a continue keeps the score, level and pellets (presumably yes); whether continues are unlimited; how lives spent are counted (lives lost, or lives granted including bought and the 10,000-point bonus) and shown on the boards and in the lobby.
- Roblox purchases go through a Developer Product (`MarketplaceService:PromptProductPurchase` and a server `ProcessReceipt` that grants exactly once); the server decides every grant, never the client.
- The hiscore entry gains a lives-spent field; existing entries without it show as unknown (or the base 3).

## Design
Paid play is decided by a new pure feature, `Logic/Pay`, and the continue by `Game`'s new offer phase; the Roblox purchase calls and the store are thin adapters, and the server decides every grant, never the client. Every number the capture left open is a guess below (**G1 to G12**), each decided with the user on 2026-10-26: all accepted as recommended.

Decisions this relies on (game-design.md): the server simulates every maze and clients send intents (*Authority*); two places, the lobby's START GAME teleports to the game place and the game over's tap back (*Two places*); 3 lives, one extra at 10,000 points, once a run (*Scoring and rules*); hiscore entries are the player's name and id, the score and the level, submitted only by the server at game over, behind a Logic-facing store (*Hiscores*); d0124's top-10 list of runs (*Hiscores*, R0044).

### 1. `Logic/Pay` (new, pure; `Lobby -> Pay`)
```lua
export type Mode = "live" | "test"
export type Product = "play" | "continue"
export type Record = { free: number?, plays: number, continues: number, receipts: { string } } -- one per player, in the store
export type Start = "free" | "credit" | "buy"
export type Products = { play: number?, continue: number? }
export type Status = { free: boolean, nextFree: number?, plays: number, continues: number }
Pay.FREE_SECONDS = 3600 -- G2
Pay.PRICE = 1           -- the user's price; the products carry it
Pay.RECEIPTS_KEPT = 50  -- receipts remembered, for granting each once
Pay.STORE = "PaidPlay"  -- DataStore of the records, key the user id
function Pay.mode(raw: any): Mode                          -- "live" only for exactly "live" (G1)
function Pay.record(raw: any): Record                      -- a stored value read defensively; nil or broken is a new player's
function Pay.freeDue(r: Record, now: number): boolean      -- none yet, or the latest free start a full FREE_SECONDS ago; a clock behind it waits
function Pay.status(r: Record, now: number): Status        -- for the lobby's line
function Pay.start(r: Record, now: number): (Start, Record) -- a free start due first (recording now), else a held play, else "buy" (nothing spent)
function Pay.product(id: any, products: Products): Product? -- by the configured ids
function Pay.grant(r: Record, product: Product, receiptId: string): (Record, boolean) -- once per receipt id; false for one already recorded
function Pay.useContinue(r: Record): (boolean, Record)     -- one held continue, once
```
Nothing mutates the record it is given. The store write is one `UpdateAsync` per decision, so two servers never overwrite each other, and a grant records its receipt id in the same write that adds the credit: a receipt is granted exactly once even when Roblox retries it.

### 2. The continue offer (`Logic/Game`, `Logic/Session`)
- `Game` gains the phase `"offer"`, `lost: number` (lives lost in the run: every death, continues included; G6), `held: boolean` and `offer: number` (the offer's length, 0 for none). `Game.OFFER_TICKS = 150` (10 s of real time at the server's 15 steps a second; G7), `Game.CONTINUE_LIVES = 3`.
- The offer is switched on **per run** by the game place's paid-play adapter: `Game.allowOffer(g, ticks)` / `Session.allowOffer(s, id, ticks?)`. Every config's default, `Session.GAME_CONFIG` included, has no offer, so a run ends at its last life exactly as today wherever the adapter is not running (specs, Studio scripts, other places). This keeps every promoted spec that runs `GAME_CONFIG` to its game over (f0018 config, f0023, f0100, f0101) unchanged: no override.
- With the offer on, the last life's dying pause ends in the offer (an `Offer` event), not the game over. The offer counts down `offer` steps unless `held`; its end is the `GameOver` event, which now carries `lives = lost`. `Game.hold(g, on)` / `Session.hold` hold and release the countdown (a purchase screen is open). `Game.decline(g)` / `Session.decline` end it **at the next step**, so the game over still comes out of a step and the hiscore submit (`Submits`, which hears step events only) sees it.
- `Game.continue(g, lives)` / `Session.continue(s, id)` during the offer: `CONTINUE_LIVES` new lives and a respawn (the player teleported to the start, the ghosts reset as after a death, `Ready` with reason `"continue"`); the score, the level, the pellets eaten and the extra life's once-per-run flag are kept, and `lost` keeps counting (G4). Outside the offer it does nothing. `Session.offering(s, id)`; `Session.isOver` stays false during the offer, so the way back to the lobby opens only at the game over.

### 3. Lives spent on the boards (`Logic/Hiscores`, `Logic/Lobby`; G6)
`Hiscores.lives(x)` keeps a whole count of at least one and nothing else. `Attempt`, `Companion`, `Row`, `Submission` and `StepEvent` gain `lives: number?`; `onStep` takes the game over's `lives` into the submission, `commit` stores it, `rows` and `lobbyRows` carry it. Once d0124 has landed (`depends_on`), its `TopRun` gains `lives` too: `topRun` takes the attempt's, `bestRun` the row's, `topRows` the entry's, and the list's own copy of each entry (d0124's sanitising pass over the stored list) keeps it. `Lobby.livesText(lives)` is `" ♥n"` after the level in `Lobby.lines`, nothing for a row without lives (rows stored before f0145; G6). The store adapter passes the submission's lives through (`HiscoreStore.submit(..., lives)`).

### 4. What the screens say (`Logic/Flow`, `Logic/Lobby`)
- `Flow.overlay` keeps its three arguments (f0065 pins the call). In the offer it shows `CONTINUE?`, the score and level, `3 NEW LIVES` and the whole seconds left (`Flow.offerSeconds`, rounded up), frees the cursor, asks for no tap and sets `offer = true`. `Flow.offerPrice(offer?)` is the line under the buttons: a continue held, else `1 ROBUX`, and in test mode (or before the server has said anything) `1 ROBUX (TEST: NOTHING IS CHARGED)`. `Flow.OFFER` holds the words (`CONTINUE`, `END GAME`), and `Flow.OFFER_KEYS` / `Flow.offerKey` the keys and controller buttons: Return, KeypadEnter or ButtonA ask, Backspace or ButtonB decline (G12; the user's rule, 2026-10-25: keyboard, console and touch for every feature).
- `Lobby.payLine(status?, mode?, now)` is the line under START GAME: `FREE GAME`, else the plays held, else `1 ROBUX A GAME, NEXT FREE GAME IN n MIN`; in test mode it adds `(TEST: NOTHING IS CHARGED)`.

### 5. The adapters (server authority)
- **`src/shared/Purchases.luau`** (new, a shared server adapter in ReplicatedStorage.Shared, required only by the two places' servers; place.spec pins that no client requires it): the mode and the product ids from attributes the publisher sets on ServerScriptService (`PaidPlay`, `PlayProductId`, `ContinueProductId`; G1, G8), the player's record through `UpdateAsync` of `Pay`'s transforms (`update`, `read`, `grant`), `ask` (Roblox's `PromptProductPurchase` in live mode, the test screen in test mode), `testGrant` (a test screen's confirmation, granted under a fresh `test:<guid>` id, in test mode only), `remote(name)` (the feature's remotes are made at run time under `ReplicatedStorage.Remotes`, as the Rank remote is, so both places' pinned remote lists stay as they are), and `start(granted)`, which installs `ProcessReceipt`: an unknown product or a failed write answers `NotProcessedYet` and grants nothing; otherwise it answers `PurchaseGranted` after the write, and a fresh grant (not a retried one) is handed to the place.
- **The lobby** (`src/lobby/server/Paid.luau`, new; `Starts` gains an optional gate): `Main.server` boots `Paid.start(require("./Starts").start(Paid.allow))`. `Starts.start(allow?)` asks `allow(player)` before a request goes (only while the player's travel is idle) and returns its press function; with no gate (as f0061's specs boot it) it does exactly what it does today. `Paid.allow` reads the record: a free start due or a play held lets the player go (the lobby charges nothing; G10); otherwise it opens the purchase screen and refuses. A store that cannot be read lets the player go (G10). One read per player at a time: a press while that player's read is under way (a real `GetAsync` yields) is dropped, so a client firing START fast costs one read and opens at most one purchase screen (lesson zz-arch/client-triggered-reads-guarded). A fresh grant of a play while the player is in the lobby presses START for them at once. `Paid` tells each player their `Pay.status` and the mode on `PayStatus`.
- **The game place** (`src/server/Continues.luau`, new; `Main.server` boots it with `Sessions.session`, a new lookup): on a player's first `Ready` on this server it charges the start (`Pay.start` through the store: the free start due, else a held play; a player who arrives with neither, after a race with another server, plays all the same, and a write that fails charges nothing and lets them play; G10) and switches the continue offer on for their run (deferred, so the session `Sessions` makes on that `Ready` exists). On `Continue`: `"ask"` during the offer uses a held continue at once, else holds the countdown and asks for a purchase; `"decline"` ends the offer. A fresh grant of a continue while the player's offer is up uses it at once; one granted after the offer ended stays held for the next (G9). Roblox's `PromptProductPurchaseFinished`, or the test screen's cancel, releases the countdown. It tells the player the mode and the continues held on `PayStatus`.
- **The clients**: `src/client/OfferView.luau` (new, booted by `Main.client`, shown every frame with Flow's overlay): CONTINUE and END GAME while `overlay.offer`, the price line under them, the test screen, and the offer's keys (`ContextActionService:BindAction` of `Flow.OFFER_KEYS`: on the key going down during the offer it sends the answer and sinks the key; at any other time it passes the key on, so FlowView's Return still returns to the lobby at the game over; OfferView binds after FlowView, so it is asked first); `FlowView` is unchanged (f0026 and f0031 pin its sends). `src/lobby/client/PayView.luau` (new, booted after `LobbyView`, which is unchanged: f0026 pins its requires): the pay line under START GAME, redrawn every 30 s, and the test screen. `src/shared/TestPurchase.luau` (new, shared client adapter): the test purchase screen, the price and "TEST PURCHASE: NOTHING IS CHARGED", BUY and CANCEL (also Return, KeypadEnter or ButtonA, and Backspace or ButtonB, sunk only while the screen is open), answered on the `Purchase` remote. The screens are centred (the offer's buttons span 20% to 80% of the width, the test screen the middle half), clear of a phone's side and top insets.

### Authority and what a client could lie about
A client sends only `StartGame` (as today), `Continue` (`"ask"` or `"decline"`, honoured only during that player's own offer) and the test screen's `Purchase` (`"confirm"`, honoured only in test mode, where nothing is charged anyway). It never sends a price, a product or a receipt: Roblox's `ProcessReceipt` is server-only, and every credit is the server's write. A forged `"confirm"` in live mode grants nothing (AC5).

### Scalability
Per step, one comparison more per player (the offer's countdown). Store traffic per player: one read when they join the lobby (and one per START), one write on arrival in the game place, one per purchase and one per continue: far under the per-player DataStore budget. Replicated: two small remote messages on joining and after each change; nothing per frame.

### Maintainability
The prices, the hour, the offer's length, the lives a continue gives and the receipts kept are constants in `Pay` and `Game`; the next product (a boost, a pass) is one `Product` value, one id attribute and one branch where it is used. The purchase plumbing is in one shared adapter for both places.

### Usability
- **Player**: the lobby says before START GAME what a game costs and when the next free one is; a bought game starts at once; the continue's countdown is long enough to decide (10 s real), stops while Roblox's purchase screen is open, and END GAME ends it at once; the boards show who bought lives (♥n). In test mode every screen says nothing is charged.
- **Developer**: `Pay` is eight pure functions over a plain record; the adapters only move values between the store, Roblox and `Pay`.

## Unknowns & experiments
- **E1. Can a player join the game place without the lobby?** The design charges on arrival (§5), and a player who arrives with nothing due plays all the same, so a direct join would be a free game. Roblox's experience setting "Allow direct access to places" is off by default for places other than the start place, so a player reaches the game place only by the lobby's teleport. Doc-based, not run headless. Fallback if the setting is on: the game place sends a player whose arrival `Pay.start` answers `"buy"` back to the lobby (one branch in `Continues`, with a case).
- **E2. ProcessReceipt's contract.** Roblox calls it on a server the buyer is in, retries a receipt until a call answers `PurchaseGranted` (also in a later session), and `PromptProductPurchaseFinished` fires when the purchase screen closes, bought or not. Doc-based. The design depends only on: grant once by `PurchaseId` (kept in the record, the latest 50), answer granted only after the write, and treat a retried receipt as nothing new (AC5's "retried receipt" case).
- **E3. Prototype and mutation check** (scratch worktree `proto-f0145`, from this prep): `./zn check f0145` AC1 to AC6 and AC8 pass; AC7 needs d0124 and passes on the combined tree (Order & dependencies). The pickman gate on the prototype: 1417 specs, every promoted spec unchanged (no override). Every Rules and mutants row was applied there one at a time and its spec run: each fails on an assertion, none on a load error. Four survived the first run and the specs gained cases for them: a continue that does not move the player (the last death now happens away from the start), a free start not shown while a play is held, a retried receipt that starts or prompts again, and a start charged on every `Ready`.
