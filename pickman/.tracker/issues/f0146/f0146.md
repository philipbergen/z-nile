# f0146: Console gamepad controls

## Problem
The user, 2026-10-25: "Console game play, the controller should steer with the left joystick and the right looks around and the x button is jump. Shoot blaster with r2".

Today the game is played with keyboard and mouse or touch only; game-design.md's Platforms row says "Gamepad isn't planned; it gets the same intents if it's added later". This changes that decision: console players (and anyone with a controller) should be able to play with a gamepad:
- **Left stick steers** the player through the maze.
- **Right stick looks around** (the camera, as the mouse does on desktop).
- **X jumps** (the spy hop, f0101).
- **R2 fires the blaster** (f0100), aimed as on desktop (the look's nearest heading).

## Non-goals
- Touch controls for fire and hop: f0110.
- The speed boost's trigger on a controller: f0143 (its double tap on forward is keyboard; its gamepad trigger is an open question there).

## Solution
- Open for prep to put to the user: which physical "X" is meant (PlayStation's cross, the bottom button, is Roblox `ButtonA`; Xbox's X, the left button, is `ButtonX`; R2 is `ButtonR2`, the right trigger on both); how the analog stick maps to the maze's four headings (dead zone, the turn buffer) and the right stick's look speed and inversion; what the other buttons do (start, pause, menus, the lobby's START GAME and hiscore screens); whether to show controller glyphs in the HUD.
- The controller produces the same intents as keyboard and touch (game-design.md's rule), so the server needs no change.
- game-design.md's Platforms row changes to include gamepad.

## Design
A controller produces the same intents as the keyboard (game-design.md: "it gets the same intents if it's added later"), so the server does not change. Everything that decides is pure Logic in a new feature, `Logic/Pad`: the button map, the left stick's fold into turn intents, the right stick's look rate. The adapters read the controller and hand the numbers to it: Controls binds the buttons beside `View.KEYS` and polls the left stick; Camera polls the right stick in its render step; FlowView binds the continue button; in the lobby a new `LobbyPad` puts Roblox's own gamepad selection on START GAME, so the D-pad moves between START and the board tabs and the bottom face button presses them (LobbyView is unchanged).

The numbers below are prep's defaults for the guesses at the end (**G1 to G8, pending the user**); each is a constant in `Pad`.

Decisions this relies on (game-design.md): clients send intents and the server simulates (*Authority*); turn intents are relative to the heading, buffered 0.8 s of game time (1.6 s real), `Back` reverses at once (*Movement*); the look is free and never changes the heading, and the desktop keys are W A S D, Space jumps, E fires, the arrows look (*Desktop keys*, f0104); the blaster aims at the look's nearest heading (*Ghost hunter tools*); a tap or Return continues at game over (f0065); the lobby's START GAME teleports to the game (*Two places*). This issue changes the *Platforms* row (the user's capture): "Desktop (keyboard and mouse), mobile (touch) and gamepad: every input produces the same intents (f0146)."

### 1. `Logic/Pad` (new, pure; `Pad -> View`, `Pad -> Movement`)
```lua
export type Steer = { held: Movement.Intent? } -- the sector the left stick is engaged in, nil when released

Pad.GAMEPAD = "Gamepad1"         -- G7: the first controller only
Pad.BUTTONS = {                  -- KeyCode names -> View.Action; G1, G4
	ButtonA = "Jump",            -- G1: the bottom face button (PlayStation's cross, Xbox's A)
	ButtonR2 = "Fire",
	ButtonR3 = "Snap",           -- G3: the right stick's click recentres the look
	DPadUp = "Forward", DPadDown = "Back", DPadLeft = "Left", DPadRight = "Right", -- G4
}
Pad.CONTINUE = "ButtonA"          -- G4: continues at game over (the lobby's START GAME is pressed by Roblox's selection)
Pad.STEER_ON = 0.6                -- G2: stick tilt that engages a sector
Pad.STEER_OFF = 0.4               -- G2: tilt below which the stick is released (hysteresis)
Pad.LOOK_DEAD = 0.15              -- G3: radial dead zone of the right stick
Pad.LOOK_YAW = 3                  -- G3: radians a second at full tilt, left and right
Pad.LOOK_PITCH = 2                -- G3: radians a second at full tilt, up and down
Pad.INVERT = false                -- G3: pushing up looks up

function Pad.action(keyName: string): View.Action?             -- BUTTONS[keyName]
function Pad.steerStart(): Steer                                -- { held = nil }
function Pad.steer(s: Steer, x: number, y: number): (Steer, Movement.Intent?)
function Pad.look(x: number, y: number, dt: number): (number, number) -- View.look's dx, dy
function Pad.isPad(inputType: string): boolean                  -- an input type name of a gamepad ("Gamepad1" to "Gamepad8")
```
- **`Pad.steer`** (x right, y up, as Roblox reports a thumbstick): the sector is the dominant axis, heading-relative like W A S D: up `Forward`, down `Back`, left `Left`, right `Right`; a tie (|x| = |y|) goes to the vertical axis. Released, a tilt of at least `STEER_ON` engages the sector and emits its intent once. Engaged, a tilt of at least `STEER_ON` into another sector moves to it and emits that intent once; a tilt below `STEER_OFF` releases; anything between keeps the sector and emits nothing. Holding the stick emits nothing more (G2: one intent per push, like a key press; a held `Back` repeated would reverse the player back and forth). A non-finite x or y releases and emits nothing.
- **`Pad.look`**: `r = sqrt(x² + y²)`; below `LOOK_DEAD`, or a non-finite input, or `dt` not finite or not positive: `0, 0`. Otherwise `a = ((min(r, 1) - LOOK_DEAD) / (1 - LOOK_DEAD))²` (a squared response, fine aim near the centre) along the unit direction, `dx = a · (x / r) · LOOK_YAW · dt / View.MOUSE_RADIANS_PER_PIXEL` and `dy = −a · (y / r) · LOOK_PITCH · dt / View.MOUSE_RADIANS_PER_PIXEL` (the sign of `dy` flips when `INVERT`), so `View.look(look, dx, dy)` turns right for a stick pushed right and up for a stick pushed up, and keeps `View.look`'s pitch limit.
- **`Pad.isPad`**: true for `"Gamepad1"` to `"Gamepad8"` (Roblox's `UserInputType` names), false for anything else.

### 2. The adapters
- **Controls** (`src/client/Controls.luau`): binds `Pad.BUTTONS`' key codes beside `View.KEYS`' (one more `BindActionAtPriority` at the same high priority, or one binding of both lists), and its handler reads `View.action(name) or Pad.action(name)`, so a pad button goes down the same paths as its key (`Jump` sends `Hop.INTENT`, `Fire` the aimed `Blaster.intent`, `Snap` calls `onSnap`, a D-pad direction its intent). For `Pad.CONTINUE` it returns `Enum.ContextActionResult.Pass` instead of `Sink`, so the next binding of that button (FlowView's) hears it too; every other key and button still sinks. On `RunService.Heartbeat` it reads `UserInputService:GetGamepadState(Enum.UserInputType[Pad.GAMEPAD])`'s `Thumbstick1` position, folds `Pad.steer(steer, x, y)` and sends the intent it emits on the Intent remote. No controller connected: no state, nothing sent.
- **Camera** (`src/client/Camera.luau`): in its render step, before `View.steer`, it reads the same gamepad's `Thumbstick2` and applies `look = View.look(look, Pad.look(x, y, dt))`; the right stick's look stays where it is left, like the mouse's, until `Snap` (R3) or an arrow.
- **FlowView** (`src/client/FlowView.luau`): binds `Pad.CONTINUE` with `ContextActionService:BindAction` (as it binds `Flow.CONTINUE_KEYS`); a press asks while the overlay asks (`live`) and does nothing otherwise. Controls passes that button on (above), so in play it jumps and at game over it also continues (a hop asked outside play does nothing on the server). `Flow.CONTINUE_KEYS` is unchanged (f0065 pins it, and that `ButtonA` is not one of its keys).
- **LobbyPad** (new, `src/lobby/client/LobbyPad.luau`, booted by the lobby's `Main.client.luau` after LobbyView): when the last input is a gamepad (`UserInputService:GetLastInputType()` at start and on `LastInputTypeChanged`, judged by `Pad.isPad(type.Name)`) and nothing is selected, it sets `GuiService.SelectedObject` to the lobby's `Start` button (found under the PlayerGui by name, after LobbyView built it). Roblox's own gamepad navigation then moves the selection with the D-pad and the left stick between START GAME and the board tabs, and its select button (the bottom face button) fires the selected button's `Activated`, so START GAME and the boards work through LobbyView's existing handlers, exactly as a click. LobbyView is unchanged: f0026's stub harness boots it with only `Players` and `ReplicatedStorage`, so a new service or require there would turn that promoted spec red.
- **game-design.md**: the *Platforms* row as quoted above, and a *Gamepad* paragraph under *Desktop keys* with the map: left stick and D-pad turn (heading-relative), right stick looks (R3 recentres), the bottom face button jumps and continues, R2 fires; in the lobby the D-pad moves between START GAME and the boards and the bottom face button presses them; Start is Roblox's menu.

### 3. What stays as it is
The server, the intents, the per-tick limit, `View.KEYS` (f0104 pins its ten keys), `Flow.CONTINUE_KEYS` (f0065), the touch layout. Roblox's own Start-button menu is not bound.

### Scalability
Per frame: one gamepad state read and a few multiplications in Controls (Heartbeat) and Camera (render step); an intent only on a sector change, so at most a few a second, far under the server's 4 a step. Nothing new is replicated.

### Maintainability
The whole map is data in `Pad` (`BUTTONS`, `CONTINUE`, the board buttons, the stick numbers); the next action is one row. Steering and look are pure functions of the stick's numbers, unit-tested without an engine.

### Usability
- **Player**: a push of the left stick is a key press (the turn buffer and `Back` behave as on the keyboard); the look has a dead zone and a squared response, so a resting thumb does not drift and small moves aim finely; R2 fires where the player looks, as E does; the same button continues at game over and starts in the lobby.
- **Developer**: `Pad.steer` and `Pad.look` take and return plain numbers; `Pad.action` mirrors `View.action`.
