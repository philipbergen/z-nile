# f0146: Console gamepad controls

## Problem
The user, 2026-10-25: "Console game play, the controller should steer with the left joystick and the right looks around and the x button is jump. Shoot blaster with r2".

Today the game is played with keyboard and mouse or touch only; game-design.md's Platforms row says "Gamepad isn't planned; it gets the same intents if it's added later". This changes that decision: console players (and anyone with a controller) should be able to play with a gamepad:
- **Left stick steers** the player through the maze.
- **Right stick looks around** (the camera, as the mouse does on desktop).
- **X jumps** (the spy hop, f0101).
- **R2 fires the blaster** (f0100), aimed as on desktop (the look's nearest heading).

Decided with the user (2026-10-25): "We support keyboard, console, and touch for every feature" (relayed by the coordinator for f0126's prep; f0126 writes the same rule into the Platforms row, and whichever of the two lands second merges the row).

Decided with the user (2026-10-25): "Accept all (Recommended)" (G1 to G8: prep's recommended defaults).

Decided with the user (2026-10-25): "Most recent; 15° margin": the most recently used controller drives (not the first controller only; G7 superseded), and an engaged stick changes direction only 15 degrees past the diagonal (design review 001 F2, F3).

Decided with the user (2026-10-25), f0143's decisions this issue's paths carry: "Same as W; D-pad yes": a Boost from the left stick's click (L3, f0143's row) cancels the buffered turn as a double tap of W does, and a double tap of the D-pad's Up boosts too, which works because the D-pad's Up takes Forward's path in Controls (§2b).

Decided with the user (2026-10-26): "Yes, stick up boosts too": a quick double push of the left stick up boosts like W and the D-pad's Up. f0143 owns every boost trigger on every device (as L3), so this issue builds nothing for it (design review 002 F4).

## Non-goals
- Touch controls for fire and hop: f0110.
- The speed boost on a controller: f0143 owns every boost trigger (G6): its `ButtonL3` row and action, its double-tap fold on Controls' Forward path (which the D-pad's Up takes), and the left stick's double push up ("Yes, stick up boosts too", 2026-10-26), which f0143 adds in Sticks..

## Solution
- Open for prep to put to the user: which physical "X" is meant (PlayStation's cross, the bottom button, is Roblox `ButtonA`; Xbox's X, the left button, is `ButtonX`; R2 is `ButtonR2`, the right trigger on both); how the analog stick maps to the maze's four headings (dead zone, the turn buffer) and the right stick's look speed and inversion; what the other buttons do (start, pause, menus, the lobby's START GAME and hiscore screens); whether to show controller glyphs in the HUD.
- The controller produces the same intents as keyboard and touch (game-design.md's rule), so the server needs no change.
- game-design.md's Platforms row changes to include gamepad.

## Design
A controller produces the same intents as the keyboard (game-design.md: "it gets the same intents if it's added later"), so the server does not change. Everything that decides is pure Logic in a new feature, `Logic/Pad`: the button map, the left stick's fold into turn intents, the right stick's look rate. The adapters read the controller and hand the numbers to it: Controls binds the buttons beside `View.KEYS` and polls the left stick; Camera polls the right stick in its render step; FlowView binds the continue button; in the lobby a new `LobbyPad` puts Roblox's own gamepad selection on START GAME, so the D-pad moves between START and the board tabs and the bottom face button presses them (LobbyView is unchanged).

The numbers below are the guesses at the end, **G1 to G8, each decided with the user (2026-10-25) as prep's default**; each is a constant in `Pad`.

Decisions this relies on (game-design.md): clients send intents and the server simulates (*Authority*); turn intents are relative to the heading, buffered 0.8 s of game time (1.6 s real), `Back` reverses at once (*Movement*); the look is free and never changes the heading, and the desktop keys are W A S D, Space jumps, E fires, the arrows look (*Desktop keys*, f0104); the blaster aims at the look's nearest heading (*Ghost hunter tools*); a tap or Return continues at game over (f0065); the lobby's START GAME teleports to the game (*Two places*). This issue changes the *Platforms* row (the user's capture and the user's rule of 2026-10-25): "Desktop (keyboard and mouse), mobile (touch) and gamepad: every input produces the same intents, and every feature supports keyboard, console and touch (f0146)."

### 1. `Logic/Pad` (new, pure; `Pad -> View`, `Pad -> Movement`)
```lua
export type Steer = { held: Movement.Intent? } -- the sector the left stick is engaged in, nil when released

Pad.BUTTONS = {                  -- KeyCode names -> View.Action; G1, G4
	ButtonA = "Jump",            -- G1: the bottom face button (PlayStation's cross, Xbox's A)
	ButtonR2 = "Fire",
	ButtonR3 = "Snap",           -- G3: the right stick's click recentres the look
	DPadUp = "Forward", DPadDown = "Back", DPadLeft = "Left", DPadRight = "Right", -- G4
}                                -- ButtonY stays free: f0126 adds ButtonY = "Pick" after this lands; later features add rows
Pad.CONTINUE = "ButtonA"          -- G4: continues at game over (the lobby's START GAME is pressed by Roblox's selection)
Pad.STEER_ON = 0.6                -- G2: stick tilt that engages a sector
Pad.STEER_OFF = 0.4               -- G2: tilt below which the stick is released (hysteresis)
Pad.STEER_MARGIN = 15             -- degrees past the diagonal an engaged stick must turn to change sector (user, 2026-10-25)
Pad.LOOK_DEAD = 0.15              -- G3: radial dead zone of the right stick
Pad.LOOK_YAW = 3                  -- G3: radians a second at full tilt, left and right
Pad.LOOK_PITCH = 2                -- G3: radians a second at full tilt, up and down
Pad.INVERT = false                -- G3: pushing up looks up

function Pad.action(keyName: string): View.Action?             -- BUTTONS[keyName]
function Pad.steerStart(): Steer                                -- { held = nil }
function Pad.steer(s: Steer, x: number, y: number): (Steer, Movement.Intent?)
function Pad.look(x: number, y: number, dt: number): (number, number) -- View.look's dx, dy
function Pad.isPad(inputType: string): boolean                  -- an input type name of a gamepad ("Gamepad1" to "Gamepad8")
function Pad.track(active: string?, inputType: string, magnitude: number): string? -- the controller that drives: a pad's input of magnitude >= STEER_OFF, else active
```
- **`Pad.steer`** (x right, y up, as Roblox reports a thumbstick): the sector is the dominant axis, heading-relative like W A S D: up `Forward`, down `Back`, left `Left`, right `Right`; a tie (|x| = |y|) goes to the vertical axis. Released, a tilt of at least `STEER_ON` engages the sector and emits its intent once. Engaged, the stick moves to another sector, emitting that intent once, only when its tilt is at least `STEER_ON` and its direction is more than 45° + `STEER_MARGIN` (60°) from the held sector's axis, so a thumb wobbling on a diagonal never flips between two intents (design review 001 F3: without the margin a ±1° wobble at 135° emitted Forward and Left alternately every frame, and each Forward cancelled the buffered turn); a tilt below `STEER_OFF` releases; anything else keeps the sector and emits nothing. Holding the stick emits nothing more (G2: one intent per push, like a key press; a held `Back` repeated would reverse the player back and forth). A non-finite x or y releases and emits nothing.
- **`Pad.look`**: `r = sqrt(x² + y²)`; below `LOOK_DEAD`, or a non-finite input, or `dt` not finite or not positive: `0, 0`. Otherwise `a = ((min(r, 1) - LOOK_DEAD) / (1 - LOOK_DEAD))²` (a squared response, fine aim near the centre) along the unit direction, `dx = a · (x / r) · LOOK_YAW · dt / View.MOUSE_RADIANS_PER_PIXEL` and `dy = −a · (y / r) · LOOK_PITCH · dt / View.MOUSE_RADIANS_PER_PIXEL` (the sign of `dy` flips when `INVERT`), so `View.look(look, dx, dy)` turns right for a stick pushed right and up for a stick pushed up, and keeps `View.look`'s pitch limit.
- **`Pad.isPad`**: true for `"Gamepad1"` to `"Gamepad8"` (Roblox's `UserInputType` names), false for anything else.
- **`Pad.track`**: the most recently used controller (decided with the user, 2026-10-25), judged from its inputs (design review 002 F3): an input from a gamepad of `magnitude` at least `STEER_OFF` takes over (a button press counts 1, a stick its tilt), so a stick alone takes over and a resting pad's drift never does; a key, a touch, a non-finite magnitude or a lesser tilt keeps the one before.

### 2. The adapters
- **Controls** (`src/client/Controls.luau`): binds `Pad.BUTTONS`' key codes beside `View.KEYS`' (one more `BindActionAtPriority` at the same high priority, or one binding of both lists), and its handler reads `View.action(name) or Pad.action(name)`, so a pad button goes down the same paths as its key (`Jump` sends `Hop.INTENT`, `Fire` the aimed `Blaster.intent`, `Snap` calls `onSnap`, a D-pad direction its intent). For `Pad.CONTINUE` it returns `Enum.ContextActionResult.Pass` instead of `Sink`, so the next binding of that button (FlowView's) hears it too; every other key and button still sinks. Controls never names the gamepad (f0027's place.spec pins that its source has no `Gamepad`), so the stick is not read here.
- **Pads** (new, `src/client/Pads.luau`, booted first by `Main`; design review 002 F2, F3): the one tracker of the driving controller. It folds every `UserInputService.InputBegan` (magnitude 1) and `InputChanged` of a `Thumbstick1` or `Thumbstick2` (magnitude its tilt) through `Pad.track`, and `Pads.stick(name): (number?, number?)` returns that stick's position on the driving controller, nil when none drives yet or it is disconnected (`GetGamepadConnected`). It alone reads a gamepad's state; Sticks and Camera read it through `Pads.stick`, which `Main` hands them. It does not rely on `LastInputType`, which Roblox may not change for a stick alone and may change for an idle pad's drift (E8). Buttons need no tracking: any controller's act through Controls, FlowView and LobbyPad.
- **Sticks** (new, `src/client/Sticks.luau`, booted by `Main` as `Sticks.start(Pads.stick)`): on `RunService.Heartbeat` it reads `Thumbstick1` through `Pads.stick`, folds `Pad.steer(steer, x, y)` and sends the intent it emits on the Intent remote (`intent:FireServer(emitted)`). Nothing driving or disconnected: nothing read, nothing sent. It reads no gamepad state itself.
- **Camera** (`src/client/Camera.luau`): `Camera.pad(read)` takes `Pads.stick` from `Main`; in its render step, before `View.steer`, it reads `local x, y = read("Thumbstick2")` and applies `look = View.look(look, Pad.look(x, y, dt))` (the stick's own numbers, never negated: Pad decides the directions); the right stick's look stays where it is left, like the mouse's, until `Snap` (R3) or an arrow.
- **FlowView** (`src/client/FlowView.luau`): binds `Pad.CONTINUE` with `ContextActionService:BindAction` (as it binds `Flow.CONTINUE_KEYS`); a press asks while the overlay asks (`live`) and does nothing otherwise. Controls passes that button on (above), so in play it jumps and at game over it also continues (a hop asked outside play does nothing on the server). `Flow.CONTINUE_KEYS` is unchanged (f0065 pins it, and that `ButtonA` is not one of its keys).
- **LobbyPad** (new, `src/lobby/client/LobbyPad.luau`, booted by the lobby's `Main.client.luau` after LobbyView): when the last input is a gamepad (`UserInputService:GetLastInputType()` at start and on `LastInputTypeChanged`, judged by `Pad.isPad(type.Name)`) and nothing is selected, it sets `GuiService.SelectedObject` to the lobby's `Start` button (found under the PlayerGui by name, after LobbyView built it); it also re-selects it when the selection becomes nil while a controller is the last input (`GuiService:GetPropertyChangedSignal("SelectedObject")`), since Roblox's ButtonB clears the selection and would leave a console player with none (design review 001 F6). Roblox's own gamepad navigation then moves the selection with the D-pad and the left stick between START GAME and the board tabs, and its select button (the bottom face button) fires the selected button's `Activated`, so START GAME and the boards work through LobbyView's existing handlers, exactly as a click. LobbyView is unchanged: f0026's stub harness boots it with only `Players` and `ReplicatedStorage`, so a new service or require there would turn that promoted spec red.
- **game-design.md**: the *Platforms* row as quoted above, and a *Gamepad* paragraph under *Desktop keys* with the map: left stick and D-pad turn (heading-relative), right stick looks (R3 recentres), the bottom face button jumps and continues, R2 fires; in the lobby the D-pad moves between START GAME and the boards and the bottom face button presses them; Start is Roblox's menu.

### 2b. Other features' buttons
The user's rule (every feature on keyboard, console and touch) makes `Pad.BUTTONS` the place every later feature adds its console button: f0126 (wall picks) adds `ButtonY = "Pick"` after this lands, so `ButtonY` stays unmapped here, and f0143 (the boost) owns the boost's button: it depends on this issue and adds `ButtonL3 = "Boost"`, its action and its case; this issue adds nothing for it (design review 001 F4). The D-pad's Up goes Forward's path in Controls, so f0143's double-tap fold there applies to it ("D-pad yes", 2026-10-25), and controls.spec pins each D-pad direction's intent. The left stick's double push up is f0143's too ("Yes, stick up boosts too", 2026-10-26): f0143 folds it in Sticks with its own taps. The acceptance specs pin each entry of this issue's map, not the map's size, so those additions keep them green. f0110 (touch fire and hop) runs Controls through a stub loader that refuses unknown requires: f0110's prep made its loaders fall back to the real `@logic/<name>` (2026-10-25), so Controls keeps requiring `Logic/Pad`; the alternative recorded if that ever changes: the map moves into View (`View.PAD_BUTTONS`, `View.padAction`) and Controls keeps requiring only View, as f0126 does with `View.PICK_INTENT` (E6).

### 3. What stays as it is
The server, the intents, the per-tick limit, `View.KEYS` (f0104 pins its ten keys), `Flow.CONTINUE_KEYS` (f0065), the touch layout. Roblox's own Start-button menu is not bound.

### Scalability
Per frame: one gamepad state read and a few multiplications in Controls (Heartbeat) and Camera (render step); an intent only on a sector change, so at most a few a second, far under the server's 4 a step. Nothing new is replicated.

### Maintainability
The whole map is data in `Pad` (`BUTTONS`, `CONTINUE`, the board buttons, the stick numbers); the next action is one row. Steering and look are pure functions of the stick's numbers, unit-tested without an engine.

### Usability
- **Player**: a push of the left stick is a key press (the turn buffer and `Back` behave as on the keyboard); the look has a dead zone and a squared response, so a resting thumb does not drift and small moves aim finely; R2 fires where the player looks, as E does; the same button continues at game over and starts in the lobby.
- **Developer**: `Pad.steer` and `Pad.look` take and return plain numbers; `Pad.action` mirrors `View.action`.

## Guesses (decided with the user, 2026-10-25)
Each is a constant in `Pad` or one paragraph of the design; prep's default is used until the user decides. Overlaps: f0110 (touch fire and hop buttons) and d0151 (touch input on a phone) change `Controls.luau` and the touch layout; f0143 (speed boost) owns the boost's controller trigger, L3 (G6), and depends on this issue; f0126 (wall picks) may add a pick action that will want a button. Each composes: a new action is one row of `Pad.BUTTONS`.
- **G1. Decided with the user (2026-10-25): "Accept all (Recommended)", the default below: which physical "X" jumps.** Default **the bottom face button, Roblox `ButtonA`**: PlayStation's cross (✕, which players call "X") and Xbox's A, where Roblox and most console games jump. The alternative is **`ButtonX`**: Xbox's X and PlayStation's square, the left face button.
- **G2. Decided with the user (2026-10-25): "Accept all (Recommended)", the default below: the left stick to the maze's headings.** Default **relative to the heading, as W A S D are** (up `Forward`, down `Back`, left and right the sides), **a push past 0.6 sends one intent, released below 0.4**, nothing repeats while held (a held `Back` repeating would reverse back and forth; the turn buffer holds a push for 1.6 s real). Alternatives: relative to where the camera looks (push toward the corridor you see); repeat a held side turn every 0.5 s so a long corridor keeps it.
- **G3. Decided with the user (2026-10-25): "Accept all (Recommended)", the default below: the right stick's look.** Default **3 rad/s across and 2 rad/s up and down at full tilt, a 0.15 dead zone, a squared response, not inverted; the look stays where it is left (like the mouse), R3 recentres.** Alternatives: spring back to the heading on release (like the arrows); an inverted-Y option (needs a settings screen, a separate issue).
- **G4. Decided with the user (2026-10-25): "Accept all (Recommended)", the default below: the other buttons.** Default **the D-pad also turns; R3 recentres; the bottom face button continues at game over; in the lobby Roblox's own selection starts on START GAME and the D-pad reaches the board tabs; Start stays Roblox's menu** (the game has no pause today; a pause would be a new feature).
