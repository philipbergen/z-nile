### F1 [high] A press with no level plays the best level, while START said START GAME and the Design says level 1
Where: f0148.md Behaviour 3 ("Below a best of 2 there are no arrows and START is as before (`START GAME`, which starts level 1)") and 5 ("the requested level when it is a whole number from 1 to the stored best, else the best"); Edge cases ("A store down in the lobby: no attribute, no picker, START as before (level 1)"); best.spec "the lobby's choice is kept when allowed, else the best is chosen" (`Best.choose({ best = 4 }, nil)` → `next = 4`); prototype `Best.choose`.
Evidence: the client sends no argument whenever `LobbyPicker.level()` is nil, i.e. whenever the attribute is not there. That happens for a player whose best is 4 in three ordinary cases: (a) START pressed before the lobby's `GetAsync` answered (the attribute "arrives after the screen", Behaviour 3; START GAME is enabled from `show("idle", true)` at once); (b) the lobby's read failed but its write in `Bests.choose` works (transient errors are per call); (c) f0145's grant press (`press(player)` with no level, F4). In each, `Best.choose(record, nil)` stores `next = 4`, the claim plays level 4 at 4× points and the extra life at 40,000, under a button that said START GAME. The sequestered best.spec pins this outcome, so the executor cannot fix it.
Critique: the default the server fills in is one the player never saw. The tempting fix is to make the client wait for the attribute before enabling START; that does not cover (b) or (c), and it changes f0061's pinned "START GAME at once".
Consequences: if nil means level 1, the server's default for a missing request agrees with what every client without a picker shows; a forged out-of-range number then needs its own rule (best, or 1: either is safe, since a client that showed a picker always sends an allowed level; a value above the best is only a forgery or a stale screen). Claim already treats "not allowed" as 1, so "anything the server cannot allow plays level 1" makes one rule across both places.
Recommendation: `Best.choose(r, nil)` stores no choice (or `next = 1`); decide and state what a non-nil, not-allowed request stores (recommend level 1, matching `Best.claim`), and update the Edge cases' "the lobby stores the best instead". Cases: best.spec `Best.choose({ best = 4 }, nil)` → claim gives 1; adapters.spec "the lobby stores …": `mod.choose(p, nil)` with a stored best of 4, then the game place's `startOf` gives 1; a mutant row "nil stores the best".

### F2 [high] `Bests.start` opens the DataStore at boot outside any pcall, ahead of the boots it must not break
Where: Interfaces (each Main calls `Bests.start()` before `Starts.start()` / `Sessions.start(...)`); prototype `src/lobby/server/Bests.luau` and `src/server/Bests.luau` (`local s = DataStoreService:GetDataStore(Best.STORE)` as the first line of `start`); adapters.spec's stub `GetDataStore` never fails.
Evidence: Roblox's `GetDataStore` itself throws in a place that cannot reach DataStores (an unpublished place: "You must publish this place to the web to access DataStore"; also any environment without DataStore access), not only the `*Async` calls. The existing adapters treat opening as a failure point: `src/lobby/server/Boards.luau` opens its stores inside the `pcall` ("a store that will not open"), and `HiscoreStore` opens per call inside `answer(pcall)`. In f0148's Mains a throw in `Bests.start()` stops the script before `Starts.start()` (the lobby has no START) and before `Sessions.start(...)` (the game place makes no session), which contradicts the Design's "a failure costs the picker or the start, never the run". The runtime tier (pickman-test: `tests/runtime/`, run in published places through Open Cloud's Luau Execution) boots these Mains too; nothing in E5 asks whether a store opens there.
Critique: the tempting fix is to move `Bests.start()` after the pinned boots in each Main; that keeps START alive but still leaves `Bests` dead with an error in the log, and the order pin in adapters.spec (`Bests.start()` first) forbids it.
Consequences: opening per call (or inside the pcall in `start`) means `store` can be nil later: `choose` and `reached` must already handle nil (they do), and `startOf` must not wait 10 s for a claim that was never started (it would, since `starts[player]` is never set).
Recommendation: open the store inside the pcall that uses it (as Boards does), so `Bests.start()` never throws; a claim whose store will not open sets `starts[player] = 1` at once. Add a stub mode where `GetDataStore` throws, with cases: the lobby's `start()` returns, sets no attribute, `choose` is no error; the game place's `start()` returns and `startOf` gives 1 without waiting (`clock.now` unchanged). Add E5's pass/fail question for the CICD runtime suite (does a store open in the Luau Execution server; fallback: the guard above).

### F3 [high] Sessions' Ready handler now yields, and f0145's game-place adapter acts on "the session made on this Ready" by `task.defer`
Where: Behaviour 6 (`Sessions`' Ready handler waits on `Bests.startOf`, up to 10 s); Regression guard's f0145 paragraph (covers only `Starts`); f0145.md §5 "The game place" and its prototype `src/server/Continues.luau` lines 62 and 105-110.
Evidence: f0145's `Continues` hears the same `Ready` remote, does its own `UpdateAsync`, then `task.defer`s `Session.allowOffer(sessionOf(player), …)` ("deferred, so the session Sessions makes on this Ready exists"), and `sendBack` refuses `sessionOf(player)` at once and once more deferred. With f0148, `Sessions` makes the session only when `startOf` returns. Whenever the claim answers after f0145's write, `sessionOf` is nil at both points: a paying player's run never gets its continue offer, and a "buy" arrival's run is never refused, so it plays until the teleport and then parks, stepping to a game over that `Submits` sends to the boards (f0145 requires "nothing submitted" for it). The race is not exotic: the claim writes the same key the lobby wrote a few seconds earlier, while f0145 writes another store (see F6 on per-key write limits).
Critique: the tempting fix is to say "the claim starts at PlayerAdded, so it is done by Ready"; that is a timing hope, not an order.
Consequences: the session's creation becomes an asynchronous event; anything else that needs it needs a signal, and whichever of f0145 and f0148 lands second must use it.
Recommendation: give Sessions an explicit "made" signal (e.g. `Sessions.made(fn)`, called with `(player, session)` right after the session is stored, beside `listen`), state in the Regression guard that the session made on a `Ready` exists only after that signal, and that f0145's `Continues` must use it in place of `task.defer` (the lead tells the f0145 prep; if f0145 lands first, f0148's execution rewires it and its specs say so). Case in adapters.spec: with `Sessions.starts` yielding, a `made` listener hears the session exactly once, after the start is known; a mutant firing it before the session exists is killed.

### F4 [high] The lobby Main pins of f0145 and f0148 cannot both pass, and f0145's grant press loses the picker's level
Where: adapters.spec "each place's Main hands the hooks over…" (`order(lobbyMain, { "Bests%.start%(%)", "Starts%.choosing%(%s*Bests%.choose%s*%)", "Starts%.start%(%)" })`); Regression guard ("both apply whichever lands first, with no argument in common"); f0145's place.spec line 58 (`Paid%.start%(%s*require%("%./Starts"%)%.start%(%s*Paid%.allow%s*%)%s*%)`); f0145.md §5 ("A fresh grant of a play while the player is in the lobby presses START for them at once"; prototype `Starts.start` returns `press(player)`).
Evidence: f0148's pin needs the literal `Starts.start()` with empty parentheses; f0145's needs `require("./Starts").start(Paid.allow)`. No single Main satisfies both (one `Starts.start` call), and f0148's `Starts%.choosing` does not match a `require("./Starts").choosing(...)` spelling either. Whichever lands second turns the other's sequestered or promoted spec red, which the Regression guard says will not happen. Separately, f0145's grant calls `press(player)` with no level, so a player who chose level 2, was refused for payment and then bought plays the best (as written, F1) or level 1 (after F1's fix), never level 2.

Recommendation: make f0148's lobby-Main pins accept both spellings and an argument (`Starts"?%)?%.choosing%(%s*Bests%.choose%s*%)` and `Starts"?%)?%.start%(` after it), and write the merged Main both specs accept into the Regression guard. Specify the combined press: Starts keeps the requested level of a press its gate refused (per player, cleared on leaving), and a grant's press passes it; the second lander adds the case (a refused press with level 2, then a grant: the store hook gets 2). ### F5 [medium] The keyboard step relies on unprocessed Left and Right in UserInputService, which Roblox's default camera may bind
Where: Behaviour 4 ("a key the engine marked processed … does nothing"); prototype `LobbyPicker` (`UserInputService.InputBegan` with `if processed … return`); lobby.spec's stub fires every key with `processed = false` except the chat case; E5 does not list it.
Evidence: pickman-arch/count-processed-input-when-tracking: "ContextActionService marks every key and button it binds as processed". The default PlayerModule's camera binds the Left and Right arrow keys through ContextActionService for camera rotation, and the lobby keeps the default player scripts (`lobby.project.json` sets only `CharacterAutoLoads: false`). The game client does not trust UIS for its keys either: `src/client/Controls.luau` binds them with `ContextActionService:BindActionAtPriority(…, High, …)` and sinks them. If the arrows arrive processed in the lobby, the picker never steps on a keyboard, and the only check is OC1, after execution.
Critique: dropping the `processed` guard instead would make chat typing step the level.
Consequences: a CAS binding needs a sink/pass rule (sink only while the picker is shown) and an unbind or pass when it is hidden; CAS does not fire while a TextBox has focus, so the chat rule still holds.
Recommendation: either an E-row with a pass/fail question run in Studio before `ready` (do Left/Right reach `InputBegan` unprocessed in the lobby?) with this fallback, or design the binding as `ContextActionService:BindActionAtPriority` on Left and Right at High priority, sinking only while the picker is shown; stub CAS in lobby.spec and assert after the press and after the release (pickman-test/assert-between-press-and-release).
Lesson: pickman-arch/count-processed-input-when-tracking

### F6 [medium] The DataStore timings the design depends on are not an experiment with a pass/fail question
Where: Unknowns E5 ("Phase 1, Observed"); Behaviour 5-6; `Bests.WAIT = 10`.
Evidence: the lobby writes `PickmanBest/<id>` and teleports; the game place's claim writes the same key seconds later. Roblox limits writes per key (documented historically as one write per key per 6 s, excess requests queued), and the claim's latency sets how long a `Ready` waits (and F3's race). E5 only says the calls work; it asks nothing about how long the claim takes after a lobby write, and has no fallback if it often exceeds `WAIT` (the player then silently plays level 1).
Critique: an Observed check after execution cannot change `WAIT` or the design.
Consequences: if same-key writes are queued, the fix may be to make the claim cheaper (read first and write only when `next` is set, cancelling the write with a nil transform result) or to wait longer.
Recommendation: add a Beta experiment with a pass/fail question ("a claim made 2 to 5 s after the lobby's write answers within N s in 20 tries"), its result recorded before `ready`, and a fallback; also return nil from the `reached` and `claim` transforms when nothing changes (UpdateAsync then writes nothing), with a stub that honours nil and a case that counts no write.

### F7 [medium] "A player who leaves before the claim answers" has no case, and its mutant survives every spec
Where: Edge cases; adapters.spec; prototype `Sessions` (`if sessions[player] ~= nil or player.Parent == nil then return`) and `Bests.startOf` (`and player.Parent ~= nil`).
Evidence: removing both `Parent` checks (run by hand on the prototype): adapters.spec 10 passed, 0 failed; every spec in `tests/acceptance/f0025`, `f0065`, `f0061`: no failure. With the mutant, a player who leaves while `startOf` waits gets a session made after `PlayerRemoving` ran, so it is never removed or parked: it steps every heartbeat and fires snapshots at a departed player for the rest of the server's life (and `runs.ready` starts a Submits run for it). Also `starts[player]` is written by a claim that finishes after `PlayerRemoving`, a per-departure leak.
Recommendation: a case in adapters.spec: `Sessions.starts` yields, the player's `Parent` becomes nil and `PlayerRemoving` fires, then the start returns: no session, `runs.ready` not called; and a case that a claim finishing after `PlayerRemoving` leaves no entry (or `startOf` of a departed player returns at once). Rows for both mutants.
