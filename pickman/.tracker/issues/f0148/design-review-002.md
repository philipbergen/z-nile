### F2 [medium] The lobby's choice write has no time bound, and the teleport waits for it
Where: Behaviour 5 ("once Travel says go and before the teleport, it hands the kept level to the store hook"); prototype `src/lobby/server/Starts.luau` (`store(player, level)` before `pcall(TeleportService.TeleportAsync, …)`) and `src/lobby/server/Bests.luau` `choose` (a bare `UpdateAsync` in a pcall); Scalability ("a failure costs the picker or the start, never the run"); E6 (measures only the game place's claim).
Evidence: a scratch probe (`.cache/rv2/hang.spec.luau`, removed after) loaded the built lobby's `Bests` with a store whose `UpdateAsync` never returns, then called `choose(player, 2)` in a coroutine. The result was 1 passed: `UpdateAsync` was called once and the coroutine was still `suspended`, so `Starts` never reaches `TeleportAsync`. The game place bounds its side (`Bests.WAIT`), but the lobby bounds nothing. A store that is slow or throttled (E6's own concern: a second write to the key within the per-key window queues) holds every START press of that player on STARTING.... From reading `Travel.request` and `Travel.status`: once Travel's 60 s cap passes, the player cools down 3 s and may press again; that press goes and calls the hook again. When the first hook finally returns, its `TeleportAsync` runs anyway (only `answered` and `failed` check the ticket), so two teleports can start. No spec has a slow or hanging hook in Starts or a hanging store in the lobby's `Bests` (`grep -n "hang" lobby.spec.luau`: none; adapters.spec's lobby cases use "ok" and "fail" only).
Critique: the tempting fix is to teleport first and write after. The claim would then usually run before the write lands and play level 1, which breaks the user's "Through the store".
Consequences: a bounded wait means a write may land after the claim. The claim then plays level 1 (or an older `next`), and the late `next` stays stored until the next arrival claims it or the next START replaces it. That is harmless for authority (it is at most the best), but the player sees START LEVEL n and plays level 1. The bound must stay well under Travel's cap so that no second press can go while the first is still writing.
Recommendation: bound the lobby's write: `Bests.choose` (or Starts around the hook) waits at most `Bests.CHOOSE_WAIT` seconds (for example 5, under Travel's 60 s cap) and then lets the teleport go. State the consequence above under Edge cases and in game-design.md's (prep) list. Extend E6's pass/fail question to the lobby's write latency, with the same fallback. Cases in adapters.spec: with a "hang" store, `choose` returns after `CHOOSE_WAIT` (clock advanced, under `CHOOSE_WAIT + 1`). In lobby.spec: a hook that yields for longer than the bound still ends in one teleport. Add mutant rows for "no bound" and for "bound past Travel's cap".
