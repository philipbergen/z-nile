# f0148: Start on any level up to your best

## Problem
The user, 2026-10-25, while setting f0126's tuning: "Once you clear a level you can choose to start on any level from 1-your best level."

Every player is affected. Today every game starts on level 1, and nothing remembers how far a player got (game-design.md, Hiscores: "No personal-best feature for now, except the lobby's 'your best' line"). What should happen: once a player has cleared a level (with f0147, by finishing its ten wall picks), each later game can start on any level from 1 up to the best level they have reached, and it starts there.

Decided with the user (2026-10-25), the split: "3 rafts in order (Recommended)": f0126 (picks and boons), then f0147 (levels, speeds, multiplier), then this issue. The work lands as sequenced rafts.
Decided with the user (2026-11-01), the best level: "Highest reached (Recommended)": the highest level the player got to by clearing the one before it (clear level 3 and you can start on 1 to 4).
Decided with the user (2026-11-01), the picker's first choice: "Your best (Recommended)": the lobby's level picker starts on the player's best level; a step down starts lower.
Decided with the user (2026-11-01), the hiscore rows: "No, keep rows as they are (Recommended)": the rows keep name, score and the level reached; the starting level is not stored with them.
Decided with the user (2026-11-01), how the choice reaches the game place: "Through the store (Recommended)": the lobby server writes the chosen level into the player's stored record (bounded by the best) just before the teleport, and the game place claims it from there once; nothing the client sends reaches the game place, and the teleport carries no data. This replaces the capture's "the chosen level travels with the teleport"; the game place still checks it against the store.
Decided with the user (2026-11-01), where the picker lives (design review 001 F8: c0188 retires the lobby once the portal is the start place): "Lobby now, portal later (Recommended)". The picker is built in the lobby; c0188 records that the portal must carry it before the lobby is removed.

## Non-goals
- How levels advance, their speeds and the score multiplier: f0147.
- The hiscore boards' rules: d0124 / R0044. A run's entry keeps its level reached.
- Paid play and continues: f0145.

## Solution
- The server remembers each player's best level reached (a DataStore behind a Logic-facing interface, as the hiscore store is), and only the server decides which level a game may start on: a client's choice above the stored best is refused.
- The lobby's START GAME offers the levels 1 to best, and the chosen level travels with the teleport; the game place checks it against the store.
- Open for prep: whether "best level" is the highest level reached or the highest cleared, what the picker looks like on desktop and touch, and whether hiscore entries show the starting level.

Prep adds (2026-11-01):
- A pure `Best` module holds the record (`{ best, next }`), the levels a run may start on, the claim and the picker; adapters in each place read and write the one DataStore, and the lobby shows the best through a player attribute.
- The lobby's picker is ◀ and ▶ either side of START, which says START LEVEL n, starting on the best, on every input; a run joined on level n plays f0147's level n.

## Design

### Behaviour
1. **The record.** Each player has one record in the experience's DataStore `Best.STORE` ("PickmanBest"), keyed by `tostring(userId)`: `{ best: number, next: number? }`. `best` is the highest level reached (the user's "Highest reached": reached by clearing the level before it), at least 1; `next` is the start the player chose in the lobby, waiting to be played. `Best.decode` reads any stored value: a table whose `best` is a whole number ≥ 1 is kept (its `next` only when also whole ≥ 1), anything else is a fresh record `{ best = 1 }`.
2. **The best rises.** The game place hears every step's events (`Sessions.listen`); each `Ready` with reason `level` raises its player's stored best to that level (`Best.raise`: the record with the higher best, or nil when it is already that high, which cancels the write; the choice kept). A death, a new run and other events write nothing.
3. **The picker** (the lobby's client). The lobby server reads each arriving player's record and sets the player attribute `Best.ATTRIBUTE` ("PickmanBest") to its best; the client's `LobbyPicker` reads it (and listens for it to change, since it arrives after the screen). Once the best is 2 or more, ◀ and ▶ (named `LevelDown`, `LevelUp`) sit either side of START, in START's row; START says `START LEVEL n` (`Lobby.button(phase, configured, level)`), starting on the best (the user's "Your best"). ◀ steps one level lower, ▶ one higher, within 1 to the best (`Best.step`); only the open way is live (`Best.picker`'s `down` and `up`). Below a best of 2 there are no arrows and START is as before (`START GAME`, which starts level 1).
4. **Every input** (Platforms): a click or a tap on an arrow; a controller moves the selection to an arrow and presses it, as it does START (the arrows are `Selectable` while shown); the keyboard's Left and Right keys step the level while the picker is shown **(prep)**: `LobbyPicker` binds them with `ContextActionService:BindActionAtPriority("PickmanLevel", …, false, Enum.ContextActionPriority.High.Value, Left, Right)`, above the default camera's own use of the arrow keys (design review 001 F5; the game client's Controls binds its keys the same way), steps on `Begin` only and returns `Sink` when it stepped, `Pass` otherwise (no picker shown, a release), so the camera keeps them when there is nothing to choose. Each arrow is at least `Lobby.BUTTON_MIN_PX` (44) pixels each way.
5. **Starting.** START sends the picker's level with the request (`StartGame:FireServer(level)`, or no argument with no picker). The lobby server's `Starts` keeps the level of each press (`held[player]`, a press with a level replacing it); once Travel says go and before the teleport, it calls the store hook (`Starts.choosing`'s, `Bests.choose`) with the kept level in the press's own thread, so the teleport waits for it (never `task.spawn` or `task.defer`: design review 003 F1), and forgets the level, so a press that did not go (one under way, a cool-down) leaves its level for the next press that goes, including a press that carries none, such as f0145's server-side press after a purchase (design review 001 F4). `Bests.choose` writes `Best.choose(record, level)`: the level when it is a whole number from 1 to the stored best, else level 1 (no level is START GAME, which the screen showed as level 1: design review 001 F1). The write waits at most `Bests.CHOOSE_WAIT` = 5 s (well under Travel's 60 s cap), then the teleport goes; a write that lands later leaves its choice for the next claim, which may be this arrival's or a later one's (design review 002 F2). With no destination nothing is chosen. The teleport is as today (no teleport data; the user's "Through the store").
6. **Claiming.** When a player arrives in the game place, its `Bests` adapter claims the record once (`UpdateAsync` with `Best.claim`): the run starts on `next` when it is allowed (1 to the best), else on level 1, and `next` is cleared, so a later arrival without a new pick starts on level 1, unless the lobby's write missed its 5 s bound and landed after the claim: that late choice is then the next arrival's start (**(prep)**: the trade for never holding the teleport, design review 003 F3). A claim whose store call fails, or whose write fails after the transform ran, starts on level 1; a claim that answers after the player left is not remembered. Each adapter opens the DataStore on first use inside a pcall and keeps it once opened, so a place that cannot reach DataStores still boots (no picker, level 1; design review 001 F2). `Sessions`' Ready handler asks `Sessions.starts`' function for the start before making the session (`Bests.startOf`, which waits up to `Bests.WAIT` = 10 s for the claim, then says 1); a second Ready that arrives while the first waits makes no second session, and a player who left during the wait gets none. Once a session exists, `Sessions` tells each function given to `Sessions.made` (the player and the session), so code that needs the new session (f0145's `Continues`) hears it there rather than by `task.defer` after Ready, whose effect may now come later (design review 001 F3).
7. **The run.** `Session.join(s, id, start)` makes the run with `Game.new(config, ramp, start)`: its level and `start` are the start, its ghosts begin on that level (`Ghosts.new(…, { level = start })`), so f0147's ramp gives that level's speeds, every point is worth `start` times, and the extra life comes at 10,000 × `start`; `Game.playAgain` starts the next run on `start` again. `Game.new` refuses a start that is not a whole number ≥ 1 and finite.
8. **The hiscore rows** are unchanged (the user's "No, keep rows as they are"): the level reached is still the run's last level.

### The split and authority
Logic decides what a record holds, which start a run may play, the claim, and the picker's state; the adapters only read and write the store, set and read an attribute, and draw the arrows. A client's level reaches only the lobby's choice, which `Best.choose` bounds by the stored best; the game place plays the stored choice (`Best.claim` checks it again against the best), never anything the client sent it.

### Scalability
- Store calls: one read per lobby arrival, one write per START, one update per game-place arrival, one update per level reached by each player (at most one a level, minutes apart). Well under DataStore budgets at any player count; a failure costs the picker or the start, never the run.
- Replication: one number attribute per player in the lobby.

### Maintainability
- The rules are one pure module with a small API; a future "start level" source (f0145's continues, say) calls `Best.claim` or `Game.new`'s `start`.
- The adapters plug in through optional hooks, so the pinned boots stay as they are.

### Usability
- Players: START tells them which level they start; the arrows appear only when there is a choice, start on the best (the multiplier rewards it), and are touch-sized; the keyboard's arrow keys work too.
- Developers: `Session.join`'s optional `start`, `Best`'s pure functions, two setters on Sessions.

### Edge cases
- A store down in the lobby: no attribute, no picker, START as before (level 1). Down in the game place: level 1 after at most 10 s.
- A choice above the best (an old record, a forged request): the lobby stores level 1 (as for no level); a record whose `next` is above its best is claimed as level 1.
- Two quick arrivals (a failed teleport retried): the first claims, the second starts on level 1.
- A lobby write that misses its 5 s bound and lands after the claim: the claim found no choice (level 1), and the late choice waits for the player's next arrival, which then starts on it (a (prep) trade, recorded in game-design.md).
- A player who leaves the game place before the claim answers: `startOf` stops waiting (`player.Parent` nil) and the Ready makes no session.
- A best above f0147's top (34): allowed; levels past 34 keep level 34's speeds, and the multiplier keeps rising.
- Beta and production: separate experiences, separate stores.
