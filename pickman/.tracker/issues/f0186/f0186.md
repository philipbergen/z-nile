## Design
A run's paid revives are counted where its continues happen, in the pure `Game` (one for each continue f0145's offer takes), carried by the `GameOver` event into `Hiscores`, stored with the hiscore rows and the top-10 list exactly as f0145 stores its lives, and shown by the pure `Lobby` view model on every board and by `Flow` at the game over. The price of a play is one pure table and one rich-text string in `Lobby`. The adapters only pass the new figures through (`Submits`, `HiscoreStore`) or draw them (`RevivesView`, new; `TestPurchase` and `PayView`, f0145's, set `RichText`). The server decides every figure; a client sends nothing new.

### 1. Counting a run's revives (`Logic/Game`, `Logic/Session`)
```lua
-- Game (after f0145)
export type Game = { …, lost: number, offer: number, held: boolean, waiting: number,
	revives: number } -- f0186: continues the run used; GameOver carries it
export type Event = { …, revives: number? } -- GameOver: the continues the run used
-- Session
export type Event = { …, revives: number? } -- copied from Game's event by `tagged`
export type PlayFrame = { …, revives: number? } -- continues the run used; nil while none
```
- `Game.new` sets `revives = 0`; `Game.continue(g, lives)` adds one only when it gives lives (in the offer, `lives` a whole number of at least one: exactly when it returns `true`); nothing else changes it (an offer opening, a death, a decline, a refusal, a continue outside the offer). `Game.playAgain` sets it back to 0 with f0145's `lost`.
- **Every `GameOver`** carries `revives = g.revives`, 0 for a run without one: the last life without an offer, the offer's countdown running out, a decline and a departure (both end the offer at the next step through the same path). A refused run emits no `GameOver` (f0145), so nothing is counted or submitted for it.
- `Session`'s `tagged` copies `revives` from Game's event, so the step events `Sessions` hands `Submits` carry it. `Session.frame`'s `play` gains `revives = if play.revives > 0 then play.revives else nil`: nil while none, so the frame of a run without revives is exactly the frame it was (promoted specs compare frames; E1), and the client reads the count from the frame it already gets.
- A continue is the only revive: the capture's "paid revives (continues)". A continue paid with a credit held, a bought one and a test one (test mode charges nothing but acts as live, f0145 G1) each count one; the count is the sim's, so no client can claim one.

### 2. Storing the revives (`Logic/Hiscores`, `src/server/Submits.luau`, `src/server/HiscoreStore.luau`)
```lua
function Hiscores.revives(x: any): number? -- a whole count from 1 to 2^53 - 1, else nil (none)
export type Attempt = { …, lives: number?, revives: number? }
export type Companion = { …, lives: number?, revives: number? } -- nil: none, or a row stored before f0186
export type Row = { …, lives: number?, revives: number? }
export type Submission = { score: number, level: number, run: number, lives: number?, revives: number? }
export type StepEvent = { kind: string, score: number?, level: number?, lives: number?, revives: number? }
export type TopRun = { …, lives: number?, revives: number? }
export type Best = { score: number, level: number, revives: number? }
-- lobbyRows' rows: { rank, name, score, level, lives: number?, revives: number? }
function HiscoreStore.submit(userId: string, name: string, score: number, level: number, run: number,
	lives: number?, revives: number?)
```
- The path is f0145's lives path, field for field: `onStep` takes `Hiscores.revives(event.revives)` into the submission; `commit` stores `Hiscores.revives(attempt.revives)`; `rows` reads `Hiscores.revives(companion.revives)`; `lobbyRows` carries `row.revives`; `topRun` takes the attempt's; the list's own copy (`ordered`) keeps `Hiscores.revives(e.revives)`; `bestRun` takes the row's on both branches (a row that names its run and one that does not); `topRows` carries the entry's; `best` takes the companion's. Every reader of a stored or sent value goes through `Hiscores.revives`, so a junk value reads as none, and none is nil everywhere (0 is never stored: the rows of a run without revives are byte for byte the rows they were, which keeps every promoted `toEqual` of a row, entry, submission or best as it is).
- `Hiscores.revives` mirrors f0197's range for its `revives` (a whole number up to 2^53 - 1) and differs only in reading 0 as nil, as f0145's `Hiscores.lives` does; f0197's reader turns pickman's nil into its 0, so the library reads every row this writes.
- **Revives never rank and never replace.** `qualifies`, `rows`' sort and the list's order (`before`) do not read them: an equal score and level with fewer revives replaces nothing and keeps its tie-break (the user id; on the list, the instant and then the id). A row that does replace another carries its own run's revives (nil when it had none), never the stored row's: `commit` builds the row from the attempt, as it does every other field.
- A bad count never refuses a run: `valid` does not read `revives` (unlike f0197's, which refuses an attempt with bad revives), so a sim bug in the count can only show as none, never lose a score. This matches f0145's `lives`.
- **Submits** passes `submission.revives` as `HiscoreStore.submit`'s seventh argument, after f0145's `submission.lives`. **HiscoreStore** puts `revives` on the attempt it gives `Hiscores.topRun` (the run's list entry) and on the attempt `Hiscores.drive` writes (the three per-player rows). Both are optional and trailing, so every older caller (f0145's specs call `submit` with six arguments, d0124's with five) is unchanged.
- **Rows written before f0186** (no `revives`): read as none, shown as "REVIVES 0" (the capture's "Old entries without the field show as no revives"). Nothing migrates.
- **Servers on the build before f0186 during a publish** (Roblox keeps old servers until they empty): they write rows and list entries without revives (their runs counted none). Their list rewrite is `ordered`'s sanitising copy, which keeps only known fields, so an entry a new server wrote with revives loses them when an old server rewrites the list in that window, and shows "REVIVES 0" from then on; the per-player rows keep them (an old server's `commit` writes only its own run's row). An old server rewrites the list only when a run of its own changes the list's ids (`driveTop` writes nothing when `sameIds` holds), and then every entry it writes is stripped. It lasts one publish window, touches only the top-10 list's display, loses no score or place, and cannot be prevented from the new build (the old build's code drops the field). New servers read old servers' rows as none. Not accepted by this prep: it is put to the user with the f0145-era rows as G6 (E8).

### 3. Every board shows the revives (`Logic/Lobby`)
```lua
export type Row = { rank: number, name: string, score: number, level: number, lives: number?, revives: number? }
Lobby.REVIVES = "REVIVES"
function Lobby.revivesText(n: any): string -- "REVIVES n" for a whole n from 1 to 2^53 - 1, else "REVIVES 0"
-- removed: Lobby.livesText, Lobby.LIVES_MARK (f0145's lives display)
```
- `Lobby.Row` keeps f0145's `lives` (the rows `Hiscores.lobbyRows` gives still carry it, and a `{ Lobby.Row }` must accept them: without the field, f0145's own `Lobby.panel(Hiscores.lobbyRows(rows))` would stop type-checking, E7), but nothing reads it. `Lobby.panel` (and so `boardPanel`) copies `revives` with each row, and no longer `lives`; `Lobby.lines` writes each row as `{mark}{rank} {name} {score} {level} {Lobby.revivesText(revives)}`, so every board (all-time, today, this week, the top-10 list's all-time panel) shows the revives after the level, "REVIVES 0" for none and for a row stored before f0186, and never f0145's "♥n" (G1, G2). The empty board keeps its message.
- `Lobby.bestLine` (the viewer's own best under the all-time board, d0124) gains the best's revives the same way: `YOUR BEST {score} {level} {Lobby.revivesText(best.revives)}`; `Hiscores.best` carries them and the lobby's `Boards` already sends the best it reads, so no adapter changes (G1).
- What the server sends is read defensively: `revivesText` takes `any` and shows anything but a whole count of at least one as none.
- `LobbyView` is unchanged: it draws `Lobby.text(...)` already (f0026 pins its requires).

### Authority and what a client could lie about
Nothing new is sent by a client. The count is the server's sim (`Game.continue`, reached only through `Session.continue`, which f0145's adapters call only for a continue the server granted); the server submits it (`Submits` from the step events), stores it (`HiscoreStore`) and reads it back (`Boards`). A client only renders the frame's `play.revives` and the rows the lobby server sends, and reads both defensively.

### Edge cases
- No continue: `GameOver.revives` 0, the submission's, row's and entry's nil, every board "REVIVES 0", the game over "REVIVES 0".
- Continues then a departure in the offer (f0145's `depart`): the `GameOver` carries the continues taken; the run is submitted once with them (AC3).
- Continues then a refusal: impossible (a refused run is refused on arrival, before any death); a refused run emits no `GameOver` and submits nothing either way.
- A new run after a game over (`playAgain`, where a run restarts in place): starts at 0.
- A continue outside the offer, or one with a bad lives count: refused by f0145, counts nothing.
- A replaced row: the new run's revives, not the old row's; an equal run with different revives replaces nothing.
- Rows and list entries stored before f0186, junk stored values, junk sent values: none, shown "REVIVES 0".
- A deploy with old servers: §2 and E8, put to the user as G6.
- Many revives: the count is unbounded by f0145 (G5, unlimited); a whole count up to 2^53 - 1 shows; the panel's TextScaled line grows by a few characters.

### Scalability
Per step nothing: one integer per run, added to on a continue. Per finished run, the submit's payload gains one optional integer in each of the four writes it already makes (three companion rows, one list entry); no new request. Replicated: one optional integer in the frame's `play` (nil while none, so nothing for most runs) and one per row in the lobby's board answers.

### Maintainability
The count lives in one place (`Game.revives`, changed only by `Game.continue` and reset by `playAgain`); one reader for stored values (`Hiscores.revives`) and one formatter for display (`Lobby.revivesText`), used by the boards, the best line and the game over. The price words are one frozen table (`Lobby.PRICE`) with the same fields as the library's `Prices` (f0201), so c0202 swaps the table for the library's without touching a caller. Data, not branches: a new board or a new screen that shows a revive count calls `Lobby.revivesText`.

### Usability
- **Player**: every row of every board ends with how many revives the run bought, so a score bought with continues reads as such, and none says "REVIVES 0"; the game over says the same under the results; the lobby says a game is "<s>5 R$</s> 1 R$ SALE"; nothing else on the screens moves.
- **Developer**: two pure functions (`Hiscores.revives`, `Lobby.revivesText`), one field (`Game.revives`) and one optional argument (`HiscoreStore.submit`'s seventh), all typed; the frame's field is nil while none, so existing frame comparisons hold.
