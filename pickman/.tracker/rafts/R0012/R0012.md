# R0012: Mobile controls

## Theme
Roadmap raft **f**: playable on a phone. It can run any time after a2 (R0004). Gamepad support is out of scope. `tracker/game-design.md` Mobile, quoted:

> **Turns:** a swipe left/right/down triggers `Left`/`Right`/`Back`, and a swipe up triggers `Forward`, to take the next junction's straight exit.
> **Look:** drag on the right half of the screen.
> **HUD:** scales to small screens. Touch targets are at least 44 pt.
> **Recentring:** a "snap look to heading" button.

Movement stays the existing rail: the same four intents, the same fixed tick. Touch adds no fifth intent and no clock.

`tracker/game-design.md` Desktop keys (user, 2026-10-17; f0104, R0035), quoted because it moves the keyboard under this raft: "**Space** jumps (the spy hop, f0101). **E** fires the blaster (f0100). The **arrow keys look** ... The snap-look key goes away." The touch snap button stays (Mobile, "Recentring"), so this raft keeps `View.snap` and `Controls.start`'s first argument `onSnap` for the button whatever Space does. A touch jump or fire control is not in this raft (f0104's Non-goals say touch needs its own; none is captured).

**Folded in, c0106 (2026-10-20).** The danger radar (d0105) now sits bottom-right, one margin above the power bar, which on a phone is where Roblox draws its touch jump button. f0029 keeps the radar, the power bar and the snap button clear of that button in portrait and landscape (f0029 AC5, `jump.spec`). c0106 is a chore, so it cannot join this feature raft; it became the chore that narrows the two d0105 cases f0029 turns red, and it must be done before this raft is readied (Order & dependencies).

Prep decisions (the user may veto any of these; do not reopen them during execution):

1. The zone is chosen at touch-begin and locked for that finger. Viewport pixels, origin top-left. `x < width/2` is the turn zone; otherwise the look zone.
2. Turn (f0027): on finger-up, if the straight-line displacement is at least 48 px and the angle is within 30 degrees of a screen axis, emit one intent: screen-left Left, screen-right Right, screen-down Back, screen-up Forward. Otherwise emit nothing. Time is ignored. A second finger is ignored while one turn-zone touch is down. A look-zone finger never emits a turn.
3. Look (f0028): each move of a look-zone finger is `View.look(look, dx, dy)` with the existing `View.MOUSE_RADIANS_PER_PIXEL` (0.004) and `View.MAX_PITCH` (`math.rad(80)`). Releasing does not emit a turn. Pitch clamps and yaw wraps the same way the mouse path does (`yaw - dx * k`, `pitch - dy * k`).
4. Snap: a button whose rectangle a pure function computes. Each side is at least 44 px. It sits in the lower-right of the safe area and its rectangle does not intersect the HUD text blocks `Hud.layout` places. Activating it is `View.snap`, the call Space makes today (f0104 later takes Space for the jump; the button keeps `View.snap`). The button is not a turn and not a look drag: a touch that begins inside it is the snap control, even on the right half.
5. Keyboard and mouse stay exactly as they are when no touch is down. Touch does not unbind them. Gamepad is out of scope: `Controls.luau` must not contain the word `Gamepad`.
6. `Hud.layout` gains an optional inset `{ top, bottom, left, right }` defaulting to all zeros. With zero insets, the returned numbers are identical to today's `Hud.layout` for the same width and height. Text never goes below `Hud.MIN_TEXT` (14). The adapter passes numbers from `Hud.safeInset` of `GetInsetArea(Enum.ScreenInsets.None)` and `GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets)`. Logic only sees numbers. It does not read `GetGuiInset`.
7. Sample viewports the specs pin: 1920×1080 inset 0; 390×844 with top inset 47; 844×390 with left inset 47. Also a zero, negative, and NaN size, matching the existing `side()` behavior (`v > 0 and v < math.huge`, else 0).
8. Turns are the four intents `Movement` already accepts (`Left`, `Right`, `Back`, `Forward`). The client fires them through the existing Intent remote. `Session.submit` already returns `false, "invalid intent"` when `Movement.isIntent` rejects the value. Do not add a fifth intent.

Two further choices, also vetoable, made so the quoted rules can be tested without Roblox:

- One finger per zone, not only per turn zone. A second look finger would otherwise add a second delta in the same frame, and a second snap finger would fire `View.snap` twice. While a finger of that zone is down, a new finger in the same zone is ignored. A turn finger and a look finger may be down together.
- `GuiService.TouchControlsEnabled = false` once, when Controls starts, so the default thumbstick does not steal the left half. The property is set false; it is never set true.
- Roblox's jump button corner is reserved anyway (c0106): it cannot show today (no Humanoid, `CharacterAutoLoads = false`, and the property above), but a later character or a game-owned touch jump goes there, so the radar moves above it on a touch screen. Both of Roblox's placements are reserved as two rectangles (f0029 E7).

## Whole-raft design
View stays the presentation math it is (stateless key table, `View.look`, `View.snap`, `View.action`). A multi-finger fold is a different feature. New feature **Touch**, public API only through `src/shared/Logic/Touch/init.luau`. Declared edge, already written in `tracker/architecture.md`: `Touch -> View`. Touch does not require Movement, Hud, or the engine. `Touch.swipe` returns `View.action("A"|"D"|"S"|"W")`, which is one of the four intent strings, never `"Snap"`.

```lua
export type Zone = "turn" | "look" | "snap"
export type Rect = { x: number, y: number, w: number, h: number } -- half-open [x, x+w) × [y, y+h)
export type Phase = "begin" | "move" | "end"
export type Event = { id: number, phase: Phase, x: number, y: number } -- no time field
export type Finger = { zone: Zone, x0: number, y0: number, x: number, y: number }
export type State = { fingers: { [number]: Finger } }
export type Effect =
	{ kind: "turn", intent: "Left" | "Right" | "Back" | "Forward" }
	| { kind: "look", dx: number, dy: number }
	| { kind: "snap" }
export type Context = { width: number, snap: Rect? }
export type Box = {
	margin: number, iconSize: number, textSize: number,
	barWidth: number, barHeight: number,
	safeX: number, safeY: number, safeW: number, safeH: number,
}

Touch.MIN_SWIPE = 48
Touch.AXIS_DEGREES = 30
Touch.MIN_TARGET = 44 -- f0029 adds this constant

function Touch.empty(): State
function Touch.zone(width: number, x: number, y: number, snap: Rect?): Zone
function Touch.swipe(dx: number, dy: number): ("Left" | "Right" | "Back" | "Forward")? -- two parameters only
function Touch.track(state: State, event: Event, ctx: Context): (State, { Effect })
export type Area = { Min: { X: number, Y: number }, Max: { X: number, Y: number } }
function Touch.toScreen(none: Area?, x: number, y: number): (number, number) -- f0027: x - none.Min.X, y - none.Min.Y
function Touch.screenSize(none: Area?, fallbackW: number, fallbackH: number): (number, number) -- f0027: none.Max - none.Min, else the fallback
function Touch.snapRect(box: Box): Rect -- f0029, on the module f0027 creates
function Touch.blocks(box: Box): { score: Rect, level: Rect, lives: Rect, power: Rect }

-- f0029, on Hud (Hud.Box is d0105's { x, y, w, h }, not Touch.Box)
Hud.JUMP_SMALL_MAX = 500
Hud.JUMP: { small: { JumpRow }, large: { JumpRow } } -- JumpRow = { right, bottom, size }, legacy first
function Hud.jumpButtons(x: number, y: number, w: number, h: number): { Hud.Box }
function Hud.bandTop(core: Hud.Area, device: Hud.Area): number -- the top bar between DangerHud's frame and the HUD's
function Hud.radarBox(width: number, height: number, size: number, touch: boolean?, bandTop: number?): Hud.Box -- touch nil/false: d0105's box
```

**Coordinate spaces** (named once, after four review rounds that each found an offset applied in one place and not another; every row is taken from Roblox's creator-docs, fetched 2026-10-20, not from earlier rounds). The canonical space is **screen pixels**: origin the top-left of the device screen, `ScreenInsets.None`. Its size is the `GetInsetArea(None)` rect's size, which `Touch.screenSize` returns (Camera docs: "To obtain the fullscreen area size on all displays, you can query the `AbsoluteSize` of a `ScreenGui` with `ScreenInsets` set to `None`"). HudView's rects, the snap button, `Touch.zone`'s width and every point `Touch.track` sees are in it. The radar and the jump buttons it avoids are computed in DangerHud's device frame (last row) and drawn there. Four spaces exist, and each has exactly one conversion:

| space | documented as | who uses it | to screen pixels |
|---|---|---|---|
| screen (`ScreenInsets.None`) | ScreenInsets enum: None is no insets; Camera: the fullscreen area | HudView's ScreenGui (None), `Hud.layout(w, h, inset)` with `w, h = Touch.screenSize(none, ViewportSize.X, ViewportSize.Y)`, `Touch.track`, `Touch.zone`, `Touch.snapRect`, `Touch.blocks` | identity |
| core-UI safe area | ScreenInsets: "core UI insets added to the DeviceSafeInsets area" | HudView's blocks (the `safe*` fields of `Hud.layout`), Roblox's touch GUI (a default ScreenGui) | `+ (safeX, safeY)`, already inside `Hud.layout`'s numbers; the inset is `Hud.safeInset(None, CoreUISafeInsets)` |
| GUI-inset origin (the core-UI area's top-left) | GetInsetArea: rects "relative to the CoreUISafeInsets area"; InputObject.Position: "The inset applied to GUI elements (such as from the top bar) is accounted for in the position" | `InputObject.Position`, `AbsolutePosition`, `GetInsetArea` rects | `Touch.toScreen(GetInsetArea(None), x, y)`, in Controls, on every touch event |
| device safe area | Camera.ViewportSize: "the dimensions of the device safe area ... includes the Roblox top bar area but does not include any device notches"; ScreenGui: `IgnoreGuiInset = true` sets `DeviceSafeInsets` | `workspace.CurrentCamera.ViewportSize` (only a fallback size and HudView's re-layout signal), DangerHud's ScreenGui, `Hud.radarBox` and its `Hud.jumpButtons(0, band, ...)` | DangerHud's own frame, drawn by the engine; inside it `Hud.bandTop(core, device)` says where the core-UI area starts (the top bar) |

Rules: Logic never converts on its own; each adapter converts once at its boundary; no adapter reads `GetGuiInset`. A new HUD element states its space in its issue.

`Touch.zone`: a point inside the snap rect (inclusive minimum, exclusive maximum) is `"snap"`, even on the right half and even when `width` is not a positive finite number. Otherwise, when `width` is finite and `> 0` and `x < width/2`, the zone is `"turn"`. Every other point is `"look"` (width 0, negative, NaN, or infinite). The zone is stored on the finger at begin. Later moves, a later width, and a snap rect passed on a later event do not reclassify that finger.

`Touch.swipe(dx, dy)`: a non-finite `dx` or `dy` (NaN or ±infinite) returns nil. Distance is `math.sqrt(dx*dx + dy*dy)`; below 48 returns nil; 48 on an axis returns that axis. The cone, which the specs require, is:

```lua
local angle = math.atan2(math.abs(dy), math.abs(dx)) -- 0 horizontal .. pi/2 vertical
local fromAxis = math.min(angle, math.pi / 2 - angle)
if fromAxis > math.rad(30) + 1e-9 then
	return nil
end
if angle <= math.pi / 4 then
	-- horizontal: dx < 0 → View.action("A") == "Left"; else "D" == "Right"
else
	-- vertical: dy > 0 → View.action("S") == "Back" (screen-down); else "W" == "Forward"
end
```

The `1e-9` is required. A plain `>` against `math.rad(30)`, and a plain `tan` test, both classify `80 * cos(rad(60)), 80 * sin(rad(60))` as the dead zone. The spec expects that vector to be `"Back"`. `1e-9` only absorbs those ulps: 31° of length 80 stays nil. The tangent boundary `dy = dx * tan(rad(30))` is horizontal; `dx = dy * tan(rad(30))` is vertical; one pixel past either boundary is nil.

`Touch.track` returns a fresh state and does not mutate the state it was given, including on move and end: the input finger's `x`, `y`, and `zone` stay, and the returned table is a different one. A begin on `Touch.empty()` still adds nothing to that empty table. Two separate tracks of one begin state to the same move both return that move's delta, so a module-level cursor cannot turn the second call into a zero step. The zero step is a second move of the **returned** state to the same point. `begin` of an id that is already down, or of a zone that already has a finger, emits nothing and adds nothing to the returned state (a second snap finger included: finger 1 stays, finger 2 is absent, and ending finger 1 leaves no fingers). Otherwise the finger is locked to `Touch.zone`. Snap emits `{ kind = "snap" }` on begin only (the same moment Space uses `UserInputState.Begin`) and nothing on move or end. A look move emits the pixel step from the previous point, including `{ dx = 0, dy = 0 }` on the returned state. A turn or snap move only updates the point on the returned state. `end` of a turn finger emits at most one swipe from `(x0, y0)` to **the end event's** position (the straight line, not the path length). Look and snap ends emit nothing. An unknown phase, or a move or end for an id that never began, emits nothing.

Nothing f0029 places covers the forward view: HUD blocks and the snap button occupy the margin bands. d0105's radar is a deliberate overlay in its lower right, and on a touch screen it is lifted above Roblox's jump button corner (f0029, "Jump button corner"). It does not overlap the forward rect whose bottom is `safeY + safeH - margin - max(iconSize, barHeight, 44)`, which is `{ x = 0, y = 20, w = 100, h = 231 }`. The three sample viewports miss both lives and that forward rect, so they never enter a fallback.
```lua
side = max(44, iconSize)
x = safeX + safeW - 2*margin - barWidth - side
y = safeY + safeH - margin - side
w = h = side
```

The gap to the power bar is exactly `margin` (half-open edges are not hits). The button misses the four blocks when `safeW >= 2 * (2*margin + barWidth + side)`. All three required samples satisfy that. A narrower safe width may overlap lives; it still has side ≥ 44 and it stays in the bottom band.

The forward view, independent of where a widget actually sits:

```lua
x = safeX
y = safeY + textSize + 2*margin
w = safeW
h = (safeY + safeH - margin - max(iconSize, barHeight, side)) - y
```

On the three samples `h > 0`, and neither the button nor the four blocks intersect it. `button.y` equals the forward bottom, so the half-open test misses.

`Hud.layout(width, height, inset?)` sanitizes each inset component with the same `side()` rule. `safeX = left`, `safeY = top`, `safeW = max(0, w - left - right)`, `safeH = max(0, h - top - bottom)`, where `w` and `h` are the sanitized viewport sides. Text, margin, and icon size still come from the **full** viewport's smaller side, so a top inset does not change `textSize` (the witness is `safeY`). `barWidth` uses `safeW` in place of `w`:

```lua
barWidth = max(0, min(round(safeW * Hud.BAR_SHARE), Hud.MAX_BAR, safeW - 2*margin))
```

Zero insets make `safeW == w`, so every width keeps today's bar, not only the samples. Do not reserve the button inside `barWidth`: that would change the zero-inset bar below the 400 px cap. New fields: `safeX`, `safeY`, `safeW`, `safeH`. `barHeight` is unchanged (`max(4, round(text * 0.4))`; at the 14 px minimum that is 6, not 4).

## Order & dependencies
