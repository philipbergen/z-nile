### F1 [high] AC5's flow pin passes a Controls that reads the screen width once, in `Controls.start`, so the per-event read the AC states can be skipped (repeat of review-004 F2's mechanism)
Where: tracker/issues/f0027/acceptance/place.spec.luau:39-68 (the "Controls reads the None area per event" case); f0027.md AC5 ("Controls reads `GetInsetArea(ScreenInsets.None)` inline in its `Touch.toScreen` and `Touch.screenSize` calls on each event"); the rules row "Controls reads the area inline per event", marked `run`; refute-004 F2 ("the read is inline, so it cannot be hoisted to `start`").
Evidence: the inline read stops hoisting only for `Touch.toScreen`, because that call needs `input.Position`. `Touch.screenSize(GuiService:GetInsetArea(None), camera.ViewportSize.X, camera.ViewportSize.Y)` takes nothing from the event, so it can sit at the top of `Controls.start`. The pin looks for `local w = Touch.screenSize(GuiService:GetInsetArea(` anywhere in the file, and for `width = w` in the `Touch.track` call. I ran this in a scratch clone (`git clone --no-hardlinks` under `$TMPDIR`, a stub `Touch/init.luau`, and a full Controls touch path that computes `local sw = Touch.screenSize(GuiService:GetInsetArea(Enum.ScreenInsets.None), camera.ViewportSize.X, camera.ViewportSize.Y)` once in `start` and passes `{ width = sw, ... }` from the handler). `lune run tests/run -- tracker/issues/f0027/acceptance/place.spec.luau` gives `4 passed, 0 failed`. A second mutant in the same clone also passes all 4. It caches the origin at start with `local ox, oy = Touch.toScreen(GuiService:GetInsetArea(Enum.ScreenInsets.None), 0, 0)` and builds the event with `x = ox + px, y = oy + py` from `local p = input.Position; local px, py = p.X, p.Y`. That is review-004 F2's cached area under another spelling. `x%s*=%s*ox%f[^%w_]` matches `x = ox + px`, and the call text no longer contains `Position`. The first mutant is the natural one ("the width does not change per event"). Controls starts in Main before `ready:FireServer()`, which is the window in which the design says the area can be empty (E5). There the width falls back to `ViewportSize` for the whole session: on the documented phone that is 733, not 851, which is exactly the screen-x-400 turn/look split that screen.spec's new case exists to prevent, now through a different door. The `run` mark on the rules row is true only for the mutants that were listed.
Critique: the tempting fix is one more pattern: require `Position` in the `toScreen` arguments, and forbid `Touch.screenSize(` before `local function`. Each round's pattern has been bypassed by the next spelling: review 003's points, 004's cache, and now the width and the origin. The text cannot express "evaluated per event". A position-only rule can: the reads must lie inside the same function body as the one `Touch.track(` call.
Consequences: a scope rule constrains structure. The handler that calls `Touch.track` must also make both reads, with no `local function point(input)` helper that returns the converted pair. The design text must say so, or a reasonable executor writes the helper and fails a sequestered spec. A cached origin computed at `(0, 0)` has to fail on its own. "Inside the handler" alone does not catch it if the executor caches `ox` in an upvalue that the handler assigns on the first event only. Pinning the `toScreen` arguments to `input.Position` closes that.
Recommendation: In the f0027 Controls case, find `trackAt = string.find(src, "Touch.track(", 1, true)`, and the start of its enclosing function, `fnAt`, which is the last `function` keyword before `trackAt`. Require both locals' matches (the `local a, b = Touch.toScreen(GuiService:GetInsetArea(...None` and the `local w = Touch.screenSize(GuiService:GetInsetArea(...None`) to start after `fnAt` and before `trackAt`. Require the `toScreen` call to read the event: `Touch%.toScreen%(%s*GuiService:GetInsetArea%b()%s*,%s*[%w_]+%.Position%.X%s*,%s*[%w_]+%.Position%.Y`. In f0027.md's Controls paragraph, state "in the same function as the `Touch.track(` call, with no helper between". Add both mutants above (the width at start, and the origin of `(0, 0)` at start) to the rules row, and re-run the row on the prototype Controls. If you would rather end text pins for adapter data flow, the mechanism alternative is a behavioural spec through `@tests/lib/fakeengine` (the testing skill allows extending it): a scripted `GuiService:GetInsetArea` that is empty on the first call and the documented phone after it, then a touch at screen x 400 that must fire `Left` on release. That costs fakeengine a client surface (UserInputService, GuiService, CurrentCamera), which is more than a final round should take on. The scope pin is enough.

### F2 [high] AC3's "re-lays from `PickmanHud`" is checked only as the substring `PickmanHud`: a HudView that reads both inset areas once passes every HudView pin, and a 180° phone flip then leaves the HUD under the notch
Where: tracker/issues/f0029/acceptance/place.spec.luau:23-74 (`has("PickmanHud")`, the `GetInsetArea` substrings, the `Touch.screenSize` line); f0029.md AC3 ("re-lays from `PickmanHud`") and Design ("`BindToRenderStep` named `PickmanHud` rewrites when the viewport size or any of the four inset numbers changes, including from a first-frame empty area to the real one"); R0012.md:188.
Evidence: In the same scratch clone, HudView reads `local none = GuiService:GetInsetArea(Enum.ScreenInsets.None)` and `local inset = Hud.safeInset(none, GuiService:GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets))` once, at module load. `lay()` keeps today's `ViewportSize` signal and calls `local sw, sh = Touch.screenSize(none, camera.ViewportSize.X, camera.ViewportSize.Y)` then `Hud.layout(sw, sh, inset)`. `start` sets `IgnoreGuiInset = true`, then `ScreenInsets` and `SafeAreaCompatibility` to None, adds the `Snap` frame and `function HudView.snapRect(`, and binds `RunService:BindToRenderStep("PickmanHud", 200, function() end)`, an empty step. `lune run tests/run -- tracker/issues/f0029/acceptance/place.spec.luau tests/acceptance/f0019/place.spec.luau` passes every HudView case. Only "Main gives Controls the snap rectangle" fails, because I left Main alone. Two wrong results follow, and the second needs no Studio premise:
- First frames empty (the design's own E5 premise): the inset stays all zeros and the size stays `ViewportSize` for the session. The score is drawn at screen `(9, 9)` in a `ScreenInsets.None` gui, under the notch and the top bar. The snap rect is laid out on 733×371 while Controls converts touches with the real area, so the drawn button and the half split disagree with the converted points.
- Rotation between LandscapeLeft and LandscapeRight: the notch changes sides, so `GetInsetArea(None)` swaps its left and right insets (59 and 0 become 0 and 59), while `ViewportSize` keeps its size and does not fire. A cached inset keeps the HUD's safe rect on the old side, and LEVEL and the power bar run under the notch. Even a correct HudView that re-lays only on the `ViewportSize` signal misses this. Only the per-frame comparison of the four numbers that the design prescribes catches it, and nothing checks for that comparison.

The design's trigger is also keyed on "the viewport or the four inset numbers", but what HudView lays out is `(sw, sh)` from the None area. The key should be the layout's actual inputs.
Critique: the tempting fix is to require the `GetInsetArea(` substrings after the `BindToRenderStep(` substring. A `lay()` defined above the bind, which the bind calls, then fails while it is correct, and a read placed after the bind but outside its callback still passes. This is F1's problem in HudView: per-frame evaluation pinned by text.
Consequences: the design has to fix one structure the pin can read. Prescribe that the `PickmanHud` callback itself makes both `GetInsetArea` reads and the `Touch.screenSize` call, compares `(sw, sh, top, bottom, left, right)` with the last key, and calls `lay(sw, sh, inset)` only when the key changed. `lay` then takes its inputs as parameters and reads no area. `HudView.show`'s re-layout on a life change reuses the last key's numbers, so it does not read the area either. The first layout before the first render step uses the fallback, with a zero inset and `ViewportSize`, which is the documented empty-area behaviour.
Recommendation: In f0029 place.spec, add a case: let `bindAt` be the position of `BindToRenderStep%(%s*"PickmanHud"`, and `body` the text from `bindAt` to the first `\n%s*end%)` after it. `body` must contain `GetInsetArea(` for `None` and for `CoreUISafeInsets`, and `Touch.screenSize(`. No `GetInsetArea(` may occur outside `body`. The existing `Hud.layout(<w>, <h>,` check stays. Update f0029.md's Design and AC3 to say this, and change the trigger key in f0029 and R0012:188 to "the screen size from `Touch.screenSize` or any of the four inset numbers". Rules row: mutants "areas read once at module load", "areas read in `start`" and "an empty `PickmanHud` with the reads in `lay()` on the `ViewportSize` signal" each fail the new case; run them on a prototype HudView. Add an Observed step to E5's Phase 1: in the device emulator, rotate a notched phone 180° and check that LEVEL and the power bar move off the notch side.

## Other areas checked, no finding
- **Coordinate-spaces table, row by row against the docs.** Screen row: `ScreenInsets.None` is "No insets are added to the fullscreen area", and Camera says "the `AbsoluteSize` of a `ScreenGui` with `ScreenInsets` set to `None`" is the fullscreen size. Correct. Core-UI row: "Core UI insets are added to the `DeviceSafeInsets` area". Correct. That settles the row's claim about `AbsolutePosition` and narrows E9's residual question (does the origin include the left notch?) to a Studio-only check, which E9's Phase 1 tap covers with stop-and-report. Correct, and it matches DangerHud's `gui.IgnoreGuiInset = true` with `gui.AbsoluteSize`.
