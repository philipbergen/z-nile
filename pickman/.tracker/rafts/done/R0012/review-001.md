### F1 [high] A swipe or a snap tap that ends before the camera's render step leaks that frame's touch motion into mouse look
Where: src/client/Camera.luau:42-51 and 68-73; src/client/Controls.luau:104-110; raft design, "Adapters, thin" (Camera bullet) and E6.
Evidence: The design takes E6's premise as its working assumption: while the mouse is locked, a touch also moves the locked mouse, so `GetMouseDelta()` carries the touch. Two flags guard against that. `mouseHeld` is cleared by `onTouch(false)` from inside `InputEnded`. `lookedThisFrame` is set only by `Camera.lookBy`. Roblox runs input events before the `PickmanCamera` render step of the same frame. Take a turn finger that moves and lifts within one frame (the last frame of any fast swipe, or a whole flick inside 16 ms). `InputChanged` updates the turn finger, which emits nothing. `InputEnded` folds the end, fires `Left`, finds no fingers left and calls `Camera.holdMouse(false)`. The render step then reads `mouseHeld == false` and `lookedThisFrame == false`, because a turn finger never calls `lookBy`, and applies `View.look(look, delta.X, delta.Y)` with that frame's touch motion. Every swipe therefore ends with a yaw jolt of its last frame's motion. A tap on the snap button (begin and end in the same frame, or the release frame of any tap) does the same thing right after `View.snap`, so the recentre lands off-centre. Design review 001 F6 named this same-frame hole ("a same-frame tap is applied twice unless a latch ... survives until the render step"), but the latch it produced is set only by `lookBy`, which closes the hole for look fingers and not for turn or snap fingers. The code comment at Camera.luau:72 ("a touch that began and ended before this step still looked") describes only the look case.
Critique: Under the premise the design builds on, the turn gesture, which is the main phone control, also turns the camera. That is the behaviour `mouseHeld` was added to stop ("mouseHeld is what keeps a swipe from also looking"). If E6 turns out false, `mouseHeld` is moot and nothing leaks, but the design chose not to rely on that. The tempting fix is to delay `onTouch(false)` in Controls by a frame with `task.defer` or a heartbeat wait. That puts timing in the adapter and still races the render step.
Consequences: Whatever holds the suppression has to outlive the release until the render step has read `GetMouseDelta` once. That makes it a second per-frame latch, which the design's "one flag and one latch" rule and the f0028 line "`holdMouse` sets `mouseHeld` and does nothing else" don't allow. The f0028 place spec pins only that `not mouseHeld and not lookedThisFrame` precedes `View.look(look, delta`, and that the first `lookedThisFrame = false` sits between that call and `snap == nil`. A fix must keep both substrings and that order. It costs one frame of real mouse delta after each touch release, which is negligible.
Recommendation: Make the release survive one render step. For example, `Camera.holdMouse(held)` sets `mouseHeld = held` and, on any call, also sets the existing latch (`lookedThisFrame = true`), so the frame in which a finger went down or came up never applies the mouse delta. Rename or re-comment the latch as "a touch touched the mouse since the last render step". Record it in f0028's Verification log as a deviation from "`holdMouse` does nothing else" and from "`lookedThisFrame` is set only in `lookBy`", with this scenario as the reason. If the author reads those two lines as binding design rules rather than implementation detail, escalate to the user with two options: the latch in `holdMouse` (one frame of mouse delta dropped per touch change), or keeping the design as written and accepting the per-swipe jolt until OC1 measures E6. Add this to OC1's steps either way: swipe fast on the left half and confirm the view does not yaw.

### F2 [medium] `onTouch` follows the fold's tracked fingers, so an ignored second finger moves the locked mouse once the tracked one lifts
Where: src/client/Controls.luau:104-110 (`local down = next(fingers.fingers) ~= nil`).
Evidence: Finger A begins in the turn zone, and the fold tracks it. Finger B begins in the turn zone too, and the fold ignores it ("one finger per zone"), but `ids[B]` is assigned. A lifts. `fingers.fingers` is now empty, so `onTouch(false)` clears `mouseHeld` while B is still physically down. Every frame after that, B's motion reaches `GetMouseDelta` (under the same E6 premise as F1) and the render step applies it as mouse look. A turn-zone finger then drags the view, which goes against "A turn finger never calls `lookBy`, so `mouseHeld` is what keeps a swipe from also looking" and f0027's Usability line "The second finger cannot contradict the first". The same happens with an ignored second look finger after the first lifts: it keeps looking through the mouse path, at whatever rate the engine gives a touch-driven mouse.
Critique: The adapter already knows every physical touch (`ids`), but it reports a different count to Camera. The tempting fix is to track the ignored finger in the fold. That breaks AC2's "a second finger in an occupied zone ... adds nothing to the returned state" and the f0028 second-snap-finger case.
Consequences: Counting physical touches means `ids` has to be cleaned up exactly once per touch, which `InputEnded` already does. A touch whose `InputEnded` never arrives would keep `mouseHeld` set (F7 covers the same hole on the fold's side). The design's wording, "when the tracked finger count leaves or returns to zero", is what has to change, so this is a recorded deviation.
Recommendation: Compute `down` from the adapter's own table of touches that are physically down (`next(ids) ~= nil`), not from `fingers.fingers`, and record the deviation in f0027's Verification log with this scenario. Add a non-sequestered adapter pin for it (see F3).

### F3 [medium] Nothing pins the arguments Controls passes into the fold or the way it dispatches the fold's effects
Where: src/client/Controls.luau:86-110; tracker/issues/active/f0027/acceptance/place.spec.luau; tracker/issues/active/f0029/acceptance/place.spec.luau:110-112.
Evidence: f0027's place spec pins `x = sx`, `y = sy`, `width = sw` and the substrings `Touch.track(`, `onTouch(`. f0029's place spec pins only that Main mentions `HudView.snapRect`. Several wrong versions of Controls still pass every check (I read the patterns in both place specs):
- `{ width = sw, snap = nil }` in place of `snap = rect`, so the drawn button on the right half is a look drag and on the left half a turn.
- `onLook(effect.dy, effect.dx)`.
- `intent:FireServer(effect.kind)`.
- An `onTouch(true)` called on every event.
- `local rect = snapRect` without the call.

Each one makes the phone controls wrong with the gate green, because the fold specs exercise only the pure fold.
Critique: The current code is right, so this is a regression trap rather than a present defect. It is the gap the pin-call-site-arguments lesson describes. The tempting fix is to rely on OC1, which runs once and by hand.
Consequences: A source-text pin is cheap but brittle. A behavioural pin needs `@tests/lib/fakeengine` to grow `UserInputService` input signals, `InputObject`s and `GuiService:GetInsetArea`. That extension must not make the fake accept less or more than it does now (testing skill).
Recommendation: Add an editable spec (for example `tests/place/controls-touch.spec.luau`; acceptance specs stay untouched) that pins, on Controls' source with comments stripped, `snap = <the local assigned from snapRect()>` in the one `Touch.track(` context, `FireServer(effect.intent)`, `onLook(effect.dx, effect.dy)` and `onSnap()`, and that `onTouch(` is called only inside a change of the held state. The stronger option is to drive Controls through fakeengine with three fingers: the snap button on the right half, a turn and a look. Either way, add a mutant row for each wrong version listed above.
Lesson: testing/pin-call-site-arguments

### F5 [low] The snap control is drawn on desktop, where it does nothing
Where: src/client/HudView.luau:116-127.
Evidence: HudView always creates the translucent `Snap` circle. On a mouse-and-keyboard screen a click is not `UserInputType.Touch`, so the circle never acts. It is a new, unlabeled dead control left of the power bar on every desktop HUD. The raft says "Keyboard and mouse stay exactly as they are when no touch is down". The design says only that the frame is visible so OC1 can tap it.
Critique: This is a visible desktop change no issue asked for. Hiding it is a product question, not a defect the author can settle alone.
Consequences: Gating on `UserInputService.TouchEnabled` hides it on desktop but still shows it on touch laptops. Gating on `LastInputType` makes it flicker as the input changes. `HudView.snapRect` should keep returning the rectangle either way, since only touches reach the fold.
Recommendation: escalate to the user: show it always (as now), show it only when `UserInputService.TouchEnabled`, or show it once a touch has been seen. Record the decision in f0029.

### F7 [low] A touch whose end never arrives locks its zone for the rest of the session
Where: src/shared/Logic/Touch/init.luau (begin refuses a zone that already has a finger) and src/client/Controls.luau (the fold is never reset).
Evidence: If an `InputEnded` for a touch is lost (for example, the app is backgrounded mid-touch; I have not verified whether Roblox guarantees an end, with `UserInputState.Cancel`, in that case), that finger stays in `fingers` for good. Every later begin in that zone is refused, so the player can never turn again (or look again), and `mouseHeld` stays set. Nothing resets the fold.
Critique: There is no recovery path, and the failure is total for that zone. Whether it can happen depends on an unverified engine guarantee.
Consequences: A reset (`fingers = Touch.empty()`, `ids = {}`, `onTouch(false)`) has to come from an engine event, for example `UserInputService.WindowFocusReleased`. A reset in the middle of a gesture drops that gesture, which is acceptable.
Recommendation: Add the E-style question to F4's Studio list (background the app mid-swipe, return, and swipe again). If it fails, reset the adapter's fold on `WindowFocusReleased` in a follow-up issue.

## Lesson candidates (for the raft lead; this reviewer writes no lesson file)
- testing: an order pin that uses the first match of a substring must anchor on text that occurs once. f0028 AC3 takes the first `lookedThisFrame = false` as "the clear", so a natural `local lookedThisFrame = false` declaration made the correct code fail, and the executor had to write `local lookedThisFrame, mouseHeld = false, false` to get past it. Check: does each substring an order pin locates occur exactly once in a correct source, declarations included?
- architecture: a suppression flag that an event releases must survive until the consumer that reads the suppressed value has run. Otherwise the event and the read race inside one frame. Here `onTouch(false)` clears `mouseHeld` before the render step reads `GetMouseDelta` (F1). Check: for each flag cleared from an input event and read in a render step, what does the render step see when the set and the clear happen in the same frame?
