### F1 [medium] The cursor criterion passes with the most likely wrong Camera change: a `setCursor` that the render step immediately re-locks
Where: tracker/issues/f0031/f0031.md:41, :91, AC3 (:206); tracker/issues/f0031/acceptance/place.spec.luau:67-73; src/client/Camera.luau:37
Evidence: Camera's render step currently does `UserInputService.MouseBehavior = Enum.MouseBehavior.LockCenter` unconditionally every frame (Camera.luau:37). An implementation that adds `function Camera.setCursor(free) UserInputService.MouseBehavior = if free then Enum.MouseBehavior.Default else Enum.MouseBehavior.LockCenter; UserInputService.MouseIconEnabled = free end` and leaves line 37 alone passes every f0031 check: `function Camera.setCursor(` exists, `MouseBehavior.Default` appears, Main calls `Camera.setCursor(overlay.playAgain)`. In play the render step re-locks the mouse on the next frame, so the PLAY AGAIN button can never be clicked with a mouse, which is exactly the failure the design itself calls out ("Without this the button can't be clicked"). The Rules and mutants row F17 only covers "not wired".
Critique: the author will reach for "it's in OC1". But this is the single most plausible adapter error here, and it can be pinned by text the same way f0054 pins the interpolate call.
Consequences: a text pin on Camera interacts with f0054/adapters.spec (which reads the same file): it must not touch the `View.interpolate(...)` line or introduce `TICK_RATE`. A pure helper instead would add a View edge-free function and a unit case, which is more surface than needed.
Recommendation: add a case to f0031 place.spec: Camera's source (comments stripped) has no unconditional lock, i.e. `string.find(camera, "MouseBehavior%s*=%s*Enum%.MouseBehavior%.LockCenter")` is nil (the conditional form `= if free then … else Enum.MouseBehavior.LockCenter` doesn't match it), and `MouseIconEnabled%s*=%s*false` no longer appears outside of `start` (or simply: `MouseIconEnabled` is assigned from a variable, `MouseIconEnabled%s*=%s*[%a_][%w_]*%s*\n`). State in the Design that the render step reads the flag set by `setCursor` and sets both properties from it every frame. Add Rules row "the render step honours the cursor flag | place :: Camera never locks the mouse unconditionally | F18 setCursor sets it once, render step re-locks | run". Update AC3's wording to match.

### F2 [medium] The "sender's own id" check accepts a handler that trusts a Player instance sent by the client
Where: tracker/issues/f0031/acceptance/adapter.spec.luau:39-54; f0031.md AC2 (:200), Rules row F13 (:183)
Evidence: the pattern `^Session%.playAgain%(%s*[%w_]+%s*,%s*tostring%(%s*[%w_]+%.UserId%s*%)%s*%)$` accepts any identifier before `.UserId`. This handler passes the spec:
```lua
playAgain.OnServerEvent:Connect(function(_player: Player, who: Player)
    local s = sessions[who]
    if s then Session.playAgain(s, tostring(who.UserId)) end
end)
```
Instances replicate as RemoteEvent arguments, so a client can pass another `Player` and restart someone else's game-over run. That is the authority hole the criterion says it closes ("for the sender's own session"), and the client-side "no arguments" check (place.spec:83-87) doesn't constrain the server.
Critique: the tempting fix is to hard-code the name `player` in the regex, which over-pins style and breaks on a rename.
Consequences: binding the parameter name means the spec has to find the handler that contains the `Session.playAgain` call. Sessions has three `OnServerEvent:Connect(function(` handlers (Ready, Intent, PlayAgain), so the spec must pick the right one, for example the one following `PlayAgain`'s local.
Recommendation: in adapter.spec, capture the handler's parameter list. For each `OnServerEvent:Connect%(function%(([^)]*)%)(.-)\nend%)` match whose body contains `Session.playAgain`, require: exactly one parameter (no comma in the list), and the call's `tostring(<x>.UserId)` uses that parameter's name, and the session lookup is `sessions[<that name>]` (or whatever table name, but indexed by that parameter). Add a mutant row "F13b reads the target from a second argument" and record that it's killed.

### F3 [low] `Pellets.slots` "returns a fresh copy" has no row and no case; a cached shared list survives
Where: tracker/issues/f0030/f0030.md:31, :43; acceptance/wire.spec.luau:53-60
Evidence: "slots describe the layout, not what is left" compares `Pellets.slots(m)` to `before`. If `slots` returns the cached table itself, `before` and the second result are the same object and `toEqual` trivially passes. A caller that mutates the list (PelletView building parts, a future fruit slot) would then corrupt the cache for every later `encode`/`decode` of that maze: wire order drift between server and client.
Recommendation: add a wire.spec case: `local a = Pellets.slots(m); a[1] = nil; table.insert(a, {x=0,y=0,kind="pellet"}); a[2].x = 99`, then `Pellets.slots(m)` still equals a fresh expectation (e.g. 244 entries, `[2]` unchanged, `encode(Pellets.new(m))` still forty `_` and `P`). Add the row "slots is a fresh list | wire :: changing a returned slot list changes nothing | returns the cached table".

### F4 [low] Hud.layout: "an infinite side counts as 0" is in the Design but neither specced nor true of the given arithmetic
Where: tracker/issues/f0019/f0019.md:44; acceptance/layout.spec.luau:71-77
Evidence: the degenerate case covers 0, negative and NaN only. With the stated formulas and no guard, `Hud.layout(math.huge, 720)` gives textSize 32 and barWidth 400, not the minimum the Design promises. Nothing distinguishes the two, so the executor may implement either.
Recommendation: decide one. Either add `{ math.huge, 720 }` and `{ 1280, -math.huge }` to the degenerate case (expect `MIN_TEXT` and whole numbers) plus a Rules row "infinite side → minimum | layout :: a zero, negative, NaN or infinite viewport… | H14 no inf guard", or delete "or infinite" from the Design.

### F5 [low] "Below the eye line" is pinned for the centre only; a power pellet's top is above the eye
Where: tracker/issues/f0030/f0030.md:35, :85, AC3 (:170); acceptance/placement.spec.luau:35-44
Evidence: height 3, power diameter 3, so the ball spans 1.5–4.5 studs while the eye is at 4 (`View.SCALE.eyeHeight`). The spec checks `height < eyeHeight` and `height + d/2 < wallHeight`, so it passes. The Usability text ("line the corridor just below eye level") and AC3 read as if the whole pellet is below the eye. Not wrong in play (the pellet is eaten before the camera reaches it), but the AC claims something the spec doesn't check.
Recommendation: either reword AC3 to "centred below the eye line" (no spec change), or, if the whole ball should be below the eye, add `View.PELLET.height + d/2 <= s.eyeHeight` to the case and lower `height` to 2.5. If you take the second option, the 0.5° corridor case is unaffected (it uses only the diameter).

### F6 [low] Client boot order and handler robustness are unstated
Where: R0015.md:63 ("each adds one boot call"); f0019.md:63; f0031.md:99; f0030.md:68; src/client/Main.client.luau:17-32
Evidence: Main connects `OnClientEvent` first and fires `Ready` last. `HudView.start` (PlayerGui) and `FlowView.start` (`WaitForChild("PlayAgain")`) can yield. If an executor appends the new `start()` calls after `ready:FireServer()` (the end of the file is the natural place for "one more boot call"), a frame can arrive while `start` is still yielding, and `HudView.show`/`FlowView.show` index nil widgets and error. Also, with the diagram's order (PelletView.show before HudView.show and Flow), a `Pellets.decode` error (strict by design) aborts the HUD and overlay updates for that frame. Separately, Main's `lit` flag isn't reset when the maze model is rebuilt, so a rebuild during a lit flash leaves new walls blue while `lit` is true.
Recommendation: one sentence in R0015's interface section: all `start()` calls go before `ready:FireServer()`, and each `show` is a no-op until its `start` has run. Reset `lit = false` when the model is rebuilt. Optionally order the per-frame calls Hud, Flow, then Pellets, so a bad pellet code can't blank the HUD. No spec needed; the f0014 place spec already shows Ready is fired.
