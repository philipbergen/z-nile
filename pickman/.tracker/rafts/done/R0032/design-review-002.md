### F1 [medium] Nobody owns setting the lobby's id on the game place: c0064 and f0065 each hand it to the other
Where: c0064.md Design, "f0065 coordination"; R0032.md Order & dependencies; R0034.md Risks and f0065.md E6, Touched modules (prep-game-over-to-lobby)
Evidence: c0064 says the game target's attribute row is "added by whichever of f0065 or this raft lands second" and "This raft does not choose f0065's attribute name". f0065's prepped design has now chosen the name: "the attribute `LobbyPlaceId` on `ServerScriptService`, `0` as checked in". Its Non-goals give "configuring their ids" to c0064, and R0034's Risks say "c0064 ... sets `GamePlaceId` on the lobby; it, or a follow-up chore, must set `LobbyPlaceId` too." Two cases:
- c0064 lands first: f0065 is never going to edit the Beta plan, so the way back stays "The lobby is not set up yet." in Beta.
- c0064 lands second: its executor has no rule row, spec case or AC asking for the row, and the Design tells it not to choose the name. Nothing in `check.sh` fails if it is left out.

Either way, f0065's O2 (from the game over back to the lobby in Beta) can never pass without an issue nobody has filed.
Critique: round 1's F1 fix left room in the specs for the row, but nobody owns adding it. The obvious fix is to "leave it to f0065". That contradicts f0065's own scope: it is a feature, its Touched list is `src/` and `default.project.json`, and it explicitly defers the ids to c0064.
Consequences: if c0064 sets `LobbyPlaceId` on the game target in split mode, the game place carries an attribute nothing reads until f0065 lands. That is harmless: f0061/lobby-place pins only `GamePlaceId == nil` on the game, and c0064's project.spec copies the game with `{}`. Once f0065 adds `"$attributes": { "LobbyPlaceId": 0 }` to `default.project.json`, `Beta.project` merges over it (`writes the attributes beside ...`), so the published game gets the real id. Legacy mode has no lobby, so the game keeps 0 there, which f0065 shows as "not set up": the right outcome. f0065's design review could still rename the attribute. If it does, both documents must change together, so c0064 must cite the name's source.
Recommendation: in c0064, make the split plan's game target `attributes = { LobbyPlaceId = <start id as a number> }`, and in legacy mode keep `{}`. Cite f0065's Design as the source of the name, and note that a rename in f0065's review must be mirrored here. Then tell R0034's author (or have the user tell them) to drop "or a follow-up chore" from its Risks and E6.
