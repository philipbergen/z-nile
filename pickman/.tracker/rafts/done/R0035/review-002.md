### F1 [medium] hud-shots measures the bars only inside the `Shots` frame, so a `Shots` frame that is never laid over the lives passes
Where: `src/client/HudView.luau:74-76` (`shots.Position = lives.Position`, `shots.Size = lives.Size`); `tests/place/hud-shots.spec.luau` (`placed`, `want`)
Evidence: `placed()` reads each bar's `Position`/`Size`, which are offsets from the `Shots` frame, and `want()` is `Hud.shotIcons(...)`, also in the lives row's own pixels. Nothing reads the `Shots` frame's own `Position` or `Size`. On a scratch clone, deleting line 75 (`shots.Position = lives.Position`) leaves `hud-shots` and `touch-adapters` at 14/14 passed, and so does deleting line 76; no other spec mentions the frame (`grep -rn "Shots\|lives.Position" tests tracker/issues/active/*/acceptance`). With line 75 gone the bars are drawn from the ScreenGui's top-left corner, on top of the score, which is the opposite of f0100's Design ("a `Shots` frame laid over the `Lives` frame") and of AC4 "the HUD bars after the lives". The refute's claim, "the shot frames sit at `Hud.shotIcons(Hud.layout(W, H, inset), lives, shots)`", holds only in the parent's coordinates.
Critique: review-001 F2 found a hole in this same wiring (HudView → the screen position of the bars), and the fix pinned one link of a two-link chain. The tempting fix is one more assertion, `Shots.Position == Lives.Position`. That passes if both frames are wrong together (for example, if the Lives frame's own placement from `Touch.blocks(l).lives` were dropped, both sit at the default and agree).
Consequences: comparing in screen pixels needs the spec to add the parent's offset to each bar's, and to know where the lives row should be (`Touch.blocks(Hud.layout(W, H, inset)).lives`, already a real module the harness can require). The stub `UDim2.fromOffset` keeps `{x, y}`, so the sum is plain arithmetic. A re-lay on a screen-size change (the render step with a new `ViewportSize`) is the other path through `lay`, and should move both frames.
Recommendation: in `tests/place/hud-shots.spec.luau` (executor-owned), make `placed` return screen boxes (`Shots.Position + icon.Position`), and `want` add `Touch.blocks(layout).lives`'s `x`/`y` to `Hud.shotIcons(layout, lives, shots)`. Add a case that changes the stub viewport between two renders and checks the bars move with the lives row. Check that deleting `shots.Position = lives.Position`, deleting `lives.Position = …` and passing lives as 0 each turn it red. Since `shots.Size = lives.Size` only bounds the frame (`ClipsDescendants` is not set), either assert it equals the lives block's size or record why it doesn't matter.
