### F1 [medium] The adapter spec passes when the radar is placed after the snapshot guard, every frame, so the radar sits over the score until play starts
Where: tracker/issues/d0105/acceptance/adapter.spec.luau, case "each render step places the radar from Hud.radarBox of the screen"; d0105.md, Decisions made in prep ("Recompute only when `AbsoluteSize` changes") and the Rules and mutants row "Each render step, when the screen size changes, places the frame ..."
Evidence: on the prototype I removed the size-change block from the top of the `RenderStepped` callback and put `local view = gui.AbsoluteSize; local box = Hud.radarBox(view.X, view.Y, radarSize); radar.Position = UDim2.fromOffset(box.x, box.y)` back where `local view` was, after `if snap == nil or m == nil or pose == nil or snap.ghosts == nil then return end`. `bash tracker/issues/d0105/check.sh`: 4/4 PASS. The case checks only that the `RenderStepped:Connect`, the call and the assignment appear in that order and that `local view = gui.AbsoluteSize` exists somewhere. With this mutant the frame keeps its default `Position` (0, 0), so until the first snapshot and pose arrive, the 120-pixel black radar sits in the top-left over the score. After that it calls `Hud.layout` and allocates two tables on every frame, which is the cost the design's caching decision exists to avoid. The design states two rules: place before the guard (the patch does this, but the design never says so), and recompute only on a size change. Neither has a spec that can fail, and the Rules table has no row for the caching rule. It folds that rule into the placement row, whose spec does not check it.
Critique: the author will be tempted to add a source grep for `placedX`. That pins a variable name rather than the behaviour, and it still lets the call sit after the guard.
Consequences: an ordering assertion against the guard has to find the guard's position robustly. The first `return` after `RenderStepped:Connect` is the guard's `return` in the current file and in the patch. If the rule is kept, it becomes a one-time rule on the adapter's shape, and a later refactor that pulls the step body into a local function will trip it. That is acceptable for a source-shape spec, and f0033's adapter spec already works this way. Dropping the caching rule instead removes one rule and one row, but then the Scalability section must say that the radar is placed every frame.
Recommendation: in `adapter.spec`, assert that the `Hud.radarBox(` call comes before the first `return` after `RenderStepped:Connect` ("placed even before the first snapshot"). Either assert that an `if` comparing `view.X`/`view.Y` sits between the step and the call, or drop the caching decision and say in Scalability that one `layout` runs per frame. Add the matching rows to Rules and mutants: "placed before the snapshot guard", whose mutant is "placement after the guard", run; and the caching rule, if it is kept. Record both in E3. Rename the case and AC3 so they don't say "each render step" if the rule is "when the size changes".

### F3 [medium] E2 tests only "the chat", but the occluder the user saw in the top-right is unidentified, and Roblox's default chat window is top-left
Where: R0037.md Experiments phase E2; d0105.md Problem, Unknowns E2, Observed O1
Evidence: The docs say Roblox's chat covers the top-right radar. `TextChatService`'s `ChatWindowConfiguration` defaults to top-left alignment, and the game sets none (`rg` over src finds no `TextChatService`, `ChatWindow`, `SetCore` or `PlayerList`). Roblox's default top-right occupants are the player list, which is shown in live servers with other players, and the top-bar buttons. `DangerHud`'s `ScreenGui` has `IgnoreGuiInset = true`, and the old radar sat at y = 16, inside the top-bar inset row. O1 says "play a level with the chat open". If the real occluder was the player list or the top bar, O1 can pass in a solo Studio session, where the player list may not appear, without showing that it was the cause. The design does not decide whether the bottom-right must also be clear of the player list (top-right, so very likely clear) or of other default bottom-right CoreGui.
Critique: the move is very likely right whichever top-right element it was. The risk is the Observed step and the stop-and-ask fallback, which are keyed to the wrong element, so the record would claim a cause nobody confirmed. The author will be tempted to append "and the leaderboard" to O1 and stop there.
Consequences: naming the occluder shapes the fallback. If it was the player list, turning it off (`SetCoreGuiEnabled(PlayerList, false)`) is a different option that is not ruled out, and the adapter spec's chat-off word list would not catch it. Touch devices put the jump button in the bottom-right, but f0029 (mobile) is a non-goal, so that needs one line, not a design change.
Recommendation: reword the Problem and E2 to "a Roblox top-right CoreGui element (the user reported chat)". Make O1 run in a live Beta server with at least two players, with the chat window open and the player list shown, and check that the radar is fully visible. Keep the fallback (stop and ask), and extend it to any CoreGui toggle: add `SetCoreGuiEnabled` and `PlayerList` to the adapter spec's forbidden words. Add a Non-goals line that the touch jump button overlap belongs to f0029.
