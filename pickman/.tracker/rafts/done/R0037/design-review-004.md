### F1 [high] The radar can still miss the current screen or the pre-snapshot frame and pass AC3: the spec pins the call's spelling, not where `view` comes from or where the write lands (follows from review-003 F1's fix)
Where: tracker/issues/d0105/acceptance/adapter.spec.luau, case "places the radar from the current screen size on every render step, before the snapshot guard"; d0105.md Rules rows "placed before the snapshot guard", "placed on every render step, with no condition", "The call is `Hud.radarBox(view.X, view.Y, radarSize)`" (all `run`); E3; AC3 ("places the radar from Hud.radarBox of the current screen before a snapshot is required").
Evidence: on the prototype's `DangerHud`, each of these mutants reports `11 passed, 0 failed` for `adapter.spec` plus f0033 `adapters.spec`:
- MG: hoist `local view = gui.AbsoluteSize` to the line before `RenderStepped:Connect`. `Vector2` is a value, so `view` is the size at `start` and never changes. The radar and the arrows never follow a resize or a rotation, and if the ScreenGui is still 0×0 at `start` the radar sits off-screen at `{-127, -140}` for the whole session. - MH: `local view = Vector2.new(1920, 1080)` inside the step. The Rules row says the hardcoded 1920×1080 mutant is killed, but only when the literal is in the call. Put in `view`, it passes.
- MA: keep `local box = Hud.radarBox(...)` before the guard, and move `radar.Position = UDim2.fromOffset(box.x, box.y)` to just after the guard's `end`. The spec checks `call < ret` and `placeAt > call`, but not `placeAt < ret`. Until the first snapshot and pose arrive, the radar keeps its default `Position` (0, 0), top-left over the score. That is the case the "before the snapshot guard" row exists for.
- MI: add `radar.Position = UDim2.new(1, -(radarSize + 16), 0, 16)` after the guard. The radar is back in the top-right once play starts. The "old corner is gone" case looks only for the exact old literal.
Critique: this is the fourth round in which the hole sits in the same mechanism: separate string finds over `DangerHud`'s source, each checking one token's position. Every fix pins one more token and leaves the gaps between the tokens open. The tempting fix is to add three more finds: `local view = gui.AbsoluteSize` after `step`, `placeAt < ret`, and one `radar.Position`. That closes these four mutants, and the next gap (for example `view = Vector2.new(...)` reassigned between the read and the call) opens the next round.
Consequences: the design already gives the exact three lines and requires them at the start of the step. Pinning them as one contiguous block directly after `RenderStepped:Connect(function()` leaves no gaps between tokens: nothing can sit between the read and the call or between the call and the write, the read is inside the step, and all three lines come before any guard. The price is a spelling pin on three lines. Renaming `box` or `view`, or reordering the lines, fails the spec. That is acceptable here: the executor applies the patch verbatim, stylua leaves these lines unchanged (checked), and any later change to the placement would need a new decision anyway. With the block pinned, the `if` frontier assertion is redundant but harmless. A fake-engine run stays ruled out (review-002).
Recommendation: in the placement case, replace the separate `call`, `placeAt` and `if` finds with one plain find of the contiguous block:
`"RenderStepped:Connect(function()\n\t\tlocal view = gui.AbsoluteSize\n\t\tlocal box = Hud.radarBox(view.X, view.Y, radarSize)\n\t\tradar.Position = UDim2.fromOffset(box.x, box.y)\n"`
on the comment-stripped source. Also assert that the source contains exactly one `radar.Position` (MI) and exactly one `local view` (no second binding of `view` later in the step). Keep the "old corner is gone" and anchor assertions as they are. Update the documents to match:
