# R0044: Hiscores remember top ten

## Theme
A single defect: the hiscores look as if they forget. They do not: every board holds one row per player (R0011's prep decision 2), so a player alone is always all-time #1 and the lobby shows one row. The user chose to keep the per-player bests and add one all-time list of the ten best runs.

Decisions this raft relies on (`tracker/game-design.md`):
> Hiscores: A **global all-time top N**, plus **daily** and **weekly** boards. No personal-best feature for now (as it read before this raft; d0124 adds the exception below).
> **Submission:** only the server submits, from its own simulated result, at game over. Clients never send scores.
> **Storage:** behind a Logic-facing interface. A fake store is used in tests, and Roblox's ordered store in the adapter.

The user's decisions for d0124 (2026-10-21), recorded in its Problem and now also in `tracker/game-design.md` (Hiscores):
> "Keep player best and a global list of top-10, so the number of rows is (10+n_players) in total"
> Today and this week: "Only all-time". Game over outside the top 10: "Only within the top 10". The lobby: "Top-10 runs plus 'your best'". Old rows: "Keep them as entries".

The "your best" line is the one exception to "No personal-best feature for now", by that decision; game-design.md says so.

## Risks & rollback
- **A global key under load** (d0124 E2): within documented limits by three orders of magnitude. If Beta shows throttling, skip the update for a score below a cached tenth place (the list only rises).
- **Old rows and mixed builds** (design review 001 F1): every list write merges the per-player bests `drive` just read, so the old rows, and every best written later by a build or server without the list, join it on the next run. With no list and an unreadable board, no list is made and that run hears nothing; the next run tries again.
- **Known limits** (design review 004 F2): the list learns of a run only from its own list write or, later, as its player's per-player best. So a run that is not its player's best is never listed if its list write fails for good (three tries), or if it was played on a build without the list. And an unnamed best written by such a build is dated 0, so on an exact tie of score and level it takes an earlier run's place. Both are rare (a failed write after retries, or an old build, and the second also needs an exact tie at the tenth place). The user accepted this limit on 2026-10-21 (d0124's Problem); a per-server retry set of unlisted runs was the option not taken.
- **A client firing the Board remote** (design review 001 F2): the per-player best read has an in-flight marker and is dropped after a leave, so a burst costs one read per player per 15 s.
- **Rollback**: revert the PR. The `HiscoreTop` key is then unused, and the per-player boards are as they were, because they keep their rules; their rows also carry `run` and `at`, which the code before this raft ignores. A later re-land merges the bests written meanwhile, each from its companion row.
- **Lessons that changed this design** (the lessons pass): prove-specs-pass-on-a-prototype (a prototype, the full gate and the mutation check, now 61 mutants run, which found weak spots in each round), pin-call-site-arguments (the job id, clock and run counter are pinned through the adapter), never-narrow-captured-scope (every narrowing is a user `Scope decision` line), new-rules-migrate-existing-work (old per-player rows, and rows written by older builds after the list exists, are merged on every write; design review 001 F1 sharpened this), specify-every-named-artifact (the stored value's schema and example), and from round 2 the new lesson zz-arch/one-id-per-thing (a run keeps one id from every source, and a best is its companion row whole).
