### F1 [high] The list is seeded once, so every run written by a build without the list after the seed is never on it: the "no memory" defect comes back on Beta's normal deploy flow
Where: d0124 Design, "Decisions made in prep" (first bullet) and the `driveTop` paragraph ("on nil with no seed yet …"); R0044 Risks & rollback ("Old rows", "Rollback").
Evidence: the seed runs only when `HiscoreTop/all/runs` is nil. Beta is "last one wins" per ready PR (`tracker/game-design.md`, Deploy; `.github/workflows/check.yml` publishes each ready PR's merge commit with main), and a publish does not shut down running servers (nothing in `.github` or `scripts` migrates them). Sequence: R0044's PR is ready and published; the user plays O1, which creates the list. Another PR, not containing R0044 (it has not merged), becomes ready and is published. The user scores 900 on that build: `drive` writes it to the per-player boards, nothing writes the list. R0044 is published again (merged, or its PR updated). The list exists, so it is never seeded again: the lobby's all-time panel shows ten runs without the 900, and "YOUR BEST 900 …" under it. The same happens for every run on an old game server still running after a publish, and after the documented rollback then re-land (the stale `HiscoreTop` key is "unused", then read again as if current).
Critique: the user's report was that scores are not remembered, and the scope decision "Keep them as entries" says stored rows start the list. Rows stored after the one seed are stored rows too, and they are lost for good: the list only ever grows from new-build runs. The tempting fix is a Risks line ("old servers may miss the list"), which leaves the wrong result in place on the exact Beta the user plays.
Consequences: making the list absorb per-player bests continuously needs (a) a read of the per-player all-time board on every run, not only the first, (b) a dedupe rule so that a run that is also the player's new best is not listed twice (the reason the design writes the list first), and (c) seed ids that change with the best (`best:<userId>` with "the stored copy wins" would keep a stale old best and refuse the newer one).
Recommendation: merge the per-player bests into the list on every write. One shape that holds: run `drive` first and hand its tail `readAll` rows (read today and thrown away, Non-goals) to `driveTop`; the transform adds the run, then adds each per-player best row as `best:<userId>:<score>:<level>` at 0 unless the list already holds an entry of that user scoring at least as much (this drops the run's own new best, and a raised best replaces nothing wrongly because the older `best:` entry is a real older run). That reverses "write the list before the per-player boards" and removes `needSeed` and the second try. Spec cases: a stored list missing a player's higher per-player best gains it on the next run of anyone; a first run that is a new best is listed once; a raised best of a player whose older `best:` entry is listed is added beside it; a failed `readAll` still writes the run (the list must not depend on that read once it exists). If the author keeps the one-time seed instead, that is a narrowing of "each submitted score persists": escalate to the user: (1) merge continuously as above (one more read per run only if `drive`'s read is not reused); (2) seed once and accept that runs on builds without the list are never listed, documented in Risks and O1/O2.
Lesson: ticket-prep/new-rules-migrate-existing-work

### F2 [high] A client can make the lobby server issue unbounded DataStore reads: the per-player best has no in-flight guard
Where: d0124 Design, Boards bullet (`bestOf` "on every `"all"` request, before `lookup`"); AC5 ("read at most once per CACHE_TTL per player"); Scalability ("state is per player present, cleared on leave"); prototype `src/lobby/server/Boards.luau` `bestOf`.
Evidence: `bests[userId]` is set only after `GetAsync` returns. Every `"all"` request that arrives while that read is in flight finds nothing fresh and starts another read. Probe on the prototype (a copy of `adapters.spec`'s world whose `GetAsync` for key `7` yields): five requests from one player in flight give `reads in flight: 5`. A client firing the Board remote in a burst gets one `GetAsync` per event until the first returns, then again every 15 s. Before this raft the lobby kept nothing per player and every read was shared per board key (the Boards header says so), so a client could not drive the lobby's read budget; now one client can exhaust it (60 + 10 per player per minute) and make every player's board read fail. The same probe shows the leave race: the player leaves while the read is in flight, the read then stores `bests["7"]`, and the entry outlives the player (a rejoin within 15 s answered the old best 80 instead of 95). The prototype's header comment still says "Nothing is kept per player".
Critique: this is a client-driven authority hole on a server budget, and the AC5 wording is met only for sequential requests, which is all the synchronous stub can model. The tempting fix (a per-player debounce on the remote) adds a second rate rule beside `CACHE_TTL`.
Consequences: marking the read in flight means a concurrent request answers without the fresh best (nil, or the last held one) while the first read runs; storing only for a present player needs the same check `answer` makes (`player.Parent ~= nil`).
Recommendation: before the `GetAsync`, store `bests[userId] = { at = now, best = held and held.best }` (the in-flight marker is a fresh entry), and after it write the result only when `player.Parent ~= nil` and the entry is still the one this read made. Update the Boards header comment. Spec cases in `adapters.spec`, with the stub's `GetAsync` able to yield for one key: several all-time requests while one best read is in flight make exactly one read and every one is answered; a player who leaves during the read leaves no entry (a rejoin within `CACHE_TTL` reads again and answers the new best). Add both rows to Rules and mutants (mutants: no in-flight marker; store after leave).

### F3 [low] Rules and mutants misses rows, and two plausible mutants survive
Where: d0124 Rules and mutants; Design (`driveTop`, `Hiscores.best`, Boards).
Evidence: run on the prototype, each restored after: `Hiscores.best` without `companion.score < 0` (accepts a negative score) passes all 58 cases; `driveTop` with `if run == nil then` instead of `not validRun(run)` passes all 58. Both are stated in the Design ("whole score >= 0"; "an invalid or nil run is `{ known = false }`, with no call"). Rules with cases but no row: "the seed is read once, and a failed seeded write retries with the same seed" (`drivetop :: the board is read once …`), "the seed's companion reads spend `get`" (`drivetop :: a seed read spends …`), "a best that cannot be read is no best" (`adapters :: a best that cannot be read …`). Both survivors are masked at the system level (`Lobby.bestLine` refuses a negative score; `topRun` only makes valid runs), hence low.
Critique: the table claims every behavioural rule; an executor that departs from the patch re-runs only `mutants.py`, which has no mutant for these.
Consequences: none.
Recommendation: add the three rows with their mutants (`seed-every-attempt`, `seed-skips-budget`, `best-error-keeps-garbage`), add `H.best({ score = -5, level = 1 })` → nil to `top :: a player's best …` and an invalid TopRun table to `drivetop :: no entry …` (expect `{ known = false }` and no `update` call), and add those two mutants to `mutants.py`.

### F4 [low] The place is heard only after the per-player write, though it is known before it
Where: d0124 Design, HiscoreStore bullet ("runs … `driveTop` …, then `Hiscores.drive` … as today, then calls `listener`"); prototype `HiscoreStore.submit`.
Evidence: `placed` is final when `driveTop` returns, but the listener waits for `drive`'s six updates and its all-time page and up to ten companion reads, whose rank is discarded. The overlay returns to the lobby on a tap (f0065), so a quick tap misses a place that was ready seconds earlier.
Critique: not a regression (today's rank also waits for `drive`), but it is free usability.
Consequences: if F1 is fixed by running `drive` first, this finding falls away; otherwise the listener fires before `drive`, and `pending` must still cover the rest of the thread (it does: it is decremented at the thread's end).
Recommendation: if the list is still written first, call the listener between `driveTop` and `drive`, with an `adapters.spec` case that the place is heard before the first `update:HiscoreEntries` (log order).

Verdict: changes
