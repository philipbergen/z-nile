### F1 [high] A per-player row joins one run's id and instant (companion) to another write's score (ordered store), and "the stored copy wins" makes the wrong score permanent (a hole in the mechanism design-review-002 F1 fixed)
Where: d0124 Design, "A run has one id from every source" and Files and API (`rows` carries `run` and `at` from the companion, `bestRun`); prototype `Hiscores.rows` (`score = entry.score`, the ordered store's value; `level`, `run`, `at` from the companion), `driveBoard` (companion `UpdateAsync` first, ordered `UpdateAsync` second, retried separately), `HiscoreStore` `io.get` (plain `GetAsync`, cached up to 4 s per server).
Evidence: a row is assembled from two stores written by two separate updates, so it is not one record:
(a) P's run Y (600, level 4) has written its companion (named Y) but not yet its ordered value (still X's 500): the normal gap between drive's two updates, or for good when the ordered update runs out of retries or budget. Another server's `readAll` in that window gets `{ score = 500, level = 4, run = Y, at = Y's }`. Probe on the prototype: Q's list write merges it, then P's own write finds Y stored, the stored copy wins, and the list is `jobB=550`, `Y=500`; P hears place 2 instead of 1, and the lobby shows Ada 500 for good.
(b) The other way round: Q's server read P's companion within the last 4 s (`GetAsync` caches per server), P's ordered value is now Y's 600, so Q's row is `{ score = 600, run = X, at = X's }`. When X is not on the list (cut, or its list write failed), X's id is listed at 600 beside Y's 600: one player's one score twice, under a real run's id.
Before round 2 the same mixed row was a separate `best:` entry; now it carries a real run's id, so it corrupts that run's own entry. No case can catch it: every fixture's row has one score.
Critique: the tempting fix, naming the row only when its companion score equals the ordered score, still leaves the unnamed fallback building `best:<userId>:<orderedScore>:<companionLevel>`, a score and level no run had (old builds have the same two-update window).
Consequences: whatever the merge uses must come from one atomic write. The companion is that write (name, user, score, level, run, at in one `UpdateAsync`); the ordered store only decides which players are on the page. `Row.score` stays the ordered value, because f0024's ranking and the lobby fallback use it, so the best needs the companion's own score beside it.
Recommendation: question the mechanism, not this race: a best is the companion row, whole. `Hiscores.rows` carries the companion's own score (e.g. `Row.runScore`, set only when it is whole and >= 0) beside `run` and `at`; `bestRun` takes id, instant, score and level from the companion (the unnamed fallback included, `best:<userId>:<companion score>:<level>`), and `mergeRun` skips a row without a valid companion score. Spec cases: `top` "a row whose ordered score lags its companion merges as the companion's run and score" and "a row whose companion is older than its ordered score merges as that older run at its own score"; `drivetop` "another server merged this run's best from a half-written row: the run is listed once at its own score"; `adapters` "a run whose ordered write fails is listed at its own score by the next run" (the stub already has `failUpdate` per store). Mutant: best-uses-ordered-score. Run `scripts/affected` and the text greps for the `Row` change, and add any promoted case it turns red to the Overrides and c0128. Rows and mutants table: one row for "a best is its companion".
Lesson: architecture/one-id-per-thing (an id is only one thing's if every field that travels with it comes from the same write)

### F2 [medium] The cover rule now hides real runs: a later run that ties (or a listed better run of the player) stops an older, unlisted run from being merged, against "the earlier run keeps a tied place"
Where: d0124 Design, "Merge the per-player bests on every write" ("adds each of those bests that no listed run of its player covers"), Rules and mutants row "A best covered by a listed run of its player (score, then level) is not added"; prototype `covered`, `mergeRun`.
Evidence: cover was round 1's way to stop the run's own best being listed twice. Since round 2 the run's own row names it, so the id dedupe does that, and cover only changes the result where it is wrong. P's run X (50, level 1, at 600) wrote its named row, but its list write ran out of retries; the merge on a later run is what recovers it. If P's next run Y ties it (50, 1, at 800), the row stays X (a tie never replaces) and Y covers it. Probe on the prototype (nine runs of 50/1 earlier than 600 and one at 700): the result is unchanged with X absent and Y missed, though X at 600 is tenth by the stated tie rule. The same happens when a listed run of P scores more than P's row (that run's per-player write failed): every older best of P is then covered for good. Removing `covered` (a temporary edit, since restored) turns seven d0124 cases red, but each of them models the run's own best, or a listed run, as an unnamed row with the same score. The adapter never writes that state: every run's row names it.
Critique: the tempting fix is to change the rule from `>=` to `>`. A strictly better listed run still hides a real older run, and the fixtures still model a state that cannot happen.
Consequences: a merge with no cover must still list each run once. Named bests dedupe by id (stored copy first). Unnamed `best:` ids are deterministic, so re-merging them is idempotent. An unnamed row next to a listed run of the same score and level is two runs (an old build's row is never replaced by a tie), so both belong on the list.
Recommendation: drop `covered`: a best is added unless its id is already there (with F1, from its companion). Rewrite the fixtures that stand for the run's own best as rows naming the run's id (`drivetop` "a run that is the player's new best is listed once", "a lower second run …", "a run below a full list …", "a best stored without the list …", "another server merged …"; `top` "a best that the run itself … covers"; `adapters` "the place heard …", where Cy's row names the stored 990 run). Add `top` "an older unlisted best that a later run ties is listed ahead of it" and "a better listed run of the player does not hide an older best". Replace the rows and mutants merge-ignores-cover, cover-ignores-level and cover-any-run-of-player with cover-by-value (any value-based skip) and no-id-dedupe-on-bests.
Lesson: architecture/one-id-per-thing (cover is a value-derived identity)
