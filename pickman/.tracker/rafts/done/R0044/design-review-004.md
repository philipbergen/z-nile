### F1 [medium] "The transform records the place from its last call" has no case: the stubs call the transform once, so a transform that keeps an earlier call's place or `blind` passes every case
Where: d0124 Design, `driveTop` paragraph ("The transform records the place from its last call") and E1 ("The function will be called as many times as needed until the data is saved"). Prototype `Hiscores.driveTop`'s `transform` (`place = nil` at its start, `blind` recomputed). The `topIo` stub in `drivetop.spec.luau` (line 28) and the store stub in `adapters.spec.luau` (line 260) each call `transform` exactly once per `update`.
Evidence: I edited the prototype temporarily (since restored): I removed `place = nil` from the start of the transform and changed `place = at` to `place = place or at`. All 78 d0124 cases still pass. Under that mutant, suppose `UpdateAsync` first runs the transform on a value in which the run places 9th, and another server's write then makes it re-run on a list where the run is cut. The cut list is returned (or nil when the ids are unchanged), and the player hears "ALL-TIME #9" for a run that is not on the list. The same holds for a `blind` that stays true once set (`blind = blind or …`): a first call on nil with nil bests, then a re-run on a list another server just created, writes the run but says nothing. E1 records the re-run as documented engine behaviour, so this is the case the rule exists for. Nothing in the Rules and mutants table pins it.
Critique: this is an acceptance hole: a wrong implementation passes `check.sh`. The tempting fix is to add one sentence to the Design, which the executor already follows on the patch and which a departure from the patch would not keep.
Consequences: the stub needs a mode that models the engine's re-run. The first call sees a stale value, its result is discarded, and the second call sees the current one. That mode must not change the existing cases, and `adapters.spec`'s store stub can keep its single call.
Recommendation: give `drivetop.spec`'s `topIo` a `rerun` value: when it is set, `update` calls `transform(rerun)` first, throws that result away, then calls `transform(top.held)` and stores the second result. Add these cases:
- "a run placed on a stale value and cut on the re-run is heard as missed N", where the second call's list is full of higher runs;
- "a run missed on a stale value and placed on the re-run is heard at its place";
- "no list and no bests on the first call, and a list on the re-run: the run is written and its place heard".
Add a row "The place and the no-list state are the transform's last call's" with the mutants place-kept-across-calls and blind-sticky, add both mutants to `mutants.py`, and record the run in E6.
Lesson: ticket-prep/spec-design-correspondence (a stated rule, here an engine behaviour from E1, with no case that fails without it)

### F2 [low] The documents do not state which top-10 runs can still be missing from the list, and they call every unnamed best "older than the list", which is wrong for rows that builds without the list write later
Where: d0124 Design, "Ties" ("An unnamed best is at 0, which is right because it is older than the list") and "Merge the per-player bests on every write". R0044 Risks ("Old rows and mixed builds", "Rollback"). Scope decision line 21 ("every run that makes the all-time top 10 stays on that list").
Evidence: (a) A run that is not its player's best never reaches the list once its own list write fails, whether retries or budget run out or the server closes first. Only the companion row is re-offered, and that holds the player's best. The same applies to every non-best run played on a build without the list: another PR's Beta build before R0044 merges, an old server still running after a publish, or a rollback window. The design is right not to invent those runs, but Risks says only that bests "join it", so a reader of line 21 expects more than the design delivers. (b) An unnamed row written by a build without the list after the list exists is newer than listed runs, yet it is dated 0. On an exact score-and-level tie at the boundary it takes the place of an earlier listed run. The order is deterministic, so this does not churn, but the stated reason is false for exactly the writers that the merge bullet names.
Critique: neither is a wrong result under the design's own rules. Today's per-player write also loses a run whose updates run out of retries (f0024). But the user's scope sentence promises more than the design delivers, and the user should be able to see the gap. The tempting fix is to quietly reword line 21, which would rewrite a user decision.
Consequences: (a) can only be closed by the server keeping its failed list entries, for example a per-server set of up to N entries merged into its next list write and lost when the server closes. That is new state and new cases, and it is the user's call, not a cut. (b) has no fix without an instant on old rows, which old builds do not write.
Recommendation: in R0044 Risks, state (a) as a residual limit: a run whose list write fails is listed later only if it is still its player's best, and non-best runs on builds without the list are never listed. Name the per-server retry set as the option if the user wants failed runs recovered. In d0124's Ties line, say that a row from a build without the list is dated 0 because it has no instant, so on an exact tie it can be placed ahead of an earlier run. Leave line 21 as the user wrote it.
Lesson: ticket-prep/new-rules-migrate-existing-work (writers that keep producing the old shape after the change)
