### F1 [high] AC3's "HudView draws a Fire and Hop frame" passes when the buttons are never on screen
Where: `acceptance/adapters.spec.luau` `hudView().frame` (lines 331-338) and the case "HudView draws a non-active Fire and Hop frame…"; f0110 Rules and mutants (no row for parenting, colour or transparency).
Evidence: `frame(name)` searches the list of every `Instance.new` result (`made`), not the HUD's tree. On the prototype I replaced `f.Parent = parent` in HudView's `button()` with a comment: `adapters.spec`, f0029's specs, `tests/place/hud-shots` and `tests/place/touch-adapters` all pass (55 passed, 0 failed). The phone would show no buttons, and a tap there would still fire, unseen. Separately, `f.BackgroundTransparency = 1` (invisible discs) with the Fire frame `WHITE` instead of `CYAN` also passes (14 passed). The Design names the colours, the transparency, the disc corner and the caption's text size (lesson `specify-every-named-artifact`), but no case reads any of them, and the stub already records `Color3.fromRGB` as `{r, g, b}` and `UDim.new` as `{s, o}`. So the proxy is free.
Critique: AC3 says "HudView draws". A wrong implementation that draws nothing passes it, and OC1 is the only thing left to catch it. The tempting fix is one `t.expect(f.Parent ~= nil)`, but that still passes a frame parented to a second ScreenGui that has the default insets (drawn offset by the top bar, so the drawn button and the hit-tested rectangle disagree).
Consequences: the helper has to find the HUD's ScreenGui. The stub's `WaitForChild("PlayerGui")` returns a fresh instance on each call, so the spec should take the `ScreenGui` named `Hud` from `made` (asserting there is exactly one) and walk down from it. The spec stays within the zz-test rules: it is sequestered and nothing is promoted yet.
Recommendation: change `frame(name)` to look among the children of the one `Hud` ScreenGui (whose `ScreenInsets` the existing code sets to `None`). In the draw case, assert Fire's `BackgroundColor3` is `{r=0,g=255,b=255}` and Hop's is `{r=255,g=255,b=255}`, `BackgroundTransparency` is `0.6`, each has one `UICorner` child with `CornerRadius` `{s=0.5,o=0}`, and the caption's `TextSize` is `Hud.layout(...).textSize`. Add Rules-and-mutants rows for "unparented", "transparent", "colours swapped" and "caption size unset", run them on the prototype, and record the results in E4.
Lesson: z-design/spec-design-correspondence

### F2 [medium] game-design.md records the prep's choices as user decisions, and the Design never weighs the cost of finger-down fire
Where: game-design.md, Mobile, the new "Fire and hop" bullet; f0110 Usability; R0051 Risks & rollback.
Evidence: the capture asks for "a fire control … and a jump gesture or button". The bullet puts these before its **(prep)** marker, which the file's header reads as decided by the user: the choice of a button over a gesture, the cyan and white colours, the FIRE and JUMP captions, "act when the finger goes down, once", and "a finger on them never looks or turns". None of these came from the user. The finger-down rule has a real cost for a phone player, and the Usability section doesn't mention it. Look is "drag on the right half", and in landscape (844×390) FIRE covers {670..740, 258..328}, the lower-right area where the right thumb starts look drags. A drag that starts there spends a shot (at most 3 held, 50% drop chance) and doesn't look at all. The alternative, firing when a short tap lifts, delays the shot by the tap's length, and the blaster's own note already asks for a press "about half a tile before the junction's centre".
Critique: the user can veto only what is marked as theirs to veto. The tempting fix is to move the **(prep)** marker and stop there, which still leaves the accidental-fire cost unstated, so the user can't judge the choice.
Consequences: none for the code or the specs (the behaviour stays finger-down). It adds one sentence to Usability and to Risks, and a veto point for the user.
Recommendation: start the bullet with only what the capture says ("touch has a fire control, aimed as on desktop, and a jump button"), and mark everything else **(prep)**. Add the trade-off to f0110 Usability and R0051 Risks: finger-down fire is instant, but a look drag that starts on FIRE wastes a shot; fire-on-lift avoids that but costs the tap's duration. State that the prep chose finger-down for the timing.

### F3 [medium] FIRE's cyan is the colour game-design.md says this user sees as white
Where: f0110 Design, HudView (`Fire` cyan `(0, 255, 255)`, `Hop` white); game-design.md, Open decisions, "Inky's colour (f0109)".
Evidence: Open decisions says "`(0, 255, 255)`, which the user sees as white". So for this user the corner holds three translucent near-white discs side by side: Snap (white, 44 px, no caption), JUMP (white, 70 px) and FIRE (cyan, 70 px). The Design's claim that "the captions say what each does" is then the only cue telling apart two discs one margin apart. That is weak at the HUD's text size on a 70 px disc, under the thumb.
Critique: the colour is a named artifact and a product choice, and the evidence against it is already in the decisions file. The tempting fix is to pick a new colour for the button alone, which breaks the Design's own link (the button matches the shot bars and the beam) and leaves two colours to keep in step when f0109 picks a new cyan.
Consequences: if the button's colour follows the shot bars' constant, f0109's later choice moves the bars, the beam and the button together. That turns f0109 into a decision about the button as well, which its Open decisions entry should then say.
Recommendation: draw FIRE from HudView's existing `CYAN` constant (one source with the shot bars). Add to the Open decisions entry for Inky's colour (f0109) that the FIRE button and the shot bars share that cyan and will follow the new colour, and mark the colour pairing **(prep)** (with F2). Make the JUMP/FIRE distinction not depend on colour alone, for example a caption at full opacity with an outline. Pin the colours in the spec (F1).

### F5 [low] Off the samples, the hop button touches the snap control and the power bar
Where: f0110 Design, "On every sample both buttons … miss each other, the snap control, the four HUD blocks"; `buttons.spec` SAMPLES.
Evidence: from the prototype's `Touch.buttons(Hud.layout(w, h))`: on 320×568 portrait (a real device size in points: iPhone SE 1st gen, iPod touch), hop {225, 478, 70, 70} and snap {182, 517, 44, 44} share column 225, rows 517 to 548. On 500×900 and 900×500, hop's bottom row 879 lies in the power bar {363/663, 879, 125/225, 9}. Where hop and snap share a pixel, snap wins, so a tap there snaps the look. These are 1 px overlaps that follow from f0029's geometry (Roblox's own jump button would sit in the same place), but this feature makes them visible and tappable.
Critique: the claim reads as general but is checked only on the samples. The tempting fix is to nudge the hop button, which gives up the Design's premise that it sits exactly where Roblox's jump button is.
Consequences: accepting and pinning these overlaps (as was done for the radar) adds one sample row and one sentence to game-design.md's (prep) text.
Recommendation: add 320×568 portrait to SAMPLES. Either pin its 1 px snap overlap (a `snapOverlap` field, like `radarOverlap`), or scope the Design's sentence to the samples and name 320×568 and 500×900 as known 1 px touches.
