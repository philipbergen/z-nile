### F1 [high] AC3's "Camera looks with the right stick" passes with a camera that never applies the stick
Where: `pickman/src/client/Camera.luau:108-115`; f0146 `acceptance/place.spec.luau` case "Camera reads Thumbstick2 through Pads.stick and applies Pad.look through View.look before View.steer" (the only check of the Camera's stick)
Evidence: the Camera's right-stick look is checked only as source text, and no spec runs Camera's render step. In the clone, each of these mutants passed all 30 cases (`lune run tests/run -- <the six specs>`: `30 passed, 0 failed, 6 spec files`):
- E: `look = View.look(look, Pad.look(x, y, dt))` → `local _ = View.look(look, Pad.look(x, y, dt))` (the stick's look computed and thrown away: the right stick does nothing);
- F: `if x and y then` → `if x and y and cursor then` (the stick looks only while the game-over cursor is free, never in play).
Both keep every pinned needle (`"Thumbstick2"`, `Pad.look(x, y, dt)`, `View.look(look, Pad.look(` before `View.steer(`), which is the defect zz-test's lesson names: a mutant that keeps every pinned call but ignores its result still passes. "Right stick looks around" is one of the four outcomes the user captured, so a Checked criterion for it can be passed by a wrong implementation.
Critique: the tempting fix is another needle (say, `look = View.look(`), which the next "assigned, then overwritten" or "gated" mutant passes again.
Consequences: a running case needs the render-step callback, `dt`, a snapshot (the pose is computed only after `latest` exists) and `CFrame`/`workspace.CurrentCamera` stand-ins; it must not depend on the stub's frame timing (`os.clock`), and it must stay open to later requires (pickman-test lesson stub-loaders-fall-back), since f0110 and f0126 change these adapters too.
Recommendation: an executor-owned spec (for example `tests/place/camera-pad.spec.luau`, not the sequestered ones) that loads Camera's real source on a stub engine as `touch-adapters.spec.luau` loads Controls: capture the `BindToRenderStep` callback, `Camera.pad` a stand-in for `Pads.stick`, `Camera.push` one snapshot, and read `Camera.pose().yaw` and `Camera.aim()` after render steps. Cases: the stick at (1, 0) for 0.5 s of steps turns the yaw by `-Pad.LOOK_YAW·0.5` (right) and stays there when released (not sprung back); (0, 1) raises the pitch (through a `CFrame.Angles` stand-in that records its arguments, or through a pitch read the case can see); a stick read of `nil, nil` and a stick inside `LOOK_DEAD` leave the look unchanged; the look applies with the cursor locked (play) as well as free; after a stick look to the right, `Camera.aim()` returns the heading to the right (R2 fires where the player looks). Each case must fail on mutants E and F.
Lesson: zz-test/source-pins-name-what-the-design-names

### F2 [high] AC4's LobbyPad passes with the selection logic wrong in four ways
Where: `pickman/src/lobby/client/LobbyPad.luau:12-29`; f0146 `acceptance/place.spec.luau` case "the lobby's Main boots LobbyPad after LobbyView; LobbyPad selects Start for a gamepad only, when nothing is selected" (needle checks only)
Evidence: no spec runs LobbyPad. In the clone each of these passed all 30 cases:
- B: `Pad.isPad(inputType.Name) and GuiService.SelectedObject == nil` → `... or ...` (a mouse or keyboard player gets Start selected, and a gamepad press steals any selection back to Start);
- C: the first `choose(UserInputService:GetLastInputType())` removed (a console player who joins with the pad as the last input gets no selection until the input type changes, so START GAME can't be pressed);
- D: the `GetPropertyChangedSignal("SelectedObject")` handler's body replaced by `local _ = UserInputService:GetLastInputType()` (ButtonB clears the selection and nothing re-selects: the case design review 001 F6 added, and the Rules row P22 says is killed);
- H: the selected object changed to a different lookup that still contains `FindFirstChild("Start", true)`.
LobbyPad's `choose` is the adapter branching rule 3 of pickman-arch puts in Logic or under a running case ("any branching an adapter does that could be wrong"), and the place.spec header itself leaves "the polls" to review. AC4 ("puts Roblox's gamepad selection on START GAME when a controller is the last input") can be passed by C, which does exactly not that at start.
Critique: the tempting fix is more needles (a count of `choose(` calls), which B and D keep passing.
Consequences: a running case needs `GuiService.SelectedObject` as a settable property whose change fires `GetPropertyChangedSignal("SelectedObject")` (and only on a real change, as Roblox does, or the stub loops), `GetLastInputType`, `LastInputTypeChanged` and a PlayerGui holding LobbyView's `Start`; extending `tests/lib/fakeengine.luau` for this must not make it accept less or more than it does for the existing lobby specs (pickman-test skill). Moving the decision into Logic (`Pad.selects(lastInput, hasSelection)`) would add a public function to Pad, a design change the executor can't make alone.
Recommendation: an executor-owned spec running LobbyPad's real source after LobbyView's (fakeengine, which already boots the lobby's adapters, extended with the members above). Cases: a gamepad as the last input at start selects `Start`; a keyboard or mouse as the last input selects nothing; `LastInputTypeChanged` to `Gamepad2` with nothing selected selects `Start`; an existing selection (a board tab) is kept on a gamepad input; the selection cleared while a gamepad is the last input is set back to `Start`; cleared while the mouse is the last input stays nil. Each must fail on B, C, D and H.
Lesson: zz-test/source-pins-name-what-the-design-names

### F3 [medium] Sticks carries an engaged sector across a disconnect, so the next controller's first push that way is swallowed
Where: `pickman/src/client/Sticks.luau:17-21` (`if x == nil or y == nil then return end` keeps `steer`); `pickman/src/client/Pads.luau` (the driver changes without Sticks knowing)
Evidence: a scratch spec in the clone (controls.spec's own stub world, boot3, beat): Gamepad1's stick pushed left (`Left` sent), Gamepad1 disconnected (one Heartbeat reads nil), Gamepad2 connected and its stick pushed left (it takes over at a tilt of 0.4 and Sticks first reads it at 0.9). Expected `{ "Left", "Left" }`; got `{ "Left" }`: `FAIL tests/scratch/stale.spec.luau :: same, but the new pad's first read is already pushed`. (A first variant that pressed Gamepad2's ButtonA before the push failed the same way only because no Heartbeat read the pad at rest in between, so it is not cited.) The fold's `held = "Left"` survived the nil reads, so the new pad's push is "held, same sector": no intent. A gradual push fails the same way, because Pads hands over at a tilt of 0.4 and an engaged fold between `STEER_OFF` and `STEER_ON` never emits: a third scratch case with both pads connected (Gamepad1 still pushed left, Gamepad2's stick taking over at -0.45, then -0.9) also got `{ "Left" }` (`FAIL ... :: two connected pads: Gamepad1 still pushed left, Gamepad2's stick takes over pushed left`; `0 passed, 3 failed`). A lone wireless pad that drops mid-push and comes back as another `GamepadN` is the disconnect case. The player's turn is lost (a missed junction), recoverable only by releasing and pushing again. Nothing pins the fold across a change of source.
Critique: the tempting fix is `steer = Pad.steerStart()` on a nil read only; that covers the disconnect but not a switch between two connected pads (Gamepad1 still pushed while Gamepad2's stick takes over), where the reading never goes nil.
Consequences: Sticks needs to know which controller it read: `Pads.stick` returning the driver as a third value, or a `Pads.driver()`; the reset must not emit by itself (a fresh fold engages only at `STEER_ON`, so a new pad held at 0.5 sends nothing until 0.6, which is the normal engage rule), and the Camera's look keeps no such state, so it needs nothing.
Recommendation: Sticks resets its fold (`Pad.steerStart()`) whenever the read is nil and whenever the driving controller differs from the one it last read. Executor-owned stub cases (in the style of controls.spec): disconnect mid-push, then the other pad pushed the same way sends the intent; two connected pads, Gamepad1 held left and Gamepad2's stick takes over pushed left, sends `Left` again; a reconnect of the same pad at rest sends nothing.

### F4 [low] Pad.track lets an infinite magnitude take over, against the Design, and Pads' magnitude rule is unpinned
Where: `pickman/src/shared/Logic/Pad/init.luau:46-51`; `pickman/src/client/Pads.luau:14-23`
Evidence: the Design (§1, `Pad.track`): "a key, a touch, a non-finite magnitude or a lesser tilt keeps the one before". `magnitude == magnitude and magnitude >= Pad.STEER_OFF` refuses NaN but accepts `math.huge`; pad.spec's track case tests only `0 / 0`. Mutant G (the NaN check dropped, so the code checks nothing non-finite at all) passed all 30 cases. In Pads, mutant A (`elseif begun then` → `else`: every non-stick `InputChanged` of a pad, such as a trigger's travel, counts as a full press) passed too; the Design's "InputChanged of a Thumbstick1 or Thumbstick2 (magnitude its tilt)" is held only by the code.
Critique: neither is reachable as a wrong result from Roblox today (a stick reports at most about 1.41, triggers change only when pressed), which is why low; but the rule written in the Design and the code disagree.
Consequences: none beyond the two cases.
Recommendation: use the module's own `finite(magnitude)` in `Pad.track`, with a unit case for `math.huge` and `-math.huge` in `tests/unit/Pad`; and a stub case that an `InputChanged` of a pad's `ButtonR2` (Position.Z 1) does not take over while a `ButtonR2` `InputBegan` does.
