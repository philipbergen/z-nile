## Open to the human
- F1: (final-review-001 F1 [high], which carries review-001 F2 [high]) a Studio play-test of the game place (Rojo, Play, with Studio API access on, which the hiscore boards need) takes the free start in `PaidPlayTest` on its first play. Every play in the next hour is then a "buy" arrival with no lobby pass, so its run is refused and the developer is kicked with "Start a game from the lobby.", because Studio cannot teleport. Before this raft every Studio play of the game place worked. OC1's Studio leg cannot run as written either, since Studio cannot teleport from the lobby to the game place. No gate sees it, because every send-back case runs in live mode. Answer: the finding is right, and every fix changes G10 ("any other 'buy' arrival (a direct join, a friend's server) is sent back"), so the executor did not pick one. The options:
  - (a) In test mode a "buy" arrival plays, or opens the test purchase screen in place. Cost: direct joins to the Beta game place play test games free and unbounded (test records only; nothing is charged either way).
  - (b) Only in Studio (`RunService:IsStudio()`) a "buy" arrival plays. Cost: one Studio-only branch in Continues, pinned by a case with a stubbed `IsStudio`. Live and Beta keep G10. Added by final review 001 F1: the sequestered adapters.spec stub's `RunService` has no `IsStudio`, so the read must be guarded (`pcall`, with an error or a missing method meaning "not Studio"). A bare call would turn its three live send-back cases red, which is an Override that sends f0145 back to prep. A second case of the executor's own pins the guarded read: with `IsStudio` absent or erroring, the live send-back holds.
  - (c) Keep it, and say in game-design.md and OC1 that a Studio play of the game place is kicked after its first game each hour while API access is on.

  Each of (a) and (b) leaves every sequestered case green, since those cases run in live mode, and needs one new case of the executor's own: a test-mode (or Studio) "buy" arrival whose teleport fails plays and is not kicked. The executor's recommendation is (b): it keeps the user's G10 everywhere a player can reach, and restores the developer's loop. Decision: the user chooses (a), (b) or (c).

  Ruled (user, 2026-11-16): (b) "Play in Studio only (Recommended)": "Only when RunService:IsStudio() is true, an arrival with nothing to pay with plays. Beta and live keep G10 as it is. One fix commit with its cases, then the layer is re-finished." Carried out on the layer:
  - Continues' `inStudio()` reads `RunService:IsStudio()` inside `pcall`, where an error or a missing method is not Studio. A Studio play counts as holding the lobby's pass (`Pay.arrive(how, passed or inStudio())`), so `Pay` and its approved interface are unchanged, and the pass is still taken on every arrival.
  - Pinned by three cases in `tests/place/paid-play-status.spec.luau`:
    - a Studio arrival with nothing to pay plays with the offer on and is not sent back (red before the fix);
    - outside Studio it is sent back and kicked on a failed teleport (red under a read that ignores IsStudio's answer);
    - with no IsStudio, or one that errors, it is sent back (red under an unguarded read, which also turns 25 sequestered adapters.spec cases red).
  - game-design.md's *Paid play* line records the exception. OC1's text sits in f0145's approved Acceptance criteria and is unchanged. In Studio its game-place steps can now be played any number of times within the hour; the lobby-to-game teleport still needs the Beta experience.
