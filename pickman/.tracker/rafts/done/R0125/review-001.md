### F1 [medium] A decline made during a revive's write that finds none (or cannot tell) opens the revive's purchase screen and holds the countdown, so the decline is not applied
Where: pickman/src/server/Continues.luau, `useOne` (the `flight.declined` branch, then `return if used == false then "empty" else "unknown"`) and `ask` (`if Session.offering(s, id) and Receipts.ask(player, Continues.TITLE, "revive") then Session.hold(s, id, true) end`)
Evidence: a live offer whose write runs (the record seen holds one revive, the store none; the same happens after a failed arrival claim, when nothing is known, or when the store fails and `useRevive` answers nil): ask, then decline while the write yields, then the write ends. `useOne` applies `Session.decline` (timer 1, held false) and answers "empty". `ask` then checks `Session.offering`, which is still true because a decline ends the offer only at the next step, so it calls `Receipts.ask` and holds the countdown again. My probe (the stub engine of c0202's offer.spec, `noFree(w, 1)`, then the store seeded to 0 revives, `hold.update`, ask, decline, release) printed `prompts 1 holding true revives 0`, and after one `Session.step` `isOver false`. The player pressed END GAME and got Roblox's revive prompt (or the test screen), with the countdown held. If they cancel, the run ends one step later. If they buy, the run continues and they are charged. f0145's rule "a decline during the write is applied after it" (Rules row M20) holds only for the used-and-refunded path. main's `ask` had the same gap (`useOne` answered "none" and `ask` prompted), so this is not a regression, but c0202 rewrote both functions, and neither offer.spec, status.spec nor any Rules row covers a decline whose write found nothing.
Critique: the tempting fix is to check `Session.offering` more strictly in `ask`, but a declined offer stays "offer" until the next step, so that check can't see the decline. Another tempting fix is to skip `Receipts.ask` whenever the countdown is not held, but that breaks the plain none-held ask, which has no hold at that point either.
Consequences: `useOne` gets a new answer, "declined": the flight was declined, the decline is applied, and nothing more is done. `ask` and `heard` must each handle it. In `ask` it acts like "refunded": no screen and no tell of none held (nothing changed). In `heard` in test mode, "declined" needs no `release`, because the decline already cleared the hold, so leaving it out of the release list is correct. In live mode, "declined" must not arm the USE_SECONDS retry: the offer is over by then, and `useOne` would answer "none" anyway. `heard`'s own grant during a declined flight answers "busy" and is unchanged. The fix changes no behaviour the capture or c0202's specs pin (no case reaches this path), but it changes main's behaviour, so it is a recorded deviation, not silent.
Recommendation: in this PR, as an emergent defect beside d0410 (zz-rules, Emergent issues; c0202's sequestered specs stay untouched): make `useOne` answer "declined" whenever `flight.declined` and the run was not continued (the refunded case may keep "refunded", since `ask` already returns on it), and make `ask` return on "declined" before `Receipts.ask`. Spec it in a non-sequestered spec on the same stub (for example a `pickman/tests/place/` spec whose watch names Continues.luau), with four cases: live and test, and a write that answers false and one that answers nil (`w.fail.update`). Each case checks that after the decline no prompt is recorded and no TestPurchase message is sent, the countdown is not held, and the run is over after one step. Check the mutant "ask ignores a declined flight", which this probe already shows the cases kill.
Lesson: zz-arch/spends-recheck-after-the-write

Upstream: zz-review
