### F1 [high] A player whose all-time asks land between the forward window and REFRESH is told they have no best, for as long as the phase holds
Where: Design §1 "The read policy" (a forward only while `now - snap.at < ttl - MARGIN`, else an answer), §2 "An ask" (**answer** sends `slot.best[name]`, which only an arcade answer to this player ever sets); the second Guess ("a dash in each for a player with no run on that game"); `acceptance/server.spec.luau:358-384` (pins `c`, who "never heard a rank", being answered with none); `acceptance/budget.spec.luau:258-320` (every player asks every board every second, so every player lands in every window, and the answer check reads rows only, never the best).
Evidence: probe, two players keeping Pickman's ALL-TIME in front, A asking at 0, 30, 60 … (as the screen does, every `REASK`), B at 20, 50, 80 …:
```
t=0 A: refresh
t=20 B: answer rank=NO best=NO(dashes)
t=30 A: refresh
t=50 B: answer rank=NO best=NO(dashes)
… (the same for every one of B's asks to t=230)
```
B has runs on Pickman, yet B's card shows `YOUR BEST — — —`, which the design defines as "a player with no run", and no lit row, indefinitely: both clients re-ask every 30 s, the refresh follows A's asks, and B's asks never reach a forward or a refresh. Any player whose first all-time ask comes 13 to 29 s after another player's refresh of that board (17 s of every 30 s, so most players in a busy portal) starts in this state; only a tab or card change that happens to land inside a window gets them out.
Critique: the "your best" line is a captured outcome, and here it shows a wrong value, not a late one. The tempting fix, forwarding every all-time ask whose best is unknown, makes a full board read outside the allowance (outside the window the arcade's cache is stale, `Hiscores.lookup` reads again), which is exactly what E3 forbids. The other tempting fix, a `REASK` below `ttl - MARGIN`, bounds how long it lasts but still draws the dashes on the first answer, and leaves F2.
Consequences: telling "not heard yet" apart from "none" adds one value to the answer and one state to the view; asking sooner while the best is pending adds asks, each answered from the snapshot with no store call; best reads stay at most one per `BEST_GAP` per title per player, because only a forward inside the window reads one.
Recommendation: (1) `BoardRelay` records per player and title whether the arcade's all-time answer has reached it (set in `heard`, not on the forward). While it has not, an all-time answer from the snapshot carries the best as pending (for example `false` in the best's place). `Board.parse` reads `false` on the all-time board as pending, `Board.view` draws YOUR BEST with a pending mark in its three cells (a named constant, never `NONE`), and `Board.askDue` treats an answer with a pending best like a wait (`WAIT_RETRY`). The player's next ask inside a forward window (at most `REFRESH - (TTL - MARGIN)` = 17 s later), or their own refresh at `REFRESH`, then reads it. (2) Cases: board (the pending cells differ from the dashes; `askDue` after a pending answer); parse (`false` is pending on all, dropped elsewhere); plan or server (a never-answered player's all-time ask between the window and `REFRESH` is answered pending, and their ask inside the next window is forwarded with `best = true`); client (pending drawn, re-asked after `WAIT_RETRY`); and a budget.spec case at the screen's cadence (players asking every `REASK` at staggered phases, on the real `Boards`): every player with a run sees their own best within `REFRESH + WAIT_RETRY`, and the sorted and standard bounds still hold. (3) Mutants: pending sent as nil; pending drawn as dashes; a pending answer re-asked only after `REASK`; heard marked on the forward.

### F2 [medium] The player's own row loses its mark on every answer from the snapshot after someone else's refresh, so it blinks on ALL-TIME
Where: §1 `rankFor` ("the held rank when it was heard at or after the board's last refresh began"), §1 "An all-time forward on 'hold' is answered instead"; `acceptance/plan.spec.luau:215-222` (L16); the Usability claim "the player's own row is lit".
Evidence: probe, B asking 5 s after A's refresh each cycle (inside the window):
```
t=5 B: forward
t=35 B: answer rank=NO best=yes
t=65 B: forward
t=95 B: answer rank=NO best=yes
```
At t=35 `bestRead(5, 35)` is "hold", so the ask is answered from the snapshot, and B's rank, heard at 5, predates A's refresh at 30, so `rankFor` returns nil. The client redraws on every answer, so B's lit row is on for 30 s and off for 30 s on ALL-TIME. In F1's phase it is never lit on any tab.
Critique: the rule guards against a mark left on a row after the rows changed, but it treats every refresh as a change, while nearly every refresh brings the same ten rows. The tempting fix, keeping any held rank, puts a stale mark on someone else's row after a new run enters the top ten.
Consequences: a held rank must be tied to the rows it was heard with. That costs one comparison of up to ten rows per arcade answer, and L16's case and Rules row change meaning (a rank is dropped only when the rows changed).
Recommendation: the snapshot keeps a `version` that `heard` bumps only when the arcade's rows differ from the held ones (`Board.sameRows(a, b)`, pure: each row's rank, name, score, level and revives). `Held = { rank, version }`, and `rankFor` keeps the rank while the versions match. Cases: a refresh that brings the same rows keeps the mark, and so does the all-time "hold" answer (server); a refresh with different rows drops it until the arcade answers that player (plan or server). Mutants: version bumped on every refresh (the blink comes back); never bumped (a stale mark on changed rows); rows compared by reference.

### F3 [medium] With one or two players, every board after the first four shows LOADING for about 35 to 40 seconds, and no criterion bounds it
Where: §1 `fill` (`RATE × max(1, players) / 60` a second, `BURST` 4), `KEEP`; Scalability "Freshness" (only a board kept in front, only for a new run); the fourth Guess; `acceptance/budget.spec.luau` (no first-answer case).
Evidence: probe, one player who reads each board for 5 s and re-asks every `WAIT_RETRY` on a wait: the four ALL-TIME boards are answered at once from the burst, then
```
asteroids|day: brought to front at t=20, first rows at t=40 (20 s of LOADING)
invaders|day: brought to front at t=45, first rows at t=81 (36 s of LOADING)
snake|day: brought to front at t=86, first rows at t=120 (34 s of LOADING)
pickman|day: brought to front at t=125, first rows at t=161 (36 s of LOADING)
pickman|week: brought to front at t=166, first rows at t=200 (34 s of LOADING)
```
(one token per 40 s at 1.5 a minute). With two players it is about 20 s each. Meanwhile the engine's own per-server sorted budget for one player is 7 a minute, and the plan already refuses any refresh that budget cannot cover (`RESERVE + COST`).
Critique: the feature checklist asks for measurable proxies. Responsiveness has no number and no case, and the common small-server case (a solo player looking at TODAY on each card) spends minutes on LOADING. The tempting fix, a larger `RATE`, breaks the experience-wide claim (1.5 per player against 2 per concurrent user) that the arcade map now records as settled.
Consequences: any change to the allowance must restate E3's experience-wide arithmetic in `arcade/.tracker/architecture.md`, keep `KEEP`'s guarantee (L12) and keep the per-server bound (L8, L9, and the live budget check).
Recommendation: state a first-answer bound for the smallest audience (for example: one player brings each of the twelve boards to the front in turn, and each is answered within N s while the engine's budget allows), and pin it with a budget.spec case on the real `Boards` alongside the existing read bounds. Pick the lever that meets it, and say in the design why both budgets still hold. Options: a per-server floor on the refill (`max(RATE × players, FLOOR)`, with FLOOR's experience-wide cost argued against the base of 300 a minute); a `BURST` of one per board, leaving the per-server limit to the live budget check that already exists; or not charging an all-time refresh a sorted token (once a title has a list, f0197 reads it with one `GetAsync`). If no lever meets a bound the user would accept, put the numbers to the user.

### F4 [high] Two Guesses narrow captured outcomes, and nothing records a Scope decision for either: the "your best" line under ALL-TIME only, and side cards left on LOADING
Where: Problem, the second and fourth Guess lines; Non-goals "Not captured, so not built: … asking for the side cards' boards"; AC1 ("the your-best line in the columns on the all-time tab"); `acceptance/board.spec.luau:191-196` and mutant B16, P8 and S4 (all pin the narrowing).
Evidence: the capture says "Each card shows **the game's hiscores** with tabs All-time / Today / This week: rank, name, score, the game's progress figure and **revives used** ("—" for none), and the "your best" line below", and game-design.md says "Below them, the "your best" line". The design shows no line under TODAY and THIS WEEK, and gives as its reason the dependency's API ("the arcade's Boards sends the best with the all-time board alone"), not the capture. Yet the stores hold each player's day and week bests (f0197: `drive` writes "three per-player boards"). Side cards: f0205 draws both neighbours at 0.8 scale, dimmed, "shown when any of it is on screen" (on 1920 x 1080 a neighbour is about 580 px wide and mostly on screen), so two cards show LOADING at every portal open, and any card the player never visits keeps showing it. The Non-goals file asking for them as "not captured", although the capture says each card shows its hiscores.
Critique: a Guess is not a Scope decision (z-design, Scope is what was captured), so as written these narrowings pass to `design: ready` without the user's ruling. The tempting answer, keeping the Guess as it stands, is the cut itself.
Consequences: each option below changes cases and possibly a dependency. Showing the day and week bests needs f0197's `serve` to send a best for every board id (f0197 is prepared, so through its raft, or a new arcade issue added to `depends_on`), plus up to two more standard reads per player and title per `BEST_GAP`. Asking for the neighbours' boards costs no store reads beyond the allowance, but competes for its tokens (F3) and adds answers.
Recommendation: escalate to the user, under `## Open to the human`, with the options and their costs. (A) The your-best line under TODAY and THIS WEEK: (a1) the player's real day and week bests, as above (the relay keeps the best per board rather than per title, parse keeps it for every id, B16, P8 and S4 invert, and budget.spec counts the extra reads); (a2) a line built from what the board already holds, the player's own row when it is in the top ten, else dashes or a "NOT IN TOP 10" mark (no new reads); (a3) ALL-TIME only, recorded as `Scope decision (user, …)`. (B) Side cards: (b1) ask for the two neighbours' boards when they become neighbours, and again every `REASK` (a client case, plus a budget.spec case that the read bounds hold); (b2) LOADING until visited, recorded as a Scope decision. Until the user rules, take "asking for the side cards' boards" out of the "Not captured" Non-goals.

### F6 [low] The column model leaves no gap between columns at the smallest text size, and the design does not say how cells align
Where: §1 `COLUMNS` (2, 8, 7, 5, 7 characters summing to `CHARS` 29, each column exactly its widest text) and "The layout"; §3 (labels set no `TextXAlignment`, so each cell is centred, the engine default); E11.
Evidence: on 320 x 480 the slot is 230 px wide and the text is 12 px, 230 / (0.65 × 29) = 12.2. The Rank column (15.9 px) holds "10" with about a pixel to spare, and the Name column after it holds an 8-character name cut with "…" edge to edge. So "10" and the name touch; so do the header's LEVEL and REVIVES (each fills its column at the model's width). 844 x 390 is nearly as tight (12.57 against 12).
Critique: E11's fallback (moving characters between columns) does not create a gap, and OC1 is the only check.
Consequences: a gap of half a character per boundary (CHARS about 31) drops 320 x 480 to about 11.4 px, below `Card.MIN_TEXT`, so a gap costs a column character somewhere (a 6-character name, a 6-digit score, or a shorter revives header, whose wording is itself a Guess).
Recommendation: model a gutter in `CHARS` and give `COLUMNS` the characters to pay for it, extending board.spec's "each column's widest text whole" case to require the gap. Name each column's `TextXAlignment` (for example rank and numbers right, name left) and pin it in the client case.

### F7 [low] E3's settled text overstates two budget facts
Where: `arcade/.tracker/architecture.md` E3 ("A read is at most one `GetSortedAsync`"; "under the per-server sorted-read budget … whatever its clients ask"); §1 `COST = { standard = 12, sorted = 1 }`; E8.
Evidence: f0197's page reader tries twice ("a rejected size 10 is tried once at 50"; "two failures fail the read"), so a refresh can make two sorted calls, and one admitted at `budget.sorted = RESERVE + 1` can spend into the reserve. E8 asks only about Studio. What `GetRequestBudgetForRequestType` returns on a fresh live server is unproven, so if it starts below `RESERVE + COST`, the first players see LOADING until it accrues.
Critique: the map's text is the record later issues quote, and place.spec pins it.
Consequences: none beyond the wording, plus one more Observed note.
Recommendation: make `COST.sorted` 2 (or state the retry as an accepted overrun into the reserve), correct the E3 text to match, and add to OC2 (or a new Observed step on a published test place) recording the budgets a fresh server reports at start.
