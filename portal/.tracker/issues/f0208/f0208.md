## Solution
Three pure leaves and a config table carry the rules. `Logic/Play` holds the server's decision from a read of the player's record, the client's intents and the server's statuses checked field by field, each card's buttons and note, their slots and the keys. `Logic/Pairing` holds the 2 PLAYERS waiting lines of one server, `Logic/Arena` which shared arena an ARENA player joins, and `src/shared/Modes.luau` each title's buttons. A server adapter, `Plays`, installs the arcade's Receipts and owns each player's one play. It reads their record through the arcade's Wallet. A free start due or a held play goes at once; a failed read writes the portal's pass (`Wallet.pass`) and goes; otherwise it opens the 1 R$ play product (`Receipts.ask`) and goes on that purchase's grant. Going is a teleport through the arcade's Travel to the title's place from the place-id attributes (`Places`). PLAY goes to a public server. ARENA goes to the shared arena's reserved server, recorded in a MemoryStore hash map. 2 PLAYERS goes to the title's waiting line, and both players teleport in one call to a fresh reserved server once a second joins. Nothing is charged in the portal (the game place's `Wallet.arrive` claims the free start or the held play, or takes the pass), and nothing rides in TeleportData. A second server adapter, `Invites`, records a waiting player's invite and sends an invited friend who lands in another portal server to the inviter's. The client adapter, `PlayButtons`, fills each card's `Buttons` slot (f0205's `CarouselView.card`) from the card states the server already sends (`Remotes.Cards`), turns taps, the carousel's PLAY (`CarouselView.onPlay`) and its own keys into requests on a new `Remotes.Play`, draws the player's play on its card, and opens Roblox's invite prompt; the portal's client boots the arcade's test purchase screen, so playtests show the same screens and charge nothing.

### 1. `src/shared/Logic/Play/init.luau` (new, pure; requires `./Card`)
```luau
export type Mode = "solo" | "arena" | "pair"
export type Phase = "idle" | "checking" | "buying" | "waiting" | "going" | "closed" | "failed"
export type Decision = "go" | "pass" | "buy" | "closed" | "busy"
export type Read = { free: boolean, plays: number }          -- PaidPlay.status's two figures, passed in
export type Status = { phase: Phase, name: string?, mode: Mode? } -- what the server tells one player
export type Intent = { action: "play" | "cancel" | "invite", name: string?, mode: Mode? }
export type Kind = Mode | "cancel" | "invite"
export type Button = { kind: Kind, text: string, price: string, enabled: boolean } -- price is rich text
export type View = { buttons: { Button }, note: string }
export type Slot = { x: number, y: number, width: number, height: number } -- of the Buttons slot's size
export type Key = "second" | "cancel" | "invite"
export type Modes = { [string]: { Mode } }
Play.MODES = { "solo", "arena", "pair" }; Play.PHASES = { the seven, in that order }  -- frozen
Play.LABEL = { solo = "PLAY", arena = "ARENA", pair = "2 PLAYERS", cancel = "CANCEL", invite = "INVITE FRIEND" }
Play.NOTE = { checking = "CHECKING...", buying = "COMPLETE THE PURCHASE", waiting = "WAITING FOR A SECOND PLAYER",
              going = "STARTING...", closed = "STORE UNAVAILABLE", failed = "COULD NOT START. TRY AGAIN.",
              other = "A PLAYER IS WAITING" }
Play.FREE = "FREE"
Play.KEYS = { Two = "second", KeypadTwo = "second", ButtonX = "second", Backspace = "cancel", ButtonB = "cancel",
              I = "invite", ButtonY = "invite" }          -- frozen; none of them is a carousel key
Play.ACTION = "PortalPlay"; Play.PRIORITY = 2500         -- above the default controls' 2000, below the test screen's 3000
Play.GAP = 0.02; Play.BUSY_SECONDS = 0.25; Play.CHECK_SECONDS = 10; Play.RECEIPT_SECONDS = 30

function Play.intent(action: any, name: any, mode: any, modes: Modes): Intent?
function Play.parse(raw: any, modes: Modes): Status?
function Play.price(state: Card.State?, prices: Card.Prices): string
function Play.view(name: string, modes: { Mode }, state: Card.State?, status: Status?, others: number, prices: Card.Prices): View
function Play.slots(count: number, noted: boolean): { Slot }
function Play.noteBox(count: number): Slot
function Play.key(name: string): Key?
function Play.second(modes: { Mode }): Mode?

```
- **The decision** (the server's, from `Wallet.read`'s answer and `Wallet.mode`): no record and `"busy"`: `busy` (read again). No record otherwise (`"down"`, or no reason): `pass` (the player goes on the portal's pass; first Guess). A record whose `free` is true, or with `plays >= 1`: `go`, in every mode, closed included (f0145's "free games and credits already held still work"; G11's order is the arrival's, `PaidPlay.start`). Neither, in closed mode: `closed` ("buying shows 'store unavailable'"). Else `buy`.
- **The intent** (a client's message): `"play"` with a name of `modes` and one of that name's modes, else nil; `"cancel"` and `"invite"` carry nothing, whatever else is sent. **The status** (`parse`, the client's read): a table whose `phase` is one of `PHASES`; with no name and no mode, just the phase; else a name of `modes` and a mode of it; anything else nil. Neither raises.
- **The price**: unknown state (or its free state not read yet): `""`; free: `"FREE"`; else `Card.strike(prices.struck) .. " " .. prices.price` (`"<s>5 R$</s> 1 R$"` with the arcade's `Prices`).
- **The card's view**: a title not published shows nothing (its badge says COMING SOON, f0205). When the player's status names this title and is not idle: `checking`, `buying` and `going` show only their note; `waiting` shows `NOTE.waiting` with CANCEL and, for 2 PLAYERS, INVITE FRIEND (both enabled, no price); `closed` and `failed` show their note above the title's buttons. Otherwise one button per mode in the title's order, `LABEL[mode]` over the price, enabled once the title's state and free state are known; and when `others > 0` on a title with 2 PLAYERS, the note `NOTE.other`. While a note shows, the mode buttons carry no price (their names only; the badge says it). A status about another title changes nothing here.
- **The slots** (scale, of the Buttons slot): `count` buttons side by side, `GAP` apart, across the slot's full width; full height, or the bottom half when there is a note. `noteBox(count)`: the whole slot with no buttons, else its top half. **Readable text** (lesson pickman-test/readable-text-has-a-number): every text a card's buttons row can show (each label and price line, each note) is at least `Card.MIN_TEXT` px on f0205's seven screens, by `Card.textSize` over the front card's `Carousel.box`, `Card.REGIONS.Buttons`, `Card.INSET` and these slots: a button with a price is two lines (each half its height), one without is one line, a note wraps. The smallest with the shipped constants is 13.1 px (WAITING FOR A SECOND PLAYER and COULD NOT START. TRY AGAIN. on 320 x 480; INVITE FRIEND 13.4 px there). "INVITE A FRIEND" would be 11.9 px on 844 x 390, hence INVITE FRIEND. **The keys**: `KEYS` above, at `PRIORITY` strictly between Roblox's default controls (2000) and the test purchase screen (3000) (lesson pickman-arch/bind-above-the-default-controls); `second(modes)` is `modes[2]`.
- **The invite's reads**: `inviter(raw)` is the user id in an invited friend's launch data, whole decimal digits of a positive id (at most 15 digits, no leading zero, no sign or spaces), else nil; `invite(raw, modes)` is an invite's stored record `{ job, name }`, a non-empty job and a title of `modes`, else nil.
- Nothing mutates its input. The word `game` appears nowhere in the file (pickman-arch rule 2); a title is a `name`.

`join` first takes `id` out of every line (a player waits in one line at most, never twice in one), then: when someone waits in `name`'s line, the first of them and `id` are the pair, in that order, and both leave it; else `id` waits at the line's end. `leave` takes `id` out of every line. Lines are per title. Nothing mutates the queue it is given.

### 3. `src/shared/Logic/Arena/init.luau` (new, pure, a leaf)
```luau
export type Record = { id: string, count: number, opened: number } -- a reserved server id, players sent, os.time() opened
Arena.CAP = 24; Arena.OPEN_SECONDS = 600; Arena.MAP = "PortalArenas"
function Arena.open(raw: any, now: number): Record?
function Arena.join(raw: any, fresh: string, now: number): Record
```
`open`: a stored value that is a record with a non-empty `id`, a whole `count` from 0 to `CAP - 1`, and a whole `opened` no later than `now` and less than `OPEN_SECONDS` before it; anything else nil. `join` is the MemoryStore transform: an open arena with one more player sent (same id and opening), else a new arena `{ id = fresh, count = 1, opened = now }`. The caller sends the player to the answer's `id`. Because `count` counts players sent, not players present, an arena closes to new players early when players leave, never late.


- **The slot**, per Player object: `{ phase, name, mode, flight, invited }`, made by each play, dropped on `PlayerRemoving`. `flight` is a serial that marks which play a yielding step belongs to; a step whose player left, or whose slot now belongs to a later play, does nothing more. **Telling**: every phase change sends `remote:FireClient(player, "status", { phase, name, mode })` to that player only, and only while they are present.

  - `"cancel"` while waiting: leave the line, `idle`. `"invite"` while waiting for 2 PLAYERS: the first invite of that wait spawns `Invites.offer(player, name)`; each answers `remote:FireClient(player, "invite")` (the client prompts). Otherwise both do nothing.

Then **the play**.
- **The play**: a new flight, phase `checking`. **The check**: `record, problem = Wallet.read(player, name)`; with a record, `read = { free, plays }` from `PaidPlay.status(record, os.time())`; `decision = Play.decide(read, problem, Wallet.mode(name))`. `busy` reads again after `task.wait(BUSY_SECONDS)`, until `CHECK_SECONDS` have passed since the first read, when the play fails (a busy read costs no store call: Wallet answers it from its in-flight flag). - **The purchase** (Receipts' handlers, which hear only players still on the server): `granted(player, name, "play")` while that player's phase is `buying` for that name: **go on** (second Guess: any other grant is a held play, used at the next PLAY). `closed(player, name, "play", false)` while buying it: `idle`. `closed(…, true)` while buying it: keep buying, and `task.delay(RECEIPT_SECONDS)`: if that flight is still buying, `idle` (third Guess). Either order of close and grant works (lesson pickman-arch/purchase-close-before-receipt). A revive's grant or close is not this adapter's (f0215, f0219, f0223 sell revives in their places).
- **Going on** by mode:
  - `solo`: **start** `{ player }` with no reserved server.
  - `arena`: `fresh = HttpService:GenerateGUID(false)`; one `MemoryStoreService:GetHashMap(Arena.MAP):UpdateAsync(name, transform, Arena.OPEN_SECONDS)` whose transform is `Arena.join(raw, fresh, os.time())`, the answer being the transform's **last** call's (UpdateAsync may call it again on another server's newer value; lesson zz-test/store-stubs-race-the-transform). An error fails the play (sixth Guess). Then **start** `{ player }` in the answer's `id`. The hash map is opened on first use inside the same `pcall` (lesson pickman-arch/open-stores-guarded).
  - `pair`: `queue, pair = Pairing.join(queue, name, userId)`; with no pair, phase `waiting`; with a pair, **start** `{ first, player }` (the first being the player who waited, found with `Players:GetPlayerByUserId`) in `HttpService:GenerateGUID(false)`, a reserved server of their own. Every change to the lines sends `remote:FireAllClients("waiting", { [name] = count })` for each title with 2 PLAYERS; a player who joins gets the current counts.
- **Start** (`go(players, name, reserved)`): if any of them is not `idle` in Travel, they all fail. Else each `Travel.request`s (a ticket each) and goes `going`; then **one** `TeleportService:TeleportAsync(destination[name], players, options)` in a `pcall`, `options = Instance.new("TeleportOptions")` with `ReservedServerId = reserved` when there is one, and nothing else (no TeleportData, no fourth argument). Returned: `Travel.answered` for each. Raised: `Travel.failed` for each and phase `failed`. `TeleportService.TeleportInitFailed(player)`: `Travel.failed(…)`, and a `going` player fails. A heartbeat once a second fails every `going` player whom Travel shows `cooling` (the 15 s timeout after an answer that did not take the player). A failed or closed player may play again once Travel is idle (tenth Guess: no retry by itself).
- **A leave** (`PlayerRemoving`): out of the line (the others hear the count), `Travel.left`, the slot dropped; so a read, a grant, an arena write or a delay that returns after the leave sends nothing, asks nothing and teleports no one.

### The split and server authority
Everything that decides is pure and unit-tested: the decision, the intent and status checks, the view, the slots, the keys, the waiting lines, the arena's transform, the invite's reads and the buttons per title. The adapters only translate: Wallet's answers into a decision, the decision into Receipts, MemoryStore and TeleportService calls, Roblox's handlers back into phases; the client's taps and keys into intents and the server's messages into instances. **The server decides** whether a player may play (their own record, never anything the client says), what they pay (Receipts' grant, never the client), where they go (the attributes the publisher set, never a place id from the client), with whom (the lines it keeps), and into which server (ids it makes). A client can only ask: a play of a title in one of its modes, a cancel, an invite. A forged intent names at most a title and a mode the server checks; a forged status or count only misdraws that client's own screen. **Nothing is charged in the portal**: the entitlement is the player's record (a free start due, or a held play bought here) or the portal's pass, and the game place consumes it on arrival (`Wallet.arrive`), so a teleport that never arrives costs nothing (G10). **TeleportData is never sent, so it can never be trusted**; the invite's launch data only names a record to look up.

### Edge cases (purchase and teleport paths)
- **The store read fails** (down or slow): the pass, then the start (first Guess). **The read is busy** (f0205's card reads or a revive's use under way): read again every 0.25 s, at most 10 s, then COULD NOT START.
- **The pass write fails** (MemoryStore down): the start goes on; the arrival treats an unreadable pass map as a pass ("Let all of them play"), and a written-but-lost pass sends the player back from the game place at no cost.
- **The purchase write fails** (Receipts answers NotProcessedYet; a test confirm's write fails): Receipts reports `closed(…, false)` for the test screen, so the card goes idle; a live receipt is retried by Roblox and granted later as a held play.
- **The receipt arrives after the player left or teleported**: Receipts grants it by user id and hands nothing to a player not here; it is a held play at that title's next PLAY (f0201: "a buyer not on this server is granted all the same").
- **The receipt arrives before the close, or after it**: both orders start the play; a close bought with no receipt for 30 s goes idle.
- **The teleport fails** (raises, TeleportInitFailed, or 15 s without leaving): COULD NOT START for that player (both, for a pair), Travel's 3 s cool-down, nothing charged.
- **A double press, a key and a tap together, or a flood of intents**: one play per player; every press while checking, buying or starting is dropped; a press while Travel is busy or cooling is dropped.
- **Two portal servers at once**: two ARENA joins race on one MemoryStore key, and the transform's last call decides, so both join the same arena; a player is only ever in one portal server, so their own play never races; a receipt processed on two servers is f0201's (one write per receipt id).
- **A player who leaves** while checked, buying, waiting or starting: out of the line, nothing asked, sent or teleported afterwards; a rejoin is a new Player object and starts afresh.
- **The partner left** between pairing and the start: Pairing never holds a departed player (the leave takes them out first); a player found missing anyway fails the newcomer's start.
- **Nothing published** (every attribute 0, as checked in): every card COMING SOON, no button, no read.
- **Studio**: test mode (f0145 G1), so the test purchase screen charges nothing; Roblox's teleport guide: "You can test TeleportAsync() teleports in Studio's Test and Team Test modes without publishing your experience" (E4); Wallet's stand-in test store keeps test credits for that server (f0201 E8).
- **Frame rate**: nothing counts frames; the heartbeat sweep reads the clock once a second.

### Scalability
Per press: one `Wallet.read` (Wallet's bounds hold the store calls: at most one `GetAsync` per player and title per 60 s while the store answers, one per 6 s while it fails; a busy answer costs nothing), so one client flooding PLAY costs at most one check at a time and, after a failure, nothing for 3 s (Travel's cool-down). Per start: one `TeleportAsync`; an ARENA start one MemoryStore `UpdateAsync` (2 request units); a 2 PLAYERS pairing none; a pass one `SetAsync` per down answer (Wallet's bound). Per wait: at most one invite `SetAsync`. Per join: at most one invite `GetAsync`, only with an inviter's id in the launch data. MemoryStore's quota is "1000 + 120 × [number of concurrent users] request units per minute", and one key takes "approximately 5,000 write request units per minute" (E4's doc check): the `snake` arena key takes 2 units per ARENA start, so 2,500 ARENA starts a minute before it throttles. Replicated: one RemoteEvent; a status is three short fields, a count table four numbers at most, sent on changes only. Server memory: a slot per player and the lines (at most one waiting player per title, since the second pairs). Client: per card a label and five buttons; drawing is a table walk on each message, nothing per frame.

### Maintainability
A new title is one `Modes` entry (beside its `Games` entry, its Catalog entry and its place in Places, from their own issues); a new mode is one `Mode` value, one label and one branch in `Plays`' going-on. Words are `Play.LABEL` and `Play.NOTE`, the price's words the arcade's `Prices`; tuning is `Play.*_SECONDS`, `Arena.CAP` and `Arena.OPEN_SECONDS` (f0212 sets the real cap after its load experiment E6 and changes `Arena.CAP` with it). The seams the next issues use are named: a game place reads its server kind (Interfaces, below), and f0207 and f0206 add their own remotes and adapters (CV1, CV2, CV5 stay green). The purchase plumbing stays the arcade's: this issue only calls `read`, `mode`, `pass`, `ask` and `start`.

### Usability
- **Player**: every text on the buttons' row is at least 12 px on the smallest phone; every card says what PLAY costs before it is pressed ("FREE", or "5 R$" struck through and "1 R$"); a free game or a held play starts at once; a purchase starts the game as soon as it is granted; a failing store never blocks a player; a 2 PLAYERS wait says so on its card, shows who else waits, and has CANCEL and INVITE FRIEND; every control works by tap, keyboard and gamepad (PLAY by Enter, KeypadEnter or A; the second button by 2 or X; CANCEL by Backspace or B; INVITE by I or Y) and none of them fires while typing in the chat; a start that could not happen says so and can be tried again 3 s later.
- **Developer**: the server's API is one `start`; the client's one `start`; a game place needs nothing from the portal but `Wallet.arrive` and its server kind; the Logic is small typed functions with the titles' buttons as data.
