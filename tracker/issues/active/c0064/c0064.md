# c0064: Publish lobby place

## Problem
R0024 (f0061) splits the experience into two places: the existing place becomes the lobby, and a new place hosts the game. The Beta deploy (`scripts/deploy-beta.luau`, the `beta` job of `.github/workflows/check.yml`) builds and publishes only `default.project.json` to the one place named by `ROBLOX_BETA_PLACE_ID`, and the runtime tests (`tests/runtime`) run in a server of that place. The lobby build is never published, its destination ids are never set (the checked-in `GamePlaceId` is 0, which the lobby reads as "not set up"), and the game place has no id to be published to.

## Non-goals
- The lobby and the teleports themselves (f0061); production publishing (undecided, see tracker/game-design.md).
- Creating the second place in Roblox: that is the user's step (an Open Cloud key scoped to the experience already covers its places).

## Solution
- A new repo variable, `ROBLOX_BETA_GAME_PLACE_ID`, for the game place; `ROBLOX_BETA_PLACE_ID` stays the experience's start place, which is now the lobby (SETUP.md says so).
- Deploy builds both projects and publishes each to its place. It injects the other place's id before building, by writing a copy of the project file with the `GamePlaceId` (lobby) attribute set; the experiment in f0061's E3 shows a built copy carries the value.
- The runtime tests run per place: the structure checks for the game place in a server of the game place, and new ones for the lobby.
- When not configured it still skips with a warning and succeeds, as today.

## Design
### Decisions made in prep (author's choices; the user may veto)
- **Which place is which** (game-design, "Two places", binding): `ROBLOX_BETA_PLACE_ID` stays the experience's start place and becomes the **lobby**; the new repo variable `ROBLOX_BETA_GAME_PLACE_ID` is the **game place**. Production publishing stays out (game-design: "production stays undecided").
- **A safe transition (legacy mode)**: until the user sets `ROBLOX_BETA_GAME_PLACE_ID`, the deploy does exactly what it does today (the game, `default.project.json`, to `ROBLOX_BETA_PLACE_ID`) plus a `::warning::` that the lobby is not published. So merging this chore never breaks Beta, and c0015's `deploy-e2e`/`deploy-cli` and c0003's runner specs stay as they are. Setting the variable switches to **split mode** on the next ready PR.
- **Injection by a project copy outside the checkout**: the deploy writes a copy of each project into a `mktemp -d` folder with every `$path` made absolute against the checkout and the attributes set on `ServerScriptService["$attributes"]`, and builds that copy. The checked-in `GamePlaceId` stays `0` (f0061's `lobby-place` pins it). E1 proves Rojo builds such a copy and the place reads the id back.
- **Build everything, then publish**: both places are built before either is published (a lobby that does not build publishes nothing). The game is published first, then the lobby; a failure stops there. Outputs (`version`, `lobby_version`) reach `$GITHUB_OUTPUT` only once every publish succeeded. A refused lobby after a published game leaves the game ahead of the lobby, which is harmless: the lobby's `GamePlaceId` is the same fixed id.
- **The PR comment is unchanged** and names `version`, which stays the game place's version (what players play and what `tests/runtime` tests). The lobby's version is in the job log (`published the lobby place (…): version N`) and SETUP.md says so. Changing the comment would only widen the overrides.
- **Runtime tests per place**: `tests/runtime/*.luau` stay the game's and run in the game place; `tests/runtime/lobby/*.luau` (new) run in the lobby with `runtime-test -- --lobby <version>`, in a sixth workflow step that runs only when a lobby was published. Top-level listing ignores the subfolder, so c0003's `scripts` spec and the default game run are unchanged.
- **The way back's id (f0065)**: f0065 (R0034, prepped in parallel) reads the lobby's id from the attribute `LobbyPlaceId` on the game place's `ServerScriptService` (`0` as checked in). This raft sets it: in split mode the game target gets `attributes = { LobbyPlaceId = <start place id as a number> }`, so both ways are configured by one publisher (design review 002 F1). In legacy mode the game target gets no attributes (there is no lobby). The copy adds the attribute even before f0065 adds it to `default.project.json`; an unread attribute is harmless. If f0065's design renames it, this one string in `scripts/lib/beta.luau` and the specs follow.

### Files and API
- `scripts/lib/beta.luau` (new, pure apart from `serde`; requires `@scripts/lib/opencloud`):
```lua
export type Place = "game" | "lobby"
export type Target = {
	place: Place,
	project: string,                   -- "default.project.json" | "lobby.project.json"
	placeId: string,                   -- digits: where it is published
	attributes: { [string]: number },  -- set on ServerScriptService in the built copy
	output: string,                    -- "version" | "lobby_version"
	runtime: string,                   -- "tests/runtime" | "tests/runtime/lobby"
}
export type Plan = { split: boolean, targets: { Target }, notice: string? }
Beta.GAME_PLACE_VAR = "ROBLOX_BETA_GAME_PLACE_ID"
Beta.MAX_PLACE_ID = 2^53 - 1
Beta.plan(env: { [string]: string? }): Plan?   -- nil = OpenCloud.configFromEnv(env) is nil (not configured)
Beta.target(plan: Plan, place: Place): Target?
Beta.project(text: string, dir: string, attributes: { [string]: number }): string
```
  - `plan`: not configured → `nil` (whatever the game variable says). Game variable missing or empty → `{ split = false, targets = { game → ROBLOX_BETA_PLACE_ID, attributes {} (no lobby to go back to), output "version", runtime "tests/runtime" }, notice = "...the lobby is not published: set ROBLOX_BETA_GAME_PLACE_ID..." }`. Otherwise the game id must match `^[1-9]%d*$` and be at most `MAX_PLACE_ID` (so the attribute is exact and f0061's `Travel.destination` accepts it), the start id must be a place id too, and they must differ; any failure raises `beta: ROBLOX_BETA_GAME_PLACE_ID ...` (or `ROBLOX_BETA_PLACE_ID`), never the key. Split → targets `{ game → game id with attributes { LobbyPlaceId = tonumber(start id) }, lobby → start id with attributes { GamePlaceId = tonumber(game id) }, output "lobby_version", runtime "tests/runtime/lobby" }`, in that order, `notice = nil`. The env is not changed.
  - `project`: decodes the JSON (error naming "project" when there is no `tree`), walks the tree (not into `$`-keys other than `$path`) making every relative `$path` string, and the `optional` of a `$path` table, absolute against `dir`; absolute paths stay. Non-empty `attributes` are merged into `tree.ServerScriptService["$attributes"]` (both created when missing; other attributes kept). With empty attributes nothing but the paths changes. Returns pretty JSON.
- `scripts/deploy-beta.luau` (rewritten as a thin driver): `pcall(Beta.plan, process.env)`: an error is printed and exits 1 before anything is built; `nil` prints today's `::warning::... not configured ...; skipped` and exits 0; a `notice` is printed as `::warning::<notice>`. For each target: a missing project prints `rojo build failed (<project>): the project file is missing`, exit 1; the copy (`Beta.project(text, process.cwd, attributes)`) goes to `<mktemp -d>/<place>.project.json` and builds to `<same dir>/<place>.rbxl`; a failed build prints `rojo build failed (<project>):` plus Rojo's output, exit 1. Then each target is published with a clone of the OpenCloud config whose `placeId` is the target's, printing `published the <place> place (<id>): version N`; a failure prints the error and, if any went out, `published before the failure: version=N`, exit 1. At the end it prints each `<output>=<N>` line and appends them all to `$GITHUB_OUTPUT`.
- `scripts/runtime-test.luau`: usage `lune run scripts/runtime-test -- [--lobby] <version> [script files...]`. `--lobby` (only as the first argument) picks the lobby target. Plan errors exit 1; not configured → today's warning, exit 0; no target for the place (the lobby in legacy mode) → `::warning::runtime tests of the lobby place are not configured (ROBLOX_BETA_GAME_PLACE_ID); skipped`, exit 0. The scripts run with `placeId` set to the target's; with no files, every `*.luau` file directly in the target's `runtime` folder.
- `tests/runtime/lobby/structure.luau` (new; strict, no requires, ends `return "PASS"`, `game` via `getfenv()` like the game's): `ServerScriptService.Lobby.Main` exists, `ServerScriptService.Server` does not, `ReplicatedStorage.Remotes.StartGame` and `.Status` exist, `Players.CharacterAutoLoads == false`, and `ServerScriptService:GetAttribute("GamePlaceId")` is a whole number ≥ 1. The game's `tests/runtime/structure.luau` is not changed here (f0065 adds its `LobbyPlaceId` check). (No `game.PlaceId` comparison: Lune cannot read it, E3; the plan already refuses equal ids.)
- `.github/workflows/check.yml`, beta job: the deploy step's env and the game runtime step's env gain `ROBLOX_BETA_GAME_PLACE_ID: ${{ vars.ROBLOX_BETA_GAME_PLACE_ID }}`; a sixth step, `if: steps.deploy.outputs.lobby_version != ''`, `run: lune run scripts/runtime-test -- --lobby "$LOBBY_VERSION"`, env `LOBBY_VERSION: ${{ steps.deploy.outputs.lobby_version }}` plus the key and the three ids. Nothing else changes (the comment step is byte-identical).
- Docs: SETUP.md's Beta section (two places, legacy behaviour, the owner's numbered one-time steps, the `--lobby` command, the comment's version is the game's), and the testing skill's `tests/runtime/` row (`tests/runtime/lobby/`, `--lobby`). The exact prototype text is in R0032's `experiments/prototype.patch`.
- Narrowed promoted specs (this chore's overrides, below): `tests/acceptance/c0015/workflow.spec.luau` and `tests/acceptance/c0003/pipeline.spec.luau`, exactly as in the patch.

### Pure/adapter split and authority
Everything that decides (which place gets which build, which ids, the copy's contents, validation) is in `scripts/lib/beta.luau` and tested without Rojo or a network. `deploy-beta` and `runtime-test` only run Rojo, the HTTP calls and the file writes. Nothing in `src/` changes; the server still reads its destination only from its own attribute.

### Scalability
Two Rojo builds (about 0.1 s each) and two publishes instead of one per ready PR, inside the existing 20-minute `beta-deploy` lock; each publish keeps OpenCloud's retry budget. A further place is one more target row (and its runtime folder).

### Maintainability
The plan is a table: f0065's lobby id, or a third place, is a row with its project, place variable and attributes. The checked-in projects never carry real ids, so forks and Studio sessions stay "not set up".

### Usability
- **Owner**: one variable to set, documented as numbered steps; until then nothing changes, and the warning in the job log says what to set.
- **Developer**: `lune run scripts/deploy-beta` by hand works the same with one more export; `runtime-test -- --lobby N` runs the lobby's checks.

## Unknowns & experiments
All run in prep on the prototype (R0032 `experiments/prototype.patch`, which applies to `main` at prep time); the executor starts from it.
- **E1** Does Rojo 7.7 build a project copy outside the checkout with absolute `$path`s, and does the place read the injected id? **Pass**: a copy of `lobby.project.json` in a `mktemp -d` folder with `GamePlaceId = 987654321` built; `GetAttribute` read `987654321` (a number), the lobby's scripts and the 17 shared modules were there. `project.spec` now pins that the copied lobby equals the original build except for the attribute, and the copied game place equals its original.
- **E2** Does `serde.encode` keep a 14-digit place id exact? **Pass**: `82331952549326` and `2^53-1` encode as integers.
- **E3** Can a runtime script run headlessly under Lune against a built place? **Pass**: `luau.load(source, { environment = { game = place } })` runs `tests/runtime/structure.luau`: `PASS` in the game place, `ServerScriptService.Server is missing` in the lobby. `game.PlaceId` cannot be read there ("missing default value"), so the lobby script does not use it.
- **E4** Does a published body deserialize in the fake server? **Pass**: `roblox.deserializePlace(req.body)` in `deploy.spec` reads the lobby's `GamePlaceId` from what was sent.
- **E5** The whole gate with the prototype (including the narrowed c0015 and c0003 specs): **pass**, 1376 cases in 195 spec files, wall time 94.9 s.
- **E6** Mutation check: 35 mutants, each applied to the prototype and run against its spec: **all killed on assertions** (see Rules and mutants). Design review 001 added five: the lobby script without its `Server`-absent, `CharacterAutoLoads` or `StartGame` checks (F2), the deploy without its `published before the failure` line (F3), and the game target told a `GamePlaceId` (F1's narrowed assertion). Design review 002 added four: the game not told `LobbyPlaceId`, told its own id, `LobbyPlaceId` in legacy mode, and the lobby script without its whole-number check. One (the lobby's runtime folder swapped for `tests/runtime`) first survived, because both folders hold a `structure.luau`; the `--lobby` case now checks the script text sent is a lobby script, and the mutant fails.
- **E7 (not provable offline)** Roblox accepts a publish to the new place and runs Luau Execution there with the existing key, and the teleport works between the two published places. **Method**: Observed O1-O2. **Fallback**: an HTTP 403 means the key is limited to one place: SETUP step 3 says to widen it; nothing in the code changes.
