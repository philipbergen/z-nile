# c0066: c0038 cleanup flake

## Problem
`tests/acceptance/c0038/deferred.spec.luau :: cleans up` (`fs.removeDir(work)` on its throwaway clone) failed once with `Directory not empty (os error 66)`. That was in a full gate on R0019's final head (2026-10-03, about a 65 s gate under several sessions' load). It then passed alone 3/3, and in the next full gate. Something is still writing into the fixture while it is removed, so the gate can go red for nothing under load. The fixture already sets `gc.auto 0` (spec line 91), so automatic gc is not the writer. A detached git child left by the clone's `done` run (for example a `maintenance` or `fsmonitor` daemon), or a lingering child of the fixture's own `tests/run`, is the likely one.

## Non-goals
- Changing `tracker.sh done` or the deferred-finding behaviour the spec pins.
- The other `cleans up` cases (c0006, c0007, c0008, c0034, c0042). They haven't flaked. They can adopt the helper later.

## Solution
A small test library, `tests/lib/cleanup.luau`, with `cleanup.removeTree(path)`. It removes a tree, retrying for a bounded time while something keeps writing into it. If the tree still can't be removed, it fails with the entries left behind, so the next flake names its writer. c0038's `cleans up` case uses it, as this chore's own override. Phase 1 tries to identify the writer under load. If it can be stopped through fixture configuration, that goes in the spec's setup, never in the `cleans up` body (AC3 pins that body).

## Design
```lua
-- tests/lib/cleanup.luau
-- Removes `path` and everything under it. While removal fails because the tree changed underneath (another process still
-- writing: an error mentioning "not empty" or "No such file"), retries every 50 ms for up to `seconds` (default 3).
-- On final failure raises "could not remove <path> after <n> tries: <error>; left: <up to 20 relative paths>", listed
-- breadth-first (shallowest first) and sorted within each directory, so the order is the same on APFS and ext4.
-- After a race it always retries at least once, even when the first attempt alone used up the bound.
-- A missing path succeeds. Any other error is raised at once. `remove` (default fs.removeDir) is the seam the spec uses
-- to race deterministically.
function cleanup.removeTree(path: string, seconds: number?, remove: ((string) -> ())?)
```
- It is a bounded poll, which the testing skill's Speed rule allows (not a fixed sleep).
- `deferred.spec.luau`'s `cleans up` becomes `cleanup.removeTree(work)`. Its other `removeDir` calls (setup, lines 71/97) stay: they run before any git child exists.
- The library must not inject git configuration or env (R0021's guards).

### Scalability
No cost when nothing races. At most 3 s when something does.

### Maintainability
One helper with its own spec. The left-behind listing turns a future flake into a diagnosis.

### Usability
The gate stops failing for no reason.

## Test plan
`acceptance/cleanup.spec.luau` (fixture `.cache/c0066-cleanup`):
- :: removes a tree and succeeds for a missing path → AC1
- :: retries a remover that races, then succeeds → AC1 (a `remove` seam failing twice with "Directory not empty")
- :: retries at least once even when the first attempt outlasts the bound → AC2 (`seconds = 0.05`, and a seam that sleeps 0.1 s, then races: at least 2 calls)
- :: gives up after its bound and lists what is left → AC2 (a seam that always races, `seconds = 0.3`: it fails naming `top.txt`, after more than 1 and at most 12 calls)
- :: raises an error that is not a race at once → AC2 ("Permission denied": exactly one call)
- :: cleans up → removes its own fixture with the helper
- `check.sh` greps → AC3
