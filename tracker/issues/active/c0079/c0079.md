# c0079: Run watchdog is reliable and specced

## Problem
When a run's launcher is killed (for example a SIGKILL to the run's whole process group), a watchdog in the specs' process group stops the specs (R0021 review 006 F2). No spec covers it; it was seen working once, by accident, during a by-hand check that also killed its own shell. A regression would leave hung specs holding the lock until someone kills them by hand.

The review of that fix (c0078's `review-of-round6-fixes.md`, F2) found three more defects:
- **A failed fork hangs the run.** `if (!fork)` is true when `fork` fails (returns `undef`). The specs' own process then turns into the watchdog and never runs the specs, while the launcher waits for it. The run hangs, holding the lock, until someone kills it by hand.
- **The watchdog dies on forwarded signals.** The launcher forwards INT, TERM and HUP to the whole group, and the watchdog doesn't ignore them. One forwarded TERM removes the protection for the rest of the run.
- **It polls a pid.** It polls `kill 0, $launcher` once a second, which a reused pid can fool. And if `getppid` already returned 1, it never fires.

## Non-goals
- The reaping at the end of a normal run: `fence-leftovers.spec` covers it, and this issue only re-checks it.
- Processes that leave the group (c0076).
- The unlink after the group is killed (c0077, in the same launcher).

## Solution
The watchdog waits on a pipe instead of polling. The launcher holds the only write end, so the watchdog's read returns end-of-file exactly when the launcher is gone, however it died. The watchdog also ignores the signals the launcher forwards, and every `fork` checks for failure. A spec drives the launcher directly (`perl -e fence.REAPER …`), with no fixture checkout.

## Design
`tests/lib/fence.luau`, `REAPER` (exported as `fence.REAPER` by c0077), becomes, in order:
1. `pipe(my $r, my $w) or die "pipe: $!";`
2. `my $pid = fork; die "fork: $!" unless defined $pid;`
3. **The specs' process** (`$pid == 0`):
   1. `setpgrp(0, 0);`
   2. `my $wd = fork; die "fork: $!" unless defined $wd;`. A failure dies with status 255 before `exec`, so the launcher reports 255 and the run fails with `fork: Resource temporarily unavailable` instead of hanging.
   3. **The watchdog** (`$wd == 0`): `close $w`; `$SIG{$_} = 'IGNORE' for qw(INT TERM HUP)`; stdio to `/dev/null`; `sysread($r, my $b, 1)` blocks until end-of-file (the only writer, the launcher, is gone); then `kill 'KILL', -getpgrp(); exit 0`.
   4. Otherwise: `close $r; close $w; exec { $ARGV[0] } @ARGV or die "exec: $!";`. The specs hold neither end, so they can't keep the watchdog waiting.
4. **The launcher**: `close $r;` keeps `$w` open until it exits. Then, as today: `setpgrp($pid, $pid)`; forward INT, TERM and HUP to `-$pid`; `waitpid`; `kill 'KILL', -$pid`; c0077's unlink; exit with the status (a signal death as 128+n).

When the launcher ends normally, its `kill 'KILL', -$pid` stops the watchdog too: the watchdog is in that group. No `kill 0` polling and no `getppid` remain.

### Scalability
One extra process and one pipe per run; no polling, so no wake-ups while the specs run.
### Maintainability
- `REAPER` is a string of Perl in `fence.luau`. Each step gets a one-line comment, and the spec drives it as a black box.
- The "every fork checks `defined`" rule is pinned by a static case, because a fork failure can't be forced deterministically (E1).
### Usability
- A run whose launcher is killed no longer leaves specs behind holding the lock.
- A fork failure is an immediate error with a message, not a silent hang.

## Unknowns & experiments
- **E1 (reasoned, not run)**: can a fork failure be forced for the inner fork only? `ulimit -u` applies to the whole user, so the outer fork, or the spec's own process starts, fail first. Not deterministic. The case is pinned statically instead: every `fork` in `REAPER` is followed by `unless defined`, and no `if (!fork)` remains. The reviewer judges this row by reading.
- **E2 (executor, Phase 1)**: does `pgrep -g <pgid>` work on the ubuntu runner, and inside the macOS jail? macOS: `pgrep -P` worked inside the jail in prep (raft E4), and `-g` is the same tool. Ubuntu: procps `pgrep` supports `-g`. Fallback: the "nothing behind" case checks the command's own background pid instead of the group.
  - Result (2026-10-05, executor): macOS: `pgrep -g <pgid>` lists the group's processes. Ubuntu: procps `pgrep -g` takes a process group id; the watchdog spec runs on the CI runner once promoted by `done`, so CI on the final head is the proof. The fallback stays available.
- **E3 (reasoned)**: does closing the write end in every process except the launcher make the watchdog's `sysread` return 0 exactly when the launcher dies? Yes: a pipe's read end sees EOF once every write descriptor is closed, and the kernel closes a dead process's descriptors. Perl opens pipe descriptors close-on-exec, so even without the explicit `close` the specs would not hold `$w` past `exec`.
- **E4 (mutation check, run in prep)**: does the spec catch today's watchdog?
  - Today's REAPER, merely exported, fails exactly the two defects: "the watchdog outlives INT, TERM and HUP…" (the forwarded TERM killed it, so the command survived the launcher's death) and the static case.
  - The designed REAPER passes 6/6. `c0058/lock`, `fence-leftovers` and `run-guard-relaunch` pass with it (12 cases).
  - A no-watchdog mutant fails the kill case.
  - Prototype: `.worktree/proto-r0260`, not landed.
- **E5 (run in prep, after design review 001 F5)**: is the launcher's end order pinned now?
  - The reviewer showed that deleting the group kill still passes the behaviour cases: the watchdog cleans up anyway.
  - The static order case now catches that mutant.

## Acceptance criteria

### Checked
- AC1: when the launcher is SIGKILLed, the command it ran is gone within 3 seconds.
- AC2: after the launcher has forwarded INT, TERM and HUP (the command ignoring them), killing the launcher still stops the command within 3 seconds.
- AC3: a normal end exits with the command's status, and no process of its group is left.
- AC4: every `fork` in `REAPER` checks `defined`; the watchdog waits on a pipe (`sysread`), not by polling a pid; and after the specs end, the source runs `waitpid`, the group kill, c0077's unlink and `exit`, in that order.
