# c0080: Fixes to review findings are checked for their consequences

## Problem
When an executor answers a code review, nothing asks it to think one step past each fix. R0021 showed the cost: several later findings were consequences of the previous round's fixes, made quickly and never thought through:
- blocking all network access also blocked the loopback that local test servers use (review 002 F2);
- clearing a stale `.cache/.git` added an `rm -rf` that could follow a symlink into the shared `.git` (review 004 F1);
- reaping by an environment token assumed `ps -E`, which current macOS doesn't support (found by hand in round 5).

Ticket-prep already requires a consequence step before a design fix; execute-raft's answer-the-review step doesn't. And when two rounds found holes in the same mechanism (the jail's deny-list), nobody stopped to question the mechanism itself; it was patched hole by hole until it became an allowlist.

The user asked for these changes to execute-raft (2026-10-04), after asking whether reviews were told to do this kind of second-order thinking.

## Non-goals
- How many review rounds a raft gets: c0071 (R0025, "Up to five review rounds, prefer three") edits the same skills. Whichever lands second merges the text; neither pins the other's wording.
- The reviewer's own Consequences field, which the review skill already requires.
- Design-review refute files (`design-refute-NNN.md`): ticket-prep already requires `consequences:` there. Enforcing it in `status prepared` is a separate change.

## Solution
- Execute-raft's answer to each finding carries its consequences, and `tracker.sh done` refuses a `fixed` answer without them, as it already refuses an unanswered finding.
- The reviewer of round 2 and later reviews the previous round's fixes as a delta, one step further.
- Both skills say to question a mechanism, rather than patch it again, once two rounds have found holes in it.
- The executor runs the full gate before every review round.

## Design
### `scripts/tracker/main.luau`, `reviewProblem`
For each finding of the latest `review-NNN.md` whose refute line starts with `fixed`, the line must also match `consequences:%s*%S`, case-sensitive, anywhere after `fixed`. A line that doesn't adds `<Fn>: a fixed answer needs "; consequences: <what the fix could break, and how that was checked, or none>"` to the `invalid` list. The message is `refute-NNN.md: …`, as for invalid deferrals. `refuted` and `deferred` answers are unchanged. An `approve` verdict with no findings needs no refute file, as today.

### `.claude/skills/execute-raft/SKILL.md`, Phase 4
- **Step 1** ("Before launching") gains: run `scripts/check.sh --full` and read the whole lint summary (the `errors`/`warnings` lines, never just the last line). A red gate is fixed before a reviewer is launched.
- **Step 4**'s fixed format becomes `- F3: fixed <short sha>: <what changed>; consequences: <what the fix could break or open, and how you checked it, or none>`. Plus one sentence: before each fix, take it one step further, as ticket-prep's consequence step does; `tracker.sh done` refuses a fixed answer without `consequences:`.
- **New step 4a**: when a finding is the second in two rounds against the same mechanism (the same guard, module or rule), stop patching. Before the next round, question the mechanism (a deny-list or an allowlist? a patch or a redesign?) and say which you chose, and why, in the refute file.

### `.claude/skills/review/SKILL.md`, Code mode
- **A new item**: on a re-review round, review the fix delta as well as the whole diff. `git diff <the previous review's commit>..HEAD` (the commit that added the previous `review-NNN.md`). For each fix, what new behaviour does it add, and what does that break or open? A defect in a fix is a finding like any other.
- **The re-review paragraph** gains one sentence: if this round finds a hole in a mechanism a previous round already found one in, the Recommendation questions the mechanism, not just the hole.

### Scalability
One more pattern per answered finding, at `done`.
### Maintainability
- The rule sits next to the existing deferral rules in `reviewProblem`, with the same message style.
- The skill edits are in the steps an executor already follows, not a new section.
### Usability
- `done` names each answer that lacks its consequences, so the executor knows exactly what to add.
