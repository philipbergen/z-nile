# c0103: Narrow key map

## Problem
The promoted key-map spec (`tests/acceptance/f0014/keys.spec.luau`) must allow later actions beside the movement keys, so new actions can be added without turning main red. The new actions are a jump key (Space), a fire key (E) and arrow-key look, which f0104 binds; f0104 also retires the snap-look key (Space today) and turns the arrow keys from turn intents into look.

## Non-goals
- Binding the new keys or changing the arrow keys (f0104). This chore only makes the spec tolerant, so f0104 and the actions it binds land without a red main.

## Solution
Narrow the spec to the keys that stay (W, A, S and D as `Forward`, `Left`, `Right`, `Back`) and let any other key map to an action it does not check; keep the checks that other keys do nothing and that every mapped action is a name. `View.snap` and the promoted `f0014/look.spec` stay as they are: f0104 removes the snap-look *key* only, and the arrow springback may reuse `View.snap` (decided in design review 001 F3).

## Design
### What f0104 will do to `keys.spec`, case by case
f0104 (R0035) rebinds the keys: the arrow keys become look actions (not turn intents), Space becomes the jump (not snap), E fires, and the snap-look key goes away. Against `tests/acceptance/f0014/keys.spec.luau` (written for the nine-key map), prototype E2 applies that map to `View.KEYS` and runs the spec as it is on `main`: all three cases fail.

| case | after f0104 | change here |
|---|---|---|
| maps WASD and the arrow keys to intents, and Space to snap | `Up`, `Down`, `Left`, `Right` and `Space` map elsewhere; the map has more than nine keys | keep W, A, S and D (`Forward`, `Left`, `Right`, `Back`); drop the other five rows; the count `toBe(9)` becomes `n >= 4`; rename "maps W, A, S and D to the movement intents" |
| other keys do nothing | `E` is bound | drop `Q` and `E` from the list (both are free for later actions); keep `w` (case matters), `Return` (Flow's key, not a movement key), `LeftShift` (a modifier that no feature binds) and the empty string |
| every action is a movement intent or Snap | jump, fire and look are not intents | every mapped action is a non-empty string, and W, A, S and D map to movement intents; rename "every mapped action is a name, and W, A, S and D map to movement intents" |

The header gains `Narrowed by c0103: …`, saying what is no longer pinned and why. `tests/unit/View/view.spec.luau` (frozen map) and `f0014/place.spec` (the client wiring: `Controls` requires `View`) need nothing.

**What f0104 must leave alone** (design review 001 F3, F4): `View.snap` (pinned by `f0014/look.spec`, AC4) and the narrowed `keys.spec` itself. f0104 rebinds `View.KEYS` and `Controls` (and touches `Camera` and `View` for look) and changes no promoted spec in the key map's area; if it needed to edit `keys.spec` again it would have to narrow `narrowed.spec` too, so it must not.

Nothing in `src/` changes. `View.KEYS` and `Controls` stay exactly as they are; this chore only makes the promoted spec tolerant.

### Scalability
No runtime change. The spec is an in-process Logic check (under 0.1 s).

### What the narrowed spec limits f0104 to
`View.action(key)` and `View.KEYS` stay (a table of key name to action; `view.spec` checks it is frozen, and that spec is f0104's to keep passing); every value is a non-empty string; `W`, `A`, `S` and `D` keep `Forward`, `Left`, `Right` and `Back` (movement intents); and `w`, `Return`, `LeftShift` and `""` stay unbound. Any other key may be bound or not.

### Maintainability
The spec pins what is stable (the four movement keys, that unbound keys stay unbound, the shape of the map) and leaves the rest of the map to whichever feature owns a key. The header line says so, so nobody restores the deleted rows. `narrowed.spec` reads the spec as text, so only `--full` runs it; its header says any later change to `keys.spec` must update it (the same arrangement as c0063).

### Usability
Developer: f0104 changes the key map without editing a promoted spec, which the gate never lets an executor do.

### Touched modules
- `tests/acceptance/f0014/keys.spec.luau`

### Affected specs
`lune run scripts/affected -- tests/acceptance/f0014/keys.spec.luau` prints `keys.spec` itself only; the other f0014 specs and `tests/unit/View/view.spec.luau` are listed under Regression guard. New: `tracker/issues/c0103/acceptance/narrowed.spec.luau`.

## Unknowns & experiments
- **E1 (run in prep: PASS)**: the narrowed spec (`experiments/narrowing.patch`, 10 lines changed) passes on current `main`: 3 cases in `keys.spec` and 9 cases with `view.spec`.
- **E2 (run in prep: PASS)**: with `View.KEYS` rewritten to f0104's map (arrows to look actions, Space to `Jump`, `E` to `Fire`, `Action` widened to `string`) the narrowed `keys.spec` and `view.spec` pass (9 cases), and the spec as on `main` fails all three of its cases. So exactly this narrowing is enough for f0104 to land, and none more is needed.
- **E3 (mutation check, run)**: `narrowed.spec` pins the narrowed `keys.spec` token for token (exactly three tolerances: whitespace is collapsed, a trailing comma before `}` is dropped so a `stylua` reflow of a table passes, and item ids are masked; comments are pinned too, so no code can hide in one) and fails on an assertion for each of these mutants of it, numbered as in design reviews 001 to 003:
  - rows and counts: the `Space` row kept (M1); the count back at `toBe(9)` (M2); `E` asserted unbound again (M3); the `W` row dropped (M5); the `Up` row kept (M7); a `["Left"] = ...` key row (M12);
  - weak assertions: W/A/S/D weakened to `~= nil` (M8); the unbound-keys check replaced by `t.expect(true)` (M9); the empty string dropped from the unbound list (M10); `isIntent(...) or true` (M11);
  - emptied or faked feeds: case 3's W/A/S/D list emptied (M13); case 3's `View.KEYS` loop over `{}` (M14); case 1's `want` loop over `{}` (M15); the key count faked with `local n = 4` (M16); the unbound list left as a dead local with its loop over `{}` (M17);
  - stubs: `Movement` required from another module (M18); `View` required from another module (M19); an extra case added (M20);
  - hiding code as a comment (design reviews 004 and 005): a loop inside `--[[ … --]]` (M21); a case name that is a string opening a long comment around a stub (M22); a line comment opening one (M23); an early `do return t.spec(…) end` (M24).
  (M4, M6 and M18 of the earlier numbering were a case emptied, a case deleted and a case wrapped in `if false`; the golden text catches all three.) A `want` table reflowed to one line by `stylua` still passes. The spec also builds its `require` text by concatenation, because the static scanner reads a literal one in a string as a real require (design review 003 F1; `promote-check R0036` is OK).
