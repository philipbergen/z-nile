# c0107: Board lists rafts and issues by readiness

## Problem
The person using the tracker board cannot see what to do next. The work lists are Active, Waiting, and Done. Waiting shows only rafts with nothing unfinished in front of them, and an issue appears only inside its raft. Ready and not-ready work are not separate groups, and they are not color-coded. A raft row does not say whether that raft is a feature, a defect, a chore, or a mix of those. A row does not offer the command that takes the next step, and there is no copy control that puts that command on the clipboard.

## Non-goals
- Changing what `ready`, `launch-raft`, `ticket-prep`, or `done` do.
- Changing `scripts/tracker.sh new raft`, which still refuses a raft whose members are not all one type. `mix` is a label for a tree whose issue types differ.
- The Stats charts. They stay a separate section, not a work list.
- The Actions artifact that publishes the board. `.github/workflows/board.yml` stays.

## Solution
- Two work lists, Rafts and Issues, instead of browsing only by Active and Waiting.
- Each list splits into ready and not ready, with a clear color for each. Done stays as a third group, grey, so finished work remains findable.
- Every raft shows its type from its issues. All one type shows feature, defect, or chore. More than one type shows a mix. The type stays readable beside the ready and not-ready color.
- A raft is ready when prep has merged (`design: ready`, status `prepared`). Its copy command is `/ready-raft <id>`. A readied raft's copy command is `/launch-raft <id>`.
- An issue with no raft is not ready to execute. Its copy command is `/ticket-prep <id>`. An issue already in a raft copies that raft's next command.
- Each row that has a command has a copy icon. Activating it writes that command to the clipboard. A draft, a review, and a finished item have no icon, because no command was named for them.

## Design
The whole-raft design in `tracker/rafts/R0038/R0038.md` is the contract. This issue is that contract.

`board.collect` (in `scripts/tracker/board.luau`) is the pure half: it reads a tracker directory and returns the model. `scripts/tracker/board.html` is the view. There is no Roblox adapter and no server. `board.luau` requires `./status` and calls `status.effective`. It does not parse stamps itself.

Raft bucket and command, after the directory checks in the raft document: a backlog raft is Ready only when `design == "ready"` and `status.effective(front, state) == "prepared"`. A missing stamp with `design: ready` is prepared. A backlog stamp that parses as `active` is not.

Issue bucket and command: `done` → done, nil. Otherwise, if `issue.raft` names a collected raft whose bucket is `ready`, the issue is `ready` and copies that command. Any other raft, including a done raft, leaves the issue `not` with no command. No raft → `not` and `"/ticket-prep " .. id`.

`stage` on a raft and on an issue is `status.effective(front, state)`. `status` stays `statusOf`, so the c0042 status assertions keep passing. The badge renders `stage`.

Raft `label`: the set of member types that are `feature`, `defect` or `chore`. Empty set → `raft.type`. One member → that type. More → `"mix"`. Do not write the label back into `type`.

`views.rafts` and `views.issues` each hold `ready`, `not` and `done` arrays of ids, sorted, each id in exactly one array. `initialView` is `"rafts"` even when Ready is empty. `tabs` and `initialTab` are absent. `home[id] == id`. No raft id contains `none:`. `pseudo` is false. A raftless issue's `dependents` lists the rafts that have a member whose `depends_on` names it, sorted, including when the issue is done. `blockedBy` stays unfinished-only. `topLevel` is unchanged, and a non-empty `blockedBy` does not remove the raft from `views`.

The page script reads `model.views`, `model.initialView`, `label`, `stage` and `command`. It does not recompute the buckets or the commands. A model whose `views` and `command` contradict `stage` still renders those `views` and those commands. Nav buttons are `#tab-rafts` and `#tab-issues`. Row classes are the bucket (`row ready`, `row not` or `row done`), plus `sel` on the selected row. They are not derived from `status` or `stage`. The type span is `class="type t-<label>"` and its text is the label. Every badge (list row, pane `<h2>`, and `idLink`) is `badge(stage)`. `stage` is never the word `ready`. An active raft is `class="row ready"` and badge `s-active`. A backlog raft that is still preparing badges `preparing` even though `status` is `ready`.

Exact stylesheet lines, so the type word cannot be the same paint as the readiness bar:

```css
#list li.row.ready { box-shadow: inset 4px 0 #22c55e; }
#list li.row.not { box-shadow: inset 4px 0 #f59e0b; }
#list li.row.done { box-shadow: inset 4px 0 #9ca3af; }
.t-feature { color: var(--ser-feature); }
.t-defect { color: var(--ser-defect); }
.t-chore { color: var(--ser-chore); }
.t-mix { color: #7c3aed; }
.copy.copied { outline: 2px solid #22c55e; }
.s-prepared { background: #22c55e33; }
.s-preparing { background: #f59e0b33; }
.s-new { background: #d1d5db33; }
```

Delete `.s-ready`, `.s-reviewed` and `.s-draft`. Keep `.s-done` and `.s-active`.

Group headings are `<li class="group">Ready</li>`, `<li class="group">Not ready</li>`, `<li class="group">Done</li>`, omitted when that array is empty. The copy control is a `<button type="button" class="copy">` with `data-command`, `aria-label="Copy <command>"` and an inline svg. The list handler handles `button.copy` and returns before it selects `li.row`. A missing `navigator.clipboard` returns without throwing. Otherwise it handles the Promise `writeText` returns so a rejection is not unhandled. Success marks that same button `copied` (`aria-label` `Copied`). A rejection does nothing and shows no extra state. A later re-render clears the mark.

A raft pane still builds Waiting for, Depends on and Dependents from the raft. An issue pane is the heading `<h2><span class="id">ISSUE</span>`, the meta, a jump `data-id` to `issue.raft` when that is set, then Depends on and Dependents (empty groups omitted, same `idLink` as a raft), then Document. Search selects that row in the view that contains the id.

The skill edit is the sentence in the raft's Whole-raft design. Leave `board.yml`, `tracker-board`, `gh run download` and `rm -rf .cache/board-ci` on that row.

### Scalability
`collect` is one pass over the tracker files plus the sorts it already does. The page paints a few hundred rows when the view changes. Nothing runs per frame, and nothing is replicated. The board is a local HTML file.

### Maintainability
The next command is the `status.effective` branch in `board.luau`. The page only reads `command`, `views` and `stage`. A new issue type that should count toward `label` is one more entry in the existing type set. Stats, marked and the chart module stay behind the same `board.render` placeholders.

### Usability
Ready is a green bar, not-ready an amber bar, done a grey bar. The type word is blue, orange, green or purple, so a chore's green word is not the ready bar. The copy button sits on the row that has a next step. Search, `/`, and the Stats button stay where they are.
