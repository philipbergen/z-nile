# c0114: Move the tracker into z-nile

## Problem
The tracker, its build, and the skills live in the same tree as the game. A second game would share that tracker's issue folders. A developer opening the repo cannot tell the tooling project from pickman.

The tracker engine, the skills, and the build that runs them move under `z-nile/`. That project has its own issues in `z-nile/tracker/`. Pickman's issues stay in the root `tracker/`. `z-nile/projects.toml` lists the projects that get a board tab. A directory that is not listed is not a project.

Decided with the user (2026-10-20):
- Each project holds its own issues in its own `.tracker/`. z-nile's are in `z-nile/.tracker/`; pickman's move to `pickman/.tracker/` in c0120.
- One shared id counter for every project, so a bare id stays unique across the repo and `find` searches every project root.
- The command is `./zn <cmd>` at the repo root, a shim to the engine in `z-nile/`. `scripts/tracker.sh` goes away.
- The work lands as sequenced rafts, one PR each: c0114, c0120, c0115, c0116, c0117, c0118.

### 2. The project registry: `z-nile/projects.toml`
```toml
# The projects in this repository (c0114). Each one keeps its issues and rafts in its own tracker root and gets a
# board tab. A directory that is not listed here is not a project. Read by z-nile/engine/projects.luau; the publish
# guard reads this file from origin/main only.
#   name: lowercase words joined by hyphens, unique
#   root: "<name>/.tracker", or "tracker" (pickman's until c0120 moves it to pickman/.tracker)
# A command works in --project's project, else in the one whose folder holds the directory ./zn runs in; pickman has
# no folder until c0120, so its work passes --project pickman.
# `retired` lists roots that once held items and hold none now; history and the trail still read them.
retired = []

[[project]]
name = "pickman"
root = "tracker"

[[project]]
name = "z-nile"
root = "z-nile/.tracker"
```
`z-nile/engine/projects.luau` is its one reader (lesson architecture/one-reader-per-format):
```lua
export type Project = { name: string, root: string }
export type Registry = { projects: { Project }, retired: { string } }
projects.FILE = "z-nile/projects.toml"
projects.LEGACY = "tracker"
projects.parse(text: string): (Registry?, string?)      -- pure; nil and the first problem
projects.shapeOk(root: string): boolean                  -- "tracker" or "<name>/.tracker"
projects.roots(reg): { string }                          -- current roots, in file order
projects.allRoots(reg): { string }                       -- current, then retired (history readers only)
projects.rootOf(path: string, roots: { string }): (string?, string?) -- root and rest, by whole segments
projects.named(reg, name): Project?;  projects.projectOf(reg, root): Project?
projects.folderOf(root: string): string?                 -- "z-nile" for "z-nile/.tracker"; nil for "tracker"
projects.inDir(reg, dir: string): Project?               -- the project whose folder holds dir (relative to the checkout)
projects.load(dir: string?, fresh: boolean?): Registry   -- the working tree's (cached per dir; fresh rereads); raises without the file
projects.at(rev: string, cwd: string?): (Registry?, string?) -- the registry at a commit; nil and why without the file
```
Rules (`parse`, lesson architecture/parsers-refuse-ambiguity): TOML through `serde.decode("toml")`, which already refuses a repeated key; top-level keys only `project` and `retired`; at least one `[[project]]`; each project has exactly `name` and `root`; a name is lowercase words joined by single hyphens; a root is `"<name>/.tracker"` (its own name) or the legacy `"tracker"`, nothing else (not `src`, `.`, `..`, an absolute path, `z-nile/tracker`, another project's folder or anything deeper); names and roots are unique; `retired` holds roots of the same two shapes, none of them current. Every refusal names the file and the rule.

**Decided with the user (2026-10-21):** "Missing also refuses". A tree or a commit with no registry is refused like one whose registry does not parse (fail closed): `load` raises ("no z-nile/projects.toml in <dir>: the tracker refuses to guess the project roots"), `at` returns nil and "<rev> has no z-nile/projects.toml", `publish.commit` refuses and pushes nothing ("origin/main has no z-nile/projects.toml (c0114 has not landed): publish from the main checkout until it does"), `audit` reports `error registry`, and every command that reads roots (sweep after a pull, worktree-prune, lessons, capture's scope) refuses instead of guessing. Nothing falls back to the old single root any more: `projects.legacy()` is gone, and `audit.scan` (which `list`, offline numbering and `remap` read through), `claims.taken`, `publish.allowed` and `trail.dirs` take their roots from the caller with no default; `audit.scan` raises without a registry. The one listed exception is `history.LOG_ARGS` and `history.parse(log)`'s default: a parser of a log it is handed, kept for its old callers (§6), which decides nothing about a live tree. Consequences:
- **Old worktrees are unaffected.** A worktree cut before c0114 runs its own engine (`scripts/tracker.sh` there is the old engine), which never reads a registry.
- **The execution window.** Until c0114 lands, origin/main has no registry, so the branch's engine publishes nothing: every capture, status change, claim, spend and emergent issue in that time is made from the main checkout, whose engine predates c0114 and keeps numbering on `tracker/next` (§5, §11). Local reads on the branch (`find`, `list`, `members`, `audit`, the gate) work, because the branch has the registry.
- **Fixtures.** Every fixture that runs the engine carries the registry: `engine.copy` copies it, and hand-built trees write it with the new `engine.registry(dir)` (§ Overrides).

**Decided with the user (2026-10-21):** "The directory gives the project unless it's given, so at root without project=fail, deduce from PWD with --project override". So:
- `--project <name>` always wins.
- Otherwise the project is the one whose folder holds the directory `./zn` is run from (`projects.inDir`): `z-nile/` and everything below it is z-nile's. A project's folder is its root's parent, so the legacy root `tracker` gives pickman no folder.
- At the checkout's root, or anywhere no project folder holds (`src/`, `tests/`, `tracker/`), a command that needs a project refuses and names `--project`: "new issue: no project holds the checkout's root: run it in a project's folder or pass --project <name> (pickman, z-nile); pickman has no folder until c0120, so its work passes --project pickman".
- The commands that need a project are `new issue` and `new raft`; `new raft` also refuses a member outside that project ("the raft is made in <root>: <id> is in <root>"). An emergent issue's raft gives its project, as before (`--project` naming another one is refused).
- **Decided with the user (2026-10-21):** "list shows all projects". The rule: at the checkout's root, or in a folder no project holds, only the commands that create an item, and so must choose its project (`new issue`, `new raft`), refuse; every other command runs there as before: read-only ones read every project, and the commands that change existing items (`status`, `ready`, `stop`, `done`, `spend`, `renumber`) take the project from the item. So `list` takes the same choice to show one project (`--project`, or the folder's), and at the root it lists every project; the skills and step 9 run `./zn list` there.
- **Consequence until c0120:** pickman has no folder, so outside `z-nile/` game work always passes `--project pickman` (make-issue and the tracker skill say so); c0120 gives pickman `pickman/`, and the directory then chooses it too.
- `zn` passes the directory: it exports `ZN_TOP` (the checkout, `pwd -P`) and `ZN_CWD` (the calling directory relative to it, "" outside it) before it `cd`s to the root. The engine trusts `ZN_CWD` only when it runs in `ZN_TOP`, so a value inherited by a spec's fixture reads as that fixture's root.
- Every skill, template and spec that captured without a flag now names the project: make-issue's step 2, the tracker skill's Projects bullet and postponed issues, ticket-prep's `new raft`, testing's two capture lines, execute-raft's deferral line, every skill's lesson-capture line (`--project z-nile`), the prompt template, and the promoted specs listed under Overrides (`--project pickman`, their items being pickman's).

The registry carries only `name` and `root` now. c0120 adds pickman's other paths (gate, Rojo projects, runtime-test folder, architecture document) when it moves them; c0120 then only changes pickman's `root` to `pickman/.tracker` and adds `"tracker"` to `retired`.

### 3. The command and the forwarders
`zn` (mode 100755):
```bash
#!/usr/bin/env bash
# z-nile's command (c0114): ./zn <command> ... from anywhere in the checkout. See .claude/skills/tracker/SKILL.md.
# The directory it is run from gives the project (a command's --project overrides it): ZN_CWD is that directory
# relative to the checkout, and ZN_TOP the checkout, so the engine trusts ZN_CWD only when it runs in ZN_TOP.
set -euo pipefail
top="$(cd "$(dirname "$0")" && pwd -P)"
here="$(pwd -P)"
case "$here/" in
"$top/"*) rel="${here#"$top"}" ;;
*) rel="" ;; # outside the checkout: like its root
esac
export ZN_TOP="$top" ZN_CWD="${rel#/}"
cd "$top"
export PATH="$HOME/.rokit/bin:$PATH"
exec lune run z-nile/engine/main -- "$@"
```
The forwarders. Each is one command and keeps its old path's mode; `exec bash` so a copy that lost its executable bit (spec fixtures copy files with `writeFile`) still runs:

| path | its one command |
|---|---|
| `scripts/tracker.sh` | `exec bash "$(dirname "$0")/../zn" "$@"` |
| `scripts/check.sh` | `exec bash "$(dirname "$0")/../z-nile/check.sh" "$@"` |
| `scripts/setup.sh` | `exec bash "$(dirname "$0")/../z-nile/setup.sh" "$@"` |
| `scripts/ci-verify.sh` | `exec bash "$(dirname "$0")/../z-nile/ci-verify.sh" "$@"` |
| `scripts/lib/ac.sh` | `source "$(dirname "${BASH_SOURCE[0]}")/../../z-nile/lib/ac.sh" \|\| { echo "ac.sh: z-nile/lib/ac.sh is missing" >&2; exit 1; }` |
| `scripts/affected.luau` | runs `lune run z-nile/affected -- <args>` with inherited stdio and exits with its code |
| `scripts/tracker/<m>.luau`, one per engine module but `main` (18) | `local m = require("../../z-nile/engine/<m>")`, one `export type X = m.X` per exported type, `return m` |
| `scripts/lib/{sh,graph,changed}.luau` | the same, onto `z-nile/lib/<m>` |

The real `ac.sh` keeps working from either path because it `cd`s to `$(dirname BASH_SOURCE)/../..`, two levels up, which is the repository root from both `scripts/lib/` and `z-nile/lib/`.

### 4. Every command across the roots
Two sources of roots, never mixed up:
- **The working tree's registry** (`projects.load()`, through `store.roots()`) for local reads and local writes: finding, listing, moving folders in the checkout.
- **origin/main's registry** (`projects.at("origin/main")`, read with git, never from the working tree) for everything published and every read of origin's tree. A root that only the working tree lists is never written to origin (lesson architecture/guards-trust-only-origin).

| command or module | root rule (c0114) | pinned by |
|---|---|---|
| `store.find/get/all/members` | every root of the working tree's registry; one id in two folders, in one root or across two, is `duplicate id <id>: <dirs>`; `Item` gains `root` | AC3 find/list/members, duplicate |
| `store.dirFor(kind, state, id, root)`, `store.kindDir(kind, root)` | the item's own root; `store.ROOT` is gone | AC3 ready, renumber |
| `publish.commit` | reads `z-nile/projects.toml` at the fetched base; no file or a bad file: refuses and pushes nothing (G4); lists origin's files under those roots and the live counter (§5); passes the roots to the build as a third argument; moves the counter at the first publish after landing (§5) | AC4, AC13 |
| `publish.allowed(path, roots, counter?)` (roots required, no default) | an item's `<ID>.md`, `check.sh` or an issue's `spend.md` under one of `roots`, or the live counter; the other counter file is never allowed from a build (the migration's tombstone is added by `publish.commit` itself, §5) | AC4 allowed, AC13 |

### 5. The shared counter
The counter's home becomes `z-nile/next`, which no later move touches (c0120 moves `tracker/`, never `z-nile/`). Same format, same rules (`ids.FILE = "z-nile/next"`, `ids.OLD_FILE = "tracker/next"`). **The branch never touches `tracker/next`**: main's engines raise it with every capture and new raft (16 times on 2026-10-20), so any branch edit of it would conflict at every merge of main, the PR's own merge after `done` included (design review 003 F1). The PR leaves it byte for byte as main has it, and adds no `z-nile/next`. Origin moves the counter once, after the landing.

Which file is the live counter is decided from the base the publish fetched, never the working tree, by `publish.counterOf(hasNew, oldText)`, for a base with the registry (`publish.commit` refuses one without it first):
- the base has `z-nile/next`: that is the counter;
- the base has no `z-nile/projects.toml` (main before c0114 lands, c0114's own execution included): `tracker/next` is the counter, and only the main checkout's engine, which predates c0114, numbers on it. The branch's engine publishes nothing there (G4), so it reserves no id: `new issue`, an emergent issue, `new raft`, `renumber` and `remap` all refuse on the branch. A merge of main is a plain merge: the branch never changed the file. `publish.counterOf` therefore takes only bases with the registry;
- the base has the registry but no `z-nile/next`, and `tracker/next` parses (c0114 has just landed): `z-nile/next` is the counter and this publish **moves it**. In its one commit and lease push it writes `z-nile/next` with `tracker/next`'s counters (raised, if the publish reserves a number; the go-up check compares against them) and the tombstone at `tracker/next`:
```
moved to z-nile/next (c0114): this file never parses, so a tracker engine from before the move refuses to number
```
  A lost lease (an old engine raised `tracker/next` meanwhile) retries on the new tip, as every publish does, and moves the raised counters. Execute-raft Phase 6 step 2's `./zn spend R0043 --phase deliver` is the first publish after the merge, so the move happens minutes after landing; until then old engines keep numbering on `tracker/next`, which is still the live counter.

`publish.commit` lists, allows and checks (it may only go up) the live counter alone and passes it to the build as its fourth argument; `reserve` reads and raises it. `publish.allowed(path, roots, counter)` allows exactly `counter` and refuses the other counter file, so no build ever writes `tracker/next` after the move: neither a counter, nor the tombstone again, nor a fresh file where c0120 has removed it. Locally, `localCounters` (offline numbering) and `audit` read `z-nile/next` when the tree has it, else `tracker/next`. `audit` reports `error old-counter` when both parse (an old engine would number from the old one) and `warning counter-unmigrated` for the state between the landing and the first publish. A compaction in a tree whose counter has not moved writes `z-nile/next` and the tombstone together.

After the move an engine from before c0114 (a worktree cut before it) reads `tracker/next` on origin, cannot parse it, and refuses `new issue`, `new raft` and `renumber` with "tracker/next on origin/main does not parse" (E5: run; still true, because the tombstone is the same text, written by the first publish instead of by the PR). Its other commands only find items under `tracker/`, so on a tooling item they say "<id> is not on origin/main". c0120 keeps the tombstone (a file, not an item folder) when it moves pickman's items.

### 6. The compaction map and history across roots
