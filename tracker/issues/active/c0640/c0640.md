# c0640: Checks never touch the real repository

## Problem
On 2026-09-30 a test run broke the shared git repository for every session.

While executing R0140, an agent ran two `lune run tests/run -- --jobs 8` suites at once in its one worktree. Both suites use the same `.cache/<name>` fixture directories, so one deleted the other's fixture clones mid-run. Every fixture lives under `<worktree>/.cache/`, inside the real worktree. When a fixture's own `.git` vanished, git searched upward, found the real worktree, and the fixture's commands ran against the real repository:
- `git remote remove origin` deleted `origin`, every `refs/remotes/origin/*` and all branch tracking, for every worktree and session;
- `git config user.*` changed the shared identity;
- the R0140 worktree was switched to a fixture branch, `collide-a`, and the agent's uncommitted work was committed there;
- fixture branches and a fixture worktree were registered in the real repository.

On 2026-10-01, while this issue was being prepared, it happened again. Its own acceptance spec, run against the runner that doesn't have these guards yet, had a setup that failed before `git init`. The later cases then ran git against the prep worktree: they wrote `user.email=e2e@example.invalid` into the shared config (every later commit, in every worktree, was authored as a fixture), committed twice onto the prep branch, and created `refs/heads/leaked`. Both incidents were repaired at the user's go-ahead.

The user's requirement: **there must not be a way that any check ever breaks the main git repository, and that must be clear in the review and skill definitions.**

## Non-goals
- A jail on Linux: CI's checkout is disposable, and the environment guards still apply there (see "Caught only by review").
- Jailing `check.sh` files: they legitimately write the checkout (`sourcemap.json`, `promote-check`) and talk to GitHub (`scripts/ci-verify.sh`). The specs they start are jailed.
- Moving fixtures out of `.cache`: with the jail, a broken fixture can't write the repository, and the fence makes git fail instead of reading it.
- Making fixture directories unique per run: the lock serialises runs instead.

## Solution
- **A jail (macOS)**: every spec runs under `sandbox-exec` with a profile that denies, at kernel level, every write to the checkout, its main checkout and their shared git directory, except the checkout's `.cache`. It doesn't matter how a spec got there: discovery from a broken fixture, an inherited `GIT_DIR`, `-C <root>`, `reset --hard`, a config write or a plain file write.
- **Environment guards** (`scripts/lib/fence.sh`), for spec runs and, through `ac.sh`, for `check.sh` files:
  - the fence;
  - override stripping;
  - a ref guard and a push guard, as git hooks;
  - for specs only: no GitHub credentials, and no network pushes.
- **Run guards** (`tests/lib/fence.luau`):
  - a per-checkout lock;
  - a fixture-identity precondition;
  - a tripwire.
- **A gate spec** proves in every run that all of it is on, the jail included, and that nothing bypasses it.
- **The rule, precisely**, in AGENTS.md and the testing, review, execute-raft and ticket-prep skills: what is protected, what is enforced at run time, what only review can catch, and that specs are run against unguarded code only in a clone under `$TMPDIR`.

## Design

### Audit of every check (prep, 2026-10-01; base 01395fc)
Every spec and `check.sh` that runs git, `tracker.sh` or `gh` was listed with the commands it runs and where.
- **Fixture specs**: c0010, c0041, c0050, c0060, c0070, c0330, c0360, c0420, c0430, c0440, `tests/tooling/worktree-fetch`, the backlog c0480 and the R0180 prep specs. Each works in its own repository under `<checkout>/.cache/<unique name>`. Their git commands reach the real repository when that fixture repository is missing: the incident's hole. Clones of the root (c0010, c0050, c0070, c0360) keep the root as `origin` for a while, which is a push path.
- **Real-root commands**: c0330 ran `tracker.sh check`/`done` at the real root under `AC_LIST=1`; they now run in a fixture (Overrides).
- **Bypasses**: five specs (c0041, c0420, c0430, c0440, `worktree-fetch`) inject `gc.auto`/`maintenance.auto` through `GIT_CONFIG_COUNT`, which would replace the guard's injected config. The setting moves into the guard (Overrides). No other spec or `check.sh` names a variable that changes where git looks, and every fixture commits as `@example.invalid`.
- **`check.sh` files**: c0010's AC3 runs `scripts/ci-verify.sh` (`gh`, and a fetch at the root), so check runs keep `gh` and fetch. c0470's AC5 copies the tree without `.git` into `.cache/c0470-gate` and runs the gate there: the fence makes git in the copy fail, and the copy's own spec run is jailed.
- **No spec writes the checkout outside `.cache`**: the full gate passes jailed (E14).

### The jail (`tests/lib/fence.luau`, macOS)
A top-level run decides its jail before it takes the lock. It re-runs itself as `sandbox-exec -p <profile> bash -c '…'` when `process.os == "macos"` and a trial of **the same profile** (`sandbox-exec -p <profile> /usr/bin/true`) succeeds. The home paths are given both as written and resolved with `realpath`, because the sandbox matches resolved paths and `~/.gitconfig` may be a symlink. The profile:
```
(version 1)(allow default)
(deny file-write* (subpath "<checkout>"))
(deny file-write* (subpath "<repo>"))                 ; for <repo> in this checkout's common git dir and every
(deny file-write* (subpath "<repo without /.git>"))   ;   PICKMAN_FENCE_REAL_GIT entry (an outer guard's repositories)
(deny file-write* (literal "~/.gitconfig"))           ; the person's own git configuration
(deny file-write* (subpath "~/.config/git"))
(allow file-write* (subpath "<checkout>/.cache"))     ; the later rule wins
```
- **Inheritance**: everything the specs start inherits the jail (workers, git, `tracker.sh`, nested runs, fixtures' `check.sh`).
- **Outer guards' repositories**: they are denied too, because a copy of the tree under a checkout's `.cache` (c0470's AC5 pattern) starts its own top-level run from a `check.sh`. Its jail must cover the real checkout, not only the copy (AC9).
- **When the jail can't apply** (inside another sandbox, which macOS can't nest (E13), or without `sandbox-exec`): the run tries harmless probe writes into every protected path, and removes any probe at once.
  - **Every probe denied**: an outer sandbox already protects the repository. The run notes it and goes on: `outer sandbox (protects the repository)`.
  - **Some probe written, but it is proven to be a fixture of a jailed outer run**: the run notes it and goes on: `outer sandbox (a fixture of a guarded checkout)`. This covers the c0640 specs' own inner runs. "Proven" means all of these, from probes rather than from environment variables alone:
    - `PICKMAN_FENCE_REAL_GIT` names a repository other than this checkout's own (an outer guard exists);
    - none of those repositories, nor their checkouts, is writable from here (so an outer jail holds them);
    - the only writable protected paths are this checkout and its own git directory;
    - the checkout lies under a ceiling entry that ends in `/.cache` (a checkout's `.cache`, not any ancestor such as `$HOME`).

    A copy of the tree started from a `check.sh` (which is never jailed) fails the second condition, and an ancestor in the ceiling fails the last one (review 005 F1).
  - **Otherwise**: it refuses, before any spec runs and before taking the lock, with `cannot jail this run (…), and it could write the repository (<paths>). Run specs outside the sandbox you are in`. So an agent whose shell is sandboxed must run specs with that sandbox off (E22).
- **What the run is told**: `PICKMAN_TEST_JAIL` is `sandbox-exec`, `outer sandbox (…)`, or `none (not macOS: environment guards only)`.
- **No bypass by wrapping**: the gate scan forbids `sandbox-exec` in checks, so nothing can wrap a run in a permissive sandbox to skip the jail.

### Environment guards (`scripts/lib/fence.sh`, new)
```bash
pickman_fence <checkout> [checks|specs] [<jail>]
pickman_fence <checkout>                       # check.sh files (ac.sh): checks mode, hooks injected
pickman_fence <checkout> specs sandbox-exec    # a jailed spec run (tests/lib/fence.luau): no hooks (item 7)
pickman_fence <checkout> specs "none (…)"      # an unjailed spec run (Linux, inside an outer sandbox): hooks
```
An inherited `PICKMAN_FENCE_SPECS=1` forces specs mode. The third argument is the jail `fence.enter()` chose; only `sandbox-exec` leaves the hooks out.
After it, every git that this shell and its children run:
1. **Fence**: `GIT_CEILING_DIRECTORIES` gets `<checkout>/.cache` appended. A sentinel file `<checkout>/.cache/.git` (`gitdir: /nonexistent/pickman-fence`) makes git fail in `.cache` itself.
2. **Overrides stripped**: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_PREFIX`, `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` are unset.
3. **Ref guard**: injected config (`GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`) sets `core.hooksPath` to `scripts/lib/git-hooks`. Its `reference-transaction` hook, in the `prepared` phase, refuses every ref update in a repository listed in `PICKMAN_FENCE_REAL_GIT` (the checkout's common git dir). There is one exception, for **a fetch from a `check.sh` flow** (`PICKMAN_FENCE_SPECS` unset): at least one ref, and every ref created or moved under `refs/remotes/`, none deleted. `scripts/ci-verify.sh` needs it. Deleting a remote ref, which is what `remote rm` does, stays refused. Fixtures update their own refs freely.
4. **Push guard**: a `pre-push` hook. It runs in the pushing repository, where the injected config applies; the receiving side of a local push drops it.
   - **Checks mode**: a local URL (absolute, relative to the pushing worktree, or `file://`) is resolved to its repository, and a push into one listed in `PICKMAN_FENCE_REAL_GIT` is refused.
   - **Specs mode**: a push goes **only** into an existing local repository that isn't protected. https, ssh, `host:path` and ssh aliases are all refused, however they're spelled.
5. **No network credentials for specs** (`specs` mode, which also sets `PICKMAN_FENCE_SPECS=1`):
   - `GH_TOKEN`, `GITHUB_TOKEN`, the enterprise variants and `SSH_AUTH_SOCK` are unset;
   - `GH_CONFIG_DIR` is an empty `<checkout>/.cache/gh-none`;
   - the injected `credential.helper=` (empty) resets git's helper list, so the keychain helper named by the system gitconfig is never asked (E18);
   - `GIT_TERMINAL_PROMPT=0`;
   - `GIT_SSH_COMMAND` prints `fence: a spec tried to use ssh; refused` and fails.
7. **Hooks only where there is no jail, and they chain on**: the hook path (items 3 and 4) is injected only when the run isn't jailed: Linux, `check.sh` files, and runs nested inside a jail. Under the jail the kernel already denies every write to the protected repositories, and a hook is a process start, slow inside the sandbox: a profile put c0041 at 25 s with hooks under the jail against 12 s without (E25). Where the hooks are injected, each guard hook, after its own check, runs the repository's own hook of the same name with the same arguments and input. A stub for every other client hook name does only that, so fixtures that install hooks (c0510's specs do, E24) behave as without the guards. The hooks find the repository as git does, without starting git: `GIT_DIR` when git exports it (during a clone it names the new repository while the working directory is still the source), otherwise the working directory, following a linked worktree's `.git` file and `commondir` (`scripts/lib/git-hooks/.repo.sh`, E26).
8. **No network transport for specs** (`specs` mode, hooks or not): injected `protocol.allow=never` and `protocol.file.allow=always`. git refuses every transport but local paths and `file://` (`fatal: transport 'https' not allowed`), however the URL is spelled (`HTTPS://`), and whether it comes from a `pushurl`, an `insteadOf` alias or `host:path` (ssh). Local pushes and clones between fixtures work. A `pushInsteadOf` rewrite (round 5) was bypassed by an uppercase scheme, a `pushurl` and an alias (review 006 F3), and is gone. `GIT_SSH_COMMAND` stays as a second refusal.

**Nesting**: a guard set up inside another keeps everything the outer one set.
- The ceiling and `PICKMAN_FENCE_REAL_GIT` are appended to.
- The first hook directory (`PICKMAN_FENCE_HOOKS`) stays in force.
- A `check.sh` started from inside a spec run keeps the spec's limits, because `PICKMAN_FENCE_SPECS` is inherited. Only a check started outside any spec run (by `tracker.sh check`, for example) has the checks-mode allowances.

### Run guards (`tests/lib/fence.luau`, new; `tests/run.luau` calls `fence.enter()` right after its `AC_LIST` refusal, before parsing `--jobs`)
The call is exactly the line `require("./lib/fence").enter()`, on its own: c0660's AC4 removes that line to run specs without the guards in a clone.
```lua
function fence.enter()  -- returns at once in a guarded run; a top-level run never returns (it exits)
```
**Guarded** means `PICKMAN_TEST_FENCE` is set, the ceiling contains `<value>/.cache`, and `pwd -P` is the value itself or lies under `<value>/.cache/`. That last condition covers a fixture copy, but never another checkout below it, such as `.worktree/X` under a marker leaked from the main checkout. Any other non-empty marker prints `note: ignoring PICKMAN_TEST_FENCE=…` and counts as top-level. A guarded run (a worker, or a run started by a spec or a fixture's `check.sh`) writes `pid-<its pid>` into the lock, if the lock exists, and returns.

A **top-level** run does the following, in order:
1. **Identity precondition**: if `git config user.email` ends in `@example.invalid`, it exits 1. The message gives the value and where it comes from (`git config --show-origin`), and says `Stop and report this; do not repair the repository yourself`, the same rule as the tripwire. The tripwire tells fixture writes by their author, which only works while the repository's identity is real.
2. **Lock** `<checkout>/.cache/tests-run.lock`, created with `mkdir`. It holds `pid`, this Lune process.
   - A lock is **stale** when every pid recorded in it (`pid` and every `pid-<n>`) is dead, or when it has none after 2 s.
   - Only the holder of the mutex `<lock>.takeover` (also `mkdir`) may remove a stale lock. A mutex is cleared when its holder is dead, or when it has no pid after 2 s.
   - `PICKMAN_TEST_TAKEOVER_PAUSE` (tests only) pauses a waiter between judging and removing, so the lock spec can stage the race the mutex prevents.
   - Otherwise the run prints `waiting for another test run (pid …) in this checkout to finish` once, and polls every 0.1 s for up to `PICKMAN_TEST_LOCK_WAIT` seconds (default 240, under the Stop hook's 300 s). It then exits 1 with `another test run (pid …) is using this checkout's fixtures (…); gave up after Ns`, and no spec runs.
3. **Snapshot**, with git run through `env -u` of the override list:
   - `git config --local --get-regexp '^(remote|core|user)\.'` without `remote.*.gh-resolved` lines;
   - `git symbolic-ref -q HEAD` and `git rev-parse HEAD`;
   - the worktrees under `<checkout>/.cache/`;
   - every ref whose tip's author email ends in `@example.invalid>`.
4. **Re-run**: through the jail (macOS, when available), then `bash -c '. scripts/lib/fence.sh && pickman_fence <checkout> specs && export PICKMAN_TEST_FENCE=<checkout> PICKMAN_TEST_JAIL=<jail> && exec lune run tests/run -- <args>'`, with output forwarded.
5. **Snapshot again, release the lock, compare.** The run fails (exit 1, or the child's own non-zero code) with `REPOSITORY CHANGED during the test run …`, the before and after of each item, and `Stop and report this; do not repair the repository yourself.`, when any of these happened:
   - the config changed;
   - the branch changed;
   - HEAD moved to a commit that doesn't descend from the old one;
   - a commit in `old..new` has an `@example.invalid` author;
   - a worktree appeared under `.cache`;
   - a fixture-written ref appeared.

   Otherwise the run exits with the child's code. A commit or pull by the person or agent in the same checkout during a background run doesn't trip it.

### `check.sh` files (`scripts/lib/ac.sh`)
After its `cd` to the repo root, `ac.sh` runs `source scripts/lib/fence.sh; pickman_fence "$(pwd -P)"` (checks mode), provided the file exists. A fixture holding only `ac.sh` runs inside an already guarded spec run.

### Gate spec (`tests/tooling/repo-fence.spec.luau`, new; case names fixed by AC6)
1. `this run is guarded for this checkout`: the marker is `pwd -P`, the ceiling contains `<here>/.cache`, and `GIT_DIR`, `GIT_INDEX_FILE` and `GIT_WORK_TREE` are unset.
2. `git finds no repository in .cache, nor in a folder below it that has none`.
3. `every git this run starts refuses ref updates in this repository`: under the jail no `core.hooksPath` is set (the jail denies the writes, case 4); elsewhere it names a directory holding both guard hooks. Either way `scripts/lib/git-hooks/reference-transaction prepared` (no refs given) fails with "refused" here, and passes in a new fixture repository.
4. `on macOS this run can write nothing in the checkout outside .cache`: `PICKMAN_TEST_JAIL` is `sandbox-exec` or `outer sandbox …`, and these harmless probes must all be refused:
   - writes to untracked probe files in the checkout, in the main checkout when run from a worktree, in the common git dir, and in `~/.config/git` (any that succeeds is removed at once);
   - opening `~/.gitconfig` for appending, writing nothing.

   A write into `.cache` succeeds. A failure names every path that was writable and says to run the gate outside a permissive sandbox. Off macOS, `PICKMAN_TEST_JAIL` starts with `none`.
5. `specs have no GitHub credentials and push only into fixtures`:
   - `GH_TOKEN`, `GITHUB_TOKEN` and `SSH_AUTH_SOCK` are unset, and `GH_CONFIG_DIR` is `<here>/.cache/gh-none`;
   - the last `credential.helper` entry is empty;
   - `git ls-remote` (run outside any repository) fails with "not allowed" for `https://…`, `HTTPS://…`, `http://…`, `git://…`, `git@host:path`, `ssh://…`, and an `insteadOf` alias;
   - where hooks run, `pre-push` refuses `https://…`, `github.com:x/y.git`, `gh:x/y` and `ssh://…`.
6. `no spec, check.sh or script switches a guard off or points git elsewhere`: what runs as a check is scanned case-insensitively: every `.luau` and `.sh` and every extensionless file (hooks, tools) under `tests/` and `scripts/`, and every `check.sh` under `tracker/`. Acceptance specs prepared under `tracker/` are scanned once promoted into `tests/`, which is when they start to run. None may contain any of these, and a failure lists each file and name:
   - `GIT_CEILING_DIRECTORIES`, `PICKMAN_TEST_FENCE`, `PICKMAN_FENCE_`;
   - `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_`;
   - `hooksPath`, `--no-verify`, `env -i`, `sandbox-exec`, `GH_CONFIG_DIR`, `osascript`, `launchctl` (ways to run work outside the jail).

   (`env -u` is not listed: unsetting a guard names its variable.) Exempt, because they are the guards: `tests/lib/fence.luau`, `scripts/lib/fence.sh`, everything in `scripts/lib/git-hooks/` (the hooks and their `.repo.sh`), this spec, and c0640's own acceptance specs and `check.sh` in each lifecycle location.

   **Allowlist** (`ALLOWED: { [path]: { [name]: reason } }`): a listed file may name exactly its listed names, and is scanned for every other. Each entry gives its reason, and the review checks every entry (review skill, Repository safety). c0640 starts it with c0510's two promoted specs (R0200 lands first, so they're in `tests/acceptance/c0510/`): `GIT_DIR`, `GIT_INDEX_FILE` and `GIT_WORK_TREE` (their fixture hooks unset what git exports to a hook), and `GIT_CEILING_DIRECTORIES` (their own fence from before these guards, which c0650 removes). c0660 adds its helper and its own spec, and c0650 narrows c0510's entries and adds its own spec. The publisher needs none (c0650).
7. `every fixture commits as <name>@example.invalid`: every `user.email` address in those files ends in `@example.invalid`, with the same exemptions.

### The rule, in the documents
- `AGENTS.md`, a second non-negotiable paragraph: "**No check may ever change the real repository.**" It covers:
  - fixtures under `.cache/`;
  - the runner's enforcement, with the jail on macOS;
  - that review catches what the runner can't see (unjailed runs on Linux, `check.sh` files' own commands);
  - that if the tripwire fires, you stop and never repair the shared git configuration yourself.
- `.claude/skills/testing/SKILL.md`, a section `## Specs never touch the real repository`:
  - the two incidents;
  - **Protected** and **Allowed writers**;
  - **Fixtures** (checked before each write);
  - **Enforced at run time**: jail, fence, overrides stripped, ref guard (and what it does *not* stop on Linux), push guard and credentials, lock, tripwire and precondition, gate spec;
  - `check.sh` files;
  - **Caught only by review**: on Linux, any write to the real checkout's index or files (`git add`, `checkout`, `reset --hard`, `worktree remove`, `remote set-url`, a plain file write); `check.sh` files' own commands; work handed to a process outside the jail (`open`, `osascript`, `launchctl`, a daemon);
  - **Running specs against unguarded code** only in a clone under `$TMPDIR`;
  - **If the tripwire fires**.

  The Speed section's "Run one suite per worktree at a time" sentence becomes "Two suites in one checkout queue on the runner's lock; separate worktrees run in parallel".
- `.claude/skills/review/SKILL.md`:
  - design mode item 9 and code mode item 8, **Repository safety**: any path to the real repository, or any weakening of a guard (naming each guard file), is **high**;
  - check the "Caught only by review" list line by line.
- `.claude/skills/execute-raft/SKILL.md`, a stop condition: `REPOSITORY CHANGED`, a refused fixture identity, or wrong-looking shared remotes, branches, worktrees or identity means stop, and never repair the shared git configuration yourself.
- `.claude/skills/ticket-prep/SKILL.md`, step 4:
  - acceptance specs never change the real repository, and, when new or edited, check each fixture before each write (older specs rely on the jail; retrofitting them is a follow-up);
  - before the guards exist on a branch, or while prototyping them, they run only in a clone under `$TMPDIR`.

### Scalability
- **Per top-level run:** one extra Lune start, one `sandbox-exec`, one bash and about ten git reads, roughly 0.2 s.
- **Per fixture ref update:** one `sh` and one git, about 50 ms per commit; c0041 alone took 14.0 s guarded against 18.0 s unguarded, within noise.
- **Full gate:** 21.8 s wall, jailed and parallel (751 cases, 119 files, on `main` `9fa1499`, at load 14-24), against 19.9-24.9 s for `main` itself; c0041, the critical path, 12 s on both (E25).
- **Worktrees:** each has its own `.cache` and lock, so separate worktrees run in parallel.
### Maintainability
- **Placement:** the environment guards live in one bash file, used by both entry points; the run guards and the jail live in one Luau module.
- **Coverage:** new specs are covered without doing anything.
- **Policing:** the gate spec stops anyone switching a guard off, and both the reason (the incidents) and the boundary (enforced versus review) are written in the testing skill.
### Usability
- A second run says why it waits.
- A tripped run says exactly what changed and what to do.
- A refused ref update, push or identity says why, and (for the identity) to stop and report rather than repair.
- The jail's state is printed when it can't apply.
- Nothing else changes for a single run.

## Unknowns & experiments
All run in prep (macOS 26.6, git 2.54, Lune 0.10.5), on scratch repositories under `/tmp` or on the prototype (`proto2-c0640`, rebased onto `01395fc` with the parallel runner).
- **E1** Does git search above a fixture folder that lacks `.git`? **Yes, which is the defect.**
- **E2** Does a ceiling stop that, while fixtures with their own repository still work? **Pass**, but not for git run in `.cache` itself; the sentinel `.cache/.git` covers that.
- **E3** Does `process.env.X = …` reach children in Lune? **Fail.** So the guards are applied by re-running through bash.
- **E4** Does Lune's `env` option add to the inherited environment, or replace it? **It adds.**
- **E5** Does the injected `reference-transaction` hook refuse ref updates in the real repository and allow them in fixtures? **Pass**, at about 50 ms per commit.
- **E7** Does a Lune child survive SIGTERM to its parent, and keep the lock? **Yes.** With captured output, the parent's `process.exec` returns only when the orphan closes its output.
- **E8** Does a `GIT_CONFIG_COUNT` set by a spec replace the injected config? **Yes**, and five specs did. Fixed: the setting moved into the guard, and the scan forbids `GIT_CONFIG_`.
- **E9** Does a `pushInsteadOf` prefix block a relative-path push? **No** (mutation M9 survived), hence `pre-push`.
- **E10** The incident's trigger, two suites at once in one checkout, is RC1. It passes on the prototype: the second waited, and the repository was unchanged.
- **E11** Is a takeover race observable? Only when staged. The lock spec holds the first waiter in the mutex and starts the second once the mutex exists; L6 is then killed every time.
