# d0105: Radar clear of the chat

## Problem
The player cannot read the radar. f0033 draws it in the top-right (`DangerHud`: anchor `(1, 0)`, position `(1, -16, 0, 16)`, and `IgnoreGuiInset` is true, so y = 16 is inside the top-bar row). The user saw a Roblox CoreGui element there, and reported it as the in-game chat, covering the map. The radar should stay visible while playing.

## Non-goals
- Turning a CoreGui off (chat, player list or the top bar). Players share a server even though each maze is private (game-design, Solo mazes). Turning the chat off was the other option the user allowed; this raft does not take it, and it does not take turning the player list off either.
- The touch jump button, and safe-area insets from a notch or a home indicator. Both belong to f0029. This raft's bar-and-radar agreement assumes no side or bottom safe-area inset.
- The explored-maze minimap (f0101). That is a different map, and it is not built yet.
- What the radar shows (walls, ghosts, rotation), the edge indicators, the power bar's place, the level label and the lives row.
- The mobile HUD layout (f0029).

## Solution
Move the radar to the bottom-right. `Hud.radarBox` returns its rectangle from the same layout numbers the power bar already uses, so the radar's bottom edge is one margin above the bar. `DangerHud` applies that rectangle on every render step. The chat stays on.

## Design
### Decisions made in prep
- **Move the frame, keep the chat.** The user allowed either. Chat stays because a server is shared (game-design, Solo mazes) and the covering window is the top-right one they saw. The corner was f0033's adapter choice, not a game-design decision.
- **Reserve the bar's slot even while it is hidden.** The radar does not jump when a power pellet starts. The gap is `margin` pixels, from `Hud.layout`, not a new constant.
- **Place every frame.** A condition on the placement cannot be checked offline, and it is what let a resize leave the radar off its corner. The cost is one `layout` per frame, the same order as the tables the step already builds. There is no size cache.

### Files and API
`src/shared/Logic/Hud/init.luau` gains:
```lua
export type Box = { x: number, y: number, w: number, h: number }
function Hud.radarBox(width: number, height: number, size: number): Box
```
`side` (already local) treats a non-positive or non-finite size as 0. `right = side(width) - margin`, `bottom = side(height) - (barHeight + 2 * margin)`, and the box is `{ x = right - s, y = bottom - s, w = s, h = s }`. `Hud.layout` is not modified. Golden values, from `experiments/overlap.luau` against the real `Hud.layout`: 1280×720 → `{1144, 555, 120, 120}`, 1920×1080 → `{1780, 904, 120, 120}`, 480×320 → `{353, 180, 120, 120}`. 120 is `(RADAR_RADIUS * 2 + 1) * CELL` = 15 × 8, the frame `DangerHud` already builds.

`src/client/DangerHud.luau`: require `Hud`. Drop `radar.AnchorPoint` and `Position = UDim2.new(1, -16, 0, 16)`. Do not assign `radar.AnchorPoint` at all: the default `(0, 0)` is the top-left `radarBox` returns, and an explicit `(0, 0)` fails the spec the same way any other anchor does. The first lines of the `RenderStepped` callback, verbatim, before the snapshot guard:
```lua
local view = gui.AbsoluteSize
local box = Hud.radarBox(view.X, view.Y, radarSize)
radar.Position = UDim2.fromOffset(box.x, box.y)
```
The arrows keep using that same `view`. No `SetCore`, `SetCoreGuiEnabled`, `TextChatService`, `ChatWindowConfiguration` or `BubbleChatConfiguration`.

The prototype is `experiments/prototype.patch` on this raft.

### Pure/adapter split and authority
The rectangle is pure `Hud`. `DangerHud` only copies it onto the frame. Nothing is sent to the server. The snapshot and `Awareness` are unchanged.

### Scalability
Every render step calls `radarBox` once: one `layout` (a five-field table) and one four-field box, then one `Position` write. The step already builds a ghosts table, a radar result and an indicators list every frame after the snapshot guard, so this is the same order of work. There is no size cache. The radar's dot pool is unchanged. A further corner is another function next to `radarBox`; the bar, the lives and the level stay on `layout`'s numbers.

### Maintainability
The bar's rectangle in `HudView` is `x = width - (barWidth + margin)`, `y = height - (barHeight + margin)`. `radarBox`'s bottom is `margin` above that `y`, so the two cannot drift apart as long as both read `layout` and the screen has no side or bottom safe-area inset. `HudView` leaves `IgnoreGuiInset` at its default (false); `DangerHud` sets it true. A notch or a home indicator moves the bar and not the radar. That is f0029. No second copy of the margin or the bar height lives in the adapter.

### Usability
The map sits in the bottom-right, clear of the top-right CoreGui the user saw, and clear of the power bar underneath it. A ghost behind and to the right puts its edge arrow over the radar's left or top part. The arrow is created after the radar, so it draws on top, and a ghost inside the radar radius is also a blip. A ghost close behind still shows a large bright arrow.

## Unknowns & experiments
- **E1** Does the box clear the power bar, the lives frame and the level label? **Pass.** `lune run tracker/rafts/R0037/experiments/overlap.luau` (the real `Hud.layout`, the formula above) on 480×320, 667×375, 800×600, 1280×720, 1920×1080, 1080×1920 and 3840×2160. At each, the gap above the bar equals `margin`, the right edges match, the box is inside the screen and in the right half, and it does not overlap the lives frame or the level label. A zero, negative or NaN size is the empty square at `{1264, 675}` on 1280×720.
- **E2** Does the bottom-right stay clear of whatever covered the top-right? **Not provable offline.** The user reported the in-game chat. The default chat window is top-left, and this game never moves it; the top-right also holds the player list and the top-bar buttons, and the old frame sits inside the top-bar row (`IgnoreGuiInset`, y = 16). **Method**: Observed O1, in a live server with two players, the chat open and the player list shown. **Fallback**: if a CoreGui element still covers the radar, stop and ask. Do not turn a CoreGui off in this raft.
- **E3** Mutation check, on the patch with no size cache. Killed on assertions: one margin instead of two (the golden boxes move); a top-edge `bottom` (the same boxes); a raw `size` (the negative-size case); restoring `UDim2.new(1, -16, 0, 16)` and dropping the call (the placement case and "the old top-right corner is gone"); the three placement lines not contiguous at the start of the step, including an `if` around the call, the call after the guard's `return`, the `Position` write moved to after the guard, `local view` hoisted to before the step, and `local view = Vector2.new(1920, 1080)` (the placement case); a second `radar.Position` write after the guard (the placement case); `radar.AnchorPoint = Vector2.new(1, 1)` ("the old top-right corner is gone"); `SetCore("ChatActive", false)` and `SetCoreGuiEnabled` of the player list ("the chat stays on").
