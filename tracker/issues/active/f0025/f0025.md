# f0025: Hiscore submit

## Problem
At game over, the server has to submit the player's final score and level from its own simulation, never from the client. The boards update without double submissions.

## Non-goals
- UI (f0026). The rank remote's listener is registered by f0026's `Ranks` module. This issue calls `HiscoreStore.submit` and does not `FireClient` a rank.
- A client-supplied run id or score.

## Solution
`Sessions` hands the events of every `Session.step` to an optional `runs` argument, and keeps a departed session stepping while `runs` asks it to. The new adapter `src/server/Submits.luau` is that argument: it holds the run state, and on `GameOver` it calls `HiscoreStore.submit` once per run. The run id and the disconnect window are pure functions on `Hiscores`, added to the module f0024 creates. `Sessions` itself requires nothing new, so f0065's boot of it on the fake engine stays as it is. The raft's Whole-raft design is the contract; the signatures below are the part this issue adds and the way `Sessions` calls it.

## Design
Add to `src/shared/Logic/Hiscores/init.luau` (no new feature edge; Session the feature does not require Hiscores):

```lua
Hiscores.LEAVE_STEPS = 45
export type RunState = { run: number, done: { [number]: boolean }, waited: number, drop: boolean }
export type Submission = { score: number, level: number, run: number }
export type StepEvent = { kind: string, score: number?, level: number? }

function Hiscores.once(done: { [number]: boolean }, runId: number): (boolean, { [number]: boolean })
function Hiscores.newRun(): RunState
function Hiscores.onAgain(state: RunState, ok: boolean): RunState
function Hiscores.leave(stepsWaited: number, sawOver: boolean): "drop" | "keep"
function Hiscores.onStep(state: RunState, events: { StepEvent }, here: boolean): (RunState, Submission?)
```

`newRun` is `{ run = 1, done = {}, waited = 0, drop = false }`. `once` returns false and the same table when `runId` is not a whole number ≥ 1 or `done[runId]` is already true. Otherwise it copies `done`, sets the copy's `[runId]`, and returns true and the copy. The input table is unchanged.

`onAgain(state, false)` returns the same table. `onAgain(state, true)` returns a new state with `run + 1`, the same `done`, the same `waited`, and `drop = false`.

`onStep` scans events. The first `kind == "GameOver"` sets `saw`. A lowercase `gameover` is not that kind. When `score` and `level` are both numbers, `once(done, state.run)` decides the submission `{ score, level, run = state.run }`. Any `event.run` or `event.tick` is ignored. A second GameOver in the same events list or a later step of the same run submits nothing. A GameOver without score or level sets `saw` and submits nothing.

When `here` is true, the returned state has `waited = 0` and `drop = false`. When `here` is false, `waited` increases by 1 (the first absent step is 1) and `drop` follows `leave(waited, saw)`. `leave` is `"drop"` if `saw` or `stepsWaited >= LEAVE_STEPS`, else `"keep"`. `LEAVE_STEPS` equals `Game.CLASSIC_CONFIG.dyingTicks` (45) but the module does not require Game. Forty-four steps away with no GameOver stays. The GameOver step while away submits and drops. A disconnect during play, with no GameOver inside 45 steps, drops with no submit.

Run id, from state that already exists: Submits starts a `newRun()` when Sessions tells it a session was made on Ready, next to the existing `Session.new(...)`. A rejoin's Ready finds `sessions[player] == nil` and creates a new session and a new run. It does not use `Session.tick`. `tick` advances every step and `Session.playAgain` does not reset it (read in prep, E4). It does not read a client value. Every `RunState` starts at run 1, and the only dedupe is its `done`; neither Submits nor `HiscoreStore` keeps one per user id (raft decision 6), so a rejoin's run and a parked run of the same user both submit.

`src/server/Sessions.luau` requires only Maze and Session (f0065's `sessions.spec` boots it on a fake that serves nothing else, with `start()`):

```lua
export type Runs = {
	ready: (s: Session.Session, player: Player) -> (),
	again: (s: Session.Session) -> (),
	step: (s: Session.Session, events: { Session.Event }, here: boolean) -> boolean,
}
function Sessions.start(runs: Runs?)
```

Ready that creates a session calls `runs.ready(s, player)` once (a repeat Ready does nothing). The heartbeat stays `for _ = 1, Session.advance(clock, dt) do`. One step per frame is wrong: `STEP_RATE` is 15 and `MAX_STEPS_PER_ADVANCE` is 5, and `LEAVE_STEPS` is 45 steps, not 45 frames. Inside that loop, for each live session:

```lua
local events = Session.step(s)
local here = player.Parent ~= nil
if runs then
	runs.step(s, events, here)
end
if here then
	snapshot:FireClient(player, Session.frame(s, tostring(player.UserId)))
end
```

A live session stays in `sessions` whatever `runs.step` answers: a `GameOver` while parented keeps the player in the live map (f0065's `Sessions.isOver` reads it). `advance` returning 0 steps nobody, sends nothing and calls no `runs.step`.

`PlayerRemoving` sets `sessions[player] = nil` and, only when `runs` was given, parks the session:

```lua
Players.PlayerRemoving:Connect(function(player: Player)
	local s = sessions[player]
	sessions[player] = nil
	if s and runs then
		table.insert(parked, s)
	end
end)
```

The same advance loop, after the live sessions, steps each parked session once, calls `runs.step(s, events, false)`, never `FireClient`s it, and keeps it only when that returns true. The list is rebuilt after the loop, not edited during it. Started without `runs`, nothing is parked: a departure is forgotten at once, as today.

While `PlayAgain` still exists, its handler keeps the f0031 shape and tells the runs only when Logic accepts it. f0065 may delete the handler; this spec allows zero calls.

```lua
local _, ok = Session.playAgain(s, tostring(player.UserId))
if ok and runs then
	runs.again(s)
end
```

There is no `task.wait` and no `task.delay` in `Sessions`. No `PlayerAdded`, no `TICK_RATE`, no `Session.snapshot(`, no `.phase`, no lowercase `gameover`. One `Session.newClock(Session.STEP_RATE)`. `Session.new` still ends with `Session.GAME_CONFIG)`.

`src/server/Submits.luau` requires `@game/ReplicatedStorage/Shared/Logic/Hiscores` and `./HiscoreStore` and is the `Runs` table. Per session object it keeps a `RunState` and `{ userId, name }`:

- `ready(s, player)`: `Hiscores.newRun()`, `tostring(player.UserId)`, and `Hiscores.cleanName` of `DisplayName` when that is a non-empty string, otherwise of `Name`, captured now.
- `again(s)`: `Hiscores.onAgain(state, true)`.
- `step(s, events, here)`: `Hiscores.onStep(state, events, here)`; store the new state; on a submission, `HiscoreStore.submit(userId, name, submission.score, submission.level, submission.run)`; when the new state says `drop`, forget the session and return false. A session it holds no state for returns false. Otherwise true.
- `pending(): number`: the runs it holds (one per `ready`, released when `step` returns false).
- `close()`: `local waited = 0; while Hiscores.holdClose(Submits.pending(), HiscoreStore.pending(), waited) do waited += task.wait(0.25) end`. The module binds it once, when first required: `game:BindToClose(Submits.close)`.

Shutdown (raft decision 6, review 003 F2): when the last player leaves, Roblox closes the server and drops yielding threads unless a `BindToClose` callback holds it (at most 30 s). The engine keeps stepping Heartbeat during the close (raft E16), so a run parked in its dying pause reaches `GameOver` and submits, and the close then also waits for that drive and for the drive of a player who reached `GameOver` and left. Pure rule, added to Hiscores:

```lua
Hiscores.CLOSE_WAIT = 25
function Hiscores.holdClose(runs: number, drives: number, waited: number): boolean -- (runs > 0 or drives > 0) and waited < CLOSE_WAIT
```

At close every player is leaving, so each held run is parked and either drops within 45 steps (about 3 s) or submits. A run whose player is never removed (a Studio stop) holds the close to the 25 s cap; work still pending then is lost.

`src/server/Main.server.luau` starts Sessions with it: `require("./Sessions").start(require("./Submits"))` (or `Sessions.start(require("./Submits"))` once f0065's Main names the local), after `Ranks.start()` (f0026).

`HiscoreStore.submit` returns immediately (f0024 spawns `drive`), so this loop does not block the overlay. A second GameOver in the run does not call `submit`, because `submission` is nil. Catch-up can call `onStep` up to five times in one frame; `once` ignores the later ones.

### Scalability
One live session per connected player, plus a parked session for at most 45 steps after `PlayerRemoving`, and one `RunState` per session in Submits, forgotten when its parked session is let go. The step itself is the existing `Session.step`, and only as many times as `Session.advance` returns. The store write is not on this thread. A full server of parked dying runs is bounded by the player count times 45 steps, then the rows are dropped.

### Maintainability
The next "when do we submit" change is `onStep`, not a new branch in `Sessions` or `Submits`. `Sessions` only passes the session, `here`, the events from `Session.step`, and, while the handler exists, an accepted play again; it knows nothing about hiscores. Another per-step server feature is another `Runs`-shaped hook, not a new require in Sessions. The run counter is not a field on `Session`, so f0031's phase pins stay true. A different pause length changes `LEAVE_STEPS` and the spec that compares it to `dyingTicks`. Deleting the play-again handler does not require a new Hiscores function: Ready already calls `newRun`.

### Usability
The player gets one submit for the run they just finished, including when they disconnect during the death pause. The overlay still appears for anyone still parented, because `FireClient` is skipped when `Parent` is nil and submit does not yield. A worse second GameOver cannot double-post. The API is `onStep` / `onAgain`: callers that pass a client run id still submit `state.run`. A rejoin during the parked window can submit its own new run; it does not steal the parked one.

## Test plan
- `run.spec` :: `once` copies, second GameOver of the same run is nil, `event.run = 99` still submits run 1, two GameOver events in one step keep the first score, `gameover` and a scoreless GameOver do not submit, two fresh `newRun()` states both submit run 1, `onAgain(true)` is run 2 and submits, `onAgain(false)` is the same table and does not submit again → AC1
- `leave.spec` :: `LEAVE_STEPS == 45 == dyingTicks`, 44 steps away stay, GameOver while away submits and drops, coming back clears `waited`, a scoreless GameOver while away drops without a submit, `holdClose` holds while a run or a drive is pending and never at `CLOSE_WAIT == 25` → AC2
- `sessions.spec` (the real `Sessions` and `Submits` sources under a stub `game` of the spec's own; a spy `Session` whose `step` counts calls and returns scripted events) :: the f0018 / f0054 / f0031 source pins; Main passes `require("./Submits")` to `.start`; Sessions asks only for Maze and Session; Ready makes one session and tells the runs once; `dt = 2 / STEP_RATE` steps each live session twice and hands the runs the events `Session.step` returned; a frame that grants no step steps and sends nothing; a long frame steps at most `MAX_STEPS_PER_ADVANCE`; after `Parent` is nil no frame is sent and the runs hear `here = false`; a live player stays live whatever the runs answer; a departed session is parked, stepped with `here = false`, never sent, and let go when the runs say stop; started with no runs a departure is forgotten at once; play again tells the runs only when Logic accepts it (when the handler exists); with Submits: a GameOver while here submits once with the captured id and cleaned display name (or `Name` when it is empty) and stays live; a departed run with no GameOver is stepped 45 times and not on the 46th frame; a GameOver while parked submits and lets the run go; a rejoin's run and the parked run both submit run 1; a parked session is stepped once per granted step (`2 / STEP_RATE` twice, `0.5 * ONE` not at all); Submits binds one close handler that returns at once with nothing held, waits for a parked run's GameOver (stepping on) and then for its drive, and gives up at 25 s → AC3
