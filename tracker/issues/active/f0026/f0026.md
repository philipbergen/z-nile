# f0026: Hiscore board ui

## Problem
Players need to see the boards (all-time, today, this week) and where they rank, from the lobby and after game over.

## Non-goals
- The mobile layout specifics (f0029). Touch targets stay at `Lobby.BUTTON_MIN_PX` (44).
- The lobby teleport (f0065).
- A second full board in the game place. Game over gains one rank line.
- Submitting a score (f0025). This issue reads, and it displays a rank the server already computed.

## Solution
The lobby panel stays `Lobby.panel` for the all-time board. Pure functions switch it to day and week. The game place pushes an all-time rank line into `Flow` without changing `Flow.overlay`. Both remotes are created at runtime. The raft's Whole-raft design has the data flow; the signatures below are this issue's.

## Design
Add to Hiscores (the module f0024 creates; Lobby and Flow still do not require it):

```lua
Hiscores.CACHE_TTL = 15
Hiscores.READ_GAP = 1
function Hiscores.boardId(raw: any): BoardId?
function Hiscores.lookup(
	cache: CacheEntry?,
	now: number,
	ttl: number,
	gap: number,
	inflight: boolean,
	fetch: (() -> { Row }?)?,
	failure: Failure?
): (CacheEntry?, { Row }?, Failure?)
function Hiscores.failureWait(gap: number, ttl: number, count: number): number -- min(gap * 2^count, ttl)
```

`boardId` returns `"all"`, `"day"` or `"week"`, or nil. `"ALL"`, a number, and a table (a client-supplied score) are nil. `lookup` is the raft's cache rule: fresh when `now >= at` and `now - at < ttl` (so `now == at + ttl` refetches), `inflight` on a stale cache does not fetch and does not move the cache or `failure`, `fetch` nil keeps the same cache, `{}` is stored as a new cache, a non-number or backwards `now` does not fetch. A successful fetch does not mutate the cache it was given. `failure` (`Failure = { at, count }`, raft type block) is the key's run of failed reads: a failed fetch returns `{ at = now, count = count + 1 }`, a successful one nil, anything else the `failure` it was given. Stale and not in flight, the key still does not fetch while `now - failure.at < failureWait(gap, ttl, failure.count)`: 2, 4, 8, then 15 s with the default constants. So a read outage costs each board key at most one read (two page sizes) per those waits, whatever the number of lobby players (review 003 F3). `gap` is only the base of those waits: there is no per-player gap (review 005 F1), because for one key the 15 s cache and the failure window always decide first, and across boards a per-player gap answered a healthy board as an empty failed one.

Lobby, functions only. `panel` is unchanged, including the cap at `MAX_ROWS` and the empty string `"No scores yet"`:

```lua
function Lobby.board(raw: any): ("all" | "day" | "week")?
function Lobby.boardTitle(id: string?): string
function Lobby.boardPanel(rows: { Lobby.Row }?, id: string?): Lobby.Panel
function Lobby.lines(panel: Lobby.Panel, highlightRank: number?): string
Lobby.READ_GAP = 1
Lobby.MAX_RETRIES = 3
function Lobby.retryAfter(failures: number): number? -- READ_GAP * 2^(failures - 1) for whole 1..MAX_RETRIES, else nil
```

`board` matches `boardId`. `Lobby.READ_GAP` equals `Hiscores.READ_GAP` (endtoend.spec asserts it) and is a copy, because `LobbyView` must not require Hiscores: f0061's promoted `lobby-adapters.spec` boots the real `LobbyView` on `tests/lib/fakeengine`, which serves it only Lobby and Travel. `boardTitle("day")` is `"TODAY"`, `"week"` is `"THIS WEEK"`, and `"all"`, nil, and anything else stay `"HISCORES"`. `boardPanel` calls `Lobby.panel` and then sets `title`. `lines` returns `panel.empty` when it is set; otherwise `` `{rank} {name} {score} {level}` `` per row, prefix `"> "` when `row.rank == highlightRank`.

Flow, functions only. `overlay` is unchanged, including the game-over detail `` `SCORE %d   LEVEL %d` `` with the three spaces the existing spec pins:

```lua
export type RankView = { over: number, rank: number?, pending: number?, pendingRun: number? }
function Flow.rankLine(rank: number?): string?
function Flow.follow(view: RankView, gameOver: boolean, wasOver: boolean): (RankView, boolean)
function Flow.hearRank(view: RankView, run: number, rank: number?, gameOver: boolean): RankView
function Flow.shownRank(view: RankView, gameOver: boolean): string?
```

`rankLine` is `` `ALL-TIME #{n}` `` for a whole number ≥ 1, else nil. It does not know N, so rank 11 is still a line. The server only `FireClient`s a rank when `rankOf` found the player in the top N; an unknown rank sends nothing. `rank` is the rank of the run whose overlay is up, and exists only while it is up; `pending` is one slot for the next run. `follow` increments `over` on the false→true edge only, and on that edge **assigns** `rank`: `pending` when `pendingRun` equals the new `over`, else nil, never the previous `rank`. It clears `pending` and `pendingRun` on that edge whatever they held. On true→false it clears `rank` and keeps `pending` / `pendingRun`. With no edge it returns the same table. `hearRank(view, run, rank, gameOver)` takes the same bit `FlowView` passes to `follow` and `shownRank`. It ignores a rank `rankLine` rejects (same table). `run == view.over` (and `over >= 1`) sets `rank` only when the bit is true, which is how a packet that arrives while the overlay is up still shows; with the bit false it returns the same table, so a packet for a run whose overlay has closed is not kept. `run == view.over + 1` stores one `pending` / `pendingRun`, whatever the bit, and does not show it. Any other run, including `over + 2`, returns the same table. So "run 1 dismissed, run 2's rank arrives, run 1's late rank arrives, run 2's overlay opens" shows `ALL-TIME #9` (run 2's), not run 1's: the design's own retry backoff (0.25, then 0.5) can produce that order. `shownRank` is nil unless `gameOver` is true. Client `over` starts at 0, so the first edge is run 1, matching the server. The game-over bit `FlowView` passes is `overlay.banner == "GAME OVER"`, which f0031 and f0065 both already produce. Do not read `overlay.playAgain` and do not add a field to `overlay`.

`src/lobby/server/Boards.luau`: at `start`, `Instance.new("RemoteEvent")`, `Name = "Board"`, parent `ReplicatedStorage.Remotes`, before any yield. On the server event, a nil `boardId` sends nothing and reads nothing. One shared cache per `cacheKey(id, os.time())`, one in-flight flag, one waiter list and one `Failure` per that key, and no per-player state (no `lastFetch`, nothing keyed by player). `lookup` with `CACHE_TTL`, `READ_GAP`, the flag, the key's `Failure` (Boards stores the one `lookup` returns), and a `fetch` that sets the flag, puts the requester on the waiter list, reads, and clears the flag. The read is `GetSortedAsync(false, pageAttempt(n))`, n = 1 then 2 on error, each `pcall`'d, then `scorePage(GetCurrentPage(), N)` (cut to the first `N` entries, so the 50-entry fallback page costs at most `N` companion reads), companion `GetAsync`s and `rows(..., N)`; not `drive`, never `AdvanceToNextPage`. `lookup`'s nil rows mean three things, told apart by Boards, not by the shape: every request gets exactly one `FireClient(player, id, Hiscores.lobbyRows(rows), Hiscores.rankOf(rows, tostring(player.UserId)), failed)`:
1. rows returned (fresh cache, or a read that succeeded, an empty board included): the requester, `failed = false`;
2. its own `fetch` ran: every waiter on that key once, with the new rows and `failed = false`, or, on a nil read, the previous cache's rows (`{}` when there were none) and `failed = true`;
3. nil rows while that key is in flight: the requester joins the waiter list and is answered by (2), once, when the read returns; it does not call `GetSortedAsync`;
4. nil rows inside the key's failure window, not in flight: the previous rows (or `{}`) with `failed = true`, without a read.

The highlight is that player's own rank on those rows, or nil when they are not on them. Answers go only to players whose `Parent` is not nil. The whole read (store opens, page sizes, `scorePage`, companion reads, `rows`) is one `pcall`: any error is a failed read (`Failure` set, flag and waiters cleared, each waiter one `failed = true` answer). A companion `GetAsync` that throws makes `rows` nil (an unknown row fails the read, it is not cached), one that returns nil is skipped. Path 4 inside a failure window answers the rows the server holds, never an empty board when it has rows. The file contains neither `SetAsync`, `UpdateAsync`, `HiscoreStore` nor `AdvanceToNextPage`. `Main` calls `Starts.start()` then `Boards.start()`. `Starts` does not require Boards and does not mention `DataStore`.

`src/server/Ranks.luau`: `Instance.new("RemoteEvent")`, `Name = "Rank"`, parent the game place's Remotes, before any yield. `HiscoreStore.listen` with a callback that resolves the player with `Players:GetPlayerByUserId(tonumber(userId))` and `FireClient(player, run, rank)`s only when that player exists and `player.Parent ~= nil`. No `OnServerEvent`, no `FireServer`. Game `Main` calls `Ranks.start()` before it starts Sessions (the order holds with f0065's `local Sessions = require("./Sessions")` above it: the pin compares the `.start(` calls).

`LobbyView.start` keeps WaitForChild of `StartGame` and `Status`, and requires only Lobby and Travel. It `FindFirstChild("Board")` and, only when that is non-nil, binds `OnClientEvent(id, rows, highlight, failed)` and `FireServer("all")` once. It must not `WaitForChild("Board")`: the f0061 fake has no Board remote and boots the empty panel (`Title` `"HISCORES"`, `Rows` `"No scores yet"`). A payload draws `Lobby.boardPanel(rows, Lobby.board(id))`'s title into `Title` and `Lobby.lines(panel, highlight)` into `Rows`. It keeps `wanted` (the board of the start ask or the last tap) and a count of asks sent: an answer for another board is neither drawn nor counted, and a scheduled retry asks only when no ask was sent since and `wanted` is still its board. A tap sets `wanted`, resets the failure count and asks. It counts failed answers in a row. A payload whose `failed` is `true` adds one and, while `Lobby.retryAfter(count)` is a number (1, 2, then 4 s), schedules one `task.delay` of it that `FireServer`s the payload's own board (`Lobby.board(id)`, or `"all"` when that is nil): a failed TODAY retries TODAY. The fourth failed answer in a row schedules nothing. Any other payload resets the count and schedules nothing. Three board controls, for `"all"`, `"day"` and `"week"`, are extra `TextButton`s whose `Text` is `Lobby.boardTitle(id)` (HISCORES, TODAY, THIS WEEK) and whose `Size.Y.Offset` is at least `Lobby.BUTTON_MIN_PX` (44); each `FireServer`s only its id, and a tap always asks, also after the retries stopped. The start button's `:FireServer()` stays empty. Do not add Board to `lobby.project.json`.

`FlowView` keeps `:FireServer()` with no arguments (f0031) and requires only Flow. `FindFirstChild("Rank")`, not `WaitForChild("Rank")`. `show` passes `overlay.banner == "GAME OVER"` into `follow`, keeps the returned bit, and sets a label from `shownRank`; `OnClientEvent(run, rank)` calls `hearRank` with that kept bit and redraws the label. Do not edit `src/client/Main.client.luau` (it still calls `Flow.overlay` and must not mention `Rank`). Do not add Rank to `default.project.json`. f0065's sequestered place spec lists the project remotes and would go red if Rank were one of them.

`adapters.spec` runs the real `Boards`, `LobbyView` and `Ranks` sources under a stub `game` of its own (instances, signals, a `DataStoreService` whose read can fail or yield, `task.delay` on a fake clock), not `tests/lib/fakeengine`, which f0061 pins and f0065 extends.

The lobby and the game place share the DataStores because they are one experience (decision 8). Boards opens them with `Hiscores.storeTarget` and the same names. It does not require `src/server/HiscoreStore.luau`, which is not in the lobby place.

### Scalability
A lobby read is one ordered page (10 entries, or the 50-entry fallback cut to the first 10) plus at most 10 companion gets, and only when the shared cache is stale, the key is outside its failure window, and no fetch for that key is already in flight. One player can cause at most three reads per 15 s (one per board). Waiters share that fetch. A fresh cache does no store call. The rank packet is one `FireClient` of two numbers per qualified run, and only while the player is parented. No per-frame store read. The overlay math is a couple of integer compares per `show`.

### Maintainability
Another board id is a `boardId` arm, a title in `boardTitle`, and a button that sends that string. The cache key already includes the period, so a new period rolls over without a new table. `Flow.overlay` stays the phase switch it is; the rank line is a separate function, so f0031's detail string does not grow a rank. Adapters do not format rows or decide freshness.

### Usability
The lobby still opens on HISCORES and "No scores yet" until a board arrives. A failed first read still answers, so the panel can show that empty line, and the client asks for the same board again after 1, 2 and 4 s, then waits for a tap. A HISCORES button brings back the all-time board. A healthy empty board does not keep asking. Day and week are explicit titles, TODAY and THIS WEEK. The player's own row is marked by rank, not by a name the client could fake. Game over keeps SCORE and LEVEL, and adds `ALL-TIME #n` only when the server has a rank for this run. A rank that arrives after the overlay closes is not shown, on that run or the next. A packet that arrives before the overlay is held and shown when the overlay appears, also when an older run's late packet arrives after it. An unknown rank leaves the line blank rather than inventing a place. Buttons stay at least 44 px.
