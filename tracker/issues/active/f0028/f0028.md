# f0028: Touch look

## Problem
A phone has no locked mouse the player can drag. The right half of the screen has to look around, and a snap control has to recentre the look, without turning those gestures into swipes.

## Non-goals
- Gyro look.
- Changing `Hud.layout`, drawing the button, or computing its rectangle (f0029). This issue hit-tests a rectangle it is given.
- Changing swipe thresholds or adding an intent (f0027).
- A second camera blend, a tick rate, or an unconditional mouse lock.

## Solution
f0027's fold already emits `{ kind = "look", dx, dy }` for a look-zone move and `{ kind = "snap" }` when a touch begins inside the rectangle. This issue applies those effects with the functions the mouse and the Space key already use, and it stops the locked-mouse delta from applying the same touch a second time.

## Design
Agree with the raft's whole-raft design. Implement after f0027: `Touch.track` and `Touch.zone` exist, and `Controls.start` already accepts `onLook` and `onTouch`.

Look state stays the `View.Look` inside `Camera`. Do not give Touch a copy of it.

```lua
local mouseHeld = false
local lookedThisFrame = false

function Camera.lookBy(dx: number, dy: number)
	lookedThisFrame = true
	look = View.look(look, dx, dy)
end

function Camera.holdMouse(held: boolean)
	mouseHeld = held
end
```

There is one flag and one latch. `mouseHeld` is set only from `onTouch` (a turn finger never calls `lookBy`). `lookedThisFrame` is set only in `lookBy`. There is no second per-frame note inside `lookBy`.

`View.look` already wraps yaw with `(a + pi) % tau - pi` into `(-pi, pi]` and clamps pitch to `±View.MAX_PITCH`. `View.MOUSE_RADIANS_PER_PIXEL` is 0.004. `View.MAX_PITCH` is `math.rad(80)`, greater than 0 and less than `pi/2`. A touch delta is raw pixels; this issue does not scale it again. `Camera.snap` stays `look = View.snap(look)`. `Camera.setCursor` stays. The render step keeps:

- `UserInputService.MouseBehavior = if cursor then Enum.MouseBehavior.Default else Enum.MouseBehavior.LockCenter`
- `UserInputService.MouseIconEnabled = cursor`
- one call `View.interpolate(prev, snap, View.alpha(os.clock() - arrived))`
- no `TICK_RATE` anywhere in the file
- `function Camera.pose(`
- `GetMouseDelta()` called every frame (the call clears the accumulator)
- `look = View.look(look, delta.X, delta.Y)` only inside `if not mouseHeld and not lookedThisFrame`
- then `lookedThisFrame = false`, and only then `if snap == nil then return`

The clear sits after the guarded `View.look(look, delta` and before `snap == nil`. A clear written above the guard zeroes the latch before this step reads it, so one touch look never suppresses that frame's mouse delta. A clear written only after the early return leaves the latch set for the rest of the session. Input can begin and end before `PickmanCamera` runs: `onTouch(false)` has then cleared `mouseHeld`, and that frame's `GetMouseDelta` still carries the touch, so the latch has to survive until this step.

The source therefore contains `GetMouseDelta()`, `function Camera.lookBy(`, `function Camera.holdMouse(`, `function Camera.snap(`, `function Camera.setCursor(`, `lookedThisFrame = true`, `not mouseHeld and not lookedThisFrame` before `View.look(look, delta`, and `lookedThisFrame = false` before `snap == nil`.

`Main` passes the new functions. After this issue, before f0029:

```lua
Controls.start(Camera.snap, Camera.lookBy, nil, Camera.holdMouse)
```

The source contains the prefix `Controls.start(Camera.snap, Camera.lookBy,` and `Camera.holdMouse`. `Controls.start(Camera.snap, Camera.holdMouse, Camera.lookBy)` passes `holdMouse` where `onLook` is and fails that prefix. It does not need `HudView.snapRect` yet. f0029 inserts that as the third argument; the prefix still matches. Do not reorder adapter `start` calls relative to `ready:FireServer()`. `DangerHud.start(Camera.pose)` stays.

Hit-test rules, implemented by f0027's `Touch.zone` / `Touch.track` and pinned here so a later edit cannot drop them:

- A begin whose point is inside the rect is snap, on either half. The minimum corner is inside; `x + w` and `y + h` are outside.
- Outside that rect, the half rule still applies. On width 800 the points (344, 720) and (320, 744) are `"turn"`. On width 390 those same points are `"look"`, and (300, 700) stays `"snap"`. A finger that begins on the left-half outside point can still swipe. Look only on the right half.
- That snap finger emits `{ kind = "snap" }` on begin and nothing on move or end, even if the finger slides off the button and even if the end position would have been a turn.
- A finger that began outside stays a look if it slides onto the button. The move's delta is from the previous point. The end emits nothing, including when the end context's snap rect is nil.
- A second snap begin adds nothing to the **returned** state. `fingers[1]` stays the original snap finger and `fingers[2]` is nil. Ending finger 2, even with a long horizontal move, emits nothing and leaves finger 1. Ending finger 1 leaves no fingers. Replacing finger 1, or storing finger 2 on the returned state, keeps `onTouch` true after the real finger ends. The turn and look occupancy cases in f0027 stay the other two zones.

`Controls` (from f0027) already routes `look` to `onLook` and `snap` to `onSnap`, and calls `onTouch` when the finger count crosses zero. This issue does not reimplement the fold. If `onTouch` is missing, that is an f0027 bug: stop and report, do not fork a second classifier.

With no touch finger down and no look already applied this frame, the render step applies `GetMouseDelta` through `View.look` as it does today. While `mouseHeld` is set, or `lookedThisFrame` is set, it does not. See raft E6. Taking the fallback that always applies the mouse delta fails the branch pin: stop and report, do not ship it.

### Scalability
`lookBy` is one `View.look` per touch move. `holdMouse` is a boolean. Nothing is replicated. The camera render step does not grow with the maze.

### Maintainability
Touch owns the gesture. Camera owns the `View.Look`. The next pointer (a pen, a second camera) calls `lookBy` and does not grow a second pitch clamp. The render step's new branch is `not mouseHeld and not lookedThisFrame`. It does not touch interpolation.

### Usability
Dragging the right half looks at the same radians per pixel as the mouse, and it stops at the same pitch. Releasing does not turn. Tapping the snap control recentres, including when the control sits on the right half. A second finger on the button does not snap again. Keyboard and mouse still work once the finger is up.

`lookBy` and `holdMouse` are typed, one job each. `lookBy` does not take a rect. `holdMouse` does not look.

## Unknowns & experiments
- **E3, run** (raft). A look move of `dy = 10000` from pitch 0, passed through the real `View.look`, has pitch `-View.MAX_PITCH`. The unclamped mutant `pitch = -dy * 0.004` is about −40, past `math.rad(80)`. A second move of the same point emits `{ dx = 0, dy = 0 }`. Fallback: none; do not clamp inside Touch. Touch emits pixels.
- **E6, reasoned.** Pass/fail: is `GetMouseDelta()` non-zero during a touch while the mouse is locked? Not run in Studio. Docs and devforum practice say a touch is that mouse. Default: always call `GetMouseDelta()`, and pass that delta to `View.look` only when `not mouseHeld and not lookedThisFrame`. `lookBy` applies the touch once and sets the latch. The latch clears after that call and before `if snap == nil then return`. Fallback if a device emulator shows the delta stays 0 during a touch: stop and report. An empty `holdMouse` plus always applying the mouse delta is source-identical to that fallback and fails the branch pin. Do not ship it.

## Acceptance criteria

### Checked
- AC1: Each move of a look-zone finger, threaded on the returned state, is the pixel delta from the previous point, including a zero delta when that point is repeated. `View.look` of a 10000 px downward delta from pitch 0 is exactly `-View.MAX_PITCH`, the upward delta is `+View.MAX_PITCH`, and a huge yaw stays in `(-pi, pi]`. The scale is `View.MOUSE_RADIANS_PER_PIXEL` (0.004).
- AC2: A touch that begins inside the snap rectangle is the snap control, even on the right half. It emits snap on begin only. The rectangle is half-open. Outside it, width 800 is `"turn"` and width 390 is `"look"`. A finger that began outside stays a look if it slides onto the button, and releasing it does not emit a turn. A second snap begin adds nothing to the returned state: finger 1 stays, finger 2 is absent, ending finger 2 emits nothing, and ending finger 1 leaves no fingers.
- AC3: `Camera.luau` still calls `GetMouseDelta()` and defines `Camera.lookBy`, `Camera.holdMouse`, `Camera.snap`, and `Camera.setCursor`. `View.look(look, delta` runs only under `not mouseHeld and not lookedThisFrame`, and `lookedThisFrame = false` sits after that call and before `snap == nil`. `Main` contains `Controls.start(Camera.snap, Camera.lookBy,` and `Camera.holdMouse`.

### Judged
None.

### Observed
None. f0029 OC1 drags the right half and taps snap on a phone-sized viewport.

## Implementation steps
1. Add `Camera.lookBy` and `Camera.holdMouse` as specified. `lookBy` sets `lookedThisFrame` and calls `View.look`. `holdMouse` sets `mouseHeld` only. Keep the mouse, cursor, pose, and interpolate lines. Always call `GetMouseDelta()`, and pass it to `View.look` only in the not-held, not-yet-looked branch. Clear the latch after that call and before `if snap == nil then return`.
2. Change the `Controls.start` call in `Main` to `Controls.start(Camera.snap, Camera.lookBy, nil, Camera.holdMouse)`. Do not start touching `HudView`.
3. Run `tracker/issues/f0028/acceptance/{look,hit,place}.spec.luau`. `look` and `hit` require `@logic/Touch` and fail until f0027 has landed on this branch. `place` fails until step 2.
4. Run `tests/acceptance/f0031/place.spec.luau`, `tests/acceptance/f0033/adapters.spec.luau`, and `tests/acceptance/f0054/adapters.spec.luau`. They stay green.
