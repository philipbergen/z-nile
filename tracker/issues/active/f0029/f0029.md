# f0029: Mobile hud layout

## Problem
The HUD and the snap control have to sit on a notched phone, in portrait or landscape, without covering the forward view. Touch targets are at least 44 px. A zero inset must not move today's layout.

Folded in from c0106 (2026-10-20): the danger radar (d0105) sits in the bottom-right corner, one margin above the power bar, which on a phone is where Roblox draws its touch jump button. This layout keeps the radar, the power bar and the snap control clear of that button, in portrait and landscape.

## Non-goals
- Tablet-specific layouts beyond the same function of width, height, and inset.
- Changing swipe thresholds, the cone, or the intent set (f0027).
- A second snap-button placement that climbs into the forward view.
- A touch jump or fire control for the spy hop (f0101) or the blaster (f0100); f0104 says touch needs its own, and none is captured yet. This issue only keeps Roblox's jump corner free.
- Turning Roblox's jump button on. It never shows in this game today (E7), so the reservation is a guard, not a feature.
- Moving the edge arrows. They keep DangerHud's ScreenGui as it is.

## Solution
`Hud.layout` takes an optional inset and reports the safe rectangle. `Hud.safeInset` turns two inset areas into that inset. `Touch.snapRect` and `Touch.blocks` place the button and the four HUD blocks in the margin bands. `HudView` passes `GetInsetArea` of `ScreenInsets.None` and `CoreUISafeInsets` through `Hud.safeInset` and draws a non-active Snap frame. It does not read `GetGuiInset`. `Main` passes `HudView.snapRect` into Controls. `Hud.jumpButtons` names Roblox's touch jump button rectangles, and on a touch screen `Hud.radarBox` lifts the radar above them (DangerHud passes `UserInputService.TouchEnabled` and `Hud.bandTop` of its two inset areas).

## Design
Agree with the raft. Numbers below were measured against the current `Hud.layout` (raft E1, E3). Implement `Touch.snapRect`, `Touch.blocks`, and `Touch.MIN_TARGET = 44` on the module f0027 created. Do not require Hud from Touch: the box is a table of numbers the adapter already has.

```lua
export type Inset = { top: number, bottom: number, left: number, right: number }
export type Layout = {
	textSize: number, margin: number, iconSize: number,
	barWidth: number, barHeight: number,
	safeX: number, safeY: number, safeW: number, safeH: number,
}
function Hud.layout(width: number, height: number, inset: Inset?): Layout

-- Min/Max areas, not Touch's x,y,w,h rect. No engine words.
export type Area = { Min: { X: number, Y: number }, Max: { X: number, Y: number } }
function Hud.safeInset(none: Area, core: Area): Inset
```

Nil inset means all zeros. Each of `top`, `bottom`, `left`, `right` passes through the existing `side()` (`v > 0 and v < math.huge`, else 0), and so do `width` and `height`. Then:

```lua
safeX, safeY = left, top
safeW = math.max(0, w - left - right)
safeH = math.max(0, h - top - bottom)
-- text, margin, iconSize: from min(w, h), the FULL viewport, exactly as today
barWidth = math.max(0, math.min(round(safeW * Hud.BAR_SHARE), Hud.MAX_BAR, safeW - 2 * margin))
barHeight = math.max(Hud.MIN_BAR_HEIGHT, round(text * 0.4)) -- unchanged; 14 px text → 6
```

Do not subtract the button from `barWidth`. Zero insets make `safeW == w`, so the five numbers match today's function for every width, not only the samples. Acceptance specs call the three-argument form as `(Hud.layout :: any)(...)` because they are sequestered and cannot grow a real parameter type later. Two-argument calls in old specs stay uncast. `Hud.safeInset` is called as `(Hud :: any).safeInset` for the same reason.

```lua
left, top = -none.Min.X, -none.Min.Y
right = (none.Max.X - none.Min.X) - (core.Max.X - core.Min.X) - left
bottom = (none.Max.Y - none.Min.Y) - (core.Max.Y - core.Min.Y) - top
-- then the existing side() on each component
```

The documented areas `(-59, -58)-(792, 334)` against `(0, 0)-(733, 313)` return `{ left = 59, top = 58, right = 59, bottom = 21 }`. The same rect for both arguments, using the core sample, is all zeros, so a constant 58 fails. Feeding `none.Min` through without the minus sign makes `side()` turn left and top into 0, which fails the 59. Treating `core.Min` as the inset is `(0, 0)` on that sample.

Pinned two-argument five-tuples `(textSize, margin, iconSize, barWidth, barHeight)`: 1920×1080 → 40, 20, 40, 400, 16; 1280×720 → 32, 16, 32, 320, 13; 390×844 → 18, 9, 18, 98, 7; 844×390 → 18, 9, 18, 211, 7; 667×375 → 17, 9, 17, 167, 7; 0×0 → 14, 7, 14, 0, 6. 3840×2160 keeps `barWidth` 400. An all-zero inset matches those five and reports the full viewport as `safe`.

- 844×390, left 47: two-arg bar 211, inset bar 199, text unchanged, `safeX 47, safeY 0, safeW 797, safeH 390`.

`Touch.blocks(box)` and `Touch.snapRect(box)`, half-open:

```lua
score: x = safeX + margin,                 y = safeY + margin,                      w = max(0, safeW/2 - 2*margin), h = textSize
level: x = safeX + safeW/2 + margin,       y = safeY + margin,                      w = max(0, safeW/2 - 2*margin), h = textSize
lives: x = safeX + margin,                 y = safeY + safeH - margin - iconSize,  w = max(0, safeW/2 - margin),   h = iconSize
power: x = safeX + safeW - margin - barWidth, y = safeY + safeH - margin - barHeight, w = barWidth,               h = barHeight

side = math.max(Touch.MIN_TARGET, iconSize)
button = {
	x = safeX + safeW - 2 * margin - barWidth - side,
	y = safeY + safeH - margin - side,
	w = side, h = side,
}
```

Return that button always. On margin 5, icon 10, bar 40×4, text 10, safe 100×300 at the origin, the only rectangle is `{ x = 6, y = 251, w = 44, h = 44 }`. It overlaps lives. It does not overlap a forward rect whose reach is `max(iconSize, barHeight, MIN_TARGET)`, not the y or h the function just returned. That view is `{ x = 0, y = 20, w = 100, h = 231 }`. The fallback `y = safeY + safeH - 2*margin - barHeight - side` is 242 on this box and sits inside that view. A spec that only forbids overlap with lives forces the fallback. A spec that builds the view from the returned y passes it. Do not port the fallback. The older prototype box at `{ x = 46, y = 132 }` is the same bug on a different width.

Forward view. The reach is `max(iconSize, barHeight, Touch.MIN_TARGET)`, never a y or h returned by `Touch.snapRect`. On the three samples the button and the four blocks miss it (`h > 0`):

```lua
y = safeY + textSize + 2 * margin
bottom = safeY + safeH - margin - max(iconSize, barHeight, Touch.MIN_TARGET)
rect = { x = safeX, y = y, w = safeW, h = bottom - y }
```

On those samples `button.y` equals `bottom`, so the half-open overlap test misses. The narrow box above is the case that overlaps lives and still misses this view. The phone button's interior point is `Touch.zone` `"snap"` with the rect and `"look"` without it (it sits on the right half: 230 ≥ 195).

`HudView`:

- Assign `IgnoreGuiInset = true` and then `ScreenInsets = Enum.ScreenInsets.None`, in that order, so the `IgnoreGuiInset` side effect cannot leave `DeviceSafeInsets`. Set `SafeAreaCompatibility` to `None`. If the type library lacks an enum, cast `(Enum :: any)`. `ClipToDeviceSafeArea` does nothing once `ScreenInsets` is `None`.
- Do not read `GetGuiInset`. Do not build the snap rect from `AbsolutePosition`: the rect comes from Logic, in screen pixels. `AbsolutePosition`, `InputObject.Position` and `GetInsetArea` all share the core-UI origin; Controls converts touches to screen pixels with `Touch.toScreen` (f0027 AC5), so the rect and the touch meet in one space.
- Call `Hud.safeInset(GetInsetArea(Enum.ScreenInsets.None), GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets))` and pass that inset to `Hud.layout(sw, sh, inset)` with `local sw, sh = Touch.screenSize(none, camera.ViewportSize.X, camera.ViewportSize.Y)` on one line (`none` the same `GetInsetArea(None)` read this frame). `ViewportSize` is the device safe area (smaller than the screen on a notched phone: on the documented phone about 733×371 against 851×392, which would put the snap button at `{458, 297}` and end the bar 127 px short of the usable edge, design review 004 F1), so it is only the fallback and the re-layout signal; it never reaches `Hud.layout(` directly. While the area is empty the inset is all zeros and the size is `ViewportSize`, with no adapter branch. The cast form `(Enum :: any).ScreenInsets` is allowed.
- Place score, level, lives, and the power bar with offset pixels from `Touch.blocks` (or the same formulas). A 0.5 scale of the full ScreenGui is wrong once `safeX` is non-zero. With a zero inset and a full-viewport GUI, the offsets match today's positions.
- `BindToRenderStep` named `PickmanHud` rewrites when the screen size from `Touch.screenSize` or any of the four inset numbers changes, including from a first-frame empty area to the real one. The `PickmanHud` render-step callback itself makes both `GetInsetArea` reads (None and CoreUISafeInsets), `local sw, sh = Touch.screenSize(none, camera.ViewportSize.X, camera.ViewportSize.Y)` and `Hud.safeInset(none, core)`, compares the key `(sw, sh, top, bottom, left, right)` with the last one, and only when it changed calls a `lay(sw, sh, inset)` whose parameters carry the same names `sw` and `sh` and which calls `Hud.layout(sw, sh, inset)`. `lay` reads no area; nothing outside that callback calls `GetInsetArea(`; `HudView.show`'s re-layout on a life change reuses the last key. Before the first render step nothing is laid out (or `lay` runs once with `ViewportSize` and a zero inset, the documented empty-area fallback, passed in by the caller). This is what catches a first-frame empty area and a 180° turn between LandscapeLeft and LandscapeRight, which swaps the left and right insets without firing `ViewportSize` (design review 005 F2).
- Frame: `Instance.new("Frame")`, `.Name = "Snap"`, `Active = false`, not a `GuiButton`. Position and size from `Touch.snapRect` of the layout box. Visible (`BackgroundTransparency` below 1) so OC1 can tap it. `function HudView.snapRect(` returns the last rect, or nil before the first layout.
- Keep `Hud.layout(`, `Hud.safeInset(`, `ViewportSize` (f0019 pins the word), and `PickmanHud`. The `Hud.layout(` line does not contain `ViewportSize`. The source does not contain `GetGuiInset`. Do not add `FireServer` or `Remotes`.

`Main`, final call:

```lua
Controls.start(Camera.snap, Camera.lookBy, HudView.snapRect, Camera.holdMouse)
```

The source contains `HudView.snapRect` and `Controls.start(`. Adapters still start before `ready:FireServer()`. `HudView.snapRect` is a function Controls calls on each touch, so `HudView.start` may stay after `Controls.start`.

### Jump button corner (c0106)

Roblox's PlayerModule (`ControlModule/TouchJump`) draws its jump button in one of two places, measured from the bottom-right of the frame the touch GUI fills, and chooses small or large by that frame's smaller side (`minAxis <= 500` is small). Both placements are reserved, as two rectangles, not their bounding box (the bounding box would put the phone snap button `{230, 791, 44, 44}` inside it; the two rectangles miss it):

| frame | legacy button | ability-controls button |
|---|---|---|
| small | 70 px, offset `(W - 95, H - 90)` | 72 px, offset `(W - 136, H - 136)` |
| large | 120 px, offset `(W - 170, H - 210)` | 120 px, offset `(W - 220, H - 232)` |

```lua
Hud.JUMP = { -- data, not branches: a third placement is one more row
	small = { { right = 95, bottom = 90, size = 70 }, { right = 136, bottom = 136, size = 72 } },
	large = { { right = 170, bottom = 210, size = 120 }, { right = 220, bottom = 232, size = 120 } },
}
-- The jump button rectangles for a touch GUI filling the frame (x, y, w, h), legacy first.
-- w and h pass through side(); x and y are used as given.
function Hud.jumpButtons(x: number, y: number, w: number, h: number): { Box }
	-- set = small when math.min(side(w), side(h)) <= JUMP_SMALL_MAX, else large
	-- each row: { x = x + fw - right, y = y + fh - bottom, w = size, h = size }

-- How far the core-UI safe area's top sits below the device safe area's (the top bar), never negative.
-- Coordinate-space free: both areas come from GuiService:GetInsetArea in one space.
function Hud.bandTop(core: Area, device: Area): number -- side(core.Min.Y - device.Min.Y)

-- d0105's function gains two optional arguments. touch nil or false is exactly today's box (bandTop ignored).
function Hud.radarBox(width: number, height: number, size: number, touch: boolean?, bandTop: number?): Box
	-- as today: l = Hud.layout(width, height); s = side(size); x = side(width) - l.margin - s
	-- y = side(height) - (l.barHeight + 2 * l.margin) - s
	-- touch == true: band = side(bandTop or 0)
	--                top = the smallest y of Hud.jumpButtons(0, band, width, max(0, side(height) - band))
	--                y = math.max(band + l.textSize + 2 * l.margin, top - l.margin - s)
```

Two frames (review 002 F1). DangerHud's ScreenGui keeps `IgnoreGuiInset = true`, so its frame is the device safe area, top bar included; `width` and `height` are that frame. HudView and Roblox's touch GUI use the core-UI safe area, which starts `bandTop` lower (58 px under the landscape top bar of the documented sample). So inside `radarBox` the touch GUI's frame is `(0, band, width, height - band)`: that frame picks the small or large set (900×520 under a 58 px bar is a 462 px side, so small) and places the buttons; and the clamp is `band + textSize + 2*margin`, below HudView's LEVEL label (which ends at `band + margin + textSize` in the same coordinates, give or take a pixel because text comes from a slightly different viewport). The bottom and right edges of the two areas are the same on phones, so nothing else shifts.

The radar keeps its right edge and is lifted to one margin above the higher button (the ability one in both sets), and never into the top text band (`band + textSize + 2*margin`, see Two frames below): on a screen too short for both, the clamp wins and the radar may touch the buttons. `Hud.radarBox` keeps its frame coordinates: DangerHud's ScreenGui stays as it is (`IgnoreGuiInset = true`, so the device safe area), and its frame's bottom-right is the touch GUI's on the samples. DangerHud: `local UserInputService = game:GetService("UserInputService")` and `local GuiService = game:GetService("GuiService")` at the top; a `local function bandTop(): number` defined in `start` before the render step, returning `Hud.bandTop(GuiService:GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets), GuiService:GetInsetArea(Enum.ScreenInsets.DeviceSafeInsets))` (core first; `(Enum :: any)` casts allowed), read every frame because rotation changes it; and one changed line, `local box = Hud.radarBox(view.X, view.Y, radarSize, UserInputService.TouchEnabled, bandTop())`. The d0105 block stays four consecutive lines, so `bandTop` is a call inside the argument list, not a local between them. Still one `Hud.radarBox(`, one `radar.Position`, one `local view =`, before the snapshot guard. `DangerHud.start(Camera.pose)` in Main does not change (f0033 pins it).

The power bar and the snap control need no rule: on every sample their place already misses both buttons (the bar's top is `margin + barHeight` above the bottom, at most 20 px for any frame up to a 499 px smaller side, and the small legacy button ends 20 px above it). Two 1 px exceptions, neither a sample, and neither moves anything (the button cannot show today, E7): at a smaller side of exactly 500 the 23 px text makes the bar's lift 21 px, a 1 px overlap with the legacy button; and on a 320 px wide portrait screen (320×568) the snap button runs x 182–226 while the small legacy button starts at 225 (review 002 F2). A rule that shifted the snap button on narrow widths would change the pinned phone rectangles.

Short screens: when the core safe height cannot hold the text band, the radar, a margin and the jump buttons, the clamp wins and the radar overlaps the higher (ability) button, never the text. On a 320 px tall landscape screen under a 58 px top bar (480×320, 568×320) the radar is at y 86, below LEVEL (ends at 79), and overlaps the ability button (y 184 onward). This is accepted and pinned.

### Scalability
`layout`, `blocks`, and `snapRect` are a handful of arithmetic operations per viewport change, not per maze tile and not per snapshot. `radarBox` with touch runs on DangerHud's render step, as today: one more `Hud.layout` call's worth of arithmetic and a two-row loop, with two small tables. The inset is four numbers from the client. Nothing is replicated.

### Maintainability
The next inset (a custom safe rect from a device) is another four numbers into `Hud.layout`. If Roblox moves its jump button, or a game-owned touch jump control (the spy hop) takes that corner, it is a row in `Hud.JUMP`, not a new branch. The button formula is one expression in `Touch.snapRect`; HudView does not reimplement it. Text scale stays `Hud.TEXT_SHARE` of the full smaller side, which is the rule f0019 already tests.

### Usability
Text never drops below 14 px, including on a notched phone, because the notch does not shrink the type. The snap control is at least 44 px on each side, in the lower-right margin, and a point in it is the snap zone rather than a look drag. Score, level, lives, and the power bar stay in the margin bands. On a touch screen the radar sits above Roblox's jump corner, so a thumb on that corner never covers it. The center is the forward view, apart from d0105's radar overlay in its lower right: on 1920×1080 it is `{ x = 0, y = 80, w = 1920, h = 936 }`; on the notched phone `{ x = 0, y = 83, w = 390, h = 708 }`; on the landscape phone `{ x = 47, y = 36, w = 797, h = 301 }`.

`layout`'s third argument is optional. `snapRect` takes a box, not a Roblox instance.
