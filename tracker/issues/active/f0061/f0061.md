## Problem
The experience is a single place that hosts the game. The user wants it split in two (2026-10-02): "create a new place in the experience, this new place will host the actual game and the current one will show a highscore list and a 'start game' button and once you click the start game you are teleported to new place". Today there is no lobby, no second place and no way to move a player between places.

## Non-goals
- The hiscore storage, submission and board contents (R0011: f0024, f0025, f0026). The lobby only hosts a panel for the rows the boards will give.
- Teleporting back to the lobby at game over, and the game-over overlay (f0065, a later raft: it needs c0063 first).
- Publishing the lobby and configuring the place ids (c0064). Until it lands, Beta publishes only the game place, so the lobby is not live there.
- Matchmaking, parties, private servers, passing data to the game place.

## Solution
A second Rojo project, `lobby.project.json`, builds the lobby place. The current `default.project.json` stays as it is and is the **game place**. The lobby shows a black screen with the hiscore panel (an empty state until R0011 gives it rows) and a START GAME button. A press is a payload-free request to the server, which asks a pure `Travel` whether this player may go, and only then calls `TeleportService` with the destination from configuration. Failures and silence are handled by `Travel` (a timeout and a cool-down), so the player sees a message and may try again.

## Design
### Decisions made in prep (author's choices; the user may veto)
- **Which place is which**: the existing place becomes the lobby (it is the experience's start place and keeps `ROBLOX_BETA_PLACE_ID`), and a new place hosts the game. In this repository `default.project.json` is the game place and `lobby.project.json` the lobby, so every existing spec, tool and the Beta runtime tests keep working unchanged until c0064 moves them.
- **The destination is configuration, not discovery**: an attribute `GamePlaceId` on `ServerScriptService`, `0` as checked in (which the lobby reads as "not set up": a disabled UNAVAILABLE button, never a stray teleport). The publisher (c0064) writes the real id into a copy of the project before building (E3). It is not looked up at runtime by place name, because that call cannot be proven offline, and the client never sends an id.
- **The hiscore panel is a model with an empty state** (user: "Empty panel now"). `Lobby.Row` is the interface R0011's board will fill; this raft does not read any store.
- **Failure handling**: one teleport per player at a time; while the engine call has not returned the player stays "going" (up to a **60 s cap**, so a hung call cannot lock the lobby for ever); once it has returned, nothing happening for **15 s** counts as a failure; after a failure the button waits **3 s** and shows "Could not start. Try again in a moment." Each request gets a **ticket**: the report of a call that was given up on at the cap names its own (old) ticket and is ignored, so it can neither cool down nor shorten the newer request. Only `TeleportInitFailed`, which carries no request id, applies to the current request (accepted).
- **No data is passed in the teleport**: the game place needs nothing from the lobby, the player's identity is the Roblox user.
- **The lobby has no character and no camera control**: a black backdrop covers the screen, the mouse is free, the button is at least 44 px tall (design: Mobile) and works for touch through `Activated`.

### Files and API

- `src/shared/Logic/Travel/init.luau` (new feature): whether a player may be sent to another place now.
- `src/shared/Logic/Lobby/init.luau` (new feature): what the lobby screen shows.
- `src/lobby/server/Main.server.luau` and `Starts.luau`, `src/lobby/client/Main.client.luau` and `LobbyView.luau` (new adapters).
- Tooling: `tests/lib/place.luau` (`place.load(project)`, the lobby script roots), `scripts/lib/graph.luau` (the selector counts `lobby.project.json` as a place change), `scripts/check.sh` (builds `lobby.project.json`), and the new test helper `tests/lib/fakeengine.luau`.
- **The fake engine** (`tests/lib/fakeengine.luau`) loads an adapter's real source with `@lune/luau`'s `luau.load(source, { environment })` and runs it against: instances with `Name`, `Parent`, children, `:WaitForChild` (a missing name fails the spec, naming the path), `:FindFirstChild`, child-by-name by dot index, `:GetChildren`, `:GetDescendants` and `:GetAttribute`; the lobby's **built place** supplies the remotes (`StartGame`, `Status`) and the `ServerScriptService` attributes, so a wrong name in an adapter fails and the project file and the adapters cannot drift apart; signals whose handlers run in a coroutine each (a yielding handler stays suspended); `pcall` across a yield; `task.spawn`, `defer`, `delay` and `wait` driven by the fake clock; `os.clock`, `Instance.new`, `Enum`, `UDim2`, `Vector2` and `Color3` as plain data; and the real Logic modules through `@game/ReplicatedStorage/Shared/Logic/<Feature>`. **That surface is the contract, exact in both directions**: an adapter may use any idiom within it (the specs accept `WaitForChild` or a dot index, any order of `Name` and `Parent`, `task.*`, `TeleportOptions` passed to `TeleportAsync`), and an executor who needs a service or a call outside it extends the fake (an extension is judged in code review: the fake must neither accept less than it does now nor accept more: the Rules table's mutants that depend on it, run as exact substitutions, must still fail, and the four correct variants must still pass). It models nothing about what the real engine does with `TeleportAsync` (E7).
```lua
-- Travel
export type Phase = "idle" | "going" | "cooling"
export type Config = { goingSeconds: number, coolSeconds: number, capSeconds: number }
export type Entry = { phase: Phase, deadline: number, cap: number, ticket: number }
export type Travel = { config: Config, entries: { [string]: Entry }, serial: number }
export type Answer = "go" | "busy" | "cooling"
Travel.DEFAULT: Config                                   -- frozen: goingSeconds 15, coolSeconds 3, capSeconds 60
Travel.MAX_PLACE_ID = 2^53 - 1
Travel.new(config: Config?): Travel
Travel.destination(raw: any): number?                    -- a whole number 1..MAX_PLACE_ID, as a number or as digits; else nil
Travel.status(t, id: string, now: number): Phase         -- a going request past its deadline becomes cooling (a failure)
Travel.request(t, id, now): (Answer, number?)            -- "go" records the request (deadline = the cap) and returns its ticket; "busy" or "cooling" say why not (no ticket)
Travel.answered(t, id, now, ticket: number?)             -- the engine call returned: the timeout now counts 15 s from here, never past the cap (nothing unless going, or for another ticket)
Travel.failed(t, id, now, ticket: number?)               -- the engine said no: cool down (nothing unless going, or for another ticket; no ticket = the current request)
Travel.left(t, id)                                       -- forget the player
-- Lobby
export type Row = { rank: number, name: string, score: number, level: number }
export type Panel = { title: string, rows: { Row }, empty: string? }
export type Button = { text: string, enabled: boolean, message: string? }
Lobby.TITLE = "HISCORES"; Lobby.EMPTY = "No scores yet"; Lobby.MAX_ROWS = 10; Lobby.BUTTON_MIN_PX = 44
Lobby.panel(rows: { Row }?): Panel                       -- ranked, at most MAX_ROWS, copies; the empty message only with no rows
Lobby.button(status: Travel.Phase, configured: boolean): Button
-- the lobby's remotes: StartGame (client to server, no arguments); Status (server to client: phase: Phase, configured: boolean)
-- the lobby's configuration: ServerScriptService attribute GamePlaceId (number; 0 = not set up)
-- the tooling: place.load(project: string?): Instance (default "default.project.json"), cached per project
```
- **`Starts` (server)**: reads `ServerScriptService:GetAttribute("GamePlaceId")` through `Travel.destination`. On `StartGame` (one parameter, the sending `Player`): with no destination it reports `idle` and stops; otherwise `local answer, ticket = Travel.request(travel, id, os.clock())`, and on `"go"` it reports `going` and calls `pcall(TeleportService.TeleportAsync, TeleportService, destination, { player })`; a call that returns calls `Travel.answered(..., ticket)` with the clock read at that moment; a failed call calls `Travel.failed(..., ticket)`, and `TeleportService.TeleportInitFailed` calls `Travel.failed` with no ticket; each then reports whatever `Travel.status` now says (a report that changed nothing is not shown as a failure). A status is never sent to a player who has left (`player.Parent == nil`: a slow call can fail after the player closed the app), and `PlayerRemoving` forgets what was shown. `PlayerRemoving` calls `Travel.left`. Once a second a Heartbeat step reports `Travel.status` for every player, so a cool-down or a timeout ends on screen by itself. A status is sent only when it differs from the last one shown to that player; a player is told the state once at first (on joining, or on the first press).
- **`LobbyView` (client)**: a ScreenGui "Lobby" with a black `Backdrop`, the title and the panel text from `Lobby.panel(nil)`, a message line and the `Start` TextButton (height `Lobby.BUTTON_MIN_PX` plus a fraction of the screen). `Status` events redraw the button from `Lobby.button(phase, configured)`; `Activated` fires `StartGame:FireServer()` with no arguments.

### Pure/adapter split and authority
Everything that decides is pure: whether a request may go, what the button says, the panel. The adapters translate the engine's events and answers into those calls and draw the result. **The server is authoritative**: the client sends no data at all, the destination is server configuration, and a spammed press is a no-op (one phase check, no engine call).

### Scalability
Per player one small entry; a once-a-second Heartbeat step over the players of the server (O(players), at most a few dozen); one `Status` message per change of phase per player; nothing is replicated while the lobby is idle. The game place is not touched.

### Maintainability
- A further place is a further `*.project.json` and `src/<place>/`: `place.load` and the selector take the project, so its specs come with it.
- `Travel` is the one place that knows when a transfer may happen: the return trip (f0065) reuses it unchanged.
- `Lobby.panel` takes rows from any board; the strings and numbers are named constants.

### Usability
- **Player**: one big button; it says STARTING... while the teleport runs, says what went wrong and when to try again, and cannot be pressed twice; the mouse is free; touch works.
- **Developer**: `rojo serve lobby.project.json` and Connect opens the lobby in Studio; setting `ServerScriptService.GamePlaceId` to a place id turns the button on. Two small typed features and two thin adapters, and a fake engine to test them against.

## Unknowns & experiments
All run on a prototype in the prep worktree (`tracker/rafts/R0024/experiments/prototype.patch`); the executor starts from it, not from nothing.
- **E1** Does Rojo put an attribute on a service from the project file, and does it survive a build? **Pass**: `ServerScriptService:GetAttribute("GamePlaceId")` reads `0` (a number) after `rojo build` and `roblox.deserializePlace`.
- **E2** Does the existing type-check stage cover the lobby's files? **Pass**: `luau-lsp analyze src` with the game's sourcemap reports a deliberate type error and a bad `@game/...` require in `src/lobby`, the same as with a lobby sourcemap, and resolves `./Starts` between the lobby's files. No new analysis stage is needed; the lobby build itself is checked by `lobby-place.spec`.
- **E3** Can a publisher inject a different place id? **Pass**: a copy of the project with `GamePlaceId` set to `987654321` builds to a place that reads it back (the mechanism c0064 uses).
- **E4** Does the test selector see `lobby.project.json`? **Fail, then fixed in the prototype**: it listed only `default.project.json`, so a change to the lobby's project selected no place spec. `scripts/lib/graph.luau` now counts both; `lobby-tooling` pins it.
- **E5** Does the whole gate stay green with the prototype? **Pass**: 928 cases in 140 spec files on current main, with the existing place specs unchanged. Two bugs the architecture specs found in the first prototype, both fixed: the lowercase word `game` in a Logic string ("Logic never touches the Roblox engine"), and the undeclared edge `Lobby -> Travel`.
- **E6** `until` is a Luau keyword: the first `Travel` entry used it as a field name and did not parse. Renamed `deadline`.
- **E8** Can a spec run an adapter's real source without Roblox? **Pass** (from design review 001): `@lune/luau`'s `luau.load(source, { environment })` runs `Starts` and `LobbyView` against a fake engine (`tests/lib/fakeengine.luau`: an instance model whose remotes and attributes come from the built lobby place, signals whose handlers run in coroutines so a yielding `TeleportAsync` can be held, `task.*` on a fake clock, `Instance.new`) and the real Logic. Review 002 found the first fake blind to names and the tree, and too strict about idioms; it now fails a wrong attribute or remote name, an unparented screen and a white backdrop, and accepts `WaitForChild` or dot index, `TeleportOptions`, `task.*` and any `Name`/`Parent` order (the four correct variants run as mutants that must pass). Five presses give one engine call; the mutants that move the call outside the guard or silence the client's `Status` handler now fail on assertions. The fake proves nothing about what the real engine does (E7).
- **E9** Luau infers `local x = Travel.request(...)` as `string | string | string` in a consumer, so a spec that passes it on as `Travel.Answer` fails the promotion type check unless the local is annotated; `Travel.request` also needs an annotated local for its own `if` expression. Found by `promote-check` on the prototype.
- **E7 (not provable offline)** What `TeleportService` does: success, `TeleportInitFailed`, the refusal in Studio, a slow reply. **Method**: the Observed criterion O1 in Studio, and O2 in Beta once c0064 publishes the lobby. **Fallback**: the 15 s timeout and the 3 s cool-down make any non-answer a recoverable failure; if `TeleportAsync` needs `TeleportOptions` for the destination, only the one call in `Starts` changes.
