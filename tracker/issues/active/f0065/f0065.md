# f0065: Game over returns to lobby

## Problem
The game place hosts the game, and the lobby (R0024, f0061) is where the hiscore list and the start button are. User, 2026-10-02: at game over, "an overlay shows the game results and waits for a tap before teleporting back to lobby". Today (R0015, f0031, built) game over offers PLAY AGAIN inside the game place; there is no way back to the lobby.

## Non-goals
- The lobby, its start button and the teleport into the game place (f0061).
- Hiscore submission and the board (R0011).
- Publishing both places and configuring their ids (c0064).

## Solution
At game over the overlay keeps the results (GAME OVER, `SCORE s   LEVEL n`, the 0.6 fade) and, instead of PLAY AGAIN, a prompt **TAP TO RETURN TO THE LOBBY**. A tap anywhere on the screen, a click, or Enter sends one payload-free `ToLobby` request. The server accepts it only when Logic says that player's run is over (`Session.isOver`), then teleports the player to the lobby with f0061's `Travel` rules (one request at a time, a 15 s timeout after the engine call returns, a 60 s cap, a 3 s cool-down), and reports the trip on `LobbyStatus`, so the prompt can say RETURNING… or "Could not return. Try again in a moment." The lobby's place id is configuration on the game place: the attribute `LobbyPlaceId` on `ServerScriptService`, `0` as checked in ("not set up"), like `GamePlaceId` on the lobby.

## Design
### Decisions made in prep (author's choices; the user may veto)
- **A tap anywhere** continues (the user's "waits for a tap"): an invisible full-screen button, shown only while a tap asks, plus `Return`/`KeypadEnter` on desktop. No delay before a tap counts: game over follows the 3 s (real time) dying pause, so a stray tap from play is unlikely, and swipes are not taps.
- **Texts** (`Flow.PROMPT`): idle "TAP TO RETURN TO THE LOBBY"; going "RETURNING TO THE LOBBY..."; cooling "Could not return. Try again in a moment."; not set up "The lobby is not set up yet." The results stay on screen in every case.
- **Not set up** (`LobbyPlaceId` 0 or invalid: Studio, or Beta before c0064 sets it): the prompt says so and a tap does nothing; there is **no fallback to playing again**, mirroring the lobby's UNAVAILABLE button (f0061). In Studio a finished run therefore ends at the results; stop and Play again.
- **Before the first report** the client assumes "idle, set up" (`Flow.NO_REPORT`): the server answers a request with the truth, so the worst case is one ignored tap followed by the right prompt. The server reports the state when the player joins and once a second after a change, so this window is about a second at the start of the run, long before any game over.
- **Logic's play again stays**: `Session.playAgain`/`Game.playAgain` are kept (pinned by f0016, f0017, f0018, f0023, f0030 specs) but nothing in the game place calls them any more.
- **Returns mirrors the lobby's `Starts`** rather than sharing code with it: the two live in different Rojo roots (`src/server`, `src/lobby/server`), and a server module in `ReplicatedStorage.Shared` would replicate to clients. All decisions are in `Travel`, so the copy is wiring only (about 90 lines). A third trip would extract a shared adapter.
- **Cursor**: free (and shown) for the whole game over, whatever the trip state (`Overlay.cursor`), so the mouse never re-locks under the results.

### Logic
`src/shared/Logic/Session/init.luau` (added):
```lua
-- Whether this player's run is over (the results are up). A player the session doesn't know has no run.
function Session.isOver(s: Session, id: PlayerId): boolean   -- members[id] ~= nil and its play.phase == "gameover"; never errors
```
`src/shared/Logic/Flow/init.luau` (changed; new edge **`Flow -> Travel`**, for `Travel.Phase`, declared in `tracker/architecture.md` in this prep):
```lua
export type Trip = { phase: Travel.Phase, configured: boolean }    -- the server's latest LobbyStatus
export type Overlay = {
	banner: string?, detail: string?, fade: number, flash: boolean,  -- unchanged
	prompt: string?,   -- game over only: Flow.PROMPT[trip.phase], or PROMPT.unset when not configured
	tap: boolean,      -- game over and configured and trip.phase == "idle"
	cursor: boolean,   -- game over only
}  -- the playAgain field is gone
Flow.CONTINUE_KEYS = frozen { "Return", "KeypadEnter" }   -- replaces PLAY_AGAIN_KEYS
Flow.PROMPT = frozen { idle = …, going = …, cooling = …, unset = … }   -- the texts above, exactly
Flow.NO_REPORT = frozen { phase = "idle", configured = true }
function Flow.overlay(play: Session.PlayFrame, rules: Game.Config, trip: Trip?): Overlay   -- trip nil = NO_REPORT; pure, fresh table, inputs untouched
function Flow.isContinueKey(keyName: string): boolean   -- replaces isPlayAgainKey
```
| phase | banner | detail | fade | flash | prompt | tap | cursor |
|---|---|---|---|---|---|---|---|
| ready / playing / dying / levelclear | as f0031 | as f0031 | as f0031 | as f0031 | nil | false | false |
| gameover | GAME OVER | SCORE s   LEVEL n | 0.6 | false | by trip (above) | configured and idle | true |

The `trip` argument is optional so two-argument callers (f0031's promoted `presentation-run`) keep type-checking. Logic word rule: no lowercase `game` and no `Enum` in Flow's source.

### Server (`default.project.json`, `src/server`)
- `default.project.json`: `Remotes` = `Ready`, `Intent`, `Snapshot`, **`ToLobby`** (client→server, no arguments), **`LobbyStatus`** (server→client: `phase: Travel.Phase, configured: boolean`); `PlayAgain` removed. `ServerScriptService` gets `"$attributes": { "LobbyPlaceId": 0 }`. (The game place must not carry `GamePlaceId`, `StartGame` or a `Lobby` folder: `f0061/lobby-place` pins that.)
- `src/server/Sessions.luau`: the `PlayAgain` handler is removed. The `sessions` table moves to module scope and `Sessions.isOver(player: Player): boolean` returns `sessions[player] ~= nil and Session.isOver(<s>, tostring(player.UserId))`. The source must keep containing no `PlayerAdded`, `gameover` or `.phase` (f0013, f0018, f0031 specs).
- `src/server/Returns.luau` (new): `Returns.start(isOver: (Player) -> boolean)`. Destination `Travel.destination(ServerScriptService:GetAttribute("LobbyPlaceId"))`. On `ToLobby` (one parameter, the sending `Player`; anything else is ignored): if `not isOver(player)` return with nothing sent; if no destination, report `idle` (configured false) and return; otherwise `Travel.request`, and on `"go"` report `going` and `pcall(TeleportService.TeleportAsync, TeleportService, destination, { player })`, then `Travel.answered(…, ticket)` with the clock at return, or `Travel.failed(…, ticket)` and report. `TeleportInitFailed` → `Travel.failed` (no ticket) and report. `PlayerAdded` → report `idle`; `PlayerRemoving` → `Travel.left` and forget what was shown. A Heartbeat step once a second reports `Travel.status` for every player. A report is sent only when it changed, never to a player whose `Parent` is nil. This is f0061's `Starts`, line for line, plus the `isOver` gate.
- `src/server/Main.server.luau`: `local Sessions = require("./Sessions"); Sessions.start(); require("./Returns").start(Sessions.isOver)`. `Sessions.start` must not declare a second, local `sessions` table (it would shadow the module's and `isOver` would always be false; `sessions.spec` runs the real module to catch it).
- `tests/runtime/structure.luau`: asserts `ToLobby` and `LobbyStatus` instead of `PlayAgain`, and that `ServerScriptService.LobbyPlaceId` is a number (c0064 may set a real id; the check doesn't care which).

### Pure/adapter split and authority
The client sends one argument-free intent. The server decides with Logic: `Session.isOver` (is this player's run over) and `Travel` (may it go now). The destination is server configuration. A spammed request costs one phase check, or one `Travel` check at game over.

### Scalability
Per frame on the client: one `Flow.overlay`, O(1), a few GUI writes. Per server: one `Travel` entry per player who asked, a once-a-second O(players) status step, one `LobbyStatus` message per state change per player. Nothing new is replicated per frame.

### Maintainability
- `Flow.PROMPT` and `Flow.CONTINUE_KEYS` are data; another end-of-run action (a hiscore entry, R0011) adds an overlay field and a row, not new branches in the adapters.
- `Travel` is shared with the lobby unchanged; `Returns` is a thin copy of `Starts` (see decisions).
- `Session.isOver` is the one place that says when a run is over, for any later server feature (hiscore submission).

### Usability
- **Player**: the results stay up until they choose; one tap anywhere (or Enter) goes back; the prompt says when the trip is under way or failed, and when to try again; the mouse is free. Touch works through `Activated`, and the tap target is the whole screen.
- **Developer**: `LobbyPlaceId` on `ServerScriptService` turns the way back on in Studio; the fake engine runs the game place's adapters as it runs the lobby's; `Flow.overlay` stays one pure function with a table of outcomes.
