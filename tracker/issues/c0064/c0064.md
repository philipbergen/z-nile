# c0064: Publish lobby place

## Problem
R0024 (f0061) splits the experience into two places: the existing place becomes the lobby, and a new place hosts the game. The Beta deploy (`scripts/deploy-beta.luau`, the `beta` job of `.github/workflows/check.yml`) builds and publishes only `default.project.json` to the one place named by `ROBLOX_BETA_PLACE_ID`, and the runtime tests (`tests/runtime`) run in a server of that place. The lobby build is never published, its destination ids are never set (the checked-in `GamePlaceId` is 0, which the lobby reads as "not set up"), and the game place has no id to be published to.

## Non-goals
- The lobby and the teleports themselves (f0061); production publishing (undecided, see tracker/game-design.md).
- Creating the second place in Roblox: that is the user's step (an Open Cloud key scoped to the experience already covers its places).

## Solution
_Draft ideas; design happens in ticket-prep._
- A new repo variable, `ROBLOX_BETA_GAME_PLACE_ID`, for the game place; `ROBLOX_BETA_PLACE_ID` stays the experience's start place, which is now the lobby (SETUP.md says so).
- Deploy builds both projects and publishes each to its place. It injects the other place's id before building, by writing a copy of the project file with the `GamePlaceId` (lobby) attribute set; the experiment in f0061's E3 shows a built copy carries the value.
- The runtime tests run per place: the structure checks for the game place in a server of the game place, and new ones for the lobby.
- When not configured it still skips with a warning and succeeds, as today.
