# c0069: Launch raft

## Problem
Execution starts with `scripts/tracker.sh launch <R>`, which makes the worktree and then `exec`s `claude` inside it. The tracker CLI then starts AI sessions. The user wants the opposite: the AI session drives, and `tracker.sh` handles mechanics only. After c0067 the prompt lives in `tracker/rafts/active/<R>/prompt.md`, so a session can start execution itself.

The user wants a **launch-raft** skill that:
- reads that prompt;
- fails when the raft is not readied or the prompt is missing;
- goes to work.

`tracker.sh launch` is removed.

## Non-goals
- Starting the session for the user. The human starts Claude in the main checkout and types `/launch-raft R…`.
- Changing the hooks. `post-edit.sh` already acts on the edited file's tree, and `stop.sh` on the session's current directory. Once the skill `cd`s into the worktree, both act there (the user's decision, 2026-10-03; c0005's AC4 specs pin both).
- Running other agents (Grok, …). They get the prompt with `tracker.sh prompt <R>`.

## Solution
- **`tracker.sh prompt <R-id> [--path]`** becomes the reader. It checks that the raft is readied on `origin/main` and that `prompt.md` exists in the main checkout. Then it prints the prompt, or with `--path` only its absolute path.
- **The launch-raft skill** runs it, reads the file, `cd`s into `$(scripts/tracker.sh worktree <R>)`, and follows the prompt.
- **`tracker.sh launch`** is deleted from `scripts/tracker.sh`, USAGE, the skills and the docs. Its promoted spec cases go.

## Design

### `cmd.prompt(pos, opts)`, `prompt <R-id> [--path]` (`scripts/tracker/main.luau`)
1. `pos[1]` must be a raft id. Anything else fails with `prompt takes a raft id (an issue's raft: tracker.sh find <id>)`. It runs from any checkout: the main checkout or a worktree.
2. `git fetch --quiet origin main`. The decision is made from `origin/main`'s tree (`ls-tree`) and never walks the local store, so a stale directory in the main checkout can't make it fail differently. On `origin/main` the raft must be in `active/` with an effective status `active`. Otherwise fail with `<R> is not readied: run /ready-raft <R> (tracker.sh ready <R>) in the main checkout`. With no origin, it fails the same way.
3. If `promptPath(R)` (in the **main checkout**, `mainRoot()`) is not a file, fail with `no prompt for <R>: run tracker.sh ready <R> in the main checkout to regenerate it`.
4. With `--path`, print the absolute path. Otherwise print the file's content exactly (`stdio.write`, with no added newline).
- `--path` joins the boolean flags in `flags()`. `--stdout` is gone.
- `prompt` writes nothing anywhere, and refuses a raftless issue (the old raft-making path is deleted).
- `prompt` stays out of `READ_ONLY` (review 002 F6): the repository guard still runs first. c0053's `commands.spec` case, which lists `prompt` among the guarded commands in a `.git`-less sandbox, depends on it. `ready` and `stop` stay out of it too.

### `scripts/tracker.sh`
Delete the whole `launch` block (lines 7–30 today). `tracker.sh launch …` then reaches Lune, which prints USAGE and exits 1 (an unknown command). The comment on `exec lune` stays.

### USAGE
- `prompt <R-id> [--path]`: print a readied raft's `prompt.md` (`--path`: its path).
- The `launch` line is removed. USAGE never contains the word "launch", not even `/launch-raft` (RC4 and prompt.spec check the plain substring).

### Skills and docs
- **`.claude/skills/launch-raft/SKILL.md`** (new, `name: launch-raft`). The description: start executing a readied raft in this session ("launch R0001", "/launch-raft"). It fails when the raft isn't readied or has no prompt. Steps:
  1. **Read the prompt.** Run `scripts/tracker.sh prompt <R> --path`. If it fails, stop and report its message: the raft isn't readied (run `/ready-raft <R>`), or the prompt is missing (run `/ready-raft <R>` again to regenerate it). Never reconstruct a prompt by hand.
  2. Read the whole file at that path with the Read tool, in chunks if needed. Don't print it through Bash: the output would be truncated.
  3. **Enter the worktree.** The prompt's hard rule 2 says to run `cd "$(scripts/tracker.sh worktree <R>)"` first. From then on, work only there, with absolute paths for subagents.
  4. **Follow the prompt** as your instructions, from its first line: the execute-raft protocol, through the merge.

  The skill also says:
  - Start the session in the main checkout, which stays on `main`.
  - Other agents (Grok, …) get the same text from `scripts/tracker.sh prompt <R>`.
- **Tracker skill, Worktrees item 3**: "Launching an agent" becomes "Starting execution". The human starts a Claude session in the main checkout and runs `/launch-raft <R>`. The skill reads the prompt and `cd`s into the raft's worktree. The hooks follow the session's current directory, and subagents get absolute worktree paths.
  - Item 1's allowed list: replace `launch` with `prompt <R-id>`. Keep `worktree` and `worktree-prune`.
  - The lifecycle table's `launch` row is removed.
  - Keep the c0046 markers that its `check.sh` AC6 still requires: `.worktree/` and "never outside".
- **ready-raft skill** (c0067): the report's next step is `/launch-raft <R>`.

### Scalability
`prompt` does one fetch and one `ls-tree`.

### Maintainability
- The CLI loses its only bash-level command, so `scripts/tracker.sh` is a single `exec`.
- One reader (`prompt`) defines "readied and has a prompt" for every consumer.

### Usability
- The session drives.
- Every failure names the fix (`/ready-raft`).
- `--path` avoids Bash output truncation for large prompts.
