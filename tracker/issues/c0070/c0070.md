# c0070: Done ready before final push

## Problem
`tracker.sh done` pushes its final commit while the PR is still a draft, so CI skips it (the workflow runs `if: draft == false`). It then runs `gh pr ready`, and the ready-for-review run tests the **previous** head. The final commit, the one that promotes acceptance specs into `tests/` and moves the items to `done/`, never gets a CI run of its own.

Seen on R0010 (a manual dispatch was needed, run 36519133807) and again on R0060 (2026-09-30): the final head `01a19a8` had only a `SKIPPED` run until the PR was converted to draft and back to ready by hand. The tracker skill's Merging step 3 documents that workaround as agent behaviour ("`SKIPPED` ... means keep waiting; if no `gate` run appears, dispatch one"), so every raft pays minutes of polling plus a manual step, and a human reading `SKIPPED` can't tell a draft skip from a real result.

## Non-goals
- Changing the CI trigger policy for drafts (`.github/workflows/check.yml` stays as it is).
- Avoiding the extra CI run that `ready_for_review` starts on the previous head. It is wasted compute, accepted: cancelling it needs a workflow concurrency group, which is a policy change.
- Anything about `start` (it still opens a draft PR).

## Solution
Move `gh pr ready` to just before the done commit is made and pushed, after every verification step. The push then happens on a non-draft PR, so its `synchronize` event starts a real `pull_request` run on the final head. If `gh pr ready` fails, `done` rolls back exactly as it already does when promotion fails, so a failed `done` leaves nothing half-applied. The PR body edit (spend summary) stays after the push, because it needs `spend.md`, which `recordAndCommit` writes; editing a PR body doesn't trigger CI (the workflow lists `opened`, `synchronize`, `reopened` and `ready_for_review` only).

## Design

### `cmd.done` in `scripts/tracker/main.luau`
Today the order is: clean tree, `reviewProblem`, `runCheck`, promote acceptance specs (`git mv`) and `promotedChecks` (rollback on failure), move members and raft to `done/`, `recordAndCommit` (commit and push), then `gh pr ready`, `gh pr view`, `gh pr edit`.

New order: the same up to and including the promotion checks, then

```lua
-- Mark the PR ready before the final push: CI skips drafts, so the push below is what gets tested.
if hasUpstream() and onGitHub() and not sh.run("gh", { "pr", "ready" }).ok then
	sh.git({ "reset", "-q", "--hard", "HEAD" })
	fail("could not mark the PR ready (rolled back); fix gh and retry done")
end
```

placed immediately before the loop that moves the members to `done/`; then the moves, `recordAndCommit`, and (when `hasUpstream() and onGitHub()`) only `gh pr view` and `gh pr edit` remain after the push. The rollback is the same `git reset -q --hard HEAD` that the promotion failure path uses, which undoes the staged `git mv` promotion.

- **Why not push first, then ready, then an empty commit?** An extra commit pollutes history and still leaves the first push untested.
- **Why not `gh pr ready` first of all?** If the review check, `check.sh` or the promotion checks then failed, the PR would be ready for review although `done` refused. Placing it after the last verification means it only runs when `done` will go through.
- **Events on GitHub**: the `ready_for_review` event runs the gate on the previous head (wasted, accepted), and the following push runs it on the final head with the PR already non-draft. Merging step 3 in the tracker skill therefore keeps polling for `headRefOid == git rev-parse HEAD` and the `gate` for that sha.
- **Failure after the ready call** (the commit or push fails, for example no network): the PR is ready while its head is stale. `done` has already moved the items locally, so the human re-runs `git push`. This window is a few seconds and the same exposure `done` had between its push and `gh pr ready` before; it's recorded in Risks.

### Skills (documentation)
- `.claude/skills/tracker/SKILL.md`: the `done` row says it marks the PR **ready** before its final push; Merging step 3 no longer says "`done` pushes and then marks the PR ready, and the ready event starts the `pull_request` run" and says the push starts it.
- `.claude/skills/execute-raft/SKILL.md`: unchanged unless it states the old order (it doesn't).

### Scalability
One more `gh` failure path, no loops. Nothing grows with repository size.

### Maintainability
The ordering is one block with a comment saying why. The spec pins the order by observation (what origin holds when `gh pr ready` runs), not by reading the code, so a later refactor of `done` can't silently restore the old order.

### Usability
For an agent: Merging step 3 becomes "wait for the `gate` on the final sha" with no draft special case to explain. For a human: a failed `done` is atomic and says what to do.

## Unknowns & experiments
- **E1 (run in prep: PASS)**: can `done`'s GitHub branch be driven headlessly, with the order of `gh pr ready` and the push observable? `onGitHub()` only tests that the origin URL contains `github.com`, so a local bare repository at `<tmp>/github.com/fixture.git` makes `done` take that branch while pushes stay local. A fake `gh` first on `PATH` records its calls and, on `pr ready`, the branch head that origin has at that moment.
- **E2 (run in prep: PASS)**: does the spec catch the bug, and does the designed order satisfy it? On the current code the spec fails (origin already has the final head when `gh pr ready` is called). With the designed order applied to a scratch copy of `main.luau` it passes 4/4, and the scratch copy was then reverted.
- **E3 (run in prep, found a spec gap)**: does the spec observe the rollback? With a fixture raft that had no acceptance spec, the "no rollback" mutant survived, because nothing had been staged yet when `gh pr ready` failed. The fixture now includes an acceptance spec for `done` to promote; the mutant dies.
- **Residual**: the real GitHub behaviour (that a push to a non-draft PR starts a `synchronize` run on the final head) is the documented Actions behaviour, observed on every raft's earlier pushes; OC1 confirms it once on the next raft.
