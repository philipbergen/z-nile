# c0075: Fixture helper fences git in the commands it runs

## Problem
`@tests/lib/fixture` checks where a command starts, not what it does (R0021 review 001 F4, fixed in part). A shell command run through `fixture.exec` (`sh -c 'cd <elsewhere> && git …'`) starts in a proven fixture and can then run git anywhere. On macOS the jail still stops writes outside `.cache`, but on Linux (no jail) only review catches it. `retrofit.spec` bans raw shell strings, but not shell strings passed through the helper.

What can go wrong on Linux, unjailed: the runner already refuses ref updates and pushes into the real repository. A shell command that `cd`s into the real checkout can still run `git checkout -- .`, `git reset --hard` or `git clean -fd`, which rewrite or delete working files without updating a ref.

## Prep history (R0026, 2026-10-04)
Prepped in R0026 and dropped from it by the user's decision after three design rounds. Each round found high holes in the shim's model of how git names a repository (`tracker/rafts/R0026/design-review-001.md` to `-003.md`, with the answers in `design-refute-*.md`). The design below is the round-2 version, and these are still open (round 3):
- a `commondir` file naming an outside repository passes both paths;
- `extensions.worktreeConfig` with `config.worktree` passes the fast path;
- `[core] worktree = …` on the section's own line evades the config trigger;
- `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY` and `worktree move` have no spec case;
- commands git itself starts (`!` aliases, hooks, `rebase --exec`, `submodule foreach`) find the real git before the shim.

The likely right mechanism is not a better shim but a real jail on Linux (a mount namespace or bubblewrap that binds the checkout read-only except `.cache`), the Linux counterpart of the macOS jail. The prototype of the shim (never landed) was in `.worktree/proto-r0260`.

## Non-goals
- Commands that call git by absolute path (`/usr/bin/git`) or through another program's own git library. The shim is a guard against mistakes, not against a spec written to escape. Those stay under the testing skill's "Caught only by review".
- Commands run with plain `process.exec`. The retrofit scan (c0060) already bans raw git and raw shell strings in the twelve converted specs.
- Config writes such as `git config --global`: not "another repository". The runner's guards and review cover them.

## Solution
Every command the helper runs, other than git itself, gets a `git` shim first on its `PATH`. The shim resolves the repository the command line would use and runs the real git only when that repository is under the checkout's `.cache`. This catches the mistake where it happens, whatever the shell string or script looks like.

## Design
### `tests/lib/fixture.luau`
- **`fixture.exec(dir, cmd, args, options)`**: when `cmd ~= "git"`, the command's `PATH` becomes `<shim dir>:<options.env.PATH or process.env.PATH>`. Everything else is unchanged: the fixture check, the refusals in `pointsElsewhere`, stdin.
- `fixture.git` (which calls `exec` with `"git"`) is unchanged: the helper itself checks those calls.
- **The shim dir**: created once per Lune process, on first use, then cached in a module-level variable.
  - It's `mktemp -d "$TMPDIR/pickman-fixture-git.XXXXXX"`. The run's temp folder is outside the checkout, writable in the jail, and removed when the run ends. Without `TMPDIR` it's the system default.
  - It holds one executable file, `git`, written with `fs.writeFile` then `chmod 755`.
- **The shim's two constants**: the real git's absolute path (`command -v git`, resolved before the shim exists), and the checkout's physical `.cache/` (`fixture.physical(".") .. "/.cache/"`, the same root `fixture.check` uses).

### The shim (`#!/bin/bash`)
**One rule: every path that names a repository or a work tree must resolve under the checkout's `.cache`, however git is told about it.** Two review rounds found holes in an earlier version that tried to model git's command line case by case, so the mechanism was bounded (c0080's rule) to this finite list of ways a path names a repository:
- `-C`, `--git-dir`, `--work-tree` and `-c core.worktree=`;
- `GIT_DIR GIT_WORK_TREE GIT_COMMON_DIR GIT_INDEX_FILE GIT_OBJECT_DIRECTORY`;
- a `.git` symlink, and the repository's own config;
- what `init`, `clone` and `worktree add`/`move` create.

Paths git merely writes files to (`archive -o`, `bundle create`, `format-patch -o`, `diff --output`) are plain file writes, and like any spec's file write on Linux they're review's to catch. The testing skill says so (c0078).

Bash 3.2, as shipped by macOS (no `${x,,}`, no `mapfile`), and no subshell on the common path: folders are resolved with `builtin cd -P` in the shim's own process, then it changes back.

- **`target <what> <path>`**: `<path>`, relative to `base`, must resolve physically under the cache. It resolves through its nearest existing folder, with no `..` in the part that doesn't exist yet. Otherwise `fixture git: refusing <what> <path>…`, exit 128.
1. **Leading options**:
   - `-C` moves `base` (it starts as the physical cwd);
   - the values of `--git-dir`/`--work-tree` (both forms) and of `-c core.worktree=` (any case) are `target`ed;
   - `-c` and `--namespace` take two arguments, every other `-…` one;
   - the first other argument is the subcommand.
2. **Repository variables**: each of the five that is set is `target`ed.
3. **`init` and `clone`** check every path a repository is made at:
   - for `init`, each positional, or `base`;
   - for `clone`, the second positional, or `base` (the source is only read);
   - the values of `--separate-git-dir` and `--template`.
   
   Value-taking options skip their value (`-b -o -u -c -j --branch --origin --upload-pack --config --depth --jobs --filter --reference --reference-if-able --shallow-since --shallow-exclude --server-option --bundle-uri --initial-branch --object-format`). Then `exec` the real git.
4. **`worktree add <path>`** and **`worktree move <wt> <new-path>`**: the new path is `target`ed (`-b`, `-B` and `--reason` skip their value).
5. `version`, `help` or no subcommand: `exec` the real git.
6. **Fast path**, with no leading option and no repository variable (the usual call, the tracker's): walk up from `base` in pure bash. At the first folder with a `.git` **directory**:
   - the folder must be under the cache;
   - so must `.git` itself, resolved (it can be a symlink into another repository: design review 002 F4);
   - its `config` is read with the `read` builtin. A `worktree =` key or an `[include…]` section (case-insensitive; keys, not values, since a remote URL may contain `.worktree`) sends the call to the slow path;
   - otherwise `exec` the real git.
   
   A `.git` file, or none, falls to the slow path.
7. **Slow path**:
   - one `rev-parse --absolute-git-dir --show-toplevel` with the same leading options and environment;
   - for a bare repository, which has no work tree, `rev-parse --absolute-git-dir --is-bare-repository` instead;
   - neither works → `fixture git: no repository or work tree here (<base>); refused`;
   - the git dir and the work tree are `target`ed, then `exec` the real git with all arguments, unchanged.

Options and variables are resolved, not refused. A promoted spec (c0008) runs a fake `gh` that calls `git --git-dir=<a fixture bare repository>`.

A pushed-to or fetched-from fixture (an origin under `.cache`) needs no check of its own: the runner's hooks already refuse pushes into the real repository.

### Scalability
One extra `git rev-parse` and one bash start per git call made from a helper-run command, a few milliseconds each. The twelve fixture specs make a few hundred such calls (tracker commands in fixtures). E1 measures the cost. Writing the shim costs a newly written executable's first run on macOS, 1–2 s (c0055 E2), once per run.
### Maintainability
- One small script, built in one function of `fixture.luau`, with its rules in order and a comment each.
- No spec has to change: the twelve converted specs keep calling the helper as before.
### Usability
- A spec that mistakenly runs git outside its fixture fails at once, saying which repository it reached and why it was refused, instead of silently changing a developer's working tree on Linux.

## Unknowns & experiments
- **E1 (run in prep)**: how much slower are the twelve fixture specs with the shim?
  - Method: `PICKMAN_JOBS=1 lune run tests/run -- <the twelve>`, timed, on the prototype.
  - First version (a `git rev-parse` on every call): 57 s → 75–78 s (+33%), over the 25% threshold.
  - The designed version (a pure-bash fast path for calls with no leading options and no repository variables): 56 s → 65 s (+16%) in two runs. All 118 cases pass.
  - After design review 001 (the config read and the `init`/`clone` checks): see E5.
  - The executor re-times it once on the final code (Phase 1). If it's over 25%, the fallback is to apply the shim only to shell strings (`sh`/`bash` with `-c`); the spec's script case then has to be escalated, since it pins scripts too.
- **E2 (reasoned)**: does every git call made by `scripts/tracker.sh` in a fixture resolve to a repository under `.cache`? Yes. The tracker runs in the fixture checkout, and its `git -C <worktree>` calls name worktrees under the fixture's `.worktree/`, which is inside `.cache`. Its pushes go to a fixture origin, and `git ls-remote`/`fetch` read a fixture origin. The twelve specs in the full gate are the proof.
- **E3 (reasoned)**: Lune's `process.exec` `env` option adds to the inherited environment rather than replacing it. Existing specs rely on this: c0008 passes only `PATH` and its `GH_*` variables, and git still finds `HOME`. So setting `PATH` alone keeps everything else.
- **E4 (prototype and mutation check, run in prep)**: does the design hold up in a prototype?
  - Setup: the shim in `.worktree/proto-r0260` (not landed).
  - **Found:**
    - The first prototype refused `--git-dir` outright, which broke c0008's promoted spec: its fake `gh` runs `git --git-dir=<fixture bare repository>`. Options and variables are now resolved, and the case "git options and variables pointing at another fixture under .cache work" pins it.
    - Passing through to the real git when there's no repository left a shell outside every repository unchecked. Now refused, with a new case.
    - In a discovered repository, git ignores `-c core.worktree`, so that case accepts "stayed in the fixture" as well as a refusal.
  - **Result:** the spec passes 10/10; c0008 passes; `scripts/tracker.sh check c0075` passes 3/3.
  - **Mutants**, each failing a case:
    - no shim;
    - `rev-parse` without the leading options;
    - only the git dir checked;
    - the fast path taken with `GIT_DIR` set;
    - `--git-dir` refused outright;
    - the shim only for `-c`;
    - pass-through when there's no repository;
    - a check against one fixture only.
- **E5 (run in prep, after design review 001)**: what does the final shim cost, and does it hold?
  - The config read (F3) and the `init`/`clone` checks (F6) first brought the cost to +34% (58 s → 78 s).
  - The final version resolves `-C` and the slow path's folders with `builtin cd` in its own process, and asks one `rev-parse` for both the git dir and the work tree: 58 s → 69 s (+19%), with 118 of 118 cases passing.
  - Mutants on the final shim, each failing a case:
    - work tree not checked;
    - git dir not checked;
    - no config read;
    - `-C` ignored;
    - the fast path taken with `GIT_DIR` set;
    - no shim;
    - `init`/`clone` passed through;
    - `--separate-git-dir` not checked;
    - the clone destination not checked;
    - no `..` guard.
  - The real repository was checked untouched after the `init` mutant (the jail refused its write).
- **E6 (run in prep, after design review 002)**: does the bounded rule hold up?
  - Setup: the one-rule shim in the prototype. Every write a wrong shim would let through goes to a stand-in cloned into the run's temp folder; the `..` case starts from a symlink under `.cache` that points into the temp folder.
  - Result: the spec passes 14/14 and c0008 passes.
  - Mutants, each failing a case:
    - variables not checked;
    - `--git-dir` values not checked;
    - `worktree add` not checked;
    - `.git` itself not checked;
    - `init`/`clone` passed through;
    - no `..` guard;
    - the clone destination not checked;
    - no config read.
  - Found on the way: the first config trigger matched any value containing `worktree`, and this repo's remote URLs contain `.worktree/`. That masked the `.git`-symlink mutant and sent fixture clones down the slow path. Keys only now.
  - Cost: 57 s → 64 s (+12%).
  - The real repository was checked untouched afterwards.

## Acceptance criteria

### Checked
- AC1: a command run through `fixture.exec` (a shell string or a script) can't run git in a repository, or with a work tree, outside the checkout's `.cache`, nor where there's no repository at all, nor make or retarget a repository or work tree outside it with `init`, `clone` or `worktree add`. That holds however it names one: `cd`, `-C`, `--git-dir`, `--work-tree`, `-c core.worktree`, the repository's own `core.worktree`, a `.git` symlink, `--separate-git-dir`, or a repository variable set inside it. Every write a wrong shim would let through in the spec is aimed at a stand-in in the run's temp folder, never at the real checkout (design review 002 F3). Each refusal says `fixture git`.
- AC2: git in the fixture and in other fixtures under `.cache` works (directly, or through `--git-dir` or `GIT_DIR`), `init` and `clone` work, and `fixture.git` is unchanged.
- AC3: the twelve converted specs and the helper's own specs (c0060, `fixture-elsewhere`) pass.
