# c0076: The jail sweeps every process a run leaves behind

## Problem
The runner stops what is left in the specs' process group when a run ends (R0021 review 005 F2). A process that leaves that group on purpose (`setsid`, a double fork into a new session) survives. It stays jailed, but it outlives the run and could change files in `.cache` that an unjailed `check.sh` later copies and runs (c0058's AC9/AC10 copies, c0049's gate copy). By the user's decision it is listed under the testing skill's "Caught only by review" for now.

Prep found a cheap way to close it on macOS (E1): the jail can tell its own processes from everything else by the kernel's signal rule.

## Non-goals
- Linux, where specs aren't jailed. The process group reaping stays the only cleanup there, and the testing skill keeps the Linux case under "Caught only by review".
- Runs not jailed because an outer sandbox protects the repository: the same.
- Work handed to a process outside the jail (`launchctl`, `open`): already banned by the gate spec scan and listed under "Caught only by review".
- The signal rule itself: c0078 adds it to the profile. This issue depends on it at run time (c0078 lands in the same PR).

## Solution
A sweeper runs as the root of the jail. It starts the specs, waits for them, and then kills every process it can signal. Under c0078's rule `(deny signal)(allow signal (target same-sandbox))`, a jailed process can signal only processes of its own sandbox, so the sweep reaches exactly the run's leftovers, whatever session or group they moved to. An interlock refuses to sweep anywhere that rule isn't in force, where `kill 0` would reach every process the user owns.

## Design
### `fence.SWEEPER` (new, `tests/lib/fence.luau`, exported)
A Perl program, run as `perl -e SWEEPER <outside-pid | -> <command> <args…>`:
1. `$SIG{$_} = 'IGNORE' for qw(INT TERM HUP)`. A Ctrl-C or a forwarded signal stops the specs, not the sweeper.
2. `my $pid = fork; die "fork: $!" unless defined $pid`. The child restores the default handlers for INT, TERM and HUP and `exec`s the command. The parent does `waitpid($pid, 0)`, and `$code` = the status (a signal death as 128+n).
3. **Interlock**: `-` in place of the pid means "my parent", read with `getppid()` once, at the sweeper's start. In the real run that's the launcher: the REAPER child `exec`s `sandbox-exec … env … perl`, so the sweeper keeps that pid, and the launcher `waitpid`s on it. The launcher survives a Ctrl-C or a TERM sent to the top process alone, both of which kill the top Lune first (design review 001 F2).
   - A parent of 1 at the start (orphaned) prints `sweeper: no launcher above me (parent 1); nothing swept` and exits 70.
   - At sweep time, `getppid()` must still be that parent, and `kill 0, $outside` must fail with `EPERM` (`$!{EPERM}`, `use Errno`). Otherwise (the parent changed, the signal went through, or any other error such as `ESRCH`) it prints `sweeper: not in a jail that refuses signals to other processes (pid <outside> answered); nothing swept` to stderr and exits 70.
   - Explicit pids are for specs.
4. **Candidates**: pids 2–99999 (macOS's `PID_MAX`). If env `PICKMAN_SWEEP_ONLY` names a readable file, only the pids listed in it, whitespace separated. That's a test seam: it can only narrow the sweep, and a real run removes it (below).
5. **Kept**: `$$` and its ancestors among the signalable candidates. Within the signalable set, a child→parent map comes from one `pgrep -a -P <p>` per signalable pid `p`. On macOS, `-a` makes `pgrep` include its own ancestors, which it hides by default; without it the sweeper's own parent never shows up, and the runner gets killed (found by prep's prototype, E4). On Linux `-a` means something else, but the sweeper never gets past its interlock there. The chain starts at `getppid()` and climbs while the parent is signalable. In a real run the sweeper's parent is outside the jail, so nothing but itself is kept. Inside a nested test, the spec's own runner is spared.
6. **Passes**, at most 50:
   - signalable = the candidates, minus those kept, for which `kill 0` succeeds;
   - if none, it exits `$code`, printing `sweeper: stopped <n> process(es) the specs left running` to stderr first if `n > 0`;
   - otherwise `kill 'STOP', @found` then `kill 'KILL', @found` (stopped first, so none can fork while the others die), adds them to `n`, and waits 50 ms.
   
   After 50 passes it prints `sweeper: processes keep appearing; this run is not clean` and exits 71.

### Launcher (`fence.REAPER`)
With env `PICKMAN_REAP_SWEPT=1`, a signal death of its command (the sweeper) is tampering: a spec killed the sweeper, which it can, being in the same sandbox. It then prints `tests/run: the jail's sweeper was killed (signal <n>): processes the specs left may still run. Stop and report this.` and exits 1. Without the variable, the existing rule applies (128+n).

### `fence.enter()`
When jailed, the command becomes:

```
sandbox-exec -p <rules> env -u PICKMAN_SWEEP_ONLY perl -e <SWEEPER> <myPid()> bash -c …
```

The prefix table is written literally as `{ "sandbox-exec", "-p", rules, "env", "-u", "PICKMAN_SWEEP_ONLY", "perl", "-e", fence.SWEEPER, "-" }`. The spec's AC4 case reads that sequence (whitespace and a trailing comma don't matter). `fence.SWEEPER` is assigned before `fence.enter` is defined.

`-` makes the sweeper use the launcher, its parent: same user, outside the jail, and alive until the sweep is done. (The first design used the top Lune pid, which a Ctrl-C kills first, so an interrupted run swept nothing: design review 001 F2.) A SIGKILL of the launcher itself skips the sweep and the unlink; the testing skill says so (c0078). The launcher's environment gets `PICKMAN_REAP_SWEPT=1` (and `PICKMAN_REAP_CACHE`, c0077). Both are for the launcher alone: the runner's `bash -c` line begins with `unset PICKMAN_REAP_SWEPT PICKMAN_REAP_CACHE;`. Without that, every spec inherits them, and a nested, unjailed launcher (c0058's fixture runs) takes its plain `bash`'s signal death for a killed sweeper and prints a false "Stop and report this". Specs that run `fence.REAPER` would also unlink links in the outer run's `.cache` (design review 002 F5). Unjailed runs get no sweeper and no `PICKMAN_REAP_SWEPT`.

### Scalability
A sweep pass is 99,998 `kill 0` calls, about 40 ms (E1), plus one `pgrep` per leftover. A clean run costs one pass.
### Maintainability
- The sweeper is about 30 lines of Perl next to `REAPER`, with one comment per step.
- Its safety rests on two checks a reader can verify: the interlock and the ancestor list.
- The test seam is named, narrowing-only, and removed by `env -u` in the one place that starts the real sweeper.
### Usability
- A run that left a detached process behind says so (`stopped n process(es)`), and the process is gone.
- A run whose sweeper was killed fails, saying to stop and report.

## Unknowns & experiments
- **E1 (run in prep)**: can the jail find its own processes without `ps`?
  - Profile `(deny signal)(allow signal (target same-sandbox))`, a Perl sweeper as the sandbox's root, and a command that double-forks a `setsid` process and exits 3.
  - Result:
    - `/bin/ps` can't run inside the jail (setuid: `Operation not permitted`).
    - `kill 0` over 2..99999 took 39 ms and found exactly the detached process; it was killed; the command's 3 passed through.
    - An unrelated process outside the jail survived; a second pass found nothing (34 ms).
- **E2 (executor, Phase 1)**: does the sweeper work as the root of a real jailed suite? That's raft RC1, which builds a fixture checkout with the runner and runs a probe spec that leaves a `setsid` process. Expected: the process is gone after the run. If it isn't, stop and escalate: the mechanism E1 proved isn't what the runner does.
- **E3 (reasoned)**: is 99999 the highest macOS pid? `PID_MAX` is 99999 in xnu's `bsd/sys/proc_internal.h`, and pids wrap below it. If a future macOS raises it, the sweep misses higher pids, which fails open. The interlock doesn't detect this. Recorded in the testing skill (c0078).
- **E4 (prototype and mutation check, run in prep)**: does the design hold up in a prototype?
  - Setup: a prototype of the sweeper, the REAPER rule and the jail prefix in `.worktree/proto-r0260` (not landed), with c0078's signal rule.
  - **Two bugs found:**
    1. BSD `pgrep -P` hides its own ancestors, so the ancestor walk found nothing, and case 2's sweep killed the spec's own runner. Fixed with `pgrep -a`, now in the design.
    2. The spec probed the outside process with its own `kill -0`, which the jail now refuses. It now uses `fence.alive` (c0078).
  - **Result:** the spec passes 8/8 with its jailed cases running, and `scripts/tracker.sh check c0076` passes 5/5, including AC5's real jailed suite.
  - **Mutants**, each failing a case:
    - no ancestor list: the runner is killed, so the run fails;
    - `exit 0` after the sweep;
    - the REAPER ignoring `PICKMAN_REAP_SWEPT`;
    - no `env -u` in the prefix;
    - an interlock that accepts `ESRCH`. That one survived the first spec; the case "…when the pid it was told is outside is gone" was added, and it catches it.
  - **Raft RC1** fails on today's code ("process … outlived the run") and passes on the prototype.
- **E5 (run in prep, after design review 001 F2)**: does the sweep survive an interrupt?
  - With the launcher form (`-`), `scripts/tracker.sh check c0076` passes 6/6, including AC6: INT to the fixture run's whole process group, and the detached process is still swept.
  - The first design's prefix (`myPid()`, the top process) fails AC6 ("process … outlived the interrupted run") and AC4.

| rule | spec :: case | mutant it kills | checked |
|---|---|---|---|

| ancestors are never swept | sweeper :: …never stops its own ancestors… | no ancestor list (`grep { $_ != $$ }` only) | run |

## Acceptance criteria

### Checked
- AC1: when jailed, the sweeper stops a process the command left in another session; it spares its own ancestors and processes outside the jail; it exits with the command's status (a signal death as 128+n).
- AC2: when it can signal the pid it was told is outside, when that pid is gone, or (in the `-` form) when its parent is already pid 1, the sweeper exits 70 and stops nothing.
- AC3: with `PICKMAN_REAP_SWEPT=1`, the launcher fails a run whose command (the sweeper) died of a signal, saying to stop and report. Without it, a signal death is still 128+n.
- AC4: the runner starts the real sweeper with `PICKMAN_SWEEP_ONLY` removed from its environment, in the launcher form (`-`). The launcher's own variables (`PICKMAN_REAP_SWEPT`, `PICKMAN_REAP_CACHE`) reach no spec.
- AC5: a real jailed suite in a fixture checkout leaves no process behind, even one that moved to its own session, and even with `PICKMAN_SWEEP_ONLY` set by the caller.
- AC6: the same suite, interrupted by INT to its whole process group while a spec waits, still leaves no process behind.
