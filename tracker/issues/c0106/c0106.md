# c0106: Narrow the radar corner specs for the jump button

## Problem
The danger radar (d0105) sits in the bottom-right corner, one margin above the power bar. On a phone that is where Roblox draws the touch jump button. f0029 (mobile HUD layout, raft R0012) owns that overlap and the safe-area insets, and its layout has to keep both the radar and the power bar clear of the jump button.

That requirement is now in f0029 (ticket-prep of R0012, 2026-10-20: its Design "Jump button corner", AC5 and `acceptance/jump.spec.luau`). It is a feature, so it cannot ride in this chore, and this chore is what is left: f0029 turns two promoted d0105 cases red, and a feature may not edit promoted specs. So this chore only narrows them, first, so `main` stays green while f0029 lands:

- `tests/acceptance/d0105/radar.spec.luau`, case "layout's numbers are unchanged, so the bar and the labels stay where f0019 put them": a whole-table `toEqual` on `Hud.layout(1280, 720)`. f0029 adds `safeX`, `safeY`, `safeW`, `safeH` to that table (the five numbers do not change).
- `tests/acceptance/d0105/adapter.spec.luau`, case "places the radar from the current screen size on every render step, before the snapshot guard": it pins the exact text `local box = Hud.radarBox(view.X, view.Y, radarSize)` with its closing parenthesis. f0029 adds a fourth and a fifth argument, the fifth a nested call. f0029's final line, verbatim (two tabs of indent):

  ```lua
  		local box = Hud.radarBox(view.X, view.Y, radarSize, UserInputService.TouchEnabled, bandTop())
  ```

## Non-goals
- Any `src/` change. The jump-button layout, `Hud.jumpButtons` and the touch argument of `Hud.radarBox` are f0029's.
- Every other d0105 case stays as it is: the three-argument `radarBox` numbers, the right edge and the margin above the power bar, the screen and overlap checks, one `radar.Position`, one `local view =`, the old corner gone, no core-gui switch, the Awareness calls.
- d0105's `check.sh`: both files keep their names, so it is not edited.

## Solution
- `radar.spec`: compare the five fields (`textSize`, `margin`, `iconSize`, `barWidth`, `barHeight`) of `Hud.layout(1280, 720)` to 32, 16, 32, 320, 13, instead of the whole table. A layout that changes any of the five still fails.
- `adapter.spec`: keep the four-line block, but match its radarBox line as a prefix: `\t\tlocal box = Hud.radarBox(view.X, view.Y, radarSize` followed by anything up to the end of that line, then the `\t\tradar.Position = UDim2.fromOffset(box.x, box.y)\n` line (for example the pattern `radarSize[^\n]*\n\t\tradar%.Position = UDim2%.fromOffset%(box%.x, box%.y%)\n` after the escaped prefix). Do not stop at the first `)`: f0029's fifth argument is `bandTop()`. Still exactly one `radar.Position` and one `local view =`, and the block still comes first in the render step.
- Two must-match witnesses for the narrowed case, both in its prep's Rules and mutants: today's three-argument block (so `main` stays green before f0029) and f0029's five-argument line above. Mutants to kill: a pattern that stops at the first `)` (`[^)]*%)`), which rejects f0029's line; and a pattern that drops the `radar.Position` line after it.
- This must be in `done/` before R0012 is readied: f0029 has `depends_on: [c0106]`.
- Needs its own single-chore raft and ticket-prep; this text is the capture.

## Design
Two edits to promoted specs, nothing else. The raft is `R0041` (single chore); f0029 (R0012) has `depends_on: [c0106]`.

**`tests/acceptance/d0105/radar.spec.luau`**, case "layout's numbers are unchanged, ...": replace the whole-table `toEqual` by the five fields (the case's name and the other six cases stay):

```lua
local l = Hud.layout(1280, 720)
t.expect({
	textSize = l.textSize,
	margin = l.margin,
	iconSize = l.iconSize,
	barWidth = l.barWidth,
	barHeight = l.barHeight,
}).toEqual({
	textSize = 32,
	margin = 16,
	iconSize = 32,
	barWidth = 320,
	barHeight = 13,
})
```

**`tests/acceptance/d0105/adapter.spec.luau`**, case "places the radar from the current screen size ...": replace the `block` string and its `string.find(src, block, 1, true)` assertion by a head matched plain, then a pattern for the rest of the radarBox line and the Position line (the counts of `radar.Position` and `local view =` stay):

```lua
-- the radarBox call may take more arguments after radarSize (f0029 adds two), so its line is matched
-- as a prefix; the Position line must follow it directly
local head = "RenderStepped:Connect(function()\n"
	.. "\t\tlocal view = gui.AbsoluteSize\n"
	.. "\t\tlocal box = Hud.radarBox(view.X, view.Y, radarSize"
local tail = "\n\t\tradar.Position = UDim2.fromOffset(box.x, box.y)\n"
local start = string.find(src, head, 1, true)
t.expect(start ~= nil).toBe(true)
local rest = string.sub(src, (start :: number) + #head)
t.expect(string.match(rest, "^[,)][^\n]*" .. string.gsub(tail, "%p", "%%%0")) ~= nil).toBe(true)
```

The design tightens the capture's "followed by anything" by one character: `radarSize` must be followed by `,` or `)` (so `radarSizes` or `radarSize2` is rejected), then anything up to the line end. The block must still open the render step (the head includes the `Connect` line), so it still comes before the snapshot guard. This was prototyped (see Unknowns). `src/` is untouched.

### Scalability
Two fixed-size text and table checks; no cost that grows with the game or the specs.
### Maintainability
The radar spec pins the five numbers f0019 owns and no more, so a later field in `Hud.layout` doesn't break it. The adapter spec pins the shape (view, box from the screen and `radarSize`, Position from the box, first in the step) and not the tail of the call, so f0029's two arguments, and a later one, don't break it. `narrow-radar.spec` and `narrow-adapter.spec` (in `tests/acceptance/c0106/`) keep both honest: each loads its promoted file with a fake `require` and shows it accept f0029's shapes and reject regressions, and each fingerprints the file's text outside the replaced region (from the narrowed assertion's first line to the end of its case, for radar; from the new comment to the line before `local function count(`, for adapter; ids normalised, with a case pinning that), so nothing else in the file can change. The Design snippets are therefore exact: the executor pastes them (stylua-formatted) and the fingerprints match; a different edit fails and the executor stops and escalates. A later change to either d0105 file also turns the c0106 spec red, so it must name c0106 on its `Overrides:` line.
### Usability
A developer who changes the radar's corner or the HUD layout still gets a failing d0105 case naming what moved. Nothing player-facing changes.
