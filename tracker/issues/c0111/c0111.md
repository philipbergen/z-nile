# c0111: Skill lessons

## Problem
Design-review findings are lost once a raft's prep merges: they sit in `design-review-NNN.md` files that no later prep reads. So the same classes of defect come back in every raft. R0039 took all 5 review rounds and 29 findings, and most of them could have been caught in the first draft: promoted specs that go red under a new mechanism, state tied to the wrong process lifetime, pure seams whose call-site inputs are unpinned, and text that contradicts itself. The only record of these lessons is one agent's private memory file, which other agents, the reviewer and the executor never see.

The user wants lessons organized under the skills, not in one file, so they can be searched and used by the pipeline:
- **Harvest at the end of design.** When the design review ends, the prep author turns the recurring findings into lessons, or adds the raft as a new source on an existing lesson. Lessons land with the prep PR.
- **Apply at the start of the next design.** The prep author walks the matching lessons against the draft before the first review round. The reviewer checks them too, and `ready-raft` puts the matching ones in the execution prompt.

Scope decision (user, 2026-10-20): "Accept them": the format and flow R0040's prep refined are the design. Lesson files are `<slug>.md`, `when: design|build|both` replaces `phase`, and sources come from per-item `harvest.md` ledgers instead of a frontmatter list. Every round is harvested as it is answered, and code reviews are harvested too, which the capture left for prep to decide.
Scope decision (user, 2026-10-20): "All build lessons is fine": the execution prompt carries every build lesson, one index line each, not only the ones whose tags match the raft.
Scope decision (user, 2026-10-20): "Keep it in c0112": seeding the 12 R0039 lessons from the private memory `design-first-pass-checklist`, and turning that memory into a pointer to the repo, are done by the backfill, c0112.
Scope decision (user, 2026-10-20): "Restore it in c0111": the captured **metrics** outcome (findings per tag across rafts, to show whether lessons reduce review rounds) is delivered here, in `tracker.sh metrics` (Design, Metrics).

## Non-goals
- **The backfill of the roughly 880 past findings:** c0112. This issue ships the mechanism and harvests only R0040's own reviews.
- **A gate on full coverage** ("every finding in the tree has a harvest line"): c0112 turns it on once the backfill makes it true. Here, coverage is checked per item by `tracker.sh lessons --uncovered <id>`, which ticket-prep and execute-raft run.
- **Changing `tracker.sh done` or `status … prepared`** to refuse an uncovered raft. That would turn three promoted specs red (`c0001/tracker-lifecycle`, `c0038/deferred`, `c0080/consequences`: their fixture reviews have findings and no harvest), and c0112's gate spec enforces the same thing on the real tree without touching fixtures.
- **Turning a lesson into a script check.** A lesson with many sources is a candidate for its own chore.
- **The author's private Claude memory.** It becomes a pointer to the repo when c0112 lands (that issue's Solution).

## Solution
A lesson is one Markdown file with frontmatter, in the folder of the skill whose work it improves. A per-item `harvest.md` ledger maps every review finding to the lessons it taught, or marks it one-off, so a lesson's sources (and its recurrence count) are computed from the ledgers, never written twice. One new read-only command, `scripts/tracker.sh lessons`, lists, searches, validates and reports coverage. The skills read their lessons when they start, harvest each review round as it is answered, and route any other new lesson by the agent's role. `tracker.sh ready` puts the build lessons in the execution prompt. `tracker.sh metrics` reports findings per lesson tag and design rounds before and after lessons.

## Design
### The rules R0040's prep refined
The Problem's two captured bullets, as R0040's prep refined them (accepted by the user, 2026-10-20):
- **Each skill has its own lessons folder.** Every skill reads its lessons when it starts. New lessons reach the right skill's folder from whoever learned them: written directly where the work can land a file, otherwise reported or captured as an issue (The skills, below).
- **Harvest at the end of design.** When the design review ends, the prep author turns each finding into a lesson, adds the raft as a new source of an existing lesson, or marks it one-off. Code reviews are harvested the same way before `done`.
- **Apply at the start of the next design.** The prep author walks the design lessons against the draft before the first review round. The design reviewer checks the same lessons, and the execution prompt carries the build lessons.
- **Backfill** every lesson already learned: that is c0112 (its own raft, after this one), because it needs this format.


### Files
**A lesson**, `.claude/skills/<skill>/lessons/<slug>.md`, id `<skill>/<slug>`. `<skill>` is an existing skill folder (one with a `SKILL.md`), and `<slug>` is lowercase kebab (`^[a-z0-9]+(-[a-z0-9]+)*$`).
```markdown
---
title: Run the promoted specs against the new mechanism
when: design
tags: [regression, overrides]
check: Does every promoted spec in the touched area still pass under the new mechanism, nested and unnested?
---
<the rule>

**Why:** <the incident that taught it>
**How to apply:** <what to do, concretely>
```
- `title`: one line, required.
- `when`: required, `design` (prep author and design reviewer), `build` (executor and code reviewer) or `both`.
- `tags`: required, `[a, b]`, at least one, each lowercase kebab, each once (a repeated tag is a problem). They are free (not a fixed vocabulary): `tracker.sh lessons --tags` lists the ones in use, so a harvester reuses them.
- `check`: required, one line ending in `?`: the question a draft or a diff is asked.
- `from`: optional, one line: a source with no item folder to hold a note entry (rare; a prep or raft records such sources as `note` entries instead). A lesson needs at least one source: a harvest entry naming it, or `from`.
- Any other key is an error, and so are a repeated key (`<id>: <key> is repeated`; the parser never keeps only the last) and an empty body. The frontmatter is the tracker's (`key: value` lines between `---` lines).

**A harvest ledger**, `harvest.md` in the item folder that holds the reviews (a raft's, or, for older items, an issue's):
```markdown
# Harvest: R0040
- design-review-001 F1: ticket-prep/promoted-specs-new-mechanism
- design-review-001 F2: testing/pin-call-site-inputs, review/lifetimes
- design-review-002 F1: one-off: a typo in the Test plan
- review-001 F3: execute-raft/stale-text-pass
```
- A line starting with `- ` is an entry, in one of two forms:
  - **review entry**: `- <review> F<n>: <target>`. `<review>` is the file's stem, `design-review-NNN` or `review-NNN`, from the same folder. `<target>` is a comma-separated list of lesson ids, or `one-off: <reason>` with a non-empty reason.
  - **note entry**: `- note <text>: <lesson ids>`, a source that is not a review finding (a stream's or reviewer's candidate, a correction by the user, a failed step). The text is everything up to the last `: ` (so it may hold a colon) and must not be empty. The ids are one or more lesson ids. A note is a source, never a finding: it covers nothing, and any number of notes may name the same lesson.
- Every other line (headings, blank lines, prose) is ignored.
- Each finding gets at most one entry.
- Findings are the `### F<n>` headings of `design-review-NNN.md` and `review-NNN.md`, matched with `tracker.sh done`'s own pattern (`\n###%s+(F%d+)`, in `reviewProblem`), so `### F1: claim` and `### F1 [low]` are both F1. `stream-review-*` files and everything under an item's subfolders (for example `experiments/`) are not reviews here.

### Module `scripts/tracker/lessons.luau`
The parsing, validation, selection and coverage are pure functions over texts. Only `load` reads files.
```luau
export type When = "design" | "build" | "both"
export type Lesson = {
	id: string, skill: string, slug: string, title: string, when: When,
	tags: { string }, check: string, from: string?, body: string,
}
-- a review entry names a finding; a note entry (review = "note", finding = "") holds its text in note
export type Entry = {
	item: string, review: string, finding: string, lessons: { string }, oneOff: string?, note: string?,
}
-- one reviewed item: review stem -> text (design-review-NNN, review-NNN), and its harvest.md text if any
export type Item = { id: string, reviews: { [string]: string }, harvest: string? }
export type Tree = {
	lessons: { [string]: string }, -- lesson id -> file text
	found: { [string]: boolean }, -- every item folder seen, reviewed or not
	skills: { [string]: boolean }, items: { Item }, problems: { string },
}
export type Query = { skills: { string }?, when: ("design" | "build")?, tags: { string }?, words: { string }? }

lessons.parse(id: string, text: string): (Lesson?, string?)          -- the lesson, or the first problem
lessons.findings(review: string): { string }                          -- "F1", "F2", … in heading order
lessons.parseHarvest(item: string, text: string): ({ Entry }, { string }) -- entries, and one problem per bad line
lessons.check(tree: Tree): { string }                                 -- every problem in the tree, sorted
lessons.sources(items: { Item }): { [string]: { string } }            -- lesson id -> "R0040 design-review-001 F1", …
lessons.uncovered(items: { Item }): { string }                        -- "R0040 design-review-001 F3", … in order
lessons.select(all: { Lesson }, sources: { [string]: { string } }, q: Query): { Lesson }
lessons.index(chosen: { Lesson }, sources: { [string]: { string } }): string -- one line per lesson
lessons.load(root: string): Tree                                      -- reads .claude/skills and tracker/ under root
```
Rules (each one has a Rules and mutants row):
- **parse**: the id's skill and slug are split at the one `/`; every rule under Files is checked. A problem names the id and the field (`ticket-prep/x: when must be design, build or both`).
- **findings**: `done`'s pattern exactly: `### F<n>` at a line start, whatever follows. `#### F1` and an `F1` inside text are not findings.
- **parseHarvest**: `- design-review-001 F1: a/b, c/d` gives one entry with two lessons. `- note ws c0010: a/b` gives an entry with `review = "note"`, `finding = ""` and `note = "ws c0010"` (`Entry` gains `note: string?`). A note with empty text, or with a target that is not lesson ids, is a problem (`<item>/harvest.md: note…`). An entry, review or note, that names one lesson twice is a problem (`… lesson <id> is named twice`) and is dropped, so a lesson never counts one entry twice. Problems: a `- ` line that does not parse (a stem other than `design-review-NNN` or `review-NNN` included); an empty `one-off:` reason; a target that is neither; a second entry for the same finding, which is reported and dropped (the first entry stands).
- **check** reports, each once, sorted:
  - every lesson that fails `parse`, names a skill with no `SKILL.md`, or has no source (no harvest line names it and no `from`);
  - every ledger problem from `parseHarvest`;
  - every review entry naming a review file the item lacks, a finding that file lacks, or a lesson id that does not exist, and every note naming a lesson id that does not exist (`<item>/harvest.md: note <text>: no lesson <id>`);
  - every problem `load` found (a file in a `lessons/` folder that is not `<slug>.md`).
  It does **not** report uncovered findings (c0112's gate does).
  **Message shape** (specs read it): each problem starts with its subject. A lesson problem starts `<lesson id>: `. A ledger line problem starts `<item>/harvest.md: `, and a problem with an entry starts `<item>/harvest.md: <review> <finding>: `. A `load` problem starts with the file's repo path.
- **sources**: one string per entry naming the lesson: `<item> <review> <finding>` for a review entry, `<item> note <text>` for a note. Within an item, review entries come first in review and finding order, then notes in file order; items in id order. One-off entries name no lesson.
- **uncovered**: every finding of every review of every item that no entry names, in item id order (plain string order, so `R0010` before `c0020`), then review stem, then finding number (F2 before F10).
- **select**:
  - `skills`: the lesson's skill is one of them.
  - `when = "design"` keeps `design` and `both`, and `"build"` keeps `build` and `both`.
  - `tags`: the lesson has every one.
  - `words`: each word, case-insensitive, is a plain substring of the id, title, tags, check or body. A word that equals the id of a lesson in `all` matches that lesson only, so `lessons --full <id>` shows exactly one.
  - Sorted by source count, more first (sources plus 1 for `from`), then by id.
- **index**: one line per lesson, `- <id> (<when>, <n> sources): <check>`, or `(1 source)`; the empty selection gives `(none)`.
- **load**: lessons are `<root>/.claude/skills/<skill>/lessons/*.md`, and `skills` is every folder under `.claude/skills` with a `SKILL.md`. Items are the folders `<root>/tracker/{issues,rafts}/{,active/,done/}<ID>` (`^[fdcR]%d%d%d%d$`) with at least one review file or a `harvest.md`, sorted by id. `found` holds every such folder's id, with or without reviews. Only files directly in the folder count (not `experiments/` or other subfolders), and `stream-review-*` files are not reviews. A missing folder is empty, not an error.

### The command
`scripts/tracker.sh lessons [--skill <s>]... [--when design|build] [--tag <t>]... [--full] [<word>...]`. It is read-only, runs in any checkout (the main checkout included), and needs no origin.
- **Wiring in `main.luau`:**
  - `--full`, `--check`, `--tags` and `--uncovered` join the boolean list in `flags()`; otherwise they would swallow the next word. No other command uses those names.
  - `lessons` is **not** added to `READ_ONLY`: that list exempts `.git`-less sandboxes, which this command never needs, and `tests/tooling/tracker-guarded.spec.luau` pins the list exactly.
  - `USAGE` gains a `lessons` line.
- **List (default):** the selection's `index`.
- **`--full`:** for each selected lesson, in the same order, three parts, with a blank line between lessons:
  - `== .claude/skills/<skill>/lessons/<slug>.md`;
  - `sources: <a>, <b>, …` (the harvest sources in `sources` order, then `from`), or `sources: none`;
  - the file's text, verbatim.
  An empty selection prints `(none)`.
- **`lessons --tags`:** one `<tag> <n>` line per tag in use, where `<n>` is the number of lessons carrying it, most used first, then by name.
- **`lessons --check`:** prints every `check` problem and exits 1 if there is any. Otherwise it prints `lessons: <n> lessons, <m> harvest entries, ok`.
- **`lessons --uncovered [<id>...]`:** prints each uncovered finding of the named items (or of every item), and exits 1 if there is any. Otherwise it prints `harvest: every finding is covered`. A named id falls into one of three cases:
  - a reviewed item: checked;
  - an item folder `load` found with no review files: prints `<id>: no reviews`, which is not an error, so a raft before its first round passes;
  - an id with no folder in any state: `<id>: no such item`, exit 2. A reader that missed a folder can never pass vacuously.
  An item whose only round approved with no findings is covered.
- **Streams:** the listing, `--full`, `--tags`, `--check` problems, the `--uncovered` list and `no reviews` go to stdout. Warnings, usage errors and `<id>: no such item` (a usage error, exit 2) go to stderr.
- **Refusals:** `--check`, `--uncovered` and `--tags` take no other option, and `--check` and `--tags` take no words. A bad or repeated `--when` value is refused, and so is an unknown option or a value option with no value (`--skill` last). Each exits 2 and prints a line with `usage`.
- **A tree with a bad lesson still lists:** the listing skips a lesson that fails `parse` and names it on stderr, so a broken file never hides the rest. `--check` is the strict path.

### The execution prompt
`tracker/templates/prompt.md` gains a section before `## Work items`:
```
## Lessons (build and both, from .claude/skills/*/lessons)
Apply each before you write the code it concerns; its full text is `scripts/tracker.sh lessons --full <id>`.
{{LESSONS}}
```
`renderPrompt` (`scripts/tracker/main.luau`) fills `LESSONS` with `index(select(lessons, sources, { when = "build" }))` from `load(".")`. A lesson that fails `parse` is left out with a `warning: <problem>` on stderr. `ready` has already published by then, so a bad lesson never stops a ready. No lessons gives `(none)`.

### The skills
Every `.claude/skills/<s>/SKILL.md` ends with the **same** `## Lessons` section; only the skill name in its read command differs. Who writes a new lesson is decided by the agent's **role**, not by which skill it is reading, because one agent follows several skills at once (a prep author follows ticket-prep and testing):
- **Read at the start:** `scripts/tracker.sh lessons --skill <s> --full`.
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `tracker.sh new`. It puts the candidate lesson (the rule, why, and the question that catches it) in its review (a finding, or the `Lesson:` line) or in its final report.
- **The lead of a prep or raft** writes it in `.claude/skills/<the skill the lesson improves>/lessons/<slug>.md`, as Files says, and records where it came from in its own `harvest.md`: review findings through the harvest, anything else (a subagent's candidate, a correction by the user, a failed step) as a `note` entry. It adds a note to an existing lesson when one fits and writes a new file only when none does, so a recurring non-review lesson shows its count. It commits both with its work. Lesson files outside the Touched modules are harmless: spend splits unclaimed files evenly.
- **Any other lead** (in the main checkout, a capture, or a metrics report) cannot land a file there. It captures the lesson with `scripts/tracker.sh new issue c lesson-<slug> --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (make-issue), and the prep that takes that issue writes the file.

In addition:
- **ticket-prep:**
  - Step 5.1 opens with the **lessons pass**, before `design: reviewed`: run `scripts/tracker.sh lessons --when design --full`, ask each lesson's `check` of the draft, fix what it finds, and name the lessons that changed the design in the raft's Risks & rollback.
  - Step 5.3 (answering a round) adds **harvest the round**, and a rerun of `promote-check <R-id>` after the round's spec edits (the test runner does not type-check):
    - add one entry per finding of that `design-review-NNN.md` to `harvest.md` in the raft folder: a new lesson, a new source for an existing one (preferred), or `one-off: <reason>`;
    - a finding that repeats a lesson the pass should have caught sharpens that lesson's `check`;
    - then run `lessons --check`.
    Harvesting every round keeps `--uncovered` (and c0112's gate) green between rounds, and lets the next reviewer judge the new lessons.
  - Step 5.5 opens with **confirm the harvest**: first harvest anything `lessons --uncovered <R-id>` still lists (rounds written before lessons existed, or a round that slipped), then `--uncovered` and `--check` pass, before `status <R-id> prepared`. The lessons and the ledger ride in the prep commit.
- **execute-raft:**
  - Phase 2B step 2's stream brief says a candidate lesson goes in the stream's final report (streams may not run `tracker.sh new`), and its report list names candidate lessons.
  - Phase 2B gains, before step 1, **candidate lessons are written as they arrive**: each time a stream's report reaches the lead (done or blocked) and each time it commits a stream review, it writes the candidates as `- note ws-<issue>: <ids>` or `- note stream-review-<issue>-NNN: <ids>`, with a new lesson file only when none fits, committed on their own (`--phase code-review --issue <issue>`). No later path (an approving review, a blocked or taken-over stream) can drop them.
  - Phase 4 step 5 (answering a round) harvests that `review-NNN.md` the same way as ticket-prep, into any lesson (a design lesson gains a source as readily as a build one; a new lesson is usually `when: build` or `both`), and commits the ledger and lessons with the refute file.
  - Phase 5 gains step 3, **confirm the harvest**, before `done`: first harvest anything `lessons --uncovered <R-id>` still lists. That includes the design reviews of a raft prepped before lessons existed (R0012, R0030 and R0035 when this lands), which its executor harvests here (the user's choice, design review 5 F1). Then `--uncovered` and `--check` pass. Its later steps are renumbered.
- **review:**
  - Design mode gains item 10, **Lessons**:
    - run `scripts/tracker.sh lessons --when design --full`, and treat a draft that repeats a lesson's defect as a finding;
    - then judge the lessons the author added since the last round (`harvest.md`): each must be one a different raft could fail, not a restated finding (that is a low finding).
  - Code mode gains the same with `--when build`.
  - The finding template gains an optional last line, `Lesson: <skill>/<slug>`, written only when the finding repeats a lesson. A harvest then names that lesson, and its source count shows it failed to prevent the defect.
- **tracker:** the command table gains the `lessons` row, Items describes the lesson format and `harvest.md`, and Worktrees item 1 (the complete list of commands that may run in the main checkout) adds `lessons` (it only reads).
- **ready-raft:** step 3 says the prompt carries the build lessons.
- **metrics:** step 2 reads `tracker.sh lessons` source counts as the recurring defect classes.
- **AGENTS.md:** a short paragraph after the skill table: each skill keeps its lessons in `lessons/`, searched with `scripts/tracker.sh lessons`; every skill reads its own when it starts; ticket-prep and execute-raft harvest every review finding into them; any other new lesson depends on the role (a prep or raft lead writes it under the skill it improves, any other lead captures a new lesson as an issue, and a subagent reports it).

### Metrics
`tracker.sh metrics` gains two tables after "Review rounds per raft", to show whether lessons reduce review rounds (the captured outcome):
```luau
export type TagCount = { tag: string, findings: number, items: number }
lessons.tagCounts(all: { Lesson }, items: { Item }): { TagCount }
export type RaftRounds = { id: string, rounds: number, start: number? }
export type Split = { rafts: number, rounds: number, mean: number }
lessons.roundsSplit(rafts: { RaftRounds }, cutoff: number?): { before: Split, after: Split }
```
- **tagCounts** (pure): every review entry, not a note, that names at least one lesson in `all` carrying a tag counts once for that tag, however many of its lessons carry it. One-off entries name no lesson, so they count nowhere, and an id `all` does not hold adds nothing. `items` is the number of distinct items with such a finding. The order is most findings first, then tag.
- **roundsSplit** (pure): `start` is the commit time (unix seconds) of a raft's `design-review-001.md`, and `cutoff` is that of the commit that added `scripts/tracker/lessons.luau`. A raft with `start >= cutoff` is "after", and every other dated raft is "before". With no cutoff, every dated raft is "before". A raft with no start or no rounds counts nowhere. `mean` is rounds over rafts, or 0 with no rafts.
- **The reader** (`cmd.metrics`) parses every lesson `load(".")` finds, skipping one that fails `parse`, and passes `tree.items`. For each raft with a design-review file, it counts `design-review-NNN.md` files and takes `start` from `git log --follow --diff-filter=A --format=%ct -- <dir>/design-review-001.md` (the oldest line). The cutoff comes from the same command on `scripts/tracker/lessons.luau`. A failed `git` gives nil.
- Output:
  - `Findings per lesson tag (harvested review findings; a finding counts once per tag).` then `| tag | findings | items |`, one row per tag;
  - `Design rounds before and after lessons (cutoff: the commit that added scripts/tracker/lessons.luau).` then `| | rafts | design rounds | rounds/raft |`, with a `before` row and an `after` row, means to one decimal place.

### Scalability
- About 880 past findings and maybe 100 lessons (after c0112): `load` reads about 2 MB of review text once, which takes well under a second in Lune.
- The prompt grows by one line per build lesson (about 150 characters). At 100 lessons that is 15 KB, beside a prompt that is already about 150 KB of inlined skills. If it outgrows that, `index` can cap by source count: a later chore, noted here.

### Maintainability
- One source of truth per fact: sources live only in the ledgers, the lesson text only in its file, and ids come from paths.
- No ids or counters to allocate: two branches that add the same slug collide as a plain git add/add conflict, resolved by merging the texts.
- Renaming a lesson leaves dangling ledger entries, which `--check` names.
- Compaction: ledgers are under `tracker/`, so `compact` already rewrites the item ids in them. Lessons hold no item ids except in free text (`from`), which compaction leaves as it is: harmless, since nothing parses it.

### Usability
- One command with grep-like words: `tracker.sh lessons lock`, or `lessons --skill testing`.
- The listing's first line is the most-repeated lesson.
- A harvester sees the tags in use (`--tags`) and every gap (`--uncovered <R-id>`), each named by file and finding.
