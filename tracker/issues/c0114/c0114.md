# c0114: Move the tracker into z-nile

## Problem
The tracker, its build, and the skills live in the same tree as the game. A second game would share that tracker's issue folders. A developer opening the repo cannot tell the tooling project from pickman.

The tracker engine, the skills, and the build that runs them move under `z-nile/`. That project has its own issues in `z-nile/tracker/`. Pickman's issues stay in the root `tracker/`. `z-nile/projects.toml` lists the projects that get a board tab. A directory that is not listed is not a project.

Decided with the user (2026-10-20):
- Each project holds its own issues in its own `.tracker/`. z-nile's are in `z-nile/.tracker/`; pickman's move to `pickman/.tracker/` in c0120.
- One shared id counter for every project, so a bare id stays unique across the repo and `find` searches every project root.
- The command is `./zn <cmd>` at the repo root, a shim to the engine in `z-nile/`. `scripts/tracker.sh` goes away.
- The work lands as sequenced rafts, one PR each: c0114, c0120, c0115, c0116, c0117, c0118.

Decided with the user (2026-10-20), from the programme review:
- Scope decision (user, 2026-10-20): "Yes, later choice wins": issues live in `<project>/.tracker/` (z-nile's in `z-nile/.tracker/`), not `z-nile/tracker/`, and the game moves in c0120. The Non-goal "The game stays at the repo root until a later game is nested" is superseded.
- Scope decision (user, 2026-10-20): "In c0115, with the rename": the skill sources move into `z-nile/skills/` in c0115, together with the rename. c0114 moves the engine and the build.

Decided with the user (2026-10-20), restated for this prep (from the brief that started it):
- `z-nile/projects.toml` lists the projects. One counter numbers every project; `find` searches every root.
- The forwarder approach of `scripts/tracker.sh` applies to `scripts/lib/ac.sh` and every other path that the `check.sh` files or the prepared rafts name.
- The gate's cache-path review (`tests/lib/cachepaths.luau`) covers `z-nile/` too.

- Skills do not move in c0114; c0115 moves and renames them. R0030 and R0039 are re-prepped after c0120, so c0114 keeps them working only through the general forwarders. Tooling stays Luau on Lune.

## Non-goals
- Renaming skills, splitting raft creation, choosing models, or drawing the new board. Those are c0115, c0116, c0117, and c0118.
- Moving pickman's `src/`, tests, or Rojo projects. The game stays at the repo root until a later game is nested. (Superseded in part by the scope decision of 2026-10-20: the game moves in c0120, not in c0114.)
- Closing c0113. That issue is the old skills page, and its non-goals forbid changing skills.

## Solution
- Add `z-nile/` and move the tracker implementation and its build there. The command the developer runs can stay `scripts/tracker.sh` if that file becomes a forwarder.
- Add `z-nile/projects.toml` with `z-nile` and `pickman`.
- Leave pickman's issue documents in root `tracker/`. Put tooling issues in `z-nile/tracker/`.

### 2. The project registry: `z-nile/projects.toml`
```toml
# The projects in this repository (c0114). Each one keeps its issues and rafts in its own tracker root and gets a
# board tab. A directory that is not listed here is not a project. Read by z-nile/engine/projects.luau; the publish
# guard reads this file from origin/main only.
#   name: lowercase words joined by hyphens, unique
#   root: "<name>/.tracker", or "tracker" (pickman's until c0120 moves it to pickman/.tracker)
# The first project is where `./zn new issue` files an issue that names no --project.
# `retired` lists roots that once held items and hold none now; history and the trail still read them.
retired = []

[[project]]
name = "pickman"
root = "tracker"

[[project]]
name = "z-nile"
root = "z-nile/.tracker"
```
`z-nile/engine/projects.luau` is its one reader (lesson architecture/one-reader-per-format):
```lua
export type Project = { name: string, root: string }
export type Registry = { projects: { Project }, retired: { string } }
projects.FILE = "z-nile/projects.toml"
projects.LEGACY = "tracker"
projects.parse(text: string): (Registry?, string?)      -- pure; nil and the first problem
projects.legacy(): Registry                              -- { pickman = "tracker" }: a tree from before c0114
projects.shapeOk(root: string): boolean                  -- "tracker" or "<name>/.tracker"
projects.roots(reg): { string }                          -- current roots, in file order
projects.allRoots(reg): { string }                       -- current, then retired (history readers only)
projects.rootOf(path: string, roots: { string }): (string?, string?) -- root and rest, by whole segments
projects.named(reg, name): Project?;  projects.projectOf(reg, root): Project?
projects.load(dir: string?, fresh: boolean?): Registry   -- the working tree's (cached per dir; fresh rereads)
projects.at(rev: string, cwd: string?): (Registry?, string?) -- the registry at a commit
```
Rules (`parse`, lesson architecture/parsers-refuse-ambiguity): TOML through `serde.decode("toml")`, which already refuses a repeated key; top-level keys only `project` and `retired`; at least one `[[project]]`; each project has exactly `name` and `root`; a name is lowercase words joined by single hyphens; a root is `"<name>/.tracker"` (its own name) or the legacy `"tracker"`, nothing else (not `src`, `.`, `..`, an absolute path, `z-nile/tracker`, another project's folder or anything deeper); names and roots are unique; `retired` holds roots of the same two shapes, none of them current. Every refusal names the file and the rule.

A tree or a commit with no registry predates c0114: `load` and `at` give it the legacy registry (one root, `tracker`). That is never wider than what that tree had. A registry that is there but does not parse is an error everywhere: `load` raises, `at` returns nil and the reason, `publish.commit` refuses, `audit` reports `error registry`.

**Guess (pending user, 2026-10-20):** pickman is listed first, so `./zn new issue` without `--project` files where it always did (`tracker/`), and every command and spec that worked before still does. Tooling captures pass `--project z-nile` (make-issue says so). The other reading (z-nile first) would move every default capture and needs no code change, only the order.

The registry carries only `name` and `root` now. c0120 adds pickman's other paths (gate, Rojo projects, runtime-test folder, architecture document) when it moves them; c0120 then only changes pickman's `root` to `pickman/.tracker` and adds `"tracker"` to `retired`.

### 5. The shared counter
The counter's home becomes `z-nile/next`, which no later move touches (c0120 moves `tracker/`, never `z-nile/`). Same format, same rules (`ids.FILE = "z-nile/next"`, `ids.OLD_FILE = "tracker/next"`). **The branch never touches `tracker/next`**: main's engines raise it with every capture and new raft (16 times on 2026-10-20), so any branch edit of it would conflict at every merge of main, the PR's own merge after `done` included (design review 003 F1). The PR leaves it byte for byte as main has it, and adds no `z-nile/next`. Origin moves the counter once, after the landing.

Which file is the live counter is decided from the base the publish fetched, never the working tree, by `publish.counterOf(hasRegistry, hasNew, oldText)`:
- the base has `z-nile/next`: that is the counter;
- the base has no `z-nile/projects.toml` (main before c0114 lands, c0114's own execution included): `tracker/next` is the counter. The branch's engine reserves there (new issue, emergent issue, new raft, renumber, remap), and a merge of main is a plain merge: the branch never changed the file;
- the base has the registry but no `z-nile/next`, and `tracker/next` parses (c0114 has just landed): `z-nile/next` is the counter and this publish **moves it**. In its one commit and lease push it writes `z-nile/next` with `tracker/next`'s counters (raised, if the publish reserves a number; the go-up check compares against them) and the tombstone at `tracker/next`:
```
moved to z-nile/next (c0114): this file never parses, so a tracker engine from before the move refuses to number
```
  A lost lease (an old engine raised `tracker/next` meanwhile) retries on the new tip, as every publish does, and moves the raised counters. Execute-raft Phase 6 step 2's `./zn spend R0043 --phase deliver` is the first publish after the merge, so the move happens minutes after landing; until then old engines keep numbering on `tracker/next`, which is still the live counter.

`publish.commit` lists, allows and checks (it may only go up) the live counter alone and passes it to the build as its fourth argument; `reserve` reads and raises it. `publish.allowed(path, roots, counter)` allows exactly `counter` and refuses the other counter file, so no build ever writes `tracker/next` after the move: neither a counter, nor the tombstone again, nor a fresh file where c0120 has removed it. Locally, `localCounters` (offline numbering) and `audit` read `z-nile/next` when the tree has it, else `tracker/next`. `audit` reports `error old-counter` when both parse (an old engine would number from the old one) and `warning counter-unmigrated` for the state between the landing and the first publish. A compaction in a tree whose counter has not moved writes `z-nile/next` and the tombstone together.

After the move an engine from before c0114 (a worktree cut before it) reads `tracker/next` on origin, cannot parse it, and refuses `new issue`, `new raft` and `renumber` with "tracker/next on origin/main does not parse" (E5: run; still true, because the tombstone is the same text, written by the first publish instead of by the PR). Its other commands only find items under `tracker/`, so on a tooling item they say "<id> is not on origin/main". c0120 keeps the tombstone (a file, not an item folder) when it moves pickman's items.

### 6. The compaction map and history across roots
`ids.MAP_FILE = "z-nile/compaction.txt"`; `ids.MAP_FILES = { "z-nile/compaction.txt", "tracker/compaction.txt" }` for history. `refuseStale` compares the local and origin copies of `z-nile/compaction.txt`, as before.

The trail (c0111, `z-nile/engine/trail.luau`) keeps its rule: the current id only, never crossing an id change. c0114 adds:
- `trail.dirs(kind, id, roots?)` lists the three folders under each root; `trail.read` takes `roots` or reads them from `head`'s registry (`projects.at(head)`, legacy when absent), current and retired.
- A move between roots is one commit that deletes the document in one folder and adds it in another, so `life` sees no gap and the life goes on. An id is unique across roots, so two roots never hold two items under one id (`audit` makes that an error).
- `trail.cuts(head)` lists the commits that changed a map's content: `git log -M --diff-filter=AM --name-only -- z-nile/compaction.txt tracker/compaction.txt`. With `-M` the c0114 move of the map is a rename, so it is no cut; a later compaction writes `z-nile/compaction.txt` and is one. Each cut carries the file it changed.
- `trail.read`'s second result is `{ { sha: string, file: string } }`, and `capture` prints `(history before <sha> not followed: it changed <file>)`. For the 2026-10-05 compaction that is still `tracker/compaction.txt`, the text c0119's spec pins; for a compaction after c0114 it names `z-nile/compaction.txt`.

`history` (the board's stats) reads every item document under every root ever (`allRoots`), keyed by id with `--no-renames`. A move between roots is a delete and an add in one commit: a done item keeps its close day, an open one keeps its spell. That is the interface c0118 needs. `metrics`' lessons cutoff (R0042: rafts dated by their `created:` day, against the local day the module was added) is the day of the earliest add of `scripts/tracker/lessons.luau` or `z-nile/engine/lessons.luau`, so the move does not reset it. R0042 read one path with `--follow`; after the move the old path is a forwarder (modified, not renamed), so `--follow` from the new path would date the move, and the lesson tracker/item-history-spans-moves-and-compaction says to avoid it anyway.
