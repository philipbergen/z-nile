# c0114: Tag each issue with a project

## Problem
The tracker, its build, and the skills live in the same tree as the game, and every issue is one list. A second game cannot have its own tab. Publish accepts only paths under `tracker/`, so a second issue directory cannot be created by `new issue`.

`z-nile/projects.toml` names the tabs. An issue carries `project:` in its frontmatter. The default is `pickman`. Documents stay under `tracker/`.

## Non-goals
- Renaming skills, splitting raft creation, choosing models, or drawing the new board. Those are c0115, c0116, c0117, and c0118.
- Moving pickman's `src/`, tests, or Rojo projects. The game stays at the repo root until a later game is nested.
- Closing c0113. That issue is the old skills page, and its non-goals forbid changing skills.
- A second issue root, a second id counter, or a change to publish, claims, ready, or stop.

## Solution
- Add `z-nile/projects.toml` as the list of tab names. It does not choose directories.
- `new issue --project z-nile` writes `project: z-nile` on a document that still lives under `tracker/issues/`. No flag writes `project: pickman`.
- A missing projects file means the one project `pickman`. A file that exists and is malformed is an error. Publish, claims, ids, ready, and stop stay on `tracker/`.

## Design
`z-nile/projects.toml` is a list of ids, in order:

```toml
id = ["pickman", "z-nile"]
```

`scripts/tracker/projects.luau`:

```lua
function projects.read(repo: string): { string }
```

`read` looks for `{repo}/z-nile/projects.toml`. A missing file returns `{ "pickman" }`. A file whose list is empty, or that repeats an id, is an error. `--project <id>` is a flag of `new issue` and of `list`, after the subcommand words, on the published path, the offline path, and an emergent issue. The id must be in `projects.read` of that checkout. An unknown id exits non-zero, publishes nothing, and the error names the ids the file lists. `list --project` with an unknown id exits non-zero. An emergent issue with `--raft` and no `--project` copies the raft's project, which is its members' common `project:`. `--project` with a different id is refused. `new issue --project z-nile` writes `project: z-nile` and the document path `tracker/issues/<id>/<id>.md`, and that document is what `git show origin/main:` returns. No flag writes `project: pickman`. `list --project z-nile` prints issues whose `project:` is `z-nile`, and rafts whose members share that `project:`. It does not print a raft whose members are `pickman`. An issue with no `project:` key is `pickman`. `find` is unchanged: there is one root. `find`, `ready`, `status`, and `audit` do not call `projects.read`, so a fixture with no projects file keeps working.

### Scalability
The list is a short file. `list --project` filters the one directory the tracker already walks.

### Maintainability
One parser owns the file. `new issue` writes one frontmatter key. Publish is not widened.

### Usability
No flag still creates a pickman issue under `tracker/issues/`. `--project z-nile` is the only new flag a developer types, and it comes after `new issue`.

## Unknowns & experiments
A second directory was rejected in design review 001 because `publish.allowed` accepts only `tracker/`. The rows stay reasoned. `projects.luau` is not in the tree, so there is no function to mutate. "tab order" fails because `z-nile/projects.toml` is missing. "project field" and "default project" fail because the published document has no `project:` line. "read rules" fails because the module is missing. "list filter" fails because `--project` is ignored, so the pickman id is printed. "unknown project" fails because `--project z-nil` currently succeeds. "emergent project" fails because `--project pickman` on an active raft currently succeeds. Each of those is the assertion that is red, not a blanket excuse.
