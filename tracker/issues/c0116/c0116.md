# c0116: Split rafting out of design

## Problem
Ticket prep both designs an issue and creates its raft. Recent rafts are almost all a single issue, so grouping is not part of the design. A prepared issue should be able to sit with no raft until something groups it. There is no command that moves issues between backlog rafts.

`z-design` designs one issue to `design: ready` and status `prepared`, and does not create a raft. `z-raft` groups prepared issues. With an argument it does what was asked. With none, it never mixes types, never pulls an active or done raft, folds defects into one open prepared defect raft, folds chores the same way, and groups features only when they share a surface. A raft that would pass about 1,500 changed lines starts another. Recombining keeps one backlog raft and retires the other. Rafts never cross projects.

## Non-goals
- Changing the design checklist for a feature, a defect, or a chore beyond taking raft creation out.
- Choosing models or drawing the board.
- Editing `.claude/skills/ticket-prep/SKILL.md` or `.claude/skills/ready-raft/SKILL.md`. The one line added to `.claude/skills/tracker/SKILL.md` is an execution step, in the same change as `zz-rules`, not part of the prep commit.
- Changing the ready error `{id} has no raft: ticket-prep makes one (--single)`. A raftless issue is still refused by `ready`. The new text lives in `zz-rules`: a prepared issue with no raft goes to `z-raft`, and `z-ready` comes after that.

## Solution
- Remove raft creation from `.claude/skills/z-design/SKILL.md`.
- Write the policy in `.claude/skills/z-raft/SKILL.md`.
- Teach `new raft` to accept prepared members.
- Add `recombine`, a worktree edit that lands by pull request.

## Design
`.claude/skills/z-design/SKILL.md` does not contain the string `new raft`. `.claude/skills/zz-rules/SKILL.md` contains `recombine` and `z-raft`, and says a prepared issue with an empty `raft:` goes to `z-raft`.

A prepared issue is held when an origin raft's effective status is `preparing` or `prepared` and that raft's `issues:` list names the issue. A raft whose effective status is `new` holds nothing. Prepared members are never restamped, by `new raft`, by the carried `status <raft> prepared`, or by `recombine`. One scan implements the hold. `new raft`, `status <issue> preparing`, and the carried skip each refuse an issue a different raft holds, and the error names that raft.

| origin state | command | result | published |
|---|---|---|---|
| members are all `new` or all `prepared`, none held, one `project:` | `new raft` | the raft is `preparing-` and `design: draft`; a `new` member is stamped `preparing-`; a `prepared` member is not | the raft, and a `new` member's status line |
| a `preparing` or `prepared` raft already lists a member | `new raft` | refused; the error names that raft | nothing |
| one `new` member and one `prepared` member | `new raft` | refused; the error names both ids | nothing |
| `project:` differs, missing read as `pickman` | `new raft` | refused; the error names `project` | nothing |
| a member is `active` | `new raft` | refused; the error names `active` | nothing |
| a different raft holds the issue | `status <issue> preparing` | refused; the error names that raft | nothing |
| a listed member is held by a different raft | `status <raft> prepared` | refused; the error names that raft | nothing |
| members are `prepared`, held by this raft, local `design: ready` | `status <raft> prepared` | the raft's status is edited locally; members are not restamped | nothing |
| a listed member is `new` | `status <raft> prepared` | refused with the `c0053` sentence | nothing |
| every listed member is `prepared` | `status <raft> new` | the raft becomes `new` and holds nothing; members stay `prepared` | only the raft document |
| members are `preparing`, as today's raft of `new` issues is | `status <raft> new` | the raft and the members become `new` | both documents, which is the `c0053` abandon |
| the raft is `preparing` | `ready` | refused | nothing |
| the prepared commit is on origin | `ready` | succeeds | the ready move |

`z-raft` writes the Theme and Order, sets `design: ready` on the raft, and runs `status <raft> prepared`. Giving that raft back is `status <raft> new`. The members stay `prepared`, and a later `new raft` of one of them succeeds.

`.claude/skills/z-design/SKILL.md` has a `description:` that does not say it groups issues into a raft. During execution, after `zz-rules` exists, one line is added to `.claude/skills/tracker/SKILL.md` naming `zz-rules` as the current raft rule. That line is not in the prep commit. `zz-rules` states the rule itself and does not tell the reader that the tracker skill's old sentences are obsolete.

`recombine` accepts only two rafts that origin shows as `prepared-`. A raft whose status starts with `preparing-` is refused, the error names `preparing`, and origin is unchanged. The checks run in this order, and each names its own reason: type, then `project:` read from origin, then the prepared state. A refusal publishes nothing and does not print the usage banner. When both are prepared, `recombine` stamps the two rafts with one fresh `preparing-` stamp and does not restamp members. It then edits the worktree: the keeper's `issues:` brackets list every member, each moved member's `raft:` is the keeper, each member's status is unchanged on origin and in the worktree, review files move onto the keeper, and the retired directory is removed. That publish is one commit. `ready` of the keeper is refused while the raft is `preparing`. Folding one prepared issue into an open raft, without a second raft, is `status <issue> preparing` only when no raft holds it, then the worktree edit, then `status <raft> prepared`. `z-raft` says so. `recombine` is only the two-raft case.

`z-raft` with no argument is the policy the skill states. This issue does not add a second command for it. The checked behavior is `new raft` on prepared issues, and `recombine`.

### Scalability
Recombine rewrites one `issues:` list and each member's `raft:` line, and moves the review files.

### Maintainability
The policy text is in `z-raft`. The command is `recombine`. The old tracker skill keeps its sentences. One line naming `zz-rules` is added in the same change as `zz-rules`.

### Usability
A prepared issue can sit with no raft. `z-design` does not make one. `ready` still refuses a raftless issue, with the same sentence it uses today.
