# c0117: Stack model files and dispatch runtimes

## Problem
Which model runs a skill is not written down. A monorepo cannot give one directory a cheaper cap and another a stronger model. A raft that touches two of those directories has no rule for which spec wins. Ready, stop, recombine, and recording spend do not need a model, and there is no command that prints the choice before a process starts.

`.models.toml` stacks like `.gitignore`: from the repo root down to the work, a closer file replaces only the keys it sets. A step about one issue resolves the repo root and each directory named in that issue's Touched modules, and uses the more powerful spec whole. Higher `rank` wins. The same rank uses the larger `max_tokens`. The four fields stay together. `tracker.sh dispatch <skill> <id> --dry-run` prints the plan and does not start a runtime. The runtime is `cursor-cli`, `grok-cli`, `claude-cli`, `cursor-app`, `claude-cloud`, or `grok-bot`. Nothing defaults to Cursor. `spend --model` and `commit --model` store the model id on the spend row, beside the token count.

## Non-goals
- Drawing the board. c0118 reads the model id this issue stores.
- Starting `agent`, `grok`, or `claude`. The checked behavior is the plan, the stack, and the spend cell.
- Pasting skill text into the prompt.

## Solution
- Add a root `.models.toml`. A closer file on the path replaces only the keys it sets.
- Resolve one spec per directory. The stronger spec wins whole.
- `dispatch --dry-run` prints `kind=script` or `kind=model` and does not launch a runtime.
- A spend row gains a model cell only when a model was recorded. A file with no such row stays nine columns.

## Design
The modules are `scripts/tracker/models.luau` and `scripts/tracker/dispatch.luau`, required as `require("@scripts/tracker/models")` and `require("@scripts/tracker/dispatch")`. They are already inside the gate's `scripts/` root. No `.luaurc` alias is added.

```lua
export type Spec = { model: string, rank: number, runtime: string, maxTokens: number }
function models.resolve(repo: string, dir: string, skill: string): Spec
function models.strongest(specs: { Spec }): Spec
```

`resolve` reads every `.models.toml` from `repo` down to `dir`. A key set closer replaces that key. A missing key is inherited. A closer `max_tokens` of 1000 replaces a root cap of 300000 on that walk. A skill that no file on that walk names is an error, and the error text contains the skill name. A model with no `rank` is an error. A runtime other than the six names is an error. `strongest` of an empty list is an error. `strongest` picks the higher `rank`. Equal ranks pick the larger `maxTokens`. The winner's four fields stay together.

For an issue, the directories are the directories of paths listed under `### Touched modules`, except paths under `tracker/` or `tests/acceptance/`. Those two prefixes are the issue's own documents and its promoted specs, and they do not join the comparison. Each remaining directory is stacked from the repo root down. The bare root is not added again. If the filter leaves no directory, the only directory is the repo root. An issue that touches `game/x.luau` and `tracker/issues/<id>/acceptance/a.spec.luau` resolves only `game/`. `dispatch.plan` runs first. `resolve` and `strongest` run only when the plan is `kind == "model"`. A script step never looks up a model. A closer file can lower a cap for an issue whose touched paths all sit under that directory. An issue that also touches a path outside it takes `strongest` of the two resolved specs, so the root's larger cap wins that mix.

```lua
export type Step = { kind: string, spec: Spec? }
function dispatch.plan(skill: string, spec: Spec?): Step
```

`z-ready`, `z-stop`, `recombine`, and `spend` return `{ kind = "script", spec = nil }`. Any other skill returns `{ kind = "model", spec = spec }`. `plan` does not launch a process.

The root `.models.toml` is this table. A model-kind skill with no row is an error from `resolve` of the repo root. `zz-review` has the higher rank, so a review does not inherit a cheaper build model.

```toml
[z-ticket]
model = "grok-4.7"
rank = 2
runtime = "grok-cli"
max_tokens = 80000

[z-design]
model = "grok-4.7"
rank = 2
runtime = "grok-cli"
max_tokens = 200000

[z-raft]
model = "grok-4.7"
rank = 2
runtime = "grok-cli"
max_tokens = 80000

[z-run]
model = "grok-4.7"
rank = 2
runtime = "grok-cli"
max_tokens = 300000

[zz-review]
model = "claude-opus-5-5-medium"
rank = 3
runtime = "claude-cli"
max_tokens = 200000
```

`scripts/tracker.sh dispatch <skill> <id> --dry-run` prints the plan and exits. A model plan prints four lines, `kind=model`, `model=<id>`, `runtime=<name>`, and `max_tokens=<n>`. A script plan prints `kind=script` and no `model=` line. There is no form of `dispatch` in this issue that starts a runtime.

`ledger.Row` grows `model: string?`. `parse` accepts 7, 9, and 10 cells. An empty tenth cell is `nil`, not `""`. `render` writes nine cells when every row has no model, and ten when any row has one. `same` compares `model`, so `appendOnly` returns an error when a published row's model changes. `tracker.sh spend --model <id>` and `tracker.sh commit --model <id>` set that cell. Without `--model`, the file stays nine columns.

### Scalability
The walk is the directories from the repo root to each touched path. A raft step resolves the issues named on the raft's `issues:` list, the same set `ready` checks, and calls `strongest` once over all of their directories.

### Maintainability
The stack rule is `resolve`. The power rule is `strongest`. The script-versus-model rule is `dispatch.plan`. Both commands write the cell through `ledger`.

### Usability
A directory drops a `.models.toml` that names only the skills it wants to change. `dispatch --dry-run` shows the choice.

## Unknowns & experiments
E1. A closer file replaces `max_tokens` and keeps `model` and `rank`. The prototype `tracker/issues/c0117/experiments/rank.luau` reimplements that rule; it does not parse toml. Result: printed `pass`. It is a sketch, not evidence the parser works. The spec is the check. Fallback: the closer file replaces the whole skill. Not taken.

E2. Paths under `tracker/` and `tests/acceptance/` are skipped, and the remaining directories take `strongest`. `tracker/issues/c0117/experiments/dirs.luau` is that filter, about forty lines, not a toml parser. An issue that lists `game/x.luau` and `tracker/issues/c0001/acceptance/a.spec.luau` prints `max_tokens=1000`. Adding `other/y.luau` prints `max_tokens=300000`. A raft whose `issues:` list names both prints `300000`. A raft whose list names only the game issue prints `1000`. Result: printed `pass`. The rows for `resolve` and `dispatch` stay reasoned because those modules are not in the tree. "model cell" does not call them. `ledger.luau` is already there and has no tenth cell, so that case stays red until the cell exists. The hyphen bug is not why: `lune run tracker/issues/c0117/experiments/literals.luau` printed `pass`, and a pattern `gsub` of `grok-4.7` would have left the token in place. "dry run" fails because `dispatch` is missing. The cap numbers that case names are what E2 already printed.

### Rules and mutants
| rule | spec :: case | mutant it kills | checked |
|---|---|---|---|
| a closer file replaces only the keys it sets | models.spec :: closer key wins | replace the whole skill from the closer file | reasoned |
| higher rank wins and keeps its own cap | models.spec :: higher rank wins whole | take the winner's model and the other cap | reasoned |
| equal rank keeps the larger cap and that spec's model | models.spec :: equal rank uses the larger cap | keep the smaller cap | reasoned |
| `z-ready`, `spend`, and `recombine` are script; `z-design` is model and keeps the spec | models.spec :: plan kinds | return script for every skill | reasoned |
| nine cells render nine columns; a model cell round-trips; an empty tenth cell is nil; a changed model fails appendOnly | models.spec :: model cell | always write ten cells, or drop the model, or treat "" as a model | reasoned |
| a missing rank, an unknown runtime, and an unnamed skill are errors, and the unnamed error names the skill | models.spec :: bad specs | default the runtime to cursor-cli | reasoned |
| dry-run prints the stacked cap and does not print usage; spend on a backlog issue writes the model; spend on an active issue names `commit --phase` | models.spec :: dry run and model flag | ignore `--model`, or record spend for an active item | reasoned |

## Acceptance criteria

### Checked
- AC1: Resolving a skill with a root file and a closer file that sets only `max_tokens` keeps the root model and rank and uses the closer cap.
- AC2: Of two specs, the higher rank is returned with its own `maxTokens`.
- AC3: Of two specs with the same rank, the larger `maxTokens` wins and its model comes with it.
- AC4: `dispatch.plan("z-ready", spec)`, `plan("spend", spec)`, and `plan("recombine", spec)` are `kind == "script"`. `plan("z-design", spec)` is `kind == "model"` and its spec is the one passed in.
- AC5: `render` of rows with no model uses the nine-column header. `append` of a row with a model uses a ten-column header, earlier rows parse back with `model == nil`, and the new row parses back with that model. A tenth cell that is empty parses as `nil`. `appendOnly` of a file whose first row's model changed returns an error.
- AC6: A model with no rank is an error. A runtime outside the six names is an error. A skill no file names is an error whose text contains the skill name. `strongest` of an empty list is an error.
- AC7: `dispatch z-run <id> --dry-run` for an issue that touches `game/x.luau` and `tracker/issues/c0001/acceptance/a.spec.luau` prints `kind=model` and `max_tokens=1000`. The same command for an issue that also touches a path outside `game/` prints `max_tokens=300000`. `dispatch z-run R0001 --dry-run`, where that raft's `issues:` list names both, prints `max_tokens=300000`. The same command for a raft whose `issues:` list names only the `game/` issue prints `max_tokens=1000`. None of these prints `usage: scripts/tracker.sh`. `dispatch spend <id> --dry-run` prints `kind=script` and no `model=` line. `spend --model grok-4.7` on a backlog issue leaves that id in `spend.md`. `spend --model` on an active issue exits non-zero and names `commit --phase`. `commit --model grok-4.7` on the active issue leaves that id in its `spend.md`. `models.resolve` of the repo root succeeds for `z-ticket`, `z-design`, `z-raft`, `z-run`, and `zz-review`.
