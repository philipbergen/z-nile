# c0117: Stack model files and dispatch runtimes

## Problem
Which model runs a skill is not written down. A monorepo cannot give one game a cheaper design model and another a stronger one. A raft that touches two of those games has no rule for which spec wins. Ready, stop, recombine, and recording spend do not need a model, but nothing stops an agent from being started for them.

`.models.toml` stacks like `.gitignore`: from the repo root down to the work, a closer file replaces only the keys it sets. A step about one issue uses that issue's spec. A step about a raft resolves every member and uses the more powerful spec whole. Higher `rank` wins. The same rank uses the larger `max_tokens`. The dispatcher runs script steps itself. A model step calls the named runtime with the skill name and the issue id, and stops at the cap. The runtime is `cursor-cli`, `grok-cli`, `claude-cli`, `cursor-app`, `claude-cloud`, or `grok-bot`. Nothing defaults to Cursor. The spend row stores the model id and the token count the adapter returns.

Decided with the user (2026-10-20):
- The supported CLIs are `agent` (Cursor), `grok` and `claude`, each with its own set of models in `.models.toml`. A CLI the file does not list is not supported.
- A priority order says which CLI to use. The dispatcher moves down the order when a CLI's remaining tokens seem insufficient for the step, which it learns by asking that CLI.
- Model steps run headless and unattended.
- The dispatcher chains the steps on its own (ticket, design, raft, ready, run) up to the pull request, and stops at a human gate (a merge) or a failure.

Decided with the user (2026-10-20), from the programme review:
- "In scope via the same CLIs": all six captured runtimes stay. cursor-app is `agent worker`, claude-cloud is `claude --cloud`, and grok-bot is `grok agent headless`, each a runtime of its CLI in `.models.toml`.
- Quota, in the user's words: "error only, but there is a catch, make sure the cli doesn't hang in waiting for more quota, it should fail on insufficient quota." The dispatcher moves down the priority order only when a CLI fails on quota, and it must make each CLI fail rather than wait (flags, a no-progress timeout, or detecting a wait message and killing it).
- "Branch protection + wrapper": `main` gets branch protection (a PR and green CI required), and agents run with a git/gh wrapper on PATH that refuses direct pushes to `main` and any merge the dispatcher didn't authorise.
- "Stop with questions.md": a step that needs the user writes `.cache/dispatch/<id>/questions.md` and exits "needs the user". The chain stops, the board shows it, and the user answers and retries.
- Reviews, in the user's words: "They must not run on opus, only use opus with claude and cursor (cursor[agent] supports both grok and opus), grok uses grok-4.7-xhigh." The review model belongs to the CLI: Opus through `claude` or `agent`, and `grok-4.7-xhigh` through `grok`. The skills' "reviewer runs on Opus" rule changes to match.
- "Name the files in the prompt": the prompt names each skill's file path and the `zn lessons --when <step>` command, and every CLI reads them itself. No skill text is pasted.
- "One oversized PR": c0117 stays one raft.

## Non-goals
- Drawing the board. c0118 reads the model id this issue stores.
- Pasting skill text, the architecture map, or other issues into the prompt.

## Solution
- Add a root `.models.toml` and the stack walker.
- Add one adapter per runtime. Each returns a token count.
- Record that count and the model id with `tracker.sh spend --tokens`. A row with no model stays unrecorded.
