# c0119: Scope fidelity in prep and review

## Problem
Prep and review cut captured scope without asking the user. R0042 (z-nile) lost most of what was captured over five design-review rounds: the move into `z-nile/` became a frontmatter tag, the skill rename became copies beside the old skills, the dispatcher became a dry run, and the board lost its live data. Each cut started as a reviewer's recommended fix (review-001 F2: "I recommend (a)", shrink scope), the author accepted it in a refute, and then rewrote the issues' Problem sections to match. Nobody asked the user, and nothing in the skills says to.

The user (2026-10-20): "Make changes to the skills to ensuring that scope isn't cut. That's a lesson learned that needs to be baked in." The user chose two rules:
- **The Problem is frozen after capture.** Prep adds detail (Solution, Design, criteria) but does not rewrite, narrow or drop what the captured Problem asks for. Any such change needs the user's answer, recorded in the document with its date and words.
- **A reviewer can't prescribe cuts.** A design review that finds a captured outcome dropped without a recorded user decision reports it as high. A Recommendation never prescribes a cut as the fix. When narrowing is the only feasible fix, it says to escalate to the user and lists the options, and the author asks the user instead of accepting it in a refute.

The lesson is also recorded in the lessons mechanism (c0111), so every later prep and review reads it.

Decided with the user (2026-10-20), on design review 006:
- The baseline is the capture: an issue's title, Problem and Solution as of its last `tracker: new <id>` commit, plus decision lines. "Capture commit + one-time audit": each prepared raft whose members' scope changed since capture gets the user's confirmation before it is readied.
- "Yes, they're scope": ideas the user gave under a captured Solution are scope too, not only the Problem.
- "Restart: 006 is round 1": a re-prep after a scope reset restarts the round count.

## Non-goals
- A scope trace table or a `tracker.sh scope` command. The user did not choose them (2026-10-20).
- Restoring R0042's members' scope. That is the R0042 re-prep itself, not this issue.

## Solution
- make-issue, ticket-prep, review (design mode) and execute-raft state the two rules.
- Two lessons in c0111's format, sourced from this correction.

## Design
The rules go into six skill files, one read-only command (`tracker.sh capture`) shows an item's capture, two lessons go into the lessons folders, and one `note` line goes into R0042's `harvest.md`. c0111 lands first in this raft, because this issue's text sits next to c0111's (review item 10, ticket-prep step 5.3) and its lessons case uses c0111's `scripts/tracker/lessons.luau`.

The rule in one place: **an issue's scope is its capture**: its title, Problem and Solution ideas at the newest commit on `origin/main` whose subject starts `tracker: new <id>` (make-issue's landing commit and the stub's publish both use it, and `tracker: new raft` does not match), or else the document's first add, plus the `Scope decision (user, …)` and `Decided with the user (…)` lines added since. Prep and review may add detail. They never drop, defer, narrow or reword away a captured outcome unless the user decided it. A later prep's landed rewrite does not become scope: the baseline stays the capture. Splitting an issue is a scope change too. Where the author cannot ask (an agent outside Claude Code, a headless dispatch), it stops and reports the options as its result. Captured Solution bullets stay as they are, and the design is added after them (round 007 F3).

**`scripts/tracker.sh capture <id>`** (in `main.luau`, read-only, the user's choice on round 007) prints `capture <sha> <path> <subject>`, then `git show <sha>:<path>`. It finds the commit with c0111's `trail.capture(trail.read(kind, id, trail.isDoc, head))`, where `kind` is `rafts` for an `R` id and `issues` otherwise, and `head` is `origin/main`, or `HEAD` when there is no `origin/main`. So it reads the item's backlog, `active/` and `done/` folders and, before the last compaction, the id `tracker/compaction.txt` renamed. A legacy slug-named document counts, and it never follows renames, so a look-alike document is never taken for the item's. A malformed id prints `usage: capture <id>`, and an id with no history prints `capture: no history for <id> on <head>`, both with exit 1. It writes nothing. It is not in `READ_ONLY` (`tests/tooling/tracker-guarded` pins that set), so it checks the repository root like other commands. It may run in the main checkout, which ready-raft needs, so the tracker skill's Worktrees list names it. A git recipe could not do this reliably: `git log --grep` with `--follow` prints nothing, and without `--follow` it misses pre-compaction paths (round 007 F1).

Where each rule goes (exact text in the Appendix):
- **make-issue**, step 4's Problem bullet: the outcomes the Problem names are the scope, and prep may not narrow them without the user.
- **ticket-prep**, a paragraph before `## 1. Form the raft`, **Scope is what was captured.**: the baseline, what prep may add, the `Scope decision` line, that a reviewer's recommendation (or the author's own judgement that something is hard) is not a decision, and that a scope too big for one raft is split into sequenced rafts, never shrunk.
- **ticket-prep**, step 5.3 (answering a round), a sub-bullet before the harvest bullet, **Never answer a finding by cutting scope.**: ask the user before answering such a finding. Without a `Scope decision` line, the answer is a redesign that keeps the outcome.
- **ticket-prep**, step 5.4: a re-prep after the user resets an item's scope restarts the round count (the user's choice for R0042: round 006 is its round 1).
- **ticket-prep**, step 5.5, after the harvest confirmation: **check the scope** of every member against its capture before `design: ready`, because the final round's answers are never reviewed and refutes are where R0042's cuts happened.
- **ready-raft**, step 2, first: **scope**. Each member must match its capture apart from added detail and decision lines, or the user is asked before the raft is readied. This is the one-time audit of the prepared rafts whose members changed since capture (R0042 Risks), and it stays for every later ready.
- **review**, after **Think one step further.**, the paragraph **Never prescribe a cut.**: a Recommendation never makes a Problem outcome smaller, later or optional. When narrowing is the only fix, it starts `escalate to the user:` and lists the options, including the cost of keeping the full scope.
- **review**, design mode item **11. Scope fidelity**, after c0111's item 10: diff each document against its capture. The title, Problem and Solution ideas may only gain detail and decision lines. Every captured outcome needs a Design and an acceptance criterion: Checked, or Judged or Observed where the testing skill allows it. An outcome dropped, deferred, moved into Non-goals, reworded away or left without a criterion, with no decision, or a Problem rewritten to match a smaller design, is **high**.
- **review**, code mode item 4 (Design adherence): a deviation that drops or shrinks a Problem outcome is **high**, and its Recommendation is to escalate.
- **execute-raft**, Stop conditions: delivering an issue would drop or shrink an outcome its Problem asks for.

The lessons, both `when: design`, written in this prep (their files ride in the prep commit, like R0040's), with their source in R0042's `harvest.md` as `- note user correction 2026-10-20, …: ticket-prep/never-narrow-captured-scope, review/no-scope-cut-as-fix`:
- `ticket-prep/never-narrow-captured-scope` (tags `scope`, `process`). Its check asks whether every outcome in `tracker.sh capture <id>` still has a Design and an acceptance criterion, or a `Scope decision` or `Decided with the user` line.
- `review/no-scope-cut-as-fix` (tags `scope`, `review`). Its check asks whether any Recommendation makes an outcome smaller, later or optional instead of escalating. It is also sourced by design-review-001 F2, whose Recommendation (a) was the first cut.

A new `.claude/skills/review/lessons/` folder holds the review lesson. c0111's loader accepts any skill folder that has a `SKILL.md`.

### Scalability
Five paragraphs and two short lesson files. The reviewer's extra step is one `git diff` per item document.

### Maintainability
The rule lives in full in ticket-prep's paragraph. The other skills point at it by its bold name, and the lessons restate it with their incident. The spec pins each place, so moving or dropping one turns it red (ticket-prep/restated-rules-move-together).

### Usability
The author asks the user once, with options, instead of losing scope silently. The reviewer's check is mechanical: `tracker.sh capture <id>` next to the current document.
