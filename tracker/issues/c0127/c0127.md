# c0127: Test lock pid reuse

## Problem
tests/run's lock (.cache/tests-run.lock) is never taken over when a stale lock's recorded pids were reused by unrelated processes: on 2026-10-21 R0034's reused worktree held a lock from 2026-10-20 listing ~370 pids, two of which were alive as a macOS MTLCompilerService and another checkout's lune run, so the gate waited 240 s and gave up; the lock should check that a holder is a test run of this checkout (e.g. its command line or start time), not just that the pid is alive

Decided with the user (2026-10-22): "Store a start id (Recommended)": each lock record gets a small file with its process's start id (the kernel's exact value, no clock), and a pid counts as reused only if its id differs. Locks written by older runners keep today's behaviour (still waited for), so a stale lock left from before the change still has to be removed by hand once. (Chosen over keeping the time-based rule, whose Linux clock-step risk design review 003 F1 found, and over a time-based rule for old locks only.)

Decided with the user (2026-10-22): "Id inside the pid file (Recommended)": workers (and R0039's launcher) store their start id as the content of their own `pid-<n>` record, which is empty today, so no extra files appear in the lock beside them and R0039's sequestered `launcher-lock.spec` (it lists the lock and expects only `pid-<launcher>`) stays green; only the top process keeps a separate `start-<pid>` file. (Chosen over changing R0039's spec, and over landing with the clash deferred; design review 005 F1.)

## Non-goals
- The existing lock files and what they hold: the top process still writes `pid` (its pid), guarded processes `pid-<n>` (empty), a waiter `<lock>.takeover/pid`. Specs and tools that read them (c0058's lock.spec, the sweeper specs reading `pid`) are unaffected; the start ids go in new files beside them.
- Taking over a lock written by an older runner (no start ids): it is waited for as today (the user's decision above).
- The wait messages (`waiting for another test run (pid …)`, `gave up after …`) still list every recorded pid.
- How long a run waits (`PICKMAN_TEST_LOCK_WAIT`, 240 s), the unowned-lock rule (`UNOWNED_SECONDS`) and `fence.alive` itself (its jail and outer-sandbox reading of `Operation not permitted`, pinned by c0078) don't change.
- Linux pid namespaces under bwrap: c0075 (R0039) decides which pids are recorded there; this issue judges whatever is recorded.

## Solution
Every process that records its pid in the lock also records its **start id** with it: a worker as the content of its own `pid-<n>` record (one file, written whole), the top process in `start-<pid>` beside its `pid` record (which holds its pid), and the takeover's owner as pid and id together in `<lock>.takeover/owner`. A start id is the kernel's own record of when the process started, read exactly and never from the clock, so one process always has the same id and a later process under the same pid has another. A recorded pid holds the lock only while it is alive **and** its start id now equals the one recorded. A reused pid's id differs, so a stale lock that names one is taken over at once. Where no id was recorded (a lock from an older runner) or the id can't be read now, a live pid still holds, as today. The id is read through perl (no setuid tool, so it works for the top process, inside the jail and inside any sandbox): `sysctl` `kern.proc.pid.<pid>` on macOS, `/proc` on Linux.

## Design
All in `tests/lib/fence.luau` (the spec runner's guard; tests/run requires it). New public members, for the specs:
```luau
fence.STARTED: string                  -- the perl program below (like fence.SWEEPER and fence.REAPER)
fence.startOf(pid: string): string?    -- `perl -e STARTED <pid>`, trimmed: the process's start id; nil for a
                                       -- non-numeric pid, an exited process, perl failing or empty output
fence.holds(isAlive: boolean, recorded: string?, current: string?): boolean
  -- false if not isAlive; true if recorded or current is nil; else recorded == current
```
`fence.STARTED` (one line, joined with spaces in the source), given the pid as its argument; it prints one id and exits 0, or exits 1:
- the pid must match `^\d+$`;
- **macOS** (`$^O eq 'darwin'`): `syscall(202, pack('i4', 1, 14, 1, $pid), 4, $buf, $len, 0, 0)`, the `__sysctl` system call for `CTL_KERN.KERN_PROC.KERN_PROC_PID.<pid>` into a 4096-byte buffer, the length packed as a 64-bit size; a returned length of 0 means no such process. A `kinfo_proc` starts with `kp_proc.p_un.__p_starttime`, a `struct timeval` (`unpack('q l')`: seconds, microseconds), stamped by the kernel at fork and never changed. The id is `"<sec>.<usec>"`, e.g. `1792691574.636820`;
- **Linux**: `/proc/sys/kernel/random/boot_id` (one per boot) and field 22 of `/proc/<pid>/stat` (`starttime`, clock ticks after boot: everything up to the last `)` is dropped, since the command name can hold spaces, and field 22 is the 20th of the rest). The id is `"<boot_id>:<ticks>"`. Both are fixed for the process's life, whatever the wall clock does;
- any other system: exit 1.
No branch reads the wall clock, and ids are compared for equality, never ordered, so clock steps, slow subprocesses and rounding don't matter (design review 003 F1; the rounds 1–2 rule compared a start time with a file time and was dropped).

Writers. An id file is always written whole (`writeWhole`: into `<path>.part-<pid>`, then `fs.move` over the target), so a reader sees the old file or the new one, never a part (a partly written id would read as a different id). **No record, no id**: an id is written only by the process that writes the record, and only where it writes the record (design review 005 F3).
- `fence.enter` in a guarded process: `<lock>/pid-<me>` with its id as the content, through `writeWhole` (empty when the id can't be read). The record and its id are one file, so they appear together, and a gate on the record (R0039's `fence.recordsPid` under bwrap) gates the id with it;
- `takeLock`, after creating the lock folder: `<lock>/start-<me>` (through `recordStart`, which writes `fence.startOf(pid)` when it is not nil), then `<lock>/pid` as today (its content is the pid, which c0058's lock.spec and the sweeper specs read). The top runs outside any jail;
- `takeOverIfStale`'s waiter, after creating the takeover folder: `<lock>.takeover/owner` = `"<pid> <id>"` (pid and id in one file, so a reader gets both at one moment; design review 004 F2), then `<lock>.takeover/pid` as today (c0058's lock.spec waits for that file);
- a pid reused within one lock (a new worker under the pid of a finished one) overwrites the old `pid-<n>` with its own id in one move; until it does, the old record is judged with the old id and does not hold, which is harmless because the process that started the new worker holds the lock by its own record (design review 005 F4).
- **Any other writer** of a record must do the same. R0039 (c0075, prepared, not merged) adds one: its launcher (`fence.REAPER`, perl) creates `<lock>/pid-<launcher pid>` with `O_CREAT|O_EXCL|O_NOFOLLOW`. Whichever of R0039 and R0047 lands second makes that record carry the launcher's id as its content: the launcher runs the reader for its own pid (`$^X -e <fence.STARTED> $$`, the program handed to it in its environment like `PICKMAN_REAP_LOCK`) and writes the id into the file it created, in one `print` before closing it. No new file appears in the lock, so c0075's `launcher-lock.spec` (it lists the lock and expects exactly `pid-<launcher>`) stays green. If R0047 lands first, its promoted `reuse.spec` recording case fails on R0039's branch until the launcher writes its id; R0039's Order & dependencies says so.

Readers:
- `lockRecords(lock): { {pid, path} }` replaces the body of `lockPids` (which now maps it to pids, for the messages and the unowned count): each `pid-<n>` record with `path` = the record itself, and the `pid` record with `path = <lock>/start-<pid>`. `start-*` and `*.part-*` files are not records.
- `stillHolds(pid, idPath)`: false if not `alive(pid)`; true if `idPath` is missing or empty (no id recorded: an older runner's record, or a worker whose id couldn't be read); else `fence.holds(true, recorded, fence.startOf(pid))`. The id is read only once the pid is known to be alive, so a stale lock's dead records (370 in R0034's) cost a `kill -0` each, as today, and no perl.
- `takeOverIfStale`: the lock is stale when it has records and none `stillHolds` (was: none `alive`). The takeover's owner is cleared when `ownerHolds(mutex, owner)` is false: its pid and id are parsed from `<lock>.takeover/owner` (`^(%d+) (%S+)$`) and judged like a record (`alive`, then `fence.holds`); a takeover folder with only `pid` (an older runner, or a waiter whose id could not be read) is judged by `alive` of that pid alone, as before. The local there is renamed `owner`.
- `perl` is found on PATH, as for `fence.REAPER` and the sweeper.

Elsewhere:
- `tests/tooling/repo-fence.spec.luau`: c0127's `reuse.spec.luau` gets an `ALLOWED` entry, `{ PICKMAN_TEST_FENCE = "runs a copied runner as a top-level run" }` (the narrow form `fence-leftovers.spec` uses), for its three folders (backlog, active, promoted) through `renamed.id("c0127")`. The guard scan still applies to every other name, and the identity scan applies (its fixture commits as `c0127@example.invalid`).
- `.claude/skills/testing/SKILL.md`, the **Lock** bullet: "A lock whose every process is gone is taken over." becomes "A lock is taken over when no process it records still holds it: each is gone, or is a reused pid, whose start id differs from the one recorded with it (a worker's `pid-<n>` holds its id, the top process's is in `start-<pid>`; the id is the kernel's start record, read through perl, inside the jail too, never from the clock). A live pid with no recorded start id (a lock from an older runner) or whose start id can't be read still holds."

### Scalability
One perl run per writer (the top process and each guarded worker, once each) and one per live recorded pid per wait step while a takeover is judged; dead records cost a `kill -0` each, as today, and the first live record that holds ends the scan.

### Maintainability
The rule is one pure function (`fence.holds`, an equality), unit-tested on its own. The I/O is the perl reader beside the sweeper's and the reaper's, with a comment naming the kernel fields it reads, and two small helpers (`recordStart`, `stillHolds`). The lock keeps its old files; the ids are additions. The skill states the rule where the lock is described.

### Usability
A crashed run's lock no longer blocks the next run for 240 s just because the system handed one of its pids to another process (R0034, 2026-10-21: a macOS `MTLCompilerService` and another checkout's `lune`), on macOS and Linux, from a plain shell or inside a sandbox. A lock left by a runner from before this change is still waited for, once, and named in the message, so it can be removed by hand. Nothing changes for a lock held by a live run.
