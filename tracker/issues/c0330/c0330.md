# c0330: Check sh after promotion

## Problem
An issue's `check.sh` stops working once `tracker.sh done` has promoted its acceptance specs. The template (`tracker/templates/issue/check.sh`) finds the repo with `git -C "$A/.."`, where `A` is the issue's `acceptance/` directory. After promotion that directory no longer exists, so the script can't find the repo root or `scripts/lib/ac.sh`: `bash tracker/issues/done/c0020/check.sh` exits 127 (`fatal: cannot change to '…/acceptance/..'`, `check: command not found`). A done raft's exit criteria therefore can't be re-run on the merged branch, for example during PR review or a later audit. Found in R0030 design-review-001 F5; c0090's `check.sh` already uses the fixed pattern.

Measured in prep (2026-09-30): of the 27 `check.sh` files under `tracker/*/done/` at the start of prep, **six issue scripts exit 127** (c0010, c0020, c0041, c0420, c0430, c0440; also c0370, a stub closed without execution), and the **raft scripts of R0010 and R0020 fail** because their RC0 loop calls those. The new issues created from the template inherit the bug.

## Non-goals
- Making every criterion re-runnable forever. Some are tied to a live branch by nature: c0010's AC3 ("CI green for this branch's exact HEAD") and AC5 ("this branch has an open PR") can never pass on a later commit. The goal is that the script **runs**, locates the repo and its specs, and reports each criterion honestly.
- Changing what any done issue checks.
- Stubs in the backlog (their `check.sh` is rewritten when their raft is prepped, and the template is fixed here).

## Solution
1. **Prep did the mechanical repair** (this PR, before execution): the six broken done `check.sh` files now use c0090's locator, and the executor does not touch them (`check.sh` files are sequestered).
2. **Executor**: fix the template with the same locator, add an `AC_LIST=1` mode that lists checks without running them, make that mode **safe** (it can't be mistaken for a pass and can't re-run specs), and fix the testing skill's example. The acceptance spec uses the list mode to prove, cheaply and permanently, that every done item's `check.sh` finds the repo, so the bug can't return unnoticed.

## Design

### The locator (template and the six repaired scripts)
```bash
HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P)" # physical: tests/run strips the physical cwd
source "$(git -C "$HERE" rev-parse --show-toplevel)/scripts/lib/ac.sh" # cds to the repo root
# sequestered specs: here before `tracker.sh done`, promoted to tests/acceptance/{{ID}} after it
A="$HERE/acceptance"
[[ -d $A ]] || A="$PWD/tests/acceptance/{{ID}}"
```
- It needs only the script's own directory, which exists in every state: `git -C "$HERE"` finds the repo from `tracker/issues/<state>/<id>/`.
- `ac.sh` changes into the repo root, so `$PWD` in the fallback is the root.
- `$A` is the sequestered directory before `done` and the promoted one after it; checks keep using `"$A/<name>.spec.luau"`.
- The template substitutes `{{ID}}` in both places.

### List mode, and why it is safe (`scripts/lib/ac.sh`, `tests/run.luau`, `scripts/tracker/main.luau`)
```bash
check() {
  local label="$1"; shift
  _ac_total=$((_ac_total + 1))
  if [[ -n ${AC_LIST:-} ]]; then
    printf 'LIST  %s\n' "$label"
    return 0
  fi
  ...
finish() {
  ...
  if [[ -n ${AC_LIST:-} ]]; then   # after the empty-script check, which still fails
    printf -- '---- %d criteria listed (none run)\n' "$_ac_total"
    return 0
  fi
```
With `AC_LIST` set, `check` prints `LIST  <label>` and runs nothing, and `finish` prints `---- n criteria listed (none run)` and returns 0 (an empty `check.sh` still fails). Without it, behaviour is unchanged. Two further pieces make the mode safe (found by design-review-001):

1. **The spec runner refuses list mode** (`tests/run.luau`): when `AC_LIST` is set and non-empty, it prints `AC_LIST is set: specs are not run in list mode (unset it to run them)` and exits 1, before collecting anything. Reason: the shared-fixture pattern (`spec_out=$(lune run tests/run -- "$spec")` at the top of a `check.sh`, used by c0041, c0420, c0430, c0440 and by every `check.sh` in this raft) runs its spec **outside `check`**, so list mode alone wouldn't stop it. Without the refusal, listing finished scripts would run four e2e specs (9 s for c0041 alone), and, once R0130 is done, the permanent c0330 spec would run `tracker/issues/done/c0330/check.sh`, which would run the same spec again, without end. With the refusal, the top-level run is instant and inert in every existing and future script, and a gate run with a leaked `AC_LIST` fails loudly instead of passing.
2. **`tracker.sh check` and `done` refuse list mode** (`runCheck` in `main.luau`): if `AC_LIST` is set and non-empty it fails with `AC_LIST is set: checks would only be listed, not run; unset it`. Without this, an exported `AC_LIST` would make `done` verify nothing and print a clean summary. The list-mode summary says `listed`, never `passed`, so a log can't be misread either.

### Testing skill
`.claude/skills/testing/SKILL.md`, "Acceptance checks": the example uses the locator above (with the fallback line shown), and one sentence says a `check.sh` must run after promotion and that `AC_LIST=1` lists a script's checks without running them.

### Scalability
Listing every done `check.sh` is one `bash` start per item (about 30) plus an instant refusal from the runner for the scripts that run a spec at top level; measured in the post-`done` layout, the permanent spec takes about a second. Running the scripts would take tens of seconds and recurse.

### Maintainability
One locator, shown in the template and the testing skill, enforced by a structural case (no live `check.sh` may contain `"$A/.."`) and a behavioural one (every finished item's script lists its checks from an unrelated directory). A new issue gets it from the template.

### Usability
`tracker.sh check <done-id>` and `bash tracker/issues/done/<id>/check.sh` work again, so an auditor can re-run a finished raft's criteria.

## Acceptance criteria

### Checked
- **AC1**: with `AC_LIST=1`, `scripts/lib/ac.sh` lists each check as `LIST  <label>` without running it, and `finish` reports `n criteria listed (none run)` (not `passed`) and returns 0, except that a script with no checks still fails; without `AC_LIST` a check runs and reports as before.
- **AC2**: the issue template's `check.sh`, rendered for an id, finds the repo root and its `$A` specs both while the specs are in `acceptance/` and after they were moved to `tests/acceptance/<id>/` (run from an unrelated directory).
- **AC3**: every `check.sh` under `tracker/issues/done` and `tracker/rafts/done` (except items marked `closed:`) reaches its `criteria listed` summary with `AC_LIST=1` from an unrelated directory, and no `check.sh` under `active/` or `done/` and not the template uses `"$A/.."`.
- **AC4**: list mode can't be mistaken for a pass or re-run specs: `tests/run` refuses to run specs when `AC_LIST` is set, a `check.sh` that runs its spec at top level (outside `check`) does nothing in list mode, and `tracker.sh check` (which `done` uses) refuses to run with `AC_LIST` set.
- **AC5**: the testing skill's check.sh example uses the new locator (the `[[ -d $A ]] || A=…tests/acceptance/<id>` fallback), mentions `AC_LIST=1`, and no longer contains `git -C "$A/.."`.
