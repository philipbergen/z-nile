# c0450: Prep catches new issues that override promoted specs

## Problem
Promoted acceptance specs in `tests/acceptance/<id>/` are never edited, and executors can't change them. When a new issue deliberately changes behavior that one of those specs pins, ticket-prep doesn't notice. The conflict first appears as a red `scripts/check.sh --full` during execution, which forces an escalation. Developers lose a run of work and have to resolve a product decision mid-raft. Prep should find the conflict and plan for it.

## Non-goals
- A "supersede" or "retire" marker for specs, or tooling to apply it.
- Any change to the sequestration rules for `check.sh` files and acceptance specs.

## Solution
Three text changes, no code:
- `ticket-prep` step 3 gets an **Override check** bullet (before the Test plan bullet). For each Touched path run `lune run scripts/affected -- <path>` **and** `grep -rlF -e <path> tests/acceptance` (the selector alone misses specs that read a file as text), read every promoted spec either lists, and name each one the issue deliberately changes on an `Overrides:` line in Regression guard. Chore issues change the spec in their own raft. Any other type files a chore that only has to **remove or narrow** the spec so `main` stays green; the issue's own Test plan re-pins the new behavior, its `Overrides:` line names the spec and the chore, and its raft's Order & dependencies says the chore must be in `done/` before `start`. No conflicts: `Overrides: none`.
- `review` design mode, item 4 (Regressions), repeats the two commands per Touched path and checks them against the `Overrides:` line. An unnamed override, a missing line or an unfilled placeholder is **high**.
- The issue template's Regression guard gets a visible `Overrides: <…>` placeholder line (outside the HTML comment, so an unfilled one is detectable).

The optional `tracker.sh` helper from the capture is dropped: two existing commands already give the list.

## Design
Documents only. A promoted spec is a spec under `tests/acceptance/<id>/`.

**Finding the conflicts.** The selector (`scripts/affected`) sees only static requires, so it misses promoted specs that read a document as text: in this repo four `c0410` specs read the review skill, the ticket-prep skill and the issue template, and `c0010/ci-workflow` reads `check.yml`. So the check is the **union** of `scripts/affected -- <path>` and `grep -rlF -e <path> tests/acceptance` per Touched path. Residual, stated rather than hidden: neither finds a spec that builds a path by concatenation or walks a directory (for example `fs.readDir("tracker/rafts")`); the step tells the author to skim the `tests/acceptance` folder names for the area too.

**Why the route is a "remove or narrow" chore.** Promoted specs change only through a chore (testing skill), a raft has exactly one type, and `main` must stay green. A chore that rewrote spec S to assert the new behavior Y would fail its own gate (`main` still does X), so it could never land. The landable chore removes S, or narrows it to what the feature keeps. Consequences, all written into the step:
- the chore names S on its own `Overrides:` line, which satisfies the check for the chore itself (no chore-on-chore loop);
- a chore issue that overrides S changes it in its own raft (the testing skill already allows chores to), with no extra chore;
- the window in which X/Y is unpinned is closed by the issue itself: its Test plan must contain a case that pins Y, and its `Overrides:` line names S and the chore;
- `tracker.sh start` does not enforce `depends_on` across rafts (only the board's `blockedBy` and `workstreams` within a raft read it), so the issue's raft document must say, under Order & dependencies, that the chore is in `done/` before `start`. Enforcing it in the tracker is a separate follow-up, not in this chore;
- a product decision behind the change goes to the user during prep.

**Where the text goes** (exact anchors; the acceptance spec reads them):
- `.claude/skills/ticket-prep/SKILL.md`: a `- **Override check**` bullet in "3. Design each issue in detail", between the Regression guard and Test plan bullets. It names `scripts/affected`, `grep -rlF`, `tests/acceptance`, `ALL`, `depends_on`, chore, `remove or narrow`, `Order & dependencies`, and the lines `Overrides:` and `Overrides: none`.
- `.claude/skills/review/SKILL.md`: item 4 of "Design mode" extended (names `Overrides:`, `scripts/affected`, `grep -rlF`, `tests/acceptance`, `depends_on`, `placeholder`, **high**).
- `tracker/templates/issue/doc.md`: under `## Regression guard`, after the comment, the line `Overrides: <promoted specs (tests/acceptance/) this issue deliberately changes, each with its chore, or none>`.

### Scalability
Two commands per Touched path at prep and again at review (seconds each); the cost grows with the number of promoted specs, not with maze or ghost counts.

### Maintainability
The rule lives in the two skills that already own prep and its review; no new mechanism to keep in sync. The acceptance spec pins the anchors above, so a wording change that drops one is a chore, the same route the rule prescribes. The existing `c0410` specs pin neighbouring sections of the same files (step 3 must keep its Rules and mutants text; the template must keep its section order), so the new text is added inside `## 3.` and the template keeps `## Test plan` then `### Rules and mutants` then `## Acceptance criteria`. The new spec reads documents as text, so `scripts/affected` selects it only under `--full` (CI), not `--affected`: accepted. The directory-walk residual above is the known gap.

### Usability
Developer-facing: a prep agent gets two concrete commands and one line to write; a placeholder in every new issue prompts it. The reviewer has the same two commands, so "unnamed override" is a mechanical finding.
