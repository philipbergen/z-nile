# c0480: Start refuses unfinished dependencies

## Problem
`tracker.sh start` doesn't look at `depends_on` across rafts. An issue that depends on an item in another raft can be started while that item is still in the backlog or in progress, and `execute-raft` reads the raft document only after `start`. c0450 relies on this ordering: a feature issue that overrides a promoted spec depends on the chore that removes or narrows the spec, and that chore must have landed first, or the full gate goes red mid-execution and the executor can't edit the spec. Today only text rules (make-prompt's readiness check, the raft document) enforce it.

## Non-goals
- Ordering rafts themselves (the board's `blockedBy` already shows raft-level blocking).
- Changing `workstreams`, `prompt`, `worktree` or `done`.
- Checking the dependency's own design state or branch: only that it is `done`.

## Solution
`start` refuses when a member issue's `depends_on` names an item that isn't a member of the same raft and isn't `done` (backlog, active, or an unknown id), before anything changes. The error names the issue, the dependency and its state. The tracker skill's `start` row documents it.

## Design
In `cmd.start` (`scripts/tracker/main.luau`), after the loop that requires every member to be `design: ready` and before the branch is created, add exactly:
```lua
	-- a dependency outside the raft must already be done: nothing else orders rafts
	local inRaft: { [string]: boolean } = {}
	for _, m in members do
		inRaft[m.id] = true
	end
	for _, m in members do
		for _, dep in store.idList(store.readFront(m.doc).depends_on) do
			if not inRaft[dep] then
				local found = store.find(dep)
				if not found or found.state ~= "done" then
					fail(
						`{m.id} depends on {dep}, which is {if found then found.state else "unknown"}: it must be done first`
					)
				end
			end
		end
	end
```
- It uses only `store.find`, `store.idList` and `store.readFront`, which already exist; `store.find` returns `nil` for an unknown id and the item's `state` (`backlog`, `active` or `done`) otherwise.
- It runs before `raftBranch`, `git switch` and `move`, so a refusal changes nothing (the spec checks the branch, the directories and a clean tree).
- It checks every member, and an in-raft dependency is exempt (a raft's issues are executed in order inside the raft).
- Prepped rafts on `main` whose issues depend on unfinished items in other rafts will now be refused at `start`, which is the point; `R0090`, `R0100` and the other roadmap rafts are examples to expect.

**Tracker skill**: the `start` row gets the sentence "and every `depends_on` of a member that isn't a member of the raft must be `done` (an unknown id is refused too)". Nothing else in the skill changes.

### Scalability
One `store.find` per cross-raft dependency, at `start` only; negligible.

### Maintainability
No new helper or state: the rule reuses the store API and the same `fail` path as the `design: ready` check. A future "ready to start" report could reuse the loop.

### Usability
The message tells the developer exactly which issue, which dependency and what state it is in; it is the first thing `start` checks after design state, so nothing is half-done on refusal.
