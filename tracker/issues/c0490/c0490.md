# c0490: Beta poll transient errors

## Problem
`beta` is now a merge condition (R0080), and both of its Open Cloud steps raise on a single transient failure: `OpenCloud.publish` raises on any status but 200 and 409, and `OpenCloud.execute` raises on any non-200 while creating or polling a Luau Execution task. So one transient 429 or 5xx turns `beta` red and blocks the merge, with no retry and no documented recovery (R0080 review-001 F2).

## Non-goals
- Retrying a network-level failure (the injected `request` raising instead of returning a status), and honouring `Retry-After`: `Response` carries no headers, and a fixed pause was enough for the 409 case.
- Changing `runSuite`, `scripts/deploy-beta.luau`, `scripts/runtime-test.luau` or the workflow: they get the retries through `publish` and `execute`.
- A pause cap for `publish`: its worst case is bounded by `MAX_ATTEMPTS` alone (4 pauses of at most 60 s).

## Solution
Retry 429 and every 5xx when publishing and when creating and polling a task, and document in the tracker skill what to do when `beta` is red.
- **User decision (2026-10-01, design review F1)**: `publish` also retries 429/5xx. Rerunning the job republishes the same build and "last one wins", so a retried publish costs at most one extra version of the same commit.
- **Code** (`scripts/lib/opencloud.luau`, the only code file):
  - `OpenCloud.isTransient(statusCode: number): boolean` is true for 429 and 500-599, false for everything else.
  - `publish` makes at most `OpenCloud.MAX_ATTEMPTS` (5) requests in all. After a 409 it pauses `cfg.retrySeconds or 60`; after a transient status it pauses `cfg.transientSeconds or 5`; any other status is final. 409 and transient failures **share the one budget**. No pause after the last attempt.
  - A private `send(cfg, request, spent)` makes a task request and while the answer is transient asks again, up to `MAX_ATTEMPTS` requests per request, pausing `cfg.transientSeconds or 5` through the injected `sleep`. It returns the last response; callers keep their `~= 200` check and error text.
  - `execute` creates a `spent` counter of transient pause seconds per call, and uses `send` for the creation POST and every poll GET. A retry whose pause would take `spent` above `cfg.transientBudgetSeconds or 60` is not made: the transient response is returned and the caller raises the usual error naming that status. Spending exactly the budget is allowed. The attempt count restarts for every request; the pause is not added to the task's `timeoutSeconds` (that bounds the task, not Roblox's blips); the budget restarts for every `execute`.
  - `Config` gains `transientSeconds: number?` and `transientBudgetSeconds: number?`. `retrySeconds` stays the 409 pause.
- **Docs** (`.claude/skills/tracker/SKILL.md`, the Merging section's `beta` bullets), as a **single line**: a red `beta` whose log shows `opencloud: ... failed with HTTP 429` or `HTTP 5xx` (publish, task creation or polling; the retries ran out) is a transient Roblox failure: rerun it with `gh run rerun <run-id> --job <job-id>`, at most 3 times; any other red `beta` (HTTP 401/403/404, a `FAIL` line without such a status) is a real failure, and `BLOCKED:` once the cause isn't a Roblox blip.
- **Promoted spec change (prep did it)**: `tests/acceptance/c0140/publish.spec.luau` "any other failure is final" asserted that 429, 500 and 503 are final on publish, which this issue reverses. Prep narrowed its status list to 400, 401, 403, 404 (main stays green: the narrowed list holds today). The executor does not touch it; the new behaviour is pinned by `publish.spec.luau` here.

## Design
- **Modules**: `scripts/lib/opencloud.luau` (tooling, Lune; no `src/`). No new dependency edge, so `tracker/architecture.md` is untouched.
- **Public API**: `OpenCloud.isTransient`, `Config.transientSeconds`, `Config.transientBudgetSeconds`. `execute`, `runSuite`, `publish` signatures are unchanged.
- **Retry rules**:
  - Transient = 429 or 500-599. 408 and every other 4xx are final (409 only for publish, which retries it).
  - Exhausted retries raise the same error as before, naming the last status and body, so `runSuite` lines read as they do today.
  - A retried task creation sends the same body. If Roblox created a task before answering 5xx, the script runs twice; the runtime tests are read-only and return `PASS`, so that is harmless (E3).
  - The API key stays out of every message (only the header carries it).

### Scalability
One request costs at most 5 attempts and 4 pauses (20 s for transient, 240 s for publish's 409). The run-level bound: one `execute` takes at most `timeoutSeconds` (120) of task time plus `transientBudgetSeconds` (60) of blip pauses, 180 s, plus request time; `beta` is publish (at most 4 pauses of 60 s = 240 s, since 409 and transient failures share 5 attempts) plus N runtime scripts (N is 1 today, `tests/runtime/structure.luau`) x 180 s. That is under the workflow's 20-minute `timeout-minutes` while N is 4 or fewer; a fifth script needs the budget or the job timeout revisited. No per-frame or replication cost (CI-only tooling).

### Maintainability
One predicate and two small loops hold the whole policy; the next endpoint calls `send`. The status classes are data in one function, not branches at call sites. The knobs are three optional config fields (`retrySeconds`, `transientSeconds`, `transientBudgetSeconds`) and the shared `MAX_ATTEMPTS`.

### Usability
The developer API gains two optional fields and one predicate; specs stay fast by injecting `sleep`. For the human, a transient red `beta` now usually never appears, and when it does the skill says exactly how to recognise it from the log and what to rerun.

## Acceptance criteria

### Checked
- AC1: `OpenCloud.isTransient` is true for 429 and 500-599 and false for 4xx other than 429 and for 2xx.
- AC2: A transient failure creating or polling a task is retried and the run completes, including through `runSuite`.
- AC3: Non-transient failures (400, 401, 403, 404, 408, and 409 for tasks) are raised at once, with no retry and no pause; publish too, for 4xx other than 409 and 429.
- AC4: Retrying is bounded: exactly `MAX_ATTEMPTS` requests per request then the same final error, a fresh budget for each request, and a per-`execute` cap of `transientBudgetSeconds` (default 60) on total transient pause.
- AC5: The pause between retries is `transientSeconds`, default 5, on creation and on polling alike, independent of `retrySeconds` and `pollSeconds`.
- AC6: Retry pauses do not shorten the task's `timeoutSeconds`.
- AC7: `publish` retries 409 (`retrySeconds`) and 429/5xx (`transientSeconds`) within one `MAX_ATTEMPTS` budget.
- AC8: The API key never appears in an error after retries.
- AC9: The tracker skill has one line that names `HTTP 429`, `opencloud:`, `transient` and `gh run rerun` for a transient-red `beta`.

### Judged
- JC1: the doc line (AC9). Pass: it tells the reader how to recognise a transient red `beta` from its log (including publish), the exact rerun command, a bound on reruns, and that other failures are not rerun. Fail: it only says "rerun", contradicts itself (a publish status both rerun and blocked), or invites unbounded reruns.
