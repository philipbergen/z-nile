# c0500: Renumber advances by one

## Problem
On an id conflict (two branches picked the same number), the Conflicts rule in the tracker skill says to renumber to the next multiple of 10 above the highest number in use. That burns ten numbers per collision. It should advance by 1: the next free number above the highest of that kind in both the local tree and `origin/main`.

## Non-goals
- Changing `tracker.sh new`: it keeps the multiple-of-10 spacing, which leaves room to insert issues.

## Solution
- `tracker.sh renumber <old>` with no `<new>` picks max+1 of that kind across the local tree and `origin/main`.
- Update the tracker skill's Conflicts bullet to match.

## Design
Edits only `scripts/tracker/` and the tracker skill; no `src/` change, so no `tracker/architecture.md` change. A runnable prototype is in `experiments/prototype.diff` (94 lines, includes the skill edit): it passes all 28 acceptance cases, on a tree that includes R0160. The executor writes the real change; the prototype is a reference, not binding.

**`scripts/tracker/store.luau`**: add the number-space rule
```lua
-- one above the highest number of `kind` in the local tree and in `otherIds` (ids seen elsewhere)
function store.nextAbove(kind: Kind, otherIds: { string }): number
```
It is **not pure**: it reads the local tree through `store.all(kind)`, so like `tracker.sh list` it fails on a malformed tree (a legacy-named document, a missing `slug:`, a duplicate id), where `renumber <old> <new>` never did. That is acceptable because Landing step 0 already runs `list`, which fails on the same problems. It takes the maximum over `store.all(kind)` (backlog, active and done, so local items in every state count) and over every element of `otherIds` that is an id of that kind (`store.isIssueId` or `store.isRaftId`; the other kind is ignored), and returns `max + 1`. `store.nextNumber` (used by `new`) is **untouched**.

**`scripts/tracker/main.luau`**:
- `originIds(): { string }` (adapter): runs `git ls-tree -d --name-only origin/main` over `tracker/{issues,rafts}/` plus their `active/` and `done/` subdirectories (trailing slashes, so git lists the children) and returns the basename of each line. A path that is missing on `origin/main` prints nothing and exits 0 (experiment E1). If the command fails (no `origin/main` ref, exit 128), `renumber` stops: `cannot read origin/main (run \`git fetch origin main\`), or pass <new> explicitly`, exit 1, and nothing has moved. The command does **not** fetch: the Conflicts procedure already runs `git fetch origin main`, and a renumber that silently goes to the network would hide a stale ref.
- `cmd.renumber` accepts `renumber <old> [<new>]`. With `<new>` the behavior is exactly today's (same-prefix check, `<new> already exists` check, reference rewrite). Without it, `new = formatId(prefix of old, store.nextAbove(store.get(old).kind, originIds()))`. If that number is above 9999 it stops (`no number above 9999 is free`) rather than write a five-digit id. The rest (move, rewrite references everywhere in the tracker) is unchanged.
- The `USAGE` line becomes `renumber <old> [<new>]  step an id (conflict resolution); <new> defaults to one above the highest`.

**`.claude/skills/tracker/SKILL.md`**, Conflicts bullet: `tracker.sh renumber <ID>` with no number; say the tool picks the number one above the highest of its kind in your tree and on `origin/main` (`f`, `d` and `c` share one space, rafts have their own), that `renumber <old> <new>` sets one by hand, keep `git fetch origin main` before it, and drop the hand-computed `git ls-tree` recipe and "next multiple of 10". The Numbering bullet (`new` picks multiples of 10) stays.

Rules:
1. `renumber <old>` picks one above the highest number of the old id's kind across the local tree and `origin/main`.
2. The local tree counts in every state (backlog, active, done); so does `origin/main`.
3. `f`, `d` and `c` share one number space; rafts have their own; the prefix of the old id is kept.
4. If `origin/main` can't be read, refuse before moving anything.
5. No number above 9999.
6. An explicit `<new>` is used exactly as given (and still refused when it exists or has another prefix).
7. `new` keeps multiple-of-10 spacing.

Decision: when the old id is itself the highest, the number advances by exactly one (f0100 becomes f0101), which is what the issue asks for. Two branches renumbering to the same number at the same time is not prevented (they conflict in git again and one renumbers once more); that is out of scope.

### Scalability
One `git ls-tree` over six directories per renumber, which is a rare, manual step; cost grows with the number of tracker items (hundreds), not with game size. Nothing is replicated.

### Maintainability
The number-space rule lives in one function (`store.nextAbove`, which takes the other ids as a parameter and reads the local tree through `store.all`), next to `store.nextNumber`, and shares the id predicates; the git read is a separate adapter function. A new item kind with its own id space would be one more branch in the predicate, the same place `new` would need it.

### Usability
Developer API: `renumber <id>` is the whole recovery step, with no arithmetic or `git ls-tree` recipe to get wrong, and a number gap of one instead of ten. Failure is explicit: it names the missing `origin/main` and says how to fix it. `<new>` still allows a manual choice.
