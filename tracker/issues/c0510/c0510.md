# c0510: Publish tracker state to main

## Problem
Parallel terminals can't see each other's tracker work until a PR merges, so they pick colliding ids, duplicate effort, and can't tell whether an item is new, being prepared, prepared, active or done. Skills can also start from a stale `main`.

## Non-goals
- Enforcing claim ownership against another terminal's give-back (decided: documented only).
- A command that publishes a raft that exists only on a prep branch (decided: land in-flight preps first).
- Bypassing review for code or design content: only tracker state may be pushed straight to `main`.
- Changing `design:` (draft/reviewed/ready), which stays.

## Solution
_Draft ideas; design happens in ticket-prep._
- `tracker.sh new` pushes the stub (the item directory and a one-line description) straight to `main` as a tiny commit, so the number is reserved at once.
- A `status:` field with `new -> preparing -> prepared -> active -> done` on issues and rafts. Each transition is a tiny commit pushed to `main`, touching only `tracker/` paths. The tracker refuses to push anything else this way.
- Exception to the PR rule, limited to tracker state files; update the tracker skill's Worktrees rule 1 and Landing a change.
- Every skill (make-issue, ticket-prep, make-prompt, execute-raft, review) starts with `git fetch origin main` and a sync before it touches tracker state.
- **Open for prep**: surviving push races (rebase and retry), branch protection, and how `status:` relates to the directory-as-status rule (`backlog/active/done`).

## Design

### The model
Three pieces: a **status** per item, a **publisher** that pushes tracker-only commits to `origin/main` with git plumbing, and **commands** that use both. Review round 1 (`design-review-001.md`) shaped most of what follows; `design-refute-001.md` answers it finding by finding.

**Statuses** (frontmatter `status:`, issues and rafts): `new -> preparing -> prepared -> active -> done`. The directory (`backlog/`, `active/`, `done/`) stays the lifecycle for the tracker's own commands; `status` is the finer, shared view of it.
- **Stored value**: `<state>` or `<state>-<three words>`, for example `preparing-quiet-copper-falcon`. **Every published or carried write is a fresh stamp** (the user's decision): two terminals making the *same* move write *different* lines, so git reports a conflict instead of merging them silently, and a double claim surfaces as a conflict on the second PR or push, never as a silent overwrite. `status.parse` accepts both forms and returns the state; `status.phrase` returns the three words of a stamped value. **The words come from real entropy** (`od -An -N4 -tu4 /dev/urandom`, folded into 31 bits, with a clock fallback): Lune's `math.randomseed` saturates seeds of 2^31 and more, so seeding with `os.time()` plus `os.clock()` (seconds since boot) gave every process the same phrase, which round 3 reproduced (60 of 60 processes). With 24 words a collision is 1 in 13,824 per pair; the `start` ownership test inherits that strength.
- **Templates carry no `status:` line.** A missing field is derived, so an item made `design: ready` the old way (offline, or in an old fixture) is `prepared` and can be started. The published stub and every move add the line (after `created:`, the last key).
- **Effective status**: `done` when the item sits in `done/`; otherwise the field when it parses; otherwise derived: `active/` gives `active`, backlog with `design: ready` gives `prepared`, a backlog item that **names a raft** (an issue with `raft:`) or **is a raft** (it has `issues:`) with any other design gives `preparing`, and any other backlog item gives `new`. So the 15 issues and 4 draft rafts that exist today (f0180-f0320, R0100-R0150) read `preparing`, not `new`, and cannot be taken into another raft.
- **Claiming an existing draft raft**: it is `preparing` only by derivation, with no stored stamp, so another terminal cannot see who has it. `status <R-id> preparing` is allowed exactly then (`status.canClaim(from, to, stored, viaRaft)`: `preparing` to `preparing` with no stored status, only through a raft) and stamps the raft and its members; a second attempt is refused because the value is stored now.
- **Allowed transitions** (six): `new>preparing`, `preparing>prepared`, `preparing>new` (abandon prep), `prepared>active`, `prepared>preparing` (reopen prep), `active>prepared` (abandon execution). **`done` is never a move target**: an item is done when `tracker.sh done` files it in `done/`, and `status <id> done` is refused. Nothing leaves done; a state never moves to itself.
- **Published or carried.** `preparing>prepared` is **carried by the prep PR**: it only edits the local documents, and reaches `main` when the PR merges, because that is when the design itself lands. **Every other transition is published** at once as a tiny commit.

**Publisher** (`scripts/tracker/publish.luau`, adapter: git plumbing, no Roblox, never touches the caller's working tree, real index, HEAD or branch):
```lua
export type Change = { path: string, content: string, mode: string? }   -- mode "100644" (default) or "100755"
export type Result = { ok: boolean, sha: string?, reason: string? }
export type Build = (paths: { string }, read: (string) -> string?) -> { Change } | string
publish.allowed(path: string): boolean
publish.commit(cwd: string, build: Build, message: string | () -> string, tries: number?): Result
```
- `allowed`: only `tracker/(issues|rafts)/[active/ | done/]<ID>/<ID>.md` and `.../check.sh` (at most one of `active/` or `done/`), where the id's prefix matches the kind (`f`, `d`, `c` under `issues`; `R` under `rafts`) and the file belongs to that same id. No `..`, no absolute path, nothing else.
- **Creation vs change** (enforced inside `commit`, not by callers): a `check.sh` is **only created**, never rewritten (`<path> already exists on origin/main: check.sh is never rewritten`); an existing document may differ from origin's **only in its single `status:` frontmatter line** (both texts need one well-formed frontmatter block, and with the `status:` line removed they must be identical), so code, designs, bodies and other frontmatter cannot reach `main` by this route. A change containing a carriage return is refused, and the `status:` key is matched at a line start only (`withFront` and `store.setFront`), so a title that mentions `status:` cannot absorb a claim.
- `commit`, per try (default 5): `git fetch origin main` (a failure, for example a lock held by a sibling worktree, consumes the try and backs off `0.15 s x try`); **resolve `origin/main` to a sha once** and use that sha for every later step (`ls-tree`, `show`, `read-tree`, `commit-tree -p`), because every terminal is a worktree of one clone and they share `refs/remotes/origin/main`, which a sibling can move at any moment; list the allowed paths at that sha; call `build(paths, read)`. A `string` result **refuses** with that text (nothing pushed); an empty list is a no-op success (`sha = nil`). Otherwise build a tree in a **private, uniquely named index file** (`<git-dir>/pickman-publish-<time>-<clock>-<random>`, removed on every exit path): `read-tree <sha>`, `hash-object -w --stdin` and `update-index --add --cacheinfo` per change, `write-tree`. If the tree equals the base tree the change is already there (no-op success). `commit-tree -p <sha>` with the message (a function message is evaluated after `build`, so it can name the allocated id). **Every git call's exit status is checked** and the result must be a hex object name of 40 or 64 digits; any failure returns `ok = false` with git's message and nothing is pushed. The push is `git push --force-with-lease=refs/heads/main:<sha> origin <new>:refs/heads/main`, so it succeeds only if origin's `main` is still that sha. A rejection starts the next try: `build` runs again against the **new** origin, so ids and claims are recomputed, never replayed. After the last try: `push rejected after N tries: <git's text>`.

**Pure rules** (`scripts/tracker/status.luau`, no requires):
```lua
status.canMove(from: string, to: string): boolean
status.carriedByPr(from: string, to: string): boolean
status.stamp(state: string, pick: (number) -> number): string          -- "<state>-<w1>-<w2>-<w3>" from a word list of 24
status.parse(value: string?): string?                                  -- the state, for "<state>" or "<state>-<w>-<w>-<w>"
status.phrase(value: string?): string?                                 -- "<w>-<w>-<w>" or nil
status.derive(state: string, design: string?, inRaft: boolean?): string  -- state is "backlog" | "active" | "done"
status.canClaim(from: string, to: string, stored: boolean, viaRaft: boolean): boolean  -- an existing draft raft is claimed by stamping preparing once; never a lone issue
status.effective(front: { [string]: string }, state: string): string
status.nextNumber(ids: { string }): number                             -- next multiple of 10 above the highest number in `ids`
```
`store.nextNumber` delegates to `status.nextNumber`; callers pass the union of local and `origin/main` ids.

**Commands** (`scripts/tracker/main.luau`; helpers `publishing()`, `mergeOrigin()`, `stamp()`, `frontOf`, `withFront`, `idsOf`, `docPath`; `store.setFront` is refactored onto `withFront`):
- **Publishing is on** when the repo has an `origin` and `PICKMAN_PUBLISH` is not `0`. Otherwise every command behaves exactly as before (local-only, no network): the mode of an offline laptop and of fixtures that test something else. A failed publish names `PICKMAN_PUBLISH=0` as the way to work locally.
- **Repo-root guard**: `tracker.sh` changes into the repository root before it starts Lune, so the working directory is the checkout the tracker belongs to. **Every command except the read-only ones** (`list`, `find`, `members`, `metrics`, `board`, `workstreams`, `promote-check` and the diagnostic `stamp`; not `prompt`, which can create a raft) first compares `git rev-parse --show-toplevel` with `pwd -P` and refuses when they differ (`refusing to run: git's repository root is ..., not ... (is .git missing here?)`), **whatever `PICKMAN_PUBLISH` says**. A fixture whose own `.git` is missing would otherwise fall through to the enclosing real repository and publish to its `origin`, or add a worktree to it; this happened to the real repository during prep (c0640 fences the spec runner from the other side). Read-only commands keep working in sandboxes on purpose (existing specs run them there), and a directory with no repository at all cannot fall through, so it is allowed. The c0510 fixtures also run git with `GIT_CEILING_DIRECTORIES=<checkout>/.cache`, so a fixture that loses its `.git` fails instead of using the real repository.
- `mergeOrigin()` is `git merge --no-edit origin/main`; if it conflicts it runs `git merge --abort` and says so (the tree is left as it was; resolve with `git merge origin/main`).
- **`new issue <f|d|c> <slug> [--desc "<line>"]`**: `--raft` is accepted only for an active raft (emergent issues); with a backlog raft it is refused (`--raft is only for emergent issues of an active raft`). Publishes the stub (`<ID>.md` with a stamped `status: new-…` and the description replacing the Problem comment, `check.sh` created at mode 100755) as one commit, allocating the id inside `build` from the **union** of the local tree and `origin/main` (step 10 as today). A lost race is retried with the next id; an id another terminal pushed is never overwritten. The commit message names the allocated id. Then `mergeOrigin()`, so the stub arrives as a tracked, clean file, **unless an active raft is on this branch** (a postponable issue filed from a raft worktree): then the stub is published but the branch is not touched, and it arrives with the final merge of `origin/main`. Emergent issues (`--raft` of an active raft, created in `active/`) belong to the raft's own PR and are **not** published.
- **`new raft`**: refuses unless the working tree is clean (it merges `origin/main` right after claiming). One commit, all-or-nothing. Each member must be on `origin/main`, must not name a raft (`already belongs to <R-id>`), must have effective status `new`, and must have the right type. It writes **only the status** (`preparing-…`, one stamp for the raft and all members): not `raft:`, which sits beside `depends_on:` where a capture PR may be editing. The raft number comes from the union of local and origin raft ids. After the push it merges `origin/main`, writes `raft: <R-id>` into each member locally and commits that (`tracker: <R-id> members`), so later merges of `origin/main` stay clean. Any failing member refuses the whole thing, naming it and its status. This is the **claim** on a set of issues.
- **`status`**: `status` lists every item that is not done as `<id> <status> <title>` from `origin/main` (after a fetch, so a stale checkout still sees the truth); `status <id>` prints that item's status; `status <id> <to>` moves it. A move is validated against the status **on `origin/main`**, not the local document, and **a move of a raft moves its members** in the same commit. **Which members**: for a published move, the raft's `issues:` list on `origin/main`; for the carried `preparing>prepared`, the list in the **local** raft document (the one the prep PR will land), and every member in it must be `preparing` on origin or the move is refused naming the member and `tracker.sh status <id> preparing` (so an issue added during prep is claimed first, and an issue dropped from the list is left alone; dropping one is followed by `status <id> new`). A published move pushes through `publish.commit` and then merges `origin/main`; the carried move edits the local documents only. `status <id> <to>` refuses to run in the main checkout; an unknown status, `done`, `active` (only `start` claims it: it checks the tree, the designs and the dependencies first) or a move that is not allowed is refused, naming the status found on origin. Giving a claim back (`status <R-id> prepared` from `active`) removes this worktree's `.cache/tracker-claim-<R-id>`. **The carried `prepared` refuses unless the raft and every member in the local list are `design: ready`** (the two fields move together; ticket-prep sets `design: ready`, then runs `status <R-id> prepared`, then makes the prep commit). **Ownership is documented, not checked** (the user's decision): any terminal can run a published give-back (`active>prepared`, `preparing>new`, `prepared>preparing`), and the skills say to use them only for your own claim. The publisher lists the tree with `--full-tree`, so it never depends on the current directory.
- **`start <R-id>`**: every local precondition first, so nothing is claimed that cannot be finished: clean tree, members `design: ready`, the refusal in the main checkout, and a branch `R<id>-<slug>` that does not already exist (unless it is the current branch). Then the claim: one commit that moves the raft and every member to `active-<stamp>`, each required to be `prepared` on `origin/main`; a refusal names the item and its status and moves, branches and pushes nothing. The stamp is saved in `.cache/tracker-claim-<R-id>` **before the push** (and restored or removed if the publish is refused): a **retry by the same terminal** (origin's value equals the saved stamp) skips the publish and continues, so a start that died right after its push can be finished, while a second terminal is refused. Then `mergeOrigin()` and the existing flow (`switch -c`, `git mv` to `active/`, commit, push, draft PR). If a step after the claim fails (branch push, `gh pr create`), local state is already consistent: finish by hand with `git push -u origin <branch>` and `gh pr create --draft`, or give the claim back with `tracker.sh status <R-id> prepared` (moves the raft and its members back in one commit).
- **`done`**: unchanged. A raft filed in `done/` is effectively `done` whatever its `status:` line says.
- **`sync [--fetch]`**: `git fetch origin main`; then, unless `--fetch`, a `merge origin/main` in a worktree or `pull --ff-only` in the main checkout; prints `synced to <short sha>`. **`--fetch` only updates `origin/main`** and is what reviewers and stream agents run, because a merge would add a commit, change HEAD past the sha a review announced, and put other items' files into the diff they judge.
- Usage text lists `status`, `sync [--fetch]` and `--desc`.

**CI** (`.github/workflows/check.yml`): `on.push` gains `paths-ignore: ['tracker/**']` so the many tiny state pushes do not each run the full gate on `main`. `pull_request` is untouched, so every PR (including the ones that carry tracker documents) still gates.

**Skills** (text, checked by AC6): `tracker.sh sync` appears without `--fetch` only in the working skills and `sync --fetch` only in review and metrics. The tracker skill gets a **Sync and claim** section (statuses, stamps, published versus carried, the direct-push exception and its whitelist, `PICKMAN_PUBLISH`, `sync`, recovery from a failed start) and corrected Conflicts and Landing text; make-issue, ticket-prep, make-prompt and execute-raft start with `scripts/tracker.sh sync`; **review and metrics use `scripts/tracker.sh sync --fetch`**, and the sequestration diff in **both** the review skill (Code mode, item 2) and execute-raft (Phase 3, step 3) becomes `git fetch origin main && git diff --find-renames=100% --name-status origin/main...HEAD -- 'tracker/**/check.sh' 'tracker/**/acceptance/**'`, which must list nothing except `R100` renames (the `start` move to `active/`). The three-dot form separates what this branch changed from what was merged in from `main`, so other terminals' new stubs are not false positives and an edit of another item's sequestered file is still caught.

With the prototype (code, skills, `check.yml` and both replacements) all other spec files pass; seven more promoted specs read skill text (c0030/pipeline, c0410/review-skill, format and ticket-prep, c0450/override-check, c0460/board-docs, c0480/start-depends), and the prototyped skill edits keep every pinned phrase.

**Overrides:** `tests/acceptance/c0041/worktree.spec.luau` and `tests/acceptance/c0140/workflow.spec.luau`, both rewritten in this issue (a chore changes promoted specs in its own raft; `replacements/`, AC8).

```
terminal A (worktree)                       origin/main                         terminal B
new issue  -- publish.commit -------------> stub (status: new-<words>)  <------ tracker.sh status
new raft   -- one commit: raft + members -> preparing-<words> (claim)   <------ new raft refused: preparing
(prep PR)  -- prepared is carried --------> merged by PR: prepared-<words>
start      -- one commit: active-<words> -> active (at backlog path)    <------ start refused: active
(raft PR)  -- merged: dir in done/ ------->  done
```

### Scalability
Each published change is one fetch plus one push of a few files, and a lost race or lock contention costs one more try (5 at most, with backoff, then a clear message); the trees involved are tens of small files. `status` reads a `git ls-tree` and one `git show` per item on `origin/main`: O(items), about 40 today, no worktree access. The tiny commits skip CI through `paths-ignore`. There is no central lock: the lease on `refs/heads/main` is the compare-and-set, against a sha pinned for the whole try.

### Maintainability
Two small, separately tested modules: `status.luau` is pure (about 70 lines with comments) and `publish.luau` is the only code that talks to the remote (about 190). `main.luau` gains command bodies that only call them. The whitelist and the create-only and frontmatter-only rules are one function and one loop in `publish.luau`, so widening what may be pushed is a visible change with a spec. The skills carry the rules in one section, which the other skills point to.

### Usability
One new reading command (`status`) answers "what is everyone doing"; `new` still prints the same path; a refused claim names the item and the status on `origin/main`. `PICKMAN_PUBLISH=0` is the offline escape hatch and is named in the error when a push fails. The numbering stays in steps of 10; renumbering (c0500) becomes rare because ids are reserved at creation. The stamp words are human readable, so a conflict in a `status:` line says who moved what.

## Unknowns & experiments
Run in prep (macOS, git 2.x, Lune 0.10.5):
- **E1** Can a commit built in a private index from a pinned `origin/main` sha be pushed from a dirty worktree on another branch without touching it? **Pass**: `publish :: pushes exactly the listed files ...` (dirty file, branch commit, HEAD, index and untracked state unchanged).
- **E2** Does a merge of `origin/main` into a worktree that holds the stub's later local edit avoid an add/add conflict? **Pass**: `commands :: a local edit of the stub merges ...`.
- **E3** Does an item that `start` published as `active` at its backlog path merge cleanly with the branch that moved it to `active/`? **Pass**: `commands :: a started raft goes back to prepared on origin, and the branch that already moved it merges cleanly` (rename plus a status edit on the old path). The final PR merge into a `main` that moved on is not run: the branch never edits `status:` after the claim, except the carried `prepared` before the claim.
- **E4** Does a lost race behave? **Pass**, two ways: a remote-detected race (a `pre-push` hook makes another clone push first: `publish :: a lost race ...`, `commands :: an id taken ...`), a **local** race (a sibling worktree of the same clone publishes while `build` runs and moves the shared `origin/main`: `publish :: a sibling worktree moving the shared origin/main ...`, which reproduced the overwrite round 1 found with a name-based prototype). A held lock on the shared tracking ref was tried and does **not** make `git fetch origin main` fail (git only warns), so retry-on-fetch-failure is untested defence in depth and its row is `reasoned`.
- **E5** Does `paths-ignore` on `push` keep PR gates? Documented GitHub behaviour (path filters apply per event); the PR trigger is not changed. Proven only in CI by the first tracker-only push after merge; if it ever gates a tracker push nothing breaks, it is only slower.
- **E6** Can git push to `main` directly? **Pass**: `gh api .../branches/main/protection` returns 404 "Branch not protected". If protection is added later, `new` and `start` fail with the push error and `PICKMAN_PUBLISH=0` restores the PR-only flow.
- **E7** Do the existing promoted specs survive? **Run on the base merged with `origin/main` at 01395fc (R0140 done)**, with the whole prototype applied (tracker code, the skill edits, the `check.yml` change and both replacements): `scripts/check.sh --full` gives 633 cases in 103 spec files, and `scripts/tracker.sh check c0510` gives all 8 criteria PASS. History: a first guard at every command broke `c0410/rounds` and `metrics-rounds` (read-only commands run in `.git`-less sandboxes on purpose) and then `tooling/migrate-odd` (a sandbox outside any repository, which cannot fall through), hence the read-only list and the no-repository allowance; without the c0041 replacement 8 c0041 cases fail, without the c0140 replacement 1 case fails.
- **E9** Is the incident real? **Observed**: during prep a spec's fixture lost its `.git` and ran `remote remove origin` and `worktree add` against the real repository (the repository is left with a stray worktree entry and missing upstream settings; not touched by this prep). `commands :: a tracker command in a directory that lost its .git refuses ...` reproduces the fall-through with an isolated outer repository.
- **E8** Can `git commit-tree` fail and be seen? **Pass**: `publish :: a git failure ...` (local `user.name` set empty).
