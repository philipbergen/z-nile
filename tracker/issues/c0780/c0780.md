# c0780: Capture lands without a pull request

## Problem
Capturing an issue (the make-issue skill) ends today with the full "Landing a change" procedure: push a branch, open a PR, wait for CI (`gate` and `beta`), merge, pull, and remove the worktree. A capture changes only tracker documents (the issue's Problem, Non-goals and Solution ideas), yet each one costs a PR and several minutes of CI, plus a Beta publish (PR #52 and #53 on 2026-10-03). The user, 2026-10-03: "I don't think PR is required, just run CI locally and push to main."

What should happen: a capture runs the gate locally (`scripts/check.sh --full`) in its capture worktree, then pushes its commit to `main` directly, retrying on a race, and removes the worktree. No PR, and no waiting for GitHub CI.

## Non-goals
- Prep (ticket-prep) PRs, raft PRs, and skill or doc edits keep landing by PR, unless the user widens this later.
- Changing CI itself.

## Solution
- make-issue step 6: commit, `scripts/tracker.sh sync`, `scripts/check.sh --full`, then `git push origin HEAD:main`. On a non-fast-forward, sync, re-run the gate and push again. Then remove the worktree.
- Tracker skill: "Landing a change" and "The direct-push exception" both name this exception. Decide whether a capture push is limited to tracker documents under `tracker/issues/<id>/`, which can be checked as publish does, or may touch anything a capture touches.
- Possibly a `tracker.sh land` (or `capture-push`) command that does the push and verifies the commit touches only that issue's documents, so the exception stays narrow and mechanical (the user wants tracker.sh to do the mechanics, and skills to drive).
- Check the promoted specs and done `check.sh` files that pin make-issue's step 6 wording ("Landing a change", PR) before changing it (the override check).
