# c0840: Jail signal rule, link probe and skill text from the round-6 review

## Problem
R0210's round-6 fixes and its post-`done` fix were merged without any review, because the user chose to land after round 6:
- writers renaming into place (`sh.writeReplacing`, `check.sh`'s `build_place` and globalTypes download, `deploy-beta`, the sentinel);
- the post-run unlink of top-level `.cache` symlinks and the outer-sandbox symlink probe;
- the watchdog in the runner's `REAPER` launcher;
- the escape-pattern change in `profile`;
- the gate spec spelling the `gh-none` path in two parts.

Every earlier round found new problems in the previous round's fixes, so these are likely to have some too.

**The review has been done** (2026-10-04, by a clean Opus subagent; the full text is in `review-of-round6-fixes.md` beside this document). Verdict: changes. This raft splits its findings by mechanism:
- **F1 [high]**, writers following a link to a directory, and the skippable unlink: **c0830**. F1's signal route stays here: the jail lets a spec signal the runner's own processes, which can skip the unlink.
- **F2 [medium]**, the watchdog's unchecked fork: **c0850**.
- **F3 [medium]**, the outer-sandbox link probe: **here**. It counts any `ln` failure as "refused", and its name is predictable, so a regular file left at that name makes a permissive sandbox pass.
- **F4 [low]**, the silent download failure: **c0830** (same lines).
- **F5 [low]**, the testing skill not describing the round-5 and round-6 mechanisms: **here**, extended to this raft's mechanisms.

The review found nothing wrong with the escape pattern, the sentinel write, `deploy-beta.luau`, the watchdog's stdio, ordering and exit codes, or the `gh-none` split. This raft's own code review is the re-review that c0840's title asked for.

## Non-goals
- The fixes c0830 and c0850 own.
- Requiring an outer sandbox to refuse signals too. An outer sandbox (Claude Code's own) allows them, and requiring it would refuse every run inside it. The unjailed case goes under "Caught only by review".

## Solution
- The jail refuses signals to anything outside it.
- The runner's liveness check counts such a refusal as "alive".
- The outer-sandbox link probe gets a random name and counts only `Operation not permitted` as a refusal.
- The testing skill describes every guard as it now is.

## Design
### Signal rule (`tests/lib/fence.luau`, `profile`)
Two rules are appended: `(deny signal (with no-log))` then `(allow signal (target same-sandbox))`, later rules winning as for the file rules. `with no-log` keeps the sweeper's ~100,000 refused probes per pass out of the system log (E4). A jailed process can signal, and probe with `kill -0`, only processes of its own sandbox: the specs and everything they start, wherever it moves. It can't signal the runner's top Lune, the launcher, the watchdog or any other process of the user (E1). c0820's sweeper depends on this rule.

### `fence.alive(pid: string): boolean` (exported; replaces the local `alive`)
True when `kill -0 <pid>` succeeds. Also true when it fails with `Operation not permitted` **while jailed** (`PICKMAN_TEST_JAIL == "sandbox-exec"`): the process exists outside the jail. Unjailed, a refusal means another user's or root's process, which can't hold this user's lock, so it reads as dead and a stale lock naming a reused pid can still be taken over (design review 001 F8). False for a malformed pid or `No such process`. Used by the lock code (`anyAlive`, `takeOverIfStale`) as today. Inside the jail the lock code only ever judges processes the spec started, but a refused probe must never read as dead.

### `fence.linkProbe(dir: string): (string, string)` (exported; used by `jail()`)
Tries to make a symlink at `<dir>/pickman-link-probe-<pid>-<8 random [a-z0-9]>`, pointing to `/nonexistent`. It returns:
- `"made"` if `ln -s` succeeded; the link is removed at once with `rm -f`.
- `"refused"` if it failed and its stderr contains `Operation not permitted`.
- `"error", <ln's stderr>` otherwise (the folder is missing, the name exists, and so on).

In `jail()`'s outer-sandbox branch:
- `"made"`, with nothing else writable: it adds `a symlink at the top of .cache` to the leaks, as today.
- `"refused"`: no leak.
- `"error"`: the run refuses, with `cannot probe the outer sandbox for links at the top of .cache: <stderr>`, exit 1, removing `runTemp` first like the other refusals.

### Testing skill (`.claude/skills/testing/SKILL.md`)
The "Specs never touch the real repository" section is brought up to date:
- **Jail (macOS) bullet**, which must state:
  - **Signals**: specs can signal only processes of their own sandbox.
  - **Symlinks at the top of `.cache`**: specs can't create them; the runner unlinks any found there before the run, after it (in the launcher too) and at the start of `scripts/check.sh`. A swap is still possible (c0830 E1).
  - **Writers**: each `.cache` line in `scripts/` is on the reviewed list in `tests/lib/cachepaths.luau`, with its reason. The writers listed there replace by rename (`scripts/lib/replace-file.pl`, or `fence.sh`'s inline rename for the sentinel). The list covers `scripts/` only: a write through a listed variable, or a write from the runner (`tests/lib`), is review's to catch (design review 001 F9).
  - **Watchdog**: it stops the specs if the launcher dies.
  - **Sweeper**: the jail's root sweeps every process of the sandbox after the specs end, and the run fails if the sweeper is killed. Its interlock watches the launcher, so an interrupted run (Ctrl-C) is still swept. A SIGKILL of the launcher itself skips the sweep and the unlink.
  - **pids**: the sweep covers pids up to macOS's 99999.
- **"Caught only by review"**:
  - Processes that leave the run's group survive **only where specs aren't jailed** (Linux, an outer sandbox).
  - Unjailed runs can signal the runner.
  - A pid above 99999 isn't swept.
  - The existing entries stay.

### Scalability
Two profile rules. `fence.alive` adds a string match on stderr. `linkProbe` is one `ln` at start-up, only in outer-sandbox runs.
### Maintainability
- `alive` and `linkProbe` become small exported functions, so a spec can pin their contracts without a sandbox.
- The skill text is the one place an agent learns what the guards do, and AC4 pins the facts it must carry.
### Usability
- A run inside an outer sandbox whose link probe fails for an unexpected reason says why, instead of passing or failing silently.
- The skill tells an agent exactly what is and isn't caught.

## Unknowns & experiments
- **E1 (run in prep)**: which SBPL rule confines signals?
  - `(deny signal)(allow signal (target same-sandbox))`: `kill -0` and TERM to an outside process were refused (the process lived); TERM to the jail's own child and to its grandchild in a group of its own were allowed.
  - `(deny signal (target others))`: allowed both outside signals (the outside process was killed) and refused the grandchild, so it's not usable.
- **E2 (run in prep)**: does any spec signal a process outside the jail? `grep` over `tests/` and the acceptance specs found `kill` only on pids the spec itself started (c0640's lock spec, `fence-leftovers.spec`, the runner's own lock code). The full gate in RC0 is the proof.
- **E3 (executor, Phase 1)**: does Lune's `process.exec("kill", {"-0", pid})` show `Operation not permitted` in stderr on macOS, for a process outside the jail? `kill` is a shell builtin in `sh`, but `/bin/kill` runs here; both print `Operation not permitted` on macOS (prep saw it from `bash`'s builtin). Method: the spec's first case. Fallback: `perl -e 'kill(0, $ARGV[0]) or exit($!{EPERM} ? 0 : 1)'`.
- **E4 (prototype and mutation check, run in prep)**: does the spec hold against a prototype?
  - Setup: the signal rules, `fence.alive`, `fence.linkProbe` and its use in `jail()`, prototyped in `.worktree/proto-r0260` (not landed).
  - Result: the spec passes 8/8 with its jailed cases running. `scripts/tracker.sh check c0840` passes AC1–AC3 there, and AC4 fails, as it must before the skill edit (`the testing skill does not mention same-sandbox`).
  - Mutants, each failing a case:
    - `alive` true only when the probe succeeds;
    - `alive` true on any failure;
    - the probe's predictable name;
    - any failure counted as a refusal;
    - no `rm` after `made`.
  - The two signal-rule rows rest on E1 (run directly with `sandbox-exec`).
- **E5 (run in prep, design review 001 F11)**: does a sweep pass flood the system log with refused signals?
  - Method: one pass of `kill 0` over 2..99999 under `sandbox-exec` with the rule, with and without `(with no-log)`, then `log show` over that minute, counting sandbox signal denials.
  - Result: zero lines either way, and also zero for a deliberate file-write denial, so `sandbox-exec` profiles evidently don't report denials to the unified log at all. Nothing to flood.
  - `(with no-log)` is adopted anyway, as cheap insurance: the run shows it still refuses (`Operation not permitted`).
