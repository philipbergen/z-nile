# c0860: Fixes to review findings are checked for their consequences

## Problem
When an executor answers a code review, nothing asks it to think one step past each fix. R0210 showed the cost: several later findings were consequences of the previous round's fixes, made quickly and never thought through:
- blocking all network access also blocked the loopback that local test servers use (review 002 F2);
- clearing a stale `.cache/.git` added an `rm -rf` that could follow a symlink into the shared `.git` (review 004 F1);
- reaping by an environment token assumed `ps -E`, which current macOS doesn't support (found by hand in round 5).

Ticket-prep already requires a consequence step before a design fix; execute-raft's answer-the-review step doesn't. And when two rounds found holes in the same mechanism (the jail's deny-list), nobody stopped to question the mechanism itself; it was patched hole by hole until it became an allowlist.

The user asked for these changes to execute-raft (2026-10-04), after asking whether reviews were told to do this kind of second-order thinking.

## Non-goals
- How many review rounds a raft gets: c0770 (R0250, "Up to five review rounds, prefer three") edits the same skills; prep orders the two.
- The reviewer's own Consequences field, which the review skill already requires.

## Solution
- execute-raft Phase 4: before each fix, the author writes its consequences into the refute line ("this changes X, which could break Y; checked by Z"), mirroring ticket-prep's consequence step.
- review skill, code mode: from round 2 on, a pass over the fix delta since the last round: for each fix, what new behaviour it adds, and what it breaks or opens.
- Both: when two rounds find holes in the same mechanism, question the mechanism (deny-list versus allowlist, patch versus redesign) before patching again.
- The executor runs the full gate (and reads the whole lint summary) before every review round, not only the touched issues' checks.
