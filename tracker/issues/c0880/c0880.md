# c0880: Tracker integrity audit

## Problem
One id in two lifecycle folders disables every tracker command, and nothing in the gate catches it. Re-filed from the parked tracker-hardening prep (its c0530, from the tracker system review's F1), whose ids now clash with `main`.

`store.find` throws `duplicate id …` when an id exists in, say, `tracker/issues/c0510` and `tracker/issues/done/c0510`. Every command that lists items goes through it: `list`, `members` (so every raft check.sh), `new`, `start`, `commit`, `promote-check` and `renumber`. Git reports no conflict, because the paths differ: an emergent issue is created in `issues/active/` and filed in `issues/done/`, while a capture on `main` creates the same number in `issues/`. No spec reads the real tracker, so CI on `main` stays green. Recovery is blocked too: `renumber` calls `store.get(old)`, which throws on the duplicate. Reproduced in the earlier prep: after `cp -R tracker/issues/c0510 tracker/issues/done/c0510`, `list` and `members` both exit 1.

## Non-goals
- Preventing the race itself: c0510 publishes stubs to `main`, and c0870 changes allocation.
- The rest of the parked tracker-hardening set (raft membership, design-ready gate, and so on), which stays parked.

## Solution
- A whole-tree audit that never stops at the first problem, run by the gate on the real tree (so every PR and every push to `main` checks it), and exposed as `tracker.sh audit`.
- `list` prints everything it can, then fails on a duplicate.
- `renumber` accepts an item directory, so one copy of a duplicated id can be renumbered.
- c0870's compaction runs the audit before and after it renumbers.
