# c0062: Gate slow c0053 commands

## Problem
Since R0020, `tests/acceptance/c0053/commands.spec.luau` has been the gate's slowest spec: 35.3 s under a load of about 14, and 27.8 s alone in prep on 2026-10-03, against 27.6 s for c0005. It drives many `tracker.sh` processes against one bare-origin fixture, and its 23 cases run serially in one file. `tests/run` parallelizes across files only, so this file is the gate's critical path. c0070 (this raft) adds a board refresh to every publish, which makes it slower still. The testing skill's Speed rule asks for the fix now.

## Non-goals
- Changing what any case asserts. The same 23 cases, with the same names and expectations.
- Speeding up the tracker CLI itself.
- Other slow specs (c0005, R0025's own new specs). If they dominate after this, file them.

## Solution
Split the spec into four or five files, `tests/acceptance/c0053/commands-<part>.spec.luau`, grouped by the state each case needs. Each file has its own fixture (`.cache/c0053-commands-<part>`) and its own setup case, which builds only the origin state its cases start from. `tests/run` then runs the parts concurrently. Shared helpers (fixture building, `tr`/`trOk`, `elsewhere`, `stub`, `setHook`) move to a new `tests/lib/trackerfix.luau`, so the parts don't duplicate 90 lines each.

## Design
- **Grouping, frozen** (review 004 F2): each group is the cases that share state. Names are abbreviated; AC1 holds the full list.
  1. `commands-new`: the original setup case "sets up a bare origin, a main checkout and a second terminal" (kept only here), "new issue publishes the stub…", "a local edit of the stub merges…", "ids are allocated above…", "an id taken by another terminal…" (the only user of `setHook`), "PICKMAN_PUBLISH=0 keeps a command local…" and "raft ids come from the union…" (these two share `offlineId`), and "stamps from processes started together differ…".
  2. `commands-claim`: "new raft claims its members…", "status lists what origin says…", "a status move refuses to run in the main checkout…", "a move to prepared is carried by the PR…" and "a move is checked against origin…". Its seed holds c-issues up to c0230, so `new issue` returns c0240 and c0250, as the cases assert.
  3. `commands-prep` (review 005 F3): "a published move abandons prep…", "a raft move follows the local member list…" and "new issue refuses --raft…" (these three share `zeta`/`rz`), and "an existing draft raft is claimed…". "a move to prepared" leaves `cap` dirty, so `new raft` can't follow it in one part. These four pass alone after a plain setup.
  4. `commands-start`: "a prepared raft starts once…" and "a start that dies after its claim…" (both name `.cache/tracker-claim-R0001`, which c0049 requires in one file), "a started raft goes back to prepared…", and "sync --fetch updates origin/main…", which runs in the `resume-r` worktree that the "dies" case creates. Its seed: R0001 (`issues: [c0240]`) and c0240 are both stamped `preparing` on origin, with designs `draft`. The case itself makes them ready and moves them to `prepared`, since origin accepts that move only from `preparing`.
  5. `commands-sync`: "sync brings a worktree and the main checkout up to date" and "a tracker command in a directory that lost its .git refuses…".

  Each part except `commands-new` starts with a case named `sets up the <part> fixture`, so the original 23 names stay unique (AC1). Its seed commit holds what earlier groups used to leave behind: for example, `commands-start` seeds a prepared raft R0001 with member c0240, design ready, as "new raft claims" and the carried move left it.
- **`tests/lib/trackerfix.luau`** (new), a thin layer over R0021's `@tests/lib/fixture`. Its git and `tracker.sh` calls go through `fixture.git`/`fixture.exec`. It has no fence and names nothing R0021's scan bans. Raw git only for `init` and `clone` to named paths.
  ```lua
  export type Fixture = { base: string, origin: string, main: string, other: string }
  function trackerfix.new(name: string, seed: { [string]: string }?): Fixture  -- seed: extra files for the first commit
  function trackerfix.tr(f: Fixture, cwd: string, args: { string }, env: { [string]: string }?): fixture.Result
  function trackerfix.trOk(f: Fixture, cwd: string, args: { string }): string
  function trackerfix.elsewhere(f: Fixture, files: { [string]: string }, message: string)
  function trackerfix.stub(id: string, title: string, status: string): string
  ```
  - The `name` gives `.cache/<name>`, unique per part (the c0049 rule: the library builds the path by concatenation, so only the parts' distinct names count).
  - Identities are `<name>@example.invalid`.
  - `setHook`, the only text naming `GIT_DIR`, `GIT_INDEX_FILE` and `GIT_WORK_TREE`, stays inside `commands-new.spec.luau`.
- **Two exceptions to the fixture rule** (review 005 F4), each with a comment giving its reason:
  - "a tracker command in a directory that lost its .git…" runs `tracker.sh` with raw `process.exec` in the `lost` directory, because having no fixture repository there is the point (`fixture.check` would refuse it). `outer` is still built with `fixture.git`, and nothing is written outside the part's `.cache` directory.
  - "stamps from processes started together differ…" starts its three `tracker.sh stamp` processes with `task.spawn`ed `fixture.exec` calls when E3 passes. Otherwise it keeps one commented `bash -c`, the only shell string in the parts.
- Every case keeps its exact `it("…")` name, so the union of names across the parts equals the original 23. AC1 checks this against the list frozen in `check.sh`.
- `tests/lib` changes force a full run (affected selection). That's fine.

### Scalability
The four parts run in parallel within the gate's job pool. The expected critical path is the slowest part, about 8–10 s, instead of 28 s.

### Maintainability
The shared fixture library removes copy-paste across the parts, and future tracker CLI specs can use it.

### Usability
A faster gate for every run.
