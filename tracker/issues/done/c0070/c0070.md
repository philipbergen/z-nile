# c0070: Board follows main

## Problem
The single-page board (`tracker.sh board`, written to `.cache/board.html`) is only as fresh as the last time someone ran it by hand, in whichever checkout they ran it. Tracker state moves on `origin/main` all the time: `new`, `status`, claims, and (after c0067/c0068) `ready` and `stop`, plus merged PRs. An open board tab then shows the past. The user wants every change pushed to `main` to update the board. The board in question is the local `.cache/board.html` of the **main checkout** (user's decision, 2026-10-03). CI's `tracker-board` artifact already rebuilds on every push and is unchanged.

## Non-goals
- Publishing the board anywhere (GitHub Pages and the like), and changing `board.yml`.
- Opening a browser. A refresh only rewrites the file, so an open tab needs a reload.
- Watching `origin` in the background. Only tracker commands, and the merge procedure through `tracker.sh sync`, refresh it.
- Pushes to raft branches (`tracker.sh commit`, `done`): they don't change `main`.

## Solution
A `refreshBoard()` step in `main.luau`. It runs after every tracker command that pushed a commit to `origin/main` and after `sync` in the main checkout. It fast-forwards the main checkout to `origin/main`, when that checkout is on `main` and can fast-forward, and rebuilds the main checkout's `.cache/board.html` with `-O`. Failures only warn: the command that published still succeeds. Landing a change, step 4, uses `<root>/scripts/tracker.sh sync` in place of `git -C <root> pull --ff-only`, so a merged PR refreshes the board too.

## Design

### `scripts/tracker/main.luau`

```lua
-- each problem is one `warning: board: …` line on stderr.

-- Every publish.commit call site goes through this: it fails like before on a refusal, and refreshes the board when a
-- commit was pushed (r.sha set). It returns r unchanged.

```
`refreshBoard()`:
1. `root = mainRoot()`.
2. If root's current branch (`git -C root branch --show-current`) is `main`, run `git -C root merge --ff-only --quiet origin/main`. `origin/main` is already fetched by publish. A merge, not a pull, so there's no second fetch. On failure (a dirty overlap, or diverged) print `warning: board: the main checkout was not updated (<git's first line>)` and go on. When root is not on `main`, warn `warning: board: the main checkout is on <branch>, not main; not updated` and go on.
3. After a successful fast-forward, run c0067's `sweepStale(root)`, so a raft that just left `active/` doesn't leave a duplicate id behind.
4. Run `bash {root}/scripts/tracker.sh board -O` (it `cd`s to `root`) and discard stdout. On failure, warn `warning: board: could not rebuild (<stderr first line>)`.

Callers:
- `published(r)` wraps `publish.commit` in `new issue`, `new raft` (both its pushes), `status` (published moves only; a carried move pushes nothing), the legacy `start` claim, `ready` and `stop`.
- In `ready` and `stop`, the refresh runs inside `published()`, right after the push and before the command's own pull. Its fast-forward and `sweepStale` do the work, and the command's own pull is then a no-op. The board doesn't read `prompt.md`, so writing the prompt afterwards changes nothing on it (review 003 F3).
- `cmd.sync`: in the main checkout, after the `pull --ff-only` and c0067's sweep, the board is rebuilt (step 4 only). In a worktree, `sync` doesn't touch the main checkout (no refresh): it merged into the worktree, not `main`.
- No refresh when `PICKMAN_PUBLISH=0` or there is no origin, since nothing reached `main`.

### Tracker skill
- **Landing a change, step 4**: `"<root>/scripts/tracker.sh" sync; git -C <root> worktree remove <path> && git -C <root> branch -D <branch>; git -C <root> worktree prune`.
- The sentence about the session's own directory: with launch-raft the session started in the main checkout and `cd`'d into the worktree, so removing the worktree removes the session's current directory. Every command after it must use `-C <root>` or absolute paths, and the final report is posted first.
- **The board row**: the main checkout's `.cache/board.html` is rebuilt after every tracker push to `origin/main` and every `sync` there. Reload the tab.
- Worktrees item 1: `scripts/tracker.sh sync` there also rebuilds the board.
- **execute-raft Phase 6** and any skill that tells you to `git pull --ff-only` the main checkout after a merge: use `<root>/scripts/tracker.sh sync`.

### Scalability
- About 0.1 s per refresh (c0067 E3: the board build takes 0.085 s), plus one fast-forward.
- Specs that publish many times (c0053's commands) each gain about 0.15 s per publish. The executor checks the gate's `slowest:` line, and if c0053's commands spec grows more than 20%, applies the fallback: build the board in-process, with `board.build` taking a root directory, instead of starting a second Lune process. That touches `scripts/tracker/board.luau`, not `tests/run.luau`, which the active R0021 is editing (review 001 F11).

### Maintainability
- One function. Every publish site reaches it through `published`, so a future publishing command can't forget it: the spec greps that `publish.commit(` appears only inside `published(…)` call expressions.

### Usability
- No new command.
- A broken refresh never blocks tracker work.

## Acceptance criteria

### Checked
- AC1: after any tracker command that pushes to `origin/main` (`new issue`, `new raft`, a published `status` move, `ready`, `stop`), the main checkout is at `origin/main` and its `.cache/board.html` equals a fresh `board -O` build of it. No opener is called.
- AC2: `tracker.sh sync` in the main checkout rebuilds the board after a push made elsewhere.
- AC3: a refresh that can't update the main checkout (not on `main`) only warns, and the command succeeds. With `PICKMAN_PUBLISH=0` the board is not touched.
- AC4: in `main.luau`, every `publish.commit(` call is wrapped by `published(`.
- AC5: Landing a change, step 4, in the tracker skill runs `scripts/tracker.sh sync` for the root, and no skill tells you to `git -C <root> pull --ff-only` after a merge.

### Judged
None.

### Observed
