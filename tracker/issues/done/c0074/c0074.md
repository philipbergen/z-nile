# c0074: Done runs the full gate after promotion

## Problem
`tracker.sh done` runs the raft's gate before promoting acceptance specs. After promotion it only type-checks `tests/`, and runs `tests/meta` and the promoted specs. Gate rules that read every spec file are skipped there: c0049's shared `.cache` literal check, R0021's repo-fence scan, and from this raft c0077's reviewed `.cache` list. So R0021's `done` passed while the gate on its final head failed: the promoted `tests/acceptance/c0049` file then named a path the scan banned. A one-line fix had to land after `done`, unreviewed.

## Non-goals
- Running the gate in `done` when it runs inside a spec run (a fixture). The fixture specs that drive `done` (c0001, c0008, c0034, c0038, c0045, c0050) clone the whole repo, `tests/` included. A full gate there would run those same specs, which run `done` in a new fixture, without end. Inside a spec run, `done` keeps today's promoted-spec checks, unless `PICKMAN_DONE_GATE=1` adds the gate. That's for a spec whose fixture stubs `scripts/check.sh`; this issue's own spec is the only one.
- Changing the raft's own `check.sh` run before promotion.

## Solution
`done` builds the final tree first: it promotes the specs and moves the raft and its members to `done/`, all uncommitted. Then, outside a spec run, it runs `scripts/check.sh --full` on that tree. If the gate fails, `git reset --hard HEAD` rolls everything back, exactly as a failed promotion does today. Only after the gate passes does `done` mark the PR ready and commit. Inside a spec run (`PICKMAN_FENCE_SPECS=1`, set by the runner's fence), it runs the promoted-spec checks instead and says so, unless `PICKMAN_DONE_GATE=1` asks for the gate anyway. That switch can only add the gate, never skip it or turn off a guard. The first design drove the outside branch in its spec by clearing `PICKMAN_FENCE_SPECS`, which would have dropped the spec-mode guards (no network, no credentials, the ref and push guards) for everything the fixture's `done` started (design review 001 F4).

## Design
`scripts/tracker/main.luau`, `cmd.done`, the new order:
1. Refuses as today: list mode, a raft that isn't active, an unclean tree, an unresolved review (c0080 adds its rule there), a failing raft `check.sh`.
2. Promotes the members' `acceptance/` folders to `tests/acceptance/<id>/` with `git mv`, collecting `promoted` (unchanged).
3. **Moves** every member, then the raft, to `done/` (`move`, a `git mv`). Formerly this happened after the ready call.
4. **Gate**, decided by `gate.doneGate(process.env)` (below):
   - `"promoted"`: it prints `done: inside a spec run, so the full gate is skipped; checking the promoted specs`. If `#promoted > 0` it runs `promotedChecks(promoted, true)`; on failure: `git reset -q --hard HEAD`, then fail `promoted acceptance specs fail in tests/acceptance (rolled back); fix and retry done` (today's message, which c0008 pins).
   - `"full"`: it prints `\n=== full gate on the done tree` and runs `sh.stream("bash", { "scripts/check.sh", "--full" })`; on failure: `git reset -q --hard HEAD`, then fail `the full gate fails on the done tree (rolled back); fix and retry done`.
5. Marks the PR ready (`gh pr ready`) when it has an upstream on GitHub, rolling back on failure as today.
6. Removes `FOCUS_FILE`, then `recordAndCommit(raft, "tracker: done <id>", …)`, then edits the PR body (unchanged).

`git reset --hard HEAD` undoes steps 2 and 3, since nothing was committed. Git removes the destination folders it empties, so no empty `done/<id>` is left beside the restored active folder. If one were left, `store.find` would report a duplicate id and every tracker command would fail. The spec checks both that no empty folder is left and that `tracker.sh list` works after the rollback. If git ever leaves one, the rollback removes the empty destination folders itself (`fs.removeDir` only when `fs.readDir` is empty). The `raft` variable is re-read after the moves (`move` returns the new item), and `recordAndCommit` writes `spend.md` into `done/<id>` as today.

### `scripts/tracker/gate.luau` (new, pure)
`gate.doneGate(env: { [string]: string? }): string` returns `"promoted"` when `env.PICKMAN_FENCE_SPECS == "1"` and `env.PICKMAN_DONE_GATE ~= "1"`, and `"full"` otherwise. `cmd.done` calls it with `process.env` and reads neither variable itself.

The branch an agent's real `done` takes (neither variable set) can't be driven from inside a spec run without dropping its guards, so the decision is a pure function, tested with plain tables. A `done` that ran the gate only with the switch passed every behaviour case (design review 002 F1).

`promote-check` (the dry run during prep) is unchanged: it still uses `promotedChecks(specs, false)`.

### Tracker skill (`.claude/skills/tracker/SKILL.md`)
The row or paragraph describing `done` states:
- the new order: promote, move to `done/`, full gate, mark ready, commit;
- that a failing gate rolls back by itself;
- that an interrupted gate (Ctrl-C) leaves the tree promoted and moved but uncommitted. Recover with `git reset --hard HEAD`, then re-run `done` (design review 001 F10).

### Scalability
The full gate takes a few minutes and now runs twice per `done`: in the raft's RC0 before promotion, and here after it. That's accepted: once per raft, and it is the bug.
### Maintainability
- One more step in a linear function, with the same rollback as its neighbours.
- The decision lives in one pure function of two variables (`doneGate`), with a message saying what was skipped.
### Usability
- `done` fails with a rolled-back tree and a message naming the gate, instead of finishing a PR whose final head is red.
- Inside a spec run it says what it skipped.

## Unknowns & experiments
- **E1 (reasoned)**: do `done`'s fixture specs all run inside a spec run, so they keep today's path? Yes. They run through `tests/run`, whose fence sets `PICKMAN_FENCE_SPECS=1`, and it reaches the `tracker.sh done` they start (environment inheritance, c0058's "the guards reach everything the run starts"). None of them overrides that variable: `grep` finds `PICKMAN_FENCE_SPECS` only in `scripts/lib/fence.sh` and `repo-fence.spec`'s banned names.
- **E2 (reasoned)**: does c0008's "rolls back and stays active when gh cannot mark the PR ready" still hold now that the moves come before the ready call? Yes. The ready failure still runs `git reset -q --hard HEAD`, which also undoes the moves; the spec asserts the active folders exist afterwards.
- **E3 (executor, Phase 1)**: does a nested `done` in c0008's fixture still finish within the runner's case time with the moves reordered? It does no extra work, only a reordering. The c0008 spec in the full gate shows it.
- **E4 (prototype and mutation check, run in prep)**: does the design hold up in a prototype?
  - Setup: the reordered `cmd.done` in `.worktree/proto-r0260` (not landed).
  - Result: the spec passes 5/5. The six `done` fixture specs pass (53 cases), and `scripts/tracker.sh check c0074` passes 4/4.
  - Mutants, each failing a case:
    - no `--full`;
    - no reset on failure;
    - the gate's result ignored;
    - the gate run even when nested;
    - the moves after the gate;
    - a rollback by `git checkout -- .`.
- **E5 (run in prep, after design review 001 F4)**: does the add-only switch work?
  - With `PICKMAN_DONE_GATE`, the spec passes 5/5 with `PICKMAN_FENCE_SPECS` left in place, and the spec no longer names it.
  - The mutant that reads the switch as "skip the gate" fails AC1 and AC2.
- **E6 (run in prep, after design review 002 F1)**: does the pure decision close the gap?
  - With `doneGate`, the spec passes 6/6.
  - Two mutants that left every earlier case green now fail AC6: the gate only with the switch (inside `doneGate`), and `cmd.done` bypassing `doneGate`.

## Acceptance criteria

### Checked
- AC1: with the gate in force (outside a spec run, or with `PICKMAN_DONE_GATE=1`), `done` runs `scripts/check.sh --full` once, on a tree where the specs are promoted and the raft and its members are in `done/`, and then commits `tracker: done <id>`.
- AC2: when that gate fails, `done` exits non-zero naming the full gate, and leaves HEAD, a clean tree, the raft active and nothing promoted.
- AC3: inside a spec run (`PICKMAN_FENCE_SPECS=1`) without `PICKMAN_DONE_GATE=1`, `done` doesn't run the gate, says it skipped it, and still checks the promoted specs. With the switch, it runs the gate (AC1, AC2 drive it that way, every guard in place).
- AC4: `done`'s promoted fixture specs (c0001, c0008, c0034, c0038, c0045, c0050) pass.
- AC5: the tracker skill's `done` row states the order (promote, move, full gate, ready, commit) and how to recover from an interrupted gate (`git reset --hard HEAD`, then `done` again).
- AC6: `gate.doneGate` returns `full` for no variables, for the switch alone, and for both; `promoted` only for a spec run without the switch. `cmd.done` decides through `doneGate(process.env)` and reads `PICKMAN_DONE_GATE` nowhere else.
