# c0460: Publish tracker board as an Actions artifact

## Problem
The tracker board (`scripts/tracker.sh board`) only exists as local HTML in the gitignored `.cache/`, so it is stale unless someone regenerates it. It should be rebuilt automatically whenever `main` changes (a merged PR is a push to `main`) and be fetchable without a checkout of the build tooling.

Decision (user, 2026-09-30): the repo is private and GitHub Pages from a private repo needs a paid plan and is public by default, while the board shows the whole backlog and spend. So the board is published as a **workflow artifact**, not to Pages.

## Non-goals
- GitHub Pages, or any publicly reachable copy of the board.
- Committing the generated HTML to the repo.
- Building on pull requests or drafts; only `main` (and manual dispatch).
- Changing the board's content or layout.
- Making `check.yml` or the full gate faster.

## Solution
A workflow `.github/workflows/board.yml`: on push to `main` and `workflow_dispatch`, check out, run `scripts/setup.sh --tools` (the tools-only mode that R0080 / c0140 added to `main`: toolchain only, the full gate stays `check.yml`'s job), run `scripts/tracker.sh board --out dist/board.html`, and upload it with `actions/upload-artifact@v4` as `tracker-board`. The tracker skill says how to download the latest artifact.

**Re-prep, 2026-09-30 (user decision):** the first design added a `PICKMAN_SKIP_GATE` variable to `setup.sh`. Meanwhile R0080 landed `setup.sh --tools`, which does the same job and whose promoted spec (`c0140/tools.spec`) contradicts c0460's old `setup.sh` rules. The user chose to re-prep c0460 on `--tools`: no change to `setup.sh` or `SETUP.md` remains in this issue.
## Design
**Workflow** (`.github/workflows/board.yml`), exactly:
```yaml
name: board
on:
  push:
    branches: [main]
  workflow_dispatch: {}
permissions:
  contents: read
concurrency:
  group: board-${{ github.ref }}
  cancel-in-progress: true
jobs:
  board:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: scripts/setup.sh --tools
        env:
          GH_TOKEN: ${{ github.token }}
      - run: scripts/tracker.sh board --out dist/board.html
      - uses: actions/upload-artifact@v4
        with:
          name: tracker-board
          path: dist/board.html
          retention-days: 30
          if-no-files-found: error
```
- Read-only token: an artifact upload needs no `actions: write`. No `pages`, `id-token`, or secrets.
- **Main only.** `workflow_dispatch` can be started on any ref, so the job has `if: github.ref == 'refs/heads/main'`: a dispatch on a branch is skipped and can't upload a branch's board that `gh run download` (which takes the newest artifact in the repo) would then hand out as "the" board.
- **Concurrency.** The group is per ref (`board-${{ github.ref }}`), because a workflow-level group is entered even when the job's `if` skips it, so a global group would let a branch dispatch cancel the `main` build. `cancel-in-progress: true` is safe: a newer push supersedes an unfinished build and the newest run always completes. Consequence: two quick merges cancel the first merge commit's run, so OC1 accepts the latest `main` run.
- **No step conditions, no `continue-on-error`**, and the `GH_TOKEN` env on the setup step stays (setup.sh dies on CI without it: "CI: GH_TOKEN missing or invalid"). The spec pins each of these.
- No `fetch-depth`: the board reads only `tracker/` (E2).

**`scripts/setup.sh`** is not changed: `--tools` is main's (c0140). That mode is the only thing standing between `check.yml`'s gate job and a green run without a gate, and main's promoted `tests/acceptance/c0140/tools.spec.luau` only reads its text (an `exit 0` before the gate), so an extra skip condition such as `|| [[ -n ${CI:-} ]]` would pass it (design review 005 F4). This issue adds `setup-tools.spec.luau`, which cuts the argument check and the gate stage out of `setup.sh` and runs them under `set -euo pipefail` against a stub gate: no argument runs `scripts/check.sh --full`; `--tools` skips it and says so; `CI`, `GITHUB_ACTIONS` and `PICKMAN_SKIP_GATE` set don't skip it; a failing gate fails the run; an unknown argument exits 2; the gate is called once, no line outside the stage changes shell options (the only `set` line allowed is `set -euo pipefail`; the spec supplies that line itself when it runs a slice, so it does not detect its deletion), no line starts a `trap`, and `exit` appears only in `die()`, the argument check and the `--tools` branch (by text). **Known residual, found by code review 003 and deferred to c0530:** the spec runs only the argument check and the lines from the `--tools` test to the gate call, so a bypass outside those lines still passes (the whole stage wrapped in a `CI` test, `[[ -n ${CI:-} ]] && exec true` before it, `exit 256`, deleting `set -euo pipefail`, an indented `set +e`). AC3 reruns both specs. The workflow's own setup step is pinned to `scripts/setup.sh --tools` with only `GH_TOKEN` in its env.

**Docs**: the tracker skill's `board` row names `.github/workflows/board.yml`, the `tracker-board` artifact and `rm -rf .cache/board-ci && gh run download -n tracker-board -D .cache/board-ci`: a fresh directory, because `.cache/board.html` is the local command's default output and `gh run download` won't overwrite an existing file (from gh's source, not run here: E6).

**Retrieval**: the artifact is a zip held by the run; anyone with read access to the repo downloads it from the Actions run page or with `gh run download`. Retention is 30 days (`retention-days`), and every push to `main` makes a fresh one, so the newest is always the current board.

### Scalability
One build per push to `main` (about the time of `setup.sh --tools`: tool downloads, no tests, no gate). Output is one ~0.6 MB file and grows with the number of tracker items. Private-repo Actions minutes are the only cost; `concurrency` bounds parallel runs to one per ref, and only `main` builds.

### Maintainability
Reuses `setup.sh --tools` (one bootstrap for local, CI, the beta job and this job) and the existing `tracker.sh board` command, so a toolchain bump needs no edit here. Swapping the destination later (Pages, a release) changes only the last step.

### Usability
Developer-facing: the latest board is one `gh run download` away; failures show as a red run on `main`. The acceptance spec pins the workflow's structure, because Actions can't run locally.
