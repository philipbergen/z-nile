# f0300: Game flow

## Problem
f0170 gives Logic a game state machine (ready, playing, dying, level clear, game over), but nothing covers how a player moves through it in Roblox:
- when a game starts after the player joins;
- what the player sees while dying, on level clear, and at game over;
- how they play again without rejoining.
Right now a finished game would leave the player frozen in the maze with no way forward.

## Non-goals
- Hiscore submission and the board (f0240, f0250). A lobby, menus beyond start/play-again, matchmaking. Mobile-specific layout (f0280).

## Solution
- The phases and their timers are already in every frame (`play.phase`, `play.timer`, from R0090). A pure `Flow` feature turns them into an overlay that `src/client/FlowView.luau` draws:
  - **ready**: "READY!" over "LEVEL n";
  - **dying**: a dark fade that deepens through the pause;
  - **level clear**: the walls flash;
  - **game over**: "GAME OVER" with the final score and level, plus a **Play again** prompt.
- Playing again is a new `PlayAgain` RemoteEvent. The client sends it with no arguments, from the button or Enter. The server relays it to `Session.playAgain` for the sender's own session, and Logic decides (only in `gameover`). The new run is visible in the very next frame.
- The mouse is free while the prompt is up, so the button can be clicked, and locked again otherwise.

## Design

### Decisions made in prep (author's choices; the user may veto)
- **Joining** needs nothing new. The server starts a session on the client's `Ready` (R0040), and the run opens with the classic 2 s `ready` pause (`Game.CLASSIC_CONFIG`; 4 s real at half speed). The overlay shows "READY!" there, as it does after each death and level. No numeric countdown: the arcade shows only "READY!".
- **Dying** gets a black fade, `FADE_MAX · (dyingTicks − timer) / dyingTicks` with `FADE_MAX = 0.6`. It runs from nothing at the moment of death to 0.6 at the end of the pause, so the maze is still visible behind it. It holds at 0.6 at game over and cuts to 0 at the respawn's ready, which is a teleport anyway. This is the draft's "brief camera effect"; the camera itself isn't moved, which keeps `Camera` (pinned by `f0520/adapters.spec`) almost untouched.
- **Level clear**: the walls are lit white when `(timer // 6) % 2 == 1`. Over the classic 60-tick pause that is five 6-tick flashes (0.4 s each in real time), and the last frames before the next level are unlit. The pellets come back with the next level's frame (f0290).
- **Game over**: "GAME OVER" over `SCORE <score>   LEVEL <level>` (three spaces), with a fade of 0.6 and a **PLAY AGAIN (Enter)** button. The keys are `Return` and `KeypadEnter`. Space is taken by snap-look, and `f0130/keys.spec` pins the movement key map to exactly nine keys, so the play-again keys live in `Flow`, not in `View.KEYS`.
- **The cursor**: the camera locks the mouse every render step. While the prompt is up, `Camera.setCursor(true)` makes it `MouseBehavior.Default` with the icon shown; otherwise it stays `LockCenter` with the icon hidden. Without this the button can't be clicked with a mouse.
- **The rules on the client**: `Flow.overlay` needs the dying pause length. The client passes `Session.GAME_CONFIG.play`, the same table the server's sessions use (`f0170/adapter.spec` pins the server to `Session.GAME_CONFIG`), so the two can't disagree.
- **No hiscore entry and no menu**: f0240/f0250 and non-goals.

### `Flow` (`src/shared/Logic/Flow/init.luau`, new feature)
```lua
export type Overlay = {
	banner: string?,     -- "READY!" (ready) | "GAME OVER" (gameover) | nil
	detail: string?,     -- "LEVEL n" under READY!; "SCORE s   LEVEL n" under GAME OVER
	fade: number,        -- 0..FADE_MAX
	flash: boolean,      -- walls lit (levelclear only)
	playAgain: boolean,  -- the prompt is shown and live (gameover only); also frees the cursor
}
Flow.FADE_MAX = 0.6
Flow.FLASH_TICKS = 6
Flow.PLAY_AGAIN_KEYS = { "Return", "KeypadEnter" }  -- frozen
function Flow.overlay(play: Session.PlayFrame, rules: Game.Config): Overlay  -- pure, fresh table
function Flow.isPlayAgainKey(keyName: string): boolean
```
| phase | banner | detail | fade | flash | playAgain |
|---|---|---|---|---|---|
| ready | READY! | LEVEL n | 0 | false | false |
| playing | – | – | 0 | false | false |
| dying | – | – | `FADE_MAX·(D−timer)/D`, clamped; `FADE_MAX` when D = 0 | false | false |
| levelclear | – | – | 0 | `(timer // 6) % 2 == 1` | false |
| gameover | GAME OVER | SCORE s   LEVEL n | `FADE_MAX` | false | true |

New feature and new edges **`Flow -> Game`** (for `Config`) and **`Flow -> Session`** (for `PlayFrame`), added to `tracker/architecture.md` in prep. `tests/meta` needs `tests/unit/Flow/`. **Logic word rule**: Flow's source must not contain the lowercase word `game` (so no "game over" in comments; `GAME OVER` and `Game.` are fine), nor `Enum`. Key names are plain strings.

### Server (`src/server/Sessions.luau`, `default.project.json`)
- `default.project.json`: `ReplicatedStorage.Remotes.PlayAgain` is a `RemoteEvent`.
- `Sessions.start`:
  ```lua
  local playAgain = remotes:WaitForChild("PlayAgain") :: RemoteEvent
  playAgain.OnServerEvent:Connect(function(player: Player)
      local s = sessions[player]
      if s then
          Session.playAgain(s, tostring(player.UserId))
      end
  end)
  ```
  The handler takes **exactly one parameter**, the sending `Player`, and uses it both to look up the session and for the id. It ignores anything the client sends, checks no phase (Logic refuses outside `gameover` and returns `false`), and never starts a session (only `Ready` does).
- `tests/runtime/structure.luau` also asserts `Remotes.PlayAgain` on the Beta server.

### Client
- `src/client/FlowView.luau` (new):
  - `FlowView.start()` builds a ScreenGui "Flow" (`IgnoreGuiInset`) with a full-screen black `Fade` frame, a `Banner` and `Detail` label and a `PlayAgain` TextButton at least 44 px tall. It binds `Flow.PLAY_AGAIN_KEYS` with ContextActionService.
  - The button's `Activated` and the keys call `PlayAgain:FireServer()` (no arguments), and only while the latest overlay's `playAgain` is true.
  - `FlowView.show(o: Flow.Overlay)` sets `Fade.BackgroundTransparency = 1 − o.fade`, the banner and detail texts and visibility, and the button's visibility.
- `src/client/MazeView.luau`: `MazeView.flash(model: Model, lit: boolean)` colours the `Wall` parts white or their normal blue.
- `src/client/Camera.luau`: `Camera.setCursor(free: boolean)`. The render step's lock line becomes conditional: `MouseBehavior = if cursor then Default else LockCenter`, and `MouseIconEnabled = cursor`. No unconditional `MouseBehavior = Enum.MouseBehavior.LockCenter` or `MouseIconEnabled = false` may remain, because the render step would undo `setCursor` every frame (design review F1). The `View.interpolate(prev, snap, View.alpha(os.clock() - arrived))` call and the absence of `TICK_RATE` stay exactly as they are (`f0520/adapters.spec`).
- `src/client/Main.client.luau`, per frame:
  ```lua
  local overlay = Flow.overlay(frame.play, RULES)   -- RULES = Session.GAME_CONFIG.play (cast to Game.Config)
  FlowView.show(overlay)
  if model and overlay.flash ~= lit then lit = overlay.flash; MazeView.flash(model, overlay.flash) end
  Camera.setCursor(overlay.playAgain)
  ```
  Plus `FlowView.start()` at boot.
- **Boot order and frame order** (design review F6): every `start()` (Camera, Controls, PelletView, HudView, FlowView) runs **before** `ready:FireServer()`, so the first frame never meets an unbuilt view. Per frame the order is `Camera.push`, `HudView.show`, the overlay lines, then `PelletView.show` last, so a strict-decode error can't stop the HUD or the overlay. When the maze is rebuilt, `lit` is reset to `false`, because the new walls are built unlit.

### Server authority
The client sends only an intent with no payload. The server picks the session from the sending `Player`, and `Game.playAgain` accepts it only in `gameover`. A spammed request is a cheap no-op (one phase check), so it needs no rate limit. A client can't skip a pause, revive or keep a score, because every phase and timer is the server's.

### Scalability
- **Per frame**: one `Flow.overlay`, O(1), a handful of GUI property writes, and wall recolouring only on a flash edge (about 10 times a level clear; O(wall parts), around 200 on the classic maze).
- **Network**: no new replication. `PlayAgain` is one event per game over.

### Maintainability
- A new phase (raft d's ghost-eaten pause, an intermission) adds a row to `Flow.overlay` and an `Overlay` field if it needs one. The adapters only draw fields.
- Timings come from `Game.Config` and two named constants.

### Usability
- **Player**:
  - the classic READY! pause tells them when control starts;
  - the fade makes a death unmistakable without leaving the first-person view;
  - the flash marks a clear;
  - game over shows the result and how to continue, with no rejoin. Enter or a click starts again at once.
- **Developer**: `Flow.overlay` is one pure function with a table of outcomes. The client's wiring is four calls in `Main`.

## Acceptance criteria

### Checked
- **AC1**: `Flow.overlay(play, rules)` follows the phase table:
  - READY! with `LEVEL n` in ready;
  - nothing in play;
  - in dying, a fade rising strictly from 0 to `FADE_MAX` 0.6 over the rules' dying pause (0.4 at a third left; 0.3 halfway through a 10-tick pause; full when there is no pause);
  - in level clear, walls lit when `(timer // 6) % 2 == 1`, five 6-tick flashes over 60 ticks, and in no other phase;
  - in gameover, GAME OVER with `SCORE s   LEVEL n`, a fade of 0.6 and the prompt, which is live in no other phase.
  
  The input is left unchanged. `Flow.isPlayAgainKey` accepts exactly `Return` and `KeypadEnter`, and neither is a movement key.
- **AC2**: The place has `Remotes.PlayAgain` (a RemoteEvent) beside Ready, Intent and Snapshot. `Sessions` listens to it with a handler whose only parameter is the sending player, which it uses for both the session lookup and `Session.playAgain(<session>, tostring(<player>.UserId))` (called exactly once), never reads the phase, and the Beta runtime structure check asserts the remote.
- **AC3**: The client's `Main`:
  - requires `FlowView` and the `Flow` feature;
  - computes `Flow.overlay(<frame>.play, …)` with `Session.GAME_CONFIG`;
  - hands the overlay to `FlowView.show`, `MazeView.flash(…, <overlay>.flash)` and `Camera.setCursor(<overlay>.playAgain)`.
  
  `MazeView.flash` and `Camera.setCursor` exist. Camera's lock line is `MouseBehavior = if <flag> then Default else LockCenter` with `MouseIconEnabled = <flag>` (never `not`), and no unconditional `LockCenter` or `MouseIconEnabled = false` is left. Every adapter's `start()` comes before `ready:FireServer()`. `FlowView` fires `PlayAgain` with no arguments on `Flow.PLAY_AGAIN_KEYS`.
- **AC4**: A whole run as the client presents it, from the frames of a real `Session`:
  1. READY!, LEVEL 1 and a fresh HUD with every pellet;
  2. the banner gone in play, and score 10 with the eaten pellet gone;
  3. the level clear (score 70, no pellets) with 6 lit frames;
  4. READY! LEVEL 2 with every pellet back and the score kept;
  5. three deaths, each fading in with the lives counting down;
  6. GAME OVER (`SCORE 70   LEVEL 2`, fade 0.6, prompt up and staying up);
  7. after `Session.playAgain`, READY! LEVEL 1, score 0, 3 lives, every pellet, no fade and no prompt.
  
  A play-again outside game over changes nothing on screen.
- **AC5**: `src/shared/Logic/Flow/init.luau` and at least one `tests/unit/Flow/*.spec.luau` exist, and `tests/meta/architecture.spec.luau` passes: `Flow` is a declared feature with unit specs, its edges are declared and acyclic, and Logic stays engine-free.
