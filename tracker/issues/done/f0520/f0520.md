# f0520: Slow the game by 50%

## Problem
The game is too fast: level 1 runs at 7.5 tiles/s with a 0.8 s turn buffer, which is hard to play in first person. The user wants **everything in game time slowed by 50%** (2026-10-01): movement, the turn buffer and, as they arrive, the ready/dying/clear pauses, the eating pause and the frightened time all take twice as long in real time.

## Non-goals
- Changing any Logic rule or any tick-pinned spec, including R0090's prepped specs (speeds in units per tick, pauses in ticks): they stay as designed.
- Per-level speed tables (R0090) and ghost speeds (raft d): they scale with the clock automatically.
- Visual smoothing times (`View.TURN_SECONDS`, 0.12 s per quarter turn) and mouse look stay in real time: **the author's choice, recorded in game-design for the user to veto** (design review F3). A key press now waits up to one step, about 67 ms instead of 33 ms.

## Solution
Slow the **clock**, not the rules. `Session.TICK_RATE = 30` stays "ticks per second of play": every rule counts ticks. Two new constants, `Session.GAME_SPEED = 0.5` and `Session.STEP_RATE = TICK_RATE × GAME_SPEED = 15`, give the number of steps the server takes per real second. The server's clock is created at the step rate, and the client's blend between snapshots comes from a small Logic function, `View.alpha(elapsed)`, so the arithmetic is tested with real values (design review F1). Nothing else changes.

## Design

### Decisions made in prep
- **User decisions (2026-10-01)**: slow everything in game time by 50%; land it now as its own small raft, on the current Movement default (so R0090 keeps its tick-based specs and is not re-prepped).
- **Half speed means 15 steps per real second**, not halved units: speeds stay 30 units/tick (7.5 tiles per *game* second, 3.75 per real second), the turn buffer stays 24 ticks (1.6 s), and R0090's pauses (60/45/60 ticks), the eating pause and the frightened ticks all double in real time with no change.
- **`newClock()`'s default stays `TICK_RATE`** (30), so the promoted clock specs (f0120) and any caller that doesn't say otherwise are unchanged. Only the adapters ask for the step rate.
- **Not a tick-rate change**: halving `TICK_RATE` would change the units of every tick-pinned spec and every pause.
- **Smoothness**: at 15 steps per second the client still renders every frame by interpolating between snapshots over 1/15 s (`View.interpolate`'s fraction); the server sends one snapshot per step (15/s, half the bandwidth).

### `src/shared/Logic/Session/init.luau`
```lua
Session.TICK_RATE = 30                                        -- ticks per second of play (unchanged)
Session.GAME_SPEED = 0.5                                      -- play runs at half speed in real time
Session.STEP_RATE = Session.TICK_RATE * Session.GAME_SPEED    -- 15: steps per real second
```
The comments must not contain the lowercase word `game` (the architecture meta rule bans it in Logic).

### `src/shared/Logic/View/init.luau`
```lua
function View.alpha(elapsed: number): number   -- real seconds since the latest snapshot arrived -> blend fraction
	return elapsed * Session.STEP_RATE          -- (View -> Session is already a declared dependency)
end
```
`View.interpolate` already clamps its `alpha` to 0..1.

### Adapters
- `src/server/Sessions.luau`: `Session.newClock(Session.STEP_RATE)` (was `Session.newClock()`).
- `src/client/Camera.luau`: `View.interpolate(prev, snap, View.alpha(os.clock() - arrived))` (was `(os.clock() - arrived) * Session.TICK_RATE`). The multiplication is no longer in the adapter, so nothing in it can be the wrong operator.

### `tracker/game-design.md` (design review F2)
- A convention line under *Movement model*: "**All durations and speeds in this document are game time** (30 ticks per game second); the game is played at half speed, so real time is twice as long."
- A *Game speed* bullet: the user's decision, the numbers (3.75 tiles/s at level 1, the turn buffer 1.6 s, 30 ticks per game second, 15 steps per real second), that slowing the clock leaves every tick-pinned rule and spec untouched, and that `View.TURN_SECONDS` and mouse look stay in real time (the author's choice, the user may veto; a key press waits up to 67 ms instead of 33 ms).
- The lines that stated real-time numbers now say game time: level 1 "7.5 tiles/s of game time (3.75 in real time)", the buffer "0.8 s of game time ... 1.6 s in real time", the tick rate "30 ticks per game second", and the run pauses "game time ... double in real time".

### Scalability
Half as many steps and snapshots per second per player (15/s instead of 30/s): server CPU and replication halve.

### Maintainability
One constant, `GAME_SPEED`, retunes the pace later (a difficulty setting, a speed-up per level) without touching any rule or spec. Rules stay in ticks.

### Usability
Level 1 becomes 3.75 tiles/s and the turn buffer 1.6 s, easier to play in first person; the camera still interpolates smoothly between 15 Hz snapshots.

- **E2 (run in prep: PASS)**: mutation check, 17 mutants (speed 1 or 0.25, `STEP_RATE` ignoring the speed, the server clock on the default or the tick rate, the client blending with the tick rate or by dividing, `View.alpha` dividing or using the tick rate, a mention only in a comment on the server, the tick rate halved, `newClock`'s default moved, the docs losing 3.75, a bare 7.5 tiles/s, the convention line or the veto note removed, the turn buffer halved): all killed by assertions.
- **Residual (Observed, OC1)**: how 15 Hz snapshots feel in Studio (smoothness) and how key presses respond.

## Acceptance criteria

### Checked
- **AC1**: `Session` has `TICK_RATE = 30`, `GAME_SPEED = 0.5` and `STEP_RATE = 15`; a clock at the step rate yields 15 steps per real second at 30, 50, 60 and 144 fps; `newClock()` still defaults to 30; `View.alpha` is elapsed times the step rate (1/30 s gives 0.5, 1/15 s gives 1); the level-1 player covers 3.75 tiles in one real second (15 in four); and the turn buffer is 1.6 real seconds.
- **AC2**: The server creates its only clock with `Session.STEP_RATE` and the client's only `View.interpolate` call blends with exactly `View.alpha(os.clock() - arrived)`; neither adapter mentions the tick rate (comments stripped).
- **AC3**: `tracker/game-design.md` records the half speed (3.75 tiles/s, 30 ticks per game second, 15 steps per real second, `STEP_RATE`), says its durations and speeds are game time with no bare real-time number left, and records the real-time choices (`TURN_SECONDS`, mouse look, 67 ms) for the user to veto.
