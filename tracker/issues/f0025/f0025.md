# f0025: Hiscore submit

## Problem
At game over, the server has to submit the player's final score and level from its own simulation, never from the client. The boards update without double submissions.

## Non-goals
- UI (f0026). The rank remote's listener is registered by f0026's `Ranks` module. This issue calls `HiscoreStore.submit` and does not `FireClient` a rank.
- A client-supplied run id or score.

## Solution
`Sessions` watches the events from `Session.step`. On `GameOver` it calls `HiscoreStore.submit` once per run. The run id and the disconnect window are pure functions on `Hiscores`, added to the module f0024 creates. The raft's Whole-raft design is the contract; the signatures below are the part this issue adds and the way `Sessions` calls it.

## Design
Add to `src/shared/Logic/Hiscores/init.luau` (no new feature edge; Session the feature does not require Hiscores):

```lua
Hiscores.LEAVE_STEPS = 45
export type RunState = { run: number, done: { [number]: boolean }, waited: number, drop: boolean }
export type Submission = { score: number, level: number, run: number }
export type StepEvent = { kind: string, score: number?, level: number? }

function Hiscores.once(done: { [number]: boolean }, runId: number): (boolean, { [number]: boolean })
function Hiscores.newRun(): RunState
function Hiscores.onAgain(state: RunState, ok: boolean): RunState
function Hiscores.leave(stepsWaited: number, sawOver: boolean): "drop" | "keep"
function Hiscores.onStep(state: RunState, events: { StepEvent }, here: boolean): (RunState, Submission?)
```

`newRun` is `{ run = 1, done = {}, waited = 0, drop = false }`. `once` returns false and the same table when `runId` is not a whole number ≥ 1 or `done[runId]` is already true. Otherwise it copies `done`, sets the copy's `[runId]`, and returns true and the copy. The input table is unchanged.

`onAgain(state, false)` returns the same table. `onAgain(state, true)` returns a new state with `run + 1`, the same `done`, the same `waited`, and `drop = false`.

`onStep` scans events. The first `kind == "GameOver"` sets `saw`. A lowercase `gameover` is not that kind. When `score` and `level` are both numbers, `once(done, state.run)` decides the submission `{ score, level, run = state.run }`. Any `event.run` or `event.tick` is ignored. A second GameOver in the same events list or a later step of the same run submits nothing. A GameOver without score or level sets `saw` and submits nothing.

When `here` is true, the returned state has `waited = 0` and `drop = false`. When `here` is false, `waited` increases by 1 (the first absent step is 1) and `drop` follows `leave(waited, saw)`. `leave` is `"drop"` if `saw` or `stepsWaited >= LEAVE_STEPS`, else `"keep"`. `LEAVE_STEPS` equals `Game.CLASSIC_CONFIG.dyingTicks` (45) but the module does not require Game. Forty-four steps away with no GameOver stays. The GameOver step while away submits and drops. A disconnect during play, with no GameOver inside 45 steps, drops with no submit.

Run id, from state that already exists: the adapter map starts at `newRun()` in the Ready handler, next to the existing `Session.new(...)`. A rejoin's Ready finds `sessions[player] == nil` and creates a new session and a new run. It does not use `Session.tick`. `tick` advances every step and `Session.playAgain` does not reset it (read in prep, E4). It does not read a client value.

The heartbeat stays `for _ = 1, Session.advance(clock, dt) do`. One step per frame is wrong: `STEP_RATE` is 15 and `MAX_STEPS_PER_ADVANCE` is 5, and `LEAVE_STEPS` is 45 steps, not 45 frames. Inside that loop, for each live session:

```lua
local events = Session.step(s)
local here = player.Parent ~= nil
local state, submission = Hiscores.onStep(runs[player], events, here)
runs[player] = state
if submission then
	HiscoreStore.submit(tostring(player.UserId), names[player], submission.score, submission.level, submission.run)
end
if here then
	snapshot:FireClient(player, Session.frame(s, tostring(player.UserId)))
end
if state.drop then
	table.insert(dropping, player)
end
```

`onStep` is called only with those `events`. After the `pairs` loop, nil each player in `dropping`. Removing during `pairs` would skip other players. `advance` returning 0 does not call `onStep` and does not move `waited`.

`PlayerRemoving` nils the live session and parks the run. `Sessions.isOver` is not this raft; f0065 adds it, and it is false once `sessions[player] == nil`.

```lua
Players.PlayerRemoving:Connect(function(player: Player)
	local s = sessions[player]
	sessions[player] = nil
	local state = runs[player]
	runs[player] = nil
	if s and state then
		table.insert(pending, {
			session = s,
			state = state,
			userId = tostring(player.UserId),
			name = names[player],
		})
	end
end)
```

The same advance loop steps `pending` with `here = false` and no `FireClient`:

```lua
local events = Session.step(parked.session)
local state, submission = Hiscores.onStep(parked.state, events, false)
parked.state = state
if submission then
	HiscoreStore.submit(parked.userId, parked.name, submission.score, submission.level, submission.run)
end
```

Drop the parked row when `state.drop`. A parked run has no player to replicate to. `Ranks` `FireClient`s only when that user id's player is still parented.

While `PlayAgain` still exists, its handler keeps the f0031 shape and calls `onAgain` only when Logic accepts it. f0065 may delete the handler; this spec allows zero calls.

```lua
local _, ok = Session.playAgain(s, tostring(player.UserId))
if ok then
	runs[player] = Hiscores.onAgain(runs[player], true)
end
```

`names[player]` is `Hiscores.cleanName` of `DisplayName` when that value is a non-empty string, otherwise of `Name`, taken when the session is created. There is no `task.wait` and no `task.delay` in `Sessions`. No `PlayerAdded`, no `TICK_RATE`, no `Session.snapshot(`, no `.phase`, no lowercase `gameover`. One `Session.newClock(Session.STEP_RATE)`. `Session.new` still ends with `Session.GAME_CONFIG)`.

`HiscoreStore.submit` returns immediately (f0024 spawns `drive`), so this loop does not block the overlay. A second GameOver in the run does not call `submit`, because `submission` is nil. Catch-up can call `onStep` up to five times in one frame; `once` ignores the later ones.

### Scalability
One live session per connected player, plus a parked row for at most 45 steps after `PlayerRemoving`. The step itself is the existing `Session.step`, and only as many times as `Session.advance` returns. The store write is not on this thread. A full server of parked dying runs is bounded by the player count times 45 steps, then the rows are dropped.

### Maintainability
The next "when do we submit" change is `onStep`, not a new branch in `Sessions`. `Sessions` only passes `here`, the events from `Session.step`, and, while the handler exists, the play-again boolean. The run counter is not a field on `Session`, so f0031's phase pins stay true. A different pause length changes `LEAVE_STEPS` and the spec that compares it to `dyingTicks`. Deleting the play-again handler does not require a new Hiscores function: Ready already calls `newRun`.

### Usability
The player gets one submit for the run they just finished, including when they disconnect during the death pause. The overlay still appears for anyone still parented, because `FireClient` is skipped when `Parent` is nil and submit does not yield. A worse second GameOver cannot double-post. The API is `onStep` / `onAgain`: callers that pass a client run id still submit `state.run`. A rejoin during the parked window can submit its own new run; it does not steal the parked one.

## Test plan
- `run.spec` :: `once` copies, second GameOver of the same run is nil, `event.run = 99` still submits run 1, two GameOver events in one step keep the first score, `gameover` and a scoreless GameOver do not submit, `onAgain(true)` is run 2 and submits, `onAgain(false)` is the same table and does not submit again → AC1
- `leave.spec` :: `LEAVE_STEPS == 45 == dyingTicks`, 44 steps away stay, GameOver while away submits and drops, coming back clears `waited`, a scoreless GameOver while away drops without a submit → AC2
- `sessions.spec` :: the f0018 / f0054 source pins, at most one `playAgain` in the f0031 shape, `newRun` on Ready, one `Session.advance`, every `onStep` after it and given `events` from `Session.step`, `FireClient` of the frame only inside `if here then`, `PlayerRemoving` nils `sessions[player]` and parks `pending`, `Ranks` checks `Parent ~= nil` before `FireClient` → AC3

## Rules and mutants

| Rule | Spec :: case | Mutant it kills | Checked |
|---|---|---|---|
| One submit per run, input `done` unchanged | run :: once and second GameOver | `once` ignores `done[runId]` | run |
| Run id is the state, not the event | run :: `event.run = 99` | `once(done, event.run)` | run |
| New run only when playAgain returns true | run :: onAgain | increment on every call | reasoned: `onAgain(false)` returns the same table; the spec asserts identity. Not sed-mutated separately from the once row |
| Keep 44 steps, drop at 45 or on GameOver | leave :: 44 steps then GameOver | `LEAVE_STEPS = 0` | run |
| Sessions does not decide the phase | sessions :: no `gameover`, no `.phase` | reading `.phase` in the adapter | reasoned: asserted against the current source shape; the new file fails the `Hiscores.onStep` count until wired |
| The advance loop steps GameOver, and a departure is parked | sessions :: advance and PlayerRemoving | one `Session.step` per Heartbeat; leave the row in `sessions` | reasoned: the current file has `Session.advance` but no `onStep` and no `pending`, so the spec fails closed |
| Play again is optional and only increments when Logic accepts it | sessions :: at most one playAgain | require the handler; call `onAgain` when it returns false | reasoned: f0065 deletes the handler. The spec allows zero calls and, when one remains, requires `if ok then` |
