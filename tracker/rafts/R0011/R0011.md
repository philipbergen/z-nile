# R0011: Hiscores

## Theme

These three issues are one feature: the server records a run, and the lobby shows it. Game design, quoted:

> Hiscores: A **global all-time top N**, plus **daily** and **weekly** boards. No personal-best feature for now.

> **Boards:** all-time top N (N **(prep)**, e.g. 50), plus daily and weekly boards keyed by UTC period.
> **Entries:** the player's Roblox display name and user ID, the score and the level reached.
> **Submission:** only the server submits, from its own simulated result, at game over. Clients never send scores.
> **Storage:** behind a Logic-facing interface. A fake store is used in tests, and Roblox's ordered store in the adapter. Beta and production have separate stores, because they are separate experiences.

> The **lobby** (the existing place, the experience's start place) shows a hiscore list and a START GAME button… The hiscore list is an empty panel until R0011 fills it. … At game over an overlay shows the results and waits for a tap, then teleports back to the lobby (f0065, after c0063).

Prep decisions, fixed here (a later veto can change them; execution does not reopen them):

1. **N = 10**, the same number as `Lobby.MAX_ROWS`. Do not change `Lobby.MAX_ROWS`. The "(prep), e.g. 50" is settled at the panel's existing cap.
2. **One row per user id per board.** A submit replaces that row only when the new score is strictly greater, or the score is equal and the level is strictly greater. Otherwise the stored row stays, including its display name. The name is written only when the row is replaced.
3. **Daily key** is the UTC date `YYYY-MM-DD`. **Weekly key** is the Monday of that UTC week, also `YYYY-MM-DD` (Monday-start). All-time has no period. This is the "keyed by UTC period" line.
4. **OrderedDataStore stores an integer only.** A companion DataStore stores `{ name, userId, level, score }` under the same key. Both sit behind one injected store. Specs use the in-memory fake. No spec calls a live DataStore or the network. This is the "Logic-facing interface / fake in tests / ordered store in the adapter" line.
5. **Board ids** are `"all"`, `"day"` and `"week"`.
6. **The server submits once per run** when its own session emits `GameOver`, using the score and level on that event, including if the player has disconnected. The only dedupe is the run state's `done`, which lives and dies with that session's `RunState` in `src/server/Submits.luau`. The store has no dedupe of its own: every `HiscoreStore.submit` drives, and `commit` decides which row stays (an equal or worse score is a no-op, a better one is written). The next visit is a new `Ready`, a new session and a new `RunState` that starts again at run 1, and it may submit; so may a parked run of the same user id that is still in its dying pause. While a play-again handler is still in this place it may submit again, and f0065 may delete that handler. A failed write retries with a small bounded backoff and never blocks the overlay. The client never sends a score. A remote that accepts a score is out of design. A closing server waits for that work: `Submits` binds one `game:BindToClose` that holds the shutdown while any run is held or any drive is in flight, for at most `CLOSE_WAIT` (25 s). The engine keeps stepping Heartbeat during a close, so a run parked in its dying pause reaches its `GameOver` and submits, and the last player's drive lands before the server stops. Work still pending at 25 s is lost (Risks). This is "only the server submits… Clients never send scores."
7. **The lobby's existing hiscore panel shows the all-time board** (`Lobby.panel`). The lobby can switch to day and week through a pure function; the adapter draws it. The game-over overlay gains the player's all-time rank as an extra line when the server knows it. There is no second full board in the game place. The lobby teleport is f0065, not this raft. This is "the hiscore list is an empty panel until R0011 fills it" and the overlay sentence, without taking f0065's teleport.
8. **No environment prefix.** Beta and production are different experiences, so they already have different DataStores ("separate stores, because they are separate experiences"). The lobby place and the game place are the same experience and share the stores: the game place writes, the lobby reads.

Personal bests stay out (the table says no personal-best feature).

`src/shared/Logic/Hiscores/init.luau` is the public API. The store is a parameter. The feature directory's callers require the directory, not a child module.

Types the module exports:

```lua
export type Io = {
```

Constants: `N = 10`, `ORDERED_STORE = "Hiscores"`, `COMPANION_STORE = "HiscoreEntries"`, `LEVEL_CAP = 10000`, `RETRY = { attempts = 3, base = 0.25, cap = 1 }` frozen, `LEAVE_STEPS = 45`, `CACHE_TTL = 15`, `READ_GAP = 1`, `CLOSE_WAIT = 25` (seconds a closing server is held for hiscore work; Roblox allows 30).

Period and store (f0024): `dayKey`, `weekKey`, `board`, `scope`, `cacheKey`, `entryKey`, `userIdFromKey`, `cleanName`, `valid`, `qualifies`, `commit`, `pack`, `retryDelay`, `attemptDelays`, `spend`, `pageAttempt`, `scorePage`, `globalName`, `storeTarget`, `rows`, `rankOf`, `lobbyRows`, `fake`, `submit`, `top`, `drive`. `os.time` is not called here. Civil dates are arithmetic (Howard Hinnant `civil_from_days` / `days_from_civil`), so a host zone cannot move the key. `1970-01-01` is Thursday, so days since Monday are `(floor(unix / 86400) + 3) % 7` (Lua `%` is floored, so negative instants work).

Keys: all-time key is the user id string. Day and week keys are `userId .. ":" .. period`. The OrderedDataStore **scope** is `Hiscores.scope(board)` (`"all"`, `"day:YYYY-MM-DD"`, `"week:YYYY-MM-DD"`) because an ordered store cannot prefix-filter. The key still carries the period suffix. Companion key and scope match. `GetSortedAsync` page size is `pageAttempt(1) == 10`, and on error one retry at `pageAttempt(2) == 50`. `scorePage(entries, n?)` turns each `{ key, value }` of the ordered page into `{ key, score = floor(value / LEVEL_CAP) }`, skips an entry without a whole-number `value`, and stops after `n` entries when `n` is given (both adapters pass `N`): it is the one place a packed integer becomes a displayed score. Do not call `AdvanceToNextPage`. If a scope is rejected, `storeTarget(kind, board, false)` is `globalName(base, scope)` with scope `"global"`.

`rows(pages, lookup: (key) -> (Companion?, err?), n): { Row }?` asks `lookup` for each key's companion. An error from `lookup` (a failed read or a refused budget) means a row the page says exists is unknown, so `rows` returns nil, the whole board unknown, never a shorter board (review 004 F2); `(nil, nil)` is an absent companion and is skipped. `top` (the fake) never errs and returns `rows(...) or {}`. `rows` keeps the first occurrence of a key, skips a missing or mismatched companion (`key == userId` or `key` prefixed by `userId .. ":"`, so `"15"` does not match user `"1"`), sorts by score desc, level desc, user id string asc, and caps at `n`. Ranks are `1..#result`. The displayed score is the page score, which `scorePage` already unpacked: `rows` never sees a packed integer and does not know `LEVEL_CAP` (a `rows` that divides would turn every hand-built page score into 0). A page shorter than `n` is not padded. Do not fetch another page to rescue a tie: the ordered integer already carries the level. `pack(score, level)` is `score * LEVEL_CAP + min(level, 9999)`. A score whose packed value is not an integer below `2^53` is invalid. Levels past 9999 stay on the companion for display and clamp in the integer; two clamped levels tie by user id. `Store.set` takes that packed integer. `fake().top` holds what `set` was given, sorts it by the packed integer descending, then key ascending, truncates to `n`, and returns `{ scorePage(<those { key, value } entries>) }`: the same function the adapters use, not a private unpacked copy.

`commit(stored, attempt)` returns nil when the row must not change, and does not mutate `stored`. Otherwise it returns a new companion. Both writes are transforms the store applies to the value it actually holds, with the shape `UpdateAsync` has: `io.updateEntry(board, key, transform: (Companion?) -> Companion?)` and `io.updateScore(board, key, transform: (number?) -> number?)`. Neither transform yields or calls `io`; either may run more than once, and may be handed a value another drive stored. The companion transform `drive` passes calls `commit` on the row it is given and remembers, from its last call, the row it saw and what `commit` returned. The row now stored, `kept`, is what `commit` returned, or, when it returned nil, the row the transform saw. The ordered transform is `function(old) return math.max(old or 0, pack(kept.score, kept.level)) end`. So a nil `commit` still runs the ordered transform, with the pack of the stored row: an ordered key that fell behind its companion (a write whose retries all failed, or a blind write elsewhere) is repaired by the next attempt, even one that does not qualify, and it can never go above the stored row. `drive` does not trust `UpdateAsync`'s return value (E13); it reads what its own transform saw. If the ordered update fails, the next try runs the same ordered transform again and does not run `commit` again. `UpdateAsync` spends a read and a write: `spend` must accept both or the call is skipped. `GetSortedAsync(false, pageSize)` is descending. Page size stays `pageAttempt` 10 then 50.

`drive` re-reads `io.budget` through `spend(budget, 1)`. Ops: `"get"` companion read, `"set"` companion write, `"getSorted"` ordered read, `"setSorted"` ordered write. `UpdateAsync` spends a read and a write of its own store's kind (`DataStoreRequestType`: `StandardRead` is the read of a DataStore `UpdateAsync`, `OrderedRead` the read of an OrderedDataStore `UpdateAsync`), so the companion update spends `"get"` and `"set"`, the ordered update `"getSorted"` and `"setSorted"`, and each skips the call if either refuses. The rank lookup's companion `GetAsync`s spend `"get"`. It does not ask for a list budget. `Enum.DataStoreRequestType.OrderedList`'s budget query is documented to return 0, so gating the top read on it would hide every board. A failed or nil `io.top` leaves `rank` nil. Writes may still have succeeded. Budget 0 on an update's read or write op does not call that update (a 0 `"getSorted"` skips only `updateScore`; the companion is still written), and the non-zero delays still pass to `io.wait`. A failed update retries. A `commit` that returns nil writes no companion and is not retried; that board's ordered transform still runs once, with the stored row's pack, and a failure of that one retries like any ordered write. `wrote[id]` is true only when the companion was replaced and its ordered write then succeeded. Boards are independent. An invalid attempt writes nothing and still calls `top`. The write path never calls `io.get`: a snapshot taken before the update cannot be published. The spec doubles store whatever a transform returns and never do the policy themselves (no max, no commit in the double).

Run policy (f0025), same module: `once`, `newRun`, `onAgain`, `leave`, `onStep`. The run id is not client-supplied and is not `Session.tick` (`playAgain` does not reset `tick`, and `tick` advances on every step). `src/server/Submits.luau` holds one `RunState` per session object, starting at `newRun()` (`run = 1`) when Sessions tells it a session was made on Ready. A rejoin's Ready creates a new session and a new run; it does not alias a parked one, so two runs for one user id can submit, both as run 1, and nothing downstream dedupes them (decision 6). While a play-again handler exists, it tells Submits only when `Session.playAgain` returns true, and Submits calls `onAgain`. f0065 may delete that handler. `once` copies `done` before writing. `onStep` looks only at `event.kind == "GameOver"` (capital G), ignores any `event.run`, and submits the first scored GameOver of that run. A GameOver without score or level sets the "saw over" flag (so a disconnect drops) and does not submit. `onStep` runs only on the events `Session.step` just returned, once per step `Session.advance` grants, including when one frame catches up five steps. `advance` returning 0 steps nothing and does not move `waited`.

`leave(steps, sawOver)` is `"drop"` when `sawOver` or `steps >= LEAVE_STEPS`, else `"keep"`. `LEAVE_STEPS` is the classic dying pause copied as a number (`Game.CLASSIC_CONFIG.dyingTicks` is 45). Hiscores does not require Game. `onStep` increments `waited` when `here` is false. At 45 steps away with no GameOver, drop without a submit (a disconnect during play is not kept for the whole run). GameOver while away submits, when `once` allows, and drops.

Read policy (f0026), same module: `boardId` returns `"all" | "day" | "week"` or nil. Numbers and tables are nil, not coerced. `lookup(cache, now, ttl, gap, inflight, fetch, failure?) -> (cache, rows, failure)` : a fresh cache (`now >= at` and `now - at < ttl`) returns its rows. `now == at + ttl` is stale. Stale and `inflight` does not fetch and does not move the cache or `failure`. Stale, not in flight, and outside the key's failure window calls `fetch`. `nil` means failure: the previous cache object stays and the rows result is nil. `{}` is an empty board and is cached. A successful fetch returns a new cache and does not mutate the one it was given. A non-number `now`, or time moving backwards past `failure.at`, does not fetch. `failure` is the key's run of failed reads: a failed fetch returns `{ at = now, count = previous count + 1 }`, a successful one returns nil, and every other outcome returns the `failure` it was given. The key is not read while `now - failure.at < failureWait(gap, ttl, failure.count)`, where `failureWait(gap, ttl, k) = min(gap * 2^k, ttl)`: 2, 4, 8, then 15 s (`now < failure.at` also waits); `gap` (`READ_GAP`) is only that base. There is no per-player state (review 005 F1): the 15 s cache, the in-flight flag and the failure window bound a key's reads, so one player costs at most three reads per 15 s (one per board) and an outage at most one read (two page sizes) per 2, 4, 8, then every 15 s, however many players ask. Nil rows therefore mean one of two things (in flight, or a failed fetch or the failure window); `Boards` tells them apart by whether its own `fetch` ran and whether the in-flight flag is set, not by the return shape.

Lobby, new functions only (`Lobby.panel` unchanged):

```lua
function Lobby.board(raw: any): ("all" | "day" | "week")?
function Lobby.boardTitle(id: string?): string -- "all"/nil/"nope" -> "HISCORES"; "day" -> "TODAY"; "week" -> "THIS WEEK"
function Lobby.boardPanel(rows: { Lobby.Row }?, id: string?): Lobby.Panel -- Lobby.panel, then the title
function Lobby.lines(panel: Lobby.Panel, highlightRank: number?): string

Lobby.MAX_RETRIES = 3
function Lobby.retryAfter(failures: number): number? -- READ_GAP * 2^(failures - 1) for 1..MAX_RETRIES (1, 2, 4 s), else nil
```

`lines` returns `panel.empty` when set, otherwise one line per row, `` `{rank} {name} {score} {level}` ``, with `"> "` on the highlighted rank. The highlight is a rank the server sends, not a name match. `Lobby.READ_GAP` is a copy, not a require: `LobbyView` requires only Lobby and Travel, because f0061's promoted `lobby-adapters.spec` boots the real `LobbyView` on `tests/lib/fakeengine`, whose module map serves only those two (a `LobbyView` that required Hiscores would fail that spec at boot). `endtoend.spec` asserts the two constants are equal.

Flow, new functions only (`Flow.overlay` unchanged, including `` `SCORE {n}   LEVEL {level}` ``):

```lua
export type RankView = { over: number, rank: number?, pending: number?, pendingRun: number? }
function Flow.rankLine(rank: number?): string? -- whole number >= 1 -> `ALL-TIME #{n}`, else nil. Do not cap at N.
function Flow.follow(view: RankView, gameOver: boolean, wasOver: boolean): (RankView, boolean)
function Flow.hearRank(view: RankView, run: number, rank: number?, gameOver: boolean): RankView
function Flow.shownRank(view: RankView, gameOver: boolean): string?
```

The model: `rank` is the shown run's rank and only exists while that run's overlay is up; `pending` is one slot for the next run. `follow` increments `over` only on the false→true edge. On that edge it **assigns** `rank`: `pending` when `pendingRun` is the new `over`, otherwise nil, never the previous `rank`; and it clears `pending` and `pendingRun` either way. On true→false it clears `rank` and keeps `pending`. With no edge it returns the same table. `hearRank` takes the same game-over bit `FlowView` passes to `shownRank`. It ignores a rank `rankLine` rejects. `run == view.over` and `over >= 1` with the bit true sets `rank` (a packet that arrives while that overlay is up still shows); with the bit false it returns the same table, so a packet for a run whose overlay has closed is not kept. `run == view.over + 1` stores one `pending` / `pendingRun`, whatever the bit, and does not show it. Any other run, including `over + 2`, returns the same table. So the order "run 1 dismissed, run 2's rank arrives, run 1's late rank arrives, run 2's overlay opens" shows run 2's rank (the retry backoff makes that order possible). `shownRank` returns the line only while `gameOver` is true. `FlowView` keeps the bit it last passed to `follow` and hands it to `hearRank` from `OnClientEvent`; `show` passes `overlay.banner == "GAME OVER"`. The client counter starts at 0 and becomes 1 on the first game over. The server run starts at 1. They meet.

Server adapters, thin:

- `src/server/HiscoreStore.luau` (game place only). `submit(userId, name, score, level, run)` always `task.spawn`s `drive` (inside `pcall`, `warn` on failure), so the heartbeat never waits. It keeps no record of what it was given: no `Hiscores.once`, no map of user id and run. A second submit for the same user id and run drives again, and `commit` decides (decision 6). `budget` maps `"get"` → `StandardRead`, `"set"` → `StandardWrite`, `"getSorted"` → `OrderedRead`, `"setSorted"` → `OrderedWrite`, through `GetRequestBudgetForRequestType`. `pending(): number` counts submits from the call until their drive ends: incremented before the spawn, decremented when the spawned function ends, also when `drive` errors (the spawned function runs `drive` and the listener inside its own `pcall` and `warn`s on error), and when the spawn itself fails. It does not read `OrderedList` or the legacy `GetAsync` / `SetIncrement` request types. `io.updateEntry` is the companion store's `UpdateAsync(key, transform)` and `io.updateScore` the ordered store's, each with the transform `drive` passed, unchanged: the adapter has no copy of the policy (no `Hiscores.commit`, no `Hiscores.pack`, no `math.max` of its own). `io.get` is the companion `GetAsync`. `io.top` is `GetSortedAsync(false, pageAttempt(1))`, on error once at `pageAttempt(2)`, then `{ scorePage(pages:GetCurrentPage(), N) }` (at most `N` entries, so at most `N` companion reads); it does not advance the page. Every call is `pcall`'d and an error is returned as the `io` error string. `wait` is `task.wait`. Opens go through `Hiscores.storeTarget(kind, board, true)`: ordered `Hiscores`, companion `HiscoreEntries`, scope from the board. `listen(fn)` sets the one callback used when `rank ~= nil`; the callback receives `(userId, run, rank)`. `adapter.spec` runs this source on a stub `DataStoreService` whose `UpdateAsync` stores what the transform returns. `read` is not required on this module: the lobby cannot require `src/server`.
- `src/server/Ranks.luau` creates `RemoteEvent` named `Rank` under `ReplicatedStorage.Remotes` at `start`, parents it before any yield, and `HiscoreStore.listen`s with a callback that finds the player with `Players:GetPlayerByUserId(tonumber(userId))` and `FireClient(player, run, rank)`s only when that player exists and `player.Parent ~= nil`. No `OnServerEvent`. No `FireServer`. `src/server/Main.server.luau` calls `Ranks.start()` before it starts Sessions.
- `src/lobby/server/Boards.luau` creates `RemoteEvent` named `Board` the same way. `OnServerEvent(player, raw)` keeps the request only when `Hiscores.boardId(raw)` is non-nil, and otherwise sends nothing and reads nothing. One shared cache per `cacheKey(id, os.time())`, one in-flight flag, one waiter list and one `Failure` per that key,, and no per-player state: a player's asks for different boards are never answered from another board's timing (review 005 F1), and nothing outlives a visitor. The whole read (both store opens, both page sizes, `scorePage`, the companion `GetAsync`s and `rows`) runs inside one `pcall`: any error there, an unknown companion included, is a failed read, so the in-flight flag and the waiter list are cleared on every path (review 004 F1). A companion `GetAsync` that throws is an unknown row (the getter returns its error), which fails the read; one that returns nil is absent and skipped. An answer goes only to a player whose `Parent` is not nil (a waiter who left gets none). It calls `lookup` with `CACHE_TTL`, `READ_GAP`, the flag, the key's `Failure` (and stores the one it returns), and a `fetch` that sets the flag, puts the requester on the waiter list, reads, and clears the flag. The read is `GetSortedAsync(false, pageAttempt(n))` for n = 1, then 2 on error, each `pcall`'d, then `scorePage(GetCurrentPage(), N)` (the page cut to its first `N` entries, so a 50-entry fallback page costs at most `N` companion reads; review 005 F4), companion `GetAsync`s, and `rows(..., N)`; not `drive`, and never `AdvanceToNextPage`. Every request is answered with exactly one `FireClient(player, id, Hiscores.lobbyRows(rows), Hiscores.rankOf(rows, tostring(player.UserId)), failed)`, where the highlight is that player's own rank on those rows, or nil when they are not on them: (1) rows returned (fresh cache or a successful read, an empty board included): that requester, `failed = false`; (2) its own `fetch` ran: every waiter on that key, once each, with the new rows and `failed = false`, or on a nil read with the previous cache's rows (`{}` when there were none) and `failed = true`; (3) nil rows while the key is in flight: the requester joins the waiter list and is answered by (2) when the read returns; (4) nil rows inside the key's failure window, not in flight: the previous rows (or `{}`) with `failed = true`, without a read. A second request while the read is yielded does not call `GetSortedAsync` again. The file contains neither `SetAsync`, `UpdateAsync`, `HiscoreStore` nor `AdvanceToNextPage`. `src/lobby/server/Main.server.luau` calls `Starts.start()` then `Boards.start()`. Starts does not require Boards and does not touch `DataStoreService`. `adapters.spec` runs this source on a stub `DataStoreService` whose read can fail or yield.
- Both adapters open stores with `Hiscores.storeTarget`. Ordered name `Hiscores`, companion `HiscoreEntries`, no beta/prod prefix.
- `LobbyView` requires only Lobby and Travel (see Lobby above). It `FindFirstChild("Board")` and binds only when it is there. It does not `WaitForChild("Board")` (the f0061 fake has no such remote and must still boot onto the empty panel). On `OnClientEvent(id, rows, highlight, failed)` it draws `Lobby.boardPanel(rows, Lobby.board(id))` into `Title` and `Lobby.lines(panel, highlight)` into `Rows`. It `FireServer("all")` once at start when the remote exists. It keeps `wanted`, the board last asked for (the start ask, or a tap), and a count of asks it has sent. An answer for any other board is not drawn and counts nothing; a retry fires only if no ask was sent since it was scheduled and `wanted` is still its board (review 004 F5). A tap sets `wanted`, resets the failure count and asks. It counts failed answers in a row: a payload with `failed == true` adds one and, while `Lobby.retryAfter(count)` is a number, schedules one `task.delay` of that many seconds that `FireServer`s the payload's own board (`Lobby.board(id)`, `"all"` when that is nil), so a failed TODAY read retries TODAY; a payload with any other `failed` resets the count and schedules nothing. After the third failed answer in a row it stops asking; a board button always asks.
```lua
export type Runs = {
	ready: (s: Session.Session, player: Player) -> (), -- a session was made on Ready
	again: (s: Session.Session) -> (), -- Session.playAgain accepted (only while the handler exists)
	step: (s: Session.Session, events: { Session.Event }, here: boolean) -> boolean, -- false: let a parked session go
}
function Sessions.start(runs: Runs?)
```

`Sessions` keeps the promoted source pins: one `Session.newClock(Session.STEP_RATE)`, `Session.new` ending `Session.GAME_CONFIG)`, `FireClient` of `Session.frame`, no `Session.snapshot(`, no `PlayerAdded`, no `TICK_RATE`, no lowercase `gameover`, no `.phase`, no `task.wait` or `task.delay`. Ready that makes a session calls `runs.ready(s, player)` once. The heartbeat is `for _ = 1, Session.advance(clock, dt) do`. Inside that loop, each live session does `local events = Session.step(s)`, `runs.step(s, events, here)` with `here = player.Parent ~= nil`, and `FireClient`s `Session.frame` only when `here`. A live session stays in `sessions` whatever `runs.step` answers (a `GameOver` while parented leaves the player in the live map: f0065's `Sessions.isOver` is `sessions[player] ~= nil and ...`). `PlayerRemoving` sets `sessions[player] = nil` and, only when started with `runs`, appends the session to a parked list. The same advance loop steps each parked session once per step, calls `runs.step(s, events, false)`, never `FireClient`s it, and lets it go (after the loop over the list, not during it) when that returns false. Without `runs` nothing is parked, so f0065's boot behaves as today. Do not add `Sessions.isOver`; f0065 does.

`src/server/Submits.luau` (f0025) requires Hiscores and `./HiscoreStore`, and is the module table `Runs`. It keeps no dedupe beyond `RunState.done`. `pending(): number` is the number of runs it holds (made on Ready, released when `step` returns false). `close()` loops `waited += task.wait(0.25)` while `Hiscores.holdClose(Submits.pending(), HiscoreStore.pending(), waited)`, the pure rule `(runs > 0 or drives > 0) and waited < CLOSE_WAIT`. The module binds it once, when first required: `game:BindToClose(Submits.close)`. At close every player is leaving, so a held run is parked and either drops within 45 steps or submits, and that submit is then a pending drive; a run whose player is never removed (Studio) holds the close until the 25 s cap. `src/server/Main.server.luau` starts Sessions with it: `require("./Sessions").start(require("./Submits"))`, or, once f0065's Main has `local Sessions = require("./Sessions")`, `Sessions.start(require("./Submits"))`; `sessions.spec` pins `.start(require("./Submits"))` either way.

## Risks & rollback

- A live OrderedDataStore can reject scope or page size 10. The fallbacks are `storeTarget(..., false)` and `pageAttempt(2)`. They are pure and specified; they were not opened against Roblox.
- `OrderedList`'s budget read is documented as 0 and was not confirmed on a server. Gating on it would blank the rank. The design does not gate.
- The rank packet can beat the client's overlay edge. `hearRank` holds one pending run, and only `over + 1`. A packet for a run whose overlay has closed is not kept (the bit is false), and the next edge assigns the rank from pending or nil, so it does not label the next run. A second early packet for `over + 2` is ignored. A rank whose write needed all three retries can arrive after its overlay closed; it is then not shown, by design.
- Disconnect during play, more than 45 steps before GameOver, does not submit. That is the bound. The player leaves `sessions` immediately, and the parked session keeps stepping inside `Session.advance` until `Submits.step` returns false (`onStep` said `drop`). Counted in steps, not frames, a disconnect at the start of the dying pause still reaches GameOver.
- Runtime remotes exist only after the server script runs. `FindFirstChild` misses them in the f0061 fake, and the panel stays the empty state that spec already requires. In a published place the server script runs first; OC1 is the check that the lobby actually fills.
- f0065 is not in this raft. Do not edit its acceptance spec. Keeping Rank out of `default.project.json` leaves its remote list intact. Its `sessions.spec` boots the real `Sessions` with `start()`; keeping Sessions' requires to Maze and Session, and parking only when started with runs, keeps that spec green. If R0034 lands first, re-run `scripts/tracker.sh check f0025` and f0065's promoted specs after the Main and Sessions merge.
- A server that closes holds for hiscore work for at most `CLOSE_WAIT` (25 s): a drive still retrying then, or a parked run whose Heartbeat did not reach `GameOver` (E16), is lost. A live player who is never removed (a Studio stop) makes the close wait the full 25 s.
- A throttled companion read now fails the whole board read (and, in `drive`, gives no rank) instead of answering a short board or a too-good rank. The F3 failure window bounds what repeated failures cost.
- A DataStore read outage costs each board key one read per 2, 4, 8, then 15 s, and each lobby client at most three retries (1, 2, 4 s) per run of failures; the panel then keeps the rows it had until the player taps a board or a healthy answer arrives.
- Two runs for one user id on one server (a rejoin during the 45-step parked pause) both drive. `commit` and the ordered max make the order of their writes irrelevant: the better row stays.
- Rollback is reverting the PR. Stores already written in Beta remain; they are not read until this code is present. No migration.
