# Refutations 001: R0011 (design mode)

- F1: fixed: the heartbeat stays `for _ = 1, Session.advance(clock, dt) do`. Inside it, each live session takes `local events = Session.step(s)`, calls `Hiscores.onStep` with those events and `here = player.Parent ~= nil`, submits only that submission, and `FireClient`s `Session.frame` only inside `if here then`. Removals happen after the `pairs` loop. `PlayerRemoving` sets `sessions[player] = nil` and parks the session and `RunState`; the same loop steps that list with `here = false` and no `FireClient`, and drops it when `onStep` says `drop`. `submit` and `Ranks` use the captured user id, and `Ranks` `FireClient`s only when `Parent ~= nil`. `sessions.spec` requires one `Session.advance`, every `onStep` after it on an `events` argument including a `false` here, the frame send after `if here then`, a `PlayerRemoving` body that both nils and mentions `pending`, and `Parent ~= nil` before `FireClient` in `Ranks`. `leave.spec` is unchanged. `Sessions.isOver` is not required. Rules rows: "The advance loop steps GameOver, and a departure is parked" and "Play again is optional and only increments when Logic accepts it" (`reasoned`). consequences: a rejoin during the parked window is a second `newRun` and may also submit; the parked run has no `Player`; `advance` returning 0 does not move `waited`; a live `drop` only happens when `here` is false. The handler may stay, in the f0031 shape, so today's promoted spec stays green, and the new spec allows zero calls so f0065 can delete it.
- F2: fixed: the "exactly one `Session.playAgain`" assert is gone. `Ready` that creates a session calls `Hiscores.newRun()`. A play-again handler, if still present, calls `onAgain` only when `Session.playAgain` returns true (`if ok then`). `run.spec` still has the second-GameOver and `onAgain` cases. `FlowView.show` passes `overlay.banner == "GAME OVER"` into `follow` and `shownRank`. `flow.spec` keeps `SCORE 1200   LEVEL 4` and does not mention `playAgain`. No new `Flow.overlay` field and no `Main.client` edit. consequences: with no in-place play again, one visit has one `GameOver` and the next visit is `Ready` / `newRun`; `onAgain` stays the pure function for a handler that still exists. A banner-string change would drop the rank line; f0031 already pins that banner.
- F3: fixed: `follow` on false→true clears `rank` unless `pendingRun` equals the new `over`, and clears `pending` when it does not match. `hearRank` of `run == over` (and `over >= 1`) still sets `rank`, including after dismiss; `run == over + 1` is the only pending slot; `run == over + 2` returns the same table. `shownRank` is nil unless `gameOver` is true. `flow.spec` runs the review's sequence: early rank 3 at `over == 0` shows on the first edge; dismiss, then `hearRank` of that run, then the next edge, `shownRank` is nil; a rank heard while that overlay is up shows; run 1 at `over == 2` is the same table. Rules row "Entry clears a rank that arrived after dismiss", mutant "entry leaves `rank` in place" (`reasoned`, not sed-run). consequences: the clear is the entry edge, not `hearRank`, because a packet that arrives while the overlay is up is `run == over` and must still show. Pending is not widened to a map.
- F4: fixed: `Hiscores.commit(stored, attempt) -> Companion?` returns nil when the row must not change and does not mutate `stored`. That function is the companion `UpdateAsync` transform. The ordered write is `UpdateAsync` of `math.max(old or 0, pack(committed.score, committed.level))`, not `SetAsync` and not the bare score. A failed ordered write retries that packed value and does not call `commit` again. `spend` must accept both the read budget and the write budget. `drive.spec` covers a lower `commit` (name stays), overlapping drives that keep 5000 and never pass the losing packed score, and a failed `updateScore` that retries `pack(5000, 4)`. `adapter.spec` requires `UpdateAsync` and `GetSortedAsync(false` and forbids `SetAsync`. `adapters.spec` requires `Boards.luau` to contain neither `SetAsync`, `UpdateAsync`, nor `HiscoreStore`. The zero-list-budget case still calls `top`. Rules rows for the pack max, both budgets, and the adapter needles (`reasoned`). consequences: the review's `committed.score` is the score `commit` accepted, and F5 makes the ordered integer the pack of that score, so a bare-score max fails the spec (`packed ~= 5000`). The transform does not yield. No Beta migration. A nil `commit` does not retry and does not write the ordered key.
- F5: fixed: `LEVEL_CAP` is 10000. `pack` is `score * LEVEL_CAP + min(level, 9999)`. `valid` rejects a score whose packed value is not an integer below `2^53` (`2^53 - 1` is invalid; the max score is `floor((2^53 - 1 - 9999) / LEVEL_CAP)`). A displayed level may be above 9999. `rows.spec` keeps the in-page string-id tie and adds `fake().top(board, 1)` for scores 10/1 and 10/7, expecting key `"2"`. The design says not to read page 2 to repair a clamped tie. Rules row "Ordered value is the packed score, higher level wins a one-row page", mutant "ordered value is the bare score" (`reasoned`). consequences: two clamped levels at one score tie by user id; `scorePage` unpacks before `rows` shows the score; `rows` of an already-unpacked page is unchanged.
- F6: fixed: `lookup` takes an in-flight flag. Stale and in flight does not fetch and does not move the cache or `lastFetch`. A nil fetch returns nil rows and the same cache, and moves `lastFetch`. After the gap, with the flag clear, it fetches again. `read.spec` runs two lookups at `now == at + ttl` (one fetch between them), the nil-fetch identity, and the retry at `last + READ_GAP`. `Boards` `FireClient`s on success (`failed = false`, including an empty board) and on failure (`failed = true`, previous rows or `{}`). `LobbyView` `FireServer("all")` again only from a failed payload after `READ_GAP` via `task.delay`, not from `WaitForChild("Board")`. Rules rows "In flight does not fetch" and "Failure still answers, and the client asks once more after the gap" (`reasoned`). consequences: a healthy empty board is cached and is not retried; waiters share one fetch and each gets one answer when it finishes; day and week stay extra requests; `Starts` still does not open a store.
