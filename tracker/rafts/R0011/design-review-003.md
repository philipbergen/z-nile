### F1 [medium] The ordered `UpdateAsync` is gated on the standard read budget, and adapter.spec rejects the right one
Where: R0011.md (`drive` ops paragraph: an update spends `"get"` and the matching write; HiscoreStore `budget` maps `"get"` → `StandardRead`); `tracker/issues/f0024/acceptance/adapter.spec.luau` ("stores are the shared names…": every queried kind must be `StandardRead`, `StandardWrite` or `OrderedWrite`)
Evidence: The `DataStoreRequestType` reference has `OrderedRead` (13), which is "GetAsync() and the read of UpdateAsync() for OrderedDataStore", and `StandardRead`, which is the read of `UpdateAsync()` for DataStore. So `io.updateScore` (ordered `UpdateAsync`) spends OrderedRead plus OrderedWrite. The design checks StandardRead plus OrderedWrite. An implementation that checks `OrderedRead` before the ordered update queries `DataStoreRequestType.OrderedRead`, and the spec's `known` check fails it. E11 lists only the three enums it checked.
Critique: The gate checks the companion's bucket before an ordered call. Once the standard reads are spent (the rank lookup alone does up to 10 `GetAsync`s per submit), it skips ordered writes that still have budget. It also lets ordered writes through when OrderedRead is exhausted. The call is then throttled and retried, so this costs reliability, not correctness. The tempting fix is to add `OrderedRead` to the spec's allowed list and leave `drive` alone. That accepts both mappings and pins neither.
Consequences: `drive` needs a fourth op name, so `Io.budget`'s op set changes in the type block and in drive.spec's budget doubles (`"get"`, `"sorted"`). The rank lookup's `GetAsync` stays StandardRead. `OrderedList` stays unread (E11).
Recommendation: Give the ordered update its own read op (`"getSorted"` → `OrderedRead`). `drive` spends `("get","set")` for the companion and `("getSorted","setSorted")` for the ordered key. adapter.spec requires that every ordered `UpdateAsync` is preceded by a query of `OrderedRead` and every companion one by `StandardRead`, and keeps forbidding `OrderedList`. drive.spec: a zero `"getSorted"` budget skips only `updateScore` and still writes the companion. Rules row: mutant "ordered update spends get". Add the enum to E11.

### F2 [medium] Nothing keeps the server alive for a submit in flight, so a solo player's score is lost when they leave
Where: R0011.md decision 6 ("including if the player has disconnected"), Risks (the parked-session bullet), the HiscoreStore bullet (`task.spawn` drive); no mention of `BindToClose` anywhere in the raft
Evidence: The lobby teleports one player at a time (`Starts.luau:49`, `TeleportAsync(…, { player })`), so a Beta game server often holds one player. When the last player leaves, Roblox shuts the server down. Threads that are still yielding are dropped unless `game:BindToClose` holds the shutdown, for up to 30 s. Two cases fail. (a) A disconnect during the 45-step dying pause: the parked session needs about 3 s more of Heartbeat before `GameOver`, and the server is already closing. (b) GameOver while present, then f0065's tap to the lobby: `drive` is about 17 serial DataStore calls (3 boards × 2 `UpdateAsync`, the sorted read, up to 10 `GetAsync`s, plus backoff). The teleport can empty the server before the all-time write lands. The design promises both submits. No spec can see the shutdown, because no stub models it.
Critique: The tempting fix is a `BindToClose` in HiscoreStore that waits until no drive is pending. That covers (b) but not (a): the parked run has not called `submit` yet when the close begins.
Consequences: The close handler has to wait for two things: Submits' parked runs (until each one drops or submits) and HiscoreStore's in-flight drives. It needs a deadline under 30 s, and Heartbeat must keep stepping while it waits. It must not run in Studio play-solo shutdown loops forever. Sessions still requires only Maze and Session.
Recommendation: Add `HiscoreStore.pending(): number` (a counter incremented before the spawn and decremented after `drive`, also on error) and `Submits.pending(): number` (states held for parked sessions). Submits binds one `game:BindToClose` that loops on `task.wait` until both are 0 or 25 s have passed. Spec it in adapter.spec and sessions.spec with the stub `game` exposing `BindToClose`: a bound function exists; it returns only after a held drive is released; with a parked run it returns after that run's GameOver submit; it gives up at the deadline. Add a Risks line. If the author would rather not do this, the alternative is to drop "including if the player has disconnected" from decision 6 for solo servers and say so.

### F3 [medium] During a read outage every lobby client makes the server read twice a second, with no end
Where: R0011.md (Boards bullet, `lastFetch` per player; the LobbyView bullet: `failed == true` → `task.delay(READ_GAP)` → `FireServer("all")`); f0026.md line 82
Evidence: Prototype `Boards.luau` with `GetSortedAsync` erroring. Client asks, the server reads at sizes 10 then 50, both fail, and the server answers `failed = true`. One second later the client asks again. The player's own `lastFetch` gap (1 s) has passed, nothing is in flight (the error came back at once), so the server reads twice more. This repeats every second, for each lobby player, for as long as they stay. The GetSortedAsync budget is on the order of 5 + 2 × players a minute. That is about 120 reads a minute per player against roughly 7. The likeliest outage is throttling, and this loop keeps the budget exhausted. Review 002 F6's case "a healthy one never retries" is fixed, and its budget arithmetic now applies to the failure path. adapters.spec checks one retry per failed answer and never runs a second failure.
Critique: The tempting fix is a server-side gap per key after a failed read. That stops the DataStore cost, but the client still gets `failed = true` every second and still asks every second: a remote-event ping-pong with no end.
Consequences: The server needs a failure window per cache key. The client needs a bound on its retries. A stale-but-present cache should still be answered during the window. A recovery must still be seen without a rejoin. Day and week share the same mechanism.
Recommendation: Pure `Hiscores.lookup` gains a per-key `failedAt` (a failed fetch sets it). The key reads at most once per `READ_GAP * 2^k` after consecutive failures, capped at `CACHE_TTL`. A request inside that window gets the previous rows and `failed = true` without a read. LobbyView retries at most `Lobby.MAX_RETRIES` (3) consecutive failed answers, and any `failed == false` answer resets the count. read.spec: two failed fetches at t and t+1 call `fetch` once. adapters.spec: on an erroring store, 10 s of a client that keeps retrying causes at most `2 × ceil(log2(...))` reads, and a fourth consecutive failed answer schedules nothing.

### F4 [low] The design gives day and week buttons but no way back to the all-time board
Where: R0011.md LobbyView bullet ("Day and week are further `TextButton`s"); f0026.md line 82; adapters.spec "day and week are buttons…"
Evidence: An implementation that follows the text literally adds TODAY and THIS WEEK only. After a tap, the only route back to HISCORES is a failed answer, whose retry `FireServer("all")`s. That retry also yanks a player off TODAY whenever a day read fails. The prototype added an `all` tab on its own initiative.
Recommendation: Name three buttons (`all`, `day`, `week`, Text from `boardTitle`). The failed-answer retry asks for the board of the failed payload's `id`, not always `"all"`. adapters.spec: activating the HISCORES button sends `{ "all" }`; a failed `"day"` answer retries `"day"`.

### F5 [low] Two design rules have no case: parked sessions step per granted step, and the store's top read falls back to 50
Where: R0011.md ("The same advance loop steps each parked session once per step"; HiscoreStore `io.top` "on error once at `pageAttempt(2)`"); sessions.spec, adapter.spec
Evidence: On the prototype, moving the parked loop outside `for _ = 1, Session.advance(...)` (once per Heartbeat, even when advance returns 0) passes all 16 sessions.spec cases. Every parked case uses `dt = ONE`. Changing HiscoreStore's `for n = 1, 2` to `for n = 1, 1` passes all 7 adapter.spec cases. The failure case fails every size, and the success case never errors at 10. The effects are small: a parked run counts its pause in steps either way, and the 50 fallback only matters if E12's size 10 is rejected.
Recommendation: sessions.spec: one parked session, `frame(w, 2 / STEP_RATE)` steps it twice, and `frame(w, 0.5 * ONE)` steps it zero times. adapter.spec: a stub whose `GetSortedAsync` errors only at size 10 still produces a rank, and the stub records sizes `{10, 50}`.
