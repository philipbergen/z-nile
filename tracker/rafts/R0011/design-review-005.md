### F1 [medium] The per-player READ_GAP only ever applies across boards, and there it answers a healthy board as an empty failed one
Where: R0011.md Boards bullet (path 4: "nil rows inside the requester's gap … the previous rows (or `{}`) with `failed = true`"); f0026.md lines 76 and 80; `lastFetch` per player, not per key
Evidence: On the prototype, with Bea seeded on both `all` and `day:2026-10-16`, player 2 asks `"all"`, then `"day"` in the same `os.time()` second. Answers: `["all", [Bea, Ada], 1, false]`, then `["day", {}, nil, true]`, with 1 read. LobbyView draws TODAY / "No scores yet" for a board that has a row, counts a failure, and fixes it 1 s later. A player who taps HISCORES → TODAY → THIS WEEK quickly on stale caches (a quiet lobby) sees this every time. The gap does nothing else. After a successful read the cache is fresh for 15 s, which is longer than the gap. After a failed one the failure window (2 s or more) covers the gap. So for one key the gap is never the deciding test, except at a period rollover. Replacing `lastFetch[player]` with `nil` in Boards' `lookup` call passes all 119 cases (mutant boards-cross-key-gap-off): no adapter case exercises the gap. The gap also undoes part of review 004 F4. Boards writes `lastFetch[player] = last` after the yielding read, so a requester who leaves while their own read is in flight is put back into the map that `PlayerRemoving` just cleared.
Critique: The tempting fix is to make path 4 answer "not yet" differently, or to defer the answer until the gap passes. That adds a timer or a fifth answer kind to a mechanism that already has four paths, to keep a guard that protects nothing.
Consequences: Without the gap, one player's reads are bounded by the in-flight flag, the 15 s cache and the failure window, per key. That is at most three keys (the client can't choose a period), so three reads per 15 s, or one per failure window during an outage. Then nothing in Boards uses `lastFetch`, and the `PlayerRemoving` connection and its source check go away. `lookup` keeps its `lastFetch` parameter (read.spec pins it as pure policy), and Boards passes nil. Keying `lastFetch` by player and key would also fix the wrong answer, but it keeps the leak and is still unreachable for a single key.
Recommendation: Boards calls `lookup` with `lastFetch = nil` and keeps no per-player state. Say so in R0011 and f0026 (path 4 becomes "inside the key's failure window"), and drop F4's `PlayerRemoving` / `lastFetch[player] = nil` sentences and source check. The "departed waiter gets no answer" part stays. adapters.spec gets a case: seeded `all` and `day`, one player asks `"all"` and then `"day"` in the same second, and gets two healthy answers with the day row and `failed = false`, from 2 reads. Add a Rules row with the mutant "a per-player gap across boards".

### F2 [medium] Nothing checks which companion store Boards opens, so a lobby that reads the wrong DataStore passes every case
Where: `tracker/issues/f0026/acceptance/adapters.spec.luau:272` (`GetDataStore = function(_: any, _name: string, scope)`: the name is ignored); the source needles at `:477` do not include `Hiscores.storeTarget`; R0011.md "Both adapters open stores with `Hiscores.storeTarget`"
Evidence: Mutant boards-companion-wrong-name, `GetDataStore(orderedName, scope)` in Boards (so the companion opens as `"Hiscores"`), passes all 119 cases. The ordered name is pinned (`reads[1].name == "Hiscores"`), and HiscoreStore's companion name is pinned in f0024 `adapter.spec`, but the lobby's companion name is not. On a live server, `GetDataStore("Hiscores", "all")` is a different, empty store. Every companion is absent and skipped, and every board is a healthy `{}`: the lobby shows "No scores yet" forever, with `failed = false`, so it never retries. Only OC1 on Beta would see it.
Critique: The lobby read is the point of f0026, and its store name has no check. The tempting fix is a source needle for `"HiscoreEntries"`. That pins a literal the design forbids (names come from `storeTarget`), and it doesn't pin which call uses it.
Consequences: none beyond the stub recording one more field.
Recommendation: The stub's `GetDataStore` records `{ name, scope }`. The healthy-read cases assert that every companion open is `("HiscoreEntries", "all")`, and the day case asserts `("HiscoreEntries", "day:2026-10-16")`, the same values `Hiscores.storeTarget("companion", board, true)` returns. Add `Hiscores.storeTarget` to Boards' source needles. Add a Rules row with the mutant "companion opened under the ordered name".

### F3 [medium] "A tap resets the failure count" has no case
Where: R0011.md LobbyView bullet ("A tap sets `wanted`, resets the failure count and asks"); f0026.md line 86; f0026 Rules table (no row)
Evidence: Mutant lobby-tap-keeps-failures (remove `failures = 0` from the button handler, keep `wanted = id` and the ask) passes all 119 cases. With the mutant, after one failed HISCORES answer a tap on TODAY whose answer fails retries after 2 s instead of 1. After the three retries have stopped, a tap whose answer fails never retries at all, so one failure leaves that board on "No scores yet" with no retry.
Critique: The rule is in the design and in the prototype, but nothing would keep it there.
Consequences: none.

### F4 [low] The 50-entry fallback page makes every read 50 companion reads, and any one of them failing fails the board
Where: f0024.md Scalability ("one ordered page of 10 and at most 10 companion reads"); f0026.md Scalability ("at most 10 companion gets"); `rows` looks up every page key, not just the first `n`
Evidence: When page size 10 is rejected (the E12 fallback), `io.top` and Boards read 50 entries, and `rows` calls the getter for each new key, so up to 50 `GetAsync`s per read. A game server's StandardRead budget is 60 + 10 × players a minute, so one submit on a solo server spends most of it on lookups. Since review 004 F2, one refused or throttled lookup makes `rows` nil, so the rank is lost (drive) or the board fails (Boards). This happens even when the failing key is far below the top 10, where it cannot change any shown row.
Recommendation: Either have the adapters truncate the `scorePage` output to `N` entries before `rows` (the page is already in packed order, so the top N keys are the first N), or state that the fallback costs up to 50 reads in both Scalability sections and in Risks. If you truncate, a skipped (absent or mismatched) companion can leave the board shorter than `N`, which "a short page is not padded" already allows. Then f0024 `adapter.spec`'s "rejects page size 10" case asserts at most `N` companion reads after the fallback, and so does a 50-entry Boards case in f0026 `adapters.spec`.

Verdict: changes
