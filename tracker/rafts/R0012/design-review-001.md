### F1 [high] look.spec's zero-delta case fails a pure fold and passes a mutating one
Where: tracker/issues/f0028/acceptance/look.spec.luau:29-40; rule in tracker/rafts/R0012/R0012.md:92 and tracker/issues/f0027/f0027.md:70; immutability pin in tracker/issues/f0027/acceptance/track.spec.luau:63-67
Evidence: The case discards the state returned by the move to (530, 190), then calls `Touch.track` again with the begin state still at (500, 200) and expects `{ dx = 0, dy = 0 }`. A pure fold, the one the raft specifies, returns `{ dx = 30, dy = -10 }` for that second call. The same calls against a fold that writes the finger in place return `{ dx = 0, dy = 0 }` and go green: the discarded first move has already set the shared finger to (530, 190). `track.spec`'s only immutability case is a begin on `Touch.empty()`, which that mutant still passes. So f0027's and f0028's checks accept the forbidden implementation and reject the required one. The rules row marks the zero step `reasoned` and says the prototype passed it; this spec never tracks the same point twice on the returned state.
Critique: The tempting fix is to delete the `{ dx = 0, dy = 0 }` assertion, or to "make the test pass" by mutating the finger. Either one ships a fold whose caller cannot reuse a prior state, which is the property the acceptance tests themselves rely on when they branch (`local _, first = Touch.track(state, …)` and then track `state` again).
Consequences: Threading only the returned state makes both the pure fold and the in-place mutant pass, because the mutant's returned state already has the new point. A module-level last position does the same without touching the table. The zero-delta rule is then still unenforced, and so is "the input state is unchanged" for move and end.
Recommendation: Thread the returned state: begin, move to (530, 190) expects `{ dx = 30, dy = -10 }`, the same point again expects `{ dx = 0, dy = 0 }`, then the move to y = 10190 expects `{ dx = 0, dy = 10000 }`. Add two cases to `track.spec` and a rules row marked for them. First, a move and an end leave the input finger's `x`, `y`, and `zone` unchanged and return a different table. Second, two separate tracks of one begin state to the same move both return `{ dx = 30, dy = -10 }`, so a module-level cursor cannot satisfy the zero step. Keep the existing begin-on-empty case.

### F2 [high] the snap far-edge case expects look where the zone rule returns turn
Where: tracker/issues/f0028/acceptance/hit.spec.luau:34-38; the rule in tracker/rafts/R0012/R0012.md:73-74 and tracker/issues/f0027/f0027.md:56; the matching pin in tracker/issues/f0027/acceptance/track.spec.luau:35-40
Evidence: `SNAP` is `{ x = 300, y = 700, w = 44, h = 44 }` and the viewport width is 800, so the split is `x < 400`. The inside points (300, 700) and (343, 743) are snap. The outside points (344, 720) and (320, 744) are outside that half-open rect and still on the left half, so `Touch.zone` is `"turn"`. The spec expects `"look"` for both. f0027 pins the same shape the other way: outside `(800, 54, 30)` and `(800, 30, 64)` are `"turn"`. No implementation of the written rule turns both specs green. A zone function edited until hit.spec passes fails track.spec.
Critique: Changing the expectations to `"look"` by special-casing those coordinates, or moving the split so that x = 344 is the right half, breaks the locked rule `x < width/2` and f0027's half pins (399/400 and 194/195). The half-open edge itself is already pinned correctly by the inside point (343, 743); the bug is only the zone of the outside point.
Consequences: Expecting `"turn"` kills "the far edge is inside" but does not kill a mutant that returns `"look"` for every point outside the rect. The button in this case sits on the left half, so the outside point is a turn, and a finger that begins there must still be able to swipe.
Recommendation: Keep width 800 and expect `"turn"` at (344, 720) and (320, 744). Add the right-half pair the other case already uses, width 390: (344, 720) and (320, 744) are `"look"`, and (300, 700) stays `"snap"`. One rules row covers both, so a mutant that paints every outside point `"look"` fails the left pair and a mutant that paints the far edge `"snap"` fails both. f0028's "far edge is look" wording in the rules table has to say "look only on the right half".

### F3 [high] ScreenInsets.None plus GetGuiInset puts the HUD under the notch, and AC3 requires that pair
Where: tracker/issues/f0029/f0029.md:106-107 and :184 and :222 and :232; tracker/rafts/R0012/R0012.md:162 and :192; tracker/issues/f0029/acceptance/place.spec.luau:29-31. Today's HudView sets neither property (src/client/HudView.luau:64-93), so it stays on the default `CoreUISafeInsets`.
Evidence: `GuiService:GetGuiInset` is documented as the inset applied to a ScreenGui whose `IgnoreGuiInset` is false, two Vector2s from the top-left and the bottom-right. It is not the device cutout. `GuiService:GetInsetArea` is the API that is, and its documented sample is relative to the core-UI origin: `GetInsetArea(None)` is `-59, -58, 792, 334` and `GetInsetArea(CoreUISafeInsets)` is `0, 0, 733, 313`. In viewport pixels that is a screen of 851×392, insets left 59, top 58, right 59, bottom 21. A top-bar-only `GetGuiInset` does not include the 59px sides or the 21px bottom. `ScreenInsets.None` is documented to leave UI under the notch and the core controls, and to be for non-interactive content. The snap button and the score are interactive. Setting `IgnoreGuiInset = true` while `ScreenInsets` is still `CoreUISafeInsets` also rewrites `ScreenInsets` to `DeviceSafeInsets`; the design never says which assignment wins. E5 asks whether the top bar is subtracted twice. It does not ask whether the notch is in the number, it was not run, and its fallback (pass zeros) fails the `GetGuiInset` substring, so the author is told to stop rather than to use the inset API. The place spec then requires `GetGuiInset` and `ScreenInsets.None`, so the implementation that clears the notch fails AC3 and the one that does not passes it. Layout specs pass a literal `{ top = 47 }` and never see this.
Critique: The tempting fix is to keep `GetGuiInset` and also set `ScreenInsets.CoreUISafeInsets` on the ScreenGui. The engine then insets the GUI, the manual inset shifts it again, and touch positions (viewport pixels) no longer match `Touch.snapRect` (GUI pixels). The button is visible in the margin and `Touch.zone` misses it. Dropping the manual inset and leaving the default `CoreUISafeInsets` avoids the double shift but leaves touch and the rect in different spaces, which is the same miss.
Consequences: `GetInsetArea` rects are relative to the core-UI origin, not the viewport. Treating `Core.Min` as the inset yields `(0, 0)` on the sample and the notch is back. Negating the wrong rect (`None.Min` used as a positive inset) yields a negative left, and `side()` turns that into 0, so the HUD does not move and the spec still looks calm unless the sample is pinned. `AbsolutePosition` is in the core-UI coordinate system, so reading it back to build the snap rect disagrees with `InputObject.Position`. `SafeAreaCompatibility` defaults to `FullscreenExtension`, which can move a large frame even after the labels are placed correctly. `ClipToDeviceSafeArea` does nothing once `ScreenInsets` is `None`. The first frames can report an empty area, same as `GetGuiInset` today.
Recommendation: Keep the ScreenGui on `ScreenInsets.None` and `IgnoreGuiInset = true`, set after each other so the `IgnoreGuiInset` side effect cannot restore `DeviceSafeInsets`, and set `SafeAreaCompatibility` to `None` (cast `Enum` if the type library lacks it). Do not read `GetGuiInset`. Add a pure `Hud.safeInset(none: Rect, core: Rect): Inset` with no engine words: `left, top = -none.Min`, `right = (none.Max.X - none.Min.X) - (core.Max.X - core.Min.X) - left`, and the same for bottom, then the existing `side()` on each component. Pin the documented sample: none `(-59, -58)-(792, 334)`, core `(0, 0)-(733, 313)` returns `{ left = 59, top = 58, right = 59, bottom = 21 }`. Pin a matching pair (none equal to core) as all zeros, so a constant 58 fails. Pin the negation mutant: feeding `none.Min` through without the minus sign returns zeros after `side()` and fails the 59. The adapter passes `GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets)` and `GetInsetArea(Enum.ScreenInsets.None)` into that function and then into `Hud.layout`. The place spec, comments stripped, requires the substrings `GetInsetArea(Enum.ScreenInsets.CoreUISafeInsets` and `ScreenInsets = Enum.ScreenInsets.None` (the cast form `(Enum :: any).ScreenInsets` allowed) and requires `GetGuiInset` to be absent. `PickmanHud` still re-lays when any of the four numbers changes, including from the first-frame zero to the real area. E5's pass/fail becomes: in the Studio device emulator, `ViewportSize` equals the None rect's size, the score is below the notch and the top bar, the snap control is above the home indicator, and a touch on the button's pixels is `Touch.zone` `"snap"` without reading `AbsolutePosition`. If those disagree, stop and report. Do not take the zero-inset fallback.

### F4 [medium] the rejected above-the-bar button passes every sample
Where: tracker/issues/f0029/f0029.md:80 and the rules row at :220; tracker/rafts/R0012/R0012.md:104 and E4 at :191
Evidence: The fallback runs only when the primary rect overlaps a block, then sets `y = safeY + safeH - 2*margin - barHeight - side`. Every pinned sample satisfies `safeW >= 2 * (2*margin + barWidth + side)`, so the primary rect misses the blocks and the branch never runs. `button.spec` therefore passes with the fallback still in the file. The row claims that mutant was `run`. On a box the samples do not cover (margin 5, icon 10, bar 40×4, text 10, safe 100×300 at the origin) the primary rect is `{ x = 6, y = 251, w = 44, h = 44 }` and it overlaps lives; the fallback y is 242, which is inside the forward view (`y` from 20 to 251). That is the E4 failure, and no spec asserts it.
Critique: Copying `proto.luau` is the path the raft warns against, and it is green. Deleting the fallback without a narrow pin leaves the next edit free to put it back. Moving the narrow button until it misses lives puts it in the forward view again, which is the bug E4 measured.
Consequences: The primary rect on that box overlaps lives and extends to x = 50, which the design already allows for a narrow safe width. A spec that only asserts "no overlap with lives" forces the fallback. A spec that only asserts "h > 0 for the forward view" passes the fallback too, because the forward rect in the spec is built from `button.h` and still misses a button that was moved up if the test uses the returned button to define the view.
Recommendation: Pin this box to `{ x = 6, y = 251, w = 44, h = 44 }` and assert it overlaps lives and does not overlap a forward rect computed from `max(iconSize, barHeight, MIN_TARGET)`, not from a y the function just returned. Add the row, `reasoned` until it is run: the mutant is the fallback y, and this case is what kills it. Keep the three sample pins as the cases that do not overlap.

### F5 [medium] a second snap finger is ignored only on the input table
Where: tracker/issues/f0028/acceptance/hit.spec.luau:65-78; the rule "emits nothing and adds nothing" in tracker/rafts/R0012/R0012.md:92 and tracker/issues/f0028/f0028.md:68
Evidence: The case discards the state returned by the second begin and asserts `again` is empty and `state.fingers[2] == nil`. `state` is the input. A pure fold that stores finger 2 on the returned state passes. Snap move and snap end emit nothing, so the stored finger never shows up in an effect list either. track.spec kills a stored second turn finger and a stored second look finger, because those emit. It has no second snap id. The adapter counts the returned fingers for `onTouch`. After the real finger ends, the extra snap finger keeps the count above zero, so `Camera.holdMouse(true)` stays and the mouse delta stays suppressed until that second finger ends.
Critique: Asserting only `again == {}` is the tempting fix, and it is what the spec does now. The finger is still down.
Consequences: Replacing finger 1 instead of adding finger 2 also emits nothing on the second begin. The first finger's later end is then an unknown id and emits nothing, and the replacement finger holds the zone. A check that only reads `fingers[2]` misses the replacement.
Recommendation: Capture the returned state. After the second begin, `fingers[1]` is still the original snap finger and `fingers[2]` is nil. End finger 2 with a long horizontal move and expect no effect. End finger 1 and expect no fingers left. One rules row: a second snap begin adds nothing to the returned state. The turn and look occupancy cases already in track.spec stay the other two zones.

### F6 [medium] holdMouse, gameProcessed, and the Controls.start order are not what the checks pin
Where: tracker/issues/f0028/acceptance/place.spec.luau:23-39; tracker/issues/f0027/acceptance/place.spec.luau:29-35; the branches in tracker/issues/f0027/f0027.md:83, tracker/issues/f0028/f0028.md:34-51, and tracker/rafts/R0012/R0012.md:160-163. The render step they edit is src/client/Camera.luau:54-60.
Evidence: f0028 AC3 passes if the names `GetMouseDelta`, `View.look(`, `function Camera.lookBy(`, `function Camera.holdMouse(`, `Camera.lookBy`, and `Camera.holdMouse` occur anywhere. `function Camera.holdMouse(_held: boolean) end` plus the render step as it is today (`GetMouseDelta` always passed to `View.look`) passes, and so does `Controls.start(Camera.snap, Camera.holdMouse, Camera.lookBy)`, which contains every name and passes `holdMouse` where `onLook` is. f0027 AC3 passes with `if gameProcessed then return end` above `Touch.track(`, because the required substrings are still in the file. None of those mutants is in a rules row. The prose also describes two suppressions: `lookBy` "notes that a touch look was applied this frame", and `holdMouse` skips the mouse delta while any finger is down. Only the second has a rule. A turn finger never calls `lookBy`, so a flag set only there does not cover a swipe. E6's own fallback (always apply the mouse delta) is source-identical to the empty `holdMouse` and would ship without failing a check.
Critique: A looser pin, or leaving this to OC1, does not hold. OC1 is one phone-sized viewport; a doubled look and a swipe that dies on the score label are both easy to miss, and both are source-checkable. The testing skill's rule is that a measurable branch is not Observed.
Consequences: Input can begin and end before `PickmanCamera` runs. `onTouch(false)` has then already cleared `holdMouse`, and that frame's `GetMouseDelta` still carries the touch, so a same-frame tap is applied twice unless a latch set by `lookBy` survives until the render step. The latch has to clear on the early `if snap == nil then return` at Camera.luau:58 as well as on the normal path, or one touch look suppresses the mouse for the rest of the session. Forbidding the identifier `gameProcessed` means the callback's second parameter is `_`. A later text box that must swallow a gesture cannot do it inside this `Controls.start`; that is a new issue, not a branch added under this spec.
Recommendation: One flag, `mouseHeld`, set only from `onTouch`. One latch, `lookedThisFrame`, set true in `lookBy` and cleared at every exit of the render step, including the nil-snapshot return. The step always calls `GetMouseDelta()` and passes the delta to `View.look` only when `not mouseHeld and not lookedThisFrame`. Delete the unspecified per-frame note as a second mechanism. Spec pins, comments stripped: `Controls.start(Camera.snap, Camera.lookBy,` in Main (f0029's `HudView.snapRect` sits in the third argument; f0028's nil still matches this prefix), `GetMouseDelta()` present, and `View.look(` of that delta only in the not-held branch. `gameProcessed` does not occur in Controls.luau. Add the rules rows for those three mutants. Taking E6's fallback fails the branch pin, which is the stop-and-report the experiment already asks for.

Verdict: changes
