### F1 [high] touch positions arrive in the GUI-inset space, but the snap rect is in screen pixels, so on the documented landscape phone a tap on the drawn button is never "snap"
Where: tracker/issues/f0029/f0029.md:125 ("Do not build the snap rect from `AbsolutePosition` (that space is the core-UI origin, not `InputObject.Position`)"); R0012.md:172 (Controls passes the event position and `snapRect()` straight to `Touch.track`) and :174; E5 (R0012.md:211, f0029.md:267, "not run in Studio").
Evidence: Roblox's `InputObject.Position` reference says: "For mouse and touch input, this is the screen position of the mouse/touch ... The inset applied to GUI elements (such as from the top bar) is accounted for in the position." `UserInputService:GetMouseLocation`, by contrast, "does not account for the `Enum.ScreenInsets`". So a touch's `Position` is measured from the core-UI origin, which is the same origin as `AbsolutePosition` and as `GetInsetArea` (the documented core area is `(0,0)-(733,313)`, and None is `(-59,-58)-(792,334)`). HudView draws in `ScreenInsets.None`, so `Touch.snapRect` is in screen pixels. Take the landscape sample (left 59, top 58). The button is drawn at screen x 583 to 627 and y 337 to 381. A finger on those pixels reports `Position` x 524 to 568 and y 279 to 323. Every point misses the rect, so the tap is `"look"` (or `"turn"`) and never `"snap"`. The 58 px offset is larger than the 44 px button. On a phone with a plain 36 px top bar, only the bottom 8 px of the button would work. The half split in `Touch.zone` moves too: the split at `ViewportSize.X/2 = 422` lands at screen x 481. No spec can see this: every Touch spec feeds positions and rects in one space. E5 is the only guard, and it needs the Studio device emulator, which a headless executor cannot run. Its fallback is "stop and report". The design text also asserts the opposite of the documentation, so an executor who skips E5 ships a snap button that does not work on any phone with a top inset.
This is the third round with a hole in the coordinate-frame mechanism: review 001 F3 (GetGuiInset under the notch), review 002 F1 (DangerHud's frame against HudView's), and now the input frame. Each fix patched one pair of spaces at the place where it was found.
Critique: The tempting fix is to shift the rect inside `HudView.snapRect()` by `(-left, -top)`. That fixes snap, but it leaves the half split in screen-minus-inset space, and it adds a fourth place that knows about frame offsets (HudView's layout, DangerHud's `bandTop`, HudView's snapRect, plus Controls' width).
Consequences: There are four spaces: screen (None), the device safe area (DangerHud), the core-UI safe area (HudView's blocks and the touch GUI), and the GUI-inset origin (input, `AbsolutePosition` and `GetInsetArea`). Each conversion needs a sign, and the round-2 bug and this one were both wrong in the same way, an offset applied in one place and not in another. Converting the input point also changes what `Touch.zone`'s `width` means: the screen width with screen x, which is consistent. f0027's specs feed screen-space points directly, so they stay valid. The conversion must be read every event or every frame, because rotation changes `GetInsetArea`.
Recommendation: Question the mechanism, and pick one canonical space. Make it screen pixels (`ScreenInsets.None`, origin top-left of the device screen): every Logic rect (blocks, snap, jump buttons, the radar after DangerHud's own frame offset) and every input point fed to `Touch.track` is in it. Add one pure conversion, for example `Hud.toScreen(none: Area, x: number, y: number): (number, number)` returning `x - none.Min.X, y - none.Min.Y`, and use it in Controls on every touch event (`GetInsetArea(Enum.ScreenInsets.None)` read there, `(Enum :: any)` cast allowed). Name the four spaces once in the raft's whole-raft design, with the one conversion each uses. Correct f0029.md:125 and R0012.md:174: `AbsolutePosition`, `InputObject.Position` and `GetInsetArea` share the GUI-inset origin; the reason not to use `AbsolutePosition` is only that the rect comes from Logic. Specs: in a pure case, `toScreen` of the documented None area maps `(524, 279)` to `(583, 337)`, and that point is `Touch.zone(844, ..., button)` `"snap"`. A zero-offset area is the identity. Add a mutant row for "positions passed unconverted", which the pinned point kills. Add a Controls source pin that `GetInsetArea` and `Hud.toScreen(` (or the chosen name) occur and come before `Touch.track(`. Keep E5's emulator check as confirmation: tap the button and see snap. A mismatch there is still stop-and-report, but the design no longer bets against the documentation.
