### F1 [high] the canonical space is "measured by `ViewportSize`", but Roblox documents `ViewportSize` as the device safe area, so on a notched phone the HUD is laid out in a frame 118 px too narrow and the touch half split is off by the notch
Where: R0012.md:88 ("The canonical space is screen pixels ... `ScreenInsets.None`, measured by `ViewportSize`") and the table row at :92 (`ViewportSize` in the screen row, identity); R0012.md:185 (Controls passes `ViewportSize.X` to `Touch.track`); f0029.md:126 (`Hud.layout(ViewportSize.X, ViewportSize.Y, inset)`); f0027.md:60 (screen pixels are what "`ViewportSize.X` measures"); E5 at R0012.md:224 (pass/fail "`ViewportSize` equals the `ScreenInsets.None` rect's size"); jump.spec.luau:243-247 and screen.spec.luau:16 (`WIDTH = 851`), which feed the full screen size as the layout and zone width.
Evidence: creator-docs `Camera.ViewportSize`: "returns the dimensions of the device safe area on the current screen. This area is a rectangle which includes the Roblox top bar area but does not include any device notches or screen cutouts ... `ViewportSize` is not equal to the fullscreen area size on displays with cutouts or notches. To obtain the fullscreen area size on all displays, you can query the `AbsoluteSize` of a `ScreenGui` with `ScreenInsets` set to `None`." `ScreenInsets.CoreUISafeInsets` is documented as "core UI insets added to the `DeviceSafeInsets` area". On the documented phone (None `(-59,-58)-(792,334)`, core `(0,0)-(733,313)`), the device safe area is about 733×371 (the notch sides and the 21 px home indicator removed, the top bar kept), not 851×392. HudView would then call `Hud.layout(733, 371, {left 59, top 58, right 59, bottom 21})` and draw the result in a `ScreenInsets.None` gui. Computed with today's `Hud.layout` plus the design's safe-rect, bar and snap formulas (`$TMPDIR/.../c/.cache/r4/vp.luau`):
- Design (None size 851×392): text 18, bar 183, snap `{547,318}`, power bar x 600–783, y 355.
- Real (ViewportSize 733×371): text 17, bar 154, snap `{458,297}`, power bar x 511–665, y 334.

So level, power and snap end 127 px left of the usable right edge (screen x 792), and the bottom row sits 21 px high. jump.spec's "landscape, under a 58 px top bar" sample (844×390) has the same shift: snap `{541,316}` against `{453,295}`. `Touch.track`'s width is 733 while its points, after `Touch.toScreen`, are screen pixels, so the split falls at screen x 366, not the middle (425). A finger at screen x 400 on the left half looks instead of turning. This is the mismatch round 3 fixed for the points, now on the width. The snap tap itself still works, because the drawn rect and the converted touch are both in None space. In portrait (390×844 with a 47 px notch and a 34 px home indicator) `ViewportSize.Y` is about 763, so the bottom row floats about 81 px above where the design puts it. No spec can see any of this: every spec passes the full screen size as a literal. E5's own pass/fail ("ViewportSize equals the None rect's size") fails by documentation, so a careful executor hits stop-and-report in Phase 1, and a hasty one ships the shift. DangerHud is unaffected: it reads `gui.AbsoluteSize` of its device-safe gui, which is the frame its row of the table names.
This is the fourth round with a hole in the coordinate-frame mechanism: review 001 F3 (GetGuiInset), 002 F1 (DangerHud against HudView), 003 F1 (input points), and now the size that defines the canonical space. The round-3 table was written from the design, not checked row by row against the documentation. Its first row is wrong. Its claim that "every point and rect Logic sees for ... the jump buttons ... is in [screen pixels]" also contradicts f0029, where `Hud.radarBox` measures the jump buttons in DangerHud's device frame `(0, band, width, height - band)`. The behavior there is consistent; the table is not.
Critique: The tempting fix is to swap `ViewportSize` for HudView's `gui.AbsoluteSize` in HudView only. That fixes the layout and leaves Controls' width on `ViewportSize`, which is a fifth pair of spaces patched in one place. A second tempting fix is to delete `ViewportSize` from HudView. That fails `tests/acceptance/f0019/place.spec.luau:61` and f0029's place.spec:31, which require the substring (as the re-layout signal).
Consequences: The fullscreen size has to come from one source for both adapters. `GetInsetArea(None)` is already read per event in Controls and per frame in HudView, and its size (`Max - Min`) is the fullscreen size. The documented first-frame empty area then gives a 0×0 screen: `Hud.layout` of 0×0 and a `Touch.zone` width of 0 (every point "look"). So the helper needs a fallback, either `ViewportSize` with a zero inset or the previous good value. On a screen without cutouts, `ViewportSize` equals the None size, so the fallback is exact there. `ViewportSize` stays in HudView only as the change signal, which keeps both substring pins green. E5 changes: in the emulator, `ViewportSize` is the None size minus the notch and home-indicator insets.
Recommendation: Question the mechanism as well as fix the row. Every row of the spaces table names the documentation sentence that defines it. Move `ViewportSize` (and `gui.AbsoluteSize` of an `IgnoreGuiInset` gui) to the device-safe row. The screen row is measured by `GetInsetArea(None)`'s size, or by the `AbsoluteSize` of a `ScreenInsets.None` gui, as the docs say. Correct the "every rect Logic sees" sentence: `Hud.radarBox` and its jump buttons are in DangerHud's device frame. Add one pure helper used by both adapters, for example `Hud.screenSize(none: Area?, fallbackW: number, fallbackH: number): (number, number)`. It returns `none.Max - none.Min` when both sides are positive and finite, else the fallback. HudView calls `Hud.layout(w, h, inset)` with it, with the inset forced to zero when the fallback was used. Controls passes its `w` as `Touch.track`'s width. Touch does not require Hud; Controls, an adapter, may require Hud.
Spec cases: the documented None area returns 851, 392; an empty `(0,0,0,0)` area and a NaN component return the fallback. A place pin that HudView's `Hud.layout(` line does not contain `ViewportSize` (`not string.find(src, "Hud%.layout%([^\n]*ViewportSize")`) and that `ViewportSize` still occurs. A Controls pin that the width in the `Touch.track(` call comes from the helper, not `ViewportSize.X`. Mutant rows: "layout from ViewportSize" (killed by the place pin) and "zone width from ViewportSize" (killed by the Controls pin). In screen.spec, a case where `ViewportSize`'s 733 against screen points puts screen x 400 on "look" while 851 gives "turn", so the row has a case that shows the difference. Rewrite E5's pass/fail to the documented relation. Before the next round, re-derive each row of the table from the fetched docs, not from the earlier rounds' text.

### F2 [high] AC5's Controls pin passes an implementation that reads the None area once at start, or one that converts a point it never uses
Where: tracker/issues/f0027/acceptance/place.spec.luau:39-62; the rules row "Controls converts before its one `Touch.track(`" (f0027.md, Rules and mutants, `reasoned`); f0027.md:91 ("Read `GuiService:GetInsetArea(Enum.ScreenInsets.None)` on each touch event (rotation changes it)"); E5's "the first frames can report an empty area".
Evidence: The pin checks that `Touch.toScreen(` occurs before the single `Touch.track(`, that `GetInsetArea(Enum.ScreenInsets.None` occurs, and that the text `x = input.Position.X` is absent. Both of these pass every assertion:
- Cached area: `local none = GuiService:GetInsetArea(Enum.ScreenInsets.None)` in `Controls.start` body, then `local x, y = Touch.toScreen(none, input.Position.X, input.Position.Y)` in the handler. `Controls.start` runs in Main before `ready:FireServer()`, which is the first-frame window in which the design itself says the area can be empty. If it is empty, `toScreen` is the identity for the whole session, and the 58 px offset round 3 fixed is back. Rotation never updates it either.
- Converted but unused: `local _sx, _sy = Touch.toScreen(GuiService:GetInsetArea(Enum.ScreenInsets.None), 0, 0)` and an event `{ id = id, phase = phase, x = pos.X, y = pos.Y }` with `local pos = input.Position`.

Neither is in the mutant column. The row lists only the literal `x = input.Position.X`, converting after tracking, and a second `Touch.track(`.
Critique: The tempting fix is to forbid more spellings (`pos.X`, `p.X`), which is endless. The other tempting fix is to leave the per-event read to E9's Phase 1 tap. That tap passes whenever the area happened to be ready at start, so it does not catch the cache.
Consequences: Pinning the data flow fixes both mutants. Tie the `GetInsetArea` read into the `toScreen` call, and tie the event's fields to its results. After F1, the same per-event read also yields the width, so the pin covers the width source too.
Recommendation: Replace the substring checks with a flow pin on comment-stripped source. `local a, b = string.match(src, "local%s+([%w_]+)%s*,%s*([%w_]+)%s*=%s*Touch%.toScreen%(%s*GuiService:GetInsetArea%(")` (allow the `(Enum :: any)` cast inside) must match. Then the `Touch.track%b()` argument text must contain `x = <a>` and `y = <b>`. The inline `GetInsetArea(` read inside `toScreen(` cannot be hoisted to `start` without losing the input. Add the two mutants above to the rules row and mark it `run` once they have been tried on the prototype Controls (the place loader reads the source, so a scratch clone with a stub Controls is enough).
