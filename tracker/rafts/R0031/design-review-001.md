### F1 [high] appendOnly's "old rows equal, field by field" can be passed by a comparison that ignores phase, tokens, subject, when and attribution
Where: c0084.md "The ledger", appendOnly bullet; Rules and mutants row "append-only: old rows equal…"; acceptance/ledger.spec.luau "accepts only appended rows…"; spend-command.spec "the publisher takes only appended rows…"
Evidence: I copied experiments/ledger.luau to scripts/tracker/ledger.luau and cut `same(a, b)` down to `a.added == b.added and a.removed == b.removed and tenths(a.minutes) == tenths(b.minutes)`. ledger.spec still passed 10/10. Every "old row changed" case edits only `minutes` (ledger.spec `edited[1].minutes = 2`, spend-command `edited[1].minutes = 0.5`). With that mutant, a published change could relabel old build rows as `capture`, add or change their tokens, or rewrite their subject or date, and the publisher would accept it.
Critique: the append-only rule is what makes the new direct-push exception safe ("a bad writer cannot rewrite spend history on `main`", Risks). Those history rewrites would also feed straight into the new per-phase metrics and the rework figure. The author will be tempted to add one case that edits `phase`.
Consequences: one case for one field still leaves the other four. Tokens also have a nil and empty-cell case that a sloppy comparison (`(a.tokens or 0) == (b.tokens or 0)`) would treat as equal to 0, which turns "no tokens reported" into "0 tokens".
Recommendation: in ledger.spec "accepts only appended rows…", add a refused case for each field of an old row (`when`, `subject`, `how`, `phase`, `tokens` nil→0 and 0→5, `removed`), each with a row appended so that only the field rule can refuse it. Add a run row to Rules and mutants: "same() compares numbers only" is killed by those cases.

### F2 [high] AC7 fails for the implementation the design describes: store.luau names spend.md and requires neither ledger nor spend
Where: c0084/check.sh `one_ledger_format` (AC7); scripts/tracker/store.luau:3 (also on origin/R0025-ready-raft)
Evidence: AC7 loops over `grep -lF "spend.md" scripts/tracker/*.luau` and requires each of them to `require("./ledger")` or `require("./spend")`. store.luau mentions `spend.md` in its layout comment ("(+ check.sh, spend.md, reviews)") and requires only `./status`. It can't require `./spend` without a cycle (spend requires store). store.luau isn't in Touched modules, and the design never mentions it. Following the documents, AC7 is red, and the sequestration rule tells the executor to stop and escalate. The check is also weak the other way: main.luau already requires `./spend`, so it would pass AC7 even if it parsed rows itself. So would a board.luau that splits cells on `|` without the literal `| when | commit |`.
Critique: the tempting fix is to delete the comment in store.luau during execution. That's an edit outside Touched modules, made to satisfy a check, and it leaves the false-pass direction alone.
Consequences: if the check instead excludes comments, it needs a comment-stripping rule in bash. Requiring a `ledger.` call is closer to the intent.
Recommendation: rewrite AC7 so that, for each module other than ledger.luau, it fails on any row-splitting construct over spend text (for example `gmatch` with `|` next to a spend read). Simpler: each module that reads or writes a `spend.md` path through `fs.readFile` or `fs.writeFile` must call `ledger.` (grep for `ledger%.parse|ledger%.append|ledger%.render`). Skip comment lines (`^%s*%-%-`) before matching. Add store.luau's comment to the Regression guard so the executor knows it exists. Run the rewritten AC7 against R0025's tree with the prototype in place, so it is red only for the right reasons.

### F3 [high] No guard that `ready` and `stop` still move items that carry a published spend.md
Where: c0084 Design `publish.luau` ("checked before, and instead of, the status-line rule… c0067's move validation is untouched"); Test plan; Regression guard (c0067 publish-move, ready)
Evidence: after this raft every captured issue has a `spend.md` on origin/main (the capture row), and prep and design-review rows land there too. c0067's `moveOnOrigin` carries every file of the directory, `spend.md` included, as a `Change` with `from`. On origin/R0025-ready-raft, `publish.commit` skips per-change rules for moves (`if c.from then continue`). The design only says the new rule runs "before, and instead of, the status-line rule". If the executor places the `/spend.md` check before the `from` skip, or in validateMoves, a moved ledger has no appended row ("no row was appended"). A moved pre-c0084 ledger also isn't in canonical form. Either way, `ready` and `stop` refuse every item that has rows. No spec covers it: c0067's publish-move and ready fixtures have no member `spend.md` (ready.spec only checks the raft's after `start`), and none of c0084's four specs runs `ready` or `stop`.
Critique: this would break the main lifecycle path right after this raft lands, and the gate wouldn't notice.
Consequences: the fix also has to decide that a moved `spend.md` must be byte-identical (c0067's rule for ordinary files). A move combined with appended rows in one publish must be refused, which R0025's "a second change at a moved path is refused" already does.
Recommendation: add a case to spend-command.spec. Publish a capture row (and an old seven-cell ledger) for both members, then run `tracker.sh ready <raft>` (R0025) in the fixture: it succeeds, and `tracker/issues/active/<id>/spend.md` on origin equals the pre-move bytes. Then run `tracker.sh stop <raft>` and assert the same in the backlog. State in the publish.luau design that the ledger rule applies only to changes without `from`. Add a Rules and mutants row ("appendOnly applied to moves") and name c0067's `ready`/`stop` among the specs to run in E5.

### F6 [medium] The prep row has a dead end: once a raft is readied, `spend --phase prep` is refused and `commit` refuses `prep`
Where: c0084 Design `spend` step 3 (active items refused) and `commit` (capture, prep, design-review refused); ticket-prep §6 text
Evidence: prep is recorded "after the prep PR has merged and before the worktree is removed". Under R0025, `/ready-raft` can run in another terminal as soon as the prep merges, which moves the members to `active/` on origin. `spend <R> --phase prep` is then refused ("inside its raft, record with tracker.sh commit --phase"), and `commit --phase prep` is refused naming `tracker.sh spend`. The prep's lines and minutes (the counted spec and check.sh lines) can then never be recorded. Each refusal points at the other command.
Critique: this is the one phase whose recording window overlaps another terminal's normal action. The messages make the agent loop between the two commands.
Consequences: allowing `commit --phase prep` on the raft branch would need prepStats to run there (the prep diff isn't on that branch), which is more machinery. Asking first is simpler.
Recommendation: make ticket-prep §6 record `prep` immediately after the merge and before telling anyone the raft is ready. Make the `spend` refusal for `prep`/`design-review` on an active item say "readied before its prep was recorded: record nothing; report it". Add the case to spend-command.spec's "refuses an item that is active" (the message for `--phase prep`).
