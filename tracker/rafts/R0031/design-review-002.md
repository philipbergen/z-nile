### F1 [high] appendOnly can skip its canonical-form and "a row was appended" checks for a new ledger and still pass AC4, and the publisher case can't tell appendOnly from a weaker rule
Where: c0084 Design "The ledger", appendOnly bullet; Rules and mutants rows "append-only: … canonical form …" and "publisher: issues' spend.md only, append-only"; acceptance/ledger.spec.luau "accepts only appended rows…"; acceptance/spend-command.spec.luau "the publisher takes only appended rows…"
Evidence: with the prototype in scripts/tracker/ledger.luau, I changed `if new ~= ledger.render(n.id, n.title, n.rows)` to `if old and new ~= …`, and ledger.spec still passed 10/10. Changing `if #n.rows <= before` to `if old and #n.rows <= before` also passed 10/10. The only refusals with `old = nil` are "not a ledger" (refused anyway, because it has no rows, and only under the unmutated rule) and a wrong id. With the first mutant, the publisher accepts a first `spend.md` with hand-edited totals, wrong row numbers, or any text that doesn't start with `|` after the table, since `parse` skips such lines. With the second, it accepts a ledger with no rows. All of these go straight to `main` under the widened direct-push exception, which skips CI. Separately, the publisher's only negative case through `publish.commit` is an edited row with nothing appended. A publisher that calls `ledger.parse` and refuses only when the row count doesn't grow (no `appendOnly`) would pass that case, AC4 and AC7: AC7 accepts any `ledger.parse(` call in publish.luau.
Critique: the canonical check is what keeps a direct-pushed file in the one format every reader and the totals comment rely on, and the design names it as part of the rule. Today it is pinned only for ledgers that already exist. The author will be tempted to add one nil-old case for edited totals.
Consequences: a nil-old case must append a valid row too, so that only the canonical rule can refuse it. Otherwise "no row appended" refuses it, and that rule is itself mutable. The publisher case needs an old row edited *and* a row appended, so that only a comparison of old rows refuses it.
Recommendation: in ledger.spec "accepts only appended rows…", add refusals with `old = nil`: (a) `ledger.append(nil, "c0930", "F", row)` with its totals comment edited; (b) the same with a line of text after the totals; (c) the same with its row renumbered `| 2 |`; (d) `ledger.render("c0930", "F", {})`, which has no rows. In spend-command "the publisher takes only appended rows…", add a `publish.commit` whose content edits row 1's subject and appends one row: refused, tip unchanged. Add Rules and mutants rows "canonical and ≥1-row checks skipped for a new ledger" (run, on the prototype) and "publisher checks only that the row count grows" (reasoned, killed by the new publish case).

### F2 [medium] Nothing pins that `spend` keeps the repository-root guard, and the design's "nothing local changes" invites listing it as read-only
Where: c0084 Design `tracker.sh spend` step 1 ("not `READ_ONLY` (`guardRepoRoot()` runs)"); Rules and mutants (no row); tests/acceptance/c0053/commands.spec.luau's "every command that is not read-only is refused" list, which can't name `spend` and isn't this raft's to edit
Evidence: `spend` publishes from `.` (`publish.commit(".", …)`, with fetch and push). On origin/R0025-ready-raft, `guardRepoRoot()` runs only for commands outside `READ_ONLY` (main.luau:2653). If `spend` is added to `READ_ONLY` (plausible for a command documented as "changes nothing in the checkout it runs in"), then run in a directory whose `.git` is missing, git falls through to the enclosing repository and `spend` fetches and pushes to that repository's origin. No case in the four specs runs `spend` in such a directory, so all of c0084's checks pass with the mutant. c0053's spec guards only the commands it lists.
Critique: this is the failure the guard exists for (testing skill, 2026-09-30), and the jail covers only spec runs, not an agent's shell.
Consequences: the case needs a nested directory inside a fixture repository (as c0053 does with `{outer}/wt/lost`), so that git finds a root other than the working directory. The assertion is the `repository root` refusal and an unchanged fixture origin, never a run against the real one.
Recommendation: add a case to spend-command.spec. Copy `scripts` and `tracker/templates` into `{base}/main/wt/lost` (inside the main clone, no `.git` of its own) and run `spend <a> --phase capture --time 1` there. It fails with "repository root" in stderr, and `tip()` is unchanged. Add a Rules and mutants row: "spend listed as read-only (no guardRepoRoot)", reasoned.

### F4 [low] The "spend never writes an active item's ledger" rule is checked before the publish build, so a `ready` landing between check and push defeats it
Where: c0084 Design `spend` steps 3 and 5; R0031 Risks "Merge conflicts on spend.md: avoided by construction"
Evidence: step 3 refuses active targets "on origin/main", and step 5's build locates each ledger with `docPath` on the build's fresh listing. `publish.commit` re-runs the build on every lease failure. If `ready` (another terminal) moves the members between the step-3 check and the push, the retried build finds `tracker/issues/active/<id>/<id>.md` and appends to `active/<id>/spend.md`. That is the race F6's fix makes likely: prep is recorded "right after the merge", the moment someone may run `/ready-raft`. `moveOnOrigin` avoids this by checking status inside its build (`verify`). The publisher itself accepts a non-move `spend.md` under `active/`, and one whose item document isn't beside it.
Recommendation: run the active-status refusal inside the build, on the `read` it is given, as `moveOnOrigin` does. In `publish.commit`, refuse a non-move `spend.md` change under `active/` (only a raft branch writes those, and it never publishes), and one whose `<ID>.md` isn't on origin in the same directory. Add the second rule as a case in the publisher spec: `publish.commit` of `tracker/issues/active/<b>/spend.md` is refused.

### F5 [low] The prep phase's minutes and recording window are ambiguous in two places
Where: c0084 "The phases" table (`prep` and `design-review` rows); ticket-prep §5/§6 edits; tracker skill Landing step 3 ("Prep … that the user didn't ask for is not merged without asking")
Evidence: (a) `design-review` records "reviewer + answering minutes", and `prep` records "author's prep minutes, landing included". Nothing says to subtract the answering time already recorded, so the natural reading (the whole prep session) counts it twice. (b) `prep` is recorded only "right after the prep PR has merged". When the agent must ask before merging (an unrequested prep), the session usually ends with the PR open and the row is never recorded. E1 shows the three-dot count is the same before the merge, and a published row doesn't conflict with the open prep PR (it never touches `spend.md`).
Recommendation: say "prep minutes, excluding the design-review answering minutes already recorded". Allow `spend --phase prep` before the merge when the agent won't merge the PR itself: "record prep when the prep PR is merged or handed to the user, whichever comes first, once". The spec needs nothing new: "prep counts the lines" already runs before a merge.
