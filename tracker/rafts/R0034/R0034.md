# R0034: Game over to lobby

## Theme
One feature, f0065: at game over the player goes back to the lobby instead of playing again in the game place. It replaces R0015's PLAY AGAIN (f0031) and reuses R0024's `Travel` (f0061) for the teleport. Nothing else in the backlog is adjacent: the narrowing of f0031's specs is a chore (c0063, R0033) and publishing the ids is c0064 (R0032).

Decisions relied on (quoted):
- **User, 2026-10-02** (f0065): at game over "an overlay shows the game results and waits for a tap before teleporting back to lobby".
- **Two places** (game-design, 2026-10-02): "At game over an overlay shows the results and waits for a tap, then teleports back to the lobby (f0065, after c0063)."
- **Authority** (game-design): "The server simulates every maze. Clients send intents and render the replicated state."
- **Platforms** (game-design): "Desktop (keyboard and mouse) and mobile (touch)." The tap target is the whole screen; Enter on desktop.
- **Deploy** (game-design): "Both places live in the Beta experience (a repo variable for the game place's id)". Setting the lobby's id on the game place at publish time is the publisher's job (see Risks).
The author's choices (texts, tap anywhere, no fallback when the lobby is not set up, Logic's play again kept) are listed in f0065's Design; the user may veto any.

## Whole-raft design
```
client (FlowView, Main)                       server (Sessions, Returns)                          engine
 Flow.overlay(frame.play, RULES, trip)          Sessions.isOver(player) -> Session.isOver(s, id)
 tap / Enter, only if overlay.tap
   ToLobby:FireServer() ---------------------->  isOver? -> Travel.destination(LobbyPlaceId)
                                                 Travel.request == "go" ------------------------->  TeleportAsync(lobby, {player})
 trip <------------- LobbyStatus(phase, configured) <-- Travel.status / failed / answered            TeleportInitFailed
```
- **Logic**: `Session.isOver` (new); `Flow` changes its `Overlay` (`playAgain` → `prompt`, `tap`, `cursor`), its keys (`CONTINUE_KEYS`, `isContinueKey`) and takes an optional `Trip`. `Travel` is reused unchanged.
- **Adapters**: `Returns` (new, game server), `Sessions` (play-again handler out, `isOver` in), `Main.server`, `FlowView`, `Main.client`.
- **Config**: `default.project.json` remotes `ToLobby`, `LobbyStatus` (no `PlayAgain`) and the attribute `LobbyPlaceId = 0`.
- **Architecture changes (made in this prep)**: the edge `Flow -> Travel` in `tracker/architecture.md`'s deps block, and Flow's row there.
- **Tests infrastructure**: `tests/lib/fakeengine.luau` grows so the real `Sessions`, `Returns` and `FlowView` run on it: more Logic modules and an override map, remote names on what is sent, `reports`, `fire`, and a client with `ContextActionService`, `receive`, `click` and `key` (f0065 Design).
Interfaces in detail: f0065's Design.

## Risks & rollback
- **Beta needs `LobbyPlaceId`**: c0064 (R0032, prepped and landed in PR #72) sets it on the game place in split mode, pinned in its specs (the name lives in `scripts/lib/beta.luau`), and f0065 starts only after c0064 is done, so Beta goes from PLAY AGAIN straight to a working way back. The attribute name `LobbyPlaceId` is shared with c0064: do not rename it.
- **The teleport is unverified offline** (E5): Travel's 15 s timeout, 60 s cap and 3 s cool-down make any non-answer a retry, and the results stay on screen.
- **The tap target might be sunk by the HUD** (E5): adapter-only fallback.
- **Size**: about 330 changed lines of code and test infrastructure (the patch) plus about 900 lines of acceptance specs.
- **Rollback**: revert the PR; PLAY AGAIN does not come back by itself (c0063 narrowed its specs, which stay valid either way), so a rollback restores f0031's adapters from history.
