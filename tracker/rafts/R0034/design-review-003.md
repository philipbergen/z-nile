### F1 [medium] Returns' request tickets are unpinned: a late answer from an abandoned call can cool down or shorten the player's newer trip, and every spec still passes
Where: f0065 Design "Server" (`Travel.answered(…, ticket)`, `Travel.failed(…, ticket)`; "This is f0061's `Starts`, line for line"); `returns.spec.luau`; the Rules and mutants table, which has no row for tickets.
Evidence: mutants H5 and H9 (the ticket left off `Travel.answered` or off `Travel.failed` in the request handler) pass all 52 f0065 cases. Travel uses the ticket to tell a report for the current request from one for a call that was given up on at the 60 s cap (`Travel.current`). f0061 pins the same handling in `Starts` with two cases (`lobby-adapters.spec :: a call abandoned after the cap reports nothing to the newer request …` and `:: an abandoned call that returns at last does not shorten the newer request's wait`). `returns.spec` has neither: its two `hold` cases release a call only after the player has left. The failing scenario with H9: call A hangs past the 60 s cap, the player taps again and call B goes, then A's error arrives late. Travel puts the player into cooling while B is still in the engine. The prompt says "Could not return", and 3 s later a tap starts a third teleport for the same player while B is still outstanding. With H5, A's late return starts B's 15 s timeout early.
I ported f0061's two cases to Returns in the scratch clone (`world(777)`, `over[P1] = true`, `ask` in place of `press`, `reports("LobbyStatus", P1)` in place of `statuses`). Both pass on the prototype, H9 fails the first and H5 fails the second.
Critique: the design copies `Starts` "line for line" but not the specs that pin it. An executor who writes Returns from the Design's prose ("then `Travel.answered(…, ticket)`") could easily drop the ticket, which is optional in Travel's signature, and nothing would go red.
Consequences: none new. The fake already has `hold` and `release(index, failure)`, and Travel is unchanged. The two cases add about 30 lines to a sequestered spec, written now in prep.
Recommendation: add the two cases to `returns.spec` as above, with the exact report string `going/true cooling/true idle/true going/true cooling/true` for the late-return case and "no third call while B is in the engine" for the late-failure case. Add a Rules row "A late answer from a call given up on at the cap does not touch the newer request (tickets)" → those two cases, mutants H9 and H5, `run`. Record them in E4 (50 mutants), and add "late answers belong to their own request" to AC3's text.

### F2 [low] A departed player's `shown` entry is pinned by no spec
Where: `src/server/Returns.luau` (prototype) `PlayerRemoving` handler; f0065 Rules row "A player who leaves is forgotten" (M25 `Travel.left` only).
Evidence: H3 (the `shown[player] = nil` line removed) passes all f0065 specs. In Roblox a returning player is a new `Player` object, so the visible effect is only that every departed `Player` stays referenced by `shown` for the life of the server, a slow leak. f0061 catches the same mutant in `Starts` (`lobby-adapters.spec`, "the same player, back: told the state again, whatever was shown before") because its fake rejoins the same object. f0065's rejoin case asks again but never checks what the player is told.
Recommendation: in `returns.spec :: a player who leaves while a trip is under way and comes back …`, make the player leave while `idle` has been shown, rejoin, and expect exactly one new `idle/true` report. Add H3 to the "A player who leaves is forgotten" row. Alternatively, accept the leak and say so in the Design.
