### F1 [high] The radar fingerprint can't pass on the Design's exact content: its region end `"\n\t\t})\n"` doesn't occur once the snippet is applied
Where: narrow-radar.spec.luau:171 (`fingerprint("radar.spec.luau", "\t\tlocal l = Hud.layout(1280, 720)\n", "\n\t\t})\n")`). c0106.md, Maintainability ("the Design snippets are therefore exact: the executor pastes them (stylua-formatted) and the fingerprints match") and Unknowns E2 ("With the prototype applied: 15 of 15 pass").
Evidence: the snippet's last line is `}).toEqual({ textSize = 32, margin = 16, iconSize = 32, barWidth = 320, barHeight = 13 })`. That is 96 columns at two tabs, so stylua keeps it on one line. In the narrowed file, `\t\t})` is followed by `.toEqual`, not by a newline, and there is no other `\n\t\t})\n` after the `local l` line. The `assert` fires, and AC1 fails on a correct execution. The executor can't fix a sequestered spec, so it must stop and escalate. E2's 15/15 must have been run on a prototype other than the Design's snippet, for example one with a multi-line expected table. So the record "the Design above is the exact content" isn't true. The recorded checksum is right: with `upTo = "barHeight = 13 })\n"` it is `579248509:3321`.
Critique: the tempting fix is to change `upTo` to `"barHeight = 13 })\n"`. That works (verified: 15/15), but it keeps the fingerprint tied to the exact formatting of the new code. Both of this round's executability risks live there: whitespace, the stylua version, and whether the snippet the author tried is the one in the Design. Prep has just shown that this coupling is easy to get wrong without anyone noticing.
Consequences: if the fingerprint stays tied to the snippet's text, each later re-format of the snippet (a stylua bump, a hand tweak in a later override) needs the c0106 checksum recomputed as well. A cut bounded by stable text outside the snippet doesn't have this problem. The fingerprint is then identical for today's file and the narrowed one, so the fingerprint case passes before the edit too. That's fine, because the witness cases are what fail today. Whatever is inside the cut is still covered by the behavioural cases. I checked that an early `return`, a hard-coded field or a dropped field inside the region each fail a witness or mutant case.
Recommendation: question the mechanism, not just the end string. Cut each region at anchors that neither today's file nor the narrowed one changes, and compute the checksum from today's file:
- radar: from the case's header line (`"layout's numbers are unchanged, so the bar and the labels stay where X put them", function()\n`, with the id already normalised to `X`) to the first `"\n\tend)\n"` after it;
- adapter: from `"\t\t\tlocal src = source()\n"` (the first one is in case 1; the other cases indent it two tabs) to `"\t\t\tlocal function count("`.

Then re-run E2 literally: apply the Design snippets as written, run `stylua`, run both narrow specs. Record that run, and record the today run, in which only the witnesses fail. Rename the two Test plan cases to match ("... is exactly today's file outside the narrowed case body"). If you keep the current anchors instead, change `upTo` to `"barHeight = 13 })\n"` and make the same literal re-run of E2.
