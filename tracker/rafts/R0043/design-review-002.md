### F1 [high] The counter during R0043's own execution: once step 2 runs, the branch's engine numbers against a `z-nile/next` that origin/main doesn't have, and every merge of `origin/main` conflicts on `tracker/next`
Where: c0114 §5, §11 ("c0114 moves itself"), Implementation steps 2-3 and 9; prototype `z-nile/engine/main.luau` `reserve` / `reserveOnOrigin` / `localNumber`
Evidence: execution runs while origin/main is still pre-c0114: `tracker/next` is the live counter, and there is no `z-nile/next` and no registry. After step 2 the branch has `z-nile/next` (moved) and the tombstone at `tracker/next`. After step 3, `./zn` and the `scripts/tracker.sh` forwarder run the new engine in the raft's worktree. Two failures follow:
- **The emergent issue collides.** In the new engine, `reserve` reads `z-nile/next` from origin, gets nothing, and returns nil ("origin has no counter"), so `reserveOnOrigin` pushes nothing. `localNumber` then numbers from the branch's local `z-nile/next`. Origin's `tracker/next` is never raised, and `publish.allowed` refuses that path. Say the branch moved the counter at `issue 122`. An emergent `./zn new issue c x --raft R0043` makes c0122 locally. The next capture on main (old engine, `tracker/next` = 122) also makes c0122. At the merge one id sits in two folders: `audit` reports a duplicate and AC12 fails, or the duplicate lands. The same happens to any other active raft's counter-only reservation: its number is reserved on `tracker/next`, which `z-nile/next` never sees.
- **The merge conflicts.** I merged a commit that raises `tracker/next` (`issue 123`) into `proto-c0114` in a scratch clone: `CONFLICT (content): Merge conflict in tracker/next`, and `z-nile/next` stayed at `issue 122`. Every capture on main during an oversized raft raises that file, so every `sync` and the final merge hit this conflict. The documents don't say how to resolve it. The natural resolution, keeping the tombstone because §5 says "nothing new ever writes the tombstone", silently drops main's raises. `nextFree` then skips only the ids it can see, so counter-only reservations made since the branch was cut are handed out again.

The same window also hides a compaction: `refuseStale` reads `z-nile/compaction.txt` on origin, finds none and returns. Today that is masked only because compaction refuses while R0043's branch changes `tracker/`.
Critique: §11 covers old engines after the landing and open branches merging across the move. It does not cover the one branch that runs the new engine against the old origin for the whole execution. The tempting fix is a sentence in the PR description ("on a conflict take the max into `z-nile/next`"). That is a manual step on every sync, nothing checks it, and it does nothing for the emergent reservation.
Consequences: the engine must choose the live counter from origin's layout, not the working tree's. That is one more rule in `publish.allowed`, which must stay origin-derived (lesson architecture/guards-trust-only-origin). It must also never let the new engine write `tracker/next` once origin has the registry, or the tombstone guarantee (E5) breaks. The merge resolution has to run on every merge, including the final one before `done`.
Recommendation:
- **Engine.** While origin/main has no `z-nile/projects.toml` (the legacy registry, which `projects.at` already reports), `reserve` reads and raises origin's `tracker/next`. `publish.allowed` allows `tracker/next` only in that case. Once origin has a registry, `tracker/next` stays never-allowed, as now.
- **Merges.** On every merge of `origin/main` into a branch that holds both files (`./zn sync`, and the merge before `done`), the engine resolves a `tracker/next` conflict itself: it keeps the tombstone and sets `z-nile/next` to the per-space maximum of the two counters. Alternatively, §11 and the execute-raft prompt state the rule, and `audit` reports `error counter-behind` when `z-nile/next` is below a parsing `tracker/next` on origin/main. Then AC12 or RC0 fails a missed resolution.
- **Specs** (roots-cli or publish-roots):
  - In a fixture origin with no registry and a parsing `tracker/next`, the new engine's emergent `new issue --raft` raises origin's `tracker/next` and pushes no `z-nile/next`.
  - The same push is refused when origin has a registry.
  - A merge of an origin whose `tracker/next` was raised leaves `z-nile/next` at the higher counter, or audit reports it.
- **Rules rows**, each with its mutant: "reserve reads `z-nile/next` only", "`tracker/next` allowed regardless of origin's registry", "conflict resolved to the branch's counter".
- **§11**: add a "the execution window" bullet.

### F2 [medium] JC1 fails the execution the design itself prescribes when a tooling item is captured during execution
Where: c0114 Judged JC1; §9 last bullet; Implementation step 9; design-refute-001 F4 consequences
Evidence: JC1 fails "when … a later commit moves a file". §9 and step 9 require any tooling item captured after this prep to be "moved the same way before `done`". That item reaches the branch by a merge of `origin/main` long after the step 2 commit. The refutation says it gets "its own renames-only commit, or the moves commit if not yet made", but JC1's rubric admits neither: a correct, well-split PR that moves one late capture in its own `R100` commit fails the Judged criterion. Captures on main during a large raft are routine, so this is likely to happen.
Recommendation: restate JC1's rubric: "Every commit that moves a file has a subject starting `c0114: move` and lists only `R100` lines under `git show -M --find-renames=100% --name-status`; no other commit moves a file." Step 9 names the subject for late moves (`c0114: move <ids> into z-nile/.tracker/ (renames only)`). The PR description lists each such commit, so the reviewer knows which commits to read. Nothing else changes: AC10 already pins only this prep's classification.

### F3 [low] The stop hook drops any changed path that merely contains `<root>/`
Where: c0114 §8 stop-hook bullet; prototype `scripts/hooks/stop.sh` (`grep -vF "$root/"`)
Evidence: the exclusion is an unanchored fixed-string match. With the root `tracker`, a code path such as `tests/lib/tracker/x.luau` or `z-nile/engine/tracker/x.luau` contains `tracker/`, so the hook drops it and doesn't gate it. No such path exists today (I checked with `git ls-files src tests z-nile`). It is a latent hole in a guard that §8 says follows the registry.
Recommendation: match the root as a path prefix, for example `awk -v r="$root/" 'index($0, r) != 1'`, or `grep -v "^$(printf '%s' "$root" | sed 's/[.[\*^$]/\\&/g')/"`. Add a gate-cover hook case with a changed `tests/lib/tracker/x.luau`: the gate runs.

### F4 [low] repo-fence's root fallback reads every failure of `require` as "no engine here"
Where: c0114 §8 repo-fence bullet; prototype `tests/tooling/repo-fence.spec.luau` (`pcall(require, "@znile/engine/projects")`)
Evidence: the fallback to `{ "tracker", "z-nile/.tracker" }` exists for fixtures that copy the runner without the engine. But it also triggers when `projects.luau` is present and fails to load, so the guard scan quietly narrows. After c0120 it would then skip `pickman/.tracker`'s `check.sh` files. In the real tree a broken `projects.luau` turns most of the gate red anyway, so this is a consistency point against the raft's own new lesson, not a live hole.
Recommendation: fall back only when `z-nile/engine/projects.luau` is not a file, and raise otherwise (lesson architecture/guard-no-is-explicit: the one explicit "no" is "no engine in this copy").
