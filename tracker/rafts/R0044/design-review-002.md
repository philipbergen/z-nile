### F1 [high] A run that is its player's new best is listed twice, and heard one place too low, when another list write lands between its per-player write and its own list write (a hole in the mechanism design-review-001 F1 recommended)
Where: d0124 Design, "Merge the per-player bests on every write" ("The run's own new best is covered by the run, so it is listed once"), "A best's id"; prototype `Hiscores.mergeRun`/`covered`, `HiscoreStore.submit`.
Evidence: the cover rule only works when the run reaches the list before anyone else merges its player's best. `submit` writes the per-player all-time row first (`BOARD_IDS` is all, day, week), then day and week (four more updates), then `readAll` (a page and up to ten `GetAsync`s), and only then the list update, retried after 0.25 and 0.5 s. Any other game over in that window, on another server or in the same server (solo mazes in a shared server, game-design.md Players), whose `readAll` comes after P's all-time write, merges P's new best as `best:<P>:<score>:<level>` at 0, because the list does not hold P's run yet. P's own write then adds the run under its real id; nothing removes the best. Probe on the prototype (`driveTop` for Q with bests `{P 500, Q 100}`, then for P's 500 run with the same bests): the list is `best:7:500:3=500`, `7:…:jobA=500`, `2:…:jobB=100`, and P hears `place = 2`. The best at 0 also outranks the run in the tie, so the player's best run of all time reads "ALL-TIME #2" and holds two of the ten places for good.
Critique: AC1's "lists each run id once" and every case are met, because the two entries have different ids for the same run; the spec cases are all sequential. The tempting fix (in `mergeRun`, drop a `best:` entry of the run's player with the run's score and level) deletes a real older run whenever a player ties their own earlier best (the per-player row is only replaced on a strictly greater score, so the old entry is a different run).
Consequences: the same run must get the same id whichever source offers it, or the merge must know whether this run is the one that wrote the best. Either way the rule "a stored copy of an id wins" is what dedupes, so it must see one id.
Recommendation: question the mechanism, not just this interleaving: a `best:` id derived from (score, level) cannot name a run. Give the run its identity in the per-player all-time row: `Hiscores.commit` (or drive's all-time transform) stores the run's `id` and `at` on the companion row it writes, `Hiscores.rows` carries them as optional `Row` fields, and `bestRun` uses them when they validate (the `validRun` rules), falling back to `best:<userId>:<score>:<level>` at 0 only for rows written by builds without them. Then the run and its best are one id from any source, under any order, and the stored copy wins. Consequences to cover: `drive`/`Attempt` must receive the id (`topRun` is built before `drive`); old builds rewrite a raised row without the fields (it becomes a `best:` entry, correct, since that run never reached the list); run `scripts/affected` and the text greps for the companion shape and add any promoted case it turns red to the Overrides and c0128 (or a new chore). Spec cases: `drivetop`/`top` "another server merged this run's best before its own write: the run is listed once and keeps its place" (both orders), "a companion row without an id still merges as best:…", "a companion id that fails validRun falls back"; mutants: bestRun-ignores-row-id, rows-drop-id. An alternative that also holds, at one extra `readAll` (11 reads) per run: write the list before the per-player boards with a separate `readAll` for the bests (the `store-top-first` order the design now forbids), so no other server can see this run's best before the run is listed; it does not fix F2.
Lesson: ticket-prep/new-rules-migrate-existing-work (the old-shape writer here is the run's own per-player write, seen by another server first)

### F2 [medium] A run pushed off the list comes back as its player's `best:` entry at 0 and evicts an earlier run it only ties
Where: d0124 Design, "Ties" ("A best is at 0, so it keeps a place a new run only ties"); prototype `mergeRun`, `covered`.
Evidence: P's run (50, level 1, at FRI) is tenth behind nine runs of 50 at level 1 made earlier. A 900 pushes it off (the cover check still sees it in that write). On the next write P's per-player best (50, 1) is in `bests` and no listed run of P covers it, so `best:7:50:1` at 0 is added, ties the nine on score and level, wins on `at`, and evicts the ninth (probe: `…109…=50` is gone, `best:7:50:1=50` is second). The next write can do the same for the evicted player's best (`best:109:…` sorts before `best:7:…`), so tied places churn on every run. The rule "the earlier run keeps a tied place" is broken: the best is a later run dated 0.
Critique: dating every best 0 is right only for rows older than the list; a best that is a run the list already ranked and cut is not older. Needs exact score and level ties at the tenth place, hence medium.
Consequences: with F1's recommendation the row carries the run's `at`, so a cut run comes back with its real date and is cut again (no write, `sameIds`). Only rows without an `at` (old builds) keep 0.
Recommendation: fix with F1 (the best's `at` is the row's when it has one). Spec case: `top` "a run cut from the list does not return as its best ahead of an earlier tie"; mutant best-at-zero-always.
