### F1 [high] The docs say "frightened time is 0 from level 17", but level 18 has 1 s, and a hard-coded `level >= 17` passes every spec
Where: `tracker/game-design.md` Levels bullet; f0160 Decisions ("**0 from level 17**"), AC1 ("0 from level 17 … from level 17 on nothing starts or ends"), and the Rules row "level 17+: no period"; `f0160/acceptance/power.spec.luau` "the period is the level's".
Evidence: Table A.1 and `levels.spec` both give level 18 1 s / 3 flashes. I changed the prototype's `Game.power` to `g.frightened = if g.level >= 17 then 0 else Levels.frightenedTicks(...)`, which is what the AC1 text literally says, and it passed all 12 specs (93/93). `power.spec` checks levels 17, 20 and 30, but not 18. `levels.spec` only pins the table, not what `Game.power` does with it. AC1 also says "nothing starts" from level 17, but the spec requires `Game.power` to return one `PowerStarted` with `ticks = 0`.
Critique: the source-of-truth document and the AC text both state a wrong rule, and the spec lets through the wrong implementation they describe. The tempting fix is to add an 18 to the spec's table and leave the prose alone. The next reader of game-design would then reintroduce the bug.
Consequences: the zero-length `PowerStarted` becomes a documented contract. Raft d will consume it: in the arcade, ghosts reverse on every energizer, even when they don't turn blue. So "nothing starts" must become "a zero-length period starts: `PowerStarted{ticks = 0}`, no frightened time, no `PowerEnded`". Otherwise raft d will have to guess.
Recommendation: reword game-design, f0160 Decisions, AC1 and the Rules row to "0 on level 17 and from level 19 on; level 18 has 1 s (30 ticks)". State that `PowerStarted{ticks = 0}` is emitted when there is no period. Add `[18] = 30` to the "the period is the level's" table. Add a Session-level case at level 18: `PowerStarted.ticks == 30`, with `PowerEnded` exactly 30 ticks later. Add a Rules row "level 18 frightens for 1 s | mutant `level >= 17 → 0`".

### F2 [high] `died`/`cleared` are only tested in `ready` and `dying`; a kill in `levelclear` or `gameover` passes every spec and soft-locks the run
Where: f0170 Rules row "only a run in play loses a life or clears"; `game.spec` "only a run in play can lose a life or clear a level"; `flow.spec` "Kill only works while the run is in play".
Evidence: I changed the prototype's guard in `Game.died` from `phase ~= "playing"` to `phase == "ready" or phase == "dying"`, and all 12 specs passed. With that implementation, a `Session.kill` during `levelclear` sends the run to `dying` and then `Ready{respawn}`. The level never advances, and every pellet is already eaten. `Pellets.remaining` stays 0, and a clear only fires on eating, so the run is stuck on an empty maze. After `gameover`, a kill takes `lives` to -1. Raft d will call `kill` from ghost collision every tick, including the tick in which the last pellet goes (the same `Session.step`, after `Game.cleared`).
Critique: AC2 ("exactly as designed") and AC3 can be passed by a wrong guard, and the case that matters most is the one raft d will hit. The tempting fix is to add one `died` call during `levelclear` in `game.spec`. That leaves `gameover`, and `cleared` in those phases, unpinned.
Consequences: this makes "kill is a no-op outside `playing`" part of raft d's contract: a ghost touching the player in the clear pause does nothing. That is the arcade's behaviour (the ghosts vanish), so no user decision is needed. The same-tick order (eat last pellet, then collision) should be stated in the Session design, so raft d doesn't reorder it.
Recommendation: in `game.spec`, `died` and `cleared` return `{}` and change nothing in `levelclear` and `gameover` (lives, level, phase and timer all unchanged). In `flow.spec` or `level.spec`, clear a tiny maze, call `Session.kill` during the clear pause (`{}`, lives unchanged), then check that `Ready{level}` still comes and the level is 2. After `gameover`, `Session.kill` returns `{}` and lives stay 0. Split the Rules row into the four phase/function pairs, each with its mutant.

### F3 [medium] `playAgain` teleports with `jumpTick = s.tick`, which is the tick the client already holds, so the camera slides instead of cutting
Where: f0170 Decisions ("Respawn is a teleport … `jumpTick = tick`"), Session design ("play again (`Ready{again}`) … teleport … `jumpTick = tick`"); `flow.spec` "play again starts a fresh run" doesn't look at `jumpTick`.
Evidence: respawn and a new level teleport inside `Session.step`, after `s.tick += 1`, so `jumpTick` is the tick of the first frame at the spawn. `Session.playAgain` runs between steps, so it sets `jumpTick` to the tick of the previous frame. On the prototype: the frame at tick 388 is `gameover` at x = 12.75. After `playAgain` and one step, the frame at tick 389 is at x = 13 with `jumpTick = 388`. `View.interpolate(frame388, frame389, 0.5)` returns x = 12.875: a slide, because `View` cuts only when `jumpTick > prev.tick`. In the real maze, the gap from the death tile to the spawn crosses walls.
Critique: the play-again flow is wired in R0150 (f0300), so this lands there as a visible glitch that nobody can trace to this raft. The tempting fix is `jumpTick = s.tick + 1` inside `reset` for every reason, but that breaks the in-step teleports, which are correct today.
Consequences: `jumpTick` needs one written meaning, "the tick of the first frame at the new position". A teleport made outside a step must then record `s.tick + 1`. A frame taken before that step would show a `jumpTick` greater than its own `tick`. That is harmless to `View`, but it has to be allowed and stated. The alternative is to defer the reset to the next `Session.step`, but then a frame between the call and the step shows `ready` at the old position. Either way the rule goes in the Session design.
Recommendation: define `jumpTick` as above, and make `playAgain` (and any future out-of-step teleport) use `s.tick + 1`. Add a flow case: play again at tick T, step once, then `frame.player.jumpTick == T + 1`, and `View.interpolate(frameT, frameT+1, 0.5)` returns the spawn exactly. Add the matching Rules row (mutant: `jumpTick = s.tick`).

### F4 [medium] The frightened player speed from Table A.1 is left out, though the frightened period is this raft's and game-design says "speeds … following the classic tables"
Where: `Levels.Row` (f0170: `speedFactor`, `frightenedSeconds`, `flashes`); f0160 design; `tracker/game-design.md` Levels bullet.
Evidence: Table A.1 has a separate Pac-Man speed while frightened: 90% on level 1, 95% on levels 2–4, 100% on levels 5–20 (against normal 80/90/100%). None of the three issues mention it, and no non-goal or user decision excludes it. Ghost speeds are raft d's, but the player's speed during the power period is only f0160's to own: `frightened` lives in `Game`, and `Session` picks the speed.
Critique: "classic rules and feel come first" (pillar 1). Raft d's ghosts will then chase a player that is 10 points too slow at level 1 for the whole period, and the table will look finished when it isn't. The tempting fix is to put it off to raft d, which would then have to touch `Session`'s speed path and `Levels` row shape after both have shipped.
Consequences: a new column `frightSpeedFactor` (relative to level 1: 1.125, 1.1875, 1.25; 1.125 from 21 on, unused because the time there is 0) gives 34, 36 and 38 units a tick. It also needs a timing rule. Proposal: the frightened speed applies in a tick when `frightened > 0` at the start of the tick, the same rule as `moving`. So the tick after eating is the first fast one, and the tick that emits `PowerEnded` is the last. The eating pause uses that tick's speed (17 units per dot at level 1 while frightened), which reproduces Table A.1's 79% "fright dots" speed. The `Session.new` speed guard must check both columns (the maximum is still 1.25, so its numbers don't change). Alternatively, the user rules it out and game-design records it as a deviation.
Recommendation: ask the user, or adopt it. If adopted: add the column to `levels.spec`'s table. Add to `power.spec`: on level 1 the step after eating the power pellet covers 34 units, and the step after `PowerEnded` covers 30 again; on level 2 it covers 36. With the slowdown on, a dot eaten while frightened costs 17 units. Add Rules rows for each case.

### F5 [medium] "A new level or play again forgets the owed pause" has no spec and no Rules row; two natural implementations of it pass
Where: f0150 Decisions ("A death or a level start forgets what is owed"), Session design ("`Ready{respawn|level|again}` … additionally clear `stall`"); Rules table (only "an owed pause is forgotten at respawn").
Evidence: two prototype mutants passed all 12 specs. One clears `stall` only in `Session.kill`, which is the obvious place for "a death forgets it". The other clears it only when `reason == "respawn"`. `slowdown.spec` only checks the death case. `level.spec` "eating on level 2 pauses for 17 units" measures a difference between two ticks, so a leftover 15 units at the start of level 2 shifts both positions and cancels out.
Critique: a design rule with no row. It fails quietly: the first step of every new level is short by the last pellet's pause. The tempting fix is to assert the level-2 first-step distance only, which leaves `again` unguarded.
Consequences: none beyond the spec cases. The eating-pause stall is already defined in units and resets in one place (`reset`), so no rule changes.
Recommendation: add to `slowdown.spec` (with slowdown on, small pauses, and the level cleared by its last pellet): the first moving step of level 2 covers the full 34 units. A run that dies owing a pause on its last life then plays again, and its first step covers 30. Add Rules rows for both mutants.

### F6 [medium] AC6's adapter spec is a text search, so an adapter that mentions the names without using them passes
Where: `f0170/acceptance/adapter.spec.luau`.
Evidence: the checks are `string.find(src, "Session.GAME_CONFIG")`, `find(src, "Session.frame(")` and the absence of `"Session.snapshot("`. Two adapters that pass: `local CONFIG = Session.GAME_CONFIG` declared and then `Session.new(Maze.layout(Maze.DEFAULT), player.UserId)` without it; and a comment `-- sends Session.frame(...)` above a `FireClient` that still sends the snapshot through a local alias. Both are plausible refactors, and both put `DEFAULT_CONFIG` (no pauses, no slowdown) on Beta.
Critique: RC2 rests on this spec. The tempting fix is more substrings, which a comment defeats the same way.
Consequences: a structural match ties the spec to the adapter's call shape. That is acceptable because stylua fixes formatting, but the spec should not pin local variable names.
Recommendation: strip `--` comments from the source first. Then require a `Session%.new%b()` call whose last argument is `Session.GAME_CONFIG`, and a `:FireClient%(%s*[%w_]+%s*,%s*Session%.frame%(` call, and require that no `Session.snapshot(` remains. Add a Rules row per mutant: the unused local, and the comment-only mention.

### F7 [low] The Rules row "frightened seconds convert to ticks by rounding | truncates" can't fail

Consequences: none.
Recommendation: relabel the row to the mutant that was run ("ignores tickRate"), and mark rounding as not observable with the current data.
