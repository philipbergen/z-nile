### F1 [low] The energizer's pause isn't 3 frames once the frightened speed exists: 45 units are owed at 30 and paid at 34
Where: f0150 Decisions ("the pause is exact and spills across ticks"), f0160 Decisions ("The eating pause is computed at the speed of the tick the dot was eaten in"), `power.spec` "a dot eaten while frightened costs 17 units" (`units(4) == 83`), `tracker/game-design.md` line 42.
Evidence: the energizer is eaten at tick 2 on a normal step, so it owes `stallUnits(power, 30) = 45`. Tick 3 runs at 34, so 34 units are paid and the player doesn't move. Tick 4 pays the remaining 11 and moves 23 units, which gives 83. That pause lasts 1 + 11/34 = 1.32 ticks, or 2.65 arcade frames, not the 3 the user decided. In the arcade, fright mode, and with it the fright speed, starts as soon as the energizer is eaten, so the 3 stopped frames cost 3 frames of distance at the fright speed (51 units). The same mismatch runs the other way at the end of the period: a dot eaten on the last fast tick (182) owes 17 units, which are paid at 30. That is 1.13 frames. Separately, game-design line 42 says the owed pause is forgotten on "a death or a new level" but leaves out play again (f0150 and its spec include it). It also doesn't mention the 17-unit dot pause while frightened. And architecture.md's `Levels` row lists "player speed factor, frightened time, flashes" but not the frightened speed column.
Critique: the gap is about 6 units (0.05 tile, about 6 ms) and can't be seen. But `power.spec` pins 83, so the deviation becomes sequestered contract, and the docs call the pause "exact". The tempting fix is to compute the energizer's pause after `Game.power`, at the frightened speed (51). That fixes the energizer, but it still leaves the `PowerEnded` boundary owing at one speed and paying at another.
Consequences: the general fix is to owe frames, not units, and pay each tick at that tick's speed. At 60 fps a tick is 2 frames, so a tick that pays p frames moves `speed - floor(speed × p / 2)`. That changes `Member.stall`'s unit and `power.spec`'s numbers (`units(4)` becomes 77, and the later values move with it). f0150's own cases don't change, because no speed change happens inside them, and the slowdown power case still reaches the wall at tick 19 after f0160 (435, 452, 480), so the staging holds.
Recommendation: either adopt the frames-owed rule, recompute `power.spec`'s 60/83/185/202/321 with the independent model, and add a Rules row (mutant: the pause owed in units at the eating speed); or keep the units model and write it down as a deviation in game-design ("the pause is distance at the eating tick's speed; across a speed change it is up to a third of a frame off"). Either way, add "or a new run" and the frightened 17-unit case to game-design line 42, and the frightened speed column to architecture.md's `Levels` row.

### F2 [low] The `Session.new` speed guard "over both columns" can't fail with the current table, and it has no Rules row
Where: f0170 Session design ("when any level's speed, in either column, would exceed one tile per tick"); Rules row "too-fast speeds refused | guard removed"; `config.spec` "level speeds scale the base speed…".
Evidence: both columns peak at ×1.25 (levels 5–20), so a guard that checks only `speedFactor`, or only `frightSpeedFactor`, refuses exactly the same base speeds (97 and above). The 96/97 boundary in `config.spec` passes either way. The refutation of review-001 F4 says the guard covers both columns, but no case can tell that it does.
Critique: this is the same situation as review-001 F7: the docs claim a guard that no spec can observe. It's harmless until a column changes, for example if a future tuning raises a frightened factor above 1.25.
Consequences: none.
Recommendation: add a Rules row "the guard covers the frightened column | guard reads only the normal column | reasoned: equivalent with the current table (both peak at 1.25)", and record it in E4, as the G10 row does.

### F3 [low] The raft's step-order contract for raft d leaves out `Game.step`, and the frightened invariant depends on `Game.power` having no phase guard
Where: R0090 "Order inside one `Session.step`" ("move, eat, power, clear; collision after"); f0160 Decisions ("While `ready`, `dying`, `levelclear`, `gameover` the counter is always 0, so 'only runs down while playing' is an invariant"); the G10 row ("equivalent").
Evidence: the actual per-player order is: read `moving` and `frightened`, then `Game.step` (which can emit `PowerEnded`), then move, eat, power, clear. So in one tick, `PowerEnded` can come before a `PowerStarted` from a second energizer, and raft d's collision (after the clear) sees `frightened == 0` on the tick the player still moved at the frightened speed. Also, `Game.power` has no phase guard (prototype `Game.power` sets `frightened` in any phase). The "invariant" holds only because Session calls it while moving. A Game-level caller in `ready` would leave a period frozen until play starts, and G10's equivalence would no longer hold.
Critique: the order line is labelled "a contract for raft d", so it should be complete. The tempting fix is to add a guard to `Game.power` silently, which changes the zero-length `PowerStarted` contract if it returns `{}` outside play.
Consequences: a guarded `Game.power` returns `{}` outside `playing` (no `PowerStarted`). That is consistent with `died` and `cleared`, and unreachable from Session today.
Recommendation: write the order in R0090 as "decide `moving`/`frightened`, `Game.step` (Playing/Ready/GameOver/PowerEnded), move, eat, power, clear; collision after". Either guard `Game.power` like `died`/`cleared` (add a `game.spec`/`power.spec` case: `Game.power` during `ready` returns `{}` and leaves `frightened` 0, mutant "no phase guard"), or state that the invariant relies on the caller.

### F4 [low] `Game.Config.tickRate` can disagree with `Session.TICK_RATE`, which silently rescales the frightened period
Where: f0170 `Game.Config` (`tickRate`), f0160 Decisions ("Duration is `Levels.frightenedTicks(level, 30)`"), prototype `Game.power` (`g.config.tickRate`) against `eat` (`Session.TICK_RATE` for the pause).
Evidence: `Session.join` accepts a `play` config with `tickRate = 60` (validation only requires > 0). Session still steps at 30 Hz, so level 1's period becomes 360 ticks (12 s) while the eating pause uses 30. Nothing refuses the mismatch.
Critique: it's a latent configuration trap: the pauses are in ticks, but the frightened time is in seconds converted at a rate Session doesn't use. The tempting fix is to drop `tickRate` from `Game.Config`, which breaks `Game`'s standalone use and the specs that build configs.
Consequences: a check in `Session.join` (or `Session.new`) adds one error message and one config case; `CLASSIC_CONFIG` and `IMMEDIATE_CONFIG` already use 30.
Recommendation: `Session.new` errors `session: play.tickRate must be {TICK_RATE}` when they differ. Add a `config.spec` case (60 refused, 30 accepted) and a Rules row (mutant: no check).

Verdict: approve
