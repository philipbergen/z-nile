### F1 [high] The indicator's offset `x - player.x + wrap * width` is wrong for the last half tile before the edge: a ghost or player whose continuous x is past the edge of the grid gets the wrong arrow or none, and the arrow flickers each time someone crosses the wrap
Where: f0320 Design, Indicators ("the ghost's offset is then taken on the side the path leaves by (`x - player.x + wrap * width`)"); prototype `offsetVia` and `occupied` in `Awareness/init.luau`
Evidence: positions in the snapshot and the camera's pose are not wrapped: `Ghosts.position` and `Movement.position` are `tile + delta * progress / 120`, so a walker heading east on tile 27 runs x from 27.0 to 27.99, and one heading west on tile 0 runs from 0 to -0.99 (f0310's `interpolateGhosts` keeps these values and does not blend across the jump). But the search runs between rounded and wrapped tiles (`floor(x + 0.5) % width`), so once a ghost or the player is more than half way across the last tile, its tile is already on the other side while its `x` is not, and `wrap * width` corrects the wrong amount. Probe on the prototype, classic maze, the player looking east (`yaw = -pi/2`):
- The player at (2,14); Blinky chasing them east through the right edge. Ghost x 27.0 and 27.4: an arrow behind (bearing 3.14, distance 3). x 27.5, 27.6, 27.9: **no arrow** (the search finds tile (0,14) 2 tiles away with no wrap, the offset is +25.6, straight ahead, inside the field of view). x -0.4: the arrow behind again (distance 2). The ghost is 2.5 tiles behind the player the whole time.
- The player crossing the right edge eastwards, a ghost at (3,14) ahead through the wrap. Player x 27.0, 27.4: arrow ahead (bearing 0.00, distance 4). Player x 27.6, 27.9: **arrow behind** (bearing 3.14, distance 3; offset -24.7 instead of +3.3).
- The same holds mirrored for a walker heading west on tile 0 with x below -0.5.

At level 1 a ghost in the tunnel moves 15 units a tick, so the arrow of a ghost 2 to 3 tiles behind vanishes for 4 game ticks (about a quarter of a second at the server's real-time rate) every time it follows the player through the wrap, and the player's own crossing turns an arrow round for 2 ticks. Meanwhile the radar (which uses the raw positions and the short way) shows the blip behind: the two aids disagree. No spec uses a fractional x near the edge (the "does not flip" case only varies y at x = 6), so the prototype passes every check, and the documented formula is the one an executor will copy.
Critique: this is the flicker review-003 asked to remove, moved from the row boundary to the column boundary, and it is again exactly when a ghost is chasing the player through the tunnel. The tempting fix is to wrap `g.x` and `pose.x` into `0..width` before taking the difference; that just moves the seam (a raw position of 27.6 wrapped is still 27.6, while its tile is 0).
Consequences: the offset must come from the same tiles the search used, plus each walker's fraction of a tile: `dx = (tile.x - here.x) + wrap * width + (g.x - floor(g.x + 0.5)) - (pose.x - floor(pose.x + 0.5))`, and `dy` the same way (no vertical wrap, so it equals `g.y - pose.y`). At the half-tile point the tile and the fraction change together, so `dx` is continuous (27.49 gives -2.51, 27.51 gives -2.49 for a player at 2). The bearing used for the field-of-view test is the bearing of that offset, so nothing else changes; the radar needs no change (its raw-position short-way offset is already continuous and agrees with the corrected indicator). No new rule or user decision.
Recommendation: state the formula above in f0320's Design (and say in the `Ghost`/`Pose` comments that `x` runs from -1 to `width` and is not wrapped). Add cases to `awareness`: `a ghost following the player through the wrap keeps its arrow as it crosses the edge` (the player at (2,14) looking east; ghost x from 26.6 to 27.9 and then -0.9 to -0.1, step 0.1, y = 14: exactly one indicator each time, `|bearing| > 2.5`, consecutive bearings within 0.3, distance never growing); `the player crossing the edge keeps a ghost ahead through the wrap ahead` (player x from 27.0 to 27.9 and -0.9 to 0, looking east, ghost (3,14): where indicated, `|bearing| < 0.2`; no arrow pointing behind); and the west-heading mirror (the player at (25,14) looking east, ghost x -0.6: one indicator, `|bearing| < 0.2`, distance 2). Rules row: "the offset is taken from the searched tiles plus each one's fraction, so positions past the edge of the grid keep their arrow", mutant "the raw `x - player.x + wrap * width`" (the current prototype), run.

### F2 [low] Document drift: one undeclared type, one ownership mismatch, one stale sentence (the type part repeats review-003 F3)
Where: f0320 API; R0100 "What each issue owns"; f0320 Maintainability
Evidence:
- `awareness.spec.luau` annotates `r: Awareness.Radar`, but f0320's API declares only `Look`, `Ghost`, `Pose`, `Options` and `Indicator` (`radar` returns an anonymous `{ radius, walls, blips }`). I removed `export` from the prototype's `Radar`: `scripts/tracker.sh check f0320` still passes 4/4, and the raft check fails `RC0: acceptance specs will survive promotion into tests/`. - f0320 Maintainability: "The radar and the indicators share `pathDistance` and `bearing`": the radar uses neither, and since round 3 the indicators use the internal search, not `pathDistance`.

Recommendation: add `export type Blip = { x: number, y: number, look: Look }` and `export type Radar = { radius: number, walls: { { x: number, y: number } }, blips: { Blip } }` to f0320's API and use `Radar` as `radar`'s return type; move `Rng` from f0190 to f0200 in the raft's ownership list; say the indicators share the search with `pathDistance` and the radar uses its own short-way rule.

Notes (no finding): the path-based wrap is otherwise right: off-row and diagonal positions, ghosts near either end, a column descent behind the player and fractional y all get the bearing of the path; a shortest path never crosses the same edge twice, so a "two wraps away" ghost cannot occur, and a reach larger than the maze still gives one consistent side. With a reach of 17 or more, equal-length paths exist and the side is whichever the search meets first; that is a genuine tie (both arrows are right), so it needs no rule. The search overwrites `wrap` rather than summing it, which would matter only in a maze with two tunnel rows; only the classic layout has ghost data. The speed order (eyes, tunnel, frightened, normal) is stated and pinned in both directions. The order f0190 → f0320 holds and each issue's specs use only its own and earlier APIs.
