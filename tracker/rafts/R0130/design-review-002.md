### F1 [high] The c0330 spec recurses without bound on the unmodified code, which is exactly where the plan tells the executor to run it first
Where: `tracker/issues/c0330/acceptance/locator.spec.luau:102-111` (case `tracker.sh check refuses to run with AC_LIST set`, which is not gated like case 6 at line 148); c0330 Implementation steps 1 ("Confirm the spec fails on the current code (it does, in prep)") and E2; R0130 Experiments phase ("Nothing is left for the executor's experiment phase except re-confirming that each spec fails on the unmodified code before implementing").
Evidence: on the current code (no list mode, no runner refusal, no `runCheck` guard), case 4 runs `scripts/tracker.sh check c0330` with `AC_LIST=1`. That runs c0330's own `check.sh`, whose top-level `spec_out=$(lune run tests/run -- "$spec")` runs `locator.spec.luau` again with `AC_LIST=1` inherited, whose case 4 runs `tracker.sh check c0330` again, and so on. I ran `lune run tests/run -- tracker/issues/c0330/acceptance/locator.spec.luau` in a scratch clone of db496d9: after 2 s there were 22 `lune run tests/run` processes, after 16 s 154, still growing linearly, and nothing ever reports (I killed the chain). The same happens for any partial implementation that has neither the runner refusal nor the `runCheck` guard (for example `ac.sh` list mode alone, a natural first commit), and for `tracker.sh check c0330` or `tracker.sh check R0130` (RC0 calls c0330's script) run before them. E2's "fails for the intended reasons (four cases)" was measured on the first, five-case spec, before case 4 existed; the eight-case spec was only run against the designed code. Case 6 got a safety gate in round 1 for this very reason; case 4 did not.
Critique: the tempting fix is a note in Implementation step 1 ("run it with a timeout"). That leaves a spec that hangs a stream agent, its machine and any gate that runs it on a regressed `tests/run`/`runCheck` (after promotion it is in every full gate, so a later refactor that drops both guards hangs CI instead of failing it).
Consequences: gating case 4 on the two earlier cases means a broken `ac.sh` or runner makes case 4 fail with a gate message instead of exercising the guard; the "no guard in runCheck" mutant still has to die, which it does as long as `ac.sh` and the runner are right (both are then proven by cases 1 and 2). Running `tracker.sh check` on c0330 itself also couples the case to c0330's own script; a target whose `check.sh` runs no spec removes that coupling.
Recommendation: in case 4, first `if not (listing and runnerRefuses) then error("AC_LIST list mode is not safe (ac.sh or tests/run): not running tracker.sh check under it") end` (verified in a scratch clone: the spec on the unmodified code then finishes in 0.2 s, 1 passed and 7 failed), and run `tracker.sh check` on an item whose `check.sh` runs no spec at top level (for example a done issue with grep-only checks), not on c0330. Re-run the final spec on the unmodified code and on a "list mode only" partial implementation, record both (bounded, failing) in a new E6, and correct E2 and Implementation step 1. Add a Rules and mutants note that no partial implementation may make the spec recurse.

### F2 [medium] c0070's spec still accepts `gh pr ready` placed before the promotion checks, though the Rules table claims that rule is run
Where: c0070 Design ("Placing it after the last verification means it only runs when `done` will go through"); Rules and mutants row "`gh pr ready` runs only after the review, `check.sh` and promotion checks pass | `does not mark the PR ready when done refuses` | `gh pr ready` at the top of `done` | run"; `done-order.spec.luau:153-169`. Follows design-review-001 F3.
Evidence: I applied the designed block in a scratch clone (spec 5/5), then moved it to just after `runCheck`, before the promotion loop (the reading "after verification" an implementer will easily land on). The spec still passes 5/5: the refusal case only refuses at `reviewProblem`; the rollback case's assertions all hold because nothing was staged yet when `gh` fails; the success case sees origin at the previous head. The same holds for the block placed between `reviewProblem` and `runCheck`. That implementation marks the PR ready whenever the promoted acceptance specs fail (`promotedChecks` then rolls back and refuses), which is the outcome the Design rejects. The row's rule names three gates, but its case kills only the first.
Critique: the tempting fix is a refusal by a failing `check.sh`. That kills only the "before `runCheck`" placement; the promotion-check placement still survives.
Consequences: a promotion failure needs a fixture member whose acceptance spec fails once promoted, but the case must leave the fixture reusable (the rollback and success cases need a promotable, passing spec), and `gh.log` must be clear of any `pr ready` line from the earlier case.
Recommendation: extend the refusal case (or add a second one) so that `done` is refused by `promotedChecks`: commit a second acceptance spec in `tracker/issues/f0010/acceptance/` that fails (for example `t.expect(1).toBe(2)`), run `done`, assert it fails with `promoted acceptance specs fail`, that `gh.log` has no `pr ready`, and that the tree is clean and the spec still in `acceptance/`; then delete that spec and commit before the rollback case. Because the promotion checks are the last refusal before the ready call, this one case kills every earlier placement. Update the row's "mutant it kills" to "`gh pr ready` anywhere before `promotedChecks` passes" and record the run in E4.

### F3 [low] c0330's `runCheck` guard is specced only through `tracker.sh check`, so a guard placed in `cmd.check` passes while `done` stays unguarded
Where: c0330 Rules row "`tracker.sh check` and `done` refuse to run with `AC_LIST` set | `tracker.sh check refuses …` | no guard in `runCheck` | run"; AC4 ("`tracker.sh check` (which `done` uses) refuses").
Evidence: the case runs only `tracker.sh check`. A guard written at the top of `cmd.check` (a plausible place for an "argument check") passes it. Then `AC_LIST=1 tracker.sh done R…` reaches `runCheck(raft)`, the raft script lists and exits 0, and `done` goes on; it is stopped only if some acceptance spec is promoted (the runner refusal then fails `promotedChecks`). A raft with no acceptance specs is moved, committed, pushed and marked ready with nothing run.
Recommendation: keep the guard in `runCheck` as designed, and also fail at the very top of `cmd.done` (before `store.get`), so that `AC_LIST=1 tracker.sh done R9999` must fail naming `AC_LIST` (rather than "not found"); add that assertion to case 4 and name the "guard in `cmd.check` only" mutant in the row.

### F4 [low] R0130's Risks bullet on the ready-then-push window contradicts c0070's corrected remedy
Where: R0130 Risks ("if the commit or push then fails (no network), the PR is ready with a stale head and the items are moved locally; the human re-runs `git push`"); c0070 Design, "Failure after the ready call".
Evidence: c0070 was reworded for design-review-001 F5: a failure before the commit needs `git reset --hard HEAD` and a re-run of `done`, and a push failure needs `git push` plus appending `spend.md` to the PR body by hand. The raft's Risks still give the old single remedy, which is wrong for the first case (there is nothing to push, and the tree holds uncommitted moves).
Recommendation: copy c0070's two-case remedy into the Risks bullet, or point to it.

### F5 [low] Nothing tells future `check.sh` authors that list mode neutralises only `tests/run`, not other top-level work
Where: c0330 Design ("With the refusal, the top-level run is instant and inert in every existing and future script"); c0330 "Testing skill" section; `tracker/templates/issue/check.sh`.
Evidence: the refusal covers `lune run tests/run` only. A future `check.sh` that does other work outside `check` (for example `out=$(scripts/check.sh --full)`, a `rojo build`, or a clone fixture) still does it in list mode, and the permanent c0330 spec then pays for it in every full gate. Today's done scripts do nothing of the sort (their top-level work is `tracker.sh members` or a refused spec run), so this is a maintainability gap, not a current failure. design-review-001 F1 suggested the sentence as optional; it was not added.
Recommendation: add one sentence to the testing skill's "Acceptance checks" (and a comment in the template): work outside `check` is limited to running a spec through `tests/run` (which list mode refuses) and cheap file reads; everything else goes inside `check`. No spec case is needed.
