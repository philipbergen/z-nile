### F1 [medium] setup-skip-gate passes a `set +e` placed just outside the stage, which makes setup.sh report SETUP OK when the gate fails
Where: tracker/issues/c0460/acceptance/setup-skip-gate.spec.luau:36-48 (`run` prepends its own `set -euo pipefail` to the extracted block) and :80-91; c0460 AC3 ("fails when the gate fails"); R0160 Risks ("`setup.sh` guard bug could silently disable the CI gate").
Evidence: In the prototype I inserted `set +e # tolerate flaky tool steps` on the line before `if [[ -n ${PICKMAN_SKIP_GATE:-} ]]; then`. Result: `setup-skip-gate.spec.luau` gave 8 passed, 0 failed. I then ran the real tail of that `setup.sh` (from the `set +e` line to the end) against a stub gate that exits 3. It printed `GATE-RAN`, then `SETUP OK.`, and exited 0. `check.yml` runs exactly this script, so a red full gate shows as a green CI run. The spec proves only that the block fails under errexit, and it supplies errexit itself. Nothing checks that `setup.sh` still has errexit when it reaches the stage. `set +o errexit`, `set +eu` or `trap '' ERR` before the stage pass the same way. Once promoted, this spec is the CI gate's only guard against such an edit.
Critique: Round 2's fix pinned what the block does when it is run under `set -e`, but AC3 and the Risks line claim the stronger property, "the run stops". The tempting fix is to also extract and run everything from line 3 onwards. That can't work, because the earlier stages install tools.
Consequences: A text rule is cheap and matches the existing `exit` rule. `setup.sh` has exactly one `set` line today (line 3, `set -euo pipefail`) and no `trap`. Pinning that means a later legitimate need (for example a tolerant tool step) must use a local `|| true`, as the `.luaurc` line already does, or go through a chore, which is the accepted route.
Recommendation: Add a case to `setup-skip-gate.spec.luau`: the only line of `setup.sh` matching `^%s*set%s` is `set -euo pipefail`, it comes before the stage, and no line contains `trap`. Add Rules and mutants rows for `set +e` before the stage, `set +o errexit` and `trap '' ERR`, run them on the prototype, and widen AC3's text to "setup.sh keeps errexit up to the stage".

### F2 [medium] (repeat of design-review-002 F5) The documented download command fails on its second use, which the design's own E6 predicts
Where: c0460 Design "Docs" (`gh run download -n tracker-board -D .cache/board-ci`), E6, OC1; board-docs.spec.luau:18; design-refute-002 F5.
Evidence: E6 says `gh run download` "refuses to overwrite" an existing file (gh 2.83.2 here; its extractor opens files with `O_EXCL`). With a single `-n`, gh extracts straight into the `-D` directory, so the first run creates `.cache/board-ci/board.html`. Every later run of the same documented command then finds that file and fails with "file exists". Round 2 said `-D .cache/ci-board` "still fails on the second download" and recommended `rm -rf … &&`. The refute renamed the directory and called it "a fresh directory", but it is fresh only once. The Usability section promises "the latest board is one `gh run download` away", which means a repeated action.
Critique: OC1 passes, because the human downloads once. The second developer use then fails, and per OC1 that becomes a chore. The tempting fix is a per-run directory such as `-D .cache/board-$(date +%s)`. That piles up directories and gives the file no stable path to open.
Consequences: An `rm -rf` in a skill row is safe only on a fixed, gitignored path (`.cache/` is gitignored). The spec must pin the removal too, or the next rewrite drops it. OC1 must use the same command line.
Recommendation: Document `rm -rf .cache/board-ci && gh run download -n tracker-board -D .cache/board-ci` in the tracker skill's board row and in OC1. Add `rm -rf .cache/board-ci` as a board-docs token with a mutant row (the `rm` removed). Reword E6 to say the command is safe to repeat because of the `rm`.

### F3 [medium] The make-prompt readiness case passes a bullet that blocks every raft with an in-raft dependency
Where: override-check.spec.luau "make-prompt's readiness check refuses…" (tokens `depends_on`, `done/`, `stop` only); c0450 Design ("every `depends_on` of a member issue that isn't a member of this raft"); c0450 Rules and mutants row "the chore really lands first".
Evidence: A hurried bullet such as "Every `depends_on` of a member issue names an item in `done/`; otherwise stop." contains all three tokens, so it passes. It is wrong for any raft whose members depend on each other. `tracker.sh workstreams` builds its waves from exactly those in-raft `depends_on` (main.luau:473-526), and the backlog already carries many of them (for example f0250 `[f0150, f0170]` and f0160 `[f0150, …]`, all undone). With that bullet, make-prompt refuses those rafts once they are prepped, until their own members are done, which never happens. The "isn't a member" exclusion is the rule's whole precision, and nothing pins it.
Critique: This is the one new rule with a real false-positive mode, and the spec tests only that the rule exists. The tempting fix is to pin the word `member`, which already appears in the existing step-2 bullet "The raft and every member are `design: ready`", so that token is satisfied regardless.
Consequences: The pinned token must be one that only the new bullet supplies. The step-2 section has no "outside" or "isn't a member" today, so `isn't a member` (or `outside this raft`) is unique. The wording in the Design must use that exact phrase.
Recommendation: In the Design, fix the bullet's phrase as "a member issue's `depends_on` id that isn't a member of this raft", and add `isn't a member` to the make-prompt case's tokens. Add a Rules and mutants row: "every `depends_on` must be in `done/` (no member exclusion)" → fails, and run it.

### F6 [low] The "remove" half of the chore route leaves the spec's owning item with a check.sh that points at a deleted file
Where: c0450 Solution and Design ("a chore that only has to **remove or narrow** the spec").
Evidence: Every promoted spec is run by its owner's `check.sh` through the fallback `A="$PWD/tests/acceptance/<id>"` (for example `tracker/issues/done/c0010/check.sh` → `$A/ci-workflow.spec.luau`). If the chore deletes the file, that `check.sh` fails when run (`tracker.sh check <owner>`). The gate stays green only because c0330 runs done items in `AC_LIST=1` mode. Done items' `check.sh` files are sequestered history, so the chore shouldn't edit them either.
Critique: Without this, the route quietly creates a broken check that someone will later re-run and misread as a regression. The tempting fix is to let the chore edit the owner's `check.sh`, which breaks sequestration for finished items.
Consequences: "Narrow" keeps the file, so the owner's check still runs. "Remove" needs either a kept file or a recorded note.
Recommendation: Write "prefer narrowing (keep the file, drop or relax the cases); if a whole spec must go, the chore records in its Regression guard that `<owner>`'s `check.sh` line for it is retired". Add no token unless you want to pin it.
