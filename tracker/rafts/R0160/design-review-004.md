### F1 [medium] Every dependency list in the spec has one element, so a check that reads only the first `depends_on` id passes
Where: tracker/issues/c0480/acceptance/start-depends.spec.luau:83-86 (every `depends_on` edit is a single id); c0480 AC1 ("any member … depends on …"); Rules and mutants (no row for list form).
Evidence: I changed the prototype's loop to `for _, dep in { store.idList(store.readFront(m.doc).depends_on)[1] } do`, and start-depends gave 9 passed, 0 failed. The same gap lets through an implementation that leaves a member's list at its first raft-mate (`return`/`break` on `inRaft[dep]`, a natural shape when the check is written as a helper). Real backlog lists have several ids and mix raft-mates with outside items: f0200 `[f0190, f0160]`, f0310 `[f0190, f0200, f0210, f0130]`.
Critique: The Design gives the code verbatim, so a careful executor won't write this. But the spec is what gets promoted, and it is the only guard against a later refactor (for example a shared "ready to start" helper, which Maintainability already invites). The tempting fix is a new sandbox raft. That adds a `new issue` and `new raft` round trip and renumbers nothing useful.
Consequences: Change only the existing late raft. f0070 gets `depends_on: [f0060, f0010]`, where f0060 is its raft-mate in R0050. The raft-mate comes first, so the exempt id comes before the refused one. That case then kills "first id only" and "stop at the first exempt id", and the existing assertions (`f0070` and `f0010` in stderr) stay valid. I ran it: the correct prototype gives 9/9, and the first-id mutant gives 7/9 (start R0050 succeeds). No other case reads f0070.
Recommendation: In the spec setup, edit f0070's frontmatter to `depends_on: [f0060, f0010]` and update the comment on line 82. Rename the case to `checks every member and every dependency in its list` and add the Rules and mutants row: "every id in a list is checked, a raft-mate first doesn't end the scan" → "first id only / return at the first raft-mate" → `run`. Record the run in E2.

### F2 [medium] An executor whose `start` is refused has no instruction, and a resumed raft worktree can refuse a dependency that has already landed
Where: c0480 Design (the `fail` message "…: it must be done first"), Non-goals ("Changing … `worktree`"), Touched modules (the tracker skill and main.luau only); execute-raft Phase 0 step 2 and Stop conditions; `cmd.worktree` (main.luau:637-647 resumes an existing branch or worktree as it is).
Evidence: (1) execute-raft's Stop conditions don't name a refused `start`. The escalation steps ("Push", "Leave the PR in draft", "Post a PR comment that starts with `BLOCKED:`") assume a PR, and a refused `start` creates none. An agent new to the repo has two obvious ways to "make start work": delete the `depends_on` entry (an ordinary tracked file, not sequestered), or move the dependency's directory. Both defeat c0450's chore route, which is what c0480 exists to enforce. (2) The check reads the raft worktree's own tree. Take `tracker.sh launch R0100` before R0090 lands: `worktree` creates `.worktree/R0100` from origin/main, and `start` is refused (f0160 active). The worktree stays. After R0090 merges, the next `worktree R0100` or `launch R0100` finds the path and prints it as it is (`if w.path == path then print(path) return`), or resumes the local branch. The fetch at the top doesn't update that branch, so `start` again says "f0160 … which is backlog: it must be done first" while f0160 is in `done/` on main. (3) A dependency that was deleted (an obsolete issue) gets "which is unknown: it must be done first". The fix there is to edit `depends_on`, which the message never mentions.
Critique: The rule is right, but its refusal path is the one part an agent will meet unprepared. The tempting fix is a longer error message alone. That fixes (2) for a human, but an agent still has no stop rule, and nothing pins the hint.
Consequences: Merging origin/main into a stale raft branch before `start` is safe. `start` needs a clean tree, and the merge commit just precedes the start commit. Editing `depends_on` must stay a human decision, because it is exactly the ordering c0450 asks for. c0470 also edits execute-raft, but in the final-verification phase, so a one-line addition to Phase 0 or Stop conditions doesn't collide; list it in both issues' Touched modules notes, or c0480's workstreams overlap changes. Putting it only in the tracker skill's `start` row, which c0480 already touches, avoids a new Touched module. But execute-raft says "don't improvise", and it only stops on listed conditions.
Recommendation: (a) Extend the message to "…: it must be done first (as this branch sees it; if it has merged, `git merge origin/main` and retry; never edit depends_on to get past this)". Pin `origin/main` in the three refusal cases of start-depends and add a mutant row (hint removed). (b) Add a Stop-conditions bullet to execute-raft: "`tracker.sh start` refuses an unfinished dependency and merging origin/main doesn't help: stop, don't edit `depends_on` or move items, and report in the final report (no PR exists yet)". Add `.claude/skills/execute-raft/SKILL.md` to c0480's Touched modules, and add a doc-token case such as `refuses an unfinished dependency` with its mutant row. Re-run `workstreams R0160`; it still gives c0480 wave 2. If you'd rather not touch execute-raft, put the same sentence in the tracker skill's `start` row, pin it in the AC4 case, and say in the Design why the Stop-conditions list doesn't need it.
