### F1 [medium] A run inside another sandbox is green and unjailed unless it happens to include the gate spec; the nesting trial also misjudges permissive sandboxes
Where: `tests/lib/fence.luau:255-257` (`jail`: trial with `(allow default)`, on failure "outer sandbox", run continues); c0640 "The jail", "Already inside a sandbox"; testing skill, Caught only by review, "Runs inside another sandbox"; Rules and mutants J3
Evidence (`--no-hardlinks` clone of the prototype under the scratchpad, with a probe spec that writes `<checkout>/WROTE-ROOT`):
- Started plainly, the probe failed (jailed). Started under an outer sandbox that allows writes to the checkout (`sandbox-exec -p '(version 1)(allow default)(deny file-write* (subpath "/nonexistent-z"))' lune run tests/run -- tests/probe/w.spec.luau`), the run printed `note: already inside a sandbox …` and `1 passed, 0 failed`, exited 0, and `WROTE-ROOT` was written. Only `repo-fence`'s jail case would have failed, and targeted runs (`tracker.sh check <id>`, `check.sh --affected` with a narrow selection, `lune run tests/run -- <spec>`) don't include it. Such a run has the Linux level of protection on a Mac, and nothing says so except a `note:` line.
- Under an outer sandbox whose profile is just `(allow default)`, the trial **succeeds** (`trial=0`), but the real profile then fails to apply (`sandbox-exec: sandbox_apply: Operation not permitted`, exit 71). The run ends with exit 71, runs no spec and prints no explanation. It fails closed, but the cause is cryptic. E13 was measured only from inside the jail, whose profile has deny rules.
- Claude Code's own Bash sandbox is a Seatbelt profile that allows writes to the project directory, which here holds the main checkout, `.git` and every worktree. It isn't enabled in this project today. If the user turns it on, the central guard silently stops applying to every agent's runs.
Critique: the user asked that no check can ever break the repository, and that the boundary be clear. The docs do list "runs inside another sandbox" under Caught only by review. But review can't catch this, because it depends on the shell a run is started from, not on code in a diff. The tempting fix is a louder note, which changes nothing for an agent that doesn't read notes on a green run.
Consequences: refusing to run in a permissive outer sandbox must not break c0640's own specs, whose inner runs are always "outer sandbox" (the jail itself), with a fixture checkout under `<root>/.cache` that the jail lets them write. It also means that an agent with a sandboxed Bash must run specs with the sandbox disabled. The user should know that, and the testing skill should say it.
Recommendation:
1. The trial applies the real profile: `sandbox-exec -p <profile> /usr/bin/true`. That way any outer sandbox is detected the same way, and an outer `(allow default)` no longer ends in exit 71.
2. When a top-level run on macOS can't jail, it probes writes before any spec runs. It uses the gate case 4 probe set: untracked files in `<here>`, the common dir and the main checkout, removed at once. There is one exception: if `<here>` lies under `<c>/.cache` for a checkout `<c>` in the inherited `PICKMAN_FENCE_REAL_GIT`, it probes `<c>` and its git dir instead. If any write succeeds, the run exits 1, names the writable paths, and says to run specs outside that sandbox.
3. Add a case to fence.spec, `a run in a sandbox that would let it write the repository refuses to start`: an inner run with `PICKMAN_FENCE_REAL_GIT=""`, whose fixture checkout the outer jail allows writing, exits 1 and runs no probe. The existing "a run inside a sandbox …" case still passes, because its probe target, the root, is denied by the outer jail. Add the mutant row "unjailed run does not probe".
4. Docs: move "runs inside another sandbox" from Caught only by review to Enforced ("refused unless the outer sandbox denies the same writes"). Add it to AGENTS.md, and add one line to the testing skill: a sandboxed agent shell must run specs with its sandbox disabled.

### F2 [medium] A `check.sh` started inside a spec run gets git's keychain credential helper back, contrary to the testing skill and AC2
Where: `scripts/lib/fence.sh` (checks mode re-exports `GIT_CONFIG_COUNT=3`, so the specs-mode `GIT_CONFIG_KEY_3=credential.helper` / empty value is ignored); testing skill "No network for specs": "A `check.sh` started from inside a spec run keeps these limits"; c0640 Environment guards "Nesting"; AC2
Evidence: in scratch, using the prototype's `fence.sh` unchanged, I ran `pickman_fence <dir> specs`, then the nested `pickman_fence <fixture>` that `ac.sh` runs in a fixture's `check.sh`. Results:
- `git config --get-all credential.helper` went from `osxkeychain` followed by an empty entry to `osxkeychain` alone.
- `COUNT=3 SPECS=1`.
- `GIT_TRACE=1 git credential fill` then ran `git credential-osxkeychain get`.

Fixture `check.sh` files run inside spec runs all the time (`tracker.sh done` in c0070, c0360 and c0010 fixtures). There, `git credential fill` returns the user's GitHub token. The push guard still refuses non-local pushes, because `PICKMAN_FENCE_SPECS` is inherited, so I found no direct path to damage. But one of the two layers the docs promise is gone, and a token is in reach of any fixture script. N4 ("helper kept") was mutated only at the spec level, and no case covers a nested `check.sh`.
Critique: the tempting fix is to also export `KEY_3` in checks mode. That would break `scripts/ci-verify.sh` in real `check.sh` flows, which need the helper.
Consequences: the mode has to follow inheritance, which R4 already does for the fetch exception: a guard set up inside a spec run is a specs-mode guard.
Recommendation: `pickman_fence` treats an inherited `PICKMAN_FENCE_SPECS=1` as `specs` mode, so it re-applies every specs-only setting, the helper reset, `GIT_SSH_COMMAND`, the unset tokens and `SSH_AUTH_SOCK`. Extend the fence case `ac.sh gives check.sh files the same guards`: run it once with `PICKMAN_FENCE_SPECS=1` in its env, and assert that the last `credential.helper` entry is empty and that `GIT_SSH_COMMAND` is still the refusal. Add mutant N6 "nested checks-mode guard drops the specs limits".

### F4 [low] The jail's "nothing a spec does can change the repository" needs two qualifiers
Where: testing skill Jail bullet; c0640 Solution "It doesn't matter how a spec got there"
Evidence and fixes:
- **Processes outside the jail act for the spec**: Seatbelt filters writes made by the spec's process tree. A request to a process that was started outside it isn't filtered: LaunchServices (`open`, used by `tracker.sh board --open`), `osascript`, `launchctl`, or a daemon that is already running. None of these is an accidental git path today. Add "work handed to a process outside the run (`open`, `osascript`, `launchctl`)" to Caught only by review, and optionally add `osascript` and `launchctl` to the scan list.
- **Symlinked home files**: Seatbelt matches resolved paths. In scratch, a `deny (subpath "/tmp/x")` did not stop a write to `/tmp/x/f`, because `/tmp` resolves to `/private/tmp`. The `~/.gitconfig` and `~/.config/git` rules use `$HOME` as given. With a dotfiles setup where `~/.gitconfig` is a symlink, git writes the target, and nothing denies that. It isn't the case on this machine. Fix: resolve each deny path, the HOME paths and the inherited `PICKMAN_FENCE_REAL_GIT` entries, with `realpath` before writing the profile, and deny both the given and the resolved path.
