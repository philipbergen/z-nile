### F1 [high] AC5 is passed by an adapter that calls TeleportAsync on every press, and by a client that never redraws on Status
Where: f0670 `acceptance/lobby-adapters.spec.luau` (all server cases are ordered text searches); Rules rows "A teleport is attempted only with a destination and after Travel.request says go", "The status reaches the player only when it changes", "The client draws Lobby's models"
Evidence: on the prototype I moved the engine call out of the guard in `Starts`:
```lua
if Travel.request(travel, id, os.clock()) == "go" then
	push(player, "going")
end
local ok = pcall(TeleportService.TeleportAsync, TeleportService, destination, { player })
```
and replaced the client's `status.OnClientEvent:Connect(show)` with `status.OnClientEvent:Connect(function() end)`. `scripts/check.sh --full` (766 passed) and `tracker.sh check f0670` (7/7) both stay green. The first mutant is exactly what the Design forbids ("a spammed press is a no-op (one phase check, no engine call)"): every press reaches the engine. The second leaves the button at its first draw (`show("idle", true)`, a live START GAME) for ever, also in an unconfigured lobby, so AC2's "button for each status" never reaches the screen. The text specs check that `"go"` appears before `TeleportAsync`, not that the call is inside the branch; the "only when it changes" case checks the literal `shown[player] ~= phase`, which a dead or bypassed comparison still contains, and which a correct dedupe written with other names fails.
Critique: the tempting fix is more source patterns (e.g. "TeleportAsync between `then` and `end`"). That is still passable by a wrong shape and breaks correct ones (a `pcall(function() return TeleportService:TeleportAsync(destination, { player }) end)` already fails the "carries the destination" case).
Consequences: driving the real adapter needs a fake engine: services, signals, a `require` that maps `@game/ReplicatedStorage/Shared/Logic/<X>` to the Logic module, and an injectable clock (`os.clock`). It is a new test helper (a Touched path) and the adapter specs then depend on its fidelity; Roblox-only behaviour (whether `TeleportAsync` yields, `TeleportInitFailed` timing) stays E7/O1/O2.
Recommendation: replace the server text cases with a behavioural spec that loads `Starts.Source` from the built lobby with `@lune/luau`'s `luau.load(source, { environment = env })`, where `env` supplies `game:GetService` fakes (RemoteEvent with `OnServerEvent`/`FireClient`, `TeleportService` with a scripted `TeleportAsync` and a `TeleportInitFailed` signal, `Players`, `RunService.Heartbeat`, `ServerScriptService:GetAttribute`), a fake `os.clock`, and a `require` returning the real Logic modules. I ran a 30-line version of this: five presses give 1 `TeleportAsync` call on the prototype and 5 with the mutant above. Cases: five presses while going give one engine call; no attribute (or 0) gives no engine call and one `Status("idle", false)`; a failing call and a `TeleportInitFailed` each give `Status("cooling", true)`, and Heartbeats past 3 s give `Status("idle", true)` once (dedupe counted as messages, not as text); the call's arguments are `(destination, { player })`; a handler given an extra client argument behaves the same. Keep only the text checks that are about absence (no `MouseBehavior`, no `TeleportService` in the client, `FireServer()` with no arguments). For the client, either run `LobbyView` the same way with `@lune/roblox` `Instance.new` and a fake `Status` signal (fire `("cooling", true)` and read `Start.Text`/`Active` and `Message.Text`), or, if Lune cannot construct the GUI (an experiment with that pass/fail question), at least pin that the `Status` handler draws through `Lobby.button`. Update the Rules table's mutants (teleport outside the guard, a no-op Status handler) and record them as `run`.

### F2 [medium] After the 15 s timeout a second TeleportAsync can run while the first still yields, and a late failure of the first cools down the second
Where: f0670 Design "Failure handling", `Starts` (prototype `StartGame` handler and `TeleportInitFailed`), `Travel.failed`; Rules row "One request per player at a time"
Evidence: t=0 press: `go`, `pcall(TeleportAsync)` yields (E7: its duration is unknown). t=15 the Heartbeat step calls `Travel.status`, which turns `going` into `cooling` (pushes "Could not start"); t=18 `idle`, the button is live; a press gives `go` and a second `TeleportAsync` for the same player while the first is still in the engine. When the first then errors (or `TeleportInitFailed` fires for it, e.g. `IsTeleporting` caused by the second), `Travel.failed(travel, id, now)` puts the *second* request into `cooling` and frees the player for a third at +3 s. `Travel` has no notion of which request a report belongs to, and `TeleportInitFailed(player, teleportResult, errorMessage, placeId, teleportOptions)` carries no request id. The Design promises "one teleport per player at a time" and the Risks section says the timeout turns any non-answer into a retry, but nothing distinguishes "the engine has not returned" from "the engine returned and nothing happened".
Critique: the tempting fix is an adapter-side `calling[player]` flag that blocks a press while the pcall yields. That moves a decision into the adapter (architecture: adapters only relay) and is untested.
Consequences: if the timeout no longer runs while the call yields, a call that never returns locks the player in STARTING... (unknown engine behaviour); if it does run, overlap must be an accepted, documented rule. Either choice adds a Travel transition and spec cases, and f0710 reuses Travel unchanged, so it inherits the choice.
Recommendation: make it a Travel rule. Add `Travel.answered(t, id, now)` (the engine call returned without error): the 15 s timeout counts from the answer, not from the request, so no second request can start while the call is in the engine; a `failed` or `answered` for a player who is not `going` changes nothing (this also drops a late `TeleportInitFailed` after the timeout). If the user prefers no lock-out risk from a hung call, add a hard cap (e.g. 60 s from the request) as a named constant. Cases in `travel.spec`: "while the engine call has not returned the player stays going past 15 s", "after the answer an unanswered teleport times out at 15 s", "a failure reported while cooling or idle changes nothing"; in the behavioural adapter spec of F1: a `TeleportAsync` that yields past 15 s gives one engine call across repeated presses. Rules rows with mutants "timeout counted from the request", "failed honoured while cooling".
