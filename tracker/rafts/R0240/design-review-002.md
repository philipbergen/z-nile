### F1 [high] The fake engine ignores names and the instance tree: AC5 passes adapters that leave the real lobby dead, and fails correct ones
Where: `tests/lib/fakeengine.luau` (prototype): `remotes.WaitForChild` returns `status` for any name but `"StartGame"`, `ReplicatedStorage.WaitForChild` and `ServerScriptService.GetAttribute` ignore their name, the client's `newInstance` registers an object in `named` whenever any `Parent` is set; server env has no `Instance` or `task`. AC5; Rules rows "The destination comes from the attribute ...", "The client draws the panel's empty state ..."
Evidence: each of these mutants passes all 57 cases of the six acceptance specs:
- `Starts`: `GetAttribute("PlaceId")` (the real lobby is UNAVAILABLE for ever, whatever c0700 sets);
- `Starts`: `remotes:WaitForChild("StatusEvent")`, or `ReplicatedStorage:WaitForChild("Remote")` (the real server yields for ever and never connects `StartGame`);
- `LobbyView`: `remotes:WaitForChild("LobbyStatus")` (the real client never gets past it: no screen at all);
- `LobbyView`: the line `gui.Parent = Players.LocalPlayer:WaitForChild("PlayerGui")` dropped, or `backdrop.Parent = gui` dropped (nothing is drawn; `c.find("Start")` still finds the button because `button.Parent = backdrop` registered it);
- `LobbyView`: the backdrop white, or `UDim2.fromScale(0.2, 0.2)` (the "black backdrop covers the screen" decision is unpinned).
The other way round, correct implementations fail: `remotes.StartGame` / `remotes.Status` by dot index (the most common Roblox idiom) fails 13 cases; setting `button.Parent` before `button.Name` fails 4; a `task.wait()` or `task.spawn` in `Starts` fails 11 (`task` is nil in the env); passing `Instance.new("TeleportOptions")` to `TeleportAsync` fails 11. The last one is the fallback E7 names ("if `TeleportAsync` needs `TeleportOptions` ... only the one call in `Starts` changes"), and the specs are sequestered, so an executor who meets it cannot take it. (The `pcall(function() return TeleportService:TeleportAsync(...) end)` form passes: good.)
Critique: AC5 says the server "takes the destination from configuration" and the client "draws `Lobby`'s models"; a wrong attribute name or an unparented GUI is exactly the wiring defect a fake-engine spec is for, and it is only caught by O1 in Studio. The tempting fix is to add the missing names as `if name ~= "Status" then error`, case by case, which leaves the fake's tree and the remote names duplicated by hand from `lobby.project.json`.
Consequences: a stricter fake must still accept every correct way of reaching an instance (`WaitForChild`, `FindFirstChild`, dot index), so it needs a real child map; its names should come from the built lobby place (`place.load("lobby.project.json")`), so the project file and the adapters can't drift apart unnoticed; a `WaitForChild` on a missing name must fail the spec (it would yield for ever); adding `task` brings a scheduling choice (run `spawn`/`defer` at once, make `wait` yield until the next `tick`). The fake's supported surface becomes a contract the executor must know.
Recommendation: give the fake a small instance model: `Name`, `Parent`, children, `WaitForChild`/`FindFirstChild`/`__index` by child name, an error naming the path for a missing child. Build the server's `ReplicatedStorage.Remotes` from the built lobby's `Remotes` children, answer `GetAttribute` only for the attribute names the built `ServerScriptService` carries, and make the client's `find(name)` search only under the `PlayerGui` through `Parent` links (so `gui.Parent` and `backdrop.Parent` count). Add `Instance.new` for `TeleportOptions` and a `task` with `spawn`/`defer`/`wait` to the server env. Cases in `lobby-adapters`: the `Start` button and `Backdrop` are descendants of the `PlayerGui`; the backdrop is black and `fromScale(1, 1)`; the server's destination is read from the attribute the built place carries (set the fake's attribute under a different name and expect no engine call). List the survivors above as mutants (`run`), and state the fake's surface in its header and in the Design's Files and API so an executor knows which idioms are supported.

### F2 [medium] The adapter may report the answer with the request's time: round 1's "timeout counted from the request" survives at the adapter (repeat of review-001 F2, adapter half)
Where: `lobby-adapters.spec.luau`; Rules row "Once the engine call has returned ... the timeout counts from the answer" (mutant "a timeout counted from the request" is killed only in `travel.spec`)
Evidence: in `Starts`, `local t0 = os.clock()` at the top of the handler and `Travel.answered(travel, id, t0)` passes all 57 cases (a plausible "read the clock once" refactor). Every case that holds a call releases it with a failure; none releases a held call successfully and then watches the 15 s. With the mutant, a `TeleportAsync` that returns after 14 s leaves the player 1 s before cooling and a new call, which is what round 1's F2 asked `answered` to prevent.
Critique: the Travel rule is right; the adapter's wiring of it is untested.
Consequences: none beyond the case.
Recommendation: add a case: `engine.mode = "hold"`, press, `tick(20)`, `release(1, false)`, `tick(14)` still shows only `going/true` and a press makes no second call, `tick(2)` shows `cooling/true`. Add the mutant "the answer reported with the request time" to the row as `run`.

### F3 [medium] The accepted overlap is misstated: a stale report of the abandoned call lets a third call start while the second is still in the engine, before its cap
Where: f0670 Decisions "Failure handling" ("... a very late failure of the first costs the newer request one cool-down (never a third call): accepted", a sentence that also reads cut off); Rules row "Accepted overlap" (`reasoned`); `lobby-adapters :: a call abandoned after the cap that fails very late ... never a third call`
Evidence: on the prototype with the fake: call A held, `tick(61)`, `tick(4)`, press (call B held, B's cap at 125). (a) `release(1, true)` (A fails): B is cooled; `tick(4)`, press: `#engine.calls == 3` while B is still in the engine. The spec case stops right after the release, inside the 3 s, so its name holds only for 3 s. (b) at t=70 `release(1, false)` (A returns): `Travel.answered` applies to B and moves B's deadline from 125 to 85; at t=89 a press makes the third call, B still in the engine. So the "one call at a time until the cap" property breaks for the newer request too, by reports that belong to the old one; f0710 reuses `Travel` and inherits whatever is written here.
Critique: the tempting fix is to soften the sentence. That is honest but leaves (b), a successful stale answer, silently shortening the newer request.
Consequences: telling reports apart needs a request identity. `TeleportInitFailed` carries none, so it can never be told apart; the `pcall` result can, because the handler's closure knows which request it made. A ticket changes `Travel.request`'s signature (e.g. a second return value) and `answered`/`failed` take it; the specs that call them (`travel`, `lobby-run`) change with it, which is cheap now and expensive after promotion.
Recommendation: either (1) give each "go" a ticket (`Travel.request` returns `"go", ticket`; `answered(t, id, ticket, now)` and the `pcall` failure ignore a ticket that is not the current one; `TeleportInitFailed` keeps applying to the current request), or (2) keep the API and write the rule as it is: "past the cap, a late answer or failure of the abandoned call is applied to the newest request; after its cool-down (or 15 s) a further call may start while that one is still in the engine". With either, finish the sentence, rename the case to what it proves and extend it past the cool-down (with (1): `#calls` stays 2 after `tick(4)`, and a stale success leaves B going to its own cap; with (2): `#calls` becomes 3, documented). Rows: (1) mutant "a stale ticket honoured" (`run`).

### F5 [low] A report that arrives after the player left re-adds them to `shown` and fires `Status` at a departed player
Where: prototype `Starts`: `sync` after a failed `pcall` and in the `TeleportInitFailed` handler; `PlayerRemoving` clears `shown[player]` first
Evidence: with the fake, `engine.mode = "hold"`, press P1, `leave(P1)`, `release(1, true)`: P1 gets a second `Status` (`idle`) after leaving, and `shown[P1]` is set again for good (a `Player` key kept for the server's lifetime). The same for `initFailed(P1)` after `leave(P1)`. The mutant "`shown[player] = nil` dropped" also survives every spec (it is not observable without this case).
Critique: a slow `TeleportAsync` that fails after the player closed the app is a realistic order; the leak is small but unbounded over a long-lived lobby server.
Consequences: the adapter needs to know a player is gone; `player.Parent == nil` is how Roblox says so, and the fake's `leave` would then set it.
Recommendation: in `push`, return when the player is no longer in the game (`player.Parent == nil`); make the fake's `leave` set `Parent = nil`; add a case "a report after the player left sends nothing" (leave during a held call, release with a failure, expect no message after the leave), with the mutants "push to a departed player" and "shown never cleared" (`run`).

Verdict: changes
