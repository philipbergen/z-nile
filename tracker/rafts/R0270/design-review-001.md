# Review 001: R0270 (design mode)
Inputs: prep worktree at 7c6fa30 plus its uncommitted prep edits (R0270.md, check.sh; c0870 and c0880 documents, check.sh, acceptance/*.spec.luau, experiments/prototype.diff); prototype branch proto-r0270 at b6ec479; origin/main 515bd7e; scripts/tracker/*, tests/acceptance/*, the review, testing, ticket-prep and tracker skills. Experiment I ran: the prototype's `tracker.sh compact` on a scratch clone of proto-r0270 (outside every repository, under the session scratchpad, bare origin of its own), then `scripts/check.sh --full` on the compacted tree.

### F1 [high] next-file.spec puts "the counter is above every number in use" into the permanent gate, but the design treats a lagging counter as a harmless warning, and the lag happens in ordinary use
Where: tracker/issues/c0870/acceptance/next-file.spec.luau, case "is above every number in use, per space"; c0880 audit table (`next-behind` is a warning, with the reason given); R0270 Risks ("Terminals running the old tracker … Harmless … the audit warns").
Evidence: `done` promotes next-file.spec to `tests/acceptance/c0870/`, so it runs in every `scripts/check.sh --full`, in CI on every PR and in every raft's check.sh. It asserts `c.issue > ids.highest("issue", list)` on the checkout's own tree. Three ordinary situations break it:
(a) An emergent issue on a raft branch. In the prototype, `new issue … --raft` calls `reserveOnOrigin` and then writes the stub locally. The local `tracker/next` is never touched, because "offline never writes the counter" and that path has no merge. So with a local counter of 954 the branch gets `c0954`, `954 > 954` fails, and the raft's gate stays red until it merges `origin/main`. `renumber <id>` behaves the same way. c0880's own design names this case as the reason `next-behind` must stay a warning: "must not fail its gate".
(b) After R0270 merges, a worktree cut earlier still runs the old tracker. It publishes `c0900` (next multiple of 10) without raising the counter. From then on every PR's CI, which tests the merge with main, fails next-file.spec. That lasts until some new-code allocation happens to push the counter past 900. Tracker-only pushes skip CI, so main itself looks green.
(c) Any `PICKMAN_PUBLISH=0` allocation (allocate.spec's own offline case leaves the local counter equal to the new id).
Critique: the spec and the design disagree about what a lagging counter is. The quick fix is to make every allocation also write the raised counter locally. That makes things worse: the branch then changes `tracker/next` differently from main, the two sides carry different phrases, and every later merge of `origin/main` hits a content conflict on that file.
Consequences: if the strict check is removed from the gate, nothing checks that the executor computed the real counter correctly. That costs no correctness (`nextFree` skips used numbers, and compaction recomputes the counter), but a wrong value would go unnoticed.
Recommendation: in next-file.spec, keep only "exists and parses" (or drop the file: real-tree.spec already makes `next-missing` and `next-malformed` gate errors). Move "above every number in use" into R0270/check.sh as an RC, which runs once at `done` and is never promoted, for example `check "RC3: tracker/next is above every number in use" bash -c '! scripts/tracker.sh audit | grep -q next-behind'`. Update AC6's wording to match. Add one allocate.spec case pinning the intended behaviour: after an emergent `new issue --raft`, the local `tracker/next` is unchanged and `tracker.sh audit` exits 0 with a `next-behind` warning.

### F2 [high] The documented compaction procedure leaves the full gate red: two specs pin real tracker ids or paths that compaction moves
Where: R0270 Risks ("in a fresh worktree `tracker.sh compact`, `scripts/check.sh --full`, PR, merge"); c0870 Non-goals (ids outside `tracker/` keep old ids); c0870 E1, which checked only `tests/acceptance/<id>` paths.
Evidence: the prototype compacted a clone of proto-r0270 to 83 issues and 27 rafts. The full gate on the result: `1187 passed, 2 failed`.
- `tests/acceptance/c0043/rounds.spec.luau` (old c0410) :: "counts design-review and review files per raft". It reads the real tracker's metrics and expects rows `R0010`, `R0030`, `R0050`, `R0070`. After compaction those rafts are `R0001`, `R0003`, `R0005` and `R0007`.
- `tests/tooling/repo-fence.spec.luau`: its `ALLOWED` table keys `tracker/issues/done/c0640/check.sh`. The folder becomes `done/c0058`, so the scan reports `tracker/issues/done/c0058/check.sh names GIT_CEILING_DIRECTORIES` and `… names sandbox-exec`.
Neither spec is touched by this raft's diff, so no check in R0270 can see the problem. The user's one-time run fails at its `check.sh --full` step. The fix needs an edit to a promoted spec, which is a separate chore and a separate PR. Meanwhile every open branch stays parked, waiting for main to go quiet.
Critique: the tempting fix is to extend `ids.rewritePaths` to `tracker/(issues|rafts)/…/<id>` paths in all files. That is wrong: fixture literals such as `"tracker/rafts/R0010/R0010.md"` in c0010/tracker-lifecycle, c0070, c0360 and c0420 start with a quote, so the token-start rule would rewrite them and break those specs.
Consequences: the fix touches a promoted spec (c0410/rounds), so it needs an Overrides entry in c0870. Specs that land between prep and the compaction (R0250, R0260) can add more such pins, so a single check now does not stay valid.
Recommendation:
(1) Add `tests/acceptance/c0410/rounds.spec.luau` to c0870's Touched modules and Overrides. Narrow it so it holds both before and after compaction: when `tracker/compaction.txt` exists, map R0010, R0030, R0050 and R0070 through `ids.parseMap`.
(2) Make the `repo-fence.spec` ALLOWED entry for c0640's check.sh hold after compaction, for example by mapping the key through `tracker/compaction.txt`, or by keying the entry on a path that compaction rewrites. Add both files to Touched modules.
(3) Add an experiment or implementation step, run after the final merge of `origin/main`: run `tracker.sh compact --force` in a `$TMPDIR` clone of the raft branch, then the full gate there. Any failure is fixed in this raft as an emergent chore.
(4) In Risks, tell the user what to do if the gate fails after compaction: discard, file a chore, fix it on main first, then compact again. Compaction is deterministic, so this is cheap.

### F3 [medium] After compaction, any branch cut before it reinflates the counter, because allocation counts the local tree's old-scheme ids
Where: c0870 Design, Allocation ("`used` is origin's ids plus the local tree's"); prototype `cmd.new` (`localIds("issue")` is added to `used`), `reserveOnOrigin(…, localIds(…))`, `renumber`; compact step 2 (only branches that change `tracker/` or `tests/acceptance/` are reported).
Evidence: compaction lands with counter `issue 84`. A worktree whose branch changed no tracker files was not "busy", so compaction neither refused nor listed it. Its tree still holds `c0890` and older. Now it runs `tracker.sh new issue c x`: `nextFree = max(84, 890 + 1) = 891`. The stub `c0891` is published to main and the counter becomes 892. One stale terminal undoes the compaction, and nothing errors: the audit sees a sound tree.
Critique: the easy fix is to count origin's ids only. That breaks the protection against unpublished local ids (offline-created items, an emergent issue not yet merged), which is why local ids are counted in the first place.
Consequences: a refusal rule needs a way out and a message, and remap already provides the way out. Branches still running pre-R0270 code can't be fixed by code. Only the procedure can cover them.
Recommendation: allocation (`new`, emergent `new`, `new raft`, `renumber`) refuses when origin/main has a `tracker/compaction.txt` that differs from the local one (or is missing locally), with a message such as "this tree predates the compaction: merge origin/main, or run tracker.sh remap on a branch that changed the tracker". Add a remap.spec case: on the stale branch, before `remap`, `new issue` refuses and origin's counter is unchanged. In compact step 2, also print every other ref ahead of `origin/main` as `not busy, but sync before allocating: <ref>`. In Risks, say that worktrees cut before R0270 merged must be removed or synced before compacting.

### F4 [medium] `renumber <directory>` on a done copy breaks its check.sh, and later collides in tests/acceptance; the docs never say which copy to renumber
Where: c0880 Design (`cmd.renumber`, "ids.rewrite … over that folder's .md and .sh files only"); cli.spec "renumber <directory> moves only that copy…" renumbers `tracker/issues/done/c0010`; the Duplicate ids bullet (implementation step 4).
Evidence: the motivating duplicate is an emergent issue filed in `done/`, so its specs are promoted to `tests/acceptance/c0510`, plus a backlog stub with the same number. Renumbering the done copy rewrites its check.sh fallback `A="$PWD/tests/acceptance/c0510"` to `…/c0521`. Nothing moves `tests/acceptance/c0510`, so `tracker.sh check c0521` no longer finds its specs. Later, `done` of the backlog `c0510` promotes into `tests/acceptance/c0510`, which already holds the other item's specs. The raft whose `issues:` lists c0510 also now points at the wrong copy.
Critique: making `renumber <dir>` also move `tests/acceptance/<old>` fixes the check.sh, but the raft reference still points at the wrong item, and more rewrites follow from that.
Consequences: choosing which copy to renumber is a rule users must follow, so the skill has to state it and a spec has to check it.
Recommendation: the Duplicate ids bullet says to renumber the copy that is not in `done/` (normally the freshly captured backlog stub, which nothing references yet). `renumber <dir>` refuses a `done/` directory, naming the other copy. Change cli.spec to renumber the backlog copy (with the same "only that copy" assertions) and add a case: `renumber tracker/issues/done/c0010` refuses and changes nothing. Add rows for both to the Rules and mutants table.

### F5 [medium] remap with several items of its own: neither the reservation count nor the numbering order is specified or tested
Where: c0870 `tracker.sh remap` step 2 ("each gets a new number from origin's counter … reserved by one publish.commit of the counter"); remap.spec has exactly one unmapped item (`c0041 -> c0003`); Rules table row "remap numbers unmapped items".
Evidence: suppose a branch has two unmapped items, `c0041` and `c0051`. One plausible implementation numbers them `c0003` and `c0004` but raises the counter by one, to 4. It passes every remap.spec case. The next `new issue` on main then publishes `c0004`, and merging the branch produces a duplicate id, which the gate then rejects through real-tree.spec. Which item gets which number is also left open (input order, or the `ids.plan` order).
Critique: a missing edge case with a plausible mutant nobody listed.
Consequences: none beyond the spec case and one sentence of design.
Recommendation: specify that the unmapped items are numbered in `ids.plan` order (number, then prefix), and that the counter is raised past the last one in the same single publish. Add a second unmapped item to the remap.spec fixture: assert both new ids, and that origin's counter ends one above the higher.

### F6 [low] The tracker skill's direct-push rule goes stale: `tracker/next` is now published, but the "direct-push exception" bullet still lists only `<ID>.md` and `check.sh`

### F7 [low] Two behaviours that no spec can fail: `audit` allowed in the main checkout, and the compact pre-audit tolerating `next-missing`
Where: c0880 `cmd.audit` ("Not refused in the main checkout"); c0870 compact step 3 ("any error other than next-missing, next-malformed refuses").
Evidence: cli.spec's fixture has no `origin`, so `refuseInMainCheckout("audit")` is a no-op there and the mutant passes. Every compact.spec fixture has a valid `tracker/next`, so a pre-audit that also refuses on `next-missing` passes too.
Critique: both are design rules without a Rules and mutants row.
Consequences: none.
Recommendation: add a compact.spec or allocate.spec case running `tracker.sh audit` in the fixture's main checkout (which has an origin), expecting exit 0. For compaction of a tree without a counter, either add a case or drop the exception from step 3. Add rows for both.

### F8 [low] allocate.spec's lost-race shim runs raw `git pull/commit/push` in a shell string, which the testing skill does not allow; the exception is recorded only in a code comment
Where: allocate.spec.luau lines 172-188 (the `{base}/shim/git` script).
Evidence: the testing skill says "Raw git only for `rev-parse`, `ls-files`, and `init` or `clone` to a named path; no shell strings". The shim `cd`s into `other` and runs `pull`, `add`, `commit` and `push`. It is safe in practice: `( cd … && … ) || exit 1` stops if the folder is missing, the fence's ceiling and `.cache/.git` sentinel keep git out of the real repository, and `other` commits as `alloc@example.invalid`. But no issue document records the exception, so the code reviewer has nothing to check it against.
Critique: an unrecorded deviation from a safety rule is the kind of precedent the "caught only by review" list exists for.
Consequences: none.
Recommendation: record the exception and its safety argument in c0870's Regression guard or Test plan, so the code reviewer can verify it line by line. Alternatively, have the shim call `"{real}" -C "{other}"`, which the fence still covers, and assert at the start of the case that `{other}/.git` exists.

Verdict: changes
