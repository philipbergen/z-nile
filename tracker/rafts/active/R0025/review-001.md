### F1 [medium] `ready` and `stop` decide raft membership from different fields, so an item can get stuck in `active/` on origin/main with no command that moves it
Where: scripts/tracker/main.luau:2589 (`cmd.ready`: `store.members(raft.id)`, the issues whose `raft:` is R) vs main.luau:2682 (`cmd.stop`: `store.idList(raft.issues)`, the raft's `issues:` list). `setStatus`, which stop's legacy path uses, also reads `issues:`.
Evidence: Take a prepared raft R with `issues: [c1, c2]` and an issue c3 whose `raft:` is R but which isn't listed. This drift is real: c0073 left R0025 for its own raft, and R0025's own `issues:` omits c0098, whose `raft:` is R0025. Nothing checks that the two fields agree (`audit` doesn't compare them). Then:
1. `ready R` moves R, c1, c2 and c3 to `active/` and stamps them active.
2. `stop R` moves only R, c1 and c2 back.
3. c3 stays in `active/` on origin/main. `status c3 new` refuses ("c3 is readied (in active/): use tracker.sh stop R"). `stop R` now refuses, because R is prepared in the backlog. `ready R` refuses too, because its verify finds c3 active, not prepared.

The only way out is a hand edit on main, which the tracker skill forbids ("The only way to change tracker state is scripts/tracker.sh"). The reverse drift (listed, but `raft:` points elsewhere) makes `stop` refuse every time, with "c… is in tracker/issues/c… on origin/main, not active/".
Critique: Both commands publish straight to origin/main, so they must agree on what they move. The tempting fix is to switch `stop` to `store.members`. That leaves the legacy give-back (`setStatus`, `issues:`) and `ready` reading different lists, and a member whose `raft:` changed while it was readied would still strand.
Consequences: One membership rule means `ready` has to refuse an inconsistent raft before it pushes anything. That is a new refusal, with its own message and spec case. `stop` must also handle a raft that was readied before the rule existed (none exist yet, since this PR introduces `ready`).
Recommendation: In `ready`, before any push, refuse unless the raft's `issues:` set equals `store.members(R)` on origin/main, naming each id that is on one side only. Make `stop` move exactly `{R} ∪ store.members(R)` that are in `active/` (the set `ready` moved). Spec cases: ready refuses a `raft:`-only member and a listed member whose `raft:` points elsewhere, and pushes nothing; stop after ready leaves no member of R in `active/`. If any sequestered spec pins the current behaviour, escalate rather than edit it.

### F2 [medium] CI's dispatched acceptance step passes without running a single spec whenever `tracker.sh members` fails
Where: .github/workflows/check.yml, the `workflow_dispatch` step: `dirs=$(scripts/tracker.sh members "$r" 2>/dev/null) || dirs=`
Evidence: When `members` exits non-zero on a raft branch, `dirs` is empty, `files` is empty, and the step succeeds without saying anything. Causes include a duplicate id after merging origin/main, an unknown raft after a renumber, or a malformed document. Merging step 3 and `scripts/ci-verify.sh` use exactly this dispatched run as the Linux proof of the sequestered specs. The full gate in `setup.sh` doesn't run them, so a red raft gets a green `gate`. The old `find tracker -path …` could not fail this way.
Critique: Stderr goes to /dev/null and the failure turns into "nothing to run". The tempting fix is to drop `2>/dev/null`. That shows the error but keeps `|| dirs=`, so the step stays green.
Consequences: Making the failure fatal also hits branches that aren't raft branches (`prep-…`, `capture-…`, `ws-…`), where `r` isn't an R-id and `members` correctly fails. Those must keep passing with nothing to run.
Recommendation: Resolve the raft only when `$GITHUB_REF_NAME` matches `^R[0-9]{4}-`, and let `members` fail the step there (no `2>/dev/null`, no `|| dirs=`). Skip the step for every other branch. Keep the literal `*/active/*/acceptance/*.spec.luau` glob that c0001's ci-workflow.spec pins. Optionally print the spec count. Add a tooling case (or an AC grep owned by c0067, if that's allowed without touching sequestered files) for "a raft branch whose members fails makes the step fail".

### F3 [low] stop-raft says `start` refuses on a stopped raft's old branch, but on that branch `start` pushes another empty commit and then dies in `gh pr create`
Where: .claude/skills/stop-raft/SKILL.md step 4; main.luau:1750-1764 (`cmd.start`, readied path)
Evidence: After `stop` and a later `ready`, the human reuses `.worktree/R` (branch `R-slug`, PR still open, as stop-raft tells them to leave it). `start R` there skips the "branch exists" refusal, because it is already on the branch. It commits `--allow-empty`, pushes, and calls `sh.must("gh", {"pr","create","--draft",…})`, which fails because a PR for the branch already exists. The refusal at line 1756 even says "switch to it and run start there", which leads straight into this path.
Critique: The skill promises a refusal the code doesn't make. The run ends in an error after a push.
Consequences: Reusing the open PR is the natural resume, so `start` needs to decide between "existing PR: reuse it" and "refuse".
Recommendation: In the readied `start` path, on a GitHub origin, look up an open PR for the branch (`gh pr list --head <branch> --state open`) before committing. If there is one, print its URL and skip `gh pr create`, or refuse before the empty commit. Then make stop-raft step 4 describe what actually happens. Spec case: start on a branch that already has an open PR (a recording `gh` stub) neither fails after pushing nor opens a second PR.
