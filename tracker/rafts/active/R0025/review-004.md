### F1 [medium] The claim stamp is used as a unique identity, but nothing makes it unique: 24³ = 13,824 values, and done items keep theirs forever, so a collision makes `stop` refuse for good or give back another raft's issues
Where: scripts/tracker/main.luau `cmd.stop` (the `for _, issue in store.all("issue")` loop: `raw == claim`, then `issue.state ~= raft.state` fails); `cmd.ready` (`stamp("active")` passed straight to `moveOnOrigin`); the legacy `cmd.start` (`local claim = stamp("active")`); scripts/tracker/status.luau `WORDS` (24 entries) and `status.stamp`
Evidence: `status.stamp` picks three of 24 words, so 13,824 `active-…` values exist. `stamp` was built to make two concurrent writes differ ("so git reports a conflict"), not to name a claim. `done` moves items with `git mv` and never restamps them, so every done raft leaves its claim stamp in `done/` forever. `grep '^status:' tracker/*/done/*/*.md` shows 8 distinct `active-…` values today, for example `active-plucky-raging-brisk` on 7 items. R0025's own `active-mellow-mellow-mellow` will be the 9th when it merges. `stop` scans every issue, `done/` included. Two failures follow:
1. Collision with a done raft. A future raft readied with `active-mellow-mellow-mellow` can never be stopped: `stop` fails with "c0062 is in done/ on origin/main, not beside R…: stop does not move it back". No retry helps, because the stamp is on origin. Only a hand edit of `status:` gets the raft back, which is the stranding `stop` exists to prevent. The chance is about D/13,824 per ready, where D is the number of done rafts. It is 0.06% today and grows with every raft.
2. Collision with another claimed raft. Readied R1 and R2 both draw `active-x-y-z`. `stop R1` then takes R2's issues, which are also in `active/` beside R1, and moves them to the backlog with R1. The only sign is the `stopped R1 (…)` list. This is a wrong result, though rare.

The sequestered `stop.spec` and these tooling specs claim rafts in fixtures with random stamps. A collision there is a one-in-13,824 flake. The fixtures have no done stamps, so only (2) applies.
Critique: Round 3 replaced membership by fields with membership by stamp, but it kept the stamp's old guarantee, "probably different from a concurrent write". Identity needs "different from every value on origin". The tempting fixes are a longer word list or ignoring `done/` in `stop`. A longer list only shrinks the odds. Ignoring `done/` removes c0068 AC1's refusal of a member already in done/: that case moves the member by hand and keeps its stamp.
Consequences: Draw the claim stamp so that no item on origin/main carries it, `done/` included. The rule becomes "a claim stamp is unique on origin when it is written". That needs:
(a) a pure helper, for example `status.freshStamp(state, used, pick)`, that redraws until the value isn't in `used`. Its unit spec gives a `pick` that first returns a used value and checks the second draw;
(b) the check inside the publish build in `ready` (`moveOnOrigin` would take the value from a function of `paths`/`read`) and in the legacy `start`. Building `used` reads every item document once, at about the size of the tree today.
After that, a stamped issue in `done/` is one this raft claimed, so the done/ refusal keeps its meaning. Stamps already on origin need no migration: the uniqueness check covers them. The legacy resume path compares against the claim file's value, which stays unique.
Recommendation: Add the unique draw as in (a) and (b), with the unit spec for the helper. Add a ready-members (or new tooling) case: seed a done/ issue whose `status:` is the value the spec forces as the first draw, ready a raft, and check its stamp differs and `stop` succeeds. If the RNG can't be forced from a tooling spec, the unit spec on the pure helper plus a check that `ready` and `start` use it is enough. One sentence in the tracker table's stop row: the claim stamp is unique on origin when it is written. None of this touches a sequestered file.

### F2 [low] A resumed legacy `start` claims a newly published member with a fresh stamp while the raft keeps the old one, so `stop` wrongly says it "was not claimed with it" and leaves it active
Where: scripts/tracker/main.luau `cmd.start`, legacy publish build (`if mine ~= "" and raw == mine then continue`, then `withFront(text, "status", claim)` for the rest) and the claim-file restore after it
Evidence: A start pushes its claim (`mine`) for R and c1, then dies before the branch is made. Then `elsewhere` publishes c2 with `raft: R`, prepared. The rerun of `start` skips R and c1 (raw == `mine`) and stamps c2 with the new `claim`. The push succeeds and `r.sha` is set, so the claim file now holds `claim`, not `mine`. Origin then has R and c1 at `mine` and c2 at `claim`. `stop R` gives back R and c1 and warns "c2 names R but was not claimed with it". That's false: this raft's own `start` claimed c2, and c2 stays `active-…` in the backlog. It can be recovered by hand (`status c2 prepared` works on a backlog item), and the warning names it, so this is low. A third `start` would also see `mine` = `claim` ≠ R's stamp and refuse "R is active on origin/main, not prepared".
Critique: Before round 3 this was harmless, because `stop` selected by `raft:`. Under stamp selection, every path that claims for a raft must write the raft's value.
Consequences: In the resumed case (the raft's raw status equals `mine`), write `mine` to the remaining items and keep the file at `mine`. Then the raft and every item it claimed share one value, and the claim file always equals the raft's stamp on origin.
Recommendation: In the legacy build, use `local value = if mine ~= "" and <raft's raw> == mine then mine else claim` for every change, and keep the claim file at the value the raft carries. Add a case where a pre-written claim file matches origin and an issue was added in between: after the rerun, the new issue carries the raft's stamp, and `stop` gives it back with no warning.
