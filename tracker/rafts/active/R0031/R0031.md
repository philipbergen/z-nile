# R0031: Lifecycle spend

## Theme
A single chore, **c0084**: record the spend of every phase of an item's life, not just the build commits, and report it. The user, 2026-10-05: "make sure we track the entire sdlc from issue entry to delivery". Tooling and skills only: a chore.

User decisions relied on (2026-10-05, given to this prep):
- each unassociated backlog issue gets its own `--single` raft;
- this raft is prepared now but **must not start until R0025 lands** (R0025 adds `ready`, `stop`, `launch-raft` and `land`, and changes `tracker.sh`);
- the non-goals in c0084: best-effort tokens, and no change to the rework definition beyond saying which phases it covers.

`tracker/game-design.md` has no decision that applies (no game behavior).

Prep decisions the user may want to adjust (none needs an answer to execute):
- **Rows outside a raft are published** to `origin/main`, like status claims: the direct-push exception grows by "an issue's `spend.md`, rows appended only", checked by the publisher. The alternative, carrying them in each PR, cannot record delivery (CI wait and merge happen after the last push) and would make `land` carry non-document files.
- **Rework counts every phase**, so a defect's capture, prep and review time count against the 20% target alongside its build time.
- A raft-level row (design review, delivery) is split over the members, so per-issue and per-type numbers stay whole; the raft summary shows the phases.

Data flow:
```
capture ──make-issue──▶ tracker.sh spend <c> --phase capture ─┐
design round ─ticket-prep─▶ spend <R> --phase design-review ───┤  published: append-only rows in each
prep PR opened ─ticket-prep▶ spend <R> --phase prep (lines) ──┤  issue's spend.md on origin/main
raft merged ─execute-raft─▶ spend <R> --phase deliver ─────────┘  (refused for items active there)
raft branch: tracker.sh commit [--phase build|code-review|deliver] [--tokens n]; done = deliver
                └─ rows in the same files, on the branch (the items are active, so spend never races it)
metrics / board ◀── ledger.parse of every spend.md
```
No `src/` change, no `tracker/architecture.md` change.

## Risks & rollback
- **History**: two existing ledgers (c0081, c0082) hold a row spanning four lines. The ledger reads them; the first `commit` or `spend` that touches such a ledger rewrites the row on one line. Nothing else changes old rows.
- **Direct pushes grow**: an appended row is validated by `ledger.appendOnly` inside the publisher (canonical form, old rows untouched, title and id unchanged), so a bad writer cannot rewrite spend history on `main`.
- **Moves**: after this raft nearly every item carries a published `spend.md`, so `ready`, `stop` and `done`'s path rewrite move ledgers all the time. The ledger rule applies only to changes without `from`; a spec case runs `ready` and `stop` over two members with ledgers (review 001 F3).
- **Merge conflicts on spend.md**: avoided by construction: `spend` refuses items active on `origin/main`, and a raft branch only writes ledgers of active items. A legacy-started raft (claimed in the backlog) is refused by its `active` status.
- **Token numbers are best effort** (the Agent tool's usage report); minutes stay the comparable measure.
- **Size**: about 1,000–1,300 changed lines: the ledger (~200, prototyped), spend and publish (~150), `main.luau` (~250), skills (~60), and the four specs (~750, written in prep and not counted by spend).
- Rollback: revert the squash commit. Published nine-column rows stay readable by a reverted tree only through its old parser, which reads the first seven cells' totals comment: `readTotals` before this raft needs the `commits=` key, so after a revert, metrics show 0 for ledgers written since. Acceptable for a rollback; re-landing restores them.
