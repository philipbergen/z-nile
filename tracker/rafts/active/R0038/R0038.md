# R0038: Board raft issue views

## Theme
One chore, one board. The person looking at the tracker cannot see what to do next: the lists are Active, Waiting and Done, Waiting hides a raft that still has something unfinished in front of it, and an issue appears only inside its raft. c0107 replaces those lists with Rafts and Issues, splits each into ready and not ready, colors the groups, shows a raft's type from its issues (or mix), and puts the next command on a copy button.

This raft does not change a decision in `tracker/game-design.md`. None of those decisions are about the tracker board.

Quoted from c0107, which is the decision this raft implements:

- Two work lists, Rafts and Issues, instead of browsing only by Active and Waiting.
- Each list splits into ready and not ready, with a clear color for each.
- Every raft shows its type from its issues. All one type shows feature, defect, or chore. More than one type shows a mix. The type stays readable beside the ready and not-ready color.
- A raft is ready when prep has merged (`design: ready`, status `prepared`). Its copy command is `/ready-raft <id>`. A readied raft's copy command is `/launch-raft <id>`.
- An issue with no raft is not ready to execute. Its copy command is `/ticket-prep <id>`. An issue already in a raft copies that raft's next command.
- Each row has a copy icon. Activating it writes that command to the clipboard.

Done stays as a third group inside each list, grey, so finished work does not disappear. A row whose rule above names no command has no copy icon: this raft does not invent a command for a draft, a review in progress, or a finished item.

`scripts/tracker.sh new raft` still refuses a raft whose members are not all one type. `mix` is only the label the board shows when a tree's issue types differ. This raft does not change that rule.

## Whole-raft design
`scripts/tracker/board.luau` decides the groups, the commands and the labels. `scripts/tracker/board.html` draws them. The page does not recompute the rules.

```
tracker files
    │  board.collect
    ▼
Model.views.rafts / .issues
    each: ready[], not[], done[]     ids, sorted
Model.rafts[].label / .command
Model.issues[].label / .command / .dependents
Model.home[id] = id
Model.initialView = "rafts"
    │  board.render  (JSON into the page)
    ▼
#tab-rafts  #tab-issues
list: Ready, Not ready, Done
row: bucket bar + type word + copy button
click copy → navigator.clipboard.writeText(command)
```

No new Logic feature and no new dependency edge. `tracker/architecture.md` stays as it is. `.github/workflows/board.yml` stays as it is.

The model changes, and the old fields go away:

```lua
export type Bucket = "ready" | "not" | "done"
export type ViewName = "rafts" | "issues"

-- Raft loses `tab`. It keeps `pseudo`, which is false for every raft (there is no No raft entry).
-- It gains:
--   label: string       -- "feature" | "defect" | "chore" | "mix" | ""
--   stage: string       -- status.effective: "new" | "preparing" | "prepared" | "active" | "done"
--   command: string?    -- nil when this row has no next command

-- Issue gains:
--   label: string       -- the issue's own type ("" when the issue has none)
--   stage: string       -- status.effective for that issue
--   command: string?
--   dependents: { string }  -- raft ids whose members depend_on a raftless issue, done or not; {} otherwise

-- Model loses `tabs` and `initialTab`. It gains:
--   views: { rafts: { ready: { string }, ["not"]: { string }, done: { string } }, issues: same }
--   initialView: ViewName   -- always "rafts"
```

`status`, `blockedBy`, `dependsOn`, `dependents` on a raft, `topLevel` and `stats` stay. `type` on a raft stays the frontmatter word. The row shows `label`, not `type`.

Bucket and command for a raft. `board.luau` requires `./status` and uses `status.effective(front, state)`. It does not reimplement the stamp parser.

| state | design | `status.effective` | bucket | command |
|---|---|---|---|---|
| done | anything | done | done | nil |
| active | anything | active | ready | `/launch-raft <id>` |
| backlog | ready | prepared | ready | `/ready-raft <id>` |
| anything else | | | not | nil |

A missing `status:` with `design: ready` is prepared, because that is what `status.derive` returns and what `tracker.sh ready` accepts. A `preparing-…` stamp wins over that derivation, so the raft is not ready. `design: reviewed` is not ready even when the stamp parses as `prepared`. A backlog raft whose stamp parses as `active` is not ready and has no command: `/launch-raft` is only for a raft that already sits in `active/`. A blocked raft stays in the bucket this table gives it. The old Waiting filter is gone.

Bucket and command for an issue:

| issue state | its raft | bucket | command |
|---|---|---|---|
| done | anything, including none | done | nil |
| not done | a raft in `ready` | ready | that raft's command |
| not done | a raft that is not `ready`, including a done raft | not | nil |
| not done | none (empty, missing, or a raft id that does not exist) | not | `/ticket-prep <id>` |

An issue that already has a raft never gets `/ticket-prep`, including an unfinished issue whose raft is done: that issue is Not ready and has no command. It does not inherit the raft's Done bucket. A done issue never copies `/launch-raft`.

`label` for a raft: collect the member issues' types, ignoring `""` and anything that is not `feature`, `defect` or `chore`. No types left → the raft's own `type`. One type → that type. Two or more → `mix`. An issue's `label` is its own `type`.

`home[id] = id` for every raft and every issue. There is no `none:<tab>` entry. A loose issue's `dependents` is the sorted list of raft ids that have a member whose `depends_on` names it, whether that issue is done or not. `blockedBy` stays unfinished-only and is not this list. Every other issue's `dependents` is `{}`.

The page:

- The nav is `<button id="tab-rafts">Rafts</button><button id="tab-issues">Issues</button>`. `#tab-active`, `#tab-waiting` and `#tab-done` are absent. `#stats-toggle` stays outside `<nav>`.
- `#list li.row.ready`, `.not` and `.done` use an inset bar `#22c55e`, `#f59e0b` and `#9ca3af`. The type word uses `.t-feature` / `.t-defect` / `.t-chore` (the existing `--ser-*` colors) and `.t-mix { color: #7c3aed; }`. `#list li.sel { background: var(--sel); }` stays, so the bar remains on the selected row. Every badge (list row, pane `<h2>`, and `idLink`) is `badge(stage)`. `stage` is `new`, `preparing`, `prepared`, `active` or `done`, never `ready`. `.s-prepared { background: #22c55e33; }` is the only green badge. Add `.s-preparing { background: #f59e0b33; }` and `.s-new { background: #d1d5db33; }`. Delete `.s-ready`, `.s-reviewed` and `.s-draft`. Keep `.s-done` and `.s-active`.
- Groups are `<li class="group">Ready</li>`, `Not ready`, `Done`, in that order, omitting an empty group. Arrow keys move through rows only. The row class is the bucket from `views`, not `status` and not `stage`.
- A row with a command has `<button type="button" class="copy" data-command="…" aria-label="Copy …">` and an inline `<svg aria-hidden="true">`. The list click handler looks for `button.copy` first. When it finds one, it copies and returns before it looks for `li.row`, so a copy click does not change the selection or rebuild the list. If `navigator.clipboard` or `writeText` is missing it returns without throwing. Otherwise it handles the Promise `writeText` returns so a rejection is not unhandled. On success the same button gains class `copied` and `aria-label` `Copied`. `.copy.copied { outline: 2px solid #22c55e; }`. A rejection does nothing and does not throw. A failed copy stays silent. A later re-render clears `copied`. That is accepted. The page groups, colors and copies from `views` and `command`. It does not derive a bucket or a command from `stage`, `status` or `state`.
- The first row of Rafts is selected on load. ArrowRight and ArrowLeft cycle the two views and select the first row. `/`, Escape, search miss, and Cmd/Alt/Ctrl arrows behave as they do now.
- A raft pane still shows Waiting for, Depends on, Dependents, the member issues and the document. Its meta shows `label`. An issue pane, in order, is the `<h2>` (id, title, badge), the meta (label and design), a Raft jump when `issue.raft` is set, then Depends on (`dependsOn`) and Dependents (`dependents`) using the same `idLink` as a raft pane (empty groups omitted), then Document (the marked body). Search for an issue selects that issue in the Issues view.

The tracker skill's `board` row replaces `Tabs Active / Waiting / Done (Waiting lists only rafts with no unfinished dependency)` with `Views Rafts and Issues, each split into Ready, Not ready and Done (a backlog raft is Ready only when its design is ready and its effective status is prepared; a readied raft is Ready; blocked rafts stay listed). A raft's shown type comes from its issues (one type, or mix). A row with a next command has a copy button`. It also replaces `Stats (a Stats button, not a fourth tab)` with `Stats (a Stats button, not a third view)`. The artifact download on that row stays.

## Experiments phase
E1 and E2 passed in prep. Nothing is left for the executor's Phase 1.

- **E1.** Does `store.readFront` keep the status stamp? Pass: a file whose frontmatter is `status: prepared-a-b-c` reads back that string (`lune run .cache/c0107-e1/e1.luau`, since removed with the cache). Fallback not needed.
- **E2.** Can the node harness complete `writeText`'s thenable before the next line? Pass: a thenable that calls its success function immediately is visible synchronously, and a thenable that calls its failure function does not throw when the caller passes a failure function. Fallback not needed. The fake clipboard returns real Promises, and the harness reads the button after `setTimeout(…, 0)`. Any handling that leaves no unhandled rejection is accepted. `node -e 'Promise.reject(new Error("denied"))'` exits 1 on Node 22, so a rejection with no handler still fails the run.
