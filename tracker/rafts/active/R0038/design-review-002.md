### F1 [high] AC3 still passes when the page buckets and copies from `stage` instead of `views` and `command`
Where: c0107.md Design ("The page script reads `model.views` … It does not recompute the buckets"); R0038.md "The page does not recompute the rules"; page.spec fixture and the case "orders Ready, then Not ready, then Done, and copies only a real command"; rules row "a design-ready raft with a preparing stamp stays Not ready" (mutant "class a row ready when `status` is `active` or `ready`").
Evidence: review-001 F2's fix added R9104, which kills a page that buckets from `status`. It doesn't kill a page that buckets from the new `stage` field: row class `stage === "done" ? "done" : (stage === "prepared" || stage === "active") ? "ready" : "not"`, command `"/ready-raft " + id` for `prepared`, `"/launch-raft " + id` for `active`, and `"/ticket-prep " + id` for an issue with no `raft`. Against the page fixture, R9100 has stage `prepared`, R9103 `active`, R9101 `preparing` (derived, because `issues:` is present), R9104 `preparing` and R9102 `done`. The fixture expects Ready, Ready, Not, Not, Done, which matches every grouping, row class, `data-command`, copy, `afterRight` and `/ticket-prep c9102` assertion in page.spec. keep.spec doesn't look at buckets. The rafts where `stage` and the bucket disagree exist only in views.spec: R9003 (`design: reviewed`, prepared stamp) and R9010 (backlog, `active-…` stamp). views.spec reads the model and never renders it. So a page showing R9010 as Ready with `/launch-raft R9010` (the command R0038 rules out for a backlog raft) passes AC3. This is the second hole in the same mechanism: "the page doesn't recompute" is enforced by picking fixtures where the recomputation and the model happen to disagree.
Critique: the tempting fix is to copy R9003 and R9010 into the page fixture. That kills this mutant and the next one (for example `design === "ready" && stage === "prepared"`, which is the board's own rule copied into the page) still passes. It also gets weaker every time a new readiness rule lands in `board.luau`.
Consequences: the mechanism should check the property itself. `board.render(m, marked)` accepts any model, so a spec can hand the page a model whose `views` and `command` contradict every field the page could recompute from. The page's other lookups (`byId`, `issueById`, `home`) still need a consistent model, so only `views.*` and `command` are changed. The real-fixture case stays, because it is what checks that `collect` and `render` work together.
Recommendation: question the mechanism and stop enumerating fixtures. Add a page.spec case that takes `board.collect(ROOT)`, then: moves `R9101` (draft, stage `preparing`) into `views.rafts.ready` with `command = "/sentinel R9101"`; moves `R9100` (prepared) into `views.rafts.done` with `command = nil`; moves `c9103` into `views.issues.ready` with `command = "/sentinel c9103"`; and moves `c9102` into `views.issues.done` with `command = nil`. Render that model and run the harness on it. Assert that the R9101 row is `class="row ready` under the Ready heading, with `data-command="/sentinel R9101"`. Assert the R9100 row is `class="row done` after the Done heading with no `copy`. Assert the same after ArrowRight for `c9103` and `c9102`. Add a rules row "the page groups, colors and copies from `views` and `command`, not from `stage`, `status` or `state`", whose mutant is the `stage` mapping above, and mark it `run` once it has been tried on a scratch page.

### F2 [medium] Badge = `stage` is pinned only on raft list rows, so the "ready" badge on a preparing raft survives in the pane, and issue `stage` is never checked
Where: R0038.md "The badge class is `s-` plus `stage`. `.s-prepared { background: #22c55e33; }` is the only green badge"; c0107.md Design ("The badge renders `stage`"); `board.html` `idLink` (`badge(it.status)`) and `renderPane` (`badge(r.status)` in the `<h2>`); views.spec and page.spec.
Evidence: today the page draws badges in three places: list rows, the pane `<h2>`, and every `idLink` (Waiting for, Depends on, Dependents, member issues). Only list rows have an assertion (`s-prepared`, `>prepared<`, `s-active`, `>preparing<`, no `>ready<` on R9104). An implementation that changes `renderList` and leaves `renderPane` and `idLink` on `status` passes every spec. It also leaves `.s-ready { background: #22c55e33; }` in place, since nothing asserts that it goes. Then the R9104 pane, or any raft that links to R9104, still shows a green "ready" badge on a raft the list calls Not ready. That is the contradiction review-001 F2 was raised to remove. Separately, no spec reads `issues.*.stage`, and no case looks at an Issues-view badge or an issue pane `<h2>` badge. A `collect` that never sets issue `stage` turns `badge(undefined)` into `""`, so issue badges disappear without any failure. The Rules and mutants table has no row for issue `stage`.
Critique: the tempting fix is one more assertion on the R9104 pane. That still leaves `idLink` and the issue rows unguarded.
Consequences: `stage` never has the value `ready` (its values are new, preparing, prepared, active and done), so a lower-case `>ready<` anywhere on the page means `status` leaked into a badge. The capitalized group heading `>Ready<` doesn't collide with that check. `.s-ready`, `.s-reviewed` and `.s-draft` become dead rules. Say whether to delete them or leave them, so a reviewer doesn't have to guess.
Recommendation: specify that every badge on the page (row, pane `<h2>`, `idLink`) is `badge(stage)`, and that `.s-ready` is removed (or no longer green). In views.spec, assert issue stages: `issues.f9001.stage == "prepared"`, `f9017 == "preparing"`, `f9004 == "active"`, `c9005 == "done"` and `c9009 == "new"`. In page.spec, open the R9104 pane (search `r9104`) and assert `>preparing<` is there. Assert that no `>ready<` appears in `list`, `pane`, `afterDown`, `afterRight` or `afterRightPane`. Assert that the html has no `.s-ready { background: #22c55e33; }`. Add rules rows for "issue `stage` is `status.effective`" (mutant: copy the raft's stage) and "pane and link badges use `stage`" (mutant: leave `idLink` on `status`).

### F4 [low] The copy harness reads its results after one microtask, so a correct `await` or `Promise.resolve` implementation fails
Where: page.spec HARNESS (`queueMicrotask(() => { out.okCopied = … })`); R0038.md Experiments, E2 ("The page must call `.then` on the return value itself").
Evidence: the success thenable queues `ok` during the click, and the reader microtask is queued right after it, so `ok` runs first only if the page calls `.then` directly on the returned object. `await navigator.clipboard.writeText(c)` or `Promise.resolve(writeText(c)).then(...)` adopts the thenable through extra jobs, so `ok` runs after the reader and `okCopied` is false. Review-001 F3 noted that an asynchronous harness makes this constraint unnecessary. The refute made the harness asynchronous but kept the one-tick read.
Critique: the spec pins how the page is written, not what it does. A future maintainer who writes the idiomatic `async` handler gets a red spec with no defect.
Consequences: reading after a macrotask also lets the rejection path settle fully. `setTimeout` comes from node itself, outside the sandbox, so the page's own globals don't change.
Recommendation: in the harness, read each phase inside `setTimeout(() => …, 0)` instead of `queueMicrotask`, and drop the ".then on the return value itself" constraint from E2 and the Design. Re-run the `.then(ok)` (no failure function) mutant: with the bad thenable, an unhandled call to `undefined` still crashes node, so that case still fails.

### F5 [low] (repeat of review-001 F3, its `file://` part) The copy button is never tried in a real browser, and a failure is silent
Where: R0038.md "The page" (copy handler); c0107.md Acceptance criteria, "Observed: None"; Unknowns & experiments.
Evidence: review-001 F3 named clipboard access from a `file://` page (the default `.cache/board.html` and the downloaded CI artifact) as an unproven assumption with no experiment and no fallback. The refute answered the missing-`navigator.clipboard` guard but not the real-browser question. The only evidence for the feature is the node harness, which fakes `navigator.clipboard`. If a browser lacks `navigator.clipboard` or rejects the write (no focus, a permission policy), the design returns or "does nothing", so the user clicks and sees no change.
Critique: the feature this chore adds could fail for every real user while every check passes.
Consequences: an Observed step costs one manual click per raft. A visible failure state needs one more class and a spec assertion.
Recommendation: add an Observed criterion: open the built `.cache/board.html` from `file://` in Chrome and in Safari, click a row's copy button, paste, and see the command. Optionally, mark a failed copy (for example `copy failed` with `aria-label` `Copy failed`) and assert it in the rejection and missing-clipboard runs, so a failure is no longer silent.

### F6 [low] A loose issue's Dependents now drops rafts once that issue is done, unlike a raft's Dependents
Where: R0038.md ("A loose issue's `dependents` is the sorted list of raft ids that record it in `blockedBy`"); c0107.md Design; `board.luau:619` today (`noRaftDependents` records every raft that depends on a raftless issue, done or not).
Evidence: `blockedBy` holds only unfinished issues (`board.luau:620`). Today the No raft pane lists a raft under Dependents even after the loose issue is done. A raft's own `dependents` also keeps finished dependencies. Under the new rule, a done loose issue with a dependent raft shows no Dependents. No fixture has a done loose issue that a raft depends on, so neither reading is tested.
Critique: a small loss of history that the documents don't call a decision. An executor who reuses the existing `noRaftDependents` loop gives the other answer and still passes.
Consequences: none beyond picking one reading.
Recommendation: define it as "the rafts whose member issues list it in `depends_on`", matching a raft's `dependents`, or keep `blockedBy` and say that this is deliberate. Add a done loose issue that a raft depends on to views.spec, and assert whichever answer the documents choose.
