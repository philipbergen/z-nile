### F1 [medium] The trail handles only the last compaction, so after the next `compact`, `capture` returns the first compaction's commit, or another item's document, for every item captured before it
Where: c0111 Design, The trail (`ranges`, `read`: "`cut` is `git log -1 … -- tracker/compaction.txt`"); prototype `scripts/tracker/trail.luau` lines 29–51 and 145–155; lesson `tracker/item-history-spans-moves-and-compaction` (check and How to apply); design-refute-007 F1 ("the next `compact` keeps working because the map names the old ids")
Evidence:
- `cmd.compact` overwrites `tracker/compaction.txt` with that compaction's map alone (`fs.writeFile(idsLib.MAP_FILE, idsLib.formatMap(map, …))`, main.luau about line 1517). So after a second compaction the file maps only the middle ids to the new ones.
- `read` takes one cut (the newest commit touching the file) and `ranges` reads the middle id's folders over all of `<cut>~1`.
- Take c0083 today, which was c0890 before a38f91f, and suppose a second compaction renames it to c0050. Then `capture c0050` reads `tracker/issues/{,active/,done/}c0083` before the cut. In that history the folder first appears in a38f91f (with `--no-renames` that is an `A`), and `cda52f9 tracker: new c0890 …` is in a folder that is never read. No `tracker: new` subject matches, so `capture` falls back to `oldestAdd` and prints `capture a38f91f … tracker: compact ids (#64)`. That is the item as it stood at the first compaction, prep rewrites included. This is exactly the defect round 007 F1 found, and this time nothing says the lookup failed.
- The middle id's folders are read over the history before the first compaction too, when that number belonged to another item. `ranges` checks "renamed away" only against the last map. An item whose middle number was used before the first compaction (for example any current `c00X0`, since a985927 created `c0070` and `c0080`) and that has no `tracker: new` commit of its own falls back to the other item's first add. Then `capture` prints a different issue's document as the baseline.
- `capture-cli.spec` and `trail.spec` each seed one compaction, so no case can see this.
Lesson: tracker/item-history-spans-moves-and-compaction, testing/no-vacuous-pass
Critique: the tempting fix is to make `compact` append to `compaction.txt` and keep `read` as it is. That gives a map with two lines for one item (old to middle, middle to new), which `ids.parseMap` refuses ("repeats an old or a new id"). `remap` and the stale-tree guard (main.luau about line 364, which compares the whole file with origin's) also read that file, so changing its format reaches beyond this raft.
Consequences: the history of maps already exists in git: each commit that changed `compaction.txt` holds its own map. Chaining them changes `ranges` to take a list of cuts, oldest last, each with its own map. An id renamed away at any cut stops the walk at that cut. Every lookup (capture, metrics) gets one more range per compaction, and today there is one.
Recommendation:
- In `read`, list every cut with `git log --format=%H <head> -- tracker/compaction.txt`, and read each cut's map with `git show <cut>:tracker/compaction.txt`.
- `ranges(kind, id, head, cuts: { { cut: string, map: { [string]: string } } })` walks back from the newest cut: the current id over `<k1>..<head>`, its predecessor in k1's map over `<k2>..<k1>~1`, and so on, with the last range at `<kn>~1`. It stops when an id was renamed away at a cut, and it says so in The trail.
- trail.spec: a ranges case with two cuts (an item renamed twice; an id renamed away at the older cut).
- capture-cli.spec: a fixture with two compactions, where the item renamed twice keeps its `tracker: new` capture from before the first one, and a number reused across the first one isn't confused with the other item.
- Rows for "only the newest cut is read" and "renamed-away checked only at the newest cut", run on the prototype.
- Change the lesson's check and How to apply to "its ids before every compaction", and fix c0119's Design, the tracker command-table row ("before the last compaction") and the refute claim the same way.

### F2 [medium] The capture rule is written as "subject starts `tracker: new <id>`", but `trail.capture` takes any `tracker: new <issue id>` commit that touched the document. No case pins which, and the two readings give different captures on the real tree
Where: c0119 Design ("the newest commit on `origin/main` whose subject starts `tracker: new <id>`"), the Appendix's ticket-prep paragraph (the same words), and c0119's decision line ("its last `tracker: new <id>` commit"); against the tracker command-table row and the prototype (`^tracker: new [fdc]%d%d%d%d`); trail.spec's capture case; capture-cli.spec; ready-raft step 2 ("land their answer as a `Scope decision` line (a make-issue capture)")
Evidence:
- On the real tree, `capture c0114` prints `ab750c0 … tracker: new c0119 c0120; record z-nile scope decisions on c0114-c0118`. Read as the skill text has it, `<id>` = c0114 matches only `fb7fd80 tracker: new c0114 c0115 …` and the stub `1df2ea8`. c0115 to c0118 match only their stubs, because `fb7fd80`'s subject starts with c0114. For c0120 the literal rule finds the stub `e65c205 tracker: new c0120 pickman-home`, whose Problem is still a placeholder. So the skills and the command give different baselines for the next five z-nile issues.
- Every `tracker: new …` subject in trail.spec and capture-cli.spec names the item's own id. A mutant that requires the item's own id passes both specs, and so does the opposite one, so neither rule is pinned (the Rules row "the capture is the newest `tracker: new <issue>` commit" has no case that tells them apart).
- The implemented rule has a consequence nobody wrote down: any capture land that also edits another document moves that document's baseline (ab750c0 did this to c0114–c0118). ready-raft step 2 tells the agent to land a scope decision as "a make-issue capture", and make-issue step 6 commits it as `tracker: new <id> <title>`. So the first decision landed on a prepared member makes that member's whole prepared document, with every prep rewrite the decision didn't cover, its new capture.
Lesson: ticket-prep/restated-rules-move-together, ticket-prep/spec-design-correspondence
Critique: the tempting fix is to change the code to the item's own id. That makes c0120's capture its empty stub and c0115–c0118's their stubs, so item 11 compares against placeholders and passes. The other tempting fix, rewording the text to match the code, leaves the ready-raft path silently moving baselines.
Consequences: whichever rule is kept, it decides which commits move a baseline, and so where an author's decision commit must say something else. A decision commit with a subject that doesn't match keeps the original capture. Then later checks show the prep rewrite again next to the decision line, and the decision line has to say what it covers.
Recommendation:

- Pin it with a trail.spec case (a `tracker: new c0050 …` commit that edits c0010's document is c0010's capture, and a `tracker: scope c0010 …` commit is not) and with a capture-cli fixture commit of each kind. Add a row for each mutant ("own id only", "any `tracker:` subject"), run on the prototype.
- The user's decision line says "its last `tracker: new <id>` commit". If you read the multi-id subject rule as more than detail, escalate to the user: (a) any capture land that touched the document, (b) only subjects that name the item's id, with c0115–c0118 and c0120 then baselined on stubs.
