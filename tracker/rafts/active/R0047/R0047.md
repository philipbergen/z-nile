# R0047: Test lock pid reuse

## Theme
A single chore in the spec runner's guard (`tests/lib/fence.luau`): the test lock must not be held by a pid the system reused. Found in R0034 on 2026-10-21, when a reused worktree's day-old lock blocked the gate for 240 s. No product decision is involved.

## Whole-raft design
`tests/lib/fence.luau` gains `fence.STARTED`, `fence.startOf` and `fence.holds` (c0127's Design). Every process that records its pid in the run's lock also records its start id beside it (a worker's as the content of its own `pid-<n>` record, written whole; the top process's in `start-<pid>`; the takeover's owner: pid and id together in `<lock>.takeover/owner`), and `takeOverIfStale` judges each recorded pid by `alive` and then by comparing its start id now with the recorded one. The testing skill's Lock bullet restates the rule. Data: start ids from the kernel (`fence.STARTED`, perl: sysctl on macOS, `/proc` on Linux), written by the recording processes and read by a waiting top process; the existing lock files don't change. No `src/` change, so `tracker/architecture.md` is unchanged. Decided with the user on 2026-10-22 (c0127's Problem): start ids, compared for equality; a lock from an older runner, with no ids, is waited for as today.

## Order & dependencies
c0127 alone, no `depends_on`. Two other rafts change `tests/lib/fence.luau` and neither is merged yet: R0039 (c0075, prepared: the bwrap jail, which adds `pidns` and `fence.recordsPid` to how pids are *recorded*) and R0043 (c0114, in execution in PR #98: the path `fence.luau` sources `fence.sh` from). This raft changes how recorded pids are *judged* (`lockPids` to `takeOverIfStale`) and adds a start-id write beside each pid write (`takeLock`, `fence.enter`'s guarded branch, the takeover), so its hunks sit next to R0039's `recordsPid` gate around the `pid-<n>` write; whoever merges second keeps both. **R0039 also adds a pid writer**: its launcher (`fence.REAPER`) creates `<lock>/pid-<launcher>`. Whichever raft lands second makes that record carry the launcher's start id as its content (c0127 Design, Writers; the user's decision of 2026-10-22, design review 005 F1), so no new file appears beside it and c0075's `launcher-lock.spec` stays green; if R0047 lands first, its promoted `reuse.spec` recording case fails on R0039's branch until the launcher writes its id. The id lives in the record, so R0039's `recordsPid` gate covers it too (no record, no id). This prep adds the same note to R0039's Order & dependencies. Whichever lands second merges `origin/main` and keeps both. Under R0039's pid namespace, the reader's `/proc` inside the jail shows the namespace's own processes, and a lock recorded across namespaces is already filtered by `recordsPid`.

## Experiments phase
All ran in prep (c0127 E1 to E7; E7 ran the Linux reader on ubuntu through a dispatched CI run). The executor proves the branch on Linux again with AC5 (`scripts/ci-verify.sh`, on a pushed head) before `done`.

RC0: the full gate, c0127's check.sh (AC1 to AC4) and the promotion dry run. c0127's `reuse.spec` is already end to end: it runs a copy of the runner against hand-built locks.

## Risks & rollback
- **A live run's lock taken over by mistake** would let two runs share `.cache` fixtures, which is how a spec once reached the real repository (2026-09-30). The rule says no only when a live pid's start id is read now and differs from the one its own process recorded; a missing or unreadable id keeps today's answer (holds). Ids are kernel values compared for equality, so no clock step, rounding or slow subprocess can make a live holder look reused (c0127 E5). The jail, ref guard and tripwire don't depend on the lock.
- **Locks from older runners** have no ids and are waited for as today (the user's decision): a stale one left from before this change still has to be removed by hand, once. The wait message names its pids.
- **The start id comes from the kernel through perl**, not from `ps`: any `sandbox-exec` (the jail, Claude Code's own sandbox) refuses the setuid `/bin/ps` (design review 001 F3). The macOS reader ran inside the jail (c0127 E6) and the Linux reader on ubuntu CI (E7); the executor proves the branch on Linux again with AC5.
- **Design review**: round 1 (`design-review-001.md`) had three highs (a record dated by the wrong file survived; a stand-in `ps` answered any arguments; the fix did nothing inside a sandbox); round 2 replaced `ps` with the kernel reader. Round 2 (`design-review-002.md`) found the unreadable-start fail-safe unpinned where the lock is judged (high), the Linux start following clock steps, and the Linux proof deferred past `done`; E7 then ran on Linux in prep. Round 3 (`design-review-003.md`) found that accepting the Linux clock-step risk rested on a false premise (Linux is a supported host, `SETUP.md`) and weakened a guard (high). The user chose start ids compared for equality (2026-10-22), which removes clocks from the rule; the design, specs and prototype were redone (c0127 E3, E4, E7), and round 3's other findings (ids read only for live pids, a stand-in that refuses one pid only, AC5 needs a pushed head) are answered in them.
- **Lessons pass**: `ticket-prep/new-rules-migrate-existing-work`: old locks have no ids and keep today's behaviour (the user's decision), and old files are unchanged, so readers of `pid` (c0058, the sweeper specs) are unaffected. `ticket-prep/restated-rules-move-together`: the testing skill's Lock bullet changes with the code (AC3). `architecture/guard-no-is-explicit`: only a read id that differs from a recorded one says "not a holder". `architecture/lock-reads-live-state`: the id is read from the kernel at judging time. `architecture/clock-before-subprocess`: no clock at all. `ticket-prep/fallbacks-name-the-modes-they-cover`: the reader works in a plain shell, the jail, an outer sandbox and on Linux. `ticket-prep/prove-specs-pass-on-a-prototype`: every case and mutant ran on the prototype, and the promoted gate ran on macOS and on Linux CI. `testing/pin-fail-safes-where-they-act`: both fail-safes (no id, unreadable id) have end-to-end cases. `ticket-prep/design-the-execution-window`: R0039 and R0043 also touch `fence.luau` (Order & dependencies). `ticket-prep/spec-design-correspondence`: one spec file per AC.
- **Round 5** (`design-review-005.md`, the last round) found that separate `start-<pid>` files beside workers' records would break R0039's sequestered `launcher-lock.spec` (it expects the lock to list only `pid-<launcher>`), whichever raft landed second (high). The user chose to store a worker's id as its record's content (2026-10-22, c0127's Problem). Round 5's other findings (the owner's two fail-safes, the id under R0039's record gate, the reused-pid sentence) are answered in c0127. Five rounds is the most the process allows, so the redesign gets no sixth review: it was re-run on the prototype (c0127 E3, E4: 17 of 17 cases, every listed mutant caught; the promoted gate on macOS and Linux CI), and the code reviewer sees it in execution.
- **Rollback**: revert the PR. The `start-*` files a newer runner leaves in a lock are ignored by an older one.
