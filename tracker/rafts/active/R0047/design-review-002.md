### F2 [medium] On Linux a forward clock step at any point in a holder's life makes it look reused; E5 and the raft's Risks say only a backward jump before the record can
Where: c0127 Design ("Neither branch reads the clock … the start is absolute"), E5; R0047 Risks ("the one way a genuine holder could look reused"); refute 001 F4 ("the start is absolute"); new lesson architecture/clock-before-subprocess ("read an absolute time (the process's start from the kernel …), so no clock is involved at all")
Evidence: on macOS `p_starttime` is wall time stamped at fork and never changes. On Linux, field 22 counts ticks after boot (on the boot clock), and `btime` is the kernel's boot offset (`offs_real - offs_boot`), which moves on every clock step (`settimeofday`, ntpd's step above 128 ms, timesyncd's step after resume, a VM's time resync). So `btime + ticks/hz` is "the start as seen through today's clock offset". Take a holder that writes `pid-<n>` at wall time W. A forward step of S > 2 s, at any later moment while it runs, makes the reader return about start + S, which exceeds W + 2. The next waiter then takes over a live lock. On macOS the window is a backward jump between start and record (E5). On Linux it is a forward step at any time from the record to the judging, which can be the whole length of a run, a suspended laptop's resume included. The claim "the start is absolute" is false for half the platforms, and the new lesson repeats it.
Critique: the author will want to call it rare and move on. It is rare, and CI runs one gate per checkout. But the Risks section exists to say exactly which mistakes can cause a false takeover, and today it names the wrong one for Linux. Linux runs are also unjailed until R0039, so the lock is one of fewer guards there.
Consequences: no wall-clock reconstruction fixes it. `now - (uptime - ticks/hz)` is algebraically the same thing. A step-proof Linux rule needs a time on the boot clock at record time, which means writing it into the record. That is a format change, which the Non-goals rule out (the author's own fence, not captured scope). Locks left by older runners, with no such field, would fall back to the mtime rule.
Recommendation: correct E5, the Design sentence and R0047's Risks. On Linux the start is rebuilt from boot-relative ticks through the current clock offset, so a forward step of more than 2 s while a run holds the lock makes it look reused. Then record the choice explicitly: either accept it (rare; CI runs one gate per checkout; say which guards still stand on Linux), or record the boot-clock start in `pid-<n>`/`pid` and compare raw ticks on Linux, with a migration line for old locks. Fix the lesson's "so no clock is involved at all" to say that it holds where the kernel stores the start as wall time (macOS), not where it rebuilds it from boot time (Linux).

### F3 [medium] The Linux reader is proven only after `done`, though CI can prove it in prep and before `done`, and its claimed fallback is wrong
Where: c0127 E7 ("no Linux here"; "Fallback: a wrong branch exits 1, which keeps today's behaviour on Linux"), Implementation step 5, R0047 Experiments phase and Risks
Evidence: (1) Linux is at hand. `.github/workflows/check.yml` takes `workflow_dispatch`, and on a raft branch it runs the raft's sequestered `active/*/acceptance/*.spec.luau` on ubuntu-latest "proven on Linux before `tracker.sh done`". `scripts/ci-verify.sh` dispatches it and waits. R0039 ran its prep experiments this way on GitHub's ubuntu-latest (R0039.md, Experiments). A throwaway branch of `proto-c0127`, with the three specs under `tests/acceptance/c0127` as in E3, would run E7 in prep. (2) The fallback claim is false. A wrong field index doesn't exit 1, it returns a wrong number. Field 21 (`itrealvalue`, 0) returns `btime`, so every pid holds, which is harmless. Field 23 (`vsize`, bytes) or a mis-scaled `hz` returns a start far in the future, so every live holder looks reused and every lock is taken over, which is the dangerous direction. (3) Found after `done`, a Linux defect means changing code after the issue's review round resolved and its check.sh passed. Nothing in c0127/check.sh or R0047/check.sh runs the Linux branch, so `done` can pass with it wrong.
Critique: deferring is acceptable only when nothing earlier can run it. Here something can. The executor reading step 5 sees a check that comes after the gate it protects (ticket-prep/no-check-red-between-steps, in reverse).
Consequences: a ci-verify run needs the branch pushed with HEAD equal to `origin/<branch>`, and it talks to GitHub. `check.sh` files may do both (testing skill; c0001's AC3 is the precedent), but they run outside the jail and must not fetch into anything but `refs/remotes/`. ci-verify only fetches.
Recommendation: run E7 in prep, by dispatching the prototype with the promoted copies on a throwaway branch, and record the run's URL and the `rules.spec` result. Move the executor's Linux proof before `done`: a check in c0127/check.sh like c0001's AC3 (`scripts/ci-verify.sh` and a successful dispatched run for HEAD), or at least an implementation step before `done`. Correct E7's fallback sentence to name both directions a wrong index can take. If the dispatch can't run in prep, record why, and keep the pre-`done` dispatch.
Lesson: ticket-prep/instructions-runnable-where-they-run
