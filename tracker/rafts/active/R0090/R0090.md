# R0090: Pellets and mechanics

## Theme
Roadmap raft **c**, the rules half of making it a game: eating, score, lives, levels and power pellets, all in pure Logic, in a solo pellet-eating run with no danger yet. It builds on R0040 (maze, movement, session) and extends its `Session`. The presentation half (HUD, drawing pellets, start / game over / play again flow) is **R0150**, split off on 2026-09-30 by the user ("Split in two") so this raft stays one reviewable, headless-testable PR.

Decisions from `tracker/game-design.md` this raft relies on (quoted):
- **Pillar 2**: "Everything that decides an outcome runs in pure Logic, can be simulated headless and is tested in CI. Roblox renders and relays input."
- **Authority**: "The server simulates every maze. Clients send intents and render the replicated state."
- **Points**: "pellet 10, power pellet 50, ghosts 200/400/800/1600 within one power period." (ghost points: raft d)
- **Lives**: "3." and **an extra life once, at 10,000 points** (user, 2026-09-30).
- **Levels**: "clearing all pellets advances to the next level. Speeds, the frightened duration and the mode schedule vary per level, following the classic tables."
- **Collisions**: "pellets are eaten when the player enters a tile."
- **Eating slowdown** (user, 2026-09-30): include the classic pause: one frame of the arcade's 60 fps per dot, three per energizer.
- **Movement**: "Level 1 is 7.5 tiles/s, the arcade's 80%"; "per-level speeds come with raft c".
- **Frightened speed** (user, 2026-09-30): the player runs faster while a power pellet is active, per Table A.1 (a second `Levels` column).

## Whole-raft design
```
  src/shared/Logic (pure, Lune-tested)
  ┌────────┐   ┌──────────┐   ┌─────────┐   ┌────────┐
  │  Maze  │◀──│ Pellets  │   │ Levels  │◀──│  Game  │   Game: one player's run (phases, lives, level, score,
  │ f0100  │   │  f0150   │   │  f0170  │   │ f0170  │   frightened counter). Levels: the one per-level table.
  └────────┘   └────┬─────┘   └────┬────┘   └───┬────┘
       ▲            │              │            │
       │    ┌───────┴──────────────┴────────────┴────────┐
  Movement ◀│ Session  (per player: Movement + Game + Pellets)│◀─@game─ src/server/Sessions.luau
            │ step / kill / playAgain / snapshot / frame  │          Session.GAME_CONFIG; FireClient(Session.frame)
            └─────────────────────────────────────────────┘
```
**Interfaces between issues**:
- **f0170 → f0150, f0160**: `Game` (`canMove`, `addScore`, `cleared`, `died`, `playAgain`, `step`), `Levels` (`playerSpeed`, `frightenedTicks`), `Session.kill`/`playAgain`/`frame`, `Session.GAME_CONFIG` and the member's `play`. f0170 also owns the events `Playing`, `Ready{reason}`, `LifeLost`, `GameOver`, `ExtraLife`.
- **f0150 → f0160**: the eating path in `Session.step` (`eat`) and `PelletEaten`; f0160 adds `Game.power` and the `PowerStarted`/`PowerEnded` events there.
- **To R0150 and raft d**: `Session.frame` (snapshot v1 + `play`), the events above, `Pellets.tiles` for f0290.
- **`Session.snapshot` stays the v1 schema untouched**; `frame` extends it. That keeps every promoted f0110/f0120/f0130 spec green, and lets later issues add fields.

**Order inside one `Session.step`** (a contract for raft d): decide `moving` and `frightened` at the start of the tick; `Game.step` (`Playing`/`Ready`/`GameOver`/`PowerEnded`); move; eat; power; clear; collision (raft d) comes after, and `Session.kill` is a no-op outside `playing`, so a ghost touching the player in the clear pause does nothing. **`jumpTick`** is "the tick of the first frame at the new position" (a teleport between steps, `playAgain`, records `tick + 1`).

**Two rule sets**: `Session.DEFAULT_CONFIG` has no pauses and no slowdown (legacy behaviour, used by all promoted specs); `Session.GAME_CONFIG` is the real game and is what the server adapter uses.

**Architecture changes** (made in prep, in `tracker/architecture.md`): new features `Levels`, `Pellets`, `Game`; new edges `Game -> Levels`, `Pellets -> Maze`, `Session -> Game`, `Session -> Levels`, `Session -> Pellets`.

## Order & dependencies

Each issue's acceptance specs pass when that issue completes and keep passing (they use explicit configs and never pin exact keys of extensible structures). ## Exit criteria
- `scripts/check.sh --full` passes, each member's `check.sh` passes, and the promotion check passes (RC0).
- **RC1**: a whole run plays headless through `Session` with `GAME_CONFIG`-style rules: countdown, eating, power pellet, clear, next level, deaths, game over, play again (f0160's `full-run` spec, run from its promoted location).
- **RC2**: the server adapter sends `Session.frame` with `Session.GAME_CONFIG` (f0170's adapter spec), and the v1 snapshot spec (f0120) still passes, so no consumer of the snapshot broke.
"Done" == `scripts/tracker.sh done R0090` succeeds.

## Risks & rollback
- **Rule sets out of step**: promoted specs only exercise `DEFAULT_CONFIG`; `GAME_CONFIG` is only exercised by f0170's config/adapter/flow specs and through R0150 in Studio. Mitigated: `full-run.spec` uses `Game.CLASSIC_CONFIG` with the slowdown on.
- **A cleared level that needs a pocket pellet**: several specs use a tiny maze with an unreachable pellet; if the executor changes how a level clears (e.g. counting pellets differently) those specs will tell.
- **Level speed table vs `Movement.UNITS`**: `Session.new` refuses a base speed where any level would exceed one tile a tick; raising the base speed in future needs a smaller tick step.
- **Rollback**: revert the PR; nothing persists (no data, no stores).
