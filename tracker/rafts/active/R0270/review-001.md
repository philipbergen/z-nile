### F1 [low] The CLI usage text omits `audit`, `compact`, `remap` and `renumber <directory>`, and misdescribes `renumber`'s default
Where: `scripts/tracker/main.luau` USAGE (lines 16-41); c0870 Implementation step 6 ("USAGE lines for `compact` and `remap`"), c0880 step 2 ("`cmd.audit` and the USAGE line"); `.claude/skills/tracker/SKILL.md` Worktrees item 1, the "tracker enforces part of this" sentence.
Evidence: `scripts/tracker.sh` with no arguments prints no `audit`, `compact` or `remap` line, and still says `renumber <old> [<new>] … <new> defaults to one above the highest`. With a `tracker/next` the default is now `max(counter, highest + 1)`, which is above the highest whenever an emergent issue reserved numbers. The skill's list of commands that refuse in the main checkout names `new`, `renumber`, `migrate`, `start`, `status`, `prompt`, but not `compact` and `remap`, which both call `refuseInMainCheckout`. The Verification logs don't record this as a deviation.
Critique: the user will run `compact` once, by hand, and in-flight branches run `remap`. `tracker.sh` with no arguments is the obvious place to find them, and two issues' implementation steps say to add these lines. The fix the author will reach for is adding three lines.
Consequences: the `renumber` line also has to cover the directory form, or it stays half wrong. Nothing tests USAGE, so the text can drift again. That's acceptable for help text, and no sequestered spec needs changing.
Recommendation: add `audit` (read-only: every problem and a count; exit 1 on an error), `compact [--force]` and `remap` lines. Change `renumber` to `renumber <old|item directory> [<new>]   …; <new> defaults to the next free number (tracker/next)`. Add `compact` and `remap` to the skill's list of commands that refuse in the main checkout.

### F2 [low] `renumber <id>` on a duplicated id doesn't name the way out, as c0880's Design says it should
Where: `scripts/tracker/main.luau` `cmd.renumber`, the `item = store.get(arg)` branch; c0880 Design, Commands: "With an id instead of a directory, renumber is unchanged (and still refuses a duplicated id, naming `renumber <directory>` as the way out)."
Evidence: in the scratch clone, after `cp -R tracker/issues/done/c0001 tracker/issues/c0001`, `PICKMAN_PUBLISH=0 scripts/tracker.sh renumber c0001` exits 1 with `tracker renumber: duplicate id c0001: tracker/issues/c0001, tracker/issues/done/c0001`. That's `store.find`'s message, and it says nothing about `renumber <directory>`. `renumber tracker/issues/c0001` then worked.
Critique: someone who hits a duplicate runs the command the Conflicts bullet teaches (`renumber <ID>`) and gets an error with no next step. Only the skill's Duplicate ids bullet tells them about the directory form. The tempting fix is to wrap `store.get` in `pcall` and append a hint to whatever it raised.
Consequences: a generic hint on every `store.get` error would also show for "no such tracker item", which is wrong there. The hint has to name the right copy: the ones not in `done/`. When neither copy is in `done/` (backlog and active), it has to name both, and the user decides which to move.
Recommendation: before `store.get(arg)`, collect `audit.scan(".")` entries with `f.id == arg`. If there are two or more, fail with `renumber: <id> is in <paths>; renumber one copy with tracker.sh renumber <directory> (not the one in done/)`, listing the non-`done/` paths as the candidates. Add a non-sequestered case to a tooling spec (fixture: one id in `issues/` and `issues/done/`; expect exit 1 and the stderr to contain `renumber tracker/issues/<id>`).

### F3 [low] `compact.apply` rewrites promoted-spec paths inside `tracker/templates/`, which the Design excludes
Where: `scripts/tracker/compact.luau` `compact.apply`, the `git ls-files` loop. c0870 Design, compact step 5(c): "`ids.rewritePaths` over every **other** tracked text file (… skipping … `tracker/templates/`, `tracker/next` and the map file)".
Evidence: `rewritesIds` returns false for `tracker/templates/…`, so templates fall into the `else ids.rewritePaths(...)` branch. Only `ids.FILE` and `ids.MAP_FILE` are skipped. Today no template names a real `tests/acceptance/<id>` (`issue/check.sh` uses `{{ID}}`), so the trial compaction changed nothing there and the "templates untouched" spec case still passes. That case only seeds whole-token ids, not paths. The temporary rename name is `.compact-<name>`, not the Design's `<new>.compacting`. Neither deviation is in the Verification log.
Critique: a template that ever gives an example path such as `tests/acceptance/c0410` would be silently rewritten, against the rule the Design and the Rules and mutants row ("templates untouched") state. The fix is one condition.
Consequences: skipping templates entirely matches the Design and needs no spec change. The opposite choice, rewriting paths in templates on purpose, would need its own Design line and a spec case, so don't make it during execution.
Recommendation: skip `tracker/templates/` in the loop (`if path ~= ids.FILE and path ~= ids.MAP_FILE and string.sub(path, 1, 18) ~= "tracker/templates/"`). Record the `.compact-<name>` temporary name as a deviation in c0870's Verification log (it's hidden from `audit.scan` because it isn't an id, which is a reason to keep it).

### F4 [low] `ids.Space` and `audit.Problem.level` are typed as `string`, not the Design's singleton unions, so a mistyped space silently hands out a used number
Where: `scripts/tracker/ids.luau` `export type Space = string -- "issue" | "raft"`; `scripts/tracker/audit.luau` `Problem.level: string`. c0870 Design: `export type Space = "issue" | "raft"`; c0880 Design: `level: "error" | "warning"`. Architecture skill, Usability: "small, typed, and hard to misuse."
Evidence: `ids.nextFree("Issue", c, used)` type-checks. It takes `c.issue` (the `else` branch), and `ids.highest("Issue", used)` returns 0 because `spaceOf` never returns `"Issue"`. So it returns the counter even when `used` holds that number, which is the "never a used number" rule broken. With the Design's union type, strict luau-lsp rejects the call.
Critique: every caller in this diff passes a correct literal, so this isn't a live bug. But the `space: string` parameters in `main.luau` (`reserve`, `reserveOnOrigin`, `localNumber`, `localIds`) carry the same looseness, and the next caller could get it wrong. The tempting fix is changing the one `export type` line.
Consequences: loops like `for _, space in { "issue", "raft" }` then infer `string` and need `:: { ids.Space }` annotations. `counts[space]` in `cmd.compact` and `store`'s `Kind` have to agree. The prototype hit a luau-lsp quirk elsewhere (E4), so if the narrowing fights the checker, keeping `string` is acceptable only as a recorded deviation.
Recommendation: make `Space = "issue" | "raft"` and `level: "error" | "warning"`, annotate the literal tables and the `main.luau` helpers' `space` parameters, and run `scripts/check.sh` (types). If it can't be done cleanly, record the deviation and its reason in c0870's and c0880's Verification logs.

### F5 [low] `remap` leaks its scratch worktree, and loses its guidance, when the remapped base can't be built
Where: `scripts/tracker/main.luau` `cmd.remap`, from `sh.git({ "worktree", "add", … scratch, mb })` to `sh.run("git", { "worktree", "remove", "--force", scratch })`.
Evidence: the only failure handled there is `git add -A` or `git write-tree` failing. `compactLib.apply(m, audit.scan(scratch), scratch)` raises on any failed `git mv` (`gitIn` → `error`). That error leaves the run before the `worktree remove`. The registration then stays in the shared repository's worktree registry, the folder stays at `.cache/tracker-remap-base`, and the user sees a raw `git mv … failed` instead of "remap committed … merge origin/main by hand", even though the remap commit already exists.
Critique: `remap` runs on real in-flight branches, the one-off moment where a confusing failure costs the most. The next `remap` does remove the stale worktree first, so nothing is lost permanently. The tempting fix is a `pcall` around `apply`.
Consequences: the `pcall` must still remove the scratch worktree in every path and give the same "remap committed, … merge origin/main by hand" message, so the user knows the branch already holds the remap commit. Re-running `remap` at that point is unsafe (F6), so the message must not invite it.
Recommendation: wrap the scratch work (`apply`, `add`, `write-tree`) in one `pcall`, always run `worktree remove --force scratch`, and on failure `fail("remap committed, but the remapped merge base could not be built (<err>): git merge origin/main by hand and resolve; do not run remap again")`. No spec change is needed. If one is wanted, a tooling case can make the scratch `git mv` fail by making a target unwritable inside the fixture.

### F6 [medium] A second `remap` after a failed merge (conflict or F5) isn't refused, and it renumbers the already-remapped ids again
Where: `scripts/tracker/main.luau` `cmd.remap`, the once-only check (`if fs.isFile(idsLib.MAP_FILE) and fs.readFile(idsLib.MAP_FILE) == shown.stdout then fail(...)`) and the `unmapped` computation; c0870 Design, remap steps 1 and 4.
Evidence: the once-only check relies on the branch having origin's `tracker/compaction.txt`, which only arrives with the merge in step 4. When `merge-tree` reports a conflict, `remap` exits 1 after committing `tracker: remap ids`, with `remap committed, but merging origin/main conflicts: git merge origin/main and resolve`. The branch then has new ids (for example `c0001` … `c0085` in the real-tree trial) and no local map. Running `tracker.sh remap` again passes the once-only check. Every new id that isn't an old key in the map (`c0001` … `c0009`, `c0011`, …) counts as "the branch's own" and gets a fresh number from origin's counter, with a second counter reservation pushed. Every new id that happens to equal an old key (new `c0041` is also old `c0041 -> c0005`) is moved onto another item's number. Nothing audits the result before `remap` commits it. `remap.spec`'s "a second remap refuses" case covers only the successful path, where the merge brought the map in.
Critique: re-running a command that just failed is the natural reaction, the conflict path is ordinary (the branch and `main` both edited one document), and the result is silent renumbering of every item on the branch, plus wasted numbers on `origin/main`. The tempting fix is to also refuse when `HEAD`'s subject is `tracker: remap ids`.
Consequences: checking only `HEAD`'s subject fails as soon as the user commits a conflict resolution, or any other work, on top. The check has to look at every commit since the merge base: `git log --format=%s <merge-base HEAD origin/main>..HEAD` containing `tracker: remap ids`. After a successful remap the merge base is `origin/main` itself, so this check and the existing map check agree. A post-apply `audit.run` (any error: refuse to commit, `git reset --hard HEAD` advice, as `compact` does) is a second net for collisions the marker can't foresee. The user decision stays as the skill states it: after a conflict, merge by hand and never re-run.
Recommendation: in `cmd.remap`, after the fetch, refuse when any commit in `merge-base(HEAD, origin/main)..HEAD` has the subject `tracker: remap ids`, with `remap: this branch is already remapped; finish with git merge origin/main`. After `compactLib.apply(m, found)` and before the commit, run `audit.run(".")` and fail on errors, leaving the tree for `git reset --hard HEAD`. Put the conflict message in the skill's Compaction bullet ("if remap reports a conflict, merge `origin/main` by hand; never run remap twice"). Spec cases (non-sequestered tooling spec, or the c0870 follow-up): (1) remap with a forced conflict exits 1, and a second remap refuses and changes nothing (same HEAD, same origin counter); (2) the refusal still holds after an extra commit on top of the remap commit.
