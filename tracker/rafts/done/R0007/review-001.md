### F1 [medium] ticket-prep's `run` label points to a "mutation check" that no skill defines
Where: `.claude/skills/ticket-prep/SKILL.md:35` (step 3, the Rules and mutants bullet); `.claude/skills/review/SKILL.md:62` (design-mode item 0)
Evidence: The bullet says "`checked` is `run` if prep's mutation check ran it, else `reasoned`. When you prototype, fill the table from the mutation check." A grep of `.claude/skills/*/SKILL.md` for `mutat` and `prototyp` finds only this line and review item 0. Ticket-prep has no step that says to prototype, where to do it, or how to plant a mutant and confirm the case fails. Review item 0 then tells the reviewer to trust `run` rows ("Rows marked `run` were mutation-tested in prep; spot-run only the `reasoned` rows you doubt"). A prep author can mark every row `run` with no procedure behind it, and the reviewer is told to skip exactly those rows. c0043's own E2 shows how it was done (a prototype in a scratch worktree), but that lives in one issue, not in the skill the next author reads.
Critique: The audit only stays cheap if `run` means something checkable. As written, the label is self-certified, which brings back the sampled-coverage problem c0043's Problem describes. The tempting fix is one sentence: "mutation check: plant the mutant and confirm the case fails."
Consequences: That sentence raises questions the next prep will hit. Where does the mutant go? Not the repo tree: the acceptance specs are sequestered, and prep commits to main. What counts as "fails"? It must be an assertion failure, not a bash or require error, which is the same rule step 4 already gives for "fails for the right reasons". What does the reviewer see? Without a recorded result, `run` still can't be verified. There's also a cost: when prep has no prototype, every row is `reasoned`, and item 0 then asks the reviewer to spot-run rows against code that doesn't exist yet.
Recommendation: In ticket-prep (step 4, after "Verify the wiring", since the specs exist by then), add a short **Mutation check** bullet. When prep prototypes the change in a scratch worktree, apply each row's mutant to the prototype and run the row's spec case, which must fail on an assertion. Mark the row `run`, and record the outcome in Unknowns & experiments (as c0043's E2 does). With no prototype, rows are `reasoned`, and the reviewer judges them by reading, not by running. Make review item 0 match that wording ("spot-check" rather than "spot-run" when there's no prototype). Record the addition in the raft's "Addressed during execution" as a local adjustment. AC4 only checks `## 3.` and `## 5.`, so adding to `## 4.` doesn't disturb it.
