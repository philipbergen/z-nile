### F1 [high] The heartbeat snippet steps once per frame and keeps a departed player in `sessions`
Where: `tracker/issues/f0025/f0025.md` (Design, the heartbeat block); `tracker/issues/f0025/acceptance/sessions.spec.luau` (the `PlayerRemoving` case); `src/server/Sessions.luau:51-57`; f0065 Design and `tracker/issues/f0065/acceptance/sessions.spec.luau` ("a player who leaves has no run any more")
Evidence: Today the heartbeat is `for _ = 1, Session.advance(clock, dt) do` around `Session.step`, and `STEP_RATE` is 15 with `MAX_STEPS_PER_ADVANCE` 5. f0025 replaces that with one `Session.step` and one `onStep` per Heartbeat. `sessions.spec` requires a single `Hiscores.onStep` call whose text contains `Parent`, and does not mention `Session.advance`. f0054 only pins `Session.newClock(Session.STEP_RATE)`. Deleting the advance loop stays green and runs the maze at Heartbeat rate, about four times `STEP_RATE`. `LEAVE_STEPS` is 45 ticks (3 s at 15 Hz). Counted once per Heartbeat, 45 frames is under a second, so a disconnect at the start of the dying pause is dropped before `Game.step` emits `GameOver`. The same spec forbids `= nil` inside `PlayerRemoving` and skips that assert when the handler is absent. f0065, already `design: ready`, requires the opposite: after `leave`, `Sessions.isOver` is false, which is `sessions[player] == nil`. Keeping the row also keeps `FireClient` on a player whose `Parent` is nil. That call throws and the rest of that heartbeat does not step. `onStep`'s events argument is not required to be the return of `Session.step`.
Critique: The tempting fix is to paste `onStep` next to today's `FireClient` and delete only the `sessions[player] = nil` line. That still throws on the departed player, still fails f0065's leave case, and still drops the run if `onStep` is outside the advance loop. A side table that is not stepped inside `Session.advance` drifts from the dying timer by the same frame-versus-tick gap.
Consequences: The player must leave `sessions` immediately so `isOver` is false and f0065 will not teleport them, while the `Session` object keeps stepping with `here = false` until `onStep` returns `drop`. A rejoin's `Ready` creates a new session and must not alias that detached one, so two runs for one user id can submit. The detached run has no `Player` to replicate to. `FireClient` of the snapshot and of `Rank` has to be skipped when `Parent` is nil. Removing entries during the `pairs` loop skips other players; removal has to happen after the loop. Catch-up can call `onStep` up to five times in one frame, including the `GameOver` step and later empty steps. `once` already ignores those. `advance` returning 0 does not move `waited`, so the window is 45 steps, not 45 frames.
Recommendation: Keep the `Session.advance` loop. Inside it, for each live session: `events = Session.step(s)`, `onStep(runs[player], events, player.Parent ~= nil)`, submit only that `submission`, and `FireClient` the frame only when `Parent ~= nil`. On `PlayerRemoving`, store the cleaned name, set `sessions[player] = nil`, and move the session and `RunState` to a pending list that the same advance loop steps with `here = false` and no `FireClient`. Drop pending when `onStep` says `drop`. `HiscoreStore.submit` and `Ranks` take the captured user id and name, and `FireClient` the rank only if that player is still parented. Spec cases: `sessions.spec` requires one `Session.advance` and the only `Hiscores.onStep` textually inside that loop, with the events argument the result of `Session.step`; `FireClient` of `Session.frame` sits in a `Parent` check; `PlayerRemoving` both nils `sessions[player]` and parks the run; `Ranks` does not `FireClient` a player with `Parent == nil`. `leave.spec` stays the pure 44-then-GameOver case. Do not require `Sessions.isOver`; f0065 adds it.

### F3 [high] A rank that arrives after the overlay closes is shown on the next run
Where: `tracker/issues/f0026/f0026.md` (`hearRank` / `follow`); `tracker/rafts/R0011/R0011.md` (the rank paragraph and Risks); `tracker/issues/f0026/acceptance/flow.spec.luau` (the stale-run case)
Evidence: `drive` is spawned and may `FireClient` the rank after the player has left the overlay (play again today, or the next visit's game over). `hearRank` sets `rank` whenever `run == view.over`, and dismiss only happens on true→false, which clears `rank` before that packet. Sequence the spec never runs: `follow` into over 1, `follow` back to playing, `hearRank(view, 1, 4)`, `follow` into over 2. `run == 1` matched the current `over` while the overlay was down, and the edge into over 2 does not clear `rank` in the issue text. `shownRank(..., true)` is then `ALL-TIME #4` for a run that did not earn it. `flow.spec` only hears run 1 after `over` is already 2, and that identity check passes if `hearRank` ignores `run < over`. The raft's "drops any other rank" sentence is not in the issue's `follow` paragraph and is not asserted.
Critique: The tempting fix is another `if run == view.over then rank = ...` guard. That is the bug: after dismiss, `over` is still the run that just ended, so the late packet looks current. Ignoring every packet while the overlay is down also drops the early packet the spec does lock (`hearRank` at `over == 0`, applied on the next edge).
Consequences: `follow` on false→true must clear `rank` unless `pendingRun` equals the new `over`, and must clear `pending` when it does not match. A late packet for the run already showing can still apply. A late packet after dismiss must not. A second early packet for `over + 2` is not stored (only `over + 1` is pending); do not widen pending to a map in this raft. `shownRank` stays nil when `gameOver` is false, including when `rank` was set and then cleared on the next edge.
Recommendation: State that rule in f0026, not only in the raft risks. Spec cases, in order: early rank 3 at `over == 0` still appears on the first edge; dismiss, then `hearRank` of that same run, then the next edge, `shownRank` is nil; a rank heard while that next overlay is up still shows; run 1 heard when `over` is already 2 stays nil and returns the same table. Add a rules-table row whose mutant is "entry leaves `rank` in place".

### F4 [high] The last `SetAsync` wins, and the specs cannot see the ordered page
Where: `tracker/issues/f0024/f0024.md` (`drive` get / `setScore` / `setEntry`); `tracker/issues/f0024/acceptance/drive.spec.luau` (the success `io`); `tracker/rafts/R0011/R0011.md` (E10, the `io.top` sentence)
Evidence: `drive` reads the companion, then `setScore`, then `setEntry`. Both calls yield. Two drives for one user interleave: run 1's score 5000 and run 2's score 100 (play again, or F1's detached run overlapping a new server) can both `get` nil or the old row, and the later `SetAsync` keeps 100. `qualifies` on a stale read does not stop that. OrderedDataStore has `UpdateAsync`; the design never calls it. The success fixture writes both `setScore` and `setEntry` through the same `store.set`, and `top` reads that store, so a drive that never writes the ordered value still ranks. Nothing names `GetSortedAsync`'s ascending flag. The API sorts low to high when that flag is true, and the fake's `top` sorts high to low, so an adapter that passes `true` ships the lowest scores and passes AC3, AC5 and AC6. `adapter.spec` only checks that the words `Hiscores.drive` and `GetSortedAsync` are absent or present as needles; `GetSortedAsync` is not even a needle.
Critique: A retry around `SetAsync` repeats the race. Writing the companion first, or the ordered value first, still leaves a window where the two disagree, and `rows` then shows the page score while `qualifies` trusts the companion, so a later attempt will not repair a lower ordered value once the companion already holds the higher score. Gating the write on `io.get` in a test double that ignores interleaving does not kill it.
Consequences: `UpdateAsync` on the ordered key must return the max of the stored integer and the attempt, and it may run the transform more than once, with no yield inside the transform. A level-only improvement does not change the integer; the companion needs its own `UpdateAsync` that applies `qualifies` and returns the stored entry unchanged when the attempt loses. Only the score that transform committed is passed to the ordered update. If the ordered update fails, retry that update with the committed score and do not run `qualifies` again. `UpdateAsync` spends a read and a write; `spend` has to require both budgets or the call is skipped. `GetSortedAsync(false, pageSize)` is descending. Page size stays `pageAttempt` 10 then 50. `scorePage` still maps `value` to the displayed score. The in-memory `fake` used by `drive` has to apply `commit` inside one function so a second attempt cannot observe a pre-write snapshot. Boards stays read-only: a `SetAsync` or `UpdateAsync` there would accept a client payload and still pass `boardId`.
Recommendation: Add `Hiscores.commit(stored, attempt) -> Companion?` (nil when the attempt must not change the row) and use it as the companion transform. Ordered write is `UpdateAsync` to `math.max(old or 0, committed.score)`, not `SetAsync`. Spec cases: commit of a lower score returns nil and the stored name stays; two overlapping drives through a fake that yields between transforms keep 5000 rather than 100; `setScore` failing after a committed companion retries the ordered max and does not write 100; adapter source contains `UpdateAsync` and `GetSortedAsync(false`, and does not contain `SetAsync`; `Boards.luau` contains neither `SetAsync`, `UpdateAsync`, nor `HiscoreStore`. Keep the zero-list-budget case calling `top`.

### F5 [medium] Equal scores are ranked by key order, then the level rule only re-sorts that page
Where: `tracker/rafts/R0011/R0011.md` (`rows` and "do not fetch another page"); `tracker/issues/f0024/f0024.md` (`fake().top` is score desc, key asc; `rows` applies level)
Evidence: `GetSortedAsync` returns N entries by the integer only. `rows` sorts those by level, and the design forbids another page when a higher level was truncated. `fake().top` is specified to do the same. `rows.spec` feeds both tied rows in one hand-built page, so the level mutant dies there and the live cut does not. Eleven players at score 100 with levels 1..11: the page of 10 is whichever keys sort first, `rankOf` is nil for the level-11 player who missed it, and the overlay stays blank. Qualifying that player required a strictly higher level at the same score, and the board then omits them.
Critique: Fetching a second page of 50, the obvious patch, still drops the 51st tie, and `pageAttempt(2)` is only the error fallback for a rejected size of 10. The rule "level desc" and the rule "never read past the first page" cannot both hold for a tie on the last slot.
Consequences: The ordered integer has to carry the level or the design has to stop claiming a level order. Packing is the one that matches `qualifies`. `valid` already allows a score up to `2^53 - 1`, so a packed value needs a smaller cap. Levels past the width clamp in the integer and keep the true level on the companion for display; two clamped levels at the same score tie by user id. `scorePage` unpacks before `rows` displays the score. A raw score written as the integer sorts as a huge level-mixed key and must not be what `setScore` stores. No Beta migration: the raft stores nothing until this code is present. `rows` of an already-unpacked page stays as specified, including "do not pad" and "page score wins".
Recommendation: Pack `score * LEVEL_CAP + level` with `LEVEL_CAP` 10000, reject a score that does not fit in an integer under `2^53`, and clamp the packed level at 9999. `fake().top(board, 1)` for two equal scores returns the higher level's key, not the lesser user-id key. `rows.spec` keeps the in-page string-id tie. One rules-table row: mutant is "ordered value is the bare score", killed by that `top(..., 1)` case. State the clamp in the design so a later change does not "fix" it by reading page 2.

### F6 [medium] A failed or overlapping lobby read tells the client nothing, and the client asks once
Where: `tracker/issues/f0026/f0026.md` (Boards and `LobbyView` request `"all"` only when the remote exists); `tracker/rafts/R0011/R0011.md` (`lookup` nil keeps the cache and sends nothing)
Evidence: `lookup` calls `fetch` when the cache is stale. `GetSortedAsync` yields. The next `OnServerEvent` still sees the old cache, because `lastFetch` is per player and the shared cache is stored only after `fetch` returns. Each of those calls spends an ordered list request. The server list budget for `GetSortedAsync` is `5 + numPlayers * 2` per minute, and the design already refuses to gate `top` on `OrderedList` because that query is documented as 0. On `fetch` returning nil the adapter sends nothing. `LobbyView` requests `"all"` once, at bind, and has no second request when no event arrives. A cold lobby whose first read fails stays on `"No scores yet"` until the player rejoins the place. An empty successful board is a different case: `read.spec` caches `{}` and `lobby.spec` shows the empty string. That path is fine.
Critique: Replying with a fresh empty panel on failure wipes a good cache and still does not retry. A per-player gap does not collapse a yield. Caching `{}` on failure, so the next lookup looks fresh, hides the board for `CACHE_TTL`.
Consequences: One in-flight fetch per `cacheKey`, started before the yield, shared by every waiter. Waiters do not call `GetSortedAsync`. When it finishes, each waiter gets one `FireClient`, including the player who arrived mid-fetch. A nil fetch does not replace the cache, and each waiter is still answered: previous rows, or the empty panel when there were none. That answer is what lets `lines` show `"No scores yet"` instead of silence. The client may send `"all"` again only after `READ_GAP` and only if the last payload was the failure empty, not on a timer while the store is healthy. A retry that ignores the gap burns the list budget the design cannot read. Day and week buttons stay the extra requests they are. `Starts` still does not open a store.
Recommendation: Extend `lookup` with an in-flight flag: stale and in flight does not call `fetch` and does not move the cache. Spec cases in `read.spec`: two lookups at `now == at + ttl` with the flag set call `fetch` once between them; a nil fetch returns nil rows and the same cache; the flag clear at `now == last + gap` fetches again. `adapters.spec` requires `Boards` to `FireClient` on both the success and the failure branch of `lookup`, and `LobbyView` to `FireServer("all")` again only from a nil result after a gap, not from `WaitForChild("Board")`. Add a rules-table row for "in flight does not fetch" and one for "failure still answers".
