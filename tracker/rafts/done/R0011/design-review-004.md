### F1 [medium] A Boards read that throws outside the pcall'd `GetSortedAsync` wedges that board key for the life of the server
Where: R0011.md Boards bullet ("a `fetch` that sets the flag, puts the requester on the waiter list, reads, and clears the flag … `GetSortedAsync` … each `pcall`'d"); f0026.md line 76
Evidence: The design protects only the two `GetSortedAsync` calls. It leaves the store opens and the rest of the read unprotected. `GetOrderedDataStore` / `GetDataStore` can throw ("You must publish this place to the web to access DataStore" in an unpublished place, or a name or scope it rejects). On the prototype, with the stub's `GetOrderedDataStore` throwing once and then healthy, the throw escapes `lookup` and the handler. `inflight["all"]` stays true. A second player 60 s later is added to the waiter list and never answered (`expected 1, got 0`). Every later request does the same, so the waiter list grows without bound, and the client never retries, because a retry needs a failed answer.
Critique: The tempting fix is to `pcall` the open as well. That fixes this throw but not the next unprotected line in the read, and the flag stays cleared only by luck.
Consequences: An error anywhere in the read becomes a failed read. It sets the key's `Failure`, so the 2, 4, 8, 15 s window applies to it as well, and each waiter gets exactly one `failed = true` answer. HiscoreStore already `pcall`s each whole call, including the open (its own `pending()` case covers an erroring drive).
Recommendation: Specify that Boards' `fetch` runs the whole read (opens, both page sizes, `scorePage`, companion reads, `rows`) inside one `pcall`. Any error is a nil read, and the flag and the waiter list are cleared on every path. adapters.spec needs a case: a stub whose `GetOrderedDataStore` throws once. The requester gets `{ id, {}, nil, true }`. After `failureWait(..., 1)` the next request reads and every request is answered. Add a Rules row with the mutant "open outside the pcall".

### F2 [medium] A companion read that fails is treated as a missing row, so a too-good rank is published and a short board is cached as healthy
Where: f0024.md line 66 ("Companion reads for that page use `get` and `spend(budget("get"), 1)`; a failure skips the row. `rankOf` the result."); R0011.md Boards bullet (companion `GetAsync`s, then `rows`)
Evidence: drive on the prototype, with page `{2: 80, 7: 50}` and `io.get` for key `"2"` returning `(nil, "throttled")`: the rank for user 7 is 1. The true rank is 2 (`expected 2, got 1`). The overlay would show `ALL-TIME #1`. Boards on the stub, seeded with Bea (80) and Ada (50), with Bea's companion `GetAsync` erroring: Ada is answered with one row, highlight 1 and `failed = false`, and that result is cached for `CACHE_TTL`. The likeliest cause is throttling, not a missing companion: one lobby read costs up to 10 `GetAsync`s against a StandardRead budget of 60 + 10 × players a minute, and drive adds up to 10 more per submit. A `"get"` budget refusal partway through the page does the same in drive.
Critique: Skipping is right for a companion that is truly absent (`(nil, nil)`). It is wrong for a read that failed: the ordered page says a better row exists. The tempting fix is to retry that one `GetAsync`. That adds budget cost in the very case where the budget is short, and the rank is still wrong when the retry also fails.
Consequences: `rows`' getter needs to signal "unknown" separately from "absent". For example, the getter returns `(Companion?, err?)` and `rows` returns nil when any getter errs, which changes `rows`' contract and rows.spec. In drive, an unknown row means `rank = nil`, so no packet is sent and the overlay shows no line, which is already a supported state. In Boards it means a failed read (nil rows), so path (2) answers `failed = true` with the previous rows, the read is not cached, and the F3 window backs off. One throttled read now fails a whole board, and the window bounds what that costs.
Recommendation: Specify the absent/unknown split in `rows`, drive and Boards. The specs need these cases. drive.spec: `io.get` errors for a key above the player, so `rank == nil`; a `"get"` budget that refuses the second page key also gives `rank == nil`. rows.spec: a getter error makes `rows` return nil, and a `(nil, nil)` row is still skipped. adapters.spec: one companion `GetAsync` error gives `failed = true` with the previous rows, nothing is cached, and the next read after the window is healthy. Add Rules rows with the mutant "error skips the row".

### F3 [medium] The window answer's "previous rows" has no case, and answering with an empty board passes
Where: R0011.md Boards bullet, path (4) ("nil rows inside the requester's gap or the key's failure window, not in flight: the previous rows (or `{}`) with `failed = true`, without a read"); f0026.md Rules row "A failed read still answers once, with the previous rows"
Evidence: In the prototype Boards I replaced the path (4) answer `answer(player, id, if cache then cache.rows else nil, true)` with `answer(player, id, nil, true)`. All 17 adapters.spec cases still pass. Every window or gap case in the spec runs with no cache (the outage starts on an empty store). Only path (2), where this requester's own fetch failed, is asserted with the previous rows (`{ "all", healthy[2], 2, true }`).
Critique: In a real outage the board was healthy a minute earlier. With this mutant, every player who asks inside the window sees "No scores yet" instead of the rows the server is holding. This is the common case the window was added for (review 003 F3), and the spec does not test it.
Consequences: none beyond the case. The highlight in that answer is the requester's own rank on those cached rows, the same rule as path (2).
Recommendation: In adapters.spec, after the healthy answer and the `CACHE_TTL` failure, have another player ask one second later (inside `failureWait(..., 1)`). That player gets `{ "all", healthy[2], <their rank or nil>, true }` with no new read. Then have the requester who just failed ask again one second later, inside their own gap, and expect the same rows. Add the mutant window-empty-rows to the Rules row.

### F4 [low] Boards keeps every visitor's `Player` in `lastFetch` for the life of the lobby server
Where: R0011.md Boards bullet ("a per-player `lastFetch`"); f0026.md line 76; no `PlayerRemoving` in the design
Evidence: The prototype's `lastFetch: { [Player]: number }` is written on every fetch and never cleared. A lobby server lives long, and each visitor passes through briefly (teleport to the game, return through f0065), so the table keeps one destroyed `Player` instance per visitor indefinitely.
Recommendation: Clear `lastFetch[player]` on `Players.PlayerRemoving`, or make the table weak-keyed (`__mode = "k"`). Say which in the Boards bullet. A source check in adapters.spec is enough. Starts' `Players` usage is unaffected.

### F5 [low] A pending retry, or a late answer, redraws a board the player has already left
Where: R0011.md LobbyView bullet (each answer is drawn; a failed answer schedules `FireServer` of its own board); f0026.md line 82
Evidence: Per the prototype LobbyView: a failed `"all"` answer schedules an `"all"` ask 1 s later. The player taps TODAY and a healthy TODAY panel is drawn. The timer then fires `FireServer("all")`. Its answer (failed, inside the window) redraws HISCORES and schedules another `"all"` retry, so the player is pulled back off the board they chose. The same happens without a failure when a tap's answer arrives after a later tap's answer (TODAY's read yields while THIS WEEK is cached): the older board is drawn last.
Recommendation: LobbyView keeps `wanted`, the board last asked for by the start ask or a tap. It draws an answer only when `Lobby.board(id) == wanted`, and a scheduled retry asks only if `wanted` has not changed since it was scheduled. Consequence: the existing case "a failed day or week answer asks again for that board" fires answers without a tap, so it must tap TODAY and THIS WEEK first. Add a case: failed `"all"`, tap TODAY, tick 1 s, and the asks are `{ "all" }, { "day" }` only.
