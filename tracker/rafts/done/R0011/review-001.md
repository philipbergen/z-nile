### F1 [medium] The three board buttons sit on top of START GAME on every screen under 2200 px tall
Where: src/lobby/client/LobbyView.luau, the board button loop (`pick.Size = UDim2.new(0.18, 0, 0, Lobby.BUTTON_MIN_PX)`, `pick.Position = UDim2.fromScale(0.26 + 0.24 * (index - 1), 0.88)`) against the existing Start button (`Size = UDim2.new(0.5, 0, 0.12, Lobby.BUTTON_MIN_PX)`, `Position = UDim2.fromScale(0.5, 0.74)`, both with AnchorPoint (0.5, 0)).
Evidence: Start spans y from 0.74H to 0.86H + 44 px, and x from 0.25W to 0.75W. The board buttons start at y = 0.88H, so they overlap Start whenever 0.86H + 44 > 0.88H, that is H < 2200 px. At x they span 0.17–0.35W, 0.41–0.59W and 0.65–0.83W, all inside Start's width. Concretely, on a 1920×1080 screen Start ends at 973 px and the buttons begin at 950 px (23 px overlap). On a phone in landscape (about 390 px tall) Start covers 289–379 px and the buttons cover 343–387 px, so 36 of the buttons' 44 px lie inside START GAME. The buttons are parented after Start and take the tap, so pressing the lower part of START GAME opens TODAY or THIS WEEK instead of starting a run, and the start label is partly hidden. On screens under about 367 px tall (0.88H + 44 > H) the buttons also run off the bottom edge. No spec catches this: `adapters.spec` checks only `Size.Y.Offset >= BUTTON_MIN_PX`, and the f0061 spec checks only that Start's scale position is in [0, 1).
Critique: the most likely quick fix is to nudge the scale, for example to 0.90. That still overlaps below 1100 px (0.86H + 44 > 0.90H), so it fixes the author's monitor and leaves every phone broken. The cause is mixing a scale-based stack with a fixed 44 px offset. Mobile polish belongs to f0029, but a primary button that is partly covered isn't polish. This raft adds the overlap, on desktop as well.
Consequences: a layout that stacks by offset has to fit the whole column (Title, Rows, Message, Start, the board row) on the shortest supported screen, so the Rows or Message heights may have to give way. The f0061 pins are loose: Start's `Size.Y.Offset >= 44`, its scale position in [0, 1), and every named element visible. So moving Start or Rows breaks no sequestered spec. Without a spec, the next layout change can bring the overlap back.
Recommendation: lay the board row out where it can't intersect Start at any height. One option is directly under the Title: put the row at `UDim2.new(x, 0, 0.16, 0)` and move `Rows` down by an offset of `BUTTON_MIN_PX` plus a gap, sizing Rows so it ends above Message on a 390 px screen. Another is to anchor the row to the bottom edge with `AnchorPoint (0.5, 1)` and a small negative offset, and move Start up by an offset so its bottom stays above the row. Add an unsequestered spec (for example under `tests/unit/Lobby` or `tests/place`, booting `LobbyView` on the fake the way f0026 `adapters.spec` does, with a fake that has a Board remote). It should compute each element's pixel rectangle from its `UDim2` Size, Position and AnchorPoint at 844×390 and 1920×1080, and assert that the Start rectangle and the three board rectangles don't intersect and all lie within the screen.
