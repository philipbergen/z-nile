### F1 [high] the radar is laid out in DangerHud's device-safe frame, but jump.spec checks it in HudView's core-safe frame, so on a 320 px tall landscape phone it covers the LEVEL label
Where: tracker/issues/f0029/acceptance/jump.spec.luau:39-40, :93-96, :177-188; tracker/issues/f0029/f0029.md:165-169 (the clamp `y = math.max(l.textSize + 2 * l.margin, ...)` and "DangerHud's ScreenGui stays as it is (`IgnoreGuiInset = true`, so the device safe area)"); E7 at f0029.md:257 ("differ only at the top (the top bar), which moves neither the buttons nor the radar"); src/client/DangerHud.luau:49 and :75.
Evidence: DangerHud's ScreenGui has `IgnoreGuiInset = true` (DeviceSafeInsets), so `gui.AbsoluteSize` and the radar's origin include the top-bar strip. HudView passes `Hud.safeInset(None, CoreUISafeInsets)`, whose `top` is the top bar. The design's own documented sample shows that strip is 58 px in landscape (`(-59, -58)` against `(0, 0)`, f0029.md:69). `frameOf` in jump.spec builds the radar frame from the HudView inset (`i.left, i.top, ...`), so the spec models the two frames as the same thing. They are the same only when `top` is 0, and every landscape sample sets top 0 (jump.spec:55, :63, :71). A pure-arithmetic copy of the design's formulas (scratch, `$TMPDIR/.../r12/p.luau`), with DangerHud's frame equal to the full screen (no notch) and HudView's core top 58, gives:
- 568×320: radar `{441, 57}` to y 177. LEVEL is `{291, 65, 270, 14}`. They overlap.
- 480×320, the spec's own "old phone, landscape": radar y 57 to 177, LEVEL y 65 to 79. They overlap.
- 480×320 with a 36 px top bar: radar y 57, LEVEL ends at 57. They just miss.
- 667×375 and 640×360 with top 58: they miss.

So AC5's "the radar misses ... the four HUD blocks" holds in the spec and fails on a real short landscape phone. The top-band clamp has the same flaw: it is `textSize + 2*margin` from the device-safe top, so on 480×200 it puts the radar at y 28, under the 58 px top bar's buttons rather than below the text band. E7's "moves neither the buttons nor the radar" is true for the bottom edge and false for the clamp. An implementation that matches the design exactly passes check.sh and still draws the radar over the level number.
Critique: The tempting fix is to set a realistic `top` on the landscape samples. jump.spec's `frameOf` would then shift the radar down by that top as well, because it uses the HUD inset for both frames, and the radar would still pass while the real adapter does not. A second tempting fix is to move DangerHud's ScreenGui to `ScreenInsets.None` like HudView. That moves the edge arrows under the notch (they are placed from `gui.AbsoluteSize`, DangerHud.luau:108-128), and moving the arrows is a stated non-goal (f0029.md:27).
Consequences: Whatever fix is chosen, the radar needs to know where the HUD's text band starts in its own frame: the core-UI top minus the device-safe top. That is one more number from `GetInsetArea`, read in DangerHud or handed over from HudView. Handing it over is a new adapter-to-adapter call. `DangerHud.start(Camera.pose)` is pinned by f0033, so the number must not arrive through `start`'s argument list. The clamp can still collide with the jump buttons on very short screens; that is accepted today (f0029.md:169) and stays accepted. The jump-button small/large choice is made on the touch GUI's frame, so the radar's own `jumpButtons(0, 0, width, height)` call can disagree with it when the two frames' smaller sides straddle 500 (a 520 px device-safe side with a 58 px top bar is a 462 px core side). Taking the same top number fixes that as well.
Recommendation: Give `Hud.radarBox` the HUD's top offset in its own frame. For example, take a fifth optional `bandTop: number?` (through `side()`, nil is 0). Choose small/large from `min(w, h - bandTop)`, compute `jumpButtons(0, bandTop, width, height - bandTop)`, and clamp at `bandTop + textSize + 2*margin`, where `textSize` and `margin` come from the full frame as today. DangerHud computes `bandTop = core.Min.Y - device.Min.Y` from `GetInsetArea(CoreUISafeInsets)` and `GetInsetArea(DeviceSafeInsets)`, as a pure helper in Hud (for example `Hud.bandTop(core, device)`), and puts it in its one `Hud.radarBox(` call. jump.spec then models two frames. Each sample carries a device inset and a core inset, `frameOf` uses the device inset for the radar, and `layout` uses the core inset for the blocks and the zone. Add a 480×320 landscape sample with core top 58 and device top 0. The radar must miss LEVEL (y at least 86) and stay inside the screen. Make the 480×200 clamp case `bandTop + 28`. The adapter pin changes to the five-argument call text, and c0106's narrowed `adapter.spec` (prefix up to `radarSize`) still accepts it. Add rows: "the radar never enters the HUD text band, measured in HudView's frame", killing a clamp from the device-safe top (y 57 on 480×320/58), and "small/large uses the touch frame". E7 needs a Studio check: in the emulator on a landscape phone, `DangerHud`'s `AbsolutePosition.Y` is 0 while `GetInsetArea(CoreUISafeInsets).Min.Y` is the top bar. If the two frames turn out to share the top, `bandTop` is 0 and nothing else changes.

### F2 [low] "the power bar and the snap control need no rule" has two 1 px exceptions, one on a real phone width
Where: tracker/issues/f0029/f0029.md:171.
Evidence: On a 320×568 portrait screen (iPhone SE first generation, many 320 dp Androids), `layout` gives text 14, margin 7, bar 80. The snap button's x range is `320 - 14 - 80 - 44 = 182` to 226. The small legacy jump button starts at `320 - 95 = 225`. Their y ranges (H−51 to H−7 against H−90 to H−20) overlap, so the two overlap by 1 px. The design already notes the second case, the power bar at a smaller side of exactly 500. Neither is a sample, so no spec fails.
Critique: It is 1 px and the button cannot show today (E7). Lifting the snap button is not worth a new branch.
Consequences: None if it is documented. A rule that shifts the snap button left on narrow widths would change the pinned phone rectangles.
Recommendation: State the 320 px portrait case next to the 500 px one in f0029.md:171, so the next layout edit does not take "no rule" as proven. No spec change.

Verdict: changes
