### F1 [high] The `--jobs N is a cap` case fails a correct implementation about 5-10% of the time (round-2 F1's fix is racy)
Where: parallel-runner.spec.luau:118-134, the `--jobs 2` half (`t.expect(lastLine(two.stdout)).toBe("1 passed, 2 failed, 3 spec files")`). c0049.md Rules row "at most and exactly `jobs` at a time". design-review-002 F1, Consequences: "neither case is flaky".
Evidence: With 2 lanes, a and b start together and wait for c. c can only start when one of them ends. The first to end has necessarily failed, because c.ready couldn't exist yet. c then starts and writes c.ready at once. The other of a/b fails at its first poll after the shared `os.time()` deadline, and that poll lands up to about 60 ms later (each poll iteration spawns a `sleep 0.05` process). If c's start-up and marker write fit inside that window, the second fixture finds c.ready and passes, and the result is `2 passed, 1 failed`. That is a legal outcome for a correct runner, but the case rejects it. Measured on the correct implementation:
- The isolated `--jobs 2` three-way run (the spec's exact fixture source and `PICKMAN_RV_TIMEOUT=1`) gave `2 passed, 1 failed` in 2 of 40 runs idle, 5 of 50 in a second idle batch, and 0 of 30 under load.
- The whole parallel-runner spec failed this case 1 of 20 idle, 0 of 20 plus 1 of 6 under load, and once inside `c0049/check.sh` AC1 under load.

An instrumented batch recorded each fixture's start second. All 5 failures had a and b starting in the same `os.time()` second, so this is not a second-boundary effect, and switching to `os.clock` would not fix it. After promotion this case runs in every full gate (CI, RC0, the stop hook on ALL), so roughly one gate in 10-20 goes red for nothing. The executor can't fix it, because the spec is sequestered.
Critique: The tempting fixes are a longer timeout or `os.clock` deadlines. Neither closes the window: it's a poll-interval vs. process-start race, not a timeout-length one.
Consequences: The deterministic fact a cap of 2 guarantees is "the first of a/b to finish failed, and c passed", so the legal outcomes are exactly `1 passed, 2 failed` and `2 passed, 1 failed`. Accepting both still kills both mutants: uncapped lanes give `3 passed` (all three overlap well inside the 1 s timeout, as measured; under extreme load an uncapped run could also time out, so kills are near-certain rather than guaranteed), and hard-coded 2 lanes are killed by the `--jobs 3` half, which uses sticky markers and a 20 s timeout and is deterministic. A serial runner is already killed by the first case.
Recommendation: In the `--jobs 2` half, assert `two.ok == false` and that `lastLine(two.stdout)` is one of `"1 passed, 2 failed, 3 spec files"` or `"2 passed, 1 failed, 3 spec files"`. A comment should give the reason: the first finisher must fail, and c always passes. Leave the `--jobs 3` half as it is. Reword the Rules row to "at most `jobs` at a time (with 2 lanes at least one of the first two fails), and N above 2 is honoured", keeping both mutants. Then re-run the case at least 30 times on a prototype (idle and under load) and record the zero failure count in Unknowns & experiments, so the next reviewer sees it was run, not reasoned. If a fully deterministic count is wanted, use live markers instead: each fixture writes `<me>.running`, waits up to the timeout for three live markers, and removes its own before it passes or errors. Under a cap of 2 that run is exactly `0 passed, 3 failed`. It costs one more sequential timeout (about 1-2 s), which pushes the spec toward the c0005 floor, so split the rendezvous cases into their own spec file if you choose it.

### F2 [low] Two `check.sh` mutants survive AC4a/AC4/AC5: tests overlapping the static stages, and a wall time that measures only the tests
Where: c0049/check.sh `gate_stages_are_started_together`, `gate_prints_timings`, `gate_static_failure`; c0049.md "Decision: the tests do not overlap the static stages" and "gate wall time … from the start of `check.sh`".
Evidence: I committed a mutant `check.sh` (in the scratch clone) that starts `lune run tests/run >"$tmp" &` just before `par_wait || exit 1`, prints the buffered result in the tests stage, and starts the wall-time clock at `== tests`. AC4a, AC4 and AC5 all PASS: it has five `par_start` lines and one `par_wait`, the headers are in order, and on a format failure it exits before printing `== tests`. Only AC6 failed, and only as collateral. AC5's orphaned background suite kept running in the deleted copy, resolved `--show-toplevel` to the outer repo, and collided with AC6's fixtures. That catch is incidental, not designed.
Critique: Both are deliberate deviations from written Design decisions rather than easy slips, so the risk is small. Still, the AC5 orphan shows the overlap variant is actively harmful: a failing gate leaves a full suite running in the background.
Consequences: A deterministic proxy for "no overlap" is possible (for example, a spec fixture in AC5's copy that writes a marker if any spec runs), but it would need a sequestered spec added to the copy, which costs more than the risk.
Recommendation: No spec change. Add two `reasoned` Rules rows that say "code review" as the check: "tests start only after `par_wait` succeeds (no background job before it)" and "`gate wall time` is measured from the first line of `check.sh`". The code reviewer then has them on the checklist.
