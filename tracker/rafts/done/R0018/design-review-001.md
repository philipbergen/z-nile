### F1 [high] A transient 429/5xx on publish still turns `beta` red and blocks the merge, and the recovery doc contradicts itself on exactly that log line
Where: c0051 Non-goals (first bullet), Solution "Docs" bullet; R0018 Theme; scripts/deploy-beta.luau:26-28
Evidence: The raft Theme says "a transient Roblox 429 or 5xx must not make it red and block a merge". `beta` runs `deploy-beta` first, which calls `OpenCloud.publish`. That function still raises at once on 429 or 503, and `deploy-beta` prints it as `opencloud: publish failed with HTTP 503: ...`. The planned doc bullet says a log showing "`opencloud: ... failed with HTTP 429` or `HTTP 5xx`" is rerun, then lists "a failed publish" as a real failure ending in `BLOCKED:`. A publish 503 matches both rules, so the agent at merge time either reruns or blocks depending on which sentence it reads first. The non-goal's reason, "the publish is not idempotent in effect: it replaces what Beta testers play", doesn't hold either. Rerunning the job (the doc's own remedy) republishes the same build, and R0008's recorded decision is "last one wins". A retried publish that Roblox had in fact accepted adds one extra version of the same commit, and the job uses the number it is given back.
Critique: So the raft's stated goal is only met for the runtime-test half of `beta`, and the doc gives two answers for the publish half. The tempting fix is to drop "a failed publish" from the doc's real-failure list. That fixes the contradiction but leaves publish blips red until a human or agent reruns the job, which is the manual step this raft exists to remove.
Consequences: Retrying publish on 429/5xx means two pauses interact in one loop: 409 waits `retrySeconds` (60) and transient statuses wait `transientSeconds` (5). Someone has to decide whether the 409 and 5xx retries share one `MAX_ATTEMPTS` budget or have separate ones. A shared budget puts the worst case at 4 × 60 s = 240 s, unchanged. The c0051 spec case `publish is unchanged: a 5xx still fails at once` and the AC8 wording would flip, and the c0015 publish spec's "any other failure is final" cases need checking for 5xx inputs.
Recommendation: Pick one of these and write it into the issue before execution.
(a) Preferred: `publish` also retries `isTransient` statuses with one shared `MAX_ATTEMPTS` budget, pausing `retrySeconds` for 409 and `transientSeconds` for 429/5xx. Rewrite AC8 as "publish retries 409 (retrySeconds) and 429/5xx (transientSeconds) within one budget; 4xx other than 409/429 is final". Replace the spec case with three: a 503-then-200 publish succeeds with naps `{5}`; a 409-then-503-then-200 publish gives naps `{60, 5}`; a permanent 503 makes exactly `MAX_ATTEMPTS` calls. Check the c0015 publish cases against this. The doc's real-failure list then names `HTTP 401/403/404` and `FAIL` lines only.
(b) If publish must stay unretried, say so in the doc explicitly: `opencloud: publish failed with HTTP 429/5xx` is rerun under the same bound, and only a publish failing with another status is real. Amend the Theme so it no longer claims the goal for the whole of `beta`.

### F2 [medium] The pause used between poll retries is unpinned: two plausible mutants survive the spec
Where: c0051 Test plan, `pauses transientSeconds between retries ...` (creation only); Rules and mutants row "pause is `transientSeconds`, default 5"
Evidence: Every case that checks pause values (`naps toEqual`) fails on the creation POST. The poll-retry cases check only `#naps`. Two mutants pass all 13 cases: the poll path pausing `poll` (3 s) instead of `transientSeconds`, and the poll path hard-coding 5 and ignoring the config. I ran both in a scratch copy. Pausing for the poll interval is the natural mistake for an executor who writes the poll retry inline in the `while` loop rather than through `send`.
Critique: AC5 says "the pause between retries is `transientSeconds`", but only half the call sites are checked, and the table has no row for the poll site. The tempting fix is to add one `{5,5}` assertion to the poll retry case, but that still leaves the hard-coded-5 mutant alive.
Consequences: none beyond one more case or assertion.
Recommendation: In `retries a transient failure polling the task ...`, or a new case, use `transientSeconds = 2` and `pollSeconds = 7` with responses `created(), 503, PROCESSING, done()`. Assert `naps` equals `{2, 7}`, which kills both mutants and shows the transient and poll pauses kept apart. Add a Rules and mutants row: "poll retries pause `transientSeconds`, not `pollSeconds`".

### F3 [medium] With AC6, `execute` has no wall-clock bound any more, and the worst case runs past the `beta` job's 20-minute timeout, ending in a red the doc says not to rerun
Where: c0051 Design "Scalability", AC6; R0018 Risks ("at most 20 s per request"); .github/workflows/check.yml `timeout-minutes: 20`
Evidence: The budget is per request, and transient pauses don't count toward `timeoutSeconds`. Each of the up to `timeout/poll + 1 = 41` polls of one task (defaults 120 s and 3 s) can therefore spend 4 × 5 s in pauses. That is 41 × (20 + 3) s, about 15.7 minutes, plus 20 s for the creation, for one runtime script. Add `deploy-beta`'s 409 retries (up to 240 s) and setup, and the job passes 20 minutes. GitHub then cancels it, and the tracker skill classifies a job "whose steps ran" and was timed out as red, not rerun. The case is a Roblox that answers 503 about four times out of five for a quarter of an hour, which is the "bad Roblox hour" the Scalability section names. "Bounded 20 s per request" is true, but it says nothing about a run.
Critique: The unbounded part is the total time, not any one request. A run that should end in a clear `FAIL ...: HTTP 503` line ends instead in a cancelled job whose log names no status. The tempting fix is to drop AC6 and count pauses toward `timeoutSeconds`. That brings back the defect AC6 guards: blips eat into the time the script itself is allowed.
Consequences: A separate cap needs a rule for which error wins when it trips, plus one spec case. Its default has to fit `MAX_ATTEMPTS`, `timeoutSeconds` and the job's 20 minutes together.
Recommendation: Keep AC6, and add a per-`execute` cap on total transient pause time, for example `transientBudgetSeconds` defaulting to 60 s. Once it is spent, the next transient answer is final and raises the usual `... failed with HTTP <status>: <body>` text. Spec cases: (1) a poll sequence whose blips together exceed the budget raises with the last status, and the sum of transient naps is at most the budget; (2) the existing `counts attempts per request ...` case still passes under the default, or its numbers are adjusted and recorded. In Scalability, state the run bound: number of scripts × (timeout + budget) + publish, under 20 minutes.

### F4 [medium] RC1 doesn't check the exit status it claims to check
Where: tracker/rafts/R0018/check.sh, RC1
Evidence: `bash -c 'env -u ... lune run scripts/runtime-test -- 1 2>&1 | grep -q "not configured"'` runs without `pipefail`, so its status is `grep`'s. A `runtime-test` that prints the warning and then exits 1 passes RC1, though RC1 says "still ends green".
Critique: c0051 doesn't touch `runtime-test`, so the risk this round is small. But RC1 is the only guard for the fork and unconfigured path of the `beta` job, and as written it can't fail on the exit code.
Consequences: none.
Recommendation: `bash -c 'set -o pipefail; out=$(env -u ROBLOX_API_KEY -u ROBLOX_BETA_UNIVERSE_ID -u ROBLOX_BETA_PLACE_ID -u OPENCLOUD_BASE lune run scripts/runtime-test -- 1 2>&1) && grep -q "not configured" <<<"$out"'`. This also unsets `OPENCLOUD_BASE`, so a stray value on a developer machine can't affect it. The file is sequestered, so make the change now, in prep.

### F6 [low] AC1-AC7 all run the same whole spec, so any one failing case fails seven labels

Evidence: Every label runs `lune run tests/run -- "$SPEC"`. A single wrong pause value reports AC1 through AC7 all as FAIL, so the per-criterion labels don't point to the failing rule. They also cost seven runs of one spec.

The split is the one that keeps "one `check` per Checked criterion" meaningful.
