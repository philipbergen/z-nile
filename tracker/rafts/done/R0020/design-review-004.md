### F2 [high] The documented way for other branches to adopt the new layout fails for any branch whose items were moved, and the conflict rule misreads such a conflict as an id collision
Where: R0020 "Merge overlap with other in-flight rafts" ("runs `git merge origin/main`, then `scripts/tracker.sh migrate` (a no-op when nothing is legacy)"); R0020 Risks ("`migrate` is idempotent and is what in-flight branches run"); c0420 Regression guard ("In-flight branches … get a clear error and the `migrate` command"); c0420 Docs and c0041 landing step 0 ("If the merge conflicts in `tracker/…/<ID>/<ID>.md`, two items picked the same number: `git merge --abort`, `renumber` …")
Evidence: this was reproduced in a scratch repo. The base has `tracker/issues/c0400/c0400-raft-browser.md`. Branch `inflight` runs what `start` does (`git mv tracker/issues/c0400 tracker/issues/active/c0400`) and edits the doc. `main` runs what `migrate` does (`git mv …/c0400-raft-browser.md …/c0400.md` plus a `slug:` line). Then `git merge main` on `inflight` exits 1 with `CONFLICT (rename/rename): … renamed to tracker/issues/active/c0400/c0400-raft-browser.md in HEAD and to tracker/issues/active/c0400/c0400.md in main`, and leaves both files in `active/c0400/`. The step "then run `migrate`" is never reached, and if it were, `migrate` would report the directory as `ambiguous`. Pre-migrating the branch before the merge doesn't help either: the merge exits 1 again with `CONFLICT (content): Merge conflict in tracker/issues/active/c0400/c0400.md`. That is a conflict on `<ID>/<ID>.md`, so landing step 0 and c0420's Conflicts text would call it "two items picked the same number" and have the agent renumber a single real item into a duplicate. `git merge -X no-renames` merges cleanly but brings back a stale `tracker/issues/c0400/c0400.md` beside the active one, which c0041's duplicate-id error then reports. This bites in both directions:
- any raft that `start`s or finishes while R0020 is open makes R0020's own Phase 5 merge of `origin/main` conflict, because R0020 renamed every document on its branch;
- any raft that is active when R0020 merges conflicts at its own Phase 5.
The tracker skill's merging rule 4 then requires `BLOCKED:`.
Critique: the tempting fix is to document "resolve the conflict by hand". An agent can't tell a move-versus-rename conflict from a real edit conflict or from an id collision without a rule, and the whole point of c0420 is that collisions are recognized mechanically.
Consequences: the procedure has to tell three kinds of conflict on `<ID>.md` apart:
- `CONFLICT (add/add)`: an id collision, so renumber;
- `rename/rename` or `file location` on a legacy document: a layout transition, which needs a recipe or tooling;
- `CONFLICT (content)`: two edits to the same item, resolved as a normal merge, never by renumbering.
A tooling answer (for example `migrate` resolving a stray backlog `<ID>.md` against a legacy document in another state) adds a state that needs spec cases. A policy answer adds a user decision and a line in the skills.
Recommendation: decide the transition policy, and write it into R0020's Order & dependencies, the Bootstrap and Risks. The simplest policy is that R0020 is executed and merged while no other raft is started or active, and no raft starts until R0020 has merged. Captures and preps that only add or edit backlog documents still use merge plus `migrate`; add a naming-spec case in which a branch that added a legacy document and edited an existing one merges a migrated `main` with exit 0, after which `migrate` converts it. Separately, narrow c0420's Conflicts text and c0041's landing step 0 to "`CONFLICT (add/add)` on `<ID>/<ID>.md`" (c0420's spec already asserts that exact marker), and say that a content conflict on a document is resolved like any other merge, never by `renumber`. If the user wants concurrent rafts during the transition, specify the recovery in tooling and give it a spec case built from the scratch scenario above.

### F3 [medium] Phase 2B has no step for a conflicting squash merge, and `tracker.sh commit` then commits the conflict markers and pushes
Where: c0430 protocol step 4 ("`git merge --squash ws-<issue>`, then `scripts/tracker.sh commit …`"); `scripts/tracker/main.luau` `recordAndCommit` (`sh.git({ "add", "-A" })` … `commit`)
Evidence: verified in a scratch repo. Two streams branch from the raft tip and change the same line. The first `git merge --squash wsA` and commit work. `git merge --squash wsB` exits 1 (`CONFLICT (content)`); then `git add -A && git commit -m …`, which is exactly what `recordAndCommit` does, exits 0, and the committed file contains `<<<<<<< HEAD … >>>>>>> wsB`. `tracker.sh commit` then pushes it. The plan keeps a wave disjoint only by the **declared** Touched modules, and nothing checks that a stream stayed inside them. Shared helpers (`tests/fixtures`, `tests/lib`), a spec a stream adds outside its declared paths, or an emergent issue (F4) all slip past it. The Luau gate would catch markers in `.luau` files, but not in skills or docs, which are what chore rafts like this one edit.
Critique: the tempting fix is a sentence: "if the squash conflicts, resolve it". That leaves the silent-marker path open whenever the lead runs the documented command after an unnoticed non-zero exit.
Consequences: a guard in `recordAndCommit` (refuse while `git ls-files -u` is non-empty, before `git add -A`) is a behaviour change to `tracker.sh commit` that needs its own Rules row and spec case. A containment check needs a definition of "inside": Touched modules, plus the issue's own document, plus `stream-review-<issue>-*` and `stream-refute-<issue>-*` files.
Recommendation: (a) in `recordAndCommit`, fail `unmerged paths: resolve the merge first` when `git ls-files -u` prints anything, before `git add -A`. Add a spec case (a conflicting `merge --squash`, then `tracker.sh commit` exits 1 and HEAD doesn't move) and a Rules row (mutant: no check). (b) Phase 2B step 4: if the squash conflicts, the lead resolves it in the raft worktree, notes it in both issues' Verification logs, reruns both issues' checks, and only then runs `tracker.sh commit`. (c) The stream reviewer checks that `git diff --name-only <raft branch>...ws-<issue>` stays inside the containment set above and treats anything outside it as a finding, and JC1's Pass clause names that check.

### F4 [medium] The stream brief and the prompt leave gaps: emergent issues, a contradicting hard rule, and leftover stream branches
Where: c0430 protocol steps 2, 3 and 5; `tracker/templates/prompt.md` hard rules 2 and 6; the tracker skill's "Emergent issues"
Evidence:
- **Emergent issues.** The brief says "stop and report … on the protocol's stop conditions", but says nothing about emergent problems. The tracker skill (which streams may read) says to run `tracker.sh new issue … --raft R…`, and prompt hard rule 6 says the same. Two concurrent streams that each do so pick the same next id from the same base. Thanks to c0420, the lead's second squash merge then hits an add/add conflict, the F3 path.
- **Hard rule 2.** The prompt says "Commit only with `scripts/tracker.sh commit`". c0430 has the lead commit stream-review files on the stream branch with plain git, and the streams commit with plain `git commit`. c0430 doesn't list the prompt's hard rules among its edits, so the prompt and Phase 2B disagree, which is a JC1 "contradictory step" for c0041 and c0430.
- **Leftover branches.** Step 5 has the lead finish a blocked stream in the raft worktree, but only step 4 (after a merge) removes `ws-<issue>`. A blocked stream's worktree and branch stay behind, `worktree-prune` never removes named worktrees, and a later `worktree ws-<issue> --from <tip>` silently resumes the stale branch (by design, `--from` is ignored for an existing branch).
Critique: the tempting fix is "streams never create issues". That is necessary but not enough: the lead still needs a way to receive a stream's emergent problem.
Consequences: an emergent problem found by a stream becomes a `blocked` report or a line in the stream's report, and the lead creates the issue in the raft worktree, keeping id allocation single-writer. The hard-rule exception has to be scoped so that it doesn't loosen commit discipline for the lead's own work.
Recommendation: the brief says streams never run `tracker.sh new`, `focus`, `commit`, `renumber` or `done`, and report emergent problems in their final report, where the lead files them. Prompt hard rule 2 gains "(in Phase 2B, stream branches are committed with plain git; the raft branch only with `tracker.sh commit`)", and JC1's Pass clause requires this. Step 5 removes the worktree and branch of a blocked or abandoned stream (the same chained command as step 4) after the lead has taken the issue over. Grep for the hard-rule wording in AC5.

### F5 [medium] c0430's plan rule "wave = 1 + max(wave of the after set)" has no case that can fail, and the surviving mutant schedules an issue alongside its own dependency
Where: c0430 Design, "Waves"; Rules and mutants (no row for the wave formula); `workstreams.spec.luau`; RC1
Evidence: the mutant `wave = 1 + #after` gives the same output as `1 + max` for every expectation in the spec. For R0010, f0030 and f0040 each have one element in their after set, so both give 2. For R0030, f0080's after set is {f0060 (wave 1), f0070 (wave 2)}, so both give 3. For RC1, c0430's after set is {c0420 (1), c0041 (2)}, so both give 3. The reason precedence (`depends_on` over `overlap` when both hold) has no case either: no fixture issue both depends on and overlaps another.
Critique: RC1 looks like extra coverage, but it's the same shape as R0030, so it can't separate the formulas.
Consequences: adding cases changes the fixture's expected outputs, so re-run the mutation check on the prototype and record it.
Recommendation: add a Rules row "wave is 1 + the max wave of the after set" with mutant `1 + #after`, killed by a chain fixture: a raft with f0110, then f0120 depending on f0110, then f0130 depending on f0120, expected waves 1, 2 and 3. Add a row for whole-component overlap (a fixture pair `src/a` and `src/ab` stays in wave 1, killing the string-prefix mutant), and one for reason precedence (an issue that both depends on and overlaps another prints `(depends_on)`). Run all three on the prototype and mark them `run`.
