### F1 [high] An unjailable run goes on unjailed whenever any `GIT_CEILING_DIRECTORIES` entry is an ancestor of the checkout, so AC1/AC10's refusal is passed by an implementation that doesn't refuse
Where: `tests/lib/fence.luau:311-318` (`fixtureOfGuarded`) and `:341-344`; c0058 Design, "The jail", "When the jail can't apply", second bullet ("this checkout lies under an outer guard's `.cache` … whose own jail protects the real repository"); testing skill, Jail bullet ("unless it proves it can't write the repository … or it is a fixture of a guarded checkout"); AC1, AC10; fence.spec `a run that can't be jailed …` (line 567)
Evidence: `fixtureOfGuarded` returns true when `here` lies under any entry of the inherited ceiling. The entry need not end in `/.cache`, and nothing checks that the guard which set it was jailed. In a scratch clone `c` with a probe spec that writes `<c>/WROTE-ROOT`:
- `sandbox-exec -p '(version 1)(allow default)' lune run tests/run -- tests/probe/w.spec.luau` refused with `cannot jail this run …`. This is correct.
- The same command with `env GIT_CEILING_DIRECTORIES=/private/tmp`, an ancestor, printed `note: not jailed …; this is a fixture of a guarded checkout`. The output then showed `wrote root: true jail: outer sandbox (a fixture of a guarded checkout)` and `1 passed`, and `WROTE-ROOT` existed afterwards. Setting the ceiling to `$HOME` or `/Users` is a common speed-up for shell prompts, and it does the same thing.
- I also ran `bash -c 'source scripts/lib/ac.sh; cd .cache/cp && lune run tests/run -- …'` inside the same permissive sandbox, with a copy of the tree in `.cache/cp`. This is c0058's own AC9 pattern and c0049's AC5. It printed the same note, and the probe wrote `<c>/WROTE-REAL` in the real checkout. The ceiling entry `<c>/.cache` came from a **checks-mode** guard (`ac.sh`), and `check.sh` files are never jailed. So the design's reason, "whose own jail protects the real repository", is false here.

In both cases the result is a Mac run inside a permissive sandbox, which is the situation review-004 F1 was about (for example, a sandboxed agent shell). It is reported as protected, and the only protection it has is the Linux level. The prototype still passes the K2 case, because that case clears the ceiling (`GIT_CEILING_DIRECTORIES = ""`). That makes the case a test of "no exception at all", not of a wrong exception. Clearing the ceiling also contradicts the spec's own header ("clear only the marker, so the outer guards stay").
Critique: the requirement is that no check can break the repository, and this exception is listed under "Enforced at run time". The tempting fix is to require the entry to end in `/.cache`. That still accepts the `ac.sh` case, because an unjailed `check.sh` sets exactly such an entry. A second tempting fix is to trust an inherited `PICKMAN_TEST_JAIL=sandbox-exec`. That is a label, which is what review-003 F2 objected to.
Consequences: the exception has to be proven by probing, the same way the "outer sandbox protects the repository" branch already is. What has to be proven is that the repositories the outer guard protects can't be written. The current checkout, a fixture, may be writable. The c0058 specs' inner runs must still go on. They do: the outer jail denies the root and its `.git`, which are inherited in `PICKMAN_FENCE_REAL_GIT`. A `check.sh` copy run (AC9, c0049 AC5) inside a permissive sandbox now refuses. That matches "run specs with that sandbox off", but AC9 then fails in a sandboxed shell, with the refusal message instead of a probe failure.
Recommendation:
- Replace `fixtureOfGuarded` with a rule that the run may go on unjailed only if all of these hold:
  - at least one inherited `PICKMAN_FENCE_REAL_GIT` entry exists;
  - every probe of an inherited entry and of its checkout (the entry without `/.git`) was **denied**;
  - every writable path is this run's own checkout or its git dir;
  - this checkout lies under a ceiling entry that ends in `/.cache`.

  Otherwise it refuses as it does today. Change c0058's "When the jail can't apply" bullet, the testing skill's Jail bullet and R0021 Risks to say this: "a fixture inside a jailed run: every repository the outer guard protects is proven unwritable".
- fence.spec `a run that can't be jailed …`: keep the inherited ceiling and pass `PICKMAN_FENCE_REAL_GIT = ""` instead (c0058's specs are exempt from the scan). It must refuse. The current prototype goes on in this case, so the case kills the mutant. Add a second inner run with `GIT_CEILING_DIRECTORIES = <inherited>:<base>`, an ancestor that isn't `.cache`, and `PICKMAN_FENCE_REAL_GIT = ""`. It must refuse too.
- AC10 (`outer`): also run AC9's `chain` copy inside the permissive outer sandbox. It must exit 1 with `cannot jail this run`, and `$real/.pickman-chain-probe` must not exist. Also run a plain run under that sandbox with `GIT_CEILING_DIRECTORIES="$(dirname "$PWD")"`. It must refuse.
- Rules and mutants: K4 "any ceiling ancestor counts as an outer guard" and K5 "an unjailed (checks-mode) outer guard is accepted", both `run`, killed by the cases above.

### F2 [low] Small gaps in the c0058 specs and checks
Where and fix:
- **The ac.sh blocks in fence.spec skip the fixture check.** Lines 329-341, 498-509 and 582-588 run `bash -c 'source "$1"; … git branch ac-escaped …'` with no `cwd`. If `$1` is missing, `source` fails and bash goes on: in a non-interactive shell outside POSIX mode a failed `source` doesn't exit. The `git branch`, `git fetch … refs/remotes/self/…` and `update-ref -d` lines then run in the spec's cwd, which is the real checkout. With the guards in place, the jail and the ref guard stop them. On an unguarded runner outside `$TMPDIR` they don't. These blocks are also the only git calls in the spec that don't go through `fixture()`, against the rule the spec's own header states. Fix: start each block with `source "$1" || exit 3; [ "$(git rev-parse --show-toplevel)" = "$(pwd -P)" ] && [ "$(pwd -P)" = "<physical repo>" ] || exit 3`, and pass `{ cwd = repo }`.
- **c0058's own checks in a sandboxed shell.** Started from inside another sandbox, AC10's nested `sandbox-exec` exits 71 (`sandbox_apply: Operation not permitted`). After F1 is fixed, AC9 fails with `cannot jail`. Both messages are correct but indirect. Optionally, the check.sh can test once for `sandbox-exec -p '(version 1)(allow default)' /usr/bin/true` and fail AC9/AC10 with "run this check outside your sandbox (testing skill)".
