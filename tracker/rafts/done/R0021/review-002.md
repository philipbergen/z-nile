### F2 [high] The jail's network deny also blocks loopback, which breaks five promoted specs that talk to a local fake server

### F3 [high] The jail still lets specs write everywhere outside the repository, including programs that later run unjailed, the runner included
Where: `tests/lib/fence.luau` `profile` (`(allow default)`, then denies only on the protected paths, the git configuration and their ancestors); testing skill, "Caught only by review".
Evidence: the profile for this worktree (printed through `fence.profile`) denies writes only to the checkout, `.git`, the main checkout, `~/.gitconfig`, `~/.config/git` and the literal ancestors. Everything else in `$HOME` is writable from a spec, including `~/.rokit/bin/lune`, `stylua`, `selene` and `rojo` (user-owned, mode 755; `lune` is the top-level runner that makes the jail decision and runs the tripwire), `~/.zshenv`, `~/.zprofile` and `~/.zshrc` (sourced by every agent shell command and terminal), `~/.claude/settings.json` (Claude Code hooks run unjailed on the next tool call) and `~/Library/LaunchAgents` (run at next login, no `launchctl` needed). A spec that writes a two-line `~/.rokit/bin/stylua` (`git -C ~/code/pickman push --force …`; exec the real one) has it run, unjailed and with the keychain, by the next gate's format stage or the PostToolUse hook after any `.luau` edit. Rewriting `lune` disables the jail for every later run. I did not plant anything; this is read from the profile and the file modes. The review-only bullet "Handing work to a process outside the jail: `open`, `osascript`, `launchctl`, or a daemon" names contacting a process, not planting a file that one runs later, and the scan names none of these paths.
Critique: the jail protects the repository's files but not the code that later acts on the repository with the person's authority, so "nothing a spec does can change the repository" doesn't hold. A blocklist (deny `~/.rokit`, the rc files, `~/.claude`, `~/Library/LaunchAgents`, `~/.local/bin`, user-owned `/opt/homebrew`) will always miss the next one.
Consequences: an allowlist (`(deny file-write* (subpath "/"))`, then allow this checkout's `.cache`, the resolved `$TMPDIR`, `/dev/null`, `/dev/tty`, `/dev/fd` and `/private/var/folders/<user>` for the system temp) breaks whatever specs or their tools write elsewhere today (lune or rojo caches, `~/Library/Caches`, `gh`). That has to be measured: one full spec run under the allowlist profile with `(debug deny)` or the sandbox log. The browser guard's `mktemp` and every fixture are already in `$TMPDIR` or `.cache`. The ancestor rules then become redundant but harmless.
Recommendation: switch the jail to a write allowlist (this checkout's `.cache` and `$TMPDIR`, plus measured entries, each with its reason in a comment). Add to the jail case a live probe that a new file `$HOME/.pickman-jail-probe-<tag>` can't be created (removed at once if it could), and state in the testing skill's Jail bullet that specs write only in `.cache` and `$TMPDIR`. If this is judged beyond c0058's scope, the author must escalate (execute-raft stop conditions) rather than leave it unnamed. The alternative the person could choose is a review-only bullet: "writing a file outside the repository that an unjailed process later runs: tool binaries, shell startup files, agent settings, launch agents".

### F4 [high] A run accepted as "outer sandbox" proves only that the protected paths are unwritable, not the network or ancestor denies the round-1 fixes rely on, and the gate doesn't probe them in that mode
Where: `tests/lib/fence.luau` `jail()` (the `#open == 0` branch and `writable`); `tests/tooling/repo-fence.spec.luau` jail case (network probe only `if jail == "sandbox-exec"`; ancestors checked by reading `fence.profile`, which no outer sandbox uses).
Evidence: when `sandbox-exec` can't start (inside another sandbox), `jail()` accepts the run if `writable(here)` is empty, that is, if direct probe files in the checkout, `.git` and the main checkout can't be created. It never tests outbound IP or an ancestor. Agent sandboxes commonly deny writes but allow network to an allowlist that includes github.com, and allow keychain lookups. In such a run, a spec's `-c protocol.allow=always` (or `GIT_ALLOW_PROTOCOL`, F5) plus a credential helper rebuilt by concatenation (the scan matches only literal text) reaches the real remote. That is review-001 F1 again, and the outer sandbox may also allow the F2 rename. The gate's jail case passes in this mode because it skips the network probe and only reads the profile string. A live ancestor probe exists and is harmless: `touch -c -r <dir> <dir>` sets a directory's times to their own values. In `$TMPDIR` under `(deny file-write* (literal "<dir>"))` it fails with `Operation not permitted`; unsandboxed it succeeds, and the mtime is unchanged (checked with `stat`). refute-001's reason for reading the profile ("a live rename probe would move the checkout") doesn't apply to this probe. `chmod` to the same mode is no probe: it returned 0 under the deny.
Critique: the round-1 fixes hold only in the `sandbox-exec` mode, and the mode that exists for agent shells, where the incidents happened, keeps the old holes.
Consequences: requiring both probes in `jail()` makes some outer sandboxes refuse runs they accept today; the skill already says to run specs with the sandbox off, so that is the intended result. The TEST-NET probe costs up to its timeout (about 2 s) only on that path. A fixture of a guarded run inherits the outer jail's denies, so it passes the same probes.
Recommendation: in `jail()`, accept "outer sandbox" or "fixture of a guarded checkout" only when, in addition to today's checks, an outbound connect to 192.0.2.1 is refused with `Operation not permitted` and every ancestor of every protected path refuses `touch -c -r a a`; otherwise refuse with a message naming which guarantee is missing. In the jail case, run the network probe (and, after F2, the loopback probe) and the `touch` probe on the checkout's ancestors in every macOS mode, instead of reading `fence.profile`. Add a case to the "can't be jailed" set (non-sequestered spec) that runs under an outer `sandbox-exec` profile denying repository writes but not network, and expects a refusal.

### F5 [medium] `GIT_ALLOW_PROTOCOL` undoes the fence's `protocol.allow=never` in one variable; the fence doesn't set or unset it, and the scan doesn't name it
Where: `scripts/lib/fence.sh:53-56`; `tests/tooling/repo-fence.spec.luau` `NAMES`.
Evidence: in `$TMPDIR` with the fence's `GIT_CONFIG_COUNT` entries: `git ls-remote https://example.invalid/x.git` gives `transport 'https' not allowed`, while `GIT_ALLOW_PROTOCOL=https git ls-remote …` gives `Could not resolve host`, so the transport is allowed. An inherited `GIT_ALLOW_PROTOCOL` in the person's environment does the same for every spec. Conversely, `GIT_ALLOW_PROTOCOL=file git -c protocol.allow=always -c protocol.https.allow=always ls-remote https://…` stays `not allowed`: the variable beats every `-c`. On Linux and in F4's outer-sandbox mode this is the only network layer.
Critique: the fence uses the weaker of git's two knobs, and leaves the stronger one open in both directions.
Consequences: setting `GIT_ALLOW_PROTOCOL=file` changes nothing for fixtures (local paths and `file://` already are the only allowed transports). A `check.sh` run from inside a spec run inherits it, as intended ("keeps these limits"). Checks-mode `ci-verify.sh` fetches aren't in specs mode, so they're unaffected.
Recommendation: in specs mode, `export GIT_ALLOW_PROTOCOL=file` (keep the config entries as the second layer). Add `GIT_ALLOW_PROTOCOL` to `NAMES` with a planted case. Add an AC-style assertion in the "specs have no GitHub credentials" case that `git -c protocol.allow=always ls-remote https://192.0.2.1/x.git` fails with `not allowed`.

### F6 [medium] The identity scan is case-sensitive and still misses `--author` (repeat of review-001 F3, in part)
Where: `tests/tooling/repo-fence.spec.luau` `identitiesIn` (patterns `user%.email…` and `EMAIL…`).
Evidence: run in lune on sample text: `git -c User.Email=me@gmail.com commit` gives no identity; `commit --author="Me <me@gmail.com>"` gives none; `git_author_email=me@gmail.com` gives none. `GIT_COMMITTER_EMAIL = "me@gmail.com"` is caught. Git config keys are case-insensitive, which the name scan already honours (`string.lower`), but `identitiesIn` doesn't. refute-001 didn't answer the `--author` half of review-001 F3. A commit written that way isn't recognisable to the tripwire as a fixture write (`fence.luau` tells them by author).
Critique: the tempting fix is lowering the text, which then also catches lowercase `email` in prose. The `@example.invalid` suffix test makes that harmless only for real addresses.
Consequences: lowering the text can flag a documentation string with a real address next to the word "email"; that file then needs an allowlist entry or the address changed. None exist today as far as the gate's corpus shows.
Recommendation: match on the lowered text for `user.email` and `email` variable forms, and add a pattern for `--author[= ]…<addr>`. Plant `User.Email`, `--author=` and a lowercase env form in the identity case.
