### F1 [medium] The fake's extension rule is one-sided, and the PlayerGui case leans on the fake: a "wider" fake lets a GUI that never shows pass all 67 cases
Where: f0061 Files and API, "The fake engine" (an executor who needs a service or a call outside the fake extends it: "the fake must never accept less than it does now"); `tests/lib/fakeengine.luau` header and `fake.client`'s `find`; `lobby-adapters :: the lobby's screen is on the player's PlayerGui ...` (`t.expect(c.find("Lobby").Parent ~= nil)`)
Evidence: change `find` in `fake.client` from `playerGui:GetDescendants()` to `localPlayer:GetDescendants()` (an extension: it accepts more) and change LobbyView to `gui.Parent = Players.LocalPlayer`, which Roblox never renders. All 67 cases of the six acceptance specs pass. The PlayerGui case only checks that the ScreenGui's `Parent` is not nil, so the "on the PlayerGui" property is enforced only by `find`, and that lives in the non-sequestered helper the executor is invited to extend. The stated rule ("never accept less") protects correct adapters from a stricter fake but says nothing about a laxer one, which is the risk an executor's extension carries. The same holds for the other strict points the specs rely on: a missing child raising, `GetService` raising for a service the fake does not model, and attributes coming only from the built place.
Critique: this is round 2's F1 fix, and a one-line change to a Touched file can quietly undo it. Code review has no rubric to catch it beyond "an extension is judged". The tempting fix is to sequester the fake, but that removes the executor's freedom to add a service or a call, which the design rightly keeps.
Consequences: a two-sided rule needs something the code reviewer can re-run. The fake-dependent mutants (wrong remote, folder or attribute name, unparented or misparented screen, white or small backdrop) must be written down exactly, or the reviewer has to rediscover them. An assertion on the parent inside the sequestered spec costs nothing and pins the case whatever `find` does.
Recommendation: in prep, (1) make the PlayerGui case assert the parent itself, e.g. `c.find("Lobby").Parent.ClassName == "PlayerGui"` and `c.find("Start")`'s ancestry reaching it through `Backdrop`, so `find`'s scope no longer carries the property; (2) state the rule both ways in f0061 and in the fake's header: "an extension may accept more correct idioms, never fewer, and must keep failing every mutant the Rules table records as killed; the strict points are a missing child raising, an unmodelled service raising, attributes only from the built lobby and `find` only under the PlayerGui"; (3) list the fake-dependent adapter mutants as exact one-line substitutions in E8 (about eight), and add to the Regression guard that a change to `tests/lib/fakeengine.luau` is reviewed by re-running them. Add the mutant "the screen parented to the player, not the PlayerGui" to the PlayerGui row (`run`).

### F2 [low] Unpinned ways for the client's screen not to show: a see-through backdrop, the top inset, a disabled ScreenGui, a hidden or off-screen button
Where: `lobby-adapters :: the lobby's screen is on the player's PlayerGui ...`; Rules row "The lobby's screen is on the player's PlayerGui: a black backdrop over the whole screen ..."; Decision "a black backdrop covers the screen"
Evidence: each of these LobbyView mutants passes all 67 cases: `backdrop.BackgroundTransparency = 1` (a plausible copy from the `label` helper, which sets it); dropping `gui.IgnoreGuiInset = true` (the top-bar band is not covered, which is the "does not cover the screen" mutant the row claims to kill, reached another way); `gui.Enabled = false`; `button.Visible = false`; `button.Position = UDim2.fromScale(0.5, 1.74)`.
Critique: O1 catches all of them in Studio, so the risk is a wasted round trip, not a shipped defect.
Consequences: the fake keeps properties as plain data, so these are plain assertions on what the view set (`nil` means the Roblox default).
Recommendation: in the same case, expect `gui.IgnoreGuiInset == true`, `gui.Enabled ~= false`, `backdrop.BackgroundTransparency` nil or 0, `button.Visible ~= false`, and the button's `Position` scales within 0..1. Add the five mutants to the row (`run`).

### F3 [low] The specs forbid the standard "tell the players already here" idiom, yet nothing pins the fallback the prototype relies on
Where: `lobby-adapters` helper `server()` ("their status is not announced until it changes", players placed with `here` before `boot`); f0061 `Starts` ("a player is told the state once at first (on joining, or on the first press)"; "Once a second a Heartbeat step reports `Travel.status` for every player")
Evidence: adding the common Roblox idiom `for _, p in Players:GetPlayers() do push(p, "idle") end` after connecting `PlayerAdded` (which covers a player who joined before the server script ran, as in Studio Play Solo) fails 10 cases. The other way round, the mutant that runs the once-a-second step over `shown` instead of `Players:GetPlayers()` passes all 67. With that mutant, a player who joined before boot is never told anything until they press. In an unconfigured lobby they see the client's first draw, a live START GAME, instead of UNAVAILABLE.
Critique: the design leaves the early player to the Heartbeat step, which is fine, but the specs pin the opposite of the idiom an executor or a reviewer is likely to add, and they leave the actual fallback open.
Consequences: accepting both ways means the early players' first status may arrive at boot or within a second, so the cases that hold exact status strings for P1 and P2 must not count it.
Recommendation: either say in `Starts` that players present at boot are told by the first step (not at boot) and add a case "a player already in the lobby at boot hears the state within a second" (boot with `here(P1)`, no attribute, `tick(1)`, expect `idle/false`), killing the "step over `shown`" mutant; or let the helper ignore an initial `idle` (compare from the first non-idle message) so the idiom passes too. The first is the smaller change.

### F4 [low] Three plausible mutants nobody listed survive
Where: `lobby-tooling :: the gate builds the lobby project too`; `lobby :: with rows the panel shows them in rank order ...` and `... at most 10 rows, the best ranks ...`; `lobby-adapters :: a failed call tells the player ...`
Evidence: (a) commenting out the stage, `# par_start "build lobby (rojo)" rojo build lobby.project.json ...`, passes, because the case is a substring search over `scripts/check.sh`. (b) `Lobby.panel` sorting by `score` descending instead of `rank` passes, because every fixture's scores fall as the ranks rise. (c) a 2 s throttle on the status step (`now - last >= 2`) passes. A 3 s one is killed.
Critique: each is small: the full gate still builds the lobby through `place.load`, boards rank by score, and a 2 s step delays the end of the cool-down by at most a second. They are still rules the design states (the gate builds both; rank order; once a second) with no case that holds them.
Consequences: none.
Recommendation: (a) match the line with a pattern anchored at the line start (`\npar_start [^\n]*rojo build lobby%.project%.json`). (b) Give one fixture two rows whose rank order differs from their score order (e.g. equal scores, ranks 2 and 1). (c) Add a tick sequence that tells 1 s from 2 s (a failure at t = 0, then `tick(1)` three times: `idle/true` is shown by the third tick; with a 2 s step it is not). List the three as mutants (`run`).
