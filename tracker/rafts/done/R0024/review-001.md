### F1 [medium] The fake engine swallows errors raised in any coroutine it resumes later, so it accepts adapters that crash
Where: `tests/lib/fakeengine.luau:297-310` (`task.spawn`, `task.defer`), `:342-355` (`tick` resuming `task.delay` timers and `task.wait` waiters)
Evidence: each of these calls `coroutine.resume(...)` and drops the result. Probe (scratch spec under `.cache`, removed): `Starts.luau` with `task.spawn(function() error("boom") end)` inserted at the top of the `StartGame` handler, booted through `fake.server(place.load("lobby.project.json"), { GamePlaceId = 123 })`, join, press: the spec passes (`1 passed, 0 failed`). The same holds for a handler that does `task.wait(1)` and then errors (the waiter is resumed by `tick`, result ignored), and for a `task.delay` callback. Only signal handlers that fail before their first yield, and `release`, re-raise.
Critique: the fake's header and f0061's Files and API make it a contract that is "exact in both directions": it must not accept more than the real engine lets work, and `task.*` is explicitly one of the idioms an adapter may use (it is one of the four correct variants). As written, an adapter that moves its body into `task.spawn` or a `task.wait` loop can raise on any line after the first yield and AC5 only notices if some later assertion happens to depend on that line. Every future adapter tested with this fake (f0065's return trip reuses it) inherits the blind spot. The tempting fix is `error(err)` straight inside `task.spawn`; that changes semantics the other way: in Roblox an error in a spawned thread is logged and never unwinds the caller, so the handler that spawned it would now abort, and a correct adapter whose spawned thread is the last thing it does would still behave differently from the engine.
Consequences: errors must be surfaced without unwinding the caller. That brings one new piece of state (a list of errors from resumed coroutines) and one rule: which spec-facing call reports them. If only `tick` reports, an error raised during `press` surfaces one call late and names the wrong step; if every entry point reports, `boot`, `press`, `join`, `leave`, `initFailed`, `release`, `tick`, `status` and `activate` must all drain the list after doing their work. The client side has no `task` today, so it needs nothing until it gains one.
Recommendation: wrap every resume the fake performs (`task.spawn`, `task.defer`, timers and waiters in `tick`, and the signal resume in `fire`) in one helper that records `debug.traceback`-style errors into a per-server list, and have every spec-facing entry point raise the first recorded error after its own work completes (`fake engine: an adapter thread failed: <err>`). Prove it on the scratch mutants above (an error in `task.spawn`, after `task.wait`, in a `task.delay` callback: each must now fail the spec), re-run the four correct variants (must pass) and the Rules-table mutants that depend on the fake as exact substitutions (must still fail), and run f0061's `check.sh`. `tests/lib/fakeengine.luau` is not sequestered and is in f0061's Touched modules, so this is in scope; record the change in the Verification log.

### F2 [low] The client shows a live START GAME before the server has said anything, also in a lobby with no destination
Where: `src/lobby/client/LobbyView.luau:71` (`show("idle", true)`)
Evidence: the screen is drawn with `configured = true` before the first `Status` arrives. In an unconfigured lobby (the checked-in state, `GamePlaceId = 0`) the first frames show a yellow, live START GAME; the correct UNAVAILABLE appears only when the queued `PlayerAdded` status is delivered, or up to a second later through the Heartbeat step when the server script started after the player (the case `a player already in the lobby when the server starts` pins). A press in that window is harmless (the server answers with nothing new: `shown` is already `idle`), but the player sees a button that then switches off by itself.
Critique: the client is meant to decide nothing; assuming `configured = true` is a guess. Flipping the guess to `show("idle", false)` just moves the flash to the configured lobby (UNAVAILABLE, then START GAME).
Consequences: a neutral first state needs a view model for "not told yet", which `Lobby.button` does not have, and `Lobby` is Logic with a sequestered spec on its button table; adding a phase would widen `Travel.Phase`.
Recommendation: hiding the button until the first status is not available: `lobby-adapters :: the lobby's screen is on the player's PlayerGui ...` boots the client and asserts every item `Visible` with no status sent. Keep `Lobby` as it is and draw the first state as not live (`Active = false`, `AutoButtonColor = false`, the grey colour, empty message) until the first `Status` event, then draw from `Lobby.button` as now. Confirm with f0061's `check.sh` that no sequestered case pins the pre-status text or colour; if one does, leave the code and note the brief flash in O1 instead.
