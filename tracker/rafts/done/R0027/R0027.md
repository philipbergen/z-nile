# R0027: Compact ids

## Theme
Both issues are about the soundness of the tracker's id space, and each needs the other: compaction (c0081) must refuse a malformed tree and prove the result sound, which is c0082's audit; c0082's audit checks c0081's counter file. Both change `scripts/tracker/main.luau`'s allocation and `renumber`, and the tracker skill's Items section. All chores (tooling).

Decisions this raft relies on (the user, 2026-10-04, in c0081's Problem and in prep):
- "a command that renumbers every item, starting from 0001 … Every reference is rewritten, as `renumber` does today."
- "Count by one, not by ten."
- "a single-line file in the tracker with two entries, `<next number> <random word>`", made in prep **one file, two lines**: f, d and c keep sharing one number space, rafts keep their own.
- "Allocation: push N+1 with a new random word to main. If that push collides … revert your change, pull the new main, and repeat."
- In prep: c0082 joins this raft; compaction **refuses unless the tracker is quiet** (`--force` overrides), and in-flight branches catch up with `tracker.sh remap`.
- The user, after design review 003: "Strict count by one … this compaction is a one-off and we're going to start from 1 and count up"; and `tracker.sh sync` stays as it is: "the IDs will be remapped completely this one time. Commit messages are no problem. Clean slate." So no numbers are skipped after the compaction, and nothing detects a plain merge of `origin/main` into a busy branch that skipped `remap` (the skill rule says to remap first).
- The user, after design review 004: the order is **R0027, then the one-off compaction, then c0083** (split harness and game suites), which plans to move chores' promoted specs out of `tests/acceptance/`; c0083 then moves folders that already carry their final ids.

- Prep decision: ids are rewritten only inside `tracker/` (`.md` and `.sh`, as `renumber` does); paths to promoted spec folders are rewritten repo-wide; code comments, skill examples and fixture literals keep old ids, mapped by `tracker/compaction.txt`.

## Risks & rollback
- **The compaction itself is not run here.** After this raft merges, the user runs it once: land or park every open prep and raft branch (today R0011, R0012, R0018, R0024, R0025, R0026 and the prep worktrees), then in a fresh worktree `tracker.sh compact`, `scripts/check.sh --full`, PR, merge. Merge only while `origin/main` still equals the sha in `tracker/compaction.txt`'s header: if anything landed meanwhile (a new item conflicts on `tracker/next`; a code or spec PR merges silently in the old scheme), reset to `origin/main` and run it again (it is deterministic and cheap). A branch that must stay open uses `--force` on the compaction and `tracker.sh remap` on the branch **before** it merges `origin/main` (a plain merge, including GitHub's "Update branch", is not detected: the user accepted this for a one-off compaction).
- **Old ids outside `tracker/` become ambiguous** after compaction (a comment `-- See c0006` may mean the old or the new c0006). `tracker/compaction.txt` and the compaction commit's date resolve them; this is inherent in renumbering from 0001.
- **Terminals running the old tracker** after this merges publish multiple-of-10 stubs without raising the counter. Harmless: allocation passes any used number, and the audit warns (`next-behind`). Before compacting, remove or sync every worktree cut before R0027 merged: old code has no stale-tree check.
- **The gate after compaction**: c0081 step 8 runs a trial compaction and its full gate before `done`, but a spec landing later may pin a real id. If the compaction PR's `check.sh --full` fails: discard the compaction branch, fix the spec on `main` first (a chore, using `tests/lib/renamed.luau`), then compact again (deterministic, so cheap).
- **A second compaction** overwrites `tracker/compaction.txt` with a map from the first compaction's ids; `renamed.id` literals written for the first one then need updating. Not expected: the space holds 9,999 issues counting by one.
- **A lost counter file**: the gate fails (`next-missing`), so it cannot land unnoticed.
- **R0025 (ready, stop, land) publishes too.** If it lands first, this raft routes its new `publish.commit` calls through `publishFresh` (`publish-guard.spec` fails until it does). If it lands after, its own gate fails on the promoted `publish-guard.spec` until its executor does the same: one-line changes, no spec edits.
- **R0025's c0072 rewrites the same skill line** (the direct-push exception bullet). Whichever raft lands second merges the two texts so that both rafts' skill specs still pass (this raft's needs `tracker/next` and "only go up" on that line).
- **Rollback**: revert the PR; the counter file then sits unused (the old code ignores it), and the ten narrowed specs still pass without it.
