### F1 [high] Nothing checks that the radar moves when the screen size changes: placing it only once, or only when both sides change, passes AC3 (follows from review-002 F1's fix)
Where: tracker/issues/d0105/acceptance/adapter.spec.luau, case "places the radar from the screen size before the snapshot guard"; d0105.md, the decision "Recompute only when `AbsoluteSize` changes", Scalability, E3, and the Rules row "One `radarBox` per size change is a preference"; AC3 ("places the radar from Hud.radarBox of the current screen").
Evidence: I ran these mutants on the prototype's `DangerHud`. Each one reports `4 passed, 0 failed` for `adapter.spec`:
- M1: `if view.X ~= placedX and view.Y ~= placedY then`. A resize that changes only the width, like dragging the side of the desktop window, leaves the radar at the old `x`. When the window narrows, the radar ends up partly or fully off the right edge.
- M2: `if placedX < 0 then`. The radar is placed on the first frame and never again. Any resize, or a phone rotating, leaves the radar off its corner, either off-screen or floating mid-screen.
- M3: `local placedX, placedY = gui.AbsoluteSize.X, gui.AbsoluteSize.Y`. If the ScreenGui already has its size when `start` runs, the first frame sees no change, and the radar stays at its default `Position` (0, 0). That is top-left, over the score, until the window is resized.
Round 2 treated the size `if` as only a cost question, and the refutation accepted that: "the cache is no longer a checked acceptance property". But the `if` also decides when the radar is moved. The design states both halves ("the first frame always places it", "when `gui.AbsoluteSize` differs from the last placed size"). Only the cost half has a Rules row, and that row says no spec checks it. The rule "the radar follows the current screen" has no row and no spec. AC3 claims it anyway.
Critique: this is the third round in a row where a string match on `DangerHud`'s source misses a run-time rule, and each time the hole sits in this cache. The tempting fix is to put back an exact-string assertion for `if view.X ~= placedX or view.Y ~= placedY then` and `local placedX, placedY = -1, -1`. That kills M1–M3 but pins a spelling. It also still misses the lost-write mutant from round 2, and a fake-engine run is ruled out (review-002).
Consequences: the cache is what makes the placement conditional, and a source-shape spec cannot check a condition. Removing the cache removes all four mutants, the "first frame" rule and the cost-only Rules row. The price is one `Hud.layout` call (a 5-field and a 4-field table) and one `Position` write per frame. The step already builds a `ghosts` table, an `Awareness.radar` result and an `indicators` list every frame after the guard, so this cost is the same order and is not a scalability trap. The Scalability section and the decision must then say "placed every frame" rather than describe a cache. An unconditional placement can be checked by shape, without pinning a spelling: there is no `if` between `RenderStepped:Connect` and the `Hud.radarBox(` call. A later refactor that adds a condition there (any cache, any guard) fails that check. That refactor would need a new decision anyway.
Recommendation: drop the cache. The step begins `local view = gui.AbsoluteSize`, then calls `Hud.radarBox(view.X, view.Y, radarSize)` and sets `radar.Position` on every frame, before the snapshot guard. Remove `placedX, placedY` from the patch. In `adapter.spec`'s placement case, add an assertion that the source between `RenderStepped:Connect` and the call has no `if` keyword. Use a frontier pattern such as `%f[%w]if%f[%W]` on the comment-stripped source, so that names like `ifX` don't match. Rename the case to "places the radar from the current screen size on every render step, before the snapshot guard". Update the documents to match:
- Replace the decision "Recompute only when `AbsoluteSize` changes" with "Place every frame". Give the reason: a conditional placement can't be checked offline, and the cost is one `layout` per frame, like the step's other per-frame tables.
- Rewrite the Scalability section the same way.
- In the Rules table, replace the cache row with "The radar is placed on every render step, with no condition" (mutants M1, M2, M3 and "the placement inside any `if`", `run`).
- Re-run the mutants and record them in E3, including the existing ones (after the guard, the hardcoded 1920×1080 call, the anchor).
- AC3's text can stay as it is. It then becomes true.
