### F1 [high] "A missing stamp is not prepared" contradicts the tracker's own status rule, so the board hides a raft that `tracker.sh ready` accepts
Where: R0038.md Whole-raft design, the raft bucket table and "A missing stamp is not `prepared`"; c0107.md Design `stampWord`; views.spec R9006 and the case "sets the raft command…"; c0107 Regression guard (the `prepared-test-test-test` stamps added to the c0042 fixtures).
Evidence: `scripts/tracker/status.luau:88-111`: `status.effective(front, state)` is `status.parse(front.status) or status.derive(state, design, inRaft)`, and `derive` returns `"prepared"` for a backlog item with `design == "ready"`. The tracker skill says the same in its Statuses line: "A missing `status:` is derived: … `design: ready` is prepared". `main.luau` `ready` (around line 2695) uses exactly `statusLib.effective(...)` and accepts `raft.state == "backlog" and st == "prepared"`. So a backlog raft with `design: ready` and no `status:` line is prepared to the tracker, and `/ready-raft` works on it. The board puts it in Not ready with no copy button, and views.spec pins that wrong result (`R9006`, `design: ready`, no stamp, expected in `not` with `command == nil`). The promoted c0042 fixtures (R0030 and others) were written with the tracker's meaning, a ready raft with no stamp. The design has to stamp them only because it redefines "prepared".
Critique: the board makes its own copy of a rule that `status.luau` already owns, with different results. c0107's Solution says "status `prepared`", and the tracker defines that status. The tempting fix is to extend `stampWord` with "or no stamp", which is still a second copy that drifts next time `status.luau` changes (for example two-word stamps: `status.parse` rejects `prepared-a-b`, `stampWord` accepts it).
Consequences: requiring `./status` from `board.luau` adds no new edge in practice (`store.luau` already requires it, and `tracker/architecture.md` doesn't cover `scripts/`). R9006 flips to Ready with `/ready-raft R9006`. The c0042 fixture stamp edits become unnecessary. A legacy-`start` raft (backlog, effective `active`) falls under "anything else" and lands in Not ready with no command. That has to be a stated decision, not an accident.
Recommendation: a backlog raft is Ready when `design == "ready"` and `status.effective(front, "backlog") == "prepared"`. The issue text needs both conditions, so keep the `design` check. Drop `stampWord`. Spec cases: R9006 (no stamp) is Ready with `/ready-raft R9006`. Add a raft with a plain `status: prepared` and `design: ready`, expected Ready. Keep `reviewed` plus a prepared stamp as Not ready. Add a backlog raft with `status: active-a-b-c` and say in the Design which bucket it goes in. Update the rules table rows "design ready with no stamp" and "design ready plus a preparing stamp" to match, and remove the `prepared-test-test-test` instruction from Regression guard and Implementation step 4.

### F3 [high] Copy feedback is lost in a real browser, and the harness can't notice
Where: R0038.md "The page" (copy button and handler); c0107.md Design (copy control); page.spec HARNESS (`button()`, `writeText`) and rules rows "a click on the icon's child…" and "a rejected writeText…".
Evidence: the copy button sits inside `<li class="row" data-id=…>`. The existing list handler (`board.html:195-198`) runs `e.target.closest("li.row")` and `select(...)`, which calls `renderList()` and replaces `list.innerHTML`. In a browser a click on the copy svg reaches that handler too, and `writeText` resolves on a later microtask. So `copied` and `aria-label="Copied"` land on a detached button and the user sees nothing. The harness can't see the problem for two reasons. Its `child.closest` answers only `"button.copy"` (`closest("li.row")` is `null`), so the row never re-renders. Its thenable calls `ok()` synchronously. The design names no CSS for `.copied`, so even without the re-render the only feedback is an aria-label nobody sees. Clipboard access from a `file://` page (Chrome, Safari, Firefox) is also an unproven assumption with no experiment and no fallback. If `navigator.clipboard` is undefined (an insecure context), the call throws synchronously, which neither the design nor a spec covers.
Critique: the AC "marks the button copied" can be met by an implementation that never shows a mark. The tempting fix is `stopPropagation` in a separate handler, but here both branches live in one list handler, so the order inside that handler is what matters.
Consequences: if the copy branch returns early, a copy click no longer selects its row. That is a decision to state, and keyboard Enter or Space on a focused copy button behaves the same way. Any later re-render (an arrow key, a view switch) still clears `copied`. Accept that, or re-apply it by `data-id`. With an asynchronous harness the "no `Promise.resolve` wrapper" constraint can go.
Recommendation: specify that a click whose target is inside `button.copy` handles only the copy and returns before row selection. Specify `if (!navigator.clipboard) return` (no throw). Pin a `.copy.copied` CSS rule. In the harness, give the child a `closest` that answers `li.row` with a row element (with `data-id`) as well as `button.copy`. Make the success thenable asynchronous (`queueMicrotask(ok)`) and read the results after an awaited tick. Assert that `list.innerHTML` and the selected row are unchanged by the copy click, and that `copied` is set afterwards. Add a run with `navigator.clipboard` undefined that asserts no throw. Add each as a rules row with its mutant (selecting the row before copying, an unguarded clipboard).

### F4 [high] The issue pane is unspecified, so a loose issue's document and the rafts it blocks can disappear from the board without any spec failing
Where: R0038.md "The page" ("An issue pane's `<h2>` is the issue…"); c0107.md Design (issue pane); keep.spec "a raft pane still says what it waits for, and search opens the issue"; c0042 smoke walk in Regression guard.
Evidence: today a loose issue is reached through the No raft pane. That pane renders each issue's document in a `<details>` (`board.html:137-142`) and lists who it blocks under "Dependents" (`board.html:135`, filled from `noRaftDependents`). An issue pane that renders `<h2>` plus a jump and nothing else (no document, no Depends on, no Dependents) passes AC1 to AC4. AC1's "keeps a loose issue's dependents" is model-only, so nothing guards what the user can actually see.
Critique: this is a regression the design creates by moving issues out of the raft panes. The tempting fix is "render the body". Dependents and Depends on would still be unspecified.
Consequences: the issue pane needs a fixed section order. Depends on may name ids that don't exist, which the hostile case already covers for links (`depends_on: [constructor]` in `tests/tooling/board.spec.luau`). That case moves from the raft pane to the issue pane, so the tooling update in step 4 must keep its "no `undefined`" assertion meaningful there.
Recommendation: specify the issue pane: `<h2>` (id, title, badge), meta (label, design), the raft jump when set, then "Waiting for"-style groups "Depends on" (`dependsOn`) and "Dependents" (`dependents`, raft ids), then "Document" (marked body). In keep.spec give `f9100` a unique body sentence and assert it appears after the search, together with "Depends on" and `c9102`. Open `#c9102` and assert "Dependents" and `R9100`. Add both as rules rows.
