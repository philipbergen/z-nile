### F1 [low] The fake clipboard's `then` returns `undefined`, so a correct `.then(onCopied).catch(...)` handler crashes the harness
Where: page.spec HARNESS, `navigator.clipboard.writeText` (`return { then: ok => queueMicrotask(ok) }` and the `bad` branch); R0038.md "The page" and E2 (the two accepted call shapes).
Evidence: `writeText(c).then(onCopied).catch(() => {})` is the most common way to write this in a browser, where `writeText` returns a real Promise. Against the fake, `.then(onCopied)` returns `undefined`, so `.catch` throws `TypeError: Cannot read properties of undefined` synchronously in the click handler. In the success phase that dispatch is not inside a `try`, so node exits and the case fails with no defect in the page. The design avoids this only by naming exactly two accepted shapes, `.then(onCopied, onFailed)` and `await` inside a rejection handler. That is the same mechanism review-002 F4 questioned: the harness's fake decides how the page must be written.
Critique: an executor who follows the documents is safe, so this is low. A later maintainer who rewrites the handler idiomatically gets a red spec, and the tempting response is to add a third accepted shape to the prose.
Consequences: if the fake returns real Promises, the prose list of shapes can go. The killed mutant stays killed: a rejected Promise with no handler is an unhandled rejection, and node 15+ exits non-zero on that by default, so "leave the rejection unhandled" still fails the run.
Recommendation: question the mechanism instead of listing shapes. Have the fake return `new Promise(r => queueMicrotask(r))` on success and `Promise.reject(new Error("denied"))` on failure, keep the `setTimeout` reads, and replace the two named shapes in R0038.md and c0107 with "any handling that leaves no unhandled rejection". Re-run the "leave the rejection unhandled" mutant once against the new fake to confirm that it still fails.

Verdict: approve
