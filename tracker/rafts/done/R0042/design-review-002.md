### F1 [high] c0115: AC5 ("copies stay equal") fails for every correct implementation, because the name swap is a Lua pattern and `-` is a quantifier
Where: `tracker/issues/c0115/acceptance/names.spec.luau:93-96`; AC5
Evidence: `bodyAfterName` runs `string.gsub(s, "name: " .. name, "name: SAME", 1)`. In a Lua pattern `z-ticket` means "zero or more `z`, then `ticket`", so the pattern never matches the literal `name: z-ticket`. I ran the call on `---\nname: <n>\n---\n`: it replaces nothing for `z-ticket`, `make-issue`, `zz-review` and `zz-arch`, and replaces only for `review`. Every pair except `zz-review`/`review` has a hyphen on both sides, and that pair has one on the new side. So the two `name:` lines are never normalised. A correct copy, whose `name:` must equal its directory (AC1/AC2), always differs from its source in that line. All seven comparisons fail, so AC5 and AC1/AC2 cannot both pass.
Critique: The spec is sequestered, so the executor cannot fix it and must stop. The tempting fix is to escape the hyphen (`%-`).
Consequences: Escaping fixes this one call, but the spec still treats the first `name: X` anywhere in the file as the frontmatter line. A skill body that quotes `name: review` (the review skill's own text could) would be rewritten instead.
Recommendation: Compare with a plain-text frontmatter rewrite: split off the frontmatter block (`^%-%-%-\n(.-)\n%-%-%-\n`), drop its `name:` line, and compare the rest of the block and the body byte for byte. Mutation-run the case in prep: a correct copy must pass, and a copy with one changed body byte must fail (see F9).

### F2 [high] c0117: AC7 contradicts the design, because the repo root always joins `strongest`, so a closer file can never lower a cap
Where: c0117 Design ("For an issue, the directories are the repo root and each directory that contains a path listed under Touched modules... then `strongest`"); `models.spec.luau` "dry run and model flag" (lines 183-200); Problem ("give one directory a cheaper cap")
Evidence: The fixture has a root `.models.toml` with `[z-run] rank = 2, max_tokens = 300000` and `game/.models.toml` with `max_tokens = 1000`, and the issue touches `game/x.luau`. By the design, `resolve(root)` gives `rank 2 / 300000` and `resolve(game)` gives `rank 2 / 1000`. `strongest` of equal ranks picks the larger cap, 300000. The spec expects `max_tokens=1000`, and `max_tokens=300000` does not contain that substring. A correct implementation fails AC7, and an implementation that passes it has to break the written rule. More generally, any stacked file that only lowers a cap or a rank is always beaten by the root's own spec. The issue's stated Problem (one directory gets a cheaper cap) can never happen. This is the second round in a row with a hole in the directory-to-spec rule (review-001 F11).
Critique: The tempting fix is to drop the root from the list "when a closer directory exists".
Consequences: Then an issue that touches `game/x.luau` and `scripts/y.luau` resolves `game` (stacked on root) and `scripts` (root only, since it has no file). `strongest` still picks root's spec through `scripts`, so the cheap cap applies only when every touched path is under the cheap directory. That may be the intended policy ("the more powerful spec wins"), but nobody has decided it, and a monorepo's root-level tooling paths would always win.
Recommendation: Decide the policy in the design, not in the spec. If the rule is "stronger wins", say plainly that a closer file can only raise a spec for mixed work, and resolve only the directories of Touched paths (each stacked from the root down), never the bare root. Fix AC7's expectation to whatever the rule gives, and add cases for: one touched path under `game/` gives 1000; a second touched path outside `game/` gives 300000. If the rule is "closest wins", replace `strongest` for the mixed case and say so. Either way, run the case against a prototype in prep (F9).

### F4 [high] c0116: `new raft` over prepared issues publishes no claim on them, so two sessions can raft the same issue, and it puts an unreviewed `design: ready` raft straight onto main
Where: c0116 Design ("Member status lines are left as they were. When every member is `design: ready`, the raft document is published with `design: ready` and a status that starts with `prepared-`"); `main.luau:805-823` (`new raft` claim loop); tracker skill lines 156-158 and 61
Evidence:
- Today's double-claim guard for `new raft` is the member's status. It is re-stamped `preparing-<stamp>`, so a second `new raft` sees `preparing`, not `new`, and refuses. The other check, `owner = frontOf(text).raft`, reads origin, where `raft:` stays empty until the prep PR lands (main.luau:822: "only `status:` is written"). With prepared members left as `prepared-…`, a second session's `new raft` (or a second `z-raft` run, whose no-argument policy is deterministic, so two runs pick the same chores) passes both checks. Two rafts then list the same issue on origin, and the conflict surfaces only when the second prep PR tries to merge its `raft:` line, or when its `ready` fails "issues: list and its members' raft: fields disagree".
- The raft document is the template (`tracker/templates/raft/doc.md`: Theme, Whole-raft design and Order are HTML comments), published `design: ready` and `prepared-…`. `ready` checks only `design: ready` and a `check "` line, which the raft template's `check.sh` already has (RC0). So a multi-issue raft whose order and interfaces were never written reaches execution. The tracker skill (unchanged, and inlined in every prompt) says only ticket-prep sets `design:` and that the move to `prepared` is carried by the prep PR, not published.
- The spec's "prepared issues raft" checks that member statuses are unchanged. That pins the hole.

Critique: This is the second round with a hole in the "who holds this issue while it is being rafted" mechanism (review-001 F7). The tempting fix is to also scan every origin raft's `issues:` list for the id.
Consequences: Scanning `issues:` closes the double raft, but nothing holds the raft itself: it is `prepared` from birth, so a `stop`, a `recombine` (F5) or a third session can act on it while its membership PR is still open. The template-design problem also remains.
Recommendation: Use the existing claim mechanism instead of a new one. `new raft` over `prepared` members stamps the raft and its members `preparing-<fresh stamp>` (status-only, exactly as for `new` members) and leaves the raft `design: draft`. `z-raft` then fills the raft's Theme and Order in its prep worktree and sets the raft and its members to `design: ready` / `prepared`. That edit lands with the prep PR, as the tracker skill already says. That brings one new rule: an abandoned z-raft must give a prepared issue back as `prepared`, not `new`. Allow `status <id> prepared` from `preparing` only when origin's document is `design: ready`, and add that to `zz-rules`. Spec cases: after `new raft`, origin shows both members `preparing-<raft's stamp>`; a second `new raft` over one of them from another fixture worktree is refused and publishes nothing; `ready` of the raft is refused until the worktree's prepared commit is pushed, then succeeds; `status <id> prepared` gives a claimed design-ready issue back, and is refused for a `design: draft` one.

### F5 [high] c0116: recombine's "claim" does not hold a prepared keeper, a refusal may already have published, and the project-refusal case passes a mutant that ignores `project:`
Where: c0116 Design (recombine paragraph); `recombine.spec.luau` "members move", "project differs" (lines 142-155), "active raft refused"
Evidence:

Recommendation: Make recombine reuse `status <R-id> preparing`: it checks every refusal against origin first (types, project, backlog, and any `preparing-` stamp it did not draw), then stamps both rafts and all their members `preparing-<fresh stamp>`, then makes the worktree edit, which sets `prepared` and lands with the prep PR. In "members move", use a keeper seeded `prepared-…` and assert `ready <keeper>` from `f.main` is refused after recombine. Add a case where a retired raft held `preparing-<other stamp>` is refused.

### F7 [high] Rafts have no project, so every view counts every raft's reviews, `new raft` can mix projects, and emergent issues default to pickman
Where: c0114 Design (only `new issue` writes `project:`); c0116 Problem ("Rafts never cross projects") and Design (only recombine checks `project:`); c0118 `Review = { raft, kind }`, `Item.project`, "`weeks` counts a review only when `doneAtByRaft[review.raft]` is set"; c0114 `list --project`
Evidence:
- `Review` has no project, and `build` filters reviews only by done time. A z-nile raft's design and code reviews are counted in the pickman view and in the z-nile view. "landed reviews" uses one project, so the mutant "count every review in every view" passes AC3. The Problem's per-project review graph is wrong for both projects.
- A raft document never gets `project:` (the raft template, `new raft` and recombine don't write it). By "missing key is pickman", every raft, including a z-nile one, is a pickman item: its band and card sit on the pickman tab, and `list --project z-nile` never prints a z-nile raft.
- `new raft` has no project check, so a raft over a pickman and a z-nile issue is created. Only recombine enforces "Rafts never cross projects".
- An emergent `new issue --raft R…` inside a z-nile raft gets `project: pickman` unless the executor remembers `--project`, and that makes a cross-project raft.

Critique: The tempting fix is to add `project:` to the raft template.
Consequences: A written raft `project:` can disagree with its members, so there is one more consistency rule for `ready` and `audit` to enforce.
Recommendation: Derive, don't store: a raft's project is its members' common project. `new raft` refuses members whose `project:` values differ (reading origin, missing = `pickman`). An emergent issue inherits its raft's project, and `--project` with a different id is refused. `view.build` keys reviews and raft items by that derived project, either by giving `Review` a `project` or by looking up the raft item. `list --project` includes rafts by the same rule. Spec cases: `build` with two projects and a done z-nile raft's two reviews gives counts only in the z-nile view; `new raft` over a pickman and a z-nile issue is refused and publishes nothing; `new issue --raft` in a z-nile raft writes `project: z-nile`.
