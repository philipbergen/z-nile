### F1 [high] A wrong implementation that dates every record by the lock's `pid` file passes AC2 and c0058's lock.spec
Where: c0127 Design, `lockRecords` ("`pid-<n>` by `<lock>/pid-<n>`"); reuse.spec cases 1 and 3; Rules and mutants table (no row)
Evidence: I changed the prototype's `lockRecords` to record `path = `{lock}/pid`` for every entry, so every pid is judged against the top `pid` file's time. `lune run tests/run -- reuse.spec.luau tests/acceptance/c0058/lock.spec.luau` gave `16 passed, 0 failed`. No case can tell the two apart: case 1 backdates both `pid` and `pid-<n>`, and case 3 ("started before it was recorded still holds") writes both files fresh. The mutant is plausible because "the record time is when the lock was taken" is the natural shortcut. It is also dangerous. A worker starts after the top `pid` file is written and records `pid-<n>` itself (`fence.enter`). If the top process dies while workers live on (killed alone, so its workers are orphaned), the mutant judges every live worker reused and takes the lock over while they still use the fixtures. That is the 2026-09-30 failure mode the lock exists to stop.
Critique: per-file dating is a rule the Design states, and no case pins it (ticket-prep/spec-design-correspondence). The fix the author will reach for is a new case with the two files at different times. The cheaper fix is to adjust the existing cases so that each mix of times shows up.
Consequences: a "newest record time" mutant is the mirror image, and it also survives today, because case 1 backdates both files. Both directions need a case. Neither change adds a run.
Recommendation: in reuse.spec, case 3 backdates `<lock>/pid` (a dead pid recorded in 2020) and keeps `pid-<n>` fresh for the live `sleep` (fake ps `00:05`): the run must still wait and give up naming the pid. Case 1 leaves `<lock>/pid` (dead) fresh and backdates only `pid-<n>`: the lock must still be taken over. Add a row "each record is dated by its own file" to Rules and mutants, with both mutants (oldest/`pid`-file time, newest time), run on the prototype and recorded in E4.
Lesson: ticket-prep/spec-design-correspondence

### F2 [high] The stand-in `ps` ignores its arguments, so a call that never asks about the recorded pid passes AC2
Where: reuse.spec `fakePs` (prints the same elapsed time for any arguments); c0127 Design `fence.startedAt` (`ps -o etime= -p <pid>`)
Evidence: I changed the prototype's call to `process.exec("ps", { "-o", "etime=" })`, dropping `-p pid`. reuse.spec: `7 passed, 0 failed`. With the real `ps`, that call prints one line per process on the terminal, so `parseElapsed` returns nil, every live pid holds, and the fix does nothing. A wrong `-p` target (the waiter's own pid, the mutex owner for a `pid-<n>` record) or `-o etimes=` (Linux-only seconds) would pass the same way. The only check on the real arguments is E1 and its Phase 1 repeat, which are manual observations, not checks.
Critique: this is testing/pin-call-site-arguments. The stand-in masks exactly the arguments the call site passes.
Consequences: a stand-in that answers per pid must give every pid the fixture runner asks about a defined answer, so the runner never receives an unexpected one. The mutex case asks about the owner pid and the record cases ask about each live record. An unknown pid has to fail like the real `ps` does (exit 1, which holds), so a wrong target turns the takeover cases red instead of passing by luck.
Recommendation: `fakePs` takes a map of pid to elapsed time (or nil for "refused") and writes a script that answers only `-o etime= -p <pid>`, exactly, for a pid in the map (`[ "$1 $2 $3" = "-o etime= -p" ]` and a `case "$4"`), printing `   <elapsed>`. Anything else exits 1 with no output. Add a mutant row ("ps called without `-p <recorded pid>`", "ps asked about the wrong pid") and run it.
Lesson: testing/pin-call-site-arguments

### F3 [high] Inside an outer sandbox the fix does nothing, and that narrowing has no Scope decision
Where: c0127 Design, "Where it runs" ("In an outer sandbox `ps` may be refused too: same fallback"); Problem; skill Lock bullet (it names only the jail)
Evidence: the testing skill accepts runs inside an outer sandbox (Claude Code's own) that protects the repository. There, `fence.alive` counts a refused `kill -0` as alive (`confined` for `outer sandbox …`). So a reused pid owned by an unrelated process outside the sandbox counts as alive, as both of R0034's pids would. `ps` is refused there for certain, not just "may be". Any `sandbox-exec` refuses a setuid exec: `sandbox-exec -p '(version 1)(allow default)' /bin/ps -o etime= -p $$` → `execvp() of '/bin/ps' failed: Operation not permitted`. So the 2026-10-21 lock still blocks for 240 s in that mode. The Problem asks for the takeover without naming a mode, and no `Scope decision` line drops one. A start-time source that works under a sandbox exists, and the runner already depends on perl: `sysctl` `KERN_PROC_PID` through perl's `syscall`. My scratch run: `perl -e 'my $m=pack("i4",1,14,1,$pid); my $b="\0"x1024; my $l=pack("Q",1024); syscall(202,$m,4,$b,$l,0,0); print unpack("q",$b)'` printed pid 1's start in epoch seconds both outside a sandbox and under `sandbox-exec (allow default)`. It printed nothing (length 0) for a missing pid. The jail's profile is `(allow default)` and does not deny `sysctl` or `process-info`. A non-setuid copy of `/bin/ps` is killed (137), so that is not an option.
Critique: the design treats "ps refused" as rare, but it is every macOS sandbox, the jail included. The fallback is safe. Calling it a limit of the environment hides that the captured outcome is missing in one supported mode.
Consequences: a sysctl source changes several things. On macOS the start is exact epoch seconds rather than whole elapsed seconds, so the slack argument changes (F4 then matters less). Judging also becomes active inside the jail, for fixture runs started by specs. That is correct, since a live outside pid answers EPERM and now gets a real start, and c0058's lock.spec must stay green under it. reuse.spec could then use real backdated records and real `sleep`s, with no stand-in, which also removes F2's gap. The "can't date" case would need a seam instead. Linux keeps `ps -o etime=` (not setuid) or reads `/proc/<pid>/stat`. And `kinfo_proc`'s layout (`p_starttime` at offset 0, 64-bit) becomes an assumption that needs an experiment.
Recommendation: add E6, a pass/fail question: does the perl `sysctl` start time answer inside the real jail (a spec under `.cache`) and inside Claude Code's sandbox, for a pid inside and one outside, and give nothing for a missing pid? If it passes, make it the macOS source of `fence.startedAt`, keep `ps -o etime=` for Linux, and extend reuse.spec with a run inside the jail that uses real processes. If it fails, escalate to the user: (a) keep the full scope and find another source (cost: more experiments); (b) accept the gap with a `Scope decision (user, …)` line, and have the skill's Lock bullet say that a sandboxed agent shell must run specs with the sandbox off, or a reused pid still blocks. Either way, the Design states the outer-sandbox outcome explicitly.

### F4 [medium] `startedAt` reads the clock after `ps` returns, so a slow `ps` makes a live holder look reused
Where: prototype `fence.startedAt` (`return if elapsed then os.time() - elapsed`, evaluated after `process.exec` returns); c0127 Design "Why 2 s of slack" ("`ps` runs a moment after `os.time()`")
Evidence: the Design's slack argument assumes the clock is read before `ps` runs. The prototype reads it afterwards. I ran a stand-in `ps` that prints `00:00` and then sleeps 3 s. `fence.startedAt` returned `before + 3`, and `fence.holds(true, at, before)` (a record written in the same second) was `false`. The top process writes `pid` about 0.1 s after it starts when the lock is free, and every worker writes `pid-<n>` at start, so a genuine holder's start and record are typically less than 1 s apart. With truncated `etime` and floored mtimes, any `ps` latency over about 1 s can push the computed start past the record by more than 2 s. That happens when a second run judges a lock during a loaded full gate. If every live record is misjudged in one scan, a live run's lock is taken over.
Critique: the risk is small but the consequence is the worst one, and the fix costs nothing. With `now` read before `ps`, computed start < true start + 1 and recordedAt > true record − 1, so slack 2 holds whatever `ps`'s latency.
Consequences: the Design should state the order and the bound. A spec must pin it, or a refactor will undo it.
Recommendation: Design: `local now = os.time()` before the `ps` call, with the bound above as the slack rationale. Add a rules.spec case that puts a stand-in `ps` on the spec's own `process.env.PATH` (restored after), printing `00:00` and then sleeping 1.2 s. Assert `fence.startedAt(<any numeric pid>) <= before`, where `before` is read before the call. Add a mutant row: "clock read after ps".

### F5 [medium] The repo-fence change exempts reuse.spec from every scan rule, though the Design says it needs only the marker
Where: c0127 Design, `tests/tooling/repo-fence.spec.luau` bullet; prototype `EXEMPT[`{dir}/reuse.spec.luau`] = true`
Evidence: `exempt(path)` skips both the guard scan ("no spec … switches a guard off": `GIT_DIR`, `--no-verify`, `osascript`, protocol overrides) and the identity scan. The Design itself says "only the marker needs the exemption". The scan already has the narrow form, `ALLOWED[path] = { PICKMAN_TEST_FENCE = "<reason>" }`, used for exactly this purpose by `tests/tooling/fence-cache-entry.spec.luau` ("runs a copied runner as a top-level run") and by c0059's adapt.spec. A whole-file exemption means a later edit to the promoted reuse.spec could name `GIT_DIR` or a real identity and the gate would not notice. That widens a guard (review item 9) for no benefit.
Critique: c0640's lock.spec is EXEMPT, but it is the fence's own spec. reuse.spec is an ordinary consumer, like fence-cache-entry.spec.
Consequences: ALLOWED is keyed by literal path, so the three folder paths must still be built from `renamed.id("c0127")`, as the prototype does for EXEMPT. That keeps compaction safe.
Recommendation: replace the EXEMPT loop with a loop that sets `ALLOWED[`{dir}/reuse.spec.luau`] = { PICKMAN_TEST_FENCE = "runs a copy of the runner as a top-level run (c0127)" }` for the three folders. Re-run E3's promoted gate on the prototype and record that the identity scan still passes (`c0127@example.invalid`).

## Lesson candidates (for the lead)
- testing: a stand-in for an external command answers only the exact arguments the design specifies, and fails like the real command otherwise, because c0127's `ps` stand-in printed for any arguments and let a call without `-p` pass; check: does every stand-in command reject arguments the design doesn't name?
- architecture: when a value is computed as "now minus an elapsed time read from a subprocess", read now before running the subprocess, because the subprocess's latency otherwise moves the result later (c0127's 2 s slack assumed the opposite order); check: is the clock read before the call it is combined with, and is the bound written down?
- ticket-prep: "the tool is refused there, so fall back" needs a check of how often "there" is (every sandbox-exec refuses setuid binaries, so the fallback covered every macOS sandbox), because c0127's fallback silently left the outer-sandbox mode unfixed; check: for each fallback, which supported modes take it, and does the Problem still hold in each?
