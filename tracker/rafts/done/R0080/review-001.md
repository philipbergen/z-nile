### F1 [low] The merge rule does not say which `beta` entry counts when a sha has more than one
Where: .claude/skills/tracker/SKILL.md, Merging step 3, the new `beta` bullets
Evidence: the rule's own recovery path creates duplicates. When the final sha was pushed while draft, step 3 says to dispatch `ci-verify.sh` for `gate`; that `workflow_dispatch` run reports `beta` as `COMPLETED`/`SKIPPED` on the same sha. The `beta` bullets then say to re-fire the ready event, which adds a `pull_request` run whose `beta` ends `SUCCESS`. `statusCheckRollup` now holds two `beta` entries for the head sha, and "`beta` must be `COMPLETED` with conclusion `SUCCESS`" does not say whether the `SKIPPED` one blocks. A literal agent either waits for nothing or posts `BLOCKED:` on a PR that is green.
Critique: it isn't a wrong merge, since SUCCESS is still required, but it is an avoidable `BLOCKED:` that engages the human. The tempting fix is "ignore SKIPPED", which is too broad: a `pull_request` run on a draft-pushed sha also reports `beta` SKIPPED, and that one has to trigger the re-fire.
Consequences: the rule must tell a dispatch run's SKIPPED from a pull_request run's SKIPPED, which the rollup entry's workflow run event (or `gh run list --commit <sha> --event pull_request`) gives.
Recommendation: add one sentence to the `beta` bullets: "Judge `beta` only by the entries from `pull_request` runs (`gh run list --commit <sha> --event pull_request --json databaseId,conclusion`); a `beta` SKIPPED from a `workflow_dispatch` run is expected and ignored, while one SKIPPED from a `pull_request` run means the sha was pushed as a draft: re-fire the ready event." Check that pipeline.spec's merge-rule case still passes, since the existing sentences stay.

### F2 [low] A transient Open Cloud error now blocks every merge, with no documented recovery
Where: scripts/lib/opencloud.luau `execute` (any non-200 create or poll raises), and the tracker skill's `beta` bullets
Evidence: a single 429 or 5xx on any of the roughly 40 polls per script raises `polling the task failed with HTTP 500`. `runSuite` records it as `FAIL`, the runtime step exits 1, and `beta` is red. The merge rule only covers `CANCELLED` (rerun when no steps ran). A red `beta` whose steps ran is "red", so a Roblox hiccup reads as a code failure and the merge stops. This is per design (c0030: "HTTP failures are errors"), but the design came before `beta` became a merge condition for every PR, captures and preps included.
Critique: the tempting fix is to retry everything in `execute`. That would also hide real 401/403 key failures and stretch the 120 s accounting, because sleeps between retries aren't counted in `waited`.
Consequences: retries must be limited to 429 and 5xx, must count toward the same timeout, and a create retry must not create duplicate tasks after a 5xx that did succeed on Roblox's side (a duplicate is harmless for read-only scripts, but it costs quota).
Recommendation: this needs no change in this PR. File a backlog chore, or note under Risks, saying either that (a) `execute` retries 429/5xx polls within the timeout, with spec cases for "a 503 poll then COMPLETE is ok", "401 is still final" and "retry pauses count toward the timeout", or (b) the merge rule allows one rerun of a red `beta` whose log shows only HTTP 429/5xx failures.

### F3 [low] SETUP.md says the comment names "the commit Beta is running", but Beta runs the PR merged with main
Where: SETUP.md, Beta publishing ("the PR comment names the commit Beta is running"); check.yml `beta` step 1 (`actions/checkout@v4` with no ref)
Evidence: on a `pull_request` event, `actions/checkout` checks out `refs/pull/<n>/merge`, the PR merged into the then-current `main`, so `rojo build` publishes that. The comment prints `github.event.pull_request.head.sha`, the PR head. When `main` has moved, Beta contains `main` commits that the named sha does not.
Critique: the comment text and the `SHA` value are pinned by the sequestered workflow.spec, so they stay. Only the docs are wrong. Checking out `head.sha` instead would publish something the gate never tested (the gate also runs on the merge ref), so that is not the fix.
Consequences: none beyond wording.
Recommendation: reword the SETUP.md line to "the PR comment names the PR's head commit; Beta runs that commit merged with `main` as of the run (what the gate tested)". Re-run docs.spec (AC6) and pipeline.spec (AC5) to confirm that the phrases they look for are still present.
