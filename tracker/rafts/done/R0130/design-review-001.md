### F1 [high] After `done R0130`, the permanent c0330 spec runs itself through its own check.sh and fails on the final head and on every later gate
Where: c0330 Design ("A script that runs setup code outside `check` ... still runs that code, which is cheap"); `tracker/issues/c0330/check.sh:13` and the same line in c0050, c0060, c0070, c0360 and the repaired done c0041, c0420, c0430, c0440 (`spec_out=$(lune run tests/run -- "$spec" 2>&1)` at top level, outside `check`); `locator.spec.luau` case 3; R0130 RC1; R0130 Risks ("the spec runs the done scripts only after proving that `ac.sh` honours it (otherwise it refuses, to avoid running the whole gate recursively)").
Evidence: `AC_LIST` only changes `check`, but the shared-fixture check.sh pattern runs the whole spec at top level. In list mode, `tracker/issues/done/c0041/check.sh` still takes 9 s (it runs the worktree e2e spec), c0420 3 s, c0430 4 s, c0440 3 s; RC1's loop takes 20 s today, not "one bash start per item". After `done R0130`, `tracker/issues/done/c0330/check.sh` exists, so `tests/acceptance/c0330/locator.spec.luau` case 3 runs it with `AC_LIST=1`, which runs `locator.spec.luau` again at top level, whose case 3 runs c0330's check.sh again, and so on. I simulated it in a scratch clone (designed `ac.sh`, c0330 moved to `done/`, its spec to `tests/acceptance/c0330`): the nested run's `cleans up` case deletes `.cache/c0330-locator`, which is the outer run's `cwd`, so the outer case 3 then dies with `c0380: could not run check.sh: ... Invalid value for option 'cwd' - path does not exist`. Had the fixture paths not collided, the recursion would have no end. `done R0130` itself still passes, because `promotedChecks` runs before the members are moved to `done/`. So the failure first shows in CI on the final head, which blocks the merge, and then on every `main` gate. The same top-level runs also make c0070, c0360, c0050 and c0060's e2e specs run a second time inside every full gate once they are done.
Critique: the obvious fix is "c0330's spec skips c0330". That removes the self-recursion but leaves nine scripts whose list mode isn't a list mode: every full gate re-runs four, later eight, e2e specs. And any future issue that copies the shared-fixture pattern, which the testing skill doesn't forbid, brings the recursion back the moment its spec lists done scripts.
Consequences: a fix has to stop top-level spec runs in list mode for every script, the existing done ones included. It needs to work without editing each future check.sh correctly, and a spec has to prove it, or it will regress silently. Editing the four done scripts again is allowed in prep (as for the six repairs), but not during execution.
Recommendation: make list mode a property of the spec runner, not of each script. `tests/run.luau` exits non-zero at once with `AC_LIST is set: specs are not run in list mode` when `AC_LIST` is set. That makes the top-level `spec_out=$(...)` cheap and non-recursive in every existing and future script, and a gate run with a leaked `AC_LIST` fails loudly instead of passing (see F2). Add `tests/run.luau` to c0330's Touched modules and Design. Add spec cases:
(a) a fixture done check.sh whose top-level line runs `lune run tests/run -- <fixture spec that touches a marker>` lists its checks under `AC_LIST=1` without the marker being touched;
(b) `AC_LIST=1 lune run tests/run -- <any spec>` fails with that message.
Add a Rules and mutants row for each. Fix the c0330 Design and Scalability text and the R0130 Risks bullet. Optionally also document in the testing skill that top-level work in a check.sh must be cheap.

### F2 [medium] `AC_LIST` set in the environment turns every check, including `tracker.sh done`'s verification, into a reported pass
Where: c0330 Design, `scripts/lib/ac.sh` list mode ("counts the check as passed, so `finish` still prints `---- n/n criteria passed`"); `cmd.done` → `runCheck` (`main.luau:283`); R0130 RC1 and c0330 spec case 3 (they grep `criteria passed`).
Evidence: `runCheck` runs `bash <item>/check.sh` and inherits the environment. With `AC_LIST=1` exported, for example left over in a shell after running RC1's command by hand, or set by an agent trying to get past a red check, every raft check.sh prints `LIST` lines and `---- n/n criteria passed` and exits 0. `done` then promotes, moves and commits a raft none of whose criteria ran. The printed summary claims passes that never happened, so a human reading the log can't tell.
Critique: the tempting fix is to unset `AC_LIST` in `runCheck`. That closes `done` but leaves `tracker.sh check` and any direct `bash check.sh` printing "criteria passed" for checks that never ran.
Consequences: changing the list-mode summary changes RC1's and the spec's `grep "criteria passed"`. Both are prep-owned and can be changed now. Exiting non-zero in list mode would break RC1's `|| exit 1` logic, so list mode should exit 0 with a different summary.
Recommendation: in list mode `finish` prints `---- n criteria listed (none run)` and returns 0 (still failing when n is 0). RC1 and spec case 3 grep for `criteria listed`. `runCheck` in `main.luau` fails (`AC_LIST is set; unset it to run checks`) when `AC_LIST` is in the environment. Add c0330 spec cases (list-mode summary text; `AC_LIST=1 tracker.sh check <id>` on a fixture fails) and their Rules and mutants rows. `scripts/tracker/main.luau` then joins c0330's Touched modules, so c0330 must follow c0360 or c0070 in the workstream plan, or `main.luau` overlaps.

### F5 [low] c0070's "a failed `done` is atomic" has two holes
Where: c0070 Design snippet and the "Failure after the ready call" bullet; Usability.
Evidence:
1. `sh.run` calls Lune's `process.exec`, which *throws* when the program can't be spawned. I checked: `pcall(process.exec, "no-such-gh-xyz", ...)` gives `false, No such file or directory`. With no `gh` on `PATH`, `done` dies with the promotion staged and no rollback, and the next `done` refuses the dirty tree.
2. If `recordAndCommit` fails before its commit (spend attribution, `git commit`), the PR is already ready, and "re-run `git push`" isn't the remedy: the tree holds uncommitted moves. If it is the push that fails, the spend summary is never appended to the PR body, which the bullet doesn't mention.
Critique: case 1 is rare in practice, because `start` needed `gh`, but it contradicts the stated guarantee.
Consequences: none beyond the text and a `pcall`.
Recommendation: wrap the call (`local ok, r = pcall(sh.run, "gh", {"pr","ready"})`; roll back unless `ok and r.ok`). Reword the failure bullet: before the commit, `git reset --hard HEAD` and re-run `done` (`gh pr ready` on a ready PR is harmless); after the commit, `git push`, then append `spend.md` to the PR body by hand.
