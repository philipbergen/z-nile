### F1 [medium] An error inside a coordinator lane hangs the runner forever instead of failing it
Where: tests/run.luau `runConcurrently` (lane body around `process.exec("lune", ...)`, and the `while running > 0 do task.wait(0.005) end` loop)
Evidence: `env PATH=/usr/bin:/bin ~/.rokit/bin/lune run tests/run -- --jobs 2 tests/unit/smoke.spec.luau tests/tooling/metrics-rounds.spec.luau` prints `No such file or directory (os error 2)` twice (tests/run line 110) and never exits. I stopped it with a perl alarm after 8 s (rc 142). The real `lune` process behind the rokit shim stayed orphaned, polling every 5 ms, until I killed it by hand. Any raise inside a lane (spawn failure, EMFILE or EAGAIN under heavy load) ends that thread before `running -= 1`, so the coordinator spins forever. `outcomes[index]` also stays nil, so a `for _, o in outcomes` merge over a table with a hole would silently skip files. The serial runner never needed `lune` on PATH. Today every caller (check.sh, ac.sh, tracker.sh, post-edit.sh) prepends `~/.rokit/bin`, but a gate that hangs is worse than a gate that fails, and the hooks run it unattended.
Critique: the tempting fix is a `pcall` around `process.exec` only.
Consequences: the lane must still produce an `Outcome` for that index (`code = -1`, the error text as stderr) so the merge counts it as one failure (the "worker with no summary" path already prints `FAIL <file>: worker exited with code -1` plus the error), and `running -= 1` must run on every path. If spawning fails for every file, the run prints N failures and exits 1, which is correct.
Recommendation: wrap the whole per-file body in `pcall`, and on error store an `Outcome` for that index that the merge treats as a dead worker. Iterate the merge with `for i = 1, #files do local o = outcomes[i]` so a missing entry is a failure rather than skipped. Add a non-sequestered spec (e.g. `tests/tooling/runner-spawn-failure.spec.luau`) that runs the runner by absolute path with a PATH that lacks `lune`, on two fixture specs under its own `.cache/<dir>`. It asserts exit code 1, one `FAIL <file>: worker exited` line per file, and the unchanged summary line, so the spec itself is the bound on how long the run can take.

### F2 [medium] AC6 failed once under load with 35 failures (c0360 setup and very likely c0041), and the cause is unexplained
Where: `scripts/tracker.sh check c0470`, AC6 (`lune run tests/run -- --jobs 8`, twice); RC2 asserts the same property
Evidence: on my first `tracker.sh check c0470` run, while the R0160 worktree was running its own checks on the same host (load average about 23), AC6 failed: `525 passed, 35 failed, 91 spec files`. The visible tail shows `tests/acceptance/c0360/deferred.spec.luau` cases failing with `No such file or directory` at `write` (line 43), meaning its setup case had already failed. The `slowest:` line for that run was `c0430 12.4s, c0070 12.2s, c0010 9.9s`. `c0041/worktree.spec.luau` was missing from it, although it takes 24-27 s in every green run, so it most likely failed early too. Its 29 cases plus c0360's 9 fit the count of 35. ac.sh keeps only the last 25 lines, so the root failure is not visible. Nine later runs (seven standalone `--jobs 8`, one `check.sh --full`, the second `tracker.sh check`) were all green. This is the "hidden shared state between specs" risk the raft lists first. c0041 and c0360 both `git clone` the worktree root (whose object store is shared with every other worktree and session) and drive `tracker.sh` in the clone, so a concurrent interaction, or a parallel-only sensitivity to a transient root state, has not been ruled out.
Critique: the tempting response is "flaky under external load, rerun". That leaves RC2 passing or failing by luck, and the raft's main risk unexamined.
Consequences: if the cause is concurrency between specs (shared root repo, the tracker CLI touching something outside the clone), `PICKMAN_JOBS=1` becomes the real default for some users, and the isolation guard (AC3, `.cache/<dir>` only) is shown to be insufficient. If it is purely external (another session's `git gc` or a commit in the shared object store while a clone reads it), it is pre-existing but more frequent now that the slow clone-based specs overlap.
Recommendation: reproduce under load (for example two `--jobs 8` suites at once, or the suite next to another worktree's gate) with full output kept (`lune run tests/run -- --jobs 8 > log 2>&1`), find the first failing case of c0041 and c0360, and record the cause in the Verification log. If it is cross-spec shared state, fix it at the source (for example clone from a private snapshot, or point every git-touching fixture at its own `.cache/<dir>`) and add the rule to the testing skill's Speed section. If it is external to the suite, say so in the Risks section with the evidence. Do not edit AC6 or RC2 (sequestered). Escalate if the fix would need that.

### F3 [low] An explicit `--jobs` above 8 is not capped, and lanes are not clamped to the file count
Where: tests/run.luau `parseJobs` / `runConcurrently` (`for _ = 1, jobs do task.spawn(...)`)
Evidence: `--jobs 200` (or `PICKMAN_JOBS=200`) spawns 200 lane threads, and up to `#files` concurrent `lune` processes (91 today). The Design's Scalability section says "Lanes are capped at 8 so a big machine does not fork hundreds of Lune processes", but only the default is capped. Lanes beyond `#files` are idle threads, which is harmless but wasteful.
Critique: capping explicit values silently would surprise someone who asks for 16 on a 32-core box.
Consequences: either the Design text or the code has to change. A silent cap needs a note in the usage text.
Recommendation: spawn `math.min(jobs, #files)` lanes. Either reword the Scalability line to say "the default is capped at 8; an explicit `--jobs` is honoured" or clamp explicit values too, and record the choice as a deviation note in c0470.md.

### F4 [low] Ctrl-C during the static stages leaves the stages running and the `par.XXXXXX` temp dir behind
Where: scripts/lib/par.sh `par_start` / `par_wait` (no trap)
Evidence: in a non-interactive bash without job control, background commands ignore SIGINT, so on Ctrl-C `check.sh` exits while stylua, selene, luau-lsp and rojo keep running to completion. `par_wait` never runs, so `${TMPDIR}/par.XXXXXX` is never removed. The stages take about 1-2 s, so the impact is a leaked directory per interrupted gate.
Critique: a naive `trap 'rm -rf "$PAR_DIR"' EXIT` in the library would override any EXIT trap the caller sets.
Consequences: the library would then own the caller's EXIT trap. Kill the stage PIDs too, or they write into a removed directory (harmless: they fail on write).
Recommendation: optional. In `par_start`, on first use, set `trap 'kill "${PAR_PIDS[@]}" 2>/dev/null; rm -rf "$PAR_DIR"' INT TERM`, and clear it in `par_wait`. Document in the header that `par.sh` owns the INT and TERM traps while a batch is open.
