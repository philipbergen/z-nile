# R0150: Presentation

## Theme
Roadmap raft **c2**, the presentation half of roadmap raft c, split off from R0090 on 2026-09-30 (user: "Split in two"). R0090 put the rules in `Session` and `Session.frame` on the wire; this raft makes them visible and playable:
- the HUD (f0180);
- pellets drawn, with their eaten state in every frame (f0290);
- the start / dying / level clear / game over / play again flow (f0300).

The three belong together because each turns the same replicated frame into something on screen, they share the client's `Main` wiring, and only together do they make a playable loop from join to play again.

Decisions from `tracker/game-design.md` this raft relies on (quoted):
- **Pillar 2**: "Everything that decides an outcome runs in pure Logic, can be simulated headless and is tested in CI. Roblox renders and relays input."
- **Pillar 3**: "Fair and readable in first person. The player can always tell where they're going and where the danger is."
- **Authority**: "The server simulates every maze. Clients send intents and render the replicated state. A session starts only when its client signals it's ready."
- **Run pauses** (R0090): "'Ready!' 2 s before play and after each death and level; death 1.5 s; level clear 2 s." (game time; double in real time)
- **Levels**: "clearing all pellets advances to the next level, which restores every pellet and puts the player back at the start." "A death keeps the pellets already eaten."
- **Lives**: "3, and one extra life, the first time the score reaches 10,000."
- **Game speed**: "Camera turn smoothing (`View.TURN_SECONDS`) and mouse look stay in real time". This raft's pulse is presentation too, and runs in real time likewise.
- **Platforms**: "Desktop (keyboard and mouse) and mobile (touch)". The mobile layout itself is R0120 (f0280).

**Author's choices made in prep** (no game-design decision covers them; the user may veto, and each is one constant or one adapter line):
- pellet look: neon `#FFB8AE` balls 1 stud (power 3) across, at 3 studs (the eye is at 4), power pellets pulsing 0.7–1× every 0.5 s real;
- HUD contents: score as plain digits, `LEVEL n`, life discs counting the life in play, and a draining power bar;
- READY!, a 0.6 black fade through dying, a 6-tick wall flash on level clear, and GAME OVER with score and level;
- play again by button or Enter, with the cursor freed only at game over.

## Whole-raft design
```
 server (src/server/Sessions)                       client (src/client/Main.client)
 ┌───────────────────────────────┐   Snapshot   ┌────────────────────────────────────────────────┐
 │ Session.step / Session.frame  │ ───────────▶ │ frame ─┬─ Camera.push(frame)                    │
 │  frame = v1 snapshot + play   │  (per step)  │        ├─ HudView.show(frame.play)            f0180│
 │        + pellets   (f0290)    │              │        ├─ o = Flow.overlay(frame.play, RULES) f0300│
 │                               │   PlayAgain  │        │  FlowView.show(o) · MazeView.flash(m, o.flash)│
 │ PlayAgain → Session.playAgain │ ◀─────────── │        │  Camera.setCursor(o.playAgain)        │
 │  (sender's own id; f0300)     │  (no args)   │        └─ PelletView.show(h, frame.pellets)  f0290 (last)│
 └───────────────────────────────┘              └────────────────────────────────────────────────┘
 Logic (pure, Lune-tested): Pellets.slots/encode/decode, View.pellet/pulse (f0290); Hud.model/layout (f0180);
 Flow.overlay/isPlayAgainKey (f0300)
```
**Module map**:

| issue | Logic (pure) | adapters |
|---|---|---|
| f0290 | `Pellets.slots`, `encode`, `decode`; `Session.Frame.pellets`; `View.PELLET`, `pellet`, `pulse` | `src/client/PelletView.luau` (new), `Main.client` |
| f0180 | `Hud` (new feature): `model`, `layout` | `src/client/HudView.luau` (new), `Main.client` |
| f0300 | `Flow` (new feature): `overlay`, `isPlayAgainKey` | `src/client/FlowView.luau` (new), `MazeView.flash`, `Camera.setCursor`, `Main.client`; `Sessions` (PlayAgain), `default.project.json`, `tests/runtime/structure.luau` |

**Interfaces between issues**:
- **f0290 → f0300**: `Frame.pellets: string` and `Pellets.decode(maze, code): { boolean }`. f0300's whole-run spec reads pellets through them.
- **f0180 → f0300**: `Hud.model(play): { score: string, level: string, lives: number, power: number }`. f0300's whole-run spec reads the HUD through it.
- **All three → `Main.client.luau`**: each adds one boot call (`PelletView.start`, `HudView.start`, `FlowView.start`), all **before** `ready:FireServer()`. Per frame the order is `Camera.push`, the HUD, the overlay, and `PelletView.show` last (a strict-decode error can't block the rest). The handler's parameter is `frame: Session.Frame`.
- **Shared input**: `Session.PlayFrame` (R0090), unchanged.

**Data flow**: everything on screen is a pure function of the latest frame, plus real time for the pulse. The client keeps only the last pellet code (to skip identical frames), the wall-lit flag and the latest overlay's `playAgain` (to gate the button). The only thing a client sends that's new is the payload-less `PlayAgain`.

**Architecture changes** (made in prep, in `tracker/architecture.md`): new features `Hud` (f0180) and `Flow` (f0300); new edges `Hud -> Levels`, `Hud -> Session`, `Flow -> Game`, `Flow -> Session` and `View -> Pellets`. The graph stays acyclic: Session doesn't depend on View, Hud or Flow.

## Risks & rollback
- **Text-checked adapters**: the adapter specs read source text, as R0040 and R0090 did, because Lune can't run Roblox GUI code. A wrong but well-named adapter could pass them, and OC1 in each issue is the backstop. The mutation table shows the specs do catch the plausible wiring errors (wrong field, wrong rules, a client-chosen id, a payload).
- **Engine behaviour**: ContextActionService and Enter (f0300 E5), and how the GUI looks at small sizes (f0180 E5). Both fall back to adapter-only changes.
- **Wire growth**: the code is per player per frame. A much larger maze or many players per server might want the cached code (f0290 Decisions), with no format change.
- **Promoted-spec brittleness**: the layout spec pins properties, not constants, so tuning sizes needs no chore. The overlay spec does pin `FADE_MAX`, `FLASH_TICKS`, the keys and the banner texts. Changing those later is a chore that narrows the spec.
- **Rollback**: revert the PR. Nothing persists (no data stores). The old client ignores `pellets` and the extra remote.
