### F1 [medium] AC2's client check is passed by an interpolation that divides by the step rate
Where: f0520 `acceptance/adapters.spec.luau` case "the client interpolates over the step rate, never the tick rate"; Rules row "the client interpolates over the step rate".
Evidence: in the scratch copy I changed Camera to `View.interpolate(prev, snap, (os.clock() - arrived) / Session.STEP_RATE)`. `adapters.spec` passes 3/3, and so does the rest of AC1–AC3. The case only checks that the call contains the text `Session.STEP_RATE` and not `TICK_RATE`. With the division, alpha stays near 0.004, so the camera always shows the previous snapshot and steps in visible 1/15 s jumps, which is the stutter OC1 is meant to rule out. Dividing is a plausible slip, because the doc says "interpolates over 1/15 s". Nothing else pins the Camera expression: f0130's interpolate specs call `View.interpolate` directly.
Critique: the AC2 criterion "the client interpolates over the step rate" can be met by a wrong implementation, and the only remaining guard is a Studio check. The fix the author will reach for first is to pin the whole expression with a source pattern (`%(os%.clock%(%)%s*%-%s*arrived%s*%)%s*%*%s*Session%.STEP_RATE%s*%)$`).
Consequences: once promoted, that pattern freezes Camera's local names and the order of the operands. Any later Camera refactor (R0150's presentation work, for example) then breaks a permanent acceptance spec and needs a chore. It also keeps the arithmetic, which is exactly what architecture rule 3 says belongs in Logic, in an adapter.
Recommendation: move the arithmetic into Logic. Add `View.alpha(elapsed: number): number`, returning `elapsed * Session.STEP_RATE` (View already depends on Session, so `architecture.md` doesn't change). Camera calls `View.interpolate(prev, snap, View.alpha(os.clock() - arrived))`. Add `src/shared/Logic/View` to Touched modules and the Affected specs list.
- Spec cases (in `speed.spec` or a new `interpolation.spec`): `View.alpha(0) == 0`; `View.alpha(1/30) ≈ 0.5` (kills both the division and the tick rate); `View.alpha(1/15) ≈ 1`.
- Adapter case: the single `View.interpolate` call's third argument starts with `View.alpha(`, and Camera still never mentions `TICK_RATE`.
- Rules rows: "alpha = elapsed × STEP_RATE", killing the mutants `/ STEP_RATE` and `* TICK_RATE`; and "Camera uses View.alpha", killing a mutant with the inline expression.

### F2 [medium] `game-design.md` keeps real-time numbers that the change makes false, and the design only adds a bullet
Where: f0520 Design "`tracker/game-design.md`" (adds "A *Game speed* bullet under Movement"); `game-design.md` lines 23 ("Level 1 is **7.5 tiles/s**"), 29 ("The buffer expires after **0.8 s** (24 ticks…)"), 37 ("Logic runs on a fixed **30 Hz** tick … Clients interpolate") and 44 ("Run pauses (R0090, 30 ticks/s): 'Ready!' 2 s …; death 1.5 s; level clear 2 s").
Evidence: an executor who follows the doc literally leaves all four lines as they are. `docs.spec` checks only that the new phrases are present, so it passes while the source of truth says, two lines apart, that the buffer expires after 0.8 s and that it lasts 1.6 s. The next prep reads "2 s" and "30 Hz" as real time. R0150 is the obvious case: a HUD countdown or a frightened timer converted with `TICK_RATE` would show game seconds while the bullet promises real seconds, and nobody can tell from the doc which one is meant.
Critique: `game-design.md` is the document "every raft design must agree with", and this change redefines what its seconds mean. The tempting fix is to add a few words, such as "(game time)", after each number.
Consequences: per-number qualifiers miss the next number someone adds. They also leave open the question R0150 will hit: which clock a HUD shows. If a countdown should show real seconds, it has to convert with `STEP_RATE`, not `TICK_RATE`, and that is a rule for adapters.
Recommendation: state one convention at the top of Movement / Tick rate: "Durations and speeds in this document are in game time: 30 ticks per game second. At `GAME_SPEED` 0.5 the server takes 15 steps per real second, so a game second lasts 2 real seconds." Reword line 37 to "30 ticks per game second, stepped at `STEP_RATE` (15 per real second)". Keep the turn buffer line in ticks, with both durations ("24 ticks: 0.8 game s, 1.6 s real"). Add a sentence saying that anything shown to the player in seconds is converted with `STEP_RATE`.
- `docs.spec` additions: the doc contains "game time" or "game second"; it no longer contains "**30 Hz** tick" and no longer contains "expires after **0.8 s**".
- A Rules row: "the doc no longer states real-time figures it contradicts", killing the mutant where only the bullet is added.

### F3 [low] Two things that stay in real time are author choices, not user decisions, and OC1 doesn't cover input latency
Where: f0520 Non-goals (`View.TURN_SECONDS`, mouse look "left alone"); Observed OC1.
Evidence: the user asked for "everything in game time". Leaving the 0.12 s camera turn in real time is a reasonable reading, but it's recorded as a non-goal, not as a user decision, and the game-design bullet as specified doesn't mention it. Slowing the clock also doubles the input path in real time. An intent now waits up to 1/15 s for a step, and the client then shows the move over another 1/15 s of interpolation: up to about 133 ms before network latency, against about 67 ms before. OC1 checks smoothness only.
Recommendation: list the camera turn and mouse look as "not slowed (prep decision; the user can veto)" in the game-design bullet. Extend OC1 with "a key press turns or reverses the player without a noticeable delay". If that fails, the fallback is the other design (halve the speeds in Logic at 30 Hz), which re-prepares the tick-pinned specs. Say so in Risks.

Verdict: changes
