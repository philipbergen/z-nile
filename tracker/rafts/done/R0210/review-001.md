### F1 [high] A spec can turn git's network back on and reach the GitHub remote with the person's keychain credential; the runner does not stop it and the review-only list does not name it
Where: `scripts/lib/fence.sh:50-57` (`credential.helper=`, `protocol.allow=never`, `protocol.file.allow=always` injected through `GIT_CONFIG_COUNT`); `tests/tooling/repo-fence.spec.luau:18-36` (`NAMES`); testing skill, "No network for specs" and "Caught only by review".
Evidence: git reads `GIT_CONFIG_COUNT` entries before `GIT_CONFIG_PARAMETERS`, so a later `-c` wins. In `$TMPDIR`, with the same env the fence injects (`GIT_CONFIG_COUNT=2`, `protocol.allow=never`, `credential.helper=`):
- `git ls-remote https://example.invalid/x.git` gives `fatal: transport 'https' not allowed` (the guard);
- `git -c protocol.allow=always ls-remote https://example.invalid/x.git` gives `Could not resolve host`: the transport is allowed again;
- `git -c protocol.https.allow=always …` does the same;
- `git -c credential.helper=osxkeychain config --get-all credential.helper` ends in `osxkeychain`: the helper reset is undone.

This machine's system gitconfig names `osxkeychain` (`/Applications/Xcode.app/.../gitconfig`), and `origin` is `https://github.com/philipbergen/pickman.git`. The jail denies file writes only, not the network or the keychain. So a spec under the jail can run `git -c protocol.allow=always -c credential.helper=osxkeychain push https://github.com/philipbergen/pickman.git <sha>:refs/heads/main` (directly, or through `fixture.git`, which skips `-c` pairs) and reach GitHub with whatever the keychain holds for github.com. I did not exercise the keychain step. The same holds for ssh: `-c protocol.ssh.allow=always` plus `env = { GIT_SSH_COMMAND = "ssh" }` uses `~/.ssh` keys without a passphrase, since only `SSH_AUTH_SOCK` is removed. And `GH_TOKEN` passed in a spec's `env`, from `security find-generic-password`, re-arms `gh`. None of `protocol.`, `credential.`, `GIT_SSH`, `GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK` or `--config-env` is in the scan's `NAMES`. The testing skill says that spec runs allow git "no network transport at all … however a URL is spelled or aliased", and its "Caught only by review" list (Linux writes, `check.sh` files' own commands, work handed outside the jail) doesn't cover this. So it is a path to the real remote beyond what c0640 documents.
Critique: the network guard is advisory: it is config, and the process it guards can override config. The obvious fix is to add `protocol.` and `credential.helper` to `NAMES`. That alone leaves `GIT_SSH_COMMAND`/`GH_TOKEN` through `env`, names built by concatenation (c0650's own spec builds banned names that way), and `include.path` in a fixture's config pointing at a file that turns protocols back on.
Consequences: a scan entry for `credential.` would flag every legitimate reader of the word (the fence itself is exempt, but specs that test the reset would need allowlist entries). A kernel-level network rule in the jail changes what specs may do (E15 found that a first profile blocked localhost too, and some spec may use a loopback port). Denying reads of `~/.ssh` and `~/.config/gh`, and the keychain service, may break a spec that legitimately reads a person's ssh config (none does today).
Recommendation: put the network guard where the file guard is, in the jail profile, and keep the scan as the second layer:
- in `profile()`: `(deny network-outbound (remote ip))` followed by `(allow network-outbound (remote ip "localhost:*"))` and `(allow network-outbound (remote unix-socket))`, re-running E15 with that form; and, independently, `(deny file-read* (subpath "~/.ssh") (subpath "~/.config/gh"))` (both as written and resolved, as for `~/.gitconfig`) and `(deny mach-lookup (global-name "com.apple.SecurityServer"))`, so no credential is readable from a spec at all;
- in `repo-fence.spec`: add `protocol.allow`, `protocol.`, `credential.helper`, `GIT_SSH`, `GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK` and `--config-env` to `NAMES`, with a planted case for each in the "gate spec fails on …" self-test (it is not sequestered: `tests/tooling`), and assert in the jail case that an outbound connection is refused by the kernel even with git's config overridden, for example `git -c protocol.allow=always ls-remote https://192.0.2.1/x.git` (an IP literal, so DNS doesn't decide it) failing at once with a permission error rather than a timeout;
- in the testing skill: under "Caught only by review", name "on Linux, a spec that re-enables git's network (`-c protocol.*`, a credential helper, `GIT_SSH_COMMAND`, a token in `env`)", since CI has no jail;
- spec cases: the jail refuses an outbound connection to a public IP while a loopback listener still works; the scan flags each new name.

### F2 [high] The jail can be escaped by renaming an ancestor of the checkout, writing, and renaming it back
Where: `tests/lib/fence.luau:278-294` (`profile`); testing skill, "Jail (macOS)": "Nothing a spec does can change the repository".
Evidence: the profile denies `file-write*` on `(subpath "<checkout>")`, the common git dir and the main checkout, but not on their ancestors. Seatbelt checks the path an operation names, so renaming a parent directory is allowed, and afterwards the protected files have paths the deny rules no longer match. In `$TMPDIR`, under `(deny file-write* (subpath "$A/prot"))`: `echo direct > $A/prot/f` gives `Operation not permitted`, `mv $A/prot $A/prot2` too, but `mv $A ${A}2 && echo escaped > ${A}2/prot/f && mv ${A}2 $A` succeeds and `prot/f` then reads `escaped`. For this repository, a spec can `mv ~/code ~/code-x`, edit `~/code-x/pickman/.git/config` (remove `origin`, set `user.email`), or commit, then move it back. The same works for `~/.config` (the person's git configuration). The gate's jail case only probes direct writes, and the scan has no name for it.
Critique: this needs a deliberate rename, so it is less likely than the incidents. But c0640 promises a kernel-level guarantee, and `fs.move` of a computed parent path is a plausible bug. The tempting fix, denying writes on `~` or `~/code` as a subpath, would also forbid every legitimate write under `$HOME` (tool caches, `~/.rokit`), so it is too broad.
Consequences: denying `(literal "<ancestor>")` for every ancestor blocks rename, unlink, chmod and chown of those directories themselves, but not writes to their other children, which are different paths. It needs a check that creating and deleting a sibling of the checkout (for example `~/code/other-file`), and writing under `$HOME/.cache` and `$TMPDIR`, still work under that profile. It also closes `~/.config` and `~` itself against a rename, which no spec should do anyway.
Recommendation: in `profile()`, for each protected path and for `~/.gitconfig`'s and `~/.config/git`'s directories, add `(deny file-write* (literal "<a>"))` for every ancestor `<a>` up to `/`, both as written and resolved. Add to `repo-fence.spec`'s jail case a harmless probe that a rename of the checkout's parent is refused, for example `os.rename(parent, parent)` or `chmod <its current mode> <parent>`, which change nothing if they were allowed. Add a `fence.spec`-style check in a scratch tree that the rename-write-rename sequence fails. Record it in the testing skill's Jail bullet ("ancestors can't be renamed").

### F3 [medium] The fixture-identity rule doesn't see the identity form this raft introduced, so the tripwire's premise can quietly erode
Where: `tests/tooling/repo-fence.spec.luau:278-296` (pattern `user%.email[^@\n]-(…@…)`); `tests/acceptance/c0010/tracker-lifecycle.spec.luau` and `tests/acceptance/c0070/done-order.spec.luau` (new `ID` tables with `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL`).
Evidence: the gate's identity rule matches only text after `user.email`. c0010 and c0070 now set their identity as `GIT_AUTHOR_EMAIL = "e2e@example.invalid"` and `GIT_COMMITTER_EMAIL`, which the pattern never reads. A spec with `GIT_AUTHOR_EMAIL = "me@gmail.com"`, or `commit --author="x <me@gmail.com>"`, passes the gate. Its commits then aren't recognisable as fixture writes, and the tripwire tells fixture-written refs and commits on HEAD only by that author (`fence.luau:183-188`, `214-220`). Also, since the fixture's own config no longer holds an identity, any c0010/c0070 command that misses `ID` silently commits as the person's real global identity.
Critique: the obvious fix is adding `GIT_AUTHOR_EMAIL` to the regex. `GIT_COMMITTER_EMAIL`, `EMAIL=` and `--author` stay open.
Consequences: a wider pattern can catch non-identity text (a doc string mentioning an address); the existing exemptions and `@example.invalid` suffix test handle that.
Recommendation: match addresses after any of `user.email`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_EMAIL`, `EMAIL` and `--author`, and add a planted case for each to the gate's self-test. In c0010 and c0070, keep the env identity, which the precondition needs (Verification log), and also check in the spec, after the commands, that every fixture commit's author is `@example.invalid` (`git log --format=%ae`), so a call that misses `ID` fails there instead of committing as the person.

### F4 [low] The fixture helper's "nothing points git elsewhere" has gaps: `-c core.worktree=…`, config through env, and shell scripts that change directory
Where: `tests/lib/fixture.luau:53-74`; `tests/acceptance/c0330/locator.spec.luau:33-62`.
Evidence: `pointsElsewhere` skips every `-c` pair, so `fixture.git(fx, { "-c", "core.worktree=" .. root, "checkout", "-f", "." })` passes the check and runs against the real checkout's files. `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT` in `options.env` aren't refused. For a non-git `cmd` only the directory it starts in is checked: c0330's "AC_LIST=1 lists a check" case runs `bash -c 'source "$1"; …'` with `$1` = the real `scripts/lib/ac.sh` "in the fixture" `fx`, and `ac.sh` immediately `cd`s to the real root, so that check runs at the real root. It only touches a marker in `.cache`, so it is harmless, but the helper's guarantee is hollow there. On macOS the jail covers all of it. On Linux the review-only list covers it.
Recommendation: refuse `-c core.worktree…`/`core.bare`/`include.` values and `GIT_CONFIG_*` env in `pointsElsewhere`, with a case in a non-sequestered spec. In the testing skill's Fixtures bullet, say that `fixture.exec` of a shell or script checks only where it starts, so a script that `cd`s (as `ac.sh` does) must itself live in the fixture.

### F5 [low] An outer guard that doesn't exist counts as "unwritable" in the fixture-of-a-guarded-run proof
Where: `tests/lib/fence.luau:297-343` (`writable` skips `not fs.isDir(dir)`; `fixtureOfGuarded` counts any `PICKMAN_FENCE_REAL_GIT` entry other than its own as an outer guard).
Evidence: with an inherited `PICKMAN_FENCE_REAL_GIT=/nonexistent/.git` and a checkout below a ceiling entry ending in `/.cache`, an unjailable run (in a permissive outer sandbox) passes all four conditions: the stale entry is "other", it isn't writable because it doesn't exist, the open paths are its own, and it lies under a `.cache` ceiling. It then runs unjailed. This needs a checkout inside some `.cache` directory and a stale variable, so it is unlikely.
Recommendation: count an entry as an outer guard only if `fs.isDir(entry)` and its probe was refused. Add a case to the "can't be jailed" set with a nonexistent entry (in a non-sequestered spec, or noted for c0640's next edit).
