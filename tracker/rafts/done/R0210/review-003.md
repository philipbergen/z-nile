### F1 [high] The jail still lets specs write files that unjailed processes later run or copy into the repository: the temporary folder holds them (repeat of review-002 F3, narrowed to what the allowlist left open)
Where: `tests/lib/fence.luau` `tempDirs`/`profile` (`(allow file-write* (subpath …))` for `$TMPDIR`, `/tmp` and `/private/tmp`, as written and resolved); `escapes` (outer sandboxes); testing skill, "Jail (macOS)" and "Caught only by review".
Evidence: I rebuilt the profile `profile()` produces for this worktree and ran it under `sandbox-exec`. A write to `$HOME/.pickman-r3probe` gives `Operation not permitted`, as the fix intends. A write into `/private/tmp/claude-501/-Users-philipbergen-code-pickman/<session>/scratchpad/` succeeds (`WROTE-SCRATCH`, the file read back `planted`, then removed). That folder is a Claude Code agent's scratchpad, and it is not idle: this raft's own session keeps executable scripts there that it runs unjailed (`mutate-all.sh` does `cd /Users/philipbergen/code/pickman/.worktree/proto2-c0640` and then `bash …/scratchpad/mutate4.sh`). It also keeps "good" copies of repository files there (`fence.good`, `rf.good`, `main.good`, `publish.good`), and another session's `mut.sh` backs files up to `/tmp/.mutbak.$$` around a test run. So a spec, under the jail, can rewrite `mutate4.sh`, or `fence.good` before the author copies it back over `tests/lib/fence.luau`, and the next unjailed `bash` or `cp` changes the repository or its remote with the person's credentials. Under the jail the keychain is still readable (`security find-internet-password -s github.com` finds an item), so the script that runs later has what it needs. The testing skill now says the jail denies home "because tools … run later without the jail", but it lists the temporary folder as allowed without that caveat. Its "Caught only by review" list names only contacting a process (`open`, `osascript`, `launchctl`, a daemon), not planting a file there that one runs later. Outer sandboxes have the same opening: `escapes` doesn't probe the temporary folder, and its home probe is one sample (a file at `$HOME` itself), so an outer sandbox that allows `~/.cache` or `~/.claude` but not `$HOME` is accepted.
Critique: the round-2 fix closed home and kept the temporary folder, which specs need (`mktemp`, the browser guard, `par.sh`). But the temporary folder is shared with every other program the person runs, agents included, and some of those programs run code from it. "Nothing a spec does can change the repository" is still false by one step of indirection. It needs a deliberate spec, as review-002 F3 did. The tempting fix, giving the jailed child `TMPDIR=<cache>/tmp` and dropping `/tmp`, isn't enough on its own: macOS `mktemp` without a template ignores `TMPDIR` and uses the per-user folder (`TMPDIR=$TMPDIR/r3t mktemp -d` printed `/var/folders/…/T/tmp.QfVgJb1SOP`), so whatever needs it would break, or the per-user folder would have to stay open.
Consequences: narrowing means a run with a private temp folder under `.cache` (made fresh under the lock and removed at the end), and a measured answer to which specs or tools write `/var/folders/…/T` or `/tmp` directly (one full run under the narrowed profile with the sandbox's deny log). If the per-user temp folder has to stay writable, a smaller version of this hole remains, and it must still be named. The real checkout's `.cache` is in the same class with lower stakes: a spec can write `.cache/tracker-focus` or `.cache/tracker-claim-<raft>`, which a later unjailed `tracker.sh commit` or `start` reads (it changes which issue a commit is charged to, or makes `start` treat a claim as its own). No code runs from there.
Recommendation: this goes to the person (last round). Either:
- (a) narrow: the jailed child gets `TMPDIR=<checkout>/.cache/tmp-<pid>`, and the profile drops `/tmp` and `/private/tmp`, keeping the per-user temp folder only if the measured run needs it, with the reason in a comment. Add a live probe to the gate's jail case that `/private/tmp/pickman-jail-probe-<tag>` can't be created (removed at once if it could). Add the same probe to `escapes`. Record the measurement in c0640's verification log.
- or (b) accept it and document it: add to the testing skill's "Caught only by review" list "planting a file outside the repository that an unjailed process later runs or copies back: the temporary folder (agents' scratchpad scripts, backup copies), the per-user temp folder, `.cache` state the tracker reads". Change the Jail bullet's "Nothing a spec does can change the repository" to say what the jail covers directly.

Either way, this edits no sequestered file. c0640's AC8 checks only for the section names, which stay.

### F3 [low] The profile trusts `TMPDIR`: a broad value, such as `$HOME` or a folder above the checkout, reopens the repository to every spec, and only the gate spec would notice
Where: `tests/lib/fence.luau` `tempDirs` (any non-empty `TMPDIR` becomes `(allow file-write* (subpath …))`).

## Main question
Beyond c0640's review-only list (Linux, `check.sh` files' own commands, contacting a process outside the jail), one path remains:
- **F1:** a file planted in the temporary folder, which the jail leaves writable, and which an unjailed process (an agent's scratchpad script, a restore copy) later runs or copies into the repository with the person's credentials.

In the `sandbox-exec` mode, direct writes, ancestor renames, home, non-loopback IP, git's network transports (`GIT_ALLOW_PROTOCOL=file`) and proxies are closed. An outer sandbox must prove home, the folders above the checkout and the network closed, and it does (checked by hand). Unix sockets and loopback daemons (docker, a local sshd or proxy) fall under the documented "a daemon" bullet. None listens on this machine today except ollama, postgres and system services.
