### F1 [high] AC3 ("neither CI nor any variable skips the gate") passes with a `setup.sh` that skips the gate on a variable every GitHub runner sets, so the one full-gate run in `check.yml` can still be bypassed
Where: `setup-run.spec.luau` `CI_ENV` (`CI`, `GITHUB_ACTIONS`, `GH_TOKEN`) and the case "no variable skips the gate: only --tools does"; c0530/check.sh AC3 label; c0530.md Design "Run" bullet ("the spec decides `CI`, `GITHUB_ACTIONS`, ..."), Rules row "CI does not skip the gate", Theme of R0230.
Evidence: each mutant below was inserted into `scripts/setup.sh`, then `setup-run.spec.luau` was run:
- `[[ -n ${RUNNER_OS:-} ]] && exit 0` on the line before `say "gate"`: **8 passed, 0 failed**.
- `[[ -n ${GITHUB_RUN_ID:-} ]] && exec true` before `say "gate"`: **8 passed, 0 failed**.
- `[[ -n ${RUNNER_OS:-} ]] && exit 0` before `say "lune type definitions"`: **8 passed, 0 failed**.
On `check.yml`'s `gate` job, `RUNNER_OS=Linux` and `GITHUB_RUN_ID` are always set, so each of these makes `scripts/setup.sh` exit 0 before `scripts/check.sh --full`, and the PR goes green with no gate. The spec's `env -i` is exactly what hides them: the sandbox sees only the four CI variables the author thought of, never the environment the real gate job has. The CI check is the issue's whole point (R0230 Theme: "the only full-gate run in CI's `check.yml`").
Critique: the tempting fix is to add `RUNNER_OS` and `GITHUB_RUN_ID` to `CI_ENV`. That kills these two and leaves the other thirty-odd default Actions variables (`GITHUB_WORKFLOW`, `GITHUB_EVENT_NAME`, `RUNNER_TEMP`, `ImageOS`, `ACTIONS_*`, ...) open, one mutant at a time, which is the same windowed-guard problem review-003 F1 described.
Consequences: forwarding the spec's own environment instead (so, on CI, the runner's real one) covers every variable the runner sets, but brings three rules. (1) Some inherited variables change how `bash` or the stub behave and must be dropped or overridden: `PATH`, `HOME`, `BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `CDPATH`, `GLOBIGNORE`, `PS4`, `BASH_XTRACEFD`, `GITHUB_PATH`/`GITHUB_ENV`/`GITHUB_OUTPUT` (point them at sandbox files), and the `STUB_*` names. (2) The real `GH_TOKEN` must be replaced by `ghs_fake`, or the stub writes it into `calls.log` via `rokit authenticate ... --token`. (3) Locally the inherited set is the developer's shell, so that case is not the same on every machine; it must assert only "the gate runs once with `--full`" and pass for any environment, never depend on a value.
Recommendation: keep the deterministic cases, and extend CI coverage in two ways. (a) Make `CI_ENV` a documented snapshot of GitHub's default runner variables (all `GITHUB_*` and `RUNNER_*` defaults plus `CI`, `ImageOS`, `ImageVersion`, `ACTIONS_RUNNER_DEBUG` unset), used by the CI, red-gate and unknown-argument cases, so a runner-variable skip fails locally too. (b) Add a case "with the caller's own environment, the gate still runs once with --full": forward the spec process's environment with the drop/override list above and `GH_TOKEN=ghs_fake`, on both platforms; on CI this is the real runner environment. Add Rules rows for both, with the three mutants above recorded as `run`, and say in AC3's prose which environments are covered. Name the residual honestly (F2).

### F2 [medium] Deleting the slice spec loses coverage it had: its `exit` scan kills an exit-form bypass outside the window that the new spec does not, so "kills every mutant it killed" is false
Where: c0530.md Design (`setup-tools.spec.luau` bullet: "Every behaviour it pinned is pinned by `setup-run.spec.luau`"), Regression guard `Overrides:` ("kills every mutant it killed plus the five it missed"), E3.
Evidence: with `[[ -n ${RUNNER_OS:-} ]] && exit 0` inserted before `say "lune type definitions"`: old `setup-tools.spec.luau` **5 passed, 1 failed** (its last case: "exits somewhere unexpected"); new `setup-run.spec.luau` **8 passed, 0 failed**. The same holds by construction for any `exit` keyed on a condition the sandbox never produces, environment or not, e.g. `[[ -d /home/runner ]] && exit 0` placed outside the `--tools`...gate window (the old scan flags any unlisted `exit` line; the new spec only sees what runs in the sandbox). E3's 20 mutants are all keyed on conditions the sandbox does produce, so the claim was never tested against this class.
Critique: the tempting fix is to keep the old spec. That keeps its leaks and false positives (review-003 F2, F3), which is why c0530 exists.
Consequences: F1's fix closes the environment-keyed part of this class. What remains are bypasses keyed on the host itself (paths like `/home/runner`, `id -u`, the date), which no sandbox run can see and only a text check could; a text check brings back the brittleness on comments and messages.
Recommendation: after F1, correct the Design and `Overrides:` text to say what is lost: "the old text scan also flagged an `exit` keyed on a host probe outside the window; the new spec cannot see host-keyed conditions; accepted residual." Record that residual in R0230's Risks. Do not keep the old spec. Optionally (author's call, decide in prep, not during execution) add one narrow structural case to the new spec: the count of lines whose first word is `exit` or that contain `&& exit`/`&& exec`/`|| exit` outside `die()` equals the known set, ignoring `#` comments; if added, it needs its own Rules row and a mutant run.

### F3 [medium] E4 (the spec on Linux) is left to the PR's final CI run after `done`, whose fallback "fixed in the PR" means editing the sequestered spec after review
Where: c0530.md E4 ("The raft PR's CI runs it once `done` has promoted it ... a Linux-only failure there is fixed in the PR"); R0230.md Experiments phase and Risks ("caught by the raft PR's final CI run on ubuntu, after `done`").
Evidence: `check.yml`'s `workflow_dispatch` step exists for exactly this: "sequestered acceptance specs of the active raft, proven on Linux before `tracker.sh done`" (`find tracker -path '*/active/*/acceptance/*.spec.luau'`). Once `start` moves c0530 to `tracker/issues/active/c0530/`, `scripts/ci-verify.sh` on the pushed raft branch runs `setup-run.spec.luau` on ubuntu. The plan doesn't use it; it waits until after promotion, when a failure can only be fixed by changing an acceptance spec nobody re-reviews. Reading the spec I found no Linux-only failure (dash runs the stub, `sh -c 'command -v ...'` finds every basic under `/usr/bin`, GNU `env -i` searches the new `PATH`), so this is a missing proof, not a known bug.
Critique: the tempting fix is to say "run CI first" without saying what happens on red. Then the executor still edits the sequestered spec, just earlier.
Consequences: a red Linux run before `done` is a defect in a sequestered file, which execute-raft treats as a stop condition: escalate, re-prep, new design review. That must be said, or the executor will "fix" it.
Recommendation: add an Implementation step between 1 and 2: "after `tracker.sh start`, push the raft branch and run `scripts/ci-verify.sh`; the dispatch step runs `setup-run.spec.luau` on ubuntu. Green: continue. Red: stop and escalate (sequestered spec), do not edit it." Change E4 to this pass/fail question with that fallback, and reword R0230's Experiments and Risks to match.
