### F1 [high] `metrics.spec` fails the gate's type stage once promoted: a multi-return inside `t.expect`
Where: `acceptance/metrics.spec.luau:114` (since 8ce06609, design review 006's answer); AC8
Evidence: with the specs copied to `z-nile/tests/acceptance/c0118/` on the stack, the gate's own Lune type command (`z-nile/check.sh` line 174), `luau-lsp analyze --base-luaurc=.luaurc --platform=standard --ignore='**/.tracker/**' --ignore='**/.cache/**' z-nile/tests/acceptance/c0118`, exits 1:
`z-nile/tests/acceptance/c0118/metrics.spec.luau(114,12): TypeError: Argument count mismatch. Function 't.expect' expects 0 to 1 argument, but 2 are specified`
The line is `t.expect(string.find(b :: string, "return 1", 1, true)).toBe(nil)`: `string.find` returns two values. The six other c0118 specs type-check clean. The runner doesn't type-check, and the gate skips `.tracker/**`, so every run in prep (006's and 007's answers) was green.
Critique: after `./zn done` promotes the spec, `z-nile/check.sh --full` is red, and the executor may not edit a sequestered spec, so execution stops on a prep defect. This is exactly the defect c0120 had (six multi-returns inside `t.expect`) and that the lesson records.
Consequences: none beyond the one line: wrapping the call in parentheses keeps only the first value, which is `nil` on the intended body, so the assertion is unchanged.
Recommendation: write `t.expect((string.find(b :: string, "return 1", 1, true))).toBe(nil)`, then rerun the promotion dry run for all seven specs (copy to `z-nile/tests/acceptance/c0118/`, run the gate's type, format and lint commands there, plus the repo-fence allow-list scan) and record the run in the Verification log, as every later edit to a spec must be.
Lesson: z-design/rerun-skipped-checks-after-edits

### F2 [low] The call search counts a string literal as the call, and a pattern hoisted out of the body is never read
Where: `acceptance/metrics.spec.luau` `scan` ("Strings are kept in the code too, so a call inside one still reads as text") and `reads`; Rules row M76
Evidence: on the stack I replaced the intended `designRoundsIn` with c0116's counter whose pattern is a module-level constant `local DESIGN_ROUND = "^design%-review%-%d+%.md$"` declared just above the function, and added `local _note = "counted as boardview.rounds(paths) counts"` in the body. The spec gave 4 passed, 0 failed. Both halves are needed: the string satisfies "calls `boardview.rounds(`" because strings stay in `code`, and the literal outside the body is never collected.
Critique: unlike 007's comment evasion, this needs deliberate obfuscation (no honest executor puts the call's text in a string), so it is low. This is the third round on this source pin (006 F3 made it, 007 F2 found a hole). A source pin can't prove data flow: `local _ = boardview.rounds(paths)` with the count taken elsewhere would pass any text reading. The tempting fix, scanning all of `main.luau` for round-file patterns, hits z-raft's coherence-review readers, which are legitimately outside metrics.
Consequences: dropping strings from the call search changes nothing for the intended body (it has no string naming the call). Accepting the residual limit means the code review, not the spec, is the guard against a counter that calls `boardview.rounds` and ignores its result.
Recommendation: in `scan`, put a placeholder (`""`) into `code` for each string, not its text, and add a self-test sample `'local s = "boardview.rounds(paths)"'` expected `calls == false`. Then stop extending the pin: write in row M76 (or the AC8 note) that the pin catches an honest miss (c0116's counters kept, with or without a comment naming the call) and that a hoisted constant or a discarded call is left to the code review.
