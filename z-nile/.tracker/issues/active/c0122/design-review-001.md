### F3 [medium] The new rule promises "a check can fetch whether or not anything is new", but a pruning fetch is refused whole, and nothing says so or pins it
Where: Design item 1 (the new Ref guard sentence), item 2, Usability; AC1/AC2
Evidence: in a throwaway origin and clone fenced by `pickman_fence` as a check.sh flow, the origin deleted branch `x` and gained one commit. `git -c fetch.prune=true fetch origin` was then refused with `fence: a check tried to change refs in the real repository … refused` / `fatal: in 'prepared' phase, update aborted by the reference-transaction hook` (exit 128), and `refs/remotes/origin/main` did not move, so the new commit was not fetched either. With `--no-prune` the same fetch exited 0 and followed `main`. `fetch.prune=true` (or `remote.origin.prune`) is a common global setting. This user's machine doesn't set it today (`git config --get-all fetch.prune` is empty). This repository deletes branches after every merged PR, so on a machine with prune configured, every check that fetches fails as soon as any upstream branch is gone.
Critique: the issue's purpose is to state the rule check authors rely on ("a check author … learns that a fetch is fine whether or not anything is new"). As written, a check author on such a machine gets a refused fetch with no hint why. One tempting fix is to let the guard accept deletions during a fetch. That widens a guard against the captured Outcome ("a deleted ref … stays refused") and needs the user. The other is to leave the gap undocumented.
Consequences: documenting `--no-prune` adds one phrase for AC3 to pin. A real-git case for the pruning refusal also pins that a whole pruning fetch fails rather than partly applying. If git ever splits pruning into its own transaction, the case would show it.
Recommendation: keep the guard as it is. Extend item 1's sentence and item 2's line, for example: "… so a check can fetch whether or not anything is new, with `--no-prune`: a pruning fetch (`--prune`, or `fetch.prune` in any config) deletes refs and is refused whole". Add that phrase to AC3's wording case. Add to `refuse.spec` (AC2, check.sh flow): the origin deletes a branch the clone tracks and adds a commit; `-c fetch.prune=true fetch` is refused with the guard's message, and both tracking refs are unmoved. Add to `fetch.spec` (AC1): the same fetch with `--no-prune` succeeds and follows `main`. If the user would rather have pruning fetches accepted, that is a guard widening: escalate to the user as a new capture with a `Decided with the user` line. Don't decide it in this prep.
