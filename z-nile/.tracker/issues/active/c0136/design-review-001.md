### F1 [high] The folded c0140 rule only fires when a design step is named, so a design-phase mistake attributed to a topic skill gets a `when: build` lesson and passes
Where: Design, The rule, decisions 1 and 2; `lessons.check` (the `designStep` test); check.spec "a mistake design made or should have caught reaches design"; zz-review item 10 text in the patch.
Evidence: c0140's capture: "a lesson's when: is design or both whenever the defect could have been caught in design, and the reviewer checks it"; the Scope decision line says the same. Decision 1 lets `erred` be "a skill the author read for it (`zz-test` for a spec, …)", and decision 2 applies the `when` rule only when `erred` or `upstream` is in `DESIGN_STEPS`. A design review's finding is by definition a mistake made in design (or the capture), but on the prototype `- design-review-001 F1 (erred zz-test): zz-test/b` with `zz-test/b` `when: build` gives `lessons.check` = 0 problems (probe P1). The sequestered check.spec pins the hole as correct: `run("- design-review-001 F1 (erred zz-execute): zz-execute/build-only\n")` is expected to be `{}`, on a design review, where nothing was executed yet. For a weak sequestered spec found by a code review, "upstream" is "an earlier step", and design is not earlier than itself: the reviewer who follows the text names `zz-test` alone, and the next design's `--when design` pass never shows the lesson. The new zz-review item 10 sentence checks only "a lesson for a design step (`z-ticket`, `z-design`, `z-raft`)", so the reviewer's check has the same hole.
Critique: The capture's outcome is "could have been caught in design"; the design delivers "names a design step", and the most common design-phase mistakes (specs and check.sh written in prep under zz-test, code shape under zz-arch) are exactly the ones rule 1 invites to be named by their topic skill. The tempting fix is to tell reviewers to "prefer `z-design`", which leaves the check unchanged and the spec still pinning the wrong case.
Consequences: Keying the phase on the review kind needs one exception: a reviewer's own mistake found in a later design round (`erred zz-review`) is a reviewer lesson, and today's one design-review-harvested `when: build` lesson is exactly that (`zz-review/run-the-evidence-you-cite`; search: every lesson id on a `- design-review-NNN F<n>:` line of every tracked harvest.md, 162 ids, joined to each lesson's `when:`, gave that one id). A code or stream finding in a file design wrote cannot be told from the review kind, so it stays the reviewer's judgment and needs explicit text. c0112's backfill inherits the stricter rule, at near-zero migration cost by that search.
Recommendation: (1) In `lessons.check`, an entry from a `design-review-NNN` finding (issue design rounds and z-raft coherence rounds) whose `erred` is not `zz-review` or `none` is a design-phase mistake: each lesson it names is `when: design` or `both`, whatever skill is named. (2) zz-review's Attribute text and item 10 (both modes): when the mistake sits in something design wrote (the issue document, `check.sh`, a sequestered spec, a prototype the design copied), `Upstream:` names `z-design` (or the erring design step is `Erred:`), so the mechanical rule fires; z-design 5.3 and zz-execute Phase 4 step 5 say the same. (3) check.spec: replace the `(erred zz-execute): zz-execute/build-only` on-a-design-review expectation with a refusal; add `(erred zz-test): <build lesson>` from a design review refused, `(erred zz-review): <build lesson>` from a design review accepted, and the same `(erred zz-test)` build line from a `review-NNN` accepted (so a mutant that judges every review kind dies). (4) A Rules and mutants row and a mutant that drops the review-kind test.
Lesson: z-design/never-narrow-captured-scope

### F2 [high] A bad step line in a committed review turns `lessons --check` red for good, and no allowed edit clears it
Where: `lessons.findingSteps` and the review-file loop in `lessons.check`; decision 3; z-design 5.5, z-raft and zz-execute Phase 5 ("must pass"); zz-review raft mode and z-raft ("a review file is never edited after it is written").
Evidence: Probes on the prototype, each against `lessons.check` with a one-finding design review: (P2) the reviewer types `Erred: z-desgin` (`findingSteps` accepts any kebab word): the entry that copies it gets `no skill z-desgin`, the entry that corrects it gets `the line says (erred z-design) but design-review-001.md F1 says Erred: z-desgin`. (P3) the reviewer writes the same skill on both lines: `findingSteps` accepts it, the copying entry is refused by `parseSteps` (`upstream is the same step as erred`), the corrected entry is refused as differing. (P5) the reviewer leaves one line off F2: `c0010/design-review-001.md F2: write both Erred: and Upstream:` whatever the harvest says. (P7) a finding whose Evidence quotes the template in a fenced block, a line `Erred: <skill, or none>` at column 0 inside the fence, gets `F1: Erred: needs a skill name or none`; reviews of z-nile's own tooling (this issue's code review included) quote templates often. (P8) a column-0 step line after the last finding (a Judged section) is charged to the last finding as `Erred: is repeated`. In each case the only fix is editing the reviewer's file.
Critique: The rule "the reviewer's lines are the entry's" assumes a reviewer never writes a bad line; a Sonnet stream reviewer or a long Opus round will. The confirmation steps then cannot pass without breaking the never-edit rule, and once c0112 puts whole-tree coverage in the gate, a tree-wide check that includes these problems blocks everyone. The tempting fix is "the author may edit the lines", which undoes the point of the reviewer's attribution.
Consequences: Validating at write time needs the writer to run a command: a reviewer subagent may run read-only `./zn lessons --check` from its worktree, and the lead writes stream and focused files itself. Files already committed still need a way out that keeps the reviewer's record. The parser must agree with `parseSteps` (one rule set for both spellings of the group), or the two forms disagree again.
Recommendation: (1) One validator for both forms: `findingSteps` passes each finding's pair through the same rules as `parseSteps` (`none` only as Erred, no upstream with `Erred: none`, Upstream differs from Erred), plus, in `check`, that each named step is a skill. (2) `findingSteps` skips fenced code blocks and ends a finding's block at the next `## ` heading. (3) zz-review: the reviewer runs `./zn lessons --check` on its file before it ends (read-only; it names its own file's problems) and fixes its own lines; the lead does the same before committing a stream or focused file. (4) A recovery for a committed bad file, decided and pinned: the preferred one is that a finding whose lines are invalid binds nothing, its entry carries the author's own group, and the file's problem is cleared by a harvest note naming it (`- note <stem> F<n> step lines invalid (erred zz-review): zz-review/<lesson>`); the alternative is that a new focused round restates the lines. (5) Cases in parse.spec and check.spec for P2, P3, P5 (with the recovery), P7 and P8, each with its Rules and mutants row.
Lesson: zz-arch/parsers-refuse-ambiguity
