### F1 [high] Two ordinary harvest paths carry a design-phase finding past the folded c0140 rule, because the phase is read from the entry's stem (same mechanism as design-review-001 F1)
Where: Design, The rule, decisions 2 and 3 (the author's disagreement note); the Focused review row of the sources table; `lessons.check` (`designReview` is `not e.note and e.review starts "design-review-"`); zz-review Focused mode in the patch.
Evidence: Probes on the prototype, `lessons.check` with the review's F1 carrying the lines for `z-design` and `none`. (Q1) `- design-review-001 F1 (erred z-design): one-off: see the note` plus `- note design-review-001 F1 the author disagrees (erred zz-test): zz-test/build-only` gives 0 problems: decision 3 itself tells the author who disagrees to add such a note, and a note is never a design review entry. (Q2) a `focused-review-001.md` in an issue's folder during prep (the capture's "the review of a review's own recommendation", "focused reviews of a rework", both of which happen between design rounds) with `- focused-review-001 F1 (erred zz-test): zz-test/build-only` gives 0 problems: the stem is not `design-review-`. (Q9) a design-review finding the reviewer marks `none`, answered `(erred none): one-off` plus a note naming `zz-execute/build-only`, also passes. In each case the lesson stays `when: build` and the next design's `--when design` pass never shows it, which is what the Scope decision line says must not happen.
Critique: Round 1 found that naming a topic skill escaped the rule; the fix keyed the phase on the file kind, and the two paths that are not a `design-review-NNN` entry (a note, a focused review) escape it the same way. The tempting fix is one more special case in `check` (a note whose text starts with `design-review-`), which leaves focused reviews and every future source kind to the next round.
Consequences: The phase has to be a fact the record carries, not a guess from the file name. A note that answers a finding needs a fixed head the engine can read (the waiver already reads `<stem> F<n>` from a note's text: one reader for both). A focused review needs a phase: the file is the lead's, written from the reviewer's text, so the heading can carry it (`# Review NNN: <id> (focused mode, design)`), and a focused file with no phase is then a problem. A note about a finding that does not use the fixed head stays unjudged: say so, and let the next reviewer judge it (item 10).
Recommendation: (1) One rule, "a finding of a design-phase review": a `design-review-NNN` round, or a `focused-review-NNN` whose heading says `design`; `check` applies the `when` rule to every entry answering one and to every note whose text starts `<stem> F<n>` of one (unless `erred zz-review`). (2) zz-review Focused mode and zz-rules Items: the heading's phase (`design` or `build`), and the note head for an author's disagreement or a further lesson of a finding (`- note <stem> F<n> <text> (erred …): …`). (3) check.spec cases: Q1, Q2 and Q9 refused; a `focused-review` marked `build` with a `zz-test` build lesson accepted; a disagreement note with a design lesson accepted; sources.spec: a focused file with no phase is a problem. (4) Rows and mutants: the note head ignored, the focused phase ignored, every focused review treated as design.
Lesson: z-design/never-narrow-captured-scope

### F5 [medium] Step names written into never-edited review files break for good when a skill is renamed or retired
Where: `findingSteps` (`Erred: no skill <x>` when `tree.skills` lacks it); the group check in `lessons.check` (`no skill <step>`); the filing rule; Maintainability ("a new skill is a step with no change").
Evidence: Every skill was renamed a month ago (c0115: `skills.RENAMED` maps eleven old names, `review = "zz-review"`, `testing = "zz-test"`, …), and its rename script (`lessons.renameLedger` through `ledgerLine`) renames lesson ids in ledgers but treats the rest of a line as prose, renaming only `<old>/<slug>` tokens, so a bare `(erred testing)` group would stay. Recommendation: `findingSteps`' skill test and `check`'s group and filing tests resolve a step through `skills.RENAMED` first; `ledgerLine` renames a group's step names as it renames ids; decide the retired-skill rule. parse.spec and check.spec cases: a review line and a group naming `testing` bind as `zz-test`, a lesson `zz-test/x` filed under it is accepted, and a renamed ledger's group names the new skill; rows and mutants.
