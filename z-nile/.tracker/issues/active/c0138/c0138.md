# c0138: Trail compaction reset

## Problem
trail.read starts an item's life at every commit that changed the compaction map and the item's document, so a compaction that keeps an id but rewrites its document in place (compact rewrites every kept document that names a renumbered id) cuts that item's history: capture and its first-review lookups then stop at the compaction for an item whose identity never changed. c0118's history reader decides from the map's own pairs instead (c0118 design review 002 F1).

## Non-goals
- Changing c0118's history reader (`history.luau`), which already reads the map's pairs.
- Following an id change (prep, from the Problem and the R0042 decision): the trail still reads the item's current id only, and a renamed id's history before the compaction stays unfollowed and marked (R0042 design review 013, the user's "Never cross; mark it"). This chore only stops marking an item the map does not rename.
- The `capture` output format: the marker text, the other markers and their order stay as they are.

## Solution
- In `trail.read`, start a new life only for an item whose id is named on either side of a changed pair (X ≠ Y) in the map lines the compaction commit adds, read with `ids.parseMap`; keep the current reset for every touched item when a map line does not parse.
- Spec it on a fixture whose compaction rewrites a kept item's document in place (its capture and first review still found across the compaction) and reuses a done id for another item (its capture stops there).
- Prep detail (added at design, 2026-11-01; the bullets above were added at capture time in b37679dc, 14 s after the capture commit 7769d615, whose Solution is empty): "the map lines the compaction commit adds" is read as the map as that commit leaves it (`git show <sha>:<map file>`, for the map file or files the commit changed), parsed whole by `ids.parseMap`. `compact` writes its whole map each time (`ids.formatMap` over `ids.plan`, only that compaction's pairs), so for a compaction the lines it adds are exactly the map as committed. The one difference from a `--unified=0` reading is a pair repeated word for word from the previous map, which a diff drops and the whole map keeps (c0118 design reviews 003 F2 and 004 F1 found that hole in three forms of the diff reading); the whole map is the safer side, because the extra reset is the marked, conservative answer.

## Design
**The rule.** `trail.read` finds an item's last life: it starts where the document last went from absent to present (`life`), or at a later commit that changed a compaction map and the item's document (`since`). Today every such commit starts a life. After this chore, such a commit starts one only when it **renamed the item's id**:

- the commit's compaction map, read whole as the commit leaves it, holds a pair `X Y` with X ≠ Y and the item's id is X or Y (an id on either side: Y is an id now naming a renumbered or reused item, X is an id renumbered away that the counter will hand out again); or
- a map the commit leaves does not parse (`ids.parseMap` returns nil), or git can't list or read it: then every item the commit touches restarts, exactly as today (an unreadable map means "reset", zz-arch rule 7).

A compaction that keeps an id and rewrites its document in place because the document names a renumbered id (`compact.apply` rewrites every kept `.md` and `.sh` under a root) starts nothing: the item's capture and its review files are found across it.

Two consequences the specs pin. (1) A commit's answer comes from the map that commit leaves and from no other: a pair an earlier map had and this commit's map lacks renames nothing, so a second compaction whose whole map keeps an id (`X X`) does not restart an item that the first one renamed and that the second rewrites in place; the restart stays at the first compaction (design review 001 F1). (2) The marker is kept as today for any life that starts at a map-changing commit, whether the map names the id or not: an item first appearing in a commit that also edited the map is marked, because the walk stops there (design review 001 F2). A rewrite in place has no start, so it has no marker.

**Prototype.** `proto-c0138`, on the base `20eb19ac` (this prep's base is `c199e8de`; `git diff 20eb19ac origin/main` of the Touched files and the specs that read them is empty, rechecked after the last edit). `prototype.patch` in this folder is the engine, skill-row and lesson edits (110 changed lines; the acceptance specs are the folder's own).

**Code** (`z-nile/engine/ids.luau` and `z-nile/engine/trail.luau`; `ids.parseMap` stays the map's one reader):
- `ids.renamedIn(map: { [string]: string }): { [string]: boolean }` (pure, in `ids.luau` beside `parseMap`): the ids on either side of a pair with X ≠ Y. A pair whose sides agree names nothing.
- `trail.renamed(maps: { string }): { [string]: boolean }?` (pure): each map text of `maps` parsed whole by `ids.parseMap` and its `ids.renamedIn` joined; nil when any text does not parse. A comment names nothing. An empty or comment-only map gives `{}` (not nil).
- `trail.resets(renamed: { [string]: boolean }?, id: string): boolean` (pure): true when `renamed` is nil (unreadable) or names `id`.
- `trail.renames(sha: string): { [string]: boolean }?` (reads git): `git diff-tree --root -r --no-renames --diff-filter=AM --name-only --no-commit-id <sha> -- <ids.MAP_FILES>` lists the map files the commit added or changed (the filter `trail.cuts` uses, without its `-M`), `git show <sha>:<file>` reads each as the commit leaves it, and `trail.renamed` judges the texts. Nil (so the caller resets) when `diff-tree` or a `show` fails, or the commit changed no map file. A map file the commit left alone or deleted is not read: a `tracker/compaction.txt` that stays in a tree beside the current map (the fixture's shape; on main the old file moved away in 05b058ea, so the two never coexist there) does not name ids for a later compaction. When a commit changes more than one map file, every one is read and the ids joined (a parse failure of any one resets).
- `trail.read`: a `cutsId(sha)` closure (a cut commit, and `trail.resets(trail.renames(sha), id)`, memoised per call so `renames` runs once per commit and only for a commit that changed the item's document; an optimisation no result depends on) replaces `cuts[c.sha] ~= nil` in `since`'s predicate. The note (`(history before <sha> not followed: it changed <map file>)`) keeps its condition (`cuts[start.sha]`): a life that starts at a map-changing commit (a first add there) is marked as today; an item merely rewritten in place has no such start, so it has no marker.
- Unchanged: `trail.cuts`, `life`, `since`, `capture`, `ambiguous`, the marker texts, `cmd.capture` in `main.luau`.

**Data flow.** `cmd.capture` -> `trail.read(kind, id, trail.isDoc, head)` -> `trail.cuts(head)` (one `git log`) -> `changes` (one `git log` of the item's folders) -> `life` -> `since` (calls `cutsId` newest first until a commit starts a life) -> note. The one new git cost is the `diff-tree` and `show` per cut commit that changed the item's document.

**Decision for the user (flagged, not asked: it changes no outcome).** The captured Solution says "the map lines the compaction commit adds". Read literally as a diff's `+` lines, it misses a pair repeated word for word (c0118 found it three times) and treats a header-only edit of the map as renaming nothing. Reading the whole map keeps c0119's existing header-edit case as it is (c0008's `fix` commit still marks) and matches c0118's reader, so the two readers answer alike. If the user prefers the literal diff reading, the changes are: `trail.renames` runs `git diff-tree -p -U0` and keeps the `+` lines (prototype mutant M7), c0119's `starts a life at the last appearance or at a commit that changed the map and the document` case (the `fix` commit's c0008 assertions) becomes an override, and the Rules table gains rows for header-only edits.

### Scalability
Per `capture` (the only caller of `trail.read` today): the two `git log` calls as now, plus one `git diff-tree` and one `git show` per map file for each cut commit that changed the item's document, normally none or one (the repository has had one compaction), at most the number of compactions that touched the item. Memoised per call. Spec cost: `kept.spec` builds a 23-commit fixture and runs eighteen `capture` calls and two scripts: about 12 to 22 s of wall time (E6); `renamed.spec` and `docs.spec` are 0.1 s. The gate already runs the three promoted trail specs; this adds one fixture spec.

### Maintainability
The decision "which ids did this map rename" is one pure function, `trail.renamed`, over `ids.parseMap` (the map's one reader, zz-arch rule 5); history's reader (c0118) answers the same question from the same reader in its own module. A later change of the map format changes `ids.parseMap` and `formatMap` only. `renames` is the only new git call, and the next kind of cut (another map file) joins `ids.MAP_FILES`, which `cuts` and `renames` both read.

### Usability
No command line changes. The user sees fewer `(history before … not followed …)` markers, only on items the map does not rename, and `./zn ready`'s scope check (a marked capture counts as unconfirmed until a `Scope decision`) stops asking about those. The marker text is unchanged. A map the reader can't read is still marked, so the user still hears about a broken map.
