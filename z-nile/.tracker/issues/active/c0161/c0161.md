# c0161: Closure skips design review

## Problem
z-design: a defect the user closes because it does not reproduce (no code change) skips the design review and goes straight to a raft

Decided with the user (2026-11-01): "Design record". Each design round quotes a record (a hash) of the design it read, so any change to the design after an approving round needs a new round: that covers a scope reset in place and a closure decided inside the same prep after a fix design was approved. It brings a zz-review format change, a reader for the record and a re-record step after compact, remap and renumber. (Relayed by the lead after the design review's round 2 F1.)

Decided with the user (2026-11-01): "Reviewer-only record". The newest round must be `approve` and quote the current design record; answering any round's findings by an edit needs a new round, and the author writes no record. The cost, one more Opus round in most preps, is accepted. (Relayed by the lead after the design review's round 3 F1 and F2.)

Decided with the user (2026-11-01): "Check at next read". When a prepared issue is next read by `new raft`, `fold` (and `recombine`, which shares its check) or `ready`, its newest round's quoted record is compared with its record as on origin/main; the issues prepared by the old engine are exempt, found by search and not by hand, and the check uses the one shared reader of the round's lines. (Relayed by the lead after the design review's round 4 F7; it replaces the `audit` error the earlier decision had left out.)

Decided with the user (2026-11-01): "Fix + round 6". Design review round 5 (the final round) found a high finding (AC7 could be passed by a wrong implementation); the user chose to fix all its findings and run a sixth round past the cap.

Decided with the user (2026-11-01): "Fix + round 7". Design review round 6 found a high finding (AC7's `raft-plan` take side could be passed by a wrong implementation); the user chose to fix all its findings and run a seventh round past the cap.

## Non-goals
- Judging what a review concluded. The engine checks that a round of this design was run and answered, never that it was right: a forged `design-review-001.md` that quotes the right hash passes, as a hand-set `design: ready` passes today (accepted risk 1).
- An `audit` error for backlog issues that are prepared with no review round. Not added: the user's "Check at next read" decision puts the comparison where an issue is next read (`new raft`, `fold`, `recombine`, `ready`), which catches a design edited after the move to prepared before the issue is rafted or readied. What stays open is in accepted risks 1 and 2 (an engine that predates the rule, a garbled `status:` line, `release`, a removed untracked round).
- The `status <id> prepared` edit made by hand when there is no origin (`PICKMAN_PUBLISH=0`), which z-design 5.5 allows.
- `stop` and `release`: they give back items that were prepared already, and the move rule is on the move that makes an item prepared. (`ready` runs the check at next read, Design part 5; it does not run the move rule.)
- A fifth reader of the record: the carried raft move (`status <R-id> prepared`) does not run `preparedRead` on the prepared members of its local folder, so a rafting PR can still carry a stale member; `ready` catches it. It would cut nothing, but it adds a reader to the four the user's decision "Check at next read" names; left out (design review 006 F2, optional), and the recovery is written instead (Design part 5).
- A shared reader for `### F<n>` headings with `lessons.findings`: `status.luau` has no requires and `lessons.luau` loads the filesystem; the copy names its twin (Maintainability).

## Design
**What happened (the cause).** d0151 ("Touch input reaches nothing on a phone") was closed on 2026-10-26 by the user's decision: it did not reproduce, so its Design said "No code change". c0161 was captured at 15:46 that day, before d0151's design review ran (its first spend row is 15:57), so the closure was on its way to a raft with no review. Two things allowed it: z-design names no closure path, so "no code" read as "nothing to review"; and nothing refuses it, because the move to `prepared` (`setStatus`, `z-nile/engine/main.luau`) checks `design: ready` only, a field the author sets by hand (z-design step 5.5). The review that finally ran (`d0151/design-review-001.md`) found a closure-specific defect (F1: the author's reading of "nothing shows on the screen" sat inside the user's `Scope decision` line) and two missing records (F2: the build played; F4: the conditions of both reports), so skipping it was not harmless.

**The fix has four parts, so the step sits on every path and cannot be satisfied by an old approval or by the author (lesson z-design/required-steps-on-every-path: "does something notice if it was skipped?"; round 3: "who writes the record this check trusts?").**

1. **The design record.** `raftplan.recordPaths(id, files, specsOnly)` is the one list of the files a design review round reads, sorted: the issue's document, `check.sh`, everything under `acceptance/` and everything under `experiments/` (an executor applies the prototype patches kept there; round 3 F6), and with `specsOnly` just `check.sh` and `acceptance/`. Not the reviews, refutes and `harvest.md` (they answer the design, they are not it), `spend.md` or `prompt.md`. `raftplan.designRecord(id, files)` is twelve hex digits over those paths, each with its length and bytes, the document without its `status:`, `raft:` and `design:` lines (the lines the process itself writes as the design is reviewed and prepared). It shares one frontmatter filter with `designHash` (`withoutFront`, byte-identical output for the existing `grouped:` hashes; pinned). The command `./zn design-record <issue-id>` (read-only, like `capture`; refuses anything but an issue id) prints it for the work tree as git sees it (tracked, and untracked that are not ignored). Outputs written after the final round (a mutation log) go to `.cache/`, not the item folder, or they stale the record.
2. **The quote, by the reviewer only.** The reviewer runs `./zn design-record <id>` before reading, in the prep worktree that holds the design (the command refuses in the main checkout, where no preparing design lives, so a subagent whose shell starts there is told instead of hashing another copy; design review 004 F4), and ends the round with one `Design record: <hash>` line (that output) and one `Verdict:` line, each at the start of a line, then runs it again when finished: if it differs the reviewer says so under `Inputs:` (the design changed under the round, which is then stale). A round is never edited, so a Design changed after it needs a new round. The author writes no record anywhere. Everything under `experiments/` is part of the record, so a log or note written after a round goes to `.cache/` or to the item folder's top level (this issue's `proposed-lessons.md` is there, beside the issue), never under `experiments/` (execution writes there after `prepared`, which is harmless).
3. **The refusal.** A pure rule `status.designReviewProblem(files, record)` in `z-nile/engine/status.luau` (no I/O; `files` is an issue folder's files, path relative to the folder, as `gitFolderFiles` returns them; `record` is the design's record now). It returns nil only when the folder's newest round approves and quotes the design as it is, else a problem that starts with the file it is about:
   - Rounds are the top-level files named `design-review-NNN.md` (three digits, anchored; a file in a sub folder, a `.bak` copy and `review-NNN.md` are not rounds). The newest round is the highest NNN.
   - No round: `has no design-review-001.md: z-design step 5 runs at least one clean review round on every issue before `prepared`, a closure (no code change) included`.
   - **One reader of the round's lines.** `status.roundLines(text)` returns the verdict, the quoted hash and a problem. A round is written once (zz-review), so a second `Verdict: ` line or a second `Design record: ` line (each at the start of a line) is refused, whichever it says and wherever it sits (`<file> has two "Design record:" lines: a round is written once (zz-review)`), and so is a `Design record:` line with anything after the hash (`… not just the hash`). No round in `origin/main`'s 441 design rounds has a second `Verdict:` line, so this costs nothing (design review 004 F3). The move to prepared, the check at the next read and the re-record after an id rewrite all read the lines through it. Only `approve` passes. `changes` is refused: `<file> says "Verdict: changes": the final round approves, so answer it by editing the design and running the next round (z-design step 5.4); a refute alone does not stand in for it`; anything else, or no such line: `<file> has no "Verdict: approve" or "Verdict: changes" line (zz-review's format)`.
   - The round's one `Design record: <hash>` line must equal `record`. No line: `<file> quotes no "Design record: <hash>" line: the reviewer ends the round with the output of ./zn design-record <id>`. A different hash: `<file> quotes Design record <h>, but the design is now <h2>: it changed after this round, or the round quoted another checkout's design; make it current with a design round for this issue, run in the worktree that holds the edit and landed with it (z-design 5.3: a Design changed after a round, or by answering one, needs a new round; for a rafted member: unfold it with the edit and the round, land, then fold it again: z-raft 2)`. So a reclaimed prepared issue whose rounds are on `origin/main` (no record, or an old design's), a scope reset in place (the earlier scope's rounds, still in the worktree), a reviewed fix design rewritten into "No code change", and a design edited to answer a `changes` round all meet the refusal; nothing is compared with `origin/main`.
   - Refutes, `harvest.md` and `spend.md` are not read: only a reviewer's word counts. The engine cannot tell what a review judged, only that a reviewer's round of this design approved it. `done`'s `reviewProblem` reads code-mode `review-NNN.md` and `refute-NNN.md` and is left as it is; the round-name pattern is `lessons.isStem`'s and the finding convention `### F<n>` is `lessons.findings`' (named in the code comment and in Maintainability).

   The call: in `setStatus` (`z-nile/engine/main.luau`, the `if carried then` block that already refuses a member that is not `design: ready`), for every target that is not a raft, refusing `{t} {problem}`: `own = gitFolderFiles(localItem.dir)`, `statusLib.designReviewProblem(own, raftplan.designRecord(t, own))`. `own` is the work tree as git sees it, the same view the raft coherence review check uses, so z-design's order works: reviews, `design: ready`, `status <id> prepared`, then the commit. The loop's earlier `continue` for a member already `prepared` on `origin/main` means a prepared issue is taken as it is. The raft's own folder is not asked for itself (its own rule is the coherence review), and it is **no stand-in for a member's**: the old prep kept a member's reviews there, and a `preparing` member of the old prep (`new raft` over `new` issues) needs its own approving round like any issue (round 3 F3: R0044, the one raft that needed the fallback, was released and readied on 2026-11-01 and no `preparing` issue on `origin/main` sits in a raft). The refusal names the issue, the file and the rule (zz-arch rule 8). It reads only the local work tree; it widens no guard (zz-arch rule 7 is about guard configuration).
4. **The re-record.** A mechanical rewrite of ids (`compact`, `remap`, `renumber`) changes the ids inside a design, so it would stale every quoted record. `keepRecords` (`z-nile/engine/main.luau`, which already re-records `grouped:` entries and the `Grouped:` lines of coherence reviews) also finds, before the rewrite, in every issue (renamed or not: the rewrite changes any design that names a renamed id) the quote of each `design-review-*.md` that equals the issue's record (read through `status.roundLines`), and after the rewrite replaces exactly those quote lines (`status.rewriteRecord`, line-based) with the issue's new record. A line that did not match before still does not (an older round's, or a forged one). It runs **before** the `grouped:` re-record (a member's grouped hash covers its reviews, so it must see the re-recorded lines; pinned by a case and mutant K7), works on the work tree as git sees it (a prep's reviews are not committed until its prep commit, and `renumber`, unlike `compact` and `remap`, runs on a dirty tree), and reads only the folders whose listing holds a `design-review-` file.

5. **Check at next read** (the user's decision "Check at next read", 2026-11-01). The move to prepared is the only place the record is compared, and a design can change after it (a gate fix, a Design sentence added while answering a PR comment, a conflict resolved in the document). So `new raft` (each prepared member), `fold` and `recombine` (both through `refuseUnraftable`, which reads the issue as it is on `origin/main` with `originFolderFiles`) and `ready` (each member, in the callback that already compares `grouped:` records, from the tree being published) also run `status.preparedReadProblem(files, record)`: when any of the issue's rounds quotes a `Design record:`, the newest round must say `approve` and quote the issue's record as it is on `origin/main`, else `<id> is prepared on origin/main but <file> …` (the rule above, reused). **An issue none of whose rounds quotes a record is exempt**: the engine that prepared it predates the rule, and every issue prepared by the new engine has a quote (the move refuses otherwise). The exempt set is found by search at execution, not listed by hand: the search in Existing work finds 30 prepared issues today and all 30 are exempt. One shared function (`preparedRead` in `main.luau`) serves the four callers, and `raft-plan` (which composes `new raft` and `fold` commands) puts a stale prepared, raftless issue on its skip list instead of planning it (`skip <id>: is prepared on origin/main but <file> …`, the one message of the rule, which already names the recovery; `raftplan.Issue` gains an optional `stale` field, so `--apply` cannot stop half way after earlier commands published their claims; design review 005 F2). `raft-plan` computes `stale` only when `origin/main` exists (`git rev-parse --verify -q origin/main`): with no origin remote it prints the plan as before, and the commands it prints (`new raft`, `fold`) refuse there on their own (design review 006 F4). `fold` and `recombine` read the issue as it is on `origin/main` (`originFolderFiles`), so a local committed edit that is not there does not stale it (it is judged at `ready`; a case pins it). The check is not run at `audit`, `list` or `status`.

   **The recovery (design review 006 F2).** A stale prepared issue is made current by a **design round for it**: an approving round that quotes its record (`./zn design-record <id>`, which works in any worktree but the main checkout), run in the worktree that holds the edit and landed with it. z-raft's own member-fix path (lesson z-raft/rafted-member-changes-stay-in-the-raft) lands exactly this state: the member is changed in the rafting branch, and `ready` then refuses it. **A rafted member takes two landings** (design review 007 F1, run end to end in `review-read`): `recordGrouped` hashes the member as it is on `origin/main`, so an edit or a round that exists only in the rafting branch never reaches `grouped:`, `fold` refuses a member whose `raft:` on `origin/main` still names a raft, and a plain re-fold lands a raft that `ready` refuses ("changed on origin/main since … grouped it"). The path that works: (1) in a rafting worktree `unfold <R-id> <id>`, make the member's edit, add its approving round (`./zn design-record <id>`, which works in any worktree but the main checkout), `status <R-id> prepared` (the raft stays prepared without the member), and land; (2) in a second rafting worktree `fold <R-id> <id>` (it records the landed design), the coherence review when the raft has several members, `status <R-id> prepared`, and land. **The cost is one extra PR per in-raft member fix.** A chore that edits another prepared issue's design files (R0078 is such a raft: c0173 edits c0075's and c0174 edits c0083's design documents and specs) runs the same round for the edited issue in its own worktree. A prepared issue with no raft is made current by a round landed with its edit, as before. The sentence is written in z-raft §1 (the skip) and §2, z-ready step 2, zz-rules (Rafting bullet), z-design 5.3 and the refusal text, and pinned in `docs.spec` and `review-rule`; cases in `review-read` pin that an approving `design-review-002.md` quoting the edited record lets `new raft`, `fold` and `ready` take the issue (each with its own issue), and walk the rafted-member recovery through rafting worktrees: the naive path (edit and round inside the landed raft) is refused by `ready` on `grouped:`, the two landings are taken.

### Scalability
One `git ls-files` in the issue's folder and the reads of its files, plus one hash over the design files, per issue moved to prepared: the calls the raft coherence check already makes per carried raft move. `keepRecords` lists each issue folder with `fs.readDir` (no git call) and runs `gitFolderFiles` only for folders that hold a `design-review-` file, twice (before and after the rewrite): about 84 of the 212 issue folders on `origin/main` today, on every `renumber`, and twice per `remap` (the branch and its scratch base); compaction runs rarely. `status` listing, `audit` and `list` are unchanged. `ready` hashes each member's folder once more (the files it already reads), `fold` and `recombine` list and read each issue's folder on `origin/main` a second time (`originFolderFiles`, beside `recordGrouped`'s), and `raft-plan` does the same once per prepared, raftless issue (about 30 today).
### Maintainability
The rule lives in `status.luau` beside the other pure status rules, takes a table of texts and a record, and has one reader of the round format (`design-review-NNN.md`, `Verdict:`, `Design record:`) that the pure spec pins in every shape. Its round-name pattern is `lessons.isStem`'s, which cannot be required from a module with no requires; the comment in `status.luau` names it. The record's file list is one function, `raftplan.recordPaths`, beside the other design-file lists in `raftplan.luau` (`isDesignFile`, `recordHash`); it says why its list differs from `recordHash`'s (the quote lives in the reviews, which `recordHash` includes; the prototypes in `experiments/` are what an executor applies), and c0181's spec proof reuses it.
### Usability
Every refusal names the issue, the file that is missing, illegible, still asking for changes or stale, and the step of z-design that explains it, so the person fixes it without reading the code. The extra work is one command (`./zn design-record <id>`) for the reviewer, and, for the author, a new round whenever the design changes after one. Offline (no origin remote), `raft-plan` prints its plan as before (it checks the record only when `origin/main` exists) and every other command behaves as before; `status` itself refuses to run there.
