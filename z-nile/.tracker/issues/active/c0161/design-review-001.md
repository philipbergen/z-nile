### F1 [high] An earlier cycle's round satisfies the rule, so a closure decided in a re-prep reaches a raft with no review of the closure
Where: Design part 1 ("The newest round is the highest NNN (so a re-prep after a scope reset, whose count restarts, is judged by its newest file)"); `status.designReviewProblem`; `setStatus`'s call.
Evidence: `status.canMove("prepared", "preparing")` is allowed, so a prepared issue with no raft is reclaimed with `./zn status <id> preparing` and redesigned. Its folder still holds the earlier prep's rounds, which are tracked and so in `gitFolderFiles`. Take a defect prepared with a fix design (`design-review-002.md`, `Verdict: approve`). The user retests, it does not reproduce, and the author reclaims it, rewrites the Design to "No code change", sets `design: ready` and runs `status <id> prepared`. The rule reads `design-review-002.md`, finds `approve`, and returns nil. Nobody reviewed the closure, which is the captured Problem: a closure "skips the design review and goes straight to a raft". The re-prep is a live path today. c0181 (`prep-lessons-codify-consolidate`) is a re-prep after a user scope reset: rounds 001 to 005 judged the earlier scope, and its new round 1 is `design-review-006.md`. Before that file exists, the rule would pass c0181 on round 005. The Design's sentence "is judged by its newest file" assumes the re-prep has written a new file. The rule doesn't check that it has. The same gap exists inside one prep: round 1 approves a fix design, then the user's retest turns it into a closure, and the old approval passes.
Critique: an existence check passes on what an earlier cycle of the same item left. The tempting fix is a sentence in z-design ("a re-prep runs a new round"). The engine still wouldn't notice the skip, which is the d0151 failure this issue exists to close (lesson z-design/required-steps-on-every-path: "does something notice if it was skipped?").
Consequences: the engine needs to know which rounds belong to this prep. The origin tree is already in hand in `setStatus` (`paths`, `read`, `treeFolderFiles`). Rounds written in this prep ride in the prep commit made after the move, so they are never on `origin/main` when the move runs. That brings these states and decisions:
- a first prep (no round on origin) behaves as designed;
- a re-prep needs at least one round newer than origin's newest (z-design 5.4 already says a re-prep's count restarts);
- a prep PR that landed rounds without the move needs a new round on the next attempt (state it);
- the legacy raft route keeps its rounds on origin (see F2), so the comparison must not apply there;
- a Design changed after its approving round inside one prep is still not caught. Either make it an accepted risk with a checkable premise (z-design 5.4 forbids it; nothing checks it), or have the reviewer quote a record of the design it read, as raft mode's `Grouped:` record does (`reviewCovers`), at the cost of a new review line and its reader. That choice changes the review format, so it goes to the user.
Recommendation: make the rule `designReviewProblem(files, originFiles)`. When `originFiles` holds a round, the newest local round must have a higher number than origin's newest, else `design-review-NNN.md is from an earlier prep (it is on origin/main): run a new round for this design (z-design step 5; a re-prep restarts the count)`. The call passes `treeFolderFiles(paths, read, <the folder of tp>)`. Spec cases:
- pure: origin has no rounds (as today); origin's newest equals the local newest (refused, naming the file); the local newest is one higher (passes); origin has 005 approve and local has 005 approve plus 006 changes with its refute (passes); a legacy-raft exemption case per F2.
- review-gate: "a reclaimed prepared issue whose approving round is on origin/main is refused until a newer round exists", driven through `status <id> preparing` from prepared, then `prepared`.
- Rules and mutants rows: "origin's rounds ignored", "`>=` for `>`", "origin read from the working tree".
Update the docs pins (z-design 5.5, zz-rules) to say the newest round is one written in this prep, and record the same-prep accepted risk, or the record-hash option, with the user's choice.
Lesson: zz-arch/records-cover-what-was-reviewed

### F2 [high] The legacy route the Design keeps is refused for the one raft on it: R0044's member d0124 has five review rounds, in its raft's folder
Where: Design part 1 ("Targets reaching the new line: … the `preparing` members a raft's carried move takes (the old prep's `new raft` over `new` issues, still supported)"); Chore checklist, Existing work ("A legacy raft made over `new` issues (R0044, `preparing`, [d0124]) will need d0124's round when it is prepared; the claim is the raft's, not a prepared one").
Evidence: on `origin/main`, `pickman/.tracker/rafts/R0044/` holds `design-review-001.md` to `005.md` with `design-refute-001.md` to `005.md`, and R0044 and d0124 are both `design: ready` and `preparing-sunny-falcon-sunny`. `pickman/.tracker/issues/d0124/` holds no review. The old prep reviewed the raft and its issues together and wrote the rounds in the raft's folder, as zz-review's Output file still describes for raft-level design rounds. With the prototype, `status R0044 prepared` reaches d0124 as a `preparing` target. It calls `designReviewProblem(gitFolderFiles(d0124's folder))` and refuses: "d0124 has no design-review-001.md: z-design step 5 runs at least one clean review round on every issue…". The Design calls this "will need d0124's round", but d0124 had five rounds. The refusal demands a sixth review of a reviewed design, which no `Decided with the user` line accepts. review-raft's first case pins the member's own folder only, so it encodes the regression.
Critique: the rule looks for the review where the new flow writes it. The old flow, which zz-rules calls still supported, writes it in the raft's folder. The tempting fix is to also accept any round in the raft's folder. That would let a new-flow raft's coherence review (raft mode, also `design-review-NNN.md` in the raft's folder) stand in for a member's design review.

A member claimed in this checkout by `status <id> preparing` (`rememberedClaim`) is a z-design issue and needs its own folder's round. F1's origin comparison must not apply to the raft folder of an old-prep raft, whose rounds are already on `origin/main` (R0044's landed with R0048's move).
Recommendation: for a `preparing` target that carries the raft's own stamp, judge the newest round of the member's folder or, failing that, of the raft's folder, with no origin comparison. Judge every other target by its own folder, F1 included. Name R0044 as the only raft on this route today, from a search pasted in Existing work (lesson zz-review/lists-paste-their-search). Spec cases in review-raft:
- a legacy raft whose own folder holds an answered round takes its stamp-claimed member;
- a raft whose folder holds an unanswered `changes` round is refused naming the raft's file;
- a member claimed by `status <id> preparing` here is refused when only the raft's folder holds a round.
Mutants: "the raft folder counts for every member"; "the raft folder never counts". If the author would rather have d0124 re-reviewed, that is a cost to the user: escalate with both options.
Lesson: z-design/new-rules-migrate-existing-work

### F3 [medium] A second reader of the review-round format, looser than the one `done` already has: an empty or partial refute counts as "answered"
Where: Design part 1 (`changes` passes "only with the same NNN's `design-refute-NNN.md` beside it"); Maintainability ("Nothing else parses the round"); zz-rules and z-design 5.5 wording ("answered design review").
Evidence:
- `reviewProblem` (`z-nile/engine/main.luau` ~3973, `./zn done`) already implements "the latest round must be resolved: verdict approve, or a same-numbered refute file that answers every finding id". It reads every `\n###%s+(F%d+)` heading and requires a `\n%-%s+F<n>:` line in the refute.
- The new reader differs in four ways: it takes the last `Verdict:` line, not the first; it matches the value exactly, where `done` reads `[Vv]erdict:%s*(%a+)`; it accepts a refute file's mere existence; and it uses `%d%d%d`, where `metrics`, `raftplan.isDesignFile` and `trail` use `%d+` and `lessons.isStem` uses `%d%d%d`.
- `c0120Move` reads `\nVerdict: approve` from review files too.
- So `design-review-001.md` with F1 to F3 and `Verdict: changes`, plus a `design-refute-001.md` that answers only F1 (or is empty), passes the move. That is z-design 5.3 skipped, under a refusal that says "answer every finding (z-design step 5.3)".
- My scan of every folder's newest round: all 25 `changes` rounds that have a refute answer every finding id. So requiring the ids costs no migration. Requiring `done`'s stricter "fixed …; consequences:" form would not be free: 24 of those 25 refutes, mostly old raft rounds, answer in another form.
Critique: lesson zz-arch/one-reader-per-format: two readers of one format drift, and here they already disagree on what "answered" means. The tempting fix is to call `done`'s `reviewProblem`. But it reads the disk directly, takes the first `Verdict` and needs `consequences:`, so it would refuse in-flight design rounds.
Consequences: a shared pure matcher is needed, plus a decision on which differences stay and why. Design mode answers are `fixed` or `refuted` (no `deferred`). The docs pins (the `ROUND` sentence) change from "with its `design-refute-NNN.md` beside it" to "with every finding answered in its `design-refute-NNN.md`".
Recommendation: extract the finding-to-answer matching into one pure function over texts, used by `done` and by `designReviewProblem`. In design mode, require every `### F<n>` of the newest round to have a `- F<n>:` line in the same round's refute, and name the missing ids in the problem. Keep the design-mode verdict reading strict, and say in a comment and in Maintainability how and why it differs from `done`'s. Share one round-name pattern constant with `lessons.isStem`. Spec cases: a refute missing F2 is refused, naming F2; an empty refute is refused; `- F1: refuted: …` alone passes. Mutant: "existence only".
Lesson: zz-arch/one-reader-per-format

### F5 [medium] Ways to reach `prepared` that the rule never sees are missing from the accepted risks, and nothing in the gate notices them
Where: Non-goals; Accepted risks 2 and 3; Existing work ("Mid-prep issues … one that hand-set `design: ready` first now meets the refusal at its `status prepared`").
Evidence:
- **Stale engines.** `./zn` runs the engine of the checkout it runs in. z-design syncs at step 1, and `refuseStale` checks only the id map, so a prep worktree made before c0161 lands runs `status <id> prepared` with the old engine. Its prep PR then merges, and nothing on the PR checks the issue. The Existing work sentence holds only for worktrees that synced after c0161 landed, and about 26 preps are in flight.
- **Derived status.** `status.effective` derives `prepared` from `design: ready` when `status:` is missing or unparsable (`c0053/status.spec` line 127 pins `{ status = "bogus", design = "ready" }` → prepared), so a prep PR that drops or garbles the line makes the issue prepared without the move.

- Accepted risk 2 rejects an `audit` check as "noise on two old items" (c0075, c0083). That premise covers only items prepared before the rule, not items that arrive by merge.
Critique: lesson zz-rules/audit-what-new-refuses: "a merge or another engine's capture can't bring one in unseen". The tempting fix is to name these paths as risks. But the stale-engine path is the ordinary state of every prep that is in flight on landing day, not an edge case.
Consequences: an `audit` error, which the gate runs, judges every backlog issue that is effectively `prepared`. It needs exemptions by decision: c0075 and c0083 (no reviews, prepared before reviews existed), R0044's members through the raft folder (F2), and anything a search finds. Its message names how to clear it: reclaim and review, or a recorded exemption. Its rule must be the same pure function the move uses (F3), minus F1's origin comparison, which has no meaning in audit.
Recommendation: either (a) add the `audit` error with its exemptions, a fixture case (a prepared issue without a round reaches the tree by a commit and audit names it), a case per exemption, and a mutant; or (b) keep it out, and rewrite accepted risk 2 with its real premise: the stale engine, the derived status and release, each named, with a `Decided with the user` line, since the guard this issue adds is otherwise bypassed by an ordinary merge. Name `release` in Non-goals with its reason either way.
Lesson: zz-rules/audit-what-new-refuses
