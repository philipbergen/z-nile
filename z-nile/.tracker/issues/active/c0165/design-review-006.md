### F1 [high] The new base trial for selected failures reports "main is red" for every spec the raft added, so `done` tells the executor to stop on a green `main`
Where: Learning step 2 ("A failed spec that was selected … still gets trial (b)"); step 3 (b) ("A failed spec that was selected gets (b) alone … if it fails on the base it prints `fails on the base too: main is red`"); Gate modes ("so a red base is told from a failure this raft caused"); Wording, zz-execute Stop conditions (``- Main is red: `./zn done` prints `fails on the base too: main is red` …``); R61; gate-learn.spec "a selected failure gets the base trial".
Evidence:
- Trial (b) checks out `<base>` in the clone and runs `lune run tests/run -- <S>` from `<dir>/<home>`. When S doesn't exist at the base, the runner fails it. Run in this worktree: `lune run tests/run -- tests/acceptance/c9999/absent.spec.luau` from `z-nile/` prints `FAIL …: could not load spec: … could not resolve child component "c9999"` and `0 passed, 1 failed`.
- A spec the raft added is always selected (its own path is in its closure), so it lands in `selectedFailures` and gets trial (b). There it "fails on the base too", and the gate prints `main is red`.
- This is the most likely selected failure at `done`. `done` first moves the raft's acceptance specs into `tests/acceptance/<id>/` (`z-nile/engine/main.luau`: the promotion and the moves, then `=== full gate on the done tree`, `check.sh --full`). That run is the first time those specs run from their promoted place. Every promoted spec, and every new unit spec the executor wrote under `tests/`, is absent at the merge base. A renamed or moved spec is absent under its new path too.
- So a raft whose own new spec fails at `done` gets `fails on the base too: main is red`, and the pinned stop condition tells the executor to stop and report red `main`. That is the confusion the user's 2026-11-03 decision relies on trial (b) to prevent ("red `main` first shows at `./zn done` … where learning's trial (b) reports 'fails on the base too'"; Gate modes: "so a red base is told from a failure this raft caused").
- gate-learn's new case can't see this: both of its specs (`broken`, `text`) exist at the base.
Critique: F4's fix applied "every failed spec" without asking whether that spec exists at the base. Before this round, only misses got (b), and a miss can never be a new file (its own path would have selected it), so the gap was unreachable until now. The tempting fix is to filter specs under `tests/acceptance/`. That still misses new unit specs and renamed specs.
Consequences: The rule needs a third outcome for trial (b): "not on the base". It must be decided before the trial (`git cat-file -e <base>:<home>/<S>` in the clone, or the changed list's added and renamed paths), so it costs no budget. It applies to misses too, for symmetry, though a miss can't be absent. The output must never contain `fails on the base too` for such a spec, or the stop condition fires.
Recommendation:
- In learning step 3 (b): a failed spec whose path doesn't exist at the base gets no trial and prints `<home>/<S>: new in this change: not tried on the base` (or prints nothing). Only a spec present at the base can print `fails on the base too`. Put the existence test in the adapter (the clone's `cat-file -e`) and add the "absent" input to the pure plan (`learn.selectedFailures` takes the base's present set, or a new `learn.baseTrials(failed, sel, present)`), so plan.spec can pin it.
- gate-learn case: in the `selected-red` fixture, add a new spec in the change commit that fails (for example a third extra spec created only in the commit). Expect no `main is red` line for it, and the existing `broken` line still printed.
- Rules row mutant: "a spec absent on the base is trialled and reported red".
- Say the same in the zz-execute stop condition's wording: "for a spec that exists on `origin/main` and also fails there".
Lesson: z-design/exact-checks-compare-against-the-merge-base (its check: "Can the author make … a judged file absent?")

### F2 [medium] Learning step 2 still says "If `sel == "ALL"`, stop", while `selectedFailures(failed, "ALL")` returns every failure. For a raft that touches shared tooling, it's unclear whether `done` reports red `main` at all
Where: Learning step 2 ("If `sel == "ALL"`, stop: every spec was selected, so nothing was missed."), step 5 (`selectedFailures` "all of them when `sel` is `"ALL"`"), plan.spec `selectedFailures(failed, "ALL") == failed`; gate-learn.spec (no case with an `ALL` selection).
Evidence:
- Step 2 reads in order: compute `sel`, and stop if it is `ALL`. The base-trial sentence comes after the stop, so a literal implementation runs no trial (b) when `sel` is `ALL`.
- The pure function says the opposite: with `ALL`, every failure is a selected failure. No gate-level case runs a full gate whose selection is `ALL`, so either reading passes check.sh.
- `ALL` is what `select.affected` returns for any change under `z-nile/lib/`, `z-nile/tests/lib/`, `z-nile/tests/run.luau`, `scripts/`, `zn` or the root configs (SHARED_FULL), and for z-nile when the change touches `z-nile/` outside `tests/` (TOOLING). Most z-nile rafts touch one of these, c0165 included. Under the "stop" reading, `done` never labels red `main` for them, which empties the decision's premise for most tooling work.
Critique: This is round 5's F4 fix not swept through the step it amended (z-design/restated-rules-move-together: "when a round's answer adds a failure path, have the earlier promises it contradicts been swept"). The tempting fix is to delete "stop". But with `ALL`, every failure gets a trial, and a broad regression at `done` can spend the whole `PICKMAN_LEARN_BUDGET` (40 one-spec trials, some of them `*` specs measured at 132–754 s) on base trials.
Consequences: Under `ALL`, the base trials are the only trials, so the budget bounds them. The design should say that a failure left untried for lack of budget prints a line, so the executor knows red `main` wasn't ruled out for it.
Recommendation: Rewrite step 2 as: "If `sel == "ALL"`, there are no misses; every failure still gets trial (b)." Add a gate-learn case whose change touches a forcing path (for example a fixture `pickman/tests/lib/` file, which forces pickman's `ALL`) with one spec red on the base. Expect `fails on the base too: main is red` for it. When the budget runs out, print `<home>/<S>: not tried on the base: learning budget spent`. Add a Rules row with the mutant "`ALL` stops before base trials".
Lesson: z-design/restated-rules-move-together

### F3 [medium] The pinned "Main is red" detection misses the most common red-`main` case: an unrelated spec red on `main` is a miss and prints `fails on the base too: not a graph miss`, never `main is red`. And the order of base trials and miss plans under the shared budget is unspecified
Where: Wording (zz-execute Stop conditions: ``- Main is red: `./zn done` prints `fails on the base too: main is red` for a spec that also fails on `origin/main`.``, pinned by docs.spec:42); Learning step 3 (b) and step 4 (a miss that fails on the base prints `not learned: … fails on the base too: not a graph miss`); `PICKMAN_LEARN_BUDGET`; gate-learn.spec "seeded graph miss" (expects `broken.spec.luau: fails on the base too: not a graph miss`).
Evidence:
- When `main` is red on a spec the raft didn't touch, that spec isn't selected, so it is a miss. Its trial (b) prints `not learned: <home>/<S>: fails on the base too: not a graph miss` (gate-learn's first case pins exactly that line for `broken`, which is red on the base). The pinned stop condition says `done` prints `fails on the base too: main is red` "for a spec that also fails on `origin/main`". For this spec it doesn't, so the stop condition's detection, read literally, never fires in the commonest red-`main` case.
- A miss that gets no trial at all also leaves red `main` unlabelled: a spend-only miss ("no candidate outside spend.md"), and a miss whose plan doesn't fit the budget ("learning budget spent"). Neither says whether the spec fails on the base.
- Misses' plans ((a), (b), (c)) and the selected failures' (b)-only trials draw on one `PICKMAN_LEARN_BUDGET`, and the Design doesn't say which goes first. If the base trials go first, many selected failures starve learning, the captured outcome "a merge failure teaches the selector". If the misses go first, they starve the red-`main` report. Neither pure function returns a (b)-only plan or its cost, so no spec pins the order or the budget accounting.
Critique: The F4 fix added a second wording for the same fact ("fails on the base too") and pinned only one of the two as the detection. The tempting fix is to loosen the stop condition to the prefix `fails on the base too`. That works only if every path that can tell red `main` prints that prefix, and two miss paths print nothing about the base.
Consequences: One wording for "fails on the base" whatever the spec's kind, and a stated budget order, affect plan.spec (a (b)-only plan or its cost), gate-learn (the miss line changes), docs.spec (the stop-condition line), and F1's "new in this change" outcome.
Recommendation:
- Print one line whenever trial (b) fails, selected or not: `<home>/<S>: fails on the base too: main is red`. For a miss, add `(not a graph miss)`, so gate-learn's first case expects both parts.
- State the budget order. A suggested order: every failure's (b) first (one trial each), then (a) and (c) for misses that passed on the base, which also saves (a) for misses red on the base. Pin it in plan.spec through a pure function that returns the base trials and the budget left. Pin it in gate-learn with a budget that fits only the base trials (the miss prints `learning budget spent`, and the red one still prints `main is red`).
- A miss that gets no trial for lack of budget, or that has spend-only candidates, prints `not tried on the base`.
- Keep the zz-execute line pinned to the one wording.
Lesson: z-design/spec-design-correspondence
