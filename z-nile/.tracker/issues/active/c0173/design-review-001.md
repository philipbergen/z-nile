### F1 [high] The sequestration exception is not one the rules allow, and the executor and the code reviewer are told by their skills to stop on it
Where: c0173.md Design, "Sequestration exception (binding, belongs to this chore)"; Implementation steps 2 and 4.

So the delivered `M  …/c0075/acceptance/wiring.spec.luau` is, by the letter of the skills, a stop in Phase 3 and a high in code review, whatever c0173.md says. The cited precedent does the opposite of what the design does: R0030.md:88 "Phase 3 and the code reviewer's item 2 name those exceptions" (c0083 edited those skill sentences as part of its delivery, and its scope rests on recorded user decisions, R0030.md:18–20). And the exception here is declared by the prep author, while zz-test reserves the only exception to "a move … that the user decides on"; c0173.md itself says "the report puts it to the lead", i.e. nobody with that authority has decided it.
Critique: the tempting fix is a sentence telling the reviewer "item 2 accepts this one line". That still leaves the skills saying the opposite, and it is a prep author granting itself a hole in the guard the whole tracker leans on (lesson z-design/accepted-risks-checked-and-decided: "a weakened guard is the user's call").
Consequences: any route that keeps the edit in execution needs (1) a user decision recorded in c0173.md, and (2) the skill sentences (zz-test Sequestered, zz-execute Phase 3 step 4 and the Phase 2B brief, zz-review Code item 2) to name the exception, as c0083 did, which is new scope (restated rules, lesson z-design/restated-rules-move-together) and a precedent for more exceptions. Routes that move the edit into a prep avoid touching the guard, but the prep brief forbade editing c0075.
Recommendation: escalate to the user: (a) **edit in prep**: lift the brief's "don't edit c0075" for this one case; the prep commit applies `wiring.patch` (and the two doc patches) directly, this design review covers it, and c0173's check.sh becomes the done-time proof of the state (AC5 then expects no sequestered diff at all); cost: c0075's own design review never saw the new case, and c0173 executes almost nothing; (b) **user-decided execution exception**: record `Decided with the user (date)` in c0173.md, and add the skill edits above to c0173's Design, Touched modules and a Checked AC that pins the new sentences; cost: four skill texts change and the guard gains a named hole; (c) **fold into the promised re-prep of c0075/R0039** (c0114/c0120): the re-prep rewrites `wiring.spec` anyway (E5: every case fails today) and carries this case, which still meets "before c0075 executes"; cost: c0173's outcome waits on that larger re-prep. Whatever the user picks, Non-goals and the Implementation steps say which.
