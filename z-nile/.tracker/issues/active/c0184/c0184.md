# c0184: Scaffold arcade homes

## Problem
Scaffold the new project homes and generalize pickman-only paths in the tooling

The user, 2026-10-31, asked for an arcade: "I want to branch out into multiple games, they will each have their own directory in the project: first person snake, first person asteroids. I also want a new project for a landing portal where you can scroll between the games and see the highscores for each". c0183 registers the five projects (`arcade`, the shared library; `portal`, the start place; the games `snake`, `invaders` and `asteroids`) with a `.tracker/` each and nothing else. A registered project with code needs the home pickman has (c0120): its gate entry, aliases, Rojo place, `src/`, runner, structural specs and skills. And three places in the tooling name pickman's folders by hand, so a second game's code would be gated, scanned and linted by accident: the stop hook, the reviewed `.cache` list, and the repository-fence scan (found in prep; the approved plan names the first two and the root `.luaurc`). What should happen: the five homes exist and pass their own gates, every hand-named pickman path in the tooling takes its homes from the registry, and the skills and docs say so.

## Non-goals
- Registering the projects, their `.tracker/` roots, designs and `deploy.yml`'s ignore list: c0183 (this chore starts from its result).
- The cross-home gate, c0185: `graph.srcAliasAllowed` and `@game/ServerStorage/`, `graph.affectedSpecs` and `affected.luau` reading every `*.project.json`'s `$path`s, the place harness (`pickman/tests/lib/place.luau`) into the shared harness, the `@arcade` alias, how a game's project file maps `../arcade/...` in (its experiments E1 and E2), and the `architecture.spec` rule that fails a Logic require resolving outside its home. This chore leaves each of those where c0185 will find it (Design, 6).
- Any feature, game, portal or library code. A home holds entry scripts that boot nothing, and the library one identity module. The one engine change is the `extends:` key of a skill (Design 2).
- Moving `sim` or `fakeengine` into the shared harness (a game that needs them asks for the move; the skills say so), and `pickman/tests/lib/place.luau` (c0185).
- `deploy.yml` beyond c0183's list, the `portal/experience.json` manifest and the N-place deploy scripts (the plan's Z3, a portal issue), and pickman's lobby (c0188).
- `scripts/check.sh` and `scripts/tracker.sh` forwarders in the new homes: c0120 kept them in pickman and z-nile only for sequestered check.sh files written before the homes; no new project has any.
- The hand lists inside c0120's check-paths and finished-file readers: c0160 (Design, 7).

## Solution
Five homes, one scaffold, one rule that checks it for every registered project (pickman included), ten skills that name pickman's as the base they extend (so a raft's prompt carries both), and the three hand-named pickman paths (and the root `.luaurc`'s `logic` and `shared` aliases) read from the registry instead. The scaffold is pickman's home, trimmed to what a home without code needs. The structural rules of pickman-arch are enforced by pickman's meta spec, which each new home runs from its own folder. Each new skill points at pickman-arch and pickman-test and states only what differs.

**The rule, `z-nile/tests/lib/home.luau`.** For every project of the registry except z-nile (the tooling, whose home holds the engine), the table above holds: the files exist with the stated content or aliases, `check.sh` is executable and names its own project, every `$path` of every `*.project.json` is a folder of the home (`..` is resolved, a link out of the home is followed and reported), `src/shared/Logic` and `src/server` are there, each wrapper is exactly its lines (`t.luau` its five; once comment and blank lines go: a require kept in a comment, or after an early return, is no wrapper; review 002 F3), the two skills exist and name themselves, and the root has `architecture.md` with exactly one closed `deps` block. It is pure over a tree and a list of projects, and requires no engine file (c0120 keeps an engine change from selecting any other project's specs; the registry reaches it as `{ name, home, root }` rows). `homespec.luau` reads the rows from `lune run z-nile/roots -- --projects` and checks the project whose home is the current folder; each home's `tests/meta/home.spec.luau` returns it. So a home's own gate judges the home, and an edit to its `.luaurc`, project file or `tests/` selects the check (review 002 F2); an edit to its `check.sh`, `stylua.toml`, `selene.toml`, `.tracker/architecture.md`, `skills/` or a `.gitkeep` selects nothing, as for every home today, and is caught only by the merge's `--full` (homes.spec's real-tree case below runs the rule on every home from z-nile; `./zn skills --check` covers a skill's name and its `extends`, not its text). A `$path` that names a file is refused for now (every mapped path is a folder today); a home that needs a file mapping widens the rule. The deps-block check in it (none, two, or one never closed) stands in for c0163's reader, which becomes the one reader of that block (zz-arch rule 5): whichever of c0184 and c0163 lands second makes `home.luau` call `deps.parse` and report its problems under the map's path, and `homes.spec` pins only that prefix and path, not the wording after it, so the switch overrides nothing. The sending of this line to c0163's prep is the lead's, recorded in the report. `RULES_HOME = "pickman"` is its one constant, the home whose meta spec holds the structural rules.

**`homes.spec`** (promoted, z-nile's): the rule holds on the real tree for every registered project but z-nile, pickman among them (the net under the per-home specs, review 003 F1: a home whose runner or `home.spec` was neutered runs nothing, and z-nile judges it; the merge's full gate runs it); every registered project has the wrapper; and the rule reads the registry and not a list of names (a fixture home `pong` with nothing but its root reports every missing file; a home with every file wrong, a require commented out of its fence wrapper, a path out of the home and a link out of it and a link inside a mapped folder that leaves the home report each, so a check that only looks for existence or text fails).

### 2. The skills
Ten files, `<home>/skills/<name>-arch/SKILL.md` and `<name>-test/SKILL.md`, in `experiments/skills/`. They are short and say where the rules are. A raft's prompt inlines only the raft's project's skills (`inlinedSkills`, c0115), so a pointer alone would leave pickman-arch out of a snake prompt (review 001 F5). So a skill may name one other skill in a new frontmatter key, `extends:`, and the prompt inlines it after the project's own, once each:
- `skills.luau` (the one reader of skill folders) reads `extends:` into `Skill.extends`; `skills.plan` reports `<dir>/SKILL.md: extends <x>, which is no other skill` for a name that is none or the skill itself, and leaves that skill out; the pure `skills.inlined(list, project)` is the order (z-nile's `INLINED`, the project's, then the bases), and `inlinedSkills` in `main.luau` calls it; `skills.bases` is the one reading of which skills are bases, and `buildLessons` keeps the lessons of a base too (review 002 F4), with the two headings of `templates/prompt.md` saying "with the skills they extend" (z-nile rafts have no `extends`, so c0115's rule that no other project's lessons reach them holds). Each of the ten skills has `extends: pickman-arch` (the `-arch` ones) or `extends: pickman-test`. No pickman name is in the engine. The zz-rules Skills bullet says so.
- **`<game>-arch`** (`snake`, `invaders`, `asteroids`, `portal`): the project's layout table, then "The rules are pickman's": read `pickman/skills/pickman-arch/SKILL.md` and its lessons first; its Layout rows, Rules 1 to 8 and Design checklist apply as written, and a rule that must differ is stated in the skill. Changes: (1) arcade features are leaves that adapters wire in; the game's Logic never requires arcade Logic and gets features as parameters; adapters require `@game/ReplicatedStorage/Arcade/...`; until c0185 a game requires nothing from `arcade/`; (2) the server is authoritative for the project's state. The Design checklist is pickman's, answered for the project from its `game-design.md` (what grows with players, what is data-driven, what makes it readable). `portal-arch` is the same with the portal's layout and its checklist (the boards' DataStore budget, a game as one config entry, scrolling on every input).
- **`arcade-arch`**: the library's Layout (`src/shared/Logic` to `ReplicatedStorage.Arcade.Logic`, `src/shared` to `ReplicatedStorage.Arcade`, `src/server` to `ServerStorage.Arcade`, no client folder), pickman's Rules 1 to 8, and four changes: a feature is a leaf and knows no game; per-game differences are parameters, never a branch on a game's name; server-only code is under `src/server`; a feature moves in as a copy, then the game switches (the plan's "arcade issue copies the feature and its specs, then a pickman issue switches the adapters and deletes the old copy"; a raft never spans two projects). How a game maps the library in is c0185's, and the skill says so.
- **`<name>-test`** (all five): "this is the project's half of testing", the spec tiers and simulation harness are pickman-test's (read it), how to run from the home, and what the home has: the three meta specs. A tier folder appears with its first spec. `sim`, `place` and `fakeengine` are pickman's helpers: a spec never requires another home's helper; one that needs a helper asks for its move into `z-nile/tests/lib/`.
- AGENTS.md gets two grouped rows (all five `-arch`, all five `-test`) after pickman's, and z-nile/README.md one Skills row. docs.spec pins that every registered project but z-nile is named in a row of each (the exact rows of today's five are check.sh's AC7). `./zn skills` writes the ten `.claude/skills/` links; `./zn skills --check` is in the gate already.

### Scalability
The stop hook runs one more `lune run z-nile/roots` (about 0.1 s) per stop. The gate gains five homes and six `home.spec` runs (about 1 s each, in each home's own jail): stylua, selene, luau-lsp and `rojo build` over a few files each, and three meta specs per home (the fence spec dominates: about 3 s per home, run in its own jail, concurrently with the others). The registry is read once per process in `cachepaths` and the fence spec. A home costs one registry entry, one deploy.yml line, and the scaffold; nothing grows with items.

### Maintainability
A further project with code is its registry entry, its root and deploy.yml entry (c0183) and a copy of a sibling home, renamed (the README says so); `homes.spec` names the file it forgot. `scaffold-homes.sh` is how these five were made and stays in this issue's experiments. The three hand lists are gone. The rules stay in one place (pickman-arch and its meta spec), and the new skills restate nothing, so a rule change is made once. The one constant is `RULES_HOME`.

### Usability
A person or agent finds a new project's gate at `<name>/check.sh`, its specs from `cd <name>`, its rules in `<name>-arch` (which says to read pickman-arch first), and the list of what a home has in the README. A missing file is a spec failure that names the home and the file.
