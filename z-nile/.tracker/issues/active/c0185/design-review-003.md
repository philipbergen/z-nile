### F1 [low] pickman-arch restates the server-file rule as round 1 had it, not as round 2 changed it
Where: `pickman/skills/pickman-arch/SKILL.md` rule 5's `@game` bullet (patch): "from a server root (a file under a `ServerScriptService` or `ServerStorage` node of the project file) also into `ServerStorage`"; Design 4 (`serverFile`: "in every place that maps it … and at least one"); check.sh AC7 (pins only the parenthetical `'also into \`ServerStorage\` (\`@game/ServerStorage/Arcade/...\`, c0185)'`).
Evidence: after design-review-002 F2, a file is a server file only when every `*.project.json` of the home that maps it puts it under a server service. A folder that pickman's default place keeps on the server and a second place replicates is no server file, and the meta spec refuses its ServerStorage require (graph.spec "every place"; the AC6 fixture's third place). The skill still says "a … node of the project file", in the singular. A developer reading it would expect that require to pass. No check pins the definition, so the sentence can stay stale indefinitely.
Critique: the fix changed the rule in code and specs but not in the one skill that restates it, the defect lesson restated-rules-move-together names.
Consequences: AC7 needs a grep of the new words. The arcade, snake and other arch skills say "server adapters also `@game/ServerStorage/Arcade/...`" without a definition, so they stay true.
Recommendation: reword the bullet to "from a server file (one that every place of the home that maps it, each `*.project.json`, puts under a `ServerScriptService` or `ServerStorage` node, and at least one place maps) also into `ServerStorage`", and add that phrase to check.sh AC7's pickman-arch greps.
Lesson: z-design/restated-rules-move-together

### F2 [low] graph.luau now has two listers of a home's project files, which round 2 asked not to drift and which already differ
Where: `z-nile/lib/graph.luau` `currentPlaces` (new in the round-2 fix) and `graph.placeInputs`; Maintainability ("One reader per format: a project's mappings are read by `graph.mappings` alone"); design-review-002 F2 Consequences ("with the project-file listing `placeInputs` already does, so the two must not drift").
Evidence: both functions `fs.readDir`, filter `%.project%.json$`, sort, `pcall(serde.decode)` and refuse a file without a `tree`, but each does it its own way. `placeInputs` guards `fs.isDir(dir)` and joins `{dir}/{name}`; `currentPlaces` reads `.` only. Their error texts differ ("the selector can't tell what its place maps" against "the server roots can't be told without it"). They have separate mutants (G7 and G13) because the code is duplicated. `graph.mappings` is shared, but the listing, decoding and validation of project files are not. The next rule about which files count (skip a non-file, ignore a dot-file, accept JSON5) will land in one copy.
Critique: the tempting fix is a comment that cross-references the two. Comments don't stop drift.
Consequences: the callers differ only on an empty home: `placeInputs` falls back to the legacy answer and `currentPlaces` returns no places. A shared function must return the list and leave that decision to each caller.
Recommendation: one private `projectsIn(dir): { { name: string, project: any } }` (sorted; a non-project is refused with one message that names the file), used by `currentPlaces` (mapping each entry to `gameRoots`) and by `placeInputs` (adding the legacy answer when it is empty). G7 and G13 then become one mutant, and graph.spec's refusal case pins the one message. AC6's broken-file case keeps the `serverFile` path covered.
Lesson: zz-arch/one-reader-per-format

### F5 [low] An absolute `$path` loses its leading `/` in `graph.mappings`, so `insideFolder` calls it inside the home and `placeInputs` resolves it under the home
Where: `graph.mappings` (through `normalize`, which drops an empty first segment), `graph.insideFolder`, `place.load`, `graph.placeInputs`; Design 3 and 4 ("the one 'stays inside' test").
Evidence: a probe in my clone gives `graph.mappings({ tree = { A = { ["$path"] = "/opt/x" } } })` the answer `A  opt/x`, and `graph.insideFolder("/opt/x")` and `insideFolder("opt/x")` both true. Rojo accepts absolute `$path`s, and c0064's `Beta.project` writes them (its spec fixture holds `"Abs": { "$path": "/opt/x" }`). So a project file with one would have `place.load` list that node as one of the home's script roots, and the selector would watch `<home>opt/x`. The home rule refuses it on the real tree, but as "no folder of the home" rather than "outside the home", so no gated tree reaches a wrong answer today. The functions' own contracts are wrong, though, and graph.spec has no case.
Recommendation: keep an absolute path absolute in `walkMappings`, by normalizing only the relative ones or keeping the leading `/`. `insideFolder` returns false for a path that starts with `/`. Add graph.spec cases `["/opt/x"] = false` and a `mappings` entry that keeps `/opt/x`, and a row whose mutant is "an absolute path counts as inside".
