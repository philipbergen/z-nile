### F1 [high] `./zn hooks` installs, and `--check` compares against, the working tree of whichever checkout runs it, so one session's install turns every other checkout's gate red, and an uncommitted hook edit starts refusing ordinary commits everywhere
Where: Design, "`./zn hooks [--check]` and `hooks.plan`" (the `source` is "the tree's `z-nile/lib/repo-hooks/reference-transaction` text"; "our file, text differs from the tree's → install"); `main.luau` `cmd.hooks` (`fs.readFile(hooksLib.SOURCE)`); Implementation step 3 ("in this worktree, `./zn hooks`: it installs this branch's hook in the shared git directory"); `hooks-plan.spec` "stale" and `hooks-command.spec` "stale", which pin the tree as the reference.
Evidence: I ran this on the prototype clone. I installed from the clone's main checkout (`--check` exit 0), then made a linked worktree `w1` and appended one comment line to the hook there without committing it. Then:
- `w1$ ./zn hooks --check` gave `… differs from z-nile/lib/repo-hooks/reference-transaction; run ./zn hooks` (exit 1).
- `w1$ ./zn hooks` gave `hooks: updated …/repo/.git/hooks/reference-transaction`.
- `repo$ ./zn hooks --check` (the other checkout) now gave the same `differs … run ./zn hooks`, exit 1.
Each checkout's gate tells it to run the command that makes the other one red. Next, in `w1` I added an uncommitted faulty line after the transaction read (`who=$(printf x | git rev-list --bogus-flag) || refuse "wip"`) and ran `./zn hooks`. An ordinary `git commit --allow-empty` in the *other* checkout then failed: `reference-transaction (z-nile/lib/repo-hooks): wip` / `fatal: in 'prepared' phase, update aborted by the reference-transaction hook`, exit 128. No branch has to change the hook for the gates to disagree. Any two trees with different hook text do it: a worktree branched before a later hook change, or one that merged main after it. Step 3 makes this chore's own executor install its unreviewed, in-progress hook for every session on the machine.
Critique: the installed hook is one file that all checkouts share, but each checkout judges and writes it from its own tree. That brings back the issue's own problem (one session's action turns other sessions' gates red), and it is the shape lesson zz-arch/guard-state-out-of-reach-or-checked warns about: "when other legitimate processes write the record … never fail on the record merely differing". It also takes the guard's code from a tree any branch can edit (zz-arch/guards-trust-only-origin). A worse case than red gates is possible: a hook that refuses every ref update in every worktree. The person can only undo it with `git -c core.hooksPath=…` or `rm`, and both are "repairing the shared git configuration", which AGENTS.md tells sessions not to do. The tempting fix is to drop the "differs" problem from `--check` (presence, marker and executable only). That silences the ping-pong but leaves a stale or WIP hook in place for good, with nothing that notices.
Consequences: one reference for every checkout is needed. The candidate is `refs/remotes/origin/main`: worktrees share it, it is reviewed, and every `./zn` publish fetches it. Using it brings these changes:
- (a) `./zn hooks` installs `git show origin/main:z-nile/lib/repo-hooks/reference-transaction` and never the working tree. It refuses when that blob can't be read. When origin/main has no such file it says "nothing to install".
- (b) `--check` compares with the same blob. On this chore's own branch, before it lands, origin/main has no hook, so the stage has nothing to judge. Step 3's pre-review install then goes away, and the stage's guard must become "origin/main has the file", not `[[ -f … ]]` in the tree.
- (c) The window between a fetch that brings a new hook text and the next `./zn hooks` turns every gate red at once. `./zn sync` already runs after every publish and `land` and is allowed to touch the main checkout's git state. It could reinstall from origin/main, which closes the window. That adds `.git/hooks` to the AGENTS.md sentence on what `./zn` edits in the main checkout.
- (d) In the Merging clone, origin/main is whatever the clone fetched. The step's sentence must say which ref it installs from there.
- (e) Fixture specs keep testing the tree's file, because `repo-hook.spec` copies `HOOK` from the tree, so a branch's new hook text is still proven before it lands.
Recommendation: take the source and the comparison from origin/main as in (a) to (e), and rewrite the `source` field, the plan table rows, step 3 and step 9 to match. Add these spec cases to `hooks-command.spec`:
- two checkouts whose trees carry different hook text: after `./zn hooks` in either one, `--check` is green in both;
- an uncommitted edit to the tree's hook is never installed;
- origin/main without the file: `./zn hooks` says nothing to install, `--check` reports nothing to judge and the stage is skipped;
- origin/main moved to a new hook text: `--check` is red until `./zn hooks` (or `sync`, if adopted) runs, then green.
Add a wiring pin for the stage's new guard, and a mutant row "source read from the working tree" that the first case kills. If you prefer not to change `sync`, the design must say who closes window (c) and pin it.
Lesson: zz-arch/guards-trust-only-origin

### F2 [medium] A push of a fixture-tip branch is not guarded, and with G2 accepted one such push stops `git fetch origin` (so `./zn sync`, `land` and every publish) for every session; G2 does not show the user this route
Where: Risks ("A fixture-tip branch on origin blocks `git fetch origin`"); Guesses G2; Existing work ("If one ever does (a prototype pushed)"); Non-goals (pre-commit/commit-msg are excluded, pre-push is never discussed); Maintainability (a `pre-push` "plugs in" later).
Evidence: In a throwaway repository with this hook installed, I made a fixture-tip branch `old-proto` before the install, as the four `proto-wall-picks-*` branches in the real repository are today (`git for-each-ref` confirms all four, both roles `proto@example.invalid`). Then `git push origin old-proto` printed `* [new branch] old-proto -> old-proto`. The remote now holds the branch (`ls-remote` lists it). Only the local `refs/remotes/origin/old-proto` update was refused (exit 128). Every later `git fetch origin` failed with the hook's refusal (exit 128) until someone deletes the branch on GitHub. The same applies to `gh pr create` or `git push -u` from a worktree whose tip is a fixture commit made before the hook, and to `git push origin <sha>:refs/heads/x` of a `commit-tree` object, which never needs a local ref.
Critique: the capture's purpose is "so prototype branches can't trip every running gate". If G2 is accepted, a pushed prototype branch no longer trips gates, but it stops every session's fetch, which is at least as bad. If G2 is rejected, the pushed branch reaches the tripwire again. So either way, a push route the hook does not cover defeats the outcome. G2 asks the user to choose between those two harms without saying that pushing an existing branch is the way it happens, or that the guard could stop it at the push.
Consequences: a `pre-push` hook from the same install would refuse to push any ref whose new tip has a fixture author or committer. That needs:
- `hooks.NAME` to become a list, one marker per hook, `plan` per hook, and `--check` covering both;
- `git-hooks/pre-push` (the fence's) already `exec`s the repository's own `pre-push`, so the chain is ready, but it needs its own case, as the reference-transaction chain has;
- `--no-verify` skips `pre-push` (it never skips reference-transaction). Say so, and keep G2's fetch refusal as the backstop.
Recommendation: add the `pre-push` hook to the design under the same command, with cases in `repo-hook.spec` or a sibling spec:
- pushing an existing fixture-tip branch is refused and the remote is unchanged;
- pushing an ordinary branch whose history holds fixture commits is allowed;
- a fenced check.sh flow's push still reaches it through the fence's chain.
Add the matching mutant rows (pre-push not installed; tip judged by its old value). Rewrite G2 so the user sees the push route and the guard that now covers it. If you instead keep `pre-push` out, write it as a Guess for the user, with the push evidence above and the cost of each option. It cannot be a prep-side Non-goal, because it decides whether the captured outcome holds.

### F3 [medium] `ALLOWED["z-nile/engine/main.luau"] = { hooksPath = … }` exempts the whole 5,700-line CLI from the scan for the one name that turns hooks off
Where: Regression guard, "(1) Three `ALLOWED` entries … `main.luau` may name `hooksPath`"; prototype `repo-fence.spec.luau` +290.
Evidence: `bannedIn(fs.readFile(path), ALLOWED[path] or {})` (repo-fence.spec:586) checks each name against the whole file. `hooksPath` is in `NAMES` (line 36) because `-c core.hooksPath=…` turns the fence's hooks off. With the entry, any later `sh.git({ "-c", "core.hooksPath=/dev/null", "push", … })` anywhere in `main.luau`, the module that pushes and publishes, passes the scan. Also, the entry is written as a plain assignment after the table literal, so it would silently replace a `main.luau` entry that another branch adds to the literal.
Critique: the scan's allowance is "one name in one file", but the file chosen here is the largest one that runs git. The only need is to name the config key in one read. zz-review's item 9 ranks any widening of a guard high. I rank it medium because the use is read-only today and the scan offers nothing narrower than a file, but the choice of file sets how wide the hole is.
Consequences: if the key moves to the pure module (`hooks.CONFIG_KEY = "core.hooksPath"` in `hooks.luau`, about 100 lines and no process calls), `main.luau` passes `hooksLib.CONFIG_KEY` and never spells the name. The allowance then goes on `hooks.luau`, where the staleness rule finds its key. The spec needs one more check: `main.luau` gets no `hooksPath` entry.
Recommendation: move the literal into `hooks.luau` and key the `ALLOWED` entry there. Add a merge-into-existing pattern (`ALLOWED[k] = ALLOWED[k] or {}` then set the name), or put the entries in the literal. Add a `repo-fence.spec` assertion, or a `wiring.spec` case, that `main.luau` does not contain `hooksPath`. Name the change in Regression guard and G1, so the user confirms every widening, not only the identity list.
Lesson: zz-test/narrow-guard-allowances

### F4 [medium] The captured "refuses any ref update" is narrowed with no recorded decision: pseudo-refs and every name outside `HEAD`/`refs/` are allowed, and the captured Problem sentence is paraphrased away
Where: Problem (the capture's sentence "The real repository refuses any ref update to a commit authored or committed under @example.invalid, so prototype branches can't trip every running gate" is gone; "What should happen" restates it); Design, "What it considers" (`$3 == "HEAD" || $3 ~ /^refs\//`); Rules row H8a; AC1 ("allows … pseudo-refs").
Evidence: `drive(repo, "prepared", "{ZERO} {fx} ORIG_HEAD\n{ZERO} {fx} CHERRY_PICK_HEAD\n")` is asserted ok (repo-hook.spec:238). The awk also lets through `worktrees/<name>/HEAD` and `main-worktree/HEAD` (neither is `HEAD` or under `refs/`). The design gives good reasons: ORIG_HEAD takes the *old* tip, so judging it would block `reset` and `rebase` away from the four old branches, and the tripwire reads only `for-each-ref` and its own `HEAD`. But nowhere does it record that the user agreed to the narrower set.
Critique: z-design's "Scope is what was captured" lets the Problem only gain detail. The prep's own memory rule ("never narrow captured scope") makes any exception to "any ref update" the user's call. The exclusion is probably right, but a reviewer can't approve it on the author's say-so. The tempting fix is to add a Non-goal, which would be a move into Non-goals with no decision line.
Consequences: if the user prefers the literal scope, the hook must judge pseudo-refs by their *new* value only and still allow the old-tip ORIG_HEAD case. That is a new rule with its own spec case (`reset --hard main` while on an old fixture branch stays allowed).
Recommendation: escalate to the user: add a G3 with these options:
- (a) allow pseudo-refs and per-worktree `HEAD` names (today's design; the tripwire never reads them);
- (b) judge them too, at the cost of `reset` and `rebase` away from old fixture branches unless the ORIG_HEAD case is special-cased.
Put the capture's sentence back in the Problem verbatim, with the detail added after it. Record the answer as `Decided with the user (…)`.
Lesson: z-design/never-narrow-captured-scope

### F5 [low] `--check` judges each configured `core.hooksPath` line rather than git's effective value, and tells a person with a global setting to remove it "in this repository"
Where: Design, `hooks.redirects` and the redirect row ("remove that setting in this repository"); `hooks-plan.spec` "redirect" case (pins the `global` wording).
Evidence: in the clone, with `HOME` holding `[core] hooksPath = /elsewhere` and a local `core.hooksPath` set to the repository's own `.git/hooks`, `git config core.hooksPath` printed the own folder, so git runs the hook. `./zn hooks --check` still said `git reads hooks from /elsewhere (global configuration), so … would never run; remove that setting in this repository` (exit 1). Removing a global setting "in this repository" is impossible, and the local override that does work is refused anyway. In the other direction, a `worktree`-scope setting in one linked worktree (`extensions.worktreeConfig`) is invisible to a `--check` run elsewhere.
Critique: E8 shows nobody sets this today, so the impact is small. But a false "refuse" in a gate stage is red for every session, and the stated fix can't be done as written.
Recommendation: decide from the effective value (`git config --show-scope core.hooksPath`: the last value wins), and drop it when it is the `command` scope or the own folder. Word the fix by scope ("in your global configuration (~/.gitconfig)" and so on). Add plan cases for a global value overridden locally to the own folder (ok) and a global value alone (refuse, with the global wording).

### F7 [low] Existing work says the old fixture branches "stay" usable, but several ordinary routes onto them are refused, and a push back from a scratch clone gets advice that doesn't fit
Where: Existing work ("a checkout, a stash, a worktree and an ordinary commit on top of one are allowed"); E6; the hook's last message line.
Evidence: in a throwaway repository with the hook and a pre-hook fixture branch `old-proto`, `git checkout --detach old-proto`, `git worktree add --detach ../wt old-proto`, `git merge --ff-only old-proto` and `git switch -c from-old old-proto` each exited 128. `git worktree add ../wt old-proto` (on the branch itself) passed, and nothing was left behind after a refusal. From a scratch clone, `git push origin HEAD:refs/heads/from-scratch` of a fixture commit was refused by the receiving repository's hook (correct), but the message the pusher sees says "A prototype lives in a scratch clone … or commits under your own identity", and they are already in one.
Critique: these are the intended refusals (each moves a ref to a fixture commit), but a session that reads Existing work and expects to inspect an old prototype detached gets an unexplained no. Since the first finding of this issue was that sessions keep missing a prose rule, the message is the main teaching tool.
Recommendation: list the refused routes in Existing work and E6 (detached checkout, `switch -c`, fast-forward, `worktree add --detach`: use `git worktree add <dir> <branch>` or a scratch clone instead). Add one line to the message for a refusal of a `refs/heads/` update with no local `HEAD` change: "if you are pushing from a scratch clone, keep the prototype there". Pin it with a `repo-hook.spec` case for a push into the hooked repository. That push is also the route the zz-test rule now recommends, and it has no case today.

## Candidate lessons (for the lead to place)
- **zz-arch: an artifact many checkouts share is installed and judged from one reviewed reference, never from the checkout that runs the command.** Why: c0189 design review 001 F1. The git hooks folder is shared by every worktree, but `./zn hooks` installed and `--check` compared the running tree's file, so two trees with different text turned each other's gates red, and an uncommitted faulty edit refused ordinary commits in every checkout. Check: with two worktrees whose source text differs, is `--check` green in both after either one installs, and is an uncommitted edit ever installed?
- **z-design: a guard that refuses one route names the neighbouring route that creates the same state.** Why: c0189 design review 001 F2. The reference-transaction hook refused the fetch of a fixture branch from origin, but nothing stopped the push that puts one there, and the risk was written as if it could only arrive from outside. Check: for each state the guard refuses, what command creates that state where the guard doesn't run (the remote, another tool, a different hook), and is that command refused or decided?
