# c0191: No leaked processes

## Problem
The user, 2026-11-01: "We cannot ever leak processes like that. There needs to be a safeguard."

**What happened.** Three `lune run p2.luau check …` processes (PIDs 72711, 10410, 29924) each held a full CPU core for about 14 hours.
- They came from a code review of PR #125 (R0052, c0117) in another session, which fed hostile `check` lines to `raftcheck.judge` in a scratch copy (`…/90b21ea5-…/scratchpad/cr4`).
- Three of those lines hit an infinite loop in `raftcheck` (c0193). The probes never ended.
- Their parent was launchd (PPID 1): the shell that started them was gone, its session ended, and nothing would ever stop them. They were found only because the machine felt slow ("several lune processes going bananas on the machine but nothing is actually running").
- They also add to the load every gate runs under (c0132's sweeper kills come at load around 30).

**Why nothing caught it.** The spec runner's jail and sweeper cover only `tests/run`. A command an agent runs itself, like a probe, an experiment, a scratch `lune run`, or a background job, has no time limit and no owner once its shell goes. The skills' rules on experiments are prose, and a stuck process breaks no rule anyone checks.

**What should happen.** No process a session or agent starts can outlive it, or run unbounded:
- every such command stops on its own within a limit;
- every such command stops when the agent or session that started it ends;
- a backstop finds any that still escape, stops them, and says so.
This is a mechanical guard, not a prose rule (c0181: lessons become checks).

Decided with the user (2026-11-01): "Scan inline Python". The hook reads `python3 -c` scripts and `python3 -` here-documents for loop and subprocess forms, as it reads `perl -e`, and refuses only on a hit; a Python file stays refused.

Decided with the user (2026-11-01): "Reap on /clear". The session-end reap also runs on `/clear` and stops the cleared conversation's tool shells, including an in-flight background gate or land; the docs say so plainly.

Decided with the user (2026-11-01): "Own time limit". A subagent's command stops at its own `./zn run` limit (at most an hour), and the session-end reaper catches anything left; the docs say so in one sentence and Observed OC3 shows it. No redesign.

Decided with the user (2026-11-01): "Yes, that boundary". The session's own tree is stopped by ancestry wherever it went, and unowned processes outside the repository's scope are never touched.

Decided with the user (2026-11-01): "Allow ./zn run". `Bash(./zn run:*)` is added to the project's `permissions.allow` (not `./zn reap`): any command wrapped in `./zn run` then runs without a permission prompt.

Decided with the user (2026-11-01): "You can use it to prove that your implementation works and then it gets removed. I'm not running that." No spec in the suite burns CPU on purpose, waits for a real limit or starts a spinner.

A proof that needs real work (a spinner stopped by `--cpu`, the wall-clock kill, the group kill, a hanging hook entry) is a script only `check.sh` runs, to prove the implementation, and only before `./zn done`: it sits in `acceptance/` for sequestration but has no `.spec.luau` name, so `tests/run` never executes it (the pattern of `reap-e2e.luau` and c0156's `kills.luau`). The suite keeps the same rules through stand-ins: a `ulimit` that records what is asked for, a clock and CPU meter the runner reads, a stub engine and a stub hook entry.

**Decided by the lead (2026-11-01), see the lead decision above; prep's earlier question:** the user said the proof "gets removed". `./zn done` still promotes the two proof files to `tests/acceptance/c0191/`, where `check.sh` skips them (the sequestered folder is gone) and the suite never runs them. Whether they must also be deleted after `done` is the user's call; if so, the executor's last step deletes them and their two `check.sh` clauses are already inert, so nothing else changes.

Lead decision (2026-11-01), from the user's words "it gets removed": after `./zn done` the executor deletes the two proof files (`acceptance/proof-bounded.luau`, `acceptance/proof-limits.luau`) as the last step, and the check.sh gate that skips them once the folder is gone stays. The hook entry's gap (E18: a syscall-heavy loop beats `ulimit -t`) stays recorded: the harness's 10 s timeout bounds it.

## Non-goals
- The `raftcheck` loop itself: that is PR #125's code-review finding, and the loop-progress rule is lesson c0193.
- The spec runner's own sweeper (c0132, c0167, c0168). This issue may reuse the runner's limits, but it doesn't change how the sweeper counts or reports.
- Stopping processes that aren't the user's z-nile or pickman work (editors, the Roblox Studio, other repositories).

## Solution
Ideas from capture; z-design decides.
- **A bounded runner,** for example `./zn run [--time <s>] -- <cmd>` or `z-nile/lib/bounded.sh`. It runs the command in its own process group with:
  - a wall-clock limit (default about 60 s);
  - a CPU-time limit (`ulimit -t`), which every child inherits and which still applies after the child is orphaned, so the kernel stops it even if everything else is gone.
  It stops the whole group on timeout, on its own exit, and when its parent dies.
- **Enforcement for agents.** A checked-in Claude Code `PreToolUse` hook on Bash (beside `scripts/hooks/`) refuses a bare `lune run`, or other long-running interpreter call, that isn't through `./zn`, a `check.sh`, `tests/run` or the bounded runner, and names the wrapper. Subagents inherit it.
- **A backstop reaper,** for example `./zn reap`. It finds this user's `lune` (and `git`, `sh`) processes that are orphaned (PPID 1) and have run past a limit, with a working directory under a session scratchpad, a `.worktree/`, or `.cache`. It stops them and reports each one: pid, age, cwd and command.
  - It runs from a `SessionEnd` hook.
  - It runs at the start of every gate and `./zn sync`, so the leak is reported where people look.
- **The spec runner** also sets the CPU-time limit on every spec process, as a second line behind the sweeper.
- **Docs, in the same words everywhere:** z-design experiments, zz-execute, zz-review code mode and zz-test say that a probe runs through the bounded runner. Lesson c0192 is the short form.
- **Experiments in prep:**
  - Does `ulimit -t` survive reparenting and kill a spinning `lune` on macOS?
  - Does Claude Code's Bash timeout kill the child tree, or leave it running (how these leaked)?
  - Can a `PreToolUse` hook tell `./zn …` from a bare `lune run` reliably, including after `cd`, `&&` and `bash -c`?

Prep detail (z-design, 2026-11-01): the experiments found that the `perl alarm` recipe itself leaks and that macOS hides the environment of system binaries; the Design records the decisions that follow (the ending session's processes are found by ancestry, the hook refuses rather than rewrites and fails open, and covers loops, follows, background calls and the Monitor tool because "a background job" is named in the Problem, `./zn run` starts before the engine, CPU limits only ever lower). Every captured outcome above has a Design and an acceptance criterion (AC1 runner, AC2 hook, AC3 and AC4 reaper and its call sites, AC5 spec-runner and engine CPU limits, AC6 docs).

## Design

### What prep found (experiments, 2026-11-01, macOS 26.6, Lune 0.10.5, Claude Code docs read the same day)
The captured ideas stand; these facts decide how each is built.
- **`perl -e 'alarm shift; exec @ARGV' 60 lune run x` leaks.** The Rokit `lune` starts the real Lune as a child; the alarm ends only the shim and the tool keeps spinning at PPID 1 (E4). This is the recipe the prep brief and one lesson give for "bounding" a probe, so the wrapper has to stop the whole group, not a pid.
- **`ulimit -t` works and survives reparenting, but is SIGXCPU only (E1).** A spinning `lune` under `ulimit -t 2` dies at 2 CPU seconds, orphaned or not. A process that ignores SIGXCPU is not stopped by macOS even with a hard limit (E1c, E1f: 33 s of CPU on a 2 s limit). So the CPU limit is a second line behind the wall-clock limit, never the only one.
- **Claude Code's Bash timeout does not kill (E2).** In this harness a call past its timeout is "moved to the background"; the docs say the same ("moves it to the background instead of stopping it"). That is how a probe outlives the call. Nothing in the docs says what happens to a background command when an interactive session exits.
- **`ps -E` shows the environment only for non-system binaries (E5).** `lune` shows `ZN_BOUNDED_DEADLINE`; `/bin/sleep`, `/usr/bin/perl` and `sh` show none. Arguments and environment share one text, so a process whose arguments merely spell the variable looks marked unless the arguments are subtracted first (the first prototype killed an `awk`'s `sh` this way).
- **`ps` and `lsof` cannot start inside the spec jail (E6)**, which is why the reaper's check against real processes runs from `check.sh` (unjailed, fenced) with a throwaway root, and its rules are specced as pure functions.
- **A detached `git maintenance run --auto --quiet --detach` is routinely a PPID-1 `git`** (E7), so "orphaned git" alone would be a bug.
- **Limits do not compose unless every setter only lowers (round 1 F2).** A lowered `ulimit -t` cannot be raised again ("Operation not permitted"; E10). Anything that sets one on a process that may already be under another, such as the jail's shell under `./zn run`, the engine or a hook, must set it only when its value is lower.
- **The loops that matter are not interpreters (round 1 F1).** On this machine, session `claude` 3465 has three agent-started Bash loops (`until gh pr view ...; sleep 30; done`, `until grep -q ... full.log; do sleep 20; done`) that have run 5 days 13 hours, one polling a log in the incident session's scratch folder that never finishes (E11). A foreground call past its timeout moves to the background, so any foreground loop becomes one of these. The Monitor tool also takes a shell command, and when a monitor expires the harness kills its shell, which orphans a Lune child the way E4 shows.
- **Claude Code's tool shells have one form** (E12): each Bash command runs in `/bin/zsh -c source <home>/.claude/shell-snapshots/snapshot-zsh-….sh … eval '…'`, a direct child of the `claude` process. MCP servers, hooks and the status line are other children of `claude`.
- **Hooks (docs, not run live: see Unknowns U1):** PreToolUse gets `tool_input.command` as JSON on stdin; exit 2 blocks and stderr reaches the agent; any other exit lets the call run; `updatedInput` can rewrite a command (version not documented); the same hooks run inside subagents; SessionEnd has a 1.5 s default budget, raised by the hook's own `timeout` up to 60 s, and fires on exit, `/clear` and `/resume` (reasons `clear`, `resume`, `logout`, `prompt_input_exit`, `other`); nothing is documented for a killed terminal or `kill -9`.

### Decisions (each keeps its captured outcome; none narrows)
1. **The bounded runner is `./zn run`**, and it starts before the engine: `zn` handles `run` first (shell, `exec perl z-nile/lib/bounded.pl`), so a broken Lune or engine cannot stop the bound from working, and it costs no Lune start (the engine is 5,600 lines). It runs in the caller's folder.
2. **The hook refuses and names the wrapper; it does not rewrite.** `updatedInput` is documented but unversioned, and a rewritten command changes what the agent thinks it ran (quoting, cwd). The captured idea says refuse. It covers the tools that take a shell command, **Bash and Monitor** (matcher `Bash|Monitor`), and refuses by class, not by program list: an interpreter with no limit, a `while`/`until` loop, a follow (`tail -f`, `watch`, `gh ... watch`, `yes`, `caffeinate` without `-t`), a detacher, the `perl alarm` recipe, and a **background Bash call** (`run_in_background: true`) or a job started with `&` in a foreground call, unless every command in it is bounded (the gate, a check, a `./zn` command, the wrapper) or ends by itself. A Monitor command is bounded by its own timeout, so loops and follows pass there; its interpreters and detachers do not. Waits of up to an hour go through `./zn run --time 3600` (a sleeping poll costs no CPU). The hook **fails open** (any error exits 0): a seatbelt that can block all work on its own bug is worse than the leak it prevents; the reaper is the backstop for what it misses. This is a recorded design choice, not a guard (it protects no repository). The hook is itself bounded: two seconds of CPU and a 10-second timeout.
3. **The reaper treats a process as a leak only on an explicit yes** (zz-arch rule 7): unknown folder, unknown parent, unreadable `ps` line = keep. Three ways to be a leak (below). It signals only after re-reading the process's start time (a reused pid is left alone, lesson zz-arch/children-need-a-lifeline).
4. **The session end stops the session's tool shells, and everything below them.** At SessionEnd the session's `claude` process is still alive, so its leaked children are not orphans yet, and macOS hides the environment of `perl`/`sh`. A tool shell is a direct child of `claude` that sources a shell snapshot (E12). The three loops that opened round 1 run in the tool shell itself and their children are `sleep`, `gh` and `grep`, so the targets are the **shells** (whatever they run), and the shell with its whole tree is stopped. MCP servers, running hooks and the status line are other children of `claude` and are never touched; on `/clear` the session goes on with them. After the session is gone, an orphaned tool shell, and the orphaned `sleep`, `tail`, `gh`, `grep`, `watch` and interpreters a loop or a killed monitor leaves, are leaks by the orphan rule a minute later. If Claude Code changes the form of its tool shell, the session rule finds nothing (it fails closed) and the orphan rule finds the leak after the session is gone: the next gate start, `sync` or session end. The pieces this depends on are Claude's, unversioned, and listed so a change is found: the snapshot folder name (`/shell-snapshots/`, whatever the config folder is), the `ugrep`/`bfs` names of `grep`/`find`, the session folder slug, its temp folder, and the process name `claude`; each fails closed.
5. **`--auto` is the only form `sync` and the gate run.** It is quiet unless it stops something, does nothing in a check run (the same `pickman_guarded` answer the publisher uses, asked quietly), never fails its caller, and is skipped in `--plan` mode. A spec run that calls `sync` in a fixture therefore never signals a process on the machine.
6. **CPU limits only lower.** The spec runner puts `ulimit -t` on the jail's shell, inherited by the workers and every spec child: default 1200 s per process, `PICKMAN_SPEC_CPU` overrides, a bad value refuses before anything is made or locked. `./zn` puts `ZN_ENGINE_CPU` (default 1800 s) on its engine (the old specs that copy the runner into a fixture by a fixed list of files copy no `cpu.sh`; the jail's shell then runs those copies without the limit rather than fail, and `runner-cpu.spec` copies it), so a loop in engine code (the incident's was in `raftcheck`) ends in half an hour instead of never; what an engine command spends is its own CPU, not its children's. `./zn run --cpu` and the hook scripts do the same. Each goes through one shell function, `zn_lower_cpu <n>` in `z-nile/lib/cpu.sh` (it reads the limit in force and sets its own only when that is lower; `zn`, both hook scripts, the jail's shell and `bounded.pl`'s `sh -c` all source it), so a run under `./zn run --cpu 100` keeps 100 and the runner's 1200 is not lowered by the engine's 1800. The sweeper stays as it is (non-goal).
7. **One sentence, word for word, in five places** (the rule, below). Pinned by a spec. It is worded by class (probe, experiment, loop, background command), because "every command" would cover `ls`, which no agent follows and no reviewer could judge.
8. **The reaper is scoped to this repository.** The default scope is the main checkout (which holds every worktree), this repository's own Claude session folders (named by the path slug Claude derives from the main checkout, so another project's sessions are out) and the runner's temp folders under `$TMPDIR`. It refuses the option combinations that would turn it on a live machine (below).

### The rule (exact text; AC6 pins it in AGENTS.md and the zz-test, z-design, zz-execute and zz-review skills)
> Run every probe, experiment, loop and background command you start yourself (anything that is not the gate, a check, a `./zn` command or the spec runner) through `./zn run --time <seconds> -- <command>`: it stops at its limit, when it ends and when you do.

AGENTS.md carries it as a **Processes:** paragraph. zz-test gets a `## Bounded commands` section (the whole mechanism in one place: runner, limits and exit codes, the hook and why it fails open, Monitor, the reaper's three rules and its call sites, the CPU limits and that they only lower, SIGXCPU's limit, what each cannot do) and two lines under Hooks. z-design carries the sentence in the "Run the cheap ones now" bullet; zz-execute in Phase 1; zz-review gets item 12 in design mode and item 11 in code mode ("Bounded commands": did the probes run that way; does any script start something nothing stops). zz-rules' main-checkout list gets `run` and `reap` ("`./zn run` runs only a command that is itself allowed there"), its Other commands list both, zz-arch's layout lists the files and says that a Lune entry the gate runs joins `TOOLING` in `z-nile/engine/boundcmd.luau`, and `pickman/skills/pickman-test` tells agents to run its `lune run scripts/runtime-test` as `./zn run --time 600 -- ...`. The lesson `z-design/probe-free-cli-lines-in-prep` says "under an alarm": it changes to `./zn run` (the raft edits that lesson; a lesson's own wording is part of this rule). c0192 (the short lesson, depends on this issue) points at the runner.

### `z-nile/lib/bounded.pl` (new; reference: `experiments/ref-bounded.pl.txt`)
`./zn run [--time S] [--cpu S] [--] <command> [args...]`. `S` is a whole number of seconds; `--time` is 1 to 3600 (default 60), `--cpu` is 1 to 3600 (default: `--time`). Anything else exits 2 with the rule named and the usage line.
- Forks the command into a process group of its own through `sh -c 'c=$(ulimit -t); if [ "$c" = unlimited ] || [ "$1" -lt "$c" ]; then ulimit -t "$1" || exit 126; fi; shift; exec "$@"'`: **`--cpu` only lowers**. When the caller's limit is lower the runner says so (`bounded: the caller's CPU limit of N s is lower than --cpu M: it stays`) and reports against the lower one. Every process of the command carries `ZN_BOUNDED_DEADLINE=<epoch seconds>`.
- A **watchdog** in that group waits on a pipe only the runner holds open; if the runner dies however it died, the watchdog sends TERM to the group, waits two seconds and sends KILL. It also acts at deadline + 3 s if the runner is stuck.
- At the wall-clock limit the runner sends TERM to the group, and KILL two seconds later (exit **124**, "stopped at the wall-clock limit (--time S s): <command>"). INT, TERM and HUP are passed to the group the same way (exit 128+n). **When the process that started the runner dies** (the shell, or the session that owned it), the runner notices within a fifth of a second (it polls `getppid`, because a parent's death sends no signal) and stops the group the same way (exit **123**, "the process that started it is gone", distinct from 129 for a HUP): the captured "when its parent dies". The runner sets `SIGCHLD` back to its default at the start (an ignored one, inherited across `exec`, would make every `waitpid` fail and every status 255). It also means that `./zn run … &` in a foreground call is stopped within a fifth of a second of the call returning: the hook refuses that spelling and names `run_in_background`. A runner whose parent is gone before it starts is an orphan from the start; it keeps its other limits and the orphan rule finds it. When the command ends, **the group gets KILL** (nothing it left behind survives its exit).
- A command that **ended with status 1 or 152 (SIGXCPU) having used 90% or more of its CPU allowance** exits **125** ("stopped at the CPU limit (--cpu S s, used X s)"): the Rokit shim turns SIGXCPU into a plain exit 1, so the signal alone cannot say, and the CPU of the children (`times`, summed over all of them while the limit is per process) alone would mislabel a parallel command that failed for its own reason. A command with any other status near the limit keeps its status and gets a stderr note.
- Otherwise the command's exit status (128+n for a signal). stdout and stderr pass through untouched.
- Limits of the design, said plainly: a CPU limit (`ulimit -t`) does not stop a loop that spends its time in system calls (E18), so the engine's and the hook entry's CPU limits are a second line, not a guarantee; a process that calls `setsid` leaves the group (the reaper's deadline rule finds it if it is not a system binary); a SIGSTOPped runner stops its own timers (the watchdog's late deadline still fires); a command that ignores SIGXCPU is stopped only by the wall-clock limit.

### `zn` (touched)
First thing after `set -euo pipefail`: `if [[ ${1:-} == run ]]; then shift; export PATH=...; exec perl "<zn's folder>/z-nile/lib/bounded.pl" "$@"; fi`. The engine path gets `ulimit -t` of `ZN_ENGINE_CPU` (default 1800; a non-number is ignored) before `exec lune run z-nile/engine/main`, set only when it lowers the limit the caller has. `./zn run` is before that and has none of it (reference: `experiments/ref-zn-and-fence.diff.txt`).

### `z-nile/engine/boundcmd.luau` (new, pure; reference: `experiments/ref-boundcmd.luau.txt`) and `z-nile/guard-bash.luau` (new entry; `ref-guard-bash.luau.txt`)
- `boundcmd.check(command: string): Verdict` with `Verdict = { ok: boolean, rule: string?, program: string?, command: string?, say: string? }`; `boundcmd.explain(v): string`; `boundcmd.withoutHeredocs(text): string`.
- It reads one shell line the way a person does: quotes, `;` `&&` `||` `|` `&` newlines, `( )` `{ }`, `$(...)`, backticks, here-documents (their bodies are data), `sh|bash|zsh|dash -c '...'` and `eval` (recursed, depth 6), shell keywords (`do`, `then`, ...), and prefix commands (`env`, `time`, `command`, `exec`, `sudo`, `nice`, `xargs`, `timeout`, `stdbuf`, `caffeinate`, with their options and assignments).
- **Context**: `boundcmd.check(command, ctx)` with `ctx = { monitor: boolean?, background: boolean?, zn: string? }`; the entry fills it from `tool_name == "Monitor"`, `tool_input.run_in_background` and `ZN_CHECKOUT` (set by `pre-bash.sh`, so the refusal names the checkout's own `<checkout>/zn run`, which exists from a scratch folder, where the incident ran).
- **Refused** (rule), a listed set of forms, not "everything long-running": `lune run <target>` or `lune <target>` unless the target is in `TOOLING` (**unbounded**); `lune repl` (**interactive**); `node`, `ruby`, `deno`, `bun`, `luau`, and `python`/`python3` unless `--version`/`--help` or an inline script that passes the scan below (**unbounded**); `rojo serve` and `rojo ... --watch` (**unbounded**); inline Python as decided above (**unbounded**); `perl -e` with `while (1)`, `1 while`, `for (;;)` or `until (0)` in the script (**unbounded**) and with `alarm` (**alarm**: it leaves the tool child behind, E4); `caffeinate` without `-t`, and `caffeinate -t N <command>` judges the command (**unbounded**); a `while` or `until` loop wherever it stands in the line (after `then`, `do`, `!`, `time`, in a `$(...)`, in a `bash -c` string, or in the body of a here-document a shell reads), except `while read`, which ends at the end of its input, and a C-style `for ((;;))` with no condition (**loop**), and `tail -f`/`-F`/`--follow`, `watch`, `gh ... watch|--watch` (**follow**), both loops and follows unless `monitor`; `nohup`, `setsid`, `disown`, `daemonize` (**detach**); and (**background**) a call with `background` set that has a command which is neither bounded (the gate, a `check.sh`, `ci-verify.sh`, a `./zn` command, the wrapper, a `TOOLING` entry) nor one that ends by itself (`cd`, `echo`, `sleep`, `export`, `test`, `printf`, `git`, `gh`, `jq`, `seq`, the filters `tail`/`tee`/`head`/`grep`/`sed`/`awk`/`wc`/`sort`/`cut`/`tr`/`cat`, `for` and `case` and their closers, ...), and a foreground call that starts a job with a single `&` and has no `wait`. Redirections (`2>&1`, `&>log`, `>&2`) are part of their word and never separate commands. A command's own text, quotes and all, is what the refusal suggests wrapping. A here-document body is data unless the command that reads it is a shell; a `<<` counts only when its terminator line follows (an unterminated one, a `<<<` here-string, `$((1<<2))` and a quoted `<<X` hide nothing).
- The prefix commands (`env`, `time`, `nice`, `timeout`, `sudo`, `xargs`, `stdbuf`, `caffeinate`) are read with the options that take a value (`timeout -s KILL 30`, `sudo -u me`, `env -S 'cmd'`); `lune ... --help` and `--version` pass.
- Inline Python is read in every spelling the line can carry: a prefix (`FOO=1 python3 - <<E`, `env ...`), a body piped in (`cat <<E | python3 -`), `-c`; its string literals are not code (an edit that mentions `while True:` or `subprocess.` passes); a `python3 -` whose script is not a here-document of the same call, or is fed from a file (`python3 - < probe.py`, `cat probe.py | python3 -`), is refused as unreadable. A `cd` moves the folder for the commands after it (it is read from `split`'s output, like the here-document owner; an operand the scanner cannot resolve, `$X`, `~`, `-` or none, refuses the tooling match); a `&` ending a group (`(cmd)&`, `{ cmd; }&`) is a job like any other, and any `&` without a `wait` is refused in every kind of call. A filter first in a command with no file operand or `<` redirect (`cat`, `grep -c x`, `tr`) reads the tool shell's stdin, which never closes, so it is not "ending by itself" in a background call.
- **What it does not cover, said plainly:** a shell script run by name (`bash probe.sh`: its contents are not read), `npm`/`npx`/`yarn`, `make`, a program written in C, any interpreter not listed, and every spelling a one-line scanner cannot read (unbalanced quotes pass). The hook is a seatbelt that makes the common leaks refuse with a useful message; the guaranteed layers are the runner when it is used, the CPU limits, and the reaper, which now also takes the shells and the sleepers a loop leaves.
- **`TOOLING`** is the exhaustive list of Lune entries an agent may start bare: `tests/run` (also `z-nile/tests/run`, `pickman/tests/run`), `z-nile/affected`, `z-nile/roots`, `scripts/affected`, with `./`, `../` and `.luau` ignored, and **only this checkout's**: an absolute target must lie under `ZN_CHECKOUT` (its `.worktree/` folders are inside it), and a relative one passes only when the call's `cwd` (in the hook's payload) is inside it, so a scratch copy of the tooling is a probe like any other. Only `tests/run` is jailed, swept and CPU-limited by the runner; `affected`, `roots` and `scripts/affected` are short tooling with no limit of their own, and the file's comment says so. `z-nile/engine/main` (agents run `./zn`, which gives the engine its CPU limit) and `scripts/cicd` (it runs the minutes-long `runtime-test` and `deploy-beta`) are **not** in it: they are wrapped like `lune run scripts/runtime-test` and the mutation runners (`python3 ... mutants.py`), which take minutes (`./zn run --time <seconds> -- ...`; zz-rules' Merging step 3 says `./zn run --time 1800 -- lune run scripts/cicd`). A new Lune entry the gate runs joins the list (zz-arch says so). - **Passes**: `./zn ...` (including `./zn run ... -- anything`: only the program is judged), `check.sh` files, the gate, `lune --version`, `lune setup`, mentions of `lune run` inside strings or comments or here-documents, and anything it cannot read (unbalanced quotes).

### `z-nile/engine/reap.luau` (new, pure; `ref-reap.luau.txt`) and `cmd.reap` in `z-nile/engine/main.luau` (the edge; `ref-main-luau.diff.txt`, which also has the usage lines, `reapAuto` and the `sync` call)
`./zn reap [--dry-run] [--min-age S] [--root DIR]... [--under PID | --session-end] [--log FILE] [--quiet] [--auto]`.
- `reap.parse(text): ({ Proc }, { string })` reads `ps -axww -o pid=,ppid=,uid=,etime=,time=,lstart=,command=`; a line it cannot read is returned as a problem and printed (under `--quiet`, as one `reap: skipped (N unreadable ps lines)`), never skipped silently. `reap.markers(text, procs): { [number]: string }` reads `ZN_BOUNDED_DEADLINE` from `ps -axww -E -o pid=,command=` by subtracting the arguments already parsed (the environment is never otherwise kept or printed). `reap.sessionRoot(procs, self): number?` is the nearest ancestor of the reaper named `claude`. `reap.wantCwd(procs, opts)` names the pids whose folder `lsof -a -d cwd -Fpn -p ...` must read. `reap.decide(procs, opts): { Target }`, `reap.line(target, verb): string`, `reap.isToolShell(command): boolean`, `reap.checkOptions(args): string?` and **`reap.scope(main, uid, temp, roots): { roots, scratch, sessionAnywhere }`** (the default scope as a pure function of the facts the edge reads: the main checkout, the user id, the physical temp folder and the `--root` values; `reapRun` takes its options from it, a docs case pins that).
- **A process is stopped only when all of these hold**: it is the user's (`uid`); it is neither the reaper nor one of its ancestors; **neither it nor any ancestor is a detached `git maintenance` or file-system monitor** (the `gc`, `repack` and `pack-objects` they start are as legitimate as they are); its working folder is under a **root** (the main checkout of the repository, which holds every `.worktree/`) or a **scratch prefix** (this repository's own Claude session folders `<tmp>/claude-<uid>/<slug of the main checkout>`, where the slug is the path with `/` and `.` turned into `-`, followed by `/` or, for a worktree session, `--`; and the runner's `<$TMPDIR>/pickman-run.*` and `pickman-guard.*` folders; another project's session folders, another repository whose name only starts the same, and a folder that merely contains `claude-<digits>` are out of scope); **and** one of:
  1. **marked**: a program of `lune`, `git`, `sh`, `bash`, `perl` (TARGETS) or `node`, `python`, `python3`, `ruby`, `deno`, `bun`, `luau`, `rojo` (INTERPRETERS), never one inside a macOS application bundle, whose environment carries `ZN_BOUNDED_DEADLINE` (ten digits) that passed more than 5 s ago (only non-system binaries show their environment, and a `setsid`'d escapee of `./zn run -- lune ...` is one);
  2. **orphaned**: its program is one of TARGETS, INTERPRETERS or `sleep`, `tail`, `gh`, `grep` (Claude Code's tool shells run it as `ugrep`, and `find` as `bfs`: both are named), `watch`, `yes`, `caffeinate` (what a loop, a follow or a killed monitor's pipeline runs; a `tmux`, an editor or a login shell is not), or it is a tool shell; every ancestor up to launchd (pid 1) is one of those or of `zsh`, `env`, `sandbox-exec` (so no terminal, session or app owns it; a missing ancestor keeps it); and it is older than `--min-age` (default 60 s);
  3. **session end** (`--session-end`, or `--under PID`): it is a **tool shell** (a direct child of the session's `claude` process, or of `PID`, whose command sources one of Claude Code's shell snapshots, `/shell-snapshots/`), whatever it is running, with everything below it. **This rule needs no folder in scope under the default scope**: the shell is the session's by ancestry, wherever it has been (a `mktemp -d` clone, as zz-rules' merge procedure makes, or `/tmp`; round 4 found a live one of this session running for 4 h 41 m with a child blocked on a stdin that never closes). With an explicit `--root` (the checks) the folder test applies to every rule, which keeps the end-to-end check's dry-run gate meaningful. Reading of the Non-goal "other repositories": a shell a session of this project started is this project's work wherever it went; the user confirmed this boundary ("Yes, that boundary", 2026-11-01): the session's own tree is stopped by ancestry wherever it went, and unowned processes outside the repository's scope are never touched.
  A target inside another target's tree is listed once, with its descendants, all stopped with it. **The gap, stated:** after a session is gone (a killed terminal, a crash), its shell is found by the orphan rule only when its folder is in scope; one that went outside it (a clone in `$TMPDIR`) stays, because it is no longer anyone's child and nothing says whose it was. The orphan rule does not take other `mktemp` folders' work: it may be another tool's.
- **Refused option combinations** (`reap.checkOptions`, exit 2 naming the option): `--under` with a pid of 1 or less, or a pid that is not a `claude` process unless a `--root` is named; `--min-age` below 60 unless a `--root` is named; a `--root` that is empty, relative, `/`, the home folder, or contains `..`. A `--root` replaces **every** default scope, which is what the checks use.
- **Platform**: macOS (it reads BSD `ps` and `lsof`). Elsewhere `--auto` returns silently and an explicit `reap` exits 2 saying so; AC4 runs on macOS, which is where the gate's jail and `SETUP.md`'s primary host are.
- Edge (`cmd.reap`, in `main.luau`): one `ps`, one `ps -E`, one `lsof` per 200 candidates, then for each target a re-read of the `lstart` of **every** process of its tree (a changed one is left out; a changed root leaves the target alone), one `kill -TERM` for every target's remaining processes, then a shared wait of up to 20 polls of 0.1 s (one `ps -o pid=,stat= -p <all ids>` and one `sleep` per poll, so the time does not grow with the number of processes: about three seconds), then one `kill -KILL` for what is left (a `./zn run` watchdog ignores TERM by design, so a tree that holds a wrapped command takes the whole wait; AC4 has a decoy that ignores TERM and must be dead after the KILL), inside the hook's 20-second budget, and "COULD NOT STOP" (exit 1) if anything survives. One line per target on stderr: `reap: stopped pid N +k child(ren), age 14h02m, cpu 840m00s, <why>, cwd <folder>: <command, 100 characters, never the environment>` (`would stop` under `--dry-run`, `reap: no leaked processes` when there is none and not `--quiet`). `--log FILE` appends each line, timestamped, with one `printf >>` per line.
- `--auto` (what `sync` and the gate run): `guarded(true)` first (the publisher's own answer, asked without printing its message, which stays for the next caller that publishes), so inside a check run it returns at once and prints nothing; `--quiet`; any error becomes one `reap: skipped (...)` line; never a non-zero exit. `reap` is **not** added to `READ_ONLY` (it runs the repository guard like every command that is not read-only).

### Scalability

## Unknowns & experiments

- **E5: what does `ps` show of an orphan, and can the reaper tell whose it was?** `ps -axww -o pid=,ppid=,uid=,etime=,time=,lstart=,command=` parses with one pattern (etime in `dd-hh:mm:ss`, `hh:mm:ss`, `mm:ss`). `lsof -a -d cwd -Fpn -p ...` gives the folder (0.06 s). ## Acceptance criteria

### Checked
- **AC1**: `./zn run [--time S] [--cpu S] -- <command>` (limits up to 3600 s) stops the command and everything it started at its wall-clock limit (exit 124) or CPU limit (exit 125, only on unambiguous evidence), kills what it leaves when it ends, stops the group when the runner itself dies and (exit 123) when the process that started it does, passes INT/TERM/HUP, gives every process `ZN_BOUNDED_DEADLINE` and a `ulimit -t` that only ever lowers the caller's, refuses a limit it cannot honour with exit 2, and starts before the engine in the caller's folder.
