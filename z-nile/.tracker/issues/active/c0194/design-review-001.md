### F1 [high] The outer-sandbox probe looks at the home's `.cache/.tmp`, but agents' trees are in the checkout root's `.cache/.tmp`: an accepted outer-sandboxed run writes into an agent's clone (review 004 F2 reopened)

Evidence: The design puts agents' trees and merge clones in "the main checkout's" `.cache/.tmp` (the hook exports `TMPDIR=$CLAUDE_PROJECT_DIR/.cache/.tmp`, the root). The probe, and runner.spec's case, look only at `<home>/.cache/.tmp` (`z-nile/.cache/.tmp`), which never holds an agent's tree. zz-test also requires an accepted outer sandbox to leave the root's `.cache` writable. I built a fixture copy of the prototype's runner (the files `copiedRun` copies) and ran `lune run tests/run -- tests/probe/seen.spec.luau` from its `z-nile/` under an outer `sandbox-exec` profile. The profile denies every write except `/dev`, `<repo>/.cache` and `<repo>/z-nile/.cache`, denies a symlink at the top of either `.cache`, and denies the network. The probe spec also tried to write `../.cache/.tmp/agent-clone.X/planted-by-spec`.
- Tree planted at `<repo>/.cache/.tmp/agent-clone.X` (where the design puts agents' trees): `note: not jailed (already inside a sandbox, and macOS can't nest them); the outer sandbox protects the repository`, `1 passed`. The spec's write into the agent's clone succeeded (`planted-by-spec` was there next to `left`).
- Control, tree planted at `<repo>/z-nile/.cache/.tmp/agent-clone.X`: refused, `(other temporary trees in .cache/.tmp)`.

Critique: The old guard (`escapes`' user-temp-folder probe) refused whenever the agents' folder was writable at all, whatever it held. The new one checks a folder the agents don't use, and checks contents rather than writability. The tempting fix is to point the same contents check at the root's folder. That keeps the time-of-check hole, and it refuses every nested fixture run, whose own root `.cache/.tmp` is writable inside the outer jail.
Consequences: A rule of "writable means leak" for the real checkout's `.cache/.tmp` folders needs a precise set of folders. The run's own home `.tmp` stays allowed only through its own run folder. zz-test's outer-sandbox sentence then has to say that an outer sandbox must close `.cache/.tmp` while leaving the rest of the root's `.cache` writable.
Recommendation: In `escapes`, treat a writable `.cache/.tmp` as a leak, whatever it holds, for each folder in the set above. Skip the folders under a ceiling `.cache`, so nested fixture runs (runner.spec, fence-leftovers, lock-start-ids, c0127/reuse) still pass. runner.spec gets these cases: a run inside an outer sandbox that leaves `<repo>/.cache/.tmp` writable refuses even when that folder is empty; the same for a home's `.tmp`; and a nested fixture run is accepted. Drop the "holds only `pickman-run.*`" exemption, or justify it for the home's folder alone. Add the outer-sandbox profile above to the Unknowns as an experiment.

### F7 [medium] The stray clearing deletes the folder of a live run that is waiting for the lock
Where: Design "Guards" row 5 ("The runner now clears, under its lock, every other `pickman-run.*` of its home (none can be live)"); `.worktree/proto-c0194/z-nile/tests/lib/fence.luau:883` (folder made), `:896` (jail decided), `:902` (`takeLock`, which waits), `:903-908` (clearing).

Critique: Holding the lock is not the same as being the only live run. The design reads liveness from a lock that is taken after the thing it judges was made.

Write the run's pid and start id into its folder, as one file written whole (`fence.startOf` already exists for the lock's records), and clear only folders whose owner is dead or missing. Recommendation: Record the owner in each run folder and clear a stray only when its owner is not alive.
