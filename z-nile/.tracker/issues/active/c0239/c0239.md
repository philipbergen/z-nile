# c0239: Full gate only at the merge

## Problem
From the user (2026-10-26), part of c0165's capture "Reuse passed test results":

- **The full gate runs only at the merge** (`./zn land`, the PR's merge, `done`). Every step before it (the author's iterations, the review, the pre-PR gate) runs only the affected specs.

Scope decision (user, 2026-10-26): "The full gate at merge runs all for real so we can find out if dependency graph has gaps" (the merge's full gate may not reuse fingerprinted passes: every spec runs).
Scope decision (user, 2026-10-26): of the full gates near a raft's merge, "done's run + CI" count as the merge's: `./zn done` runs every spec for real, and the merge condition's "full gate on the final head" accepts that run when the content is the same, instead of running it again; CI stays as it is.
Decided with the user (2026-10-31): "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected." (zz-execute Phase 0's baseline, Phase 3 steps 2-3, Phase 4 step 1, zz-review code mode item 1, Phase 5 step 2, `./zn done`'s gate and the raft `check.sh` template's RC0 are affected-only; the merge keeps one full gate.) The 2026-10-31 session also decided "Phase 0 gets no full red-main baseline; red main surfaces at the merge gate".
Decided with the user (2026-11-03), c0165 design review 004 F2: asked what zz-execute Phase 0 does about red main, the user chose "No baseline": Phase 0 runs no gate and reads no CI result; red `main` first shows at `./zn done` and the merge.

Scope decision (user, 2026-11-04), design review 001 F1: asked which of the two decisions above governs `./zn done`'s gate (2026-10-26: `done` runs every spec and the merge accepts that run; 2026-10-31: `done` is affected-only and the merge keeps the one full gate), the user chose "A: done affected, merge full". `./zn done` runs the affected gate; the merge's clean-clone `--full` is the one fresh full gate, which can catch graph misses and what only a clean checkout shows. The 2026-10-26 lines about `done`'s full run counting as the merge's, and the Solution bullet's "the merge condition: the same content as `done`'s full run, reused", are replaced by this choice; no `--full --reuse` is built.

An affected baseline on an unchanged worktree selects no spec, so it can't stand in for a red-main check (c0165 design review 003 F1). Depends on c0165 (the affected selection and reuse it builds on) and c0180 (affected selection by command).

Split from c0165 (user, 2026-11-03: "Split it"), which had grown to a 600-line design and a sixth review round; c0165 keeps the fingerprint, reuse and store outcomes, and this issue keeps the outcomes below. Every outcome is the user's 2026-10-26 capture, not narrowed.

Prior design work: c0165's prep branch `prep-reuse-test-results` (commit a03b4995; `z-nile/.tracker/issues/c0165/`: the design, six review rounds and their answers, and the acceptance specs) holds a design for the whole of c0165; this issue's prep takes the part that is its own.

## Non-goals
- The affected selection and fingerprint reuse themselves: c0165, c0180.
- Telling a red `main` from the raft's own failure at `done`: c0240 (it reports "fails on the base too"); take care that a spec the raft added, absent at the base, is not reported as red `main` (c0165 design review 006 F1).

- Reusing `done`'s full run at the merge (`--full --reuse`, a full digest, a read-only path to the main checkout's db): not built (Scope decision, 2026-11-04). `done` is affected and the merge's clean-clone full gate runs every spec, so nothing here depends on c0165's `gates` table beyond the affected mode.
- The "depends on ... c0180" sentence in the Problem is c0180's own ordering (c0241 gives c0180 `depends_on` c0239); this issue does not wait for c0180.

## Solution
- Gate modes by step: author iterations, stream checks, review, after merging `origin/main`, raft RC0: `--affected`; `./zn done`, `./zn land`, CI, `setup.sh`: `--full`, fresh; the merge condition: the same content as `done`'s full run, reused.
- Restate the rule in zz-execute, zz-rules, zz-review, zz-test, `templates/prompt.md`, the raft `check.sh` template, `AGENTS.md` and the stop hook (one project-scoped affected call from the selector's forcing rules, falling back to the unscoped call for any answer it can't use).

## Design
The Solution's gate-mode bullet lists CI among the `--full` runs; CI runs only `setup.sh --tools` (c0172 pins "GitHub Actions does not run it"), so the one full gate is `./zn land`, `setup.sh` and the merge's clean clone.

c0165 builds the affected selection and reuse. This issue states **which step runs which gate**, makes `./zn done` run the affected gate, and moves the stop hook to a project-scoped call. It builds no reuse of the full gate (Scope decision, 2026-11-04). It decides nothing about selection (c0165, c0180), waiting or crashes (c0238) or learning (c0240).

Decisions it relies on (quoted from the Problem): "The full gate at merge runs all for real so we can find out if dependency graph has gaps"; "I want a full end 2 end to have run before the final merge into main ... Along the way we run efficiently and only the affected"; Phase 0 gets no baseline (2026-11-03, "No baseline"); and, 2026-11-04, "A: done affected, merge full".

### `./zn done`
- `z-nile/engine/gate.luau`: `doneGate(env)` returns `"affected"` (was `"full"`) or `"promoted"` (unchanged: inside a spec run, without `PICKMAN_DONE_GATE=1`).

### Stop hook (`scripts/hooks/stop.sh`)
Today it runs one unscoped `scripts/check.sh --affected` whenever a gated path changed. It becomes: run `lune run z-nile/specs -- scope` (no arguments), then run `scripts/check.sh --affected --project <name>` when the answer is exactly one project name **and** the command exited 0, and the unscoped `scripts/check.sh --affected` for everything else (`ALL`, any other output, an empty answer, a nonzero exit even after printing a name, a tree before c0114 with no `z-nile/specs`). The hook's own filter of gated paths is unchanged.
- **`scope` reads the gate's own change set** (design review 002 F1): the same set `check.sh --affected` selects from (the branch against its base, plus uncommitted and untracked files, read by the function c0165's gate calls), never the hook's filtered list, so a change to the root `scripts/`, `zn` or a root config, or a committed change on the branch, is seen.
- `select.scope(ctx, changed)` (a pure function in c0165's `z-nile/lib/select.luau`; the argument order follows `select.affected(ctx, changed, only)`) returns a project name only when (1) `select.affected(ctx, changed)` is not `ALL`, (2) it holds at least one spec, (3) every selected spec file lies in that one project's home, and (4) every changed path lies under that project's home or its tracker root. Anything else, and any read that fails, returns `ALL`. Rule (4) keeps the other projects' static stages (format, lint, types, build) in the unscoped call whenever their files change.
- **The limit, stated** (user decision, 2026-11-04, design review 002 F6: "ship it, state the limit"): once c0165 lands, a spec that declares `*` is selected for every edit outside z-nile (c0165.md line 220, narrowed for two specs by c0242), so rule (3) is false for a pickman, arcade or game edit and `scope` answers `ALL`: the hook runs exactly today's call until those `*` specs are narrowed. This issue ships the mechanism and the cases that keep it safe; it saves nothing on the real repository yet. E5 measures this after c0165 lands.
- The CLI prints the answer and nothing else; the pure function carries the rule, tested with plain tables.

### Scalability
A change's gate time falls from several full runs (author, reviewer, `done`, merge) to affected runs plus the one full gate at the merge; `done`'s run is now the affected gate (seconds to a minute) instead of about 230 s idle. The stop hook's scoped gate is never narrower than the unscoped one, and today (the `*` specs) it is never narrower and never faster: it answers `ALL`.
### Maintainability
One rule table (zz-test) with a line in each file that restates it, all pinned by one docs spec; `doneGate` is one pure function; `select.scope` is one pure function over the selector.
### Usability
An author runs `--affected` throughout and sees the full gate once, at the merge. A red `main` first shows at the merge (the user's "No baseline" decision).
