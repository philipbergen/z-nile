# c0256: Dispatch retry passes answer

## Problem
dispatch: a headless step that stops with questions.md gets the user's answer back when the run is retried

c0117 (`./zn dispatch`) stops a step that needs the user with `.cache/dispatch/<id>/questions.md`; the user answers and retries, but c0117 defines no input that carries the answer into the re-run step. c0247 (z-ticket confirms intent) needs it: a headless z-ticket (`dispatch new "<words>"`) writes its restatement as a question and stops, and the user's approval or correction must reach the retried step.

Decided with the user (2026-11-05), c0247 design review 001 F1: "Restate via questions.md": headless z-ticket writes the restatement to questions.md and stops "needs the user"; the user approves or corrects it with `dispatch retry`.

Scope decision (user, 2026-11-08): "Widen c0256". c0256 hands the re-run step the full list of restatements and corrections with their dates and the user's reply, not only the latest question and reply. (Decided during c0260's prep, which depends on c0256 for it.)

## Non-goals
- The wording of z-ticket's confirmation is c0247's. This chore only gives a retried step the user's answer.

## Solution
- `./zn dispatch retry <id>` accepts the user's answer to the questions.md the step wrote (a file or text) and hands it to the re-run step with the question, so the step reads both.
- It works for any step that stops with questions, not only z-ticket.
- Detail from c0247 design review 002 F1: `dispatch new` keeps the original words so a retry can re-run the step; a step that stops with `questions.md` is recorded as "needs the user", never as a failure ("z-ticket made 0 issues"); the retry of a `new` run names its id; and the reply reaches the re-run step together with the question.
- On `dispatch retry` (and when a re-run step starts), the dispatcher hands the re-run step every restatement and every correction of the capture so far, each with its date, in order, together with the user's reply to the latest question; the re-run step reads them from the state folder the dispatcher names in its prompt. c0260's capture record copies them, dated, into `## Ask (verbatim)` and records the restatement and the reply as `### Q1` of `## Interview`. A dispatched capture's ask is dated from the first message, not from the retry. (Needed by c0260, which depends on c0256 for it.)

## Design
A chore: tooling only (`z-nile/engine/`), nothing under any game's `src/`. It gives `./zn dispatch retry` an input for the user's answer and gives every re-run step the whole conversation so far, as files in the run's state folder.

Decisions it relies on (quoted): "Restate via questions.md" (the user, 2026-11-05, c0247 design review 001 F1: headless z-ticket writes the restatement to questions.md and stops "needs the user"; the user approves or corrects it with `dispatch retry`) and "Widen c0256" (the user, 2026-11-08: c0256 hands the re-run step the full list of restatements and corrections with their dates and the user's reply, not only the latest).

### The exchange (a new pure module)
`z-nile/engine/exchange.luau` (pure over names and texts; the dispatcher reads and writes the files). Each run's state folder gets `exchange/`, one file per message, `NNN-<kind>.md`:

| kind | what it holds | written by |
|---|---|---|
| `ask` | the user's own request, word for word, only as `001` | `./zn dispatch new "<words>"`, at its start |
| `question` | a copy of the `questions.md` the step stopped with (a restatement is a question), and the step that asked | the dispatcher, when the step ends |
| `answer` | the user's reply (an approval or a correction) | `./zn dispatch retry` |

A file is `date: <UTC time>` (the dispatcher's `now()`, `YYYY-MM-DDTHH:MM:SSZ`), for a question a `step: <name>` line (the step that asked), one blank line, then the message exactly as it was written (no escaping, no newline added). Public API (all pure):
- `exchange.name(n, kind)`, `exchange.parseName(name)` (three digits, a known kind, `.md`; nothing else is a name).
- `exchange.render(date, body, step?)`, `exchange.parse(name, text): (Entry?, string?)` (`Entry = { n, kind, date, step, body }`; refuses a missing or loose date line, a question without its `step:` line, a step line on any other kind, naming the file).
- `exchange.order(names)`: the names in number order however the folder listed them; refuses a stray name, a gap, a repeat and a broken alternation (an `ask` only first, a `question` after an `ask` or an `answer`, an `answer` after a `question`). Names that start with a dot are not part of it.
- `exchange.next(names, kind)`: the next number, or why that kind may not follow (also: the exchange holds 999 messages and says so when full).
- `exchange.seal(texts)`, `exchange.changed(sealed, texts)`: the sha256 of each file the dispatcher wrote, and the first difference now (`added X`, `changed X`, `removed X`); no seal means nothing was written.
- `exchange.answerRefusal(text)`: why an answer is refused (blank, over `LIMIT` = 64 KiB, a NUL byte), or nil. `exchange.NO_REPLY`: `(no reply: the user ran retry without an answer)`.

The order of the conversation is the number; dates are information, not the key.

### The dispatcher (adapter, `dispatcher.luau`, `dispatch.luau`)
1. **Reading is strict.** `exchangeRead(st)` refuses an `exchange` folder that is a link and any entry that is not a regular file (`readlink`, because `fs.isFile`/`fs.isDir` follow links; review 001 F4), runs `exchange.order`, compares the files with the seal in `state.json` (a step that rewrote, added or deleted a message is noticed: F5) and parses every file (a numbered file with no date line is refused: F9). Every use of the exchange goes through it.
2. **Writing and naming are safe.** `exchangeAdd(st, kind, body, step?)` reads first, asks `exchange.next`, writes the whole file under its final name with `sh.writeReplacing` (a fresh exclusive temporary file, renamed: a link planted at that name is replaced, never followed: F4), records its sha256 in `st.sealed` and saves the state. Every name the dispatcher picks in a folder a step can write (`answered-N.md`, `questions-refused-N.md`, `exchange-<time>`, `exchange-forgotten-<time>`) comes from one helper, `freeName`, for which "free" means nothing at all there, a link included (`readlink`; round 2 F2), and every move is `fs.move` (a rename that never follows a link), never `mv`.
3. **A step stops with questions.** After a model step ends, the dispatcher reads the exchange (a step that changed it fails) and copies the step's `questions.md` into it as the next `question`, with the step's name, **always** (no test of whether the last message is a question, because no step starts with an open question: item 5; review 003 F2). A question that is blank, over 64 KiB or holds a NUL byte, a `questions.md` that is a link, a rewritten or stray file and a full exchange are each the exchange refusing: the step is recorded as `failed` with the reason and its spend row is written as for any step (F7), and the question is set aside as `questions-refused-N.md`, so the chain stops on the failure and not on a question nobody can answer. A `z-ticket` that made no issue and left `questions.md` is a question stop, not "z-ticket made 0 issues". One that **made an issue and also left `questions.md`** fails (review 004 F1: a capture asks before it makes): the step is `failed` naming the issue ("z-ticket made <id> and asked a question … `./zn dispatch <id>` goes on with the issue, or `retry new --forget-exchange` drops the capture"), and the question is set aside as `questions-refused-N.md` and never enters the exchange, so the retry adopts the issue (item 8).
4. **`./zn dispatch retry <id> [--answer <text> | --answer-file <path>] [--forget-exchange]`.** Before anything is touched: both flags, a repeated flag, a blank answer, one over 64 KiB or with a NUL byte, a file that is not a regular file (a link included), a link at `questions.md`, and `--forget-exchange` with an `--answer` when no `questions.md` waits, or for `new` (it drops the capture, so there is nothing to answer), are refused with the reason, all decided before the exchange is moved (review 003 F5). Then `--forget-exchange` sets the exchange folder aside as `exchange-forgotten-<time>` (never deleted) and drops its seal (the user's way past a record a step damaged, named in every refusal of an unreadable exchange; a boolean flag in the option parser). Then the exchange is read (a refusal says how to go on). The **answer** is, in this order: the flag's text or file; else what the user **wrote into `questions.md`** (the way zz-rules has always said to answer: when the file differs from the question the dispatcher copied, compared as an editor leaves it, without line-end and trailing-space differences, the whole edited file is the answer: F1, round 2 F5); else `NO_REPLY` (a retry with no answer still re-runs, as in c0117, for the user who fixed something outside the text). A flag together with a real edit is refused, naming how on (restore the file from the exchange's question file, or delete it and use the flag); a blanked file with a flag takes the flag, and without one is refused; a deleted `questions.md` lets a flag answer the exchange's last unanswered question (nothing to move). When the retry **itself** copies the question (a run waiting from c0117, or one whose dispatcher died before the copy), any answer written in the file is inside the copy, so a plain retry records `UNKNOWN_REPLY` and the step is told to read the question file: text the user added to its question is their answer, and if it holds only its own question the user gave no reply and the question stands (round 2 F4, review 003 F4: it must not read its own proposal as approved). The order is: the question is copied if it is not yet; **the answer is written first, with `st.answering` (the sha256 of the `questions.md` it was written for) saved in the same write**; `questions.md` is set aside as `answered-N.md`; the marker is cleared; the step re-runs. A retry that died between the last steps leaves the **recorded** half state (`questions.md` with exactly that hash): the next retry only finishes the move, and a flag then is refused ("an answer is already recorded"); any other waiting `questions.md` after a last answer is a new question, copied and answered as usual (F10, round 2 F1: the state is recorded when entered, never guessed from the files).
5. **The re-run step is told, and told the truth.** `modelStep` reads the exchange (an unreadable one refuses the step, naming the file and the way on, before any CLI starts) and gives `dispatch.prompt` the ordered names, the step that asked the latest question, the step the item's last attempt ran, and whether the latest answer is `NO_REPLY` or `UNKNOWN_REPLY`. With at least one message the prompt gets one paragraph after the "You are running…" line, in one of these forms (F2, F1, round 2 F11): the step that asked the latest question **and ran last** reads "This is a re-run … the last file is an answer: do not ask again what it settles" (or, after `NO_REPLY`, "your question stands unanswered: decide whether you can go on without it, and if not write questions.md again and stop"; after `UNKNOWN_REPLY`, "read the answer in the question file"; with a question last, "it has no reply"); any other step, or the same step after something else ran, reads "Earlier steps of this run have already exchanged messages … They settle those steps' questions, not yours: an approval there is not an answer to a question you must ask the user" (so c0260's z-design, which must ask the user to confirm a capture, is shown the capture's conversation and is not told it was confirmed). With nothing exchanged the prompt is byte for byte the first run's. **No step starts with an open question** (review 003 F2): when the exchange ends in a question and no `questions.md` waits (the user deleted it, then retried; a fresh `dispatch <id>` never starts the step then: the chain stops, "z-design ended but <id> is still new"), `modelStep` first records the answer `WITHDRAWN` ("(no reply: questions.md was removed without an answer)"; the prompt treats it as `NO_REPLY`: the question stands), so a question a step leaves after it is always its new one, copied at the stop, and a flag answers that one. This is the one place a model step starts, so the chain, one-step runs and every retry get it.
6. **A step started by hand while a question waits starts nothing** (F6): `dispatch <step> <id>` prints "a question waits … retry <id> --answer …" (exit 3), as `dispatch <id>` already stops on it; the retry sets the question aside first and then starts the step.
7. **A nested step** (a review the author started through `./zn dispatch zz-review`) that stops with questions cannot be answered by a retry of its own folder, which nobody retries: its stop message tells the author to write these questions into its own `$ZN_DISPATCH_DIR/questions.md` and stop. The user's answer reaches the re-run author, which dispatches its review again, and **that nested step's prompt also names the exchange of the run that started it (read only, through the same strict reader and the parent's seal) with "an answer there may settle a question you asked before"** (round 2 F3): the answer reaches the step that asked, with no file moved and no state shared.
8. **A capture (`dispatch new "<words>"`).** At its start (not in a `--dry-run`): if a `questions.md` waits, the words are not taken and the chain stops on the question; if the slot's last capture **failed or was lost and still has its words**, the new words are refused ("`retry new` re-runs it, or `retry new --forget-exchange` drops it": round 2 F7); otherwise any earlier `exchange/` is set aside as `exchange-<unix time>/` (never deleted; the seal is reset), `001-ask.md` records the words with the time of this first message, and `st.pushes` is reset. The stops of a capture name `new` (`./zn dispatch retry new`): the chain's facts carry the display id `new` for a blank id. `retry new` with a recorded ask first asks item 9 which issues this capture's own pushes added. **Exactly one is adopted** (review 006 F1), as when the step succeeds: the slot is saved finished, the capture's exchange and its seal move to that issue (refused if the issue already has an exchange), nothing is re-run and the message says `./zn dispatch <id>` goes on with it (an `--answer` given is said not to have been taken); this covers z-ticket dying after `./zn new`, failing after it, and making an issue and then asking. More than one refuses, naming them and `retry new --forget-exchange`. An issue another session landed never counts, so a capture that waits on a question, or one that failed, is retried at once. With none made it re-runs z-ticket with those words. `dispatch new` saves the reset seal at once after setting an earlier exchange aside, and its refusal names `retry new --forget-exchange` (review 004 F3). Without an ask it **clears the slot** (a c0117-era waiting capture is set aside as `answered-N.md`, the state's outcome is reset) and says to start again with `dispatch new`, and refuses an `--answer`. When z-ticket makes the issue, the slot `new` is saved as finished (`outcome ok`, "captured as <id>", no seal) before the run moves to the issue's folder, and the issue's state (with the moved exchange's seal) is saved right after the move and before the spend is recorded (review 004 F3) (F3: it stayed `running` after every capture, so the second `dispatch new` was refused as "lost"), and the exchange moves with it, seal included, so the capture's whole conversation belongs to the item it made. c0260 reads it from there.

Server authority: none (tooling). Pure/adapter split: `exchange.luau` and `dispatch.prompt` are pure; every read, write, link test, `os.date` and the process are in `dispatcher.luau`.

9. **The pushes a run makes are recorded before they are made** (review 004 F2). `broker.push` gains an optional `intent(base, sha)` hook, called after its fast-forward and tracker-state checks and just before `git push`: `base` is main as the broker fetched it, so the commits `base..sha` are this request's alone, whatever other sessions landed. The dispatcher's hook appends `{base, sha}` to `st.pushes` and saves, so a `kill -9` before, during or after the push leaves the intent, and origin tells whether it landed. `dispatcher.issuesAddedBy(ctx, pushes)` (a new function of `dispatcher.luau`; the `originIssueIds` of the real context goes) reads main like every other check does, `freshMain`: fresh from the pinned URL into the dispatcher's own ref, with its retries. It returns the issue files added in `base..sha` (`git diff --no-renames`, so a user's `diff.renames` cannot hide a new file; the path pattern is `…/issues/<id>/<id>.md` only, the folder an issue is created in, so a move to `active/` or `done/` is not a capture, and an executor must not swap it for `publish.itemPath`, which normalizes states and would count moves: review 006 F2) for each push whose `sha` is an ancestor of that fetched main. **It has three answers, and "cannot tell" refuses** (review 005 F1): a fetch that fails, a `merge-base` that exits other than 0 or 1 and a failed diff return nil and the reason, never an empty list, because "none made" is the answer that lets a second capture run. `retry new` refuses before anything moves ("cannot tell whether this capture made an issue: <why>; nothing was changed, run the retry again"); the z-ticket step's end fails the step ("could not tell what z-ticket made: <why>; `retry new` checks again"), or, when `questions.md` waits, leaves the question waiting, because the retry's own check runs before the answer is taken. It answers two questions exactly: what **z-ticket's own step** made (the pushes after the step's start: none is a question stop, one is the capture, more than one or one with a question fails), and what **a capture** made before its dispatcher died (all `st.pushes` since `dispatch new`, which resets them, as does `--forget-exchange` on `new`). c0117's check "z-ticket made N issues" counted origin's whole issue list and failed whenever another session landed an issue during the step; it is exact now. `st.before`, `--before` and the flag `--recapture` of the first answer to review 003 F1 are gone.

### Scalability
A run's exchange is at most 999 small files (a round is two); the prompt names them, it does not paste them. An answer is at most 64 KiB. `exchange.order` sorts the names of one folder.
### Maintainability
One reader per format (`exchange.parse`, behind one strict `exchangeRead`) and one pure ordering rule used by the dispatcher and the specs; c0260's capture record and the board can read the same folder. The prompt text is three short paragraphs in `dispatch.prompt`.
### Usability
The stop message tells the user what to type (`retry new --answer "…"`) and that writing into `questions.md` works too, a mistyped flag is refused with the reason before anything moves, a plain `retry` still works, and a refusal that blocks a retry says how to go on.

## Acceptance criteria

### Checked
- AC1: the exchange module names, renders, parses and orders messages as specified: a message is kept exactly, a question names the step that asked, a loose date line, a stray name, a gap, a repeat and a broken alternation are refused, the next number follows the last, the exchange holds 999 messages, the seal notices an added, changed or removed file, an answer or a question over 64 KiB, blank or binary is refused, and a text is compared as an editor leaves it.

- AC3: a step that stops with questions leaves its question, dated and with its step, in the run's exchange; `./zn dispatch retry <id>` takes the user's answer from `--answer`, `--answer-file` or the edited `questions.md`, stores it after the question, sets `questions.md` aside as before and re-runs the step, which can read both; a retry with no answer still reruns and records no reply; and the dispatcher refuses what it cannot take safely before anything moves (both flags, an edit with a flag, a blank, oversized or binary answer, an answer where no question waits, a link, a rewritten or unreadable exchange), fails a step that rewrote the exchange with its spend recorded, finishes a retry that died after storing the answer from a recorded marker, never from a guess, and skips a planted link when it picks a name.
