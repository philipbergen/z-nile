### F1 [high] `retry new` refuses every waiting capture once any other issue has landed on origin since the capture began, and the only way on drops the capture
Where: Design, The dispatcher, 8 ("`retry new` with a recorded ask first compares origin's issues with `st.before`: an issue made since … refuses, naming it"); prototype `retry` (`if st.before then … if #made > 0 then return refuse(…)`), which runs for every `retry new` with an ask, whatever the slot's outcome.
Evidence: probe R1 (r3b.spec). `dispatch new "my words"` with z-ticket in `questions` mode stops: "stop: needs the user: read questions.md, then ./zn dispatch retry new --answer …"; exchange `001-ask.md,002-question.md`. Then another run lands an unrelated issue (a one-step `dispatch z-design c0010` whose script runs `./zn new issue c someone-elses-thing`: `pickman/.tracker/issues/c0020/c0020.md`). Then the user answers the restatement: `retry new --answer "Approved."` prints "stop: c0020 was made since this capture began: if it is this capture, ./zn dispatch c0020 goes on with it; otherwise ./zn dispatch retry new --forget-exchange drops the capture", exit 1, "z-ticket runs after retry: 0", and the exchange is unchanged. The capture never stopped as lost or failed: z-ticket only asked its question, as c0247 makes it do on every dispatched capture.
Critique: this is the flow the chore exists for (c0247's restate-and-approve, c0260's rounds of corrections, each a `retry new`). In this repository other sessions land captures all the time (`git log` on origin/main today: `cc7aa2b7 tracker: new c0290 …`, `36a9d032 tracker: new c0289 …`, `94e3422a tracker: new c0291 …` within minutes), and a capture can wait hours for the user's answer, so the refusal is the normal case, not an edge. Its first suggestion sends the user to dispatch someone else's issue; its second throws away the capture's conversation. The guard was added for review 002 F6 (a capture that landed its issue and died), but it is keyed on "any issue new on origin", which is shared state other writers change, not on what this capture did. The tempting fix is to skip the check after a question stop only; a lost or failed capture then still refuses on another session's issue.
Consequences: telling "this capture's issue" apart needs a fact only this run writes. The run's publish broker is the only way a dispatched step lands on main, and the state already lists what it pushed (`pushed`, "the commits its publish broker pushed to main"); whether that list is saved before a `kill -9` of the dispatcher must be checked, since the case review 002 F6 added kills it right after `./zn new`.
Recommendation: run the check only when the slot's last z-ticket attempt ended `lost` or `failed` (a question stop means z-ticket ended and was judged; the "made" test already ran or was skipped by design), and count as "made by this capture" only the issues added by commits this run's broker pushed (record them when the broker pushes, in the same save, so a killed dispatcher leaves them: zz-arch/record-crash-states-when-entered); an issue another writer landed never counts. If the pushes cannot be recorded before the kill, escalate to the user: the options are (a) the refusal lists the candidates with their titles beside the capture's words and a flag continues the capture anyway, or (b) the check is dropped and a double capture after a kill is accepted. Spec cases (capture.spec, promoted): R1's sequence expects the retry to run z-ticket once, record `003-answer.md` and move the exchange to the issue it made; the existing "landed its issue and died" case keeps refusing; and a lost capture after an unrelated landing re-runs. Rows: "a question stop's retry never refuses on another writer's issue" (mutant: today's unconditional check) and "only this run's pushes count" (mutant: any new issue counts).
Lesson: z-design/slot-state-proven-by-two-runs

### F2 [high] The question copy is still guessed from the files ("copied already" when the last message is a question), so after a deleted questions.md the step's next question is never recorded, and the next plain retry stores that question as the user's answer
Where: Design, The dispatcher, 3 ("copies the step's `questions.md` into it as the next `question`, … once"); prototype `exchangeQuestion` (`if last and last.kind == "question" then return nil -- copied already`); Design 4 ("a deleted `questions.md` lets a flag answer the exchange's last unanswered question").
Evidence: probe R2 (r3.spec). `dispatch c0010` stops with "Which scope?" (`001-question.md`). The user deletes `questions.md` (the design gives a deleted file a meaning) and runs a plain `retry c0010`; the re-run step is told "The last file is a question: it has no reply" and writes a new question, `## Q2\nA DIFFERENT question`. The chain stops "needs the user", but the exchange is still only `001-question.md`: the new question was not copied. `retry c0010 --answer "answer to Q2"` then says "stop: questions.md was edited and --answer was given: use one of them (restore it from …/exchange/001-question.md, or delete it and use --answer)": the step's own new question is taken for a user's edit, and the way on it names would answer the old question. A plain `retry c0010` then writes `002-answer.md` = `## Q2\nA DIFFERENT question\n`, sets the file aside as `answered-1.md`, and the re-run is told "The last file is an answer: it replies to your latest question, so do not ask again what it settles". The record c0260 copies into `### Qn` pairs "Which scope?" with the step's own words as the user's answer, and Q2 is nowhere. The same happens without a retry: with `questions.md` gone, `dispatch c0010` no longer stops on it (the stop reads the file) and the chain runs the step with the question still open.
Critique: review 002 F1 found the half state guessed from the files and the design fixed it with a recorded marker; the same kind of guess sits one function away ("the last message is a question" is read as "this `questions.md` was copied"), and it is wrong whenever a question was left open without an answer. This prep's own lesson says a state is recorded when it is entered, never guessed. The tempting fix is to compare the waiting file's text with the last question's, which a user's edit breaks (it would copy the edit as a second question, and the alternation then refuses it).
Consequences: the open question needs a defined end when no answer comes, which is one more answer marker and a prompt sentence; once every step start closes an open question, "the last message is a question" means "copied at the stop and not yet answered" at the retry, by construction.
Recommendation: question the mechanism, not the hole: make the invariant "no step starts with an open question". In `modelStep`, the one place a step starts, when the exchange's last message is a question and no `questions.md` waits, add an answer `exchange.WITHDRAWN` = "(no reply: questions.md was removed without an answer)" before the prompt is built (the prompt treats it as `NO_REPLY`: the question stands); after a step, a waiting `questions.md` is then always copied, with no "copied already" test. Spec cases (retry.spec, promoted): R2's sequence expects `001-question, 002-answer (withdrawn), 003-question = Q2`, then `--answer` is stored as `004-answer` and the re-run is told its latest question is answered; the chain variant (`dispatch c0010` after deleting the file) the same. Rows: "a step never starts on an open question" (mutant: the marker not written) and "a question after a step is always copied" (mutant: today's copied-already rule).
Lesson: zz-arch/record-crash-states-when-entered

### F4 [medium] After an `UNKNOWN_REPLY` the step is told to "treat what you find as their answer", though the question file may hold only its own question
Where: `dispatch.prompt`, the `exchangeUnknownReply` form; Design, The dispatcher, 4 and 5 ("the step is told to read the answer in the question"); AC2.
Evidence: probe R4 (r3.spec). `dispatch c0020` stops with "Which scope?"; the user, without editing anything, runs `retry c0020 --forget-exchange` (the way on that every refusal of a damaged exchange names). The retry copies the question itself and records `002-answer.md` = "(the question was copied when the user retried, so any answer they wrote is inside it)", and the step's prompt reads: "The last file says your question was copied when the user retried, so any answer they wrote is inside the question file: read it there, and treat what you find as their answer." The question file holds only the step's question. The same text follows every c0117-era waiting question and every question whose dispatcher died before the copy, whether the user wrote anything or not.
Critique: the steps that ask are the ones that propose something and wait for approval (c0247's restatement, c0260's z-design confirmation, a review's final round). "Treat what you find as their answer" invites the step to read its own proposal as approved, which is the failure those issues exist to prevent; the no-reply form ("your question stands unanswered") exists for this reason.
Consequences: none beyond the sentence and its case.
Recommendation: say both cases: "read the question file: text the user added to your question is their answer; if it holds only your question, the user gave no reply and your question stands, so decide whether you can go on without it, and if not write questions.md again and stop." Pin it in exchange.spec (the `UNKNOWN_REPLY` form contains "if it holds only your question" and not "treat what you find as their answer") with a mutant that drops the clause.
