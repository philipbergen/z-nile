# Answers to design review 012 (round 5 of the split re-prep): c0263

Two highs, three mediums, three lows. The user decided on 2026-11-09 ("Round 6 with the fixes") that all eight are fixed as the reviewer specified and one more fresh review follows (design-review-013). Every finding is fixed, with the prototype (`proto-c0263-raft`, pushed to origin), the specs and the document changed together; consequences are named.

- F1: fixed. A merge in progress is finished when `MERGE_HEAD` is an ancestor of `ref` (a hand merge of `origin/main` or of an older commit of it), settled against `MERGE_HEAD` as before and never aborted by us; `ref` is then merged on top by the ordinary path. When that second merge stops, only it is aborted and the message says the hand merge was committed. `mergeRef` now returns whether it aborted: `mergeOrigin`, `raftingStart` and `land` print "merge aborted" only then, a refusal says nothing was aborted, the hand-merge trailer is printed only for a conflict in another file, and a refusal never advises `git merge --continue` while paths are unmerged. Case (ix) is the reviewer's P1 (main moves on while the user resolves by hand: the sync finishes the merge, the record reads Base, Main, Ours, the file published last is in the tree); (vii) stays a refusal; mutant `merge: resumed only when MERGE_HEAD equals ref`. Behaviour 5, AC6, zz-rules and the lesson note (zz-arch/guard-no-is-explicit) say "a merge of origin/main, or of an older commit of it". Consequence: a hand merge of a branch main already contains is finished too (harmless: its commits are in origin/main).
- F2: fixed. A record is written only when the settled text differs from the merged index's entry at the path, and through the index (`hash-object -w`, `update-index --cacheinfo`, `checkout-index -f`: no untracked leftover for an abort to miss); a path the merge did not leave unmerged that has unstaged changes (or is untracked) and that we would have to write or remove stops the merge, naming it (commit or stash). Case (x) is P5 (an uncommitted row survives; `git status` shows the record modified; HEAD's record is the committed text), (xv) the stop (a hand merge whose records git paired wrongly meets an unstaged edit in a record we must rewrite: the sync stops, the merge stays in progress, the edit is still there); mutants `merge: writes every settled record` and `merge: writes over uncommitted changes`. The removal side's twin check is the same predicate; no fixture leaves an old record path in place with unstaged edits (git's own merge refuses first), so that row is `reasoned`.
- F3: fixed. One read-side layout (`itemPathOf`: `publish.itemPath` plus `rafts/retired/<R-id>/`) is used by the merge, remap's settling and the document search of `planRecords`; `publish.allowed` is untouched, so `./zn record` never publishes into a retired raft. Case (xi) is P2 (a raft our branch retired, a row published into the live path: the row ends in `retired/R…/provenance.md`, no live folder); mutant `merge: ignores retired records`. Issues in `retired/` stay an audit error.
- F4: fixed. `provenance.compactionProblem(baseMap, oursMap, theirsMap, oursChanged, theirsChanged)` stops when one side's map differs from the base's and the other side changed a record, and when both differ from the base's and any record changed; provenance.spec's old assertion that pinned the hole is replaced by both directions; record.spec (xii) is P3 (a stale branch's first record meets main's compaction map) and (xiii) P4 (the compaction's own branch meets a row main published), each stopping with `./zn remap` named; (vi) still merges (our side neither compacted nor changed a record). Mutants `guard ignores a one-sided change`, `guard ignores a compaction on both sides`, `merge: settles across a compaction`. The alternative (enforcing `refuseStale` in `mergeRef`) was not taken: coarser, it would cover every file, and it may override c0081 specs. Lesson note zz-rules/item-history-spans-moves-and-compaction amended. Consequence: any worktree older than a compaction that changes a record stops at its next sync until it runs `./zn remap`, which is the rule `refuseStale` already states for the commands that publish.
- F5: fixed. (xiv): a rebase stopped at `edit` (`-c sequence.editor=… rebase -i`): the sync refuses, says nothing was aborted, HEAD is unmoved and `rebase-merge` is still there; mutant `merge: ignores a rebase in progress`. A cherry-pick or a revert: git refuses a merge itself (run by the reviewer); the checks stay as the engine's own message.
- F6: fixed. The three texts say "when both sides changed the record" (AC6, zz-rules, the Limit); AC7 and Behaviour 7 say the README names `provenance.md` and `./zn record` and points to zz-rules, Provenance, for the rest, and the README line says so; zz-rules says that after a `remap` stop the merge is by hand (its base predates the compaction, so `./zn sync` would stop on the compaction, and `remap` refuses a second run).
- F7: fixed. (vi) gives the renumbered item a row of its own and expects it at the new id; the two vacuous expects are gone (`guarded` lost its id parameter, the audit line of remap-shapes is a plain `trOk`); a comment says the compaction map left on main by (v) and (vi) is the reason cases that change a record are placed before them.
- F8: refuted (with a consequence kept): a temporary `GIT_INDEX_FILE` is the variable the repository's guards refuse (`tooling/repo-fence.spec` lists it among the names no workspace code may use; R0210), so using it in the engine would trip them. The window is real but narrow (a kill between `read-tree` and `reset HEAD` leaves a staged state), and `git reset` clears it; Behaviour 5 states it. The worktree is never touched.
