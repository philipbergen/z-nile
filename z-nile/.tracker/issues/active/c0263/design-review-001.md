### F1 [high] stamps.spec (AC3) cannot pass for any implementation of this Design: its fixture has no origin, and `status`, `unfold`, `fold` and `recombine` refuse without one
Where: acceptance/stamps.spec.luau:70 (`git remote remove origin`), :101, :103, :105, :125, :168-175; main.luau:1604 (`cmd.status`), 1648-1662 (`raftingStart`), 286-289 (`publishing`)

The no-origin fixture also takes the wrong branch of the commands it does run. `new raft` without an origin takes the offline path (main.luau:1334-1384, `store.setFront(m.doc, "raft", id)` at 1369), not the published path z-raft uses (1188-1332, setFront at 1319). `status <id> new` with its new `unblocked_by` line is only real inside `publish.commit`, where the validator at publish.luau:464 must accept the second line. `fold`, `recombine` and the emergent `new issue --raft` don't run at all. So no AC exercises any of the published stamps the Design adds, or the validator change they need.
Critique: the only Checked criterion for four of the five captured outcomes (approved, unblocked, rafted, delivered, all live) is a spec that can't go green. The author will be tempted to give the clone a bare origin and keep everything else. But with an origin, `new`, `status` and every rafting command refuse in the main clone (`refuseInMainCheckout`, main.luau:195), `new raft` over a prepared issue wants it prepared *on origin* (1256-1264), and the carried `status <R> prepared` wants a Theme, an Order and a grouped record (1539-1561).
Consequences: the fixture needs worktrees and a landing step (push the prep to the bare origin's main) between `status prepared` and `new raft`, the way c0116/claims.spec.luau does (`trackerfix.new`, `land(wt)`). `done` still needs the no-origin path, or `start` pushes and opens a PR.
Recommendation: rewrite stamps.spec in two parts. (a) A `trackerfix` fixture (bare origin, `git worktree add` worktrees, `land()`) that drives the published paths. (b) A `clone.isolated` no-origin part for the offline `new raft`, `start` and `done`. Run the whole spec on a scratch prototype before round 2, and record the run in Unknowns & experiments.

### F2 [high] backfill.spec (AC10) contradicts the Design twice: it has no `origin/main`, and its second run is on a dirty tree
Where: Design §6 ("run in a worktree on a clean tree", "`git log origin/main --reverse …`"); acceptance/backfill.spec.luau:55 (`git init`, no remote), :91-108
Evidence: in a scratch repository with no remote, `git log origin/main --oneline` prints `fatal: ambiguous argument 'origin/main': unknown revision or path not in the working tree.` The fixture has no remote, so the Design's log pass fails and `backfill` exits non-zero at :91. After the first run, :103 stages the changes and :105 runs `backfill` again, with the tree dirty (staged changes count in `git status --porcelain`) and `again.ok` expected true. A command that refuses a dirty tree, as the Design says it does, fails :106. The idempotency check also compares `git diff --cached --stat` (:104, :108), which counts lines per file: a second run that rewrites a back-filled value to another value of the same shape passes it.
Critique: a correct implementation fails AC10, and a wrong one (one that overwrites on a rerun) passes the "changes nothing" clause. The tempting fix is "fall back to HEAD when there is no origin". That gives the real tree two log sources and puts an untested branch in the command.
Consequences: whichever source the Design picks, the spec must run that source: an origin in the fixture, or a stated rule ("the log of `origin/main` when it exists, else `HEAD`") with a case on each side. The clean-tree rule has to either hold in the spec (commit between runs) or be dropped from the Design on purpose.
Recommendation: give the fixture a bare origin (push `main` after building the history) and run the command in a worktree, matching the Design. Commit the first run's result before the second run. Compare the full text of every document (or `git diff HEAD` being empty) after the second run, not `--stat`. Add a case where `backfill` refuses a dirty tree. If the Design keeps a HEAD fallback, add a no-origin case too.

### F3 [high] An interactive agent's stamps say `human:<git name>`: the fallback records the user for work an agent did, against the decided "agent:<model id> … effort"
Where: Solution, Actor grammar ("else `human:<name of git var GIT_AUTHOR_IDENT>`"); Usability ("`--actor` or `ZN_ACTOR` is the only thing an interactive agent must remember"); Problem, second "Decided with the user" line ("from the dispatcher's `.models.toml` spec or the session's trailer")
Evidence: this review runs in an interactive Claude Code session. Its environment has `CLAUDECODE=1`, `CLAUDE_EFFORT=high`, `AI_AGENT=claude-code_2-1-319_agent` and `CLAUDE_CODE_ENTRYPOINT=cli`, and no `ZN_ACTOR`. `provenance.resolve(nil, nil, "Philip Bergen")` gives `human:Philip Bergen` (provenance.spec:52). So every `./zn done`, `new raft`, `fold` or `status <id> new` an interactive session runs without remembering the flag stamps the user. The history shows how much work that is: 1,665 of origin/main's commits are authored `Philip Bergen` and nearly all of them were made in agent sessions. Nothing reads "the session's trailer" the Problem names.
Critique: this is a wrong value in the common case, written as a recorded (not `(from git)`) fact. The Non-goals say "never a plausible name". The tempting fix is to refuse a stamping command in an agent session that has no actor. But the specs inherit the session's environment (`fixture.exec` passes `env` on top of the parent's), so every promoted spec that runs `done`, `new raft` or `fold` (c0001 lifecycle, c0116 claims and recombine, c0008, c0038, c0084, …) would go red whenever the gate runs inside Claude Code.
Consequences: the engine can tell that an agent session is running and what its effort is, but not its model id. So the value needs a form for "an agent, model not known": `agent:unknown effort <CLAUDE_EFFORT>` fits the grammar. The skills must still tell sessions to set `ZN_ACTOR` with the model (z-design, zz-execute, zz-rules), or a SessionStart hook could export it. And `git var GIT_AUTHOR_IDENT` fails outright with no identity configured (`fatal: empty ident name (for <>) not allowed`), a failure path the Design doesn't name.
Recommendation: give `resolve` a fourth, pure input, the session hint `{ agent: boolean, effort: string? }`, read at the edge from `CLAUDECODE`/`AI_AGENT` and `CLAUDE_EFFORT` (or the equivalents of the other CLIs the dispatcher runs). Order: flag, env, then `agent:unknown effort <effort|unknown>` in an agent session, else the git human. A failing `git var` gives `unknown`, never a refusal. Add pure cases for each branch of that order. Name the session variables in the Design and in zz-rules. Have the specs that assert the human fallback clear the hint, so a run inside Claude Code doesn't turn them red. If the user wants the model id itself recorded interactively, escalate to the user: the options are a SessionStart hook that exports `ZN_ACTOR`, a skill rule plus `agent:unknown`, or reading the trailer of the session's newest commit on the branch.

### F9 [medium] Every key is appended right after `status:`, so the back-fill and the stamps conflict with in-flight branches that edit the status line
Where: Behaviour 6 and Implementation step 8; store.luau:183-197 (`withFront` appends a missing key as the last line, and `status:` is the last key of every stub, main.luau:1125)
Evidence: `store.withFront` adds a missing key after the last frontmatter line, which is `status:` in every document `new` writes. The back-fill adds up to five lines right after `status:` in nearly every issue document. A prep worktree in flight changes that `status:` line with its carried `status prepared` (main.luau:1575). When it next merges origin/main, the two changes touch adjacent lines and git reports a conflict. The same happens at c0263's own final merge if any published move lands between step 8 and the merge. zz-rules Merging step 4 turns such a conflict into `BLOCKED:`.
Critique: the Design treats the back-fill as a local edit, but it writes files main writes during the raft.

Recommendation: write every provenance key at a fixed slot, directly after `type:` (between `type:` and `title:`; `id` and `type` never change). Do it in `provenance.set`/`fill`, for the stamps and the back-fill alike, so no insert touches `status:`, `raft:` or `design:`. Pin the slot as a rule in provenance.spec, and say in the Design what an in-flight prep does if it conflicts anyway.
