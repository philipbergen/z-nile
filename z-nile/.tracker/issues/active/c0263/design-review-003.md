### F1 [high] `provenance.md` has two write channels, and their appends conflict: a correct implementation cannot pass record.spec's give-back case, and real tickets will conflict and collide on row numbers
Where: Solution (prep detail, "A command that happens in a PR (approve, rafting, done) appends its row in the PR; one that is published (`status <id> new`) appends it in the same published commit"), Behaviour 3, 4, 6, 10; `acceptance/record.spec.luau` "a raft's give-back records its issues and never the raft"
Evidence:
- `new raft` (published path) writes the members' `raft:` lines and commits them in the worktree (`main.luau:1316-1333`, `tracker: <R> members`); under the Design that commit also holds each member's new `provenance.md` with row 1 `rafted`. `status <R> new` then publishes from origin's tree, where the file does not exist, so it creates it with row 1 `unblocked`, and `mergeOrigin()` (`main.luau:332-340`) runs `git merge origin/main`, which aborts on conflict and fails the command.
- Probe (`./zn run --time 30`, scratch repo): a branch adds `p.md` = header + `| 1 | t | rafted | …`, main adds `p.md` = header + `| 1 | t | unblocked | …`; `git merge main` prints `CONFLICT (add/add): Merge conflict in p.md`. Second probe: main's file is the branch's plus one row (the "build from the worktree's file" variant) is still `CONFLICT` (add/add), and two branches that each append one row to a common file conflict too (`CONFLICT-append`).
- So record.spec's `trOk(W2, { "status", rid, "new" }, …)` fails for every implementation the Design describes, and so does promoted `c0053/commands-prep` (F2). In production the same happens whenever a ticket gets a published row while a branch holds an unmerged one: `./zn record <id> ranked`/`confirmed` (published) on an issue whose prep PR carries its `approved` row, c0250's resolve while a raft PR carries rows, a designer's give-back after `approve`. Even a hand-resolved conflict leaves two `| 1 |` rows, which `provenance.parse` refuses by design ("the parser refuses a repeat"), so audit (and `done`'s gate, `compact`) then fail.
- E7's lenient runs could not see this: the appends do not exist yet, so the conflicting files were never written.
- spend.md, the model the Design cites, avoids this by having one channel per state ("an active item's spend.md is recorded on its raft branch", `publish.luau:447-451`; a backlog item's is published), and `ledger.parse` ignores row numbers.
Critique: the record's merge behaviour is the core of "ONE append-only record per ticket", and the Design never says what happens when two writers append. The tempting fix (build the published append from the worktree's file) still conflicts (second probe) and leaks branch-only rows (`approved`, `rafted`) to main before their PR lands. Also unspecified: which file a published append is built from, and how `./zn record` decides that an issue is "not in a worktree's PR" (no command can know that).
Consequences: any fix changes the parse rules (numbering), the append-only rule shared by publish, the rafting gate and land, and audit; a merge driver is configuration (`.gitattributes` is never tracker state, `trackerstate.luau` header), so it rides this PR and needs a human merge; GitHub's own PR merge may not run git's merge drivers, which decides whether a driver is enough.
Recommendation: make the record merge-safe by construction and prove it on a prototype: (a) drop row numbers (rows ordered by `when`, then file order; `appendOnly` = the old rows are a prefix-preserving subsequence of the new, judged against the merge base, never "same rows plus more at the end"), plus a union merge for `provenance.md` (`.gitattributes`), with an experiment E8 that answers "does a GitHub squash merge of a PR with a branch row and a main row produce both rows?" and a fallback (the engine resolves a `provenance.md`-only conflict itself in `mergeOrigin`, `sync` and before the PR, by taking the union); or (b) escalate to the user: one file per event (`provenance/<when>-<event>-<n>.md`, which never conflicts) instead of the decided "ONE record". Either way, state which tree a published append is built from (origin's) and replace "not in a worktree's PR" with a rule a command can evaluate. Spec cases: record.spec's existing give-back case passing; a prep worktree with a committed `approved` row while `./zn record <id> ranked` publishes, then a merge both ways (worktree merges origin; the PR merged into main) keeps both rows and audits clean.

### F3 [high] `--said` lets any agent session approve its own design: the decided "refused until a human has run `./zn approve`" becomes a speed bump
Where: Behaviour 2 (agent session with `--said`), Usability ("approval always names the human")
Evidence: Q2 (2026-11-08): "`./zn status <id> prepared` refuses until a human has run `./zn approve <id>`". The Design lets the command run in an agent session (`CLAUDECODE`/`AI_AGENT` set) whenever `--said` is non-empty; the row then reads `human:<git name>`, because an agent's commits carry the user's git identity. Nothing ties the words to the user: an agent that types `--said "approved"` produces a row indistinguishable from a real approval except for `via=`. This repository's agents are told to keep going unattended ("Continue and parallelize", "Unattended: branch on a guess"), and z-design step 6 lets an interactive lead merge a prep PR the user requested. Only `ZN_DISPATCH=1` refuses; a headless `claude -p` outside the dispatcher has `CLAUDECODE` and passes with any words.
Critique: this is an authority hole in the one human step the issue adds, and the `--said` path is prep's invention, not a decided line. The tempting fix (require `--said` to quote the session's last user message) cannot be checked by the engine.
Consequences: every option changes the interactive z-design flow the skills describe and how the user approves in a Claude Code session (a `!` command runs in the session's shell and, per E5's variables, may carry `CLAUDECODE`).
Recommendation: escalate to the user: options (a) `approve` refuses whenever `CLAUDECODE`, `AI_AGENT` or `ZN_DISPATCH` is set, so the user runs it in their own terminal (cost: a terminal switch per prep; z-design stops at `design: ready` and asks); (b) keep `--said` as the Design has it, recorded as an accepted risk the user decides (an agent can self-approve; `via=` shows it); (c) a confirmation an agent's tool shell cannot give (read from `/dev/tty`; needs an experiment for Claude Code's `!` and Bash tool). Whatever the user picks: a spec case for the refusal in each environment, and z-design's step 5 says the lead stops and asks before `approve` in every interactive session.

### F4 [high] who.spec's "oldest first" assertion depends on the wall clock, so a correct implementation fails it
Where: `acceptance/who.spec.luau` "who prints the derived entries and the record, oldest first, …" (`t.expect(order[1]).toBe("idea")`); Behaviour 7
Evidence: the fixture's commits set names and emails but no dates (`env()` in who.spec), so every derived entry is dated at run time. The stored rows are fixed at `2026-11-08 09:00` (approved) and `09:30` (rafted). The fixture the author left (`.cache/c0263-who/main`, `git log --date=format:'%Y-%m-%d %H:%M'`) shows every commit at `2026-11-08 10:45`. Oldest first therefore puts `approved` (09:00) before `idea` (10:45) on any run after 09:00 today and on every later day; `order[1]` is `approved`. Also every derived entry falls in the same minute (`when` has minute resolution), so their order is a tie the Design never breaks.
Critique: the assertion can be passed only by an implementation that does not sort by time (for example derived first, then stored), the opposite of the Design. `provenance.spec`'s pure case uses fixed dates and is fine.
Consequences: a tie-break rule is needed anyway: real engine publishes (claim, status, spend) land within the same minute.
Recommendation: set `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` per commit in who.spec (dates before and after the stored rows, so the stored rows interleave), and state the tie-break in Behaviour 7 (equal `when`: git log order, then file order; a stored row after a derived entry of the same minute). Add a pure case in provenance.spec with two entries in one minute.
