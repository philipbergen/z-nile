### F5 [high] The union puts the worktree's rows before main's, so after a `./zn sync` main's record is no longer a prefix, and the rafting gate's append-only rule refuses the PR; provenance.spec pins that order
Where: Behaviour 11 (`git merge-file --union` of stages 1/2/3), Behaviour 10 (the rafting gate: "old rows are unchanged"), Interfaces (`appendOnly`: "the publish and gate rule"; `union`), `acceptance/provenance.spec.luau:151-158` (`urows[2]` = ours' `rafted`, `urows[3]` = theirs' `unblocked`)
Evidence: probe against the prototype. Take a base with an `approved` row. The rafting worktree appends `rafted` (ours), and main gets `ranked` from `./zn record` (theirs). `union(base, ours, theirs)` gives approved, rafted, ranked. `appendOnly(theirs, united, "c0010")` gives `row 2 differs from origin/main: rows are only appended`. `git merge-file -p --union ours base theirs` on a real add/append conflict gives the same order (`| rafted |` then `| ranked |`). The dispatcher already refuses a rafting PR whose items main changed since the PR was cut ("rebase first", zz-rules Dispatch). So such a PR is refused before the sync for being stale, and after the sync by the gate's prefix rule: the dispatcher can never pass it. This happens whenever a published row (rank, c0260's confirmation, c0250's unblock) lands on a ticket while its rafting PR is open. dispatch.spec's gate cases never union, so nothing catches it.
Critique: two rules of the Design contradict each other on the dispatcher's main path, and the sequestered pure case pins the half that breaks it. The tempting fix (the gate accepts any subsequence) also changes the publish validator's shared rule, and an edited row could then hide among reordered ones.
Consequences: every engine merge has `origin/main` as theirs. If the union keeps main's rows first, then main's file is a prefix of every merged branch. This also holds when two branches each unioned: after A lands, B's next sync gives base, M, A, B. The record's file order then no longer means "time" (`who` sorts by `when` anyway), and "the newest approval" must be the last `approved` row in file order, which approvals keep, since only PRs write them.
Recommendation: specify the union as base rows, then theirs' (origin/main's) new rows, then ours' new rows, implemented in `provenance.union` (not `git merge-file --union`, whose order is ours-first). Change provenance.spec's union case to expect approved, unblocked, rafted. Add a dispatch.spec case: main gains a `ranked` row on c0096 after the PR is cut, the PR's record is main's plus `rafted` (what the union yields), and the gate merges it. Add a row to Rules and mutants ("union puts ours first": killed).
Lesson: z-design/exact-checks-compare-against-the-merge-base
