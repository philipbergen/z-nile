## Behaviour 2 (approve) and 9 (the dispatcher prep gate) and 12 (frozen list)

2. **Design approved by (AC4, AC5).**
   - `./zn approve <id>`, in a prep worktree, for an issue that is `preparing` on `origin/main` with `design: ready` here. It computes the design hash (`raftplan.recordHash` over the issue's folder in this worktree: the document without `status:`/`raft:`, `check.sh`, `acceptance/`, the design reviews, refutes and `harvest.md`, the same hash z-raft's `grouped:` record uses; `provenance.md` is not among those files), appends `approved | human:<git name> | design=<hash>` and commits the issue's folder as `tracker: approve <id>`, so the human is the git author of that commit.
   - **It is refused in any agent session.** An agent session is one where `CLAUDECODE` or `AI_AGENT` is set and non-empty, or `ZN_DISPATCH` is set (a dispatched step). The refusal, first of all, says: `approve is refused in an agent session or a dispatched step: run ./zn approve <id> yourself, in your own terminal, in this worktree (<path>)`. There is no `--said`, no flag, no variable and no configuration that lets an agent through, and the engine reads no "allow" input. How an interactive prep is approved: the agent finishes the design and the reviews, commits, and tells the user to run `./zn approve <id>` in a terminal of their own in the prep worktree (a `!`-prefixed command typed in the agent's session inherits the session's variables and is refused too: open point 1); the user then says so, and the agent runs `./zn status <id> prepared`. **The argument that the human really ran it.** The guard detects an agent session by what a session carries, as every guard in zz-rules does ("Keep same user, accept detection"): it catches the honest mistake and the casual workaround, and it is not a security boundary against an agent that deliberately starts a process without those variables (`env -u`) or edits files by hand. What the design adds so that "a human ran it" is true in the engine's terms: (a) the only way to the row through `./zn` is a process with no agent marker; (b) no code path sets, clears or ignores the markers (the fixtures' `trackerfix.approve` helper clears them only in a test process it starts, and no engine command reads it); (c) `status prepared` re-derives the approval from the committed row and the design hash, so a hand-written row for a design that nobody approved fails only if the hash differs, and the row's `tracker: approve` commit is there for the user to see in `./zn who` (the approving human and the time); (d) the dispatcher's prep gate never merges, so a human reads the PR before it lands.
   - The other refusals, in this order after the agent-session one: the main checkout (`approve runs in a worktree`); no git identity; an issue not `preparing` on origin; a design not `ready` here; a tree with changes outside the issue's folder (`outside`: approve commits the issue's folder, its design files and the record, and nothing else).
   - `./zn status <id> prepared` (the carried move) refuses, after every refusal it already has (the existing checks, `design: ready` among them, come first, so `c0053/commands-claim:107`'s `design: ready` answer is unchanged), each issue it moves until the newest `approved` row of that issue's `provenance.md` has `design=` equal to the hash of the folder now: `<id> has no current approval: ./zn approve <id>` or `<id> was redesigned since its approval (<old> -> <new>): ./zn approve <id> again`. This covers an issue named alone and a member a raft's move changes (a member already prepared on `origin/main` is taken as it is). A redesign after a stop (`prepared -> preparing`, edits, `prepared`) changes the hash, so it needs a fresh approval; a stop with no edit keeps the hash and the old approval. No flag skips the refusal, and the move refuses under `ZN_DISPATCH`.
   - **The frozen list (Behaviour 12) and the doors.** `fold`, `new raft` and `ready` (the three ways a prepared issue enters a raft), `./zn raft-plan` and `audit` hold every prepared backlog issue to the same rule: it needs a current approval, or the frozen list must cover its design. They refuse before they publish anything (a refused `fold` leaves `origin/main` and the raft's status as they were); `raft-plan` skips it (`skip <id>: <reason>`, never a command), so `raft-plan --apply` is never left half applied; `audit` reports an error `unapproved-prepared`. The rule is in force once the base has the frozen list: a tree whose base has none enforces nothing at the doors (the carried move still needs an approval). z-design's offline instruction (`PICKMAN_PUBLISH=0`: edit the status line by hand) says to run `./zn approve <id>` first, in the user's terminal.
   - The design reviewer's `Verdict: approve` is no longer the approver; z-design's rounds are unchanged.

## Behaviour 9

9. **The dispatcher (AC7).** The `prep` gate never merges: `dispatch.luau`'s merge branch is for `raft` only. Every prep stop is exit 4 with the existing reason of its turn (not in `auto_merge`, draft, red, unmergeable, carries code) followed by `; approve the design with ./zn approve <id>, then merge it yourself and run ./zn dispatch <id> again`; the gate checks stay in the order they are in, so each existing assertion on a reason stays true; when no condition fails (a green, mergeable, clean PR that the gate would once have merged) the reason is `the prep PR #n waits for the user's approval and merge`, never the old fallthrough "its head commit is unknown"; the suffix follows that reason too. `auto_merge` keeps accepting `prep` as a name (no config breaks) but it has no effect; `.models.toml` drops it. A dispatched z-design step ends at an open PR with `design: ready` and status `preparing`; it never runs `approve` or `status prepared`: the carried `status <id> prepared` refuses an issue under `ZN_DISPATCH` (after every other refusal) as `approve` does, so a dispatched step cannot hand-write an `approved` row and pass the move. The user runs `./zn approve <id>` and `./zn status <id> prepared` in the prep worktree, commits, pushes and merges. The in-session path (an interactive z-design) does the same with `--said`.

## Behaviour 12

12. **The frozen list (AC13).** `z-nile/provenance-exempt.txt`, one line per issue, `<id> <design hash>`, `#` comment lines allowed, is written once by `./zn provenance freeze` (a worktree command, refused in the main checkout and once the file exists on `origin/main`): it lists every backlog issue that is `prepared` in the tree it runs in, with `raftplan.recordHash` of its folder. The executor runs it as the last step of c0263's raft, after merging `origin/main`, and commits the file; it is then frozen: the doors and `audit` read it from the base (`origin/main`), never from the working tree, so no PR can add its own exemption. An id on the list passes without an `approved` row only while its design hash is the listed one; a redesign (any change to the document, `check.sh`, `acceptance/`, reviews, refutes or `harvest.md`) needs a fresh approval like any other issue, which then governs (the listed hash no longer matters once a current `approved` row exists). A prepared issue that landed after the freeze, or one merged by a PR cut before it, has no listing and needs `./zn approve` (a migration note in the skills). Active and done issues are not checked.

## Edge cases

- Two approvals: the newest decides; an approval whose hash matches an older design is stale, never valid. `approve` twice on one design: a second row, still current.
- `status prepared` for a raft: each moved issue needs its own current approval; the raft's own document needs none.
- An unfolded item: its `rafted` rows stay as history; the current raft's row is the newest whose `raft=` matches.
- `git var GIT_AUTHOR_IDENT` fails (no identity): the human is `unknown`; `approve` refuses on it.
- A person's trailer (an email that is a commit author's elsewhere) beside an agent's: the agent. Two agent trailers: the last.

## Acceptance AC4, AC5, AC7, AC13

- AC4: `./zn approve <id>` records an `approved` row with the human and the design hash, as a `tracker: approve` commit authored by the human's git identity, in a plain terminal session; it is refused in every agent session (`CLAUDECODE`, `AI_AGENT`, `ZN_DISPATCH`, whatever else is passed) with a message naming the user's own terminal, and otherwise refuses the main checkout, no git identity, an issue not preparing, a design not ready and changes outside the issue's folder, each for its own reason.
- AC5: `./zn status <id> prepared` refuses an issue until its newest `approved` row matches the design hash now (also after a stop and a redesign, and under `ZN_DISPATCH`), takes a current one, a raft's carried move refuses each issue it moves that has no current approval, and `fold`, `new raft`, `ready` and `raft-plan` refuse or skip, and `audit` reports as an error, a prepared issue that has no current approval unless the frozen list covers its design, before publishing anything.

## AC7, AC13
