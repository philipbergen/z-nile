**The lease and ownership.** The branch name carries the claim stamp, and a takeover has a new stamp, so ownership is the pair (stamp on `main`, branch `hb/<stamp>`). **One rule for the lease** (in `heartbeat.plan`, argument `remembered`): the sha this checkout last wrote for that stamp (its throttle entry `<stamp> <epoch> <sha>`), else the sha it just read, else empty (create only if absent); a beat is `git push --force-with-lease=<branch>:<lease> origin <commit>:<branch>`. **A beat is bound to the stamp its holder owns**, never to whatever `main` says now: "my stamp" is the claim memory `.cache/tracker-stamp-<id>` (written by every claim publish and by an adoption). `beat <id>` (explicit, `--watch` and the autobeat alike) beats only that stamp; when `main` shows another stamp or none it refuses with `<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`, exits 1 (the autobeat says it once and carries on), drops the entry and never rewrites the memory. A checkout with no memory (a fresh clone, a raft worktree made after `ready`) refuses a bare `beat <id>` (`beat: <id>'s claim is not held by this checkout (use --adopt to take it on)`). **`--adopt` is the stated adoption** and the way a checkout comes to own a claim it did not publish (z-run in the raft worktree after `ready`, a human in the main checkout): it beats origin's stamp and **writes the memory in the adopting **worktree** (a main-checkout `--adopt`, and the dispatcher's `--adopt --stamp`, write none: the main checkout holds no work and beats once per command). **Adoption never overrides a remembered different stamp**: where the memory differs from `main`'s stamp, `--adopt` refuses with the takeover text like any other beat. A takeover never reuses the old owner's worktree (it is discarded, below), so the old process finds either a refusal or its discard notice, whichever form it uses; a *different* checkout that adopts is by definition a new owner. The memory is **never dropped by the observation that triggers a refusal** (dropping it would let the old owner's `--adopt` or carried move through); it ends only with its checkout (a discarded worktree) or by a claim-ending command run in that checkout (`status <id> new`, `release`, `stop`, `done`). The dispatcher's `--adopt --stamp <S>` and an `--adopt` in the main checkout write no memory (the main checkout holds no work; a human adopting there beats once per command). `--adopt --stamp <S>` (the dispatcher's form) refuses when `main` no longer shows `<S>`. The takeover, after publishing the new claim stamp on `main`, runs **one atomic push**: delete `hb/<old>` with a lease on the sha it read, create `hb/<new>` create-only. So the old owner's next beat finds its branch gone and its lease rejected (it cannot recreate it); it re-reads and learns the loss as above. **A create-only write** (the branch absent when read, which is also what a beat in a checkout without a remembered sha sees after a takeover) can race a takeover in the window between the beat's main read and its branch read: so after any create-only write the beat re-reads `main`, and when the stamp changed it deletes what it created (lease on its own sha) and reports the loss. Telling a lease rejection from another failure needs no classification: any failed write is followed by a re-read and `heartbeat.rejected` (retry on the sha there, create, or lost), and a second failure is a failed tick. What is **said** (`beat: <id>: <git's message>` on stderr): a failure whose git message does not contain `(stale info)`, the text git itself prints for a lease rejection (E10) and which a same-claim co-beater causes harmlessly, so those retry silently; a retry that fails too is always said. Pruning deletes are separate best-effort pushes (a vanished target never fails the beat). If the rejection came from a co-beater of the same claim (same stamp, another sha) the beat retries once on what is there. An old owner that comes back by a command that does not beat (a plain `status`) learns the same thing from its entry's stamp check.

Every checkout reads into its own shared `refs/zn/hb-seen/*` (a ref-lock contention between two concurrent commands counts as unreadable, retried once as `publish` retries, and fails safe: unknown is never lost). **When the branch is deleted** (the user: "when the heartbeat drops or task completes"): by the command that ends the claim, best effort with a lease on the sha seen and said on failure like a first beat: `status <id> new` (give-back), `stop`, `done` (it drops the branch, the entry and the memory of the worktree: the claim is finished there, so no autobeat recreates the branch while the PR waits for its merge; the open PR parks the claim), and the takeover (the old owner's branch). `ready` cannot know the rafting claim's branch (the carried `prepared` replaced its stamp), so the rafting branch and a merged raft's branch are left to the pruner. A merge happens on GitHub where no `./zn` runs, so pruning (a branch of an unclaimed stamp older than the limit, by the next beat of anyone) stays as the backstop. A lost claim's branch is kept until its takeover (it is the evidence the claim went quiet). **Taking over a lost `active` claim** (a readied raft), in this order: `./zn worktree R0010 --takeover` (discard and recover, below; it needs the lost verdict, so it comes first), `./zn stop R0010` (records the lost stamp in its subject, `tracker: stop R0010 (claim <stamp>)`, drops the old branch), `./zn ready R0010` (a fresh `active-` stamp and its first beat), then `/z-run`, whose loop starts in the fresh worktree with a plain `./zn beat R0010 --adopt` (no memory there). A parked raft is left alone.

heartbeat.plan(stamp, epoch, beats, claimed, now, remembered?): Push    -- replace the claim's branch (lease: the sha seen, "" to create); never backwards; delete long-unclaimed branches with their leases
heartbeat.takeoverPlan(oldStamp, newStamp, epoch, beats): Push          -- create the taker's branch, delete the old owner's with a lease: one atomic push
heartbeat.rejected(stamp, originStamp, beats): { action, lease?, why? } -- after a rejected beat: "lost" (ended / taken over), "retry" on the sha there, or "create"

- **`./zn beat <id> [--watch]`**: fetches `origin main` first (so claims and the claimed set are current), refuses (exit 1, naming the item and the rule) an item that is not a claim (checked first), then one that this checkout does not hold or that was taken over (above): `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`, `beat: c0060 is done: no claim to beat`. Before writing it reads the beats (one fetch, above), builds the beat commit (`git commit-tree <origin/main tree> -p <origin/main tip> -m "hb <stamp> <epoch>"`) and pushes `plan`'s write with its lease and its deletions; on a rejection it calls `heartbeat.rejected`. It pushes only branches (and, from a worktree, writes its ignored throttle entry `<stamp> <epoch> <sha>`); it changes no tracked file, index, HEAD, branch or config of the checkout, so it runs in the main checkout and in any worktree and publishes nothing to `main`. `--watch` repeats it every `INTERVAL` seconds (fetching each tick) and **refuses unless `ZN_BOUNDED_DEADLINE` is set to a number**, i.e. it runs under `./zn run` (`beat --watch must run as ./zn run --time 3600 -- ./zn beat <id> --watch`); each tick asks `heartbeat.watch`, and it exits 0 with a message on `stop-restamped` (claim ended or taken over) or `stop-bound` (the next tick would pass the bound); a failed tick relays git's stderr (`beat: <id>: <git's message>`) and the loop retries at the next tick; `stop-restamped` prints the autobeat's text (`<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`).

- **Takeover**: `status <id> preparing` (or `<R-id>`) on a `preparing` claim keeps its refusal text (`<id> is preparing on origin/main: cannot move to preparing`, c0053's) with `; claim alive: last heartbeat <n>m ago, limit <m>m` for a live claim, `; claim parked (an open pull request names it)` or `; claim parked (a dispatcher waits on questions.md)` for a parked one, `; no heartbeat verdict: <reason>` when anything was unreadable or malformed (naming the ref and `git push origin :<ref>`, or git's message). Only an explicit lost verdict allows it, and the verdict travels into `setStatus`'s `publish.commit` callback, which calls `heartbeat.canTakeOver(kind, judgedStamp, originStamp)` with the stamp origin holds *at that moment* (a claim restamped since the verdict is refused naming the new stamp: the push is the lock). Inside the callback the stamp-record check comes **before** the member design check (so a raft move whose member is still `design: draft` is refused as "taken over" first). It draws a stamp with `freshStamp("preparing")` (checked against `origin/main`, as `ready` does: issue claims drew with `stamp()` before, a 1.4 % chance today that two live claims share a stamp), and **in the same step deletes the old owner's branch and creates its own in one atomic push (`heartbeat.takeoverPlan`)**; if that push is rejected because the old owner beat meanwhile, it re-reads and repeats once. **The takeover is recorded** (the capture's "recorded (c0263)") in the claim commit's subject, `tracker: <id> preparing (takes over <old stamp>)`, which `git log` and any provenance reader of history see; a normal claim keeps `tracker: <id> preparing`. Every claim publish (`status <id|R-id> preparing`, the takeover included, and z-raft's `new raft`, `fold`, `unfold` and `recombine`; `setStatus` today writes the memory for issues only, so it gains the raft case) records the new stamp in `.cache/tracker-stamp-<id>` of the checkout that made it (a file of its own: `.cache/tracker-claim-<id>` keeps c0116's meaning, "this checkout owns the rafting claim", which `release` and `fold` read; a prep prototype of this rule left c0116/claims and c0053/commands-{claim,prep,start} green, 37 of 37, E8). The carried `status <id> prepared` and `./zn done` (the user's "refuse") refuse only when this checkout **remembers** a stamp and it differs from origin's (a checkout with no record passes, as today; a checkout's own re-claim updates its record, so c0053/commands-prep's flow stays green); the taker therefore claims from inside the worktree it will work in, and a rafting taker's `release` and `fold` need `--force`, as after any `status R preparing` today. The refusal reads: `<id>'s claim was taken over (now <stamp>): …`. An `active` claim is taken over as today (`./zn stop`, `/z-run`).

- **Why not `reap`, the sweeper, or `sync`**: they clean local leftovers; a beat leaves nothing local but the throttle file (ignored, under `.cache`).
