### F1 [high] A returning old owner is routed into the taker's copy without being told, by the very lookup this layer adds
Where: c0277.md Design, "The lookup is by family" (line 145), "Not changed, on purpose" (line 148), Readings 1 (line 154), U1 (line 205); prototype `cmd.worktree` (main.luau 5896: `local live = heartbeat.currentOf(...)`, then `print` with no notice)
Evidence: The Problem's first outcome is that "a process that wakes up there knows it has been discarded". The design gives it two signals: the `./zn` refusal (only reachable from inside the renamed folder) and "its paths gone". A path that is gone does not say "you were discarded", and the design's own lookup answers the obvious next step with the taker's checkout. Two concrete routes:
(1) A z-run session starts in the main checkout and `cd`s into `.worktree/R0010` (zz-rules Worktrees 3). After the rename its working directory is gone. Claude Code's Bash tool then resets the shell to the session's start directory (it prints `Shell cwd was reset to …`), which is the main checkout. The agent's skill says `cd "$(./zn worktree R0010)"`. Run in the main checkout, which carries no marker, that prints `.worktree/R0010-1` silently. The old agent now works in the taker's copy. Once the taker has claimed, the copy's memory is the taker's stamp, so c0274's backstop (memory against main) passes too. That is the Problem's opening hazard ("a returning old session could carry on in the taker's checkout and never learn it lost the claim"), and E5 doesn't test it: E5 used a plain shell, which follows the moved folder. U1 is exactly this case, it is left to Phase 1, and its fallback ("the marker is the signal and the path is the second") doesn't cover it.
(2) Line 148 says a dispatched step whose worktree is discarded loses its beats, "and the next `./zn dispatch <id>` resolves the worktree through the lookup to the taker's copy". Nothing stops that next dispatch from being the old run's own chain. `claimBeat` returns once the cwd is gone and records nothing in the run state. The discarded model, refused at every `./zn` command and told to "pick up something new", ends normally. The chain then reads origin/main, picks its next step and starts it in `worktree(ctx, …)`, which is the taker's copy. Its `--adopt --stamp` reads the taker's stamp from main, so it beats that claim as well. The c0265 hand-off had a rule for this ("it does not reuse an old worktree for a step on an item whose claim is lost"), and this design dropped it without saying so.
Critique: The rename is how the design carries out the user's words, but on its own it changes the failure mode rather than closing it: the old owner moves from the old path into the copy. The tempting fix is to make the lookup refuse to print a fresh copy. That locks out the taker too, who needs `./zn worktree <name>` after a session restart.
Consequences: Any notice the lookup prints, the taker reads as well, so its wording has to name both roles. A dispatcher that stops after a discard needs a retry rule: `./zn dispatch retry <id>` would rerun the step in the taker's copy. Retry therefore refuses while origin/main's stamp is not the one the run started with (c0274's binding). The notice has to be shown for as long as the discarded worktree exists, which ties it to the sweep (F2).
Recommendation: (a) While its family has a discarded member, a plain `./zn worktree <name>` prints on stderr a notice read from that member's marker: `<old path> was discarded <when> (<items>' claim taken over); <copy> is the taker's. If your work was in <old path>, you were discarded: clear your context and pick up something new.` Add a discard.spec assertion on the existing "a plain lookup finds the copy" case, and a Rules row whose mutant drops the notice. (b) When `claimBeat` stops for a discard or a vanished cwd, the dispatcher records it in the step's outcome and ends the chain, failing like a `lost` step. It never starts the next step. Add a proof or dispatch case: a fake CLI renames its own worktree and exits 0, and no second step starts. Retry refuses as above. (c) z-run, z-design and zz-execute Phase 0 say: if the worktree you were working in is gone, you were discarded, so do not look it up again. AC6 pins the phrase. (d) Run U1 in prep under `./zn run --time …`, either in a throwaway worktree or with one `claude -p` probe, and write its result and a fallback that covers route (1) into Unknowns.

### F2 [high] The sweep judges "unrecovered" by sha reachability, which every normal landing defeats, so discarded worktrees are effectively never removed
Where: c0277.md "The sweep" (line 146), Readings 3 (line 156), Rules row "one that holds uncommitted files or commits on no origin ref is kept" (line 250); prototype `hb.sweepDiscarded` (main.luau 5810: `rev-list --count <ref> --not --remotes=origin`); sweep.spec "once the work is recovered" (line 150)
Evidence: The renamed branch holds the old worker's pushed commits as well as its unpushed ones. (1) Rafts: `./zn finish` makes a layer one commit and force-pushes it, and `restack` rebases it. Once the taker finishes the layer it continued, the old worker's pushed WIP commits are reachable from no `refs/remotes/origin/*`. `keepReason` then says "N commit(s) exist nowhere else", and the worktree is kept after `done` and listed by `reap` for good. (2) Preps: the prep PR is squash-merged (zz-rules Merging), and this repository deletes merged head branches (`gh api repos/philipbergen/z-nile` gives `delete_branch_on_merge: true`). After the next `fetch --prune`, which every `./zn worktree` and `--takeover` runs, every commit of the discarded prep branch is unreachable, pushed ones included. (3) The note's own recovery path is `git -C <copy> cherry-pick <range>` and `cp` of the dirty files. That gives new shas and leaves the old files in place, so the worktree is still "unrecovered". sweep.spec's "recovered" case instead pushes the discarded branch under a new name (`HEAD:refs/heads/prep-ahead-recovered`) and deletes the dirty file. Nobody recovers work that way, so the spec passes while the real flows keep every worktree. Q1's chosen option ("removed with its branch by ./zn done or z-stop") becomes, in practice, the option the user rejected ("Until you remove it: never removed automatically; ./zn reap lists discarded worktrees").
Critique: Readings 3 sets out to keep only work that exists nowhere else. Measured by sha, work that was squashed, finished or cherry-picked counts as nowhere else. The tempting fix, counting only commits after the pushed tip, still keeps every worktree whose unpushed commits the taker cherry-picked, and every worktree with copied dirty files.
Consequences: A content test reads origin/main's tree, at the cost of one `git merge-tree` per discarded worktree. A commit taken only in part stays kept (fail closed). A later change on main to the same lines makes the merge conflict, so the worktree is kept and listed. That is acceptable, and the listing should say why.
Recommendation: Record the pushed tip in the marker's header (`pushed: <sha>`, read by `discardParse`), and count as recovered every commit reachable from it: the copy started there. For what remains, count the change as recovered when it is already in origin/main: a `git merge-tree --write-tree origin/main <renamed>` whose tree equals `origin/main^{tree}`. Count a dirty file as recovered when its bytes equal origin/main's file at that path, or it is a deletion main also has. Anything else stays kept (fail closed). Add sweep.spec cases for: (a) a raft layer finished by the taker (the branch force-pushed as one squashed commit), then the raft done: removed; (b) a prep squash-merged into the fixture's main, its remote branch deleted and pruned: removed; (c) the note's cherry-pick and `cp` followed and the copy landed: removed; (d) an unpushed commit never taken: still kept. Add the matching Rules rows. If the author keeps sha reachability, the outcome no longer matches Q1. In that case, escalate to the user: options are content-based recovery (above), sha-based keeping with most discarded worktrees left for `reap` (Q1's rejected option in effect), or removing every finished discarded worktree, as Q1 literally says.
Lesson: zz-arch/history-tests-survive-squash

### F3 [high] AC5 says `done` and `stop` sweep, but nothing checks it, and the reasoned rows' reason is false
Where: c0277.md AC5 ("`done` and `stop` run the same sweep"), Rules rows "`done` and `stop` run the same sweep after their last step" (line 255, reasoned); Decided Q1 ("removed with its branch by `./zn done` or z-stop"); check.sh AC5 (sweep.spec only)
Evidence: Q1 names `done` and z-stop as the removers. sweep.spec runs only `worktree-prune`, `sync` and `reap`. A prototype with the two `pcall(hb.sweepDiscarded, true)` calls deleted from `cmd.done` and `cmd.stop` passes check.sh in full. The row's reason ("`done` runs the whole delivery and `stop` needs a readied raft") is not a reason no fixture can observe it. `tests/acceptance/c0068/stop.spec.luau` and `c0275/autobeat.spec.luau` already ready and stop a raft in a fixture. `c0008/done-order.spec.luau` and `tests/tooling/stack-land.spec.luau` run `done` in fixtures, and the gate is skipped inside a spec run.
Critique: The checked criterion promises behaviour that a wrong implementation passes. "`sync` will catch it later" isn't Q1's wording, and it isn't what AC5 states.
Consequences: z-run's lost-raft path is stop, ready, `--takeover`. On a second loss, that path's `stop` sweeps the first discarded worktree, because between stop and ready the raft reads as prepared. That is not the user's "aborted". The clean ones lose nothing, but the design should say so as a reading for veto and pin it.
Recommendation: In sweep.spec, ready a raft (as c0068 does), take over its worktree, end the work with `./zn stop R…`, and assert that `stop`'s own output and tree show the clean discarded worktree and its branch removed and an unrecovered one kept. Add the same with `done` (as c0008/done-order does). Mark both rows `run`, with the "call removed" mutants. Add the stop-for-re-ready reading to Readings for veto.
Lesson: z-design/reasoned-rows-claim-testable-reasons

### F4 [medium] The family is decided by name, not by branch, so unrelated `-<digits>` worktrees join it and a takeover by a copy's name breaks the numbering and the branch
Where: c0277.md "The lookup is by family" (line 145), Chore checklist (1) ("same answer for every worktree that was never discarded", line 159); prototype `heartbeat.currentOf` (heartbeat.luau 560), `cmd.worktree` (main.luau 5896), `hb.takeover` by name (main.luau 5589 to 5593)
Evidence: (1) `suffixOf(base, name)` accepts any `<base>-<n>`. `currentOf` returns the highest one, whatever branch it is on. This checkout has `.worktree/zn-step-2-5` to `-8` today, so `./zn worktree zn-step-2` would print `.worktree/zn-step-2-8` instead of creating `zn-step-2`. Likewise `./zn worktree prep-foo` returns another issue's `prep-foo-2` (slug `foo-2`). `--takeover prep-foo` would judge and, if its claims are lost or over, discard that other item's worktree under prep-foo's numbers. The hand-off made the lookup branch-based ("returns the worktree of the `<name>` family that has the branch checked out"). The design dropped that and says nothing. (2) By name, `base = target` and `hb.worktreeTarget(target)` use the raw target. After a first takeover, `./zn worktree prep-hello-1 --takeover`, the copy's name the takeover printed, does the following: it computes copy `prep-hello-1-1` and renames the copy's branch `prep-hello` to `prep-hello-discarded-1`. That fails with "already exists" while the first discard is kept. Once the first discard is swept, the rename succeeds and the new copy is cut on a new branch `prep-hello-1` from origin/main. That breaks "the numbered copy is on the original branch name and continues the pushed branch". No case covers either.
Critique: A joined key (`<name>-<n>`) whose name part can itself end in `-<digits>` collides with real names. Requiring "no such worktree exists" isn't enough, because names like these are made all the time.
Consequences: A branch-based family needs a rule for rafts, whose copies are detached or on a layer. Unrelated `-<n>` names must still count as taken when numbering, so that paths never collide.
Recommendation: A named worktree `<name>-<n>` is a member of `<name>`'s family only when it is on the family's branch `<name>` (copies keep the original branch name). A raft copy `R####-<n>` is a member when detached or on that raft's layer. Both by name and by id, the takeover takes the base, branch and detach from the named worktree (`baseOf(cur.branch, cur.name)`), not from the raw target. `nextSuffix`'s `taken` keeps every existing entry under `.worktree/`. Cases: an unrelated `prep-foo-2` on its own branch leaves `./zn worktree prep-foo` creating `.worktree/prep-foo`, and `--takeover prep-foo` doesn't touch it; `--takeover prep-hello-1` (after the fresh limit) gives `.worktree/prep-hello-2` on branch `prep-hello` and `prep-hello-discarded-2`. Add Rules rows with the "membership by name only" and "base from the raw target" mutants.
Lesson: zz-arch/joined-keys-forbid-their-separator

### F5 [medium] Q2's push recipe, run in a discarded worktree, silently pushes the taker's branch, and only a bare `git push` is guarded
Where: c0277.md The skills and docs (line 151: z-design "push `prep-<slug>` after every commit"); prototype z-design text "`git push -u origin prep-<slug>`"; step 4 ("unset its upstream ... a bare `git push` ... must not move the PR head")
Evidence: Branches are shared across worktrees. After a takeover, the local `prep-<slug>` is the copy's. An old prep process in the renamed folder commits on `prep-<slug>-discarded-1` and then runs the recipe `git push -u origin prep-<slug>`. That pushes the taker's local branch, publishing the taker's unpushed commits and setting its upstream, and reports success. The old process believes its draft is pushed, never runs a `./zn` command that would tell it, and its own commits stay local. A `git push origin HEAD:prep-<slug>` from the renamed folder fast-forwards the PR head with the old worker's post-discard commits whenever the taker hasn't pushed since. That is the spelling the fixtures themselves use. The upstream unset covers only the bare form.
Critique: The guard stops one spelling of the action it means to stop. The design adds the recipe as Q2's outcome, so the interaction is this layer's.
Consequences: Routing the push through `./zn` costs one engine start per commit, and c0275 then autobeats, which is wanted for a live prep. The recipe has to stay right for a prep that was never discarded.
Recommendation: Spell Q2's push as a `./zn` command first, then the push, e.g. `./zn sync --fetch && git push -u origin HEAD:prep-<slug>`. In a discarded worktree `sync` is refused with the marker's text, so the push never runs and the process is told. Pin the exact phrase in AC6, and add a guard.spec assertion that `sync --fetch` is refused there (it is in the refused list, without `--fetch`). Say in the Design that git commands outside `./zn` are not guarded, and why that is acceptable.
Lesson: zz-arch/guards-decide-from-the-tools-resolution

### F6 [medium] The fail-closed and partial-failure branches have no case that can fail
Where: c0277.md step 4 ("A failure after the marker puts everything back (the directory, the branch, the marker)"), Guards (line 165: "treats an unreadable `origin/main` as 'no claim is known to be over'"), Rules row "a failure after the marker puts back..." (E33, E34 only); prototype `hb.takeover` undo (main.luau 5710), facts (5678), `hb.addWorktree` (5435 to 5450), sweep (5785)
Evidence: (1) No mutant drops the directory move-back. The only failure case (`locked`) fails at the move, so `moved` is never true in any spec. (2) `hb.addWorktree` for a branch that exists only on origin runs `git branch --track <branch> origin/<branch>` and then `worktree add`. If the add fails, the local `<branch>` exists, undo's `git branch -m <renamed> <branch>` fails (its result is not checked), and the marker is removed anyway. The old worktree is then back at its path with no marker, on `<branch>-discarded-n` with no upstream, and the next command there autobeats the lost claim. (3) The fact reads are unchecked. A failed `git -C <old> status --porcelain` gives an empty list, and the note tells the taker "nothing else was left here" while files are dirty. That breaks "kept and shown to the taker". (4) In `discardRefusal`, a held or unheld claim with no verdict is refused: `not (v and …)`, which is right. But no plan.spec case has `verdict = nil` for a held claim, so the mutant `if v and not canTakeOver(…)` (nil passes) survives. (5) The sweep's unreadable-origin rule (`live = paths == nil or …`) has no case. (6) recover.spec asserts `.cache/tracker-beater/c0010` is absent, but specs start no beater (c0275), so the assertion holds whatever the code does. (7) A stray non-worktree directory at `.worktree/<name>-<n>` is not in `taken`, so every takeover of that family fails at `worktree add`, for good.
Critique: These are the branches that decide whether work is lost or the old process is left untold. Each is plausible to get wrong, and none is pinned.
Consequences: Checking undo's own steps means deciding what is left when a step can't be undone. Leaving the marker in place (fail closed) means the old process stays refused and the taker is told what is half done.
Recommendation: Create the copy with one command (`git worktree add --track -b <branch> <path> origin/<branch>`). Have undo check each step, never remove the marker unless the directory and branch are back, and name what it couldn't restore. Refuse the takeover (nothing moved yet) when a fact read fails. Count every entry under `.worktree/` as taken. Cases: a git shim that refuses `worktree add` for the copy path, as the race case shims `status` (directory, branch and marker as they were, no stray branch); a `status --porcelain` shim that fails (refused, nothing moved); a plan case for a held claim with `verdict = nil` (refused, "no heartbeat verdict"); a sweep with origin/main unreadable (nothing removed); either a beater pid file planted before the takeover, or the vacuous assertion dropped. Add Rules rows for each with its mutant.
