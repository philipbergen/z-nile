# c0330: Trace takes claims from a stub capture's Problem

## Problem
Decided with the user (2026-11-14), answering how to fix the trace gate for tickets captured with an empty Solution: "Tooling ticket first (Recommended)" (option text: "File and fast-track a chore: when a ticket's captured Solution is empty (only the template), the trace takes its claims from the captured Problem's outcomes alone. R0092, R0099 and R0100 wait for it, then rebuild trace.md and land. One small extra raft before the three."). Restored by the coordinator after `./zn idea` dropped it (c0260 fixes that drop); idea review F1 and F2 refine "alone" and the readied-raft outcome, see idea-refute-001.md.

- `./zn trace <R-id>` refuses a ticket whose captured document has an empty `## Solution` with "ticket <id> is missing captured ## Solution" (`trace.deriveClaims`, `z-nile/engine/trace.luau:367-433`).
- `./zn done` refuses a raft that holds such a ticket, because its trace is refused.
- `./zn new --desc` writes the captured Problem and leaves the captured Solution as the template comment.
- 26 of 46 designed tickets were captured that way (counted by R0092's executor, 2026-11-14), among them c0264 (R0092), c0280 (R0099) and c0274 (R0100).
- R0092 is blocked at done on c0264 with every review passed.

## Non-goals
- `./zn new --desc` is not changed: it still leaves the captured Solution as the template comment.
- No captured Solution is written or backfilled for the 26 tickets captured without one.
- The refusals for a missing captured `## Problem` and for missing `## Acceptance criteria` are not changed.
- This change does not fill in, restack or land any raft's `trace.md`: R0092, R0099 and R0100 write their own P and AC rows and land themselves (design-review-001 F1 narrowed this fence: the generic outcome that a readied raft passes once its rows are filled is the Solution's last bullet).
- The trace check's rules for P and AC rows are not changed.

## Solution
- `trace.deriveClaims` returns no S claims and no "missing captured ## Solution" error for a ticket whose captured `## Solution` holds only the template comment or nothing.
- Such a ticket keeps its P claims from the captured Problem's outcomes and its AC claims from its acceptance criteria, with the same ids and row labels as today.
- A ticket whose captured `## Solution` has outcomes still gets one S claim per outcome, as today.
- A ticket whose captured document has no `## Problem` outcomes is still refused with "ticket <id> is missing captured ## Problem".
- `./zn trace <R-id>` writes a `trace.md` skeleton with no S rows for such a ticket, and `./zn trace --check` neither expects S rows for it nor reports a Solution refusal.
- An already-readied raft holding such a ticket, when its trace skeleton is rebuilt on the main that carries this change, gets a skeleton with no S rows and no Solution refusal for that ticket.
- (Added in prep) A readied raft holding a ticket captured with only the template under `## Solution`, whose `trace.md` is rebuilt on the main that carries this change and fills its P and AC rows, passes `./zn trace <R-id> --check` and `./zn done`: the captured outcome "a raft already readied rebuilds its trace skeleton on the new main and passes" (AC10 proves it end to end).

## Design
The change is in `trace.deriveClaims` (`z-nile/engine/trace.luau`) and has two parts, both through one new helper:

1. **The refusal narrows.** The branch that appended "ticket <id> is missing captured ## Solution" for every Solution with no outcome now fires only for a Solution that has text but no outcome (for example a fence only). A Solution that is empty once comments and whitespace are removed (the template comment, a blank section, a multi-line comment, or no section) has no S claims and no refusal. `extractOutcomes` already drops comments, so the test is `trim(stripComments(body)) == ""`.
2. **One reader for both sections.** `extractOutcomes(body, keepPrepLines)` ends the captured part at a prep-addition line (`Decided with the user`, `**Scope decision`, `(Added in prep`) unless `keepPrepLines` is true. A new `readSection(body)` reads once the old way and, when that finds no outcome, again with `keepPrepLines`. `deriveClaims` reads `## Problem` and `## Solution` through it. So a section that is only a decision line has that line as its claim, and a section that opens with a decision line followed by outcomes has the line and every outcome after it (c0157's Problem shape: P1 is its decision line, then its six others). A section with an outcome before the line reads as today. This is why c0330's own `./zn done` can pass (E3): its capture's Problem is a single `Decided with the user` line, which today derives no outcome and is refused as a missing Problem. It removes a refusal for those Problems (the ones with a leading decision line) and adds none.

Nothing else changes: the P block (still refused with "missing captured ## Problem" when even the second read finds no outcome), the AC block (still refused when it has none), `trace.skeleton`, `trace.check`, `main.luau`'s `./zn trace` and `./zn done` paths all call `deriveClaims` and take its claims and errors as they are, so they treat both kinds of ticket alike with no code of their own.

Decided with the user (2026-11-14), quoted from the Problem: "when a ticket's captured Solution is empty (only the template), the trace takes its claims from the captured Problem's outcomes alone." The idea review's refinement stands (idea-refute-001.md F1, F2): such a ticket keeps its AC claims. Design-review-001 F1 found that the captured "and passes" had been narrowed on a reviewer's recommendation without a user decision; it is restored as a prep bullet under the Solution (the raft passes once its own P and AC rows are filled, which this change cannot do for it) and proved end to end in AC10, so no scope decision is needed.

Edits, with the restated rules that move together with the engine (checklist: restated rules):
- `z-nile/engine/trace.luau`: delete the refusal, a comment says why; add `readSection` and the `keepPrepLines` parameter; the header contract (CLI paragraph and "Stable claim names" paragraph) says a captured `## Solution` is optional, yields S claims only when it has outcomes, and that a section is read again with decision lines as text when the first read finds nothing.
- `z-nile/skills/zz-rules/SKILL.md`, the `trace` row of the command table: says a ticket captured with only the template under `## Solution` gets no S claims and is not refused, and that a missing captured `## Problem` or `## Acceptance criteria` fails naming the ticket and section, and that a captured section whose first read finds no outcome is read again with those lines as text. Pinned by AC6.
- `z-nile/tests/tooling/trace.spec.luau`, the case "derives stable P, S and AC claims ...": its `noSolution` block asserted the refusal; it now asserts no error and no S claim. ### Scalability
One refusal fewer in a loop over a raft's tickets; the cost is unchanged. A ticket with no S claims has fewer rows, so a raft's table is shorter.

### Maintainability
The rule lives in one place, `deriveClaims` with its `readSection`, so Problem and Solution read decision lines the same way; `skeleton`, `check`, `done` and the `--check` path derive from it, so they cannot disagree about which tickets have S rows. The contract comment and the zz-rules row restate it and AC6 pins both, so wording and code move together.

### Usability
A worker no longer has to write a Solution into a ticket that was captured as a one-line `--desc` to get past `./zn done`; the trace asks for P and AC rows, which is what the ticket's Problem and criteria actually say. The error for a missing Problem or criteria is unchanged.
