### F1 [high] For an issue in `active/`, the retry of an unpushed approval pushes whatever branch the raft's worktree has checked out, not the top layer that holds the approval, and reports success
Where: c0369.md Design section 1 (the raft's worktree "judged by the raft's top layer ... whatever that worktree has checked out"; "an approval it does not hold is recorded there, one it holds is pushed"), section 3 ("An issue in `active/`": "before it records, the acting run refuses unless its checkout is on the raft's top layer"; "`--publish` is that push's retry"); prototype `cmd.approve` (`if publishOnly then count() return end` runs before the top-layer check; `pushBranch` pushes `symbolic-ref HEAD`); Rules and mutants rows "`--publish` is the push's retry for an issue in `active/` too" and "for an issue in `active/` the `pushed` answer ...".
Evidence: a probe case appended to `approve-raft.spec.luau` in `proto-c0369-landed-mut1` (then restored): the raft worktree `.worktree/R0001` on a new top layer `R0001/2/c0001` with an unapproved change; `PICKMAN_PUBLISH=0 ./zn approve c0001` from the main checkout records `tracker: approve c0001` on `R0001/2/c0001` and fails with the retry line, as designed. The worktree is then checked out on `R0001/1/c0001` (an executor fixing a lower layer before a restack, zz-execute's normal flow). `./zn approve c0001` from the main checkout prints `c0001: publishing from .worktree/R0001` and `It lands with R0001: pushed to R0001/1/c0001, nothing to publish.`, exit 0, and `refs/heads/R0001/2/c0001` does not exist on origin (`expected "4c00f273…", got nil`). `load` judged the copy at the top layer (holds, unpushed), so `choose` gave `record = false`; the placed run took `--publish`, which skips the top-layer check that guards recording, and `pushBranch` pushed the checked-out lower layer. Every later run repeats it: the top layer stays unpushed, so `./zn done` (which lands only the published top-layer tip) keeps waiting for an approval the command keeps saying it pushed. No case builds this state: `approve-raft.spec`'s `--publish` call runs only after the layer is already pushed, so it takes the `pushed` answer and never reaches `pushBranch`; approve-branch's "keeps the record when the push fails" covers the prep branch only.
Critique: the guard the user's ruling asked for ("top layer, clean tree, push the layer") is applied to the run that records and not to the run that only pushes, and the push takes its branch from the checkout while the placement takes it from the layer list, so the two disagree whenever the worktree is not on the top layer. The tempting fix is to run the top-layer check before `count` in the push-only run as well. That refuses correctly, but sends the person to get the raft's worktree back onto its top layer before a plain retry can push, which is the "go and change that worktree" step the capture removes, for a push that needs no checkout at all.
Consequences: pushing the top layer by name changes three things. `count`'s `approval.md` presence check reads the checkout's file, which on a lower layer may be missing or older, so for an active push-only run it must judge the top layer's committed copy (what `load` already judged). The success line must name the top branch. And a local top layer that diverged from `origin/<top>` must still be refused as a non-fast-forward push, never forced, with the retry line. A top layer that exists only on origin is already pushed and needs nothing.
Recommendation: for an issue in `active/`, have the push step push the raft's top layer by its own name, `git push origin refs/heads/<top>:refs/heads/<top>` (never forced), whatever the worktree has checked out, with `<top>` from `layergit.layersOf(<R>)` in the acting run. That is the same layer `load` judged. Make `count`'s presence check for that case read `approval.md` at `<top>`, and keep the record run's top-layer and clean-tree refusals as they are. Add to section 3 the sentence that the push of an active issue's approval is of the top layer by name, and add to AC7 "a failed or skipped push of an active issue's approval is retried by `./zn approve <id>` or `--publish` from anywhere, pushing the top layer even when the raft's worktree is on another layer". Add an `approve-raft.spec` case: on a new top layer, with publishing off, it records and fails naming the retry, with nothing on origin. Then, with the worktree checked out on the layer below, the plain command and `--publish` from the main checkout push the top layer (`origin/<top>` equals the local top, `It lands with R0001: pushed to <top>`), the lower layer's origin ref is unchanged, nothing is recorded a second time, and asked again it says `c0001 is approved in .worktree/R0001: it lands with R0001`. Add a mutant entry and Rules row "approve: an active issue's retry pushes the checked-out branch" (the push of HEAD put back). Rerun `mutants.py` for the touched entries.
