### F1 [high] Every real net's own suite inherits PICKMAN_WATCH_NET_READY, so a promoted spec goes red in every run and the net never records a pass
Where: Design §2 (`PICKMAN_WATCH_NET_READY=<ready file> ./zn run … ./zn watch-net`; `watchcmd.net()` writes the file the variable names); prototype `signalReady()`; guess G4 (`PICKMAN_WATCH_KICK_WAIT`).
Evidence: the variable is set on the net's command, so the net's `z-nile/check.sh --full` and every spec it runs inherit it (Lune's `process.exec` passes the environment on, and tests/run.luau's worker `env` only adds two keys). Any fixture `./zn watch-net` in that suite then calls `signalReady()` and writes the outer kick's absolute marker path, which the jail denies (fence.luau `profile`: no write outside the run's `.cache` and temp). On the prototype, `PICKMAN_WATCH_NET_READY=<scratch>/ready.marker lune run tests/run -- tests/acceptance/c0278/readers.spec.luau` gives `FAIL … watch-net files a new slow-tier-red defect …: tracker.sh watch-net failed (1): tracker watch-net: Operation not permitted (os error 1)`. c0278/readers is a promoted fast-tier spec, so in every real net run `--full` is red, `applyRepairs` extends c0278's watch file with the landed sources, writes a watch-miss defect and pushes both to main, and `recordPass` is never reached. `tests/tooling/watch-map.spec.luau` fails the same way in the slow tier. Unjailed (Linux), the fixture's net would instead write into the kicking checkout's real `.cache`. E5 could not see this, because no gate ran inside a real net.
Critique: the fix's first real run would make the net push false repairs, and the "no pass since" line would never clear. The tempting fix is `process.env.PICKMAN_WATCH_NET_READY = nil` in the net after reading it. A Lune `process.env` assignment does not take a variable away from children (zz-arch/child-env-passes-through-exec), so that fix holds only by chance.
Consequences: the marker becomes an argument of `watch-net`, so the usage text, `cmd["watch-net"]`'s option parsing and the cachepaths entry change. G4's knob has the same shape: it is inherited by the net and by every nested kick in the net's suite, which is harmless today but becomes a trap if the wait ever changes behaviour that a spec pins.
Recommendation: pass the marker as a flag, `./zn watch-net --ready <file>`, which nothing below the net sees, and make the kick's bound a flag too (`./zn watch-kick --wait <s>`; G4 rewritten). Add a row and a case: the fixture's stub `z-nile/check.sh` writes `env` into a file under the fixture, and the case asserts that it holds no `PICKMAN_WATCH_NET_READY` (and no `PICKMAN_WATCH_KICK_WAIT`) after a kick; mutant: the marker passed by environment. Record the c0278 run above as an experiment that fails on the prototype and passes on the revision.

### F2 [high] The reaper stops the net the kick detached: any `./zn sync` or gate start a minute after the kick kills the whole run, the worker's own Phase 6 sync included
Where: Design §2's shell line `cd "$1" || exit 1; ( … ./zn run --time 3600 -- ./zn watch-net …; echo $? > …; mv … ) >/dev/null 2>&1 &`; Root cause ("the kick starts the net detached"); Unknowns ("Not proven here").
Evidence: the `( … )` subshell is a `bash` whose parent, the kick's `bash -c`, exits at once, so it is reparented to launchd. Probe (`./zn run --time 40`, the same shell form around `sleep 25`): `89670 1 bash -c cd "$1" || exit 1; ( sleep 25 > …` and `reap: would stop pid 89670 +1 child(ren), … orphaned (its parent is gone)` from `./zn reap --dry-run --root <scratch> --min-age 1`. In real use `bash` is ORPHANABLE, its only ancestor is pid 1 (`ownerless`), and its cwd (the kicking checkout, under `<main>/.worktree/…`) is in the default scope. After 60 s, the next `reapAuto()` (every `./zn sync`) or `./zn reap --auto` (the start of every `z-nile/check.sh` run in any worktree) stops the subshell's tree: `bounded.pl`, the net's `lune`, and its `check.sh --full`. zz-execute Phase 6 step 4 runs `"<root>/zn" sync` after the spend, the report and the PR comment, well past a minute. The `--auto` path is quiet, so the kill leaves no line anywhere. The old form leaves the same orphan (second probe: `9453 1 bash -c cd "$1" && sleep 20 …`), so this is a second reason, besides the relative path, why a net can die silently. A `./zn run` started without the subshell would stop itself instead (`bounded.pl` exits 123 when its starter is gone).
Critique: the Design's Expected behaviour is a kick that starts a net which runs the fast suite and then the slow tier. With this design the net gets its worktree, the kick says "started", and the next sync on the machine ends it. That case falls under the Non-goal's "only the 'no pass since' line shows it", so the line would keep firing on a healthy machine. The tempting fix is `nohup` or `setsid`. Neither changes the parent pid or the cwd the reaper judges.
Consequences: the reaper needs to know the net, which touches `engine/reap.luau` and its specs, and adds a named exemption to a guard. It must stay narrow: only the kick's exact shape (the subshell whose command is the kick's line naming `./zn watch-net`, and its tree, including rokit's `lune` shim), never any orphan carrying a deadline. The net stays bounded, because `bounded.pl` and the MARKED rule still stop it at its 3600 s deadline. If the exemption is a separate issue, it must be in this raft (an issue added to the raft, not a backlog ticket), or the net still never passes after this lands.
Recommendation: add to the Design a `reap` exemption for the net's tree, matched by the kick's command line (as zz-test/detached-helpers-meet-the-reaper describes for helpers that outlive their starter), with a pure case in the reaper's rules: a `ps` listing holding the kick's subshell at age 120 s with ppid 1 and its tree is not a target, and the same tree with another command still is. Add an experiment run the way the real command runs it: a fixture kick whose stub gate sleeps on a marker, then after the subshell is more than a minute old (or with `--min-age 1` and `--root <fixture main>`), `./zn reap --dry-run` does not list it. Add a row with the mutant "no exemption". Touched modules gain `z-nile/engine/reap.luau` and its spec.

### F3 [high] Two kicks now start two nets in the one standing worktree with no lock: the second net's rebase rewrites the tree under the first net's running suite
Where: Design §1 ("reuses that worktree when it exists") and §2; Scalability; the Test plan's "a second kick from another worktree" (sequential: it settles the first net before the second kick).
Evidence: before this fix, only kicks from the main checkout (the dispatcher's) reached `.worktree/watch-net`. Kicks from worktrees, which means every `./zn land` of a capture and every raft's Phase 6, failed at `git worktree add`. After it, every kick reaches the same directory. A capture landed while a net runs its `--full` (minutes, then the slow tier) starts net 2. Net 2's `ensureWorktree` runs `git fetch` and `git rebase --quiet origin/main` in `<main>/.worktree/watch-net`, which fast-forwards the files the first suite is reading. The first net then reads failures from a mixed tree and pushes `applyRepairs` watch-file extensions and watch-miss defects onto main, or records `head` as passed on a run that saw part of a later main. When net 1 has written repair files and not yet committed them, net 2's rebase fails instead, and the second kick reports a false error with exit 1. Net 2's `check.sh` then meets the runner's per-checkout lock (`waiting for another test run`, up to 240 s). Nothing in watchcmd.luau serialises nets.
Critique: this is a wrong result on main, created by the new reach of the kick. The tempting fix is a lock file the second net just waits on. A net can run for an hour, so the kick or a landing would wait with it.
Consequences: a lock brings a lock owner, a stale lock (a net killed by its deadline or the reaper), and the landings that arrive during a run, which the running net's `sincePassed` (fixed at its start) does not cover. G1's reason ("a retry would start a second net while the first may be fine") also rests on this.
Recommendation: one lock per repository, held from before `ensureWorktree`'s fetch to the net's end: a file in the git common dir holding the pid and the start id, taken over when no process it records still holds it (the runner's lock rule, zz-test "Lock"). A net that finds a live lock touches a rerun request beside it, writes its ready marker, prints `watch-net: already running (pid N); a rerun is requested` and exits 0. The kick prints that and exits 0. The running net, at its end, runs once more if a rerun was requested. Cases: two kicks from two worktrees while the stub gate holds on a marker give one suite at a time (the stub appends `start`/`end` lines to a fixture file and the spec asserts no overlap), the second kick exits 0 with "already running", and the worktree's HEAD does not move during the first run. A lock whose pid is dead is taken over. A rerun request makes the first net run again. Rows: the mutants "no lock", "a stale lock holds forever" and "the request is dropped".
Erred: z-design

### F5 [high] G1 shrinks a captured outcome: at its bound the kick returns while the net has neither its worktree nor has exited, and says success
Where: guesses.md G1; Design §2 ("At the bound: prints 'still starting …' on stderr and returns true"); acceptance case "a kick whose net is still starting at the wait's bound says so on stderr and exits 0".
Evidence: Solution 2 (idea stage, #499): "`./zn watch-kick` returns only after the net it started has either created or reused its worktree or exited". G1 makes the kick return in a third state, with exit 0. The same state also covers a net whose subshell was killed before either file was written (F2's reaper, a SIGKILL). The kick then waits the full 120 s and says "still starting" about a net that is gone.
Critique: scope is the user's. The guess records the choice, but a guess that shrinks an outcome is still a finding (zz-review, Design mode), and here a design exists that keeps the whole outcome. G1's reason (a retry after exit 1 would start a second net) holds only without F3's lock.
Consequences: keeping the outcome moves the bound into the net. Its start (both fetches and the rebase) runs under a start limit and exits with one line when the limit passes. The kick also has to tell "exited" from "running", which needs the subshell's pid (`echo $!` from the `bash -c`, whose stdout the kick reads). A bound in the kick is still needed as a backstop for a stuck kick, but it can then say failure.
Recommendation: the net bounds its own start (`./zn run --time <start> -- git fetch …` for each fetch, a `--start <s>` flag, default 120) and fails with `watch-net: no worktree after <s> s (<step>)`. The kick waits for the marker, the exit file, or the subshell's pid being gone (that is an exit: it prints `watch-net: the net ended before it had its worktree` and returns false). The kick's own backstop (start plus a margin) is a failure, exit 1. G1 is then withdrawn. The bound case asserts exit non-zero with the net's line. Add a row for the pid-gone exit, with a case that kills the fixture's net group before ready. If the user prefers exit 0 at the bound, record their answer as a `Decided with the user (YYYY-MM-DD)` line.

- G2 (no line when the history has no pass commit): sound. The captured rule compares against "the last pass commit", which does not exist, and every fresh fixture or clone would otherwise warn. - G5 (a landing waits and keeps its exit status): sound. With F5 the wait is bounded by the net's start limit, and with F3 a landing during a running net returns at once with "already running".
