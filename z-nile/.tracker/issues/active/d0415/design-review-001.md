### F1 [high] A nested review run's unrecorded row is never shown by `dispatch status` and never written, and nested runs are how the chain runs every review
Where: d0415.md, The change, item 6; AC5; `acceptance/dispatch.spec.luau` "AC5: a row that cannot be recorded stays pending ...".
Evidence: a step started inside a dispatched step gets a fresh state folder, `{ZN_DISPATCH_DIR}/{step}-{mode}-{id}-{n}` (dispatcher.luau:2128-2140, a new `n` per run), while `dispatch status <id>` and `flush` read `dirOf(ctx, id)` = `{home}/{id}` (dispatcher.luau:110). Under `./zn dispatch`, z-design's and z-raft's reviews are such nested runs. This machine already shows it: `.cache/dispatch/d0298/zz-review-raft-R0094-1/state.json` holds a pending `design-review` row of 165,345 tokens, and `./zn dispatch status R0094` prints `"pending": {}`. The same holds for R0077, R0069 and R0072 under d0298, and for f0339's and c0359's nested design reviews. The design's status line reads `st.pending` of `{home}/<id>` only. `flush` runs only on that folder, and the next nested run claims `-2`, so nothing ever reads the row again. The new `UNRECORDED spend` line goes to the stderr of a `./zn` command the author model ran, a tool output that nobody reads under the chain. The AC5 case dispatches top-level only, so an implementation that ignores nested folders passes it.
Critique: the captured outcome is about any review run. For the reviews the unattended chain runs, the spend stays on no ledger and in no report, which is the fourth Problem bullet unchanged. The tempting fix is to make `dispatch status` glob the nested folders.
Consequences: listing alone still never writes the row. `flush` must also take nested rows, and must then rewrite the nested `state.json` without the taken row, or a later flush writes it twice. A nested folder whose run is still alive (its `beat` fresh) must be skipped. A child cannot instead add its row to `{home}/{id}/state.json`: when the parent is the same item (z-design of c0010 runs the nested review of c0010), the parent holds that file in memory and its `save` at the end overwrites the child's write. A row whose item has left the backlog is still never taken (F4).
Recommendation: add one edge reader, `pendingRows(home, id)`: the rows of `{home}/{id}/state.json` plus those of every state folder under `{home}` named `<step>-<mode>-{id}-<n>`, each with its file. `dispatch status <id>` and `flush` at the start of a top-level run of `<id>` both use it, and `flush` removes a written row from the file it came from, skipping folders whose run is alive. Rules and mutants rows and cases in `dispatch.spec`: (a) a nested run (`ZN_DISPATCH_DIR` set to a parent folder) whose row cannot be recorded, then `dispatch status <id>` lists it (mutant: status reads `{home}/{id}` only); (b) a later top-level `./zn dispatch <id>`, with the row now recordable, writes it once and the nested `state.json` no longer holds it, and a second run writes nothing (mutant: the row is written but left in the nested file). The same reader feeds F2's report.

So "the way `./zn spend <R-id>` shares it" is not what the design builds, and G2's own example ("gives c0189 a design-review-002 row") describes the branch's members, not what the Design and specs pin. The fixture cannot tell the two apart, because origin's R0095 and the author's worktree both list `c0030, c0040`.
