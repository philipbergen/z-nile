# f0399: z-work works every ticket

## Problem
- z-work takes only rafts that are ready, so a ticket that is captured, designed or prepared but not yet rafted and readied gets no work from a z-work session.
- Nothing states the order in which z-work would pick among tickets at different steps and with different dependencies.

## Non-goals
- z-work never lands a ticket the human has not approved, however green its gates are.
- This ticket does not change what `./zn dispatch` does, which stays with c0267 and c0252.
- This ticket does not define stacked PR delivery or part landing (c0248), work rank beyond the order above (c0249), or how an added issue waits inside its raft (c0394).

## Solution
- With no raft named, z-work picks any ticket that is not landed and does its next step (design it, fix it, raft it, or implement it), using its best judgement where the ticket leaves a choice open.
- z-work picks in two tiers, and the tier always wins: every ticket with no unmet dependency comes before any ticket that has one.
- Inside a tier, z-work picks the ticket furthest along first (ready raft, then rafted, then prepared, then designed, then captured), so a captured ticket with no dependency is taken before a prepared ticket that depends on an unlanded one.
- A ticket has an unmet dependency when a ticket it depends on has not landed on main.
- z-work starts the second tier only when no ticket in the first tier has a step left that it can do without the human.
- z-work branches a ticket with an unmet dependency off that dependency's branch, not off main.
- z-work puts a ticket and the tickets it depends on in one raft.
- z-work records every guess and assumption it makes in the ticket it made it for, each with what it chose and why.
- A ticket picked up before it was approved may go through every step up to landing, and does not land until the human approves it.
- A ticket with a material change, guess or judgement call pauses after all its gates pass, and continues only on the human's approval.

## Design

Every **Guess (prep)** below is a choice the capture left open, made without the user (the user, 2026-11-16: "make guesses and evidence based assumptions to work through the design without me. I'll review them all before approving"). They are listed again under Unknowns & experiments, G1 to G22, each with its evidence and what the other choice would cost.

Words used below. A **guess** is any choice the worker makes that the approved contract of an issue does not already make: an open question answered, a judgement call, a ruling it would otherwise have asked for, a deviation from the design while building. A **material change** is a change to any part of an issue's contract (its Problem, Solution, Design, Acceptance criteria, Test plan, `check.sh`, acceptance specs or `guesses.md`). **Guess mode** is a session that takes its actions from `./zn work next` and is not under `./zn dispatch` (`ZN_DISPATCH` unset), or a session the user told to guess. An approval **holds** when the issue's `approval.md` exists and its last row's hash equals the contract's hash now (`approval.verdict`, state `holds`).

Where this sits (**Guess (prep) G1, G2**). f0399 is designed on today's `main`: on `work.luau`'s `./zn work next`, with no dependency on the vision raft (c0248 to c0254) or on c0394. It does not edit their documents. Section 9 says what each of them meets when it is built after f0399. `experiments/prototype.patch` is the reference for the pure modules (`guesses.luau`, `contract.luau`, `openlist.luau`, `raftplan.luau`, `work.luau`): the sequestered pure specs pass on it.

### 1. Guesses are a file the approval covers

**The file.** `<issue dir>/guesses.md`, one line per guess, oldest first:

```
# guesses
- G1 (design, 2026-11-16): <what was open>. Chose: <what the worker chose>. Why: <the evidence>.
```

The step is `design`, `raft` or `build`. Ids count up from G1 with no gap. A field holds no line break and neither of the marks ` Chose: ` and ` Why: `. A guess is never edited or removed once it is pushed: a guess the worker changes its mind on gets a new line that names the old one.

**`z-nile/engine/guesses.luau`** (new, pure):

```luau
export type Guess = { id: string, step: string, when: string, open: string, chose: string, why: string }
guesses.FILE = "guesses.md"
guesses.STEPS = { "design", "raft", "build" }
-- nil and the problem for a text that is not the header and well-formed lines numbered from G1
function guesses.parse(text: string): ({ Guess }?, string?)
-- the file's new text with one more guess; nil and the problem for an unknown step, an empty field,
-- a field with a line break or a mark, or a `text` that does not parse
function guesses.append(text: string?, step: string, when: string, open: string, chose: string, why: string): (string?, string?)
function guesses.render(list: { Guess }): string
function guesses.has(text: string?, id: string): boolean
-- is `new` the guesses of `old` with nothing removed or changed, and any number added?
function guesses.extends(old: string?, new: string?): boolean
```

**`./zn guess <issue-id> --step design|raft|build --open "<…>" --chose "<…>" --why "<…>"`** writes the issue's `guesses.md` in this worktree and prints `<Gn> recorded for <id>: commit it with your work`. It commits nothing (as `./zn idea`), refuses the main checkout (`refuseInMainCheckout`), an id that is not an issue in this checkout, an issue in `done/` (`<id> is done: nothing left to guess`), and what `guesses.append` refuses, printing `guess: <the problem guesses.append gives>` and leaving the file as it was. An empty option value is an empty field. The date is today's (UTC).

**`./zn guesses <issue-id|R-id> [--check]`** is read-only (it joins `READ_ONLY`). For an issue, or each member of a raft in the raft's order, it prints a head line `<id>: <n> guesses, <approved|not approved|changed since approval (<parts>)>` and then the guess lines as written. An issue with no `guesses.md` prints its head line alone, with `0 guesses`. `--check` prints nothing on stdout, and exits 1 with `<path>: <problem>` on stderr when a `guesses.md` does not parse. It reads this checkout, so the person runs it in the worktree that holds the work.

**The approval covers it.** `contract.build(doc, check, specs, guesses: string?)` gains an optional fourth text. When it is given and not empty, the parts gain one named `guesses` (its normalized text); otherwise the parts are today's, so no existing approval changes. In `contract.order` it sorts after `check.sh` and before the specs. A spec named `guesses` is refused as `design` and `check.sh` are. Every caller of `contract.build` hands it the file: `approval.collect` (which also lists `<issue dir>/guesses.md` among the contract's paths, so `approve` refuses an uncommitted one), `readycheck.reason` (from `Member.files["guesses.md"]`, which `readyfacts` and `workread` fill), and `./zn approve <id> --publish`, which builds the contract from `origin/main`'s folder listing and takes `guesses.md` from that listing. Those three are all the callers outside `contract.luau`.

So a guess recorded after an approval makes that approval stop holding, and every message that names changed parts names `guesses`. This is what enforces the capture's "pauses after all its gates pass": section 3 lets nothing land without an approval that holds. **Guess (prep) G3.** `guesses.md` is not one of `raftplan.isDesignFile`'s files, so a guess recorded while rafting does not make a raft's `grouped:` record stale.

**Guesses are only added.** `./zn finish`, `./zn done` and `./zn approve` refuse, before their other checks (right after the fetch), an issue whose `guesses.md` in this tree does not extend (`guesses.extends`) the one on `origin/main` (at the issue's path there) and, for a layer that is already pushed, the one at `origin/<layer branch>`: `<id>: guesses.md no longer holds <Gn> as it was pushed: a guess is never removed or changed (add a new one that names it)`. So a pushed guess cannot be deleted to bring an old approval back. A guess written and removed before any push leaves no trace; the zz-review reviewers read the diff for judgement calls with no guess (section 7).

### 2. A guessed answer under "Open to the human"

Today a refuted finding or an unclosed high stops for the person's `Ruled (user, YYYY-MM-DD):` line. In guess mode the worker answers it with a guess instead:

```
- F2: <the finding>. Answer: <the answer>. Decision: <what the human must decide>
  Guessed (agent, 2026-11-16): G3
```

In a raft's document the guess is named with its issue: `Guessed (agent, 2026-11-16): c0010 G3` (a raft has no approval of its own, so a raft-level guess is recorded in the member it concerns, or in the raft's first member in its order when it concerns the whole raft). A later `Ruled (user, …):` line on the same bullet is the person's ruling as today.

`openlist.luau`:

```luau
-- today's meaning, unchanged: bullets with no `Ruled (user, YYYY-MM-DD):` line
function openlist.pending(doc: string): { string }
-- bullets with neither a Ruled line nor a Guessed line
function openlist.waiting(doc: string): { string }
-- the Guessed lines of bullets with no Ruled line; `issue` is nil when the line names only a guess,
-- and `guess` is "" when the line names none
function openlist.guessed(doc: string): { { id: string, issue: string?, guess: string } }
```

`openlist.problem` judges by `waiting`, and its message is unchanged. Who asks what:

| asker | accepts a Guessed bullet | why |
|---|---|---|
| `./zn status <id> preparing` (`idea.designRefusal`, `openlist.pending`) | no | the idea is the person's (G7) |
| the dispatcher (`dispatcher.luau`, `openlist.pending`) | no | dispatch is unchanged (Non-goals) |
| `./zn status <id> prepared`, `./zn ready`, `./zn done`'s review check (`openlist.problem`) | yes | the guess is in a `guesses.md` an approval must cover |
| `./zn approve` (`openlist.waiting`) | yes | approving is the person's ruling on every guess the hash covers |

`./zn status <id> prepared`, `./zn approve`, `./zn ready` and `./zn done` refuse a Guessed line that names no guess, or one that does not exist: `<id>: F2's Guessed line names <issue> <Gn>, which is not in <issue>'s guesses.md` (for a line that names no guess, the words after its colon stand where `<issue> <Gn>` does, and `<issue>` is the document's own issue, or the raft's first member). Each checks the bullets of the documents it already judges: the issue's for `status` and `approve`, the raft's and every member's for `ready` and `done` (`guesses.has`; `status`, `approve` and `done` read this checkout, `ready` reads the folders on `origin/main` it already loads). **Guess (prep) G8.**

### 3. Approval is checked at the landing, not at ready

Today `ready` refuses a member with no approval or a changed contract (`readycheck.reason`, `approval.reasonOf(…, true)`), `finish` refuses a changed contract, and `done` refuses a changed contract but lets a member with no approval on `origin/main` land. After f0399:

**The record of a readying.** `./zn ready` (outside the dispatcher) adds the trailer `Lands: approved` to the body of its one ready commit on `origin/main` (`tracker: ready <R> <title>`), and with `--on <D>` (section 6) the trailer `On: <D>`. The raft's document is not changed, so `publish.movedEdit`, `stop` and the promoted ready-and-stop round trip (`c0068/stop.spec`) are untouched. `layergit.readyRecord(raftId): { lands: boolean, on: string? }` reads the newest commit on `origin/main`'s first-parent history whose subject starts `tracker: ready <R> `, `tracker: start <R>` or `tracker: stop <R> `, and returns that commit's trailers when it is a ready commit, else `{ lands = false }`. A commit on `origin/main` cannot be rewritten by the worker, and nothing in a worktree is read for it, so no edit on a layer turns the rule off. A raft stopped and readied again is judged by its new ready commit. `finish`, `done`, `start`, `restack`, `stack` and `workread` all ask `readyRecord` (workread from the `git log` it already runs for the holder, with the body added to its format).

- **ready**, outside the dispatcher, asks for no approval: a member with none is accepted. A member whose approval holds is accepted. A member whose approval no longer holds is accepted when `guesses` is the only changed part (a guess recorded since), and refused with today's message when any other part changed: an approved contract that was edited in the backlog goes back to the person before work starts on it. **Guess (prep) G19.**
- **ready under the dispatcher** (`ZN_DISPATCH` set) is today's: every member needs an approval that holds, and no `Lands:` trailer is written. The dispatcher's only approval stop is this refusal (its `z-ready` step is `./zn ready`), and c0267's design is built on it; a raft readied this way has every member approved and lands by today's rule. `readycheck.Raft` gains `requireApproval: boolean?`, which `readyfacts` sets from `ZN_DISPATCH`; `workread` leaves it unset.
- **finish**, on a raft whose record has `lands`, does not refuse a member whose approval does not hold. It prints `note: <id> is not approved (<no approval | changed: <parts>>): <R> will wait for ./zn approve <id> before it lands`. On any other raft it refuses as today.
- **done**, on a raft whose record has `lands`, refuses unless every member's approval holds in the tree it lands, naming all of them in one message: `<R> waits for approval: <id> (no approval), <id> (changed: guesses, design). The person runs ./zn approve <id> in this worktree; ./zn guesses <R> lists what to review.` On any other raft it behaves as today (an approval on `origin/main` must hold, a member with none is left alone), so the six active rafts readied before approvals existed (R0061, R0068, R0070, R0073, R0078, R0084), every raft readied under the dispatcher, and every existing fixture that starts a raft without `ready` land as they do now. **Guess (prep) G4.**
- **The whole raft waits** for its last unapproved member: `done` lands all layers or none, as today. **Guess (prep) G5.**
- **approve for an active issue.** The person runs `./zn approve <id>` in the raft's worktree (`./zn worktree <R>`). For an issue in `active/` the command refuses unless the worktree is on the raft's top layer with a clean tree (`<id> is active in <R>: run ./zn approve <id> on <top layer branch> (cd "$(./zn worktree <R>)")`), commits `approval.md` there as today, and pushes that layer (`git push origin HEAD`; a failed push is the command's failure, and the commit stays). Its last line is `It lands with <R>: pushed to <branch>, nothing to publish.` `./zn approve <id> --publish` refuses for an active issue: `<id> is active in <R>: its approval lands with the raft`. Who may run it does not change (a terminal on stdin, never under `ZN_DISPATCH`). An issue still in the backlog is approved and published as today. **Guess (prep) G6.**
- **A layer stays finished.** `layergit.isPostFinishPath` also accepts `approval.md` and `guesses.md` in any issue's folder (`…/issues/active/<id>/approval.md`, `…/issues/<id>/approval.md`, and the same for `guesses.md`), so the approval commit, and a guess recorded while answering the code review, do not turn a finished layer back into an unfinished one.
- `./zn land` (a capture) is unchanged.

### 4. What `./zn work next` picks with no raft named

`work.luau` (pure). `Input` and `RaftFact` gain optional fields, so every existing literal still type-checks:

```luau

	id: string,
	root: string, -- the project's tracker root
	status: string, -- the effective status: new, preparing, prepared, active, closed (no done issue is listed)
	raft: string, -- "" when it is in none
	designReady: boolean,
	sized: boolean, -- has a size: z-raft can use
	deps: { string }, -- depends_on
	draftBlock: string, -- "" when z-design's claim gate accepts it (idea.designRefusal), else its reason
	added: boolean?, -- has `waits:` in its frontmatter (a c0394 added issue): never picked here

export type Carrier = { session: string, age: number } -- who last asked for an item, and how many seconds ago
-- Input, new optional fields:
--   issues: { IssueFact }?            nil: the picks are today's
--   session: string?                  this session's id (sessionread's running session); nil or "": it cannot be named
--   carriers: { [string]: Carrier }?  by raft or issue id
-- RaftFact, new optional fields:

work.STALE = 6 * 3600
function work.free(id: string, input: Input): boolean -- may this session resume an item nobody named?
function work.unmet(deps: { string }, issues: { IssueFact }): { string } -- the ids that are in the list
-- the one unlanded raft `r` could be built on, or nil and the reason: "depends on <x>, which is in no active raft
-- with every layer finished", or "depends on <R1> and <R2>: a raft is built on one raft"
function work.baseFor(r: RaftFact, rafts: { RaftFact }, issues: { IssueFact }): (string?, string?)
```

**Unmet dependency.** An issue has one when a `depends_on` id is not in `done/` on `origin/main`; a raft has one when any member has one outside the raft. This is the capture's definition.

**Whose held work.** The capture's order starts with the ticket furthest along, and that is work already started. Today an unnamed session never resumes a held raft, because the holder is a person and a second session of that person may be building it. f0399 adds the missing fact. `./zn work next` keeps `<main checkout>/.cache/work/carriers.tsv` (ignored, one line `<id>\t<session>\t<epoch seconds>` per item, where `<session>` is the id `sessionread`'s running session has: Claude Code's `CLAUDE_CODE_SESSION_ID`, Kimi's session id): a call that names an item, and an unnamed call whose pick is an item, write that item's line with this session and the time; a named call whose action is `end`, `wait` or `none` removes it. `work.free(id, input)` is true only when this session can be named and the item has no carrier, or this session is its carrier, or its carrier last asked more than `work.STALE` (six hours) ago. A session that cannot be named (Grok, Cursor) resumes nothing unnamed, as today. **Guess (prep) G13.** c0265's heartbeat replaces this file when it lands.

**The order** (`work.decide`, no raft named; the count of releases in a row is checked first, as today). The first that exists is the pick; inside one line the lowest id wins (`work.rankKey`, which c0249 replaces):

Tier 1, nothing unmet:
1. **done**: an active raft this author holds, free, whose next action is `done`.
2. **resume**: an active raft this author holds, free, whose next action is `implement`, `finish`, `restack`, `review`, `trace` or `final-review`. Its line starts `Resuming <R>: you hold it and no live session carries it.`
3. **ready**: a backlog raft `ready` would accept (`block == ""`).
4. **fix**: a backlog raft `ready` refuses for something the worker can repair (`work.fixable`: prepared, no `questions.md`, no unmet dependency, and the refusal is not a changed approval).
5. **rafting**: a backlog issue that is `prepared`, `design: ready`, sized and in no raft.
6. **fix**: a backlog issue that is `prepared` and in no raft with no `size:`.
7. **draft** (resume): a `preparing` issue that is `mine` and free.
8. **draft**: a backlog issue that is `new`, in no raft, with `draftBlock == ""`.

Tier 2, something unmet, only when tier 1 has no pick:
9. **ready** `--on <D>`: a backlog raft that `ready` refuses only for its unmet dependencies (`blockOn == ""`), when `work.baseFor` names one active raft `D` whose every member has a finished layer (section 6).
10. **rafting**, **fix**, **draft** (resume), **draft**: as 5 to 8, when every unmet dependency is `design: ready` (prepared, active).

This is the capture's order: the tier wins, and inside a tier the ticket furthest along is first (a raft to land, a raft being built, a raft to ready or repair, a prepared issue, a design under way, an issue to design). **Guess (prep) G10, G11.** Every unnamed pick's line keeps today's `you hold <ids>: name one to resume it.` when this author holds rafts that were not picked.

**"Fix it"** (the capture: "design it, fix it, raft it, or implement it"). **Guess (prep) G20**: it means repair what stops a ticket from moving when the worker can repair it. Inside an action that is today's work, done in guess mode: answer a review's findings, make a red check green, restack. Between actions it is the new action `fix`, for the two states that today are only skipped with a reason: a raft `ready` refuses (a stale `grouped:` record, a coherence review that predates its record, a member that is not `design: ready`, an open bullet the worker may answer with a guess), and a prepared issue with no `size:`. A `fix` that does not clear the refusal is offered again; the worker counts a `fix` that changed nothing as a release, so two in a row stop the session.

What is never picked without being named, each with a reason line (below): an issue that is `preparing` in another checkout or carried by a live session, and a raft another person holds or a live session carries; an issue whose idea was not challenged or has an unruled bullet (**G7**); anything closed; a c0394 added issue (**G15**).

**The actions' lines.** An issue-level pick has `raft = ""` and `ticket = <id>`, and `work.say` prints `<id>: <action> - <why>` for it (today's `nothing: …` form is only for `none`):

- `draft`: `Design <id> in guess mode (z-design): ./zn status <id> preparing in a prep worktree, record every open choice with ./zn guess, merge the prep pull request when it is green, then ask again.` For tier 2 it adds `It depends on <ids>, not landed: design from their documents, and run prototypes on their layer branches where they have one.` A resume says `<id> is being designed and its prep worktree is here: resume it (z-design, guess mode), then ask again.`
- `rafting`: `<id> is prepared and in no raft. Run z-raft with no argument in guess mode (./zn raft-plan --apply), merge the rafting pull request when it is green, then ask again.`
- `fix` for a raft: `ready refuses <R>: <block>. Repair it in guess mode (z-raft: a new coherence round, ./zn unfold and fold again, or the member's z-design), merge the pull request when it is green, then ask again.` For an issue: `<id> is prepared with no size:, so z-raft cannot place it. Record z-design's estimate of changed lines as size: by a tracker pull request, merge it when it is green, then ask again.`
- `ready`: today's line; for tier 2, `<R> is prepared and depends on <D>, whose layers are finished. From the main checkout run ./zn ready <R> --on <D>, then ask again.`
- `wait` (new, from `work.forRaft`, after the final review is approved and the trace passes): `<R> waits for the person: ./zn approve <ids> in its worktree (<id> (<why>), …); ./zn guesses <R> lists what to review. Tell the person, then ask again with no raft.` The same action, with `<R> is built on <D>, which has not landed.`, when everything is approved and the raft it is built on is not done.
- `done`, `implement`, `finish`, `restack`, `review`, `trace`, `final-review`, `release`, `end`: unchanged, except that the review line's `Do not guess a ruling.` becomes `Do not guess a ruling under ./zn dispatch; otherwise answer an open ruling with a recorded guess (./zn guess).`

`work.forRaft(r)` gives `wait` where it gives `done` today when `r.unapproved` is not empty, or when `r.on` names a raft that has not landed. A raft whose record has no `lands` never has `unapproved` filled, so it goes to `done` as today.

**Naming an issue.** `./zn work next <issue-id>` and `./zn work <issue-id>` are accepted (`^[fdc]%d%d%d%d$`). `work.forIssue(i, input)`: an issue in a raft gives that raft's action; `new` gives `draft` (or `none` with its reason); `preparing` gives `draft` with `<id> is being designed: resume its prep worktree (z-design, guess mode), then ask again.`; `prepared` with no raft gives `rafting` or `fix`. Naming resumes a held design whoever carries it, as naming a raft does.

**When nothing is picked**, the head line stays `nothing to do - no claimable raft[ in <project>]` and the reason lines follow as today. `work.skipped` keeps one line per raft, and `work.skippedIssues(issues, all, input)` adds one per backlog issue in no raft that was not picked (`issues` is the project's, `all` is every issue, since a dependency may be another project's): `<id>: is being designed (preparing): name it to resume`, `<id>: its idea needs the person (<draftBlock>)`, `<id>: depends on <dep>, which is not designed`, `<id>: depends on <dep>, which is closed (won't do): its depends_on needs the person`. A raft at `wait` prints `<R>: waits for approval: <id> (<why>), …`. `./zn work queue` prints the same lines. `./zn work status` adds ` waits for approval: <ids>` to the row of a raft at `wait`.

**After a pick.** A `wait` is not a release: the session says what waits and asks again with no raft. A `draft` the worker gives back (section 7) counts as a release, so two in a row stop the session as two blocked rafts do (**G18**).

**Reading the facts** (`workread.collect`). The issue documents of every issue not in `done/` are already in its one `cat-file --batch`; it adds each `new` raftless issue's `idea-review-001.md` to that batch and builds the `IssueFact`s from them (`idea.designRefusal` for `draftBlock`, `raftplan.parseSize` for `sized`, `waits:` for `added`, the folder `.worktree/prep-<slug>` under the main checkout for `mine`). `lands` and `on` come from the ready commits its one `git log` already lists, and `onLanded` from the tree listing. `outside` is the members' `depends_on` less the members. `blockOn` is read only for a prepared backlog raft with `outside` ids that are not done: `readycheck.reason` once more with `Raft.onMembers` set to the members of the raft `work.baseFor` names, and `""` when it and `readycheck.record` pass. `unapproved` is read only for an active raft with `lands` whose final review is approved: one `git ls-tree -r` of the top layer's tip under each member's folder and one `cat-file --batch` for the documents, `check.sh`, specs, `guesses.md` and `approval.md` there, judged by `approval.reasonOf(…, true)`. `session` is `sessionread`'s running session, and `carriers` is the carriers file.

`dispatch.next` is not changed, and the spec that holds the two decisions to the shared facts still holds: a prepared backlog raft is `ready` here and `z-ready` there.

### 5. z-raft bundles a ticket with what it depends on

`raftplan.Issue` gains `deps: { string }?` (its `depends_on`), filled by `cmd.raft-plan`. `raftplan.plan`:

- **features**: two candidates, or a candidate and an open prepared backlog raft, are also joined when one depends on the other (or on a member of that raft), whether or not their Touched paths overlap.
- **chores and defects**: candidates are placed in dependency order (an issue after the candidates it depends on, lowest id first among the free). An issue that depends on an issue already in a bin goes into that bin; otherwise the first bin that fits, as today.
- **the cap never splits a dependency**: an issue joined to a raft by a dependency is placed there even when the sum passes `raftplan.CAP`. (The user's standing rule: "stack dependencies in one raft".)
- unchanged: one type and one project per raft, a `solo: true` or over-cap issue is a raft by itself, a `single: true` raft takes nothing, and only a prepared backlog raft is folded into.

So "z-work puts a ticket and the tickets it depends on in one raft" holds for a dependency of the same type and project that is not yet readied. A dependency of another type or project, a solo one, or one already in an active or done raft, stays in its own raft, and the dependent's raft is built on it (section 6). **Guess (prep) G12**, from the user's standing rule "never mix c/f/d" in one raft.

### 6. A raft built on a raft that has not landed

**`./zn ready <R> --on <D>`** readies `R` although members depend on issues that are not done. It accepts when: every dependency of `R`'s members outside `R` is done or a member of `D`; `D` is active on `origin/main`; and every member of `D` has a finished layer (`layergit.layersOf(D)`, `layergit.layerFinished`). It adds the trailer `On: <D>` beside `Lands: approved` to the ready commit (section 3). Refusals, each naming the rule, checked in this order: `--on <D>: <D> is not an active raft`; `--on <D>: nothing in <R> depends on <D>`; `--on <D>: <m> depends on <x>, which is not done and not in <D> (a raft is built on one raft)`; `--on <D>: <D>'s layer for <x> is not finished: <R> can be built on <D> once every layer of <D> is finished` (a member of `D` with no layer yet is not finished). `readycheck.reason` takes the base's members as done for the dependency rule (`Raft.onMembers: { string }?`). Without `--on`, `ready` is today's. `--on` is refused under the dispatcher (`--on is not for ./zn dispatch`).

**The base commit.** `D`'s top layer was cut before `R` was readied, and perhaps before `R` was designed, so its tree holds `R` and its members in the backlog or not at all. A layer cut straight from it would read `R` as a backlog raft. So `R` gets one commit between `D` and its first layer: the branch `<R>/base`, whose commit `tracker: base <R> on <D>` has `D`'s top layer tip as its parent and a tree that differs from it only in `R`'s own tracker folders: `R`'s raft folder and each member's folder, exactly as they are on `origin/main` (`git checkout origin/main -- <those folders>`, and any copy of the same ids at another state's path removed). `layergit.buildBase(raft)` makes it and pushes it (`--force-with-lease`); it is current while its parent is `D`'s top layer tip. The name does not parse as a layer (`stack.parse` wants `<R>/<n>/<issue>`), so `layersOf`, the trace and `done` never count it.

**`layergit.raftBase(raft): (string, string)`** is the one place that says what a raft's lowest layer sits on: the tip sha and the pull-request base. When `readyRecord(raft).on` is nil, or the raft it names is in `rafts/done/` on `origin/main`, it is `layergit.mainTip()` and `main`. Otherwise it is the tip of `<R>/base` and that branch name. Every site that takes `mainTip()` as a raft's base asks it instead: `layergit.startLayer` (layer 1's start point, pull-request base and the `belowBase` of layer 2), `cmd.finish`, `cmd.restack` (both uses), the trace's two walks (`traceProblems`), `cmd.done`'s walk, `workread`'s `stacked`, and `./zn stack`, which prints `built on <D> (<D's top layer branch>)` above the rows.

- **start**, for layer 1 of a raft with `On:`, calls `buildBase` first and cuts the layer from it. The worktree then reads `R` as active with its rewritten `check.sh` paths, as any readied raft's does, so `start`'s legacy backlog path and its "must be done first" rule are not met. **finish, the reviews, the trace** work as on any raft: the finish commit's parent is the base commit, so each diff is `R`'s own work and holds nothing of `D` or of the carry (E1, run).
- **done** refuses while the base has not landed: `<R> is built on <D>, which has not landed: ./zn done <D> first, then ./zn restack <R>`.
- **restack**, while `D` is unlanded and its top layer moved (a fix, a restack), rebuilds `<R>/base` on the new tip and rebases `R`'s layers onto it. Once `D` is done, `raftBase` says `main` and the same rebase (`stack.rebaseUpstream`: the parent of the layer's finish commit, here the base commit) carries only `R`'s own commit onto `main`, where `R`'s folders already are as the base commit had them (E1, run: one commit, no backlog copy, a file main added to the member's folder kept). It retargets layer 1's pull request to `main` (`gh pr edit <n> --base main`; a failed edit warns, as the other body edits do). As after any restack today, `work next` then asks again for whatever the rebase made stale (the trace's check, E7) before `done`.
- **stop**: `./zn stop <D>` is unchanged and leaves `R` as it is (its branches still exist); `R` then waits (`built on <D>, which has not landed`) until `D` is readied and landed again. `./zn stop <R>` is unchanged; the next `ready` writes a new record.
- A chain works: `R` on `D` on `E`. Each is landed in turn.

The prep of an issue with an unmet dependency is a prep worktree from `main` as always (a prep pull request holds only tracker files). Its prototypes and experiments, which need the dependency's code, run in a scratch worktree cut from the dependency's layer branch when it has one. **Guess (prep) G11.**

### 8. Edge cases

- No issue facts (`Input.issues == nil`, every existing caller and spec literal): the picks are today's, and `fix` is never offered.
- A session that cannot be named: nothing held is resumed, as today.
- A raft with `lands` and no guess, every member approved before `ready`, nothing changed: no `wait`; it lands as today.
- An approval made on the layer, then a new guess: the approval no longer holds and `wait` comes back, naming `guesses`.
- Two sessions of one person offered the same `rafting` or `draft`: the second's fold or `./zn status <id> preparing` is refused on `origin/main` as today, and it asks again. A resume is offered to one of them (the carriers file).
- `--on` a raft that is then stopped, or whose layers are rebuilt: covered in section 6.
- A dependency ring between two rafts: neither is in tier 1 and neither base has finished layers, so neither is offered; the reason lines name the dependency.
- A dependency on a closed issue never lands: the dependent is not picked, and its reason line says the person has to change `depends_on`.

### Scalability
`work next` with no raft named makes the git calls it makes today plus blobs in a batch it already runs (one `idea-review-001.md` per `new` raftless issue: 34 today), one small file read (the carriers), and one directory check per `preparing` issue (12 today). `blockOn` costs one more `readycheck.reason` per prepared backlog raft with an unmet outside dependency. The approval read of an active raft is two git calls, made only for a raft whose final review is approved (at most a few at a time). The picks are one pass over the issues and one over the rafts, with a dependency lookup by id. `raftplan.plan`'s dependency join is one pass over each candidate's `deps`. `readyRecord` is one `git log -1` on `origin/main`; `raftBase` adds, for a raft with `On:`, one `git cat-file -e` and one `rev-parse`.

### Maintainability
One reader per thing: `guesses.luau` for the file, `contract.build` for what an approval covers, `openlist` for the three kinds of bullet, `layergit.readyRecord` for how a raft was readied, `layergit.raftBase` for what a raft sits on, `work.decide` for the order (the skill carries none of it), `work.free` for whether held work may be resumed. A new step of the pipeline is one more numbered line in `work.decide` with its `why`. A new thing an approval must cover is one more optional part in `contract.build`. A new fact about a readying is one more trailer.

### Usability
New command line: `guess <issue-id> --step design|raft|build --open <text> --chose <text> --why <text>`, `guesses <issue-id|R-id> [--check]`, `ready <R-id|issue-id> [--on <R-id>]`, `work [<R-id>|<issue-id>]` and `work next [--released <n>] [<R-id>|<issue-id>]`. Each joins the usage text; `guesses` joins the read-only set; `guess` joins the commands refused in the main checkout. Every refusal above names the item and the rule. The person's whole part is: read `./zn guesses <R>` in the raft's worktree, run `./zn approve <id>` there for each issue named, and the next `./zn work next` lands the raft.
