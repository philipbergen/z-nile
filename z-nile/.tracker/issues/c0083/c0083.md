# c0083: Split harness and game specs into two suites

## Problem
Two kinds of spec live in one suite:
- **game specs**, for the code that ships (`src/`): `tests/unit`, `contract`, `integration`, `scenario`, `place`, `runtime` and the game issues' promoted acceptance specs (`f`/`d` ids);
- **harness specs**, for the tooling around it: the tracker CLI, the gate (`scripts/check.sh`), the spec runner and its guards, setup and the build. That's `tests/tooling` and most chores' promoted acceptance specs (c0001, c0008, c0053, c0058 and others).

Today `scripts/affected` sends any change under `scripts/` or `tests/lib/` to a full run of both. A tracker-only change runs every game spec. A game change runs every harness spec too, whenever the gate falls back to a full run. And `check.sh --full` (the Stop hook's and `done`'s gate) always runs both. The harness specs are the slow ones (fixture clones, nested runs, jailed runs), so game work pays for them on every gate.

The user wants (2026-10-04): "put all the build/tracker related tests in a separate test suite and set up so that it doesn't run unless files in the tracker/build harness is being changed", "and vice versa": the game suite doesn't run unless game files change.

(That is the capture, kept as written. Its paths are from before the repository was restructured; the section "Where each captured outcome stands on today's tree" maps every one to today's.)

## Non-goals
- Speeding up individual specs (c0062 covers the slow c0053 commands spec).
- Changing what CI on GitHub runs: GitHub only builds and publishes; testing is local. Today `.github/workflows/deploy.yml` publishes and runs no spec (c0172), `z-nile/setup.sh` runs `--full`, and neither changes here.
- The static stages (format, lint, types, build), which stay whole-repo; they're fast. (Today they are per project, `--project`, and `--suite` only chooses which projects.)

## Solution
- Decide each spec's suite by where it lives: for example `tests/harness/` (moved from `tests/tooling` and the chores' `tests/acceptance/c*`) and `tests/game/`, or a header tag. Promotion (`tracker.sh done`) must then route a chore's acceptance specs to the harness side and a feature's or defect's to the game side.
  - *Today:* a spec's suite is its project's home. `z-nile/tests/` is the harness (the tooling's `tests/tooling` and `tests/acceptance/c*`, c0120), and each game project's own `tests/` (`pickman/tests/`, `arcade/tests/`, `portal/`, `snake/`, `invaders/`, `asteroids/`) is the game. `./zn done` promotes an item's acceptance specs to its project's `<home>/tests/acceptance/<id>` (`projects.promotedDir`), whatever the item's type. **Guess (prep) G5**; see Open to the human.
- Map the paths each side owns: harness = `scripts/`, `tests/lib/` runner and guard files, `tracker/templates`, `.claude/skills`?, `rokit.toml`, hooks, `setup.sh`; game = `src/`, `default.project.json`, the game test libraries. Decide the shared paths (`tests/lib/t.luau`, `.luaurc`, `selene.toml`), where a change must still run both.
  - *Today:* harness = `z-nile/` (engine, `lib/`, `check.sh`, templates, skills, `tests/`, `affected.luau`), the root's `scripts/` forwarders and `zn`; game = a game home's `src/`, `tests/`, Rojo project files and `scripts/`. A path both read forces every project's static stages: `zn`, the root's `scripts/` and its `.luaurc`, `selene.toml`, `stylua.toml`, `rokit.toml` (`select.SHARED_FULL`); but no game spec can watch any of them (`watch.forSuite`), so for specs they are the harness's, as is every root file (`.models.toml`, `LICENSE`, `.github/`, a document). The runner, its libraries and the hooks are z-nile's (`z-nile/tests/run.luau`, `z-nile/tests/lib/`). **Guess (prep) G6**
- `scripts/affected` and `check.sh` select per suite (`--suite harness|game|all`, or by changed paths), including `--full`: "full" then means every spec of each affected suite. Something must still run both: decide when (a nightly or manual `--all`, `done` of a raft that touched both, a change to shared paths).
  - *Today:* `z-nile/affected` and `z-nile/check.sh`. Selection by changed paths exists (the watch map). `--suite` and a `--full` per affected suite do not (see the table).
- Watch the interactions: `done` runs the full gate after promotion (R0026 c0074); the Stop hook's gate; raft `check.sh` RC0 lines (`check.sh --full`); the gate spec scan (repo-fence), which reads every spec file; the test-selector graph.
  - *Today:* `./zn done` runs `--affected` (c0239), the Stop hook no longer exists, a raft's RC0 is `--project <project> --affected` (the raft template), the fence scans every home whatever the selection, and the require graph is replaced by the watch map (c0165, c0180). One line each in the table.

### Modules and signatures
```
z-nile/lib/suites.luau   (new, pure)
  type Suite = "harness" | "game"
  suites.GAME: { string }                                -- arcade, pickman, portal, snake, invaders, asteroids
  suites.of(project: string): Suite                      -- game when listed, else harness
  suites.projects(names: { string }, which: string): { string }  -- harness | game | all, registry order
  suites.changed(rules: select.Rules, changed: { string }): { Suite }   -- by location, sorted; none for a tracker document
  suites.crossings(spec: string, paths: { string }): { string }          -- watch.forSuite's drops
z-nile/lib/context.luau      -- build adds a problem per crossing (G4)
z-nile/affected.luau         -- --suite <harness|game|all|changed>: project names, one per line; 2 on a bad value
z-nile/check.sh              -- --suite harness|game|all|changed
z-nile/skills/zz-test/SKILL.md -- command row, "## Suites"
```
Data flow: `check.sh --suite <s>` asks `lune run z-nile/affected -- --suite <s> [--base REF]`, which for `changed` reads the changed paths (`changes.files(base)`), the registry and `select.rules`, calls `suites.changed` and prints `suites.projects` of the result. `check.sh` keeps two lists. `wanted` is the static stages' projects (as today: `--project`, or the static narrowing `affected --static`); `spec_wanted` is the spec stage's, with `spec_narrow` set when the spec stage is narrowed (the stage's existing `picked` filter is joined by `spec_picked`). `harness` and `game` set both to that suite's projects in every mode. `changed` sets `spec_wanted` to the touched suites' projects and narrows the spec stage only in a `--full` run; the static stages then run today's narrowing plus those projects, so a root config still reruns every project's static stages. In `--affected` and `--static`, `changed` changes nothing: since c0165 and d0297 the affected loop runs every project's watch-map selection and project narrowing lives on the static stages, and that stays. `all` is parsed away (`suite` stays empty), so it is the bare gate in every mode. A bare gate is untouched.

Pure/adapter split (zz-arch): `suites.luau` is pure over plain tables (`select.Rules`, name lists) and only requires `select` and `watch`, both pure; `context.luau` and `affected.luau` are the adapters that read files; `check.sh` is the shell edge.

Rules:
1. A project is game when `suites.GAME` names it, else harness: a new tooling project is never skipped as a game. **Guess (prep) G2**
2. A path's suite is its location, the partition `watch.forSuite` already applies to watch lists: under a game home the game's; under z-nile, or under no home (a root file: `zn`, the root's `scripts/`, `.luaurc`, `.models.toml`, `.github/`, `LICENSE`, `AGENTS.md`), the harness's; under a project root (a tracker document) none, because it selects no spec (**Guess (prep) G3**). The old places c0120 emptied are outside every home, so they are the harness's (its old-roots spec fails on them). A change is the union of its paths' suites. Whether a root file should also touch the game suite is **Guess (prep) G6**.
3. A spec's watch list holds only paths of its own suite (`watch.forSuite`); one that does not fails `watch-check`, which every gate that runs specs already runs, naming the spec and the path. **Guess (prep) G4**
4. `--suite` is `harness`, `game`, `all` or `changed`; any other value, no value, `--project` beside it, or `--slow` beside it exits 2 before a tool runs. `--suite all` is the bare gate in every mode. `harness` and `game` narrow the static stages and the specs, in `--plan`, `--affected`, `--full` and `--static`. `--full --suite changed` runs every fast-tier spec of the projects of each touched suite, with today's static stages plus those projects', and nothing when no suite is touched and the static narrowing names no project (it prints `no project changed` and passes, as the static narrowing does). `--affected` and `--static` with `changed` are the bare gate.
5. A gate with no `--suite` is exactly today's: `--full` every project, `--affected` every project's selection.
6. Merging's clean-clone gate stays the bare `--full`; no skill sends a merge to `--suite changed`. **Guess (prep) G1**

No Roblox code, no player behaviour changes, no `src/` change.

### Scalability
`suites.changed` is linear in changed paths times registered homes (a handful); `suites.crossings` is linear in a watch list, run once per spec in `context.build` (732 lists, measured `watch-check` unchanged at about a second). `--suite` removes work: `--suite game --full` skips z-nile's specs, the slow ones. A new game project joins by one name in `suites.GAME` (and `watch.GAME_HOME`, which AC2 keeps equal).
### Maintainability
One module names the suites; the second list (`watch.GAME_HOME`) cannot drift because AC2 compares them for every registered project, and a project in neither is harness by rule 1. `--suite` reuses `wanted` and `narrow`, no new state in `check.sh`. Documentation is one section.
### Usability
`z-nile/check.sh --suite game --affected` while working on a game, `--suite harness` for the tooling, `--full --suite changed` for a full run that skips the suite no file of the change touches. `--plan` shows what a suite runs. A bad value says what the four are.
