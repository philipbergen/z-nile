### F1 [high] `--suite changed` gives no suite to root files the harness specs watch, so it skips specs the bare gate runs
Where: c0083.md Design, Rules 2 and 4, and the data flow paragraph; prototype.patch `suites.changed`; suites.spec.luau:98 (`AGENTS.md`, `SETUP.md` give `{}`); prototype.patch:145 (the spec loop narrows `--affected` when a suite is named)
Evidence: `watch.forSuite` gives every path outside a home to the tooling's specs (`home == ""` is kept for a tooling spec). So the real tree has harness specs that watch root files. `lune run z-nile/affected -- .models.toml` prints 19 z-nile specs, `.github/workflows/deploy.yml` 8, `LICENSE` 5 and `NOTICE` 5. Run against the real registry, the prototype's `suites.changed` returns `{}` for each of these four paths: they are not forced, not under a tracker root and not under a home. Over all 732 real watch lists, 37 entries name a path whose watching spec's suite is missing from `suites.changed({path})`. So for a branch that changes only `.models.toml`, `check.sh --affected --suite changed` gets no project, prints `no project changed` and passes, while the bare `--affected` runs 19 harness specs. `--full --suite changed` runs nothing at all. A mixed change (`.models.toml` plus `pickman/src/x.luau`) loses the 19 harness specs the same way. Behind this is a second change nobody stated. Since #293 ("the gate runs every spec the map lists"), the affected spec loop never narrows by project (check.sh's comment: "Project narrowing stays on the static stages above"). Prototype line 145 narrows it whenever `--suite` is set. The Suites text the design adds also says "the harness keeps tooling and root paths", which contradicts Rule 2.
Critique: `suites.changed` decides by location and the forcing table. The watch map decides by `watch.forSuite`. The two partitions disagree for every root file, and AC1 pins the disagreement as correct. The tempting fix is to add `.models.toml` and `.github/` to a list. That leaves `LICENSE`, `NOTICE` and the next root file a harness spec watches still uncovered.
Consequences: if a path under no home and no project root touches the harness (the rule `forSuite` already applies), then an `AGENTS.md` or `SETUP.md` change also names the harness. `--full --suite changed` then runs z-nile's whole fast tier for a documentation edit, and `--affected --suite changed` runs z-nile's selection, which is empty for those files, so nothing extra. G3 (tracker documents touch nothing) is unchanged. The other option derives a root path's suite from the specs the watch map selects for it. That makes a `--full` decision depend on the very map whose gaps the full run exists to catch.
Recommendation: Rule 2 gains "a path under no home and no project root touches the harness (`watch.forSuite` gives the root to the tooling's specs)". Flip suites.spec:98 to `{ "harness" }` and add `.models.toml`, `.github/workflows/deploy.yml` and `LICENSE` to it. Add an invariant case on the real tree, run from the top as AC5's real-tree case is: for every spec in `context.build`'s watches and every path in its list, `suites.changed(rules, { path })` contains `suites.of(<the spec's project>)`. It fails on the prototype today (37 entries). Add a gate.spec AC3 assertion: `affected --suite changed .models.toml` prints `z-nile`. In `--affected`, keep #293's rule for `changed`: the spec loop narrows only for an explicit `harness` or `game`. Add an AC4 stub case where `--suite changed` answers `pickman` while `affected --project z-nile` returns a spec, and the z-nile spec still runs. Add Rules and mutants rows: "a root path touches no suite" and "`--suite changed` narrows an affected run's specs".
