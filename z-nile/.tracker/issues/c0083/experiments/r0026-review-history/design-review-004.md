### F1 [high] The full runs that dominate a raft still run both suites, so the user's "doesn't run unless …" isn't delivered where most gating happens, and no user decision covers that
Where: c0083 Solution ("`--full` still runs everything. `done`'s gate (c0074) and the raft's RC0 use it"); Scalability; execute-raft Phases 0, 3, 5 and 6; tracker skill, Merging step 2; review skill, Code mode item 1.

For a game-only raft, the skills still call `scripts/check.sh --full` at least seven times: execute-raft Phase 0 ("Confirm `scripts/check.sh --full` passes"), Phase 3 steps 2 and 3 (the double-check and the gate-speed record), the reviewer's Code mode item 1, Phase 5's rerun after merging `origin/main`, RC0 (`check "RC0: repo gate passes (full)" scripts/check.sh --full`, in every raft's `check.sh`), c0074's new full gate inside `done`, and the merge condition "`scripts/check.sh --full` on the final head". With selection everywhere, F3's and F4's misses land broken code that nobody ever runs. Keeping `--full` everywhere quietly leaves the user's pain as it is.

Its correctness then rests wholly on the selector, so F3 and F4 must be fixed first. c0074's spec pins `args: --full` for `done`'s gate (`done-gate.spec.luau` lines 172 and 209), so changing `done` would mean editing a settled member's sequestered spec. Recommendation: put the question to the user before execution and record the answer, quoted, in the raft's binding decisions. Suggested options:
- (a) one full run per raft, `done`'s (c0074, unchanged). Phase 0, Phase 3, the reviewer's run, Phase 5's rerun and RC0 use a new `check.sh --branch` (suite selection over `origin/main...HEAD` plus the working tree). The merge condition reuses `done`'s run when the head is unchanged.
- (b) `--full` everywhere, as designed (accepting that the request applies only to the Stop hook and manual runs).

If the answer is (a): add `--branch` to c0083's Design, Touched modules (execute-raft, tracker, review skills, the RC0 generator in `scripts/tracker/`) and Test plan, with cases that `--branch` selects the harness suite for a branch touching only `scripts/` and no harness spec for a branch touching only `src/`. ### F2 [high] The Stop hook never runs for a harness-only change, so harness edits get no automatic gate at all, and the design's claims about the hook are wrong
Where: `scripts/hooks/stop.sh` line 11 (`grep -E '^(src|tests)/'`); c0083 Problem ("`check.sh --full` (the Stop hook's and `done`'s gate)"), E4 ("The Stop hook runs `check.sh --affected`, which benefits"), Usability ("The Stop hook's gate gets faster on single-side work, with no new flag"); testing skill, Hooks ("On stop: `scripts/check.sh --affected` runs if `src/` or `tests/` changed").
Evidence: the hook runs `check.sh --affected`, not `--full`, and only when a changed path starts with `src/` or `tests/`. A session that edits only `scripts/tracker/main.luau`, a skill under `.claude/`, or `tracker/templates/prompt.md` gets `changed` empty, and the hook exits 0 with nothing run. The prototype's selector prints 81 specs for `scripts/hooks/stop.sh` and for `scripts/tracker/main.luau`, but nothing ever asks it. So the half of the request that says the harness suite runs when harness files change isn't met by any automatic gate. c0083 doesn't list `stop.sh` as Touched.
Critique: the tempting fix is to widen the regex to `^(src|tests|scripts|\.claude|tracker/templates)/`. That adds a second, hand-kept copy of `suites.HARNESS`/`GAME`/`SHARED`, which drifts the first time a pattern is added (F4 adds several).
Consequences: the hook would then run the whole harness suite, with fixture clones, nested runs and jailed runs, after every turn that touches `scripts/`. The hook's timeout is 300 s (`.claude/settings.json`), and nobody has measured the harness suite against it: if it's longer, every harness turn ends in a timeout. Static stages also run for `.claude/`-only changes, which costs a little.
Recommendation:
- `stop.sh` decides by the selector itself: run the gate when `lune run scripts/affected` prints anything (a list or `ALL`), or when a changed path is Luau (static stages), and exit 0 otherwise. That keeps one source of truth.
- Add `scripts/hooks/stop.sh` to Touched modules, and a spec case in a fixture copy of the hook with a stub `scripts/check.sh` that logs its call. It checks that a change to only `scripts/x.luau` calls the gate, and a change to only `tracker/issues/x/x.md` doesn't.
- Add an experiment with a pass/fail question: does `check.sh --suite harness` finish under 300 s on the prep machine? If not, the fallback (raise the timeout, or have the hook run the static stages plus the harness specs that depend on the change by require) is a decision recorded in the doc.
- Correct the Problem, E4 and Usability text, and the testing skill's Hooks line (AC5 should grep for its new wording).
