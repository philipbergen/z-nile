# guesses
- G1 (design, 2026-11-20): When a game pull request is merged, the clean-clone check that runs every spec of every project (`check.sh --full`) also runs the tooling's specs even though only game files changed. The capture asked that 'full' mean every spec of each affected suite, and a later user decision (2026-10-26, c0239: 'The full gate at merge runs all for real so we can find out if dependency graph has gaps') asked that the merge's full gate run everything. Example: a PR that edits only pickman/src/... : narrowed, the merge runs the six game projects and skips z-nile's specs; as decided on 2026-10-26, it runs all seven. Chose: Build the narrowed full as an opt-in flag (`check.sh --full --suite changed`) and leave Merging's clean-clone gate as the bare `--full` (everything), so the 2026-10-26 decision stands and the narrow full exists for anyone who wants it. A spec pins that Merging stays bare. Why: Two user statements disagree and neither may be dropped. The merge's full gate exists to catch watch-map gaps in either direction, and narrowing it would hide exactly a game change that breaks a tooling spec. If the user prefers the narrowed merge, Merging's one sentence changes to `--full --suite changed --base <merge-base>` and spec AC10 is flipped; nothing else changes. Under this guess no gate step runs differently from today: the saving the capture asks for comes only from the other option.
- G2 (design, 2026-11-20): A game project and the tooling are two suites, but the registry only lists projects. Which suite is a project that no list names, for example the omarchy board app another issue (c0257) is adding? Example: z-nile-omarchy is neither pickman nor z-nile. Chose: A project named in suites.luau's game list (arcade, pickman, portal, snake, invaders, asteroids) is the game suite; every other project, including one added later, is the harness suite. A spec checks that this list and watch.forSuite's own list agree for every registered project, so they cannot drift. Why: If a new tooling-like project were taken for a game, its changes would run game suites and its own specs would be skipped on a tooling change: the harness default is the safe side. The other option is to default to game, which hides a new tooling project from tooling gates.
- G3 (design, 2026-11-20): Does a change to a tracker document (an issue file, a spend row) touch a suite? Example: the commit of this very prep changes only z-nile/.tracker/... files. Under `--suite changed` should that run the harness suite? Chose: No: a path under a project's tracker root touches no suite, because the watch map selects no spec for it (it is the same rule as today's affected selection). A tracker document beside a code change counts only the code's suite. Why: Today's gate selects no spec for a tracker document and a prep or capture merge should not run a whole suite. The other option would count a tracker document as its project's suite, which would run every spec of z-nile for each tracker-only pull request.
- G4 (design, 2026-11-20): A watch file (the list of paths that make a spec run) may name a path from the other suite, by a hand edit or a merge. Today `./zn finish` drops such paths when it writes a list, but nothing refuses one that is already there. Example: a tooling spec's list gains pickman/src/Game.luau, so every game edit runs a tooling spec. Chose: The gate refuses it: `lune run z-nile/watch-check` (already run in every gate that runs specs) fails naming the spec and the path, like it does for a path that does not exist. The real tree has 732 lists and none crosses today. Why: A silent leak would break the captured rule that one suite does not run for the other's change without anyone noticing. The other option is to only drop the paths when the map is read, which hides the bad list instead of fixing it.
- G5 (design, 2026-11-20): The capture says each spec's suite is decided by where it lives (for example tests/harness/ and tests/game/, or a header tag) and that promotion sends a chore's acceptance specs to the harness side and a feature's or defect's to the game side. Since then the repository was split into project homes: z-nile/tests/ is the harness suite and each game project's tests/ the game suite, and promotion (./zn done) sends an item's specs to its own project's home. Example: a chore for pickman promotes into pickman/tests/acceptance, a defect for z-nile into z-nile/tests/acceptance. Chose: Keep today's layout as the answer: a spec's suite is its project's home, promotion routes by the item's project (pinned by a spec), and no tests/harness or tests/game folder and no header tag is added. Why: Routing by item type would send a game chore's specs to the tooling suite, which is the wrong suite for them; the project home already carries the harness/game line. The other option is to add the literal folders, which moves ~700 specs and every watch file for no behaviour the home does not already give. This is on the open list too, because the capture named the folders as examples and a person should confirm.
- G6 (design, 2026-11-20): Which suite does a change to a file that belongs to no project count as: the root's zn command, the root's scripts/ and hooks, rokit.toml, .luaurc, selene.toml, .models.toml, LICENSE, a document such as AGENTS.md? The capture listed scripts/, hooks, rokit.toml and setup.sh as the harness's and named .luaurc and selene.toml as candidates for 'both'. Example: you edit scripts/hooks/pre-bash.sh; should 'full for the suites this change touches' (check.sh --full --suite changed) also run every game project's specs? Chose: The harness only (a path outside every game home and every project root is the tooling's), because the specs that watch those files are all tooling specs today (lune run z-nile/affected on .luaurc, selene.toml, zn, .models.toml or the hooks selects only z-nile specs) and no game spec can watch them. The static stages (format, lint, types, builds) keep today's rule, so a root config such as selene.toml still reruns every project's static checks, which --suite changed leaves alone. Why: This is what the capture's 'the game suite doesn't run unless game files change' asks for. The other option treats every shared path as touching both suites (every project's full specs for a hook edit): it matches how the static stages already treat zn and the root configs, but it runs the game suite for files no game spec reads, which is the waste the capture wants gone. The cost of my choice is that check.sh keeps two project lists under --suite changed (static stages and specs), and a change that really did need the game specs for a root file (none exists today) would be caught at the merge's full gate or the net, not earlier.
