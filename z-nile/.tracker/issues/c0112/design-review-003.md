### F1 [medium] (repeat of design-review-002 F7) AC3 and AC6 take their base from the local `origin/main`, so moving that ref makes both pass with nothing compared
Where: check.sh `ac3()` (`git merge-base HEAD origin/main`, then `HEAD == base` passes) and `ac6()` (`git diff … origin/main...HEAD`); design-refute-002 F7.
Evidence: on the clone3 copy (scratch branch `rev3`, one commit above e0b266e7), I turned `R0012 design-review-001 F4: zz-test/no-vacuous-pass` into a one-off and committed. ac3's body, run verbatim, printed `merge base e0b266e7… / lesson zz-test/no-vacuous-pass lost the source: R0012 design-review-001 F4` and exited 1. After `git update-ref refs/remotes/origin/main HEAD` it printed `HEAD is on origin/main (merged, or no commit yet): nothing to compare` and exited 0. With the same ref moved, ac6's three-dot diff is empty, so every edited review passes too. Round 2 recommended taking main's tip from `git ls-remote origin refs/heads/main`. The refute adopted the merge base but did not answer that part. The lesson the design cites asks "Can the author make the base equal HEAD?" and answers it the same way.
Critique: this is the third round on AC3's reference: a frozen list, then main's tip, now a local ref. Each fix moved the reference without asking who controls it. `done` never fetches (main.luau `cmd.done` only runs `reviewProblem` and `runCheck`), so whatever `refs/remotes/origin/main` says when `done` runs is what AC3 and AC6 judge against.
Consequences: reading the remote makes `done` need the network (it already pushes, so this costs nothing new). The tip must also be present locally (fetched) before `merge-base` can use it. A base taken from the remote can still be fed by a swapped origin URL (`remote set-url`), so the check prints the URL it resolved, as c0115's check.sh does. The empty range stays a pass, but only when HEAD is an ancestor of the remote tip, which means the branch has landed.
Recommendation: in check.sh, compute one base for both criteria: `tip=$(git ls-remote origin refs/heads/main | cut -f1)`. It is red when ls-remote fails or the tip is not a local object, and the output prints `git ls-remote --get-url origin`. Then `base=$(git merge-base HEAD "$tip")`. AC3 archives `$base`. AC6 diffs `"$base" HEAD` with the same `--diff-filter=DMRT`. Take the code from c0115's `trusted-base` (`git grep -l ls-remote -- '*/check.sh'` lists `z-nile/.tracker/issues/done/c0115/check.sh` and `active/c0134/check.sh`). Add a `run` row: a lost source plus `git update-ref refs/remotes/origin/main HEAD` stays red, in a fixture whose origin is a local bare repository under `$TMPDIR`.
Lesson: z-design/exact-checks-compare-against-the-merge-base

### F5 [medium] The brief makes every one-off `(erred none)`, which contradicts c0136's rule and JC1's own pass rule for a mistake too specific for a lesson
Where: worker-brief.md line 13 ("`erred none` is only for … a refuted finding, a clarity note"), line 31 ("a typo, a number or name specific to that one item … A one-off is always `(erred none)`") and line 6 (the Hard rules' output list omits `when-change.txt`, which round 2 F4 asked to align); The method 3 ("A draft that restates one finding … is dropped and its lines become one-offs"); JC1 (a) and stratum 4.
Evidence: c0136 "The rule" 2: "`erred none` (a one-off only) is a finding that points out no mistake". Rule 3: "A refuted finding keeps the reviewer's step: `(erred z-design): one-off: refuted, <why>`". A typo in a design document, or a game-specific number a design got wrong, is a mistake z-design made, too specific for a lesson. c0136 writes that as `(erred z-design): one-off: …`, and the brief writes it as `(erred none)`. So does every line of a draft the merge pass drops for "restating one finding". JC1 (a) passes an entry only when "`erred` names the step that made the mistake", so a sampled one-off written by the brief fails stratum 4, and the stratum is redone. The design says the brief restates c0136 "in their words" and that step 1 fixes differences in the brief. This difference is in the brief and in the Design's own merge-pass text.
Critique: a step attribution is the outcome c0136 hands to c0112 ("c0112 attributes every past entry"). One-offs are 9% of entries in the c0111 era, so about 170 lines of 1937 would carry the wrong step, by instruction.
Consequences: workers then name a step on one-offs, which raises the share of non-`none` lines with no lesson. `check` allows that (c0136's form), and JC1 (a) already judges it.
Recommendation: in the brief, a one-off names the step that erred whenever the finding points out a mistake (`(erred z-design): one-off: <reason>`). `(erred none)` is only for a finding that points out none: a taste call, or a disagreement with no mistake on either side. A refuted finding that was the reviewer's slip is `(erred zz-review)`. Apply the same rule in The method 3 for a dropped draft's lines. Add `when-change.txt` to the Hard rules' output list. JC1 stratum 4 judges the step as well as the one-off.
