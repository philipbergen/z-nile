### F1 [high] "sources-kept must pass for both merge parents" is red for a lesson merge that keeps every source, so c0112's own c0181 procedure can never pass it, and the pinned zz-rules rule blocks c0181 if c0112 lands first
Where: docs.spec (the zz-rules sentence: "Then `lune run z-nile/tests/acceptance/c0112/sources-kept.luau -- <git archive of each merge parent> .` must pass for both parents"); Existing work (b) ("c0112's own merges of `origin/main` (the straggler pass, step 6, the c0181 procedure) run `sources-kept.luau` against both merge parents"); Existing work (d) ("if c0181 arrived, apply its id rename map … to this branch's ledgers and drafts" and "If c0112 lands first, nothing changes here"); sources-kept.luau lines 69-73 (`lesson {id} is gone`, then `continue`).
Evidence: c0181's prep (c0181.md line 34: "a new lesson that overlaps an old one is merged into it, keeping every source id"; line 125: `lesson-merge` "rewrites every harvest.md of every item … through `lessons.renameIds(text, {[from] = into})`", "deletes the `from` files", and verifies that the sources of `into` after the merge are the union). I made that merge in a copy of the c0136 tree. I merged `zz-test/narrowing-pins-the-whole-file` into `zz-test/narrowing-keeps-each-members-check`: its 3 ledgers (R0045, c0150, c0153) were rewritten, deduplicated, and the `from` file deleted. `./zn lessons --check` on the result: `156 lessons, 1071 harvest entries, ok`. Then `lune run sources-kept.luau -- <tree before> <tree after>` printed `lesson zz-test/narrowing-pins-the-whole-file is gone` and exited 1 (with the c0136 engine). So:
(1) In c0112's "likely case" (c0181 lands while the raft runs), the c0112 parent of the merge still has every `from` lesson, with the sources the waves added to it. The procedure in (d) removes them, and (b) then requires the check against that parent to pass. It cannot. (d)'s "rerun `backfill-check.sh` over every earlier wave's items" fails the same way, because the workers' `<OUT>/harvest` files still name the `from` ids, and (d) renames "ledgers and drafts", not those files.
(2) If c0112 lands first, the sentence is on main. c0181's branch merges main, and its idempotent `lesson-merge` folds c0112's new lessons ("rewrites a late reference"). The check against main's parent is then red for every lesson it merged, so "nothing changes here" is false. The same holds for any later branch that consolidates, which c0181 makes routine.
Critique: this is the fourth round on the conflict rule (round 1 F8, round 2 F3, round 3 F2). Round 3 moved it from wording to a property, which is right, but the property was written as "no lesson id disappears". The invariant that matters is "no source disappears". c0181 deletes lesson ids on purpose and keeps their sources. The file's own header also still says "run by check.sh only (a promoted spec would outlive the migration)", while the docs sentence makes it a permanent tool that no promoted spec pins.
Consequences: the tempting fix is "skip the check when c0181 is involved", which reopens round 3's same-skill loss. A merge allowance can become a free pass to delete a lesson unless it is verified, not claimed. AC3 itself does not need the allowance: after c0112 merges a main that holds c0181, its merge base already lacks the `from` lessons. An allowance must therefore never reach AC3, which `check.sh` runs without options and the executor cannot edit.
Recommendation: question the mechanism, so the check states the source invariant. Give `sources-kept.luau` a mode `--merges` (decided now, while the file can still change): a lesson gone from the current tree is kept when exactly one current lesson of the same skill holds every source the base gave it, and that lesson is named in the message (`merged into <id>`). AC3 keeps calling it without the mode (strict, since c0112 "never renames a lesson"). The docs sentence, the merge pass and (b)'s per-parent runs use `--merges`. In (d), add the workers' `<OUT>/harvest` files to what the rename map rewrites before the validator reruns. Fix the file's header to say it is also the permanent conflict check. `run` rows on a copy: the merge above passes with `--merges` and fails without it; a deleted lesson whose sources went to two lessons is red; a survivor in another skill is red; one source of `from` missing from the survivor is red. Pin the mode with a promoted spec case, not a check.sh line, because the rule must outlive `done`: a `sources-kept.spec.luau` under `acceptance/` runs the script on two small trees it writes under `.cache`, and asserts the strict and `--merges` outcomes above. Put the c0181 case to c0181's lead with the order question (d) already asks.

### F2 [medium] (repeat of design-review-003 F3) batches.sh still reads an engine crash as "nothing to do": lune exits 1 on an uncaught error, the same status as "listed something"
Where: experiments/batches.sh lines 25-35 (`((rc <= 1))` is a result; `todo` keeps only lines whose first word is an item id; an empty `todo` prints `nothing to do` and exits 0); design-refute-003 F3 ("exit 0/1 of the lists are results, anything else an error"); Rules row "the hold fails closed" (run with "an engine without `--unattributed`", which exits 2).

### F3 [medium] held.sh holds the raft's own items: its own worktree branch is "a recently committed worktree branch that changes their harvest.md", so the one-off audit's items are all held by the raft itself
Where: experiments/held.sh lines 35-41 (every `git worktree list` branch with a commit in 14 days, the raft's own included); The method 1 ("the lead reruns it right before each wave"; "a wave takes only items that are not held") and 4(a) (the one-off audit, "batches of the items that hold them", "validates them like a wave's"); step 4(c) and step 6 (the straggler pass reruns `batches.sh`).
Evidence: on my copy I made a branch `raft-c0112` with one commit that changes `pickman/.tracker/issues/done/c0150/harvest.md`, checked it out in a worktree, and ran `held.sh <that worktree>` (gh stubbed empty). It printed `c0150 branch raft-c0112` among `held: 11`. After wave 1, every item the raft has harvested is held by the raft. The one-off audit only touches items whose one-offs the waves wrote, so a lead who follows "rerun it right before each wave" finds every audit item held. The rule then says those items wait for "the last wave", which has already run, or need an override "it can show is stale", which this hold is not. In the straggler pass, an item c0112 already harvested that has a new review on main is likewise `--open`, not `--settled`.
Critique: the hold exists to keep two writers off one ledger, and the raft is the writer the hold protects, not a competitor.
Consequences: run from the main checkout, the script would not know which branch is "self". Since the design always runs it in the raft's worktree, the branch checked out there is the natural self.
Recommendation: held.sh skips the branch checked out at `<repo>` (`git -C <repo> branch --show-current`; a detached HEAD skips nothing and says so) and prints `self: <branch>`. State in The method 1 that the raft's own commits never hold an item. Run rows: the raft's branch changing a ledger does not hold it; another worktree's recent branch changing a ledger does.
