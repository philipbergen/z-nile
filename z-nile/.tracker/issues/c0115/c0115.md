# c0115: Rename skills and write the z-nile README

## Problem
The skills are named for the old steps (`make-issue`, `ticket-prep`, `ready-raft`, `launch-raft`, `execute-raft`, `stop-raft`, `review`, `tracker`, `architecture`, `testing`, `metrics`). An agent cannot see which names are the pipeline and which are only called from inside a step. The one-page map, where it exists, describes that old flow.

Pipeline skills become `z-ticket`, `z-design`, `z-raft`, `z-ready`, `z-run`, and `z-stop`. Skills called only from inside a step become `zz-review`, `zz-rules`, `zz-arch`, `zz-test`, and `zz-stats`. The `zz-` prefix is reserved: a game does not add a skill under it. `z-nile/README.md` opens with the picture of the tracker, the skills, the dispatcher, `.models.toml`, and the board.

Decided with the user (2026-10-20):
- z-nile's skills live in `z-nile/skills/`. A project's own skills live in `<project>/skills/` (pickman: its architecture rules and the Roblox half of testing). The harness finds them through `.claude/skills/<name>` links that a tracker command generates.
- The old names are removed. This is a rename, not a copy.

Decided with the user (2026-10-20), from the programme review:
- "z-nile owns zz-arch/zz-test": `zz-arch` holds z-nile's tooling architecture rules (new, from today's tooling half), and `zz-test` holds the gate, `check.sh`, sequestration and the fence. Pickman's halves get their own non-`zz` names in `pickman/skills/` (for example `pickman-arch`, `pickman-test`).
- "Committed relative symlinks": `.claude/skills/<name>` are generated relative symlinks, committed and checked in the gate (`zn skills --check`). Every tool, spec and Touched path uses the real `z-nile/skills/…` path.
- "Delete it": `.claude/README.md` is deleted, and the links to it in `AGENTS.md` and `SETUP.md` change.
- "c0115 writes them": c0115 writes short feature, defect and chore design checklists where `z-design` reads them, and the README names them.
- c0115 also moves the skill sources into `z-nile/skills/` (c0114's decision).

### 4. Skill folders, the links and `./zn skills`
Folders: z-nile's skills are `z-nile/skills/<name>/SKILL.md`. A project's are `<project name>/skills/<name>/SKILL.md`, by its name in `z-nile/projects.toml` (pickman's: `pickman/skills/`). The folder is the project's home, the folder that holds its root (`projects.folderOf`, c0120's G16: there is no `home` key), which for a registry root `<name>/.tracker` is `<name>/`: z-nile's skills are in `z-nile/skills/`, pickman's in `pickman/skills/`.

Links (the decided "committed relative symlinks"): `.claude/skills/<name>` is a symlink, git mode 120000, whose target is `../../<folder>/<name>`, for example `../../z-nile/skills/zz-test`. `.claude/skills/` holds the links and nothing else. E1 shows that Claude Code and Cursor load a committed link from a fresh `git worktree add`.

`z-nile/engine/skills.luau` is the one reader of the skill folders (lesson zz-arch/one-reader-per-format):
```lua
export type Folder = { project: string, path: string }      -- "z-nile", "z-nile/skills"
export type Entry = { name: string, text: string? }         -- a folder entry and its SKILL.md text (nil: none)
export type Found = { folder: Folder, entries: { Entry } }
export type Skill = { name: string, project: string, dir: string } -- dir "z-nile/skills/zz-test"
export type Present = { [string]: string | false }          -- .claude/skills: name -> link target, false: not a link
skills.LINKS = ".claude/skills"
skills.ZNILE = "z-nile"
skills.INLINED = { "zz-execute", "zz-rules", "zz-arch", "zz-test", "zz-review" }
skills.folders(reg): { Folder }           -- z-nile's first, even when the registry doesn't list it; then each project's
skills.frontName(text): string?           -- the frontmatter's name:
skills.plan(found): ({ Skill }, { string }) -- pure: the skills, sorted by name, and every problem
skills.target(s): string                  -- "../../" .. s.dir
skills.diff(list, present): { string }    -- pure: what is wrong with .claude/skills; {} when exact
skills.load(root): ({ Found }, Present)   -- reads the folders of root's registry (a missing or bad one refuses, c0114) and readlink
skills.trackedNonLinks(root): { string }  -- tracked paths under .claude/skills whose mode isn't 120000
skills.apply(root, list, present): ({ string }, { string }) -- writes the links; refuses (writes nothing) on a non-link
```
`plan`'s rules, each a problem naming the folder:
- an entry without `SKILL.md` (`<dir>: no SKILL.md`);
- a `name:` that isn't the folder's name;
- a z-nile skill not named `z-…` or `zz-…`;
- a project skill named `z-…` or `zz-…` ("the z- and zz- prefixes are z-nile's"), even in a project named `z` or `zz`;
- a project skill not named `<project>-…`;
- one name in two folders, naming both.

A skill with a problem is left out.

`diff`'s problems, one per entry:
- `<path>: missing (a link to <target>)`;
- `<path>: links to <have>, not <target>` (a wrong or absolute target);
- `<path>: not a link …` (a real folder or file);
- `<path>: no skill folder of that name (remove it)` (an extra link, or a dangling one).

`skills.linkedParents(root)` (readlink on `.claude` and `.claude/skills`; `fs.isDir` follows links, so it can't tell) reports `<path>: a link (to <target>), not a folder of this repository; make it a real folder` for either one. `skills.trackedNonLinks` reports, from `git ls-files -s -- .claude .claude/skills`: `.claude` or `.claude/skills` tracked itself, in any mode (`<path>: tracked itself (mode <m>); it must be a real folder`); a path under `.claude/skills/` in a mode other than 120000 (`<path>: tracked as a file (mode <m>), not a link`); and a link deeper than `.claude/skills/<name>`.

`./zn skills [--check]` (in `main.luau`):
- a plan problem fails either form, writes nothing, and prints the problems;
- a linked `.claude` or `.claude/skills` fails either form and writes nothing: `--check` reports it in place of the `diff` problems (which would be read from the link's target), and the write mode refuses before `apply`, which refuses again by itself. Nothing outside the repository is ever removed or written (lesson zz-arch/guard-no-is-explicit: the guard acts only on two real folders);
- `--check` prints `skills: <n> skills, one link each, ok`, or fails with every `diff` problem and every tracked-path problem above, ending "run ./zn skills in a worktree to fix the links". It only reads, so it may run in the main checkout;
- without `--check`, it refuses in the main checkout of a repository with an origin (`refuseInMainCheckout`, like `new`). It also refuses, writing nothing, while any entry of `.claude/skills` is not a link. Otherwise it removes each wrong or extra link (`rm -f`, never recursive), makes each missing one (`ln -s <target>`), and prints `linked …` and `removed …` lines, then `skills: <n> skills linked`. A second run prints no `linked` or `removed` line.

AC2 runs c0115's own `--check` and changed `--plan` in a plain clone under `.cache/c0115-ac2`, not in the checkout (lesson zz-test/new-commands-run-in-a-copy: a wrong `--check` that writes would otherwise write the raft's checkout and pass on what it wrote). The clone checks the committed links, as CI does.

The gate (`z-nile/check.sh`) adds one static stage beside the builds, exactly `[[ -d z-nile/skills ]] && par_start "skills (./zn skills --check)" ./zn skills --check`. `--plan` prints `skills: .claude/skills` after the build lines. The stage is a static stage: it runs in every gate run, whatever `--project` picks, so each of CI's per-project jobs (c0120's G6) runs it, because the links span every project. CI runs it on a fresh checkout, so a branch that forgot to commit a link fails there.

Every reader that goes through git, and every spec, reads the real folder: git refuses a path beyond a symlink ("fatal: pathspec … is beyond a symbolic link", E1), and the Override check greps the real path. AC4's second case pins it: no code or spec under `zn`, `scripts/`, `z-nile/` (skills, README and `.tracker/` aside), `z-nile/tests/` (promoted specs aside) or `pickman/` (its skills, `.tracker/` and promoted specs aside) names a path through a link (`.claude/skills/<name>/…`).

The zz-rules skill gains a **Skills** bullet before **Lessons** ("- **Skills**: z-nile's skills live in `z-nile/skills/<name>/SKILL.md`, a project's own in `<project>/skills/<name>/SKILL.md` …, which `./zn skills` writes and `./zn skills --check` (in the gate) checks … a project's skill is named `<project>-…`, and `./zn skills` refuses any other"). Its command table gains a `| skills | ./zn skills [--check] |` row; the main checkout's read-only list says "`lessons`, `skills --check` and `capture <id>` (they only read)"; the refusal list says "`compact`, `remap` and `skills` (without `--check`) refuse"; Other commands lists "`./zn skills [--check]`"; and the usage text names `skills [--check]` (lesson zz-rules/exhaustive-lists-name-new-things).

### 5. Lessons and the ledgers
- **Folders.** `lessons.load(root)` reads every folder of `skills.folders(registry)` that exists. A tree whose registry is missing or doesn't parse refuses (c0114: "a missing registry refuses"; `lessons: no z-nile/projects.toml …`), never guessing the folders. A tree with a registry and neither folder (one from between c0114 and c0115, or a fixture made that way) reads `lessons.LEGACY_SKILLS = ".claude/skills"`, as before, and never both: a stray `.claude/skills/<old>/lessons` beside the real folders is never read. The `Tree` gains optional `folders` (skill → real folder) and `owners` (skill → project). `lessons.folderOf(tree, skill)` gives the folder, or the legacy place for a hand-built tree. One skill in two folders is a load problem naming both. A lesson whose skill has no `SKILL.md` reports `<id>: no skill <s> (no <s>/SKILL.md in any skills folder)`.
- **Ids.** A lesson's id stays `<skill>/<slug>`, now with the new names (`zz-test/plain-find-for-literals`). `lessons --full` prints `== <real folder>/lessons/<slug>.md`.
- **One rule, three users** (design review 002 F1; lesson zz-test/one-rule-one-function). `z-nile/engine/skills.luau` holds the rename map and the two rules, and the rename script, AC4 and AC5 all call them:
  - `skills.RENAMED` (old skill → new, `architecture` → `zz-arch` for ids), `skills.RENAMED_PATH` (old skill → real folder, `architecture` → `pickman/skills/pickman-arch` for paths), `skills.HYPHENATED` and `skills.WORDS`, all between the markers `-- c0115 rename map: begin` and `-- c0115 rename map: end`, the one block AC4's scan leaves out (a missing block is an error);
  - `skills.lessonIndex(root)`: every existing `<skill>/<slug>` in the skills folders;
  - `skills.oldLessonIds(text, existing)`, the prose rule: an `<old>/<slug>` token not after a name character, `/` or `.` counts only where its renamed lesson exists, so `tracker/next`, `scripts/tracker/x` and `review/x` never count; `skills.renameLessonIds` renames them;
  - the ledger rule, in `z-nile/engine/lessons.luau` beside the format's one reader (design reviews 003 F1 and 004 F1; lesson zz-arch/one-reader-per-format): `lessons.ledgerOldIds(text, existing)` and `lessons.renameLedger(text, existing)` cover every byte of a ledger with one of two rules. The id list of an entry `lessons.parseHarvest` returns takes the id rule: every parsed id of an old skill counts, known or not, and is renamed in place, so the list's separators and spaces stay byte for byte (design review 005 F2). Every other part of a ledger is prose and takes the prose rule: the rest of an entry's line (a note's text, a one-off's reason), and every line `parseHarvest` skips (the `# Harvest:` heading, paragraphs such as R0042's line 2, indented sub-bullets, blank or odd lines) or refuses (which `lessons --check`, AC6, still fails). Only parsed ids are reported as unknown. (`skills.luau` can't hold it: `lessons.luau` requires `skills.luau`.) No other format c0115's rules read goes through a reader that skips lines: AC4, AC5's lesson files and the script read whole files (SKILL.md, lesson frontmatter and body, README, code, every live `.md`) through the prose and name rules, and tracker documents, `check.sh` files among them, are history AC4 leaves out;
  - `skills.oldNames(text)`: §8's name forms with their replacements, earliest and longest match first; `skills.renameOldNames` applies them.
- **The ledgers.** Every `harvest.md` under every root (done items included: the ledgers are data, not frozen captures) and every lesson body is rewritten by `rename-lesson-ids.luau`, in this item's `experiments/`. Run it as `lune run "$(./zn find c0115)/experiments/rename-lesson-ids"`, with `-- --dry-run` to preview. It maps `make-issue→z-ticket`, `ticket-prep→z-design`, `ready-raft→z-ready`, `launch-raft` and `execute-raft→z-run`, `stop-raft→z-stop`, `review→zz-review`, `tracker→zz-rules`, `metrics→zz-stats`, `testing→zz-test` and `architecture→zz-arch`. It rewrites an `<old>/<slug>` token only where `<new>/<slug>.md` exists, so `scripts/tracker/x.luau` is never touched, and in each lesson body it also renames the old skill names (`skills.renameOldNames`): lessons keep arriving between this prep and the execution, and their prose names the old skills. It exits 1 naming any parsed ledger id with no lesson at the new place; prose in a note or a one-off never makes it fail. It is idempotent (E4). The executor runs it after the move and again after any merge of main that brings new ledger lines (c0112).
- **c0112.** Either order works. If c0112 (the backfill) lands first, its entries are rewritten by the same run. If it lands after, it writes new ids itself, since the old folders are gone and `lessons --check` would refuse old ones.
- **Text.** Skill text and lesson bodies that cite a lesson id use the new id (`lesson zz-arch/one-reader-per-format`). A lesson that quotes an old id or an old skill name as an example or as history names it in words ("the old testing-skill id of no-vacuous-pass", "the design skill"), never as a token, or the rename turns the example into a false statement (design review 002 F4, 003 F2): `plain-find-for-literals` now shows `string.find(s, "ab-cd")` (nil in Lune, as the old example was), and `instructions-runnable-where-they-run` says "reads the design skill and the testing skill".
