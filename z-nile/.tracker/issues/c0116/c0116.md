# c0116: Split rafting out of design

## Problem
Ticket prep both designs an issue and creates its raft. Recent rafts are almost all a single issue, so grouping is not part of the design. A prepared issue should be able to sit with no raft until something groups it. There is no command that moves issues between backlog rafts.

`z-design` designs one issue to `design: ready` and status `prepared`, and does not create a raft. `z-raft` groups prepared issues. With an argument it does what was asked. With none, it never mixes types, never pulls an active or done raft, folds defects into one open prepared defect raft, folds chores the same way, and groups features only when they share a surface. A raft that would pass about 1,500 changed lines starts another. Recombining keeps one backlog raft and retires the other. Rafts never cross projects.

Decided with the user (2026-10-20): the work lands as sequenced rafts; this one follows the skill rename (c0115).

Decided with the user (2026-10-20), from the programme review:
- "Short coherence review": z-raft writes a raft's Theme, Order and interfaces, and runs one short raft-only coherence review when a raft groups several issues (always for features that share a surface).
- "A `solo:` marker": z-design writes `solo: true` from a recorded user decision (such as sequenced rafts), and z-raft never folds a solo issue with others.
- "recombine <keeper> <other> [ids…]": it moves the listed issues, or all of them, into the keeper, and retires the other raft only when it ends up empty.
- "Rules always hold": with an argument, z-raft still refuses mixed types, active or done rafts, and cross-project rafts.
- "On the issue, rolled up": an issue's design reviews, refutes and `harvest.md` live in its own folder, and metrics, the review skill and the board roll them up to the raft.
- "z-design writes `size:`": z-design records an estimate of changed lines, and z-raft sums them. An issue over the cap is a raft by itself and is never split automatically.

Decided with the user (2026-10-21), from design review 002: "Keep one PR" (c0116 lands as one PR, given at about 1,670 changed lines, over the 1,500-line guide, rather than as two sequential issues).
Decided with the user (2026-10-21), after design review 003: "Still one PR" (re-confirmed at about 1,890 changed lines).

## Non-goals
- Changing the design checklist for a feature, a defect, or a chore beyond taking raft creation out. The three checklists are named in the README by c0115; the signatures and specs of a designed issue stay ticket-prep's job.
- Choosing models or drawing the board.

## Solution
- Remove raft creation from the design skill.
- Add `z-raft` with the policy above.
- Add a backlog-only recombine command on `zz-rules` that moves `raft:` and `issues:` and retires the empty raft.

(Added in prep, after the captured bullets.)
- The lock (the user-approved plan): an issue's membership is its own `raft:` line, edited only in the rafting PR; two PRs that raft one issue edit that one line, so the second can't merge cleanly; the published raft stamp claims only the raft.
- `./zn fold`, `./zn release` and `./zn raft-plan [--apply]` (the no-argument policy as a pure module, so c0117 can run z-raft as a script step), and `new raft` over prepared issues.
- Design reviews on the issue, rolled up by `metrics`; `promote-check` takes an issue; `audit` warns about a given-back raft with no member.

### 1. The lock, and one table for every command
The earlier attempt (R0042 design reviews 001 to 005) computed "who holds a prepared issue" from origin `issues:` lists, which change only when a PR merges, so every round found one more command that read them stale (lesson zz-arch/lock-reads-live-state). This design reads no `issues:` list to decide a hold. Two places change at the moment membership changes, and the lock lives there:
- **The `raft:` line.** An issue's raft is its own `raft:` line. `new raft`, `fold` and `recombine` write it in the rafting worktree, and only the rafting PR carries it to `main`. Two PRs that raft one issue edit that one line, so the second can't merge cleanly (U1: a content conflict on merge, squash and rebase; an identical edit merges cleanly, which is harmless).
- **The raft's stamp.** The published claim stamps rafts only, with a fresh `preparing-…` value that no item on `origin/main` carries (`freshStamp`, the rule `claimStamp` already used for `active-…`). A prepared issue is never restamped. `recombine` gives its two rafts one value, and "the same claim" means "the same stamp", never "the same raft id".

**The rule, once.** An issue belongs to the raft its `raft:` line names on `origin/main`. A command that claims or prepares a raft refuses an issue whose origin `raft:` names a different raft, unless that raft carries this raft's own stamp (recombine's other raft). No command restamps an issue that is `prepared` on `origin/main`. `ready` (unchanged) reads membership from `raft:` lines and refuses a raft whose `issues:` disagrees.

**What was grouped is recorded** (review 002 F1; lesson architecture/locks-detect-change). A claim check sees only claims that are still open; a full z-design cycle (claim, redesign, carried prepare, land) inside the rafting window leaves none. So `new raft`, `fold` and `recombine` write into the raft's `grouped:` line a hash of each prepared member's document as it is on `origin/main` when it is grouped (`grouped: [c0013@1a2b3c4d5e6f, …]`; `raftplan.designHash` leaves out the `status:` and `raft:` lines, which ready, stop and the rafting PR itself change). The carried `status <R> prepared` and `ready <R>` refuse a member whose document no longer hashes to its record: "<id> (<recorded> → <now>): changed on origin/main since <R> grouped it". Old-flow members (stamped with the raft's value) have no record and are exempt. A single-member raft is checked too (its Theme quotes the design). I chose this over restamping members because the user's plan says the raft stamp claims only the raft, and because restamping would bring back review-004 F1's give-back problem (`prepared>new`) on every release (G16).

**What the record covers** (review 003 F1; lesson architecture/records-cover-what-was-reviewed), stated once as `raftplan.isDesignFile(rel, id)`: the files of the member's folder that make up its reviewed design: its document (hashed without `status:` and `raft:`), `check.sh`, every file under `acceptance/`, and its `design-review-*`, `design-refute-*` and `harvest.md`. Not `spend.md` (`./zn spend` after the landing), `prompt.md` or `experiments/`. A new file kind in an issue folder is classified there. `raftplan.recordHash(id, files)` hashes the design files sorted by path, each path with its length and bytes. **Every hash reads git's view, never a directory walk** (review 004 F1; lesson architecture/one-reader-per-format): `recordGrouped` reads origin/main; the carried move and `ready` read the tree they publish (`treeFolderFiles` inside the build, so a redesign landing after `ready`'s pull is seen too); the carried move's raft reviews read `gitFolderFiles(dir)` (`git ls-files -co --exclude-standard`: tracked files, and untracked ones that aren't ignored, since a review may not be committed yet when the carried move runs); and `keepRecords` reads `gitFolderFiles(dir, true)`, the index (`git ls-files -c`), because a rewrite commits only tracked files (review 005 F1). So Finder's `.DS_Store`, an editor's swap file, a merge's `*.orig`, or a work file left in a member folder during a `renumber`, never change a hash. One reader, one view per caller, each chosen for what that caller's commit carries (lesson architecture/one-reader-per-format).

**A review of the record** (review 003 F2). zz-review's raft mode quotes the raft's `grouped:` value in its Inputs as `Grouped: [...]`. For a raft of two or more members, the carried move (after its Theme check) and `ready` need a `design-review-NNN.md` in the raft's folder whose quoted record covers the current one: every current entry, with the same hash. A fold, re-fold or recombine changes the record, so it needs a new round; an `unfold` only drops entries, so it needs none. The check is on content, not commit order, so it holds after the rafting PR's squash merge. Refusal: "<R>'s coherence review predates its record (<ids>): run a new raft-mode round (zz-review); never edit a review that is already written". It names the record's ids, not the `Grouped:` line, so it hands no one text to paste into an old review (review 004 F4). z-raft and zz-review say a review file is never edited after it is written.

**Refusing an edited review** (review 004 F4, asked whether it is feasible): only partly. In the carried move the branch's history could show a review modified after its first commit, but `compact` and `remap` legitimately edit a review's `Grouped:` line, so the check would need their commits exempted. On `main` the rafting PR's squash merge leaves each review a single commit, so `ready` could never tell. Not built: the user decided G20 (2026-10-21, "Accept, rely on the skills"): the message and the skills carry the rule, the code review and the PR diff catch an edit, and the engine can no more authenticate a review than it can tell a pasted line from a written one.

**No exemption by absence** (review 003 F5). The carried move refuses a member it takes as `prepared` that this rafting grouped (its origin `raft:` is not R) and that has no entry: "<id> has no grouped: record in <R>: fold it again (only a member stamped with <R>'s value is exempt)". The exemption is explicit: an old-flow member is `preparing` with the raft's own stamp.

**Mechanical rewrites re-record** (review 003 F4). `compact` (on its tree and on remap's merge-base scratch), `remap` and `renumber` rewrite ids in member documents, which changes their hashes. `keepRecords(root, idMap, rewrite)` notes, before the rewrite, every `grouped:` entry whose member matches it. After the rewrite it writes the new hash under the new id, in the raft's document and in its reviews' `Grouped:` lines. An entry that did not match before is left alone. The second call, on remap's merge-base scratch, is kept although no case can tell it apart (review 004 F2): HEAD and origin/main re-record the same entries to the same values, so git's merge never needs the base's line. It is kept so the three sides of remap's merge match in every line, which is what that scratch exists for. It is marked `reasoned`.

Every new publish is preceded by `refuseStale()` (c0081's publish-guard pins it). `fold`, `recombine` and `new raft` need a clean tree, refuse the main checkout, and merge `origin/main` first, so the local tree holds everything `origin/main` does when they read membership.

**The cases the earlier rounds broke, with this table** (each is a spec case, §Test plan):
- *Concurrent rafting of one issue* (review-002 F4): both `new raft`s publish; the first PR merges; the second's `git merge origin/main` stops with `CONFLICT (content): Merge conflict in <root>/issues/<id>/<id>.md`; its carried `status <R2> prepared` refuses, naming the first raft; `release R2` publishes only R2's document, and the issue's origin bytes never changed.
- *Fold into a prepared raft* (review-005 F2): the claim publishes R's status alone; the members' origin bytes stay equal; another checkout's `fold` and `status R preparing` are refused, and so is `ready R`; the carried move takes the folded issue; after the merge `ready R` claims it.
- *Give back a fold* (review-003 F1): `release R` puts R back to `prepared` (its design is ready on origin), with its old members; `ready R` works.
- *Recombine* (review-005 F1): both rafts share one stamp; the carried `status K prepared` takes the moved issue whose origin `raft:` still names O, because O carries K's stamp; a raft with another stamp is refused, naming it; after the merge both rafts are readyable, and an emptied O is gone.
- *A raft at `new` that lists a held issue* (review-005 F2's third bullet): `status <R> preparing` refuses the listed issue another raft's `raft:` names.
- *A member re-claimed for design during the rafting* (review 001 F1): B's `status c0013 preparing` succeeds (nothing on origin says c0013 is being rafted) and merges into the rafting worktree cleanly; the carried `status RX prepared` then refuses, naming B's stamp, and leaves origin's c0013 alone; the rafting drops c0013 and prepares the rest. Once it lands, z-design's claim of a member refuses ("is in RX"). The other order (B claims after the carried move, before the landing) meets at `ready`, which refuses the raft while the member is `preparing`.
- *A redesign landed inside the rafting window* (review 002 F1, both orders): one that lands after the carried move is caught by `ready`, and one that lands before it by the carried move. Each refusal names the member and both hashes, and `./zn unfold` takes the member out.
- *Abandon* (review-004 F1): `release` (or `status R new`) never meets `prepared>new`, because prepared issues are never targets.

**Who else can claim a member while a rafting is open** (review 001 F1; lesson architecture/claims-name-who-else-can-claim). The raft-only stamp leaves a member's `status:` unstamped from `new raft`/`fold`/`recombine` until the rafting PR lands. ### 2. The new commands
Signatures in `z-nile/engine/main.luau` (each `function cmd.<name>(pos, opts)`; `raft-plan` is `cmd["raft-plan"]`):
```
unfold <R-id> <issue>...                      take members out of a backlog raft, back to no raft (z-raft)
fold <R-id> <issue>...                        put prepared, raftless issues into a prepared backlog raft (z-raft)
recombine <keeper> <other> [<issue>...]       move the other backlog raft's members (all, or those named) into the
                                              keeper; retire the other when it ends up empty (z-raft)
release <R-id> [--force]                      give back a rafting claim: what carries its stamp goes back to
                                              prepared (design ready) or new (z-raft)
raft-plan [--apply]                           print z-raft's plan for every prepared, raftless issue (--apply runs it)
promote-check <R-id|issue-id>                 (was <R-id>)
```
- Shared helpers: `raftingStart(what)` (refuse the main checkout, need an origin and a clean tree, `refuseStale`, merge `origin/main`), `rememberClaim(R, value)` / `rememberedClaim(R)` over the existing `claimFile(R)` (`.cache/tracker-claim-<R>`, which `start` already uses; the directory is made when missing), `refuseUnraftable(issue, raft)`, `listValue(ids)`, `sectionWritten(text, heading)` (text beyond the template's comment), `freshStamp(state)` (`claimStamp()` is now `freshStamp("active")`), `promotedItems(item)` (an issue is its own promotion set).
- The record (review 002 F1, 003 F1): `raftplan.isDesignFile(rel, id): boolean`, `raftplan.recordHash(id, files: {[rel]: text}): string`, `raftplan.designHash(text): string` (the document without `status:` and `raft:`), `raftplan.parseGrouped(value): ({[id]: hash}, problem?)` (a malformed entry or an id twice is a problem), `raftplan.renderGrouped(map): string` (sorted by id); in main.luau, `localFolderFiles(dir)`, `treeFolderFiles(paths, read, dir)`, `originFolderFiles(dir)`, `recordGrouped(raftDoc, ids, forget?)`, `regrouped(map, now): {string}`, `reviewCovers(raftDir, map): boolean` and `keepRecords(root, idMap, rewrite)`.
- `claims.carriers(cwd, value, ref?, roots): ({string}?, string?)` in `claims.luau`: the documents whose line is `status: <value>`, one `git grep -l`; `{}` when none, nil and git's message when it can't tell (the same contract as `claims.taken`).
- Outputs: `fold` prints `folded <ids> into <R>`; `recombine` prints `recombined <O> into <K>: <ids>` and then `retired <O>: its folder is deleted in this branch` or `<O> keeps <ids>`; `release` prints `released <id> (<prepared|new>), …` and `this branch's own rafting commits are left as they are: reset it to origin/main or remove the worktree`; `promote-check` prints `copied <n> acceptance specs` before its checks (so a promotion that found nothing to copy is visible: lesson zz-test/no-vacuous-pass).
- Commit subjects in the worktree: `tracker: <R> members` (new raft, as today), `tracker: fold <ids> into <R>`, `tracker: recombine <O> into <K> (<ids>|no members)`. Published subjects: `tracker: new raft <R> <slug>`, `tracker: fold into <R> (claim)`, `tracker: recombine <O> into <K> (claim)`, `tracker: release <R>`.
- Refusals use the existing shapes: `<what> must run inside a worktree: cd "$(./zn worktree <target>)"`, `<id> already belongs to <R>`, `<id> is solo: true (a recorded user decision): it is rafted alone`, `a raft holds issues of one project: …`, `rafts never cross projects: <K> is in <root>, <O> in <root>`, `<id> is not a member of <O>`, `recombine needs two different rafts`.

### 3. The no-argument policy: `z-nile/engine/raftplan.luau` (pure)
```lua
export type Issue = { id: string, type: string, root: string, state: string, status: string, design: string?,
	raft: string, size: number?, solo: boolean, touched: { string }? }
export type Raft = { id: string, type: string, root: string, state: string, status: string, single: boolean,
	members: { string } }
export type Op = { kind: string, raft: string?, type: string, root: string, issues: { string }, single: boolean }
export type Skip = { id: string, reason: string }
raftplan.CAP = 1500
raftplan.overlaps(a: string, b: string): boolean        -- equal, or a parent folder by whole components
raftplan.touches(a: { string }?, b: { string }?): boolean -- any overlap; nil or empty shares nothing
raftplan.parseSize(value: string?): number?             -- a positive whole number of lines, else nil
raftplan.plan(issues: { Issue }, rafts: { Raft }, cap: number?): ({ Op }, { Skip })
```
The rules, in this order (each is a Rules-and-mutants row):
1. **Candidates**: backlog, effective status `prepared`, `design: ready`, `raft:` empty. Everything else is ignored.
2. A candidate with no `size:` (or one that isn't a positive whole number) is skipped: `Skip { id, "no size: (z-design records its estimate of changed lines)" }`.
3. A `solo: true` candidate, or one whose size is over the cap, is a `new` op by itself with `single = true`.
4. The rest are grouped by (project root, type): never across either.
5. **Open rafts** of that root and type take more only when they are backlog, `prepared` and not `single: true`, and every member has a `size:`. Their current size is the sum of their members' sizes. A raft with a member that has no `size:` is not open (review 001 F3: its size is unknown, so the cap can't be kept); when its project and type have candidates, the plan adds `Skip { R, "<member> has no size:, so its raft's size is unknown (not folded into)" }`, printed `skip <R>: …`, and opens another raft instead. With an argument z-raft may still `fold` into it.
6. **Defects and chores**: each candidate, by id, goes into the first bin with room (`size + issue ≤ cap`): the open rafts by id, then the rafts this plan has opened, in the order opened; when none fits, a new raft (`single = false`, so a later issue may fold in).
7. **Features**: connected components over shared surfaces (`touches`), the open feature rafts taking part through their members' Touched paths; each component is filled as in 6, from its own open rafts only. A feature with no Touched modules is a component by itself.
8. **Order**: the ops sorted by root, then type (feature, defect, chore), then their first issue id; the input's order never matters.

`raft-plan` (main.luau) builds the records from the tree (`store.all`, `statusLib.effective`, `store.typeOf`, `Item.root`, `touchedModules`, `raftplan.parseSize(front.size)`, `front.solo == "true"`, `front.single == "true"`, `store.members`) and prints each op as the command that carries it out, then the skips:
```
./zn new raft feature f0060 f0060 f0070
./zn fold R0030 d0010 d0020
./zn new raft chore c0040 c0040 --single
skip c0050: no size: (z-design records its estimate of changed lines)
```
A new raft's slug is its first issue's slug. With no op and no skip it prints `raft-plan: nothing to raft (no prepared issue without a raft)`. Without `--apply` it only reads, so it may run in the main checkout (and it skips nothing: `guardRepoRoot` still runs, as for every command not in `READ_ONLY`). `--apply` refuses the main checkout, then runs each printed command in this process, in order (`cmd.new`, `cmd.fold`), each committing its own edits. `workstreams` keeps its own rule (an issue with no Touched modules overlaps everything there, the safe direction for parallel streams) and now calls `raftplan.overlaps`, one rule for both (lesson zz-arch/one-reader-per-format).
