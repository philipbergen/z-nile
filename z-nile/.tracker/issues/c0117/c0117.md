# c0117: Stack model files and dispatch runtimes

## Problem
Which model runs a skill is not written down. A monorepo cannot give one game a cheaper design model and another a stronger one. A raft that touches two of those games has no rule for which spec wins. Ready, stop, recombine, and recording spend do not need a model, but nothing stops an agent from being started for them.

`.models.toml` stacks like `.gitignore`: from the repo root down to the work, a closer file replaces only the keys it sets. A step about one issue uses that issue's spec. A step about a raft resolves every member and uses the more powerful spec whole. Higher `rank` wins. The same rank uses the larger `max_tokens`. The dispatcher runs script steps itself. A model step calls the named runtime with the skill name and the issue id, and stops at the cap. The runtime is `cursor-cli`, `grok-cli`, `claude-cli`, `cursor-app`, `claude-cloud`, or `grok-bot`. Nothing defaults to Cursor. The spend row stores the model id and the token count the adapter returns.

Decided with the user (2026-10-20):
- The supported CLIs are `agent` (Cursor), `grok` and `claude`, each with its own set of models in `.models.toml`. A CLI the file does not list is not supported.
- A priority order says which CLI to use. The dispatcher moves down the order when a CLI's remaining tokens seem insufficient for the step, which it learns by asking that CLI.
- Model steps run headless and unattended.
- The dispatcher chains the steps on its own (ticket, design, raft, ready, run) up to the pull request, and stops at a human gate (a merge) or a failure.

Decided with the user (2026-10-20), from the programme review:
- "In scope via the same CLIs": all six captured runtimes stay. cursor-app is `agent worker`, claude-cloud is `claude --cloud`, and grok-bot is `grok agent headless`, each a runtime of its CLI in `.models.toml`.
- Quota, in the user's words: "error only, but there is a catch, make sure the cli doesn't hang in waiting for more quota, it should fail on insufficient quota." The dispatcher moves down the priority order only when a CLI fails on quota, and it must make each CLI fail rather than wait (flags, a no-progress timeout, or detecting a wait message and killing it).
- "Branch protection + wrapper": `main` gets branch protection (a PR and green CI required), and agents run with a git/gh wrapper on PATH that refuses direct pushes to `main` and any merge the dispatcher didn't authorise.
- "Stop with questions.md": a step that needs the user writes `.cache/dispatch/<id>/questions.md` and exits "needs the user". The chain stops, the board shows it, and the user answers and retries.
- Reviews, in the user's words: "They must not run on opus, only use opus with claude and cursor (cursor[agent] supports both grok and opus), grok uses grok-4.7-xhigh." The review model belongs to the CLI: Opus through `claude` or `agent`, and `grok-4.7-xhigh` through `grok`. The skills' "reviewer runs on Opus" rule changes to match.
- "Name the files in the prompt": the prompt names each skill's file path and the `zn lessons --when <step>` command, and every CLI reads them itself. No skill text is pasted.
- "One oversized PR": c0117 stays one raft.

Decided with the user (2026-10-21), from design review 001 F3: "Bot token, no bypass". Headless agents run with a separate GitHub credential (a fine-grained token or a GitHub App) that can push branches and open PRs but can't bypass protection, merge, or write protection or rulesets. Only the dispatcher merges, with the user's token, after its own checks; agents never merge. Agents never see the user's token: `GH_TOKEN`, `GITHUB_TOKEN` and gh's configuration are the bot credential's in the agent's environment, and the user's gh configuration is out of its reach as far as the OS allows. `main`'s ruleset requires a PR and green CI with no bypass for the bot; the user's admin bypass is for tracker-state pushes only, which only the dispatcher or `./zn` makes. The wrapper is a convenience layer, not the boundary, and decides from git's own resolution against a private fresh fetch. A post-step tripwire the agent can't bypass checks that origin's `main` moved only as authorised.

Decided with the user (2026-10-21), from design review 001 F6 (Guess G16): "Cap model calls, record real total". For `cursor-cli` and `cursor-app`, whose stream has no running token count, the step stops after N model calls, counted from the distinct `model_call_id`s in the stream. N is `max_calls` in each such spec of `.models.toml`, and the walk validates it; an `agent` spec without `max_calls` is an error (fail closed), never unlimited. The final result's real token total goes on the spend row. N calls are not N tokens: the user tunes N.

Decided with the user (2026-10-21), from design review 002 F4: "Persisted watermark". The dispatcher keeps the last commit of `main` it vetted in a file kept where a well-behaved step never writes, and detected if it changes (the wording of the user's later "Keep same user, accept detection"; it read "outside any agent's reach"): not in the repository or any worktree, but `$ZN_WATERMARK_DIR`, else `$XDG_STATE_HOME/zn-dispatch`, else `~/.local/state/zn-dispatch`, in a folder named for the repository, file `main-seen`. At the start of every run and of every step, and after every step, it checks every commit of `main` since that watermark with the same tracker-state function the broker uses. Any unvetted commit stops the chain until the user acts (`./zn dispatch vet`). This detects a late push after the fact; it doesn't prevent it.

Decided with the user (2026-10-21), from design review 003: "Keep same user, accept detection". Unattended agents run as the user's own OS user. Every guard (the wrapper, the publish broker, the tripwire, the watermark and the merge gates) detects honest mistakes and casual misbehaviour; none is a security boundary against a determined agent. The design, zz-rules and the README say so plainly; what is detectable or cheap is fixed, and the rest is written down as known limits.

Decided with the user (2026-10-23), after design review 005: "Fix, no more review". Its three findings are fixed as the reviewer recommended, and the design is ready; the code review checks them.

## Non-goals
- Drawing the board. c0118 reads the model id this issue stores.
- Pasting skill text, the architecture map, or other issues into the prompt.

## Solution
- Add a root `.models.toml` and the stack walker.
- Add one adapter per runtime. Each returns a token count.
- Record that count and the model id with `tracker.sh spend --tokens`. A row with no model stays unrecorded.


(Added in prep, after the captured bullets.)
- The prompt names files instead of pasting them (the user's "Name the files in the prompt"): a model step's prompt names its skill's `SKILL.md` and the `./zn lessons --when <design|build> --full` command; the raft's `prompt.md` names the skill files, the architecture map and the build lessons command (its lessons index stays, c0111).
- Every captured runtime has an adapter: `claude-cli`, `claude-cloud`, `grok-cli`, `grok-bot`, `cursor-cli` and `cursor-app`, the last three as runtimes of their CLI (the user's "In scope via the same CLIs").
- `./zn dispatch` with its chain, its gates, `questions.md`, `stop`, `retry` and `status`, the git/gh wrapper, the review-model rule, `spend --model` and `commit --model`, and branch protection on `main` as a step for the user.
- From the user's "Bot token, no bypass" (2026-10-21): the agent credential in every step's environment, the publish broker that pushes a step's tracker state with the user's credential, the post-step tripwire, and the supervisor's lifeline, run lock and checked stop that keep a step from outliving or escaping its dispatcher.

### 1. `.models.toml` and the stack (`z-nile/engine/models.luau`, pure but for `walk`)
The file at the repository root (and optionally closer to the work: a project's home, an issue's folder):
```toml
order = ["claude", "grok", "agent"]        # the CLI priority order, top first
[dispatch]
auto_merge = ["prep", "raft"]              # the merge gates the dispatcher may pass itself (never the run's PR)
stall_seconds = 300                        # no output for this long kills the step
[z-design.claude]                          # one table per model step and CLI
model = "claude-opus-5-5"
effort = "high"                            # optional
rank = 3
runtime = "claude-cli"
max_tokens = 3000000
```
```lua
export type Spec = { cli: string, model: string, effort: string?, rank: number, runtime: string, maxTokens: number }
export type Settings = { autoMerge: { string }, stallSeconds: number }
export type Layer = { path: string, order: { string }?, settings: { [string]: any }, skills: { [string]: { [string]: { [string]: any } } } }
export type Resolved = { skill: string, order: { string }, specs: { [string]: Spec }, settings: Settings }
models.CLIS = { "claude", "grok", "agent" }
models.RUNTIMES = { claude = { "claude-cli", "claude-cloud" }, grok = { "grok-cli", "grok-bot" }, agent = { "cursor-cli", "cursor-app" } }
models.parse(text: string, path: string): Layer          -- every error names the file and the key
models.folders(dir: string): { string }                    -- ".", then each folder down to dir
models.walk(repo: string, dir: string): { Layer }          -- every .models.toml on that walk, root first
models.resolve(layers: { Layer }, skill: string): Resolved
models.reviewRule(skill: string, spec: Spec): string?      -- why a zz-review spec breaks the user's rule
models.strongest(specs: { Spec }): Spec
models.forRaft(own: Resolved, members: { Resolved }): Resolved
models.tries(r: Resolved): { Spec }                        -- the order's CLIs that name the skill, in order
models.id(spec: Spec): string                              -- the id a row records: "grok-4.7-xhigh"
```
Rules (each a Rules-and-mutants row):
- **Stacking.** A closer file replaces only the keys it sets: `order` whole, each `[dispatch]` setting, each field of each `[<skill>.<cli>]` table. A CLI table the closer file does not name keeps the farther file's whole.
- **Only three CLIs.** A `[<skill>.<cli>]` table or an `order` entry naming anything but `claude`, `grok`, `agent` is an error ("a CLI the file does not list is not supported"). A repeated `order` entry is an error; a repeated table or key is the TOML reader's error (it refuses duplicates: lesson zz-arch/parsers-refuse-ambiguity).
- **Runtimes belong to their CLI**: `claude-cli`, `claude-cloud`; `grok-cli`, `grok-bot`; `cursor-cli`, `cursor-app`. Any other pairing is an error.
- **Nothing defaults** (the capture's "Nothing defaults to Cursor"): no file on the walk, no `order`, a skill no file names, or a spec missing `model`, `rank`, `runtime` or `max_tokens` is an error naming it. Unknown fields and settings are errors; counts are whole numbers ≥ 1.
- **Which walk.** A step about one issue walks to the issue's own folder (`<root>/issues/<id>/`, wherever its lifecycle folder is). z-ticket walks to the project's home (`--project`, else the registry's first). A step about a raft resolves each member's walk and takes, per CLI, `strongest` of the members' specs; `order` and the settings come from the raft's own walk (its folder). Rafts never cross projects (c0116), so a project's `.models.toml` lowers or raises its own members' specs, which is the Problem's "a cheaper design model for one game and a stronger one for another".
- **The power rule.** `strongest`: the higher `rank`; the same rank takes the larger `max_tokens`; a tie keeps the first; the winner travels whole (model, effort, runtime, cap). `strongest({})` is an error. Ranks compare specs of one CLI (a raft's `claude` spec against its members' `claude` specs).
- **The review rule** (the user's: "only use opus with claude and cursor, grok uses grok-4.7-xhigh"): a `zz-review` spec through `claude` or `agent` must be an Opus model (`claude-opus-…`); through `grok` it must be `grok-4.7` with `effort = "xhigh"` (the `grok` CLI has no `grok-4.7-xhigh` model id: probe E3; Cursor's `agent` lists `grok-4.7-xhigh` and the Opus ids). Anything else is an error at resolve time.
- **The cursor cap** (the user's "Cap model calls, record real total"): an `agent` spec (`cursor-cli`, `cursor-app`) needs `max_calls`, a whole number ≥ 1; without it the walk is an error naming the skill and CLI, never unlimited. The other CLIs may omit it. `Spec.maxCalls`. N calls are not N tokens: a call re-reads the whole context, so the token spend of N calls grows with the session; the user tunes N (the root file's guess: 200 for the authors, Guess G1). A call count can miss calls (a stream that drops `model_call_id` and prints no turn), so an `agent` spec also needs `max_minutes`, a wall-time ceiling (review 003 F7: fail closed; the root file's guess 240), and the runner kills a step past it as `cap`. `Spec.maxMinutes`. Turns count too: the first `thinking` or `assistant` line, or `tool_call` `started` without a `model_call_id`, after a `user` line or a finished tool call, starts one.
- **Never tracker state** (review 003 F4): a `.models.toml` grants authority (a gate, a cap, which CLI runs), so it is configuration: the one tracker-state function refuses it in any case, the broker never pushes one and the gates never merge one. A closer file changes only by a reviewed PR that a human merges; a step that wants one asks in `questions.md`.
- **The row's model id** is `model`, plus `-<effort>` when the spec sets one (`claude-opus-5-5-high`, `grok-4.7-xhigh`), the same spelling Cursor's ids use.

The root `.models.toml` (Touched modules) names all five model steps on all three CLIs, order `claude`, `grok`, `agent` (Guess G1).

### 4. Adapters (`z-nile/engine/adapters.luau`, pure) and the runner (`runner.luau`)
```lua
export type Request = { prompt: string, model: string, effort: string?, cwd: string, session: string }
export type Acc = { live: number, final: number?, byMessage: { [string]: number }, quota: string?, errorText: string?, lastText: string, session: string? }
export type Adapter = { cli: string, runtime: string, estimated: boolean, argv: (Request) -> { string }, feed: (Acc, string) -> () }
adapters.get(runtime: string): Adapter
adapters.finish(acc: Acc, exitOk: boolean, stderr: string, runtime: string): ("ok" | "failed" | "quota", string)
adapters.tokens(acc: Acc): number      -- final when the CLI gave one, else the running count
adapters.QUOTA, adapters.WAITING, adapters.STDIN
```
| runtime | command line (probed 2026-10-21 where marked) | stream | running count | final count |
|---|---|---|---|---|
| `claude-cli` (E1 ✔) | `claude -p <prompt> --output-format stream-json --verbose --model <m> --permission-mode bypassPermissions --permission-prompts none --session-id <uuid> [--effort <e>]`, cwd = the worktree | NDJSON | each `assistant` message's `usage`, once per message id (its blocks repeat it) | `result.modelUsage`, summed over models (subagents included) |
| `claude-cloud` (E6, unproven) | `claude --cloud <prompt> -p --output-format stream-json --verbose --model <m>` | as claude-cli | as claude-cli | as claude-cli |
| `grok-cli` (E1 ✔, tools ✔) | `grok -p <prompt> --output-format streaming-json -m <m> --always-approve --cwd <wt> -s <uuid> [--reasoning-effort <e>]` | NDJSON (ACP updates) | each `usage` line (one per model call) | the `end` line's `usage` |
| `grok-bot` (E7, unproven) | `grok agent -m <m> [--reasoning-effort <e>] --always-approve headless`, the prompt on stdin | as grok-cli | as grok-cli | as grok-cli |
| `cursor-cli` (E1 ✔) | `agent -p --output-format stream-json --model <m>[\[effort=<e>\]] --force --trust --sandbox disabled --workspace <wt> <prompt>` | NDJSON | none (`callCapped = true`): the step stops after `max_calls` model calls, one per distinct `model_call_id` and one per turn with none (E3), or after `max_minutes` of wall time | the `result` line's `usage`: the row's real total |
| `cursor-app` (E8, unproven) | `agent worker --model <m> --workspace <wt>`, the prompt on stdin | as cursor-cli | as cursor-cli | as cursor-cli |
**The count**, the same for every CLI: input + cache writes + output (reasoning included in output by all three), cache reads left out (Guess G3). From the probes: claude 2 + 9,841 + 4 = 9,847; grok (16,114 + 112) + (296 + 11) = 16,410 + 123 = 16,533 (the per-call lines sum to the end line); agent 15,155 + 28 = 15,183. The caps (`max_tokens`) use the same count.

**Quota** ("error only … make sure the cli doesn't hang in waiting for more quota"): the dispatcher moves down `order` only on outcome `quota`, which only the CLI's own signals report (review 001 F8): claude's `rate_limit_event` with `status = "rejected"` (printed once per call; the probe showed `allowed` with `utilization 0.78`), an error `result` or error line whose text names a rate or usage limit (`adapters.QUOTA`), a failed exit whose stderr names one, or a stall after the CLI's own wait message (`adapters.WAITING`: "retrying in", "resets at", …) in what the CLI printed itself (`Acc.cliText`: a non-JSON line, a `system` or error line, an error result, stderr). The model's own words (assistant text) are never read for either, so a model that writes "I'll try again" and then runs a quiet tool is `stalled`, not quota. No probe could make a CLI exhaust its quota without spending it (E5); the stall rule is what makes any CLI fail rather than wait.

**Open tool calls** (review 001 F8): each adapter tracks the tool calls started and not finished (claude: an assistant `tool_use` block until its `tool_result`; grok: `tool_call` until a `tool_call_update` with `status` `completed` or `failed`; agent: `tool_call` `started` until `completed`, probe E3). While one runs, the stall limit is `dispatch.tool_seconds` (default 900; a full gate is quiet for two to three minutes) instead of `stall_seconds`.

**claude's sandbox** (programme review E6, review 001 F14): claude's argv carries `--settings '{"sandbox":{"enabled":false}}'`, whatever the user's settings say, so a gate run inside the step engages its own jail (macOS can't nest sandboxes); agent gets `--sandbox disabled`; grok runs without one unless `GROK_SANDBOX` is set, which the dispatcher does not set.

**The runner** (`runner.run(Request) -> Result`, outcomes `ok | failed | quota | cap | stalled | stopped`; review 001 F4): the CLI starts under a perl **supervisor**. The supervisor takes an flock on `<state>/run.lock`, forks the CLI into a new process group it leads (its stdin from `<state>/stdin`: the prompt for the stdin runtimes, else empty), writes the group's id to `<state>/pid`, and waits. Its own stdin is a pipe from the dispatcher: the **lifeline**. On end of file (the dispatcher died, however it died: Ctrl-C, a closed terminal, a crash) and on its own TERM, INT or HUP it kills the group (TERM, then KILL after 2 s); when the CLI exits it kills what is left of the group and exits with the CLI's code. One `kill -TERM -<pgid>` stops the CLI and everything it started (a `check.sh`, a Bash tool's children). The runner reads stdout line by line into the adapter, keeps the last 4 KB of stderr, serves the publish broker (§5) on every tick, and every 50 ms checks, in order: the stop marker (`stopped`), the running count past `max_tokens` (`cap`), a quota signal (`quota`), and the time since the last stdout line against the stall or tool limit (`quota` after the CLI's own wait message, else `stalled`). A killed step's count is what it streamed so far. A process that left the group (setsid) is not waited for (zz-test, "Caught only by review").
```lua
export type Identity = { pgid: number, lockFile: string }
runner.sameRun(id: Identity): boolean      -- the supervisor still holds the run's flock; pgid a whole number > 1
runner.killGroup(pgid: number, grace: number?)   -- never pgid <= 1 (`kill -- -1` signals every process of the user)
runner.holdLock(path: string): Child?      -- an flock holder that lets go when its stdin closes (the run lock)
runner.held(path: string): boolean
```
A run's identity is its flock, not `ps` (start time and command line): `ps` is setuid and the specs' jail refuses it, and an flock can't be fooled by pid reuse, because the supervisor holds it for exactly as long as the group lives.

### 5. The dispatcher (`z-nile/engine/dispatcher.luau`; `cmd.dispatch` in `main.luau`)
```
dispatch <id> [--dry-run]                              the chain from the item's tracker state
dispatch new "<description>" [--project <name>] [--dry-run]   z-ticket, then the chain on the new issue
dispatch <step> <id> [--mode design|code|raft|stream] [--dry-run]    one step
dispatch stop|retry|status <id>
dispatch vet                                           the user's: take main as vetted after a tripwire stop
```
`main.luau` passes a context: `fail`, `mainRoot`, `onGitHub` (now the URL as configured, `git config --get remote.origin.url`, before any `insteadOf` rewrite), `checking` (below), `origin(id) -> { path, front, state, status }?` (origin/main's document, through `originTree`/`docPath`/`frontOf`/`stateOfPath`/`statusLib.effective`, the readers `ready` uses: lesson zz-arch/one-reader-per-format), `originIssueIds()`, `prView(branch)` (`gh pr view <branch> --json number,state,isDraft,mergeable,statusCheckRollup,headRefOid` on a GitHub origin, else nil: the seam the gate specs drive with a fake gh), `prMerged(sha)` (`gh api repos/{owner}/{repo}/commits/<sha>/pulls`, filtered by `dispatch.prMergedFrom`: whether a pull request merged into `main` has `sha` as its merge commit; false off GitHub). `--dry-run` is a boolean flag (`flags()`); `dispatch` is not in `READ_ONLY` (it runs `guardRepoRoot`). A dry run starts nothing, takes no lock and writes nothing (review 001 F11).

**The agent credential** (`z-nile/engine/credential.luau`; the user's "Bot token, no bypass"). `credential.token() -> (string?, string)` reads the agent's token from the file `$ZN_AGENT_TOKEN_FILE` names (then nowhere else), else `~/.config/zn/agent-token`, else the macOS keychain item `zn-dispatch-agent` (`security find-generic-password -s zn-dispatch-agent -w`). Without one, no CLI starts: the attempt fails "no agent credential …" (not quota, so the chain stops). `credential.agentEnv(base, token, configDir)` gives the step's environment `GH_TOKEN` and `GITHUB_TOKEN` = the agent's token, `GH_CONFIG_DIR` = an empty folder of the step's own (`<state>/gh`, so gh reads none of the user's hosts or keychain entries through its configuration), `GH_PROMPT_DISABLED=1`, `GIT_TERMINAL_PROMPT=0`, `SSH_AUTH_SOCK` empty, and two git configuration entries appended after whatever `GIT_CONFIG_COUNT` already carries (the repository guards' own, inside a check): `credential.helper` reset to empty, then a helper that answers `username=x-access-token` and the agent's token. **What isn't enforceable** (said in zz-rules too): the agent runs as the same OS user, so a process that goes looking can still read the user's own credentials where they live (the login keychain, `~/.config/gh`, `git credential-osxkeychain`); only a separate OS user, or an OS sandbox that macOS can't nest with the gate's jail, would stop it. The server's protection (§8) is what stops the agent's own credential, and the tripwire (below) is what catches the user's credential being used from a step.

**Tracker state** (`z-nile/engine/trackerstate.luau`, pure but for `check` and `checkEach`; review 002 F1, F2, review 003 F1, F4, F8, F10): one definition, used by the wrapper (§7), the broker, the tripwire, the watermark and the merge gates (§6), never respelled. `trackerstate.check(git, base, sha, roots, opts)` reads `git diff-tree -r --raw --no-renames --no-abbrev base sha` (a rename's source is a deletion it judges; both sides' modes) and both trees (`git ls-tree -r --full-tree`), and `judge` passes the change only when every path: is under `<root>/` of the registry it is judged by (with the slash: `tracker-x/` and `z-nile/nextgen/` are not) or is exactly `z-nile/next` (a gate's `allow` may add skill lessons); is plain (ASCII letters, digits, `.`, `_`, `-`, `/`: no quoted or Unicode path, no empty, `.`, `..` or `.git` component in any case); is a regular file (100644 or 100755: no symlink 120000, no gitlink 160000); is not `.gitattributes`, `.gitmodules` or `.models.toml` in any case (git's configuration, and a setting that grants authority: a gate, a cap); if added, doesn't differ only in case from another path of the resulting tree; and passes the caller's narrower `only` rule. With `sequestered` (every caller here passes it), each item the change touches is judged **per item**: the set of its sequestered files (an exact-case `check.sh` and anything under `acceptance/`, relative to the item's folder) is the same in both trees, each unchanged or, for a `check.sh` whose item folder moved, exactly `paths.rewrite(old, the moved folders)` (as `ready`, `stop` and `done` write it); the item lies in one folder after; only an item with no file on the base adds them (a new item's stub); a sequestered name in another case is refused; `own` lists the ids a gate's PR may change. `trackerstate.checkEach(git, from, to, rootsAt, opts, pass?)` judges each first-parent commit against its parent by its parent's registry, as the watermark and the broker both do. A git failure is a refusal.

**The publish broker** (`z-nile/engine/broker.luau`; review 002 F3, F7, review 003 F3, F10). The agent's credential can't push to `main`, but a step's own `./zn` commands publish tracker state there all the time (`status`, `spend`, `new issue`, `land`). Each top-level run serves a broker folder of its own, `.cache/dispatch/<id>/broker`, and makes a run token (a uuid); a step's environment names both (`ZN_PUBLISH_BROKER`, `ZN_PUBLISH_TOKEN`), and a nested dispatcher (a review) inherits them, so its author's run serves it. `publish.commit`'s push and `land`'s push write a request (`<uuid>.req`: the token and the commit) and wait for the answer (`<uuid>.res`, up to 600 s). The dispatcher serves the folder on every runner tick and after the step: it claims each request by renaming it (`.req` to `.taken`: of two servers only one wins), refuses a request whose token is not its run's, and never raises (the whole serve is under `pcall`; a failure is an answer). The push itself fetches `main` from the run's pinned fetch URL into `refs/zn-dispatch/run-<id>/main` (its own ref, never the tracking ref), refuses any commit that is not a fast-forward of it ("rebuild it on main and ask again"; `publish.commit` already rebuilds and retries on a refused push), refuses a history the watermark would refuse (`trackerstate.checkEach`, each commit against its parent: "squash it and ask again"), and then pushes to the pinned push URL with a plain `git push` with the user's credential, **never forced** (a `main` that moved since the fetch refuses it). It records each commit it pushed (`state.pushed`), for the log only: nothing is exempt from the tripwire because the broker pushed it.

**Fetch refs of the run's own** (review 005 F1). Git compares and swaps a ref, so two fetches into one shared ref fail with "cannot lock ref" (the reviewer measured 84 to 99 failures in 300 against a moving `main`), and a late one can set it back. Every dispatcher process fetches into `refs/zn-dispatch/run-<id>/<name>` (`main`, `broker`, `models`, `pr-<n>`), `<id>` a uuid whose lock file, `<git common dir>/zn-dispatch-runs/<id>.lock`, a helper holds for the process's life (`runner.holdLock`); the wrapper fetches into `refs/zn-wrap/<id>/main` and deletes it. `freshMain` returns the sha and the run keeps it (`guard.fresh`): the tripwire's "HEAD moved only forward along main", the gates' merge base and the registry reads use that sha, never a ref read later. A fetch is retried three times with back-off, as `publish.commit` does; one that still fails stops the run as a tripwire whose detail says so ("could not be fetched … (after retries: the network?)"), and `retry` clears it. The run deletes its refs at its end (`dispatcher.main` always), and every run's start and `vet` delete the refs of runs whose lock nobody holds (`sweepRefs`: a lost run's leftovers).

**The watermark and the tripwire** (the user's decisions "Bot token, no bypass", "Persisted watermark" and "Keep same user, accept detection"; review 001 F3, review 002 F4, review 003 F2, F3, F6, F9). **What the dispatcher pins** at its start and holds in memory for the whole run (`guard`): origin's fetch and push URLs (`git ls-remote --get-url origin`, `git remote get-url --push origin`), the configuration that resolves them (`git config --get-regexp '^(remote\.origin\.|url\.)'`), and the watermark as it last read or wrote it. Every fetch and push of the run names the pinned URLs, never `origin`. **The watermark** (`dispatcher.watermarkPath`) is the last commit of `main` the dispatcher vetted, in `main-seen` under `$ZN_WATERMARK_DIR`, else `$XDG_STATE_HOME/zn-dispatch`, else `~/.local/state/zn-dispatch`, in a folder named for the repository (from `git rev-parse --git-common-dir`), with `origin-url` (the pinned URLs) beside it, never in the repository or a worktree; each item's `state.json` mirrors it (`watermark`). `dispatcher.vetMain(ctx)` fetches `main` fresh and runs `trackerstate.checkEach` from the watermark: each first-parent commit must be tracker state against its parent (sequestered, by the parent's registry) or a pull request's merge into `main` on GitHub (`ctx.prMerged`); a watermark that is not an ancestor of `main` (a rewrite) is unvetted. The file is shared by every dispatcher of the repository and by `vet` (review 004 F1): within a run the dispatcher vets from its own in-memory copy (`guard.mark`) to fresh `main`, whatever the file says, so another run's honest advance is never a trip, while a step that deletes or rewrites the file is still caught by the commits it pushed (W1, W2); the file is read only when the run has no copy yet (at its start), and a missing one then is never trusted (only `vet` writes one: no trust on first use). Writes go through `dispatcher.advanceMark` under an flock on the watermark's folder and only move it forward: written when the file is missing, equal or an ancestor; an older `main` (another run already wrote a newer one) leaves it; a diverged file trips; `vet` writes whatever is there. A file gone mid-run is written again, with a note on stderr. Each run re-vets commits another run already vetted while two overlap (a `diff-tree` and two `ls-tree` per commit). When every commit passes, the watermark moves to `main`; otherwise the first unvetted commit is named, the outcome is `tripwire` and the chain stops (exit 5). `dispatcher.guardStart` runs **at the start of every run**: origin's URLs as `origin-url` says (else "origin's URL changed since the last run"), the watermark not gone and not behind the item's mirror, then `vetMain`; `vetMain` runs again **before every model step and after every step** (once the step's group is gone and the broker's last requests are answered), so no interval goes unwatched: a process a step left behind (a `setsid` child) that pushes after the step's check is caught at the next run. After a step the tripwire (`dispatcher.tripwire(ctx, st, before) -> string?`) also checks origin's configuration against the pinned value, and the main checkout: its `git status --porcelain --untracked-files=all` and `git diff HEAD` are unchanged, and its HEAD moved only forward along `main`. Anything else sets the attempt's outcome to `tripwire` with what tripped it, keeps the step's spend, and stops every later run until the user looks and runs `./zn dispatch vet`, which lists every commit since the watermark with its verdict (tracker state, a pull request's merge into main, or "NOT VETTED, you accept it: …") and then moves the watermark to `main` and writes `origin-url`; `vet --dry-run` lists and writes nothing. **Known limits** (the user's "Keep same user, accept detection"): it detects a late push (a stolen credential, an absolute path to git, a process left behind) after the fact, at the next run, and never prevents one; nothing a step did is undone; a process left behind can rewrite `main-seen`, its mirror and `origin-url` between runs (to `main` as it is), and the next run then trusts them; a merge made with the user's credential is a pull request's merge and passes (G20); an agent can read the user's credentials and run `vet` itself. These are the user's, by rule (zz-rules).

After the attempts: z-ticket's id is the one issue on `origin/main` that was not there before (anything else fails "z-ticket made <n> issues"); a review's note is the review file it wrote (`design-review-NNN`, `review-NNN`). **Spend** (`record`): each attempt that spent tokens gets one row with its model id and minutes: a `code-review` row (code and stream modes) is printed as `record: ./zn commit -m "<id>: <note>" --phase code-review --time <m> --tokens <n> --model <id>` for the author (it rides with the review file, as today); a `deliver` row, or any row for an item that is not in the backlog, is kept in `state.pending`; every other row is `./zn spend <id> --phase <phase> --time <m> --tokens <n> --model <id> --note <note>` from the `zn-dispatch` worktree (synced first; `spend` changes nothing there and counts no prep lines from it). A failed publish keeps the row pending. **Who records what** (programme review F8): the dispatcher records each dispatched session's tokens and model; a step under the dispatcher records its own minutes and lines as its skill says, without `--tokens` for its own session; a dispatched reviewer is a session of its own, so its row is the dispatcher's and nothing is counted twice.

**A script step** (`scriptStep`): `./zn <command>` with forwarded output, in the main checkout (`z-ready`, `z-stop`, `zz-stats`) or the `raft-<id>` worktree; its outcome is its exit code.

**The run state** (programme review F10, for c0118): `.cache/dispatch/<id>/state.json` = `{ id, dir, mode ("chain"|"step"), step, reviewMode, cli, runtime, model, run: { pgid, lockFile }?, worktree, startedAt, tokens, outcome, detail, follows, merged: [pr], pushed: [sha], history: [{ step, cli, runtime, model, outcome, detail, tokens, minutes }], pending: [{ id, phase, tokens, model, minutes, note }] }`, written through `sh.writeReplacing`; beside it `lock` (the run lock), `run.lock`, `pid`, `stdin`, `stop`, `gh/`, `questions.md` (from a step), `answered-<n>.md`; and a folder `<step>-<mode>-<id>-<n>/` with its own `state.json` and files for each step a step dispatched (a review its author started: review 001 F5), claimed with a plain `mkdir` (never `-p`) and retried at `n + 1`, so two started at once get two folders (review 002 F11). All ignored, in the main checkout (AGENTS.md's ignored-files list names `.cache/dispatch/`). Outcomes: `running`, `ok`, `failed`, `quota`, `cap`, `cap-unknown`, `stalled`, `stopped`, `tripwire`, `lost`.
- **One dispatcher per item** (review 001 F4): a top-level run takes `<id>/lock` with an flock held by a helper process (`runner.holdLock`) that lets go when the dispatcher ends or dies, so a live run refuses a second ("… is being dispatched by another live ./zn dispatch") and a dead one frees the lock at once. A run that finds the state `running` with the lock free knows its dispatcher died: the step is marked `lost` and nothing is resumed; only `retry` goes on. A nested step uses its author's lock.
- `status <id>` prints every state under the folder; `stop <id>` writes each run's stop marker and kills its group only when `runner.sameRun` still holds (the supervisor holds the run's flock; a group id that is not a whole number above 1 is never signalled); a `running` state whose run lock is held but whose group isn't up yet (the step is starting) keeps its marker and says "stop requested", and only a state whose lock is free is marked `lost` (review 002 F10). The stop marker is cleared before the state says `running`, never after, and the runner, finding one, returns `stopped` without starting the CLI; `retry <id>` takes the lock, keeps `questions.md` as `answered-<n>.md`, clears the outcome and reruns the same step (a one-step run, with its review mode) or the chain, on the same order.

Facts come only from tracker state, never from a model's prose (F3): origin/main's document (`where`, effective `status`, `design:`, `raft:`), the run state (`last`, `ownClaim` = this dispatcher ran z-design on it, `questions`), the rafting worktree's `raft:` line (`localRaft`), `./zn lessons --uncovered <id>` in the last step's worktree, the PR the item's state points at through `ctx.prView` (`prep-<slug>` while preparing, `raft-<id>` while prepared and raftless, `<R>-<slug>` while active; `green` = every check SUCCESS, NEUTRAL or SKIPPED, and at least one), and the item's **settings from its own walk** (`dispatcher.settings(id)`: `models.settings` over the walk to the item's folder; review 001 F7). A one-step run's outcome is not the chain's, except `tripwire` and `lost`, which stop every later run until `retry`.
The rule, in order (each a row of the table):
1. `questions.md` → stop 3, "needs the user" (F4; the scope escalation of the approved plan).
2. The last step ended `tripwire` → stop 5.
3. The last step ended `failed`, `cap`, `cap-unknown`, `stalled`, `stopped`, `lost` or `quota` (every CLI) → stop 1, naming `./zn dispatch retry`.
4. The last step was z-design, z-raft, z-run or zz-review and `lessons --uncovered` lists a finding → stop 1 (the approved plan: the chain never passes a review step with an unharvested finding).
5. A step that ended ok but moved nothing → stop 1: z-design and the issue is still `new`; z-design and no prep PR; raft-plan and no `raft:`; z-ready and the raft not active; z-run and its PR still a draft.
6. No item: with a description → z-ticket; else stop 1.
7. An issue: done → stop 0; with a `raft:` on origin and prepared or active → follow the raft; `new`, or `preparing` by this dispatcher → the prep gate when it has a PR, else z-design; `preparing` by another terminal → stop 1; prepared and `design: ready` → the rafting gate when it has a PR, else `raft-plan` (script, in `raft-<id>`), then z-raft on the raft it named; anything else → stop 1.
8. A raft: done → stop 0 after writing the pending rows (`spend <R> --phase deliver`); prepared in the backlog → `z-ready` (script, main checkout); other backlog states → stop 1; active → z-run until its PR is open and not a draft (`./zn done` ran), then the **run gate**.
9. **Gates.** A closed PR → stop 1; a merged PR that origin doesn't show yet → stop 1 ("./zn sync"). `prep` and `raft` are passed by the dispatcher itself only when the item's `auto_merge` names them, the PR is not a draft, green and mergeable, and its head is the gate's own tracker state (review 002 F6, review 003 F5; `dispatcher.judgePr`, before the chain decides): the dispatcher fetches `refs/pull/<n>/head` from the pinned URL into `refs/zn-dispatch/run-<id>/pr-<n>`, refuses unless it equals `headRefOid`, and judges `merge-base(main, head)..head` with `trackerstate.check`, sequestered, plus the gate's narrower rule: a prep PR only paths under the issue's own folder on `origin/main` (whose own sequestered files it may change) and skill lessons (`<z-nile or project>/skills/<skill>/lessons/<name>.md`); a rafting PR only its own items' files (the issue, a raft it adds and that raft's `issues: [...]`, and `z-nile/next`), never another item's sequestered files (a block-style `issues:` list parses to no members, so such a PR waits for a human: fail closed); never a `.models.toml`. gh's `files` is never read (a rename's source is missing there, and it stops at 100). An unknown head never merges. **Only the dispatcher merges**, with the real `gh` on the real PATH and the user's credential, pinned to the head it checked (`gh pr merge <pr> --squash --match-head-commit <head>`, so a push to the branch after the check, by the bot or anyone, voids the merge and the next run looks again), records the PR in `state.merged`, then `./zn sync`. A prep that also changes, say, an architecture map waits for a human (fail closed). An unset `auto_merge`, or settings that can't be read, mean no auto-merge (fail closed; the root file sets `["prep", "raft"]`, and an item's own `auto_merge = []` wins). Otherwise stop 4, naming the PR and why. The **run gate is always a human's** (stop 4, "ready to merge"): z-run's Phase 6 is skipped under the dispatcher (F3). After the human merges, `./zn dispatch <R>` writes the run's pending rows.

### 7. The git and gh wrapper: a convenience layer (`z-nile/bin/git`, `z-nile/bin/gh`, `z-nile/engine/wrapper.luau` pure, `wrap.luau` its entry)
The boundary is the agent's credential, the server's protection and the watermark (the user's decisions). The wrapper catches honest mistakes early and with a clear message, and it is hardened anyway (review 001 F1, F2; lesson zz-arch/guards-decide-from-the-tools-resolution):
```lua
wrapper.splitGit(args) -> (globals, command?, rest)   -- git's own options (values included) before the command
wrapper.parsePorcelain(text) -> { Update }            -- `git push --dry-run --porcelain`'s `<flag>\t<src>:<dst>` lines
wrapper.decidePush(PushFacts) -> Decision             -- main updated only with tracker state, never deleted
wrapper.PLUMBING                                      -- send-pack, http-push, receive-pack: refused
wrapper.splitGh(args, aliases) -> words               -- gh's global options skipped, an alias expanded
wrapper.decideGh(args, aliases) -> Decision           -- an allow-list of commands; gh api reads and comments
wrapper.parseGhAliases(text)                          -- `gh alias list`'s lines; a shell alias expands to "!"
```
- **Routing.** `z-nile/bin/git` sends to `wrap` every invocation that names `push`, `send-pack`, `http-push` or `receive-pack`, carries any `-c` or `--config-env`, or whose command word is an alias (`git config --get alias.<word>` with the real git); everything else is the real git at once, so the tracker's many git calls cost nothing. `z-nile/bin/gh` sends every call to `wrap`. Without `ZN_REAL_GIT`/`ZN_REAL_GH` a shim exits 2 rather than guess.
- **git push.** `wrap` resolves an alias with the same global options (a shell alias is refused), refuses plumbing, then asks git itself: the same options and arguments with `push --dry-run --porcelain` (without `-q`, which would silence it; a dry run that doesn't end with `Done` refuses). For every update whose destination is `refs/heads/main` (whatever spelling, refspec, wildcard, `push.default`, `remote.<name>.push` or `--all`/`--mirror` produced it), it fetches the remote's `main` into `refs/zn-wrap/<id>/main`, a private ref, and passes the push only when the change from the merge base to the source is tracker state by that fresh main's registry (`trackerstate.check`, sequestered: §5's one definition, the broker's); a deletion of `main` is refused. The local `refs/remotes/<remote>/main` is never read.
- **gh.** Allowed: `pr create|view|comment|ready|edit|list|checks|diff|status|close`, `issue view|list|comment`, `run view|list|watch|rerun|download`, `workflow run|view|list`, `release download|view|list`, `repo view`, `auth status`, and `gh api` reads plus `POST` to `repos/<o>/<r>/issues/<n>/comments` or `…/pulls/<n>/comments`; a GraphQL query is allowed unless it is a mutation. Everything else is refused: `pr merge` (however spelled: `-R o/r pr merge`, an alias), `alias set`, `repo edit`, any other API write (`-X`/`--method`/`-X<VERB>` other than GET, or fields without a method). A spec walks every `gh` command the skills name against this list (the merges are the dispatcher's and a human's).
- `$ZN_REAL_GIT push …` with the user's credential gets past the wrapper by design; the watermark is what sees it, at the latest at the next run.

### 8. Branch protection and the agent credential: steps for the user (never run by an agent)
The user's decision "Bot token, no bypass" makes the server's half real: the agent's credential can't merge or bypass, and only the user (the repository admin) bypasses, for tracker-state pushes, which only the dispatcher's broker or the user's own `./zn` makes. Implementation step 9, for the user (each an admin action on GitHub or the user's machine; no agent runs them):

### Scalability
- A step resolves at most one walk per member (a handful of small TOML files); `facts` reads one origin document, one `gh pr view` and one `lessons --uncovered` per chain action; a chain is capped at 30 actions.
- The runner polls every 50 ms and buffers only the current line and 4 KB of stderr, whatever the session's length; usage is summed incrementally.
- The wrapper adds a Lune start (~0.1 s) to every `gh` call and to a git `push`, plumbing push, `-c`, `--config-env` or alias (plus one `git config --get alias.<word>` per git call to tell); a push also costs a dry run and a fetch of `main`. Every other git call goes straight to the real binary.
- The broker answers within a 50 ms tick; each request costs one fetch and one push. The watermark costs a fetch, a `diff-tree` and two `ls-tree -r` per commit `main` gained since it (a `gh api` call for a code commit), at a run's start and before and after each step; the broker's push a fetch and the same per commit of the request; a gate a fetch of the PR's head and one judgment.

### Maintainability
- One pure module per concern: the stack (`models`), the steps, prompt and chain (`dispatch`), the stream formats (`adapters`), the push and merge rules (`wrapper`); the impure parts (`runner`, `dispatcher`, `wrap`) only gather facts and start processes. A new runtime is one adapter entry and one row in `models.RUNTIMES`; a new CLI is one entry in `models.CLIS`.
- The chain reads tracker state only, so it can be resumed from any point by running it again.
- The CLIs' observed stream lines are pinned in the adapters spec; a CLI that changes its format fails that spec, not the user's night.

### Usability
- `--dry-run` everywhere: the step's CLIs in order with model, rank and cap, or the chain's next action.
- Every stop says why and what to run next (`retry`, the PR number, the questions file). Exit codes: 0 done, 1 failure, 3 needs the user, 4 at a merge gate, 5 the tripwire (then `./zn dispatch vet`, the user's).
- One file says which model runs what, and a project or an issue overrides one key without copying the rest.
