# c0118: Board per project with review graphs

## Problem
The tracker board is one page of every raft and issue. It cannot show two games without mixing them. It has no picture of the pipeline, and no graph of how many design reviews and code reviews a week of landed rafts took, or which model spent the tokens on those reviews.

The new board lists every project in `projects.toml` as a tab on the left, `z-nile` included. One project is selected. Its columns are ticket, design, raft, ready, run, and done. Each issue is a card. A raft is a band behind its members. Done cards stay 24 hours, adjustable from 1 hour to 30 days. Click a card for the worktree, the PR, the checks, the model, and the spend. The only actions are stop, retry, and open. Two charts use their own range, 90 days by default, open to all history: review rounds by week, and tokens by model for `design-review` and `code-review`.

Decided with the user (2026-10-20): stop, retry and open work from the page. The board is served by a local server (localhost only) that shows live state and runs those actions; the old board is replaced.

Decided with the user (2026-10-20), from the programme review:
- "Carry navigation and Stats": the new board keeps the old board's navigation (views, search, id jump, rendered documents) and its Stats view (c0073), alongside the new tabs, cards and the two charts.
- "One page, two modes": `zn board` writes a static page with embedded data (the CI artifact and the main checkout's refresh), and `zn board --serve` serves the same page with live polling and the actions.
- Scope decision (user, 2026-10-20): "Split: static board, then server": c0118 is the static board (project tabs, columns, cards, raft bands, the done window, both charts, navigation and Stats). The localhost server, its live worktree, PR and checks data, and the stop, retry and open actions move to c0121.

## Non-goals
- Replacing `tracker.sh board` until this page covers the same navigation.
- Editing the workflow from the canvas. The page reads the tracker, worktrees, and GitHub.
- Starting a model. Stop, retry, and open call the dispatcher from c0117.
- (Moved by the Scope decision above, not cut:) the localhost server, live PR and checks data from `gh`, and the stop, retry and open actions are c0121's. This page leaves c0121 one seam to fill (Design §9).

## Solution
- Draw the page from that project's tracker documents, `git worktree list`, and `gh`.
- Count `design-review-NNN.md` and `review-NNN.md` on rafts that landed that week.
- Split spend tokens by the model id c0117 records. A row with no model is the unrecorded line.

Added in prep (detail after the captured bullets, nothing above changed):
- `gh` is read only by c0121's server (the Scope decision moves live PR and checks there). The static page reads the tracker documents, `git worktree list`, the branch names and HEAD's commit time, all local, and says on each card that PR and checks are live on the served board.
- "Landed that week" is the raft's first arrival in `done/`, in UTC, from history; a raft's rounds are its own folder's, its members' and those of every raft retired into it, each file once (c0116 puts z-design's reviews on the issue).
- "Ready" and "run" are told apart by the raft's branch (`<R-id>-…`, local or on origin) having a commit after the raft's latest arrival in `active/`: `start` and z-run create it after `ready`, the CI checkout fetches it, and a branch left from before a `stop` launched nothing.

## Design
c0118 replaces the board page in place: the same command (`./zn board [--out PATH] [-O]`), the same output path, the same CI workflow and the same refresh of the main checkout's copy after every publish and `sync` (c0070), so nothing that builds or ships the page changes. What changes is what the page holds and shows. The old board's model, views, search, id jump, rendered documents, copy buttons and Stats section stay field for field (the "Carry navigation and Stats" decision); the new parts are added beside them.

--   initialView becomes "board".

`collect(root)` (one tracker folder, as specs pass) keeps working: one project named after the folder (or, for `<name>/.tracker`, the folder above), its `root` field that name, so no path from outside the tree reaches the page, and no facts unless given. `collect(nil, checkout)` reads every project of the checkout's registry in registry order and the checkout's own facts.

`history.luau`: `Parsed` gains `doneAt: { [string]: number }?` and `activeAt: { [string]: number }?` (issues and rafts). `history.logArgs(roots)` appends the compaction maps `ids.MAP_FILES` (`z-nile/compaction.txt`, `tracker/compaction.txt`) to the pathspec. `Parsed` also gains `warnings: { string }?` (a compaction map line that does not parse), which the board adds to `problems`. The log's commit line is `@@C %cI %H`. `history.parse(log, roots?, readMap?)` takes `readMap: (sha: string, path: string) -> string?`, which returns a compaction map's whole text as committed at that commit. `history.read` passes `git show <sha>:<path>`, run once per compaction commit (one so far, ever), so `parse` stays pure. The cache key is `v7 <HEAD> <roots>`.

### 3. The columns (programme review F6)
A total function of the issue's effective status (`status.effective`, the five words) and whether its raft is launched:

| effective status | raft launched? | column | the pipeline step behind it (c0115) |
|---|---|---|---|
| `new` | any | ticket | z-ticket captured it |
| `preparing` | any | design | z-design is designing it |
| `prepared` | any (a backlog raft, or no raft yet: c0116's "prepared, no raft") | raft | waiting for z-raft or z-ready |
| `active` | no | ready | z-ready moved it to `active/`; nobody launched it |
| `active` | yes | run | z-run (or `start`, or the dispatcher) made its branch |
| `done` | any | done | `done/` |
| anything else | | refused: `boardview.column: <word> is not an effective status (new, preparing, prepared, active, done)` | |

**Launched** (design review 001 F3) means a ref named `<R-id>-…`, as plain text anchored at the start, in `git for-each-ref --format=%(committerdate:unix) %(refname:short) refs/heads refs/remotes/origin` (an `origin/` prefix is dropped first), **whose tip commit is newer than the raft's latest arrival in `active/`** (history's `activeAt`, strictly later). `ready` publishes the move to `active/`; `start` then cuts the branch from that `origin/main` and makes its `tracker: start` commit, so a launched raft's branch tip is always later. `stop` leaves the branch as it is (zz-rules), so a raft stopped and readied again keeps a branch whose tip predates its new ready: that raft is ready, not run, until someone launches it (R0045's `R0045-narrow-hiscore-adapter-pins` is that shape today). When history gives no `activeAt` (a shallow clone, a raft claimed by the legacy `start`), any such branch counts. The CI workflow already checks out with `fetch-depth: 0`, which fetches every branch and its commits, so the artifact tells ready from run too. An issue in `active/` with no raft (legacy) is ready. `R00200-x`, `feature/R0020-x` and `xR0020-y` are not R0020's branch.

### 4. Raft bands
Within each column, `boardview.bands` groups the cards by raft, in raft id order, then the raftless cards; ids sorted. A raft whose members sit in two columns (an emergent issue already done, say) gets a band in each. The band's head is the raft's id link, title and status badge.

### 5. Done times and the done window (programme review F5)
- `history.parse` records, for every issue **and raft** (raft documents are now classified; a retired raft's folder `rafts/retired/` is no area), `doneAt`: the instant of the first commit in which the item arrives in `done/`, converted to UTC epoch seconds with `stats.seconds` (the offset `%cI` writes is honoured, so a Sunday 23:30 −07:00 landing is Monday 06:30 UTC). A move between roots (c0114, c0120) is a delete and an add in one commit, which history already reads as no change; a later return to `done/` keeps the first instant.
- **Compaction** (design review 001 F1 and F2). The 2026-10-05 compaction re-added every item under a new id and reused ids for other items (`R0100 R0010`: the done "Ghosts" became R0010 at the very path where "Foundation", landed 2026-09-28, had been). Following identity across that is what the lesson `zz-rules/item-history-spans-moves-and-compaction` forbids. So:
  - A commit is a **compaction** when it changes a map in place, or adds one whose content is not a map it deletes in the same commit. Moving the map (c0114's `git mv`, which lands on main squashed with R0043's own `done/` move) is no compaction; `trail.cuts` reads it with renames for the same reason. The rule is read from the log's own diff lines (the map paths are in the pathspec), so `parse` stays pure.
  - A compaction **ends the dated life of every id named on either side of a pair in the whole map it leaves** (design reviews 002 F1 and 003 F2): for `X Y` with X ≠ Y, both X and Y now name another item. Both halves matter: the new side is an id reused for another item (R0010), and the old side is an id renumbered away that the counter will hand out again (the dense renumbering puts every old id above the new count on the old side only; on the real log, dropping that half leaves 92 stale dates, R0030 and R0040 among them). The map is **read whole at that commit** (design review 004 F1): `readMap(sha, path)` at the compaction commit's own sha and the path the commit's diff names (the file moved from `tracker/` to `z-nile/` since), through `ids.parseMap`, the map's one reader. `compact` writes the whole map each time with only that compaction's pairs, so the map as committed is exactly that compaction's renames. It is never the diff, which drops a pair repeated word for word from the last map, and never a rebuild from hunks, which needs every add and every removal right; three review rounds found holes in the diff-based forms. A pair an earlier map had and this map drops no longer renames: a kept id named only by an earlier map keeps its dates. Without a reader (a caller that passes none) or when a map can't be read, every item the commit touches is undated, with a warning. For those ids, `doneAt` and `activeAt` are cleared and the item's place after the commit is no arrival. A later arrival in `done/` dates it afresh (the item now named R0030 takes its own landing when it lands); a re-add straight into `done/` stays undated. A reused id at the same path shows in git as a change, which is why the map, not the kind of change, decides.
  - **An id the compaction keeps keeps its dates**, even when `compact` rewrites its document in place because the document names a renumbered id (`depends_on`, `raft:`, body text). Otherwise a second compaction would undate every kept item that names a renumbered one, and clear the `activeAt` of active rafts, so a branch left by a `stop` would launch them again.
  - **A map line that does not parse** makes the commit end the dated life of every item it touches (fail closed: an unreadable map means "reset"), and `Parsed.warnings` names the commit; the board adds it to `problems`.
  - `closed` and `spells` stay issues only and exactly as before (Stats reads them; c0073 pins them).
- **Undated done items.** A done item that history leaves undated (a compaction ended its dated life, or there is no history at all: a shallow clone) is dated by the newest row of its own `spend.md` (a raft by its members' newest row), a field no id change rewrites, and marked `doneFrom = "spend"`; a raft's rows end at its `done` commit (phase `deliver`), so the date is the landing to within the delivery. An item with neither is undated: hidden in the done column, absent from the charts. The model's `history` says whether git history was read, and the page says so when it was not (§8).
- `activeAt` is the latest commit in which the item arrives in `active/` from elsewhere in its current life (a move between roots inside `active/` is no arrival); §3 uses it.
- The cache key is `v7` so no cache from before these rules is reused.
- **As-of time.** The page is a snapshot: `asOf` is HEAD's commit time (`git log -1 --format=%ct HEAD`), so two builds of one tree are byte-identical (c0042, c0073 and c0070 pin that). Each done card carries `age = max(0, asOf − doneAt)`. The page shows a done card while `age ≤ window`; the window select offers 1 h, 3 h, 6 h, 12 h, 24 h (selected), 2 d, 3 d, 7 d, 14 d, 30 d. Decided with the user (2026-10-23): see G1. c0121's server passes its own `asOf` (the request time) through `facts`.

### 6. Review rounds by week (programme review F7)
- A raft's rounds are the `design-review-NNN.md` and `review-NNN.md` files of: its own folder; every issue whose `raft:` names it (z-design's reviews live on the issue, c0116 §6); and every retired raft whose `retired:` names it, followed through chains (R0018 retired into R0019, retired into R0010, counts for R0010; at most 100 hops). Each path is counted once (`boardview.rounds`). `design-refute-*`, `refute-*`, `stream-review-*` and `harvest.md` are not rounds.
- `metrics` counts its rounds through the same `boardview.rounds`, so the chart and the tables share one rule (design review 006 F3). c0116's metrics has two counters, and both call it over a folder's file paths: `designRoundsIn(dir)` (its design count, which feeds the per-issue "Design rounds per issue" table, `raftDesignRounds` (the raft's folder plus each member's, through their `raft:` lines) and the retired rafts' own rows from `retiredRafts()`) and `codeRounds(dir)` (its code count, the raft's folder). Neither keeps a round-file pattern of its own, which `metrics.spec` pins in the source (their outputs can't tell a copy from the shared rule). The tables' scopes stay c0116's, unchanged: the raft's folder plus members for design, the raft's folder for code, retired rafts as their own rows.
- The chart: for each project, the rafts in its `rafts/done/` with a `doneAt`, bucketed by the UTC ISO week of `doneAt` (Monday labels, "Oct 19"), two stacked series "Design reviews" and "Code reviews". Every week from the range's start to the as-of week has a value (0 when nothing landed). The range starts at `asOf − days` (a raft landing exactly then counts), or at the earliest landing for all history.

### 7. Tokens by model
- Rows: every issue's `spend.md` in the project, read with `ledger.parse` (one reader per format; the old board's private seven-column reader is gone). A raft's `spend.md` is a summary, never read for rows. Kept rows: phase `design-review` or `code-review`, `tokens > 0`, dated (`rowInstant` of `when`, UTC minute) in the range and not after `asOf`.
- One series per model id, largest total first, ties by id, at most 8; the rest summed as "other models"; a row with no model is the "unrecorded model" series, always last. Tokens are split across a raft's members when recorded (`spend.attribute`), so the sum over issues counts each token once.
- A tall axis is scaled to "k tokens" above 10,000 a week and "M tokens" above 10,000,000 (prep found the raw axis labels clipped at millions).
- The charts are drawn by the existing `chart.svg` (stacked bars), one SVG per project, chart and range key, embedded in the model; the page shows the selected range's. Series colours are CSS classes (`ser-design`, `ser-code`, `ser-m1`…`ser-m8`, `ser-other`, `ser-unrecorded`) with light and dark values.

### 8. The page
- **Layout**: header (title, the view switch Board · Rafts · Issues, Stats, search); then the project tabs on the left (`#projects`, one button per registry project, the selected one marked), then the Board (`#board`: the done-window and range selects and the as-of time, the six columns, the two charts) or the list (`#list`), then the pane (`#pane`, the document). On the Board the pane is 30em wide.
- **Opening**: the first project in the registry, the Board view (`initialView = "board"`). Decided with the user (2026-10-23): see G2.
- **Every view shows the selected project only**: the Board's columns, and the Rafts and Issues lists (filtered by each item's `project`). The Stats section stays as it is: the whole repository. Decided with the user (2026-10-23): see G3.
- **Keys**: Left and Right cycle Board, Rafts, Issues; Up and Down move through the visible cards in column order, or the list; `/` focuses the search.
- **Search and links**: an id jumps to it in its own project (the tab follows). On the Board an issue that is a visible card stays on the Board and is selected; anything else opens in Rafts or Issues as before. A project name, typed or as `#<name>`, selects that project; selecting a tab sets `#<name>`.
- **A card click** selects it and shows the pane: the old document pane plus a "Run" block: column, model (the distinct model ids in its spend rows, else the dispatcher state's model, else "unrecorded"), spend (minutes, tokens, lines), the dispatcher's state from `.cache/dispatch/<id>/state.json` (step, outcome, model, and "waiting for answers (questions.md)" when that file exists; c0117 §12 hands this to the board), the raft's branch and worktree, and "PR and checks: live on the served board (`zn board --serve`, c0121)". A raft pane gets the same block with its members' spend summed and its review rounds.
- No git history (a shallow clone, `model.history == false`): the done column says "history unavailable (shallow or no git): done times from spend rows", and the chart area adds "history unavailable (shallow or no git): landings dated from spend rows". No as-of time at all: the done column says "no as-of time: done cards have no age" and the chart area "no as-of time: no charts".

### 9. One page, two modes: the seam for c0121
`zn board` writes the page; c0121's `zn board --serve` serves the same `board.render` output and polls. The page defines `window.znBoard.load(model, statsHtml?)`: it replaces the model (and, when given, the Stats section's HTML, which `board.render` otherwise draws once), re-indexes, and keeps the view, the project (unless it is gone), the selected item, the done window and the range, then re-renders (design review 001 F5; `page.spec` pins all five). c0121 builds each polled model with `board.collect(nil, root, facts)` where `facts.asOf` is the request time, and fills each item's reserved `pr` (`{ number, url, state }`) and `checks` (`{ state, url? }`), nil in every model c0118 builds: the card then shows the PR link and the checks state (an issue shows its own, else its raft's PR and checks) instead of the "live on the served board" sentence. What c0121 still adds is its own: the server, `/api/state`, the polling, the actions and their guards (its Problem carries the programme review's F3, F4, F8, F9 and F11). The static page never calls `load`. Nothing in c0118 opens a port, calls `gh` or runs an action.

### 10. Facts
`board.readFacts(dir)` runs, in `dir`, `git log -1 --format=%ct HEAD`, `git for-each-ref --format=%(committerdate:unix) %(refname:short) refs/heads refs/remotes/origin` (each tip's commit time, for §3) and `git worktree list --porcelain`, and reads `dir/.cache/dispatch/<id>/state.json` (top level only, ids only; `step`, `outcome`, `model` strings; anything else ignored) and the presence of `questions.md` beside it. A git call that fails leaves that fact empty; a state file that does not decode is skipped. It writes nothing, fetches nothing and needs no network: no `gh`. Its one `.cache` line (`local home = \`{dir}/.cache/dispatch\``) is on the reviewed list in `tests/lib/cachepaths.luau` as a read ("nothing is written"), as c0077's scan requires.

### Scalability
- Per build: the existing history log (one `git log`, cached by HEAD under `.cache/tracker-history.json`, plus one `git show` per compaction commit when the cache is cold: one in the repository's life so far), three more git calls (`log -1`, `for-each-ref`, `worktree list`: about 20 ms together), one read of each issue's `spend.md` (cached in-process, read once per build though both the card and the charts use it), a `readDir` of each raft and member folder for review files, and the dispatcher's state files. Linear in items; measured 0.47 s for the real tree (two projects, 145 items) against the old board's 0.43 s (programme review's timing).
- The page: 16 small SVGs (2 projects × 2 charts × 4 ranges, about 3 KB each) and a few fields per item add about 80 KB to the 2.93 MB page (3.01 MB). Each project adds 8 SVGs. The done column holds every done item's id; the page filters by age in the browser, so a wider window needs no rebuild.
- `boardview` is O(items + weeks); `tokensByWeek` sorts the models once.

### Maintainability
- A new project is a `[[project]]` in `z-nile/projects.toml`: it gets a tab, columns and charts with no code change. A new pipeline column is one row in `boardview.column`, one entry in `COLUMNS`/`LABELS` and one CSS-free label in the page. A new range or window is one entry in `RANGES` or `WINDOWS`. A new review kind is one pattern in `boardview.rounds`, which `metrics` shares.
- One reader per format: spend through `ledger.parse`, the registry through `projects.load`, history through `history.read`.
- Everything the page decides that could be wrong is in `boardview` (pure, unit-specced); the page's script only filters by `age ≤ window` and by project, and both are specced through node.

### Usability
- The command line is unchanged (`./zn board [--out PATH] [-O]`), so no exhaustive list changes: the main checkout's list already names `sync`, which rebuilds the board; `board` stays in `READ_ONLY`; the usage text is unchanged. `--serve` is c0121's and is not accepted yet.
- The page opens where the user looks first (the first project's pipeline), keeps every old key and link, and a project is one click, one `#name` or one search away. Cards say their type by colour and word, as the old rows did.
