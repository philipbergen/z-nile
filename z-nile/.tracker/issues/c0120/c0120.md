# c0120: Move pickman into pickman/

## Problem
The game lives at the repo root beside the tooling, so a second game cannot sit beside it and a developer cannot tell the game from the tracker. The user (2026-10-20) wants each project to hold its own issues in its own `.tracker/`, and pickman's files moved into `pickman/`: its `src/`, its tests, its Rojo projects and places, and its tracker items into `pickman/.tracker/`.

Decided with the user (2026-10-20):
- The move raft is readied only when no raft is active. Prepped rafts move with the tree.

From the plan the user approved (2026-10-20): specs are promoted into the project they belong to, and each project has its own gate.

Decided with the user (2026-10-20), from the programme review:
- "Run checks from the project dir": `zn check` runs a pickman item's `check.sh` with the working directory at `pickman/`, so the paths sequestered files name still resolve. A spec asserts that every path each `check.sh` names exists. No sequestered file changes. (Amended for finished items by the 2026-10-21 decision on Guess 3, below.)
- "No active raft, no open branches": c0120 is readied only when no raft is active and no branch or worktree changes `tracker/`, `src/` or `tests/` (compact's busy-branch check). Afterwards a gate check fails if the old root reappears.
- R0030 (c0083) and R0039 (c0075) are re-prepped after c0120 lands.

Decided with the user (2026-10-21), on this design's guesses (each in the Guesses section, in the user's words):
- z-nile gets a home of its own, `z-nile/`: its specs, runner and harness move into `z-nile/tests/`, and the repository root belongs to no project (Guess 1, "z-nile/ is its home").
- c0120 rewrites the paths it breaks in **finished** items' `check.sh` files, in the edits commit, and AC11 checks finished files too (Guess 3, "Rewrite them too"). This is the user's one exception to "sequestered files never change", for finished items only; c0114 has the same one.
- CI runs one gate job per project (Guess 6, "One job per project").
- A project's `scripts/check.sh` forwarder and a raft's RC0 run that project's gate only (Guess 7, "pickman's gate only").
- The tracker fixture specs move to the final layout, each an override (Guess 11, "Move fixtures to new layout").

## Non-goals
- Moving the tracker engine, skills and build into `z-nile/`, and z-nile's own issues: c0114.
- Renaming skills: c0115.
- Editing an **unfinished** item's `check.sh` or any acceptance spec (the decided line). R0012's RC1 is the one consequence (§12, Guess 4); finished items' `check.sh` files are rewritten (§12).
- Removing c0114's root forwarders and shims (`scripts/`): c0114's forwarder-removal raft.

## Solution
- `git mv` the game and pickman's tracker items in one change, with history pathspecs that still see the old paths.

(Added in prep, after the captured bullet.)
- Every project has a **home**, the folder that holds its `.tracker/`: `pickman/` and `z-nile/`. A project's `check.sh` files and specs run in its home. The repository root belongs to no project.
- The root's `tests/` goes away: pickman's specs, helpers and promoted folders move into `pickman/tests/`, and the tooling's (the shared runner and harness, the tooling specs, the fixtures, z-nile's promoted folders) into `z-nile/tests/`.
- `ac.sh` runs each `check.sh` from its project's home, and the one runner (`z-nile/tests/run.luau`, required by `pickman/tests/run.luau`) runs from a home, with that home's `.luaurc`, `.cache`, lock and jail. Every path an unfinished sequestered file names resolves where it was written for. c0120 rewrites the paths its moves break in finished `check.sh` files, and a spec proves every path in every `check.sh` resolves.
- Each project has its own gate (`z-nile/check.sh --project <name>`, `<home>/check.sh`) and its own CI job. Promotion puts a member's specs in its project's `tests/acceptance/`.
- Readiness and resurrection: `./zn busy tracker src tests` lists what holds the old paths, and AC16 makes it a check. Afterwards `./zn audit` and a promoted gate spec fail if `tracker/` holds anything but the counter file, if the root's `tests/` or pickman's old places come back, or if a promoted folder sits outside its item's project.

After c0120 the root holds no project's files: `.luaurc`, `rokit.toml`, `selene.toml`, `stylua.toml`, `.gitignore`, `zn`, `AGENTS.md`, `CLAUDE.md`, `SETUP.md`, `.github/`, `.claude/`, and c0114's forwarders and shims in `scripts/` (with `scripts/hooks/`). No `tests/` is left at the root.

**Which promoted folder moves where.** A promoted folder belongs to its item's project: `tests/acceptance/<id>` moves into `<home>/tests/acceptance/<id>`, where `<home>` is the home of the project whose root holds `./zn find <id>` (`tracker/…` is pickman's before c0120; `z-nile/.tracker/…` is z-nile's). Every one of the 74 promoted folders on c0114's tree (31 pickman, 43 z-nile, c0114's own included) has an item. The rule is mechanical, it is the one `done` follows (§7), and it is what `audit`'s `misplaced-spec` checks (§9). A spec that tests another project's code from its item's folder is a **cross-project spec**: it stays with its item and reaches the other project's files by a path from its own home (c0041's graph specs read `../z-nile/tests/fixtures/graph`, f0061's lobby spec reads `../z-nile/check.sh`). Changes under the shared runner, harness or `z-nile/lib/` force every project's full run (§6), so these run whenever the tooling they test changes.

The moves are written down here, not in a committed script. On a tree with c0114 done, the `git mv` lines of the table above, then the promoted folders:
```bash
for d in tests/acceptance/*/; do
  id=$(basename "$d"); at=$(./zn find "$id")
  case "$at" in
    tracker/*) home=pickman ;;
    z-nile/.tracker/*) home=z-nile ;;
    *) echo "no project for $id ($at)"; exit 1 ;;
  esac
  mkdir -p "$home/tests/acceptance"; git mv "${d%/}" "$home/tests/acceptance/$id"
done
```
`./zn find` is run from a project's folder or with `--project` (c0114 Guess 3); `find` searches every root whatever the project. The result is the renames-only commit (JC1).

### 2. Homes
A project's **home** is the folder that holds its root: `projects.homeOf` gives `dirname(root)` for a root `<home>/.tracker`. `z-nile/projects.toml` after c0120:
```toml
retired = ["tracker"]

[[project]]
name = "pickman"
root = "pickman/.tracker"

[[project]]
name = "z-nile"
root = "z-nile/.tracker"
```
There is no `home` key: the home follows from the root, the folder c0114 already uses to tell the project from the current directory (c0114 Guess 3). After c0120, `pickman/` and anything under it gives pickman, and `z-nile/` gives z-nile; at the root, a command that needs a project refuses unless `--project` names one (c0114).

`z-nile/engine/projects.luau` (c0114's one reader) gains:
```lua
projects.homeOf(reg: Registry, path: string): string    -- the home of the project whose *current* root holds the
                                                         -- repo-relative path (by whole prefix "<root>/"); "." (the
                                                         -- root, which belongs to no project) otherwise
projects.acceptanceRoots(reg: Registry): { string }      -- "<home>/tests/acceptance", once each, in registry order
```
Parser rules, added to c0114's (which refuse an unknown key, a repeated name or root, a bad root shape, and a missing registry, c0114 Guess 4): a current root is `<name>/.tracker`, so a project's home is its own name, and `home` is an unknown key. The parser derives `Project.home` from the root, so every caller reads it as before; the legacy root `tracker` (before c0120) has the home `.`. A retired root carries no home.

`z-nile/roots.luau` (c0114's reader for the shell) gains two modes:
- `lune run z-nile/roots -- --projects` prints `name<TAB>home<TAB>root` per project, in registry order. `ac.sh`, the gate and CI's dispatch step read it, and nothing else in shell parses the file.
- `--luau-dirs [<name>...]` derives each named project's folders from its home: the home's `src/`, `tests/` and `scripts/` where they exist, the home itself for z-nile (its engine and libraries), and the project's root, always (c0114's rule; stylua skips hidden folders unless named). z-nile's also names the root's `scripts/` (Guess 13). An unknown name exits 2.

### 3. Checks run from their project's home
`z-nile/lib/ac.sh`, which every `check.sh` sources, works as follows:
1. Before any `cd`, it resolves the script bash runs (`$0`) to a physical path. **A sourced `check.sh` refuses** (review 001 F6): when the first `BASH_SOURCE` entry past `ac.sh` and its forwarder is a `check.sh` that is not `$0`, `ac.sh` exits 1 with `ac.sh: <check.sh> is sourced by <caller>: run a check.sh with bash, never source it`. An inline `bash -c 'source <ac.sh>; check …'` sources no `check.sh` and keeps working (c0034 uses one).
2. It changes to the repository root, checks the guard file and fences the **root** as before. `ZN_ROOT` is exported as the physical root.
3. It reads `lune run z-nile/roots -- --projects` and takes the home of the project whose root is a prefix of the `check.sh`'s root-relative path. The loop reads through process substitution, never a here-string (E5).
4. It fails closed. A `check.sh` under a `.tracker/` folder that no current root holds, or whose registry can't be read, exits 1: `ac.sh: <path> is under no project root that z-nile/roots lists: refusing to guess its home`. Any other `check.sh` (a fixture's loose script, a retired root's) runs from the root, as before.
5. **It fences the home** (review 001 F1, review 002 F1), with `pickman_home_fence "$ZN_ROOT/<home>" || exit 1` from `z-nile/lib/fence.sh`. Every home is now a folder, so every project's `check.sh` gets it. The fence is four steps, each a function, run in this order by both `pickman_fence` (the root's and the runner's) and `pickman_home_fence`:
   1. **Ceiling** (`pickman_fence_ceiling`): `<dir>/.cache` joins `GIT_CEILING_DIRECTORIES` (once). It touches no other variable, cannot fail, and runs first.
   2. **Refusals** (`pickman_fence_refusals`): reads only. A `.cache` that is a symlink or a file, or a sentinel `.cache/.git` that is a folder, refuses ("Stop and report this"), in every mode, never waived.
   3. **Environment** (`pickman_fence_env`). Its refusals are reads that come before any change: no ref-guard hooks outside the jail (c0114's `jailed` waiver unchanged), and **no repository found**. The protected repository (`real`, `git rev-parse --git-common-dir`) is read once through `_pickman_fence_git`: a clean `env -u` of every repository override and of the inherited ceiling, for that one read only. So no inherited `GIT_DIR` or `GIT_COMMON_DIR` redirects it (code review 001 F1, 002 F2), and no ceiling at the checkout's root hides the checkout from a home (code review 002 F1); the shell keeps its ceiling, which nested fences accumulate. A read that finds nothing refuses in every mode: an empty answer never means "nothing to protect". From its first change on it never returns early: it unsets the inherited overrides and sets the whole set again (`PICKMAN_FENCE_REAL_GIT`, `core.hooksPath`, `gc.auto`, `maintenance.auto`, the spec settings, `GIT_CONFIG_COUNT`), so whichever step refuses, the guards the shell inherited are never weaker than before.
   4. **Sentinel** (`pickman_fence_sentinel`): the writes. `mkdir .cache`, the sentinel by `rename(2)` (a link there is unlinked first), and `gh-none` in spec mode. It comes last, so a refused write leaves the environment fully guarded.

   `pickman_home_fence` differs from `pickman_fence` in one case only: the sentinel's write fails while all three of the runner's jail markers are set (`PICKMAN_TEST_JAIL=sandbox-exec`, `PICKMAN_FENCE_SPECS=1`, `PICKMAN_TEST_FENCE`) **and** `<home>/.cache` lies outside the run's own `.cache` (review 003 F2). That is the jail refusing a write outside the one place it lets a spec write: c0034's list mode lists every finished `check.sh` from inside a jailed run. It prints `fence: the jail refused <home>/.cache's sentinel; its ceiling and every other guard hold` and goes on. The waiver tests for the jail, never for "the write failed": every other failure refuses, and nothing hides the fence's stderr. **An outer sandbox must let every home's `.cache` be written** (testing skill, Jail): the waiver never keys on an outer sandbox's label (review 004 F1).
6. It changes to the home.

`pickman_guarded <dir>`, which the publisher asks, reads both ways: the clean read and the caller's own environment, which is how the caller's git will act. It answers `guarded` when either names a protected repository, exits 1 (treated as guarded) when either read fails or is empty, and answers `unguarded` only when both name unprotected repositories (code review 003 F1). The runner's own reads (`tests/lib/fence.luau`'s `git()`: the tripwire's snapshot, the protected paths, the worktree list) strip the same overrides and the ceiling, and `fence.enter` refuses a checkout where git finds no repository (code review 002 F1).

**Every other guard tied to a folder** is the home's: the run's lock and jail (§4), the runner's unlinking of links at the top of `.cache` and `fixture.check`'s "under this run's `.cache`", the gate's sweep of every home's `.cache` (§6), `cachepaths` (covering `pickman/scripts` and `z-nile/scripts`), promote-check's copies (§7) and sync's prompt sweep (c0114). The tripwire's "a worktree appeared under `.cache`" counts a worktree under any `.cache` of the checkout.

`./zn check <id>`, `done`, `promote-check` and a raft's member loop all run `bash <dir>/check.sh`, so all of them get the home. From a home, the paths that unfinished sequestered `check.sh` files name resolve unchanged:
- `lune run tests/run`: the home's runner (§4);
- `tests/meta/architecture.spec.luau`, `tests/tooling/…`, `src/…`, `tests/unit/…`: the home's;
- `"$PWD/tests/acceptance/<id>"`: the item's promoted folder;
- `scripts/tracker.sh` and `scripts/check.sh`: the home's forwarders, below;
- git pathspecs: `git diff -- src/server` from `pickman/` means `pickman/src/server`.

AC11 proves it for every unfinished `check.sh` (§12 lists the exceptions).

**Paths the engine prints** (`find`, `members`) are relative to the folder `./zn` was run from: `zn` exports `ZN_CWD="$(pwd -P)"` before its `cd`, and the engine's `callerPath` makes paths relative to it (unchanged from the root, `.tracker/issues/f0104` from `pickman/`, `../z-nile/.tracker/…` for a z-nile item from `pickman/`, absolute from outside the checkout). R0035's `$(scripts/tracker.sh find "$1")/acceptance/…`, every raft's member loop and CI's dispatch step (§11) keep working.

**Forwarders in each home**, kept like c0114's root forwarders until every raft whose sequestered `check.sh` names them is done:
| path | its one command |
|---|---|
| `<home>/scripts/tracker.sh` (100755) | `exec bash "$(dirname "$0")/../../zn" "$@"` |
| `<home>/scripts/check.sh` (100755) | `exec bash "$(dirname "$0")/../check.sh" "$@"`: the project's own gate (Guess 7) |
| `pickman/check.sh` (100755, permanent) | `exec bash "$(dirname "$0")/../z-nile/check.sh" --project pickman "$@"` |

z-nile's gate entry is `z-nile/check.sh` itself, so in `z-nile/` the forwarder `scripts/check.sh` runs `../check.sh --project z-nile`: `exec bash "$(dirname "$0")/../check.sh" --project z-nile "$@"`. With no `--project`, `z-nile/check.sh` runs every project's gate (local runs, `land`, `setup.sh`).

**Templates.** A new `check.sh` runs from its home, so `z-nile/templates/raft/check.sh` names the root through `$ZN_ROOT` and its project's gate through `{{PROJECT}}`:
- `check "RC0: project gate passes (full)" "$ZN_ROOT/z-nile/check.sh" --project {{PROJECT}} --full`
- `for dir in $("$ZN_ROOT/zn" members {{ID}})`
- `"$ZN_ROOT/zn" promote-check {{ID}}`

`new raft` fills `{{PROJECT}}` with the raft's project. The issue template's comment says `# cds to the item's project home`. A `check.sh` names its own item folder through `$HERE` or `./zn find`, never by a literal home-relative path.

### 4. The runner runs from a project's home
`z-nile/tests/run.luau` is the one runner. Each other home's `tests/run.luau` is a one-line `return require("../../z-nile/tests/run")`, so `lune run tests/run` in `pickman/` runs the shared runner with `pickman/` as its working directory. The runner:
- computes `ROOT` from its own location (`debug.info(1, "s")`, three folders up from `z-nile/tests/run.luau`) and `HOME_PREFIX` from the working directory: `"z-nile/"` or `"pickman/"`. **A run from a folder that is no project's home refuses** (`tests/run: <dir> is no project's home (z-nile/projects.toml)`); there is no `tests/` at the root to run anyway;
- loads a spec as `require(<path from the runner to the home> .. file)`, where a spec path is relative to the home, or absolute (stripped as before);
- collects `tests/` relative to the home, so each home runs only its own specs;
- re-runs itself as `lune run tests/run` (relative), the home's entry, and ends with `return nil` so a home can require it.

The fence runs with `here` = the home: the jail allows writes only in `<home>/.cache` (and the run's temp folder), the lock is `<home>/.cache/tests-run.lock`, and the tripwire snapshots the same repository. `tests/lib/fence.luau` sources `"<ROOT>/z-nile/lib/fence.sh"`, passing the root as `$4`; `protectedPaths(here)` adds the checkout's toplevel. `fence.sh`'s ref-guard hooks default to `git-hooks/` beside `fence.sh` itself.

So every project's specs, their relative `.cache/…` fixtures and their jail are their home's. A spec that needs the repository's toplevel (to copy the tooling into a fixture, or to read a document) asks git for it, and writes only under its home's `.cache` (`fixture.physical(".")` + `/.cache`). The homes have separate locks and `.cache` folders, so their suites could run together; the gate runs them one after the other. **Every gate proves its own guards**: `pickman/tests/meta/fence.spec.luau` is `return require("../../../z-nile/tests/tooling/repo-fence.spec")`; repo-fence scans the whole checkout from its toplevel and probes that the root, the root's `.cache` and the other homes are unwritable from the jail (E3).

**The harness.** `t` (every spec) and `renamed` are re-exported from `pickman/tests/lib/`. `sim`, `place` and `fakeengine` are pickman's. `fence`, `fixture`, `clone`, `cleanup`, `engine`, `trackerfix` and `cachepaths` are the tooling's. `tests/fixtures/graph` moves with the selector spec that requires it relatively.

### 5. Aliases and the require graph
`pickman/.luaurc`:
```json
{ "languageMode": "strict", "aliases": { "logic": "./src/shared/Logic", "shared": "./src/shared", "tests": "./tests", "scripts": "./scripts", "znile": "../z-nile" } }
```
`z-nile/.luaurc`:
```json
{ "languageMode": "strict", "aliases": { "tests": "./tests" } }
```
A home's `.luaurc` defines only what differs from the root's: every file resolves an alias from the nearest `.luaurc` that defines it, inheriting the rest from parents (Lune 0.10.5, luau-lsp 1.70.1). The root `.luaurc` keeps `languageMode`, `lune`, `znile` (`./z-nile`), `scripts` (`./scripts`, c0114's shims, which z-nile's code requires until the forwarder-removal raft), `logic` and `shared` into `pickman/src`, and `tests` into `z-nile/tests`: a worktree lies inside the main checkout, and an alias its own chain doesn't define resolves through the **main checkout's** `.luaurc` (U2, Guess 8), so the root defines every alias a project uses (Guess 15).

`z-nile/lib/graph.luau` matches that resolution: `graph.aliases(dir?)` merges every `.luaurc` from the filesystem root down to `dir`, a nearer alias replacing a farther one; `normalize` keeps a leading `..`; `@game` resolves through the nearest `default.project.json` at or above the file's folder; `affectedSpecs` marks each home's place library as changed when that home's `src/` or project files change. The graph is built over every home's `src/`, `tests/` and `scripts/`, and z-nile's code.

`pickman/tests/meta/architecture.spec.luau` keeps the game's rules and runs from `pickman/`. `z-nile/tests/meta/architecture.spec.luau` keeps the tooling's two: every require under the home's `tests/` resolves, and `--!strict` over z-nile's `tests`, its code and the root's `scripts` (`.tracker` aside).

### 6. Each project's gate
`z-nile/check.sh [--project <name>]... [--affected [--base REF] | --full | --plan]` is the one gate. No `--project` runs every project; each `--project` adds one; an unknown name exits 2. The projects come from `z-nile/roots -- --projects`.

For each picked project, with `p` its home:
| stage | reads |
|---|---|
| format, lint | `z-nile/roots -- --luau-dirs <name>` (§2) |
| Roblox types | `p/src`, from the home (`rojo sourcemap default.project.json -o sourcemap.json`, `luau-lsp analyze … src`), where the home has a `default.project.json` |
| Lune types | the home's `tests/` and `scripts/`, z-nile's code for z-nile, `--ignore='**/.tracker/**'` |
| builds | every `p/*.project.json`, into `p/.cache/check.rbxl` or `p/.cache/check-<stem>.rbxl`, through `build_place` |
| specs | from the home: `(cd p && lune run tests/run)`; in affected mode `lune run z-nile/affected -- --project <name>` selects, relative to the home |

- `--plan` prints each stage's reading and exits before writing anything.
- Each home's `.cache` gets the top-level-link sweep.
- `z-nile/tests/lib/cachepaths.luau` lists the new `.cache` lines and covers every home's `scripts/`.

`z-nile/affected.luau` (`--project <name>` prints that project's selection relative to its home, or `ALL`):
- The shared runner and harness (`z-nile/tests/run.luau`, `z-nile/tests/lib/`), `z-nile/lib/`, `zn`, the root's `scripts/` and the root configs (`.luaurc`, `rokit.toml`, `selene.toml`, `stylua.toml`) force every project's full run.
- A home's own `tests/lib/`, `tests/run.luau`, `tests/meta/`, `scripts/`, `.luaurc` or project files force that project's full run; the rest of `z-nile/` (the engine, the gate) forces z-nile's.
- A file at an old place (the root's `tests/`, `src/` or project files, a retired root) forces z-nile's full run, whose old-roots spec then fails (§9).
- A document under any current root selects nothing.

**What a project's gate proves** (Guess 7): `pickman/check.sh` and pickman's `scripts/check.sh` run pickman's stages only, and so does a pickman raft's RC0. A game raft's `done` no longer proves z-nile is green; CI's z-nile job does, on every push (§11). The same holds the other way: a z-nile raft's RC0 runs z-nile's gate, and the shared-harness rule above puts pickman's full run into CI's pickman job whenever the shared runner or harness changes.

### 8. The freeze: `./zn busy`
`./zn busy [<path>...]` is read-only and exits 1 when anything holds the paths, printing one line per holder:
- every raft active on `origin/main`, except the current branch's: `raft R0010 is active`;
- every branch, local or on origin, except `main` and the current branch, that changes the paths since it left `origin/main` (`compact.busyRefs(current, paths?)`): `branch <ref> changes <paths>`;
- every other worktree with uncommitted or untracked changes under the paths (`git --no-optional-locks -C <wt> status --porcelain -- <paths>`): `worktree <path> has uncommitted changes under <paths>`.

Without paths it guards `compact.guarded()`. It reads the last fetch and never fetches. AC16 can't fetch either: the ref guard refuses a fetch that has nothing new (captured as c0122). So Implementation step 11 runs `./zn sync --fetch` just before `check.sh`. The command that readies c0120 is c0114's engine, which has no `busy` (decided: Guess 5), so the person who readies c0120 checks by hand, read-only, in the main checkout: `./zn list active` lists nothing, and
```bash
git fetch -q origin; for r in $(git for-each-ref --format='%(refname:short)' refs/heads refs/remotes/origin); do
  case $r in main|origin/main|origin/HEAD|origin) continue ;; esac
  git diff --quiet origin/main..."$r" -- tracker src tests || echo "busy: $r"; done
git worktree list --porcelain | sed -n 's/^worktree //p' | while read -r w; do
  [ -n "$(git --no-optional-locks -C "$w" status --porcelain -- tracker src tests)" ] && echo "dirty: $w"; done
```
prints nothing.
