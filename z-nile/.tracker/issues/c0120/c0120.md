# c0120: Move pickman into pickman/

## Problem
The game lives at the repo root beside the tooling, so a second game cannot sit beside it and a developer cannot tell the game from the tracker. The user (2026-10-20) wants each project to hold its own issues in its own `.tracker/`, and pickman's files moved into `pickman/`: its `src/`, its tests, its Rojo projects and places, and its tracker items into `pickman/.tracker/`.

Decided with the user (2026-10-20):
- The move raft is readied only when no raft is active. Prepped rafts move with the tree.

From the plan the user approved (2026-10-20): specs are promoted into the project they belong to, and each project has its own gate.

Decided with the user (2026-10-20), from the programme review:
- "Run checks from the project dir": `zn check` runs a pickman item's `check.sh` with the working directory at `pickman/`, so the paths sequestered files name still resolve. A spec asserts that every path each `check.sh` names exists. No sequestered file changes.
- "No active raft, no open branches": c0120 is readied only when no raft is active and no branch or worktree changes `tracker/`, `src/` or `tests/` (compact's busy-branch check). Afterwards a gate check fails if the old root reappears.
- R0030 (c0083) and R0039 (c0075) are re-prepped after c0120 lands.

## Non-goals
- Moving the tracker engine, skills and build into `z-nile/`, and z-nile's own issues: c0114.
- Renaming skills: c0115.
- Moving z-nile's own specs, runner or test harness out of the root's `tests/`. The tooling's home is the repository root (§2), and its specs are promoted there, as now.
- Running each project's gate as its own CI job. CI keeps one `gate` job, which runs every project's gate (§6, Guess 6).
- Editing any sequestered `check.sh` or acceptance spec, finished or not (the decided line). Two consequences are recorded in §12 instead: R0012's RC1 and finished items' stale paths.

## Solution
- `git mv` the game and pickman's tracker items in one change, with history pathspecs that still see the old paths.

(Added in prep, after the captured bullet.)
- Give every project a **home** in `z-nile/projects.toml`: the folder its `check.sh` files and specs run in. Pickman's is `pickman/` (root `pickman/.tracker`); z-nile's is the repository root. `tracker` becomes a retired root, so history, the trail and capture still read it.
- `ac.sh` runs each `check.sh` from its project's home, and the one spec runner runs from a home (`pickman/tests/run.luau`), with that home's `.luaurc`, `.cache` and jail. So every path a sequestered file names resolves where it was written for, and no sequestered file changes. A spec proves every path a live `check.sh` names exists.
- Each project gets its own gate (`z-nile/check.sh --project <name>`, `pickman/check.sh`). Promotion puts a member's specs in its project's `tests/acceptance/`.
- Readiness and resurrection: `./zn busy tracker src tests` lists what holds the old paths, and AC16 makes it a check. Afterwards `./zn audit` and a promoted gate spec fail if `tracker/` holds anything but the counter file, or if a promoted folder sits outside its item's project.

### 2. Homes: `z-nile/projects.toml`
```toml
retired = ["tracker"]

[[project]]
name = "pickman"
root = "pickman/.tracker"
home = "pickman"

[[project]]
name = "z-nile"
root = "z-nile/.tracker"
home = "."
```
`z-nile/engine/projects.luau` (c0114's one reader) gains `home`:
```lua
export type Project = { name: string, root: string, home: string }
projects.homeOf(reg: Registry, path: string): string     -- the home of the project whose *current* root holds the
                                                          -- repo-relative path (by whole prefix "<root>/"); "." otherwise
projects.acceptanceRoots(reg: Registry): { string }      -- "<home>/tests/acceptance" ("tests/acceptance" for "."),
                                                          -- once each, in registry order
```
Parser rules, added to c0114's (which already refuse an unknown key, a repeated name or root, and a bad root shape):
- `home` is optional; absent means `"."`. The legacy registry (no file) is `{ pickman, root tracker, home "." }`.
- A home is `"."` or the project's own name, nothing else: not `src`, `..`, `pickman/`, or another project's name. The message is `<name>'s home must be "." or "<name>"`.
- A home other than `"."` requires the root `<home>/.tracker` (`<name>'s home <home> needs the root <home>/.tracker`), so a home always holds its own root.
- Homes may repeat only as `"."`: a non-root home equals its unique name.

`z-nile/roots.luau` (c0114's reader for the shell) gains two modes:
- `lune run z-nile/roots -- --projects` prints `name<TAB>home<TAB>root` per project, in registry order. `ac.sh`, the gate and CI's dispatch step read it, and nothing else in shell parses the file.
- `--luau-dirs [<name>...]` now derives each named project's folders (every project's with no name) from its home. That is the home's `src/`, `tests/` and `scripts/` where they exist, the root project's own folder (`z-nile/`), and every root, always (c0114's rule; stylua skips hidden folders unless they are named). An unknown name exits 2.

A c0114-era engine's parser refuses the `home` key (E4). So once c0120 is on `origin/main`, an engine from between c0114 and c0120 publishes nothing (c0114 §2: a registry that does not parse publishes nothing), and its worktree must merge `origin/main` first. It fails closed, as F4 asks.

### 3. Checks run from their project's home
`z-nile/lib/ac.sh`, which every `check.sh` sources, now works as follows:
1. Before any `cd`, it resolves the script bash runs (`$0`) to a physical path. For a `check.sh` run as `bash <path>/check.sh`, that is the `check.sh` itself, also through the `scripts/lib/ac.sh` forwarder. **A sourced `check.sh` refuses** (review 001 F6): the first `BASH_SOURCE` entry past `ac.sh` and its forwarder is the file that sourced `ac.sh`. When that file is a `check.sh` and is not `$0`, `ac.sh` exits 1 with `ac.sh: <check.sh> is sourced by <caller>: run a check.sh with bash, never source it`. Sourced, `$0` would be the caller, and a pathspec guard would run from the caller's folder and could pass vacuously. An inline `bash -c 'source <ac.sh>; check …'` sources no `check.sh` and keeps working (c0034 uses one).
2. It changes to the repository root as before, checks the guard file and fences the **root** as before. `ZN_ROOT` is exported as the physical root.
3. It reads `lune run z-nile/roots -- --projects` and takes the home of the project whose root is a prefix of the `check.sh`'s root-relative path. The loop reads through process substitution, never a here-string: inside a jail bash cannot create a here-string's temp file, and a silently empty loop would run a pickman `check.sh` from the root (E5).
4. It fails closed. A `check.sh` under a `.tracker/` folder that no current root holds, or whose registry can't be read, exits 1: `ac.sh: <path> is under no project root that z-nile/roots lists: refusing to guess its home`. Any other `check.sh` (a fixture's loose script, a retired root's) runs from the root, as before.
5. **It fences the home too** (review 001 F1, review 002 F1). A `check.sh`'s own fixtures go in its home's `.cache` (the testing skill's `.cache/<unique name>`, relative to the folder it runs in). Without a fence there, a fixture whose `git init` failed would let git find the real repository. For a home other than the root, `ac.sh` runs `pickman_home_fence "$ZN_ROOT/<home>" || exit 1`, from `z-nile/lib/fence.sh`. `pickman_fence` itself is split into four steps, each a function, which both fences run in this order:
   1. **Ceiling** (`pickman_fence_ceiling`): `<dir>/.cache` joins `GIT_CEILING_DIRECTORIES` (once). It touches no other variable, cannot fail, and always runs first, so no other step's order can remove it.
   2. **Refusals** (`pickman_fence_refusals`): reads only. A `.cache` that is a symlink or a file, or a sentinel `.cache/.git` that is a folder, refuses ("Stop and report this"). They apply in every mode, spec runs and the jail included, and nothing waives them.
   3. **Environment** (`pickman_fence_env`): the git and spec guards. Its one refusal, no ref-guard hooks outside the jail (c0114's `jailed` waiver unchanged), is a read that comes before any change. From its first change on it never returns early: it unsets the inherited overrides (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_CONFIG_PARAMETERS` and the rest) **before it derives anything from git**, so the protected repository (`real`, read by `git rev-parse --git-common-dir`) is read in a clean environment, never redirected by an inherited `GIT_DIR` (a hook's relative `.git`, or another repository; code review 001 F1), then sets the whole set again (`PICKMAN_FENCE_REAL_GIT`, `core.hooksPath`, `gc.auto`, `maintenance.auto`, the spec settings, `GIT_CONFIG_COUNT`). So whichever step refuses, the guards the shell inherited are never weaker than before the call.
   4. **Sentinel** (`pickman_fence_sentinel`): the writes. `mkdir .cache`, the sentinel by `rename(2)` (a link there is unlinked first), and `gh-none` in spec mode. It comes last, so a refused write leaves the environment fully guarded.

   `pickman_fence` (the root's and the runner's) refuses on any step's failure, as before. `pickman_home_fence` differs in one case only: the sentinel's write fails while all three of the runner's jail markers are set (`PICKMAN_TEST_JAIL=sandbox-exec`, `PICKMAN_FENCE_SPECS=1`, `PICKMAN_TEST_FENCE`) **and** `<home>/.cache` lies outside the run's own `.cache` (neither `$PICKMAN_TEST_FENCE/.cache` nor under it, the comparison c0114's `jailed` test makes; review 003 F2). That is the jail refusing a write outside the run's `.cache`, the one place it lets a spec write; inside it a failed write has another cause and refuses. The waiver never keys on an outer sandbox's label, whose probes check the repository, not `<home>/.cache`; so **an outer sandbox must let every home's `.cache` be written** (testing skill, Jail), or a `check.sh` run in a home there (c0034's list mode) refuses, failing closed (review 004 F1), as in c0034's list mode, which lists every finished pickman `check.sh` from inside the root's jail. It then prints `fence: the jail refused <home>/.cache's sentinel; its ceiling and every other guard hold` and goes on; the kernel refuses every write there, git finds no repository below the ceiling, and the environment is the root fence's. The waiver tests for the jail, never for "the write failed": every other failure refuses (`fence: cannot write <home>/.cache's sentinel; refusing`), spec runs included, and nothing hides the fence's stderr. `ac.sh` names no guard variable, so it needs no repo-fence `ALLOWED` entry. The same audit found `ac.sh` hiding the stderr of the `z-nile/roots --projects` lookup it fails closed on; it no longer does.
6. It changes to the home.

The specs a `check.sh` starts fence their own home (§4). Its own commands run git in the real repository only to read (`git diff`, `merge-base`), as before; review keeps catching those (testing skill, Caught only by review).

**Every other guard tied to a folder** (review 001 F1's consequence), checked:
- The run's lock and its jail are the home's (§4).
- The runner's unlinking of links at the top of `.cache` acts on the home's `.cache` (`here`), and so does `fixture.check`'s "under this run's `.cache`".
- The gate sweeps every home's `.cache` (§6).
- `cachepaths` covers `pickman/scripts`.
- `promote-check`'s transient copies go to the member's home (§7).
- `sync`'s sweep of stale `prompt.md` files reads every root (c0114).
- **One gap, closed:** the tripwire's "a worktree appeared under `.cache`" looked only at the run's own `.cache`. An unjailed run from `pickman/` (Linux) could register a worktree under the root's `.cache` unseen, so `fence.luau`'s snapshot now counts a worktree under any `.cache` of the checkout.

That keeps working:

### 4. The runner runs from a project's home
`tests/run.luau` stays the one runner. `pickman/tests/run.luau` is `return require("../../tests/run")`, so `lune run tests/run` in `pickman/` runs the shared runner with `pickman/` as its working directory. The runner then:
- computes `ROOT` from its own location (`debug.info(1, "s")`, the runner's absolute path) and `HOME_PREFIX` from the working directory: `""` at the root, `"pickman/"` in pickman's home;
- loads a spec as `require("../" .. HOME_PREFIX .. file)`, where a spec path is relative to the home, or absolute (stripped as before);
- collects `tests/` relative to the home (`collect("tests")`, unchanged), so each home runs only its own specs;
- re-runs itself as `lune run tests/run` (relative), which is the home's entry, and ends with `return nil` so a home can require it.

The fence runs with `here` = the home: the jail allows writes only in `<home>/.cache`, the lock is `<home>/.cache/tests-run.lock`, and the tripwire snapshots the same repository. Changes:
- `tests/lib/fence.luau` sources `"<ROOT>/z-nile/lib/fence.sh"`, passing the root as `$4`, instead of the cwd-relative `z-nile/lib/fence.sh`. `protectedPaths(here)` adds the checkout's toplevel when it differs from `here`.
- `z-nile/lib/fence.sh`: the ref guard's hooks default to `git-hooks/` beside `fence.sh` itself, not `$here/z-nile/lib/git-hooks`. This is the same folder when `here` is the root. A home has no `z-nile/` of its own.

So pickman's specs, their relative `.cache/...` fixtures (`place`'s builds, `sim`'s replays, c0041's graph fixtures) and their jail are pickman's. Separate homes have separate locks and `.cache` folders, so the two suites could run together; the gate runs them one after the other. **pickman's gate proves its own guards**: `pickman/tests/meta/fence.spec.luau` is `return require("../../../tests/tooling/repo-fence.spec")`. `repo-fence` reads the checkout's root by `git rev-parse --show-toplevel` (`checkout`): it scans the whole checkout from there, takes the hooks there, and from a home also probes that the root and the root's `.cache` are unwritable (E3).

**The harness split (U3).** The shared modules stay at the root:
- `t` (every spec) and `renamed` (pickman's c0063, c0103 and c0106 use it) are re-exported from `pickman/tests/lib/`. `renamed` reads the compaction map from the working folder, then from the root of the tree that holds it.
- `sim`, `place` and `fakeengine` are pickman's.
- `fence`, `fixture`, `clone`, `cleanup`, `engine`, `trackerfix` and `cachepaths` are the tooling's.

`tests/fixtures/graph` stays at the root, because z-nile's selector spec requires it relatively to compare the graph with Lune's own `require`.

### 5. Aliases and the require graph
`pickman/.luaurc`:
```json
{ "languageMode": "strict", "aliases": { "logic": "./src/shared/Logic", "shared": "./src/shared", "tests": "./tests", "scripts": "./scripts" } }
```
The root `.luaurc` keeps `tests`, `scripts`, `znile` and `lune`. It points `logic` and `shared` at `./pickman/src/shared/...` (Guess 8). U2 showed that Lune 0.10.5 and luau-lsp 1.70.1 resolve an alias from the nearest `.luaurc` that defines it, inheriting the rest from parents. A worktree lies inside the main checkout, so an alias the worktree's root doesn't define resolves through the **main checkout's** `.luaurc`, to the main checkout's files. Defining the two at the root keeps them inside the checkout.

`z-nile/lib/graph.luau` matches that resolution:
- `graph.aliases(dir?)` merges every `.luaurc` from the filesystem root down to `dir` (default `"."`), a nearer alias replacing a farther one, with lowercased keys and `~` targets skipped. Each target is relative to its own `.luaurc`, returned relative to the current folder; a cache is kept per absolute folder. `graph.resolve` looks an alias up in `graph.aliases(dirname(from))`.
- `normalize` keeps a leading `..` that climbs above the current folder, so a graph built from `pickman/` reaches `../z-nile/lib/graph.luau`.
- `@game` resolves through the project file of the file's own place: the nearest `default.project.json` at or above the file's folder (`pickman/`). `graph.gameRoots()` with no `./default.project.json` returns no roots, frozen and cached, instead of failing.
- `affectedSpecs` marks every place library in the graph, `<home>/tests/lib/place.luau`, as changed when that home's `src/` or project files change. A graph with no place library still marks the root's, as before (c0041's and the selector's fixtures).

`pickman/tests/meta/architecture.spec.luau` keeps the game's rules (features, Logic purity, `src` aliases, the declared deps, unit specs per feature) and runs from `pickman/`. It requires `@znile/lib/graph`, reads `.tracker/architecture.md`, and checks `--!strict` over pickman's `src`, `tests` and `scripts`. The new root `tests/meta/architecture.spec.luau` keeps the tooling's two rules: every require under `tests/` resolves, and `--!strict` over `tests`, `scripts` and `z-nile` (`.tracker` aside).

### 6. Each project's gate
`z-nile/check.sh [--project <name>]... [--affected [--base REF] | --full | --plan]` is the one gate.
- No `--project` runs every project (CI, `done`, `land`, `setup.sh`); each `--project` adds one. An unknown name exits 2 (`check.sh: no project <name> in z-nile/projects.toml`).
- The projects come from `z-nile/roots -- --projects`. A tree without `z-nile/roots.luau` predates c0114: it is one project at the root.

For each picked project, with `p` its home's prefix:
| stage | reads |
|---|---|
| format, lint | `z-nile/roots -- --luau-dirs <picked>` (§2) |
| Roblox types | `p/src`, from the home (`rojo sourcemap default.project.json -o sourcemap.json` and `luau-lsp analyze … src` in `pickman/`; a sourcemap's paths are relative to its project file), definitions and base `.luaurc` given as `../` paths |
| Lune types | the home's `tests/` and `scripts/` and the root project's own folder, `--ignore='**/.tracker/**'` |
| builds | every `p/*.project.json`, into `p/.cache/check.rbxl` (default) or `p/.cache/check-<stem>.rbxl`, through `build_place` (built outside, renamed in) |
| specs | from the home: `lune run tests/run` at the root, `(cd pickman && lune run tests/run)`; in affected mode `lune run z-nile/affected -- --project <name>` selects, relative to the home |

- `--plan` prints each stage's reading (`format:`, `lint:`, `types (Roblox):`, `types (Lune):`, `build:`, `specs: <name>, from <home>`) and exits before writing anything.
- Each home's `.cache` gets the top-level-link sweep that the root's had.

### 8. The freeze: `./zn busy`
`./zn busy [<path>...]` is a read-only command, listed in the tracker skill's main-checkout list and command table. It prints one line per holder and exits 1 when anything holds the paths:
- every raft active on `origin/main` (`<root>/rafts/active/<R>/`), except the raft of the current branch (`R0010-…`): `raft R0010 is active`;
- every branch, local or on origin, except `main` and the current branch (local and `origin/<current>`), that changes the paths since it left `origin/main`. This is compaction's own check, `compact.busyRefs(current, paths?)`, which now takes paths: `branch <ref> changes <paths>`;
- every other worktree of the repository with uncommitted (or untracked) changes under the paths, read with `git --no-optional-locks -C <wt> status --porcelain -- <paths>` so its index is never rewritten: `worktree <path> has uncommitted changes under <paths>`.

Without paths it guards `compact.guarded()`. `busy` reads `origin/main` and the origin branches as of the last fetch (review 001 F8). It never fetches itself, because it is read-only and runs in the main checkout. AC16 can't fetch either: the ref guard refuses a fetch from a `check.sh` that has nothing new (an empty ref transaction; reported separately). So Implementation step 11 runs `./zn sync --fetch` just before `check.sh`, and AC16's label says it reads the last fetch. **c0120's readiness**: `./zn busy tracker src tests` prints nothing. AC16 runs it on the raft branch at `./zn check` and `done`, so the move can't be finished while anything holds those paths. The command that readies c0120 is main's at that time, c0114's, which has no `busy` (Guess 5). Until `busy` exists, the person who readies c0120 checks these by hand, read-only, in the main checkout: `./zn list active` lists nothing, and
```bash
git fetch -q origin; for r in $(git for-each-ref --format='%(refname:short)' refs/heads refs/remotes/origin); do
  case $r in main|origin/main|origin/HEAD|origin) continue ;; esac
  git diff --quiet origin/main..."$r" -- tracker src tests || echo "busy: $r"; done
git worktree list --porcelain | sed -n 's/^worktree //p' | while read -r w; do
  [ -n "$(git --no-optional-locks -C "$w" status --porcelain -- tracker src tests)" ] && echo "dirty: $w"; done
```
prints nothing.

## Acceptance criteria

### Checked
- AC1: `z-nile/projects.toml` gives pickman the root `pickman/.tracker` and the home `pickman`, and z-nile the root `z-nile/.tracker` and the home `.`, with `tracker` retired. Its parser accepts a home only as `.` or the project's name, and a folder home only with `<home>/.tracker` as its root. `homeOf` and `acceptanceRoots` follow the registry, and `z-nile/roots --projects` prints it.
- AC2: pickman's `src/`, project files, game spec tiers, test helpers and fixtures, publishing scripts, promoted specs (by item) and tracker items and documents live in `pickman/`, and none of them is left at its old place. `tracker/` holds only the counter file. The home's `.luaurc`, runner, re-exports and forwarders are as §3-§5 say.
- AC3: `ac.sh` runs a `check.sh` from its project's home with `$ZN_ROOT` set, so pathspecs and paths mean that project's files. A `check.sh` under a `.tracker/` folder that no project's root holds, or whose registry can't be read, refuses to run. `find` and `members` print paths from the caller's folder, and a pickman raft's prompt inlines pickman's architecture map.
- AC4: the shared runner, run from a home, collects and runs only that home's specs, there, with that home's aliases and `.cache`.
- AC5: the require graph resolves aliases per folder as Lune does, keeps `../`, resolves `@game` per project and marks each home's place library. The selector picks per project, relative to the home, with the full-run rules of §6.
- AC6: `z-nile/check.sh` runs each project's stages from its home (`--project` for one, `pickman/check.sh` for pickman's), and `--plan` prints them and writes nothing.
- AC7: `done` and `promote-check` promote and check a pickman member's specs in `pickman/tests/acceptance/<id>` from `pickman/`. Spend leaves out every project's promoted specs, and compaction renames and rewrites them.
- AC8: `capture` and history follow an item across the move into `pickman/.tracker`.
- AC9: `./zn busy` lists the active rafts (but its own), the branches and the dirty worktrees that hold the given paths, and exits 1 when any does.
- AC10: `./zn audit` reports a file under a retired root (the counter file aside) and a misplaced promoted folder. The repository has neither, and none of pickman's old places is tracked at the root.
- AC11: every literal path in an unfinished item's `check.sh`, in every project root, exists from its project's home or lies under that item's (or its raft members') Touched modules. The restamped check.sh files of R0030, c0083, R0039 and c0075 are exempt as they are now. The scan's reach (each `check.sh` read from its home, a vanished path reported) is proved on a fixture. The live loop has no floor on how many items there are (review 001 F3).
- AC12: CI ignores only the project roots and the counter on push, runs a dispatched raft's sequestered specs from their home, and runs the beta job's deploy and runtime tests from `pickman/`. `deploy-beta` builds from the project file's folder, and the stop hook gates `pickman/`.
- AC13: the skills, AGENTS.md, SETUP.md, the templates and the usage say where pickman lives and what a home is, and name no old path to pickman's architecture map or game design.
- AC14: the repository-fence, structure and isolation specs pass in both homes.
- AC15: `./zn audit` reports no error on the real tree.
- AC16: as of the last fetch (step 11 runs `./zn sync --fetch` first), `./zn busy tracker src tests` prints nothing on the raft branch: no other raft is active, and no branch or worktree changes those paths.
- AC17: R0012 is in `done/` (`./zn find R0012` ends in `rafts/done/R0012`): Guess 4's chosen option, enforced. If the user picks (b) instead, R0012's `check.sh` joins AC11's restamped list and AC17 goes; with (c), AC17 goes and the edit is named in Overrides.
