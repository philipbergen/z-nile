# c0121: Board server with live actions

## Problem
Split from c0118 by the user (2026-10-20, "Split: static board, then server"). These outcomes are c0118's captured ones:
- The board is served by a local server, localhost only, that shows live state: click a card for its worktree, its PR, its checks, the model and the spend.
- The only actions are stop, retry and open, and they work from the page through the dispatcher (c0117).
- `zn board --serve` serves the same page `zn board` writes, with live polling (the user's decision: one page, two modes).

Carried from c0118's programme review (2026-10-20), whose server, action and live-data findings moved here with the split (c0118 design review 001 F4). Each is a requirement on this issue's design, not a change of its outcomes:
- **F3 (high), CSRF and DNS rebinding.** Loopback is not safe by itself: any page in the person's browser can send a simple cross-origin `POST`, and a rebinding domain reaches `127.0.0.1` with a foreign `Host`. Bind `127.0.0.1` explicitly; refuse a `Host` other than `127.0.0.1:<port>` or `localhost:<port>`; accept actions only as `POST` with `Content-Type: application/json` (so a preflight is forced) and answer `OPTIONS` with 403 and no CORS headers; require an `X-Zn-Token` equal to a random token made at start, embedded only in the served page and printed once in the start URL; refuse a foreign `Origin`; never act on a `GET`; validate ids against the model and pass argument arrays, never `sh -c`. One spec case per guard: wrong Host, foreign Origin, missing or wrong token, `GET` that does not act, unknown id refused before any process runs (each 403 or a refusal).
- **F4 (high), who runs stop and retry, and where.** `stop` runs only in the main checkout, so the server does too: add `zn board --serve` to the main checkout's allowed command list ("read-only except the three actions, each delegated"), keep it out of `READ_ONLY` so the repository guard runs, and update the `tracker-guarded` pin. Stop and retry call c0117's `dispatch stop|retry <id>` and read its run state (`.cache/dispatch/<id>/state.json`); say whether those run in the main checkout.
- **F8 (medium), live data without blocking.** `gh pr list` took 0.5 s and needs auth: call it once per project per refresh, cache about 30 s, refresh in a background task and never on the request path; `/api/state` returns the cached data and its age; when `gh` is missing or fails the card says "checks unavailable" and the page still renders. Read a running raft's spend from its worktree's `spend.md` (build and code-review rows reach main only at the merge). Rebuild the model only when HEAD, `origin/main` or a worktree's HEAD changed. Cases: a failing stub `gh` gives a 200 with checks unavailable; two `/api/state` calls in the cache window call the stub once.
- **F9 (medium), test seams.** `net.serve(0, …)` reports port 0, so specs can't use port 0: `serve.start({ root, port, runner, opener, gh, now })` returns `{ url, token, stop }` with every effect injected; specs run it in-process on a random port with retry (c0003's helper) and drive it with `net.request`; the CLI takes `--port` and fails clearly when it is taken. `open` is never the real one in specs (the runner's browser guard fails the run); a retried dispatcher is never the server's child (or it dies with the server) and never detached into a new session. Also, word for word from the review: "The page's JS is tested with the c0042 node harness, with `fetch` stubbed"; specs "stop it in a final case"; and "repository-safety review checks that no stub spawns a real process outside `.cache`" (c0118 design review 002 F3).
- **F11 (low), a stale server.** Record the engine tree's hash at start; when HEAD's differs, the page says "server is out of date: restart". One case with a fixture HEAD change.
- c0118's seam for this issue: the page's `window.znBoard.load(model, statsHtml?)` swaps the model (and the Stats section), keeping the view, project, selection, done window and range; `board.collect(nil, root, facts)` with `facts.asOf` set to the request time builds each polled model; the Issue and Raft types carry `pr` and `checks` fields, nil in the static page, for this issue to fill.

Decided with the user (2026-10-25): "Sequence, c0121 solo (Recommended)": c0121's prep (#119) lands only after c0118 is done, and c0121 is its own raft, never rafted with c0118 (design review 003 F1).
Decided with the user (2026-11-08), after code review 001 of R0084 found that a Retry on a card that never ran would start the item's whole unattended chain: "Refuse with 409 (Recommended)". `serve.plan` refuses a retry for a card the dispatcher has no run state for (409, nothing runs), as it refuses a stop (G9).
Decided with the user (2026-11-08), from the same review (each poll cost 0.235 s of CPU, and `./zn` stops its engine at 1800 s): "Fix the cost only (Recommended)". The model is encoded once per build and per `gh` answer, not per poll; the limit is not raised (G10).

## Non-goals
- The static page, its columns, cards, charts, navigation and Stats: c0118.
- Starting a model, or any action besides stop, retry and open (c0118's captured "The only actions are stop, retry, and open").
- Serving anything but 127.0.0.1, or to anyone but the person at this machine: no remote access, no TLS, no accounts.

## Solution
<!-- The approach in one paragraph. -->
Prep's detail (the capture's Solution was empty; nothing captured is changed):
- One module, `z-nile/engine/serve.luau`. The guard, the action plan and the `gh` parse are pure. `serve.start` wires them to Lune's `net.serve` on 127.0.0.1, with every effect injected (the runner of `./zn`, the opener, `gh`, the clock, the model's key, the engine's hash), so specs run it in-process on a random port with stubs and never reach the network beyond loopback.
- The page is c0118's page. The server sets `model.live` (the session token, the poll interval, the checks state, the stale flag) and fills each raft's reserved `pr` and `checks`. The page polls `/api/state` and hands each model to c0118's `znBoard.load`.
- Stop and retry run c0117's `./zn dispatch stop|retry <id>` as argument arrays; open opens the card's PR, else its raft's worktree.

### 3. The guard (programme review F3; the experiments below)
Every request goes through `serve.guard` before any route, so a refused request runs no stub, reads no model and starts no process:
| refusal | status | why |
|---|---|---|
| `Host` not `127.0.0.1:<port>`, `localhost:<port>`, `127.0.0.1` or `localhost` | 403 | DNS rebinding: a page on `evil.example` resolved to 127.0.0.1 still sends `Host: evil.example[:port]`. The bare names are allowed because some clients (Lune's `net.request`, E2) send no port; a rebinding page never sends them. |
| any `OPTIONS` | 403, no `Access-Control-*` header | a cross-site preflight for a JSON POST fails, so the browser never sends the POST |
| an `Origin` other than `http://127.0.0.1:<port>` or `http://localhost:<port>` | 403 | CSRF from any other site |
| `/` without `?token=<token>`, or not a GET | 403 / 405 | the page carries the token; only the URL the server printed opens it |
| `/api/*` without `X-Zn-Token: <token>` | 403 | a custom header also forces a preflight from any other origin |
| `/api/action` not a POST, or its `Content-Type` not `application/json` | 405 / 415 | a GET never acts; a simple form post can't send JSON |
| `/api/state` not a GET; any other path | 405 / 404 | |
The token is 16 random bytes (`od -An -tx1 -N16 /dev/urandom`), made at start, embedded only in the served page's model, and printed once in the start URL (`http://127.0.0.1:<port>/?token=<token>`). The server binds `127.0.0.1` explicitly (E1, E6: the LAN address is refused), through `Options.listen` (default `net.serve`), so `server.spec` records the bind and pins its address and port (design review 002 F1).

### 4. The actions (programme review F4)
`serve.plan` decides from the model alone, never from free text: the id must be a key of `model.home` (an id the model shows), else `400 refused: unknown id <id>`; the action must be stop, retry or open.
- **stop**: acts on the run the card belongs to (design review 003 F3). The card's dispatch state comes from the model (`Dispatch`, c0118's reader, which c0121 extends with `follows: string?`, the raft an issue's chain moved on to, c0117's `state.json` field). With no state for the card's id, `serve.plan` answers `409 refused: nothing is running for <id>` and runs nothing (`./zn dispatch stop` on an id with no run would create a state folder for it). Otherwise: while the card's own outcome is `running`, the target is the card's own id (a step of its own runs; c0117 writes `follows` once, at the follow, and never clears it, so the pointer alone does not say the run moved, design review 004 F1); else the target is the `follows` id when that id has state, else the card's own id (a stale follow, its raft done, falls back). A follow only points forward, issue to raft, so one hop is enough. A lost own run is the one case the first click does not reach the raft's live run: its answer says `lost`, and a second click (the own outcome now `lost`) follows. It runs `./zn dispatch stop <target>` and waits; 200 with its output, 500 when it fails. `serve.plan(m, action, id): (Plan?, string?, number?)`: the third value is the refusal's status, 409 here (a stop with nothing running, a retry of a card that never ran) and 400 for every other refusal; the server answers `text(code or 400, "refused: " .. why)`.
- **retry**: only for a card with a run state (G9): with none, `serve.plan` answers `409 refused: nothing to retry for <id>: it has never run` and runs nothing (`./zn dispatch retry` on an id with no state creates one and runs the item's whole headless chain, which is a start; code review 001 F1 of R0084), like stop. Otherwise it keeps the card's own id (its chain follows by itself) and starts `./zn dispatch retry <id>` (c0117) in a task of its own and answers 202 once it has run for `serve.RETRY_WAIT` (1 s), or with the dispatcher's output if it exits sooner (the chain can run for hours). It runs as a child process of the server, in the server's process group, never detached into a new session (`setsid`), so stopping the server (Ctrl-C) stops a retry it started; c0117 then marks that run `lost` and `./zn dispatch retry <id>` resumes it. Ctrl-C and a closed terminal reach the whole foreground group, so the retry dies with the server; a `kill` of the server's pid alone leaves the retry running until its current step ends: the dispatcher prints only between steps, and Lune raises a write to the closed pipe as an error (EPIPE), not a signal, the retry's current step runs to its end, and the dispatcher then dies at its next output line, which comes before it records the outcome (dispatcher.luau's step summary print precedes the save), so the state shows `running` until the next `./zn dispatch <id>` marks it `lost`, and `./zn dispatch retry <id>` runs the step again (design review 004 F3, run in a scratch script; 003 F5 had it the other way). Stop it with `./zn dispatch stop <id>` instead of killing the server's pid. The server keeps the retry's output on its pipe: Lune's `process.exec` can't send a child's output to a file without a shell, which §4 rules out (argument arrays only), and Ctrl-C reaches the whole group (G3). The server waits up to 1 s (`serve.RETRY_WAIT`) for the child: a dispatcher that refuses at once (a held run lock) is answered 200 or 500 with its output, and a chain that keeps running is answered 202 (design review 001 F6). Decided with the user (2026-10-24): G3.
- **open**: opens the item's own PR, else its raft's PR (from the `gh` cache), else its raft's worktree folder, with `open` (macOS) or `xdg-open`; 400 when there is none.
- The real effects are built by `serve.effects(top, exec, os)` (`exec` is `process.exec` in the CLI, a recording stub in `guard.spec`): the runner is `exec("<top>/zn", args, { cwd = top })`, an argument array, never `sh -c`; the opener is `exec("open" | "xdg-open", { target })` by `process.os`; and `gh` is `exec("gh", serve.GH_ARGS, { cwd = top })`, where a `gh` that can't be started reads "gh is not installed" and a failing one its stderr (design review 001 F8).
- **Where**: the server runs only in the main checkout (`git rev-parse --show-toplevel` must equal the first worktree), because c0117's run state (`.cache/dispatch/`) and `stop` live there; elsewhere `./zn board --serve` refuses: "board --serve runs in the main checkout (<path>), where the dispatcher's run state and stop live". zz-rules' list of main-checkout commands names it.
- **The repository guard**: `board` stays in `READ_ONLY` (it only writes a page), and `board --serve` is excepted (`not READ_ONLY[name] or (name == "board" and --serve given)`), so `guardRepoRoot` runs before any action can. The programme review asked to "keep it out of READ_ONLY ... and update the tracker-guarded pin"; the exception keeps the pin (`tests/tooling/tracker-guarded.spec.luau`) unchanged and is pinned by `cli.spec` instead. Decided with the user (2026-10-24): G4.

### 5. Live data (programme review F8)
- **`gh`**: one `gh pr list --state all --limit 200 --json number,headRefName,state,isDraft,url,statusCheckRollup,isCrossRepository` per refresh, for the repository (every project shares it, so "once per project" is once). A refresh is started by a page or state request when the last one is 30 s old, runs in a task of its own (E3: a subprocess in one task does not block the others), and is never awaited by the request: the request answers with the cache as it is, so the first answer says "checks loading", and a request while `gh` is still running starts no second one (the busy flag; design review 001 F1, with a `gh` stub that yields as `process.exec` does). `parsePrs` keys PRs by head branch, and a branch with several PRs keeps an open or draft one over a merged or closed one, then the highest number, whatever the order `gh` lists them in; a cross-repository PR (a fork whose branch has the same name) is skipped (design review 001 F3). A raft gets the PR of its launched branch (`raft.branch`, c0118 §3). Draft open PRs read `draft`; checks read `failing` (any FAILURE, ERROR, CANCELLED, TIMED_OUT or ACTION_REQUIRED), `pending` (anything not finished), `passing`, or `none`.
- When `gh` is missing, fails or prints something else, `model.live.checks` is `unavailable` and every card without a PR says "checks unavailable"; before the first answer it is `loading`. The page still renders (200).
- **Spend**: a launched raft's members show the `spend.md` rows in its worktree (`<worktree>/<root>/issues/active/<id>/spend.md`), where build and code-review rows sit until the merge; a member without one there keeps main's.
- **Rebuilding**: the key's one `.cache` read (`<root>/.cache/dispatch`) is on the reviewed list in `tests/lib/cachepaths.luau` as a read. The model is rebuilt only when its key changes (HEAD and `origin/main`, every worktree's HEAD from `git worktree list --porcelain`, and each `.cache/dispatch/<id>/state.json`'s change time), or when the model is 60 s old (so done ages and the as-of time move). The PR and checks are laid on each time from the cache.
- **`/api/state`** returns `{ model, statsHtml }`, encoded once per build of the model and per `gh` answer (a generation counter: rebuilds plus changed `gh` answers, read in the same step as the data it labels, before `engineHash` yields, so a `gh` answer landing during that wait is served by the next poll; `gh`'s version moves only when its output differs from the last), not per poll (G10; the encoding was 0.235 s of CPU per poll on the 6.7 MB model): the model's JSON, with `live` left out, and the Stats are kept per generation, and each poll splices its own small `live` block (token, checks age, stale flag) into the kept text before the model object's closing brace. `model.live` carries `checks`, `checksAge` (seconds since the last `gh` answer) and `stale`.

### 6. The page (c0118's seam)
- The served page is `board.render(model)` with `model.live` set. Its script: when `model.live` is present and the browser has `fetch` and `setInterval`, it shows `#live` ("live · checks N s old", "checks unavailable", "checks loading", or "server is out of date: restart" in red) and polls `GET /api/state` with `X-Zn-Token` every `live.poll` (5) seconds, handing `{ model, statsHtml }` to `znBoard.load` (c0118 §9: view, project, selection, window and range kept). A failed poll adds "the server did not answer".
- A served card's Run block gains Stop, Retry and Open buttons; each sends `POST /api/action` with `Content-Type: application/json`, `X-Zn-Token` and `{ action, id }`, and shows "<action>: <status> <answer>" under the buttons.
- A served card with no PR says "checks unavailable", "checks loading" or "no PR" instead of the static page's "live on the served board".
- The static page has no `model.live`: no buttons, no polling, no fetch, `#live` hidden.
- **Document links** (code review 001 F3 of R0084, design review 011 F1): the vendored marked keeps a `javascript:` href, and writes `jav&#x61;script:` unescaped, which a browser decodes to `javascript:`; on the served page such a link could read the session token and post the actions. The page's renderer writes the anchor itself, never marked's: the href and the title are escaped (so each attribute holds exactly the string that was tested; a quote in a title must not open an attribute), and it is kept only when, after the control characters and spaces a browser ignores inside a scheme are stripped, it has no scheme (relative, `#id`) or the scheme is `http`, `https` or `mailto`; any other scheme (`javascript:`, `data:`, `vbscript:`, `file:`) renders as the link's text. This is `board.html` code, so it holds on the static page too. Image sources are left to marked (an image `src` does not run script).

### 7. A stale server (programme review F11)
`serve.start` records `git rev-parse HEAD:z-nile/engine` at start; each model compares it with the current one, and `live.stale` is true when they differ, so after a `sync` that changed the engine the page says "server is out of date: restart". A commit outside `z-nile/engine` leaves the hash as it is. `server.spec` runs the real `serve.keyOf` and `serve.engineHash` on a fixture repository, and one server with the default hash on it (design review 001 F2).

### 8. The command
`./zn board --serve [--port N]` (default 8417):
- refuses `--out`, `-O`, `--open` and positional arguments ("usage: board --serve [--port N]  (--serve writes no file: --out, -O and --open don't apply)");
- refuses a port that is not an integer from 1024 to 65535;
- refuses outside the main checkout (§4);
- fails when the port is taken: "board --serve: port N is taken (already serving?); pick another with --port", and on any other start failure says it: "board --serve could not start: <why>" (`serve.startError`; design review 001 F5);
- prints the URL with its token once, and serves until stopped (Ctrl-C).

### Scalability
- Per page poll (every 5 s per open tab): the key (`git rev-parse` once, `git worktree list` once, a `stat` per dispatcher state, about 20 ms) and, only when it changed or every 60 s, a model build (about 0.37 s of CPU on the real tree). `gh` at most once per 30 s whatever the number of tabs, off the request path. The response is the whole model (about 6.7 MB today on the real tree; the documents dominate), encoded once per generation (§5); loopback only. **How long the server lives** (design review 011 F3; measured on the real tree, G10): a steady poll costs about 2.7 ms of the server process's own CPU (it was about 0.10 s), a model rebuild about 0.37 s every 60 s and a changed `gh` answer about 0.10 s, so about 0.40 s of CPU a minute for one open tab left idle (each commit in a worktree, fetch of `origin/main` or dispatcher state write changes the key and forces one more rebuild, and a changed `gh` answer measured 0.13 s): the 1800 s CPU limit of `./zn` (c0191) is reached after about three days, not nine hours (design review 012 F3: CPU time of the process, measured on the real tree; wall-clock timings depend on load). When it ends the kernel stops the server, the page says "the server did not answer" on its next poll, and `./zn board --serve` starts it again (the limit is not raised, G10).
- Handlers don't block each other (E3), so a stop that waits on `./zn dispatch stop` doesn't stall polling.

### Maintainability
- A new action is a branch in `serve.plan` and a button in `actions()`; the guard needs no change. A new live field goes in `board.Live` and `model()`.
- Every effect is injected, so the next server feature is specced in-process.

### Usability
- One command prints one URL; the page is the board people already use, plus a status line and three buttons.
- Refusals name the rule (the Host, the Origin, the token, the method, the id).
- Exhaustive lists: the main checkout's command list names `./zn board --serve`; the usage text names it; `READ_ONLY` keeps `board` with the `--serve` exception stated beside it.
