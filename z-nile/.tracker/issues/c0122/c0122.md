# c0122: Ref guard accepts a fetch with nothing new

## Problem
A `check.sh` flow that runs outside any spec run may fetch into the real repository: the ref guard (`scripts/lib/git-hooks/reference-transaction`) allows updates under `refs/remotes/`. But when the fetch has nothing new, git still runs a ref transaction with no refs in it, and the guard requires at least one ref (`[ "$lines" -gt 0 ] && [ "$fetch_only" = yes ] && …`), so it refuses the fetch and the fetch fails. A check therefore can't fetch for itself: c0120's AC16 had to rely on `./zn sync --fetch` being run first instead. Found by the c0120 prototype work (2026-10-21).

Reproduced 2026-10-21 in a scratch fixture (an origin and a clone, the clone's git directory listed in `PICKMAN_FENCE_REAL_GIT`, `core.hooksPath` at the guard folder, git 2.54.0): the first fetch, with one new commit, passes (`f87e7f4..36ccf44  main -> origin/main`, exit 0); the second, with nothing new, fails:

```
fence: a check tried to change refs in the real repository (…/d1/clone/.git); refused
fatal: in 'prepared' phase, update aborted by the reference-transaction hook
```

A logging hook shows what git sends on that fetch: `preparing, 0 ref lines`, `prepared, 0 ref lines`, `committed, 0 ref lines`.

**Outcome:** an empty transaction from an allowed fetch (a `check.sh` flow, not a spec run) is accepted, so a check can fetch whether or not anything is new. Everything else the guard refuses today stays refused: any update outside `refs/remotes/`, a deleted ref, and every ref update during a spec run.

**Prep finding (2026-11-01):** the Outcome's code change is already on `main`. c0131 (R0047, done 2026-10-22) was filed as an emergent issue because R0047's `check.sh` needed this very fix, and it added to the hook (`z-nile/lib/git-hooks/reference-transaction`) the line `[ "$lines" -eq 0 ] && [ -z "$PICKMAN_FENCE_SPECS" ] && chain "$@"`; its promoted specs (`z-nile/tests/acceptance/c0131/{accept,refuse}.spec.luau`) pin it by feeding the hook an empty transaction by hand. Re-run on today's `main` (git 2.54.0, fixtures in a throwaway clone, E1): the Problem's reproduction now passes (first fetch, then the fetch with nothing new, both exit 0) and every refusal in the Outcome still holds. What c0131 left undone, and this issue now delivers so the Outcome is pinned as captured ("a check can fetch whether or not anything is new"): (1) nothing runs a real `git fetch` with nothing new through the fence, so a change in what git sends, or in how the fence wires the hook, would go unseen; (2) the two places that restate the rule (the zz-test skill's Ref guard bullet, `fence.sh`'s header) still describe only a fetch that creates or moves a ref. The Problem's empty transaction is how newer git batches a fetch: git 2.50.1 (the Command Line Tools' git on this machine) gives each ref of a plain fetch its own transaction and starts none for a fetch with nothing new, so the bug cannot occur there; git 2.54.0 (`/usr/bin/git`) puts the whole fetch in one. `--atomic` makes both do the latter, which is why the specs and the documented command use it (design review 004 F1). The paths in the Problem (`scripts/lib/...`) are from before c0114; the hook is now in `z-nile/lib/git-hooks/`.

## Non-goals
- Trusting an inherited `PICKMAN_FENCE_HOOKS`: c0123.
- Letting spec runs fetch: they stay without network or fetch.

## Solution
The hook already accepts the empty transaction (c0131), so the code does not change. This issue makes the Outcome hold by proof and by words:
- A spec that lets **real git** send the fetch: a fixture origin and clone under `.cache`, the clone fenced by `z-nile/lib/fence.sh` as a `check.sh` flow (or as a spec run), then `git fetch` with something new, with nothing new, and with something new again plus a branch the clone has no ref for.
- The same spec file family pins what stays refused through real git: a spec run's fetch (new or not), a pruning fetch, a branch update, and removing a remote.
- The zz-test skill's Ref guard bullet and `fence.sh`'s header state the rule as the hook has implemented it since c0131, and a spec pins their wording.

## Design
**No behaviour change.** The guard stays exactly as it is on `main`: `z-nile/lib/git-hooks/reference-transaction` is not edited, and no code line of `z-nile/lib/fence.sh` changes (one comment line does). The behaviour that stays is what c0131's two promoted specs pin and what the new end-to-end specs pin through real git.

**Decisions relied on.** `pickman/.tracker/game-design.md` holds the game's decisions; none applies to the tooling. The relevant standing rules are zz-test's "Specs never touch the real repository" (the Ref guard, No network for specs, Fence and Overrides stripped bullets) and zz-arch rule 7 (guards fail closed).

### The end-to-end specs (sequestered, in `acceptance/`)
`fetch.spec.luau` (AC1) and `refuse.spec.luau` (AC2) build, under this home's `.cache` (`c0122-fetch` and `c0122-refuse`, one folder each), a fixture origin (`git init -b main`, committed as `c0122@example.invalid`) and its `--no-hardlinks` clone through `@tests/lib/clone`, and write a small bash script beside them:
```
source "$1" || exit 90            # z-nile/lib/fence.sh
case "$3" in                      # the marker, set here: Lune's env table cannot unset a variable
checks) unset PICKMAN_FENCE_SPECS ;;     # a check.sh flow, as ac.sh leaves it
empty) export PICKMAN_FENCE_SPECS= ;;    # exported empty
specs) export PICKMAN_FENCE_SPECS=1 ;;   # a spec run
*) exit 92 ;;
esac
pickman_fence "$2" || exit 91     # fence the clone, as ac.sh or the runner does
cd "$2" && shift 3 && git "$@"
```
Every fetch the cases run passes, with `-c`, the fetch settings its result depends on (`fetch.prune`, `fetch.pruneTags`, `remote.origin.prune` and `remote.origin.pruneTags` all false and `remote.origin.tagOpt=--tags` for the plain cases, so the tag case does not depend on the host's `tagOpt` and `-c remote.origin.tagOpt=` empty would not reset it (design review 004 F2); all on, with `remote.origin.tagOpt=--tags`, for the safe-form case, so its flags must win): the host's git configuration never decides a case, because command-line `-c` outranks global and system config and names nothing the gate scan bans (design review 003 F2; lesson zz-test/specs-set-host-markers-explicitly). Every fetch is `--atomic` except AC1's plain ones (a bringing fetch and a nothing-new fetch, whose outcome is `ok` on every git; the `after` fetch, which moves `main` and creates `extra` at once, is atomic so that a multi-ref transaction reaches the hook on every git: design review 005 F3): git 2.50.1 may refuse a plain fetch ref by ref and starts no transaction for a plain fetch with nothing new, so the refusals are pinned with `--atomic` (design review 004 F1). Each case runs it through `fixture.exec(clone, "bash", {script, fence.sh, clone, <mode>, <git args>})`, so git runs in the fixture only, through the shared fixture helper, with the marker set by the case itself whatever the surrounding run has (lesson zz-test/specs-set-host-markers-explicitly). A real check.sh flow has the marker **unset** (only `fence.sh` ever sets it, and only to `1`), so every check.sh-flow case runs in `checks` mode; a hook that fails on an unset variable would otherwise pass (design review 002 F1, M13); one nothing-new fetch also runs in `empty` mode. `pickman_fence` records the clone's git directory in `PICKMAN_FENCE_REAL_GIT` and points `core.hooksPath` at the guard folder beside `fence.sh`, so the hook sees a protected repository and real git sends the real transaction. Nothing outside `.cache` is written; the sentinel the fence writes lands in `clone/.cache`.
- `fetch.spec` :: AC1: with a new commit in the origin a check.sh flow's fetch succeeds and the clone's `refs/remotes/origin/main` equals the origin's tip; a second fetch with nothing new succeeds; a third (nothing new again) succeeds, and one more in `empty` mode; a fetch after one more commit and a new branch `extra` succeeds, follows `main` and creates `refs/remotes/origin/extra` (a created ref, not only a moved one).
- `fetch.spec` :: AC1, the safe form: after the origin deletes `extra`, commits again and tags the commit `v1`, with `fetch.prune`, `fetch.pruneTags`, `remote.origin.prune`, `remote.origin.pruneTags` and `remote.origin.tagOpt=--tags` all on, `git fetch --atomic --no-prune --no-prune-tags --no-tags origin` succeeds, follows `main`, keeps the stale `refs/remotes/origin/extra` and creates no tag.
- `refuse.spec` :: AC2, case 1 (a spec run, `PICKMAN_FENCE_SPECS=1`): a fetch with nothing new is refused with the guard's own message (`fence: a check tried to change refs in the real repository`), and so is a fetch with a new commit; the tracking ref has not moved.
- `refuse.spec` :: AC2, case 2 (a check.sh flow): a pruning fetch is refused whole. The clone has fetched a branch `gone`; the origin deletes it and commits; `git fetch --prune` is refused with the guard's message, `refs/remotes/origin/main` has not moved and `refs/remotes/origin/gone` is still there (a refused prune does not half-apply; `fetch.prune` or `remote.<name>.prune` in any configuration is the same fetch).
- `refuse.spec` :: AC2, case 3 (a check.sh flow): after a synchronising `--no-prune --no-tags` fetch, the origin commits and tags `v1`; an `--atomic` fetch of `origin` (with `remote.origin.tagOpt=--tags` pinned, so the tag is in the fetch's own refspecs) is refused with the guard's message, `refs/remotes/origin/main` has not moved and no `refs/tags/v1` exists.
- `refuse.spec` :: AC2, case 4 (a check.sh flow): a fetch by the origin's **path**, `git fetch --atomic <origin path> '+refs/heads/*:refs/remotes/origin/*'`, which ignores every `remote.origin.*` key and follows the tag the way a default fetch does (backfill, the path most sensitive to the git version), is refused with the guard's message, `refs/remotes/origin/main` has not moved and no `refs/tags/v1` exists (design review 005 F2).
- `refuse.spec` :: AC2, case 6 (a check.sh flow, last because it leaves a refspec in the clone's configuration): with `remote.origin.fetch +refs/heads/*:refs/heads/up/*` added, the safe form is refused with the guard's message, `refs/remotes/origin/main` has not moved and no `refs/heads/up/main` exists.
- `refuse.spec` :: AC2, case 5 (a check.sh flow): `git update-ref refs/heads/evil HEAD` is refused with that message and creates nothing; `git remote remove origin` (which deletes `refs/remotes/origin/main`) is refused with that message and the tracking ref and HEAD are unchanged.
- Each case compares one summary line (`line({...})` sorts the keys into `a=1 b=x`) so a failure prints every field.
