# c0123: Fence trusts only its own ref guard hooks

## Problem
`pickman_fence` in `scripts/lib/fence.sh` keeps an inherited `PICKMAN_FENCE_HOOKS` whenever that folder has an executable `reference-transaction` ("the first guard's hook stays in force: a nested copy may lack scripts/lib/git-hooks"), and points `core.hooksPath` at it. So a caller that exports `PICKMAN_FENCE_HOOKS` at a folder of permissive `reference-transaction` and `pre-push` hooks switches the ref and push guard off for every git a check runs. The macOS jail still protects spec runs there, but Linux runs and `check.sh` files have only the hooks. Found by c0120 code reviews 002 and 003 (2026-10-21).

Confirmed 2026-10-21 in a scratch fixture (a throwaway checkout with copies of `fence.sh` and `scripts/lib/git-hooks/`, fenced as a `check.sh` flow, then `git update-ref refs/heads/evil HEAD` in it):

```
--- no inherited value:
hooks=…/d2/checkout/scripts/lib/git-hooks
fence: a check tried to change refs in the real repository (…/d2/checkout/.git); refused
fatal: in 'prepared' phase, update aborted by the reference-transaction hook
exit 128
--- inherited PICKMAN_FENCE_HOOKS=…/d2/permissive:
hooks=…/d2/permissive
exit 0
```

and the branch `evil` exists afterwards.

**Outcome:** the fence trusts only hooks that are its own, or refuses an inherited value it can't verify, so no inherited variable can switch the ref guard off. Nested fences keep working, including a nested copy that lacks `scripts/lib/git-hooks`.

Scope decision (user, 2026-11-01): "All in c0123". It covers the whole Outcome, "no inherited variable can switch the ref guard off", including the members four design reviews found beyond the hook folder (exported shell functions, `PATH`, `BASH_ENV`, `CDPATH`, `GIT_EXEC_PATH`): besides verifying the hook folder, every launcher (`./zn`, the gate and the other entry scripts, the engine's check runs, the spec runner and its fence) starts what it runs in an allow-listed environment.

Decided with the user (2026-11-01): "Accept". Every fenced check gets the fixed `PATH` directories and git's global config pinned to the account's `~/.gitconfig` (else `~/.config/git/config`, else `/dev/null`); SETUP.md says where tools must live. What it costs: a tool from nvm, asdf or nix, or a git config kept only at a custom `XDG_CONFIG_HOME`, is not seen inside checks.

Decided with the user (2026-11-01): "I'm not running that". Specs must be fast and cheap: nothing under `acceptance/` spins the CPU, waits or sleeps for real, or writes files in bulk; a proof that needs real work is a `check.sh`-only script run once and never promoted. The five specs here were read for it (none spins, waits or sleeps), and the killed-run case plants a dead pid instead of killing a run.

Decided with the user (2026-11-01): "Exclude .cache/.tmp". A folder believed on `PATH` for being under a `.cache` of the checkout is never one under `.cache/.tmp` (where every agent's scratch trees go, c0194): there only the run's own folders are kept, and the runner names them.

## Non-goals
- The empty-transaction refusal of a fetch with nothing new: c0122.
- The jails themselves (macOS `sandbox-exec`, the Linux jail of c0075).

## Solution
- Verify the inherited folder before trusting it: for example, it is the repository's own guard folder (by path), or its hooks match the guard's (by content).
- Otherwise refuse the inherited value rather than use it.


## Design
Paths today (the capture's `scripts/lib/...` became `z-nile/lib/...` in c0114): the fence is `z-nile/lib/fence.sh`, the ref guard's hooks are `z-nile/lib/git-hooks/` (19 files: the 18 hooks and `.repo.sh`), the fence's specs are in `z-nile/tests/`. Decisions relied on: none from `game-design.md` (a tooling chore). The rules it follows are the zz-test skill's "Specs never touch the real repository" and zz-arch rule 7 (guards fail closed). The design has three parts, in the order of the Problem: **(1)** the fence trusts only its own hook folder (pin, candidates, messages); **(2)** the guard's own files ignore the caller's shell and `CDPATH`; **(3)** every launcher starts its children in the allow-listed environment (the scope decision of 2026-11-01). Part 3 supersedes the earlier idea of a partial fix: with it, the exported-function, `PATH`, `BASH_ENV`, `CDPATH` and `GIT_EXEC_PATH` routes are closed at the first process of ours, and parts 1 and 2 stay as the second line (they also hold where the fence is used on its own, as the fixtures use it).

**The rule.** A hook folder is *the guard's own* when its files are exactly the pinned content: the SHA-256 over the folder's entries, in byte order of name, each as `len(name) NUL name NUL len(bytes) NUL bytes`. Anything that is not a plain file (a link, a folder), an unreadable entry, an empty folder or a missing folder has no digest. `reference-transaction` and `pre-push` must also be executable (git silently skips a hook that is not). File modes are not part of the digest (fixtures `chmod -R +x` their copies). The fence uses a folder only when it is the guard's own, whatever PICKMAN_FENCE_HOOKS says, **its own folder included**: an edited stub or a stray file in `z-nile/lib/git-hooks/` (an editor backup, Finder's `.DS_Store`, both invisible to `git status`) makes the fence refuse. That strictness is kept on purpose (a name list that skipped some files would need its own rule and spec), and the refusal says *what* differs (below) and never prints the pin.

**Hooks changes** (design review 004 F1): `z-nile/lib/git-hooks/.repo.sh` (`(CDPATH= cd -P -- "$_d" && pwd -P)`) and `pre-push` (`CDPATH= cd -P -- "$url"`), one line each; every other hook is untouched, so the pin changes once, with these two.

**`z-nile/lib/fence.sh` changes** (the prototype is `experiments/prototype.patch`, a diff against the tree of 2026-11-01 that passes every spec of this issue):
1. `_PICKMAN_FENCE_HOOKS_SHA256=<hex>` and `_PICKMAN_FENCE_HOOKS_NAMES="<the 19 names, sorted, space-separated>"`: the pins, constants at the top of `fence.sh` (the names only feed the diagnosis). The digest's value when this was designed: `a14e39a44d5ab57bea2b4a510d98c0e5bf98b880fe0d3929b155f7cac26cced2`. The executor recomputes both from the folder as it is on the day (`. z-nile/lib/fence.sh; pickman_fence_hooks_digest z-nile/lib/git-hooks`; `ls -A z-nile/lib/git-hooks | LC_ALL=C sort | tr '\n' ' '`), because c0122 or another item may have changed a hook meanwhile.
2. `pickman_fence_hooks_digest <dir>`: prints the digest, exit 1 when it has none. Inline `command perl` (so an exported shell function named `perl` is not what answers) with `Digest::SHA` (core since perl 5.9.3; `fence.sh` already needs perl for the sentinel's rename), because fixtures copy `fence.sh` alone. About 10 ms.
2b. `_pickman_fence_hooks_why <dir>`: words for a message, never the pin: `not a folder`, or the entries the folder has that the guard has not (`unexpected .DS_Store`; whole names, walked by glob, so `pre-push copy` is one name and `*` is never expanded), the guard's it lacks (`missing commit-msg`), else `a file differs in bytes or kind, or reference-transaction or pre-push is not executable`.
3. `_pickman_fence_hooks_ok <dir>`: true only when the two guard hooks are executable and the digest equals the pin. Every other outcome (perl missing, `Digest::SHA` missing, unreadable file) is false: the one explicit yes is the match (zz-arch rule 7, lesson guard-no-is-explicit).
4. In `pickman_fence_env`, replacing the "first guard's hook stays in force" lines: candidates in order, the inherited value first (so the first guard's folder stays in force down nested fences, and a nested copy that lacks `git-hooks` finds it), then `$_pickman_fence_lib/git-hooks`. Each candidate is resolved with `cd … && pwd -P` *first* and the resolved path is what is checked and what is used (design review 002 F2): a link retargeted, or a function named `pwd`, between check and use cannot swap the folder; a candidate that does not resolve is "not a folder". The first that is the guard's own is used. A non-empty inherited value that is not the guard's own prints `fence: ignoring PICKMAN_FENCE_HOOKS=<value> (not the ref guard's own: <why>)` on stderr and is not used.
5. The refusal keeps its place (read-only, before anything changes) and its words' start, `fence: no ref guard at <own folder> (<why>); refusing. Stop and report this.`, now for "no folder that is the guard's own"; a refused fence leaves the inherited `PICKMAN_FENCE_HOOKS` as the caller had it. Under the jail's waiver (all three runner markers) with no folder of the guard's own, the fence goes on without hooks, as it does under the jail, and no longer sets `core.hooksPath` at an unverified folder.
6. After the point of no return (where `GIT_CONFIG_COUNT` is rebuilt), **on the non-jail path only** (a `manage` flag set inside `if [[ $jail != sandbox-exec ]]`): `unset PICKMAN_FENCE_HOOKS`, then export it only when a verified folder was chosen. A rejected value is never left in the environment for the next fence or child. Under the jail (`pickman_fence <dir> specs sandbox-exec`) the fence neither reads nor changes the variable, as today (design review 001 F6): the kernel covers the repository there, and every fence that later uses the value verifies it.
6b. At source time `unset CDPATH` (before `_pickman_fence_lib` is computed), and `unset GIT_EXEC_PATH CDPATH` in the environment strip beside `GIT_DIR`. A person whose git needs `GIT_EXEC_PATH` (a relocated build) loses it inside a fenced check: git finds its own exec path; noted, not pinned.
7. Comments: the header line about the hooks folder says it is "pinned by content (c0123)"; the old "the first guard's hook stays in force: a nested copy may lack …" comment is replaced by the prototype's.

**Refuse or ignore (the capture allowed both: "refuses an inherited value it can't verify").** Ignored with a message, then the fence goes on with its own folder if that is the guard's own, and refuses if it has none. Why: the ref guard stays on either way, and an outer fence from an older checkout (a different hook folder) must not make a newer nested copy refuse. A forged value cannot switch anything off, and the person sees it named.

**The real repository's own hook (c0189).** c0189 installs a `reference-transaction` hook in the real repository's common hooks folder (`<git-dir>/hooks/`). It is not the fence's own hook, and the fence treats it as repository data, as it does a fixture's own hooks since c0058:
- `core.hooksPath` is always the guard's folder; `.git/hooks` is never a candidate (a folder holding an executable `reference-transaction` with other bytes fails the digest, and a spec pins it).
- The guard's `reference-transaction` stub decides only in the `prepared` phase: there it runs the repository's own hook only *after* it allows the update, and a refused update never reaches it as `prepared`. Every other phase (`preparing`, `committed`, `aborted`) is passed straight to it, so it also sees a refused update, as `preparing` then `aborted` (design review 001 F4; checked with a logging hook). Git ignores a hook's exit code outside `preparing` and `prepared`, so the repository's hook can only refuse more. A c0189 hook that acts on `prepared` only (its Solution does) is consistent with this; one that logs every call sees the other phases. `pre-push` chains after its decision. All existing behaviour, unchanged, now pinned phase by phase.
- **c0189's hook is a script a caller starts, so it is held to the same rule as the guard's 18 hooks** (review 008 F2). c0189 adds `z-nile/lib/repo-hooks/reference-transaction` (POSIX sh, executable) as a tracked file; every git in the real repository starts it, and macOS's `/bin/sh` imports an exported function named `git` into a plain `#!/bin/sh` script (E13). ### Part 3: the allow-listed environment (the scope decision)
**The rule.** The first process of ours a caller starts puts its environment on a list and its `PATH` on a fixed value; everything it starts after that inherits only that. The list is one file, `z-nile/lib/cleanenv.list` (`allow <NAME>` or `<PREFIX>*`; `fence <NAME>` for the fence's own exported state, kept only while `PICKMAN_FENCE_REAL_GIT` is set; `path <dir>` for the fixed directories in order, a leading `~` being `$HOME`; `internal <glob>` and `proof <glob>` for the run's own `PATH` entries). The prototype's list keeps: `HOME USER LOGNAME SHELL TERM COLORTERM NO_COLOR CLICOLOR* FORCE_COLOR LANG LC_* TZ TMPDIR __CF_USER_TEXT_ENCODING SSH_AUTH_SOCK GH_TOKEN GITHUB_TOKEN GH_ENTERPRISE_TOKEN GITHUB_ENTERPRISE_TOKEN GH_HOST GH_CONFIG_DIR` and the proxy and certificate names (`http_proxy` family, `SSL_CERT_*`), `CI GITHUB_ACTIONS GITHUB_PATH` (setup.sh hands Rokit's folder to the next workflow step through it), the shell's own `PWD OLDPWD SHLVL _`, `AC_LIST`, `ZN_*`, `PICKMAN_*` (our own knobs and markers), `CLAUDE_PROJECT_DIR` and `CLAUDE_ENV_FILE` (the two names the SessionStart hook reads; the rest of the `CLAUDE_` family is dropped) and `GIT_AUTHOR_*` and `GIT_COMMITTER_*` (identity: a sample of 51 specs showed the tracker's commit specs pass them through `./zn`); the fence's state (`GIT_CEILING_DIRECTORIES GIT_CONFIG_COUNT GIT_CONFIG_KEY_* GIT_CONFIG_VALUE_* GIT_ALLOW_PROTOCOL GIT_SSH_COMMAND GIT_TERMINAL_PROMPT`); `PATH` = the run's own entries, each believed **by where it is, never by a variable and never by how its path reads** (design reviews 005 to 008: every marker is a name a caller can set, every place an agent can write is forgeable, and on a volume that folds letter case `.cache/.TMP` is `.cache/.tmp`), then `~/.rokit/bin:/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`. A run's entry is kept only when (1) its name matches an `internal` glob (`*/pickman-guard.*`, `*/pickman-run.*/bin`, `*/pickman-stub.*`), (2) its **canonical path** matches one again, and (3) that path lies **inside a folder the runner registered for this run**. Canonical means `cd -P` with `CDPATH` empty, then the spelling the kernel stores, from the program `/bin/pwd -P` (the shell builtin's `pwd -P` keeps the caller's letters: review 008 F1); both readers run that one command on every path they compare: the entry, the checkout that holds the cleaner, and each registry line, and refuse a result that is not one absolute line. The runner writes the registry, `tests-run.lock/folders` (its run folder, resolved), right after it takes its lock, and the file goes with the lock; the cleaner reads it from the `.cache` of every top-level folder of its own checkout (and of the trusted checkout; never a dot-folder: both readers read the same list), found from its own file's place (for a copy kept under a `.cache`, the checkout above the first `/.cache/`), never from the environment. A registered folder is believed **only while the run that registered it holds it** (review 009 F2): its `.pickman-owner` (the pid, a tab and the process's start id, which the runner writes) names a process that is alive and is not a reused pid. Alive is `kill -0`, and `Operation not permitted` counts as alive (a signal across the jail's edge, as the runner's `fence.alive` reads it inside a jail; the readers read it as alive everywhere, because they cannot tell whether they run in one without trusting a marker, and a pid of another user's is then judged by its start id; the probe runs in the C locale, since the message is translated; a pid of 0, the caller's own process group, is refused); a start id that is missing or cannot be read now leaves it holding, as `fence.holds` does; a folder with no readable owner is dead. The shell reader decides it in `_pickman_holds` and the Lune reader in `cleanenv.holds`, both with the start-id program of `tests/lib/fence.luau` (`STARTED`, embedded in both readers and pinned equal by `cleanenv.spec`); a killed run's registry, which `SIGKILL` leaves behind, therefore proves nothing. Nothing is believed for lying under a `.cache`: a stub, bin or guard folder a spec left behind, one an agent made with `mktemp -t pickman-stub` in `.cache/.tmp`, and another spelling of either all lie outside a registered folder and are dropped (this keeps the user's "Exclude `.cache/.tmp`" decision and goes further). A link out of the registered folder is dropped, an entry that matches two globs is kept once, and the fence's own state (`GIT_CEILING_DIRECTORIES GIT_CONFIG_COUNT GIT_CONFIG_KEY_* GIT_CONFIG_VALUE_* GIT_ALLOW_PROTOCOL GIT_SSH_COMMAND GIT_TERMINAL_PROMPT`, the `fence` names; a check-mode fence also unsets `GIT_SSH_COMMAND`, `GIT_ALLOW_PROTOCOL` and `GIT_TERMINAL_PROMPT` itself before it works, since a check's git uses the person's own ssh and protocols (review 007 F3)) is kept only while a kept `proof` folder (`*/pickman-run.*/bin` or `*/pickman-guard.*`, the run's own, one of which every run puts on `PATH`) is on `PATH`: a forged `PICKMAN_FENCE_REAL_GIT` gains no folder and keeps no fence name, and a proof-named folder nobody registered proves nothing. `~` is the account's home from the passwd database (`/usr/bin/id -un`, then tilde expansion of `~user`, which reads `getpwnam`), **never `$HOME`** (review 005 F1). `GIT_CONFIG_GLOBAL` is set by the cleaner to the account's `~/.gitconfig` (else `~/.config/git/config`, else `/dev/null`) and `XDG_*` is not admitted: git's global config names programs git runs (`core.fsmonitor`), so neither `HOME` nor `XDG_CONFIG_HOME` may pick it; and because git expands a leading `~` in a config path from `$HOME`, the cleaner **refuses** when `HOME` is not the account's home and the pinned config holds a `~` path under any key but the data files git only reads (`excludesFile`, `attributesFile`, `template`, `ignoreRevsFile`), naming the line (review 006 F3). Rokit's folder stays first because it pins the tools (`lune` 0.10.5; Homebrew may carry another). Everything else is dropped: `XDG_*`, exported functions (`BASH_FUNC_*`), `BASH_ENV`, `ENV`, `SHELLOPTS`, `CDPATH`, `GIT_EXEC_PATH`, `GIT_DIR` and the other `GIT_*`, `LD_*`/`DYLD_*`, `PYTHON*`, and every name no one listed. A name is added to the list in a reviewed change (a spec pins the list's shape, not its members).

**The shell reader and the entry scripts.** `z-nile/lib/cleanenv.sh` defines `pickman_clean_env "$0" "$@"`, using only builtins and the absolute `/bin/pwd` until `PATH` is fixed. If the exported names and `PATH` already are the list's, it returns. Otherwise it starts the script again, in place: `exec /usr/bin/env -i <allowed NAME=value…> PATH=<fixed> PICKMAN_CLEANED=<its own pid> /bin/bash -p "$@"`. The cleaner first reads the account's name and home with absolute `/usr/bin/id` and a tilde expansion (it refuses when it cannot tell), and an entry kept once however many `internal` globs match it. A list line with no value (`allow` alone) is an unknown entry for both readers. The marker carries the shell's own pid (an `exec` keeps it): a restarted shell that is still dirty refuses instead of looping, and a value forged by the caller can only make it refuse. With no script to restart (an inline `bash -c 'source ac.sh'`, which fixtures use) it **refuses unless the shell is privileged (`[[ $- == *p* ]]`, a test no imported function can fake)**, then unsets the valid names in place and refuses when an imported-function carrier (a name that is no identifier) is present (design review 006 F5; the fixtures that call it that way start `/bin/bash -p -c`). A list line whose value is empty (`allow `, `path `, `internal `, `proof `) is an unknown entry for both readers; the shell's `path ` would have put the current directory on `PATH` (review 006 F4). Every script a caller can start begins `#!/bin/bash -p` and these three lines (`_c=${BASH_SOURCE[0]%/*}…; . "$_c/…/cleanenv.sh" && pickman_clean_env "$0" "$@" || exit 1`): `zn`, `z-nile/check.sh`, `z-nile/setup.sh`, `scripts/hooks/post-edit.sh`, `scripts/hooks/stop.sh`. The eight forwarders (`scripts/{tracker,check,setup}.sh`, `pickman/check.sh`, `pickman/scripts/{check,tracker}.sh`, `z-nile/scripts/{check,tracker}.sh`) do nothing before they `exec /bin/bash -p "${0%/*}/…"`, so they are `-p` and use no external command. `z-nile/lib/ac.sh` calls it first (a `check.sh` the engine starts is already clean; one started by hand is restarted, or refused when its bash ran a `$BASH_ENV`). `#!/bin/bash -p` is what keeps `$BASH_ENV` unread and functions un-imported: privileged mode, checked on macOS bash 3.2 (E13). The git hooks start `#!/bin/sh -p` (all 18) for the same reason, and `.repo.sh` and `pre-push` resolve with `CDPATH= cd -P --`.

**The Lune reader and the launchers.** `z-nile/lib/cleanenv.luau` (pure `parse` and `clean(env, spec, gitConfigGlobal)`, plus `facts`, `load`, `current` and the restart's argument list at the edge; `facts` asks `/usr/bin/id` and `/bin/sh -p` for the account's home, so no environment variable decides it) applies the same rules to `process.env`. `z-nile/tests/run.luau` calls it before anything else that starts a process (before `fenceLib.homes()`, which starts bash and lune, and before `fence.enter()`; design review 005 F4): a dirty runner starts itself again as `/usr/bin/env -i <allowed> PATH=<fixed> lune run tests/run -- --cleaned <args>`; `--cleaned` marks the restart, and a restarted runner that is still dirty refuses. The shell one has to exist because the first process is bash (`zn`, the gate); the Lune one because `tests/run` is a Lune script a person starts directly.

### Scalability
Per fence setup: one `perl` start per candidate tried (one when the inherited value or the own folder is the guard's, two when a bad inherited value is tried first), reading 18 files of about 10 KB in all. Measured +15 ms per `pickman_fence` call (10 calls: 0.41 s before, 0.56 s after). A gate sets up one fence per home and per `check.sh`; none grows with the items. Part 3 adds to every entry script start the cleaner's checks (`id -un`, the tilde expansion, a `/bin/pwd` for the checkout and one for each registry line and each `internal` entry, and while a run is live a `kill -0` and a start-id `perl` per registry line): measured about 15 ms per start of an already-clean script (20 starts of an empty prologue script: 0.54 s against 0.25 s without it); while a run is live and a registry line exists, a start costs about twice that (review 010: 43 ms against 88 ms from a dirty shell, the perl start-id probe and the `kill` per line), which every `./zn`, `ac.sh` and gate start inside a run pays, plus one `exec` of `/usr/bin/env` and a second bash start from a dirty shell (typically about 10 ms more), and one Lune restart for a dirty `tests/run` (the runner already restarts once for the browser guard, so a run goes from two starts to three). The jail's own spec runs set no hooks, but every fixture fence a jailed spec sets up without a jail argument (`ac.sh` in a fixture, `c0114/guards`, `c0120/homes`, about 40 spec files use `pickman_fence`) starts perl once per candidate inside the sandbox: measured 10 digests under a `sandbox-exec` profile in 0.14 s, so well under 1 s across a gate.

### Maintainability
One definition of "the guard's own": `pickman_fence_hooks_digest`. The pin is one constant, and a spec checks it against the folder, so editing a hook is a one-line, loudly-failing follow-up. A future jail (c0075's `bwrap`) changes the `if` around the block, not the rule. A new hook file in the folder is a pin update. Fixtures copy `fence.sh` alone; the digest function is inline in it. A new variable a launcher must pass is one line in `cleanenv.list`; a new entry script is one shebang and one prologue (`entries.spec` fails until it has them); a new Lune spawn of a shell is `/bin/bash -p` (the same scan).

### Usability
The person who exports a bad value sees `fence: ignoring PICKMAN_FENCE_HOOKS=<value> (not the ref guard's own: <why>)` and the fence goes on guarded. Where no folder is the guard's own, `fence: no ref guard at <own folder> (<why>); refusing. Stop and report this.` names the folder and what differs (`unexpected .DS_Store`, `missing commit-msg`, `a file differs in bytes…`), and never the pin, so the person removes the stray file instead of re-pinning. The editor of a hook gets, from the pin case: `z-nile/lib/fence.sh pins <old> but z-nile/lib/git-hooks is <new>: set _PICKMAN_FENCE_HOOKS_SHA256 to it`. There is no command-line change and no new list to join.
