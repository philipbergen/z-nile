# c0123: Fence trusts only its own ref guard hooks

## Problem
`pickman_fence` in `scripts/lib/fence.sh` keeps an inherited `PICKMAN_FENCE_HOOKS` whenever that folder has an executable `reference-transaction` ("the first guard's hook stays in force: a nested copy may lack scripts/lib/git-hooks"), and points `core.hooksPath` at it. So a caller that exports `PICKMAN_FENCE_HOOKS` at a folder of permissive `reference-transaction` and `pre-push` hooks switches the ref and push guard off for every git a check runs. The macOS jail still protects spec runs there, but Linux runs and `check.sh` files have only the hooks. Found by c0120 code reviews 002 and 003 (2026-10-21).

Confirmed 2026-10-21 in a scratch fixture (a throwaway checkout with copies of `fence.sh` and `scripts/lib/git-hooks/`, fenced as a `check.sh` flow, then `git update-ref refs/heads/evil HEAD` in it):

```
--- no inherited value:
hooks=…/d2/checkout/scripts/lib/git-hooks
fence: a check tried to change refs in the real repository (…/d2/checkout/.git); refused
fatal: in 'prepared' phase, update aborted by the reference-transaction hook
exit 128
--- inherited PICKMAN_FENCE_HOOKS=…/d2/permissive:
hooks=…/d2/permissive
exit 0
```

and the branch `evil` exists afterwards.

**Outcome:** the fence trusts only hooks that are its own, or refuses an inherited value it can't verify, so no inherited variable can switch the ref guard off. Nested fences keep working, including a nested copy that lacks `scripts/lib/git-hooks`.

## Non-goals
- The empty-transaction refusal of a fetch with nothing new: c0122.
- The jails themselves (macOS `sandbox-exec`, the Linux jail of c0075).

## Solution
- Verify the inherited folder before trusting it: for example, it is the repository's own guard folder (by path), or its hooks match the guard's (by content).
- Otherwise refuse the inherited value rather than use it.
