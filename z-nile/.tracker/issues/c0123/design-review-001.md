### F3 [medium] A stray ignored file in `git-hooks/` refuses every fence with no cause named
Where: Design "The rule" (every entry is digested), Usability, `fence.sh` refusal message
Evidence: `.gitignore:7` ignores `.DS_Store` and the user's `~/.gitignore_global` ignores `*~` (`git check-ignore -v` on `z-nile/lib/git-hooks/.DS_Store` and `…/reference-transaction~`), so neither shows in `git status`. In a scratch checkout with the prototype I added an empty `z-nile/lib/git-hooks/.DS_Store` and ran `pickman_fence`: `fence: no ref guard at …/z-nile/lib/git-hooks (the pinned reference-transaction, pre-push and the other hooks); refusing. Stop and report this.` The folder is there and both hooks are executable; nothing tells the reader that an extra file is the cause.
Critique: on the user's macOS host, opening the folder in Finder or leaving an editor backup after touching a hook makes every `check.sh`, `./zn check` and Linux gate refuse, and agents are told to stop and report with no clue. Usability claims the hook editor gets the pin case's message, but this fence refusal is what everyone sees first. Failing closed is right; the diagnosis is missing.
Consequences: the tempting fix, ignoring dotfiles or backups in the digest, is a narrowing a later attacker could use (any name git doesn't run is harmless today, but the list then needs its own rule and spec). A message that prints the computed digest invites an agent to re-pin to get past the guard.
Recommendation: keep the strict digest and make the refusal say why: when the own folder exists, the message names what differs. Either pin a per-file manifest (name → sha, 19 lines) so the message can say `unexpected file .DS_Store` / `pre-commit differs` / `commit-msg missing`, or keep the single digest and on mismatch list the folder's entries with the hint "an extra file (an editor backup, .DS_Store) counts too: remove it; never change the pin to make a fence pass". Add a case: own folder + `.DS_Store` → refused, stderr names `.DS_Store`, and contains no pin value. Update the Usability section and, if the manifest form is chosen, the wording sentence "pins the SHA-256 of every file's name and bytes".

### F4 [medium] The c0189 contract is wrong about phases: the repository's own hook runs before the guard decides and after it refuses
Where: Design "The real repository's own hook (c0189)" ("the guard decides first, the repository's hook can only refuse more, and a refusal by the guard never reaches it"); the skill sentence pinned by `wording.spec` case 1 ("the guard runs it after it allows an update, and it can only refuse more"); Rules row "the repository's own hook runs after the guard allows, and decides alone after that"
Evidence: `reference-transaction` starts with `[ "$1" = prepared ] || chain "$@"`. In a scratch checkout with the prototype, an own `.git/hooks/reference-transaction` that logs `$1`, fenced as a check.sh flow, then `git update-ref refs/heads/x HEAD`: the guard refused (`fence: a check tried to change refs in the real repository …; refused`, exit 128) and the own hook's log was `preparing` then `aborted`. So the repository's hook runs in `preparing` before the guard has decided anything, and does receive the transaction the guard refused (as `aborted`).
Critique: this is the sentence c0189's author will build on, and it is pinned into the zz-test skill by a promoted spec. A c0189 hook written on the belief that it is only ever called for updates the guard allowed (for example, one that logs or acts on every call) would misread `preparing`/`aborted` calls. Safety holds (in `prepared` the guard decides first; git ignores exit codes except in `preparing`/`prepared`, so the own hook can only refuse more), but the stated contract doesn't.
Consequences: the chaining case currently asserts only that `prepared` appears in the log after an allowed fetch; it would not catch a guard that chains `prepared` before deciding.
Recommendation: restate it phase by phase in the Design and the skill sentence (and in `wording.spec`): "the guard decides only in the `prepared` phase and runs the repository's own hook there only after it allows the update; every other phase (`preparing`, `committed`, `aborted`) is passed straight through, so the repository's hook also sees a refused update as `aborted`, and it can only refuse more." In the chaining case, also assert that after a refused branch write the own hook's log holds no `prepared` (only `preparing`/`aborted`), and add that mutant (chain `prepared` before deciding) to the row. Tell c0189 (its Solution already acts on `prepared` only, which is consistent).

### F5 [medium] An exported shell function or PATH still decides the new check, and the design doesn't say what remains of "no inherited variable"
Where: `pickman_fence_hooks_digest` (runs `perl` by name); Outcome ("so no inherited variable can switch the ref guard off"); skill bullet "The guards trust their own environment" as rewritten
Evidence: scratch checkout `B` holding `fence.sh` alone, `PICKMAN_FENCE_HOOKS` at a folder whose `reference-transaction` and `pre-push` are `exit 0`, and the inherited variable `BASH_FUNC_perl%%='() { echo f9f467d5…; }'`: the fence trusted the permissive folder (`HOOKS=…/P`) and `git update-ref refs/heads/evil HEAD` printed `ESCAPED`. The class is older than this issue: with today's guard folder and nothing inherited, `BASH_FUNC_git%%='() { command git -c core.hooksPath=/nonexistent "$@"; }'` gives `ESCAPED` from bash and from a `/bin/sh -c` child. So this is not a new weakening, but the rewritten bullet now reads as if the hook route is closed while an inherited variable still switches it off.
Critique: the reviewer brief and the Outcome both ask whether any inherited variable can still switch the guard off. The design never names exported functions or PATH. The digest call is one place where the fence can cheaply stop trusting a function.
Consequences: `command perl` closes the function route for the digest but not a PATH `perl`; neither closes `git` itself. Closing the whole class (refusing or unsetting imported functions, pinning PATH) changes how every check runs and is a scope question.
Recommendation: (1) call `command perl` in `pickman_fence_hooks_digest` and add a case: exported `perl` function printing the pin + permissive inherited folder in `bare` → refused with `ignoring`; (2) name the residue in the "trust their own environment" bullet: "exported shell functions (`BASH_FUNC_*`) and `PATH` reach git and perl themselves; review a check that sets them"; (3) escalate to the user: either this issue also closes exported functions for `git` (for example the fence refuses when the environment carries `BASH_FUNC_git%%`/`BASH_FUNC_perl%%`, or unsets imported functions; cost: a new refusal for every caller, a spec, and a wording change), or that class is captured as its own issue and the Outcome is read as being about `PICKMAN_FENCE_HOOKS`, recorded with a `Decided with the user` line.

### F6 [medium] The jailed fence now drops a genuine inherited folder it never examined, which the Design doesn't say
Where: prototype `unset PICKMAN_FENCE_HOOKS` after the point of no return (Design item 6: "A rejected value is never left in the environment"); `z-nile/tests/lib/fence.luau:858` (`pickman_fence "$1" specs "$2"` with `$2 = sandbox-exec` under the jail)

Recommendation: move the `unset`/re-export inside the non-jail path (under the jail leave the inherited variable exactly as the caller had it, as today), state it in item 6 ("under the jail the fence neither reads nor changes it; every fence that uses it verifies it"), and add a case: genuine inherited value, `pickman_fence <dir> specs sandbox-exec` → the variable is unchanged and `core.hooksPath` is empty.
