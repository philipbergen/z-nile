### F1 [medium] The residue is misstated: `command perl` does not close the function route, and PATH or a function still makes a permissive `PICKMAN_FENCE_HOOKS` pass the pin itself (repeat of design-review-001 F5)
Where: Design "What an inherited variable can still do" ("`BASH_FUNC_perl%%` for the new digest, which `command perl` now closes"); skill sentence pinned by `wording.spec` case 2 ("Exported shell functions (`BASH_FUNC_*`) and `PATH` reach git itself, which the pin does not cover"); Rules row "perl is asked for by itself" (M19)
Evidence: a scratch repository holding the prototype's `fence.sh` alone, `PICKMAN_FENCE_HOOKS` at a copy of the guard folder whose `reference-transaction` and `pre-push` are `exit 0`, then `pickman_fence "$PWD"` and `git update-ref refs/heads/evil HEAD`:
- nothing else inherited: `fence: ignoring … (not the ref guard's own: a file differs …)`, `REFUSED` (correct);
- `PATH=<dir with a perl that echoes the pin>:$PATH`: `HOOKS=…/perm`, `ESCAPED`;
- `BASH_FUNC_command%%='() { echo <pin>; }'`: `HOOKS=…/perm`, `ESCAPED`;
- a *genuine* inherited folder and `BASH_FUNC_pwd%%='() { echo …/perm; }'`: `HOOKS=…/perm`, `ESCAPED` (the folder is verified, then `$(cd "$hooks" && pwd -P)` returns another one; see F2).
Under bash 3.2 (macOS `/bin/bash`), imported functions named `command`, `builtin` and `unset` all shadow the builtins (checked: `type command` says "command is a function"; `unset -f` prints the function's output). Bash refuses to import a function whose name has a `/` (`error importing function definition for '/usr/bin/perl'`).
Critique: the captured mechanism (an inherited `PICKMAN_FENCE_HOOKS` at a permissive folder) still switches the guard off with one more inherited variable, and the skill tells reviewers the opposite: that functions and PATH only reach "git itself, which the pin does not cover". Round 1 found a hole in the perl call, and `command perl` closes only the one spelling a spec pins. No per-call hardening inside bash can close this, because every command bash runs by name can be a function. The question put to the user has to say that, or the user decides on a false premise.
Consequences: rewording the sentence changes `wording.spec` case 2's pinned phrase. Calling `/usr/bin/perl` by absolute path does close PATH and imported functions for the digest (both hosts have it; Linux CI's `ubuntu-latest` does), but `cd`, `pwd`, `echo` and git remain. The only complete closure is outside bash: whoever starts `bash` for a `check.sh` or a spec run (`tests/run`, `ac.sh`'s callers, `tests/lib/fence.luau`) strips every `BASH_FUNC_*` and pins PATH first. That changes how every check runs, so it belongs to the user.
Recommendation: (1) say it accurately in the Design paragraph and the skill sentence, for example: "Exported shell functions (`BASH_FUNC_*`, including ones named `command`, `cd` or `pwd`) and `PATH` reach every command the fence and its hooks run by name, the pin's own perl included, so with one of them a permissive `PICKMAN_FENCE_HOOKS` still passes: review a check that sets them." Pin that phrase in `wording.spec` case 2. (2) Keep `command perl` and its case, but say what M19's row really proves (a function named `perl`), or switch to `/usr/bin/perl` with a case for a PATH perl. (3) escalate to the user: the hook-folder route is closed only in an environment with no imported functions and a clean PATH. Options: (a) this issue also has the launchers start bash with every `BASH_FUNC_*` removed and a fixed PATH (cost: a change to how every check and spec run starts, specs for each launcher, and the skill text); (b) capture that as its own issue and record a `Decided with the user` line reading the Outcome as the hook-folder route in a clean environment; (c) `/usr/bin/perl` plus F2's ordering as a partial step here, with the rest as in (b).
Lesson: zz-arch/guards-decide-from-the-tools-resolution

### F2 [medium] The fence verifies one path and uses another: resolution happens after verification
Where: prototype `pickman_fence_env`: `_pickman_fence_hooks_ok "$inherited"` → `hooks=$inherited` → `[[ -z $hooks ]] || hooks=$(cd "$hooks" && pwd -P) || hooks=`; Design item 4 ("The first that is the guard's own is used, resolved with `pwd -P`")
Evidence: F1's fourth probe: a genuine inherited folder passes `_pickman_fence_hooks_ok`, then the resolution step's `pwd` (a function there) names a permissive folder, and `core.hooksPath` is set to it (`ESCAPED`). Without functions the same gap is a race: an inherited value that is a link (the spec's `link-to-guard` case) is verified through the link and resolved later, so a link retargeted in between is used unverified.
Critique: the order is new in this issue (the old code never resolved the path). "Verify what you use" is the general rule (lesson guards-decide-from-the-tools-resolution), and here it costs nothing: resolve each candidate first, then verify the resolved path. A `pwd` function then makes verification fail, and the fence falls back or refuses (fails closed).
Consequences: the "ignoring" message should still print the value the caller exported, not the resolved one (the spec greps `ignoring PICKMAN_FENCE_HOOKS=<dir>`). A candidate whose `cd` fails is "not a folder", as today. The link case's expectation (`HOOKS=[{own}]`) is unchanged.
Recommendation: in item 4, resolve each candidate with `pwd -P` before `_pickman_fence_hooks_ok`, and use exactly the resolved path that passed. Add a Rules row "the folder used is the folder verified" with a case: a genuine inherited folder and `BASH_FUNC_pwd%%` printing the permissive folder → not `ESCAPED` (refused or guarded). Its mutant is today's order (resolve after verify), which that case kills.

### F3 [medium] The digest's framing has no case and no row, and the documented fallback would drop it
Where: Design "The rule" (`len(name) NUL name NUL len(bytes) NUL bytes`); `pickman_fence_hooks_digest`; E6's fallback ("compute with `shasum -a 256`/`sha256sum` as a second branch"); Rules row "any difference from the guard's files rejects"
Evidence: I mutated the prototype's `$s->add(length($n), "\0", $n, "\0", length($c), "\0", $c)` to `$s->add($n, $c)`, re-pinned the constant, and ran `inherited-hooks.spec`: 11 passed, 0 failed. With the real framing, folders `{a: "bc"}` and `{ab: "c"}` give different digests (`1703b5df…` and `4a727fea…`). Without it they give the same digest.
Critique: the framing is what makes "names and bytes" one unambiguous record. Without it, a renamed entry can absorb the tail of the file before it, so a guard hook could be cut down to its comment header (a script that exits 0) while the digest stays the same. That is hard with today's files (the names would need the moved bytes, with no `/`, in sort order), but the mutant is plausible and nobody listed it: E6's fallback is the obvious shell rewrite, and `cat`-ing files into `shasum` loses the framing exactly.
Consequences: none beyond one case; the fallback, if it is ever written, must keep the framing.
Recommendation: add a row "the digest frames every name and file" (mutant: names and bytes concatenated without lengths) with a case in `the pinned digest is…`: two scratch folders `{a: "bc"}` and `{ab: "c"}` must have different digests (and neither equals the pin). Say in E6 that a shell fallback must hash the same framed stream (for example through `printf '%s\0%s\0%s\0' …`), and that this case gates it.
Lesson: z-design/spec-design-correspondence

### F4 [low] The refusal's diagnosis splits names and expands globs, so it misnames the stray file most likely to appear
Where: prototype `_pickman_fence_hooks_why` (`for n in $(ls -A "$d" 2>/dev/null)`)
Evidence: in the scratch copy, a guard folder with an extra `pre-push copy` (Finder's own name for a duplicated file) gives `unexpected copy`; one with a file named `*` gives `unexpected AGENTS.md; unexpected CLAUDE.md; unexpected pickman; …` (the working directory's entries). The fence still refuses, which is correct.
Critique: Design 2b and Usability promise the message names the entry, so that the person removes it instead of re-pinning. A wrong name sends them looking for a file that isn't there.
Consequences: names with newlines would need `ls -A` replaced with a glob loop; nothing else.
Recommendation: walk the entries with globs (`for f in "$d"/* "$d"/.[!.]* "$d"/..?*; do [[ -e $f || -L $f ]] || continue; n=${f##*/}; …`) and compare whole names. Add `pre-push copy` to the own-folder case's table (`says = "unexpected pre-push copy"`), with a row whose mutant is the word-split loop.
