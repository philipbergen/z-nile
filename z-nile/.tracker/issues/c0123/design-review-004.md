### F1 [high] Any exported `CDPATH` switches the ref guard off through the guard's own, verified hooks, on Linux's dash too, and so does `GIT_EXEC_PATH`. The residue, the skill sentence and option (a) all miss them, and the Design wrongly calls them unclosable
Where: `z-nile/lib/git-hooks/.repo.sh:26` (`(cd "$_d" && pwd -P)`, where `_d` is `.git` or git's relative `GIT_DIR=.git`); `reference-transaction:10` (`input=$(cat)`); Design "What an inherited variable can still do" ("Every command bash runs by name can be replaced by an exported shell function … or by a `PATH` entry"; "Nothing inside bash can close this"); "Open question for the user" ("(a) the launchers start bash with every `BASH_FUNC_*` removed and a fixed `PATH` … only (a) closes it"); the zz-test sentence `wording.spec` case 2 pins ("Exported shell functions (`BASH_FUNC_*` …) and `PATH` reach every command …, so with one of them a permissive `@F@HOOKS` still passes").
Evidence: a scratch checkout holding a copy of the prototype's `z-nile/lib` (genuine hooks, digest matching), no `PICKMAN_FENCE_HOOKS`, `PICKMAN_TEST_JAIL=none`, `pickman_fence "$PWD"`, then `git update-ref refs/heads/evil HEAD`:
```
--- clean            fatal: in 'prepared' phase, update aborted by the reference-transaction hook   GUARDED
--- CDPATH=<dir holding a .git>   hooks=…/co/z-nile/lib/git-hooks   ESCAPED
--- CDPATH=<same>, PICKMAN_FENCE_SPECS=1                              ESCAPED
--- GIT_EXEC_PATH=<dir with a `cat` that swallows stdin>:$(git --exec-path)   ESCAPED
```
The guard hook on its own, fed a branch creation in the protected repository (`PICKMAN_FENCE_REAL_GIT` = the checkout's `.git`), exits as follows:
```
/bin/sh  (bash 3.2)  CDPATH=.:<x>   exit=0      /bin/dash  CDPATH=.:<x>   exit=0
/bin/sh  (bash 3.2)  CDPATH=<x>     exit=0      /bin/dash  CDPATH=<x>     exit=0
same hooks with .repo.sh:26 as (CDPATH= cd -P -- "$_d" && pwd -P): exit=1 in all four
```
`CDPATH=".:/nonexistent" dash -c 'cd .git'` prints the directory. A shell prints the new folder whenever a non-empty `CDPATH` entry resolved a relative `cd` (and `.git` does not start with `./`). So `repo_common` returns two lines, `common` never equals a protected path, and the hook allows the write. The value needs no planted folder: `CDPATH=.:anything`, a common profile setting, is enough. Dash imports no functions, so this is the Linux path, where the hooks are the only guard. With `GIT_EXEC_PATH`, git puts its exec-path in front of `PATH` for the hooks, so `$(cat)` runs the planted `cat` and an empty input is the "fetch with nothing new" that a `check.sh` flow may make. A launcher that fixes `PATH` does not stop that.
Critique: this is the fourth round in which the list of what an inherited variable can still do turned out short (round 1 functions, round 2 `PATH`/`command`, round 3 `pwd` through the hooks, now `CDPATH` and `GIT_EXEC_PATH`). The mechanism is the problem: naming variables one by one from probes. It also leads to two wrong statements the user would decide on. The first is "nothing inside bash can close this": both of these are closed by the guard's own files, with no launcher change (the fixed `.repo.sh` above). The second is "only (a) closes it": (a) as written (strip `BASH_FUNC_*`, fix `PATH`) leaves `CDPATH`, `GIT_EXEC_PATH` and `BASH_ENV` open. (`BASH_ENV` is sourced by every non-interactive bash, `check.sh` included. With a `BASH_ENV` file defining `git` it also ESCAPED, run.) The tempting fix is to add `CDPATH` and `GIT_EXEC_PATH` to the paragraph and the skill sentence. That is round five of the same list.
Consequences: closing them changes `z-nile/lib/git-hooks/` (`.repo.sh`, and `reference-transaction`/`pre-push` if `cat` goes), so the pin changes. Step 1 already recomputes it, c0189's `repo-hook.spec` drives that chain (its `cd` behaviour is unchanged without `CDPATH`), and c0122 must rebase onto the new pin if it lands second. The fence's own `_pickman_fence_lib="$(cd "$(dirname …)" && pwd -P)"` is captured the same way when `fence.sh` is sourced by a relative path (the specs' `. z-nile/lib/fence.sh`). With `CDPATH=.:…` that yields two lines and the fence refuses. That fails closed, but it is the same defect, so clear `CDPATH` there too. If `GIT_EXEC_PATH` is closed by the fence unsetting it (beside `GIT_DIR` in the strip), git finds its own exec path, but a hook run outside a fence keeps it. Reading stdin with the shell's own `read` instead of `cat` closes it in the hook itself.
Recommendation: (1) Close in this issue what the guard's files can close, because the captured Outcome asks for it ("no inherited variable can switch the ref guard off"). In `.repo.sh`, `(CDPATH= cd -P -- "$_d" && pwd -P)`. In `fence.sh`, the same for `_pickman_fence_lib` and the candidates' `cd`. Either `unset GIT_EXEC_PATH` in the fence's strip line or no PATH lookup for the hooks' input (`cat`). Add cases to `inherited-hooks.spec`: genuine hooks with `CDPATH=.:<fixture folder holding a .git>` exported gives GUARDED (mutant: plain `cd`); genuine hooks with `GIT_EXEC_PATH` at a folder whose `cat` swallows stdin gives GUARDED (mutant: `$(cat)` with no unset). Add Rules rows, pin recomputed, and the promotion dry run rerun. (2) Stop listing the residue. State it as a class in the Design and in the skill sentence: "the fence and its hooks run in the caller's environment, so a variable that the shell or git reads to find a command or a file can still switch the guard off". Quote the probed members as examples (exported functions where `/bin/sh` is bash, `PATH`, `BASH_ENV`). Drop "with one of them a permissive `@F@HOOKS` still passes", which says the escape needs a forged hook folder too, while the Design says one variable alone does it. Keep `@F@` in the new needle. (3) Re-cost the options before they go to the user. (a) closes the class only as an allow-listed environment (the launchers start bash under `env -i` with a named list), not by removing `BASH_FUNC_*` and fixing `PATH`. Say what (b) and (c) leave once (1) is in.
Lesson: zz-test/derive-after-stripping-overrides (a guard's derived repository read through an override, here `CDPATH` on a relative `GIT_DIR=.git`); zz-arch/guards-decide-from-the-tools-resolution
