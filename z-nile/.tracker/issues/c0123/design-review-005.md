### F1 [high] The `PATH` rule leaves the ref guard switchable by one inherited variable: `HOME` picks the first fixed directory, and any folder named `pickman-stub.*` is kept first. Both work through the very hook route the capture names
Where: `z-nile/lib/cleanenv.list` (`path ~/.rokit/bin`, the first fixed entry, `~` being `$HOME`; `internal */pickman-stub.*`, `*/pickman-guard.*`, `*/pickman-run.*/bin`); Design part 3 "The rule" and "Boundaries, stated" (b) ("None of them reaches the fence's own `core.hooksPath`"); E15 ("the stub name is the opt-in").
Evidence: `fx/co/probe.sh` is an entry script exactly as the Design writes one (`#!/bin/bash -p`, the three-line prologue), then `. z-nile/lib/fence.sh; pickman_fence "$PWD"`, then `git update-ref refs/heads/evil HEAD`:
```
--- clean                                              git=/usr/bin/git perl=/usr/bin/perl   GUARDED
--- PICKMAN_FENCE_HOOKS=<permissive>                   fence: ignoring PICKMAN_FENCE_HOOKS=… (not the ref guard's own: …)   GUARDED
--- HOME=<evil> (<evil>/.rokit/bin/perl prints the pin) + PICKMAN_FENCE_HOOKS=<permissive>
    PATH=<evil>/.rokit/bin:/opt/homebrew/bin:…   perl=<evil>/.rokit/bin/perl   HOOKS=<permissive>   ESCAPED
--- PATH=<x>/pickman-stub.x:$PATH (<x>/pickman-stub.x/git = env -u GIT_CONFIG_COUNT /usr/bin/git "$@")
    PATH=<x>/pickman-stub.x:/Users/…/.rokit/bin:…   git=<x>/pickman-stub.x/git   ESCAPED
```
The third case is the captured escape (a permissive hook folder trusted), restored by one admitted variable after part 3. The same `HOME` also picks the `lune` that `./zn` and the runner's restart start, and `fence.sh`'s own `PATH="$HOME/.rokit/bin:$PATH"` in `pickman_fence_dirs`. Also, `HOME` and `XDG_CONFIG_HOME` choose git's global config, which names programs git runs. A `core.fsmonitor` script there that runs `git -c core.hooksPath=/var/empty update-ref …` wrote `refs/heads/evil2` in the fenced repository during a fenced `git status`, with `HOME=<dir with .gitconfig>` and with `XDG_CONFIG_HOME=<dir with git/config>` alike (clean: GUARDED). `launchers.spec` cannot see either route: its planted folder is named `evil`, and it never sets `HOME`.
Critique: the Outcome the user ruled on is "no inherited variable can switch the ref guard off", and the Problem names `PATH` as a member. The allow-list closes `PATH` by value and then reopens it through a name pattern any caller can create and a directory any caller can choose. Boundary (b) is true of `core.hooksPath` but hides this. AC4 is passed by an implementation with both holes (the prototype). The tempting fix is to drop `~/.rokit/bin` or rename the stub pattern. The first breaks every host whose `lune` is from Rokit. The second is still a name the caller can make.
Consequences: (1) a home not taken from `$HOME`: the account database's (`~$(/usr/bin/id -un)` in bash, which reads `getpwnam`, not `HOME`). That changes the meaning for every spec that sets `HOME` to a fixture (`c0055/setup-run` does), so the cleaner must keep `HOME` as a value while the fixed `PATH` never derives from it. (2) An `internal` entry kept only when it is named by the pattern *and* resolves (physically, `cd -P`) under a folder the cleaner derives from its own location, never from the environment: the checkout's or a home's `.cache`. This moves the runner's `pickman-guard.*` and `pickman-run.*` from `$TMPDIR` into the home's `.cache` (or they are matched by their own created path, passed only from the runner's restart argument list, never the environment). Spec stubs already live under `.cache`, and `launchers.spec`'s `evil` folder stays dropped because it lacks the name. (3) git's global config for a fenced check: either the fence sets `GIT_CONFIG_GLOBAL` to the account's own `~/.gitconfig` and drops `XDG_CONFIG_HOME` from the list, or Boundaries says that the user's config files (not a variable) are trusted and the variables that relocate them are not admitted.
Recommendation: make the fixed `PATH`, the `lune` the launchers start, and the git config files independent of every admitted variable, as above, in both readers. Add cases to `launchers.spec` (or `cleanenv.spec`): `HOME=<fixture>` with `.rokit/bin/{git,perl}` and an inherited permissive hook folder gives GUARDED (the mutant `path ~` read from `$HOME` fails it); `PATH=<outside .cache>/pickman-stub.x:…` drops the entry (the mutant "name pattern only" fails it); `XDG_CONFIG_HOME` / `HOME` with a `core.fsmonitor` gives GUARDED. Add Rules rows for each, and state in Boundaries what is still the caller's after the fix.
Lesson: zz-arch/guards-decide-from-the-tools-resolution; zz-test/derive-after-stripping-overrides

### F2 [high] CI regresses: `GITHUB_PATH` is not on the list, so `setup.sh` no longer hands Rokit's folder to the next workflow step, and the deploy step cannot find `lune`
Where: `.github/workflows/deploy.yml` (`run: z-nile/setup.sh --tools`, then `run: lune run scripts/deploy-beta`); `z-nile/setup.sh:53-54` (`if [[ -n ${GITHUB_PATH:-} ]]; then echo "$HOME/.rokit/bin" >>"$GITHUB_PATH"`); `cleanenv.list` (no `GITHUB_PATH`).
Evidence: an entry script with the prologue, started as `env CI=true GH_TOKEN=x GITHUB_PATH=/tmp/gp RUNNER_TEMP=/tmp/rt ./probe3.sh`, prints `GITHUB_PATH=unset CI=true GH_TOKEN=set RUNNER_TEMP=unset`. Critique: the beta deploy stops on the next push. Recommendation: add `allow GITHUB_PATH` (and decide `GITHUB_OUTPUT`/`GITHUB_ENV` by reading every script the workflow starts through a launcher: today only `setup.sh`). Name `c0055/setup-run` in Overrides (copy list), and add a `cleanenv.spec` or `launchers.spec` case that starts `setup.sh --tools`'s prologue with `GITHUB_PATH` set and sees it kept. Add `.github/workflows/deploy.yml` to the Design's list of launchers it checked.

### F4 [medium] Boundaries is not complete: launchers that run a caller's environment before cleaning are unstated, and one contradicts the Design
Where: Design part 3 "The Lune reader and the launchers" ("`z-nile/tests/run.luau` calls it before anything else that starts a process"); "Boundaries, stated" (a), (b), (e).
Evidence: (1) `run.luau` calls `fenceLib.homes()` (line 31) before the cleaning block (line 69). That is `/bin/bash -p -c '. fence.sh && pickman_fence_dirs'`, which runs `PATH="$HOME/.rokit/bin:$PATH" lune run z-nile/roots` (`fence.sh:268`) under the caller's `PATH` and `HOME`. (2) `lune run z-nile/engine/main -- check <id>`, started directly, is a Lune launcher that does not clean. Its `runCheck` starts `/bin/bash -p check.sh`, and the template's first external command, `source "$(git -C "$HERE" rev-parse --show-toplevel)/z-nile/lib/ac.sh"`, resolves `git` by the caller's `PATH` and so chooses which `ac.sh` (which fence) is sourced. Boundary (a) states this only for "a check.sh started by hand with plain bash". (3) Boundary (e) says the forged `fence` names "give git config to the forger's own commands, not to the fence of a check". But the engine's and a `check.sh`'s git commands before `ac.sh` fences are not the forger's. I probed `core.worktree` through `GIT_CONFIG_*` against the template's `rev-parse` and it did not move the top (git reads that key only from the repository), so this is a wording defect, not a demonstrated escape.
Critique: the user decided on "every launcher". An unstated launcher is where the next round's hole is.
Consequences: cleaning in `engine/main.luau` (the Lune reader, as `tests/run` does) makes `zn`'s own cleaning a fast path. The engine restart needs the same `--cleaned` guard and a `launchers.spec` case that starts `lune run z-nile/engine/main` directly under the poison.
Recommendation: move the cleaning above `fenceLib.homes()` in `run.luau` (and make `fence.sh` stop prepending `$HOME/.rokit/bin` itself, which F1's fixed `PATH` already covers). Either clean in the engine's entry or state it as boundary (a′) with the supported entry (`./zn`). Reword (e) to what holds. Add the engine case to `launchers.spec` if it is cleaned, and an `entries.spec` assertion that `run.luau` starts no process before the cleaning (a text order check, as the jail-line assertion already does).

### F5 [medium] The two readers are not idempotent on overlapping `PATH` entries, and they disagree on a malformed list line. AC3 claims both and no case seeds them
Where: `cleanenv.sh` (the `internal` loop appends once per matching glob; fixed directories are appended without removing equal internal entries); `cleanenv.luau` `clean` (the same); `parse` versus the shell's `${line%% *}`/`${line#* }`.
Evidence: `env PATH=<x>/pickman-guard.1/pickman-stub.2:/usr/bin:/bin ./probe3.sh` → `cleanenv: the environment is still not the allow-list after a restart; refusing.` exit 1 (the entry matches two globs, so it is kept twice, then four times). `env HOME=<x>/hm/pickman-stub.me ./probe3.sh` gives the same refusal (the fixed `~/.rokit/bin` also matches `*/pickman-stub.*`). The guard turns a loop into a wrong refusal, which is the fail-closed outcome, but AC3 says "cleaning it again changes nothing". By reading: a line `allow` with no value makes the shell admit a variable named `allow` (no space, so `${line#* }` is the whole line), while the Lune parser refuses it as unknown.
Critique: a refusal the person cannot explain ("still not the allow-list") from an ordinary nested temp folder. And two readers that disagree on input `cleanenv.spec` doesn't plant.
Consequences: dedupe means "first occurrence wins" in both readers, and an internal entry equal to a fixed directory is dropped (the fixed one stays in its place).
Recommendation: dedupe in both readers, and make the shell parser require `kind value` with a non-empty value. Seed both readers in `cleanenv.spec`'s comparison with: an entry matching two globs, an internal entry equal to a fixed directory, a duplicated internal entry, and a value-less `allow` line (both refuse). Add the mutant "append per glob" to the Rules table.
