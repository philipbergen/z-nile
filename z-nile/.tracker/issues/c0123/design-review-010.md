### F1 [medium] The verdicts of the guard and of the cleaner are computed by a perl that runs in the caller's environment, so `PERL5LIB` or `PERL5OPT` decides them: the capture's own fixture escapes again, and an inline cleaner believes a reused-pid registry
Where: `z-nile/lib/fence.sh` `pickman_fence_hooks_digest` (`command perl -e 'use Digest::SHA; …'`); `cleanenv.sh` `_pickman_holds` (`cur=$("$_pickman_perl" -e "$_pickman_startid" "$pid" 2>/dev/null) || return 0`); `cleanenv.luau` `cleanenv.holds` (`process.exec("/usr/bin/perl", …)`, which inherits the environment, then `return not r.ok or …`); the Design's "parts 1 and 2 stay as the second line (they also hold where the fence is used on its own, as the fixtures use it)"; E11's residue list (only `PATH` perl and `BASH_FUNC_command%%`); AC1.
Evidence: (a) The fence used on its own, as in the capture's confirmed fixture: a scratch repository with a copy of `z-nile/lib`, a folder `perm` whose `reference-transaction` and `pre-push` are `exit 0`, and `lib/Digest/SHA.pm` reduced to `sub hexdigest { "<the pin>" }`. Run as `env -i HOME=… PATH=/usr/bin:/bin PICKMAN_FENCE_HOOKS=…/perm /bin/bash -p -c '. lib/fence.sh; pickman_fence "$PWD" && git update-ref refs/heads/evil HEAD'`. Without `PERL5LIB` the fence prints `ignoring PICKMAN_FENCE_HOOKS=… (missing .repo.sh; …)`, the guard refuses, and the exit is 128. With `PERL5LIB=…/lib` it prints `hooks=…/perm` and exits 0, and `refs/heads/evil` exists. This is under `bash -p` with the system `PATH`, so it is neither residue E11 records. (b) The cleaner, inline (`bash -p -c '. cleanenv.sh && pickman_clean_env'`, the form ac.sh takes with no script): a registry line whose owner record names pid 1 with a wrong start id, the way a killed run's pid looks once it has been reused. With nothing else set, the folder and the forged `GIT_SSH_COMMAND` and `GIT_CONFIG_*` are dropped. With `PERL5OPT=-MNoSuchR10` (no file needed: perl dies, exit 2, "cannot tell", so the run "holds") the stale `pickman-guard.q` is first on `PATH` and it prints `SSH=evil COUNT=1`. The same variable on a script start makes the restart refuse (`still not the allow-list after a restart`), because the second pass runs without `PERL5OPT`. So the restart is what saves entry scripts and the runner, not the liveness rule.
Critique: this is the third hole in the same mechanism: the guard's verdict is produced by a tool started in the environment it is judging (`BASH_FUNC_perl%%`, rounds 1 and 2; `PATH` perl, recorded as residue; now perl's own variables). Part 3 drops `PERL5*` before the supported launchers reach the fence. But the Design claims part 1 holds on its own, AC1's cases drive the fence on its own, and `cleanenv.sh` runs its perl *before* it cleans anything. The tempting fix is to add `PERL5LIB PERL5OPT` to an `unset` line. That is one more name list: `PERLLIB`, `PERL5DB` and `PERLIO` layers come next.
Consequences: the perl must start in an environment the guard builds, not one it inherits. `/usr/bin/env -i /usr/bin/perl …` (absolute paths, empty environment) does that, and it also closes the `PATH`-perl residue of E11. The cost is that a host whose only perl is not `/usr/bin/perl` cannot verify. That fails closed (the fence refuses), and `fence.luau`'s `STARTED` already assumes a system perl. Every fixture copies `fence.sh` alone, so this costs no new file. In the Lune reader, `process.exec`'s `env` option merges with the parent's environment, so it has to start `/usr/bin/env -i` as well. `perl -T` would be the other option: it ignores `PERL5LIB` and `PERL5OPT`, but not every variable perl reads, so it is weaker.
Recommendation: start every perl whose output decides a guard (`pickman_fence_hooks_digest`, `_pickman_holds`, `cleanenv.holds`) as `/usr/bin/env -i /usr/bin/perl -e …` (fall back to refusing when the program is missing), and update E11's residue to say the `PATH`-perl route is closed. Cases: in `inherited-hooks`, `PERL5LIB` at a planted `Digest/SHA.pm` that prints the pin, and `PERL5OPT=-M<missing>`: the permissive folder is ignored and the guard refuses the write. In `cleanenv`, both readers under `PERL5OPT=-M<missing>` with a reused-pid registry: dropped, on the inline path as well. Mutants: `command perl` kept in each of the three places.
Lesson: zz-arch/verify-the-value-you-use (proposed by this prep); a candidate for the lead: "a guard's verifier runs in an environment the guard builds (absolute program, `env -i`), because a tool's own variables (`PERL5LIB`, `PERL5OPT`) choose the verdict it prints (c0123 review 010 F1); check: which programs does this guard start before or without cleaning, and which of their own variables change what they print?"

### F2 [medium] Under c0075's Linux jail (`--unshare-pid`) the registry's owner cannot be seen, so every jailed runner drops its own run's folders and the fence's names, and the design says c0075 has "no semantic overlap"
Where: c0123 Design, "Other in-flight work": "c0075 (prepared): … Textual neighbours, no semantic overlap"; `_pickman_holds` and `cleanenv.holds` (`kill -0 <pid>` on the pid the outer runner wrote in `.pickman-owner`); `fence.luau` `guarded()` (a nested run counts as guarded only when `GIT_CEILING_DIRECTORIES` holds `<marker>/.cache`, and that is a `fence` name); c0075.md lines 31, 42 and 92 (`--unshare-pid … --new-session --die-with-parent`; "Inside the jail `echo $PPID` is a number of the jail's own namespace"; "never under bwrap, where an outside pid is absent").
Evidence: the outer runner writes `.pickman-owner` with its host pid, then starts `exec lune run tests/run` inside the jail. Under c0075 that inner runner lives in a new pid namespace, so `kill -0 <host pid>` fails with "No such process" (or reaches an unrelated jail process with another start id). Both readers then read the registry line as dead and drop `runTemp`, the guard folder and every `fence` name (the ceiling, `GIT_CONFIG_*`, `GIT_ALLOW_PROTOCOL=file`, the refusing `GIT_SSH_COMMAND`). The inner runner restarts "clean", `guarded()` is false without the ceiling, and it either tries to fence and take the lock its own parent holds, or runs specs without the spec-mode fence. Which of the two happens depends on c0075's lock rework, which does not know about this registry. On macOS the same edge reads `Operation not permitted`, so that is the only jail the rule was proved on (L6). Nothing runs the gate on Linux (E17), so no spec would show it.
Critique: c0075 and this round's liveness rule change the same mechanism (who may judge a recorded pid, from which namespace). The design quotes c0075's text but not its pid-namespace decisions (lesson design-the-execution-window: "when another prepared raft changes the same mechanism, has its design been read for every writer and reader it adds"). The tempting fix is to believe the owner whenever `PICKMAN_TEST_JAIL=bwrap`. That is a marker, and Boundary (c) says markers are believed for nothing.
Consequences: the reader needs a fact no variable can forge that says the pid belongs to another namespace. c0075 already plans `<lock>/pidns` (the runner's `readlink /proc/self/ns/pid`) and `fence.pidNamespace()`. The runner can write its namespace into `.pickman-owner` as well (a third field; macOS writes none). A reader whose own namespace differs cannot judge the pid. It can keep the line only while the namespace it recorded still exists? That cannot be seen from inside either. So keeping the line there means a killed run's registry is believed by readers in some other jail. That is narrow: a jail dies with its run (`--die-with-parent`), and its own home's registry was rewritten by its own outer runner, but other homes' stale registries would count. This is a decision on Linux semantics, which is the user's (accepted-risks-checked-and-decided) or c0075's.
Recommendation: rewrite the c0075 paragraph to name the overlap, add the namespace field and rule (or another fact both preps agree on) to whichever of c0123 and c0075 lands second, and tell c0075's prep in the same round. Add a `cleanenv.spec` case with a planted owner record whose namespace differs from the reader's (pure input to `holds`, so it runs on macOS), and a row in Rules and mutants. If the pick keeps a cross-namespace line believed, put it to the user as a `Decided with the user` line.
Lesson: z-design/design-the-execution-window; z-design/quote-other-preps-before-promising; z-design/fallbacks-name-the-modes-they-cover

### F3 [low] A live run roughly doubles an entry script's start, and Scalability says "a few ms"
Where: Scalability ("while a run is live a `kill -0` and a start-id `perl` per registry line"); refute 009 F2 ("the check adds a few ms only during a run").
Evidence: 20 starts of an empty script that has the prologue (`env -i HOME=… PATH=/x`, so dirty: two passes): 0.86 s with no registry, 1.76 s while my AC6 run held the lock with one registry line. That is about 43 ms against 88 ms per start: the perl starts (one per pass) plus `kill`, `/bin/pwd` and `read`. Inside the jail every one of the many `./zn`, `ac.sh` and gate starts the specs make pays it. The user's rule is that specs must be fast and cheap.
Recommendation: state the measured cost, both cold and during a run. Optionally skip the start-id perl when the pid is the reader's own ancestor (bash's `$PPID` chain is no help across `env -i`), or cache the verdict per registry line in `PICKMAN_CLEANED`'s restart (the second pass's verdict is the one that counts).

### F4 [low] Text that disagrees with the mechanism
Where and evidence:
- The Design says `Operation not permitted` counts as alive "as the runner's own `fence.alive` reads it". `fence.alive` reads it as alive only when confined (`sandbox-exec` or an outer sandbox) and otherwise as dead ("another user's process, which can't hold this user's lock"). Both readers read it as alive everywhere. A deliberate difference needs its own reason, the case that pins it, and the effect of a start id that reads "cannot tell" (exit 1, "no such process", also reads as holding: on a Linux `/proc` mounted `hidepid=2`, another user's reused pid gives EPERM and then exit 1, so it holds).
- The bash `kill` builtin's message is `strerror`, which glibc translates under the `LANG`/`LC_*` the list admits, so the `*"Operation not permitted"*` match depends on the locale on Linux (dash in the Lune reader is not translated). Run `kill` under `LC_ALL=C`.
- An owner record naming pid `0` passes `kill -0` (the process group), which needs a forged file (Boundary (e)); `0` can be refused for free.
- check.sh's AC3 label omits what round 9 added to the doc's AC3 (the writer, liveness, the teardown).
- Step 7 says 71 files and −175; the patch applies as 73 files, +1193 −176.
Recommendation: fix the sentences, refuse pid 0, use `LC_ALL=C` for the probe, and bring the label in line with the doc's AC3 (lesson spec-design-correspondence: "does every check's label say exactly what its command verifies").
