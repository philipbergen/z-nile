# c0136: Review lessons go to the step that erred

## Problem
The user, 2026-10-23: "Any time there is a review that points out a mistake, that is a learning lesson to the step or the step prior, we need to capture that both from the past and going forward."

Today c0111 harvests design-review and code-review findings into lessons, filed under whichever skill the harvester picks, and c0112 will backfill past design and code reviews (it leaves out stream reviews). Nothing says which step a lesson belongs to. A code review that finds a design hole, or a design review that finds a capture that was too vague, teaches the step that made the mistake, often the step before the one being reviewed, but the lesson usually lands on the step under review, where the next author of the erring step never reads it. Reviews other than design and code reviews (stream reviews, programme reviews, focused reviews of a rework, the review of a review's own recommendation, and user corrections) are not harvested at all.

What should happen:
- Every review finding that points out a mistake becomes a lesson (or a note on an existing one) for the step that made the mistake, or the step before it when that step should have prevented it. The harvest line names that step.
- This holds for every kind of review: design, code, stream, programme, focused re-reviews, and user corrections.
- Going forward, every new review is harvested this way.
- From the past, every review already on `main` is harvested this way too (the backfill, c0112, uses the same rule).

Scope decision (user, 2026-10-25): "Fold into c0136" (c0140, "a lesson's when: follows its origin", folded in): a lesson's `when:` reaches the erring step's phase too: `design` or `both` whenever the mistake was design's or could have been caught there, so the design step's lessons pass shows it. A code-review lesson marked `build` for a design hole never reaches the next design.

## Non-goals
- The lesson file format and `lessons` command: c0111 (done).
- The bulk backfill work itself: c0112, which should take this rule.
- Renaming skills: c0115.

## Solution
- A harvest line names the erring step (the skill that made the mistake), and `lessons --check` refuses a lesson filed under a step the line does not name.
- The review skill asks every reviewer, for each finding: which step made this mistake, and which earlier step should have caught it?
- Extend harvesting to stream reviews, programme reviews, focused re-reviews and user corrections.
- c0112 depends on this, so the backfill attributes by the same rule.
- The harvest sets `when:` by the erring step: `design` or `both` when design made the mistake or should have caught it; the reviewer checks it, and `lessons --check` refuses a harvest line naming a design-phase step for a `build`-only lesson.

### The rule (the interface c0112, c0166 and c0181 build on)

Four decisions, each following from the capture, none a product choice:

1. **A step is a skill.** `erred` is the skill whose instructions the author was following when the mistake was made: `z-ticket` for a vague capture, `z-design` for a design hole, `z-raft` for a bad grouping, `z-ready` for a wrong prompt, `zz-execute` for a build mistake, `zz-review` for a reviewer's own mistake, or a skill the author read for it (`zz-test` for a spec, `zz-arch` or `pickman-arch` for code). It is never the step under review by default: a code review that finds a design hole names `z-design`, a design review that finds a capture too vague names `z-ticket`. `upstream` is an earlier step's skill that should have prevented or caught the same mistake (the capture that left the point out, the design that did not specify it, the earlier review that missed it); it is optional. The topic skills stay valid homes, so the 149 lessons already filed under them need no move.
2. **A lesson is filed under its `erred` skill or its `upstream` skill**, and only those. `lessons --check` refuses any other filing. A lesson is `when: design` or `both`, never `build`, when its line names a design step (`z-ticket`, `z-design`, `z-raft`, `lessons.DESIGN_STEPS`, as `erred` or `upstream`) **or answers a finding that is design's**, except a lesson filed under `zz-review` for the reviewer's own mistake (a reviewer reads its own skill's lessons whatever their `when:`, so that one may be `build`; a lesson for the same line filed under its upstream skill reaches design). A finding is design's, decided once and applied to its entry and to every note headed for it, when its review is a design-phase review, or the step lines that bind on it or the group of its entry name a design step (so a third lesson in a note about a code finding the reviewer attributes to `z-design` is held to the same rule as the finding's own lesson). A design-phase review is a design round (an issue's, or z-raft's coherence round) or a focused review whose heading says `design`; every phase the reader cannot resolve fails closed: a focused heading must say exactly `(focused mode, design)` or `(focused mode, build)` (`Design`, `both`, a missing word are problems, and a review of both design's files and code is `design`), an unresolved phase counts as design for the `when` rule, and a note headed `<stem> F<n>` must name a review of its item and a finding that review has, as an entry must; the answer is the finding's entry or a note about it (`- note <stem> F<n> <text> (erred <skill>): …`, how an author records a disagreement or a lesson in a third skill). A design round's finding is a mistake design made or should have caught, whatever topic skill (`zz-test`, `zz-arch`) the line names (the folded c0140: a design hole reaches the next design, and a design-phase mistake filed under a topic skill still does). A code or stream finding in something design wrote (the issue document, `check.sh`, a sequestered spec, a prototype it copied) names `Upstream: z-design`, so the same rule fires; that part is the reviewer's judgment (zz-review item 10), since no file says who wrote what. `erred none` (a one-off only) is a finding that points out no mistake.
3. **The reviewer's lines are the entry's.** Each finding of a new review carries `Erred:` and `Upstream:` (`none` when no step applies). The harvest entry copies them, and `lessons --check` refuses an entry that differs. A review that has the lines on some findings must have them on all. Lines that cannot be read (a skill that does not exist, the same skill on both lines, `none` with an upstream, a missing line, a line quoted inside a code fence or after a section heading is not read at all) bind nothing: `lessons --check` reports the finding, and because a committed review is never edited, a note `- note <stem> F<n> step lines invalid (erred zz-review): <lesson ids>` (and, for a focused heading with no readable phase, `- note focused-review-NNN phase <design|build> (erred zz-review): <lesson ids>`, which also supplies the phase) waives that finding's problems (and carries the lesson about the reviewer's slip); `check` requires the note to be `erred zz-review` and to name a review that exists and a finding that has such a problem, so it cannot hide anything else. Reviewer and lead run `./zn lessons --check-review <path>` (read-only, on one new review, wherever it is: an interactive reviewer's file, a dispatcher's state folder, a Sonnet reviewer's text a lead has written out) before the file is handed back or committed; it refuses unreadable lines, a finding with no lines (bolded or bulleted ones included; a review with no finding passes) and a focused heading with no phase, judged from the text whatever the file is called. z-design 5.3, z-raft, zz-execute Phase 2B and Phase 4 each run it on every round they receive, and a failure sends the round back to its reviewer; so a committed bad file is the rare path. A fence is read by one rule (up to three spaces in, three or more backticks or tildes, closed by the same character at least as long; a fence never closed is read as no fence, so a slip shows as a problem), and the findings a review has are the `### F<n>` headings `lessons.findings` and `done` read, so any disagreement is a reported problem, not a legacy file. A refuted finding keeps the reviewer's step: `(erred z-design): one-off: refuted, <why>`; the author who thinks the reviewer attributed the mistake wrongly adds a `- note … (erred <the step they think>): <lesson>` beside it.
4. **Entries written before c0136 keep working, and a new round cannot pass as one.** (An entry with no group is read as before only while the review it answers has no step lines; if the review gives them, `--check` refuses it: it copies them.) A review with no step lines reads as written before c0136 and nothing in the text tells the two apart, so `--check-review` is the line between them: it is run on every new round, refuses one with findings and no lines, and old reviews are never run through it. A round without lines goes back to its reviewer before it is committed or harvested (z-design 5.3, zz-execute Phase 2B and Phase 4), and a lead uses a stream or focused reviewer's text as it is and never adds lines itself. Only a round committed before c0136 is named by its harvester (`./zn lessons --unattributed` still lists the entries that name no step). Skill names in never-edited records are read through `skills.RENAMED`, so a later rename (as c0115's) keeps them valid, and the ledger rename renames a group's names with its ids. An entry or note with no group is read as before and judged by nothing about steps. `./zn lessons --unattributed [<id>...]` lists the review entries and notes that name no step (exit 1; it judges those two kinds only, so an entry kind a later change adds, such as c0181's `- codify` line, is not judged), the way `--uncovered` lists unharvested findings: z-design, z-raft and zz-execute run it for their item beside `--uncovered`, and c0112 runs it over the whole tree once it has attributed the past (its gate invariant).

**Every review kind is a source.** A finding of any of these is harvested as an entry; what leaves no file is a note. A focused review's heading names the phase it looked at, `(focused mode, design)` or `(focused mode, build)` (design when the work reviewed is the issue document, its specs or `check.sh`), and `check` refuses one without it:

| kind | file (where) | harvest | coverage |
|---|---|---|---|
| design review (issue), z-raft coherence review | `design-review-NNN.md` (the item; phase design) | entry | `--uncovered` |
| code review | `review-NNN.md` (the raft) | entry | `--uncovered` |
| stream review | `stream-review-<issue>-NNN.md` (the raft; the lead writes it from the Sonnet reviewer's text) | entry, written as the file is committed | `--uncovered` (new: c0136) |
| focused review: a rework, a fix, an earlier review's recommendation | `focused-review-NNN.md` (in the folder of the `harvest.md` the lead writes in: the issue's during prep, the raft's during a raft's execution, whatever item it concerns; the lead writes it from the reviewer's text; phase in its heading) | entry | `--uncovered` (new: c0136) |
| programme review, user correction, failed step, subagent candidate | none | `- note <text> (erred <skill>): <lesson ids>` | none: nothing on disk says one happened |

The last row is the limit: no command can know that a user corrected the work. The rule is the lead-in paragraph in every skill (below), the same text for every role, and the next reviewer judges the harvest (zz-review item 10).

**Forms.** In `harvest.md`:
```
- design-review-001 F1 (erred z-design): z-design/a
- design-review-001 F2 (erred z-design, upstream z-ticket): z-ticket/b, z-design/a
- review-001 F4 (erred none): one-off: the reviewer misread the spec
- stream-review-c0010-001 F1 (erred zz-execute): zz-test/c
- note the fixture seeded one state (erred zz-test): zz-test/c
- note design-review-001 F2 a spec rule too (erred zz-test): zz-test/c      (a further lesson of a finding, a third skill)
- note design-review-001 F4 step lines invalid (erred zz-review): zz-review/c   (the waiver)
- design-review-001 F3: z-design/a            (before c0136: no step, still read)
```
In a review file, after `Lesson:`: `Erred: <skill, or none>` and `Upstream: <earlier skill, or none>`. A note's group is the end of its text (`^(.-)%s*%((erred [^()]*)%)$`); parentheses elsewhere in a note stay text, so `- note ws-<issue>: <lesson ids>` and every existing note read as before.

### Modules

**`z-nile/engine/lessons.luau`** (pure over texts; `load` still the only reader):
- `Entry` gains `erred: string?` and `upstream: string?`.
- `local function validSteps(erred: string, upstream: string?): string?`: the one rule for a pair of steps, whether spelled as a group or as a review's two lines: skills are lowercase kebab, `none` only as `erred`, no upstream with `erred none`, `upstream` never `none` (it is left out) and never equal to `erred`. `local function parseSteps(inner: string)` reads `erred <skill>` or `erred <skill>, upstream <skill>` and applies it; it refuses a missing skill, a repeated key, an unknown key and `upstream` alone.
- `parseHarvest` reads `^%- (%S+) (F%d+)(.*)$`, then ` (…)` + `:` or `:`; for a note it strips the trailing group from the text. A malformed group is a problem naming the item and the finding (or note); `erred none` with a lesson is a problem. `isStem` gains `stream-review-<c|d|f>NNNN-NNN` and `focused-review-NNN`; `load` already reads every stem `isStem` accepts, so stream and focused reviews are items' reviews with no other change, `uncovered`, `sources` and `tagCounts` included.
- `lessons.findingSteps(review: string, skills: { [string]: boolean }?): ({ [string]: FindingSteps }, { string })` with `FindingSteps = { erred: string, upstream: string? }`: the `Erred:` and `Upstream:` line of each `### F<n>` block, a line starting at column 0 outside a code fence and before the next `## ` heading. Problems, each `F<n>: …`: a repeated line, a value that is not a skill name or `none`, a pair `validSteps` refuses, a skill that is not in `skills` (when given), a finding missing one of the two once any finding has either. A finding with a problem binds nothing (it is left out of the result); the skills it returns are the current names (`canon`). A review with neither line anywhere returns `{}` and no problem.
- `lessons.DESIGN_STEPS = { "z-ticket", "z-design", "z-raft" }`: the one list of design steps. `lessons.reviewPhase(stem, text)`: `design` for a `design-review-NNN`, the heading's exact `design` or `build` for a focused review (`none` for anything else), `build` for every other review. `lessons.checkNewReview(stem, text, skills)`: what `--check-review` reports (the step-line problems, a finding with no lines, a focused heading with no phase). `lessons.noteHead(text)`: the `<stem> F<n>` head of a note about a finding, and the rest (one reader for the waiver and for the phase of a note). A local `canon(name, skills)` reads a step through `skills.RENAMED` unless a skill of that name exists.
- `lessons.check` adds, per entry that has a group: each named step is a skill (`tree.skills`); each named lesson's skill is `erred` or `upstream`; none of its lessons is `when: build` when a named step is in `DESIGN_STEPS` or the entry (or a note headed `<stem> F<n>`, which must name a review of the item and a finding it has) answers a finding of a design-phase review (`reviewPhase`, an unresolved phase counting as design) whose `erred` is neither `zz-review` nor `none`; a review entry equals the finding's `Erred:` and `Upstream:` when the finding binds them. And per review file: the `findingSteps` problems (given `tree.skills`), as `<item>/<stem>.md <problem>`, except a finding the item's `harvest.md` waives with a note `<stem> F<n> step lines invalid …` (which must be `erred zz-review`, and name a review and a finding that has a problem, else it is a problem itself); a focused review whose heading names no readable phase is a problem unless a phase note supplies it; an entry with no group that answers a finding whose lines bind is a problem; a grouped note that is not a head and has an `F<n>`-shaped word anywhere, or a first word containing `review-` (`design-review-01 F1`, `f1`, a comma after the stem, `review 002 F1`, `design review 001 F1`), is refused with the form, while legacy notes (no group) and notes that merely mention a review are not judged. Steps are compared and filed through `canon`.
- `lessons.unattributed(items: { Item }): { string }`: `<item> <review> <finding>` or `<item> note <text>`, for every entry with no `erred`, items by id, entries in file order.

### Scalability
`--check` parses each review for its step lines once per file and once more per grouped entry that answers one of its findings (`findingSteps`: linear in the review's bytes, about 200 review files today; the result is not cached, which a later change may do) and each lesson named by a grouped entry once (`lessons.parse`); no git call, no new file read beyond the two new stems, which are files `load` already walks. `--unattributed` is `--uncovered`'s cost.

### Maintainability
A new review kind is a stem in `isStem` and a row in the table above; a new design step is an entry in `DESIGN_STEPS`; a new skill is a step with no change (it need only exist, which `check` reads from `tree.skills`). The group has one parser (`parseSteps`) and one reader (`parseHarvest`), which `ledgerLine`, `sources`, `uncovered`, `unattributed` and the CLI count all use.

### Usability
`./zn lessons --unattributed [<id>...]` mirrors `--uncovered` (usage line, exit 1 on a gap, `no reviews`, `no such item`, exit 2 on mixed options). Every refusal names the file, the finding or note, and the rule it broke (`R0010/harvest.md: design-review-001 F1: lesson zz-test/c is filed under zz-test, which the line does not name (erred z-design)`). The reviewer's job is two short lines per finding; the author's is to copy them.
