# c0139: Rename script refuses conflicts

## Problem
The user, 2026-10-25, asked for this after c0115's rebase: twice `rename-lesson-ids` ran while a merge had left `harvest.md` conflicted. It rewrote ids on both sides of the conflict markers and reported success, so the counts looked right while the file still held markers; the resolution then threw that work away. Any tracker script that rewrites tracked files (the lesson-id rename, `rewrite-finished`, `./zn` commands that edit item documents) should refuse a file that holds merge-conflict markers, or refuse to run while the tree has unmerged paths, and say which file to resolve first.


## Non-goals
- Resolving conflicts: the tools only refuse and name what to resolve, and how.
- The commands that only read or only print (the conflict-OK list in the Design): they keep working mid-merge, so a script can still locate an item and a person can still look around.

## Solution
- Refuse up front when `git diff --name-only --diff-filter=U` is not empty, naming the paths.
- Also refuse a file whose lines start with `<<<<<<< `, `=======` or `>>>>>>> ` (a conflict committed by mistake).

## Design
**The rule.** A tool that can write tracked files does not run over a merge conflict. Before it writes anything it refuses, naming each path to resolve and how (`conflicts.RECOVERY`: resolve with plain git — edit the file or `git checkout --ours/--theirs`, then `git add` and `git commit`; a conflict that reached main lands its fix by a pull request made with plain git and gh, since `./zn` refuses until then), when any of these holds:
1. **unmerged paths**: `git diff --name-only --diff-filter=U` is not empty (a merge, rebase or cherry-pick stopped on conflicts);
2. **a whole conflict in a working file** under a project root or a skills folder: the file as it is on disk, tracked or untracked but not ignored (what the writing commands' `git add -A` would commit; design review 001 F2), holds a line starting `<<<<<<< ` followed later by a line starting `>>>>>>> `, named `<path>:<line of the opener>`. Markers quoted inline, indented, a lone opener or a closer before the opener are no conflict (plain prefix compares). `=======` is not read (a markdown underline can be seven `=`);
3. **the registry can't be read**, or **any git read fails** (`git diff` not ok; `git grep` exiting other than 0 for a hit or 1 for none): fail closed, naming the command and its error (design review 002 F2; the same rule as c0152's merge-check). **Outside a repository** is one predicate, `conflicts.outsideRepo(top)`, shared with audit's scan (design review 003 F1): no `.git` entry at `top` (a folder, or a worktree's `gitdir:` file) **and** none of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE` inherited. Only then does the guard skip, since nothing can be mid-merge there: `migrate` runs in such a tree (tooling's migrate-odd spec). The condition is tested on disk and in the environment, never read from git's wording: git says "not a git repository" for a corrupt HEAD, a linked worktree whose admin folder is gone, an unreadable `.git` and a stray `GIT_DIR` as well, and each of those refuses, naming the failed read (a broken checkout then stops every writing command until it is repaired, which is right: none of its git operations can succeed). `top` is the checkout's top, where `./zn` always runs.

**One list of folders (F3).** `conflicts.folders(top)` returns every project root of the registry (`projects.roots`) and every skills folder (`skills.folders`), or nil and why. The engine, both scripts and the audit all use it, so no caller has its own list.

**Which commands refuse (F1).** Every command except those that only read or only print. The conflict-OK list, decided command by command in `main.luau`'s `conflictOk(name, args)` (separate from `READ_ONLY`, which means "may run in a git-less sandbox" and keeps guarding `guardRepoRoot()` alone):
- all of `READ_ONLY` (`list`, `audit`, `find`, `members`, `metrics`, `board`, `workstreams`, `promote-check`, `stamp`): they read;
- `busy`, `capture`, `prompt`: read-only reports; `lessons` in every form (its search, `--full`, `--tags`, `--check` and `--uncovered` only read);
- `status` with no positional argument or one id (the list, one item), its options aside (`--project <p>`, read with `flags` as the handler reads them, design review 002 F3); `status <id> <to>` writes and refuses;
- `raft-plan` without `--apply` (`--apply` writes and refuses);
- `skills --check` (plain `skills` writes the links and refuses).
`check` refuses on purpose: it runs specs that clone and judge the tree, and a conflicted tree gives meaningless results. A new command refuses until it is added to the list (a new entry needs a reason here, lesson zz-rules/exhaustive-lists-name-new-things).

### Scalability
One `git diff` and one `git grep` per writing command, over the tracker roots and skills folders: about 20 ms on today's tree (the prototype's `./zn status` is unchanged to the eye).

### Maintainability
One module decides "conflicted", used by the engine and both scripts (lesson zz-test/one-rule-one-function). A new command is covered by default; only a command (or form) added to `conflictOk` runs over a conflict, each with its reason in the Design; `READ_ONLY` keeps its own meaning (may run without git) and guards `guardRepoRoot()` alone.

### Usability
The refusal names every file to resolve, unmerged paths first; the read-only commands still work, so `./zn find` keeps working inside a merge.
