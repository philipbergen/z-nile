# c0139: Rename script refuses conflicts

## Problem
The user, 2026-10-25, asked for this after c0115's rebase: twice `rename-lesson-ids` ran while a merge had left `harvest.md` conflicted. It rewrote ids on both sides of the conflict markers and reported success, so the counts looked right while the file still held markers; the resolution then threw that work away. Any tracker script that rewrites tracked files (the lesson-id rename, `rewrite-finished`, `./zn` commands that edit item documents) should refuse a file that holds merge-conflict markers, or refuse to run while the tree has unmerged paths, and say which file to resolve first.


## Non-goals
- Resolving conflicts: the tools only refuse and name what to resolve.
- Commands that only read (`./zn`'s `READ_ONLY` list: `list`, `audit`, `find`, `members`, `metrics`, `board`, `workstreams`, `promote-check`, `stamp`): they keep working mid-merge, so a script can still locate an item.

## Solution
- Refuse up front when `git diff --name-only --diff-filter=U` is not empty, naming the paths.
- Also refuse a file whose lines start with `<<<<<<< `, `=======` or `>>>>>>> ` (a conflict committed by mistake).

## Design
**The rule.** A tool that rewrites tracked files does not run over a merge conflict. Before it writes anything it refuses, naming each path to resolve, when either:
1. **unmerged paths**: `git diff --name-only --diff-filter=U` in the checkout is not empty (a merge, rebase or cherry-pick stopped on conflicts) — message `<tool>: refusing to run while the checkout has unmerged paths; resolve them first:` and one path per line;
2. **a committed conflict**: a tracked file under a project root (`pickman/.tracker`, `z-nile/.tracker`) or a skills folder (`z-nile/skills`, `pickman/skills`) holds a **whole** conflict — a line starting `<<<<<<< ` followed later by a line starting `>>>>>>> ` — message `<tool>: refusing to run: these tracked files hold merge-conflict markers; resolve them first:` and `<path>:<line of the opening marker>` per file. Markers quoted inline, indented, or a lone opener are no conflict (lesson zz-test/plain-find-for-literals: plain prefix compares, no patterns). `=======` alone is not required or read (a markdown underline can be seven `=`).

**Where.**
- `z-nile/engine/conflicts.luau` (new, strict, reads only): `markerLine(text): number?`, `unmerged(top): {string}`, `marked(top, folders): {string}` (one `git grep -l -I -e '^<<<<<<< '` over the folders, then `markerLine` on each hit's index copy, `git show :<path>`), `refusal(top, tool, folders): string?` (unmerged first, then committed conflicts).
- `z-nile/engine/main.luau`: at dispatch, right after `guardRepoRoot()` for every command outside `READ_ONLY` (the existing list of commands that may run in git-less sandboxes and only read), `conflictsLib.refusal(".", "tracker <name>", conflictFolders())` and `fail` on a refusal; `conflictFolders()` is every project root of the registry plus every skills folder (`skills.folders`). One hook covers every writing command (`status`, `new`, `commit`, `done`, `ready`, `stop`, `fold`, `unfold`, `recombine`, `renumber`, `remap`, `migrate`, `compact`, `spend`, `append`, `sync`, `land`, `skills`, …) without touching their fifteen write sites (lesson z-design/design-the-execution-window: c0117, c0118 and c0121 change `main.luau` heavily; this change is two hunks).
- c0115's rewriting scripts, still the tools that rename lesson ids and rewrite finished `check.sh` files after a merge (c0118's and c0121's streams ran them from `done/c0115`): `z-nile/.tracker/issues/done/c0115/experiments/rename-lesson-ids.luau` and `rewrite-finished.luau` call `conflicts.refusal(<top>, "<script>", <roots and skills folders>)` right after finding the checkout's top, before reading or writing, and exit 2 on a refusal. They are a finished item's experiments, not its `check.sh` or acceptance (not sequestered); c0115's AC14 runs them with `--check` and stays green on a clean tree.

### Scalability
One `git diff` and one `git grep` per writing command, over the tracker roots and skills folders: about 20 ms on today's tree (the prototype's `./zn status` is unchanged to the eye).

### Maintainability
One module decides "conflicted", used by the engine and both scripts (lesson zz-test/one-rule-one-function). A new writing command is covered by default; only a command added to `READ_ONLY` is exempt, and that list already means "reads only".

### Usability
The refusal names every file to resolve, unmerged paths first; the read-only commands still work, so `./zn find` keeps working inside a merge.
