# c0141: Check paths touched from home

## Problem
Found 2026-10-25 by c0115's prep gate on landed c0120. `z-nile/tests/acceptance/c0120/check-paths.spec.luau` exempts a path an unfinished check.sh names when it lies under one of the item's Touched modules entries (its own work will create it). The entries are repository-relative (`pickman/skills`), but the path is compared as the check reads it from its home after a literal `cd`: c0115's AC12 ran `cd .. && ./zn busy … pickman/skills` from `z-nile/`, which the spec reports as `../pickman/skills (from z-nile)` and never matches `pickman/skills`. Every item whose check.sh names a path it creates after a literal `cd` out of its home fails the gate the moment its prep lands. c0115 worked around it by running from `$ZN_ROOT`.

What should happen: the exemption resolves the path to its repository-relative form (home plus the path, `..` folded) before comparing it with Touched entries.

## Solution
- In `under` (or before calling it), normalize `<home>/<path>` to a repository-relative path; add a case: a check.sh in z-nile/ with `cd .. && x pickman/new-thing` and `pickman/new-thing` Touched is exempt; the same path not Touched is listed.
- A promoted-spec change: a chore that overrides c0120/check-paths (its own `Overrides:` line).

## Design
c0120's promoted `check-paths.spec.luau` (AC11) scans every unfinished item's `check.sh` for literal paths that don't exist from its project home, and exempts a path "under a Touched modules entry of the item (or of a member, for a raft), which its own work will create". Its literal reader already follows a literal `cd <dir>` (the words after it are relative to `<dir>`), so from `z-nile/` a `cd .. && … pickman/skills` reads as `../pickman/skills`. The exemption then compares that home-relative string with the Touched entries as written, so `../pickman/skills` never matches `pickman/skills` (the capture's defect; c0115's AC12 worked around it by running from `$ZN_ROOT`).

**The rule (c0141).** The exemption compares the path's **repository-relative form** — the item's project home joined with the path, `.` and `..` segments folded — with each Touched entry read **both ways the trackers write them today**: repository-relative (c0115, c0117: `z-nile/skills`, `pickman/skills`) and relative to the item's home (pickman's items: `src/shared/Logic/Hiscores/init.luau`, `tests/acceptance/f0024/adapter.spec.luau`). A path whose folding climbs above the checkout (more `..` than segments) has no repository-relative form and is **never exempt**: it is reported as written. Nothing else changes: which words are literal paths, which items are scanned, the glob rule, the restamped files and the report's wording (`<check.sh>: <path as written> (from <home>)`).

Why both readings: the capture says Touched entries are repository-relative, but the live backlog shows both conventions (pickman's documents are home-relative since c0120 moved pickman into `pickman/`; c0115 and c0117 wrote repository-relative entries). Reading only one would turn the live scan red (the prototype's mutant D: the real-tree case fails). Choosing one convention for every document is a separate question for the user (Unknowns, Q1), not this chore's.

**Where it lives.** The scanner moves out of the spec into a test library, so the rule can be pinned by a sequestered spec of its own (a spec's locals can't be required):
- `z-nile/tests/lib/checkpaths.luau` (new, strict): `literals(text): {string}`, `present(base, home, path): boolean`, `touched(doc): {string}`, `under(path, own): boolean`, `items(base): {Item}`, `scan(base, skip: (text) -> boolean): Scan` — moved unchanged from the spec except `scan`, which takes the restamped test as `skip` and applies the new comparison — plus two new functions:
  - `repoPath(home: string, path: string): string?` — `home` "." (or "") is the checkout's top; folds `.` and `..`; nil when it climbs above the top; glob characters are kept as text.
  - `owned(home: string, entries: {string}): {string}` — each entry as `repoPath(".", e)` and as `repoPath(home, e)` (both when they differ; an entry that climbs above the top is dropped).
  - In `scan`: `if not present(base, home, p) and not (at and under(at, own))`, with `at = repoPath(home, p)` and `own = owned(home, entries)`.
- `z-nile/tests/acceptance/c0120/check-paths.spec.luau` (promoted; an override, see Regression guard) keeps its constants that are its own (RESTAMPED, `blob`, the fixture `FX`/`REGISTRY`/`put`) and every case unchanged, and gets `literals`, `present`, `under`, `items` and `scan` from the library (its `scan(base)` wraps `checkpaths.scan(base, restamped)`).
- No engine code changes; `z-nile/tests` is the harness, skipped by cachepaths' writer list.

### Scalability
The comparison adds one string fold per literal and two per Touched entry: the live scan reads about 30 `check.sh` files with a handful of literals each, unchanged in time (about 0.1 s).

### Maintainability
One reader of the rule instead of one hidden in a spec; `repoPath` and `owned` are pure and tested directly. The library is the only place the exemption is decided (lesson zz-test/one-rule-one-function): the engine's own Touched readers (`spend.ownedPaths`, raft-plan's overlap) compare raw entries and are not changed here (Unknowns, Q2).

### Usability
The report line is unchanged, so a reader still sees the path as the `check.sh` wrote it and the home it was read from.

- **Q1 (for the user, not blocking).** Touched modules are written two ways in live documents (repository-relative and home-relative). This chore accepts both. Should one convention be made the rule (and the documents migrated)? That would be a new item.
