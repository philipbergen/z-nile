# c0141: Check paths touched from home

## Problem
Found 2026-10-25 by c0115's prep gate on landed c0120. `z-nile/tests/acceptance/c0120/check-paths.spec.luau` exempts a path an unfinished check.sh names when it lies under one of the item's Touched modules entries (its own work will create it). The entries are repository-relative (`pickman/skills`), but the path is compared as the check reads it from its home after a literal `cd`: c0115's AC12 ran `cd .. && ./zn busy … pickman/skills` from `z-nile/`, which the spec reports as `../pickman/skills (from z-nile)` and never matches `pickman/skills`. Every item whose check.sh names a path it creates after a literal `cd` out of its home fails the gate the moment its prep lands. c0115 worked around it by running from `$ZN_ROOT`.

What should happen: the exemption resolves the path to its repository-relative form (home plus the path, `..` folded) before comparing it with Touched entries.

## Solution
- In `under` (or before calling it), normalize `<home>/<path>` to a repository-relative path; add a case: a check.sh in z-nile/ with `cd .. && x pickman/new-thing` and `pickman/new-thing` Touched is exempt; the same path not Touched is listed.
- A promoted-spec change: a chore that overrides c0120/check-paths (its own `Overrides:` line).

## Design
c0120's promoted `check-paths.spec.luau` (AC11) scans every unfinished item's `check.sh` for literal paths that don't exist from its project home, and exempts a path "under a Touched modules entry of the item (or of a member, for a raft), which its own work will create". Its literal reader already follows a literal `cd <dir>` (the words after it are relative to `<dir>`), so from `z-nile/` a `cd .. && … pickman/skills` reads as `../pickman/skills`. The exemption then compares that home-relative string with the Touched entries as written, so `../pickman/skills` never matches `pickman/skills` (the capture's defect; c0115's AC12 worked around it by running from `$ZN_ROOT`).

**The rule (c0141).** The exemption compares the path's **repository-relative form** — the item's project home joined with the path, `.` and `..` segments folded — with what the item's Touched entries name, read in **the document's own convention, from its text alone** (design review 002 F1; never from what exists on disk, which the item's own work changes and which differs between checkouts):
- when **any** Touched entry of a document starts with a registered project's home (`z-nile`, `pickman`, read from the registry's roots, never a hand list), **every** entry of that document is read from the checkout's top (`z-nile/skills`, `.models.toml`, `AGENTS.md`);
- otherwise every entry is read from the item's home (`src/shared/Logic/New`, `.github/workflows/new.yml` in `pickman/`), and a root path is written `../AGENTS.md`.
A raft's members are each read by their own document's convention. An entry that climbs above the checkout names nothing. A path a check names whose folding climbs above the checkout has no repository-relative form and is **never exempt**: it is reported as written. Nothing else changes: which words are literal paths, which items are scanned, the glob rule, the restamped files and the report's wording (`<check.sh>: <path as written> (from <home>)`).

Why per document: the live backlog has one convention per document (the search, rerun it at execution: for each unfinished item document, the first segments of its Touched entries — `for f in $(git ls-files | grep -E '\.tracker/(issues|rafts)/(active/)?[fdcR][0-9]{4}/[fdcR][0-9]{4}\.md$'); do awk '/^### Touched modules/{f=1;next} /^#/{f=0} f' $f | grep -oE '^- `[^`]+`' | sed 's/^- `//;s/`$//' | cut -d/ -f1 | sort -u | tr '\n' ' '; echo " $f"; done`): pickman's c0128, c0150, d0124, f0126 are home-relative throughout; z-nile's c0117, c0075, c0083 mix `z-nile/` with bare root names (`AGENTS.md`, `.models.toml`, `scripts/…`), so they are repository-relative throughout. Reading each entry from the disk (the round-001 draft) misread an item's own new path until it existed, and c0117's `.models.toml`. A home-relative document naming a root path bare (`AGENTS.md` meaning the root's) would read it as the home's: the search finds none, and z-design's Touched-modules guidance now says to write `../AGENTS.md`.

**Where it lives (design review 001 F3).** The scanner moves out of the spec's body into a module **in c0120's promoted folder**, beside the modules already there (`rewrites.luau`, `finished.luau`), so it stays under "never edit promoted specs" (zz-test) and a later item can change it only through an `Overrides:` line:
- `z-nile/tests/acceptance/c0120/checkpaths.luau` (new, strict): `literals(text): {string}`, `present(base, home, path): boolean`, `touched(doc): {string}`, `under(path, own): boolean`, `items(base): {Item}`, `scan(base, skip: (text) -> boolean): Scan` — moved unchanged from the spec except `scan`, which takes the restamped test as `skip` and applies the new comparison — plus:
  - `repoPath(home: string, path: string): string?` — `home` "." (or "") is the checkout's top; folds `.` and `..`; nil when it climbs above the top; glob characters kept as text.
  - `owned(home: string, entries: {string}, homes: {string}): {string}` — one document's entries read by its convention, `homes` being every registered project's folder (`projects.folderOf` of each root); no file system access.
  - In `scan`: `if not present(base, home, p) and not (at and under(at, own))`, with `at = repoPath(home, p)` and `own` the item's `owned(home, …)` plus, for a raft, each member's.
- `z-nile/tests/acceptance/c0120/check-paths.spec.luau` (promoted; Overrides) keeps its own constants (RESTAMPED, `blob`, the fixture `FX`/`REGISTRY`/`put`) and every case unchanged; it requires `./checkpaths` and its `scanFrom(base)` wraps `checkpaths.scan(base, restamped)`. It defines no scanner function of its own (`literals`, `present`, `touched`, `under`, `items`, `scan`, `repoPath`, `owned`) and no `PREFIXES` (design review 001 F2: pinned by c0141's spec, so the gate can't keep running an old copy).
- `z-nile/skills/z-design/SKILL.md`: the Touched modules bullet says a list has one convention (from the top when it names any `<home>/…` path, else from the home with `../X` for a root path).
- No engine code changes.

### Scalability
The comparison adds one string fold per literal and, per Touched entry, one fold and at most two existence checks: the live scan reads about 30 `check.sh` files with a handful of literals each, unchanged in time (about 0.1 s).

### Maintainability
One reader of the rule, in the promoted folder that protects it; `repoPath` and `owned` are tested directly. The library is the only place the exemption is decided (lesson zz-test/one-rule-one-function): the engine's own Touched readers (`spend.ownedPaths`, raft-plan's overlap) compare raw entries and are not changed here (Unknowns, Q2).

### Usability
The report line is unchanged, so a reader still sees the path as the `check.sh` wrote it and the home it was read from.

- **Q1 (for the user, not blocking).** Touched modules are written two ways in live documents (repository-relative and home-relative). This chore accepts both. Should one convention be made the rule (and the documents migrated)? That would be a new item.
