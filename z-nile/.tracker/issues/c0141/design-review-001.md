### F1 [high] Reading every Touched entry both ways exempts paths no item will ever create, including one main reports today
Where: c0141.md Design, "The rule (c0141)" and `owned`; prototype `checkpaths.owned`/`scan`
Evidence: probe spec on the prototype (fixture registry as in the c0141 spec), `checkpaths.scan` printed `{ }` (both exempt) for:
- z-nile item c0001, Touched `z-nile/skills`, check.sh `test -d z-nile/skills/new` (run from `z-nile/`, so it tests `z-nile/z-nile/skills/new`). `owned("z-nile", {"z-nile/skills"})` = `{z-nile/skills, z-nile/z-nile/skills}`, and `repoPath` gives `z-nile/z-nile/skills/new`, under the second reading. This is the commonest check.sh mistake (a repository-relative path written in a check that runs from its home), and the check fails when it runs.
- pickman item f0002, Touched `src/New` (home-relative), check.sh `cd .. && test -d src/New` (tests the root's `src/New`, which nothing creates). `owned` adds the repository-relative reading `src/New`, so it's exempt. On main the same item is reported (`../src/New` isn't under `src/New`): this is a **regression** the both-ways reading brings.
Either way the path checked isn't the one the item creates, so the check fails at execution, which check-paths exists to stop in prep. The fixture covers neither case, and mutants C/D only remove a reading.
Critique: the "both ways" reading is ambiguous, and the design settles the ambiguity by accepting both, so every entry owns two paths. The tempting fix is to drop one reading. That turns the live scan red (mutant D) or breaks c0115/c0117-style entries.
Consequences: the entry needs one interpretation, chosen from its own text. An entry whose first segment names a registered project home (`z-nile/`, `pickman/`, from `projects.toml`, not a hand list) is repository-relative only. Any other entry is home-relative, except a root-level path (`zn`, `AGENTS.md`, `.github/…`, the `FILES` set and root folders that exist at the top), which stays ambiguous. Both readings remain only for those, and they're the rare case. A home literally containing a folder named after another home (`z-nile/pickman/…`) would read wrong. Today nothing like that exists, and the rule should state it.
Recommendation: specify `owned` so that an entry starting with `<home of any registered project>/` is read only repository-relative, and every other entry only from the item's home, except entries that resolve to an existing or Touched root-level path (state the exact rule). Add fixture cases: (a) z-nile item, Touched `z-nile/skills`, check `test -d z-nile/skills/new` → reported; (b) pickman item, Touched `src/New`, check `cd .. && test -d src/New` → reported; (c) the existing c0001/f0003/c0005 still exempt. Add mutants "both readings for every entry" (killed by a/b) and "home prefix not from the registry". Re-run E1 on the live tree. If some live item turns red, list it and its path (z-design/new-rules-migrate-existing-work).

### F2 [high] AC2 (and AC1) pass with c0120's promoted spec unchanged, so the gate keeps the old rule and the captured defect stays
Where: check.sh AC2; c0141.md Acceptance criteria
Evidence: in a scratch clone at d24aabc8 (main, c0120's spec untouched), adding only the prototype's `z-nile/tests/lib/checkpaths.luau` and running AC2's command `bash -c 'test -f tests/lib/checkpaths.luau && lune run tests/run -- tests/acceptance/c0120/check-paths.spec.luau'` from `z-nile/` → `4 passed, 0 failed`. AC1 runs only against the library. An executor who adds the library and never rewires c0120's spec passes both checks. The gate's live scan (c0120's own copy of `scan`) then still reports `../pickman/skills (from z-nile)`, which is the capture's Problem ("fails the gate the moment its prep lands").
Critique: neither criterion ties the gate's scan to the new rule. The obvious fix, grepping c0120's spec for `require("@tests/lib/checkpaths")`, still passes a spec that requires the library but keeps a local `scan`.
Consequences: the pin has to show that the scan the gate runs is the library's. A text pin works if it covers both halves: the require, and no local definition of the moved functions.
Recommendation: add a Checked criterion (or extend AC2) that c0120's spec takes its scan from the library. For example, a c0141 spec case reads `tests/acceptance/c0120/check-paths.spec.luau` and asserts that it requires `@tests/lib/checkpaths`, that it calls `checkpaths.scan(`, and that it has no `local function` named `literals|present|touched|under|items|scan` and no `PREFIXES =`. Mutant: the library added and c0120's spec untouched → red. Lesson z-design/spec-design-correspondence.
Lesson: z-design/spec-design-correspondence

### F3 [medium] Moving the scanner out of the promoted spec takes the rule out from under "never edit promoted specs"
Where: c0141.md Design, "Where it lives"; Regression guard
Evidence: the zz-test skill (line 25) says promoted `tests/acceptance/<id>/` files are never edited, and z-design asks for an `Overrides:` line only for a promoted spec a design changes. After the move, c0120 AC11's rules (`PREFIXES`, `FILES`, the quote and grep-pattern readings, `present`'s glob rule) live in `z-nile/tests/lib/checkpaths.luau`, which any later item can edit with no `Overrides:` line. A promoted spec only has to stay green, and its fixture cases pin only some of those rules. For example, dropping a prefix such as `.github/` from `PREFIXES` would be caught, if at all, only by the real-tree case, and only while some live check.sh names such a path.
Critique: the design says it moves the code "so the rule can be pinned by a sequestered spec of its own". But it also removes the strongest pin the rule had: its text was frozen. The tempting fix ("say in the skill that `tests/lib/checkpaths.luau` is protected") is a rule no check enforces.
Consequences: the library's place decides its protection. A file inside the promoted folder (`z-nile/tests/acceptance/c0120/checkpaths.luau`, the same pattern as `rewrites.luau` and `finished.luau`, which already sit beside c0120's specs as modules) stays under "never edit". c0141's own spec can require it by path, and later items can change it only through an Override. The cost is one cross-folder require from c0141's promoted spec to c0120's folder, which becomes an edge that the next mover of c0120's folder must follow.
Recommendation: put the moved scanner in c0120's promoted folder (as `rewrites.luau` and `finished.luau` already are), keep the `Overrides:` line naming the spec and the new module, and update Touched modules, the AC2 label and the Affected specs line to match. If the author keeps `tests/lib`, the design must say which check stops a later item from weakening it, and the spec cases must pin each `literals` rule.

Candidate lessons (for the lead):
- zz-test: when a rule moves from a sequestered or promoted file into a shared library, its acceptance criteria must pin that the old caller uses the library, because otherwise "library exists and passes" is met while the gate runs the old copy; check: does any criterion fail if the old file keeps its own copy?
- z-design: reading one field two ways to accept two conventions doubles what every entry claims; check: for each value, which readings could it have, and does a case show that the reading not meant exempts nothing?

Verdict: changes
