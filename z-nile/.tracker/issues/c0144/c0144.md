# c0144: Colorful cli output

## Problem
The user, 2026-10-25: "`zn status` should use columns and ansi colors for a visually appealing output in terminal. Similarly for other commands that produce output. Be creative, use colors and terminal features well."

Today `./zn status` prints one plain line per item (`f0143 new Speed boost escape`): the id, the state word and the title run together with no alignment, no color and no grouping, so a long backlog is hard to scan. The other commands that print for a person (`list`, `members`, `busy`, `audit`, `check`, `metrics`, `lessons`, `workstreams`, `spend`, `capture`, `promote-check` and the like) are plain text too. What should happen: in a terminal, `zn status` lays its output out in aligned columns with ANSI colors, and so do the other commands that produce output, using colors and terminal features well and creatively.

## Non-goals
- The HTML board (`./zn board`, c0118) and the board server (c0121).
- What each command reports: the facts and exit codes stay the same; only how they are shown changes.

## Solution
- Color and layout only when stdout is a terminal; plain, stable text when piped or redirected, and honour `NO_COLOR` (and a `--no-color` or `--color=always` switch), so specs, scripts and the skills' instructions that read the output keep working.
- `status`: aligned columns (id, type, state, title, raft, owner or claim), colored by type and by lifecycle state, grouped (by project, then by state or raft), with the terminal width respected (titles truncated with an ellipsis).
- Other commands: color PASS/FAIL and counts in `check` and `audit`, headings and tables in `metrics`, `members`, `busy`, `workstreams`, `lessons`; use terminal features where they help (bold and dim, Unicode box or bar glyphs, clickable OSC 8 hyperlinks to item files and PRs, a summary line), falling back cleanly where unsupported.

## Design
The rule: **plain text whenever stdout is not a terminal, byte for byte what each command prints today; the rich look only on a terminal (or when forced), and color only inside it.** Every script, spec, `check.sh`, `$(...)`, CI job and agent shell (Claude Code's Bash tool is not a terminal: E2) reads stdout through a pipe, so none of them can see a change; only a person at a terminal does.

**Deciding the mode (pure: `z-nile/engine/term.luau`).**
- `export type Mode = { rich: boolean, color: boolean, links: boolean, unicode: boolean, width: number }`; `term.PLAIN` is the plain mode.
- `term.choice(value: string?): (Choice?, string?)` reads `--color=<auto|always|never>` (`auto` when absent); any other value is refused: `--color takes auto, always or never (got "<value>")`.
- `term.decide(choice: Choice, env: { [string]: string? }, tty: boolean, ttyColumns: number?): Mode`:
  - `rich` = `choice == "always"` or `tty`. Not rich → exactly `term.PLAIN` (nothing else runs).
  - `color` = rich and (`choice == "always"`, or `choice == "auto"` and `NO_COLOR` unset or empty (no-color.org) and `TERM ~= "dumb"`). The explicit `--color=always` wins over `NO_COLOR`. `never`, `NO_COLOR` and `TERM=dumb` keep the layout and drop the color (G4).
  - `links` = color and `ZN_HYPERLINKS ~= "0"` (G3).
  - `unicode` = the first non-empty of `LC_ALL`, `LC_CTYPE`, `LANG` names UTF-8 (`utf-8`/`utf8`, any case); else ASCII glyphs (`+ x ! * - ->`, `#`/`.` bars, `.` for the ellipsis).
  - `width` = `COLUMNS` when it is a number ≥ 20, else the terminal's columns when ≥ 20, else 80.
- Helpers, all pure over plain text: `paint(mode, style, text)` (16-color SGR only, so the terminal's theme picks the shades on light and dark backgrounds: G1); `kindOf(id)`; `link(mode, url, text)` (OSC 8 `ESC]8;;url ESC\ text ESC]8;; ESC\`); `strip`, `width` (escapes take no columns; UTF-8 characters one each); `fit(mode, text, n)` (cut with `…`); `wrap(text, n)` (at spaces, a longer word whole); `columns(mode, cols, rows, indent?, sep?)` (aligned, `right` for numbers, one `flex` column shrunk to fit the width down to 8 columns, styled after fitting); `bar(mode, fraction, cells)` (eighth blocks); `rule(mode, title)` (a heading line; a title too long for it wraps in bold instead, so no word is lost); `glyph(mode, name)`.
- The styles (G1): feature green, defect red, chore blue, raft magenta; `new` plain, `preparing` cyan, `prepared` green, `active` bold yellow, `done` and `retired` dim; PASS/ok green, FAIL/error bold red, warning yellow; ids and headings bold, secondary text dim.

**The adapter (`z-nile/engine/main.luau`).**
- `flags()` learns two global options: `--no-color` is a switch (it takes no value, so `members --no-color R0003` keeps `R0003`), and `--color=<v>` is stored as `--color` (`--color <v>` already works as a value option). The dispatch reads them once before the handler runs, sets `colorChoice` (the last one given wins; `--no-color` is `never`), removes both from `opts` so no command sees them, and refuses a bad value (above).
- `outputMode()` works the mode out on first use: `isTerminal(1)` runs `sh -c '[ -t 1 ]'` with stdout forwarded (the child shares the engine's stdout, E1), and on a terminal `terminalColumns()` reads `stty size </dev/tty`. Nothing is exported to children: a nested `./zn` (in `$(...)`, `| cat`, a `check.sh`, a spec that runs `lune run …/engine/main` directly) probes its own stdout and is plain (E1, E3). Lune can't set its own environment for children anyway (E3).
- `say(text, rich?)` prints `text` as it is (plain), or the lines `rich(mode, text)` makes of it. Each command builds today's text exactly as now and passes it, with the rows its look needs, to `say`; the plain branch is today's code path, so piped output can't change (AC3 compares it byte for byte with the base engine).
- `fail(msg)` paints its message (error style, with the error glyph) only when stderr is a terminal (`isTerminal(2)`) and the choice allows color; piped, it is today's text exactly.
- `sh.stream(cmd, args, env?)` (`z-nile/lib/sh.luau`) gains an optional `env`; `runCheck` passes `NO_COLOR=1` to `check.sh` when the run is rich but uncolored (`--no-color`, `--color=never`), so ac.sh drops its color too.

**Each command's look (pure: `z-nile/engine/look.luau`)**. A renderer reads only the lines its own command just built (or the rows it was handed); any line it does not recognise passes through unchanged, never dropped, so a later change to a command's text degrades to plain-looking lines and loses no fact (lesson zz-arch/one-reader-per-format: these are not file formats, and the fallback is pinned in render.spec). Every look keeps every word of the plain text (AC2 compares the words at 200 and at 60 columns; only `status` and `list` titles may be cut, with an ellipsis, as the capture asks):
- `look.prUrl(origin: string?, branch: string): string?`: an active raft's pull requests as a GitHub search for its branch, from origin's configured URL (`git config --get remote.origin.url`, read only when links are on): `git@github.com:o/r(.git)`, `https://github.com/o/r(.git)`, `ssh://git@github.com/o/r(.git)`; nil for anything else (a path, another host). The branch is `<id>-<slug>` (zz-rules: a raft's branch), percent-encoded outside `[A-Za-z0-9._-]`.
- `status`: grouped by project (a rule line with its name, projects sorted), then by state in the order active, preparing, prepared, new (a heading `ACTIVE (n)` in the state's style); one layout per project so the columns line up under every heading: id (colored by kind, an OSC 8 link to the item's document, or for an active raft to its pull requests), type, state, title (the flex column), raft (linked like that raft's own id), and the claim's three stamp words (dim; dropped first when keeping them would leave the title under 24 columns). A summary line ends it: `<n> items: <a> active · <p> preparing · <q> prepared · <m> new`. The rows carry the type, raft, claim and project, which the plain line does not (the capture's "id, type, state, title, raft, owner or claim"; there is no owner field, so the claim words stand for it).
- `list`: today's columns (id, state, type, raft, title), colored (`done` and `retired` dim), ids linked (an active raft to its pull requests), the title fitted.
- `members`: a bullet, the id (linked to its document), the folder dim.
- `busy`: each reason with a warning glyph, ids colored, wrapped to the width.
- `audit`: each `error`/`warning` line as a glyph and severity (error red, warning yellow) and its code, the path and message wrapped under it; the summary with `0 errors` green or `n errors` red, warnings likewise.
- `check`: the `=== <id> check.sh` heading as a rule; ac.sh colors its own `PASS`/`FAIL`/`LIST` and the `----` summary when *its* stdout is a terminal (`[ -t 1 ]`) and `NO_COLOR` is empty and `TERM` isn't `dumb`; the words stay the same, so stripped of color the text is today's. Nothing is exported, so a check.sh inside `$(...)` or a spec stays plain. `promote-check`: the heading as a rule and `✔ promote-check OK` in green.
- `workstreams`: the raft line bold, one line per wave (`wave 1 → c0134  c0135`), `parallel: yes` green, `no` yellow.
- `lessons`: each lesson's id bold with a bar of its sources against the most-cited one and its `(<when>, <n> sources)`, the check wrapped under it; `== <path>` headings bold; the `--check`/`--uncovered` ok lines green.
- `metrics`: its markdown tables boxed (`│` columns, a `─` line under the header, numbers right-aligned), section lines bold, and each rework rate with a bar against the 20% target (green under, red over). The report is collected as one page first (a local `print`, and `metricsLessons(print)` writes through it), so the plain page is printed in today's order.
- `capture`: its header line with the label bold and the sha dim; the document as is. `spend`: each share row with its id colored and `+added`/`-removed` green/red, the commit sha marked ok.
- The usage text (no command, or an unknown one): command names bold, descriptions dim. It gains one paragraph naming `--color=auto|always|never` and `--no-color`, in plain text too.

**Not given a look (G2):** `find`, `worktree`, `prompt --path`, `stamp`, `raft-plan` (commands to run: they stay copyable), `board`'s path, and the gate and spec runner (`z-nile/check.sh`, `tests/run`), whose output is not `./zn`'s; the HTML board and server stay non-goals.

**Decisions this relies on.** The capture (the user, 2026-10-25) asks for columns and color in a terminal, the same facts and exit codes, plain text when piped, NO_COLOR and a switch. No `game-design.md` decision is involved (tooling only). No new dependency edge outside z-nile (no architecture map change: z-nile has none).

### Scalability
One `sh` probe of stdout per command that prints through `say` (only on its first print), one `stty` probe when it is a terminal, one `sh` probe of stderr per refusal: constant, whatever the number of items, roots or projects. Rendering is linear in the lines printed; `status` lays out each project once. No git call is added.

### Maintainability
A new command's look is one pure function in `look.luau` over the text it already prints, wired with one `say(text, look.x)`; the mode rules live in `term.decide` alone (one reader of `--color`, `NO_COLOR`, `TERM`, `COLUMNS`, the locale). ac.sh keeps its own three-line rule because it is shell and must decide for its own stdout (zz-arch rule 2). A new project needs nothing: status groups by `projects.folderOf` of each root.

### Usability
- The usage text names `--color=auto|always|never` and `--no-color`; zz-rules' "Other commands" says how output is shown and that only piped output is to be parsed (pinned in AC2).
- A bad `--color` value names the rule. `ZN_HYPERLINKS=0` turns links off for a terminal that shows them badly.
- Exhaustive lists: no new command, so the main checkout's command list and `READ_ONLY` are unchanged; the usage text is the one list that changes.

## Unknowns & experiments
- **E1. Can the engine tell a terminal from a pipe, and its width?** (pass) Lune 0.10.5's stdio has no isatty (`color ewrite format prompt readLine readToEnd style write`). `process.exec("sh", {"-c", "[ -t 1 ]"}, {stdio = {stdout = "forward"}}).ok` is false piped and true under a pty (`script -q /dev/null …`); `stty size </dev/tty` gives `0 97` after `stty cols 97`, and `0 0` when unset (so the 80 fallback). Fallback had it failed: the `zn` wrapper passing `[ -t 1 ]` as an argument.
- **E2. Do agents see a terminal?** (pass: no) In Claude Code's Bash tool `[ -t 1 ]` and `[ -t 0 ]` are false (`TERM=xterm-ghostty`, `CLAUDECODE=1`), so agents always get plain text.
- **E3. Does an env var reach children, and would one leak into nested runs?** Writing `process.env.NO_COLOR` in Lune does not reach `process.exec` children; `process.exec(…, {env = {NO_COLOR = "1"}})` adds it to the inherited environment (`1|/Users/…`). Specs run `lune run …/engine/main` directly (c0052, c0114, c0116, c0120 specs), so a TTY flag exported by `zn` would leak into them: the probe-per-process design avoids any export.
- **E4. Does `script` give a pty inside the spec jail, on macOS and on CI's Linux?** (pass on macOS) look.spec's pty cases pass in the jailed runner on macOS (`script -q /dev/null bash -c …`); on Linux it uses `script -qec … /dev/null`: proved by the prototype's CI run (Verification of E5).

## Acceptance criteria

### Checked
- AC1: the pure rules (term.spec, render.spec): rich layout only on a terminal or with `--color=always`; color only inside it, never with `--color=never`/`--no-color`, `NO_COLOR` (non-empty) or `TERM=dumb` unless forced; the width from `COLUMNS`, the terminal, else 80 (≥ 20); Unicode by locale; links only with color unless `ZN_HYPERLINKS=0`; fit, wrap, columns, bars; each command's look (groups and order, glyphs, bars, colors, PR and file links) passing any unknown line through.
- AC2: piped, every command prints no escape sequence and the same bytes with `--color=never`, `--no-color` (anywhere) or `NO_COLOR`; on a terminal or with `--color=always` it prints the rich look (status grouped by project and state in aligned columns with a summary; every command's look) that keeps every word of the plain text, fits the width (only status and list titles cut, with an ellipsis), links ids to their documents, uses ASCII outside UTF-8; a nested `./zn` with a piped stdout stays plain; `./zn check` colors PASS only on its terminal and not with `--no-color`; a refusal is colored only on a terminal's stderr; a bad `--color` is refused; the usage text and zz-rules say how output is shown.
- AC3: piped, every command prints byte for byte what the engine before c0144 printed (base: the merge-base with origin's main as `git ls-remote` reports it).
- AC4: the specs that read `./zn`'s output still pass.
