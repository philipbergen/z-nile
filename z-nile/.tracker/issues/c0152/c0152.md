# c0152: Merge past tracker only main

## Problem
zz-rules **Merging** step 4 says that if `main` moved since the PR's green CI, the merger merges `origin/main` in, reruns `check.sh --full`, pushes and waits for CI again. With several sessions publishing tracker state (spend rows, captures, claims) to `main` every few minutes, a PR's 15-minute cycle rarely finishes before `main` moves again, so the cycle can loop indefinitely. Three merges on 2026-10-25 (#126, #117 and earlier ones) went in with `main` one or more tracker-only commits ahead, against the letter of the rule, each recorded as a deviation.

Since R0063 "Local ci only" (#180), steps 2 and 3 of Merging are a local full gate in a clone outside the repository and `lune run scripts/cicd` there, and GitHub Actions is no longer read; step 4's fallback repeats both. The cycle this issue saves is those two steps, and the outcome asked for is unchanged.

What should happen: the rule says when a PR may merge although `main` moved: when every commit `main` gained since the PR's green head is tracker-only (the publisher's tracker-state classes) and touches none of the PR's files, so GitHub's squash merge produces exactly the tree CI tested plus those tracker changes. Any other movement (code, specs, skills, or a tracker file the PR also changes) still requires merging `main` in and a new green CI.

Decided with the user (2026-10-25): "Run those checks first" (design review 001 F1: before the skip, merge-check also runs the gate stages that read tracker files on the would-be merged tree; design review 002 F2: those stages are the list a pasted search finds, kept in one file, not a hand list of two).
Decided with the user (2026-10-26): "Skip re-trial for spend-only moves" (design review 003 F1: after the trial merge-check reads main's tip again; when main moved only by spend rows, or other files the stage list marks `notrial`, it judges the new commits by rule 1 and says ok without running the trial again; any other move runs the trial again). Reviewer's note beside the decision (design review 004): a spend row that arrives during the check is never tried, so a PR that changes code reading spend rows (the board, metrics, the spend format) can merge over a row it never ran against; the decision accepts that. A row for a folder the PR moved away is tried (rule 3), since it is no row of a live item.

## Non-goals
- Branch protection or required-checks settings on GitHub.
- The dispatcher's own merge vetting (c0117 G20).

## Solution
- State the exception in zz-rules Merging step 4 with the exact test (e.g. `git diff --name-only <green head>...origin/main` lists only tracker-state paths, disjoint from `git diff --name-only origin/main...HEAD`), and give it one helper (`./zn merge-ready <pr>` or a function `done`/the Merging poll uses) so leads don't each improvise it.
- A spec case for each side: a tracker-only spend row on main allows the merge; a code commit, or a tracker file the PR also edits, does not.
## Design
**The rule (zz-rules Merging step 4).** When `main` moved after a PR's head passed Merging steps 2 and 3 (the local full gate in a clone outside the repository and `lune run scripts/cicd`, R0063), the merger first runs `./zn merge-check <that head>`. When it says ok, the PR merges without repeating steps 2 and 3, **pinned on both sides** (design review 003 F1): the head with `gh pr merge <pr> --squash --match-head-commit <the sha it prints>` (design review 001 F2: a push after the check makes GitHub refuse the merge; the merger runs merge-check again once steps 2 and 3 pass on the new head), and the base by running `git ls-remote origin refs/heads/main` right before that merge and merging only when it prints the `judged main <sha>` merge-check printed, else running merge-check again (GitHub has no flag that pins the base, and `--squash` lands on whatever main is; this brings the race back to the seconds the old rule had). It quotes the ok lines in its merge comment. merge-check takes about 2–3 minutes idle and 10 or more under load (E5b: one trial, 599 s at load 50), up to three trials: zz-rules says to run it in the background (or with no timeout) and wait for its verdict line (design review 004 F3), and its first progress line names its trial folder (`merge-check: trial of main <sha> in <folder>`), so a run killed midway names what it left (design review 003 F3). When it says no, the existing rule applies unchanged: merge `origin/main` in (clean merge), repeat steps 2 and 3 (the local full gate in a clone outside the repository, and `lune run scripts/cicd` there), push, and check step 4 again, or `BLOCKED:` on a conflict (R0063).

**ok** means both:
1. **Main's new commits are skippable tracker state.** Every commit `origin/main` gained since the PR's head left it (`git rev-list <head>..<tip>`; a merge commit judged by its first-parent diff, `diff-tree -m --first-parent`, so its own changes count, design review 001 F3) changes only paths `publish.allowed(path, roots)` accepts (the publisher's definition, read with the registry at main's tip: an item's `<ID>.md`, `check.sh` or an issue's `spend.md` under a registered root, and the id counter), **adds** or **moves** any `check.sh` it touches (a new item's; a move as `ready` and `done` make: **the same item's** `check.sh` deleted and added with the same blob and mode in that commit, read from `diff-tree --raw` and paired by item id, never by blob alone, which a decoy item with the same text would match, design review 002 F3; a **changed or dropped `check.sh` is a no**, design review 001 F4: the stricter reading c0117's `trackerstate` takes, chosen now so the verdict is the same whichever lands first), and touches none of the files the PR changes (`git diff --name-only <merge-base> <head>`).
2. **The would-be merged tree passes the gate stages that read tracker files** (decided with the user, 2026-10-25: "Run those checks first"; design review 001 F1). `git merge-tree --write-tree <head> <tip>` (a conflict is a no), `git commit-tree` of that tree with both parents (one unreferenced commit object in the checkout's store), then **the trial checkout: its own repository in a fresh folder under `$TMPDIR`** (`mktemp -d "$TMPDIR/merge-check.XXXXXX"`, as remap does; design review 002 F1): `git clone --no-hardlinks --no-checkout <checkout> <folder>`, a full copy of the objects, unreferenced loose ones included, so the merge commit and the history the finished specs read come with it and nothing points back at the checkout (no `objects/info/alternates`; design review 003 F2: round 002's `--shared` left the real object store reachable from the trial; about 0.3 s and 18 MB here), `git remote remove origin`, `git checkout --detach <merged commit>`. Every stage is spawned with `PICKMAN_FENCE_REAL_GIT` set to the merger's git directory plus whatever it inherited, so the nested runs' jail (macOS) denies writes to it and their reference-transaction and pre-push hooks refuse ref updates and pushes into it: the trial runs code no gate of the merger's has run (main's new check.sh files under `AC_LIST=1`, the merged tree), and its nested runs protect only their own checkout otherwise. It is never a worktree of the merger's checkout and nothing goes under its `.cache`, so the fence of any spec run in that checkout (which watches worktrees registered under `.cache`) never sees it. There every **stage** runs: the `run <home> <spec>` lines of `z-nile/tests/merge-stages.txt` **as the merged tree has it**, each `lune run tests/run -- <spec>` from its home. A listed spec missing from the merged tree is a no (never a skip, lesson zz-test/no-vacuous-pass), and so is a tree without the file or with no `run` line; a trial folder that can't be removed is a no naming it. The folder is removed before the verdict.
3. **Main's tip is pinned (design review 003 F1).** After the trial merge-check reads origin's tip again. Unchanged: ok, printing `judged main <tip>`. Moved: it fetches the new tip's objects only (`git fetch --no-write-fetch-head --refmap= origin refs/heads/main`: no ref moves), requires the old tip to be an ancestor, and judges the new commits by rule 1 (any no is a no). When every path they change matches a `notrial <glob>` line of the merged tree's stage list and belongs to a live item (its item's document is still in that folder in the merged tree: the PR's copy when the PR changed that folder, else main's; design review 004 F2: a first spend row at the old folder of an item the PR moved would otherwise leave an orphan folder audit rejects) (today only `*/.tracker/**/spend.md`, decided with the user, 2026-10-26: "Skip re-trial for spend-only moves"; c0042's and c0043's board and metrics stages do read spend rows, which the decision accepts because only `./zn spend` writes them), it says ok with the new tip as judged, without a new trial. Any other move runs the trial again on the new tip, at most three trials (design review 004 F1). After the third trial the tip is read once more: unchanged, or moved only by `notrial` rows of live items, is ok; any other move is a no, "origin's main kept moving during the check (3 trials): run merge-check again". zz-rules gives one instruction for that no and for "moved during the check … can't be judged here": run merge-check again; every other no falls back to the old rule. The `notrial` set is kept in the stage list, beside the stages it exempts from, never in code.
   **The stage list (design review 002 F2).** One file, `z-nile/tests/merge-stages.txt`: a `run` line per stage, a `skip` line per search hit that reads no item file a tracker-only commit can change, each with its reason. It came from this search (rerun it; c0152's promoted `stages.spec` holds the pattern and fails when a hit is on neither list):

   36 hits on main 3fdc2856 (the reviewer's phrase search, 22 hits, plus the reads a subagent's second search found: `audit.run/scan/leftovers(TOP)`, `board.collect(nil, root)`, `lessons.load(TOP)`, `cwd = TOP`, done check.sh reads). **Run (15):** c0082/real-tree (it is `./zn audit` in the gate), c0120/check-paths, c0114/classified (unique slugs, kinds per root, every unfinished check.sh lists under `AC_LIST=1`), c0114/finished, c0042/cli, c0043/rounds, c0116/retired, c0115/lessons, c0119/scope-lessons, c0120/finished (every done check.sh), c0120/layout, c0120/old-roots, c0073/board-stats, tooling/board, tooling/repo-fence (every check.sh under every root). **Skip (21, 23 after the re-prep for R0063; E8)**, each reason in the file: pickman's c0063 and c0103 narrowed (one fixed done item each), f0054 docs and meta/architecture (root documents, not item state: a change to them isn't tracker-only), and z-nile's c0060/fixture, c0081/renamed, c0114 gate-cover/guards/layout/roots-cli, c0115 absence/docs/layout/prompt/readme/trusted-base, c0116 docs/promote, c0120 gate-homes/graph-homes/registry-home (skills, docs, the registry, the compaction map, fixtures, or `zn find` of fixed ids). A spec added later that walks the real tree's items joins the list in the change that adds it, or `stages.spec` fails (lesson zz-rules/exhaustive-lists-name-new-things). The list is read from the merged tree, so a PR that changes it is judged with its own list; main's skippable commits can't touch it (it isn't tracker state).
Also ok: main hasn't moved past the head. **No**, naming each commit (`<short sha> <subject>`) and path, or the failing check, ending "merge origin/main in and run the gate again". Main's tip is read from the remote (`git ls-remote origin refs/heads/main`), never the local tracking ref (lesson zz-review/sequestration-reference-not-a-ref); a tip that isn't a local commit is a no ("git fetch origin"). **Every failed git read is a no** naming the command (design review 001 F5; lesson zz-arch/guard-no-is-explicit). The ok and no outputs both print `merge with --match-head-commit <full head sha>` on ok.

**One definition of tracker state (design review 001 F4).** Today `publish.allowed` plus the "adds only" rule for `check.sh`. c0117 (R0052, in code review) adds `z-nile/engine/trackerstate.luau`, "the one definition … the merge gates all use". If c0117 lands first, c0152's execution takes `trackerstate` instead of `publish.allowed` (its stricter judgement of sequestered files agrees with rule 1's "adds only"); if c0152 lands first, c0117's lead switches `mergecheck` to `trackerstate` in its rebase. Either way the merge-commit, existing-`check.sh` and spec cases keep the same verdicts.

### Scalability
Rule 1 is one `ls-remote`, one `merge-base`, one `rev-list` and one `diff-tree` per new main commit. Rule 2 adds a merge-tree, a full clone (about 0.3 s, 18 MB) and the listed stages: 136 s on the real repository at load 4–6 (E4; c0120/finished alone is about 100 s), against the 15-minute cycle it saves. Rule 1's refusals come before the trial, so a no on main's commits costs seconds. **How often rule 3 runs the trial again** (design reviews 003 F1 and 005 F3), from main's first-parent log (`git log --first-parent --format='%ct|%s' --since='2026-10-25 08:00' origin/main`, 266 commits), a window of the check's length placed every 30 s; "spend" is a subject starting `tracker: spend`, a "PR merge" one with `(#`:

| check length | main moved | spend rows only (no new trial) | a new trial needed | a PR merge in the window (a no) |
|---|---|---|---|---|
| 180 s (idle) | 23% | 12% | 11% | 3% |
| 600 s (load, E5b) | 44% | 17% | 27% | 10% |
| 1200 s | 52% | 15% | 38% | 16% |

So under the usual load about 27–38% of checks run a second trial, roughly 7–14% a third, and 10–16% end in a no because a prep or raft PR merged meanwhile. That converges (below round 003's threshold of half): no escalation. The fixture spec's cost is in Test plan and E7.

### Maintainability
The exception is decided by one command every merger runs (a lead, a stream, later c0117's dispatcher), instead of each lead improvising and recording a deviation (three such on 2026-10-25: #126, #117 and #129's base). Tracker state stays one definition: if the publisher allows a new kind of path, merge-check follows.

### Usability
Each refusal names the commit and the path, and ends "merge origin/main in and run the gate again"; the ok line says how many commits and that none touches the PR.
