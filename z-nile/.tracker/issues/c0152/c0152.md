# c0152: Merge past tracker only main

## Problem
zz-rules **Merging** step 4 says that if `main` moved since the PR's green CI, the merger merges `origin/main` in, reruns `check.sh --full`, pushes and waits for CI again. With several sessions publishing tracker state (spend rows, captures, claims) to `main` every few minutes, a PR's 15-minute cycle rarely finishes before `main` moves again, so the cycle can loop indefinitely. Three merges on 2026-10-25 (#126, #117 and earlier ones) went in with `main` one or more tracker-only commits ahead, against the letter of the rule, each recorded as a deviation.

What should happen: the rule says when a PR may merge although `main` moved: when every commit `main` gained since the PR's green head is tracker-only (the publisher's tracker-state classes) and touches none of the PR's files, so GitHub's squash merge produces exactly the tree CI tested plus those tracker changes. Any other movement (code, specs, skills, or a tracker file the PR also changes) still requires merging `main` in and a new green CI.

## Non-goals
- Branch protection or required-checks settings on GitHub.
- The dispatcher's own merge vetting (c0117 G20).

## Solution
- State the exception in zz-rules Merging step 4 with the exact test (e.g. `git diff --name-only <green head>...origin/main` lists only tracker-state paths, disjoint from `git diff --name-only origin/main...HEAD`), and give it one helper (`./zn merge-ready <pr>` or a function `done`/the Merging poll uses) so leads don't each improvise it.
- A spec case for each side: a tracker-only spend row on main allows the merge; a code commit, or a tracker file the PR also edits, does not.
## Design
**The rule (zz-rules Merging step 4).** When `main` moved after a PR's head went green, the merger first runs `./zn merge-check <green head>`. When it says ok, the PR merges without another cycle: GitHub's squash merge is then exactly the tree CI tested plus main's new tracker changes. The merger quotes the ok line in its merge comment. When it says no, the existing rule applies unchanged: merge `origin/main` in (clean merge), rerun the full gate, push, wait for green CI again, or `BLOCKED:` on a conflict.

**ok** means: every commit `origin/main` gained since the PR's head left it (`git rev-list <head>..<tip>`) changes only paths `publish.allowed(path, roots)` accepts (the publisher's own definition of tracker state, read with the registry at main's tip: an item's `<ID>.md`, `check.sh` or an issue's `spend.md` under a registered root, and the live id counter `z-nile/next`), and none of those paths is a file the PR changes (`git diff --name-only <merge-base> <head>`). Also ok: main hasn't moved past the head. **No**, naming each commit (`<short sha> <subject>`) and path: any other path (code, specs, skills, an acceptance spec under a tracker root, the registry), or a tracker path the PR also changes. Main's tip is read from the remote (`git ls-remote origin refs/heads/main`), never from the local tracking ref, which one `update-ref` forges (lesson zz-review/sequestration-reference-not-a-ref); a tip that isn't a local commit is a refusal ("git fetch origin"). A merge commit on main is judged by its first-parent diff.

**Where.**
- `z-nile/engine/mergecheck.luau` (new, strict, reads only): `judge(dir, head): Verdict` with `Verdict = { ok: boolean, lines: {string}, url: string }`; it uses `publish.allowed` and `projects.at(tip)` (one definition each, lesson zz-arch/one-definition-of-tracker-state).
- `z-nile/engine/main.luau`: `cmd["merge-check"]` (prints each line as `merge-check: <line>` and `merge-check: origin is <url>`, exit 0 ok, 1 no), its usage line, the require.
- `z-nile/skills/zz-rules/SKILL.md`: Merging step 4's new first sentence (above), the commands table row, and `merge-check` in the main checkout's read-only command list.

### Scalability
One `ls-remote`, one `merge-base`, one `rev-list` and one `diff-tree` per new main commit: a handful of commits per cycle, well under a second.

### Maintainability
The exception is decided by one command every merger runs (a lead, a stream, later c0117's dispatcher), instead of each lead improvising and recording a deviation (three such on 2026-10-25: #126, #117 and #129's base). Tracker state stays one definition: if the publisher allows a new kind of path, merge-check follows.

### Usability
Each refusal names the commit and the path, and ends "merge origin/main in and run the gate again"; the ok line says how many commits and that none touches the PR.
