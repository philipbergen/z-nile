# c0152: Merge past tracker only main

## Problem
zz-rules **Merging** step 4 says that if `main` moved since the PR's green CI, the merger merges `origin/main` in, reruns `check.sh --full`, pushes and waits for CI again. With several sessions publishing tracker state (spend rows, captures, claims) to `main` every few minutes, a PR's 15-minute cycle rarely finishes before `main` moves again, so the cycle can loop indefinitely. Three merges on 2026-10-25 (#126, #117 and earlier ones) went in with `main` one or more tracker-only commits ahead, against the letter of the rule, each recorded as a deviation.

What should happen: the rule says when a PR may merge although `main` moved: when every commit `main` gained since the PR's green head is tracker-only (the publisher's tracker-state classes) and touches none of the PR's files, so GitHub's squash merge produces exactly the tree CI tested plus those tracker changes. Any other movement (code, specs, skills, or a tracker file the PR also changes) still requires merging `main` in and a new green CI.

Decided with the user (2026-10-25): "Run those checks first" (design review 001 F1: before the skip, merge-check also runs the gate stages that read tracker files on the would-be merged tree; design review 002 F2: those stages are the list a pasted search finds, kept in one file, not a hand list of two).

## Non-goals
- Branch protection or required-checks settings on GitHub.
- The dispatcher's own merge vetting (c0117 G20).

## Solution
- State the exception in zz-rules Merging step 4 with the exact test (e.g. `git diff --name-only <green head>...origin/main` lists only tracker-state paths, disjoint from `git diff --name-only origin/main...HEAD`), and give it one helper (`./zn merge-ready <pr>` or a function `done`/the Merging poll uses) so leads don't each improvise it.
- A spec case for each side: a tracker-only spend row on main allows the merge; a code commit, or a tracker file the PR also edits, does not.
## Design
**The rule (zz-rules Merging step 4).** When `main` moved after a PR's head went green, the merger first runs `./zn merge-check <green head>`. When it says ok, the PR merges without another cycle with `gh pr merge <pr> --squash --match-head-commit <the sha it prints>` (design review 001 F2: a push after the check makes GitHub refuse the merge; the merger runs merge-check again after the next green CI), and quotes the ok line in its merge comment. When it says no, the existing rule applies unchanged: merge `origin/main` in (clean merge), rerun the full gate, push, wait for green CI again, or `BLOCKED:` on a conflict.

**ok** means both:
1. **Main's new commits are skippable tracker state.** Every commit `origin/main` gained since the PR's head left it (`git rev-list <head>..<tip>`; a merge commit judged by its first-parent diff, `diff-tree -m --first-parent`, so its own changes count, design review 001 F3) changes only paths `publish.allowed(path, roots)` accepts (the publisher's definition, read with the registry at main's tip: an item's `<ID>.md`, `check.sh` or an issue's `spend.md` under a registered root, and the id counter), **adds** or **moves** any `check.sh` it touches (a new item's; a move as `ready` and `done` make: **the same item's** `check.sh` deleted and added with the same blob and mode in that commit, read from `diff-tree --raw` and paired by item id, never by blob alone, which a decoy item with the same text would match, design review 002 F3; a **changed or dropped `check.sh` is a no**, design review 001 F4: the stricter reading c0117's `trackerstate` takes, chosen now so the verdict is the same whichever lands first), and touches none of the files the PR changes (`git diff --name-only <merge-base> <head>`).
2. **The would-be merged tree passes the gate stages that read tracker files** (decided with the user, 2026-10-25: "Run those checks first"; design review 001 F1). `git merge-tree --write-tree <head> <tip>` (a conflict is a no), `git commit-tree` of that tree with both parents (one unreferenced commit object in the checkout's store), then **the trial checkout: its own repository in a fresh folder under `$TMPDIR`** (`mktemp -d "$TMPDIR/merge-check.XXXXXX"`, as remap does; design review 002 F1): `git clone --shared --no-checkout <checkout> <folder>` (it borrows the checkout's objects read-only, so the stages that read history see it), `git remote remove origin` (nothing run there can reach the checkout), `git checkout --detach <merged commit>`. It is never a worktree of the merger's checkout and nothing goes under its `.cache`, so the fence of any spec run in that checkout (which watches worktrees registered under `.cache`) never sees it. There every **stage** runs: the `run <home> <spec>` lines of `z-nile/tests/merge-stages.txt` **as the merged tree has it**, each `lune run tests/run -- <spec>` from its home. A listed spec missing from the merged tree is a no (never a skip, lesson zz-test/no-vacuous-pass), and so is a tree without the file or with no `run` line; a trial folder that can't be removed is a no naming it. The folder is removed before the verdict.
   **The stage list (design review 002 F2).** One file, `z-nile/tests/merge-stages.txt`: a `run` line per stage, a `skip` line per search hit that reads no item file a tracker-only commit can change, each with its reason. It came from this search (rerun it; c0152's promoted `stages.spec` holds the pattern and fails when a hit is on neither list):
   ```
   git grep -lE 'real tree|every unfinished|this checkout.s working tree|reads the real|the real checkout|audit\.(run|scan|leftovers)\((TOP|root)|board\.collect\(nil, (TOP|root)\)|lessons\.load\(TOP|cwd = TOP[ ,}]|\{(TOP|root)\}/issues|rewrites\.premove\(TOP|readFile\("\.tracker/' -- 'z-nile/tests/**/*.spec.luau' 'pickman/tests/**/*.spec.luau'
   ```
   36 hits on main 3fdc2856 (the reviewer's phrase search, 22 hits, plus the reads a subagent's second search found: `audit.run/scan/leftovers(TOP)`, `board.collect(nil, root)`, `lessons.load(TOP)`, `cwd = TOP`, done check.sh reads). **Run (15):** c0082/real-tree (it is `./zn audit` in the gate), c0120/check-paths, c0114/classified (unique slugs, kinds per root, every unfinished check.sh lists under `AC_LIST=1`), c0114/finished, c0042/cli, c0043/rounds, c0116/retired, c0115/lessons, c0119/scope-lessons, c0120/finished (every done check.sh), c0120/layout, c0120/old-roots, c0073/board-stats, tooling/board, tooling/repo-fence (every check.sh under every root). **Skip (21)**, each reason in the file: pickman's c0063 and c0103 narrowed (one fixed done item each), f0054 docs and meta/architecture (root documents, not item state: a change to them isn't tracker-only), and z-nile's c0060/fixture, c0081/renamed, c0114 gate-cover/guards/layout/roots-cli, c0115 absence/docs/layout/prompt/readme/trusted-base, c0116 docs/promote, c0120 gate-homes/graph-homes/registry-home (skills, docs, the registry, the compaction map, fixtures, or `zn find` of fixed ids). A spec added later that walks the real tree's items joins the list in the change that adds it, or `stages.spec` fails (lesson zz-rules/exhaustive-lists-name-new-things). The list is read from the merged tree, so a PR that changes it is judged with its own list; main's skippable commits can't touch it (it isn't tracker state).
Also ok: main hasn't moved past the head. **No**, naming each commit (`<short sha> <subject>`) and path, or the failing check, ending "merge origin/main in and run the gate again". Main's tip is read from the remote (`git ls-remote origin refs/heads/main`), never the local tracking ref (lesson zz-review/sequestration-reference-not-a-ref); a tip that isn't a local commit is a no ("git fetch origin"). **Every failed git read is a no** naming the command (design review 001 F5; lesson zz-arch/guard-no-is-explicit). The ok and no outputs both print `merge with --match-head-commit <full head sha>` on ok.

**One definition of tracker state (design review 001 F4).** Today `publish.allowed` plus the "adds only" rule for `check.sh`. c0117 (R0052, in code review) adds `z-nile/engine/trackerstate.luau`, "the one definition … the merge gates all use". If c0117 lands first, c0152's execution takes `trackerstate` instead of `publish.allowed` (its stricter judgement of sequestered files agrees with rule 1's "adds only"); if c0152 lands first, c0117's lead switches `mergecheck` to `trackerstate` in its rebase. Either way the merge-commit, existing-`check.sh` and spec cases keep the same verdicts.

**Where.**

### Scalability
Rule 1 is one `ls-remote`, one `merge-base`, one `rev-list` and one `diff-tree` per new main commit. Rule 2 adds a merge-tree, a shared clone and the listed stages: 136 s on the real repository at load 4–6 (E4; c0120/finished alone is about 100 s), against the 15-minute cycle it saves. Rule 1's refusals come before the trial, so a no on main's commits costs seconds.

### Maintainability
The exception is decided by one command every merger runs (a lead, a stream, later c0117's dispatcher), instead of each lead improvising and recording a deviation (three such on 2026-10-25: #126, #117 and #129's base). Tracker state stays one definition: if the publisher allows a new kind of path, merge-check follows.

### Usability
Each refusal names the commit and the path, and ends "merge origin/main in and run the gate again"; the ok line says how many commits and that none touches the PR.
