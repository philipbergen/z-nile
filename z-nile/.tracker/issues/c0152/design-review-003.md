### F1 [high] The merge isn't pinned to the main tip merge-check judged, and the trial widened that window from seconds to minutes
Where: Design, "The rule (zz-rules Merging step 4)"; prototype zz-rules step 4 ("when it says ok … merge without another cycle with `gh pr merge <pr> --squash --match-head-commit <the sha it prints>`"); `mergecheck.judge` (it reads `ls-remote` once, before the trial)
Evidence: `judge` reads main's tip once (`git ls-remote origin refs/heads/main`), then runs the trial. That took 136 s in E4, at a load of 4–6, and today's load average is 10–14. `--match-head-commit` pins only the PR's head. `gh pr merge --squash` squashes onto whatever `main` is when it runs, and the repository has no branch protection to report `BEHIND` (step 4's own text). Main moves every few minutes: `git log origin/main --since='2026-10-26 07:36' --until='2026-10-26 08:50' --oneline | wc -l` gives 30 commits in 74 minutes. Among them is a code merge (`ea89c0ed R0045: Narrow hiscore adapter pins (#131)`), and yesterday's run includes prep PRs that land sequestered specs (`tracker: prep c0150 … (#128)`). Each of these lands untested whenever it falls inside the 136 s plus the merge. Before c0152, step 4's check ran seconds before the merge. Now the PR merges over commits that neither rule 1 nor the trial judged, which is the "main red after a merge that skipped CI" this item exists to prevent.
Critique: lesson zz-arch/skips-pin-what-they-verified asks "can the commit that gets merged differ from the one the check judged (a push after the check, **another session's push**)". The head is pinned; the base isn't. The tempting fix is a sentence telling the merger to "merge promptly", which leaves the window as it is.
Consequences: GitHub has no flag that pins the base, so the pin has to be a re-read. With main moving about every 2.5 minutes and each check costing about 136 s, a check that has to be rerun whenever main moved can loop much like the cycle it replaces. That outcome needs measuring, not assuming.
Recommendation: (1) merge-check reads origin's tip again after the trial and returns no ("origin's main moved during the check (<old>..<new>): run merge-check again") when it changed. The ok output prints the judged tip (`merge-check: judged main <full sha>`). (2) Step 4 runs `git ls-remote origin refs/heads/main` right before `gh pr merge` and merges only when it prints that sha; otherwise it reruns merge-check. That brings the race back to the seconds the old rule had. (3) Record in Scalability how often a rerun is needed, using the log above. If it doesn't converge (for example, more than half of the checks need a rerun), escalate to the user. Options: (a) accept the remaining seconds-wide race; (b) on a rerun, judge only the newly gained commits with rule 1 and run a fresh trial (same cost); (c) skip the re-trial when the new commits are spend rows only. That narrows "Run those checks first" and is the user's call. Spec case: a fixture stage spec that pushes a spend commit to the fixture's own bare origin (under `.cache`) while the trial runs, which must give a no naming the move. Mutant: "the second tip read dropped". Rules-and-mutants row: "the merge is pinned to the judged tip".
Lesson: zz-arch/skips-pin-what-they-verified

### F2 [high] The shared clone takes the merger's repository out of the trial's guards, while the trial runs main's new check.sh files and the merged code
Where: Design rule 2 ("`git clone --shared --no-checkout` … `git remote remove origin` (nothing run there can reach the checkout)"); prototype `checkout`; lesson zz-arch/throwaway-checkouts-outside-the-repo ("A `git clone --shared` with its origin removed keeps the history")
Evidence: in a scratch shared clone of the prototype (`git clone -q --shared --no-checkout <proto worktree> trial; git -C trial remote remove origin; git -C trial checkout -q --detach da611027`), a probe spec run through `lune run tests/run` from `trial/z-nile` printed:
```
REAL_GIT=…/scratchpad/dr-chores-4/c0152/trial/.git
ALT=/Users/philipbergen/code/pickman/.git/objects
REAL READ ok=true .git          (git -C /Users/philipbergen/code/pickman rev-parse --git-common-dir)
```
The nested runner protects only the clone (`protectedPaths`: the common dir plus `PICKMAN_FENCE_REAL_GIT`). The clone's `objects/info/alternates` names the real object store, so "nothing run there can reach the checkout" is false. On macOS the jail's `(deny file-write* (subpath "/"))` still blocks writes. The environment guards (the reference-transaction hook refuses only repositories listed in `PICKMAN_FENCE_REAL_GIT`) and the tripwire's snapshot now cover only the clone. On Linux, where there is no jail, nothing guards the real repository during the trial. The trial runs code no gate run of the merger's has run: classified executes every unfinished check.sh under `AC_LIST=1`, main's new captures included, and every stage runs the merged tree. In review 002's worktree design the trial's common dir was the real repository, so it was protected automatically. The move to a clone dropped that protection. The repository-safety rubric counts any weakening of the guards as high.
Critique: the tempting fix is to delete the alternates file after cloning, which breaks the clone, or to say "Linux is review's job", which is exactly the case review must catch here.
Consequences: a full copy removes the alternate. It costs `git clone --no-hardlinks --no-checkout`, about 0.3 s and 18 MB here (`count-objects`: 15.8 MiB packed). It copies the whole objects folder, unreferenced loose objects included, so the `commit-tree` merge commit can still be checked out. Probe: `commit-tree` in a scratch source, then `clone --no-hardlinks`, then `checkout --detach <it>`, gave ok, with only `commit-graphs` and `packs` under `objects/info`. With a full copy, the real repository's gc, repack and prune can't affect a running trial either. Under defaults they can't hurt it today anyway (no `gc.*` config, 2-week prune expiry), but a manual `gc --prune=now` could. The env guard is still needed for absolute-path writes on Linux. The runner accepts an inherited list and adds to it: with `PICKMAN_FENCE_REAL_GIT=<scratch src>/.git` set, the probe printed `<src>/.git:<trial>/.git` and passed.
Recommendation: build the trial with `git clone --no-hardlinks --no-checkout` (no alternates). Spawn every stage with `PICKMAN_FENCE_REAL_GIT` set to the merger's common dir plus whatever it inherited, so the hooks guard the merger's repository from inside the trial. Run an experiment: does `fence.snapshot` record refs and config of the repositories in that list? If not, say so in Unknowns, with Linux as the residual risk. Correct the Design's "nothing run there can reach the checkout", and the lesson's How to apply, which now prescribes `--shared`. Spec cases: a fixture stage spec asserts that the trial has no `objects/info/alternates` and that `PICKMAN_FENCE_REAL_GIT` names the fixture checkout's common dir. Mutants: "`--shared` kept" and "env not passed".

### F3 [medium] merge-check runs longer than an agent's default command timeout, and a killed run's trial folder isn't named or cleaned up
Where: Design Scalability (136 s), zz-rules step 4 and the command row; prototype `trial` (it removes the folder only on its normal path)
Evidence: the Bash tool agents run commands with times out by default after 120000 ms. E4 took 136 s at load 4–6. A merger that runs `./zn merge-check <head>` as step 4 says gets the process killed mid-trial. The `$TMPDIR/merge-check.XXXXXX` folder (21 MB for a bare checkout here, more once the stages' fixtures fill its `.cache`) and any nested `tests/run` stay behind. The design's "a trial folder that can't be removed is a no naming it" covers only a failed `removeDir`, not a kill. Review 002 F1 raised the killed-run case for the old worktree. The move to `$TMPDIR` made the leftover harmless to the fence but left it unnamed.
Recommendation: zz-rules step 4 and the table row give the expected time ("about 2–3 minutes; run it with a 10-minute timeout or in the background"). merge-check prints the trial folder before it starts (`merge-check: trial in <folder>`), so a killed run's leftover is named. Spec case: the folder line is printed and the folder is gone afterwards (extend the existing "leaves nothing behind" case).
