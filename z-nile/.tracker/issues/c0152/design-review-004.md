### F1 [medium] "At most three trials" has no case: a check with no cap, or a cap of two, passes every spec, and the outcome after the third trial isn't stated
Where: AC1 ("at most three"); Design rule 3; the Rules and mutants table (no row for the cap); merge-check.spec `moveDuringTrial` (one trigger, one push); prototype `mergecheck.MAX_TRIALS = 3`, `judge`'s loop; zz-rules step 4 and the table row
Evidence: the trigger file holds one sha, and the probe stage removes it after pushing that sha once, so main moves at most once per check. The longest case is "any other tracker move …", which expects exactly 2 trials. Traced by hand (not run: see Inputs):
- `MAX_TRIALS = 2`: after trial 1 the move is not spend-only and `trials (1) >= 2` is false, so trial 2 runs, the tip is unchanged, and the result is ok with 2 trials. The case passes.
- The cap check deleted (an unbounded loop): the same, passes.
- `MAX_TRIALS = 1`: gives no after trial 1, which the case kills.
So AC1's "at most three" can be met by an implementation without a cap. This is medium, not high: under every cap mutant each ok still rests on a trial of the judged tip, or on a notrial-only move judged by rule 1. The verdict stays right; only how long the check runs and whether it stops change. The design text also leaves two things open. "At most three trials, then no" doesn't say that a spend-only move after the third trial is ok, which is what the code does. And the "kept moving" no tells the merger to "run merge-check again", while step 4 says a no falls back to the old rule.
Recommendation: let the trigger hold a list of shas, with the probe pushing the next one on each trial. Add two cases:
- (a) three non-spend tracker moves: exit 1, "kept moving (3 trials)", and `trials(stdout) == 3`. This kills a cap of 2, a cap of 4 and an unbounded loop. Prepare at most 4 shas, so an unbounded mutant still stops.
- (b) two non-spend moves, then a spend-only move after trial 3: ok, 3 trials, `judged main <the last sha>`. This pins the 4th-move outcome.
Add the Rules row "at most three trials; a spend-only move after the third is ok, any other is no", with the mutants "cap 2", "no cap" and "no after the third whatever the move". State both outcomes in rule 3, AC1 and zz-rules. Also say in zz-rules what the merger does after "kept moving": run merge-check again, or fall back to the old rule, but one of them.
Lesson: zz-test/seed-every-enumerated-case

### F2 [low] A spend-only move can create an orphan item folder that no trial sees
Where: Design rule 3 (the notrial skip); prototype `judge` (`matchesAny(p, notrial)`)
Evidence: path (ii) above. `./zn audit` in the scratch clone reports `no-document` for a folder holding only `spend.md`. The PR never names `<old folder>/spend.md`, so rule 1's overlap test can't catch it. It needs a PR that moves or renumbers an item with no `spend.md` at its base (a compaction, or a move of an item no prep has spent on), plus that item's first spend row landing during the trial. That is rare, but it is a wrong ok, and main goes red.
Recommendation: count a notrial path as notrial only when its item's document is still at the same folder in the would-be merged tree (`git cat-file -e <head>:<folder>/<id>.md` when the PR changed that folder, else the tip's). Otherwise run the trial again. This doesn't narrow the user's decision: it only refuses the skip where the row isn't a row of a live item. Spec case: the PR moves a fixture item that has no `spend.md` into `done/`, and the probe pushes a first `spend.md` at its old path. Expect a second trial, and a no from audit. Mutant: "notrial by glob alone".

### F3 [low] "About 2–3 minutes … a 10-minute timeout" is below the design's own measurement under the usual load
Where: zz-rules step 4 and the merge-check row; Design rule text; E5b
Evidence: E5b's single trial on the real tree took 599 s at load 50. E5's fixture spec took 658 s at load 52. Load averages of 10–50 are what this machine sees during agent runs (`uptime` while reviewing: 11.6, 18.4, 29.2). Rule 3 allows up to three trials. A merger that follows "a 10-minute timeout" gets killed at load 50 even with one trial. The check fails safe (a killed run merges nothing, and its folder is named), but the merger loses the run and the merge.
Recommendation: say "about 2–3 minutes idle and 10 or more under load, up to three trials: run it in the background (or with no timeout) and wait for its verdict line", and update docs.spec's pinned phrase to match.
