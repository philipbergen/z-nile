## Design
**What the measurements say (prep, 2026-10-25, 18 CPUs, scratch clones of main at a0ac545e).** The 520 s gate the capture records ran while about six other gates ran on the same machine (load average 13 to 24). The two specs are slow mostly because of that contention, and the gate is long because of how the runner schedules them:
- In isolation at load 4 to 9: claims.spec 83 s wall (71 s of CPU), finished.spec 80 s; the full gate 216 s; z-nile's tests stage 214 s. At load 13 to 24 the same two specs took 383 s and 307 to 371 s: each `./zn` call in claims.spec averaged 2.0 s (122 calls, 246 s) where it takes 0.3 s on an idle fixture, and each AC18 judge in finished.spec 3.6 s (78 runs, 283 s) where it takes 0.85 s.
- Where the time goes in each: claims.spec's 21 cases share one fixture and run 122 `./zn` commands (publishing ones make about 80 git calls each); finished.spec's two AC18 cases run its judge (`finished.luau`, 58 `git show` and ~30 other git calls per run) 78 times. Neither has a cheap shared-fixture win: the claims cases build on each other's state, and the judge reads a different tree each time by design.
- The runner takes spec files in path order on `min(max(cpus, 2), 8)` lanes. With the 177 per-file times of one run (the fixture `durations.luau`), path order ends at 213.5 s (measured 214.5 s) because claims.spec (121 s) and finished.spec (111 s) start a third of the way through; slowest first ends at 162.6 s, which is the floor for 8 lanes (1300 s of work / 8), so after it a faster claims.spec would not shorten the gate at all.
- Splitting either file was considered and is not taken: c0116's and c0120's finished `check.sh` files run them by name (`"$A/claims.spec.luau"`, `"$A/finished.spec.luau"`), so a split would narrow two finished criteria (a change only the user can make, zz-test), and it would not lower the floor above.

**The change: the runner schedules slowest first** (no spec, fixture or assertion changes; the lane count stays `min(max(cpus, 2), 8)`).
1. `z-nile/tests/lib/schedule.luau` (new, pure, no I/O):
   - `schedule.order(files: {string}, durations: Durations): {string}`: files with no recorded duration first (a new spec may be slow), then the recorded ones slowest first, ties by path; `files` itself is not changed. With no record it is path order, as today.
   - `schedule.parse(text): Durations?` (lines `<seconds>\t<path>`; any malformed line makes the whole record nil), `schedule.render(old, runs): string` (merged, sorted by path), `schedule.makespan(files, durations, lanes): number` (the wall time lanes take in that order).
2. `z-nile/tests/run.luau`:
   - The concurrent coordinator takes files in `schedule.order(files, recorded())` order; outcomes stay indexed by path order, so every printed line, the counts and the exit code are as today.
   - After a concurrent run it merges this run's per-file seconds into `.cache/spec-durations.tsv` in the home (gitignored; the runner already writes `.cache`), only for files under `tests/` (a spec that runs a fixture's spec files through the runner names `.cache/…` paths, which are not the home's). A failed write is ignored: it only costs the order. An in-process run (`--jobs 1`, one file) neither reads nor writes the record and runs in path order, as today.
3. CI starts with no record, so its order stays path order (a fresh checkout); persisting the record in CI is a guess (G2).

**Load-sized lanes were tried and dropped.** The prototype first sized the lanes by the load average (`max(2, min(8, floor(cpus − load)))`), so that several gates on one machine would stop oversubscribing it. Measured on the prototype at load 15.5: the gate took 2 lanes and 493 s (1300 s of z-nile spec work on 2 lanes), against 345 s in path order on 8 lanes at a lower load. The one-minute load counts other sessions' gates and lags, so a gate that sizes itself by it starves itself. Contention between concurrent gates is the machine's to manage (G3), not each runner's.

### Scalability
The record is one line per spec file of the home (177 for z-nile, ~206 for pickman); read once and written once per run. `schedule.order` is a sort, `makespan` O(files × lanes). A new spec file runs first until it has a time, so it can't be stuck at the end.

### Maintainability
One pure module holds the policy and is tested on fixed inputs; the runner only gathers inputs (files, record) and acts. The record format is plain text, sorted, one rule (`parse` refuses it whole) for a bad file.

### Usability
Nothing changes in how the gate is run or read. `PICKMAN_JOBS`/`--jobs` keep overriding. Deleting `.cache/spec-durations.tsv` returns to path order.

## Unknowns & experiments
- **E1. Where the time goes.** Profiled per case and per subprocess (prep, scratch clones): claims.spec 21 cases, 122 `./zn` calls 246 s at high load, 83 s whole spec at load 4.6; finished.spec judge 78 runs 283 s at high load, 68 s at load 6.7; git inside the judge 4553 calls. **Result:** contention and path-order scheduling, not a single slow operation.
- **E2. Slowest first on real durations.** 177 recorded file times: path order 213.5 s simulated (214.5 s measured), slowest first 162.6 s on 8 lanes (−24%). Pinned by schedule.spec's "cuts a real run's wall time" case (≥ 20%).
- **E3. Prototype run.** The prototype runner, second run with the record, at load 10 to 15: z-nile tests 185.6 s (path order at the lighter load 6 to 9: 214.5 s). The two failures in that run were the new spec's own (a fixture name shared with c0060, a multi-return in t.expect), fixed; the full gate on the prototype, path order then with the record, is in the Verification log.
- **E4. Does a nested runner pollute the record?** Yes, found on the first prototype run: c0470's runner spec runs fixture specs from this home and their `.cache/…` paths were recorded (198 lines for 177 files). Fixed (record only `tests/`), pinned by schedule.spec.

## Regression guard
- Every spec's assertions and fixtures are unchanged; only the order files start in and the default lane count change. Specs that assumed concurrency or order between files would show up in the prototype's full run (E3).
- The runner's other rules stay pinned by their promoted specs: c0120's runner-home (home, aliases, ceiling), c0049's isolation scan, c0470's runner spec (files, `--jobs`, in-process path) — all must stay green unchanged.
Overrides: none

## Test plan
- `schedule.spec` :: orders unrecorded files first, then recorded ones slowest first, ties by path → AC1
- `schedule.spec` :: reads and writes the record, and refuses a malformed one whole → AC2
- `schedule.spec` :: cuts a real run's wall time on 8 lanes by at least a fifth → AC3
- `schedule.spec` :: the runner starts the slowest recorded file first, records every run, and reports in path order → AC4
- `schedule.spec` :: a malformed record runs in path order and is replaced by a good one → AC2, AC5
- `schedule.spec` :: reports in path order whatever order the files ran and finished in → AC4
- the full gate per project, unchanged specs → AC5

### Rules and mutants
| rule | spec :: case | mutant it kills | checked |
|---|---|---|---|
| unrecorded files start first | schedule :: orders…; the runner starts… | unrecorded last (M1) | run: killed (2 cases) |
| recorded files slowest first | schedule :: orders…; cuts a real run…; the runner starts… | path order kept (M2); fastest first (M3); the runner ignores the order (M13) | run: all killed |
| ties by path | schedule :: orders… (b, d at 5) | ties by insertion order (M4) | reasoned: table.sort is unstable, so a dropped tie-break passes or fails by chance |
| a malformed record is no record | schedule :: reads and writes…; a malformed record… | skip bad lines (M9) | run: killed |
| the record merges, never drops | schedule :: reads and writes… | render writes only this run (M10) | run: killed |
| report in path order | schedule :: reports in path order… | outcomes in finish order (M11) | run: killed (added after the first mutation run, where it survived) |
| only the home's tests/ recorded | schedule :: the runner starts… (fixture x) | every file recorded (M12) | run: killed |

## Acceptance criteria

### Checked
- AC1: the runner takes unrecorded spec files first, then recorded ones slowest first, ties by path.

- AC4: the runner itself starts the slowest recorded file first, records only the home's tests/ files, and reports in path order with unchanged counts and exit code.
- AC5: no promoted spec changes (the full gate per project is the raft's RC0).
