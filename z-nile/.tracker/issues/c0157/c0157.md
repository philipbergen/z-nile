# c0157: Gate contention and tripwire

## Problem
Decided with the user (2026-10-25), from c0154's G3 ("Accept all (Recommended)"): capture a separate chore to limit concurrent gates machine-wide, covering today's second cause too.

Two problems hit every session's gate when several sessions work on one machine at once (seen all day on 2026-10-25, up to ~6 streams plus other sessions):
- **Contention.** Each gate runs its spec files on up to 8 lanes, whatever else is running. With several gates at once the machine is oversubscribed (load average 13 to 26 on 18 CPUs): the full gate took 520 s instead of ~216 s, and single specs 3 to 5 times longer (c0154's measurements: claims.spec 383 s against 83 s, finished.spec 307–371 s against 80 s). Sizing one runner's lanes by the load average does not help: measured in c0154's prep, a gate at load 15.5 took 2 lanes and 493 s.
- **The tripwire fires on another session's refs.** The runner fails any run during which the repository's remotes, config, branch or history changed (AGENTS.md). Other sessions creating refs in the real repository while a gate runs (prototype branches, seen twice today: `proto-wall-picks-base2`, `proto-wall-picks-base3`) trip the running gate's tripwire, so an innocent gate fails and must be rerun.

What should happen:
- **A machine-wide gate slot:** concurrent gates on one machine share the CPUs instead of each taking 8 lanes: e.g. a shared lock or slot count (per user, outside any one checkout) that queues a gate beyond the limit, or divides the lanes among the running gates, so N gates take about as long together as they would one after another, and a lone gate is never slowed.
- **The tripwire tells a spec's ref change from another session's:** a ref another session creates (in the real repository, by its own work) no longer fails a running gate, while a ref or history change made by a spec still does; or sessions create prototype refs only in scratch clones, never in the real repository, and the skills say so.

## Non-goals
- The per-run spec order: c0154 (slowest first).
- Making individual specs faster.
- When a PR may merge after `main` moved (the land/merge race): c0152.
- Why the jail's sweeper is killed (signal 9): c0132.

## Solution
- Slot: a flock-based semaphore under a per-user state folder (`$XDG_STATE_HOME` or `~/.local/state/zn/gate-slots`), taken by `z-nile/check.sh` (and `./zn land`/`done`'s gates) before the test stage, with a message while waiting; or lanes divided by the number of gates holding slots.
- Tripwire: compare against a baseline that ignores refs outside the run's own namespace (e.g. only `HEAD`, the current branch, `main`, the remotes and config count), or record which process made a change; and a z-design / zz-execute rule that prototypes live in scratch clones (`$TMPDIR`, the scratchpad), as several preps already do.
- Find whether the jail or the fence already distinguishes the run's own git activity (`GIT_DIR` fencing into `.cache`) and build on it.
## Design
**What the measurements and the record say (prep, 2026-10-26).**
- Contention: c0154's measurements (in the Problem) and today's loads of 60 to 800 on 18 CPUs with up to about ten gates at once: timing-sensitive specs flaked (f0013's bench, c0117's stall cases, c0077's broken pipe, c0080's clone failures) and gates took 10 to 28 minutes.
- The tripwire: it flags a ref only when its tip's author is a fixture identity (`fence.luau`, `FIXTURE_EMAIL = "@example.invalid"`), so another session's ordinary branch never trips it. The trips recorded on 2026-10-25 (f0109's E5: `refs/heads/proto-wall-picks-base2` at f0cac9ba) were another session's prototype commits **authored `proto <proto@example.invalid>`** in the real repository (`git log --all --author=example.invalid`: f0126's prep rounds 7 to 9, `proto-wall-picks-base*`), made in "scratch worktrees" of the real repository, which z-design's mutation check told it to use. To the tripwire such a commit is exactly a spec's escape: same identity, same repository, during the run. On macOS the jail refuses every write to the real `.git` during a spec run, so there it can only come from outside the run; on Linux (CI, unjailed) the tripwire is the guard that catches a spec's escape, and it cannot tell who wrote a commit.

**Part 1: machine-wide gate slots.** `z-nile/check.sh` runs each project's spec stage while holding one of K slots shared by every checkout of this user on this machine. K = `max(1, floor(cpus / 8))`, 8 being the runner's lane cap (`min(max(cpus, 2), 8)`), so the running gates' lanes never exceed the CPUs: 2 on this 18-CPU machine, 1 on CI's 4. A lone gate takes a slot at once and runs exactly as before; a gate beyond K waits, saying who holds the slots, and starts when one is given back. N gates then take about as long together as one after another (K at a time, each at full speed), instead of each slowing all.
- `z-nile/tests/lib/gateslot.luau` (new): `LANES = 8`; `slotsFor(cpus, lanes): number`; `dir(env): string?` (`ZN_GATE_SLOTS`, else `$XDG_STATE_HOME/zn/gate-slots`, else `$HOME/.local/state/zn/gate-slots`); `parseOwner(text)`; `try(dir, max, me, myId, label, probe, unownedSeconds): (string?, {string})`: a slot is a folder `slot-<n>` taken by `mkdir` (atomic), with `owner` "<pid> <start id> <label>"; a slot whose owner is gone or a reused pid (start id differs, `fence.holds`), or whose owner file is still unwritten after 5 s, is removed and retaken; `release(slot, me)` removes it only if this process owns it.
- `z-nile/tests/slot.luau` (new, a script): `lune run z-nile/tests/slot.luau -- acquire <pid>` waits for a free slot and records `<pid>` (with its start id) as its holder; `release <pid>` gives back the slot that pid holds (only that pid's). It takes no slot inside a guarded test run (`PICKMAN_TEST_FENCE` set and no `ZN_GATE_SLOTS`): a gate a spec runs in a fixture already runs inside its outer gate's slot, and the jail refuses the state folder. `ZN_GATE_SLOTS_MAX` overrides K (0: no slot). `ZN_GATE_SLOT_WAIT` bounds the wait in seconds: past it `acquire` returns without a slot and says `no gate slot after Ns; running without one`.
- `z-nile/check.sh`: `run_specs` runs `lune run "$slot" -- acquire $$` before each project's `lune run tests/run` and `release $$` after it, and an `EXIT` trap releases too (`slot="$PWD/z-nile/tests/slot.luau"`, the repository root). The holder is the gate's own shell, so a gate killed mid-stage leaves a slot whose holder is gone, which the next waiter takes. The spec command itself is unchanged, so c0120's gate-homes spec (it stubs `lune` and asserts `<home>|lune|run tests/run --`) stays as it is. Every gate goes through it: `./zn land`, `done`, `check` and the raft checks run `check.sh`.
- `scripts/hooks/stop.sh`: `ZN_GATE_SLOT_WAIT=120 scripts/check.sh --affected`, so the Stop hook (300 s budget) never times out queued behind full gates.
- `z-nile/tests/lib/fence.luau`: `fence.myPid` exported (the slot's owner pid).

**Part 2: another session's prototype refs** (the capture's second branch: "sessions create prototype refs only in scratch clones, never in the real repository, and the skills say so"; G1).
- One rule, in the same words in z-design (a new "Where a prototype lives" bullet before the mutation check, which now says "scratch clone"), zz-execute (Phase 1) and zz-test ("Other sessions' refs", before "If the tripwire fires"): "Prototypes and experiments live in a scratch clone (`git clone` of the checkout into the scratchpad or `$TMPDIR`), never in a branch or worktree of the real repository, and nothing is ever committed in the real repository under a fixture identity (`@example.invalid`): every gate running on the machine reads such a ref as a spec's escape and fails (c0157)."
- The tripwire keeps failing such a run (it is the Linux guard), but its message now names each appeared ref with its tip's author, date and subject, and the likely cause: `refs/heads/proto-base2 <sha> (proto <proto@example.invalid>, <date>: proto f0126 round 8 (scratch))` and "(a session that commits under an @example.invalid identity in the real repository, such as a prototype branch, trips this too: prototypes belong in scratch clones, z-design skill)". So the victim knows at once it was another session's prototype, not its own specs. `fence.snapshot` and `fence.changes` are exported for the spec.

**Overlaps.** c0154 (done) orders spec files within a run; c0157 only decides when a gate's run starts: they compose. c0132 (in design) changes the sweeper inside `tests/run`/`fence`; c0157 touches `fence.luau` only to export `myPid`, `snapshot`, `changes` and to extend the fixture-refs message: whichever lands second merges those lines. c0152 (in flight) is the merge rule; queued gates make a gate's wall time longer for the queued one, which c0152's tracker-only rule absorbs (the land race is not c0157's).

### Scalability
One `mkdir` per slot per second while waiting, one `perl` start-id probe per held slot per second; K folders in all. A lone gate's overhead is one Lune start and one `mkdir`.

### Maintainability
The slot policy is one module tested on fixed inputs and through the wrapper; the wrapper is the only taker; `check.sh` is the only caller. The rule of Part 2 is one sentence repeated verbatim and pinned in all three skills.

### Usability
A queued gate prints one line naming the holders (pid and checkout) and the folder. `ZN_GATE_SLOTS_MAX=0` turns slots off for one run.

## Guesses (pending user)
1. **G1** (pending user): the tripwire outcome is met by the capture's second branch (skills keep prototypes in scratch clones and fixture identities out of the real repository; the message names the ref's author and the cause), not by the tripwire ignoring other sessions' refs. Recommended: accept. The alternative, ignoring fixture-authored refs on a jailed macOS run (the jail already refuses a spec's writes there), weakens the guard where something outside the jail (a daemon a spec talks to) could still write, and changes nothing on Linux; it needs your decision.
2. **G2** (pending user): K = floor(cpus / 8), at least 1 (2 here). Recommended: accept; the alternative, K = 1, makes every second gate wait even when the CPUs would hold two.
3. **G3** (pending user): the Stop hook waits at most 120 s for a slot, then runs its affected specs without one. Recommended: accept; the alternatives are to fail the hook after 120 s, or to exempt the hook from slots.
