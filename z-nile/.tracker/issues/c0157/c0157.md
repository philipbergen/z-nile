# c0157: Gate contention and tripwire

## Problem
Decided with the user (2026-10-25), from c0154's G3 ("Accept all (Recommended)"): capture a separate chore to limit concurrent gates machine-wide, covering today's second cause too.

Two problems hit every session's gate when several sessions work on one machine at once (seen all day on 2026-10-25, up to ~6 streams plus other sessions):
- **Contention.** Each gate runs its spec files on up to 8 lanes, whatever else is running. With several gates at once the machine is oversubscribed (load average 13 to 26 on 18 CPUs): the full gate took 520 s instead of ~216 s, and single specs 3 to 5 times longer (c0154's measurements: claims.spec 383 s against 83 s, finished.spec 307–371 s against 80 s). Sizing one runner's lanes by the load average does not help: measured in c0154's prep, a gate at load 15.5 took 2 lanes and 493 s.
- **The tripwire fires on another session's refs.** The runner fails any run during which the repository's remotes, config, branch or history changed (AGENTS.md). Other sessions creating refs in the real repository while a gate runs (prototype branches, seen twice today: `proto-wall-picks-base2`, `proto-wall-picks-base3`) trip the running gate's tripwire, so an innocent gate fails and must be rerun.

What should happen:
- **A machine-wide gate slot:** concurrent gates on one machine share the CPUs instead of each taking 8 lanes: e.g. a shared lock or slot count (per user, outside any one checkout) that queues a gate beyond the limit, or divides the lanes among the running gates, so N gates take about as long together as they would one after another, and a lone gate is never slowed.
- **The tripwire tells a spec's ref change from another session's:** a ref another session creates (in the real repository, by its own work) no longer fails a running gate, while a ref or history change made by a spec still does; or sessions create prototype refs only in scratch clones, never in the real repository, and the skills say so.

## Non-goals
- The per-run spec order: c0154 (slowest first).
- Making individual specs faster.

## Solution
- Slot: a flock-based semaphore under a per-user state folder (`$XDG_STATE_HOME` or `~/.local/state/zn/gate-slots`), taken by `z-nile/check.sh` (and `./zn land`/`done`'s gates) before the test stage, with a message while waiting; or lanes divided by the number of gates holding slots.
- Tripwire: compare against a baseline that ignores refs outside the run's own namespace (e.g. only `HEAD`, the current branch, `main`, the remotes and config count), or record which process made a change; and a z-design / zz-execute rule that prototypes live in scratch clones (`$TMPDIR`, the scratchpad), as several preps already do.
- Find whether the jail or the fence already distinguishes the run's own git activity (`GIT_DIR` fencing into `.cache`) and build on it.
