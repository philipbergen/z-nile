# c0160: Check paths third project

## Problem
c0120's check-paths validation (landed by R0048, PR #107), `z-nile/tests/acceptance/c0120/check-paths.spec.luau`, only ever exercises the two project homes that exist today, z-nile and pickman. Nothing proves it works for a third project, such as a hypothetical `game2/` home registered in `z-nile/projects.toml`, so a path rule that hard-codes the two known homes passes unnoticed. Concretely:

- The fixture's `REGISTRY` (the "in a fixture, each check.sh is read from its home" case) registers only `pickman` and `z-nile`, and its expectations (`s.byHome` equal to `{ pickman = 2, ["z-nile"] = 1 }`, the two `bad` lines) only cover those two. `items` (through `projects.roots`) and `scan` (through `projects.homeOf`) are never run on a third root, so a regression that only walks or resolves the known roots would stay green.
- `literals` decides what is a literal path through `PREFIXES`, which names `z-nile/` and `pickman/` by hand (the same list is copied in `z-nile/tests/acceptance/c0120/rewrites.luau`, which `finished.spec.luau` and `override-markers.luau` use). A check.sh that names `game2/src/gone.luau` from the repository root (after `cd ..`, or through a path relative to the checkout) is not read as a path at all, so a vanished path under a third home is never reported.
- The live case (`scan(TOP)`) only sees the two real roots, so it cannot catch either gap.

Who is affected: whoever adds a third project to the repository. Its check.sh files would be checked only by accident, and a check guarding a path that moved away would pass (the very failure c0120 AC11 exists to stop).

What should happen: specs with a third fixture project (built under `.cache/` only, never in the real repository) prove that check-paths finds a third project's unfinished items, resolves each check.sh's paths from that project's own home exactly as it does for z-nile and pickman, reports a vanished path there as `<file>: <path> (from <home>)`, honours its Touched exemption, and counts it in `byHome`; and that a literal path under the third project's home is recognised as a path from every home, with no top-level folder list that names the two current homes by hand (a home taken from the registry instead).

## Non-goals
<!-- Explicit scope fences. Anything tempting that belongs to another issue. -->
- Adding a real third project to the repository (registry, CI matrix, required check): only a fixture under `.cache/`.
- Resolving paths after a literal `cd ..` against Touched entries: that is c0141.

## Solution
<!-- The approach in one paragraph. -->
- Extend the fixture registry (or add a case) with a third project, e.g. `name = "game2"`, `root = "game2/.tracker"`, home `game2/`, with backlog and active items whose check.sh name a present path, a glob, a Touched path and a vanished one; expect the same report and `byHome` entry as the other two homes.
- Derive the home prefixes in `PREFIXES` (check-paths and `rewrites.luau`) from the registry's homes rather than listing `z-nile/` and `pickman/`, and prove a `game2/...` path is read as a literal.
- A promoted-spec change: a chore that overrides c0120/check-paths (and rewrites.luau if touched), with its own `Overrides:` line.
