# c0160: Check paths third project

## Problem
c0120's check-paths validation (landed by R0048, PR #107), `z-nile/tests/acceptance/c0120/check-paths.spec.luau`, only ever exercises the two project homes that exist today, z-nile and pickman. Nothing proves it works for a third project, such as a hypothetical `game2/` home registered in `z-nile/projects.toml`, so a path rule that hard-codes the two known homes passes unnoticed. Concretely:

- The fixture's `REGISTRY` (the "in a fixture, each check.sh is read from its home" case) registers only `pickman` and `z-nile`, and its expectations (`s.byHome` equal to `{ pickman = 2, ["z-nile"] = 1 }`, the two `bad` lines) only cover those two. `items` (through `projects.roots`) and `scan` (through `projects.homeOf`) are never run on a third root, so a regression that only walks or resolves the known roots would stay green.
- `literals` decides what is a literal path through `PREFIXES`, which names `z-nile/` and `pickman/` by hand (the same list is copied in `z-nile/tests/acceptance/c0120/rewrites.luau`, which `finished.spec.luau` and `override-markers.luau` use). A check.sh that names `game2/src/gone.luau` from the repository root (after `cd ..`, or through a path relative to the checkout) is not read as a path at all, so a vanished path under a third home is never reported.
- The live case (`scan(TOP)`) only sees the two real roots, so it cannot catch either gap.

Who is affected: whoever adds a third project to the repository. Its check.sh files would be checked only by accident, and a check guarding a path that moved away would pass (the very failure c0120 AC11 exists to stop).

What should happen: specs with a third fixture project (built under `.cache/` only, never in the real repository) prove that check-paths finds a third project's unfinished items, resolves each check.sh's paths from that project's own home exactly as it does for z-nile and pickman, reports a vanished path there as `<file>: <path> (from <home>)`, honours its Touched exemption, and counts it in `byHome`; and that a literal path under the third project's home is recognised as a path from every home, with no top-level folder list that names the two current homes by hand (a home taken from the registry instead).

## Non-goals
- c0141's rule (the Touched exemption read in one convention per document): c0160 builds on it and changes nothing in it.
- The hand list of root **file** names (`FILES`: `default.project.json`, `zn`, `AGENTS.md`, …) and of bare folders (`FOLDERS`): they are file and folder names, not homes; a third project with root files of its own adds them when it exists (G2).
- The engine's own readers of Touched entries (`spend.ownedPaths`, raft-plan's overlap), as c0141 leaves them.
- Adding a real third project to the repository (registry, CI matrix, required check): only a fixture under `.cache/` (the capture's).
- Resolving paths after a literal `cd ..` against Touched entries: that is c0141 (the capture's).

## Solution
The literal-path readers of c0120's check-paths scan (c0141's `checkpaths.luau`) and of its finished-file rewrite (`rewrites.luau`) stop naming `z-nile/` and `pickman/` by hand: a word that starts with any registered project's home is a literal path, the homes read from a registry: the check-paths scan takes the scanned checkout's, and a reader called without homes (as `rewrites.rewrite` calls its reader) takes the registry of the checkout it runs in, which for every caller today registers the same two homes (design review 002 F2). A new spec builds a fixture checkout under `.cache/c0160-third` that registers a third project, `tern`, and proves the scan reads its check.sh files, backlog and active, from its own home (a present path, a vanished one, a glob that matches and one that doesn't), reads `tern/…` paths named from another home, and exempts its own Touched work, as it does for pickman and z-nile.

## Design
**Where the hand lists are (2026-10-26, main at c29d793a plus c0141's prototype).** Two literal-path readers decide which words of a check.sh are paths by a list of top-level prefixes that names the two homes by hand: `{ "src/", "tests/", "scripts/", "z-nile/", "pickman/", "tracker/", ".tracker/", ".github/", ".claude/" }`.
- `z-nile/tests/acceptance/c0120/check-paths.spec.luau:32` today; c0141 moves it unchanged into `z-nile/tests/acceptance/c0120/checkpaths.luau` (its prototype, `proto-check-paths-home`). The scan already takes each item's home and the Touched convention's homes from the registry (`projects.homeOf`, c0141's `homes`), so only this list is hand-written.
- `z-nile/tests/acceptance/c0120/rewrites.luau:20` (`rewrites.literals`), used by `rewrites.rewrite` (the move's rewrite, judged by `finished.luau`) and by finished.spec's live case over every finished check.sh.
So a third project's check.sh is read from its home already (its `src/…` paths are read), but a `tern/…` path is no literal path to either reader: a check that names `tern/src/x` from the top after `cd ..`, or a Touched `tern/…` entry's own work named that way, is never checked. No spec registers a third project.

**The rule (c0160).** A word is a literal path when it starts with one of the fixed top-level folders (`src/`, `tests/`, `scripts/`, `tracker/`, `.tracker/`, `.github/`, `.claude/`) **or with `<home>/` for a home of the registry**: the registry of the checkout being scanned, or, when a reader is called without homes, of the checkout the module runs in (`git rev-parse --show-toplevel`, read once per process). `<home>/` includes the slash: `ternary/x` is no `tern` path. Everything else in both readers is unchanged (the `FILES` and `FOLDERS` lists, quoting, `cd`, globs, the report's wording).

**Changes** (both files in c0120's promoted folder, so through this chore's `Overrides:` line):
1. `z-nile/tests/acceptance/c0120/checkpaths.luau` (c0141's module):
   - `PREFIXES` becomes `FOLDER_PREFIXES` (the seven fixed folders); `homesAt(top): {string}` (every root's `projects.folderOf`, the code c0141 writes inline in `scan`, moved out) and `checkoutHomes()` (the running checkout's, cached).
   - `checkpaths.literals(text: string, homes: {string}?): {string}`: the prefixes are `FOLDER_PREFIXES` plus `<h>/` for each of `homes or checkoutHomes()`. Existing calls with one argument (check-paths.spec's literal case) read the checkout's registry: pickman and z-nile, as now.
   - `scan(base, skip)`: `local homes = homesAt(<base>)` (replacing c0141's inline loop) and `literals(text, homes)`, so a fixture's registry decides its homes.
2. `z-nile/tests/acceptance/c0120/rewrites.luau`: the same `FOLDER_PREFIXES` and cached `checkoutHomes()`; `rewrites.literals(text: string, homes: {string}?): {Literal}` with the same default. `rewrites.rewrite` keeps calling it with one argument, so it reads the homes of the checkout it runs in, not of the checkout its `world` reads (finished.spec's fixtures included); a one-line comment at that call says so (design review 002 F2). Every caller (finished.luau on its fixtures and the real checkout, finished.spec's cases and its live scan) runs from z-nile/ in a checkout that registers pickman and z-nile, so each reads exactly the homes it reads today; finished.spec's fixtures register the same two.
3. New spec `z-nile/tests/acceptance/c0160/third-project.spec.luau` (sequestered until done): a fixture checkout under `.cache/c0160-third/` whose registry has pickman, z-nile and `tern` (`tern/.tracker`), exercised through `checkpaths.scan` and both readers.
No engine code, no other spec, no skill changes.

**Why depends_on c0141.** c0160 edits `checkpaths.luau`, which c0141 creates (the prototype is built on c0141's prototype applied to main), and its spec calls `checkpaths.scan`. c0141 is prepared, not yet rafted; c0160 lands in a raft after c0141's is done (z-ready refuses otherwise). Its check.sh names no `checkpaths.luau` path literally (c0141's AC3 note: main's unfixed scan would read it from z-nile/ and not match a repository-relative Touched entry, turning every gate red while c0160 waits in the backlog).

### Scalability
One `git rev-parse` and one registry read per process for the default, and one registry read per scan (c0141 already reads it). The prefix list grows by one entry per project.

### Maintainability
The homes are the registry's in both readers; adding a project needs no edit to either. The two readers stay two (as c0120 left them, "the same reading"); merging them is not this chore's.

### Usability
No output changes: the report line is still `<check.sh>: <path as written> (from <home>)`.
