# c0162: Spec runner checks its Lune version

## Problem
Who is affected: anyone who runs specs, single specs or mutants by typing `lune run tests/run …` directly, as the skills show (`z-nile/skills/zz-test/SKILL.md` lines 15 and 18, the check.sh example at 51–52, `pickman/skills/pickman-test/SKILL.md`, `SETUP.md` line 42) and as executors, reviewers and preps do for single specs and mutant scripts (for example c0153's `experiments/mutants.py`).

What happens now: the commands that go through z-nile already put rokit's tools first: `zn` line 14, `z-nile/check.sh` line 11 and `z-nile/lib/ac.sh` line 70 each `export PATH="$HOME/.rokit/bin:$PATH"` (since 05b058ea), so `./zn`, the gate and `check.sh` files run the Lune that `rokit.toml` pins (`lune-org/lune@0.10.5`). But a direct `lune run tests/run …` runs whatever `lune` is first on the shell's PATH. On this machine that is Homebrew's `/opt/homebrew/bin/lune`, 0.11.1. The runner never checks or names its version: `z-nile/tests/run.luau` re-runs itself with `process.exec("lune", …)` (line 98) on the inherited PATH, and its output prints no Lune version. (Even rokit's shim, `~/.rokit/bin/lune`, resolves the pin only under a folder with a `rokit.toml`: run from `/` it printed 0.11.1 here.) Found 2026-10-26 by a stream whose local spec and mutant runs used 0.11.1. Some specs' results depend on the Lune version: c0153's eps-0 round-trip subcase depends on 0.10.5's JSON decoder losing one ulp. CI runs the pinned version, so a local result can disagree with CI's, silently.

What should happen:
- The spec runner (`z-nile/tests/run.luau`, which each home's `tests/run.luau` requires) compares the Lune it runs on with the version `rokit.toml` pins, and fails closed (or at the least warns loudly) when they differ, with a message that says how to run the pinned one (`PATH="$HOME/.rokit/bin:$PATH"`, or `./zn`).
- The runner prints the Lune version it ran on in its output, so every run's record names it.
- Optionally, the skills and docs that show a bare `lune run tests/run` (zz-test, pickman-test, SETUP.md) tell readers to run it through the pinned path.

## Non-goals
- Changing `zn`, `z-nile/check.sh` or `z-nile/lib/ac.sh`: they already put rokit's bin first.
- Upgrading the pinned Lune, or changing which version `rokit.toml` pins.
- Changing c0153's eps-0 subcase (c0153 owns it).

## Solution
- At the runner's start, read `rokit.toml`'s `lune` entry (found from the runner's own repository, not the current folder) and compare it with the running Lune's version; refuse to run on a mismatch, naming both versions and the fix.
- Print `lune <version>` in the runner's header or summary line.
- The skills' examples use the pinned path, or say the runner refuses an unpinned Lune.

## Design
The spec runner checks which Lune it runs on before it runs anything, against the version `rokit.toml` pins, and names it in its output. A pure module reads and judges; the runner does the reads.

### 1. `z-nile/tests/lib/lunepin.luau` (new, pure; the one reader of `rokit.toml`'s lune pin)
```luau
lunepin.FIX: string -- 'run the pinned Lune: PATH="$HOME/.rokit/bin:$PATH" lune run tests/run …, or ./zn and the gate, which do'
function lunepin.pinned(text: string): (string?, string?)   -- rokit.toml text -> "0.10.5", or nil and the problem
function lunepin.places(root: string): { string }           -- where rokit.toml is looked for, nearest first
function lunepin.running(version: string?): string?         -- _VERSION ("Lune 0.10.5+709") -> "0.10.5"
function lunepin.reported(line: string?): string?           -- a `lune --version` line ("lune 0.10.5") -> "0.10.5"
function lunepin.check(pinned: string?, problem: string?, running: string?, where: string): string? -- nil, or the refusal
```
- `pinned` reads only the `[tools]` table's `lune` key; comments, spacing and other tools are ignored. It refuses (zz-arch rule 6, lesson parsers-refuse-ambiguity) a second `lune` key, a `lune` key outside `[tools]`, a value that is not `"lune-org/lune@<x.y.z>"`, and a file with no pin, naming the line.
- `places(root)`: `<root>/rokit.toml`, then the same name in each folder above `root`, up to `/`. This is how rokit's shim finds its pin, and it is why a fixture copy of the runner under `.cache/` with no `rokit.toml` of its own takes the repository's (E2).
- `check` passes only `running == pinned`. Every other outcome refuses (zz-arch rule 7, lesson guard-no-is-explicit): another version, an unknown one (`running` nil) and no readable pin. The refusal names the running version (or "of an unknown version"), the pinned one, the `rokit.toml` it read and `lunepin.FIX`, or, for a pin it can't read, the problem.

### 2. `z-nile/tests/run.luau` (the shared runner; every home's `tests/run.luau` requires it)
- **The pin**: right after the home check, the runner walks `lunepin.places(ROOT)` (`ROOT` is the runner's own repository, two folders above its file, never the current folder), reads the first `rokit.toml` that exists, and keeps `PIN` (or its problem) and `PIN_FILE`. `RUNNING = lunepin.running(_VERSION)`.
- **The outermost run** (the one with no live browser guard, which today only sets up the guard and re-runs itself as a child: lines 82–118) decides the Lune the child runs on, before it relaunches:
  - On the pinned Lune it keeps the PATH.
  - On another Lune it puts `$HOME/.rokit/bin` first on the child's PATH (rokit's shim there resolves the pin from the home, which is under `ROOT`) and asks that PATH which Lune it gives: `lune --version`, parsed by `lunepin.reported`; a probe that fails keeps the shell's version (G1).
  - It applies `lunepin.check` to the Lune the child will run on. A refusal goes to stderr, the guard directory is removed, and the run exits 2 before any spec loads.
  - Otherwise it prints one line to stdout, the first of the run (G2): `tests/run: lune <v> (rokit.toml pins <v>)`, plus `; this shell's lune is <w>, so ~/.rokit/bin's runs` when it switched.
- **Every inner run** (the guarded child, each `--jobs` worker, a spec's nested run of a fixture; all of them see a live `PICKMAN_OPEN_GUARD`) checks its own `RUNNING` with `lunepin.check` right after the relaunch block. On a refusal it exits 2 with the refusal on stderr, before any spec loads. It tries nothing and prints nothing (workers' last line stays the summary the coordinator parses; nested runs' output stays as specs expect it).
- The outermost process runs the home check, the list-mode check, `fence.enter()` and the guard setup on whatever Lune the shell gave it, as today: they run no spec. Every spec runs in the child, on the pinned Lune.

### Not changed

- **No behaviour change for players**: none of `pickman/src` changes; the pickman gate shows it (E3).
- **Overrides**: none. Every promoted spec that runs a copy of the runner (c0059 adapt, c0120 runner-home, c0154 schedule) passes unchanged: their fixtures have no `rokit.toml` and take the repository's (E2, E3).

Mutation scripts that call the runner directly (c0153's `experiments/mutants.py`, preps' runners) do the same.
- **Shared state**: none. The runner writes nothing new.
- **Restated rules**: the three documents above; AC3 pins the sentence in each.
- **Moves**: none.
- **Guards**: the check fails closed (rule 7). The pin comes from the working tree's `rokit.toml`, which a branch can edit (lesson guards-trust-only-origin). That is deliberate: the check does not widen a guard, it makes a run agree with CI, and CI reads the same commit's `rokit.toml`. A branch that changes the pin changes CI's Lune with it.

### Scalability
One more file read per runner process (the walk usually stops at the first folder), and one `lune --version` process only when the outermost run is on another Lune. A `--jobs 8` run reads `rokit.toml` 10 times (outermost, child, 8 workers): microseconds next to a spec.

### Maintainability
The pin's format has one reader (`lunepin.pinned`, lesson one-reader-per-format; `setup.sh` reads `rokit.toml` only through `rokit install`). A new tool pin would get its own reader function there. A new runner entry point (a home's `tests/run.luau`) requires the shared runner, so it inherits the check.

### Usability
The refusal names both versions, the `rokit.toml` it read, and the fix (zz-arch rule 8). The switch says it happened. Every run's output, and so every gate log and check run, starts with the Lune it ran on.

## Unknowns & experiments
- **E1. Does a running Lune know its version, and do the shim and the pin agree?** Pass. `_VERSION` is "Lune 0.10.5+709" on rokit's 0.10.5 and "Lune 0.11.1+740" on Homebrew's. `lune --version` prints "lune 0.10.5" or "lune 0.11.1". rokit's shim resolves the pin from the current folder's `rokit.toml` or the nearest above it. Run from `/` it fell through to the next `lune` on PATH (0.11.1). With a `rokit.toml` pinning an uninstalled version it fails ("No such file or directory"). So the runner probes rather than trusts the shim, and the fixture specs run the pinned binary itself (`~/.rokit/tool-storage/lune-org/lune/<v>/lune`, where `setup.sh`'s `rokit install` puts it on every host and on CI).
- **E2. Does checking break the runner's fixture specs?** The first prototype read only `<ROOT>/rokit.toml`. The full gate failed 15 z-nile cases (c0059 adapt 2, c0120 runner-home 6, c0154 schedule 5, run-record-merge 2), all with "no readable rokit.toml" in a fixture copy under `.cache/`. Reading the nearest `rokit.toml` at or above `ROOT` (rokit's own rule) fixed every one with no spec change. Fallback, unused: give each fixture a `rokit.toml` (three promoted specs overridden).
- **E3. Prototype** (scratch worktree `proto-c0162`): the full gate of both projects passes at 50128704 (pickman 1487 passed, z-nile 1249 passed, 0 failed; lint and types clean). Both projects' CI jobs were dispatched on the pushed prototype branch with `z-nile/ci-verify.sh` (run 40457568843), but GitHub refused to start them: "The job was not started because recent account payments have failed or your spending limit needs to be increased". Every run in the repository fails this way since about 05:14 UTC on 2026-10-27. The CI proof is still owed: rerun `z-nile/ci-verify.sh` on `proto-c0162` once billing is fixed. The prototype branch also holds the three acceptance specs at their promoted path, `z-nile/tests/acceptance/c0162/`, so CI ran them on Linux too (rokit stores the pinned Lune at the same `~/.rokit/tool-storage` path there). `./zn check c0162` on it: AC1 to AC4 pass.
- **E5. Mutation check** (the Rules table, on the prototype, `scratchpad/mut0162.py`): every row's mutant was applied alone and its spec run. M1–M3, M5 and M7–M15 fail on an assertion. M4 and M6 break the runner that runs the specs (it checks itself first), so every run refuses before a spec loads: they are killed, but not on an assertion. M4 was also evaluated directly: the mutated `running("Lune 0.10.5+709")` returns "0.10.5+709", which pin.spec's assertion rejects. M6 (only the current folder's `rokit.toml`) is reasoned: no home has a `rokit.toml` of its own, so every run from a home refuses.
- **E4. Repair by hand**: from `z-nile/` with Homebrew's Lune (0.11.1), `/opt/homebrew/bin/lune run tests/run -- tests/tooling/run-lane-error.spec.luau` printed `tests/run: lune 0.10.5 (rokit.toml pins 0.10.5; this shell's lune is 0.11.1, so ~/.rokit/bin's runs)` and passed. With `HOME=/nonexistent` it refused (exit 2) naming 0.11.1, 0.10.5, the `rokit.toml` and the fix. With a live guard (an inner run) it refused at once. CI has one Lune only, so AC2's repair case uses a logging rokit `lune` in the fixture's HOME (runner.spec) rather than a second real version.
- **Lessons pass**: guard-no-is-explicit (the check's only pass is equality; unknown and unreadable refuse); parsers-refuse-ambiguity (`pinned`'s refusals); one-reader-per-format; guards-trust-only-origin (answered under Guards); guards-decide-from-the-tools-resolution (the outermost run asks the child's PATH which Lune it gives, and the child checks itself).

## Guesses
- **G1. On another Lune: refuse, warn, or switch first?** Recommended: **switch first, then refuse**. The outermost run puts `$HOME/.rokit/bin` first and runs on the pin when rokit has it. It refuses (exit 2, before any spec) only when that gives another Lune too, and every inner run refuses on another Lune. Refusing alone is safest but breaks every direct run in a shell whose Homebrew Lune comes first, which is how this machine is set up. Warning alone lets a run on the wrong Lune pass silently into a record (the capture's problem). Switching keeps direct runs working and every spec on the pin, and the line says what happened.
- **G2. Where the version is named?** Recommended: **the first line of the outermost run's stdout**, `tests/run: lune <v> (rokit.toml pins <v>)`. The summary line stays as it is, because the coordinator parses each worker's last line and many specs match the summary text. Inner runs print nothing, so nested runs' output is unchanged.
