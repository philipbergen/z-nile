# c0163: Conflict marker gate

## Problem
Observed 2026-10-26: PR #154 (`6bfad12f`, "tracker: prep R0051 Touch fire and hop (f0110)", by another session) merged git conflict markers into `origin/main`, in `pickman/.tracker/architecture.md` lines 27–33 (rows of the features table) and 66–70 (inside the ```` ```deps ```` block: `<<<<<<< HEAD` / `Touch -> Hud` / `=======` / `Session -> Picks` / `>>>>>>> origin/main`). The local full gate and CI both passed, so every session that synced afterwards inherited the markers, and nothing said so.

Two things let it through:
- **The gate never looks for markers.** `z-nile/check.sh` (its static stages: format, lint, types, build, skills) and so `./zn land`, `zn commit`, CI (`.github/workflows/`, `z-nile/ci-verify.sh`) and the PR flow's guards accept any committed text. c0045 only made `recordAndCommit` refuse while `git ls-files -u` lists unmerged paths, which says nothing once a conflicted file has been `git add`ed and committed.
- **The deps reader skips what it can't parse.** `declaredDeps()` in `pickman/tests/meta/architecture.spec.luau` matches each line of the deps block against `^%s*(%w+)%s*%->%s*(%w+)%s*$` and silently ignores any line that isn't an edge. The marker lines were ignored without a word, and the two sides of the conflict were both read as edges, so the spec checked a graph nobody had agreed on: in effect one side's edge is wrong or dropped, and nothing said which. The acceptance specs that read the same block with the same `string.match(arch, "```deps\n(.-)```")` (`pickman/.tracker/issues/f0143/acceptance/place.spec.luau`, `pickman/.tracker/issues/active/f0146/acceptance/place.spec.luau`) inherit the same blindness.

What should happen:
- **The gate fails on a committed conflict marker, in every mode** (`--affected` as well as `--full`, so `./zn land` and CI both catch it): any tracked text file holding a line that starts with `<<<<<<< ` or `>>>>>>> `, or that is exactly `=======`, fails the gate with the file and line number of each one. A file that documents markers on purpose can be exempted explicitly (a named, committed list, not a pattern that could hide a real conflict). Today `git grep -nE '^(<<<<<<< |>>>>>>> |=======$)'` finds no such file: the only hits are the real markers in `pickman/.tracker/architecture.md`, and the files that mention markers (`z-nile/.tracker/issues/c0139/c0139.md`, `z-nile/.tracker/rafts/done/R0002/design-review-004.md`, `z-nile/tests/acceptance/c0045/workstreams.spec.luau`) do so mid-line, so the exemption list starts empty.
- **The architecture deps reader fails closed.** `declaredDeps()` fails, naming the line, on any line of the deps block that is neither an edge (`A -> B`), a blank line nor a comment, instead of skipping it.

## Non-goals
- Refusing to rewrite a conflicted file in tracker scripts (`rename-lesson-ids`, `rewrite-finished`, `./zn` commands that edit documents): c0139.
- Refusing `zn commit` / `done` while paths are unmerged: done in c0045 (`recordAndCommit`).
- Removing the markers now on `main` in `pickman/.tracker/architecture.md`: session pickman-f4's fix. This chore keeps them from coming back unnoticed.

## Solution
- A marker stage among `z-nile/check.sh`'s static stages (they run in every mode), over `git ls-files` minus binary files and the exemption list, printing `<file>:<line>: conflict marker` for each hit; or a tooling meta spec that the selector always runs. It must see the tree being gated (the merge `./zn land` makes), not only `HEAD`.
- `declaredDeps()` raises on an unrecognised line (blank lines and comment lines allowed); the acceptance specs that parse the block could share one reader rather than each keeping its own `string.match` (one reader per format, zz-arch).
- A fixture spec for each: a planted marker in a fixture repository fails the stage with its file and line; a planted non-edge line in a deps block fails the reader.
