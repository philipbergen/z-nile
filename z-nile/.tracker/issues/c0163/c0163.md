# c0163: Conflict marker gate

## Problem
Observed 2026-10-26: PR #154 (`6bfad12f`, "tracker: prep R0051 Touch fire and hop (f0110)", by another session) merged git conflict markers into `origin/main`, in `pickman/.tracker/architecture.md` lines 27–33 (rows of the features table) and 66–70 (inside the ```` ```deps ```` block: `<<<<<<< HEAD` / `Touch -> Hud` / `=======` / `Session -> Picks` / `>>>>>>> origin/main`). The local full gate and CI both passed, so every session that synced afterwards inherited the markers, and nothing said so.

Two things let it through:
- **The gate never looks for markers.** `z-nile/check.sh` (its static stages: format, lint, types, build, skills) and so `./zn land`, `zn commit`, CI (`.github/workflows/`, `z-nile/ci-verify.sh`) and the PR flow's guards accept any committed text. c0045 only made `recordAndCommit` refuse while `git ls-files -u` lists unmerged paths, which says nothing once a conflicted file has been `git add`ed and committed.
- **The deps reader skips what it can't parse.** `declaredDeps()` in `pickman/tests/meta/architecture.spec.luau` matches each line of the deps block against `^%s*(%w+)%s*%->%s*(%w+)%s*$` and silently ignores any line that isn't an edge. The marker lines were ignored without a word, and the two sides of the conflict were both read as edges, so the spec checked a graph nobody had agreed on: in effect one side's edge is wrong or dropped, and nothing said which. The acceptance specs that read the same block with the same `string.match(arch, "```deps\n(.-)```")` (`pickman/.tracker/issues/f0143/acceptance/place.spec.luau`, `pickman/.tracker/issues/active/f0146/acceptance/place.spec.luau`) inherit the same blindness.

What should happen:
- **The gate fails on a committed conflict marker, in every mode** (`--affected` as well as `--full`, so `./zn land` and CI both catch it): any tracked text file holding a line that starts with `<<<<<<< ` or `>>>>>>> `, or that is exactly `=======`, fails the gate with the file and line number of each one. A file that documents markers on purpose can be exempted explicitly (a named, committed list, not a pattern that could hide a real conflict). Today `git grep -nE '^(<<<<<<< |>>>>>>> |=======$)'` finds no such file: the only hits are the real markers in `pickman/.tracker/architecture.md`, and the files that mention markers (`z-nile/.tracker/issues/c0139/c0139.md`, `z-nile/.tracker/rafts/done/R0002/design-review-004.md`, `z-nile/tests/acceptance/c0045/workstreams.spec.luau`) do so mid-line, so the exemption list starts empty.
- **The architecture deps reader fails closed.** `declaredDeps()` fails, naming the line, on any line of the deps block that is neither an edge (`A -> B`), a blank line nor a comment, instead of skipping it.

## Non-goals
- Refusing to rewrite a conflicted file in tracker scripts (`rename-lesson-ids`, `rewrite-finished`, `./zn` commands that edit documents): c0139.
- Refusing `zn commit` / `done` while paths are unmerged: done in c0045 (`recordAndCommit`).
- Removing the markers now on `main` in `pickman/.tracker/architecture.md`: session pickman-f4's fix. This chore keeps them from coming back unnoticed.

## Solution
- A marker stage among `z-nile/check.sh`'s static stages (they run in every mode), over `git ls-files` minus binary files and the exemption list, printing `<file>:<line>: conflict marker` for each hit; or a tooling meta spec that the selector always runs. It must see the tree being gated (the merge `./zn land` makes), not only `HEAD`.
- `declaredDeps()` raises on an unrecognised line (blank lines and comment lines allowed); the acceptance specs that parse the block could share one reader rather than each keeping its own `string.match` (one reader per format, zz-arch).
- A fixture spec for each: a planted marker in a fixture repository fails the stage with its file and line; a planted non-edge line in a deps block fails the reader.

## Design
**The marker scan (pure, `z-nile/engine/markers.luau`).** One concern, texts in and problems out (zz-arch rule 4):
- `markers.isMarker(line: string): boolean`: a line that starts with seven `<`, `>` or `|` followed by a space or the end of the line (git's `<<<<<<< HEAD`, `>>>>>>> origin/main`, and `||||||| base` under the diff3 and zdiff3 conflict styles), or is exactly seven `=`; a trailing carriage return is ignored, so a CRLF file reads the same. Mid-line, indented, six or eight long, glued to a word (`<<<<<<<x`) or `=======` with a trailer is not a marker. The `|||||||` line is prep's addition to the capture's three (git writes it with `merge.conflictStyle=diff3`, so a conflict resolved under that style leaves it too); nothing else widens.
- `markers.isBinary(text)`: git's rule, a NUL byte in the first 8000 bytes.
- `markers.scan(path, text): { Hit }` (`Hit = { path, line }`, 1-based lines); none for a binary text.
- `markers.parseExemptions(text): (paths, problems)`: one plain repository-relative path per line, blank lines and `#` comments allowed; a pattern (`*`, `?`, `[`), an absolute path, a `..` step, a backslash or a repeat is a problem naming `z-nile/marker-exemptions.txt:<line>` (zz-arch rule 6).
- `markers.check(files, exempt, tracked): { string }`: `<path>:<line>: conflict marker` for each marker outside an exempted file, sorted by path, then one problem per exemption that names no tracked text file (a stale exemption fails rather than lingering).
- `markers.EXEMPTIONS = "z-nile/marker-exemptions.txt"`: committed, header comments only (empty). Today `git grep -nE '^(<<<<<<< |>>>>>>> |=======$)'` finds no file that documents markers at a line start.

**The command (`z-nile/engine/main.luau`, `cmd.markers`, usage `markers`).** Read-only, so it runs in the main checkout too. It scans the tree being gated: the working tree's tracked files (`git ls-files -s -z` for the set and the modes), which is the merge `./zn land` stages and commits and the branch CI checks out. Speed (E1): `git grep -z -l -I -e '^<<<<<<<' -e '^>>>>>>>' -e '^|||||||' -e '^======='` over the working tree names only the files with a line that starts like a marker (a superset of `isMarker`; `-I` skips binaries as `isBinary` does), only those are read, and `markers.check` decides; `git grep` exit 1 means no match, any other failure fails the command. Symbolic links (mode 120000) and submodules (160000) are not scanned (git grep reads a link's blob, its target path, so a link is never a candidate anyway; the mode check keeps them out of the tracked set the exemptions are checked against). Exemptions come from `git show origin/main:z-nile/marker-exemptions.txt` (zz-arch rule 7: configuration that widens a guard never comes from the working tree a branch can edit); when origin/main has no list (a fixture without origin, or before c0163 lands), none apply: fail closed. The working tree's copy must still parse, so a malformed edit fails on the branch that makes it. Failure prints each problem and `resolve each conflict (or, for a file that documents markers, name it in origin/main's z-nile/marker-exemptions.txt)`; success prints `markers: <n> tracked files, no conflict markers`.

**The gate stage (`z-nile/check.sh`).** `[[ -f z-nile/engine/markers.luau ]] && par_start "markers (./zn markers)" ./zn markers`, among the static stages, after the skill links, before `par_wait`: they run in every mode, so `--affected` (land, `zn commit`) and `--full` (CI, `done`) both fail on a marker. `--plan` prints `markers: every tracked text file` under the same condition. The condition follows the skills stage's (`[[ -d z-nile/skills ]]`): a tree without z-nile's engine (c0077's and c0120's gate fixtures copy check.sh without it; check.sh already reads such a tree as one project at the root) has no `./zn` to run. Found by E2: unguarded, c0077's promoted `replace-file.spec` failed ("the build lands as a regular file…": its stub-tool tree stopped at the marker stage, before the tests stage it expects). In this repository the module is always there, and a branch that deleted it would also fail the promoted `markers.spec`, which z-nile's full run (forced by any engine change) loads.

**The deps reader (`z-nile/lib/deps.luau`, beside `graph.luau`, which pickman's meta spec already requires through `@znile`).** The one reader of an architecture document's ```` ```deps ```` block (zz-arch rule 5): `deps.parse(md: string, name: string): (Graph, { string })` reads `Consumer -> Provider` edges, allows blank lines and `#` comment lines, and names every other line with the document's line number (`<name>:<line>: "<text>" in the deps block is not an edge (A -> B), a blank line or a # comment`); no block, two blocks, or one never closed is a problem too. `pickman/tests/meta/architecture.spec.luau`'s `declaredDeps()` reads through it and raises the problems, so a marker in the block fails both cases that read the graph, naming the line, instead of being skipped.

**The two acceptance specs that read the block (decision).** `pickman/tests/acceptance/f0146/place.spec.luau` (promoted) and `pickman/.tracker/issues/f0143/acceptance/place.spec.luau` (f0143's sequestered spec, backlog) find one edge each by substring (`has(deps, "\nPad -> View\n")`); they parse no graph, so they are not readers of the format, and a conflict that leaves their edge in place passes them. They are left as they are: the marker stage fails first on any marker anywhere, and the meta spec (forced into every pickman run by the selector when `tests/meta/` or the touched code changes, and in every `--full`) fails on any stray line in the block. Changing them would override f0146's promoted spec and edit another issue's sequestered spec for no rule they would then hold. No Override.

**Spec fixtures write markers only under `.cache` or as strings.** The specs build every marker with `string.rep` (no line of their source starts with one, so the stage never flags the specs themselves), and write marker files only in fixture repositories under `z-nile/.cache/c0163-*` (trackerfix), which are not tracked.

### Scalability
Per gate run: two git processes (`ls-files -s -z`, `grep -l`), one `git show`, and one file read per candidate file (none on a clean tree). Measured on this repository (2403 tracked files): `./zn markers` 0.6 s wall alone (2.1 s when it read every file, E1); in the gate it runs beside the type and lint stages (0.8–1.7 s), so the static stages' wall time is unchanged. The deps reader is linear in architecture.md.

### Maintainability
One module per concern: the marker rule and the exemption format in `markers.luau` (its one reader of the list), the block in `deps.luau` (its one reader). A new marker kind is one entry in `OPENERS`; a new exemption is one line on main, reviewed like any change. zz-arch's Layout table names `deps.luau` among `z-nile/lib/`'s shared modules, and its rule 5 adds `markers.luau` (the exemption list) and `lib/deps.luau` (an architecture document's deps block) to the readers it lists.

### Usability
`./zn markers` names `<file>:<line>` for each marker and says what to do; a malformed or stale exemption names the list's line or path. The usage text gains one line; the command is read-only, so it is in no refusal list.
