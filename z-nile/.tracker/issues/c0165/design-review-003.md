Recommendation: Phase 0 step 1 reads ``Confirm `z-nile/check.sh --full --reuse` passes here.`` Change the Wording line, its docs.spec pin and the Gate modes row. State in the Design why the baseline needs every spec: an empty change set selects nothing. No new rule is needed: `--full --reuse` already exists and has its cases.

### F2 [high] The `*` class puts `c0120/finished` (132–754 s) into every affected gate that runs z-nile's specs: a pickman-only change goes from 0 z-nile specs to 25, and the stop hook's gate passes its 300 s timeout under load
Where: Design, `select.luau`, `inputs.tsv` format and the `*` bullets ("The cost: those 21 run in every gate that runs z-nile's specs"); Scalability (no line for the `*` set); `scripts/hooks/stop.sh` (`scripts/check.sh --affected`, with `"timeout": 300` in `.claude/settings.json`).
Evidence:
- On the prototype, `lune run z-nile/affected -- --project z-nile pickman/src/shared/Logic/.gitkeep` prints 25 specs: the 21 `*` specs plus `c0115/absence`, `c0120/check-paths`, `c0120/graph-homes` and `repo-fence`. On the worktree, the same command prints 0.
- The `*` set's recorded durations (prototype `z-nile/.cache/spec-durations.tsv`) add up to about 300 s. `c0120/finished` alone is 132.13 s. In this checkout's other worktrees it is 132.66, 135.62, 137.15 and 149.72 s idle, and 255.61, 353.33, 359.61, 394.10 and 753.89 s under load. `c0116/retired` is 30–564 s.
- One spec file is one lane, so every all-project `--affected` gate now lasts at least `c0120/finished`'s time, about the idle full gate's ~216 s.
- The stop hook runs `--affected` for any change under `pickman/` or `z-nile/`, a one-line game change included. Under load it now passes its 300 s timeout, and the hook is cut off instead of gating the stop. Today that gate runs pickman's affected specs only.
- design-review-002 F9 split gate.spec so that promotion "adds no gate floor". The `*` class adds a larger one.
Critique: A Design statement names the cost but never measures it, and the cost defeats the capture's first outcome ("later steps skip rerunning it") for every change. The tempting fix is dropping the expensive specs' `*`. That brings back the hole design-review-002 F2 closed.
Consequences: `*` lumps two dependencies together:
- git state that changes (HEAD's tree, which the HEAD clones read, plus any refs a spec reads);
- immutable history (fixed commits read with `log` or `show`), which a content declaration covers.

A spec of the first kind is safe to reuse when every blob and the HEAD commit (and the refs it reads) are the same. That makes `*` specs reusable between identical runs, but not across edits. Iteration stays slow unless a spec's real inputs are narrower than "everything". `c0120/finished` checks finished items' `check.sh` paths, which depend on the existence of almost every file. The stop hook isn't in Touched modules.
Recommendation: Question the mechanism:
- (a) Split `*`: a spec that reads only fixed history gets content declarations; a spec that reads HEAD or refs gets a fingerprint of every blob plus `git rev-parse HEAD` (and each ref it reads), reused like any other spec. Add a Rules row and a gate-learn case: the same content and HEAD is reused, and a new commit on the same content reruns.
- (b) Measure the `*` set's wall time in Scalability and E6, idle and under load, against the stop hook's 300 s.
- (c) If `c0120/finished` (or another slow spec) still runs on every change after (a), escalate to the user. The options: accept that floor on every affected gate and the stop hook's timeout (and raise the timeout, which touches `scripts/hooks/stop.sh` and `.claude/settings.json`), or let the stop hook gate `--project` of the changed homes only. Say what each costs.

Never drop a spec's declaration to win the time back.
Lesson: z-design/declare-what-full-runs-covered

### F3 [medium] Whole-gate reuse skips the `*` specs on a new commit of the same content, which contradicts "its pass is never reused"
Where: Design, `inputs.tsv` format ("`decide` treats it as fresh, so its pass is never reused"); Whole-gate reuse (`extra` is the mode, the projects, the base and the learned text, and no HEAD); `fingerprint.digest`.
Evidence: The `*` specs exist because "their result depends on git state that no path's content shows". The whole-gate digest is content only. An author runs `--affected` on an uncommitted change: it passes, and the `gates` row is recorded. In that run the HEAD-clone specs (`c0044/naming`: "a clone of the repo's committed HEAD … the working tree's tooling overlaid") tested the old HEAD's non-tooling files. The author commits. The blob map is unchanged, and so are the merge base, the digest and the selection. The reviewer's `--affected` prints `reused: an affected gate passed on this content`, so no `*` spec ever runs against a HEAD that holds the change before `done`. The same holds for history readers after a reword or amend. The concurrent path breaks the rule too: two runs whose `*` spec has no row both insert, and the loser waits, then reuses the winner's pass (`reused … (waited for pid N)`), which came from another worktree's HEAD.
Critique: A rule stated in the Design doesn't hold through the second reuse path. Today's merge gate is still fresh (`done`), so this is a pre-merge miss, not a forged pass on `main`.
Consequences: Adding HEAD to the full digest would break the user's decision ("done's run + CI count as the merge's"): `done` runs on an uncommitted tree, which the commit then moves. That decision is binding. Say what it implies: at the merge, the `*` specs ran on `done`'s pre-commit HEAD, and CI covers the final head.
Recommendation: For the affected digest, add `HEAD <commit>` to `extra` whenever the selection holds a `*` spec (or adopt F2(a)'s per-spec HEAD fingerprint and drop "never reused"). In the full digest, keep content only and write the implication above beside the scope decision. A lost insert race on a `*` spec runs it unclaimed instead of reusing the winner's row. Add a gate-reuse case: `--affected` passes on a dirty tree with a `*` spec selected, the change is committed, and the next `--affected` runs the `*` spec. Add a Rules row with the mutant "HEAD left out of the affected digest".

### F4 [medium] `gate-record` writes the `gates` row with no jail check, so design-review-002 F3's hole (vacuous guard-spec passes reused by jailed runs) reopens through whole-gate reuse
Where: Design, Whole-gate reuse ("At the end, after the last stage passed … `gate-record` … writes the row"); `reuseplan.records` and its two named callers (`specs run`, `record --full`); prototype `gateRecordCommand` (no jail read) and `check.sh` lines 282–286.
Evidence: When `records(jail, …)` is false (an outer sandbox on macOS, as in a session in the main checkout, whose `.claude/` is writable per design-review-002 F3), `specs run` records nothing and prints `not recorded: <jail>`. `check.sh` then reaches its end and calls `gate-record --digest <d> --mode affected …`, which writes the row anyway. A later jailed `--affected` on the same content, base and projects (the same worktree, rerun from a jailed shell) is reused whole. `repo-fence:499`, `c0078/jail-signals` and `c0076/sweeper` then never run their jailed cases on that content. The same holds for a `full` row and `--full --reuse` at the merge.
Critique: A companion record is written outside the gate that guards the main record. The tempting fix makes `check.sh` parse `not recorded` from the orchestrator's output, which is fragile.
Consequences: `check.sh` has no jail of its own to read. Only the orchestrator (affected) and `record --full` (full) see the runner's jail. A gate in which no spec ran (all reused, or none selected) has no jail to judge, and recording it is safe: its spec results came from rows a strong jail recorded. `records`'s `nested` argument is why R47b can't be tested: every spec's orchestrator is nested.
Recommendation:
- When a run's jail doesn't record, `specs run` and `record --full` exit 0 but write a marker, `<home>/.cache/spec-norecord-<check.sh pid>`. Or name the marker file in an env var `check.sh` sets. `gate-record` refuses when the marker exists, and `check.sh` removes it.
- Key `records` on the jail string instead of `nested`. Record for `sandbox-exec`; for `outer sandbox (a fixture of a guarded checkout)` (the only form a nested macOS run has, fence.luau:715); and for `none …` off macOS.
- Then a fixture can test the call sites. A stand-in runner reports `outer sandbox (protects the repository)`, and the case expects no `specs` row and no `gates` row. That turns R47b into `run`.
- Add Rules rows for both call sites, with the mutant "`gate-record` ignores the jail".

### F6 [medium] Two claim paths make concurrent runs duplicate, and one of them deletes the live owner's row
Where: `reuseplan.decide` (row "any | true | - | run"); affected step 2 ("Each `run` claims"); `holds` = `fence.holds(fence.alive(pid), …)`; `fence.alive` (fence.luau:110–121); capture, "Concurrent runs wait, they don't duplicate".
Evidence:
- (a) With `fresh` (`--fresh`, or any `*` spec), `decide` returns `run` even for a `running` row whose owner holds. The prototype claims with a compare-and-swap on that row (`UPDATE … WHERE state='running' AND owner_pid IS <live pid>`), which succeeds and takes over a live run. The owner's later `record` is refused, since the row isn't its own any more, and the spec runs twice. The Design says `--fresh` "still claims, so a concurrent reusing run waits for it". It doesn't say that a fresh run steals from a live owner.
- (b) `fence.alive` treats `kill -0`'s "Operation not permitted" as alive only when `PICKMAN_TEST_JAIL` says the caller is confined. The orchestrator runs outside the runner, where that variable is unset. An orchestrator in Claude Code's outer sandbox gets EPERM for an owner outside it, which reads as dead, and it takes the live owner's row over. It then runs the spec, and because `records` is false in an outer sandbox, it "releases its claims", deleting the row. The live owner's record is refused, since its row is gone: the CAS sees no row it owns. Its waiters see no row and claim again, so the spec runs three times and nothing is recorded. `sweepResults` uses the same `alive`, so it can delete a live run's results file in the same home.
Critique: Each one breaks the capture's wait outcome in a mode the Design names (`--fresh`, `*`, the outer sandbox). The tempting fix for (b) passes `PICKMAN_TEST_JAIL` to the orchestrator, which isn't jailed and doesn't know the jail.
Consequences: EPERM from `kill -0` always means the pid exists. A reused pid owned by another user is ruled out by the start id, which `holds` already compares. If `startOf` fails across the sandbox, `holds(true, s, nil)` is true: wait, then the timeout. That is the safe side.
Recommendation:
- `decide(running, fresh, holds=true)` is `wait` (a fresh run never takes over a live owner). On a `passed` or `failed` row, `--fresh` claims by compare-and-swap as now. Add plan.spec rows for both.
- The orchestrator's liveness counts EPERM as alive. Give `fence` a variant (an export, no behaviour change for the runner) or a `holds` option, and use it in the sweep too.
- Add a gate-wait case: a `--fresh` run against a held owner prints `waiting for pid`, and the spec ran once. Add an R-row for each, with the mutants "fresh steals a live owner's row" and "EPERM reads as dead".
