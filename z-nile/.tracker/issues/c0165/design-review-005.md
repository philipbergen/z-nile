### F1 [high] The new stop hook breaks every worktree cut after c0114 and before c0165: today's `affected` reads `--gate-projects` as a changed path and prints `ALL` or spec paths, which the hook passes on as `--project` names (repeat of design-review-004 F1's mechanism)
Where: Modules (`scripts/hooks/stop.sh`: "pre-c0114 trees keep the unscoped call"); Gate modes table (stop hook row: "pre-c0114 trees without `z-nile/roots.luau` retain the unscoped call"); R57; stop-hook.spec (the old-tree case removes only `z-nile/roots.luau`); `zz-arch/lessons/project-gates-use-selector-forcing.md` ("How to apply").
Evidence:
- The hook is the main checkout's (`.claude/settings.json:40`, `"$CLAUDE_PROJECT_DIR"/scripts/hooks/stop.sh`), and it gates whatever worktree the session is in (`stop.sh:7–10`, "this hook runs from the main checkout against any worktree", `stop.sh:24–26`). Once c0165 lands and the main checkout fast-forwards, every session in a worktree branched before c0165 runs the new hook against that tree's own `z-nile/affected.luau`. `git worktree list` shows 63 worktrees today, and every one has `z-nile/roots.luau`, so the design's only old-tree test calls them new.
- Today's `affected.luau` (lines 145–157) puts every argument other than `--base`, `--project` and `--` into the changed list, so `--gate-projects` is read as a path. Run in this worktree:
  - `lune run z-nile/affected -- --gate-projects z-nile/lib/x.luau` prints `ALL`, exit 0;
  - `… --gate-projects src/x.luau` prints `ALL`, exit 0;
  - `… --gate-projects pickman/src/shared/Logic/Maze/init.luau` prints `pickman/tests/acceptance/c0002/place-rules.spec.luau` and more spec paths, exit 0;
  - `… --gate-projects pickman/README.md` prints nothing, exit 0.
- The designed hook turns each line into a `--project` flag. `z-nile/check.sh:46` refuses a name not in the registry (`check.sh: no project ALL in z-nile/projects.toml`, exit 2). So the hook reports "failed; fix before finishing" on every stop where a home or old-root file changed, in every in-flight raft, until each one merges main. That is a false failure: the gate fails closed on a tree that is fine. And an empty answer (no line printed) has no designed behaviour: a hook that reads "no projects" as "nothing to gate" skips the gate (fails open).
- The same gap applies in the new tree: if the session has broken `z-nile/lib/select.luau` or `z-nile/affected.luau` (exactly the files c0165 adds and later issues will edit), `--gate-projects` crashes or prints nothing. The design doesn't say what the hook does when the helper exits non-zero or prints no project. stop-hook.spec has no case for either.
Critique: design-review-004 F1 asked the hook to fall back for trees "with no `z-nile/roots.luau`", and the author did that. But the test was the wrong feature: it detects c0114, not the helper the hook now calls. This is the defect `zz-rules/main-checkout-tools-span-the-move` names ("work on a tree from before this change as well as after it, until the old trees are gone"). The tempting fix is to key the fallback on `z-nile/lib/select.luau` instead. That covers the middle era, but still trusts whatever the helper prints and still has no answer for a helper that crashes in the new tree.
Consequences: The hook needs one rule for "the helper's answer can't be used", whatever the cause: an old tree, a crash, no output, or a line that isn't a project. The safe answer is today's unscoped `scripts/check.sh --affected` (every project's affected gate, a superset). Validating each line needs the registry's project names, which the hook can read without the new helper.
Recommendation:
- In the hook, use the helper's answer only when the tree has `z-nile/lib/select.luau`, the helper exits 0, it prints at least one line, and every line is a registered project name (for example, every line matches one `name = "<x>"` in `z-nile/projects.toml`, or a `--names` answer from `z-nile/roots`, which exists since c0114). Otherwise make the unscoped `scripts/check.sh --affected` call. Say this in Modules, the Gate modes row and R57.

Mutants: "fallback keyed on `roots.luau` only", "helper failure skips the gate".
- Add the middle-era tree to the zz-arch lesson's "How to apply" (a hook asks the tree whether it has the helper before calling it), or note it on `zz-rules/main-checkout-tools-span-the-move`.

### F2 [high] A declared ref moving never selects its spec, so "a declared ref's movement reruns it" can't happen, and gate-reuse's `headgate` case fails for a correct implementation
Where: `inputs.tsv` format ("`ref:refs/...` adds that one named ref to the spec's fingerprint; ref creation, movement or deletion reruns it"); `isInput` (paths only); fingerprint guarantees ("any spec changes when one of its declared refs moves"); R53; AC7 ("an affected whole-gate digest includes HEAD for a `*` selection and every selected declared ref"); `acceptance/gate-reuse.spec.luau:95–124` (`headgate`, the last step).
Evidence:
- Selection is path-only: `affected` returns "every spec S for which some changed path satisfies `isInput(ctx, S, path)`", and `isInput` has no rule for a ref. A spec is fingerprinted, and so rerun, only after it is selected. So a declared ref that moves while no path changes never reruns its spec. The design's sentence "movement … reruns it" holds only when an unrelated path change happens to select the spec.
- The `headgate` case's last step depends on exactly that. Its `b` spec declares `*` and `ref:refs/remotes/origin/main`. After the commit step, it runs `update-ref refs/remotes/origin/main HEAD` and expects `b` to run a third time (`count(ran(dir), "b")).toBe(3)`). But `refs/remotes/origin/main` is also the affected base (`changed.files`: merge base with `origin/main`, `z-nile/lib/changed.luau:17–33`). Reproduced in a scratch repository with the case's steps: before the move the change set is `pickman/src/A.luau`; after it, `merge-base HEAD origin/main` equals HEAD and the change set is empty. A correct gate selects nothing, `b` stays at 2, and AC7 is red with no possible implementation.
- The step also can't kill the mutant it is there for ("declared refs left out" of the fingerprint and digest). Moving the base already changes the whole-gate digest, and `b` isn't run at all. Round 4's recommendation asked for "a gate-level case that moves a declared ref without moving HEAD". This one moves the base instead, so no gate-level case moves only a declared ref.
Critique: The ref form was designed on the fingerprint side only. The tempting fix is to change the case to expect 2, which makes the spec pass. But the design would still promise reruns it can't deliver, and the first spec that declares `ref:refs/remotes/origin/main` would never rerun after a fetch.
Consequences: A rerun on ref movement needs the selector to pick the spec without a path change. Selection is stateless (it can't know the ref's last value), so the only stateless rule is that a spec with a `ref:` entry is always selected in its project's affected runs, and its fingerprint (which holds the ref) decides between reuse and run. That keeps AC1's direction (a fingerprint change implies selection) and costs one fingerprint per gate, reused while the ref stands still. The whole-gate digest then always holds that spec's declared refs, as the Design already says for "every selected declared ref".
Recommendation:
- Add to `isInput`/`affected`: a spec with any `ref:` entry is selected in every affected run of its project (as for `"ALL"`, a stateless rule), so its fingerprint decides. Fix the "reruns it" sentence to say how it happens. Add a select.spec case: an empty change set still selects a `ref:` spec and no other spec. Rules row mutant: "`ref:` specs selected only by paths".
- In `headgate`, add a step that moves a declared ref that is not the base (for example `ref:refs/heads/declared`, created before run 1 and then moved to a new commit with HEAD and `origin/main` fixed). Expect no whole-gate reuse and `b` run again. That kills "declared refs dropped from the digest or fingerprint". With the always-selected rule, the existing base-moving step is then also correct as written.
- If the author would rather keep selection path-only, the alternative is to change the claim to "a declared ref is part of the fingerprint when the spec is selected", fix the case to expect no rerun on a base move, and say in Usability that a ref-only move reruns nothing until a path selects the spec. Choose one; leaving both is this finding.
Lesson: z-design/spec-design-correspondence

### F3 [high] stop-hook.spec fails its type check: the failure step assigns the exit code into the string local `calls`, so `done`'s promoted-spec type check stops a correct implementation
Where: `acceptance/stop-hook.spec.luau:94–97` (`ok, calls = stop()` then `t.expect(calls).toBe(2)`).
Evidence: `stop()` returns `(boolean, number, string)`. `local ok, _, calls = stop()` gives `calls` the type `string`. The failure step's `ok, calls = stop()` assigns the second value (the exit code, a number) to it. `luau-lsp analyze --base-luaurc=.luaurc --platform=standard` on the file prints `stop-hook.spec.luau(96,16): TypeError: Expected this to be 'string', but got 'number'`. `./zn promote-check c0165` prints the same line beside the expected missing-module errors. This one doesn't depend on any module that execution adds. `select.spec`'s errors at 368 and 370 disappear once `fingerprint.GitState` exists, because `GIT` is annotated. `done` runs the promoted checks (`promotedChecksAll`, `z-nile/engine/main.luau:3940`), and the executor may not edit a sequestered spec. The case was new in round 4, and the round's verification didn't rerun the type check after the edit.
Critique: At runtime, the value is the code (2), so the case passes. Only the type stage sees it. The tempting fix is to cast. It is clearer to read the three results into their own names.
Consequences: none.
Recommendation: Write `local failOk, code = stop()` and assert `failOk == false` and `code == 2`. Assert the log too (`"--affected\n"`, one call), so a hook that fails without calling the gate is told apart. Rerun `./zn promote-check c0165` after every spec edit, and record the run in the refute.
Lesson: z-design/rerun-skipped-checks-after-edits

### F4 [medium] The Phase 0 decision's premise holds only for failures the raft's change didn't select: a red `main` spec that the change selects is never labelled "fails on the base too", and the pinned zz-execute wording says it is
Where: Problem (`Decided with the user (2026-11-03)`: "red `main` first shows at `./zn done` and the merge, where learning's trial (b) reports 'fails on the base too'"); Gate modes ("so a red base is told from a failure this raft caused"); Wording (zz-execute Phase 0: "a red `main` first shows there as a failure on the base too"); Learning step 2 ("A failed spec that was selected is an ordinary failure"); `zz-execute/SKILL.md:118` (Stop conditions: "Main is red.").
Evidence: Learning runs trials only for misses, `F \ sel`. Take a spec S that is red on `main` and that the raft's change selects (it touched S's module):
- S fails in the author's first affected run, which is not "first … at `done`";
- at `done`, S is in `sel`, so it is an ordinary failure, and no trial (b) runs or prints "fails on the base too".
The author then debugs a red `main` as their own defect, which Phase 0's old stop condition existed to prevent. Stop conditions still lists "Main is red", and with no Phase 0 check nothing defines how it is detected.
Critique: This isn't a reason to undo the user's "No baseline" decision. The design's account of what follows from it is wrong for one class of failure, the class an executor is most likely to meet. The tempting fix is to soften the wording. That leaves the executor with no way to tell a red base apart.
Consequences: A base trial for a selected failure costs one trial per failed spec at `done`, within the existing `PICKMAN_LEARN_BUDGET`. It reports only and learns nothing. An affected-run equivalent would cost a clone per failing run, so keep it to the full gate, where the decision says red `main` shows.
Recommendation: In full mode, run trial (b) (the base alone) for every failed spec, selected or not, within the budget. For a selected spec that also fails on the base, print `fails on the base too: main is red` and learn nothing. Add `learn.plan` and gate-learn cases: a selected failure that fails on the base prints the line, and one that passes on the base prints nothing. Make the Phase 0 wording and the Gate modes sentence say red `main` is reported at `done` for any failing spec. Give zz-execute's "Main is red" stop condition its detection ("`done` prints `fails on the base too`"), and pin it in docs.spec. If the author sees a reason not to extend the trial, escalate to the user: the decision was taken on the premise that trial (b) reports red `main`, and it doesn't for selected specs.
Lesson: z-design/accepted-risks-checked-and-decided
