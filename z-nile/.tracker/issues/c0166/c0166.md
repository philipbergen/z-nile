# c0166: Reviewers read only relevant lessons

## Problem
The user, 2026-10-26: "Have reviewers read only the relevant lessons, picked by the files and areas an issue touches, instead of all of them."

And, in the same capture: "It's an important feedback to previous efforts when a review finds an issue, that needs to go back to either the code or the design or prep prompt where the mistake was made or where the prompt was unclear. We need lessons that are actionable, searchable, and effective. They need to support high chance of success. When we hit 5 rounds that's a failure of making it clear what the goal was previously. Make each prompt so clear that 5 rounds of review is rare."

Today zz-review item 10 has every design reviewer run `./zn lessons --when design --full` (about 124 lessons on 2026-10-26) and every code reviewer `--when build --full` (about 62), and ask each lesson's `check` of the draft or diff. There are 131 lesson files, and every harvest adds more, so each review pays to read them all, most have nothing to do with what the issue touches, and the checks that do apply are diluted among the rest. Rafts still reach 5 review rounds (R0039), which means the earlier prompt (capture, design, ready prompt) did not make the goal clear.

What should happen:
- (a) Each design and code reviewer reads only the lessons relevant to the files and areas the issue touches (its Touched modules or diff paths, its project, the skills it exercises), and asks only those `check`s.
- (b) Lessons are actionable (each has a concrete check question), searchable (selectable by path and area, not only by skill, phase and tag) and effective (it is measured whether a lesson stops its defect from recurring, and an ineffective one is rewritten).
- (c) A review finding goes back into the code, design or prep prompt where the mistake was made or which was unclear. c0136 owns that routing (this issue depends on it); this issue relies on it and must not leave it out.
- (d) Five review rounds is rare. A raft that reaches it is treated as a failure of the earlier prompt: it is reported, and traced to the prompt that was unclear.

## Non-goals
- Which skill a lesson is filed under, and sending a finding back to the step that erred: c0136.
- Backfilling past reviews: c0112.
- The lesson file format and `lessons` command as they stand: c0111 (done).

## Solution
- Map touched paths and areas to lessons: a `paths:` or `areas:` field on each lesson, or a tag-to-path table.
- A selector, e.g. `./zn lessons --for <id>` or `--paths <p>...`, that the review brief runs instead of the full `--when` list; a small always-read core (e.g. tags `review`, `process`).
- `lessons --check` flags a lesson no selector can reach (so none goes unread) and one without a concrete `check:` question.
- zz-stats reports review rounds per raft, and lessons whose defect recurred after they existed.
- A raft that reaches 5 rounds gets a note tracing which earlier prompt was unclear, harvested as a lesson for that step.

### Selection

`lessons.select` keeps its signature and gains an optional fourth argument, the skill-folder map (`tree.folders`). `Query` gains `paths: { string }?`.

```lua
function lessons.relevant(lesson: Lesson, paths: { string }, skillFolder: string?, table: lessonareas.Table?): boolean
function lessons.select(all: { Lesson }, sources: { [string]: { string } }, q: Query, folders: { [string]: string }?, table: lessonareas.Table?): { Lesson }
function lessons.laterCount(sourceCount: number): number -- max(0, sourceCount - 1)
function lessons.staleSource(notOnBase: boolean, afterCheck: boolean, firstSource: boolean): boolean
function lessons.recurred(afterCheck: boolean, firstSource: boolean): boolean
function lessons.promptFailure(text: string): { string } -- matching bullet lines, each including the leading "- "
function lessons.needsPromptNote(kind: string, before: number, after: number, bullets: { string }, notes: { string }?, known: { [string]: boolean }?): boolean
function lessons.promptNote(text: string): { string } -- matching harvest-note lines
function lessonareas.parse(text: string): lessonareas.Table -- core, areas, exercised, skills, problems
```

`Tree` gains `areas: lessonareas.Table?`, set by `lessons.load` from the text it read. `relevant`, `select` and `lessons.check` do not read the file. A spec passes the table it parsed. `kind` is `"design"` or `"code"`. `staleSource` is true only when `notOnBase` and `afterCheck` and not `firstSource`. `recurred` is true only when `afterCheck` and not `firstSource`. That is the count `since check` prints, without the base test. `needsPromptNote` is true only when `before < 5` and `after >= 5` and the loop is not satisfied. The loop is satisfied only when some bullet starts with `- <kind> rounds reached 5 at ` and every note line that matches `- note 5 <kind> rounds, <step> prompt unclear: <ids>` has the bullet's `<capture|design|ready>` word and ids that parse and, when `known` is passed, ids that are in `known`. One matching note whose id is absent leaves the loop unsatisfied, even when another note is valid. A bullet with no matching note is not satisfied. `known` nil skips the existence check. `laterCount(1)` is 0: the first source is the origin, not a recurrence. `from:` counts as one source. This does not check which skill the lesson is filed under: that is c0136.

`Query` gains `exercised: { string }?`, the skill names `--mode` names. When `q.paths` is nil, `select` does not call `relevant`, does not apply `exercised`, and does not apply a path-exercised skill. When `q.paths` is a table, including an empty one, a lesson is kept when its skill is in `exercised`, or its skill is path-exercised for a query path, or `relevant` says so. A path-exercised skill is a `skill <name>:` row whose prefix overlaps a query path. `--when` still runs first. The CLI passes nil, not `{}`, for the empty-Touched case and for the not-repository-relative case. An empty table with `exercised` nil keeps only core lessons. An empty table with `exercised` set also keeps those skills. `select` takes the table as its fifth argument. When that argument is nil, the core arm and the tag arm miss and no skill is path-exercised.

`relevant`, only when it is called, and only from the table argument:

1. Any tag in `table.core` matches. Core does not bypass `--when`. A nil table makes this arm miss.
2. Else if the lesson's own `paths` is not nil, it matches only when one of those prefixes overlaps a query path. Tags and the skill folder are not consulted. Core already returned. This arm does not read the table.
3. Else it matches when the skill folder overlaps a query path, or some tag's area prefix overlaps a query path. A prefix whose text is `@skill` means the skill folder. A nil `skillFolder` makes that arm miss. A prefix whose text is `@item` matches a query path that contains `/.tracker/issues/` or `/.tracker/rafts/`. `@item` does not match a source path. A nil table makes this arm miss.

Overlap is whole components, the same rule as `raftplan.overlaps`: equal, or one path plus `/` is a prefix of the other. `z-nile/engine` overlaps `z-nile/engine/main.luau` and does not overlap `z-nile/engine-extra`. The three lines live in `lessonareas.overlap`. `lessonareas` does not require `raftplan` or `lessons`. `lessons` requires `lessonareas`. No file is read to decide a match.

`Lesson` gains `paths: { string }?`. Absent key parses as nil. A present key is a bracket list of repository-relative prefixes: segments of letters, digits, `.`, `_` and `-`, joined by `/`. No leading `/`, no `..`, no empty segment, no trailing slash, at least one entry, no repeats. Anything else is a parse error naming the lesson id (`paths must be a [p, q] list`, `paths needs at least one path`, `path <p> is not a repository path`, `path <p> is repeated`). An unknown key is still refused (`unknown key owner`). Do not reject a short `check:` at parse time: c0111 parses `Does it?` and `Is it?`.

### The command

`LESSONS_USAGE`, and the `lessons` row of zz-rules, become:

```
usage: ./zn lessons [--skill <s>]... [--when design|build] [--tag <t>]... [--full] [--for <id>] [--diff] [--paths <p>]... [--mode design|raft|code|stream] [<word>...]
       ./zn lessons --tags | --check | --uncovered [<id>...] | --rounds <id> | --stale
```

`--diff`, `--rounds` and `--stale` are boolean flags, the same way `--full` is (they do not consume the next word). `--for`, `--mode` and `--paths` take one value each; `--paths` repeats like `--tag`. A second `--for` or a second `--mode` exits 2. `--mode` must be `design`, `raft`, `code` or `stream`; any other value exits 2. `--paths` with no value exits 2. The zz-rules row still starts `` | lessons | `./zn lessons `` (c0111). `--tags`, `--check`, `--uncovered`, `--rounds` and `--stale` are exclusive modes. Combining one of them with any other flag, including `--when`, `--skill`, `--tag`, `--full`, `--for`, `--diff`, `--paths` or `--mode`, exits 2. `--stale --when build` exits 2 and does not take `--when` as a value. `--rounds` with no id exits 2. A usage error exits 2, as today. When `z-nile/lesson-areas.md` is missing or `parse` returns a problem, `--for` and `--paths` exit 1 with `lessons: lesson-areas.md is missing` or `lessons: lesson-areas.md does not parse`, and `--check` reports that line. `buildLessons` then passes `paths = nil` and the ready command warns `warning: lesson-areas.md is missing; no path filter`. `--diff`'s own failure stays the diff warning; a missing `origin/main` does not by itself fail `--for`.

`--for` and `buildLessons` select with the union of the table at `origin/main` and the working tree's table: a core tag, mode skill, skill prefix or area prefix present in either table counts. A branch can add a row and cannot drop one. No `origin`, or no `origin/main`, uses the working tree alone and warns `warning: no origin table; using the working tree`. `--check` still validates the working tree's file only. `--for <id>` reads the item (`store`). An unknown id exits 1 with `lessons: no item <id>` and prints no index. Paths come from `touchedModules` in `main.luau` (backticked `` `path` `` bullets under `### Touched modules`). A raft's paths are the union of its members' lists; the raft document itself is not scanned. The project filter is `buildLessons`'s test: keep a lesson whose owner is nil, `z-nile`, or `projectOfRoot(item.root)`. `--mode` sets `exercised` from the mode line in `lesson-areas.md`. `--for` also adds each item's own folder (the issue folder, or for a raft each member folder and the raft folder) to the path list, after the repository-relative check below.

A path is repository-relative when its first segment is a project name in `projects.toml` (`pickman`, `z-nile`) or a root-level file or folder the area table names (`AGENTS.md`, `zn`, `scripts`). `--paths` without `--for` does not apply the project filter: a lesson from any project can match. The decision is text, not a stat of the path. One path that fails this test makes the whole item fall back to `paths = nil`.

- No Touched modules (nil or empty union): pass `paths = nil` (no path filter) and write stderr `warning: <id> has no Touched modules; no path filter`.
- A Touched path that is not repository-relative: pass `paths = nil` and write stderr `warning: <id> Touched path <p> is not repository-relative; no path filter`. Do not also print the empty warning. The item keeps every lesson the project filter keeps.
- `--diff` unions `git diff --name-only origin/main...HEAD` (committed names only). On a non-zero exit, stderr `warning: diff unavailable; --for uses Touched modules only`, and the diff contributes nothing. If Touched modules already supplied repository-relative paths, those paths stay; the filter does not open to every lesson. If they did not, `paths` stays nil and the empty warning also applies. When the diff succeeds and Touched modules were nil or empty, the diff paths are the filter (the empty warning still prints) and they are not discarded.
- `--paths <p>...` unions those prefixes into the same list. With no `--for` and no successful `--diff`, the list is exactly the `--paths` arguments. Zero `--paths` arguments is a usage error. `--paths` does not add an item folder and does not set `exercised` unless `--mode` is also set.
- When any of `--for`, `--diff` or `--paths` was used, stderr also gets `lessons: <n> for <id-or---paths> (<k> core)`. `k` counts selected lessons that matched by a core tag. stdout stays today's index or `--full` text, so a prompt can embed it.

`buildLessons` uses the same repository-relative rule. It passes the union as `paths` when every path is repository-relative and the union is non-empty, and nil when the union is empty or any path is not repository-relative. ### Rewrite, five rounds, metrics

A source is what `lessons.sources` already records, plus `from:` as one source. The introducing commit of a new lesson file is the origin even if that commit also adds `from:` and a harvest line: `beforeCount` is 0 because the id is absent on HEAD. A one-off names no lesson, so it gains no source.

The comparison base is `git merge-base HEAD origin/main`, never HEAD, never `HEAD^1`, and never a branch tip the author can move. One function, `staleSource`, is what `--uncovered <id>`, `--stale` and `./zn commit` use. A source is stale when it is not reachable from that base, it was added after the commit that last changed the lesson's `check:` line, and it is not the lesson's first source. A source added in the same commit that changed the check is not after the check. A lesson introduced on the branch, then given another source by a later commit, is stale: the base count being 0 does not exempt the second source. `since check` is the count of sources that pass `recurred` (after the check, and not the first), with no base test. The count is the ledger source count, not the set of staged lesson files. A lesson file in that same delta that does not parse is `commit: <id> does not parse` from `./zn commit`, and `<id> does not parse` from `--uncovered` and `--stale`. A source that is already on the base, including one that arrived by merging `origin/main`, is not stale. The function does not refuse a harvest line `sources` already ignores.

A source or a fifth review file is in force exactly when the commit that added it has `z-nile/lesson-areas.md` in its tree. A commit from before that file existed is not a failure. `engine.copy` copies `z-nile/lesson-areas.md` (along with the rest of `z-nile/`) into every fixture, and `clearLessons` removes only the `lessons` folders, so once the file exists it is in every fixture's seed; sitting at `z-nile/lesson-areas.md` beside `z-nile/skills/` rather than inside `z-nile/skills/` avoids Lune's `ENOTDIR` on `fs.isDir("z-nile/skills/<entry>/lessons")` and `fs.isFile("z-nile/skills/<entry>/SKILL.md")` in `engine.clearLessons` and the promoted skill specs (`c0111/skill-docs`, `c0114/docs`, `c0115/prompt`, `c0115/readme`, `c0115/skills`, `c0120/docs`). c0111 and c0115 rely on that copy. A case that shows the exemption removes the copied file, commits, and pushes that commit to the fixture's origin before the harvest. The first source of a lesson is its `from:` line when that line is present. Otherwise it is the source whose ledger line was added by the earliest commit: `git log --reverse` on those lines, ancestry first, then commit date. A source is after the check when its commit is a descendant of the commit that last changed `check:` (`git merge-base --is-ancestor`), or the source is new in the index and the check is unchanged from HEAD. A source on a branch and a check change merged from main, neither an ancestor of the other, is not after the check. `git remote` with no `origin` skips the stale check: `./zn commit` succeeds and warns `warning: no origin; stale check skipped`. `origin` present but `origin/main` or the merge base unresolved fails closed: `--stale` exits 1 and `./zn commit` refuses, both with `no merge base origin/main`. That is not the `--diff` warning.

`./zn lessons --uncovered <id>` keeps today's uncovered-finding report and also prints each stale lesson and each unparseable lesson in the delta, and exits 1 if either list is non-empty. `./zn lessons --stale` prints only those delta lines and exits 1 when any exist, and exits 0 on a delta that has none. `z-nile/check.sh` runs `./zn lessons --stale`. On `origin/main` the merge base is `origin/main`, the delta is empty, and the command exits 0, so historical lessons are not rewritten and R0039 is not a gate failure. `./zn commit` on a raft branch uses the same function and the same base, and refuses `commit: <id> gained a source and its check line did not change` or `commit: <id> does not parse`. Prep and stream commits are plain git; they are caught by `--uncovered <id>` at the steps that already require it, and by `--stale` in the gate.

A loop is one of: an issue's own `design-review-NNN.md` files, a raft folder's own `design-review-NNN.md` files, a member's own `design-review-NNN.md` files, or a raft folder's own `review-NNN.md` files. The counts are not added together. Stream files (`stream-review-*`) are not rounds. R0061's members at 4, 3 and 4 are three loops under 5, not one loop at 11. R0062's raft round plus two members at 4 are the same. A raft is reported, and `--rounds` exits 1, when any one of those loops is at least 5 and that loop has no satisfying bullet and note.

The bullet, under a `## Prompt failure` heading, is one physical line:

`- <design|code> rounds reached 5 at <file>: the <capture|design|ready> prompt was unclear: "<quote>".`

`promptFailure` returns every line matching that shape. The `<file>` names the loop: a bullet in the loop's own document satisfies that loop, and a bullet in the raft document satisfies a member loop only when `<file>` contains that member's folder. The harvest line, in the same document's ledger and the same commit, is `- note 5 <design|code> rounds, <capture|design|ready> prompt unclear: <lesson ids>`, which is c0111's note syntax. The step word is the bullet's step word. The ids must be lesson ids that exist. A five-round note is an ordinary source, so the crossing commit changes each named existing lesson's check line, or names a lesson created in that same commit (its first source is the note, so it is not stale). Which skill they are filed under is c0136's rule, quoted above; this issue does not check it. A bullet without that note does not satisfy the loop. A note that names an id that does not exist does not satisfy it.

`./zn lessons --rounds <id>` reads the working tree. For an issue, the design count is `design-review-NNN.md` in its folder and the code count is 0. For a raft, the printed design count is the raft folder's own design-review files and the printed code count is the raft folder's own review files. It prints `rounds: <id> design <n>, code <m>` and exits 0 when every loop of that raft is under 5 or satisfied. It exits 1 with `rounds: <id> <design|code> reached 5 without a prompt-failure note` for the raft's own loop, or `rounds: <raft> <member> design reached 5 without a prompt-failure note` for a member loop. The gate does not run `--rounds` (R0039's own loop would stay red). The author runs it on the item they are committing.

`./zn commit` on a raft branch also refuses, with `commit: <id> <design|code> rounds reached 5 without a prompt-failure note` (and the member id when the loop is a member), when `needsPromptNote` is true for that loop's HEAD count against its index count. A loop that was already at least 5 on HEAD does not refuse. Prep worktrees are not on a raft branch, so `./zn commit` is not available there; z-design and z-raft run `--rounds` and require exit 0 before the review-file commit. That commit is the one that adds the review file, the bullet and the harvest note, including when the verdict is approve. The count that reaches 5 is that document's own loop, not the sum of the raft's members.

Metrics, after the existing review-rounds table, prints two sections and does not exit 1 for a missing note:

```
## Review rounds at 5
- <raft>: design <n>, code <m>; missing
- <raft>: design <n>, code <m>; <the bullet without its leading "- ">
- <raft>: <member> design <n>; missing
- <raft>: <member> design <n>; <the bullet without its leading "- ">

## Lesson recurrence
- <lesson-id>: later <n>, since check <m>
```

A raft line uses the raft folder's own loops. A member line is printed when that member's own design loop is at least 5. `n` and `m` in the raft line are that folder's own counts, not a sum. `missing` means that loop has no satisfying bullet and note. Recurrence lists only lessons with `laterCount > 0`, most later first, then id. `since check <m>` counts sources whose harvest line (or `from:` line) was added after the commit that last changed the lesson's `check:` line. `m > 0` means the lesson recurred after its current check. A source added in the same commit that changed the check counts in `later` and not in `m`. The git walk is the edge (`git log` for the check line, and for each source line). This issue does not rewrite historical lessons and does not edit done rafts. R0039's own loop prints `missing`. R0061 and R0062 do not appear, because no one of their loops is at 5.

## Acceptance criteria

### Checked

- AC1: A lesson is selected for a path when it is core, or its skill is in the mode's exercised set, or its `paths:` prefixes overlap that path, or, with no `paths:`, its tag area or its skill folder overlaps that path, by whole components. `@item` matches the item folder. A nil path list does not filter. `--when` still drops the other phase, core and exercised skills included.
- AC2: `--for` reads Touched modules, a raft unions its members, and an item with none warns and does not filter. A Touched path whose first segment is neither a project name nor a root-level file the table names warns and does not filter. `--diff` unions the committed diff against `origin/main`; when git fails it warns and uses Touched modules only; when it succeeds and there were no Touched modules, the diff paths are the filter. `--paths` with no value exits 2. `--mode` selects the exercised set. Another project's lessons are left out. An unknown id exits 1 with no index.
- AC3: A `paths:` value that is empty, absolute or contains `..` is a parse error naming the lesson. `--check` names an unlisted tag when the tree has folders, a check that repeats the title, and, when the tree has folders, a check of fewer than 4 words. Four words are not that problem. A hand-built tree without folders does not gain an unlisted-tag problem or the word problem. On the real tree every tag is a key, every prefix is a legal path or `@skill` or `@item`, and no problem contains the text `scope`. Today's exact rows are checked by `acceptance/named-areas.luau`, which the gate does not collect. A missing or unparseable area file makes `--for` and `--paths` exit 1 and `--check` report it, and `buildLessons` applies no path filter.
- AC4: A source that is not on `git merge-base HEAD origin/main`, was added after the commit that last changed `check:`, and is not the lesson's first source, is reported by `./zn commit` on a raft branch, by `./zn lessons --uncovered <id>`, and by `./zn lessons --stale`. The comparison counts ledger sources, so a commit that stages only `harvest.md` is included. A source already on the base, including one merged from `origin/main`, is not reported. The first source, a one-off, a source in the same commit as the check change, and a source added by a commit that does not contain `lesson-areas.md` are not reported. A lesson file in the delta that does not parse is reported. No `origin` remote skips the check with a warning. `origin` without a resolvable `origin/main` refuses. Metrics lists each lesson with a later source as `later <n>, since check <m>`, most later first, then id.
- AC5: `./zn lessons --rounds` exits 1 when any one loop (the issue, the raft folder's own design reviews, one member's design reviews, or the raft folder's code reviews) is at least 5 and that loop has no prompt-failure bullet and matching harvest note, and exits 0 when every such loop is under 5 or satisfied. Counts are not summed. `./zn commit` refuses the commit that crosses 5 for that loop without the bullet and the note, and does not refuse a later commit once that loop was already at least 5. Metrics lists each such loop with the bullet or `missing`. Stream review files do not count.
- AC6: The design, code, raft and stream briefs and the author's lessons pass name `./zn lessons --when design --full --for <id>` or `./zn lessons --when build --full --for <id> --diff`, and name `--mode`. Those files still contain `lessons --when design --full` and `lessons --when build`. The rewrite sentence says the same commit changes the check line, and names `--uncovered` and `--stale`. zz-stats names `since check` and still contains `unchanged`.
- AC7: The ready prompt's lesson index uses the same selection, including mode `code`.
