# c0166: Reviewers read only relevant lessons

## Problem
The user, 2026-10-26: "Have reviewers read only the relevant lessons, picked by the files and areas an issue touches, instead of all of them."

And, in the same capture: "It's an important feedback to previous efforts when a review finds an issue, that needs to go back to either the code or the design or prep prompt where the mistake was made or where the prompt was unclear. We need lessons that are actionable, searchable, and effective. They need to support high chance of success. When we hit 5 rounds that's a failure of making it clear what the goal was previously. Make each prompt so clear that 5 rounds of review is rare."

Today zz-review item 10 has every design reviewer run `./zn lessons --when design --full` (about 124 lessons on 2026-10-26) and every code reviewer `--when build --full` (about 62), and ask each lesson's `check` of the draft or diff. There are 131 lesson files, and every harvest adds more, so each review pays to read them all, most have nothing to do with what the issue touches, and the checks that do apply are diluted among the rest. Rafts still reach 5 review rounds (R0039), which means the earlier prompt (capture, design, ready prompt) did not make the goal clear.

What should happen:
- (a) Each design and code reviewer reads only the lessons relevant to the files and areas the issue touches (its Touched modules or diff paths, its project, the skills it exercises), and asks only those `check`s.
- (b) Lessons are actionable (each has a concrete check question), searchable (selectable by path and area, not only by skill, phase and tag) and effective (it is measured whether a lesson stops its defect from recurring, and an ineffective one is rewritten).
- (c) A review finding goes back into the code, design or prep prompt where the mistake was made or which was unclear. c0136 owns that routing (this issue depends on it); this issue relies on it and must not leave it out.
- (d) Five review rounds is rare. A raft that reaches it is treated as a failure of the earlier prompt: it is reported, and traced to the prompt that was unclear.

## Non-goals
- Which skill a lesson is filed under, and sending a finding back to the step that erred: c0136.
- Backfilling past reviews: c0112.
- The lesson file format and `lessons` command as they stand: c0111 (done).

## Solution
- Map touched paths and areas to lessons: a `paths:` or `areas:` field on each lesson, or a tag-to-path table.
- A selector, e.g. `./zn lessons --for <id>` or `--paths <p>...`, that the review brief runs instead of the full `--when` list; a small always-read core (e.g. tags `review`, `process`).
- `lessons --check` flags a lesson no selector can reach (so none goes unread) and one without a concrete `check:` question.
- zz-stats reports review rounds per raft, and lessons whose defect recurred after they existed.
- A raft that reaches 5 rounds gets a note tracing which earlier prompt was unclear, harvested as a lesson for that step.
