## Idea
c0117's dispatcher supports three CLIs, `claude`, `grok` and `agent`, and refuses any other CLI in `.models.toml`. The user runs three more agent CLIs on this machine, and z-nile can dispatch to none of them. They become supported dispatch CLIs, beside the three:
- `agy` (Google Antigravity CLI, `~/.local/bin/agy`): Gemini, Claude (Opus and Sonnet 5.5) and GPT-OSS models.
- `kimi` (Kimi Code, `~/.kimi-code/bin/kimi`): Moonshot's Kimi models.
- `opencode` (`~/.opencode/bin/opencode`): the CLI through which DeepSeek's models are reached. The capture's "deepseek" is this CLI (Q1). Every model opencode reaches is available through it, not only DeepSeek's (Q3).

Each of the three:
- has its own set of models in `.models.toml`, tied to each command and activity as c0261 ties them for every supported CLI, and can appear in `order`;
- has a local runtime with an adapter that runs one model step headless and unattended, reports the step's token count on the spend row (or fails rather than record zero), fails on insufficient quota rather than waiting for more, and obeys c0117's stall and cap rules, as c0117's three adapters do;
- is found by its skills the way prep proves works for it: naming the skill's path in the prompt, as for grok and agent, or the CLI's own skill discovery.

**Who may review through them** (the capture's open review rule, settled by Q2 and Q4). c0175 extends to the three the rule of which model may run a review through each CLI (today `models.reviewRule`: Opus, or grok at xhigh). A final round through any of them runs only on one of c0261's sharp kinds: agy offers Opus, and kimi's kinds are c0261's (k3.1-pro or k3-256k at high or max). A DeepSeek model reviews only middle rounds, as a cheap family in c0251's rotation, and never a final round. Which family runs which round is c0251's. *(Superseded 2026-11-16: any model may run any review; see the Scope decision in the Problem.)*

**z-work in them.** A person can start any of the six by hand and run z-work (c0253). Whichever of c0175 and c0253 lands second proves that z-work runs in agy, kimi and opencode. In the same way, whichever of c0175 and c0251 lands second gives every model of agy, kimi and opencode its `family` for c0251's rotation.

Every z-nile document that lists the supported CLIs (the skills, the README, the root `.models.toml`) names all six: `claude`, `grok`, `agent`, `agy`, `kimi` and `opencode`.

Solution ideas from the capture: add the three to `models.CLIS`, with local runtimes in `models.RUNTIMES` and one adapter each beside c0117's. Their headless routes, from their `--help` (2026-10-31), are still to be probed in prep: `agy -p <prompt> --output-format stream-json --model <id> --effort <level> --dangerously-skip-permissions` with `--print-timeout`; `kimi -p <prompt> --output-format stream-json -m <alias> --auto`; opencode's own. Prep finds whether each stream reports token usage, how each signals exhausted quota, and whether any of them hangs waiting for quota.

Not here: the dispatcher itself and its three CLIs (c0117), remote or cloud runtimes of these CLIs (c0142), making any of them first in `order` (the user's call in `.models.toml`), and which family reviews which round (c0251).

### Scalability
A third CLI costs two table rows and an adapter, as the Design of c0117 intended: the dispatcher already takes any runtime `adapters.get` knows, and `models.forRaft` loops `models.CLIS`. What does not scale by itself is the set of models opencode reaches, which is per machine: it is a pattern, not a list in code (`opencode-<provider>-<model>`), and a provider needs no line: `family.of` places an opencode model by its own model line, so only a new model line needs a `[families]` prefix. The agy effort table is the one list in code (seven prefixes); a new agy model line is a row, and an unknown prefix is left unclamped, so a new model never breaks a try, it can only run at the effort the CLI then accepts or refuses. The session-store readers are a table keyed by runtime in one module; a third store is one function. A step's added cost is zero when the stream counts (the common case) and one bounded subprocess (20 s) when it does not.

### Maintainability
One reader per format and one module per concern (zz-arch): `adapters.luau` stays pure (lines in, counts out), `sessionusage.luau` holds the two store readers behind one function, and `runner.luau` loses its kimi-only branch for a runtime-keyed call (no third `if runtime ==`). Each CLI's token rule is stated once at the head of `adapters.luau` with the probe date and version, so a flag or event rename shows as a failing recorded-line spec, and the E-results in this issue say which lines were recorded from which version (agy 1.5.7, opencode 1.18.31, kimi 2.6.0). The model-id mapping (opencode) and the effort table (agy) are the two places that encode a CLI's own naming; each has one function and a spec that names every form. The fake CLIs in `tests/lib/fakecli.luau` print the recorded shapes, so a dispatcher spec that needs a new CLI starts one.

### Usability
For the user: the six CLIs are named in every document that lists them, in one place per fact (`zz-rules` for the routes and ids, `zz-review` for who may review). A `.models.toml` error names the file, the key and the CLIs that exist (`not a supported CLI (claude, grok, agent, kimi, agy, opencode)`). A spend row records the model and effort that ran (agy's lowered effort is on the row, never one it refused), and an agy or opencode step with no count says `no token count (agy-cli)` on its trail rather than recording a zero. For the executor: every adapter rule has a recorded line and a spec; no probe needs repeating.
