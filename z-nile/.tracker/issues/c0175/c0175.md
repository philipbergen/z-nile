# c0175: Agy, kimi and opencode dispatch CLIs

## Problem
The user (2026-10-31): "add support for "agy" and "kimi" to zile".

c0117's dispatcher supports exactly three CLIs, `claude`, `grok` and `agent` (Cursor), and makes any other CLI in `.models.toml` an error ("a CLI the file does not list is not supported"; `models.CLIS`, `models.RUNTIMES`). The user also runs two more agent CLIs on this machine, and today z-nile can't dispatch a step to either one:
- `agy` (Google Antigravity CLI, 1.4.10, `~/.local/bin/agy`): its models are Gemini, Claude (Opus and Sonnet 5.5) and GPT-OSS (`agy models`).
- `kimi` (Kimi Code, 2.4.0, `~/.kimi-code/bin/kimi`): Moonshot's Kimi models.

What should happen: `agy` and `kimi` are supported dispatch CLIs, beside `claude`, `grok` and `agent`. Each has its own set of models in `.models.toml`, can appear in `order`, and has a local runtime with an adapter. That adapter runs one model step headless and unattended, reports the step's token count on the spend row, fails on insufficient quota rather than waiting for more, and obeys c0117's stall and cap rules, as c0117's three local adapters do. Every z-nile document that lists the supported CLIs (the skills, the README, the root `.models.toml`) names the five CLIs.

User (2026-11-07): "manually start any cli (kimi, agy, claude, grok, agent, deepseek) run a command, z-work."

Added by the user (2026-11-07): **deepseek** is supported too, the same way as agy and kimi, so the documents name six CLIs.

Decided with the user (2026-11-11), idea interview Q1: "deepseek is accessed via opencode" (the capture's sixth CLI is `opencode`, the CLI through which DeepSeek's models are reached; it is supported the same way as agy and kimi).

Decided with the user (2026-11-11), idea interview Q2: "Rotate within sharpness" (c0261 says how sharp a round is and c0251 says which family: a final round takes the first sharp kind (Opus, kimi-k3, grok-xhigh) whose family differs from the author's and the previous round's, and middle rounds rotate the same way among cheap models; this settles who reviews through agy (Opus) and kimi (kimi-k3)).

Decided with the user (2026-11-11), idea interview Q3: "Every model it reaches" (every model opencode reaches is available through it, each tied to activities in `.models.toml` like any CLI's models, not only DeepSeek's).

Decided with the user (2026-11-11), idea interview Q4: "Middle rounds only" (a DeepSeek model is a cheap family in c0251's rotation for middle rounds and authoring and never runs a final round; final rounds stay on c0261's sharp kinds).

## Non-goals
- The dispatcher itself, and the three CLIs it already supports: c0117.
- Remote or cloud runtimes of agy, kimi or opencode (agy `--remote-control`, kimi `web`/`rc`): c0142 is where remote runtimes live.
- Running pickman's game work on these CLIs by default. Which CLI comes first in `order` is the user's call in `.models.toml`.
- Which family reviews which round: c0251.

## Solution
- Add `agy` and `kimi` to `models.CLIS`, with local runtimes (say `agy-cli` and `kimi-cli`) in `models.RUNTIMES`, plus one adapter each beside c0117's.
- Their headless routes, from their `--help` (2026-10-31), still to be probed in prep: `agy -p <prompt> --output-format stream-json --model <id> --effort <level> --dangerously-skip-permissions`, with `--print-timeout`; `kimi -p <prompt> --output-format stream-json -m <alias> --auto`. Prep must find whether each stream reports token usage (else the step fails rather than recording zero, c0117's rule), how each one signals exhausted quota, and whether either one hangs waiting for quota.
- The review rule (c0117 §1: Opus through `claude` or `agent`, grok at xhigh through `grok`) has to say what a `zz-review` spec may be through `agy` (which offers Opus 5.5) and through `kimi` (which has no Opus). That is the user's decision in prep.
- Skills: each CLI's skill discovery (`kimi --skills-dir`, agy's own) decides whether naming the skill's path in the prompt is enough, as it is for grok and agent (c0115 E1).

## Idea
c0117's dispatcher supports three CLIs, `claude`, `grok` and `agent`, and refuses any other CLI in `.models.toml`. The user runs three more agent CLIs on this machine, and z-nile can dispatch to none of them. They become supported dispatch CLIs, beside the three:
- `agy` (Google Antigravity CLI, `~/.local/bin/agy`): Gemini, Claude (Opus and Sonnet 5.5) and GPT-OSS models.
- `kimi` (Kimi Code, `~/.kimi-code/bin/kimi`): Moonshot's Kimi models.
- `opencode` (`~/.opencode/bin/opencode`): the CLI through which DeepSeek's models are reached. The capture's "deepseek" is this CLI (Q1). Every model opencode reaches is available through it, not only DeepSeek's (Q3).

Each of the three:
- has its own set of models in `.models.toml`, tied to each command and activity as c0261 ties them for every supported CLI, and can appear in `order`;
- has a local runtime with an adapter that runs one model step headless and unattended, reports the step's token count on the spend row (or fails rather than record zero), fails on insufficient quota rather than waiting for more, and obeys c0117's stall and cap rules, as c0117's three adapters do;
- is found by its skills the way prep proves works for it: naming the skill's path in the prompt, as for grok and agent, or the CLI's own skill discovery.

**Who may review through them** (the capture's open review rule, settled by Q2 and Q4). c0175 extends to the three the rule of which model may run a review through each CLI (today `models.reviewRule`: Opus, or grok at xhigh). A final round through any of them runs only on one of c0261's sharp kinds: agy offers Opus, and kimi's kinds are c0261's (k3.1-pro or k3-256k at high or max). A DeepSeek model reviews only middle rounds, as a cheap family in c0251's rotation, and never a final round. Which family runs which round is c0251's.

**z-work in them.** A person can start any of the six by hand and run z-work (c0253). Whichever of c0175 and c0253 lands second proves that z-work runs in agy, kimi and opencode. In the same way, whichever of c0175 and c0251 lands second gives every model of agy, kimi and opencode its `family` for c0251's rotation.

Every z-nile document that lists the supported CLIs (the skills, the README, the root `.models.toml`) names all six: `claude`, `grok`, `agent`, `agy`, `kimi` and `opencode`.

Solution ideas from the capture: add the three to `models.CLIS`, with local runtimes in `models.RUNTIMES` and one adapter each beside c0117's. Their headless routes, from their `--help` (2026-10-31), are still to be probed in prep: `agy -p <prompt> --output-format stream-json --model <id> --effort <level> --dangerously-skip-permissions` with `--print-timeout`; `kimi -p <prompt> --output-format stream-json -m <alias> --auto`; opencode's own. Prep finds whether each stream reports token usage, how each signals exhausted quota, and whether any of them hangs waiting for quota.

Not here: the dispatcher itself and its three CLIs (c0117), remote or cloud runtimes of these CLIs (c0142), making any of them first in `order` (the user's call in `.models.toml`), and which family reviews which round (c0251).
