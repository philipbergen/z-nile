### F1 [high] opencode's subagent tokens never reach the count or the cap, and agy's are unprobed
Where: c0175.md Design outcome 3 (`opencodeFeed`, l.174), outcome 4 (l.175), E4 and E7 (l.254, l.257), Guess l.160
Evidence: opencode's `run` loop (binary: `if(B.type==="message.part.updated"){let J=B.properties.part;if(J.sessionID!==W)continue; … if(J.type==="step-finish"){if(Z("step_finish",{part:J}))continue}`) prints the parts of its own session only. A `task` tool call runs a child session (`session.created` with a `parentID`, kept in a set only for permissions), and that child's `step_finish` is never printed. `opencode export <session>` (E7) reads that one session's `info.tokens`. opencode's own prompts push subagents ("Launch up to 3 explore agents IN PARALLEL (single message, multiple tool calls)"). So a DeepSeek implementation step that sends out three explore agents records only the parent's tokens on its spend row, and `acc.live > r.cap` never sees the children: `max_tokens` cannot stop it. The probes' own log also shows a separate small-model title call for each session (`message=stream providerID=deepseek modelID=deepseek-flash … small=true agent=title`), outside every step. agy has `invoke_subagent` and parallel subagents (binary strings: `invoke_subagent`, `_total_subagent_count`, "parallel subagents"). Whether its `result.usage` counts them was never probed: E1's prompts were "reply ok" and "echo hi".
Critique: The Problem asks that each adapter "reports the step's token count on the spend row" and "obeys c0117's stall and cap rules", and the design quotes c0117's "Cap model calls, record real total" to justify having no call cap ("both new CLIs have [a running count]"). With subagents, that running count is incomplete. Ruling 2 ("if agy or opencode print no token usage headless, the runner reads that CLI's own session files") fits this case exactly, because the child sessions print none. The fix the author will reach for is to export the child sessions after the step. That corrects the row, but not the live cap.
Consequences: Turning subagents off changes what opencode can do (no explore agents), so it is a choice for the user to walk through. Reading the children needs their ids (from `--print-logs` `session.created`/`parentID` lines, not yet seen) and one bounded export for each. For agy it needs one tiny probe, or a setting (`AllowedSubagents_Disabled` appears in agy's config proto).
Recommendation: Hold the cap first. Run dispatched opencode with its `task` tool denied or disabled through the step's environment (`OPENCODE_CONFIG_CONTENT`, which the binary reads; a probe settles the key). Record that as a Guess with its cost, add an argv/env spec case, and add a Rules row whose mutant leaves `task` on. If the user would rather keep subagents, count the children instead: `opencodeFeedErr` records the child session ids from the log, the runner adds each child's export after the step (ruling 2), and the Design states the cost that the live cap then sees only the parent. For agy, run one tiny bounded probe that makes it call `invoke_subagent` and compare `result.usage` with its steps, or else disable subagents the same way; either way it is a Guess. In the same probe, either state the title call as a known undercount or turn it off, if opencode's config allows that.

### F3 [medium] One running-tool flag for opencode: the first tool to finish in a parallel batch makes a long sibling look stalled
Where: outcome 3, `opencodeFeed`/`opencodeFeedErr` (l.174); Rules rows M19-M21 (l.355-357); prototype `z-nile/engine/adapters.luau:541-567`
Evidence: `opencodeFeedErr` sets `acc.open["permission"] = true` on any `evaluated permission=` line, and any `tool_use` clears it. Each tool logs its own permission line when it starts (E6; the user's log has them for read, glob, webfetch and bash), with no call id in the line, and prints its `tool_use` only when it is done. opencode tells its models to run tools in parallel ("If the commands are independent and can run in parallel, make multiple bash tool calls in a single message", "Maximize use of parallel tool calls"). Take a step that runs `z-nile/check.sh --full` and a `read` in one message. The read's `tool_use` clears the mark at once, stdout then stays silent while the gate runs, and after `stall_seconds` (300 s) the runner kills the step as `stalled`. That is the false stall E6 was meant to remove. The two pipes are also read by separate tasks, so a fast tool's permission line can arrive after its `tool_use` and leave the mark set. That one is benign: the tool limit applies until `step_finish`.
Critique: The mark models one tool at a time, but the real producer hands over batches. Every spec case feeds one permission line and then one `tool_use`.
Consequences: A counter needs a floor and a reset. A tool that evaluates two permissions (bash plus `external_directory`) keeps the count above zero until `step_finish`. That means the tool limit for the rest of the step, which is bounded and the same as today's out-of-order case.
Recommendation: Count open permissions: +1 for each permission line, -1 (floor 0) for each `tool_use`, back to 0 at `step_finish`. Spec: two permission lines and one `tool_use`, then quiet past the stall limit but under the tool limit, is not stalled; after the second `tool_use` and `step_finish`, no tool is running. Add a Rules row whose mutant is "any tool_use clears every running tool", and add the same parallel case to `runner-cli.spec` (a fake that logs two permissions, prints one `tool_use` and sleeps past the stall limit).
Lesson: zz-test/seed-every-enumerated-case

### F4 [medium] `--print-logs` puts the model's own commands into the stderr that the runner reads for quota and waits
Where: outcome 3 argv (l.174), E6 (l.256), Guess l.161; prototype `z-nile/engine/runner.luau:286-288` and `adapters.finish`
Evidence: With `--print-logs --log-level INFO`, opencode's whole INFO log goes to stderr, and its permission lines quote the command: `message=evaluated permission=bash pattern="sleep 6"` (E6), `pattern=https://opencode.ai` (the user's log). The runner keeps the last 4096 bytes in `stderrTail`. On a stall it calls the step quota when `adapters.mentions(acc.cliText .. "\n" .. stderrTail, adapters.WAITING)` matches, under the comment "only what the CLI itself printed counts as a wait for quota, never the model's words". `adapters.finish` calls a non-zero exit quota when stderr has a QUOTA word, and otherwise names the failure by stderr's last line. So:
- an opencode step working on z-nile that runs `grep -n quota z-nile/engine/adapters.luau` and then fails for another reason ends as `quota`;
- a step whose command contains "try again" or "waiting for" and then hangs ends as `quota` instead of `stalled`: quota moves the chain on to the next try in the half-changed worktree, while stalled stops it;
- a plain failure is named by an INFO line such as `message=loop session.id=…`.

Every opencode case passes `stderr = ""` to `adapters.finish`, and none hands it a log tail.
Critique: The fakes' `prose` mode exists because c0117 pins exactly this rule for claude ("the model's own words about waiting and trying again: a stall after them is a stall, not quota"). This design reopens that rule for opencode without saying so.
Consequences: A filter needs a way to tell log lines from the CLI's own error text. opencode's retry and quota log wording is unknown (F5), so a filter could also hide a real wait line.
Recommendation: For an adapter with `feedErr`, let the adapter say which stderr lines are log lines (for opencode: `timestamp=… level=… run=…`). The runner then feeds those lines only to `feedErr` and keeps the rest in `stderrTail`. Once F5's probe has recorded opencode's own retry log line, `opencodeFeedErr` may set the wait mark from that one line. Spec cases, each with a Rules row:
- a permission line whose pattern says `quota`, then exit 1 with `UnknownError`, ends as `failed`;
- a pattern with `try again`, then quiet past the stall limit, ends as `stalled`;
- a failure is named by the error event's message, not by a log line.
Lesson: zz-test/seed-every-enumerated-case

### F5 [medium] The quota experiments stop at "not provoked", though the binaries answer most of it; a long provider wait ends `stalled`, not quota
Where: E3 (l.253), E5 (l.255), Guess l.167, Implementation step 9 (l.409); agy-adapter.spec `QUOTA` and runner-cli.spec `AGY_QUOTA`
Evidence (from `strings`, no CLI run):
- opencode's `SessionRetry` retries errors that match `429`, `rate limit`, `too many requests`, `resource exhausted|resource_exhausted`, `try again (later|in)` and more, up to `RETRY_MAX_RETRIES=5` times. The delay starts at `RETRY_INITIAL_DELAY=2000` ms and doubles, capped at `RETRY_MAX_DELAY_NO_HEADERS=30000` ms, but a `retry-after` header raises the cap to `RETRY_MAX_DELAY=2147483647` ms.
- The retry is a `session.status {type:"retry"}` event, which the run loop does not print.
- opencode's Zen quota text is `"Free usage exceeded, subscribe to Go"`.
- agy's own changelog strings say "the CLI now waits the delay the server asks for … and stops right away instead of retrying when the delay is longer than 30 seconds or the quota is a daily or billing cap", and show "Model unavailable (attempt 2/10), retrying in 12s".
- agy's internal pattern is `QUOTA_RE = /RESOURCE_EXHAUSTED|quota|\b429\b|exhausted your capacity|rate.?limit/i`.
- `adapters.QUOTA` has none of `resource_exhausted`, `resource exhausted`, `exhausted your capacity` or `free usage exceeded`.
Critique: The Problem and the captured Solution ask prep to find "how each one signals exhausted quota, and whether either one hangs waiting for quota". The Guess's cost ("ends as failed, and the dispatcher still moves to the next CLI; only the trail's word differs") holds for an error. It does not hold for a wait. A provider that answers 429 with a `retry-after` over 300 s makes opencode wait silently, and the runner ends the step `stalled`, which stops the chain (`dispatcher.luau:1206`: only quota and a role's `failed` move on). That is the "waits for quota" outcome the Problem forbids, reported as a stall. The agy quota line in the specs ("RESOURCE_EXHAUSTED: quota exceeded …") is invented, and it passes only because it also contains the word "quota".
Consequences: Adding the words costs nothing. Telling opencode's silent wait apart needs to see what it prints while it waits (perhaps a stderr log line), which stays unknown until probed. If it prints nothing, the stall is the only signal, and the user should know that cost.
Recommendation: Add `resource_exhausted`, `resource exhausted`, `exhausted your capacity` and `free usage exceeded` to `adapters.QUOTA`, with a case for each (agy's `result.error`, opencode's `error.data.message`). Run E5 at no quota cost against a loopback provider: an OpenAI-compatible fake server under `.cache`, named as a custom provider through `OPENCODE_CONFIG_CONTENT`, that answers 429 once without and once with `retry-after: 400`, bounded by `./zn run`. Record stdout and stderr while opencode waits. If stderr shows a retry line, `opencodeFeedErr` marks it as the CLI's own wait, so a stall after it is quota (F4's filter keeps that line). If nothing shows, say in the Guess that a long provider wait ends `stalled` and stops the chain. Record agy's changelog behaviour in E3 (waits up to 30 s, stops on daily and billing caps, retries capacity errors up to 10 times), and replace the invented line with a quoted one.

### F7 [medium] The id grammar narrows Q3's "every model it reaches" without a scope decision
Where: Guess l.164; outcome 1 `opencode` pattern (l.170); Problem Q3 (l.34, l.93)
Evidence: The pattern `^opencode%-[%w_%.]+%-[%w%._%-]+$` and `ledger.isModel` (`^[%w][%w%._%-%[%]]*$`) both refuse `/`, `:` and `@` in a model's name. In opencode's own catalogue on this machine (`~/.cache/opencode/models.json`, 324 providers), 5819 of 9878 model ids contain one of them: all 378 of openrouter's, 416 of vercel's, 84 of huggingface's, 79 of deepinfra's, and more. The three providers this machine reaches today are fully nameable (deepseek 4/4, xai 12/12, opencode/Zen 139/139). No provider name contains `_`, so the rule of writing a provider's `-` as `_` is safe.
Critique: The user turned down "Only DeepSeek" and chose "Every model it reaches: All of opencode's providers become available". The Guess's cost ("a model with a slash is unreachable until the ledger takes one") cuts that decision for whole providers the user may add later, and it does so as a guess. z-design's "Scope is what was captured" needs a `Scope decision` line for that. Today the outcome is met only because of the credentials this machine happens to hold.
Consequences: An encoding keeps the ledger's alphabet, but it makes ids longer and has to round-trip. A scope line needs the user.
Recommendation: escalate to the user, with two options:
1. Keep the grammar and record `Scope decision (user, …)`: models whose opencode name has `/`, `:` or `@` are out until the ledger takes them. Cost: openrouter, huggingface and similar gateways cannot be used through opencode.
2. Keep the full scope with a reversible encoding inside `[%w._-]` (for example, `/` and `:` as two-character sequences, checked to be unambiguous over models.json's names), decoded by `opencodeModel`. Add a spec case for each character and a round-trip case over a sample of real catalogue ids. Cost: ids that are harder to read.

Either way, AC1 and AC4 state the rule.

## Lesson candidates (reviewer's, for the lead)
- zz-arch (a note on liveness-reads-the-first-signal): a running-tool mark that is fed start and end events counts open calls, never a flag, because agent CLIs run tool calls in parallel. Check: what does the mark say after two starts and one end?

- z-design: before marking a CLI's quota, retry or error behaviour "not determined", read what the installed CLI says about itself (its changelog and error strings, `strings` on the binary, its catalogue) and probe it against a loopback provider, which spends no quota. Check: was each "not provoked" unknown tried at zero cost first?
- z-design: probe a new agent CLI inside a throwaway git repository with the dispatcher's PATH, not only in a scratch folder, because a dispatched step always runs in a worktree. Check: what does the CLI write in the repository's git directory, and which git does its shell run?
