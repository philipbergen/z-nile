# c0178: Shared fixture images

## Problem
As captured (2026-10-31): spec fixtures are built from scratch per spec (four repos, ~243 tooling files each as loose objects); build packed images once and clone them, to cut file churn and processes.

The user (2026-10-31), after a full gate pegged fseventsd at a whole CPU core: "This is not acceptable. Find a better solution. Test has to be thorough and complete but also very fast and efficient." And (2026-11-24), after 40-second jobs took 5 to 15 minutes while several workers gated: "why have we built a bottleneck into the process? Can that not be removed".

Measured (c0179, merged as #791, 2026-11-24): one full gate (`z-nile/check.sh --full`, 385 s) makes **1,929,894 file events** under its worktree, **1,927,831 (99.9%) under `z-nile/.cache`**: the Lune spec fixtures. `fseventsd` spends about 124 CPU-seconds on one gate, Spotlight more. A volume's markers (`no_log`, `never_index`) do not make a file cheaper (c0179 E3, E4); fewer files and detaching a volume instead of removing its files do (c0179 E8: removal is half of all events).

What should happen: a fixture costs a few files and processes, not thousands, with every spec case kept and every guard still in force.

Decided with the user (2026-10-31): fewer files **and** a fixture volume fseventsd ignores (c0179); every case stays (thorough and complete).

Decided with the user (2026-11-01), after design review 001 (they stand; the redesign keeps each outcome, see "How the decisions are kept"):
- Scope decision (user, 2026-11-01): "Fix in c0178" for the working tree the eight repository-cloning specs check out: design `--no-checkout` plus the paths each of those specs reads, in this issue.
- Scope decision (user, 2026-11-01): "Convert them" for the 11 hand-built four-repository fixtures: move them onto `trackerfix.new` / the shared builder, with their overrides.
- Scope decision (user, 2026-11-01): "Drop it": the in-process `c0120/finished` part is removed from c0178; no issue picks it up.
- Decided with the user (2026-11-01): "keep your choice" for the `fixture.check` memo: only the home's physical path is memoised per process.
- Decided with the user (2026-11-01): "keep it, with your reason stated" for the clones that copy their packs instead of hardlinking them.
- Decided with the user (2026-11-19): "go ahead and update the test to match" (the old harness spec's line count). The redesign has no such spec; nothing is left for it to change.
- Decided with the user (2026-11-01): `noLessons` for worktree-heavy specs is not taken (it conflicts with G7, the user's 2026-10-21 decision).

Redesigned 2026-11-24 from the experiments below (the design of 2026-10-31/11-18, its acceptance specs, its check file and its prototype are removed from this folder; they are in git at `5e8f5eaa4:z-nile/.tracker/issues/c0178/`). Three of its choices are now known to be wrong or superseded: `cp -cR` copies one file event per file (c0179: about 2,031 events for a 1,020-entry tree, against 2 for one `clonefile(2)`); removing a passing spec's fixtures costs one event per entry, which is half of all events; and its "Interface for c0179" assumed a fixture volume c0179 did not build.

## Non-goals
- Changing what any spec case proves, or dropping a case: every case stays, and every spec keeps the paths it uses today.
- The Go tests' fixtures (c0179 did them).
- Moving run state (the lock, the durations, the results file) off the home's `.cache`, or the board, `measure.tsv` and the live daemon's files in the root's `.cache`.
- `fseventsd` markers on any volume (c0179 refuted them).

## Solution
1. **Clone, never rebuild** (slice 1): `trackerfix.new` makes its fixture by one whole-tree `clonefileat(2)` of this run's packed template (built once per run, lessons choice and tooling state), rewrites the nine files that name the template's path, and then gives the fixture its own identity and seeded files with one amended seed commit, so a spec sees what it sees today.
2. **Detach, never remove** (slice 2): a gate-driven run on macOS mounts a throwaway RAM disk over its home's `.cache` for the run and detaches it at the end, so no fixture file is ever removed one by one; every other run keeps today's `.cache`.
3. **The user's 2026-11-01 scope** (slices 3 and 4): the hand-built four-repository fixtures move onto `trackerfix.new` (and so onto the template), and the repository-cloning specs write fewer files.

## Design

### What the experiments decided (summary; the numbers are in Unknowns & experiments)
- The fixture helper to cut is `trackerfix.new`, and only it: its fixtures (plain, and inside `netfix.world`) hold **98.9%** of the entries the suite leaves under `z-nile/.cache` (E1: 706,679 of 714,809 entries in 82 of 144 fixture folders of a fully gated worktree); `engine.copy`'s own users 0.5%, live fixtures 0.1%, the rest 0.5%. The repository-cloning and hand-built four-repository specs are in the slow tier (`z-nile/tests/slow.tsv`), outside the full gate's 1.93 million.
- A trackerfix fixture is about 7,983 entries (a seed 2,244, a bare origin 1,240, `main` 2,249, `other` 2,249); 61% of them are loose objects (1,222 per repository, hardlinked between the four), 37% the three checkouts of the tooling (E2). Building it costs about 10,450 file events; removing it about one event per entry; git's temp-file-and-rename writes make a loose object cost about three events.
- One `clonefileat` of a template, plus the rewrite, costs **about 40 events per fixture** against 10,454 for a build (E2), works inside the spec jail (E4), never shares an inode or a write with its template (E3), and fails across volumes (`EXDEV`, E6).
- In a whole spec file the fixture is only part of the cost: the spec's own commits, pushes and `./zn` worktrees stay. With the full slice 1 (packed template, index refresh, packed pushes into the origin) the steady-state events of the three heaviest spec files fall by 77%, 61% and 58% (light-path 225,599 to 51,305; models-dispatch 112,318 to 43,500; f0399/land 81,361 to 34,024) (E5), and **the removal of the previous run's fixtures becomes about half of what is left** (54%, 51% and 37% of the three heavy spec files' steady-state events).
- A per-run RAM disk over the home's `.cache` makes that removal free: detaching it logs next to nothing (light-path on the volume: 162,395 events for the mount, the run and the detach together, against 156,942 for the run's creates on disk; with slice 1, 23,744 against 225,599 today: E7), and the run on it costs only its creates. It needs no admin rights, mounts in 0.4 to 0.9 s, detaches in 0.1 to 0.5 s (once a 10 s detach, once `Resource busy`, once an 11 s staging unmount: Spotlight's first look at a new volume), and leaks nothing measurable into the kernel zone (E6).

### Slice 1: `trackerfix.new` from a per-run template
**Shared and per case.** What is shared is one **template** per (run, lessons choice, tooling state); everything else is per case, as today.
- *The template*: `<home>/.cache/fixture-templates/<run>-<lessons|nolessons>-<tooling key>/`, holding `origin.git`, `main` and `other` exactly as `trackerfix.new` makes them today for a fixture named `fixture-template` with no seeded files, except: the seed's objects are packed (`git repack -adq` and `prune-packed` in the seed before the bare clone, so each repository holds one pack, hardlinked by git's local clone), the seed folder is not kept (no spec reads `<base>/seed`: `git grep` over every spec and every sequestered acceptance folder finds the word only in hand-built fixtures' own folders), and the bare origin has `receive.unpackLimit=1` in its local config (a push into it lands as one pack, not one loose object per object: c0179's receive-side cut; the checkouts' own configuration is untouched, so the product's own fetches and commits are as today).
- *`<run>`* is the basename of the run's own temp folder (`$TMPDIR`, `pickman-run.XXXXXX`, fresh per run and the same for every worker of the run, nested runs having their own). A template is never used by another run: the first `trackerfix.new` of a worker removes every template folder of another run (they can only be left by an earlier run: the lock lets one run per home at a time) from inside the jail.
- *The tooling key*: one `perl` walk of the files `engine.copy` copies (`zn`, `scripts/`, `z-nile/` minus `engine.STATE` and its skills, then the skills), hashing each relative path, mode, size and mtime (no file is read), about 1,000 `lstat`s. Called on each `trackerfix.new`, it gives a new template when a tooling file changed after the template was made, which is what a fixture sees today (it copies the tooling at its own time). A change that keeps size and mtime is the one it misses (a tool that restores mtimes); see Risks.
- *Who builds it, when*: lazily, by the first `trackerfix.new` that needs it in any worker of the run, inside the jail. It builds in `<template>.build.<random>`, rewrites that build's own nine path-naming files to the final path (E5 found this the hard way: a template built in one folder and renamed names the build folder), then publishes by `rename(2)`. A worker that loses the rename removes its build and uses the winner's (at most one duplicate build per concurrent worker, 8 lanes). `trackerfix.builds()` counts this process's builds (a spec seam).
- *Never handed to a spec, and checked before each clone*: `trackerfix.template(noLessons)` returns its path (a seam for this ticket's spec); no `Fixture` field names it. After the rename the builder writes `<template>.stamp` beside it; before every clone `trackerfix.new` runs `find <template> -newer <template>.stamp -o -cnewer <template>.stamp` (stats, no reads) and raises `trackerfix: template changed: <path> (a spec wrote into <template>); every later fixture of this run refuses` when anything changed. Modes are left writable (c0179 had to give up read-only modes for a cache the product checks: here a frozen mode would be cloned into every fixture and a fixture must be writable).

**The clone step.** One helper, `z-nile/tests/lib/fxclone.luau`, `fxclone.tree(src, dst, opts?: { copy: boolean? }): "clone" | "copy"`: on macOS one `perl -e 'syscall(462, -2, $src, -2, $dst, 0)'` (`clonefileat` with both folders `AT_FDCWD`; the number is macOS's and is called only when `$^O eq "darwin"`, never on Linux, where 462 is another call), inside the jail, from the spec's own process; where it fails (`ENOTSUP`, `EXDEV`, any error), or on Linux, or with `copy = true`, `cp -a --reflink=auto` on Linux and `cp -Rp` elsewhere, and the result says `"copy"`. It refuses a destination that exists (`clonefileat` does: `EEXIST`, E3; the copy path checks first) and raises naming both paths. It is the only place that copies a fixture tree.

**The rewrite list** (exact, from E3: the files of a fresh template that name the template's absolute path, and the same nine in every fixture), held as `trackerfix.REWRITE`:
`main/.git/config`, `main/.git/logs/HEAD`, `main/.git/logs/refs/heads/main`, `main/.git/logs/refs/remotes/origin/HEAD`, the same four under `other/.git/`, and `origin.git/config` (its `remote.origin.url` names the seed). Each is rewritten by replacing the template's path, as a whole path (followed by `/`, a space or a line end, never a prefix of a longer name), with the fixture's, through a sibling temp file and `rename(2)`. `origin.git`'s remote then names `<base>/seed`, a folder that does not exist (it existed before; no spec reads it, and git reads it only for a fetch inside the bare origin, which no spec does).

**After the clone** (all through `fixture.git`/`fixture.exec`, so every command is checked as today): `git update-index -q --refresh` in `main` and `other` (a clone has new inodes and ctimes; without it `git add -A` freshens every object and `reset --hard` rewrites every file: E5 measured 16,015 of 44,942 events from that alone); the identity in `main` and `other` (as today); the seeded files written into `main`, `seal.stamp(main, name)`, `git add -A`, `git commit -q --amend --reset-author -m seed` (one seed commit, authored and committed by `<name>@example.invalid`, holding the tooling and the seeded files, as today); `git push -q -f origin HEAD:main`; in `other`, `git fetch -q origin` and `git reset -q --hard origin/main`. 13 git processes and 2 `perl` (today 79 processes, the 2026-11-01 measure).

**The guard** "any file in a cloned fixture that names the template's path is on the rewrite list" is this ticket's spec case `template.spec :: the rewrite list is exactly the files of a fresh template that name the template's own path`: it greps a fresh template for its own path and compares the list with `trackerfix.REWRITE`, so a git version, a template step or an engine write that names the path somewhere new fails it, naming the file; and `:: no file of a cloned fixture names the template or a template build folder` greps a whole fixture.

**Cleanup (slice 1 alone).** No change: a fixture stays after its run, and the next `trackerfix.new` of the same name removes it (`fs.removeDir`, one event per entry), as today; a template of an earlier run is removed by the first fixture of the next run. A packed fixture is about 2,200 entries plus what its spec made, against about 7,980 plus. The 2026-10-31 design's per-spec sweep is not built: it costs the same removal events, only sooner (E8 in c0179).

### Slice 2: the per-run fixture volume
**Decided by E6 and E7: use it, for gate-driven runs on macOS only.** After slice 1 the removal of the previous run's fixtures is 54%, 51% and 37% of the three heavy spec files' steady-state events of a heavy spec file's events, and a detached volume removes nothing.
- *Where*: mounted **over the whole `<home>/.cache`**, so every fixture path a spec names today (`.cache/<name>`, 225 of 410 spec files under `z-nile/tests` spell one) is on it with no spec edit. A mount under a sub-folder would need every fixture path to move (the 2026-10-31 "Interface for c0179"); a mount elsewhere would need a new jail rule. E6: the jail's rules match by path, so a volume mounted at `.cache` is written exactly like the folder (writes inside allowed, outside denied, a symlink at its top refused, the mount point itself not removable), `pwd -P` of a path on it is the same path (so `fixture.check` passes unchanged), and git's ceiling and the sentinel are paths too.
- *Who, when*: the outermost runner's top process (`z-nile/tests/lib/fence.luau`'s `enter`, outside the jail), only when `fxvolume.wanted` says so: macOS, not a guarded (nested or worker) run, `hdiutil` present, and `PICKMAN_FIXTURE_VOLUME=1`, which `z-nile/check.sh` exports for the spec stages it runs (`--affected`, `--full`, `--slow`, so `./zn finish`, `done` and the merge gates). A run by hand (`lune run tests/run -- <file>`) and every check.sh run keep their fixtures on disk as today, so a failing spec can still be read afterwards by running it alone. Order, inside `enter`, after the stale-volume sweep and `takeLock` and before the snapshot: `hdiutil attach -nomount ram://<sectors>`, `newfs_apfs -v <name> <dev>`, `diskutil mount -mountOptions nobrowse -mountPoint <runTemp>/fx-stage <volume>`; on the staged volume write the lock folder's records (a copy of `tests-run.lock`), `spec-durations.tsv`, `.metadata_never_index`; `diskutil unmount`, then `diskutil mount -mountOptions nobrowse -mountPoint <home>/.cache <volume>`, `mdutil -i off <home>/.cache`. A second run of the same home therefore always sees a lock: the disk's before the mount, the volume's copy after it. The fence's sentinel and the link sweep then run on the volume as on the folder.
- *What is carried out*: after the launcher returns (the specs' group is gone), the top process copies `spec-durations.tsv` and the `PICKMAN_RESULTS` file (the orchestrator's, `z-nile/specs.luau`) into the run temp, detaches, and moves them into the disk's `.cache` with `replace-file.pl` (a rename, never through a link). Nothing else on the volume survives the run: that is the point.
- *Detach*: `hdiutil detach <dev>`, retried every 0.5 s for 30 s (E6: a fresh volume was once busy for 10 s while Spotlight looked at it), then `hdiutil detach -force <dev>` (the specs' group and the sweeper are done; a straggler's open file is what force exists for). A detach that still fails prints `fixtures: volume <name> could not be detached: <error>; ./zn reap detaches it` and fails the run.
- *Naming and stale volumes*: the volume is named `znfx-<pid>-<start key>` (`fxvolume.name`: the top process's pid and an 8-hex digest of its kernel start record, `fence.startOf`; at most 63 characters). At the start of every run (before `takeLock`), and in `./zn reap`, `fxvolume.stale` lists the mounts whose mount point is exactly this home's physical `.cache`, whose `diskutil info` says `Protocol: Disk Image` and whose volume name starts `znfx-` and names an owner that is gone (pid gone or start key changed): each is detached with `-force`. Nothing else is ever detached: not another home's, not a live run's, not a volume without the prefix, not a real disk (AC5's cases).
- *Size, and a full volume*: `ram://16777216` (8 GiB). E7 measured 344 MiB in 70,664 entries for light-path with today's fixtures and 120 MiB in 30,956 entries with slice 1 for light-path on it and the RAM it takes (a RAM disk takes memory as it is written, not at attach: the free pages fell by about the used size during the run and came back at the detach). A full gate's fixtures were 3.0 GB on disk before slice 1 (E1: the leftover of a fully gated worktree), and slice 1's clones share their template's blocks. A full volume makes a spec's write fail with `ENOSPC` (E6: `dd` stopped at 61 of 100 MiB on a 64 MiB volume, small files still fitted); the top process reads `df` before the detach and prints `fixtures: volume <name> was full (<used> of <size>): a failure above may be that` so a full volume is never silent.
- *Lifecycle*: per run, never per checkout or machine (a per-checkout volume would keep the previous run's fixtures and remove them file by file again; a machine-wide one would share fixtures and locks between worktrees). A crash or `kill -9` of the top process leaves the volume mounted (its RAM held) until the next run of that home or `./zn reap`; a reboot discards it (a RAM disk), and the disk's lock is taken over as today. Two worktrees gating in turn each make their own (the machine-wide gate queue runs one gate at a time).
- *Fallback*: `fxvolume.wanted` false, or any step failing before the mount: the run goes on with the disk's `.cache` exactly as today, saying `fixtures: volume not used (<reason>)` once (only when the gate asked for one). Nothing needs admin rights (E6: no step asked for a password).

### The spec-facing interface
Unchanged: `trackerfix.new(name, seed?, opts?)`, the `Fixture` table (`base`, `origin`, `main`, `other`, each the same path as today), `tr`, `trOk`, `elsewhere`, `stub`; `netfix`, `live`, `engine.copy`, `clone.isolated` unchanged in slices 1 and 2. No spec file changes in slices 1 and 2. What a spec can see differ:
- `<base>/seed` does not exist (no spec reads it).
- The fixture's repositories hold one pack each instead of loose objects; the origin keeps pushes as packs.
- `main`'s reflog has a `commit (amend)` entry after the clone's; `other`'s has `fetch` and `reset` entries; the origin holds the template's original seed commit as an unreachable object.
- The index's stat data is refreshed once at creation.
- With slice 2, in a gate-driven run, nothing a spec wrote under `.cache` exists after the run (by hand, as today).
- Timing: a fixture takes about 0.8 s (E5's `pack2`, under load 7 to 10; a build took 4 to 6 s in the 2026-11-01 measure), the first of a run about 2.7 s (it builds the template).
`removeDir` does what it does today. Rollout: slice 1 changes one helper, so every one of the 87 spec files that build a trackerfix or netfix fixture gets it at once; there is no per-spec switch. The safety net is that every such spec still runs in the merge's gate and this ticket's AC3 compares every passed case with the base.

### Scalability
A fixture costs one `clonefileat` (2 file events however large the tooling grows), nine small rewrites, and the spec's own seeded files and commits; the template is built once per run, per lessons choice and per tooling change. The tooling key is about 1,000 `lstat`s per `trackerfix.new` (a few milliseconds). The volume costs about 0.5 s at the start and 0.2 s at the end of a gate's spec stage, and holds a run's fixtures in RAM; its size is fixed at 8 GiB of sparse RAM disk.

### Maintainability
One place copies a fixture tree (`fxclone.tree`), one list names the files to rewrite (`trackerfix.REWRITE`, guarded by its case), one module decides about volumes (`fxvolume`: pure over `mount` and `diskutil` text, so its decisions are specced without a disk). The template is today's builder run once, so `trackerfix`'s shape has one definition.

### Usability
Nobody does anything new. A gate prints `fixtures: volume <name> (<size>) mounted on <home>/.cache` and, at its end, `fixtures: volume <name> detached (<used> used)`; a run by hand prints nothing new. A failed gate's fixtures are gone with its volume: run the failing spec by name to keep them.

## Risks and what review should watch
- **Shared state between cases.** The template is shared by every fixture of a run; a spec that writes into it (by a path it should not have) would poison every later fixture. The `-newer` check before each clone turns that into a loud failure of the next fixture, naming the path; the spec case writes into it on purpose.
- **A spec that relied on a fresh build's side effect**: the seed folder, loose objects, a reflog with only the clone entry, the seed commit's exact author time, or the index's stat data. Found none by `git grep`; AC3's passed-case comparison over the whole suite is the net.
- **Order dependence**: the first fixture of a run builds the template (2.7 s instead of 0.8 s), so a spec's first case is slower than its others; no spec asserts timing (zz-test forbids it).
- **Stale templates after the tooling changes mid-run**: the tooling key changes and a new template is made; a change that keeps size and mtime is missed (a tool that restores both). Today's builds would have seen it.
- **EXDEV**: a template and its clones must be on one volume; both are under `.cache` (disk or volume). `fxclone.tree` falls back to a copy on any clone error, so a mixed layout is slow, not wrong; AC2's numbers catch a silent fallback on macOS.
- **The syscall number**: 462 is `clonefileat` on macOS only; on Linux x86-64 it is another call. `fxclone` checks `$^O` and `process.os`; review checks no path reaches the syscall off macOS.
- **A volume that will not detach**: a process still holding a file. Retried, then forced; a failure fails the run and `./zn reap` detaches it later.
- **Kernel memory**: no measurable change per make and detach (+135 over 20 cycles) or per spec file between modes (E5); AC3 compares the zone per suite.
- **The lock across the mount**: a second run reads the lock on whichever `.cache` it sees; the staged copy closes the window. A waiting run holding a file open on the volume makes the plain detach fail, and the force then drops its handle: the waiting run's next read fails and it reads again (review checks `lockRecords` survives a vanished file).
- **What a gate hides**: during a gate-driven run, anything a check.sh put in the home's `.cache` before it is hidden under the volume; only the gate's own spec stages ask for a volume, and the gate puts nothing there first.
