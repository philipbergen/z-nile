### F1 [high] The shared, writable git template is checked per spec file, so in a concurrent run the wrong file is failed, and harness.spec's own case writes into the live run's template and plants hooks in other specs' fixtures (repeat of design-review-001 F10 and design-review-002 F6)
Where: Design, Decisions "*Template folder (F10, F6 of round 2)*"; `fence.enter` (`GIT_TEMPLATE_DIR="$3/git-templates"`, one folder per run); `run.luau` `templateExtras()` after each file; harness.spec "a spec that writes into git's template is named, the template is restored, and the run fails"; Rules row "git's template"
Evidence: Every worker of a concurrent run is `lune run tests/run -- --jobs 1 <file>`. It inherits the one `GIT_TEMPLATE_DIR` (the coordinator's `env` adds `PICKMAN_WORKER` and `PICKMAN_TALLY` to the inherited environment). Each worker checks that folder after its own file, and the first worker to look reports and removes whatever is there.
The harness case's nested run overrides only `PICKMAN_JOBS`, `PICKMAN_WORKER` and `PICKMAN_TALLY`, and it is `guarded`, so `fence.enter` returns early. It asserts `git template changed: {template}/hooks/post-checkout` with `template = process.env.GIT_TEMPLATE_DIR` of the outer run, which proves its nested spec writes `hooks/post-checkout` and `description` into the template the whole gate is using.
In a full gate the window runs from that write until the nested runner's check. During it:
- any worker that finishes a file prints `FAIL <its file>: git template changed: …`, removes the entries, keeps its fixtures and fails the run. The nested runner then finds nothing, exits 0, and the harness case fails `expect(code).toBe(1)`. Two innocent failures, while the culprit passes.
- any worker that runs `git init` or `git clone` copies the hook into a fixture for good. I ran this with plain git and a shared template folder. A clone made while `hooks/post-checkout` and `description` were present printed `hint: The '…/b/.git/hooks/post-checkout' hook was ignored because it's not set as executable.` After the template was restored, `ls b/.git/hooks` still showed `post-checkout` and `description` still held `x`. Every later `git checkout` in that clone printed the hint again on stderr.
A real stray write behaves the same: a spec's leftover process writing after its file ended, or a bug in a spec. That failure is pinned on whichever file finishes next.
Critique: this is the third round to find a hole in the one run-wide template folder: shared and writable (round 1), read-only and unremovable (round 2), now checked by every worker at once. The check cannot attribute a write it shares with seven other processes, and the spec that tests the check is itself a writer. The tempting fix is to give only the harness case its own `GIT_TEMPLATE_DIR`. That removes the self-inflicted flake but leaves the misattribution and the contamination for any real write. The restore also removes entries one by one under `hooks/` and `info/`, reading through them with `fs.isDir`. On a run with no jail (Linux), a `hooks` replaced by a symlink makes the runner delete the link target's files.
Consequences: a template per spec file means the runner, not the launcher, owns the folder. Processes that outlive their file keep a path to it, so the folder must outlive the file. It must also not be reused.
Recommendation: question the mechanism. Give every spec file its own template. In `run.luau`'s per-file loop, before loading the file, make `<TMPDIR>/git-templates.<pid>.<n>/{hooks,info}` and set `process.env.GIT_TEMPLATE_DIR` to it, so it reaches every child of that file only. After the file, check that folder alone: any extra fails that file, named. Leave the folder in place for the run temp's removal: no per-entry deletes, and nothing is reused. The launcher's folder stays only as the default for processes outside any file. Cases (harness.spec):
1. An in-process run of two files (`--jobs 1`), where the first writes `hooks/post-checkout`: only the first is named, and a `git init` in the second has an empty `.git/hooks`.
2. A nested `--jobs 2` run of the same two files, where the writer sleeps after writing and the other file inits after it: only the writer is named.
3. After the existing case, the outer run's `$GIT_TEMPLATE_DIR/hooks` is still empty.
Rules row mutants: "one template for the run" and "check the run's folder, not the file's". Update the AC4 text with them (F5).
Lesson: zz-arch/several-writers-check-the-subject

### F2 [medium] `clone.isolated` leaves the clone's `origin` pointing at the shared repository image, so a push from a fixture lands in the image and every later clone inherits it
Where: `clone.luau` `clone.isolated` (`from = clone.image()` for this checkout, no remote change after the clone); Design "The rule" ("nothing a spec does to the fixture can reach the image"); Non-goals ("a cheaper setup that makes the same state"); `z-nile/lib/fence.sh:11` (the pre-push guard covers pushes into the real repository only)
Evidence: I ran a probe spec under the runner in the scratch copy. It called `clone.isolated(root, dest)` with no `paths`, committed, and ran `git push -q origin HEAD:refs/heads/rv3-pushed`, which printed `ok=true`.
- `git config remote.origin.url` in `dest` printed `…/z-nile/.cache/images/repo-d7c9d0b67c5833ad8b8973fd/repo.git`.
- `git show-ref refs/heads/rv3-pushed` in the image printed `695095080d… refs/heads/rv3-pushed`.
- A second `clone.isolated(root, again)` listed `origin/rv3-pushed` under `git branch -r`.

Before c0178, `origin` was the real repository, so the fence's pre-push hook refused such a push. All 13 callers in the repository run `git remote remove origin` right after the clone (`git grep -n '"remote"'` over them), and c0122's sequestered specs clone a fixture origin, not this checkout, so nothing does this today.
Critique: the image is shared by every spec of every later run until HEAD moves, and its key (root and HEAD) cannot see a change made to it. One spec that pushes, or fetches into `origin`'s config, changes what every other spec starts from, with no error. The rule the Design opens with does not hold for this image. `remote.origin.url` is also part of the state the Non-goal promises is unchanged. The tempting fix is `remote remove origin` inside `clone.isolated`. That changes state the 13 specs don't read today, and a spec of an unlanded prep may read it.
Consequences: restoring the old URL also restores the old reads: `git fetch origin` in such a clone reads the live repository, as before c0178.
Recommendation: after cloning from the image, run `git remote set-url origin <source>` (through `fixture.git`), so the clone's state is what a direct clone made and the pre-push guard refuses a push as it did. Case (clone-image.spec): a clone of this checkout has `remote.origin.url` equal to the checkout; a push to `origin` from it fails under the runner; the image's `show-ref` is unchanged. Rules row: mutant "origin left at the image".

### F3 [medium] The launcher prunes a folder it spells itself, and the source pin passes with the prune aimed anywhere: a mutant that prunes the home survives
Where: `fence.luau` `pruning.run(\`{cache}/images\`)`; `images.dir()` ("The one place that decides where images are; nothing else builds an image path"); `engine.luau` `registerFixture` (`.cache/images` again); Design "Interface for c0179" (five places spell the home's `.cache`); harness.spec "the launcher prunes the images once, under the run's lock and before any spec starts"; Rules row "pruning"
Evidence: in the scratch copy I changed the call to `pruning.run(here) -- MUTANT`, which makes the unjailed launcher prune the project home, and ran `lune run tests/run -- tests/acceptance/c0178/harness.spec.luau`. The result was `12 passed, 0 failed, 1 spec files`. The pin counts `pruning%.run%(` and orders it between `takeLock(lock)` and `local argv = {`; it never reads the argument.
The launcher's literal is a second spelling of `images.dir()`, and `registerFixture` holds a third. c0179's interface lists five places that read the fixture root, and these two are not among them. If c0179 moves `images.dir()`, the launcher keeps pruning the old folder, the new folder is never pruned, and no case notices. Images then pile up without bound, one per tooling change.
Critique: this is the one recursive removal the runner makes outside the jail. The Design names it as the runner write review must check, and its target is the one argument nothing pins. The tempting fix is to call `images.dir()` from `fence.luau`. That makes a cycle, because `images.luau` requires `fence` (for `fence.startOf` and `fence.alive`).
Consequences: the folder's location needs an owner that both `fence` and `images` can require: `pruning.luau`, which has no dependencies, or a small module of its own.
Recommendation: move the location into `pruning` as `pruning.dir(home)` (`<home>/.cache/images`). `images.dir()` returns `pruning.dir(<physical cwd>)`, the launcher calls `pruning.run(pruning.dir(here))`, and `registerFixture` asks `pruning.dir`. Add it to c0179's list as the sixth place.
Replace the source pin with a behavioural case. In a nested home under `.cache` with its own `.cache/images` (a nested launcher is refused, so run `pruning.run(pruning.dir(home))` the way the launcher does), plant an old `seed-<24 hex>` image there and an old `x.lock` folder in the home. The image goes and the home's folder stays. Keep a pin only for the call's exact text, `pruning.run(pruning.dir(here))`, and name that text in the Design. Rules row mutants: "prune given the home", "prune given `.cache`".
Lesson: zz-test/pin-call-site-arguments

### F4 [medium] Two more specs that run `done` clone sparsely with no tooling in their lists, and the table says they list it; the hand-kept lists are still the mechanism (repeat of design-review-002 F8)
Where: Design "Per-spec clone paths" (row "`c0008/done-order`, `c0074/done-gate`, `c0080/consequences`, `c0038/deferred`, `c0116/promote`, `c0120/promote-home` … none (they list their tooling)"); Decisions "*Tooling lists (round 2 F8)*"; overrides.spec "the specs that list their own tooling list its folders"; `z-nile/engine/main.luau:4075-4076` (`done`'s `rollback()` is `git reset -q --hard HEAD`)
Evidence: c0038's `paths` are eight tracker entries. c0120/promote-home's are 23 entries with no `zn`, no `scripts/`, no `z-nile/lib/` and no `z-nile/engine/`. Both commit the overlay with `git add -A --sparse` and both run `tr({ "done", "R0010" })` (c0038:64, c0120:224). c0116/promote has `tooling = true`, which is not "none". I ran this in a scratch repository: after a `--no-checkout` clone with `sparse-checkout set --no-cone /keep/`, an overlay `scripts/` committed with `git add -A --sparse`, then `git reset -q --hard HEAD`, `ls w/scripts` gave `No such file or directory`.
No current case reaches a rollback in these two specs. The first raft whose change makes `done`'s gate or promoted spec fail in one of them will see the rollback delete `zn` and `scripts/`, and every later case will fail with a missing `scripts/tracker.sh` instead of the real cause. The Design's promise that "a raft that adds a folder a spec reads fails that spec loudly, naming the path" will not hold there. overrides.spec checks only three of the five specs that run `done`.
Critique: the round-2 fix went spec by spec, and the table and the pin were written from that short list. The tempting fix is to add the four folders to c0038 and c0120 and two names to the pin. Then the next spec that clones sparsely and runs `done` repeats this.
Consequences: the overlay already writes every tooling file to disk, so making it part of the sparse set costs no file.
Recommendation: question the mechanism. Make the overlay part of the sparse set in one helper, `clone.overlay(root, dest)`: the `ls-files -co` copy of `engine.PATHSPECS`, then `git sparse-checkout add` of the overlay's top paths after the spec's commit. Git then finds the files already on disk and writes nothing, and every reset keeps the tooling. The tooling entries leave the six lists, and the overrides case pins that every cloning spec that overlays calls the helper. If the lists stay instead, give c0038 and c0120/promote-home the same four folders, correct the table row, and make the overrides case cover every cloning spec that runs `done`. That set comes from a search pasted in the Design (`git grep -ln '"done"' -- <the 13 files>`).
Lesson: z-design/new-rules-migrate-existing-work

### F5 [medium] The sequestered AC4 and three Design passages still describe what round 2 replaced: a read-only template and a dead-lock takeover
Where: `check.sh` AC4 and c0178.md AC4 ("make no sample hook from a template [that] a write cannot change"); Decisions "*The lock (F7)*" ("a waiter that finds the owner dead renames the lock to `<id>.lock.dead.<random>` and retries, so exactly one builds"); Test plan `images.spec` ("a dead owner is taken over at once"), `harness.spec` ("git's template is empty, read-only")
Evidence: the Modules text and the prototype say "no takeover … a few duplicate builds at worst" (`images.luau` breaks out of the loop on `ownerDead`). Decisions F10 says the template "stays writable". `grep -n "read-only\|cannot change\|taken over\|exactly one"` over c0178.md and check.sh finds the four places above.
Critique: AC4's label is sequestered: no one may edit it during execution. Its label then promises something the code does not do (a write *can* change the template; it is detected afterwards), and a code reviewer judging the label against the code has to rule it unmet. An executor who reads Decisions F7 builds the takeover that round 2 removed because it could delete a live lock.
Consequences: none beyond the text, but F1 changes AC4's wording again: write it once, after F1.
Recommendation: rewrite AC4 in both files to the checked behaviour, for example "…make no sample hook, and a write into a spec file's git template fails that file, naming it". Rewrite Decisions F7 to the no-takeover rule. Correct the two Test plan lines. Then grep for the replaced words again.

### F6 [low] `swept.register` compares the runner's own names case-sensitively on a case-insensitive volume: `.cache/Images` and `.cache/TESTS-RUN.LOCK` are accepted
Where: `swept.luau` (`OWN[segment]`); harness.spec "swept refuses…"; Rules row "swept"
Evidence: I ran a probe spec in the scratch copy (APFS, case-insensitive here: `ls -d /Users/philipbergen/code/pickman/Z-NILE` resolves). `pcall(swept.register, HOME .. "/.cache/Images")` returned `true`, and so did the call for `/.cache/TESTS-RUN.LOCK`. `fs.isDir(".cache/Images")` was `true`, and `swept.pending()` listed both. A sweep then removes the images folder mid-run (round 2 F1's race) or the run lock with its pid records. A helper gets there from a spec-chosen name (`trackerfix.new("Images")`, a `clone.isolated` destination).
Recommendation: compare `string.lower(segment)` with the lower-case names, and refuse a first segment with any byte outside ASCII, since normalisation forms differ too. Add `<cache>/Images` and `<cache>/TESTS-RUN.LOCK` to the refusal case, with the mutant "names compared as typed".

### F7 [low] `trackerfix.worktrees` judges `origin/<name>` from refs main has not fetched, while `./zn worktree` fetches first
Where: `trackerfix.worktrees` (the `show-ref --verify refs/remotes/origin/<name>` loop runs before anything fetches)
Evidence: in a probe spec in the scratch copy, `f.other` pushed `HEAD:refs/heads/raft-taken` to origin. `main sees origin/raft-taken before: false`. Then `trackerfix.worktrees(f, { "raft-first", "raft-taken" })` returned two paths. In the second, `raft-taken@{upstream}` gave `fatal: no upstream configured`, while `./zn worktree raft-taken` would have tracked `origin/raft-taken` (`branch --track`). The helper made a branch that is not fresh, without the refusal its docstring promises.
Recommendation: before judging, run `git fetch -q --prune origin` in `f.main` through `fixture.git`, which is what `cmd.worktree` does first. A worktrees.spec case: a branch another clone pushed to origin is refused, naming `refs/remotes/origin/<name>`.
