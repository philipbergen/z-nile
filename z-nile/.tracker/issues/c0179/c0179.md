# c0179: Meter file events, and fewer files in Go tests

## Problem
The user (2026-10-31), after a full gate pegged fseventsd at a whole CPU core: "This is not acceptable. Find a better solution. Test has to be thorough and complete but also very fast and efficient."

Measured 2026-10-31: one worktree's `z-nile/.cache` changed 10,711 files in 10 s during a full gate (`find -newer`, so files made and removed inside the window are not even counted); fseventsd ran at about 80-100% of a core and `mds_stores` at about 35%. The z-nile suite is 1265 cases in 183 files, about 1,850 s of spec time and 185-230 s of wall time idle (up to 1,800 s under load); `c0116/claims` and `c0120/finished` take about 175 s each idle and set the floor. c0175's capture ran the full gate three times (about 6 min each) and still lost the race to main.

macOS logs every file change on the main disk in fseventsd and Spotlight indexes it, so the specs' throwaway fixtures under each home's `.cache` cost a CPU core even after c0178 cuts how many files they write.

What should happen: on macOS, spec fixtures live on a volume that fseventsd doesn't log and Spotlight doesn't index, made without admin rights; where it is missing (Linux, CI, a new machine) fixtures fall back to `.cache` as today. Every guard (the jail, the fence, `fixture.check`, the sentinel) follows the fixture root and still fails closed.

Decided with the user (2026-10-31): "Yes, and fewer files": the volume and c0178.

## Non-goals
- Cutting files per fixture: c0178.
- Moving run state (the lock, durations, the board) off `.cache`.

## Solution
**Superseded by the 2026-11-24 experiment (see Design, Verdict): the volume does not cut `fseventsd` CPU. The bullets below are the original idea, kept for the record.**
- `./zn fixtures-volume`: a sparse APFS disk image (`hdiutil create -type SPARSE -fs APFS`, no admin) attached `-nobrowse` at a fixed per-user path, with `.fseventsd/no_log` and `.metadata_never_index`; run by `setup.sh`, re-attached by `./zn` when missing.
- `fixtures.root()`: `<volume>/<checkout id>/<home>/` when attached, else `<home>/.cache/`; specs take fixture folders from `fixtures.dir("<name>")` instead of a literal `.cache/<name>`, and the gate's unique-literal rule becomes a unique fixture name.
- The jail profile, `fixture.check`, the sentinel `.git` and `cachepaths.ALLOWED` take the fixture root by physical path.
- Experiment first: an FSEvents watcher on the volume sees nothing during a fixture build, and `mds_stores` ignores it; fallback a RAM disk with the same markers.

## Design

### Verdict (the experiment decided it)
**Do not build the fixture volume.** These volume settings (`.fseventsd/no_log`, `.metadata_never_index`, a RAM disk, a sparse image) do not cut `fseventsd`'s cost on this machine (E3, E4); detaching a volume instead of removing its files, and where the folder sits, were untested when this verdict was written (E8 and E9 below test them, and change nothing here): with `no_log` set, a live FSEvents stream on the volume still receives every event (6,082 events on each of the main disk, a plain image, a no_log image and a RAM disk for the same 3,000-file workload), and `fseventsd`'s CPU-seconds per file written are the same on the RAM disk with both markers as on the main disk (about 60 to 75 microseconds per file; E4). `no_log` only skips the write of the log pages (131 log files on the plain image, none with `no_log`), which is not where the CPU goes. Sparse images are worse: 3x to 8x slower wall time for the same CPU-seconds (E4). Spotlight's `mds`/`mds_stores` showed no response to the workload on any volume (E4: idle control already 100 to 260% for `mds_stores`, from other sessions), so there is no measurable `mds` gain to promise either.

What the experiment did find (E5, E6): Go tests are a very large source of file events (197,458 events in `$TMPDIR` in 70 s from `go test ./internal/host ./cmd/zn`, about 2,800 a second), and no volume trick removes them. The cure that works is the other half of the user's 2026-10-31 decision: fewer files (c0178 for the Lune specs, and the same idea for the Go tests: one template built once per package, which `internal/host/host_test.go` already does for one fixture and the rest do not).

So this ticket changes from "make a volume" to **"meter the file-event load, and spend the c0178 budget where the events are"**. The owner decides at `## Open to the human` whether to retitle and keep this ticket for that (recommended), close it as refuted, or still build the volume for another reason (isolation only, never for CPU).

### What this ticket delivers instead (slim)
1. `z-nile/scripts/fsevents-meter.sh` (a shell script around an FSEvents client in Swift (about 85 lines), source kept beside it and built on first use into `.cache/bin/`; see Open to the human): a read-only meter that, for a command run under `./zn run`, prints the number of file events under each root it names (`<home>/.cache`, `$TMPDIR`, `~/Library/Caches/go-build` excluded) and the CPU-seconds `fseventsd` spent over the same window (cumulative `ps -o cputime=` delta; one idle control window of equal length printed beside it). It is the script the acceptance criteria call. macOS only; elsewhere it prints `meter: not available on this host` and exits 0.
2. Per-package Go test fixtures built once (a `TestMain` template and `cp -R` / `git clone --local` per test) in `z-nile/go/internal/host` and `z-nile/go/cmd/zn`, the two packages the experiment measured; the numbers decide whether other packages follow.
3. The measured top writers of the Lune specs (from the meter, per spec file) are c0178's input, not this ticket's work.

The meter is only a reading tool: it writes nothing but its own report under `.cache/`, never touches git, and takes no part in the gate's verdict.

### Answers to the questions the brief asked (for the record, with the experiment's evidence)
- **Can the volume be delivered first, alone?** Technically yes: mount it at `<home>/.cache/fx` and point `TMPDIR` for the run at it needs no spec edits for the TMPDIR part (the jail already allows the run's own TMPDIR, `tests/lib/fence.luau` `profile`), but the `.cache/<name>` fixtures (72 spec files carry the literal) would still need `fixtures.dir`. It would not remove the cost, so the question is moot. `depends_on: [c0178]` stays: fewer files is the cure, and this ticket's meter measures c0178's gain.
- **One volume per machine, checkout or run; who creates and removes it?** Not built. If the owner still wants one: per checkout, a RAM disk (no admin: E1) attached by the runner's top process before the jail starts, mounted at `<home>/.cache/fx` (inside the jail's allowed path: E2), detached by the same process at the end and by `./zn reap` after a crash. Never per machine (two worktrees would share fixtures and the lock), never the gate's own job.
- **Guards if it were built** (all hold with the mount inside `.cache`, E2): jail: the profile's `(allow file-write* (subpath <cache>))` already covers a mount point under it, and a volume mounted outside `.cache` is denied (E2); fence: `GIT_CEILING_DIRECTORIES` and the `.cache/.git` sentinel are untouched, since fixtures stay under `<home>/.cache/`; `fixture.check`: it compares `pwd -P` to `<cwd>/.cache/`, and a path on the mount resolves to the same prefix, so it passes unchanged; `cache-paths`: its reviewed list is of lines that name `.cache`, so it changes only if a script mounts; one suite per checkout: the lock lives in `.cache`, unchanged; tripwire: unchanged. Because nothing is built, no test is added for them here.
- **Fallback** (Linux, CI, no `hdiutil`, full disk, failed mount): fixtures stay under `.cache` exactly as today with one line `fixtures: volume not used (<reason>)`; never a hard failure. Stated for completeness; not built.
- **Go tests' temp trees:** they do contribute heavily (E5, 197,458 events in 70 s for two packages). They would move with `TMPDIR` only if a volume helped, and it does not, so the lever is fewer files per test (slice 2).

### Scalability
The meter reads two folders' event counts and one daemon's cumulative CPU; cost is one FSEvents stream per root for the length of the measured command. The Go change reduces file operations per test from "build a repository" to "copy a template"; it scales with the number of tests, not with the gate's parallelism.
### Maintainability
No new guard, no volume lifecycle, no new fallback path to keep honest. The meter is one script with one spec on its parsing (a pure function over two `ps` samples and a count). The Go template follows the pattern already in `host_test.go`.
### Usability
Nobody has to do anything: no setup step, no mount to forget, no leftover volume after a crash. The owner gets one number (events a second, `fseventsd` CPU per 100,000 files) to watch c0178 against.

## Unknowns & experiments
Run 2026-11-24 (Pacific, about 00:10 to 01:00), on the owner's Apple-silicon Mac, in `.worktree/c0179-design/.cache/exp/` (scratch, never committed), every command under `./zn run`. **The machine was busy with other sessions throughout (load average 8 to 32, `mds_stores` 100 to 260% of a core and `fseventsd` 0 to 26% in the idle controls).** Per-run CPU percentages therefore carry a spread of tens of points and are trusted only where a ratio or a count is deterministic (E3, E4's CPU-seconds per file, E5). Nothing needed admin rights or a password.

Mounts before: 13 lines of `mount`, 1 disk image (an iOS simulator runtime); after: the same (`mount` list identical, `hdiutil info` shows only that image). All volumes detached; image files deleted.

**E1: which volumes can a plain user make, and where can they mount?**
- Sparse APFS image: `hdiutil create -type SPARSE -fs APFS -size 4g` 1.0 s, `hdiutil attach -nobrowse -noverify -mountpoint <dir>` 0.2 s. Mounts at a path under the worktree's `.cache`. Mounted `apfs, local, nodev, nosuid, journaled, noowners, nobrowse`. No admin.
- RAM disk: `hdiutil attach -nomount ram://2097152` returns a device owned by the user (`brw-r----- philipbergen`); `diskutil erasevolume APFS <name> <dev>` 1.7 s works WITHOUT admin and mounts at `/Volumes/<name>`; `diskutil unmount` then `diskutil mount -mountPoint <dir under .cache> <diskNsM>` 0.2 s remounts it inside `.cache`. `newfs_apfs` directly on the device failed (`Resource busy`, because the erase had already made the container); not needed. `ram://N` is 512-byte blocks; 2,097,152 gave 1.0 GiB, held in RAM.
- Other filesystems on a RAM disk (HFS+, ExFAT) also mount without admin (E3 uses them). The MS-DOS attempt did not mount at a custom path (not pursued).
- Case: both are case-insensitive APFS like the main disk (`diskutil info`: personality `APFS`, git `core.ignorecase=true`, `touch A; touch a` gives one file). `noowners` is on for both (files appear owned by the user, as on the main disk for the user).

**E2: git, the jail and path resolution on the volumes** (script `exp/e.sh`, `exp/jail.sh`)
- Hard links (`2 links`), symlinks, modes (chmod 755 and 000), FIFO, AF_UNIX socket bind, `flock` (perl, LOCK_NB), a 444-character path (6 levels of 60-character names), `git init`/commit/`git mv F f`/`clone --no-hardlinks`/`clone --local` (objects hard-linked, link count 2) and `git worktree add`: all work, on the RAM disk and on the sparse image, same as the main disk.
- The jail (the `sandbox-exec` profile shape from `tests/lib/fence.luau` `profile`: deny writes under `/`, allow `subpath <.cache>`): a write to a file on the RAM volume and on the sparse volume mounted under `.cache` is **allowed** (`WRITE-OK`, as on the main disk); with a profile that allows only `/private/tmp/zzz`, the same write is **denied** (`Operation not permitted`). So the sandbox decides by the mount-point path and a volume mounted inside `.cache` is inside the allowed path; one mounted elsewhere would need its own allowed entry. `realpath`, `pwd -P` and Python's `realpath` of the mount point all return the same path under `.cache` (no `/Volumes` resolution), so `fixture.check` (`pwd -P` against `<cwd>/.cache/`) would pass.

**E3: does `no_log` / `.metadata_never_index` / `mdutil` stop the event stream?** A small FSEvents client (`exp/fsw.swift`, file-level events on one path) counted events while 3,000 files in 100-file folders were written and removed on each volume (8 s window):

| volume | events seen |
|---|---|
| main disk (`.cache/exp/main`) | 6,082 |
| sparse, no markers | 6,082 |
| sparse, `.fseventsd/no_log` | 6,083 |
| sparse, `no_log` + `.metadata_never_index` | 6,082 |
| RAM disk APFS, both markers | 6,082 |
| RAM disk HFS+ | 6,048 |
| RAM disk ExFAT | 12,163 |

Every filesystem tried delivers every event to a client; `no_log` changes only the daemon's own log: after the workloads the plain image's `.fseventsd/` held 131 log pages and the `no_log` ones held only the `no_log` file. `mdutil -i off <mount>` and `mdutil -d <mount>` both **worked without sudo** on a user-mounted volume (`Indexing and searching disabled.`), and a volume `.Spotlight-V100` appeared anyway.

A second set with a RAM disk (no_log + never_index), three runs: main 35/49/48 % `fsevents`, 7.0 to 9.4 s wall; RAM 42/49/26 %, 5.7 to 14.5 s; sparse no_log 34/37/30 %, 8.1 to 14.8 s. Too noisy to read.

Reading: `fseventsd` spends the same CPU-seconds for the same files on the main disk and on the RAM disk with both markers (about 10 s per 160,000 files, 60 to 75 microseconds a file). The sparse image looks lighter as a percentage only because it is 2x to 8x slower in wall time (files-phase 12 to 16 s against 4 to 6 s on the main disk in the 40,000-file runs); its CPU-seconds are the same or higher. `mds` and `mds_stores` show no response to any case (the idle control is at their level), so nothing here shows a Spotlight gain from a volume; the spread (`mds_stores` idle 97 to 264%) is other sessions. **Trust: ratios and counts yes, single percentages no.**

**E5: where do the events come from?** Same FSEvents client, watching `$TMPDIR` (`/private/var/folders/.../T`) and the checkout's `z-nile/.cache` during real work:
- `go test -count=1 ./internal/host ./cmd/zn` (70 s wall, passed): **197,458 events under `$TMPDIR`**, about 2,800 a second, from two packages alone (Go's link and test work folders plus each test's `t.TempDir`/`os.MkdirTemp`; the Go build cache under `~/Library/Caches` is outside the watched root).
- Lune specs `tests/tooling/board.spec.luau`, `tests/acceptance/c0057/guard.spec.luau`, `tests/acceptance/c0082/cli.spec.luau` from `z-nile` (175 s wall of which most was waiting for the machine-wide gate queue; 32 cases passed): 138 events under `$TMPDIR` and **0** under `z-nile/.cache`, which is not understood (the same client saw 5 events from 5 files written there by hand, and the run wrote `.cache/spec-durations.tsv`); the Lune side needs a re-measure on a spec that builds fixtures before c0178 relies on it.

**E6: kernel memory** (`zprint | awk '$1=="data.kalloc.1024"{print $7}'`). Baseline readings 808,287 / 808,292 / 808,276 (two seconds apart, stable). Five `hdiutil create` + attach + detach cycles of a sparse image: 808,261 to 808,226 (-35). Five RAM-disk attach + erase + detach cycles: 808,172 to 806,463 (-1,709). So neither mounting nor detaching a volume leaks into that zone. The per-case readings in E4 moved by about -1,000 to +4,580 around the runs, in both directions and equally on the main disk (-1,043, -399, -448, +25), which is other sessions' activity, not the volume. The largest rise (+4,580) was a sparse no_log run that took 67.8 s while the load average was 12 to 10; a leak per run on a volume cannot be excluded or shown at this noise (another gate was running).

**E7: space, full disk, reboot, crash, session end** (reasoned from the above; not run because the volume is not built). A RAM disk lives only until detach or reboot, and a crash leaves it attached (a leaked RAM disk holds its memory until `hdiutil detach`), so the owner of a mount must detach on exit and the reaper must find strays by name; a sparse image survives reboots on disk (stale fixtures) and grows to its `-size` ceiling, and a full image fails writes inside the specs. The `.cache` of this machine's main checkout is 2.9 GB in total (Go build cache and built binaries included), which is the order of what a RAM disk of 1 to 2 GiB would have to hold on top of the fixtures; one gate's peak fixture size was not measured (no read-only window on a running gate).
