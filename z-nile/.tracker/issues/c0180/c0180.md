# c0180: Affected selection by command, end to end final

## Problem
The user (2026-10-31), after a full gate pegged fseventsd at a whole CPU core: "This is not acceptable. Find a better solution. Test has to be thorough and complete but also very fast and efficient."

Asked for a speed target, the user (2026-10-31): "Is a hybrid possible? Running the tests in process and only running affected tests while working through the design code and review, then once it's all done the final gate is running all tests properly end 2 end".

Measured 2026-10-31: one worktree's `z-nile/.cache` changed 10,711 files in 10 s during a full gate (`find -newer`, so files made and removed inside the window are not even counted); fseventsd ran at about 80-100% of a core and `mds_stores` at about 35%. The z-nile suite is 1265 cases in 183 files, about 1,850 s of spec time and 185-230 s of wall time idle (up to 1,800 s under load); `c0116/claims` and `c0120/finished` take about 175 s each idle and set the floor. c0175's capture ran the full gate three times (about 6 min each) and still lost the race to main.

Today every spec calls the tracker and `./zn` as subprocesses (`bash scripts/tracker.sh` -> `bash zn` -> `lune`, plus the guards: about 20-40 processes a call, about 837 call lines), and any z-nile change outside `z-nile/tests/` forces z-nile's full suite (`z-nile/affected.luau`), so every build and review gate of tooling work runs everything end to end.

What should happen: while designing, building and reviewing, the gate runs only the affected specs, with the engine called in-process; the final gate runs every spec end to end, as today. An in-process pass never counts as the final gate.

Decided with the user (2026-10-31), relayed by the ZNILE_TESTLIMIT session and folded into c0165: "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected."
- The full gate runs once per raft: zz-rules Merging step 2 runs `z-nile/check.sh --full` in a clean clone of the exact final head, right before `gh pr merge`. Captures keep `./zn land`'s full gate, because that is their merge.
- Every gate before it is `--affected` (here, in-process): zz-execute Phase 0's baseline, Phase 3 steps 2-3, Phase 4 step 1 (the author), zz-review code mode item 1 (the reviewer), Phase 5 step 2 (after merging main), `./zn done`'s gate on the done tree (affected plus its promoted-spec checks), and the raft `check.sh` template's RC0 (`--project {{PROJECT}} --affected`).
- So `done` no longer runs the full gate. Gate placement itself is c0165's to build; c0180 makes the gates before the merge in-process and keeps the merge gate end to end.

Scope decision (user, 2026-11-01), after prep measured the in-process driver (calling the engine in-process saves about 0.17 s per `./zn` call: about 27% of `c0005/worktree`, but about 5% of the 3,166 s z-nile suite, whose slowest specs spend most of their time building fixtures and running git, c0178's work; it needs about 190 file paths, 190 subprocess calls, 154 outputs and 11 exits in `main.luau` reworked; and every tracker spec reaches the engine through `main.luau`, so an engine change would still select about every tracker spec): "Select by command (Recommended)": "Re-scope c0180: keep ./zn as a subprocess; split main.luau into one module per command, record during each full end-to-end run which commands each spec invoked, and let --affected run only specs that used a changed command. Engine work then runs a handful of specs instead of ~100. Records your decision line; same 'full e2e at merge' rule."
- So the in-process driver (`run(argv, ctx)`, `fixture.zn`, `ZN_SPEC_DRIVER`) and its experiments are out of scope; `./zn` stays a subprocess in every run, and every run (affected or full) is end to end.
- The gate-placement decision above stands, without its "(here, in-process)".

Scope decision (user, 2026-11-01), on the title after design review 001 F10: "Rename (Recommended)": the title becomes "Affected selection by command, end to end final"; the slug stays `hybrid-inprocess-gate`.

Decided with the user (2026-11-01), on how the split lands (about 11 open branches edit `main.luau`, among them the active rafts R0052, R0056, R0059 and R0061): "All at once, after active rafts (Recommended)": "Split all 37 commands in one go, but c0180's raft is readied only when no active raft changes main.luau (checked with ./zn busy at z-ready). Other branches port their edits by hand when they merge main. Full selection gain from day one."

## Non-goals
- Reusing results of identical content: c0165.
- Fixture construction and the fixture volume: c0178, c0179.
- The in-process driver (`run(argv, ctx)`, `fixture.zn`, `ZN_SPEC_DRIVER`): out of scope by the user's decision of 2026-11-01.
- Narrowing selection for the rest of `z-nile/` (the gate, the templates, the skills, the lessons): those still force z-nile's run.
- Gate placement (which step runs `--full`): c0165.

## Solution
`./zn` stays a subprocess in every run (the Scope decision). `main.luau` is split into one module per command; each multi-file spec run records which commands every passing spec ran; an affected run that asks for the records selects, for a change to the engine's Luau files, only the specs that require, declare or ran the changed code, and every other spec stays selected as today. The full gate at the merge stays end to end. (The in-process ideas added to this section after the capture were dropped by the Scope decision; the capture's Solution was empty.)

## Design

### Overview
Three parts, in the order they run:
1. **Command modules.** `z-nile/engine/main.luau` keeps argv parsing, the `READ_ONLY` set, the repository guard and a dispatch table; each of the 37 commands moves, with the helpers only it uses, to `z-nile/engine/cmd/<name>.luau`; the helpers two or more commands use move to sixteen shared modules beside the existing ones in `z-nile/engine/`. No command's behaviour, output, refusal or exit code changes.
2. **The command trace.** When `ZN_SPEC_TRACE` is set, the engine records the command it is about to run (`usage` for none or an unknown one) as an empty file in each `.cache/spec-trace/<name>` directory the variable lists. The spec runner gives every spec file of a multi-file run its own trace directory, and after the run merges each passing spec's commands into `<home>/.cache/spec-commands.tsv`, keyed by a hash of the spec's test-side require closure and of the tooling that launches `./zn`.
3. **Selection by command.** In c0165's `select.luau`, when the records are loaded (`--recorded`), a change to an engine Luau file (`z-nile/engine/**/*.luau`) that no program requires no longer forces z-nile's full run. It is an input of a z-nile spec when the spec requires it, declares it, is `*`, has no matching record (fail closed), or ran a command whose module closure (plus the dispatch core) contains it. Because c0165's fingerprints use the same `isInput`, reuse follows the same rule. Without `--recorded` nothing changes.

Product decisions relied on (quoted from the Problem): "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected." (2026-10-31); "Select by command (Recommended)" (2026-11-01); "All at once, after active rafts (Recommended)" (2026-11-01). This issue changes no gate placement: c0165 builds that, and every run stays end to end.

Rules (each pinned by AC1 on the real tree):
- **One module per command.** For every command `main.luau` dispatches, `z-nile/engine/cmd/<name>.luau` exists (the file name is the command name, `raft-plan.luau` and `worktree-prune.luau` included), and it returns one function `cli.Handler = (pos: { string }, opts: cli.Opts, usage: string) -> ()`; `main.luau` passes `USAGE` as `usage` (only `new` reads it, for its `fail(usage)`), so no module requires `main.luau` and `USAGE` stays where `c0120/docs` and `c0116/docs` read it. Every file in `cmd/` is a dispatched command. No module defines `cmd.<name>`.
- **Lazy, literal dispatch.** `main.luau` maps each name to a function that runs `require("./cmd/<name>")` with a literal path (so the graph scanner sees the edge and nothing else loads), for example `new = function() return require("./cmd/new") end`.
- **A thin core.** The dispatch core is the require closure of `main.luau` without the edges into `cmd/`: exactly `main.luau`, `cli.luau` and `z-nile/lib/sh.luau`. A change to anything else in the engine therefore never selects every command by itself.
- **No command module is named `usage`**: that name is the trace's record of the usage path (part 2).
- **Only `main.luau` and command modules require a command module**, and nothing requires `main.luau`. `raft-plan --apply` runs `fold` and `new` in its own process (today through the `cmd` table); `cmd/raft-plan.luau` requires `./fold` and `./new` with literal requires and calls them from a table of those two, refusing any other name (`raft-plan: cannot run <name>`), so its closure holds their code and a change to `cmd/fold.luau` also selects the specs that ran `raft-plan`. No command is run through a computed name, and `raft-plan` is the only command module that requires others (exactly `./fold` and `./new`, AC1). The shared modules form no cycle (the graph's closure from each `cmd/` module terminates; `guard`/`boardrefresh`'s only cycle is broken by `mainguards`).
- **No other behaviour changes.** Every command's stdout, stderr, exit code and file effects stay as they are. The whole existing suite is the regression guard (the raft's RC0, and the merge's full gate).
- Module-level cells move with their only users (`guardedRun` into `guard`, `seeded` into `stamps`, `originSpend`/`originChecked` into `cmd/metrics`); no new module-level mutable state.
- `z-nile/engine/projects.luau` stays self-contained (it requires no new module): `c0120/ci` and `c0114/gate-cover` copy it alone into fixtures.
- Local-name collisions (`cmd.stamp` against the `stamp` helper, `cmd.audit` against the `audit` module local, and `board`, `spend`, `status`, `lessons`, `skills` likewise) are resolved inside each command module by naming the required module `<name>Lib`, as `main.luau` already does for `statusLib`.

The split is mechanical: the code of every function moves unchanged except for the `local x = require(...)` lines each new module needs, one alias line per shared helper a module uses (`local fail = cli.fail`, so the bodies stay byte-identical), the `cmd.<name> = function` header becoming `return function`, and `raft-plan`'s two calls (above). E11 prototyped exactly this.

**Changes to `main.luau` that land during execution.** The readiness check (step 1) waits until no active raft changes `main.luau`, but a raft readied later may still land a `main.luau` change while c0180 runs. When a merge of `origin/main` brings one, the executor ports it by hand into the module that now holds that code (the split's layout says which), re-runs `split.spec` and the whole z-nile suite, records it in the Verification log as a deviation, and lets the code reviewer read that port beside the moved text. Implementation step 2 does it as one commit of moves only, so the review reads it as moved text (`git diff --color-moved`).

### 2. The command trace
**Engine side** (`main.luau`, before the dispatch table is consulted, so before the usage path, the guard and the handler):
- `ZN_SPEC_TRACE` unset or empty: nothing happens (every interactive and gate use).
- Otherwise it is a `:`-separated list of directories. Every entry is checked before anything is written. An entry is accepted only when its physical path (`pwd -P` run in it, one process per entry) equals the entry as given, which rules out `.` and `..` components and any symlinked component, and that path ends `/.cache/spec-trace/<name>`, the shape the runner makes (`<name>` one path component). `.cache` folders are ignored by git everywhere in the repository, so no such directory is tracked, whatever folder the checkout lives in. Any other entry (relative, missing, a file, outside a `.cache/spec-trace/` folder, reached through `..` or a link) refuses before the command does anything, with exit 2 and `zn: ZN_SPEC_TRACE entry <dir> is not a .cache/spec-trace/<name> directory by its physical path` on stderr.
- The name recorded is the command name when the dispatch table holds it, and otherwise `usage`: no command and an unknown command both run `main.luau`'s usage path, which is the dispatch core's code. No command module may be named `usage` (AC1).
- It then writes an empty file `<dir>/<name>` in every entry with `sh.writeReplacing` (the reviewed writer: a sibling temporary file and `rename(2)`, which never writes through a link). A failed write refuses: exit 2, `zn: cannot record the spec trace in <dir>: <error>`. The trace fails closed: a run of the engine that left no trace is impossible.
- A command that fails after the trace (any `fail`, refusal or error) has still been recorded, which is what selection needs: the spec exercised that code.
- The variable is inherited by everything the command starts, so a nested `./zn` (a `check.sh` the `check` command runs) is traced too. The write sits in `main.luau`, so every way of starting the engine's CLI is traced: `./zn`, `scripts/tracker.sh`, and the specs that run `lune run <root>/z-nile/engine/main` directly (`c0052/new-spacing`, `c0052/renumber`, `c0114/registry`, `c0114/roots-cli`, `tooling/migrate-odd`). Engine code that runs without the CLI (a program that requires an engine module) is covered by part 3's program rule instead.

**Runner side** (`z-nile/tests/run.luau`, only in `runConcurrently`, the path that already records durations):
- Before starting a file's worker, the coordinator creates a fresh directory `<home>/.cache/spec-trace/<n>-<random>` (`<n>` the file's index; refused if it exists) and starts the worker with `ZN_SPEC_TRACE=<physical dir>` followed by `:<inherited value>` when the runner itself inherited one. A nested run (a spec that runs a gate in a copy of the tree) therefore records into its own directories and into its outer spec's.
- After the worker exits, the coordinator lists the directory: every name matching `^[a-z][a-z%-]*$` is a recorded command; every regular file, of any name (a leftover `.<name>.pickman-tmp.<pid>.<rand>` from a killed write included), is removed; then the directory is removed, never recursively. If the directory can't be removed (something other than a file is in it), the runner prints `tests/run: could not remove <dir>` on stderr and goes on; the run's outcome doesn't change.
- After every worker, alongside the durations, it merges a record for every home spec file (`tests/…`) whose worker exited 0 with `N passed, 0 failed` into `<home>/.cache/spec-commands.tsv`, using a temporary file and a rename, exactly as the durations record is written; a failed write is ignored (it costs selection precision, never correctness, see below). A failing spec keeps its earlier record. A full run (no files named) drops the lines of spec files that no longer exist. The keys come from one call of `lune run z-nile/recordkey -- <repo-relative spec paths>`, run from the repository root (the parent of the home) after the workers end.
- The one-file and `--jobs 1` path creates no directory and writes no record (as for durations), but an inherited `ZN_SPEC_TRACE` passes through to the spec untouched.

**The record format** (`<home>/.cache/spec-commands.tsv`, one reader: `z-nile/lib/commandrecord.luau`):
```
# spec commands v1
tests/acceptance/c0005/worktree.spec.luau	3f9c…(64 hex)	find,list,new,prompt,start,worktree,worktree-prune
tests/meta/architecture.spec.luau	a01b…(64 hex)	-
```
- The first line is exactly `# spec commands v1`. The text ends with a newline, and no line is blank. Each other line has three tab-separated fields: a path starting `tests/` and ending `.spec.luau`; a 64-character lowercase hex key; `-` or a comma-separated, sorted, duplicate-free list of names matching `^[a-z][a-z%-]*$` (`usage` among them). A spec appears at most once. `commandrecord.parse` refuses a file breaking any rule (nil and the line number with the rule), and a refused file counts as no records.
- **Merging**: an entry whose key equals the old entry's key adds its commands to the old ones (the union), so a spec that runs a command only on some runs (a lost race) keeps it; an entry with a new key replaces the old one. A command a spec stopped running therefore leaves its record only when the code behind the key changes, which is exactly when the record is rebuilt anyway.
- `commandrecord.key(paths: { string }, bytes: (string) -> string): string` (the sha256 of `spec commands key v1\n` and one `<path>\t<sha256 of its bytes>\n` line per distinct path, sorted), `commandrecord.parse(text: string): (Records?, string?)`, `commandrecord.render(records: Records): string`, `commandrecord.merge(old: Records, new: Records, keep: { [string]: boolean }?): Records` (`keep`, when given, drops old entries it lacks; new entries always stay), with `export type Records = { [string]: { key: string, commands: { string } } }`. Pure.

**The key's files** (one function, `z-nile/lib/recordkey.luau`, and its CLI `z-nile/recordkey.luau`; both callers, the runner and `context.commands`, use it, so their keys agree by construction):
- `recordkey.files(g: graph.Graph, spec: string, tooling: { string }): { string }`, pure: the repo-relative files of the spec's require closure that lie under its home's `tests/` folder, plus `tooling`.
- `recordkey.tooling(root: string): { string }`: the files that start `./zn` or decide what it runs outside the test code, listed from `git ls-files` at `root` (with untracked files of the same folders): `zn`, everything under `scripts/`, `z-nile/check.sh`, everything under `z-nile/lib/` and under `z-nile/templates/`.
- `recordkey.keys(root: string, specs: { string }): { [string]: string }`: builds the graph of every home's `src` and `tests` plus `z-nile/engine` from `root` (as `context.luau` does), and returns `commandrecord.key(recordkey.files(…), read under root)` for each spec. The CLI prints `<spec>\t<key>` per line and exits 2 naming the spec it can't key.
- So a record is valid while the spec, the test helpers it reaches, and the tooling that launches `./zn` are unchanged; an engine change never invalidates it. A change to `scripts/`, `z-nile/lib/` or `z-nile/check.sh` forces every project's or z-nile's run anyway, and that run rebuilds the records.

### 3. Selection by command (in c0165's `z-nile/lib/select.luau` and `context.luau`)
- **Records are read only when asked.** c0165 decided that "a bare selection call never reads machine-local state" (c0165.md, `affected.luau` row); the records are machine-local. So `z-nile/affected` loads them only with a new flag, `--recorded`, which `z-nile/check.sh`'s selection call and `z-nile/specs.luau` pass beside `--learned`. A bare call and `--graph-only` load none.
- `select.Context` gains `recorded: Recorded?`, with `export type Commands = { [string]: { string } }` and `export type Recorded = { commands: Commands, forced: { [string]: boolean } }`: `commands` maps a repo-relative spec path to the commands of every record whose key equals the spec's current key (the union, when several worktrees hold one); a spec with no such record is absent. `forced` is the set below. `recorded` is nil unless `--recorded` loaded it.
- **The program rule.** Engine code also runs without the CLI: a program that requires an engine module runs it directly (today `z-nile/affected.luau` and `z-nile/roots.luau` require `engine/projects.luau`, and the gate and the stop hook run them). `select.forcedEngine(g: graph.Graph): { [string]: boolean }`, pure, returns every engine Luau file in the require closure of a program, where the programs are the Luau files at the top of `z-nile/` (`affected`, `roots`, c0165's `specs`, c0180's `recordkey`), every Luau file under the root's `scripts/` except `scripts/tracker/` (the forwarders, which only specs require), and every Luau file under each home's `scripts/`. Today that set is `{ z-nile/engine/projects.luau }`. The context's graph gains these roots.
- `select.forces(rules, p, recorded: Recorded?)`: for a path under `z-nile/engine/` ending `.luau`, it returns `"z-nile"` when `recorded` is nil (a bare call, `--graph-only`) or `recorded.forced[p]`, and nil otherwise. Every other rule is unchanged: any other path under `z-nile/` outside `z-nile/tests/` (the gate, the templates, the skills, `z-nile/engine/board.html`) still forces z-nile. `affected`, `gateProjects` and `isInput` pass `ctx.recorded`. So `c0114/gate-cover` and `c0120/graph-homes` (c0165 runs them with `--graph-only`) and every bare call keep `ALL` for engine files.
- The graph of the context gains the root `z-nile/engine` (beside every home's `src` and `tests`, and the program roots), so the engine's own requires are edges.
- `select.engineUses(ctx, command): { [string]: boolean }?`: the closure of `z-nile/engine/cmd/<command>.luau` together with the dispatch core (the closure of `z-nile/engine/main.luau` that does not follow edges into `z-nile/engine/cmd/`). For `usage` it is the core alone. Any other name with no module returns nil.
- `isInput(ctx, S, p)` for an engine Luau path `p` that `forces` doesn't force, a spec `S` of the tooling home (`z-nile/`) and loaded records, in addition to c0165's clauses (`*`, a declared or learned `Inputs` entry, `p` in S's own closure):
  - S has no entry in `ctx.recorded.commands`: true (no matching record: fail closed, today's behaviour for that spec);
  - any command of S's entry has `engineUses` nil (a recorded command that no longer has a module): true;
  - `p` is in `engineUses(ctx, c)` for some command `c` of S's entry: true;
  - otherwise false.
  For a spec of any other home, an engine path is an input only through c0165's clauses, as today (engine changes never forced pickman).
- `context.commands(root: string, rules: select.Rules, g: graph.Graph): (Recorded, { string })` (new in `context.luau`; `g`'s paths are repository-relative, files are read under `root`; the second value is the warnings, which the CLIs print to stderr) builds `recorded`: the keys from `recordkey.keys`; the records from `<home>/.cache/spec-commands.tsv` of this checkout and of every other worktree of the repository (`git worktree list --porcelain`, read only), each parsed with `commandrecord.parse`; a missing file contributes nothing and prints nothing; a refused or unreadable file is skipped with one stderr line `affected: ignoring <path>: <reason>` and contributes nothing; `forced` from `select.forcedEngine(g)`. Reading siblings means a fresh worktree reuses what any other worktree recorded for the same code.
- **The whole-gate digest** (c0165's `fingerprint.digest` extras, which already carry the learned-inputs text) also carries, when records were loaded, the rendered `commands` table (one `<spec>\t<commands>` line per spec, sorted), so a gate that passed with one set of records never stands in for a selection made with another.
- **Declarations** (in c0165's `z-nile/tests/inputs.tsv`, AC8): every spec that reads engine files as text, copies them, or runs engine code by any way other than the CLI and the programs above declares them (prep's audit, E8, redone in round 2 with the searches for programs, `z-nile/check.sh`, the stop hook and `engine.copy` followed by a gate). ### Scalability
- Engine: one `pwd -P` and one `sh.writeReplacing` (a perl process, about 10 ms each at load 23, E5) per traced command per trace directory; a full z-nile run makes at least 1,207 traced calls (E2), so about 24 s of spec time out of 2,537 s. Untraced runs pay one environment read.
- Runner: one `fs.writeDir`, one `readDir` and a few removals per spec file; one `lune run z-nile/recordkey` per multi-file run after the workers end (a graph build and one sha256 per key file, a second or two).
- Selector: one `git worktree list` plus one file read per worktree (about 30 worktrees today), one key per spec (the closures are already computed for c0165's `isInput`), and `engineUses` once per command (37 closures over about 60 engine files).
- Effect (E2, measured on the full z-nile suite; lower bounds, since E2's wrapping `zn` missed the specs that run `engine/main` directly (`c0052/new-spacing`, `c0052/renumber`, `c0114/registry`, `tooling/migrate-odd`) and the `./zn` calls with no command; `projects.luau` now forces, so its row is z-nile's whole run; 183 specs, 2,537 spec-seconds, of which the 74 specs that run `./zn` take 2,003): a change to one command module selects 1 to 34 trace specs (11 to 1,388 spec-seconds; for example `lessons` 6 specs, 260 s; `done` 11, 216 s; `worktree` 32, 1,388 s), a small shared module 12 to 41 specs, and the publishing core (`store`, `projects`, `gitroot`, `guard`, `origin`, `boardrefresh`, `cli`) 46 to 68 specs (1,585 to 1,894 s). ### Maintainability
- A new command is a new `cmd/<name>.luau` and one dispatch line; AC1 fails until both exist. Its specs are recorded on their first passing multi-file run; until then they are selected by every engine change (fail closed).
- A new shared helper goes into the shared module of its concern, or into a new module beside them; the core stays `main`, `cli` and `sh` (AC1).
- One reader per format: `commandrecord.luau` reads and writes the record; one key function, `recordkey.luau`, serves the runner (through its CLI) and `context.luau`.
- A new program that requires engine modules is picked up by the program rule from its place (the top of `z-nile/`, `scripts/`, a home's `scripts/`); a program elsewhere, or a spec that runs engine code without the CLI, declares its engine inputs (zz-test's Command trace).
- Restated rules updated in the same change (Wording, pinned by AC7): zz-test's **Affected selection** (the engine no longer forces z-nile's run; the trace and record), zz-arch's **Layout** rows for `z-nile/engine/`.

### Usability
- One new flag, `z-nile/affected --recorded` (passed by `z-nile/check.sh`'s selection and by `specs.luau`, beside `--learned`): `lune run z-nile/affected -- --recorded <paths>` prints the narrowed selection, and a bare call prints today's. `ZN_SPEC_TRACE` is set only by the runner and documented in zz-test. `lune run z-nile/recordkey -- <specs>` prints the keys.
