# c0180: Hybrid gate, in-process inner, end to end final

## Problem
The user (2026-10-31), after a full gate pegged fseventsd at a whole CPU core: "This is not acceptable. Find a better solution. Test has to be thorough and complete but also very fast and efficient."

Asked for a speed target, the user (2026-10-31): "Is a hybrid possible? Running the tests in process and only running affected tests while working through the design code and review, then once it's all done the final gate is running all tests properly end 2 end".

Measured 2026-10-31: one worktree's `z-nile/.cache` changed 10,711 files in 10 s during a full gate (`find -newer`, so files made and removed inside the window are not even counted); fseventsd ran at about 80-100% of a core and `mds_stores` at about 35%. The z-nile suite is 1265 cases in 183 files, about 1,850 s of spec time and 185-230 s of wall time idle (up to 1,800 s under load); `c0116/claims` and `c0120/finished` take about 175 s each idle and set the floor. c0175's capture ran the full gate three times (about 6 min each) and still lost the race to main.

Today every spec calls the tracker and `./zn` as subprocesses (`bash scripts/tracker.sh` -> `bash zn` -> `lune`, plus the guards: about 20-40 processes a call, about 837 call lines), and any z-nile change outside `z-nile/tests/` forces z-nile's full suite (`z-nile/affected.luau`), so every build and review gate of tooling work runs everything end to end.

What should happen: while designing, building and reviewing, the gate runs only the affected specs, with the engine called in-process; the final gate runs every spec end to end, as today. An in-process pass never counts as the final gate.

Decided with the user (2026-10-31), relayed by the ZNILE_TESTLIMIT session and folded into c0165: "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected."
- The full gate runs once per raft: zz-rules Merging step 2 runs `z-nile/check.sh --full` in a clean clone of the exact final head, right before `gh pr merge`. Captures keep `./zn land`'s full gate, because that is their merge.
- Every gate before it is `--affected` (here, in-process): zz-execute Phase 0's baseline, Phase 3 steps 2-3, Phase 4 step 1 (the author), zz-review code mode item 1 (the reviewer), Phase 5 step 2 (after merging main), `./zn done`'s gate on the done tree (affected plus its promoted-spec checks), and the raft `check.sh` template's RC0 (`--project {{PROJECT}} --affected`).
- So `done` no longer runs the full gate. Gate placement itself is c0165's to build; c0180 makes the gates before the merge in-process and keeps the merge gate end to end.

Scope decision (user, 2026-11-01), after prep measured the in-process driver (calling the engine in-process saves about 0.17 s per `./zn` call: about 27% of `c0005/worktree`, but about 5% of the 3,166 s z-nile suite, whose slowest specs spend most of their time building fixtures and running git, c0178's work; it needs about 190 file paths, 190 subprocess calls, 154 outputs and 11 exits in `main.luau` reworked; and every tracker spec reaches the engine through `main.luau`, so an engine change would still select about every tracker spec): "Select by command (Recommended)": "Re-scope c0180: keep ./zn as a subprocess; split main.luau into one module per command, record during each full end-to-end run which commands each spec invoked, and let --affected run only specs that used a changed command. Engine work then runs a handful of specs instead of ~100. Records your decision line; same 'full e2e at merge' rule."
- So the in-process driver (`run(argv, ctx)`, `fixture.zn`, `ZN_SPEC_DRIVER`) and its experiments are out of scope; `./zn` stays a subprocess in every run, and every run (affected or full) is end to end.
- The gate-placement decision above stands, without its "(here, in-process)".

Decided with the user (2026-11-01), on how the split lands (about 11 open branches edit `main.luau`, among them the active rafts R0052, R0056, R0059 and R0061): "All at once, after active rafts (Recommended)": "Split all 37 commands in one go, but c0180's raft is readied only when no active raft changes main.luau (checked with ./zn busy at z-ready). Other branches port their edits by hand when they merge main. Full selection gain from day one."

## Non-goals
- Reusing results of identical content: c0165.
- Fixture construction and the fixture volume: c0178, c0179.
- The in-process driver (`run(argv, ctx)`, `fixture.zn`, `ZN_SPEC_DRIVER`): out of scope by the user's decision of 2026-11-01.
- Narrowing selection for the rest of `z-nile/` (the gate, the templates, the skills, the lessons): those still force z-nile's run.
- Gate placement (which step runs `--full`): c0165.

## Solution
- `z-nile/engine/main.luau` exposes `run(argv, ctx)`; cwd, env, exit and output go through `ctx`, and every subprocess through `sh` with `ctx.cwd` (Lune can't change directory); no module-level mutable state in the engine, by rule and spec.
- One driver, `fixture.zn(dir, argv, opts)`, for every spec's tracker and `zn` call; `ZN_SPEC_DRIVER=inprocess|e2e`, e2e being today's path.
- The inner gate (`check.sh`, `--affected`, the stop hook) selects by the engine's require graph (building on c0165's selector) and runs in-process; `--full` (the merge gate, and `./zn land` for captures) runs all, end to end.
- Experiments: count the exec, cwd and exit sites outside `sh`; run ten heavy specs both ways, results equal and speedup measured.
- (prep, after the scope decision of 2026-11-01) The in-process bullets above are replaced by the decision: `./zn` stays a subprocess; `main.luau` is split into one module per command; each multi-file spec run records which commands every spec ran; an affected run selects, for a change to the engine's Luau files, only the specs whose recorded commands use the changed file. The last bullet's measurement was made, and its results are E1 and E2.

## Design

### Overview
Three parts, in the order they run:
1. **Command modules.** `z-nile/engine/main.luau` keeps argv parsing, the `READ_ONLY` set, the repository guard and a dispatch table; each of the 37 commands moves, with the helpers only it uses, to `z-nile/engine/cmd/<name>.luau`; the helpers two or more commands use move to sixteen shared modules beside the existing ones in `z-nile/engine/`. No command's behaviour, output, refusal or exit code changes.
2. **The command trace.** When `ZN_SPEC_TRACE` is set, the engine records the command it is about to run as an empty file named after the command in each directory the variable lists. The spec runner gives every spec file of a multi-file run its own trace directory, and after the run writes each passing spec's commands to `<home>/.cache/spec-commands.tsv`, keyed by a hash of the spec's test-side require closure.
3. **Selection by command.** In c0165's `select.luau`, a change to an engine Luau file (`z-nile/engine/**/*.luau`) no longer forces z-nile's full run. It is an input of a z-nile spec when the spec requires it, declares it, is `*`, has no matching record (fail closed), or ran a command whose module closure (plus the dispatch core) contains it. Because c0165's fingerprints use the same `isInput`, reuse follows the same rule.

Product decisions relied on (quoted from the Problem): "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected." (2026-10-31); "Select by command (Recommended)" (2026-11-01); "All at once, after active rafts (Recommended)" (2026-11-01). This issue changes no gate placement: c0165 builds that, and every run stays end to end.

Rules (each pinned by AC1 on the real tree):
- **One module per command.** For every command `main.luau` dispatches, `z-nile/engine/cmd/<name>.luau` exists (the file name is the command name, `raft-plan.luau` and `worktree-prune.luau` included), and it returns one function `cli.Handler = (pos: { string }, opts: cli.Opts, usage: string) -> ()`; `main.luau` passes `USAGE` as `usage` (only `new` reads it, for its `fail(usage)`), so no module requires `main.luau` and `USAGE` stays where `c0120/docs` and `c0116/docs` read it. Every file in `cmd/` is a dispatched command. No module defines `cmd.<name>`.
- **Lazy, literal dispatch.** `main.luau` maps each name to a function that runs `require("./cmd/<name>")` with a literal path (so the graph scanner sees the edge and nothing else loads), for example `new = function() return require("./cmd/new") end`.
- **A thin core.** The dispatch core is the require closure of `main.luau` without the edges into `cmd/`: exactly `main.luau`, `cli.luau` and `z-nile/lib/sh.luau`. A change to anything else in the engine therefore never selects every command by itself.
- **Only `main.luau` requires a command module**, and nothing requires `main.luau`. The shared modules form no cycle (the graph's closure from each `cmd/` module terminates; `guard`/`boardrefresh`'s only cycle is broken by `mainguards`).
- **No other behaviour changes.** Every command's stdout, stderr, exit code and file effects stay as they are. The whole existing suite is the regression guard (the raft's RC0, and the merge's full gate).
- Module-level cells move with their only users (`guardedRun` into `guard`, `seeded` into `stamps`, `originSpend`/`originChecked` into `cmd/metrics`); no new module-level mutable state.
- `z-nile/engine/projects.luau` stays self-contained (it requires no new module): `c0120/ci` and `c0114/gate-cover` copy it alone into fixtures.
- Local-name collisions (`cmd.stamp` against the `stamp` helper, `cmd.audit` against the `audit` module local, and `board`, `spend`, `status`, `lessons`, `skills` likewise) are resolved inside each command module by naming the required module `<name>Lib`, as `main.luau` already does for `statusLib`.

The split is mechanical: the code of every function moves unchanged except for the `local x = require(...)` lines each new module needs and the `cmd.<name> = function` header becoming `return function`. Implementation step 2 does it as one commit of moves only, so the review reads it as moved text (`git diff --color-moved`).

### 2. The command trace
**Engine side** (`main.luau`, after the command name resolves to a dispatched command and before the guard and the handler run):
- `ZN_SPEC_TRACE` unset or empty: nothing happens (every interactive and gate use).
- Otherwise it is a `:`-separated list of directories. For each entry, in order: it must be an absolute path (starts with `/`), contain the segment `/.cache/`, and be an existing directory; otherwise the command refuses before doing anything, with exit 2 and `zn: ZN_SPEC_TRACE entry <dir> is not an absolute directory under a .cache folder` on stderr.
- It then writes an empty file `<dir>/<command>` with `sh.writeReplacing` (the reviewed writer: a sibling temporary file and `rename(2)`, which never writes through a link). A failed write refuses the same way: exit 2, `zn: cannot record the spec trace in <dir>: <error>`. The trace fails closed: a command that ran but left no trace is impossible.
- An unknown command, or no command, prints the usage as today and writes nothing. A command that fails after the trace (any `fail`, refusal or error) has still been recorded, which is what selection needs: the spec exercised that command's code.
- The variable is inherited by everything the command starts, so a nested `./zn` (a `check.sh` the `check` command runs) is traced too. The write sits in `main.luau`, so every way of starting the engine is traced: `./zn`, `scripts/tracker.sh`, and the five specs that run `lune run <root>/z-nile/engine/main` directly (`c0052/new-spacing`, `c0052/renumber`, `c0114/registry`, `c0114/roots-cli`, `tooling/migrate-odd`).

**Runner side** (`z-nile/tests/run.luau`, only in `runConcurrently`, the path that already records durations):
- Before starting a file's worker, the coordinator creates a fresh directory `<home>/.cache/spec-trace/<n>-<random>` (`fs.writeDir` after checking it does not exist; `<n>` is the file's index) and starts the worker with `ZN_SPEC_TRACE=<absolute dir>` followed by `:<inherited value>` when the runner itself inherited one. A nested run (a spec that runs a gate in a copy of the tree) therefore records into its own directories and into its outer spec's.
- After the worker exits, the coordinator lists the directory's entries (names matching `^[a-z][a-z%-]*$`; anything else is ignored), removes each file and then the directory (never recursively).
- After every worker, alongside the durations, it merges a record for every home spec file (`tests/…`) whose worker exited 0 with `N passed, 0 failed` into `<home>/.cache/spec-commands.tsv`, using a temporary file and a rename, exactly as the durations record is written; a failed write is ignored (it costs selection precision, never correctness, see below). A failing spec keeps its earlier record. A full run (no files named) drops the lines of spec files that no longer exist.
- The one-file and `--jobs 1` path creates no directory and writes no record (as for durations), but an inherited `ZN_SPEC_TRACE` passes through to the spec untouched.

**The record format** (`<home>/.cache/spec-commands.tsv`, one reader: `z-nile/lib/commandrecord.luau`):
```
# spec commands v1
tests/acceptance/c0005/worktree.spec.luau	3f9c…(64 hex)	find,list,new,prompt,start,worktree,worktree-prune
tests/meta/architecture.spec.luau	a01b…(64 hex)	-
```
- The first line is exactly `# spec commands v1`. The text ends with a newline, and no line is blank. Each other line has three tab-separated fields: a path starting `tests/` and ending `.spec.luau`; a 64-character lowercase hex key; `-` or a comma-separated, sorted, duplicate-free list of names matching `^[a-z][a-z%-]*$`. A spec appears at most once. `commandrecord.parse` refuses a file breaking any rule (nil and the line number with the rule), and a refused file counts as no records.
- **The closure key** is `sha256` (`serde.hash`) of `spec commands key v1\n` followed by one `<path>\t<sha256 of the file's bytes>\n` line per distinct file of the spec's require closure that lies under the home's `tests/` folder, paths relative to the home, sorted. It changes when the spec or any test helper it reaches changes, and not when the engine changes, so a record is valid exactly while the code that decides which commands the spec runs is unchanged.
- `commandrecord.key(paths: { string }, bytes: (string) -> string): string`, `commandrecord.parse(text: string): (Records?, string?)`, `commandrecord.render(records: Records): string`, `commandrecord.merge(old: Records, new: Records, keep: { [string]: boolean }?): Records`, with `export type Records = { [string]: { key: string, commands: { string } } }`. Pure; the runner and the selector's context both call `key` on the closure the graph gives (`graph.closure`), filtered to `tests/` of the spec's home.

### 3. Selection by command (in c0165's `z-nile/lib/select.luau` and `context.luau`)
- `select.forces(rules, p, commands: Commands?)`: when `commands` is given (the records were loaded), a path under `z-nile/engine/` ending `.luau` returns nil; when it is nil (c0165's `--graph-only`, which loads neither inputs nor records) it forces z-nile as today. Every other rule is unchanged: any other path under `z-nile/` outside `z-nile/tests/` (the gate, the templates, the skills, `z-nile/engine/board.html`) still forces z-nile. `affected`, `gateProjects` and `isInput` pass `ctx.commands`.
- `select.Context` gains `commands: Commands?`, `export type Commands = { [string]: { string } }`: repo-relative spec path → the commands of every record whose key equals the spec's current key (the union, if several sources hold one). A spec with no such record is absent. `context.luau` fills it whenever it loads the inputs; under `--graph-only` it stays nil, so `c0114/gate-cover` and `c0120/graph-homes`, which c0165 runs with `--graph-only`, keep their `ALL` for engine files unchanged.
- The graph of the context gains the root `z-nile/engine` (beside every home's `src` and `tests`), so the engine's own requires are edges.
- `select.engineUses(ctx, command): { [string]: boolean }`: the closure of `z-nile/engine/cmd/<command>.luau` together with the dispatch core (the closure of `z-nile/engine/main.luau` that does not follow edges into `z-nile/engine/cmd/`). A name with no module returns nil.
- `isInput(ctx, S, p)` for an engine Luau path `p`, a spec `S` of the tooling home (`z-nile/`) and loaded records (`ctx.commands` not nil), in addition to c0165's clauses (`*`, a declared or learned `Inputs` entry, `p` in S's own closure):
  - S has no entry in `ctx.commands`: true (no matching record: fail closed, today's behaviour for that spec);
  - any command of S's entry has `engineUses` nil (a recorded command that no longer has a module): true;
  - `p` is in `engineUses(ctx, c)` for some command `c` of S's entry: true;
  - otherwise false.
  For a spec of any other home, an engine path is an input only through c0165's clauses, as today (engine changes never forced pickman).
- `context.commands(root: string, rules: select.Rules, g: graph.Graph): (Commands, { string })` (new in `context.luau`; `g`'s paths are repository-relative, files are read under `root`; the second value is the warnings, which the CLIs print to stderr) builds `commands`: for each spec of each home, the key from the graph's closure; the records from `<home>/.cache/spec-commands.tsv` of this checkout and of every other worktree of the repository (`git worktree list --porcelain`, read only), each parsed with `commandrecord.parse`; a refused or unreadable file is skipped with one stderr line `affected: ignoring <path>: <reason>` and contributes nothing. Reading siblings means a fresh worktree reuses what any other worktree recorded for the same test code.
- **Declarations** (in c0165's `z-nile/tests/inputs.tsv`, AC8): once engine files stop forcing, every spec that reads engine files as text or copies them declares them (prep's audit, E8). The lines c0180 adds (home-relative spec, then the input):

Why a stale or wrong record can't hide a failure from the merge: records narrow only `--affected` runs; the merge's gate is `--full`, end to end (the user's decision), and c0165's learning records any miss it finds there. A record is also never trusted across a change to the test code that decides the commands (the key).

### Scalability
- Engine: one `sh.writeReplacing` (a perl process, about 10 ms at load 23, E5) per traced command per trace directory; a full z-nile run makes 1,207 traced calls (E2), so about 12 s of spec time out of 2,537 s. Untraced runs pay one environment read.
- Runner: one `fs.writeDir`, one `readDir` and a few removals per spec file; one graph build of the home's `tests/` (about 0.3 s) and one sha256 per closure file per recorded spec, once per run.
- Selector: one `git worktree list` plus one file read per worktree (about 30 worktrees today), one key per spec (the closures are already computed for c0165's `isInput`), and `engineUses` once per command (37 closures over about 60 engine files).
- Effect (E2, measured on the full z-nile suite, 183 specs, 2,537 spec-seconds, of which the 74 specs that run `./zn` take 2,003): a change to one command module selects 1 to 34 trace specs (11 to 1,388 spec-seconds; for example `lessons` 6 specs, 260 s; `done` 11, 216 s; `worktree` 32, 1,388 s), a small shared module 12 to 41 specs, and the publishing core (`store`, `projects`, `gitroot`, `guard`, `origin`, `boardrefresh`, `cli`) 46 to 68 specs (1,585 to 1,894 s). Today every engine change runs all 183. c0165's `*` specs (about 15, `c0120/finished` at about 250 s under load) are selected by every change, so they set the affected gate's wall-time floor until c0178 speeds them up.

### Maintainability
- A new command is a new `cmd/<name>.luau` and one dispatch line; AC1 fails until both exist. Its specs are recorded on their first passing multi-file run; until then they are selected by every engine change (fail closed).
- A new shared helper goes into the shared module of its concern, or into a new module beside them; the core stays `main`, `cli` and `sh` (AC1).
- One reader per format: `commandrecord.luau` reads and writes the record, used by the runner and by `context.luau`.
- Restated rules updated in the same change (Wording, pinned by AC7): zz-test's **Affected selection** (the engine no longer forces z-nile's run; the trace and record), zz-arch's **Layout** rows for `z-nile/engine/`.

### Usability
- No new command or flag. `lune run z-nile/affected -- <paths>` prints the narrower selection; `ZN_SPEC_TRACE` is set only by the runner and documented in zz-test.
- The two refusals name the variable and the directory. A sibling's malformed record prints one `affected: ignoring …` line.

## Unknowns & experiments
- **E1** (measured 2026-10-31, the decision's basis): does calling the engine in-process pay? `c0005/worktree` ran 31.1 s with 50 `./zn` calls taking 17.3 s inside `zn`; a no-op `bash zn nosuchcmd` costs 0.12 s at load 24, plus the harness's three `fixture.check` processes per call.
