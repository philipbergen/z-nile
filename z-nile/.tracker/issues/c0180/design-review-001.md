### F1 [high] Engine code reached without a dispatched `./zn` command is invisible to selection, so an affected gate stays green while a spec it should have run fails
Where: Design §3 (`isInput` for engine paths), §2 ("An unknown command, or no command, … writes nothing"), Declarations, E8, Wording (Command trace bullet)
Evidence: The design's only routes from an engine Luau file to a z-nile spec are the spec's own requires, a declaration, `*`, a missing record, and the commands `main.luau` dispatched. Two real routes bypass all of them.
- Other entry points require engine modules. `git grep -nE 'require\([^)]*engine/' -- '*.luau' ':!z-nile/engine/*'` finds `z-nile/affected.luau:13` and `z-nile/roots.luau:11` (`require("./engine/projects")`), plus the `scripts/tracker/*.luau` forwarders, which are required in-process only. `z-nile/check.sh:32,89,205` runs `lune run z-nile/roots` and `lune run z-nile/affected`, and so does `scripts/hooks/stop.sh:21`. Specs that start them, from `git grep -nE '"z-nile/(roots|affected)"|z-nile/roots|scripts/affected"|"z-nile/check.sh"|hooks/stop' -- 'z-nile/tests/*.spec.luau'`: `c0120/graph-homes` (runs `lune run z-nile/affected` at the top), `tooling/gate-home-cache` and `tooling/fence-every-home` (`engine.copy`, then the gate in the copy), `c0077/replace-file` (`z-nile/check.sh --full` in a copy), `c0120/gate-homes`, `c0114/gate-cover` and `c0120/ci` (these two are declared), and `c0120/registry-home` (it requires `projects` itself, so it is covered). E2's log shows 0 `./zn` calls each for graph-homes, gate-home-cache, replace-file and fence-every-home. So their records would be `-`, and none of them is in the Declarations or in c0165's `declared/z-nile.tsv` (`grep -n 'graph-homes\|gate-home-cache\|replace-file\|fence-every-home' declared/*.tsv`: only graph-homes, for `pickman/` and `z-nile/tests/` paths). I ran it: in `scratchpad/split`, a `break` in `projects.roots`'s loop (`engine/projects.luau:112`) gives `FAIL tests/acceptance/c0120/graph-homes.spec.luau … :185: expected "|", got "|ALL\n"`. Under c0180, `--affected` for that change selects the specs whose recorded commands reach `projects.luau`, and graph-homes isn't among them.
- `./zn` with no command (or an unknown one) runs `main.luau`'s `USAGE` path and, by design, records nothing. `c0115/docs.spec.luau:175` runs only `bash {TOP}/zn` and asserts `skills [--check]` in the output. E2 shows 0 calls for it, and it isn't declared. In the split clone, `s/skills \[--check\]/skills [--chek]/` in `engine/main.luau` → `FAIL c0115/docs.spec … :176: ./zn usage is missing: skills [--check]`. A `main.luau` change is "selected" through the core only for specs that dispatched a command.
- c0180's own `endtoend.spec` copies `z-nile/engine/projects.luau` and `board.html` into its fixture and runs `z-nile/affected` there. It is a copier by E8's own definition, and it isn't declared either.
E8's audit searched for readers of engine text and copiers (`engine/main`, `readFile(` of engine paths, …). It never searched for processes that execute engine code without passing the trace.
Critique: This is exactly the under-selection the design says can't happen ("a change to an engine Luau file selects the z-nile specs that require it, declare it, … ran a command whose module … reaches it"). `projects.luau` is the selector's and the gate's own dependency, so a change to it is the change whose testing matters most. The tempting fix is to add the six specs found here to the Declarations. That patches today's list and leaves the next probe, gate spec or usage check uncovered, with nothing to flag it.
Consequences: The fix makes some engine files keep forcing, so its rule needs a graph that includes the other entry points (`z-nile/*.luau`, `scripts/`), which c0165's context doesn't build today. The usage marker becomes a name in the record format and in `engineUses`, so it must be one no command can ever take. c0165's learned edges would catch the remaining misses, but only after a merge gate has failed on the PR.
Recommendation: Close both routes by rule, not by list.
- (a) An engine Luau file in the require closure of any Luau file outside `z-nile/engine/` and outside every home's `tests/` (today `z-nile/affected.luau`, `z-nile/roots.luau`, c0165's `z-nile/lib/select.luau` and `specs.luau`, and `scripts/**`) still forces z-nile's run, as today. Today that is `projects.luau`, which the publishing core already selects for 46-68 specs, so it costs little. Add these to the context graph's roots. Cases: `select.spec`, an engine module required by a non-engine tooling file forces even with records; `split.spec` on the real tree, that set is exactly what the graph computes, and no engine file is in `g.dynamic` (a dynamic require would also escape selection).
- (b) A run that dispatches nothing records a reserved name (for example `usage`) whose `engineUses` is the dispatch core. `split.spec` asserts that no `cmd/usage.luau` exists. Change `trace :: unknown command` to expect that file, and let `commandrecord.parse` accept the name.
- (c) Redo E8 with the searches above (`lune run`, `z-nile/check.sh`, `stop.sh`, `engine.copy` followed by a gate or probe) and declare what (a) doesn't cover, including `endtoend.spec` (`z-nile/engine/projects.luau`, `z-nile/engine/board.html`). Extend the zz-test Command trace wording: a spec that runs engine code through anything but `./zn` or `engine/main` (a probe, `z-nile/roots`, `z-nile/affected`, the gate in a copy) declares those engine files.
- Add Rules rows for (a) and (b), with the mutants "only `main.luau` traces" and "projects.luau no longer forces".

### F2 [high] The trace's path guard accepts `..` (and symlinked folders), so a traced command writes into the repository outside `.cache`
Where: Design §2 Engine side ("must be an absolute path (starts with `/`), contain the segment `/.cache/`, and be an existing directory"); trace.spec refusal cases; Lessons pass (zz-arch/guard-no-is-explicit)
Evidence: In `scratchpad/proto`, whose trace code is the Design's (`main.luau:5624-5646`), `ZN_SPEC_TRACE="$P/z-nile/.cache/../engine" ./zn list` exits 0 and creates `z-nile/engine/list`, a new file in the tracked tree (`git status`: `?? z-nile/engine/list`; removed afterwards). The test is a substring test on the unresolved text, so `<anything>/.cache/../<anywhere>` passes, and so does a symlink under `.cache` that points out of it. On macOS the jail would deny the write. Unjailed runs (Linux, or an outer sandbox that allows the repository) write it, and AGENTS.md puts those runs on review.
Critique: The design presents this check as the trace's guard and cites guard-no-is-explicit, but the guard decides on the spelling, not on where the write lands. The tempting fix is to refuse the substring `..`. That still lets symlinked components through, and a checkout that itself lives under a `.cache` folder (`~/.cache/src/pickman`) passes every path in it.
Consequences: Resolving the path physically needs one `realpath`/`pwd -P` per entry per traced call (a process at load 23, about the cost of the write itself), or Lune's own canonicalisation if it has one. The refusal message must not change in a way the specs pin.
Recommendation: Refuse an entry unless it equals its own physical path (no `.`/`..` components, no symlinked component) and that physical path has a `.cache` component. Write with `sh.writeReplacing` as now. Cases in trace.spec: `{traces}/a/..` and a symlink in `{traces}` to `f.main` both refuse with exit 2, before work (`clean()`), and leave no file. Add a Rules row with the mutant "substring test on the given text".
Lesson: zz-arch/guards-decide-from-the-tools-resolution

### F3 [medium] A bare `z-nile/affected` now reads machine-local records from every worktree, contrary to c0165's decided rule
Where: Design §3 (`context.luau` "fills it whenever it loads the inputs"; `context.commands` reads `<home>/.cache/spec-commands.tsv` of every worktree); Usability; endtoend.spec (`affected` without any flag)
Evidence: c0165.md:75: "It reads the db's learned inputs only with `--learned`, which `check.sh`'s selection call passes. A bare selection call never reads machine-local state." That came from c0165 design review 001 F2, where machine-local state turned `c0120/graph-homes` red on one machine and left it green in CI ("Bare `affected` is what reviewers paste into Override checks (zz-review item 4), so its output should be the committed answer"). c0180's records are machine-local (`.cache`, every worktree) and are read on every bare call. The Override check for an engine path then prints a list that depends on which worktrees exist and which specs last passed in them, where today it prints `ALL`, and it misses F1's specs.
Critique: The design relies on c0165 but contradicts one of its decided rules without saying so (z-design/quote-other-preps-before-promising: a disagreement goes to the user or that prep first). The tempting fix, "skip the records under `PICKMAN_TEST_FENCE`", breaks endtoend's nested selection, just as it did for c0165's learned rows.
Consequences: An explicit flag means every caller that wants narrowing must pass it: check.sh's selection, `specs.luau`, and endtoend's calls. Records also narrow which specs a gate runs, so c0165's whole-gate digest (whose extras already carry the learned-inputs text) must carry what narrowed it. Otherwise a gate reused from a run with more records stands in for a wider selection on the same content.
Recommendation: Load records only when asked: reuse `--learned` or add `--recorded`, passed where `--learned` is. A bare call and `--graph-only` leave `commands` nil, so engine Luau files force as today. Add the records' text (or the selected set) to the digest extras. Cases: endtoend, a bare call on `cmd/list.luau` with records present prints `ALL`, and the flagged call narrows. Add a Rules row with the mutant "records read unconditionally". Update the Usability line and the Command trace wording.
Lesson: z-design/quote-other-preps-before-promising

### F4 [medium] A record outlives the code that decided its commands: the key covers only test files, and merge replaces rather than accumulates
Where: Design §2 ("The closure key … a record is valid exactly while the code that decides which commands the spec runs is unchanged"), `commandrecord.merge` ("replaces"), §3 (sibling worktrees' records, "the union, if several sources hold one")
Evidence: Non-test tooling also decides which commands a spec runs. `git grep -nE 'zn |/zn' z-nile/check.sh z-nile/templates` finds `z-nile/check.sh:184` (`./zn skills --check`, run by every spec that runs the gate in a copy) and `z-nile/templates/raft/check.sh:10,14` (`members`, `promote-check`, run by every spec that checks a raft). Scenario: a branch adds `./zn audit` to `z-nile/check.sh` and lands, and its worktree is removed. A fresh worktree has no records of its own. It reads the main checkout's or another sibling's records, which have the same key because the test code is unchanged and which lack `audit`. A later change to `cmd/audit.luau` there then doesn't select the gate-running specs. In one worktree too: a spec that fails in the multi-file run keeps its old line, and the rerun of just that spec is a one-file run, which writes nothing, so the stale line stays. A spec whose path depends on timing (a lost race that runs `release`) records one sample, and the next run replaces it with another.
Critique: The fail-closed promise ("a command that ran but left no trace is impossible") holds for one run, not for the record that selection reads later. The tempting fix is to put the engine in the key. That invalidates every record on every engine edit, which is exactly the change selection exists for.
Consequences: Widening the key to the launching tooling costs nothing in the worktree that changed it, since those paths force z-nile's run, and that run re-records. Union merging means a command a test stopped running drops out only when the test code changes, which is what the key already tracks.
Recommendation: Add to the key the blobs of the non-engine files that can start `./zn` or decide what it runs: `zn`, `scripts/**`, `z-nile/check.sh`, `z-nile/lib/**`, `z-nile/templates/**`. Write the set in the Design, and decide whether it moves into one function (zz-test/one-rule-one-function). `merge` unions the commands when the key is unchanged and replaces them when it changed. Fix the "valid exactly while" sentence. Cases:
- `commandrecord :: merge`: union on an equal key, replace on a new one.
- `record.spec`: a rerun that records fewer commands keeps the union.
- `endtoend`: editing the fixture's `z-nile/check.sh` in W2 makes W1's record count as absent in W2.
- Rules rows with the mutants "replace on an equal key" and "key without the launching tooling".
Lesson: zz-arch/records-cover-what-was-reviewed

### F5 [medium] The selection half of the feature (R22-R34) has never been run, step 1 can't tell a real failure from an expected one, and nothing checks that the runner's and the selector's keys agree on the real tree
Where: E6 (open), E9, E10 ("R22 to R32 and R34 stay `reasoned` until c0165's … exist"), Implementation step 1 ("rerun every sequestered spec … send the issue back to z-design if a spec must change"), step 10 (E7)
Evidence: `select.spec`, `endtoend.spec` and `inputs.spec` call c0165's modules plus c0180's own `select`/`context` changes, which no prototype has. In step 1, before execution, they can only fail, and the step doesn't say which cases must pass then or what a failure means. Nothing in the steps runs R22-R34's mutants once c0165 lands, so the rows that hold the feature's logic reach the executor unproven. E6 is the risk that matters most. If the runner's key (graph rooted at the home's `tests`) and the context's key (graph from the root with every home's roots plus `z-nile/engine`) differ on the real tree, for example through alias resolution, then every spec counts as unrecorded and every engine change selects all of z-nile. The feature then delivers nothing while AC1-AC9 all pass, because AC5 uses a hand-built context and AC6 a fixture. E7's measurement compares records, not selection, and has no pass bar.
Critique: All nine criteria can pass on an implementation that never narrows anything on the real tree, which is the outcome the user chose this re-scope for ("Engine work then runs a handful of specs instead of ~100"). The tempting fix is to measure it once in step 10. That is a Verification-log line, and the next refactor of the graph or aliases breaks it silently.
Consequences: Making E6's fallback the design (one function computes the key for both callers) removes the risk by construction, but that function must take the home and build or reuse the home's own graph in both callers. A real-tree check must not depend on machine-local records, or it breaks zz-test's Deterministic rule.
Recommendation:
- Make one function, for example `commandrecord.closureFiles(home, spec)` over one graph construction, the only source of the key for the runner and `context.commands`. Add a promoted spec (a rule, not today's text) asserting it for every spec of both homes on the real tree, read-only.
- Add a real-tree case in `split.spec` or `select.spec`: `engineUses` of every dispatched command is non-nil and excludes at least one engine Luau file, so the feature can't be vacuous.
- Rewrite step 1: on the prototype after merging origin/main, `commandrecord`, `trace`, `record`, `split`, `docs` and `narrowed` must pass, and a failure sends the issue back. Then add the selection to the prototype on landed c0165, run R22-R34 there with each mutant alone, and record the results before `ready`. A surviving mutant sends the issue back to z-design.
- Give E7 a pass bar, for example "`cmd/lessons.luau` selects at most 15 z-nile specs after one recorded full run".
Lesson: z-design/prove-specs-pass-on-a-prototype, z-design/instructions-runnable-where-they-run

### F7 [medium] Several Design rules have no case and no row, so a wrong implementation passes
Where: Design §2 Runner side, §3 `context.commands`; Rules and mutants
Evidence: No case or row covers these. In each, the plausible mutant passes all nine specs.
- "the union, if several sources hold one": endtoend reads only W1's record, so "first source wins" passes.
- "names matching `^[a-z][a-z%-]*$`; anything else is ignored", and "removes each file and then the directory (never recursively)": no case puts a stray file in a trace directory. A killed engine leaves `.<cmd>.pickman-tmp.<pid>.<rand>` (`replace-file.pl` line 32), the non-recursive removal then fails, and the Design doesn't say whether the runner errors, warns or keeps going.
- Which worktrees warn: a worktree with no record file, which is most of the 30, must not print `affected: ignoring …`. The Design's "refused or unreadable" includes "absent".
- `raft-plan: cannot run <name>`: no case.
Critique: Each is a sentence an executor implements by guess. The first and third change what selection prints. The second can fail a whole run.
Consequences: The stray-file rule needs a decision: warn and leave the directory, or remove the known temporary pattern. Either one adds a case.
Recommendation:
- endtoend: give W2 its own record for the same key with a different command, and assert the union.
- record.spec: plant `.list.pickman-tmp.1.abcdef` and `Foo` in a trace directory through the stub. Assert that neither name enters the record and that the run's outcome is the one the Design decides.
- endtoend: assert that W2's selection prints no `ignoring` line for a worktree with no record.
- plan-cli or split: assert that the refusal case, or `cmd/raft-plan`, requires only `./fold` and `./new`.
- Add a row for each.
Lesson: z-design/spec-design-correspondence
