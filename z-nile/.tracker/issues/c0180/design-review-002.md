### F5 [medium] A record still outlives what decides its commands: the engine and declared data choose nested commands, and the records that know better are thrown away when their worktree goes (repeat of design-review-001 F4's mechanism)
Where: Design §2 ("So a record is valid while the spec, the test helpers it reaches, and the tooling that launches `./zn` are unchanged; an engine change never invalidates it"), Merging, Runner side ("a failed write is ignored (it costs selection precision, never correctness)"); §3 `context.commands` (records from every worktree's `.cache`); the closing paragraph ("A record is also never trusted across a change to the code that decides the commands (the key)")
Evidence: Specs record commands they never name. In E2's log, `tests/acceptance/c0034/locator.spec.luau` ran `check,done,find,members,new`, and `grep -cE 'members|promote-check'` on the spec is 0: `members` runs because `check` and `done` (engine code, `main.luau:2742` `sh.stream("bash", { `{item.dir}/check.sh` })` and `:4096`) run the raft's `check.sh`, whose template runs `./zn members`. The engine decides which nested commands run, and so do item `check.sh` files a spec copies from the real tracker. Neither is in the key. A failing scenario:
1. Branch X changes `cmd/done.luau` so that `done` also runs each member's `check.sh` (new nested `members` and `promote-check`). Its gate selects the `done` specs, which re-record with the new commands, in X's worktree only. X lands, and its worktree is removed, taking its `.cache/spec-commands.tsv` with it. The main checkout never runs specs, so it holds no records.
2. Branch Y, in a worktree made later, changes only `cmd/promote-check.luau`. The records it reads (its own, none yet, and the siblings' made before X landed) have the same key, because the engine isn't in it, and lack `promote-check` for the `done` specs. Y's affected gate doesn't select them; the merge's full gate fails them.
A failed record write (Runner side) loses the same kind of knowledge: a union addition under an unchanged key is dropped, so it costs correctness, not only precision.
Critique: Round 1 found that the key missed the launching tooling; the fix added it, but the mechanism (machine-local per-worktree files, valid by a key that leaves out some of what decides the commands) has the same hole one layer down. The Design's sentence "never trusted across a change to the code that decides the commands" is false as written. The miss is caught by the merge's full gate, which is the backstop the user accepted, but its cost is a failed merge after a green affected gate, the race the Problem opens with. Engine changes land on main every day or two (`git log --since=2026-10-18 --oneline origin/main -- z-nile/engine scripts/tracker`: 6 squash merges, with about 11 open branches editing `main.luau`), so the window is real. The tempting fix is to add the whole engine to the key. That invalidates every record on every engine edit, which is the change selection exists for.
Consequences: Any fix decides where records live and what invalidates them. Moving them into c0165's shared db (the main checkout's `.claude/`) keeps them when a worktree goes, but adds a writer to that db from inside the jail, which c0165 forbids (only the unjailed orchestrator writes it). Keying by the engine at the merge base invalidates every record after each engine change on main, so the first engine-touching affected gate in each worktree then runs all of z-nile once.
Recommendation: Question the mechanism, then pick with the user where needed:
- (a) Key each record also by the engine as it was at the recording checkout's merge base with `origin/main` (`git rev-parse <base>:z-nile/engine`). A branch's own engine edits are in its diff, so they select through the records as designed; an engine change that lands on main makes older records count as absent (fail closed) until a run re-records. Cost: one wider gate per worktree after each engine change on main. Cases: `endtoend`, a record made at base B1 doesn't count in a worktree at B2 whose engine differs; `record`, the runner writes the base engine id.
- (b) Make the record durable across landing: have the unjailed orchestrator (c0165's `specs.luau`), not the jailed runner, merge each run's records into the shared db, or copy them to the main checkout's `.cache` at `./zn land`/merge, and say which.
- (c) escalate to the user: keep today's mechanism and accept that a main change to nested-command behaviour can hide a spec from affected gates until the merge's full gate; then rewrite the "never trusted" sentence to name the window, and make the runner warn on a failed record write.
Whichever is chosen, add a Rules row with the mutant "a record trusted after the engine that ran it changed on main" (for (a)) and a case that seeds it.

### F6 [medium] The gate's own run rewrites the records its fingerprints and whole-gate digest read, so a change's second gate reruns the specs whose records changed and records no whole-gate row
Where: Design §3 ("Because c0165's fingerprints use the same `isInput`, reuse follows the same rule"; "The whole-gate digest … also carries, when records were loaded, the rendered `commands` table"); R28, R45; c0165.md "specs.luau run" step 3 ("A spec whose fingerprint, computed again … after the run, differs … is released and not recorded") and "Whole-gate reuse" ("At the end … computes the digest again. If it is unchanged … `gate-record`")
Evidence: (reasoned from both designs; c0165 has no prototype to run it on.) An author edits spec S (which runs `./zn list`). S's key changes, so S has no record: fail closed, every engine Luau file is an input, and S's fingerprint F_a covers them all. The gate runs S; the runner writes S's new record (`list`). Then:
- per spec: c0165 records S's row under F_a (or releases it, if its post-run recomputation reloads the context). The reviewer's gate on identical content now computes F_b, over `cmd/list`'s closure and the core only, finds no row, and runs S again;
- whole gate: the digest read before the run has no line for S; the one read after the run has `S\tlist`, so the gate counts as changed and writes no row, and the reviewer's identical gate runs too. A sibling worktree's run that adds a matching-key record during the gate does the same.
c0165's Problem promises "the author's pass serves the reviewer". With this, it doesn't for exactly the specs a change touched, which are the ones most often selected.
Critique: The interplay is between two designs and neither says it. The tempting fix is to leave records out of fingerprints. Then reuse ignores which engine files a spec ran, and a passing row survives an engine change that should rerun it.
Consequences: Recording under the fingerprint computed after the run (from the records that run wrote) is sound only when the new records select no more than the old ones did. A union from a sibling can add commands mid-run, and then the run has not covered the wider set. c0165's "inputs changed during the run" rule must tell the run's own record writes apart from real input changes.
Recommendation: Specify, in c0180 and agreed with c0165's prep: per-spec rows of a spec whose record this run created or extended are stored under the fingerprint computed from the post-run records, when every engine input of that fingerprint was also an input of the pre-run one (a subset check, which is what makes it sound); the whole-gate row is likewise recorded under the post-run digest when the post-run selection is a subset of the one that ran. Cases (with c0165's gate fixture, step 1): an affected gate after editing a spec that runs a command, then a second identical gate that reuses every spec and the whole gate; and a sibling adding a command for a selected spec during the gate, after which nothing is recorded. Rows for each, with the mutants "pre-run fingerprint stored" and "post-run digest stored without the subset check".
Lesson: z-design/quote-other-preps-before-promising
