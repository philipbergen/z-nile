### F1 [high] Specs that run engine code in-process through the `scripts/tracker/` forwarders lose their engine inputs: the graph stops at the forwarder, so with records the unit specs of `board`, `ids`, `lessons`, `status` and a dozen other engine modules are never selected for a change to their own module

Evidence: `graph.build` lists files only under its roots and builds `deps` only for those files (`z-nile/lib/graph.luau:386-410`: `graph.listLuau(root, g.files)` … `g.deps[file] = deps`), so a required file outside the roots is a leaf. ```

Each forwarder is `local m = require("../../z-nile/engine/<m>") return m`. `git grep -lE 'require\("@scripts/tracker' -- z-nile/tests | wc -l` gives 40 spec files. So, with records, a change to `z-nile/engine/board.luau` selects `c0042/cli` and `tooling/board` (they ran `board`) but not the nine board-model specs; a change to `engine/ids.luau` selects none of `c0081/ids`, `next-file`, `renamed`. These are the specs that test those modules directly, the most likely to fail. c0165's learning doesn't repair it: its context has no records (AC10), so an engine path forces `ALL` there and its step 2 stops ("nothing was missed"); every such change fails only at the merge's full gate, each time.
Critique: The `-` clause relies on "`p` in S's own closure" to cover in-process engine use, and the real graph has no such edge. `select.spec` passes because its hand-built graph holds the forwarder's edge the real graph lacks; `endtoend.spec` has no forwarder; R26 is `reasoned`. This is z-design/trace-every-way-code-runs' defect one layer further: the audit listed the forwarders and assumed the graph followed them. The tempting fix is to add `scripts/tracker` to the roots. It works for today's 18 forwarders, and the next module outside the roots that a spec requires and that requires the engine (`z-nile/lib/recordkey.luau` already requires `engine/projects`, forced only by luck) leaves the same dangling edge.

Following edges out of the roots adds files to c0165's graph, which changes no output today (`scripts/` and `z-nile/lib/` force every project), but the `--graph-only` pins (`tooling/affected`, `c0120/graph-homes`, `c0114/gate-cover`) must be re-run. A fail-closed alternative needs a definition of "dangling": a resolved `.luau` target that the graph holds no `deps` entry for.
Recommendation: Make the closure complete instead of enumerating roots: `graph.build` (or the context's builder, shared with `recordkey.graph`) follows every resolved require target transitively, inside the repository, whether or not it lies under a root. If c0165's graph must stay bounded by its roots, `isInput` instead fails closed for an engine path when S's closure holds a `.luau` file the graph has no `deps` for (as for a missing record). Correct E8's "the graph covers them" and the Wording. Row: mutant "the graph stops at files outside its roots". The graph half runs on `proto` now (it needs only `recordkey.graph`); the selection half in the amendment.

### F2 [medium] A sibling's record describes the sibling's engine, not the base's: the key leaves out the recording branch's own engine edits, so a record made on a branch that changed which nested commands run counts in every worktree on the same base (repeat of design-review-002 F5's mechanism, a third hole in record validity)
Where: Design §2, The key's files (`recordkey.engineBase`) and "So a record is valid while … A branch's own engine edits are in its diff … so they never invalidate them"; **What a record can miss** ("Records from other worktrees made on another merge base never count"); §3 `context.commands` (records from every worktree of the repository)
Evidence: The key is the spec's test-side closure, the launching tooling and the engine tree at `git merge-base HEAD origin/main`. A branch's commits don't move that merge base, and `record.spec`'s "an uncommitted engine edit changes none" (R50, run) pins that the working tree's engine stays out. Which commands a spec records is partly decided by the engine: `proto`'s record has `c0034/locator  check,done,find,members,new`, and `members` comes from the raft `check.sh` that the engine's `check` and `done` run (review 002 F5). A failing scenario:
1. An engine change lands on main (base B1); every record counts as absent. Worktree W1, on branch X, which changes `cmd/done.luau` to run member checks without `./zn members`, runs its gate first at B1. `locator` passes and records `check,done,find,new` under key K.
2. Worktree W2, on branch Y at B1 (with `done` unchanged), changes only `cmd/members.luau`. W2 has no record of its own for `locator`, so W1's line with key K counts; `locator` isn't selected, though under Y's engine it runs `members`. The merge's full gate fails it, and c0165's learning can't learn it (its context loads no records, so engine paths force `ALL`).
"What a record can miss" doesn't list this case. Right after each engine change on main, the first records at the new base come from whichever worktrees run first, and about 11 open branches edit the engine.
Critique: Each round has added one more decider to the key (round 1 the tooling, round 2 the base engine). The one left out, the engine the recording run actually ran, is left out on purpose so that a branch's own records survive its own edits. That is right for this worktree's records and wrong for a sibling's. The tempting fix is to put the working-tree engine into the key. Then every edit kills the branch's own records, and selection never narrows on the branch doing the engine work.
Consequences: Telling own records from siblings' needs either a new field (the engine as the run saw it, hashed without writing objects, as `commandrecord.key` hashes files; the format becomes `v2` with four fields, and parse, render and merge rules for it), or dropping sibling reads. The cost of dropping them is one unnarrowed engine gate per fresh worktree, the same cost the design already accepts after every engine change on main.
Recommendation: Question the mechanism and pick one: (a) each line also records the hash of `z-nile/engine` as the run saw it; this worktree's own lines count by key alone, and a sibling's line counts only when its engine hash equals this checkout's base engine (the sibling ran main's engine unmodified); or (b) `context.commands` reads only this worktree's record. In both cases, state in **What a record can miss** that c0165's learning never learns a record miss, so the merge's full gate catches it every time. Case (`endtoend`, in the amendment): W1 commits an engine change on its branch under which spec `e` runs fewer commands, and records; W2 on the same base, with no record of its own, selects `e` for the module of the command W1's engine skipped. Row: mutant "a sibling's record counted whatever engine it ran". This narrows no outcome: selection by command stays, and only which records count changes.
Lesson: zz-arch/records-cover-what-was-reviewed

### F3 [medium] The reuse behaviour round 2's F6 answer rests on has no case anywhere, R45's planned case would be an unnamed override of a promoted spec, and the spec list's way into the digest is unspecified

Critique: The answer to F6 is sound on paper (fingerprints are a superset of the selection, and the digest carries the list), but its two load-bearing claims, per-spec reuse on the second gate and no whole-gate reuse across different selections, are pinned by nothing. Recommendation: Specify the carrier now: the selection is computed once per project before the digest, written to one file, and passed to all three subcommands (for example `--specs <file>`). Add a c0180 spec (for example `acceptance/reuse.spec.luau`, written now against c0165's quoted `gatefix` like `select.spec`, run in the amendment, and requiring the promoted gatefix through `renamed.id`) with three cases: an affected gate on an engine change, then an identical second gate, which reuses every spec per spec; a third identical gate, which reuses the whole gate; and a sibling's record that widens the selection on unchanged content, after which the whole gate is not reused and the newly selected spec runs. Rows: "the spec list left out of the digest" (the widened case fails), "the list recomputed after the run" (the third gate doesn't reuse).
