### F1 [high] `endtoend`'s union case asserts that W1 counts W2's `edited` entry, which the Design forbids and the new R55 case asserts the opposite of: the designed implementation fails AC6, and only a wrong, asymmetric rule passes both cases
Where: `acceptance/endtoend.spec.luau`, "W2's own record for the same key adds its commands to W1's" (the line `write(W2, …, \`…{B}\t{key}\tfind\tedited\n\`)`, then `t.expect((affected(W1, "z-nile/engine/cmd/find.luau"))).toBe(lines({ B, C }))`), against "another worktree's entry recorded on an edited engine serves only its own worktree" and Design §3, `context.commands` ("this checkout's own entries always count, another worktree's only when `clean`"); Test plan ("W2's own record … adds its commands (the union, even marked `edited`, since it is W2's own)")
Evidence: this round changed W2's line from three fields to `…\tfind\tedited` and kept both assertions (`git diff 19b088e0..b0d77f6f -- …/endtoend.spec.luau`). In W1, W2's entry for B is another worktree's and `edited`, so by the Design it doesn't count; W1's own entry for B is `-`; so `cmd/find.luau` selects only C (the failing, unrecorded spec) in W1, and the spec expects `B, C`. The next case makes the same rule run the other way: W1's entry for A, marked `edited`, must not count in W2 (`A, C` there) while it counts in W1 (`C`). No symmetric reader satisfies both cases. A reader that trusts every entry in the repository's main worktree (W1 is the fixture's main worktree, W2 a linked one) and only clean entries elsewhere passes both, and it's wrong. The tempting fix is to delete W1's assertion. That leaves R42 (union across worktrees) tested only inside W2, and nothing would fail if a reader let W1 read W2's edited entries.
Consequences: Fixing the case means two cases: one where the union really crosses worktrees (both entries `clean`), and one where an `edited` sibling entry is ignored, from each side. The R55 case already covers the second from W2's side.
Recommendation: In the union case, give W2's line `clean` and keep `B, C` in both worktrees (the union across worktrees, R42); then rewrite it as `edited` and assert `B, C` in W2 (its own entry) and `C` in W1 (another worktree's edited entry: R55 from W1's side). ### F2 [medium] A record still vouches for content that never ran: the runner reads the keys and the `clean` stamp after the workers end, so an edit made during a run is recorded as already run (the fourth hole in record validity; the mechanism needs a rule, not another field)
Where: Design §2, Runner side ("The keys come from one call of `lune run z-nile/recordkey` … after the workers end"), **The key's files** (`recordkey.engineState`: "the runner gives it to every entry of the run"), and "So a record is valid while the spec, the test helpers it reaches, the tooling that launches `./zn`, and the engine the branch started from are unchanged"; `proto/z-nile/tests/run.luau` `recordCommands` (calls `keysOf(names)` after the lanes finish); `recordkey.TOOLING`
Evidence: I ran it on `proto`. Two scratch specs: `a` requires `./helper`, whose `run()` writes `list` into each `ZN_SPEC_TRACE` directory, then waits 8 s; `b` is empty. Before the run, `lune run z-nile/recordkey -- z-nile/tests/zzrace/a.spec.luau` printed key `51e08a1e…`. I started `lune run tests/run -- --jobs 2 tests/zzrace/a.spec.luau tests/zzrace/b.spec.luau` and, 4 s in, edited the helper to write `list` and `status`. The run passed and recorded:
```
tests/zzrace/a.spec.luau	cda66c04a076d54544b5e9eac65ae511d8e72e088a8d42cee708020332e0fceb	list	edited
```
and `recordkey` on the edited tree printed the same `cda66c04…`. So the record says the helper that runs `list` and `status` runs only `list`. Any later selection whose key matches the edited content reads it: a change to `cmd/status.luau` doesn't select `a`. The `clean` stamp has the same timing: an engine edit discarded during the run (`git restore z-nile/engine`) is stamped `clean`, and siblings then trust a record of an engine that differed (round 3 F2's case, reached through the clock instead of a commit). The stamp also covers only `z-nile/engine`, while other code that decides which commands a spec ends up running is in neither the key nor the stamp: `recordkey.TOOLING` is `zn`, `scripts`, `z-nile/check.sh`, `z-nile/lib`, `z-nile/templates`, not the runner `z-nile/tests/run.luau` or the programs `z-nile/check.sh` runs (`z-nile/affected.luau`, c0165's `specs.luau`), and a nested gate's specs record into their outer spec (§2, Runner side).
Critique: Round 1 added the tooling to the key, round 2 the base engine, round 3 the `clean` field, and each closed one way a record can describe something other than what ran. This is the same mechanism again. c0165 already settled the timing for its own records: its R31 records a pass "only under the fingerprint its run started from", with a case that edits an input mid-run (c0165.md, zz-arch/read-paired-facts-at-one-moment). The tempting fix is to move the `recordkey` call before the workers. On its own that records commands from code edited between the key read and a late lane's start under the old key, which is harmless (a key that no longer matches counts as absent), but it doesn't fix the stamp's coverage, and a fifth decider will turn up next round.
Consequences: A rule replaces the list: a record vouches only for the tree that ran. That needs (1) the keys and the stamp read before the first worker starts and again after the last one ends, with an entry written only where the two keys agree and stamped `clean` only when both stamps were; and (2) a stamp that covers everything outside the key, so the list of deciders can't miss one. For example, `clean` means "this worktree differs from its merge base only inside project roots (`*/.tracker/`)": a prep worktree (tracker files, sequestered specs) still shares its records, and an execution branch, which edits code, keeps its own. One more `recordkey` call per multi-file run (E12: 0.8 s for 405 keys).
Recommendation: Write rule (1) into §2's Runner side and rule (2) into **The key's files** (`engineState` becomes, for example, `treeState`, and the record's fourth field keeps its two values with the wider meaning; restate it in the Wording's Command trace bullet). Update **What a record can miss** and the "So a record is valid while …" sentence to match. Cases, in `record.spec` (they run now, on `proto`): a fixture spec that rewrites its own helper while it runs (the fixture is under `.cache`, so the write is allowed) leaves no entry under the new key; a run during which the fixture's engine is edited and then restored is stamped `edited`; a change to the fixture's copied runner (or any file outside `.tracker`) makes the run `edited`. Rows: "keys read only after the run", "the stamp read only after the run", "the stamp reading only `z-nile/engine`". Run them with `mut2.py` and record them in E14.
Lesson: zz-arch/read-paired-facts-at-one-moment, zz-arch/records-cover-what-was-reviewed

### F3 [medium] R45's planned reuse case covers only the harmless direction: the widening case round 3 asked for, where whole-gate reuse would skip a selected spec, was dropped without an answer, and the three-gate sequence E9 describes doesn't hold together (repeat of design-review-003 F3, in part)
Where: E9 ("add `acceptance/reuse.spec.luau` … two identical `--affected` gates …; the second reuses every spec the first ran and records a whole-gate row, and a third after the records narrowed the selection reuses every spec through per-spec reuse"); row R45; design-refute-003 F3; design-review-003 F3's Recommendation (its third case: "a sibling's record that widens the selection on unchanged content, after which the whole gate is not reused and the newly selected spec runs")
Evidence: Selection widens on unchanged content routinely: §3 reads every worktree's record, so when a sibling worktree is removed (after every landing) or its entry turns `edited`, its specs lose their record and are selected (fail closed). If the selected list is missing from the digest, the next gate's digest equals the earlier, narrower gate's, `gate-check` reuses the whole gate, and the newly selected spec never runs. That is the wrong result R45 exists to prevent. The planned cases only narrow, where whole-gate reuse of a gate that passed a superset is harmless, so the planned case kills "left out of the digest" only if it asserts which reuse path ran, and the plan doesn't say it does. The sequence itself doesn't add up: if gate 1 runs with no records, gate 2's selection is already narrower (the records gate 1 wrote), so gate 2 can't "reuse every spec the first ran"; if records existed before gate 1, gates 1 and 2 select the same list, and no "third after the records narrowed" is possible on unchanged content. The refute answers round 3's first two cases and doesn't mention the third.
Critique: The case that shows the failure (a selected spec skipped) is the one missing, and the one kept passes for both the right and the wrong digest unless it asserts the mechanism. The tempting fix is to leave the sequence to the amendment's judgement, which is what round 3 F3 already found.
Consequences: The widening case needs a way to widen on unchanged content inside c0165's `gatefix`: a second fixture worktree whose record is removed between the gates, so the fixture needs two worktrees, as `endtoend` has.
Recommendation: Rewrite E9's `reuse.spec` plan as concrete gates with the observable each asserts. (1) Records present; affected gate on an engine change; an identical second gate reuses the whole gate (`reused: an affected gate passed …`). (2) A sibling worktree's record removed, content unchanged: the third gate does not reuse the whole gate, and the newly selected spec runs. Make that spec fail in the fixture, so a skipped spec shows up as a gate that passes when it should fail. (3) Optionally, the narrowing direction with per-spec reuse. Give R45 both mutants with the case that kills each: "spec list left out of the digest" dies in (2), and "list recomputed after the run" dies in (1) (gate 1's row would be stored under the list the records produced after the run).
Lesson: z-design/spec-design-correspondence, zz-test/pin-fail-safes-where-they-act
