### F1 [medium] The `clean` stamp's two-read rule has no case: a runner that reads the tree state only before the run, or only after it, passes `record.spec` (repeat of design-review-004 F2, in part)
Where: Design §2, Runner side ("it is `clean` only when both reads said so"); **The key's files** (`recordkey.treeState`, "the runner gives every entry of the run the conjunction of its two reads"); `acceptance/record.spec.luau:297-328`; Rules and mutants (R53, R57, R58; no row for the conjunction); **What a record can miss**
Evidence: I ran both single-read mutants on `proto` (798859c9), each alone, against today's `record.spec`: `local clean = cleanBefore and cleanAfter` → `local clean = cleanAfter`: `13 passed, 0 failed, 1 spec files`; → `local clean = cleanBefore`: `13 passed, 0 failed, 1 spec files`. Round 4's Recommendation asked for the row "the stamp read only after the run"; R57 covers only the keys. The stamp read once is the defect round 4 F2 found (an engine restored during the run stamped `clean`), so the fix is unpinned. Separately, two reads can't see an edit made and undone inside the run (clean, edited, clean; or a helper edited and restored), and **What a record can miss** doesn't name that residual.
Critique: The Design states a rule no case checks, and the obvious single read (one `keysOf` call that returns both the keys and the state, used for the state only after the run) is the cheapest to write. The tempting fix is a case that edits the tree before the run, which both mutants still pass.

The fixture spec that changes the tree must itself be committed first, or its own file makes the tree `edited` before the run. Its flags must sit under the fixture's ignored `.cache/`.
Recommendation: Add to `record.spec`'s merge-base case, after line 328 (I ran this text in a clone of 3e37c7d9 with `proto.patch`: 13/13 pass; `cleanAfter` alone fails on the second assertion, `cleanBefore` alone on the first): write `z-nile/tests/h.spec.luau`, whose one case creates `{base}/z-nile/late.luau` when `{base}/.cache/h-create` exists and removes `{base}/z-nile/early.luau` when `{base}/.cache/h-remove` exists; `commit("h")`; remove the record; with `h-create`, run `--jobs 2` and expect `a`'s entry `clean == false` (clean before, edited after); remove the flag, `late.luau` and the record; write `z-nile/early.luau`, set `h-remove`, run, expect `early.luau` gone and `a`'s entry `clean == false` (edited before, clean after); remove the flag and the record, run again and expect `clean == true` (the control). ### F2 [medium] R45 names two mutants, but the amendment's `reuse.spec` plan can kill only one: "list recomputed after the run" survives every step, and the case where it does harm (records lost while a gate runs) is not in the plan (repeat of design-review-004 F3, in part)
Where: E9, the `reuse.spec` plan, steps (1) to (4); row R45 ("the list recomputed after the run, or left out of the digest extras"); Design §3, **The whole-gate digest**; design-refute-004 F3
Evidence: The plan seeds the records first, so gate 1's selection Ln is made from them. A run only merges entries for the specs it ran, which were already selected: an entry it adds keeps them selected or narrows them, so the selection recomputed after gate 1 is again Ln, and the mutant stores the same row. Steps (2) and (3) then behave the same for the mutant as for the design, and step (4) names only the other mutant. The mutant does harm when records are lost while a gate runs: a sibling worktree removed (after every landing), a sibling entry turned `edited`, or the record file rewritten. Then the list recomputed after the run is La ⊃ Ln. The mutant stores the row under La; the next gate on the same content selects La, finds the row, reuses the whole gate, and La minus Ln never runs. The Design as written (the list handed over before the run) gets this right; nothing tests it. The plan also says only "records seeded": if they are seeded by a gate, c0165's db holds per-spec passes for La minus Ln, and step (3)'s "exactly La minus Ln runs" fails for the correct implementation too.
Critique: This is the third round to find a hole in R45's test plan (rounds 3 and 4 found the widening direction missing and then the sequence broken). The mechanism itself (the list fixed before the run, in the digest) holds; what keeps failing is that the plan lists the cases one at a time. The tempting fix is to drop the second mutant from the row, which leaves the harmful case unguarded.
Consequences: A step that loses records during gate 1 needs a fixture spec in Ln that removes the record file while it runs. The runner then writes only the run's own entries at the end, and c0165's end-of-gate digest ignores `.cache`, so `gate-record` still writes the row. The seeding must leave no per-spec pass rows for La minus Ln.
Recommendation: In E9, enumerate every way the selection on unchanged content can differ from the list a gate ran, with one step each: records written by the run (narrowing, step 1), records lost between gates (step 3), and records lost during the run (new step 5: a spec of Ln removes the record file while gate 1 runs; the next gate selects La, does not print `reused: an affected gate passed`, and `ran.log` gains exactly La minus Ln; the mutant "list recomputed after the run" reuses the whole gate there and runs nothing). Say the records are seeded by a raw multi-file `tests/run` in the fixture (or by hand-written lines keyed through `z-nile/recordkey`), never by a gate, so c0165's db holds no pass for La minus Ln. Give R45's row both mutants with the step that kills each.
Lesson: z-design/spec-design-correspondence, zz-test/pin-fail-safes-where-they-act
