# c0181: Lessons codified and consolidated

## Problem
The user (2026-10-31), asked whether fixtures could copy lessons only where needed: "Can we have a consolidation process that combines lessons as we go to keep it tight, coherent, and complete?", and then: "I'd also like lessons to turn into checks when they are written, there's probably not a 1-1 opportunity to codify a lesson into a check but a significant portion should be. If it can be codified as a test it can be much less verbose in the lesson, limiting content and search".

Today a lesson is prose only (133 lesson files under `z-nile/skills/*/lessons/`, plus the projects'): each step reads them with `./zn lessons --full` and asks each one's check question by hand, nothing enforces them, they grow without merging, and every spec fixture copies all of them (c0115).

What should happen: when a lesson is written, its rule becomes a check the gate runs wherever it can be codified, and the lesson then shrinks to a short pointer to that check; a significant portion of the existing lessons are codified the same way; overlapping lessons are combined as they accumulate, keeping the set tight, coherent and complete (no source or rule lost).

Scope decision (user, 2026-11-01): "All lessons that can be converted to code should be"

Decided with the user (2026-11-01): "One raft in waves" (G4: c0181 stays one issue and one raft, run in waves of one skill group each; `solo: true`).

Decided with the user (2026-11-01): "On demand" (G6(a): the gate-time and per-commit mutation, tree and gate runs run through `./zn prove`, with the stamp checked at the move to prepared).

## Non-goals
- The fixtures' lesson copy itself stays (c0115); it shrinks as lessons do.
- Which skill a lesson is filed under and sending a finding back to the step that erred: c0136. Reading only the lessons relevant to an issue's paths: c0166. Harvesting the reviews already on `main`: c0112. The content of the two new lessons c0192 and c0193 (they use this process).

## Solution
- At every place a lesson is written (z-design's harvest, zz-execute's harvest, a lead's note), ask first whether the rule can be checked mechanically: a lint over texts run in `check.sh`'s static stage, or a spec case; `harvest.md` records `codified <path>` or `not codifiable: <why>`.
- A codified lesson keeps its frontmatter plus `enforced_by: <check>` and one line of why; the check's failure message names the lesson and how to fix it; `./zn lessons` shows enforced lessons as one line (or hides them).
- A backfill sweep of the existing lessons, reporting the share codified.
- Consolidation as we go: a new lesson that overlaps an old one is merged into it, keeping every source id; `./zn lessons consolidate` lists clusters to merge.
- Guards: every `enforced_by` exists, runs in the gate and fails on a fixture that breaks its rule.
- Reconcile with R0040, c0112, c0136 and c0166.

## Design
The issue is one chore with five moving parts, all in the tooling (scope reset by the user on 2026-11-01: every lesson that code can decide is converted, see the Problem and E2): a **state** every lesson carries (enforced by a check, or why it cannot be), the **checks** a lesson can point at (lints run in the gate's static stage, spec cases the runner already runs, and rules the tool runs at the moment of the mistake), the **shared tools** several lessons need (a proof stamp, a mutant runner, a tree-growing test helper), a **consolidation** command pair (a report and a merge that loses no source), and the **process text** that makes the lead of a prep or raft ask both questions whenever a lesson is written. A **backfill sweep** then applies it to the 149 lessons on `main` (z-nile 138, pickman 11). No game behaviour changes and `pickman/.tracker/game-design.md` is not relied on.

### The state (data model, `z-nile/engine/lessons.luau`)
`lessons.parse` accepts five more frontmatter keys (each once). The Lesson type gains them as **optional** fields (`enforcedBy: { string }?`, `enforced: ("full" | "part")?`, `notCodifiable: string?`, `distinct: { string }?`, `merged: { string }?`), as does `Item.dir: string?`, because promoted specs (`c0111/metrics-lessons`, `c0111/harvest`) build `Lesson` and `Item` literals by hand and a required field would break their type check, which the gate runs and `tests/run` does not; `parse` always fills the lists (empty when the key is absent), every reader treats nil as empty:
- `enforced_by: <ref>[, <ref>…]`, with `enforced: full | part`. A ref is a repository-relative path and, for a spec, optionally ` :: "<case name>"` (quoted, because case names hold commas). Its kind follows its path, tested in this order: a name ending `.spec.luau` is a **spec** (and must name a case); `z-nile/lints/<slug>.luau` is a **lint**; `z-nile/engine/rules/<slug>.luau` is a **rule** (a check the tool runs at the moment of the mistake, below); nothing else is a ref.
- `not_codifiable: <one line>`: why no text lint or spec case can decide the rule.
- `distinct_from: <lesson id>[, …]`: lessons of the same skill this one was compared with and kept apart.
The caps and the body measure (`lessons.CAPS`, `lessons.bodyBytes`, `lessons.capOf`) live in `lessons.luau`, the format's module, so `codify` and `consolidate` can both read them without requiring each other.
- `merged: <lesson id>[, …]`: lessons `lesson-merge` folded into this one (a hint for a stale reference, below).
`parse` stays permissive (a lesson with none of the keys parses as before; the promoted fixtures' lessons have none). The rule that every lesson states one of the two is the **policy**, which only `./zn lessons --check --policy` and the gate run, so no promoted spec's fixture changes (Regression guard).

### The policy (`z-nile/engine/codify.luau`, new, pure)
`codify.policy(all: {Lesson}, env: Env): {string}` with `Env = { files: {[string]: string}, homes: {string}, skills: {string}, docs: {[string]: string} }` returns problems, each naming the lesson and its way out. `files` holds the text of every path a lesson's `enforced_by` names (the edge reads them; an absent path does not exist); `homes` the registered projects' homes (`z-nile`, `pickman`, from `projects.load`); `skills` the names of the tree's skills; `docs` the texts of the skills' `*.md` (each `SKILL.md` and `checklists/`) and `AGENTS.md` (a path with a `/lessons/` folder in it is never scanned, even when supplied). Rules:
1. **State**: exactly one of `enforced_by` (with `enforced`) and `not_codifiable`; `enforced` without `enforced_by`, or the reverse, is a problem.
2. **Caps** on the body (the text after the frontmatter, trimmed): full 500, part 1,200, none 2,500 bytes, the cap itself allowed. A fully enforced lesson is a pointer: the rule and how to fix a failure. `enforced: full` is a claim the policy cannot read and review judges: every clause of the lesson's `check` is decided by the named checks (zz-review item 10 makes a `full` lesson whose `check` leaves a clause a finding).
3. **A lint ref** names `z-nile/lints/<slug>.luau` (not a `.spec.luau`) whose text holds `lesson = "<this id>"`; **a rule ref** is the same for `z-nile/engine/rules/<slug>.luau`. **A spec ref** is `<path> :: "<case>"` where the path ends `.spec.luau`, lies under `<home>/tests/` for a registered home and not under a `.cache` folder (the only place the gate runs specs from: `run.luau` collects `tests/` of each home; so a sequestered issue spec, an `experiments/` file or `z-nile/lints/x.spec.luau` is refused), the case is **named `[<this id>] …`**, and the spec's text holds `it(` followed by optional whitespace and the quoted name (stylua wraps long names onto their own line; the name is matched as plain text). A spec ref without a case, or a case not named for the lesson, is a problem. The `[<id>]` name is how the failing case names its lesson (the footer) and the static proof that a case was written for this rule; whether it fails when the rule is broken is recorded when the lesson is written: the item's `- codify` line for a spec ref carries `mutant: <what was broken>` and `--check --policy --item <id>` requires it (below). A promoted case cannot be renamed, so a lesson is enforced by a new case in a **new spec file outside `tests/acceptance/`** (`tests/meta/` or `tests/tooling/`; AC11b fails on any edit to a promoted file), never by pointing at the old one; a codifying helper is a new function or an opt-in, never a changed default of a helper that promoted specs already call.
4. **Reason**: `not_codifiable` is at least 15 characters and holds a space (no `n/a`).
5. **Overlap**: `consolidate.hardPairs` for lessons of one skill: each hard pair is a problem unless either lesson lists the other in `distinct_from`; `distinct_from` naming a lesson that does not exist, or itself, is a problem.
6. **Merge marker**: a body that still holds `<!-- merged from` is a problem until it is rewritten.
7. **Dangling ids** over `docs`: a backticked `<skill>/<slug>` taken whole, or one right after the word `lesson ` (any case), **whose skill is in `skills`** (so `origin/main`, `tests/run`, `z-nile/next` and `lesson foo/bar` are not lesson ids), and whose lesson does not exist, is a problem naming the file; when the id is in some lesson's `merged:` the message says `merged into <id>`. A longer id (`zz-test/old10`) is its own token; ids inside lesson files are not scanned (a lesson names another by `distinct_from` and `merged`, which rules 5 and the merge command handle).
**The harvest `codify` line** (`- codify <lesson id>: <ref>[ mutant: <what>][ part: tried <what>]` or `- codify <lesson id>: not codifiable: <why>`) is read by `lessons.parseCodify(item, text): ({CodifyEntry}, {string})` in the format's own module; `parseHarvest` skips these lines, so they are never findings, sources, `uncovered` or `tagCounts` input. The line is history: `codify.ledger(all, entries)` (run by `--check --policy` over every item) checks only its shape and that its lesson exists or appears in some lesson's `merged:`. `codify.ledger` and `codify.agree` return lines `<item>/harvest.md: codify <lesson id>: <what is wrong>`. `codify.agree(all, entries)` compares it with the lesson (a `not codifiable` line for an enforced lesson, a ref for an unenforced one, a spec ref without `mutant:`) and runs only for the item you name: `./zn lessons --check --policy --item <id>`, which z-design 5.5 and zz-execute Phase 5 run. A later codification of a lesson, or a `lesson-merge`, therefore never turns a done item's ledger red.

### The checks a lesson points at
**Lints** (`z-nile/lints.luau` runner, `z-nile/lints/lib/lint.luau`, `z-nile/lints/registry.luau`, one module per lint in `z-nile/lints/`). A lint is a pure scan over texts:
```
export type Hit = { line: number, message: string }
export type Def = {
  lesson: string, under: { string }, match: { string }, skip: { string }?, allow: { [string]: string }?, scanLints: boolean?,
  scan: (path: string, text: string) -> { Hit }, bad: { [string]: string }, good: { [string]: string },
}
lint.run(def, files) -> { string }          -- "lesson <id>: <path>:<line>: <message>" per hit
lint.scanned(def, files) -> number           -- files in scope
lint.baseline(def, files) -> { string }      -- allow entries that match nothing, or have no reason
lint.selfTest(def) -> { string }             -- problems: bad not flagged, good flagged, a fixture out of scope
```
`files` is `{[repo-relative path]: text}`. A file is in scope when it starts with a prefix of `under`, matches one of the Lua patterns of `match`, holds no `skip` substring and is not under `z-nile/lints/` (the lints' own `bad` fixtures would flag themselves) unless the def sets `scanLints`. A hit is cleared by `lint-ok <lesson id>: <reason>` (reason non-empty) on its line or the line above, or by a baseline (a reason is required): `allow` in the `Def` clears **repository paths** (history that is never edited); an **item's own baseline** is a file in its folder, `<item folder>/lint-allow.md`, with lines `- <lesson id>: <reason>`, which clears that lesson's hits in that folder and every folder below it (an item folder is `<root>/{issues,rafts}[/active|/done|/retired]/<id>`; a `lint-allow.md` anywhere else clears nothing and is a problem). `lint.unknownAllows(files, ids)` lists the lines naming a lesson that no registered lint enforces (a typo, a lint removed), which the runner reports. The new file kind joins the lists that classify an item folder's files: `trail.isDoc` (it would otherwise count as the item's document) excludes it, and it is not a design file for `raftplan.isDesignFile` (a baseline changed after rafting is not a design change); `z-nile/engine/trail.luau` joins Touched. The file is a `.md` under a project root, so `ready`, `done`, `compact` and `renumber` move and rewrite it with no code change (it names no item id), where a key in a lint module would go stale at the next compaction. A baseline entry that clears nothing (a path key matching no file, or a `lint-allow.md` line whose lint no longer hits in that folder) is a problem, and so is one with no reason; **a `lint-allow.md` under `done/` or `retired/` is history and is not judged stale** (the lints skip finished items, so every baseline would otherwise go stale at its item's `./zn done` and turn the finishing raft's gate red; c0083, in R0030, is the first). The markers lint's own `Def` is `under = { "" }` and `match = { "" }` (every tracked non-binary file: `zn`, `.py`, `.json`, `.patch` and the git hooks too; the runner skips a file with a NUL byte in its first 8 KB for every lint), scanning for a line `<<<<<<< …`, `>>>>>>> …` or exactly `=======`.
The runner (`lune run z-nile/lints [-- --root <dir>] [-- --only <lesson id>]`, a leading `--` ignored) first checks `--only` against the registry (an unknown lesson exits 2) and the root (not a readable folder exits 2); lists the root's files with `git ls-files -co --exclude-standard` when the root is a git work tree (so an ignored file such as a readied raft's `prompt.md`, which inlines specs, is never read; an untracked, unignored file is read, so a new file is linted before `git add`), and walks it without following links otherwise (skipping `.git`, `.cache`, `.worktree`); runs every registered lint; skips a listed path that is not a regular file (a tracked link such as `.claude/skills/<name>`, an entry deleted from the work tree but still indexed, which `lesson-merge` leaves before any `git add`); reads the lessons from the root's own skills folders (`lessons.load(root)`, the repository by default) **after** the scan and under `pcall` (a root with no registry prints the violations without the body, exit code unchanged, as the footer does); prints each violation, and once per lesson after its violations the lesson's body (the pointer: the fix); and exits 1 on a violation, on a lint that **scanned 0 files** or a bad baseline (a vacuous lint fails closed), 2 on a usage error. Each lint module returns a `Def`; the registry lists them; the meta check in `wiring.spec` proves each passes `selfTest` and is named by the lesson it says it enforces, and the reverse.
**Specs**: a spec case named `[<lesson id>] …`, written for the lesson (rule 3 of the policy; a tool refusal such as a `ready` or `land` rule is a rule in `z-nile/engine/rules/`, the third kind of ref, whose command-level behaviour a spec case named `[<lesson id>] …` pins). `tests/run.luau` prints, under a failing case, `lesson <id> is enforced here: <title>` and the lesson's body for every lesson whose spec ref is the failing file **and** case (`codify.footer(all, specPath, caseName)` over the lessons under `PICKMAN_LESSONS_ROOT`, default the repository; it never changes a result). The runner loads `codify` and `lessons` **lazily, on a case failure only, under `pcall`** (a computed-path `pcall(require, …)` as it already does for spec files): seven promoted specs run copies of the runner that hold only `tests/run.luau`, `tests/lib`, `lib` and the `.luaurc` files (`run-record-merge`, `fence-leftovers`, `fence-inherited-env`, `lock-start-ids`, `c0127/reuse`, `c0120/runner-home`, `c0114/gate-cover`), so a missing engine, registry or lessons folder prints exactly what the runner printed before.
**Gate**: `z-nile/check.sh` starts two static stages, **unconditionally** (unlike `skills (./zn skills --check)`, which waits for `z-nile/skills`): `lessons (./zn lessons --check --policy)` and `lints (lune run z-nile/lints)`; `--plan` prints `lessons: ./zn lessons --check --policy` and `lints: lune run z-nile/lints`. Reading every tracked text file takes 0.6 s and the scans 0.3 s (E3, measured over `git ls-files`: the set the runner reads in a work tree).

### Rules at the moment of the mistake (the tool kind)
About 35 of the lessons the plan converts are about a mistake made while using the tool (a `prepared` document that does not meet a rule, a `ready` raft, a `land` with a wrong subject, a `done` that skips a step). A lint cannot stop those, because it runs only in the gate; a rule refuses the command at the moment. `z-nile/engine/rules.luau` is the pure framework (`rules.enforce(hook, view, out)` takes the printer and returns the exit code; `main.luau` is the only edge that prints and exits) and `z-nile/engine/rules/<slug>.luau` holds one rule each (a lesson may have several, at several hooks), listed in `z-nile/engine/rules/registry.luau` as `{ path = "z-nile/engine/rules/<slug>.luau", rule = <Rule> }`:
```
export type Hook = "preparing" | "prepared" | "ready" | "land" | "done" | "commit" | "spend" | "audit" | "rewrite" | "clean"
export type View = { hook: Hook, id: string, files: { [string]: string }, extra: { [string]: any }? }
export type Rule = {
  lesson: string, hook: Hook, check: (view: View) -> { string },
  presence: boolean?, report: boolean?, raft: boolean?, needs: { string }?, applies: ((view: View) -> boolean)?, bad: View, good: View,
}
rules.define(rule) -> Rule                         -- validates the shape
rules.applies(rule, view) -> boolean               -- presence rules: the item's document has a data row in its Rules and mutants table; otherwise true
rules.check(list, view) -> { string }              -- "lesson <id>: <problem>" for each non-report rule of the view's hook that applies, minus the item's lint-allow.md
rules.reports(list, view) -> { string }            -- the same for report rules, which print and never refuse
rules.baseline(rule, view) -> { string }           -- a lint-allow.md line for this lesson that clears nothing (judged only where the view is built from the folder alone)
rules.memberReports(list, memberView) -> { string } -- the prepared-hook rules run for a member at ready/fold, as reports
rules.selfTest(rule) -> { string }                 -- bad is flagged with the lesson's id, good is clean, the hooks agree
```
`view.files` is the file map of the folder of the item the problem concerns (an issue's folder; a raft's folder for a raft-level rule such as `ready <R-id>`, whose members' folders are in `extra.members`), `view.extra` carries what a hook has beyond it (the captured text from `./zn capture`, the other items' documents, the commit subject for `land`, the staged set for `commit`, the lessons tree, the stamp), and each command builds its view at the edge and calls `rules.enforce(hook, view)`, which prints each problem followed once per lesson by the lesson's body (the pointer) and refuses (exit 1) before it writes anything (`reports` are printed and do not refuse). An item's `lint-allow.md` clears a rule's problems for the item the problem concerns exactly as it clears a lint's.
**What each hook's view carries (`extra`, built at the edge by one function per hook in `main.luau`, never by a rule).** `prepared` and `audit`: `capture` (`./zn capture`), `tree` (the tracked paths of the work tree), `others` (id to file map of the other items), `stamp` (the parsed `proof.md` or nil), `listing` (the `AC_LIST=1 bash check.sh` output and the `bash -n` status), `changed` (paths changed on `origin/main` since the stamp's `base`); `ready`: those plus `members` (each member's `prepared` view); `preparing`: `capture`, `members`; `land`: `subject`, `commits` (each `{ sha, subject, added }`), `scope`; `done`: `landed` (sha), `members`; `commit`: `staged` (paths), `unmerged`; `spend`: `phase`, `landed`; `rewrite`: `paths`, `unmerged`; `clean`: `worktree`, `branch`, `changedFiles`, `originHas` (per file: same content on `origin/main`). `rules.check`, `rules.reports` and `rules.selfTest` call a rule with a copy of the view whose `extra` holds only the rule's `needs`, so an undeclared read is nil in production as in the self-test. A rule declares the keys it reads (`needs = { "capture", ... }`); `rules.selfTest` refuses a key its hook does not build, and a `bad`/`good` view carries every key the rule needs.
**Presence and absence.** A rule that requires something to be present (a stamp, a section, a mutant column) is a *presence rule* (`presence = true`) and judges a design only when the item's document has a **data row** in its `### Rules and mutants` table. The template `./zn new` renders has the heading and the header lines but no row (pinned by `rules.spec` against the real template), and no promoted fixture writes a row (`git grep -nF '| rule |' -- z-nile/tests pickman/tests` finds only c0043's pins of the header), so the issues the promoted specs create with `./zn new` and move to `prepared` or `ready` are never judged. A rule that refuses a bad thing (a range in a commit subject, a conflict marker in a rewrite's input) is an *absence rule* and judges every view; its `bad` view is what the lesson names, which a stub does not contain. A rule with `raft = true` is raft-level (an issue-level rule never runs on a raft view); a raft-level presence rule applies when a member in `extra.members` (carried by the `preparing`, `prepared` and `ready` views of a raft) has a data row.
**Hooks and the commands that build their views.** `preparing`: `./zn status <id> preparing` (the claim); `prepared`: `./zn status <id|R-id> prepared`; `ready`: `./zn ready` and `fold` (a raft is judged by each member's `prepared` rules over its member's folder, then by its own `ready` rules); `land`: before the push; `done`; `commit`: the staged set before the commit; `spend`; `audit`: `./zn audit` runs the rules of `prepared` over every prepared item and reports (its edge builds a view only for an item some rule applies to, a data row or an absence rule, and a key it cannot build in a fixture without git is reported, never a crash, so the promoted `audit` specs stay as they are) (the gate does not run `audit`: its rules only report, so the F rows that cite `./zn audit` are enforced at `prepared` and `ready`); `rewrite`: the start of `migrate`, `remap`, `compact`, `skills`, `renumber`; `clean`: `./zn clean`, a new command (below). E2's `hook` column is mapped to these; the rows whose moment this design does not build are listed in G6, not parked.
**Order.** `rules.enforce(hook, view)` runs **after the command's existing refusals and before its first write after them** (at `land`: after the scope check, before the gate). Two promoted specs plant the very input of an absence rule to test an older refusal and assert its message: `c0072/land.spec.luau:241-247` (a commit of an issue document with a subject that lists no id, expecting the path in the scope refusal) and `c0045/workstreams.spec.luau:352-377` (conflict markers in a squash merge, expecting `unmerged`): with this order they stay green, and AC11 runs both. The sweep greps, per absence rule, the promoted specs that drive its command (`git grep -lE '"(land|commit|done|spend|ready|status)"' -- z-nile/tests pickman/tests`) and a rule message that must contain a substring an older message carried keeps it.
**Existing work.** Every prepared item a new presence rule would refuse gets a `lint-allow.md` with the reason in the PR (the sweep measures the count per wave: E2 knows it for 22 of the 41 hooked rows); a `lint-allow.md` under `done/` or `retired/` is history. A `lint-allow.md` line naming a lesson is checked against the ids of both registries (`lint.unknownAllows` receives the lint ids and the rule ids). `rules.spec` pins the framework; each rule has a `bad` and a `good` view in its module, and the sweep writes a command-level case `[<lesson id>] …` per rule (a lesson's `enforced_by` lists the rule module and that case); the wiring of the hooks is pinned by `rules.spec` as a text pin on `rules.enforce("<hook>"` in `main.luau` for each hook, as well as by those cases. `./zn status <id> prepared` is the busiest hook (about 20 rules); the first rule the executor writes is `z-design/touched-paths-exist` (hook `prepared`, E2's F-turned-P row, a presence rule over the document's Touched modules), which gives every hook's wiring a real rule to run.

### Consolidation (`z-nile/engine/consolidate.luau`, new, pure)
`consolidate.similar(a, b)` = `0.65 * Jaccard(words of title + check) + 0.35 * Jaccard(tags)`, rounded to hundredths; words are the matches of `[a-z][a-z0-9%-]*` in the lowercased title and check (hyphenated words whole), three letters or more, not in the module's `STOP` constant (the stop list of `experiments/E4-planted-scores.luau`: `the and for are but not you all can had her was one our out has have this that with from into than then does each every any its when what which who how would could should these those they them their there been being were also only same such both between through during before after above below until while about against over under again more most other some very just onto`); the score is `math.floor(raw * 100 + 0.5) / 100`; a pair's score depends on the two lessons alone, so adding a lesson never turns another pair red. `HARD = 0.35`, `SOFT = 0.20`. `hardPairs(all): { { a: string, b: string, score: number, same: boolean } }` (`a` sorts before `b`): same-skill pairs at HARD or more that neither lists in `distinct_from`. `report(all, id?)` lists, with no id, each **cluster** (the connected components of the same-skill pairs at SOFT or more, the unit a merge is decided on) as a line `cluster <skill>: <id>, <id>, …` followed by its pairs with their scores (a HARD pair not cleared marked `must resolve`), then the `related` cross-skill pairs at SOFT or more (never gated: a rule that two steps both need is not merged into one step's file, c0136), then the bodies over their cap; given an id it lists only the pairs that name that lesson, and its over-cap line. `./zn lessons --consolidate [<lesson id>]` prints it (exit 0; an unknown id exits 2; it takes no other option). Calibration on the real lessons (E1): detection finds topic neighbours, not paraphrases (true overlaps share few words but all their tags), 31 same-skill pairs are candidates and 6 hard (two clusters of real overlap: the claims/locks lessons and the fold lessons of `pickman-arch`, plus one pair to mark distinct).
**`./zn lesson-merge <into> <from>…`** (writes; not READ_ONLY; refuses to run in the main checkout of a repo with an origin, like `new`) calls `consolidate.mergePlan(tree, docs, into, froms)`, a pure function returning every file text to write or delete, then applies it. Refusals (nothing written): a lesson that does not exist, `into` among `froms`, a repeated `from`, lessons of different skills (a lesson is filed under the step that erred, c0136), both `into` and a `from` carrying a `from:` note (merged by hand), and a `from` that is **enforced** (its lint's `lesson =` field, its `lint-ok` marks and its `[<id>]` case names hold the id: merge before codifying, or un-enforce first; the sweep merges first). It then: rewrites every harvest.md of every item (backlog, `active/`, `done/`, `retired/`) through `lessons.renameIds(text, {[from] = into})` (in the format's own module, byte-preserving like `renameLedger`; an entry naming both ids names `into` once); rewrites every `<from>` token in the skills' `SKILL.md`, `checklists/` and `AGENTS.md` and in the `distinct_from` of other lessons (deduplicated; whole-id match: `zz-test/old1` does not touch `zz-test/old10`), and **never** in the survivor's own `merged:` line, its markers, or its body; drops the merged ids from `into`'s own `distinct_from`; gives `into` the union of tags, the widest `when`, the `enforced_by` union (`enforced: full` only when every merged lesson, `into` included, was enforced `full`; a judged `from` folded into an enforced `into` leaves it `part`, so the folded rule is asked again), `not_codifiable` only if none is enforced, a `merged:` list (existing entries kept), and a `from:` carried from the one that had it; appends, under `<!-- merged from <id>: tighten -->`, each `from`'s title, its `check` line and its body (so the question a step asked is folded into the survivor, not lost with the file); deletes the `from` files. It runs its writes **inside `keepRecords`** (c0116 review 003 F4: the helper `compact`, `remap` and `renumber` use; `harvest.md` is a design file for `raftplan.recordHash`, so a rafted member's harvest rewrite would otherwise leave its raft's `grouped:` entry stale and `ready` and `fold` would refuse the raft with no design change behind it), with an empty id map (`keepRecords` lists the index's paths and reads their bytes from disk, so a rewritten harvest's new bytes are hashed; a deleted lesson file is in no record): every `grouped:` entry whose member matched its record before is re-recorded, in the raft's document and in the `Grouped:` lines of its coherence reviews; an entry that did not match stays stale. Today R0053, R0054 and R0062 carry records, and f0126's harvest alone names about 30 lessons. It **verifies the invariant before writing**: the sources of `into` after the rewrite equal the union of the sources of `into` and every `from` before; otherwise it refuses. Re-run for an id already gone (and listed in `into`'s `merged:`), it rewrites any reference main added since (a harvest line in a branch merged later); `lessons --check` says `no lesson <id> (merged into <survivor>)`. `mergeLedger(text, froms, into)` is that rewrite as a pure function, returning the text and the number of lines it changed.

### The backfill sweep
Every lesson on `main` gets a state, in waves by skill (the lead runs the waves as subagents by hand: they touch disjoint folders, and `./zn workstreams` plans the issues of a raft, not the waves inside one). The plan is `experiments/E2-classification.tsv`, one row per lesson, read from the lessons themselves by five readers (class F full / P partly / N none; kinds L lint, S spec, T tool rule, helper; the clauses decided and left; the mechanism; the hook; today's hits; estimated lines; the risk or the reason). **The user's decision is the target: every lesson in the plan with class F or P is enforced; a lesson stays `not_codifiable` only with a reason that names what decides the rule.** The 7 N rows carry their reasons in the plan (the author's intent for a name or a range, a design's prose, a mutation set nobody has written); the code review judges each reason (JC2), and a reviewer who finds a symptom code can decide moves the lesson to P. A merge keeps the stricter class: a survivor takes the strictest class (F over P over N) among its own id and every id in its `merged:` line, and AC10b and JC3 judge it by that. Within a wave: **merge first** (`./zn lessons --consolidate`, `lesson-merge`, `distinct_from`), then build the shared tools the wave needs, then each lesson's check (the lint, rule or case first, with its mutant run, then the lesson shrinks to its cap), then `not_codifiable` for the rest, then tighten the bodies that remain. ### Scalability
Scores are pairwise over 149 lessons today (11,026 pairs, milliseconds); `--consolidate <id>` is linear. Lints read the tree once (0.6 s for 15 MB) and each scan is a line loop; the cost grows with files, not lessons, and a lint with a narrow `under` reads fewer files. A new lesson adds a state line and, when codified, a lint of about 30 lines; the lesson set stops growing as prose.
### Maintainability
One reader per format holds: `lessons.luau` reads lessons and ledgers (and gains `renameIds`), `codify.luau` and `consolidate.luau` take parsed values and texts, `main.luau` reads and writes at the edge; a lint is one pure module with its own fixtures, so a wrong lint is caught by its own `selfTest` in the gate. The process is stated once (zz-rules, Writing a lesson); the 14 skill paragraphs point at it. A lesson that becomes a check leaves a 500-byte pointer, so the text agents read shrinks with the codified share.
### Usability
A lead writing a lesson runs two commands and answers two questions; the failure messages name the lesson and the fix; `./zn lessons --codified` and `--consolidate` show the state of the set at a glance; steps read fewer lessons because the gate asks the enforced ones.

## Acceptance criteria

### Checked
- AC1: A lesson file may carry `enforced_by`, `enforced`, `not_codifiable`, `distinct_from` and `merged`, and one without them parses as before.
- AC2: The policy requires a state on every lesson, caps the body by level, checks that each named check exists where the gate runs it (a lint that names the lesson, or a case named for it under a project's `tests/`), makes a near-duplicate pair merge or be marked distinct, refuses an unrewritten merge and a skill text naming a lesson that is gone; a harvest `codify` line is checked for shape and its lesson, and compared with the lesson only for the item named.
- AC3: A fully enforced lesson is one line and hidden from `--when` and the prompt index, a partly enforced one stays with its question, `--enforced` and `--codified` report.
- AC4: A lint is a pure scan over a scope that names its lesson, honours `lint-ok` marks and a baseline (by path or by item), proves itself on bad and good fixtures, reads only the work tree's own files, prints the lesson's body once, and fails closed on an empty scope.
- AC5: The gate runs the policy and the lints as static stages on every run, and the registered lints and the lessons naming them are the same set.
- AC6: A failing spec case named by a lesson's `enforced_by` prints that lesson under it, and any other failure prints as before.
- AC7: Overlap is scored from two lessons' own text, hard pairs are same-skill at 0.35 or more, and `--consolidate [<lesson id>]` reports them as clusters, related lessons of other skills and bodies over their cap.
- AC8: `lesson-merge` folds lessons of one skill into one, rewrites every harvest.md and id, loses no source, refuses what it should and changes nothing when it does.
- AC9: The skills and `AGENTS.md` state the codify-and-consolidate process once and point at it, in one order.
- AC12: A rule is a pure check the tool runs at the moment of the mistake, a presence rule judges only a document whose Rules and mutants table has a data row, it names its lesson, proves itself on a bad and a good view, is cleared per item by `lint-allow.md`, is registered and named by its module both ways, every command calls it for its hook, and the proof stamp round-trips and goes stale.
- AC10: The policy and the lints pass on the repository and no hard pair is left.
- AC10b: Every lesson has a state, every lesson the plan calls F is enforced full or records the clause tried or decided, every lesson that is not enforced and does not say what was tried is an N row of the plan, and the lesson files weigh at most 220,000 bytes.
- AC10c: No lesson file is deleted unless a surviving lesson lists it in merged:.
- AC11: The lesson specs that exist, the two that pin real lessons and the zz-arch table, the two guard scans, the two skill-text pins of the refusal sentence, the two that copy the runner and the two that plant a bad input for an older refusal pass unchanged.
- AC11b: No promoted spec changes.
- AC11c: The promoted lesson specs and the new modules type-check as the gate checks them (a new required field breaks a hand-built Lesson or Item).

### Judged
- JC3: The clauses code can decide were converted. Rubric, ruled on by the code reviewer: for every lesson the plan calls F that is not `enforced: full` (or the survivor that merged it) and for ten P rows the reviewer chooses, the lesson's remaining `check` holds no clause that E2's "decided clauses" column lists, unless the item's harvest has a `- codify <id>: … part: tried <what>` or `part: decided <the decision>` line saying why that clause was given up. Pass: none found. Fail: the clause is converted.
- JC2: Every `not_codifiable` reason is right. Rubric, ruled on by the code reviewer: for each of the lessons left `not_codifiable` (the 7 of E2 and any the sweep adds), the reviewer tries to name a text pattern, a tracker or git state, or a run that shows the mistake; the reason passes when it names what decides the rule and the reviewer finds no such symptom, and a `tried:` reason passes when it says what was built and why it did not decide the rule. Pass: no lesson in the sample (every N row and every `tried:` lesson) has a symptom the reviewer can decide. Fail: any lesson with one: it moves to the plan's P and is converted.
- JC1: The sweep loses no rule. Rubric, ruled on by the code reviewer: for each lesson the sweep merges, shortens or marks `enforced`, every rule its removed text stated is in the survivor's rule, in the lesson's remaining `check`, or decided by the named check (a `full` lesson leaves no clause of its `check` undecided). Pass: no rule the reviewer finds missing in a sample of ten changed lessons chosen by the reviewer, including every merge and every `full` lesson. Fail: any rule missing.

## Implementation steps
Size, about 17,000 lines: the mechanism (engine: `lessons.luau` +120, `codify.luau` 220, `consolidate.luau` 280, `main.luau` +190; the lint library and runner 150; the rules framework 250) about 1,200; the footer, gate stages, process text and the 149 lesson files (a state line each, bodies cut or merged) about 1,300; the plan's checks and tools, E2's `lines` column, about 11,000, plus the `[<lesson id>] …` case each enforced lesson needs (about 25 lines for each of 142, E2's `lines` column omits it: 3,500), (`./zn prove` 400, `./zn mutate` 250, the tree-growing helper 200 counted once). It is a raft by itself and larger than anything the process has run; G4 says what splitting would cost. The waves are the unit of review: each wave's PR section lists its lessons, their checks and baselines.
**Waves** (decided with the user: one raft, run in waves). Wave W0 is the mechanism, W1 to W5 convert the lessons, W6 closes. Every wave starts by merging `origin/main` into the branch (lesson files and harvest ledgers are the files `main` keeps writing: a newcomer lesson gets a row in `experiments/E2-classification.tsv`, a conflicting edit is resolved before the wave's first edit), ends with `./zn lessons --check --policy`, `lune run z-nile/lints` and the specs the selector lists for what the wave touched, and its PR section lists the lessons it converted, their checks, the baselines it added and the `tried:` and `decided` records. Within a wave: merge first, then the shared tool the wave needs, then each lesson's check, then the `not_codifiable` reasons, then the tightening.
