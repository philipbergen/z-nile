### F1 [high] check.sh's AC11c line turns the promoted c0120/check-paths spec red today, and its AC10 line turns c0120/finished red at `done`
Where: check.sh:62-65 (`typecheck`), check.sh:45 (AC10's `lune run z-nile/lints`).
Evidence: I ran `lune run tests/run -- --jobs 1 tests/acceptance/c0120/check-paths.spec.luau` from z-nile/. Result: `3 passed, 1 failed`, with the message `expected "", got "z-nile/.tracker/issues/c0181/check.sh: z-nile/tests/acceptance/c0111 (from z-nile)\ z-nile/.tracker/issues/c0181/check.sh: z-nile/tests/acceptance/c0119 (from z-nile)"`. The scanner reads every word that starts with `z-nile/` as a path from the item's home. It ignores `cd "$ZN_ROOT"`, because a `cd` to a `$` word sets no folder (check-paths.spec.luau, `literals`). So `z-nile/tests/acceptance/c0111` resolves to `z-nile/z-nile/tests/…`, which doesn't exist, and no Touched entry covers it. `z-nile/engine` and `z-nile/lints` pass only through the Touched exemption. c0120/finished.spec has no such exemption, so once the item is in `done/`, `z-nile/engine`, `z-nile/lints` and AC10's `lune run z-nile/lints` (read as `z-nile/z-nile/lints.luau`) go red there too. Critique: The tempting fix is to add the two acceptance folders to Touched modules. That is false: this issue doesn't touch them. It also doesn't help at `done`, where nothing is exempt.
Consequences: Paths spelled through `"$ZN_ROOT"/…` are skipped by both scanners, because a word starting with `$` is never a literal. luau-lsp takes absolute paths, and the `--ignore='**/.tracker/**'` globs still match them.
Recommendation: Spell every checkout path in check.sh as `"$ZN_ROOT"/z-nile/engine`, `"$ZN_ROOT"/z-nile/lints`, `"$ZN_ROOT"/z-nile/tests/acceptance/c0111`, `"$ZN_ROOT"/z-nile/tests/acceptance/c0119` and `lune run "$ZN_ROOT"/z-nile/lints`. ### F3 [high] The three "fully enforced" rows still leave clauses, so AC10b's full floor of 3, which has no slack, can only be met by mislabelling (repeat of design-review-002 F4)
Where: experiments/E2-classification.tsv (the three F rows); G1; E3; AC10b (`full -ge 3`); Problem ("complete (no source or rule lost)").
Evidence: Each row read against its lesson's own `check`, by the definition the Design now gives (every clause decided):
- `zz-test/pipe-filter-keeps-the-failure`. The check is "In every `cmd | filter || true` **(or a filter after a pipe)**, does a failure of `cmd` itself still turn the check red?". The planned lint flags only `… | filter || true` in unfinished check.sh files. It misses `[[ -z $(git diff … | grep -v x) ]]`, the same defect without `|| true`. It also flags the correct form, `printf '%s\n' "$out" | grep -v x || true` over captured text, so it needs a `lint-ok` that carries a human's reading. E3 gives exactly that as the reason `plain-find-for-literals` is only partly enforced ("a lint of intent needs lint-ok marks"). The refute raised this row to `full` for the same property.
- `zz-rules/grep-markers-before-merge-commit`. The check says "over the whole tree". The markers lint's `match` is `.md`, `.luau`, `.sh`, `.toml`. `git ls-files` also holds `zn` (the main script, no extension), 13 `.py`, 11 `.txt`, 3 `.json`, 2 `.tsv`, 32 `.patch`, 2 `.diff` and the git hooks, none of which the lint reads.
- `zz-test/split-paths-still-need-renamed-id`. The check is about paths "to a **real** `tests/acceptance/<id>` or tracker folder". Fixtures build the same shapes for fixture folders (gate-cover's `z-nile/.tracker/issues/c0001/acceptance/x.spec.luau`). Telling the two apart is a reading, so again a `lint-ok` judgement.
An honest count is therefore at most 2, and only 1 unless the markers scope is widened. AC10b requires 3. The executor either stops for the user or marks a row `full`, and that row's unchecked clause then drops out of every `--when` reading and the build index: a rule lost.
Critique: This is the second round in which the full floor fails against the definition. The fixed count with zero slack is the problem, not only its rows. Re-labelling one more row won't hold.
Consequences: Every option changes a number in G1 or adds a check, and each needs the user's yes, because G1 is the author's guess.
Recommendation: Question the mechanism, and put these options to the user in G1 with their costs:
(a) Design the missing clause checks so that each row is honestly full. Widen the markers lint to every tracked regular file (NUL check for binaries, `allow` by path for any `.patch`/`.diff` that carries marker lines on purpose). Make pipe-filter also flag `$(… | filter)` substitutions whose left side is not a `printf`/`echo` of a captured variable. Each of these comes with a `bad` fixture.
(b) Split a partly decidable lesson by hand into a mechanical lesson (the lint's exact pattern, `enforced: full`, its source a `- note` line) and the judged rest. That needs a sentence in zz-rules' new section and a case showing a split keeps every source.
(c) Recount honestly and set the full floor to that count.
Whichever is chosen, AC10b's number and E2 must match a row-by-row re-read that names, for each F row, why no clause is left.

### F4 [high] "Complete (no source or rule lost)" has no criterion for rules: `lesson-merge` drops the merged lessons' `check` and title, and the byte target pushes cuts that nothing checks
Where: Problem ("keeping the set tight, coherent and complete (no source or rule lost)"); Consolidation, `lesson-merge` ("appends each `from` body under `<!-- merged from <id>: tighten -->`"); The backfill sweep ("tighten every body over its cap"); G1 (220,000 bytes); AC8, AC10b; merge.spec.luau:16-18.
Evidence: The merge gives `into` the union of tags, `when`, `enforced_by`, `merged` and `from`, and appends each `from` **body**. The `from`'s `check:` (the rule's question, the line every step asks) and its `title` appear nowhere, and its file is deleted. merge.spec can't notice, because `lesson()` gives every fixture lesson the same `title: A lesson` and `check: Is it pinned?`. The sweep also has to cut about 15,000 bytes below the capped size (G1's own arithmetic), by tightening bodies that are already under their caps. Nothing checks that a cut sentence's rule survives. AC8 pins "loses no source", but no criterion pins "no rule lost". The capture names both.
Critique: Sources got a mechanical invariant and rules got none, while a byte target rewards cutting rules.
Consequences: Keeping the `from`'s check in the marker block makes the "tighten" step fold it, and the marker rule already blocks the lesson until it is rewritten. A rule-retention check over prose can't be fully mechanical, so part of it is a Judged criterion with a rubric.
Recommendation: (1) `mergePlan` appends, under each marker, the `from`'s `title` and `check` lines before its body. merge.spec gives each lesson its own check and asserts that both merged checks' text is in `keep.md`. (2) Add a criterion for the sweep. Checked part: every `check:` line that the branch removes from a lesson file (from `git diff origin/main...HEAD -- '*/lessons/*.md'`) either still appears in some lesson on HEAD, or belongs to a `part` lesson whose new check is the clause E2 names. Judged part, for the code review: every removed body sentence's rule is in the survivor, in the lesson's check, or decided by the named check. Add a Rules row: mutant, a merge that drops the `from`'s check.

### F7 [medium] `lint-allow.md`'s reach is undefined, so a blanket exemption passes every case, and the new file kind joins no list
Where: Design, Lints ("an item's own baseline is a file in its folder … which clears that lesson's hits in every file of that folder"); lints.spec.luau:89-123; trail.luau:53-67; raftplan.luau:362-370.
Evidence: (a) `lint.run` is pure over `files` and knows no project roots, so "its folder" has to come from a path pattern, and none is given. Every case puts `lint-allow.md` next to the hit, so this mutant passes them all: honour a `lint-allow.md` in any folder and every folder below it. A `z-nile/lint-allow.md` line `- zz-test/pipe-filter-keeps-the-failure: …` would then silence the lint across z-nile/. The opposite reading (same folder only) can't clear a hit in an item's `acceptance/` spec. Those are sequestered, so they can't take a `lint-ok` mark, and E3's plain-find hits may be there. (b) Each lint's `baseline` judges only its own lesson's lines. A line naming a lesson that has no registered lint (a typo, a lint removed) is never reported stale (lesson zz-test/allowlist-keys-exist). (c) `trail.isDoc("lint-allow.md")` is true ("a Markdown file directly in its folder that is not a review, refute, ledger or prompt file"), so the trail counts it as the item's document. `raftplan.isDesignFile` doesn't list it either, so adding or changing a baseline after z-raft doesn't touch the member's record.
Recommendation: Define an item folder as `<root>/{issues,rafts}[/active|/done|/retired]/<ITEM id>`. Its `lint-allow.md` clears its lesson's hits in that folder and every folder below it, and a `lint-allow.md` anywhere else is a problem. The runner reports a line whose lesson no lint enforces. Add the file to `trail.isDoc`'s exclusions and decide on `isDesignFile` (with an override check against c0116's record specs if it joins). Add `z-nile/engine/trail.luau` (and `raftplan.luau` if changed) to Touched. Cases: a hit in `c0083/acceptance/x.spec.luau` is cleared; a `z-nile/lint-allow.md` clears nothing and is a problem; a line for an unenforced lesson is a problem.
Lesson: zz-rules/exhaustive-lists-name-new-things
