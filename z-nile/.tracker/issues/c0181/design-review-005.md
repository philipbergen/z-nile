### F2 [medium] An item's `lint-allow.md` goes stale on the day that item finishes, so the baselines c0181 plants turn other rafts' gates red
Where: Design, The checks ("a `lint-allow.md` line whose lint no longer hits in that folder is a problem"); Chore checklist, Existing work (d); E3 and the E2 row `zz-test/pipe-filter-keeps-the-failure` (the lint scans "an unfinished check.sh", "8 lines outside `done/`").
Evidence: c0083 is `status: prepared-…`, `raft: R0030` (`./zn find c0083` gives `z-nile/.tracker/issues/c0083`). The sweep puts `z-nile/.tracker/issues/c0083/lint-allow.md` there with `- zz-test/pipe-filter-keeps-the-failure: <reason>`. When R0030 runs and its `./zn done` moves c0083 to `issues/done/c0083`, the file moves too, and the pipe-filter lint no longer scans that check.sh (it is finished). So the line clears nothing, the gate's `lints` stage reports a bad baseline, and R0030's merge gate is red for a file R0030 never wrote. The same holds for any lint whose scope ends at `done/`, and for any hit that the owner's own work removes. E3 plans 14 `lint-allow.md` files for `touched-paths-exist` in designed pickman issues. Each of those goes stale when its issue finishes or is fixed.
Critique: The stale rule is right for the `Def`'s `allow` paths (zz-test/allowlist-keys-exist). For an item's own baseline, though, it creates a cleanup duty on another raft that no skill tells that raft about. The tempting fix is "the message says delete it". That still leaves a red gate in someone else's raft at merge time.
Consequences: (a) Don't judge staleness for a `lint-allow.md` under `done/` or `retired/`: a finished item's baseline is history, like the ledgers. This means one more branch in `lint.baseline`, and the file can stay. (b) Have `./zn done` drop the lines that no longer hit: a new writer in `done`, with its own cases and guard. (c) Keep the rule, have the message name the file and say "delete this line", and add to zz-execute Phase 5 and Existing work (d) that R0030 and the 14 pickman issues' rafts will meet it.
Recommendation: Take (a), the smallest change that keeps every gate green. State it in the Design next to the stale rule. Add a lints.spec case: the same stale `lint-allow.md` gives one baseline problem at `issues/c0083` and none at `issues/done/c0083` or `rafts/retired/R0030`. Add a Rules row whose mutant judges a done folder. Name R0030 (c0083) in Existing work (d) with what happens at its `done`.
Lesson: z-design/new-rules-migrate-existing-work
