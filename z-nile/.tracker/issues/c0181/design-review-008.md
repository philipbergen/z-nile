### F1 [medium] Nine of the nineteen F rows leave a clause of their lesson's `check` undecided, and the frozen plan locks them in as F
Where: experiments/E2-classification.tsv and acceptance/plan-classes.tsv (class F); G1 ("`enforced: full` means every clause of the lesson's `check` is decided by the named checks … a fully enforced lesson leaves every step's reading").
Evidence: I read each F row's columns 4 to 6 against its lesson file (`awk -F'\t' '$2=="F"' …`, then each `check:` line). Most of these rows generalise from today's instances: the lesson asks about *this* guard, list or record, and the mechanism decides only the files that exist now:
- `pickman-test/assert-between-press-and-release`: the check asks for an assertion "after the press and again after the release". The lint decides only "between a press fire and its release fire there is an assertion". The body's "after the release, assert nothing was added" and "add the wrong-phase mutant" are left (column 6: "The wrong-phase mutant is the lesson's own row, not checked here").
- `zz-test/new-commands-run-in-a-copy`: the check asks about "a new mode" of a command. The lint allow-lists the subcommands `usage, find, audit, lessons`, so a sequestered case that runs a new `lessons` mode or the new rule-running `audit` against the real checkout passes it. c0181 itself adds both.
- `zz-test/sentences-in-checks-are-grep-patterns`: "and any scanner in flight been run on this check.sh". A rule on main cannot run another prep's unlanded scanner.
- `zz-arch/reorder-by-position`: the check covers any reorder. The lint covers "the runner and tests/lib" only, and the spec covers only c0154's scheduler.
- `zz-arch/several-writers-check-the-subject`: "Who else legitimately writes this record?" is a design question for every new record. The mechanism is c0117's watermark (unpromoted, G6(d)).
- `zz-arch/one-definition-of-tracker-state`: the lint reads a named list of guard files (publish, wrapper, broker, tripwire, watermark), so a new guard outside the list is undecided.
- `zz-test/derive-after-stripping-overrides` and `zz-test/guards-move-with-the-working-directory`: "Cases already exist" for today's guards. For the next guard or the next moved folder ("this guard", "when this changes the folder") nothing decides it.
- `zz-test/allowlist-keys-exist` (borderline): "this allow-list". Only repo-fence's `ALLOWED` is pinned.
Critique: `full` takes the lesson out of every `--when` reading (Listing, `select`). Each left clause is then asked by no one, which is what G1 forbids. The executor follows the frozen F class, and the code reviewer's JC1 ("every `full` lesson" is sampled) then fails these at the end of a 13,500-line review. The tempting fix is to leave the classes and let the executor decide `part` per row. That leaves the plan wrong and the sequestered file unchangeable.
Consequences: about nine rows move F→P. The plan becomes 10 F, 131 P, 8 N, and each moved row's column 5 states the clause left, which becomes that lesson's `check`. The counts in G1, E2 and the Implementation steps change with it.
Recommendation: in prep, re-judge every F row with one test. If the mechanism names specific files, modules or instances, it decides "this X" only for those, so the lesson is P, unless the lesson is about those instances alone. Then fix both plan files (the frozen copy is still editable in prep) and the counts. For a row that can be made F by widening the mechanism (for example, a lint over every module that sorts a work list, or `new-commands-run-in-a-copy` allowing commands, not command names with any mode), say so in column 6.
Lesson: z-design/full-enforcement-means-every-clause (named in harvest.md for review 006 F7; written at landing)

### F3 [medium] The proof stamp makes `./zn prove` mandatory for every prep and re-proving mandatory at `ready` after main moves, from places where it cannot run, and no skill step says to run it
Where: Shared tools, `./zn prove` ("Tool rules at `prepared` and `ready` read it: missing, stale … is a refusal"; "stale … when `prove.baseStale` finds a path changed on `origin/main` since `base` under one of the item's Touched modules"); G5 ("the author runs each on demand"); the process bullets (z-design 5.1/5.3/5.5, zz-execute; no z-ready, no z-design step for `prove`); E2 rows `prove-specs-pass-on-a-prototype` and `rerun-skipped-checks-after-edits` (F; "`status prepared` and `ready` refuse unless proof.md … records promote-check OK").
Evidence:
- Every prep z-design writes has a data row in Rules and mutants (z-design SKILL.md:39), so every one meets these presence rules and needs a `proof.md`. Today a prototype is optional: SKILL.md:56 says "when you prototype …; a row you didn't run (no prototype …)". So the rule makes a prototype and a `prove` run (the item's specs, the overlapping items' specs, `promote-check`, lint, up to 600 s) a step of every prep. G5 still calls it "on demand", and G6 does not list it for the user, who is sensitive to CPU load.
- `ready` runs only in the main checkout (zz-rules SKILL.md:49: "`ready` and `stop` refuse to run anywhere else"), while `prove` refuses the main checkout (Shared tools). `ready` reads the item from origin/main (main.luau:4647-4671 hashes origin's files). A stamp that went stale because main changed a Touched path therefore needs a worktree, a prototype (E2's risk column: "prototypes are scratch worktrees", removed after prep) and a PR that lands the new `proof.md`, all before `ready`. For a z-nile item whose Touched list holds `z-nile/engine/main.luau`, which almost every z-nile raft changes, that is the normal case.
- `./zn prove <id> [--proto <worktree>]`: what it runs against without `--proto` is not specified.
- An item prepared on main after the sweep's last merge of origin/main has neither a stamp nor a `lint-allow.md` (Existing work (f) lists only what the PR sees), so its `ready` is refused.
- The lesson's own moment is prep: "before each review round and before the prep commit, run `git diff <prototype base> origin/main …`" (prove-specs-pass-on-a-prototype.md). It does not say "at ready".
Critique: this is a workflow change for every prep and every ready, and its cost (CPU, a kept prototype, an extra PR per stale ready) belongs to the user. Built as written, `ready` blocks most z-nile rafts after any engine change, and the way out (a `lint-allow.md` per item) turns the rule into a blanket exemption.
Consequences: judging base staleness only at `prepared` keeps the lesson's clause at its own moment. `ready` then judges the hash (renames are restamped) and only reports a moved base, which is a `report` rule the framework already has.
Recommendation: (1) Base staleness refuses at `prepared` only. At `ready` it is a report rule, and the hash and the `run`-row results still refuse. (2) Escalate to the user in G6, with the cost: a mandatory `prove` (and so a prototype) for every prep with a data row, against the stamp required only when a row is marked `run`. Record the provisional choice. (3) Specify `prove` without `--proto` (it runs in the current worktree, so a reasoned row's spec failing on a missing module is recorded `fail` and refuses nothing). (4) Add the step to z-design (before 5.5: run `./zn prove <id>`, commit `proof.md`) and to z-ready (what a refusal for a stale stamp means and who re-proves), each with a docs.spec pin. (5) Make the presence rule judge only items stamped `prepared` after the rule landed, or have the PR's last merge list the items it must baseline, so that new arrivals on main are not refused silently.

### F5 [medium] rules.spec's `needs` case requires `selfTest` to pass a rule whose `bad` and `good` views lack the key it needs, which the Design says they must carry
Where: rules.spec.luau:169-176; Design, "What each hook's view carries" ("`rules.selfTest` refuses a key its hook does not build, and a `bad`/`good` view carries every key the rule needs").
Evidence: `rule({ needs = { "capture" }, hook = "prepared" })` builds its `bad` and `good` from `view(...)`, which sets no `extra` (rules.spec:25-27, 40-41). The case then expects `rules.selfTest(reads)` to be `{}` (line 171). The natural reading of the Design's sentence is that `selfTest` checks the views carry what the rule needs. An implementation built that way returns a problem, and the case fails for it. If `selfTest` does not check this, the sentence is unenforced. Separately, a rule that reads an `extra` key it never declared still sees `nil` and may pass silently, which is the fail-open shape round 007 F6 was about.
Critique: a sequestered case that fails a reasonable implementation of the Design stops the executor, who may not edit it.
Consequences: if `selfTest` checks the views, every rule's `bad`/`good` must carry its `needs` keys, which is more fixture text per rule but no new mechanism.
Recommendation: decide that `selfTest` refuses a `bad` or `good` view that lacks a declared key. Give the case's `reads` rule views with `extra = { capture = "…" }`, and add an assertion that the same rule with bare views fails `selfTest` naming `capture`. Have `rules.check` pass each rule a view whose `extra` holds only its declared `needs`, so an undeclared read is `nil` in the rule's own `bad` view and `selfTest`'s "bad is flagged" catches it. Pin that with one more assertion.
