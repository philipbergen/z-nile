### F4 [medium] The stop hook fails open when `z-nile/roots` prints something other than name-home-root lines
Where: `scripts/hooks/stop.sh` (tooling.patch) lines 19-26; Design 3 ("Without `z-nile/roots.luau` ... it keeps the old list, as c0114's and c0120's specs pin. If the registry does not parse it gates every change: fail closed").
Evidence: the first `z-nile/roots.luau` (05b058ea, R0043) ignores `--projects` and prints the roots one per line with exit 0. awk then sees an empty `$2` for each line and builds `gated='src|tests|z-nile||'`, and `/usr/bin/grep -E '^(src|tests|z-nile||)/'` exits 2 with "empty (sub)expression". `|| true` swallows that, `changed` is empty, and the hook exits 0. Run on a fixture repository holding 05b058ea's `z-nile/` and a changed `src/a.luau`, with stdin `{"cwd": ...}`, the prototype hook printed `grep: empty (sub)expression`, exited 0 and never called the stub gate. Today's main hook, on the same fixture, wrote `gate.log` (it gated). No live worktree has such a `roots.luau` today (checked over `git worktree list`), but the hook's stated job is to keep every older tree's behaviour, and the same path fails open for any empty home or a home with a regex character.
Critique: the hole is in how the hook reads the registry's output, not in the registry itself. The tempting fix, a special case for c0114 trees, leaves the general hole open.
Consequences: validating the output means deciding what a valid home looks like. The registry's parser already restricts roots to `<name>/.tracker`, so a home is a plain folder name.
Recommendation: build `gated` only from lines with three tab-separated fields whose home matches `^[A-Za-z0-9_-]+$`. Any other line, or no line, switches to `[^/]+`. Treat grep's exit 2 as "gate" rather than "nothing changed" (`|| [[ $? -eq 1 ]] || changed=ALL`). Add a generic.spec case: a tree whose `z-nile/roots.luau` ignores `--projects` (a copy of 05b058ea's text, or a stub that prints `tracker`) gates a change under `src/`. Add a run mutant: today's awk line.
Lesson: zz-arch/guard-no-is-explicit

### F5 [medium] A new project's raft prompt doesn't carry the rules its skills defer to
Where: Design 2 ("Each project's raft prompt inlines its own skills (`skills.INLINED`, c0115), so they are short and say where the rules are"); `z-nile/engine/main.luau` `inlinedSkills`.
Evidence: `inlinedSkills(project)` inlines `skills.INLINED` (the five zz- skills) and then only the skills whose `sk.project == project`. A snake raft's prompt therefore holds `snake-arch` and `snake-test`, whose substance is "Read `pickman/skills/pickman-arch/SKILL.md` first ... Its Layout rows, Rules 1 to 8 and Design checklist are snake's too" and "The spec tiers ... are pickman's ... read it". pickman-arch and pickman-test are not inlined. z-ready's own description promises "the self-contained prompt ... for any agent (Opus, Grok, ...)". The design's reasoning runs backwards: because the prompt inlines only the project's own skills, short pointer skills leave the rules out of the prompt.
Critique: the tempting fix is to copy pickman's rules into each skill, which the design rightly rejects (five copies that drift).
Consequences: the prompt builder has to know a skill's base. A hand list such as "games also get pickman's" would be a new pickman-only path in the tooling, which is the thing this chore removes.
Recommendation: give a project skill an optional frontmatter key (for example `extends: pickman-arch`), read by `skills.luau` (one reader). `inlinedSkills` appends each named base after the project's own skills, refusing a missing name. Each of the ten skills names its base. Add a spec case (generic.spec, or a new z-nile tooling spec): the rendered prompt of a fixture snake raft contains pickman-arch's and pickman-test's SKILL.md. Add a mutant: `inlinedSkills` without the base step. This stays inside the captured "generalize pickman-only paths in the tooling" and adds no game code.
