# c0189: Real repository refuses fixture identity commits

## Problem
The real repository refuses any ref update to a commit authored or committed under @example.invalid, so prototype branches can't trip every running gate

The user (2026-10-31), after another gate failed on `REPOSITORY CHANGED … refs written by a fixture appeared: refs/heads/proto-f0147`: "This is really annoying".

The tripwire (`z-nile/tests/lib/fence.luau`, `snapshot`/`changes`) fails a run when a ref whose tip is authored by `*@example.invalid`, the spec fixtures' identity, appears during it. Other sessions make prototype worktrees in the real repository and commit there as `proto <proto@example.invalid>`, so to every running gate their branches look exactly like a spec escaping its jail. Each trip costs a full gate re-run (about 6 min) and a question to the user. On 2026-10-31 five such refs existed: `proto-f0147` (d1c34d36, "proto f0147: spec types (scratch)") and `proto-wall-picks-base`, `-base2`, `-base3`, `-touch`. c0157 diagnosed this (its E1), but its fix is a prose rule ("prototypes live in scratch clones"), which sessions keep missing.

What should happen: no commit made under a fixture identity can land on a ref of the real repository, so a prototype can't trip anyone's gate; the session that tries is told at once what to do instead. Spec fixtures (their own repositories under `.cache`) are unaffected, and the tripwire keeps catching a real escape.

Decided with the user (2026-10-31):
- "New fast chore": a mechanical guard, shipped ahead of c0157. c0157 keeps its gate slots and its clearer tripwire message, and its prose rule points here.
- "Yes, retry once": until this lands (and after, for anything it misses), a session may retry a gate or `./zn land` once without asking when the tripwire's only finding is refs that are each checked out in a live `.worktree/<name>` outside `.cache`; it says so, and stops and asks if it fires again. Every other finding still stops and is reported. AGENTS.md and zz-test's "If the tripwire fires" say so.

Decided with the user (2026-11-01): G2 "Accept" (no pre-push hook; a pushed fixture-tip branch fails fetches loudly until deleted on origin), G4 "Delete them" (the four old proto-wall-picks-* branches are deleted once no worktree holds them).

## Non-goals
- Machine-wide gate slots and the tripwire's clearer message: c0157.
- Deleting or rewriting the existing fixture-identity branches: they belong to other sessions; the guard only refuses new updates to them, and prep reports them to the user.
- Prep adds (nothing the capture asked for): chaining a person's own `reference-transaction` hook behind this one (`./zn hooks` refuses to overwrite one instead); a `pre-commit` or `commit-msg` hook (a ref update is where almost every commit, branch, fetch and worktree passes through; the exceptions git makes are in Risks); any change to the tripwire's code (`fence.luau` is read, not edited); a check in CI (GitHub Actions does not run the gate).

## Solution
- A `reference-transaction` hook in the real repository's common hooks folder (every worktree): on `prepared`, for each new non-zero commit, one `git log --no-walk --format='%H %ae %ce'`; an author or committer email ending `@example.invalid` refuses the transaction with a message naming the scratch clone or the user's own identity as the fix.
- `./zn hooks` installs it by rename (never overwriting an unknown hook); `./zn hooks --check` (read only) is in the gate's static stage beside `./zn skills --check`; `setup.sh` runs `./zn hooks`.
- The same words in z-design (its experiments bullet), zz-execute Phase 1 and zz-test: a prototype lives in a scratch clone or commits with the user's identity, never as `@example.invalid` outside `.cache`; and the retry-once rule in zz-test and AGENTS.md.
- Experiments: which refs on origin and locally have fixture-identity tips (so no fetch the user needs is refused); that commit, fetch, `worktree add -b` and `update-ref` all run the hook; its cost per `./zn` publish.
- Prep detail (added after the capture, same outcomes): the hook reads the transaction with `awk` and the identities with one `git rev-list --no-walk=unsorted --stdin --format='%ae%x09%ce'` instead of `git log` (see Design, "The hook"); `./zn hooks` also refuses a git configuration that moves the hooks folder, because the hook would never run; the gate's stage and `--plan` line; the merge's clone runs `./zn hooks` before its gate.

### The hook: `z-nile/lib/repo-hooks/reference-transaction`
`./zn hooks` installs `origin/main`'s copy of it (below) as `<git common dir>/hooks/reference-transaction` (`git rev-parse --path-format=absolute --git-common-dir`). That folder is shared by the main checkout and every worktree, so one install covers all sessions. Its second line is the marker `# pickman-repo-hook: reference-transaction`.
- **When it acts.** Only in git's `prepared` phase (the other three phases exit at once). git then aborts the transaction when the hook exits non-zero (`fatal: in 'prepared' phase, update aborted by the reference-transaction hook`).
- **What it considers.** One `awk` reads the `<old> <new> <ref>` lines. An update counts when `old` differs from `new`, the ref is `HEAD` or starts with `refs/`, and `new` is a non-zero hex object name; and, once a fixture identity has matched (the slow path, so an ordinary update costs nothing more), only when the ref does not already hold `new` (`git rev-parse -q --verify <ref>`: during `prepared` the ref is locked but not yet written). That test is for refs under `refs/` that every worktree shares; `HEAD` and the per-worktree refs (`refs/bisect/`, `refs/worktree/`, `refs/rewritten/`) are judged by the line's `old = new` only, because git may run the hook in another worktree than the one whose `HEAD` it writes: `git worktree add --detach <dir> <fixture commit>` run from a checkout already at that commit would otherwise read the caller's `HEAD`, find it equal, and pass (design review 005 F2). The two tools that need the test, `rebase --abort` and `pack-refs`, write a branch, not `HEAD`. So these are allowed without a look: **deleting a ref** (`new` all zeros; `git branch -D` sends `0000 0000`, `update-ref -d <ref> <old>` sends `<old> 0000`), a **no-op update**, a write of the value the ref already holds, whether the line says `<v> <v>` (a `git stash`, a checkout or a worktree on a branch that already sits at a fixture commit) or leaves the old value unverified, `0000 <v>` (what `git rebase --abort` and `git pack-refs` send for the ref they restore or pack; design review 004 F1), a **symbolic update** (`new` is `ref: …`), and a **pseudo-ref** (`ORIG_HEAD`, `CHERRY_PICK_HEAD`, `REBASE_HEAD`, `AUTO_MERGE`, a worktree's own `worktrees/<name>/HEAD`, …). The pseudo-refs are a narrower reading of the captured "any ref update" than the literal one: see G3, which asks the user.
- **What it reads.** The distinct new names go to one `git rev-list --no-walk=unsorted --stdin --format='%ae%x09%ce'`: the author and committer address of each new commit. (The capture's `git log --no-walk --format='%H %ae %ce'` does the same job; `rev-list` is plumbing that no `log.showSignature` or other user setting can pad with extra lines, and `--stdin` keeps the argument list short for a fetch with thousands of refs.) A tree or blob prints nothing and so is allowed; a tag peels to its commit. If `rev-list` fails (a missing object, a broken repository) the hook **refuses**: `reference-transaction (z-nile/lib/repo-hooks): cannot read the new commits; refusing (remove the hook only if git itself is broken)` (a guard acts on its one explicit "no", zz-arch rule 7).
- **What it refuses.** A new commit whose author **or** committer address ends in `@example.invalid`, in any letter case, and only at the end (`x@notexample.invalid`, `x@example.invalid.test` and `example.invalid@normal.test` pass). A cheap case-insensitive substring test runs first, so an ordinary update costs no exact test.
- **What it says** (stderr, exit 1), one line per identity, the refs after the colon (a tag object is peeled to its commit first, so an annotated tag's ref is named too):
```
reference-transaction (z-nile/lib/repo-hooks): refused. A commit written under a fixture identity (@example.invalid) cannot become a ref of this repository:
  <8-char sha> (author|committer <address>): <ref> [<ref>…]
A remote-tracking ref means a branch on the remote carries the identity: delete that branch there.      (only when a listed ref is under refs/remotes/)
If this stopped a rebase or cherry-pick of older prototype commits: git rebase --abort (or git cherry-pick --abort), then merge instead of rebasing, or move the prototype to a scratch clone.
If this stopped a checkout, switch, reset or fast-forward merge (not a commit), git has already changed your files: git reset --merge puts them back and keeps your own edits. Merge a prototype branch with git merge --no-ff; look at one with git worktree add <dir> <branch>.     (only when HEAD is among the refused refs)
Fixture identities belong only to spec fixtures under .cache. A prototype lives in a scratch clone (git clone this checkout into $TMPDIR or the scratchpad) or commits under your own identity (git commit --amend --reset-author takes over a prototype commit; c0189, zz-test skill). Pushing a prototype to a repository with this hook is refused the same way.
```
(The checkout line exists because git changes the index and working tree before it writes the ref: after a refused `checkout --detach`, `switch -c`, `reset --hard` or `merge --ff-only` the fixture commit's files are in the tree, and an ordinary `git commit -a` would record them and revert newer work (design review 005 F1). `git reset --merge` puts the tree back and keeps the person's own edits; it is not for a refused commit, where it would drop the staged work, so the line says "not a commit" and appears only when `HEAD` is among the refused refs, never for a fetch, `update-ref`, `branch` or `tag`. `--reset-author` is named because `--amend` keeps the prototype's author and a retry under the person's own identity would be refused again. The last sentence is for the session that does keep its prototype in a scratch clone and then pushes it back: the receiving repository refuses it, and the pusher's side shows only this text. A local push reaches the hook after git has moved the pushed objects into the repository, so it reads them like any other commit; `repo-hook.spec` pins the push both ways.)
- **Same domain as the tripwire.** `z-nile/tests/lib/fence.luau` has `FIXTURE_EMAIL = "@example.invalid"` and the tripwire flags a ref whose tip's **author** has it. The hook refuses a superset of what it sees (author or committer, `HEAD` too, any letter case), but it does not see everything the tripwire does: git writes `git branch -m <old> <new>` (the creation of `<new>`) and `git branch -c` outside a ref transaction, so a fixture-tip ref can still appear that way (E12, Risks, G4), and a `git merge --no-ff` of a fixture branch under an ordinary identity brings fixture commits into `HEAD`'s history, which the tripwire's "HEAD gained commits written by a fixture" rule reads. `wiring.spec` pins that both name the same domain (lesson zz-test/one-rule-one-function: the hook is shell and cannot call the Luau constant, so a spec reads both).
- **No effect on fixtures.** A fixture has a repository of its own (`git init`, or a `git clone`, which copies no hooks), so nothing installs this hook there; `repo-hook.spec` proves a plain repository and a clone of a hooked one still take fixture commits. A check run's fence points git at `z-nile/lib/git-hooks/` (`core.hooksPath`, unjailed runs only); that hook decides first and, for what it allows (a fetch into `refs/remotes/`, an empty transaction), runs the repository's own hook of the same name with the same arguments and input. So in a fenced `check.sh` flow this hook still runs for a fetch onto a fixture tip. What the fence's hook (c0122, c0123) passes on and when: it decides only in the `prepared` phase and runs the repository's hook after it has allowed the update; the other phases (`preparing`, `committed`, `aborted`) go straight to the repository's hook with the same arguments and input, so this hook also sees a refused update as `preparing` then `aborted`: it acts on `prepared` only and exits at once in the other three. An empty transaction (a fetch with nothing new) arrives with empty input and passes; a fetch that brings refs under `refs/remotes/` passes unless a new tip is a fixture identity, and E1 finds none on origin. This chore adds and changes nothing under `z-nile/lib/git-hooks/` (c0123 pins its content): the hook is in `z-nile/lib/repo-hooks/` and is installed only into the real repository's common hooks folder. `repo-hook.spec` drives the fence's hook with the fixture named as protected and proves both: a normal fetch passes, a fixture tip is refused with this hook's message, a branch update is still the fence's refusal, an empty transaction passes through the chain, and the other three phases pass straight through it.

### `./zn hooks [--check]` and `hooks.plan`
`hooks.plan(state)` is pure. `state` = `{ dest, from, source, kind, installed, executable, redirects }`: where the hook goes; where the reference text came from (`from` = `origin/main` or `tree`) and the text itself (nil when that place has none); what is at `dest` (`absent`, `file`, `link`, `other`), the installed text and its executable bit; `reviewed` (the installed text is one `origin/main`'s history of the source has held), and the git setting that moves the hooks folder, if it does. It returns `{ action = "ok" | "install" | "refuse" | "none", problems, older }`; every problem is one line starting `hooks:` and names the path and the fix. In the table `<ref>` is `origin/main's z-nile/lib/repo-hooks/reference-transaction` or, for `from = tree`, `this tree's z-nile/lib/repo-hooks/reference-transaction`:
| state | action | problem |
|---|---|---|
| `from = origin/main` and that copy does not exist (before the change that adds the hook has landed) | none | `hooks: origin/main has no z-nile/lib/repo-hooks/reference-transaction yet, so there is nothing to install or check` |
| the reference text missing, or without the marker | refuse | `hooks: <ref> is missing or has no "# pickman-repo-hook: reference-transaction" line, so there is nothing to install` |
| git follows a setting that moves the hooks folder (any scope but `command`) | refuse | `hooks: git reads hooks from <path> (<scope> configuration), so <dest> would never run; remove that setting from your <scope> git configuration, or set it to this repository's own hooks folder` |
| `dest` is a symbolic link | refuse | `hooks: <dest> is a symbolic link; ./zn hooks replaces only its own regular file: remove the link, then run ./zn hooks` |
| `dest` is a folder or special file | refuse | `hooks: <dest> is not a regular file; ./zn hooks replaces only its own regular file: move it aside, then run ./zn hooks` |
| nothing at `dest` | install | `hooks: <dest> is missing; run ./zn hooks` |
| a file with no marker line | refuse | `hooks: <dest> is a hook ./zn hooks does not recognise (no "# pickman-repo-hook: reference-transaction" line); it never overwrites one: move it aside, then run ./zn hooks` |
| our file, executable, text differs from the reference but is one `origin/main` has held | install, `older` | `hooks: <dest> is an older reviewed copy of <ref>; run ./zn hooks to update` |
| our file, text differs from the reference and `origin/main` never held it (a hand edit, a branch's copy), or it is not executable | install | `hooks: <dest> differs from <ref>; run ./zn hooks` |
| our file, exact, not executable | install | `hooks: <dest> is not executable, so git skips it; run ./zn hooks` |
| our file, exact, executable | ok | none |
All problems are listed (source, then redirects, then the file), not only the first; any `refuse` makes the action `refuse`; `none` is returned before anything else is judged. `hooks.blobIds(raw)` reads the blob names out of `git log --first-parent --format= --raw --no-abbrev origin/main -- <source>` (the new name of every `:<mode> <mode> <old> <new> <status>` line, a deletion's zeros left out); `cmd.hooks` hashes the installed file (`git hash-object`) and looks it up, only when the installed text differs from the reference and is ours (one extra git read, only then). "Ours" means a line that is exactly the marker. `hooks.redirects(listed, own)` turns `git config --show-scope --get-all <hooks.CONFIG_KEY>` output (`<scope><TAB><value>` lines, in the order git reads them) into at most one redirect, the value git follows: the last one, ignoring the `command` scope (what the fence passes through the environment), and none when that value is the repository's own `hooks` folder. So a global value that a local one sets back to the own folder is no redirect. The setting's name is spelled once, as `hooks.CONFIG_KEY`, in this pure module; `main.luau` passes the constant and names nothing.

**Why `origin/main`, and not the working tree (design review 001 F1).** The installed file is one file all checkouts share. Judging and installing it from whichever tree runs the command made two checkouts with different hook text turn each other's gates red, and let an unmerged, unreviewed edit become every session's hook (a faulty one would refuse every ref update everywhere). So the reference is `origin/main`'s copy, read with `git ls-tree` and `git cat-file blob` (the raw bytes: nothing trimmed, so the installed file's blob id is one `origin/main` holds; design review 003 F2) from the local remote-tracking ref (no network; `./zn sync` and every publish keep it fresh). A repository with **no `origin` remote at all** (the Merging clone, which removes `origin`; a repository with no remote) has nothing else and uses its own tree's copy, which is a reviewed head there. A repository **with** an `origin` whose `main` was never fetched is an error (`hooks: origin has no main fetched; run git fetch origin main`), never the tree's copy: that would be the unreviewed-install route again (design review 002 F4). A repository whose `origin/main` has no such file yet (this chore's own branch until it lands) has nothing to install or judge: `none`, exit 0. A failed read of `origin/main` (`ls-tree`, or its history) is an error in both modes (`hooks: cannot read origin/main: …`), never "no hook" (design review 002 F3; pinned by a case and mutant S5).

**"Reviewed" means a text main itself held (design review 003 F1, 004 F2).** PRs land here by `gh pr merge --squash` (zz-rules Merging) and a capture lands as the single commit `./zn land` pushes, so each text on `main`'s first-parent chain was a reviewed tip. `--first-parent` also keeps out the work-in-progress commits of a PR that was merged with a merge commit (#152 was one: 4 of `origin/main`'s 1,210 commits are merges), which a plain `git log origin/main -- <source>` would list as held. What would break "reviewed" is a rebase-merge or a direct push of several commits, which the flow forbids. A shallow or rewritten `main` loses old texts, which only makes `--check` red until one `./zn hooks`. (`hooks-command.spec` models a merge-commit PR, the case `--first-parent` exists for.)

**A legitimate fetch does not turn gates red (design review 002 F1).** The record `origin/main` is moved by every session's fetch, so judging the installed file by "differs from `origin/main`'s" would turn every session's gate (`done`, `land`, the stop hook's) red at the first fetch of a changed hook, and the fix writes the shared git directory, which AGENTS.md tells sessions not to repair. `--check` therefore also accepts, with the note above and exit 0, an executable copy of our own file that `origin/main`'s history has held: an older reviewed hook still refuses fixture commits. A text `origin/main` never held stays red, and `./zn hooks` always installs the newest. The cost: a fix to the hook cannot force itself on gates; whoever wants it everywhere says so, and each session updates with one line.
`cmd.hooks` (main.luau) reads the state: `git rev-parse --path-format=absolute --git-common-dir`, `test -L/-f/-e/-x` on `dest`, `git rev-parse --verify -q refs/remotes/origin/main`, `git ls-tree` and `git cat-file blob origin/main:<source>` (or the tree's file), the config command above, the installed file. Then:
- `none` (either mode): prints its one line to stdout, writes nothing, exits 0.
- `./zn hooks --check`: writes nothing. An `older` copy prints its note to stdout and exits 0. `ok` prints `hooks: reference-transaction installed in <dir>, ok` (exit 0); anything else prints the problems to stderr and exits 1.
- `./zn hooks`: `refuse` prints the problems and exits 1, touching nothing; `ok` prints `hooks: <dest> is up to date` and writes nothing; `install` writes the reference text to a temporary file of its own in `<dir>` (`mktemp <dir>/.reference-transaction.new.XXXXXX`: two installs at once, as after the merge when every session is told to run the command, must not share one name, or one could move the other's not-yet-executable file into place; design review 003 F4) through `sh.writeReplacing` (z-nile/lib/replace-file.pl: never written through a link), `chmod 755`, then `mv -f` onto `dest` (a rename: the old hook keeps working until the new, complete, executable one replaces it), and prints `hooks: installed <dest>` or `hooks: updated <dest>`. A failure removes the temporary file and prints `hooks: could not install <dest>: <why>` (exit 1).
- An unknown option or an argument: `usage: ./zn hooks [--check]` (exit 1).
- **Where it runs.** In the main checkout (it writes the git directory, not the working tree: zz-rules' list of commands allowed there gains `./zn hooks`, and `hooks --check` joins its read-only commands), in any worktree (the folder is the shared one), and in a clone. It is not in `READ_ONLY` (main.luau): `guardRepoRoot` runs first, so a fixture whose own `.git` is missing cannot fall through to an enclosing repository.

### The rules in prose

### Chore checklist

- **Existing work.**
  - *Fixture-identity refs and branches that hold fixture commits today* (E1, re-run at the end of prep, 2026-11-01): four local branches have a fixture-identity **tip**: `proto-wall-picks-base`, `-base2`, `-base3` and `-touch` (`proto@example.invalid`, 2026-10-25); no remote-tracking ref has one. ### Scalability
The hook costs 3 execs for the three non-acting phases plus, on `prepared`, one `awk`, one `git rev-list` and a subshell. Only after a fixture identity has matched (the slow, refusing path) does it loop in the shell: one `git rev-parse` per update of the transaction, and one more per kept update. A 4,000-ref transaction took 70 ms (E7); the first draft, which looped in sh, took 12 s on macOS's bash 3.2. `./zn hooks` is 1 `git rev-parse`, 1 `git config`, 4 `test` calls and two file reads, whatever the number of worktrees (the folder is shared). The gate gains one static stage that runs in parallel with the others.

### Maintainability
The domain is spelled in three places (the hook, `fence.luau`, `repo-fence.spec`'s fixture rule) and one spec pins the first two together. The hook's behaviour is in one 50-line file; the state-to-action logic is one pure function with a table above; the command is the only reader and writer. A second repository hook (say a `pre-push`) plugs in by adding a file under `z-nile/lib/repo-hooks/`, a name in `hooks.NAME` generalised to a list, and a marker line; the pure `plan` already takes a state per hook.

### Usability
A refused commit says which ref, which commit and which role, and the two ways out (a scratch clone or your own identity), and, for a remote-tracking ref, that the branch must go from the remote. A missing or stale hook says `run ./zn hooks`; a hook it does not know, a link, a folder and a redirecting setting name the file or the setting. `./zn` with no command lists `hooks [--check]`. Every list that must name the command does (zz-rules main-checkout list, table and "Other commands"; usage; zz-arch layout; reviewer's guard list; SETUP.md).

### Risks
- **A fixture-tip branch on origin blocks `git fetch origin`** until deleted there (E5), and nothing refuses the push that puts it there (E11): a worktree whose tip is a fixture commit made before the hook, or a `commit-tree` object, can be pushed. The captured outcome is "refuses any ref update"; the alternative, exempting `refs/remotes/`, would let such a ref reach the tripwire again (today's behaviour for that case). A `pre-push` hook under the same command would close the route (about 40 lines, a second name in `hooks.NAME`, three cases); `git push --no-verify` would still skip it, which the fetch refusal backs up. Not decided here; G2.
- **A fix to the hook cannot force itself on gates.** An older reviewed copy passes `--check` with a note (F1); a session updates with one idempotent line. `./zn sync` could reinstall after its fast-forward; not done (it would put the git directory among what `sync` edits, which AGENTS.md lists).
- **Routes the hook cannot see** (E12, design review 002 F2): `git branch -m <old> <new>` reports only the deletion of `<old>`, `git branch -c` and a copy call no hook, and `git merge --no-ff` of a fixture branch under an ordinary identity brings fixture commits into history without a fixture tip. So a session that renames or copies one of the four old `proto-wall-picks-*` branches still creates a new fixture-tip ref and trips every running gate,. Closed only by removing the input: the four old branches. They are other sessions' branches, so G4 asks the user; the zz-test bullet tells sessions never to rename or copy a fixture-tip branch.
- **The reference can be moved by the same user.** `origin/main` is the local remote-tracking ref; `git update-ref refs/remotes/origin/main <commit>` or `git fetch origin <branch>:refs/remotes/origin/main` points it at any commit, and `./zn hooks` then installs that commit's hook text (design review 003 F5). Known limit: the threat this guard answers is a careless session, and moving `origin/main` is a deliberate act; `--check` stays offline, and a published-tip check (`git ls-remote`) on the install path is not added.
- **Cost.** About +30 to +45 ms per ref update on a machine at load 25 (E3), of which +15 to +25 ms is the bare cost of any hook running four times.
- **git older than 2.28 has no `reference-transaction` hook**; the fence already needs it (`SETUP.md`'s supported hosts have 2.34+). `--check` does not test the version.
- **A hook install is per repository.** A new clone or machine needs `./zn hooks` (`setup.sh` does it; the gate says so).

## Acceptance criteria

## Guesses (pending user)
1. **G1** (pending user): `repo-fence.spec` widens in two narrow ways (Regression guard): `hooks.luau` (a pure module with no process call) may name the setting that moves the hooks folder, and `repo-hook.spec` alone may commit under four non-fixture addresses inside its own `.cache` fixture. The first is the one name the scan bans because it turns the fence's hooks off, allowed in the file that only holds the string; the second relaxes the rule that a fixture never commits under a real identity, needed to prove the hook lets an ordinary identity and the lookalike domains through; the jail and the ref guard still stop anything reaching the real repository. Recommended: accept. The alternatives: derive the lookalike addresses from the fixture one at run time (passes the scan without saying so; not recommended), or drop the cases that need a non-fixture identity (the hook's allow side would go untested).
2. **G2** (decided: `Decided with the user (2026-11-01): "Accept"`, option (a), no `pre-push` hook): the hook refuses a fetch into `refs/remotes/` too, as the capture says ("any ref update"), and nothing refuses a push. A prototype pushed to origin (`git push origin <old fixture-tip branch>`, or a worktree whose tip is a fixture commit made before the hook; E11) reaches the remote, because only the local remote-tracking update is refused; then `git fetch origin` fails for every session until the branch is deleted there (E5). Today the same ref would trip every running gate instead. Options and costs: (a) accept as designed: the failure is loud and the message names the fix; (b) add a `pre-push` hook to the same install: about 40 lines, `hooks.NAME` becomes a list, three more cases (push of an existing fixture-tip branch refused, an ordinary branch with fixture history allowed, the fence's chain), and `git push --no-verify` still skips it; (c) exempt `refs/remotes/` from the hook: a fetched fixture-tip ref then reaches the tripwire as it does now, and nothing fails a fetch. Recommended: (a) now, (b) as its own chore if a push ever happens (it has not in the repository's history; E1 finds no fixture tip on origin).
3. **G3** (pending user): "refuses any ref update" is read as the updates of `HEAD` and of refs under `refs/` to a non-zero, changed object name: the pseudo-refs `ORIG_HEAD`, `CHERRY_PICK_HEAD`, `REBASE_HEAD`, `AUTO_MERGE`, `FETCH_HEAD` and a worktree's own `worktrees/<name>/HEAD` are left alone, as is a symbolic update. Reason: `ORIG_HEAD` takes the *old* tip, so judging it would block `reset` and `rebase` away from the four old branches, and the tripwire reads only `for-each-ref` and its own `HEAD`. Recommended: accept. The alternative judges them too, by their new value only; then `git reset --hard main` while on an old fixture branch must stay allowed (a new rule and spec case), and nothing the tripwire flags becomes any harder to create.
4. **G4** (decided: `Decided with the user (2026-11-01): "Delete them"`, option (a); the lead asks the owning sessions and deletes the branches no worktree holds, outside this raft): the hook cannot see `git branch -m` and `git branch -c` (E12), so the four `proto-wall-picks-*` branches can still be renamed or copied into new fixture-tip refs that trip every running gate (and the tripwire's rule "HEAD gained commits written by a fixture" is not covered by any ref hook either). Options: (a) delete the four branches once `git worktree list` shows no worktree holds them: closes the route for good, and they belong to other sessions; (b) keep them and accept the route as a known limit, which the zz-test bullet already states ("never rename or copy a branch whose tip is a fixture commit: delete it, or look at it with `git worktree add <dir> <branch>`"). The same applies, with the same options, to the history-holding branches `proto-f0147` and `proto-f0143-deps` (Existing work): their owners may rebuild them without the old commits (for example as a squash under their own identity), or keep them and only merge. Recommended: (a), by their owners, when convenient; (b) until then.
