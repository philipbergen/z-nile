# c0189: Real repository refuses fixture identity commits

## Problem
The user (2026-10-31), after another gate failed on `REPOSITORY CHANGED … refs written by a fixture appeared: refs/heads/proto-f0147`: "This is really annoying".

The tripwire (`z-nile/tests/lib/fence.luau`, `snapshot`/`changes`) fails a run when a ref whose tip is authored by `*@example.invalid`, the spec fixtures' identity, appears during it. Other sessions make prototype worktrees in the real repository and commit there as `proto <proto@example.invalid>`, so to every running gate their branches look exactly like a spec escaping its jail. Each trip costs a full gate re-run (about 6 min) and a question to the user. On 2026-10-31 five such refs existed: `proto-f0147` (d1c34d36, "proto f0147: spec types (scratch)") and `proto-wall-picks-base`, `-base2`, `-base3`, `-touch`. c0157 diagnosed this (its E1), but its fix is a prose rule ("prototypes live in scratch clones"), which sessions keep missing.

What should happen: no commit made under a fixture identity can land on a ref of the real repository, so a prototype can't trip anyone's gate; the session that tries is told at once what to do instead. Spec fixtures (their own repositories under `.cache`) are unaffected, and the tripwire keeps catching a real escape.

Decided with the user (2026-10-31):
- "New fast chore": a mechanical guard, shipped ahead of c0157. c0157 keeps its gate slots and its clearer tripwire message, and its prose rule points here.
- "Yes, retry once": until this lands (and after, for anything it misses), a session may retry a gate or `./zn land` once without asking when the tripwire's only finding is refs that are each checked out in a live `.worktree/<name>` outside `.cache`; it says so, and stops and asks if it fires again. Every other finding still stops and is reported. AGENTS.md and zz-test's "If the tripwire fires" say so.

## Non-goals
- Machine-wide gate slots and the tripwire's clearer message: c0157.
- Deleting or rewriting the existing fixture-identity branches: they belong to other sessions; the guard only refuses new updates to them, and prep reports them to the user.

## Solution
- A `reference-transaction` hook in the real repository's common hooks folder (every worktree): on `prepared`, for each new non-zero commit, one `git log --no-walk --format='%H %ae %ce'`; an author or committer email ending `@example.invalid` refuses the transaction with a message naming the scratch clone or the user's own identity as the fix.
- `./zn hooks` installs it by rename (never overwriting an unknown hook); `./zn hooks --check` (read only) is in the gate's static stage beside `./zn skills --check`; `setup.sh` runs `./zn hooks`.
- The same words in z-design (its experiments bullet), zz-execute Phase 1 and zz-test: a prototype lives in a scratch clone or commits with the user's identity, never as `@example.invalid` outside `.cache`; and the retry-once rule in zz-test and AGENTS.md.
- Experiments: which refs on origin and locally have fixture-identity tips (so no fetch the user needs is refused); that commit, fetch, `worktree add -b` and `update-ref` all run the hook; its cost per `./zn` publish.
