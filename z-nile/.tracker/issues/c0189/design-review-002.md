### F1 [medium] A legitimate fetch of a changed hook turns every session's gate (and the stop hook's) red until someone writes the shared git directory: the issue's own harm, decided by prep alone (repeat of design-review-001 F1, consequence (c))
Where: Existing work, "Every other worktree and session" ("When a later change edits the hook, every gate is red … from the first fetch of that change until someone runs `./zn hooks`"); Risks, second bullet ("`./zn sync` could reinstall …; not done"); `hooks.plan`, the row "our file, text differs from the reference → install" (which `--check` turns into exit 1); `hooks-command.spec`, "when origin/main moves to a new hook text, --check is red until ./zn hooks installs it".
Evidence: The spec case passes on the prototype. `trackerfix.elsewhere` pushes a new hook text, then `fetchOrigin()` runs, then `--check` exits 1 with `differs from origin/main's z-nile/lib/repo-hooks/reference-transaction; run ./zn hooks`. `refs/remotes/origin/main` is one ref for the main checkout and every worktree, and `./zn land`, every publish and `./zn sync` move it (`git fetch --quiet origin main`, main.luau `cmd.land`). So the first fetch by any session turns the static stage red for every session whose branch has the stage. That includes `./zn done`, `./zn land` and the stop hook's gate ("It is static, so it runs … in the stop hook's gate"). The fix tells each of those sessions to write `<git common dir>/hooks/`. AGENTS.md tells sessions to "never repair the shared git configuration yourself", so the cautious ones will stop and ask: "a question to the user" per session, which is exactly what the Problem says each trip costs.
Critique: the record (`origin/main`) is written by legitimate writers (every fetch), and the guard fails because the installed copy merely differs from it. That is the defect lesson zz-arch/guard-state-out-of-reach-or-checked names: "when other legitimate processes write the record … never fail on the record merely differing". An older reviewed hook still refuses fixture commits, so a red gate here protects nothing. The author declined the `sync` reinstall, and AGENTS.md names that as a rule change, but no Guess records the choice. The fix the author will be tempted to make is to drop the "differs" problem from `--check`. That brings back round 1's problem: a WIP or unmerged edit installed by hand would never be noticed.
Consequences: judging the installed copy as "a version `origin/main` has held" adds one read: the blob ids `SOURCE` has had on `origin/main` (one `git log --format= --raw origin/main -- <SOURCE>`, or `rev-list` plus `ls-tree`). It also adds one state, "ours, executable, an older reviewed copy". A text never on `origin/main` (a hand edit or a branch's copy) must still be red. `./zn hooks` still installs the newest. A hook fix that must reach every session at once can no longer force itself on gates, so the message says how to update. In the no-`origin/main` case (the Merging clone) only the tree's copy counts, as today. A trampoline hook (a fixed installed file that runs `git show refs/remotes/origin/main:<SOURCE>`) would remove the drift entirely. But it puts a git read on every ref update, and it needs a defined answer for a missing ref or blob that is neither "refuse everything everywhere" nor fail-open. I do not recommend it.
Recommendation: make `--check` green, with a one-line note (`hooks: <dest> is origin/main's copy from <short sha>, older than its newest; run ./zn hooks to update`), when the installed file is ours, executable, has no redirect, and its blob is one `origin/main`'s history of `SOURCE` holds. It stays red for any other text. Add `history: { string }` (the reviewed blob ids) to `hooks.State`, plus a plan row and a mutant row. Cases:
- `hooks-plan`: an older reviewed blob is `ok` with the note; a text never on origin/main is `install` (red).
- `hooks-command`: the "origin/main moves" case becomes green-with-note, and `./zn hooks` then updates. A hand-edited copy (today's "stale" case) stays red. A mutant "any text of ours is ok" is killed by the hand-edit case.

If you keep red-on-differs instead, put it to the user as G4, with this evidence and the costs of each option (red window and per-session questions; the `sync` reinstall and its AGENTS.md change; the reviewed-history rule above). Do not leave it decided in Risks.
Lesson: zz-arch/guard-state-out-of-reach-or-checked

### F2 [medium] `git branch -m` and `git branch -c` create a new ref at an existing fixture commit without the hook ever seeing it, so the four old `proto-wall-picks-*` branches can still trip every running gate; the "superset of the tripwire" claim is false
Where: Design, "Same domain as the tripwire" ("so nothing the tripwire flags can be created in the real repository"); Non-goals ("a ref update is the one place every commit, branch, fetch and worktree passes through"); E2 ("yes for all, and for `branch` …"); Existing work, "Fixture-identity refs today" ("They stay. … deleting one is allowed"); AC1.
Evidence: I ran these on git 2.54.0 (Apple Git-157), the machine's git, in a throwaway repository with a branch `old` at a `proto@example.invalid` commit. A logging hook in front of the prototype hook recorded each call.
- `git branch -m old archived` exits 0. The hook received only `d5ff6d45… 0000… refs/heads/old` (the deletion) in every phase, never the creation of `refs/heads/archived`. Afterwards `for-each-ref` lists `refs/heads/archived <proto@example.invalid>`.
- `git branch -c archived copied` exits 0, and the hook was not called at all (the log is empty). `refs/heads/copied <proto@example.invalid>` now exists.
- A new ref with a fixture tip is exactly the tripwire's main rule (`fence.luau` `snapshot`, `fixtureRefs`), so either command, run by any session, trips every gate running at that moment. The real repository holds four such branches today (`git for-each-ref` shows `proto-wall-picks-base`, `-base2`, `-base3`, `-touch`, both roles `proto@example.invalid`), all in `packed-refs`.
- Consequence seen too: the renamed ref is loose, and `git gc` then prints the hook's refusal and `error: failed to run pack-refs` (gc still exits 0). `pack-refs` sends every loose ref as a `0000 → <sha>` creation. With the fixture refs already packed, `pack-refs` passed.
- The tripwire's other rule, "HEAD gained commits written by a fixture" (`changes`, any author in `before..after`), is not covered either. `git merge --no-ff old` under an ordinary identity exited 0, and `git log` over the new range listed `e0d824b proto@example.invalid fixturework`. Only that checkout's own gate can trip from this, so it matters less, but it also contradicts the claim.

Critique: the capture's outcome is "refuses any ref update to a commit authored or committed under @example.invalid, so prototype branches can't trip every running gate". The files backend renames and copies refs outside a ref transaction, so no `reference-transaction` hook can refuse these, and the design states the opposite. A session that "tidies" or archives the old prototype branches, a plausible act now that the prose rule tells everyone they are a problem, trips everyone again. The tempting fix is to refuse deleting a fixture-tip ref, since a rename shows up as a deletion. That would forbid the one clean-up the design allows, and it still would not stop `branch -c`.
Consequences: this is a git limitation, so the remaining route can only be closed by removing its input (the existing fixture-tip refs) or accepted as a known limit. The branches are not prep's to delete (Non-goals: "they belong to other sessions"), which makes it the user's call. If the user deletes them, the "old branches" special cases (E6 and the old-branch spec case) stay as they are: no-op updates are still allowed for any branch that remains. The rename hole then has nothing left to act on, because no new fixture commit can get a ref through the hook.
Recommendation: escalate to the user, as G4 (or G5 if F1 becomes G4), with the evidence above. The options:
- (a) delete the four `proto-wall-picks-*` branches once `git worktree list` shows no worktree holds them. This closes the rename and copy route for good.
- (b) keep them and accept the route as a known limit, written in Risks and in the zz-test bullet ("never rename or copy a branch whose tip is a fixture commit: delete it, or look at it with `git worktree add <dir> <branch>`").

Either way, correct the "superset" sentence and the Non-goals sentence so they say what the hook does not see (`branch -m`, `branch -c`, history under an ordinary tip). Add to E2 the probe for rename and copy, with the logged hook input. No spec case is needed for git's limitation. A wiring pin for the zz-test sentence goes with option (b).

### F3 [medium] "A failed read of origin/main is an error, never 'no hook'" is a fail-safe with no row and no case: a mutant that treats the failure as `none` passes every spec
Where: Design, "Why `origin/main`" ("A failed read of `origin/main` is an error, never 'no hook'"); Chore checklist, Guards ("a read of `origin/main` that fails is an error"); prototype `cmd.hooks` (`if not listed.ok then fail("hooks: cannot read origin/main: …")`); Rules and mutants (no row); `hooks-command.spec` (no case); `mutate.py` (no mutant).
Evidence: in the prototype clone, with the hook installed and `--check` exit 0, I ran `git update-ref refs/remotes/origin/main <blob of AGENTS.md>`. `./zn hooks --check` then printed `hooks: cannot read origin/main: fatal: not a tree object` (exit 1), so the prototype is right. Pointing the ref file at a missing object (`rev-parse --verify -q` still exits 0) gave the same message. But `grep -rn 'cannot read origin' acceptance/ c0189.md experiments/mutate.py` finds only the Design sentence. Replace the `fail` with `source = nil` (so the plan says `none`, exit 0, and the gate passes with no hook) and no case fails.
Critique: `none` is the only state that passes without a hook, and the design itself says so. The branch that keeps a failure from reaching `none` is that guard's own "no", and it is unpinned (lesson zz-test/pin-fail-safes-where-they-act; zz-arch/guard-no-is-explicit). An executor who "simplifies" the two reads into one `sh.run("git", {"show", …})` and takes a failure as "no file" ships a gate that passes on a broken `origin/main`.
Consequences: none beyond the case. It runs in a fixture (`refs/remotes/origin/main` set to a blob with `update-ref`, then restored), so it changes nothing outside `.cache`.
Recommendation: add a `hooks-command.spec` case: "a read of origin/main that fails is an error in both modes, and nothing is installed". Set `refs/remotes/origin/main` to a blob, run `--check` and `./zn hooks`, and expect each to exit 1 with `hooks: cannot read origin/main`, `dest` unchanged and no `.reference-transaction.new`. Then restore the ref. Add the matching row ("a failed read of origin/main is an error, never none") with mutant S5 ("a failed `ls-tree` is taken as no file"), and run it.
Lesson: zz-test/pin-fail-safes-where-they-act

### F4 [low] The tree's copy is chosen when the `origin/main` ref is missing, not when there is no `origin`; in the real repository that is the unreviewed-install route round 1 closed
Where: Design, "Why `origin/main`" ("A repository with no `origin/main` ref at all … uses its own tree's copy"); prototype `cmd.hooks` (`git rev-parse --verify -q refs/remotes/origin/main`, else `from = "tree"`); AC3.
Evidence: the switch is the ref, not the remote. A checkout that has an `origin` but lost or never fetched `refs/remotes/origin/main` takes the tree branch. In the real repository that means the running worktree's unmerged copy, installed in the shared folder for every session: round 1 F1's harm. Ways to get there include `git branch -dr origin/main`, a narrowed `remote.origin.fetch`, or a `git clone --single-branch -b <other>` of a machine's repository. Nothing does this today, which is why this is low. The only legitimate no-`origin/main` case the design names is the Merging clone, and that clone has no `origin` at all (zz-rules Merging step 2: `git remote remove origin`).
Recommendation: take the tree's copy only when `git remote` lists no `origin`. An `origin` without `refs/remotes/origin/main` is an error in both modes (`hooks: origin has no main fetched; run git fetch origin main`). Add a `hooks-command.spec` case (origin kept, `git update-ref -d refs/remotes/origin/main`: exit 1, nothing installed) and its mutant row. The existing "a clone with no origin/main" case already removes the remote, so it stays as it is.

### F5 [low] An annotated tag at a fixture commit is refused, but the message names no ref, though AC1 says it names "the ref"
Where: Design, "What it says" (`<8-char sha> (author|committer <address>): <ref> [<ref>…]`); AC1 ("naming the ref, the role, the address and the fix"); the hook's last `awk` (refs keyed by the transaction's new name, findings keyed by `rev-list`'s commit).
Evidence: I fed the prototype hook `0000… <annotated tag object> refs/tags/x` (a tag `-a` at a `proto@example.invalid` commit). It exited 1 and printed `e0d824b2 (author proto@example.invalid):` and `e0d824b2 (committer proto@example.invalid):` with nothing after the colon. `git tag -a annot old` gives the same lines. The cause: `rev-list` prints the peeled commit, while `refs[]` is keyed by the tag object's name. The same mismatch would hide the `refs/remotes/` hint for a tag object fetched under a remote-tracking ref.
Recommendation: map peeled names back to their refs. For example, the first `awk` also emits `<new> <ref>`, and the identity read prints `%H` together with the name it was given, using `git cat-file --batch-check='%(objectname) %(objecttype)'` before the `rev-list`, or by peeling with `<new>^{commit}` per distinct name. Then add the annotated tag to `repo-hook.spec`'s "update-ref, branch, tag …" case, asserting `refs/tags/<name>` in the message.

## Candidate lessons (for the lead to place)
- **z-design (or zz-arch): a guard over "every ref update" lists every git command that writes refs, and probes each with a logging hook.** Why: c0189 design review 002 F2. E2 probed commit, fetch, branch, tag, push, stash, merge and reset, then concluded that the `reference-transaction` hook sees every ref write. But `git branch -m` reports only the deletion, and `git branch -c` calls the hook not at all, so a fixture-tip ref appears unseen. Check: for each command that creates or moves a ref (`branch -m/-c`, `pack-refs`, `update-ref --stdin`, `fetch`, `push`, `clone`, `worktree add`, `notes`, `replace`), what did a logging hook receive, and is each one refused, allowed on purpose, or a stated limit?
- **Note for zz-arch/guard-state-out-of-reach-or-checked:** a shared artifact judged against a reviewed reference that legitimate writers move (`origin/main`, fetched by every session) accepts every version that reference has held. It refuses only text the reference never held, so one session's fetch never turns every gate red (c0189 design review 002 F1).

Verdict: changes
