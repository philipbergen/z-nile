# c0195: Ref guard misses branch copy

## Problem
The fence's ref guard misses a branch copy: git branch -c <old> <new> runs no reference-transaction hook on git 2.54, so wherever there is no jail (check.sh flows, Linux spec runs) a check can create refs/heads/<new> in the real repository; found by c0122's design review

## Non-goals
- c0122's fetch rule and its specs (prepared); c0123 (the fence trusts only its own hooks).
- The macOS jail, which already denies a spec's write to the real repository's refs: this is about the runs without one.
- Writes that are not refs, which the sweep (E1) found also pass the hook, in the real repository, where there is no jail: `git remote rename` rewrites `remote.<name>.*` config before the hook refuses its ref renames, and `git reflog expire`/`reflog delete` (and `gc`'s reflog step) rewrite reflogs without any ref transaction. Config and reflogs are not refs; they are the AGENTS.md "review must catch" class for check.sh flows (the runner's tripwire already compares `remote.*` config in spec runs). Reported for a capture (Report, below), not done here.
- A git that git itself starts (a hook, a `!` alias, `rebase --exec`, an editor, a filter, a merge driver) finds git's own exec path first on its `PATH` (E4), and a git called by its full path skips the `PATH`: neither reaches the fence's git. Both are written in a check's own code or a fixture's own configuration; review catches them (the zz-test bullet says so), and on macOS the jail denies them anyway.
- Writing a ref file by hand (`cp`, `echo > .git/refs/heads/x`): not git; review's, as today.

## Solution
Ideas from capture; z-design decides.
- Reproduce first on both gits on this machine (2.54.0 and the Command Line Tools' 2.50.1), in a throwaway repo: c0122's design reviewer saw `git branch -c main evil` exit 0 and create `refs/heads/evil` with the guard installed.
- Find every ref-writing command that skips `reference-transaction` (branch copy, and any other the git source or a sweep turns up), and cover each: a fence-side wrapper, a refusal of `branch -c`/`-C` in the fenced environment, or the tripwire catching the new ref after the fact.
- A real-git case per command found, on both gits.

## Solution
The fence gets a git of its own. Where it sets the ref guard's hooks (no jail: check.sh flows, Linux spec runs), it also puts the hooks' folder first on the `PATH`, and that folder gains one file, `git` (`z-nile/lib/git-hooks/git`, POSIX sh). That script finds the command git would run; in a repository the fence protects (`PICKMAN_FENCE_REAL_GIT`) it refuses, before git starts, a `git branch` copy or rename in any spelling, and any command that is not one of git's own builtins (an alias or an external command, whose expansion it can't see). Everything else, and everything in a fixture, is the real git at once (`exec`), so a fixture's specs see no change. The real git is the first git on the `PATH` that is not a fence's, found once per fence and exported as `PICKMAN_FENCE_GIT`. Under the jail no hooks are set and the fence's git is taken off the `PATH`. Prevention, not the tripwire: the real repository is shared by every session, so a new ref after a check can't be told from a person's (Unknowns, E5). The issue lands after c0123 (G1), which makes the hook folder the guard's own by content and fixes the `PATH` at every entry; the fence's git rides in the verified folder.

## Design
Decisions relied on: none from `pickman/.tracker/game-design.md` (a tooling chore; nothing in `pickman/` changes). The rules followed: zz-test's "Specs never touch the real repository" (the Ref guard and the jail bullets), zz-arch's rule that guards fail closed (lesson `zz-arch/guard-no-is-explicit`), and `zz-arch/guards-decide-from-the-tools-resolution` (the fence's git asks git which repository a command acts on, with the same options; it allow-lists git's own commands rather than parsing aliases).

### What git does today (E1, both gits on this machine)
`e1-sweep.sh` fences a throwaway repository exactly as `ac.sh` fences the checkout and runs 47 ref-writing commands, each in a fresh copy, with a logging hook in front of the guard. On git 2.54.0 and 2.50.1, in both modes (`checks`, `specs`):
- `branch -c`, `-C`, `--copy` (and the current branch's `branch -c <new>`): **exit 0, the hook never called, the ref created or overwritten.** The bug, reproduced.
- `branch -m`, `-M` (any): the hook sees only the deletion of `<old>`, refuses it, git exits 128, but the branch's reflog is left at `logs/refs/.tmp-renamed-log`: a refused rename still damages the real repository.
- Every other command the sweep tried reaches the hook and is refused or allowed as designed: `branch <new>`, `-f`, `checkout`/`switch` (`-b`, `-B`, `-C`, `--orphan`, `--detach`), `symbolic-ref` (set, `-d`), `update-ref`, `tag`, `remote rename`/`remove`/`set-head`, `pack-refs`, `refs migrate`, `stash`, `notes`, `replace`, `worktree add` (`-b`, `--detach`), `fast-import`, `fetch` into `refs/heads/` (refused) and into `refs/remotes/` (allowed in `checks` mode only, c0131), `push .` (pre-push), `replay` (2.54's `--ref-action=update` too), `rebase` (`--update-refs` too), `commit`, `reset`, `gc`, `init` (re-init), `clone` into `.cache`.
- Not refs (Non-goals): `remote rename` rewrites config before its refused ref renames; `reflog expire`/`delete` rewrite reflogs; a hand-written ref file.

### The fence's git: `z-nile/lib/git-hooks/git`
A POSIX `#!/bin/sh -p` script (the folder's shebang rule after c0123, which `entries.spec` pins for every file under `z-nile/lib/git-hooks/`); git runs no hook named `git`, so the file is inert as a hook. Its steps, in order:
1. **The real git.** `real=$PICKMAN_FENCE_GIT`. If it is empty, not executable, or the same file as the script itself (`[ "$real" -ef "$0" ]`, which would start itself forever), print `fence: the real git is not known (PICKMAN_FENCE_GIT); refusing. Stop and report this.` and exit 1. Every other outcome goes on.
2. **The command.** The first argument past git's own options, skipping the value of each option that takes one separately: `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`, `--attr-source` (probed on both gits, E3; `--exec-path` without `=` prints and exits, and the rest take only `=` forms or none). No command (`git --version`): `exec "$real" "$@"`.
3. **One of git's own?** `PICKMAN_FENCE_GIT_BUILTINS` holds, space-separated, `git --list-cmds=builtins` less `git --list-cmds=deprecated` (2.54 lets an alias replace `pack-redundant` and `whatchanged`; 2.50 has no such list and no such exception). A git builtin can't be hidden by an alias (git ignores such an alias), so a builtin other than `branch` is `exec`'d at once. That is the fast path: a `case` over the string, no process.
4. **`branch`.** It needs the repository only when its arguments, up to `--`, hold a copy or a move: `--cop`, `--copy`, `--mo`, `--mov`, `--move` (git's own unambiguous abbreviations; `--c`, `--co`, `--m` are ambiguous and git refuses them), or a short-option cluster `-…` holding `c`, `C`, `m` or `M` before any `u` (whose value is the rest of the cluster). Every argument is scanned, values included, so an option's value spelled like a flag (`--format -c`) is refused too in a protected repository: a read nobody runs, refused rather than missed. No copy or move: `exec`.
5. **Not one of git's own** (an alias, an external `git-<name>`, a deprecated name, a typo): needs the repository, like 4.
6. **Which repository.** `"$real" <the options before the command> rev-parse --path-format=absolute --git-common-dir`, in the same environment, made physical with `cd … && pwd -P`. No repository (the command would fail in git too): `exec`. Compared with each entry of `PICKMAN_FENCE_REAL_GIT`, each made physical: a match refuses with `fence: a check tried to copy or rename a branch (git writes it outside the ref guard's hook) in the real repository (<dir>); refused` or `fence: a check tried to run '<name>', which is not one of git's own commands (an alias or an external command) in the real repository (<dir>); refused`, exit 1. No match: `exec "$real" "$@"`.
The prototype's text is in `experiments/prototype.patch`; the executor ports it onto c0123's tree (E6).

### The fence: `z-nile/lib/fence.sh`
In `pickman_fence_env`, inside the existing `if [[ $jail != sandbox-exec ]]` block, after the hooks' own refusal and before anything changes (the read-only refusals stay first, lesson guard-no-is-explicit):
- `$hooks/git` not executable, outside the jail's waiver (`jailed`): `fence: no ref guard at $hooks (git); refusing. Stop and report this.` (after c0123 this is one more name the digest pins: a folder without it fails the digest, and c0123's own message names it, `missing git`).
- `gitreal=$(_pickman_fence_real_git "$hooks")`: the first `git` on the `PATH` (executable, not a folder) whose folder is neither `$hooks` (by name or `-ef`) nor this `fence.sh`'s own `git-hooks` folder. `builtins=$(_pickman_fence_builtins "$gitreal")`. Either empty: `fence: no git on the PATH besides the fence's own, or it can't list its commands; refusing. Stop and report this.`
- The `else` branch (the jail) sets `unshim=1`.
After the point of no return, beside `core.hooksPath`: with `gitreal`, `export PICKMAN_FENCE_GIT=$gitreal PICKMAN_FENCE_GIT_BUILTINS=$builtins` and `PATH="$hooks:$(_pickman_fence_path_without "$hooks")"` (the folder first, once: every other entry naming it, by name or `-ef`, is dropped); with `unshim`, the inherited `$PICKMAN_FENCE_HOOKS` and this file's own `git-hooks` are dropped from the `PATH`. Then `export PATH`. New helpers, beside `_pickman_fence_git`: `_pickman_fence_path_without <dir>`, `_pickman_fence_real_git <hooks>`, `_pickman_fence_builtins <git>` (signatures and bodies in the patch). The header gains the line `#   - where it sets those hooks, finds git first in their folder (git-hooks/git, c0195), which refuses there the ref` and two continuation lines. The fence's own reads (`_pickman_fence_git`, `pickman_guarded`) keep calling `git`: inside a nested fence that is the fence's git with `PICKMAN_FENCE_GIT` set, which `exec`s at once.

Server authority, pure/adapter split: not applicable (shell guards; no Luau module changes). The only shared rule is the set of folders the fence protects, read as before from `PICKMAN_FENCE_REAL_GIT`.

### Scalability
One fence setup adds one `git --list-cmds=builtins` and one `--list-cmds=deprecated` (two git starts, about 10 ms) and a `PATH` walk; a gate sets up one fence per home and per check.sh, so this grows with the homes, not the items. Each git call where the hooks are set adds one `sh` start: 2 to 4 ms per call on this machine under load 11 (E2: 11.9 → 15.9 ms and 13.7 → 15.2 ms for `rev-parse HEAD`). That cost falls only on check.sh flows' own git calls and on Linux spec runs: macOS spec runs are jailed, so the fence's git is off their `PATH`. Only a `branch` copy or move and a non-builtin in any repository cost one more git (`rev-parse`); nothing else forks.

### Maintainability
One file, one place: the fence's git lives in the guard's hook folder, is copied, inherited, verified (c0123) and set with it; nothing else names its location. A new jail goes in the one condition (c0075). A new ref-writing route git adds outside a transaction joins step 4's flag list and `copy.spec`/`rename.spec`'s forms, found by rerunning `experiments/e1-sweep.sh <git>` on the new git. The builtin list comes from git itself, so a new git command needs no edit. The sweep is the method for "every ref-writing command" (lesson candidate in the Report).

### Usability
The two refusals name the rule and the repository, and start `fence:` like the fence's others; the "not known" refusal ends "Stop and report this." as the fence's environment refusals do. A person who runs `git` by hand outside a check sees no change: the fence's git is only on a fenced `PATH`. The other names in the hook folder (the 18 hook stubs) are on that `PATH` too; none is a command a check runs (nothing in the repository calls a `pre-commit` tool), and a stub run as a command only runs the repository's own hook of that name. Exhaustive lists that must name the new file: zz-arch's `z-nile/lib/` row (changed), zz-review's guard-file list (names `z-nile/lib/git-hooks/` already: unchanged), c0123's pin names (recomputed).
