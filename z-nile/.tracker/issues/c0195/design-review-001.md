### F1 [high] The fence's git fails open: any failure to learn the repository runs the copy
Where: c0195.md Design, "The fence's git" step 6 ("No repository (the command would fail in git too): `exec`"); prototype.patch, `git-hooks/git`, `common=$( … ) || exec "$real" "$@"` and `common=$(cd … && pwd -P) || exec "$real" "$@"`
Evidence: the only thing that refuses is a match. Every other outcome of the `rev-parse` (a non-zero exit, empty output, a `cd` that fails) execs the real git with the copy or rename, which then writes to whatever repository it finds. That does not mean "no repository". Three cases where `branch -c main evil` in the protected repository goes through:
(1) The fork for `$( … )` fails. That is the per-user process limit this machine just hit. `exec` needs no fork, so the copy runs.
(2) A git older than 2.31 has no `--path-format` (Linux spec runs are a named target). There the `rev-parse` exits 128 on every call, so every copy and rename runs.
(3) The options before the command are misread (F2), so the replayed `rev-parse` is malformed and fails. M3 dies today only through this path (`--namespace x` makes `x` the command, the `rev-parse` fails, the copy runs, exit 0).
Critique: this is the lesson's defect exactly. A missing or failed answer leads to the unguarded action. The "git would fail too" argument holds only when git truly finds no repository, and the shim can't tell that from a failure of its own probe. The tempting fix is to refuse when `rev-parse` exits 128 and prints "not a git repository". That parses a message (locale, wording across versions) and still lets cases (1) and (3) through on any other exit code.
Consequences: refusing on every failure has a cost. A non-builtin run outside any repository inside a fenced check (`git lfs install --skip-repo` in `/tmp`) is refused too. A grep of the repository finds no such call (no `git lfs`, `submodule`, `filter-branch` or `request-pull`). A branch copy or move with no repository fails in git anyway, so refusing it costs nothing. M3 stays killed after the fix, because its refusal then says `not one of git's own commands`, not `copy or rename a branch`, and copy.spec checks that needle.
Recommendation: for a branch copy or move, and for a non-builtin, only one outcome execs: an answer that succeeded, is not empty, resolves (F3), and matches no protected entry. Every other outcome refuses with its own message: `fence: could not tell which repository '<sub>' acts on; refused`. State the cost of the non-builtin case in Usability. Add a rule row and a case in closed.spec. The case uses a stub real git, first on the `PATH` before the fence, that delegates everything except a `rev-parse … --git-common-dir`, which it fails. A `branch -c main evil` in the protected fixture must then be refused, and the stub must record no `branch` call. Mutant: the current `|| exec`.
Lesson: zz-arch/guard-no-is-explicit

### F2 [high] The hand-written parse of git's own options lets `git --shallow-file status branch -c main evil` through on the fast path
Where: Design step 2 and E3 (the list of options that take a separate value); prototype `case $a in -C | -c | --git-dir | --work-tree | --namespace | --config-env | --attr-source) skip=1 ;; -*) ;;`
Evidence: `handle_options` in git.c has long taken `--shallow-file <file>` as a separate value (receive-pack passes it to its children). E3 lists the options it probed, and this one is not among them. The shim takes the option's value as the command. With `git --shallow-file status branch -c main evil`, `status` is a builtin other than `branch`, so the shim execs at once. git then reads `--shallow-file status` and runs `branch -c main evil`: a copy in the protected repository, with no hook. The same happens with any separate-value option a future git adds (`--attr-source` arrived in 2.42; the dispatcher's own wrapper, z-nile/bin/git, still lists `--super-prefix`). The default branch, `-*) ;;`, treats an option the shim doesn't know as harmless.
Critique: the guard decides from its own copy of git's grammar, not from what git resolves, and the open branch of that copy is the permissive one. The tempting fix is to add `--shallow-file` to the list. That fixes today's git and leaves the next new option open.
Consequences: a closed option list needs every flag-only option of both gits (`-p`, `--paginate`, `-P`, `--no-pager`, `--bare`, `--no-replace-objects`, the four pathspec flags, `--no-optional-locks`, `--no-advice`, `--no-lazy-fetch`, the `=` forms) as well as the value-taking ones. A git that adds an option then gets "refused in a protected repository" until the list learns it. That is the fail-closed direction, and rerunning the E3 probe on the new git is the maintenance step (put it in Maintainability beside the sweep).
Recommendation: make the option loop closed. Known value options skip their value, known flags and `=` forms pass, and any other argument starting with `-` before the command means "the command is unknown". That takes step 5's path: it needs the repository, and with F1 it is refused when the probe fails. Extend E3 to probe `--shallow-file` and every option in both gits' `git.c`, and record the lists. Add copy.spec forms `--shallow-file x status branch -c main evil` (its free form must copy, which proves git accepts it on that version) and an option the shim doesn't know before `branch -c` (real form refused, with its own needle). Add a rule row: "an option before the command that the fence's git does not know is never skipped as harmless". Mutant: `-*) ;;` kept.
Lesson: zz-arch/guards-decide-from-the-tools-resolution

### F3 [high] The repository is compared by the spelling the shell's `pwd -P` keeps, so a case-folded `--git-dir` (or `GIT_DIR`) reaches the real repository on macOS
Where: Design step 6 ("made physical with `cd … && pwd -P`"); prototype `common=$(cd "$common" … && pwd -P)` and `[ "$common" = "$(cd "$p" … && pwd -P)" ]`
Evidence: c0123's E25 found on this machine (APFS folds case) that the builtin `cd -P && pwd -P` keeps the caller's letters, while `/bin/pwd -P` gives the stored ones. `rev-parse --path-format=absolute` keeps the letters of a `--git-dir` or `GIT_DIR` it was given. Take `git --git-dir=<ROOT in upper case>/.git branch -c main evil` in a check.sh flow (unjailed on macOS). `common` is the upper-case path, `PICKMAN_FENCE_REAL_GIT` holds the stored one, the string comparison fails, and git creates `refs/heads/evil` in the real repository. AC3's own route (`--git-dir` aimed at the protected repository) is open under another spelling.
Critique: the tempting fix is `/bin/pwd -P`, as c0123 did. That costs a fork on every slow-path call, and on macOS it still depends on that program's behaviour.
Consequences: `[ "$common" -ef "$p" ]` (same device and inode) needs no fork, follows symlinks and ignores spelling. An entry that no longer exists is simply not a match, the same as today.
Recommendation: compare each protected entry by identity (`-ef`), and keep the physical path only for the message. Add an away.spec form with `--git-dir=` naming the protected fixture in other letters. It is meaningful only on a case-folding volume: the case decides by `-ef` between the two spellings whether the volume folds, and otherwise records that it was skipped. Add a rule row, with the string comparison as its mutant. (`pickman_guarded` in fence.sh has the same string comparison; that is pre-existing and not this issue's, but say so in Report.)
Lesson: zz-arch/compare-canonical-spellings

### F4 [high] The cleaner rule built on c0123 trusts the variables c0123 says are believed for nothing, and misquotes c0123
Where: c0195.md "On top of c0123", "The cleaner" bullet; Implementation step 4; E6's fallback; rules-table row "after c0123, an entry script restarted inside a fence keeps the fence's folder first…"
Evidence: c0195 writes that c0123's `cleanenv.list` "keeps the fence's exported state with `fence <NAME>` lines while `PICKMAN_FENCE_REAL_GIT` is set", and adds a rule that keeps "a leading `PATH` entry that is `-ef` `$PICKMAN_FENCE_HOOKS`" under the same condition. c0123's current text, lines 99 and 107, says the opposite. The fence names pass "only while a kept `proof` folder (`*/pickman-run.*/bin` or `*/pickman-guard.*`, the run's own…) is on `PATH`: a forged `PICKMAN_FENCE_REAL_GIT` gains no folder and keeps no fence name". Boundary (c) adds that the markers, `PICKMAN_FENCE_REAL_GIT` among them, are "believed for nothing: no `PATH` folder and no fence name depends on them". Under c0195's rule, a person's shell that sets `PICKMAN_FENCE_REAL_GIT=/x`, `PICKMAN_FENCE_HOOKS=/evil` and `PATH=/evil:…`, with `/evil/git`, starts `./zn`, and the cleaner keeps `/evil` first. c0123's AC4 (`launchers.spec`: "the planted `git` is not found") is reopened. Separately, the shim execs whatever `PICKMAN_FENCE_GIT` names, and c0123's `PICKMAN_*` allow line passes it from any caller. So once the shim's folder is kept on a cleaned `PATH`, a forged `PICKMAN_FENCE_GIT` chooses every git a launcher runs. A forged `PICKMAN_FENCE_GIT_BUILTINS` holding an alias name lets that alias through.
Critique: E6 calls this an executor experiment with a fallback "if c0123's cleaner can't keep the folder". By c0123's own rules it must not keep it. So the "design" path is the one c0123 forbids, and the fallback is the only design that holds. The tempting fix is to verify `$PICKMAN_FENCE_HOOKS` by digest inside the cleaner. That is a third reader of the pin (perl under `env -i` in both cleaners), and the shim would still believe `PICKMAN_FENCE_GIT`.
Consequences: with the fallback, an entry script restarted inside a fenced check.sh (`./zn` called by a check) runs git without the fence's git. Only our own tooling runs there, not a check's commands. On Linux spec runs, the runner's own fence (tests/lib/fence.luau relaunch) puts the shim back, because it calls `pickman_fence` after its restart. The limit then has to be stated, and E6 stops being conditional. The `systemGit` override must also accept the folder the fence actually used: under c0123 that is the inherited folder verified by content, which need not be "that run's checkout".
Recommendation: make the fallback the design. There is no cleaner rule and no `fence PICKMAN_FENCE_GIT*` lines (they would be dead anyway, since `PICKMAN_*` already passes as a value). Add the limit sentence to the zz-test bullet and to AC8's needles: "an entry script restarted inside a check runs git without it; only the tooling's own commands run there". Make the shim believe no caller-settable variable for its real git. Either it walks the `PATH` behind its own folder at each call (builtins only: `[ -x ]` and `-ef "$0"`'s folder, no fork), or the design states why `PICKMAN_FENCE_GIT` cannot outlive the fence that set it. For the builtin list, say what a forged `PICKMAN_FENCE_GIT_BUILTINS` can do and accept it in writing (the "a check's own commands" review class) or close it. Narrow the `systemGit` override to "a folder whose digest is the pin, holding `git`", not a path. Re-quote c0123 from its current text, and add a case in the c0123 style: a forged `PICKMAN_FENCE_REAL_GIT`, `PICKMAN_FENCE_HOOKS` and `PICKMAN_FENCE_GIT` through an entry restart never run a planted git.
Lesson: zz-arch/allow-list-entries-are-not-caller-chosen; z-design/quote-other-preps-before-promising

### F5 [high] The sweep missed ref writes that bypass the hook: `stash drop`/`pop` and `reflog … --updateref` move `refs/stash` outside a transaction; the design files them under "not refs"
Where: E1 / e1-sweep.sh (the 47 commands); Non-goals, third bullet ("`reflog expire`/`reflog delete` … rewrite reflogs without any ref transaction. Config and reflogs are not refs"); captured Solution idea "Find every ref-writing command that skips `reference-transaction` … and cover each"
Evidence: by reading git: `stash drop` (and `pop`, which applies then drops) calls `reflog_delete(…, EXPIRE_REFLOGS_REWRITE | EXPIRE_REFLOGS_UPDATE_REF)`. The files backend's `files_reflog_expire` then locks the ref and writes `refs/stash` directly with `commit_ref`, not through a ref transaction, so no `reference-transaction` hook runs. The same holds for `git reflog delete --updateref` and `git reflog expire --updateref`. The sweep ran `reflog delete HEAD@{0}` and `reflog expire --all` without `--updateref`, in a fixture with no stash, and `stash` only as a push (refused by the hook). A check.sh that runs `git stash pop` or `git stash drop` in a worktree of the real repository rewrites a person's real `refs/stash` and its reflog. Deletions are not in the sweep either (`branch -d/-D`, `tag -d`, `update-ref -d`, `fetch --prune`, `remote prune`, `worktree remove`/`prune`), so the claim that "every other command … reaches the hook" does not cover them.
Critique: the Problem and the captured Solution ask for every ref write that skips the hook. Filing a ref write (`refs/stash`) under "reflogs are not refs" narrows that scope without a `Scope decision` line. The tempting fix is to add `stash` to the refused list. Whether `stash drop` is refused only in a protected repository, and whether `stash` push/apply/list still run, is a rule that needs its own cases.
Consequences: refusing `stash drop`/`pop`/`clear` and `reflog delete`/`expire` with `--updateref` in a protected repository adds a `stash` scan to the shim (and a `reflog` scan), with the same any-spelling problem as `branch`: `--updateref` abbreviations, `stash pop` against `stash apply`. If the probe shows `stash drop` does pass through the hook on both gits, the rows record that instead.
Recommendation: before the design is final, extend e1-sweep.sh. Add a fixture with two stashes and run `stash drop`, `stash pop`, `stash clear`, `reflog delete --updateref refs/stash@{0}`, `reflog expire --updateref --expire=now refs/stash`, plus the deletion forms and `worktree remove`/`prune` of a linked worktree. Record exit, refs and reflogs on both gits. Every route the probe shows skipping the hook joins the shim (rule rows, `copy`/`rename`-style specs with real and free forms, the any-spelling scan). If an outcome is to stay out, it needs `escalate to the user:` with the options (cover it now, or a `Scope decision` line and a capture), not a Non-goal.

### F6 [high] closed.spec's "would only start itself" case, and the mutation rerun E6 asks for, is an unbounded fork chain on a macOS run
Where: closed.spec, the third AC7 case (`perl -e "alarm 20; exec @ARGV" <hooks>/git rev-parse HEAD` with `PICKMAN_FENCE_GIT` set to the shim); E6/E7 (rerun e2-mutants.py, M16 and M17); e2-mutants.py (`./zn run --time 300 -- lune run tests/run`)
Evidence: on macOS the runner's own fence is the jailed one, which exports no `PICKMAN_FENCE_GIT_BUILTINS` (the prototype exports it only on the non-jail path), so the case runs with that variable unset. Under M17 (no `-ef "$0"`), and under M16 for the `<hooks>/git` value, the real git is the shim itself. `rev-parse` is then "not one of git's own", so the shim forks `common=$( "$real" … rev-parse … )`, which starts the shim again, which forks again. Each level waits on its child, so the processes are all alive at once, growing at roughly one per sh start. The alarm kills only the first pid, and the orphaned chain keeps growing. At a few ms per level, macOS's per-user limit (a few thousand) is reached within seconds, long before `./zn run`'s 300 s. E7 records that the earlier prototype lacked the `-ef "$0"` test entirely, so the earlier sessions ran this exact condition for real. That plausibly explains the machine reaching its process limit and E9's `sweeper: stopped 4 process(es)`.
Critique: a spec's failure mode for its own mutant must be a red case, not a resource exhaustion. A regression that drops the self-test turns every macOS gate into a fork bomb. The tempting fix is a shorter alarm, which does not reach the children.
Consequences: setting `PICKMAN_FENCE_GIT_BUILTINS` in the case makes the mutant an `exec` loop in one pid, which the alarm does end. A `ulimit -u` cap inside the case does not help: it is per user, not per tree, and would fail at once on a busy machine.
Recommendation: the case sets `PICKMAN_FENCE_GIT_BUILTINS = "rev-parse"` (and runs a builtin), so that every mutant of the self-test loops by `exec` only. Also cap the loop in the shim itself: a depth marker the shim exports to the git it starts (`PICKMAN_FENCE_DEPTH`), refusing past 1, so no git the shim starts can start the shim again through `PICKMAN_FENCE_GIT`. Add a rule row with its own mutant. E6 must say the mutation rerun is safe only after this change, and record each mutant's outcome in a file of its own (e2-mutants.out held one `bounded:` line, no results).

### F8 [medium] Plausible mutants no row lists, and rules with no case
Where: Rules and mutants; away.spec, others.spec, copy.spec, wiring.spec
Evidence: each of these passes all eight specs as written:
(a) The `rev-parse` run in a cleaned environment (`env -u GIT_DIR …`, or `/usr/bin/env -i` as c0123 starts its verifiers). That is the house style for a guard's own reads (`_pickman_fence_git`). It misses `GIT_DIR=<real>/.git git branch -c main evil` and `GIT_COMMON_DIR`. No case sets either, and step 6's "in the same environment" has no row.
(b) The `branch` scan stopping at the first non-option. git's parse-options accepts options after the positionals (`git branch main evil -c`), and no form puts the flag last.
(c) Only the last entry of `PICKMAN_FENCE_REAL_GIT` compared (`${…##*:}`). In every case the fixture is the last entry, so the outer, protected checkout is never the target of a nested fence.
(d) Under the jail, only one of the two folders dropped. In wiring.spec `$PICKMAN_FENCE_HOOKS` and the fence's own `git-hooks` are the same folder.
(e) An external command refused only when no `git-<name>` exists. The case uses a command that doesn't exist, so git's own "not a git command" would fail it either way, apart from the needle.
(f) The deprecated names not subtracted. The design says 2.54 lets an alias replace `whatchanged`/`pack-redundant`, yet no form aliases one.
(g) The shim compares only the common dir. With `GIT_DIR=<real>/.git GIT_COMMON_DIR=<fixture>/.git`, a rename of the current branch rewrites the real repository's `HEAD`. This is exotic: state it as a limit, or compare `--git-dir` too (one `rev-parse` with both).
Critique: these are the obvious wrong implementations an executor porting onto c0123's style would write, (a) above all. A guard whose specs pass with the hole open has an acceptance criterion a wrong implementation passes.
Consequences: env-setting cases name `GIT_DIR`, which `repo-fence.spec`'s gate scan flags. They need a third `ALLOWED` entry (for away.spec), and wording.spec's allowance needle list must not then fail on the extra block (it checks presence only, so it doesn't).
Recommendation: add the rows, with these cases. (a) away.spec forms run with `GIT_DIR` (and `GIT_COMMON_DIR`) naming the protected fixture from a free folder (the driver needs an env column). (b) copy.spec `branch main evil -c` and rename.spec `branch side moved -m`, each with a free form proving git accepts it. (c) A case with two protected fixtures under nested fences, the copy refused in the outer one. (d) wiring's jail case with the outer hooks folder a verified copy at another path. (e) others.spec with a stub `git-c0195ext` on the `PATH` that writes a marker: refused in the protected repository, marker absent, and the same stub run in a fixture. (f) On a git whose `--list-cmds=deprecated` is not empty, `-c alias.whatchanged='branch -c main evil' whatchanged` refused. (g) Either a stated limit in the zz-test bullet or the `--git-dir` comparison with its case.
