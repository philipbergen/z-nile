# c0225: Sweeper misses exiting leftovers

## Problem
The jail's sweeper misses leftovers that are mid-exec when it probes: the jail's kill 0 does not answer for them, so one negative probe ends the sweep and they outlive the run (c0168 design review 002: 2 of 30, 3 of 60 and 7 of 60 sweeps); c0076's design, the same shape as one negative probe ending a guard

## Non-goals
- Counting other runs' dying processes, and the exit-71 verdict a foreign zombie causes: c0168. This issue keeps what a pass stops and counts as it is, and changes only when the sweep ends.
- Why the jail's sweeper is sometimes killed (signal 9), and the report about it: c0132 and c0167.
- Linux and other unjailed runs, which have no sweeper (c0075).
- The launcher (`fence.REAPER`), the watchdog, the interlock and the jail's profile: unchanged.

## Solution
<!-- The approach in one paragraph. -->
In `fence.SWEEPER`, the sweep no longer ends on the first scan that finds nothing. It ends only after **five scans in a row, at least 50 ms apart, found nothing**; a scan that stops something starts that count again, and 50 passes that each stopped something still end in "processes keep appearing" (exit 71), as now. A leftover one scan misses (the jail's `kill 0` not answering for it while it is mid-exec) is found by a later scan, and a miss now needs five misses in a row over at least 200 ms. So that a spec can stand in for a missed probe, the test seam `PICKMAN_SWEEP_ONLY` takes `<pid>@<n>`: that pid is a candidate only from the nth scan on. The runner strips the seam, so real runs never read it, and it can only narrow a sweep, never widen one (an entry is a decimal pid from 1 up with an optional `@` and a scan number from 1 up; anything else, `0` and a leading zero included, is ignored). The testing skill's Sweeper bullet and the comment above `fence.SWEEPER` say both.

## Design

### What prep found (2026-11-15, macOS 26.6.2, the pinned Lune, load 10 to 14 on this machine)
- **The miss did not reproduce today (E1 to E3).** In a jail with the runner's signal rules, `kill 0` answered every one of 4,000 probes of a detached process that re-execs itself without a pause (about 370 execs a second, E1). The unpatched sweeper stopped such a leftover in 750 of 750 sweeps: 240 in a jail with the runner's whole profile (E2: the looper started 0, 0.01 and 0.2 s before the sweep, re-execing through `perl -e` or a script file as c0168's reviewer's did), and 210 in a real jailed spec run of this checkout's runner (E3), some of them run beside E2 to load the machine. c0168 design review 002 measured 2 of 30, 3 of 60 and 7 of 60 on 2026-11-0x (macOS 26.6, load 10 to 15), with a trace line showing that every survivor was never found. Its scripts are gone, so the difference (a later macOS point release, the load, the looper) is not known.
- **So the fix must not depend on the mechanism.** Whatever makes one scan miss a live process of the sandbox (a process mid-exec, the kernel swapping its process record during exec, a slow exec under memory pressure), the sweep must not take one scan's "nothing" as the end. The rule below holds for any miss shorter than the settle window. A miss lasting over 200 ms on every probe would still end the sweep: that is a process the jail does not answer for at all, which this design cannot see (Limits).
- **No explicit "no" exists inside the jail (zz-arch rule 7).** The only listing a sandboxed process gets of its own sandbox is `kill 0` per pid: it answers for the sandbox's processes and refuses (EPERM) every other process, so a refusal can mean "another sandbox" or "ours, but not answering now" (E1: a full scan sees about 1,000 EPERM and 99,000 ESRCH). `pgrep` reads a `sysmond` sample that misses processes mid-exec too (c0168 review 002 F1, 4 of 67 and 11 of 92 queries) and can't tell a sandbox. `ps` can't run in the jail (c0132 E4). A `sysctl(KERN_PROC_ALL)` read lists every process but cannot tell which sandbox one is in either. So the "no" the end of the sweep acts on can only be made stronger by asking again, spaced in time: that is this design.
- **Cost (E4).** A clean run's unseamed sweep (every pid 2 to 99999, nothing left) took 0.103 s wall (median of 20) and 0.076 s CPU before, and takes 0.423 s wall (max 0.464) and 0.169 s CPU with the prototype: five full scans (about 25 ms each) and four 50 ms pauses (an earlier four-scan prototype: 0.331 s and 0.145 s). That is about +0.32 s wall and +0.09 s CPU for every jailed `tests/run`: once per project home in a gate (seven homes, so about +2.2 s on a gate of minutes) and once per `check.sh` that runs specs. A nested run inside a spec is never jailed (macOS can't nest sandboxes), so it has no sweeper and pays nothing.

### The rule (in `fence.SWEEPER`, `z-nile/tests/lib/fence.luau`)
A **scan** is one pass's probe of every candidate (`kill 0` on every pid of `@cand`, ancestors and itself excepted), followed, when it found something, by the existing 50 ms re-probe. Scans are numbered 1, 2, … from the start of the sweep, empty or not.
1. **An empty scan** (nothing answered, or nothing still answered the re-probe) adds one to the run of empty scans. When that run reaches **five**, the sweep ends: it prints `sweeper: stopped <n> process(es) the specs left running` when it stopped any (n > 0) and exits with the command's status, as today. Otherwise it pauses **50 ms** and scans again.
2. **A scan that finds something** stops it (STOP, then KILL), counts it, **sets the run of empty scans to 0**, and pauses 50 ms, as today.
3. **After 50 scans that each stopped something** the sweep prints `sweeper: processes keep appearing; this run is not clean` and exits 71, as today (today's loop is 50 passes, every one of which stops something, because an empty one ends it). Empty scans do not count toward the 50: the limit counts stopping scans only. (A loop that kept today's `for 1 .. 50` and let empty scans spend passes would end a clean run with 71 after ten stopping scans each followed by four empty ones; AC9 pins it, design review 001 F5.)
4. **The test seam** (`PICKMAN_SWEEP_ONLY`, a file read once before the first scan, as today): its entries are separated by white space. An entry `<pid>` is a candidate from scan 1 and an entry `<pid>@<n>` from scan n on; both numbers are decimal digits from 1 up (`^[1-9]\d*(?:@[1-9]\d*)?$`), and any other entry is ignored (design review 001 F8: `0` would make `kill 0, 0` stop the sweeper's own group, and `007` would be probed as pid 7 but keyed as "007", so the ancestors' map would miss it). A pid listed twice takes its last entry. A seam that can't be read still refuses (exit 70). With no seam (every real run: the runner removes it with `env -u`), every pid 2 to 99999 is a candidate in every scan, and the scan line is the one every seamed spec runs: the seam only decides what `@cand` holds at each scan (F3: entries from scan n on wait in `%later` and are moved into `@cand` at the top of scan n; with no seam `%later` is empty, so a real run executes no line a seamed spec does not).

The ancestors' map (`%keep`), the interlock, the zombie re-probe and the messages are as before. The Perl changes by the lines in `experiments/ref-patch.diff`:
```perl
my @cand = 2 .. 99999; my %later; my $only = $ENV{PICKMAN_SWEEP_ONLY}; if (defined $only && $only ne '') {
open(...) or do { ...unreadable...; exit 70 };
local $/; my $t = <$f>; my %from; @cand = (); for (split /\s+/, ($t // '')) { next unless /^([1-9]\d*)(?:@([1-9]\d*))?$/;
$from{0 + $1} = 0 + ($2 // 1) } for (keys %from) { if ($from{$_} > 1) { $later{$_} = $from{$_} } else { push @cand, $_ } } }
my %keep = ($$ => 1); my %up; my @can = grep { $_ != $$ && kill(0, $_) } (@cand, keys %later);   # the ancestors' map covers hidden pids too
...
my %gone; my ($scan, $quiet, $busy) = (0, 0, 0); while (1) { $scan++; 1 while waitpid(-1, 1) > 0;
for (keys %later) { if ($later{$_} <= $scan) { push @cand, $_; delete $later{$_} } }
my @found = grep { !$keep{$_} && kill(0, $_) } @cand;                                            # unchanged from today
if (@found) { select(undef, undef, undef, 0.05); @found = grep { kill(0, $_) } @found }
unless (@found) { if (++$quiet >= 5) { my $n = keys %gone;
print STDERR "sweeper: stopped $n process(es) the specs left running\n" if $n; exit $code }
select(undef, undef, undef, 0.05); next }
$quiet = 0; kill 'STOP', @found; kill 'KILL', @found; $gone{$_} = 1 for @found; last if ++$busy >= 50;
select(undef, undef, undef, 0.05) }
print STDERR "sweeper: processes keep appearing; this run is not clean\n"; exit 71;
```
The comment above the `fence.SWEEPER` assignment gains (after "71 if processes keep appearing."): "It ends only after five scans in a row, at least 50 ms apart, found nothing: one scan can miss a live process of the sandbox (c0225). PICKMAN_SWEEP_ONLY, a file of pids, narrows the candidates (a test seam; the runner removes it with `env -u`); an entry `<pid>@<n>` is a candidate only from the nth scan on, standing in for the scans that miss it." The comments inside the table over the candidates and the passes say the same in fewer words (the patch).

**Why five, and 50 ms.** One scan of today's sweeper is one probe and, if it answers, a re-probe 50 ms later; c0168's reviewer measured that pass missing an exec-looping leftover in at worst 7 of 60 sweeps, q ≈ 0.12 per scan. Scans 50 ms apart (plus a full scan's 25 ms) fall at unrelated points of any exec cycle (E1: about 2.7 ms an exec), so a miss needs five independent empty scans: at q = 0.12 that is about 1 in 40,000 sweeps of such a leftover, against 1 in 5,000 for four, 1 in 600 for three and 1 in 8 today. At what E1 to E3 measured today (no miss in 4,000 probes and 750 sweeps) it is far smaller. 50 ms is the sweeper's existing pause. z-nile's goals put no escape before cost, so the count is the one that makes the worst measured rate negligible, at about +0.32 s a jailed run (E4); each scan more or less moves the cost by about 0.08 s. The values are two literals in the passes' loop (`5` and the pause's `0.05`), named by the skill and the comment, so a later issue that measures a longer or more frequent miss changes three places, all pinned by AC7.

**Why this fails closed (zz-arch rule 7).** The sweep guards against a run's leftovers outliving it, and its unguarded action is ending. Before, one scan's "nothing" ended it. Now ending needs five "nothing"s over at least 200 ms, and any scan that finds something sends it back to the start of the count, so a child forked by a process it just stopped (before the STOP) is looked for by at least five more scans. Nothing it used to stop goes unstopped: a scan stops everything it finds, as before. The seam's new entry form can only remove candidates from scans, and only in a spec run (the runner strips the variable); an entry it can't parse is ignored, never read as "every pid", and `0` is no longer parsed at all (F8).

**Limits, said plainly.**
- A live process of the sandbox that the jail's `kill 0` does not answer for in five scans 50 ms apart still outlives the run. None was seen (E1 to E3); the design names the window so a later measurement can be held against it.
- Five empty scans more often meet another run's exiting process, which the jail answers for for a moment (c0168): such a scan stops it (as today), counts it, and starts the count of empty scans again, which costs five more scans (about 0.3 s). c0168 measured that churn at 1 pass in 120 at load 14 (f = 0.008 per scan), so a run ends with 71 only if 50 stopping scans come with no five empty ones in a row: P = (1 - (1 - f)^5)^50, about 1e-70 at f = 0.008. Sustained churn would change that: at f = 0.4 per scan P is about 0.017 a run, where today one empty pass ends the sweep. Nothing measured is near that, and c0168's end test (below) removes the case. What is stopped does not change. Once in 4 runs of AC5's real run on a busy machine the sweep counted 3 where 1 was the run's own: counting other runs' processes is c0168's.
- A foreign zombie the jail answers for in every scan still ends the sweep with 71 after 50 stopping scans, as today (c0168). Under this rule a zombie found in every scan is a stopping scan, never an empty one: see "With c0168" below.
- A pid reused between two scans by another process of the sandbox is just another leftover, and is stopped.

**With c0168 (design review 001 F6).** c0168 (`sweep-counts-other-runs`, still `preparing`, a stalled prep) also changes when the sweep ends. Its snapshot (af1e1f9b9, rule 5) ends the sweep "on a pass that counts nothing and finds no pid the pass before did not find", so a zombie found in every pass and never counted still lets the sweep end with the command's status; its note at line 125 says "c0225 changes this end test and must carry both as a guard (the lead's note to c0225)". Read plainly, this issue's "empty" would contradict that: a scan that finds that zombie is not empty, five empty scans never come, and the sweep ends with 71 after 50 scans (c0168's own mutant M12). The combined rule, which whichever lands second takes as its definition: **a scan is empty when, after the re-probe, it leaves nothing to stop; once c0168 lands, a scan is empty when it counts nothing and finds no pid the scan before did not find. The sweep ends after five empty scans in a row, and any other scan sets the count to 0.** Whichever lands second also carries the guard the other names: c0168's forking-tree real run (its AC6) if c0225 lands first, or AC9 here (the stopping-scan limit) and the five-scan cases if c0168 lands first. The rule reaches c0168's next prep through this document on `main`: its "Existing work" search (`grep -rlE 'SWEEPER|keep appearing'` over the items outside `done/`) finds this issue. c0168's documents are not edited from here, and no `depends_on` is needed because either order works under the rule (a hand merge of the one Perl loop and the one skill line); fixing the order is the user's call if they prefer it.

### Scalability
The sweep's cost is fixed per run, not per spec: five scans of 99,998 pids (about 25 ms each) and four 50 ms pauses when nothing is left, plus five more scans after the last scan that stopped something. A run that leaves n processes behind costs the same stopping scans as today. Nothing grows with the number of specs or homes beyond one sweep per jailed run.
### Maintainability
- The rule is two literals (`5`, `0.05`) and one counter in the passes' loop, next to the existing pause; the comment above the assignment states it once and names c0225, the skill bullet states it for readers of the testing rules, and AC7 keeps the two in step.
- The seam's `@<n>` form is the one way a spec can stand in for a probe the jail misses, so the next change to when the sweep ends is testable the same way, without timing.
- c0168's coming change (what is counted, and its end test) plugs in at the same place, between the re-probe and the kill; the combined rule above says what "empty" means then, so neither design has to invent it when the second lands.
### Usability
A person sees nothing new on a clean run: the same `stopped <n>` line when something was left, and the same exit statuses (the command's, 70, 71). A run ends about a third of a second later. A spec author who needs a sweep in a spec reads the seam's `<pid>@<n>` form in the Sweeper bullet.
