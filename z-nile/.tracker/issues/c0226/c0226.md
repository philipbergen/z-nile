# c0226: Trail cuts move and change

## Problem
trail.cuts lists a commit that moves the compaction map and changes it in the same commit as no cut (-M --diff-filter=AM), so the trail follows renamed ids across it, while c0118 counts such a commit as a compaction; found by c0138's prep, older than c0138

## Non-goals
- c0138 (trail compaction reset, prepared): it changes which items a compaction resets, not which commits count as cuts.
- Which items a cut restarts (`since`'s predicate, c0138's `renames`/`resets`), the capture marker's text, `trail.read`'s signature, and how history dates an item once a commit is a compaction (`renamedIds`, `date`): all unchanged.
- Merge commits: `git log -p` shows no diff for a merge by default, as the `--name-only` log before did and as history's log does; main lands by squash. Unchanged.

## Solution
Ideas from capture; z-design decides.
- Make `trail.cuts` count a commit that renames the map file and changes it in the same commit, as c0118 does; a case with such a commit.

The approach: move history's rule for "this commit is a compaction" (`isCut`, c0118) into `ids.luau` as `ids.cutFile`, the one rule both readers judge by, and have `trail.cuts` read the maps' history as history does, from a patch log with rename detection off, so a move is a deletion and an add whose contents the rule compares. A map moved unchanged stays no cut; a map moved and changed in one commit becomes one, named by the file it moved to. `trail.cuts` gains the optional `dir` that c0284 also gives it, so a spec can run it on a fixture repository in-process.

## Design

**The defect, shown (E1).** In a scratch repository whose compaction map is moved and changed in one commit (12 lines, one pair and the header changed, so git's similarity stays over 50%), `git log -M --diff-filter=AM --name-only -- <maps>` (today's `trail.cuts`) lists only the plain adds and in-place changes: the move-and-change commit is a rename (`R0xx`), so the filter drops it, and so does a move that only reorders the map's lines. history (c0118) reads the same commit with `--no-renames -p` and its `isCut` counts it, because the added map's content is not the deleted one's. The two readers disagree about which commits are compactions, and the trail follows renamed ids across the one history cuts at.

**Product decisions relied on.** None of pickman's `game-design.md` applies (tooling only). The rule is c0118's, unchanged: "A compaction (a commit that adds or changes a map's content; moving the map is none)" (`history.luau` header) and "only a commit that adds or changes a map's content is a compaction: a `git mv` of the map, even squashed with a landing, is not" (lesson zz-rules/item-history-spans-moves-and-compaction, from c0118 design review 001 F2). c0118's own fixture already pins the move-and-change shape for history: "a fourth compaction that also moves the map back: its content changes (a delete plus an add whose content differs is a compaction, not a move)" (`tests/acceptance/c0118/history.spec.luau`). The user's rule that an id change is never followed (R0042 design review 013) is why a missed cut matters.

**Code.**
- `z-nile/engine/ids.luau` (pure; the module that owns the compaction map, zz-arch rule 5), placed right after `ids.TOMBSTONE`, away from `parseMap` where c0138 adds `ids.renamedIn`:
  - `export type MapDiff = { path: string, added: boolean, deleted: boolean, plus: { string }, minus: { string } }`: one map file's change in one commit, from a `--no-renames` patch (moved here from `history.luau`, unchanged).
  - `ids.mapPatchLine(m: MapDiff, line: string)` (design review 001 F2: the map patch's one reader): applies one line of a map file's patch, after its `diff --git` line, to `m`. `new file mode` or `--- /dev/null` marks it added; `deleted file mode` or `+++ /dev/null` deleted; a `+` or `-` line that is not a `+++ `/`--- ` header is a content line (its text after the sign goes to `plus` or `minus`); every other line is ignored: `index`, hunk headers (`@@ -0,0 +1,13 @@`), mode lines and `\ No newline at end of file` (it starts with `\`, so a map that differs only in its final newline reads as the same lines, as history has always read it). These are history's map-line rules today, moved, not changed.
  - `ids.cutFile(maps: { MapDiff }): string?`: history's `isCut`, moved word for word, returning the map file instead of `true`. A commit is a compaction when a map is changed in place (neither added nor deleted), or added with content (its `plus` lines joined by `\n`) that no map deleted in the same commit had (their `minus` lines joined the same way). Returns the first such map of `maps` in their order (the patch's path order), else nil (a plain move, a deletion, no map).
- `z-nile/engine/history.luau`: `type MapDiff = ids.MapDiff`; `isCut` is deleted and `flushCommit` uses `ids.cutFile(maps) ~= nil`. In the patch loop a map file's lines go to `ids.mapPatchLine(curMap, line)` (a branch `elseif curMap then` before `elseif cur then`), so the map branch inside the item branch goes, and `flushFile` no longer copies `added`/`deleted` onto the map (the reader sets them). Item files keep their own add/delete marker check: their `cur.added`/`cur.deleted` drive arrivals. `renamedIds`, `date` and every result are unchanged. Its header comment gains the move-and-change sentence (below); the comment on `isCut` that claimed "trail.cuts reads it the same way, with renames" goes with `isCut`.
- `z-nile/engine/trail.luau`:
  - `trail.cutsArgs(head: string): { string }` (pure): `{ "log", "--no-renames", "--diff-filter=AMDT", "-p", "--unified=0", "--format=@@%H", head, "--", <ids.MAP_FILES...> }`. `--no-renames` makes a move a deletion plus an add (git's `log -p` detects renames by default, `diff.renames`). The filter names every status a path-limited log without renames reports (add, modify, delete, type change), so it filters nothing in practice; it is written out because c0284's sequestered trace spec counts the cuts log by the substring `--diff-filter=AM` (`board.spec.luau` line 412), which `AMDT` still contains.
  - `trail.parseCuts(log: string): { [string]: string }` (pure): only the framing. `@@<sha>` opens a commit, `diff --git a/… b/<path>` opens a map diff, and every other line of that diff goes to `ids.mapPatchLine`, the reader history uses. At each commit's end `ids.cutFile` judges its diffs; a cut commit maps its sha to the file. Hunk headers (`@@ -0,0 +1,13 @@`) never match `^@@(%x+)$`.
  - `trail.cuts(head: string, dir: string?): { [string]: string }` = `trail.parseCuts(git(trail.cutsArgs(head), dir) or "")`. `local function git(args, dir: string?)` runs in `dir` when given (the same signature and body c0284's prototype gives both). `trail.read` is unchanged: it still calls `trail.cuts(head)`.
  - The module header's sentence "Moving the map (c0114) is not a compaction." becomes "Moving the map unchanged (c0114) is not a compaction; moving and changing it in the same commit is one (c0226: `cuts` judges by ids.cutFile, history's rule)." The comment on `cuts` says the same.
- `z-nile/skills/zz-rules/lessons/item-history-spans-moves-and-compaction.md`: in the c0118 paragraph, "(c0118 design review 001 F2; `trail.cuts` reads it with renames for the same reason)." becomes "(c0118 design review 001 F2), and a `git mv` that also changes the map's content is one: `trail.cuts` and history judge both by the one rule, `ids.cutFile`, over a log without renames (c0226: the `-M` log `trail.cuts` read before listed a moved and changed map as no compaction)."

**Why one rule, one reader, and the patch log.** The defect is two readers with two rules for one question, so the fix is one rule (`ids.cutFile`) over diffs built by one reader (`ids.mapPatchLine`): history and `trail.cuts` keep only their own framing of the log. Comparing blob ids (`--raw`) would be cheaper to parse, but it differs from history's line-joined comparison when only a final newline changes (a move that drops it is a cut by blob, none by lines); reading the same patch lines through the same reader makes the two agree by construction, and `cuts.spec` pins that they do (a parity case over the fixture, with such a move). Git's rename score cannot stand in for the comparison: a reordered map can score `R100` while its content differs (the spec's reorder case), and history counts that as a compaction.

**Pure/adapter split.** `ids.cutFile`, `trail.cutsArgs` and `trail.parseCuts` are pure; `trail.cuts` is the edge (one `git log`, read-only). No server/client authority (tooling).

### Scalability
One `git log` per `trail.read` (per `capture`), as before; it now carries the maps' patches. Every compaction writes the whole map (~113 lines today), so the log grows by one map per compaction and per map move: today 2 commits and about 230 lines; a hundred compactions of 400-line maps is about 40,000 short lines, parsed linearly. The pure parse is O(lines). No new process. The spec builds one 10-commit repository, runs `trail.cuts` four times and `history.parse` once in-process: about 3 to 6 s; AC1 to AC3 together take about 6 s of wall time with the runner's start (E2).

### Maintainability
Which commits are compactions is one function, `ids.cutFile`, and how a map's patch is read is one function, `ids.mapPatchLine`, both beside the map's other rules in `ids.luau` (zz-arch rule 5: `ids.luau` reads the map). History and `trail.cuts` call both and keep only their log framing, with rename detection off in both logs. A change to how a map's patch reads (a new marker line, a prefix setting) is made once and seen by both readers; `cuts.spec`'s parity case fails if they ever count different commits. A new map location joins `ids.MAP_FILES`, which `cutsArgs` and history's `logArgs` both read.

### Usability
No command line changes. The user sees `(history before <sha> not followed: it changed <map>)` on an item whose life starts at a commit that moved and changed the map, the same commit history undates at; before, `capture` silently followed the renamed id across it. The marker's text is unchanged.
