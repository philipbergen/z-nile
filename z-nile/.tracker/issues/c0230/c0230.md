# c0230: Lesson fast tests

## Problem
zz-test: a test is fast and cheap on a shared machine; a proof that needs real work (a CPU spinner, a big fixture, a sleep) is a check.sh-only script run once to prove the implementation and never promoted, because c0191's runner-cpu spec burned a core on every full gate; check: does this spec burn CPU, wait, or write many files, and if so is it a one-time proof outside the promoted suite?

Decided with the user (2026-11-01): "You can use it to prove that your implementation works and then it gets removed. I'm not running that. Make a lesson, fast tests are important".

## Non-goals
- c0181's checks for lessons in general, and c0178's cheaper fixtures: this lesson is the rule they serve.

## Solution
Ideas from capture; z-design decides.
- A zz-test lesson, short (c0181): a test on a shared machine is fast and cheap; it does not burn CPU, sleep for seconds, or write thousands of files.
- A proof that needs real work is a `check.sh`-only script (c0156's pattern), run once by the executor to prove the implementation and never promoted, so it is not in the full suite.
- Enforcement as a check (c0181): the runner reports spec files slower than a budget or that start a CPU-bound child, and c0178's `fixtures: N files written, M processes started` line is the cost signal.

## Solution
The rule becomes one consolidated zz-test lesson and one line of the zz-test skill's Speed section, and the spec runner enforces it by reporting. Every concurrent run (the coordinator: two or more files, more than one job) starts each worker under a small CPU measurer, a perl wrapper that waits for the worker and prints the CPU of the worker and of every process it waited for as the last line of the worker's stdout. The coordinator takes that line off, and after `slowest:` (and after c0178's `fixtures:` line) and before its summary prints `over budget:` with one line per spec file whose own wall seconds are over 60 s or whose measured CPU is over 3 s (ruled with F3 below, a guess pending the user's confirmation). It reports only: the run's outcome, its other lines and its exit code do not change. The limits change for one run with the runner flag `--budget <wall>:<cpu>`, which no nested run inherits. c0178's `fixtures: N files written, M processes started` line stays the signal for files and processes, and the lesson names both lines. A proof that needs real work stays what c0191 made it: a check.sh-only script run once, never promoted.

**3. The budget module** (new, pure): `z-nile/tests/lib/budget.luau`, beside `schedule.luau` and `slow.luau`, the one reader of the limits and of the measurer's line and the one writer of the report. No I/O.
```luau
export type Limits = { seconds: number, cpu: number }
export type Cost = { file: string, seconds: number, cpu: number? }
budget.DEFAULT: Limits            -- { seconds = 60, cpu = 3 }
budget.LESSON: string             -- "zz-test/specs-never-burn-real-resources"
budget.SHOWN: number              -- 10
budget.CPU_PREFIX: string         -- "zn-spec-cpu "
budget.MEASURE: string            -- the perl measurer, run as `perl -e budget.MEASURE <command> <args...>`
budget.limits(value: string?): (Limits?, string?)
budget.takeCpu(stdout: string): (number?, string)
budget.over(costs: { Cost }, limits: Limits): { Cost }
budget.render(over: { Cost }, limits: Limits): string?
```
- `limits(value)`: `value` is the `--budget` flag's value. nil (no flag) is `DEFAULT`. `"<wall>:<cpu>"`, each matching `^%d+$` or `^%d*%.%d+$` and greater than 0, sets both. Anything else, the empty string included, returns `(nil, 'tests/run: --budget must be <wall seconds>:<cpu seconds>, each a positive number (got "<value>")')`.
- `MEASURE`: `fork`; the child `exec`s the command (`exit 127` when it can't); the parent `waitpid`s, reads `(times)[2, 3]` (the user and system CPU of the children it and they waited for), prints `zn-spec-cpu %.3f\n` and exits with the child's status (`128 + signal` for a signal), as `fence.WORKER_LANE` does. A process the worker detached and never waited for is not counted (a lower bound, said in the skill line).
- `takeCpu`: only the **last** line counts (after one trailing newline), and only when it is `zn-spec-cpu ` followed by `%d+%.%d+`; then it returns that number and the stdout up to that line; otherwise `(nil, stdout)` unchanged. It reads only the last 64 bytes and requires a newline (or the start of the text) right before the line, so a line longer than the tail is never the measurer's, and a megabyte line costs nothing (F4: the first prototype's `^(.-)([^\n]*)\n?$` took 40 s on one 100 KB line). A spec's own output can't speak for the measurer, which prints after the worker has exited.
- `over`: a file is over when `seconds > limits.seconds` or (`cpu ~= nil` and `cpu > limits.cpu`), strictly; a file with no CPU is judged on wall only. Slowest first, ties by path.
- `render`: nil when nothing is over; else the header `over budget: <n> spec files over <wall> s wall or <cpu> s cpu (lesson zz-test/specs-never-burn-real-resources)` (limits printed with `%g`), then for each of the first `SHOWN` files `  <file> <seconds %.1f> s wall, <cpu %.1f> s cpu` (or `cpu not measured`), then `  and <k> more` when there are more.

**4. The runner** (`z-nile/tests/run.luau`; the prototype is `experiments/prototype.patch`, cut with full blob ids against `main` at 4e24823d):
- It requires `./lib/budget` (in `tests/lib`, so every promoted spec that copies the runner with its `tests/lib` still loads it: lesson zz-test/runner-copies-must-still-load).
- **The flag** `--budget <wall>:<cpu>` (F2: a flag, never an environment variable, because every nested run a spec starts inherits the environment: the first draft's `PICKMAN_SPEC_BUDGET=0.01:0.01` turned `c0049/parallel-runner` red, in-process too). In the early block that refuses `--slow` with `--exclude-slow` (before the measurement wrapper, the guard and the lock), every `--budget` in `process.args` has its next argument checked with `budget.limits(<next> or "")`, and a refusal is written to stderr and the run exits 2, so nothing runs (a missing value is refused as `got ""`). The top process already forwards its arguments through `bounded.pl`, the browser guard's rerun and the jail's launcher, so the coordinator sees the flag. The argument loop consumes `--budget` and its value into `budgetValue`. The coordinator builds each worker's argv itself and never adds the flag, so no worker and no nested run started by a spec sees it. The usage string and the header comment name it.
- `Outcome` gains `cpu: number?`. In `runConcurrently`, every worker is started as `perl -e budget.MEASURE lune run tests/run -- --jobs 1 --report-seconds <file>`; with `PICKMAN_WORKER_LANES` set, the lane wrapper runs that measurer (`perl -e fence.WORKER_LANE <lanes> perl -e budget.MEASURE lune ...`). The measurer is independent of the lanes on purpose: the prep found that a top-level run never has `PICKMAN_WORKER_LANES` in its workers' environment (E3, captured as c0352), so a measure inside the lane wrapper would see nothing. `fence.luau` is not changed.
- `report(o)` first does `o.cpu, o.stdout = budget.takeCpu(o.stdout)`, before it looks for `seconds` and the summary, so the summary is again the last line and the measurer's line is never printed.
- After `slowest:` (and after c0178's `fixtures:` line, which `depends_on: [c0178]` puts there first), the coordinator builds one `Cost` per outcome (`file`; `seconds`: the worker's own, from its `seconds` line, as `slowest:` uses, never the coordinator's clock, which includes the wait for a lane; `cpu`: the measurer's number), and prints `budget.render(budget.over(costs, limits), limits)` when it is not nil, with `limits = budget.limits(budgetValue)`. Then the summary and the exit code exactly as before.
- The in-process path (one file, or `--jobs 1`) accepts the flag and prints no report: it has no measurer (Lune reads no child CPU, and the outer wrapper's `bounded.pl` measures the whole run), and it is the path a check.sh line and a worker take, where a report would be repeated per file. The gate's affected, full and slow runs are all concurrent, so every promoted spec is reported there.
- Slow-tier files are reported like any other when a run includes them (`--slow` lists the slow tier's debt, at most ten lines and a count).

**Budgets (ruled with F3: a guess pending the user's confirmation).** 60 s wall and 3 s CPU per spec file (option (b) of F3, Open to the human). Wall is the looser limit because a loaded machine stretches wall time five-fold (c0178: load 18 to 35) and CPU much less. The CPU limit is low so that a short CPU-bound child is reported in almost any file, as the capture asks ("the runner reports spec files ... that start a CPU-bound child"): c0191's spinners burned about 2 s each, and the review's 4.5 s spinner is reported in every file (a trivial file measures 0.0 s, E5). Measured on the prototype (E4, E11, E13): the slowest fast-tier z-nile file takes 6.7 s of wall and 4.2 s of CPU at light load, pickman's 2.7 s and 2.3 s; z-nile has 10 fast files over 2 s of CPU and 4 over 3 s at light load, and 13 over 3 s at load 5 to 16 (E13), pickman 1 over 2 s; the fast tiers total 82.9 s (z-nile, 161 files) and 38.7 s (pickman, 269 files) of CPU. So every z-nile gate lists 4 to 13 honest files, the heavy ones the Speed section already asks to split, as debt until they are split; it reports only, so the outcome never changes. The slow tier has 19 files over 60 s wall or 30 s CPU, and more at 3 s. Another default changes `budget.DEFAULT`, the two pinned sentences (the Speed bullet in `docs.spec`, the report header in `budget.spec`) and AC1's default case only.

**Why report, not fail (prep).** The capture asks that the runner *reports*. Wall and CPU vary with the machine, so a failing budget would turn the gate red on load, not on code; the report is beside `slowest:` where the skill's "Monitor continuously" bullet already sends whoever runs a gate.

**The tests burn nothing** (the rule they test). `runner-budget.spec` gives every perl of its nested runs a stand-in `times` through `PERL5OPT=-I<fixture>/perl -MZnFakeTimes` (a module of one `BEGIN { *CORE::GLOBAL::times = sub () { (0.25, 0.5, 3, 4.125) } }`, written in the spec's own `.cache/c0230-budget`), so the measurer's number is exactly 7.125 through the real coordinator, on lanes and without: the report must say `7.1 s cpu`, list both files at `--budget 1000:7` on CPU alone and none at `1000:8` (F1: the first draft's format-only check passed a report that showed the wall as the CPU). Nothing in `z-nile` names `PERL5OPT` (`git grep -i PERL5` is empty), so neither the fence nor repo-fence touches it, and the lane wrapper and fence's start-id perl call no `times`. The wall cases use 0.2 s `sleep` fixtures against a 0.1 s limit. The real CPU of a grandchild, and the wall being the worker's own while every lane is held, are proved once by `proof-cpu.luau` (no `.spec.luau` name), which check.sh runs only before `./zn done`, under `ulimit -t 60` and `./zn run --time 120`, as c0191's proofs are (about 1 s of CPU and 4 s of wall).

**No behaviour change** besides the report: every result line, `slowest:`, the summary and every exit code are as before (AC2's "nothing over budget" case pins the four lines; `c0049/parallel-runner`, `c0165/results` and the runner-copying specs pass on the prototype, E6, E10).

### Scalability
One more process per spec file of a concurrent run: the measurer perl, which forks once and waits (about 3 ms; 161 z-nile files and 269 pickman files per full gate add well under a second). No file is read or written: the CPU travels on the worker's stdout, which the coordinator already reads, and `takeCpu` reads 64 bytes of it. The report is O(files) after the run. Nothing grows with items, roots or projects; every home's run uses the same runner.

### Maintainability
One concern, one module: `budget.luau` owns the limits, the measurer, the line's format and the report, and `run.luau` calls it in four places (the early refusal, the argument loop, `report`, the summary). A new measure (c0178's per-file files or processes, if wanted later) is a field of `Cost` and a clause of `over`. The lesson is the single statement of the rule; the skill line points at it.

### Usability
The report names the limits and the lesson, so whoever reads it knows the rule and where it is written; at most ten files are listed, then a count. `--budget` is the one knob, a flag of `lune run tests/run` (in its usage text and header comment), refused before anything runs when malformed, naming the value. The gate does not pass it: a look at other limits is `lune run tests/run -- --budget <w>:<c> [files]` by hand. No `./zn` command, usage text or command list changes.

## Regression guard
- The coordinator's output when nothing is over budget: the result lines, `slowest:` and the summary only. Pinned by AC2 ("nothing over budget prints no report and the output is as before") and by `c0049/parallel-runner` (slow tier: four cases count the lines and the `slowest:` line) and `c0165/results` (compares two runs' reports without `slowest:`).
