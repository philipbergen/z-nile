### F1 [high] AC2 passes an implementation that reports the wall seconds as the CPU
Where: c0230.md Design §4, the summary bullet ("one `Cost` per outcome (`file`, `seconds` …; `cpu`)"); `acceptance/runner-budget.spec.luau:109` onwards (the cpu column is checked only against `%d+%.%d s cpu$`); `acceptance/proof-cpu.luau`; Rules table (no row for the coordinator's wiring from the measurer to `Cost.cpu`).
Evidence: in the clone I replaced `prototype.patch:191`'s `cpu = o.cpu` with `cpu = if o.cpu ~= nil then o.seconds else nil` (the measurer and `takeCpu` stay; the report prints the wall time in the cpu column). `lune run tests/run -- .tracker/issues/c0230/acceptance/runner-budget.spec.luau` gave `7 passed, 0 failed`, and `(ulimit -t 60; zn run --time 120 -- lune run …/proof-cpu.luau)` printed all 8 `ok` and exited 0. The burn file's wall time (~1 s) is over 0.3 and at least 0.5, and the cheap file's wall time (~0.0) is under 0.3, so the one-time proof can't tell the CPU from the wall time either. The suite pins the measurer's sum (M13, a stand-in `times`) and `over` (M7, pure), but nothing pins that the number the measurer printed is the one the report shows.
Critique: AC2's CPU half ("over the per-file … CPU budget") can be met by a second wall-clock budget. That is the half that is meant to catch a CPU-bound child (Budgets, prep). The author will be tempted to assert "cpu < wall" for the 0.2 s naps. That is a race against the CPU of Lune's start-up (I measured 0.0 to 0.1 s cpu for a trivial worker at load 10), and it pins no number.
Consequences: the exact fix is a stand-in `times` for every perl in a nested run, through the real coordinator. I ran it: `PERL5OPT="-I<dir> -MZnFakeTimes"`, where `ZnFakeTimes.pm` is `BEGIN { *CORE::GLOBAL::times = sub () { (0.25, 0.5, 3, 4.125) } } 1;`, on two fixtures (a 0.2 s nap and a no-op) with `PICKMAN_SPEC_BUDGET=0.1:1000`, printed `  .cache/rv-spin/nap.spec.luau 0.2 s wall, 7.1 s cpu` (top-level run, through bounded.pl and the jail). PERL5OPT reaches every perl of that nested run: the lane wrapper (it calls no `times`) and fence's start-id perl (no `times`). Nothing in `z-nile/tests`, `z-nile/lib` or the engine names PERL5OPT (`git grep -i PERL5` is empty), so neither the fence nor repo-fence strips or flags it. The module lives in the spec's own `.cache/c0230-budget`.
Recommendation: add to `runner-budget.spec` a case run on lanes and without them. Write `ZnFakeTimes.pm` under `{base}/perl` and run the nested run with `PERL5OPT = "-I{base}/perl -MZnFakeTimes"`. (a) With `0.1:1000`, each NAP file's line ends exactly `, 7.1 s cpu`. (b) With `1000:7`, both files are listed on CPU alone (wall far under 1000). (c) With `1000:8`, no report. Add Rules rows: "the report's cpu is the measurer's number" (mutant `cpu = o.seconds`) and "the CPU limit is applied by the coordinator" (mutant: the costs are built without `cpu`). Run both mutants and record them in E9. proof-cpu stays the one real burn.

### F2 [high] `PICKMAN_SPEC_BUDGET` is inherited by every nested run a spec starts, so the documented knob turns promoted specs red
Where: c0230.md Solution ("It reports only: the run's outcome, its other lines and its exit code do not change"), Usability (`PICKMAN_SPEC_BUDGET` "the one knob"), Budgets ("`PICKMAN_SPEC_BUDGET` lowers the limits for a look"); the Speed bullet and the lesson ("It reports only: the outcome stands"); `prototype.patch` (the coordinator reads `process.env.PICKMAN_SPEC_BUDGET` and passes the environment on to workers unchanged).
Evidence: on the prototype, `PICKMAN_SPEC_BUDGET=0.01:0.01 lune run tests/run -- tests/acceptance/c0049/parallel-runner.spec.luau` gave `FAIL … every listed spec runs exactly once, with fewer jobs than specs … parallel-runner.spec:363: expected 8, got 15` and `15 passed, 1 failed`. The same file without the variable gave `16 passed, 0 failed`. The nested coordinator inherited the limits and printed a header plus six file lines. That was a one-file, in-process top-level run, so clearing the variable only for the coordinator's workers would not stop it: an in-process run's specs inherit the top process's environment, and E3 shows a Lune `process.env` assignment can't take it away. `runner-budget.spec:49` defends itself (`PICKMAN_SPEC_BUDGET = ""`). `c0049` and `c0165/results` (its `stable()` compares two nested reports) do not.
Critique: the outcome stands only while nobody uses the knob the design tells people to use. c0178 met the same trap (its E6: "the nested coordinator read the outer run's counts") and fixed it with a folder per coordinator. Nothing here does the same. The tempting fix is to add `PICKMAN_SPEC_BUDGET = ""` to every spec that pins a nested runner's output, as c0049 does for `PICKMAN_JOBS`. That overrides promoted specs (c0049, c0165, and whichever pin nested output next) and leaves a rule every future spec must remember.
Consequences: a runner flag, `--budget <wall>:<cpu>`, is never inherited. The top process already forwards `process.args` to bounded.pl and the launcher forwards `"$@"`. The coordinator builds each worker's argv itself, so no worker and no spec ever sees the flag. The flag needs: a value parser beside `--jobs` (`run.luau:227`); the early refusal naming `--budget` (exit 2, before the wrapper and the lock); `budget.limits`' message; the usage comment; the Speed bullet's and the lesson's sentence (docs.spec pins both); and `runner-budget.spec` and `proof-cpu.luau` passing it in args instead of env. An in-process run accepts it and prints nothing, as now. The gate can't pass it, which is fine for "a look" by hand; the skill line says to run `lune run tests/run -- --budget …` directly.
Recommendation: replace the environment variable with `--budget`, as above. Add two `runner-budget` cases. In each, an outer run with `--budget 0.001:0.001` has one fixture spec that runs a nested concurrent run of two no-op fixtures and writes the nested stdout to `{base}/nested.out`. The outer run is concurrent (that fixture plus a no-op) in one case and in-process (that fixture alone) in the other. Assert that `nested.out` holds no `over budget` line and ends with its summary, and that the concurrent outer run prints its own block. Add a Rules row "a run's budget never reaches the runs its specs start" (mutant: read `PICKMAN_SPEC_BUDGET` as well), run.

### F3 [high] The per-file CPU budget cannot see the CPU-bound child the Problem names; the captured "reports … spec files that start a CPU-bound child" is reworded to "over 30 s of CPU"
Where: capture's Solution idea 3 ("the runner reports spec files slower than a budget or that start a CPU-bound child"); the Problem ("because c0191's runner-cpu spec burned a core on every full gate"); c0230.md:88 Budgets ("The CPU limit is what catches 'a CPU-bound child' … A spinner of a few seconds stays under; the lesson's check question is what catches those at design").
Evidence: c0191's first prep (a1272ede) shows the spinners the user objected to. `runner-cpu.spec` "a process that burns CPU is stopped by the limit" ran `perl -e 'alarm 20; 1 while 1'` under `PICKMAN_SPEC_CPU=2` (≈2 s of CPU). `engine-cpu.spec` spun under `ZN_ENGINE_CPU=2`. `bounded.spec`'s `--cpu` cases each burned about a second. At the defaults it printed no report. With `PICKMAN_SPEC_BUDGET=1000:1` it printed `spin.spec.luau 4.5 s wall, 4.5 s cpu`. So a file with a 4.5 s CPU-bound child, twice c0191's, is invisible to the report. No total-CPU threshold separates it from honest specs: E4 has fast-tier files at 3.2 s of CPU (`c0115/lessons`), and the slowest z-nile file (6.7 s wall × 0.75) is about 5 s.
Critique: the report the capture asks for would not have flagged the spec that caused the issue. The design hands that case back to a reading at design time, which is the mechanism that already let c0191's rounds 1 to 5 through. Raising this as a threshold tweak won't hold, because any threshold low enough to see a 2 s spinner also lists honest specs heavier than it.
Consequences: (a) To detect a CPU-bound child as such, something must sample per process (any one descendant past N s of CPU). That matches the Speed section's "split or stub a spec that takes more than about a second", but it is noise until they are split. (c) Keeping 30 s needs a recorded scope decision that spinners under 30 s are caught only by the lesson's question.
Recommendation: escalate to the user, with one measurement first: a fast-tier run per home with the limit at 0.001 s and `SHOWN` raised locally, listing every file's CPU, so each option's list is known. The options: (a) a per-process CPU sampler in the launcher, the full captured outcome, at the cost above; (b) the per-file CPU default lowered to a measured value (for example 3 s), which reports c0191-style spinners in light files and lists today's heavy files until they are split; (c) keep 30 s and record `Scope decision (user, …)` that "a CPU-bound child" means one that pushes its file past 30 s. Whichever is chosen, add a check.sh-only proof case (proof-cpu's pattern): a 2 s spinner fixture is reported at the defaults (a, b), or the decision line is recorded (c). With F1's stand-in, the suite can then pin "a file with 3 s of child CPU is listed at the defaults" without burning anything.

### F4 [medium] `takeCpu` is quadratic in the length of a line: one 100 KB line stalls the coordinator for 40 s
Where: c0230.md Design §3 `takeCpu`; `prototype.patch:63` `string.match(stdout, "^(.-)([^\n]*)\n?$")`, called on every worker's whole stdout in `report`.
Evidence: a probe calling the prototype's `budget.takeCpu` on `FAIL x :: y\n     expected "<n × a>"\n1 passed, 1 failed, 1 spec files\nzn-spec-cpu 0.100\n` took 0.408 s at n = 10,000, 3.675 s at 30,000 and 40.540 s at 100,000. 10,000 ordinary 120-byte lines took 0.619 s. The lazy `(.-)` retries `[^\n]*` from every position of a line. The coordinator is a single Lune thread, so while it matches, no other lane's result is reported. A failing `toBe` on a long single-line string (a `serde.encode` result, a file list) prints both values on one line (`t.luau:49`). A 300 KB line costs about 6 minutes, and 1 MB about an hour, past the runner's own 3600 s bound.
Critique: this is the cost the lesson forbids, put into the runner's failure path. The obvious patch, `string.match(stdout, "\n([^\n]*)\n?$")` without the anchor, is quadratic too.
Consequences: the measurer's line is at most about 30 bytes, so reading only the last 64 bytes is enough. The rule "only the last line counts" still holds if the line before the match must be a newline or the start of the text. Nothing else changes.
Recommendation: `takeCpu` reads the last line from `string.sub(stdout, -64)` (after one trailing `\n`), requires a `\n` before it unless that line is the whole stdout, and builds `body` with one `string.sub`. Add `budget.spec` cases: a 1 MB line followed by the measurer's line returns the CPU and the body unchanged, and a 1 MB line with no measurer's line returns `(nil, stdout)`. Both are instant when the code is right. Add a Rules row (mutant: the whole-stdout pattern), run once under `./zn run --time 20`, where the mutant does not finish. A regression would also show as that spec file over budget.
