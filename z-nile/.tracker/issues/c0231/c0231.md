# c0231: Hook refuses bare yes

## Problem
boundcmd: refuse a bare 'yes' (Decision 2 lists it as a follow) while still passing 'yes | head', because review-001 F4 of R0071 found it passes and the sequestered c0191 spec requires 'yes | head -3' to pass; check: does the rule read whether yes's output is piped to a bounded consumer?

## Non-goals
- Chasing every spelling of a never-ending writer (`seq inf`, `cat /dev/zero`, `tail -f`, `printf` loops): c0191 names the rest as limits in zz-test and the reaper is the backstop. Only `yes` changes here.
- Reading scripts (`bash probe.sh`) or a `yes` in a file: the hook reads one line.
- Any change to the wrapper, the reaper or the CPU limits.

## Solution
Captured outcome (kept): `boundcmd` refuses a bare `yes` (c0191 Decision 2 lists it as a follow) while still passing `yes | head`, as R0071 review 001 F4 found and the sequestered c0191 spec requires (`yes | head -3` passes). The rule reads whether `yes`'s output is piped straight into a bounded consumer.

Detail added by prep: `checkText` hands `checkCommand` an `After` record (the next pipeline stage when the command ends in `|` or `|&`, and whether the command is a `case` pattern). `yes` is refused as a `follow` unless (a) it sits in a Monitor call (bounded by its own timeout, c0191), (b) it is a `case` pattern (no command), or (c) its stdout is not redirected and the stage right after its pipe is a `head` that stops at its count, or a command bounded by its own means (`boundedish`: `./zn …`, the wrapper, a check.sh). The refusal names the head and the wrapper.

## Design
Prototype: `experiments/prototype.patch` (diff of `z-nile/engine/boundcmd.luau` and `z-nile/skills/zz-test/SKILL.md` against today's main; the branch itself changes neither). It applies cleanly to main at the prep commit.

### The rule
`boundcmd.luau`, pure text (no process is started by the hook or by its specs):
- `type After = { pipe: { string }?, pattern: boolean }`; `checkCommand(words, depth, raw, after)` gains the optional fourth parameter, passed on through `caffeinate -t N <cmd>`.
- `headReads(words)`: the stage resolves (through `env`, prefixes) to `head`, with no `xargs` before it, and no negative count (`-n -3`, `-n-3`, `-c -1`, `--lines=-2`, `--bytes=-2`, `--lines -2`): a negative count reads everything first, which `yes` never finishes.
- `stdoutAway(args)`: `>f`, `1>f`, `>>f`, `&>f`, `>&2` on the yes command: its pipe then gets nothing (`2>&1` and `2>/dev/null` do not count).
- The `yes` branch of `checkCommand` (after the wrapper/`caffeinate` branch, before FOLLOWERS), matching the resolved name (`/usr/bin/yes`, `env yes`, `FOO=1 yes`, `nice yes`, `time yes`, `timeout 5 yes` all resolve to `yes`; `timeout` bounds time, not output, so it is still refused), returns `refuse("follow", "yes", line, say)`; say names `yes | head -3` and `<zn> run --time <seconds> -- sh -c '<pipeline>'`.
- `checkText` tracks `cases` (open `case` ... `esac` spans) so `case "$a" in yes) ...` patterns are no command; `esac` closes the span.
- No exempt argument: BSD `yes --version` prints `--version` for ever (E1).
- zz-test's two restatements (Hooks list, hook paragraph) list a `yes` that no `head` reads among the follows and drop `yes` from what passes.

### Forms the rule allows, and why (each has a spec)
| form | why | spec |
|---|---|---|
| `yes \| head -3`, `head`, `-n 5`, `-n3`, `-c 100`, `--lines=2`, `--bytes 10`, `\|&`, `/usr/bin/head`, a newline after the pipe | head exits at its count; `yes` dies of SIGPIPE (E1: status 141) | allowed :: head forms |
| `yes 2>/dev/null \| head`, `yes 2>&1 \| head`, `yes \| head -3 \| sort`, `yes \| head -3 > out`, `yes \| (head -3)`, `{ head -3; }`, `env LC_ALL=C head` | stderr redirects do not touch the pipe; later stages cannot lengthen yes; groups and prefixes still run that head | allowed |
| `x=$(yes \| head -1)`, backticks, `sh -c`, `eval`, here-document to a shell, after `cd d &&` | nested text is judged by the same rule | allowed :: nested |
| `yes \| ./zn run --time 5 -- cat`, `yes \| ./zn status c0231`, `<checkout>/zn run -- cat`, `bounded.pl`, `bash z-nile/check.sh` | a stage bounded by its own means (`boundedish`) ends within its limit and closes the pipe (engine CPU 1800 s, run `--time` at most 3600) | allowed :: bounded stage |
| `./zn run --time 5 -- yes`, `./zn run --time 10 -- sh -c 'yes \| rm -i a'` | the wrapper bounds the whole command and the hook does not look inside it | allowed :: wrapper |
| any `yes` in a Monitor call | Monitor is bounded by its own timeout (c0191 Decision 2) | contexts |
| `echo yes`, `grep -rn "yes"`, `git commit -m yes`, a here-document body, `# yes`, `which yes`, `[ "$a" = yes ]`, `case` patterns `yes)`, `y\|yes)`, `(yes)` | `yes` is data, not the command | mentions |
Refused: a bare `yes` (any arguments, any prefix, any separator `; && \|\| newline`, a group end, `$(...)`, backticks, `sh -c`, `eval`, a shell's here-document), `yes > out`, `yes 1>/dev/null \| head`, `yes \| cat\|wc\|tee\|grep\|sed\|while\|xargs\|rm\|git add -p`, `yes \| sort \| head` (a later head is not the stage after yes), `yes \| head -n -3`, `yes \| xargs head`. A background call judges `yes \| head -3` as `background` (not bounded by its own means) and a bare one as `follow`.

Judgement calls, not the user's: (1) a stage bounded by its own means counts as a consumer: `./zn …` workers pipe into the repository's own commands all day, and the stage ends within its own limit; (2) a `timeout 5 yes` stays refused: the time is bounded but the tool shell would take the output; (3) the pipe must be `|` or `|&` straight after `yes`, not a later stage: one rule, easy to read.

### Scalability
One extra pass over the already-split command list: `ends[k]` and `commands[k + 1]` are indexed, `cases` is an integer; cost is linear in the line, within the 2 s CPU the hook gets (R0079 fuzz: 20,000 lines in 0.59 s).

### Maintainability
All of it sits in `boundcmd.luau` beside FOLLOWERS, reusing `resolve`, `basename` and `boundedish`; no second reader of the pipeline. One restated rule (zz-test) moves with it and is pinned by AC7.

### Usability
An agent that types `yes | head -3` or `yes | ./zn …` sees nothing new. One that types a bare `yes` or `yes > /dev/null` gets the follow refusal naming `yes | head -3` and the exact `<checkout>/zn run --time <seconds> -- sh -c '<pipeline>'`.

## Acceptance criteria

### Checked
- AC1: a yes whose output no head reads straight from its pipe is refused as a follow, however it is reached, ended, nested or redirected
- AC2: yes piped straight into a head with a non-negative count, or into a command bounded by its own means (the wrapper, ./zn, a check.sh), passes in every spelling and nesting, and the wrapper runs any yes
- AC3: a pipe into anything but such a head (a filter, a loop, xargs, a later head, a negative count) does not save yes
- AC4: a yes that is no command (a mention, an argument, a case pattern) passes, and a closed case hides nothing
- AC5: a Monitor command may run yes, and a background call judges yes as before
- AC6: the refusal names the follow rule, the head that ends yes and the wrapper, and the hook entry refuses with exit 2
- AC7: zz-test restates the rule: a yes no head reads is a follow, and yes is no longer listed as passing
- AC8: the promoted seatbelt specs stay green: c0191 boundcmd, hooks and docs, c0244 homes, the review fixes
