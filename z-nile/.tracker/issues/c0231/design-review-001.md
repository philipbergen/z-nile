### F1 [high] A case pattern that starts with `yes` and has more alternatives (`yes|y)`) is refused, so AC4 is unmet while its spec passes
Where: prototype `checkText` (`pattern = cases > 0 and ends[k] == ")"`); `acceptance/mentions.spec.luau` AC4; Design "The rule" (`checkText` tracks `cases` …) and the table row "`case` patterns `yes)`, `y|yes)`, `(yes)`"
Evidence (reasoned by tracing `split`): `split` cuts a pattern alternation at every `|`, the same way it cuts a pipe. In `case "$a" in\n  yes|y) echo y ;;\nesac`, command k is `{"yes"}` with `ends[k] = "|"`, and command k+1 is `{"y"}` with `ends = ")"`. For k, `pattern` is false because its end is `|`, not `)`, and `pipe = {"y"}` is not `head`, so the hook returns `follow` / `yes`. The same happens to `… no) :;; yes|y) :;; esac` on one line, to `"yes"|n)`, to `yes | no)`, and to the same text in a shell's here-document (`bash <<EOF … EOF`, read by `checkText(body, 1)`). The spec has only `y|yes)`, where yes is the last alternative, and the first alternative right after `case … in` on the same line, which is swallowed into the `case` command. Neither form reaches the bug. The rule has the opposite hole too: inside a case body, any command ended by `)` counts as a pattern. So `case $a in x) (yes) ;; esac` and `case $a in x) (cd d; yes) ;; esac` pass, and that yes runs for ever.
Critique: AC4 says a case pattern passes. The prototype passes the sequestered spec and still breaks AC4 for the most common way to match an answer (`yes|y)`). The easy fix is "also treat a `|`-ended command as a pattern when the next one ends in `)`". That makes `x) yes | (cat) ;;` a pattern too, because `split` drops the `(` (an empty command is not recorded), so a real never-ending pipeline would pass.
Consequences: telling a pattern from a command needs to know where the pattern position is (after `in` and after `;;`), not only what ended the command. Today `split` reports `;;` as two `;` and records nothing for the second, and it reads `;&` as a `&` job (line 348 rewrites the end to `&`). Both would need a real separator.
Recommendation: have `split` return `;;`, `;&` and `;;&` as single separators. Nothing else reads `ends` for `;`, and the background and `&` checks look only at `|`, `|&` and `&`. Then keep an `inPattern` state in `checkText`, beside `cases`. It is set by a `case` command that ends in `\n` or `(`, by a `case … in <word>` that ends in `|`, and by any command ended by `;;`, `;&` or `;;&` while `cases > 0`. While it is set, a command ended by `|` or `)` is a pattern, and a `)` clears the state. Add spec cases to AC4 (pass): `case "$a" in\n  yes|y) echo y ;;\nesac`, `case "$a" in no) :;; yes|y) :;; esac`, `case "$a" in no) :;; "yes"|n) :;; esac`, and `bash <<EOF\ncase $1 in\n  yes|y) echo;;\nesac\nEOF`. Add these to AC1 (refused): `case "$a" in x) (yes) ;; esac`, `case "$a" in x) yes | (cat) ;; esac`, `case "$a" in x) yes | cat ;; esac`. Add a row "only a pattern position is a pattern" with the mutant "any `)`-ended command inside a case is a pattern", and rewrite M10, M11 and M12 against the new state. Re-run c0191 `boundcmd.spec` for the `;;` and `;&` separator change (AC8).

### F3 [medium] A redirection before the program hides a bare `yes`: `>/dev/null yes`, `2>/dev/null yes`, `env >f yes`
Where: `resolve` (`if program ~= nil and string.match(program, "^%d*[<>]") then program = nil`), which the prototype's yes branch relies on; AC1 "however it is reached, ended, nested or redirected"
Evidence (reasoned): for `>/dev/null yes`, `words[1]` is `>/dev/null`, so `resolve` returns `nil`, `checkCommand` returns OK, and a yes that burns a core passes. `2>/dev/null yes`, `> out yes` and `env >/dev/null yes` behave the same way (`env`'s option loop stops at the redirect word, which then becomes the "program" and is nulled). These are exactly the "redirected" spellings AC1 claims, and the sequestered `refused.spec` has none of them, so a prototype with the hole passes AC1.
Critique: the obvious fix is to skip leading redirect words in `resolve`. `resolve` serves every rule, so that fix also starts refusing `2>/dev/null tail -f x`, `>log lune run p.luau` and the like. That is correct, but it changes c0191's behaviour beyond `yes`.
Consequences: skipping a separate operator (`>`, `>>`, `2>`, `<`, `&>`) must also skip its file operand, or the file name becomes the program. The `) > log 2>&1` case `resolve` already handles (a group's trailing redirect) must still resolve to nil. The new refusals for the other rules need AC8 re-run and an Overrides check.
Recommendation: in `resolve`'s prefix loop, skip words matching `^%d*[<>]` and `^&>`. Skip one more word when the redirect word is a bare operator. Add AC1 cases `>/dev/null yes`, `2>/dev/null yes`, `> out yes`, `env >/dev/null yes`, an AC8-side regression case that `) > log 2>&1` still passes, and a Rules and mutants row "a leading redirection does not hide the program". If the author keeps the change local to `yes`, say so in the Design and narrow AC1's wording to match. That is a design choice, not a cut: the outcome stays refused.

### F4 [medium] The consumer rule is an allow-list, which reverses the module's stated principle without saying so, and it refuses consumers that end on their own (`yes | rm -i a`, `yes | git add -p`)
Where: Design "Refused" list and Judgement calls (1) to (3); `acceptance/consumers.spec.luau` ("yes | rm -i a b", "yes | git add -p", "yes | ./installer"); `boundcmd.luau` header ("refuses only what it positively recognises. Anything it cannot read passes")
Evidence: the capture asks "does the rule read whether yes's output is piped to a bounded consumer?". `rm -i a b`, `cp -i`, `mv -i` and `git add -p` read only the answers they need and then exit. `yes` dies of SIGPIPE on its next write (E1 shows that mechanism with `head`), so these are bounded consumers, and the sequestered spec pins them as refused. The design does this on purpose (only `head` and `boundedish` count), but none of the three Judgement calls names it. The module's header still says it refuses only what it recognises, while this rule refuses every consumer it does not recognise.
Critique: the allow-list is defensible. The hook cannot tell `rm -i` from a reader that reads to EOF (`git hash-object --stdin`, `./installer`), and an unknown reader would leave `yes` running for ever. But a reader of the module and of zz-test will believe the opposite principle, and the next rule written in this file may follow the header and not this rule.
Consequences: if the allow-list stays, the refusal for `yes | rm -i a` has to give the agent a way through, and today it offers only `head` and the wrapper. If prompt-answering consumers are allowed instead, the list needs its own both-sides cases (`yes | rm -i a` passes, `yes | rm a` passes since rm reads nothing, `yes | git hash-object --stdin` refused) and a rule for flags.
Recommendation: keep the allow-list and record it as Judgement call (4): "an unknown consumer may read to EOF, so only a consumer known to stop counts; a prompt-answering command goes through the wrapper". Amend the module header comment and the zz-test hook paragraph to state the exception ("`yes` is the one rule that needs a recognised consumer"). Pin that clause in AC7. Leave `consumers.spec`'s `rm -i` and `git add -p` cases as they are, now backed by a Design sentence (z-design/spec-design-correspondence).

### F5 [low] A pipe outside the command that holds `yes` is not carried in: `sh -c 'yes' | head -3`, `{ yes; } | head -3`, `(yes) | head -3` are refused
Where: prototype `checkCommand` (the `SHELLS` and `eval` branches call `checkText` without `after`; only `caffeinate` passes it through); `split` (a group's `;` or `)` ends the yes command)
Evidence (reasoned): `sh -c 'yes' | head -3` checks the inner text `yes` alone, with no pipe, and returns `follow`. `{ yes; } | head -3` gives yes the end `;`, and `(yes) | head -3` gives it `)`. All three end at once in a shell. The Design says nested text "is judged by the same rule", but here the outer pipe is lost. Lines this repo's workers type (`yes | head -n 5`, `yes | ./zn …`, `./zn run --time N -- yes`) are not affected. The cost is a refusal with a misleading message for rarer spellings. Related and older, now newly exposed: an unterminated or non-`[%w_]` here-document word (`<<'END-OF-MSG'`) leaves its body as commands, so a prose line that starts with `yes ` is refused.
Critique and consequences: carrying the pipe into `sh -c` is one argument. Groups would need `split` to record group ends, which this issue should not take on.
Recommendation: pass `after` into `checkText` for `sh -c` and `eval` as the last command's `after` (a `checkText(text, depth, after?)` parameter applied to the final command only), with an AC2 case `sh -c 'yes' | head -3`. Name the group forms and the here-document word limit under zz-test's "spellings a one-line scanner cannot read" (pinned by AC7), so the refusal is documented and not a surprise.

### F6 [low] The reasons given for Judgement calls (1) and (2) don't hold
Where: Design, Judgement calls; "Forms the rule allows" bounded-stage row
Evidence: (1) says "`./zn …` workers pipe into the repository's own commands all day" and that the stage "ends within its limit (engine CPU 1800 s …)". A grep of `*.md`, `*.sh`, `*.luau` and `zn` finds no `yes |` anywhere outside c0231, and no `./zn` command prompts: `approve` refuses without a terminal. A CPU limit is no wall-clock bound either: `./zn work` and `./zn dispatch` can run for hours. The allowance is still safe, but for a different reason. A stage that doesn't read stdin leaves `yes` blocked on a full pipe, not spinning, and `yes | ./zn run …` is bounded by `--time`. (2) refuses `timeout 5 yes` because "the tool shell would take the output", yet the table allows `./zn run --time 5 -- yes`, which sends the tool shell the same output for the same 5 s.
Recommendation: restate (1) as "a stage bounded by its own means either ends within its wall limit (`./zn run`, a check.sh) or doesn't read stdin, so `yes` blocks on a full pipe and uses no CPU". Restate (2) as "the wrapper is the one sanctioned bound (process group, stops when its caller ends, marked for the reaper); `timeout` is none of these". No spec change.

### F7 [low] The head-count rules rest on GNU behaviour that the supported host doesn't have, and some spellings slip past them
Where: Design "`headReads`"; Unknowns (E1 tests `--version` and SIGPIPE only)
Evidence: "a negative count reads everything first" is GNU `head`. macOS's BSD `head -n -3` exits with "illegal line count", which also ends `yes`. Refusing it is harmless, but the stated reason is untested on the host (reasoned, not run). The GNU spellings `-qn -3`, `-vn-3` and the abbreviation `--lin=-3` pass `headReads` and would never end under a GNU `head` on PATH (Homebrew gnubin). A huge positive count (`head -n 1000000000000`) also passes, and in practice it does not end.
Recommendation: reword the Design reason as "a GNU `head` on PATH reads everything first for a negative count; BSD `head` refuses it; either way it is no proof the pipe closes". Treat any option cluster that ends in `n` or `c` followed by a negative value, and any `--l…=`/`--b…=` prefix with a negative value, as negative. Add those two consumers.spec cases. A huge count can stay a named limit in zz-test.
