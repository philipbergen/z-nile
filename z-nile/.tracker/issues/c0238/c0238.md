# c0238: Concurrent runs wait and crashed owners are taken over

## Problem
From the user (2026-10-26), part of c0165's capture "Reuse passed test results", which reuses a passed spec by its fingerprint in a SQLite database shared by every worktree:

- **Concurrent runs wait, they don't duplicate**: when two runs reach the same fingerprint at once (two worktrees, or the author and the reviewer), the second waits for the first's result and uses it.
- **Crash detection**: a `running` row stores its owner's PID (plus the process start id, so a reused PID isn't mistaken for the owner). A waiter sees a crashed or killed run at once, takes the row over and runs the spec itself, instead of waiting forever.

Needs c0165's store and fingerprints.

Split from c0165 (user, 2026-11-03: "Split it"), which had grown to a 600-line design and a sixth review round; c0165 keeps the fingerprint, reuse and store outcomes, and this issue keeps the outcomes below. Every outcome is the user's 2026-10-26 capture, not narrowed.

Prior design work: c0165's prep branch `prep-reuse-test-results` (commit a03b4995; `z-nile/.tracker/issues/c0165/`: the design, six review rounds and their answers, and the acceptance specs) holds a design for the whole of c0165; this issue's prep takes the part that is its own.

## Non-goals
- Fingerprints, the store and reuse themselves: c0165.
- Limiting concurrent gates machine-wide: c0157.

## Solution
- A run claims a fingerprint by inserting a `running` row in one transaction; a second run polls until the row is `passed` or `failed`. A dead owner (the same PID and start-id check as the runner's `tests-run.lock`) frees the row.
- A `failed` row on the same fingerprint is either reported as the same failure or rerun once to tell a flake apart (prep decides).
- A poll costs one db read and one liveness check per distinct owner, not per waited spec.
