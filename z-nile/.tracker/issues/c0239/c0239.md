# c0239: Full gate only at the merge

## Problem
From the user (2026-10-26), part of c0165's capture "Reuse passed test results":

- **The full gate runs only at the merge** (`./zn land`, the PR's merge, `done`). Every step before it (the author's iterations, the review, the pre-PR gate) runs only the affected specs.

Scope decision (user, 2026-10-26): "The full gate at merge runs all for real so we can find out if dependency graph has gaps" (the merge's full gate may not reuse fingerprinted passes: every spec runs).
Scope decision (user, 2026-10-26): of the full gates near a raft's merge, "done's run + CI" count as the merge's: `./zn done` runs every spec for real, and the merge condition's "full gate on the final head" accepts that run when the content is the same, instead of running it again; CI stays as it is.
Decided with the user (2026-10-31): "I want a full end 2 end to have run before the final merge into main for the chore/defect/feature. Along the way we run efficiently and only the affected." (zz-execute Phase 0's baseline, Phase 3 steps 2-3, Phase 4 step 1, zz-review code mode item 1, Phase 5 step 2, `./zn done`'s gate and the raft `check.sh` template's RC0 are affected-only; the merge keeps one full gate.) The 2026-10-31 session also decided "Phase 0 gets no full red-main baseline; red main surfaces at the merge gate".
Decided with the user (2026-11-03), c0165 design review 004 F2: asked what zz-execute Phase 0 does about red main, the user chose "No baseline": Phase 0 runs no gate and reads no CI result; red `main` first shows at `./zn done` and the merge.

An affected baseline on an unchanged worktree selects no spec, so it can't stand in for a red-main check (c0165 design review 003 F1). Depends on c0165 (the affected selection and reuse it builds on) and c0180 (affected selection by command).

Split from c0165 (user, 2026-11-03: "Split it"), which had grown to a 600-line design and a sixth review round; c0165 keeps the fingerprint, reuse and store outcomes, and this issue keeps the outcomes below. Every outcome is the user's 2026-10-26 capture, not narrowed.

Prior design work: c0165's prep branch `prep-reuse-test-results` (commit a03b4995; `z-nile/.tracker/issues/c0165/`: the design, six review rounds and their answers, and the acceptance specs) holds a design for the whole of c0165; this issue's prep takes the part that is its own.

## Non-goals
- The affected selection and fingerprint reuse themselves: c0165, c0180.
- Telling a red `main` from the raft's own failure at `done`: c0240 (it reports "fails on the base too"); take care that a spec the raft added, absent at the base, is not reported as red `main` (c0165 design review 006 F1).

## Solution
- Gate modes by step: author iterations, stream checks, review, after merging `origin/main`, raft RC0: `--affected`; `./zn done`, `./zn land`, CI, `setup.sh`: `--full`, fresh; the merge condition: the same content as `done`'s full run, reused.
- Restate the rule in zz-execute, zz-rules, zz-review, zz-test, `templates/prompt.md`, the raft `check.sh` template, `AGENTS.md` and the stop hook (one project-scoped affected call from the selector's forcing rules, falling back to the unscoped call for any answer it can't use).
