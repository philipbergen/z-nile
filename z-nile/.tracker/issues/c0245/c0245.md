# c0245: Capture matching ignores registry

## Problem
boundcmd toolingMatch: an absolute runner path under the checkout and a ../ path from another home match tests/run by suffix or after normalising, so <checkout>/nowhere/tests/run and ../../snake/tests/run pass the seatbelt whatever the registry says (R0075 review 002 F3, found while fixing c0244); check: does a path form that reaches the gate's runner decide from the registry's homes, not from its suffix?

## Non-goals
- **Which commands the seatbelt refuses otherwise** (interpreters, loops, follows, detachers, background calls) and how it reads a shell line (`split`, `resolve`, the `cd` tracking in `checkText`) stay c0191's. Only the decision "is this `lune run` target the gate's own tooling" changes.
- **The registry and how the hook reads it** stay c0244's: `z-nile/guard-bash.luau` keeps loading `projects.load(ZN_CHECKOUT)` and passing every project's `home` as `Context.homes`, or nil when the registry can't be read. This issue does not edit guard-bash.
- **Symlinks and the file system.** The seatbelt stays pure over the command text (boundcmd's header: "This is a seatbelt, not a jail"). A path whose `..` follows a symlink inside the checkout can reach another file than its text says; the old suffix rule accepted every such path too, so this is no new way past it, and `./zn reap` stays the backstop. Case-insensitive file systems: `Snake/tests/run` is refused (the registry's names are compared exactly), which is the safe direction.
- **New TOOLING entries.** The table keeps its entries (less the bare `tests/run`, which becomes `RUNNER`, below); adding one stays the rule zz-arch states.

## Solution
`toolingMatch` resolves a `lune run` target to the file it names before it consults anything: an absolute path as written, a relative one from the folder the command runs in (the call's, moved by its `cd`s), with `.` and `..` resolved and repeated slashes folded, `.luau` dropped. Inside the checkout, the path is taken from the top of its tree (the checkout itself, or a worktree under `.worktree/<name>/`), and that path, never a suffix of it, is looked up: an entry of `TOOLING` (all of them paths from the top of the tree, such as `z-nile/affected`) or a registered home's runner, `<home>/tests/run` for a home in `Context.homes`. A path that is not inside the checkout is a scratch copy and never counts. The bare `tests/run` stops being a table entry: from inside a home it resolves to that home's runner, and anywhere else (the root, a worktree's top, a `.cache` probe folder) it names no runner, as `SETUP.md` says ("Specs run from a project's home …, never from the root"). With no checkout, or a relative target and no known folder, the path alone decides exactly as today. A refused target whose name the old rule would have accepted gets a reason in the refusal, so the agent sees why `tests/run` was not the gate's here. The match has two callers, the foreground walk (`checkText`, through `checkCommand`) and a background call's second walk (`boundedish`), and both read a relative target from the folder the `cd`s before it moved to, through one `cd` step (design review 001 F1).

## Design

### The rule
`z-nile/engine/boundcmd.luau`, pure, no new requires:

- `TOOLING: { [string]: boolean }` loses `["tests/run"]`; its comment says each entry is "its path from the top of a tree of the checkout (the checkout itself, or one of its worktrees)" and that every registered home's runner counts as well. `local RUNNER = "tests/run"` names a home's runner from inside that home.
- `local function endsIn(t: string, key: string): boolean`: `t` ends in `/<key>`.
- `local function byName(target: string): boolean`: today's rule, unchanged in effect, used when the context is too thin to resolve: a relative target, `normalise`d, is `RUNNER`, a `TOOLING` entry or `homeRunner(t)`; an absolute one ends in `/RUNNER` or `/<entry>` of `TOOLING`. (Today's absolute branch looked up `TOOLING[t]` on an absolute `t`, which never matches; dropping it changes nothing.)
- `local function treePath(target: string, dir: string, checkout: string): string?`: `full` is `target` when it starts with `/`, else `dir .. "/" .. target`. It walks `string.gmatch(full, "[^/]+")`: `..` removes the last part (`table.remove` on an empty list is a no-op, so `/..` is `/`, as the file system reads it), `.` is skipped, anything else is appended. It splits `checkout` the same way into `top`, returns nil unless `#parts > #top` and `parts[i] == top[i]` for every `i` (whole parts, so `/x/pickman2` is not inside `/x/pickman`), skips a leading `.worktree/<name>` pair when two or more parts follow `top` (one level: worktrees are not nested), and returns the rest joined by `/`, with one trailing `.luau` removed.
- `toolingMatch(target)`:
  ```lua
  local checkout = CTX.checkout
  local absolute = string.sub(target, 1, 1) == "/"
  if checkout == nil or (not absolute and CTX.cwd == nil) then
      return byName(target)
  end
  local dir = if absolute then "/" else CTX.dir
  if dir == nil or (not absolute and not insideOf(dir, checkout)) then
      return false
  end
  local path = treePath(target, dir, checkout)
  return path ~= nil and (TOOLING[path] == true or homeRunner(path))
  ```
  `insideOf` stays as it is. `CTX.dir` is nil after a `cd` the scanner can't resolve, which refuses a relative target as today. The folder must be inside the checkout, as today; the new part is that the resolved path must be too, and is looked up whole.
- **Both callers follow the `cd`s** (design review 001 F1). `toolingMatch` has two callers: `checkCommand`'s `lune` branch, reached from `checkText`'s walk, and `boundedish`, which `boundcmd.check`'s background loop calls once more for every command of a background call, after `checkText` has put `CTX.dir` back to the call's folder. The `cd` step moves out of `checkText` into `local function followCd(words: { string })`, unchanged in effect (resolve the `cd` operand against `CTX.dir`; an operand with `$`, `~` or a backtick, `-`, or none makes it nil). `checkText` calls it after each command, as now. The background loop sets `CTX.dir = CTX.cwd` before it, calls `followCd(words)` at the end of every iteration (whether or not the command was loose), and sets `CTX.dir = CTX.cwd` after it, so the `&`/`wait` scan and any caller see the call's folder. It keeps `checkText`'s simplifications: a `(…)` subshell's `cd` is not undone at `)`. Before c0245 the bare `tests/run` key matched from any folder, which hid that the background walk read a stale folder; with the file rule, `cd pickman && lune run tests/run` in the background would resolve from the root and be refused.
- `homeRunner(t)` is unchanged (plain-folder filter, nil `homes` adds nothing); with nil `homes` the two runners in `TOOLING` (`z-nile/tests/run`, `pickman/tests/run`) still count, which c0244's "a checkout whose registry cannot be read keeps today's list" pins.
- The refusal of an unbounded `lune run` (`checkCommand`) appends a reason when `target ~= nil and byName(target)`: `` `{target}` here is not the gate's own: only a registered home's `tests/run` and the tooling in this checkout or one of its worktrees count, by the file the path reaches.`` It is given for every such target: absolute, relative (`tests/run` from the root, `../../snake/tests/run` from `C/pickman`) or after a `cd` the scanner can't resolve (design review 001 F2). A probe whose name looks like nothing in the table gets no reason. The refusal's parenthesis becomes "(the gate, `./zn …`, check.sh files and `lune run tests/run` from a project's home need no wrapper)" (design review 001 F3): without "from a project's home" it would restate the old rule beside the reason that contradicts it. No spec pins the old phrase (`grep -rn "need no wrapper" z-nile/tests pickman/tests` finds nothing).
- No new `while` or `repeat` loop: the walks are generic `for` loops over `gmatch` and the `top` list, so c0193's loop lint (R0072, active) has nothing new to list.

What each form does (the cases in `absolute.spec`, `relative.spec`), checkout `C`, homes `pickman`, `z-nile`, `snake`:

The only targets that pass now and did not are spellings of a file the gate owns (`affected` from `z-nile/`, in the foreground or the background, `//`, `/..`); every other change refuses.

### Scalability
The cost is a few string walks per `lune run` word (bounded by the path's parts), against the 17 ms hook start c0244 measured; the registry is still read once per call by guard-bash. A new home needs nothing here (its runner counts from the registry); a new tool joins `TOOLING` by its tree path.

### Maintainability
One function decides a resolved path (`treePath` plus the two lookups) and one keeps the thin-context rule (`byName`); one `cd` step (`followCd`) serves both walks, so the foreground and background readings of a line can't drift; the suffix loop survives only in `byName`, for callers that give no checkout (the hook always gives one: `scripts/hooks/pre-bash.sh` sets `ZN_CHECKOUT`). A reader sees one table whose keys mean one thing (a path from a tree's top), and the bare runner is a named constant, not a key that meant "any folder".

### Usability
An agent that types `lune run tests/run` in a home, `cd pickman && lune run tests/run` from the root (in the foreground or with `run_in_background`, the form `SETUP.md:42`, zz-test and pickman-test teach), `lune run <checkout>/snake/tests/run`, or `lune run ../z-nile/tests/run` from another home sees no change. One that runs the runner's name from the root, a worktree's top or a probe folder, or reaches a home the registry doesn't list, is refused with the wrapper to use and, now, the reason (AC4), instead of a silent pass of an unbounded file.
