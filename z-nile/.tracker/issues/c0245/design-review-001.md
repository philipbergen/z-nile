### F1 [high] A background call that `cd`s into a home before `lune run tests/run` is now refused, the form zz-test and SETUP.md document
Where: c0245.md, Design, "The rule" (`toolingMatch` reads `CTX.dir`); `z-nile/engine/boundcmd.luau:888` (the background loop in `boundcmd.check` asks `boundedish(words)`, which calls `toolingMatch(args[2])` at :470) after `checkText` has put `CTX.dir` back to the call's folder (:715). Neither the Design, its table nor the Regression guard mentions this second caller.
Evidence: with `{ checkout = C, cwd = C, homes = <the seven homes>, background = true }`, origin/main's boundcmd against the prototype's:
- `cd snake && lune run tests/run`: old ok, new refused (`background`)
- `cd pickman && lune run tests/run -- tests/x.spec.luau`: old ok, new refused
- `cd z-nile && lune run tests/run`, `cd z-nile; lune run tests/run`, `cd pickman\nlune run tests/run`: old ok, new refused
- `cd pickman && lune run tests/run > log 2>&1` and `… 2>&1 | tail -5`: old ok, new refused
- `(cd pickman && lune run tests/run)`, `cd .worktree/R1/pickman && lune run tests/run`: old ok, new refused

The same commands in the foreground pass. `checkText` accepts the `lune run` with the folder its `cd`s moved to (`C/pickman` gives `pickman/tests/run`). The background loop then asks `boundedish` again with `CTX.dir == C`, so `tests/run` resolves to the root's `tests/run`, which is no longer a `TOOLING` key: `lune` is "loose" and the call is refused. Before c0245 the bare `tests/run` key matched from any folder, which hid the stale folder. `cd pickman && lune run tests/run` is the form `z-nile/skills/zz-test/SKILL.md:17`, `pickman/skills/pickman-test/SKILL.md:11` and `SETUP.md:42` teach, and `run_in_background` is how an agent runs a long suite from a session at the checkout root. No promoted case can see it: c0191's background cases (`boundcmd.spec.luau:340-356`, `"lune run tests/run -- tests/unit"` at :347) pass no checkout and take `byName`, and nothing in c0244's or c0245's specs sets `background`. E1's green suite does not cover it. The Usability claim "An agent that types `lune run tests/run` in a home … sees no change" is false for this call.
Critique: this is a regression in the documented way of running a home's specs. The quick fix is to make `boundedish` call `byName` for `lune run` (or skip the folder when `background` is set). That is safe today, since `checkText` has already refused any `lune run` the file rule rejects. But it puts a second rule beside the first, and its target choice already differs from `checkCommand`'s (`args[2]` against "the first non-option word"). The two would drift with the next change to either (zz-test/one-rule-one-function).
Consequences: the background walk has to follow the same `cd`s as `checkText` does: `&&`, `;`, newlines, an unresolvable operand making the folder unknown. It inherits `checkText`'s simplification that a `(…)` subshell's `cd` is not undone at `)`, which already holds in the foreground. After the walk, `CTX.dir` must be put back to `CTX.cwd`, so the later `&`/`wait` scan and any caller see the call's folder. One background spelling also widens: `cd z-nile && lune run affected` passes, as it does in the foreground. That is the same gate file and fits the Design's table.
Recommendation: move the `cd` step out of `checkText` (the block after `checkCommand`, :696-713) into one `local function followCd(words: { string })` that both walks call. In `boundcmd.check`'s background loop, set `CTX.dir = CTX.cwd` before the loop, call `followCd(words)` at the end of each iteration, and put `CTX.dir = CTX.cwd` back after it. I sketched exactly this on the prototype: `check.sh` stays 8/8, `stylua` stays clean, and every case above passes. Add:
- to `relative.spec` (AC2) a case "AC2: a background call reads each command from the folder its `cd`s moved to", with `background = true`. Ok: `cd pickman && lune run tests/run` from `C`, `cd z-nile && lune run tests/run -- a 2>&1 | tail -5` from `C`, `cd snake\nlune run tests/run` from `C`, `cd .worktree/R1/snake && lune run tests/run` from `C`. Refused: `cd .. && lune run tests/run` from `C/z-nile`, `cd nowhere && lune run tests/run` from `C`.
- to `hook.spec` (AC5) one payload with `tool_input.run_in_background = true` (`cd pickman && lune run tests/run`, cwd `ROOT`, code 0), so guard-bash's background flag reaches the rule through the real call site.
- a Rules and mutants row: "a background call reads each command from the folder its `cd`s moved to", killed by those cases, mutant M21 "the background loop reads the call's folder (no `followCd`)", run.
- a background row in the Design's table, and a Regression guard sentence saying that no promoted background case passes a checkout, so c0245's new case is the only guard.
AC2's text and the check.sh label should say "including a background call".
Lesson: zz-test/pin-call-site-arguments
