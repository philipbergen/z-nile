# c0246: Home rule reads every path spelling

## Problem
z-nile/tests/lib/home.luau paths() checks a $path only when it is a string; Rojo also accepts {"optional": "..."}, which maps a path outside the home past the home rule (R0075 review 003 F1: snake mapping ../pickman/src/shared that way passed home.spec and built); read the object form through the same checks and report any other non-string $path; c0185 widens this same check and must be told; check: does the format allow another spelling of this key, and what does my reader do with a value of a type it did not expect?

Scope decision (user, 2026-11-06): "re scope". The `optional` object form is delivered: c0185 (R0076, #237) moved every `$path` read into `graph.mappings`, which `z-nile/tests/lib/home.luau` now uses, and `tests/acceptance/c0185/{library,graph}.spec` pin it. What remains of this issue: the home rule reports a `$path` of any other type or shape (a number, a boolean, an `optional` that is not a string, a table without `optional`), which `graph.mappings` now skips without a word (probed 2026-11-06: each gave zero mappings), instead of letting it pass unseen; check: does the format allow another spelling of this key, and what does my reader do with a value of a type it did not expect?

Scope decision (user, 2026-11-07): "Spellings + nested files (Recommended)": c0246 also makes the home rule's nested-project line cover any `*.project.json` at any depth of a mapped folder (round 4 F1: Rojo builds one and follows its `$path`); `*.project.jsonc`, commented project files beyond the existing fail-closed line, and a Rojo-driven check (`rojo sourcemap`) are separate chores captured at hand-off.

Scope decision (user, 2026-11-07): "1" (after the round-5 report): both round-5 highs are fixed in c0246 and one more review round is run beyond the five-round limit: a link inside a mapped folder that Rojo follows to a project file inside the home, and a `syncRules` key in a home's project file.

Scope decision (user, 2026-11-08): "3" (after the round-7 report): the Rojo-driven check is brought into c0246 now, as the net that closes the reader-vs-Rojo class by construction (links, chained links, `syncRules`, case, nested files, `.jsonc` and comments reaching a file); one more review round follows the redesign.

## Non-goals
- Reading an array `$path` as a mapping. Rojo 7.7.1 builds `"$path": ["../outside"]` (probed at prep, E1), but it is not a documented spelling; the rule reports it instead of following it, so a home's top-level `*.project.json` can never hold one.
- Changing what `graph.mappings`, `graph.gameRoots` or `graph.placeInputs` return: they keep skipping a value they cannot read. Only the home rule reports it, and the rule runs on every registered home at every gate, so an unreadable `$path` in a top-level `*.project.json` of a home never reaches `main`.
- A top-level `*.project.jsonc` of a home, and a commented top-level project file beyond the existing fail-closed `maps no $path` line: the project-file lister (`home.luau`), the gate's builds and the other readers of project files match `*.project.json` only, so teaching them the second format is a separate chore, captured at hand-off. Nested ones Rojo loads from a mapped folder are covered by the Rojo-driven check below (user decision of 2026-11-08).
- Project files outside the registered homes (z-nile's own has none) and a node that is not a table (Rojo rejects it).

## Solution
`graph.unreadable(project)` lists the nodes whose `$path` the one walker (`walkMappings`, c0185) skips, and `home.problems` reports each as a problem of the project file. The two share the walker, so what is read and what is reported cannot drift apart. The home rule also asks Rojo itself what each project file builds (`rojo sourcemap --include-non-scripts`) and judges the files it names: that closes by construction what a reader of the project files can miss (links at any depth, `syncRules`, casing, nested project files, `.jsonc`). The README's home paragraph states the rules.

## Design
The captured scope was narrowed by the user on 2026-11-06 (see the Problem): the `optional` form is already read (c0185), what remains is reporting every other `$path` value.

**Quoted decisions relied on:** `Scope decision (user, 2026-11-06): "re scope"`. No game-design decision applies (tooling only).

**Rojo's real spellings (E1, E2).** Rojo 7.7.1 accepts: a string; `{"optional": "<string>"}` (other keys in the table ignored); and a one-element array of strings, which maps that folder (even `["../outside"]`). It refuses a number, a boolean, `{}`, `{"optional": 5}`, a two-element array, a nested array, an empty array and the key spelled `$Path` at its own parse; `null` is the key absent. The key `$path` has no other spelling (`$Path` fails). But Rojo reserves only six `$` keys (`$className`, `$id`, `$ignoreUnknownInstances`, `$path`, `$properties`, `$attributes`); any other table child whose key starts with `$` (`$X`, `$schema`) is built as an instance (with a warning) and its `$path` is followed, outside the home too (E4). The walker skips every `$` child, so such a node is the same hole as the array. So the reader sees two spellings and the rule must name the rest, the array above all: it builds, and today passes the rule unseen.

### `z-nile/lib/graph.luau`
- `export type Unreadable = { instance: string, what: string, dollar: boolean? }` (`instance` as `GameRoot.instance`, `""` for the tree node; `dollar` true for the next bullet's node).
- A table child whose key starts with `$` and is not one of the six `RESERVED` keys is reported as `{ instance = <its whole instance path, e.g. "A/$schema">, what = "a node Rojo builds although its key starts with $", dollar = true }` and is not walked (the readers still return what they did). The six reserved keys stay unreported.
- `walkMappings(node, prefix, out, bad: { Unreadable }?)`: after its `optional` unwrap, a `path` that is not nil and not a string is appended to `bad` with `what = describe(path)`; the recursion passes `bad` on, and the walker's comment ("both of Rojo's forms") is reworded: Rojo 7.7.1 also builds a one-element array, which the reader deliberately does not read (E1). `mappings` and `gameRoots` pass no `bad`, so their results do not change.
- `graph.unreadable(project: any): { Unreadable }`: like `graph.mappings` (a table without a table `tree` has none), sorted by `instance` (the walk order of a decoded object is not defined).
- `what` (a local `describe`, one word list, pinned by the spec): `"a number"`, `"a boolean"`, and for a table: `"an optional that is a <type>"` when it has an `optional` key that is not a string, else `"an array"` when it has an element `[1]`, else `"a table without an optional string"`.

### `z-nile/tests/lib/home.luau`
In the per-file loop of `problems`, beside `graph.mappings(decoded)`: `local unreadable = if ok then graph.unreadable(decoded) else {}`, and for each, `bad(h, "<file> has a $path that is <what> at <where>: only a string or {\"optional\": string} is read")` with `<where>` = `the tree root` for `""`, else `node <instance>`; a `dollar` entry is reported as `<file> has a node named <instance> (<what>), whose mappings are not read`. `maps no $path` fires only when the file has no readable *and* no unreadable `$path` (a file whose only `$path` is unreadable gets the one precise line). A file that does not decode (Rojo 7.7.1 builds one with a comment or a trailing comma, which Lune's decoder refuses) still gets `maps no $path` as before: that line is the rule's fail-closed answer for a file it cannot read, so the `unreadable` guard must not turn it off (`ok` stays out of the condition). The comment at `graph.luau` "the build refuses it too" is reworded: Rojo may build what the decoder refuses.

**The Rojo-driven check (user decision of 2026-11-08; rounds 3 to 7 had each found one more way Rojo loads what the readers do not see).** Two local functions of `home.luau` and one block in the per-file loop, after the mapped-folder checks (which stay as they are, so c0184's and c0185's pinned lines are unchanged):
- `home.problems` first probes `rojo --version` once (about 10 ms). If it fails, every home gets `rojo cannot be run (rojo --version fails), so what Rojo reads is not judged` (once per home) and the net does not run. A shim (rokit, when the pinned Rojo is not installed) exits 1 exactly as a refused file does, so only this probe tells "cannot run" from "refuses" (round 8 F3).
- `rojoReads(dir, name): ({ Read }?, string?)` with `Read = { file, instance }` runs `rojo sourcemap --include-non-scripts <dir>/<name>` through `process.exec` (stdout only, nothing is written) and returns every `filePaths` entry of the printed tree (relative to the project file's folder) with the node's instance path (the names below the root node, `/`-joined; the root is the project's `name`). A non-zero exit gives `nil, nil`: once the probe has passed, Rojo refuses that file, so its build fails too and nothing is read (a link loop, a missing mapped folder, a malformed file); the net prints no line for it, and the cause is named by the existing lines when there is one (a loop gets none, which is harmless: nothing is built). An answer that is not JSON gives `nil, "<why>"`, reported as `<file>: <why>` (fail closed).
- `realPaths(paths): { string }?` runs `realpath` once on all of them (a result with fewer or more lines than paths gives nil, reported as `<file>: the files Rojo reads cannot be resolved`; a file name with a newline lands here).
- In the loop, for each project file and each file Rojo reads, by its real path: (1) a file in the library's `src/shared` or `src/server` (by real path, a folder that is absent has no file) must sit at or below that folder's node, `ReplicatedStorage/Arcade` or `ServerStorage/Arcade`, the instance path Rojo printed: otherwise `<file> makes Rojo put <path> at <instance>, which is not the library's node (<node>)`, once per project file (round 8 F1: the server folder reaching a client through a link in a linked folder or a `syncRules` project; the same node rule the reader's `maps the library's X at Y` line holds, now judged on Rojo's answer; it also applies to the library's own project, whose files are inside its home); (2) any other file must lie inside the real path of the home (with a trailing `/`, so `pong2` is not `pong`): otherwise `<file> makes Rojo read <path>, which is outside the home (and the library's two folders)`, once per project file however many follow. Every entry whose name ends in `.project.json` or `.project.jsonc` and is not the project file itself gives `<file> loads <path> as a nested project (Rojo would follow its own mappings)`, one per entry.
Why this closes the class: Rojo reports the files it really reads and where it puts them, canonicalized and in its own spelling, so links (also inside linked folders), `syncRules`, the casing of `default.project.json` (Rojo reports `src/four/Sub/default.project.json` for `DEFAULT.PROJECT.JSON`, E9), nested files at any depth, `.jsonc` and commented files are judged by what Rojo does, with no second model of its file discovery. The real path is used so a file listed lexically inside the home through a link out is still outside. A project loaded through `syncRules` (any file name) is judged by the files it reads; its own file is not named a nested project (only the name tells that), and one that reads only the home's files is harmless. `rojo` is a gate tool already (`lib/workspace.luau` checks it), and one `sourcemap` takes about 30 ms. What stays open is in Non-goals.

**No behaviour change for players:** nothing under any `src/` or any Rojo project file changes; `rojo build` of every place is as before (probe: no registered project file holds a non-string `$path`, so the new line is silent on the real tree; `homes.spec` "the rule holds on the real tree" and AC4 show it).
**Existing work:** no prepared, active or mid-prep item's project file holds one (grep of every tracked `*.project.json` for a non-string `$path`: none). A branch adding one fails its home's `home.spec` at once, which is the point.
**Shared state, moves, guards:** none touched. The rule is a read-only report; it fails closed on what it cannot read, as `maps no $path` does.
**Restated rules:** only the README paragraph restates the `$path` rule (grep of the skills, AGENTS.md and `README.md` for `$path`: README of z-nile only; `pickman-arch` mentions place files, not the rule); AC4 pins the new wording.

### Scalability
The unreadable walk is linear in a project file's nodes and shared with `mappings`; the net costs one `rojo sourcemap` (about 30 ms) and one batched `realpath` per top-level project file of each home, a few dozen processes in the whole gate.
### Maintainability
No second walker: the reporter is the reader's own walk with one more branch (c0185's "one walker"). `describe` is the single place the kinds of value are worded, and the spec pins every wording.
### Usability
A violation names the file, the node (or the tree root) and what the value is, and says what is read. A home author who writes `["../x"]` is told, not silently trusted.
