# c0247: Ticket confirms intent

## Problem
z-ticket: confirm that what the user described is what they mean, before the ticket is created

User (2026-11-05): "It should use plan mode to make sure that what the user describe is what they mean".

Now z-ticket sharpens the user's words into the Problem and never checks them with the user, so a misreading survives until prep, where a design review has to find it. Before `./zn new`, z-ticket should show the user what it understood and create the stub only once they approve.

Decided with the user (2026-11-05), from design review 001 F1: "Restate via questions.md". Under `./zn dispatch` (c0117, headless) z-ticket writes the restatement as the question in `questions.md` and stops "needs the user"; the user's approval or correction reaches the re-run step through `dispatch retry`, which c0256 (a chore captured for it, after c0117) provides, so c0247 depends on c0256.

Decided with the user (2026-11-05), from design review 001 F3: "Yes, key on your words". A ticket made only from the agent's own finding (a review finding, a failed step, a graph miss) has no words of the user's to check and is filed at once; one that carries the user's words (a request, a correction, a problem they point out) is restated.

## Non-goals
- No design, scope or acceptance criteria at capture: the confirmation only checks intent. Detail stays with z-design, and scope is still only what the user said.

## Solution
- Before creating anything, z-ticket restates the request: the outcome, who is affected, the non-goals, the type (feature, defect or chore) and the project. The user approves or corrects it, and the stub is created from the approved version.
- In Claude Code this is plan mode (the restatement is the plan). The skill text states the rule so that other agents confirm in their own way.
- A message with several tickets gets one restatement covering all of them, not one stop per ticket.

## Design
**Where.** z-ticket's `SKILL.md` gets one unnumbered paragraph, `**Confirm intent first.**`, placed before step 0, and step 0 gains "after the confirmation above" (its pinned prefix `0. **Open a capture worktree first**` stays). Steps 0 to 6 keep their numbers and labels, because promoted and active specs refer to them by number (c0135's slug spec says "step 5"). `z-nile/README.md` gets two matching edits (the skills table row and flow step 1). Nothing in the engine, the gate or `./zn` changes: this is a rule in a skill, which is what agents follow.

**The paragraph** (pinned sentence by sentence by `acceptance/docs.spec.luau`):

> **Confirm intent first.** When the ticket carries words of the user's (a request, a correction, a problem they point out), restate it before anything is created (no worktree, no `./zn new`): the title, the outcome, who is affected, the non-goals, the Solution ideas, the type (feature, defect or chore) and the project, as you would write them into the Problem, with any overlap `./zn list backlog` shows. The user approves or corrects it, and the stub is made from the approved version. A correction means you restate again. Under `./zn dispatch` (`ZN_DISPATCH=1`), on any CLI, never use plan mode and never only print: ask it the way the dispatcher's prompt tells you to ask the user a question, and stop. Otherwise, in Claude Code, when `EnterPlanMode` is offered (or listed as a deferred tool: load it with ToolSearch) and you are not already in plan mode, call it, write the restatement to the plan file, ending with the line `Next: capture with the z-ticket skill, steps 0 to 6; build nothing.`, and call `ExitPlanMode`: the user's approval is the go-ahead, and a rejection means you ask what to change and restate. Without it, or if the user declines plan mode, or if you are already in plan mode (leave its plan alone), print the restatement and stop until the user answers; a subagent returns the restatement to its lead, which confirms it with the user. A message with several tickets gets one restatement covering all of them, one block per ticket. The restatement adds no design and no scope: it is the user's words, sharpened. A restatement the user has already approved counts, whether they gave it in this conversation or it comes in your brief or in the reply `./zn dispatch retry` hands over. A ticket made only from your own finding (a review finding, a failed step, a graph miss you found) has no words of the user's to check and is filed at once.

Step 0 becomes: `0. **Open a capture worktree first**, after the confirmation above and before anything is created:` (the rest of the step is unchanged). README table row: "after the user confirms a restatement of the request, captures a feature, defect or chore as a backlog issue, in a `capture-<slug>` worktree, landed with `./zn land`". README flow step 1: "**z-ticket**: the user confirms a restatement of the request first (plan mode in Claude Code); then, in `capture-<slug>`, the issue lands on `main` with `design: draft` and status `new`. No PR."

**Decisions and limits.**
- Plan mode is the Claude Code mechanism the user asked for (the Problem quotes it). The rule is stated for every reader of the skill, the most specific environment first and exclusive (review 003 F1): a dispatched run, on any CLI (`claude -p`, `grok -p`, `agent -p`), asks the restatement as a question the way the dispatcher's prompt says (`questions.md` today, `escalation.md` once c0250 lands: the paragraph does not name the file, so c0250 needs no Override, review 004 F2) and stops, and never uses plan mode or only prints (user decision, review 001 F1); otherwise a session that is offered `EnterPlanMode` uses it (never replacing a plan the user is already writing, and ending the plan file with a line that keeps a cleared context from building anything); a CLI without it, or a user who declines it, gets the restatement printed; a subagent returns it to its lead, which asks the user.
- z-ticket creates nothing before approval (no worktree of its own, no `./zn new`), so a rejected restatement leaves no trace to clean up. Under `./zn dispatch` the dispatcher opens its own `capture-zn-*` worktree before the step starts; that is c0117's and holds no item. Overlaps with the backlog (`./zn list backlog`, read only) are part of the restatement, so the duplicate question is asked once, before the stub exists; step 5 stays as the re-check after `./zn sync`.
- The restatement shows the scope-bearing parts: the title, Problem outcomes and Solution ideas (z-design, Scope is what was captured), plus the type and the project, which decide rework counting and where the item lives.
- Which tickets are held is decided by whose words they carry, not by how they are filed (user decision, review 001 F3): a lesson from the user's correction or a problem they point out during a raft is restated, and a user who is present has just spoken, so it stalls nothing; a ticket made only from the agent's own finding is filed at once, so an unattended raft never stops on its own findings.
- A restatement the user already approved is not asked twice: in the conversation, in a subagent's brief, or in the reply `./zn dispatch retry` hands to the re-run step. Without that sentence a retried headless z-ticket, a new session, would restate and stop for ever (review 002 F1).
- **c0256 must cover** (review 002 F1, now in its Solution): `dispatch new` keeps the original words so a retry can re-run z-ticket; a step that stops with `questions.md` is recorded as "needs the user", not "z-ticket made 0 issues"; the retry of a `new` run names its id; and the reply reaches the re-run step with the question.
- It costs one round trip per message, not per ticket.
