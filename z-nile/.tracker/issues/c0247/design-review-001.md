### F3 [high] The exemption is keyed on how a ticket is filed, not on whose words it carries, so user-described tickets skip the confirmation
Where: pinned paragraph's last two sentences; Design "Decisions and limits" bullet 3; AC3
Evidence: "So does a ticket an agent files from a skill rule or its own finding (a lesson, an emergent issue, a graph miss)". The skill rule that files lessons says a lesson comes "from a review finding, **a correction by the user**, or a step that failed", and "Any other lead … captures it: `./zn new issue c lesson-<slug> …` (z-ticket skill)" (z-ticket lines 31-34, the same in z-design, zz-execute, zz-rules, zz-test). A lesson the lead captures from the user's correction is filed "from a skill rule" and is exempt, though its text is the user's words, sharpened: exactly what the capture asks to confirm. The same for a postponed emergent issue the user points out mid-raft (zz-rules "Can be postponed"). And the Design glosses "already approved" as "they said yes to a proposed capture", which is a yes to filing, not to a restatement of outcome, type and project. No `Scope decision` line covers either.
Critique: the capture's outcome is "confirm that what the user described is what they mean, before the ticket is created". The first sentence of the paragraph says that; the last exempts a class of user-described tickets by mechanism. Both are pinned verbatim by AC3, so the narrowing becomes a promoted rule (M5 "kills" the version that drops it).
Consequences: keying on source means a lead in a raft or prep pauses for one restatement when the user's words started the ticket. The user is present in that case (they just spoke), so it stalls nothing; an agent's own finding (a review finding, a failed step, a graph miss the agent found) still goes straight through. A split (z-design: "new issues captured through z-ticket … the user's call") needs a line too: the user approved the split, not the new Problems' wording.
Recommendation: rewrite the last two sentences on source: "A ticket made only from your own finding (a review finding, a failed step, a graph miss you found) has no words of the user's to check and is filed at once; one that carries the user's words (a lesson from their correction, a problem they point out during a raft, the issues of a split they decided) is restated like any other. A restatement counts as approved only when the user approved that restatement in this conversation, not a yes to filing." Pin both sentences in AC3, and add rows whose mutants are the old mechanism-keyed exemption and the "yes to filing counts" reading. If the author believes lessons from user corrections should stay exempt, that is escalate to the user: with the options (confirm them: one round trip per correction; exempt them: a `Scope decision` line).
