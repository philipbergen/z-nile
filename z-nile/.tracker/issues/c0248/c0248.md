# c0248: Stacked PR delivery of a raft

## Problem
A raft is delivered today as one branch and one PR, however many issues it holds, so a reviewer, a revert and a failure all see the whole raft at once. The general model should be a **stacked PR set**: one layer per issue of the raft (a branch and a PR each), layer 1 on `main`, layer N on layer N-1, in the raft's Order (depends_on, then id). Each layer carries its issue's change, specs, spend and review; each is reviewed and gated on its own diff; layers merge bottom-up, each retargeted to `main` as the one below merges. A one-issue raft is a stack of one, so the model is general, not an exception. Streams (zz-execute Phase 2B) may still build a layer.

What should happen: zz-rules, zz-execute, z-run, `./zn start`/`done`, the prompt template and the raft template say it. The raft's own PR record (Theme, Order) names the stack; `done` moves an issue to `done/` in its own layer; a red or blocked layer stops the layers above it and not the ones below.

Part of the z-nile vision (z-nile/README.md, section How it should work). Layer 1 of the vision raft, which is itself delivered as a stacked PR set, c0248 to c0254 in that order. The README edit in `.worktree/docs-znile-vision` rides in this layer.

## Non-goals
- Changing how a single issue is designed or sized.
- The dispatcher's merging of layers (c0252) and the escalation of a blocked layer (c0250).
- The full-force review that is part of a layer's completion: c0262.
- When the dispatcher lands a stack or the green layers below a block, and with which credential: c0252.
- Switching a raft to another CLI when its own runs out of quota: c0253.

## Solution
- Layer branch name `R0010-<n>-<issue-slug>`, base = the layer below.
- Reuse the Phase 2B workstream worktrees as the way a layer is built.
- Record the stack's layer-to-PR map in the raft folder.

## Idea
A raft of several tickets is delivered as a **stacked PR set**: one layer per ticket, in the raft's Order (depends_on, then id), layer 1 on `main` and each next layer on the one below. A one-ticket raft is a stack of one. #296 (landed 2026-11-11, branch `cut-2.4-stack`) built most of the mechanics: a layer is a branch (`R0010/1/c0010`), one commit (`./zn finish`) and one draft PR on the layer below; each layer is code-reviewed on its own diff; `./zn restack` rebases the layers above a change; `./zn stack` reads the stack; `./zn done` lands it. c0248 keeps what #296 built and adds the rest:

- **Each ticket is worked to completion before the next one is picked up** (Q1). A layer is complete when it is built, reviewed, full-force reviewed (c0262) and green on top of the layer below. It is not merged. Only then does the next layer start.
- **One worker carries every layer, in order** (Q5), so its context remains from the first ticket to the last. The supervisor (c0253) runs the raft in one CLI session and resumes it for each layer (Q2, Q6). Two machines work on one raft only through a takeover (c0274). zz-execute's line "Two machines work on different layers of the same raft" changes to this.
- **Except when the raft's CLI runs out of quota** (Q7). The worker waits a short limit for it, then continues on another CLI in a new session that reads the raft's notes, and the raft's context is lost from then on (c0253 owns the switch).
- **The stack lands as one bind** (Q4): one `--no-ff` merge of the top layer (#296's `./zn done`), with one full gate on that top. This replaces the captured "layers merge bottom-up, each retargeted to `main` as the one below merges".
- **A red or blocked layer stops the layers above it, not the ones below** (Q3). The green layers below a blocked one land now, as a shorter bind of the prefix with one full gate on its top green layer. The raft is blocked at that layer (c0250) and resumes there after the resolve. c0248 makes `./zn done` able to land that prefix; c0252 decides when it runs and with which credential.
- Each layer carries its ticket's change, specs, spend and review, and is gated on its own diff. `done` moves a ticket to `done/` in its own layer. The raft's PR record (Theme, Order) names the stack.
- A layer may still be built by streams, subagents of the worker committing on that layer (#296: commits on a layer, whoever made them, become its one commit).
- zz-rules, zz-execute, z-run, `./zn start` and `done`, the prompt template, the raft template and the README's Stacked delivery section say all of it. The README's Roadmap says again that c0248 to c0254 are one raft (Q8), the line c0264's prepared README rewords to "z-raft then groups them": whichever of c0248 and c0264 lands second makes it say so.

**R-vision stays one raft** (Q8): c0248, c0249, c0250, c0251, c0252, c0253 and c0254, in that order, delivered as such a stack, with c0248 its first layer. It starts only when every member's outside dependency is done: c0257, c0260, c0261, c0263, c0283 and the heartbeat raft (c0265, c0274, c0275, c0277).

#296 overtook the capture's Solution ideas: it chose `R0010/<n>/<issue>` over `R0010-<n>-<issue-slug>`, reads the stack from git instead of a layer-to-PR map in the raft folder, and replaced the Phase 2B stream branches with commits on the layer. The capture's "the README edit in `.worktree/docs-znile-vision` rides in this layer" already landed with R0085 (#246), and that worktree is gone. The user retired both at the confirmation (Q9).

Not here: how a single issue is designed or sized, the full-force review itself (c0262), the dispatcher's landing of a stack and its credential (c0252), the escalation of a blocked layer (c0250), and the switch to another CLI (c0253).
