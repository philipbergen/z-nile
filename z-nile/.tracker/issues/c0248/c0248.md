# c0248: Stacked PR delivery of a raft

## Problem
A raft is delivered today as one branch and one PR, however many issues it holds, so a reviewer, a revert and a failure all see the whole raft at once. The general model should be a **stacked PR set**: one layer per issue of the raft (a branch and a PR each), layer 1 on `main`, layer N on layer N-1, in the raft's Order (depends_on, then id). Each layer carries its issue's change, specs, spend and review; each is reviewed and gated on its own diff; layers merge bottom-up, each retargeted to `main` as the one below merges. A one-issue raft is a stack of one, so the model is general, not an exception. Streams (zz-execute Phase 2B) may still build a layer.

What should happen: zz-rules, zz-execute, z-run, `./zn start`/`done`, the prompt template and the raft template say it. The raft's own PR record (Theme, Order) names the stack; `done` moves an issue to `done/` in its own layer; a red or blocked layer stops the layers above it and not the ones below.

Part of the z-nile vision (z-nile/README.md, section How it should work). Layer 1 of the vision raft, which is itself delivered as a stacked PR set, c0248 to c0254 in that order. The README edit in `.worktree/docs-znile-vision` rides in this layer.

## Idea
A raft of several tickets is delivered as a **stacked PR set**: one layer per ticket, in the raft's Order (depends_on, then id), layer 1 on `main` and each next layer on the one below. A one-ticket raft is a stack of one. #296 (landed 2026-11-11, branch `cut-2.4-stack`) built most of the mechanics: a layer is a branch (`R0010/1/c0010`), one commit (`./zn finish`) and one draft PR on the layer below; each layer is code-reviewed on its own diff; `./zn restack` rebases the layers above a change; `./zn stack` reads the stack; `./zn done` lands it. c0248 keeps what #296 built and adds the rest:

- **Each ticket is worked to completion before the next one is picked up** (Q1). A layer is complete when it is built, reviewed, full-force reviewed (c0262) and green on top of the layer below. It is not merged. Only then does the next layer start.
- **One worker carries every layer, in order** (Q5), so its context remains from the first ticket to the last. The supervisor (c0253) runs the raft in one CLI session and resumes it for each layer (Q2, Q6). Two machines work on one raft only through a takeover (c0274). zz-execute's line "Two machines work on different layers of the same raft" changes to this.
- **Except when the raft's CLI runs out of quota** (Q7). The worker waits a short limit for it, then continues on another CLI in a new session that reads the raft's notes, and the raft's context is lost from then on (c0253 owns the switch).
- **The stack lands as one bind** (Q4): one `--no-ff` merge of the top layer (#296's `./zn done`), with one full gate on that top. This replaces the captured "layers merge bottom-up, each retargeted to `main` as the one below merges".
- **A red or blocked layer stops the layers above it, not the ones below** (Q3). The green layers below a blocked one land now, as a shorter bind of the prefix with one full gate on its top green layer. The raft is blocked at that layer (c0250) and resumes there after the resolve. c0248 makes `./zn done` able to land that prefix; c0252 decides when it runs and with which credential.
- Each layer carries its ticket's change, specs, spend and review, and is gated on its own diff. `done` moves a ticket to `done/` in its own layer. The raft's PR record (Theme, Order) names the stack.
- A layer may still be built by streams, subagents of the worker committing on that layer (#296: commits on a layer, whoever made them, become its one commit).
- zz-rules, zz-execute, z-run, `./zn start` and `done`, the prompt template, the raft template and the README's Stacked delivery section say all of it. ## Design
What #296 (`cut-2.4-stack`, landed 2026-11-11) and #297 (`zn-step-2-5`) already build, and c0248 keeps: a layer is a branch `R0010/<n>/<issue>`, an empty `tracker: start` commit, then one `<issue>: <title>` commit made by `./zn finish` (which runs the issue's `check.sh` and the specs the watch map selects for the layer's diff, writes `results.txt`, squashes and pushes); a draft PR per layer, based on the layer below; `./zn restack` and `./zn stack`; `./zn start` opens layer N+1 only when layer N is finished on the tip of N-1 (`layergit.startLayer`, layergit.luau:257-270), so one layer is open at a time; `./zn done` lands the whole stack with one `git merge --no-ff` of the top layer's tip (`<R>: bind <ids>`), after a final review and a checked trace, moving every member and the raft to `done/` in that bind commit, running the affected gate on the done tree and retargeting every layer's PR to `main` before the push.

What c0248 adds, by outcome. Decisions it relies on (quoted for z-raft): Q1 "Green on the layer below", Q3 "They merge now", Q4 "#296's one bind", Q5 "One worker, in order", Q8 "Keep one raft", and the prep decisions "When its layer lands", "Yes, every landing" and "Only at the last landing" (2026-11-12).

**1. A layer is complete before the next one starts** (Q1). Complete means finished (as today), green on top of the layer below (as today), and **reviewed**: its own code review, in its own folder, settled and current. c0262 adds the full-force review to the same rule later; c0248 makes the rule one pure function that c0262 extends.
- **Where a layer's review lives.** `review-NNN.md` and `refute-NNN.md` in the **issue's folder** (`<root>/issues/active/<id>/`), numbered from 001 per issue (the capture's "each layer carries its ticket's ... review"). The findings a layer's review leaves for the human go under `## Open to the human` in the **issue document**, and its harvest in the issue folder's `harvest.md` (`./zn lessons --uncovered <issue>` pairs that folder's reviews with that ledger). The final review's open list stays in the raft document.
- **The tool stamps the reviewed commit.** Within its first 12 lines a layer review or refute carries `Commit: <sha>` (the layer's finish commit) and `Patch: <id>` (`git patch-id --stable` of that commit). The reviewer never writes them: the dispatcher stamps a code review it files (outcome 8), and `./zn commit` stamps a `review-NNN.md` or `refute-NNN.md` it commits in an issue folder that has none, from the layer's finish commit at that moment, and refuses one when the layer is not finished.
- **The rule** (`completion.layer`, pure). Input: the layer's current finish sha and its patch id, the newest review's text, its refute's text (or nil), the issue document, and a lookup of backlog ids for deferred answers. The layer is complete when:
  1. a newest review exists and has a `Verdict:` line;
  2. every finding of it is answered by the same rules `done` applies to the final review (moved, not copied, from `main.luau`'s `reviewProblem`: an answer per finding, `fixed` needs `consequences:`, a high is never deferred, a refuted or unclosed high is under the issue document's `## Open to the human` with a `Ruled (user, …)` line); a review with `Verdict: approve` and no findings needs no refute;
  3. it is **current**: the review's `Commit:` is the finish sha, or its `Patch:` is the finish commit's patch id (a clean rebase keeps the patch, so a restack keeps the review); or, for the fix flow only, the review has findings, its refute answers at least one of them `fixed`, and the refute's stamped `Commit:` or `Patch:` matches the current finish. A refute never carries an approve with no findings, or a review whose answers are all `refuted` or `deferred`, to a changed patch.
  Any other outcome, including an unreadable file or a missing stamp, is "not complete" with a named reason (fail closed).
- **Where it is enforced.** `./zn start` refuses to open layer N+1 until layer N is complete: `"<id> is not complete: <reason>"`. `./zn done` refuses a bind any of whose layers, the top one included, is not complete.
- **Post-finish files.** `layergit.isPostFinishPath` and `trace.isTrackerFileOf` accept `review-NNN.md`, `refute-NNN.md` and `harvest.md` in the layer's own issue folder, and the raft folder's `spend.md` (which `./zn commit` rewrites on every commit), so committing a layer's review after its finish keeps the layer finished.

**2. One worker carries every layer, in order** (Q5). The code already opens one layer at a time. c0248 changes the text: zz-execute Phase 2B's "Two machines work on different layers of the same raft (`./zn stack <R-id>`)" becomes "One worker holds the raft and builds its layers one at a time, each complete before the next starts; a second machine works on the raft only through a takeover (c0274)"; streams stay subagents committing on the layer; the prompt template's "that work is another layer of this raft" becomes "that work runs as subagents committing on the layer you are on". The resumed session and the switch to another CLI on quota are c0253's.

**3. The stack lands as one bind** (Q4). Unchanged from #296; c0248 rewrites the README text that still says "layers merge bottom-up" and "today a raft is one branch and one PR".

**4. The green layers below a block land now** (Q3): **`./zn done <R-id> --through <issue>`**.
- **Which layers.** The bind lands the layers from the lowest one not yet landed up to and including `<issue>`'s; without `--through` it lands every layer not yet landed.
- **Each landing has its own final review and trace** ("Yes, every landing"). The final review of a landing is `final-review-NNN.md` and its trace `trace-NNN.md` (same NNN), both in the raft folder, committed on the landing's top layer after its finish. NNN is one more than the highest final review already on `origin/main`, so a landing's files never overwrite or stand in for an earlier landing's. `./zn trace <R-id> [--through <issue>]` prints the skeleton for exactly those layers, and `./zn trace <R-id> [--through <issue>] --check` checks the newest `trace-NNN.md` not yet on `origin/main`. The bind message's `Trace:` names that file, which no later bind changes. A raft with no cut-over marker (outcome 9) keeps #297's single `trace.md`.
- **The raft's checks on a landing.** `done` runs the raft's `check.sh` with `ZN_BIND_MEMBERS=<the landing's ids>`, and with `ZN_BIND_EARLY=1` when layers stay unlanded. `./zn members <R>` and `./zn promote-check <R>` print and check only `ZN_BIND_MEMBERS` when it is set (and refuse an id that is not a member), so RC0 runs the landing's own members' checks and promotion. On an early landing `ac.sh` skips the raft-wide lines `RC1` and up, printing `SKIP RCn: an early landing; it runs at the last landing` (the user's decision, "Only at the last landing"); the last landing runs them all. No raft `check.sh` is edited: the scoping is in what it calls.
- **What it does.** It promotes only the landing's members' acceptance specs and moves only them to `done/` ("When its layer lands"); the raft stays in `active/` until its last layer lands, then moves as today; the bind message lists only the landed ids, with the final review's `Verdict:` and `Trace:`, and its `Issue:` spend trailers list only those ids; it retargets the landed layers' PRs and the next layer's PR to `main`; it runs the affected gate on the done tree and pushes, rolling back as today.
- **The layers above a landing.** A layer whose issue is in `done/` **on `origin/main`** is landed (never read from the layer's own tree, which predates the landing). The lowest unlanded layer is treated exactly as layer 1: its base is `origin/main`. `restack` rebases its own commits (from its `tracker: start`) onto `origin/main` and the layers above it onto it; until then `./zn stack` shows it `claimed`, and `finish`, `done` and `trace` refuse it (`"<branch> is not based on main: ./zn restack <R>"`); `start` cuts a layer above landed ones from `origin/main` with its PR based on `main`. The rebase changes its finish sha but not its patch, so its review stays current (outcome 1, rule 3), and the second landing adds its own `final-review-NNN.md` and `trace-NNN.md` with no add/add conflict. `./zn stack` prints a landed layer as `landed`; `start` never reopens it; the count check is "one layer per member not yet landed", whether the landed branches were kept (GitHub's default) or deleted. Positions do not change.
- **Stopped and readied again.** `./zn stop` of a partly landed raft leaves its landed members in `done/` and gives back the rest (today it refuses a raft with a member in `done/`, which c0068's promoted stop spec pins: Overrides); `./zn ready` skips members in `done/` on `origin/main`, and `start` resumes above them at their positions.
- **When it runs.** c0248 provides the command; who runs it on a block (the dispatcher) is c0252's, and marking the raft `blocked` is c0250's.

**5. Each layer carries its ticket**: change, specs, spend rows and `results.txt` (as today), its review and harvest (outcome 1), and its move to `done/` in the bind that lands it (outcome 4).

**6. The raft's PR record names the stack.** Each layer's PR body holds `Raft **R0010**: <title>`, the raft's Theme (its first paragraph), its Order section, and a **Stack** table, one row per layer: position, issue, branch, PR, state (`landed`, `complete`, `finished`, `claimed`, `missing`), with this layer marked. A pure `stack.prBody(input): string` renders it; `start`, `finish`, `restack` and `done` rewrite it on every open layer PR of the raft with `gh pr edit <n> --body-file -`. A failed edit prints a warning and does not fail the command (the PR body is a view, not state).

**7. The documents say it.** zz-rules (the stack paragraph; the `start` row: the next layer waits until the one below is complete; the `done` row: `--through`, landed layers, the moves, `ZN_BIND_MEMBERS`; Merging: a layer's open list is the issue document's), zz-execute (Phase 2B; Phase 4 per layer, after the layer's finish and before the next `start`, dispatched with the issue id, files in the issue folder, stamped by the tool, open list and harvest in the issue's documents, `approve` with no findings goes to the next layer; Phase 5's final review and `done` per landing, `--through` below a block), zz-review (Output file: code mode in the issue's folder, final mode once per landing as `final-review-NNN.md` with `trace-NNN.md`; Code mode inputs: the layer's diff, with `Commit:` and `Patch:` stamped by the tool), z-run, the prompt template, the raft template's Order section (its order is the stack's), and the README: Stacked delivery rewritten to what is built and marked `*exists* (c0248)`, the Roadmap's c0248 row `exists`, and "c0248 to c0254 are one raft (R-vision), delivered as a stacked PR set in that order" (Q8) with no "bottom-up" left. Whichever of c0248 and c0264 lands second keeps that sentence; c0248's promoted docs spec pins it, so a later c0264 that drops it goes red.

**8. Reviews can be produced headless.**
- `./zn dispatch zz-review <issue-id> --mode code` (the layer's issue id, not the raft's) files the reviewer's `review.md` into the issue folder as the next `review-NNN.md`, stamped with `Commit:` and `Patch:` (`layergit.layerFinishSha` and `git patch-id --stable`), and refuses a layer that is not finished. The one-round rule holds per issue folder.
- `./zn dispatch zz-review <R-id> --mode final [--through <issue>]` passes `--through` into the prompt's `./zn trace`. The reviewer writes the filled trace beside `review.md` as `$ZN_DISPATCH_DIR/trace.md`; the dispatcher fetches `origin`, files both under one NNN as the next `final-review-NNN.md` and `trace-NNN.md`, and fails a final review that wrote no trace. Its one-round refusal counts only final reviews not yet on `origin/main`, so each landing gets exactly one.
- The dispatch prompts name the issue document for a layer review's `## Open to the human`.

**9. Cut-over for rafts in flight.** `./zn ready` writes `layers: reviewed` in the front matter of every raft it readies once c0248 is on `main`; the publish rule that a moved document may only change its status line (`publish.luau`) also accepts that line. `start`, `done`, `trace` and `restack` apply outcomes 1 and 4's per-landing files only to a raft that carries it. A raft readied before (in flight when c0248 lands: R0090, R0093, and R-vision itself, which is readied before its own first layer lands) keeps today's rule (finished layers, the raft-folder review, one `trace.md`, one landing), and a refusal names the rule that applies. A stopped raft keeps its marker when readied again.

### Scalability
A raft has at most a handful of layers. The completion check reads three small files per layer and runs one `git patch-id` per layer, once per `start` and once per layer at `done`; the PR body refresh is one `gh pr edit` per open layer PR, only on commands that already call `gh`. A restack after `main` moves no longer forces new reviews (the patch rule). c0248's own `check.sh` runs only fast specs (AC15), so the R-vision layers above it do not pay for the slow tier at every finish and restack.

### Maintainability
One rule, one place: the review-answer rules move from `main.luau` to the pure `completion.luau`, used by the final review and the layer review, and c0262 extends `completion.layer` instead of adding a gate. The tool, not the author, stamps what a review vouches for. The early landing reuses `done`'s path with a member subset, and the raft's checks are scoped through the commands it calls, so no sequestered raft `check.sh` changes. Old rafts keep today's rule through one marker.

### Usability
A refusal names the layer and the missing piece (`c0010 is not complete: review-001.md reviewed 9b8e7f0 (patch 4c1d…), the layer is at a2f3c1d (patch 7e02…): the change differs, so answer it in refute-001.md with a fixed finding or review again`). `./zn stack` shows `landed` and `complete`. `done --through` is one flag on the command people already run; its refusals use today's wording with the layer named; a skipped raft-wide check says when it will run.
