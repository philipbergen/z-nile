# c0248: Stacked PR delivery of a raft

## Problem
A raft is delivered today as one branch and one PR, however many issues it holds, so a reviewer, a revert and a failure all see the whole raft at once. The general model should be a **stacked PR set**: one layer per issue of the raft (a branch and a PR each), layer 1 on `main`, layer N on layer N-1, in the raft's Order (depends_on, then id). Each layer carries its issue's change, specs, spend and review; each is reviewed and gated on its own diff; layers merge bottom-up, each retargeted to `main` as the one below merges. A one-issue raft is a stack of one, so the model is general, not an exception. Streams (zz-execute Phase 2B) may still build a layer.

What should happen: zz-rules, zz-execute, z-run, `./zn start`/`done`, the prompt template and the raft template say it. The raft's own PR record (Theme, Order) names the stack; `done` moves an issue to `done/` in its own layer; a red or blocked layer stops the layers above it and not the ones below.

Part of the z-nile vision (z-nile/README.md, section How it should work). Layer 1 of the vision raft, which is itself delivered as a stacked PR set, c0248 to c0254 in that order. The README edit in `.worktree/docs-znile-vision` rides in this layer.

## Idea
A raft of several tickets is delivered as a **stacked PR set**: one layer per ticket, in the raft's Order (depends_on, then id), layer 1 on `main` and each next layer on the one below. A one-ticket raft is a stack of one. #296 (landed 2026-11-11, branch `cut-2.4-stack`) built most of the mechanics: a layer is a branch (`R0010/1/c0010`), one commit (`./zn finish`) and one draft PR on the layer below; each layer is code-reviewed on its own diff; `./zn restack` rebases the layers above a change; `./zn stack` reads the stack; `./zn done` lands it. c0248 keeps what #296 built and adds the rest:

- **Each ticket is worked to completion before the next one is picked up** (Q1). A layer is complete when it is built, reviewed, full-force reviewed (c0262) and green on top of the layer below. It is not merged. Only then does the next layer start.
- **One worker carries every layer, in order** (Q5), so its context remains from the first ticket to the last. The supervisor (c0253) runs the raft in one CLI session and resumes it for each layer (Q2, Q6). Two machines work on one raft only through a takeover (c0274). zz-execute's line "Two machines work on different layers of the same raft" changes to this.
- **Except when the raft's CLI runs out of quota** (Q7). The worker waits a short limit for it, then continues on another CLI in a new session that reads the raft's notes, and the raft's context is lost from then on (c0253 owns the switch).
- **The stack lands as one bind** (Q4): one `--no-ff` merge of the top layer (#296's `./zn done`), with one full gate on that top. This replaces the captured "layers merge bottom-up, each retargeted to `main` as the one below merges".
- **A red or blocked layer stops the layers above it, not the ones below** (Q3). The green layers below a blocked one land now, as a shorter bind of the prefix with one full gate on its top green layer. The raft is blocked at that layer (c0250) and resumes there after the resolve. c0248 makes `./zn done` able to land that prefix; c0252 decides when it runs and with which credential.
- Each layer carries its ticket's change, specs, spend and review, and is gated on its own diff. `done` moves a ticket to `done/` in its own layer. The raft's PR record (Theme, Order) names the stack.
- A layer may still be built by streams, subagents of the worker committing on that layer (#296: commits on a layer, whoever made them, become its one commit).
- zz-rules, zz-execute, z-run, `./zn start` and `done`, the prompt template, the raft template and the README's Stacked delivery section say all of it. The README's Roadmap says again that c0248 to c0254 are one raft (Q8), the line c0264's prepared README rewords to "z-raft then groups them": whichever of c0248 and c0264 lands second makes it say so.

**R-vision stays one raft** (Q8): c0248, c0249, c0250, c0251, c0252, c0253 and c0254, in that order, delivered as such a stack, with c0248 its first layer. It starts only when every member's outside dependency is done: c0257, c0260, c0261, c0263, c0283 and the heartbeat raft (c0265, c0274, c0275, c0277).

#296 overtook the capture's Solution ideas: it chose `R0010/<n>/<issue>` over `R0010-<n>-<issue-slug>`, reads the stack from git instead of a layer-to-PR map in the raft folder, and replaced the Phase 2B stream branches with commits on the layer. ## Design
What #296 (`cut-2.4-stack`, landed 2026-11-11) and #297 (`zn-step-2-5`) already build, and c0248 keeps: a layer is a branch `R0010/<n>/<issue>`, an empty `tracker: start` commit, then one `<issue>: <title>` commit made by `./zn finish` (which runs the issue's `check.sh` and the specs the watch map selects for the layer's diff, writes `results.txt`, squashes and pushes); a draft PR per layer, based on the layer below; `./zn restack` and `./zn stack`; `./zn start` opens layer N+1 only when layer N is finished on the tip of N-1 (`layergit.startLayer`), so one layer is open at a time; `./zn done` lands the whole stack with one `git merge --no-ff` of the top layer's tip (`<R>: bind <ids>`), after a final review and a checked trace, moving every member and the raft to `done/` in that bind commit, running the affected gate on the done tree and retargeting every layer's PR to `main` before the push.

- **The tool stamps the reviewed commit.** Within its first 12 lines a layer review or refute carries `Commit: <sha>` (the layer's finish commit) and `Patch: <id>` (`git patch-id --stable` of that commit). The reviewer never writes them, and nobody else does: the dispatcher stamps a code review it files (outcome 8) with the finish commit it gave the reviewer, and `./zn commit` stamps a `review-NNN.md` or `refute-NNN.md` it commits in the layer's issue folder from the layer's finish commit, and refuses one when the layer is not finished. A committed round is never deleted or renamed through `./zn commit`, and a round the layer's history had and HEAD lacks (deleted by a plain `git commit`) comes back only as it was: its restore (the very text the deleting commit removed) is committed, and any other file of that number is refused, naming the restore ("restore it with git checkout <sha>^ -- <path>"), so no finding vanishes behind a fresh file of the same number. A stamp already on a new file is accepted only when it is true, a commit's own: its `Commit:` names a commit whose patch id is its `Patch:` (what the dispatcher writes for the finish it gave the reviewer, or a retried commit wrote); such a file is committed as it is, needs no `Inputs:` check (the tool vouched for it when it stamped it), and `completion.layer` then judges it current (the finish's patch, a clean restack between the dispatch and the commit included) or a stale round that is answered and followed by the next round. Any other stamp is refused ("no commit's own stamp: the tool stamps it; remove the line"). `./zn commit` checks its arguments and every new review and refute before it writes any stamp, so a command run again after a commit that failed once the files were stamped (and staged) finds that true stamp and goes on, and the `./zn commit … --phase code-review` zz-execute Phase 4 step 3 gives commits a dispatched round as it is. - **The rule** (`completion.layer`, pure). Input: the layer's current finish sha and its patch id, the newest review's text, its refute's text (or nil), the issue document, and a lookup of backlog ids for deferred answers. The layer is complete when:
  1. a newest review exists and has a `Verdict:` line;
  2. every finding of it is answered by the same rules `done` applies to the final review (moved, not copied, from `main.luau`'s `reviewProblem`: an answer per finding, `fixed` needs `consequences:`, a high is never deferred, a refuted or unclosed high is under the issue document's `## Open to the human` with a `Ruled (user, …)` line); a review with `Verdict: approve` and no findings needs no refute;
  3. it is **current** (`completion.current`, exported so f0417's `roundread.current` reads the stamps through it): the review's `Commit:` is the finish sha, or its `Patch:` is the finish commit's patch id (a clean rebase keeps the patch, so a restack keeps the review); or, for the fix flow only, the review has findings, its refute answers at least one of them `fixed`, and the refute's stamped `Commit:` or `Patch:` matches the current finish. A refute never carries an approve with no findings, or a review whose answers are all `refuted` or `deferred`, to a changed patch.

### Scalability
A raft has at most a handful of layers. The completion check reads three small files per layer and runs one `git patch-id` per layer, once per `start`, once per layer at `done`, and once per finished layer of each active marked raft in `./zn work next` (a handful of git calls per raft, the same order as `workread`'s existing per-layer `rev-list`); the fork is one `git merge-base` per lowest layer (d0331's cost). The PR body refresh is one `gh pr edit` per open layer PR, only on commands that already call `gh`. A landing no longer forces a restack, and a restack after `main` moves no longer forces new reviews (the patch rule). c0248's own `check.sh` runs only fast specs (AC15), so the layers above it do not pay for the slow tier at every finish and restack.

### Maintainability
One rule, one place: the review-answer rules move from `main.luau` to the pure `completion.luau`, used by the final review, the layer review and `work next`, and c0262 and f0417 extend `completion.layer`'s input instead of adding a gate. The lowest-layer rule is one function (`layergit.baseOf`) that every command calls, and it is d0331's fork. The tool, not the author, stamps what a review vouches for. The early landing reuses `done`'s path (and d0331's retry loop) with a member subset, and the raft's checks are scoped through the commands it calls, so no sequestered raft `check.sh` changes. Old rafts keep today's rule through one marker. `main.luau`'s new helpers live in one table, so the six layers above c0248 have room under the local limit.

### Usability
A refusal names the layer and the missing piece (`c0010 is not complete: review-001.md reviewed 9b8e7f0 (patch 4c1d…), the layer is at a2f3c1d (patch 7e02…): the change differs, so answer it in refute-001.md with a fixed finding or review again`). `./zn stack` shows `landed` and `complete`; `./zn work next` names the layer to review and the landing's trace file. `done --through` is one flag on the command people already run; its refusals use today's wording with the layer named; a skipped raft-wide check says when it will run; an unmarked raft's refusal of `--through` says it lands whole.
