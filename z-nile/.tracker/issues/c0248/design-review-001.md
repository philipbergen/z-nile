### F4 [high] Every restack makes every layer review above it stale, and the tools leave no allowed way back
Where: Design outcome 1, rule 3 "the review is current: its `Commit:` is the layer's finish sha, or its refute's `Commit:` is" (c0248.md:181); Usability's refusal text "(re-review, or answer it in refute-001.md ...)" (c0248.md:229); zz-execute Phase 5 step 2 ("If `main` moved, `./zn restack <R-id>` ... so the stack is on that main before `done`") and the final-review step ("if a fix changes a layer, `./zn finish` and `./zn restack`"); dispatcher.luau:1203-1215; zz-review "A second review of the same kind is refused" (line 24) and "Never edit a review once it is written".
Evidence: `done` fetches and then requires layer 1 to be stacked on origin/main's tip (prototype `baseFor` → `baseOf(1)` = `mainTip()` = origin/main; `is-ancestor(onto, tip)` or "not stacked ... ./zn restack"). In this repository main moves with every tracker commit (13 commits between the prototype's base and now), so nearly every `done` is preceded by a restack. A restack rebases every layer, so every finish sha changes and every layer becomes "not complete". The design never mentions restack. The ways back it offers are blocked: a second dispatched code review in the same folder is refused ("already has review-001.md: one round ... there is no second round"), and editing review-001.md breaks zz-review's rule. The prototype's fixtures take that forbidden path: stack-land.spec adds `seal.layerReview(wt, "c0020") -- the restack rewrote the layer, so its review names the new finish commit`, which overwrites review-001.md, and E1 and layers-land rewrite review-001.md too. The remaining path is an author-written refute per layer. Each refute commit moves that layer's tip, which un-stacks every layer above it, so this takes N refutes and N restacks bottom-up, and it starts again whenever main moves before `done`.
Critique: this turns a pure rebase into N rounds of paperwork that certify nothing, since the author writes the carrying line. The tempting fix (accept any review whose `Commit:` is an ancestor) is wrong after a rebase, because old shas are not ancestors.
Consequences: identity has to be judged by the layer's own change. `git patch-id --stable` of the finish commit is stable across a clean rebase and changes when a conflict resolution or a fix changes the patch. The old commit object is gone in other clones after a force-push, so the patch id must be recorded at review time, not recomputed from the old sha. That needs a writer the author does not control: the dispatcher already moves `review.md` into place and can stamp the header.
Recommendation: define "current" as: the review's `Commit:` is the finish sha, or its `Patch:` (the finish commit's `git patch-id --stable`, stamped by the tool when the review is filed: the dispatcher on `--mode code`, and `./zn commit` for a review file in the interactive path) equals the current finish commit's patch id. Keep the refute carry only for the fix flow (F8). Say in zz-execute that a restack keeps reviews whose patch is unchanged, and that a changed patch needs the refute of the fix flow. Spec cases: main moves, `restack`, `done` lands with no new review files; a restack whose conflict resolution changes layer 2's patch leaves layer 2 not complete, naming both shas; a `Patch:` of another change is not complete; no `Patch:` falls back to sha equality. Remove the review-rewriting from the stack-land, E1 and layers-land fixtures.
Lesson: new candidate below (rules keyed to a sha)

## Candidate lessons (for the lead to write; I write no lesson files)
- z-design, "scenario specs follow the decided order": when a user decision fixes an order of events (the next layer exists and blocks, then the green layers below it land), does each scenario spec run that order rather than a reordering that is easier to set up, and is every reordering justified? Because c0248's AC7 sealed layer 2 before cutting layer 3, the only order that hides the second bind's add/add conflict.
- z-design, "rules keyed to a sha": for every rule that names a commit (a review's `Commit:`, a trace's `Commit:`), which commands rewrite that sha (restack, re-finish, a rebase onto a moved main), how often does that happen in this repository, and what way back do the existing tools allow (one-round refusals, never-edit rules)? Because c0248's currency rule made every restack invalidate every layer review, with no allowed re-review.
- z-design, "fixtures that stand in for a template render the template": when a command runs a file every item gets from a template (a raft's check.sh), does the spec's fixture use the rendered template rather than `true`? Because c0248's `done --through` passed with a trivial raft check.sh but cannot pass with the real one.
