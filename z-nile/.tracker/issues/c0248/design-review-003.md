### F1 [high] A layer whose patch changes after its review is settled can never be complete again on the headless path, and the skills forbid the interactive way back

The same happens to an approve with no findings that a conflicting restack changes, the AC5 case: rule 3 forbids a refute to carry it. Only the sequestered fixture reaches `complete` again, and it does so by writing `review-002.md` with `git` (AC5 "the tool-stamped review-002 settles it"), a path no skill or command offers. f0417 later files "a rebuilt layer's next round" through its `stale` input, but only for a raft with `Rounds: on`, and f0417 is readied only after R0093 lands. ### F2 [medium] The "tool's" stamp can be written by anyone and is taken from the finish at commit time, not from the commit the reviewer read
Where: c0248.md outcome 1 ("The reviewer never writes them … `./zn commit` stamps … from the layer's finish commit at that moment"), Maintainability ("The tool, not the author, stamps what a review vouches for"); prototype `completion.stamp` ("A text that already carries a line keeps it") and `layergit.stampLayerReviews`; sequestered `layers-land.spec` AC4 ("a file that already carries a stamp keeps it", lines 420-427); `tests/lib/seal.luau:309` (`seal.layerReview` writes `Commit: {sha}` by hand).
Evidence: (1) A review or refute that already holds a `Commit:` and `Patch:` line in its first 12 lines is committed as written. The sequestered AC4 case requires this, so the design text "a reviewer never writes them" is contradicted by its own contract. A refute hand-stamped with the current finish carries a `fixed` answer to any patch. (2) In the session path the stamp is the layer's finish when `./zn commit` runs. Suppose the reviewer approves finish X, then the worker changes the layer (a gate fix) and re-finishes to Y before committing the review. `./zn commit` refuses while the layer is unfinished, and after the re-finish it stamps Y. An approve of X then reads as current for Y, which nobody reviewed. The dispatched path is right: it stamps the sha it computed before the reviewer ran.
Critique: The stamp exists so that completion is vouched for by someone other than the author (review 001 F4's "a writer the author does not control"). As specified, the author controls both what the stamp says and when it is taken. The tempting fix is to overwrite any existing stamp. That closes (1) but not (2), and it would rewrite a refute's stamp on every recommit.
Consequences: The session path needs a record of what the reviewer was given. zz-review's format already asks for `Inputs: <commit sha / files reviewed>`, so the stamp can be checked against it. The `Inputs:` line then becomes load-bearing for a layer review. A short sha (seven or more characters) must match the finish, or have the finish's patch id when the object exists (a clean restack between the review and the commit). Anything else is refused, naming both. `seal.layerReview` and the AC4 case change in prep (a hand stamp is refused). The fixtures that build stale reviews (`staleReview`, AC5's `review-002.md`) go through a seal helper that commits with `git`, which the rule cannot see and which stays a fixture-only path.
Recommendation: In outcome 1, say that `./zn commit` and the dispatcher refuse a new layer review or refute that already holds `Commit:` or `Patch:` ("the tool stamps it: remove the line"). Say also that `./zn commit` stamps a session review only when its `Inputs:` line names the finish commit (or one with the same patch id), and otherwise refuses, naming both shas ("commit the review before re-finishing, or review again"). Change AC4's "keeps it" assertion to the refusal, and add a case with an `Inputs:` sha that is older than the finish. Add Rules rows (mutants: the existing stamp kept; `Inputs:` ignored). Pin the zz-review sentence that a code-mode `Inputs:` names the layer's finish commit.
