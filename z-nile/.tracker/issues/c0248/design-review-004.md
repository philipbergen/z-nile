### F1 [high] The next-round rule files a second review while the newest round's findings are still unanswered, so a worker can replace a refute (and the human's ruling) with another reviewer
Where: c0248.md outcome 1 "The way back after a change" ("`dispatch.filing` files the next round only while the folder's newest round is not current for the layer's finish … and refuses 'one round' while it is current") and outcome 8; prototype `dispatcher.modelStep` (computes `current = completion.current(review, refute-or-nil, stampSha, stampPatch)` for the newest round), `dispatch.filing` (`if last >= 1 and p.current == false then return { number = last + 1 }`), `completion.current`; `work.luau:343` ("run its code review … or answer the open one, until it is complete"); zz-execute Phase 4 step 6 as prototyped ("run only when a fix changed the layer's patch after its newest round was **settled**"); dispatch-review.spec AC10 code case.
Evidence: The ordinary Phase 4 flow on a marked raft: `review-001.md` has F1 [high], stamped with finish X. The worker commits a fix and re-finishes to Y, then, instead of writing `refute-001.md`, runs `./zn dispatch zz-review c0020 --mode code` again (`work next` offers exactly that: "run its code review … or answer the open one"). The dispatcher reads review-001 and no refute: `completion.current` is false (stamp X is not Y, and `fixedAnswers(nil)` is 0), so `current = false` and `filing` returns `last + 1`. `review-002.md` is filed, stamped Y. If it approves, `completion.layer` reads the newest round only, and the layer is complete: review-001's high finding was never answered, never went under `## Open to the human`, and the refusal text the same function still prints ("one round, then the author answers it") is false. Review 003 F1's Consequences named the guard ("refuses only while the newest round is current, **or has unanswered findings**"); the design and the prototype kept only the first half. The prototype's zz-execute says "settled", the design says only "not current", and AC10's code case starts from an approved round, so neither mutant row (`filing-ignores-current`, `filing-always-next`) nor any case can tell the two apart.
Critique: c0248 turns the one tool-enforced round of today (a second dispatch is always refused) into a round the worker can reopen at will by changing the patch, which every fix does. That is the authority hole lesson z-work/answered-review-is-not-reviewed-again names from the other side: a second reviewer started to flip a verdict. The tempting fix is to have `current` include "settled" inside `completion.current`, but `completion.current` is also rule 3 of `completion.layer` and f0417's `roundread.current`; changing its meaning moves completion too.
Consequences: The dispatcher needs a second fact: whether the newest round is answered. `completion.reviewProblem(review, refute, doc, {kind = "layer"})` already says it, but it also waits for a human ruling on a refuted or unclosed high finding; requiring that before a next round would make a final-review fix wait on the human. So "answered" should mean what `reviewProblem` checks before the open-list gap: an approve, or every finding with an answer line in the refute. The refusal then needs its own words ("answer review-001.md in refute-001.md first"), so the "one round" refusal stays for a current round. f0417's `stale` input meets the same question, and the interface bullet to f0417 must carry it.
Recommendation: State in outcome 1 and outcome 8 that the next round is filed only when the newest round is answered (approve, or a refute line for every finding) **and** not current; the dispatcher computes both (`FilingInput.current` stays the "current" fact, plus `answered: boolean?`, or one `next: boolean?` it computes from both), with a refusal naming the refute to write. Make `work.luau`'s review action say "answer review-NNN.md" when the newest round has unanswered findings, and "run the layer's next review round" only when it is answered and not current. Add to AC10's code case, before the approved-round path: a review with one finding, a fix and re-finish without a refute, and a dispatch refused with the answer-first words and no `review-002.md`. Add a Rules row "a next round needs the newest one answered" with the mutant "filing ignores answered", killed by that step, and send f0417's prep the rule for its `stale` input.

### F2 [medium] "The tool stamps, never the author" holds only for a new file on a first, clean `./zn commit`: an edited committed stamp is committed unchecked, and a failed commit leaves a stamp that the retry refuses
Where: c0248.md outcome 1 ("Both refuse a review or refute that already carries a `Commit:` or `Patch:` line"); prototype `layergit.stampLayerReviews` (walks only `?? ` untracked paths, and writes each stamp to disk inside the loop) and `cmd.commit` (calls `stampLayerReviews()` before its `--phase`, `--tokens`/`--time` refusals and before `git commit`, whose failure restores only the cost rows); layers-land.spec AC4.
Evidence: (a) After a final-review fix re-finishes layer 2 to Z, `start`/`done` refuse "review-001.md is not current". Editing the committed `review-001.md`'s `Commit:` line to Z and running `./zn commit` commits it: the file is ` M`, not `??`, so `stampLayerReviews` never reads it, and `completion.current` now reads the approve of Y as current for Z. The same holds for a committed refute. (b) A worker with a new `review-002.md` runs `./zn commit -m … --phase prep` (or any argument `cmd.commit` refuses after the stamp, or a commit that fails): the stamp is already written, the commit is refused, and the retry is refused "review-002.md already carries a Commit: or Patch: line: the tool stamps it; remove the line". The same when a new refute is stamped first and a new review later in the same loop fails its `Inputs:` check. The only way out the tool prints is deleting stamp lines by hand, which is the act the rule exists to forbid.
Critique: Refute 003 F2 answered "hand stamps refused", and AC4 pins only the new-file, first-attempt case. The tempting fix for (b) is to let a stamp that equals the current finish through, which reopens (a) for new files.
Consequences: Checking every file first and writing stamps only after `cmd.commit`'s own refusals (just before `git add`) closes (b); a failed `git commit` must then put the files back as they were (as it does the cost rows). For (a), a committed layer review or refute is never edited (zz-review: "a file is never edited after you hand it back"), so `./zn commit` can refuse any staged or unstaged change to a tracked `review-NNN.md` or `refute-NNN.md` in the layer's issue folder. A fixture that needs to rewrite one keeps committing with `git`, as the stale fixtures already do.
Recommendation: In outcome 1, say that `./zn commit` refuses a change to a committed layer review or refute ("a review is never edited; the next round is a new file"), and that it checks every new file before it writes any stamp and stamps only after its own argument checks, restoring the files if the commit fails. Add to AC4: an edited committed `review-001.md` (its `Commit:` changed) is refused; `./zn commit --phase prep` with a new review is refused and leaves the file without a stamp, and the retry with good arguments stamps it. Add Rules rows for both (mutants: tracked files not checked; stamp written before the argument checks).
