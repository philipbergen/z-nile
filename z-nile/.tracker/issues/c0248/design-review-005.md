### F1 [high] A committed refute can never be corrected, yet its answers are checked only after it is committed: a refute `done` rejects leaves the layer incomplete with no way out through the tool
Where: c0248.md outcome 1 ("A review or refute already committed is never rewritten: `./zn commit` refuses a change to one ('a later answer or review is the next round's file')"); prototype `layergit.stampLayerReviews` (`if code ~= "??" then fail("… is committed: a review round is never rewritten …")`, for `refute-NNN.md` as well as `review-NNN.md`); zz-execute Phase 4 step 4 ("`./zn done` refuses a fixed answer without `consequences:`") and step 5 ("Then commit the refute file"); `completion.reviewProblem` (missing answers, a fixed answer without `consequences:`, a bad `deferred` line).
Evidence: The ordinary Phase 4 order is: commit the fixes, commit `refute-001.md`, and later `./zn start`/`./zn done` read it with `reviewProblem`. Nothing checks the refute's answers when `./zn commit` stamps it: only reviews get the `Inputs:` check. So a refute with `- F2: fixed abc1234: renamed it` (no `consequences:`), or one that leaves a finding out, is stamped and committed. `start` then refuses "refute-001.md: F2: a fixed answer needs \"; consequences: …\"", and the author's fix, editing `refute-001.md`, is refused by `./zn commit` ("is committed: a review round is never rewritten"). The way out the refusal names, "a later answer or review is the next round's file", is refused too: `dispatch.filing` refuses a next round while the round is current, and (refute 004 F1) while it is not answered. The layer cannot become complete, and `start` of the next layer and `done` wait on it forever, unless the author commits with plain `git` around the tool. Round 004 F2 recommended refusing any change to a committed review **or refute**; the refute half was not thought one step further, and refute 004's "a refute is answered once, as zz-execute already says" has no such sentence in zz-execute, which expects `done`'s refusal to be answered by fixing the refute.
Critique: The stamp is what F2(a) had to protect (an edited `Commit:` line that makes a stale approve current). A refute's answer lines are not the stamp, and they are exactly what `done` asks the author to fix.
Consequences: Either `./zn commit` refuses a defective refute before it is ever committed (the answer checks of `reviewProblem`, without the open-list gap, with the `backlog` predicate), which makes "answered once" true; or a committed refute may change only in lines other than `Commit:`/`Patch:` (compared with `HEAD`'s copy), and is then re-checked. The first keeps the rule simple and moves `done`'s refusal to the commit, where it can still be fixed; a partial refute (some findings answered) is then refused at commit, which zz-execute step 5's "then commit the refute file" already implies.
Recommendation: In outcome 1, say that `./zn commit` checks a new `refute-NNN.md` with `completion.reviewProblem`'s answer checks (every finding answered, `consequences:` on each fixed answer, `deferred` only for a medium or low finding to a backlog issue; not the open-list gap) before stamping it, and refuses it with `reviewProblem`'s words, so a committed refute is always answered and the "never rewritten" rule leaves no dead end. Add to AC4: a refute with a fixed answer lacking `consequences:` is refused by `./zn commit` and left unstamped, and the corrected refute is stamped. Add a Rules row with the mutant "refute answers not checked at commit". Correct refute 004's claim about zz-execute, or add the sentence to zz-execute Phase 4 step 5.

### F2 [high] The dispatcher reads `unanswered` without the backlog predicate, so any round whose refute defers a finding is never answered and its next round is refused for good; no case drives the dispatcher's computation
Where: prototype `dispatcher.modelStep`'s `filingNow` (`completion.reviewProblem(review, refuteText, doc, { kind = "layer", reviewName = …, refuteName = … })`, no `backlog`); `completion.reviewProblem` (`elseif not (opts.backlog ~= nil and opts.backlog(target)) then table.insert(invalid, "{id}: {target} is not a backlog issue")`); `main.luau`'s `H.reviewProblem` and `layergit.luau:474`, which pass `backlog`; c0248.md outcome 1 ("by `done`'s rules"); dispatch-review.spec AC10 code case (pure `dispatch.filing` assertions only); Rules row "a layer's next round waits for the newest to be answered".
Evidence: Layer c0010's `review-001.md` has F2 [medium], answered `- F2: deferred c0123: later` with c0123 in the backlog: `done` and `start` accept it. A final review's fix re-finishes the layer, so round 001 is not current. `./zn dispatch zz-review c0010 --mode code` computes `unanswered = "refute-001.md: F2: c0123 is not a backlog issue"` (with `backlog` nil every deferred line is invalid) and `filing` refuses "… is not answered (…): answer it in its refute before another round". The refute cannot be edited (F1), and the answer is valid. The layer can never be reviewed again, so it never becomes complete and the landing waits. The AC10 additions call `dispatch.filing` with a hand-made `unanswered`, and the e2e path starts from an approved round, so neither this bug nor a mutant that drops `unanswered = completion.reviewProblem(…)` from the dispatcher (passing nil) fails any case. Round 004 F1 asked for the e2e step (a review with a finding, a fix and re-finish without a refute, a refused dispatch and no `review-002.md`); refute 004 replaced it with the pure call.
Critique: "By the rule `done` and `start` apply" is the design's claim; the call differs from both in the one argument that judges a deferral.
Consequences: Passing `backlog` makes the dispatcher's reading the same as `start`'s; the issue document is already read there, and the store is available in `modelStep`.
Recommendation: Pass the same `backlog` predicate `H.reviewProblem` uses (or call one shared helper that both use, so they cannot diverge). Add to AC10's code case, through the dispatcher: a round with a finding and no refute, the layer re-finished, a dispatch refused with "is not answered" and no `review-002.md` filed; then a refute deferring a medium finding to a backlog issue, and the dispatch files `review-002.md`. Add Rules rows for "the dispatcher computes `unanswered`" (mutant: `unanswered` left nil) and "a deferred answer counts as answered" (mutant: `backlog` not passed), both killed by those steps.

### F3 [medium] "Puts the files back … so the same command can run again" fails for every failure after `recordAndCommit`'s `git add -A`: the stamped file stays staged and the retry is refused as "committed"
Where: c0248.md outcome 1 ("puts the files back as written when the commit does not happen (`layergit.unstamp`), so the same command can run again"); prototype `cmd.commit` (`pcall(recordAndCommit, …)`, then `layergit.unstamp`), `recordAndCommit` (`sh.git({ "add", "-A" })` before `store.get(id)` of each `--issue`, `fail("could not write the measured row")` and `git commit`), `main.luau`'s `fail` (`process.exit(1)`, which `pcall` never sees), `stampLayerReviews` (`code ~= "??"` means committed); Rules row "a failed commit puts the stamped files back" (reasoned: "not reachable from a fixture without a broken git").
Evidence: `./zn commit -m … --issue c9999` with a new `review-002.md`: the stamp is written, `git add -A` stages it, `store.get("c9999")` errors, `pcall` catches it and `unstamp` rewrites the working file without the stamp. The index still holds the stamped copy, so `git status` shows `AM`, and the corrected retry is refused "review-002.md is committed: a review round is never rewritten" (it never was). A failing commit hook reaches the same state. `fail` paths inside `recordAndCommit` (unmerged paths, the measured row) exit the process, so `unstamp` never runs and the retry is refused "already carries a Commit: or Patch: line". A worker who ran `git add` on a new review before `./zn commit` (status `A `) is refused the same false way. The reasoned row's premise is wrong: `--issue c9999` reaches the path in a plain fixture.
Critique: This is F2(b) of round 004 again, one layer down: the refusal names a state that is not true and a way out that does not exist.
Consequences: Deciding "committed" by whether the path exists in `HEAD` (`git cat-file -e HEAD:<path>`) fixes the false refusals for staged new files; `unstamp` must also put the index back (`git reset -q -- <paths>`) so the retry sees `??` or `A ` without a stamp; `fail`-style exits after the stamp need `unstamp` before them, or the stamp written after them.
Recommendation: In `stampLayerReviews`, treat a path as committed only when `HEAD` has it; in `cmd.commit`, have `unstamp` restore the index as well as the files, and keep every `process.exit` refusal of `recordAndCommit` before the stamp or behind the restore. Turn the reasoned row into a run row: AC4 runs `./zn commit -m … --issue c9999` with a new review, expects the refusal, the file unstamped and `git status` showing it untracked, then the corrected command stamps and commits it.
