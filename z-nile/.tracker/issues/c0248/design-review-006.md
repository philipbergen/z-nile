### F1 [high] A dispatched layer review cannot be committed the way zz-execute says: `./zn commit` runs the `Inputs:` check on it, and the dispatcher neither gives the reviewer the finish commit nor checks that the review names it
Where: zz-execute Phase 4 step 2 (`./zn dispatch zz-review <issue-id> --mode code` "prints the `./zn commit … --phase code-review --model <id>` line for step 3 (a headless run always uses it)") and step 3 ("you commit it on the layer: `./zn commit -m "c0010: review-NNN" --phase code-review --model <reviewer model>`"); prototype `layergit.stampLayerReviews` (every new `review-` file goes through `completion.reviewedShas` and is refused "names no commit on its Inputs: line that is the layer's finish … commit the review before re-finishing, or review again"); `dispatch.luau`'s code-mode prompt (tells the reviewer only that "the dispatcher numbers it, stamps it with the layer's `Commit:` and `Patch:`"; no finish sha); `dispatcher.luau`'s filing (checks `completion.hasStamp`, never the `Inputs:` line); c0248.md outcome 1 ("A review committed by `./zn commit` must name the commit it read on its `Inputs:` line"); dispatch-review.spec AC10 (the fake reviewer writes `# Review\n\nVerdict: approve` or one finding, no `Inputs:` line, and every dispatched round is committed with plain `git commit`, lines 200, 224 and `commitFolder`).
Evidence: The dispatcher files `review-001.md` stamped with the finish, untracked in the issue folder. Step 3's `./zn commit … --phase code-review` reaches `stampLayerReviews`: the file is not in `HEAD`, so it is new; its stamp equals the finish, so this round's own-stamp rule lets it through; then the review check finds no hex word on `Inputs:` (the fake reviewer's, or a real one that writes zz-review's own `git diff <layer below>...HEAD`) and refuses it. Even a reviewer that names `git rev-parse HEAD` fails from the second round on: in AC10's round 4, `HEAD` is the `refute-003.md` commit made after the finish, whose patch id is not the finish's. The refusal's ways out do not work: the review was not stale, and "review again" is refused "one round" (the filed file is the folder's newest round and is current). Before this round the same commit was refused outright as hand-stamped, so the step 3 path has never been run by any case; this round's F3 answer redefined what `./zn commit` accepts on a stamped new file without trying the file the dispatcher stamps.
Critique: Outcome 1 has two writers of a review's stamp and one check of what the review read, applied only at the second one; the dispatched path inherits the session path's check without the information that check needs.
Consequences: Every headless layer review stops at step 3, and an interactive worker must hand-edit the reviewer's `Inputs:` line (which zz-review says nobody edits) or commit with plain `git`. Two shapes of fix: (a) the dispatcher puts the finish sha in the code-mode prompt ("name `<finish>` on your `Inputs:` line") and, before filing, applies the same check `stampLayerReviews` applies (one shared function over `completion.reviewedShas`, the finish and its patch), keeping a review that fails it as `review-unfiled-N.md` with that reason; then `./zn commit` accepts the dispatched file unchanged. (b) `./zn commit` skips the `Inputs:` check for a new review whose stamp is the finish; this lets a hand-written exact stamp bypass the check, which refute 005 F3 called harmless only because the `Inputs:` check still applied, so (a) is the one that keeps the rule.
Recommendation: Take (a). In outcome 1 and outcome 8, say the dispatcher gives the reviewer the finish commit (the one it stamps, not `HEAD`) and files only a review whose `Inputs:` names it or a commit with its patch, by the same function `./zn commit` uses. In AC10, have the fake reviewer write `Inputs: git diff <below>...<finish>` from a value the fixture reads (`ZN_DISPATCH_DIR` beside a file the prompt names, or the prompt text the fake captures), commit every dispatched round with `./zn commit -m … --phase code-review --model <id>` as step 3 says, not plain `git`, and add one dispatch whose review names no commit: not filed, kept as `review-unfiled-N.md`, the reason named. Rules rows: "a dispatched review is committed by step 3's command" (mutant: the own-stamp exception dropped, or the dispatcher's prompt without the sha) and "the dispatcher files only a review naming the finish" (mutant: the dispatcher's check dropped), each killed by those steps.

### F2 [medium] Narrowing the committed-file check to "the stamp changed" skips a deleted round, so `./zn commit` now removes a committed review or refute, and a removed one comes back as a new file with a fresh stamp
Where: prototype `layergit.stampLayerReviews` at df9598312 (`if not path or not name or not fs.isFile(path) then continue`, before the `git show HEAD:<path>` compare); at f136c884f the same loop refused any status but `??`, a deletion (` D`) included; c0248.md outcome 1 ("so a stale stamp cannot be edited to the new finish", "so a finding never disappears behind a new round"); AC4 (no deletion case).
Evidence: (1) Layer c0010, `review-003.md` with an unanswered F1 at finish Z. `git rm` (or `rm`) of `review-003.md`, then `./zn commit -m …`: the status line ` D …/review-003.md` names an own round, `fs.isFile` is false, the file is skipped, and `recordAndCommit`'s `git add -A` commits the deletion. The folder's newest round is now `review-002.md`, stale and settled, so `./zn dispatch zz-review c0010 --mode code` files a new `review-003.md`, and the unanswered F1 is gone with no refute, harvest or ruling (`./zn lessons --uncovered c0010` pairs only the files that remain). (2) `refute-001.md` stamped at finish Y, layer re-finished to Z: delete it in one `./zn commit`, write it again in the next; it is not in `HEAD`, so it is new and is stamped Z, and its `fixed` answer carries round 001 to Z (rule 3) without a next round. Both were refused before this round; neither needs plain `git`.
Critique: The refusal was narrowed from "a committed round changes" to "a committed round's stamp changes" for the in-place edit refute 005 F1 needed; a deletion has no text to compare and fell out of the check with no sentence and no case. "New" read from `HEAD` alone also forgets every earlier commit of the layer.
Consequences: A worker stuck on "is not settled" has a one-command way out that erases the finding, which outcome 1 says never happens. A refusal of a deleted own round leaves a plain `git rm` and `git commit` followed by a `./zn commit` of the re-added file; reading "new" as "never committed on this layer" (no commit in `<layer base>..HEAD` touched the path, `git log --format=%H -1 <base>..HEAD -- <path>` empty) closes that too, and still treats the failed-commit retry (staged, never committed) as new.
Recommendation: In outcome 1, say that a committed review or refute is never removed or renamed (`./zn commit` refuses a deleted or renamed own round: "<name> is committed: a round is never removed; answer it, or review again"), and that a file is new only when no commit of the layer has had it. In `stampLayerReviews`, refuse a status line for an own round whose file is gone, and decide "committed" by the layer's history rather than `HEAD`.
