### F1 [medium] A dispatched review that the layer outgrows before step 3 commits it cannot be committed or replaced: `./zn commit` says "remove the line", which leads to the `Inputs:` refusal, and the dispatcher reads the uncommitted file as the folder's round
Where: prototype `layergit.stampLayerReviews` at 7284100b3, lines 900-909 (a stamp that is not exactly the current finish sha and patch is refused "the tool stamps it; remove the line"; `ownStamp` exempts only an exact match); `dispatcher.luau` `filingNow` (`reviewsIn({cwd}/{l.dir})` reads the working tree, so the filed, uncommitted `review-NNN.md` is the newest round, and `completion.current` accepts its stamp by patch); `dispatch.luau` line 272 (the code-mode prompt names no finish commit, so a dispatched review's `Inputs:` names at most the layer below); c0248.md outcome 1 ("or a commit with the finish commit's patch id (a clean restack between the review and its commit)"; "A new review that already carries the tool's own stamp for the finish ... needs no `Inputs:` check").
Evidence: (1) Clean restack. The dispatcher files `review-003.md` stamped `Commit: X`, `Patch: P`. Before step 3 the layer is restacked cleanly: finish X', patch P. Step 3's `./zn commit … --phase code-review` refuses (`c ~= sha`): "already carries a Commit: or Patch: line that is not the layer's finish: the tool stamps it; remove the line". Removing it sends the file through the `Inputs:` check, which finds no hex word naming X or a commit with patch P (the prompt never gave one; zz-review's `git diff <layer below>...HEAD` names only the layer below) and refuses "commit the review before re-finishing, or review again". Dispatching again is refused "one round": the uncommitted file is the newest round and is current by patch. The outcome-1 promise that a clean restack between a review and its commit is accepted holds for a session review and fails for a dispatched one, the path a headless run always takes. (2) A fix re-finished before step 3 (finish Y, patch Q; a worker that fixes before committing, or a step 3 that failed and was retried after a fix): the same two refusals, and a new dispatch is refused "is not settled (F1 is not answered in refute-003.md)", while `./zn commit` of review-003 with refute-003 still refuses review-003. In both, the only exits are hand-editing `Commit:` to the current finish (which `ownStamp` then accepts, the hand stamp outcome 1 says nobody writes) or deleting the uncommitted review, whose findings then exist nowhere.
Critique: Before this round the dispatched file never reached `./zn commit`'s stamp rules (review 006 F1), so this round opened the path and walked it only for a layer that does not move between step 2 and step 3. The tempting fix is to exempt any stamp the dispatcher wrote, or to re-stamp a dispatched file with the current finish; the second records a review of Y that read X.
Consequences: The stamp is either the tool's statement of what was reviewed or a hand claim, and the file cannot say which. What a hand claim can gain is only "current": a stale stamp makes the layer incomplete, which is the safe direction. A stamp whose `Commit:` is a commit whose patch id is its `Patch:` cannot claim a review of a commit with a different change. So one rule covers the stamp and the `Inputs:` line alike: what is named must be a commit with the claimed patch. A stale stamp committed as it is then makes the round need an answer and the next round, which `completion.layer` and the dispatcher already handle.
Recommendation: In outcome 1 and `stampLayerReviews`, accept a new file's stamp when `layergit.patchId(<Commit>)` equals its `Patch:` (refuse any other stamp, naming that rule), and commit it unchanged: with the finish's patch it is current (a clean restack), with another it is a stale round, committed so its findings are kept, answered, and followed by the next round. Keep the `Inputs:` check for an unstamped review. Change the refusal so its way out works under one round per folder (lesson below). AC4 or AC10 cases: a dispatched round with a clean restack before `./zn commit` is committed and the layer is complete; a dispatched round with a fix re-finished before `./zn commit` is committed with its old stamp, the dispatcher refuses until `refute-NNN.md` answers it, then files round N+1; a stamp whose `Commit:` has a patch other than its `Patch:` is refused. Rules rows with mutants "exact-sha stamp only" (killed by the restack case) and "stale stamp refused" (killed by the fix case).

### F2 [medium] The re-add refusal is a dead end with no case: a round deleted by a plain `git commit` can never be committed again, its restored original included, and every reviewer numbers the next round with that number
Where: prototype `layergit.stampLayerReviews` at 7284100b3, lines 872-877 (`git log -1 HEAD -- <path>` non-empty and the path not in HEAD: refused "was committed and deleted: a review round is never added again; review again as the next round"); c0248.md outcome 1 ("a round the layer's history had and HEAD lacks ... is never added again"); Rules row "a round the layer's history had is never added again | none | ... | reasoned"; `dispatch.filing` (`last + 1` over the files in the folder) and zz-review's Output file numbering (from the files present).
Evidence: Layer c0010 has `review-001.md` and `review-002.md` committed; someone runs `git rm …/review-002.md && git commit`. (a) `./zn dispatch zz-review c0010 --mode code` numbers from the files present and files `review-002.md` again; step 3's `./zn commit` refuses it. "Review again as the next round" files `review-002.md` again: the next round's number is the deleted one, for the dispatcher and for a session reviewer alike. (b) Restoring the deleted round (`git checkout <deleting commit>^ -- …/review-002.md`) is also refused: the path is not in HEAD and the history had it, and the check does not compare the file with what was deleted. So the layer's newest committed round stays `review-001.md` (stale), no `./zn commit` can add any `review-002.md`, and the layer never becomes complete except by another plain `git commit`. The row is `reasoned` because "it needs a plain `git commit` that deletes a round first", but the AC4 fixture already runs plain `git` (`git(wt, { "checkout", "--", path })`), so the case is two lines; review 006 F2 asked for it.
Critique: The refusal guards against a round coming back with a fresh stamp, but it refuses the one act that undoes the deletion, and the way out it names cannot be taken. Without a case, nothing shows either.
Consequences: Accepting the restored file means comparing it with the version the deleting commit removed. The same rule as an edit of a committed round applies: the stamp must equal that version's, other text may be corrected. A file of that name with any other stamp, or none, stays refused. Numbering past a deleted round is then not needed.
Recommendation: In outcome 1 and `stampLayerReviews`, read the deleting commit (`git log -1 --format=%H HEAD -- <path>`) and accept a re-added file whose `Commit:` and `Patch:` equal those of `git show <deleting>^:<path>`; refuse any other with "<name> was committed and deleted in <sha>: restore it (git checkout <sha>^ -- <path>) and answer it", the command it names being one that passes. AC4 cases: a committed round removed with plain `git rm` and `git commit`; a fresh unstamped file of that name refused with those words; the file restored by the printed command and `./zn commit` accepted. Make the row `run` with the mutant "the history check dropped" (killed by the refusal case) and add the row "a restored round is committed" with the mutant "a restored round refused" (killed by the restore case).
