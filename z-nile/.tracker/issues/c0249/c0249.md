# c0249: Issues and rafts have a rank

## Problem
Tickets have no order. A worker (or you) cannot say which ticket comes next. Every issue and raft should carry `rank:` (integer, lower first). `depends_on` stays a hard constraint; `rank` orders what is free. The next item is the lowest rank among items whose `depends_on` are all done and whose status is claimable.

What should happen: z-ticket and z-design append by default; `./zn rank <id> top|after <id>|<n>` reorders; a raft takes the best rank of its members; `./zn next` prints the next claimable item; `./zn list` and the board show the stack in order; the engine audit rejects a malformed rank.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

## Idea
Tickets have no order, so neither a worker nor the user can say which comes next. Every issue and raft can carry a `rank:`, an integer where lower comes first.

- **Unset is the default and the lowest rank** (Q2): below every set rank. Equal or unset ranks fall back to the ticket number, so the order is always stable. z-ticket and z-design write no rank, and unset does the appending. Only a person sets a rank: with `./zn rank`, in the board app, or when z-raft asks.
- **`./zn rank <id> top|after <id>|<n>`** reorders, and can also unset a rank.
- **A raft's rank** (Q5). z-raft asks for a rank when it makes a raft, and unset is a valid answer. The answer is the raft's own rank and overrides its members' ranks. A raft with no rank of its own takes the best rank of its members.
- **Who set it.** Setting or unsetting a rank (with `./zn rank`, in the board app, or as z-raft's answer) records who set it in c0263's record (`./zn record <id> ranked`). The user's c0263 decision (2026-11-08) and c0264's design give that row to this issue.
- **`./zn next`** prints the next claimable item, in this order:
  - lost work first: anything in progress but lost (a stale heartbeat, c0265) comes before anything not yet started, whatever its rank, even if a human started it without updating the rank;
  - then the claimable raft with the lowest rank;
  - only when no raft is claimable, the issue with the lowest rank whose design a worker may draft (Q1). Which issues qualify is c0253's: a confirmed idea (c0260).
  `depends_on` is a hard constraint, and rank only orders what is free. An item that waits on undone work, or is blocked (c0250), is skipped, and its rank is left as it is.
- **Claimable** (Q1, and the user's 2026-11-08 scope decision): a worker carries a raft to merge, and it may draft the design of an issue, but a person approves it.
- **`./zn list` and the board show the stack in order.** Blocked items come first, because they wait on the person (c0250), then the order `next` uses. The engine's audit rejects a malformed rank.
- **The Omarchy app (c0257) follows the rank and reorders by drag and drop** (Q3). c0249 makes the app order tickets and rafts by rank (unset last, the ticket number as the tiebreak), the rank part of what c0257's capture gave to "the order c0249 defines". The app's hook today calls `./zn rank {id} --before {beforeId}`, so c0249 either gives `./zn rank` that form or changes the hook. c0249 therefore depends on c0257.
- **The README.** Its "lowest rank among items whose status is claimable" says what claimable means above. Its older line that every item "gets a rank" moves to the Rank and lost work sub-section, where unset is a valid rank. Its "z-ticket and z-design append by default" becomes "unset by default" (Q2).

**R-vision stays one raft** (Q4): c0249 is its second layer.

Solution ideas from the capture: an integer in the frontmatter with gap numbering (10, 20, 30), so one move edits one file, and a pure `next` function in the engine over the parsed tracker.

### The rank line (`z-nile/engine/rank.luau`, new, pure, strict)
`rank: <n>` is one line of an issue's or a raft's front matter, written by `./zn rank` **right after `id:`** (at the top of the block when there is none). That is the line no prep branch edits: a prep edits `design:` and `status:` (the carried move to `prepared`), so a rank written beside them conflicts with every open prep (probed: a branch that edits `design:` and `status:` and a main that inserts a line above `status:` do not merge; the same rank after `id:` merges, `drag.spec` pins it). c0248's `layers:` and c0250's `blocked:` lines are added last by `store.withFront`, far from the top, so none of the three sits beside another. `n` is a whole number from 1 to 999999: no sign, no leading zero, no fraction, and nothing after it: no marker, no word (who set a rank is read from `provenance.md`, below). The captured "integer in frontmatter" therefore holds exactly: the value is a bare integer. **Unset is no line, or an empty value** (`rank:`); `./zn rank <id> unset` removes the line, and z-ticket, z-design and z-raft write none (the templates carry none). A rank orders work that is not started, so **only a backlog item has one**: on an active, done or retired item the line (if one is left) is not read and counts as unset (`rank.factOf`). A malformed value counts as unset for the order and is the audit's to refuse.

**Who set a rank is in `provenance.md`, never in the line** (ruled, "Read provenance.md"). A drag among unset items ranks the unset items above the drop so that the order holds; nobody chose those ranks, and the `ranked` row of each carries `moved=<the item dragged>`. A rank counts as **a person's** when the item's latest `ranked` row has no `moved=` field, or the item has no `ranked` row (a hand edit); it is **moved-written** when its latest `ranked` row has `moved=`. A raft whose own rank is unset takes the best rank *a person set* on a member, so a moved-written rank does not count for it (A raft's rank, below). Reading it is `rank.movedBy(record)` over the text of the member's `provenance.md`; the callers read that file only for a backlog item that has a rank.
```
rank.MAX = 999999   rank.GAP = 10
type Fact = { id, kind: "issue"|"raft", state: "backlog"|"active"|"done"|"retired", status, rank: number?, moved: boolean?,
              raft: string?, members: {string}, dependsOn: {string}, root: string, design: string?, approved: boolean?,
              ownRank: number?, ownMoved: boolean? }   -- ownRank and ownMoved: set by rank.stack only; moved: its latest ranked row has moved=
rank.parse(value: string?): (number?, string?)               -- (nil,nil) unset; (n,nil), a bare whole number; (nil, why) otherwise (` auto` included)
rank.movedBy(record: string?): boolean                      -- the text of an item's provenance.md: is its latest ranked row written with moved=?
rank.problem(text: string): string?                          -- the audit's check over one document
rank.withRank(text: string, value: number?): string?
rank.where(path: string, roots: {string}): (state?, id?, root?)  -- publish.itemPath's reading, plus a retired raft's path
rank.factOf(path: string, front: {[string]: string}, roots, record: string?): Fact?  -- one reader of a front table (and, for an item with a rank, the text of its provenance.md), for every caller
rank.isBlocked(status: string?): boolean                     -- the stored word `blocked` or `blocked-…` (c0250)
rank.less(ar, aid, br, bid): boolean                         -- the one comparator (work.luau uses it too)
rank.effective(f: Fact, byId): number?                       -- the rank the order uses
rank.order(facts, opts: { lost: {string}?, blockedFirst: boolean?, world: {Fact}? }?): {Fact}
rank.listOrder(facts, lost: {string}?, world: {Fact}?): {Fact}  -- what `./zn list` prints
rank.depsMet(f, byId): boolean
rank.next(facts, ctx: { lost, claimable, mayDraft, scope }): (Pick?, string)
rank.stack(facts, kind): {Fact}                              -- the backlog items of a kind in order, with ownRank
rank.plan(stack, id, how: "top"|"last"|"before"|"after"|"set"|"unset", arg): ({Change}?, string?, string?)  -- changes, refusal, notice
```
`rank.problem` reads the front block as `store.readFront` and `audit.front` do (the text between the leading fences, `key: value` per line); it is the check of one key, and `rank.spec` pins the cases where the readers would skip a line silently. `rank.where` is not a second reader of item paths: it calls `publish.itemPath` (the tracker's one reader) and adds only the retired-raft path that the publisher never sees, for the roots a registry lists (a folder that merely looks like a root is not an item). `factOf` takes the front as a table, so `main.luau` (`frontOf`), `workread.luau` (`frontText`) and `store.readFront` all feed the one function; it takes the text of the item's `provenance.md` as a string, so each caller reads that file its own way (a batch of the base, or the checkout) and only for an item that has a rank.

### The order (one comparator)
`rank.less`: a set rank before an unset one, then the lower rank, then **the ticket number**: a raft before an issue, then the number (f, d and c share one number space, so `f0420` and `c0420` tie on the number), then the id. Equal or unset ranks therefore always sort the same way (AC9). `rank.order` adds, in front of that and only when asked: **blocked items first** (`blockedFirst`: they wait on the person, c0250), and **lost work before everything else but blocked** (`lost`, the heartbeat's own order, longest silent first: c0265's `heartbeat.order`). Blocked is the stored status word `blocked` or `blocked-…` (c0250's grammar; read from the front, so it works before c0250 lands and after it).

### A raft's rank (Q5)
`rank.effective`: a raft's own rank if it has one, else the **lowest rank a person set on one of its members** (the issues its `issues:` line lists that are in the backlog; a rank whose item's latest `ranked` row carries `moved=` does not count); a raft with neither is unset. The own rank *overrides*: a raft with rank 50 whose member has rank 10 is placed at 50. It is read the same way by `list`, `board`, `next`, `work next` and the move. A move that places a raft gives it a rank of its own (never a member's).

Ruled (user, 2026-11-16, "Read provenance.md"): who set a rank is read from the item's `provenance.md` and the line stays a bare integer. This answers F2 of the design review: dragging an issue that is in no raft ranked the unset issues above it, including members of rafts, and Q5 then moved the rafts (probed: c0050 in R0002, c0100 in R0001, nothing ranked; `next` prints R0001; after dragging c0300 before c0200 the members are ranked 10 and 20 and, with every rank counted, `next` prints R0002). With the rule, the members' rows say `moved=c0300`, so they do not count and `next` still prints R0001. The design had weighed (a) freezing every raft whose rank would change with an own rank, (b) this, and (c) accepting the reorder, and the mark in the line (`rank: 30 auto`); the user chose (b). **Cost of the choice: one `provenance.md` read per ranked member when a raft's rank is computed** (an unset raft opens the record of each ranked member; with no ranks anywhere it reads none), and the order depends on a second format (`provenance.parse`, c0263). A hand-edited `rank: 20` with no `ranked` row is always a person's, which is right. **A renumbering keeps a person's rank counting** (the coordinator's direction after the ruling, 2026-11-17: the ruling changed where the mark is stored, not the behaviour): when two ranked neighbours leave no room and a renumbering shifts items, it looks at whether each item's rank counts now (its latest `ranked` row has no `moved=`, or there is no row). If it counts, the new row records the shift as `shifted=<the item moved>` (the trail is kept, and the rank keeps counting however often it is shifted); if it does not count, the row is written with `moved=<the item moved>`. A rank a move wrote on an unranked item always gets `moved=`. Asking for the place of a moved-written rank (`rank <id> top` where it already is, or `rank <id> <n>`) makes it a person's: no line changes, and a `ranked` row without `moved=` is appended.
Guess (revision, 2026-11-16): two readings of the rule that remain. ### The move (`rank.plan`)
`./zn rank <id> top | last | before <id> | after <id> | <n> | unset`. The stack is the backlog items of the item's kind (issues, or rafts), in the order above without lost or blocked (a person is moving things in the order they see). The moved item goes to the asked place; its new rank is
- **a gap**: between its new neighbours' ranks, 10 above the one before it (or half of the one after it, for the top), or the middle of a gap smaller than 10, so that one move edits one file; verified by sorting the result;
- **among or after unset items**: the unset items above the drop are ranked too, in steps of 10 after the highest rank there is, their `ranked` rows written with `moved=` (so a raft ignores them), and the moved item is ranked after them, its row without `moved=` (a person's). **No rank that exists changes**, so a person's ranks and the rafts they place stay as they are;
- **below the unset items** (`last`, which is what the app sends for a card dropped below the last one: `--before ""`): the moved item is **unset**, so it sorts among the unset items by number, and nothing is renumbered. The command prints a notice line (`dropped below the unset items: it sorts among them by number, and nothing is renumbered`) and the app's notice repeats it. With every item ranked, `last` goes after the last one;
- else, only when two ranked neighbours leave no room (equal or adjacent ranks, rank 1 at the top): **the ranked items from the top through the moved one are renumbered 10, 20, 30 ...** in the same change, each row but the moved item's written with `shifted=<the item moved>` when a person set that rank (it keeps counting) and `moved=<the item moved>` when a move wrote it.
`<n>` sets the number as given (refused outside 1 to 999999); `unset` removes it. An anchor must be a backlog item of the same kind; a done, active, missing or other-kind anchor is refused naming the rule. A move to where the item already is changes nothing.
Guess (prep, 2026-11-16): the captured `top|after <id>|<n>` is extended with `last`, `before <id>` and the flag form `--before <id>` (`--before ""` = last): the Omarchy app's hook is `./zn rank {id} --before {beforeId}` with an empty `{beforeId}` for a card dropped last, and the Idea says c0249 either gives `./zn rank` that form or changes the hook. Cost: one more spelling to keep; the alternative (changing the hook to `after`) cannot say "last" through a template with no branches. Ruled (user, 2026-11-16, "Accept as written").
Guess (prep, 2026-11-16): a drop below the unset cards **unsets** the card (the user's own gesture, "drag and drop reordering", cannot put a card after items that sort by number, so the notice says where it went). Alternatives: (a) rank everything above the drop, as the first prototype did: measured on today's tracker (194 unset backlog issues, `experiments/E3-plan.luau.txt`) a drop of any card at the end ranks 193 other cards, 388 files in one commit; (c) refuse, naming how many items the move would rank. Cost of the choice: a card dropped last does not stay last; it returns to its place among the unset cards, which the notice says. The drop *among* unset cards is not changed and still ranks the unset cards above it: measured, card 150 dropped before card 120 writes 120 changes (119 moved-written ranks and the moved card: 240 files with their `ranked` rows), card 5 before card 2 writes 2, card 5 to the top 1, card 5 after card 10 writes 10. Once a column has been ranked from the top the rest of the drags are small, and those ranks are moved-written (their rows say `moved=`), so they reorder nothing else; the first drag in a long column of unset cards is the expensive one. Ruled (user, 2026-11-16, "Accept as written").

### The command `./zn rank` (main.luau, one function; the edge is `rk` and `cmd.rank`)
- **Where it runs.** In the **main checkout** as well as in a worktree: the board app's `rankCommand` runs in the repository (Q3: "so a drag persists as a rank on origin/main"), so it joins the complete list of commands that may run there (zz-rules) and AGENTS.md's list of what edits it. There it requires what `ready` and `stop` require (an origin, `main` checked out and clean) and only **fast-forwards** the checkout after publishing (`pullMain`), as they do; in a worktree it merges origin/main. It refuses without an origin, and a dirty or off-main main checkout, before anything is published.
- **What it publishes.** One commit on origin/main through `publish.commit` (retried on a lost race): the changed documents with the `rank:` line set or removed, and, for **each changed item**, one appended `ranked` row in its `provenance.md` (c0263): `| <when> | ranked | <actor> | rank=<n\|unset>; was=<n\|unset> |`, with `; moved=<id>` on a neighbour a move ranked, or renumbered when a move wrote its rank (the field that says a move, not a person, wrote that rank), and `; shifted=<id>` on a neighbour a renumbering shifted whose rank a person set (the trail is kept and the rank keeps counting). Asking for the place a moved-written rank already has changes no `rank:` line: the commit holds only that item's new row, without `moved=`. The actor is c0263's live actor (`--actor`, `ZN_ACTOR`, an agent session, else the git name), through the one function `rk.actor` (c0263's inner `liveActor` of `cmd.provenance` now calls it). It calls `provenance.record` in the same commit and not `./zn provenance record`, which refuses the main checkout and makes a commit per row. Message: `tracker: rank <id> <how>`.
- **The plan is made inside the publish.** The build closure `publish.commit` calls on each attempt reads the documents of the base that attempt fetched and plans from them, so two drags at once give the second a plan made from the first's result (`drag.spec`: a competitor lands a rank during the first push; the second plan renumbers under it instead of placing the card beside a stale rank). Because the closure needs hundreds of documents, `publish.commit` gains an optional fifth argument to the build, `readMany(paths)`, one `git cat-file --batch` of the base (nil for a missing file; the plan reads the `provenance.md` of each ranked item the same way), as `workread.facts` reads; the other publishers ignore it.
- **After the publish.** The rank is on origin/main from here. Bringing it into this checkout can fail (a lock a sibling `sync` holds): then `rank` says so on stderr (`rank: saved on origin/main, but this checkout could not be brought up to date: …`) and **exits 0**, so the board app does not report "priority not saved" for a rank that is saved (F13 of the design review; `drag.spec` holds an `index.lock`).
- **Refusals** (each names the item or the rule and publishes nothing): not an item id, an unknown option, a bad usage, a number outside 1 to 999999, an item that is not on origin/main, **not in the backlog** (`c0100 is done: a rank orders work that is not started`), an anchor that is not in the backlog stack of the item's kind, an item moved after itself, a main checkout that is dirty or not on `main`.
- **The publisher** (`publish.commit`) takes the new change on its own terms: an existing document may differ from origin's only in its `status:` line **or its `rank:` line** (one of each), and a rank change is refused on any document under `active/` or `done/` (`a rank is published for a backlog item only`; a retired raft is no tracker item file to the publisher at all). See Hashes and guards.
Guess (prep, 2026-11-16): `rank` writes the `ranked` row in the same commit as the rank, as part of the one publish. Cost: if c0263's record API moves (a row's grammar), `rank` changes with it; the alternative, a second commit through `./zn provenance record`, leaves a rank on main with no row when the second fails, and cannot run in the main checkout. Ruled (user, 2026-11-16, "Accept as written").

### The pick: `./zn next` (`rank.next`, `cmd.next`, `workread.facts`)
Reads origin/main (a fetch, and the same reads as `./zn work next`; it does not read this checkout, so a rank published from another worktree is seen at once: `command.spec`): `./zn next` prints one line, `<id> lost|raft|rafting|draft <why>`, and exits 0; with nothing to take it says why on stderr and exits **1** (a loop can test it; c0253 takes what it prints). In order:
1. **lost work first**, whatever its rank or kind: the first id of `heartbeat.order` whose verdict is `lost` (c0265: `hb.judgeAll`, `rk.lost`), not done or retired, in the project's scope; `why` = `its heartbeat is stale`. When the heartbeats or the pull requests cannot be read it says so on stderr and goes on: unknown is never lost. In a protected checkout it reads no remote and says so.
2. **the claimable raft with the best rank**: a backlog raft with status `prepared` that `./zn ready` would accept (`work.claimable` over `workread.collect`, the same facts `work next` uses), whose dependencies are all done (`rank.depsMet`: its members' `depends_on` outside the raft); the best by the order above (own rank, else a member's best person-set rank, then the number); `why` = `rank <n\|unset>`.
3. **the best-ranked approved issue that is in no raft**: a backlog issue with status `prepared`, `design: ready`, an `approval.md` on origin/main, in no raft, whose dependencies are done; `<id> rafting approved, in no raft`. The worker rafts it (`./zn raft-plan --apply`; z-raft groups by its fixed policy, which may put it with others, so the printed id is the one to start with and not necessarily the one z-raft groups first). This is the 2026-11-13 re-ruling's "rafts approved issues itself by the fixed policy": with no person to raft, approved issues would otherwise pile up unrafted while the loop drafts new ones.
4. **only when none of the above exists**, the best-ranked backlog issue with status `new`, in no raft, with its dependencies done, whose design a worker may draft: **the claim gate of z-design** (`idea.designRefusal`, read from origin/main's document and `idea-review-001.md`: the idea was challenged and its open lines ruled). c0253 narrows this to a confirmed idea when c0260 lands, by passing another `mayDraft`. A person approves what the worker drafts (`./zn approve`, c0283).
A raft or issue that waits on undone work, or is `blocked` (a status other than `prepared`/`new`), is skipped and **its rank is left as it is**: when the dependency lands it is first again at the same place. From a project's folder the pick is that project's (`projects.inDir`), from the checkout root any project's, as `work next`. **Claimable** (scope decision 2026-11-08) is exactly this: a worker carries a raft to merge, rafts what is approved, and may draft the design of an issue, but a person approves it; the README's "lowest rank among items whose status is claimable" says so.
Guess (prep, 2026-11-16): the order is lost, claimable raft, rafting, draft. It follows the re-ruling's own sequence ("drafts designs and stops at your approval, then rafts approved issues itself") read as a pipeline the worker keeps moving forward: delivery before new drafts, as the confirmed Idea already puts a claimable raft before an issue to draft. Alternatives: draft before raft (more drafts for the person to approve, approved work waits); raft before the claimable raft (a raft the user ranked first waits while approved issues are grouped). Cost if wrong: a worker takes one kind of work before another; each is one line of `rank.next`. Ruled (user, 2026-11-16, "Accept as written").
Guess (prep, 2026-11-16): "approved" for the rafting pick is that `approval.md` exists beside the issue on origin/main (the design is `ready`), not that its hash still holds. Cost: an issue redesigned after its approval can be offered, and `./zn ready` later refuses it and the worker stops at the person; the alternative, hashing each prepared issue's design, check and specs on every `next`, reads files for every prepared issue. Ruled (user, 2026-11-16, "Accept as written").
`./zn work next` takes rafts in the same order: `RaftFact` gets a `rank` (own, else the members' best person-set rank, backlog only) and `work.before` (replacing the placeholder `work.rankKey`, which was the id) is `rank.less`. Lost work first is `./zn next`'s and c0253's, not `work next`'s (it offers backlog rafts only). Guess (prep, 2026-11-16): `next` exits 1 with no item. ### The stack in `list` and on the board
**`./zn list` stays offline (decided with the user, 2026-11-16: "Stay offline, fast (Recommended)") and prints, in this order: every blocked item first (rafts, then issues, each in the stack's order), then the rafts and then the issues, each in the stack's order; `./zn list --lost` also asks the remote and puts lost work (the heartbeat's order, any kind and rank) after the blocked items.** The blocked part is c0250's shape exactly as its `work-board.spec` pins it (`R0020 c0020 c0040 R0010 c0010 c0030 c0050`: the blocked raft and issues first, then the rest as `list` printed them, rafts then issues); lost work, with `--lost`, is the part this layer adds, after the blocked items. A non-backlog item counts as unset. Behaviour change, stated: the unranked order is by ticket number across f, d and c (it was by id text: all `c`, then `d`, then `f`), which the captured fallback asks for.
`--lost` reads lost work as `./zn lost` and `next` read it (`rk.lost`): a fetch of `main` and of the heartbeat branches, one `git log -S` per claim, `gh` only when a claim is stale. With no origin or `PICKMAN_PUBLISH=0` there is nobody to ask and it says nothing; in a protected checkout, with unreadable heartbeats or pull requests, or when the remote cannot be asked, it says so on stderr (`list: lost work not read (…); unknown is never lost`) and lists without lost work. **Without `--lost`, `list` reads no remote and says nothing about lost work** (ruled, "Stay offline, fast (Recommended)"): measured on today's tracker (479 items, 69 claimed items, a loaded machine), `./zn list backlog` takes **0.45 s offline against 9.7 s with the read** (3.1 s user, 4.1 s system for the network and the claims' `git log`), so lost-first ordering lives in `./zn next`, `./zn lost`, `./zn status` and the board, and `list` shows it only on request. **The board.** `board.collect` gives every issue and raft `rank` (its own, backlog only) and `effectiveRank` (the order's), `boardview.bands` puts each column's bands in the stack's order (a raft band by its raft's rank, the raftless cards as one band by their best card, a band holding a blocked card first) and the cards in a band in the same order, and each bucket of the Rafts and Issues **views** (`views.rafts.ready`, `views.issues.not` and the rest, which sorted by id text) is ordered the same way, a blocked item first (F7 of the design review: the Ready bucket of rafts is the list `next` and `work next` choose from). c0276's `board.withVerdicts` (layer 4 of R0100, which lands before this layer) then moves the **lost** cards first inside each band and bucket with a stable sort and marks them; it does not call `rank.order`, and the two compose: a lost card first in its band, the rest in rank order (`board.spec` calls the function on a collected model). `rank.order` takes the lost ids too (`list --lost` passes them), so the board needs none of its own. Lost work first in the app, and its marks, are c0290's (the user, 2026-11-09).

### Hashes and guards (the new front-matter line meets every reader of the front matter)
A `rank:` edit is made by a command on a document that is also hashed and compared. Each one, read and decided:
- **`raftplan.designHash` / `recordHash`** (a raft's `grouped:` record of each member's design): skip `status:` and `raft:`; now `rank:` too, or ranking a grouped member would make `ready` say "changed on origin/main since grouped". A body line `rank:` or a key `ranked:` still counts.
- **The approval contract** (`contract.build`): hashes the design sections, `check.sh` and the specs, never the front matter; a rank edit voids no approval (pinned).
- **`publish.commit`'s status-only rule** (`withoutStatus`): now `status:` and `rank:`, one of each; a rank change is refused for an `active/` or `done/` document. c0248 also extends this function (its `layers: reviewed` line, lower in the stack): both lines are stripped in the one function, and the merge of the two is a two-line union.
- **A prep branch's merge.** Written right after `id:`, a published rank merges with a prep that edits `design:` and `status:` (`drag.spec`: the worktree commits both edits, a rank is published from the main checkout, `./zn sync` succeeds with both). A merge conflict is therefore not the expected case; a prep that edits the first lines of its document (`id:`, `type:`) would conflict, and nothing in the tooling rewrites them.
- **`readycheck`, `approval.collect`, `trail`, the capture guard** (`CAPTURE_KEYS`), **dispatch's tracker-state judgement**: read no front line other than what they name; none names `rank`. A capture PR still edits only the title, `depends_on` and sections; `rank` lands by direct publish, not by a capture.
- **Moves** (`ready`, `stop`, `done`) carry the document byte for byte except `status:`, so a rank travels with its item; an item that leaves the backlog keeps a stale `rank:` line that is not read.
- **Merges**: `provenance.md` appends merge by c0263's union.

## Acceptance criteria

### Checked
- AC1: `rank:` in an issue's or a raft's front matter is a whole number from 1 to 999999, a bare integer and nothing else (an empty value or no line is unset; who set it is read from the item's `provenance.md`, never from the line: a latest `ranked` row with a `moved=` field means a move wrote it); setting a rank writes one line right after `id:`, the line no prep branch edits, and unsetting removes every rank line; only a backlog item has a rank (an active or done item's counts as unset); and a document path gives its state, id and root through the registry, a retired raft's too, and only for a registered root.
- AC2: `./zn rank <id> top | last | before <id> | after <id> | <n> | unset`, and the board app's `rank <id> --before <id>` (an empty id means last), give the item a rank in a gap between its neighbours (one file edited); an item dropped among or after unset ones is given a rank with the unset ones above it (their `ranked` rows carry `moved=`), after the highest rank there is, and no rank that exists changes; with no room between ranked neighbours the ranked items are renumbered from the top (each row but the moved item's says `shifted=` for a rank a person set, which keeps counting, and `moved=` for one a move wrote); an item dropped below the unset ones is unset and a notice line says so; the change is one commit on `origin/main` holding the changed `rank:` lines and a `ranked` row of the live actor for each (a neighbour's names the item that moved it), planned inside the publish from the files of the base that publish fetched, so two drags at once give the second a plan made from the first's result; it runs in the main checkout, which it only fast-forwards, and in a worktree, which merges origin/main, and a rank that is on origin/main is reported as saved, exit 0, when this checkout cannot be fast-forwarded; a move to where the item already is publishes nothing, except that asking for the place of a moved-written rank appends a row without `moved=` and changes no line; and an item that is done, active, missing or of another kind, a bad number, anchor or option, a dirty main checkout or one off `main` are refused with the rule and publish nothing.
