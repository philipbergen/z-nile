# c0250: Escalation to the human: blocked state and resolve

## Problem
When a worker fails in a way it cannot fix (review rounds exhausted, a tool or library the design did not cover, an ambiguity, a red gate after N attempts, every CLI out of quota, a guard fired) there is no formal way to push the item back to the human. c0117 only writes a local `.cache/dispatch/<id>/questions.md`, which another host cannot see.

What should happen: a new status `blocked` on `origin/main` with `blocked: review-exhausted | design-gap | needs-decision | red-gate | quota | tripwire`; an `escalation.md` in the item's folder, landed with it, holding the reason, what was tried, the open findings or error verbatim, the options with a recommendation and the resume commands; the worker parks the branch and PR, releases its claim, and moves on to the next unblocked item that does not depend on it; `./zn resolve <id> amend-design|approve|split|retry|abort` records the human's decision and the item rejoins the stack at its old rank; the board lists blocked items first.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

## Idea
A worker that hits a wall it cannot get past never guesses. It escalates formally to the human. Today c0117 only writes a local `.cache/dispatch/<id>/questions.md`, which no other host can see.

- **The walls:** review rounds exhausted, a tool, library, dependency or scope the design did not cover, an ambiguity only the human can settle, a gate still red after N fix attempts, every CLI out of quota past the cap, and a guard that fired.
- **State.** The item goes to status `blocked` on `origin/main`, so every host and the board see it. `blocked:` holds a reason from a closed list: `review-exhausted`, `design-gap`, `needs-decision`, `red-gate`, `quota`, `tripwire`.
- **The note.** `escalation.md` in the item's folder is landed with the state. It holds the reason, what was tried, the open findings or the error verbatim, the options with a recommendation, and the exact resume commands. It is in git, so it works across hosts, and it replaces c0117's `questions.md`.
- **A raft blocks as a whole.** A worker holds a whole raft (c0253). When any ticket of the raft blocks, the raft is marked blocked. The worker parks the branch and PRs, releases its claim, clears its context, and takes the next raft that does not depend on the blocked one.
- **A blocked layer stops the layers above it, not the ones below** (c0248; Q1). The green layers below the blocked one land now, with one full gate on the top green layer. The raft is blocked at that layer and resumes there after the resolve.
- **Quota waits before it blocks** (Q3, Q6). When the raft's CLI runs out of quota, the worker keeps its claim and its beat and waits a short limit, then continues on another CLI with quota in a new session. When every CLI in `order` is out, it waits with no model running and continues as soon as any CLI has quota. It blocks with `quota` only when every CLI stays out past a cap set in `.models.toml`. c0250 adds the `quota` reason and the cap. The waiting is the worker's (c0253), which has the beat (c0265, c0275).
- **The human resolves.** The board lists blocked items first, with the reason and the question. `./zn resolve <id> <decision>`, where the decision is one of:
  - `amend-design`: back to z-design, with the note as input;
  - `approve`: for example, accept the new dependency, recorded in the design;
  - `split`: carve out an issue;
  - `retry`: more rounds or attempts;
  - `abort`: z-stop.
  The decision is committed to the item, and the item rejoins the stack at its old rank.
- **Who resolves** (Q5): the user, or an interactive agent the user tells to, recorded as on the user's word with the user's message quoted. A headless session is refused. Resolving records who unblocked it, with the user's quoted message when an agent ran it on the user's word: `resolve` writes an `unblocked` row in c0263's record (`./zn record <id> unblocked`). That row is the only one for an unblock by `resolve`. The other unblock, `status <id> new` after a stop, is c0282's row.
- **Only the user re-approves a changed design** (Q8). When a resolve changes an approved design (for example, an `approve` that accepts a new dependency), the item waits for the user's own `./zn approve` before `ready` or `done` continue. An agent may resolve on the user's word, but #295's contract check holds.
- **The README.** Its `quota` row ("every CLI failed on quota") says every CLI stayed out past the cap, and its "takes the next unblocked item" says the worker takes the next raft.

**R-vision stays one raft** (Q7): c0250 is its third layer. (Replaced on 2026-11-19 by R0093's grouping, "go wwith 1 first then": see the Problem's last Decided line.)

Solution ideas from the capture: a closed reason list in the engine, with one lifecycle edge per `resolve` decision, replacing `questions.md` in c0117's design.

Not here: notifications beyond the board; the N of rounds and attempts, and the quota cap's value (the dispatcher's configuration); the worker's wait itself (c0253); and the landing of the green layers below a block (c0248, c0252).

**1. The blocked state.**
- `blocked` joins the closed status list (`status.NAMES`) and is stamped like the others (`blocked-<three words>`). Four edges join `status.ALLOWED`: `preparing>blocked` (an issue in design, or a draft raft in rafting), `active>blocked` (a readied raft; its members move with it), and `blocked>new` and `blocked>prepared`, which only `./zn resolve` takes (outcome 4). `./zn status <id> blocked` is refused ("only ./zn block blocks"), and so is `./zn status <id> <to>` from `blocked` ("only ./zn resolve unblocks").
- A blocked item's front matter carries `blocked: <reason>`. The reason is one of `review-exhausted`, `design-gap`, `needs-decision`, `red-gate`, `quota`, `tripwire` (`escalation.REASONS`, the one closed list). `resolve` removes the key.
- A blocked item holds no claim. No worker owns it, it needs no beat (c0265 never calls it lost), `./zn work next` and c0249's `next` never take it (it is not `prepared`), and an item that depends on it waits (its `depends_on` is not done). Its `rank:` line is never changed, so after the resolve it rejoins the stack where it was.

**2. The note: `escalation.md`.**
- The note lives in the blocked item's folder: the raft's folder for a raft, the issue's for an issue. It is published with the state in one commit. `z-nile/engine/escalation.luau` (new, pure) is its one reader and writer.
- Shape:
  ```
  # Escalation: R0120
  Item: R0120
  Reason: red-gate
  From: active
  Layer: c0230
  Actor: agent:claude-opus-5-5 effort high
  Session: 6f1c…
  Open: F2, F5
  When: 2026-11-20 03:10

  ## Question
  <one paragraph the human answers>

  ## What was tried
  <the attempts>

  ## Open findings or error
  <verbatim>

  ## Options
  - retry: <what it means here> (recommended)
  - amend-design: <what it means here>

  ## Resume
  ./zn resolve R0120 retry --answer "<your answer>"
  ./zn resolve R0120 amend-design --answer "<your answer>"
  ```
- The worker writes `## Question`, `## What was tried`, `## Open findings or error` and `## Options`. Each option is a bullet starting with one decision (outcome 4), and exactly one bullet ends with `(recommended)`.
- `./zn block` writes the header lines and `## Resume`. The header lines are `Item`, `Reason`, `From`, `Layer` for a readied raft (outcome 3; a draft raft has no layers, so its note has no `Layer:` line), `Actor` (the live actor, as c0263 reads it), `Session` (the running CLI session, as `sessionread` reads it, when one is known), `Open` (for `review-exhausted`, the ids of the unruled bullets under `## Open to the human` in the item's document and, on a raft, the Layer member's, as `openlist.pending` reads them) and `When` (UTC).
- `## Resume` has one line per decision the options name, each an exact `./zn resolve` command:
  - `split`'s line carries `--title "<the new issue's title>"`;
  - a `review-exhausted` note's lines carry one `--rule <Fn>="<your ruling>"` per open id;
  - a closing line says that an agent adds `--said "<the user's message>"`.
- It refuses a note that is missing a section, has an option naming no decision, does not have exactly one recommendation, or already holds a `## Resolution` ("this is the last block's note: write the new one").
- `resolve` appends `## Resolution`. When the same item blocks again, `block` first renames the resolved `escalation.md` to `escalation-NNN.md` (the next free number), so `escalation.md` is always the current block and every earlier one is kept.

**3. Blocking: `./zn block <id> <reason> [--layer <issue>]`.**
- Where it runs: the worker runs it in the item's worktree, after writing `escalation.md` in the item's folder there.
  - For an issue in design, that is the prep worktree.
  - For a draft raft being rafted, the rafting worktree.
  - For a readied raft, the raft's worktree.
- What it refuses:
  - an unknown reason;
  - an item that is neither `preparing` nor `active` on `origin/main`;
  - a note of the wrong shape;
  - the main checkout ("block runs where the note was written");
  - an issue that is a member of an active raft: "c0210 is in R0010, readied: block the raft: ./zn block R0010 <reason> --layer c0210";
  - a `--layer` that is not a member of the raft still in `active/`;
  - the reason `tripwire` in an agent session (`provenance.hint`): after a tripwire, the person checks the checkout and files the block (outcome 6).
- **The Layer** of a raft is `--layer`, which is required when two or more members are still in `active/` on `origin/main` (refused without it, exit 1, nothing published: `"<R> has c0210, c0220 still in active/: name the blocked layer: --layer <issue>"`); with one member left there, that member is the Layer (design review 004 F1). Only the step knows which layer needs the decision: under `./zn dispatch` nothing lands before a block, and on a raft without `layers: reviewed` nothing lands at all, so "the lowest member still in `active/`" would name a green layer below the blocked one. Every text that tells a step to block a raft gives `--layer <issue>` (the step prompt, the Headless paragraphs, z-work step 5, zz-execute's To escalate, zz-rules' `block` row). The Layer is never read from the current branch: after `done --through` the checkout sits on the lower layer, and before the first `start` it is detached.
- **Re-filing:** on an item that is already `blocked` but whose note is missing or does not parse on `origin/main`, `block` publishes the new note without moving the item (the recovery path; `audit` names it). The reason must equal the item's `blocked:` (a blocked item with no `blocked:` line takes the given reason), and a note on `origin/main` that does not parse is kept as `escalation-NNN.md`.
- One tracker commit on `origin/main`, `tracker: <id> blocked <reason>`:
  - an issue or a draft raft in `preparing`: status `blocked-…`, `blocked: <reason>`, and `escalation.md` added;
  - an `active` raft: the raft and every member still in `active/` move to the backlog stamped `blocked-…` with `blocked: <reason>`, with their `check.sh` paths rewritten back, as `./zn stop` moves them (its `moveOnOrigin`). A member already in `done/` stays there (c0248): the folder decides, since a landed member keeps the raft's claim stamp. `escalation.md` is added to the raft's folder. The raft's `prompt.md` and claim file are removed, and the main checkout is fast-forwarded, as `stop` does.
- It prints the parked branches and PRs, which are left as they are, as `stop` leaves them. It comments `BLOCKED: <reason>: <the question>` on the Layer's PR: it finds the Layer's branch with `layergit.layersOf` (unchanged) and runs `gh pr comment` on it. It skips the comment, with a warning, when the Layer has no PR yet, and a failed comment only warns (the PR is the visible record, zz-rules) and removes the worktree's copy of the note: main's copy is the note, and the next restack or sync brings it back.
- The green layers below the blocked one land before the block (Q1): c0248's `./zn done <R> --through <issue>`. z-work's worker runs it (outcome 6). Under `./zn dispatch` a step never runs `./zn done`: it blocks, and the dispatcher lands the layers below under c0252. After a tripwire nothing lands (outcome 6).

**4. Resolving: `./zn resolve <id> <decision> [--answer <text> | --answer-file <path>] [--said <text>] [--title <text>]`.**
- **Who** (Q5). Refused while `ZN_DISPATCH` or `ZN_HEADLESS` is set (c0253's headless loop sets `ZN_HEADLESS`, recorded on c0253): "resolve is the human's: a headless session is refused". Refused when the running CLI session is the note's `Session:`: an agent never resolves a block its own session filed. In an agent session (`provenance.hint(env).agent` with `ZN_DISPATCH` unset), `--said "<the user's message>"` is required, and it is recorded quoted as the user's word. A human in a terminal (no marker) needs none. No terminal test applies, because an interactive agent has no terminal. It runs in any checkout, the main one included, and publishes to `origin/main` itself.
- **Refused:** an item that is not `blocked` on `origin/main`; a decision outside the five; `split` without `--title`; `--answer` together with `--answer-file`; a `review-exhausted` resolve that leaves an id of the note's `Open:` without a `--rule <Fn>="<ruling>"`.
- **Rulings** (`review-exhausted`). `resolve` records each `--rule` in `## Resolution` (`Ruled F2: "<words>"`); in an agent session they are recorded as the user's word, with `--said`. It edits no document's open list: the list lives where it was written (a prep branch, a layer, the raft document). The next step runs `./zn rulings <id>` in its worktree, which writes `Ruled (user, <date>): <words>` under each bullet of the document's `## Open to the human` from the note's Resolution, and refuses a bullet with no recorded ruling. No agent writes a ruling of its own.
- **One tracker commit**, `tracker: <id> resolve <decision>`:
  - appends `## Resolution` to `escalation.md`: `Decision:`, `Answer:` (the text, or `none`), `By:` (c0263's live actor), `Said:` (the quoted words, in an agent session only) and `When:`;
  - removes `blocked:` and moves the status (table below);
  - appends c0263's `unblocked` row to the item's `provenance.md` (`provenance.record`, detail `decision=<d>` and, in an agent session, `said="<words>"`). It is the only row for this unblock: `resolve` never calls `status <id> new`, so c0282 adds none (c0282's Overlaps row);
  - leaves `rank:` as it is.

| decision | blocked from `preparing` (an issue or a draft raft) | blocked from `active` (a raft) |
|---|---|---|
| `retry` | `new`: its next design or rafting step reads the note with its resolution | `prepared`: the next `ready` resumes it at the blocked layer (c0248's `ready` skips landed members, and `start` reuses the parked layer's branch and PR) |
| `approve` | an issue: as `retry`, and the answer becomes a Decided line in the item's Problem; a draft raft: as `retry`, with the answer only in the Resolution | as `retry`, and the Decided line goes in the Problem of the member the note's `Layer:` names. That changes its approved contract, so `ready` refuses the raft until the user's own `./zn approve <member>` (Q8; #295's hash, c0283). `resolve` re-records that member's `grouped:` entry and every coherence review's `Grouped:` line for it, as compact and remap do (`keepRecords`): the change is the user's decision, so it gets no new raft-mode round |
| `amend-design` | an issue: `new` with `design: draft`, and z-design reads the note; a draft raft: as `retry` | the `Layer:` member leaves the raft (as `./zn unfold` takes it out) and goes to `new` with `design: draft`, with a copy of the note in its folder; the raft goes `prepared` with the rest |
| `split` | an issue: a new backlog issue of the item's type (as `./zn new`, `idea: unchallenged`), titled by `--title`, with the answer as its Problem; the item gains `Scope decision (user, <date>): "<the user's words>" (split into <new id>)` and then goes as `amend-design`. A draft raft: refused ("a draft raft has no design to split: resolve it amend-design, then split the issue in z-design") | the same on the `Layer:` member, which leaves the raft as in `amend-design` |
| `abort` | `new`: the claim is given back, as `status <id> new` | `prepared`, as z-stop leaves a raft; it prints the parked branches and PRs to close |

- **The Decided line's words** (Q5). In a terminal it quotes the answer: `Decided with the user (<date>), resolve approve: "<answer>"`. In an agent session it quotes `--said` and names the option: `Decided with the user (<date>), resolve approve: "<said>" (the option: <answer>)`. The line goes at the end of the document's `## Problem`; a document with no `## Problem` is refused, since the publish rule accepts the line only there.
- **A raft the Layer leaves.** When `amend-design` or `split` takes the Layer out and no unlanded member remains, the raft moves to `done/` if a member landed and to `retired/` if none did. Its whole folder moves to `<root>/rafts/done/<R>/` or `<root>/rafts/retired/<R>/` in the resolve's one commit, the only folder move a `blocked` or `resolve` commit may make. The moved `escalation.md` gains the resolution, and the moved `provenance.md` the `unblocked` row (only when the raft already has one: a moved folder gains no new file). The document loses `status:` and `blocked:`, and a retired raft gets `retired: emptied`. A member in `done/` is never touched by any decision.
- On a raft, the raft and every member it moved to the backlog carry `blocked:`, and a decision moves them together: each blocked member goes to `prepared` with the raft, except the `Layer:` member where its row says otherwise. The one `unblocked` row goes in the raft's `provenance.md`.
- The user's words in a `Scope decision` line are `--said` in an agent session and the answer in a terminal: only the user changes scope (z-design).
- After `retry`, `approve` or `amend-design`, the dispatcher's next run on the item re-runs the step with the note and its resolution (outcome 5).
