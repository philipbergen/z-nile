### F2 [high] "The re-run on any host reads it" has no design and no criterion: the resolution reaches the next step only on the host whose exchange still ends in the note's question
Where: c0250.md Problem (Decided prep Q1, "resolve carries it": "the re-run on any host reads it"), Design 4 decision table ("its next design or rafting step reads the note with its resolution"; "z-design reads the note"), Design 5 ("it copies the `## Resolution` as the answer wherever the chain resumes the item"), `## Open to the human` F1's Answer ("the resolution is in git and the re-run on any host reads it"); `experiments/prototype.patch:447-462` (`exchangeResolution`); AC8
Evidence: the only path from the note to a step is the exchange copy, and the prototype adds the answer only when `tail and tail.kind == "question"` (patch:454), that is, only in the `.cache/dispatch/<id>/exchange/` of the host whose dispatcher copied the note's question at the block. On another host, after `dispatch stop` or a cleared `.cache`, or for a block filed by an interactive z-work worker (no dispatcher, no exchange), the exchange is empty: nothing is copied, `dispatch.prompt` gets no exchange paragraph and names no `escalation.md`, and no skill sentence tells z-design, z-raft or zz-execute to read a resolved note in the item's folder (none of docs.spec's pins does; the prototype's skill edits add none). For `retry` the user's `--answer` lives only in the note (a Decided line is written only for `approve`), so a resolve such as `retry --answer "use the library"` is lost to the re-run. For a raft, `resolve retry` makes it `prepared`, and the worker that readies it again is a fresh session (it "clears its context"); nothing points it at the raft folder's note. Every AC8 case resumes on the same host with the exchange intact, so an implementation that never reads the note on a resume passes.
Critique: the tempting fix is "copy the resolution when the exchange is empty". c0256's `exchange.order` refuses an exchange that opens with an answer, and a question needs a `step:` line the note does not record.
Consequences: the note stays in the folder after its resolution is used (until the next block archives it), so the dispatcher must remember which resolution it already carried (or it copies it again on every resume). The question copied on a fresh host needs a step name: the step the chain resumes with is the honest one. An interactive step needs the instruction in its skill, since no exchange exists there.
Recommendation: (1) dispatcher: on a resume of an item whose `escalation.md` on origin/main holds a `## Resolution` the run has not carried (record the note's blob sha in the run state when it is carried), add the note's `## Question` first when the exchange does not end in it (with `step:` the step the chain resumes), then `answerText(resolution)`, and clear the last outcome as today; a note already carried is not added again. (2) z-design, z-raft and zz-execute (and z-work step 5's resume) say, pinned in docs.spec: "When the item's folder holds `escalation.md` with a `## Resolution`, read it before you start: it is the human's decision on the last block." (3) dispatch-block.spec case: after the resolve, remove `.cache/dispatch/c0010` (another host) and run `./zn dispatch c0010`: the exchange is `001-question.md, 002-answer.md`, the prompt says "The last file is an answer", and a second `./zn dispatch c0010` adds nothing. Add the rows (resolution carried on a fresh host; carried once) to Rules and mutants.
