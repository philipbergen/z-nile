### F2 [high] A resolved raft resumes through `z-ready`, so its z-run re-run is told the resolution settles another step's question, not its own
Where: c0250.md Design 5 ("the resolution reaches the next step on any host, once": (b) "adds the note's `## Question` as a question whose `step:` is the step being resumed"; "So c0256's prompt paragraph ... still hold"), Design 4 table (`retry` from `active`: `prepared`, "the next `ready` resumes it"), AC8; c0256.md item 5; c0256 `prototype.patch:555` (`exLastStep = st.history[#st.history].step`); main `dispatch.luau:466-476` (a backlog `prepared` raft routes to the script step `z-ready`, then `z-run`); `dispatcher.luau:1424` (`scriptStep` appends to `st.history`)
Evidence: dispatch-block's z-run case blocks R0010 (exchange `001-question.md`, `step: z-run`). After `./zn resolve R0010 retry` the raft is `prepared`, so `./zn dispatch R0010` runs `z-ready` (a script step, recorded in `st.history`), then `z-run`. At z-run's start c0256 computes `exchangeAsker = "z-run"` and `exchangeLastStep = "z-ready"`, so the prompt is not "This is a re-run ... the last file is an answer" but "Earlier steps of this run have already exchanged messages ... They settle those steps' questions, not yours: an approval there is not an answer to a question you must ask the user". For `resolve approve` that tells the model the opposite of the human's decision. On a fresh host it is worse: rule (b) writes the question with `step:` "the step being resumed", which for a backlog raft is `z-ready`, a script that never asks. No AC8 case resumes a raft (the z-run case stops after the block), so an implementation with this behaviour passes every case. The raft path is the main one for this reason list: `red-gate`, `quota` and `tripwire` are raft blocks.
Critique: the tempting fix is to make c0256's "ran last" ignore script steps. That changes a c0256 rule its sequestered `exchange.spec` and `retry.spec` pin ("a step that asked long ago, with something else run since, is not told it is a re-run"), and c0256's specs cannot change.

The question's `step:` must be the model step that resumes the item, which depends on the item: `z-run` for a raft blocked from `active`, `z-design` for an issue, `z-raft` for a draft raft (F3). A fixture whose chain runs `z-ready` needs a raft `ready` accepts under the dispatcher (its member approved, if `requireApproval` applies).
Recommendation: (1) the carried question's `step:` is the model step the item resumes with (`z-run` for a raft from `active`, `z-raft` for a draft raft, `z-design` for an issue), never a script step; (2) when the exchange's last two messages are the carried note's question and resolution (the run state's record), `modelStep` gives the prompt `exchangeLastStep = exchangeAsker` for that step, so it reads the re-run form ("The last file is an answer"); c0256's rule is unchanged for every other exchange.
