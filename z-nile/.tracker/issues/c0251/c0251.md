# c0251: Cross-model review pool with fallback

## Problem
A review by the same model that wrote the work shares its blind spots. Reviews should be heterogeneous. c0117 only fixes which model reviews per CLI (Opus through `claude` or `agent`, `grok-4.7-xhigh` through `grok`).

What should happen: `.models.toml` names a review pool; the dispatcher picks the first member whose model family differs from the author's recorded model and from the previous round's reviewer, so rounds rotate. Same-family review (Opus on Opus) is allowed but is only the fallback: it runs when no different-family CLI can (out of tokens or quota, CLI missing) and never blocks the chain. Every review records its model and whether it was a fallback; the board flags fallback reviews so the human can ask for a cross-model re-review. zz-review and the skills' "reviewer runs on Opus" rule change to match.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

## Solution
- A `family` key per model in `.models.toml`.
- A pure picker over (pool, author, prior reviewers, available CLIs).

Prep detail (2026-11-15): the per-model `family` key is a prefix table in `.models.toml`, by the user's ruling on design Q1 (a stamped or typed id that no toml entry names still maps to a family). The picker and its parts:
- `[families]` in `.models.toml`: a prefix table, family = model line (opus, fable, sonnet, haiku, kimi, grok, deepseek). The user edits it. `family.of(id)` is the one function that maps an id to a family.
- A pure picker `reviewpool.order` over (the role's tries, the author's writers, the previous reviewers, families). Three tiers: 1 differs from the author and the previous round; 2 differs from the author only; 3 is the author's family (the flagged fallback), its exact model last. A role opts in with `rotate = true`.
- `models.tries` no longer drops the author's model or stops: the exact author model is the last try of tier 3, so a review never blocks.
- A role's pool may hold several models on one CLI (Decided 2026-11-15, design Q5): `[member.<name>]` tables (cli, model, runtime) and a role key `pool = [names]`, kept beside `fallbacks`. `Resolved` gains an ordered list of specs; `order` and `specs` stay as the per-CLI view. Fable joins the design-challenge, raft and code-review pools.
- A new `[roles.stream-review]` on a cheap model (stream mode today borrows `code-review`), with `rotate = true`, away from the author's family; its second model is a cheap Sonnet member, and it has no CLI fallback until c0175 adds opencode. Authoring roles keep their order and gain cheap families as fallbacks when c0175 adds opencode.
- `Fallback: <reason>` stamped beside c0306's `Model:`/`Effort:`; the dispatcher (every mode, stream included), the idea stage (`./zn idea` stamps `idea-review-001.md`) and the interactive `spend`/`commit` write it; the board flags the newest round of a kind (design, code, final, idea, stream) when it carries one, with the route that works from where the item is worked; a flagged round is superseded by the next round in any item, marked or not (the cross-model re-review).
- `./zn dispatch zz-review <id> --mode <m> --dry-run [--author <model id>]` prints the pick for an interactive lead.
- The live author: `--author <model id>` on `./zn dispatch zz-review`, `./zn spend` and `./zn commit` (else `ZN_MODEL`, else the spend rows, else the writing role's first choice, shown as `assumed`) is the writer every pick and every derived stamp is made against.
- Pool members and rotation apply to review steps only: a step that authors on the same role (`z-raft` on `raft`) tries the role's model and then its fallbacks, as before.
- Skills, `.models.toml` comments and the README say it. AGENTS.md is c0332's, by the user's ruling (Scope decision in the Problem); c0251 does not touch it.

## Idea
A review by the same model family as the author shares its blind spots, so reviews should be heterogeneous. c0117 only fixes which model reviews per CLI.

- **A review pool.** `.models.toml` names a review pool, and each model has a family.
- **Sharpness from c0261, family from c0251** (Q1). c0261 says how sharp a round is: sharp for every final round (the idea review, the raft review, the final design and code review rounds, the full-force review) and cheap on the way. c0251 says which family runs it. A round takes the first pool member at its sharpness whose family differs from the author's recorded model and from the previous round's reviewer, so successive rounds rotate. A final round is drawn only from c0261's sharp kinds: any Opus; kimi's k3.1-pro or k3-256k at high or max; and grok at xhigh. Middle rounds rotate the same way among the cheap models. Which models may review through c0175's CLIs is c0175's (agy offers Opus, and kimi offers its kinds).
- **DeepSeek** (Q3). DeepSeek models, reached through opencode (c0175), are a cheap family in the rotation for middle rounds; c0175's review rule keeps them out of final rounds. Whichever of c0175 and c0251 lands second gives every model of agy, kimi and opencode its `family`.
- **Same family only as the fallback.** A same-family review (Opus on Opus) is allowed, but only when no different-family CLI can run it (out of tokens or quota, or the CLI is missing). It never blocks the chain.
- **Visible.** Every review records its model and whether it was a fallback. The board flags fallback reviews, so the human can ask for a cross-model re-review when tokens return.
- **The rules change to match.** zz-review's and the skills' "reviewer runs on Opus" rule changes, and so does every other place that states it, including AGENTS.md's pin of design and code reviewers to Opus 5.5 (the text c0293 rewrites). The README's "round one Opus" line follows c0261's cheap middle rounds (the user's 2026-11-08 scope decision), so the README stays true.

**R-vision stays one raft** (Q2): c0251 is its fourth layer.

Solution ideas from the capture: a `family` key per model in `.models.toml`, and a pure picker over the pool, the author, the prior reviewers and the available CLIs.

Not here: adding new CLIs (c0175: agy, kimi and opencode; c0142), changing what a reviewer looks for, how sharp each round is (c0261), and which models may review through the new CLIs (c0175).

## Design
**Prep choices (the user may veto each; every one below is mine except 5, which is Decided design Q5).**
1. A fallback is tier 3 only: the same family as the author. A try that runs after a quota or a missing CLI is not a fallback unless it is tier 3. Tier 2 (same family as the previous round's reviewer) is not flagged.
2. (Veto-able.) The previous reviewers are found like this. Take the stamped review files of every folder the review reads (an issue's folder; a raft's own folder as coherence rounds; each member's folder), and the highest lifecycle rank among them up to the kind being written (design 1, coherence 2, code 3, final 4). In each folder the newest round at that rank, by that folder's own numbering, is a previous reviewer; all of them count, each model once. Round numbers are never compared between folders: c0248 numbers each layer's reviews from 001. A refused, flagged or off-model round counts like any other stamped one, in any item, marked or not (c0306 stamps every review it files, and `spend`/`commit --model` stamp too). A stream review reads no priors. An idea review is not a prior either (rank 0): a design review rotates on the author only.
3. (Veto-able.) The author set for the tiers is the writers of the mode's last step (c0325 `Writer.step`): design for design, raft for raft, build for code, stream and final, idea for the idea challenge. For `final`, c0325's STEPS also lists idea and design; counting them would make Fable, Opus and Sonnet all "the author" and send every final review to kimi or grok. Provenance still covers all steps. A live author (choice 4) is the writer of that last step: for a final review it is the build's writer, not c0325's first step.
4. (Veto-able.) The live author and the interactive lead. The author a pick or a stamp is made against comes, in this order, from `--author <model id>` (on `./zn dispatch zz-review`, `./zn spend` and `./zn commit`, validated by `ledger.isModel`), `ZN_MODEL`, the spend rows, and the writing role's first choice (provenance `assumed`, named in the dry-run's `pool:` line and in a `Fallback:` reason). An interactive design or raft review has no row yet when it runs: `spend --phase prep` and the `raft-prep` row are written at the PR, after the review. So the lead gives its own model id. Without it the stamp is the honour system's: a Fable lead whose subagent is also Fable, who gave no `--author`, gets no flag (the assumed writer is the design role's Opus); a flag raised against an assumed writer says so. The tool derives the stamp: the lead types no reason. The lead may stay on a Claude subagent when the pick is not Claude (Q3), and the stamp is then derived. The plan the stamp uses is the dry-run's: the pinned walk of main; only when main cannot be read (no origin) does it read the checkout's `.models.toml` files, and the reason then ends "plan from the checkout's .models.toml".
5. (Decided, design Q5.) A role's pool may list several models on the same CLI, so an Opus-written design is picked to Fable first, on a Claude subagent, unflagged; kimi and grok follow, Opus last as the flagged fallback. Outcome 12 is the schema.
6. (Veto-able.) An unknown family never counts as different: a try with no family goes to tier 2 when the author is known, tier 1 when the author is unknown (nothing to differ from, no flag). A `rotate = true` role whose model, or whose pool member's or fallback's model, matches no family fails when the role is resolved for a review.
7. The fallback record is a stamped line `Fallback: <reason>` (one line, no newline, at most 120 characters), beside `Model:`/`Effort:`, within the first 12 lines. The reason names the cause and, when the author's provenance is `assumed` or `unknown`, says so.

**Outcomes.**

1. **Families.** `z-nile/engine/family.luau` (new, pure).
   ```luau
   export type Families = { [string]: { string } }   -- family -> id prefixes
   family.of(id: string, f: Families): string?        -- longest matching prefix of models.bareModel(id); nil when none
   family.same(a: string?, b: string?): boolean       -- both non-nil and equal
   ```
   `.models.toml` (root file, stacks like `[fallback.*]`; a closer file replaces only the family keys it sets):
   ```toml
   [families]
   opus = ["claude-opus-"]
   fable = ["claude-fable-"]
   sonnet = ["claude-sonnet-"]
   haiku = ["claude-haiku-"]
   kimi = ["kimi-"]
   grok = ["grok-"]
   deepseek = ["deepseek-"]   # reachable once c0175 adds opencode
   ```
   `models.parse` reads `[families]` into `Layer.families`; it refuses a non-list, an empty prefix, and a prefix listed under two families in one file. `models.families(layers): family.Families` merges the walk. `models.parse` also accepts `rotate = true|false` on a role (any other type is an error). The id check at load (`rotate = true` role whose model has no family) lives in `models.resolveRole`, so fixtures with no `[families]` and no `rotate` load as today. The captured "a `family` key per model" is replaced by the prefix table (design Q1), because a typed id like `claude-opus-5-5[1m]` and every id c0175 adds map without a `.models.toml` entry.

2. **The picker.** `z-nile/engine/reviewpool.luau` (new, pure).
   ```luau
   export type Tier = 1 | 2 | 3
   export type Pick = { spec: models.Spec, tier: Tier, exact: boolean, family: string? }
   export type Plan = { picks: { Pick }, authorFamilies: { string }, priorFamilies: { string }, provenance: string, walk: string? }   -- walk: "main" (the pinned walk) or "checkout"
   reviewpool.order(tries: { models.Spec }, families: family.Families, authors: { string }, priors: { string }): { Pick }
   reviewpool.fallbackReason(p: Pick, provenance: string, via: string): string?   -- nil unless p.tier == 3
   reviewpool.interactiveReason(plan: Plan, ran: string): string?                -- tier 3, or the first pick is not a claude- id and ran ~= it
   ```
   `order` is a stable partition: tier 1, then tier 2, then tier 3 with `exact == false` before `exact == true` (the exact bare model of a writer); the role's order inside each group. `authors` and `priors` are bare model ids; a family is "the author's" if it equals any author's family. No tier-3 pick is ever dropped, so the list is empty only when `tries` is. Availability (missing CLI, quota) stays the dispatcher's loop. `interactiveReason` ends its reason with `; plan from the checkout's .models.toml` when `plan.walk == "checkout"`.

3. **Previous reviewers.** `z-nile/engine/reviewfiles.luau` (c0306's, extended) gains `priors(folders: { { kind: string, dir: string } }, upto: number): { string }`: reads each folder's review files with `read(dir)` (the one reader), and returns the models of the previous round (prep choice 2): the stamped files of rank <= `upto` (`reviewmodel.RANK`: design 1, coherence 2, code 3, final 4), and in each folder the newest round at the top rank. It reads stamped files in any item, marked or not. A stream review and an idea review read no priors. Unstamped files are skipped.
