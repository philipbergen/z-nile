# c0251: Cross-model review pool with fallback

## Problem
A review by the same model that wrote the work shares its blind spots. Reviews should be heterogeneous. c0117 only fixes which model reviews per CLI (Opus through `claude` or `agent`, `grok-4.7-xhigh` through `grok`).

What should happen: `.models.toml` names a review pool; the dispatcher picks the first member whose model family differs from the author's recorded model and from the previous round's reviewer, so rounds rotate. Same-family review (Opus on Opus) is allowed but is only the fallback: it runs when no different-family CLI can (out of tokens or quota, CLI missing) and never blocks the chain. Every review records its model and whether it was a fallback; the board flags fallback reviews so the human can ask for a cross-model re-review. zz-review and the skills' "reviewer runs on Opus" rule change to match.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

## Solution

- A pure picker over (pool, author, prior reviewers, available CLIs).

Prep detail (2026-11-15, revised to the user's rulings of 2026-11-16): the per-model `family` key is a prefix table in `.models.toml`, by the user's ruling on design Q1 (a stamped or typed id that no toml entry names still maps to a family). The picker and its parts:
- `[families]` in `.models.toml`: a prefix table, family = model line (opus, fable, sonnet, haiku, kimi, grok, deepseek, composer). The user edits it. `family.of(id)` is the one function that maps an id to a family.
- A pure picker `reviewpool.order` over (the role's tries, the author's writers, the previous reviewers, families). Three tiers: 1 differs from the author and the previous round; 2 differs from the author only; 3 is the author's family (the recorded fallback), its exact model last. A role opts in with `rotate = true`.
- `models.tries` no longer drops the author's model or stops: the exact author model is the last try of tier 3, so a review never blocks.
- A role's pool may hold several models on one CLI (Decided 2026-11-15, design Q5): `[member.<name>]` tables (cli, model, runtime) and a role key `pool = [names]`, kept beside `fallbacks`. `Resolved` gains an ordered list of specs; `order` and `specs` stay as the per-CLI view. Fable joins the design-challenge, raft-review and code-review pools.
- Any model may run any review (user, 2026-11-16): c0306's fixed list of review models is removed, and the one quality rule is the frontier floor below.
- The frontier floor (user, 2026-11-16): `[review] frontier = [...]` in `.models.toml` is an editable list of models, and every landing (`./zn done`, `done --through`, the dispatcher's) needs one code or final review of the landed code by a model on it. A pure `frontier.check` gives the verdict and the problem code `no-frontier-review` (c0252's `landcheck` calls it); a person's `done` is refused naming it; the dispatcher runs one extra review round, `./zn dispatch zz-review <id> --mode final --frontier`, on a frontier model before it lands, and waits (exit 6) while no frontier model has quota.
- The author is recorded, never assumed or typed (user, 2026-11-16): a design's or raft's writer is its document's `designed-by: <model id>` front-matter line (a list once another model revises it; the tool writes it under dispatch, the lead interactively; a design or raft review of a document without it is refused), and the code's writers are the build rows c0325 records. It is a record for the stats: no board flag and no cross-model re-review (Scope decision, 2026-11-16).

## Idea
A review by the same model family as the author shares its blind spots, so reviews should be heterogeneous. c0117 only fixes which model reviews per CLI.

- **A review pool.** `.models.toml` names a review pool, and each model has a family.
- **Sharpness from c0261, family from c0251** (Q1). c0261 says how sharp a round is: sharp for every final round (the idea review, the raft review, the final design and code review rounds, the full-force review) and cheap on the way. c0251 says which family runs it. A round takes the first pool member at its sharpness whose family differs from the author's recorded model and from the previous round's reviewer, so successive rounds rotate. A final round is drawn only from c0261's sharp kinds: any Opus; kimi's k3.1-pro or k3-256k at high or max; and grok at xhigh. Middle rounds rotate the same way among the cheap models. Which models may review through c0175's CLIs is c0175's (agy offers Opus, and kimi offers its kinds).
- **DeepSeek** (Q3). DeepSeek models, reached through opencode (c0175), are a cheap family in the rotation for middle rounds; c0175's review rule keeps them out of final rounds. Whichever of c0175 and c0251 lands second gives every model of agy, kimi and opencode its `family`.
- **Same family only as the fallback.** A same-family review (Opus on Opus) is allowed, but only when no different-family CLI can run it (out of tokens or quota, or the CLI is missing). It never blocks the chain.
- **Visible.** Every review records its model and whether it was a fallback. The board flags fallback reviews, so the human can ask for a cross-model re-review when tokens return.
- **The rules change to match.** zz-review's and the skills' "reviewer runs on Opus" rule changes, and so does every other place that states it, including AGENTS.md's pin of design and code reviewers to Opus 5.5 (the text c0293 rewrites). The README's "round one Opus" line follows c0261's cheap middle rounds (the user's 2026-11-08 scope decision), so the README stays true.

**R-vision stays one raft** (Q2): c0251 is its fourth layer.

Solution ideas from the capture: a `family` key per model in `.models.toml`, and a pure picker over the pool, the author, the prior reviewers and the available CLIs.

Not here: adding new CLIs (c0175: agy, kimi and opencode; c0142), changing what a reviewer looks for, how sharp each round is (c0261), and which models may review through the new CLIs (c0175).

11. **The frontier floor.** `z-nile/engine/frontier.luau` (new, pure; the one place the rule lives).
    ```luau

    export type Verdict = { met: boolean, code: string?, problem: string?, listed: { string } }
    frontier.CODE = "no-frontier-review"
    frontier.listed(model: string?, effort: string?, list: { string }): boolean   -- bare model id equals an entry; an <id>@<effort> entry needs that effort
    frontier.seenIn(files: { [string]: string }): { Seen }                       -- the code (review-NNN) and final (final-review-NNN) reviews of a folder; never a design, coherence, stream or idea review
    frontier.check(seen: { Seen }, list: { string }): Verdict                    -- met when one listed review is among them (anywhere in the landing); an empty list sets no floor
    models.frontier(layers): { string }          -- the closest file's [review] frontier, replaced whole; {} when none sets it
    reviewfiles.frontierVerdict(dirs: { string }, list: { string }): frontier.Verdict   -- reads the folders of a landing and calls check
    ```

### Scalability
- The picker is a stable partition over at most a handful of tries (one per CLI plus the members) and a few ids; the prior read is one `read(dir)` per folder the review already reads (a raft of 10 members is 11 folders of small files). The floor reads the same folders once at `done`. Adding a model line (c0175's agy, opencode) is one `[families]` entry, no code; adding a frontier model is one list entry. Adding a CLI or a new family needs no change in `reviewpool` or `frontier`.

### Maintainability
- One mapping from id to family (`family.of`), one tier function (`reviewpool.order`) shared by the run, the dry-run, the idea path and the interactive stamp, one stamp reader (`reviewmodel.fallbackOf`), one reader of the writer's line (`designedby.of`), one floor function (`frontier.check`) shared by `done` and c0252. The user's families, the frontier list and the stream list live in the toml, not in code (unlike c0306's `KINDS`, which this layer removes). The tier rule replaces three restatements of "never the model that wrote it" (zz-review, z-raft, the `models.tries` error).

### Usability
- The human edits tables to change what counts as the same family, what counts as a frontier model, and the stream list. A design or raft review of a document with no `designed-by` line is refused with the line to add; the lead writes one line, and under dispatch nobody does. An interactive lead runs one command and starts the first `pick:`. A landing with no frontier review is refused naming the one command that clears it, and the dispatcher runs that command itself and waits for quota. The dry-run and `fallback:` stderr line say why.
