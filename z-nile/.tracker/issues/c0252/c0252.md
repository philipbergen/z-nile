# c0252: Dispatcher merges a green PR autonomously

## Problem
c0117's chain stops at a merge as a human gate. For autonomous delivery the dispatcher itself should merge a layer (c0248) once its own checks pass: CI green, the layer below merged, the full gate run once at the merge, review approved with no open high finding, no regression, and `main` moved only by tracker-only commits (c0152). The agents' bot credential still cannot merge; only the dispatcher merges, with its own credential.

What should happen: the dispatcher merges layers bottom-up, retargets the next layer, and escalates (`blocked`, c0250) instead of merging when a check fails.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

## Idea
c0117's chain stops at a merge as a human gate. Without a human, the chain should go all the way to the merge (c0261: "c0252 builds it"). A raft's stack lands once the dispatcher's checks pass.

- **What lands** (Q1, Q4). A raft's stack (c0248) lands as one `--no-ff` bind of its top layer (#296's `./zn done`), with the full gate run once on that top, once every layer is complete: green on the layer below. The captured "the dispatcher merges layers bottom-up and retargets the next layer" becomes this bind.
- **A block lands what is below it** (Q3). When a layer blocks, the green layers below it land now as a shorter bind, with one full gate on the top green layer. The blocked layer and the layers above it wait for the resolve.
- **The preconditions.** CI green, every layer in the bind complete, the full gate run once at the merge, the review approved with no open high finding, no regression, and `main` moved only by tracker-only commits (c0152). The preconditions are one pure function over the PR state, and each check is a named reason in the escalation.
- **One lander, with the dispatcher's credential** (Q2, Q5). `./zn done` stays the one command that lands a stack, and the `./zn merge` of Q2 is this `done`. It checks the preconditions and pushes `main` with the dispatcher's credential wherever it runs: in a z-work worker, started by a person or headless, or in the user's own `/z-run`. An agent's own credential never merges.
- **A failed check escalates.** When a check fails, the item goes `blocked` (c0250) instead of merging.
- **The README** (the user's 2026-11-08 scope decision). Its Autonomous delivery line, which says an item is designed, reviewed and merged "with no human in the loop", says that a worker drafts the design and a person approves it, and that a person rafts (c0253's Q1), so the README stays true. The approval gate the scope decision asks for exists: #295's `./zn approve`, with `ready`'s refusal without it, and c0283's refusal of `prepared` without it. c0252 adds no gate of its own.

**R-vision stays one raft** (Q6): c0252 is its fifth layer.

Not here: branch protection on GitHub itself (a step for the user), merging anything that is not a z-nile raft's stack, and the design-approval gate (#295, c0283).

## Design
The dispatcher lands a raft's finished stack by running `./zn done` itself, after one pure check of everything the Problem lists and, for a game, the clean-clone gate. The merge is `./zn done` (the Idea, Q5: one lander for all), run by the dispatcher in the raft's own worktree with its own environment and the user's credential, and judged and performed by the **base's** engine (the main checkout's, `./zn -C <worktree> …`), never by the stack's own `zn`. The agents' credential still cannot merge: `done` in a session that holds it runs every check and leaves a land request for a lander (the dispatcher, or a person's `./zn lander`) instead of pushing. Everything below was prototyped on `proto-c0252-rulings` (`proto-c0252`, which is `proto-c0251` + `proto-c0250` + `proto-c0248` + `origin/main`, merged with `proto-c0251-rulings`, the revised c0251; see Unknowns); the prototype's specs are this issue's `acceptance/` folder. Under the user's 2026-11-16 rulings the stack also lands only with a frontier review (c0251's floor), and the dispatcher runs the one extra round that provides it (outcomes 1, 3, 5, 6 and 8, G14 and G15).

### Scalability

### Maintainability

## Acceptance criteria

### Checked
- AC1: `landcheck.problems` returns one named problem, with its kind (wait, redo, block or review) and escalation reason, for each failed check: a layer not built or not complete, a final review with no Verdict or not answered, an unruled high finding, a stale trace, approval drift, a landing with no review by a frontier model (AC22), a stack that changes the gate's own driver, a game stack with no `cicd.toml`, a red or waiting clean-clone gate, and a top-layer pull request that is unreadable, closed or merged, in a state it does not know, whose head is not the layer tip, with no check registered, with a check failed, cancelled or still running, or (when it is not a draft) conflicting or with an unknown mergeable; a read that failed (git, the registry) is a wait; a clean input, and a draft layer whose only check was SKIPPED, give none; tracker state is told from code by `trackerstate`, the one definition.
- AC2: `landcheck.classify` lands a clean input, blocks a block problem at once, lets a wait wait and never block, reads a problem kind it does not know as a wait, and runs the worker again on a redo problem (a red check included) until `merge_retries` repeats of the same failure are spent, then blocks under that problem's reason; a redo outranks a wait, and a worker that changes the failure's codes or the top tip starts the count again.
- AC3: The `escalation.md` the dispatcher files for a block is a note `escalation.parse` and `escalation.check` accept and names every problem, with the one option each code recommends (`approve` for an unruled high finding and approval drift, `retry` for the rest, never `amend-design`); `landcheck.findBind` finds the bind on main's first-parent line among tracker commits and refuses a missing or doubled one; a block request round-trips with the Layer's tip and a malformed one is refused.
- AC4: "Green" is read from the pull request's rollup: SUCCESS, NEUTRAL and SKIPPED pass, failed (cancelled, timed out, startup failure included) and still-running (stale and unknown states included) checks are named, and a pull request text that cannot be read, an empty rollup or a missing state is a named failure, never green.
- AC5: `dispatch.next` on an active raft lands a finished raft whose checks pass (through the layer the verdict names), stops at the gate (exit 4) when `run` is not in `auto_merge` or a check is pending, runs `z-run` again as a counted try for a fixable problem and tells that rerun which checks it runs for, files a block for a block verdict, lands the green layers below a requested block first and then files it, waits at the gate with the request kept while those layers' CI runs, never lands a red prefix, and keeps an old single-branch raft's pull request and a human's merge.
- AC6: `z-land`, `z-block`, `z-gate` and `z-commit` are script steps run in the raft's own worktree; `models` accepts `run` in `auto_merge` (and still refuses any other word) and reads `merge_retries` (default 2) and the rerun cap, and no longer knows `merge_attempts`.
- AC7: `./zn land-check <R-id> [--through <issue> | --below <issue>] [--json]` reads a real raft: a pending check is a wait, a failed one a redo, an unreadable pull request, a head that is not the layer tip, a conflict, a check not yet registered and a mergeable GitHub is still computing are named, a draft layer whose only check was skipped and a green top layer pass with exit 0, `--below` judges the layers under a Layer on their own top, and a raft with no layer branches gets an explicit no-layers answer (exit 2).
- AC8: `./zn done` in a session that holds the agent's credential (`ZN_DISPATCH` or `ZN_HEADLESS`) runs every check, writes a land request and pushes nothing, and refuses a failed check there too; in a person's session it refuses every problem the dispatcher would not land on for a person, a wait included (CI running, no check registered, GitHub still computing, a pull request it cannot read), naming the codes and changing nothing, and lands a stack whose top layer is green.
- AC9: Under `ZN_DISPATCH`, `./zn block` on a raft checks the reason and the note as before, then writes `block-request` (with the Layer's published tip) and a copy of the note in the dispatcher's state folder and publishes nothing.
- AC10: `./zn dispatch <R-id>` lands a finished raft whose top layer is green with the dispatcher's own environment (the user's credential, no `ZN_DISPATCH`, no `ZN_HEADLESS`): one `--no-ff` bind on `origin/main`, the raft in `done/`, exit 0, and a second run finds it done.
