# c0252: Dispatcher merges a green PR autonomously

## Problem
c0117's chain stops at a merge as a human gate. For autonomous delivery the dispatcher itself should merge a layer (c0248) once its own checks pass: CI green, the layer below merged, the full gate run once at the merge, review approved with no open high finding, no regression, and `main` moved only by tracker-only commits (c0152). The agents' bot credential still cannot merge; only the dispatcher merges, with its own credential.

What should happen: the dispatcher merges layers bottom-up, retargets the next layer, and escalates (`blocked`, c0250) instead of merging when a check fails.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

Scope decision (user, 2026-11-08): "humans approve the design, humans interact (plan mode) over the idea". c0264's Design: the README's Autonomous delivery line says an item is designed, reviewed and merged "with no human in the loop"; this issue must reword it to "a worker drafts, a person approves" and add a person-approval gate, so the README stays true.

Decided with the user (2026-11-11), idea interview Q1: "Green on the layer below" (a layer is complete when it is built, reviewed, full-force reviewed (c0262) and green on top of the layer below, not merged; only then the next layer starts, and the stack lands at the end with one full gate on its top).

Decided with the user (2026-11-11), idea interview Q3: "They merge now" (when a layer blocks, the green layers below it land now, with one full gate on the top green layer; the raft is blocked at that layer and resumes there after the resolve).

Decided with the user (2026-11-11), idea interview Q4: "#296's one bind" (the stack lands with one `--no-ff` bind of its top layer (#296's `./zn done`), with one full gate on its top; a block lands the green layers below it as a shorter bind (the prefix 1..k-1); the captured 'layers merge bottom-up, each retargeted to main as the one below merges' is replaced).

## Idea
c0117's chain stops at a merge as a human gate. Without a human, the chain should go all the way to the merge (c0261: "c0252 builds it"). A raft's stack lands once the dispatcher's checks pass.

- **What lands** (Q1, Q4). A raft's stack (c0248) lands as one `--no-ff` bind of its top layer (#296's `./zn done`), with the full gate run once on that top, once every layer is complete: green on the layer below. The captured "the dispatcher merges layers bottom-up and retargets the next layer" becomes this bind.
- **A block lands what is below it** (Q3). When a layer blocks, the green layers below it land now as a shorter bind, with one full gate on the top green layer. The blocked layer and the layers above it wait for the resolve.
- **The preconditions.** CI green, every layer in the bind complete, the full gate run once at the merge, the review approved with no open high finding, no regression, and `main` moved only by tracker-only commits (c0152). The preconditions are one pure function over the PR state, and each check is a named reason in the escalation.
- **One lander, with the dispatcher's credential** (Q2, Q5). `./zn done` stays the one command that lands a stack, and the `./zn merge` of Q2 is this `done`. It checks the preconditions and pushes `main` with the dispatcher's credential wherever it runs: in a z-work worker, started by a person or headless, or in the user's own `/z-run`. An agent's own credential never merges.
- **A failed check escalates.** When a check fails, the item goes `blocked` (c0250) instead of merging.
- **The README** (the user's 2026-11-08 scope decision). Its Autonomous delivery line, which says an item is designed, reviewed and merged "with no human in the loop", says that a worker drafts the design and a person approves it, and that a person rafts (c0253's Q1), so the README stays true. The approval gate the scope decision asks for exists: #295's `./zn approve`, with `ready`'s refusal without it, and c0283's refusal of `prepared` without it. c0252 adds no gate of its own.

**R-vision stays one raft** (Q6): c0252 is its fifth layer.

Not here: branch protection on GitHub itself (a step for the user), merging anything that is not a z-nile raft's stack, and the design-approval gate (#295, c0283).

## Design
The dispatcher lands a raft's finished stack by running `./zn done` itself, after one pure check of everything the Problem lists. The merge is `./zn done` (the Idea, Q5: one lander for all), run by the dispatcher in the raft's own worktree with its own environment and the user's credential; the agents' credential still cannot merge, and `done` is refused for a dispatched step. Everything below was prototyped on `proto-c0252` (`proto-c0251` + `proto-c0250` + `proto-c0248` + `origin/main`, see Unknowns); the prototype's specs are this issue's `acceptance/` folder.

### Outcomes
1. **`z-nile/engine/landcheck.luau` (new, pure, `--!strict`).** `landcheck.problems(i: Input): { Problem }` returns one named problem per failed check; `landcheck.classify(ps, tries, cap): Verdict` says what the chain does; `landcheck.escalation(ps, raft, layer, tries): string` is the `escalation.md` body; `landcheck.ownBind(parents, topTip): boolean`; `landcheck.requestText` / `parseRequest` (the block request); `landcheck.isTracker`, `codeOf`, `touchesGame`, `checks`, `lines`. The name avoids `mergecheck` (c0152's prep uses it). Types: `Kind = "wait" | "redo" | "block"`; `Problem = { code, kind, text, reason, layer? }` (`reason` is an `escalation.REASONS` word); `Input = { raft, layers: { { issue, incomplete? } }, through?, topIssue, topTip, pr: Pr?, prError?, reviewProblem?, openHigh, traceProblems, approvalDrift?, verdictMissing, codeMoved, changedPaths, gameRoots, cicd }`; `Verdict = { action: "land" | "wait" | "redo" | "block", problems, reason?, layer? }`. The codes, with kind and reason: `layer-incomplete` (redo, design-gap), `no-verdict` (redo, review-exhausted), `open-high` (block, review-exhausted), `review-open` (redo), `trace-stale` (redo), `approval-drift` (block, needs-decision), `main-moved` (redo, red-gate), `cicd-missing` (wait), `pr-unreadable` (wait), `pr-closed` (block, needs-decision), `pr-head-moved` (redo, red-gate), `ci-failed` (block, red-gate), `ci-pending` (wait), `pr-conflicting` (redo, red-gate). "Green" on the top layer's head is: no failed and no running check on a head equal to the layer tip, `SUCCESS`, `NEUTRAL` and `SKIPPED` passing (a draft layer's `deploy` workflow is skipped, so CI alone proves nothing about a draft, and the static stages and the gate run by the landing itself, `done`'s affected gate and the author's `finish`, carry the proof until c0359's `static` workflow gives the rollup a meaning). `classify`: no problem lands; a `block` problem blocks at once under its reason; a `redo` problem runs the worker again until `tries >= cap`, then blocks under its own reason; otherwise a `wait` waits, and a `redo` outranks a `wait`.
2. **The edge, `z-nile/engine/landread.luau` (new, reads only) and `./zn land-check`.** `landread.parsePr(text): (Pr?, why?)` reads `gh pr view <layer branch> --json state,isDraft,headRefOid,mergeable,statusCheckRollup` (a text it cannot read is a named failure, never green); `landread.pr(branch)` runs gh; `landread.diffNames(a, b)`. `./zn land-check <R-id> [--through <issue> | --below <issue>] [--json]` (read-only, in the `READ_ONLY` set and the usage text) builds the `Input` in `H.landInput` (main.luau, a field of the `H` table because the file is at Luau's 200-local limit) from `layergit.layersOf`, `layergit.completeReason`, `reviewProblem`, `traceProblems`, `approval.refusal`, the raft document's open list and the paths main gained since the stack's fork (`git merge-base origin/main <tip>`), prints one `code (kind): text` line per problem (or JSON with `through`, `top`, `tip` and the problems) and exits 1 when any. `--below <issue>` is the layers under a Layer: the last unlanded member before it, judged on its own top; with nothing below it prints nothing to land.
3. **The dispatcher's step.** `dispatch.STEPS` gains `z-land` (`argv = { "done", "{id}" }`, `where = "run"`) and `z-block` (`{ "block", "{id}" }`); `where = "run"` is the raft's own worktree (`worktree(ctx, id)`, where z-run ran), not the rafting worktree `raft-<id>`. `Action.kind` gains `"land"` (`target`, `through?`, `tip`) and `"block"` (`reason`, `layer?`); a step action may carry `redo = true`. `Facts` gains `layered`, `land: LandFacts?` (`action`, `through?`, `tip?`, `lines`, `problems`, `reason?`, `layer?`, `tries`) and `blockRequest`. `dispatch.next` on an active raft: a block request first (the prefix lands when its verdict is `land` and `auto_merge` names `run`, else the block is filed at once); an old raft with an open, non-draft pull request keeps `gate(f, "run", pr)` (a human's merge); a verdict of `land` lands (or stops at exit 4, "ready to land … leaves the landing to a human", when `run` is not in `auto_merge`), `wait` stops at the gate (exit 4) with the reasons, `redo` runs `z-run` again as a counted try, `block` files a block; with no verdict the worker runs.
4. **The stale pull-request lookup.** `dispatcher.facts` looked up an active raft's pull request by the pre-#296 branch `{id}-{slug}`, which a layered raft never has, so nothing ever landed it. For a layered raft it now looks up nothing (the landing reads the top layer's pull request itself), and the old name stays for an old single-branch raft. The old stop "z-run ended but the PR is still a draft" is for that old raft only.
5. **The landing.** The chain's `land` action checks out the layer tip in the raft's worktree (`done` refuses any other commit), moves a pending `escalation.md` aside (a requested block's note; `done` needs a clean tree) and puts it back, runs `z-land` (`./zn done <R> [--through <issue>]`, the dispatcher's own environment), then `dispatcher.afterLand(ctx, tip)` (outcome 7), `landTries = 0`, `./zn sync` and `./zn watch-kick`. A failed `done` rolls back as it always does; the chain stops with exit 1 and `./zn dispatch retry <R>`.
6. **The escalation through c0250.** The `block` action writes `landcheck.escalation(...)` as `escalation.md` in the raft's folder of the raft worktree (when a worker's note stands, because it asked, it is kept), then runs `z-block` (`./zn block <R> <reason> [--layer <issue>]`), removes the request and syncs; the next pass stops with exit 3 on the blocked raft. The note is the four sections c0250's parser requires, every problem under "Open findings or error", and exactly one `(recommended)` option: `approve` when a person must rule (`open-high`, `approval-drift`), `retry` after a capped fixable problem, else `amend-design`. A capped `redo` counts: `State.landTries` is incremented when a `redo` action runs the worker and reset by a landing or a block.

## Acceptance criteria

### Checked
- AC1: `landcheck.problems` returns one named problem, with its kind (wait, redo or block) and escalation reason, for each failed check: a layer not complete, a final review with no Verdict or not answered, an unruled high finding, a stale trace, approval drift, code gained by `main` since the stack's base (tracker state gained is not), a game stack with no `cicd.toml`, and a top-layer pull request that is unreadable, closed, whose head is not the layer tip, that conflicts, whose check failed or is still running; a clean input, and a draft layer whose only check was SKIPPED, give none.
- AC2: `landcheck.classify` lands a clean input, blocks a block problem at once, lets a wait wait and never block, and runs the worker again on a redo problem until `merge_attempts` tries are spent and then blocks under that problem's reason; a redo outranks a wait.
- AC3: The `escalation.md` the dispatcher files for a block is a note `escalation.parse` and `escalation.check` accept, with one recommended option and every problem named; `landcheck.ownBind` accepts only a merge whose second parent is the layer tip; a block request round-trips and a malformed one is refused.
- AC4: "Green" is read from the pull request's rollup: SUCCESS, NEUTRAL and SKIPPED pass, failed and still-running checks are named, and a pull request text that cannot be read is a named failure, never green.
- AC5: `dispatch.next` on an active raft lands a finished raft whose checks pass (through the layer the verdict names), stops at the gate (exit 4) when `run` is not in `auto_merge` or a check is pending, runs `z-run` again as a counted try for a fixable problem, files a block for a block verdict, lands the green layers below a requested block first and then files it, never lands a red prefix, and keeps an old single-branch raft's pull request and a human's merge.
- AC6: `z-land` and `z-block` are script steps run in the raft's own worktree; `models` accepts `run` in `auto_merge` (and still refuses any other word) and reads `merge_attempts` (default 2).
- AC7: `./zn land-check <R-id> [--through <issue> | --below <issue>] [--json]` reads a real raft: a pending check is a wait, a failed one a block, an unreadable pull request, a head that is not the layer tip and a conflict are named, a green top layer passes with exit 0, and `--below` judges the layers under a Layer on their own top.
- AC8: `./zn done` is refused while `ZN_DISPATCH` is set, refuses a stack whose top layer has a failed check (naming the code, changing nothing), and goes on past a check that is still running, which is a person's to judge.
- AC9: Under `ZN_DISPATCH`, `./zn block` on a raft checks the reason and the note as before, then writes `block-request` in the dispatcher's state folder and publishes nothing.
- AC10: `./zn dispatch <R-id>` lands a finished raft whose top layer is green: one `--no-ff` bind on `origin/main`, the raft in `done/`, exit 0, and a second run finds it done.
- AC11: The chain stops at the gate (exit 4) with the reason on a pending check and lands nothing; it blocks at once on a failed check; on a fixable problem it runs the worker again twice and then blocks under the problem's reason; each block files an `escalation.md` that parses and names the problems, and the chain exits 3.
- AC12: A block the worker requests lands the green layers below the Layer first (`done --through`), then files the block, and the raft is left blocked with the worker's own note.
- AC13: zz-rules, zz-execute, every headless skill section, the README, the root `.models.toml` and the step prompt say that the dispatcher lands a green stack with `./zn done` after its checks, that `done` is refused for a worker, and that a worker's block is a request.
- AC14: After the dispatcher's own bind the guard's mark moves to it (`dispatcher.afterLand`), so the next `vetMain` is clean; a main tip that is not that bind, and a foreign commit, still trip it.
- AC15: The promoted specs of the dispatcher, the models, the wrapper guards, `done`, the loop rules and the skills' shared sections still pass (the fast ones; the slow ones are named in Implementation steps).
