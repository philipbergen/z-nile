### F1 [high] The dispatcher's landing is judged and performed by the branch's own engine, run with the user's credential
Where: Design outcome 3 and G2 (`where = "run"`); prototype `dispatcher.landFacts` (`zn(wt, args)` runs `{wt}/zn land-check`) and `dispatcher.scriptStep` (`process.exec(`{dir}/zn`, ...)` for `z-land`).
Evidence: `local function zn(dir, args) ... process.exec(`{dir}/zn`, args, { cwd = dir })` with `dir = worktree(ctx, id)`. That is the raft's worktree, checked out on the top layer that the worker wrote. So the `zn` script, `main.luau`'s `done` and `H.landInput`, `landcheck.luau`, `z-nile/check.sh` and `affected.luau` that decide and perform the landing are the stack's own versions. The step runs with the dispatcher's environment: the user's credential and no wrapper. Take a raft whose layer changes `landcheck.classify` (the next landing check, the Maintainability section says, is "one more `landcheck.problems` branch") and introduces a bug that maps `block` to `land`, or a layer whose `affected.luau` selects nothing. That raft is judged by its own bug and pushed to `main` by its own `done`, with no person in the loop.
Critique: zz-arch rule 7 says configuration that widens a guard is read from `origin/main`, never from the working tree a branch can edit. The prep and raft gates follow that rule: the dispatcher's own code judges the PR head it pinned. The new `run` gate does not. zz-rules says the guards are not a boundary against a determined agent. This case needs no determined agent: an honest bug in a tooling raft is enough, and most of this repository's rafts are tooling rafts. It is also the indirect path by which the agent's work reaches the merge: the agent writes `zn`, and the dispatcher runs it as the user. The tempting fix is "run `{mainRoot}/zn`". But `zn` binds the engine to the checkout it lives in (only `work` reads another worktree), so done would act on the main checkout.
Consequences: (a) `zn`/the engine needs a mode, like `work`'s, that runs the main checkout's engine (`origin/main`'s code, which only fast-forwards) against the raft's worktree for `land-check` and `done`. (b) A stack that changes a format `done` reads (c0248's `trace-NNN.md`, review names, the layer shape) is then judged by the older engine and may be refused. That stack needs one landing by a person, and the user should hear that. (c) The gate on the merged tree still runs the merged tree's specs, as CI runs a PR's code. The gate's driver (`z-nile/check.sh`, `affected.luau`, `tests/run.luau`, `specs.luau`) must either come from `origin/main` too, or a stack that changes those paths is a named `wait` (`self-gating`) for a person.
Recommendation: Run `land-check` and `done` for the dispatcher with the engine of the main checkout, pointed at the raft's worktree, and say so in outcome 3, G2 and zz-rules Dispatch. Add a land-chain case in which the top layer commits a `landcheck.luau` whose `problems` returns `{}`, the pull request's check is `FAILURE`, and the chain still files `ci-failed` (exit 3). Add a Rules row for "the landing's judge is `origin/main`'s code". Decide (b) and (c) with the user, listing the paths that make a stack self-gating.

### F8 [medium] A rerun worker is not told why it runs again, and a run that ended mid-raft counts as a failed try
