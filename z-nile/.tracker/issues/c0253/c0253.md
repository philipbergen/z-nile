# c0253: Worker pull loop: zn work

## Problem
There is a dispatcher that chains steps for one item, but nothing that takes the next ticket from the stack and keeps going. `./zn work` should wrap any supported AI CLI (claude, agent, grok, as `.models.toml` lists them), headless, and loop: `./zn next`, claim, run the item's next step in its own worktree with the model the file names, record spend, repeat, until the stack is empty or every remaining item is blocked. It runs on the engineer's host or another.

What should happen: `./zn work [--cli <name>] [--once] [--max-items N]`, graceful stop, a lock so one worker does not run twice for the same item, and a summary of what it moved and what it blocked.

Part of the z-nile vision (z-nile/README.md, section How it should work). To be delivered in the raft **R-vision** as one **stacked PR set**, one layer per ticket in this order: c0248, c0249, c0250, c0251, c0252, c0253, c0254.

User (2026-11-07): "I want this Z-NILE system to work in the following way, manually start any cli (kimi, agy, claude, grok, agent, deepseek) run a command, z-work. That command will make this agent pick up a raft and move it forward. The goal is to move all human interaction up to the idea and design stages and then have these workers carry it all the way. we want the agent instances to stay with a particular raft all the way to merge. Only if it is blocked would it let go, at which case it marks the raft blocked and clears its context and grabs the next raft."

User (2026-11-07): "Also explicitly state that a worker clears itself and picks up the next raft whenever a raft is merged."

Added by the user (2026-11-07):
- **Manual start, any CLI.** A person starts any CLI by hand (kimi, agy, claude, grok, agent, deepseek) and runs **z-work**. That agent becomes a worker. The headless `./zn work` above is the same worker launched without a person. A CLI that can't read skills gets the same instructions printed by a `./zn` command.
- **A raft, not a step.** The worker picks up a raft: the first claimable one in the order (c0249), with lost work first (c0265). It moves the raft forward and stays with it all the way to merge, as a PR stack, one ticket at a time (c0248).
- **It lets go only when blocked.** Then it marks the raft blocked (c0250), clears its context and grabs the next raft.
- **A worker clears itself whenever a raft ends.** When the raft is merged, or released because it is blocked, the worker clears its context and picks up the next raft. Context stays only within one raft.
- **It beats** (c0265) every 5 minutes while it holds a raft.
- **It is cheap** (c0261): the worker itself never orchestrates or waits on an expensive model.
- An agent can't clear its own context in every CLI, so design settles how the clearing happens. One option is a cheap supervisor that runs each raft in a fresh CLI session.

## Idea
The goal is to move all human interaction up to the idea and design stages, and have workers carry the rest all the way to merge. There is a dispatcher that chains steps for one item, but nothing takes the next raft from the stack and keeps going.

- **Manual start, any CLI** (Q8). A person starts any supported CLI by hand and runs **z-work**. That session starts the supervisor, `./zn work`, which runs each raft in a new headless session of the same CLI. How the supervisor runs is an option (Q12), with no default picked yet (Q13: the design proposes one for the user to approve). Started detached, it outlives the person's session (the session-end reaper and `./zn reap` leave it running), `./zn work status` and the board show its progress, and `./zn work stop` ends it. Run with the person's session as its window, closing or clearing the CLI stops it, and each progress check runs on that session's model. The headless `./zn work` is the same supervisor, launched without a person. A CLI that can't read skills gets the same instructions printed by a `./zn` command. The supported CLIs are `claude`, `grok` and `agent`, plus `agy`, `kimi` and `opencode` once c0175 adds them (the capture's "deepseek" is reached through opencode). Whichever of c0175 and c0253 lands second proves z-work runs in those three.
- **What it picks up** (Q1). It takes what `./zn next` prints (c0249): lost work first (c0265, taken over through c0274), then the first claimable raft. It carries that raft from rafted to merge: z-ready, z-run, the reviews, and the landing through `./zn done` with the dispatcher's credential (c0252; Q4, Q10). Only when no raft is claimable does it draft the design of a confirmed idea (c0260). It stops the draft for the person's approval: `./zn approve` (#295), with `prepared` refused without it (c0283). A person rafts, so z-raft can ask for the rank.
- **A raft, one ticket at a time** (Q2, Q7). It stays with the raft all the way to merge, as a PR stack (c0248). It builds the layers in order, each complete (green on the layer below) before the next starts. One worker holds a raft; a second works on it only through a takeover (c0274).
- **Context stays within one raft** (Q3). The supervisor (no expensive model) starts a fresh CLI session per raft and resumes that same session for each layer. Ending that session is the clearing. Whenever a raft ends, merged or released because it is blocked, the worker clears its context and picks up the next raft.
- **Quota** (Q9, with c0250). When the raft's CLI runs out of quota, the worker keeps its claim and its beat and waits, with no model running, up to a short limit set in `.models.toml`. Then it continues on another CLI with quota, in a new session that reads the raft's notes, and the raft's context is lost from then on. The worker keeps those notes as it goes (where it is, what it learned, what is open), so a session on another CLI, or a taker (c0274), can continue from them. When every CLI is out, it waits, and it blocks with `quota` only past c0250's cap.
- **It lets go only when blocked.** It marks the raft blocked (c0250), clears its context and grabs the next raft.
- **It beats** (c0265, c0275) every 5 minutes while it holds a raft.
- **It is cheap** (c0261). The worker itself never orchestrates or waits on an expensive model. Each step runs on the model `.models.toml` names for it, and spend is recorded per step.
- **Idle, it waits for work** (Q6). When nothing is claimable, it waits by polling `origin/main` from a plain `./zn` loop with no model running, until a raft or a confirmed idea becomes claimable or it is stopped. This replaces the captured "until the stack is empty or every remaining item is blocked".
- **The command.** `./zn work [--cli <name>] [--once] [--max-items N]`, with a graceful stop, a lock so one worker does not run twice for the same item, and a summary of what it moved and what it blocked. It runs on the engineer's host or another.
- **The README** (the user's 2026-11-08 scope decision, and Q6). Its worker end, which still says the worker "takes the next item" and designs it, says the worker takes the next raft (sub-section The worker, z-work). The workflow picture's `design` step says a worker drafts the design and a person approves it. ## Design
`./zn work` becomes a supervisor: a plain Lune program that holds no model. It is, as captured, "a thin loop over the engine's `next` and the dispatcher": it runs `./zn next` (c0249), and for what it prints runs `./zn dispatch <id> --worker`, the dispatcher's own chain for that item, as a child of the main checkout's engine; then it reads the child's exit code and asks `next` again. Every duty of a model step is therefore the dispatcher's and is not rebuilt: the wrapper first on the session's `PATH` with `ZN_REAL_*`, the agent credential, the publish broker, the tripwire (`guardStart`, `vetMain`, the snapshot after each step), the measured spend row of each session, the prep, raft and run merge gates under `auto_merge`, `claimBeat` (c0275), and the nested reviews. What this issue adds is the loop, and a **worker mode** of the dispatcher (`--worker`, with `--cli` and `--no-run`) for the three things Q3, Q8 and Q9 need and a plain run does not: one CLI session per raft that a rerun resumes, the person's CLI first, and a wait for quota before the next CLI. It is prototyped on `proto-c0253` (the pins are in Unknowns); the specs in `acceptance/` pass on it and fail for the right reason without it.

**In-process or a child.** The loop runs `./zn dispatch` as a child (`env -u … <main>/zn dispatch …`), not the dispatcher library in its own process. Why: one implementation (`dispatcher.main` keeps its lock per item, its lifeline to the step's process group, its tripwire watermark and its run state, none of which a second caller would reproduce); the supervisor stays small, model-free and restartable (a crash of a chain does not take the loop with it, and a stop of the loop leaves the chain's own `lost` handling to `retry`); and the child starts with the starter's markers and session ids cleared, which an in-process call could not do. Cost: one process start per dispatch run (about two seconds), and the child's output goes to the supervisor's terminal or log.

### The turn (one pass of `workloop`)
1. **Resume first (F15).** The state file of the main checkout names the raft the previous run held (`held:`); the first turn dispatches it again, before anything is asked of `next`. A stop asked, or a supervisor that died, leaves the claim exactly as the chain left it: a raft with an open pull request is parked (c0265), not lost, so it is not taken over by another worker, and only this clone's `./zn work run` resumes it. `work stop` and `work status` say which raft stays held and how to resume it (`./zn work run`, or `./zn work <R>` in a session).
2. **Read `next`, fail closed (F9).** `parseNext`: exit 0 with one `<id> lost|raft|rafting|draft <why>` line is a pick; exit 1 with `next: nothing to take: …` on stderr is "nothing claimable"; every other outcome (a fetch that failed, exit 128, a Lune trace that exits 1) is a failed read: the loop says so, waits a minute and reads again, and after five in a row stops naming the error. A failed read is never a pick and never an empty stack. With nothing claimable the loop idles a minute at a time, in one-second slices that look for the stop file, with no model; `--once` ends instead.
3. **Run the pick through the dispatcher.** `world.lock(id)` is an flock in the main checkout's `.cache/work/` (held elsewhere: skipped and waited on, not spun on). The state file now names the item as held. `./zn dispatch <id> --worker [--cli <the person's CLI>] [--no-run]` runs the chain: for a `draft` pick z-design and the prep gate, for a `rafting` pick `raft-plan --apply`, z-raft and the raft gate, for a `raft` pick `z-ready`, z-run, the reviews, `land-check` and the run gate that lands it, for a `lost` pick whatever the chain finds. Its exit code is all the loop reads (`dispatch.EXIT`): **0** the chain ended (moved); **3** the item is blocked (c0250's block, or a question): counted, and the loop takes the next pick, which `next` offers because a blocked item is skipped (F4); **4** a gate is pending: for a `draft` the prep PR waits for the person's `./zn approve`, which is not the loop's to wait for, so the pick is parked and the loop goes on; for a `raft`, `rafting` or `lost` pick the loop waits a minute and dispatches again (a dispatch run on an item whose PR is open starts no session: the chain is state-based), bounded by the **clock**, not a count, at two hours, and then stops naming the item (F6, F8); **1** a failure: run again once as `./zn dispatch retry <id>`, and a second failure stops the worker naming the item, with the claim left held (a crash or a stall is the dispatcher's `failed`/`lost`, never read as "no progress"); **5** the tripwire stopped the chain: the worker stops, names the item and keeps the claim; any other code stops it. The supervisor never runs `./zn stop`, `ready`, `done`, `lander` or `block` itself (F1, F4, F6): the chain does, with its guards.
4. **A raft is one session (Q3).** In worker mode the dispatcher's z-run step keeps the session it started in the item's run state, with the CLI. A rerun of the step (a landing check a worker can fix, a retry after a failure, a restart of the supervisor) on that CLI resumes it with the CLI's resume flag and the same id, and the prompt says "this is a resumed session; you have read the skill; continue" and names the skill, the raft and the notes (every prompt names its skill, F19). The next raft has a run state of its own, so its session is new: ending the session is the clearing.
5. **Quota (Q9, c0250).** A try that ends `quota` keeps the claim; the dispatcher beats it (c0275's `claimBeat`, with the claim's stamp, around the wait) and waits the CLI's `quota_wait_minutes` once, then tries the next CLI of the role's order in a new session (not resumed) whose prompt says "taken over from a session on <cli>; read the skill, then the raft's notes". With every CLI out the step ends `quota`; the all-out loop waits five minutes (beating) and runs the step again, tracking `quotaSince`, **one unbroken outage**: a session that spent tokens or ended ok clears it (F5b), a new outage counts from zero. Past `quota_cap_hours` (c0250; never when none is set) it writes `escalation.md` from the pure `supervise.quotaEscalation` (the four sections, one recommended option) in the raft's worktree and runs the real `./zn block <R> quota` through the dispatcher's `z-block` step, whose exit status is checked (F5a). Layers green below a block are landed by c0252's block flow.
6. **The raft's notes (F5c).** `<raft folder>/notes.md`: where the raft is, what was learned, what is open. The z-work headless branch tells the z-run session to keep it current at each layer boundary and before it ends (committed with `./zn commit`, so it rides on the layer); every worker-mode prompt names it; a switched session and a taker (c0274) read it first.
7. **Lander and who may land (F1d).** The loop lands nothing. The run gate lands, with the dispatcher's credential, under `[dispatch] auto_merge` as read from `origin/main`, with the base's engine (c0252). A host that must not land marks itself in the **user's own** file outside the repository (`~/.config/zn/host.toml`: `[work]` `land = false`, G5); the supervisor then passes `--no-run`, which drops the `run` gate from that process, so the request waits for a person's `./zn lander`. A host with no file lands, as `./zn dispatch` does today.
8. **Stop.** `.cache/work/stop` is seen between dispatch runs and during every wait; the loop ends after the dispatch run in progress (it is never killed), prints the summary and leaves the held raft held.

The README says so; `status` says "ended without a summary (see the log: it was killed or died)" when the process is gone and the log has no summary. A person who wants it unlimited sets `ZN_ENGINE_CPU` for the start. Cost if wrong: a constant.

Guess (prep, 2026-11-16): **G14, the notes are a file in the raft's folder, `notes.md`, committed on the layer.** Alternative: the issue's Verification log (appended at the end of execution only, so too late). Cost if wrong: `supervise.notesPath` and the skill's sentence.

Guess (prep, 2026-11-16): **G15, the person's CLI is detected from the markers the starter's CLI sets and passed as `--cli`.** The skill tells the session to pass `--cli <the CLI it runs in>`; `workedge.run` falls back to `supervise.starterCli(env)` (`CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` is claude, `KIMI_SESSION_ID` kimi) when it is absent; with neither, the role's own order applies. - **Shared state:** the supervisor writes only `.cache/work/` (ignored); the dispatcher writes `.cache/dispatch/` as it does; both read `origin/main`.
- **Restated rules:** the README worker end, the picture and step 5, `z-work`, `zz-rules` (starting execution), `zz-test`'s reaper paragraph, the root rules file and the usage text change together, pinned by AC12.
- **Moves:** none.
- **Guards:** the supervisor starts no model, so none of the dispatcher's guards is rebuilt (F1); what it adds is its own: it runs only in the main checkout (so the base's engine is the one that runs, c0252 G2), never inside a headless or dispatched session, never detached inside a check, with the starter's markers cleared from its child, `.models.toml` read from `origin/main`, and the host's land setting read from a file outside the repository. ### Scalability
One `./zn next` (one fetch, c0249's one `cat-file --batch`) per poll, one dispatch run per pick turn (the chain reads origin/main after each step), nothing per beat but the dispatcher's one child per five minutes. State is one small file rewritten on each transition. Idle cost is one fetch a minute per supervisor; N supervisors in N clones multiply that by N.

### Maintainability
A new CLI plugs in at `models.CLIS` plus one row of `supervise.RESUME` (a spec fails otherwise) and its adapter (c0175). A new dispatch exit code is one branch of `afterDispatch`; a new pick kind one of `parseNext`'s list. `.models.toml` is read only by `models.luau`; `.cache/work/state` only by `supervise.parseState`; the host file only by `workedge`. The pure module is specced without a process; the loop over a fake `World` that answers only the documented forms; the worker mode of the dispatcher over the fake CLIs; the whole path once end to end.

### Usability
`./zn work [--cli <name>] [--once] [--max-items N] [--detach]`, `./zn work run`, `./zn work stop`, `./zn work status` (the supervisor's line, then who holds which raft). Every refusal names the option, the CLI or the rule (`--max-items takes a whole number, at least 1`, `--cli kimi is not among role design's tries (claude)`, `the supervisor runs in the main checkout: <path>`, `a supervisor already runs in this clone`). Exhaustive lists the command joins: `flags()`'s boolean list (`--once`, `--detach`, `--worker`, `--no-run`: lesson `new-boolean-flags-join-the-parsers-list`; the specs pass each before a positional), the usage text, `cachepaths`' reviewed list. The supervisor is not read-only: it changes a checkout through the dispatcher.
