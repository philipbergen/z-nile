### F1 [high] The lost-race path covers two claims, and only after a failed step. A race lost earlier, a `rafting` pick, a `lost` pick, or a resumed item ends with the worker stopped or with two hosts on one item
Where: Design §1 (c0254.md:157-162), Rulings "`rafting` is a pick the supervisor takes, claimed like a raft" (c0254.md:131), AC1 (c0254.md:349); prototype `dispatch.luau` `next` (the issue branch: `if f.status == "preparing" then return stop(dispatch.EXIT.failure, "… is being prepared by another terminal")`; the active-raft branch ends `return { kind = "step", step = "z-run", target = f.id }` with no ownership test), `dispatcher.luau:2789` (`own = true` when any `z-design` attempt, or a `claim` that ended ok, is in the run state's history), `dispatcher.luau:3292-3309` (the verdict runs only after a failed script step). c0249.md:295 (the four pick kinds and the claim each makes); zz-rules Rafting ("The published claim (`new raft` over prepared issues …) stamps the raft only").
Evidence:
- **(a) The race is lost before the claim step.** The window runs from host B's `./zn next` (its fetch) to the fetch that host B's `./zn dispatch <id> --worker` child makes. It includes the supervisor's lock and a process start of about 2 s (c0253's own figure). Suppose host A claims in that window. For a **draft**, B's facts read `preparing`, `ownClaim = false`, so `dispatch.next` returns `stop(EXIT.failure, "c0010 is being prepared by another terminal")`. That is exit 1, not 6. `supervise.afterDispatch` retries once and then stops (pure.spec pins `afterDispatch("raft", 1, 1).kind == "stop"`). `workloop.run` sets `heldAtEnd = p.id`. So the worker stops, and its state file says it holds an item it never claimed. For a **raft**, B's facts read `where = active`, and `dispatch.next` returns `z-run`. Host B then runs a model session on the raft host A just readied. No claim step runs, so `claimVerdict` is never asked. Two hosts now work one raft.
- **(b) `rafting` picks are not claimed at all across hosts.** c0249's `next` offers "the best-ranked approved issue that is in no raft", read from `origin/main`'s `raft:` line. That line changes only when the rafting PR merges. `new raft` over prepared issues "stamps the raft only" (zz-rules). The dispatcher finds the rafting PR by the branch name `raft-<id>` only after it is opened (`dispatcher.facts`). Until then, every idle host's `next` offers the same issue. Each host runs `raft-plan --apply` and a z-raft session. The second branch push or PR then collides, and nothing reads that as a lost race (`claimVerdict` returns "failed" for `raft-plan`).
- **(c) `lost` picks race too.** Lost work comes first in every host's order (c0249). Suppose two hosts take over the same lost item. The second takeover is refused because origin was "restamped since the verdict" (c0274). The refused step is not `claim` or `z-ready`, so it is a failure: retry once, then stop the worker.
- **(d) A resumed item is "own" from history, not from its stamp.** Host A's supervisor restarts holding c0010 (c0253's "Resume first"). Meanwhile host B has taken c0010 over (c0274). A's run state still lists `claim ok`, so `ownClaim` is true and `dispatch.next` runs z-design on B's claim. The dispatcher's beat then uses `heartbeat.dispatchStamp(started, remembered)`, which takes main's stamp when the worktree remembers none (c0275). So host A keeps B's claim alive while doing B's work, and the board's trailer names B.
- The Problem says "Two of them must not take the same item … a rejected push means the worker takes the next item". AC1 checks only a failed `claim`/`z-ready` step.
Critique: The tempting fix is to also treat exit 1 with the words "being prepared by another terminal" as taken. That reads prose, which c0253's loop refuses to do ("never the dispatcher's prose"), and it still leaves (b), (c) and (d).
Consequences: The dispatcher must know which state the pick was offered in, and which stamp is its own. That needs a recorded stamp in the run state, and a change to what `new raft` publishes or what `next` skips. The `next` change touches c0249's interface.
Recommendation: (1) The supervisor passes the pick's kind to the dispatcher (`--pick draft|raft|rafting|lost`). In worker mode, `dispatch.next` stops with `EXIT.taken` whenever origin shows the item has left the state that pick was offered in, under a stamp this run did not write: a draft no longer `new`, a raft no longer prepared in the backlog, a rafting issue that another raft on origin lists, or a lost item restamped since. Do this before any step, so plain `./zn dispatch` is unchanged. (2) Own-ness comes from a stamp, not from history. After a won claim, the run state records the stamp it read on origin (`st.claim = { id, stamp }`). `ownClaim`, and the active-raft branch in worker mode, require that stamp to equal origin's current one. If it does not, the result is `taken`, and `workloop` clears `held` for a resumed pick that comes back `taken`. (3) Make a worker's rafting claim exclusive across hosts. Either `next` skips an issue that a `preparing` raft on origin lists in `issues:`, and `new raft` refuses such an issue inside its publish build (re-read on every lease retry), or rafting stamps the member. Then treat a refused `raft-plan` as a claim step in `claimVerdict`. (4) Add the takeover step of a `lost` pick to the verdict's claim steps. Spec cases (pure, over `dispatch.next` facts): a worker's draft pick that reads `preparing`/not own gives `stop` with code 6, not 1; a worker's raft pick that reads `active` with no recorded stamp gives code 6, not `z-run`; a resumed raft whose recorded stamp differs from origin's gives code 6; a plain dispatch of the same facts behaves as today. Race spec: two clones both raft-plan one approved issue, and the second refuses. Rules rows for each, with mutants such as "own from history" and "worker check skipped for active rafts".
Lesson: zz-test/pin-call-site-arguments

### F2 [high] The verdict reads the worker's own landed claim as `lost`, so the worker abandons a raft it just readied, or an issue it can then never give up
Where: Design §1 "`failed` … or the stamp is this worker's own because the push landed and a later step failed" (c0254.md:160); prototype `dispatcher.luau:2765` (`local mine = if ctx.memoryIn and st.worktree then ctx.memoryIn(st.worktree, target) else ""`), `scriptStep` (`where == "main"` gives `dir = ctx.mainRoot()`, so `st.worktree = dir`); `main.luau` `cmd.ready` (runs in the main checkout under `mainCheckoutGuards("ready")`, remembers nothing); `publish.luau` `commit` (every attempt rebuilds on a fresh `origin/main`); c0274.md:69 ("`ready` and `stop` run in the main checkout, which holds no work and remembers nothing").
Evidence:
- **z-ready.** `mine` is read from `memoryIn(mainRoot, R)`. Under R0100 that is `cm.read(R, mainRoot)`, which is always "", because ready writes no memory there. On the prototype `ctx.memoryIn` is nil (it is c0275's field), so `mine` is "" for every step. Take a `ready` whose lease push lands and which then fails: `pullMain()` fails ("readied on origin/main, but pulling the main checkout failed"), or the prompt write fails. It reads `before = backlog/prepared`, `after = active/active-…`, `mine = ""`, and returns `lost`. The run then ends with exit 6, and `dropLostAttempt` deletes the attempt. The worker goes to `next` and leaves the raft it holds in `active/`. Today's chain would retry once, and `ready`'s reissue path (`reissue = raft.state == "active" and st == "active"`) would recover.
- **The issue claim.** Suppose a push reaches origin but reports failure (the connection drops). `publish.commit` retries on a fresh origin, its build sees the item already `preparing`, and it refuses with "cannot move to preparing". The command fails before R0100's `cm.remember` (which runs only after a successful publish) and before the first beat. The verdict reads our stamp with `mine = ""` and returns `lost`. The claim then stays on origin with no beat ever written. c0274 refuses to take such a claim over ("<id> has never beaten: not lost, no takeover"), so nobody but a person can free it.
- pure.spec's case "a failed claim … whose stamp is this worker's is a failure" passes `mine` from a stub `memoryIn`. The real call site never supplies it for z-ready.
Critique: The tempting fix is to write memory in the main checkout for ready. c0274 forbids that ("the main checkout holds no work and writes none").
Consequences: The verdict needs a fact that says "this attempt wrote this stamp" and that survives a crash between the push and the end of the step.
Recommendation: Give the `Worker:` trailer an attempt token. The dispatcher sets `ZN_ATTEMPT=<run id>/<n>` in a claim step's environment, and `withWorker` writes `attempt=<token>` into the trailer. `claimVerdict` reads the trailer of the commit that set origin's current stamp (`git log -1 -S<stamp> origin/main`, or the newest trailer naming the stamp). A token equal to this attempt's means `failed` (ours), never `lost`. Keep `mine` as a second source. Spec cases: (a) a `ready` that lands and then fails its pull (a fixture main checkout with a dirty tracked file) gives `failed` and no exit 6, and a retry regenerates the prompt; (b) a claim whose trailer carries this attempt's token gives `failed` even when `memoryIn` is ""; (c) another attempt's token gives `lost`. Rules rows: "the verdict ignores the trailer's token", and "`mine` read from the main checkout".
Lesson: zz-test/pin-fail-safes-where-they-act

### F3 [high] On a layer branch the push rule reads a claim memory that a raft worktree never holds, so a lost lead's layer commits are always pushed, and G10's stated cost is not the real one
Where: Design §2 "`xhost.pushDecision` refuses to push for a claim the worker's checkout remembers but `origin/main` shows under another stamp" (c0254.md:166); G10 (c0254.md:210); prototype `main.luau:1595` (`facts.claim = heartbeat.holds(rememberedClaim(owner), at)`) and `main.luau:453` (`rememberedClaim` reads c0116's `.cache/tracker-claim-<id>`); R0100 `cm.file` = `.cache/tracker-stamp-<id>`; c0274.md:69 (the work claim's memory is written by `beat --adopt` in a worktree; "`--adopt --stamp S` (the dispatcher's form) … writes no memory").
Evidence:
- A raft's claim is made by `ready` in the main checkout, which writes no memory. c0274's work-claim memory is `tracker-stamp-<R>`, written only when z-run runs `./zn beat <R> --adopt` in its worktree. Under dispatch the beat is the dispatcher's `--adopt --stamp S`, which writes none. The prototype reads `tracker-claim-<R>` (c0116's "owns the rafting claim"), which a raft's work worktree never has.
- So for every `R####/<n>/<id>` branch, `claim` is `unheld`, G10 allows the push, and the `taken`/`ended` refusal is dead code for rafts. It fires only for preps, because `status <id> preparing` writes c0116's file for issues. Every AC2/AC3 case in race.spec is a prep (`prep-c0010`, `prep-c0011`), and mutant R22 replaces the result of `holds`, not the reader. So nothing catches this.
- G10 says its cost is "a person's push after a takeover; the `behind` rule still stops it". It is in fact every lost lead's push on a layer. `behind` stops nothing until the taker has pushed. Take a taker that built its worktree from origin's tip and has not committed yet. The lost lead's late commit fast-forwards origin. From then on, every push by the taker is refused (`behind > 0`, "git fetch, then decide"), so Q3 lapses for the taker silently (F10).
Critique: The tempting fix is to swap in `cm.read`. Under dispatch, nothing adopts, so the memory can still be empty.
Consequences: The push rule needs the work claim's stamp in every worktree that commits on a layer, including dispatched ones.
Recommendation: Name c0274's `cm.read(id)` as the one memory reader for the push rule. It falls back to c0116's file, so preps still work. When it returns "" under dispatch, use the stamp the dispatcher is beating: c0275's `dispatchStamp`, passed to the model step as `ZN_CLAIM_STAMP` together with `ZN_CLAIM_ID`. Restate G10 to cover only a checkout with neither, and give its true cost. Race spec, a layer case: host A readies R0010 and starts layer 1. Host A adopts, or under the env stand-in sets `ZN_CLAIM_STAMP`, commits and pushes. Host B takes over (stop, ready, adopt) and pushes nothing yet. Host A's next `./zn commit` on `R0010/1/c…` is not pushed, and origin keeps B's tip. Rules row with the mutant "reads c0116's claim file only".

### F4 [high] The push refusal tells a lost worker to keep working on the taker's branch, the opposite of what c0274 and c0277 tell it
Where: prototype `xhost.luau:121` (`…: not pushing {f.branch}; continue from the taker's push in a new worktree (./zn worktree {f.branch})`); Usability "A lost worker is told why its push was refused and where to continue (`./zn worktree <branch>`)" (c0254.md:228); c0274.md:73 ("this checkout's work is no longer the claim's; stop here (./zn lost lists lost work to pick up)"); c0277's marker ("Clear your context and pick up something new"); c0275 ("stop working it").
Evidence: Follow the text on the lost host. c0277's family lookup sees that the worktree's memory reads `taken`, discards it, and prints a numbered copy built from origin's branch, which is the taker's tip. The copy remembers no claim, so it is `unheld`, and it has `behind = 0` because it was built from the taker's push. The lost worker's next `./zn commit` in the copy is therefore pushed onto the taker's branch. A headless model reads its tool output literally. Two workers then push one item's branch.
Critique: The tempting fix is to change only the wording. The refusal must also mean "stop", and nothing in the push rule may let a fresh copy of a taken item push without a claim.
Consequences: The refusal is the lost worker's last signal, and it must match c0274's text. A copy with no claim must not count as a person's session (G10).
Recommendation: Use c0274's text (`hb.lostText` plus "this checkout's work is no longer the claim's; stop here (./zn lost lists lost work to pick up)") for `taken`/`ended`, and make `./zn commit` exit non-zero after the commit (F10). Restrict G10's `unheld` push to a branch that origin's main does not show under a live claim stamp the checkout cannot vouch for. Then a taken item's branch is pushed only by a checkout that holds the stamp (memory or `ZN_CLAIM_STAMP`). Spec: the race case checks the refusal text and the exit code, and a numbered copy with no memory, made on the lost host, does not push the taken prep's branch. Rules row: "the refusal advises continuing".
Lesson: z-design/instructions-runnable-where-they-run

### F5 [high] `finish` and `restack` force-push with a lease that c0254's per-commit fetch refreshes, so a lost lead's `./zn finish` overwrites the taker's pushed layer
Where: AC2 "a worker whose claim was taken over or has ended is never pushed again, so it cannot move the taker's branch" (c0254.md:350); README "never pushes that branch again"; Guards (c0254.md:219); prototype `main.luau:1576` (`git fetch --quiet origin <branch>` in `pushAfterCommit`), `main.luau:4138-4143` (`cmd.finish`: `remote = layergit.shaOf("origin/<branch>")`, `--force-with-lease=refs/heads/<branch>:<remote>`), `main.luau:4285-4289` (`cmd.restack`, the same); R0100 `cmd.finish`/`cmd.restack` hold no claim check (only `done` checks `holds`).
Evidence: I ran the probe `./zn run --time 60 -- bash leaseprobe.sh`, with two clones of one bare origin in the scratchpad. Clone A pushed a layer. The taker, clone B, pushed `taker1` on top of it. A committed `late` and ran `git fetch origin <branch>` (pushAfterCommit's fetch). A's `origin/<branch>` moved to the taker's tip: "A's origin/ref after 'git fetch origin <branch>': 22488cc (origin tip 22488cc)". A then squashed as `finish` does and pushed with `--force-with-lease=refs/heads/<branch>:$(git rev-parse origin/<branch>)`, and the result was "finish-style lease push: accepted". Afterwards "taker1 on origin branch: 0": the taker's commit is gone from origin. zz-rules counts on this lease ("A layer branch is pushed with `--force-with-lease`, so a rewritten branch refuses the push"), and the new fetch empties it. A lost lead that wakes up runs `./zn commit` (refused, F4) and then `./zn finish` per zz-execute.
Critique: The tempting fix is to check the claim in `pushAfterCommit` only, which already happens. The forced pushes are the dangerous ones, and they stay open.
Consequences: Every engine command that pushes a layer or prep branch must apply one rule, and the lease must name a sha that this checkout pushed or built on, never one it just fetched.
Recommendation: Route every engine push of a layer or prep branch (`pushAfterCommit`, `finish`, `restack`, and `start`'s and `done`'s branch pushes) through `xhost.pushDecision`'s claim rule, refusing on `taken`/`ended`. Read origin's tip without moving the remote-tracking ref: use `git ls-remote origin refs/heads/<branch>`, count with `merge-base --is-ancestor`, and treat an absent object as "cannot count", which refuses. Then the lease ref keeps meaning "what this checkout last saw". Race-spec case: after host B takes over and pushes, host A's `./zn commit` followed by `./zn finish <id>` leaves origin at B's tip. Rules rows: "finish skips the claim check", and "the fetch updates `origin/<branch>`".

### F6 [high] A lost claim step leaves a stale prep worktree and branch on the losing host, and a later takeover there continues from it instead of from the pushed draft. AC2's case removes it by hand
Where: AC2 (c0254.md:350), race.spec "AC2: a taker on host B continues in a worktree of its own, built from the pushed branch" (it runs `worktree remove --force wtB` and `branch -D prep-c0010` before the taker's `./zn worktree`); prototype `dispatch.STEPS.claim.where = "prep"` with `scriptStep`'s `worktree(ctx, "prep-<slug>")`; `cmd.worktree` (main.luau:4559 on) returns an existing path at once (`if w.path == path then print(path) return`) and prefers a local branch (`worktree add path branch`) over `origin/<branch>`; c0277's lookup returns a member that remembers nothing "as before"; `dropLostAttempt` removes nothing.
Evidence: Host B's claim step creates `.worktree/prep-<slug>` on a new branch `prep-<slug>` from `origin/main`, with `--no-track`, and then loses the race. Host A works and pushes `prep-<slug>` commits, then dies. Its item becomes lost work, which comes first in host B's `next`. Host B's takeover runs `./zn worktree prep-<slug>`, gets the stale worktree back unchanged, and works from `origin/main`, not from A's draft. Its first `./zn commit` sees `behind > 0` and is never pushed again. The spec reaches its green result only by deleting that state first ("host B's earlier prep worktree knows nothing of A's work"). So the realistic state is untested, and AC2's "it has every pushed commit" fails in it.
Critique: The tempting fix is to delete the worktree in `dropLostAttempt`. That covers the claim step but no other stale local branch, such as a person's earlier attempt or a prototype.
Consequences: Worktree lookup for layer and prep names must prefer origin's progress, and never discard local work.
Recommendation: (1) `dropLostAttempt` removes the claim step's worktree and local branch when they are clean and hold no commit beyond their base (the dispatcher made them for the claim alone). (2) `./zn worktree <prep-or-layer name>` fast-forwards a clean local branch that is an ancestor of `origin/<branch>`, and refuses, naming the command, when the two diverge. Race spec: rewrite the AC2 case without the manual removal. B loses the claim race, A pushes two commits, and B's later `./zn worktree prep-c0010` is at A's tip. Add a case where a diverged local branch is refused. Rules rows for both.

### F7 [high] Q5's lost-host leftover is designed by nobody: c0277 hands several hosts to c0254, and G9 hands the lost host back to c0277

Add a Checked AC7 for Q5 on the lost host, with race-spec cases: (a) after B's takeover, A's `./zn sync` marks A's prep worktree discarded; (b) after B's prep is given back or merged, A's sync removes it when clean; (c) one holding an unpushed commit is kept and listed by `./zn reap`. These cases require c0277's functions, which are in `depends_on`. Drop Implementation step 9's "decide whether".

### F8 [high] "Who did the work" is read from the process that folds a row or starts a claim, not from the step. The dispatcher's spend rows, review rows and every worker's claim trailer get the wrong CLI or `unknown`
Where: Design §4 (c0254.md:175: "`cli` is `ZN_CLI`, which the dispatcher sets next to `ZN_MODEL` for each attempt"), §5 (c0254.md:179: the trailer is "made by the tool that publishes the claim, with the worker's identity"), AC4, AC5; prototype `costrow.luau:128` (`local who = xhost.identity(process.env, costrow.hostName())`, applied to every row); `dispatcher.luau:665-701` (`publishMeasured` folds each step's measured row in the dispatcher's own process, with `rowLine` carrying `model` but no `cli`), `dispatcher.luau:737` (a code-review row is printed as `record: ./zn commit … --phase code-review --model <reviewer>` and folded by the author's commit), `modelStep` (`env.ZN_CLI = spec.cli` is set only in the child's env table); `scriptStep` (`process.exec` with no `env`, so the claim step and `ready` inherit the dispatcher's env); c0253 (the supervisor starts the dispatcher with the starter's markers cleared); c0325.md:226 ("`spend`/`commit` take [`ZN_MODEL`] only for `capture`, `prep` and `build` … and never for a reviewer's row").
Evidence:
- **Spend.** The measured row of every dispatched model step is folded by `costrow.plan` in the dispatcher's process. That covers the z-design session, the reviewer rows (`design-review-NNN`) and a run's pending `deliver` rows. `ZN_CLI` is never set in the dispatcher's own env. Under the supervisor the cell reads `unknown`. When a person runs `./zn dispatch` inside Claude Code (`CLAUDECODE=1` is inherited), it reads `claude` even for a step that ran on grok or kimi. A code-review row is folded by the author's `./zn commit`, so it records the author's CLI next to the reviewer's model. That breaks c0325's rule that the author's env never labels a reviewer's row.
- **Claims.** The worker's `claim` step and its `z-ready` step are script steps that run in the dispatcher's env. Every worker claim's trailer therefore reads `cli=unknown model=-`. ## Lesson candidates (for the lead to write; a reviewer writes no lesson file)
- zz-review or z-design, "a race has a window before the claim, not only at it".
