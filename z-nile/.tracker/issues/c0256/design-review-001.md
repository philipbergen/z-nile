### F1 [high] The answer c0117 documents (written in questions.md) is dropped and recorded as "no reply"
Where: Design, The dispatcher, 2 (a retry with no answer records `NO_REPLY`); Docs ("nothing else in the file changes"); `dispatch.next`'s stop message.
Evidence: today the rule says the user answers in `questions.md`. zz-rules SKILL.md:177: "It stops (exit 3) when a step wrote `questions.md` … (the user answers in that file and runs `./zn dispatch retry <id>`, which keeps it as `answered-<n>.md`)". c0117's promoted case is titled "…retry keeps the answers and reruns". The prototype's stop message still begins "needs the user: answer questions.md, then …" (P1 output). P7: questions stop, the user edits `questions.md` to add `ANSWER: the small scope`, then runs a plain `retry`. Result: `002-answer.md` = `(no reply: the user ran retry without an answer)`, `answered-1.md` holds the user's answer, and the re-run step's log has neither `answered-1` nor "the small scope". The prompt then says "When the last file is an answer, it replies to the latest question: do not ask again what it settles", so the no-reply entry is presented as settling the question.
Critique: this is the Problem's own outcome ("the user's answer back when the run is retried"), lost on the path the current docs teach. The design leaves line 177 as it is, so after landing the skill gives two contradictory instructions (restated-rules-move-together). The tempting fix is to reword line 177 only. A user who follows the old habit, or the stop message's first words, still loses the answer without being told.
Consequences: honouring an edited `questions.md` brings a new rule: what counts as an answer when the file was edited *and* `--answer` was given, and what the stored answer holds (the whole edited file, not a diff). The no-reply wording needs its own prompt sentence.
Recommendation: at retry, when no `--answer`/`--answer-file` is given and `questions.md` differs byte for byte from the last copied `question`, store the edited file verbatim as the `answer`. When both an edit and a flag are present, refuse ("questions.md was edited and --answer given: use one"). Change the stop message to "read questions.md, then …--answer… (or write your answers into it)". Make zz-rules :177 and the new bullet say the same thing. In `dispatch.prompt`, say that a `NO_REPLY` answer settles nothing ("the question stands; decide whether you can go on without it"). Spec cases (retry.spec, promoted): an edited questions.md plus a plain retry stores the edit as the answer and the step reads it; an edit plus `--answer` is refused before anything moves; the prompt for a NO_REPLY last answer lacks "do not ask again". Mutants: the edit ignored; the NO_REPLY wording missing.
Lesson: z-design/restated-rules-move-together

### F2 [high] Every later step of the run is told it is "a re-run of this step", including z-design after a dispatched capture, which conflicts with c0260
Where: Design, The dispatcher, 3 ("This is the one place a model step starts, so chain, one-step runs and every retry get it"); `dispatch.prompt`'s paragraph; Existing work (c0260).
Evidence: P1. A capture stops with questions; then `retry new --answer "Approved."` with z-ticket in `ticket` mode and z-design `ok`. The chain's next step, z-design for the new c0040 (not a re-run), gets: "This is a re-run: the user and earlier runs of this step have already exchanged messages … read … `.cache/dispatch/c0040/exchange/` … 001-ask.md, 002-question.md, 003-answer.md … When the last file is an answer, it replies to the latest question: do not ask again what it settles." c0260 on origin/main (line 72) says: "**z-design does not design such a ticket until the user confirms it** … dispatched: a `questions.md` stop … answered through c0256's hand-over". The capture's "Approved." is handed to z-design as settling the question, which is the confirmation c0260 requires z-design to ask for. The same thing happens for every step of one item's state folder (z-design, then z-raft with `--for`). A file does not record which step asked, so z-raft is told that z-design's answer settles its questions.
Critique: the prompt states something false ("earlier runs of this step"), and the dependent issue's flow is undermined. No spec looks at a non-re-run step's prompt, so `step.spec` and `capture.spec` stay green. The tempting fix, dropping the paragraph for steps other than the one that asked, would also hide the capture's conversation from z-design, which c0260 wants z-design to show.
Consequences: recording the asking step adds a field that `exchange.parse` must read strictly. The prompt then needs two texts, one for a re-run of the step that asked and one for a step that reads an earlier step's exchange. c0260's reading has to name which entries it copies (the capture's, those z-ticket asked).
Recommendation: put the asking step in each `question` file (a strict `step: <name>` line after `date:`, or `NNN-question-<step>.md`). An `answer` belongs to the question before it. `dispatch.prompt` adds the re-run paragraph ("do not ask again what it settles") only when the latest question was asked by this step. Any other step gets a neutral sentence ("earlier steps of this run exchanged these messages with the user; they settle those steps' questions, not yours"). Existing work should say that c0260's z-design confirmation stop answers through this exchange and how its prompt reads. Spec cases: capture then z-design, where z-design's prompt has no "re-run" or "do not ask again" but names the folder; a z-design Q/A then a z-raft step without "settles"; the re-run of z-design still has the paragraph. Mutant: the paragraph added for any step with an exchange (what the prototype does now).
Lesson: z-design/quote-other-preps-before-promising

### F3 [high] After the first finished dispatched capture no other capture can start, and c0256 turns c0117's recovery into a dead end; a failed capture's retry names no id
Where: Design, The dispatcher, 4 ("a later capture starts clean"); `retry new` ("no capture waits"); captured outcome "the retry of a `new` run names its id".
Evidence: P5 on the unpatched base and on the prototype, with two `dispatch new` in a row (z-ticket `ticket`). After the first capture, `.cache/dispatch/new/state.json` keeps `"outcome": "running"`: `modelStep` moves `st.dir` to the issue mid-step and never saves `new` again (c0117, present on base). The second `dispatch new` gives "stop: new's last step was lost (its dispatcher died): ./zn dispatch retry new". On base, `retry new` resets the state (it prints "new is not on origin/main") and a third `dispatch new` runs z-ticket. On the prototype, `retry new` gives "stop: no capture waits: ./zn dispatch new "<description>" starts one" and returns before the state is reset. A third `dispatch new` then prints "stop: z-ticket ended lost: ./zn dispatch retry " (the id is empty). Nothing short of editing `.cache` by hand clears it. A `new` run left waiting by c0117 (questions.md, no `001-ask.md`) is stuck the same way: `dispatch new` gives "words were not taken" and `retry new` gives "no capture waits".
Critique: `dispatch new` is the flow this chore exists for (c0247's headless z-ticket). The design's "starts clean" claim was never run past one capture. The outcome "the retry of a `new` run names its id" holds only for the questions stop, and only because `st.id` stays `"new"` when no issue was made. Every other stop of a capture prints `retry ` with no id.
Consequences: finishing the `new` slot needs a rule for what `new/state.json` says once its run has moved to an issue, and for what `retry new` does with a lost or failed state that has no ask. Migrating c0117-era `new` runs is one more case (new-rules-migrate-existing-work).
Recommendation: when z-ticket hands the run to `<id>`, save the `new` state as finished (`outcome = "ok"`, `detail = "captured as <id>"`, `run = nil`) under the lock it holds. Give every stop of a capture `new` as its id (facts carry a display id of `new` when `id == ""`). `retry new` with no ask: when the state is lost or failed, or a c0117-era `questions.md` waits, reset it, set that `questions.md` aside as `answered-N.md`, and say "start again with ./zn dispatch new" so the next `new` runs. Spec cases (capture.spec): two captures in a row both run z-ticket; a capture whose z-ticket fails prints `./zn dispatch retry new`; a c0117-era waiting `new` (questions.md, no exchange) can be cleared and a new capture starts. Mutants: `new` state not finalised; the empty id.
Lesson: z-design/new-rules-migrate-existing-work

### F4 [high] The dispatcher writes the user's answer through a link that a step planted, overwriting a tracked file in the main checkout
Where: prototype `exchangeAdd` (`fs.writeFile(`{dir}/.{name}`, …)` then `fs.move`); Design, Guards ("nothing near the fence … changes. The dispatcher writes only under `.cache/dispatch/`").
Evidence: P8. A step writes `questions.md` and `ln -s <main>/pickman/.tracker/issues/c0010/c0010.md "$ZN_DISPATCH_DIR/exchange/.002-answer.md"`. Then `retry c0010 --answer "WRITTEN THROUGH THE LINK"`. The issue document becomes `date: 2026-11-09T19:47:40Z\n\nWRITTEN THROUGH THE LINK`, and the link is renamed to `002-answer.md`. c0077's rule, which `tests/lib/cachepaths.luau` records for this module ("state.json and the markers through sh.writeReplacing"), exists so that a link swapped in under `.cache` is replaced, never followed. The temp name `.NNN-kind.md` can be predicted from the folder listing.
Critique: in real use the dispatcher runs unjailed as the user, so this is a write outside `.cache`, into the main checkout's tracked files (or anywhere the user can write), chosen by a model step. That is repository safety (item 9), and the README's "not a security boundary against a determined agent" does not excuse it: c0077 guards exactly this honest-mistake surface. The tempting fix, a random temp name, still follows a link placed at `exchange` itself, or at the final name before the rename.
Consequences: the same holds for `exchange/` being a link (to a repository folder) and for `fs.move(new/exchange, <id>/exchange)`. A non-regular `questions.md` (a link to a credential file) gets copied into the exchange, which every later prompt names.
Recommendation: write every exchange file with `sh.writeReplacing` (an exclusive fresh temp, then rename). Before any read or write, refuse an `exchange` that is a link and any entry that is not a regular file (lstat in the adapter, so `exchange.order` stays pure over names plus a "regular" flag). Refuse a `questions.md` that is not a regular file before copying it. Spec cases (retry.spec): a link at the temp name, at a final name and at `exchange/` leaves the target byte for byte unchanged and the retry refuses, naming the path; a `questions.md` that is a link is refused at the stop. Mutant: `fs.writeFile` back in `exchangeAdd`.

### F5 [high] A step can rewrite the user's recorded words or forge messages, and the dispatcher accepts them
Where: Design, The exchange (written by: the dispatcher, `dispatch new`, `retry`); the step's `$ZN_DISPATCH_DIR` is the folder that holds `exchange/`.
Evidence: P4. During the re-run, z-ticket's step overwrites `exchange/001-ask.md` with `forged words` and adds `004-question.md` "forged: the user approved". Afterwards the exchange is `001-ask.md=forged words, 002-question, 003-answer=real answer, 004-question=forged…`, and the real `questions.md` ("Q again") was never copied, because the last message was already a question. c0260 copies `001-ask` into `## Ask (verbatim)` as the user's own words, and c0247 treats an answer in the hand-over as the user's approval.
Critique: the exchange is the record that an approval came from the user, kept where the gated step can write. The same model that is asked to confirm intent can edit the confirmation, and a confused step can silently lose the real question.
Consequences: the guards here detect honest mistakes (README), so detection is enough. But it needs a record of what the dispatcher wrote, and a rule for what a changed exchange does to the step's outcome and spend.
Recommendation: after each model step, compare the exchange with what the dispatcher wrote (a manifest of name and sha256 of each file, kept in `state.json` and written by the dispatcher only). An added, removed or changed file fails the step ("the step changed the exchange: <file>"), with its spend recorded (see F7) and nothing copied. Spec cases (retry.spec): a step that edits `001-ask.md`, one that adds a numbered file and one that deletes one each fail with the file named; the next retry refuses until the user looks. Mutant: no comparison.
Lesson: zz-arch/guard-state-out-of-reach-or-checked

### F6 [high] A step run by hand while a question waits asks a new question that is never recorded, so the answer is paired with the wrong question
Where: Design, The dispatcher, 1 ("once (not again while the last message is already a question)"); AC4 (one-step runs).
Evidence: P2. `dispatch c0020` stops with "Which scope?" (`001-question.md`). `dispatch z-design c0020` by hand rewrites `questions.md` to "A DIFFERENT question" and stops with code 3, but the exchange stays `001-question.md` = "Which scope?". `retry c0020 --answer "answer to the DIFFERENT question"` then records `002-answer.md` after "Which scope?", and the re-run step reads that pairing.
Critique: one-step runs are an entry the design names as supported. The record c0260 copies into `### Qn` would hold a wrong question/answer pair, and nothing shows it. The tempting fix is to copy whenever the text differs, but the alternation rule refuses a question after a question.
Consequences: either a step can't start while a question waits, or an unanswered question gets an automatic "no reply" before the next one. Each choice changes what c0117's one-step entry does.
Recommendation: refuse to start any model step while `questions.md` waits, unless the start comes through `retry`: `dispatch <step> <id>` prints "a question waits: ./zn dispatch retry <id> --answer …" and starts nothing. This matches `dispatch <id>`, which already stops on it. Spec case (step.spec): a by-hand step while a question waits starts nothing and the exchange is unchanged. Mutant: the guard removed. No promoted spec starts a step by hand while a question waits: `git grep -n 'questions' -- z-nile/tests/acceptance/c0117 z-nile/tests/tooling/dispatch-guards.spec.luau` hits only control-cli:135-170 (the chain stops and a capture's z-design asks) and dispatch.spec:39,169,229 (pure facts and the prompt), so the refusal needs no Override.

### F7 [medium] When the exchange can't take a step's question, the step's spend is lost and its state stays `running`
Where: prototype `modelStep` (the `exchangeQuestion` error is raised before `record(...)` and `save(st)`); Design, The dispatcher, 1.
Evidence: P3. A step writes `exchange/notes.md` and `questions.md`. Output: "dispatch: z-design on claude: ok (done), 123 tokens", then stderr "the exchange of this run cannot take the question: notes.md is not an exchange file". There is no `spend:` line, `state.json` has `outcome=running` and `history=0`, and the next `dispatch c0030` says "c0030's last step was lost (its dispatcher died)". The same path follows a full exchange (999).
Critique: the tokens are spent and never recorded, and the state misnames the cause. This breaks results-land-on-every-path. The Lessons pass cites that lesson only for the entry points.
Consequences: deciding the outcome of such a step (failed, with the reason) also decides whether the chain stops on the waiting `questions.md` or on the failure.
Recommendation: copy the question after `record` and `save`, or catch its refusal, record the attempt as `failed` with the reason, save, and stop exit 1 naming the file. Spec case (retry.spec): a step that leaves a stray file and a question records its spend row, ends `failed` with the reason, and the next run repeats the reason, not "lost". Mutant: error before record.
Lesson: z-design/results-land-on-every-path

### F8 [high] A dispatched step (a review started by its author) that stops with questions is told to use a retry that refuses it
Where: Design, The dispatcher, 3 (only chain, one-step and retry are considered); captured "It works for any step that stops with questions"; AC4.
Evidence: P6. z-design is in `author` mode (it runs `./zn dispatch zz-review c0010 --mode design`) and zz-review in `questions` mode. The nested review prints "stop: needs the user: answer …/.cache/dispatch/c0010/zz-review-design-c0010-1/questions.md, then ./zn dispatch retry c0010 --answer "<your answer>"", and its question is copied to `zz-review-design-c0010-1/exchange/001-question.md`. `./zn dispatch retry c0010 --answer "my answer to the reviewer"` answers "stop: no question waits for an answer in …/c0010: --answer has nothing to answer". The dispatched prompt tells every step, reviewers included, to write `questions.md` "when a decision needs the user (… a final review round that goes to the user …)".
Critique: a captured outcome goes unmet for one class of steps, and the new message names a command that refuses. Re-running the author dispatches a new nested folder (`-2`) with no exchange, so even a plain retry never shows the reviewer the answer.
Consequences: the answer has to reach a step whose state folder is new on every run, so either the question moves up to the run the user retries, or nested folders inherit the parent's exchange. Either way the asking step must be recorded (F2).
Recommendation: when a nested step stops with questions, the dispatcher moves its `questions.md` up to the top run's state folder (recorded as asked by `zz-review`, F2's step field), so the chain stops there and `retry <id> --answer` reruns the author. A nested step's prompt names the top run's exchange (read-only, as context), so the re-dispatched reviewer sees the question and the answer. Spec case (step.spec): author plus a reviewer that asks; the retry with an answer reruns the author, the second reviewer's prompt names the exchange, and the reviewer's log reads the answer. If the user would rather keep nested questions out of scope, escalate to the user: the options are (a) the design above; (b) the nested stop prints an instruction that works today (answer by re-running the author with `retry <id>` and no answer) and the answer is not carried, which leaves "any step" short and needs a `Scope decision` line.

### F9 [medium] The Rules and mutants table misses rules the Design states, and the mutation script counts any failure as a kill
Where: Rules and mutants; `experiments/mutants.py` (`if code == 0: SURVIVED else red`).
Evidence: from reading the Design and the specs: (1) "sets aside any earlier `exchange/` as `exchange-<unix time>/` (never deleted)" has no row and no case. No spec runs a second `dispatch new` after a capture left an exchange, so `fs.removeDir(old)` survives. (2) "an unreadable folder refuses the step, naming the file": `modelStep` uses `exchangeNames` (names only), so a numbered file with no date line passes at the step start. The case only plants a stray name. (3) The re-run paragraph for a step that did not ask (F2) has no row. (4) `mutants.py` marks any non-zero exit as killed, including a spec that fails to load, a timeout (`./zn run` limit) and the sweeper's exit 71 above. The recorded "killed on an assertion" is the author's reading of one printed line, not something the script checks.
Critique: the design says the mutants were killed on an assertion, but the script doesn't enforce it, and a row that has no case can't fail.
Consequences: none beyond the cases.
Recommendation: add rows and cases for (1) a second capture after a failed one keeps `exchange-<t>/` (`capture.spec`) and (2) a dated-line-less `002-answer.md` refuses the step start (`retry.spec`'s by-hand case), plus F2's row. In `mutants.py`, count a mutant as killed only when exit is 1 and the output has a `FAIL <spec> :: <case>` line followed by an assertion message (`expected` or the case's own `error(`), and report exit 70, 71 or 124 as "INCONCLUSIVE".
Lesson: z-design/spec-design-correspondence

### F10 [low] The retry loses a typed answer if it dies between setting questions.md aside and writing the answer, and then refuses the same answer
Where: Unknowns, "Accepted (reasoned): … nothing is lost"; Design, The dispatcher, 2 (the order: copy, move, add).
Evidence: from the prototype's order (`fs.move(q, answered-N)` then `exchangeAdd(answer)`), and from the refusal "no question waits", which P4 and P6 printed whenever `questions.md` was absent. After a Ctrl-C between the two operations, `questions.md` is gone, so `retry --answer "<the same answer>"` is refused, and a plain retry re-runs with the question unanswered. The same order means an answer that would be message 1000 is refused after `questions.md` has moved, which contradicts "refused before anything moves".
Critique: the window is small, but the user's text is lost and the CLI won't take it again, which is what "nothing is lost" says can't happen.
Consequences: writing the answer first makes "an answer recorded, questions.md still waiting" a state the next retry must finish.
Recommendation: check `exchange.next(names, "answer")` and write the answer first, then move `questions.md`. A retry that finds the last message is an answer while `questions.md` still waits only finishes the move, and refuses a new `--answer` with "an answer is already recorded: <file>". Spec case: a fixture in that half state, then retry with no answer, moves `questions.md` and adds nothing.

### F11 [low] `--answer-file` reads a file of any size or content into every later prompt's reading list
Where: Design, The dispatcher, 2 (`readAnswer`).
Evidence: from the prototype's `readAnswer`, which checks only `fs.isFile` and that the text is not blank. A mistyped path (a log, a binary) is stored verbatim and named to every later step.
Critique: it burns tokens on every later step and puts unreadable content in the exchange that c0260 copies into `## Ask (verbatim)`.
Consequences: a limit is a number the user may want to tune.
Recommendation: refuse an answer over 64 KiB, or one with a NUL byte, naming the size, before anything moves. Add one case to `retry.spec`'s refusal list.

Existing work claims (checked on origin/main 836019e0): c0247 is prepared, `depends_on: [c0256]`, and its paragraph names no file (its line 46). c0260 is prepared and depends on c0247 and c0256. c0250 is new and says "Replaces `questions.md` in c0117's design". c0121 is preparing, and its retry is a plain `./zn dispatch retry <id>`. All as the design says. Missing: c0260's z-design confirmation stop, which also answers through this exchange (see F2).

Candidate lesson (for the lead): z-design: a dispatcher feature that keys state by `new` (or any slot reused by many runs) is proven with two runs in a row, not one, because c0256's design said "a later capture starts clean" while c0117 left `new/state.json` `running` after every capture (F3). Check: does a spec run the flow twice in the same fixture?
