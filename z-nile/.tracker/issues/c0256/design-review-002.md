### F1 [high] The "retry died after storing the answer" state is guessed from `questions.md` plus a last answer, so a crash after a re-run step asked again loses the new question, refuses its answer and tells the step its question was settled (repeat of review-001 F10, in its fix)
Where: Design, The dispatcher, 4 ("A retry that died between the last two leaves 'answer recorded, `questions.md` still waiting': the next retry only finishes the move"); Unknowns, "Accepted … A dispatcher killed between a step's end and the copy of its question is covered: the retry copies it"; prototype `retry` (`local half = waiting and last ~= nil and last.kind == "answer"`).
Evidence: probe Q1. `dispatch c0010` stops with "Which scope?" (`001-question.md`). `retry c0010 --answer "first answer"` re-runs z-design, whose step writes `## Q1\nsecond question\n` to `questions.md` and then the dispatcher is killed (`kill -9 "$ZN_DISPATCHER_PID"`). The folder now holds `exchange/001-question.md,002-answer.md`, `answered-1.md` and the new `questions.md`. `dispatch c0010` says "c0010's last step was lost (its dispatcher died): ./zn dispatch retry c0010". `retry c0010 --answer "answer to the second question"` says "stop: an answer is already recorded (002-answer.md); run retry without --answer". A plain `retry c0010` then moves the second question to `answered-2.md` (`## Q1\nsecond question`), adds nothing (`exchange` still `001-question.md,002-answer.md`), and the re-run step's prompt says "This is a re-run … When the last file is an answer, it replies to your latest question: do not ask again what it settles." From the code (not probed): any answer the user wrote into the second `questions.md` is moved aside unread too, since the half branch skips the edit test.
Critique: two facts that do not belong together (a waiting file and the kind of the last message) are read as one state. They also describe "the re-run step asked again and its dispatcher died before the copy", which is the round-2 case every capture correction and every c0260 confirmation goes through, and which c0121's board makes ordinary (Ctrl-C of the server kills a running retry, G3). The record c0260 copies into `### Qn` then pairs the second question with nothing and the first answer with both, which is the wrong-pairing defect review 001 F6 was about. The tempting fix is to compare `questions.md` with `answered-N.md`'s text, which a user's edit breaks, or with the last question's body, which a new identical question breaks.
Consequences: an explicit marker is new state: it must be written in the same save as the answer (or the window reopens), cleared after the move, survive `--forget-exchange` (which drops the answer it refers to) and be ignored by a retry that finds no `questions.md`. The existing half-state case builds its state by copying `answered-1.md` back by hand; with a marker that fixture no longer produces the half state and must be built by the dispatcher's own steps.
Recommendation: record the half state, never infer it: before `exchangeAdd(st, "answer", …)` set `st.answering = sha256(the questions.md text the answer was taken from)`, so `exchangeAdd`'s `save` writes both at once; clear it after the move and in `--forget-exchange`. The half state is `waiting and st.answering == sha256(questions.md)`; any other waiting file after a last answer is a new question: copy it (asked by `st.step`, dated at the retry, as the design already says for round 1) and take the answer as usual. Spec cases (retry.spec, promoted): Q1's sequence with the fake `kill -9 "$ZN_DISPATCHER_PID"` expects `003-question.md` = "second question" and `004-answer.md` = the flag, and the re-run told its question was answered; the half state made for real by planting a directory at `answered-1.md` (the move fails after the answer was written), then a plain retry finishes the move and adds nothing. Rows: "a new question after a last answer is copied" (mutant: today's `last.kind == "answer"` rule) and "the half state is the recorded one" (mutant: the marker ignored).
Lesson: zz-arch/read-paired-facts-at-one-moment

### F5 [medium] "The edited file is the answer" compares bytes, so reading the question in an editor can block `--answer`, and a blank or deleted file leaves no way to answer
Where: Design, The dispatcher, 4 ("when the file differs from the question the dispatcher copied, the whole edited file is the answer"; "A flag together with an edited `questions.md` is refused"); the stop message ("read questions.md, then … --answer …").
Evidence: probe Q4: a step writes `## Q1\nWhich scope?` (no final newline), the user opens and saves it in an editor that adds one (vim with its default `fixendofline`, or VS Code with `files.insertFinalNewline`; the probe appends the `\n` itself), then `retry c0040 --answer "the small scope"` says "stop: questions.md was edited and --answer was given: use one of them"; a plain retry would store the unchanged question as the user's answer. Probe Q5: a user who empties `questions.md` gets "questions.md as edited: the answer is empty"; `--answer` then gets "edited and --answer was given"; after deleting the file, `--answer` gets "no question waits for an answer … --answer has nothing to answer", while the exchange's last message is still the unanswered `001-question.md`. Only restoring the file byte for byte (from `exchange/001-question.md` minus its header, which no message mentions) gets out.
Critique: the stop message tells the user to read the file, the rule then treats the editor's save as an answer, and three refusals in a row name no way on (the lesson behind `--forget-exchange` was to avoid dead ends). The tempting fix is to drop the edit-plus-flag refusal, which reopens review 001 F1's ambiguity.
Consequences: a normalised comparison is one more rule to state and pin; "waiting" defined by the exchange as well as the file changes what `--answer` accepts after a deletion.
Recommendation: treat an edit that changes only line ends and trailing whitespace as no edit (compare after `\r\n`→`\n` and trimming trailing whitespace per line and at the end); a whitespace-only edit plus a flag takes the flag. Let `--answer` answer the exchange's last unanswered question when `questions.md` is gone (nothing to move). Spec cases (retry.spec, promoted): a final newline added plus `--answer` stores the flag; a blank edit refused with that hint; a deleted `questions.md` plus `--answer` stores the answer after the question. Where: Design, The dispatcher, 8 ("`retry new` with a recorded ask re-runs z-ticket with those words (a failed capture is retried the same way)"); the prototype's `retry` (`elseif ask then … dispatcher.chain(ctx, "", o3, st)`), where the chain computes `--before` afresh.

### F11 [low] A step is told "This is a re-run: you stopped this run with a question" whenever it asked the latest question of the folder, however long ago
