### F1 [high] A z-ticket that makes its issue and then asks a question is never checked, so the answer's retry captures the request a second time
Where: Design, The dispatcher, 8 ("A capture that waits on a question is never compared: z-ticket was judged and made nothing … the z-ticket step's own check already takes its own snapshot at every start"); prototype `modelStep`, `if step == "z-ticket" and outcome == "ok" and not fs.isFile(`{stateDir}/questions.md`) then` (the made-check is skipped whenever `questions.md` exists); `retry`, `if st.before and not unanswered and not opts["--recapture"] then`.
Evidence: probe P1. z-ticket in `script` mode runs `./zn new issue c made-then-asked …; printf '## Q1\nShould I also capture the follow-up?\n' > "$ZN_DISPATCH_DIR/questions.md"`. `dispatch new "make one thing"` stops "needs the user … retry new --answer", exchange `001-ask.md,002-question.md`, and c0020 is on origin. Then `retry new --answer "No, just the one."` with z-ticket in `ticket` mode: z-ticket runs a second time ("z-ticket runs: 2"), makes c0030 ("spend: c0030 capture 123 tokens"), the exchange moves to c0030 and the chain goes on with z-design c0030. Origin now holds `c0020` and `c0030` for one request; c0020 has no exchange and no run, and nothing told the user it exists.
Critique: round 3's fix exempts a question stop from the guard on the premise "z-ticket was judged", but the judgement (the made-check) is exactly what is skipped when `questions.md` exists: the two exemptions stack, and the double capture review 002 F6 closed is open again on this path, with no kill needed. A model that captures and then asks a follow-up ("should I also capture X?") is an ordinary behaviour, and c0260's interview adds more question rounds after the restatement. The tempting fix is to run the made-check at a question stop too and fail the step when it finds one issue; over origin's issue list that check is again the shared-state count F2 is about (another session's capture during the step makes it "made 1").
Consequences: a z-ticket that made an issue and asked needs a defined outcome: either the question belongs to the issue it made (the slot is finished, the exchange and `questions.md` move to the issue, and the user answers with `retry <cX>`, whose re-run step is z-ticket for an existing issue, which c0117's chain may not allow), or the stop is a failure naming the issue (z-ticket must ask before it makes), with the question set aside so the user sees it. Either needs the issues this run made, which F2's record gives exactly.
Recommendation: at every z-ticket end, question or not, compute what this run made (F2's record of its own pushes); when it made an issue and left `questions.md`, fail the step with "z-ticket made <cX> and asked a question: a capture asks before it makes; ./zn dispatch <cX> goes on with the issue, or retry new --forget-exchange drops the capture" and set the question aside as `questions-refused-N.md` (the existing failure path), so `retry new` then refuses by the ordinary check. State the rule in Design 8 in place of "was judged and made nothing". Spec case (capture.spec, promoted): P1's sequence expects the stop to fail naming c0020, `retry new --answer …` to be refused before any z-ticket starts, and one issue on origin. Row: "a question stop after an issue was made is not a waiting capture" (mutant: today's `not fs.isFile(questions.md)` guard on the made-check).
Lesson: z-design/slot-state-proven-by-two-runs

### F2 [medium] The refusal-with-a-flag rests on "no list of this run's issues is exact", but the broker can record each push before it makes it and the retry can verify it exactly; without that the refusal names the wrong issue and its flag invites a double capture
Where: Design, The dispatcher, 8 ("the dispatcher cannot record a push before it happens, and the broker pushes whole fast-forwards of main, so no list of this run's issues is exact"); Unknowns, Decided here; design-refute-003 F1; prototype `retry` (the `made` list over `ctx.originIssueIds()` against `st.before`) and `modelStep`'s `push` closure (`if ok then table.insert(st.pushed, sha) end`, saved only at the step's end).
Evidence: probe P3. z-ticket's script lands `another-sessions-thing` (c0050, standing in for another session's capture during the step) and then this capture's `this-captures-thing` (c0060), then `kill -9 "$ZN_DISPATCHER_PID"`. `retry new` prints "stop: c0050, c0060 was made since this capture began: if it is this capture, ./zn dispatch c0050 goes on with it; if it is another session's, ./zn dispatch retry new --recapture runs the capture again …". It sends the user to the other session's issue, and when two are listed the either/or has no right branch: the user who reads c0050 as not theirs and runs `--recapture` captures the request twice. On the premise: every push from a dispatched step goes through this dispatcher's broker (`publish.luau` and `main.luau` call `broker.request` whenever `ZN_PUBLISH_BROKER` is set), and `broker.push` holds both ends of the push before it runs `git push`: `fresh` (origin's main, just fetched) and `sha` (the request, refused unless `fresh` is its ancestor). The commits `fresh..sha` are therefore only this step's commits, whatever other sessions landed before. The push cannot be recorded after it happens, but its intent can be recorded before it, and its outcome checked afterwards against origin (`git merge-base --is-ancestor <sha> origin/main`): exact, crash-proof (a kill before, during or after the push leaves the intent, and origin says whether it landed), and the pattern this prep's own lesson zz-arch/record-crash-states-when-entered asks for.
Critique: "Decided here" turns a solvable correctness question into a user decision on information that cannot decide it (P3), at the cost of a flag, a refusal on every failed capture on a busy repository, and a docs sentence. The tempting fix is to sort the list or print titles; the user still has to guess.
Consequences: the state gains `pushing: { { base, sha } }` (or `pushed` entries gain their base and are saved before the push); `broker.push` gains an optional hook called between its ancestry check and `git push` (broker.luau joins Touched modules; c0117's broker cases keep passing with the hook absent); `retry new` lists the issue files added in `base..sha` for each recorded push that is on origin; `--recapture` and its help and zz-rules text go (or stay as a no-op only if c0247/c0260 name it, which they do not); the same record makes F1's check exact, and could make c0117's own "z-ticket made N issues, not one" exact too (optional, say so in Existing work if not done).
Recommendation: record each broker push's `{base, sha}` in the run's state, saved before `git push`; `retry new` (and F1's check) count only issues added by recorded pushes that reached origin; drop `--recapture`. Spec cases (capture.spec, promoted): P3's sequence expects the refusal to name c0060 only; "a failed capture beside an issue another session made" expects `retry new` to re-run z-ticket with no flag; the existing "landed its issue and died" case still refuses. Rows: "only this run's pushes count" (mutant: any new issue on origin counts), "the push is recorded before it is made" (mutant: recorded after `git push`, killed by the kill-9 case).
