### F1 [high] A failed `git fetch` makes `issuesAddedBy` silently return nothing, so `retry new` captures the request a second time
Where: Design, The dispatcher, 9 ("`ctx.issuesAddedBy(pushes)` … fetches origin and returns the issue files added in `base..sha` for each push whose `sha` is an ancestor of `origin/main`"); prototype `main.luau` `issuesAddedBy`: `sh.run("git", { "fetch", "-q", "origin", "main" })` (its result is dropped; `sh.run` never throws), then `merge-base --is-ancestor push.sha origin/main` (any non-zero exit, an error included, reads as "did not land") and `if added.ok then … end` (a failed diff is skipped); `retry`'s `if #made > 0 then return refuse(…)`.
Evidence: probe P1. z-ticket in `script` mode runs `./zn new issue c landed-thing …; kill -9 "$ZN_DISPATCHER_PID"` under `dispatch new "words whose capture dies"`: c0020 lands on origin and `state.json` holds 1 recorded push. Then `retry new` with a `git` wrapper first on PATH that fails only the first `git fetch -q origin main` it sees (a network blip; every other git call passes, so the broker's and the guards' fetches from the pinned URL succeed). The retry prints no refusal and no warning: "next: z-ticket … ok (done) … spend: c0030 capture … next: z-design c0030 …", exit 1 only at z-design's own claim check; the wrapper's marker shows its one fetch failed; origin afterwards holds `c0010/c0010.md c0020/c0020.md c0030/c0030.md`. One request, two issues, c0020 orphaned with no run and no exchange, and nothing told the user. The broker's push is to the pinned URL, which never moves `refs/remotes/origin/main`, so after a kill the tracking ref is stale and the check rests entirely on that one fetch. All 67 c0256 cases pass on the prototype that ignores it.
Critique: Design 8 promises "the capture is never made twice"; that guard now has a silent off switch on the commonest failure there is. It also departs from the dispatcher's own rule for reading main ("freshly fetched from the pinned URL into a ref of the dispatcher's own (never the tracking ref an agent can rewrite, never `origin` as the configuration says later)", `freshMain` in `dispatcher.luau`): `issuesAddedBy` fetches `origin` as the shared configuration resolves it, once, without the retries `broker.push` uses, and reads `origin/main`, which a step can rewrite and which keeps whatever a step wrote when that fetch fails (the z-ticket made-check runs right after the step). The tempting fix is to check the fetch's `ok` and return `{}` with a warning; an empty list still means "nothing made", so the retry goes on and the double capture stays.
Consequences: `issuesAddedBy` gets three answers, not two: the ids, "none", or "cannot tell" (fetch failed, `merge-base` exited other than 0 or 1, `diff` failed). Each caller needs a rule for "cannot tell": `retry new` refuses before anything moves, naming the reason ("cannot tell whether this capture made an issue: <why>; nothing was changed, run the retry again"); the z-ticket made-check at a step's end fails the step without a question ("could not tell what z-ticket made: <why>; ./zn dispatch retry new checks again") or, when `questions.md` waits, leaves it waiting (the retry's own check runs before the answer is taken, so it refuses then if an issue was made). Moving the read into `dispatcher.luau` over `freshMain` (pinned URL, own ref, its retries) keeps one reader of main; the `Ctx` field changes type, and every fake or test context that builds a `Ctx` follows.
Recommendation: make `issuesAddedBy` return `({ string }?, string?)`: nil and the reason when the fetch (from the pinned URL into the dispatcher's own ref, as `freshMain` does, with its retries) fails, when `merge-base --is-ancestor` exits with anything but 0 or 1, or when the diff fails; ancestry is judged against that fetched ref, never `origin/main`. `retry new` refuses on nil before anything moves, naming the reason; the z-ticket check at a step's end fails the step on nil (or, with `questions.md`, leaves the question waiting for the retry's check). Add to Design 9 one sentence ("a check that cannot tell refuses, never reads as none"). Spec case (capture.spec, promoted): P1's sequence, with the wrapper under the fixture's `.cache` folder failing the first `fetch` it sees: `retry new` exits non-zero naming the fetch, starts no z-ticket and origin keeps one issue for the capture; a second plain `retry new` then refuses naming that issue. Row: "a check that cannot tell what a capture made refuses" (mutant: the fetch's result ignored; mutant: a `merge-base` error read as not landed, reasoned if no fixture can make it error). Hardening worth one word in the same sentence: `git diff --no-renames`, so a user's `diff.renames=copies` cannot turn a new issue file into a copy and hide it from `--diff-filter=A`.
Lesson: zz-arch/guards-count-only-this-runs-writes
