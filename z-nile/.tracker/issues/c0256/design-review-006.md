### F1 [medium] On every path where `retry new` finds "made by this capture", the capture's exchange never reaches the issue it made, and the only way on sets the user's words aside
Where: Design, The dispatcher, 3 ("`./zn dispatch <id>` goes on with the issue, or `retry new --forget-exchange` drops the capture"), 8 ("`retry new` … any refuses, naming exactly those … so the capture is never made twice"; "the exchange moves with it, seal included, so the capture's whole conversation belongs to the item it made. c0260 reads it from there"), 9 ("the z-ticket step's end fails the step … `retry new` checks again"); AC5 ("the whole exchange moves to the issue it made, which the next step reads as other steps' messages"); prototype `retry` (`elseif #made > 0 then return refuse(…)`) and `modelStep` (the exchange moves only in the `target = made[1]` branch).
Evidence: probe P1, deterministic, no kill. z-ticket in `script` mode runs `./zn new issue c made-then-asked …; printf '## Q1\nShould I also capture the follow-up?\n' > "$ZN_DISPATCH_DIR/questions.md"`. `dispatch new "make one thing"` fails as designed ("z-ticket made c0020 and asked a question … ./zn dispatch c0020 goes on with the issue"); `retry new` refuses ("c0020 was made by this capture: ./zn dispatch c0020 goes on with it, or … --forget-exchange drops the capture's words"). Following that advice, `dispatch c0020` runs z-design c0020, whose prompt names no exchange (`P1 z-design prompt names an exchange: false`), and the folders read `new/exchange: 001-ask.md`, `c0020/exchange:` (empty). The slot then stays blocked: `dispatch new` refuses "a capture failed and still has its words", and the only way on, `retry new --forget-exchange`, leaves the user's dated ask in `new/exchange-forgotten-1794445803`, belonging to no item. The same refusal is the outcome of the other two paths the design routes there: a z-ticket that landed its issue and was killed (capture.spec's own case ends with `--forget-exchange`), and since round 5 a z-ticket that made its issue while `issuesAddedBy` could not tell (the step fails, "`retry new` checks again", and the retry then refuses naming the issue). In all three the capture succeeded on origin, so it is the issue, not the slot, that should hold the conversation.
Critique: rounds 2 to 5 each found a hole in "refuse naming the issue" as a guard against a second capture, and that part now holds. What the refusal leaves behind was never designed: the issue is told to go on without the ask, dated from the first message, that the widened scope ("every restatement and every correction of the capture … each with its date") and c0260's later steps read from `<id>/exchange/`, and the user has to throw that record away to capture anything else. The fix that suggests itself, naming the exchange folder in the refusal so the user can move it by hand, writes into a folder the dispatcher seals and gives the user a manual repair on a path the dispatcher already knows the answer to.
Consequences: an "adopt" outcome for a capture whose own pushes made exactly one issue: the slot is saved finished ("captured as <id>", no seal, as the success path does), the exchange moves to `<id>` and the issue's state is saved with the seal right after (the existing adjacent save). That brings three rules. (1) `<id>` already has an exchange (the user ran `dispatch <id>` first and a step there asked): refuse, naming both folders, and move nothing. (2) More than one issue made: keep today's refusal naming all of them, since no single item owns the conversation. (3) The made-then-asked question, which never entered the exchange, stays set aside as `questions-refused-N.md` but must be findable from the issue (moved beside the exchange, or named in the failure message). The zz-rules sentence "the retry names that issue, and `./zn dispatch <id>` goes on with it" gains "and moves the capture's exchange to it" (not an AC7 pin), and the `--forget-exchange` branch of the "made by this capture" message goes.
Recommendation: when `retry new` (and the made-then-asked end of a z-ticket step, which can tell) finds that this capture's pushes made exactly one issue, finish the capture as the success path does: adopt the issue, move the exchange with its seal, and either go on with `<id>`'s chain or print "captured as <id>: ./zn dispatch <id> goes on with it". Refuse when `<id>` already holds an exchange, and keep the refusal for more than one issue. State it in Design 8 and 9, in place of "goes on with it, or … drops the capture's words". Spec cases (capture.spec, promoted): in "a z-ticket that made an issue and then asked …", after the failure `new/exchange` is empty and `<id>/exchange` is `001-ask.md`, and the next `dispatch new "<words>"` is taken without `--forget-exchange`; in "landed its issue and died …", after the second plain `retry new`, `<id>/exchange` holds the ask and z-design `<id>`'s prompt names it; a case where `<id>` already has an exchange is refused with nothing moved. Rows: "a capture whose own pushes made one issue gives that issue its exchange" (mutant: today's refusal), "an issue that already has an exchange is not overwritten" (mutant: the move without the test).
Lesson: z-design/results-land-on-every-path

### F2 [low] `issuesAddedBy` brings a third reader of the tracker's item paths, matching neither existing one, and the design does not say which paths count
Where: prototype `dispatcher.issuesAddedBy`, `string.match(path, "/issues/(%w+)/(%w+)%.md$")` with `store.isIssueId`; the removed `originIssueIds` used `publish.itemPath`; `trackerstate.itemOf` is the dispatcher's own reader for tracker paths (lifecycle leads `active/`, `done/`); Design 9 ("returns the issue files added in `base..sha`").
Evidence: `publish.itemPath` strips `active/` and `done/` and requires `[fdc]%d%d%d%d`; the new pattern matches only a backlog path (`…/issues/<id>/<id>.md`), and none under a lifecycle folder. That is the right set for "a capture made it", because `--no-renames` reports any move as an add (an issue moved into `done/` would show up as added under `publish.itemPath`). But the design names neither the set nor the reason, so an executor who follows zz-arch's rule 5 and switches to `publish.itemPath` would count moves as captures.
Critique: zz-arch rule 5 ("One reader per format") and its lesson ask for the existing reader to be reused, or for a new one to match it exactly and say so. This one differs on purpose and says nothing.
Consequences: none beyond one sentence and a case.
Recommendation: build the test on `trackerstate.itemOf` (rel `<id>.md`, no lifecycle lead) or keep the pattern, and either way add to Design 9: "an issue is made when its backlog document `<root>/issues/<id>/<id>.md` is added; with `--no-renames` a move shows as an add, so lifecycle folders never count". Add the reasoned row "a moved issue is not a made one" (mutant: `publish.itemPath`), or a case whose pushes move an issue into `done/`.
Lesson: zz-arch/one-reader-per-format
