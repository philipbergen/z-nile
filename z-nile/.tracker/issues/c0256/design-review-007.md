### F2 [high] Item 10 still refuses to adopt into an issue that has an exchange of its own, which is where the made-and-asked stop sends the user; the capture is then stuck for good
Where: Design 10 (the adoption) and 8 ("refused if the issue already has an exchange"); prototype `dispatcher.finishCapture` (`if fs.isDir(\`{dest}/{exchange.DIR}\`) … return \`{target} already has an exchange\`` runs before `lock(dest, true)`); Rules and mutants row C57 ("the 'issue already has an exchange' refusal: reasoned"); the made-and-asked stop text "./zn dispatch <id> goes on with the issue, or … --forget-exchange drops the capture".
Evidence: probe P1, on the prototype. z-ticket makes c0020 and writes questions.md, and the step fails "made c0020 and asked a question". The user does what the stop says: `./zn dispatch c0020`. The slot keeps `[001-ask.md]`. `dispatch new "other words"` prints "stop: a capture failed and still has its words: ./zn dispatch retry new re-runs it, or ./zn dispatch retry new --forget-exchange drops it". The only way on is `--forget-exchange`, which sets the user's dated ask aside in the slot, so it never reaches c0020. Any question z-design asks causes this. Under c0260 (which depends on this issue), z-design always stops on a dispatched capture to confirm it ("a `questions.md` stop, safe because the issue exists"), so in c0260's world the path is certain. R0093 code review 001 F1's Consequences assumed that "an issue that has an exchange is already refused" was harmless, and item 10 inherited that.
Critique: item 10 exists for exactly this path ("the stop of 'z-ticket made <id> and asked' tells the user to go on with `./zn dispatch <id>`"), and it closes it only when the issue's first steps asked nothing. AC9 covers only a z-design in `ok` mode. Separately, the exchange test runs before the issue's lock is taken, so an issue run that ends between the test and the lock can leave an exchange that `fs.move` then lands on. That breaks the rule of the lesson this prep added. The tempting fixes are to name `--forget-exchange` in the refusal, which throws the conversation away, or to reword the stop message, which does not help a user who already ran `./zn dispatch <id>`.
Consequences: a join is safe. A capture's exchange ends in an ask or an answer at adoption: its question is either set aside (made and asked) or never copied (killed before the copy). An issue's own exchange starts with a question (only `dispatch new` writes an ask). So "the capture's messages first, the issue's renumbered after them" passes `exchange.order`. The issue's waiting `questions.md` and `st.answering` (a hash of the file, not a name) are untouched, and its next prompt still takes the asker and the last step from the issue's own entries and history. The join is a rename under a lock, with two seals to check first and one to save after, so it needs a crash rule: build the joined folder beside the old one, set the old one aside, move the new one in, then save the seal (adjacent statements, as in Accepted). That contradicts "keeps that state whole". It happens only when an issue made seconds earlier already has a run, so either keep those fields there too or refuse in that path and let `retry new` adopt.
Recommendation: in `finishCapture`, take `lock(dest, true)` first, then read both exchanges through `exchangeRead` (the issue's against its own seal). When the issue has messages, join them as above in place of the refusal, and refuse only an unreadable exchange (naming `--forget-exchange` for the one that is damaged). Make the made-and-asked stop name `./zn dispatch retry new` first ("gives <id> its conversation"), and keep `./zn dispatch <id>` as the second way on, since both orders now work. Add an adopt.spec case: made-and-asked, then `./zn dispatch <id>` with z-design in `questions` mode, then `retry new` is ok. The issue's exchange is `001-ask.md,002-question.md` (the question's `step: z-design` kept), `retry <id> --answer x` stores `003-answer.md`, the re-run z-design's prompt has "This is a re-run", and `dispatch new "other words"` then runs z-ticket. The mutant is the refusal kept. Make the row "the exchange test is taken under the lock" reasoned (no deterministic race). Update the zz-rules bullet ("its conversation moves to it") only if its wording no longer holds.

### F5 [medium] adopt.spec waits a fixed 4 seconds for a killed dispatcher's step to end, as retry.spec and capture.spec do; under this machine's load that makes a sequestered spec flaky
Where: `acceptance/adopt.spec.luau:260` (`task.wait(4) -- the step the killed dispatcher left behind ends by itself; its run is held until then`); the same wait at `retry.spec.luau:540` and `capture.spec.luau:377`.
