# c0257: Omarchy board app

## Problem
A native omarchy-shell app (bar icon + tiled window) that shows every znile ticket and raft, kept in z-nile-omarchy/

User (2026-11-07): "We need a rank field that if unset is lowest rank and falls back to ticket number (always a stable sort order), we want the z-nile ui in omarchy to reflect this and we want drag and drop reordering."

Added by the user (2026-11-07):
- The app orders tickets and rafts by the order c0249 defines: lost work first (c0265), then rank, with unset ranks last and the ticket number as the tiebreak.
- It marks lost items.
- Drag and drop sets the rank through `./zn rank` once c0249 exists. Until then it keeps the order for the session, as it does today.

Decided with the user (2026-11-11), in c0249's idea interview Q3: "c0249 wires it" (c0249 builds `./zn rank` and sets this app's `rankCommand` to it, so a drag persists as a rank on origin/main; c0249 depends on c0257 landing first).

Owners (idea review 002, 2026-11-11): the app's rank order (unset last, the ticket number as the tiebreak) and the `rankCommand` wiring are c0249's; lost work first in the app, and its marks, are c0290's (the user, 2026-11-09).

## Non-goals
- No change to the board engine or the board page: the app reads what `./zn board` already writes (the page's embedded `board-data` JSON). A `./zn board --json` is not built here (c0121's served board or a later chore may; the app takes it when it exists, and it must print the same model).
- Rank order, lost-work-first order and the lost marks are c0249's and c0290's (the Owners line in the Problem). Persisting a drag is c0249's (`rankCommand`).
- No Roblox, Luau or game code of the app: its home has no `src/`, `.luaurc`, Rojo files or Lune runner. It is a registered project of the new `app` kind (G1, ruled), and nothing else about an app home is built here: promoting Luau acceptance specs into an app home (`./zn done`'s promoted checks need the home's `tests/run`) stays unsupported and fails loudly as it does today; c0257 itself stays a z-nile chore in z-nile's root, because it changes the engine and the gate.
- The app never writes tracker state itself. Every action goes through an external command given as an argument array (a terminal with the chosen AI CLI, `wl-copy`, the configured `rankCommand`).

## Solution
Land the working prototype (pull request #243, branch `omarchy-board-app`, commit `38f7334788efc7b3f3701a7d1ae905f9dbaf3ae3`, built outside the pipeline) with every change made on it up to that commit (the user, 2026-11-16: "carry all changes in the raft"; besides the prototype reviewed at `e467e31`, it adds the cycling blocked/unblocked and approval chips, Esc stepping back one level, the guesses-to-review chips, fetch.sh's `approved` list and the Qt 6.12 crash avoidance of d0389, with 20 model tests) as `z-nile-omarchy/znile.board/`, and make it gateable: the prototype's node test, a hermetic spec for `fetch.sh`, a contract spec between the engine's board page and the app's model, text specs for the package, its documents and its no-shell rule, a deploy-workflow ignore for the folder, a watch-map rule so a change to the app selects these specs, and READMEs whose test command works on today's node. The prototype's behaviour stays as it is: the executor takes the files from the commit above and changes only what the Design lists.

## Design

### What the app is (from the prototype; the Design pins what the specs can reach)
A native omarchy-shell plugin (Quickshell, QML) `znile.board`, kinds `service`, `bar-widget`, `panel`:
- `Service.qml` runs `fetch.sh <repo>` on a timer (`refreshIntervalSec`, default 120 s) and when asked, `prs.sh` (open pull requests, `[]` when `gh` cannot answer) and `agents.sh` (installed AI CLIs). Every external program is started with an argument array (`Process.command`, `Quickshell.execDetached`), never a shell string.
- `BarWidget.qml`: a kanban glyph with the active ticket count; click opens the panel, right-click refreshes.
- `Board.qml` (the panel) with `TicketTile`, `Chip`, `IdChip`, `IdLinks`, `CopyBox`, `TypeBadge`, `PlainLabel`, `SmoothWheel`, `NewTicketDialog`: columns New, Preparing, Prepared, Active (Done behind a chip), a Tickets/Rafts switch, stage bar, 30-day opened/closed chart, project/type/blocked filters and search; cards with type, project, pipeline bar, raft, blockers, open PRs, cost and the next command; details beside the card with the description as sanitised markdown; dive-in (a new terminal in the repo with the chosen AI CLI in its ask-first mode); drag within a column to reorder.
- `Model.js` (`.pragma library`, pure): `normalize(raw)` (ids validated against `^[fdcR][0-9]{4}$`, text clipped, unknown stages become `new`, blockers computed: dependencies outside the item's raft block, in-raft ones only order; a raft lists its blocked tickets), `columns`, `sortByPriority`, `reorder`, `rankArgv`, `safeMarkdown`, `attachPrs`, agent argv, cost roll-ups, `activity` and `weekSummary` (the chart).
- `fetch.sh <repo>`: `./zn board --json` if `z-nile/engine/main.luau` has that flag, else `./zn board -O --out <cache>/board.html` and the JSON the page embeds (`<script type="application/json" id="board-data">`); adds `projects` (id to project, from which registered root holds the item's folder, via `lune run z-nile/roots -- --projects`), `projectOrder`, `paths`, `spend` (each item's `spend.md` totals line and phase rows), `webBase` (from a github `origin` in its three spellings), `repo`, `fetchedAt`; drops `home`. Exit 2 with no `./zn`, 3 with no `lune`, 4 with no `python3`.

### Its own project, of a new kind (G1, ruled 2026-11-16)
`z-nile-omarchy/` at the repository root, as captured ("kept in z-nile-omarchy/"), is a **registered project of its own** (the user: "it is its own thing", carried inside c0257). Today every registered project but z-nile must have a Luau home, which an app of QML, JS and shell does not have, so the registry gets a project **kind**:
- **Registry.** `z-nile/projects.toml` gains `[[project]] name = "z-nile-omarchy"`, `root = "z-nile-omarchy/.tracker"`, `kind = "app"`, last. `z-nile/engine/projects.luau`'s `parse` accepts the key `kind` with the one value `"app"` (any other value, or `kind` on a project named `z-nile`, is refused, naming the project); a project without it is a Luau project, as every one is today. Each `Project` keeps exactly `{ name, root, home }` (the promoted c0114 and c0120 registry specs compare whole tables with `toEqual`), and the registry gains `apps: { string }`, the app projects' names in registry order (empty when there are none). `lune run z-nile/roots -- --projects` keeps its three columns; a new `--apps` prints the app names, one per line; `--luau-dirs` leaves app homes out (their `.tracker/` root is still listed, as every root is).
- **Its home** is `z-nile-omarchy/`: `check.sh` (`exec bash "$(dirname "$0")/../z-nile/check.sh" --project z-nile-omarchy "$@"`, executable), its root `.tracker/` with `architecture.md` (what the app is, no `deps` block: it requires no Luau module) and empty `issues/` and `rafts/` (each kept by a `.gitkeep`), the skills `skills/z-nile-omarchy-arch/SKILL.md` (the plugin's structure: pure `Model.js` versus QML, argument arrays only, untrusted text, and the Qt 6.12 markdown rule of d0389) and `skills/z-nile-omarchy-test/SKILL.md` (node tests in `znile.board/tests/`, run by the gate's node stage; probes through `./zn run`), linked by `./zn skills`, and the plugin `znile.board/` with the top `README.md`. No `.luaurc`, `src/`, `tests/` or project file.
- **The home rule** (`z-nile/tests/lib/home.luau`, `problems`) checks an app home for what an app home has, and nothing of a Luau home: `check.sh` with that exact line and executable; the root with `issues/` and `rafts/`; the two skills. It reports each missing piece by name, as it does for a Luau home, and returns the app in `checked`. A Luau project is checked exactly as today.
- **The gate** (`z-nile/check.sh`) reads `lune run z-nile/roots -- --apps` once. For a picked app it adds nothing to the format, lint, Lune-types or build stages (an app home has no Luau; today a home without `src/` is treated as tooling and its whole folder would go to luau-lsp) and runs no spec stage. Instead it runs a **node stage**: `node --test` on every `*.test.mjs` under `<home>/*/tests/` (sorted; a stage failure when there are none), from the checkout's top, and fails the gate when node fails. `--plan` prints `node: <file> ...` for each picked app. Selection: `--full` and `--project z-nile-omarchy` pick it; `--affected` and `--static` pick it when a changed path is under its home (`select.staticProjects` already maps a home's paths to its project; AC13 pins it).
- **Skill names.** z-nile keeps the `z-` and `zz-` prefixes (`z-nile/engine/skills.luau`, `plan`), and the project's own name starts with `z-`: a skill named `<project>-…` in a project's `skills/` is that project's even when the project's name starts with `z-`, unless the project is named `z` or `zz` (c0115's case for a project `zz` stays as it is). AC12 pins it. `./zn skills` links the two new skills into `.claude/skills/`.
- **Watch map.** `watch.forSuite` keeps an app's paths for a tooling spec (AC10, G8): a z-nile spec that reads the app (the c0257 specs) is selected when the app changes. An app's own node tests are run by the node stage whenever its home changed, so they need no watch file.
- **Deploy.** The app never publishes a Roblox place (G3, the user: "app is a no deploy for roblox"): `deploylist.luau` yields `<home>/**` for an app (the whole home, which holds its root) and `<root>/**` for a Luau project, in registry order, then `z-nile/next`; `deploy.yml`'s push ignore list gets `'z-nile-omarchy/**'` after `'asteroids/.tracker/**'`. The two specs that compare the list with the registry (`c0120/ci`, `c0114/gate-cover`) read it through `deploylist.luau` and are not edited.
- **Who owns what.** This issue (c0257) is z-nile's: its specs promote to `z-nile/tests/acceptance/c0257/`. New tickets for the app are captured with `--project z-nile-omarchy` (or from inside `z-nile-omarchy/`) and live in its root; their acceptance is node tests and `check.sh` checks, since an app home cannot promote Luau specs (Non-goals). c0249 and c0290 stay where they are.
- **Docs.** `z-nile/README.md`'s "A project's home" gets the app kind (what an app home holds, that the gate runs its node tests and no Luau stages, that it never deploys); `AGENTS.md` names `z-nile-omarchy/` and its two skills in the skills table; `zz-rules` (Projects) names the `kind` key. The sentences c0184/docs pins verbatim (AGENTS.md's "Every project with code has the same home as `pickman/` (c0184)", README's "the gate checks it for every project of `z-nile/projects.toml` except z-nile") are kept word for word, and the app kind is a new sentence after each. c0184/docs also wants, for every project but z-nile and pickman, an AGENTS.md line naming its `-arch/SKILL.md` and a README line naming its `-arch` and `-test` skills: the app's two skills satisfy it, so that spec is not edited.

### Scalability
The board page's JSON is large: today `fetch.sh` prints 9.77 MB for 356 issues and 101 rafts (probe E2; the page carries every body, the history and the charts), in 2.1 s on this machine, every `refreshIntervalSec` (120 s) and when `main` moves. `Model.normalize` clips titles to 200 and bodies to 6,000 characters, but the JSON is parsed whole. That is acceptable at this size and the refresh never overlaps itself (`Service.qml` queues one more); if the board grows past a few tens of MB the fix is `./zn board --json` with only what the app reads, not a change to the app (Guess G5).

### Maintainability
One pure module (`Model.js`) holds every rule and is tested under node; the QML is rendering and process wiring. The contract with the engine is one place (`fetch.sh` and the keys `Model.normalize`, `activity` and `weekSummary` read), pinned by AC7 and AC8. **How an engine change is caught:** a change to `z-nile/engine/board.luau` or `stats.luau` selects c0257's specs under `--affected` only if the specs' watch map names it; `./zn finish` writes that map from the changed sources of this layer's own diff, and this layer changes no engine file, so the map names the app's paths (AC10) and not the engine's. A rename in the engine is therefore caught at the merge gate (`z-nile/check.sh --full` runs every spec) and then, if it slipped, by the watch net, which adds the file to the spec's watch. The app's own files are selected by the watch map from the first change (AC10). Known debt: `Board.qml` is 1,113 lines; splitting it is a later chore (not captured here).

### Usability
The app is a convenience view: a person sees every ticket and raft at a glance, where it is in the pipeline, what blocks it, and can dive in with the AI CLI of their choice, in ask-first mode. Errors: a missing repo path, `lune`, `python3` or `./zn` show the script's message in the panel (exit 2, 3, 4; AC7 for 2 and 3); `gh` failing leaves `[]` and the board still loads (AC7). Drag works within a column and lasts for the session until `rankCommand` is set.

### Security
Tracker text is untrusted. Titles render as plain text; descriptions through `safeMarkdown` (every `<` outside code becomes `&lt;`, images become links); ids are matched against `^[fdcR][0-9]{4}$` before use; document paths with `..` are dropped; links only for a `https://github.com/<owner>/<repo>/blob/main/` base; PR links only for `https://github.com/.../pull/<n>`. The AI CLI starts in a new terminal with its normal ask-first mode (no agent's argv carries an auto-approve flag: a rule with its own case), on a click; `rankCommand` runs as an argument array with each `{id}`/`{beforeId}` replaced inside one element. These rules are pinned in the sequestered `rules.test.mjs`, not only in the app's own test file.
