# c0257: Omarchy board app

## Problem
A native omarchy-shell app (bar icon + tiled window) that shows every znile ticket and raft, kept in z-nile-omarchy/

User (2026-11-07): "We need a rank field that if unset is lowest rank and falls back to ticket number (always a stable sort order), we want the z-nile ui in omarchy to reflect this and we want drag and drop reordering."

Added by the user (2026-11-07):
- The app orders tickets and rafts by the order c0249 defines: lost work first (c0265), then rank, with unset ranks last and the ticket number as the tiebreak.
- It marks lost items.
- Drag and drop sets the rank through `./zn rank` once c0249 exists. Until then it keeps the order for the session, as it does today.

Decided with the user (2026-11-11), in c0249's idea interview Q3: "c0249 wires it" (c0249 builds `./zn rank` and sets this app's `rankCommand` to it, so a drag persists as a rank on origin/main; c0249 depends on c0257 landing first).

Owners (idea review 002, 2026-11-11): the app's rank order (unset last, the ticket number as the tiebreak) and the `rankCommand` wiring are c0249's; lost work first in the app, and its marks, are c0290's (the user, 2026-11-09).

## Non-goals
- No change to the engine or the board page: the app reads what `./zn board` already writes (the page's embedded `board-data` JSON). A `./zn board --json` is not built here (c0121's served board or a later chore may; the app takes it when it exists, and it must print the same model).
- Rank order, lost-work-first order and the lost marks are c0249's and c0290's (the Owners line in the Problem). Persisting a drag is c0249's (`rankCommand`).
- No Roblox, Luau or game code. The app is not a registered project and has no `src/`, `.luaurc` or Rojo files.
- The app never writes tracker state itself. Every action goes through an external command given as an argument array (a terminal with the chosen AI CLI, `wl-copy`, the configured `rankCommand`).

## Solution
Land the working prototype (pull request #243, branch `omarchy-board-app`, commit `e467e31017007f60dccd73e7550cf6b23547a880`, built outside the pipeline) as `z-nile-omarchy/znile.board/`, and make it gateable: the prototype's node test, a hermetic spec for `fetch.sh`, a contract spec between the engine's board page and the app's model, text specs for the package and its no-shell rule, a deploy-workflow ignore for the folder, and a README whose test command works on today's node. The prototype's behaviour stays as it is: the executor copies it from the branch (`git checkout origin/omarchy-board-app -- z-nile-omarchy`) and changes only what the Design lists.

## Design

### What the app is (from the prototype; the Design pins what the specs can reach)
A native omarchy-shell plugin (Quickshell, QML) `znile.board`, kinds `service`, `bar-widget`, `panel`:
- `Service.qml` runs `fetch.sh <repo>` on a timer (`refreshIntervalSec`, default 120 s) and when asked, `prs.sh` (open pull requests, `[]` when `gh` cannot answer) and `agents.sh` (installed AI CLIs). Every external program is started with an argument array (`Process.command`, `Quickshell.execDetached`), never a shell string.
- `BarWidget.qml`: a kanban glyph with the active ticket count; click opens the panel, right-click refreshes.
- `Board.qml` (the panel) with `TicketTile`, `Chip`, `IdChip`, `IdLinks`, `CopyBox`, `TypeBadge`, `PlainLabel`, `SmoothWheel`, `NewTicketDialog`: columns New, Preparing, Prepared, Active (Done behind a chip), a Tickets/Rafts switch, stage bar, 30-day opened/closed chart, project/type/blocked filters and search; cards with type, project, pipeline bar, raft, blockers, open PRs, cost and the next command; details beside the card with the description as sanitised markdown; dive-in (a new terminal in the repo with the chosen AI CLI in its ask-first mode); drag within a column to reorder.
- `Model.js` (`.pragma library`, pure): `normalize(raw)` (ids validated against `^[fdcR][0-9]{4}$`, text clipped, unknown stages become `new`, blockers computed: dependencies outside the item's raft block, in-raft ones only order; a raft lists its blocked tickets), `columns`, `sortByPriority`, `reorder`, `rankArgv`, `safeMarkdown`, `attachPrs`, agent argv, cost roll-ups.
- `fetch.sh <repo>`: `./zn board --json` if `z-nile/engine/main.luau` has that flag, else `./zn board -O --out <cache>/board.html` and the JSON the page embeds (`<script type="application/json" id="board-data">`); adds `projects` (id to project, from which registered root holds the item's folder, via `lune run z-nile/roots -- --projects`), `projectOrder`, `paths`, `spend` (each item's `spend.md` totals line and phase rows), `webBase`, `repo`, `fetchedAt`; drops `home`. Exit 2 with no `./zn`, 3 with no `lune`.

### Where it lives, and which project
`z-nile-omarchy/` at the repository root, as captured ("kept in z-nile-omarchy/"). It belongs to the **z-nile project**: the issue, its specs and its spend are z-nile's, and the gate that guards it is z-nile's (`z-nile/tests/acceptance/c0257/` after promotion). It is not a registered project (see Guess G1). The root belongs to no project, so the home rule, `deploy.yml`'s per-root ignores and `projects.toml` do not name it; the one place that must know it is `deploy.yml`'s push ignore list (below).

### How it is tested by the gate
The gate is Luau on Lune. The app's tests are node (Model.js is a QML `.pragma library` script that the test loads with `new Function`). Node is **already in the toolchain** (SETUP.md: "the full gate needs it": c0042's page smoke test runs the board page's scripts under node), so no toolchain is added for the model. Five spec files in `z-nile/.tracker/issues/c0257/acceptance/` (promoted to `z-nile/tests/acceptance/c0257/` by `./zn done`) reach everything a macOS or Linux CI machine can reach without Quickshell:
- `app.spec.luau` (AC1): every file of the plugin exists; `manifest.json` parses, has `schemaVersion` 1, id `znile.board`, the three kinds, and entry points that name real files; `settings.json` keeps `repoPath`, a `refreshIntervalSec` of at least 30 and an empty `rankCommand`.
- `modeltests.spec.luau` (AC2): runs the app's own `tests/model.test.mjs` under node (no failures, at least 12 passing).
- `rules.spec.luau` + `rules.test.mjs` (AC3): prep's extra cases for rules the app's tests left unpinned (the mutation check found two survivors).
- `deploy.spec.luau` (AC4), `noshell.spec.luau` (AC5), `docs.spec.luau` (AC6): text rules.
- `fetch.spec.luau` (AC7): `fetch.sh` against a fixture repository under `.cache` with stub `zn` and `lune` and `HOME` pointed into the fixture.
- `contract.spec.luau` (AC8): the engine's `board.collect`/`render` on a fixture tracker; the page's `board-data` goes through the app's `normalize` under node.
The specs find the app under the checkout; `ZN_C0257_TREE` points them at another tree that holds `z-nile-omarchy/` (prep ran them against the prototype that way; it is a test seam, read nowhere else).
The QML (rendering, drag, terminal launch) cannot run on the gate's machines; that part is **Observed** (OC1 to OC3). The QML and shell are not covered by stylua or selene; AC5 scans them for shell strings.

### Relation to the other boards (they must not diverge)
There is one model: the board page's embedded JSON, built by `board.collect` in the engine. The page (c0118), the served page (c0121, raft R0084, not landed: its `window.znBoard.load(model)` takes the same model), and this app all read it. The app reads it by key and ignores keys it does not know, so c0276's `heartbeat` and `minutes` and c0249's `rank` are additive and break nothing (c0276's ledger row for c0257 says the same). AC8 pins both halves: the keys the app reads must exist on the page's items (an engine rename fails the spec of the app's chore, not silently the app), and extra keys change nothing the app shows (rules.test.mjs, "additive keys"). The marks and the lost-first order in the app are **c0290**'s, designed after this lands and c0276 lands; the app's rank order and `rankCommand` wiring are **c0249**'s, which depends on this (c0249 sets `rankCommand`, so a drag persists). This issue keeps the order by ticket number, which is the tiebreak c0249 keeps, and keeps a drag for the session.

### Scalability
The board page's JSON is large: today `fetch.sh` prints 9.77 MB for 356 issues and 101 rafts (probe E2; the page carries every body, the history and the charts), in 2.1 s on this machine, every `refreshIntervalSec` (120 s) and when `main` moves. `Model.normalize` clips titles to 200 and bodies to 6,000 characters, but the JSON is parsed whole. That is acceptable at this size and the refresh never overlaps itself (`Service.qml` queues one more); if the board grows past a few tens of MB the fix is `./zn board --json` with only what the app reads, not a change to the app (Guess G5).

### Maintainability
One pure module (`Model.js`) holds every rule and is tested under node; the QML is rendering and process wiring. The contract with the engine is one place (`fetch.sh` and the keys `Model.normalize` reads), pinned by AC7 and AC8, so an engine change that breaks the app fails the engine chore's gate, not a person's desktop. Known debt: `Board.qml` is 1,113 lines; splitting it is a later chore (not captured here).

### Usability
The app is a convenience view: a person sees every ticket and raft at a glance, where it is in the pipeline, what blocks it, and can dive in with the AI CLI of their choice, in ask-first mode. Errors: a missing repo path, `lune` or `./zn` show the script's message in the panel (exit 2 and 3, AC7); `gh` failing leaves `[]` and the board still loads. Drag works within a column and lasts for the session until `rankCommand` is set.

### Security
Tracker text is untrusted. Titles render as plain text; descriptions through `safeMarkdown` (every `<` outside code becomes `&lt;`, images become links; AC2/AC3 cases); ids are matched against `^[fdcR][0-9]{4}$` before use; document paths with `..` are dropped; links only for a `https://github.com/<owner>/<repo>/blob/main/` base; PR links only for `https://github.com/.../pull/<n>`. The AI CLI starts in a new terminal with its normal ask-first mode (no auto-approve flag), on a click; `rankCommand` runs as an argument array with each `{id}`/`{beforeId}` replaced inside one element.
