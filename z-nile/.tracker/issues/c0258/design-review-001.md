### F2 [high] The "already landed" start check misses a branch that merged the commit an earlier land pushed, which is the Problem's own case and the state `./zn sync` produces
Where: c0258.md Design 2 (`landrace.start`, line 60; cmd.land step 1, `own` = `git diff --name-only <merge-base HEAD base> HEAD`, line 62), "Where main is today" (line 35), AC4 (line 200)
Evidence: a git probe run in `.cache/review-c0258-own` with `./zn run --time 30`. Main M0 has `x.md`. Branch `capture-x` commits C1 (edits `x.md`). Main gets S (the same edit plus `spend.d/r.tsv`, as land's commit-tree push makes it), then M2. The branch then merges main, which is what zz-rules "Landing a change" step 0 (`./zn sync`: "a fetch and a merge of `origin/main`") does, and what today's `take(now)` did after a push that reported failure but landed. Output: `own (diff fork..HEAD): 0`, `left (diff main..HEAD): 0`, `own commits not on main (no merges): C1`. So `landrace.start(0, 0)` is `nothing` (pinned by landrace.spec), and land still fails `nothing to land: this branch has no change against origin/main`, exit 1. That is the 2026-11-05 outcome the Problem reports. AC4 says "a branch whose changes `origin/main` already holds prints `already landed on main`". This branch's change, C1, is held by main, and it gets "nothing to land". landed.spec's case cherry-picks onto a fresh branch that never merged main, so it passes.
Critique: the merge base moves past the branch's own commits as soon as the branch merges a main that holds them. A diff from the merge base then measures nothing. The rule that "already" was meant to state, "this branch made changes and main holds them", has to read the branch's own commits, not its net diff from a moving base. Going forward the in-run `contains` check catches most silent landings. Two paths still reach this state: a push reported as failed while main did not move, landed late (a `broker.request` that gave up after `broker.WAIT_SECONDS` = 600 s while the dispatcher still pushes, or a fetch that doesn't see the push yet), followed by the documented `./zn sync` and rerun; and every capture worktree left from before c0258 that merged its landed commit.
Consequences: take `own` from the branch's own non-merge commits not on main (`git log --no-merges --format= --name-only <base>..HEAD`, before the merge, each path once). Then a branch whose own commits cancel out (an edit and its revert) has `own > 0` and `left = 0`, and says "already landed", exit 0. That is harmless, because main lacks nothing the branch has, but the design must say so. A branch with no commit of its own still has `own = 0` and fails "nothing to land" (c0072's `capture-f` case and landed.spec's `capture-empty` stay as they are). The mid-loop `take(now)` reads the same `own`.
Recommendation: define `own` as above in Design 2 step 1 and in `landrace.start`'s comment. State the revert outcome in Usability. Correct the "Where main is today" bullet: the 2026-11-05 branch had merged its landed commit. Add a landed.spec case: a capture lands, then a second worktree holding the same change runs `git merge origin/main` (or `./zn sync`) before `land`; expect `already landed on main: origin/main <tip>`, exit 0, no gate run, origin unchanged. Keep the existing empty-branch case. Add a Rules and mutants row (`run`) whose mutant is the prototype's diff-from-merge-base `own`, and confirm the new case kills it.

### F8 [low] Giving up drops the push's own error, and under the broker ten tries can take 100 minutes
Where: prototype `cmd.land`, `fail(\`lost the race to main {landrace.TRIES} times: run land again\`)`; c0258.md:75 ("The ten-push bound and the gate's own bound bound the command")
Evidence: under the dispatcher each push is a `broker.request`, which waits up to `broker.WAIT_SECONDS` = 600 s and then returns false with `no answer from the dispatcher's publish broker in 600 s`. If main moves meanwhile, which is likely in ten minutes, land merges and asks again: up to 10 × 600 s, against 3 × 600 s today. It then reports a race, and the broker's message is gone.
Critique: a persistent push failure (a broker that doesn't answer, a hook rejection) is reported as a race, and Scalability doesn't state the worst case.
Consequences: failing at once on a broker "no answer" is also safe, because the next run's start check finds a late push. That is a choice the author should state, not leave implicit.
Recommendation: append the last push's output to the give-up line (`… run land again (last push: <stderr>)`), state the broker's worst case in Scalability, and say whether a broker "no answer" is retried.

## Candidate lessons (for the lead to file)
