# c0260: Capture interview and idea review

## Problem
User (2026-11-07): "we also need better z-ticket command that really challenges the idea and writes it out both the verbatim given by the user and each question asked and its answer and then with all that kept on the ticket write out a clean fully formed idea and reviews that in a clean adversarial agent to make sure that the written out idea actuall corresponds to what the user did, then confirm the idea as it now stands with the user. Then z-design takes over (as it stands today), writing acceptance tests as code and a design and reviewing back and forth."

z-ticket today sharpens the user's words into a Problem and lands it. It asks nothing about the idea, keeps no record of the user's own words or of any exchange, and nothing checks the Problem against what the user said. The idea stage is one of the two places a human works (README, Intent; c0264), so it has to be thorough. What should happen:
- **Verbatim.** The user's ask is kept on the ticket word for word, every message of it, dated.
- **Interview.** z-ticket really challenges the idea: it asks the questions that expose gaps, conflicts, edge cases and unstated assumptions. Every question and its answer is kept on the ticket, in order.
- **Clean idea.** From the verbatim ask and the interview, all kept on the ticket, z-ticket writes a clean, fully formed idea.
- **Idea review.** A clean adversarial agent (fresh context, the sharp model, c0261) checks that the written idea matches what the user said: nothing dropped, nothing added, nothing bent. Its findings are answered before the user sees the idea.
- **Confirmation.** The user confirms the idea as it now stands, and the confirmation is recorded on the ticket. Only a confirmed idea goes to z-design, which takes over as it is today.

### The idea loop (the user's ruling of 2026-11-13, F15: "Loop until it approves"; design-review-011 answered in design-refute-011.md)
`./zn idea <id>` now runs: the author drafts; then up to `idea.MAX_ROUNDS` (5) challenges, each followed by a revision **except the last**: draft, challenge, revise, challenge, … , revise, challenge (at most ten calls: the draft, five challenges, four revisions). Where the run's loop starts and how many challenges it may make is `idea.loopStart(doc, names)` (`{ first, left }`: the highest `idea-review-NNN.md` plus one, and `idea.MAX_ROUNDS`), which `cmd.idea` asks once and nothing else computes (`for n = 1, start.left`, the output's `of at most <left>`). A pass's challenger is a fresh call on the `idea-challenge` role shown the current idea, the user's Ask and Interview, and, from the second pass on, the previous pass's findings with the author's answers ("raise a finding for any point that still fails, including one an earlier round missed; an earlier finding whose answer holds is not raised again; approve when nothing remains"). The author's revision is shown the current idea and answers each finding by id (`revised`, or `disputed: <reason>`). The loop ends when a challenge returns `approve` with no findings, when a pass has only questions for the user, or after the fifth challenge.
- **The last challenge is never followed by a revision (F1).** What the user is shown is exactly what the last challenger judged, so every review's `Round:` line names the state it judged and the last one is the state shown. Everything the last challenge found goes under `## Open to the human` unanswered, whatever the author would have said; `--confirm` and the claim refuse until the user rules it, for an agent-filed ticket as for any other. (A `revised` the challenger already rejected four times is not believed a fifth time.)
- **Questions for the user (F4).** A challenger writes a finding only the user can settle as `- F2: ask: <the question>`. The author is never shown or asked to answer it, no later pass closes it, it is kept under `## Open to the human` (renumbered F1.. with the other leftovers) whatever the last verdict was, and a pass whose only findings are `ask:` ends the loop with no revision call. z-ticket 4a has the capturer ask each one (AskUserQuestion): an answer that changes or adds to the idea is recorded (the rulings so far as `### Qn` first) and a new loop runs; any other answer is its `Ruled` line, and the idea is confirmed as it stands (**Guess (prep) G13**). A `revise` verdict with no finding is not a usable answer (the next model is tried).
- **Each pass is written when it completes (F2),** in this order: the document (the revised idea, that pass's open lines, `idea: challenged`), then the refute, then the review, which binds. A model failing later exits non-zero naming the passes written; `--confirm` then refuses (the review's `Round:` names the idea it judged, not the revision written after it) and the next `./zn idea` numbers on. Nothing is lost that was paid for. The draft alone is lost if the first challenge fails (as on main).
- **The limits of the processes that run it (F2).** A dispatched z-ticket step runs `./zn idea` as one tool call; its runner stops it after `tool_seconds` (900 s in `.models.toml`) without output. Under `ZN_DISPATCH=1` every model call therefore beats into `$ZN_DISPATCH_DIR/idea-call-<n>/beat` (the runner's nested-step heartbeat, once a second while the call is inside its own stall limits), so the step stays alive while a model works; z-ticket 4a gives the Bash tool a two-hour timeout for it in Claude Code, as the Headless section does for reviews. Unknown E6 measures the wall time of a real five-pass loop against both limits.
- **Who may challenge (F3).** `cmd.idea` keeps the set of models that wrote text in this run: the draft's and each revision's, compared as `spec.model` **without the effort** (a role's tries all carry the role's effort, so `models.id` differs between the author's use and the challenger's). Each challenge starts without any try whose model is in the set, fallbacks included (`modelstep.drive`'s `exclude`), and fails with main's message when none is left. The main-wide part is not this issue's: `models.tries`' own author exclusion compares `models.id`, which appends the effort, so it never matches a fallback or a different effort, for `code-review` too; the coordinator captures that as its own ticket. c0260 leaves `Resolved.authorModel` unset and filters inside `drive`, so the new ticket may fix `models.tries` without touching this loop.
- **The cap is five**, the owner's (2026-11-18: "a new review round and so on up to 5 times", ruled for c0260 on 2026-11-19; the first design's three is replaced). `idea.MAX_ROUNDS` is the one place the number is written: the loop reads it through `idea.loopStart`, the output prints it, every spec reads it and one `loop.spec` case pins 5, and the skills write "5 times (`idea.MAX_ROUNDS`)". **Cost bound:** a run makes at most ten calls, but a call is up to four tries (the primary and the role's fallbacks `kimi`, `grok`, `agent`), each capped by the role's `max_tokens` (300000), so one run can spend up to 40 tries and about 12 M tokens, and a "challenge" may be run by a fallback instead of Opus. The user's ruling for agent tickets (F6) was offered at "one author call and one Opus challenge per agent ticket"; under the loop an agent ticket costs up to ten calls (five Opus challenges): the report to the user says so. A user's change starts a new loop with its own cap, so the loop never runs away from the user's confirmation, which closes the stage.
- **Recording.** Every challenge is a pass with its own `idea-review-NNN.md` (the challenger's words, the `Round:` line above them) and, when the author answered findings, its own `idea-refute-NNN.md`. The numbers continue from the highest in the folder, so a pass is a round, within a run and across runs. A user's change after the idea is shown is `--record` and `./zn idea` again: a new loop whose passes number on. Spend: every model call keeps its measured row (phase `idea` or `idea-challenge`) with `round <review number>` in the subject (the draft the run's first number, a revision the number of the challenge it answers) and the output prints `(round n)` per call, so two runs' rows never collide, and `idea: rounds <k> of at most 5, approved` or `…, not approved`.
- **The `Round:` binding.** A `Confirmed` line says `after round N` with N the highest review number, and `--confirm`, the claim, the audit and `./zn land` bind it to that last review, whose `Round:` is the state the user sees: counts of the Ask's messages and the Interview's questions, hash of the Problem, Solution and Non-goals.
- **Agent-filed tickets loop too** (F6): same loop, no user words in the challenge prompt. `./zn idea` rewrites the whole Problem, so it keeps the Scope decision line the marker needs (`capturecheck.keepScope`); the first prototype lost it and the ticket was no longer an agent ticket.
