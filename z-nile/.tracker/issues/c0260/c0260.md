# c0260: Capture interview and idea review

## Problem
z-ticket interviews the user, keeps the verbatim ask and every question and answer, writes a clean idea, has it checked adversarially and confirmed by the user

## Non-goals
- A guard that makes every new issue carry a `capture/` folder: an issue captured from an agent's own finding (a lesson, a review's follow-up) has no user words to keep, `./zn new` stays usable for it, and every issue before c0260 has none. The audit judges the shape of a `capture/` folder where one exists (below), nothing more.
- Reading `capture/` anywhere else than z-design: the raft prompt, the board and `./zn capture` are unchanged.
- Changing the retry of an unattended capture (`./zn dispatch retry` keeps no description for a new capture): the design below avoids needing it.

## Solution
(Added in prep, after the captured text; the Problem above is the whole captured scope.)
- z-ticket becomes eight steps: keep the ask verbatim, interview, classify, create the stub, write the clean idea, have a clean reviewer check it (`./zn dispatch zz-review <id> --mode idea`), have the user confirm it, land. The record is `<id>/capture/`: `ask.md` (the verbatim ask, every question with its options and the user's answer, the confirmation), `idea-review-NNN.md` (the reviewer's) and `idea-refute-NNN.md` (the author's answer to each finding).
- zz-review gains an idea mode; the dispatcher gains the review mode `idea`, which lands the review in `capture/` and records its spend under `capture`.
- `./zn land` lets a capture add the `capture/` files; `./zn audit` checks their shape (`z-nile/engine/capturecheck.luau`).
- z-design reads `capture/`; the confirmed Problem stays the scope.

## Design
**STATUS (prep stopped after review round 2): NOT ready. Open user decisions, from design-review-002 F1, F2, F3: (1) the dispatched confirmation needs the answer hand-over that c0256 captures; (2) the agent-finding captures skip the review and confirmation; (3) c0247 (prepared) and c0135 (active) pin z-ticket text this rewrites. See design-refute-002.md.**

Chore: tooling and skills only; nothing a player sees changes.

**The flow** (z-ticket, `z-nile/skills/z-ticket/SKILL.md`, rewritten as steps 0 to 8 plus "The capture folder" and the Headless section). 1 the ask copied verbatim into `capture/ask.md`; 2 the interview (rounds of at most four questions, each with options and costs, every question, option list and answer kept in the user's words; none dropped; `None: <why>` when the ask was complete); 3 classify; 4 `./zn new issue …` then `capture/ask.md` is written; 5 the clean idea in the issue document (Problem, Non-goals, Solution ideas; nothing the user did not say or answer); 6 `./zn dispatch zz-review <id> --mode idea` with a two-hour Bash timeout, findings answered one line each in `idea-refute-NNN.md` (`fixed`, `refuted`, `ask`), at most three rounds, another round after a high finding or after answers that changed the outcomes; 7 the user confirms (Claude Code: AskUserQuestion "Confirm" / "Change it"); a change they ask for joins the interview and goes back through 6; 8 land. The ask, interview and confirmation of an issue captured from an agent's own finding are skipped (no user words), and it gets no `capture/`.

**The capture folder** (`<id>/capture/`, a subfolder so no reader of an item's top-level documents sees it: `trail.isDoc` counts any `*.md` directly in the folder as an item document, a name with a slash is not one). `ask.md` is exactly the sections `## Verbatim ask`, `## Interview`, `## Confirmation`; the interview is `### Qn` blocks (`Question:`, `Options:`, `Answer:`) numbered from 1, or `None: <why>`; the confirmation is the one line `Confirmed (user|unattended, YYYY-MM-DD) after idea-review-NNN: <words>` naming the highest review round. Every `### Fn` finding of `idea-review-NNN.md` has a `- Fn: fixed|refuted|ask: <text>` line in `idea-refute-NNN.md`.

**Engine** (pure over texts, reads at the edge: zz-arch):
- `z-nile/engine/capturecheck.luau` (new): `capturecheck.check(ask: string, files: { [string]: string }): { string }` returns the problems of one folder (no I/O); `capturecheck.REVIEW` and `.REFUTE` are the file-name patterns (also `main.luau`'s land scope and `audit.luau`'s file filter use them: one definition of the names).
- `z-nile/engine/audit.luau`: for each found item whose folder has `capture/`, read `ask.md` and the review and refute files and add one `capture` error per problem (path `<item>/capture`); a `capture/` with no `ask.md`, or with any other file, is an error. An item with no `capture/` is not checked.
- `z-nile/engine/dispatch.luau`: `REVIEW_MODES.idea = { lessons = "design", phase = "capture" }` (a reviewer reads the design lessons, like the other design-time reviews; its row is the capture's cost, so `spend --phase capture` is unchanged and `metrics` needs no new phase); the review prompt names `capture/idea-review-NNN.md`; the unknown-mode message lists `idea`.
- `z-nile/engine/dispatcher.luau`: for mode `idea` the landing prefix is `idea-review-` and the landing folder `<item dir>/capture` (made if missing); every other mode is as it was.
- `z-nile/engine/main.luau`, `captureScope` (what `./zn land` accepts): besides edits to draft issue documents, an add or edit (`A` or `M`) of `<root>/issues/<id>/capture/<name>` where `<name>` is `ask.md`, `idea-review-NNN.md` or `idea-refute-NNN.md`, a plain file (mode 100644), of an issue whose document on `origin/main` says `design: draft`. Anything else in `capture/` (another name, a nested path, a link, an issue that is no draft) is refused as today.
- Skills: `zz-review` (idea mode, 7 attack items; `idea-review-NNN.md` in Output file), `z-design` (reads `capture/`; `ask:` lines put to the user before the first review round; the confirmed Problem is the scope), `zz-rules` (item layout, dispatcher modes, spend row of an idea review), `z-nile/README.md` (z-ticket's Skills row, the pipeline's step 1, a Roadmap row `capture interview and idea review | c0260 | exists`).

**Headless (the dispatcher).** `./zn dispatch new "<description>"` cannot ask anyone, and a stop after `./zn new` would leave a stub that a retry duplicates (`z-ticket made 2 issues, not one`, and `retry` keeps no description for a new capture). So an unattended capture does not stop: the ask is the description; the Interview is `None: unattended, nobody could be asked`; steps 5 and 6 run as usual (a finding that needs the user is answered `ask:`); the Confirmation is `Confirmed (unattended, …)`. That is not the user's confirmation, and the design does not pretend it is (design review 001 F1): **z-design, before its first review round, shows the user the clean idea and every `ask:` line** (interactive: AskUserQuestion; dispatched: its `questions.md` stop, which is safe because the issue exists), records the questions and answers as `### Qn` blocks, rewrites the answered `ask:` lines `fixed: asked as Qn`, and replaces the Confirmation with `Confirmed (user, …)`. `./zn audit` fails an issue that is `design: ready` and still unattended, and `capturecheck` ties the forms together (`unattended` needs a `None:` interview; a `user` confirmation allows no open `ask:`). Every captured outcome therefore holds for every capture that has a user: the interview and the confirmation happen, later for a dispatched one. **Open question for the user (not a decision of this prep):** an issue captured from an agent's own finding (a lesson, a review's follow-up: no user words) skips the ask, the interview, the review and the confirmation and has no `capture/`; keeping the adversarial review for those too would need a `capture/` with no ask, which this design does not build.

**Review round 1 additions** (all in the prototype). *Fences (F3):* the Verbatim ask, and an Answer of several lines, sit in a fenced block (the fence one backtick longer than the longest backtick run in the text, at least three); `capturecheck` treats fenced lines as text, never as headings or fields, and an unclosed fence is an error. *Batch (F4):* an optional `## Part` section between the Verbatim ask and the Interview names the sibling ids and quotes this issue's part. *Interactive review (F2):* z-ticket step 6 allows what z-design step 5.2 allows: where the dispatcher cannot run, a fresh subagent on `model: "opus"` given zz-review's Idea mode writes `capture/idea-review-NNN.md` itself and the author records its `capture` spend row (`--note idea-review-NNN`). *Land (F6, F9):* a later land may append questions and change the Confirmation (`capturecheck.appendOnly` compares the Verbatim ask, the Part and the existing questions with the base's), may not touch a landed `idea-review-NNN.md`, and may not carry capture files into an issue whose status on the base is no longer `new-…` (another terminal claimed it); a deletion is refused as before. *Audit (F8):* names starting with `.` are ignored (a Finder's `.DS_Store`). *Lessons (F10):* the idea review reads `./zn lessons --skill z-ticket --skill zz-review --full`, not the design lessons (`REVIEW_MODES.idea.skills`). *Restated rules (F7):* `main.luau`'s refusal text, zz-rules' land, direct-push and spend sentences. *Rounds (F14):* at most three rounds the author starts; a change the user asks for at step 7 always gets one more.

**No behaviour change** for players: nothing under any game's `src/` is touched. The behaviour that stays exactly as it is: `./zn land` of every capture that adds no `capture/` file (c0072's `land.spec` cases), every existing review mode and its landing (c0117's `dispatch-cli.spec`).
**Existing work**: no existing item has a `capture/` folder, so the audit's new rule fails none; an in-flight capture worktree that predates this lands as before (no `capture/`, nothing required); the five siblings captured at the same time (c0261, c0262, f0263, c0264, f0265) and every draft in the backlog keep their documents. `main` writes no file this branch edits during the raft (no counter, map or registry).
**Shared state**: none; `z-nile/next` and the tracker documents are untouched.
**Restated rules**: every place that restates the capture flow, the dispatcher's modes or an item's folder is edited together: z-ticket, zz-review, z-design, zz-rules (Items layout, Dispatch Steps, the `dispatch` usage line, Spend), the engine's usage line in `dispatcher.luau` and the unknown-mode message, and the README (skills.spec pins the places).
**Moves**: none.
**Guards**: `captureScope` is a guard on what a capture may push; it stays fail-closed: the new allowance is an allow-list of three exact name forms, a plain file, for a draft issue the base holds, and the existing refusals are untouched. The audit rule only reports. The new allowance is bounded further: capture files ride only into an unclaimed draft, `ask.md` only grows and a landed review is never edited.

### Scalability
One review per round, three rounds at most, on the capture of one issue; a batch capture repeats the ask and the interview in each issue's `ask.md` (a few KB each). The audit reads only the `capture/` folders that exist.
### Maintainability
One definition of the file names and of the shape (`capturecheck`), shared by the audit and `land`; the skill shows the template and a spec feeds the skill's own template through `capturecheck`, so the skill and the check cannot drift. The dispatcher gains a table row, not a branch of logic beyond a prefix and a folder.
### Usability
The user answers focused questions (options and costs, four at a time) instead of a one-line capture, sees the review's findings and the answers before confirming, and every later reader finds what they said in `capture/ask.md`.
