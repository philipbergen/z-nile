# c0260: Capture interview and idea review

## Problem
User (2026-11-07): "we also need better z-ticket command that really challenges the idea and writes it out both the verbatim given by the user and each question asked and its answer and then with all that kept on the ticket write out a clean fully formed idea and reviews that in a clean adversarial agent to make sure that the written out idea actuall corresponds to what the user did, then confirm the idea as it now stands with the user. Then z-design takes over (as it stands today), writing acceptance tests as code and a design and reviewing back and forth."

z-ticket today sharpens the user's words into a Problem and lands it. It asks nothing about the idea, keeps no record of the user's own words or of any exchange, and nothing checks the Problem against what the user said. The idea stage is one of the two places a human works (README, Intent; c0264), so it has to be thorough. What should happen:
- **Verbatim.** The user's ask is kept on the ticket word for word, every message of it, dated.
- **Interview.** z-ticket really challenges the idea: it asks the questions that expose gaps, conflicts, edge cases and unstated assumptions. Every question and its answer is kept on the ticket, in order.
- **Clean idea.** From the verbatim ask and the interview, all kept on the ticket, z-ticket writes a clean, fully formed idea.
- **Idea review.** A clean adversarial agent (fresh context, the sharp model, c0261) checks that the written idea matches what the user said: nothing dropped, nothing added, nothing bent. Its findings are answered before the user sees the idea.
- **Confirmation.** The user confirms the idea as it now stands, and the confirmation is recorded on the ticket. Only a confirmed idea goes to z-design, which takes over as it is today.

Decided with the user (2026-11-07): "Keep headless, confirm later" (asked "z-ticket is always human driven isn't it?"; options: human-only, headless stops and waits, headless records unattended and confirms later). A dispatched capture (`./zn dispatch new`) records its interview and confirmation as unattended; z-design asks the user for the real confirmation of the idea before designing.

Decided with the user (2026-11-08): "Exempt, with a Scope decision line" (captures from an agent's own finding, a lesson or review follow-up, have no user words): they carry no `## Ask (verbatim)`, interview, idea review or confirmation, record that an agent filed them and from which finding, and carry a `Scope decision` line.

- The full-force review (c0262) reads these sections as "the original ask".

**Record enforcement** (the user, 2026-11-08: "Only tickets created after c0260 lands"). `./zn status <id> preparing` (for a raft, each member) refuses an issue marked `capture: required` that has neither the record nor `## Filed by (agent)`; `./zn audit` refuses the same at `design: reviewed|ready` (not in `done/`, which passed the claim gate). **How the cut-over is read** (design-review-004 F1 moved this from git history to the issue itself, after probes showed a renumbering or compaction, a merge-commit landing and a shallow clone each changing what history said): `./zn new issue` writes the frontmatter line `capture: required` when the base holds the marker file `z-nile/.tracker/capture-since` (checked on `origin/main`, else `HEAD`; the c0260 PR adds the file), and the claim and the audit judge that line; no history is read. An emergent issue (`--raft`) is not marked. A squash or merge landing, a shallow clone, a renumbering or a compaction cannot change what an issue is, and a reused id inherits nothing. An issue made before the landing has no line and is never judged (nothing is migrated); an in-flight ticket made before the landing is exactly that. One made after it, by any terminal (`new` refuses a stale tree first, so the marker is visible), carries the line. A fixture that copies the tooling but no tracker state has no marker file, so its issues get no line: the promoted c0114 and c0116 specs that claim bare stubs stay green. Before the marker file is on `origin/main` the claim gate returns at once (no issue can carry the line, and a layout from before c0114 has no readable roots). There is no lookup to fail, so nothing to fail closed on; the remaining way round the gate is deleting the line from a document by hand, which a code reviewer sees in the diff.
