# c0260: Capture interview and idea review

## Problem
User (2026-11-07): "we also need better z-ticket command that really challenges the idea and writes it out both the verbatim given by the user and each question asked and its answer and then with all that kept on the ticket write out a clean fully formed idea and reviews that in a clean adversarial agent to make sure that the written out idea actuall corresponds to what the user did, then confirm the idea as it now stands with the user. Then z-design takes over (as it stands today), writing acceptance tests as code and a design and reviewing back and forth."

z-ticket today sharpens the user's words into a Problem and lands it. It asks nothing about the idea, keeps no record of the user's own words or of any exchange, and nothing checks the Problem against what the user said. The idea stage is one of the two places a human works (README, Intent; c0264), so it has to be thorough. What should happen:
- **Verbatim.** The user's ask is kept on the ticket word for word, every message of it, dated.
- **Interview.** z-ticket really challenges the idea: it asks the questions that expose gaps, conflicts, edge cases and unstated assumptions. Every question and its answer is kept on the ticket, in order.
- **Clean idea.** From the verbatim ask and the interview, all kept on the ticket, z-ticket writes a clean, fully formed idea.
- **Idea review.** A clean adversarial agent (fresh context, the sharp model, c0261) checks that the written idea matches what the user said: nothing dropped, nothing added, nothing bent. Its findings are answered before the user sees the idea.
- **Confirmation.** The user confirms the idea as it now stands, and the confirmation is recorded on the ticket. Only a confirmed idea goes to z-design, which takes over as it is today.

## Non-goals
- Changing z-design, which takes over as it is today.
- The basic restatement and approval before the stub is created: that is c0247 (being prepared). This issue builds on it.
- Which model is sharp (c0261) and who is recorded as having confirmed (c0263).

## Solution
- New sections on the issue doc: `## Ask (verbatim)`, `## Interview` (Q and A pairs), `## Idea`, `## Idea review`, and a confirmation line with who and when.
- The idea review is a zz-review mode (`--mode idea`) whose reviewer sees only the verbatim ask, the interview and the idea.
- The full-force review (c0262) reads these sections as "the original ask".

**The record is sections on the issue document** (the capture's choice, so a reader finds the ask, the exchange and the idea in one file; my earlier `capture/ask.md` folder is dropped): `## Ask (verbatim)` (every message of the user's ask, each dated `(YYYY-MM-DD)`, in fenced blocks so a pasted plan's headings stay text), `## Interview` (`### Qn` with `Question:`, `Options:`, `Answer:`, in order), `## Idea` (the clean idea; this is what Problem, Non-goals and Solution are written from, and the Problem the user confirmed stays the scope), `## Idea review` (one block per round: findings, each answered `fixed|refuted|ask`), and a last line `Confirmed (<who>, YYYY-MM-DD): "<words>"` (who is recorded; which identity is c0263's). Consequences, all simpler than v1: `./zn land` already lets a capture edit a draft issue's sections, so **no `captureScope` change**; no `trail.isDoc` hazard; no append-only comparison beyond a check that a landed `## Ask (verbatim)` is unchanged, which `capturecheck` can do against the base text.
**The reviewer's raw output** still needs a file: a dispatched review is moved to `idea-review-NNN.md` by the dispatcher. It lands beside the document in `<id>/capture/` (a subfolder, because `trail.isDoc` counts top-level `*.md`), and `## Idea review` summarises it and carries the answers. This is the one `captureScope` allowance kept (name form `idea-review-NNN.md`, plain file, unclaimed draft). Justification against the capture's "sections": the raw review is a record, the section is what the user and z-design read.
**The idea review** is `zz-review --mode idea` (REVIEW_MODES.idea, phase `capture`), seeing only `## Ask (verbatim)`, `## Interview` and `## Idea` (its prompt names those three sections; the author must not give it the Problem, which is derived). It checks the idea against what the user said: nothing dropped, added or bent. Its findings are answered before the user sees the idea; the user then confirms the idea as it stands. The full-force review (c0262) reads these sections as "the original ask".
**Models are tied to activities, not tiers** (the user, 2026-11-07, via c0261: "I don't want weird names for each model, I want real model names assigned to tasks ... Don't invent a bunch of names, just tie the models to each command and activity"). z-ticket has two model activities, and `.models.toml` names a real model per CLI for each, by command and activity: **`z-ticket-sharpen`** (writing the clean idea from the ask and the interview) and **`z-ticket-review`** (the idea review, which is `zz-review --mode idea`). These two names are this design's assumption; c0261 settles the naming scheme and c0260 follows it. The seam: the idea mode asks the existing model resolution (`dispatcher.resolve`, `models.luau`) for its activity's table instead of `[zz-review.<cli>]`, with no tier word anywhere; `REVIEW_MODES.idea` carries the activity name (`activity = "z-ticket-review"`) and the dispatcher resolves that key, falling back to nothing (a missing table is the existing 'no file names it' error). c0260's specs assert only that the idea review resolves the model that `.models.toml` names for its activity (a fixture file names a fake model; the case checks that model is the one started) and never a tier or a specific real model id. The interactive subagent form uses the review model of the CLI as z-design does.
**Engine (as in v1, narrowed):** `capturecheck` becomes a pure check over the issue document's sections (order, dated asks, numbered Q blocks, answered findings, the Confirmation naming a who and a date and following the last review round), called from `./zn audit` for an issue that has an `## Ask (verbatim)` section (issues before c0260 have none: not checked); `dispatch.luau`/`dispatcher.luau` mode `idea` (lands in `capture/`, spend under `capture`, capture-skill lessons only); skills z-ticket, zz-review, zz-rules, README.
**Open questions for the user (not decided here):**
1. *Dispatched captures.* A dispatched capture (`./zn dispatch new`) has no user. c0247 already stops it for a restatement through `questions.md` and c0256; the new capture adds an interview, a review and a confirmation, all of which need the user. The user also said that humans work the idea in plan mode (README Intent, c0264), which conflicts with any unattended path. Options: (a) a dispatched capture stops at the interview and the confirmation (needs c0256's hand-over; a capture must not create the stub before the user has approved, which c0247 provides); (b) a dispatched capture records "unattended" and z-design confirms with the user later (my v1 design); (c) dispatched captures are not supported: `./zn dispatch new` is removed or only creates a stub from an already confirmed idea. Cost: (a) waits on c0256 and a resumable capture; (b) the idea is confirmed late and the plan-mode intent is not met; (c) removes a flow.
2. *Captures from an agent's own finding* (a lesson, a review follow-up: no user words) have nothing to put under `## Ask (verbatim)`. Options: (a) exempt them (c0247 already does) with a Scope decision line; (b) give them the idea review without an ask or confirmation; (c) the user confirms those too. Cost: (b) and (c) add a variant to the check and the skill.
3. *c0135 (active) pins "a duplicate (step 5)" in z-ticket's text:* the executor keeps step numbers stable or c0135 is named as an Override once the rewrite is designed.

### Scalability
One review per round, three rounds at most, on the capture of one issue; a batch capture repeats the ask and the interview in each issue's `ask.md` (a few KB each). The audit reads only the `capture/` folders that exist.
### Maintainability
One definition of the file names and of the shape (`capturecheck`), shared by the audit and `land`; the skill shows the template and a spec feeds the skill's own template through `capturecheck`, so the skill and the check cannot drift. The dispatcher gains a table row, not a branch of logic beyond a prefix and a folder.
### Usability
The user answers focused questions (options and costs, four at a time) instead of a one-line capture, sees the review's findings and the answers before confirming, and every later reader finds what they said in `capture/ask.md`.
