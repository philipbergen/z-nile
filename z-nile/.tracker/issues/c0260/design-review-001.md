### F1 [high] Two capture paths drop captured outcomes ("confirmed by the user", "checked adversarially") with no Scope decision line
Where: c0260.md Design, "Headless (the dispatcher)" ("**(prep) choice for the user to veto**"); Design "The flow" last sentence and z-ticket's new preamble ("An issue captured from an agent's own finding … skips the ask, the interview, the review and the confirmation (steps 1, 2, 6 and 7)"); Unknowns "Scope check".
Evidence: the capture's Problem is "z-ticket interviews the user, keeps the verbatim ask and every question and answer, writes a clean idea, has it checked adversarially and confirmed by the user". Under `./zn dispatch new` the design lands the issue with `Confirmed (unattended, …): the user started this dispatch with this ask`; no user ever confirms the clean idea, and z-design later puts only the `ask:` lines to the user, never the idea for confirmation. For an agent's own finding the design also skips step 6, the adversarial check. Neither path has a `Scope decision (user, YYYY-MM-DD)` or `Decided with the user` line; the document itself calls the first a prep guess for the user to veto.
Critique: zz-review item 11 and z-design/never-narrow-captured-scope: an outcome dropped on a path without a recorded user decision is high, however well argued. The tempting fix is to write "the user can veto" more prominently and land the prep as is, which makes the guess the decision.
Consequences: each option changes a different part. (a) Keeping the unattended capture with a later confirmation at z-design means `capture/ask.md` gets a second confirmation state (unattended, then user), so capturecheck's "one line" rule, z-design's step and an audit or claim rule must agree. (b) Stopping the dispatched capture needs a persisted description and a resumable `new` in the dispatcher (the cost the design names). (c) The user accepts the narrowing, which is a `Scope decision` line.
Recommendation: escalate to the user: (a) full scope at low cost: the unattended capture lands as designed, and z-design, before anything else, shows the user the clean idea and every `ask:` line (interactive: AskUserQuestion; dispatched: its `questions.md` stop, which is safe because the issue exists) and replaces the Confirmation line with `Confirmed (user, …) after idea-review-NNN: …`. Add a spec case that z-design's text requires this, and a capturecheck/audit rule that a `prepared` or later issue whose `capture/ask.md` says `unattended` is an error, which proves the confirmation happened before prep finished; (b) stop the dispatched capture for the interview and the confirmation (dispatcher change: persisted description, resumable capture); (c) accept the unattended confirmation as the scope, recorded as `Scope decision (user, …)` in the Problem. Separately, ask whether an agent-finding capture still gets the idea review (it costs one Opus run and has a finding to check fidelity against), or record the skip as a `Scope decision`.
Lesson: z-design/never-narrow-captured-scope

### F3 [high] A verbatim ask that contains a `## ` line (a pasted plan) can never pass capturecheck, so the ask must be edited to land
Where: capturecheck.luau `sections()` (every `^## ` line opens a section, fences ignored); z-ticket step 1 ("Copy the user's request exactly as they wrote it … It is never edited") and its batch sentence ("A batch captured from one request or plan").
Evidence: probe, ask.md with the Verbatim ask `Here is my plan:\n\n## Goals\n- scarier ghosts`: `ask.md sections must be exactly Verbatim ask, Interview, Confirmation, in that order (found: Verbatim ask, Goals, Interview, Confirmation)`. The same holds for an `## ` line inside a multi-line Answer. Plans pasted from plan mode, and the plans this repository's batch captures come from, are headed with `##`.
Critique: the gate's audit then fails, and land fails, unless the author edits the user's words, which is the captured outcome "keeps the verbatim ask" broken by the check meant to keep it. The tempting fix is "indent the ask" or "drop the headings", which is still an edit.
Consequences: the ask must be held in a container the parser can skip: a fenced block whose fence is longer than any backtick or tilde run in the text (CommonMark's rule), or `> `-quoted lines. capturecheck must then parse fences (an unterminated fence is an error, not "everything after it is the ask"), the template in z-ticket changes, the spec's template case changes with it, and the reviewer's Fidelity attack reads inside the fence. Multi-line Answers need the same container or a rule that an Answer is one line.
Recommendation: put the Verbatim ask, and any Answer longer than one line, in a fenced block (fence = one more backtick than the longest run in the text, at least three); capturecheck ignores headings inside fences and refuses an unterminated one. Spec cases: a Verbatim ask holding `## Goals`, a ```` ``` ```` block and a `### Q1` line passes with its exact text recovered; an unterminated fence is refused; the skill's template still passes.
Lesson: zz-arch/parsers-refuse-ambiguity

### F4 [medium] A batch capture must say "which part is that issue's", and ask.md has no place to say it
Where: z-ticket step 1 ("copies the whole ask and the whole interview into each of its issues' `ask.md` and says which part is that issue's"); capturecheck's section and interview rules.
Evidence: probe: a line `This issue is part (a).` before `### Q1` gives `Interview: text before the first ### Q1 block: …`; a fourth section is refused ("sections must be exactly …"); the Confirmation must be one line. The only place the check accepts it is inside the Verbatim ask (`(c0901 is part a)` passes), which step 1 forbids editing.
Critique: z-design/specify-every-named-artifact: the skill names an artifact the template cannot hold, so each batch author will invent one, and the audit rejects most inventions.
Consequences: a new slot is a new rule in capturecheck, the template, the spec and zz-review's Fidelity attack (the reviewer judges the issue against its part, not the whole ask).
Recommendation: add an optional `## Part` section (between Verbatim ask and Interview, present only for a batch, naming the sibling ids and quoting this issue's part), or a `Part:` line as the Interview's first line; capturecheck accepts exactly that form. Spec cases: a batch ask.md with the part passes; text in any other place still fails.
Lesson: z-design/specify-every-named-artifact

### F5 [medium] `ask:` answers and the `unattended` confirmation are not tied to the dispatched path, and z-design and z-ticket disagree on which `ask:` lines go to the user
Where: z-ticket step 6 (an interactive `- Fn: ask:` "goes back to step 2 as a new question"); z-ticket "A capture under the dispatcher" ("every `ask:` line that no later line of the Problem answers"); z-design "The capture folder" ("Every `- Fn: ask: …` line … is a question for the user that the capture could not ask (an unattended capture): put them to the user"); capturecheck.
Evidence: probes: an interview with real `### Q1` answers and `Confirmed (unattended, 2026-11-07) …` passes with no problem; a `Confirmed (user, …)` folder whose refute says `- F1: ask: which sound?` passes. So an interactive author can skip the user by writing `unattended`, and an interactive capture leaves `ask:` lines that z-design, by its own text, re-asks the user even though step 2 already asked them (or skips them, by the parenthesis). z-design's "every" and z-ticket's "that no later line of the Problem answers" are two different rules.
Critique: the audit is the design's only guard on the record, and it accepts the two states the flow says cannot happen. The tempting fix is a sentence in each skill, which keeps both readings.
Consequences: making it checkable adds two capturecheck rules, and an interactive answered `ask:` must be rewritten once asked (`fixed: asked as Q3`), which the refute grammar must allow.
Recommendation: capturecheck: `unattended` requires the Interview to be `None: unattended…` and vice versa; a `- Fn: ask:` line is allowed only with an `unattended` confirmation (an interactive one is rewritten `fixed: asked as Qn …` once the user answers). z-design then asks every `ask:` line, one rule in both skills. Spec cases for each refusal and the accepted unattended folder.

### F6 [medium] `land` lets a later capture rewrite the verbatim ask and the reviewer's own record; "the ask is never edited" is enforced nowhere
Where: captureScope (`kind == "A" or kind == "M"` for all three names); land.spec "land edits a capture file that an earlier land added" (rewrites a landed `ask.md` to `edited\n`); Design "Guards" ("an allow-list … the existing refusals are untouched").

### F8 [medium] The audit judges `capture/` from disk, so an ignored Finder `.DS_Store` fails the gate
Where: prototype audit.luau's new loop (`fs.readDir(dir)`, any name but the three is `not a capture file`).

### F9 [medium] The unconfirmed stub stays claimable during the review rounds and the confirmation, and land does not check that nobody claimed it
Where: z-ticket step 4 (the stub is pushed at once), steps 6–7 (up to three review rounds, then the user's confirmation, possibly much later); captureScope (checks `design: draft` and an unchanged status between base and HEAD, never that the base's status is `new`).
Evidence: reading captureScope: after `git merge origin/main`, HEAD's status equals the base's, so if another terminal ran `./zn status <id> preparing` on the stub, `was.status == now.status` and the capture's confirmed Problem, and its `capture/` files (base doc `design: draft` still), land into an issue whose prep started from the one-line stub. Before c0260 the window between `./zn new` and land was a few minutes; it is now review rounds plus however long the user takes to confirm.
Critique: z-design reads `capture/` and the confirmed Problem as the scope; a prep that started before them read neither.
Consequences: refusing a claimed issue means a capture whose stub was claimed must stop and tell the user (the prep holds the issue); the message must say so.
Recommendation: captureScope refuses a capture change (document or `capture/` file) to an issue whose base status is not `new-…`, with a message naming the claim. Spec case in land.spec: claim the stub on origin, then land the capture: refused, origin unchanged.

### F10 [medium] An idea reviewer is told to read all of z-nile's design lessons every round
