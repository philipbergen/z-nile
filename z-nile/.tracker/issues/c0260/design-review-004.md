### F1 [high] The cut-over is keyed on the id's path and on plain ancestry, so `./zn compact`/`renumber` and a merge-commit landing lock older tickets out for ever, and an id reused by a compaction lets a new ticket through
Where: c0260.md Design, **Record enforcement** ("the oldest commit that adds its document (`:(glob)**/<id>/<id>.md`) … `git merge-base --is-ancestor`", "In-flight tickets are not locked out"); `capturecut.of`; `refuseUncaptured` (fails closed on `unknown`).
Evidence: (P1) a fixture repo: `c0300` added, then the marker, then the rename a compaction makes (`git mv issues/c0300 issues/c0270`, `c0300.md` → `c0270.md`, which is exactly `compact.apply`: `moveAll` plus `git mv {old}.md {new}.md`). The pathspec names only the new path, so git sees no rename: the first `A` of `**/c0270/c0270.md` is the compaction commit, a descendant of the landing → **"P1 renamed pre-landing issue: after (claim refused)"**. Every pre-landing `none` issue a post-landing compaction renumbers is then refused at the claim, and every one at `design: reviewed|ready` turns the audit red on every gate (compact's own `auditErrors` passes, because the new paths are not committed yet when it audits). Compaction is live (`#61`/`#64`, `refuseStale` reads its map). The reverse: when a compaction gives a post-landing ticket an id an older issue once held, the first `A` of that path is the old issue's, so it is `older` and the exemption is had by omission. (P2) a merge-commit landing (`git merge --no-ff pr`) while a stub was pushed to main: the marker's first commit is on the PR branch, the stub's is on main, neither is an ancestor of the other → **"unknown (claim refused forever)"**. zz-rules says `--squash`, but main holds merge-commit PR merges as recent as #206 (2026-11-01), and `Merge origin/main into …` commits on branches. The refusal text then says "shallow clone … sync with full history", which does not help. design-review-003 F2's own Consequences named this: "`created:` is stable across `compact`/`renumber`, ids are not."
Critique: the user's decision is "Older tickets are untouched". Both probes break it, fail closed with no way out. The tempting fix is to add `--first-parent` (fixes P2) and to follow the compaction map (fixes P1 only for compactions, not `renumber`, and needs every map ever written).
Consequences: any history-based identity has to survive id rewrites, merge shapes, shallow clones and the fixture clones of the real repository (13 promoted specs `git clone` the checkout with its history; `engine.empty` leaves the marker file in place). A mark written into the ticket itself survives all of them: `compact`, `renumber` and moves keep frontmatter, and `captureScope` already refuses any frontmatter change but `title` and `depends_on`.
Recommendation: question the mechanism, not the hole. Preferred: `./zn new` stamps a frontmatter line (for example `capture: c0260`) into every stub it creates **when origin/main's tree holds `z-nile/.tracker/capture-since`** (tracker state, so seeded fixtures keep making bare stubs and c0114/window and c0116/claims stay green); the claim and the audit judge only issues carrying that line; nothing reads history, so shallow clones, merge commits and compactions are irrelevant and `unknown` disappears. If the author keeps history instead: `--first-parent` on origin/main for both lookups, the compaction map and `renumber` followed, and cases for P1, P2 and an id reused by a compaction. Either way add rows to Rules and mutants, run on the prototype with the marker **committed**.
