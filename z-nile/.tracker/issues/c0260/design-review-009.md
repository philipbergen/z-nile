### F1 [high] A dispatched pipeline can never confirm: `--confirm` is refused in the dispatched z-design step that is supposed to run it
Where: c0260.md Design, "Decisions of the user" (Keep headless, confirm later); `cmd.idea` (`if opts["--confirm"] and dispatched then fail`); z-design's new bullet "Confirm an unattended capture first … (dispatched: a `questions.md` stop … answered through `./zn dispatch retry`) … Then `./zn idea <id> --confirm "<their words>"`"; `dispatcher.modelStep` (dispatcher.luau:771, env `ZN_DISPATCH = "1"` at :869).
Evidence: every model step the dispatcher starts runs with `ZN_DISPATCH=1`, z-design included (dispatch.luau:323 chains `z-design` after a capture). `./zn dispatch new "<ask>"` lands `Unconfirmed (unattended …)`. The chain goes on to z-design, which writes `questions.md` and stops. The user answers, `./zn dispatch retry <id>` re-runs z-design, still under `ZN_DISPATCH=1`, and z-design runs `./zn idea <id> --confirm "…"`, which fails with "a dispatched run never confirms". The audit then fails `design: reviewed` while the last line is `Unconfirmed`, so the dispatched prep can't finish. record.spec pins the refusal ("--confirm … is refused by a dispatched run"). No case runs a dispatched z-design confirmation.
Critique: this breaks the user's "Keep headless, confirm later" on the one path it exists for. The tempting fix is to drop the refusal, or to have the agent type the `Confirmed` line by hand. A prep PR runs no capture check, so a hand-typed line is not refused. Either way an agent's word stands in for the user's.
Consequences: a dispatched `--confirm` needs a source for the user's words that the agent can't make up. c0256 already supplies one: the exchange folder (`.cache/dispatch/<id>/exchange/`, read only through `exchange.parse`/`exchangeRead`), which holds the user's dated reply and says whether the latest answer is `NO_REPLY` or `UNKNOWN_REPLY`. That needs c0256's reader to be landed, which `depends_on` already ensures.
Recommendation: under `ZN_DISPATCH=1`, `--confirm` takes no words on the command line. It quotes the user's latest reply from c0256's exchange. It is refused when there is no reply, when the reply is `NO_REPLY` or `UNKNOWN_REPLY`, or when the question it answers was not asked by z-design for this id. `<who>` is the user from the exchange, not the agent's git identity. Keep the capture-time refusal: a dispatched capture asks nobody, so its exchange holds no confirmation answer. Fix the z-design bullet to match. Spec cases in record.spec: (1) a dispatched `--confirm` with an exchange reply confirms and quotes it; (2) with `NO_REPLY` it is refused; (3) with words given on the command line it is refused; (4) the capture-time dispatched refusal still holds. Add a Rules row for each.
Lesson: z-design/results-land-on-every-path

### F2 [high] A dispatched capture with an open finding can't record `Unconfirmed`, and the claim refuses its open points before z-design can show them, so the capture stops and waits
Where: `cmd.idea` `--confirm`/`--unattended` branch (`idea.designRefusal` is called for both); `setStatus` (`idea.designRefusal` refuses pending `## Open to the human` bullets at `status <id> preparing`); c0260.md: "an unanswered or disputed one is under `## Open to the human` for the user at z-design"; z-ticket 4b: "Under `./zn dispatch` … do not stop, run `./zn idea <id> --unattended`".
Evidence: the unattended challenge prompt says "a question that should have been asked and was not is a finding". The author can't ask anyone, so it can only answer such a finding `disputed` or leave it, and either way it stays open. `--unattended` then fails with "cannot confirm: open to the human (F1) …". The Headless rule makes the agent stop until the user rules in the document, which is "headless stops and waits", the option the user turned down on 2026-11-07. A capture that lands with no Confirmation is still refused at the claim: `satisfies` needs a Confirmation, and `designRefusal` needs every point ruled. So the open points can never reach "the user at z-design", whose confirmation step comes after the claim (z-design §1). The only dispatched case in record.spec uses the approving stub, so this path is untested.
Critique: the code contradicts both the Design's sentence and AC1 ("a dispatched capture does not stop"). The tempting fix is to let `--unattended` skip the open-point check. That alone moves the dead end to the claim.
Consequences: deferring the open points means relaxing main's "ruled before the claim" rule for this one class of ticket. The relaxation has to be narrow, and the open points must still be ruled before design.
Recommendation: `--unattended` needs only `idea: challenged` and a review, not ruled open points. The claim skips the open-point part of `designRefusal` only for a ticket that is marked `capture: required`, `idea: challenged`, and whose last Confirmation line is `Unconfirmed (unattended …)`. `--confirm` keeps refusing unruled points, which is how z-design's confirmation has the user rule them. The audit reports an issue at `reviewed` or `ready` that still has an unruled idea open point. Update z-ticket 4b, "A capture under the dispatcher" and the Design sentence. Spec cases: a dispatched capture whose challenger raises a finding the author disputes records `Unconfirmed` and lands; its claim succeeds; `--confirm` is refused until the point is ruled; the same ticket at `reviewed` with the point unruled is an audit error; a user capture with an unruled point is still refused at the claim, as on main.

### F3 [high] The record's readers and splicers outside `capturecheck.sections` don't respect fences: they cut, overwrite or rewrite the user's verbatim words
Where: `idea.recordText` (uses `sectionBody`), `idea.apply`/`replaceSection` (used for `## Open to the human`), `openlist.pending`/`sectionOf`, and the splice offsets in `capturecheck.appendRecord`, `addConfirmation` and `dropConfirmed` (`string.find(out, "\n## " .. title .. "\n")`).
Evidence: read-only probes of the prototype's modules.
(a) The Ask holds a fenced pasted plan: "Here is my plan:", then "## Goals", "- scarier ghosts, ALL of them", "## Open to the human", "none". `capturecheck.check` reports 0 problems, but `idea.recordText` returns the Ask cut off after "Here is my plan:". Neither the author nor the challenger is given "ALL of them".
(b) `idea.apply` with one open finding replaces the user's fenced "none" and the closing fence with "- F1: an open point.". `openlist.pending` then reads the fenced copy, and the document has an unclosed fence.
(c) The Ask quotes a ticket containing "## Interview", "### Q1", "## Confirmation", and an `--record` adds `### Q2`. `appendRecord` returns success and `check` passes, but the Q1/Q2 text has been spliced into the user's verbatim message, over "## Confirmation\nConfirmed (", and the real `## Interview` has no Q2.
Pasting an issue document into a request is ordinary in this repository, and ten tickets already carry exactly these headings. The skill's own 0a text names pasted plans as the reason for the fences. shape.spec proves only that `capturecheck.check` handles fences. No case runs `./zn idea`, `--record` or `--confirm` on such an ask.
Critique: the user's words are silently lost, rewritten, or hidden from the challenger. That is the outcome the issue exists to prevent. The tempting fix is to patch `recordText` alone.
Consequences: `openlist` is shared with design and code reviews and with raft documents, so making its section lookup skip fenced lines changes how they are read too. No real heading sits inside a fence, but the openlist and c0116 specs must stay green. Main's `idea.apply` also rewrites Problem, Solution and Non-goals by the first textual match. Those sections come before the Ask today, but the fix should not depend on that order.
Recommendation: export one fence-aware section reader and one section replacer from `capturecheck` (`section(doc, title)` and `replace(doc, title, body)`, both built on `sections`). Use them in `idea.recordText`, in `idea.apply` for all four sections, in the three splices, and through `openlist.sectionOf` (skip fenced lines). Spec cases in record.spec: one fenced message holding `## Goals`, `## Open to the human`, `## Interview` and `## Confirmation` goes through `--record`, a round with an open finding, `--confirm`, a second `--record`, a round 2 (`dropConfirmed`) and `--confirm`. After each step the message is byte-identical, and both prompt logs hold it whole. Add a mutant row: "`recordText` stops at the first `\n## `".
Lesson: z-design/user-words-parsers-accept-anything

### F4 [high] The Confirmed line isn't tied to what was challenged or confirmed: a message recorded after the last round is never challenged and still passes the claim
Where: `cmd.idea --record` (doesn't touch `## Confirmation`); `--confirm` (checks only `designRefusal`, the round number and `satisfies`); `capturecheck.check` (compares the Confirmation's round with the highest review number only); `captureScope` (lets the Problem, Solution and Non-goals change by hand).
Evidence: probe of a marked, challenged document with `Confirmed … after round 1`. `appendRecord` adds "no wait, ALL the ghosts, and not before the boss level". The result is accepted, `confirmed` stays true, `satisfies` is true and `check` reports 0 problems, so the claim and the audit both accept it. Likewise, after a change of the user's is recorded with `--record`, an agent can skip the new round and run `--confirm`: it writes `Confirmed … after round 1` for an idea that never saw the correction. A hand edit of the Problem after `--confirm` also lands, with the Confirmed line kept.
Critique: the capture asks that the user "confirms the idea as it now stands" and that the challenge checks the idea against "what the user said". Neither holds once the record or the idea can move after round N without voiding the line. The tempting fix (refuse `--record` after a Confirmed line) misses the record-then-confirm order and the hand edit.
Consequences: main already ties an approval to what it approved (`contract.luau`, sha256 of the named sections, checked by `ready`, `done` and `land`). A similar tie for the confirmation must not fire after the claim, because z-design adds detail and `Decided with the user` lines to the Problem. So it is checked while `design: draft` (land, claim, `--confirm`), not by the audit at `reviewed`. The ten hand-made tickets are unmarked and unaffected.
Recommendation: each `./zn idea` round records what it was given: the number of Ask messages and Interview questions, plus the sha256 of its Problem, Solution and Non-goals as written. The engine writes these on a line it owns in the round's refute, or in an `idea-round-NNN` line of the document. Say where, and say that the review file stays the challenger's words. The Confirmation line carries the same counts and hash. `--confirm` refuses when the record has grown since the last round or the idea differs from what that round wrote. `--record` after a Confirmed line drops it, as a round does. The claim and `./zn land` (for a draft) refuse a Confirmed line whose counts or hash don't match. Spec cases: record after confirm drops the line; confirm after a record with no new round is refused; a hand-edited Problem after confirm is refused at the claim and at land; a z-design edit after the claim is not an audit error.
