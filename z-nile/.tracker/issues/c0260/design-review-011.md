### F1 [high] At the cap, a finding the challenger has already rejected the author's `revised` for is closed. The user is shown an unchallenged revision with nothing open, and `--confirm` and the claim pass
Where: c0260.md, The idea loop ("whose findings the author still answers once; what is then disputed or unanswered goes under `## Open to the human`"); prototype `main.luau:7166-7212`; `tests/tooling/idea.spec.luau` "records every finding…" (prototype change).
Evidence: a probe on the prototype ran a challenger that raises F1 in every pass and an author that answers `- F1: revised` every time (`LOOP_UNTIL=9`, `LOOP_ANSWER=revised`). Its output read `idea: rounds 3 of at most 3, not approved`, but `## Open to the human` was `none`, and `./zn idea <id> --confirm "ok"` succeeded: `Confirmed (c0260-loop, 2026-11-14) after round 3: "ok"`. The challenger rejected the author's `revised` twice (it raised F1 again in passes 2 and 3). The third `revised` is believed without any check, and the idea the user confirms is the third revision, which no challenger has seen. The only record that the loop did not approve is a stdout line. The changed `idea.spec` case pins this behaviour: after three passes in which F1 is raised each time, it asserts `has(open, "- F1:") == false`. The `Round:` line of `idea-review-003.md` names the post-revision state (`idea 5506efb60174`), a state its own challenger never judged, while reviews 001 and 002 name the state they judged. So one field means two things.
Critique: the user's ruling was "Loop until it approves (with a cap)". At the cap the idea has not been approved, yet the document, the claim gate and `--confirm` treat it as settled. For an agent-filed ticket (F6) no human looks at it at all. The obvious fix is to describe this in z-ticket 4a. That leaves the gate blind.
Consequences: making the leftovers visible means every capped loop needs a human ruling before the claim and `--confirm`. That includes agent-filed tickets, which is the point of the cap. A dispatched capture still goes through: the claim skips open points for an `Unconfirmed` ticket, and z-design asks the user.
Recommendation: end the loop on a challenge. The draft, then challenge, revise, challenge, revise, challenge: at most six calls. When the third challenge still has findings, they all go under `## Open to the human` as unanswered bullets, and no revision follows. What the user sees is then exactly what the last challenger judged, so every review's `Round:` line names the state it judged, and the last one is the state shown. (If the author must keep the last word, the alternative is to list every finding of the last challenge under Open to the human, `revised` ones marked "revised after the last challenge, not re-challenged". The `Round:` field then keeps two meanings, and that has to be stated.) Specs: a `loop.spec` case where the challenger never approves and the author answers `revised`. Expect: F1 open, `--confirm` refused with "open to the human", and `status preparing` refused for an agent-filed capped ticket until it is ruled. Change `idea.spec` to `calls 6` with F1, F2 and F3 open. Fix the Design's call counts ("seven", "four author calls") and AC12. Add a mutant row: "a capped loop closes a `revised` finding". M34 becomes equivalent under the first option; drop it.

### F2 [high] A long loop is killed by the limits of the processes that run it. Because it writes nothing until the end, every paid pass is lost, and a retry repeats the same loop
Where: c0260.md, The idea loop ("Nothing is written until the loop ends (a model failing mid-loop leaves the tree as it was)"); Unknowns (no wall-time experiment); prototype `main.luau:7137` (`fail` on any call), `:7212` (first write); `runner.luau:254`; `.models.toml` `[dispatch] tool_seconds = 900`.
Evidence: a dispatched z-ticket step runs `./zn idea` as one tool call of its agent CLI. While a tool runs, the dispatcher's runner kills the step after `tool_seconds` (900 s) without output (`runner.luau:254`). Only nested dispatcher steps keep it alive: `beatFile` is set only by `dispatcher.luau:999`, and `./zn idea`'s model calls (`modelstep.launch`) set none. The loop more than doubles the calls (up to seven, three of them Opus at `effort = "xhigh"`, each allowed up to 300 s of silence and 300000 tokens). With roughly two minutes or more per Opus pass, a three-pass loop can pass 900 s. The step is then killed, the tree holds nothing, and `./zn dispatch retry` starts the same loop again. A challenger that never approves always runs the full loop, so the retry fails the same way. In Claude Code, z-ticket gives no timeout for `./zn idea`: the Headless section gives a long timeout only to `./zn dispatch zz-review` (prototype z-ticket line 56). With the Bash tool's default the same kill happens interactively. Without any kill, a failure of the last call (the third revision unparseable after all four tries) still discards two challenges, two revisions and the draft. Spend rows survive in `.cache/measure.tsv`, so the work is paid and recorded, but gone.
Critique: the brief's question "can a crash lose paid work" has the answer yes, by design, and the unattended path (the user's "Keep headless") is the one most exposed. Tuning the stall limits is the tempting fix. It does not save the passes already done.
Consequences: writing per pass needs an order that never leaves a review binding a document that lacks that pass's open points. A run stopped at pass k must leave a state from which `--confirm` refuses and a rerun numbers on.
Recommendation: (1) Write each completed pass when it completes, in this order: the document first (revised idea, that pass's open lines, `idea: challenged`), then the refute, then the review last, because the review is what binds. A run stopped after pass k leaves reviews 1..k and exits non-zero naming the pass. `--confirm` then refuses (the document's state is not review k's), and the next `./zn idea` numbers on from k+1. Replace "nothing is written until the loop ends" in the Design. (2) Under `ZN_DISPATCH=1`, have each model call of `./zn idea` beat into the step's state folder (runner's `beatFile`, the mechanism nested reviews use), so the dispatched step stays alive while a call is inside its own limits. (3) Have z-ticket step 4a tell a Claude Code session to give `./zn idea` the long Bash timeout, as Headless does for reviews. (4) Add an Unknown with a pass/fail question: a three-pass loop on the real roles, run under `./zn run --time`, recording its wall time against 900 s and the Bash limit. Spec cases: a challenger stub that exits non-zero on its second call (no fallbacks) leaves `idea-review-001.md`, `idea-refute-001.md` and the first revision, then exits non-zero, and a rerun writes 002. A `ZN_DISPATCH=1` run with `ZN_DISPATCH_DIR` set leaves a fresh beat file under it while a slow stub call runs.

### F3 [high] The challenger is kept off the draft's model only. A revision written by a fallback can be challenged by that same model, and with the real `.models.toml` even the draft exclusion never matches
Where: c0260.md, The idea loop ("A pass's challenger is a fresh call on the `idea-challenge` role (never the author's model)"); prototype `main.luau:7154` (`challenge.authorModel = wrote`, set once from the draft); `models.luau:570` (`models.id(spec) ~= r.authorModel`), `:588`.
Evidence: (a) the revisions' `run(...)` results are discarded, so `authorModel` stays the draft's model for all three challenges. Take a draft by `claude-fable-5-2` after which the Claude CLI's quota runs out. The roles share it and both fall back to `["kimi", "grok", "agent"]` in the same order. The revision is then written by kimi, the next challenge's Opus try fails, and kimi challenges kimi's own revision. (b) `models.id` carries the effort, and a fallback try "uses the role's effort". So kimi as the author is `<kimi>-medium` and as the challenger `<kimi>-xhigh`, which never compare equal. With today's `.models.toml` the exclusion matches no challenger try at all. Main's spec "the author is refused as its own challenger" passes only because its fixture roles set no effort. Part (b) is main's bug. The loop adds up to two more texts per run and runs this path three times.
Critique: zz-review's Who reviews rule ("A challenge is never run by the model that wrote the text") and the user's "clean adversarial agent" both depend on this, and the Design restates it for every pass. The shared-quota outage that breaks it is the most likely way a long loop fails.
Consequences: models.tries is shared with the dispatcher (`code-review` names an author), so changing it there widens the change. Filtering inside `./zn idea` keeps the change local.
Recommendation: in `cmd.idea`, keep the set of models that wrote text in this run (the draft's and each revision's `driven.model`, compared as `spec.model`, without the effort). Before each challenge, run its tries without any spec whose model is in the set. When none is left, fail before the call with main's message ("the only model left is the author's"). Spec case in `loop.spec` or `idea.spec`: roles with an `effort` on both and kimi and grok fallbacks; the author's Claude stub fails from the first revision on (kimi writes it), and the challenger's Claude stub fails at the second challenge. Assert that the second challenge does not start kimi (grok runs) and that, with grok removed, it fails with the message. Add a Rules row. Report main's effort-in-id comparison as a candidate issue for the lead (it also makes `code-review`'s exclusion inert).

### F4 [medium] A question only the user can answer cannot be settled inside the loop. A later challenger that accepts "left for the user" closes it, and it disappears from `## Open to the human`
Where: prototype `idea.luau:364` ("raise a finding only for a point still disputed or newly introduced. Approve when nothing remains disputed"); the challenge prompt's "a question that should have been asked of the user and was not … is a finding" (every capture); c0260.md, The idea loop.
Evidence: `./zn idea` is not interactive, so the author can answer "you should have asked the user X" only by disputing it ("only the user can answer") or by "revising" with an invented answer. If the author disputes, a pass-2 challenger that accepts the dispute approves with no findings. `openLines` reads only the final pass, so the question the first challenger raised is under no bullet, and the claim and `--confirm` never ask for it. On main's single pass the same dispute stayed open. If the author invents an answer, the next challenger may flag it as added, unless that was the last revision (F1). If the challenger keeps raising it, the loop always spends its cap on a point it cannot close. The same instruction also tells passes 2 and 3 not to raise a dropped, added or bent word that pass 1 missed in text the revision did not touch: that point is neither "still disputed" nor "newly introduced".
Critique: the loop turns the challenger's most valuable finding for the user (an unasked question, the user's "really challenges the idea") into either a lost bullet or a guaranteed full-cost run.
Consequences: a reply form for questions changes zz-review's reply shape and `openLines` and `priorText`, and z-ticket 4a must ask those questions and record the answers as the next `### Qn` before a rerun.
Recommendation: give the challenger the form `- F<n>: ask: <the question for the user>`. The author is never asked to revise or dispute such a finding, and no later pass may close it. At the end of the loop it goes under `## Open to the human` whatever the last verdict was. A pass whose only findings are `ask:` ends the loop. Reword the later-pass instruction to "raise any point that still fails, including one an earlier round missed; for each earlier finding say whether its answer holds". The cap bounds the extra cost. Specs: a stub challenger that returns an `ask:` finding and then approves leaves that bullet open, and `--confirm` is refused until it is ruled. A pass with only `ask:` findings makes no revision call. Add a Rules row each.
