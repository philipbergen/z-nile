# c0261: Model tiers: cheap, sharp and wait

## Problem
User (2026-11-07): "We want to be economical so we want to use sharp expensive models for all final reviews but we only need a cheaper and faster model on the way there. Be smart about it across different providers (agent and grok are 4.6 high for cheap 4.7 xhigh for expensive not much point in getting more granular). Use cheap haiku or composer models or similar when waiting for things, don't orchestrate and wait on expensive models, keep it cheap."

Today `.models.toml` names one model per skill and CLI, and the expensive one runs whole steps: z-design and z-run on Opus or grok-4.7 high, and every review round on the review model. Waiting (for a gate, CI, a PR's checks, a subagent) costs as much as the model that waits. What should happen:
- Each CLI has three tiers: **cheap** (fast, for authoring and the way there), **sharp** (expensive, for every final review) and **wait** (the cheapest, for waiting and polling).
  - grok and agent: cheap is 4.6 at high, sharp is 4.7 at xhigh, with no finer levels.
  - claude: cheap is Sonnet, sharp is Opus, wait is Haiku.
  - agent's wait tier is composer, or similar.
  - Every other supported CLI (kimi, agy, deepseek once supported, c0175) is mapped the same way.
- **Sharp runs every final review:** the idea review (c0260), the final design review round, the final code review round and the full-force review (c0262). Everything on the way (authoring, middle review rounds, streams, fixes) runs cheap.
- **Nothing expensive orchestrates or waits.** A long wait or poll runs on the wait tier, and an orchestrating loop (the worker, c0253) runs cheap and hands sharp work to a sharp step.
- Spend records the tier with the model, so the cost per tier shows.

## Non-goals

## Solution
- `tier = "cheap" | "sharp" | "wait"` per step in the skills, and `[tiers.<cli>]` tables in `.models.toml` that the existing per-skill tables reference. The exact model ids are checked against each CLI at design.
- zz-review learns which round is final, and z-design and zz-execute ask for sharp only there.
- (prep) Detail added after the captured bullets, nothing removed: `.models.toml` keeps its per-skill, per-CLI tables and gains a table for each activity that really runs a different model (`zz-review-code`, `zz-review-stream`, `z-wait`), each naming a real model and effort per CLI; a review that nothing is judged after (the design, raft and final reviews) takes the expensive `zz-review` table and the commands refuse one that did not run on a final-review model; `z-wait` is the polling step; `./zn metrics` shows the cost per model. ## Design
**Redesigned onto main 10dd3c85 (2026-11-12).** The first design (2026-11-07/08) counted up to five review rounds and called the last of them "final". Main no longer has rounds: a design review is one round (#292), a raft is reviewed once per layer and then once as a finished stack, and `./zn done` reads only `final-review-NNN.md` (#296, #297). Every user decision in the Problem is kept with its effect; only the mechanism moved onto that shape, and each change is listed in Unknowns & experiments (Redesign log).

**One rule: tie a real model to each command and activity.** `.models.toml` already has one table per skill and CLI (`[z-design.claude]`: model, effort, rank, runtime, budget). This issue adds no vocabulary: it adds a table where an activity runs a different model, and sets the models. The activity is the table's key.

| activity (key) | what runs | claude | grok | agent (Cursor) |
|---|---|---|---|---|
| `z-ticket` | sharpening an idea into a ticket | `claude-sonnet-5-5` at high **(prep)** | `grok-4.6` at high **(prep)** | `cursor-grok-4.6-high` |
| `z-design` | authoring a design (not the cheap model: the user, 2026-11-08) | `claude-opus-5-5` at medium | `grok-4.7` at high | `grok-4.7-high` |
| `z-raft` | grouping prepared issues | same as `z-ticket` | same | same |
| `z-run` | executing a raft | same as `z-ticket` | same | same |
| `zz-review-code` | a layer's code review (the work on the way: the final review of the stack follows) **(prep, Open to the human F1)** | same as `z-ticket` | same | same |
| `zz-review-stream` | a stream review | same | same | same |
| `zz-review` | every final review: the design review (its one round, dispatched as `zz-review-design`), the raft review (`zz-review-raft`), the final review of the stack (`zz-review-final`), the idea review (c0260, `zz-review-idea`) | `claude-opus-5-5` | `grok-4.7` at xhigh | `claude-opus-5-5-high`, else `kimi-k3-high`, else `grok-4.7-xhigh` |
| `z-wait` | the waiting step | `claude-haiku-5-5` | `grok-4.5` at low **(prep)** | `composer-2.5` |

Claude's on-the-way model is `claude-sonnet-5-5` at high **(prep)**: the user's example named "sonnet-5.5-high", E1 probed `claude-sonnet-5-5` (it answers); grok and agent on the way are the capture's "4.6 high". Ranks stay what they are for ordering a raft's members: 2 on the way, 3 for z-design, 4 for a final review, 1 for the wait. The capture's model names were examples (the user, 2026-11-08), so the cells are the user's (accepted 2026-11-08); they are real names checked in E1. z-run goes from Opus (rank 3) to the cheap model (the user: "fine for z-run"), and z-design stays off the cheap model (the user: "z-design should be opus-5.5-medium and grok-4.7-high").

**A review activity no file names falls back to the `zz-review` table.** `models.resolveActivity(layers, activity)` resolves the activity's own table when any layer names it, else (a `zz-review-…` activity) the `zz-review` table, else it is c0117's "no file names it" error. The root file therefore carries no table for `zz-review-design`, `-raft`, `-final` or `-idea`: nothing about them differs from `zz-review`. A new review mode is expensive until someone gives it its own table, and a file that only has a `zz-review` table (c0117's fixtures) resolves as before.

**Which reviews are final (the redesign).** A review is **final** when nothing is judged after it. With one round each, that is a fact about the review's kind, not about a round count or a verdict: the design review (its one round), the raft review, the final review of the finished stack (`--mode final`, `final-review-NNN.md`, the review `./zn done` reads) and the idea review (c0260). A layer's code review (`--mode code`, `review-NNN.md`) and a stream review are on the way: the stack's final review follows and judges the whole diff and the trace. So `models.ON_THE_WAY` names the two reviews that are not final, `zz-review-code` and `zz-review-stream`; `models.reviewRule` binds `zz-review` and every other `zz-review-<x>` activity (Opus on claude, a grok model at xhigh on grok, on agent Opus as the first choice with the fallbacks the user named), so a review mode added later (c0260's idea review, c0262's per-ticket full-force review) is expensive and bound until someone names it on the way; `zz-review-code`, `zz-review-stream` and every other command take any model. There is no `--final` flag and no `*-final` activity: `dispatch.activityOf(step, mode)` is `REVIEW_MODES[mode].activity`, or `zz-review-<mode>` for a mode with no field (so c0260's `idea` needs none). The user's "expensive models run every final review" is therefore met without ever guessing which round is last. **(prep)** The layer code review on the way is cheap: that is the one place this redesign lowers the model of a review that ran on Opus before (the final review of the stack, which is expensive and mechanically checked by the trace, carries the rest). This default reverses a rule the skills call the user's ("a reviewer on the author's model shares its blind spots") and leaves no expensive model applying Code mode's own checklist (sequestration, repository safety, weak tests), so it is **not decided here**: it is the first item under `## Open to the human` (F1), and the user must rule before `./zn approve`.

**An ordered preference within a CLI (the user, 2026-11-08: "opus-5.5-high if available, else kimi 3.1 pro, else grok-4.7-xhigh").** A table may carry `fallback = ["kimi-k3-high", "grok-4.7-xhigh"]`: models of the same CLI, same runtime and budget, tried in order. `models.tries` lists a spec's `model` and then each fallback before the next CLI. `models.available(spec, listed)` says whether the CLI lists the model (`listed` is the ids `agent --list-models` or `grok models` print, nil for a CLI with no list: assumed available). The dispatcher reads each CLI's list once per run (`parseModelList` takes the lines as the CLIs print them: grok `  - id` after a banner, agent `id - description` under a heading and a tip line), with the same binary resolution and `.cache` fence as the CLI itself, fails open on a failed or empty list (one stderr line), and skips a try whose model is not listed as an attempt with outcome `missing` and the detail "model <id> not listed by <cli>". What could not be verified: the CLI lists `kimi-k3-high`, `kimi-k3-max`, `kimi-k3-low` and `kimi-k2.7-code`, no "kimi 3.1 pro"; `kimi-k3-high` is the stand-in, **for the user's veto**.

**Waiting (the user: without a human the chain goes all the way to the merge).** The dispatcher had no polling step (E2); the user's decisions make waiting a model activity and take the human out of the wait, so this issue gives the chain one polling step and no waiting-for-a-human state:
- `dispatch.next` returns `{ kind = "step", step = "z-wait", waitFor, pr, head }` when a prep or rafting gate has only its PR's checks, or GitHub's merge computation, left to wait for: the gate is one `auto_merge` names, the PR is not a draft, no check has already failed (`Pr.failed`, from the rollup), it is not `CONFLICTING` (`Pr.conflicting`), it carries nothing a human must judge (`judged`), its head is known and not yet waited on (`Facts.waitedHead`), and it is either not green (`waitFor = checks`) or green with `mergeState` UNKNOWN, GitHub still computing (`waitFor = mergeable`). It waits once per head, then re-reads the PR: green and mergeable means the gate merges, as c0117 built it. A step that ended without the checks passing leaves `waitedHead` set, so a rerun does not wait again on the same head: the chain stops with exit 4 naming the reason (the failed-step stop exempts `z-wait`; a case pins it).
- Exit 4 stays, and for reasons that are not waiting for a human: a draft; a conflict; a failed check; a PR the one tracker-state function says carries something outside the item (`judged`); a wait that ran out (`wait_minutes`); a gate `auto_merge` leaves to a human by configuration; and the run gate, which `models.GATES` does not list, so until c0252 ("the dispatcher merging after its own checks", the user: "c0252 builds it") the run PR still stops at exit 4. `waitFor = "merged"` is built here for it.
- `dispatch.waitCommand(what, pr, seconds, every)` is `./zn run --time <seconds+every+30> -- bash -c '<loop>'`: a loop that polls (`gh pr checks <n>`: rc 0 passes, rc 8 pending, "no checks" yet; any other rc is a failure only the third time in a row; or `gh pr view <n>` for `mergeable` and for `merged`), sleeps `every` seconds only if the next poll still fits before its own deadline, and ends 0 (holds), 2 (cannot hold) or 3 (ran out). The dispatcher passes `seconds = 600`, `every = 30`.
- `dispatch.waitPrompt(command, times)`: run the command with a tool timeout of `<bound>×1000` ms, again on exit 3 at most `times` times, stop on 0, 2 or any other code, and do nothing else. `dispatch.prompt` returns this alone for `z-wait`. `times` = ceil(`[dispatch] wait_minutes` × 60 / 600); `wait_minutes` defaults to 60 and is parsed by `models.parse` like `stall_seconds`.
- The step runs in the item's own worktree like any model step, records its row under the phase of the gate (`prep`), with the model of `z-wait`. The dispatcher never reads the model's words; it re-reads the PR as the gates do. `./zn dispatch z-wait <id> --pr <n> --until checks|merged [--dry-run]` is the manual form.
- Waiting for a review (the user: "Accept the blocking wait"): the author waits for a nested `zz-review` as one blocking shell command; there is no wait model for it. The user accepted that a z-design session on Opus at medium blocks on its nested review (2026-11-08: "Accept it"); with one review round per design it is now one Opus cache rewrite per design.

**The cost per model shows (re-checked against #294).** Spend rows are `spend.d/<writer>.tsv` lines (and older `spend.md` files) with a `model` column, so the real model name is the record; no column is added. Two facts of #294 matter: the dispatcher writes its rows with the model it started, and `./zn commit` records the `--model` it is given, but `./zn spend` replaced a typed `--model` with the first model its transcript reading found in the span, which for an interactive review is often the author's. So `spend.chooseModel(typed, measured)` is added and `./zn spend` uses it: **a typed `--model` wins** (the lead's report of its reviewer, as before #294), the measured one fills a row with none. `ledger.byModel(rows)` sums tokens, the measured AI time (`ai` seconds as minutes, wall as the fallback; a model whose time could not be read shows `?`) beside the legacy typed minutes, and rows per model id (rows with none under `none`), and `./zn metrics` prints it as a "by model" table `| model | tokens | ai minutes | typed minutes | rows |` (`ledger.renderByModel`) over the rows of `spend.md` and `spend.d` of every issue. The reviewers' tokens still come from the runner.

**Back-compat.** A file with only per-skill tables and pinned models (c0117's fixtures) resolves exactly as before (AC12); the root file is the one that changes. `models.reviewRule` keeps its c0117 behaviour for the `zz-review` table (the first choice through agent stays Opus); fallbacks, allowed through agent only, may also be `kimi-k3-high`, `kimi-k3-max` or a grok model at xhigh.

**Pure/adapter split, server authority.** Rules are pure in `models.luau`, `dispatch.luau`, `ledger.luau`, `spend.luau` (`chooseModel`) and `finalround.luau`; `dispatcher.luau` (resolve by activity, the wait step and its `waitedHead`, `wait_minutes`, the model-list read, the raft-mode row) and `main.luau` (the two refusals, the metrics table) are the adapters. No Roblox code.

**Commands refuse (the user, 2026-11-08: "Commands refuse"; judged by kind of model).** `./zn status <id> prepared` (an issue's and a raft's own design review) and `./zn done` (the final review) refuse unless that review was recorded on a model of a final-review KIND. Pure module `z-nile/engine/finalround.luau`; the kinds are defined once in `models.luau` (`models.FINAL_SHAPES` per CLI family: claude any `claude-opus-…`; grok any `grok-…-xhigh`; agent any Opus, `kimi-k3-high`/`kimi-k3-max` (stand-ins) or `kimi-k3.1-pro-high/max`, any `grok-…-xhigh`; kimi `k3.1-pro` or `k3-256k` at high or max; `models.isFinalModel(id)`). The review rule and the commands read the same list, so no id is named anywhere in the rule: a new Opus id passes, a Sonnet, a non-xhigh grok or `kimi-k2.7-code` fails.
- Which round: `lastRound(files, kind)`: the highest `design-review-NNN.md` (kind `design`, in the item's or the raft's folder; older items may hold several) or the highest `final-review-NNN.md` (kind `final`, in the raft's folder). A layer's `review-NNN.md`, a stream review, a refute and a harvest are not rounds (they were the "code" kind of the first design, which judged the last `review-NNN.md`, a file `done` no longer reads).
- Which row records it, matched by phase and exact subject: design phase `design-review`, subject `design-review-NNN` for an ISSUE (what `./zn spend --note` and the dispatcher write) and `<R-id>: design-review-NNN` for a RAFT (`./zn spend <R-id> --phase design-review` spreads the row over the members with that subject; every other phase keeps its note as written); final phase `code-review`, subject `<R-id>: final-review-NNN` (the `./zn commit -m` line the dispatcher prints and zz-execute Phase 5 now says). A member's own round, another raft's row, a stream review's and a later `<id>: … fixes` are not it. When several exact rows record the round (a retry, a fallthrough), one on a final-review kind is enough.
- Which rows are read (re-checked against #294): this checkout's `spend.md` and `spend.d/*.tsv` of the item (design) or of the members (final, and a raft's design round), through the one reader `./zn metrics` uses. `./zn spend` commits its row on the branch, so an interactive row is here (a design-review row keeps its subject exactly as typed: the measured span's note is not appended to it, or no row could match); the dispatcher publishes its design-review row to `origin/main`, where it arrives with `./zn sync` (the refusal says so). The dispatcher's buffered row of a code, stream or final review carries the subject it prints (`<id>: <note>`), so a dispatched final review proves itself. A file that does not parse refuses with its own text, never "no rows".
- The cutoff and the base (keyed on the rows, not on commit times): the rule binds an item when `finalround.luau` has landed on `origin/main` (the UTC minute of the merge onto main that first brought it there: `git log --first-parent --diff-filter=A`, because `./zn done` lands `--no-ff` and the plain query returns the layer commit's date) and the item's first review row of the kind's phase is at or after that minute, or there is no such row yet. An item in flight at the landing is never locked out, and so is not one whose rows are model-less but dated before. A repository with no `origin` remote, or whose base has no root `.models.toml`, has nothing to hold a round to and nothing binds; an `origin/main` that cannot be read is a refusal with its own text (a fixture with an origin and no `origin/main` ref makes c0008's done-order cases red: Overrides). An ISSUE with no design review round at all is refused too (a raft with none, a single issue or an unchanged record, is not).
- The refusal text, one per kind: "the last design review round (design-review-001) was not recorded on a final-review model: its spend row has model X (or no model, or no row); a final review runs a model of a final-review kind (any Opus, kimi k3.1-pro or k3-256k at high or max (the agent CLI's kimi-k3-high and kimi-k3-max stand in), any grok model at xhigh; .models.toml names them for zz-review in order of preference). Run it with ./zn dispatch zz-review <id> --mode design (an interactive reviewer's row: ./zn spend <id> --phase design-review --model <its model id> --note design-review-001; its model is the lead's report), if it was dispatched ./zn sync first, then try again"; for the final review `--mode final` and `./zn commit -m "<R-id>: final-review-NNN" --phase code-review --model <its model id>`. With every model of every CLI unavailable the only way out is a reviewed edit of `.models.toml`.
- Wiring, prototyped and run: `finalRoundRefusal(kind, dir, rows, owner, requireRound)` in `main.luau`, called at the carried move's `design: ready` check (each target, a raft's own folder included, whose rows are its members') and in `cmd.done` after `reviewProblem`, before the raft's check; `./zn spend <R-id>` prefixes the raft's id for the design-review phase; `./zn metrics` prints the by-model table last.
- **The dispatched raft review of a new raft (the user: "Build it now, one more round").** The dispatcher's `record` wrote every design-review row from its `zn-dispatch` worktree, synced to origin/main, where a NEW raft's membership is not yet known; a raft-mode review's row (`zz-review --mode raft`, phase `design-review`, a raft id) is now written with `zn(cwd, spend …)` from the author's worktree (main's `record` already receives that `cwd`), after a `./zn spend <R-id> --phase design-review --begin` there before the reviewer starts so the runner measures the span (no typed `--time` or `--tokens`, which #294 ignores), committed on the author's branch and never also kept pending; when that write fails the dispatcher prints the exact `./zn spend <R-id> --phase design-review --model <the reviewer's model> --note design-review-NNN` line for the author to run.

### Scalability
A new CLI adds its tables to the activities that exist; a spec fails an activity without a model for a CLI of `models.CLIS`. A new activity is one table (or none, when it should take `zz-review`'s). The waiting loop is one condition per call; the refusal reads the rows of one item or one raft's members.

### Maintainability
Models are written once per activity and CLI, in the file; the rules (`activityOf`, `resolveActivity`, `reviewRule`, `waitCommand`, `byModel`, `finalround.check`, `chooseModel`) are pure functions with their own cases. The exact model names are pinned only at check time (ZN_C0261_EXACT on this issue's check lines), so a model upgrade edits the file and its check, not a promoted spec.

### Usability
A user reading `.models.toml` sees each command and activity with its real model; `./zn dispatch … --dry-run` prints `activity=` and the model it would start; `./zn metrics` shows cost per model; a refusal names the review, the model it ran and the command that fixes it.
