# c0261: Model tiers: cheap, sharp and wait

## Problem
User (2026-11-07): "We want to be economical so we want to use sharp expensive models for all final reviews but we only need a cheaper and faster model on the way there. Be smart about it across different providers (agent and grok are 4.6 high for cheap 4.7 xhigh for expensive not much point in getting more granular). Use cheap haiku or composer models or similar when waiting for things, don't orchestrate and wait on expensive models, keep it cheap."

Today `.models.toml` names one model per skill and CLI, and the expensive one runs whole steps: z-design and z-run on Opus or grok-4.7 high, and every review round on the review model. Waiting (for a gate, CI, a PR's checks, a subagent) costs as much as the model that waits. What should happen:
- Each CLI has three tiers: **cheap** (fast, for authoring and the way there), **sharp** (expensive, for every final review) and **wait** (the cheapest, for waiting and polling).
  - grok and agent: cheap is 4.6 at high, sharp is 4.7 at xhigh, with no finer levels.
  - claude: cheap is Sonnet, sharp is Opus, wait is Haiku.
  - agent's wait tier is composer, or similar.
  - Every other supported CLI (kimi, agy, deepseek once supported, c0175) is mapped the same way.
- **Sharp runs every final review:** the idea review (c0260), the final design review round, the final code review round and the full-force review (c0262). Everything on the way (authoring, middle review rounds, streams, fixes) runs cheap.
- **Nothing expensive orchestrates or waits.** A long wait or poll runs on the wait tier, and an orchestrating loop (the worker, c0253) runs cheap and hands sharp work to a sharp step.
- Spend records the tier with the model, so the cost per tier shows.

Decided with the user (2026-11-07): "wait is a model activity the dispatcher uses for steps that only poll/babysit (CI, a review, a merge gate)".
Decided with the user (2026-11-07): "(b) we have everything we need we just need to define the right model for each activity, there is full modularity already".
Decided with the user (2026-11-07): "we're sticking with model names as they are not aliases".

(So `.models.toml` ties a real model name, with its effort, per CLI to each command and activity; there are no cheap, sharp or wait names, no `[tiers.<cli>]` tables and no `tier = ...` key: this replaces the capture's two Solution ideas about them. The intent stays: expensive models on every final review, cheap ones on the way and for waiting.)

A human stop remains for a real block or a question.)

## Non-goals
- Model-family rotation between review rounds (c0251); the tiers say how sharp, c0251 says which family.
- Remote runtimes (c0142).

## Solution
- `tier = "cheap" | "sharp" | "wait"` per step in the skills, and `[tiers.<cli>]` tables in `.models.toml` that the existing per-skill tables reference. The exact model ids are checked against each CLI at design.
- zz-review learns which round is final, and z-design and zz-execute ask for sharp only there.
- (prep) Detail added after the captured bullets, nothing removed: `.models.toml` keeps its per-skill, per-CLI tables and gains a table for each activity that really runs a different model (`zz-review-design`, `zz-review-code`, `zz-review-stream`, `z-wait`), each naming a real model and effort per CLI; `zz-review --final` selects the final round of a design or code review; `z-wait` is the polling step; `./zn metrics` shows the cost per model. The user's decision above replaces the two captured ideas that name tiers.

## Design
**One rule: tie a real model to each command and activity.** `.models.toml` already has one table per skill and CLI (`[z-design.claude]`: model, effort, rank, runtime, budget). This issue adds no vocabulary: it adds a table where an activity runs a different model, and sets the models. The activity is the table's key.

| activity (key) | what runs | claude | grok | agent (Cursor) |
|---|---|---|---|---|
| `z-ticket` | sharpening an idea into a ticket | `claude-sonnet-5-5` at high **(prep)** | `grok-4.6` at high **(prep)** | `cursor-grok-4.6-high` |
| `z-design` | authoring a design | same | same | same |
| `z-raft` | grouping prepared issues | same | same | same |
| `z-run` | executing a raft | same | same | same |
| `zz-review-design` | a design review round on the way | same | same | same |
| `zz-review-code` | a code review round on the way | same | same | same |
| `zz-review-stream` | a stream review | same | same | same |
| `zz-review` | every final review: the final design round (`--final`, dispatched as `zz-review-design-final`), the final code round (`zz-review-code-final`), the raft review, the idea review (c0260), the full-force review (c0262) | `claude-opus-5-5` | `grok-4.7` at xhigh | `claude-opus-5-5-high`, else `kimi-k3-high`, else `grok-4.7-xhigh` |
| `z-wait` | the waiting step | `claude-haiku-5-5` | `grok-4.5` at low **(prep)** | `composer-2.5` |

Claude's on-the-way model is `claude-sonnet-5-5` at high **(prep)**: the user's example named "sonnet-5.5-high", E1 probed `claude-sonnet-5-5` (it answers) and the old `claude-sonnet-5` without effort; grok and agent on the way are the capture's "4.6 high" (the user's example also said grok-4.7-high for sharpening: the capture's line wins, marked for veto). Ranks stay what they are for ordering a raft's members: 2 on the way, 4 for a final review, 1 for the wait. The capture's model names were examples (the user, 2026-11-08), so **every model cell is a proposal for the user's veto**; they are real names checked in E1 (what each CLI lists), chosen to keep the capture's intent: cheap on the way and for waiting, expensive on every final review. z-design and z-run go from Opus (rank 3) to the cheap model: the capture says authoring and the way there run cheap, so that is the **(prep)** cost change for the user's veto. A user's example "z-ticket-sharpen / z-ticket-review" is the pair `z-ticket` (sharpen) and `zz-review-idea` (review the idea, c0260's mode, covered by the `zz-review` table until someone wants it on another model): no new name was invented. Every other CLI (`kimi`, `agy`, `deepseek`, c0175) gets its tables when it is supported, and a spec fails an activity that lacks one for a CLI in `models.CLIS`.

**A review activity no file names falls back to the `zz-review` table.** `models.resolveActivity(layers, activity)` resolves the activity's own table when any layer names it, else (a `zz-review-…` activity) the `zz-review` table, else it is c0117's "no file names it" error. So the expensive `zz-review` table is the default of every review, a new review mode is expensive until someone gives it its own table, and a file that only has a `zz-review` table (c0117's fixtures) resolves as before. A closer file may set any activity's table, stacking as ever.

**The final-review rule is a property of the activity.** `models.FINAL_REVIEWS` names the final-review activities (`zz-review`, `zz-review-design-final`, `zz-review-code-final`, `zz-review-raft`, `zz-review-idea`, `zz-review-final`); `models.reviewRule` binds exactly those: Opus on claude, a grok model at xhigh on grok, and on agent Opus as the first choice with the fallbacks the user named. The rounds on the way (`zz-review-design`, `-code`, `-stream`) and every other command take any model. c0117's text "Opus through `claude` or `agent`, any grok model at `xhigh` through `grok`" stays true and is extended in the skills: "(agent falls back to a kimi model, then grok at xhigh, when Opus is not listed)".

**An ordered preference within a CLI (the user, 2026-11-08: "opus-5.5-high if available, else kimi 3.1 pro, else grok-4.7-xhigh").** A table may carry `fallback = ["kimi-k3-high", "grok-4.7-xhigh"]`: models of the same CLI, same runtime and budget, tried in order. `models.tries` already lists the specs the dispatcher tries across the CLIs in `order`; it now lists a spec's `model` and then each fallback before the next CLI. `models.available(spec, listed)` says whether the CLI lists the model (`listed` is the ids `agent --list-models` or `grok models` print, nil for a CLI with no list: assumed available); the dispatcher reads the list once per run at the edge and skips a try whose model is not listed, naming it on stderr as it does a CLI that is not installed (the executor's wiring, tests first). The review rule checks the first choice (Opus on agent) and each fallback (Opus, a kimi model, or `grok-…-xhigh`). What could not be verified: the CLI lists `kimi-k3-high`, `kimi-k3-max`, `kimi-k3-low` and `kimi-k2.7-code`, no "kimi 3.1 pro"; `kimi-k3-high` is the stand-in, **for the user's veto**. The other CLIs get no fallback list now; one is a line in their table.

**Which round is final (zz-review learns it).** `./zn dispatch zz-review <id> --mode design|code [--final]`: `dispatch.activityOf(step, mode, final)` returns the activity key: the mode's round on the way, or with `--final` the mode's final-round key. A mode entry may carry `activity` and `final`; one that does not is `zz-review-<mode>`, and is its own final round when that key is in `models.FINAL_REVIEWS` (so c0260's `idea` and c0262's `final` modes need no new fields: whichever lands second adds nothing); any other mode with `--final` is refused (a stream review is never final). The term **final round** keeps one meaning, the one z-design 5.4, 5.5 and zz-execute step 7 already use: the round after which the round rule runs no further round. What changes is that it is always a round run with `--final`: a round on the way never ends the count, because when the rule would stop after one, the next round is run with `--final`; round 5 is run with `--final`; and from the first round run with `--final` on, every round is. So "a final round holds a high only in round 5", 5.5's ready rule and step 7's merge block read as before (a `--final` round 2 that holds a high is followed by another `--final` round, so it is not the final round). The raft review is one round per grouping and always expensive. Cost note **(prep)**: an issue whose first round would have stopped pays one more round, on the expensive model; that is how "expensive models on every final review" is met when the last round cannot be known before it runs.

**Waiting (the user: without a human the chain goes all the way to the merge).** The dispatcher had no polling step (E2); the user's decisions make waiting a model activity and take the human out of the wait, so this issue gives the chain one polling step and no waiting-for-a-human state:
- `dispatch.next` returns `{ kind = "step", step = "z-wait", waitFor, pr, head }` when a prep or rafting gate has only its PR's checks, or GitHub's merge computation, left to wait for: the gate is one `auto_merge` names, the PR is not a draft, no check has already failed (`Pr.failed`, from the rollup), it is not `CONFLICTING` (`Pr.conflicting`), it carries nothing a human must judge (`judged`), its head is known and not yet waited on (`Facts.waitedHead`), and it is either not green (`waitFor = checks`) or green with `mergeState` UNKNOWN, GitHub still computing (`waitFor = mergeable`: a green PR right after another prep merged into main). It waits once per head, then re-reads the PR: green and mergeable means the gate merges, as c0117 built it. A step that ended without the checks passing (exit 2 failed or closed, 3 ran out) leaves `waitedHead` set, so a rerun does not wait again on the same head: the chain stops with exit 4 naming the reason; a `z-wait` that ended `cap`, `stalled` or `quota` on every CLI counts the same (the executor exempts `z-wait` from the failed-step stop; a case pins it).
- Exit 4 stays, and for reasons that are not waiting for a human: a draft; a conflict; a failed check; a PR the one tracker-state function says carries something outside the item (`judged`); a wait that ran out (`wait_minutes`); a gate `auto_merge` leaves to a human by configuration (`auto_merge = []`, a deliberate setting); and the run gate, whose PR c0117 made the human's merge and c0252 ("the dispatcher merging after its own checks") changes: `models.GATES` does not list `run`, so until c0252 the run PR still stops at exit 4. Flagged for the coordinator: the user's "all the way to merge" for the run PR is c0252's, and `waitFor = "merged"` is built here for it.
- `dispatch.waitCommand(what, pr, seconds, every)` is `./zn run --time <seconds+every+30> -- bash -c '<loop>'`: a loop that polls (`gh pr checks <n>`: rc 0 passes, rc 8 pending, "no checks" yet; any other rc is a failure only the third time in a row, so one transient `gh` error is not a failed check; or `gh pr view <n>` for `mergeable` (MERGEABLE holds, CONFLICTING cannot) and for `merged`), sleeps `every` seconds only if the next poll still fits before its own deadline (`end=$((SECONDS+<seconds>))`), and ends 0 (holds), 2 (cannot hold: a failed check, a closed PR) or 3 (ran out). The runner's bound sits above the deadline by one sleep and a margin for `gh` itself, so a timeout is 3, not 124. The dispatcher passes `seconds = 600`, `every = 30`.
- `dispatch.waitPrompt(command, times)`: run the command with a tool timeout of `<bound>×1000` ms (Claude Code's Bash default of 120 s would kill a 10-minute poll; E5 measures grok and agent), again on exit 3 at most `times` times, stop on 0, 2 or any other code, and do nothing else. `dispatch.prompt` returns this alone for `z-wait` (no skill to read, no lessons, no spend line). `times` = ceil(`[dispatch] wait_minutes` × 60 / 600); `wait_minutes` defaults to 60 and is parsed by `models.parse` like `stall_seconds`.
- The step runs in the item's own worktree like any model step, records its row under the phase of the gate (`prep` for a prep gate, `raft` rows as `prep` since z-raft is prep; no new phase), with the model of `z-wait`. The dispatcher never reads the model's words; it re-reads the PR as the gates do. `./zn dispatch z-wait <id> --pr <n> --until checks|merged [--dry-run]` is the manual form (the PR and condition come from its flags; `--dry-run` prints the command).
- Waiting for a review: the author waits for a nested `zz-review` as one blocking shell command, on its cheap model (z-design and z-run are cheap now), which spends no turns while it blocks (E6 could not be measured here: the auto-mode classifier refused a bypass-permissions probe; the claim is the executor's Phase 1 probe and the user's to confirm). The wait model is not needed for it, and "nothing expensive waits" holds because no expensive activity authors or orchestrates.

**The cost per model shows.** Spend rows already record the model that spent their tokens (c0117), so the real model name is the record; no column is added. `ledger.byModel(rows)` sums tokens, minutes and rows per model id (rows with none under `none`), and `./zn metrics` prints it as a "by model" table (`ledger.renderByModel`). The final round's model differs from a round on the way's, so the cost of final reviews shows apart.

**Back-compat.** A file with only per-skill tables and pinned models (c0117's fixtures) resolves exactly as before (AC12); the root file is the one that changes. `models.reviewRule` keeps its c0117 behaviour for the `zz-review` table, except that agent also accepts grok at xhigh.

**Pure/adapter split, server authority.** Rules are pure in `models.luau`, `dispatch.luau` and `ledger.luau`; `dispatcher.luau` (resolve by activity, `--final`, the wait step and its `waitedHead`, `wait_minutes`) and `main.luau` (the flag, the metrics table) are the adapters. No Roblox code.

**Commands refuse (the user, 2026-11-08: "Commands refuse").** `./zn status <id> prepared` and `./zn done` refuse unless the LAST design review round (for `prepared`) or the last code review round (for `done`) was recorded on a final-review model. New pure module `z-nile/engine/finalround.luau`:
- `lastRound(files, kind)`: the highest `design-review-NNN.md` (kind design) or `review-NNN.md` (kind code) among the item's or raft's folder files; stream reviews, refutes and harvests are not rounds.
- Where a round's model is recorded: the `model` of its spend row, found by the round's stem (`design-review-002`) in the row's subject or attribution: the dispatcher writes the row (`design-review-NNN`, or the printed `./zn commit -m "<R-id>: review-NNN" --model` line), an interactive reviewer's row gets `--model <its model id>` (z-design 5.2 and z-raft's spend lines, zz-execute Phase 4's commit line), and the author's own lines (the answering `design-refute-NNN` row) carry `--model <your model id>` (F11) so the cost per model shows; those rows are not the check's.
- `finalModels(resolved)`: the ids of every try of `zz-review` on every CLI, fallbacks included, as a row records them. The ordered list is what the escape is: a CLI whose preferred model is unavailable falls to the next, and the row records the one it used, which is on the list. A CLI whose whole list is unavailable has no escape but a reviewed edit of `.models.toml` (a PR a human merges).
- `enforced(firstRoundAt, landedAt)`: the rule binds an item whose first round file was committed at or after `landedAt`, the commit time of `finalround.luau`'s first add on the base (`git log --diff-filter=A --format=%ct --reverse origin/main -- z-nile/engine/finalround.luau`, the oldest); an uncommitted first round binds; with the module not yet on the base nothing binds; no calendar date, so an item in flight when this lands is never locked out, and the executor's own PR is not held to it before it lands.
- `check(kind, files, rows, finalModels, enforced)`: nil, or the refusal text: "the last design review round (design-review-002) was not recorded on a final-review model: its spend row has model X (or no model, or no row); a final round runs one of the models .models.toml names for zz-review, in this order of preference: <list>. Run it with ./zn dispatch zz-review <id> --mode design --final (an interactive reviewer: ./zn spend <id> --phase design-review ... --model <its model id> --note design-review-002 ...), then try again".
- Wiring (the executor, tests first): in `main.luau`, at the two `design: ready` checks of the carried move to `prepared` and in `reviewProblem` for `done`; the inputs are `fs.readDir` of the folder, the parsed `spend.md` of the item (a raft: its members and itself), `finalround.finalModels(dispatcher.resolve("zz-review", id, nil))` and the two commit times above. Sequestered command cases to write first, each with a Rules and mutants row marked `reasoned` until then: (a) `status <id> prepared` in a fixture whose last round row has model `claude-sonnet-5-5-high` exits 1 with the text above; (b) the same with a final model passes; (c) the same item with its first round committed before the module's add passes; (d) `done` on a fixture raft with a cheap last `review-NNN` row exits 1; (e) with a final-model row it goes on to the check. ### Scalability
A new CLI adds its tables to the activities that exist; a spec fails an activity without a model for a CLI of `models.CLIS`. A new activity is one table (or none, when it should take `zz-review`'s). The waiting loop is one condition per call.

### Maintainability
Models are written once per activity and CLI, in the file; the rules (`activityOf`, `resolveActivity`, `reviewRule`, `waitCommand`, `byModel`) are pure functions with their own cases. The exact model names are pinned only at check time (ZN_C0261_EXACT on this issue's check line), so a model upgrade edits the file and its check, not a promoted spec.

### Usability
A user reading `.models.toml` sees each command and activity with its real model; `./zn dispatch … --dry-run` prints `activity=` and the model it would start; `./zn metrics` shows cost per model.
