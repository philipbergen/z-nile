# c0261: Model tiers: cheap, sharp and wait

## Problem
User (2026-11-07): "We want to be economical so we want to use sharp expensive models for all final reviews but we only need a cheaper and faster model on the way there. Be smart about it across different providers (agent and grok are 4.6 high for cheap 4.7 xhigh for expensive not much point in getting more granular). Use cheap haiku or composer models or similar when waiting for things, don't orchestrate and wait on expensive models, keep it cheap."

Today `.models.toml` names one model per skill and CLI, and the expensive one runs whole steps: z-design and z-run on Opus or grok-4.7 high, and every review round on the review model. Waiting (for a gate, CI, a PR's checks, a subagent) costs as much as the model that waits. What should happen:
- Each CLI has three tiers: **cheap** (fast, for authoring and the way there), **sharp** (expensive, for every final review) and **wait** (the cheapest, for waiting and polling).
  - grok and agent: cheap is 4.6 at high, sharp is 4.7 at xhigh, with no finer levels.
  - claude: cheap is Sonnet, sharp is Opus, wait is Haiku.
  - agent's wait tier is composer, or similar.
  - Every other supported CLI (kimi, agy, deepseek once supported, c0175) is mapped the same way.
- **Sharp runs every final review:** the idea review (c0260), the final design review round, the final code review round and the full-force review (c0262). Everything on the way (authoring, middle review rounds, streams, fixes) runs cheap.
- **Nothing expensive orchestrates or waits.** A long wait or poll runs on the wait tier, and an orchestrating loop (the worker, c0253) runs cheap and hands sharp work to a sharp step.
- Spend records the tier with the model, so the cost per tier shows.

Decided with the user (2026-11-07): "wait is a model activity the dispatcher uses for steps that only poll/babysit (CI, a review, a merge gate)".
Decided with the user (2026-11-07): "(b) we have everything we need we just need to define the right model for each activity, there is full modularity already" (the per-skill, per-CLI structure of `.models.toml` and `models.luau` stays as it is; cheap, sharp and wait are the vocabulary for choosing each activity's model, not a refactor; add a wait entry only if the dispatcher actually has a polling step to bind it to).
Decided with the user (2026-11-07): "we're sticking with model names as they are not aliases" (models are named by their real names, never aliases).
Decided with the user (2026-11-07): the mapping of activities to tiers and the existing ranks and caps stay as the design proposes ("keep your guesses"); the design's choices are marked **(prep)** and listed for the user's veto.

## Non-goals
- Model-family rotation between review rounds (c0251); the tiers say how sharp, c0251 says which family.
- Remote runtimes (c0142).

## Solution
- `tier = "cheap" | "sharp" | "wait"` per step in the skills, and `[tiers.<cli>]` tables in `.models.toml` that the existing per-skill tables reference. The exact model ids are checked against each CLI at design.
- zz-review learns which round is final, and z-design and zz-execute ask for sharp only there.
- (prep) Detail added after the captured bullets, nothing removed: the tier tables are `[tiers.<cli>.<tier>]` (CLI, then tier) holding `model`, optional `effort` and `rank`; a per-skill table says `tier = "cheap"` and keeps its own `runtime`, `max_tokens` and caps; `zz-review --final` selects the sharp tier for a final round; `z-wait` is the polling step the wait tier is bound to; the spend ledger gets a `tier` column.

## Design
**Reconciling the capture with the user's chat answers (the one open question for the user).** The capture asks for `[tiers.<cli>]` tables that the per-skill tables reference. The user's answer to prep's questions was "(b) we have everything we need, we just need to define the right model for each activity, there is full modularity already" (no new tier layer, no refactor), and "we're sticking with model names as they are not aliases". Both hold in this design: (1) the tier tables are only the lookup from a class to a real model name, per CLI (`[tiers.claude.sharp] model = "claude-opus-5-5"`), and nothing else; (2) every per-skill, per-CLI table keeps its structure and keys, and a table that sets its own `model` keeps it exactly as c0117 had it (a file without any `tiers` table resolves as before: AC2); the new `tier` key is additive; (3) no alias anywhere (AC3, AC11). If the user meant "no `[tiers.*]` tables at all" the capture's Solution bullet is the part to change (the per-skill tables would then each name the model, and the finding of AC9 to AC11 would still hold with the models written in each table): this is put to the user in the report and is not decided here.

**Tiers and the real model of each CLI (the capture's, checked against the CLIs on this machine).**

| tier | claude | grok | agent (Cursor) |
|---|---|---|---|
| cheap (rank 2) | `claude-sonnet-5` | `grok-4.6` at high | `cursor-grok-4.6-high` |
| sharp (rank 4) | `claude-opus-5-5` | `grok-4.7` at xhigh | `grok-4.7-xhigh` |
| wait (rank 1) | `claude-haiku-5-5` | `grok-4.5` at low **(prep)** | `composer-2.5` |

E1 below checks each id: `agent --list-models` lists `cursor-grok-4.6-high`, `grok-4.7-xhigh` and `composer-2.5`; `grok models` lists `grok-4.7`, `grok-4.6` and `grok-4.5`; `claude --model claude-haiku-5-5` answers and reports `modelUsage` `claude-haiku-5-5`. The grok CLI is not signed in here, so grok's effort values (`high`, `xhigh`, and `low` for the wait tier) are the existing adapter's `--reasoning-effort` values and `low` is unverified. grok's wait model and `composer-2.5` (rather than `composer-2.5-fast`) are the design's choices (**(prep)**, for the user's veto). Every other CLI (`kimi`, `agy`, `deepseek`, c0175) gets its three tiers in the same table when it is supported: c0175 adds `[tiers.<cli>.*]` with its CLI, and the rule "a CLI lists all three tiers" is checked at resolve (a tier a step needs and its CLI lacks is an error naming it), so the mapping is mechanical.

**Which activity runs which tier (`dispatch.luau` and the file).**
- The tier of a step is the `tier` key of its per-skill table: `z-ticket`, `z-design`, `z-raft`, `z-run` are `cheap` (z-design and z-run were Opus rank 3 and become cheap rank 2: the capture says authoring and the way there run cheap; **(prep)** note for the user: this is the cost change); `z-wait` is `wait`; `zz-review` is `cheap` by default.
- `dispatch.tierOf(step, mode, final)` overrides it for reviews: a `design`, `raft` or `code` round is cheap, and sharp when `--final`; a `stream` review is cheap and is never final (an error); the `idea` mode (c0260) and the `final` full-force mode (c0262) are sharp always. Each mode in `REVIEW_MODES` declares `tier = "round" | "cheap" | "sharp"`; c0260 and c0262 add their entries with `sharp`, and a spec fails any mode without one.
- `models.resolve(layers, skill, tier?)` takes that tier: the tier's model, effort and rank (a closer file replaces only the keys it sets), the skill table's own `runtime`, `max_tokens` and caps. A table with its own `model` keeps it when the call names no tier; a call that names a tier (`--final`) takes the tier's model. `Spec.tier` carries it to the spend row.
- **The sharp tier is the review model of the CLI** (c0117 G7 stays: the reviewer is Opus on claude); the capture's newer words make agent's sharp model `grok-4.7-xhigh`, so `models.tierRule` replaces `reviewRule` for a sharp spec: Opus on claude, a grok model at xhigh on grok and agent (**(prep)** consequence: agent reviewers are no longer Opus; AGENTS.md's "Opus 5.5" reviewers line and the skills' "Opus through `claude` or `agent`" sentence change). `reviewRule` is kept for a `zz-review` table that pins its own model and names no tier (c0117's fixtures).

**Which round is final (zz-review learns it).** The reviewer cannot know before it runs that its round is the last: the stop rule needs the round's severities and the answers. So the author runs middle rounds cheap, and when the round rule (z-design step 5.4, zz-execute step 7) would stop, it runs **one more round sharp** (`./zn dispatch zz-review <id> --mode design --final`). That round is the final round; the rule then applies to it as to any (a high finding fixed or refuted, or an answer more than minor, means another sharp round, with `--final`); the cap of 5 rounds counts it. Once a round was sharp, later rounds are sharp. z-design, z-raft (`--mode raft --final`) and zz-execute (`--mode code --final`) say so; in an interactive session the cheap rounds use a `model: "sonnet"` subagent and the final one `model: "opus"`. `zz-review` reads `--final` as the tier switch and prints it with the model on its `describe` line.

**Waiting (the polling step the user's answer requires).** The dispatcher had no polling step (E2): its gates end the run (exit 4), a nested review is waited on by an idle author, quota is never waited out. The user's answer (a) makes waiting a model activity, so this issue adds one: `dispatch.STEPS["z-wait"]` (kind model, tier wait, phase `wait`). `./zn dispatch z-wait <id> --until checks|merged --pr <n> [--minutes M]` starts the wait tier's CLI headless with `dispatch.waitPrompt(command, times)`, where `command` is `dispatch.waitCommand(until, pr, 600)`: a bounded `./zn run --time 600 -- bash -c '<gh poll> || exit 3'`, exit 0 when the condition holds, 3 when not yet. The model runs it, runs it again on 3, at most ceil(M*60/600) times (default M = 60), and does nothing else. 600 s is under `tool_seconds` (900), so a poll is never killed as a stall. The dispatcher never reads the model's words: after the session it re-reads the PR (`gh`, as the gates do) and exits 0 when the condition holds, 4 when not (the wait ran out). An interactive session has no dispatcher to run the step: the skills tell it to run the same printed command (`./zn dispatch z-wait <id> --until … --dry-run` prints `waitCommand`) as one shell command with a subagent on the wait tier (the Agent tool's smallest model), never a loop on its own model. Nothing expensive waits because every waiting activity has this step or that rule, written for the skills: an orchestrating session (the worker, c0253, not yet built) runs a cheap tier and hands sharp work to `zz-review`; a lead that must wait runs `z-wait`, never loops on its own model. The author waiting on a nested `zz-review` is idle during that single shell command (no tokens), so it needs no wait step; zz-execute keeps that rule and adds that a wait over 10 minutes goes to `z-wait`.

**Spend records the tier.** `ledger.Row.tier` and an eleventh column `tier` (header `HEADER_TIER`) appear only when some row records one, exactly as the model column did (c0117): a ledger with none keeps its header; `parse` reads 7, 9, 10 or 11 cells; a tier needs a model and must be `cheap`, `sharp` or `wait`; rows already written stay as they are and keep their model-only cell count when no row has a tier (render widens the file once, as c0117's did). `./zn spend` and `./zn commit` take `--tier <t>`; the dispatcher passes the tier of every step it records, including the reviewer's `./zn commit … --model <id> --tier <t>` line. `stats` and the board group by the model column as before; a per-tier cost report is the first use of the column and is left to zz-stats (listed in Non-goals below). New phase `wait` in `ledger.PHASES` for the wait step's own row.

**Reconciling mechanisms with c0117's rules.** Back-compat is the rule: c0117's specs build fixtures with pinned models and no `tiers` table, and they must pass unchanged except where listed under Overrides. Every new error names the file and key as c0117's do.

**Pure/adapter split, server authority.** All rules are pure and in `models.luau`, `dispatch.luau`, `ledger.luau` (text in, text out, as zz-arch asks); the adapters are `dispatcher.luau` (passes the tier to `resolve`, the flag, the new step's run and the `--tier` on rows) and `main.luau` (flags). No Roblox code, no client/server question.

### Scalability
A new CLI adds its three `[tiers.<cli>.*]` tables and the per-skill tables that already exist keep working; a new step names a tier; a new review mode declares one (a spec fails otherwise). A fourth tier would be one name in `models.TIERS`, one in `ledger.TIERS` and a table per CLI.

### Maintainability
The model of each class is written once per CLI, in the file; the per-skill tables no longer repeat model ids, so changing the sharp model is one edit. The rules (`tierOf`, `tierRule`, `waitCommand`, the ledger column) are pure functions each with their own cases; `reviewRule` stays for pins only.

### Usability
A user reading `.models.toml` sees three tiers per CLI and which step uses which; `./zn dispatch --dry-run` prints `tier=` with each try; the author's commands for a final round and a wait are the ones the skills print.
