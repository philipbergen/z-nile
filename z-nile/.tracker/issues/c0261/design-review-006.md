### F1 [high] A dispatched raft review of a new raft never writes its row before the rafting PR merges, so `status <R-id> prepared` refuses every new raft of several issues that the dispatcher prepares
Where: prototype `dispatcher.luau` `record` (a design-review row: `ctx.origin(id)` backlog → `zn(worktree(ctx, "zn-dispatch"), { "spend", id, … })` after `zn sync`, else `st.pending`); `main.luau` `cmd.spend` (`targets = store.members(id)`; `if not raftItem or #targets == 0 then fail("run ./zn sync first")`); `store.members` (issues whose own `raft:` line names the raft); `new raft` (publishes the raft doc only, then "membership is written locally and committed"); Design, Commands refuse ("`./zn spend <R-id> --phase design-review --note design-review-NNN` (z-raft's line, and the dispatcher's `record` for a raft-mode review, which calls the same path) spreads the row over the members").
Evidence: the probe seeds prepared c0011 and c0012 (empty `raft:`) and a root `.models.toml`. In worktree `prep-raft` it runs `new raft chore pair c0011 c0012 --project pickman` (→ R0010), adds Theme and Order, sets `design: ready` and writes `design-review-001.md` quoting `Grouped: [c0011@…, c0012@…]`, then commits. In a second worktree `zn-dispatch` synced to main (what `record` uses) it runs `spend R0010 --phase design-review --time 4 --tokens 50 --model claude-opus-5-5 --note design-review-001`. Output:
- `DISPATCHSPEND ok=false :: run ./zn sync first`. On origin/main no issue names R0010 yet, so `store.members` is empty and the row goes to `st.pending`. `flush` writes it only after the rafting PR lands.
- `STATUS1 ok=false :: R0010: the last design review round (design-review-001) was not recorded on a final-review model: its spend row has no row; …`
- The same `spend` from `prep-raft` (the interactive path) writes `R0010: design-review-001` into both members, and then `STATUS2 ok=true`.
So under `./zn dispatch` every new raft of two or more issues is refused at its carried move: `new raft` is how z-raft's no-argument policy makes rafts. Before c0261 this pending row cost only bookkeeping; the new check turns it into a lockout. The refusal's own way out tells a cheap author to write the row by hand with "<its model id>". It does not know that id, because the dispatcher printed only "could not record". The pending row is then flushed as well, after the merge, so the spend counts twice. `fold` and `recombine` into a raft that already has members on main still write the row, but only to those old members, so the bug shows only for a raft that main doesn't know yet. No spec saw this: the raft path is escalation (2), and final-round-raft.spec runs `spend` from the worktree that holds the membership.
Critique: the tempting fix is to make `cmd.spend` take a raft's members from its published `issues:` line when no issue names it. That works for `new raft`, because its published doc carries `issues:`. It is wrong for `fold`, which writes `issues:` only locally, and for `recombine`'s moved members. And it lets a spend row describe membership the rafting PR has not landed.
Consequences: the membership that counts for a raft round is the one the rafting branch carries, and only the author's worktree holds it. If the dispatcher records a raft-mode review's row from the step's own worktree (`cwd`, where it already places the review file), `cmd.spend` there publishes to origin/main and changes nothing locally, as the interactive path does. Three things follow:
- A top-level `./zn dispatch zz-review <R-id> --mode raft` started from the main checkout hits `refuseInMainCheckout("spend")`. It must either run in the rafting worktree or keep the row pending and say so.
- `flush` must not write the row a second time.
- The other modes keep `zn-dispatch`.
Recommendation: record a raft-mode review's row with `zn(cwd, spend …)` in the author's worktree (keep `zn-dispatch` for every other phase and mode), and state it in the Design's "Which spend.md is read" and in `record`'s comment. Sequester two cases:
1. The command case, in the probe's shape: after `new raft`, a raft row on Sonnet is refused, one on a new Opus id passes, and a member's own Opus `design-review-001` does not stand in. This is escalated path (2), which is cheap; mark its row `run`.
2. A dispatcher case: c0117's fakecli as the reviewer in `--mode raft` on a new raft. Assert that each member's spend.md on origin holds `R0010: design-review-001` with the fake's model before `status R0010 prepared`, which then passes.
Mutants: "the row recorded from zn-dispatch" (killed by case 2), "no prefix" (killed by case 1).
Lesson: z-design/results-land-on-every-path

### F2 [medium] The cutoff's wiring has no case that can fail: every command fixture writes its rows in the same minute as the seed commit that "lands" finalround.luau, so a `finalRoundRefusal` that always enforces, or that swaps the arguments to `enforced`, passes check.sh
Where: prototype `main.luau` `finalRoundRefusal` (`finalround.enforced(finalround.firstWhen(rows, kind), landedWhen)`, `landedWhen` from `git log --diff-filter=A --format=%ct --reverse origin/main -- z-nile/engine/finalround.luau` via `os.date("!%Y-%m-%d %H:%M", …)`); final-round-cli.spec (trackerfix's seed holds the engine, so the landing is the seed commit, and every row is written seconds later); final-round.spec's `enforced` and `firstWhen` cases are pure; Rules row "the rule binds by the rows' own `when`" (`run`).
Evidence: in final-round-cli's first case, `landedWhen` and every row's `when` are the same UTC minute (unless the run happens to cross a minute boundary). So `enforced(first, landed)` and the swapped `enforced(landed, first)` are both `>=` on equal strings: true, enforced. `enforced = true` written into the wiring also leaves all three CLI cases green. No case gives the rows a `when` before the landing, which is the property 005 F3 asked to pin ("a fixture whose design-review row is back-dated … passes `status prepared`"). The refute answered with pure cases, which cannot see the call site.
Critique: the design's promise, "an item in flight at the landing, whose rounds are already recorded, is never locked out", lives entirely in this call. Its two plausible wiring mutants survive. The swap is the worse one: the rule never binds once rows are dated after the landing, and check.sh stays green.
Consequences: a back-dated row needs no clock: `trackerfix.elsewhere` can commit to origin a spend.md whose row reads `2020-01-01 00:00`, and a row dated `2099-01-01 00:00` is unambiguously after. Neither touches the gate's speed.
Recommendation: add one case to final-round-cli. A model-less design-review row dated `2020-01-01 00:00` on origin passes `status <id> prepared`; the same round with its only row dated `2099-01-01 00:00` is refused "no model". Give it a `run` row with the mutants "always enforced" and "arguments swapped".
Lesson: zz-test/pin-call-site-arguments
