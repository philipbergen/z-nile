### F2 [low] The raft cutoff exempts every raft review recorded after the landing while its members were prepped before it, though a row with the raft's prefix already proves that the round was recorded under the new rule
Where: Design, "The dispatched raft review of a new raft" (last sentence: "The raft cutoff takes the earliest review row among the members' rows, so a raft grouped after the landing from members prepped before it is exempt (transitional and lenient, by design)"); proto main.luau `finalRoundRefusal` (`finalround.enforced(finalround.firstWhen(rows, kind), landedWhen)` over the members' rows).
Evidence: read from the code, not run. For a raft, `rows` are its members' spend rows, and `firstWhen` takes the earliest design-review `when`, which is a member's own prep round. Every issue that is prepared on the day of the landing was prepped before it. So for as long as such issues are being grouped, no raft review is held to the rule. A Sonnet raft review recorded the week after the landing as `R0010: design-review-001` passes `status R0010 prepared`. That case is exactly what `final-round-newraft.spec` refuses, but only because the spec's fixture writes every row after the seed.
Critique: the cutoff exists so that an item whose rounds were recorded before the rule existed is not locked out. A raft round written with the `<R-id>: ` prefix was recorded by c0261's own `spend`, so it postdates the landing by construction. The members' rows are only a proxy for "recorded before", and here the proxy is far more lenient than the purpose needs. Computing the cutoff over the raft's own prefixed rows alone (006 F4's first option) is wrong: a raft reviewed before the landing has no prefixed row, and its nil `firstWhen` would read as "no row yet, enforced", which locks it out.
Consequences: binding a raft when any member row carries its `<R-id>: design-review-` subject has one narrow lockout window. A z-raft session that is in flight at the landing and follows the old skill text records its row without `--model`, and the new `spend` gives it the prefix, so the refusal fires. The refusal text already names the way out: re-record the row with `--model`.
Recommendation: escalate to the user: either keep the members' cutoff as written (the raft rule rarely binds until the pre-landing prepared issues are rafted), or enforce for a raft when any member row carries the raft's prefixed subject, else by the members' cutoff (with the in-flight window above). Put it in Open question 2's veto list either way. For the second option, add a final-round-cli case: members' rows dated `2020-01-01 00:00` and a Sonnet `R0010: design-review-001` row are refused, and the same without the prefixed row passes.

### F3 [low] When the author-worktree write fails, the row is kept pending, but the stderr line gives no model or tokens, and a row the author writes by hand is later written a second time by `flush`
Where: proto dispatcher.luau:427-432 (`dispatch: could not record {id}'s {phase} row from the author's worktree (…): kept as pending`); `flush` (a pending non-deliver row is written when its item is in the backlog on origin); Design: "a failed write is the only case kept pending, and then `flush` writes it once".
Evidence: read from the code. A failed `spend` in the rafting worktree (a publish race, say) leaves the row pending. `flush` at the end of the same run tries from `zn-dispatch`, where the members are still unknown, and fails again. The z-raft author's `status <R-id> prepared` then refuses with "there is no row", and the refusal tells it to run `./zn spend <R-id> … --model <its model id>`. A dispatched author does not know that id, because the stderr line does not print it. If the author writes the row anyway, the next run's `flush`, after the rafting PR merges, writes it a second time. 006 F1 named the same gap for the old message. No case makes the write fail (zz-test/pin-fail-safes-where-they-act).
Critique: the tempting fix is to drop the pending fallback. That loses the row whenever nobody acts on the message.
Consequences: printing the exact `./zn spend` command is enough for the author to write the row. Keeping it pending as well is what causes the double write.
Recommendation: on a failed write, print the full `./zn spend <R-id> --phase design-review --time … --tokens … --model <model> --note design-review-NNN` line for the author to run, and do not also keep the row pending, or keep it pending and say in the line that it will be written after the merge, and not both. Pin the line with a fakecli case whose fake `zn` publish fails, or record the row as `reasoned` if a failing publish cannot be staged cheaply.
Lesson: zz-test/pin-fail-safes-where-they-act
