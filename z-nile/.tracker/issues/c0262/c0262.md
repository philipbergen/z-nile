# c0262: Full force final review

## Problem
A final limited-view review per ticket checks the ask against the design and the design against the implementation, and sends it back when off course

Decided with the user (2026-11-07): "Full force = (a): the final review runs on the strongest model (Opus now); it is not a no-waiver hard gate."
Decided with the user (2026-11-07): "per issue yes, which is layer in the pr": the final review is per issue, a layer within the raft's one PR.
Decided with the user (2026-11-07): the view's contents: "ok" (ask, design, the design's branch edits, check, acceptance specs, skill, diff).
Decided with the user (2026-11-07): "we're sticking with model names as they are not aliases, you carried the idea too far": the final review names concrete models by the existing review rule (Opus for claude and agent, grok at xhigh), with no sharp tier or alias and no dependency on c0261.
Decided with the user (2026-11-07): the exemption (rafts in flight and rafts z-raft did not make) is kept.
Decided with the user (2026-11-07): "a failed merge review goes back to blocked and needs human intervention": a final review that does not approve sets the item BLOCKED for the user; there is no send-back-to-executor loop and no round cap.

## Non-goals
- No change to the code review (zz-execute Phase 4), the stream reviews or the design review: the final review comes after the code review and judges something else (the ask against the design, the design against the implementation), from a smaller view.
- No new spend phase and no new `.models.toml` table: the final review resolves through `zz-review`'s table today, which `models.reviewRule` binds to Opus (claude, agent) or a grok model at xhigh (AC5). No alias, no tier of its own, no dependency on c0261.
- Not the verbatim ask's capture (c0260 keeps it in the ticket): this issue reads whatever `./zn capture` returns, so c0260's section is in `ask.md` once it exists.
- No change to the game, to a project's `src/`, or to any promoted spec. Not a no-waiver gate (the user's decision): rafts in flight and rafts z-raft did not make are exempt.
- No automatic send-back loop, no round cap, no automatic re-prep (the user's decision): a failed final review stops for a human.

## Solution
A new `zz-review` mode, `final`, run once per ticket (issue) of a raft after the code review is resolved and before `./zn done`. It gives a fresh reviewer on the review model of the CLI (Opus; grok at xhigh) a limited view built by `./zn final-view`: the ask as captured, the issue's design as it stood on the base (plus the branch's edits to it, as a patch to check), its `check.sh` and acceptance specs, the zz-review skill, and the implementation diff for its Touched modules. It holds no execution record (no Verification log, review, refute, harvest, spend or prompt file). The reviewer compares the ask with the design, and the design with the implementation, and writes `Verdict: approve` or `Verdict: changes`, each finding tagged `Off course:` (`implementation`, `design` or `ask`). `./zn done` refuses a raft until every ticket's newest final review approves. A final review that does not approve sets the item BLOCKED: the executor posts the findings, stops with the PR in draft, and a human intervenes; a new final round that approves clears it.

## Design
Quoted decisions relied on: none from `game-design.md` (tooling only). The user's decisions of 2026-11-07 are in the Problem. Standing rules: "the review model belongs to the CLI" (Opus through `claude`/`agent`, grok at `xhigh`), "Never narrow captured scope", "Keep same user, accept detection" (the limited view is a convenience layer, not a security boundary).

### Product choices
Decided by the user (Problem): per issue as a layer in the raft's PR; the view's contents; concrete model names by the review rule; the exemption; a failed review goes BLOCKED for a human. Still a **(prep)** choice, for the user to veto:
1. **(prep)** How a human clears a BLOCKED final review: a new round (`./zn dispatch zz-review <issue> --mode final`) after their intervention, which must approve. There is no waiver command; a human who disagrees with the reviewer fixes the cause or reruns the round. Alternative: a `Decided with the user` line that waives a round. ### Rules
- **R1 View**: `finalreview.view{id, ask, doc, designChanges, check, diff, skill, acceptance?, others?, emergent?}` returns `README.md`, `ask.md`, `design.md`, `design-changes.patch`, `check.sh`, `implementation.patch`, `skill.md` and, for each acceptance spec, `acceptance/<name>`. `design.md` is the issue document **as it is on the base** without its `status:` and `raft:` frontmatter lines and without the `## Verification log` section to the end of the file. `design-changes.patch` is the diff of that document between the base copy and HEAD's, both stripped the same way (`finalreview.designText`: no `status:`/`raft:` lines, no Verification log), so the executor's log is in no file; every other edit the executor made to the design, including any `Scope decision` or `Decided with the user` line it added, which `README.md` calls claims to check, not decisions. `skill.md` is the zz-review skill as on the base, or HEAD's when the base has no `## Final mode` heading (the raft that adds the mode reviews itself; the README says `skill.md comes from the branch`). The base copy of the issue document is found by id in any folder of the base (the legacy-start path moves it), and diffed against HEAD's. `README.md` names the comparisons, the files, the `Off course:` tag, lists the other members whose Touched modules overlap this issue's with the shared paths (their hunks in the patch may be theirs: flag, do not fail), says when the member is emergent, and names no repository path. The view also holds `unclaimed.patch`: the branch's changes (outside the raft's and the issues' folders) that no member's base Touched modules claim, with their paths listed in the README as "no design calls for these" (a change outside every Touched list is seen by one final review as flagged, never silently). A member present only on the branch (an emergent issue) is built when its HEAD document says `emergent: true`: `design.md` from HEAD, `design-changes.patch` empty, and the README says the whole design was written during execution; a non-emergent member absent from the base refuses. It refuses to build (`empty implementation diff`) when the diff is empty.
- **R2 Ask**: `ask.md` is `./zn capture <id>` (the document as captured, with its marker line) followed by the base document's `Scope decision (user, ...)` and `Decided with the user (...)` lines. A capture marker (`no capture commit: first add`, ...) makes the ask weaker evidence and the README says so. An emergent member's ask is its own Problem (filed by the executor) and the README says that too.
- **R3 Diff**: `implementation.patch` is `git diff <base>...HEAD -U10 -- <pathspecs>`; `finalreview.pathspecs(touched, excludes)` returns the Touched modules (read from the issue's **base** document, so a branch that drops a Touched line does not drop the file) (or `.` when it names none) followed by `:(exclude)<path>` for the raft's folder and the issue's folder only (not every tracker folder: a Touched `architecture.md` or another project's tracker file stays in). `<base>`: `--base`, else `origin/main`, else the local `main`. A Touched path that matches no change is not an error but an empty whole diff is. A patch bigger than the reviewer's `max_tokens` fails the step as any step does (the human then splits the work).
- **R4 Command**: `./zn final-view <issue> --out <folder> [--base <ref>]` writes the view into a folder that does not exist or is empty, refuses a folder that holds files, an unknown issue, a design missing on the base and an empty diff, and writes nothing in those cases. It reads the repository and writes only that folder; it may run in a raft worktree or a clone, never in the main checkout's tracked tree. The exhaustive lists it joins: the usage text in `main.luau`, zz-rules' command list and the dispatcher's `--mode` usage; the executor finds the rest with `grep -rn 'promote-check'` and updates each.
- **R5 Mode**: `dispatch.REVIEW_MODES.final = { lessons = "none", phase = "code-review" }` and `dispatch.modelSkillOf("zz-review", mode)` returns `zz-review` for every mode. Its prompt names the view folder as the working directory and `skill.md` in it (never a repository path), `final-review-<issue>-NNN.md` as where the dispatcher places `review.md`, has no `./zn lessons` line, and replaces "Never edit the main checkout" with "write only `<state>/review.md`; edit nothing else, the main checkout included" (pinned by mode.spec). The dispatcher builds each run's view in a fresh folder, `<state dir>/view-<n>` claimed atomically with a plain `mkdir` (a retry or the next round never meets a busy folder), running `./zn final-view` in the raft's worktree, and starts the CLI with that folder as its working directory, and lands the review in the raft's folder (`dispatch.landing`, pure, for all four modes). It prints the `record:` line a code review prints, with `-m "<issue>: final-review-NNN"` and `--issue <issue>`.
- **R6 Gate**: `finalreview.problem{raft, created, grouped, issues, reviews}` returns nil when the raft is exempt (`exempt(created, grouped)`: no `grouped:` record, or created before `2026-11-08`; an unreadable `created` is not an exemption) or when each member's newest `final-review-<id>-NNN.md` (by number) has `Verdict: approve` and no `[high]` or `[medium]` finding (the skill forbids approving with either). Members are the base raft document's `issues:` united with the branch's members, so an emergent member counts and a member dropped on the branch still counts. Otherwise it returns a text: the member with no review (and `./zn dispatch zz-review <id> --mode final`), a newest review with no `Verdict:` line, or a review with a medium finding in an approve (`approve with a medium finding: not a valid approve`), or a review that did not approve: `final-review-<id>-NNN.md did not approve: BLOCKED for the user; a new round after the intervention clears it`. Files that are not `final-review-<member>-NNN.md` are ignored; `final-refute-*` files mean nothing to the gate. There is no round count. `cmd.done` calls it after `reviewProblem`, before `runCheck`. `grouped:` and `created:` come from the raft document **on the base** (found by id in any folder; `--base` rule of R3), so a branch that edits its own raft document does not change them; where the base has no such document the raft is not exempt.
- **R7 BLOCKED**: a final review whose verdict is not `approve`, or that has a `[high]` finding, sets the item BLOCKED. It records: the review file (committed with `./zn commit --phase code-review`, so the findings and the `Off course:` tags are in the PR), the executor's `BLOCKED:` PR comment listing each finding, and a harvest of the round. The PR stays in draft, nothing is merged, and `done` refuses (R6). A human clears it by intervening (a fix, a design or scope decision, a change to the raft) and starting a new round; only a newer approving round clears it. Code a human changes in answer is seen by that next final round's diff. The user's decision ("needs human intervention") puts the human, not a further automated round, between a failed final review and main; whether a human fix also wants a code-review round is the human's call and the skill says so.
- **R8 One reader**: the verdict and finding-heading reader (`finalreview.verdict(text)`, the lowercase word after `Verdict:` at a line start, nil for none or for two such lines; `findings(text)`, `### F<n> [severity]`), the stem test and the file-name test live in `finalreview`, a leaf module that requires nothing from the engine. `main.reviewProblem` (code review) uses its verdict reader, `lessons.isStem`, `trail.isDoc`, `dispatch.landing` and `finalreview.problem` use its names. New edges: `main`, `lessons`, `trail`, `dispatch` -> `finalreview` (none back).
- **R9 Skills**: zz-execute Phase 4 steps 4 and 7 end "go to Phase 4B" where they said Phase 5; zz-review gains `## Final mode (from zz-execute Phase 4B)` (preamble inputs, the Lessons section and every `./zn` command do not apply in the view; read only the view; judge only hunks the design calls for and flag, not fail, the rest) and a sentence in Who reviews (`--mode final` runs Final mode, from zz-execute Phase 4B) placed after, not inside, the sentence c0117 pins; zz-execute Phase 2 step 5 gains "a design deviation is recorded under `### Deviations` in the Design, which the reviewer sees in `design-changes.patch`"; zz-execute gains `## Phase 4B: Final review, one per ticket, limited view` between Phase 4 and Phase 5; zz-rules' Dispatch lists the `final` mode and Merging says `./zn done` also needs the final reviews; the prompt template's goal state lists them.

### Data flow
`zz-execute Phase 4B` (executor, raft worktree, after Phase 4 resolved) -> for each member: `./zn dispatch zz-review <issue> --mode final` -> dispatcher: `./zn final-view <issue> --out <state>/view` -> CLI (cwd = view) -> `<state>/review.md` -> `final-review-<issue>-NNN.md` in the raft folder, `record:` line printed -> executor commits it, reads the verdict: `approve` -> next member; otherwise BLOCKED (R7) -> `./zn done` -> `finalreview.problem`. Interactive path: `./zn final-view <issue> --out <folder>`, a fresh `model: "opus"` subagent with that folder, the executor writes the returned text as `final-review-<issue>-NNN.md`. Run Phase 4B on c0262's own raft too when it is grouped and created on or after the cutoff.

### Pure vs adapter
`z-nile/engine/finalreview.luau` is a pure leaf (texts in, texts out). `main.luau` reads files and git (the edge); `dispatch.luau` stays pure; `dispatcher.luau` runs processes. z-nile has no architecture map.

### Guards
- Fail closed: an unreadable `created`, a review without a `Verdict:`, a missing member, a design missing on the base and an empty diff all refuse. The view command never writes outside `--out`.
- The limited view is not a security boundary: the reviewer runs as the user and can read the checkout above the state folder (which is under the main checkout's `.cache`). The folder, the prompt and the skill limit what it is told. Known limit, said in zz-rules beside the other guards.
- Specs: AC7 and AC8 run in fixtures under the home's `.cache` with their own repositories; no spec changes the real repository, git config or refs.
- An author who hand-writes an `approve` defeats the gate exactly as with `review-NNN.md` today; the code reviewer and the PR record are the catch.

### Scalability
A raft of n issues costs n final reviews, each on a diff limited to one issue's modules and a ~10 KB design, so cost grows with the sum of the issues' diffs, never with the whole PR n times. Context is `-U10`; the reviewer's `max_tokens` in `.models.toml` is the cap. `finalreview.problem` reads only the file names and texts it is handed. One review at a time per item (the dispatcher's lock).
### Maintainability
One leaf module owns the view, the reader of a review, the names and the gate; each skill rule has one text, pinned by AC6. The cutoff day is a named constant (`finalreview.FROM`). c0136's moves of stream files and `Erred:`/`Upstream:` finding lines are not adopted here (see Existing work).
### Usability
The executor never builds a view by hand: `./zn dispatch zz-review <issue> --mode final`, or `./zn final-view`. `./zn done` names the member and the file and says what to run. A failed review tells the human exactly what clears it (a new round).
