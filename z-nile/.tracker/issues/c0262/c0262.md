# c0262: Full force final review

## Problem
A final limited-view review per ticket checks the ask against the design and the design against the implementation, and sends it back when off course

Decided with the user (2026-11-07): "Full force = (a): the final review runs on the strongest model (Opus now, c0261's `sharp` tier later); it is not a no-waiver hard gate."
Decided with the user (2026-11-07): "a failed merge review goes back to blocked and needs human intervention": a final review that does not approve sets the item BLOCKED for the user; there is no send-back-to-executor loop and no round cap.

## Non-goals
- No change to the code review (zz-execute Phase 4), the stream reviews or the design review: the final review comes after the code review and judges something else (the ask against the design, the design against the implementation), from a smaller view.
- No new spend phase and no new `.models.toml` table: the final review resolves through `zz-review`'s table today, which is the strongest each CLI has (AC5). c0261 will name a `sharp` tier; the mode carries `tier = "sharp"` so it can read it.
- Not the verbatim ask's capture (c0260 keeps it in the ticket): this issue reads whatever `./zn capture` returns, so c0260's section is in `ask.md` once it exists.
- No change to the game, to a project's `src/`, or to any promoted spec. Not a no-waiver gate (the user's decision): rafts in flight and rafts z-raft did not make are exempt.
- No automatic send-back loop, no round cap, no automatic re-prep (the user's decision): a failed final review stops for a human.

## Solution
A new `zz-review` mode, `final`, run once per ticket (issue) of a raft after the code review is resolved and before `./zn done`. It gives a fresh reviewer on the strongest model (the `sharp` tier: Opus now) a limited view built by `./zn final-view`: the ask as captured, the issue's design as it stood on the base (plus the branch's edits to it, as a patch to check), its `check.sh` and acceptance specs, the zz-review skill, and the implementation diff for its Touched modules. It holds no execution record (no Verification log, review, refute, harvest, spend or prompt file). The reviewer compares the ask with the design, and the design with the implementation, and writes `Verdict: approve` or `Verdict: changes`, each finding tagged `Off course:` (`implementation`, `design` or `ask`). `./zn done` refuses a raft until every ticket's newest final review approves. A final review that does not approve sets the item BLOCKED: the executor posts the findings, stops with the PR in draft, and a human intervenes; a new final round that approves clears it.

## Design
Quoted decisions relied on: none from `game-design.md` (tooling only). The user's decisions of 2026-11-07 are in the Problem. Standing rules: "the review model belongs to the CLI" (Opus through `claude`/`agent`, grok at `xhigh`), "Never narrow captured scope", "Keep same user, accept detection" (the limited view is a convenience layer, not a security boundary).

### Product choices (prep), for the user to veto
The user answered "Full force" and "what a failed review does". These remain **(prep)**, not user decisions; the cost of changing each is named:
1. **(prep)** "Per ticket" is per issue, not per raft: a raft of three issues gets three final reviews, each on its own Touched modules. Alternative: one per raft (cheaper; the ask is then three asks and the diff is everything). Cost: the view and the gate key on the raft.
2. **(prep)** "Limited view" is the folder in R1 (ask, design, the design's branch edits, check, acceptance specs, skill, diff; no reviews, refutes, harvest, Verification log, spend or prompt). Alternative: also hand over the code review's verdict (more context, less independence).
3. **(prep)** The exemption: the requirement applies to rafts z-raft made (a `grouped:` record on the base) and created on or after 2026-11-08, so rafts in flight and fixture rafts are not stopped. (The user said it is not a no-waiver gate; the exact exemption is mine.)
4. **(prep)** The model is the `zz-review` table today (strongest each CLI has) and c0261's `sharp` tier later.
5. **(prep)** How a human clears a BLOCKED final review: a new round (`./zn dispatch zz-review <issue> --mode final`) after their intervention, which must approve. There is no waiver command; a human who disagrees with the reviewer fixes the cause or reruns the round. Alternative: a `Decided with the user` line that waives a round. Cost: a rule for who may write it and a gate that reads it.

### Rules
- **R1 View**: `finalreview.view{id, ask, doc, designChanges, check, diff, skill, acceptance?, others?, emergent?}` returns `README.md`, `ask.md`, `design.md`, `design-changes.patch`, `check.sh`, `implementation.patch`, `skill.md` and, for each acceptance spec, `acceptance/<name>`. `design.md` is the issue document **as it is on the base** without its `status:` and `raft:` frontmatter lines and without the `## Verification log` section to the end of the file. `design-changes.patch` is the branch's diff of that document against the base: every edit the executor made to the design, including any `Scope decision` or `Decided with the user` line it added, which `README.md` calls claims to check, not decisions. `skill.md` is the zz-review skill as on the base. `README.md` names the comparisons, the files, the `Off course:` tag, lists the other members whose Touched modules overlap this issue's with the shared paths (their hunks in the patch may be theirs: flag, do not fail), says when the member is emergent, and names no repository path. It refuses to build (`empty implementation diff`) when the diff is empty.
- **R2 Ask**: `ask.md` is `./zn capture <id>` (the document as captured, with its marker line) followed by the base document's `Scope decision (user, ...)` and `Decided with the user (...)` lines. A capture marker (`no capture commit: first add`, ...) makes the ask weaker evidence and the README says so. An emergent member's ask is its own Problem (filed by the executor) and the README says that too.
- **R3 Diff**: `implementation.patch` is `git diff <base>...HEAD -U10 -- <pathspecs>`; `finalreview.pathspecs(touched, excludes)` returns the Touched modules (or `.` when it names none) followed by `:(exclude)<path>` for the raft's folder and the issue's folder only (not every tracker folder: a Touched `architecture.md` or another project's tracker file stays in). `<base>`: `--base`, else `origin/main`, else the local `main`. A Touched path that matches no change is not an error but an empty whole diff is. A patch bigger than the reviewer's `max_tokens` fails the step as any step does (the human then splits the work).
- **R4 Command**: `./zn final-view <issue> --out <folder> [--base <ref>]` writes the view into a folder that does not exist or is empty, refuses a folder that holds files, an unknown issue, a design missing on the base and an empty diff, and writes nothing in those cases. It reads the repository and writes only that folder.
- **R5 Mode**: `dispatch.REVIEW_MODES.final = { lessons = "none", phase = "code-review", tier = "sharp" }`. Its prompt names the view folder as the working directory and `skill.md` in it (never a repository path), `final-review-<issue>-NNN.md` as where the dispatcher places `review.md`, and has no `./zn lessons` line. The dispatcher builds the view into `<state dir>/view` (running `./zn final-view` in the raft's worktree), starts the CLI with that folder as its working directory, and lands the review in the raft's folder (`dispatch.landing`, pure, for all four modes). It prints the `record:` line a code review prints, with `-m "<issue>: final-review-NNN"` and `--issue <issue>`.
- **R6 Gate**: `finalreview.problem{raft, created, grouped, issues, reviews}` returns nil when the raft is exempt (`exempt(created, grouped)`: no `grouped:` record, or created before `2026-11-08`; an unreadable `created` is not an exemption) or when each member's newest `final-review-<id>-NNN.md` (by number) has `Verdict: approve` and no `[high]` finding. Otherwise it returns a text: the member with no review (and `./zn dispatch zz-review <id> --mode final`), a newest review with no `Verdict:` line, or a review that did not approve: `final-review-<id>-NNN.md did not approve: BLOCKED for the user; a new round after the intervention clears it`. Files that are not `final-review-<member>-NNN.md` are ignored; `final-refute-*` files mean nothing to the gate. There is no round count. `cmd.done` calls it after `reviewProblem`, before `runCheck`. `grouped:` and `created:` come from the raft document **on the base** (found by id in any folder; `--base` rule of R3), so a branch that edits its own raft document does not change them; where the base has no such document the raft is not exempt.
- **R7 BLOCKED**: a final review whose verdict is not `approve`, or that has a `[high]` finding, sets the item BLOCKED. It records: the review file (committed with `./zn commit --phase code-review`, so the findings and the `Off course:` tags are in the PR), the executor's `BLOCKED:` PR comment listing each finding, and a harvest of the round. The PR stays in draft, nothing is merged, and `done` refuses (R6). A human clears it by intervening (a fix, a design or scope decision, a change to the raft) and starting a new round; only a newer approving round clears it. Code a human changes in answer is seen by that next final round's diff; the human's decision is the review of it (the user's decision: human intervention).
- **R8 One reader**: the verdict and finding-heading reader (`finalreview.verdict(text)`, lowercase word after `Verdict:`; `findings(text)`, `### F<n> [severity]`), the stem test and the file-name test live in `finalreview`, a leaf module that requires nothing from the engine. `main.reviewProblem` (code review) uses its verdict reader, `lessons.isStem`, `trail.isDoc`, `dispatch.landing` and `finalreview.problem` use its names. New edges: `main`, `lessons`, `trail`, `dispatch` -> `finalreview` (none back).
- **R9 Skills**: zz-execute Phase 4 steps 4 and 7 end "go to Phase 4B" where they said Phase 5; zz-review gains `## Final mode (from zz-execute Phase 4B)` (preamble inputs, the Lessons section and every `./zn` command do not apply in the view; read only the view; judge only hunks the design calls for and flag, not fail, the rest) and a sentence in Who reviews (`--mode final` runs Final mode, from zz-execute Phase 4B) placed after, not inside, the sentence c0117 pins; zz-execute gains `## Phase 4B: Final review, one per ticket, limited view` between Phase 4 and Phase 5; zz-rules' Dispatch lists the `final` mode and Merging says `./zn done` also needs the final reviews; the prompt template's goal state lists them.

### Data flow
`zz-execute Phase 4B` (executor, raft worktree, after Phase 4 resolved) -> for each member: `./zn dispatch zz-review <issue> --mode final` -> dispatcher: `./zn final-view <issue> --out <state>/view` -> CLI (cwd = view) -> `<state>/review.md` -> `final-review-<issue>-NNN.md` in the raft folder, `record:` line printed -> executor commits it, reads the verdict: `approve` -> next member; otherwise BLOCKED (R7) -> `./zn done` -> `finalreview.problem`. Interactive path: `./zn final-view <issue> --out <folder>`, a fresh `model: "opus"` subagent with that folder, the executor writes the returned text as `final-review-<issue>-NNN.md`. Run Phase 4B on c0262's own raft too when it is grouped and created on or after the cutoff.

### Pure vs adapter
`z-nile/engine/finalreview.luau` is a pure leaf (texts in, texts out). `main.luau` reads files and git (the edge); `dispatch.luau` stays pure; `dispatcher.luau` runs processes. z-nile has no architecture map.

### Guards
- Fail closed: an unreadable `created`, a review without a `Verdict:`, a missing member, a design missing on the base and an empty diff all refuse. The view command never writes outside `--out`.
- The limited view is not a security boundary: the reviewer runs as the user and can read the checkout above the state folder (which is under the main checkout's `.cache`). The folder, the prompt and the skill limit what it is told. Known limit, said in zz-rules beside the other guards.
- Specs: AC7 and AC8 run in fixtures under the home's `.cache` with their own repositories; no spec changes the real repository, git config or refs.
- An author who hand-writes an `approve` defeats the gate exactly as with `review-NNN.md` today; the code reviewer and the PR record are the catch.

### Scalability
A raft of n issues costs n final reviews, each on a diff limited to one issue's modules and a ~10 KB design, so cost grows with the sum of the issues' diffs, never with the whole PR n times. Context is `-U10`; the reviewer's `max_tokens` in `.models.toml` is the cap. `finalreview.problem` reads only the file names and texts it is handed. One review at a time per item (the dispatcher's lock).
### Maintainability
One leaf module owns the view, the reader of a review, the names and the gate; each skill rule has one text, pinned by AC6. The cutoff day is a named constant (`finalreview.FROM`). c0136's moves of stream files and `Erred:`/`Upstream:` finding lines are not adopted here (see Existing work).
### Usability
The executor never builds a view by hand: `./zn dispatch zz-review <issue> --mode final`, or `./zn final-view`. `./zn done` names the member and the file and says what to run. A failed review tells the human exactly what clears it (a new round).
