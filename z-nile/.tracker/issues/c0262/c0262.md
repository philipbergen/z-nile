# c0262: Full force final review

## Problem
A final limited-view review per ticket checks the ask against the design and the design against the implementation, and sends it back when off course

## Non-goals
- No change to the code review (zz-execute Phase 4), the stream reviews or the design review: the final review comes after the code review and judges something else (the ask against the design, the design against the implementation), from a smaller view.
- No new spend phase and no new `.models.toml` table: the final review runs through `zz-review`'s table today. c0261 (the `sharp` tier) will name the model it reads; until it lands `zz-review`'s Opus entry (rank 4) is the sharp model.
- Not the verbatim ask's capture (c0260 keeps it in the ticket); this issue reads whatever `./zn capture` returns and reads c0260's section too once it exists.
- No change to the game, to a project's `src/`, or to any promoted spec.

## Solution
A new `zz-review` mode, `final`, run once per ticket (issue) of a raft after the code review is resolved and before `./zn done`. It gives a fresh Opus reviewer a limited view built by `./zn final-view`, a folder holding only the ask as captured, the issue's design, its `check.sh` and acceptance specs, and the implementation diff for the issue's Touched modules: no execution record (Verification log, review, refute, harvest, spend and prompt files). The reviewer compares the ask with the design, and the design with the implementation, and writes `Verdict: approve` or `Verdict: changes` with each finding tagged `Off course:` (implementation, design or ask). `./zn done` refuses a raft until every ticket's newest final review approves, so a ticket that is off course is sent back: the executor fixes the implementation and a new reviewer rules again (at most 3 rounds), and a design that is off the ask is a stop condition (BLOCKED, the user decides).

## Design
Quoted decisions relied on: none from `game-design.md` (tooling only). The user's standing rules this design follows: "the review model belongs to the CLI" (`.models.toml`: Opus through `claude`/`agent`, grok at `xhigh`), "Never narrow captured scope", "Keep same user, accept detection" (the limited view is a convenience layer, not a security boundary; see Guards).

### How each captured outcome is met (scope fidelity)
| Captured words | Design |
|---|---|
| "A final ... review per ticket" | one review per member issue of the raft, `final-review-<issue>-NNN.md` in the raft's folder, required for every member by `./zn done` (AC2) |
| "limited-view" | `finalreview.view` builds a folder with only five kinds of file (AC1); the dispatched reviewer's working directory is that folder (AC3) |
| "checks the ask against the design" | `ask.md` (the capture) and `design.md`; the mode's rules in zz-review (AC5) |
| "and the design against the implementation" | `design.md`, `check.sh`, `acceptance/` and `implementation.patch` (AC1, AC5) |
| "sends it back when off course" | `Verdict: changes` blocks `done` (AC2); zz-execute Phase 4B says what the executor does with it (AC5) |

### Product choices (prep), for the user to veto
The Problem leaves these open. Each is read from its own words and the pipeline's existing rules, marked **(prep)**, and is not a user decision. Nothing in `game-design.md` touches it (it is the game's file). If the user overrules one, the cost is named:
1. **(prep)** "Per ticket" is per issue, not per raft: a raft of three issues gets three final reviews, each on its own Touched modules. Alternative, one per raft: cheaper, but the "ask" is then three asks and a diff of everything. Cost of changing: the view and the gate key on the raft.
2. **(prep)** "Limited view" is the folder in AC1 (ask, design, check, acceptance specs, diff; no reviews, refutes, harvest, Verification log, spend or prompt). It is limited by construction and instruction, not by a sandbox. Alternative: also hand over the code review's final verdict (more context, less independence). Cost: the view builder gains a file.
3. **(prep)** "Sends it back" is: `done` refuses a ticket whose newest final review is `changes`; implementation findings go back to the executor for a fix and a new clean reviewer; a finding that the design is off the ask is the existing stop condition "design is wrong beyond local adjustments" (BLOCKED, the user decides, since the sequestered design and checks cannot be edited by the executor). Alternative: send a design-off-ask ticket back to z-design automatically (`./zn stop`, re-prep): faster for a wrong design, but it throws away the raft's other tickets and needs the user's scope rules anyway. Cap of 3 rounds then BLOCKED (the code review's cap is 5, prefer 3; a smaller cap fits a smaller review).
4. **(prep)** The review model is the CLI's review model (Opus today), and c0261's `sharp` tier once that lands. Alternative: a different model for finals; cost: a second review table.
5. **(prep)** The requirement applies from 2026-11-08 to rafts z-raft made (`grouped:` present), so rafts already in flight and fixture rafts are not stopped. Alternative: apply to every raft and edit about 15 promoted `done` fixtures; cost: a large override list.

### Rules
- **R1 View**: `finalreview.view{id, ask, doc, check, diff, acceptance?}` returns the file map `README.md`, `ask.md`, `design.md`, `check.sh`, `implementation.patch` and, for each acceptance spec, `acceptance/<name>`. `design.md` is the issue document without the `status:` and `raft:` frontmatter lines and without the `## Verification log` section to the end of the file. `README.md` names the three comparisons and the `Off course:` tag.
- **R2 Ask**: `ask.md` is `./zn capture <id>` (the document as captured, with its marker line) followed by the current document's `Scope decision (user, ...)` and `Decided with the user (...)` lines (z-design's definition of scope). When c0260 puts the verbatim ask in the captured document it is in the capture, so nothing here changes.
- **R3 Diff**: `implementation.patch` is `git diff <base>...HEAD -U25 -- <pathspecs>` where the pathspecs are the issue's Touched modules (`finalreview.pathspecs`), or `.` when it names none (then the reviewer sees the whole branch), always followed by `:(exclude,glob)**/.tracker/**`. `<base>` defaults to `origin/main`; `--base` overrides it.
- **R4 Command**: `./zn final-view <issue> --out <folder> [--base <ref>]` writes the view into a folder that does not exist or is empty, and refuses a folder that holds files and an unknown issue. It reads the repository and writes only that folder.
- **R5 Mode**: `dispatch.REVIEW_MODES.final = { lessons = "none", phase = "code-review" }`. Its prompt names the skill's file, the view folder as the working directory, `final-review-<issue>-NNN.md` as where the dispatcher places `review.md`, and has no `./zn lessons` line. The dispatcher builds the view into `<state dir>/view` (by running `./zn final-view` in the raft's worktree), starts the CLI with that folder as its working directory, and lands the review in the raft's folder (`dispatch.landing`, pure). It prints the same `record:` line a code review prints, with the note `final-review-<issue>-NNN`.
- **R6 Gate**: `finalreview.problem{raft, created, grouped, issues, reviews}` returns nil when the raft is exempt (`exempt(created, grouped)`: no `grouped:` record, or created before `2026-11-08`; an unreadable `created` is not an exemption) or when each member's newest `final-review-<id>-NNN.md` has `Verdict: approve` and no `[high]` finding; else a text naming the member, `sent back` when a review exists, and for round 3 `BLOCKED`. Files that are not `final-review-<member>-NNN.md` are ignored. `cmd.done` calls it after `reviewProblem` and before `runCheck`.
- **R7 Rounds**: `finalreview.MAX_ROUNDS = 3`. Round 1 or 2 with `changes`: the message says to fix, answer in `final-refute-<issue>-NNN.md` and start round N+1. Round 3 with `changes`: it says BLOCKED, escalate. The author's `fixed`/`refuted` answers never clear a ticket; only a newer approving review does (a reviewer rules on every refutation).
- **R8 Harvest**: the stems `final-review-<issue>-NNN` are review stems for `lessons.luau` (so `./zn lessons --uncovered <R-id>` lists their findings and the raft's `harvest.md` answers them), and `final-review-*`/`final-refute-*` are not item documents for `trail.isDoc`.
- **R9 Skills**: zz-execute Phase 4 steps 4 and 7 end "go to Phase 4B" where they said Phase 5 (the approving round, a round with no findings, and the final round with only medium or low findings all reach it); zz-review gains `## Final mode (from zz-execute Phase 4B)`; zz-execute gains `## Phase 4B: Final review, one per ticket, limited view` between Phase 4 and Phase 5; zz-rules' Dispatch lists the `final` mode and Merging says `./zn done` also needs the final reviews; the prompt template's goal state lists them. The sentences other promoted specs pin (the headless section, Phase 4's harvest and re-review steps, Phase 5, Phase 2B, the Dispatch steps line) are not edited; `grep -rn 'to Phase 5'` over `tests/` finds no spec pinning the two edited sentences.

### Data flow
`zz-execute Phase 4B` (executor, in the raft worktree, after Phase 4 resolved) -> for each member: `./zn dispatch zz-review <issue> --mode final` -> dispatcher: `./zn final-view <issue> --out <state>/view` -> CLI (cwd = view) -> `<state>/review.md` -> `final-review-<issue>-NNN.md` in the raft folder, `record:` line printed -> executor commits it (`./zn commit ... --phase code-review`), reads the verdict, fixes or escalates, harvests the round -> `./zn done` -> `finalreview.problem`. Interactive path: `./zn final-view <issue> --out <folder>`, a fresh `model: "opus"` subagent with that folder, the executor writes the returned text as `final-review-<issue>-NNN.md`.

### Pure vs adapter
`z-nile/engine/finalreview.luau` is pure (texts in, texts out; zz-arch: pure modules over texts, reads at the edge). `main.luau` reads the files and git (the edge) and calls it; `dispatch.luau` stays pure (mode table, prompt, `landing`); `dispatcher.luau` runs processes. No new dependency edge between engine modules beyond `main -> finalreview` and `dispatcher -> (zn final-view)`; z-nile has no architecture map to update.

### Guards
- Fail closed: an unreadable `created`, a review without a parseable `Verdict:` and a missing member all refuse `done`. The view command never writes outside `--out`.
- The limited view is not a security boundary: the reviewer runs as the user and can read the checkout above its working directory. The folder, the prompt and the skill limit what it is told; zz-review's Final mode tells it to read nothing else. Known limit, said in zz-rules next to the other guards.
- Specs: AC6 reads the real repository and writes one new folder under the home's `.cache` (the jail allows exactly that); no spec or check changes the repository, git config or refs. The reviewer must confirm that (Repository safety).
- A final review file is the dispatcher's placement; an author who writes an `approve` by hand defeats it exactly as with `review-NNN.md` today (the code reviewer and the PR record are the catch).

### Scalability
A raft of n issues costs n final reviews of rounds 1..3, each on a diff limited to one issue's modules plus a ~10 KB design, so cost grows with the sum of the issues' diffs, never with the whole PR n times; the view is capped by `-U25` context and the reviewer's `max_tokens` in `.models.toml`. `finalreview.problem` reads only the raft folder's file names it was handed. One review at a time per item (the dispatcher's per-item lock), issues in the raft's order.
### Maintainability
One pure module owns the view, the rule and the cap; one text owns each skill rule; the stems live in one place per consumer (lessons, trail). A fourth place that must know the file name pattern is a smell: `finalreview.STEM` is exported and the two consumers use it (executor note: `lessons.luau` and `trail.isDoc` call it rather than repeat the pattern). The cutoff day and the round cap are named constants.
### Usability
The executor never builds a view by hand: `./zn dispatch zz-review <issue> --mode final`, or `./zn final-view` for the interactive path. `./zn done` names the member and says what to run (`./zn dispatch zz-review <issue> --mode final`) and, for a sent-back ticket, the round to start. A raft readied before this lands is untouched (exemption), and its prompt, written earlier, does not mention Phase 4B.
