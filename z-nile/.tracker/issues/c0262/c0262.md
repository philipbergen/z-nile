# c0262: Full force final review

## Problem
User (2026-11-07): "We are missing a final full force review where we take the original ask and the design and the implementation and final adversarial check that the design covers the idea and tha tthe implementation delivers the design."

User (2026-11-07): "The final full fiorce revieq should be fed a limited view of the tickets so that it looks at it only on its merits as given and not with the broader context of all the compromise on the way. It should be clear if we stayed on course and there should be a redo if not"

Code review checks the code against the Design, and design review checks the design against the capture, but no review takes the original ask, the design and the implementation together. Every reviewer also sees the whole trail of reviews, refutes and decisions, so a drift agreed to round by round is never seen as a drift. What should happen:
- **Once per ticket, before its layer merges** (c0248), a full-force adversarial review checks that the design covers the idea and that the implementation delivers the design. It runs on the sharp model (c0261) in a fresh context.
- **Limited view:** the reviewer is given only the original ask (verbatim ask, interview and confirmed idea, c0260, or the capture for older tickets), the design and the implementation as given. It sees none of the compromise on the way: no design reviews, refutes, harvests, PR comments or worker notes. It judges the result on its merits.
- **A clear verdict** says whether we stayed on course, with each gap named against the ask or the design.
- **A redo when off course:** the ticket goes back to z-design when the design missed the idea, or its layer is rebuilt when the implementation missed the design. Then the review runs again. A second off-course verdict blocks the ticket (c0250) for the human.

Decided with the user (2026-11-07): "per issue yes, which is layer in the pr": the final review is per issue, a layer within the raft's PR.
Decided with the user (2026-11-07): the view's contents: "ok" (the ask, the design, the design's branch edits, the check, the acceptance specs, the skill and the implementation diff).
Decided with the user (2026-11-07): "we're sticking with model names as they are not aliases, you carried the idea too far": the final review names concrete models by the existing review rule (`models.reviewRule`: Opus for claude and agent, a grok model at xhigh), with no alias; c0261 assigns the final-review activity's real model per CLI later.
Decided with the user (2026-11-07): "Full force = (a)": the final review runs on the strongest model, and it is not a no-waiver hard gate: the exemption of rafts in flight and rafts z-raft did not make is kept.
Decided with the user (2026-11-08): "Design c0262 after c0248 and c0260 are prepared": c0262 is held, and its design resumes once both are prepared.

Reconciled with the capture above, which is the newest word: a first off-course verdict is a redo and a second off-course verdict blocks the ticket for the human (see Design, Reconciliation).

- Choosing the sharp model (c0261).
- No new spend phase and no new `.models.toml` table or alias; c0261 will assign the final-review activity's real model per CLI (no tier names), and until then the review rule's concrete names apply.
- No change to the game, to a project's `src/`, or to any promoted spec.
- The stacked layers (c0248), the blocked status (c0250) and the interview sections (c0260) are those issues' to build; this design reads them through named seams (Design, Seams) and works with today's one-PR raft.

## Solution
- `zz-review --mode final`, with a brief built by `./zn` from a fixed list of files, so the limited view is enforced and not left to the reviewer's restraint.
- Verdict `on-course` or `off-course`, written to `final-review-NNN.md` in the ticket folder.

### Rules
- **R1 View**: `finalreview.view{id, ask, doc, designChanges, check, diff, skill, unclaimed, acceptance?, others?, emergent?, designSource?}` returns `README.md`, `ask.md`, `design.md`, `design-changes.patch`, `check.sh`, `implementation.patch`, `unclaimed.patch`, `skill.md` and, for each acceptance spec, `acceptance/<name>`. `design.md` is the issue document **as it is on the base**, without its `status:` and `raft:` lines and without the `## Verification log` section to the end of the file. `design-changes.patch` is the diff of that document between the base copy and HEAD's, both stripped the same way (`finalreview.designText`), so the executor's log is in no file; every other edit the executor made to the design, including a `Scope decision` or `Decided with the user` line it added, is there and the README calls it a claim to check, not a decision. `skill.md` is the zz-review skill as on the base, or HEAD's when the base has no `## Final mode` heading (the raft that adds the mode reviews itself; the README says `skill.md comes from the branch`). The base copy of the issue document is found by id in any folder of the base (a legacy start moves it). `unclaimed.patch` holds the branch's changes (outside the raft's and the issues' folders) that no member's base Touched modules claim, their paths listed in the README as "no design calls for these". A member present only on the branch (an emergent issue) is built when its HEAD document says `emergent: true`: `design.md` from HEAD, `design-changes.patch` empty, and the README says the whole design was written during execution; a non-emergent member absent from the base refuses. `README.md` names the comparisons, the files, the `Gap:` tags, lists the other members whose Touched modules overlap with the shared paths (their hunks may be theirs: flag, do not fail), and names no repository path. It refuses to build (`empty implementation diff`) when the diff is empty.
- **R2 Ask**: `ask.md` is `finalreview.askOf(<base document>, <./zn capture output>)` followed by the base document's `Scope decision (user, ...)` and `Decided with the user (...)` lines. A capture marker (`no capture commit: first add`, ...) makes the ask weaker evidence and the README says so. An emergent member's ask is its own Problem, filed by the executor, and the README says that too.
- **R3 Diff**: `implementation.patch` is `git diff <base>...HEAD -U10 -- <pathspecs>`; `finalreview.pathspecs(touched, excludes)` returns the Touched modules (read from the issue's **base** document, so a branch that drops a Touched line does not drop the file; `.` when it names none) followed by `:(exclude)<path>` for the raft's folder and the issue's folder only. `<base>`: `--base`, else `origin/main`, else the local `main`. A patch bigger than the reviewer's `max_tokens` fails the step as any step does.
- **R4 Command**: `./zn final-view <issue> --out <folder> [--base <ref>]` writes the view into a folder that does not exist or is empty; it refuses a folder that holds files, an unknown issue, a design missing on the base (unless emergent), and an empty diff, and writes nothing in those cases. It reads the repository and writes only that folder; it runs in a raft worktree or a clone, never in the main checkout's tracked tree. The exhaustive lists it joins: the usage text in `main.luau`, zz-rules' command list and the dispatcher's `--mode` usage; the executor finds the rest with `grep -rn 'promote-check'` and updates each.
- **R5 Mode**: `dispatch.REVIEW_MODES.final = { lessons = "none", phase = "code-review" }`; `dispatch.modelSkillOf("zz-review", mode)` returns `zz-review` for every mode. Its prompt names the view folder as the working directory and `skill.md` in it (never a repository path), `final-review-NNN.md` as where the dispatcher places `review.md`, has no `./zn lessons` line, and replaces "Never edit the main checkout" with "write only `<state>/review.md`; edit nothing else, the main checkout included" (pinned by mode.spec). The dispatcher builds each run's view in a fresh folder, `<state dir>/view-<n>` claimed atomically with a plain `mkdir`, running `./zn final-view` in the raft's worktree, starts the CLI with that folder as its working directory, and lands the review in **the issue's own folder** as `final-review-NNN.md` (`dispatch.landing`, pure, for all four modes). It prints the `record:` line a code review prints, with `-m "<issue>: final-review-NNN"` and `--issue <issue>`.
- **R6 Gate**: `finalreview.problem{raft, created, grouped, issues, reviews}` (`reviews`: member -> file name -> text) returns nil when the raft is exempt (`exempt(created, grouped)`: no `grouped:` record, or created before `2026-11-08`; an unreadable `created` is not an exemption) or when each member's newest `final-review-NNN.md` (by number) has `Verdict: on-course` and no `[high]` or `[medium]` finding. Otherwise it returns a text naming the member and: no review (and `./zn dispatch zz-review <id> --mode final`); no `Verdict:` line; an on-course with a high or medium finding; **`REDO`** for a newest off-course verdict when it is the ticket's first off-course file, routed by its findings' `Gap:` lines (`design`: back to z-design; `implementation`: rebuild the layer; both: z-design first), saying a new round follows the redo; **`BLOCKED for the human`** when the ticket has two or more off-course files. Members are the base raft document's `issues:` united with the branch's members. Files that are not `final-review-NNN.md` in the member's folder are ignored. `grouped:` and `created:` come from the raft document **on the base** (found by id in any folder); where the base has no such document the raft is not exempt. `cmd.done` calls it after `reviewProblem`, before `runCheck`.
- **R7 Redo and block** (zz-execute Phase 4B). On a first `off-course` verdict the executor commits the file (`./zn commit --phase code-review`) and comments `REDO <issue>: <gaps>` on the PR. `Gap: implementation`: the layer is rebuilt (Phase 2 for that issue again: tests first, implement from the design and ACs with the findings as input; Phase 4 step 6's re-review conditions apply to the rebuild's diff), then a new final round runs. `Gap: design`: the design missed the idea, so the ticket goes back to z-design: the executor stops with the PR in draft, and `./zn stop <R-id>`, `./zn unfold <R-id> <issue>`, a z-design redesign of the issue (its folder, with `final-review-NNN.md` and its harvest, travels with it), z-raft, z-ready and z-run redeliver it; the next final round is numbered on. A second `off-course` verdict is BLOCKED for the human: the executor comments `BLOCKED:` with the findings, leaves the PR in draft and stops (c0250 seam). A human clears it by intervening and running a new round; only a newer on-course round clears it. A final review's findings are harvested like any review's. Code a human changes in answer is seen by the next final round's diff.
- **R8 One reader**: the verdict reader (`finalreview.verdict(text)`: the lowercase `on-course`/`off-course` after `Verdict:` at a line start, nil for none, for another word or for two such lines), the finding-heading reader (`### F<n> [severity]`), the stem test (`final-review-NNN`) and the file-name test live in `finalreview`, a leaf module that requires nothing from the engine. `lessons.isStem`, `trail.isDoc` (which also excludes `final-refute-*`), `dispatch.landing` and `finalreview.problem` use its names. `main.reviewProblem` (the code review) keeps its own `approve` reader. New edges: `main`, `lessons`, `trail`, `dispatch` -> `finalreview` (none back).
- **R9 Skills**: zz-execute Phase 4 steps 4 and 7 end "go to Phase 4B" where they said Phase 5; Phase 2 step 5 gains "a design deviation is recorded under `### Deviations` in the Design, which the reviewer sees in `design-changes.patch`"; zz-execute gains `## Phase 4B: Final review, one per ticket, limited view` between Phase 4 and Phase 5; zz-review gains `## Final mode (from zz-execute Phase 4B)` (the preamble inputs, the Lessons section and every `./zn` command do not apply in the view; read only the view; judge only hunks the design calls for and flag, not fail, the rest; the verdict and `Gap:` template) and a sentence in Who reviews (`--mode final` runs Final mode, from zz-execute Phase 4B) placed after, not inside, the sentence c0117 pins; zz-rules' Dispatch lists the `final` mode and Merging says `./zn done` also needs the final reviews; the prompt template's goal state lists them.

### Data flow
`zz-execute Phase 4B` (executor, raft worktree, after Phase 4 resolved) -> for each member: `./zn dispatch zz-review <issue> --mode final` -> dispatcher: `./zn final-view <issue> --out <state>/view-<n>` -> CLI (cwd = view) -> `<state>/review.md` -> `<issue folder>/final-review-NNN.md`, `record:` line printed -> executor commits it, reads the verdict: `on-course` -> next member; first `off-course` -> REDO (R7); second -> BLOCKED -> `./zn done` -> `finalreview.problem`. Interactive path: `./zn final-view <issue> --out <folder>`, a fresh `model: "opus"` subagent with that folder, the executor writes the returned text as `final-review-NNN.md`. Phase 4B also runs on c0262's own raft when it is grouped and created on or after the cutoff.

### Pure vs adapter
`z-nile/engine/finalreview.luau` is a pure leaf (texts in, texts out). `main.luau` reads files and git (the edge); `dispatch.luau` stays pure; `dispatcher.luau` runs processes. z-nile has no architecture map.

### Guards
- Fail closed: an unreadable `created`, a review without a `Verdict:`, a missing member, a design missing on the base (unless emergent) and an empty diff all refuse. The view command never writes outside `--out`.
- The limited view is not a security boundary: the reviewer runs as the user and can read the checkout above the state folder (under the main checkout's `.cache`). The folder, the prompt and the skill limit what it is told. Known limit, said in zz-rules beside the other guards.
- Specs: AC7 and AC8 run in fixtures under the home's `.cache` with their own repositories; no spec changes the real repository, git config or refs.
- An author who hand-writes an `on-course` file defeats the gate as with `review-NNN.md` today; the PR record is the catch.

### Scalability
A raft of n issues costs n final reviews per round, each on a diff limited to one issue's modules and a ~10 KB design, so cost grows with the sum of the issues' diffs, never with the whole PR n times. Context is `-U10`; the reviewer's `max_tokens` in `.models.toml` is the cap. At most two off-course verdicts per ticket, so a ticket costs at most three rounds before a human. One review at a time per item (the dispatcher's lock).
### Maintainability
One leaf module owns the view, the readers, the names and the gate; each skill rule has one text, pinned by AC6. The cutoff day is a named constant (`finalreview.FROM`).
### Usability
The executor never builds a view by hand: `./zn dispatch zz-review <issue> --mode final`, or `./zn final-view`. `./zn done` names the ticket and the file and says what to do (the command, the REDO route, or that a human must act).
