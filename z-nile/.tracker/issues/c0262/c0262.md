## Problem

Code review checks the code against the Design, and design review checks the design against the capture, but no review takes the original ask, the design and the implementation together. Every reviewer also sees the whole trail of reviews, refutes and decisions, so a drift agreed to round by round is never seen as a drift. What should happen:
- **Once per ticket, before its layer merges** (c0248), a full-force adversarial review checks that the design covers the idea and that the implementation delivers the design. It runs on the sharp model (c0261) in a fresh context.
- **Limited view:** the reviewer is given only the original ask (verbatim ask, interview and confirmed idea, c0260, or the capture for older tickets), the design and the implementation as given. It sees none of the compromise on the way: no design reviews, refutes, harvests, PR comments or worker notes. It judges the result on its merits.
- **A clear verdict** says whether we stayed on course, with each gap named against the ask or the design.
- **A redo when off course:** the ticket goes back to z-design when the design missed the idea, or its layer is rebuilt when the implementation missed the design. Then the review runs again. A second off-course verdict blocks the ticket (c0250) for the human.

### The user's words on the last review
"reviews are back and forth EXCEPT for the last one that just verifies that the diff matches the original ask." The earlier reviews (idea, design, code) stay back and forth with the author (up to a round of answers). The ticket's final review is the one that is not: one question, **does the diff deliver the original ask**. Its view holds the design only so a gap can be named where it arose (`Gap: design`: the design does not cover what the ask needs; `Gap: implementation`: the design covers it but the diff does not deliver the design), which is what the captured redo needs to route. It has no refutation round: the author is not shown to argue with it; a wrong off-course verdict costs one redo, and a second blocks the ticket for the human. The captured wording "design covers the idea, implementation delivers the design" is kept as the two gaps; the verdict is judged on the ask. Whether that is the right reading is the first bullet under Open to the human.

### The two reviews' different jobs (the user's ruling, 2026-11-13)
Quoted in the Problem: "each layer is a small piece toward a complex goal, each layer is judged narrowly to see that we did the best we could in that scope, the final raft review judges the soplution as a whole to ensure that we have delivered an efficient, regression-free and bug free implementation of the raft total objective".
- **The ticket's final review (this ticket)** judges one layer, narrowly, within that ticket's scope: does the diff deliver the original ask.
- **The raft-level final review (#297, kept permanently, nothing built or changed here)** judges the solution as a whole against the raft's total objective: efficient, regression-free and bug-free.
- **A gap, named for capture, not fixed here**: #297's final mode (zz-review "Final mode", step 3 "Judge substance") asks whether each cited design section answers its claim, each cited test proves it, each cited source line implements it, and that nothing extra is in the diff. It does not ask about efficiency, regressions or bugs against the raft's total objective, and `trace.md` has no row for the raft's objective as a whole. The user's job for that review is therefore only partly done by #297: a follow-up issue should extend final mode to ask those three questions of the whole stack.

### Design
Pure rules in one module, reads at the edge, one new command. Written against the first design review (design-review-001); each choice below answers a finding and is named by it in `design-refute-001.md`.

**`z-nile/engine/finalview.luau` (new, pure; zz-arch: texts in, texts out)**
- `finalview.keepPath(path, issue, raft): boolean`: false only for this ticket's own folder, this raft's folder, `spend.d/` anywhere and `.cache/`. Another item's document the ticket delivers (a `Scope decision` landed on an acting item, an emergent issue) and a project's own `game-design.md` or `architecture.md` are deliverables and are kept.
- `finalview.ask(captured, base): string`: the judged text comes from the **base** document (origin/main's copy: the approved prep plus ready's move; never the branch under review). `## Ask (verbatim)`, `## Interview`, `## Idea` and `## Confirmation` as the base has them (c0260's record, read by name; a dispatched capture's later interview answers, idea update and `Confirmed (...)` line are in the base, not in the capture commit); else the capture's Problem, Solution, Non-goals. Plus every line of the base carrying `Scope decision (user, `, `Decided with the user (` or `Confirmed (`, in any section and in a list or bold; plus, for each `Ruled (user, ...)` bullet under `## Open to the human`, only its `Decision:` clause and the ruling (never the finding or the author's Answer, which are trail).
- `finalview.design(base): string`: the base's Design and Acceptance criteria sections; a line that names a design review, a refute, a `review NNN` or a round is dropped (the README says so). New z-design rule: those two sections cite none.
- `finalview.changes(base, tip): string`: lines the layer added (`+`) or removed (`-`) in those two sections and among the decision lines, since the base, headed "claims to check, not the design as given"; nothing of the Verification log or any other section. It is `design-changes.patch` in the view when not empty. A decision line added on the layer is therefore never in `ask.md`.
- `finalview.assemble(input): {[path]: text}`: `ask.md`, `design.md`, `design-changes.patch`, `diff.patch`, `contract/<path>` (the base's `check.sh` and acceptance specs) and `README.md`. `finalview.allowed(path)` is the whole list of what a view may hold.
- `finalview.viewId(files, patchId)`: sha256 of every file but the README and `diff.patch`, plus the **patch id** (`git patch-id --stable`) of the diff. A clean restack, or main moving (a capture rewrites `z-nile/next`), leaves it alone (c0248's rule 3 keys its reviews on patch ids the same way); a redo that changes the design, the contract or the change changes it.
- `finalview.parse(n, text): Review` and `finalview.problem(review): string?`: a review is `### F<n>` findings, each with a one-word `Gap: design` or `Gap: implementation` line and a `Measured against: "<quote>"` line, then `View: <id>` and `Verdict: on-course | off-course`. Fail closed: no readable verdict, no View, an on-course with findings, an off-course with none, a finding with no one-word Gap (the README's template wording is not a Gap) or with no quote, are each a problem.
- `finalview.state(reviews, view): {state, why, latest}`: `none`, `on-course` (the latest review judged this view on-course), `review-again` (it judged another view), `redo-design` (off course on this view with any `Gap: design`), `redo-layer` (implementation gaps only), `blocked` (two off-course reviews, the latest off-course), `invalid`. A review of a view an earlier off-course review already judged is `invalid` ("reviewed again without a redo"). `latest` is the latest verdict, so `review-again` after an off-course verdict (the redo not yet reviewed) is told from one after an on-course verdict (the layer moved).

**`z-nile/engine/finalread.luau` (new, the edge)**: `where(issue)` finds the ticket's layer, its tip (the local branch when ahead of origin's) and its base (the tip of the layer below, or main; after c0248 `layergit.baseFor`, which is origin/main for the lowest unlanded layer); `files(issue, at)` reads the base document, `check.sh` and `acceptance/` from **origin/main's copy of the issue folder** (the tip only for a ticket not on origin/main), the capture (`trail.capture`, as `./zn trace` does), and the diff as `git diff <base>...<tip>` (three dots: from the merge base, so main's own work never shows reversed) limited to `keepPath` files; `reviews(issue, at)` reads `final-review-NNN.md` from **both** origin/main's issue folder and the layer tip, by number; `state(issue)`; `lastNumber(issue)`; `viewDir(issue)` (`$ZN_FINAL_VIEW_ROOT/<id>`, default `$TMPDIR/zn-final/<id>`: never inside a checkout, so no `CLAUDE.md`, `AGENTS.md` or project memory sits above the reviewer); `write(issue, dir)` writes the view whole.

**`z-nile/engine/main.luau`**: `cmd.final` (`./zn final <issue-id> [--view]`): without `--view` prints `<id>: <state> - <why>`; with `--view` writes the view, lists it and prints the brief for an interactive reviewer (start it in that folder; tell it only to read `README.md`). `cmd.done` refuses, before its other review checks, a member whose state is `redo-design`, `redo-layer`, `blocked`, `invalid`, or `review-again` after an off-course verdict (the redo not reviewed again); a member with no final review is **not** refused by this rule (the user's 2026-11-07 "Full force = (a)"). The refusal covers the members being landed: today every member (no `--through`); after c0248, the landing set (`ZN_BIND_MEMBERS`), so a blocked layer above never refuses `done --through` for the on-course layers below it (c0248 Q3). main.luau holds exactly 200 top-level locals: `cmd.final` is a field of `cmd`, and the modules are required inside functions.

**`z-nile/engine/completion.luau` (c0248's, extended here) and the cut-over**: `completion.layer(input)` gains an optional `final: string?`, a `finalview.state` word. With `final` given, the layer is complete only when it is `on-course`; any other word is "not complete" with the reason `the ticket's final review is <word>: ./zn final <issue>`; with `final` nil nothing changes. **c0262 has its own cut-over, as c0248 has `layers: reviewed`**: once c0262 is on main, `./zn ready` writes a second front-matter line `final: ticket` on every raft it readies (the publish rule for moved documents accepts it, as it accepts c0248's line), and `./zn start` (layer N+1) and `./zn done` pass `final` only for a raft carrying it. After a layer is finished, `forRaft` returns: `review` (the layer's code review first, while `reviewReason` is set: the final review is the last review), then `work.finalStep` unless the state is `on-course`: `final-review-ticket` (none, review-again), `rebuild` (redo-layer), `redesign` (redo-design), `blocked` (blocked, invalid). `rebuild`, `redesign` and `blocked` tell the worker to harvest each finding of the ticket's review into the issue's `harvest.md` first (nobody else will; `./zn lessons --uncovered` reads that folder), and, when the layer below is on course, to land the green layers first with `./zn done <R> --through <the issue below>`. ### Scalability
One review per ticket instead of one per raft: N model runs for an N-ticket raft (each on the `final-review` role), each over one layer's diff, so its cost grows with the ticket and not with the stack. The view is built from a handful of `git show`/`git diff` calls; `workread` calls `finalread.state` only for a finished layer, and `finalread.files` (the diff) only when the layer has a review to compare, so a cold `./zn work next` adds no git work for layers without one. A very large diff is the reviewer's context limit, the same as a code review's.

### Maintainability
All rules are in one pure module (`finalview`) with a spec that names each; the edge is one module (`finalread`) and `main.luau` gains one command. The ask sections are one constant. The state names are the strings `work.luau` branches on, listed in one place (`finalview.state`'s comment). The reviewer's README and the zz-review section are the same text twice; docs.spec pins the phrases of the second, view.spec the first. No duplicate of `trace`: the raft-level review reads its own files and a ticket's reads its own.

### Usability
A worker sees one line from `./zn work next` and does it. A person asks `./zn final c0010` and reads one state with a reason (`blocked - 2 off-course verdicts: ...`). An interactive reviewer is given a folder and one README; there is nothing to configure. The refusal at `done` names the ticket, the state and the command to read.
