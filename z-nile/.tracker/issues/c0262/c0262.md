# c0262: Full force final review

## Problem
User (2026-11-07): "We are missing a final full force review where we take the original ask and the design and the implementation and final adversarial check that the design covers the idea and tha tthe implementation delivers the design."

User (2026-11-07): "The final full fiorce revieq should be fed a limited view of the tickets so that it looks at it only on its merits as given and not with the broader context of all the compromise on the way. It should be clear if we stayed on course and there should be a redo if not"

Code review checks the code against the Design, and design review checks the design against the capture, but no review takes the original ask, the design and the implementation together. Every reviewer also sees the whole trail of reviews, refutes and decisions, so a drift agreed to round by round is never seen as a drift. What should happen:
- **Once per ticket, before its layer merges** (c0248), a full-force adversarial review checks that the design covers the idea and that the implementation delivers the design. It runs on the sharp model (c0261) in a fresh context.
- **Limited view:** the reviewer is given only the original ask (verbatim ask, interview and confirmed idea, c0260, or the capture for older tickets), the design and the implementation as given. It sees none of the compromise on the way: no design reviews, refutes, harvests, PR comments or worker notes. It judges the result on its merits.
- **A clear verdict** says whether we stayed on course, with each gap named against the ask or the design.
- **A redo when off course:** the ticket goes back to z-design when the design missed the idea, or its layer is rebuilt when the implementation missed the design. Then the review runs again. A second off-course verdict blocks the ticket (c0250) for the human.

### The user's words on the last review
"reviews are back and forth EXCEPT for the last one that just verifies that the diff matches the original ask." The ticket's final review asks one question, **does the diff deliver the original ask**. Its view holds the design only so a gap can be named where it arose (`Gap: design`: the design does not cover what the ask needs; `Gap: implementation`: the design covers it but the diff does not deliver the design), which the captured redo needs to route ("Judge on the ask (Recommended)", 2026-11-13). It has no refutation round: a wrong off-course verdict costs one redo, and a second blocks the ticket for the human.

### The two reviews' different jobs (the user's ruling, 2026-11-13)
- **The ticket's final review (this ticket)** judges one layer, narrowly, within that ticket's scope: does the diff deliver the original ask.
- **The raft-level final review (#297, kept, nothing changed here)** judges the solution as a whole against the raft's total objective. A gap is named for capture, not fixed here: #297's final mode does not ask about efficiency, regressions or bugs against the raft's total objective; a follow-up issue should extend it.

### `z-nile/engine/finalview.luau` (new, pure; zz-arch: texts in, texts out)
- `finalview.keepPath(path, issue, raft): boolean`: false only for this ticket's own folder, this raft's folder, `spend.d/` anywhere and `.cache/`. Another item's document the ticket delivers and a project's own `game-design.md` or `architecture.md` are deliverables and are kept.
- `finalview.ask(captured: string, base: string, front: { [string]: string }?): string`: the judged text comes from the **base** document (origin/main's copy), read with `capturecheck.section`, never from the branch under review. By kind (**Guess (prep) G6** for the last two):
  - **recorded by c0260** (`front` given, `capturecut.required(front)`, and `capturecheck.kind(base)` not `"none"`): `## Ask (verbatim)` and `## Interview` (an agent-filed ticket, kind `"agent"`: `## Filed by (agent)`), then the confirmed idea, the base's `## Problem`, `## Solution` and `## Non-goals`, each headed "(the confirmed idea)", then `## Confirmation`;
  - **a hand-made record** (kind `"user"`, unmarked): `## Ask (verbatim)`, `## Interview`, `## Idea` and `## Confirmation` as the base has them, and with no `## Idea` the capture's Problem, Solution and Non-goals headed "(as captured)";
  - **an older ticket**: the capture's Problem, Solution and Non-goals, "(as captured)".
  Then, for every kind, the user's later decisions: every line of the base carrying `Scope decision (user, `, `Decided with the user (` or `Confirmed (`, in any section, in a list or bold, outside `## Open to the human`; and for each `Ruled (user, ...)` bullet there, only its `Decision:` clause and the ruling (never the finding or the author's Answer).
- `finalview.design(base): string`: the base's Design and Acceptance criteria sections; a line that names a design review, a refute, a `review NNN` or a round is dropped. z-design's rule: those two sections cite none.
- `finalview.changes(base, tip): string`: lines the layer added (`+`) in those two sections and among the decision lines, and lines it removed (`-`) from those two sections, headed "claims to check, not the design as given"; `design-changes.patch` when not empty. A decision line added on the layer is never in `ask.md`. A decision line only the base holds is never a `-`: decisions are only added, so it reached main after the layer was cut (a resolve's Decided line, say) and is in `ask.md` already.
- `finalview.assemble(input: Input): { [path]: text }` with `Input = { id, captured, base, front?, tip, contract, diff, patchId }`: `ask.md`, `design.md`, `design-changes.patch`, `diff.patch`, `contract/<path>` (the base's `check.sh` and acceptance specs) and `README.md`. One call builds one ticket's view. `finalview.allowed(path)` is the whole list of what a view may hold.
- `finalview.viewId(files, patchId)`: sha256 of every file but the README and `diff.patch`, plus the patch id (`git patch-id --stable`) of the diff. A clean restack or main moving leaves it alone; a redo that changes the ask, the design, the contract or the change changes it. The one line it leaves out of `ask.md` is the Decided line `./zn resolve` writes (c0250's `escalation.decidedLine`, `Decided with the user (<date>), resolve <decision>: ...`, `RESOLVE_LINE`): it is the human's ruling on a review, read back as that review's ruling, and stays in `ask.md` for every later reviewer, but it never moves the view it rules on (the blank lines and an emptied decisions heading around it are normalised away for the id). Any other new decision line changes the view. Two arguments: a later ticket may add an optional third (f0417's contract hash) without changing any case here.
- `finalview.parse(n, text): Review` and `finalview.problem(review): string?`: a review is `### F<n>` findings, each with a one-word `Gap: design` or `Gap: implementation` line and a `Measured against: "<quote>"` line, then `View: <id>` and `Verdict: on-course | off-course`. Fail closed: no readable verdict, no View, an on-course with findings, an off-course with none, a finding with no one-word Gap or no quote, are each a problem. `Review.quotes` holds each finding's quote.
- `finalview.unquoted(review, files): string?`: each quote must stand in the view it judged, compared loosely (case, runs of white space, curly quotes, `*` and backtick marks and a patch line's leading `+ `/`- ` do not count; at least `finalview.MIN_QUOTE`, 8, characters): a `Gap: design` finding quotes `ask.md` (the ask the design missed), a `Gap: implementation` finding `ask.md`, `design.md` or `design-changes.patch`. A quote the view does not hold is a problem; the README says so. The edge sets `Review.unquoted` from it for a review of the current view, and `finalview.state` reads it exactly as it reads `problem`: a review the human ruled `retry` (set aside) or `approve` (counted on course) is not held to it.
- `finalview.mayFileAgain(state): boolean`: true for `review-again`, and for `none` once a retry set every review aside; the dispatcher's one rule for a further round.
- `finalview.ruling(issue, layer: string?, findings: string?, decision: string?): (number?, string?)` (**Guess (prep) G3**): a c0250 note rules on this ticket's review N when its `Layer:` is the ticket, its `## Open findings or error` names `final-review-NNN.md` (the first one named), and it holds a `## Resolution` with a `Decision:`; anything else is nil.
- `finalview.state(reviews, view, ruled: { [number]: string }?): { state, why, latest }`, `ruled` the human's decisions by review number:
  - a review ruled `retry` is set aside (not counted, its view not judged): the review runs again;
  - a review ruled `split` reads as one ruled `amend-design` (c0250's plan takes the ticket out of its raft to be re-prepped either way; **Guess (prep) G9**, which replaces G3's "split ... change nothing"); `abort` changes nothing;
  - a review ruled `approve` counts as on course;
  - `none`: no review left; `invalid`: a review `problem` names, or a review of a view an earlier off-course review already judged ("reviewed again without a redo");
  - `blocked`: two off-course reviews counted and the latest off-course, **whatever the view**, unless the human ruled `amend-design` on that latest review; its `why` names that latest review (`final-review-NNN.md`), which the block's note names;
  - `review-again`: the latest review judged another view; `on-course`: the latest judged this view on course (or was approved); `redo-design`: off course on this view with any `Gap: design`, or ruled `amend-design`; `redo-layer`: implementation gaps only.
  `latest` is the latest counted verdict, so `review-again` after an off-course verdict (the redo not yet reviewed) is told from one after an on-course verdict (the layer moved). A third off-course verdict after a ruling blocks again: the human sees every repeat.

## Acceptance criteria

### Checked
- AC1: the view is built from the fixed files only: the ask is, from the base document, the c0260 record's messages and interview (or agent filing), its confirmed idea (Problem, Solution, Non-goals) and its confirmation; a hand-made record's sections with the capture standing for a missing idea; or the capture for an older ticket; plus the user's later decisions and rulings, wherever recorded; the design is the approved Design and Acceptance criteria without citations of reviews; the layer's own edits to them appear only apart, as claims; the diff has no bookkeeping of this ticket or raft.
- AC2: the view's id changes when the ask, the design, the contract or the patch changes, and not with the README, the diff text, a restack, main moving, or the Decided line `./zn resolve` writes (which stays in the ask); a decision line main gained after the layer was cut is never shown as the layer's change.
- AC3: the reviewer's README sets the one question (does the diff deliver the original ask), the two gaps, the two verdicts, and forbids the trail.
- AC4: a review with no readable verdict or View, a finding with no one-word Gap or no quoted measure, a quote the view it judged does not hold (a design gap must quote the ask), an on-course with findings, or an off-course with none, is not read.
- AC5: the ticket's state follows its reviews: none, on-course, redo by the gap named, review-again once the view changed, blocked at the second off-course verdict whatever the view, invalid (including a second review of an already judged view); it says what the latest verdict was.
- AC6: a finished layer of a marked ticket without an on-course final review keeps the next layer (and the stack's restack) from starting, and the worker is told to run the ticket's final review through the dispatcher (never a reviewer it starts itself), after the layer's own code review.
- AC7: off course by the implementation rebuilds the layer; off course by the design sends the ticket back to z-design; either, and a block, tells the worker to harvest the review's findings first.
- AC8: a second off-course verdict blocks the ticket for the human through `./zn block <R> review-exhausted --layer <issue>` (an unreadable review: `needs-decision`) with `escalation.md` naming the latest review (the one `./zn final` names), never `questions.md`; on a raft with `layers: reviewed` the complete layers below land first with `--through` (a landed one has nothing to land); a raft without it is told it lands whole and is never told `--through`; and the text says each resolve decision's next step (approve and retry: ready the raft again; amend-design and split: re-prep the ticket, the new issue already captured by a split; abort: nothing is readied).
- AC9: a layer read without the final-state fact is not held up.
- AC10: on a real layer of a raft with `layers: reviewed`: the layer's code review comes first, then the ticket's final review; the layer is not complete (`./zn stack`) until it is on course; the view holds none of the planted trail and is outside the checkout; `./zn final` follows the reviews committed on the layer and in origin/main's folder; main moving and a restack leave an on-course ticket on course with a diff free of main's work; the judged texts come from origin/main; a review quoting a line the view does not hold is invalid until the human's retry sets it aside; `./zn done` refuses an off-course ticket and an unreviewed redo; `./zn work next` reads the state after a real `./zn finish`; the raft is readied again after a retry; a second off-course verdict blocked through a real `./zn block` with the note the worker is told to write and resolved by a real `./zn resolve approve` is on course, with the human's words in the ask; the mark is read from origin/main; and `./zn status <id> prepared` marks the ticket `final: ticket`.
- AC11: the dispatcher runs the final review in a view folder outside every checkout with a prompt naming only its README and no exchange, does not place a review the state cannot read, lands `final-review-NNN.md` in the ticket's folder, and files a further one only when the state is `review-again` or, after a retry set every review aside, `none`, numbered after every review the ticket has.
- AC12: zz-review, zz-execute, zz-rules and z-design say the ticket's final review as this design states it.
- AC13: c0248's `completion.layer`, given the ticket's final-review state as `final`, calls a layer complete only for `on-course` and names any other state; without `final` it is unchanged; `final` never completes a layer c0248 calls incomplete.
- AC14: the human's resolve of a blocked ticket rules on the review its note names: `approve` puts it on course (the real route is AC10's), `retry` sets the review aside so it runs again, `amend-design` and `split` send it to z-design, and without a ruling the block holds whatever the view; a note of another ticket, or one with no resolution, rules on nothing.
