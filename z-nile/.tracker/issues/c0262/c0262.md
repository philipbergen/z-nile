# c0262: Full force final review

## Problem
User (2026-11-07): "We are missing a final full force review where we take the original ask and the design and the implementation and final adversarial check that the design covers the idea and tha tthe implementation delivers the design."

User (2026-11-07): "The final full fiorce revieq should be fed a limited view of the tickets so that it looks at it only on its merits as given and not with the broader context of all the compromise on the way. It should be clear if we stayed on course and there should be a redo if not"

Code review checks the code against the Design, and design review checks the design against the capture, but no review takes the original ask, the design and the implementation together. Every reviewer also sees the whole trail of reviews, refutes and decisions, so a drift agreed to round by round is never seen as a drift. What should happen:
- **Once per ticket, before its layer merges** (c0248), a full-force adversarial review checks that the design covers the idea and that the implementation delivers the design. It runs on the sharp model (c0261) in a fresh context.
- **Limited view:** the reviewer is given only the original ask (verbatim ask, interview and confirmed idea, c0260, or the capture for older tickets), the design and the implementation as given. It sees none of the compromise on the way: no design reviews, refutes, harvests, PR comments or worker notes. It judges the result on its merits.
- **A clear verdict** says whether we stayed on course, with each gap named against the ask or the design.
- **A redo when off course:** the ticket goes back to z-design when the design missed the idea, or its layer is rebuilt when the implementation missed the design. Then the review runs again. A second off-course verdict blocks the ticket (c0250) for the human.

Decided with the user (2026-11-11), in c0248's idea interview Q1: "Green on the layer below" (a layer is complete when it is built, reviewed, full-force reviewed and green on top of the layer below; so this review runs once per ticket before the next layer starts, and is part of that layer's completion; the stack then lands as one bind, c0248 Q4).

### The user's words on the last review
"reviews are back and forth EXCEPT for the last one that just verifies that the diff matches the original ask." The earlier reviews (idea, design, code) stay back and forth with the author (up to a round of answers). The ticket's final review is the one that is not: one question, **does the diff deliver the original ask**. Its view holds the design only so a gap can be named where it arose (`Gap: design`: the design does not cover what the ask needs; `Gap: implementation`: the design covers it but the diff does not deliver the design), which is what the captured redo needs to route. It has no refutation round: the author is not shown to argue with it; a wrong off-course verdict costs one redo, and a second blocks the ticket for the human. The captured wording "design covers the idea, implementation delivers the design" is kept as the two gaps; the verdict is judged on the ask. Whether that is the right reading is the first bullet under Open to the human.

### Design
Pure rules in one module, reads at the edge, one new command.

**`z-nile/engine/finalview.luau` (new, pure; zz-arch: texts in, texts out)**
- `finalview.keepPath(path): boolean`: false for a path under `.tracker/issues/`, `.tracker/rafts/` or `.cache/`. A project's own `.tracker/game-design.md` and `architecture.md` are the design's branch edits and are kept.
- `finalview.ask(captured, current): string`: `## Ask (verbatim)`, `## Interview`, `## Idea` of the captured text when present, else `## Problem`, `## Solution`, `## Non-goals` as captured; plus the lines of the current Problem that begin `Scope decision (user, ` or `Decided with the user (` (the user's later words are part of the ask; nothing else of the current document is).
- `finalview.design(current): string`: the `## Design` and `## Acceptance criteria` sections only (Unknowns & experiments, Regression guard, Open to the human, Verification log and the rest record how the design was reached).
- `finalview.assemble(input): {[path]: text}`: `ask.md`, `design.md`, `diff.patch`, `contract/<path>` for the check and the acceptance specs, and `README.md` (`finalview.INSTRUCTIONS`, with `View: <id>`). `finalview.allowed(path)` is the whole list of what a view may hold.
- `finalview.viewId(files)`: sha256 of every file but the README, in sorted order. A redo that changes the design, the contract or the diff changes it.
- `finalview.parse(n, text): Review` and `finalview.problem(review): string?`: a review is `### F<n>` findings, each with `Gap: design | implementation`, then `View: <id>` and `Verdict: on-course | off-course`. It fails closed: no readable verdict, no View line, an on-course with findings, an off-course with none, a finding with no Gap, are each a problem (the ticket stops for the human, nobody guesses).
- `finalview.state(reviews, view): {state, why}`: `none` (no review), `on-course` (the latest review judged this view on-course), `review-again` (the latest review judged another view: the redo happened, or the layer moved), `redo-design` (off course on this view with any `Gap: design`), `redo-layer` (off course on this view, implementation gaps only), `blocked` (two off-course reviews, the latest off-course: a redo that did not fix it), `invalid`.

**`z-nile/engine/finalread.luau` (new, the edge)**: `where(issue)` finds the ticket's layer (`R<id>/<n>/<issue>`, the newest raft's), its tip (the local branch when it is ahead of origin's, else origin's) and its base (the tip of the layer below, or main); `files(issue, at)` reads the captured text (`trail.capture`, as `./zn trace` does), the document, `check.sh` and `acceptance/` at the tip, and the diff limited to `keepPath` files; `reviews(issue, at)` reads the `final-review-NNN.md` files **committed on the layer**; `state(issue)`; `write(issue, dir)` writes the view folder whole (never merging into an old one). All through `lib/sh`; nothing is written outside `.cache/final/<id>`.

**`z-nile/engine/completion.luau` (c0248's, extended here)**: `completion.layer(input)` gains an optional `final: string?`, a `finalview.state` word. With `final` given (the callers pass it for a raft carrying `layers: reviewed`), the layer is complete only when `final == "on-course"`; any other word is "not complete" with the reason `the ticket's final review is <word>: ./zn final <issue>`; with `final` nil nothing changes, so a raft in flight keeps today's rule. It never completes a layer c0248's own checks call incomplete. `./zn start` (layer N+1) and `./zn done` pass `finalread.state(issue)` as `final` for a marked raft: that is what makes "the next layer starts only after the ticket's final review" a refusal and not only the worker's instruction. `layergit.isPostFinishPath` and `trace.isTrackerFileOf` (c0248 widens them to a layer's review, refute and harvest files) also accept `final-review-NNN.md` in the layer's own issue folder, so committing the review after the finish keeps the layer finished (on today's main any tracker file of the ticket is accepted: `fixture.spec` commits one after a real `./zn finish`).

**`z-nile/engine/main.luau`**: `cmd.final` (`./zn final <issue-id> [--view]`): without `--view` prints `<id>: <state> - <why>`; with `--view` writes `.cache/final/<id>/` and lists its files. `cmd.done` refuses, before its other review checks, a member whose state is `redo-design`, `redo-layer`, `blocked` or `invalid` (for an unmarked raft this is the whole rule; a marked raft is refused by `completion.layer` for every state but `on-course`); a member with no final review is **not** refused by the unmarked rule (the user's 2026-11-07 "Full force = (a)": not a no-waiver hard gate; a raft readied before this exists is not held to it). main.luau is capped at 200 top-level locals and holds exactly 200: `cmd.final` is a field of `cmd`, and both modules are required lazily inside the function, under names no spec reads.

**`z-nile/engine/work.luau` and `workread.luau`**: `LayerFact.finalState: string?` (nil means the fact was not read, so a caller that does not set it, like `work.spec`, is not held up; the edge always sets it for a finished layer, from `finalread.state`). After a layer is finished, `forRaft` returns `work.finalStep` unless the state is `on-course`: `final-review-ticket` (none, review-again), `rebuild` (redo-layer: fix the layer against the review's gaps, `./zn finish`, the review runs again), `redesign` (redo-design: `./zn stop`, `./zn unfold`, re-prep the ticket with z-design, z-raft, z-ready), `blocked` (blocked, invalid: `questions.md`, `./zn stop`, no third review). The next layer's `implement`, and the stack's `restack`, come only after every finished layer is `on-course`.

**`z-nile/engine/dispatch.luau` and `dispatcher.luau`**: `./zn dispatch zz-review <issue-id> --mode final` (a raft id keeps today's meaning). The dispatcher writes the view (`finalread.write`), runs the reviewer with the view folder as its working directory and a prompt that names only `README.md` there (no skill path, no `./zn lessons`, no `./zn trace`), and lands `review.md` as `final-review-NNN.md` in the issue's folder, as it lands every review (the landing and its spend row, phase `code-review`, are main's `REVIEW_MODES.final`). The "one round" refusal gets one exception: a second file is placed only when `finalread.state` is `review-again`.

**Skills**: zz-review gains "Final mode on a ticket (the last review)"; zz-execute Phase 3 gains step 4a; zz-rules gains the `final` row, the file in the layout and the `done` refusal. A spec pins each (docs.spec).

**Who is bound**: the reviewer's folder is the tool's, not the reviewer's restraint (the captured Solution). Reading the repository is still possible for a same-user process; the prompt forbids it and the view holds everything the verdict needs. A deliberate read outside the folder is detectable only by review of its transcript, which is accepted (standing rule).

**Server authority / game**: none; tooling only. No `src/` or game change.

### Scalability
One review per ticket instead of one per raft: N model runs for an N-ticket raft (each on the `final-review` role), each over one layer's diff, so its cost grows with the ticket and not with the stack. The view is built from a handful of `git show`/`git diff` calls; `workread` calls `finalread.state` only for a finished layer, and `finalread.files` (the diff) only when the layer has a review to compare, so a cold `./zn work next` adds no git work for layers without one. A very large diff is the reviewer's context limit, the same as a code review's.

### Maintainability
All rules are in one pure module (`finalview`) with a spec that names each; the edge is one module (`finalread`) and `main.luau` gains one command. The ask sections are one constant. The state names are the strings `work.luau` branches on, listed in one place (`finalview.state`'s comment). The reviewer's README and the zz-review section are the same text twice; docs.spec pins the phrases of the second, view.spec the first. No duplicate of `trace`: the raft-level review reads its own files and a ticket's reads its own.

### Usability
A worker sees one line from `./zn work next` and does it. A person asks `./zn final c0010` and reads one state with a reason (`blocked - 2 off-course verdicts: ...`). An interactive reviewer is given a folder and one README; there is nothing to configure. The refusal at `done` names the ticket, the state and the command to read.

## Acceptance criteria

### Checked
- AC1: the view is built from the fixed files only: the ask is the capture (or Ask, Interview, Idea) plus the user's later decisions, the design is Design and Acceptance criteria, and the diff has no ticket or raft bookkeeping.
- AC2: the view's id changes when the design, the contract or the diff changes, and not with the README.
- AC3: the reviewer's README sets the one question (does the diff deliver the original ask), the two gaps, the two verdicts, and forbids the trail.
- AC4: a review with no readable verdict or View, a finding with no Gap, an on-course with findings, or an off-course with none, is not read.
- AC5: the ticket's state follows its reviews: none, on-course, redo by the gap named, review-again once the view changed, blocked at the second off-course verdict, invalid.
- AC6: a finished layer without an on-course final review keeps the next layer (and the stack's restack) from starting, and the worker is told to run the ticket's final review.
- AC7: off course by the implementation rebuilds the layer; off course by the design sends the ticket back to z-design.
- AC8: a second off-course verdict, or an unreadable review, blocks the ticket for the human with `questions.md`.
- AC9: a layer read without the final-state fact is not held up.
- AC10: on a real layer: the view holds none of the planted trail, `./zn final` follows the reviews committed on the layer, `./zn done` refuses an off-course ticket, and `./zn work next` reads the state after a real `./zn finish`.
- AC11: the dispatcher runs the final review in the view folder with a prompt naming only its README, lands `final-review-NNN.md` in the ticket's folder, and places a second one only after the layer changed.
- AC12: zz-review, zz-execute and zz-rules say the ticket's final review as this design states it.
- AC13: c0248's `completion.layer`, given the ticket's final-review state as `final`, calls a layer complete only for `on-course` and names any other state; without `final` it is unchanged.
