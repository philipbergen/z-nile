### F1 [high] The human's ruling cannot lift an `invalid` state that comes from an unquoted review: after `resolve retry` (or `approve`) the ticket stays `invalid`, the dispatcher refuses a further review and `done` refuses the ticket
Where: c0262.md, `finalread.state` ("a review of the current view whose quotes `finalview.unquoted` refuses makes the state `invalid`"), `finalview.state` (retry sets a review aside, approve counts it on course), `finalview.mayFileAgain`, `cmd.done`'s refusal of `invalid`, `work.luau` `blocked` (invalid) bullet; AC14; prototype `z-nile/engine/finalread.luau:272-281`.
Evidence: `finalread.state` loops over every review of the current view and returns `{ state = "invalid" }` on the first unquoted one before it calls `finalview.state(reviews, view, finalread.rulings(issue, at))`; the rulings are never consulted for that check, while the pure `finalview.state` skips `problem` for a review ruled `retry` or `approve`. Probe on `proto-c0262-r2-mut`: in `fixture.spec`, right after the committed review 002 quoting "a line nobody wrote" reads `invalid`, the case pushed the layer, wrote the note the worker is told to write (`## Open findings or error` first line `final-review-002.md`), ran a real `./zn block R0010 needs-decision --layer c0010` (ok) and a real `./zn resolve R0010 retry --answer "review it again"` (ok) from a terminal environment; `./zn final c0010` then printed `c0010: invalid - final-review-002.md F1 quotes no line of ask.md, design.md or design-changes.patch ("a line nobody wrote")`. From there `mayFileAgain("invalid")` is false, so `./zn dispatch zz-review c0010 --mode final` refuses before any reviewer starts; `work next` says block again with `needs-decision`; `done` refuses `invalid`. Only `abort` or deleting the committed file gets past it. The route is reachable as the design keeps it: a person's own CLI in `./zn final --view`'s folder (the path the design keeps for a person) writes a review no dispatcher checked, and the person commits it.
Critique: AC14 says `retry` "sets the review aside so it runs again" and `approve` "puts it on course"; on this path neither holds. The fixture's real route never rules on the unquoted review (it overwrites 002 with a quoted one before blocking), and review 002's F2 asked for a real `resolve retry` route, which was not added; that case would have shown this. The tempting fix is to skip the quote check for the latest review only, which still leaves an earlier unquoted review of the same view blocking every later state.
Consequences: the quote check and the ruling must meet in one place. If the check moves into the pure state, `finalview.state` needs the files (or a per-review quote problem computed at the edge) and must apply the same `retry`/`approve` filter as `problem`; an approved unquoted review then counts on course on the human's word, as an approved unreadable one already does. A `retry` of the only review gives `none`, and `mayFileAgain` files the next number after it.
Recommendation: compute the quote problem at the edge per review (`Review.quoteProblem: string?`, set by `finalread` for a review of the current view) and let `finalview.state` treat it exactly as `problem`: skipped for a review ruled `retry` (set aside) or `approve`; state it in the `finalview.state` and `finalread.state` contracts. Cases: verdict.spec AC14 "a retry sets an unquoted review aside (none); approve of an unquoted review is on course"; fixture.spec AC10 the real route above (block `needs-decision` on the unquoted review, real `resolve retry`, `./zn final` says `none`, and `finalview.mayFileAgain` of that state is true), with a mutant row "the quote check ignores rulings". Lesson candidate (z-design): when an edge adds a refusal in front of a pure state that the human's rulings lift, does every ruling lift that refusal too, and does a case run the real ruling on an item in that refused state?
Erred: z-design
