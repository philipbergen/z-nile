# c0263: Ticket provenance

## Problem
User (2026-11-07): "tickets need authors (whose idea, take it from git, then who approved the design, who unblocked a blocked ticket and so on)."

Nothing on a ticket says who had the idea or who decided anything. User decisions are prose lines (`Scope decision (user, …)`), and the design has no explicit human approval. With workers carrying tickets from raft to merge (c0253), the human acts at only a few points, and each of those should be on the record. What should happen:
- **Author:** whose idea it was, taken from git (the author of the ticket's capture commit).
- **Design approved by:** the human who approved the design. Design approval is an explicit human step before `prepared`, since design is a human stage (README, Intent; c0264).
- **Unblocked by:** whoever resolved a block (c0250), each time.
- **And so on:** who confirmed the idea (c0260), who set the rank, who rafted it, and which worker (host, CLI, model) delivered each layer (c0254).
- The board shows them.

Decided with the user (2026-11-08), Q1 storage, "Derive from git, store only the rest": what git knows (the idea's author, who made each status change) is read from history by `./zn who`; only what git cannot tell (a human's approval when a bot pushed it, and decisions) goes in ONE append-only record per ticket. Not five frontmatter keys. (Supersedes the earlier "(c) frontmatter keys" answer of 2026-11-07.)
Decided with the user (2026-11-08), Q2 approve, "Prepared is refused without it": `./zn status <id> prepared` refuses until a human has run `./zn approve <id>`; a redesign after a stop needs a fresh approval; the human is the git author of the approve commit; under the dispatcher the prep gate stops and waits for the user, not auto-merge. (Supersedes the 2026-11-07 reading of "approved the design" as the design reviewer's `Verdict: approve`.)
Decided with the user (2026-11-08), Q3 dependencies, "Land first, define a small record API": c0263 does not depend on c0250, c0260, c0254 or rank; it defines a small record function that those tickets call when their event happens (blocked/unblocked, idea confirmed, rank set, layer delivered); events whose tickets do not exist yet are simply not recorded until they exist.
Decided with the user (2026-11-08), Q4 worker identity, "Read c0254's spend rows": c0263 only reads host, CLI and model that c0254 puts on spend rows, and the dispatcher starts passing them; until c0254 exists, delivered-by records the actor grammar the user chose (`human:<git name>` or `agent:<model, version, effort>`) without host.
Decided with the user (2026-11-08), Q5 readings, "Confirm all": rafted is the rafting PR merge, one entry per ticket layer; delivered is the raft PR merge; unblocked is a `status <id> new` after a stop; `release` is not stamped; an interactive session without `--actor` records `agent:unknown` plus the effort; back-fill uses the git author for engine publishes (no trailer).
Decided with the user (2026-11-07), still standing: the actor is `human:<git name>` or `agent:<model id>` "including agent-model-version-effort": for an agent the model, its version and its effort are recorded (for example `agent:claude-opus-5-5 effort high`), from the dispatcher's `.models.toml` spec or the session's trailer. "rafted" is the rafting PR merge "with layers in case there are multiple tickets": a rafting PR or raft PR can hold several tickets, so provenance is recorded per ticket (a layer per ticket inside the PR), not once per PR; the same holds for "delivered". "yes, back-fill existing done and backlog items from git where possible, in addition to items from now on."

## Non-goals
- Access control: recording who did something is not permission to do it.
- Worker identity on spend rows (c0254); this issue reads it.
- (prep) Frontmatter keys, and a back-fill that writes into old documents: the 2026-11-08 Q1 decision derives instead (below).

## Solution
- Derive what git knows (the author, the committer of each status change) instead of storing it twice. Store only what git can't tell: a human's approval when a bot pushed it, and the decisions.
- `./zn approve <id>` records the design approval; `./zn who <id>` prints the history.

Prep's detail, below the captured bullets. One record per ticket, `provenance.md` in its folder (a raft's folder too, for events on a raft), append-only rows with no row numbers (so two appends merge). `./zn who <id>` merges what git says (read at the time, never stored) with the record's rows. Existing done and backlog items need no write: `who` reads their git history, which is how the "back-fill from git where possible" decision is met under Q1. A command that happens in a PR (approve, rafting, done) appends its row in the PR; one that is published (`status <id> new`, `./zn record`) appends it in its published commit built from `origin/main`'s file; the engine's own merges union the file when both sides appended (Behaviour 11).

| event | derived from git | stored in the record | written by |
|---|---|---|---|
| idea | the author of the capture commit (`human:<name> (from git)`) | nothing | nothing |
| status changes | the author and trailer of each `tracker: <id> <status>` commit of the item's life | nothing | nothing |
| `approved` | nothing (a bot may push it) | the human, the design hash, the user's words | `./zn approve` |
| `unblocked` | (no stored row) the author of each `tracker: <id> new` commit of the life, printed as `unblocked` and never also as a status line | the actor | `status <id> new`; c0250's resolve through the record API |
| `confirmed` (c0260), `ranked` | nothing | the actor | `./zn record`, called by their tickets |
| `rafted` | (no stored row) the newest life commit whose subject is `tracker: raft <the ticket's current raft> …` (the rafting PR's squash) | the actor, `raft=<R-id>`, one row per ticket | `new raft`, `fold`, `recombine`, an emergent `new issue --raft` |
| `delivered` | (no stored row) the life commit that first added the ticket's document under `done/` | the actor, `raft=<R-id>`, one row per member | `done` |
| merged | always: the author and trailer of that same `done/` commit, as a `merged` entry of its own (who merged the raft PR) | nothing | nothing |
| worker (host, CLI, model) | read at `who` time from the ticket's spend rows: the newest `deliver` row that has a model, else the newest `build` row that has one | nothing | c0254 puts host and CLI on the rows; until then only the model column exists |

**The record file** (`provenance.md`, written by `provenance.render`, read by `provenance.parse`): a header line `# Provenance: <id>`, a blank line, the table header `| when | event | actor | detail |` and its separator `|---|---|---|---|`, then one line per event, `| <when> | <event> | <actor> | <detail> |`. `<when>` is `YYYY-MM-DD HH:MM` in UTC (git dates are printed in UTC by `who` too); `<actor>` is the stored grammar below without the ` (from git)` suffix; `<detail>` is `key=value` parts joined by `; `, empty when there is none (the cell is then a single space: `|  |`), with `|` written `/` and newlines written as spaces. Example:
```
# Provenance: c0263

| when | event | actor | detail |
|---|---|---|---|
| 2026-11-08 09:00 | approved | human:Philip Bergen | design=1a2b3c4d5e6f; said="yes, approved" |
| 2026-11-08 09:30 | rafted | agent:claude-opus-5-5 effort high | raft=R0100; via=dispatch:raft-plan |
```

**Actor grammar** (the user's, 2026-11-07), the stored form: `human:<name>`, or `agent:<model> effort <level>`; a value read from git ends ` (from git)`; `unknown` when nothing says. `<model>` is `provenance.modelId(text)`: lower-case, each run of non-alphanumeric characters one `-`, trimmed, so `.models.toml`'s `grok-4.7` and git's `Grok 4.7` are both `grok-4-7` and `Claude Opus 5.5` and `claude-opus-5-5` the same; the version is part of the model id; `<level>` is the spec's `effort` or `unknown`.

**The live actor** (a command that records), in this order: `--actor "<value>"`, else `ZN_ACTOR` (only `human:<name>` or `agent:<model> effort <level>`, nothing else, refusing the command before it changes anything; the dispatcher sets `ZN_ACTOR` for each attempt of a model step from that attempt's spec, `provenance.agent(spec.model, spec.effort)`, and for a script step it runs itself (`raft-plan --apply`, `z-ready`) the user who started the pipeline, `human:<git name>`, with `ZN_VIA=dispatch:<step>`, which a row records as `via=dispatch:<step>`); else, when `CLAUDECODE` or `AI_AGENT` is set and non-empty, `agent:unknown effort <CLAUDE_EFFORT|unknown>`; else `human:<name from git var GIT_AUTHOR_IDENT>`, or `unknown` when git has no identity.

## Design

### Behaviour (every outcome the Problem names, each with a Checked criterion)
1. **Author (AC3, AC8).** `./zn who` reads the item's life with `trail.read` (the reader `./zn capture` uses: the last time the document went from absent to present, cut at a compaction, so a reused number is a new life) and takes the capture commit by `trail.capture`: its author, `human:<name> (from git)`. Nothing is stored. A trailer is never read for the idea.
2. **Design approved by (AC4, AC5).**
   - `./zn approve <id> [--said "<the user's words>"]`, in a prep worktree, for an issue that is `preparing` on `origin/main` with `design: ready` here. It computes the design hash (`raftplan.recordHash` over the issue's folder in this worktree: the document without `status:`/`raft:`, `check.sh`, `acceptance/`, the design reviews, refutes and `harvest.md`, the same hash z-raft's `grouped:` record uses; `provenance.md` is not among those files), appends `approved | human:<git name> | design=<hash>; said="<words>"` and commits it as `tracker: approve <id>`, so the human is the git author of that commit. Each refusal has its own message: the main checkout (`approve runs in a worktree`); a tree with changes outside the issue's folder (`outside`: approve commits the issue's folder, its design files and the record, as `tracker: approve <id>`, and nothing else); a dispatched worker (`ZN_DISPATCH` set: a worker cannot approve); an issue not `preparing` on origin; a design not `ready` here; no git identity; and an agent session (`CLAUDECODE` or `AI_AGENT` set) without a non-empty `--said`, because the agent's commit carries the human's git identity and the words are the evidence. In an agent session the row reads `human:<git name>; via=agent:<actor>; said="…"`: the interactive prep that the user already approved in the session records their words through `--said`, then runs `./zn status <id> prepared`. That an agent can run it with words it invented is a limit of recording, not of authority (open question 1).
   - `./zn status <id> prepared` (the carried move) refuses each issue it moves until the newest `approved` row of that issue's `provenance.md` has `design=` equal to the hash of the folder now: `<id> has no current approval: ./zn approve <id>` or `<id> was redesigned since its approval (<old> -> <new>): ./zn approve <id> again`. This covers an issue named alone and a member a raft's move changes (a member already prepared on `origin/main` is taken as it is). A redesign after a stop (`prepared -> preparing`, edits, `prepared`) changes the hash, so it needs a fresh approval; a stop with no edit keeps the hash and the old approval. No flag skips the refusal.
   - Downstream, so a hand-edited `status:` line is not the only gate: `fold`, `new raft` and `ready` (the three ways a prepared issue enters a raft) refuse an issue whose newest approval is stale (it was redesigned after approval), each before it publishes anything (a refused `fold` leaves `origin/main` and the raft's status as they were); `./zn raft-plan` skips such an issue (`skip <id>: approval is stale (./zn approve <id>)`, never a command), so `raft-plan --apply` is never left half applied; and `audit` warns on a prepared issue with a stale approval. A prepared issue with no `approved` row at all predates this rule and is let through (grandfathered by absence: open question 3 says what that costs, and approve.spec pins it so changing it is a deliberate edit). z-design's offline instruction (`PICKMAN_PUBLISH=0`: edit the status line by hand) says to run `./zn approve <id>` first, which works offline.
   - The design reviewer's `Verdict: approve` is no longer the approver; z-design's rounds are unchanged.
3. **Unblocked by (AC6).** `cmd.status` appends `unblocked | <live actor> | ` to the issue's `provenance.md` in the same published commit as the status line, on every `status <id> new` (a raft's move: each issue it changes, never the raft). `release`'s give-back is not recorded. c0250's resolve calls `./zn record <id> unblocked --detail "block=<reason>"` once per resolution ("each time"), on the ticket or on the blocked raft: rows accumulate, `who` prints all.
4. **Rafted by (AC6).** At each place the engine writes `raft:` to a non-empty value (`new raft` in its published and offline paths, `fold`, `recombine`, an emergent `new issue --raft`) it appends `rafted | <live actor> | raft=<R-id>` to that ticket's `provenance.md`, one row per ticket (a layer per ticket, even when a raft holds several); the row rides the rafting PR with the `raft:` line, so the rafting PR merge is when it lands. `unfold` removes nothing; `who` shows the newest `rafted` row whose `raft=` is the ticket's current `raft:`, earlier ones as history.
5. **Delivered by (AC6).** `done` appends `delivered | <live actor> | raft=<R-id>` to each member's `provenance.md` and stages it with the moves, so `done`'s rollback (`git reset --hard`) removes it and a retry appends once; one row per member, riding the raft PR. Under zz-rules' Merging the agent that ran `done` merges its own PR, and the squash commit's `Co-Authored-By` agrees. The row is made before the merge, so where the user merges the run PR it still names the delivering agent: a limit, stated. The worker (host, CLI, model) is not stored: `who` reads it from the ticket's spend rows (Q4): the model column the dispatcher already writes today, and the host and CLI columns once c0254 adds them (the dispatcher starts passing them with c0254); with none, the row has the actor only.
6. **Record API for the other tickets (AC6).** `provenance.record(text, event, actor, detail, now)` (pure: returns the new `provenance.md` text) and `./zn record <id> <event> [--actor A] [--detail "k=v"]`, which publishes the append (built from `origin/main`'s file, validated by the publish rule below) for the events `unblocked`, `confirmed` and `ranked`, on an issue or a raft in the backlog or in `active/` (a worker blocks while it holds a raft: an `unblocked` row is published into the active item's record and reaches the raft's branch through the union merge of Behaviour 11); `approved`, `rafted` and `delivered` are written only by their commands, and any other event name is refused. c0250, c0260 and the rank ticket call it when their event happens, so c0260's capture needs no `./zn land` change; events of tickets that do not exist are not recorded.
7. **`./zn who <id>` (AC3, AC8).** Prints one line per event, oldest first: `<when>  <event>  <actor>  <detail>  (git | record)`, parts joined by two spaces, an empty detail omitted: the derived entries (idea; each status change with the author of its `tracker: <id> <status>` commit in the item's life, its trailer's agent when it has one, except that a `tracker: <id> new` commit is printed once, as `unblocked`; the git fallbacks of the table for an event with no stored row; and always a `merged` entry for the commit that added the item under `done/`, so the delivering agent and whoever merged are both on the record) and the stored rows, the worker from the spend rows appended to a `delivered` line as `worker=<…>`. A commit's actor is `agent:<modelId> effort unknown (from git)` when it carries a `Co-Authored-By`/`Co-authored-by` trailer whose email is not the email of any commit author in the log (a person is whoever commits), else `human:<author> (from git)`; the engine's own `tracker: <id> <status>` publishes carry no trailer, so a give-back an agent ran reads as the human git shows (Q5, stated). Ties in time keep derived before stored, then file order. Read-only, so it may run in the main checkout. Existing done and backlog items work with no write.
8. **The board shows them (AC9).** `board.build` reads history once per build: one `git log` in trail's format over every root, parsed once by a single `trail.parse` call given every item folder as `dirs` (O(lines), not O(items x lines): E9 measured the per-item version at 5 s for 336 items), the commits bucketed by item, then `trail.life` per item; a tree without git or history builds with the stored rows only, as `history`'s "history unavailable" does) and passes the result into `board.collect` as an optional argument after R0083's `facts`; `collect` puts `provenance: { Entry }` on each `Issue`/`Raft` model, and the item view's script writes a "Provenance" section from it. R0083 (c0118, active: `collect`/`build` take `facts`) and c0265 (work heartbeat, still being designed: its `buildBoard` will compose `collect`/`withVerdicts`/`render`) both change this file; the later to land merges the other's `board.luau` change.
9. **The dispatcher (AC7).** The `prep` gate never merges: `dispatch.luau`'s merge branch is for `raft` only. Every prep stop is exit 4 with the existing reason of its turn (not in `auto_merge`, draft, red, unmergeable, carries code) followed by `; approve the design with ./zn approve <id>, then merge it yourself`; the gate checks stay in the order they are in, so each existing assertion on a reason stays true; when no condition fails (a green, mergeable, clean PR that the gate would once have merged) the reason is `the prep PR #n waits for the user's approval and merge`, never the old fallthrough "its head commit is unknown". `auto_merge` keeps accepting `prep` as a name (no config breaks) but it has no effect; `.models.toml` drops it. A dispatched z-design step ends at an open PR with `design: ready` and status `preparing`; it never runs `approve` or `status prepared` (both refuse under `ZN_DISPATCH`). The user runs `./zn approve <id>` and `./zn status <id> prepared` in the prep worktree, commits, pushes and merges. The in-session path (an interactive z-design) does the same with `--said`.
10. **Where the writes may land (AC6, AC10).** The publish validator accepts an issue's or raft's `provenance.md` as a create or an append only (every old row byte for byte, at least one new), in a non-`active/` folder, like `spend.md`, and in `active/` only when every new row is `unblocked`; `publish.allowed` learns the name. The dispatcher's rafting gate accepts, beside the `raft:` line, `<issue folder>/provenance.md` whose old rows are unchanged and whose new rows are `rafted` rows only (the file may already hold the prep PR's `approved` row). `audit` reports a `provenance.md` that does not parse, has an unknown event, a bad actor, or a header naming another id.
11. **Two writers, one file (AC6).** The record is written by published commits on `main` and by commits a PR carries, so two appends between merges conflict in git (E8). The engine's merges of `origin/main` (`mergeOrigin`, `sync`, `land`, `fold`/`recombine`'s) resolve a conflict confined to `provenance.md` files by union (`git merge-file --union` of the stage-1/2/3 blobs) and commit; a conflict in any other file aborts as it does today. Rows carry no number, so a union is a valid file; zz-rules' Merging step 4 and z-design say to merge with `./zn sync`, which unions the record, never plain `git merge`.

### Interfaces
`z-nile/engine/provenance.luau` (new; pure; requires no module that touches the file system; strict):
```
type Hint = { agent: boolean, effort: string? }
type Row = { when: string, event: string, actor: string, detail: string }
type Commit = trail.Commit                                          -- with author, email, trailers
type Entry = { when: string, event: string, actor: string, detail: string, source: "git" | "record" }
type Derived = { idea: Entry?, statuses: { Entry }, unblocked: { Entry }, rafted: Entry?, delivered: Entry?, merged: Entry? }
provenance.EVENTS: { "approved", "unblocked", "confirmed", "ranked", "rafted", "delivered" }
provenance.PUBLISHED: { "unblocked", "confirmed", "ranked" }      -- what ./zn record may publish
provenance.modelId(text: string): string
provenance.human(name: string): string
provenance.agent(model: string, effort: string?): string        -- "agent:<modelId> effort <effort|unknown>"
provenance.isValid(value: string): boolean                       -- the stored grammar, with the optional " (from git)"
provenance.isLive(value: string): boolean                        -- human:<name> or agent:<model> effort <level>, no suffix
provenance.resolve(flag: string?, env: string?, hint: Hint, gitName: string?): (string?, string?)
provenance.fromTrailer(trailer: string): string?

provenance.render(id: string, rows: { Row }): string
provenance.record(text: string?, id: string, event: string, actor: string, detail: string, now: string): (string?, string?)
provenance.appendOnly(old: string?, new: string, id: string): string?     -- the publish and gate rule
provenance.union(base: string?, ours: string, theirs: string): string    -- Behaviour 11's merge, pure
provenance.approval(rows: { Row }, hash: string): ("none" | "stale" | "current", string?)
provenance.select(life: { Commit }, id: string, state: string, raft: string, people: { [string]: boolean }): Derived
provenance.merge(derived: Derived, rows: { Row }, worker: string?): { Entry }

provenance.problems(path: string, text: string): { string }      -- audit
```
`trail.luau` gains `author`, `email` and `trailers` on `trail.Commit` (optional fields, additive) and `isDoc` stops counting `provenance.md` as a document (it would otherwise break the life rule). Its log format becomes `--format=@@%H %ct %s%n@A%an%n@E%ae%n@T%(trailers:key=Co-Authored-By,valueonly,separator=%x1f)` with `--name-status`: one header line, then three tagged lines (`@A` author, `@E` email, `@T` the trailer values separated by the unit separator, empty when none); a change line `M\tpath` and these tags cannot be confused, and no commit body is read, so a body line that looks like a change line cannot misparse (a trail case pins it; `capture`'s output is unchanged). Callers: `main.luau` (`cmd.approve`, `cmd.who`, `cmd.record`, the appends in `status`, `new raft`/`fold`/`recombine`/emergent, `done`, the refusals in the carried move, `fold`, `new raft` and `ready`, the shared union merge), `publish.luau`, `dispatcher.luau` (the rafting gate, `ZN_ACTOR`/`ZN_VIA` per attempt and script step), `dispatch.luau` (the prep gate), `board.luau`, `audit.luau`. `models.luau` is read only.

### The split
Pure and unit-tested: all of `provenance.luau`. Adapters (thin): `main.luau` reads `git var GIT_AUTHOR_IDENT`, the environment, the files, `trail.read` and the git log, calls `raftplan.recordHash` (existing) and hands texts to the pure functions. Each wiring is checked through its caller (AC4 to AC9), not only the pure function, because an unwired caller passes every pure case and breaks the dispatcher, publish or audit.

The refusal text keeps the substring `status: line` (`c0053/publish.spec:167` pins it). Published appends are built from `origin/main`'s file, never from a worktree's.
- **Dispatcher rafting gate**: Behaviour 10; its error text `beyond its raft: line` is kept.
- **`./zn land`**: unchanged (c0260's `confirmed` row is published by `./zn record`).
- **`status prepared` and every spec that drives it**: see Overrides.
- **Merges of `origin/main`**: Behaviour 11; every merge helper in `main.luau` goes through one function.
- **Board**: Behaviour 8.
- **`done`'s rollback**: Behaviour 5; `c0074/done-gate.spec` is in the Regression guard.
- **z-design, zz-rules, README, zz-execute, z-raft skills** describe approve, the record and the union merge; promoted docs specs pin phrases (`c0116/docs.spec:54` pins "**then run `./zn status <id> prepared`**"; `c0111/skill-docs.spec:105-111` requires "lessons --uncovered <id>" before the first "status <id> prepared`" in z-design's step 5, so the approve text goes after the harvest confirmation).
- **In-flight preps** (designs already `ready` and not yet `status prepared` when this lands) are refused until `./zn approve`: a migration note in the skills. Items already prepared are grandfathered by having no record (Behaviour 2); done items need nothing.

### Scalability
One small file per ticket, appended; `who` reads one item's trail (one `git log` on its folders, as `capture` does) and the board one pass for all items; audit parses a file per item that has one.
### Maintainability
One module, one event list, one hash (the existing record hash), one guard rule per file kind mirrored on `spend.md`, one history reader (trail) shared with `capture`. `main.luau` gets call sites, not logic (zz-arch: pure over texts, reads at the edge).
### Usability
`./zn who <id>` answers "who did what"; the board shows it; `approve` prints what to run next; forgetting `--actor` records `agent:unknown`, never the user as a bot's work, and approval always names the human.

### Edge cases
- Empty or missing `provenance.md`: no rows; `who` falls back to git for old items; audit accepts absence.
- A malformed `ZN_ACTOR`/`--actor`, or one that is `none`/`unknown`/carries the suffix: the command refuses before it changes anything.
- Two approvals: the newest decides; an approval whose hash matches an older design is stale, never valid. `approve` twice on one design: a second row, still current.
- `status prepared` for a raft: each moved issue needs its own current approval; the raft's own document needs none.
- An unfolded item: its `rafted` rows stay as history; the current raft's row is the newest whose `raft=` matches.
- `git var GIT_AUTHOR_IDENT` fails (no identity): the human is `unknown`; `approve` refuses on it.
- A person's trailer (an email that is a commit author's elsewhere) beside an agent's: the agent. Two agent trailers: the last.
- Offline (`PICKMAN_PUBLISH=0` or no origin): `status`, `record`, `fold` and the other published commands refuse as they do now; `approve` and the appends of `new raft` (offline path) and `done` are local.
- `said` text containing `|` or a newline is stored with `|` as `/` and newlines as spaces.
- Two rows identical (same minute, actor, detail) are both kept.
- A compaction or a reused number: `who` reads only the item's current life (trail's rule).

## Open questions (for the user; the design stands on the first answer given in each, each changes one rule)
1. **An agent can run `approve` with words it made up.** Today `--said` is the evidence and the row says `via=agent:…`. Options: (a) keep it (recorded, auditable by reading the chat, not enforced); (b) refuse `approve` in any agent session, so the user must run it in their own terminal (a hard guarantee, one more step for the user in an interactive prep); (c) the command prints a short code only the user sees in their terminal, and an agent session accepts `--code <it>`. I recommend (b) if "the human ran it" must hold, else (a).
2. **Prepared issues with no `approved` row are let through** (grandfathered by absence), which also means an issue whose `status:` line is hand-edited to `prepared` with no approval passes `fold`, `new raft`, `ready` and `audit`. Options: (a) keep it (designed and pinned by approve.spec); (b) refuse them until approved, which means approving every item now prepared (c0260, c0261, c0262, c0264 and the rest) and every promoted spec fixture that seeds a prepared issue (c0116's claims, recombine and plan specs, `ready` specs) gets an approval row: dozens more Overrides; (c) grandfather only the ids prepared when c0263 merges (a frozen list in the repository, written by the raft's last step) and refuse every other prepared issue without a current approval in the four doors and in audit as an error: the strict reading of "Prepared is refused without it", with the fixtures seeding ids outside the list needing the same approval rows as (b) for the specs that drive a door. I recommend (c) if the rule must be a gate, else (a).
