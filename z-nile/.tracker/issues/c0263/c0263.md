# c0263: Ticket provenance

## Problem
User (2026-11-07): "tickets need authors (whose idea, take it from git, then who approved the design, who unblocked a blocked ticket and so on)."

Nothing on a ticket says who had the idea or who decided anything. User decisions are prose lines (`Scope decision (user, …)`), and the design has no explicit human approval. With workers carrying tickets from raft to merge (c0253), the human acts at only a few points, and each of those should be on the record. What should happen:
- **Author:** whose idea it was, taken from git (the author of the ticket's capture commit).
- **Design approved by:** the human who approved the design. Design approval is an explicit human step before `prepared`, since design is a human stage (README, Intent; c0264).
- **Unblocked by:** whoever resolved a block (c0250), each time.
- **And so on:** who confirmed the idea (c0260), who set the rank, who rafted it, and which worker (host, CLI, model) delivered each layer (c0254).
- The board shows them.

Decided with the user (2026-11-08), Q1 storage, "Derive from git, store only the rest": what git knows (the idea's author, who made each status change) is read from history by `./zn who`; only what git cannot tell (a human's approval when a bot pushed it, and decisions) goes in ONE append-only record per ticket. Not five frontmatter keys. (Supersedes the earlier "(c) frontmatter keys" answer of 2026-11-07.)
Decided with the user (2026-11-08), Q2 approve, "Prepared is refused without it": `./zn status <id> prepared` refuses until a human has run `./zn approve <id>`; a redesign after a stop needs a fresh approval; the human is the git author of the approve commit; under the dispatcher the prep gate stops and waits for the user, not auto-merge. (Supersedes the 2026-11-07 reading of "approved the design" as the design reviewer's `Verdict: approve`.)
Decided with the user (2026-11-08), Q3 dependencies, "Land first, define a small record API": c0263 does not depend on c0250, c0260, c0254 or rank; it defines a small record function that those tickets call when their event happens (blocked/unblocked, idea confirmed, rank set, layer delivered); events whose tickets do not exist yet are simply not recorded until they exist.
Decided with the user (2026-11-08), Q4 worker identity, "Read c0254's spend rows": c0263 only reads host, CLI and model that c0254 puts on spend rows, and the dispatcher starts passing them; until c0254 exists, delivered-by records the actor grammar the user chose (`human:<git name>` or `agent:<model, version, effort>`) without host.
Decided with the user (2026-11-08), Q5 readings, "Confirm all": rafted is the rafting PR merge, one entry per ticket layer; delivered is the raft PR merge; unblocked is a `status <id> new` after a stop; `release` is not stamped; an interactive session without `--actor` records `agent:unknown` plus the effort; back-fill uses the git author for engine publishes (no trailer).
Decided with the user (2026-11-07), still standing: the actor is `human:<git name>` or `agent:<model id>` "including agent-model-version-effort": for an agent the model, its version and its effort are recorded (for example `agent:claude-opus-5-5 effort high`), from the dispatcher's `.models.toml` spec or the session's trailer. "rafted" is the rafting PR merge "with layers in case there are multiple tickets": a rafting PR or raft PR can hold several tickets, so provenance is recorded per ticket (a layer per ticket inside the PR), not once per PR; the same holds for "delivered". "yes, back-fill existing done and backlog items from git where possible, in addition to items from now on."

## Non-goals
- Access control: recording who did something is not permission to do it.
- Worker identity on spend rows (c0254); this issue reads it.
- (prep) Frontmatter keys, and a back-fill that writes into old documents: the 2026-11-08 Q1 decision derives instead (below).

## Solution
- Derive what git knows (the author, the committer of each status change) instead of storing it twice. Store only what git can't tell: a human's approval when a bot pushed it, and the decisions.
- `./zn approve <id>` records the design approval; `./zn who <id>` prints the history.

Prep's detail, below the captured bullets. One record per ticket, `provenance.md` in its folder, append-only rows. `./zn who <id>` merges what git says (read at the time, never stored) with the record's rows. Existing done and backlog items need no write: `who` reads their git history, which is how the "back-fill from git where possible" decision is met under Q1. A command that happens in a PR (approve, rafting, done) appends its row in the PR; one that is published (`status <id> new`) appends it in the same published commit.

| event | derived from git | stored in the record | written by |
|---|---|---|---|
| idea | the author of the capture commit (`human:<name> (from git)`) | nothing | nothing |
| status changes | the author and trailer of each `tracker: <id> <status>` commit | nothing | nothing |
| `approved` | nothing (a bot may push it) | the human, the design hash, the user's words | `./zn approve` |
| `unblocked` | (an old item) the author of a `tracker: <id> new` commit | the actor | `status <id> new`; c0250's resolve through the record API |
| `confirmed` (c0260), `ranked` | nothing | the actor | the record API, called by their tickets |
| `rafted` | (an old item) the newest commit that set the ticket's `raft:` | the actor, `raft=<R-id>`, one row per ticket | `new raft`, `fold`, `recombine`, an emergent `new issue --raft` |
| `delivered` | (an old item) the commit that added the ticket under `done/` | the actor, `raft=<R-id>`, `worker=<host/CLI/model>` once c0254 passes it | `done`, one row per member |

**Actor grammar** (the user's, 2026-11-07), the stored form: `human:<name>`, or `agent:<model> effort <level>`; a value read from git ends ` (from git)`; `unknown` when nothing says. `<model>` is `provenance.modelId(text)`: lower-case, each run of non-alphanumeric characters one `-`, trimmed, so `.models.toml`'s `grok-4.7` and git's `Grok 4.7` are both `grok-4-7` and `Claude Opus 5.5` and `claude-opus-5-5` the same; the version is part of the model id; `<level>` is the spec's `effort` or `unknown`.

**The live actor** (a command that records), in this order: `--actor "<value>"`, else `ZN_ACTOR` (only `human:<name>` or `agent:<model> effort <level>`, nothing else, refusing the command before it changes anything; the dispatcher sets `ZN_ACTOR` for each attempt of a step from that attempt's spec, `provenance.agent(spec.model, spec.effort)`); else, when `CLAUDECODE` or `AI_AGENT` is set and non-empty, `agent:unknown effort <CLAUDE_EFFORT|unknown>`; else `human:<name from git var GIT_AUTHOR_IDENT>`, or `unknown` when git has no identity.

## Design

### Behaviour (every outcome the Problem names, each with a Checked criterion)
1. **Author (AC3, AC8).** `./zn who` reads the capture commit by `./zn capture` semantics (the newest `tracker: new` commit listing the id, else the document's first add): its author, `human:<name> (from git)`. Nothing is stored. The author is the human whoever typed the command; a trailer is never read for the idea.
2. **Design approved by (AC4, AC5).**
   - `./zn approve <id> [--said "<the user's words>"]`, in a prep worktree, for an issue that is `preparing` on `origin/main` with `design: ready` here. It computes the design hash (`raftplan.recordHash` over the issue's folder in this worktree: the document without `status:`/`raft:`, `check.sh`, `acceptance/`, the design reviews, refutes and `harvest.md`, the same hash z-raft's `grouped:` record uses; `provenance.md` is not among those files), appends `approved | human:<git name> | design=<hash>; said="<words>"` and commits it as `tracker: approve <id>`, so the human is the git author of that commit. It refuses: in the main checkout; under the dispatcher (`ZN_DISPATCH=1`: a worker cannot approve); with an issue not `preparing` or whose design is not `ready`; in an agent session (`CLAUDECODE` or `AI_AGENT` set) without a non-empty `--said`, because the agent's commit carries the human's git identity and the words are the evidence; with a git identity of `unknown`. In an agent session the row reads `human:<git name>; via=agent:<actor>; said="…"`: the interactive prep that the user already approved in the session records their words through `--said`, then runs `./zn status <id> prepared`.
   - `./zn status <id> prepared` (the carried move) refuses each issue it moves until the newest `approved` row of that issue's `provenance.md` has `design=` equal to the hash of the folder now: `<id> has no current approval: ./zn approve <id>` or `<id> was redesigned since its approval (<old> -> <new>): ./zn approve <id> again`. This covers an issue named alone and a member a raft's move changes (a member already prepared on `origin/main` is taken as it is and needs nothing). A redesign after a stop (`prepared -> preparing`, edits, `prepared`) changes the hash, so it needs a fresh approval; a stop with no edit keeps the hash and the old approval. The refusal is the Q2 rule and no flag skips it.
   - The design reviewer's `Verdict: approve` is no longer the approver; z-design's rounds are unchanged.
3. **Unblocked by (AC5, AC6).** `cmd.status` appends `unblocked | <live actor> | ` to the issue's `provenance.md` in the same published commit as the status line, on every `status <id> new` (a raft's move: each issue it changes, never the raft). `release`'s give-back is not recorded. c0250's resolve will call `provenance.record`/`./zn record <id> unblocked --detail "block=<reason>"` once per resolution ("each time"): rows accumulate, `who` prints all.
4. **Rafted by (AC6).** At each place the engine writes `raft:` to a non-empty value (`new raft` in its published and offline paths, `fold`, `recombine`, an emergent `new issue --raft`) it appends `rafted | <live actor> | raft=<R-id>` to that ticket's `provenance.md`, one row per ticket (a layer per ticket, even when a raft holds several); the row rides the rafting PR with the `raft:` line, so the rafting PR merge is when it lands. `unfold` removes nothing (append-only); `who` shows the newest `rafted` row whose `raft=` is the ticket's current `raft:` and prints earlier ones as history.
5. **Delivered by (AC6).** `done` appends `delivered | <live actor> | raft=<R-id>[; worker=<$ZN_WORKER>]` to each member's `provenance.md` before it moves them to `done/`, one row per member, riding the raft PR; under zz-rules' Merging the agent that ran `done` merges its own PR, and the squash commit's `Co-Authored-By` agrees. Until c0254 the dispatcher sets no `ZN_WORKER`, so the row has the actor only; c0254 passes the worker host/CLI/model through that variable (or `--detail`). The row is made before the merge, so where the user merges the run PR it still names the delivering agent: a limit, stated.
6. **Record API for the other tickets (AC6).** `provenance.record(text, event, actor, detail)` (pure: returns the new `provenance.md` text) and `./zn record <id> <event> [--actor A] [--detail "k=v"]` (appends in this worktree and commits it, `tracker: record <id> <event>`; or, for `unblocked`, `confirmed` and `ranked` on a backlog issue not in a worktree's PR, publishes the append). The closed event list is `approved, unblocked, confirmed, ranked, rafted, delivered`; `approved` only through `approve`; any other name is refused. c0250, c0260, c0254 and the rank ticket call it when their event happens; events of tickets that do not exist are not recorded.
7. **`./zn who <id>` (AC8).** Prints one line per event, oldest first: `<when>  <event>  <actor>  <detail>  (git | record)`: the derived entries (idea; each status change with the author of its `tracker: <id> <status>` commit, its trailer's agent when it has one; for an item with no stored `rafted`/`delivered`/`unblocked` row, the git fallbacks of the table) and the stored rows. A commit's actor is `agent:<modelId> effort unknown (from git)` when it carries a `Co-Authored-By`/`Co-authored-by` trailer whose email is not the email of any commit author in the log (a person is whoever commits), else `human:<author> (from git)`; the engine's own `tracker: <id> <status>` publishes carry no trailer, so a give-back an agent ran reads as the human git shows (Q5, stated). It is read-only, so it may run in the main checkout. Existing done and backlog items work with no write.
8. **The board shows them (AC9).** `board.luau` reads each item's derived and stored entries once per build (one git-log pass for the whole board, not one per item; `provenance.history`), puts them on the `Issue` model as `provenance: { Entry }`, and the item view lists them under a "Provenance" heading in `who`'s order. c0265 (work heartbeat, prepared) also changes `board.luau` (`board.withVerdicts`) and claim stamps: this issue adds a model field and one view section and touches neither; the executor of the later of the two merges the other's `board.luau` change.
9. **The dispatcher (AC7).** The `prep` gate is never passed by the dispatcher: `dispatch.luau`'s gate takes the merge branch only for `raft`; a prep PR stops (exit 4) with `the prep PR #n waits for the user: a design is approved by a human (./zn approve <id>), then merged`. `auto_merge` keeps accepting `prep` as a name (so no config breaks) but it has no effect; `.models.toml` drops it. A dispatched z-design step ends at an open PR with `design: ready` and status `preparing`; it never runs `approve` or `status prepared` (both refuse under `ZN_DISPATCH`). The user then runs `./zn approve <id>` and `./zn status <id> prepared` in the prep worktree, commits, pushes and merges.
10. **Where the writes may land (AC6).** Three guards read a document and must now let `provenance.md` through: the publish validator accepts an issue's `provenance.md` create or append only (rows after the old rows byte for byte, the ledger form), like `spend.md`; the dispatcher's rafting gate accepts, beside the `raft:` line, the same file appended with `rafted` rows only; `./zn land`'s `captureScope` accepts the append of a `confirmed` row to a backlog draft issue's `provenance.md` (c0260's capture). `audit` reports a `provenance.md` that does not parse, has an unknown event, a bad actor or numbering, or sits in a raft's folder.

### Scalability
One small file per ticket, appended; `who` and the board read the git log once per run (0.6 s for the whole history, E2), not once per item; audit parses a file per item that has one.
### Maintainability
One module, one event list, one hash (the existing record hash), one guard rule per file kind mirrored on `spend.md`. `main.luau` gets call sites, not logic (zz-arch: pure over texts, reads at the edge).
### Usability
`./zn who <id>` answers "who did what"; the board shows it; `approve` prints what to run next; forgetting `--actor` records `agent:unknown`, never the user as a bot's work, and approval always names the human.

### Edge cases
- Empty or missing `provenance.md`: no rows; `who` falls back to git for old items; audit accepts absence.
- A malformed `ZN_ACTOR`/`--actor`, or one that is `none`/`unknown`/carries the suffix: the command refuses before it changes anything.
- Two approvals: the newest decides; an approval whose hash matches an older design is stale, never valid.
- `approve` twice on the same design: a second row (append-only), same hash, still current.
- `status prepared` for a raft: each moved issue needs its own current approval; the raft's own document needs none.
- An item whose `raft:` was unfolded: its `rafted` rows stay as history; the current raft's row is the newest whose `raft=` matches.
- `git var GIT_AUTHOR_IDENT` fails (no identity): the human is `unknown`; `approve` refuses on it.
- A person's trailer (an email that is a commit author's elsewhere) beside an agent's: the agent. Two agent trailers: the last.
- Offline (`PICKMAN_PUBLISH=0`): appends are local edits, as status is.
- `said` text containing `|` or a newline is stored with `|` as `/` and newlines as spaces.
