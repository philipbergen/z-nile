# c0263: Ticket provenance

## Problem
User (2026-11-07): "tickets need authors (whose idea, take it from git, then who approved the design, who unblocked a blocked ticket and so on)."

Nothing on a ticket says who had the idea or who decided anything. User decisions are prose lines (`Scope decision (user, …)`), and the design has no explicit human approval. With workers carrying tickets from raft to merge (c0253), the human acts at only a few points, and each of those should be on the record. What should happen:
- **Author:** whose idea it was, taken from git (the author of the ticket's capture commit).
- **Design approved by:** the human who approved the design. Design approval is an explicit human step before `prepared`, since design is a human stage (README, Intent; c0264).
- **Unblocked by:** whoever resolved a block (c0250), each time.
- **And so on:** who confirmed the idea (c0260), who set the rank, who rafted it, and which worker (host, CLI, model) delivered each layer (c0254).
- The board shows them.

Decided with the user (2026-11-08), Q1 storage, "Derive from git, store only the rest": what git knows (the idea's author, who made each status change) is read from history by `./zn who`; only what git cannot tell (a human's approval when a bot pushed it, and decisions) goes in ONE append-only record per ticket. Not five frontmatter keys. (Supersedes the earlier "(c) frontmatter keys" answer of 2026-11-07.)
Decided with the user (2026-11-08), Q2 approve, "Prepared is refused without it": `./zn status <id> prepared` refuses until a human has run `./zn approve <id>`; a redesign after a stop needs a fresh approval; the human is the git author of the approve commit; under the dispatcher the prep gate stops and waits for the user, not auto-merge. (Supersedes the 2026-11-07 reading of "approved the design" as the design reviewer's `Verdict: approve`.)
Decided with the user (2026-11-08), Q3 dependencies, "Land first, define a small record API": c0263 does not depend on c0250, c0260, c0254 or rank; it defines a small record function that those tickets call when their event happens (blocked/unblocked, idea confirmed, rank set, layer delivered); events whose tickets do not exist yet are simply not recorded until they exist.
Decided with the user (2026-11-08), Q4 worker identity, "Read c0254's spend rows": c0263 only reads host, CLI and model that c0254 puts on spend rows, and the dispatcher starts passing them; until c0254 exists, delivered-by records the actor grammar the user chose (`human:<git name>` or `agent:<model, version, effort>`) without host.
Decided with the user (2026-11-08), Q5 readings, "Confirm all": rafted is the rafting PR merge, one entry per ticket layer; delivered is the raft PR merge; unblocked is a `status <id> new` after a stop; `release` is not stamped; an interactive session without `--actor` records `agent:unknown` plus the effort; back-fill uses the git author for engine publishes (no trailer).
Decided with the user (2026-11-08), approve and agents, "Refuse in any agent session": `./zn approve <id>` is refused in any agent session; "a human ran it must be true, not just reported". The `--said` evidence path is gone.
Decided with the user (2026-11-08), the existing prepared issues, "Grandfather those prepared now": a frozen list of the issue ids that are prepared when c0263 merges passes without an `approved` row; any other prepared issue without an approval is refused as an error (fold, new raft, ready, raft-plan, audit); a hand-edited `status: prepared` no longer slips through.
Decided with the user (2026-11-07), still standing: the actor is `human:<git name>` or `agent:<model id>` "including agent-model-version-effort": for an agent the model, its version and its effort are recorded (for example `agent:claude-opus-5-5 effort high`), from the dispatcher's `.models.toml` spec or the session's trailer. "rafted" is the rafting PR merge "with layers in case there are multiple tickets": a rafting PR or raft PR can hold several tickets, so provenance is recorded per ticket (a layer per ticket inside the PR), not once per PR; the same holds for "delivered". "yes, back-fill existing done and backlog items from git where possible, in addition to items from now on."
Scope decision (user, 2026-11-08): "Split it and prototype first, like c0265" (c0263 keeps the record: provenance.md, ./zn record, the append-only publish rule, audit, the union of two writers; ./zn who and deriving from git moved to c0280, the unblocked/rafted/delivered rows to c0282, ./zn approve and the prepared gate with the frozen list and the dispatcher's prep gate to c0283, the board to c0284; one raft, delivered a layer at a time in depends_on order).

## Non-goals
- Access control: recording who did something is not permission to do it.
- Worker identity on spend rows (c0254); c0280 reads it.
- `./zn who`, deriving the idea's author and the status changes from git, the merge entry and the worker: c0280.
- The `unblocked` row on `status <id> new`, the `rafted` rows of `new raft`/`fold`/`recombine`/an emergent issue and the `delivered` rows of `done`, with `ZN_ACTOR`/`ZN_VIA` per dispatcher attempt and the rafting gate's allowance: c0282.
- `./zn approve`, the refusal of `status <id> prepared` without it, the refusal in any agent session, the frozen grandfather list and the dispatcher's prep gate: c0283.
- The board's provenance section: c0284.
- (prep) Frontmatter keys, and a back-fill that writes into old documents: the 2026-11-08 Q1 decision derives instead (c0280).

## Solution
- Derive what git knows (the author, the committer of each status change) instead of storing it twice. Store only what git can't tell: a human's approval when a bot pushed it, and the decisions.
- `./zn approve <id>` records the design approval; `./zn who <id>` prints the history.

Prep's detail, below the captured bullets. One record per ticket, `provenance.md` in its folder (a raft's folder too, for events on a raft), append-only rows with no row numbers (so two appends merge). This issue is the layer that holds the record itself; the layers above it write rows and read them (c0280 to c0284, one raft, in `depends_on` order): `who` merges what git says (read at the time, never stored) with the record's rows; `approve`, the lifecycle commands and the dispatcher append rows; the board shows them. A row written in a PR rides the PR; one that is published is built from `origin/main`'s file; the engine's own merges union the file when both sides appended (Behaviour 5).

**The record file** (`provenance.md`, written by `provenance.render`, read by `provenance.parse`): a header line `# Provenance: <id>`, a blank line, the table header `| when | event | actor | detail |` and its separator `|---|---|---|---|`, then one line per event, `| <when> | <event> | <actor> | <detail> |`. `<when>` is `YYYY-MM-DD HH:MM` in UTC; `<actor>` is the stored grammar below without the ` (from git)` suffix; `<detail>` is `key=value` parts joined by `; `, empty when there is none (the cell is then a single space: `|  |`), with `|` written `/` and newlines written as spaces. Events (closed list): `approved`, `unblocked`, `confirmed`, `ranked`, `rafted`, `delivered`. Example:
```
# Provenance: c0263

| when | event | actor | detail |
|---|---|---|---|
| 2026-11-08 09:00 | approved | human:Philip Bergen | design=1a2b3c4d5e6f; said="yes, approved" |
| 2026-11-08 09:30 | rafted | agent:claude-opus-5-5 effort high | raft=R0100; via=dispatch:raft-plan |
```

**Actor grammar** (the user's, 2026-11-07), the stored form: `human:<name>`, or `agent:<model> effort <level>`; a value read from git ends ` (from git)` (` (from git, first add)` for an idea taken from a first add; c0280 produces these); `unknown` when nothing says. `<model>` is `provenance.modelId(text)`: lower-case, each run of non-alphanumeric characters one `-`, trimmed, so `.models.toml`'s `grok-4.7` and git's `Grok 4.7` are both `grok-4-7`; the version is part of the model id; `<level>` is the spec's `effort` or `unknown`.

**The live actor** (a command that records), in this order: `--actor "<value>"`, else `ZN_ACTOR` (only `human:<name>` or `agent:<model> effort <level>`, nothing else, refusing the command before it changes anything; c0282 makes the dispatcher set it), else, when `CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID` or `ZN_DISPATCH` is set and non-empty (`provenance.hint`), `agent:unknown effort <CLAUDE_EFFORT|unknown>`; else `human:<name from git var GIT_AUTHOR_IDENT>`, or `unknown` when git has no identity.

## Design

### Behaviour (every outcome this layer owns, each with a Checked criterion)
1. **The record file and its pure module (AC1, AC2).** `provenance.md` in an item's folder (an issue's or a raft's, in the backlog, `active/` or `done/`); `z-nile/engine/provenance.luau` is the only code that reads or writes its text (format in the Solution). **`parse` reads exactly the grammar and refuses everything else, naming the line**: line 1 `# Provenance: <id>`, line 2 empty, line 3 the table header, line 4 its separator, then one line per row of exactly four cells (a `|` cannot be inside a cell), one final newline; a row with a fifth cell, no leading bar, an indentation, a prose line, a blank line, a missing final newline, an unknown event or a bad actor is refused, and no line is ever skipped (`parsers-refuse-ambiguity`: design-review-005 F13 and 008 F2 were both about a line filter that kept the rest). `render` is the inverse of `parse` (an empty detail is the row `|  |` and round-trips), and `record` appends one row (`|` in a detail is written `/`, a newline a space), refusing an event outside the list and an actor that is not a live form. `isValid` is the stored grammar (`human:<name>`, `agent:<modelId> effort <level>`, `unknown`, each with the optional ` (from git)` / ` (from git, first add)` suffix); `isLive` is the form a command may record (no suffix, no `unknown`, no `none`); `modelId` gives one spelling per model; `hint(env)` is the one definition of an agent session for every layer (`CLAUDECODE` for Claude Code, `AI_AGENT`, `CURSOR_AGENT` for the `agent` CLI, `GROK_SESSION_ID` for the `grok` CLI, or `ZN_DISPATCH` for a dispatched step, set and non-empty; the effort is `CLAUDE_EFFORT`), so c0283's refusal of `approve` calls the same function; `resolve` takes the flag, then `ZN_ACTOR`, then the hint, then the git name (`unknown` with no identity) and refuses a given value that is not live.
2. **`./zn record <id> <event> [--actor A] [--detail k=v]` (AC3).** It calls `refuseStale()` and publishes one appended row, built from `origin/main`'s file (`read` of the publish builder, never the worktree's), in one commit `tracker: <id> record <event>`, and then merges `origin/main` (`mergeOrigin`). **Which events on which item**: a backlog issue or raft takes `unblocked`, `confirmed` and `ranked` (`provenance.PUBLISHED`); an active issue or raft (a worker blocks while it holds a raft: c0250 blocks whole rafts) takes `unblocked` only; a done item takes none (its record is written in a pull request, never published). It refuses every other event name, an actor that is not live, an id that is not on `origin/main`, the main checkout and an offline repository (`PICKMAN_PUBLISH=0` or no origin, as `spend` does), each before it publishes anything. c0250 (unblock), c0260 (confirm) and the rank ticket call it when their event happens (Q3 of the Problem); c0282 and c0283 write `rafted`, `delivered` and `approved` themselves, in a PR. **The live actor** (`liveActor`, the adapter) reads `--actor`, `ZN_ACTOR`, `CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID`, `ZN_DISPATCH`, `CLAUDE_EFFORT` and `git var GIT_AUTHOR_IDENT`, and hands them to `provenance.hint` and `provenance.resolve`; the record cases drive each source on its own through `./zn record` (E5, run: a Claude Code session sets `CLAUDECODE`, `CLAUDE_EFFORT` and `AI_AGENT`; the `agent` CLI (cursor-agent) starts its shell tools with `CURSOR_AGENT=1`, read from its installed bundle; the `grok` CLI's tool shells carry `GROK_SESSION_ID` and `GROK_AGENT`, probed by running `grok -p` once, bounded by `./zn run --time 150`, with the Claude variables unset; `GROK_AGENT` is also a setting a user may export, so only `GROK_SESSION_ID` counts; a dispatched step, which any CLI runs under, counts through `ZN_DISPATCH`).
3. **Where a published write may land (AC4).** `publish.allowed` learns the name `provenance.md` (in an issue's or a raft's folder, one level, like `spend.md`); the validator in `publish.commit` accepts a `provenance.md` as a create or an append only (`provenance.publishProblem`: it parses, its header names the folder's id, every old row is unchanged in all four cells and in place, at least one row is new), only when the item's document is on `origin/main`, and only when every new row's event is published (`unblocked`, `confirmed`, `ranked`); in `active/` (an issue or a raft) only `unblocked` rows, and in `done/` none. An `approved`, `rafted` or `delivered` row is never published: it is written in a PR. The direct-push rule for a document stays "only `status:`" (`c0053/publish.spec:167` pins the substring `status: line`).
4. **`audit` (AC5).** `audit.run` reports, as an `error` of kind `provenance`, a `provenance.md` that does not parse, has an unknown event or a bad actor, or whose header names another id than its folder's; absence is fine, and a raft's record is fine.
5. **Two writers, one file (AC6).** The record is written by published commits on `main` and by commits a PR carries, so two appends between merges conflict in git (E8). Every `git merge` of `origin/main` the engine makes (`mergeOrigin`, so `sync`, `record` and the other published commands; `raftingStart`, so `fold`, `recombine` and `new raft`; `land`) goes through one function, `mergeRef(ref)`, and `remap`'s own merge settles records by the same routine (`planRecords`). **Records are settled by item id, never by git's pairing of files.** Git pairs small, templated files across ids and across folder moves (E14), so it can neither be trusted to report the records that changed nor to keep a row with its own item. The steps of `mergeRef`:
   - *Refuse first*, saying so (a refusal aborts nothing and says nothing was aborted): a cherry-pick, a revert or a rebase in progress, and a merge in progress of a branch `ref` does not contain (`MERGE_HEAD` is not an ancestor of `ref`). Not ours to finish or abort.
   - *Finish a hand merge*: a merge in progress of `ref` or of an older commit of it (a hand merge that has only records left; `origin/main` moves about once a minute here, so equality with the tip would make the documented way through fail) is settled and committed as it is, and is never aborted by us; then `ref` is merged on top by the ordinary path. When that second merge stops, only it is aborted and the message says the hand merge was committed.
   - *Merge* with `--no-commit`. A fast-forward, an up-to-date merge or a refusal by git to start needs nothing more.
   - *Collect the ids* of every record either side changed since the merge base (`git diff --name-only --no-renames <base> HEAD` and `<base> MERGE_HEAD`, old and new paths alike, ours first), then the unmerged ones. A record is a `provenance.md` in an item's own folder, by the one layout publish and audit use (`publish.itemPath`: `<root>/(issues|rafts)/[active/|done/]<id>/provenance.md`), read with one addition: a raft's folder under `rafts/retired/` (where `recombine` moves a retired raft on its branch while its record may still be published into; publishing into `retired/` stays refused by `publish.allowed`). An id-named folder deeper in an item's folder, such as c0263's own `experiments/split/<id>/`, is not a record. Any other unmerged path stops the merge.
   - *Stop across a compaction* (`provenance.compactionProblem(base map, our map, their map, ...)`): a side whose `z-nile/compaction.txt` differs from the merge base's has reused ids, so an id may name another item on the other side. The merge stops, naming `./zn remap` (on the compaction's own branch, compact again on the current `origin/main`), when a side compacted and the other side changed a record (so when both compacted, their numberings possibly differing, any changed record stops it). A side that compacted and changed records while the other changed none is safe: every record is the compacted side's.
   - *Settle each id* (`provenance.settle`, pure, over the record of that id at `HEAD`, `MERGE_HEAD` and the base, found with `provenance.locate` over `git ls-tree` wherever each commit keeps the item's folder; the same id in two places in one commit stops): neither side changed it, keep; one side changed it, that side's version (a deletion included; a one-sided edit of an old row is taken, because a `renumber` rewrites ids in records main never touched); both deleted it, delete; both changed it, `union`; **changed on one side and absent on the other** (the id changed: a `renumber` or a compaction), **or a side that did not only append when both changed it, or a record that does not parse, stop**.
   - *Write, never over uncommitted work*: the settled text is written through the index (`hash-object -w`, `update-index --cacheinfo`, `checkout-index -f`: no half-written file for an abort to miss) beside the item's one document in the merged tree (found by `<id>/<id>.md`, in a retired raft's folder too; no document, or two, stops), and only when it differs from the merged index's entry there (git leaves a path it did not touch alone, and so do we: an uncommitted row in a record survives a sync). A path the merge did not leave unmerged that has uncommitted changes (or is untracked) and that we would have to write or remove stops the merge, naming it: commit or stash it. Every other path of that id's record is removed with `git rm -f` (which also removes the folder it empties: a folder left behind made the engine see the item twice). A path still unmerged after all that stops, and the merge is committed with `git commit --no-edit` (the message git prepared).
   - *A stop aborts the merge we started* (no `MERGE_HEAD`, the tree as it was, the message naming the item and why), and so does any error: the body runs in a `pcall`.
   Same id, different path is the folder-move case: the record is found wherever the folder went, so it follows its item whichever side moved it (`ready` to `active/`, `done` to `done/`, `stop` back) and however git paired the files; no git option is used for it, because `merge.directoryRenames=true` would also carry every other file added in the folder (a review file in a raft folder `stop` moved) silently along, where today the sync stops, and the record case pins that stop. The union orders the rows base first, then the target branch's (`origin/main`'s) new rows, then ours, minus ours that equal one of theirs taken as a multiset: after a sync `origin/main`'s record is still a prefix of the PR's, which a gate that compares them needs (c0282's rafting gate); `git merge-file --union` puts ours first and is not used. **`remap`** merges `origin/main` against a remapped base with `git merge-tree`, which maps the base and the branch onto the new ids, so the id does name the same item there and no compaction guard is needed. When its conflicts (if any) are all records, `settleRemapRecords` settles the ids of every record either side changed since the remapped base, clean merges included, in the index (`read-tree`, `hash-object`, `update-index`, `write-tree`, then the index is put back to HEAD; the worktree is never touched; a kill in between leaves a staged state that `git reset` clears: a temporary `GIT_INDEX_FILE` was not used because the repository guards refuse that variable, `tooling/repo-fence`); any other conflict, or a record that cannot be settled, stops as it always did, with the message `tooling/remap-once` pins. **When a sync stops**, the message says whether anything was aborted and how to go on, and zz-rules (Provenance) says it once: for a conflict in another file, `git merge origin/main`, resolve every conflict except `provenance.md`, `git add` the files, and run `./zn sync` again, which finishes that merge and unites the records; the refusals, the compaction stop and the id-change stop give only their own way through, and a refusal never advises `git merge --continue` while paths are unmerged. After a `remap` stop, merge by hand (its base is from before the compaction, so `./zn sync` would stop on the compaction, and `remap` refuses a second run). **Limit, stated.** `renumber` rewrites an id in old rows and headers on a branch, and it is the routine fix for an id collision: a sync after one stops at the id (changed on one side and absent on the other, or a changed old row when both sides changed the record) and names `./zn remap` or the row; the branch's record is merged by hand, under the new id. A compaction on main is the same stop, and `./zn remap` is the way through (it settles the records).
6. **`trail`** stops counting `provenance.md` as an item's document (`trail.isDoc`), or a record added to a folder would change what `trail.read` takes for the item's life (`./zn capture`, and c0280's `who`).
7. **Docs (AC7).** zz-rules (a Provenance section, the item layout, the direct-push exception, the merge instruction) name `provenance.md`, `./zn record`, `--actor`/`ZN_ACTOR`, the session variables and the union through `./zn sync` with the hand way through; the README names `provenance.md` and `./zn record` and points to zz-rules, Provenance, for the actor options, the session variables and the merge (the README line says so); the other layers add their own commands to the same text.

### Interfaces
`z-nile/engine/provenance.luau` (new; pure; requires no module; strict):
```
type Hint = { agent: boolean, effort: string? }
type Row = { when: string, event: string, actor: string, detail: string }
provenance.EVENTS: { "approved", "unblocked", "confirmed", "ranked", "rafted", "delivered" }
provenance.PUBLISHED: { "unblocked", "confirmed", "ranked" }      -- what ./zn record may publish
provenance.modelId(text: string): string
provenance.human(name: string): string
provenance.agent(model: string, effort: string?): string        -- "agent:<modelId> effort <effort|unknown>"
provenance.isValid(value: string): boolean                       -- the stored grammar, with the optional " (from git)"
provenance.isLive(value: string): boolean                        -- human:<name> or agent:<model> effort <level>, no suffix
provenance.hint(env: { [string]: string? }): Hint                   -- the one agent-session test: CLAUDECODE, AI_AGENT, CURSOR_AGENT, GROK_SESSION_ID or ZN_DISPATCH set and non-empty; effort = CLAUDE_EFFORT
provenance.resolve(flag: string?, env: string?, hint: Hint, gitName: string?): (string?, string?)
provenance.parse(text: string): ({ Row }?, string?)              -- exactly the grammar; refuses anything else, naming the line
provenance.render(id: string, rows: { Row }): string
provenance.record(text: string?, id: string, event: string, actor: string, detail: string, now: string): (string?, string?)
provenance.appendOnly(old: string?, new: string, id: string): string?     -- every cell of every old row unchanged, in place
provenance.publishProblem(old: string?, new: string, id: string, allowed: { string }): string?  -- appendOnly + the new rows' events
provenance.union(base: string?, ours: string, theirs: string): (string?, string?)  -- the base's rows, theirs' new rows, then ours' new rows minus theirs' (a multiset); nil and why when a side does not parse or does not extend the base
provenance.settle(common: string?, ours: string?, theirs: string?): ("keep" | "write" | "remove")?, string?, string?  -- what a merge does with one item's record: keep (neither side changed it), write the text (one side changed it, or the union of both), remove (the changing side, or both, deleted it); nil, nil, why to stop (an id changed, a side did not only append, an unparsable record)
provenance.compactionProblem(baseMap: string?, oursMap: string?, theirsMap: string?, oursChanged: boolean, theirsChanged: boolean): string?  -- the reason to stop when a side numbers items differently from the base and a record changed on the other side
provenance.locate(paths: { string }, id: string): (string?, string?)   -- the id's record among the item-record paths of one commit; nil and why for two
provenance.problems(path: string, text: string): { string }      -- audit
```
Later layers add to this module (`fromTrailer`, `fromCommit`, `select`, `merge`, `workerOf` in c0280; `approval`, `approvalProblem`, `exemptParse`, `exemptRender` in c0283) without changing what is above. Callers in this layer: `main.luau` (`cmd.record`, `mergeRef`, `liveActor`), `publish.luau`, `audit.luau`, `trail.luau` (`isDoc`).

### The split
Pure and unit-tested: all of `provenance.luau`. Adapters (thin): `main.luau` reads `git var GIT_AUTHOR_IDENT`, the environment and the files, runs git, and hands texts to the pure functions. Each wiring is checked through its caller (AC3 to AC6), not only the pure function, because an unwired caller passes every pure case and breaks publish, audit or the merge.

### Where the new file bites (each place read, not assumed)
- **`publish` direct-push rule**: one branch for `provenance.md` beside `spend.md`'s; a document's rule is unchanged.
- **`trail.isDoc`**: Behaviour 6.
- **Merges of `origin/main`**: Behaviour 5; the three direct `git merge` calls of `main.luau` (`mergeOrigin`, `raftingStart`, `land`) now call `mergeRef`; `sync` in the main checkout is a fast-forward; `remap`'s own `merge-tree` merge settles records through `settleRemapRecords`. (`git grep -nE 'git merge origin/main|merge origin/main' -- 'z-nile/engine/*.luau'` finds the texts that name it.)
- **`raftplan.recordHash`** lists design files by name; `provenance.md` is not one, so rows appended later never change the hash. No change.
- **Existing records**: none exist (no row is written until a later layer lands), so nothing migrates; `audit` accepts absence.

### Overlaps with siblings (named, not touched)
c0280 (who), c0282 (lifecycle rows), c0283 (approval gate), c0284 (board) build on this module and this merge; each prototypes on `proto-c0263-raft`'s shape. **c0265** (work heartbeat) and **R0083** (c0118) change `board.luau`, which this layer does not touch. **c0250** (blocked; blocks whole rafts, hence a record in a raft's folder), **c0260** (confirmation), **c0254** (worker identity), the rank ticket: they call `./zn record`; none is a dependency (Q3).

### Scalability
One small file per ticket, appended; the union reads three blobs of one file; audit parses a file per item that has one.
### Maintainability
One module, one event list, one guard rule per file kind mirrored on `spend.md`, one merge function for every merge of `origin/main`. `main.luau` gets call sites, not logic (zz-arch: pure over texts, reads at the edge).
### Usability
`./zn record` names the events it takes when it refuses one; forgetting `--actor` records `agent:unknown` in an agent session, never the user as a bot's work; a conflicting record is united by `./zn sync` with no hand work.

### Edge cases
- A missing `provenance.md`: no rows; audit accepts absence. An empty file is not a record: `parse` and audit refuse it.
- A malformed `ZN_ACTOR`/`--actor`, or one that is `none`/`unknown`/carries the suffix: the command refuses before it changes anything.
- Two rows identical (same minute, actor, detail) are both kept; the union keeps a row repeated in the base repeated, and a row both sides appended once.
- A `|` or a newline in a detail is stored as `/` or a space.
- `git var GIT_AUTHOR_IDENT` fails (no identity): the human is `unknown`.
- Offline (`PICKMAN_PUBLISH=0` or no origin): `record` refuses as `spend` does.
- A merge that conflicts in the record and in a document aborts and leaves the tree as it was; so does one where a side's record does not parse or edited a row of the shared version (the message names the row), one where an id changed on either side, one that crosses a compaction with records changed on both sides, an item whose record or document sits in two places, and a path left unmerged.
- Both sides deleted a record: it is deleted. A record only one side changed: that side's, whichever path git paired it with.
- A merge, cherry-pick, revert or rebase in progress when `mergeRef` is called: refused (a merge of the very `origin/main` is finished, never aborted).
- `renumber` and `compact` rewrite ids in old rows and headers on a branch: Behaviour 5, Limit.
