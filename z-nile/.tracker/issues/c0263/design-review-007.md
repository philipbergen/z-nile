### F1 [high] The board reads history through another reader than `who`: no compaction cut and no `raftAt`, so for the back-filled items its entries differ from `who`'s, against AC9's "equals"; the board case looks only at c0010, which needs neither
Where: Behaviour 8 ("one `git log` … parsed once by a single `trail.parse` call …, the commits bucketed by item, then `trail.life` per item"); the table's `rafted` row ("`raftAt`, one `git show` per commit that touches the document, `who` only"); Behaviour 1 / AC3 (`who` reads `trail.read`); AC9 ("the decoded `board-data` equals `who`'s entries, in order"); `acceptance/who.spec.luau:225-268` (only c0010); c0263.md:140 (`people` "from the same pass over the same log")
Evidence:
- `trail.read` applies the compaction cut after `trail.life` (`trail.luau:359-363`, `trail.since(lived, start, … cuts[c.sha] …)`); Behaviour 8 names `trail.life` only. A probe over every issue of the real tree (both readers on the same `git log`): `84 of 251 items have a compaction cut`, and for 7 of them `trail.capture` picks another commit, so the board's idea differs from `who`'s. For example `c0060: idea read=05b058ea "R0043: z-nile 2, the tracker moves into z-nile …" life=94c053a9 "R0010: Foundation (#1)"`; the same holds for c0010, c0040, c0041, c0050, c0070 and c0080.
- The board has no `raftAt`, because the Design gives it to `who` only. A probe of the prototype's `select` on who.spec's c0050 life gives `who rafted: human:Bob (from git)` with `raftAt` and `board rafted (no raftAt): none` without it. So every item rafted before c0263 lands, which is every done item and the whole back-fill, has a rafter in `who` and none on the board.
- who.spec's board case checks c0010 only, whose rafter is a stored row and whose life has no cut. A board built as Behaviour 8 says passes it. The case also leaves out `when`, so a board whose dates differ from `who`'s passes too (006 F6 asked for it).
- `people`: c0263.md:140 says both take it "from the same pass over the same log", Scalability says `who` reads one item's trail, and the refute-006 answer ("one `git log --format=%ae` over the whole log") is not in the document.
Critique: the Design states two readers of one history and a criterion that says they agree, and the sequestered case cannot tell them apart. "The board shows them" is a captured outcome, and for the back-filled items the board would show something else, or less. The tempting fix (give the board its own `raftAt` pass and its own cut) leaves two copies of the rules for the next rule to drift in.
Consequences: one edge function serves both. It is built from one `git log` pass in trail's format, one `trail.cuts(head)` call, one `%ae` set and one `raft:`-value pass, and gives each item its life (cut applied), `people` and `raftAt`. `who` calls it for one item (its folders), and the board calls it for all. The board's `raftAt` then comes from one more pass (for example `git log -U0 --no-renames --format=@@%H -G'^raft:' -- <roots>`, parsing each document's `+raft:` line per sha; E2 measured a `-U0` pass of the roots at 0.6 s), not from a `git show` per commit. The Interfaces gain that function, and AC9 can only be true through it.
Recommendation: specify the shared edge function (name, signature, the four inputs it reads once) in Interfaces and Behaviours 1, 7 and 8, and say that `who` and `board.build` both call it. Extend who.spec's board case to compare, for c0010, c0050 (rafter Bob, from `raftAt`) and an item whose life a compaction cuts (a fixture commit that changes `z-nile/compaction.txt` and the document together, as `trail.cuts` reads it), every field of every entry (`when` included) against `./zn who <id>`'s lines parsed back. Add Rules rows "the board's life ignores the compaction cut" and "the board has no `raftAt`", killed by those items, and a `who` case for the compaction cut (AC3 names it; today's row is reasoned with no case).
Lesson: zz-arch/one-reader-per-format

### F5 [medium] The union is unspecified for repeated rows: the prototype's set de-duplication drops one of two identical rows the Edge cases keep, and main's record is then no longer a prefix
Where: Behaviour 11 ("base first, then the target branch's (`origin/main`'s) new rows, then ours"); Edge cases ("Two rows identical (same minute, actor, detail) are both kept"; "`approve` twice on one design: a second row"); `acceptance/provenance.spec.luau:162-175`
Evidence: a probe of the prototype's `union` on a base holding the same `approved` row twice (one `approve` run twice in a minute), with ours appending `rafted` and theirs `ranked`, prints `base rows 2`, `united rows 3` and `appendOnly(theirs, united): row 2 differs from origin/main: rows are only appended`. The prototype keys every row of base, theirs and ours into one `seen` set, so a duplicate of the base collapses. After such a sync, the rafting gate refuses the PR. If the PR is a raft PR, its squash deletes a row of main. The pure cases have no repeated row, so this union passes them. The case that does exist (`union(one, ours, ours) == ours`, :174) needs the opposite: identical rows on both sides collapse.
Recommendation: define the union in Interfaces. The base's rows are kept positionally (the common prefix). Theirs' new rows are theirs after that prefix. Ours' new rows are ours after that prefix, minus theirs' new rows taken as a multiset (each match removes one). Add pure cases: a base with two identical rows (all of them kept, and `appendOnly(theirs, united)` nil), and the same row appended on both sides with one more row on ours (that row once, the extra one after it).
