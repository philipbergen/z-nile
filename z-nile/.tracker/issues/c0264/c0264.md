# c0264: README states z-nile's intent

## Problem
User (2026-11-07): "BTW please update the readme with all this so that we capture what the intent of znile is."

`z-nile/README.md` describes where z-nile is headed ("How it should work", c0259), but it does not say what z-nile is *for*. It also lacks the workflow the user set out on 2026-11-07, quoted in full under "The ask" below. What should happen:
- A new **Intent** section near the top states what z-nile is for:
  - All human interaction moves up to the idea and design stages.
  - Workers carry everything from there to merge.
  - Cost stays low: sharp, expensive models for every final review, cheap and fast ones on the way there, the cheapest when waiting.
- "How it should work" describes, each labelled *captured* with its ticket:
  - **The worker (c0253):** a person starts any CLI (kimi, agy, claude, grok, agent, deepseek) and runs `z-work`. The agent picks up a raft and stays with it all the way to merge, delivering it as a PR stack, one ticket at a time, each worked to completion before the next.
  - **When a raft ends, the worker moves on.** When the raft's last layer merges, or it is blocked and released, the worker clears its context and picks up the next raft.
  - Blocked (c0250), with who unblocked it.
  - The capture interview and idea review (c0260), then z-design as it is today.
  - Model tiers (c0261).
  - The full-force final review with its limited view and redo (c0262).
  - Rank and the lost-first order (c0249, c0265).
  - Provenance (c0263).
  - The board app's rank order and drag and drop (c0257).
- The roadmap table and the diagram gain the new tickets.

### The ask, verbatim (every message, 2026-11-07)
> "I want this Z-NILE system to work in the following way, manually start any cli (kimi, agy, claude, grok, agent, deepseek) run a command, z-work. That command will make this agent pick up a raft and move it forward. The goal is to move all human interaction up to the idea and design stages and then have these workers carry it all the way. we want the agent instances to stay with a particular raft all the way to merge. Only if it is blocked would it let go, at which case it marks the raft blocked and clears its context and grabs the next raft. We need a concept of blocked, we also need better z-ticket command that really challenges the idea and writes it out both the verbatim given by the user and each question asked and its answer and then with all that kept on the ticket write out a clean fully formed idea and reviews that in a clean adversarial agent to make sure that the written out idea actuall corresponds to what the user did, then confirm the idea as it now stands with the user. Then z-design takes over (as it stands today), writing acceptance tests as code and a design and reviewing back and forth. BTW please update the readme with all this so that we capture what the intent of znile is. We want to be economical so we want to use sharp expensive models for all final reviews but we only need a cheaper and faster model on the way there. Be smart about it across different providers (agent and grok are 4.6 high for cheap 4.7 xhigh for expensive not much point in getting more granular). Use cheap haiku or composer models or similar when waiting for things, don't orchestrate and wait on expensive models, keep it cheap. We are missing a final full force review where we take the original ask and the design and the implementation and final adversarial check that the design covers the idea and tha tthe implementation delivers the design. We need a priority for tickets, and tickets need authors (whose idea, take it from git, then who approved the design, who unblocked a blocked ticket and so on). I want a model where a raft of multiple tickets is deliveered as a PR stack and where each ticket is worked on to completion before the next can be picked up and if we can stay in teh same worker for it all so that context remains that would be great."

> "We need a rank field that if unset is lowest rank and falls back to ticket number (always a stable sort order), we want the z-nile ui in omarchy to reflect this and we want drag and drop reordering. But anything that is in progress but lost (we need agents to update a heartbeat on a ticket every 5 minutes pushed to main) is higher than anything that is not yet started, even if a human went and started the thing witout updating rank. We also recognize depends on to ensure that we work arouind rank when something is blocked. when making rafts we should ask for rank, unset is valid."

> "Also explicitly state that a worker clears itself and picks up the next raft whenever a raft is merged."

> "The final full fiorce revieq should be fed a limited view of the tickets so that it looks at it only on its merits as given and not with the broader context of all the compromise on the way. It should be clear if we stayed on course and there should be a redo if not"

## Design

**How it should work** keeps every sub-section c0259 wrote, and their legend and labels, and changes them as follows:
- The diagram gains the capture interview and design approval at the engineer end. At the worker end it gains `z-work`, lost-first claiming, one ticket at a time with the full-force review, and the two "clear context" edges: raft merged, and raft released when blocked. It keeps the words "engineer end" and "worker end" (c0259 AC4). - **Two ends, one stack:** the worker end is any CLI running `z-work`, by hand or headless.

It no longer says design runs with no human, which would contradict Intent and c0263 (review 001 F2).
- **The worker** runs cheap. It never orchestrates on an expensive model, and its waiting, for a gate, CI or a review it handed to a sharp model, runs on the wait tier, as the user said "don't orchestrate and wait on expensive models" (review 001 F3).
