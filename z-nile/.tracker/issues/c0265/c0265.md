# c0265: Work heartbeat and lost items

## Problem
User (2026-11-07): "anything that is in progress but lost (we need agents to update a heartbeat on a ticket every 5 minutes pushed to main) is higher than anything that is not yet started, even if a human went and started the thing witout updating rank."

A claim today is a status stamp pushed to `main`, and it stays forever: when the agent holding it dies (a crash, a closed terminal, a lost host), nothing can tell, and the item sits claimed with no one working it. What should happen:
- An agent working on a ticket or raft updates a **heartbeat** on it every 5 minutes, pushed to `main`, so every host and the board see it.
- An item that is in progress (claimed or started) whose heartbeat is stale is **lost**.
- Lost work comes before anything not yet started in the order (c0249), whatever its rank and even if a human started it without updating the rank. The next worker resumes it.
- A worker that takes over lost work does so as a normal claim, and the takeover is recorded (c0263).

Decided with the user (2026-11-07): "three beats" (the stale limit is 900 s, three beats of 300 s).
Decided with the user (2026-11-07): "ok" (lost work is listed first in `./zn lost` and at the top of `./zn status`; a lost `preparing` claim can be taken over directly; the skills say to take lost work first; the README's Order puts lost before rank; the fuller dispatch refusal stays out unless needed).
Decided with the user (2026-11-07): "flatline" (a claim with no beat is flatlined: lost, judged from its landing time against the 900 s limit).
Decided with the user (2026-11-07): "a" (a claim with an open pull request, a dispatcher gate or a `questions.md` is parked: never lost, shown `[parked]`).
Decided with the user (2026-11-07): "refuse" (the old claimant's carried `status prepared` is refused once the claim's stamp has changed).
Decided with the user (2026-11-07): "ok" (takeover branch handling: a taker continues from the old agent's pushed branch where one exists, else starts fresh; a lost rafting claim the same way, members following).
Decided with the user (2026-11-07): "yes it's not specific we need to come up with a good method" (the capture's "pushed to main" does not fix the storage; the method is chosen on its merits, below).

## Non-goals
- The rank order itself (c0249), which reads the heartbeat.
- Several hosts racing for one item (c0254).
- Moved by the user's scope decision, each in its own issue of the same raft (layers 2 to 5, in `depends_on` order): **c0274** the takeover of a lost claim (`status <id> preparing` on a lost claim, the atomic branch swap, the claim memory and `--adopt`, the old owner's refusal and its notice, the takeover recorded in the claim commit's subject, `stop` recording the lost stamp); **c0275** the automatic beats (the first beat on every claim path, the autobeat of every `./zn` command in a worktree, the tick of long commands, the dispatcher's beats, the branch drops at a claim's end); **c0276** the board's verdicts; **c0277** discard and recover worktrees (`worktree --takeover`, numbered copies, the discard guard, the lookup).
- Until c0275 lands a claim gets no beat by itself: whoever works it runs `./zn beat <id>` or `./zn beat <id> --watch` (the skills say so). Until c0274 lands a lost claim is taken over by hand as today (`status <id> new`, then `preparing`; `stop` then `ready` for a raft).

## Solution
- How often the beats land on `main` matters: one commit per 5 minutes per worker is a lot of history. Design weighs a heartbeat ref (`refs/zn/heartbeat/<id>`) or one small file updated in place against plain commits, and puts the choice to the user.
- The time after which a heartbeat is stale is set at design (for example 15 minutes, three missed beats).
- `./zn beat <id>`, and a beat built into z-work's loop (c0253) and into long `./zn` commands.
- Design decision (the user's heartbeat-branch idea, made to work in prep): a claim (`preparing-…` on an issue or a raft, `active-…` on a readied raft) is a lease proved by a **heartbeat branch** `hb/<claim stamp>` on origin: one commit with `main`'s tree and tip, replaced by every beat (a force-with-lease push), never a commit on `main`. A claim whose newest beat (else its landing time) is older than 900 s is stale; unless an open pull request, a dispatcher gate or a `questions.md` names it (parked), it is lost. This issue (the core layer) writes `./zn beat`, reads the verdicts for `./zn lost` and the `./zn status` markers (lost claims first), and tells the skills to take lost work first; the takeover, the automatic beats, the board and the worktree discard are the sibling layers named in Non-goals.

## Design
This is layer 1 of the raft that delivers the work heartbeat (c0265, then c0274, c0275, c0276, c0277 in `depends_on` order). It builds the heartbeat branch, the one command that writes it, and the verdicts everything else reads. It was prototyped on branch `proto-c0265-raft` (scratch, never landed; the later layers prototype on top of it) and every spec below passes on it.

### Chore checklist (z-design/checklists/chore.md)
- **No behaviour change** for players: none of this touches `pickman/src/` or any game. For tooling: every existing `./zn` command behaves as it did, except that `./zn status` (the list) appends a marker to a claim line that has a verdict worth showing and prints lost claims first, and gains one hb-branch fetch (and one `gh pr list` only when a claim is stale). The unmarked lines are pinned by `c0053/commands-claim` (list text `c0240 preparing`, `f0300 new remote-only`).
- **Overrides**: see Regression guard (the prototype's affected run decides).
- **Existing work**: on the day this lands every existing claim has no beat, so every claim older than 900 s reads lost (flatline, the user's word) until its owner runs `./zn beat <id>` (core `beat` beats whatever stamp `main` shows, so no adoption is needed). The executor lists those claims in the PR. A prep or raft mid-flight is not otherwise affected: nothing in this layer refuses or rewrites a claim. Sequestered `check.sh` files are untouched.
- **Shared state**: `main` is only read (`git fetch origin main`, `git show origin/main:…`, one `git log -S` per claim). The only writes are pushes of `refs/heads/hb/*` branches and a local fetch into `refs/zn/hb-seen/*`; nothing tracked, no index, HEAD, branch or config of the checkout changes, so `beat` runs in the main checkout and in any worktree.
- **Restated rules**: zz-rules (a Heartbeat bullet and its command-table row), z-design, z-raft, z-run and zz-execute (the loop and "take `./zn lost` first"), the README (Order, Roadmap), `SETUP.md` (NTP) and the usage text change with it, and `check.sh` AC5 pins each by phrase.
- **Moves**: none.
- **Guards**: `beat` asks `guarded(true)` before its first network call and refuses in a protected checkout; `lost` asks it first too and reads nothing there; `./zn status` already refuses there (`publishing()`), before any fetch. Reads fail safe: unknown is never lost (zz-arch rule 7).

### Assumptions to veto
- **Basis of "flatline" (the user's single word)**: a claim that never had a beat is judged lost from the time it landed, so on the day this lands every existing claim older than 900 s reads lost until its owner beats it. Said plainly in the PR.
- **"Deleted when the heartbeat drops" (the user, 2026-11-08)**: in this layer a heartbeat branch is deleted by the **pruner** (the next beat of anyone deletes the branch of a stamp no claim holds once it is older than the limit, with a lease on the sha seen); a lost claim's branch is kept as evidence. The commands that end a claim (`status <id> new`, `stop`, `done`) dropping their own branch immediately, and the takeover's atomic swap, are c0275's and c0274's; until they land the pruner is the only deleter. Say so if you wanted the drops in this layer.
- **Everything about taking work over** (reading the user's "ok", "refuse" and 2026-11-08 words) is c0274 and c0277's; here lost work is only found, listed and ordered first.

### Where a beat lives: the heartbeat branch (decided with the user, 2026-11-08)
The capture says "pushed to `main`, so every host and the board see it" and itself warns that one commit per 5 minutes per worker is a lot of history. The user: not a commit on `main`; perhaps a PR label, a title timestamp or a comment; or a commit on a heartbeat branch deleted when the heartbeat drops, and a takeover deletes it and creates a new one so the old owner learns it lost the claim. Constraints established in prep: no churn or conflicts on `main`; works for a claim with no PR yet (every prep claim precedes its PR); works with the dispatched agent's token and the `z-nile/bin` wrappers; one cheap read for every beat; nothing written in the main checkout; visible from other hosts; and the user's: a takeover must tell the old owner it lost the claim when it comes back.

| method | no churn on main | claim with no PR | agent token and wrappers | one cheap read | main checkout untouched | other hosts | old owner learns it lost |
|---|---|---|---|---|---|---|---|
| **heartbeat branch `hb/<stamp>`, one replaced commit, force-with-lease (chosen)** | yes | yes | a branch push passes `decidePush` (only `main` is judged); the agent token unproven (U1, fallback: the dispatcher pushes) | one `git fetch` of `refs/heads/hb/*` into `refs/zn/hb-seen/*` (0.8 s, E10) | yes | yes | **yes, at the push**: the server rejects a lease on a branch that was replaced or deleted (E10) |
| `refs/zn/hb/<stamp>/<epoch>` refs (the earlier design) | yes | yes | the same | one `ls-remote` | yes | yes | only with the same lease: the namespace was never the difference |
| PR label, PR title timestamp or PR comment (the user's) | yes | **no**: a prep claim has no PR | a comment and `gh pr edit` are allowed by the wrapper | one call per PR | yes | yes | no lease: an edit cannot be conditional |
| commits to `main` | **no** | yes | needs the direct-push exception widened | a fetch | no | yes | no |
| repo variables / commit statuses | yes | yes | need permissions the wrapper refuses | one call | yes | yes | no lease |
| git notes ref | yes | yes | a notes push passes `decidePush` | a fetch | yes | yes | no lease; notes merges conflict between workers |

The branch is the user's idea and it works: E10 ran it on the real origin (create, replace with a right lease, rejected with a stale lease, delete with a lease, create-only with an empty lease, a beat to a deleted branch rejected). The branch is chosen because it is the user's, it is visible in GitHub (the capture's "every host and the board see it"), and every cost it adds is cosmetic: `git fetch` creates `origin/hb/*` tracking branches in each clone, and GitHub may show a "recent pushes" banner (not verifiable here). `./zn busy` stays silent because the beat commit has **`main`'s tree and `main`'s tip as its parent** (E11); an orphan or empty-tree commit would list as a busy branch changing every project root (E12; mutant E1 below). A branch push triggers no workflow (`deploy.yml` runs on `main` and pull requests).

**The lease.** The branch name carries the claim stamp, so the lease is the claim: a re-claim has a new stamp and a new branch, and a dead claim's branch never keeps its successor alive. A beat is `git push --force-with-lease=<branch>:<sha seen> origin <commit>:<branch>` (`--force-with-lease=<branch>:` creates only when absent). When the push is rejected, any failure is followed by a re-read of `main` and of the branches and `heartbeat.rejected` decides: `lost` (the item no longer shows this stamp: taken over, or the claim ended), `retry` on the sha now there, or `create`; the beat tries at most twice. What is **said** (`beat: <id>: <git's message>` on stderr): a failure whose git message does not contain `(stale info)`, the text git prints for a lease rejection (E10), which a co-beater of the same claim causes harmlessly and which therefore retries silently. **A create-only write** (no branch when read) can race a takeover or a give-back between the beat's reads and its push, so after any create-only success the beat re-reads `main` and, when the stamp changed, deletes what it created (lease on its own sha) and reports the loss. The beats are read **before** `main`, so a branch a taker created after the beat read its list is never judged unclaimed by the beat's own pruning.

### The beat (pure module `z-nile/engine/heartbeat.luau`, no I/O, no clock)
```
export type Beat = { stamp: string, epoch: number, ref: string, sha: string }
export type Entry = { ref: string, sha: string, subject: string }          -- one per branch under the prefix, as the single read returns it
export type Claim = { id: string, state: string, stamp: string, since: number?, match: { string } } -- since: epoch the claim landed; match: the ids a PR may name
export type Verdict = { id: string, state: string, stamp: string, silent: number, kind: string } -- live | stale | unknown | parked | lost
export type Pr = { title: string, head: string }
export type Push = { write: { ref: string, subject: string, lease: string }?, delete: { { ref: string, lease: string } } }
heartbeat.PREFIX = "refs/heads/hb/"   INTERVAL = 300   STALE = 900   SKEW = 300
heartbeat.branch(stamp): string                                         -- "refs/heads/hb/<stamp>"
heartbeat.subject(stamp, epoch): string                                 -- "hb <stamp> <epoch>"
heartbeat.parse(entries: {Entry}): ({Beat}, {string})                   -- beats, and a problem (with its cure) per branch under the prefix that is not one
heartbeat.setting(env, name, default): number                           -- ZN_BEAT_EVERY, ZN_NET_SECONDS: only inside a spec run, positive whole numbers
heartbeat.clock(env, real): number                                      -- ZN_NOW only when env.PICKMAN_FENCE_SPECS == "1"
heartbeat.judge(claims, beats, now, stale?): {Verdict}                  -- live | stale | unknown
heartbeat.settle(verdicts, parked: {[string]: boolean}?): {Verdict}     -- stale -> parked | lost; nil (unknown) leaves stale
heartbeat.parkedBy(prs: {Pr}, claims, runStates: {[string]: boolean}?): {[string]: boolean} -- per STAMP: a PR (or run state) naming any item holding a stamp parks every item holding it; whole ids only
heartbeat.order(verdicts): {Verdict}                                    -- lost first, longest silent first; the rest in input order
heartbeat.plan(stamp, epoch, beats, claimed, now): Push                 -- replace the claim's branch (lease: the sha seen, "" to create); never backwards; delete long-unclaimed branches with their leases
heartbeat.rejected(stamp, originStamp, beats): { action, lease?, why? } -- after a rejected beat: "lost" (ended / taken over), "retry" on the sha there, or "create"
heartbeat.watch(startStamp, originStamp?, now, deadline, every): "beat" | "stop-restamped" | "stop-bound"
```
- **Name.** The lease id is the claim stamp. Items that share a stamp (a raft and its members) share its branch. The epoch is in the commit subject `hb <stamp> <epoch>` (the beat commit has `main`'s tree and tip), so one `git fetch -q --prune origin '+refs/heads/hb/*:refs/zn/hb-seen/*'` and one `git for-each-ref --format='%(refname) %(objectname) %(subject)' refs/zn/hb-seen/` read every beat. `parse` accepts a branch `hb/(preparing|active)-<word>-<word>-<word>` whose subject names the same stamp; any other branch under the prefix is a problem naming it and its cure `git push origin :<ref>` (zz-arch rule 6).
- **What a claim is** (one definition, used by `beat`'s refusal, `judge`'s list and `plan`'s claimed set): an item on `origin/main` whose effective state (`status.effective` with its folder) is `preparing` or `active` and whose stored `status:` carries a stamp. Items in `done/` (about 30 keep `status: active-…`) and `rafts/retired/` are never claims; a derived `preparing` raft with no stored stamp has no lease.
- **Kinds.** `last = max(claim.since, newest beat of the claim's stamp not dated past now + SKEW)` (such a beat is ignored; one up to `SKEW` ahead reads as `now`); `since` is the epoch the claim landed on `main` (`git log -1 --format=%ct -S"status: <stamp>" origin/main -- <doc>`, E4, 18 ms, one call per claimed item; an unreadable one with no beat is kind `unknown`: shown `[stale?]`, never lost; the edge never passes `0`). `silent = max(0, now - last)`; `silent > STALE` is `stale`, otherwise `live` (exactly the limit is live). A never-beaten claim is therefore silent since it landed (flatline). `settle` turns a stale claim into `parked` when `parked[id]`, else `lost`, but only when the parked table was read; `nil` leaves it `stale`, shown `[stale?]`: unknown is never lost (zz-arch rule 7). The lease is per stamp: a raft and its members share one stamp, so a PR that names only `R0061` parks its members too.
- **Parked.** A stamp is parked when an open PR's title or head branch names one of the `match` ids of an item holding it (whole ids: `c0060` does not match `c00600`; a raft's `match` is its own id and its members'), or when a dispatcher run state `.cache/dispatch/<id>/questions.md` exists in the main checkout (`mainRoot()`, wherever the command runs; read through a new six-line `dispatcher.waitsOnUser(root, id)`, so the `.cache` path stays in the dispatcher: `c0077/cache-paths` reviews every `.cache` literal). A dispatcher stopped at a merge gate has an open PR, so the PR rule covers it. The source is one `gh pr list --state open --json title,headRefName --limit 200`, made **lazily**, only when some claim is stale (the common `status` costs nothing extra); a failing `gh` makes the list unknown. **Limit of the user's decision (a)**: a `questions.md` parks only on the host that ran it (another host sees a dispatched prep waiting on the user, with no PR yet, as lost after 15 minutes); nothing is lost until workers run on several hosts (c0254).
- **Order.** `order` is the one definition of "picked first": lost work, longest silent first, then the rest as listed. (c0249's rank reads it.)
- **Plan.** `plan` replaces the claim's branch (lease: the sha seen, `""` when there is none) and lists the branches of stamps no claim holds that are older than `STALE` for best-effort deletion, each with a lease on the sha seen (a young one may be a claim this checkout has not fetched); `write` is nil when the branch already holds this second or a later one (never backwards).

### The engine edge (`z-nile/engine/main.luau`, the one place that reads and writes)
- **Bounded network calls.** Every call the heartbeat makes (`git fetch`, `git push`, `gh pr list`) is made as `<cmd> <subcommand> …` from the checkout's own directory (never `git -C`, so the specs' shims see the subcommand first) through a small perl wrapper that runs it in a process group of its own and kills the group after `heartbeat.setting(env, "ZN_NET_SECONDS", 10)` seconds, which counts as unreadable (`timed out after N s`). The wrapper polls with `waitpid(WNOHANG)`: perl defers a signal handler while a `system` call blocks, so an alarm handler cannot interrupt the call (found by running the proof against the prototype), and the wrapper must not kill its own group (Lune reports a signal-killed child as success).
- **`./zn beat <id> [--watch]`**: asks the guards first (`guarded(true)` then `publishing()`: refuses in a protected checkout with `beat: not beating <id> from a protected checkout …`, before any network call), fetches `origin main`, and refuses (exit 1, naming the item and the rule) an item that is not a claim: `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`, `beat: c0060 is done: no claim to beat`, `beat: c9999 is not on origin/main`. It beats **the stamp `main` shows for the item**: core keeps no claim memory, so the old owner of a taken-over claim that beats again beats the taker's claim (c0274 adds the memory that refuses it, and its `--adopt`). One beat reads the branches (one fetch), then `main`, builds the beat commit (`git commit-tree <origin/main tree> -p <origin/main tip> -m "hb <stamp> <epoch>"`, identity `zn-beat@example.invalid`), and pushes `plan`'s write with its lease and its deletions. It pushes only branches and changes no tracked file, index, HEAD, branch or config of the checkout, so it runs in the main checkout and in any worktree and publishes nothing to `main`. `--watch` repeats it every `INTERVAL` seconds (`ZN_BEAT_EVERY` in a spec run) and **refuses unless `ZN_BOUNDED_DEADLINE` is set to a number** (an epoch second, which `./zn run` exports), i.e. it runs under `./zn run` (`beat --watch must run as ./zn run --time 3600 -- ./zn beat <id> --watch`); each tick re-reads `main` and asks `heartbeat.watch`, and it exits 0 with a message on `stop-restamped` (`<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`) or `stop-bound` (the next tick would pass the bound); a failed tick says `beat: <id>: <git's message>` on stderr and the loop retries at the next tick.
- **`./zn lost`**: one line per lost item, `<id> <state> <minutes>m` (minutes floored), in `heartbeat.order`; a raft's members each get their own line (verdicts are per item, the raft's stamp shared); nothing when none; exit 0. When the beats (the one fetch) or the pull requests cannot be read it says `lost: heartbeats unreadable: <message>` / `lost: pull requests unreadable: <message>` on stderr, prints nothing and exits 1. A malformed beat branch on origin makes every stale claim unknown and is named with its recovery on stderr (`lost: refs/heads/hb/garbage: not a beat (…); clear it with git push origin :refs/heads/hb/garbage`); lost then lists nothing it cannot confirm and exits 0. In a protected checkout (`guarded(true)`, asked **before** `publishing()`) it prints `lost: not read in a protected checkout (no remote is read)` on stderr, nothing on stdout, and reads nothing.
- **`./zn status`** (the list): every line as before, with lost claims first (longest silent first) as `<id> <status> <title> [lost <n>m]`, parked `[parked]` and stale but unconfirmed `[stale?]`. Unreadable beats: the list prints as today with `status: heartbeats unreadable` on stderr; a malformed branch is named on stderr. `status <id>` and every move are unchanged. In a protected checkout `./zn status` refuses exactly as it does today (`publishing()` is false there), before any fetch.
- **`ZN_NOW`, `ZN_BEAT_EVERY`, `ZN_NET_SECONDS`**: honoured only when `PICKMAN_FENCE_SPECS=1`, decided by the pure `heartbeat.clock` and `heartbeat.setting` (the user's "accept"). `SETUP.md` gains one sentence: hosts keep network time (NTP).

### Scalability
`status`/`lost`: one fetch of the hb branches (0.8 s), one `git log -S` per claim and, only when a claim is stale, one `gh pr list`. A beat: one fetch of `main`, one fetch of the hb branches, one `git fetch`-free commit-tree, one push of a one-commit pack per working agent every 5 minutes. A branch push triggers no workflow. Origin holds one branch per live claim, deleted by the pruner once its claim is gone.
### Maintainability
`heartbeat.luau` is the one reader and writer of the heartbeat branch format; the lease id is the existing claim stamp; `./zn work` (c0253) calls `settle` and `order`; the limit and interval are constants; the sibling layers add functions to this module, never a second format.
### Usability
Two commands and three markers, each refusal naming the item and the rule. Until c0275 lands an agent beats by hand or with `--watch`, which the skills say.

## Acceptance criteria

### Checked
- AC1: the pure rules: a beat is the branch hb/<claim stamp> whose commit subject carries the epoch, replaced with a lease on the sha seen (create-only when there is none) and never backwards; a rejected beat learns whether it lost the claim; a claim is stale only strictly past 900 s and a never-beaten claim is silent since it landed; a stamp is parked when a pull request names any item holding it; the clock, the tuning settings and the watch loop's stops are decided; a stale claim is lost only when the pull requests were read and none names it, parked when one does, and stays unknown when they could not be read; lost work is ordered first and longest silent first; and only long-unclaimed branches are listed for deletion, each with its lease
