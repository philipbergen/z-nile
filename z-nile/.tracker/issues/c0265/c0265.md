# c0265: Work heartbeat and lost items

## Problem
User (2026-11-07): "anything that is in progress but lost (we need agents to update a heartbeat on a ticket every 5 minutes pushed to main) is higher than anything that is not yet started, even if a human went and started the thing witout updating rank."

A claim today is a status stamp pushed to `main`, and it stays forever: when the agent holding it dies (a crash, a closed terminal, a lost host), nothing can tell, and the item sits claimed with no one working it. What should happen:
- An agent working on a ticket or raft updates a **heartbeat** on it every 5 minutes, pushed to `main`, so every host and the board see it.
- An item that is in progress (claimed or started) whose heartbeat is stale is **lost**.
- Lost work comes before anything not yet started in the order (c0249), whatever its rank and even if a human started it without updating the rank. The next worker resumes it.
- A worker that takes over lost work does so as a normal claim, and the takeover is recorded (c0263).

Decided with the user (2026-11-07): "three beats" (the stale limit is 900 s, three beats of 300 s).
Decided with the user (2026-11-07): "ok" (lost work is listed first in `./zn lost` and at the top of `./zn status`; a lost `preparing` claim can be taken over directly; the skills say to take lost work first; the README's Order puts lost before rank; the fuller dispatch refusal stays out unless needed).
Decided with the user (2026-11-07): "flatline" (a claim with no beat is flatlined: lost, judged from its landing time against the 900 s limit).
Decided with the user (2026-11-07): "a" (a claim with an open pull request, a dispatcher gate or a `questions.md` is parked: never lost, shown `[parked]`).
Decided with the user (2026-11-07): "refuse" (the old claimant's carried `status prepared` is refused once the claim's stamp has changed).
Decided with the user (2026-11-07): "ok" (takeover branch handling: a taker continues from the old agent's pushed branch where one exists, else starts fresh; a lost rafting claim the same way, members following).
Decided with the user (2026-11-07): "yes it's not specific we need to come up with a good method" (the capture's "pushed to main" does not fix the storage; the method is chosen on its merits, below).
Decided with the user (2026-11-07): "accept" (the clock-skew risk is accepted: machines use NTP; `ZN_NOW` and `ZN_BEAT_EVERY` are honoured only inside spec runs).

## Non-goals
- The rank order itself (c0249), which reads the heartbeat.
- Several hosts racing for one item (c0254).

## Solution
- How often the beats land on `main` matters: one commit per 5 minutes per worker is a lot of history. Design weighs a heartbeat ref (`refs/zn/heartbeat/<id>`) or one small file updated in place against plain commits, and puts the choice to the user.
- The time after which a heartbeat is stale is set at design (for example 15 minutes, three missed beats).
- `./zn beat <id>`, and a beat built into z-work's loop (c0253) and into long `./zn` commands.
- Design decision (this prep, for the user to veto): the choice put to the user is a heartbeat ref (`refs/zn/hb/<claim stamp>/<epoch>` on origin, outside `main`). A claim (`preparing-…` on an issue or a raft, `active-…` on a readied raft) is a lease proved by a beat pushed every 5 minutes; a claim whose newest beat (else its landing time) is older than 900 s is stale; unless an open pull request, a dispatcher gate or a `questions.md` names it (parked), it is lost. `./zn lost` lists lost claims, `./zn status` marks them and lists them first, a lost `preparing` claim is taken over by the next `status <id> preparing`, and the skills tell whoever picks work to take lost work first.

## Design

### Assumptions to veto
- **Basis of "flatline" (Q4)**: the user's single word. Read as: a claim that never had a beat is judged lost from the time it landed, so on the day this lands every existing claim older than 900 s reads lost until its owner beats. The executor lists those claims in the PR, and their owners run `./zn beat <id>` from their worktree (any later `./zn` command there then keeps it alive).
- **Takeover (decided, "ok")**: a taker continues from the old agent's pushed work branch when one exists (`./zn worktree prep-<slug> --from origin/prep-<slug>`), else starts fresh; a lost rafting claim (`preparing-…` on a raft) is taken over by `status <R-id> preparing`, its members following. The refusal of the old claimant's carried move is the user's ("refuse").
- **Limit of decision (a)**: a dispatcher's `questions.md` parks only on the host that ran it (another host sees a dispatched prep waiting on the user, with no PR yet, as lost after 15 minutes). A run state under an R-id parks that raft's stamp. Cost: nothing until workers run on several hosts (c0254).
- **Rename (landed)**: the user's capture rewrote f0265 as this chore, c0265 (PR #258). Its added outcomes are covered: a beat in long `./zn` commands (the outer-command tick; `./zn work` will call the same tick), the takeover recorded in the claim commit subject, and "every host and the board see it" (the board contract above). "Even if a human started it without updating the rank": lost work already comes before not-yet-started work however it was started, so a human-started claim that goes quiet is lost like any other; the part this design cannot see is an item started with **no claim stamp at all** (there is no lease to expire), and the order rule c0249 owns rank. c0266 (classified spec) owns the gate failure that filing features in z-nile's root caused.
- **The one place the user may still veto**: the storage method (below). The user left it open ("we need to come up with a good method") and this design owns the choice.

### Where a beat lives: the method (the user: "we need to come up with a good method"; the one place to veto)
The capture says "pushed to `main`, so every host and the board see it" and itself warns that one commit per 5 minutes per worker is a lot of history. Its intent is: any host and the board can tell, from the shared remote, which in-progress items are alive. Constraints established in prep: no churn or conflicts on `main`; works for a claim with no PR yet (every prep claim precedes its PR); works with the dispatched agent's own token and `z-nile/bin` wrappers; one cheap read for every beat; nothing written in the main checkout; visible from other machines.

| method | no churn/conflict on main | claim with no PR | agent token and wrappers | one cheap read | main checkout untouched | other hosts see it |
|---|---|---|---|---|---|---|
| **ref `refs/zn/hb/<stamp>/<epoch>` on origin (chosen)** | yes | yes | a ref push outside main passes `decidePush` (E1); the agent token unproven (U1, fallback: the dispatcher pushes) | one `ls-remote` (0.65 s), no objects | yes | yes: it is on the shared remote |
| commits to `main` (one file per item, or one file updated in place) | no: 12 pushes an hour per worker, each a fast-forward of `main`, so workers retry against each other; history and the main checkout move every few minutes | yes | needs the direct-push exception widened and the broker | a fetch plus reads | no: `sync` moves it | yes |
| a dedicated heartbeat branch (one file per item, or per-item branches) | yes for `main`, but workers contend on one branch (non-fast-forward retries), or per-item branches fill every branch list, `busy` and the board | yes | branch push allowed | one `ls-remote` for branches, a fetch for file text | yes | yes |
| repository variables (`gh api …/actions/variables`) | yes | yes | writing needs the Actions-variables permission and `z-nile/bin/gh` refuses `gh api` writes but comments (E6) | one call; the store also holds the deploy's place ids | yes | yes |
| PR comments | yes | **no**: nothing to comment on | comments allowed | one call per PR | yes | yes |
| commit statuses/checks on `origin/main`'s sha (`zn/hb/<stamp>`) | yes | yes | needs `statuses:write`; wrapper refuses | one combined-status call (100 contexts max) | yes | yes |
| git notes ref | yes | yes | ref push | fetch the notes | yes | yes, but notes merges conflict between workers |

The ref is the only method that meets every constraint: it is a branch-like name on the shared remote that no branch list shows, it costs one `ls-remote`, and it needs nothing but a `git push`. **How the "beat pushed to main" reading is satisfied:** a beat is pushed to the same shared remote `main` lives on, and every host and the board read it with one `ls-remote` of that remote, so "every host and the board see it" holds; what is not literally true is that the beat is a commit on the `main` branch, and that is the churn the capture warns about, so it serves the capture's intent better. If the user wants beats inside `main` after all, only the edge changes (the pure module is storage-free), at the cost of the churn above.

### The beat (pure module `z-nile/engine/heartbeat.luau`, no I/O, no clock)
```
export type Beat = { stamp: string, epoch: number, ref: string }
export type Claim = { id: string, state: string, stamp: string, since: number?, match: { string } } -- since: epoch the claim landed; match: the ids a PR may name
export type Verdict = { id: string, state: string, stamp: string, silent: number, kind: string } -- live | stale | unknown | parked | lost
export type Pr = { title: string, head: string }
heartbeat.PREFIX = "refs/zn/hb/"   INTERVAL = 300   STALE = 900   SKEW = 300
heartbeat.refName(stamp, epoch): string
heartbeat.parse(refs: {string}): ({Beat}, {string})                     -- beats, and a problem per malformed ref under the prefix
heartbeat.setting(env, name, default): number                       -- ZN_BEAT_EVERY, ZN_NET_SECONDS: only inside a spec run, positive whole numbers
heartbeat.clock(env, real): number                                     -- ZN_NOW only when env.PICKMAN_FENCE_SPECS == "1"
heartbeat.judge(claims, beats, now, stale?): {Verdict}                  -- live | stale
heartbeat.settle(verdicts, parked: {[string]: boolean}?): {Verdict}     -- stale -> parked | lost; nil (unknown) leaves stale
heartbeat.parkedBy(prs: {Pr}, claims, runStates: {[string]: boolean}?): {[string]: boolean} -- per STAMP: a PR (or run state) naming any item holding a stamp parks every item holding it; whole ids only
heartbeat.canTakeOver(kind, judgedStamp, originStamp): boolean          -- lost, for the stamp origin still holds
heartbeat.watch(startStamp, originStamp?, now, deadline, every): "beat" | "stop-restamped" | "stop-bound"
heartbeat.order(verdicts): {Verdict}                                    -- lost first, longest silent first; the rest in input order
heartbeat.plan(stamp, epoch, beats, claimed, now): { write: string?, delete: {string} }
```
- **Name.** The lease id is the claim stamp. Items that share a stamp (a raft and its members) share its beats; a re-claim has a new stamp, so a dead claim's beats never keep its successor alive. The epoch is in the ref name, so one `ls-remote` reads every beat and no object is fetched. `parse` accepts `^refs/zn/hb/(preparing|active)-<word>-<word>-<word>/<digits>$`; any other ref under the prefix is a problem naming the ref and the rule (zz-arch rule 6).
- **What a claim is** (one definition, used by `beat`'s refusal, `judge`'s list and `plan`'s claimed set): an item whose effective state (`status.effective` with its folder) is `preparing` or `active` and whose stored `status:` carries a stamp. Items in `done/` (about 30 keep `status: active-…`) and `rafts/retired/` are never claims; a derived `preparing` raft with no stored stamp has no lease.
- **Kinds.** `last = max(claim.since, newest beat of the claim's stamp not dated past now + SKEW)` (such a beat is ignored; one up to `SKEW` ahead reads as `now`); `since` is the epoch the claim landed on `main` (an unreadable one, `since` nil with no beat, is kind `unknown`: shown `[stale?]`, never lost, takeover refused; the edge never passes `0`) (`git log -1 --format=%ct -S"status: <stamp>" origin/main -- <doc>`, E4, 18 ms, one call per claimed item). `silent = max(0, now - last)`; `silent > STALE` is `stale`, otherwise `live` (exactly the limit is live). A never-beaten claim is therefore silent since it landed (flatline). `settle` turns a stale claim into `parked` when `parked[id]`, else `lost`, but only when the parked table was read; `nil` (the pull requests could not be read) leaves it `stale`, shown `[stale?]`: unknown is never lost (zz-arch rule 7). The lease is per stamp: a raft and its members share one stamp, so a PR that names only `R0061` parks its members too.
- **Parked.** A stamp is parked when an open PR's title or head branch names one of the `match` ids of an item holding it (whole ids: `c0060` does not match `c00600`), or when a dispatcher run state `.cache/dispatch/<id>/questions.md` exists in the main checkout (`mainRoot()`, wherever the command runs: a takeover runs in a worktree). A dispatcher stopped at a merge gate has an open PR, so the PR rule covers it. The cheapest reliable source is one `gh pr list --state open --json title,headRefName --limit 200`, made **lazily**, only when some claim is stale (the common `status` costs nothing extra); a failing `gh` makes the list unknown.
- **Order.** `order` is the one definition of "picked first".
- **Plan.** A beat is one atomic push (`git push --atomic origin <sha>:<refName> :<old>…`) of `plan.write` plus deletions: the older beats of the same stamp, and the beats of a stamp no claim holds only when older than `STALE` (a young unclaimed beat may be a claim this checkout has not fetched). `write` is nil when a beat of the same second exists; a newer beat of the stamp is never deleted.

### The engine edge (`z-nile/engine/main.luau`, the one place that reads and writes)
- **`./zn beat <id> [--watch]`**: fetches `origin main` first (so claims and the claimed set are current), refuses (exit 1, naming the item and the rule) an item that is not a claim: `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`, `beat: c0060 is done: no claim to beat`. It pushes `plan`'s write and deletions with the commit `refs/remotes/origin/main` points at; it pushes only refs (and, from a worktree, writes its ignored throttle entry); it changes no tracked file, index, HEAD, branch or config, so it runs in the main checkout and in any worktree and publishes nothing to `main`. `--watch` repeats it every `INTERVAL` seconds (fetching each tick) and **refuses unless `ZN_BOUNDED_DEADLINE` is set to a number**, i.e. it runs under `./zn run` (`beat --watch must run as ./zn run --time 3600 -- ./zn beat <id> --watch`); each tick asks `heartbeat.watch`, and it exits 0 with a message on `stop-restamped` (claim ended or taken over) or `stop-bound` (the next tick would pass the bound); a failed tick relays git's stderr (`beat: <id>: <git's message>`) and the loop retries at the next tick; `stop-restamped` prints the autobeat's text (`<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`).
- **Automatic beats.** (Never from a protected checkout: the engine's own `guarded(true)` answers, as it does for `reap --auto`, so a nested `./zn lessons` in a `check.sh` or spec flow of the real repository never fetches or pushes; one reader of the fence, its answer fails closed; fixtures are unguarded and still beat.) A `beat` made in a **worktree** writes `.cache/tracker-beats/<id>` there (`<stamp> <epoch>`, ignored); the **main checkout never writes or reads one** (it holds no work: the dispatcher's and `ready`'s beats there are ref pushes only). Every `./zn` command except `beat`, `run`, `reap` and `READ_ONLY` ones first reads the worktree's entries; for each, if origin's stamp for the id differs from the entry's (a takeover, a give-back, a finished item) the entry is deleted and nothing is beaten; else, if the epoch is at least `INTERVAL` old, it beats that item; when it drops an entry it says once on stderr `<id>'s claim was taken over (now <stamp>): stop working it` if another claim now holds the item, or `<id>'s claim ended` if the item is no longer a claim (finished or given back), the same words `--watch` uses. The entry's epoch advances on a **failed** attempt too, so a hung or offline remote costs one bounded attempt per interval and warns once on stderr; a failure never fails the command. Each heartbeat call, made as `git <subcommand> …` from the checkout's own directory (never `git -C`, so the specs' shims see the subcommand first) (fetch, `ls-remote`, `git grep`, push, `gh pr list`) runs in its own process group (as `runner.luau` starts its children) and the group is killed after `heartbeat.setting(env, "ZN_NET_SECONDS", 10)` seconds, which counts as unreadable (`ZN_BEAT_EVERY` and `ZN_NET_SECONDS` are honoured only inside spec runs, by that one pure function). A session that keeps working keeps its claim alive for as long as it runs any `./zn` command in its worktree (`commit`, `spend`, `status`, `check`, `dispatch`…), with no loop and no network call inside the interval. A first beat never fails its claim: it runs after the publish, is best effort, and a failure is said on stderr (`beat: <id>: <message>`) while the claim stands and the command exits 0 (the claim is already on `main`). **The worktree's throttle entry is written whether the first beat succeeded or not** (a failed attempt advances it, as any failed attempt does), so a claim whose first beat failed is still beaten by the worktree's next command after an interval. First beats: `status <id> preparing`, `status <R-id> preparing`, `new raft`, `fold`, `unfold`, `recombine`, `ready` and a legacy `start` beat right after their publish. **Long outer commands** (`check`, `done`, `land`, `dispatch`) start a background tick for as long as they run, in a worktree that holds entries (the capture's "a beat into long `./zn` commands"); a nested `./zn` inside them never beats (`guarded`). The gate script `z-nile/check.sh` run directly is not a `./zn` command and has no tick: a long gate runs under `./zn done`/`land`, or with the `--watch` loop running (the skills say so). A readied raft nobody starts gets its first beat from `ready` and then reads lost 15 minutes later: that is the case "an in-progress item whose worker is gone", and `/z-run` re-adopts it (its worktree writes the entry).
- **Guarded checkouts**: the explicit `./zn beat` and the dispatcher's `zn beat` child run `publishing()` like every other publisher and refuse (naming the rule) when `guarded(true)` says a check protects the checkout; the fence's pre-push hook is the second line, not the first.
- **`./zn lost`**: one line per lost item, `<id> <state> <minutes>m` (minutes floored), in `heartbeat.order`; a raft's members each get their own line (verdicts are per item, the raft's stamp shared); nothing when none; exit 0. When the beats (`ls-remote`) or the pull requests cannot be read it says `lost: heartbeats unreadable: <message>` / `lost: pull requests unreadable: <message>` on stderr, prints nothing and exits 1. A malformed beat ref on origin makes every stale claim unknown (`stale`, shown `[stale?]`, never lost, takeover refused) and is named with its recovery on stderr: `lost: refs/zn/hb/garbage: not a beat (…); clear it with git push origin :refs/zn/hb/garbage`.
- **The board** (the capture's "every host and the board see it"): `buildBoard` (used by `cmd.board` and by `refreshBoard`, which rebuilds `.cache/board.html` after every publish, `land` and main-checkout `sync`) computes the same verdicts as `status` (one `ls-remote`, the lazy `gh pr list`, the same bounded calls) and hands `board.build(root, checkout, verdicts?)` a table `{[id]: {kind, minutes}}`. **Contract:** `board.collect` adds two keys to the item record of a claim whose verdict is not live: `heartbeat` (`"lost"`, `"parked"` or `"stale"`) and `minutes` (silent minutes, floored); live and unclaimed items carry neither key. The model is embedded as sorted-key JSON in `<script id="board-data">` (`board.encode`), the browser script renders a `lost Nm` / `parked` / `stale?` badge beside the id from those keys (rendered text is the page's business; the specs assert the data), and within each bucket `views.*` lists lost items first, longest silent first, then the rest as before. **In a protected checkout the verdict reads are skipped** (for `./zn status` and `./zn lost` too: `./zn status` refuses in a protected checkout exactly as it does today, because `publishing()` is false there, before any fetch; `lost` asks `guarded(true)` **before** `publishing()`, prints `lost: not read in a protected checkout (no remote is read)` on stderr and exits 0 with nothing on stdout) (`guarded(true)`: a `check.sh` or spec flow of the real repository, the gate's `./zn board` runs included): the page is built without verdicts and no remote is read, exactly as today. Unreadable beats or pull requests: no keys beyond what is known (stale), a one-line note, and the page still builds. `refreshBoard` therefore pays the same bounded reads after each publish; that cost is intended, because a board that loses its marks minutes after a rebuild would not be the board the capture asks for. `board.build` without verdicts is unchanged, so `tooling/board.spec` and the promoted board specs are not affected.
- **`./zn status`** (the list): lost claims first (longest silent first), each `<id> <status> <title> [lost <n>m]`; parked `[parked]`, stale but unconfirmed `[stale?]`; every other line and `status <id>` unchanged. Unreadable beats: the list prints as today with `status: heartbeats unreadable` on stderr.
- **Takeover**: `status <id> preparing` (or `<R-id>`) on a `preparing` claim keeps its refusal text (`<id> is preparing on origin/main: cannot move to preparing`, c0053's) with `; claim alive: last heartbeat <n>m ago, limit <m>m` for a live claim, `; claim parked (an open pull request names it)` or `; claim parked (a dispatcher waits on questions.md)` for a parked one, `; no heartbeat verdict: <reason>` when anything was unreadable or malformed (naming the ref and `git push origin :<ref>`, or git's message). Only an explicit lost verdict allows it, and the verdict travels into `setStatus`'s `publish.commit` callback, which calls `heartbeat.canTakeOver(kind, judgedStamp, originStamp)` with the stamp origin holds *at that moment* (a claim restamped since the verdict is refused naming the new stamp: the push is the lock). Inside the callback the stamp-record check comes **before** the member design check (so a raft move whose member is still `design: draft` is refused as "taken over" first). It draws a stamp with `freshStamp("preparing")` (checked against `origin/main`, as `ready` does: issue claims drew with `stamp()` before, a 1.4 % chance today that two live claims share a stamp), beats at once, and that beat's `plan` prunes the old claim's beats after the grace. **The takeover is recorded** (the capture's "recorded (c0263)") in the claim commit's subject, `tracker: <id> preparing (takes over <old stamp>)`, which `git log` and any provenance reader of history see; a normal claim keeps `tracker: <id> preparing`. Every claim publish (`status <id|R-id> preparing`, the takeover included, and z-raft's `new raft`, `fold`, `unfold` and `recombine`; `setStatus` today writes the memory for issues only, so it gains the raft case) records the new stamp in `.cache/tracker-stamp-<id>` of the checkout that made it (a file of its own: `.cache/tracker-claim-<id>` keeps c0116's meaning, "this checkout owns the rafting claim", which `release` and `fold` read; a prep prototype of this rule left c0116/claims and c0053/commands-{claim,prep,start} green, 37 of 37, E8). The carried `status <id> prepared` (the user's "refuse") refuses only when this checkout **remembers** a stamp and it differs from origin's (a checkout with no record passes, as today; a checkout's own re-claim updates its record, so c0053/commands-prep's flow stays green); the taker therefore claims from inside the worktree it will work in, and a rafting taker's `release` and `fold` need `--force`, as after any `status R preparing` today. The refusal reads: `<id>'s claim was taken over (now <stamp>): …`. An `active` claim is taken over as today (`./zn stop`, `/z-run`).
- **`ZN_NOW`, `ZN_BEAT_EVERY`, `ZN_NET_SECONDS`**: honoured only when `PICKMAN_FENCE_SPECS=1`, decided by the pure `heartbeat.clock` and its twin for the other two (the user's "accept"). `SETUP.md` gains one sentence: hosts keep network time (NTP).
- **The dispatcher** (`z-nile/engine/dispatcher.luau`): while a model step runs, every `INTERVAL` it starts `zn beat <id>` for the item the step works (a raft's id for z-raft and z-run), one child at a time, killed after 60 s (E3: a `process.exec` in a `task.spawn` does not stall the supervising loop). A refusal (no claim yet) is ignored; any other failure is written once per step to the run's stderr. Under `ZN_DISPATCH=1` the step starts no loop (the skills say so).
- **Why not `reap`, the sweeper, or `sync`**: they clean local leftovers; a beat leaves nothing local but the throttle file (ignored, under `.cache`).

### The skills
`zz-rules`: a Heartbeat paragraph (the ref, the limit, parked, `beat`, `lost`, takeover, `ZN_NOW`) and its command table rows, and the main-checkout list ("`beat` writes a ref under `refs/zn/hb/` only"). `z-design` (claim step: start `./zn run --time 3600 -- ./zn beat <id> --watch` in the background unless `ZN_DISPATCH=1`; when it reports its bound, restart it, or rely on the automatic beat of every `./zn` command in the worktree; Candidates: take `./zn lost` first, and continue a lost prep from `origin/prep-<slug>`), `z-raft`, `z-run` (each: take `./zn lost` first; z-design: continue a lost prep from the old agent's pushed branch with `./zn worktree prep-<slug> --from origin/prep-<slug>` when it exists, else start fresh; z-run says a lost raft is re-adopted; the same loop for the raft; `z-run` of a lost raft re-adopts it) and `zz-execute` (the loop) gain one bullet each. The README's Order says lost work comes before `rank`, its Roadmap gets `work heartbeat | c0265 | exists`, the usage text lists `beat` and `lost`.

### Scalability
`status`/`lost`: one `ls-remote` and, only when a claim is stale, one `gh pr list`. A beat: one fetch, one `ls-remote`, one `git grep`, one push (no objects) per working agent every 5 minutes; throttled locally so frequent `./zn` commands cost nothing. Refs trigger no workflow (`deploy.yml` runs on `main` and pull requests). Origin holds one ref per live claim.
### Maintainability
`heartbeat.luau` is the one reader and writer of the ref format; the lease id is the existing claim stamp; `./zn work` (c0253) calls `settle` and `order`; the limit and interval are constants.
### Usability
Two commands and four markers, each refusal naming the item and the rule; no agent has to remember to beat (claims, any `./zn` command, the dispatcher, the loop).

### Experiments run now
- **E1 (pass)**: `git push --atomic origin refs/heads/main:refs/zn/hb/<s>/<new> :refs/zn/hb/<s>/<old>` in a local bare origin (`./zn run --time 60 -- bash e1.sh`): 58 ms, no objects; `ls-remote` shows only the new ref; `push --dry-run --porcelain` gives `*`/`-` lines to non-main destinations, which `wrapper.decidePush` passes.
- **E2 (pass)**: `./zn run --time 90 -- git push origin origin/main:refs/zn/probe-c0265/1`-style probe (named `refs/zn/hb/probe-c0265/1` then; U1's probe must use `refs/zn/probe/…`, outside the prefix) accepted and deleted on the real origin with the user's credential; `ls-remote` 0.65 s. Agent token unproven (U1).
