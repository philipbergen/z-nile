# c0265: Work heartbeat and lost items

## Problem
User (2026-11-07): "anything that is in progress but lost (we need agents to update a heartbeat on a ticket every 5 minutes pushed to main) is higher than anything that is not yet started, even if a human went and started the thing witout updating rank."

A claim today is a status stamp pushed to `main`, and it stays forever: when the agent holding it dies (a crash, a closed terminal, a lost host), nothing can tell, and the item sits claimed with no one working it. What should happen:
- An agent working on a ticket or raft updates a **heartbeat** on it every 5 minutes, pushed to `main`, so every host and the board see it.
- An item that is in progress (claimed or started) whose heartbeat is stale is **lost**.
- Lost work comes before anything not yet started in the order (c0249), whatever its rank and even if a human started it without updating the rank. The next worker resumes it.
- A worker that takes over lost work does so as a normal claim, and the takeover is recorded (c0263).

Decided with the user (2026-11-07): "three beats" (the stale limit is 900 s, three beats of 300 s).
Decided with the user (2026-11-07): "ok" (lost work is listed first in `./zn lost` and at the top of `./zn status`; a lost `preparing` claim can be taken over directly; the skills say to take lost work first; the README's Order puts lost before rank; the fuller dispatch refusal stays out unless needed).
Decided with the user (2026-11-07): "flatline" (a claim with no beat is flatlined: lost, judged from its landing time against the 900 s limit).
Decided with the user (2026-11-07): "a" (a claim with an open pull request, a dispatcher gate or a `questions.md` is parked: never lost, shown `[parked]`).
Decided with the user (2026-11-07): "refuse" (the old claimant's carried `status prepared` is refused once the claim's stamp has changed).
Decided with the user (2026-11-07): "ok" (takeover branch handling: a taker continues from the old agent's pushed branch where one exists, else starts fresh; a lost rafting claim the same way, members following).
Decided with the user (2026-11-07): "yes it's not specific we need to come up with a good method" (the capture's "pushed to main" does not fix the storage; the method is chosen on its merits, below).
Decided with the user (2026-11-08): "I don't know where to put the beats, could be a label on the PR that keeps rotating, or a comment or an update to the PR title with a timestamp, it should not be a commit on main but it could be a commit on a heartbeat branch that gets deleted when the heartbeat drops or task completes. If a job is taken over the take over deletes the heartbeat branch and creates a new one, this would tell the process that it lost the ownership if it comes back around. Think it through and come up with a solution that works." (the storage method is reopened and designed below: a heartbeat branch per claim, with the takeover semantics the user describes).
Decided with the user (2026-11-07): "accept" (the clock-skew risk is accepted: machines use NTP; `ZN_NOW` and `ZN_BEAT_EVERY` are honoured only inside spec runs).

## Non-goals
- The rank order itself (c0249), which reads the heartbeat.
- Several hosts racing for one item (c0254).

## Solution
- How often the beats land on `main` matters: one commit per 5 minutes per worker is a lot of history. Design weighs a heartbeat ref (`refs/zn/heartbeat/<id>`) or one small file updated in place against plain commits, and puts the choice to the user.
- The time after which a heartbeat is stale is set at design (for example 15 minutes, three missed beats).
- `./zn beat <id>`, and a beat built into z-work's loop (c0253) and into long `./zn` commands.
- Design decision (the user's heartbeat-branch idea, made to work in prep): a claim (`preparing-…` on an issue or a raft, `active-…` on a readied raft) is a lease proved by a **heartbeat branch** `hb/<claim stamp>` on origin: one commit, replaced by every beat (a beat is a force-with-lease push), never a commit on `main`. The branch is deleted when the heartbeat drops (the claim ends, is given back, or is long unclaimed). A takeover deletes the old owner's branch and creates its own in one atomic push, so the old owner's next beat is rejected by the server and it learns it lost the claim. A claim whose newest beat (else its landing time) is older than 900 s is stale; unless an open pull request, a dispatcher gate or a `questions.md` names it (parked), it is lost. `./zn lost` lists lost claims, `./zn status` marks them and lists them first, a lost `preparing` claim is taken over by the next `status <id> preparing`, and the skills tell whoever picks work to take lost work first.

## Design

### Assumptions to veto
- **Basis of "flatline" (Q4)**: the user's single word. Read as: a claim that never had a beat is judged lost from the time it landed, so on the day this lands every existing claim older than 900 s reads lost until its owner beats. The executor lists those claims in the PR, and their owners run `./zn beat <id>` from their worktree (any later `./zn` command there then keeps it alive).
- **Takeover (decided, "ok")**: a taker continues from the old agent's pushed work branch when one exists (`./zn worktree prep-<slug> --from origin/prep-<slug>`), else starts fresh; a lost rafting claim (`preparing-…` on a raft) is taken over by `status <R-id> preparing`, its members following. The refusal of the old claimant's carried move is the user's ("refuse").
- **Limit of decision (a)**: a dispatcher's `questions.md` parks only on the host that ran it (another host sees a dispatched prep waiting on the user, with no PR yet, as lost after 15 minutes). A run state under an R-id parks that raft's stamp. Cost: nothing until workers run on several hosts (c0254).
- **Rename (landed)**: the user's capture rewrote f0265 as this chore, c0265 (PR #258). Its added outcomes are covered: a beat in long `./zn` commands (the outer-command tick; `./zn work` will call the same tick), the takeover recorded in the claim commit subject, and "every host and the board see it" (the board contract above). "Even if a human started it without updating the rank": lost work already comes before not-yet-started work however it was started, so a human-started claim that goes quiet is lost like any other; the part this design cannot see is an item started with **no claim stamp at all** (there is no lease to expire), and the order rule c0249 owns rank. c0266 (classified spec) owns the gate failure that filing features in z-nile's root caused.
- **Storage method (decided with the user, 2026-11-08)**: the heartbeat branch below. The user's own alternatives (a rotating PR label, a PR title timestamp, a PR comment) fail "a claim with no PR yet" and are kept out; the earlier `refs/zn/hb/*` ref design (rounds 1 to 11) is replaced.

### Where a beat lives: the heartbeat branch (reopened by the user, 2026-11-08)
The capture says "pushed to `main`, so every host and the board see it" and itself warns that one commit per 5 minutes per worker is a lot of history. The user: not a commit on `main`; perhaps a PR label, a title timestamp or a comment; or a commit on a heartbeat branch deleted when the heartbeat drops, and a takeover deletes it and creates a new one so the old owner learns it lost the claim. Constraints established in prep: no churn or conflicts on `main`; works for a claim with no PR yet (every prep claim precedes its PR); works with the dispatched agent's token and the `z-nile/bin` wrappers; one cheap read for every beat; nothing written in the main checkout; visible from other hosts; **and the user's: a takeover must tell the old owner it lost the claim when it comes back.**

| method | no churn on main | claim with no PR | agent token and wrappers | one cheap read | main checkout untouched | other hosts | old owner learns it lost |
|---|---|---|---|---|---|---|---|
| **heartbeat branch `hb/<stamp>`, one replaced commit, force-with-lease (chosen)** | yes | yes | a branch push passes `decidePush` (only `main` is judged); the agent token unproven (U1, fallback: the dispatcher pushes) | one `git fetch` of `refs/heads/hb/*` into `refs/zn/hb-seen/*` (0.8 s, E10) | yes | yes | **yes, at the push**: the server rejects a lease on a branch that was replaced or deleted (E10) |
| `refs/zn/hb/<stamp>/<epoch>` refs (my rounds 1 to 11) | yes | yes | the same | one `ls-remote` | yes | yes | only on the next `./zn` command of the old owner (its stamp check), unless I added the same lease: the namespace was never the difference |
| PR label, PR title timestamp or PR comment (the user's) | yes | **no**: a prep claim has no PR | a comment and `gh pr edit` (label, title) are allowed by the wrapper | one call per PR | yes | yes | no lease: an edit cannot be conditional |
| commits to `main` | **no** | yes | needs the direct-push exception widened | a fetch | no | yes | no |
| repo variables / commit statuses | yes | yes | need permissions the wrapper refuses (it refuses `gh api` writes but comments) | one call | yes | yes | no lease |
| git notes ref | yes | yes | a notes push passes `decidePush` | a fetch | yes | yes | no lease; notes merges conflict between workers |

The branch is the user's idea and it works: E10 ran it on the real origin (create, replace with a right lease, rejected with a stale lease, delete with a lease, create-only with an empty lease, a beat to a deleted branch rejected). The ref namespace could carry the same lease, so it no longer wins on semantics; the branch is chosen because it is the user's, it is visible in GitHub (the capture's "every host and the board see it"), and every cost it adds is cosmetic: `git fetch` creates `origin/hb/*` tracking branches in each clone, and GitHub may show a "recent pushes" banner (not verifiable here). `./zn busy` stays silent because the beat commit has **`main`'s tree and `main`'s tip as its parent** (E11); an orphan or empty-tree commit would list as a busy branch changing every project root (E12). A branch push triggers no workflow (`deploy.yml` runs on `main` and pull requests).

**The lease and ownership.** The branch name carries the claim stamp, and a takeover has a new stamp, so ownership is the pair (stamp on `main`, branch `hb/<stamp>`). **One rule for the lease** (in `heartbeat.plan`, argument `remembered`): the sha this checkout last wrote for that stamp (its throttle entry `<stamp> <epoch> <sha>`), else the sha it just read, else empty (create only if absent); a beat is `git push --force-with-lease=<branch>:<lease> origin <commit>:<branch>`. **A beat is bound to the stamp its holder owns**, never to whatever `main` says now: "my stamp" is the claim memory `.cache/tracker-stamp-<id>` (written by every claim publish and by an adoption). `beat <id>` (explicit, `--watch` and the autobeat alike) beats only that stamp; when `main` shows another stamp or none it refuses with `<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`, exits 1 (the autobeat says it once and carries on), drops the entry and never rewrites the memory. A checkout with no memory (the main checkout, a fresh clone) refuses a bare `beat <id>` (`beat: <id>'s claim is not held by this checkout (use --adopt to take it on)`); `--adopt` is the stated adoption: it beats origin's stamp and writes the memory, and `--adopt --stamp <S>` (the dispatcher's form, with the stamp it read when the step started) refuses when `main` no longer shows `<S>`, so a dispatched step stops beating a claim that was taken over. The takeover, after publishing the new claim stamp on `main`, runs **one atomic push**: delete `hb/<old>` with a lease on the sha it read, create `hb/<new>` create-only. So the old owner's next beat finds its branch gone and its lease rejected (it cannot recreate it); it re-reads and learns the loss as above. **A create-only write** (the branch absent when read, which is also what a beat in a checkout without a remembered sha sees after a takeover) can race a takeover in the window between the beat's main read and its branch read: so after any create-only write the beat re-reads `main`, and when the stamp changed it deletes what it created (lease on its own sha) and reports the loss. Telling a lease rejection from another failure needs no classification: any failed write is followed by a re-read and `heartbeat.rejected` (retry on the sha there, create, or lost); a second failure is a failed tick whose message relays git's stderr. Pruning deletes are separate best-effort pushes (a vanished target never fails the beat). If the rejection came from a co-beater of the same claim (same stamp, another sha) the beat retries once on what is there. An old owner that comes back by a command that does not beat (a plain `status`) learns the same thing from its entry's stamp check.

Every checkout reads into its own shared `refs/zn/hb-seen/*` (a ref-lock contention between two concurrent commands counts as unreadable, retried once as `publish` retries, and fails safe: unknown is never lost). **When the branch is deleted** (the user: "when the heartbeat drops or task completes"): by the command that ends the claim, best effort with a lease on the sha seen and said on failure like a first beat: `status <id> new` (give-back), `stop`, `ready` (it drops the rafting `preparing-…` branch in the same step as the first beat of the new `active-…` stamp), `done`, and the takeover (the old owner's branch). A merge happens on GitHub where no `./zn` runs, so pruning (a branch of an unclaimed stamp older than the limit, by the next beat of anyone) stays as the backstop. A lost claim's branch is kept until its takeover (it is the evidence the claim went quiet). **Taking over a lost `active` claim** (a readied raft) is `./zn stop <R-id>` then `./zn ready <R-id>`: `stop` records the lost stamp in its commit subject (`tracker: stop R0010 (claim <stamp>)`) and drops the old branch, `ready` draws a fresh `active-` stamp with its first beat, so the old z-run session is told by the same rules; z-run says so (a raft that `./zn lost` lists is re-adopted this way, and a parked one is left alone).

**How a "beat pushed to main" reading of the capture is served:** the beat is pushed to the same shared remote `main` lives on, every host and the board read it with one fetch, and it is not a commit on `main`, which is the churn the capture itself warns about and the user excludes.

### The beat (pure module `z-nile/engine/heartbeat.luau`, no I/O, no clock)
```
export type Beat = { stamp: string, epoch: number, ref: string, sha: string }
export type Entry = { ref: string, sha: string, subject: string }          -- one per branch under the prefix, as the single read returns it
export type Claim = { id: string, state: string, stamp: string, since: number?, match: { string } } -- since: epoch the claim landed; match: the ids a PR may name
export type Verdict = { id: string, state: string, stamp: string, silent: number, kind: string } -- live | stale | unknown | parked | lost
export type Pr = { title: string, head: string }
export type Push = { write: { ref: string, subject: string, lease: string }?, delete: { { ref: string, lease: string } } }
heartbeat.PREFIX = "refs/heads/hb/"   INTERVAL = 300   STALE = 900   SKEW = 300
heartbeat.branch(stamp): string                                         -- "refs/heads/hb/<stamp>"
heartbeat.subject(stamp, epoch): string                                 -- "hb <stamp> <epoch>"
heartbeat.parse(entries: {Entry}): ({Beat}, {string})                   -- beats, and a problem (with its cure) per branch under the prefix that is not one
heartbeat.setting(env, name, default): number                           -- ZN_BEAT_EVERY, ZN_NET_SECONDS: only inside a spec run, positive whole numbers
heartbeat.clock(env, real): number                                      -- ZN_NOW only when env.PICKMAN_FENCE_SPECS == "1"
heartbeat.judge(claims, beats, now, stale?): {Verdict}                  -- live | stale | unknown
heartbeat.settle(verdicts, parked: {[string]: boolean}?): {Verdict}     -- stale -> parked | lost; nil (unknown) leaves stale
heartbeat.parkedBy(prs: {Pr}, claims, runStates: {[string]: boolean}?): {[string]: boolean} -- per STAMP: a PR (or run state) naming any item holding a stamp parks every item holding it; whole ids only
heartbeat.canTakeOver(kind, judgedStamp, originStamp): boolean          -- lost, for the stamp origin still holds
heartbeat.watch(startStamp, originStamp?, now, deadline, every): "beat" | "stop-restamped" | "stop-bound"
heartbeat.order(verdicts): {Verdict}                                    -- lost first, longest silent first; the rest in input order
heartbeat.plan(stamp, epoch, beats, claimed, now, remembered?): Push    -- replace the claim's branch (lease: the sha seen, "" to create); never backwards; delete long-unclaimed branches with their leases
heartbeat.takeoverPlan(oldStamp, newStamp, epoch, beats): Push          -- create the taker's branch, delete the old owner's with a lease: one atomic push
heartbeat.rejected(stamp, originStamp, beats): { action, lease?, why? } -- after a rejected beat: "lost" (ended / taken over), "retry" on the sha there, or "create"
```
- **Name.** The lease id is the claim stamp. Items that share a stamp (a raft and its members) share its branch; a re-claim has a new stamp, hence a new branch, so a dead claim's branch never keeps its successor alive. The epoch is in the commit subject `hb <stamp> <epoch>` (the beat commit has `main`'s tree and tip), so one `git fetch -q --prune origin '+refs/heads/hb/*:refs/zn/hb-seen/*'` and one `git for-each-ref --format='%(refname) %(objectname) %(subject)' refs/zn/hb-seen/` read every beat. `parse` accepts a branch `hb/(preparing|active)-<word>-<word>-<word>` whose subject names the same stamp; any other branch under the prefix is a problem naming it and its cure `git push origin :<ref>` (zz-arch rule 6).
- **What a claim is** (one definition, used by `beat`'s refusal, `judge`'s list and `plan`'s claimed set): an item whose effective state (`status.effective` with its folder) is `preparing` or `active` and whose stored `status:` carries a stamp. Items in `done/` (about 30 keep `status: active-…`) and `rafts/retired/` are never claims; a derived `preparing` raft with no stored stamp has no lease.
- **Kinds.** `last = max(claim.since, newest beat of the claim's stamp not dated past now + SKEW)` (such a beat is ignored; one up to `SKEW` ahead reads as `now`); `since` is the epoch the claim landed on `main` (an unreadable one, `since` nil with no beat, is kind `unknown`: shown `[stale?]`, never lost, takeover refused; the edge never passes `0`) (`git log -1 --format=%ct -S"status: <stamp>" origin/main -- <doc>`, E4, 18 ms, one call per claimed item). `silent = max(0, now - last)`; `silent > STALE` is `stale`, otherwise `live` (exactly the limit is live). A never-beaten claim is therefore silent since it landed (flatline). `settle` turns a stale claim into `parked` when `parked[id]`, else `lost`, but only when the parked table was read; `nil` (the pull requests could not be read) leaves it `stale`, shown `[stale?]`: unknown is never lost (zz-arch rule 7). The lease is per stamp: a raft and its members share one stamp, so a PR that names only `R0061` parks its members too.
- **Parked.** A stamp is parked when an open PR's title or head branch names one of the `match` ids of an item holding it (whole ids: `c0060` does not match `c00600`), or when a dispatcher run state `.cache/dispatch/<id>/questions.md` exists in the main checkout (`mainRoot()`, wherever the command runs: a takeover runs in a worktree). A dispatcher stopped at a merge gate has an open PR, so the PR rule covers it. The cheapest reliable source is one `gh pr list --state open --json title,headRefName --limit 200`, made **lazily**, only when some claim is stale (the common `status` costs nothing extra); a failing `gh` makes the list unknown.
- **Order.** `order` is the one definition of "picked first".
- **Plan.** `plan` replaces the claim's branch (the one lease rule above) and lists the branches of stamps no claim holds that are older than `STALE` (a young one may be a claim this checkout has not fetched) for best-effort deletion, each with a lease on the sha seen; `write` is nil when the branch already holds this second or a later one (never backwards). `takeoverPlan` creates the taker's branch and deletes the old owner's with a lease, in one atomic push. `rejected` is what a beat does when its lease was stale (above).

### The engine edge (`z-nile/engine/main.luau`, the one place that reads and writes)
- **`./zn beat <id> [--watch]`**: fetches `origin main` first (so claims and the claimed set are current), refuses (exit 1, naming the item and the rule) an item that is not a claim (checked first), then one that this checkout does not hold or that was taken over (above): `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`, `beat: c0060 is done: no claim to beat`. Before writing it reads the beats (one fetch, above), builds the beat commit (`git commit-tree <origin/main tree> -p <origin/main tip> -m "hb <stamp> <epoch>"`) and pushes `plan`'s write with its lease and its deletions; on a rejection it calls `heartbeat.rejected`. It pushes only branches (and, from a worktree, writes its ignored throttle entry `<stamp> <epoch> <sha>`); it changes no tracked file, index, HEAD, branch or config of the checkout, so it runs in the main checkout and in any worktree and publishes nothing to `main`. `--watch` repeats it every `INTERVAL` seconds (fetching each tick) and **refuses unless `ZN_BOUNDED_DEADLINE` is set to a number**, i.e. it runs under `./zn run` (`beat --watch must run as ./zn run --time 3600 -- ./zn beat <id> --watch`); each tick asks `heartbeat.watch`, and it exits 0 with a message on `stop-restamped` (claim ended or taken over) or `stop-bound` (the next tick would pass the bound); a failed tick relays git's stderr (`beat: <id>: <git's message>`) and the loop retries at the next tick; `stop-restamped` prints the autobeat's text (`<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`).
- **Automatic beats.** (Never from a protected checkout: the engine's own `guarded(true)` answers, as it does for `reap --auto`, so a nested `./zn lessons` in a `check.sh` or spec flow of the real repository never fetches or pushes; one reader of the fence, its answer fails closed; fixtures are unguarded and still beat.) A `beat` made in a **worktree** writes `.cache/tracker-beats/<id>` there (`<stamp> <epoch> <sha>`, ignored); the **main checkout never writes or reads one** (it holds no work: the dispatcher's and `ready`'s beats there are ref pushes only). Every `./zn` command except `beat`, `run`, `reap` and `READ_ONLY` ones first reads the worktree's entries; for each, if origin's stamp for the id differs from the entry's (a takeover, a give-back, a finished item) the entry is deleted and nothing is beaten; else, if the epoch is at least `INTERVAL` old, it beats that item; when it drops an entry it says once on stderr `<id>'s claim was taken over (now <stamp>): stop working it` if another claim now holds the item, or `<id>'s claim ended` if the item is no longer a claim (finished or given back), the same words `--watch` uses. The entry's epoch advances on a **failed** attempt too, so a hung or offline remote costs one bounded attempt per interval and warns once on stderr; a failure never fails the command. Each heartbeat call, made as `git <subcommand> …` from the checkout's own directory (never `git -C`, so the specs' shims see the subcommand first) (fetch, `git grep`, push, `gh pr list`) runs in its own process group (as `runner.luau` starts its children) and the group is killed after `heartbeat.setting(env, "ZN_NET_SECONDS", 10)` seconds, which counts as unreadable (`ZN_BEAT_EVERY` and `ZN_NET_SECONDS` are honoured only inside spec runs, by that one pure function). A session that keeps working keeps its claim alive for as long as it runs any `./zn` command in its worktree (`commit`, `spend`, `status`, `check`, `dispatch`…), with no loop and no network call inside the interval. A first beat never fails its claim: it runs after the publish, is best effort, and a failure is said on stderr (`beat: <id>: <message>`) while the claim stands and the command exits 0 (the claim is already on `main`). **The worktree's throttle entry is written whether the first beat succeeded or not** (a failed attempt advances it, as any failed attempt does), so a claim whose first beat failed is still beaten by the worktree's next command after an interval. First beats: `status <id> preparing`, `status <R-id> preparing`, `new raft`, `fold`, `unfold`, `recombine`, `ready` and a legacy `start` beat right after their publish. **Long outer commands** (`check`, `done`, `land`, `dispatch`) start a background tick for as long as they run, in a worktree that holds entries (the capture's "a beat into long `./zn` commands"); a nested `./zn` inside them never beats (`guarded`). The gate script `z-nile/check.sh` run directly is not a `./zn` command and has no tick: a long gate runs under `./zn done`/`land`, or with the `--watch` loop running (the skills say so). A readied raft nobody starts gets its first beat from `ready` and then reads lost 15 minutes later: that is the case "an in-progress item whose worker is gone", and `/z-run` re-adopts it (its worktree writes the entry).
- **Guarded checkouts**: the explicit `./zn beat` and the dispatcher's `zn beat` child run `publishing()` like every other publisher and refuse (naming the rule) when `guarded(true)` says a check protects the checkout; the fence's pre-push hook is the second line, not the first.
- **`./zn lost`**: one line per lost item, `<id> <state> <minutes>m` (minutes floored), in `heartbeat.order`; a raft's members each get their own line (verdicts are per item, the raft's stamp shared); nothing when none; exit 0. When the beats (the one fetch) or the pull requests cannot be read it says `lost: heartbeats unreadable: <message>` / `lost: pull requests unreadable: <message>` on stderr, prints nothing and exits 1. A malformed beat ref on origin makes every stale claim unknown (`stale`, shown `[stale?]`, never lost, takeover refused) and is named with its recovery on stderr: `lost: refs/heads/hb/garbage: not a beat (…); clear it with git push origin :refs/heads/hb/garbage`.
- **The board** (the capture's "every host and the board see it"): `buildBoard` (used by `cmd.board` and by `refreshBoard`, which rebuilds `.cache/board.html` after every publish, `land` and main-checkout `sync`) computes the same verdicts as `status` (one fetch of the hb branches, the lazy `gh pr list`, the same bounded calls) **only when `guarded(true)` says the checkout is unprotected**, and applies them with a new pure function `board.withVerdicts(model, verdicts): Model` between `board.collect` and `board.render`. **No existing signature changes**: `board.collect` and `board.build` keep their parameters, which matters because the active raft R0083 (c0118, PR #250) gives their third parameter to `facts: Facts?` and its sequestered specs call them that way; c0265 touches neither, so the two merge in `main.luau` and `board.luau` only by position (a conflict the later lander resolves: `buildBoard` composes `collect`/`withVerdicts`/`render` itself instead of calling `build`). **Contract:** `board.withVerdicts` adds two keys to the item record of a claim whose verdict is not live: `heartbeat` (`"lost"`, `"parked"` or `"stale"`) and `minutes` (silent minutes, floored), and reorders each bucket of `views.*` (lost first, longest silent first, then the rest as before); live and unclaimed items carry neither key. The model is embedded as sorted-key JSON in `<script id="board-data">` (`board.encode`), the browser script renders a `lost Nm` / `parked` / `stale?` badge beside the id from those keys (rendered text is the page's business; the specs assert the data). **In a protected checkout the verdict reads are skipped** (for `./zn status` and `./zn lost` too: `./zn status` refuses in a protected checkout exactly as it does today, because `publishing()` is false there, before any fetch; `lost` asks `guarded(true)` **before** `publishing()`, prints `lost: not read in a protected checkout (no remote is read)` on stderr and exits 0 with nothing on stdout; **every heartbeat path, the autobeat and the explicit `beat` included, asks the guard before its first network call**): the page is built without verdicts and no remote is read, exactly as today (the gate's `./zn board` runs included). Unreadable beats or pull requests: no keys beyond what is known (stale), a one-line note, and the page still builds. `refreshBoard` pays the same bounded reads after each publish; that cost is intended, because a board that loses its marks minutes after a rebuild would not be the board the capture asks for. Without verdicts `board.render` is unchanged, so `tooling/board.spec` and the promoted board specs are not affected. Landing order with R0083 is free; the executor reads R0083's `board.luau` first (Phase 1) and tells its lead.
- **`./zn status`** (the list): lost claims first (longest silent first), each `<id> <status> <title> [lost <n>m]`; parked `[parked]`, stale but unconfirmed `[stale?]`; every other line and `status <id>` unchanged. Unreadable beats: the list prints as today with `status: heartbeats unreadable` on stderr.
- **Takeover**: `status <id> preparing` (or `<R-id>`) on a `preparing` claim keeps its refusal text (`<id> is preparing on origin/main: cannot move to preparing`, c0053's) with `; claim alive: last heartbeat <n>m ago, limit <m>m` for a live claim, `; claim parked (an open pull request names it)` or `; claim parked (a dispatcher waits on questions.md)` for a parked one, `; no heartbeat verdict: <reason>` when anything was unreadable or malformed (naming the ref and `git push origin :<ref>`, or git's message). Only an explicit lost verdict allows it, and the verdict travels into `setStatus`'s `publish.commit` callback, which calls `heartbeat.canTakeOver(kind, judgedStamp, originStamp)` with the stamp origin holds *at that moment* (a claim restamped since the verdict is refused naming the new stamp: the push is the lock). Inside the callback the stamp-record check comes **before** the member design check (so a raft move whose member is still `design: draft` is refused as "taken over" first). It draws a stamp with `freshStamp("preparing")` (checked against `origin/main`, as `ready` does: issue claims drew with `stamp()` before, a 1.4 % chance today that two live claims share a stamp), and **in the same step deletes the old owner's branch and creates its own in one atomic push (`heartbeat.takeoverPlan`)**; if that push is rejected because the old owner beat meanwhile, it re-reads and repeats once. **The takeover is recorded** (the capture's "recorded (c0263)") in the claim commit's subject, `tracker: <id> preparing (takes over <old stamp>)`, which `git log` and any provenance reader of history see; a normal claim keeps `tracker: <id> preparing`. Every claim publish (`status <id|R-id> preparing`, the takeover included, and z-raft's `new raft`, `fold`, `unfold` and `recombine`; `setStatus` today writes the memory for issues only, so it gains the raft case) records the new stamp in `.cache/tracker-stamp-<id>` of the checkout that made it (a file of its own: `.cache/tracker-claim-<id>` keeps c0116's meaning, "this checkout owns the rafting claim", which `release` and `fold` read; a prep prototype of this rule left c0116/claims and c0053/commands-{claim,prep,start} green, 37 of 37, E8). The carried `status <id> prepared` (the user's "refuse") refuses only when this checkout **remembers** a stamp and it differs from origin's (a checkout with no record passes, as today; a checkout's own re-claim updates its record, so c0053/commands-prep's flow stays green); the taker therefore claims from inside the worktree it will work in, and a rafting taker's `release` and `fold` need `--force`, as after any `status R preparing` today. The refusal reads: `<id>'s claim was taken over (now <stamp>): …`. An `active` claim is taken over as today (`./zn stop`, `/z-run`).
- **`ZN_NOW`, `ZN_BEAT_EVERY`, `ZN_NET_SECONDS`**: honoured only when `PICKMAN_FENCE_SPECS=1`, decided by the pure `heartbeat.clock` and its twin for the other two (the user's "accept"). `SETUP.md` gains one sentence: hosts keep network time (NTP).
- **The dispatcher** (`z-nile/engine/dispatcher.luau`): while a model step runs, every `INTERVAL` it starts `zn beat <id> --adopt --stamp <S>` for the item the step works (`<S>` is the stamp `main` showed when the step started; a mismatch means the claim was taken over mid-step: the dispatcher stops beating and says so once) (a raft's id for z-raft and z-run), one child at a time, killed after 60 s (E3: a `process.exec` in a `task.spawn` does not stall the supervising loop). A refusal (no claim yet) is ignored; any other failure is written once per step to the run's stderr. Under `ZN_DISPATCH=1` the step starts no loop (the skills say so).
- **Why not `reap`, the sweeper, or `sync`**: they clean local leftovers; a beat leaves nothing local but the throttle file (ignored, under `.cache`).

### The skills
`zz-rules`: a Heartbeat paragraph (the heartbeat branch and its lease, the limit, parked, `beat`, `lost`, takeover, `ZN_NOW`) and its command table rows, and the main-checkout list ("`beat` pushes only `hb/*` branches"). `z-design` (claim step: start `./zn run --time 3600 -- ./zn beat <id> --watch` in the background unless `ZN_DISPATCH=1`; when it reports its bound, restart it in the same worktree (a restart elsewhere needs `--adopt`), or rely on the automatic beat of every `./zn` command in the worktree; Candidates: take `./zn lost` first, and continue a lost prep from `origin/prep-<slug>`), `z-raft`, `z-run` (each: take `./zn lost` first; z-design: continue a lost prep from the old agent's pushed branch with `./zn worktree prep-<slug> --from origin/prep-<slug>` when it exists, else start fresh; z-run says a lost raft is re-adopted; the same loop for the raft; `z-run` of a lost raft re-adopts it) and `zz-execute` (the loop) gain one bullet each. The README's Order says lost work comes before `rank`, its Roadmap gets `work heartbeat | c0265 | exists`, the usage text lists `beat` and `lost`.

### Scalability
`status`/`lost`: one fetch of the hb branches (0.8 s) and, only when a claim is stale, one `gh pr list`. A beat: one `fetch` of `main`, one fetch of the hb branches, one `git grep`, one push of a one-commit pack per working agent every 5 minutes; throttled locally so frequent `./zn` commands cost nothing. A branch push triggers no workflow (`deploy.yml` runs on `main` and pull requests). Origin holds one branch per live claim, deleted when the claim drops.
### Maintainability
`heartbeat.luau` is the one reader and writer of the heartbeat branch format; the lease id is the existing claim stamp; `./zn work` (c0253) calls `settle` and `order`; the limit and interval are constants.
### Usability
Two commands and four markers, each refusal naming the item and the rule; no agent has to remember to beat (claims, any `./zn` command, the dispatcher, the loop).
