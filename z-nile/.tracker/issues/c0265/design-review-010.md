### F1 [high] `./zn status` fails in a protected checkout today, so "the list prints as before" is false and lost.spec's protected case cannot pass for a correct implementation; the fix the spec invites also reads the remote
Where: Design, The board ("In a protected checkout the verdict reads are skipped (for `./zn status` and `./zn lost` too: the list prints as before, …)"); Regression guard ("`status` and `lost` read nothing in a protected checkout either"); lost.spec:292-294 (`local listing = zn(h.f.main, { "status" }, LATE, { PICKMAN_FENCE_REAL_GIT = listed }); t.expect(listing.ok).toBe(true)`); engine/main.luau:1605 (`if not publishing() then fail("status needs an origin remote (PICKMAN_PUBLISH=0 disables it)")`), 286 (`publishing()` is `… and not guarded()`), 1400 (`originPaths` runs `git fetch --quiet origin main`).
Evidence: `cmd.status` asks `publishing()` before it lists, and `publishing()` is false whenever `guarded()` says the checkout is protected. In the case's protected fixture, `status` therefore prints `not publishing: … is protected by the repository guards` and exits 1, as it does today. My replay against the unchanged engine fails at exactly lost.spec:293 (`expected true, got false`), and that is the "as before" behaviour the design promises to keep. An implementation that keeps the list "as before" fails the spec. One that changes `status` to list there goes through `originPaths()`, which runs `git fetch origin main`. That is a remote read in the real checkout, against the rule "no remote is read". The fixture cannot see it, because the shim counts only `ls-remote`. So the case fails the stated design and can be passed by a wrong one. Round 9's F2 Recommendation had the same false premise ("status lists exactly as today with no remote read").
Critique: the tempting fix is a sentence: "status skips `publishing()` in a protected checkout". That changes an existing command's guard to satisfy a spec, and it still reads the remote unless the fetch is skipped as well.
Consequences: if `status` is allowed in protected checkouts, it needs a no-fetch list (from the local `origin/main`, possibly stale), a rule about which refusal text applies to `status <id> <to>` there, and a case for both. That is new behaviour the capture does not ask for. Keeping today's refusal brings nothing new: `status` already reads nothing there, because it refuses before `originPaths()`.
Recommendation: keep `status` as it is in a protected checkout and say so truthfully. In The board's parenthetical and in the Regression guard, write: "`./zn status` refuses there as it does today (`publishing()` is false: `not publishing: … protected`), before any fetch or verdict read". Change lost.spec's protected case to `t.expect(listing.ok).toBe(false)`, `t.expect(has(listing.stderr, "protected")).toBe(true)`, no `[lost`, and `calls()` unchanged. `lost` keeps its exit-0 note, and the design should say that `lost` asks `guarded(true)` before `publishing()`, so it reaches the note and not `publishing()`'s refusal. Narrow the Rules row's `status` mutant to "status reading verdicts (or fetching) before its guard", or drop it, since today's refusal comes first. Lesson: z-design/prove-specs-pass-on-a-prototype. The replay of the unchanged engine shows this as an assertion failure on a line the feature does not own. Next time, read the failures of a replay like this, not only count them.
Lesson: z-design/prove-specs-pass-on-a-prototype
