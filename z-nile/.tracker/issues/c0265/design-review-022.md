### F3 [medium] The heartbeat's reads treat refs that every checkout shares as the command's own: two concurrent reads fail on each other's ref locks, and a beat's tree and parent come from two reads of a ref that a sibling can move
Where: c0265.md:67 (Shared state: "a local fetch into `refs/zn/hb-seen/*` … so `beat` runs in the main checkout and in any worktree"), :116 (Name), :125 (beat: "`git commit-tree <origin/main tree> -p <origin/main tip>`"), Rules row E1 (c0265.md:209: "a one-commit branch whose tree is main's tree and whose parent is main's tip (so `./zn busy` is silent)"); prototype main.luau:1458 (`readBeats`), :1663-1664 (`tree` and `tip`, two `rev-parse` calls); publish.luau:343-350.
Evidence:
- **Ref locks.** `./zn run --time 180 -- bash probe/lock.sh` sets up scratch repositories: a clone and its worktree fetch `+refs/heads/hb/*:refs/zn/hb-seen/*` at the same moment while another clone replaces four beat branches, for 60 rounds. Output: `concurrent fetches: 120, failed: 59`, each failure of the form `error: cannot lock ref 'refs/zn/hb-seen/preparing-a-a-a': is at dea1200f… but expected 4e081814…`. A failed read makes `beatOnce` return `err` (the beat fails and says so), makes `status` print `status: heartbeats unreadable` with no markers, and makes `lost` exit 1. The window is the fetch's whole round trip (0.8 s against origin, E10), not just the moment of the ref write.
- **Split read.** `./zn run --time 60 -- bash probe/split-read.sh`: a beat reads `origin/main^{tree}` at X; a sibling worktree's `git fetch origin main` then moves the shared `origin/main` to Y; the beat reads `origin/main` (now Y) as its parent. Busy's own diff (`git diff --name-only origin/main...<ref> --`, compact.luau `busyRefNames`) prints `pickman/.tracker/issues/c0001/c0001.md`. So `./zn busy` lists the beat as a branch changing a project root, which is E12's rejected shape, until the next beat replaces it.
- **The precedent.** `publish.commit` already handles both cases for its own fetch. It retries a failed fetch with backoff ("a lock held by a sibling worktree: back off, retry", publish.luau:346), and "every later step names this sha, never `origin/main`: sibling worktrees share that ref". The monolithic design also retried the heartbeat read once (experiments/split/c0274/design.md:27: "a ref-lock contention between two concurrent commands counts as unreadable, retried once as `publish` retries"). The core dropped that retry without saying so.
Critique: c0275 is captured to run this read on every `./zn` command in every worktree, and c0276 to read it for the board. Collisions therefore become routine exactly as parallel work grows, which is the situation the heartbeat exists for. The fail-safe holds (nothing reads lost), but `lost`, which z-design's Candidates step and c0253's worker call first, fails spuriously, beats fail, and a beat can make `busy` refuse a move or a compaction for up to five minutes. The split read breaks the Design's own row E1.
Consequences: a retry costs at most one more fetch, and only under contention. Naming one sha changes nothing else. The claims read in the same attempt (`git show origin/main:<p>` in `claimsOf`, and `git log -S … origin/main` for `since`) should name that sha too, so the claimed set and the beat commit describe one `main`.
Recommendation:
- `readBeats` and the heartbeat's fetch of main (`beatPaths`) retry once, after a short backoff, when the fetch fails and its stderr says `cannot lock ref`. A second failure is unreadable, as today. Case: a shim marker fails the first `fetch … hb-seen` with git's lock text; `beat` still lands and `lost` still lists. Add a row for the mutant "no retry".
- Each beat attempt resolves `origin/main` once, to a sha, builds `commit-tree <sha>^{tree} -p <sha>`, and reads the claimed set at that sha. Case, in edge.spec (it has the race shims): a shim marker that, after answering the first `rev-parse` naming `origin/main`, pushes a new main commit from `other` and fetches it into the checkout. Expect the beat commit's tree to equal its parent's tree, and `busy` to stay silent. Add a row for the mutant "tree and tip read apart".
- Say in the Shared state bullet that these namespaces are shared by every checkout of the repository, and how a collision is handled.
Lesson: zz-arch/read-paired-facts-at-one-moment, zz-arch/lock-reads-live-state

### F5 [low] race.spec's 10 s and 12 s bounds fail on a loaded host
Where: proofs/race.spec.luau:138 (`ZN_BOUNDED_DEADLINE = started + 10`, `ZN_BEAT_EVERY = "1"`), :145, :198 (`started + 12`), :203.
Evidence: one of my two race.spec runs on the envelope failed with `race.spec:145: expected true, got false` ("a later tick beat"), at load average 185 on 18 cores. The other run passed, at 163. The variant in the failing run (F1's A) adds code only to the autobeat, which the envelope never runs for `beat`. Why it fails: the first tick makes two tries, each with two fetches, a push and a re-read after the rejection, and the loop stops when `now + every >= deadline`. So if startup plus the first tick take more than about 9 s, no second tick runs. The coordinator says this host is usually that loaded.
Recommendation: with F1's and F4's race.spec edits, give both cases a bound of `started + 40` and make their elapsed checks `< 60`. Record the load of E16's runs.
