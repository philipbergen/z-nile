**The lease and ownership.** The branch name carries the claim stamp, and a takeover has a new stamp, so ownership is the pair (stamp on `main`, branch `hb/<stamp>`). **One rule for the lease** (in `heartbeat.plan`, argument `remembered`): the sha this checkout last wrote for that stamp (its throttle entry `<stamp> <epoch> <sha>`), else the sha it just read, else empty (create only if absent); a beat is `git push --force-with-lease=<branch>:<lease> origin <commit>:<branch>`. **A beat is bound to the stamp its holder owns**, never to whatever `main` says now: "my stamp" is the claim memory `.cache/tracker-stamp-<id>` (written by every claim publish and by an adoption). `beat <id>` (explicit, `--watch` and the autobeat alike) beats only that stamp; when `main` shows another stamp or none it refuses with `<id>'s claim was taken over (now <stamp>)` or `<id>'s claim ended`, exits 1 (the autobeat says it once and carries on), drops the entry and never rewrites the memory. A checkout with no memory (a fresh clone, a raft worktree made after `ready`) refuses a bare `beat <id>` (`beat: <id>'s claim is not held by this checkout (use --adopt to take it on)`). **`--adopt` is the stated adoption** and the way a checkout comes to own a claim it did not publish (z-run in the raft worktree after `ready`, a human in the main checkout): it beats origin's stamp and **writes the memory in the adopting **worktree** (a main-checkout `--adopt`, and the dispatcher's `--adopt --stamp`, write none: the main checkout holds no work and beats once per command). **Adoption never overrides a remembered different stamp**: where the memory differs from `main`'s stamp, `--adopt` refuses with the takeover text like any other beat. A takeover never reuses the old owner's worktree (it is discarded, below), so the old process finds either a refusal or its discard notice, whichever form it uses; a *different* checkout that adopts is by definition a new owner. The memory is **never dropped by the observation that triggers a refusal** (dropping it would let the old owner's `--adopt` or carried move through); it ends only with its checkout (a discarded worktree) or by a claim-ending command run in that checkout (`status <id> new`, `release`, `stop`, `done`). The dispatcher's `--adopt --stamp <S>` and an `--adopt` in the main checkout write no memory (the main checkout holds no work; a human adopting there beats once per command). `--adopt --stamp <S>` (the dispatcher's form) refuses when `main` no longer shows `<S>`. The takeover, after publishing the new claim stamp on `main`, runs **one atomic push**: delete `hb/<old>` with a lease on the sha it read, create `hb/<new>` create-only. So the old owner's next beat finds its branch gone and its lease rejected (it cannot recreate it); it re-reads and learns the loss as above. **A create-only write** (the branch absent when read, which is also what a beat in a checkout without a remembered sha sees after a takeover) can race a takeover in the window between the beat's main read and its branch read: so after any create-only write the beat re-reads `main`, and when the stamp changed it deletes what it created (lease on its own sha) and reports the loss. Telling a lease rejection from another failure needs no classification: any failed write is followed by a re-read and `heartbeat.rejected` (retry on the sha there, create, or lost), and a second failure is a failed tick. What is **said** (`beat: <id>: <git's message>` on stderr): a failure whose git message does not contain `(stale info)`, the text git itself prints for a lease rejection (E10) and which a same-claim co-beater causes harmlessly, so those retry silently; a retry that fails too is always said. Pruning deletes are separate best-effort pushes (a vanished target never fails the beat). If the rejection came from a co-beater of the same claim (same stamp, another sha) the beat retries once on what is there. An old owner that comes back by a command that does not beat (a plain `status`) learns the same thing from its entry's stamp check.

- **Automatic beats.** (Never from a protected checkout: the engine's own `guarded(true)` answers, as it does for `reap --auto`, so a nested `./zn lessons` in a `check.sh` or spec flow of the real repository never fetches or pushes; one reader of the fence, its answer fails closed; fixtures are unguarded and still beat.) A `beat` made in a **worktree** writes `.cache/tracker-beats/<id>` there (`<stamp> <epoch> <sha>`, ignored); the **main checkout never writes or reads one** (it holds no work: the dispatcher's and `ready`'s beats there are ref pushes only). Every `./zn` command except `beat`, `run`, `reap` and `READ_ONLY` ones first reads the worktree's entries; for each, if origin's stamp for the id differs from the entry's (a takeover, a give-back, a finished item) the entry is deleted and nothing is beaten; else, if the epoch is at least `INTERVAL` old, it beats that item; when it drops an entry it says once on stderr `<id>'s claim was taken over (now <stamp>): stop working it` if another claim now holds the item, or `<id>'s claim ended` if the item is no longer a claim (finished or given back), the same words `--watch` uses. The entry's epoch advances on a **failed** attempt too, so a hung or offline remote costs one bounded attempt per interval and warns once on stderr; a failure never fails the command. Each heartbeat call, made as `git <subcommand> …` from the checkout's own directory (never `git -C`, so the specs' shims see the subcommand first) (fetch, `git grep`, push, `gh pr list`) runs in its own process group (as `runner.luau` starts its children) and the group is killed after `heartbeat.setting(env, "ZN_NET_SECONDS", 10)` seconds, which counts as unreadable (`ZN_BEAT_EVERY` and `ZN_NET_SECONDS` are honoured only inside spec runs, by that one pure function). A session that keeps working keeps its claim alive for as long as it runs any `./zn` command in its worktree (`commit`, `spend`, `status`, `check`, `dispatch`…), with no loop and no network call inside the interval. A first beat never fails its claim: it runs after the publish, is best effort, and a failure is said on stderr (`beat: <id>: <message>`) while the claim stands and the command exits 0 (the claim is already on `main`). **The worktree's throttle entry is written whether the first beat succeeded or not** (a failed attempt advances it, as any failed attempt does), so a claim whose first beat failed is still beaten by the worktree's next command after an interval. First beats: `status <id> preparing`, `status <R-id> preparing`, `new raft`, `fold`, `unfold`, `recombine`, `ready` and a legacy `start` beat right after their publish. **Long outer commands** (`check`, `done`, `land`, `dispatch`) start a background tick for as long as they run, in a worktree that holds entries (the capture's "a beat into long `./zn` commands"); a nested `./zn` inside them never beats (`guarded`). The gate script `z-nile/check.sh` run directly is not a `./zn` command and has no tick: a long gate runs under `./zn done`/`land`, or with the `--watch` loop running (the skills say so). A readied raft nobody starts gets its first beat from `ready` and then reads lost 15 minutes later: that is the case "an in-progress item whose worker is gone", and `/z-run` re-adopts it (its worktree writes the entry).
- **Guarded checkouts**: the explicit `./zn beat` and the dispatcher's `zn beat` child run `publishing()` like every other publisher and refuse (naming the rule) when `guarded(true)` says a check protects the checkout; the fence's pre-push hook is the second line, not the first.

- **The dispatcher** (`z-nile/engine/dispatcher.luau`): while a model step runs, every `INTERVAL` it starts `zn beat <id> --adopt --stamp <S>` for the item the step works (`<S>` is the stamp `main` showed when the step started, or, for a step that makes its own claim, the stamp in the memory of the step's worktree, re-read at each tick; a mismatch means the claim was taken over mid-step: the dispatcher stops beating and says so once) (a raft's id for z-raft and z-run), one child at a time, killed after 60 s (E3: a `process.exec` in a `task.spawn` does not stall the supervising loop). A refusal (no claim yet) is ignored; any other failure is written once per step to the run's stderr. Under `ZN_DISPATCH=1` the step starts no loop (the skills say so).

- **Why not `reap`, the sweeper, or `sync`**: they clean local leftovers; a beat leaves nothing local but the throttle file (ignored, under `.cache`).

`zz-rules`: a Heartbeat paragraph (the heartbeat branch and its lease, the limit, parked, `beat`, `lost`, takeover, `ZN_NOW`) and its command table rows, and the main-checkout list ("`beat` pushes only `hb/*` branches"). `z-design` (claim step: start `./zn run --time 3600 -- ./zn beat <id> --watch` in the background unless `ZN_DISPATCH=1`; when it reports its bound, restart it in the same worktree (a restart elsewhere needs `--adopt`), or rely on the automatic beat of every `./zn` command in the worktree; Candidates: take `./zn lost` first, and continue a lost prep from `origin/prep-<slug>`), `z-raft` (a lost rafting claim: `./zn worktree --takeover <R-id>`), `z-run` (each: take `./zn lost` first; z-design: take over a lost prep with `./zn worktree --takeover <id>` (never plain `./zn worktree`, which would enter the old worker's checkout), then `./zn status <id> preparing` in the path it prints; z-run says a lost raft is taken over by `--takeover`, `stop`, `ready` and a plain `./zn beat <R-id> --adopt` in the fresh worktree; the same loop for the raft; `z-run` of a lost raft re-adopts it) and `zz-execute` (the loop) gain one bullet each. The README's Order says lost work comes before `rank`, its Roadmap gets `work heartbeat | c0265 | exists`, the usage text lists `beat` and `lost`.

`status`/`lost`: one fetch of the hb branches (0.8 s) and, only when a claim is stale, one `gh pr list`. A beat: one `fetch` of `main`, one fetch of the hb branches, one `git grep`, one push of a one-commit pack per working agent every 5 minutes; throttled locally so frequent `./zn` commands cost nothing. A branch push triggers no workflow (`deploy.yml` runs on `main` and pull requests). Origin holds one branch per live claim, deleted when the claim drops.
### Maintainability
`heartbeat.luau` is the one reader and writer of the heartbeat branch format; the lease id is the existing claim stamp; `./zn work` (c0253) calls `settle` and `order`; the limit and interval are constants.
### Usability
Two commands and four markers, each refusal naming the item and the rule; no agent has to remember to beat (claims, any `./zn` command, the dispatcher, the loop).

## Acceptance criteria text

- AC2: a claim, ready, new raft, any ./zn command in a claimed worktree (once an interval has passed, never in the main checkout) and beat each write the beat as a one-commit branch hb/<stamp> that changes no path (main gets only the claim, no file changes, ./zn busy stays silent), beat works from the main checkout, keeps another terminal's fresh beat of a claim it has not fetched, never beats from a protected (fenced) checkout and the explicit beat refuses there, refuses what nobody claims (done items included), and --watch refuses to run without a numeric bound
- AC3: lost and status say which claims are lost and list them first, tag parked and unconfirmed ones without calling them lost, a never-beaten claim and an unstarted readied raft are lost, a takeover that meets a restamped claim is refused, fold beats, a beat revives one, unreadable beats or pull requests, a malformed beat ref make nothing lost and refuse a takeover, a failed beat attempt is not retried inside the interval, the takeover is recorded in the claim commit's subject, the board's model carries each verdict (lost, parked, stale) with lost work first in its bucket (longest silent first) and the publish-rebuilt board too, a protected checkout reads no remote (the board carries no verdicts, status refuses before any fetch, lost says so), an entry for a claim that ended says so, a failed first beat does not fail the claim, a lost claim (an issue's or a raft's) is taken over with a fresh stamp (a bare beat from a checkout that does not hold the claim, a restarted loop, an adoption over a remembered stamp and the dispatcher's stamp-bound form never adopt the taker's claim; a lost readied raft is taken over by stop then ready; the takeover deletes the old owner's branch and creates its own in one push), a beat that races a takeover is rejected by its lease and the old owner learns it lost the claim, a create-only beat that races one deletes what it created, and the old claimant's carried move is refused and its worktree stops beating
- AC4: a model step the dispatcher runs on a claimed item beats for it while the step works (not only before or after); the proof is pinned by hash, so a changed proof fails here
- AC5: (the proof is pinned by hash, so a changed proof fails here) a hung remote is bounded, beat --watch says a failed tick, keeps beating, ends before its bound and stops when its claim is restamped, and a long check beats while it runs

## Pure code left out of the core layer

The core `heartbeat.plan` has no `remembered` argument. The lease rule with a remembered sha (the throttle entry `<stamp> <epoch> <sha>`) is `plan(stamp, epoch, beats, claimed, now, remembered?)` in `../heartbeat.monolith.proto.txt`, with its case in `heartbeat.cases.luau.txt`. The core `heartbeat.clock` and `heartbeat.setting` take a `specRun: boolean` (the guards answer `checking()`; the engine and specs must not name the guards variables: tooling/repo-fence bans them), unlike the prototype file.

## Lesson from the core prototype

`tooling/repo-fence.spec` bans the guards variable names (`PICKMAN_FENCE_`, `PICKMAN_TEST_FENCE`, ...) in engine files and specs. The engine asks `checking()` (the guards' own answer) and passes a boolean to pure functions; a spec makes a checkout "protected" by appending `pickman_guarded() { echo guarded; }` to the fixture's own `z-nile/lib/fence.sh` and restoring it (see c0265 `acceptance/beat.spec.luau`, the protected-checkout case). Run `z-nile/check.sh --affected` on your prototype before review 1: the first gate run on the core caught this.
