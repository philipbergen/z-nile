### Discard and recover (the user's 2026-11-08 rule: the old worktree is discarded, a copy continues the work)
The user: "Rename the old worktree and create a copy to continue the work and call it R123-1 R123-2 and so on. That way a process that wakes up knows it has been discarded and can clear and pick up something new." **Reading taken (for the user to veto): the copy is the numbered one.** Sessions, file tools, hooks and run state address a checkout by *path*, so the old worktree stays at its path and is marked discarded (a waking process finds its own directory, which tells it), while the taker works in `.worktree/<name>-<n>` (`R0010-1`, `R0010-2`, ... / `prep-<slug>-1`, ...). Moving the old directory aside and reusing its path for the taker would hand the waking process the taker's checkout, which it would then beat and edit without ever being told. The old worktree's local **branch is renamed** (the "rename the old worktree"), so the taker's copy keeps the original branch name, and the PR's head keeps working.

**`./zn worktree --takeover <id>`** (or by name: `./zn worktree <name> --takeover [--item <id>]`; a prep: `prep-<slug>`; a raft: `R0010`) does, in this order. The form by id **resolves the id to a branch first**, then runs the by-name steps on it, the fresh check included: the branch of the non-discarded worktree whose claim memory names the id (a worktree whose remembered stamp differs from `main`'s while another's matches is not a candidate; a discarded worktree is never one), else `prep-<slug>` for an issue (as the dispatcher already derives it) and the raft branch for a raft; with no worktree on the host it creates that name, marked fresh. So it does not depend on a name the old worker chose (`prep-<slug>`, z-raft's `raft-<slug>`):
1. Finds the current worktree of `<name>`: the one with the branch checked out (the original dir, or the latest copy `<name>-<n>`). If none exists it just creates `<name>` as `./zn worktree` does. A worktree that is **fresh** (it has `.cache/fresh`, written with the epoch by any `--takeover` that creates a worktree, the no-worktree path included, and removed when it gets claim memory: a taker is starting in it) is refused while younger than `STALE`, so a second taker cannot discard the first taker's copy; a copy whose taker crashed before claiming becomes takeable after the limit.
2. Which claims it takes over: the claims that worktree remembers (`.cache/tracker-stamp-*`); for a raft name, the raft's own claim (so an active raft whose z-run never adopted can be taken over); otherwise `--item <id>` names it, **accepted only when the worktree's branch is the item's own** (`prep-<slug>` for an issue, the raft branch or `R…` for a raft, or a `ws-<member>` of that raft), else it refuses naming both and moves nothing (the lost verdict is about the item, not about whose worktree this is). None found: it refuses and says to use `--item`. **Every claim must be lost or already ended** (judged with the guarded reads and `settle`), else it refuses (`claim alive`, `parked (an open pull request names it)`, `no heartbeat verdict: <reason>`) and moves nothing.
3. Chooses `<name>-<n>` with `heartbeat.nextSuffix` (the smallest `n >= 1` with no directory and no local branch of that name), writes `.cache/discarded` in the old worktree (what happened, the copy's path, the dirty files from `git status --porcelain`, the commits not on `origin/<branch>`, or on `origin/main` when nothing was pushed, as `git log --oneline` subjects, and the raft's `ws-<issue>` stream worktrees), and renames its branch `git branch -m <branch> <branch>-discarded-<n>` then `git branch --unset-upstream` on it **when it has one** (a copy built from `origin/<branch>` has; a never-tracked branch does not, and the command would fail): a bare `git push` from the discarded worktree must not move the PR head. **A raft takeover discards its `ws-<issue>` stream worktrees the same way** (marked, branches renamed, numbered copies not created: z-run recreates streams from the raft branch). The note's first line is `discarded worktree: <path>` (the old path), then the copy's path, the dirty files, the unpushed commits and `git -C <copy> cherry-pick origin/<branch>..<branch>-discarded-<n>`. The old worktree's `.cache/tracker-beats/*` entries are deleted by the discard, and a running `--watch` loop or dispatcher tick re-checks `.cache/discarded` each tick and stops, so nothing revives the claim between the discard and the taker's claim.
4. Creates `.worktree/<name>-<n>` on `<branch>` continuing **the old agent's pushed branch** (`origin/<branch>` via the existing `worktree` code when the local branch is absent, else `origin/main`), writes `.cache/fresh` there, and prints its path on stdout and the recovery note on stderr: the discarded worktree's path, its dirty files and unpushed commits, so the taker looks at them and takes what is useful (nothing is deleted: "try to recover the work, not just discard it").
**Looking a worktree up by name** becomes branch-based: `./zn worktree <name>` (and the dispatcher's and z-run's `cd "$(./zn worktree R0010)"`) returns the worktree of the **`<name>` family** that has the branch checked out: `.worktree/<name>` and `.worktree/<name>-<n>` (n numeric), skipping any marked discarded. A branch checked out at any other path keeps today's refusal (`already used by worktree at ...`, c0005's promoted case, which discard.spec keeps pinned with `worktree main`). When the family holds only discarded worktrees (the `ws-<issue>` streams after a raft takeover, a copy removed by hand) the lookup creates `<name>-<n>` with the next free number. So every path that asks gets the taker's copy, and only a process that kept the old path stays in the discarded worktree.
**The old process** keeps its directory, its memory and its stale lease. Every `./zn` command run in a worktree with `.cache/discarded` **except the read-only set and `reap`** (the session-end reaper of a session whose project directory is the discarded worktree must still stop its processes; the autobeat exempts `beat`, `run` and `reap` for the same reason) (`READ_ONLY` in main.luau: `list`, `audit`, `find`, `members`, `metrics`, `board`, `workstreams`, `promote-check`, `stamp`) refuses with exit 1 and: `this worktree was discarded: <id>'s claim was taken over. Clear your context and pick up something new. Your work is kept here: <dirty files, unpushed commits>`; this covers the beat, the autobeat, `--watch`, `status`, `done` and `lessons`. The marker can be deleted by the old worker; the stamp check (its memory against `main`) is the backstop, as for any old owner. **A dispatcher that was itself suspended past the limit** and finds its claim lost discards its own worktree before its next step (intended: its unpushed work is kept in the discarded worktree and listed in the note; a beat would otherwise revive a claim nobody was working). **The dispatcher** resolves every worktree it addresses through the lookup (`.worktree/ws-{id}` for a stream reviewer, `.worktree/raft-{id}` for the facts it reads, the step worktree), never by a built path, so after a takeover it reaches the taker's copy, and it does not reuse an old worktree for a step on an item whose claim is lost: it runs `./zn worktree --takeover <id>` first (and stops with a `questions.md` when the claim is parked or its verdict unknown). The taker then claims in its copy (`status <id> preparing`, the takeover of a lost claim, with the hb branch swap), and for a raft runs `stop` and `ready` as above. `./zn worktree-prune` lists discarded worktrees ("kept: holds the discarded work of <id>") and never removes them, whatever its rule for named worktrees; the taker removes one by hand (`git worktree remove`, then `git branch -D <branch>-discarded-<n>`) once its work is recovered. `./zn busy` names a discarded worktree while it holds changes under the paths asked for, like any worktree, and its renamed branch while it changes them: wanted, until removed.

heartbeat.nextSuffix(name, taken): string                              -- the smallest free "name-n"; the engine builds `taken` from the directories `<name>-<n>` and from the branches `<branch>-discarded-<n>` (each mapped to `<name>-<n>`)

`zz-rules`: a Heartbeat paragraph (the heartbeat branch and its lease, the limit, parked, `beat`, `lost`, takeover, `ZN_NOW`) and its command table rows, and the main-checkout list ("`beat` pushes only `hb/*` branches"). `z-design` (claim step: start `./zn run --time 3600 -- ./zn beat <id> --watch` in the background unless `ZN_DISPATCH=1`; when it reports its bound, restart it in the same worktree (a restart elsewhere needs `--adopt`), or rely on the automatic beat of every `./zn` command in the worktree; Candidates: take `./zn lost` first, and continue a lost prep from `origin/prep-<slug>`), `z-raft` (a lost rafting claim: `./zn worktree --takeover <R-id>`), `z-run` (each: take `./zn lost` first; z-design: take over a lost prep with `./zn worktree --takeover <id>` (never plain `./zn worktree`, which would enter the old worker's checkout), then `./zn status <id> preparing` in the path it prints; z-run says a lost raft is taken over by `--takeover`, `stop`, `ready` and a plain `./zn beat <R-id> --adopt` in the fresh worktree; the same loop for the raft; `z-run` of a lost raft re-adopts it) and `zz-execute` (the loop) gain one bullet each. ## Lesson from the core prototype

`tooling/repo-fence.spec` bans the guards variable names (`PICKMAN_FENCE_`, `PICKMAN_TEST_FENCE`, ...) in engine files and specs. The engine asks `checking()` (the guards' own answer) and passes a boolean to pure functions; a spec makes a checkout "protected" by appending `pickman_guarded() { echo guarded; }` to the fixture's own `z-nile/lib/fence.sh` and restoring it (see c0265 `acceptance/beat.spec.luau`, the protected-checkout case). Run `z-nile/check.sh --affected` on your prototype before review 1: the first gate run on the core caught this.
