# c0266: Classified spec znile features

## Problem
The c0114 classified spec fails ('no feature or defect is filed in z-nile's root') now that f0263 and f0265 are filed there, which turns every z-nile gate red; either the spec or where those issues are filed has to change

Scope decision (user, 2026-11-12): "Q1 is none of A, B, or C. z-nile owns its own tracker at `z-nile/.tracker`. Now that z-nile is separated, that tracker holds chores, features, and defects: `c`, `f`, and `d` tickets are all allowed. Do not rename d0298 to a chore. Rewrite the spec that forbids features and defects in z-nile's root so all three types are allowed there." (Asked as d0298's Q1, `.cache/dispatch/d0298/answered-1.md`; d0298 depends on this chore.)

## Non-goals
- Renaming or retyping any item. The ruling keeps every `f` and `d` in z-nile's root where it is, d0298 included.
- Tooling changes. `./zn new issue <f|d|c> --project z-nile` already accepts every type, `stats.luau` and `./zn metrics` already count every root's issues by type (`store.all("issue")`, `store.typeOf`), and watch-net already writes `type: defect` items (`watchcmd.luau`). Only the spec and the texts that restate the old rule are wrong.
- The other red in `c0114/classified`: since #383 (c7c28fec, 2026-11-15 00:40 PST) its first two cases fail with `two rafts share the slug capture-interview-and-idea-review: R0106, R0091` (E2). `./zn raft-plan` names a new raft by its first issue's slug (`raftplan.luau`, `slugOf[op.issues[1]]`), c0260's first raft R0091 was retired, and its new raft R0106 took the same slug, which the spec's `bySlug` refuses across retired rafts (c0116's override). It was not captured with c0266, which names only the chores-only case, and whether the tooling or the spec is wrong is that item's design, not this one's. No item owns it yet; the slow-tier defect d0303 lists `c0114/classified` among its red specs, and d0298's AC5 (the slow tier green) sees it. It is reported to the user in the prep PR. c0266's AC3 judges only its own case for that reason.
- `c0116/retired`, which reruns `classified` in a clone: it turns green with the rest of `classified`, so it waits on the red above; c0266 does not change it.

## Solution
Rewrite the case of `z-nile/tests/acceptance/c0114/classified.spec.luau` that wants every issue in z-nile's root to be a chore into one that holds all three types there, as the user ruled, and bring every text that restates "CI, test and tooling fixes are chores" into line with it (lesson z-design/restated-rules-move-together).

- The case "no feature or defect is filed in z-nile's root" becomes "z-nile's root holds chores, features and defects, each typed by its id": every issue in `z-nile/.tracker` (backlog, `active/`, `done/`) has a `type:` that is the type its id's letter names (`store.typeOf`), and the defect slugged `main-red-specs-after-cuts` (d0298, which the user said stays a defect) is a defect there.
- The first case's chore check on the 67 slugs c0114 moved stays: they were chores, and it keeps that record. One comment says it is not a rule for the root.
- z-ticket, the README, zz-rules, zz-test, zz-stats and the chore checklist say the new rule: every project root holds all three types, z-nile's included; a wrong spec (the code is right) is a chore, even when it is a bug; a z-nile command, gate script, guard, hook or workflow that does the wrong thing is a defect; z-nile's defects count in the rework rate as every root's do.

## Design
A working prototype is `prototype.patch` beside this document (`git diff` of the seven files on e88b4100, the base this design read). The documents are the contract; the executor applies the patch.

Product decisions: none. z-nile's tooling has no `game-design.md`; the decision this chore carries is the user's ruling quoted in the Problem. Architecture: no new dependency edge (no code changes, and both new specs require only `@lune/*` and `@tests/lib/*`).

### 1. The classified case (`z-nile/tests/acceptance/c0114/classified.spec.luau`)
The case at line 326 of the base,
```lua
it("no feature or defect is filed in z-nile's root", function()
	for _, item in allItems("issue") do -- c0120 override: read at the top
		if item.root == "z-nile/.tracker" then
			t.expect(string.sub(item.id, 1, 1)).toBe("c")
		end
	end
end)
```
is replaced, with a two-line `c0266 override:` comment above it, by
```lua
it("z-nile's root holds chores, features and defects, each typed by its id", function()
	local wrong: { string } = {}
	local defect = false
	for _, item in allItems("issue") do -- c0120 override: read at the top
		if item.root == "z-nile/.tracker" then
			local typed = store.readFront(item.doc).type
			if typed ~= store.typeOf(item) then
				table.insert(wrong, `{item.id}: type {typed or "(none)"}`)
			end
			if item.slug == "main-red-specs-after-cuts" then
				defect = store.typeOf(item) == "defect"
			end
		end
	end
	t.expect(table.concat(wrong, "\n")).toBe("")
	t.expect(defect).toBe(true)
end)
```
`allItems` already returns each item's absolute `doc` and its `root` and `slug` (read by a child run at the checkout's top, c0120). `store.typeOf` of an issue is the type its id's letter names (`store.TYPES`); `store.all` lists only ids matching `[fdc]%d%d%d%d`, so every listed issue is a chore, feature or defect by its id, and the non-trivial rule is that its document agrees. On e88b4100 every issue in z-nile's root agrees (E1). The slug is the item's stable name (c0114: a compaction changes ids, never slugs), so the pin survives a renumbering of d0298 but not a retype to a chore, which the user refused.

In `filed`, the `elseif root == "z-nile/.tracker" and store.typeOf(item) ~= "chore"` branch gains a two-line `c0266 override:` comment: z-nile's root holds all three types; the items c0114 moved were chores, and the branch keeps that record, not a rule for the root. Nothing else in the file changes.

### 2. The restated rule (six texts)
Each sentence is replaced exactly as `prototype.patch` shows; `acceptance/docs.spec.luau` quotes every new sentence and every old phrase.
- `z-nile/skills/z-ticket/SKILL.md`, step 1 (Classify the work): the defect is **product** behaviour (a game's, the portal's, the arcade library's, or z-nile's own: its commands, the gate, the guards, the runner, the selector); the chore is "refactors, infrastructure or upkeep", and its bold rule becomes "A spec that is wrong while the code is right is always a chore, even when it's a bug", with the examples a flaky or wrong spec, a test-selector graph miss (a hole in the watch map) and a game's own broken spec or test helper; a new bullet says every root holds all three types (c0266) and that a z-nile command, gate script, guard, hook or workflow that does the wrong thing is a z-nile defect. "a broken gate script, `setup.sh`, hook or workflow" and "tracker CLI bugs" leave the chore examples, since those are z-nile defects now.
- `z-nile/README.md`, The flow: "CI and test fixes are chores." becomes "Every project root holds all three, z-nile's included (c0266): a wrong spec is a chore, and a z-nile command, gate or guard that does the wrong thing is a defect (z-ticket)."
- `z-nile/skills/zz-rules/SKILL.md`, the Items table's chore row.
- `z-nile/skills/zz-test/SKILL.md`, the `tests/acceptance/<id>/` row ("a wrong spec is always a chore") and the Watch miss bullet (watch-net's captured defect for the failing spec stays a defect: z-nile's root holds defects).
- `z-nile/skills/zz-stats/SKILL.md`, the Rework % bullet: chores exclude every fix of a wrong spec; every root's features and defects count, z-nile's included.
- `z-nile/skills/z-design/checklists/chore.md`, its first paragraph.

Kept as they are, because they agree with the new rule: zz-execute's "file a watch-miss chore" (a hole in the map is a chore, and c0239's docs spec pins that sentence), zz-rules' emergent-issue rule (the correct type), z-design's Override check (an override is a chore: a wrong spec).
