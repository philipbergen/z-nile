# c0267: Dispatcher design step person approval

## Problem
The dispatcher chain (`./zn dispatch <id>`, c0117, done) runs its `design` step with a model and no person: the README's workflow picture and its dispatcher line show it as a worker's step. What should happen: the chain's `design` step produces a draft, and a person approves it before the ticket is prepared.

Scope decision (user, 2026-11-08): "humans approve the design, humans interact (plan mode) over the idea". c0264's Design: the README lines that let a worker design (Autonomous delivery, the worker end, the dispatcher chain, `claimable`) read as drafts that a person approves; c0117 is done, so this issue makes the chain's `design` step a draft that a person approves, so the README stays true.

Scope decision (user, 2026-11-15): "We want a flexible system. Approval can wait until we actually start implementation, but it can be done at any time once the design is complete. So I can have a ticket with design and I approve, I can have a raft of three tickets and they are not designed and that's fine. I then design the raft all three layers and approve the first one and start implementation on it but the two other layers must wait until approved and the bottom layer can merge before the rest is done as long as it doesn't break anything. So I can ask you to design everything that is waiting and have you record all your guesses and then I can sit down for an approval session where you walk me through every design and its guesses, one by one." This answers questions.md Q1 with none of A, B or C as written: the chain's design step still produces a draft, and the person's approval is required before the implementation of that ticket's layer starts, not before the ticket is prepared or rafted. The chain designs, merges the prep and rafts without stopping; it stops, as a step waiting for the person (not a failure), where a layer's implementation would start without a matching approval. Reading by Claude (not the user's words, to confirm at approval): the parts of this statement beyond the chain's design step (a raft holding undesigned tickets, per-layer approval inside a started raft, the bottom layer merging before the rest) are noted here as the direction and belong to their own tickets where c0267's capture does not cover them; the design names which.

## Non-goals
- The person-approval gate itself (c0252) and the explicit approval step `./zn approve` with its provenance record (c0263): this issue only makes the dispatcher chain's `design` step stop at a draft for them, and does not build or duplicate either.
- The worker end and the picture's `design` step (c0253), `claimable` (c0249) and the `preparing` claim (c0254): their own issues.

## Solution
<!-- The approach in one paragraph. -->
The chain keeps designing, merging the prep and rafting without a person, as today; what changes is the one place where implementation starts. Before it runs `z-ready` on a prepared backlog raft, `dispatch.next` reads, from a new fact, which of the raft's issues have no approval on `origin/main` that matches their contract (`approval.md`, #295's hash). While any has none, the chain stops with exit 3, as a step waiting for the person and not as a failure, and the stop names each issue, why (no approval, an unreadable one, or which contract parts changed since), and the commands that approve it in a terminal of the person's own. When the person has approved and published, `./zn dispatch <R-id>` goes on to `z-ready`. A raft `./zn ready` would refuse for anything else still goes to `z-ready`, which fails as it does today, so the wait never hides another refusal and a person is never asked to approve a raft that could not start anyway. The README's picture and dispatcher line, zz-rules' chain rule and z-design's step 5 say so.

## Design
### What the user decided, and what this issue builds of it
- Scope decision (user, 2026-11-15), quoted in the Problem: "Approval can wait until we actually start implementation, but it can be done at any time once the design is complete." Read with the answer to Q1 (`.cache/dispatch/c0267/answered-1.md`): the chain does not stop before `prepared` or before rafting; it stops, waiting for the person, where a layer's implementation would start without a matching approval.
- Where implementation starts today: `./zn ready <R-id>` claims the raft, moves it to `active/` and writes the prompt; `z-run` then starts the bottom layer. `ready` already refuses any member without a matching approval (#295, `readycheck.reason` → `approval.reasonOf(..., true)`), so today the chain runs `z-ready`, which fails (exit 1, "z-ready ended failure"): the stop is there, but it reads as a failure and names no way through. This issue moves that stop one step earlier, into the chain's own decision, as exit 3.
- Which members must be approved: every member of the raft, because that is what `./zn ready` requires today, and the chain's stop must agree with the command it guards (otherwise the person approves one layer and the chain fails on the next). Per-layer approval inside a started raft (approve the first layer, start it, the others wait) is the user's stated direction but is not in c0267's capture: it changes `ready` and `start`, and is named below as another ticket's. When that ticket changes which members `ready` requires, it changes the caller of `readycheck.waiting` the same way (one line: the members it passes), and this stop follows.
- "It can be done at any time once the design is complete": both paths already work and stay as they are. Before the prep merges, a person runs `./zn approve <id>` in the prep worktree and the prep PR carries `approval.md` (the prep gate accepts it: it is in the issue's own folder). After it merges, the person approves in any worktree on `origin/main` and publishes with `./zn approve <id> --publish` (#295, c0283). Either way the chain sees the approval on `origin/main` at its next decision.

### The chain's stop (pure, `z-nile/engine/dispatch.luau`)
- `export type Unapproved = { id: string, state: string, changed: { string } }`: `state` is `"none"` (no `approval.md`), `"bad"` (it does not parse) or `"changed"` (its latest row no longer matches the contract; `changed` names the parts, as `contract.changed` gives them: `design`, `check.sh`, a spec's name).
- `Facts` gains two optional fields: `unapproved: { Unapproved }?` (a prepared backlog raft only: its issues that wait for an approval, in layer order, when approvals are all `./zn ready` would refuse it for; `nil` when not read) and `unreadable: string?` (why those approvals could not be read). Optional, so the facts the promoted c0117 and work specs build (which leave them out) keep their answers: `Overrides: none`.
- `Action` gains `waiting: string?`, set to `"approval"` on this stop only, for a reader (status, the board) that wants to show "waiting for the person" without parsing `why`.
- `dispatch.waitingWhy(raft: string, unapproved: { Unapproved }): string`: the stop's text, pure. It starts `waiting for the person (not a failure): no layer of <R> starts until a person approves the design of each of its issues on origin/main.`, then one `<id>: no approval.` / `<id>: its approval.md does not parse.` / `<id>: its contract changed since approval (<parts>).` per issue in the given order, then `In a terminal of your own, from the main checkout, for each:` and, per issue, `cd "$(./zn worktree approve-<id>-$(date +%s) --from origin/main)" && ./zn approve <id> && ./zn approve <id> --publish`, then `Then run ./zn dispatch <R> again.` The worktree name carries the time so that a later re-approval (after the contract changed) gets a fresh worktree on today's `origin/main`, never a reused one on an old commit whose approval `--publish` would refuse (`./zn worktree <name>` reuses an existing name and ignores `--from`). No `retry`: the stop records no outcome (the chain only saves its state), so a plain `./zn dispatch` decides again from the facts.
- `dispatch.next`, in the raft branch, `where == "backlog"` and `status == "prepared"`, before it returns `z-ready`: `unreadable` set → stop exit 1, `the approvals of <R>'s issues could not be read from origin/main: <why>` (a failure: the chain cannot judge; fails closed rather than readying); `unapproved` non-empty → `{ kind = "stop", code = EXIT.user, why = waitingWhy(...), waiting = "approval" }`; otherwise `z-ready` as today. Nothing else in `next` changes: every stop above the state switch (questions, the open list, tripwires, a failed step, unharvested findings) still comes first; an issue's states (design, the prep gate, raft-plan, z-raft, the rafting gate, follow) never read the field; an active raft goes to `z-run` (its approvals were held by `ready`, and `done`/`land` still check them).

### Which issues wait (pure, `z-nile/engine/readycheck.luau`, `z-nile/engine/approval.luau`)
- `approval.stateOf(parts: contract.Parts, approvalText: string?): (string, { string }, string?)`: `"none"`, `"bad"` with the parse error, `"holds"`, or `"changed"` with the parts. It is the one reading of an approval's text (zz-arch rule 5): `approval.reasonOf` is rewritten over it with its words unchanged byte for byte (AC6 pins all four), and `readycheck.waiting` uses it.
- `readycheck.reason(r)` becomes `refusal(r, true)` over a local `refusal(r: Raft, approvals: boolean)`, the old body with the per-member approval check behind the flag. `reason`'s answers do not change (the flag is true).
- `export type Unapproved` (the same shape as dispatch's) and `readycheck.waiting(r: Raft, order: { string }): { Unapproved }?`: `nil` when `refusal(r, false)` refuses or the design files are not loaded, or when `readycheck.record` refuses (the grouping record, which `ready` judges inside its carried move); otherwise the members whose `approval.stateOf` is not `"holds"`, sorted by their place in `order` (members `order` leaves out come after, by id). A member whose contract does not build is skipped here because `refusal` already refused it (`<id>: <err>`).

### Reading it from origin/main (adapters)
- `z-nile/engine/workread.luau`: `blockFor` (the reader `./zn work next` already uses, which builds each backlog raft's `readycheck.Raft` from `origin/main`'s blobs) also returns `readycheck.waiting(raft, order)`, with `order` the raft's layer order (`RaftFact.issues`, `stack.order` over its Order section); `work.RaftFact` gains `unapproved: { { id: string, state: string, changed: { string } } }?` (structurally the same type; `work.luau` stays free of a `readycheck` require). New `workread.unapproved(id: string): ({ readycheck.Unapproved }?, string?)`: `pcall(workread.collect, id)`, the raft's `unapproved` (or `{}` when another refusal comes first or ready would accept), or `nil` and why when the read fails or the raft is not on `origin/main`. One reader: the dispatcher reads approvals exactly as `work next` does.
- `z-nile/engine/dispatcher.luau`: `Ctx` gains `approvals: (raftId: string) -> ({ dispatch.Unapproved }?, string?)`; `dispatcher.facts` calls it only for a raft that is `backlog` and `prepared` on `origin/main` and sets `unapproved`/`unreadable` (a call that answers neither is `unreadable = "no answer"`). `z-nile/engine/main.luau`'s `cmd.dispatch` wires `approvals` to `require("./workread").unapproved`.
- Authority: the dispatcher reads only `origin/main` (as every other fact), never the main checkout's working tree and never a model's prose. The stop is not a guard: `./zn ready` still refuses an unapproved member itself, so a wrong answer here can only stop the chain early or let `ready` refuse, never ready an unapproved raft.

### Scalability
One more read per chain action at a prepared backlog raft: `workread.collect` (one `git ls-tree -r origin/main`, one `git for-each-ref`, and `git cat-file --batch` calls for the rafts' and issues' documents and design files, the same reads `./zn work next` makes). The chain reaches that state once per run (it stops or readies right after), so it is one collect per dispatch run, growing with the number of open rafts and issues on `origin/main`, as `work next` does. No read for any other state.

### Maintainability
The rule "which members must be approved before implementation starts" lives in one pure place, `readycheck` (`refusal`'s approval check for `ready`, `waiting` for the chain), and both read approvals through `approval.stateOf`. The ticket that brings per-layer approval changes the member set there, and `ready`, `work next` and the chain follow. The dispatcher's fact goes through the existing `work next` reader (`workread`), not a second reader of `origin/main`'s tracker files.

### Usability
The stop prints `stop: waiting for the person (not a failure): ...` with the issues, their reasons and the literal commands, and exits 3, the same code as the other "needs the user" stops (questions, the open list). `--dry-run` prints the same line. `./zn dispatch <R-id>` (or the issue's id, which follows its raft) goes on once the approvals are published; no `retry` is needed. No new command, flag or usage line; no exhaustive list grows.
