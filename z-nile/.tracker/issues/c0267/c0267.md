# c0267: Dispatcher design step person approval

## Problem
The dispatcher chain (`./zn dispatch <id>`, c0117, done) runs its `design` step with a model and no person: the README's workflow picture and its dispatcher line show it as a worker's step. What should happen: the chain's `design` step produces a draft, and a person approves it before the ticket is prepared.

Scope decision (user, 2026-11-08): "humans approve the design, humans interact (plan mode) over the idea". c0264's Design: the README lines that let a worker design (Autonomous delivery, the worker end, the dispatcher chain, `claimable`) read as drafts that a person approves; c0117 is done, so this issue makes the chain's `design` step a draft that a person approves, so the README stays true.

Scope decision (user, 2026-11-15): "We want a flexible system. Approval can wait until we actually start implementation, but it can be done at any time once the design is complete. So I can have a ticket with design and I approve, I can have a raft of three tickets and they are not designed and that's fine. I then design the raft all three layers and approve the first one and start implementation on it but the two other layers must wait until approved and the bottom layer can merge before the rest is done as long as it doesn't break anything. So I can ask you to design everything that is waiting and have you record all your guesses and then I can sit down for an approval session where you walk me through every design and its guesses, one by one." This answers questions.md Q1 with none of A, B or C as written: the chain's design step still produces a draft, and the person's approval is required before the implementation of that ticket's layer starts, not before the ticket is prepared or rafted. The chain designs, merges the prep and rafts without stopping; it stops, as a step waiting for the person (not a failure), where a layer's implementation would start without a matching approval. Reading by Claude (not the user's words, to confirm at approval): the parts of this statement beyond the chain's design step (a raft holding undesigned tickets, per-layer approval inside a started raft, the bottom layer merging before the rest) are noted here as the direction and belong to their own tickets where c0267's capture does not cover them; the design names which.

Scope decision (user, 2026-11-15, on design review 001 F2): "Those were examples, all three could be approved and then built and shipped". The per-layer cases in the statement above are examples, not requirements: a raft whose issues are all approved and then built and shipped satisfies it.

## Solution
<!-- The approach in one paragraph. -->
The chain keeps designing, merging the prep and rafting without a person, as today; what changes is the one place where implementation starts. Before it runs `z-ready` on a prepared backlog raft, `dispatch.next` reads, from a new fact, which of the raft's issues have no approval on `origin/main` that matches their contract (`approval.md`, #295's hash). While any has none, the chain stops with exit 3, as a step waiting for the person and not as a failure. The stop names each issue and why (no approval, an unreadable one, or which contract parts changed since), and prints one whole command line per issue that approves it in a fresh worktree on `origin/main`, publishes it and removes that worktree. When the person has run them, `./zn dispatch <R-id>` goes on to `z-ready`. A raft `./zn ready` would refuse for anything else still goes to `z-ready`, which fails as it does today, so the wait never hides another refusal and a person is never asked to approve a raft that could not start anyway. The README's picture and dispatcher line, zz-rules' chain rule and ready row, z-design's step 5 and z-ready say so, and `ready`'s own refusal names the same way through.

### The chain's stop (pure, `z-nile/engine/dispatch.luau`)
- `export type Unapproved = { id: string, state: string, changed: { string }, why: string?, file: string }`: `state` is `"none"` (no `approval.md`), `"bad"` (it does not parse; `why` is the parse error) or `"changed"` (its latest row no longer matches the contract; `changed` names the parts, as `contract.changed` gives them: `design`, `check.sh`, a spec's name); `file` is the member's `approval.md` path.
- `Facts` gains two optional fields: `unapproved: { Unapproved }?` (a prepared backlog raft only: its issues that wait for an approval, in layer order, when approvals are all `./zn ready` would refuse it for; `nil` when not read) and `unreadable: string?` (why those approvals could not be read). Optional, so the facts the promoted c0117 and work specs build (which leave them out) keep their answers: `Overrides: none`. `Action` does not change: the stop is told apart by exit 3 and its first words, as the other "needs the user" stops are (nothing saves an action, so a field on it would have no reader: design-review-001 F6).
- `dispatch.approveLine(u: Unapproved): string`: one whole command line, run from the main checkout: `w="$(./zn worktree approve-<id>-$(date +%s) --from origin/main)" && (cd "$w" && ./zn approve <id> && ./zn approve <id> --publish) && git worktree remove "$w" && git branch -D "${w##*/}"`. For `"bad"` the subshell starts with `git rm -q <file> && git commit -qm "tracker: drop <id>'s unreadable approval.md" && ` (`./zn approve` refuses to append to a file that does not parse, and `--publish` replaces the file on origin/main). The worktree name carries the time so that a later re-approval (after the contract changed) gets a fresh worktree on today's `origin/main`, never a reused one on an old commit whose approval `--publish` would refuse (`./zn worktree <name>` reuses an existing name and ignores `--from`); the subshell brings the person back to the main checkout, and the worktree and its branch are removed only after `--publish` succeeded, so a failure keeps them for a retry.
- `dispatch.waitingWhy(raft: string, unapproved: { Unapproved }): string`: the stop's text, pure, one item per line: `waiting for the person (not a failure): no layer of <R> starts until a person approves the design of each of its issues on origin/main.`; one reason line per issue in the given order (`<id>: no approval.`, `<id>: its approval.md does not parse (<why>); ./zn approve refuses to add to it, so its line removes it first.`, `<id>: its contract changed since approval (<parts>).`); `In a terminal of your own, from the main checkout, run each line:`; one `approveLine` per issue in the same order, with nothing after it; `Then run ./zn dispatch <R> again.` No `retry`: the stop records no outcome (the chain only saves its state), so a plain `./zn dispatch` decides again from the facts.
- `dispatch.next`, in the raft branch, `where == "backlog"` and `status == "prepared"`, before it returns `z-ready`: `unreadable` set → stop exit 1, `the approvals of <R>'s issues could not be read from origin/main: <why>` (a failure: the chain cannot judge; fails closed rather than readying); `unapproved` non-empty → `stop(EXIT.user, waitingWhy(...))`; otherwise `z-ready` as today. Nothing else in `next` changes: every stop above the state switch (questions, the open list, tripwires, a failed step, unharvested findings) still comes first; an issue's states (design, the prep gate, raft-plan, z-raft, the rafting gate, follow) never read the field; an active raft goes to `z-run` (its approvals were held by `ready`, and `done`/`land` still check them).

### Which issues wait (pure, `z-nile/engine/readycheck.luau`, `z-nile/engine/approval.luau`)
- `approval.stateOf(parts: contract.Parts, approvalText: string?): (string, { string }, string?)`: `"none"`, `"bad"` with the parse error, `"holds"`, or `"changed"` with the parts. It is the one reading of an approval's text (zz-arch rule 5): `approval.reasonOf` is rewritten over it, and `readycheck.waiting` uses it.
- `reasonOf`'s answers keep their heads (state and way through): `<id> has no approval: run ./zn approve <id>, then ./zn approve <id> --publish`, `<id>: <file> does not parse: <why>`, `<id>'s contract changed since approval: <parts>.`. The no-approval answer's tail changes (design-review-001 F9): `..., in a terminal of your own, in a worktree on origin/main (not the main checkout).` replaces `from the worktree that holds the design. This is a one-time step for an item prepared before approval.`, which is wrong on the dispatched path, where the design is merged and rafted before approval and no worktree holds it. AC6 pins the heads and the absence of "one-time step", so a later item (f0339 appends a page requirement) may add to the tail.
- `readycheck.reason(r)` becomes `refusal(r, true)` over a local `refusal(r: Raft, approvals: boolean)`, the old body with the per-member approval check behind the flag. `reason`'s answers do not change (the flag is true). A refusal another item adds to `ready` goes in `refusal` above the flag (c0250's `blocked` raft, d0295's Order, c0306's judged reviews), so that `waiting` stays nil for a raft `ready` refuses for it.
- `export type Unapproved` (the same shape as dispatch's) and `readycheck.waiting(r: Raft, order: { string }): { Unapproved }?`: `nil` when `refusal(r, false)` refuses or the design files are not loaded, or when `readycheck.record` refuses (the grouping record, which `ready` judges inside its carried move); otherwise the members whose `approval.stateOf` is not `"holds"`, each with its `why` and `file`, sorted by their place in `order` (members `order` leaves out come after, by id). A member whose contract does not build is skipped here because `refusal` already refused it (`<id>: <err>`).

### Reading it from origin/main (adapters)
- `z-nile/engine/workread.luau`: `blockFor` (the reader `./zn work next` already uses, which builds each backlog raft's `readycheck.Raft` from `origin/main`'s blobs) also returns `readycheck.waiting(raft, order)`, with `order` the raft's layer order (`RaftFact.issues`, `stack.order` over its Order section); `work.RaftFact` gains `unapproved: { { id: string, state: string, changed: { string }, why: string?, file: string } }?` (structurally the same type; `work.luau` stays free of a `readycheck` require). New `workread.unapproved(id)`: `pcall(workread.collect, id)` handed to the pure `workread.unapprovedFrom(ok: boolean, input: any, id: string): ({ readycheck.Unapproved }?, string?)`: the raft's `unapproved` (or `{}` when another refusal comes first or ready would accept), or `nil` and why when the read failed, gave no rafts, or did not see the raft. One reader: the dispatcher reads approvals exactly as `work next` does.
- `z-nile/engine/dispatcher.luau`: `Ctx` gains `approvals: (raftId: string) -> ({ dispatch.Unapproved }?, string?)`. `dispatcher.approvalFacts(ctx, kind, where, status, id): ({ dispatch.Unapproved }?, string?)` calls it only for a raft that is `backlog` and `prepared` on `origin/main` (anything else: `nil, nil`, no call), through `pcall`: an error is unreadable with its message, an answer of neither a list nor why is `"no answer"`. `dispatcher.facts` sets `unapproved`/`unreadable` from it. `z-nile/engine/main.luau`'s `cmd.dispatch` wires `approvals` to `require("./workread").unapproved`.
- Authority: the dispatcher reads only `origin/main` (as every other fact), never the main checkout's working tree and never a model's prose. The stop is not a guard: `./zn ready` still refuses an unapproved member itself, so a wrong answer here can only stop the chain early or let `ready` refuse, never ready an unapproved raft.

### Scalability
One more read per chain action at a prepared backlog raft: `workread.collect` (one `git ls-tree -r origin/main`, one `git for-each-ref`, and `git cat-file --batch` calls for the rafts' and issues' documents and design files, the same reads `./zn work next` makes). The chain reaches that state once per run (it stops or readies right after), so it is one collect per dispatch run, growing with the number of open rafts and issues on `origin/main`, as `work next` does. No read for any other state (AC11 pins that no other state calls it).

### Maintainability
The rule "which members must be approved before implementation starts" lives in one pure place, `readycheck` (`refusal`'s approval check for `ready`, `waiting` for the chain), and both read approvals through `approval.stateOf`. A later ticket that changed which members must be approved would change the member set there, and `ready`, `work next` and the chain would follow. The dispatcher's fact goes through the existing `work next` reader (`workread`), not a second reader of `origin/main`'s tracker files. The stop's text is one pure function (`waitingWhy`, `approveLine`), so the commands it prints are pinned in one place.

### Usability
The stop prints `stop: waiting for the person (not a failure): ...` and then one line per issue with its reason, and one whole command line per issue to paste, and exits 3, the same code as the other "needs the user" stops (questions, the open list). `--dry-run` prints the same lines. `./zn dispatch <R-id>` (or the issue's id, which follows its raft) goes on once the approvals are published; no `retry` is needed. No new command, flag or usage line; no exhaustive list grows.

## Acceptance criteria

### Checked
- AC1: on a prepared backlog raft with an issue whose approval on origin/main is missing, unreadable or changed, `dispatch.next` stops with exit 3, and its text (`dispatch.waitingWhy`) is lines: it waits for the person and is not a failure; one reason line per issue in the given order (the parse error for an unreadable one, the parts for a changed one); `In a terminal of your own, from the main checkout, run each line:`; one whole `dispatch.approveLine` per issue (fresh worktree on origin/main, approve, publish, remove the worktree and branch; an unreadable file removed first); `Then run ./zn dispatch <R> again.`; no `retry`.
- AC2: with no unapproved issue, or with the field absent, the raft gets `z-ready`; with `unreadable` set the chain stops with exit 1 naming why, even when the list is empty.
- AC3: the chain's issue states (z-design, the prep gate's merge, raft-plan, z-raft, the rafting gate's merge, follow) and an active raft never stop for an approval, and a backlog raft that is not prepared still fails as before.
- AC4: questions.md, an unruled open list, a failed or tripped step and a done item still stop first, with their own texts.
- AC5: `readycheck.waiting` returns an empty list when every approval holds, names the missing, unreadable (with why) and changed (with the parts) ones in the given layer order (others after, by id), each with its file, and returns nil when `ready` would refuse the raft for anything else first (a dependency, a member with no `check` line, a draft raft or member, files not loaded, the grouping record).

- AC7: `./zn dispatch <R>` on a fixture raft whose issue has no approval prints the stop (also under `--dry-run`), exits 3, leaves the raft in the backlog on origin/main and starts no CLI, says the same on a second run; and the printed line for that issue, run as printed from the main checkout (approve and publish through the helper), brings `next: z-ready` and leaves no `approve-<id>-` worktree or branch.

- AC10: the specs that pin the chain, the worker, ready, approve and the README stay green (the list in `check.sh`).
- AC11: `dispatcher.approvalFacts` calls the reader only for a prepared backlog raft and passes its answer through; a reader error, or an answer with neither a list nor why, is unreadable; `workread.unapprovedFrom` gives nil and why for a failed collect, an answer with no rafts or a raft collect did not see, and the raft's list (or an empty one) otherwise.
