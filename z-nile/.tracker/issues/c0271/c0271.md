# c0271: Lesson read pr state before pushing

## Problem
zz-rules: read a PR's state (OPEN, CLOSED or MERGED) and its comments before treating it as the place the work lives, and again before every push or report that it was updated, because PR #256 was closed by another session with a comment and an agent kept pushing review rounds into it for hours while reports said the PR was updated; check: did you read `gh pr view <n> --json state` and the newest comments before this push, and does your report quote that state?

## Non-goals
- A tool that refuses the push (a check of the PR's state in `z-nile/bin/git`, in `./zn commit`, or in the dispatcher before a step pushes): the capture asks for the rule and its question, not a guard. It is the natural way to codify the lesson (c0181's question), and it is left for a capture by the user; nothing here blocks it.
- c0181's lesson mechanism (`enforced_by`, `enforced`, the caps, consolidation): this issue writes the lesson in today's format and keeps it under c0181's 1,200-byte cap for a partly enforced lesson, and names a spec case `[zz-rules/read-pr-state-before-pushing] …` that c0181's backfill can point `enforced_by` at.
- Reopening, retargeting or recovering a closed PR's work: the rule only says to stop and report; what happens to the work is the reader's (or the user's) call.

## Solution
<!-- The approach in one paragraph. -->
The rule becomes one zz-rules lesson, written in this prep (zz-rules skill, Lessons: "The prep that takes the issue writes the file"), and one sub-bullet of zz-rules' Landing a change, step 2, written by the executor, which every session reads before it pushes. The sub-bullet is pinned word for word by a promoted spec whose cases are named for the lesson. The lesson's own words are checked once by `check.sh`, never by a promoted spec, because c0181 rewrites lessons.

## Design
No game behaviour changes; `pickman/.tracker/game-design.md` is not relied on, and no dependency edge is added. Prep choices are marked **(prep)**.

**1. The lesson (written in this prep).** `z-nile/skills/zz-rules/lessons/read-pr-state-before-pushing.md`, id `zz-rules/read-pr-state-before-pushing`, in the format of zz-rules' Items (frontmatter `title`, `when`, `tags`, `check`; a body with the rule, **Why:** and **How to apply:**). Its source is the note in this issue's `harvest.md` (`- note PR #256 …: zz-rules/read-pr-state-before-pushing`), so `./zn lessons` lists c0271 on its sources line. The prep writes it, rather than the executor, because zz-rules says so for a lesson captured as an issue, and the dispatcher's prep gate admits skill lessons in a prep PR (zz-rules, Dispatch: "a prep PR: the issue's own folder, whose sequestered files it may change, and skill lessons"); the rule then works from the day the prep merges. Text as committed:

```
---
title: A PR's state and newest comments are read before every push to it and every report that it was updated
when: both
tags: [github, landing, reporting, coordination]
check: Did I read `gh pr view <n> --json state,comments` (the state, and the newest comments) right before this push to the PR's branch, or this report that the PR was updated, and does my report quote the state I read?
---
Another session or the user can close or merge a PR while an agent works on its branch, usually with a comment that says where the work went. A push to that branch still succeeds, but nobody reads it, so the work is lost and every "PR updated" report is false.

**Why:** c0271: PR #256 (a prep of c0264) was closed by another session with a comment naming the prep that replaced it, and an agent kept pushing review rounds into it for hours while its reports said the PR was updated.

**How to apply:** read `gh pr view <n> --json state,comments` before you take a PR as where the work lives, and again before every push to its branch (`git push`, or a `./zn` command that pushes) and every report about it. Only an `OPEN` PR takes the push. A `CLOSED` or `MERGED` one takes nothing: report its state and newest comment, and stop. A report that a PR was updated quotes the state it read (zz-rules skill, Landing a change, step 2).
```
- `when: both` **(prep)**: a push to a PR happens in prep (the design PR, its review rounds) and in build (`./zn commit` pushes every commit of a raft, zz-rules: "Every `./zn commit` pushes").
- The `check` keeps the captured question, made one sentence ending in `?` (the format's rule): "did you read `gh pr view <n> --json state` and the newest comments before this push, and does your report quote that state?" becomes `--json state,comments`, because the comments are what the capture asks to read and `state` alone does not return them (E1).
- The body is 931 bytes (c0181's cap for a partly enforced lesson is 1,200).

**2. The skill line (the executor's change).** `z-nile/skills/zz-rules/SKILL.md`, `## Landing a change`, gains one sub-bullet directly under step 2 (`2. **Push and open the PR**: …`) and before step 3 (`3. **Merge** …`), as a line of its own, word for word (pinned by `acceptance/docs.spec.luau`):

> `   - **Read the PR before every push to it.** Before you take a PR as where the work lives, and again before every push to its branch (`git push`, or a `./zn` command that pushes, such as `commit`) and every report that it was updated, read `gh pr view <number or branch> --json state,comments`: its state and its newest comments. Only an `OPEN` PR takes the push. A `CLOSED` or `MERGED` one takes nothing: push nothing to its branch, report its state and newest comment (it usually says where the work went), and stop. A report that the PR was updated quotes the state it read. A branch with no PR yet (`gh` answers `no pull requests found`) gets its first push and PR as above (lesson zz-rules/read-pr-state-before-pushing).`

(three spaces, `- `, then the text; the backticks inside are literal.) Why step 2 **(prep)**: Landing a change is "One procedure for every change: a raft, a capture, a prep or an edit", and step 2 is where every PR is pushed, so every pusher reads it there; a lesson alone is read only when someone searches. `<number or branch>` because the first push of a branch has no number yet, and `gh pr view <branch>` also finds a closed PR (E1), so a branch whose PR was closed is not mistaken for a new one. "and stop" is the whole of the reaction: what becomes of the work is not this rule's (Non-goals).
