# c0271: Lesson read pr state before pushing

## Problem
zz-rules: read a PR's state (OPEN, CLOSED or MERGED) and its comments before treating it as the place the work lives, and again before every push or report that it was updated, because PR #256 was closed by another session with a comment and an agent kept pushing review rounds into it for hours while reports said the PR was updated; check: did you read `gh pr view <n> --json state` and the newest comments before this push, and does your report quote that state?

## Non-goals
- A tool that refuses the push (a check of the PR's state in `z-nile/bin/git`, in `./zn commit`, or in the dispatcher before a step pushes): the capture asks for the rule and its question, not a guard. It is the natural way to codify the lesson (c0181's question), and it is left for a capture by the user; nothing here blocks it.
- c0181's lesson mechanism (`enforced_by`, `enforced`, the caps, consolidation): this issue writes the lesson in today's format and keeps it under c0181's 1,200-byte cap for a partly enforced lesson, and names spec cases `[zz-rules/read-pr-state-before-pushing] …` that c0181's backfill can point `enforced_by` at.
- Reopening, retargeting or recovering a closed PR's work: the rule only says to stop and report; what happens to the work is the reader's (or the user's) call.

## Solution
<!-- The approach in one paragraph. -->
The rule becomes one zz-rules lesson, written in this prep (zz-rules skill, Lessons: "The prep that takes the issue writes the file"), and one sub-bullet of zz-rules' Landing a change, step 2, written by the executor, which every session reads before it pushes; zz-execute's Phase 4, where a raft's review rounds push and report, gains one sentence that points at it and stops its "carry on" from passing a failed or closing read. Both skill texts are pinned word for word by a promoted spec whose cases are named for the lesson. The lesson's own words are checked once by `check.sh`, never by a promoted spec, because c0181 rewrites lessons.

## Design
No game behaviour changes; `pickman/.tracker/game-design.md` is not relied on, and no dependency edge is added. Prep choices are marked **(prep)**.

**1. The lesson (written in this prep).** `z-nile/skills/zz-rules/lessons/read-pr-state-before-pushing.md`, id `zz-rules/read-pr-state-before-pushing`, in the format of zz-rules' Items (frontmatter `title`, `when`, `tags`, `check`; a body with the rule, **Why:** and **How to apply:**). Its source is the note in this issue's `harvest.md` (`- note PR #256 …: zz-rules/read-pr-state-before-pushing`), so `./zn lessons` lists c0271 on its sources line. The prep writes it, rather than the executor, because zz-rules says so for a lesson captured as an issue, and the dispatcher's prep gate admits skill lessons in a prep PR (zz-rules, Dispatch: "a prep PR: the issue's own folder, whose sequestered files it may change, and skill lessons"); the rule then works from the day the prep merges. Text as committed:

```
---
title: A PR's state and newest comments are read before every push to it and every report that it was updated
when: both
tags: [github, landing, reporting, coordination]
check: Did I read the PR's state, head and newest comments (`gh pr view <n> --json state,headRefOid,comments`, trimmed as zz-rules' Landing a change step 2 says) right before this push to its branch, or this report that it was updated, and does my report quote the state I read?
---
Another session or the user can close or merge a PR while an agent works on its branch, usually with a comment that says where the work went. A push to that branch still succeeds, but nobody reads it, so the work is lost and every "PR updated" report is false.

**Why:** c0271: PR #256 (a prep of c0264) was closed by another session with a comment naming the prep that replaced it, and an agent kept pushing review rounds into it for hours while its reports said the PR was updated.

**How to apply:** follow zz-rules skill, Landing a change, step 2, before you take a PR as where the work lives and again before every push to its branch and every report that it was updated. Only an `OPEN` PR takes the push. A `CLOSED` or `MERGED` one whose head is in your history or in origin's branch takes nothing: report its state and newest comment, and stop. One whose head is in neither was an earlier use of the name (z-stop's start fresh). A read that fails twice stops the push; a PR you merged yourself keeps its post-merge report. A report that a PR was updated quotes the state it read.
```
- `when: both` **(prep)**: a push to a PR happens in prep (the design PR, its review rounds) and in build (`./zn commit` pushes every commit of a raft, zz-rules: "Every `./zn commit` pushes").
- The `check` keeps the captured question, made one sentence ending in `?` (the format's rule): "did you read `gh pr view <n> --json state` and the newest comments before this push, and does your report quote that state?" reads `--json state,headRefOid,comments`, because the comments are what the capture asks to read and `state` alone does not return them (E1), and the head decides whose PR it is (point 2); it names the trimmed form of the skill line rather than restating it (design review 001 F5).
- The body is 1,087 bytes (c0181's cap for a partly enforced lesson is 1,200). Its How to apply points at the skill line for the mechanics, which are too long for the cap, and keeps the outcomes AC1 checks: only `OPEN` takes the push, this work's closed or merged PR takes nothing and the agent stops, an earlier use of the name (start fresh), a read that fails twice, a PR you merged yourself.

**2. The skill line (the executor's change).** `z-nile/skills/zz-rules/SKILL.md`, `## Landing a change`, gains one sub-bullet directly under step 2 (`2. **Push and open the PR**: …`) and before step 3 (`3. **Merge** …`), as a line of its own, word for word (pinned by `acceptance/docs.spec.luau`):

> `   - **Read the PR before every push to it.** Before you take a PR as where the work lives, and again before every push to its branch (`git push`, or a `./zn` command that pushes, such as `start` or `commit`) and every report that it was updated, read its state, head and newest comments: `gh pr view <number or branch> --json state,headRefOid,comments --jq '{state, headRefOid, newest: [.comments[-2:][] | {author: .author.login, createdAt, body}]}'`. An `OPEN` PR takes the push. A `CLOSED` or `MERGED` one is this work's when its head is in the history you push or in origin's tip of the branch: after `git fetch origin refs/pull/<n>/head`, `git merge-base --is-ancestor <headRefOid> HEAD` exits 0, or `git ls-remote --heads origin <branch>` prints a tip and, after `git fetch origin <branch>`, `git merge-base --is-ancestor <headRefOid> FETCH_HEAD` exits 0. This work's closed or merged PR takes nothing: push nothing to its branch, report its state and newest comment (it usually says where the work went), and stop. When each test exits 1 (or origin has no such branch), the PR was an earlier use of the branch's name (z-stop's start fresh), and the branch gets its first push and a new PR, as a branch with no PR does (`gh` answers `no pull requests found`). Any other answer (another `gh` or `git` error) is no answer: retry once, then push nothing and stop. A PR you merged yourself (Merging, or the raft `./zn done` landed) is `MERGED` by design: its post-merge report and step 4 go on, and nothing more is pushed to its branch. A report that the PR was updated quotes the state it read (lesson zz-rules/read-pr-state-before-pushing).`

(three spaces, `- `, then the text; the backticks and quotes inside are literal.) The choices in it:
- **Where (prep)**: Landing a change is "One procedure for every change: a raft, a capture, a prep or an edit", and step 2 is where every PR is pushed. A lesson alone is read only when someone searches; a raft's executor is reached by point 3.
- **Whose PR it is (design review 001 F1)**: `gh pr view <branch>` also reports a closed PR whose branch was deleted (#306, E1), and z-stop's start fresh reuses the name (`gh pr close <pr> --delete-branch`, then `start` makes new ones), so a state alone would refuse that documented flow forever. The fact that ties a closed or merged PR to the work being pushed is its head: in the history pushed (the incident: every push after the close carries it), or in origin's tip of the branch (a layer `./zn restack` rewrote locally while origin still holds the old head). `git fetch origin refs/pull/<n>/head` first, because GitHub keeps that ref for a closed PR and another machine may not have the object (E6); without it `merge-base` exits 128, which is an error, never "not ours". When both tests exit 1, or origin has no such branch, the PR is an earlier use of the name, and the branch gets its first push and a new PR (start fresh from `origin/main`, E6). A squash-merged PR's head is not in `main`, so a later branch of the same name from `main` is an earlier use too; a `--no-ff` landed raft's head is, but no raft branch name is cut again after `done`. What the test cannot see: a layer restacked after its PR was closed *and* its branch deleted on origin reads as an earlier use and gets a new PR, which, unlike the incident's silent pushes, is a visible PR; no documented flow does that (start fresh cuts from `origin/main`, and z-stop's keep-them path reuses the open PR).
- **Failed reads (design review 001 F4)**: `gh` exits 1 both for `no pull requests found` and for a network or auth failure, so the bullet names the one "no PR" answer and makes every other answer no answer: retry once, then push nothing and stop (lesson zz-arch/guard-no-is-explicit).
- **A PR you merged yourself (design review 001 F3)**: after Merging's `gh pr merge` or `./zn done`, the next acts are reports on a `MERGED` PR (zz-execute Phase 6's final comment, Landing step 4); the exception lets them go on and keeps the push stopped ("Post no further commits to the branch", zz-execute Phase 6).
- **The trimmed read (design review 001 F5)**: `--jq '{state, headRefOid, newest: [.comments[-2:][] | {author: .author.login, createdAt, body}]}'` keeps the state, the head and the two newest comments (#256 closed with two). Measured 2026-11-15 (E7): #49 1,949 bytes, #66 2,737, #256 1,022, against 26,680, 34,910 and the full dump untrimmed. The dispatcher's `gh` wrapper decides on `pr view` alone (`wrapper.decideGh`), so the flags pass it.
- "and stop" is the whole of the reaction: what becomes of the work is not this rule's (Non-goals).
