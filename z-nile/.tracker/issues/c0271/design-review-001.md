### F1 [high] The CLOSED/MERGED stop, keyed on `gh pr view <branch>`, blocks z-stop's documented "start fresh" re-ready
Where: Design 2 (the bullet: "`<number or branch>` because … `gh pr view <branch>` also finds a closed PR (E1)"; "A `CLOSED` or `MERGED` one takes nothing: push nothing to its branch, … and stop"); the lesson's How to apply; `z-nile/skills/z-stop/SKILL.md:16`; zz-execute step 2 (`./zn start` opens branch `R0010/1/c0010`).
Evidence: z-stop step 4 says: "To start fresh, close the PR and delete the branch (`gh pr close <pr> --delete-branch` …), and `start` makes new ones." `start` names the first layer `<R-id>/1/<issue>` again, and it pushes. gh still reports the old PR for a branch name that no longer exists. `gh pr view unfold-c0261-R0090 --json number,state` returned `{"number":306,"state":"CLOSED"}` while `git ls-remote --heads origin unfold-c0261-R0090` printed nothing. So the agent that z-work or the dispatcher starts on the re-readied raft reads CLOSED before `./zn start` pushes, pushes nothing and stops: the documented fresh start can never run. The same happens to any deterministic branch name (`prep-<slug>`, `raft-<id>`) cut again after its PR was closed and the branch deleted.
Critique: the rule can't tell "this work's PR was closed" (the incident) from "an earlier use of this branch name was closed" (the owner's own restart). The tempting fix is to give a branch that is absent on origin its first push. That reopens the incident whenever the closer used `--delete-branch`: the agent's next push recreates the branch and opens a new PR for work that was deliberately discarded.
Consequences: the test has to be a fact git can read that ties the closed PR to the work being pushed: the PR's head is in the history being pushed. `./zn restack` rewrites a layer's local history, so for a restacked layer a test against HEAD alone fails open, while origin's tip of the branch still holds the old head. On another machine the PR's head object may be missing, and `git merge-base` then exits 128, which must not read as "not ours". The lesson body is 931 of the 1,200 bytes c0181 allows, so the lesson should point at the bullet for this test rather than restate it.
Recommendation: add `headRefOid` to the read and fetch `refs/pull/<n>/head` (GitHub keeps it for closed PRs; the dispatcher already fetches it). A `CLOSED` or `MERGED` PR is this work's PR when `git merge-base --is-ancestor <headRefOid> HEAD` exits 0, or when origin's tip of the branch contains it. Then push nothing and stop. When neither holds, the PR is an earlier use of the name, and the branch gets its first push and a new PR, as for a branch with no PR. Name z-stop step 4's start fresh as the example. Any other exit (128, an empty oid) means push nothing and stop. Record the #306 run as the second half of E1. Add E6: a scratch repo with a bare origin under `.cache`, run through `./zn run`, covering three cases (the incident stops, start fresh pushes, a restacked layer whose origin tip still holds the head stops). Update BULLET in docs.spec, the lesson's How to apply (one pointer), AC1's words and check, and add mutant rows for "the start-fresh clause dropped" and "the origin-tip clause dropped".
Lesson: z-design/refusing-memory-names-how-its-owner-gets-back-in

### F2 [high] `experiments/mutants.sh` guards the real repository with a string prefix, so a `..` path or a link under /tmp reaches the checkout
Where: `experiments/mutants.sh:8-9` (`case "$C" in /tmp/*|/private/tmp/*|/var/folders/*) …; cd "$C"`), and `save`/`restore` with fixed `/tmp/c0271-{R,L,H}` files.
Evidence: `bash -c 'C="/tmp/../Users/someone/code/pickman"; case "$C" in /tmp/*|/private/tmp/*|/var/folders/*) echo "accepted: $C";; esac'` printed `accepted: /tmp/../Users/someone/code/pickman`, because a `case` `*` matches `/`. Given such a path, or a link under /tmp that points at a worktree, `cd` lands in a real checkout. There M5 deletes the real lesson, M9 empties the real `harvest.md`, and M2 to M4 rewrite the real zz-rules SKILL.md. The restore copies back from fixed /tmp names, so a `./zn run --time` kill between an edit and its restore leaves the real files mutated, and two runs at once overwrite each other's saves. No gate, check or spec runs this script, only a person or agent re-running the prep's mutation check, but item 9 makes no exception for scripts run by hand.
Critique: the tempting fix is to also refuse `..` in the argument. That still accepts a link and any other spelling of the same path.
Consequences: the guard has to decide from what git resolves, not from the spelling. A clone made with `mktemp -d` under the future `.cache/.tmp` (c0194, active) would be refused by the /tmp-only list, so the guard should accept "a separate repository" rather than particular folders.
Recommendation: `C=$(cd "$1" && pwd -P) || exit 2`. Refuse when `git -C "$C" rev-parse --path-format=absolute --git-common-dir` equals the git directory of the checkout that holds the script (`git -C "$(dirname "$0")" rev-parse --path-format=absolute --git-common-dir`), and when `git -C "$C" remote` lists `origin` (the review clone's was removed). Keep the saves in `$(mktemp -d)`. Re-run the 10 mutants and record the result in E4.
Lesson: zz-arch/guards-decide-from-the-tools-resolution

### F3 [medium] A MERGED PR the agent merged itself is told to "take nothing … and stop", which contradicts the post-merge steps that report on it
Where: the lesson's How to apply ("again before every push to its branch … and every report about it … A `CLOSED` or `MERGED` one takes nothing: report its state and newest comment, and stop"); the bullet ("every report that it was updated"); `z-nile/skills/zz-execute/SKILL.md:91` (Phase 6 step 3: "Post it as a comment on the merged PR … before cleanup"); zz-rules Merging ("Then follow Landing a change, step 4").
Evidence: after the agent's own `gh pr merge` (Merging), or the merge of a raft that `./zn done` landed, the next required acts are reports about that PR: the final report comment on the merged PR, then Landing step 4. Read as the lesson words it ("every report about it"), the state is MERGED, so the agent stops, and the final report and the cleanup are skipped. The bullet and the lesson also disagree about what triggers the read ("that it was updated" against "about it").
Critique: the tempting fix is to drop MERGED from the stop. That reopens the case where another session merged the PR and the agent keeps pushing into it.
Consequences: with F1's test, the agent's own merged PR counts as "this work's", so an explicit exception is needed. It covers reports only, never a push: Phase 6 step 4 already says "Post no further commits to the branch". It can be keyed on a fact the agent already holds, the merge sha that Merging reads with `gh pr view <pr> --json mergeCommit`.
Recommendation: add one sentence to the bullet: "A PR you merged (Merging, or the raft `./zn done` landed) is MERGED by design: its post-merge report and Landing step 4 go on, and nothing more is pushed to its branch." Make the lesson's trigger the bullet's ("every report that it was updated"). Pin it through BULLET, add the words to AC1, and add a mutant row for "the exception dropped".

### F4 [medium] The rule is missing where a raft's review rounds push and report, and zz-execute says there to carry on past a failed `gh` call

Add mutant rows for "pointer dropped", "the not-carried-past clause dropped" and "the failed-read sentence dropped".

### F5 [medium] `--json state,comments` before every push dumps every comment (27 to 35 KB on a busy PR), and Scalability counts only wall time
Where: Scalability ("one `gh pr view` call (a few hundred milliseconds)"); the bullet; the lesson's `check`.
Evidence: on 2026-11-15, `gh pr view 49 --json state,comments` printed 26,680 bytes (29 comments), #66 printed 34,910 (29) and #329 printed 13,052 (12). `gh pr view 49 --json state,comments --jq '{state, newest: (.comments[-1] | {author: .author.login, createdAt, body: .body[0:200]})}'` printed 303. Every `./zn commit` in a raft pushes, so every read lands in the agent's context, and a dispatched step is killed when it passes `max_tokens` (zz-rules, Dispatch).
Critique: the tempting fix is `--json state` alone. That drops the comments the capture asks to read (E1).
Consequences: a `--jq` filter changes the pinned bullet, the lesson's `check` and AC1's grep (`gh pr view <n> --json state,comments`). The dispatcher's wrapper decides on `pr view` alone (`wrapper.decideGh`), and c0117's scan of the skills' `gh` commands still matches. How many of the newest comments to keep is a choice: the closing comment is the last one, and #256 had two.
Recommendation: name a trimmed form in the bullet and the lesson, for example `gh pr view <number or branch> --json state,headRefOid,comments --jq '{state, headRefOid, newest: [.comments[-2:][] | {author: .author.login, createdAt, body}]}'` (F1 needs `headRefOid`). State its measured size in Scalability, and update AC1's grep and BULLET to match. Mind the lesson's 1,200-byte budget alongside F1 and F3.
