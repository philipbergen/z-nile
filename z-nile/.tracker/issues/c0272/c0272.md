# c0272: Lesson superseding prep releases claim

## Problem
z-design: a session that supersedes another prep (closing its PR, or preparing the same issue elsewhere) also gives back or takes over the issue's claim and names the live branch where the other worker will see it, because a closing comment on PR #256 reached nobody and the agent holding the claim kept designing; check: when I closed or replaced another worker's PR, did I run `./zn status <id>` to hand over or release the claim and leave the new branch name on the claim, the issue and the old PR?

## Non-goals
- Any change to the claim mechanism: a stamp that names its branch, a `--note` on `./zn status`, a refusal of a superseded worker's next push or publish. The lesson uses the tools as they are (E1 proves each step); a mechanism is a new issue for the user. The stale memory a dispatched claim writes (design review 001's candidate) is d0358, captured from this prep; the lesson does not depend on a memory's contents.
- Finding another prep before claiming (c0270, `z-design/one-prep-per-issue`, which adds z-design step 1's **One prep per issue**) and reading a PR's state before pushing to it (c0271, `zz-rules/read-pr-state-before-pushing`). Those are the other two lessons of the same incident; this one is the superseding session's side.
- Editing z-design's or zz-rules' `SKILL.md`: the captured outcome is the lesson. The rule it leans on, zz-rules **Whose claim** ("Never give back a claim you did not make; ask the user"), stays as it is.

## Solution
One new, short lesson, `z-design/superseding-prep-hands-over-the-claim` (`when: design`), whose `check` keeps the captured question word for word and adds four clauses (the user's decision, the take-over's two commands in the live worktree, removing the superseded worktrees' claim memories, stopping a dispatched worker). Its body tells the c0264 incident and gives the hand-over as commands that work from any worktree today: find every candidate holder, stop a dispatched one, take the claim over (or release it) in the live prep's worktree and remove the superseded memories, and name the live branch on the old PR (if it has one) and, through `./zn land`, in a line under the issue's title on `origin/main`. A `harvest.md` note makes the capture its source. `check.sh` pins the lesson's words, that the mechanisms it names still exist, and that the lessons tooling reads it.

## Design
The captured outcome is the lesson; there is no code. The design work is to make each act the captured check names ("hand over or release the claim and leave the new branch name on the claim, the issue and the old PR") a command that works with today's tracker, proven in a clone (E1).

### Decisions
1. **A new lesson, under z-design.** The capture opens "z-design:", and the superseding session is a prep's lead. No existing lesson covers it: `./zn lessons supersede claim` finds only `restated-rules-move-together`, and `./zn lessons closing PR handover` finds nothing. The two nearest are its siblings from the same incident (Non-goals): c0270's is about the worker that is about to start a second prep, c0271's about the worker that keeps pushing to a closed PR. This one is about the session that closes the PR. File: `z-nile/skills/z-design/lessons/superseding-prep-hands-over-the-claim.md`.
2. **Only on the user's decision.** zz-rules **Whose claim** says a claim's ownership is documented, not checked, and "Never give back a claim you did not make; ask the user." In the incident the PR was closed "by the user's decision (2026-11-07)" (#256's first comment). The lesson keeps that order: the user decides, then the session hands the claim over. Under `ZN_DISPATCH=1` the question goes to `questions.md` like any other.
3. **"On the claim" means the claim's only memory is in the live branch's worktree.** A published claim is a `status:` line and nothing else (zz-rules, The direct-push exception: an existing document changes only in its `status:` line), so no branch name can ride on it. What binds a claim to a branch is the worktree that remembers it: `./zn status <id> preparing` writes `.cache/tracker-claim-<id>` in the checkout it runs in (`rememberClaim`, `z-nile/engine/main.luau`), and a worktree is `.worktree/<branch>` (zz-rules, Worktrees). So:
   - **Find every candidate, never judging by contents** (design review 001 F2). `./zn status <id>` prints only the state; `git worktree list | grep -e <id> -e <slug>` prints each branch; `ls <main checkout>/.worktree/*/.cache/tracker-claim-<id>` lists every worktree that remembers a claim (with the main checkout's path, so it runs from inside a prep worktree, where a bare `.worktree/` does not exist); `./zn dispatch status <id>` shows a dispatched step. A memory's text cannot decide: memories go stale (c0264's superseded worktree still remembers a claim on an issue now `done`), and a dispatched claim remembers the stamp it replaced (d0358).
   - **Take over in the live prep's worktree**: `./zn status <id> new`, then `./zn status <id> preparing` (a claim cannot be re-claimed while `preparing`: "cannot move to preparing", E1). The fresh stamp on `origin/main` is the live worktree's. `status <id> new` alone releases it when no prep continues.
   - **Remove each superseded worktree's memory**: `rm <main checkout>/.worktree/<old>/.cache/tracker-claim-<id>`. After it the listing names only `.worktree/<live branch>` (E1b, with a second stale memory seeded). The file is ignored run state in the other session's worktree; its only readers are `release` (rafts) and the carried raft move's "a claim this checkout made" (main.luau, `status`), and neither runs for an issue in a superseded prep. If the user later revives the old prep, its own claim writes the memory again. This touches another session's worktree, which is why the whole hand-over waits for the user's decision (Decision 2).
4. **"On the issue" is a dated line directly under its title, on `origin/main`, by `./zn land`** (placement fixed in design review 001 F1). The other worker reads its own document, which changes only when its sync merges `origin/main`. A capture worktree may land edits to a draft backlog issue's body (`captureScope`: "a capture edits only the title, depends_on and the sections"; `preparing` with `design: draft` qualifies). Both preps rewrite their Non-goals, Design and frontmatter, so a line under `## Design` conflicts in both, and in a prep worktree a conflicting `./zn sync` aborts the merge (`mergeOrigin`): the line would never reach the old worker and would break the live prep's next sync. The space between `# <id>: <title>` and `## Problem` is written by no prep, so the line goes there: `Prep moved (<date>): live on <branch> (PR #<n>)`, the newest on top when there is more than one hand-over. E1 commits a different rewrite of the document in each prep worktree first, then lands the line: the land is accepted, `origin/main` holds it, both preps' `./zn sync` exit 0 and each keeps its own Design and holds the line, `./zn capture <id>` still prints the original `tracker: new` commit, and the stamp, `./zn status` and `./zn lessons --check` are unchanged. It is outside the Problem and Solution, so the captured scope is not edited, and outside the sections `./zn approve` hashes (Problem, Solution, Design, Acceptance criteria, Test plan). No reader takes the text right under the title (design review 001 grepped `store.luau`, `board.luau`, `boardview.luau`).
5. **"On the old PR" is its body and a comment, then the close, when it has one.** #256's closing comment is the incident: it alone reached nobody. The lesson puts the name in the body (for a person reading `gh pr view`) and a comment (which c0271's lesson makes the other worker read, with the state, before a push: `gh pr view <n> --json state,comments`), then closes it. A prep often has no PR yet during design (design review 001 F6); then the claim and the issue's line are the places, and the lesson says "(if it has one)" so nobody opens a PR on the other worker's branch to comment on.
6. **Stop a dispatched worker.** A worker running under `./zn dispatch` reads nothing until its step ends. `./zn dispatch status <id>` shows one, `./zn dispatch stop <id>` stops its process group. The lesson names both.
7. **Short, not codifiable today.** The body is 1,298 bytes in 11 lines. The cap pinned is 1,500: the hand-over needs the four searches, the removal and the no-PR case (design review 001 F2, F6), and c0181's cap for a lesson no check enforces is 2,500 ("full 500, part 1,200, none 2,500 bytes"), so the lesson stays valid once c0181 lands. The act happens on GitHub and in another session's worktree, so nothing in the repository's text shows the mistake; once c0181 lands, the executor sets `not_codifiable:` with that reason and records the `codify` line (AC6, the same conditional c0270 uses).
8. **The executor writes the lesson; prep proved it.** The reference text is `experiments/ref-lesson.md.txt`. The executor copies it to the lesson path and appends the harvest note, so `check.sh` fails before execution and the lesson lands through its raft (the shape c0192 and c0270 use). The note: `- note PR #256 was closed with a comment that reached nobody, and the agent holding the claim on c0264 kept designing (the capture of c0272) (erred z-design): z-design/superseding-prep-hands-over-the-claim` (a note naming a lesson that does not exist fails `./zn lessons --check`, so prep does not write it).
