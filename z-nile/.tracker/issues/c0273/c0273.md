# c0273: Home rule reads project jsonc

## Problem
z-nile/tests/lib/home.luau and the project-file lister match only *.project.json, so a top-level *.project.jsonc of a home (Rojo 7.7.1 builds it, comments included, which Lune's decoder refuses) is never read by the home rule, listed, or gate-built; teach every reader of a home's project files the second format, or fail closed on it; c0246 already covers nested ones through rojo sourcemap; check: which readers of a project file list files by suffix, and what do they do with a name Rojo builds that they do not match?

## Non-goals
- Nested project files Rojo loads from a mapped folder, the `$path` spellings, links, `syncRules` and the files Rojo reads from outside the home: c0246 (the Rojo-driven check via `rojo sourcemap --include-non-scripts`).
- Reading a commented project file's mappings (a JSONC decoder for Lune): the captured Solution fails closed on a file the decoder refuses, and the Rojo-driven net still judges what Rojo reads of it.
- `default.project.jsonc` as a home's default place: the readers that name `default.project.json` (the place harness, `graph.gameRoots`, the gate's sourcemap, the beta deploy) keep that name, and the home rule keeps requiring it.
- `OLD_ROOTS` in `z-nile/lib/select.luau`: it names the two files c0120 moved out of the root, not a home's project files.

## Solution
- Run the Rojo-driven check of c0246 on every `*.project.json` and `*.project.jsonc` of a home (the lister matches both), and fail closed on a commented file the decoder refuses.
- Check the gate's builds and other readers of project files for the same suffix match.

## Design
Chore, tooling only. Captured scope kept as it is: the lister matches both names, the Rojo-driven check of c0246 runs on every `*.project.json` and `*.project.jsonc` of a home, a commented file the decoder refuses fails closed, and the gate's builds and the other readers that match a project file by suffix learn the second name.

**Quoted decisions relied on:** none of `game-design.md` (tooling only). c0246's user decision of 2026-11-08 ("3": the Rojo-driven check is the net under the readers) is what this chore extends to the `.jsonc` name; its Non-goal handed exactly this chore over ("the project-file lister (`home.luau`), the gate's builds and the other readers of project files match `*.project.json` only, so teaching them the second format is a separate chore").

**What Rojo and Lune do (E1, E2).** Rojo 7.7.1 builds and sourcemaps `x.project.jsonc` with a comment and trailing commas, and a commented `x.project.json` too. `rojo sourcemap <dir>` of a folder holding only `default.project.jsonc` uses it; a folder holding both `default.project.json` and `default.project.jsonc` uses the `.json` one. Lune's `serde.decode("json", …)` refuses a comment (`key must be a string at line 2 column 3`) and decodes a `.jsonc` that has none.

**Inventory of the readers that match a project file by suffix** (grep of `z-nile/`, `scripts/`, `zn` and every home for `project.json`, `project%.json`, `*.project.json`): (1) the home rule's lister, `z-nile/tests/lib/home.luau` (`%.project%.json$`); (2) graph's one lister `projectsIn`, `z-nile/lib/graph.luau`, behind `currentPlaces` (the server-file rule: `graph.serverFile` and `graph.srcAliasViolations`, which the "src requires" case of every home's `tests/meta/architecture.spec` runs from that home) and `graph.placeInputs` (reached only through `graph.affectedSpecs`, which only specs call since spec selection became the committed watch map in #293: `tests/tooling/affected.spec`, pickman's `c0002/affected-place.spec` and `f0061/lobby-tooling.spec`; `z-nile/affected.luau` requires no graph, design review 001 F1); (3) the selector's forcing pattern, `HOME_FULL` in `z-nile/lib/select.luau` (`[^/]*%.project%.json$`); (4) the gate's builds, `z-nile/check.sh` (the `*.project.json` glob and `basename "$f" .project.json`). Every other reader names its file: `default.project.json` (`graph.gameRoots`, `placeDirOf`, `gameRootsAt`, `place.load`'s default, the gate's `rojo sourcemap default.project.json`, `pickman/scripts/lib/beta.luau`) or `lobby.project.json` (`beta.luau`, pickman's specs). Those stay as they are, because the home rule keeps a home's default place `default.project.json` (below). `OLD_ROOTS` in `select.luau` names the two files c0120 moved out of the root; it is a record of that move, not a lister, and stays.

### `z-nile/lib/graph.luau`
- `graph.PROJECT_FILE = "%.project%.jsonc?$"`, the one pattern every lister uses, with the comment: Rojo 7.7.1 builds both names, comments included.
- `graph.isProjectFile(name: string): boolean`: `string.match(name, graph.PROJECT_FILE) ~= nil`. `x.json`, `x.jsonc`, `x.project.json.bak`, `x.project.jsonx`, `x.project.jsoncc` and `project.json` are not project files.
- `graph.projectStem(name: string): string?`: the place a project file builds, `string.match(name, "^(.*)%.project%.jsonc?$")` (`lobby` for `lobby.project.json` and for `lobby.project.jsonc`, `a.b` for `a.b.project.jsonc`), nil for any other name.
- `projectsIn` lists by `graph.isProjectFile` (it keeps its `fs.isFile` test, its name sort and its error). A file it cannot decode, a commented `.jsonc` included, stays the error naming it, which now also says why: `graph: <dir>/<name> is not a Rojo project (JSON with a tree): its mappings can't be told (a comment or a trailing comma, which Rojo builds, is not JSON to Lune's decoder)` (c0185's spec pins the text up to `is not a Rojo project`, which is kept). So the server-file rule fails closed on a commented `.jsonc` (every home's architecture spec stops, naming it), as it already does for a commented `.json`; it never skips the place. Its comment and `placeInputs`' comment say `*.project.json` and `*.project.jsonc`.

### `z-nile/tests/lib/home.luau`
- The lister keeps `name` when `graph.isProjectFile(name)`. Everything the per-file loop does then applies to a `.jsonc` unchanged: the decode, `graph.mappings`, `graph.unreadable`, the reader's `$path` lines, `maps no $path` for a file the decoder refuses (c0246's fail-closed line, which a commented `.jsonc` now gets), and the Rojo-driven net (`rojoReads`, which already reads a `.jsonc`, E1). The net's nested-project test already compares the real path of each file Rojo names with the project file itself, so a `.jsonc` is not its own nested project.
- New, right after the `maps no $path` line, for a file the decoder refuses (`ok == false`): `<name> is not JSON to Lune's decoder (a comment or a trailing comma, which Rojo builds): only what Rojo reads of it is judged` (design review 001 F5). `maps no $path` stays as the fail-closed line (c0246's spec counts it), and this line says why, which matters most for the format whose purpose is comments. It also fires for a commented `*.project.json`; no spec counts that file's other lines.
- `missing default.project.json` stays as it is: `default.project.jsonc` is not the default place (by-name readers above), so a home holding only that file is told it lacks `default.project.json`, and the file is still read and judged like any other project file.
- New, after that line: for each listed `name` that is `<stem>.project.json` (stem from `graph.projectStem`) while `<stem>.project.jsonc` is listed too, one problem `<stem>.project.json and <stem>.project.jsonc both build the place <stem>: keep one`. Why: Rojo builds a folder from its `.json` alone (E1), and the gate would build both into one `check[-<stem>].rbxl`, so the two files cannot both be meant. It is reported once per stem (only the `.json` name triggers it), `default` included.

### `z-nile/lib/select.luau`
`HOME_FULL`'s project-file entry becomes `"[^/]*" .. graph.PROJECT_FILE` (select already requires graph): a change to a home's top-level `*.project.jsonc` forces that project, as a `*.project.json` does. A nested `src/x.project.jsonc` is no place of the home and forces nothing, as before for `.json`.

### `z-nile/check.sh`
- After the `for f in "${p}"*.project.json; do …; done` line (kept exactly, f0061's `lobby-tooling.spec` pins it), a second line: `for f in "${p}"*.project.jsonc; do [[ -f $f ]] && places+=("$h|$f"); done # Rojo builds both names (c0273)`. So `--plan` lists a home's `.jsonc` builds after its `.json` ones, and c0120's pinned plan of a tree with no `.jsonc` is unchanged.
- The stem: `stem=$(basename "$f")`, `stem=${stem%.project.jsonc}`, `stem=${stem%.project.json}`, so `lobby.project.jsonc` builds into `.cache/check-lobby.rbxl`. Where a `default.project.jsonc` would land is no rule (design review 001 F4): the home rule refuses every home that holds one (alone it is `missing default.project.json`, beside `default.project.json` it is the same-place line), and the gate's `rojo sourcemap default.project.json` fails for a home without the `.json`.
- The header comment's `builds:` line says `every p/*.project.json and p/*.project.jsonc`.

### Scalability
One more `fs.readDir` match per entry and one stem pass over a home's handful of project files; the net's cost is per project file as in c0246 (about 30 ms each), and a `.jsonc` is one more file only where a home has one (none today).
### Maintainability
One pattern, `graph.PROJECT_FILE`, behind the two Luau listers and the selector, and one stem function; the shell gate cannot require Luau, so its two globs and two suffix strips sit beside each other with a comment naming c0273, and AC5 pins them by behaviour. A third Rojo spelling later is one edit to the pattern plus the gate's lines.
### Usability
A `.jsonc` author gets the same lines a `.json` author gets. A commented file is told `maps no $path` and, on the next line, that it is not JSON to Lune's decoder (a comment or a trailing comma) so only what Rojo reads of it is judged; it still gets every line the Rojo-driven net finds, and graph's error says the same. A home with both names of one place is told which place and to keep one.
