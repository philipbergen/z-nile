# c0274: Take over lost claim

## Problem
Scope decision (user, 2026-11-08): "yes go ahead and split the whole thing up and tie them togetjer in a raft so we can run through these a layer at a time in a PR" (c0265's design was split into c0265, c0274, c0275, c0276 and c0277, one raft, delivered a layer at a time in depends_on order; this issue carries c0265's takeover outcomes).

Carried from c0265's capture (User, 2026-11-07): "anything that is in progress but lost ... is higher than anything that is not yet started". Lost work is found and listed by c0265; this issue makes it resumable:
- **The next worker resumes it.** A lost claim (c0265's verdict) is taken over by the next claim of it, a lost `preparing` claim directly by `./zn status <id> preparing` (and `<R-id>` for a rafting claim, its members following), a lost readied raft by stop then ready.
- **A worker that takes over lost work does so as a normal claim, and the takeover is recorded (c0263).**
- **The old owner learns it lost the claim if it comes back**, and its late moves are refused.

Decided with the user (2026-11-07): "ok" (a lost `preparing` claim can be taken over directly).
Decided with the user (2026-11-07): "refuse" (the old claimant's carried `status prepared` is refused once the claim's stamp has changed).
Decided with the user (2026-11-07): "ok" (takeover branch handling: a taker continues from the old agent's pushed branch where one exists, else starts fresh; a lost rafting claim the same way, members following).
Decided with the user (2026-11-08): "If a job is taken over the take over deletes the heartbeat branch and creates a new one, this would tell the process that it lost the owernship if it comes back around." (from the heartbeat-branch decision quoted in full in c0265).

## Non-goals
- The heartbeat, the lost/parked verdicts, `./zn lost` and the `status` markers: c0265.
- Beating without being asked (claim paths, every `./zn` command, long commands, the dispatcher): c0275.
- The worktree a taker works in, and what happens to the old worker's worktree: c0277.
- The board: c0276.
- Several hosts racing for one item: c0254.

## Solution
A lost claim (c0265's verdict) is taken over by the next claim of it, with the same commands that make any claim: `./zn status <id> preparing` on a lost `preparing` claim (an issue's, or `<R-id>` for a rafting claim with its members following), and `./zn stop <R-id>` then `./zn ready <R-id>` on a lost readied raft. Only a lost verdict, judged for the stamp `origin/main` still holds at the moment of the publish, allows it; every other verdict keeps today's refusal and names why. The takeover is recorded in the claim commit's subject, deletes the old owner's heartbeat branch and creates the taker's in one atomic push (the user's design), and the old owner is told when it comes back because a checkout remembers the stamp of the claim it works under (`.cache/tracker-stamp-<id>`) and a beat, the carried `status <id> prepared` and `./zn done` are refused when that stamp is not the one `main` shows.

### The change
Pure (`z-nile/engine/heartbeat.luau`, no I/O):
```
heartbeat.takeoverPlan(oldStamp, newStamp, epoch, beats): Push        -- create the taker's branch (create-only), delete the old owner's with a lease on its sha
heartbeat.canTakeOver(kind, judgedStamp, originStamp): boolean        -- only "lost", and only for the stamp origin still holds
heartbeat.takeoverRefusal(id, kind, silent, why?): string             -- "claim alive: last heartbeat 2m ago, limit 15m" | "claim parked (...)" | "<id> has never beaten: not lost, no takeover" | "no heartbeat verdict: <why>"
heartbeat.holds(remembered?, originStamp?): "held" | "unheld" | "taken" | "ended"
heartbeat.lostText(id, originStamp?): string                          -- "<id>'s claim was taken over (now <stamp>)" | "<id>'s claim ended" (main.luau's lostText delegates)
```
Engine edge (`z-nile/engine/main.luau`, the one place that reads and writes):
- **The claim memory.** `rememberStamp(id, stamp)` writes `.cache/tracker-stamp-<id>` (a file of its own: `.cache/tracker-claim-<id>` keeps c0116's meaning, "this checkout owns the rafting claim", which `release` and `fold` read). Every claim publish of a worktree remembers its stamp: `status <id> preparing` (an issue's, a raft's, a takeover's), and `rememberClaim` (`new raft`, `fold`, `unfold`, `recombine`) writes both files. `ready` and `stop` run in the main checkout, which holds no work and remembers nothing. `stampMemory(id)` reads the stamp file and, when absent, `.cache/tracker-claim-<id>` (a worktree that claimed before this landed). The memory ends only with its checkout or with a claim-ending command run in it (`status <id> new` drops it, `release` drops its members', `done` drops a raft's work claim; `stop` and `ready` run in the main checkout, which remembers nothing, so they end no worktree's memory); **never by the observation that triggers a refusal** (dropping it would let the old owner's next move through).
- **`./zn beat <id> [--watch] [--adopt] [--stamp S]`.** After c0265's refusal of an item that is not a claim (checked first: the refusal order is c0265's constraint), the beat is bound to the stamp its checkout remembers, `heartbeat.holds(memory, main's stamp)`: `taken` refuses (exit 1) with `<id>'s claim was taken over (now <stamp>)`, `--adopt` included (**adoption never overrides a remembered different stamp**), and so does a restarted `--watch` loop; `unheld` and no `--adopt` refuses with `beat: this checkout does not hold <id>'s claim (use --adopt to take it on)`; `--adopt` is the stated way to take on a claim the checkout did not make (z-run in a raft's worktree after `ready`), it beats origin's stamp and remembers it in a **worktree** (the main checkout holds no work and writes none). **No worktree re-adopts a claim over a remembered different stamp** (the user, 2026-11-12: "Drop in-place re-adoption"): a lead who stops and re-readies its own raft continues in c0277's numbered worktree copy like any taker, and the old worktree stays refused. A taker's stop and the owner's stop are the same two commands, so there is no fact the engine could read to tell them apart without the holes four review rounds found in every attempt. `--adopt --stamp S` (the dispatcher's form) refuses with the takeover text when `main` no longer shows `S`, and writes no memory; `--stamp` without `--adopt` is refused. `--adopt` joins `flags`' boolean list; the usage line names `--adopt` and `--stamp`.
- **The takeover, in `setStatus` (`status <id|R-id> preparing`).** When the target is already a stamped `preparing` claim on `origin/main`, `judgeAll` runs once before the publish (one `git log -S` per claim, the beats, and the pull requests only when some claim is stale), and the verdict travels into `publish.commit`'s build callback, which calls `heartbeat.canTakeOver(kind, judgedStamp, originStamp)` with the stamp **origin holds at that moment** (the push is the lock: a claim restamped since the verdict is refused naming the new stamp, and the callback runs again after a lost push race). Anything but an explicit lost verdict keeps c0053's refusal text `<id> is preparing on origin/main: cannot move to preparing` and appends why (`takeoverRefusal`): `claim alive: last heartbeat <n>m ago, limit 15m`, `claim parked (...)`, `<id> has never beaten: not lost, no takeover` (a `[no beat]` claim), or `no heartbeat verdict: <reason>` (anything unreadable: the beats, the pull requests, a malformed beat branch with its cure, or an item that is no stamped claim). An **issue whose stamp a raft on origin also holds is taken over only through that raft** (`c0030 holds R0011's claim: take it over with ./zn status R0011 preparing`; `./zn lost` lists members separately, and a member taken alone would split the stamp and delete the raft's shared branch), and a raft takeover **refuses with the member named** when a member holds a claim of its own under another stamp. A lost claim is restamped with `freshStamp("preparing")` (the same draw every claim makes), its members that hold the old stamp following in the same commit; the build sets `takeover = { old }` and the **subject** is `tracker: <id> preparing (takes over <old stamp>)` (c0263's "recorded", where `git log` shows it). After the publish and the merge the checkout remembers the new stamp (an issue's takeover also writes the c0116 claim file, as any issue claim does; a raft's takeover also writes the c0116 claim file, so the taker becomes the rafting owner and can fold, unfold and release it, while the old owner's `release` is refused). A beat that lands between the verdict and the publish does **not** save the claim: the publish is the lock, and the swap deletes whatever branch the old stamp has (the lease is the sha read, re-read once).
- **The branch swap** (`swapBranches`): after the publish, **one atomic push** (`git push --atomic --force-with-lease=<new>: [--force-with-lease=<old>:<sha read>] origin <commit>:<new> :<old>`), the commit being `main`'s tree with `main`'s tip as parent, authored by the checkout's own identity (c0265's rule), through the bounded network wrapper. An old owner that beat meanwhile makes the lease fail the whole push (atomic: the taker's branch is not created either); the swap re-reads the beats and repeats once. A second failure is said on stderr (`takeover: <id>: the heartbeat branch swap failed (<git's message>); the claim stands`) and does not fail the claim: `main` shows the new stamp, so the old owner's stamp-bound beat is refused anyway and the pruner deletes the old branch once it is unclaimed and old. An old owner that beats the deleted branch later finds its lease rejected, and the server does not let it recreate it (c0265's E10; E1 below ran the atomic form on the real origin).
- **Telling the old owner.** The carried `status <id> prepared` (checked **first inside the build callback**, before the member design check, so a raft whose member is still `design: draft` is refused as "taken over" first) and `./zn done <R-id>` (for the work stamp, `active-…`, this checkout adopted; checked before the clean-tree check) compare `heartbeat.holds(memory, origin's stamp)` and refuse on `taken` or `ended` with `<id>'s claim was taken over (now <stamp>): this checkout's work is no longer the claim's; stop here (./zn lost lists lost work to pick up)`. **The old owner's late give-back is refused too**: `status <id> new` (and `<R-id>`) from a checkout whose memory reads `taken` is refused before the publish with the same text, because it would end the taker's live claim (the captured "its late moves are refused"); a checkout that remembers nothing gives back as today, so zz-rules' "ownership is documented, not checked" holds for everyone who has no proof it lost the claim. `done`'s check fails open where origin cannot be read (nothing to compare; the same as a checkout with no memory), and the memory is keyed by id, so an id compaction or `renumber` (which keep the stamp) leaves a worktree remembering nothing under the new id, which passes. A checkout with **no memory** passes, as today (a worktree made before this landed runs its own engine and is not told: "Existing work" below); a checkout's own re-claim updates its memory, so c0053/commands-prep's flow stays green.
- **`stop`** stays open to anyone (the user's documented "ownership is documented, not checked") but now **judges the claim it gives back** (the main checkout already fetches; one `judgeAll`, read before the give-back, fail closed: unreadable beats leave no verdict, unreadable pull requests leave only the stale verdicts unsettled, so a live raft still records live) and writes the verdict in its subject, `tracker: stop R0010 <title> <note>`: `(claim <stamp>)` when the claim was live or parked, `(claim <stamp>, lost <n>m)` when lost, `(claim <stamp>, unjudged)` when nothing could be read or the claim never beat. The note is a record only: nothing reads it back. A takeover of a lost readied raft (**stop, then ready**) is therefore recorded as one in `git log`, and the old lead's `done` is refused by the stamp it adopted. The skills tell z-run to take over only a raft `./zn lost` lists.
- **Both memory files end together**: `cm.drop` removes `tracker-stamp-<id>` and the c0116 `tracker-claim-<id>` that `cm.read` falls back to, so a raft given back with `status <R> new` is never later told it was "taken over".
- **A takeover restamps every carrier of the old stamp** in the one commit (a recombine's other raft, a member claimed with it) and the taker becomes the c0116 owner of every raft among them: the claim is the stamp, so there is one claim, one branch and one swap.
- **`release` is a give-back too**: a checkout whose memory reads `taken` is refused before anything, with or without `--force` (`--force` is the user's word that a claim is abandoned, not for a checkout that holds proof it lost it).

### Assumptions to veto
- The owner who stops and re-readies its own raft continues in c0277's numbered copy; the old worktree stays refused (decided by the user, see Unknowns & experiments, "Drop in-place re-adoption"). The keep path in z-stop step 4 therefore waits on c0277's `worktree --takeover`.
- **`stop` and `ready` do not check the lost verdict**: `./zn stop` stays open to anyone (the user's documented "ownership is documented, not checked"), so a lost readied raft is taken over by stop then ready and the skills tell z-run to do it only for a raft `./zn lost` lists; the stamp in the subject is the record. The alternative (stop refusing a live raft) changes a documented rule and is not taken.
- **A lost `preparing` claim's refusal text is one line per cause** (`claim parked (an open pull request or a dispatcher waiting on questions.md names it)` does not say which; the earlier design had two texts).
- **The memory is per worktree, per item, and ends at a claim-ending command or with its checkout**: a human who gives a claim back from another worktree leaves the first worktree's memory, which then reads "taken over"/"ended" if it comes back (correct: it lost the claim).

### Scalability
A takeover costs one `judgeAll` (one fetch of the hb branches, one `git log -S` per claim, one `gh pr list` only when some claim is stale), the publish it would make anyway, and one atomic push of a one-commit pack. A beat gains one file read. Nothing runs for a claim that is not already a claim.
### Maintainability
`heartbeat.luau` stays the one reader and writer of the beat format and now also owns the takeover's decisions (`canTakeOver`, `takeoverRefusal`, `holds`, `lostText`); `main.luau` has one place for the memory (`stampFile`, `rememberStamp`, `dropStamp`, `stampMemory`) and one for the swap (`swapBranches`); the sibling layers add to these, never a second format or a second memory.
### Usability
The refusal says why and what to do (`claim alive: …`, `has never beaten: …`, `no heartbeat verdict: <reason and its cure>`), the old owner is told what happened to its claim and to stop, and the takeover is visible in `git log` and on `./zn lost` going quiet.
