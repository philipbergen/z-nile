### F1 [high] The owner's re-adoption reads only the raft's stops, so a rafting claim that is made, goes lost and is taken over between the owner's live stop and the next `ready` is invisible: the old lead's plain `--adopt` takes the new claim and its `done` passes (repeat of design-review-003 F1's mechanism)
Where: prototype main.luau:1769-1783 (`readoptable`: `git log -S "status: <current>"`, then `git log -1 --grep "^tracker: stop <R-id> " <oldest>^`); c0274.md Design, the `./zn beat` bullet ("only when the raft's claim history on `origin/main` runs straight from the remembered claim to the current one … nothing came between the two claims (a worktree left behind while a later claim went lost and was taken over is refused …)"); AC3 ("a worktree left behind while a later claim went lost is refused"); the prototype's zz-rules Heartbeat paragraph ("when its `stop` recorded the claim live or parked and no other claim came between"); Rules row T1.
Evidence: PROBE R, on the bare prototype (one readied raft R0010 with member c0040, prepared; worktrees wt2, wt3 and wt4; a fake `gh` that lists no pull request; `AT = T0 + 12*STALE`):
1. The main checkout readies R0010 (A = `active-badger-badger-violet`). wt4 syncs and runs `beat R0010 --adopt` at T0+100, so its memory is A.
2. The owner's keep path: the main checkout's `stop R0010` at T0+200 writes `tracker: stop R0010 Lost (claim active-badger-badger-violet)`.
3. wt3 claims the prepared raft for re-rafting, `status R0010 preparing` (P = `preparing-falcon-mongoose-raging`), and runs nothing after. At AT `./zn lost` lists `R0010 preparing 179m`, and wt2 takes it over: `tracker: R0010 preparing (takes over preparing-falcon-mongoose-raging)`.
4. The taker's rafting PR lands, which sets `prepared-lucky-violet-heron` on main (modelled as one commit pushed from `other`). The main checkout readies R0010 again (B = `active-heron-falcon-plucky`).
5. wt4's plain `beat R0010 --adopt` at AT+20: `ok=true code=0`, and its memory becomes B. wt4's `done R0010` passes the stamp check and stops later, at `no review-NNN.md: run the adversarial code review first`.

main's history, newest first: `tracker: ready R0010 Lost`, `Merge pull request #9 …`, `tracker: R0010 preparing (takes over preparing-falcon-mongoose-raging)`, `tracker: R0010 preparing`, `tracker: stop R0010 Lost (claim active-badger-badger-violet)`, `tracker: ready R0010 Lost`. The latest *stop* before B's `ready` is still the owner's live stop, so `stopAllowsReadopt` says yes.
Critique: The Design promises that nothing came between the two claims, and that a worktree left behind while a later claim went lost and was taken over is refused. zz-rules says it to every agent. A rafting claim is a claim of the raft (`preparing-…`), and here it went lost and was taken over, yet the old lead is let in. The path is an ordinary one. A readied raft is stopped and readied again (z-stop step 4) most often to change it with z-raft, and `fold`, `unfold`, `recombine` and `status <R-id> preparing` all claim it in between. c0277 does not cover it. Its `--takeover R0010` by id picks the worktree whose memory matches main's stamp (the rafting worktree that holds P), so the old lead's worktree is never discarded. c0275 only tells it once. So the final tree has two leads for B, the old one with work for a member list the re-rafting may have changed, and check.sh passes. This is the fourth hole in the re-adoption mechanism: round 1 refused the owner; round 2's `--replace` let anyone in; round 3 searched the remembered stop anywhere and let any `preparing-` memory in; round 4 reads one kind of commit (a stop) and calls it the chain. The tempting fix is to add the rafting subjects (`tracker: <R> preparing`, `fold into`, `unfold from`, `recombine`) to the grep. That is still a list of subjects, which the next command that claims a raft escapes.
Consequences: The fact to read is that the status the current claim replaced is the one the remembered claim's stop wrote. Bind the two by value, not by searching for a type of commit. `stop` writes a fresh `prepared-W`; any claim made in between rewrites the raft's `status:` (a claim, its takeover, the carried `prepared` its pull request lands); `ready` replaces whatever is there. This brings new edges:
- An owner that re-rafts its own raft between its stop and its ready is refused, which fails closed: it continues in c0277's numbered copy, so z-stop step 4 must say re-adoption holds only when nothing claimed the raft in between.
- A docs-only edit of the raft's document between stop and ready leaves `status:` alone, so it still lets the owner in.
- `prepared-W` comes from `stamp("prepared")`, which is not checked for uniqueness (24 words), so a carried `prepared` after a claim in between can draw W again. The read must take the newest commit before the `ready` that changed `status: <W>` in the raft's document, which is the commit that wrote the value the `ready` replaced, and require that commit to be the stop. The oldest such commit would still be the stop after a redraw, and would let the old lead in.
- Scoping every read to the raft's document (`-- '*/rafts/<R-id>/<R-id>.md' '*/rafts/active/<R-id>/<R-id>.md'`) also drops the cross-raft stamp collisions (24 words) and the `--grep` matches on message bodies (zz-arch/history-tests-survive-squash: match the subject only).

I sketched this read in a third scratch clone: steps 1 to 3 below, without the path scoping of step 1, and taking the oldest commit in step 3, which is the same commit when nothing was redrawn. PROBE R's `--adopt` then exits 1 with `R0010's claim was taken over (now active-indigo-silver-copper)`, wt4's memory stays A, and `done` is refused with the takeover text. takeover.spec's 11 cases still pass, the owner's keep path among them.
Recommendation: Question the mechanism. Make `readoptable`, in this order:
1. Find the commit that introduced `current`: the oldest `-S "status: <current>"` commit on origin/main, scoped to the raft's two document paths.
2. Read the raft's `status:` in that commit's parent. It must be a `prepared-…` value W.
3. The commit that wrote that W must have a subject that `heartbeat.stopAllowsReadopt(subject, remembered)` accepts. That commit is the newest that changed `status: <W>` before it: `git log -1 --format=%s -S "status: <W>" <intro>^ -- <the backlog path>`.
Anything else is a refusal.

### F2 [medium] The old rafting owner's member moves are not refused: its `status <member> new` gives back part of the taker's claim, and its carried `status <member> prepared` goes through, because the stamp check reads only the item's own memory while the claim is the raft's stamp

Critique: The takeover moves the members with the raft because the claim is the stamp. But the old owner's proof that it lost the claim (its memory) is looked up under the item's id, and a member has none. So the old rafting owner splits the taker's claim. c0030 is now `new` inside the taker's raft, and the taker's carried `status R0010 prepared` then refuses with `c0030 is new on origin/main: claim it first …` (read at main.luau:2129-2131, not run).
