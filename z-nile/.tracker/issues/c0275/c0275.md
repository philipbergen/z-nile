# c0275: Automatic heartbeats

## Problem
Scope decision (user, 2026-11-08): "yes go ahead and split the whole thing up and tie them togetjer in a raft so we can run through these a layer at a time in a PR" (c0265's design was split into c0265, c0274, c0275, c0276 and c0277, one raft, delivered a layer at a time in depends_on order; this issue carries c0265's automatic-beat outcomes).

Carried from c0265's capture (User, 2026-11-07): "we need agents to update a heartbeat on a ticket every 5 minutes". c0265 gives the beat (`./zn beat`); an agent that must remember to run it will forget, and a claim that is worked but not beaten reads lost after 15 minutes. What should happen:
- **A claim beats from the moment it is made** (every claim publish gives the first beat).
- **A session that keeps working keeps its claim alive**: an agent's own `./zn` commands in its worktree beat its claim, throttled to one beat per interval.
- **"A beat built into ... long `./zn` commands"** (c0265's capture, Solution): long commands beat while they run.
- **The dispatcher beats the item a model step works on** while the step runs.
- A beat never fails the command it rides on, and never runs inside a check or spec flow of the real repository.

## Non-goals
- The beat itself, its storage and the verdicts: c0265.
- Which claim a checkout owns and what an old owner is told: c0274 (an automatic beat is bound to it).
- z-work's own loop: c0253 (it calls the same beat).
- The board: c0276.
