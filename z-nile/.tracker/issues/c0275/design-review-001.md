### F1 [high] The pinned beater proof fails on the prototype: case 2 deletes the claim memory before the beater has started its loop
Where: proofs/beater.spec.luau, "a beater ends, saying why, when its worktree no longer holds the claim" (lines 105-122); check.sh AC3 (hash d7ca2a10…); Unknowns E5 and E7 (E26), and the Design's statement "Every sequestered spec below passes on it".
Evidence: I ran `lune run tests/run -- tests/acceptance/c0275/proofs/beater.spec.luau` on bd929cad twice. Both runs gave `FAIL … beater.spec:121: expected true, got false`. The worktree's `.cache/tracker-beater/c0101.log` reads:
```
bounded: the caller's CPU limit … it stays
beat: this checkout does not hold c0101's claim (use --adopt to take it on)
bounded: … / beat: this checkout does not hold c0101's claim … (twice more)
```
The case reads the pid, sees it alive and deletes `tracker-stamp-c0101` and `tracker-claim-c0101` within milliseconds of the claim command's return. The beater is still booting at that point (bash `zn`, two `git` calls, `bounded.pl`, `lune`, the fence, a fetch). When it reaches c0274's binding check in `cmd.beat`, the memory is already gone, so it exits with the refusal and never enters its loop. `endsWithin` passes and the log assertion fails. The memory-gone path is exercised only by case 3, and case 3 asserts no text. A claim that has been given back also stops through `stop-restamped`, so case 3 cannot kill E26 ("memory test replaced"). E26's recorded kill is therefore unproven. The log also shows a second defect. The case-3 commands in the same worktree restarted the c0101 beater three times, each refused at once. `hb.autobeat` calls `hb.ensureBeater` for every mark, but nothing checks that the worktree still holds the claim. A worktree whose memory is gone but whose mark remains therefore starts a beater on every command, and each one fetches `main` before it refuses.
Critique: AC3 is sequestered and pinned by hash. The executor cannot edit the proof, so `./zn check c0275` and `./zn done` fail on a correct implementation. The tempting fix is a sleep before the deletion, which is still a race.
Consequences: if the case first waits for the beater's first push, it tests the loop's memory stop for real. The hash must be re-pinned and E5 rerun. If `ensureBeater` refuses where the memory is gone, the beater's start rule gains a fact (`held`).
Recommendation: in case 2, wait (bounded, as `endsWithin` does) until `pushes()` has grown since the claim before deleting the memory, then assert the log line. Re-pin the hash. Rerun E5 and E26 and record three consecutive green runs with their date. Add `held` (this worktree's memory names the mark's stamp) to `heartbeat.BeaterFacts`, so a worktree that no longer holds the claim starts no beater. Add a plan case for it and an autobeat case: delete the memory, run two commands, and `starts()` is unchanged. Add a Rules row for each.

### F2 [high] `/clear` ends the session but not its beater: Q1's "stops when the session ends" holds only when the `claude` process exits
Where: Design, "The background beater" (`--session <pid>` ended); Assumptions to veto ("`/clear` and the session-end hook stop a session's tool shells, not it; it stops itself on `--session`"); U1; the prototype's `reap.isBeater` comment ("a session end by the session rule"); Test plan, reap line ("at a session end it is stopped").
Evidence: `scripts/hooks/session-end.sh` runs `./zn reap --session-end` for every reason except `resume`, so `clear` included. AGENTS.md says "A `/clear` ends the background commands of the conversation it clears". A `/clear` keeps the `claude` process, and the hook runs inside it. The beater's `--session` is that pid, so `kill -0` keeps succeeding. The reaper's session rule stops only direct tool-shell children of `claude` (`p.ppid == opts.under and reap.isToolShell`), while the beater's ppid is 1, and `underBeater` now waives the orphan rule for it. reap.spec's third case asserts that a beater survives a session end (`{200}` only). After `/clear` the claim therefore keeps beating for up to its hour: the last beat comes about 50 min after the last command, so it reads live for about 65 min while nobody works it and nobody can take it over. U1 asks whether the beater ends "within a minute of the `claude` process ending" after a `/clear`. The process does not end, so that half of U1 fails by construction, and its fallback ("the SessionEnd hook could run a beater sweep") is the design this needs now, not a later question for the user.
Critique: the user decided "stops when the session ends", and this repository's own definition of a session end includes `/clear`. Leaving the hour to bound it narrows a captured decision.
Consequences: a later conversation in the same process that works the worktree gets the beater back at its next `./zn` command, with the same `--session` pid. `resume` must not stop it, and the hook already exits early on `resume`. A subagent's end fires no SessionEnd: unchanged. Another CLI's beater carries no `--session`: unchanged (its hour and its worktree bound it). A beater stopped mid-push is harmless: the push is atomic on the remote, and its pid file names a dead pid, which already means "restart".
Recommendation: the session-end reaper stops a beater whose command line carries `--session <under>`. That is one clause in `reap.decide` (why: "started by the session that is ending") plus a pure `reap.beaterSession(command): number?`. Add a reap.spec case with `under = 50`: a beater with `--session 50` is stopped, and one with `--session 77` or none is spared. Add a Rules row. Correct the reap.luau comment, the Test plan line, zz-test's reaper sentence and U1, which then probes only a real process exit. With this, AGENTS.md's "the session-end reaper catches anything left" stays true.

### F3 [medium] The detach never waits for its new parent, so the beater survives only by a race
Where: prototype `hb.DAEMON` (main.luau); Design ("a double fork and `setsid`, then it waits until it has been left to its new parent before it `exec`s the runner"); E1; the lesson detached-helpers-meet-the-reaper.
Evidence: `my $orig = getppid();` runs in the starter perl before `fork`, so `$orig` is the engine's pid. In the child, `getppid()` is the starter perl's pid, which differs from `$orig` from the start, so the loop ends on its first pass. Probe of the same loop, with the parent kept alive for 1 s (`./zn run --time 20 -- perl -e …`): `child waited 0 iterations; ppid now 12610 (the living parent); orig (grandparent) 12489`. There is one fork, not two. `bounded.pl` records `$origppid = getppid()` when it starts and stops its command with exit 123 when that changes. The beater lives only because the starter perl (`print; exit 0`) usually exits before the child has exec'd bash `zn`, two `git` calls and `bounded.pl`. On a loaded host the child can win. `bounded.pl` then records the short-lived starter, sees ppid 1 within 0.2 s and stops the beater ("the process that started it is gone"). The next command restarts it, but meanwhile a waiting session has no beater. The proofs pass by timing.
Critique: a longer sleep before the `exec` is the tempting fix, and it is still a race.
Consequences: comparing with `$$` (the starter's pid) makes the child wait for the reparent, which also works with a Linux subreaper (new parent ≠ 1). If the wait expires, the child must exit instead of exec'ing a runner that would stop at once.
Recommendation: `my $orig = $$;` before the fork (or a true double fork), and exit when the wait expires. Record a prep probe (E1d): run the DAEMON 50 times under a parallel load with a command that prints its `getppid`, and get the new parent every time. Add a `reasoned` Rules row naming that probe (a spec cannot observe the race). Fix the Design's "double fork" wording and the lesson's "How to apply".

### F4 [medium] Every beater records itself as a `./zn run` measurement and adds up to about an hour of wall to the claimed ticket's spend
Where: Design, "The background beater" and "The dispatcher" (`zn run --time 60 -- zn beat … --adopt --stamp`); `zn` lines 8-25; bounded.pl 141-154; zz-test ("A finished `./zn run` … appends one line to that checkout's `.cache/measure.tsv`"); zz-rules, the `commit` row.
Evidence: `./zn run` sets `ZN_MEASURE_BUFFER=1` and `KIND=run` whenever `ZN_MEASURED` is unset, and `bounded.pl` appends one `run` line with the wall and CPU to `$ZN_TOP/.cache/measure.tsv` when its command ends. Only the gate and the spec runner set `ZN_MEASURED` (tests/run.luau:94, 348). A claim made from a tool shell therefore starts a beater that, when it ends (its hour, its session, its claim), adds up to about 3300 s of wall to the worktree's buffer. The buffer attributes it through `.cache/tracker-focus`, and `./zn commit`, `spend` and `done` fold it into `spend.d/<writer>.tsv` as an `other` row. Each beater-hour adds about an hour of measured wall to the ticket. The dispatcher's child adds a `run` line to the main checkout's buffer every interval of every step. The proofs run with `ZN_MEASURED=1`, so none of them can see it.
Critique: this corrupts the measured spend that zz-stats reports, and nothing guards it.
Consequences: setting `ZN_MEASURED=1` in the beater's environment (in the DAEMON, before the `exec`) leaves `beaterArgv`, plan.spec's pin and `reap.isBeater` unchanged. The dispatcher's child takes the same variable in its env.
Recommendation: start both with `ZN_MEASURED=1`. Add an autobeat case: the fake `perl` records `$ZN_MEASURED` beside the start, and the claim command runs with `ZN_MEASURED` unset. Add a reasoned or spec'd row for the dispatcher's child.

### F5 [medium] Always-on heartbeat fetches share `refs/remotes/origin/main` with the commands' own fetches, which do not retry
Where: Design, "Every `./zn` command", "Long commands", "The background beater", "The dispatcher"; Scalability; c0265's `hb.beatPaths` (`git fetch -q origin main`) and `hb.readBeats`; main.luau's own fetches (`mergeOrigin` at 1506 and about 25 other `sh.git({"fetch", …})` calls, which throw on failure).
Evidence: `git fetch origin main` also updates `refs/remotes/origin/main` (the opportunistic tracking update), a ref every worktree shares. When two processes update one ref at once, one of them fails with "cannot lock ref". c0265's `hb.netRetry` comment says so, and dispatcher.luau:174-180 moved the dispatcher's own fetches to private refs for this reason. With this layer, every held claim has a beater fetching `main` every 300 s, the ticker fetches from inside `done` and `land` while their own fetches run, and the dispatcher's child fetches in the main checkout at every interval of every step. A command's unretried `sh.git` fetch that meets one of these while `main` has moved throws, so a claim's `mergeOrigin()` or `done` mid-landing fails. Before this layer that took two people's commands in the same second.
Critique: "a beat never fails the command it rides on" is broken indirectly, and the chance grows with the number of claims held.
Consequences: (a) the heartbeat reads into a ref of its own: `git fetch --refmap= origin +refs/heads/main:refs/zn/hb-main/<worktree name>`. c0265's `originTree`, `claimStampOf` and `claimsOf` already take an `at` ref. There is one ref per worktree, overwritten each time and deleted with the worktree. (b) Alternatively, the engine's own fetches get the lock retry, but that is about 25 call sites outside this layer.
Recommendation: (a), with an autobeat case: with origin's `main` moved, an autobeat leaves the worktree's `refs/remotes/origin/main` where it was. Add a Rules row.

### F6 [medium] `hb.begin` asks two git calls and a non-quiet guard before it reads the marks folder
Where: prototype `hb.autobeat` (`if inMainCheckout() or not hb.mayBeat()`), `hb.mayBeat` = `publishing()`, `goneNow` in `cmd.beat`; Regression guard ("behaves as before (no extra network call, no output): `hb.begin` reads one folder"); Chore checklist ("outputs gain, at most, one stderr line"); Scalability ("three local checks").
Evidence: (1) `inMainCheckout()` runs `git rev-parse --show-toplevel` and `git worktree list --porcelain`, and `publishing()` runs `git remote get-url` and `guarded()` (bash sourcing fence.sh). Measured here with 60 worktrees: 53 ms for the fence answer and 76 ms for the git calls, so about 0.13 s is added to every non-read-only command in every worktree, marks or not. (2) `publishing()` calls `guarded()` without `quiet`. In a protected worktree it writes `not publishing: <cwd> is protected by the repository guards (a check run)` on stderr. Every nested non-read-only `./zn` in a check.sh run inside a worktree (`./zn lessons --check`, `./zn sync`, …) gains that line, although it publishes nothing. The protected case asserts only `nested.ok`. c0276's prep asks `guarded(true)` first, quietly, for this reason. (3) `goneNow` evaluates `inMainCheckout()` every 5 s, which is two git spawns per beater. After a `git worktree remove` (the proof only moves the folder), `sh.git` throws "Unable to read current working directory", so the loop dies through `fail` instead of saying "its worktree is gone".
Recommendation: read `hb.markIds()` first and return when it is empty. Then use a quiet guard (`publishing` with a quiet flag, still the one reader). Compute "is the main checkout" once before the watch loop, and test `fs.isDir(home)` before anything that spawns. Cases: the protected case asserts no `not publishing` on stderr. A no-mark worktree's command has an empty stderr. A proof (or an existing proof's variant, re-pinned with F1) removes the worktree with `git worktree remove --force` and expects "its worktree is gone". Correct Scalability.

### F7 [medium] Rules and mutants: rules the Design states, two of which the layer rule says are pinned, have no case
Where: Design, the layer rule ("Kept by every layer, and pinned here: … the commands that never autobeat (`beat`, `run`, `reap`, and the read-only ones)"), "Ends of a claim", "The first beat of a claim"; the Rules and mutants table.
Evidence: (a) No case runs `beat`, `reap` or a read-only command in a worktree with a due mark and checks that nothing beat. A mutant that drops `beat` or `reap` from `hb.begin`'s exemptions passes every case, and c0277 relies on `reap`'s. `run` never reaches the engine, because `zn` execs `bounded.pl` before Lune, so that exemption is dead code and cannot be pinned. (b) `hb.dropBranch` deletes "only when no claim on `origin/main` still holds that stamp". Members of a rafting claim carry the raft's stamp, so a mutant without that check deletes a live raft's branch when a member is given back, and no case catches it. (c) The first beat runs "before `mergeOrigin()` can exit", which c0276's hand-off relies on. A mutant that moves it after `mergeOrigin()` passes, because no case's merge fails. (d) The "main checkout reads no mark" row is false as written: `hb.attempt` reads `.cache/tracker-beats/<id>` in the main checkout (`ready`, a main-checkout `--adopt`, the dispatcher's child). A stale or planted file there gives a wrong lease and one rejected push.
Recommendation: add cases for (a) a due mark, then `./zn members` and `./zn reap --dry-run` in that worktree, with `hbPushes()` unchanged (drop `run` from the pin and from `hb.begin`); (b) a rafting claim with a folded member, give the member back, and the raft's branch stays; (c) a shim that makes the merge after a claim fail, and the claim's branch still exists. For (d), make `hb.attempt` skip `readMark` in the main checkout and extend the planted-mark case to `ready`. Add one row each.

### F10 [low] Smaller gaps
Where: Design, "Ends of a claim", "The background beater", Usability; check.sh AC4.
Evidence: (a) The normal end of a prep or a rafting claim (the carried `status <id> prepared`, then the merge of its pull request) is not under Ends of a claim. That is fine while the PR is open, because the claim is parked. Afterwards the branch waits for the pruner. A lingering worktree whose item is later re-claimed (a raft readied with an `active-…` stamp) is told `<id>'s claim was taken over (now active-…): stop working it` (`holds(preparing-x, active-y)` = taken), which is false. (b) A give-back that races the beater's in-flight attempt is undone: `hb.attempt` writes the mark after the push, after `hb.ended` dropped it, which resurrects the mark and possibly the branch. (c) Two `./zn` commands at once both find no live beater and start two. The pid file is written after the start and is not created exclusively, so one beater runs untracked for its hour. (d) Reuse of the beater's own pid within its hour (only reuse of the session's pid is listed) leaves the claim without a beater. (e) AC4's zz-test check greps the single word `beater`.
Recommendation: (a) tell "ended" rather than "taken over" when the remembered stamp's kind is `preparing` and the new one is `active` for the same item, or say it in the lost text. (b) Write the mark only while the memory still names the stamp. (c) Create the pid file exclusively before the start. (d) Check the pid's command line with `reap.isBeater` in `ensureBeater`. (e) Grep the reaper sentence's phrase instead.

Lesson candidates (for the lead to place):
- zz-test: "a session end" in this repository includes `/clear`, which keeps the `claude` process, so a session-scoped helper must also be stopped by the SessionEnd hook and not only by a pid liveness check. Check: does the design say what stops the helper on each SessionEnd reason?
- zz-test: a detach that waits for its reparent compares `getppid()` with the starter's `$$`, not with the starter's own parent. Check: did a probe show the wait loop iterating while the starter lives?
- zz-test: every `./zn run` measures itself into the checkout's spend buffer unless `ZN_MEASURED` is set, so a long-lived helper under `./zn run` inflates the ticket's spend. Check: does a helper the engine starts carry `ZN_MEASURED=1`?
- z-design: a proof that changes a fact to stop a background process first waits until the process has reached the loop that reads the fact. Check: does each stop case wait for the process's first observable action before changing the fact?
