# c0276: Board shows lost work

## Problem
Scope decision (user, 2026-11-08): "yes go ahead and split the whole thing up and tie them togetjer in a raft so we can run through these a layer at a time in a PR" (c0265's design was split into c0265, c0274, c0275, c0276 and c0277, one raft, delivered a layer at a time in depends_on order; this issue carries c0265's board outcome).

Carried from c0265's capture (User, 2026-11-07): the heartbeat is pushed "so every host and the board see it". What should happen:
- **The board shows each claim's verdict** from c0265 (lost, parked, stale), and lost work first within its bucket, longest silent first, as `./zn lost` and `./zn status` order it.
- The board's own rebuilds (after every publish, `land` and main-checkout `sync`) keep the marks.
- The board still builds when the heartbeats or pull requests cannot be read, and reads no remote inside a check or spec flow of the real repository.

## Non-goals
- The verdicts and their order: c0265.
- The board per project and its facts (c0118, R0083): this issue adds to the board without changing its existing signatures.
- The board app's rank order and drag and drop: c0257.

## Solution
<!-- The approach in one paragraph. -->
Prep's detail (the capture's Solution was empty; nothing captured is changed): a pure function `board.withVerdicts(model, verdicts)` puts each claim's verdict on its card and moves lost work to the front of its bucket and band; the engine edge reads the verdicts with the reads `./zn status` already makes (c0265's `judgeAll`) and hands them to `board.build` through one new optional parameter, in `./zn board` and in every rebuild (`buildBoard`, which `refreshBoard` and `sync` call); the page draws a small mark beside the id. Nothing is read in a protected checkout, and whatever cannot be read leaves the page built with what is known.

## Design
Decided with the user (2026-11-07), carried from c0265's design: the board "sees" the heartbeat with the same verdicts as `status`; "three beats" (the stale limit is 900 s); lost work is listed first. This issue is layer 4 of the raft c0265, c0274, c0275, c0276 and c0277 (one PR, delivered a layer at a time in `depends_on` order); it depends on c0265 only and nothing depends on it. It was designed against c0265's prototype (`origin/proto-c0265-raft`, c0265's engine code), on the branch `proto-c0276`.

### 1. The pure part (`z-nile/engine/board.luau`)
```lua
export type Verdict = { id: string, kind: string, silent: number }   -- board.luau requires no heartbeat module; the engine edge copies id, kind and silent into this record (a { heartbeat.Verdict } is not a { board.Verdict } in Luau: the table types differ)
-- Issue and Raft gain  heartbeat: string?  ("lost" | "parked" | "stale" | "nobeat")  and  minutes: number?
function board.withVerdicts(m: Model, verdicts: { Verdict }): Model
function board.build(root: string?, checkout: string?, facts: Facts?, verdicts: { Verdict }?, notes: { string }?): string   -- two new, optional, trailing parameters
-- Model gains  notes: { string }?  (why the marks are missing or weaker: set only when a read was tried and failed; absent otherwise)
```
- **Kinds to marks.** `lost` is `"lost"`, `parked` is `"parked"`, `stale` and `unknown` are `"stale"` (unconfirmed: shown `stale?`, never lost), `nobeat` is `"nobeat"` (a claim made before the heartbeat landed and never beaten: c0265's `[no beat]`); `live` and any other kind, and an id the board does not show, add nothing. A marked card gains `heartbeat` and `minutes` (`math.floor(silent / 60)`, as `lost` prints it); every other card is left exactly as it was, so a model without verdicts is byte-identical (`board.encode`) and `tooling/board.spec` and the promoted board specs are not touched.
- **Order.** Inside each bucket of `views.rafts` and `views.issues` (ready, not, done) and inside each band's `ids` of `columns` (the project board, which is the page's default view), the `lost` cards come first, longest silent first, then every other card in the order it had (a stable order; equal silence keeps the old order). The bands themselves keep their order (a decision of this design, read from the capture's "lost work first within its bucket" as the cards of a bucket or band; a band is marked on its head by its raft's own verdict, see section 2). Parked, stale and `nobeat` cards never move: only lost work is promoted, as in `./zn status`.
- **Pure and non-mutating**: it returns a new model (the cards it marks are copies); the model it is given is never changed, and nothing reads a clock or a remote.
- `board.build` calls `withVerdicts` between `collect` and `render` when `verdicts` is given. **No existing signature changes**: `board.collect` is untouched, `board.build` keeps `(root, checkout, facts)` and gains the trailing optional `verdicts` and `notes`, so every caller of the existing forms (R0083's `facts` form included, landed as #263) builds the same page as before.

### 2. The page (`z-nile/engine/board.html`)
`mark(item)` draws `<span class="mark m-<heartbeat>">…</span>` from the item's own keys: `lost 35m`, `parked`, `stale?`, `no beat`; nothing when the item has no `heartbeat`. It is added after the type on a board card, on the **band head** beside its raft (a rafting claim stamps the raft only, so the band head is where it shows on the Board view), after the stage badge on a list row, and in the heading of the issue and raft panes; `.mark` styles it (lost in the alert colour). It reads only the model's keys, so a model that `znBoard.load` swaps in carries its own marks, and a page without verdicts is drawn as before except for **one space** after the type on each board card (`card()` writes `"</span> " + mark(i) + "<br>"`); c0118's page specs, which assert their own strings, pass with it. The model's `notes` (set by the engine only when a read was tried and failed) are drawn in the page's `#problems` area, one line each, so a page rebuilt by an agent whose stderr nobody reads still says why it has no marks. The mark is styled with an `--alert` colour token that has its own dark-mode value (`#c0392b` is 3.3:1 on the dark background), and a left margin so it never touches the stage badge.

### 3. The engine edge (`z-nile/engine/main.luau`, the one place that reads)
```lua
local boardVerdicts: (fresh: boolean) -> ({ board.Verdict }?, { string })   -- forward-declared before buildBoard, assigned beside judgeAll
buildBoard(root)      -- local verdicts, notes = boardVerdicts(true); board.build(nil, root, nil, verdicts, notes)   (refreshBoard, which publish, `land` and main-checkout `sync` call: they have just fetched or pushed main)
cmd.board             -- local verdicts, notes = boardVerdicts(false); board.build(nil, nil, nil, verdicts, notes)  (fetches main itself)
```
`boardVerdicts()` returns nil (a page without marks, exactly today's) and reads **no remote** when `guarded(true)` says a check protects the checkout (asked first, quietly) or `publishing()` is false (no origin, or `PICKMAN_PUBLISH=0`). Otherwise it makes the reads `./zn status` makes, each bounded like every heartbeat call (`netRetry`, `ZN_NET_SECONDS`): one fetch of `origin main` (skipped when `fresh`: a publish, `land` and `sync` have just fetched or pushed it, and a rebuild that fetched again would double the reads of every fixture spec that publishes, design review 001 F4), `originTree`, then `judgeAll` (one fetch of the beat branches; `gh pr list` only when some claim is stale). What cannot be read:
- the fetch of main: `warning: board: origin/main could not be read; built without lost-work marks`; the registry: `warning: board: origin/main's projects could not be read; built without lost-work marks`; no marks either way;
- the beat branches (`judgeAll`'s `beatsError`): `warning: board: heartbeats unreadable; built without lost-work marks`, no marks;
- the pull requests (`prsError`): `warning: board: pull requests unreadable; stale claims are shown unconfirmed`, and the verdicts judge returned (stale claims stay `stale`, never lost);
- a malformed beat branch: its cure as one `warning: board: …` line, stale claims stay stale (judgeAll's own rule).
**The function is total**: after the guard, every read runs inside a `pcall`, and a throw (a document another checkout moved between two reads) is one `warning: board: the lost-work marks could not be read; built without them` and no marks. Each failure prints exactly one `warning: board:` line (a malformed beat branch, one per branch, with its cure). The page is built in every case and the command exits 0. `refreshBoard` is `buildBoard`'s caller after every publish, `land` and `sync`, so it pays the same bounded reads, which is intended: a board that lost its marks a minute after a rebuild would not be the board the capture asks for. A wrapped `pcall` in `buildBoard` keeps the existing "could not rebuild" warning as the last resort.

### Scalability
A page build pays at most one fetch of main, one fetch of the beat branches and one `gh pr list` (only when a claim is stale), each bounded to `ZN_NET_SECONDS` (10 s), plus `claimsOf`'s `git show` and `git log` per claim (about 25 claims: 18 ms each, c0265 E4). Every publish, `land` and `sync` rebuilds the board, so each pays that: the cost is the one `./zn status` pays, and it is intended. `withVerdicts` is linear in the cards. No new state. Measured on the real repository (review 002 F9): about 0.6 to 0.7 s for the read of the beat branches and about 0.5 s for `gh pr list` while any claim is stale, on every publish, `land` and `sync`; in the spec fixtures about +10% on three publishing specs (E7).
### Maintainability
The mapping from verdict kinds to marks and the order live in one pure function with its own spec; the engine edge is one function that composes c0265's reads and holds no rule; the page reads keys only. `board.luau` takes a structural `Verdict` and requires no heartbeat module, so the board and the heartbeat stay decoupled and c0180's split moves `boardVerdicts` with the heartbeat code.
### Usability
A person sees at a glance which cards are lost (red, `lost 35m`), parked, unconfirmed or never beaten, with the longest silent first in their band, on the page they already open, and a rafting claim on its band head; a claim by z-raft stamps the raft only, so it shows on its band head (and in the Rafts list), while a readied raft's members carry its stamp and show it on their cards. Bands keep their order: lost work is first inside its band and bucket, a lost raft's band is marked, not moved. Until a worktree has merged a main that holds this change, its publishes rebuild the board without marks (section 5; the README and the zz-rules row say so). Without a remote (or in a check) the page is the page it was, and a read that failed says why in one `warning: board:` line and one note at the top of every view instead of silently dropping the marks.

They do not assert that a claim has no beat, how many branches exist, or that a claim made with no beat is lost by flatline. E3 ran them with the envelope.
