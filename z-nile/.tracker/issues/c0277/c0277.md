On one host a taker (c0274) and the old owner can share one worktree, so a returning old session could carry on in the taker's checkout and never learn it lost the claim. What should happen:
- **A takeover discards the old worker's worktree**, so a process that wakes up there knows it has been discarded and can clear its context and pick up something new.
- **A numbered copy continues the work** (`R123-1`, `R123-2` and so on).
- **The work is recovered, not just discarded**: what the old worker left (pushed commits, unpushed commits, uncommitted files) is kept and shown to the taker.

Decided with the user (2026-11-11), idea interview Q1: "Until the raft merges" (the renamed old worktree is kept until the raft's last layer merges or the raft is aborted, then removed with its branch by `./zn done` or z-stop; `./zn reap` lists any left over).

Decided with the user (2026-11-11), idea interview Q2: "Same as rafts" (a design draft follows the raft rules: a prep branch is pushed after every commit, so a taker on any host gets the draft, and a discarded prep worktree is kept until the prep's PR merges or the prep is stopped, then removed; `./zn reap` lists leftovers).

## Non-goals
- Taking over the claim itself and telling an old owner through its beat: c0274.
- The automatic beats that a discarded worktree must stop: c0275.
- Several hosts: c0254.

## Solution
A takeover of a lost claim discards the old worker's worktree and the taker works in a numbered copy, in three moves. `./zn worktree <name> --takeover` (or `--takeover <id>`) refuses unless every claim the old worktree holds is lost or already over; then it renames the old directory (`<name>-discarded-<n>`, so its old path is gone), leaves a marker `.cache/discarded` that makes every `./zn` command there refuse and tell its process to clear and pick up something new, renames its branch, and creates the copy `<name>-<n>` on the original branch name, continuing the old agent's pushed branch. Nothing is deleted: the pushed commits are in the copy, the unpushed commits and the uncommitted files stay in the renamed worktree, and a note lists all three with the commands that take them. A sweep removes a discarded worktree with its branch once the work it was discarded for ends (the raft merged or was stopped, the prep merged or was given back), never one that still holds unrecovered work, which `./zn reap` lists.

### The change
Pure (`z-nile/engine/heartbeat.luau`, no I/O, no clock):
```
heartbeat.DISCARDED = ".cache/discarded"; heartbeat.FRESH = ".cache/fresh"      -- relative to a worktree's top
heartbeat.suffixOf(base, name): number?                  -- 0 for base, n for base-n (digits only, n >= 1), else nil
heartbeat.nextSuffix(base, taken): string                -- the smallest free "base-n"; `taken` mixes directories and renamed branches
heartbeat.currentOf(base, members, discarded): string?   -- the family's highest-numbered member not marked discarded
heartbeat.baseOf(branch?, dirName): string               -- the name the branch had before any discard (a raft layer stands for its raft)
heartbeat.fresh(epoch?, now, limit): boolean             -- a copy its taker has not claimed in yet, younger than the limit
heartbeat.ownsBranch(branch?, id, slug?): boolean        -- `--item` is accepted for the item's own branch only
heartbeat.discardRefusal(facts, why?): string?           -- nil when every claim is lost or already over; else the first reason (c0274's wording)
heartbeat.discardText(DiscardFacts): string              -- the marker: a header the engine reads back, then the body every command and the taker are shown
heartbeat.discardParse(text): Discard?                   -- the one reader of that format
heartbeat.discardedText(text): string                    -- what a command in a discarded worktree is told (a damaged marker still refuses)
heartbeat.discardEnded(live, items): boolean             -- no item it was discarded for is a live claim any more
heartbeat.keepReason(dirty, unreachable): string?        -- why a finished one is kept anyway
heartbeat.gone(sessionAlive?, worktreeThere, memoryThere, discarded?)   -- gains "its worktree was discarded", after "its worktree is gone"
```
Engine edge (`z-nile/engine/main.luau`; **no new top-level local**: every function is in the tables `hb` and `cm`, the chunk is near Luau's 200):
- **`./zn worktree <name> --takeover [--item <id>]` and `./zn worktree --takeover <id>`** (`hb.takeover`; `--takeover` joins `flags`' boolean list; the usage text names both forms). It refuses in a protected checkout and without an origin, and from the worktree it would discard. Steps, in this order:
  1. **Resolve the worktree.** By name, the family's current member (`<name>` and `<name>-<n>`, the highest not marked discarded). By id (an issue's or a raft's), the worktree whose claim memory **equals the stamp `origin/main` shows** (a worktree that remembers another stamp holds nothing of this claim: E2.3), else the copy a **discarded** worktree that remembers the claim left (its marker says where: the second taker of a lost claim finds the first taker's copy and meets its freshness, E2.1), else the worktree the work is done in: `prep-<slug>` (as the dispatcher names it) or the raft's own name. A raft target (`R0010`) is both a name and an id. **No worktree to discard: the taker's is made as `./zn worktree` makes it**, marked fresh (a copy `<name>-<n>` when the family has had a discard), and nothing else happens.
  2. **A copy its taker is still starting in is refused** while younger than `STALE` (900 s): a second taker cannot discard the first taker's copy (`.cache/fresh` holds the epoch; any takeover that creates a worktree writes it; claim memory removes it, in `cm.remember`); after the limit a copy whose taker never claimed can be taken over.
  3. **Every claim must be lost or already over.** The claims are the ones the worktree remembers (`cm.ids`: `tracker-stamp-<id>`, and `tracker-claim-<id>` for a worktree from before c0274), the target item, and `--item <id>`, **accepted only when the worktree's branch is the item's own** (`prep-<slug>`, `raft-<slug>`, the raft's name or one of its layers; else it refuses naming both and moves nothing: the lost verdict is about the item, not about whose worktree this is). None found: it refuses and says to use `--item`. One `hb.judgedFor` (c0274's verdict read, now a function of `hb` that `setStatus` shares) judges them; a claim `origin/main` shows under another stamp or none is already over and passes; a live, parked, never-beaten, unknown or unreadable one refuses with c0274's reason and nothing moves.
  4. **The discard.** Facts first, read-only: the dirty files (`git status --porcelain`), the pushed commits (`origin/main..origin/<branch>`), the unpushed commits (`origin/<branch>..HEAD`, else `origin/main..HEAD`), the pushed tip. Then: write the marker `.cache/discarded` **first** (from here the old process is told whatever fails next); rename the branch `<branch>-discarded-<n>` (a detached head with commits of its own gets the branch `discarded-<R-id>-<n>` to keep them on: a name `R####-` does not prefix, because the board and `busy` read `R####-…` as the raft's own branch) and unset its upstream when it has one (a bare `git push` from the discarded worktree must not move the PR head); **rename the directory** `.worktree/<base>-discarded-<n>` with `git worktree move`; create the numbered copy `.worktree/<base>-<n>` (the smallest free number; `n` is shared by the directory, the branch and the copy) on the **original branch name**, continuing the old agent's **pushed** branch (`origin/<branch>`, else cut from `origin/main`: c0274's rule, and the remote branch is never touched), write `.cache/fresh` in it, delete the old worktree's marks and pid files, print the copy's path on stdout and the note on stderr. The marker is created **exclusively** (a hard link, `hb.claimFile`): a second taker that meets it refuses and undoes nothing of the winner's. A failure after the marker puts back exactly what this process did (the directory, the branch), checking each step, and removes the marker only when both are back; when one cannot be restored it says which and **leaves the marker** (fail closed: the old process stays told). A fact read that fails (`git status`) refuses before anything moves, so a note never says "nothing else was left here" over files it could not read. `locked` (the rename), a refused `worktree add` (the copy) and a failing `status` are the cases specs make. The copy is created by one command (`git worktree add --track -b <branch> <path> origin/<branch>`), so no stray local branch is left behind.
  5. **The note** (stderr, and the body of the marker): `discarded worktree: <renamed path>`, the copy, the pushed commits ("the copy has them"), the unpushed commits ("kept on `<branch>-discarded-<n>`; take them with `git -C <copy> cherry-pick <range>`"), the uncommitted files ("kept in `<path>`; copy what you need, for example `cp`"). Lists are cut at 20 with a count. Nothing is deleted.
- **The old process is told.** `hb.refuseDiscarded(name)` runs in `main`'s dispatch for every command not on `READ_ONLY`, and for `reap` never: a command in a worktree with `.cache/discarded` exits 1 with the marker's body (`this worktree was discarded: <id>'s claim was taken over. Clear your context and pick up something new.` and what is kept), before `guardRepoRoot` and `hb.begin`. A damaged or empty marker refuses too (a marker is present or it is not). The directory rename adds the second signal: a tool that addresses the old path finds it gone, and a shell whose working directory was the folder finds the marker (E5). The old path is **never given to anyone else while a discarded worktree of its family exists**: such a family gets the next number, not its bare name, even when the copy was removed by hand (`discardedNumbers` reads the renamed directories and branches; every other entry under `.worktree/` counts as taken too, `takenNames`). Once the sweep has removed the discarded worktree, its work has ended and no old process of that work is expected; the bare name is then free like any other (review F9: a tombstone was weighed and not taken, one more file to keep and sweep for a case the end of the work already covers). **A process that is routed to the lookup is told** (review F1): when the family has a discarded member, a plain `./zn worktree <name>` prints on stderr `notice: <old path> was discarded (<items> was taken over); <copy> is the taker's. If your work was in <old path>, you were discarded: clear your context and pick up something new.`, which the taker reads too, and the skills (z-design, z-run, zz-execute) say that a session whose worktree is gone or refuses every `./zn` command was discarded and does not look it up again.
- **The lookup is by family** (`cmd.worktree`, `hb.wtList`, `hb.worktreeTarget`, `hb.addWorktree` are the old function split into reusable parts): `./zn worktree <name>` (z-run's `cd "$(./zn worktree R0010)"`, the dispatcher's `worktree(ctx, name)` for `prep-<slug>` and `raft-<id>`) returns the family's current member. **Membership is by branch** (review F4): `<name>` is always a member; a numbered copy `<name>-<n>` only when it is on the family's branch `<name>` (a raft's copy: detached, or on one of its layers). An unrelated `prep-foo-2` on its own branch is no member of `prep-foo` and its number is taken when the family numbers a copy. A takeover by a copy's own name (`prep-hello-1`) takes the base and the branch from that worktree, not from the raw name. A branch checked out anywhere else keeps today's refusal (`already used by worktree at …`, c0005's promoted case, `worktree main`). So every path that asks gets the taker's copy.
- **The sweep** (`hb.sweepDiscarded`, called by `sync` in the main checkout, `worktree-prune`, `done` after its push and `stop` after its publish; it does nothing, and fetches nothing, when no worktree carries a marker). The user's Q1 and Q2: a discarded worktree is kept until the work it was discarded for ends (no item in its marker is a live claim on `origin/main`: the raft is in `done/` or was stopped, the prep merged or was given back), and is then removed with its renamed branch. **Assumption to veto: nothing unrecovered is ever removed.** The test is by **content, never by sha** (review F2: `finish` squashes a layer, a prep is squash-merged and its head branch deleted, a cherry-pick makes a new commit, so a sha test would keep every discarded worktree): a commit counts as recovered when it is reachable from the pushed tip the copy started at (recorded in the marker's `pushed:` line) or from any origin ref, or when merging the branch into `origin/main` with the pushed tip as base changes nothing (`git merge-tree --write-tree`: its change is already there); an uncommitted file counts when its blob equals `origin/main`'s file at that path, or when it is deleted and main lacks the path. A folder, an unreadable status and a conflicting merge count as unrecovered (fail closed). One that still holds anything unrecovered is **kept** and named (`kept discarded worktree <path>: the work of <ids> ended, kept: <why>`), and a plain `./zn reap` lists those ("`./zn reap` lists any left over"; `--quiet`, `--auto` and `--session-end` say nothing of them). `worktree-prune` also removes a done raft's numbered copies (`R0010-1`). The removal runs only after that test found nothing unrecovered, so it is `git worktree remove --force` (git would refuse the untracked files the test found already in main) and `git branch -D` of the renamed branch. An unreadable `origin/main` removes nothing (no claim is known to be over).
- **Ends of a loop**: `goneNow` gains the marker (belt: the rename already makes the folder it started in vanish), `claimBeat` stops (needed, above).
- **Not changed, on purpose**: `dispatcher.luau`'s `raft-<id>` and `ws-<id>` built paths. The first only reads an issue's `raft:` line from a rafting worktree and falls back to `origin/main`; the second names the legacy stream worktrees (c0265's hand-off discarded them too, but layers replaced streams: zz-execute Phase 2B, and no command makes a `ws-` branch). A dispatched step whose own worktree is discarded loses its beats, its path and its claim; **the chain then stops** (review F1): `claimBeat` writes the step's `questions.md` ("the worktree of this step was discarded ... nothing was started in the copy"), the dispatcher stops there as it does on any question (exit 3) and only the user's `./zn dispatch retry <id>` goes on, in the taker's copy through the lookup. `claimBeat` gained a fifth optional argument for it (c0275's four-argument calls are unchanged).

### Readings of the user's words, for veto
1. **"Rename the old worktree" renames its directory** (and its branch), and **"create a copy ... call it R123-1" is the taker's copy**: the old directory is renamed `<name>-discarded-<n>`, the copy is `<name>-<n>`, and nobody is ever given the old path again. Two readings were weighed. The hand-off kept the old directory at its path with a marker and renamed only the branch; it is not taken, because the confirmed Idea says the old worktree is renamed and that a process that wakes up there "finds its paths gone", and the Q1 question it answered says "continues in a copy, R123-1". The other reading (the old worktree becomes `R123-1` and the copy takes the original path `R123`) is not taken either, for the hand-off's reason: a process that addresses the checkout by path (sessions, file tools, hooks and run state do) would then edit the taker's checkout without being told. Here the marker and the missing path are two independent signals, and the old path is never reused.
2. **The copy continues the pushed branch**, so unpushed commits and uncommitted files are not in it; they stay in the renamed worktree and branch, listed with the command that takes them (c0274's 2026-11-07 decision, quoted above). The alternative, the copy carrying the old HEAD, would publish work nobody pushed.
4. **`stop` is also the first step of a lost raft's takeover** (stop, ready, `--takeover`), and it sweeps: a second loss of the same raft removes the clean discarded worktree of the first, because between the stop and the ready the raft reads as prepared. That is not the user's "aborted", but the sweep removes only what holds nothing unrecovered, so no work is lost; the case that pins `stop`'s sweep (sweep :: stop removes ...) pins it.
3. **A discarded worktree that still holds unrecovered work is kept after its work ends** (the sweep, above): the user's Q1 ("removed with its branch by `./zn done` or z-stop") and the principle in his words ("there is a point in trying to recover the work") pull apart exactly here. The sweep removes every clean one; it will not delete uncommitted files or commits that exist nowhere else.

### Assumptions to veto
- **The copy is the taker's, numbered; the old directory is renamed** (Readings, 1).
- **A discarded worktree with unrecovered work outlives its raft or prep** (Readings, 3), and `./zn reap` is where it is listed.
- **The sweep runs in `sync`** (the main checkout), `worktree-prune`, `done` and `stop`. A prep that merges has no `./zn` command of its own, so `sync` (which landing a change runs last, zz-rules Landing, step 4) is where "the prep's PR merges, then removed" happens.
- **`--takeover` makes no claim.** The taker claims in the copy (`status <id> preparing`, whose first beat c0275 gives and whose swap c0274 makes). Between the two the claim is still lost and still the old stamp; nothing beats it (the marker, the missing path, the deleted marks, the stopped loops).
- **A session of another host reaches the same copy through the pushed branch**, as c0274 and c0254 say; this layer works on one host's worktrees.

### Scalability
A takeover costs one fetch (with `--prune`), one verdict read (`judgeAll`: the beats, one `git log -S` per claim, the pull requests only when some claim is stale), a few `git` calls on the worktree (status, two logs, a rename, a move, an add), and no network write. A command in a discarded worktree costs one `isFile`. The sweep costs one `git worktree list` per `sync`, `prune`, `done` and `stop`, and nothing more when no worktree carries a marker; with markers, one fetch of `main` and a few git calls each. The lookup reads the worktree list once, as before.
### Maintainability
`heartbeat.luau` stays the one place the marker's format (`discardText`/`discardParse`), the numbering and the refusal are decided; `main.luau` has one takeover (`hb.takeover`), one sweep (`hb.sweepDiscarded`), one refusal (`hb.refuseDiscarded`), one lookup (`hb.wtList`, `cmd.worktree`) and one creation (`hb.addWorktree`) for the plain command and the takeover; `hb.judgedFor` is now the one verdict read for `setStatus` and the takeover. The next kind of worktree that needs a copy (a project's own, a `ws-` stream) plugs in as a name; the next thing that must end with a discarded worktree joins the sweep's `discardEnded` rule.
### Usability
The refusal names the worktree, the item and the reason (`claim alive: last heartbeat 2m ago, limit 15m`, `it is fresh`, `it remembers no claim; name the item with --item`, `--item c0010 is accepted only for c0010's own branch`), and the old process is told what happened, to clear its context and pick up something new, and what is kept. The taker reads one note: where the old work is, what is in it and the commands that take it. The skills give the two commands (`cd "$(./zn worktree --takeover <id>)"`, then the claim).
