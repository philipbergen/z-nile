# c0278: Close issue wont do

## Problem
There is no ./zn command to close an issue that will not be done, so a moot ticket can only stay in the backlog or be removed by hand-editing tracker state, which the rules forbid: c0266 is moot since PR #258 renamed f0263 and f0265 and cleared the c0114 classified failure, and c0268 is moot since c0264 rewrites the conflicting README lines in place instead of adding a reading rule. Scope decision (user, 2026-11-08): "Capture a chore for closing an issue": add a way to close a ticket as won't-do with a reason, recorded and kept in history (the item's folder, its reviews and spend stay findable, and the board, list and raft-plan no longer offer it), then close c0266 and c0268 with it.

Guess (Claude, 2026-11-15; not a Scope decision until the user rules on F1 under Open to the human), made under the user's standing instruction ("If you have questions make a guess and be clear about it, so that I can ask you before I approve"; 2026-11-15: "design everything that is waiting and have you record all your guesses"): Q1 (in the dispatcher's questions) is option A: c0278 would no longer close c0266, because the user gave c0266 a new scope on 2026-11-12 and its design merged on 2026-11-15 (#394); c0278 would close only c0268. The design below follows this guess; `prepared` and `ready` refuse until the user rules, and the ruling then replaces this line with a `Scope decision (user, <date>)` line in their words.

## Non-goals
- Reopening a closed issue. Nothing in this chore moves an issue out of `closed`. A close made by mistake is undone by a pull request that reverts the close commit (`git revert <sha>`), which `./zn audit` accepts because the document is restored exactly as it was. A `reopen` command is a new ticket.
- Closing a raft. A raft that will not be worked is emptied with `unfold` and retired with `recombine`, or given back with `release` or `stop`, as today. `close` takes an issue id and refuses a raft id.
- Counting closed issues in the board's Stats (opened, closed, net, days in state) or in `./zn metrics`. A closed issue is left out of both, the same way it is left out of the board's columns. Stats count an issue as closed when it reaches `done/`, and that meaning stays.
- Changing how a dependency on an unfinished item is refused by `ready` or `start`. A closed issue is not `done`, so a `depends_on` naming it is still refused there. This chore stops one from being created where tracker state is pushed or merged by `./zn` and the dispatcher: `close` refuses an issue a live item depends on, `./zn land` refuses a capture that adds a closed issue to a `depends_on` (Design section 5), and the dispatcher's prep and rafting gates refuse a PR whose merge `audit` would report `closed-dependency` for (audit's errors are among the readers those gates hold a PR to). What is left is a pull request merged by hand, which only `./zn audit` reports. The refusal in `ready` and `start` is unchanged.
- Engines from before this lands. They read `closed-…` as a status they don't know and derive `new` or `prepared` from the document, so an unsynced worktree's own `./zn list` or board still shows the item. Every skill starts with `./zn sync`, which brings in the new engine.

## Solution
Add `./zn close <issue> --reason "<why>"`. It publishes one tracker-only commit to `origin/main`, as `status` does. The commit stamps the issue's `status:` line `closed-<three words>` and adds one frontmatter line, `wont_do: <why>`. The issue stays where it is, in its backlog folder. Its document, `check.sh`, reviews, `harvest.md`, `spend.md`/`spend.d/`, acceptance specs and experiments are not moved or changed, so `find`, `capture`, `lessons` and spend keep reading them as before.

`closed` is a final status. `list` (unless asked for `list closed`), the bare `status` listing, the board, `raft-plan`, `fold`, `new raft`, `idea`, the dispatcher and watch-net's open-defect test all leave the issue out. No `status` move takes an issue into or out of `closed`. `close` refuses an issue that something still holds: it is readied or done, being prepared, in a raft, or named in a live item's `depends_on`.

`--carry` makes the same edit in this checkout's tree and publishes nothing, so the edit lands with the branch's pull request. That is how this chore's raft closes c0268 in the same merge that brings the engine that reads it.

`./zn audit` reports a close that wasn't made by `close`: a `wont_do:` line without a `closed` status, or the reverse. It also reports a closed issue that is in a raft, outside the backlog, or named in a live item's `depends_on`. The publish guard accepts a document edit only when it is exactly a close, and refuses any later publish of a closed document. `./zn land` refuses a capture that edits a closed issue's document or adds a closed issue to a `depends_on`.

## Design
Product decisions: none. z-nile's tooling has no `game-design.md`, and `z-nile/.tracker/` has no `architecture.md` (the tooling's structure rules are zz-arch's, and its one new module follows them). The decision this chore carries is the user's scope line in the Problem. Its parts map to the design as follows:
- "recorded" is the `wont_do:` line and the close commit;
- "kept in history" means the folder stays where it is and nothing in it is moved or rewritten;
- "findable" is covered by `find`, `capture`, `status <id>`, `list closed`, `lessons` and spend, which read the item as before;
- "no longer offer it" is covered by the board, `list`, `raft-plan` and every other place that hands out work.

**Why a status and not a `closed/` folder.** A folder would have to be taught to about twenty readers that walk the lifecycle folders. Among them are `stateOfPath`, `publish.itemPath`, `validateMoves`, `paths.itemAt`, trackerstate's `LIFECYCLE`, the dispatcher's `LIVES`, `trail`'s `FOLDERS`, the lessons scan, `costrow`, audit's `STATES`, `compact`/`renumber`/`migrate`, `sweepStale` and fixtures' `engine.empty`. Four of those are guards. Each one missed would make a closed item silently disappear from history, renumbering or the sequestration guard (the survey recorded in Unknowns, E2). A status needs the readers that hand out work to skip one value, and needs the guard to accept one edit shape. Every reader that only has to find the item keeps working unchanged. E1 shows the other half: today's engine already ignores a stray folder, so the status design also needs no migration.

### 1. The rules: `z-nile/engine/closing.luau` (new, pure)
Pure over texts and tables (zz-arch rule 4). It requires only `./status`.

```luau
export type Facts = {
	id: string,
	kind: string,            -- "issue" | "raft" (store.isRaftId)
	where: string,           -- "backlog" | "active" | "done" | "none" (not on the tree judged)
	status: string,          -- statusLib.effective of the document there
	raft: string,            -- its raft: line, "" for none
	dependents: { string },  -- ids of backlog or active items whose depends_on names it, sorted
}
closing.KEY = "wont_do"
function closing.isClosed(front: { [string]: string }): boolean       -- status.parse(front.status) == "closed"
function closing.reasonOf(front: { [string]: string }): string?      -- the trimmed wont_do value, nil when missing or empty
function closing.checkReason(reason: string?): string?               -- why it can't be a reason, or nil
function closing.refusal(f: Facts, how: string): string?              -- why `close` refuses, or nil; how = "origin/main" | "this tree"
function closing.edit(text: string, reason: string, stamp: string): string?   -- the closed document, nil without frontmatter
function closing.guard(before: string, after: string): string?        -- publish guard: why `after` is not exactly a close of `before`
function closing.closedDoc(text: string): boolean                    -- the document is closed or carries wont_do (either one)
```

- `checkReason`: it refuses nil, and anything that is empty or only whitespace after trimming (`close needs --reason "<why it won't be done>"`). It also refuses a value holding `\n` or `\r` (`a reason is one line: it is the document's wont_do: line`). The reason is stored trimmed.
- `refusal` checks in this order, first match wins. Each message names the rule and the way out (zz-arch rule 8; lesson z-design/refusals-name-a-way-out-that-works):
  1. a raft: `<id> is a raft: close takes an issue (a raft is emptied with ./zn unfold and retired with ./zn recombine, or given back with ./zn release or ./zn stop)`;
  2. `where == "none"`: `<id> is not on <how>`;
  3. `where == "done"`: `<id> is done: a done issue is not closed`;
  4. `where == "active"`: `<id> is readied (in active/): give its raft back with ./zn stop <raft>, then close it`;
  5. `status == "closed"`: `<id> is already closed`;
  6. `status == "preparing"`: `<id> is being prepared (preparing on <how>): its holder gives it back first (./zn status <id> new)`;
  7. `raft ~= ""`: `<id> is in <raft>: z-raft takes it out first (./zn unfold <raft> <id>), then close it`;
  8. `#dependents > 0`: `<id> is named in the depends_on of <a, b>: drop it there first (by pull request), or close those too`;
  9. anything else is closable. That is `new`, or `prepared` with no raft.
- `edit` sets `status:` to `stamp` and adds `wont_do: <reason>` as the frontmatter's last key, through `store.withFront`'s rule (it is copied, not required: `closing` stays pure and free of `store`'s I/O; lesson zz-arch/one-reader-per-format: the same anchored line rule). Every other byte is kept. A document already holding a `wont_do:` line is not `edit`'s input, because `refusal` rule 5 or the audit catches it first.
- `guard(before, after)` returns nil exactly when all of the following hold:
  - `before` has well-formed frontmatter, its effective `status:` parses to anything but `closed`, and it has no `wont_do:` line;
  - `after` is `before` with its `status:` line replaced by a `closed-<w>-<w>-<w>` stamp and exactly one `wont_do: <r>` line appended as the frontmatter's last line, where `checkReason(r)` is nil.

  Every other pair gets a reason. The guard recomputes `edit(before, r, stamp)` from `after`'s own values and compares the result byte for byte, so the writer and the validator agree.
- `closedDoc(text)`: `isClosed(front) or front.wont_do ~= nil`. The publish guard uses it to refuse touching a closed document again.

### 2. The command: `cmd.close` in `z-nile/engine/main.luau`
`./zn close <issue> --reason "<why>" [--carry]`.
- **Arguments.** One positional id. A missing or second positional prints `usage: ./zn close <issue> --reason "<why>" [--carry]`. `--carry` joins `flags`' boolean list (`main.luau:836-853`); without that, it would swallow the next argument. `checkReason(opts["--reason"][1])` runs first.
- **Where.** `refuseInMainCheckout("close")`, as `status <id> <to>` does: the main checkout is edited only by `./zn` itself. `refuseStale()` follows, as in `setStatus`.
- **Published (default).** `publishing()` must hold; otherwise it fails with `close needs an origin remote (PICKMAN_PUBLISH=0 disables it): ./zn close <id> --reason "<why>" --carry closes it in this tree`. Then it calls `published(publish.commit(".", build, message))`, the same wrapper `setStatus` uses (the board refresh and the broker path come with it). The build makes every check on the base it was handed (lesson zz-arch/checks-inside-the-publish-build):
  - `docPath(paths, id)` and `read` give the document, `stateOfPath` the `where`, `statusLib.effective` the status, and `front.raft` the raft;
  - dependents come from one `git grep -l -w -e <id> --and -e '^depends_on:' <base> -- <root>/issues/ <root>/rafts/ …` over the fetched base (E4: git's ERE has no `\b` here, so the `-w --and` form is the design). `publish.Build` gains a fifth argument, `base: string`, the sha `publish.commit` resolved (`publish.luau:354`), so the grep and the reads see one tree. Each hit is kept only when it is an item document (`publish.itemPath`, rel `<ID>.md`), is not `done/` (`stateOfPath`), is not closed (`closing.isClosed`), and its `depends_on`, read with `store.idList`, holds the id;
  - `closing.refusal(facts, "origin/main")` returns the refusal string;
  - otherwise the build returns `{ { path = <doc>, content = closing.edit(text, reason, stamp("closed")) } }`.

  The message is `tracker: close <id> won't do`, a blank line, then `Reason: <why>`. On success it prints `closed <id> on origin/main (<sha>): <why>`. The working tree is not touched, as with `status <id> preparing`. A worktree sees the change on its next `./zn sync`.
- **Carried (`--carry`).** No origin is needed and nothing is published. The facts come from this tree:
  - `store.find(id)` gives the `where`, through `item.state`, with nil meaning `none`;
  - the local document gives the status and raft;
  - dependents come from `store.all("issue")` and `store.all("raft")` filtered the same way (backlog or active, not closed, `depends_on` holds the id).

  In both modes a dependent's own `raft:` and status (other than `closed`) do not matter: an active dependent in a raft holds the issue as a backlog one does.

  `closing.refusal(facts, "this tree")` runs. Otherwise it writes `closing.edit` into the item's document and prints `closed <id> in this tree (carried): commit it; it lands with this branch's pull request`. It does not stage or commit. The writer is the same function as the published path's, so the two modes produce the same bytes. A spec compares them.
- The stamp is `stamp("closed")` (`main.luau:384`), the plain draw `setStatus` uses (`main.luau:1524`), in both modes. It is not `freshStamp` (`main.luau:638`, redrawn until no item on `origin/main` carries it): that freshness matters only for an `active-…` claim, which `stop` matches by stamp, and nothing matches a `closed-…` stamp.

### 3. The status vocabulary: `z-nile/engine/status.luau`
`NAMES` gains `closed`, so `status.parse("closed-quiet-copper-falcon")` is `closed` and `status.effective` returns it. `ALLOWED` gains nothing, so `canMove(closed, x)` and `canMove(x, closed)` are false for every x. The comment above `ALLOWED` says that `closed` is set only by `./zn close` and nothing leaves it.

### 4. Readers that offer work, and how each leaves a closed issue out
- **`cmd.status`** (`main.luau:1703`):
  - the bare listing skips an item whose effective status is `closed`, in the same loop that already skips `done`;
  - `status <id>` prints `closed`;
  - `status <id> closed` fails with `only ./zn close closes an issue: ./zn close <id> --reason "<why>"`. That check comes after `statusLib.parse(to)`, which now accepts it, and before the `active` refusal.
- **`setStatus`**: in its target loop, right after the `active/` refusal, a target whose effective status is `closed` fails with `<t> is closed (won't do): nothing moves a closed issue`. This holds for `status <id> preparing|new|prepared` and for a raft's members (lesson zz-arch/new-refusals-keep-the-old-order: it is the second refusal, after `active/`, so every existing refusal text still comes first where it did).
- **`cmd.list`** (`main.luau:2933`): the shown state of an issue whose document `closing.isClosed` is `closed`, replacing the path's `backlog`.
  - With no state argument, or with `backlog`, closed rows are skipped.
  - `list closed` prints only them, as the same `%-6s %-8s %-8s %-7s %s` row followed by `  (won't do: <reason>)`.
  - `active`, `done` and `retired` are as today.
  - The shared-number warning still counts closed ids, which keeps their numbers used.
- **The board** (`board.luau`): issues whose front `closing.isClosed` are dropped right after `scan(root, "issues")`, before cards, bands, dependencies, Stats and charts are built. `boardview.column` is never called with `closed` and is unchanged (`c0118/view` keeps pinning its five statuses).
- **`raft-plan`, `fold`, `new raft`**: unchanged. `raftplan.isCandidate` wants `prepared` (`raftplan.luau:80`), `refuseUnraftable` wants `prepared` (`main.luau:1781`), and `new raft` wants `new` or `prepared` (`main.luau:1321`), so `closed` already fails each one. Specs pin all three.
- **`idea`** (`main.luau:6785`): a closed issue is refused with `idea: <id> is closed (won't do): nothing to write`, after the "not an issue" refusal.
- **The dispatcher** (`dispatch.luau`, `dispatch.next`): for an issue whose `f.status == "closed"`, it returns `stop(dispatch.EXIT.done, "<id> is closed (won't do): nothing to run")`. This sits right after the `where == "done"` stop, so a closed issue is a finished chain rather than a failure.
- **watch-net** (`watchcmd.luau:663`, `openDefect`): a `git grep` hit whose document `closing.isClosed` is not open. A closed `slow-tier-red` defect no longer stops watch-net from filing a new one. The per-path test becomes the exported pure `watchcmd.isOpenDefect(path: string, text: string): boolean` (not under `/done/` or `/retired/`, and not closed), which `openDefect` calls with each hit's file read from `dir`.
- **Already safe, pinned by specs, unchanged:**
  - z-work's picker (`workread.slot` reads rafts, and a closed issue is in none);
  - `ready` (a raftless issue is refused);
  - `release` (it restores only its own stamp);
  - `metrics` (done and `--include-active` only);
  - `claims` (a closed stamp is one more phrase taken).

### 5. The publish guard: `z-nile/engine/publish.luau`
- Existing-document edits (`publish.luau:477-483`):
  - when `withoutStatus` differs, the edit is accepted only if `closing.guard(existing, c.content)` is nil, and the message becomes `<path>: a published change to an existing document may only edit its status: line (or be one close: ./zn close)`;
  - before either test, an existing document that `closing.closedDoc` is refused with `<path>: <id> is closed on origin/main: a closed issue's document is never published again`. That also refuses a status-only edit of a closed issue by any engine that has this guard.
- `validateMoves` (`publish.luau:306-312`): a moved document whose source `closing.closedDoc` is refused with the same "never published again" reason. Close never moves anything, and ready, stop and done never take a closed issue, so this only fails closed.
- `publish.Build` gains `base: string` as its fifth argument, passed by `publish.commit`. Existing builds ignore it.
- **`./zn land`'s capture scope** (`captureScope`, `main.luau:2313`), the other path that pushes tracker documents to `main` (it does not go through the existing-document test above). Two refusals are added at the end of the per-document loop body, after the existing status-line check, so every existing refusal still comes first (lesson zz-arch/new-refusals-keep-the-old-order):
  1. the edited document's `base` version is `closing.closedDoc`: `not a capture change: <path> is closed (won't do): its document is never published again`;
  2. an id in the HEAD version's `depends_on` (read with `store.idList`) that the `base` version's does not hold, whose backlog document at `base` (`git ls-tree <base> -- <root>/issues/<id>/<id>.md` over `base`'s registry roots, then `git show`) is `closing.closedDoc`: `not a capture change: <path> adds <id> to depends_on, and <id> is closed (won't do): drop it from depends_on`. An id is added when it is in the HEAD version's id list and not in the `base` version's (a set difference: a reordered list adds nothing; a `base` line `store.idList` can't read gives no ids, so every HEAD id is judged). Only ids the capture adds are judged: a dependency already on `base` (from a PR merged by hand) is not the capture's to fix, and `audit` reports it.

  A capture that both edits a closed document and adds a closed id gets refusal 1 only, since it comes first. A capture of a closed issue's `spend.md` alone is already refused (a capture's spend record needs its issue document in the same land), and with the document it meets refusal 1.

  The cost is one `ls-tree` per root and one `git show` per added id, and only when `depends_on` changed. One definition of closed holds here too (`closing.closedDoc`; lesson zz-arch/one-definition-of-tracker-state).

### 6. The audit: `z-nile/engine/audit.luau`
`audit.run` gains four error codes. They are not in `ITEM_CODES`, so `list` still prints. Each names the one way to clear it (lesson zz-rules/audit-what-new-refuses):
- `closed-mismatch`, a `wont_do:` line without a `closed` status, or a `closed` status without a non-empty `wont_do:`: `<id>: wont_do: and a closed status go together, and only ./zn close writes them: restore both lines from origin/main, or close it with ./zn close <id> --reason "<why>"`;
- `closed-not-backlog`, a closed issue under `active/` or `done/`, or a raft whose document is closed or carries `wont_do:`: `<id> is closed outside the backlog: only a backlog issue is closed; restore its document by pull request`;
- `closed-in-raft`, a closed issue whose `raft:` is set, or a raft whose `issues:` names a closed issue: `<id> is closed but <raft> holds it: empty its raft: line and drop it from <raft>'s issues: by pull request`;
- `closed-dependency`, a backlog or active item whose `depends_on` names a closed issue: `<dep> depends on <id>, which is closed (won't do): drop <id> from <dep>'s depends_on by pull request`.

`closed-mismatch` is an issue's code only: a raft that is closed or carries `wont_do:` gets `closed-not-backlog` alone. In `closed-in-raft` the `<id>` is always the closed issue's, whichever side names the raft. Audit walks the backlog and `active/` items for `closed-dependency` and every state folder for `closed-not-backlog`.

It reads through audit's own `front` (it reads malformed trees) and the predicates of `closing` over the table it gives (`closing.isClosed`, `closing.reasonOf`), so there is one rule for what counts as closed.

### Scalability
- A published close costs:
  - one `publish.commit`: a fetch, one `ls-tree` of the roots, one `git show` of the document;
  - one `git grep` over the base for dependents, plus one `git show` per hit (a handful at most);
  - one stamp-freshness grep, and one push.

  It does not grow with the item count, apart from the one grep. E3 measured 28 ms per `git show` on this machine: reading every one of the 199 backlog documents would cost about 5.5 s, which is why a single grep is used.
- `--carry` reads the local tree through `store.all`: about 300 frontmatter reads from disk, well under a second.
- The added checks in `list`, the board and audit are one table lookup per item they already read. watch-net reads one more file per grep hit, and a hit is rare.

### Maintainability
- What counts as closed is one function, `closing.isClosed`, and the reason has one reader, `closing.reasonOf`. Every reader goes through them: `list`, the board, watch-net, audit, the publish guard and the command.
- The guard and the writer share `closing.edit`. A new reader that hands out work joins by calling `closing.isClosed`.
- A future `reopen` would be one more allowed edit shape in `closing.guard` and one `ALLOWED`-like rule.
- No lifecycle folder changes, so compaction, renumbering, trail, lessons, trackerstate and the sequestration guard need no change.

### Usability
- The command line is `./zn close <issue> --reason "<why>" [--carry]`. Every refusal names the rule and the next command (section 1).
- Exhaustive lists it joins:
