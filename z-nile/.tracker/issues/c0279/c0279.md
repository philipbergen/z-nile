# c0279: Dispatch stop spec waits on wall clock

## Problem
The promoted spec z-nile/tests/acceptance/c0117/dispatch-cli.spec.luau case 'dispatch stop kills the running step's group, and retry reruns the same step' fails on main whenever the machine is loaded (line 692, expected true, got false: absentAfter(<fakes>/grandchild-stop, 3) gives the killed step's grandchild 3 wall-clock seconds to disappear), so the full gate goes red and every ./zn land refuses: it failed two of three split-capture lands on 2026-11-08 and c0263's gate, with control-cli taking 905 s against 329 s unloaded, while it passes on an idle machine. Make the case prove the kill without a wall-clock wait (or a bound that holds under load), as the user's standing rule that promoted specs wait for nothing requires; nothing else in c0117's dispatcher changes. Scope decision (user, 2026-11-08): "Capture it now". Scope decision (user, 2026-11-08): "Yes, every load-sensitive case in that file": c0279 covers every case of z-nile/tests/acceptance/c0117/dispatch-cli.spec.luau that the load runs show failing under load (at least "dispatch stop kills the running step's group, and retry reruns the same step" and "an agent's git and gh refuse a code push to main and a merge, before the real gh runs"), so one raft clears the gate.

## Non-goals
- No change to the dispatcher (`z-nile/engine/dispatcher.luau`, the supervisor, `stall_seconds`): the cases are wrong, not the code they test. The prototype shows no case needs one.
- No new wall-clock wait, and no longer one: a bound that only a missing kill can reach is the only kind this issue adds.
- `control-cli.spec.luau`'s `absentAfter(grandchild-orphan, 5)` and the `kills the step's whole process group past max_tokens` case's `absentAfter(grandchild-cap, 3)` have the same shape. No load run failed either (18 runs of dispatch-cli, 0 failures of the cap case), so they are outside the widened scope; they are named in Unknowns & experiments E5 for a later chore.

## Solution
(captured ideas: make the case prove the kill without a wall-clock wait, or with a bound that holds under load.) Three causes were found by running the file alone and under load, and each is fixed in the fake CLI (`z-nile/tests/lib/fakecli.luau`) and the one case that waited:
1. The stop case waited 3 s for a file its grandchild would touch after 2 s. It now has the grandchild record its pid and sleep 120 s, and the case polls for that pid's death (`kill -0`), with a 60 s bound that only a kill that never comes can reach.
2. The `stop` and `push` fakes were silent for longer than the dispatcher's 2 s stall limit while they ran `./zn dispatch stop`, `git commit`, `git push` and `gh` (the log shows `stalled`, not `stopped`): both now beat every 0.5 s like the `claim` and `ticket` fakes.
3. Every fake printed its first line only after a pipeline of `sed`/`head`/`printf` processes: a loaded machine took over 2 s to reach it, and any case stalled at 0 tokens (seen on the quota fallthrough case). The first line is now the script's first command.
`FAKE_DELAY` (seconds, default 0) delays the stop and the push inside the heartbeat; only a `check.sh` sets it, to simulate a slow machine without the promoted spec waiting for anything.

- **Moves**: none. **Guards**: no guard, publisher or gate code changes; the fake `stop` mode still runs `./zn dispatch stop` through the same wrapper.

**Changes** (all in `z-nile/tests/`):
- `lib/fakecli.luau`, `script()`: (a) `echo '{"type":"system"}'` becomes the first command after the shebang; (b) `stop)`: heartbeat loop in the background, then `sh -c 'echo $$ > "$FAKE_DIR/grandchild-stop.pid"; exec sleep 120' &`, a bounded wait (at most 60 s) for the pid file, `sleep "${FAKE_DELAY:-0}"`, `./zn dispatch stop "$FAKE_STOP"`, `sleep 20` as before; (c) `push)`: heartbeat loop started first (`hb=$!`), `sleep ${FAKE_DELAY:-0}`, the existing commands, `kill $hb` before the `ok` line.
- `acceptance/c0117/dispatch-cli.spec.luau`: new helper `deadWithin(pid: string, seconds: number): boolean` (polls `kill -0 <pid>` every 0.1 s, true the moment the process is gone, false only after `seconds`); the stop case replaces `absentAfter(grandchild-stop, 3)` with `deadWithin(<pid read from grandchild-stop.pid>, 60)`. Everything else in the case, and `absentAfter` for the cap case, stay.

Why the poll is not a wall-clock wait: it returns as soon as the process is gone (about 0 s when the dispatcher killed the group before `stop` returned, which is what happens), and the 60 s bound is reached only by a kill that never happens; under any load the case can only get slower, never fail, unless the kill is broken. The grandchild's `sleep 120` cannot end by itself inside that bound, so a kill that never happens can no longer look like one that did (the old `touch`-after-2 s grandchild made a late kill look like no kill).

### Scalability
No cost: the case ends when the process does (about as fast as before); the fakes start one `echo` earlier. 25 cases, no new process per case beyond the two the stop and push fakes already started.
### Maintainability
One shared pattern, "a fake that does slow work beats while it works", now holds for every fake (the first line for startup, the loop for the slow part); the comment in `fakecli.luau` names the reason (stall limit 2 s), so the next fake follows it. `FAKE_DELAY` is the one knob for proving it.
### Usability
A kill that fails now fails with `expected true, got false` at the `deadWithin` line after at most 60 s; the stall case now fails as `stalled`, which names the cause, only when it really stalls.

- **E2 (the fix holds under the same load)**: fixed code, 5 runs under the same load: 5 of 5 green (25 passed each); before: 4 of 8 green. (A first, partial fix without the first-line change failed the fallthrough case once in 1 run; that run is not counted.) The load was lighter in some runs, so the counts are weak evidence, which is why E3 exists.
- **E3 (a deterministic slow machine)**: `FAKE_DELAY=3` on the fixed code: 25 of 25 green (the stop and the push each delayed 3 s inside the heartbeat, over the 2 s stall limit and over the old 3 s wait). The same slowness on the unfixed fakes (a 3 s sleep first thing, before the stop, before the push, patched into the old fake): 6 passed, 19 failed (`stalled` in every case with a startup over 2 s), the stop and push cases among them. The first line first is what makes startup slowness harmless to the fixed fakes; the dispatcher still counts the process spawn before it.
