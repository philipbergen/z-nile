## Solution
Prep's detail, below the captured outcomes (this issue's Problem is its whole capture; it has no Solution bullets of its own). The lifecycle commands write the rows c0263's record holds, each in the commit that makes the change it records, so a row lands when its change does:
- `status <id> new` appends `unblocked | <live actor> | ` to each issue it gives back, in the published commit, built from `origin/main`'s file (a raft's give-back: each issue it changes, never the raft; `release` none).
- `new raft`, `fold`, `recombine` and an emergent `new issue --raft` append `rafted | <live actor> | raft=<R-id>` to each ticket (one row per ticket, with `; via=dispatch:<step>` when a dispatcher script step ran the command), staged with the `raft:` line, so the rafting PR carries both and the row lands at its merge.
- `done` appends `delivered | <live actor> | raft=<R-id>` to each member, staged with the moves, so the raft PR carries them and a rollback removes them.
- The dispatcher gives each attempt of a model step its own `ZN_ACTOR`, and a script step the user who started the pipeline with `ZN_VIA=dispatch:<step>`; its rafting gate lets a rafting PR change a ticket's `provenance.md` only by appending `rafted` rows.

## Design

### Behaviour (every outcome this issue owns, each with a Checked criterion)
Built on c0263's `provenance.luau` (`record`, `resolve`, `hint`, `agent`, `human`, `publishProblem`, `appendOnly`) and `liveActor` (now `./zn provenance record` is c0263's command); this issue adds the callers, four small adapter helpers and the pure functions below. Prototyped first (branch `proto-c0282` on `proto-c0263-raft`, never landed; `experiments/proto.patch` is its engine and docs diff against `proto-c0263-raft`).

1. **Who a lifecycle row names (AC1, AC2, AC3).** `lifecycle.who(opts): (actor, via?)` in `main.luau` (one of four helpers in a table, `lifecycle`: `who`, `now`, `append`, `check`; main.luau is at Luau's limit of 200 locals, E9, so three more `local function`s do not compile) is called first in `status <id> new`, `new raft`, `fold`, `recombine`, `done` and an emergent `new issue --raft` (a plain `new issue`, `status <id> preparing` and the rest read no actor). It takes c0263's `liveActor(opts)` (`--actor`, else `ZN_ACTOR`, else the agent-session hint, else the git name), then `provenance.via(process.env.ZN_VIA)`. It refuses the command, naming the cause, **before anything is published or written**, when `--actor` or `ZN_ACTOR` is not a live form, when git has no identity and nothing else names the actor (`unknown` is not a recordable actor), or when `ZN_VIA` is set and is not `dispatch:<step>` (lower-case letters, digits and hyphens). Without this the claim of `new raft` or `fold` would be published and the row then refused: the same partial state c0263's `./zn provenance record` avoids by building its row inside the publish builder. `--actor` is accepted by every command that writes a row, and `raft-plan --apply` hands its own `--actor` to each command it runs. `lifecycle.check(dir)` parses a member's `provenance.md` and refuses naming the file, so a record that does not parse (a hand edit) refuses `new raft`, `fold`, `recombine` and `done` before the claim is published or a folder moved, with the tree and origin as they were; `done` also rolls back if an append fails after that.
2. **Unblocked by (AC1).** In `setStatus(id, to, opts)`, when `to == "new"`, the builder adds to the published commit, for each moved target that is an issue, `provenance.record(read(<its provenance.md>), t, "unblocked", actor, "", now)`: the row is built from `origin/main`'s file (the builder's `read`), so a worktree's own `rafted` row never reaches `main`, and it is part of `changes`, so any refusal the builder returns first (a taken-over claim, a readied member) publishes no row. One published commit holds the document(s) and the record(s) and nothing else; c0263's validator accepts `unblocked` rows in the backlog. A raft's `status <R> new` records its issues and not the raft (a block on a raft is c0250's, through `./zn provenance record`). `release`, which gives a rafting claim back through its own commit, records nothing (Q5). Every give-back appends: rows accumulate ("each time").
3. **Rafted by (AC2).** `lifecycle.append(dir, id, event, actor, detail)` (`main.luau`, the one adapter: reads or creates `<dir>/provenance.md` through `provenance.record`, writes it and stages it) is called at each place the engine writes `raft:` to a non-empty value, **after** `mergeOrigin()` and next to the `git add` of the document: `new raft`'s published path (per member) and its offline path, `fold`, `recombine` (per moved member) and the emergent issue's offline write (the new issue's own folder in `active/`). `provenance.raftDetail(raft, via)` gives the detail: `raft=<R-id>`, then `; via=dispatch:<step>` only when `ZN_VIA` is set. The rows are committed with the `raft:` line by the same commit the command already makes (`tracker: <R> members`, `tracker: fold …`, `tracker: recombine …`), so the rafting PR holds both and a published append of another row meets them in c0263's union, not in git. `unfold` and `release` remove nothing and write nothing: an unfold leaves the `rafted` row as history, and the newest row naming the ticket's current raft is the one c0280 shows. The raft's own folder gets no row.
4. **Delivered by (AC3).** Under the stack (main's `done` merges the top layer with `--no-ff --no-commit` onto main's tip, promotes the specs, moves the items, runs the gate and commits one binding commit) the rows are written in that same uncommitted merge: in `cmd.done`, after the members are moved to `done/` and before the raft's own move and the gate, `lifecycle.append(item.dir, item.id, "delivered", actor, provenance.raftDetail(raft.id, nil))` runs for every member, staged with the moves. `done`'s rollback (`git reset --hard`) removes the rows, including a created file, so a retry appends once (a rolled-back run leaves the stack as it was); the raft's folder gets none; the rows land in the binding commit, which is the raft PR's merge. `finish` (a layer's commit) and `restack` write no row. The worker is not stored (Q4). The row is made when `done` runs, before the merge: the squash commit's author and `Co-Authored-By` agree where the agent that ran `done` merges its own PR (zz-rules, Merging), and where the user merges it the row still names the delivering agent, not the merger: a limit, stated (c0280 prints the merger from the `done/` commit).
5. **The dispatcher (AC4).** In `dispatcher.luau`'s attempt loop `env.ZN_ACTOR = provenance.agent(spec.model, spec.effort)` is set per attempt, after the runtime's own variables, so a fallthrough's second attempt has its own model, the dotted id is one spelling (`grok-4.7` → `grok-4-7`) and the effort is the spec's. It wins over the session hint (`ZN_DISPATCH` makes every dispatched step an agent session). `dispatcher.scriptStep` runs `./zn <command>` with `ZN_VIA=dispatch:<step>` and, when git names the user (`git var GIT_AUTHOR_IDENT` in the step's directory), `ZN_ACTOR=human:<name>`: the pipeline is the user's, started from a terminal or from an agent session, and its rows say so (Decided with the user, 2026-11-12: "The user, via dispatch"); with no identity `ZN_ACTOR` is left unset and the engine resolves as it always does.
6. **The rafting gate (AC5).** In `dispatcher.judgePr`'s rafting branch, `shapeOf` accepts `<root>/issues/<id>/provenance.md` of a **backlog** issue only when all of these hold, each with its own reason: the same PR moves that issue's own `raft:` line from empty or another raft to a raft R (so a record with no raft change, an unfold and a row on an issue the PR does not raft are refused); and `provenance.raftedProblem(old, new, id, R)` holds on the file as the base and the head hold them (read untrimmed: the dispatcher's `git` helper trims, and a record without its final newline does not parse): every old row byte for byte in place (the prep PR's `approved` row, `unblocked` rows main published), at least one new row, every new row `rafted`, with a live actor (not `unknown`, not a git-derived form) and the detail `raft=R` or `raft=R; via=dispatch:<step>`. A record of an issue in `active/`, `done/` or `retired/`, of a raft (any state: a rafting PR writes `rafted` rows on issues and a raft's record is main's), a removal, any other event, an edited old row and every other file keep the existing refusals (`it changes <path>: a rafting PR changes only a backlog issue's raft: line`). The existing rule that refuses a PR for an item main changed since the base keeps a stale PR out (a row main published after the PR was cut) and now says `run ./zn sync in its worktree (it merges main and unites a provenance.md both sides appended), then push`, because only `./zn sync` unites a record. A rafting PR changes neither `approval.md` nor `spend.d/` (published by `ready`, and by the dispatcher on its own branch), so the gate's other refusals need no allowance for them; `done`'s tree holds both and the rows sit beside them.
7. **Docs (AC6).** zz-rules (Provenance) gains the **Lifecycle rows** paragraph, and the README line names the three events.

### Pure and adapter split, server authority
Pure and unit-tested: `provenance.via`, `provenance.raftDetail`, with c0263's `record`/`resolve`. Adapters (thin): `main.luau` reads the environment (`ZN_VIA`, via `lifecycleWho`), the files and git, and hands texts to the pure functions; `dispatcher.luau` sets an environment and reads the PR's blobs. No game code and no client: the tracker's own authority is `origin/main` (the published rows are built from its file, and the gate reads its base, never the working tree). Each wiring is checked through its caller (AC1 to AC5), not only the pure function.

### Scalability
One small append per ticket per event, on the item's own folder; the rafting gate reads two blobs per carried record; no scan grows with the number of items.
### Maintainability
Three private helpers and two pure functions; the five commands call them, and the row grammar is c0263's. Adding a sixth lifecycle event is one `appendRow` call and one entry in c0263's closed event list.
### Usability
A bad actor, a bad `ZN_VIA` and a missing git identity refuse the command up front and say which; `--actor` works on every command that writes a row; a rollback leaves nothing to clean up.

### Edge cases
- `status <id> new` that moves nothing records nothing. A raft move that skips a prepared member (never restamped) records nothing for it.
- Two `fold`s of one ticket (an `unfold` between them) leave two `rafted` rows; the newest naming the current raft counts (c0280).
- A ticket with no `provenance.md` gets the file created (`done` too: an old member with no record gets one `delivered` row).
- A `|` or a newline in `ZN_VIA` is refused (the shape check), so a row cell is never split.
- `PICKMAN_PUBLISH=0` (offline): `new raft`, an emergent issue and `done` write their rows locally; `status` and `fold` need an origin as before.
- The emergent issue is made in the raft's worktree in `active/`: its `rafted` row names the raft it was made in; `done` then adds its `delivered` row like any member.

## Existing work
Nothing migrates and nothing fails on the day this lands: no rule is added that an old item can break. Items rafted, readied or done before it have no `rafted` or `delivered` row; c0280 derives theirs from git (its table: the commit at which `raft:` became the current value; the commit that added the document under `done/`), and an active raft readied before this lands runs the engine of its own branch, so its `done` writes no `delivered` rows (derived the same way). A row written by this layer to an item whose engine merges `main` from before it is simply an appended row (c0263's union). The frozen list of c0283 is data this issue's specs do not seed.
