## Non-goals
- The record itself (`provenance.md`, its grammar, `./zn record`, the append-only publish rule, `audit`'s record check, the union of two writers in the engine's merges and `remap`): c0263. This issue only appends `approved` rows through `provenance.record` and reads rows through `provenance.parse`.
- `./zn who` and the derivation from git (c0280), the `unblocked`, `rafted` and `delivered` rows and `ZN_ACTOR`/`ZN_VIA` per dispatcher attempt (c0282), the board's provenance section (c0284).
- Approving anything but an issue's design: not a raft's own document, not the idea (c0260's interview and confirmation are the human step over the idea, and `humans interact (plan mode) over the idea` stays theirs), not a merge.
- Access control, and a defence against an agent that deliberately starts a process without the session variables or edits files by hand: recording who approved is not permission to approve (the guard catches the honest mistake and the casual workaround, as every guard in zz-rules does; see Behaviour 1).
- A dispatcher that stops its design step at a draft before a PR exists (c0267), the worker end (c0253) and the dispatcher's autonomous merge of layers (c0252): their own issues; this one only makes the prep gate never merge (Behaviour 5) and names them below.
- Migrating old issues by writing `approved` rows into them: the frozen list covers every issue prepared now (Behaviour 4); no old document is edited.
- Making `compact`, `remap` or `renumber` keep approvals through an id rewrite: such a rewrite changes the document (and so the hash) of a prepared issue, which then needs `./zn approve` again, exactly like a redesign (Edge cases). c0116's `keepRecords` re-records `grouped:` entries only; an approval is not re-recorded.

## Solution
Design approval is an explicit human step before `prepared`. This layer adds three things on top of c0263's record, and no other state:
- **`./zn approve <id>`**, refused in any agent session, appends `approved | human:<git name> | design=<hash>` to the issue's `provenance.md` and commits the issue's folder as `tracker: approve <id>`, so the human is the git author of that commit.
- **The refusal**: `./zn status <id> prepared` (the carried move) takes an issue only when its newest `approved` row has the hash of the folder now; `fold`, `new raft` and `ready` refuse, `raft-plan` skips and `audit` reports a prepared backlog issue that has no current approval, unless `z-nile/provenance-exempt.txt` on `origin/main` lists the issue at its current design (the frozen list of the issues prepared when this lands, written once by `./zn provenance freeze`).
- **The dispatcher's prep gate never merges**: it stops, whatever `auto_merge` says, and waits for the user to approve and merge.

### Behaviour 1: `./zn approve <id>`
- **Where it runs**: a prep worktree, for an issue that is `preparing` on `origin/main` with `design: ready` in this worktree. It computes the design hash `raftplan.recordHash(id, gitFolderFiles(dir))` (the document without `status:` and `raft:`, `check.sh`, `acceptance/`, the design reviews, refutes and `harvest.md`; the same hash z-raft's `grouped:` record uses, so `provenance.md`, `spend.md`, `prompt.md` and `experiments/` are not in it), appends `approved | human:<git name> | design=<hash>[; said="<words>"]` (`provenance.record`, the time in UTC) and commits the issue's folder as `tracker: approve <id>`: `git add -A -- <folder>` then `git commit`, so the human is the git author of that commit and the commit holds the issue's folder and nothing else.
- **It is refused in any agent session.** `provenance.hint(sessionEnv()).agent` is true (`sessionEnv()` is the one place `main.luau` reads the six variables, `liveActor` uses it too). The refusal comes first of all and says `approve is refused in an agent session or a dispatched step: run ./zn approve <id> yourself, in your own terminal, in this worktree (<path>)`. No flag (`--said` included), variable (a `ZN_ACTOR` that claims a human included) or configuration lets an agent through, and the engine reads no "allow" input. The human is always the git identity (`git var GIT_AUTHOR_IDENT`'s name), never `ZN_ACTOR` or a flag.
- **The user's words** (the capture: "records the human, the design hash and the user's words"). The human may type `--said "<their words>"`; they are recorded as `said="<words>"` after the hash (a `|` is written `/`, a `"` `'`, a line break a space, by `provenance.record` and `approve`). The words are optional, an empty `--said` is refused, and **any other option is refused** (`approve: unknown option <opt>`), so nothing a human types is silently dropped. The agent-session refusal still comes first, so words never let an agent through (c0263's "the `--said` evidence path is gone" is about an agent reporting the user's words; here the human is the one typing, in their own terminal). Whether the words should be required is the user's call (open question Q1 in the hand-off report).
- **The argument that the human really ran it.** The user's words are "refuse in any agent session": "a human ran it must be true, not just reported". The guard detects an agent session by what the session carries, as every guard in zz-rules does ("Keep same user, accept detection"): it catches the honest mistake and the casual workaround and it is not a security boundary against an agent that deliberately starts a process without those variables (`env -u CLAUDECODE ./zn approve`) or edits files by hand. What the design adds so that "a human ran it" is true in the engine's terms: (a) the only way to the row through `./zn` is a process with no agent marker; (b) no engine path sets, clears or ignores the markers (the spec harness clears them in the processes it starts, `fixture.exec`, and the engine never reads it); (c) `status prepared` accepts only a **committed** row (the working-tree file must equal HEAD's, so a row appended by hand fails as `has changes that are not committed`) whose `design=` equals the hash now, and its refusal names what the approval covered, never the hash a row would need, so an agent refused there cannot copy the right value from the message; (d) the dispatcher's prep gate never merges (Behaviour 5), so a human reads the PR before it lands. The limit, stated: prep PRs are squash-merged, so the `tracker: approve` commit does not reach `main`; what survives is the row (and `who`, c0280, prints it with its time); the doors judge rows, not commits, and an agent that makes a commit by hand is the guard's stated limit.
- **Its other refusals**, in this order after the agent-session one, each with its own message and nothing written: an option other than `--said`, the main checkout (`approve must run inside a worktree`), no origin (`approve needs an origin remote`), no git identity (`approve needs a git identity`), an issue that is not `preparing` on `origin/main` (`<id> is <status> on origin/main: approve takes an issue that is preparing`), a design that is not `ready` here (`not design: ready`), and a tree with changes outside the issue's folder (`approve commits <id>'s folder and nothing else: commit or discard the change outside it first (<path>)`; another issue's folder is outside too). A `provenance.md` that does not parse is refused with `provenance.record`'s reason. The hash is taken over the folder as git sees the working tree (tracked files and untracked ones that are not ignored), before the record is written, so a design file git has not seen yet is in it and `approve` commits it.
- **The order of an interactive prep** (z-design step 5, zz-rules "Design approval"): the agent finishes the design and the reviews, sets `design: ready`, commits everything (the prep commit), and tells the user to run `./zn approve <id>` in a terminal of their own in the prep worktree; the user says so; the agent runs `./zn status <id> prepared`, commits it and pushes. A `!`-prefixed command typed in the agent's session inherits the session's variables and is refused too (E4, OC1).

### Behaviour 2: `./zn status <id> prepared` needs a current approval
The carried move refuses, after the per-issue refusals it already has (`design: ready` among them, so `c0053/commands-claim`'s `design: ready` answer is unchanged; the raft-level checks, a raft's Theme and coherence review, come after the per-issue loop and so after this one), each issue it moves until the newest `approved` row of that issue's `provenance.md`, **committed** (`<id>'s provenance.md has changes that are not committed: the approval is the commit ./zn approve <id> makes`: tracked and equal to HEAD's), has `design=` equal to `recordHash` of the folder now: `<id> has no current approval: ./zn approve <id>` (no row, or a row that names no design) or `<id> was redesigned since its approval (it covered <old>): ./zn approve <id> again`. It covers an issue named alone and each member a raft's move changes (`new` issues claimed with the raft or `preparing` ones); a member already prepared on `origin/main` is taken as it is, and a raft's own document needs none. A redesign after a stop (`prepared -> preparing`, edits, `prepared`) changes the hash and needs a fresh approval; a stop with no edit keeps the hash and the old approval. Under `ZN_DISPATCH` the move refuses an **issue** (after the approval check) as `<id>: a dispatched step does not prepare a design`; a raft's own move under `ZN_DISPATCH` (z-raft, all members already prepared) is unchanged. No flag skips the refusal. The frozen list is not read here: a listed issue taken through `preparing` again is a deliberate re-prep and needs its approval like any other.

### Behaviour 3: the doors
`fold`, `new raft` (with prepared members) and `ready`, the three ways a prepared issue enters a raft or an active raft, `./zn raft-plan` and `./zn audit` hold every prepared backlog issue to one rule, `provenance.approvalProblem(id, hash, rows, exempt)`: a current approval passes; so does an id on the frozen list at its current design hash (`redesigned since the freeze` once it differs, which then needs `./zn approve`); a stale approval is `<id>'s approval no longer covers its design (<old> -> <new>)`; no approval and no listing is `<id> is prepared without an approval and is not on the frozen list`. The rule is **in force once the base has the frozen list**: `exempt == nil` (no `z-nile/provenance-exempt.txt` on `origin/main`, or no origin) enforces nothing at the doors (the carried move still needs an approval, because its approval check does not read the list). The list is read from `origin/main`, never from the working tree (guards-trust-only-origin). **Failing closed:** a list that was on `origin/main` (`git log -1 origin/main -- <file>` names a commit) and is gone is read as an empty list, so the rule is in force with nothing exempt and `audit` reports `exempt-list-gone` naming the file; one that does not parse refuses everything that reads it (`<id>: origin/main's z-nile/provenance-exempt.txt does not parse: …`). Only a base that never had the file, or no origin, enforces nothing (a shallow clone that has lost the add commit looks like a base that never had it: stated limit).
- `fold` and `new raft` check inside their published claim's build (read from the tree `origin/main` has), `ready` inside `moveOnOrigin`'s verify step (the same tree it publishes), so each refuses before it publishes anything: a refused `fold` leaves `origin/main` and the raft's status as they were.
- `raft-plan` reads the local tree (`gitFolderFiles`) and the list from `origin/main`: an unapproved prepared raftless issue is never planned; it prints `skip <id>: <reason>` and nothing else for it, so `raft-plan --apply` (which runs the printed commands) is never left half applied.
- `audit` reports `unapproved-prepared` (an error, path the issue's folder, the reason above) for each prepared backlog issue that fails the rule, in `cmd.audit` only (`audit.run`'s other callers, `compact` and `remap`, do not run it). Active and done issues are not checked.
- `recombine` moves already-rafted members between rafts and is not a door; `unfold` and `stop` take issues out and are not checked.

### Behaviour 4: the frozen list
`z-nile/provenance-exempt.txt` (`provenance.exemptRender`, parsed by `provenance.exemptParse`): `render` writes two `#` comment lines, then `<id> <12-hex design hash>` per line, sorted; `parse` accepts those and any blank or `#` line anywhere, entries in any order, and refuses an entry that is not `<id> <12 hex>` and an id twice. `./zn provenance freeze` writes it once: a worktree command (refused in the main checkout, with no origin, and once `origin/main` has the file: `<file> is frozen: it is on origin/main`), listing every backlog issue that is `prepared` in the tree it runs in and every `active` issue with `design: ready` (a raft's `stop` gives such an issue back to the backlog stamped `prepared`, with no approval), each at `recordHash` of its folder. It does not commit. **`./zn provenance freeze --check`** (read-only, a worktree command) compares the list committed at HEAD with what `freeze` would write from this tree, in both directions (an issue prepared or readied and not listed, a listed id that is neither, a wrong hash), failing with the differences; the executor runs it after `freeze` and again after the last `./zn sync` before the merge, and AC8 runs it (`audit` cannot judge a list that is not yet on the base). The executor runs `freeze` as the last step of this raft, after merging `origin/main`, and commits the file; from the merge on, the doors and `audit` read it from `origin/main`, so no PR can add its own exemption. If `--check` finds an issue that was prepared after the freeze, rerun `./zn provenance freeze` (it rewrites a list that is not yet on the base) and commit. After the merge an issue prepared by a PR cut before the freeze, or after it, has no listing and needs `./zn approve` (a migration note in zz-rules). **Fixtures** never hold the real list: `z-nile/tests/lib/engine.luau` adds `provenance-exempt.txt` to `engine.STATE` and `:(exclude)z-nile/provenance-exempt.txt` to `engine.PATHSPECS`, so a fixture's base has a list only when its seed gives one (the rule is then not in force in the 50-odd specs that drive a door or `audit`). **A compaction** (`compact`, `remap`, `renumber`) renumbers items: a listed id then names another issue or none, and every approval of a rewritten document is stale; the list can never be rewritten. This voids the grandfather of every listed issue (cost: stop, `./zn approve`, `prepared`, PR for each prepared issue, about 30 today); whether compaction should instead carry the list through `keepRecords`, or refuse while a prepared issue is listed or approved, is the user's call (open question Q2 in the hand-off report); until they answer, this design accepts the cost.

### Behaviour 5: the dispatcher's prep gate (`dispatch.luau`, `gate`)
The `prep` gate never merges, whatever `auto_merge` says: the merge branch is for `raft` only. Every prep stop is exit 4 with the reason it already had in its turn (not in `auto_merge`, draft, red, unmergeable, carries code) followed by `; approve the design with ./zn approve <id>, then merge it yourself and run ./zn dispatch <id> again`. The checks stay in the order they were, so every existing assertion on a reason stays true; a green, mergeable, clean PR the gate would once have merged says `the prep PR #<n> waits for the user's approval and merge` (never the old fallthrough "its head commit is unknown"), with the same suffix. `auto_merge` keeps accepting `prep` as a name (no config breaks), with no effect; the root `.models.toml` drops it and its comment says why. A dispatched z-design step ends at an open PR with `design: ready` and status `preparing`: it never runs `approve` (refused under `ZN_DISPATCH`) or `status <id> prepared` (refused for an issue, Behaviour 2). The user runs `./zn approve <id>` and `./zn status <id> prepared` in the prep worktree (`.worktree/prep-<slug>`; `./zn worktree prep-<slug>` prints it), commits, pushes and merges. The stop's suffix does not name that path: `gate` is a pure function over facts that carry no worktree, and adding one would change every dispatcher spec's facts for a path the user already has from `./zn worktree`.

### Scalability
`approvalFault` reads one folder's files (a few files) per issue it judges; `audit` and `raft-plan` do it for each prepared backlog issue (tens today, a `git ls-files` and some reads each), once per command, no loop over history. The frozen list is one file read once per command.

### Maintainability
One rule, one function: the doors, `audit` and (through the same `approval`) the carried move use `provenance.approval`/`approvalProblem`; the agent-session test is `provenance.hint` through `sessionEnv()`, the same function `liveActor` calls; the design hash is `raftplan.recordHash`, the one list of what a design is. The pure rules live in `provenance.luau` (text in, text out, spec'd without a repository), the adapter calls them with files read at the edge (zz-arch).

### Usability
Every refusal names the command to run (`./zn approve <id>`, `./zn approve <id> again`) and, for the agent-session one, where (your own terminal, in this worktree, with the path). The doors and `audit` name the issue and the reason in the same words.
