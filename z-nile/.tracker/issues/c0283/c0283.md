## Solution
Two additions on top of #295's `./zn approve`:
- **It is refused in an agent session even with a terminal** (`CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID`, read through c0263's `provenance.hint`), the user's c0263 decision "refuse approve in any agent session".
- **It records the approval in c0263's record**: an `approved | human:<git name> | design=<first 12 hex of the approval's hash>` row in the issue's `provenance.md`, in the same `tracker: approve` commit as `approval.md`.

- **`./zn approve <id> --publish` publishes that row with `approval.md`** in one commit, and the publish validator accepts exactly one appended `approved` row only when the same commit appends the matching `approval.md` row (the same human, a hash that starts with the row's `design=`). This is how the approver of a prep PR that the dispatcher already merged reaches `main`, and so `./zn who` and the board (re-prep, "Re-prep c0283").

### Behaviour 1: `./zn approve` is refused in an agent session
In `cmd.approve`, in the branch that writes (not `--check`), after #295's `ZN_DISPATCH` refusal and before its terminal check: the environment is read through `provenance.AGENT_VARS` (new, the one list `provenance.hint` reads: `CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID`, `ZN_DISPATCH`), and `provenance.hint(env).agent` refuses with `<id>: approve is refused in an agent session, terminal or not. Run ./zn approve <id> yourself, in your own terminal, in this worktree (<path>).` In a session with no terminal at all the `zn` wrapper's own terminal test answers first (#295's text); with a terminal an agent holds, this engine check answers. There is no flag, option, variable or configuration that lets an agent through: a `ZN_ACTOR` that claims a human changes nothing, and the engine reads no "allow" input. A `ZN_DISPATCH` session keeps #295's own answer (`ZN_DISPATCH is set`). `--check` only reads and stays allowed everywhere. **The argument that the human really ran it**, the one zz-rules' guards all use ("Keep same user, accept detection") and the user's c0263 decision "refuse approve in any agent session" (2026-11-08) asks for: the guard detects an agent session by what the session carries (the markers an agent CLI sets), so it refuses the honest mistake and the casual workaround even when the agent has a terminal; it is not a security boundary against a process started without the markers (`env -u CLAUDECODE ./zn approve`) or against files edited by hand, and `approve` has no code path that sets, clears or ignores the markers (the spec harness clears them in the processes it starts). What #295 adds to "a human ran it" (a terminal, a git identity, a commit by that identity that `ready` re-derives from the contract) stays. A `!` command typed in an agent's session inherits the session's variables and is refused too (E4, OC1).

### Behaviour 2: the `approved` row
`cmd.approve`, after #295 has decided the approval text and before it writes anything: the item's `provenance.md` (if any) must have no uncommitted change (`<id>: commit <path> first, then ./zn approve <id>`), and `provenance.approved(text, id, who, hash, now)` returns the new record or refuses (`<id>: <why>`: a name the record cannot hold, a record that does not parse); only then are `approval.md` and `provenance.md` written, `git add`ed and committed together as `tracker: approve <id>` (`git commit -- <both paths>`), so a refusal leaves the tree and `HEAD` as they were. The row is `| <UTC YYYY-MM-DD HH:MM> | approved | human:<git name> | design=<first 12 hex> |`. **How it relates to `approval.md`:** `approval.md` stays the authority (the full hash, its parts, who and when to the second, and the file `ready`, `done`, `land` and `--check` read); the row puts the same approval, by the same human and in the same commit, in the record `who` (c0280) and the board (c0284) read, with the first 12 hex of the hash so a reader can tie the two. Nothing reads the row to decide anything, so a row edited by hand changes no gate; c0263's append-only rule and union keep the record's old rows. A second approval (after a redesign) appends a second row; an issue approved before this lands has `approval.md` and no row, which is left alone. The row carries no words.

### Behaviour 4: `--publish` carries the row (re-prep, R0099 F1)
**The gap.** `.models.toml` sets `auto_merge = ["prep","raft"]` and `approve` refuses under `ZN_DISPATCH`, so a dispatched prep PR merges before any human approves; the human then approves in a new worktree of `main` and runs `./zn approve <id> --publish`, which published `approval.md` alone. The row Behaviour 2 wrote sat in a local commit nobody pushes, and c0263's validator would refuse it anyway (`provenance.PUBLISHED` is `unblocked`, `confirmed`, `ranked`). Without a fix `who` and the board show no approver for a dispatched prep, which misses c0263's captured outcome "Design approved by". The interactive path (the human approves before the prep PR merges) still carries both files in the `tracker: approve` commit, as Behaviour 2 says.

**In `cmd.approve --publish`** (after #295's checks, where it decides `onMain == localText`): the worktree's `provenance.md` is parsed; the row it holds that is `approved` with `detail == design=<first 12 hex of the local approval.md's last row's hash>` is this approval's row. When `origin/main`'s record does not hold that row (event, actor and detail), the record to publish is `provenance.record(origin/main's provenance.md, id, "approved", row.actor, row.detail, row.when)`: origin's file with the row appended, never the worktree's file, so rows published meanwhile are kept and the old rows stay in place. The one `publish.commit` then carries `approval.md` and `provenance.md`, subject `tracker: approve <id>`. An approval made before this lands has no row and publishes `approval.md` alone, as before; "already approved" is printed when `approval.md` already equals origin's.

**In `publish.luau`**, the `provenance.md` branch: the rule of c0263 is applied first (`publishProblem(existing, new, id, allowed)`, `allowed` unchanged: `provenance.PUBLISHED`, `unblocked` only in `active/`). Only when it refuses, the item is not in `active/` and the same commit changes the same folder's `approval.md`, the pure rule `provenance.approvedPublishProblem(old, new, id, approvalOld, approvalNew)` decides, and its answer (nil or its reason) replaces the refusal. It holds when and only when: the record is an append of exactly one row (`publishProblem` with `allowed = {"approved"}`: parses, header names the id, old rows in place, every new row `approved`), `approvalNew` parses and extends `approvalOld` (the `origin/main` text, if any) by exactly one row with every old row's `when`, `who` and `hash` unchanged, the new row's `actor` is `human:` plus that approval row's `who`, and its `detail` is exactly `design=` plus the first 12 hex of that approval row's hash. Everything else stays refused, naming the file: a lone `approved` row (also beside an `approval.md` that did not change), a row of another human or another hash, two rows (or two approval rows), an old approval row rewritten, another issue's `approval.md` in the commit, an `active/` issue, a done one (its record is written in a PR). `provenance.PUBLISHED` and `./zn provenance record` are not changed, so a person cannot publish an `approved` row with no `approval.md` behind it: **c0263's contract is unchanged** (its validator, its `appendOnly`/`publishProblem` and its specs run green on the prototype); the one added case lives in c0283's function and `publish.luau`'s branch.

**What it rests on.** `approval.md` stays the authority: the row is derived from it by the same command, and the validator ties the two by human and hash prefix, in the commit that publishes both. It does not prove a human ran `approve` (nothing in `publish.commit` can: "Keep same user, accept detection", Behaviour 1 is the guard); it removes the one way to publish a row with no approval behind it.

One extra file read and write per `approve` (a human step).

### Maintainability
One list of agent markers (`AGENT_VARS`), read by `hint` and by `approve`; one record writer (`provenance.record`); the pure row builder is spec'd without a repository.

### Usability
The refusal names the command to run and where (your own terminal, in this worktree, with the path); the prep stop names `./zn approve <id>`.
