## Solution
Three additions on top of #295's `./zn approve`:
- **It is refused in an agent session even with a terminal** (`CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID`, read through c0263's `provenance.hint`), the user's c0263 decision "refuse approve in any agent session".
- **It records the approval in c0263's record**: an `approved | human:<git name> | design=<first 12 hex of the approval's hash>` row in the issue's `provenance.md`, in the same `tracker: approve` commit as `approval.md`.
- **The dispatcher's prep gate never merges**: it stops, whatever `auto_merge` says, and waits for the user to approve and merge.

### Behaviour 1: `./zn approve` is refused in an agent session
In `cmd.approve`, in the branch that writes (not `--check`), after #295's `ZN_DISPATCH` refusal and before its terminal check: the environment is read through `provenance.AGENT_VARS` (new, the one list `provenance.hint` reads: `CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT`, `GROK_SESSION_ID`, `ZN_DISPATCH`), and `provenance.hint(env).agent` refuses with `<id>: approve is refused in an agent session, terminal or not. Run ./zn approve <id> yourself, in your own terminal, in this worktree (<path>).` In a session with no terminal at all the `zn` wrapper's own terminal test answers first (#295's text); with a terminal an agent holds, this engine check answers. There is no flag, option, variable or configuration that lets an agent through: a `ZN_ACTOR` that claims a human changes nothing, and the engine reads no "allow" input. A `ZN_DISPATCH` session keeps #295's own answer (`ZN_DISPATCH is set`). `--check` only reads and stays allowed everywhere. **The argument that the human really ran it**, the one zz-rules' guards all use ("Keep same user, accept detection") and the user's c0263 decision "refuse approve in any agent session" (2026-11-08) asks for: the guard detects an agent session by what the session carries (the markers an agent CLI sets), so it refuses the honest mistake and the casual workaround even when the agent has a terminal; it is not a security boundary against a process started without the markers (`env -u CLAUDECODE ./zn approve`) or against files edited by hand, and `approve` has no code path that sets, clears or ignores the markers (the spec harness clears them in the processes it starts). What #295 adds to "a human ran it" (a terminal, a git identity, a commit by that identity that `ready` re-derives from the contract) stays. A `!` command typed in an agent's session inherits the session's variables and is refused too (E4, OC1).

### Behaviour 2: the `approved` row
`cmd.approve`, after #295 has decided the approval text and before it writes anything: the item's `provenance.md` (if any) must have no uncommitted change (`<id>: commit <path> first, then ./zn approve <id>`), and `provenance.approved(text, id, who, hash, now)` returns the new record or refuses (`<id>: <why>`: a name the record cannot hold, a record that does not parse); only then are `approval.md` and `provenance.md` written, `git add`ed and committed together as `tracker: approve <id>` (`git commit -- <both paths>`), so a refusal leaves the tree and `HEAD` as they were. The row is `| <UTC YYYY-MM-DD HH:MM> | approved | human:<git name> | design=<first 12 hex> |`. **How it relates to `approval.md`:** `approval.md` stays the authority (the full hash, its parts, who and when to the second, and the file `ready`, `done`, `land` and `--check` read); the row puts the same approval, by the same human and in the same commit, in the record `who` (c0280) and the board (c0284) read, with the first 12 hex of the hash so a reader can tie the two. Nothing reads the row to decide anything, so a row edited by hand changes no gate; c0263's append-only rule and union keep the record's old rows. A second approval (after a redesign) appends a second row; an issue approved before this lands has `approval.md` and no row, which is left alone. The row carries no words.

### Behaviour 3: the dispatcher's prep gate never merges
`dispatch.luau`, `gate`: the merge branch is for `raft` only. Every prep stop is exit 4 with the reason it already had in its turn (not in `auto_merge`, draft, red, unmergeable, carries code) followed by what the user does, by reason: `; approve the design with ./zn approve <id>, then merge it yourself and run ./zn dispatch <id> again` when nothing else holds the PR back (not in `auto_merge`, or no condition fails); `; when that is resolved, approve the design with ./zn approve <id>, merge it yourself and run ./zn dispatch <id> again` for a draft, red CI or an unmergeable PR; and, for a PR the judgement holds back (code, another item's files), `; a prep PR carries only its issue's folder and skill lessons` with no instruction to merge it. The checks keep their order, so each existing assertion on a reason stays true. A green, mergeable, clean PR the gate would once have merged says `the prep PR #<n> waits for the user's approval and merge` (never the old fallthrough "its head commit is unknown"), with the first suffix. `auto_merge` keeps accepting `prep` as a name, with no effect; the root `.models.toml` drops it and its comment says why. A dispatched z-design step ends at an open PR with `design: ready` and status `preparing`; it never runs `approve` (refused under `ZN_DISPATCH` by #295 and as an agent session here). The user runs `./zn approve <id>` in the prep worktree (`.worktree/prep-<slug>`; `./zn worktree prep-<slug>` prints it), commits, pushes and merges; the stop's suffix does not name that path because `gate` is a pure function over facts that carry no worktree.

### Behaviour 4: the texts
zz-rules' approve row says the refusal (agent session, terminal or not), the row and that it records no words; its Landing step 3 and its chain paragraph say the dispatcher passes the rafting gate only and a prep PR waits for the user; z-design step 5 says the human runs `./zn approve` in a terminal of their own (a `!` command included) and step 6 says the dispatcher stops at the prep gate for the user; the README's Provenance line and AGENTS.md name the human approval. `tests/tooling/dispatch-texts.spec.luau` pins those sentences and is edited here (its z-design constant splits; z-raft's sentence is unchanged: the rafting gate still merges).
