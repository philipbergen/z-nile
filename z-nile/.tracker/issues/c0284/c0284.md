# c0284: Board shows provenance

## Problem
Scope decision (user, 2026-11-08): "Split it and prototype first, like c0265" (c0263 Ticket provenance was split into c0263 (the record: provenance.md, ./zn record, the append-only publish rule, the union of two writers) and this issue and its siblings; one raft, delivered a layer at a time in depends_on order; this issue depends on c0263, which its prep writes into depends_on). Carried from c0263's capture (User, 2026-11-07): "The board shows them": the board's item view shows each ticket's provenance, the same entries ./zn who prints for it (one shared reader of the history, so the two views cannot disagree). It also depends on the issue that builds ./zn who, and it shares board.luau with c0276 (board shows lost work) and R0083 (c0118): it adds to the board without changing their signatures.

## Non-goals
- The record, `./zn provenance record`, the append-only publish rule and the union of two writers: c0263. The reader (`who.entries`, `who.fronts`, `who.people`, `trail.lifeOf`, the derivation and the merge): c0280. This issue calls them, and changes no `Entry`, `Derived`, `select` or `merge`.
- The lifecycle rows (c0282) and the approval (c0283): their rows print when they exist, like any stored row.
- The served board (c0121, c0289) and the Omarchy app (c0290, c0257) are built by other issues. They read the same model, so the `provenance` key reaches them without a change here, but this issue builds and tests the static page only.
- Writing anything: the board reads and never stores a provenance row.

## Solution
Captured (see Problem): the board's item view shows each ticket's provenance, the same entries `./zn who` prints for it, from one shared reader of the history. Prep's detail below that bullet (nothing captured is changed): a new edge module `boardprov` reads the history once per build and hands every item to c0280's `who.entries`; `board.collect` puts the result on each `Issue` and `Raft` as `provenance`; the item view's script writes a "Provenance" section from it.

## Design

### Decisions this layer relies on (quoted)

There is no exception (c0263's hand-off excepted the derived `rafted` fallback; c0280's `who.entries` derives it from `who.fronts`, so the board shows it too).
- c0280's layer rule: this layer "calls `who.entries` with `who.fronts` and `who.people` and builds lives with `trail.lifeOf`; it may add fields to the board model and may not change `Entry`, `Derived`, `select`/`merge` semantics or `provenance.line`". The additive `dir` parameters and the batching of `who.sideTrailers` below change no semantics of those.
- Decided with the user (2026-11-12), the actor on `merged`: "The agent trailer" (c0280's; the board prints whatever `who` prints).

### Behaviour (every outcome this layer owns)
1. **The model carries the entries `who` prints (AC1).** `Issue` and `Raft` gain `provenance: { boardprov.Entry }?` (`boardprov.Entry` is `provenance.Entry`). For an item with history on the published mainline, the entries are `who.entries(life, people, rows, spend, fronts, mark)`, the call `cmd.who` makes, so `provenance.line` of each board entry is the line `./zn who <id>` prints. `board.collect` fills the field in one block before it sorts `problems`: it builds one `boardprov.Item` per issue and raft (`id`, `kind`, the folder as the board reads it, and for an issue its spend rows through `who.spend`; a raft's `spend.md` is a roll-up and names no worker) and calls `boardprov.read(items, dir, problems)`.
2. **The history is read once per build (AC3).** `boardprov.read` reads, for every item together: one `git log --first-parent` of `<root>/issues` and `<root>/rafts` for every root of the registry at the head (`trail.logArgs`, the log `trail.read` runs, now built in one place), parsed once by `trail.parse` given every item folder as `dirs`; the commits bucketed by the item folder they changed (`boardprov.bucket`); each bucket cut into a life by `trail.lifeOf` with `trail.cuts(head)` and `who.want`, as `read` cuts it (so a reused number, a compaction cut and the file filter agree with `who`); one `who.sideTrailers` over the parsed commits, which reads the second parent of **every** merge in one `git log --no-walk=unsorted --stdin` (a history gains a merge per landed raft, and a process per merge would grow with it; E10); one `who.fronts` for every life (one `git cat-file --batch`); one `who.people`. Five git processes for any number of items, merges and lives (E1: 372 items, 1,240 entries, 0.7 s on top of a 1.6 s board).
3. **The checkout is the one the board was given, and the history is the published mainline (AC2).** Every git call of the board's history read runs in the board's checkout (`board.collect`'s `checkout`, the directory `history.read` reads too), never in the folder `./zn` happens to run in, and on `who.head(dir)`: `origin/main`, else `HEAD`. To do that, c0280's `who.head`, `who.people`, `who.fronts`, `who.sideTrailers` and c0263's `trail.cuts` gain a trailing optional `dir` (nil: the current folder, as before), and `trail.logArgs` is extracted from `trail.changes` unchanged. `who.sideTrailers` is batched as Behaviour 2 says (its results and the lives it serves are what c0280's `who.spec` pins, and `who` is one merge faster). Without `dir` a spec that builds the board of a fixture checkout from the real repository's folder would show the real repository's history; a board built in a worktree with unpublished commits would show them.
4. **The same refusals and fallbacks as `who` (AC4, AC5).** `who` refuses an item whose `provenance.md` does not parse, an issue whose `spend.md` does not parse, and an item with no history on the mainline. The board must still build, so: an item whose `provenance.md` does not parse is named in `model.problems` (`<path> does not parse: <why>`, the form the board uses for `spend.md`) and has no `provenance`; an issue whose `spend.md` does not parse (named once, by the existing spend reader) has none either, so no entries `who` never prints are shown; every other item is unchanged. An item with no commit on the mainline that holds its document (it exists in a worktree only) shows its stored rows alone, and one with neither history nor a stored row has no `provenance` key (the list is never empty: a key with `[]` would change every existing page for nothing). The history is read whenever the checkout is a git repository's top level (`history.atTop`, the check `history.read` makes first), shallow or not: a shallow clone shows what `./zn who` prints for it (the truncated log read the same way), while `model.history` stays false as before. Only a tree with no git of its own (a root passed by a spec, a folder inside another repository) shows the stored rows alone, which is `who.entries` with an empty life.
5. **The page (AC1).** `board.html` gains `provenanceOf(item)`: nothing when the item has no `provenance`, else `<h3>Provenance</h3>` and a table with one row per entry (`when`, `event`, `actor`, `detail`, `source`, every cell escaped by the page's `esc`), called after the run details in `renderIssue` and in `renderPane` (the raft view). It reads the keys only; the order is the model's (oldest first, as `who` prints it).
6. **Docs (AC6).** The zz-rules board row and the README's board paragraph name the Provenance section.

### Interfaces
```
-- z-nile/engine/boardprov.luau (new; the edge, plus one pure function)
export type Entry = provenance.Entry
export type Item = { id: string, kind: string, dir: string, spend: { provenance.Spend } }
boardprov.bucket(commits: { trail.Commit }): { [string]: { trail.Commit } }          -- pure
boardprov.read(items: { Item }, dir: string?, problems: { string }): { [string]: { Entry } }
-- additive, in the layers below
trail.logArgs(head: string, specs: { string }, firstParent: boolean): { string }
trail.cuts(head: string, dir: string?)
who.head(dir: string?), who.people(head: string, dir: string?), who.fronts(commits, dir: string?), who.sideTrailers(life, dir: string?)
who.spend(rows: { ledger.Row }): { provenance.Spend }                                 -- cmd.who and the board both map spend rows here
history.atTop(dir: string): boolean                                                    -- the check history.read makes first, exported
-- board.luau: Issue.provenance, Raft.provenance: { boardprov.Entry }?
```
`main.luau` is at Luau's limit of 200 local variables: this layer adds no top-level local (the one changed line is inside `cmd.who`, which already requires `who` inside the function).

### Where it bites (each place read, not assumed)
- `board.collect` is the one place a model is made; `board.build`, `./zn board`, the sync refresh (`buildBoard`) and the specs all go through it, so every page carries the field. `history.read` returns nil unless the checkout is a git top level that is not shallow; `boardprov` is given the checkout whenever `history.atTop` holds.
- `trail.parse`'s `inDir` is a set, so passing every item's three folders per root costs memory and no time; the git pathspecs are the two kind folders per root, not the item folders (7,000 pathspecs would not be a cost anyone wanted to measure).
- `who.sideTrailers` matches by sha over the list it is given, so calling it on all parsed commits sets the trailers on every copy `lifeOf` clones afterwards.
- The page embeds the model as JSON: 372 items add about 1,240 entries (about 200 bytes each). Pages of specs that have no git history and no `provenance.md` are byte-for-byte what they were.
- Specs that read the board and were not in my first list (`c0057/open`, `c0057/guard`, `tooling/tracker-guarded`, `c0053/commands-sync`) were run by the reviewer: green.

### Scalability
Five git processes per build: the mainline log, the authors' emails, the compaction cuts, one `cat-file --batch`, one `git log --no-walk --stdin` for every merge's second parent; constant in the items, the merges and the lives. The pure work is O(commits). The JSON grows with the entries. Measured on the real tree (about 2,000 commits, 372 items): `board.collect` takes +0.7 s of wall time on an idle machine (2.3 s against 1.6 s) and, as the reviewer measured under load, about 0.40 s of its own CPU against 0.31 s. Reading each item alone costs about 0.25 s each (E2: 70 s for 280 issues under load).

### Maintainability
One reader per format: the log is `trail`'s (`logArgs`, `parse`, `lifeOf`), the record is `provenance.parse`, spend is `ledger.parse` through `who.spend`, the entries are `who.entries`. The next event the record learns needs no change here (a stored row prints, a derived one comes from `who`). The page reads keys, so c0254's worker columns reach it through `who.spend` alone.

### Usability
A reader opens an item and sees its history in `who`'s order and words, with `(from git)` in the actor where git said it and `git`/`record` as the source. A bad record is named on the board's problem list, not a failed build.
