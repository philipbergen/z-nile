### F6 [medium] One `git log -1` per merge grows with every landing, and AC3 pins that shape while counting none of the other per-build reads
Where: Design, Behaviour 2 ("A constant number of git processes for any number of items") and Scalability; AC3; `acceptance/board.spec.luau:362-373`; `who.sideTrailers`.
Evidence: `readLives` calls `who.sideTrailers` on every parsed commit, which is one process per distinct merge that touched an item's document or record. Since #296 every `./zn done` lands with a `--no-ff` merge (zz-rules, the `done` row; c0280, Behaviour 3), so each raft landed from now on adds one process to every board build. Measured through `./zn run` in the proto worktree: 50 × `git log -1 --format=%(trailers:…)` took 2.35 s, and one `git log --no-walk=unsorted --format=@@%H %(trailers:…)` over the same 50 commits took 0.10 s. The case asserts `singles == 1` for the fixture's one merge, so a batched read (no `git log -1` line) fails it, and one merge can't tell per merge from batched. It counts neither `who.people` nor `trail.cuts` (lines 361-369 count only `--first-parent` logs and `cat-file --batch`), so a mutant that calls either once per item keeps every count.
Critique: this scalability trap grows for the project's whole life, in a function the design calls constant. The tempting fix, an in-process memo, doesn't help `./zn board` or `sync`, which each start a new process.
Consequences: batching inside `who.sideTrailers` changes c0280's implementation, not its semantics, which c0280's layer rule allows (`Entry`, `Derived`, `select`/`merge` and `line` are unchanged), and `who` then also reads its life's merges in one process. With very many merges, the shas go through `--stdin` (no argv limit). A second parent that can't be read gives no values, as today.
Recommendation: read every merge's second-parent Co-Authored-By values in one process (`git log --no-walk=unsorted --stdin '--format=@@%H%n%(trailers:key=Co-Authored-By,valueonly,unfold,separator=%x1f)'`) and set `sideTrailers` as today. Add a second `--no-ff` landing of another item to the fixture, whose top layer carries a different agent trailer (both merged actors equal `who`'s). AC3 then counts exactly one second-parent read for the two merges, plus one people log, one cuts log, one mainline log and one cat-file, matched as F4 says. AC3's text and Scalability become "one read of every merge's second parent". Rows: "one second-parent read per build" (mutant: per merge), "one people read" (mutant: per item), "one cuts read" (mutant: per item).

Where: Design, Behaviour 4; the new block in `board.collect` (`spendRows`); `boardprov.read`; `history.read`'s shallow refusal.
