# c0285: Lesson capture squash keeps tracker new

## Problem
zz-rules (Merging): a capture that lands by pull request keeps its capture commit's subject, 'tracker: new <ids> <title>', as the squash-merge subject, because PR #258 (the user's capture-workers commit 2e282833, 'tracker: new c0260 c0261 c0262 c0263 c0264 c0265 c0248 c0249 c0250 c0253 c0175 c0257 ...') was squashed by the coordinator as 'tracker: capture workers carry rafts to merge ...', so ./zn capture fell back to the old one-line stubs for those issues and z-design's scope checks compared against the wrong text; check: does the squash subject of a capture PR start with 'tracker: new' and list every id its capture commit listed?

## Non-goals
- **Codifying the rule** (c0181). c0181 (prepared, solo) owns the lesson states (`enforced_by`, `not_codifiable`) and the sweep that states every lesson on `main`, so it states this one when it lands after it; if c0181 lands first, the executor stops and asks the user (Decisions 6). No hook, lint or dispatcher change is made here.
- **Repairing the captures already lost.** `./zn capture` still answers a stub or a first add for c0260, c0261, c0263, c0264, c0265, c0304 and f0171 (E1). A new capture commit for any of them would be a capture of its own, with the user's words; this issue changes no item but its own.
- **The dispatcher's squash** (`z-nile/engine/dispatcher.luau` `merge`, which passes no `--subject`). It merges only gate PRs (prep, rafting), and the new Merging text says those must carry no capture commit; making it read the PR's commits is c0181's sweep's to classify.
- **`./zn land`**: it already keeps the capture (its pushed commit takes the branch's first subject, `main.luau` `cmd.land`), and is not touched.

## Solution
One new, short lesson, `zz-rules/squash-keeps-the-capture-commit`, `when: both`, whose `check` keeps the captured question word for word and adds the later-edit clause; one paragraph in zz-rules Merging, right after the `gh pr merge … --squash --subject` line it qualifies, that tells the merger to keep a capture's subject with every id, and to land a PR whose later commits edit the captured documents by a merge commit instead; a pointer to it in Landing a change step 3, where "any other PR is merged with `gh pr merge --squash`"; a note on z-ticket's `land-a-challenged-idea` lesson, the instruction that opens capture PRs; and the harvest note that makes the incident the lesson's source.

## Design
The captured outcome is the lesson; the Merging paragraph is the skill text that restates it (chore checklist, Restated rules: Merging's own squash template `--subject "<raft>: <title> (#<pr>)"` is what the coordinator followed for PR #258).

### Decisions
1. **A new lesson, not a note on an old one.** `zz-arch/history-tests-survive-squash` is about tool rules that decide by "a commit of branch X that main doesn't have"; `zz-rules/item-history-spans-moves-and-compaction` is about lookups of an item's past across moves. This one is about how a merger lands a capture. Neither's `check` asks it.
2. **Under zz-rules, `when: both`.** The captured Problem opens "zz-rules (Merging):". Merges are run by prep leads, raft leads and coordinators, so the lesson reaches the design pass (`--when design`) and the build pass and raft prompt (`--when build`).
3. **The rule is about the tree too, not only the subject.** `./zn capture` (`cmd.capture`: `trail.read` with `trail.isDoc`, then `trail.capture`) takes the newest commit whose subject names the id after `tracker: new`, and prints the item document at that commit. A squash that keeps the subject but also carries later edits of the same document (a prep built on an unlanded capture, as #265 was: it carried d8c92926, the capture of c0260 to c0265 again) makes `./zn capture` print the later text, so scope checks would compare the design with itself (E5: the squash rows). The rule therefore has two branches. When nothing later in the PR changes the capture's item documents, squash with `tracker: new <every id> <title> (#<pr>)`; this keeps the captured rule ("keeps its capture commit's subject … as the squash-merge subject"), and it is the case of every real loss but #265 (#57, #178, #258, #317). When a later commit does, land the PR with a merge commit (`gh pr merge <pr> --merge --subject "<title> (#<pr>)"`), which brings the capture commit to `main` whole, subject and tree (E5: the merge rows). The captured question is kept word for word and gains one clause ("And does no later commit of that PR change those documents, or does the capture commit reach `main` whole (a merge commit)?"): detail, not a narrowing.
4. **A merge commit, not a split** (design review 001 F1). Splitting the PR (the capture cherry-picked into a PR of its own, then `origin/main` merged back) conflicts on exactly the documents the later commits changed, and Merging condition 4 then says `BLOCKED:`; `./zn land` can't take the capture either, since it refuses anything but sections, titles and `depends_on` of draft backlog documents, and both real cases carried more (2e282833 renamed f0263 and f0265, and their `check.sh`; #317's capture commit 0eda093d added `idea-review-001.md` and `idea-refute-001.md`). The repository allows merge commits (`gh repo view --json mergeCommitAllowed` is `true`; #341 landed that way), and rafts already land as `--no-ff` merges through `./zn done`, so `main`'s history readers already see side-branch commits. A merge commit's subject never starts `tracker: new`, so it is never taken for a capture.
5. **"Their documents" is defined** (review 001 F2): the item documents each capture commit changed (`git show --name-only --format= <capture sha>`), never `spend.md`, reviews or other files of the item's folder, because `./zn capture` prints only the item document (`trail.isDoc`). A later spend or idea-review commit (#317, #387) changes none, so those PRs squash. A sync merge of `origin/main` into the branch shows in `git log <capture sha>..<head> -- <doc>` only when `main` changed that document, and then the merge-commit branch is right anyway.
6. **c0181 first is a stop** (review 001 F3). If `z-nile/engine/lessons.luau` names `not_codifiable` when the executor starts, c0181's policy wants a state for this lesson, and the later-edit clause is a git state of the PR branch that a check could decide, so no true `not_codifiable` reason exists for the whole lesson while the clause is undecided. The executor then stops and asks the user (zz-execute stop conditions), with two options: codify the branch-side clause (and perhaps the dispatcher's assumption) here, which grows the issue past its Non-goals; or record the clause as not codified, with a `Decided with the user` line. AC4 then asks only that a state line exists (`^(enforced_by|not_codifiable):`), never its words.
7. **The listing gives what the next step needs** (review 001 F4): `gh pr view <pr> --json commits --jq '.commits[] | "\(.oid) \(.messageHeadline)"'` prints each sha with its headline, `git fetch origin pull/<pr>/head` gets a head the merger may not have, and with one capture commit the subject is its headline plus ` (#<pr>)`.
8. **The dispatcher sentence runs the right way** (review 001 F5): the dispatcher's squash takes GitHub's default subject, so a step it merges must carry no capture commit, and its captures land on `main` first (by `./zn land`, or a challenged idea's pull request, which z-ticket's `land-a-challenged-idea` lesson already makes merge before the prep can claim the item).
9. **The harvest note is the source** (zz-rules, Items): `- note PR #258 squashed its capture commit 2e282833 under another subject, so ./zn capture fell back for c0260, c0261, c0263, c0264 and c0265 (the capture of c0285): zz-rules/squash-keeps-the-capture-commit`, appended to `z-nile/.tracker/issues/c0285/harvest.md` in the same commit as the lesson (a note naming a lesson that does not exist fails `./zn lessons --check`, so prep does not write it). It has no colon before its last one.

### Scalability
One lesson of 11 lines (about 250 tokens in every `--full` read of design and build lessons, 406 today), a 370-byte note on another, one paragraph of about 1,700 bytes and one sentence in zz-rules. The check the paragraph asks for is one `gh pr view`, one `git show` and one `git log` per merge of a PR that carries a capture commit; other merges do nothing new.

### Maintainability
The rule lives once in zz-rules Merging and once in the lesson, each pointing at the other; Landing a change and z-ticket's lesson point at Merging rather than restate it. The promoted spec pins only the skill's phrases, never a lesson's words, so c0181 may cut or merge either lesson without an override (c0192's choice). If the dispatcher's `merge` ever passes a subject, the sentence "The dispatcher's squash takes GitHub's default subject" changes with it, and the spec names it.

### Usability
A merger reads one paragraph next to the command it types: list the capture commits (one command given, with shas), read their documents (one command), check for later edits (one command), then one of two named landings, and a check afterwards (`./zn capture <id>` with no marker). A prep lead reading `./zn lessons --when design` meets the same question before trusting a capture; a capture lead opening a challenged idea's PR meets it in z-ticket's lesson.
