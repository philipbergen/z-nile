The squash subject keeps a capture. A capture lands with `./zn land`, which keeps its commit, but one may ride in a pull request (a challenged idea's, a capture sent by pull request, or a branch built on one). `./zn capture` finds a capture by its subject, `tracker: new <ids> <title>`, and prints the item document at that commit (z-design, Scope is what was captured), so list the pull request's capture commits first: `gh pr view <pr> --json commits --jq '.commits[] | "\(.oid) \(.messageHeadline)"'` (and `git fetch origin pull/<pr>/head` for its head). Their documents are the item documents each capture commit changed (`git show --name-only --format= <capture sha>`, without `spend.md`, reviews or other files): the text `./zn capture` prints. When no later commit of the pull request changes their documents (`git log <capture sha>..<head> -- <their documents>` prints nothing; a later spend or idea-review commit, as on #317 and #387, changes none), the squash subject is `tracker: new <every id they list> <title> (#<pr>)`, which for one capture commit is its headline and ` (#<pr>)`. When one does, a squash would show `./zn capture` the later text, so land the pull request with a merge commit instead: `gh pr merge <pr> --merge --subject "<title> (#<pr>)"`, which brings every capture commit to `main` whole. Afterwards `./zn capture <id>` names the capture commit for each id, with no `(no capture commit: …)` marker. The dispatcher's squash takes GitHub's default subject, so a step it merges (a prep, a rafting) must carry no capture commit: its captures land on `main` first (by `./zn land`, or a challenged idea's pull request) (lesson zz-rules/squash-keeps-the-capture-commit).
