# c0286: Raft plan keeps tied issues together

## Problem
raft-plan rafts an issue alone that the user tied to others in one raft. User (2026-11-08) split c0265 into c0265, c0274, c0275, c0276 and c0277: "yes go ahead and split the whole thing up and tie them togetjer in a raft so we can run through these a layer at a time in a PR". The siblings' depends_on orders the layers, but `./zn raft-plan` never reads depends_on, so once c0265 is prepared and the others are not, `raft-plan --apply` makes c0265 a raft by itself and the layered PR is lost (c0265 design-review-021 F4). The same holds for c0263's split (c0280, c0282, c0283, c0284). What should happen: an issue the user tied to others is never rafted without them; raft-plan skips it and names why until every tied issue is prepared, then groups them as one raft; z-raft with arguments still does what it is asked.

## Non-goals
- `raft-plan` does not read `depends_on`. The order of a tie's layers stays the raft's **Order & dependencies** (z-raft §3), written from the members' `depends_on`; a tie says only which issues share a raft. `depends_on` alone can't be the tie: it also names issues in other rafts (an Overrides chore that must be in `done/` before `start`, a dependency raft's whole chain: lesson z-design/depends-on-inherits-the-dependency-raft).
- No command but `raft-plan` reads `tied:`. `new raft`, `fold`, `unfold`, `recombine`, `ready` and `audit` stay as they are: arguments override a tie (the capture's last clause), and a `tied:` value that can't be read is a `raft-plan` skip, not an audit error.
- The board and `./zn status` do not show ties.
- The heartbeat family (c0265, c0274, c0275, c0276, c0277) needs nothing: all five are in R0100, active, one raft.

## Solution
A recorded user decision that issues land as one raft is written as a front-matter line, `tied: [<ids>]`, on each tied issue by its own prep, naming every other issue of the tie. `raftplan.plan` reads the ties as undirected edges and takes connected groups over every issue in the tree, so the first member prepared already carries the tie. A group with any member not prepared is skipped, each prepared member named with the members it waits for; a group whose members are all prepared is one raft, whatever its size or surface; a group of which some members already sit in one open prepared raft folds the rest into it. A raft holding a tied issue takes no other issue from the plan. The executor writes `tied:` (as the line after `id:`) on the families the user tied whose members are not all in one raft yet: as recommended under Open to the human F1, R0093's six (c0247, c0248, c0250, c0256, c0260, c0262) and the rest of R-vision (c0249, c0251 to c0254).

### Behaviour 1: the `tied:` line
- An issue's front matter may hold `tied: [c0274, c0275]`: the issue ids (f, d or c) of the other issues the user tied it to. `[]` and no line mean no tie. The line sits right after `id:` (review 001 F7): git merges two edits on adjacent lines as a conflict (zz-rules: `raft:` beside `depends_on:`), and of the lines around it `id:` changes only in an id rewrite and `type:` never, while `title:` is rewritten by `./zn land` (a capture's `title`), `raft:` by rafting and `design:`/`status:` by prep. An id rewrite (`compact`, `remap`) rewrites ids in every `.md` under the project roots, `tied:` included; a `renumber` of one copy of a duplicated id rewrites only inside its folder, so a tie naming that id then names the other copy, as `depends_on:` does, and a tie naming an id no issue has is skipped and named (cause 1).
- `raftplan.parseTied(value: string?): ({ string }, string?)` reads it, the one reader (lesson zz-arch/one-reader-per-format): `nil` or `""` → `{}`; `[a, b]` → the ids in order; anything else is a problem and the list is `{}`: `tied: is not a list of issue ids: <value>` (no brackets), `tied: names <e>, which is not an issue id` (an R id, a short id), `tied: names <id> twice` (lesson zz-arch/parsers-refuse-ambiguity, as `parseGrouped` does).
- A candidate (prepared, `design: ready`, raftless, in the backlog) whose line has a problem is skipped with the problem as its reason; its own line adds no edges. So is every other backlog issue whose line has a problem, prepared or not (`skip <id>: tied: …`, after the candidates' skips, by id; review 001 F2): a tie lost to a malformed line is never silent. An issue in `active/` or `done/` is not the plan's to name.
- `raftplan.Issue` gains `tied: string?`, the raw value. `cmd["raft-plan"]` in `z-nile/engine/main.luau` passes `tied = front.tied` (reads stay at the edge, the parse is in the pure module).

### Behaviour 2: the tie, as connected groups
- Each id an issue's `tied:` names (other than its own) is an undirected edge between the two. A **tie** is a connected group of two or more ids over every issue passed in, in every state (backlog, active, done), and every id named even if no issue has it. So a tie declared on one member alone (the first prepared, or one not prepared yet) holds for all of them, and A–B plus C–B makes {A, B, C}.
- An issue in no tie is planned exactly as before (Regression guard).

### Behaviour 3: what the plan does with a tie
Whether a candidate can be planned is one predicate, `unplannable(i): (reason?, note?)` (review 001 F3): no `size:` (`no size: (z-design records its estimate of changed lines)`, note `no size:`), an unreadable `tied:` (the parse problem, note `tied: unreadable`) or an unknown type (`unknown type <t>`, the same note), in that order. The candidate loop skips with the reason, as it does today, and the tie's verdict counts such a candidate as a member still waiting, with the note. Whatever later reason the loop gains (c0161's `stale`, Behaviour 6) goes into this predicate, so the loop and the verdict can't disagree.
Each tie with at least one plannable candidate gets one verdict, computed once over its members sorted by id; the first cause found, in this order, makes every candidate of the tie a skip, `skip <id>: tied to <the other ids, sorted, ", ">: <cause>` (each pair of neighbouring causes is pinned by a case that has both, review 001 F5):
1. an id no issue has: `<id> is not in the tree`;
2. two types or two project roots: `<id> is a <type> of <root> and <first> a <type> of <root>: one raft holds one type of one project` (`<first>` is the tie's lowest id);
3. a `solo: true` member: `<id> is solo: true, a raft by itself: z-raft with arguments decides`;
4. a member outside the backlog with no `raft:` (done or active by a legacy path): `<id> is <state> with no raft: z-raft with arguments decides`;
5. members in two or more rafts: `its members are in <R1> and <R2>: z-raft with arguments decides (./zn recombine)`;
6. members in one raft R that is being rafted (in the backlog, `preparing`, not single: a fold or recombine not landed yet): `R, which holds some of them, is being rafted: raft-plan places them once that rafting lands` (review 001 F4: its way through is that rafting's merge and another `raft-plan`, not z-raft with arguments);
7. members in one raft R that is not open (not in the tree, not in the backlog, not `prepared`, or `single`): `R, which holds some of them, is not in the tree` or `R, which holds some of them, is <state>, <status>` or `… is single`, then `: z-raft with arguments decides` (except the not-in-the-tree form);
8. members still waiting (raftless backlog members that are not candidates, or candidates the predicate refuses): `<id> (<status>, design <design>)` or `<id> (<note>)`, joined with ", ", then `not prepared yet: raft-plan rafts them together when every one is (retry a dispatched member once that rafting has merged)`.
Otherwise the verdict is one op over all the tie's candidates, sorted: `fold R` when one open raft R holds the other members, else `new` (not `single`). The cap is not applied: the user's decision groups them, as R0100 (3,300 lines) does today. A tied issue over the cap goes with its tie, not alone. Features are grouped whatever their surface.
A candidate the predicate refuses keeps its own skip line (as today), and its tie waits for it (cause 8).
The causes 6 to 8 are the ones the order matters for in practice: a tie whose raft is readied while a member is still `new` names the raft (7), not the wait (8), because the wait would never end.

### Behaviour 4: a raft that holds a tied issue is the tie's
An open raft with any member in a tie is no fold target for untied issues (defects and chores skip it when they look for the lowest raft that fits; features don't count it as a surface). It prints no skip line for that: it is simply not a candidate bin. Its own tie folds into it by Behaviour 3.

### Behaviour 5: arguments still do what was asked
`./zn new raft <type> <slug> <ids…>` and `./zn fold <R-id> <ids…>` do not read `tied:`: `z-raft c0030` rafts a tied issue alone when asked (pinned by `plan-cli :: with arguments…`).

### Restated rules
The rule "an over-cap issue is a raft by itself" is restated in z-raft §1, z-design Size and solo and raftplan's header: all three gain the tie exception (the header's bullet stays and the c0286 bullet follows it). zz-rules' "gives `single: true` only to a raft of one `solo` or over-cap issue" stays true (a tie's raft is not single). zz-rules' raft-plan row gains the skip for an unreadable `tied:` on any backlog issue.
The way through a dispatched stop (review 001 F4, lesson z-design/dispatched-refusals-name-their-way-through), written in z-raft §1 and the cause-8 skip text: the dispatcher's stop after a `raft-plan` step that placed nothing (`raft-plan put <id> in no raft (see its skip line)`, `dispatch.luau`) points at the skip line, which `scriptStep` forwards. Each tied member prepared before the last stops there. The last member's own chain (prepared, raftless: `dispatch.next` gives it the `raft-plan` step) rafts the whole tie and carries it through z-raft and the raft gate. A stopped member is retried only after that rafting PR has merged: on `origin/main` it is then in the raft, and its chain follows the raft. A retry while that PR is open would see every member still raftless on `origin/main` (`new raft` publishes the raft with no member) and plan the same tie again, a second raft and a second rafting PR that the gate refuses once the first merges. If the last member was prepared outside the dispatcher, one `raft-plan` (or one retry) rafts the tie, not one per member.

### Scalability
The ties are one union-find over the issue ids (about 400 today, every state) plus one verdict per tie, each over its own members: linear in the tree, and `raft-plan` already reads every document. The verdict is cached per group, so a tie of n candidates costs one pass, not n.

### Maintainability
One reader (`parseTied`), one place for the rule (`raftplan.plan`), one predicate for what a candidate needs (`unplannable`, shared by the candidate loop and the verdict), the cause order written once as the verdict's sequence of returns, each with its own spec case and each neighbouring pair with a combined one. `main.luau` adds one field. No new module or dependency edge, so `z-nile`'s architecture map is unchanged.

### Usability
The person running `raft-plan` (or reading a dispatch's output) sees, per skipped issue, which members it is tied to and exactly why it waits (each waiting member with its status and design, or the raft or member that breaks the tie and that z-raft with arguments decides). A designer writes one line in front matter; the z-design skill says when and what.
