# c0291: Lesson notes merge without conflict

## Problem
Lesson files conflict on almost every prep merge: preps append an '**Also:**' or 'Note (...)' paragraph at the end of the same lesson (z-nile/skills/*/lessons/*.md), so merging origin/main into a prep branch stops with a content conflict that is always resolved by keeping both paragraphs. On 2026-11-09 it stopped the merge gates of #257 (restated-rules-move-together.md, spec-design-correspondence.md) and #265 (spec-design-correspondence.md), each costing a hand resolution and a new 25-minute full gate. What should happen: two branches that each append notes to one lesson merge cleanly with both notes kept (for example a union merge for lesson files, or one note file per source), the merge never loses or reorders a note, './zn lessons --check' still validates the result, and a real edit to a lesson's rule or check still conflicts.

## Non-goals
- **Moving the notes already in lesson files.** The `**Also:**`, `Note (...)` and dated paragraphs that earlier preps appended to 42 lessons (`grep -rlE '^\*\*Also:\*\*|^Note \(|^\*\*Note\*\* \(' z-nile/skills/*/lessons */skills/*/lessons | sort -u | wc -l`) stay in their files: moving them would edit the end of those files in this raft, which is exactly the hunk every in-flight prep that appended a note also edits (a new conflict for each), and a moved paragraph is a chance to lose one. Only new notes take the new form (Existing work).
- **Refusing a paragraph appended to a lesson's file.** `./zn lessons --check` cannot tell a stray note from a real rule edit that ends with a new sentence (both are text added at the end of `<slug>.md`), so it does not try; refusing it would refuse legitimate edits. A stray append costs what it costs today: a conflict only when another branch appends to the same lesson. The rule is stated where the format is (zz-rules, Items) and pinned (AC4). This narrows nothing the capture asked for: the capture's outcome is that *notes* merge cleanly, and it names "one note file per source" as a way to get there.
- **Merge drivers, union attributes and `git` configuration.** None is added (see Solution, rejected options). No `.gitattributes` exists today, and AC2 fails if one makes lesson files merge by union.
- **c0263's union resolver** for its record file inside the engine's merge helper (`mergeOrigin`): a different file and a different mechanism; this issue does not touch any merge helper.
- **The body caps, codify pointers and `lesson-merge` of c0181**: Existing work says what c0181 must do with a notes folder; this issue writes none of it.

## Solution
A note added to an existing lesson becomes a file of its own beside the lesson, `<skills folder>/<skill>/lessons/<slug>/<YYYY-MM-DD>-<label>.md`, instead of a paragraph appended to `<slug>.md` (the capture's "one note file per source"). Two branches that each add a note add two different paths, so `git merge`, `git merge-tree` (the dispatcher's backstop) and GitHub's mergeability all see no conflict and keep both. The lessons reader (`z-nile/engine/lessons.luau`, the format's one reader) reads each lesson's notes folder, and every reader that shows or searches a lesson reads its file followed by its notes in name order (the date first, so oldest first): the order is a function of the file names, so no merge can reorder it. `./zn lessons --check` refuses a notes folder with no lesson, a file in it not named as a note, a folder inside it, and an empty note. The lesson's own file still holds its frontmatter (`title`, `when`, `tags`, `check`, `from`) and its rule, so two edits of a rule or `check` still meet on the same lines of one file and still conflict. `dispatch.isLesson` accepts a note path, so the dispatcher's prep gate lets a prep PR carry a note as it carries a lesson, and zz-rules (Items) states the format.

Rejected (each was weighed against the capture's four outcomes):
- *A union merge for lesson files* (`.gitattributes`: `lessons/*.md merge=union`). It needs no config, but it turns every conflict in a lesson into a silent concatenation, so two different edits of one `check:` line become two `check:` lines (which `--check` would catch as "check is repeated") and two edits of the rule paragraph become both paragraphs, silently (which nothing catches): the capture's "a real edit to a lesson's rule or check still conflicts" fails. GitHub's own mergeability check does not promise to honour merge attributes either, so the dispatcher's gate (`mergeable`, which is what stopped #257 and #265) could still refuse.
- *A custom merge driver* (`merge=zn-lesson`, a script that keeps both sides' appended tails and falls back to a normal merge otherwise). It keeps real edits conflicting, but a driver is named in git configuration, which this repository never changes (AGENTS.md: the runner's tripwire fails a run when config changes; agents never repair the shared git configuration), so it would have to be injected (`GIT_CONFIG_*` environment) into every engine merge (`mergeOrigin`, `raftingStart`, `land`, `done`, `sync`) and the dispatcher's `merge-tree`; a hand `git merge` and GitHub's merge never run it. The PR on GitHub would stay unmergeable, which is the failure the capture names.
- *An engine-side resolver after a failed merge* (read the three stages of each conflicted lesson, keep both tails): the same gap at GitHub and at a hand merge, and it overlaps c0263's change to `mergeOrigin`.

Note files are the only option that works for every merger with no configuration.

## Design
No game behaviour changes; nothing under `pickman/src/` or any game's `tests/` is touched, and `pickman/.tracker/game-design.md` is not relied on. z-nile has no `architecture.md`; no module gains a `require` (`lessons.luau` keeps `projects`, `skills`, `stats`; `dispatch.luau` and `main.luau` keep theirs).

### The format (zz-rules, Items)
- A lesson is `<skills folder>/<skill>/lessons/<slug>.md`, as today.
- Its **notes folder** is `<skills folder>/<skill>/lessons/<slug>/`, a folder beside the file with the slug as its name. Each note is one file in it, named `<YYYY-MM-DD>-<label>.md`: the day the note is written (a real date: month 1 to 12, day 1 to 31, through `lessons.day`, the existing date reader) and a label in lowercase kebab (`kebab`, the existing slug rule: `[a-z0-9-]`, no leading, trailing or doubled dash). The convention is to name the note's source (`c0291-design-review-001-f2`, `r0068-review-002-f3`, `c0291-note-user-correction`), so two branches writing notes from two sources never pick the same name. Nothing parses the label: it is a name, not a reference, so a stale id in a note's name (after `./zn renumber` or `./zn compact`, which rewrite ids only in `.md` and `.sh` files under a project root, `compact.luau` `rewritesIds`, so never in a lesson or a note) is harmless.
- A note's text is free Markdown: the paragraph a prep would have appended. It names its source in its text, as appended notes do today. It has no frontmatter.
- Hidden entries in a notes folder (`.DS_Store`, editor swap files) are skipped, as in `lessons/` itself.
- Two notes of one name with different texts are an add/add conflict in git (E1 c, and pinned in `notes-merge.spec`), so a note is never overwritten silently; the same name and the same text merge cleanly (pinned too). No merge attribute may touch lessons or notes (rows M18, M21).

### `z-nile/engine/lessons.luau` (pure over texts; `load` still the only reader)
```luau
-- a note to a lesson (c0291): one file `<lesson's slug>/<YYYY-MM-DD>-<label>.md` beside the lesson
export type Note = { name: string, text: string }
export type Tree = {
	lessons: { [string]: string },          -- unchanged: lesson id -> the text of `<slug>.md`, exactly as read
	notes: { [string]: { Note } }?,         -- new: lesson id ("<skill>/<folder name>") -> the files of that notes folder,
	                                        -- as read; optional, so a hand-built tree (specs) without it still type-checks
	... -- every other field unchanged
}
function lessons.noteName(name: string): (string?, string?)   -- date, label; nil, nil when not a note name
function lessons.compose(text: string, notes: { Note }): string
function lessons.text(tree: Tree, id: string): string?          -- compose(tree.lessons[id], tree.notes[id] or {}), nil for no lesson
```
- **`noteName`** matches `^(%d%d%d%d%-%d%d%-%d%d)%-(.+)%.md$`, then requires `lessons.day(date)` and `kebab(label)`.
- **`compose`** with no notes returns `text` byte for byte (so every reader's output for a lesson without notes is exactly today's: `lessons-cli.spec`'s exact `--full` case pins it). With notes, it returns `text`, a `\n` if `text` does not end in one, then for each note **in ascending byte order of `name`** (the date first, then the label): `\n`, the note's text, and a `\n` if the note does not end in one. So each note starts after exactly one blank line, whatever order the folder was read in.
- **`text`** is what every reader that **shows, searches or measures** a lesson uses. `tree.lessons[id]` stays the file's own text, which a **writer** of `<slug>.md` uses (none exists in `main` today; c0181's `lesson-merge` will be one, Existing work), so composing never writes notes back into the file.
- **`load`**: in each skill's `lessons/` folder, an entry that is a folder (not hidden) is a notes folder: its files, sorted, become `tree.notes["<skill>/<folder name>"]` (`{ name, text }` each, read whole); a hidden entry in it is skipped; a non-file entry in it (a folder) is a load problem `<skill folder>/lessons/<folder>/<entry>: not a note file`. Today such a folder is the problem `…/lessons/<folder>: not a lesson file`; that wording stays for every other non-lesson entry (a `.txt`, `lessons-hidden.spec`). `load` judges no names and drops nothing: every non-hidden file of a notes folder, misnamed or empty, reaches `check`, which names it (design review 001 F4).
- **`check`** gains, before the harvest loop, for each `id, list` in `tree.notes or {}` (bound to a typed local first, `local notesOf: { [string]: { Note } } = tree.notes or {}`: strict Luau refuses to iterate the union `tree.notes or {}` directly, E2) (the folder is `lessons.folderOf(tree, skill)/lessons/<slug>`):
  - no `tree.lessons[id]`: `<folder>/lessons/<slug>/: notes with no lesson <slug>.md` (a notes folder whose lesson was deleted or renamed, or a folder named by mistake);
  - each note whose `noteName` is nil: `<folder>/lessons/<slug>/<name>: not a note file (a note is <YYYY-MM-DD>-<label>.md)`;
  - each well-named note whose trimmed text is empty: `<folder>/lessons/<slug>/<name>: the note is empty`.
  These join the sorted, de-duplicated problem list like every other. The lesson's own parse, skill and source checks are unchanged and **still run on the file's own text (`tree.lessons[id]`), never on `lessons.text`**: a lesson whose rule was deleted but which has a note is still "the body is empty" (design review 001 F5).
- **`select`, `index`, `sources`, `tagCounts`** are unchanged: `select` searches `Lesson.body`, which carries the notes once the lesson is parsed from `lessons.text` (below).

### `z-nile/engine/main.luau` (`cmd.lessons`, two lines)
- `parsedLessons` parses `lessonsLib.text(tree, id)` instead of `tree.lessons[id]`, so a word that only a note holds finds its lesson (listing, `--full`, `--when`, `--tag`), and a parsed lesson's `body` is its file's body followed by its notes.
- `--full` writes `lessonsLib.text(tree, l.id)` instead of `tree.lessons[l.id]`. The `== <path>` and `sources:` lines are unchanged.
- `--check`'s success line (`lessons: N lessons, M harvest entries, ok`) is unchanged (it counts lessons and entries, not notes). `metrics` (line 6690) reads `tags` only and keeps reading the file text.

### `z-nile/engine/dispatch.luau`
`dispatch.isLesson(path)` is true for exactly two shapes, and nothing deeper:
- a lesson file, `^[^/]+/skills/[^/]+/lessons/[a-z0-9][a-z0-9%-]*%.md$` (today's `[^/]+%.md` narrowed to a slug's shape: every lesson on `main` is kebab, since `parse` refuses others, and the narrowing shuts out `lessons/CLAUDE.md`, an instruction file Claude Code would load);
- a note, `^[^/]+/skills/[^/]+/lessons/[a-z0-9][a-z0-9%-]*/%d%d%d%d%-%d%d%-%d%d%-[a-z0-9][a-z0-9%-]*%.md$`, the shape of `lessons.noteName` (the date's range and the label's dash rules stay `check`'s), written as a pattern so `dispatch.luau` gains no `require`.

It is the prep gate's allowance (`dispatcher.judgePr`: a prep PR may carry its issue's folder and skill lessons), so a dispatched prep that writes a well-shaped note is not refused, and one that writes `lessons/<slug>/also.md`, `lessons/<slug>/CLAUDE.md` or `lessons/Upper/…` is refused at its gate with the existing message ("outside the issue's own folder and the skill lessons"). Nothing between a prep PR and `main` runs `lessons --check`, so the gate's shape is what keeps a misnamed note off `main` (design review 001 F2).

### `z-nile/skills/zz-rules/SKILL.md` (Items), one new bullet after **Lessons**
> - **Lesson notes**: a note added to an existing lesson (a new source's detail, a sharper example) is a file of its own, `<skills folder>/<skill>/lessons/<slug>/<YYYY-MM-DD>-<label>.md` (the day it is written, and a lowercase kebab label naming its source, such as `c0291-design-review-001-f2`), never a paragraph added to the end of `<slug>.md`. Two branches that add notes to one lesson add different files, so they merge without a conflict and keep both. `./zn lessons` reads a lesson's notes after its file, in name order (oldest first), and searches them (`--full` prints them after the file, under the file's path: the note files are the record, so never copy that text back into `<slug>.md`); `--check` refuses a notes folder with no lesson, a file in it not named that way, and an empty note. An edit to the lesson's rule, `check` or other frontmatter is still an edit of `<slug>.md`, and two such edits still conflict. The paragraphs that older notes added to a lesson's file stay where they are.

### The shared `## Lessons` paragraph, in all 25 skills (design review 001 F1)
The lead bullet of the paragraph every skill ends with closes today with "It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work." Read under the new rule, "writes a new file only when none does" says the opposite of it, at the moment a lead writes a note. In every skill that has the paragraph (the 25 `SKILL.md` files under Touched modules: 13 in `z-nile/skills/`, 12 in the projects' `skills/`; never the copies under `z-nile/.tracker/issues/done/c0184/experiments/`, which are a finished item's record) that sentence becomes, identically:

The rest of the paragraph is unchanged, so `c0111/skill-docs.spec` (the paragraph identical in every skill, its pinned substrings) still holds; `notes-docs.spec` walks every skill through `skills.folders(projects.load(TOP))` and requires the new sentence in every `## Lessons` section that has the lead bullet, and the old one in none. z-design step 5.3 ("A finding that repeats a lesson sharpens that lesson's `check`") is an edit of the lesson's file and stays true; AGENTS.md ("Each skill keeps what reviews and mistakes taught it in its `lessons/` folder") stays true.

### Data flow
`./zn lessons …` → `lessons.load(".")` (reads `<slug>.md` files and notes folders) → `lessons.check(tree)` for `--check`, or `parsedLessons` → `lessons.parse(id, lessons.text(tree, id))` → `select` → `index` or `--full` (`lessons.text`). Merges: no engine code runs; the layout makes them clean.

### Server authority
Not applicable (tooling; no game code).

### Scalability
`load` adds one `readDir` per notes folder and one `readFile` per note; today there are 405 lessons and no notes folders, and a busy lesson gains one note per prep that touches it . `compose` sorts each lesson's notes (n log n in its own notes) and concatenates once per lesson read; `check` is linear in notes. No new git calls or processes. The dispatcher's `isLesson` adds one `string.match` per path.

### Maintainability
The format has one reader (`lessons.load`) and one composer (`lessons.text`); a new reader of lessons (c0166's selector, c0181's caps, a prompt that inlines lessons) calls `lessons.text` for the whole lesson and `tree.lessons[id]` only to rewrite the file. A new lesson kind or project plugs in exactly where lessons do (`skills.folders`). The path rule for "is this a lesson file" is `dispatch.isLesson`, and the one spec that had its own copy now calls it.

### Usability
No new command or option: a lead writes a note with any editor at a path the zz-rules bullet spells out, and `./zn lessons --check` (which every harvest step already runs) names the folder or file and the rule for each mistake (`notes with no lesson <slug>.md`, `not a note file (a note is <YYYY-MM-DD>-<label>.md)`, `the note is empty`, `<entry>: not a note file`). `./zn lessons --full <id>` shows the lesson as one text, its notes in order. Exhaustive lists a new file kind must join (zz-rules/exhaustive-lists-name-new-things): the prep gate's allowance (`dispatch.isLesson`, changed to the note's shape), the c0115 old-id scan (changed), the affected selector (a note path selects nothing, as a lesson path does: probed, `lune run z-nile/affected -- z-nile/skills/z-design/lessons/one-file-two-write-channels/2026-11-15-c0291-design-review-001-f1.md` prints nothing), `skills.lessonIndex` (counts `*.md` names only, so a notes folder is not a lesson id: read), the watch tools (`watch.luau`, `watchcmd.luau` skip every path under `/lessons/`: read), `engine.clearLessons` in the spec fixtures (removes a whole `lessons/` folder, notes included: read).
