# c0293: AGENTS.md covers only engaging the pipeline

## Problem
The user (2026-11-10): "Clean up AGENTS.md, it shoudl only talk about how the skills ticket, design, raft, ready, run are engaged. The parts about pickman moves into pickman/AGENTS.md"

Every agent session loads the root `AGENTS.md` first (through `CLAUDE.md`'s `@AGENTS.md`). Its 36 lines mix how the pipeline is engaged with pickman's description (the game, its folder, its home, its `game-design.md`), the arcade's five projects and their skill rows, a row for every `zz-` skill, the lessons paragraph and three repo-wide rules. An agent reads past the games to find how to start work, and each game's parts load in sessions that never touch it.

What should happen:
- The root `AGENTS.md` talks only about how the `z-ticket`, `z-design`, `z-raft`, `z-ready` and `z-run` skills are engaged.
- pickman's parts move into `pickman/AGENTS.md`.

Decided with the user (2026-11-10): "Keep in root AGENTS.md". The three repo-wide rules that are neither the pipeline nor pickman's (**Subagents**, **Processes** and **No check may ever change the real repository**) stay in the root `AGENTS.md`, as a short block after the pipeline part.

Decided with the user (2026-11-10): "Each its own AGENTS.md". The other five projects' parts move the way pickman's do: `arcade/`, `portal/`, `snake/`, `invaders/` and `asteroids/` each get an `AGENTS.md` with their own description and their `<name>-arch` and `<name>-test` rows, the same shape as pickman's, and each project folder (pickman's too) gets a `CLAUDE.md` of `@AGENTS.md`, so Claude Code loads it when it works in that folder.

## Non-goals
- Changing what any rule says: the text moves or goes, and a kept rule means what it meant.
- The README's intent work (c0264, c0268, R0090, R0092).
- Editing the skills, beyond a line that pointed at text this issue moves.

## Solution
- The root `AGENTS.md`: the non-negotiables that decide how work enters the pipeline (no code without an issue, every change in a worktree, landing by pull request), then each stage and how it is engaged: `/z-ticket` to capture, `/z-design <id>`, `/z-raft`, `/z-ready <R-id>`, `/z-run <R-id>` from a session in the main checkout, `/z-stop` to give a raft back, or the whole chain headless with `./zn dispatch <id>` (`.models.toml`). Then the kept block: Subagents, Processes, No check may ever change the real repository.
- What is neither a stage nor a project's (the `zz-` skill rows, the lessons paragraph, the project-home sentence of c0184, the `SETUP.md` and `z-nile/README.md` pointers) goes by the user's "only", unless the design shows it is part of engaging a stage; the step skills already name the `zz-` skills they call and read their own lessons. A drop the design is unsure of goes to the user.
- `pickman/AGENTS.md`: the game's sentence, its home, its `game-design.md` and `architecture.md`, and the `pickman-arch` and `pickman-test` rows; `pickman/CLAUDE.md` is `@AGENTS.md`, mirroring the root (Claude Code reads a folder's `CLAUDE.md`, not its `AGENTS.md`). The five other homes the same.
- Overrides to expect (a chore changes them in its own raft): the promoted specs that read `AGENTS.md`, under `z-nile/tests/acceptance/` in `c0111`, `c0114`, `c0115`, `c0116`, `c0117`, `c0120`, `c0165`, `c0183`, `c0184`, `c0191` and `c0239` (some only use the name in a fixture), and the `AGENTS.md` rows of `z-nile/tests/inputs.tsv`.
- Open items whose sequestered specs read `AGENTS.md`: active `c0136` and `c0194`; backlog `c0075`, `c0083`, `c0112`, `c0141`, `c0181`, `c0189`, `c0192` and `c0261`. Each either reads the new file or this issue waits for it (`depends_on`).
