# c0294: Lesson moved part rewrites owner

## Problem
z-ticket: when an interview answer moves a part to another ticket, or adds a depends_on edge into a ticket that already owns that part, rewrite that ticket's text in the same capture and check its captured outcomes can still be built in the new order, because the 2026-11-11 worker idea interview gave c0257's rankCommand wiring to c0249 with an edge c0249 -> c0257, which left c0257's captured 'orders by the order c0249 defines' with no owner able to build it (idea review 001 F5); check: for each answer that moves a part or adds an edge, does the other ticket name the new owner, and can each of its outcomes still be built?

## Non-goals
- **Codifying the rule** (c0181). c0181 (prepared, solo, R0074) owns the lesson states (`enforced_by`, `not_codifiable`) and the sweep over every lesson on `main`; Decisions 5 says what the executor does if c0181 lands first. No lint, hook or engine change is made here.
- **Changing z-ticket's steps.** c0260 (prepared) owns z-ticket's interview steps (0a, 0b, 2a, 4a, 4b); this issue adds no step text, so it neither waits for c0260 nor conflicts with it (the lesson fits the interview as recorded today and as c0260 builds it).
- **Repairing c0257, c0249 or c0276.** c0257 and c0249 were fixed by the 2026-11-11 capture itself (c0257's decision and Owners lines); c0276's Non-goal was reported to the user then. This issue edits no item but its own.

## Solution
One new, short lesson, `z-ticket/moved-part-rewrites-the-owner`, `when: both`, whose `check` keeps the captured question word for word and adds one clause (a ticket the capture cannot edit is named to the user); and the harvest note in c0294's own `harvest.md` that makes the 2026-11-11 incident its source.

## Design
The captured outcome is the lesson: its rule (an answer that moves a part, or adds an edge into the ticket that owns it, rewrites that ticket in the same capture, and its outcomes are walked in the new order), its incident and its check question. Nothing else restates the rule (Chore checklist, Restated rules).

### Decisions
1. **A new lesson, not a note on an old one** (zz-rules, Items: "adds a note to an existing lesson when one fits"). The two nearest are `z-ticket/split-designs-name-each-owner`, whose check asks whether the ticket that *receives* a handed part can do it (its dependencies put what it needs before it), and `z-ticket/carry-the-plan-order-into-depends-on`, which asks whether a plan's order sentences become `depends_on` lines. Neither asks about the ticket that *loses* the part or that an edge now points into, and that is where the 2026-11-11 gap was: c0249 could build what it took; c0257's remaining outcome could not be built by c0257, which now had to land first. The captured check question is its own, and a note cannot carry a `check`.
2. **Under z-ticket, `when: both`.** The Problem opens "z-ticket:". Captures happen in the design pass (z-ticket, z-design's new captures) and in the build pass (an emergent issue a raft captures, `./zn lessons --when build`), as for the sibling `split-designs-name-each-owner` (`both`). c0136 (active, R0068) requires a lesson whose step is a design step (`z-ticket`) to be `design` or `both`, never `build`: `both` meets it.
3. **The check keeps the captured question word for word** (its first letter capitalised, as every lesson's check is) and adds one sentence, "And is each ticket this capture cannot edit named to the user?". That is detail of the captured "rewrite that ticket's text in the same capture": a capture cannot rewrite a ticket past `design: draft` (land lets a capture edit only an issue document that is `design: draft` on both sides with an unchanged status line, `z-nile/engine/main.luau` `captureScope`), nor one whose current text lives on its prep branch, where main's copy is superseded by the prep's next merge. The 2026-11-11 capture met the second case: c0276 was `design: draft` on main, but the Non-goal naming c0257 existed only on its prep branch (draft PR #281), and was reported to the user. The how-to names both cases (review 001 F5). Nothing captured is narrowed.
4. **The how-to quotes the answer and separates what the user picked from what the capturer settled.** c0249's idea review round 2, F26 (high) found the first fix of F5 crediting the user's Q3 with words the option did not say; the landed fix was a decision line quoting Q3's option and a separate `Owners` line. The lesson's how-to asks for the same two lines, so the fix of this mistake does not repeat F26 (lesson `z-design/agents-quote-the-users-words` is the general rule). The Why follows the landed record (0e91b4d7), not round 1's fix: it quotes c0257's captured outcome word for word ("orders tickets and rafts by the order c0249 defines", c0257 at 0e91b4d7^; c0294's capture paraphrases it as "orders by the order c0249 defines") and gives each part its final owner (c0249 the rank order and the wiring, c0290 lost work first), and AC4 reads the quote from the lesson and finds it in that commit (review 001 F1; lesson z-design/lesson-facts-come-from-the-record).
5. **c0181 first.** If `z-nile/engine/lessons.luau` names `not_codifiable` when the executor starts, or after any merge of origin/main into the raft before `done` (c0181 landed), the lesson is written from `experiments/ref-lesson-c0181-first.md.txt` (the same text plus `not_codifiable: whether an outcome can still be built in the new order is a reading of what each outcome needs; no text marks which outcome a moved part served`), and the executor appends `- codify z-ticket/moved-part-rewrites-the-owner: not codifiable: <the same reason>` to `harvest.md` and runs `./zn lessons --check --policy --item c0294`; if that names a hard overlap pair with this lesson, the executor adds the `distinct_from:` line c0181's message asks for (Decisions 1 is the reason), which AC1's line cap does not count. The branch is not expected to fire: review 001 computed c0181's `similar()` score of this lesson against every z-ticket lesson at 0.22 (`split-designs-name-each-owner`, `capture-subject-lists-every-id`), 0.21 (`idea-settles-what-it-builds-on`), 0.20 (`carry-the-plan-order-into-depends-on`) and 0.09 (`search-the-backlog-before-capturing`), under c0181's hard threshold of 0.35 (its G1 lets the user move it). Today's `--check` refuses the key (E3a), so the branch is AC6's and only runs after c0181.
