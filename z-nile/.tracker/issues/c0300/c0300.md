# c0300: Restack drops unfinished layer commits

## Problem
- `./zn restack <R-id>` on a raft whose current layer is unfinished (several work commits on top of its `tracker: start` commit) rebases only the layer's last commit onto the new main and drops the others.
- A restack whose rebuilt layer fails its check can leave the layer branch and its remote pointing at that truncated commit (seen in R0093 on 2026-11-12, branch `R0093/1/c0256`).
- `./zn finish <issue>` on a layer that is only behind main refuses with "is not based on the layer below: ./zn restack <R-id>", so the documented way on leads straight into the truncating restack.

Note (c0248's prep, 2026-11-13): c0248 (prepared) adds one exception to restack's conflicts: a conflict in the raft's derived `spend.md` alone (rewritten both by a landing's bind and by a later layer's review commit) is resolved by taking `main`'s copy, which the next `./zn commit` regenerates; any other conflict still stops. The Non-goal "Restack does not resolve rebase conflicts itself" leaves that exception in place.

## Non-goals
- Restack does not become all-or-nothing across the stack: it still stops at the first conflict, and layers it already rebased and pushed before the failure stay moved.
- Restack does not promise that a layer's branch and its remote are both back at their starting commits after a hard kill between the push and the local update.
- Restack does not resolve rebase conflicts itself.

## Solution
- After a successful restack of an unfinished layer, the layer holds one commit for each commit it held before, with the same subject and the same change, in the same order, on top of the new main.
- A restack that cannot do this for a layer refuses that layer without changing its branch or its remote, and says what to do instead.
- After a restack fails or is interrupted, neither the layer branch nor its remote points at a commit set missing a commit the layer held before.
- When `finish` refuses a layer that is only behind main, following the command it names moves the layer onto the new main with no hand rebase, and `finish` then succeeds.

## Design

### Cause (read from the code on `origin/main` 7241e890)
- `stack.rebaseUpstream` (z-nile/engine/stack.luau) first tests the tip: when the tip's subject starts with `<issue>: ` and the tip's parent is not in the lower layer, it returns the tip's parent, meaning "this tip is the finish commit, rebase only it". Workers title their commits `<issue>: …` (R0093's layer `R0093/1/c0256` held `c0256: Dispatch retry passes answer`, then `c0256: review 001 F1, F2, F5: …`, `c0256: review 001 F1: …`, `c0256: verification log: …`), so on an unfinished layer, or a finished one with commits after its finish, the test fires on the last worker commit and `git rebase --onto <onto> <tip^> <layer>` rebuilds only that commit.
- `cmd.restack` (z-nile/engine/main.luau) rebases on the layer branch itself: `checkoutLayer`, `reset --hard <tip>` (with `tip` = origin's copy when there is one, so an unpushed local commit is dropped right there), then the rebase moves the branch. The branch sits on the rebuilt (truncated) commit while `check.sh` runs; a red check puts it back, but a check that is killed or a session that ends leaves it there, and the next push from that branch publishes it. E2 reproduces this: on today's code a restack killed during its check leaves `R0010/1/c0010` holding only `c0010: three`.
- `git rebase` without flags also drops, silently, a commit whose patch is already upstream (E1: "dropping … -- patch contents already upstream"), so even a correct upstream can lose a commit.
- `cmd.finish` on a layer only behind main refuses with `<branch> is not based on the layer below: ./zn restack <R>` (main.luau `cmd.finish`), which leads into the above. The refusal is right; the command it names is what is fixed. `finish` itself does not change.

### The change
One pure module gains the rules, `main.luau`'s `cmd.restack` gains the order of operations, and `stack.rebaseUpstream` loses the tip test.

**`stack.rebaseUpstream(issue: string, raftId: string, rows: { CommitRow }): string?`** (z-nile/engine/stack.luau; the `tipSubject`, `tipParent` and `parentInLower` parameters go). `rows` are the commits of `merge-base(tip, onto)..tip`, oldest first. It returns the parent of the first row whose subject starts with `tracker: start <raftId>` or with `<issue>: `, else nil (the caller then uses the merge-base). The layer's first own commit is always one of those: an unfinished layer starts with its `tracker: start` commit (`cmd.start`), a finished one with its finish commit (`cmd.finish` squashes everything above the base into it), and a lower layer's commits carry the lower issue's id and no `tracker: start` (a layer opens only on a finished lower layer, `layergit.startLayer`). The case the tip test was for (a finished layer above a rewritten lower layer) is the same first-row rule: the old lower commits come first in `rows` and do not match. **`layercommits` is required inside `cmd.restack`**, not at the top of `main.luau`: the file has 199 top-level `local` lines on 7241e890, and a 200th (the prototype's first try) sits at Luau's limit of 200, so the next change to add one would fail to compile.

**New pure module `z-nile/engine/layercommits.luau`** (texts in, texts out; no requires):
- `export type Commit = { subject: string, change: string }`
- `export type Copies = { localSha: string?, remoteSha: string?, remoteInLocal: boolean, localInRemote: boolean, sameCommits: boolean, localStacked: boolean, remoteStacked: boolean }`: the two copies of one layer branch as git answered for them. `sameCommits`: each copy's own commits (from its own `rebaseUpstream`, compared by `keepsCommits`) are one list. `localStacked`/`remoteStacked`: the base the layer goes onto is an ancestor of that copy.
- `layercommits.pickTip(c: Copies): (string?, string?)`: the copy of the layer that holds every commit. Both absent → `nil, "it has no tip"`. Equal, or only one present → that one. Origin's copy an ancestor of the local branch (unpushed local commits) → local. Local an ancestor of origin's (a stale clone) → origin. Neither an ancestor of the other: a rebuilt copy is never an ancestor or a descendant of the copy it replaces, so with `sameCommits` they are one layer on two bases (a restack killed between moving the branch and pushing it; a clone holding the old copy after another clone restacked and pushed): origin's copy when only it is on the base, else the local one. Without `sameCommits` → `nil, "the local branch and its origin copy have diverged"` (a rebase of either copy would drop the other's commits).
- `layercommits.changeKey(patch: string, raftId: string): string`: a commit's change as a text a clean rebase leaves alone. `patch` is `git diff-tree -p -U0 --binary --full-index --no-renames --no-commit-id -r <sha>`. Each file's section keeps its mode lines (`new file mode`, `deleted file mode`, `old mode`/`new mode`), its changed lines and its binary patch; its header loses the paths and blob ids (`diff --git`, `index`, `---`, `+++`), since a rename on the new base moves the path (a clean rebase by merge-ort follows it; review 001 F2) and a moved base changes the blobs; every hunk header (`@@ …`) is cut to `@@` (line numbers and the function context move). Only the header loses those lines: a removed Luau comment reads `--- …` in a -U0 patch and stays a change. The sections are sorted (a rename can reorder them) and joined. A file section whose `diff --git` line ends in `/<raftId>/spend.md` is left out (the raft's derived spend ledger, which c0248's restack takes from main on a conflict and the next `./zn commit` regenerates). With `-U0` no context line is in the key, so a change elsewhere in the same file (E1: line 7 changed on main, the commit changes line 10) keeps it. `--binary --full-index` makes a binary change part of the key (a binary file that rebased cleanly has the same old and new blobs, so the same literal or delta). Without paths the key cannot tell a change from the same change in another file; a clean rebase moves a change to another file only through a rename, which is the case it must accept.
- `layercommits.keepsCommits(before: { Commit }, after: { Commit }): string?`: nil when `after` holds one commit for each commit of `before`, position by position with the same subject and change; otherwise what differs, naming the commit: `"<subject>" is missing after the rebase`, `commit <i> was "<a>" and is "<b>" after the rebase`, `"<subject>" is empty on the new base (its change is already there)`, `"<subject>" changes something else after the rebase`, or `the rebase made <n> commits from <m>`.

**`cmd.restack`, per layer** (z-nile/engine/main.luau; the loop's shape, the fetch, the old-shape refusal, `alreadyStacked` and the `owns` check stay):
1. `localSha` = `refs/heads/<layer>`, `remoteSha` = `refs/remotes/origin/<layer>`. When both exist, differ and neither is an ancestor of the other, restack reads each copy's own commits (steps 3's reading, for each copy against `onto`) and sets `sameCommits`. `tip` = `layercommits.pickTip(...)`. No tip → switch back, refuse: `restack stopped at <layer>: <why>; nothing was changed. Bring them together (git switch <layer>; git pull --rebase origin <layer>; git push origin <layer>) and run ./zn restack <R> again`.
2. Already stacked on `onto`: when origin has the layer and its copy is not `tip` (the restack before was killed after moving the branch and before pushing, or the local branch is ahead), `tip` goes through steps 6-8 (the branch to `tip`, the check, the push), then `below = tip` and the next layer. Otherwise `below = tip` and the next layer (as today).
3. `upstream` = `stack.rebaseUpstream(issue, raft, rows)` or the merge-base; `held` = the `Commit` list of `upstream..tip` (subject from `git log -1 --format=%s`, change from `changeKey`).
4. `git switch --quiet --detach <tip>`, then `git rebase --quiet --reapply-cherry-picks --empty=keep --onto <onto> <upstream>`: the rebase runs on a detached HEAD, so the layer branch has not moved. `--reapply-cherry-picks --empty=keep` makes git keep every commit (a commit whose change is already on `onto` comes out empty instead of being dropped, E1), so the one judge of what was kept is step 5. A conflict → `git rebase --abort`, switch back, refuse as today (`restack stopped at <layer>: conflict`; c0248's `spend.md` resolution, when it lands, sits in this branch before the abort and continues the rebase on the same detached HEAD).
5. `layercommits.keepsCommits(held, <Commit list of onto..HEAD>)`; a difference → switch back (the branch was never moved), refuse: `restack stopped at <layer>: <what differs>; nothing was changed. Rewrite or drop that commit by hand (git rebase --onto <onto> <upstream> <layer>), push it with --force-with-lease, and run ./zn restack <R> again`.
6. `git switch --quiet -C <layer> <rebuilt>`: the branch moves only now, to a layer that keeps every commit. (Steps 6-8 are one local function, `moveLayer(layer, rebuilt, was, remoteSha)`; `publish` is taken by the module.)
7. `check.sh` (as today); red → `git reset --hard <localSha or tip>` (the branch back where it was), switch back, refuse as today.
8. Push with `--force-with-lease=refs/heads/<layer>:<remoteSha or tip>` (as today, with the lease on origin's own copy), `below = rebuilt`.
At every point a kill can land, the branch names `localSha` or the full rebuilt layer and origin names `remoteSha` or the full rebuilt layer: never a set missing a commit. A kill between steps 6 and 8 leaves the branch on the rebuilt layer and origin on the old one: neither is an ancestor of the other, both hold the same commits, so the next restack picks the local copy (step 1); if main moved again it rebuilds that copy, and if not, step 2 checks and pushes it. Either way the next restack finishes the layer with no hand repair (two fixture cases). A kill during step 4 leaves a rebase in progress on a detached HEAD; the branch is untouched, and the next restack's clean-tree check refuses until `git rebase --abort`.

**Restated rules** move with it, pinned by AC5: the usage line (`restack <R-id>  rebase each layer onto the one below, keeping every commit; stop at the first conflict, lost commit or red check`), the contract comment at the top of `stack.luau` (adds `Every one of them is kept, with its subject and change, or the layer is refused unchanged.`), and zz-rules' "One layer per ticket" bullet, which keeps its sentence `./zn restack <R-id>` rebases the layers above a change. and gains, right after it, `A restack keeps every commit of each layer, or refuses that layer and leaves it as it was.` (a sentence of its own, so c0248's edit of the same line, which keeps that sentence and adds after it, unions with this one). The README's "brings the stack onto a moved `main`" and zz-execute's restack steps stay true and do not change.

The exact code is `experiments/prototype.patch` (prototype 73ab3a7a on 7241e890; 251 lines added, 67 removed in code, docs and the tooling spec).

### Scalability
Per rebased layer, restack adds two `git rev-list` and, per commit of the layer, one `git log -1` and one `git diff-tree` before and after the rebase: 4 git calls per commit, about 40 for a ten-commit layer, each a few milliseconds. Copies that are neither an ancestor of the other (rare: a killed restack, a stale clone, real divergence) cost one more reading of each copy. Each `ancestor` question is one `git merge-base --is-ancestor` (four per layer). Layers already stacked cost what they do today, unless origin lacks their copy, which then pays one check and one push. A raft has a handful of layers. Patches are compared as strings in memory; a layer's own patches are small (kilobytes to a few megabytes).

### Maintainability
The rules (which copy, what a change is, what "kept" means) are one pure module with its own spec; `cmd.restack` only asks git and calls it. A future caller that rewrites a layer (c0248's landed-layer restack) reuses `keepsCommits` and `changeKey`. `main.luau` gains no top-level local (199 `local` lines before and after, measured on the prototype); the module is required inside `cmd.restack` with a comment saying why.

### Usability
Each refusal names the layer, says what differs (the commit's subject, and whether it came out empty or different), says `nothing was changed`, and gives the commands to go on (for diverged copies `git switch <layer>; git pull --rebase origin <layer>; git push origin <layer>`) and `./zn restack <R>` to rerun. A restack killed mid-check needs no repair: the next one finishes the layer. The usage text names the new stop reason ("lost commit"). `./zn finish`'s refusal is unchanged and now leads to a restack that works.
