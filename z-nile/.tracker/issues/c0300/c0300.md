# c0300: Restack drops unfinished layer commits

## Problem
- `./zn restack <R-id>` on a raft whose current layer is unfinished (several work commits on top of its `tracker: start` commit) rebases only the layer's last commit onto the new main and drops the others.
- A restack whose rebuilt layer fails its check can leave the layer branch and its remote pointing at that truncated commit (seen in R0093 on 2026-11-12, branch `R0093/1/c0256`).
- `./zn finish <issue>` on a layer that is only behind main refuses with "is not based on the layer below: ./zn restack <R-id>", so the documented way on leads straight into the truncating restack.

## Non-goals
- Restack does not become all-or-nothing across the stack: it still stops at the first conflict, and layers it already rebased and pushed before the failure stay moved.
- Restack does not promise that a layer's branch and its remote are both back at their starting commits after a hard kill between the push and the local update.
- Restack does not resolve rebase conflicts itself.

## Solution
- After a successful restack of an unfinished layer, the layer holds one commit for each commit it held before, with the same subject and the same change, in the same order, on top of the new main.
- A restack that cannot do this for a layer refuses that layer without changing its branch or its remote, and says what to do instead.
- After a restack fails or is interrupted, neither the layer branch nor its remote points at a commit set missing a commit the layer held before.
- When `finish` refuses a layer that is only behind main, following the command it names moves the layer onto the new main with no hand rebase, and `finish` then succeeds.
