### F1 [high] After a restack killed during its check, the next restack refuses the layer as "diverged", and following the refusal's advice puts main's commits into the layer and publishes them
Where: c0300.md Design, `cmd.restack` steps 1, 2, 6-8 and the paragraph "At every point a kill can land … the next restack sees local ahead of origin and pushes it"; `layercommits.pickTip`; restack-keeps.spec "AC3: a restack killed during its check …".
Evidence: Step 6 moves the branch to the rebuilt layer before the check, and step 8 pushes after it. So a kill during step 7 (the scenario Problem 2 names: "a check that is killed or a session that ends") leaves the branch on the rebuilt layer, on the new main, and origin on the old layer. A rebuilt commit is never a descendant of the commit it replaces. Probe (a): after `git rebase --reapply-cherry-picks --empty=keep --onto main <base>`, `merge-base --is-ancestor <old tip> <rebuilt>` is false, and the reverse is false too. So `pickTip(local, remote, false, false)` returns `nil, "the local branch and its origin copy have diverged"`. The next `./zn restack` stops with "Bring them together (git pull --rebase, then git push)". Probe (d) followed that advice from exactly this state (branch = rebuilt start/one/two on the moved main, origin = the old layer, upstream set as `cmd.start`'s `push -u` sets it). `git pull --rebase` left `origin/main..L` = `tracker: start R0010 x`, `c0010: one`, `c0010: two`, `main moves`, `tracker: start R0010 x`. Main's commit is now copied into the layer and the empty start commit appears twice. `git push` then publishes that. The restack after it holds `main moves` as a layer commit, so step 5 refuses it as a lost change. That is a dead end with a polluted origin. The design says the opposite ("the next restack sees local ahead of origin and pushes it"). The spec never checks: after the kill, the AC3 case puts the branch back by hand (`git switch -f`, `git reset --hard origin/<layer>`) before the next case. The same ancestry test also refuses a clone whose branch is the old copy after another clone restacked and pushed. Today's `layerTip` takes origin there, and it works.
Critique: The tempting fix is to say in the refusal "or `git reset --hard origin/<layer>`". That throws away a full rebuilt layer, plus any commit made after the kill, and still leaves the false sentence in the Design. The second tempting fix is to make pickTip prefer the local copy whenever neither is an ancestor. That brings back M4: a genuinely diverged origin commit (another terminal's `c0010: other`) would be rebuilt away.
Consequences: Telling "the same layer on two bases" apart from "two different layers" needs both copies' commit lists. So pickTip gains an input, and restack runs `commitsOf` for both copies, but only when neither copy is an ancestor of the other. A second gap remains. If main does not move again, the rebuilt local copy is already on `onto`, and step 2 (`alreadyStacked` → `continue`) never pushes. Origin would then stay on the old layer even with a corrected pickTip, and the PR would show the old commits until `finish` force-pushes. The diverged refusal also names no branch, but the refused layer is often not the current one (restack usually runs from the top layer).
Recommendation:
(1) `pickTip` gets a fifth argument, `sameCommits: boolean`. It is true when the layer commits each copy holds (from each copy's own `rebaseUpstream`, compared by `keepsCommits(remoteHeld, localHeld) == nil`) are equal. When neither copy is an ancestor of the other and `sameCommits` is true, take the copy that `onto` is an ancestor of, else the local copy. When `sameCommits` is false, refuse as diverged.
(2) In step 2, when the picked tip is already stacked but origin's copy differs from it, push it with `--force-with-lease=refs/heads/<layer>:<remoteSha>` before `continue`. This is how a restack finishes the push a kill interrupted.
(3) The diverged refusal names the branch and works for real divergence: `git switch <layer>; git pull --rebase origin <layer>; git push origin <layer>`.
(4) Replace the false sentence in the Design with these rules.
Spec cases: in restack-keeps, drop the hand reset from the kill case and add "AC3: the restack after a killed one finishes the layer". Main drops kill.txt, `./zn restack R0010` succeeds, and the local copy, origin's copy and `held(...)` all equal the full layer. Add a second kill case where the trigger is a file in the fixture's own `.cache`, not on main, so the rerun finds the layer already stacked and must push. In layercommits.spec, add pure cases for neither-ancestor with the same commits (a tip comes back) and with different commits (diverged). Rows and mutants: "same-commit copies refused as diverged" (the current prototype), "already stacked never pushes", "neither-ancestor takes local without comparing" (M4 again).

### F2 [medium] `changeKey` keys a fresh diff's paths, so a clean rebase over a rename on main is refused as a lost change "already there"
Where: Design, `layercommits.changeKey` and the `keepsCommits` message `"<subject>" does not keep its change on the new base (part or all of it is already there)`; E1.
Evidence: Probe (b): main runs `git mv a.txt renamed.txt`, and the layer's `c0010: edit a` changes line 15 of a.txt. `git rebase --reapply-cherry-picks --empty=keep --onto main` is clean (merge-ort follows the rename), and the rebuilt commit's diff starts `diff --git a/renamed.txt b/renamed.txt`. Its key changes (e408dc66 → d6a2e758) while the `tracker: start` and `c0010: add block` keys stay the same. Step 5 refuses a layer that lost nothing, and the message says part or all of its change is already on main, which is false. This repository renames often (the c0183/c0184 project moves, refactors that move engine modules), so a layer in flight across one is refused. E1 covered moved line numbers, context and binary blobs, not paths.
Critique: The tempting fix is to run `diff-tree -M`. That doesn't help: the rebuilt commit's diff has no rename in it (both sides are at the new path), so its paths still differ from the old commit's.
Consequences: A key without paths has to compare file sections in any order, because git orders sections by path and a rename can reorder them. Without paths it also can't tell a change from the same change in another file, which a clean rebase produces only through a rename. The rule should say so. Mode lines (`new file mode`, `deleted file mode`, `old mode`/`new mode`) and binary patch text stay in the key. The spend.md exclusion is still decided from the `diff --git` line, before the path lines are dropped.
Recommendation: Key each file section without its `diff --git`, `---` and `+++` lines, sort the sections, and join them. Make the refusal say what it knows: when the rebuilt key is empty, `"<subject>" is empty on the new base (its change is already there)`; otherwise `"<subject>" changes something else after the rebase`. Pure cases: the same section under another path gives the same key; two sections in another order give the same key; one section missing gives a different key. Fixture (optional, cheap in this spec): main renames `pickman/src/one.luau` before the AC1/AC4 restack, and the restack still succeeds. Row and mutant: "path lines kept in the key".

### F3 [medium] Plausible mutants of `changeKey` survive the pure spec, and some rules of the Design have no row
Where: layercommits.spec "AC1: the raft's derived spend.md is left out …" and "AC1: a commit's change survives …"; the Rules and mutants table.
Evidence: (a) In a mutant whose `skip` is set on a spend.md section and never cleared, every file after it is dropped. It passes all three spend cases, because SPEND comes last (`was .. "\n" .. SPEND`) or alone. In a real commit, git sorts `pickman/.tracker/rafts/active/R0010/spend.md` before `pickman/src/...` (`.` < `s`), so the spend section comes first. Under this mutant, every source change after it drops out of the key, and a commit whose source change became empty passes step 5. M8 (`skip = false`) is a different mutant. (b) A key built only from `+` lines passes every pure case, because every patch carries the same `-old`. The fixture can't catch it either: its emptied commit has no patch at all. Under (b), a commit whose deletions are already on main passes. (c) No row covers "local behind origin → origin's copy" (the pure spec has a case, but no mutant is listed), "a red check puts the branch back to `localSha`" (AC3 red asserts it), or "a conflict leaves the branch where it was" (step 4, now on a detached HEAD, covered only by the slow stack-land).
Critique: Adding the cases alone isn't enough. Each row must name a case that fails for its mutant.
Consequences: none beyond the rows and cases.
Recommendation: Add `changeKey(SPEND .. "\n" .. was, "R0010") == changeKey(was, "R0010")` and `~= changeKey(SPEND, "R0010")`. Add a pair that differs only in a `-` line (keys differ). Add rows M12 (skip never cleared), M13 (`+` lines only), M14 (a stale local copy wins over origin), M15 (no reset on a red check) and M16 (the conflict path leaves the branch moved). Run them with mutants.py and record them in E3.

### F4 [medium] Under `./zn dispatch`, `./zn finish c0300` and `./zn restack` run c0300's check.sh in the environment E6 says breaks it, and the design gives a way round it only for `./zn check`
Where: E6, Implementation step 5, `depends_on: []`; `z-nile/engine/main.luau` `cmd.finish` (runs `runCheck` before squashing) and `cmd.restack` step 7; `z-nile/engine/work.luau:279`.

## Candidate lessons (for the lead to place)
- z-design: For every state a kill can leave a rewrite in (the branch moved and origin not, or the reverse), what does the next run of the same command read from that state? Does a spec run that next command with no hand repair? A rewritten commit is never an ancestor or a descendant of the one it replaces, so "ahead/behind" tests read a half-finished rewrite as divergence. (From F1.)
- zz-arch: A "same change" key built from a fresh diff must survive what a clean rebase can do to that diff: moved lines, moved context, changed blob ids, and also renames on the new base and a different order of file sections. Which of those does the key's own spec cover? (From F2.)
