# c0302: Layer branch breaks clone fixtures

## Problem
- `z-nile/tests/acceptance/c0074/done-gate.spec.luau`, `z-nile/tests/acceptance/c0080/consequences.spec.luau` and `z-nile/tests/acceptance/c0120/promote-home.spec.luau` each build their fixture with `git clone` of the checkout and remove `origin`, so on a stack layer branch (`R<NNNN>/<n>/<id>`) `./zn start` in the fixture finds no main (`layergit.mainTip`), refuses with 'no main branch', and 4 cases of each spec fail.
- Any z-nile raft that changes a file those specs watch (their `watch.txt`: `z-nile/engine/main.luau`, `z-nile/lib/sh.luau`, `z-nile/check.sh`, …) is red on its own layer branch in `z-nile/check.sh --affected`, `./zn finish` and its RC0, for a reason unrelated to its change.
- Confirmed on 2026-11-11 on a fresh worktree of origin/main (10dd3c85): `consequences.spec` gave 5 passed under a plain branch name, and 1 passed, 4 failed after `git checkout -b R9999/1/c9999`.
- The fix written in R0093 as emergent issue d0296 (`git checkout -q -B main` after `git remote remove origin` in each spec) passed all three on the layer branch but never reached main, because R0093 was stopped.

## Non-goals
- `layergit.mainTip` and `./zn start` keep their behavior: a repository with no `origin/main`, no `main` and only a bottom layer branch is still refused with 'no main branch'.
- No spec's `watch.txt` and no part of the affected-spec selection (`z-nile/affected.luau`) changes.

## Solution
- Each of the three fixtures names its own branch `main` after removing `origin`, so the three specs give the same results when the checkout is on `R9999/1/c9999` as on a plain branch name.
- Every other spec under `z-nile/tests/` that clones the checkout and runs `./zn start` in the clone is run on a layer branch, and any that fails there gets the same fix.
- Detail (prep, 2026-11-14): the run of every spec under `z-nile/tests/` on a layer branch (E1) found four more fixtures of the same shape, red for the same reason: `c0001/tracker-lifecycle.spec.luau` (5 cases), `c0008/done-order.spec.luau` (4), `c0038/deferred.spec.luau` (8) and `c0050/start-depends.spec.luau` (3). They get the same fix, so seven specs change.

## Design
**The fix.** Each of the seven promoted specs builds its fixture by cloning the checkout and removing `origin`. The clone then holds one branch: the one the checkout is on. On a stack layer branch that is a layer name, so `layergit.mainTip` (`z-nile/engine/layergit.luau:65`) finds no `origin/main`, no `main` and no other branch below `HEAD`, and `./zn start` refuses with 'no main branch'. Each spec gains two lines right after its one `git({ "remote", "remove", "origin" })` line:

```luau
		-- c0302: the clone has no origin, so its branch is its main: on a stack layer branch `./zn start` finds no other
		git({ "checkout", "-q", "-B", "main" })
```

The seven files, all under `z-nile/tests/acceptance/`: `c0001/tracker-lifecycle.spec.luau`, `c0008/done-order.spec.luau`, `c0038/deferred.spec.luau`, `c0050/start-depends.spec.luau`, `c0074/done-gate.spec.luau`, `c0080/consequences.spec.luau`, `c0120/promote-home.spec.luau`. `experiments/narrow.patch` is the change as a diff from origin/main 9e8f3a5d (seven files, 14 insertions, no deletion). Nothing else changes: no engine file, no helper, no `watch.txt`, no `inputs.tsv` row, no `slow.tsv` row.

**Why this line.** `git checkout -q -B main` names the clone's current commit `main` and switches to it, whatever the checkout's branch was: a layer branch, a plain branch, `main` itself (`-B` resets it to where it already is) or a detached head (E2 ran all four). It is the line five other fixtures already use (`c0044/naming.spec.luau:92`, `c0005/worktree.spec.luau:126`, `c0045/workstreams.spec.luau:111`, `c0046/launch.spec.luau:77`, `tooling/worktree-fetch.spec.luau:71`), which is why those pass on a layer branch today. It is also the fix d0296 wrote in R0093 for the first three. Rejected: `-b main` (fails when the checkout is on `main`); changing `mainTip` to accept a lone layer branch (a Non-goal, and it would hide a real mistake); a shared helper for the clone-and-name step (it would rewrite seven promoted fixtures for no new behaviour; the scan below keeps the rule instead).

**No behaviour change.** The tooling is untouched. `layergit.mainTip` and `./zn start` still refuse a repository with no `origin/main`, no `main` and only a layer branch (Non-goal 1). No spec pinned that refusal before (`git grep -nE 'no main branch|mainTip' -- z-nile/tests pickman/tests` found nothing), so this issue adds one: `acceptance/maintip.spec.luau` (AC4) builds a `git init` repository under the home's `.cache` whose only branches are layer branches, runs `layergit.mainTip` there through a probe script, and expects the failure and 'no main branch'; with a `main` it expects main's commit. The rejected design (mainTip falling back to `HEAD` on a lone layer branch) turns it red (mutant C1). Every assertion of the seven specs stays as it is: AC1 pins each file as its base plus the two lines, byte for byte. On a plain branch, `main` and a detached head the seven give the same 50 passed as before (E2). One fixture detail does change off a layer branch: the clone's first branch is now `main`, not the checkout's branch name. `c0074/done-gate.spec.luau`'s `fresh()` already handles a fixture that has a `main` (it moves it back behind the layer), and E2 shows all six of its cases pass in every state.

**The rule, kept.** A new promoted spec, `tests/acceptance/c0302/fixtures.spec.luau` (AC3), reads every `.spec.luau` under `z-nile/tests` as text (from the checkout's top). Its population is every spec whose code clones (`clone.isolated(` or `"--no-hardlinks", `, whatever the source is called: `root`, `TOP`, `engine.TOP`), removes `origin` and runs `{ "start"`. For each clone that a start follows, `{ "checkout", "-q", "-B", "main" }` must stand after that clone and before that start. Code means the text with every comment removed: line comments, trailing comments and block comments (`--[[ ]]`, `--[=[ ]=]`), with strings kept. So a naming in a comment, in an earlier helper, or after the start does not count (design review 001 F4: the first version of the scan passed all three, and missed a checkout called `TOP`). It is fast (text only) and it also asserts that the seven fixed specs are in its population, so the scan cannot go blind unseen. Today's population is ten specs: the seven, and `c0044/naming`, `c0005/worktree` and `c0045/workstreams`, which already name their branch. `c0116/promote.spec.luau`, `c0006/clone.spec.luau` and the specs that clone a fixture's own origin never start after such a clone, so they are outside the rule and unchanged. A spec that needs a lone layer branch on purpose builds it with `git init`, as `maintip.spec` does.

**Where the rule is enforced.** The scan runs in the full gate and the watch net, not in `--affected`: its watch list is what it requires (`tests/lib/t.luau`), and `z-nile/tests/inputs.tsv` no longer selects anything (`sel.parseInputs` has no caller). So a new offending spec is named at the next full gate, after its own raft's affected gate. That is the same reach as every other whole-tree scan here (c0269's `titles.spec`). The rule is textual: a fixture that builds its clone some third way is not seen, and the one-time whole-suite run on a layer branch (E1) is what finds those.

**Sequestered specs are not scanned**, on purpose. The scan walks `z-nile/tests`, not unfinished items' `acceptance/` folders. The search `grep -rlE 'clone\.isolated\(|"--no-hardlinks", ' --include='*.spec.luau' z-nile/.tracker pickman/.tracker | grep -v /done/` (2026-11-14) finds five sequestered specs: c0282's `lifecycle.spec.luau`, c0178's `clone-image.spec.luau` and `overrides.spec.luau`, c0122's `refuse.spec.luau` and `fetch.spec.luau`. Copied into a prototype's `z-nile/tests`, only c0282's is rejected (E8). Scanning sequestered specs would make c0302's own AC3 red until c0282 is re-prepared, and c0302 is what stops every z-nile raft that touches these specs' watch lists from being red on its layer branch; so c0282's fixture is fixed by its own re-prep (c0340, below) and the next such spec is named when it is promoted.

**The proof on a layer branch** is real work, so it runs once from `check.sh` (AC2) and is never a promoted case (user rule: specs fast, real-work proofs one-time). All seven specs are in `z-nile/tests/slow.tsv`, so no gate, `./zn finish` or merge gate runs them: without a check line nothing in the raft would run the files it changes (lesson z-design/guards-name-slow-tier-specs). The lesson zz-test/check-sh-never-runs-the-slow-tier says the opposite for the general case, because a check.sh line is paid at every finish, restack and done. Here the slow specs are the change itself, so the line stays, once, and its cost is stated: measured at 33 s for the layer-branch run and 32 s for the plain-branch run, about 65 s for each `./zn check c0302` (design review 001 F6; the first draft ran the seven a second time in the checkout, which during execution repeated the layer-branch run and never ran the plain half). z-raft should place c0302 where few layers restack above it.

`acceptance/layer.sh` works on a copy, never the checkout: a fresh `mktemp -d` under `$TMPDIR`, outside the repository, removed by a trap on every exit (zz-test, Writers: a whole tree is never built at a fixed name under `.cache`, where a concurrent jailed spec may write; design review 001 F7). It clones the checkout there with `--no-hardlinks`, checks the clone is its own checkout, copies the working tree's seven specs over the clone's, removes the clone's `origin`, and runs the seven twice in the clone: on `R9999/1/c9999` with no other local branch, then on the plain branch `c0302-plain` with no other. Both must pass, which is the captured outcome ("the same results when the checkout is on `R9999/1/c9999` as on a plain branch name").

**Dispatched runs.** On main today `c0008/done-order` fails one case in a dispatched step's environment (`ZN_DISPATCH=1`, the broker and token variables, `z-nile/bin` first on `PATH`), with or without this fix; d0298 owns that, and d0298 `depends_on` c0302. So that the two do not wait on each other, `layer.sh` starts the clone's runner with those variables unset and without any `z-nile/bin` on `PATH` (the list is d0298's `dispatched` helper, read on 2026-11-14). E7: in that environment `layer.sh` gives 50 passed twice, while `done-order` run directly gives 4 passed, 1 failed. AC1, AC3 and AC4 pass there too. Once d0298 lands the unsetting is redundant and harmless. The affected gate at `./zn finish` does not run the seven (slow tier), so it is not red under dispatch for this reason.

**The whole-file pin** is `acceptance/narrow.py` (c0269's model): each of the seven files must equal its merge base with origin's published main (read with `git ls-remote`, never the local ref) with exactly the two lines inserted after the one origin removal, as bytes. A deleted assertion, a reworded comment, a CRLF copy or a base that already holds the line is red. It is relative to the base, so it does not tie the executor to prep's blobs: if another raft changes one of the seven first, the insertion still applies after the same anchor and AC1 still holds. It is not a digest in a promoted spec on purpose: several unfinished items change these same files (below), and each would have to move a digest. It spells each path whole, so a compaction rewrites it with the folder it names.

### Scalability
The scan reads about 260 spec files as text once (0.1 s); the mainTip pin takes 0.6 s. The fix adds one git command to each of seven fixture set-ups.

### Maintainability
One idiom for every clone-and-start fixture, already used by five specs, and a scan that names any new fixture that forgets it. The scan's failure prints the offending paths.

### Usability
A z-nile raft that changes a file these specs watch is no longer red on its own layer branch in `z-nile/check.sh --affected`, `./zn finish` and RC0 for a reason unrelated to its change.
