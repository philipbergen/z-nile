# c0305: The dispatcher waits on a cheap model

## Problem
- The dispatcher stops its chain at a prep or rafting gate whose pull request has only pending checks, or GitHub's pending merge computation, left to wait for, although `[dispatch] auto_merge = ["prep", "raft"]` already lets it merge that gate once it is green and mergeable.

## Non-goals
- This does not merge the run's pull request (c0252 does that), does not add a wait model for a lead's blocking wait on its nested review, and does not change which gates `auto_merge` names.

## Solution
- `.models.toml` gains a `[roles.wait]` table that names one real model per CLI, and at a prep or rafting gate in `auto_merge` whose pull request is only pending, the dispatcher runs one time-limited wait step on that role's model and then merges the gate if it is green and mergeable, and stops the chain if the pull request is a draft, has a conflict, has a failed check, or the limit runs out.

## Open to the human
- F1: The solution isn't the smallest one that fixes the problem. Waiting until a pull request's checks pass and GitHub says it can be merged is mechanical, and `.models.toml`'s `[dispatch] auto_merge = ["prep", "raft"]` shows the dispatcher already merges green, mergeable prep and rafting gates itself without any model. A time-limited poll inside the dispatcher, ahead of that merge it already does, would solve the problem with no model. Instead the idea adds a "wait role" that doesn't exist (`.models.toml` has no `[roles.wait]` or any other wait role) and runs a model step just to poll. The phrase "the cheapest model its CLI names for a wait role" also can't be checked true or false until that role is defined. Answer: disputed: the user decided on 2026-11-07 that "wait is a model activity the dispatcher uses for steps that only poll/babysit", so replacing the wait step with a model-free poll would cut scope the user set and needs their answer; the uncheckable phrase is fixed by having the Solution define `[roles.wait]` itself.
