# c0306: Commands refuse a review off the review models

## Problem
- `./zn status <id> prepared` today accepts an issue whose design review was recorded on any model, for example `claude-sonnet-5-5`.
- `./zn done <R-id>` today accepts a raft whose layer code reviews or final review of the stack were recorded on any model.
- No command defines which recorded models count as review models, so nothing catches a lead who forgets to run a review on one.

Carried from c0261 (Model tiers), which the user retired on 2026-11-12 ("Retire, file leftovers": #299, the roles table, already names a real model for every stage, so c0261 was closed and what main still lacks was filed as new tickets). c0261 was designed on the pre-#299 .models.toml; its prototype proto-c0261 (be21970f, base 10dd3c85) is a reference only. Related: c0251 (the cross-model review pool). (Restored by c0306's prep, 2026-11-13, from the captured text, `./zn capture c0306`, which `./zn idea` rewrote.)

Decided with the user (2026-11-08): "Commands refuse".

Decided with the user (2026-11-08), as relayed: the rule judges by kind of model, not by exact ids (any Opus, any kimi-k3, any grok-...-xhigh), so a model upgrade in .models.toml does not lock out items in flight.

Decided with the user (2026-11-12): "Expensive layer reviews" (every review but a stream review runs on the expensive model, a layer's code review included).

Decided with the user (2026-11-12): "Honour system (Recommended)" (for an interactive review the refusal accepts the model id the lead types: the rule guards against forgetting, not cheating).

Decided with the user (2026-11-14), prep Q1: "Fable for every review (Recommended)" (`claude-fable-` is a fourth review-model kind for every judged review, since #339 runs the final review on `claude-fable-5-2`; the idea's list, which refused Fable, predates that ruling).

Decided with the user (2026-11-14), prep Q2: "Judge it at ready (Recommended)" (`./zn ready` also refuses a raft whose coherence review is not on a review model, before any work starts, so the 2026-11-12 ruling holds for every review but a stream review).

Decided with the user (2026-11-14), prep Q3: "Mark at claim (Recommended)" (once c0306 is on main, `./zn status <id> preparing` writes `reviews: judged` into an issue that has no review yet, and every command that creates a raft writes it into the new raft; a marked item is judged and an unstamped review in it is refused; an issue claimed before the landing stays exempt even if its first review comes later; no record's date is read).

Decided with the user (2026-11-14), design review 001 F2: "Later round supersedes (Recommended)" (a new round of a kind is allowed only when the newest one is off the review models, in the dispatcher and in zz-review; it takes the next number, so no number is reused, and the judges judge only the newest round of each kind per folder; the cheap round stays as history).

Decided with the user (2026-11-14), design review 001 F6: "Skip refused tries (Recommended)" (in every review step except a stream review, the dispatcher skips any try whose model and effort the rule would refuse, today only grok-4.7 at the raft role's `high`, and fails at once if no try is left; the Non-goal on which model the dispatcher picks gains that one exception).

Decided with the user (2026-11-14), design review 001 F3: "Fix c0161's specs now (Recommended)" (R0080, readied and not started, is stopped; c0161's own prep gives the hand-written rounds in its `review-gate` and `review-raft` specs a `Model: claude-opus-5-5` line, which is harmless before c0306; R0080 is readied again; so c0306 and c0161 land in either order).

Decided with the user (2026-11-20): "Review rounds should be toml config" and "toml should have a setting for easy, normal, risky" (the most rounds a review may run is read from TOML: one number per stage (idea, design, implementation) for each of three risk levels, easy, normal and risky. A change that is low risk and easily fixed or reverted gets just a few; one that is complex, large and not easily reverted is allowed more. The numbers are maximums: the skills say so, and say the reviewer is expected to find everything in the first round. The idea cap is configured the same way: "configurable, ideally just one round". f0417 owns the rule. The 2026-11-14 line above, "a new round of a kind is allowed only when the newest one is off the review models", is replaced by it: a further round is allowed up to the configured maximum, on the review models or off them.)

## Non-goals
- The commands do not verify that a typed model id is the model that actually ran the review.
- This change does not alter `.models.toml`, the roles table, or which model the dispatcher picks for any stage, except that in a marked item a review step skips a try the rule would refuse (design review 001 F6, ruled 2026-11-14).
- This change does not build the cross-model review pool, which stays with c0251.
- This change does not re-review or re-record any review made before it lands.

## Solution
- A review record counts as "on a review model" when its model id starts with `claude-opus-` (on any CLI, `claude` or `cursor-cli`), or starts with `claude-fable-` (prep Q1), or starts with `kimi-code-k3`, or starts with `grok-` and its recorded effort is `xhigh`.
- By that rule `claude-opus-4-1`, `claude-opus-5-5[1m]`, `claude-fable-5-2`, `kimi-code-k3.2` and `grok-4.7` at `xhigh` pass, and `claude-sonnet-5-5` and `grok-4.7` at `high` are refused.
- The four patterns are one fixed list in the tooling's code and are not read from the ids in `.models.toml`, so changing `[roles.final-review]` or a fallback to another id of the same pattern refuses no item.
- `./zn status <id> prepared` refuses an issue whose design review is not on a review model, and the refusal names the recorded model and the four patterns.
- `./zn done <R-id>` refuses a raft when any layer's code review, or the final review of the stack, is not on a review model.
- `./zn ready <R-id>` refuses a raft whose coherence review is not on a review model (prep Q2).
- A stream review is never judged by the rule.
- A review record carries the model id and the effort it ran at, and a `grok-` record with no effort is refused.
- For an interactive review the record holds the model id and effort the lead types, and the commands judge that typed value like any other.
- An item whose first review record is dated before this change lands is exempt from every refusal. The cut-over is a mark the tool writes into the item, `reviews: judged`, at the claim of an issue with no review yet and at the creation of a raft, once this change is on main; an unmarked item is exempt (prep Q3).

## Design
What c0306 builds on: #299's roles table (`.models.toml` `[roles.*]`, `models.id(spec)` = `<model>-<effort>`), the dispatcher's review filing (`dispatcher.luau`, one `review.md` moved to `<dir>/<prefix>NNN.md`), the carried move to prepared (`setStatus`, `designOpen`), `readycheck.reason` (shared by `./zn ready` and `./zn work next`), `./zn done`'s `reviewProblem`, and the record calls `./zn spend` and `./zn commit` (`--model`). It does not depend on c0248, c0161 or c0263, and is written so each of them can land before or after it (outcome 9). Decisions it relies on: "Commands refuse" (2026-11-08), "judge by kind" (2026-11-08), "Expensive layer reviews" and "Honour system" (2026-11-12), and prep Q1 "Fable for every review", Q2 "Judge it at ready" and Q3 "Mark at claim" (2026-11-14).

**1. The review models.** `z-nile/engine/reviewmodel.luau` (new, pure) holds the one list, `KINDS`, in this order:
- `claude-opus-` (any CLI: `claude`, `cursor-cli`);
- `claude-fable-` (prep Q1);
- `kimi-code-k3`;
- `grok-`, only at effort `xhigh`.

`reviewmodel.ok(model, effort)` is true when the model id starts with one of the four prefixes, plain (no pattern), and for `grok-` only when the effort is `xhigh`. A `grok-` record with no effort fails. Effort is judged for `grok-` only, so Opus at `low` passes, as the idea's list says. The list is code. It is never read from `.models.toml`, so a change of role or fallback to another id of the same kind refuses nothing (the 2026-11-08 ruling). `reviewmodel.describe()` renders the list for refusals: `claude-opus-*, claude-fable-*, kimi-code-k3*, grok-* at effort xhigh`.

**2. The record: two stamped lines in the review file.**
- A review's model and effort are recorded in the review file itself as `Model: <id>` and `Effort: <level>`, within its first 12 lines (`reviewmodel.read(text): (string?, string?)`, the one reader). The record travels with the file. So a review the dispatcher filed in a prep worktree is judged there, which a spend row on the dispatcher's local `zn-dispatch` branch is not. A record never matches a spend row by its subject.
- The reviewer never writes the lines. Only the tool does (`reviewmodel.stamp(text, model, effort?): (string?, string?)` prepends them when absent), in three places:
  - **the dispatcher**, when it files a review in any mode (design, raft, code, final, stream): the model and effort of the spec of the attempt that ended the step and wrote the file (`spec.model`, `spec.effort`; never `models.id`, whose id carries the effort as a suffix). A fallback that wrote the review is the one recorded. In a marked item, a review step (every mode but stream) skips, before starting it, any try whose `(spec.model, spec.effort)` `reviewmodel.ok` refuses (today only `grok-4.7` at `[roles.raft]`'s `high`), and fails at once, "no try of role <role> is a review model", when none is left (F6, ruled). In a marked item (outcome 4), a reviewer's file that already opens with a `Model:` line fails the step ("the tool records the model, the reviewer writes no Model: line") and files nothing; in an unmarked item it is filed as the reviewer wrote it, as today;
  - **`./zn spend <id> --phase design-review --note design-review-NNN --model <id> [--effort <level>]`** (an interactive design or coherence review), on `<the item's or raft's folder>/design-review-NNN.md`. The `--begin` form stamps nothing;
  - **`./zn commit --phase code-review --model <id> [--effort <level>]`** (an interactive code or final review), on every `review-NNN.md`, `final-review-NNN.md` and `design-review-NNN.md` the commit carries (untracked, added or modified; not deleted) that has no `Model:` line. A stream review, a refute and a harvest are never stamped by `commit`.
- The reader and writer at the edge are one new module, `z-nile/engine/reviewfiles.luau`: `read(dir)` (the folder's design, code and final review files, name to text), `judge(dir, kind, owner)`, `judgeDone(dirs)`, `stampFile(path, model, effort?)` and `effortOption(opts)`. `reviewmodel` stays pure.
- `Effort:` comes from `--effort`. Only for a `claude-` id, when none is typed, it comes from `CLAUDE_EFFORT` (an interactive Claude Code subagent runs at its session's effort); for any other id it is never taken from the environment, and with none typed the line is left out. In a marked item, `spend` and `commit` refuse a `grok-` id with no typed `--effort` ("a grok- review is judged by its effort: --effort <level>"), since effort is judged for `grok-` and the lead's own `CLAUDE_EFFORT` is not the grok review's (review 001 F5).
- A file that already carries a `Model:` line is never stamped again. `stamp` returns the refusal "`<file>` already records `<model>`: a review is recorded once; run a new round", whether the new value differs or not.
- The lines sit beside c0248's `Commit:` and `Patch:` (the same first-12-lines rule, each reader taking only its own key), so either can land first.
- `ledger.isModel` also accepts `[` and `]`, so `claude-opus-5-5[1m]`, an example of the idea's, can be typed. `models.luau` validates `.models.toml` ids with the same function, so such an id becomes valid there too; no role names one today.

**3. The honour system, and its two traps.** An interactive review is judged on the model and effort the lead types (the 2026-11-12 ruling). Two of today's defaults would silently record the author's own model instead, so:
- `./zn spend` keeps a typed `--model` over the session model it measures (today the measured one wins), in every item. (Prep found that `sessionread.span` is handed `process.cwd` with its trailing `/`, so `spend` may never find the Claude session it measures; that is d0328, and a typed `--model` wins either way.)
- In a marked item (outcome 4), the record refusals. A review file's owner is the document of its folder, `<folder>/<folder name>.md` (an issue's or a raft's).
  - `./zn commit --phase code-review` refuses to commit an unstamped review file without `--model`: "`<file>` is a review: --model <the reviewer's model id> records it". Today it takes the lead's own model.
  - `./zn commit` with any other phase refuses to commit an unstamped review file at all: "`<file>` is a review: commit it with --phase code-review --model <the reviewer's model id>". A review's `--model` is never taken for another phase's spend, and an unstamped review enters a marked item only through a raw `git commit`, outside the protocol.
  - `./zn spend --phase design-review --note design-review-NNN` (a reviewer's run) is refused without `--model`, naming the same flag. A `design-review` spend with any other note, a `design-refute-NNN` one or none (the author's answering span after `--begin`, as z-design step 3 and z-raft record it), is the author's: it records exactly as today and stamps nothing, and a typed `--model` on it is the row's model, as on any spend (review 001 F1). A lead who leaves the note off a reviewer's run leaves the review unstamped, which `status prepared` and `ready` then refuse with the "record it" way out.
- In an unmarked item, `spend` and `commit` with no `--model` behave exactly as today, and with `--model` they stamp. So the Solution's "exempt from every refusal" holds for these refusals too, and every item in flight on the landing day records and lands as it does today.
- A refute (`design-refute-NNN`, `refute-NNN`, `final-refute-NNN`) is the author's, so no flag is required for it, at `spend` or at `commit`.

**4. The cut-over mark: `reviews: judged`** (prep Q3).
- Once c0306 is on main, two commands write the front-matter line `reviews: judged`:
  - `./zn status <id> preparing` writes it into an issue that has no `design-review-NNN.md` on origin/main, in the claim's published commit;
  - `./zn new raft` writes it into the raft document it makes, in both forms: the published one (`--project`, the stub with the claim stamp) and the local one (written in the worktree, carried by the rafting PR; it never reaches `publish.luau`, and a later published change of that raft carries the mark on both sides, which `publish.luau` accepts). These are the only two places the raft template is rendered: `fold`, `unfold`, `recombine`, `compact` and `remap` change raft documents that exist, and carry the line.
- Nothing removes or changes the line. `status <id> new`, `stop`, compaction and remap carry it as they carry every front-matter key. The mark is no part of a design's record: `raftplan.designHash` skips a front-matter `reviews:` line, as it skips `status:` and `raft:`, so a claim's mark never makes a grouped member read as redesigned; a document without the line hashes as before.
- `reviewmodel.judged(front)` reads it.
- An unmarked item is exempt from every refusal below. An issue claimed before the landing stays exempt even if its first review comes later, and an issue re-claimed after the landing with an earlier review stays unmarked.
- A marked item is judged on the newest round of each kind the command judges, in each folder it reads (F2, ruled: a later round supersedes). A file with no `Model:` line is refused, so leaving out the record never passes (lesson exemption-markers-refuse-omission). No record's date and no history is read.
- `publish.luau` accepts the line in two published changes and refuses it everywhere else (`publish.markProblem(path, existing, content): string?`):
  - added to an existing issue document (`…/<id>/<id>.md`, an issue id) in a change whose front-matter `status:` becomes `preparing-…` (the claim);
  - present in a new raft document (`…/rafts/R####/R####.md`), the stub `./zn new raft --project` publishes.
- It is refused when it is removed or changed, added on any other status move, added in a new issue's stub, or added to a raft's document by a raft's claim. Only the front matter is read: a `status:` or `reviews:` line in the body is neither the claim nor the mark. The claim's other comparison (a status-only change) is made with the mark line set aside, so the claim still passes as a status move.

**5. What each command judges** (`reviewmodel.problem(files, kind, owner, onOrigin?): string?`, pure, over `{ [name]: text }`). In each folder it reads, the newest round of each kind is judged (`design-review-NNN.md`; for `code`, the newest `review-NNN.md` and the newest `final-review-NNN.md` apart), and a refused one is named:
- **`./zn status <id> prepared`** (the carried move): for each issue target (the item, or each member of a raft) whose local document is marked, the newest `design-review-NNN.md` in its folder (kind `design`). An earlier round is history: a cheap round followed by one on a review model passes, and a cheap round after one on a review model is refused (F2, ruled). A raft target's own design reviews are not judged here: they are `ready`'s (prep Q2). An issue with no design review is not refused here: that is c0161's rule ("has a review"), and `designOpen` stays as it is. The check runs after `designOpen`.
- **`./zn ready <R-id>`**, through `readycheck.reason`, so that `./zn work next` gives the same refusal:
  - for a marked raft, every `design-review-NNN.md` in the raft folder (kind `coherence`, prep Q2);
  - each marked member's design reviews, again. This covers the ways an issue returns to prepared without `status prepared`: `./zn stop`, a remap, and c0250's `resolve`.
- **`./zn done <R-id>`**, after `reviewProblem` and before `runCheck`: for a marked raft, every `review-NNN.md` and `final-review-NNN.md` in the raft folder and in each member's issue folder (kind `code`). Reading the member folders is how c0248's per-layer reviews join with no change. A stream review (`stream-review-*`) is never judged, and neither is a refute or a harvest.
- **`./zn work next`**:
  - its `ready` refusals come from `readycheck` (above);
  - `workread` gains a `codeModel` fact: the `code` rule over the raft folder's review files, read where `reviewState` reads them (origin/main, the layer tips and the local folder). So `work.decide` prints the refusal, not "Run ./zn done", for a raft whose own reviews `done` would refuse. It does not read the members' folders: today no code review is written there, and c0248, which adds them, extends this read (outcome 9).
- The refusal names the item, the file, what was recorded ("`claude-sonnet-5-5` at effort `high`", "no `Model:` line" or "an empty `Model:` line") and `reviewmodel.describe()`. Then it names the ways out that work from where the file is, which `problem` picks by kind and by what was recorded:
  - always: run the round again on a review model and record it (`./zn dispatch zz-review <id> --mode design|raft|code|final`, the mode the file's kind and name give, or a fresh subagent on that role's model);
  - only for a design or coherence review that records no `Model:` line: if it did run on one, record it, `./zn spend <id> --phase design-review --note design-review-NNN --model <id> --effort <level>`, then commit the file (at `status prepared` the file is in this worktree). A recorded review is recorded once, so an off-model record has only the first way out;
  - a coherence review at `ready` and `work next` is on origin/main, so either way out is made in a rafting worktree and lands by pull request, and the refusal says so. A member's design review there cannot be fixed in place: a new round changes the member's design record, and `ready` would then refuse it as "changed since grouped". So its refusal names the route that works: take the member out (`./zn unfold <R-id> <id>` in a rafting worktree), run the new round on a review model in its prep and record it (`./zn spend <id> --phase design-review --note design-review-NNN --model <id> --effort <level>`), land that, and fold it back (`./zn fold <R-id> <id>`, a new record; a raft of several issues then needs a new coherence review);
  - a code or final review at `done` is already committed, so it has only the first way out, committed with `./zn commit -m "<id>: review-NNN" --phase code-review --model <id> --effort <level>`.
- **A later round supersedes** (review 001 F2, ruled 2026-11-14). In a marked item, a new round of a kind is allowed when the newest round of that kind in its folder is one the judge refuses (off the review models, an empty `Model:` line, or none), and only then. It takes the next number (`lastRound + 1`), so no number is reused and the cheap round stays where it is, as history. The dispatcher files it in every mode and keeps its one-round refusal otherwise. zz-review's "a second review of the same kind is refused", and the one-round sentences of z-design step 5, z-raft and zz-execute, gain the same exception. So the refusal's first way out works: `./zn dispatch zz-review <id> --mode <mode>`, or a fresh subagent writing the next number, then the round is answered like any other. In an unmarked item the one-round rule is as today.

**6. Not judged.** A stream review (the 2026-11-12 ruling). The idea review: `./zn idea` runs it on the `idea-challenge` role, and no lead records or types it, so there is nothing to forget. The reviews of an unmarked item.

### Scalability
- Each judge reads the few review files of one item, all of which the command already reads or lists.
- `work next` reads them where it already reads `reviewState`.
- No history, spend file or network read is added.

### Maintainability
- One list (`KINDS`) and one reader (`read`), in one pure module.
- One writer function (`stamp`), used by the dispatcher, `spend` and `commit`.
- The commands share `problem`, so a fifth kind is one row, and a new review kind (c0248's layers) is a list of names.

### Usability
- The refusal names the file, what was recorded and both ways out: run it again, or record the model it ran on.
- The record sits in the review the person reads.
- The board and `metrics` keep reading spend rows as today.
