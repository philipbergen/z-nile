# c0314: Every command applies the same open-list check

## Problem
- `./zn approve` checks only `openlist.pending` (`z-nile/engine/main.luau:5846`: every bullet under `## Open to the human` carries a ruling), while `./zn status <id> prepared` (`designOpen`, `main.luau:1496`) and `./zn ready` (`readycheck.luau:74`) apply the full `openlist.problem` rule, so `approve` accepts a design that `ready` later refuses.
- `openlist.answerKind` matches only `- F1:`, so a refute answer that copies the severity tag from the review's heading (`- F1 [high]: fixed: ...`) reads as unanswered and no command names the expected form.
- Seen 2026-11-13: c0264's design-refute-009 wrote all eleven answers with the tag, the user approved c0264, R0092's rafting PR merged, and `./zn ready R0092` then refused with "open to the human (F1, F4)"; the repair took two more PRs (#333, #334).

## Non-goals
- `./zn status <id> prepared` and `./zn ready` keep their current open-list behaviour, since both already apply `openlist.problem`.
- The rule `openlist.problem` enforces (refuted findings, highs not answered fixed, failed Judged criteria) is not changed.
- Fold refusing a member that origin/main still lists, and the grouped hash covering the refute file, are not changed.

## Solution
- `./zn approve` refuses a design whenever `openlist.problem` reports a gap for it, with the same message `./zn ready` prints, so a design `approve` accepts is never refused by `ready` on the open-list rule.
- A refute answer line carrying a severity tag (`- F1 [high]: fixed: ...`) is either read as the answer to F1 or refused by every command that reads the refute file with a message naming the expected form `- F1: fixed: ...`; it is never silently read as unanswered.
