# c0334: Design record differs on empty files

## Problem
- On main it is unconfirmed whether `./zn work next` and `./zn ready` disagree about a grouped member whose folder holds an empty file (`acceptance/.gitkeep`), and no spec covers it.
- `./zn work next` reads the member's folder with `workread`'s `filesUnder`, which drops a file whose body is empty (`z-nile/engine/workread.luau:366`), while z-raft records the grouping with `originFolderFiles` and `./zn ready` reads with `treeFolderFiles`, which both keep it (`z-nile/engine/main.luau:973` and `:991`).

Reclassified (2026-11-15): filed as d0334 by c0306's prep, but a tooling bug is a chore (z-ticket, Classify the work: "Anything related to CI or tests is always a chore, even when it's a bug"). The user ruled "Re-file, leave d0328", so it keeps its number as c0334.

## Non-goals
- What z-raft records does not change: `raftplan.recordHash` and the `grouped:` hashes already stored in raft documents stay valid without re-grouping.
- For any edit other than adding or removing an empty file, what each command reports stays as it is today.
- The prototype's raft fixtures that avoid `.gitkeep` are not rewritten here.

## Solution
- A spec groups a member holding an empty `acceptance/.gitkeep` and shows that `./zn work next` and `./zn ready` both report it unchanged against the record z-raft stored.
- An empty file counts as part of a member's design record, so after grouping, adding or removing one makes both `./zn work next` and `./zn ready` report the member changed.
- Both commands take a member's files through one shared reader, so no second place decides whether an empty file counts (lesson zz-arch/one-reader-per-format).
