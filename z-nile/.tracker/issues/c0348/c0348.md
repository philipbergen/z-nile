# c0348: Deliver spend reaches main

## Problem
- After `./zn done`, `./zn spend <R-id> --phase deliver` commits the deliver row only on the worktree's local branch and pushes nothing, so the row never reaches origin/main unless someone opens a pull request by hand (R0103's 44d8457cf was stranded, R0101's 1425b00e2 was recovered only by #480).
- Decided with the user (2026-11-15): the issue stays a chore, as captured ("Keep chore").
- Decided with the user (2026-11-15): when a branch holds rows of the done issue that have not landed, the deliver row stays on that branch with a note and the worker posts `BLOCKED:` instead of cleaning up ("Yes, keep on branch"); the command does not fail in that case.
- Decided with the user (2026-11-15): design review 001 F1's phase refusal is not added; the publish is guarded by the equality rule and the deliver-row rule ("Accept as designed").

## Non-goals
- Rows for phases other than deliver, and the deliver rows already lost or hand-recovered (R0103, R0101), are not changed by this issue.

## Solution
- In a fixture, following zz-execute's delivery steps for a raft through `./zn done` and `./zn spend <R-id> --phase deliver` leaves the deliver row on the fixture's origin main with no hand-made pull request, and zz-execute and zz-rules both name that same route.

## Design
Decided by prep (a guess for the approval session, not a ruling): the row reaches main because the command that records it publishes it. The other route, moving the step to before `./zn done`, does not meet the captured Solution (it names `./zn done` and then `./zn spend <R-id> --phase deliver`), and `spend` refuses an active item, so before the landing there is nothing it can record.

History that binds this design: PR #291 ("Stop bookkeeping from blocking the gate") made `spend` commit on the work branch and push nothing, on purpose, so that bookkeeping does not move `main` under running gates. That holds for every row that has a branch to ride (capture rides `./zn land`, prep and design-review ride the prep pull request, build, code-review and deliver-before-done ride the raft). It left one row with no branch: the deliver row zz-execute Phase 6 step 2 records after `./zn done`. This design publishes what that one call records and nothing else (its deliver row, and the measure lines the call folds with it), as one tracker-only commit per call. A gate stays valid when main moves by tracker documents alone (#291), so the publish blocks no gate.

### The rule
`./zn spend <id> --phase deliver` publishes its row to `origin/main` when two things hold:
1. The work is landed: the raft `<id>` names (if it is a raft) and every issue the row is shared over are in `done/` on `origin/main`, as the fetch at the start of the command reads it.
2. This checkout holds exactly origin's rows: for every `spend.d/<writer>.tsv` the call will append to, the worktree's text before the call equals `origin/main`'s text at that path (both absent counts as equal). The published append is then exactly what this call adds, and the local commit holds the same bytes (design review 001 F1).

In every other case nothing is published:
- `capture`, `prep`, `design-review` and `--begin` never publish.
- A `deliver` row for an item that is not done commits on the branch only and prints, on stderr, `spend: <id> is not done on origin/main, so its deliver row stays on this branch and reaches main with it` (exit 0).
- Landed work whose file on this branch holds rows origin does not (the branch recorded other rows for the done issue and has not merged): the row commits on the branch only, with `spend: <id>'s rows on this branch are not on origin/main yet, so its deliver row stays on this branch and reaches main with it` (exit 0). Publishing would carry the branch's rows to main with it.
- Landed work whose file lacks rows origin holds (the checkout is behind): the command fails before it writes anything, `spend: <path> has rows on origin/main that this checkout lacks; nothing was recorded: run ./zn sync, then record again`.
- Neither text holds the other: it fails the same way, naming the file (`… differs from origin/main's rows (neither holds the other's); nothing was recorded: run ./zn sync and settle that file, then record again`).

A raft's worktree right after `./zn done` is in the first state: `done` pushed the commit it stands on.

### `z-nile/engine/main.luau`, `cmd.spend`
The command keeps its order up to `costrow.plan`. Before `costrow.writeFiles`, for landed work, it reads `git show origin/main:<path>` for each planned file and classifies it with `publish.rowsRelation(file.previous, originText)`: `behind` and `diverged` fail there (nothing is written yet), `ahead` turns the publish off for this call. Then `costrow.writeFiles`, and for a row that is to be published:
1. `refuseStale()`, then `publish.commit(".", build, "tracker: spend <id> deliver")`. `build` returns one `publish.Change` per planned file: its path relative to the checkout's top, and the file's whole new text (`PlannedFile.text`: what the worktree's file held, plus the new row). The publisher retries a lost push on the new `origin/main` (its own five tries), and re-checks the append rule against that base each time.
2. If the publish fails: `costrow.restore(planned)` puts the files back, the measure buffer is not rewritten, no commit is made, and the command fails with `spend: could not publish <id>'s deliver row to origin/main (<the publisher's reason>); nothing was recorded, so run it again once that is fixed`. The same command run again records one row.
3. If it succeeds: the local `git add` and `git commit --only` run as today, so the worktree holds the same row in one commit and is clean, then `costrow.writeBuffer`. The command prints its `measured` lines, then `published <id> deliver to origin/main <sha>`, then the local HEAD as today.
4. If the `git add` or the local commit fails after the publish succeeded: the written paths are unstaged (`git reset -q -- <paths>`) and then restored, so the tree is exactly what it was before the command; `costrow.writeBuffer` still runs, because the row is recorded; a warning on stderr says `spend: the row is on origin/main (<sha>) but could not be committed here (<why>). This checkout does not hold it: ./zn sync brings it. Do not record it again.`; the command exits 0. Failing there would invite a second run and a duplicate row. If the unstage itself fails, the message names the `git reset` to run by hand. The same unstage runs on the failure path with no publish, which today leaves the index staged (design review 001 F2).

The publish comes before the local commit so that a failed publish leaves nothing to undo in git. `--begin` returns before this point, as today. The comment above the origin checks, which says the row is "pushed nowhere", is rewritten to say which row is published.

`landed` is computed in the loop that already reads each item's document path on `origin/main` (`stateOfPath(doc) == "done"` for the raft and for every share), so the command makes no new git read. With publishing off (`PICKMAN_PUBLISH=0`) the command already refuses before this point.

### `z-nile/engine/publish.luau`
- `publish.allowed(path, roots, counter)` also takes `<root>/issues/done/<id>/spend.d/<writer>.tsv`, where `<root>` is a registered root of `origin/main`, `<id>` is an issue id and `<writer>` is one segment of `[%w._-]`. It takes no `spend.d` path in the backlog or in `active/`, none for a raft, no other extension and nothing deeper. Every path it took before, it still takes, and nothing else new.
- `publish.measuredReason(existing: string?, content: string): string?` is new and pure: why `content` may not replace `existing` (origin's text, nil when the file is new there), or nil. Origin's bytes must be the start of `content` ("not an append to its rows on origin/main (run ./zn sync, then record again)"), at least one byte must follow ("no new row"), the text must end with a newline ("the last row has no newline"), the whole text must parse with `buffer.parseTsv`, the one reader of that format ("does not parse as measured rows (<err>)"), and the rows after origin's must hold a `deliver` row ("no deliver row among the new rows").
- The validator does not refuse the other phases among the new rows, though design review 001 F1 recommended it. Rows the call folds from the measure buffer take the phase of the stage they ran in (`buffer.fold`: a run takes its begin mark's phase, a runner line `test`, the rest `other`), so a legitimate deliver publish can carry rows of any phase, and a refusal there would fail a raft's publish closed. The leak F1 found is closed where it arises, by rule 2 above; the deliver-row rule keeps any writer that is not this command off the path.
- `publish.rowsRelation(mine: string?, origin: string?): "same" | "behind" | "ahead" | "diverged"` is new and pure, by bytes (rows are only ever appended): how a checkout's copy of a measured-rows file stands to origin's. `publish.luau` gains `require("./buffer")`; `buffer` requires only `ledger`, so there is no cycle.
- `publish.commit` checks every such change with `measuredReason`, and refuses when `<root>/issues/done/<id>/<id>.md` is not on the base it read (`no <id>.md beside it in done/ on origin/main`). Every refusal names the path. The guard fails closed: a path `allowed` does not take is refused by the existing "not a tracker item file" branch.

### First-pass checks that changed the design
- Promoted specs run against the prototype: `c0081/publish-guard.spec` went red until `refuseStale()` stood on the line before the publish. `c0084/spend-command.spec` pins "pushes nothing" for a done item's deliver row and is slow-tier, so no gate would have shown it: it is an Override, run once by AC7.
- Lifetime owner: the row's only durable home is `origin/main`. The worktree that holds the local commit is removed by the next Phase 6 step, so the publish, not the commit, is what counts as recorded (step 2 and step 4 above follow from that).
- Order of operations: publish, then commit. The reverse leaves a commit to undo when the publish fails.

### Scalability
One `git show origin/main:<path>` per planned file for landed deliver work (the refs are already fetched), then one `publish.commit` per call that publishes: its usual fetch, one `ls-tree` of the roots, one `git show` per changed file, one `hash-object` and the `mktree` calls per changed path, and one push. The changed files are one per issue the row is shared over (a raft's members), so the cost grows with the raft's size, not with the number of items, roots or projects. No call is added to any other phase or command. A raft publishes once, after its landing.

### Maintainability
A new measured-row format or writer goes through `buffer.parseTsv` and `costrow`, as today; the publisher learns nothing about rows beyond "parses, and only appended". A future command that must publish a measured row for landed work calls `publish.commit` with the same change shape. The path rule lives in `publish.allowed` with the other path rules.

### Usability
- No new command or flag. The usage text is unchanged.
- New output: `published <id> deliver to origin/main <sha>` (stdout); on stderr the two "stays on this branch" notes, the behind and diverged refusals, the failed-publish refusal and the committed-nowhere warning, each quoted above. Each names the item or the path, and the rule.
- Exhaustive lists checked: the main checkout's command list and the read-only set are unchanged (`spend` already refuses in the main checkout and is already a writer).

- F1: design review 001 F1 (high) recommended two guards against rows of an unmerged branch reaching main with the deliver publish: publish only when the worktree's file equals origin's, and have the publisher refuse new rows of the phases that ride a branch (capture, prep, design-review, build).
