# c0352: Spec env reaches the specs

## Problem
- `z-nile/tests/lib/fence.luau:896` sets `PICKMAN_WORKER_LANES` only by assigning `process.env`, which in Lune 0.10.5 does not reach a child process, and the `export` list that starts the jailed run (`fence.luau:929`) does not name it.
- In a top-level `lune run tests/run -- a.spec.luau b.spec.luau` from `z-nile/`, the inner runner reads `PICKMAN_WORKER_LANES` as nil at `z-nile/tests/run.luau:368` and starts its workers with plain `lune`, not through `fence.WORKER_LANE`.
- The c0049/parallel-runner lane cases pass only because they set `PICKMAN_WORKER_LANES` themselves, so no spec fails while the shared eight-lane rule in the zz-test skill's Speed section is not in force.

## Non-goals
- The `PICKMAN_TEST_JAIL` handling is not changed, because `fence.luau:929` already exports it to every spec process in every mode.
- The `process.env` assignments inside spec files (such as `work.spec.luau:274` and `sweeper-interlock.spec.luau:84`) are not changed, because they are read in the same process.
- The lane count, the lane wrapper `fence.WORKER_LANE` and the suspected c0049/parallel-runner lane starvation from d0298's design review 001 F2 are not changed or investigated here.

## Solution
- The command `fence.enter` uses to start the jailed run passes the `workerLanes()` folder to the inner runner as `PICKMAN_WORKER_LANES`, the same way it already passes `PICKMAN_TEST_JAIL`.
- A spec that does not set `PICKMAN_WORKER_LANES` itself runs a top-level run of two spec files and fails unless the inner runner starts its workers through `fence.WORKER_LANE` with that lanes folder.
- A z-nile check fails when a file under `z-nile/` outside `tests/tooling/`, `tests/acceptance/` and `.tracker/` assigns a `process.env` variable that the command starting its child process does not pass explicitly, with the `PICKMAN_TEST_JAIL` assignment at `fence.luau:922` as the one named in-process exception.
