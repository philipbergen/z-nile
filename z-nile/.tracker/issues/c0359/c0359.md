# c0359: Prep gate merges unlinted folders

## Problem
- A pull request whose head fails the full gate's static stages (`stylua --check`, `selene`) can merge to `main` by every path (the dispatcher's prep and raft gates under `auto_merge`, `gh pr merge`, the GitHub button), because CI (`.github/workflows/deploy.yml`) runs no gate; on 2026-11-15 this let #397, #399, #408 and #417 land and left `main` failing `stylua --check` on 16 files and `selene` on two warnings until #433.

Scope decision (user, 2026-11-15): "Learn a lesson from this and make sure it can't happen again", said after Claude merged 28 prep pull requests by hand on CI green and `main` failed the static stages (the incident above). It is why this issue covers every merge path and carries the lesson, not only the dispatcher's gates as first captured.

## Non-goals
- This issue does not run the spec stages or any `check.sh` in CI, and does not reformat or relint files already on `main`.

## Solution
- A required status check on `main` runs the static stages (`stylua --check` and `selene`) over the pull request's head and blocks every merge path while it fails, the dispatcher's prep and raft gates refuse a pull request whose head fails those stages, and a lesson under zz-rules (Landing a change) records that CI green is not the gate and that whoever merges by hand first runs the static stages on the head, citing the 2026-11-15 incident and c0292's E3.
- Detail added in prep (the captured bullet above is the scope): the static stages are one new gate mode, `z-nile/check.sh --lint` (format and lint alone, every project, never narrowed). A new workflow, `.github/workflows/static.yml`, runs it on every pull request as the check `static`; a committed ruleset, `.github/rulesets/static.json`, which the repository admin posts once, makes `main` require that check. The dispatcher's prep and raft gates run the same command on the PR's merge with today's `main` before they merge. The lesson is `zz-rules/hand-merge-runs-static-stages`, and Landing a change step 3 points to it.

### Decisions
1. **One definition of the two stages, a new gate mode `--lint`.** The full gate's format and lint stages are `stylua --check "${LUAU_DIRS[@]}"` and `selene --quiet "${LUAU_DIRS[@]}"` over `z-nile/roots --luau-dirs` (every project's folders, each `.tracker/` named). `z-nile/check.sh --lint` runs exactly those two stages and stops. The two `par_start` lines move into one shell function, `lint_stages`, that both the normal static section and `--lint` call, so they cannot drift (c0292's AC6 greps for the two command strings; they stay word for word). `--lint` is never narrowed by the change (unlike `--static`): the merge check must not trust the selector, and on GitHub there is no `origin/main` to diff against. It runs after the registry read, the folder list and the fence's read-only refusals, and before everything that writes, fetches, builds or reaps (`./zn reap --auto`, the `.cache` prerequisites, the Luau type download, the sourcemaps, `lune setup`). `--lint --plan` prints `format: <dirs>` and `lint: <dirs>` only. The list is never empty: `z-nile/roots` names every project's root, existing or not (E5), so no empty-list rule is needed. Both stages (and the settings stage of Decision 4) run in parallel through `par.sh`, as today, and each reports when another fails. The reap line keeps the words `c0191/docs` pins and skips lint mode: `[[ -n $plan ]] || [[ $mode == lint ]] || ./zn reap --auto || true`, so `--lint` never starts `./zn` (in the dispatcher's scratch tree that would start the engine's reaper from inside the main checkout; on GitHub it would start lune for nothing).
2. **The required check is a new workflow, `.github/workflows/static.yml`**: `name: static`, one job `static` (the check run's name is the job id; no `name:`, no `if:`, no `needs:`), on `pull_request` with types `opened, synchronize, reopened, ready_for_review` and no path, branch or draft filter (a filtered workflow reports nothing, and a required check that never reports blocks the PR forever; a prep PR touches only `.tracker/`, which is what must be checked). Steps: `actions/checkout@v4`, `z-nile/setup.sh --tools` (the pinned stylua, selene and lune, as `deploy.yml` installs them), `z-nile/check.sh --lint`. `permissions: contents: read`, no secret, concurrency `static-<PR number>` with cancel-in-progress. It runs no spec, no item's `check.sh` and no runtime test. A checkout of a `pull_request` event is GitHub's merge of the head into the base (E2), so the check judges what would merge. **Known limit** (design review 001 F7): the workflow file and the script come from that merge too, so a PR that changes `static.yml`, the gate's two stages or the tools' settings is judged by its own copy and passes its own `static`; only the dispatcher's gates are safe from it (their shape rule refuses such a PR). zz-rules' Merging close and the lesson say so: the review of such a PR checks the change, and its hand merge runs `main`'s `--lint` on it. `pull_request_target` would trade this for running PR code with the base's token, which the workflow spec forbids.
3. **The ruleset is committed, `.github/rulesets/static.json`, and posted once by the repository admin** (the agent credential can't write rulesets: zz-rules, The agent credential): `name: static`, `target: branch`, `enforcement: active`, `conditions.ref_name.include: ["~DEFAULT_BRANCH"]`, one rule `required_status_checks` with `[{ context: "static", integration_id: 15368 }]` (15368 is the GitHub Actions app every check run here reports, E3, so no other app or a bare commit status can satisfy it), `strict_required_status_checks_policy: false` (no forced rebases; the dispatcher's own check below reads today's main), `do_not_enforce_on_create: false`, and one bypass actor, the repository admin role (`RepositoryRole` 5, `bypass_mode: always`). SETUP.md gives the commands to post, read and delete it. It sits beside `no-force` (deletion and non-fast-forward), which it does not change.

4. **The dispatcher's gates lint the merge themselves** (lesson zz-arch/merge-gate-checks-what-it-merges: the gate judges the PR's own commits, never a host's summary). New `dispatcher.lintMerge(ctx: Ctx, number: number, main: string, ref: string, base: string?): string?` in `z-nile/engine/dispatcher.luau`, called last in `dispatcher.judgePr`, after `trackerstate.check` and `dispatcher.backstop` both pass, for both the prep and the raft gate (the run gate is a human's and unchanged). It lists the PR's changed paths (`git diff --name-only --no-renames <merge base or the empty tree> <head ref>`) and returns nil when none is lintable (below). Otherwise it makes `git merge-tree --write-tree <judged main> <head ref>` (a conflict refuses), exports that tree whole (`git archive` and `tar`) into `<main checkout>/.cache/dispatch/lint-<pr>-<time>-<random>/tree`, a folder of this judgement alone, and runs `perl <main checkout>/z-nile/lib/bounded.pl --time 600 -- env ZN_MEASURED=1 bash z-nile/check.sh --lint` there (`ZN_MEASURED` skips the gate's own measurement row; the bound fails a hang closed). Exit 0 returns nil; anything else returns `its merge fails the static stages (z-nile/check.sh --lint, exit <n>):` and the first 40 lines of its output, which name the failing files. Running it before the shape judgement would run a PR's own script; AC5 pins the order.
   - **`dispatch.lintable(path: string): boolean`** (pure, `z-nile/engine/dispatch.luau`): true when the path's last component, lowercased, ends `.lua` or `.luau`, ends `.toml`, `.yml` or `.yaml`, or starts with `.`; false otherwise (`.md`, `.sh`, `.json`, `.tsv`, `.luau.txt`, `z-nile/next`). The stages read `.lua` and `.luau` files, and their settings are TOML (`stylua.toml`, `selene.toml`), YAML (selene's standard libraries) and dotfiles (an ignore list); a prep PR rarely carries any but `.luau`, so the extra kinds cost nothing and miss nothing. The names are by kind, not by tool, so no engine module names either tool (c0292's AC6 greps `engine/*.luau` for the two words). A PR that changes none of them can't change what the stages report, so it is not exported or linted at the gate. A prep PR may carry any regular file in its folder, and stylua obeys a `.styluaignore` (or a `stylua.toml`) beside the files it walks: a `.styluaignore` of `*` hides the folder's unformatted specs from the gate, from GitHub's `static` and from the full gate alike (the reviewer's probe). `lint_stages` therefore starts a third stage, `settings (none under .tracker/)`, the shell function `tracker_settings`: it lists every file under a `.tracker` entry of `LUAU_DIRS` whose name, in any case, is `.styluaignore`, `stylua.toml`, `.stylua.toml` or `selene.toml`, and fails naming them. Every mode that runs the two stages runs it. `git ls-files` finds none under any `.tracker/` today, so nothing in flight breaks; a nested `selene.toml` is not read by selene (the probe), but refusing it costs nothing and keeps one rule.

### Scalability
- The required check: one extra Actions job per pull request event (drafts included, where `deploy` skips), about 20 s like `deploy` (the setup is the same), so one billed minute per push. The repository is private (`gh api repos/{owner}/{repo}`: `private: true`), so minutes count against the account's included allowance (3,000 a month on Pro). At 100 pushes a day `static` alone is about 3,000 minutes a month, and with `deploy` about 6,000: roughly the allowance again in overage, a recurring cost that is the user's to accept. Implementation step 6 puts it to the user beside the ruleset post (design review 001 F6).
- The gate: per judgement of a PR that changes a lintable path, one `git diff`, one `merge-tree`, one `archive` of the merged tree (50 MB today, 0.15 s) and its extraction, and one `--lint` run: 4.9 s of wall time and about 50 s of CPU over the whole repository today (E4; stylua dominates). A PR without a lintable path costs one `git diff`. A chain judges an open PR once per pass, so a dispatched prep pays this once per `./zn dispatch` at its gate. It grows with the repository's Luau, not with the PR.
- `--lint` reads every project's folders whatever changed: the same cost on GitHub and locally (4.9 s).

### Maintainability
- The two stages live in one place, `lint_stages` in `z-nile/check.sh`; GitHub and the dispatcher both run that script, so a new stage, tool flag or project reaches all three through the registry (`z-nile/roots --luau-dirs`) and nothing else. A new kind of configuration file joins `dispatch.lintable`, the one rule for "can this change what the stages say".
- The required context is pinned to the workflow's job id (AC2), so renaming the job without the ruleset turns a spec red instead of leaving every PR blocked on a check that never reports.
- The ruleset is a committed file pinned by a spec (AC2) and its live state by AC7; a change to it is a reviewed PR plus the admin's `gh api -X PUT repos/{owner}/{repo}/rulesets/<id> --input .github/rulesets/static.json` (SETUP).

### Usability
- A held PR names the failing files in the stop line, also when the rollup is red (`waits for green CI, and for a human: …`; `./zn dispatch <id>` and the board show it), and a hand merge has one command to run, the same one GitHub runs, plus `gh pr checks <pr> --required`.
- `z-nile/check.sh --lint` joins the usage line and the zz-test gate table; `--lint --plan` prints its folders.
- SETUP gives every command the admin needs (post, read, delete the ruleset; re-run an old PR's check), and the Scalability note on Actions minutes.
