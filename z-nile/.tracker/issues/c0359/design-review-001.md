### F1 [high] `./zn done` lands every raft on `main` by an admin push that skips the required check. The design calls that a tracker publish and tells the user the only path left open is `--admin`
Where: c0359.md Decisions 3, Guess G1 (line 39); Documents, "zz-rules, Merging close" (line 48); AC10.
Evidence: G1 counts "`done`'s push" among "every tracker publish (`./zn status`, `new`, `land`, `done`'s push, the dispatcher's broker)" and concludes "the only merge path left open is a deliberate admin override (`gh pr merge --admin`, the button's 'bypass rules' box)". But `./zn done` merges the raft's top layer with `--no-ff`, retargets the layer PRs and runs `git push --quiet origin HEAD:refs/heads/main` (`z-nile/engine/main.luau:5269`, "This is the binding commit on main"). That push carries the raft's code, and it is how every raft PR lands. With `bypass_mode: always` for the admin role, GitHub accepts it whatever `static` says. The same goes for `./zn land` (`main.luau:2540`) and the watch net's repair push (`watchcmd.luau:789`). The sentence AC10 would write into zz-rules, "The repository admin may bypass the ruleset, because the tracker's own pushes to `main` need it; a merge never does.", is false on the day it lands: `./zn done` is a merge, and it needs the bypass. Without it no raft could land at all, because a commit made locally by `done` has no check run.
Critique: the captured Solution says the required check "blocks every merge path while it fails". G1 is put to the user as a pending guess on the premise that only `--admin` escapes, so the user would rule on a false premise. The fix the author will reach for is to reword the sentence and move on. That leaves two things unsaid: what holds `done` instead, and whether anything pins it.
Consequences: done's own gate is what holds it. `z-nile/check.sh --affected` on the merged tree runs the format and lint stages over every folder of each project the raft changed (narrowed by project, not by file). That covers what the raft brings. Files of another project already red on `main` don't hold it, which is the right rule and is the incident's complaint the other way round. Inside a spec run `done` skips its gate, so no spec can prove this through `done` itself. The other option, having `done` also run `--lint` (every project, about 5 s), would refuse a raft on other projects' red files, the 2026-11-15 pain. That is a design choice to make out loud, not a default.
Recommendation: add to the Design a table of every command that writes `main`, made by a search the design names so it can be rerun (`git grep -n 'refs/heads/main' z-nile/engine`): the dispatcher's gate merge, `gh pr merge` and the button, `./zn done`, `./zn land`, the broker and publish, the watch-net repair. Give each the guard that holds it: lintMerge plus green; the required check, subject to F2; done's `--affected` gate; land's `--static` and its documents-only rule; tracker state only; the repair's own scope. Rewrite G1 so it names `done`'s and `land`'s bypassing pushes and what holds them. Rewrite the Merging close sentence to say so, for example "the tracker's own pushes and `./zn done`'s landing push need it; `./zn done` lands a raft only after its own affected gate, whose format and lint stages read every project the raft changes". Update AC10's literal to match and keep the `lacks "a merge never does"` sense out. In the Regression guard, name the promoted specs that pin that `done` runs `--affected` and that `--affected` runs both stages over each changed project's folders whole (`c0120/gate-homes`). If none pins done's call, add a check.sh line that greps `cmd.done`'s body for the gate call.
Lesson candidate (z-design): when a design claims a guard covers "every path" to `main`, has it listed every command that pushes `main` (a named search of the engine) and the guard that holds each? Check question: "Which commands write `main`, and which guard does each pass?"

### F2 [high] Whether `gh pr merge` refuses a failing PR when the user who runs it can bypass the ruleset is assumed, not tested. That is exactly how the incident's merges were made
Where: Decision 3, G1 ("`gh pr merge` without `--admin` and the button do not take by default (E2: gh refuses a `BLOCKED` merge client-side)"); E2; E6 to E8; OC1.
Evidence: E2 shows from gh's source that `blockedReason` refuses when `mergeStateStatus` is `BLOCKED`. It does not show that GitHub reports `BLOCKED` to a viewer who may bypass. Every hand merge here runs with the admin's credential (zz-rules Merging: "your credentials are the admin's"), and the admin role is the ruleset's bypass actor. If GitHub reports `CLEAN` or `UNSTABLE` to that viewer, then plain `gh pr merge --squash` (no `--admin`) merges a PR whose `static` is red. So would zz-rules Merging condition 4, which reads the same `mergeStateStatus`. That is the 2026-11-15 path: 28 hand merges by the admin. Public reports disagree on this: a MongoDB bug report says GitHub shows a PR as mergeable to an admin that can merge it, despite protections. No Phase-1 experiment asks the question. E6 tests a tracker publish, E7 the rule's parameters and E8 a green run and a reopen. OC1 looks at the web page, which shows the bypass box whatever the API says.
Critique: the captured outcome "blocks every merge path while it fails" rests on an assumption nobody has tested and that has no fallback. The tempting fix is to add the probe and nothing else. If the probe fails, the design has no answer and the outcome is unmet.
Consequences: if GitHub does not report `BLOCKED` to the admin, only two things close the path. One is the separate pushing identity G1 already names as the alternative (a deploy key or GitHub App as the only bypass actor; it changes the broker, publish, `land`, `done` and the repair push, and needs a new credential). The other is the user accepting that hand merges are held only by the rules (a scope decision). Either way it is the user's call, not the executor's.
Recommendation: add E10 (Phase 1, read-only, run as the admin after posting the ruleset). On a scratch draft PR whose `static` is red (an unformatted `.luau` on a throwaway branch, closed afterwards), `gh pr view <n> --json mergeStateStatus,mergeable` must say `BLOCKED`. Fallback: stop and ask the user, through `questions.md`, to choose between the separate pushing identity (with its cost) and an explicit `Scope decision` that hand merges rely on the rules. Make the hand-merge rule not depend on the viewer either way: Landing a change step 3's new sentence, Merging condition 4 and the lesson's How to apply also require `gh pr checks <pr> --required` to pass (it reads the required checks' states, not the viewer's merge state). Pin that in AC8 and AC10.
Lesson candidate (z-design): has a server rule's effect on the admin's own client been measured as the admin, rather than inferred from the docs and from the client's source?

### F3 [medium] In practice the stop line that names the failing files never shows: a red or pending `static` check stops the gate first at "waits for green CI", and the design's reason for skipping unlintable PRs is contradicted by the required check
Where: Decision 4, "Message" and lintable's last sentence ("a failing file already on `main` does not hold it (that is the watch net's and the required check's to report)"); Usability ("A held PR names the failing files"); `dispatch.gate` (`z-nile/engine/dispatch.luau`, reasons in the order draft, `not pr.green`, `not pr.mergeable`, `carries`); gate.spec (every fake rollup is `SUCCESS`).
Evidence: when a prep PR's own spec is unformatted, GitHub's `static` runs the same `--lint` on GitHub's merge and fails. `parsePr` sets `green = false`, and `dispatch.gate` returns "the prep PR #n waits for green CI" before it reaches `carries`, so the named files are computed and dropped. The same happens right after a step opens its PR, while `static` is still running. lintMerge's message reaches the user only when GitHub's run was green against an older `main`. Separately: when `main` is red (by a bypassing push, F1), `static` fails on every PR whatever it changes, so a docs-only PR is not "not held". The required check holds it, and the gate stops it at "waits for green CI". Once `main` is fixed, those red runs stay red until a new `pull_request` event: re-running a run reuses the original event's `GITHUB_SHA`, the merge with the old red `main`. SETUP's recovery text covers only PRs opened before `static.yml`.
Critique: Usability promises something the chain never says, and gate.spec can't see it because its fake rollup is always green. Reordering `dispatch.gate` so `carries` comes before green would change the reason text that c0261's prepared specs read: `dispatch-activities.spec` and `dispatch-wait-cli.spec` assert `has(why, "waits for green CI")`, and c0261's `z-wait` keys on `judged` and `Pr.failed`.
Consequences: appending keeps both items' substrings. A stop that already says "waits for green CI" gains the judgement, and c0261's no-wait rule for a judged PR is unchanged.
Recommendation: in `dispatch.gate`, when `not pr.green` and `carries` are both set, the reason becomes `the <gate> PR #n waits for green CI, and for a human: <carries>`. Add a gate.spec case whose rollup is `FAILURE` and whose PR carries an unformatted spec: exit 4, the stop names the file, nothing merged. Add a Rules row for it, with the mutant "the green reason alone". Quote c0261's rule in Existing work. Fix the lintable rationale: a PR with no lintable path is not exported because it can't change what the stages say, and the required check, not this gate, holds it while `main` is red. Add to SETUP and the Design what happens when `main` is red: every PR's `static` fails until `main` is fixed, then each needs a push or a close and reopen, because `gh run rerun` re-judges the old merge. Add one sentence to the lesson.

### F4 [medium] A `.styluaignore` inside a prep's own folder hides that folder from the format stage at the gate, in GitHub's check and in the full gate
Where: Decision 4, `dispatch.lintable` ("their settings are TOML …, YAML … and dotfiles (an ignore list)"); the prep gate's shape rule (the issue's own folder, any regular file); zz-rules, Tracker state (refuses only `.gitattributes`, `.gitmodules`, `.models.toml`).
Evidence: probe, `./zn run --time 60` in a `$TMPDIR` copy of the root's `stylua.toml`. `stylua --check t/.tracker/issues/c1` (unformatted spec) exits 1. The same spec beside `t/.tracker/issues/c2/.styluaignore` containing `*` exits 0. `stylua --check t/.tracker` reports 2 diffs for 3 unformatted folders, so the ignored one is skipped when the whole `.tracker` is walked too, which is what `lint_stages` does. A nested `selene.toml` is not read (selene still exits 1). A prep PR may carry `<issue>/.styluaignore` or `<issue>/acceptance/.styluaignore`. The design marks it lintable and then lints with it in force, so the gate, `static` and the full gate all pass unformatted specs. If the ignore file sits in `acceptance/`, it may be promoted along with the specs.
Critique: this repeats a known lesson: an allow-listed tracker path holds a setting that changes what a gate checks. The tempting fix is adding the name to `lintable`, which it already is; linting doesn't help when the linter obeys the file.
Consequences: refusing it in `trackerstate` would change the wrapper, the broker and the tripwire too. That is a wider change than needed. Refusing it in `--lint` makes all three layers agree, because they share `lint_stages`. `git ls-files` shows no such file under any `.tracker/` today, so no existing work breaks.
Recommendation: `lint_stages`, and so `--lint`, `--static` and the full gate, fails first, naming the file, when any of the named folders that is a `.tracker/` holds a file whose lowercased name is `.styluaignore`, `stylua.toml`, `.stylua.toml` or `selene.toml` (a `find … -iname` over the `.tracker/` entries of `LUAU_DIRS`). Add lint.spec and gate.spec cases with an input only this guard refuses: a `.styluaignore` of `*` beside an unformatted spec, held, naming the ignore file. Add a Rules row (mutant: no such check). State in Existing work that the search found none.
Lesson: zz-arch/authority-config-is-not-tracker-state

### F5 [medium] No Rules row or case covers "`--lint` reaps nothing", so a mutant that drops it passes every listed spec
Where: Decision 1 ("before everything that writes, fetches, builds or reaps (`./zn reap --auto`, …)"); Implementation step 1 (the reap line); Rules and mutants (no row).
Evidence: the design keeps `[[ -n $plan ]] || [[ $mode == lint ]] || ./zn reap --auto || true`. `c0191/docs` pins only `[[ -n $plan ]] || `, `|| true` and the line's place before `par.sh`. lint.spec's snapshot ignores processes. Deleting `[[ $mode == lint ]] || ` keeps every c0359 spec and `c0191/docs` green. Then every gate judgement starts the engine's reaper from a scratch tree inside the dispatcher's own main checkout while the dispatcher's steps run, and every GitHub `static` run starts `./zn` (lune and the engine) for nothing.
Critique: this is a behavioural rule from Decision 1 with no row and no case.
Consequences: none beyond the case. The fixture is a copy, so its `zn` can be replaced.
Recommendation: add a lint.spec case: replace the fixture tree's `zn` with a script that writes a mark under the fixture's `.cache` and exits 0; after `--lint` the mark is absent. Add a Rules row (mutant M25: the `[[ $mode == lint ]] ||` clause dropped), run in `mutants.py`.

### F6 [low] The Actions-minutes estimate understates the new total and leaves a recurring cost implied rather than asked
Where: Scalability, first bullet; Usability ("the user may watch the bill").
Evidence: "at 100 pushes a day that is about 3,000 minutes a month, the size of a Pro account's included private-repository minutes, which `deploy` already spends at the same rate". `deploy` runs on every non-draft PR push, so with `static` the total is about twice the included minutes, and the extra half is billed overage. That holds only if the repository is private; the design doesn't say which it is.
Critique: a new recurring cost is the user's to accept, and step 6 already asks the user to post the ruleset.
Consequences: none.
Recommendation: state the combined estimate and whether the repository is private, and add it to step 6's `questions.md` beside the ruleset post, so the user accepts the cost with the post.

### F7 [low] A pull request is judged by its own copy of the checker, and the design doesn't state that limit
Where: Decision 2 ("A checkout of a `pull_request` event is GitHub's merge … so the check judges what would merge"); the lesson; zz-rules Merging close.
Evidence: for `pull_request` events GitHub takes the workflow file from the PR's merge commit, and `--lint` runs that tree's `z-nile/check.sh`, `stylua.toml` and `selene.toml`. A code PR that edits `static.yml`'s last step, `lint_stages`, or the root settings passes its own `static` and lands. Only the dispatcher's gates are protected, through the shape rule.
Critique: "blocks every merge path" holds only for PRs that leave the checker alone. A reviewer of such a PR needs to know it.
Consequences: none (`pull_request_target` would trade this for running PR code with the base's token, which the workflow spec rightly forbids).
Recommendation: add a Known limit to the Design, the Merging close and the lesson: a PR that changes `.github/workflows/static.yml`, `z-nile/check.sh`'s stages or the tools' settings judges itself by its own copy, so its code review checks that change and the hand merge runs main's `--lint` on it.
