## Non-goals
- Ready still reads approvals only from `approval.md` on origin/main.
- `./zn approve` never merges, or changes the state of, a prep pull request.
- `./zn approve` does not retry a failed publish or push on its own.
- What an approval records and who may approve stay as c0283 left them.

## Solution
- When the design it approves is already on origin/main, one `./zn approve <id>` records the approval and publishes `approval.md` to origin/main (what `--publish` does today), so ready counts it at once with no second command.
- When the design is on an unmerged prep branch, one `./zn approve <id>` commits `approval.md` to that branch, pushes it so the prep pull request carries it, and prints that the approval counts when that pull request merges.
- When the publish or push fails, the approval stays recorded locally, and the command prints that it does not count yet and names the one command that retries it, `./zn approve <id> --publish`; it counts once that retry succeeds.
- `--publish` stays as that retry and `--check` behaves as it does today.
- The c0283 approve specs this changes are listed under Overrides, and the issue depends on c0283 being done.

## Design
`./zn approve <id>` becomes one command, run from the main checkout or any worktree: it finds the place, says where it acts, records the approval there, and makes it count. It builds on c0283's approve (the agent-session refusal, the `approved` row, the pair that `--publish` publishes), which is why `depends_on: [c0283]`. Prototype: `proto-c0369` (origin/main merged with `proto-c0283-publish`, then this change; never merged); `experiments/prototype.patch` is the change and `experiments/mutants.py` the mutation runner.

Every choice below marked **(prep)** answers a question the capture left open; each is listed again in the report for the person's approval session. The two the design review sent to the user are `Scope decision` and `Decided with the user` lines in the Problem.

### 1. The place (`z-nile/engine/approveplace.luau`, new)
A pure rule over what the edge read. A *copy* of the issue is its document, `check.sh`, specs and `approval.md` in one checkout or at one commit: whether it is `design: ready`, its slug, its contract hash (`contract.hash`), and whether its last approval row holds for that contract (`none`, `changed`, `holds`, `bad`).

- **Which worktrees are read** (the user's scope decision of 2026-11-15, "Only prep-<slug>"): the linked worktree on the branch `prep-<slug>` (the issue's slug, read from origin/main's copy; z-design step 1 makes that worktree), the worktree the command is run in, and the command's own (section 2). No other worktree is opened: a prototype, a mutation copy or a raft's worktree that carries a changed copy of the issue is never a place unless the command is run inside it. The main checkout is never a place.
- **A worktree's design is its own** when its copy is `design: ready` and its contract is none of: origin/main's (when main's copy is ready), the contract of a ready copy at the worktree's merge-base with origin/main, the contract of a ready copy origin/main held at any commit since that merge-base that changed the issue's folder. So a worktree that is only behind main, and a prep worktree left behind after its pull request was squashed onto main, hold nobody's design. A draft never counts as "main's design", whatever its text hashes to (the contract leaves the front matter out). This is the capture's "holds a newer one". **(prep)**
- **Waiting**: a read worktree with a design of its own whose approval does not hold. **Held for main**: a read worktree whose approval holds for the very contract origin/main holds ready and unapproved (a prep that merged before the person approved, the command's own worktree after a failed publish). **Held, own**: a design of its own whose approval holds; it is *pushed* when the worktree is on a branch whose `origin/<branch>` is at its `HEAD`. A worktree that holds an approval of any other design (a leftover of a failed publish after main's design was replaced, a merged prep) is nothing: it is never retried, pushed or published.
- `./zn approve <id>`, in order: a waiting worktree is the place and a new approval is recorded there (the one the command runs in before the prep worktree); else a worktree held for main, or held, own and unpushed, is the place and what it holds is published or pushed with nothing new recorded (so an approval is never recorded twice for one design); else origin/main is the place when its copy is ready and its approval does not hold; else, when main's approval holds, it prints `<id> is already approved on origin/main`; else, when a pushed, held worktree exists, `<id> is approved in <name>: it counts when its pull request merges`; else it refuses: `<id>: nothing to approve: it is not design: ready on origin/main, and the worktree of its prep branch (prep-<slug>) holds no design: ready of its own.` (or `it is not on origin/main, and no worktree of its prep branch holds a design: ready of its own.`).
- At most one worktree is on `prep-<slug>`, so more than one place can be meant only when the command is run inside another worktree that also holds a design of its own, and running it there says which. The capture's "refuses and names each" has no case left and nothing ever tells the person to change directory (the scope decision records this).
- `./zn approve <id> --publish` (the retry) never records: a held worktree (for main, or own and unpushed) is the place; then the two printed lines above; else `<id> has no recorded approval to publish. Run ./zn approve <id>.` It finds its place from anywhere. **(prep)**
- `--check` is unchanged and reads the checkout it runs in.

### 2. Recording, in the place
- Before anything is written the command prints `<id>: approving in <place>` (or `publishing from <place>` when it only publishes or pushes); `<place>` is the worktree's path from the main checkout (`.worktree/prep-<slug>`) or `origin/main`.
- **A worktree**: the engine starts itself there (`lune run <this checkout>/z-nile/engine/main -- approve <id> [--publish]`, working directory the place, `ZN_TOP` and `ZN_CWD` set as `./zn work` does for another worktree, `ZN_APPROVE_IN=<the place>`, the terminal inherited), and exits with its code. `ZN_APPROVE_IN` equal to the checkout's top makes that run act where it is and skip placement, and nothing else: the terminal, `ZN_DISPATCH` and agent-session refusals come before placement in every run, with the variable set or not, and a run that records still refuses the main checkout (`refuseInMainCheckout("approve")` stays for the run that acts). The code that records is c0283's, unchanged: the same preconditions (design: ready, open list ruled, `check.sh`, a committed contract, a committed record), the same `tracker: approve <id>` commit of `approval.md` and `provenance.md`. The engine that runs is the one the person invoked, not the place's own copy. **(prep)**
- **origin/main**: nothing is written in the main checkout or in the worktree the command ran in. The command makes a detached worktree of origin/main at `<main checkout>/.worktree/.approve-<id>` (a name `./zn worktree` cannot make, so no person's worktree is ever in the way), records there, and removes it (`git worktree remove`, no force) once the approval is published. This is what "stays recorded locally" needs when the publish fails. A path taken by anything else (a folder that is no worktree, a worktree on a branch, one with changes) is refused, naming it; a clean detached one left by an earlier failure is moved to origin/main and reused. **(prep)**
- A repository with no origin has no origin/main to compare: `approve` records in the checkout it runs in and publishes nothing, as #295 does today (its main-checkout refusal already applies only with an origin).

### 3. Making it count, in the same command
After recording (and alone for a held approval or `--publish`), in the place:
- **Publishing off** (`PICKMAN_PUBLISH=0`, or inside a check): nothing leaves the machine. The record stays where it is, and the command fails with the line below (`publishing is off`), so the command's worktree is kept and the retry finds it.
- **Published** when origin/main's copy is `design: ready` and its contract is the one approved: one `tracker: approve <id>` commit through `publish.commit` that holds origin/main's `approval.md` with this approval's row appended (never the worktree's file, so a row main has is never lost) and, as c0283 does, origin/main's record with the approved row appended. It prints `published <id> to origin/main: it counts now`; when origin/main's last row is already this one, `<id> is already approved on origin/main`.
- **Pushed** otherwise: `git push origin HEAD:refs/heads/<branch>`, printing `pushed <branch>: the approval counts when its pull request merges`.
- **A failure** (publishing off, the publish, the push, a place on no branch) leaves the commit, exits 1 and prints `<id>: approved in <place>, but it does not count yet: <reason>. Retry: ./zn approve <id> --publish`. `<place>` is the worktree's path, or `a worktree of origin/main`. Nothing retries by itself.
- The record line comes after the place line and before the count line: `approved <id> <hash> in <place>`.

### 4. The texts
- `approval.reasonOf`: `<id> has no approval: run ./zn approve <id> in a terminal, from anywhere in the checkout. This is a one-time step for an item prepared before approval.`; the changed-contract line ends `Run ./zn approve <id> again.`
- The refusals in `zn` and `cmd.approve` (no terminal, `ZN_DISPATCH`, agent session) end at `in a terminal.` / `in your own terminal.`: no worktree is named. No refusal of this command tells the person to go into a worktree.
- zz-rules' approve row (which worktrees are read, the placement, the publish, the push, the command's worktree, the held approval, the retry; "in the worktree where the design is" goes), z-design step 5, z-ready's approval bullet, AGENTS.md's Design approval line and the comment in `tests/lib/seal.luau` say one command from anywhere. The docs spec pins each and the absence of the old wording.

### Scalability
One `git fetch origin main`, one `git worktree list`, origin/main's copy (a registry read, one `ls-tree`, a `show` per contract file), and at most three worktrees' copies (files of the issue's folder). For a read worktree whose ready contract is not main's: a `merge-base`, that commit's copy, and one copy per commit of origin/main that changed the issue's folder since (a handful for an issue in prep). Nothing grows with the number of worktrees. Measured read-only on this repository (198 worktrees) with the prototype's `load` and `choose`: 0.08 to 0.15 s of CPU per issue (E5).

### Maintainability
The rule is one pure function with its own spec; the reads are three functions in the same module; `cmd.approve` keeps c0283's recording and publishing bodies and gains the placement block, the push and the appended row. A new kind of place is a new `Choice.kind`.

### Usability
`./zn approve <id>`: one line from anywhere; it says where it acts before it records; every refusal names the id and what to do (the path in the way, the retry command) and none sends the person into a worktree. Usage text: `approve <issue-id> [--check|--publish]`, unchanged. Lists a command joins: none new (`approve` is already in the usage text; the main checkout's list of writers in AGENTS.md is unchanged, since approve does not write the main checkout).

## Acceptance criteria

### Checked
- AC1: `approveplace.choose` takes a read worktree whose design is its own (not main's, not a ready copy's at its merge-base, not one main held since) with no matching approval, the one the command runs in before the prep worktree; otherwise a worktree that holds an approval of main's unapproved design or an unpushed approval of its own design, with nothing new recorded; otherwise origin/main when its ready design has no matching approval; never a worktree whose record is of a design that is nobody's; `--publish` never records; and it says `approved`, `pushed` or refuses by the texts of section 1, none of which sends the person into a worktree.
- AC2: run from the main checkout, from a worktree that is only behind main, and inside a worktree that left main before the design was replaced, `./zn approve <id>` on a design merged to origin/main with no matching approval says `approving in origin/main`, records and publishes in one command (one `tracker: approve <id>` commit on origin/main with `approval.md` and the approved row, the place, record and published lines in that order), commits nothing in the main checkout or the worktree it ran in, leaves no worktree of its own, says `already approved` when asked again, keeps the terminal, `ZN_DISPATCH` and agent-session refusals before anything is made (with `ZN_APPROVE_IN` naming the main checkout too, where a placed run is refused), refuses a taken `.worktree/.approve-<id>` by name, and is not stopped by a person's `.worktree/approve-<id>`.
- AC3: run from the main checkout on a design that exists only in the worktree of `prep-<slug>`, it says `approving in .worktree/prep-<slug>`, commits the approval on that branch, pushes it, leaves origin/main and the main checkout as they were and prints that it counts when the pull request merges; a draft on main with the same text takes nothing; asked again it says where the approval waits; a redesign there is approved there while main holds the older approved design; a prep worktree whose design main already held is not taken.
- AC4: a worktree on any other branch that holds a ready design of its own (a prototype) is never read from elsewhere: it is not approved, not pushed and not named, with the prep waiting or approved; run inside it, the command records there.
- AC5: with publishing off, or when the publish or the push fails, the command exits non-zero, the commit stays where it was recorded, and the output says it does not count yet and names `./zn approve <id> --publish`; that retry, and the plain command asked again, publish or push the same row from another checkout with no second approval, and the command's worktree is removed after it; a record left by a failed publish of a design main has since replaced is never retried (the retry says there is none, the plain command approves main's design); an approval a prep holds for the design that reached main without it is published as it is, appended to main's rows, none of which is lost.
- AC6: zz-rules, z-design, z-ready, AGENTS.md, `tests/lib/seal.luau` and the refusals the tooling prints state the one command from anywhere, and none names a worktree to run in or a second command.
- AC7: the specs that read approve stay green (c0283's `approval.spec` and `publish.spec`, the narrowed `approve.spec` and `docs.spec`, `tooling/approve.spec`, `tooling/approve-publish.spec`, `tooling/readycheck.spec`, `tooling/work.spec`), and the real tree's `./zn audit` and `./zn lessons --check` pass.
