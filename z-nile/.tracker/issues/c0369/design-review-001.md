### F1 [high] A recorded approval is retried whatever design it was for: a stale worktree takes over the plain command and `--publish`, and can rewrite main's `approval.md`
Where: c0369.md Design §1 ("**Recorded** worktrees: approval `holds` and its last row ... is not a row of origin/main's `approval.md`", and the order "else one recorded, unpushed worktree is the place"); prototype `approveplace.luau` `unpublished` and `choose`; `main.luau` `count()`.
Evidence: `unpublished(main, w)` only asks whether the worktree's own last row holds for *its own* contract and is missing from main. It never asks whether that contract is the worktree's own design or main's. `choose` checks `#recorded > 0` before "approved". I ran `approveplace.choose` from the prototype:
- A detached `.worktree/approve-c0001` left by a failed publish of design `old` (row r1). Main was later redesigned to `new` and approved (r9). Then `choose(..., false)` and `choose(..., true)` both return `worktree .worktree/approve-c0001`. In that worktree `count()` finds main's contract differs, so `approval.refusal` is nil and it goes to `pushBranch()`, which fails with "on no branch". The command exits 1 with `approved in a worktree of origin/main, but it does not count yet ... Retry: ./zn approve c0001 --publish`. The retry does the same thing. From then on, every `./zn approve <id>` on an issue that is approved fails until the person finds and removes the worktree by hand. The design's own failure path (§2 "kept after a failure") creates exactly that worktree.
- A stale prep worktree that holds an older approved design `A` (r1, never published; `landed = true`) while main holds `B` approved (r2). The plain command returns `worktree .worktree/stale`. `count()` then pushes that stale branch to origin and prints `pushed ...: the approval counts when its pull request merges`, which is false.
- c0283's own case, which the Checklist's "Existing work" says is "found by `--publish` or by the plain command". The prep merged before approval (main ready `A`, no approval) and the human recorded r1 in the prep worktree under the old flow. The plain command returns `main origin/main`. It records a **second** approval r2 in a scratch worktree and publishes that, while the prep worktree keeps r1. The next plain `./zn approve` (main holds `A` with r2) returns `worktree .worktree/prep`. `count()` there finds the contract the same and `onMain ~= localText`. It then publishes the prep's whole `approval.md` (r1). publish.luau:491-500 accepts `approval.md` "whole", so main's row r2 is replaced. The provenance row is skipped as `seen` (same actor and detail). The output says `published ... it counts now` for an issue that was already approved.
Critique: the "retry" set includes approvals of designs that are nobody's to count. The tempting fix is "skip recorded worktrees once main holds". That still leaves the S2 case (a second approval instead of publishing the held one) and the infinite-retry loop with `--publish`.
Consequences: a recorded worktree whose contract is main's current ready contract is the c0283 use case and should be published as is, not re-recorded. One whose contract is neither its own design nor main's is stale and must be ignored, but the person may still want to know about it. Comparing rows by `(when, who, hash)` stops being the right test of "main already has it": by hash, a main that holds the same contract has it.
Recommendation: define *recorded* as `holds` **and** (`own(main, w)` **or** (`main.ready` and `w.copy.hash == main.hash` and `main.state ~= "holds"`)). Order the plain command so that a recorded worktree holding main's own unapproved contract is published before a new approval is made on main ("no second approval", as AC5 already says for the retry). Treat a stale recorded worktree as not a place. Optionally name it in the `already approved` line, but never push it or publish it. Add place.spec cases for (a) a stale scratch left by a failed publish after main was re-approved: `approved`, for both modes; (b) a stale prep with an older approved design: `approved`; (c) a recorded worktree on main's own unapproved contract: that worktree is taken for the plain command, not `main`. Add an approve.spec case that ends with main's `approval.md` unchanged and `already approved` after a stale record exists. Add the mutants "recorded ignores own/main" and "main first over a recorded same-contract worktree".
Lesson: z-design/new-rules-migrate-existing-work

### F2 [high] "A design of its own" cannot tell a prep worktree from a prototype: on today's repository `./zn approve c0283` would approve and push `.worktree/proto-c0283-publish`
Where: c0369.md Design §1, the first bullet and "Every linked worktree of the repository is looked at"; E5 ("the rule was not run against the real repository").
Evidence: I ran the prototype's `approveplace.load` and `choose` read-only against the real worktrees (188 in `git worktree list`). For `c0283` (active, approved on main), 36 worktrees hold a ready copy whose hash differs from main's. The result is `worktree .worktree/proto-c0283-publish`, because the prototype added `acceptance/publish.spec.luau` and mutants to c0283's folder (`git diff --stat $(git merge-base origin/main HEAD) HEAD -- '*c0283*'` there: 10 files). That gives it a contract of its own, `changed` against its approval. The child would record a human approval of a prototype's contract on the prototype branch and `git push` it (the probe saw `pushed = true` for that branch). The same holds for any redesign of an issue that is ready on main: z-design's prototypes and `*-mut` copies carry the issue's specs (mutants.py's docstring: "with this issue's specs copied into z-nile/.tracker/issues/c0369/acceptance"). Then either the prototype is taken, or the prep is refused as "more than one worktree" alongside it.
Critique: this is an authority problem as well as a wrong place. The human approves a contract they never reviewed, and nothing shows it before it is recorded and pushed. The tempting fix is to skip `proto-*` names. That is a deny list, and the next convention (`*-mut`, `raft-*`, review copies, dispatcher worktrees) gets through it.
Consequences: whatever marks "the prep" is a rule other commands must keep true: zz-rules' `prep-<slug>` branch name, which z-design step 0 already makes (`./zn worktree prep-<slug>`). A prep made under another name is then found only when the command runs inside it, which §1 already allows. The c0369 fixtures (`prep-one`, `prep-two`, `left-behind`, ...) would need slug-based names. Since this reads the capture's "the one worktree under `.worktree/` whose checkout holds the issue `design: ready`" more narrowly than its literal words, it needs the user's word.
Recommendation: escalate to the user: (a) a worktree is a place only when its branch is `prep-<slug>` (the issue's slug), or `approve-<id>` for a retry, or the command runs inside it. This is cheap (F7) and matches zz-rules. (b) Keep the content rule but exclude a named list (`proto-*`, `*-mut`, `raft-*`, `R*/…` layer branches). Cost: a list to maintain, and misses fail silently. (c) Keep the content rule as is. Cost: prototypes are approved and pushed, as the c0283 probe shows. Whichever is chosen: print the place and the contract hash **before** recording, and add place.spec and approve.spec cases with a prototype worktree that carries a changed copy of a ready issue (not taken, or named in the refusal for (c)). Record the ruling as a `Decided with the user` line.
Lesson: z-design/new-rules-migrate-existing-work

### F4 [high] The several-worktrees refusal tells the person to change directory, which captured outcome 3 and AC6 both forbid
Where: capture's added outcomes ("When more than one place could be meant, it refuses and names each"; "The person never has to be told a worktree path or change directory to approve"); Design §1 ("several are refused, naming each ... unless the command runs inside one of them"); prototype `approveplace.luau:113`; AC6.
Evidence: the refusal (probe output) is `c0001: more than one worktree holds a design of its own with no matching approval: .worktree/prep-a, .worktree/proto-a. Run ./zn approve c0001 inside the one you mean, or remove the others (git worktree remove <path>).` AC6 says no refusal "names a worktree to run in". docs.spec only checks six fixed old phrases, so it passes. The way out the design offers is exactly what outcome 3 says the person never has to do. c0299's `./zn approve <worktree>` form, which would resolve it, is "not carried ... and is not built".
Critique: outcome 2 (refuse and name each) and outcome 3 (never change directory) can both hold only if the refusal can be answered from where the person stands. The tempting fixes reword the refusal (the same cd under other words) or drop "unless the command runs inside one" (that removes the only way through).
Consequences: a selector argument is a new CLI surface (usage text, `zn` wrapper parsing, the f0339 page). It must refuse a name that is not among the candidates and must not let `--check` and `--publish` mix with it wrongly.
Recommendation: escalate to the user: (a) add a selector, e.g. `./zn approve <id> --in <name>`, accepted only when `<name>` is one of the refused candidates, printed in the refusal as the command to run. place.spec gets a case for each of: a named candidate taken, a non-candidate refused, and `--publish --in`. (b) Keep the cd advice and record a `Scope decision` that outcome 3 does not hold when several designs exist. Cost: the user's words "should not be my problem" stay unmet in that case. Either way, AC6 must state the rule so a docs.spec case can fail on the refusal's text.

### F5 [medium] `PICKMAN_PUBLISH=0` no longer keeps the plain command offline: a merged design is published to origin/main anyway
Where: Design §3 ("With `PICKMAN_PUBLISH=0`, or inside a check, it prints `not publishing: <branch> is not pushed`", for the push only); prototype `main.luau` `count()`.
Evidence (read, not run): `pushBranch()` tests `publishing()`. The origin/main branch of `count()` goes straight to `refuseStale()` and `publish.commit(...)`, and `publish.luau` has no `PICKMAN_PUBLISH` test (`grep -n PICKMAN_PUBLISH z-nile/engine/publish.luau`: no hit). Before c0369 the plain `approve` never published. Now a person or fixture with `PICKMAN_PUBLISH=0` and an origin has `./zn approve <id>` push a `tracker: approve` commit to origin/main. Every other publishing command refuses or stays local under that variable (`needs an origin remote (PICKMAN_PUBLISH=0 disables it)`, main.luau:1819, 1865, 2295 ...).
Critique: the tempting fix is a bare `if not publishing() then return end` in the main path. Then the parent sees `ran.ok` and removes the scratch worktree, and the recorded approval is silently lost.
Consequences: with publishing off, the main path must keep the scratch worktree (or not make one) and say where the record waits, and the retry must find it.
Recommendation: in `count()`, when `publishing()` is false on the origin/main path, print `not publishing: <id> is approved in <place> and not published` and exit non-zero (or exit 0 with the worktree kept, but say which), so the parent keeps the scratch. Add an approve.spec case with `PICKMAN_PUBLISH=0`: origin/main's commit count unchanged, the scratch kept, and `--publish` without the variable publishes the same row. Add a mutant "the main path ignores PICKMAN_PUBLISH".

### F6 [medium] `ZN_APPROVE_IN` is a new variable on the approve path with no spec that it lets nothing through, and it re-opens writing the main checkout
Where: Design §2 ("`ZN_APPROVE_IN` equal to the checkout's top makes that run act where it is and skip placement; it lets nothing through"); Rules and mutants row "the refusals ... come before anything is made" (`reasoned`); zz-rules' approve row ("with no flag, option or variable that lets one through").
Evidence: approve.spec's refusal case never sets `ZN_APPROVE_IN`. A mutant that guards the refusal block with `if not onlyCheck and process.env.ZN_APPROVE_IN == nil then` survives every listed case. The row is `reasoned` as "not one text to replace", but that one-line mutant is a text to replace. The refusal case already asserts `fs.isDir(scratch) == false`, which would also kill "placement before refusals". Also, with `refuseInMainCheckout("approve")` removed, `ZN_APPROVE_IN=$PWD ./zn approve <id>` in the main checkout (and any repository with no origin, §2's last bullet, "as today", which is no longer true: today it is refused) commits `approval.md` in the main checkout. AGENTS.md says only `./zn`'s ready/stop/sync may write there.
Critique: c0283's guard exists so that no variable lets an agent through. A new variable that no spec pins is the first thing an executor will simplify. The tempting fix is "document it". That does not pin it.
Consequences: whether an empty or foreign `ZN_APPROVE_IN` is refused, and whether the main checkout stays refused when the variable names it.
Recommendation: add approve.spec cases: `ZN_APPROVE_IN=<main checkout> CLAUDECODE=1` (refused, nothing made), `ZN_APPROVE_IN=<main checkout>` with a terminal (refused: the main checkout is never written, keeping `refuseInMainCheckout` for the placed run), and `ZN_DISPATCH=1` under `ZN_APPROVE_IN`. Change the row to `run` with the two mutants above. Correct §2's "as today" for the no-origin case, or keep that case refused in the main checkout.

### F7 [medium] The scalability claim is unmeasured and its numbers are wrong for this repository: 188 worktrees, 5 to 10 s of reads before anything happens
Where: Design "Scalability" ("On this repository (about 90 worktrees) ... a few file reads"); E5.
Evidence: `git worktree list | wc -l` = 188. The probe's `load` + `choose` against the real repository: c0369 2.2 s CPU (73 worktrees hold it), f0148 5.1 s (187 hold it, 186 ready, all main's hash), c0283 10.2 s (185 hold it, 36 need `merge-base` + `atRev` + history reads). That is before `git fetch`, the child's own start and the publish. `inTree` builds a full contract (`approval.collect`) for every worktree that holds the issue, which on a backlog issue is nearly all of them, because each checkout holds every issue.
Critique: the cost grows with every worktree left behind, and stale worktrees are this repository's norm. `--publish` pays it again. The tempting fix is to parallelise the reads. That keeps the linear cost.
Consequences: a cheap first filter has to agree with the contract reader (lesson zz-arch/records-cover-what-was-reviewed: whatever the filter compares must cover every file the contract hashes, including promoted specs).
Recommendation: if F2 resolves to a name rule, the scan reads one or two worktrees. Otherwise compare each worktree's tree id of the issue folder (`git -C <wt> rev-parse HEAD:<dir>` plus `git status --porcelain -- <dir>`) with main's and the merge-base's before building a contract. Record the measured time on this repository in E5, and add a place-level case where a worktree whose folder tree equals main's is never built.

### F8 [medium] `.worktree/approve-<id>` is already the name people use, on a branch, so the scratch path is "in the way" for those ids
Where: Design §2 ("A path already taken (... a worktree on a branch ...) is refused, naming it").
Evidence: the real repository has `.worktree/approve-f0148` on branch `approve-f0148` (cf22eaea4 `tracker: approve f0148`), made by hand with `./zn worktree approve-f0148`, the way c0283's main-checkout refusal (`cd "$(./zn worktree <target>)"`) sends people. Under c0369, any later approval of f0148 placed on origin/main (a contract change after done, zz-execute step 5) refuses with `... is in the way (a worktree on a branch, or with changes): remove it`. That is a manual step and a worktree to delete, which the Problem says should not be the person's problem.
Critique: the tempting fix is to reuse a branch worktree. That would commit on someone's branch.
Consequences: a name that `./zn worktree` cannot produce, and a cleanup rule for a failed run's leftover.
Recommendation: put the command's worktree where no person's worktree goes (e.g. `.worktree/.approve-<id>`, or `.cache/approve-<id>` if `worktree-prune` and the guards allow it). Keep it detached and reuse only a clean detached one. Pin the name in approve.spec, with a case where `.worktree/approve-<id>` on a branch exists and the command still publishes.
