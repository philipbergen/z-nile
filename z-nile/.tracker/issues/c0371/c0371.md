# c0371: Check paths reads homes right

## Problem
- z-nile's full gate is red on main on `tests/acceptance/c0120/check-paths.spec.luau` since preps f0201 (#392) and c0292 (#414) merged on 2026-11-15, although both `check.sh` files are right.
- The spec refuses a path read from the item's home (arcade's `src/shared/Logic/PaidPlay/init.luau`, `tests/unit/PaidPlay`) when the Touched entry that covers it is written as a repo path (`arcade/src/shared/Logic/PaidPlay`).
- The spec reads a command after `cd "$ZN_ROOT"` from the item's home, so c0292's `(cd "$ZN_ROOT" && lune run z-nile/roots -- --luau-dirs)` is reported as `z-nile/roots` and `z-nile/roots.luau` missing from `z-nile/`.
- The spec reads quoted text searched for by a helper other than `grep` or `rg` as a path (c0292's `has "$L" ... "`tests/run`"`).
- The red spec blocks every finish whose watch selects it (R0099's c0263 layer).

Scope decision (user, 2026-11-15): "Full scope (Recommended)": the search-helper rule detects a check's search helpers from their definitions in the same check.sh (has, g, words, has_all) and reads their quoted arguments as text across line continuations.
Scope decision (user, 2026-11-15): "Capture its own issue (Recommended)": finished.spec's misreadings are c0374, not c0371.

## Non-goals
- finished.spec's misreadings of check.sh files are c0374 ("finished-spec-reads-homes-right"), not c0371.
- No `check.sh` of f0201, c0292 or any other item is edited to make the spec pass.
- No path is looked up from a second place when it is missing from where its command runs, so c0120 AC11 keeps reporting every case it reports today.
- The way items write their Touched entries does not change.
- d0362 is not reopened, since it no longer reproduces after #388.

## Solution
- A path in a check that is missing from where its command runs passes when a Touched entry covers it, whether that entry is written as a repo path or as a path from the item's home.
- A path in a command that follows `cd "$ZN_ROOT"` in the same command list or subshell is looked up from the repo root, and every other path is looked up from the item's home only.
- Quoted text passed to a check's own search helper, as c0292's `has` is, is not read as a path.
- A path that is missing from where its command runs (the item's home, or the repo root after a cd there) and is covered by no Touched entry is still reported, even when it exists somewhere else in the repository.
- The spec's fixture still reports z-nile's `test -f src/server` although `pickman/src/server` exists, and reports a z-nile check that runs `git diff --quiet -- scripts/…` with no cd when that path is missing from `z-nile/`.
- `tests/acceptance/c0120/check-paths.spec.luau` passes on main with f0201's and c0292's `check.sh` files unchanged, and z-nile's full gate is green.

## Design
The c0120 spec (`z-nile/tests/acceptance/c0120/check-paths.spec.luau`) keeps its scan functions local, so nothing else can test them. The chore moves them into a module and fixes the scan there, so c0371's cases (and the promoted spec) read one implementation.

**Moves** (own renames-only commit first): `TOP`, `RESTAMPED`, `PREFIXES`, `FILES`, `FOLDERS`, `blob`, `substituted`, `patternWords`, `literals`, `present`, `touched`, `under`, `items`, `scan` go verbatim from the spec to `z-nile/tests/acceptance/c0120/check-paths-scan.luau` (a helper module beside `finished.luau`, `rewrites.luau`), which returns `{ TOP, blob, RESTAMPED, literals, present, touched, under, items, scan }`. The spec requires it as `./check-paths-scan`; c0371's spec as `@tests/acceptance/c0120/check-paths-scan`. The fixture helpers (`FX`, `REGISTRY`, `put`) stay in the spec. Then the change commit. `experiments/prototype.patch` is the prototype's diff of the two files (the moved module with the changes below; it makes the live tree pass).

**Changes to the scan** (`z-nile/tests/acceptance/c0120/check-paths-scan.luau`):
1. `literals(text): { Lit }` with `type Lit = { path: string, root: boolean }`. `root` is true when the word follows `cd "$ZN_ROOT"`, `cd "$ZN_ROOT/<sub>"` (then the path is `<sub>/<word>`) or `cd "$(git rev-parse --show-toplevel)"` on the same line, until an unmatched `)` closes the subshell (count `(` and `)` in the line between the cd and each word) or the line ends. A literal `cd <dir>` keeps its old meaning (`dir/` prefix, home). The first test of the spec reads `.path`.
2. `scan` looks a literal up with `present(base, if lit.root then "." else home, lit.path)`. A literal missing there is exempt only if `under(lit.path, own)` or `under(repoPath, own)`, where `repoPath` is `lit.path` for a root literal and `<home>/<path>` otherwise (the Touched entry written as a repo path, which is how nearly all items write it, or from the home). No path is looked up from a second place (Non-goals): `src/server` of a z-nile check stays missing though `pickman/src/server` exists, and an entry for `pickman/src/server` does not cover z-nile's.
3. `patternWords` also marks a word directly after `\`` preceded by a backslash (a Markdown code span inside a quoted argument: c0292's `"\`tests/run\`"` given to its helper `has`) as text, in `literals`, before the path test: `string.sub(line, starts[i] - 2, starts[i] - 1) == "\\`"`.
4. `patternWords` marks the argument of `echo` (after its options; a quoted argument to its closing quote) as text. Found by the prototype, not in the capture: after 1 to 3, c0292's `echo "z-nile/roots --luau-dirs no longer lists z-nile/.tracker"` was still reported (E2), and the capture's outcome is that main's gate is green.

**Decision on 3 (generalise or narrow).** Generalising to "every argument of any helper the check defines" would need the scan to parse function definitions and line continuations (c0292's call is spread over lines, the scan reads one line at a time), and would blind it to real paths passed to helpers (`typecheck src/x`, `spec c0001 src/y`; the 15 helper names in live checks differ in what their arguments are: `g` takes the pattern first, `has` the file first). A rule keyed on the helper's name (`has`) fails the first check that names its helper otherwise. The narrow rule keys on what marks the text as prose and works across continuation lines: the escaped backtick that opens a code span inside double quotes, which is how a check writes a Markdown literal (every live instance: E3). It leaves an unquoted/plain quoted literal given to a helper (`has "$L" "tests/gone.md"`) read as a path, as before; the spec case pins that (the check writes prose in a code span, as c0292 does; zz-test says so).

**No behaviour change** for players or for the gate beyond the scan: nothing outside `z-nile/tests/acceptance/c0120/`, `c0371`'s own specs and one skill sentence changes. **Existing work:** every change makes the scan report less, except rule 1's root reading, which can report a path after `cd "$ZN_ROOT"` that exists from the home but not from the root. The live tree has none (the spec passes on it, E4), and a check.sh in an open prep worktree is read the same way when it merges (E5, reasoned). **Shared state:** no counter or registry is touched. **Restated rules:** `z-nile/skills/zz-test/SKILL.md`, "Every literal path resolves from its home" (line 78), gains the sentence: a Touched entry may be written as a repo path or a path from the home; a command "after `cd "$ZN_ROOT"` is read from the repository root" until its subshell closes; a word "inside a code span" of quoted text and "an `echo` message" are prose. AC4 pins the four phrases. The spec's own header comment changes with the code. **Guards:** nothing near the repository guards, the publisher or the gate; the scan only reads, and fails closed in that a missing path is still reported.

### Scalability
The scan is linear in the lines of the check.sh files, one pass per line, as before; the paren count adds a scan of the text between a cd and each following word on the same line, which is bounded by the line.

### Maintainability
One module holds the scan (it was a 300-line block inside a spec); the spec and c0371's cases share it, so a rule is changed in one place with its case beside it. Rules 3 and 4 are two small marks in the places that already mark text (`patternWords`, the word loop).

### Usability
An author of a check.sh writes Touched entries as repo paths, as the template says, and names the files their work creates from their home without the spec refusing them; the report now names where a path was looked up (`from the repository root`).

## Unknowns & experiments
- E1 (run): what does the prototype read from each form of cd? `experiments/E1-literals.luau` prints it: `(cd "$ZN_ROOT" && lune run z-nile/roots ...)` gives `z-nile/roots.luau` at the root; `cd "$(git rev-parse --show-toplevel)"` the same; after the closing paren the path is the home's. Pass.
- E2 (run): with rules 1 to 3 only, is the live tree green? Fail: c0292's `echo "z-nile/roots ..."` was still read (a fourth misreading). Fallback was a Touched exemption (wrong, it is not work to create). Rule 4 added; the live tree then passes.
- E3 (run): is the escaped-backtick span the only quoted-prose form in live checks? The live scan reports only c0292's `"\`tests/run\`"` before the fix and nothing after, so no other live check needs a rule for prose (a bare quoted path given to a helper would have been reported too). Pass.
- E4 (run): the spec with the prototype on this tree: `lune run tests/run -- tests/acceptance/c0120/check-paths.spec.luau` 4 passed, 0 failed; the whole c0120 folder was loaded by the same runner. The three reported misreadings and the echo are gone; f0201's and c0292's `check.sh` unchanged (AC3).
- E5 (reasoned): whether a check.sh in one of the 143 open prep worktrees reads a path after `cd "$ZN_ROOT"` that exists only from its home. A recursive grep over the worktrees hit the 120 s limit; the spec's live scan covers main, and a prep that still has such a line is told by the spec on its own PR (a path after the cd, named from the home, is a real mistake: the command runs at the root). Fallback: that prep fixes its line.
- E6 (reasoned): a `(` or `)` inside quoted text between a cd and a word miscounts the subshell depth. It ends the root reading early (the word is then read from the home): a false report at worst, never a missed one. No live check does it (E4).
- d0362 (same spec, c0283's `zn find` fallback) does not reproduce since #388 prefixed `$PWD`; not folded in.
