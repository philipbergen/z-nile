# c0386: Promoted c0371 spec trips fence scan

## Problem
- On origin/main cd308d633, `z-nile/tests/tooling/repo-fence.spec.luau` and the `tests/meta/fence.spec.luau` of all six project homes (pickman, arcade, portal, snake, invaders, asteroids) fail with "checks must not override the repository guards: z-nile/tests/acceptance/c0371/check-paths-homes.spec.luau names env -i", because line 694 of that promoted spec holds the fixture text `env -i grep -qF "src/nothing" "$F"`.

## Non-goals
- The fence scan's ban on `env -i` is not loosened for any other file, no new spec case is added for c0371's accepted limitation that an unlisted introducer leaves a helper's arguments read as paths, and the gate hole that let the spec land is left to c0387.

## Solution
- The promoted spec no longer trips the fence scan (the fixture text is built from parts, or the spec gets an ALLOWED entry in `repo-fence.spec.luau` with its reason), its case "grep's pattern is text as main reads it" still asserts that an unquoted `grep` after `env -i` gives no findings, and all seven fence specs pass on main.

## Design
Verified again on origin/main 9947d2d8b (2026-11-15, prep worktree): `z-nile/tests/tooling/repo-fence.spec.luau` fails 1 of 10 cases, "no spec, check.sh or script switches a guard off or points git elsewhere", with `z-nile/tests/acceptance/c0371/check-paths-homes.spec.luau names env -i`, and `./zn check c0386` shows the same failure in the six homes' `tests/meta/fence.spec.luau` (they `require` the same spec). The literal is line 694, one entry of the list in the case "grep's pattern is text as main reads it: an unquoted grep after git, a wrapper or an option (review 004 F1)".

**The fix: build the fixture text from two literals.** Line 694 becomes
```luau
-- in two parts: the repository fence scan bans the literal in a file that runs as a check (c0386)
"env " .. '-i grep -qF "src/nothing" "$F"',
```
The value handed to `findings` is byte for byte the old one, so the case tests exactly what it tested; nothing else in any file changes (`experiments/prototype.patch`, +2/-1).

**Why not an ALLOWED entry.** The scan (`repo-fence.spec.luau`, NAMES and `bannedIn`) exists to keep every file that runs as a check from naming a way to switch a guard off; `env -i` is on NAMES because an `env -i` start drops the fence's environment (`GIT_CEILING_DIRECTORIES`, `GIT_CONFIG_*`, the run markers). ALLOWED is for a file with "a real need to name one" (zz-test skill, Gate spec), and each entry is file-wide for that name: an entry for c0371's spec would also let a real `env -i` start, added to that spec later, pass the scan. This spec never runs `env`; it only hands the words to a pure scanner. Lesson zz-test/narrow-guard-allowances asks for the narrowest allowance, and lesson zz-test/dry-run-promoted-specs-under-the-guard-scan says "Prefer building a guarded name from parts in a spec that only quotes it"; `repo-fence.spec.luau` does the same for its own planted texts ("built by concatenation so this file names none of it", line 616). The Non-goal "the fence scan's ban on `env -i` is not loosened" is kept to the letter: no allowance anywhere. Rewording the command (another env option, or dropping `-i`) was rejected: `env grep` without an option is already the `env` row of the introducer case (line 389), so the option is what this entry adds, and another option (`-u NAME`) would change what is tested.

**What the case guards, and why the rebuilt entry still guards it.** `z-nile/tests/acceptance/c0120/checkpaths.luau` line 602 reads a grep's pattern as text when grep is in command position **or unquoted**; after `env -i`, grep's previous word is `-i`, which is neither an introducer nor a `-…c` option, so only the `or unquoted` branch reads `src/nothing` as text. Dropping that branch (the regression of c0371 review 004 F1) turns the case red, and it still does when the list holds only the rebuilt entry (E2).

**Why the lesson did not catch it.** zz-test/dry-run-promoted-specs-under-the-guard-scan (4 sources before this prep) asks the designer to run the scan with the specs at their promoted place after every edit round. c0371's text came in from design review 004 F1, the very pattern the lesson's Why describes. No c0371 document or R0112 document records a guard-scan run; R0112's "promotion dry run" (RC0) was `./zn promote-check`, which type-checks and runs `tests/meta` but runs no guard scan; and `./zn done`'s affected gate selected no fence spec (c0387). The lesson's question was simply never asked, and nothing visible showed it missing. The harvest sharpens its check to ask for a *recorded* run in Unknowns & experiments that a reviewer can see is absent (`harvest.md` note). A mechanical check (promote-check running `repo-fence.spec.luau` over the copied files) would be a tooling change outside this scope; it is offered to the session lead as a candidate capture, not designed here. This prep ran the dry run itself (E3), and it caught this chore's own new spec naming the option in a header comment.
