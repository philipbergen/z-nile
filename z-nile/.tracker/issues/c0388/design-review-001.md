### F1 [high] AC2 cannot tell whether c0042's cli spec checks issue folders at all: a spec with its issue half deleted passes every check
Where: acceptance/roots.spec.luau:126-133 (case "c0042's cli spec takes its folders from the module and names no tracker root itself"); c0388.md Rules and mutants, row "the cli spec uses the module and keeps no list" (M12, M13); Design, The change ("a loop over `found.issues` asserting `m.home[id] ~= nil`"); AC2.
Evidence: case 6 pins three strings: `require("./ondisk")`, `ondisk.items(TOP)` and `t.expect(rafts).toBe(#found.rafts)`. It also pins that `.tracker/` and `fs.readDir` are absent. None of them is in the issue half. In the replay, mutant R1 deleted the three lines `for _, id in found.issues do … end` from the patched cli.spec. Mutant R2 changed the loop to `for _, id in found.rafts do`, which passes because `m.home` holds raft ids too. Both gave cli.spec 3 passed and roots.spec 6 passed, so AC1, AC2 and AC3 all pass. The capture asks for the counting "for rafts and for issues", and the Design says the spec loops over `found.issues`. No check fails when that loop is gone.
Critique: a captured outcome (issue folders are counted from every registered root) can be dropped by a wrong implementation without any check failing. The tempting fix is a single `string.find(text, "found.issues")`. That still passes R2 if `found.issues` survives in a comment or in an unused local.
Consequences: the new pins are exact text, like the case's existing three. Any rewording of the loop, F2's included, must change the pins in the same commit, or AC2 goes red on a correct spec. One mutant is still left to the code reviewer: a loop that is present but asserts nothing.
Recommendation: case 6 also asserts that the cli spec text contains the issue loop's header (`for _, id in found.issues do` today) and its lookup (`m.home[id]`), using the final text F2 settles on. Add rows M17 (the issue half deleted) and M18 (the issue loop walks `found.rafts`) to the Rules and mutants table, add both mutants to mutants.py, rerun it (18/18 killed on an assertion), and update E4.

### F2 [medium] The rule "an issue folder with no document is listed" rests on a false claim: the page drops such a folder, so the case goes red on it
Where: Design, The change ("one with no document is listed (the page shows it)"); prototype.patch line 75 (ondisk.luau's header: "a folder with no document is listed (the page shows it)"); roots.spec.luau:45-47; guesses.md G1 ("a folder with no document still counts"); Rules and mutants row "an issue with no document is listed" (M16).
Evidence: `board.luau:196` adds a folder only when `isId(name) and fs.isFile(doc)`, where doc is `<dir>/<name>/<name>.md`. `m.home` is built only from those items (`board.luau:1044-1047`). So the page does not show a doc-less folder, and `ondisk.items` lists it. In the replay, an issue folder holding only an ignored file turned the case red at `cli.spec:70: expected true, got false`, and the message did not name the folder. The raft half has the same rule without saying so: `ondisk.items` counts every `^R%d%d%d%d$` folder whether or not it has a document, while the page counts only those that do. Such folders arise from ignored files left in an item folder after a move (`.gitignore` ignores `.cache/` anywhere and `rafts/active/*/prompt.md`; AGENTS.md has `./zn` clear them, in the main checkout only). Keeping these folders is a judgement call, it is in the diff, and no guess records it.
Critique: the rule's only stated reason is false, and the falsehood would be committed in the helper's comment and the spec's comment. The case's behaviour on such a folder is the same as before c0388. A reader who trusts the comment, though, will expect the case to pass on a leftover folder and will be left debugging a bare `expected true, got false` (E2 already needed a print to find c0268). The tempting fix is to delete "(the page shows it)", which leaves the rule with no reason and no guess.
Consequences: whichever way the rule goes, both halves must agree. Keeping the folders means a leftover folder in a worktree keeps the slow case red there until it is removed, as it does today. Dropping them means the raft half has to check for the document too, needs a raft fixture with no document, and M16 is inverted.
Recommendation: record the choice as G3 and apply it to both halves. I recommend keeping today's behaviour, which also matches the captured "counts the folders" wording: a raft or issue folder with no document is still counted. The page drops it (`board.luau:196`), so it turns the case red as a broken item or a leftover, not an item the page drops on purpose. Rewrite the Design sentence, the helper's comment, roots.spec's comment, G1 and the M16 row to say exactly that. Make the issue half name what it misses: collect the ids with no place into `missing` and assert `t.expect(table.concat(missing, " ")).toBe("")`, since `toEqual` on a table prints only `table: 0x…`. Add a doc-less raft folder to roots.spec's fixture (expected in `found.rafts`), with a mutant that checks for the raft's document. F1's pins then follow the new loop text.

### F5 [low] mutants.py edits the tree it is started in, so a killed run leaves a mutant in that working tree
Where: experiments/mutants.py (the docstring "Run from z-nile/ with the prototype applied", and `open(path, "w")` on the relative paths `MOD` and `CLI`); E4's record.
Evidence: the script rewrites `tests/acceptance/c0042/ondisk.luau` and `cli.spec.luau` in whatever home it is started from, and restores them in `finally`. Each mutant's subprocess may run 120 s, and the documented `./zn run --time 300` stops the script with a signal. Python runs no `finally` on SIGTERM unless a handler is installed, so a stop during a mutant leaves that mutant in the tree. After Implementation step 1, the raft worktree is exactly the tree the docstring describes. E4 does not name the bounded command or the tree it ran in.
Critique: this repeats the lesson's defect: no relative writes, and cd into the script's own fixture under `.cache/` first. A mutant left behind would turn AC2 red, so it would be caught. It would still cost a confused round in the executor's worktree.
Consequences: none for the specs. The same 16 (later 18) mutants give the same result in a scratch copy, because roots.spec reads only the home.
Recommendation: make the script take no target. It builds its own copy under `<checkout>/.cache/c0388-mut/` (a `git clone --shared` of HEAD with prototype.patch applied and the item folder copied in, as this review's replay did), cds into its `z-nile/` before any write, and removes the copy at the end. E4 then records the `./zn run --time` command it ran under.
