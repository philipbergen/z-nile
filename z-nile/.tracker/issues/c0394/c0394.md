# c0394: Findings stay in their raft

## Problem
- As of 2026-11-16 the tracker had 371 issues opened against 147 closed, about 2.5 opened for each one closed (z-nile alone: 264 opened, 88 done, 150 in the backlog).
- About 60% of all issues (roughly 220 of the 371) cite a raft, a review finding or a one-off incident, so findings are the largest single source of opened issues and by themselves outnumber the 147 closed.
- zz-rules "Emergent issues" ("Can be postponed: new issue into the backlog"), zz-execute's "Follow-ups filed" report line and the review skills' "deferred <id>" answer each tell an agent to open a backlog ticket for a finding.
- AGENTS.md and every skill's Lessons section tell a lead that is not a prep or raft lead to capture a new lesson as an issue.
- No rule lets a first one-off tooling incident end as a lesson line instead of a z-nile ticket.

## Non-goals
- A person describing new work to z-ticket still captures a ticket as today.
- No issue already in the backlog is closed, moved or re-rafted by this issue.
- The approval rule for ordinary raft members is unchanged.
- This issue sets no target for the opened-to-closed ratio and adds no check that measures it.

## Solution
- A finding made while designing or delivering a raft (a review finding, a failed step, something noticed in passing) never opens a backlog ticket and is never parked in a list or a final-report section.
- The agent that has the finding decides whether it is worth doing, and for one that is not it writes a lesson saying not to worry about it.
- A worth-doing finding under a stated size threshold is fixed in the raft that found it, with no new issue.
- A larger worth-doing finding is added to the raft that found it as a new member issue, which the agent designs with recorded guesses, tells the user about, and does not implement before the user approves it.
- The rest of that raft is implemented and its pull request merges without waiting for that approval, and the raft then stays in `active/` and is not done.
- The added issue never moves to the backlog, and once approved it is implemented on a further pull request of the same raft.
- The raft is done when every member is implemented or the user has rejected the added issue.
- A worth-doing finding made while designing an issue that has no raft yet is added to that issue's own design when it is under the size threshold.
- A larger one becomes a new issue bound to the issue being designed, so z-raft always puts both in the same raft.
- Whoever learns a lesson writes it straight into the lessons file whatever its role (a subagent still reports it to its lead), and AGENTS.md and every skill's Lessons section (z-nile's and every project's) no longer tell any lead to capture a lesson as an issue.
- A z-nile tooling ticket is opened only when the user asks for it or when the same failure has happened a second time, and a first one-off incident gets a lesson line.
- zz-rules "Emergent issues", zz-execute's "Follow-ups filed" report line and the review skills' "deferred <id>" answer are changed so that no skill tells an agent to open a backlog ticket for a finding.

## Design
Every **Guess (prep)** below is a choice the capture left open, made without the user and waiting for their approval (the user, 2026-11-16: "design it with guesses and wait for approval"). They are listed again under Unknowns & experiments, G1 to G9.

### 1. What a finding becomes (skills)
A finding is anything an agent notices while designing or delivering tracked work that the work itself does not already answer: a review finding, a failed step, a defect seen in passing. zz-rules gains a section **Findings** that replaces **Emergent issues**, and it is the only place the rule is stated; z-design, zz-execute, zz-review, z-ticket and AGENTS.md point at it. The agent that has the finding picks exactly one of four ends, in this order:

1. **It blocks the raft** (the raft's `check.sh` cannot pass, or shipping without it breaks something): fix it now as a must-fix emergent issue, `./zn new issue <t> <slug> --raft <R>`, as today. Unchanged.
2. **Not worth doing**: write a *don't-worry lesson* and move on. It is an ordinary lesson file (zz-rules, Items) whose `tags:` include `not-worth-doing`, whose `check:` asks the question that recognises the finding next time, and whose body says why it is not worth doing. A second finding of the same kind adds a note to that lesson; it does not write a second file.
3. **Worth doing and small**: fix it where it was found, with no new issue: in the layer being delivered (zz-execute), or in the design being written (z-design). Small means at most **50 changed lines**, counted as `size:` is (code, skills and docs; not specs, `check.sh` or experiments). **Guess (prep) G1**: 50.
4. **Worth doing and larger**: it becomes an *added issue* of the work that found it, and never a backlog ticket:
   - found while delivering a raft: `./zn new issue <t> <slug> --raft <R> --wait --found "<where>" [--before <id>]` (section 2), in front of the layer that found it when main would be worse off if that layer landed without it, else last;
   - found while designing an issue: `./zn new issue <t> <slug> --with <id>` (section 5).
   The agent designs the added issue to `design: ready` with every open choice recorded as a **Guess (prep)**, does not implement it, and tells the user (section 6).

A z-nile ticket outside these four ends (an incident met in the main checkout, a metrics report, a capture) is opened only when the user asked for it, with their words quoted in the Problem, or when the same failure has happened twice, with both incidents cited (date, raft or pull request). A first one-off incident gets a lesson, or a note on an existing one. z-ticket step 1 says so, and `idea.challengePrompt` (`z-nile/engine/idea.luau`) gains a second argument, the issue's project (`idea.challengePrompt(doc, project)`, passed by `main.luau`), and for `z-nile` tells the challenger to raise a finding when the Problem neither quotes the user nor cites two incidents: "not a ticket: a first incident is a lesson (zz-rules, Findings)".

**Lessons are written by whoever learns them.** The role rule in AGENTS.md and in every skill's **Lessons** section (z-nile's 13 skills and the 12 project skills) becomes two bullets:
- **A subagent** reports the candidate to the agent that launched it (unchanged).
- **Every lead** (a prep, a raft, the main checkout, a capture, a metrics report) writes it in `<skills folder>/<skill>/lessons/<slug>.md`, or adds a note to the lesson that fits. A prep or raft lead records it in its `harvest.md` and commits it with its work, as today. Any other lead gives the lesson's frontmatter a `from:` line (zz-rules, Items) and lands it by a pull request from a `lessons-<slug>` worktree. No lead opens an issue for a lesson.

zz-execute's final report loses `Follow-ups filed:` and gains `Added issues waiting for approval: <id>: <title> (found <where>; <before <id> | last>; <n> guesses) | none`. z-design's report gains the same line.

### 2. An added issue in an active raft (engine)
Decided with the user (2026-11-16): where an added issue sits in the raft's order says what may land without it. "Can't you rearrange the raft instead? … If we have a raft with ticket T1, during T1 we discover these things that will break with T1, so we add T2 in front, raft is now T2:T1, then for T1 we find something that needs doing but not breaking, the raft now is T2:T1:T3." A raft lands bottom-up, so nothing above a waiting issue lands before the user has answered it. There is no separate "hold" mark.

`./zn new issue <t> <slug> --raft <R> --wait --found "<where>" [--before <id>]` does what `--raft <R>` does today (the issue is made in `active/` on the raft's branch, `emergent: true`, only the counter is pushed) and also:
- writes `waits: approval` and `found: <where>` in the frontmatter (`<where>` is the finding's own name and severity, for example `R0101 review-001 F3 high`, or `R0101 c0333 layer` for something seen in passing), and `before: <id>` when `--before` names a member of the raft that has not landed;
- appends the id to the raft document's `issues:` line (the raft's `R####.md` is already a post-finish path, `layergit.isPostFinishPath`), so `audit.membership` and `workread.build` see it;
- prints `<id> waits for approval in <R>, <before <id> | last>: tell the user`.
It refuses `--wait` without `--raft` ("--wait needs --raft <R-id>: an added issue is made in the raft that found it"), `--wait` without `--found`, and a `--before` that names a landed member or no member. Pushing the counter moves `origin/main`, as it does for a must-fix emergent issue today, so the agent runs `./zn restack <R>` before the next `finish`.

The agent's one question is where the issue belongs. **In front of** the layer that found it (`--before <that issue>`) when main would be worse off if that layer landed without it. **Last** (no `--before`) otherwise. A fix that must ship with a layer but needs that layer's code is neither: that layer's own design was wrong, so it is fixed in the layer when small, and when it is not the layer's contract changes and the user approves it again (the approval check already refuses the drift).

A new pure module **`z-nile/engine/added.luau`** owns the rule, and every command goes through it:
```luau
export type Fact = {
	id: string,
	state: "backlog" | "active" | "done",
	waits: string?, -- the frontmatter value
	before: string?, -- the frontmatter value
	approved: boolean, -- read at the edge
	finished: boolean, -- its layer exists and is finished (layergit.layerFinishSha); false for a landed member
}
export type Plan = {
	order: { string }, -- every member, in landing order
	landed: { string }, -- state done
	lands: { string }, -- what `done` lands now, in order (may be empty)
	blocker: string?, -- the first waiting member in the order, if any
	unfinished: string?, -- the first member below the blocker that is neither landed nor finished
	above: { string }, -- the unlanded members after the blocker
}
-- nil, or the problem: a `waits:` value other than "approval", or a `before:` naming no unlanded member, names the item and the rule
function added.problem(fact: Fact, members: { string }): string?
-- waits for the user: `waits: approval`, not approved, not done
function added.isWaiting(fact: Fact): boolean
-- `base` is stack.order's order of the members without `waits:`; each member with `waits:` goes directly before the
-- member its `before:` names, else last; several before the same member, and several last, go by lowest id first
function added.place(base: { string }, facts: { Fact }): { string }
function added.plan(order: { string }, facts: { Fact }): Plan
```
`approved` is read at the edge by `main.luau`: the issue's `approval.md` is in the working tree and `approval.verdict` finds no drift. The user runs `./zn approve <id>` in the raft's worktree. While the issue is only on the raft's branch the approval is a commit on the current layer (a path under the added issue's folder, so the layer stays finished); once the issue is on `origin/main` (a part has landed) `approve --publish` puts it there as for any issue. Once approved, an added issue is an ordinary member in its place; `waits:`, `found:` and `before:` stay in its frontmatter as the record of how it came.

`layergit.orderedMembers(raft)` returns `added.place(stack.order(…), facts)`.

**Layer numbers stop meaning order.** A layer's branch is still `R0010/<n>/<issue>`, and `<n>` is now the next free number when the layer is opened, never changed afterwards. So putting T2 in front of T1 leaves T1's branch `R0010/1/T1` and its pull request as they are and opens T2 as `R0010/2/T2`; the order is the one `added.place` gives, `./zn stack <R>` prints it, and `restack` rebases each layer onto the layer of the member before it in that order and retargets its pull request's base. For a raft with no added issue the numbers equal the order, as today. **Guess (prep) G10**: this, rather than renaming branches (which closes their pull requests).

- **start**: `layergit.startLayer` opens a layer for the first member in the order that has no layer and is not waiting. Its base is the layer of the nearest member below it that has one and has not landed, else `origin/main`. It no longer asks for the layer below to be finished when the member below is waiting, so work goes on above a waiting issue. With every unlanded member either waiting or already started it fails as today, and when one waits it says `<R> waits for the user: ./zn approve <id>, or ./zn reject <id>`.
- **finish**: unchanged for the layer's own checks. `layergit.isPostFinishPath` also accepts any path under a waiting member's folder (`issues/active/<id>/**`: its document, `check.sh`, `acceptance/`, `approval.md`, reviews and experiments), so designing or approving the added issue on a layer does not unfinish it.
- **restack**: when a member below a layer gains a layer (T2 was approved and implemented), `./zn restack <R>` rebases the layers above onto it in the plan's order; each rebased layer is finished again (`./zn finish`), which reruns its checks on the new base.
- **members**: `./zn members <R>` prints the landed members and those `done` would land now; `--all` prints every member. The raft's `check.sh` (`for dir in $(zn members <R>)`) therefore does not run the checks of a waiting issue or of a layer above it. `stop`, `spend` and `audit` use `store.members` and are unchanged.
- **done**, by `added.plan`:

  | the plan | `./zn done <R>` |
  |---|---|
  | no blocker, nothing unfinished, something to land | today's landing: those members and the raft move to `done/` |
  | `unfinished` is set | today's refusal: `<id> is not finished: ./zn finish <id>` |
  | a blocker, something to land below it | **a part lands**: every existing check runs over `lands` only (the layers, the trace, the reviews); those members move to `done/` and their specs are promoted; the raft, the blocker and the members above it stay in `active/`; the binding commit is `<R>: bind <ids>` with the added line `Waiting: <blocker>` and `Trace: <active raft dir>/trace.md`; it prints `landed <R> in part: <blocker> waits for ./zn approve <blocker>` |
  | a blocker, nothing to land below it | refused: `<R> has nothing to land: <blocker> waits for ./zn approve <blocker>, or ./zn reject <blocker>`, and when `above` is not empty it adds `(<ids> are above it)` |
  | no blocker, nothing to land, something landed | **the raft closes**: no merge and no review is asked for; the raft moves to `done/` in one published tracker commit `tracker: close <R>` |
  | no member has a layer and none has landed | today's refusal (no layers) |

  Each part is one landing with its own code review, trace and final review. A later part's `review-NNN.md` and `final-review-NNN.md` take the next numbers and its `trace.md` replaces the earlier one (which stays in history at the sha its binding commit names).
- **reject**: `./zn reject <id> --lesson <lesson id>`, the human's command, run in the raft's worktree (it refuses under `ZN_DISPATCH` and without a terminal, as `approve` does). It refuses an issue that is not a waiting member, and a lesson id `./zn lessons` does not know or that lacks the `not-worth-doing` tag. It removes the issue's folder and its id from the raft's `issues:` line in one commit `tracker: reject <id> (<lesson id>)`, published to `origin/main` when the issue is there (after a part landed) and local to the current layer when it is not. The members that were above it are no longer blocked; it prints `./zn done <R>` when the plan then has something to land or the raft can close. **Guess (prep) G2**: rejection is a command the human runs, and it requires the don't-worry lesson, so a rejected finding is not raised again.
- **stop**: `./zn stop <R>` (run in the main checkout, as today) refuses a raft with a landed member: `<R> has landed <ids>: it can only be done (./zn approve or ./zn reject its waiting issue)`.
- **work next** (`work.forRaft`, `workread.build`): the raft's issues come from the same plan. An unlanded member that is not waiting and has no finished layer gives `implement` or `finish` as today, also above a blocker. When every such member is finished and a blocker remains, the action is `done` if the plan lands something, else the new action `wait`: `<R> waits for the user: ./zn approve <id>, or ./zn reject <id>`. The pull loop (`./zn work` with no raft) treats `wait` as it treats `none` and takes the next raft; `./zn work <R>` prints it and ends. After a part lands, zz-execute Phase 6 runs for the part (spend, report), and the worktree is kept while a member has a layer that has not landed.
- **list and board**: `./zn list` prints `waits (<found>)` after the title of a waiting issue; the board's issue data gains `waiting: boolean` and `found: string` beside `emergent` (`board.luau`) and its card shows `waits for approval` and where it was found. **Guess (prep) G3**: these two places, the command output and the reports are how the user is told; no notification is sent.

### 3. Review answers
`openlist.answerKind` gains two kinds, for `refute-NNN.md`, `final-refute-NNN.md` and `design-refute-NNN.md`:
- `- F3: dropped <lesson id>: <why>`: not worth doing. Accepted for a medium or low finding only; the lesson must exist and carry the `not-worth-doing` tag.
- `- F3: added <id>: <why>`: accepted for a finding of any severity (decided with the user, 2026-11-16: "That seems like something that should be added, I still have to approve so it does not go unnoticed"; a high finding main would be worse off without goes in front, `--before`, section 2); `<id>` must be a member of this raft with `waits: approval` (in a design refute: an issue whose `with:` names the issue under review).
A high finding is never `dropped`: it is fixed, refuted, added or left to the human. `deferred <id>` stays parsed for refute files already written (13 rafts are active today): `done` accepts it under today's rule and prints `deferred is legacy (c0394): answer dropped or added`. No skill mentions it any more. **Guess (prep) G4**: legacy answers are accepted, not refused, so no active raft has to re-answer a review.

### 4. What stays the same
A must-fix emergent issue, the approval rule for ordinary members (`ready` still needs every non-waiting member approved), `finish`, the trace rules per member, a raft with no added issue (the first row of the table is today's code path, and `tests/tooling/stack-land.spec.luau`, `stack-fix.spec.luau` and `trace-land.spec.luau` stay green unchanged), and z-ticket for a person describing new work.

### 5. An added issue at design time (engine)
`./zn new issue <t> <slug> --with <id>` makes a backlog issue as `new issue` does (the stub is published) with `with: <id>`, `waits: approval` and `found: <where>` in its frontmatter (`--found` is required, as in section 2; `--before <id>` puts it in front of the issue it is bound to, else it comes last). It refuses unless `<id>` is `preparing` on `origin/main`: "--with <id>: an added issue is made by the prep that found it". It rides that prep: designed in the same worktree, prepared in the same pull request. It may be of another type than `<id>`, as an emergent issue may. **Guess (prep) G5**.
- `raftplan` puts an issue with `with: <id>` in the raft that holds `<id>`, whatever its type, size or Touched modules, and plans neither without the other being prepared. `fold`, `unfold` and `recombine` move an issue and the issues bound to it together.
- `ready` does not ask a waiting member for an approval (`readycheck`), and `added.place` puts it in the raft's order (section 2), so the raft is readied and delivered while it waits, and lands as far as its place allows.

### 6. Telling the user
The user asked to be told ("you should let me know you did this"). The agent tells them in its reply at the moment it adds the issue, and the record is: the command's own line (section 2), a pull-request comment `Added <id> (<title>), found <where>, <before <id> | last>: waits for approval, <n> guesses`, the final report line (section 1), `./zn list`, the board, and `done`'s line when a part lands.

### Scalability
`added.place` and `added.plan` are pure over the members' facts. `orderedMembers` adds one frontmatter read (already made by `store.members`) and one `approval.verdict` per member with `waits:`: none for a raft without added issues, so every existing command makes the git calls and file reads it makes today. `raftplan` reads one more frontmatter key from documents it already reads.

### Maintainability
One module (`added.luau`) owns the order, what waits and what lands; `start`, `done`, `members`, `work next`, `ready`, `stop`, `list` and the board all ask it. The frontmatter keys `waits` and `with` are read through `store.readFront`, the one frontmatter reader, and `added.problem` refuses an unknown value. The four ends of a finding are stated once (zz-rules, Findings) and pointed at from the other skills.

### Usability
New command line: `new issue … --raft <R> --wait --found <where> [--before <id>]`, `new issue … --with <id> --found <where> [--before <id>]`, `members <R> --all`, `reject <id> --lesson <lesson id>`. Each joins the usage text; It joins `approve` in zz-rules' Worktrees list of commands run in a worktree, and `members --all` stays read-only. Every refusal above names the item and the rule.

### Existing work
- 13 active rafts: none has a member with `waits:`, so `added.place` returns `stack.order`'s order, each layer's number is its position, and each lands by the first row of the table. Their written `deferred <id>` answers are still accepted (section 3).
- Prepared and mid-prep issues: none uses `--with`. Sequestered specs of c0181 (`acceptance/docs.spec.luau:54`) and c0260 (`acceptance/skills-ticket.spec.luau:170`) pin the old Lessons bullet and the `lesson-<slug>` capture line; each is re-pinned by its own prep when c0394 has landed (their specs are not promoted, so main stays green), and c0394's prep tells both in their documents (a `Note (c0394)` line under each Problem).
