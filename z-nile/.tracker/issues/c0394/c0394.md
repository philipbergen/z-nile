# c0394: Findings stay in their raft

## Problem
- As of 2026-11-16 the tracker had 371 issues opened against 147 closed, about 2.5 opened for each one closed (z-nile alone: 264 opened, 88 done, 150 in the backlog).
- About 60% of all issues (roughly 220 of the 371) cite a raft, a review finding or a one-off incident, so findings are the largest single source of opened issues and by themselves outnumber the 147 closed.
- zz-rules "Emergent issues" ("Can be postponed: new issue into the backlog"), zz-execute's "Follow-ups filed" report line and the review skills' "deferred <id>" answer each tell an agent to open a backlog ticket for a finding.
- AGENTS.md and every skill's Lessons section tell a lead that is not a prep or raft lead to capture a new lesson as an issue.
- No rule lets a first one-off tooling incident end as a lesson line instead of a z-nile ticket.

- Decided with the user (2026-11-16): "Build on c0248 (Recommended)" (c0394 does not land a raft in part itself: it depends on c0248 and uses its `done --through`), "Keep it as one issue" (the skill rules and the engine stay one issue), and "Wait for the vision raft" (c0394 joins the vision raft, c0248 to c0254, as a layer after c0248, and nothing changes for agents until that raft lands).
- Decided with the user (2026-11-16): "In front by default (Recommended)" (a high finding's added issue goes in front of the layer whose review found it; placing it last needs the user's ruling).
## Non-goals
- A person describing new work to z-ticket still captures a ticket as today.
- No issue already in the backlog is closed, moved or re-rafted by this issue.
- The approval rule for ordinary raft members is unchanged.
- This issue sets no target for the opened-to-closed ratio and adds no check that measures it.

## Solution
- A finding made while designing or delivering a raft (a review finding, a failed step, something noticed in passing) never opens a backlog ticket and is never parked in a list or a final-report section.
- The agent that has the finding decides whether it is worth doing, and for one that is not it writes a lesson saying not to worry about it.
- A worth-doing finding under a stated size threshold is fixed in the raft that found it, with no new issue.
- A larger worth-doing finding is added to the raft that found it as a new member issue, which the agent designs with recorded guesses, tells the user about, and does not implement before the user approves it.
- The rest of that raft is implemented and its pull request merges without waiting for that approval, and the raft then stays in `active/` and is not done.
- The added issue never moves to the backlog, and once approved it is implemented on a further pull request of the same raft.
- The raft is done when every member is implemented or the user has rejected the added issue.
- A worth-doing finding made while designing an issue that has no raft yet is added to that issue's own design when it is under the size threshold.
- A larger one becomes a new issue bound to the issue being designed, so z-raft always puts both in the same raft.
- Whoever learns a lesson writes it straight into the lessons file whatever its role (a subagent still reports it to its lead), and AGENTS.md and every skill's Lessons section (z-nile's and every project's) no longer tell any lead to capture a lesson as an issue.
- A z-nile tooling ticket is opened only when the user asks for it or when the same failure has happened a second time, and a first one-off incident gets a lesson line.
- zz-rules "Emergent issues", zz-execute's "Follow-ups filed" report line and the review skills' "deferred <id>" answer are changed so that no skill tells an agent to open a backlog ticket for a finding.

## Design
Every **Guess (prep)** below is a choice the capture left open, made without the user and waiting for their approval (the user, 2026-11-16: "design it with guesses and wait for approval"). They are listed again under Unknowns & experiments, G1 to G12.

### 1. What a finding becomes (skills)
A finding is anything an agent notices while designing or delivering tracked work that the work itself does not already answer: a review finding, a failed step, a defect seen in passing. zz-rules gains a section **Findings** that replaces **Emergent issues**, and it is the only place the rule is stated; z-design, zz-execute, zz-review, z-ticket and AGENTS.md point at it. The agent that has the finding picks exactly one of four ends, in this order:

1. **It blocks the raft** (the raft's `check.sh` cannot pass, or shipping without it breaks something): fix it now as a must-fix emergent issue, `./zn new issue <t> <slug> --raft <R>`, as today. Unchanged.
2. **Not worth doing**: write a *don't-worry lesson* and move on. It is an ordinary lesson file (zz-rules, Items) whose `tags:` include `not-worth-doing`, whose `check:` asks the question that recognises the finding next time, and whose body says why it is not worth doing. A second finding of the same kind adds a note to that lesson; it does not write a second file.
3. **Worth doing and small**: fix it where it was found, with no new issue: in the layer being delivered (zz-execute), or in the design being written (z-design). Small means at most **50 changed lines**, counted as `size:` is (code, skills and docs; not specs, `check.sh` or experiments). **Guess (prep) G1**: 50.
4. **Worth doing and larger**: it becomes an *added issue* of the work that found it, and never a backlog ticket:
   - found while delivering a raft: `./zn new issue <t> <slug> --raft <R> --wait --found "<where>" [--before]` (section 2), in front of the layer that found it when main would be worse off if that layer landed without it, else last;
   - found while designing an issue: `./zn new issue <t> <slug> --with <id> --found "<where>" [--before]` (section 5).
   The agent designs the added issue as z-design says, design review included, to `design: ready` with every open choice recorded as a **Guess (prep)**, does not implement it, and tells the user (section 6).

A z-nile ticket outside these four ends (an incident met in the main checkout, a metrics report, a capture) is opened only when the user asked for it, with their words quoted in the Problem, or when the same failure has happened twice, with both incidents cited (date, raft or pull request). A first one-off incident gets a lesson, or a note on an existing one. z-ticket step 1 says so, and `idea.challengePrompt` (`z-nile/engine/idea.luau`) gains a second argument, the issue's project (`idea.challengePrompt(doc, project)`, passed by `main.luau`), and for `z-nile` tells the challenger to raise a finding when the Problem neither quotes the user nor cites two incidents: "not a ticket: a first incident is a lesson (zz-rules, Findings)".

**Lessons are written by whoever learns them.** The role rule in AGENTS.md and in every skill's **Lessons** section (z-nile's 13 skills and the 12 project skills) becomes two bullets:
- **A subagent** reports the candidate to the agent that launched it (unchanged).
- **Every lead** (a prep, a raft, the main checkout, a capture, a metrics report) writes it in `<skills folder>/<skill>/lessons/<slug>.md`, or adds a note to the lesson that fits. A prep or raft lead records it in its `harvest.md` and commits it with its work, as today. Any other lead gives the lesson's frontmatter a `from:` line (zz-rules, Items) and lands it by a pull request from a `lessons-<slug>` worktree. No lead opens an issue for a lesson.

zz-execute's final report loses `Follow-ups filed:` and gains `Added issues waiting for approval: <id>: <title> (found <where>; <before <id> | last>; <n> guesses) | none`. z-design's report gains the same line.

### 2. An added issue in an active raft (engine)
Decided with the user (2026-11-16): where an added issue sits in the raft's order says what may land without it. "Can't you rearrange the raft instead? … If we have a raft with ticket T1, during T1 we discover these things that will break with T1, so we add T2 in front, raft is now T2:T1, then for T1 we find something that needs doing but not breaking, the raft now is T2:T1:T3." There is no separate "hold" mark.

Decided with the user (2026-11-16): "Build on c0248" and "Wait for the vision raft". c0394 does not land a raft in part itself. It is a layer of the vision raft after c0248 (`depends_on: [c0248]`) and uses what c0248 builds, with the user's rulings recorded there: `./zn done <R> --through <issue>` ("They merge now": the green layers below a block land now), a ticket moves to `done/` "When its layer lands", the raft stays in `active/` until its last layer lands, every landing has its own `final-review-NNN.md` and `trace-NNN.md` ("Yes, every landing"), the raft-wide `RC1`+ checks run "Only at the last landing", `members` and `promote-check` are scoped by `ZN_BIND_MEMBERS`, a landed layer is one whose issue is in `done/` on `origin/main`, and one worker builds the layers one at a time, each complete before the next starts ("One worker, in order"). c0394 changes none of these.

**Making it.** `./zn new issue <t> <slug> --raft <R> --wait --found "<where>" [--before]`, run in the raft's worktree on the open layer:
- makes the issue in `<root>/issues/active/<id>/` with `emergent: true`, `waits: approval`, `found: <where>` (the finding's own name and severity, for example `R0101 c0333 review-001 F3 high`, or `R0101 c0333 layer` for something seen in passing) and, with `--before`, `before: <the open layer's issue>`;
- adds the id to the raft document's `issues:` line;
- **publishes both to `origin/main` in one commit** (`tracker: add <id> to <R> (<before <issue> | last>)`, the lease push `new issue` already makes for a backlog stub), and commits nothing on the layer. The audit holds the issue as it holds any emergent one (`audit.raftHolds`), and `audit.membership` sees the two edits together;
- prints `<id> waits for approval in <R>, <before <issue> | last>: tell the user`.
It refuses `--wait` without `--raft` ("--wait needs --raft <R-id>: an added issue is made in the raft that found it"), `--wait` without `--found`, and `--before` when the current branch is not an unfinished or finished-but-unlanded layer of the raft ("--before puts the issue in front of the layer you are on"). `--before` takes no id: an added issue goes in front of the layer that found it, or last.

An added issue's folder is **never committed on a layer**. Its design is an ordinary prep (z-design, in a `prep-<slug>` worktree, with the design review and its own pull request), made by the raft's lead while the raft goes on, with every open choice a **Guess (prep)**; `./zn status <id> preparing|prepared` accept an active issue that carries `waits:`. The user approves it with `./zn approve <id>` as any issue. So `./zn work next`, the board and `./zn list`, which read `origin/main`, see it from the moment it is made, and no layer's finish state depends on it.

The agent's one question is where it belongs. **In front** (`--before`) when main would be worse off if the layer that found it landed without it. **Last** otherwise. A fix that must ship with a layer but needs that layer's code is neither: that layer's own design was wrong, so it is fixed in the layer when small, and when it is not the layer's contract changes and the user approves it again (the approval check already refuses the drift).

A new pure module **`z-nile/engine/added.luau`** owns the rule:
```luau
export type Fact = {
	id: string,
	landed: boolean, -- in done/ on origin/main (c0248's layergit.landed)
	waits: string?, -- the frontmatter value
	before: string?, -- the frontmatter value
	approved: boolean, -- approval.md on origin/main with no drift
}
-- nil, or the problem: a `waits:` value other than "approval", or an unlanded added issue whose `before:` names an
-- issue that is not a member without `waits:`; names the item and the rule. A landed issue is never judged.
function added.problem(fact: Fact, facts: { Fact }): string?
-- waits for the user: `waits: approval`, not approved, not landed
function added.isWaiting(fact: Fact): boolean
-- `base` is stack.order's order of the members without `waits:`; each member with `waits:` goes directly before the
-- member its `before:` names, else last; several before the same member, and several last, go by lowest id first
function added.place(base: { string }, facts: { Fact }): { string }
-- the first waiting member in the order, and the last member below it (nil when it is first or everything below
-- it has landed): what `done` lands through when no --through is given
function added.blocker(order: { string }, facts: { Fact }): (string?, string?)
```
`layergit.orderedMembers(raft)` returns `added.place(stack.order(…), facts)`, and c0248's `stack.bindMembers` takes that order. Once approved, an added issue is an ordinary member in its place; `waits:`, `found:` and `before:` stay as the record of how it came.

**Layer numbers stop meaning order.** A layer's branch is still `R0010/<n>/<issue>`; `<n>` is the next free number when the layer is opened and never changes. Putting T2 in front of T1 leaves T1's branch `R0010/1/T1` and its pull request as they are, and T2 opens as `R0010/2/T2`; `./zn stack <R>` prints the order. Every site that reads a number as a place goes through two helpers, `layergit.layerBelow(raft, issue)` (the layer of the nearest earlier member in the order that has one and has not landed, else `origin/main`; it replaces c0248's `baseFor(raft, position)`) and `layergit.topLayer(raft, through)` (the layer of the last member being landed). The sites (E5, run in prep): `cmd.finish` (`issues[layer.position - 1]`, main.luau:3747-3755), `cmd.worktree` re-entry (4259), the trace and `done` (`layers[#layers]`, 4905 and 5033, and `done`'s `layer.position == i`), `cmd.stop` (6112), `work.luau:194-199,426`, `workread.build`, `board.luau:714`, `layergit.startLayer`, `layersOf`, `restack`, and the contract text at the top of `stack.luau` ("1-based position", "rebase each layer onto the tip of the one below"), which changes with them. For a raft with no added issue the numbers equal the order, as today. **Guess (prep) G10**: this, rather than renaming branches (which closes their pull requests).

- **start**: opens the layer of the first member in the order that has no layer and is not waiting, when the layers below it in the order are complete (c0248's rule) or waiting. When that member is in front of an open layer (T2 approved, in front of T1), T1's layer is parked as it is: T2's layer is cut from `layerBelow(T2)`, and after T2 is complete `./zn restack <R>` rebases T1 onto it (T2's folder is on `origin/main`, not on T1's layer, so the rebase meets nothing of T2's) and T1 is finished again, which reruns its checks; its review stays current when its patch is unchanged (c0248, outcome 1). With nothing to open and a member waiting it says `<R> waits for the user: ./zn approve <id>, or ./zn reject <id>`.
- **done**: `./zn done <R>` with no `--through`, when a member waits, lands through `added.blocker`'s second result and prints `landed <R> through <issue>: <blocker> waits for ./zn approve <blocker>`; with nothing below the blocker to land it refuses: `<R> has nothing to land: <blocker> waits for ./zn approve <blocker>, or ./zn reject <blocker>`. `--through <issue>` refuses an issue at or above a waiting member. Everything else about a landing is c0248's.
- **reject**: `./zn reject <id> --lesson <lesson id>`, the human's command, run in any worktree (it refuses under `ZN_DISPATCH` and without a terminal, as `approve` does). It refuses an issue that is not a waiting member, and a lesson id `./zn lessons` does not know or that lacks the `not-worth-doing` tag. It removes the issue's folder and its id from the raft's `issues:` line in one published commit `tracker: reject <id> (<lesson id>)`; when no unlanded member is left, that commit also moves the raft to `done/` (there is nothing to bind). **Guess (prep) G2**: rejection is a command the human runs, and it requires the don't-worry lesson, so a rejected finding is not raised again.
- **stop**: c0248's `stop`, unchanged (ruled by the user, 2026-11-16: "the 248 stop behavior is fine, the tickets still have dependencies and are not lost, the point of not leaving tickets behind was for rafts that are processed to a full land"). A waiting added issue is given back with the rest of the raft: it stays a member of that raft (the raft's `issues:` line and its own `raft:`), keeps `waits:`, `found:` and `before:`, and is stamped `prepared` when its design is ready and `new` when it is not. `./zn ready` of that raft later takes it back to `active/` with the others, whatever its design state, because it waits.
- **work next** (`work.forRaft`, `workread.build`): members come from `orderedMembers`. A raft whose every unlanded member is waiting, or complete below a waiting one with nothing left to land, gives the new action `wait`: `<R> waits for the user: ./zn approve <id>, or ./zn reject <id>`. When layers below the blocker are complete and unlanded the action is `done`. The pull loop (`./zn work` with no raft) treats `wait` as it treats `none` and takes the next raft; `./zn work <R>` prints it and ends.
- **list and board**: `./zn list` prints `waits (<found>)` after the title of a waiting issue; the board's issue data gains `waiting: boolean` and `found: string` beside `emergent` (`board.luau`) and its card shows `waits for approval` and where it was found. **Guess (prep) G3**: these, the command output and the reports are how the user is told; no notification is sent.

### 3. Review answers
The answer rules are c0248's `completion.reviewProblem` (moved there from `main.luau`), used for a layer's review, a landing's final review and, through `openlist.problem`, a design refute. It gains two kinds:
- `- F3: dropped <lesson id>: <why>`: not worth doing. Accepted for a medium or low finding only; the lesson must exist and carry the `not-worth-doing` tag. A high finding is never dropped.
- `- F3: added <id>: <why>`: `<id>` must be an added issue of this raft (`waits:` in its frontmatter, a member), or in a design refute an issue whose `with:` names the issue under review. For a **high** finding (decided with the user, 2026-11-16: "That seems like something that should be added, I still have to approve so it does not go unnoticed", and "In front by default") it is accepted only when `<id>` is in front of the reviewed layer (`before:` names the issue whose review this is; a layer's review is in its issue's folder, c0248), or when the finding has a `Ruled (user, YYYY-MM-DD):` bullet under `## Open to the human` that lets it go last. Otherwise the refusal is `F3 [high] is added as <id>, which is not in front of <issue>: add it with --before, or rule it under ## Open to the human`. A high finding of a **final** review (no single layer) needs the ruling.
`openlist.needsHuman` and the "Then the human" sentences of z-design step 4 and zz-execute Phase 4 step 6 change with it: a high answered `added` in front is not on the open list. `deferred <id>` stays parsed for refute files already written: it is accepted under today's rule and `done` prints `deferred is legacy (c0394): answer dropped or added`. No skill mentions it any more. **Guess (prep) G4**: legacy answers are accepted, not refused, so no raft in flight has to re-answer a review.

### 4. What stays the same
A must-fix emergent issue, the approval rule for ordinary members (`ready` still needs every non-waiting member approved), `finish`, `members`, the trace rules, everything c0248 says about a landing, a raft with no added issue (`added.place` returns `stack.order`'s order and `added.blocker` nil, so every command takes c0248's path), and z-ticket for a person describing new work.

### 5. An added issue at design time (engine)
`./zn new issue <t> <slug> --with <id> --found "<where>" [--before]` makes a backlog issue as `new issue` does (the stub is published) with `with: <id>`, `waits: approval`, `found: <where>`, `idea: finding` and, with `--before`, `before: <id>`. It refuses unless `<id>` is `preparing` on `origin/main` ("--with <id>: an added issue is made by the prep that found it"), takes `<id>`'s project and refuses another `--project` ("an added issue is made in its issue's project"), as `--raft` does. It may be of another type than `<id>`, as an emergent issue may. **Guess (prep) G5**.
- **Its path to prepared.** `idea: finding` is a value `./zn status <id> preparing` accepts in place of `challenged`: the issue's source is its `found:` line, not an idea, and `idea.challengePrompt`'s z-nile rule (section 1) does not apply to it. It is designed in the prep that found it, in that prep's worktree, gets its own design review (z-design step 5, with `./zn dispatch zz-review <bound id> --mode design`), and is prepared in the same pull request as `<id>`. The same holds for an added issue in a raft (section 2): `./zn new issue --raft --wait` writes `idea: finding` too.
- `raftplan` puts an issue with `with: <id>` in the raft that holds `<id>`, whatever its type, size or Touched modules, and plans neither without the other being prepared. `fold`, `unfold` and `recombine` move an issue and the issues bound to it together.
- `ready` does not ask a waiting member for an approval (`readycheck`), and `added.place` puts it in the raft's order (section 2), so the raft is readied and delivered while it waits, and lands as far as its place allows.

### 6. Telling the user
The user asked to be told ("you should let me know you did this"). The agent tells them in its reply at the moment it adds the issue. The record is the command's own line (section 2), `./zn list`, the board, `done`'s line when it lands through a member below a waiting one, and two lines the skills prescribe: a pull-request comment `Added <id> (<title>), found <where>, <before <issue> | last>: waits for approval, <n> guesses` (zz-execute) and the final report line (section 1).

### Scalability
`added.place` and `added.blocker` are pure over the members' facts. `orderedMembers` adds one frontmatter read (already made by `store.members`) and one `approval.md` read from `origin/main` per member with `waits:`: none for a raft without added issues, so every existing command makes the git calls and file reads it makes today. `new issue --raft --wait` makes one lease push, as a backlog `new issue` does. `raftplan` reads one more frontmatter key from documents it already reads.

### Maintainability
One module (`added.luau`) owns the order and what waits; `start`, `done`, `work next`, `ready`, `list` and the board ask it, and every "which layer is below, which is the top" goes through `layergit.layerBelow` and `layergit.topLayer`. The frontmatter keys `waits`, `with`, `before` and `found` are read through `store.readFront`, the one frontmatter reader, and `added.problem` refuses an unknown value. The four ends of a finding are stated once (zz-rules, Findings) and pointed at from the other skills. The landing itself is c0248's code, unchanged.

### Usability
New command line: `new issue … --raft <R> --wait --found <where> [--before]`, `new issue … --with <id> --found <where> [--before]`, `reject <id> --lesson <lesson id>`. Each joins the usage text, and `reject` joins `approve` in zz-rules' list of commands that publish. Every refusal above names the item and the rule.
