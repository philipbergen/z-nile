# c0436: One set of stage names

## Problem
- A ticket's place is told today in several vocabularies at once (the status values and folder names new, preparing, prepared, active and done, the idea states unchallenged and challenged, the design states draft, reviewed and ready, the skill names, and the board's column names), so a person has to translate between them.
- No single word today tells apart an item that left the flow without landing (an issue closed as won't do by `./zn close`, a raft under `rafts/retired`) from one that is still in the flow.

Decided with the user (2026-11-21, stored names): looking at README.html's "Stored today" row the owner said: "I think active -> reviewing is better terms and stage five should be approval -> complete not approval.md". So the stored status of a ticket in review is `reviewing` (today `active`), and the fifth stage is stored as `approval`, then `complete` once the owner has approved (today `active` plus an `approval.md` file). The lead's reading, for the owner to correct: this means the stored values change too, not only the words shown; whether the last stage keeps `done` or is stored as `landed` is still open.

Decided with the user (2026-11-21, the bundle stage): "should we insert a stage at 2.5 for rafting, call it bind or group, assemble? Something to show that we raft one or more together. My goal here is to have more and more adjacent functionality rafted together so that there are fewer and more meaty PRs (more layers)" and then "raft only means something if you know about z-nile, find a word recognizable without inside knowledge". The stages are seven: idea, design, bundle, code, review, approval, landed. "Bundle" was chosen by the lead as the word recognizable without inside knowledge, for the owner to overrule. "Raft" stays as the noun for one bundle and is explained in plain words ("a bundle of tickets delivered together") where a page first uses it; whether the noun itself is renamed is open. README.html and the mockup show seven stages.

Decided with the user (2026-11-21, row label): "stored today is a strange label. How about status or state name or status transition or something like that". README.html's row is now "Status", written as transitions (preparing → prepared, approval → complete).

Decided with the user (2026-11-21, skill names): "rename z-run to z-code, z-ticket could be z-idea or z-new? Or stay ticket, please reason that one through for me". Decided: the skill `z-run` becomes `z-code`. The lead recommends `z-ticket` becomes `z-idea` (it matches the stage and the `./zn idea` command; "ticket" names the whole unit, "new" is the status word being retired). Both renames are built with this ticket.

Decided with the user (2026-11-22, skill names confirmed): asked "4 z-idea or z-new?" and then "z-code or z-implement", the lead recommended `z-idea` and `z-code` (each skill carries the name of the stage it performs; `z-new` would sit beside `./zn new issue` with another meaning; `z-implement` would give the code stage two words) and the owner answered: "okay go aheaed". So `z-ticket` becomes `z-idea` and `z-run` becomes `z-code`.

## Non-goals
- This ticket does not rename the stored status values or the folders (`active/`, `done/`, `rafts/retired/`); they are only shown under the new words, and renaming them would be a separate ticket.
- The steps a ticket goes through, and what each step requires, do not change; only the words for them do.
- The skill and command names z-design, z-raft, z-ready and z-work are not renamed by this ticket (`z-ticket` and `z-run` are: see the 2026-11-22 ruling).

## Solution
- Everywhere a person reads or types the stage of an item that is in the flow (the commands' output and arguments, the board and the app, the skills, the README, the live layer's events and the stats), the stage is one of idea, design, code, review, approval or landed, and no other word names any of those six stages.
- The one exception, in every one of those places, is a literal file path or a literal stored `status:` value: a command's output, the board, the app, a skill, the README, a live event or the stats may still print one (such as the `…/rafts/active/<R-id>/prompt.md` that `./zn prompt <R-id> --path` prints, or `…/done/<ID>`) to say where a file is or what a file holds, and never to say which stage an item is at.
- The skills and the README each state once which stage every folder name and stored `status:` value stands for.
- An item that left the flow without landing (an issue whose stored status is the `closed-…` stamp `./zn close` writes, a raft under `rafts/retired`) is shown in all those places with the one terminal word closed, never at any of the six stages.
- Every existing ticket and raft, written before the change, is shown at exactly one of the seven words (the six stages or closed), with no edit made to its file by hand.

## Design
First slice (the lead's scope for this build): the two skill renames, and the stage words a person reads in the docs, the board labels and the app. The stored status values, folders, ids, `raft:` keys and the commands `./zn raft-plan`, `./zn new raft`, `./zn ready` and `./zn work` and the skills z-design, z-raft, z-ready and z-work are not renamed (Non-goals).

- **Skills.** `z-nile/skills/z-ticket` becomes `z-idea` and `z-run` becomes `z-code` (`git mv`, lessons move with the folder). Each old name stays as a one-line alias skill (`z-nile/skills/z-ticket/SKILL.md`, `z-nile/skills/z-run/SKILL.md`: "Renamed to z-idea", it hands over). `./zn skills` needs no change: an alias is a folder whose `name:` is its folder name, so it gets its own `.claude/skills/<name>` link, and a session mid-way that types `/z-run` is handed over.
- **Old records.** `skills.MOVED` (`z-ticket` to `z-idea`, `z-run` to `z-code`) and `skills.movedId` make a harvest ledger or review that names `z-ticket/<lesson>` or `(erred z-run)` read as the moved skill, so no history file is edited; `lessons.canon` applies it, and `DESIGN_STEPS` lists `z-idea` as well as `z-ticket`.
- **Dispatch.** The step keys `z-ticket` and `z-run` are stored (the dispatcher's state files, its step rows, `.models.toml` role lookups) and stay. `dispatch.stepKey` maps a typed `z-idea` or `z-code` to the key, `dispatch.skillName` gives the skill folder a step reads, and `models.roleFor` and `models.activityFor` answer to both skill names.
- **Words shown.** The seven stage names (idea, design, bundle, code, review, approval, landed) are used in the README (a Seven stages section that says once which skill, status value and folder stands for each stage), AGENTS.md, README.html's Status row (`prepared (bundle)`), the skill descriptions that name a stage (z-idea, z-raft, z-code), the board's column labels (`boardview.LABELS` and board.html: Idea, Design, Bundle, Ready, Code, Landed; the column keys stay) and the app and its mockup (the skill a ruling names). "Raft" stays as the noun for one bundle, with its id, commands and folders.
- **Specs.** Pins of the renamed skills' paths and names are updated to the new names (the docs specs of c0114, c0115, c0117, c0119, c0259, c0266, f0399, rounds-skills, work-graph, the board and app command specs c0042 and c0107); specs of dispatch step keys keep the keys. New: `z-nile/tests/tooling/skill-renames.spec.luau`.

### Scalability
Aliases are two folders and two links; adding a later rename is one `MOVED` row.
### Maintainability
One table (`skills.MOVED`) holds the renames, read by the lessons check and nothing else; the dispatcher keeps its stored keys, so no stored file is migrated.
### Usability
A person types the stage's name (`/z-idea`, `/z-code`); the old names still work and say where they went.
