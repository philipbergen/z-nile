# c0460: Behavioral acceptance and build mutants

## Problem
- z-design step 3 has the designer write a `### Rules and mutants` table inside the hashed `## Test plan`, and step 4's mutation check runs that table on a prep prototype before any real code exists (`z-nile/skills/z-design/SKILL.md:39`, `:56`).
- After prep, no step records whether a mutant was killed against the built code: `zz-execute` never mentions mutants, `zz-review` audits the prep table only in design mode's item 0 (`z-nile/skills/zz-review/SKILL.md:92`, under `## Design mode` at `:88`), and code mode (`:115`–`:129`) has no mutant step at all.
- z-design's acceptance-spec rule says only "Require only through aliases" (`z-nile/skills/z-design/SKILL.md:51`), so z-nile's sequestered specs pin internal engine modules: at `c530e048b`, `git grep -n 'require("@znile/engine/' c530e048b -- 'z-nile/.tracker/issues/**/acceptance/**' | wc -l` prints 274.

## Non-goals
- Existing acceptance specs, sequestered or promoted, that require `@znile/*` or `@scripts/*` modules are left unchanged.
- Acceptance specs in `arcade`, `pickman`, `portal` and the other games keep their `@arcade/*`, `@shared/*` and `@logic/*` requires, and the require rule here covers only z-nile's acceptance specs.
- A ticket with no `Mutants: mutants.md` line keeps its `### Rules and mutants` subsection and approval hash unchanged and owes no `mutants.md`. That covers a ticket designed before this lands, whatever its table holds, and one captured but not yet designed. Its table stays on design mode's item 0 audit only when it has at least one row.
- Sequestered `acceptance/` specs and `check.sh` stay in z-design.
- The `./zn check-design` linter (`f0461`) and the pre-code approval gate (`f0465`) are not built here.

## Solution
- z-design step 4 says that an acceptance spec under `z-nile/.tracker/issues/<id>/acceptance/` may require only `@tests/lib/*` and `@lune/*`, and reaches z-nile's behaviour only through `./zn` or `lune run` commands and the files they read and write; in any such spec written after this lands, a `grep 'require("@'` finds no other alias.
- z-design drops the Rules and mutants step and the mutation check, and the issue template's `## Test plan` ends with the line `Mutants: mutants.md` instead of a `### Rules and mutants` subsection; z-design step 3 tells the designer of a ticket captured earlier to replace its `### Rules and mutants` subsection, which has no rows, with that line, so every ticket designed after this lands carries `Mutants: mutants.md` and no `### Rules and mutants` heading.
- `zz-execute` Phase 2 gains a step for a layer whose ticket carries `Mutants: mutants.md`, run once the layer's specs are green: apply each behavioural rule's mutant to the built code, run a spec case that must fail on an assertion, and write one row per rule (`rule | spec :: case | mutant | result`) to `<issue-dir>/mutants.md`, with `result` set to `killed` or `survived`.
- When a mutant survives the acceptance case, the executor writes a case in the layer's own specs under the project's `tests/` (never in the sequestered `acceptance/` folder) that kills it, and names that case in the row; a row ends `killed` or the layer does not finish.
- `mutants.md` sits outside the five sections `contract.luau` hashes (`Problem`, `Solution`, `Design`, `Acceptance criteria`, `Test plan`), so writing it leaves the ticket's approval hash unchanged, and a spec pins that.
- `./zn finish <issue>` refuses a layer only when its ticket's `## Test plan` carries `Mutants: mutants.md`, its `risk:` is not `easy`, the layer's commits change at least one file other than `.md` and `*.spec.luau` files, and `mutants.md` is missing, has no row, or has a row whose result is not `killed`; any other ticket is never refused for `mutants.md`, and a spec pins each of those cases.
- `zz-review` design mode's item 0 audits a `### Rules and mutants` table only when it has at least one row. For a ticket carrying `Mutants: mutants.md`, it checks only that the Design names its behavioural rules.
- `zz-review` code mode gains a step that audits the layer's `mutants.md` when the ticket carries `Mutants: mutants.md`; a missing row, a spec case that can't fail, or a plausible mutant nobody listed is a finding. The step's text names `mutants.md` and never "Rules and mutants", so `z-nile/tests/acceptance/c0043/review-skill.spec.luau:47` stays green.
- The ticket's `Overrides:` line names the two promoted cases this turns red, `z-nile/tests/acceptance/c0043/ticket-prep.spec.luau:28` (step 3 asks for the table) and `z-nile/tests/acceptance/c0043/table.spec.luau:11` (the template has `### Rules and mutants` after Test plan), and z-design's override rule handles them: a chore narrows them first, so that the template case asserts that `## Test plan` ends with `Mutants: mutants.md`, and the step 3 case asserts that step 3 asks for that line.
