# c0462: Spec runner no vacuous pass

## Problem
- The shared spec runner (`z-nile/tests/lib/t.luau`, `z-nile/tests/run.luau`) passes an `it(...)` case that makes no assertions, and today only a reviewer applying `zz-test/no-vacuous-pass` stops such a case.

## Non-goals
- No file of an item on the exempt list is edited, whether a spec, a proof or a helper such as `c0165/gatefix.luau`, so its hash pins (such as c0265 AC4 and c0275 AC3) still match, and a case in those files passes or fails exactly as it does today, including a case that runs nothing.
- The runner does not detect any vacuous pass other than a case with zero assertions: not assertions that cannot fail, greps that find nothing, `|| true`, `diff` over process substitution, or cases that depend on each other's output.
- A run under a `.cache/` directory without `--require-assertions` does not check fixture specs for zero assertions.

## Solution
- `t.luau` counts the assertions of the running case: each `t.expect(...)` matcher call and each call to a new `t.assert(cond, msg)` (which raises `msg` when `cond` is false) adds one, nothing else adds to the count, and `fixture.exec` does not count.
- `run.luau` fails any case whose count is still zero when it finishes, with a message naming the spec file and the case, in every registered project home, except for cases in a spec file that belongs to an item on the exempt list.
- A spec file belongs to an item when it is under that item's folder in any tracker state or under some project's `tests/acceptance/<id>/`, which covers its sequestered acceptance specs and its proof specs (such as c0265's `proofs/race.spec.luau` and c0275's `proofs/long.spec.luau`, `beater.spec.luau` and `dispatch.spec.luau`).
- A run of `run.luau` whose project home is under a `.cache/` directory (a fixture copy, such as the ones `c0058/lock.spec.luau`, `c0058/fence.spec.luau` and `c0165/gatefix.luau` build) does not apply the zero-assertion check, unless it is started with the explicit flag `--require-assertions`; no existing fixture passes that flag, so their probes `first`, `second`, `env` and `slow1` pass exactly as they do today.
- This item's own acceptance specs prove the check by running the copied runner on a `.cache` fixture with `--require-assertions`, and by showing that the same fixture passes without it.
- The exempt list is a checked-in file of item ids, holding every item other than this one that has at least one spec file in the tree that merges.
- A script writes the list from the branch head after that head is rebased onto current main, and the merge goes in only after a full gate passes on that head.
- If main has moved before the merge, the head is rebased again and the script runs again; the full gate runs again only if the list the script writes changed or the new main commits changed a file under any `tests/` directory or any `.spec.luau` file, so commits that only touch tracker state never repeat the gate.
- An id on the list stays exempt after its specs are promoted or its item changes state, and every item not on it is checked, including this issue and any item prepared after the merge.
- The design lists every case outside the exempt items that asserts only through local error helpers or not at all (about 64 at capture, such as `has`/`absent` in `z-nile/tests/tooling/models-skills.spec.luau` and the cases in `app-md`, `app-copy` and `app-links`), and rewrites each to call `t.expect` or `t.assert`, so `--full` and `--slow` stay green in all 7 project homes.
- The lesson `zz-test/no-vacuous-pass` stays in force and is not graduated; it gets one added line saying the runner now catches a case with zero assertions, while review still catches `check.sh` greps that find nothing, `|| true`, `diff <(a) <(b)`, assertions that cannot fail, and cases that read each other's output.
