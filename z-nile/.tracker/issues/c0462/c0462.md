# c0462: Spec runner no vacuous pass

## Problem
- The shared spec runner (`z-nile/tests/lib/t.luau`, `z-nile/tests/run.luau`) passes an `it(...)` case that makes no assertions, and today only a reviewer applying `zz-test/no-vacuous-pass` stops such a case.

## Non-goals
- No file of an item on the exempt list is edited, whether a spec, a proof or a helper such as `c0165/gatefix.luau`, so its hash pins (such as c0265 AC4 and c0275 AC3) still match, and a case in those files passes or fails exactly as it does today, including a case that runs nothing.
- The runner does not detect any vacuous pass other than a case with zero assertions: not assertions that cannot fail, greps that find nothing, `|| true`, `diff` over process substitution, or cases that depend on each other's output.
- A run under a `.cache/` directory without `--require-assertions` does not check fixture specs for zero assertions.

## Solution
- `t.luau` counts the assertions of the running case: each `t.expect(...)` matcher call and each call to a new `t.assert(cond, msg)` (which raises `msg` when `cond` is false) adds one, nothing else adds to the count, and `fixture.exec` does not count.
- `run.luau` fails any case whose count is still zero when it finishes, with a message naming the spec file and the case, in every registered project home, except for cases in a spec file that belongs to an item on the exempt list.
- A spec file belongs to an item when it is under that item's folder in any tracker state or under some project's `tests/acceptance/<id>/`, which covers its sequestered acceptance specs and its proof specs (such as c0265's `proofs/race.spec.luau` and c0275's `proofs/long.spec.luau`, `beater.spec.luau` and `dispatch.spec.luau`).
- A run of `run.luau` whose project home is under a `.cache/` directory (a fixture copy, such as the ones `c0058/lock.spec.luau`, `c0058/fence.spec.luau` and `c0165/gatefix.luau` build) does not apply the zero-assertion check, unless it is started with the explicit flag `--require-assertions`; no existing fixture passes that flag, so their probes `first`, `second`, `env` and `slow1` pass exactly as they do today.
- This item's own acceptance specs prove the check by running the copied runner on a `.cache` fixture with `--require-assertions`, and by showing that the same fixture passes without it.
- The exempt list is a checked-in file of item ids, holding every item other than this one that has at least one spec file in the tree that merges.
- A script writes the list from the branch head after that head is rebased onto current main, and the merge goes in only after a full gate passes on that head.
- If main has moved before the merge, the head is rebased again and the script runs again; the full gate runs again only if the list the script writes changed or the new main commits changed a file under any `tests/` directory or any `.spec.luau` file, so commits that only touch tracker state never repeat the gate.
- An id on the list stays exempt after its specs are promoted or its item changes state, and every item not on it is checked, including this issue and any item prepared after the merge.
- The design lists every case outside the exempt items that asserts only through local error helpers or not at all (about 64 at capture, such as `has`/`absent` in `z-nile/tests/tooling/models-skills.spec.luau` and the cases in `app-md`, `app-copy` and `app-links`), and rewrites each to call `t.expect` or `t.assert`, so `--full` and `--slow` stay green in all 7 project homes.
- The lesson `zz-test/no-vacuous-pass` stays in force and is not graduated; it gets one added line saying the runner now catches a case with zero assertions, while review still catches `check.sh` greps that find nothing, `|| true`, `diff <(a) <(b)`, assertions that cannot fail, and cases that read each other's output.

## Design

Decided with the user (2026-11-27): none beyond the capture; every outcome of the capture is designed below. Product decisions in `pickman/.tracker/game-design.md`: none apply (tooling only).

### The rule, as built

1. **Count.** `z-nile/tests/lib/t.luau` keeps one module-local counter. Each *matcher call* (`.toBe`, `.toEqual`, `.toBeNear`, `.toBeTruthy`, `.toThrow`) adds one before it checks; `t.expect(x)` alone adds nothing. A new `t.assert(cond: any, msg: string?)` adds one, then raises `msg` (default `"assertion failed"`) when `cond` is false or nil. `t.assertions(): number` reads the counter and `t.reset()` zeroes it; the runner is their only caller. `fixture.exec` and every other helper add nothing.
2. **Pure rules** live in a new `z-nile/tests/lib/vacuous.luau` (no I/O):
   - `vacuous.parseExempt(text: string): { [string]: true }?` reads the list (one id per line, `#` comments and blank lines allowed, every id `^[cfd]%d%d%d%d+$`, sorted, unique); `nil` when any line is malformed.
   - `vacuous.itemOf(path: string): string?` is the item id of a spec path: the first path component after `.tracker/` or after `tests/acceptance/` that matches `^[cfd]%d+$`, for a path relative to a home, to the root or absolute (`../pickman/.tracker/issues/active/c0123/acceptance/x.spec.luau`, `tests/acceptance/c0123/x.spec.luau`). Any other path gives `nil`.
   - `vacuous.exempt(list, path): boolean` is `itemOf(path)` found in the list.
   - `vacuous.inCache(root: string): boolean` is true when the physical repository root has a `.cache` path component (a fixture).
   - `vacuous.inherited(value: string?, measured: string?, list): string?` is `value` when `measured == "1"` and `value` is on the list, else `nil`.
   - `vacuous.gateNeeded(changed: { string }): boolean` is true when any changed path is a `*.spec.luau` or lies under a `tests/` component (the landing rule below).
   - `vacuous.message(file, caseName): string`: `case made no assertion (call t.expect(...).toX() or t.assert(...)): <file> :: <case>`.
3. **The runner** (`z-nile/tests/run.luau`) takes a new flag `--require-assertions`. The check is *on* when the flag is given or `inCache(ROOT)` is false. When on, the runner reads `vacuous-exempt.txt` beside the runner (`<RUNNER_DIR>/vacuous-exempt.txt`, so a fixture's copy of the runner reads its own); a missing file or one `parseExempt` refuses exits 2 with a message (fail closed, never an empty list). In the case loop, after `xpcall`: `t.reset()` before each case; a case that passed with `t.assertions() == 0` and whose file is not `exempt` becomes a failure with `vacuous.message` as its error, so it prints as `FAIL <file> :: <case>`, counts in `failed` and records `ok=false` in `PICKMAN_RESULTS`. When the check is off because of `inCache` and no flag, the runner prints one line, `assertion check off: fixture under .cache`, at its start (so a real checkout that happens to sit under a `.cache` path shows the weakening instead of hiding it). The coordinator builds its worker argument list once (`workerArgs(file)`, used by both its plain and its lane-wrapped branch) and passes `--require-assertions` on in it when it was given it; the measurement and browser-guard re-executions already pass every argument.
4. **The exempt list** `z-nile/tests/vacuous-exempt.txt` and its writer `z-nile/vacuous-exempt.luau` (`lune run z-nile/vacuous-exempt` prints the list; `-- --write` rewrites the file; `-- --check` exits 1 when the file differs from what the tree gives; `-- --gate-needed <old> <new>` prints `yes` when `vacuous.gateNeeded` holds for `git diff --name-only <old>..<new>` and `no` otherwise, and exits non-zero with empty stdout on a ref git cannot resolve; it reads the working directory's repository, while `--write` and `--check` read the writer's own checkout). The writer lists every id that has at least one `*.spec.luau` under `<home>/.tracker/**/<id>/` or `<home>/tests/acceptance/<id>/` for any registered home (`z-nile/projects.toml`), minus `c0462`. It reads `git ls-files` of the checkout, so ignored files and `.cache` never count. An id stays on the list for good: nothing removes an id when its item moves, its specs are promoted or its folder goes.
5. **Rewrites.** Every case outside the exempt items that makes no assertion today is rewritten to call `t.expect` or `t.assert`: local `has`/`absent`/`must`-style helpers call `t.assert` (their text stays), and a "sets up"/"cleans up" case asserts what it made or removed (`t.assert(fs.isDir(repo), ...)`, `t.assert(not fs.isDir(base), ...)`). `acceptance/rewrite-list.txt` (fast tier) and `acceptance/rewrite-list-slow.txt` (nine z-nile slow-tier cases) in this issue's folder (sequestered, so they cannot be trimmed) is the list measured at prep (file :: case, per home); the executor reruns the measurement (E1) and the rewrite is done when the list is empty. At prep the lists hold 47 cases in 34 files (46 in z-nile, 1 in pickman): 38 in `rewrite-list.txt`, 9 in `rewrite-list-slow.txt`.

6. **Nested real runs.** Some exempt specs start the real runner on probe files under a home's `.cache` (`z-nile/tests/acceptance/c0049/parallel-runner.spec.luau`, in the slow tier, runs `lune run tests/run` with `cwd` the real home on `.cache/c0470-runner/*.spec.luau` files that assert nothing; `z-nile/tests/acceptance/c0057/guard.spec.luau` does the same on `.cache/c0550-guard/*`, and `tests/tooling/run-guard-relaunch.spec.luau` on `.cache/run-guard-relaunch/records.spec.luau`; `run-lane-error` and c0181's footer start none, E1b), where the check is on, so the file's own exemption has to follow into the nested run. While the in-process case loop runs a case of a spec file whose `itemOf` is on the list, it sets `process.env.ZN_VACUOUS_PARENT = <id>` and clears it when the case ends (as `fence.luau` sets `PICKMAN_WORKER_LANES`; a child inherits it, workers too). A runner honors an inherited value only when `ZN_MEASURED == "1"` (it runs inside a measured run, never a person's bare shell) and the id is on its own list (`vacuous.inherited(value, measured, list): string?`), prints `assertion check off: started by exempt <id>` and applies no check. A nested run started from a case of a file that is not exempt gets no variable and is checked: `run-guard-relaunch`'s probe, whose one case only writes a file, is on `rewrite-list` and gets a `t.assert`. The variable is dropped where an unmeasured process becomes a measured one: both re-executions start the child with `env -u ZN_VACUOUS_PARENT ZN_MEASURED=1 …` (`z-nile/check.sh`'s `gatequeue_run … env ZN_MEASURED=1 "$0"` and `run.luau`'s own re-execution with `env ZN_MEASURED=1 lune run tests/run`), so a stray `export ZN_VACUOUS_PARENT=…` in a shell is gone before any case runs, and only a runner below those two honors it. A person who sets `ZN_MEASURED=1` by hand skips the lock and the measurement already, and with it this drop: the check is then off for a listed id, and each runner process prints the off line, so the weakening is visible and not claimed away.

### How it lands (the order matters)
The list is taken from the tree that merges, and the merge goes in only after a full gate on that head. zz-rules Merging step 4 merges `origin/main` with plain git (not a rebase; the outcome the capture needs, a list taken from the tree that merges, holds either way: **Guess (prep) G2**). This is a one-time landing procedure of this raft, not a standing rule (after it lands the list is frozen: a standing `--check` would fail on every later item). z-raft carries it into the raft's Order and `./zn ready` into its prompt.md, the executor (who merges, zz-rules Merging) follows it from the implementation steps, and the `Ready to merge at <sha>` PR comment records the commands, because the merge is a human's gate under the dispatcher:
1. On the tip after the last code commit: `git merge origin/main`, then `./zn run --time 120 -- lune run z-nile/vacuous-exempt -- --write`, commit the list if it changed (`./zn commit`).
2. The one full gate (`--full`, all 7 homes) on that head must pass (memory: full gate only at merge), and right after it, one after the other and never in parallel, `z-nile/check.sh --slow`, which runs the slow tier with the check on (`--full` does not run it): the nine slow-tier rewrites and c0049's nested exemption are proven only by this run. Record both in the Verification log. Then `./zn done`. `done` and every restack in between reruns AC5, which is red whenever main gained an item with specs since the last `--write`: the fix is on the tip, in that order (merge main, `--write`, commit, `./zn finish`), never an edit of AC5.
3. If main moved after `done` (zz-rules Merging step 4): merge it in, then `./zn run --time 120 -- lune run z-nile/vacuous-exempt -- --gate-needed <the main you gated> <the main you merged>` and `... -- --check`. When either says so (`yes`, or `--check` red), run `--write`, commit, push and rerun the full gate and the slow run (`vacuous.gateNeeded` answers `yes` for the same changes for both); when neither does, the squash merge goes in. Commits that touch only tracker state never repeat the gate.
4. Fix-forward, right after the merge: `--check` on the merged main. An id still missing (an item's prep merged in the seconds between) gets one PR whose only change is `--write`, before any other work lands. The damage of a miss is bounded: the item's own sequestered case fails its raft, which stops for a human, and that PR repairs it.
`lune run z-nile/vacuous-exempt` goes in `z-nile/engine/boundcmd.luau`'s `TOOLING` (and its spec), so the PreToolUse hook lets an agent run it.

### Scalability
One integer add per assertion and one set lookup per vacuous case (only for the failing path); the list is read once per runner process (about 205 lines). A worker reads it once per file, as it parses its own args: under 1 ms.

### Maintainability
One pure module (`vacuous.luau`) holds every rule and is unit-tested; `run.luau` only calls it. The exempt list is data with a writer and a `--check`, so nobody edits it by guess. Cases outside the list cannot grow a no-assertion case again without the gate failing.

### Usability
A failing case prints the file and the case and says what to call. A real checkout under a `.cache` path prints a visible "assertion check off" line.
