# c0468: Narrow raft stage pins

## Problem
- `f0464` (Retire raft PR stage) makes `./zn ready <issue>` ready any prepared ticket in no raft alone, makes `./zn raft-plan` plan no raft by default, has `./zn work next` answer `ready` (never `rafting`) for a raftless ticket and has `./zn dispatch` run `z-ready` on it instead of `raft-plan` and z-raft. A run of z-nile's whole suite, the slow tier included, on f0464's prototype (2026-11-28) turned red these promoted cases, each of which pins the stage f0464 removes:
  - `z-nile/tests/acceptance/c0116/plan-cli.spec.luau`: "prints the plan as commands and the skips, in the main checkout, writing nothing", "--apply stops at the first refusal and leaves what it did" and "--apply runs the commands in a worktree: rafts claimed, raft: lines written, only the skip left" (the no-argument plan's fold and new-raft lines and `--apply` running them);
  - `z-nile/tests/acceptance/c0116/issue-design.spec.luau`: "claims an issue alone and carries its move to prepared, with no raft" (its last assertion: `ready <id>` on the raftless prepared issue is refused, naming z-raft);
  - `z-nile/tests/acceptance/c0116/docs.spec.luau`: its four cases, through the pins of z-design's "z-raft groups it later" and its `/z-raft` Next step, z-raft's no-argument policy (`- **No argument**: run `./zn raft-plan`.` and the fold, surface and cap sentences under it), zz-rules' "a raftless issue goes to z-raft" and z-ready's "If the issue has no raft, stop: z-raft makes one";
  - `z-nile/tests/acceptance/c0117/dispatch.spec.luau`: "rafts a prepared issue: raft-plan, then z-raft, then the raft gate, then follows the raft" (its first expectation, `step raft-plan c0010`);
  - `z-nile/tests/acceptance/f0399/pick.spec.luau`: "with nothing unmet it lands a held approved raft, then readies, then rafts, then drafts", "fix is offered for a raft ready refuses for a repairable reason and for a prepared issue with no size, …", "tier 2 rafts or drafts a ticket only when every unmet dependency is designed" and "an issue can be named: draft, a held design to resume, rafting, or its raft's action" (the issue-level `rafting` action and the unsized `fix`);
  - `z-nile/tests/acceptance/f0399/land.spec.luau`: "work next reads the issue facts: draft for a challenged issue, rafting for a prepared one, …" (`c0110: rafting - `);
  - `z-nile/tests/acceptance/f0399/docs.spec.luau`: "z-design and z-raft have Guess mode before Headless" (its pin of z-raft's "goes into the raft of what it depends on").
- A promoted spec is never edited during a feature's execution, and a spec that asserts behaviour main does not have yet cannot land, so f0464 cannot start while these pins stand (z-design, Override check).
- `c0458` (prepared) edits `f0399/pick.spec.luau` too (it drops the `codeReview` fields), so the two edits must not race.

## Non-goals
- No engine, skill or document change: f0464 makes those, and pins the new behaviour in its own acceptance specs.
- No promoted spec is removed, and no line of a finished item's `check.sh` changes.
- No pin of behaviour f0464 keeps is dropped: a rafting already begun (its worktree or PR), a raft of several a person names and its coherence review, `ready <R-id> --on <base>` for a raft, the light path's words and `raft-plan`'s main-checkout refusal of `--apply` stay pinned.

## Solution
- Each case listed in the Problem is narrowed so that it passes both on today's `main` and once f0464 has landed: the assertions that pin the retired stage (the default plan's commands, `--apply` running them, the issue-level `rafting` action, the unsized `fix`, the dispatcher's `raft-plan` step for a raftless issue, ready's refusal of a raftless issue naming z-raft, and the skill sentences f0464 rewrites) are removed, and every other assertion of the same case stays.
- Each narrowed spec still runs from its own owner's `check.sh`, unchanged.
- It lands after `c0458` (`depends_on`), on the `f0399/pick.spec.luau` that c0458 leaves.
