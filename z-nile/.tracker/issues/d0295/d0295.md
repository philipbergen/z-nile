# d0295: Raft order names non members

## Problem
A raft whose Order & dependencies section names an issue that is not its member makes ./zn start refuse: since #296 (stacks), stack.order reads every [fdc]NNNN id in that section as a layer, so R0090's Order (which named c0264 and c0260 to say R0090 merges before their rafts) was refused with 'c0264 is in R0090's Order and is not a member' (2026-11-12, R0090/1/c0261, PR #303). z-raft tells the author to write cross-raft order in the Order section (lesson z-raft/cross-raft-order-written-in-both, 'For each X before Y, does Y's raft document say it'), so following the skill produces a raft that cannot start. What should happen: a raft can state an order against other rafts and their issues without those ids being read as its layers, and z-raft, its lessons and stack.order agree on where that order is written; z-raft's own checks (status prepared) refuse an Order that start would refuse, before the raft is readied.

## Non-goals
- `ready` and `work` refusing a `depends_on` cycle among members the Order does not name. The capture asks this of `status <R> prepared`, and it does (the carried move runs the whole `stack.order`, as `start` does). `ready` and `work` refusing it too is beyond the capture, and the promoted `tests/acceptance/c0067/ready.spec.luau` ("prompt.md embeds the workstreams plan, or the error when it can't be built") readies such a raft (R0060, seeded prepared, never passed through `status prepared`) on purpose, so it needs an Override: its own defect, d0360 (captured 2026-11-15 by this prep). Here `ready` and `work` refuse the faults of the Order's text.
- No change to what `stack.order` accepts: a non-member id, a repeated member and a dependent before its `depends_on` stay refusals (the promoted `tests/acceptance/c0116/recombine.spec.luau` and `claims.spec.luau` and `tests/tooling/stack.spec.luau` pin them). The fix moves the refusal earlier and gives cross-raft order its own section; it does not make the Order lenient.
- Active rafts. The six active rafts whose Order `start` refuses today (R0061, R0068, R0070, R0073, R0078, R0084, all in the old single-branch shape that `stack.oldShapeMessage` says is being stopped separately) are not edited: `start` already refuses them and this issue changes nothing for them. When one is given back (`./zn stop`, stamped prepared), `ready` refuses it with the message below and its re-rafting writes the section.
- Rafts held by an open rafting or design (`preparing`/`new`: R0040, R0062, R0071 on 2026-11-15) are not edited: their own `status <R> prepared` now refuses with the fix named.
- The dispatched step's variables reaching fixture specs (d0355, fixed by d0298's `fence.STEP_VARS`).
- c0309 (lesson: a layer branch `R0090/1/c0261` repeats its member). Its lesson text is c0309's; this issue only makes the commands refuse that repeat before `start` (AC2 and AC3 pin it).

## Solution
The Order is read by one function, `stack.orderSection`. The carried `./zn status <R> prepared` runs exactly what `start` runs (`layergit.order`: `stack.order` on that section and the members' `depends_on`), so it refuses every order `start` would refuse, a `depends_on` cycle included. `readycheck.reason` (shared by `./zn ready` and `./zn work`) refuses the faults of the Order's own text (`stack.orderProblem`, the first half of `stack.order`: an id that is not a member, a member named twice, a dependent named before its `depends_on`), so a raft prepared before this landed is refused before it is readied too. An order against other rafts and their issues has its own section, `## Cross-raft waits`, right after the Order: the raft template has it, z-raft and its two lessons say so, and the raft's prompt carries it. The prepared backlog rafts whose Order `start` would refuse today are migrated in this issue.

## Design

### Reproduction
`acceptance/order-section.spec.luau :: reproduces R0090` runs `stack.order` on R0090's Order text as it was refused, and `acceptance/order-ready.spec.luau :: refuses R0090's Order` hands the same text to `readycheck.reason`: on main it returns nil (ready and work would accept the raft) and the case fails on the missing refusal. `acceptance/order-cli.spec.luau` shows the carried `status <R> prepared` accepting such an Order on main (the case fails with "was accepted").

### Expected behaviour
The reworked work is #296's stacks (c0248, "The raft's own PR record (Theme, Order) names the stack", done in R0090's predecessor rafts) and the lesson `z-raft/order-names-members-once` ("Put item-level cross-raft waits in a `## Cross-raft waits` section"), which named the section but no command or template carried it, and whose own text says "`./zn status <R> prepared` and `ready` do not run it, so a broken Order is found only when the first layer starts".

### Root cause
- `z-nile/engine/main.luau` `setStatus`, the carried raft move: it checks only that the Theme and Order are written (`sectionWritten`), never what `stack.order` makes of the Order.
- `z-nile/engine/readycheck.luau` `readycheck.reason`: no Order check, so `ready` claims a raft `start` refuses, and `work next` hands it out.
- `z-nile/skills/z-raft/SKILL.md` §3 and `z-raft/lessons/cross-raft-order-written-in-both.md` say to write an order in "both raft documents" without naming the section, and the raft template (`z-nile/templates/raft/doc.md`) has no other place for it, so the Order is where it went.
- No spec caught it: `stack.spec` tests `stack.order` alone, and no spec runs a raft with a cross-raft sentence through `status prepared` or `ready` and then `start`.
- Three copies of the section cut (`layergit.raftSection`, `workread.section`, `main.raftSection`) read the Order; a check that cut it differently from `start` would not be "what start would refuse".

### The change
**`z-nile/engine/stack.luau`** (pure), one new function, the only reader of the Order section:
```luau
-- the text after `## Order & dependencies` up to the next `## ` heading, trimmed; "" when the document has none
function stack.orderSection(doc: string): string
```
It cuts as `layergit.raftSection` does today (a `### ` subheading stays inside; `\n## ` ends it), except that a missing section is `""` rather than `(no ## Order & dependencies section)`; both name no id, so `stack.order` gives the same result.

A second new function holds the first half of `stack.order` (its three named-id checks, moved verbatim), and `stack.order` calls it before its topological fill, so `start`'s refusals and their wording are unchanged:
```luau
-- the faults of the Order's own text: an id that is not a member, a member named twice, a dependent named before
-- its in-raft depends_on. A depends_on cycle among members the Order does not name is not one (stack.order refuses it).
function stack.orderProblem(raftId: string, section: string, members: { Member }): string?
```

**`z-nile/engine/layergit.luau`**: its private `raftSection` goes; a new
```luau
function layergit.order(raft: store.Item): ({ store.Item }?, string?)
```
returns the members in `start`'s order or `stack.order`'s refusal, reading `store.members(raft.id)` and their `depends_on` as `orderedMembers` does today; `layergit.orderedMembers` becomes `layergit.order` plus the existing `fail`. The member list is one function both use, and the carried move asks the second:
```luau
function layergit.memberSpecs(raft: store.Item): { stack.Member } -- store.members(raft.id), each with its depends_on
function layergit.orderProblem(raft: store.Item): string? -- stack.orderProblem(raft.id, stack.orderSection(doc), memberSpecs)
```
`layergit.orderProblem` is what `experiments/order-scan.luau` (AC5) judges: it asks what the Migration can fix, the Order's text, and lists a cycle separately. `start`, `finish`, `stack`, `commit` and `done` keep calling `orderedMembers`, unchanged.

**`z-nile/engine/workread.luau`**: its private `section` goes (its only caller is the Order); `build` calls `stack.order(id, stack.orderSection(text), specs)`.

**`z-nile/engine/readycheck.luau`** (pure; new require of the pure `./stack`): after the members' `depends_on` check and before `if not r.loaded`, so a caller that has not loaded the design files yet (the `loaded = false` contract) is refused too:
```luau
readycheck.ORDER_FIX = "name only members there, each once, and write an order against another raft or its issues under ## Cross-raft waits (z-raft); ./zn stack <R-id> reads it as start does"
-- in reason: specs built from r.members (id, dependsOn = the ids of m.deps)
local orderErr = stack.orderProblem(r.id, stack.orderSection(r.doc), specs)
if orderErr then
	return `{r.id}'s Order & dependencies: {orderErr}: {readycheck.ORDER_FIX}`, true
end
```
`r.members` are the issues whose `raft:` is the raft in both callers (`readyfacts` through `store.members`, `workread.blockFor` from origin/main's documents), the same set `layergit.memberSpecs` reads, and `m.deps` holds every `depends_on` id (`stack.orderProblem` keeps the in-raft ones).

**`z-nile/engine/main.luau`**:
- `setStatus`, in the `carried and rafted` block right after the Theme and Order `sectionWritten` loop, the order `start` stacks (a `depends_on` cycle included):
  ```luau
  local problem = layergit.orderProblem(raftItem)
  if problem then
  	return `{id}'s Order & dependencies: {problem}: {require("./readycheck").ORDER_FIX}`
  end
  local _, cycle = layergit.order(raftItem)
  if cycle then
  	return `{id}'s Order & dependencies: {cycle}: its members' depends_on must not form a cycle (z-design)`
  end
  ```
  The Order-text faults come first, with the advice to move cross-raft ids out; whatever `start` still refuses after them is a `depends_on` cycle (`stack.order`'s only other refusal), whose fix is in the members' designs, so its message says so instead.
  The validator's return is the refusal, so nothing is written and nothing published (the carried move edits only after the validator returns `{}`).
- `renderPrompt`: `CROSS_RAFT = raftSection(raftDoc, "Cross-raft waits")` beside `ORDER` (a raft without the section renders `(no ## Cross-raft waits section)`, as a missing Theme does today).

**`z-nile/templates/prompt.md`**: after the `### Order & dependencies\n{{ORDER}}\n` block, `\n### Cross-raft waits\n{{CROSS_RAFT}}\n`.

**`z-nile/templates/raft/doc.md`**: the Order's comment becomes "Execution order of member issues and why. Member ids only, each once: `./zn start` reads every f/d/cNNNN here as a layer. Raft ids (R<NNNN>) may appear." (placeholders, never live ids: the comments reach the prompt of every raft that leaves them) and a new section follows it, before `## Experiments phase`:
```
## Cross-raft waits
<!-- Orders against other rafts and their issues (this raft merges before R<NNNN>; <issue-id> is done first),
     written in both rafts' documents. Never read as layers. Write None. when there are none. -->
```

**`z-nile/skills/z-raft/SKILL.md`**: §3's Order bullet keeps its pinned start (`c0116/docs.spec`) and gains "`./zn start` reads every item id in this section as a layer, so it names only members, each once (a layer branch such as `R0090/1/c0261` names its member again). ### Server authority
Not a game change. The checks run where the commands already run: the carried move in the rafting worktree on its local tree; `ready` on the tree it just pulled (origin/main), and `work next` on origin/main's documents; neither pushes more than before.

### Scalability
`layergit.orderProblem` reads every issue document once (`store.members`), which the carried move already did for the members; `readycheck.reason` adds one string scan of the raft document and one pass over its members: O(members), no git calls, no processes. `work next` runs it once per prepared raft, on texts it already holds.

### Maintainability
One reader for the Order (`stack.orderSection`) and one judge of its text (`stack.orderProblem`, which `stack.order` calls first), used by `start`'s path (`layergit`), the carried move (through `layergit.orderProblem`), `ready`/`work` (`readycheck`) and the board's facts (`workread`); the refusal's advice is one constant (`readycheck.ORDER_FIX`). A future command that needs the Order reads it through `stack.orderSection`. `main.raftSection` stays for the prompt's sections (Theme, Order, Whole-raft design, Cross-raft waits), which are rendered, not parsed for ids.

### Usability
Refusals name the rule and the fix: `R0090's Order & dependencies: c0264 is in R0090's Order and is not a member: name only members there, each once, and write an order against another raft or its issues under ## Cross-raft waits (z-raft); ./zn stack <R-id> reads it as start does`. `./zn work` shows the same reason for a raft it skips. A cycle at `status <R> prepared` reads `R0050's Order & dependencies: dependency cycle among: c0050, c0060: its members' depends_on must not form a cycle (z-design)`. No new command, flag or usage text; the raft template and the prompt gain the section.

None: tooling only. No `game-design.md` decision is relied on.
