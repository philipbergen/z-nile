# d0298: Main red specs after cuts

## Problem
Scope decision (user, 2026-11-12): z-nile owns its own tracker at `z-nile/.tracker`. Now that z-nile is separated, that tracker holds chores, features, and defects (`c`, `f`, and `d`). The spec that forbids features and defects in z-nile's root is pinning removed behaviour.

Promoted specs red on unmodified origin/main (10dd3c85 and 610e9ed1, 2026-11-12), each confirmed by a prep agent on a clean base worktree: c0116/compact-record (2 cases, 'contract changed since approval', since #295), c0045/workstreams (2), c0049/parallel-runner (1), c0116/claims ('a redesign landed after the carried move is caught by ready', 1), c0116/retired (through c0114/classified). c0008/done-order fails on a fixture with an origin but no origin/main ref ('origin/main cannot be read', since #296). The tooling gate is --affected, so a PR whose paths do not select these never sees them, and a game PR's --full gate in a clean clone is red. What should happen: every promoted spec passes on main again, each fix in the raft that owns the behavior (or the spec's own chore), and the full gate is green on main.

## Non-goals
- Running the slow tier on the landing path: d0303 (watch-net's defect for the slow tier failing on b0c78fb6) owns that, and it lists the same red specs this issue fixes. Whether d0303 closes as this issue's duplicate once d0298 is done is a ruling for whoever takes d0303 (z-ticket, Duplicates), not this design's.
- Deciding whether z-nile's own items may be defects. That is c0266's question (the spec's own chore, already captured, "either the spec or where those issues are filed has to change"), asked to the user as Q1 on 2026-11-12. d0298 depends on c0266 and does not answer it.
- Rewriting `c0045/workstreams`: its two stale cases are c0304's, the override chore filed for them (d0298 depends on it).
- A `check.sh`'s own commands under a dispatched step. They keep the step's environment, as today: a check may run `./zn` read commands there, and none is red. Only spec processes, which the Problem names, lose it.
- c0302 ("three promoted specs fail when the checkout is on a stack layer branch"): another cause (the branch, not the environment); not reproduced here.
- Re-approving c0261, whose approval is stale because #308 redesigned it after #302 approved it. That is a human's `./zn approve`, not a rewrite.

## Solution
- An id rewrite (`renumber`, `compact`, `remap`, and `remap`'s scratch merge base) re-records every approval whose last row held before it, judged from the files git tracks: the same row (when and who kept, the new hash and parts), no new row; an approval that did not hold is left as it was. So `ready`, `done` and `land` take a raft after a compaction exactly as they take it when nothing was rewritten.
- `ready` judges a raft's `grouped:` record (and its coherence review's quote) before its members' approvals, from origin/main, so a member redesigned since grouping is named with both record hashes, what z-raft must redo; the carried move's validator still judges the record again on the tree it publishes.
- The spec runner removes a dispatched step's environment before any spec starts: it unsets `fence.STEP_VARS` (the step's run state, the publish broker, the real git and gh, the agent's git token) and drops every `z-nile/bin` entry from PATH (`fence.stepPath`). The gh tokens and gh's configuration were already `fence.sh`'s.
- c0304 narrows `c0045/workstreams`' two stale cases, and c0266 settles `c0114/classified` (and with it `c0116/retired`); both are done before d0298 is readied (`depends_on`).
- Every promoted spec passes on main again: z-nile's slow tier and the full gate are green, and the specs that failed only inside a dispatched step pass there too.

Q1 (`.cache/dispatch/d0298/questions.md`, 2026-11-12) got no answer: `retry` kept the file as `answered-1.md` with the question alone. This design no longer needs it. The Problem says each fix lands "in the raft that owns the behavior (or the spec's own chore)", and the classified spec's own chore is c0266, which asks the same question. So d0298 depends on c0266 and leaves the ruling to c0266's prep. - **Expected behaviour**: c0116 AC10 ("compact and renumber re-record every grouped: entry that matched before the rewrite ... so ready still takes a raft nothing redesigned"); c0116's claims case ("a redesign landed after the carried move is caught by ready, naming the member and both hashes"); zz-test, "Specs never touch the real repository" (a spec's fixtures are its own; nothing it does reaches the real repository or its publishing). It reworks #295 (approval of the design contract, which added the second record no rewrite carries and put the approval check ahead of the record check) and c0117 (the dispatcher, whose step environment reaches spec runs).
- **Root cause**: (1) `keepRecords` (`z-nile/engine/main.luau`) carries only `grouped:` records across a rewrite, and #295 added `approval.md`, a second record of the same documents. (2) `cmd.ready` runs `approval.refusal` for every member before `moveOnOrigin`'s validator judges the record. (3) `fence.enter`'s bash line (`z-nile/tests/lib/fence.luau`) passes the whole inherited environment to the specs, and only the gh credential and git's configuration were replaced (by `fence.sh`). No gate caught (1) or (2) because both specs are in the slow tier, which `--affected` excludes; nothing caught (3) because only a spec run inside a dispatched step sees it.
- **Siblings**: every id rewrite goes through `keepRecords` (`renumber`, `compact`, `remap` and `remap`'s scratch base: `grep -n "keepRecords(" z-nile/engine/main.luau`, four call sites), so all four carry approvals. `land`'s `approvedDrift` and `done`'s approval check read the same approvals, and they stop refusing a compaction once the approvals are carried (a compaction landed with `./zn land` hit `approvedDrift` before). No other command checks approvals before the record. Spec processes start only through `fence.enter` (`tests/run` nested inside a guarded run skips it and inherits the scrubbed environment), so one change covers every spec; `check.sh` commands are fenced by `ac.sh` and keep the step's environment (Non-goals).
- **Regression guard**: below.
- **Smallest change**: the carry joins `keepRecords`; the record check moves ahead of the approvals as one named local function both callers use; the scrub is one list, one pure function and one changed shell line. `approval.collect` is rebuilt on the new folder reader so there is one reader of an issue's contract (lesson zz-arch/one-reader-per-format), with no change in what it returns.

### 1. Approvals survive id rewrites (`z-nile/engine/approval.luau`, `z-nile/engine/main.luau`)
New in `approval.luau`, pure:
- `approval.partsOf(id: string, files: { [string]: string }, promoted: { [string]: string }?): (contract.Parts?, string?)`: the contract parts from an issue folder's view (`files`: path relative to the folder -> text): `<id>.md`, `check.sh`, and every `acceptance/**.spec.luau` under its name relative to `acceptance/`; when `files` holds no spec, the `*.spec.luau` files of `promoted` (path relative to the promoted folder) instead. That is `approval.collect`'s rule, and `collect` is rewritten to build the same view from disk and call it.
- `approval.holds(text: string, parts: contract.Parts): boolean`: `approval.md`'s text parses, has a row, and its last row's hash is `contract.hash(parts)`.
- `approval.reseal(text: string, parts: contract.Parts): (string?, string?)`: the text with its last row's `hash` and `parts` replaced by `parts`' (`contract.hash`, `contract.partHashes`), `when` and `who` kept, every earlier row as it was; nil and the parse error when it does not parse.

In `keepRecords(root, idMap, rewrite)`, before `rewrite()`: for every issue id in `before` (audit's scan), the view is `gitFolderFiles(dir, true)` (the index: what the rewrite commits) and the promoted view `gitFolderFiles(<root>/<home>/tests/acceptance/<id>, true)` (`projects.homeOf` of the folder; the root's own home is `tests/acceptance/<id>`). The issue is kept when the view holds `approval.md` and `approval.holds(it, partsOf(...))`. After `rewrite()`: each kept issue's new id (`idMap[id] or id`), its folder in the new scan, the same two views, and `approval.md` is written with `approval.reseal`. A rewrite that commits (`compact`, `remap`) commits after `keepRecords` returns, so the carried rows ride in its own commit; `renumber` leaves them in the working tree with its other edits. An approval that did not hold is never touched. Every state is one path: the scan gives backlog, `active/` and `done/` folders alike, and a done issue's specs are read from its promoted folder (the case seeds a backlog and a done issue; an active one differs only in its folder, which the scan supplies).

Why in place and not a new row: `contract.reapprovals` (rows minus one) counts re-approvals in `./zn metrics`; a mechanical rewrite is not a human re-approval, and the row's `who` stays the human who approved. Why the index: a work file in an approved folder (untracked) is not part of what the rewrite commits, so it must not decide whether the approval held (the same reason `keepRecords` hashes grouped records from the index, c0116 review 005 F1).

### 2. `ready` judges the record first (`z-nile/engine/main.luau`, `cmd.ready`)
The validator closure passed to `moveOnOrigin` becomes `local function recordRefusal(paths: { string }, read: (string) -> string?): string?` with the same body (the `grouped:` record against the members' folders, then `reviewCovers` for a raft of several members). `ready` calls it once before the approval loop, on origin/main (`git ls-tree -r --name-only origin/main` and `git show origin/main:<path>`: the tree it has just fast-forwarded to), fails with its refusal, and then runs the approvals as today; `moveOnOrigin` still gets `recordRefusal` as its validator, so a redesign landing between the pull and the move is caught on the published tree. Messages are unchanged.

### 3. Spec runs drop a dispatched step's environment (`z-nile/tests/lib/fence.luau`, zz-test)
- `fence.STEP_VARS: { string }` = `ZN_DISPATCH`, `ZN_HEADLESS`, `ZN_DISPATCH_DIR`, `ZN_DISPATCH_HOME`, `ZN_REAL_GIT`, `ZN_REAL_GH`, `ZN_PUBLISH_BROKER`, `ZN_PUBLISH_TOKEN`, `ZN_DISPATCHER_PID`, `ZN_AGENT_GH_TOKEN`: every variable `dispatcher.luau`'s step environment and `credential.agentEnv` set, except those `fence.sh` already handles (`GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK` unset; `GH_CONFIG_DIR`, `GIT_TERMINAL_PROMPT` and the `GIT_CONFIG_*` entries replaced), `GH_PROMPT_DISABLED` (it only turns prompts off) and PATH. It never names `ZN_TOP`, `ZN_CWD` or a `ZN_MEASURE*` variable, which the runner and a fixture's `./zn` read.
- `fence.stepPath(path: string): string`: PATH without every entry that ends in `/z-nile/bin` (with or without a trailing slash), from any checkout (the dispatcher puts the main checkout's first, and a run starts in a worktree), the rest in order.
- `fence.enter`'s bash line starts `unset PICKMAN_REAP_SWEPT PICKMAN_REAP_CACHE <STEP_VARS>; PATH="$7"; ...` and ends `shift 7`, with `fence.stepPath(process.env.PATH or "")` as its seventh argument. That shell is where every spec process starts (inside the jail when there is one), so the specs and every nested runner inherit the result. The runner's own reads before it (the measuring prelude, the guards' `git` calls) still run in the step's environment; that is the wrapper's job and unchanged.
- zz-test, "Specs never touch the real repository", gains one bullet under "Enforced at run time": a dispatched step's environment, what it carries, that the runner unsets `fence.STEP_VARS` and drops `z-nile/bin` from PATH, and that a variable added to the step's environment goes on the list or is named as handled in d0298's spec.

### Scalability
The carry adds two `git ls-files` per issue to a rewrite (the before and after views; `gitFolderFiles` already runs one per grouped member). On main's ~300 items a compaction gains about 600 short git calls, seconds, once per compaction; `renumber` and `remap` touch the same scan. `ready` gains one `ls-tree` of origin/main and one `git show` per member and raft file it reads, as its validator already does on the published tree. The scrub is a fixed list of 10 names.

### Maintainability
One reader of an issue's contract (`approval.partsOf`, used by `collect` and `keepRecords`); one record check used twice (`recordRefusal`). The step-variable list sits beside the guard that uses it, and `stepenv.spec`'s first case reads the dispatcher's step environment and `credential.agentEnv`, so a variable added there without a decision fails a spec.

### Usability
Nobody runs a new command. A compaction or renumber no longer silently breaks every approval it touches (today the human would have to re-approve every prepared issue after a compaction). `ready` names what z-raft must redo first. An executor's gate and the post-landing net give the same answers inside a dispatched step as outside it.
