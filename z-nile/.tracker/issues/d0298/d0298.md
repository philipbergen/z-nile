# d0298: Main red specs after cuts

## Problem
Promoted specs red on unmodified origin/main (10dd3c85 and 610e9ed1, 2026-11-12), each confirmed by a prep agent on a clean base worktree: c0116/compact-record (2 cases, 'contract changed since approval', since #295), c0045/workstreams (2), c0049/parallel-runner (1), c0116/claims ('a redesign landed after the carried move is caught by ready', 1), c0116/retired (through c0114/classified). c0008/done-order fails on a fixture with an origin but no origin/main ref ('origin/main cannot be read', since #296). Prep findings so far (2026-11-12, on origin/main 2aed52eb; design paused on the question in `.cache/dispatch/d0298/questions.md`):

- **E1 (run) Which reds are real and which come from the run's environment?** Each named spec was run twice in this prep worktree: once in the dispatched step's own environment and once with the dispatcher's step variables removed (`ZN_DISPATCH*`, `ZN_HEADLESS`, `ZN_PUBLISH_BROKER`, `ZN_PUBLISH_TOKEN`, `ZN_REAL_GIT`, `ZN_REAL_GH`, the agent credential's `GH_*` and `GIT_CONFIG_*`, and `z-nile/bin` dropped from `PATH`). In the clean environment the only failures are: `c0116/compact-record` (2: `after compact, ready takes ...` and `remap re-records ...`, both "c0001's contract changed since approval"), `c0045/workstreams` (2), `c0116/claims` (1: `a redesign landed after the carried move is caught by ready ...`), `c0114/classified` (1: `no feature or defect is filed in z-nile's root`) and through it `c0116/retired` (1). `c0049/parallel-runner` passed 5 runs of 5 (one of them in the dispatched environment), `c0008/done-order` 5 of 5 and `c0114/trail-move` 7 of 7. The whole slow tier in the clean environment (`z-nile/check.sh --slow`, 98 files) gave 854 passed and 7 failed, exactly the seven cases above (watch-net's fast suite had passed on the same main, d0303). `trail-move` rerun in the dispatched environment fails 3 cases: its fixture's `git push origin HEAD:main` is refused by the wrapper. In the dispatched environment many more cases fail: a fixture's `git push origin HEAD:main` goes to the z-nile wrapper on `PATH` and is refused ("git push to main refused"), and a fixture's `./zn new`, `start` or `fold` publishes through `ZN_PUBLISH_BROKER`, a folder in the main checkout's `.cache/` that the spec jail denies ("Operation not permitted"). `done-order`, `trail-move` (d0303's list) and the parallel-runner report are of that kind: a spec run inside a dispatched step (an executor's gate, the post-landing net started from one) inherits the step's environment.
- **E2 (read) compact-record.** Since #295 a seeded design-ready issue carries `approval.md`. `compact`, `renumber` and `remap` rewrite ids in the member's document (the `## Design` text names ids), so the contract hash changes and `ready` refuses with "contract changed since approval". `keepRecords` (`engine/main.luau`, c0116 review 003 F4) re-records the `grouped:` entries across the rewrite, but nothing re-records an approval. Root cause: #295 added a second record of the document and no rewrite carries it.
- **E3 (read) claims.** `cmd.ready` runs the approval check (`approval.refusal`, before the move) ahead of the grouped-record check (inside `moveOnOrigin`'s validator), so a member redesigned after grouping is now refused as "contract changed since approval" and never named with its record hashes (`c0022 (<old> → <new>)`), which the spec pins.
- **E4 (read) workstreams.** Since #296 a raft's worktree is detached until a layer exists and layers are `R0010/1/f0010`, so the branch `R0010-demo` the case `worktree --from bases the new worktree on the ref` bases on no longer exists; and `done` now refuses before reading reviews when the local layer tip is not the published one ("done checks the commit it lands"), so `stream review files are not review rounds` never reaches the review check. Both are deliberate #296 behaviour: the cases' setup is stale, and each needs a narrow rewrite of the promoted spec (an override).
- **E5 (read) classified.** `z-nile/.tracker` holds four defects, d0295, d0297, d0298 (this issue) and d0303. c0114's rule (README "CI and test fixes are chores", z-ticket's "defect: game or product behavior", the chore checklist "tooling fixes are chores even when they fix a bug", and the user's own rename of f0263/f0265 to c0263/c0265 in #258 to clear this spec) says z-nile's items are chores; but `./zn new issue d --project z-nile` accepts a defect, and watch-net (#293, #311) writes `type: defect` ids `dNNNN` in z-nile's root by design. c0266 (backlog, "Classified spec znile features") is the spec's own chore and says "either the spec or where those issues are filed has to change". `renumber` refuses a type change ("same type prefix"), and renaming d0298 during its own dispatch chain breaks the chain (the dispatcher reads `d0298` on origin/main, and the prep gate takes only the issue's own folder). This is Q1 in questions.md.
