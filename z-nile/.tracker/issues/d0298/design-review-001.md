### F4 [medium] The carry spec seeds only one-row approvals, so a reseal that drops or rewrites the history passes
Where: carry.spec.luau (seed, renumber and compact cases); Rules and mutants, row "the carried row is the same row".
Evidence: `seal.stamp` writes one row per issue (seal.luau:103-155, `approval.append` on an empty file), and the hand-written c0550 approval has one row. With one row, every assertion (`#after == #before`, the last row's `when` and `who`) also holds for these mutants: `reseal` rendering only the new row (history dropped); `reseal` writing `rows[1]`; `holds` reading `rows[1]`. The Design promises "every earlier row as it was". No case can see that promise broken, and the table lists none of these mutants.
Critique: `contract.reapprovals` counts rows for `./zn metrics`. A carry that collapses history would silently zero the re-approval count of every issue a compaction touches.
Consequences: none beyond two extra seeded issues.
Recommendation: Seed one approved issue with a two-row `approval.md`: an older row with a different hash, `when` and `who`, then the row that holds. After renumber and after compact, assert two rows, the first row's rendered text byte-identical, and the second row's `when` and `who` kept with the new hash. Seed another issue whose first row matches its current contract but whose last row does not, and assert it is not carried. Add these three mutants to the table and run them.
