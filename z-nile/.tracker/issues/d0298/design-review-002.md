### F1 [high] The carry ignores f0399's guesses rule: a wrong `partsOf` passes AC1, and an approval `ready` accepts before a compaction is refused after it
Where: Design §1 (`approval.partsOf`, `approval.holds`, `keepRecords`); Solution, first bullet ("So `ready`, `done` and `land` take a raft after a compaction exactly as they take it when nothing was rewritten"); `acceptance/carry.spec.luau` (no seed has a `guesses.md`); Rules and mutants (no row for `guesses.md`).
Evidence: (1) Mutant run on the prototype: `approval.partsOf` passing `nil` instead of `guessText` to `contract.build` (so neither `collect` nor the carry hashes `guesses.md`): `carry.spec` 4 passed, 0 failed; `tests/tooling/approve.spec` 3 passed, 0 failed. The one rule this revision added has no case and no row. (2) `readycheck.reason` (readycheck.luau, the `elseif m.approval then` branch) lets a non-dispatched `ready` (z-work, the main way in) take a member whose last approval row differs from its contract only in `guesses` (a guess recorded after approval, which f0399 allows and "approval is flexible" makes common). `approval.holds` requires the full hash, so `keepRecords` does not carry that approval. A compaction or renumber that rewrites an id in the member's design then makes `contract.changed` return `design, guesses`, and `ready` refuses "contract changed since approval: design, guesses". Before the rewrite it accepted the same raft. That breaks the Solution's sentence, and it happens in exactly the state current main produces.
Critique: The port added `guesses.md` to the parts (correct: approve hashes it since f0399) but kept the 2026-11-12 notion of "held", which predates partial holds. The tempting fix is to carry every approval whose diff is guesses-only by resealing it whole. That would mark a guess the human never approved as approved, and would let `done` and a dispatched `ready` (both strict, `approval.reasonOf`) through where they refused before.
Consequences: Carrying a guesses-only approval means resealing every part the row approved except `guesses`, whose recorded part hash must stay as it was. The row's `hash` can't be recomputed for the approved guesses text (that text is gone), so the design must say what `hash` holds then. One option is to keep the old value: it no longer equals any current contract, so `contract.changed` falls through to the per-part comparison and returns `guesses`, as before the rewrite. A third state also needs a rule: the rewrite edits `guesses.md` itself (a guess line naming a renumbered id). In a fully held approval the reseal covers it. In a guesses-only one the kept `guesses` hash still differs, which is correct.
Recommendation: Define "held" as ready's two rules, and carry each one as it stood. (a) The last row holds fully: reseal as now. (b) The last row's changed parts are exactly `guesses`: reseal every other part, keep the row's `guesses` part hash and state what `hash` holds. Then non-dispatched `ready` still takes it, and `done`, `land` and dispatched `ready` still refuse it, as before the rewrite. Seed two issues in `carry.spec`: one approved with a `guesses.md` whose guess names another seeded id (fully held; after renumber and compact `approve --check` passes), and one whose `guesses.md` gained a guess after approval (after renumber and compact, `approve --check` names only `guesses` changed, not `design`). Add rows: "the contract includes guesses.md" (mutant: `partsOf` drops it) and "a guesses-only approval is carried with its guess still unapproved" (mutants: `holds` needs the full hash, which is the port as it stands; reseal the `guesses` part too). Run them as E16's mutants were. If you judge case (b) should not be carried, record that as a guess with its consequence (every such approval goes back to the person after a compaction) and correct the Solution sentence.

### F2 [medium] G1's early record check also comes before "only a prepared raft is readied", so `ready` on a done or non-prepared raft gives wrong z-raft advice
Where: Design §2 (call placed before `readyfacts.reason`); `prototype.patch` `cmd.ready` (`local early = recordRefusal(...)` runs for every raft that is not a reissue); guesses.md G1.
Evidence: `readycheck.reason` refuses first with `{r.id} is {r.status} in {r.dir} on origin/main: only a prepared raft is readied`. The early check now runs ahead of it, for every raft except an active one with status `active` (`reissue`). A done member's design files have changed since grouping: `check.sh` paths were rewritten on the move, `acceptance/` was promoted away, and the verification log was appended. So the record no longer matches. Probe on origin/main's tree, calling `readycheck.record` exactly as `recordRefusal` builds it: `R0133: c0304 (ee054433c7c0 → 61d843e2318d), c0374 (...), c0411 (...) changed on origin/main since R0133 grouped it: z-raft drops it (./zn unfold R0133 <id>) or folds it again with a new coherence review`, and the same for R0134/d0406. On the prototype, `./zn ready R0133` (or `ready c0304`) therefore tells the user to unfold members of a done raft, where main says the raft is done. A backlog raft whose status is not `prepared`, such as one being rafted (`preparing-…`), is affected the same way. G1 lists questions, dependencies and design-not-ready as the refusals it pushes behind the record, but not this one.
Critique: The record check makes sense only for a raft `ready` could otherwise take. Before it, the status refusal is the one a user needs. The tempting fix is to move the record check into `readycheck.reason` after its first test, which the module header forbids (a file on disk must never change a hash).
Consequences: Gating the early call keeps `readycheck.reason` unchanged. The early check then runs only for a backlog raft whose effective status is `prepared`, the same condition `reason` tests first. Every other raft gets main's message. The questions, dependency and design refusals stay behind the record, as G1 chose.
Recommendation: In `cmd.ready`, call `recordRefusal` early only when `raft.state == "backlog"` and the effective status is `prepared`; say so in Design §2 and amend G1's consequence. Add a `ready-order` case: a raft not in that state (e.g. a seeded raft in `rafts/done/` whose member changed after grouping, or a backlog raft with a non-prepared status) is refused with "only a prepared raft is readied" and without "changed on origin/main since". Add a row whose mutant is the ungated early call.
