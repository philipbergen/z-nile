# d0331: Finish refuses layer one when main moved

## Problem
- `./zn finish` refuses layer 1 unless it contains the newest commit of origin/main (`layergit.mainTip()` at z-nile/engine/main.luau:3746, refusal at :3761), so every commit main gains during a 32 to 36 second restack makes finish refuse again.
- `./zn done` applies the same rule to layer 1 (main.luau:5066-5073, "is not stacked on the layer below"), so a stack that is behind origin/main is refused there too, even when it merges cleanly.
- On R0072 (2026-11-14) a restack pushed layer 1, GitHub rejected layer 2's push with only "(failed)", and the remote stack was left half moved with no message naming the layer that was not pushed.
- Scope decision (user, 2026-11-14): "Stop after 9". Asked whether `./zn done` should keep merging and gating again for as long as `main` keeps moving during its gate, or stop after a number of lost attempts, rolled back, asking for `./zn done <R>` again. So done makes at most nine attempts, and "main gained commits during each of 9 attempts" is a third refusal for `main`'s sake beside the conflict and the red gate of the Solution's fifth bullet.
- Decided with the user (2026-11-14): "Wait for c0302". Asked how d0331 gets past its own regression check, since `c0074/done-gate.spec` (and every spec that clones the checkout) fails on a layer branch until c0302 (Layer branch breaks clone fixtures) lands: run the slow guards once outside the check, or wait. So `depends_on: [c0302]`, and the check runs those specs itself.
- Decided with the user (2026-11-14): "True by definition (Recommended)". Asked whether the first Solution bullet's "the layer holds only its own commits above it" needs a check that refuses a layer 1 carrying another branch's commits (design review 001 F9), or holds by definition because nothing of `main` is above the fork. No new refusal.
- Decided with the user (2026-11-14): "Any lowest layer". Asked which rule the layer above an already-landed part of its raft follows once c0248 (Stacked PR delivery) lands rafts in parts: c0248's (restack it onto `main`'s newest commit) or this issue's. It is judged by its fork too: no restack after a partial landing. No partial landing exists before c0248, so d0331 builds the rule for layer 1 only, and c0248 goes back to design after d0331 lands (its AC8 refusal and restack step change, its `baseFor` calls `mainFork` for the lowest unlanded layer, `depends_on` gains d0331).

## Non-goals
- The stacking rule for layers 2 and up, in finish and in done, does not change.
- The gate `./zn done` runs, the single `--no-ff` merge and the binding commit do not change.
- c0300 (restack dropping unfinished commits) is not fixed here.
- The number of tracker bookkeeping commits on main is not reduced here.

## Solution
- `./zn finish` accepts layer 1 when the merge base of the layer and origin/main is a commit of origin/main and the layer holds only its own commits above it, however many commits origin/main has gained since.
- `./zn finish` on layers 2 and up still refuses unless the layer contains the tip of the layer directly below.
- `./zn done` accepts a stack whose layer 1 sits on any commit of origin/main, and lands a stack that is behind origin/main and merges cleanly, with no restack.
- `./zn done` merges the top layer onto the origin/main tip it fetched and runs the gate on that merged tree, which is the only place the stack is checked against current main.
- `./zn done` refuses for main's sake only when that merge conflicts or the gate on the merged tree is red, and the refusal names `./zn restack <R>`.
- When the push to main is rejected because main gained commits during the gate, `./zn done` merges onto the new tip, runs the gate again and pushes again itself, without asking for a restack.
- `./zn work next` never offers a restack for a raft whose only difference from origin/main is commits main gained.
- A `./zn restack` whose push of one layer is rejected exits non-zero naming each layer that was not pushed, and the next `./zn restack` of that raft brings the remote stack back to one layer on top of the other.

## Design
Type: defect. Reworks #296 ("Land a raft as a stack of one commit and one pull request per ticket", 2026-11-11), which wrote the rule, and #297 (the trace), which copied it. zz-stats counts it as rework.

**Reproduction.** `acceptance/layer-one.spec.luau :: AC1`: a raft is started, its layer 1 holds one work commit, another clone pushes one commit to `origin/main`, and `./zn finish c0010` fails on `main` today with `R0010/1/c0010 is not based on the layer below: ./zn restack R0010` (run 2026-11-14 on 59831e01d: 5 of the 6 cases fail, the first for exactly that message).

**Expected behaviour.** zz-rules, Items: "`R0010/1/c0010` is position 1, issue c0010, based on main; the next layer is based on the one below." A layer cut from `main` and never rebased is based on `main`. The user (2026-11-14): "Why is the system seemingly allergic to main moving, after all that is the single most desirable attribute?"

**Root cause.** Every command that walks a stack starts its "layer below" at `layergit.mainTip()`, the newest commit of `origin/main`, and then asks `git merge-base --is-ancestor <below> <tip>`. For layers 2 and up `<below>` is the tip of the layer below, which is right: a layer's pull request must show only its own change. For layer 1 it turns "sits on `main`" into "contains this second's `main`". `stack.finished` adds `parent == base`, so a finished layer 1 also stops counting as finished the moment `main` moves. No spec caught it because every fixture finishes and lands with nothing else pushing to its origin (zz-test/landings-move-every-rafts-base was written for the same blind spot, and worked around it by restacking in the fixture).

**The rule after this issue.** Layer 1 is judged against its **fork**: the merge base of the layer's tip and `main`'s tip, which is the newest commit of `main` the layer contains. Layers 2 and up are judged exactly as today. The commits above the fork are the layer's own by construction (the capture's "the layer holds only its own commits above it"): `fork..tip` holds nothing that is on `main`, and `finish` squashes exactly that range into the one finish commit (AC1 checks that the file `main` gained is in neither the finish commit nor the layer's watch file). Only two commands look at `main`'s newest commit: `./zn restack` (its job is to move the stack there) and `./zn done` (it merges onto it and gates the merged tree).

**1. One helper, `layergit.mainFork`** (`z-nile/engine/layergit.luau`):
```luau
-- The commit layer 1 is judged against: where `tip` left main, not main's newest commit.
-- With no shared commit it is main's tip, so every caller's own check still refuses.
function layergit.mainFork(tip: string, main: string?): string
```
`main` defaults to `layergit.mainTip()`. It runs `git merge-base <main> <tip>` and returns the trimmed sha, or `main` when git fails or prints nothing (fail closed: the callers' ancestor checks then refuse as they do today).

**2. Siblings: the seven places that judge layer 1, all changed here.**
| where | today | after |
|---|---|---|
| `cmd.finish` (`main.luau`) | `base = layergit.mainTip()` | `base = layergit.mainFork("HEAD")`; the `layer.position > 1` branch, the ancestor check, `layergit.diffPaths(base)` and `git reset --soft base` are unchanged and now use the fork |
| `layergit.startLayer` | `baseTip = layergit.mainTip()` | `baseTip` is `mainFork(<layer 1's tip>)` when layer 1 exists, else `mainTip()`; a new layer 1 is still cut from `origin/main` |
| `cmd.stack` (the view) | `below` starts at `origin/main` | `below` starts at `mainFork(<layer 1's tip>, below)` when layer 1 has a tip |
| trace skeleton (`./zn trace <R>`) | `baseTip = layergit.mainTip()` | `mainFork(localOrOriginTip(layers[1]))`; `baseTip` also feeds `diffNamesBetween(baseTip, topTip)`, so the changed sources stop including `main`'s own commits in reverse |
| trace check (`traceProblems`) | `baseTip = layergit.mainTip()` | the same |
| `cmd.done`, the stacked and finished walk | `onto = layergit.mainTip()` | `onto = layergit.mainFork(<layer 1's tip>)` |
| `workread.layerFacts` and `workread.stacked` (`./zn work next`, `queue`, `status`) | `base`/`onto` start at `mainSha` | start at `layergit.mainFork(tips[1].sha, mainSha)` when layer 1 has a tip |

`cmd.restack` is not in the table: it keeps `onto = layergit.mainTip()` for layer 1, because moving the stack onto `main`'s tip is what it is for. Nothing else in the engine compares a layer with `main` (searched: every `mainTip`, `"merge-base"`, `layerFinished`, `layerFinishSha` in `z-nile/engine/`; the dispatcher's `merge-base` calls judge pull requests, not layers).

**3. `./zn done` and a `main` that moves.** done already switches to a detached `origin/main`, merges the top layer with `--no-ff --no-commit`, promotes, moves the items to `done/` and runs the affected gate on that tree. That stays the only place the stack meets current `main`. Three changes:
- **Conflict.** `fail(stack.doneConflict(top, raft.id, detail))`: `<layer> does not merge onto main: ./zn restack <R>, resolve the conflict, then done again`, then git's own text.
- **Red gate.** Both rollback messages keep their text and gain `stack.restackHint(raft.id)`: `. If main moved under the stack: ./zn restack <R>`. The sentence `the affected gate fails on the done tree (rolled back); fix and retry done` stays in `main.luau` word for word, because `tests/acceptance/c0239/done.spec.luau` reads the engine's text for it.
- **Rejected push.** The steps from `local layerBranch = …` to the push of the binding commit become the body of `for attempt = 1, stack.DONE_ATTEMPTS do … break end` (`DONE_ATTEMPTS = 9`, the user's number), each attempt starting from the raft item as it was before the loop. When the push fails, done fetches first and reads origin's `main`:
  - **It is the binding commit** (the push reached origin and reported failure; `cmd.start` already handles this for its own push): print `stack.donePushLanded(raft.id)` and go on as landed. Nothing is rolled back and the pull requests stay on `main`.
  - Otherwise done puts the pull request bases back and rolls back as today, and asks `stack.doneRetry(mainMoved, attempt, basesRestored)`, where `mainMoved` is "origin's `main` is not the commit **this attempt** merged onto" (`mergedOnto`, read inside the loop):
    - `"failed"` (`main` did not move, so the rejection has another cause: a hook, a protected branch, a lost connection): today's `could not push the binding commit to main (rolled back)…`. Not tried again, on any attempt.
    - `"lost"` (`main` moved and a pull request base could not be put back): `fail(stack.doneLost(raft.id, fixes))`: `main gained commits during the gate, and a pull request base could not be put back (rolled back). Put it back with: gh pr edit <n> --base <base>[; …]. Then run ./zn done <R> again`. Not tried again: a second attempt would read `main` as that pull request's base and lose the real one for good.
    - `"again"` (`main` moved, every base is back, an attempt is left): print `stack.doneAgain(raft.id, attempt + 1)` and run the body again, so the merge, the promotion, the gate and the binding commit are all redone on the new tip. This is what a person does today by running `./zn done` again, minus the restack.
    - `"moved"` (the same on the last attempt): `fail(stack.doneMoved(raft.id))`: `main gained commits during each of 9 attempts (rolled back): run ./zn done <R> again`. It does not name restack.
  The limit is the user's scope decision of 2026-11-14 (in the Problem): the capture set none, and its fifth Solution bullet allowed a refusal for `main`'s sake only on a conflict or a red gate. After nine gates lost in a row the command stops spending CPU and says so, and the same command continues.
- **The cost of a discarded attempt is kept.** The gate's wrapper appends one measured line to `.cache/measure.tsv`, keyed by the detached head; the binding commit folds it into the ticket's `spend.d` rows and removes it from the buffer; the rollback then discards that commit, and the next attempt's head is another one, so today a rolled-back done loses its gate's cost. `costrow.Planned` gains `rows: { [string]: { ledger.Row } }` (what the fold took from the buffer, by ticket, without the caller's extra rows). `recordAndCommit` gains a last parameter `carry: { [string]: { ledger.Row } }?`, adds those rows to the commit's rows, and returns `carry` plus `planned.rows`. done keeps what the discarded attempt returned (`lostRows = attemptRows` on `"again"`) and passes it to the next attempt, so the binding commit that lands holds one row per gate that ran. A crash between attempts loses them, as a crash loses the buffer's lines today.

New in `z-nile/engine/stack.luau`, all pure: `DONE_ATTEMPTS: number`, `doneConflict(layerName, raftId, detail): string`, `restackHint(raftId): string`, `doneRetry(mainMoved: boolean, attempt: number, basesRestored: boolean): string` (`"failed"`, `"lost"`, `"again"`, `"moved"`, in that order of tests), `doneAgain(raftId, attempt): string`, `doneMoved(raftId): string`, `doneLost(raftId, fixes: { string }): string`, `donePushLanded(raftId): string`, `restackUnpushed(raftId, layers: { string }, detail): string`. The contract header of `stack.luau` ("which the Python port reads") gains the fork under `branch:` and the retry, its limit and the landed push under `land:`.

**4. `./zn restack` and a rejected push.** The push of a rebased layer becomes `sh.run` instead of `sh.git`. When it fails, restack resets the local layer branch to the commit it had (`git reset --hard <before>`, as the red-check path does, so no command reads the local tip as a moved stack), switches back to the branch it started on and fails with `stack.restackUnpushed(raft.id, left, stderr)`: `restack stopped: the push of <layer> was rejected; not pushed: <that layer and every layer above it>. Run ./zn restack <R> again`, then git's text. The repair needs no new code: `layergit.layerTip` prefers origin's tip, so the next restack sees the rejected layer still off the layer below and rebases and pushes it and the layers above it (shown by E2 on `main` as it is).

**5. `./zn work next`.** No change in `work.luau`. Its `restack` line is reached only when every layer is finished and `stacked` is false; with the fork in `workread`, a moved `main` makes neither false, so the next line after a moved `main` is the one the stack has earned (start the next layer, the review, the trace). A layer off the layer below still shows as not finished and gets the `finish` line, whose refusal names the restack, as today.

**6. Skills.** `z-nile/skills/zz-execute/SKILL.md`, Phase 5 step 2 becomes: "2. A `main` that moved needs no restack: `./zn finish`, `./zn trace` and `done` judge layer 1 against the commit where it left `main`, and `done` merges the stack onto the newest `main` and runs the gate on that merged tree. If `main` moves again during that gate, `done` merges and gates again by itself, up to nine times. Run `./zn restack <R-id>` only when `done` reports a conflict or a red gate on the merged tree (renumber colliding IDs, rerun `z-nile/check.sh --affected`, commit with `./zn commit --phase deliver`), or after a fix on a lower layer." In step 3, "after the last layer is finished and restacked" becomes "after the last layer is finished, and the layers above any fixed layer are restacked". `z-nile/skills/zz-rules/SKILL.md`, Items, after "`./zn restack <R-id>` rebases the layers above a change.": "Layer 1 only has to sit on a commit of `main`: `main` moving past it is no reason to restack, and `./zn done` merges the stack onto the newest `main` itself." `z-nile/skills/zz-review/SKILL.md`, final mode: "Run once per raft on the finished, restacked stack," becomes "Run once per raft on the finished stack, with the layers above any fixed layer restacked,". `experiments/apply-docs.py` holds the four edits. The lesson `z-nile/skills/zz-test/lessons/landings-move-every-rafts-base.md` gains a dated note in this prep (a lesson is the lead's to edit): after d0331 a landing no longer leaves another raft's lowest layer refused, so a fixture needs no restack between its cases for that reason. Step 2 writes `done` without `./zn` on purpose: `tests/acceptance/c0111/skill-docs.spec.luau` requires that the first `./zn done` in Phase 5 comes after the harvest confirmation of step 4 (the prototype's gate caught the first wording).

**Smallest change.** One helper, seven one-line call sites, one loop around existing code in `done` with its push-failure branch, one `sh.run` and one reset in `restack`, the rows a fold took passed through `recordAndCommit`, nine small pure functions, four sentences in three skills. No refactor.

**Other work that touches the same lines.** c0248 (Stacked PR delivery, prepared, in no raft) designs a `baseFor` over these call sites and says the lowest unlanded layer above a landing is based on `origin/main`'s tip; its sequestered `layers-land.spec :: AC8` expects `is not based on main: ./zn restack R0010` there. The user decided (2026-11-14, in the Problem) that such a layer is judged by its fork too, so c0248 is redesigned after d0331 lands; d0331 does not edit c0248's documents or specs (they are sequestered and approved; only c0248's own prep may). c0300 (new) is about commits a restack drops and is not touched. c0302 is a dependency (the user's decision).

### Scalability
One extra `git merge-base` per command that walks a stack (per raft in `./zn work queue`). done's retry costs one more gate per attempt, at most nine; with no retry a person paid the same gate plus a restack by hand.

### Maintainability
The rule lives in one function, `layergit.mainFork`, and every site calls it; `acceptance/layer-one.spec.luau` fails if any of the seven goes back to `main`'s tip (one mutant per site, all run). done's retry decision is a pure function with its own cases.

### Usability
A worker no longer sees `is not based on the layer below` on layer 1, and `./zn work next` no longer sends it back to `finish` a layer that was finished. The refusals that remain say what to run: a conflict and a red gate name `./zn restack <R>`, nine lost gates name `./zn done <R>` again, a rejected restack push names the layers left and `./zn restack <R>` again.
