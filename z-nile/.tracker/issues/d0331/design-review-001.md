### F1 [high] AC7's "a push rejected for any other reason is not retried" passes for an engine that retries every rejected push
Where: d0331.md, Design §3 "Rejected push" and Rules and mutants rows "a push lost for another reason is not retried" and "a retry merges onto the fetched tip"; acceptance/retry.spec.luau, acceptance/done-moved.spec.luau
Evidence: the only cases where done's push of the binding commit fails are AC6 and AC7 of done-moved, and in both `main` moved. "Not moved" is tested only on the pure function (`stack.doneRetry(false, …) == "failed"`), never through `./zn done`. P1: with `stack.doneRetry(true, attempt, #unrestored == 0)` in main.luau, so that a hook rejection, a protected branch or a lost connection is retried as if main had moved, all 17 cases pass. A second plausible wrong implementation, `mergedOnto` read once before the loop, so that from attempt 2 on any rejection counts as "main moved", also passes. The Rules table's mutant for the rule (`done-retry-any-failure`) lives in stack.luau, so it cannot see the call site that computes `mainMoved`.
Critique: the criterion is Checked and check.sh's AC7 line names it, yet an engine that spends nine gates on every rejected push passes. The tempting fix is one more pure-function case, which still cannot see the wiring.
Consequences: an integration case needs a push to main that origin rejects while main stands still. The fixture's other pushes to main (the stub gate's `elsewhere` commits from `f.other`, `trackerfix.elsewhere`) must still go through. A per-attempt `mergedOnto` case also needs one move followed by a rejection that has nothing to do with main.
Recommendation: add to done-moved.spec a fourth one-ticket raft and an origin `update` hook that rejects `refs/heads/main` only when the new commit's subject starts with `R0040: bind` and a file `<base>/reject-bind` exists (`git log -1 --format=%s "$3"`), so that `elsewhere` pushes still pass. Case (a), main still: done fails with `could not push the binding commit to main (rolled back)`, `gateRuns() == 1`, one `pr edit 1 --base layerbase`, and no "each of 9 attempts". Case (b), the stub gate moves main once and creates `reject-bind`: `gateRuns() == 2`, the same "could not push" refusal, nothing about nine attempts. Add the two rows `done-moved-always` (main.luau passes `true`) and `done-merged-onto-once` to the Rules and mutants table, both run.

### F5 [medium] Every attempt done rolls back loses that attempt's gate cost from the spend record
Where: d0331.md, Design §3 "Rejected push" and E5; main.luau `recordAndCommit` (costrow.plan / writeFiles / writeBuffer), costrow.luau, z-nile/lib/bounded.pl
Evidence: the gate (`z-nile/check.sh` wrapped by bounded.pl with `ZN_MEASURE_BUFFER=1`) appends a measurement line to `.cache/measure.tsv` with `ZN_MEASURE_HEAD` set to the detached merge base. `recordAndCommit` folds the lines `buffer.fold` takes (by the focused issue's id while `.cache/tracker-focus` exists, otherwise by a head equal to the detached HEAD) into the binding commit's `spend.d/<writer>.tsv` rows. It then rewrites the buffer with only the lines it kept (`costrow.writeBuffer(planned.bufferText)`). When the push fails, the rollback's `reset --hard layerBranch` throws away the binding commit, and with it the only copy of those lines. The next attempt's gate line carries the new head, so the final binding commit records one gate where the command ran up to nine.
Critique: the design says it "costs one more gate per attempt", and that is true, but zz-stats will never see it. One rollback lost one gate before. The loop makes the loss routine. The tempting fix is to restore `planned.bufferPrevious` on rollback, but the restored lines carry the old head, which `buffer.fold`'s `mine()` will not take at the next attempt, so they would sit in the buffer until they age out.
Consequences: the carried rows have to be attributed to the same issue as the final attempt's. A crash between attempts loses them as today.
Recommendation: either keep each discarded attempt's taken rows (the `planned.files` rows) in memory and pass them to the next attempt's `recordAndCommit` as extra rows, or run each attempt's gate with `ZN_MEASURE_ID` set to the raft's first member (measure.pl's `buffer` already reads it) and, on a rollback after the binding commit, write the buffer back to `planned.bufferPrevious` plus whatever was appended since, so the next fold takes those lines by id. Either way the binding commit holds one row per gate that ran. Add a done-moved case: the stub gate appends a measurement line the way bounded.pl does (or with `./zn record --phase test`), and AC6 asserts two gate rows in the landed issue's `spend.d`. Add the matching mutants row.

### F6 [medium] A push that reached origin but reported failure is retried as "main moved", and the retry crashes on its own landing
Where: d0331.md, Design §3 `doneRetry`; prototype loop in cmd.done
Evidence: after a failed push, done puts the bases back, rolls back, fetches, and compares origin's main with `mergedOnto`. If the push landed but the client saw an error (the case `cmd.start` handles at main.luau:3688-3696, "a push that reached origin but reported failure (the connection dropped after it)"), origin/main is the binding commit, so `mainMoved` is true and the answer is "again". Attempt 2 then detaches at the landed commit, `merge --no-ff --no-commit land` says "Already up to date", and `move(m, "done")` runs `git mv` on folders that are already in `done/`, which raises through `sh.git`. That leaves a detached HEAD, the pull request bases restored to the layer branches (so GitHub never marks the upper ones merged), and the local `main` and the main checkout not updated.
Critique: the loop turns a rare failure that today only prints a wrong "rolled back" into a crash after a successful landing, with the PR state undone. The tempting fix is to compare origin/main with the binding commit's sha, but the binding commit was just reset away, so its sha has to be kept.
Consequences: the "landed" answer must redo the retargeting (or skip the restore) and run the post-landing steps. It must also check that the top layer is reachable from origin's main, not just that main moved.
Recommendation: after the fetch, if `land` is an ancestor of origin/main, answer "landed". Retarget the recorded pull requests to `main` again, run the post-landing steps (local `main`, the main checkout), and print that the push reported failure but reached origin. Make `doneRetry` (or a separate pure function) take that fact, with retry.spec cases. Add a done-moved case with a `git` shim on PATH that passes every call through and exits 1 after a successful push of `HEAD:refs/heads/main`: done prints `landed`, origin has one bind, and the PR's last edit is `--base main`.

### F7 [medium] When a pull request base is not put back, done answers "main gained commits during each of 9 attempts", which is false
Where: d0331.md, Design §3 (`"moved"` … "or a base could not be put back"); acceptance/retry.spec.luau (`doneRetry(true, 1, false) == "moved"`)
Evidence: on attempt 1, a failed `gh pr edit --base <old>` leads to `fail(stack.doneMoved(raft.id) .. extra)`, which prints `main gained commits during each of 9 attempts (rolled back): run ./zn done R0010 again; could not put back R0010/2/c0020`. Running done again then reads that PR's base as `main`, records it as the old base, and `restoreBases` skips base `main`, so the original base is never restored.
Critique: the message gives a false count and the wrong next step, and the sequestered spec pins the merged answer.
Consequences: a fourth answer needs its own message, its own spec case and its own mutant. The person has to set the base back by hand before running done again.
Recommendation: add an answer `"lost"` (bases not put back, at any attempt) whose message names each layer left on `main` and the base it had (`gh pr edit <n> --base <base>`), then says to run `./zn done <R>` again. Keep `"moved"` for the last attempt only. Update retry.spec to `doneRetry(true, 1, false) == "lost"`, and add a mutants row.

### F9 [medium] The capture's "the layer holds only its own commits above it" is made true by definition, and nothing refuses a layer that does not
Where: d0331.md, "The rule after this issue" ("The commits above the fork are the layer's own by construction"), AC1
Evidence: `fork..tip` never holds a commit of main, because that is what a merge base is, so the condition as designed cannot fail. A layer 1 that merged another raft's unlanded layer, or was cut from a branch that is not main, holds commits that are neither main's nor its own. finish squashes them into `<issue>: <title>`, and done lands them. AC1 checks only that main's new commit is absent.
Critique: one of the two conditions in the capture's first Solution bullet has no check and no criterion.
Consequences: a check must accept the histories the tools make: a fresh layer (its claim `tracker: start <R>` sits on main), a layer that merged `origin/main` (its fork moves up, and its claim is still the oldest own commit), a re-finished layer (no claim left, its finish commit is the root), and a layer restack moved.
Recommendation: refuse layer 1 when `fork..HEAD` holds a commit that is neither the raft's claim commit, the issue's finish commit, a merge of main, nor a descendant of the claim or the finish commit. Name the first such commit and `./zn restack <R>`. Cases: a layer 1 that merged a side branch is refused, one that merged `origin/main` is accepted, and a re-finished one is accepted. Or put this reading to the user and record a `Decided with the user` line that the by-construction reading holds.
