### F1 [medium] The `reasoned` row "the fork is not taken while the raft sits on an unlanded raft's base commit" is not an equivalent mutant: a stopped restack reaches a state that tells them apart, and no spec covers it
Where: d0331.md, Rules and mutants, the `reasoned` row and the paragraph under the table ("restack rebuilds the base and moves layer 1 in the same command, so no reachable state tells the two apart"); Design 2, the `workread` paragraph.
Evidence: `cmd.restack` calls `layergit.buildBase(raft)` first. When D's top layer has moved, that call rebuilds `<R>/base` and pushes it to `origin/<R>/base`. Only after that does restack rebase layer 1, and three paths leave layer 1 where it was: `restack stopped at …: conflict` (rebase aborted), `… check.sh failed` (`reset --hard before`), and d0331's own new rejected-push path (`reset --hard before`). After any of them, `origin/<R>/base` is the new base B2 and layer 1 still holds the old base B1. Today (and with this design) `finish` takes `base = raftBase tip = B2`, `is-ancestor B2 HEAD` is false, and it refuses with `is not based on the layer below: ./zn restack R`. Now take the mutant the row names (the fork taken on `<R>/base` too, e.g. `layerOneBase` returning `mainFork(firstTip, tip)` when `pr ~= "main"`). It gets `merge-base(HEAD, B2)`, which is below B1, so the ancestor check passes and `finish` squashes B1 (and whatever of D's old layer lies above that merge base) into R's finish commit. That is the E10 defect again, now before D lands. `f0399/on.spec` never stops a restack, so nothing kills this mutant.
Critique: the design itself is right (`layerOneBase` returns `raftBase` unchanged when `pr ~= "main"`), but the rule is unguarded, and the stated reason it can't be guarded is false. An executor who "simplifies" `layerOneBase` to one `mainFork` call passes every spec. The tempting fix is to reword the paragraph and keep the row `reasoned`, which still leaves the rule unguarded.
Consequences: a new case needs a way to make restack stop after `buildBase`. A conflict is the cheapest: D's re-finished layer and R's layer 1 change the same file. The case also checks `workread`. The Design's claim that `workread` keeps `mainFork` still holds there: layer 1's finish parent B1 is neither B2 nor the fork, so the layer reads as not finished both ways and `work next` gives `finish`, which refuses.
Recommendation: add a case to `on-landed.spec` (or a sibling spec), before D lands: R's layer 1 is finished on B1, D's top layer gains a change and is finished again, and `./zn restack R0020` stops at layer 1 on a conflict. Then `./zn finish f0030` refuses naming `./zn restack R0020` and leaves HEAD as it was, and `origin/R0020/base` is not an ancestor of HEAD (the state is real). Add the mutant `unlanded-base-forked` (`layerOneBase` takes the fork when `pr ~= "main"`), mark the row `run`, record the kill in E11, and correct the equivalence sentence (the `workread` half stays `reasoned`, for the reason above).
