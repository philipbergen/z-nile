Critique: Design 1a exists to keep "the layer holds only its own commits above it" true for a layer cut from a base commit (G2, E10). The guard identifies "the base commit" by the ref's current value, but a layer can hold any earlier value of that ref. The obvious fix is to also read the local `<R>/base` or the reflog. That fails in another clone (round 002 F2) and when the local ref has already moved (`buildBase` moves the local branch before the push too).
Consequences: identify the base commit by what it is, not by where a ref points. `buildBase` commits every base commit with the subject `tracker: base <R> on <D>`, so the guard can be "some commit in `mainFork(firstTip, onto)..firstTip` has the subject `tracker: base <raftId> on `" (one `git log --grep` over the layer's own range). This also covers the other clone with no ref (round 002 F2, with no ref read at all) and the hand-deleted `<R>/base` that Design 1a now accepts as a squash. The subject becomes a contract between `buildBase` and `layerOneBase`. Keep it in one place (a `stack.luau` or `layergit` constant used by both), and list it in the `stack.luau` contract header. `landed-base-local-only` loses its meaning, and the guard's mutants become "the current ref only" (the prototype as it is) and "existence of the ref only". Open question: does the next `./zn restack R0020` bring a layer 1 on B1 (B1 above R0010's old finish, after R0010 landed with a different finish) onto `main` as one finish commit with neither B1 nor R0010's old commit in it? That is f0399's and `stack.rebaseUpstream`'s path, and it is not run today. If it does not, the refusal text leads to a restack that cannot repair the layer.
Recommendation: change the guard in Design 1a and `layerOneBase` to look for a base-commit subject of the raft in `fork..firstTip` (drop the ref read and the "deletes it by hand" sentence), with the subject as a shared constant. Add a case to `on-landed.spec` (a fresh fixture, or a reordering in which case 2 leaves layer 1 on B1 through the landing).
