# d0426: Spec runs leak kernel memory

## Problem
- On 2026-11-21 at 04:38 PST the owner's Mac kernel-panicked with "zone map exhausted … likely due to memory leak in zone [data.kalloc.1024]" at 20,764,352 elements in use.
- Each `z-nile/check.sh --affected` run adds about 3,400 to 4,900 in-use elements to `data.kalloc.1024` (as read by `zprint`) that do not come back after minutes of rest and that only a reboot frees.
- That measurement is of a whole gate run (format, lint, type checks, Rojo builds, the Go build, vet and test stages, and the specs), so it does not show which stage leaks.
- Nothing in the gate, the spec runner, the worker's stop message or the board reads or shows that count, so no session learns the zone is filling before the machine panics.
- The operation that leaks is not named: batches of 100 to 300 plain process spawns, sandbox-exec runs, git init/clone/worktree add, file creation and deletion, lune starts, ptys, flock and znlive daemon operations each added nothing.
- No skill tells workers and reviewers to limit gate runs, so every session and worker on the machine adds to the same count.

## Non-goals
- This work does not fix the macOS kernel defect itself or report it to Apple; it only stops the gate from triggering it.
- This work does not guard any kernel zone other than `data.kalloc.1024`.
- This work does not reboot the machine or free the zone itself; it only tells the person a reboot is due.
- This work adds no meter or guard for operating systems other than macOS.
- This work does not use root or any tool that needs it; every reading comes from `zprint` as the ordinary user.
- The leak check is not a spec and is not run by the gate; it is run by hand on the owner's machine.

## Solution
- Before starting, the gate and the spec runner read the in-use count of `data.kalloc.1024`: above the warning level they print one line saying a reboot is due and how full the zone is, and above the refuse level they do not start and say to reboot.
- Where the count cannot be read (no `zprint`, another OS), the gate and the spec runner print nothing about it and run as they do today.
- The warning and refuse levels are settings whose defaults are both below 20,764,352, the count at which this machine panicked.
- One command prints the current count and both levels, and the worker's stop message and the board show the same three numbers.
- This work names the leaking operation: the ticket records which gate operation leaks, where it runs (a gate stage, the spec runner, or a spec's own fixture code), and the meter readings from the bisection that show it.
- This work also removes the leak: the code the bisection names is changed so the gate no longer performs that operation, or performs it in a way that does not leak.
- A leak check reads the zone's in-use count, runs `z-nile/check.sh --affected` three times in a row with no other gate running on the machine, waits five minutes after the last run ends, and reads the count again.
- The leak check passes only if the second reading is at most 1,000 elements above the first, which is under a tenth of the 10,200 or more that three runs of today's gate add.
- The leak check prints both readings, the difference and the 1,000 limit, and the work is not done until it passes on the owner's machine.
- From the first merge of this work, the zz-test, zz-execute and zz-review skills tell workers and reviewers to run targeted spec files while iterating and the gate once, with one gate at a time on the machine.
- The change that makes the leak check pass also removes that guidance from the skills, so the guidance is gone from all three when the work is done.

## Design
### Step 2: the machine-wide gate queue
- Lock: one file, `<base>/pickman-gate-queue-<uid>/lock`, `<base>` = `/private/tmp` on macOS and `/tmp` elsewhere (the shared spec lanes' precedent in tests/lib/fence.luau). Outside every checkout so all checkouts, worktrees and repositories share it; not `$TMPDIR`, which a sandbox or another account's shell may set differently. The folder is 0700, must be a plain folder owned by this user, never a symlink.
- Mechanism: `z-nile/lib/gatequeue.pl` (perl, `Fcntl` flock; no `flock` binary). It opens the lock file, takes an exclusive flock, forks the command and waits; the command (exec closes the descriptor) never holds it. The lock is the open handle of the waiting parent, so SIGKILL, a crash or a normal exit releases it: there is no lock file to clean.
- Holder description: the holder writes one tab-separated line (pid, checkout, mode, since) into the lock file itself, only after it holds the lock. A reader reads it only after its own try of the lock failed, and believes it only if that pid is alive; with no lock held nothing is read ("no gate is running").
- Waiting: first a non-blocking try. On failure it prints `gate: waiting for another gate on this machine: pid P, checkout C, mode M, since T`, registers `waiting/<pid>` (a file the waiter flocks while it waits, so a dead waiter is seen and removed), then blocks in flock under `alarm` (no polling). On getting the lock: `gate: proceeding after waiting N s`.
- Bound: `ZN_GATE_WAIT` seconds, default 1800; 0 fails at once; a timeout fails (exit 1) naming the holder and the wait; it never runs unqueued. A non-number falls back to the default.
- Switch: `ZN_GATE_QUEUE=off` skips with one line. `ZN_GATE_QUEUE_DIR` (specs) overrides the folder.
- Where: check.sh's outermost block (`ZN_MEASURED` unset), after `kzone_guard`, for every mode but `--plan`; it wraps the `bounded.pl --time 3600` call, so the hour limit excludes the wait. A fixture gate inside a spec run has `ZN_MEASURED` set (or never reaches this block) and takes no lock.
- `./zn gate-queue` runs `gatequeue.pl --list`: one line for the holder, one per waiter, or `no gate is running`.
- Not queued: `lune run tests/run -- <files>` (iterating workers run a few files; the runner's own per-checkout lock and the shared eight worker lanes stay). `./zn finish`, `./zn done` and `./zn land` run `z-nile/check.sh` as a child (engine/main.luau `sh.stream("bash", {"z-nile/check.sh", ...})`), so they queue.
- Not fair: flock grants in no promised order; a waiter waits at most the bound.

## Acceptance criteria

### Checked
- AC1: while one gate holds the machine lock a second waits, printing one line naming the holder, and proceeds when the first ends, however it ends (exit, SIGKILL).
- AC2: the wait is bounded by `ZN_GATE_WAIT` (0 fails at once); a timeout fails naming the holder and never runs the command.
- AC3: `ZN_GATE_QUEUE=off` runs unqueued and says so; a description file with no lock held is never believed.
- AC4: the default lock folder is per user and outside every checkout; `--plan` and an inner (`ZN_MEASURED`) gate take no lock; `./zn gate-queue` lists the holder and the waiters.
