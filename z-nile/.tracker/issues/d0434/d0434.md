# d0434: Restack stops on conflict

## Problem
- `./zn restack <R-id>` aborts the rebase at the first conflict and leaves the layer's branch unchanged, so the worker must rebase the whole layer by hand outside zn.
- A `./zn restack <R-id>` run after a hand rebase that exists only on the local branch takes the layer's tip from `origin`, finds it not stacked, and `git reset --hard`s the local branch to it, discarding the hand rebase.
- When a restack has stopped on a conflict, `./zn work next` does not name continuing it as the raft's action.

Decided with the user (2026-11-21, who resolves): "zn restack conflict shoudl be handled by the ai skill around it". So a conflict during a restack is not a stop for the person: the engine leaves the rebase in progress and names the conflicted files, and the skill the worker follows (zz-execute, through z-work) tells the worker to resolve the conflicts itself, rerun what the resolved files affect, and continue the restack with the one command. Only a conflict the worker cannot resolve with confidence (two sides that both changed the same behaviour on purpose) goes to the person, as a question that names the files and both intents.

## Non-goals
- zn does not resolve conflicted files itself or pick a side for the worker.
- It does not reuse resolutions through git's rerere or any other store of past resolutions.
- A restack run in which no layer conflicts and no layer's local branch holds commits that `origin`'s branch lacks leaves the same branches and pushes as today.
- It does not change when a restack is required or how often main moves during a landing.

## Solution
- When a layer's rebase conflicts, `./zn restack <R-id>` leaves that rebase in progress in the raft's worktree, exits non-zero, and prints the layer, each conflicted file and the exact command that continues.
- After the worker has resolved and staged the conflicted files, one zn command continues the in-progress rebase, runs that layer's `check.sh`, pushes the layer when it passes, and only then restacks the remaining layers, without restarting any layer already rebased in that run.
- Restack takes a layer's tip from the local branch in the raft's worktree whenever that branch holds any commit that `origin`'s branch for the layer lacks, and from `origin` otherwise.
- When the local tip it takes is not based on the current tip of the layer below (for example, a hand rebase onto a main that has since moved, or a layer above one that restack just moved), restack rebases that local tip onto the layer below and never rebases `origin`'s tip for that layer.
- When `origin`'s branch for a layer holds a commit whose change is on neither the local branch nor the layer below, restack exits non-zero, names the layer, and changes no branch for it or any later layer.
- Restack never runs `git reset --hard` on a local branch holding commits that `origin`'s branch lacks.
- Restack skips a layer as "already stacked" only when `origin`'s branch for that layer is itself at the stacked tip.
- When a layer's stacked tip is on the local branch but not on `origin`'s branch, whether from a hand rebase, a rebase restack just made from the local tip, or a continued resolution, restack runs that layer's `check.sh` and pushes the layer when it passes, before it restacks the next layer.
- When that `check.sh` fails, restack exits non-zero, names the layer, pushes nothing for it or any later layer, and leaves the layer on its local branch (a restacked tip stays there unpushed, for the worker to fix and `./zn finish`; a branch that held a tip of its own is not touched).
- After any restack or continue run that exits zero, `origin`'s branch for every layer of the raft is stacked on the layer below, so `./zn done` does not reply "run ./zn restack".
- A conflict resolution counts as kept once it is a commit on the layer's local branch or is staged in the in-progress rebase, and no restack run removes either without the worker's explicit abort command.
- While a raft's worktree has a restack rebase in progress, `./zn work next` names the continue command as that raft's action.

## Design
Risk reason (risky): it rewrites published layer branches and decides which tip a restack trusts; a wrong choice discards or republishes work.

- **Cause of R0138's reset.** `layergit.layerTip` returns `origin/<layer>` before the local branch; `cmd.restack` took it, judged "already stacked" on it, then `checkoutLayer` + `git reset --hard <origin tip>` overwrote the hand-rebased local branch. Now `restackplan.source` takes the local tip whenever it holds a commit origin's lacks; the only reset left is of a branch that holds nothing origin lacks.
- **Modules.** `engine/restackplan.luau` (pure: `source`, `decide`, `trusted`, `emptied`, `movedSince`, `restoreTo`, `published`, `pushReason`, marker text, messages); `engine/restackcmd.luau` (git edge, modes start/continue/abort); `cmd.restack` in `main.luau` is a few lines; `workread.restackStopped` + `work.luau` answer `work next`.
- **Marker** `<worktree git dir>/zn-restack.state`: written when a run starts (raft, back, start commit, per layer `orig` local tip and `judged`, origin's tip after the run's fetch), rewritten as branches move (`left`, also for layers taken as they are, so `--abort` works after a `--continue`; `pushing <layer> <sha>` before each push and `pushed <layer> <sha>` after it, `red <layer> <sha>` at a red check), `conflict <layer> <own commits>` and `file` lines added at a stop, removed at the end. A crash anywhere leaves `--continue` and `--abort` usable.
- **Walk.** Each layer: tip = local if it holds a commit origin lacks, else origin's. Diverged (both have extra commits): local is taken only if origin's tip is `refs/zn/pushed/<layer>`, the tip this clone itself pushed (written by `start`, `finish` and restack after their push succeeded); otherwise (a fresh clone, a layer someone else pushed, a tip merely fetched or reset to) exit 1 naming both shas and what to do (fetch, rebuild on origin's tip, or ask), nothing changed. No reflog, no pre-fetch tip. Stacked + on origin: skip. Stacked, local ahead: check.sh. Not stacked: `rebase --onto` (rerere off); a rebase or resolution that leaves fewer own commits stops with "emptied ... stop and ask". Every layer runs its check.sh; a red check stops the run, pushes that layer and everything above it never, and keeps the restacked tip on the layer's branch (see Red check).
- **Publishing (per layer; the owner's ruling of 2026-11-22 reversed G1).** A layer is pushed on its own as soon as it is restacked (or its local tip is taken) and its `check.sh` passes, before the next layer is restacked: `git push --force-with-lease=refs/heads/<layer>:<lease> origin <layer>`. The lease is the tip this run itself pushed for the layer when it did (a layer pushed, then rebased again after main moved while a conflict waited), else the origin tip the run judged after its fetch (empty: the layer must not exist on origin, never a plain `--force`). Both are kept in the marker so `--continue` uses the same value, never the current remote-tracking ref. A refused push prints only git's reason lines, never its words about the remote, which carry the remote's address. Crash windows: the marker gets `pushing <layer> <sha>` before the push; `--continue`, `--abort` and the next plain restack ask origin (`git ls-remote`) whether that sha landed and, when it did, note it (`refs/zn/pushed`, the `pushed` line, the remote-tracking ref), so a run killed after the push is neither treated as unpushed by `--abort` nor refused as foreign later (test seam: `ZN_RESTACK_KILL=before-push|after-push|after-note` exits the run there; nothing else sets it). `refs/zn/pushed/<layer>` and the marker's `pushed <layer> <sha>` line are written only after that push succeeded. A stop (conflict, red check, emptied commit, refused lease) leaves the layers below it, which passed, pushed, and it and the layers above it not pushed. `restacked` is still emitted once, at the end of a run that moved or pushed anything: it means the raft is restacked, so a run that stops emits nothing, and the run that finishes the stack (a `--continue` or a plain restack) emits it.
- **Red check.** The restacked tip stays on the layer's branch, not pushed (the marker's `red <layer> <sha>`); layers below that passed are pushed, it and those above are not. Nothing is reset: a reset would make the next restack rebase the old tip onto the same layer below and hit the same red check, and `./zn finish` refuses a layer not based on the layer below, so the worker could never fix it. The worker fixes the layer on that tip, runs `./zn finish <issue>`, then `./zn restack` (the tip is local-ahead of origin and `refs/zn/pushed` still equals origin's tip, so it is this clone's own work and is trusted). `work next` answers `restack` with a note that names the fix and `finish` (not "Run ./zn restack") while the branch is still at the red tip; once the worker changed the layer it answers as for any unstacked raft.
- **Conflict.** The rebase stays in progress on that layer; exit 3 (0 success, 1 every refusal); message names layer, files, `--continue`, `--abort` and the layers already pushed. A plain restack then refuses and names both commands. `work next` answers `restack` with the resolve-and-continue note.
- **Continue.** Refuses naming `unmerged: <file>` and `conflict marker: <file>:<line>` (markers looked for only in the recorded conflicted files), then `GIT_EDITOR=true git rebase --continue`, then the walk again (the continued layer is local-ahead: checked; the layers above rebased); one more stop repeats. With no rebase in progress it refuses a dirty worktree.
- **Abort.** Refuses (naming them, changing nothing) a branch that is at neither of the two shas the run could have left it at (`orig`, or for a pushed layer its pushed tip, and `left`), and a dirty worktree when no rebase runs; else aborts the rebase, returns to the start branch (or commit), restores the local branches of the layers this run has not pushed (deletes only ones the run created and did not push). A layer the run pushed is put to the tip it pushed (a pushed layer that was rebased again and not pushed goes back to its pushed tip; a branch the run created and pushed is kept), because `--abort` never force-pushes origin back; the message names those layers. The half-moved stack is continuable: a later plain `./zn restack` finds the pushed layers local == origin and stacked, skips them, and restacks the rest from the layer below. Origin then holds the pushed layers on the new base while the layers above still rest on the old commits, the same state any amend of a lower layer leaves, which `./zn done` refuses until restacked.
- **Skills.** zz-execute Phase 5 step 2 and z-work step 3 tell the worker what to do (specs by name via `z-nile/affected`, red check after continue, empty resolution, repeat, unattended = questions.md, never skip/drop/force-push).

### Scalability
One walk is a few git calls per layer, as before.
### Maintainability
Decisions are pure and spec'd without git; main.luau gains no top-level local.
### Usability
The conflict message prints the layer, each file and both commands; `work next` names the action.

## Acceptance criteria

### Checked
- AC1: When a layer's rebase conflicts, `./zn restack <R-id>` leaves that layer's rebase in progress in the raft's worktree, exits 3, prints the layer, each conflicted file, the continue and abort commands and the layers already pushed; the layers below it that passed are pushed, it and the layers above it are not, and no `restacked` is emitted.
- AC2: A restack run while one is in progress refuses with exit 1, names `--continue` and `--abort`, and leaves the marker, the stopped commit and any staged resolution as they were.
- AC3: While a restack is stopped on a conflict, `./zn work next <R-id>` answers `restack`, names the conflicted file, the `--continue` command, the specs command and the empty-resolution rule.
- AC4: `--continue` refuses while a path is unmerged, and while a conflict marker is staged in a conflicted file, naming each, and leaves the rebase in progress.
- AC5: After the resolution `--continue` finishes the rebase, restacks the layers above on it with trees equal to a by-hand rebase (a Markdown `=======` underline in another file does not block it), pushes each layer in a push of its own once its check passes (layer 2 before layer 3 is restacked), emits `restacked` once, removes the marker and returns to the starting branch; a following restack says already stacked.
- AC6: `--abort` restores the local branch of every layer the run has not pushed (a pushed layer that was rebased again and not pushed goes back to the tip it pushed; a branch the run created and pushed is kept), the worktree and the starting branch exactly as before the run, and leaves every layer the run pushed at the tip it pushed (origin is never moved back) and names it; with nothing pushed origin is as before the run; a following `--continue` says no restack is in progress.
- AC7: A layer whose local branch was hand rebased onto the layer below keeps its tip and the layer above it is restacked on it and pushed; when the hand rebased layer's check.sh is red it and the layers above it are not pushed.
- AC8: A restack that stopped on a conflict, whose rebase the worker then continued by hand, is finished by a plain restack that keeps that rebase.
- AC9: When origin's branch for a layer holds a commit that the local branch was never based on, restack exits 1 naming the layer and both tips and changes no branch.
- AC10: When a restacked layer's `check.sh` fails, restack exits 1 naming the layer, pushes nothing for that layer or any layer above it (a layer below that passed is already pushed) and keeps the layer's restacked tip on its local branch, unpushed, naming `./zn finish <issue>` as the way on.
- AC11: zz-execute and z-work tell the worker to resolve a restack conflict itself, run the specs by name with the command that lists them, continue with one command, repeat if a later layer stops, recover from a red check, stop and ask on an empty resolution or an unclear owner's side, and never skip, drop or force-push by hand.
- AC12: Origin's layer re-finished with the same subject but other content by someone else, while the local branch is stale, is refused and not overwritten.
- AC13: A push to a layer from another clone between the stop and `--continue` is not overwritten: that layer's push fails its lease, origin keeps that commit, nothing above it is pushed (layers below that passed are), it is not noted as pushed and nothing is emitted.
- AC14: A rebase or resolution that leaves a layer with fewer own commits than it had stops with "emptied ... stop and ask" and pushes neither that layer nor any above it.
- AC15: `--continue` and `--abort` with no rebase in progress refuse a dirty worktree and discard nothing; a restack that stopped mid-walk (a red check) leaves a marker so `--abort` restores the layers it had not pushed; the layers that passed were pushed.
- AC16: `--abort` refuses a branch that moved since the run left it, names it, changes nothing and deletes nothing.
- AC17: A layer someone else fast-forwarded before the run is built on by it, and its first push succeeds with their commit included and `refs/zn/pushed` noted.
- AC18: A re-finish by someone else, fetched into this clone before the run, is not overwritten by a stale local copy (exit 1, both tips named, origin unchanged).
- AC19: After an abort, a local amend does not overwrite a commit the first run had only fetched (a layer the run could not push, built on someone else's fast-forward, is put back and its amend is refused).
- AC20: After a conflict, a resolution, a continue and a later red check, `--abort` restores every branch the run had not pushed and keeps the one it pushed.
- AC21: A diverged layer this clone did not push (no `refs/zn/pushed`) is refused, naming both tips and what to do.
- AC22: A layer this clone pushed and then amended locally is trusted: restacked and pushed.
- AC23: Someone pushes and a fetch follows between the stop and `--continue`: that layer's push fails its lease and origin keeps their commit; it is not noted as pushed.
- AC24: A marker with no conflict recorded and a rebase in progress is treated as a stopped restack (`restack`, `--continue`, `work next`).
- AC25: After an abort that left layers pushed, a plain `./zn restack` goes on from them (does not push or rebase them again), stops on the same conflict, and a `--continue` finishes the stack, each remaining layer pushed once; a `--continue` straight from the half-published state pushes only the layers above.
- AC26: A red check above a pushed layer leaves the restacked tip on the layer, unpushed; `work next` names the fix on that tip and `./zn finish <issue>` (not the restack that would hit the same red check); a plain restack with nothing fixed stops again and loses nothing; after the fix and `./zn finish`, a plain restack finishes the stack, pushes only the layers above, and the layer below keeps what it pushed.
- AC27: `--continue` after main moved again (and was fetched) re-pushes a layer the run had already pushed under the lease of its own push, not the stale pre-run tip, and the stack ends on the new main; when that second pass is red, `--abort` puts the layer back on the tip it pushed.
- AC28: A restack killed before its push, after it, or between the note and the marker is reconciled with origin by the next restack and by `--abort`: a push that landed is noted (`refs/zn/pushed`, `pushed`) and its layer stays; one that did not land is put back.
- AC29: A layer that is not on origin is pushed under a must-not-exist lease (another clone creating it first keeps its commit), and a layer with no local branch that a run created and pushed stays after `--abort`.

## Verification log
- 2026-11-22, review round on per-layer publishing: red tests committed first (restackplan.spec 4 red, acceptance spec 6 red), then the fixes; the acceptance spec (30 cases), restackplan.spec, stack-land.spec and the ticket's check.sh are green; each fix has a hand mutant (see the mutant table), each verified applied with `git diff --stat` before its run.
- Decision (a `--continue` after main moved mid-run): it re-rebases and re-pushes the layers it already pushed, so the stack ends on the current main. The alternative, freezing the base the run started with, would finish on a base `./zn done` refuses anyway and cost a second restack; it needs a stored base and a special case in every layer's `onto`. Re-rebasing cannot loop: a pass moves a layer only when the layer below or main moved since, each push is leased on the run's own previous push, and a run ends when a pass moves nothing.
- A half-published stack shows the pull request of an upper layer with the lower layer's old commits (its base branch was rewritten under it). A hand `gh pr merge` there would bring those old commits into the base. zn's own `done`, the stack landing and `finish` refuse that state (not stacked: run `./zn restack`), so merge only through them.
- Defect, 2026-11-24: `./zn restack <R-id>` had no main-checkout refusal. The launcher `zn` changes into its own checkout for every command but `work`, so the main checkout's `zn restack <R-id>` typed inside a raft's worktree ran in the main checkout, where a plain restack fetches, writes `zn-restack.state` under the main checkout's git dir, switches any layer branch not checked out elsewhere, resets, rebases, runs checks and pushes (a worker was told to run main's zn from a worktree and happened to use `--continue`, which answered "nothing to continue"). Fixed: `cmd.restack` calls `refuseInMainCheckout` before `restackcmd.run`, so every form (plain, `--continue`, `--abort`) refuses before any fetch or write with `restack must run inside a worktree: cd "$(./zn worktree <R-id>)" && ./zn restack <R-id>[ --continue| --abort]`; the helper takes the worktree's target and the command to run there when the caller knows them. Spec: stack-land.spec "restack, --continue and --abort refuse in the main checkout and change nothing there" (a branch on origin the main checkout has not fetched makes a fetch visible; HEAD, branch, status, worktree list, every ref, the wt's HEAD and the marker are compared). Red first (202f34ce6: the plain restack exited 0 in the fixture's main checkout); mutant (the refusal removed): red again; this ticket's acceptance spec `restack-conflict.spec.luau` runs every restack in the raft's worktree: it passes (31 cases with the set-up, 184 s), unchanged.

## Open to the human
- Scope question (G1), answered. The captured Solution says each layer is pushed "when it passes, before it restacks the next layer". The lead had decided to push everything at the end in one atomic push. Asked "during a restack, are layers pushed one at a time as each passes, or all together once the whole stack is done?", the owner answered (2026-11-22), verbatim: "1 yes push early, you may push before each review and when ready." So the Solution sentence stands and G1 is overruled (guesses.md): a layer is pushed when its check passes. Rule for `--abort` after some layers were pushed (a builder's choice inside that ruling, open to the owner): it restores only the layers not yet pushed and never force-pushes origin back.
