# d0434: Restack stops on conflict

## Problem
- `./zn restack <R-id>` aborts the rebase at the first conflict and leaves the layer's branch unchanged, so the worker must rebase the whole layer by hand outside zn.
- A `./zn restack <R-id>` run after a hand rebase that exists only on the local branch takes the layer's tip from `origin`, finds it not stacked, and `git reset --hard`s the local branch to it, discarding the hand rebase.
- When a restack has stopped on a conflict, `./zn work next` does not name continuing it as the raft's action.

Decided with the user (2026-11-21, who resolves): "zn restack conflict shoudl be handled by the ai skill around it". So a conflict during a restack is not a stop for the person: the engine leaves the rebase in progress and names the conflicted files, and the skill the worker follows (zz-execute, through z-work) tells the worker to resolve the conflicts itself, rerun what the resolved files affect, and continue the restack with the one command. Only a conflict the worker cannot resolve with confidence (two sides that both changed the same behaviour on purpose) goes to the person, as a question that names the files and both intents.

## Non-goals
- zn does not resolve conflicted files itself or pick a side for the worker.
- It does not reuse resolutions through git's rerere or any other store of past resolutions.
- A restack run in which no layer conflicts and no layer's local branch holds commits that `origin`'s branch lacks rebases the same layers onto the same bases as before this ticket; what changes for it is only how it publishes (each layer pushed on its own once its check passes, the owner's ruling of 2026-11-22) and where it may run (never in the main checkout, see Design).
- It does not change when a restack is required or how often main moves during a landing.

## Solution
- When a layer's rebase conflicts, `./zn restack <R-id>` leaves that rebase in progress in the raft's worktree, exits non-zero, and prints the layer, each conflicted file and the exact command that continues.
- After the worker has resolved and staged the conflicted files, one zn command continues the in-progress rebase, runs that layer's `check.sh`, pushes the layer when it passes, and only then restacks the remaining layers, without restarting any layer already rebased in that run.
- Restack takes a layer's tip from the local branch in the raft's worktree whenever that branch holds any commit that `origin`'s branch for the layer lacks, and from `origin` otherwise.
- When the local tip it takes is not based on the current tip of the layer below (for example, a hand rebase onto a main that has since moved, or a layer above one that restack just moved), restack rebases that local tip onto the layer below and never rebases `origin`'s tip for that layer.
- When `origin`'s branch for a layer holds a commit whose change is on neither the local branch nor the layer below, restack exits non-zero, names the layer, and changes no branch for it or any later layer.
- Restack never runs `git reset --hard` on a local branch holding commits that `origin`'s branch lacks.
- Restack skips a layer as "already stacked" only when `origin`'s branch for that layer is itself at the stacked tip.
- When a layer's stacked tip is on the local branch but not on `origin`'s branch, whether from a hand rebase, a rebase restack just made from the local tip, or a continued resolution, restack runs that layer's `check.sh` and pushes the layer when it passes, before it restacks the next layer.
- When that `check.sh` fails, restack exits non-zero, names the layer, pushes nothing for it or any later layer, and leaves the layer on its local branch (a restacked tip stays there unpushed, for the worker to fix and `./zn finish`; a branch that held a tip of its own is not touched).
- After any restack or continue run that exits zero, `origin`'s branch for every layer of the raft is stacked on the layer below, so `./zn done` does not reply "run ./zn restack".
- A conflict resolution counts as kept once it is a commit on the layer's local branch or is staged in the in-progress rebase, and no restack run removes either without the worker's explicit abort command.
- While a raft's worktree has a restack rebase in progress, `./zn work next` names the continue command as that raft's action.

## Design
Risk reason (risky): it rewrites published layer branches and decides which tip a restack trusts; a wrong choice discards or republishes work.

- **Cause of R0138's reset.** `layergit.layerTip` returns `origin/<layer>` before the local branch; `cmd.restack` took it, judged "already stacked" on it, then `checkoutLayer` + `git reset --hard <origin tip>` overwrote the hand-rebased local branch. Now `restackplan.source` takes the local tip whenever it holds a commit origin's lacks; the only reset left is of a branch that holds nothing origin lacks.
- **Modules.** `engine/restackplan.luau` (pure: `source`, `decide`, `trusted`, `emptied`, `movedSince`, `abortRefuses`, `strayed`, `restoreTo`, `published`, `pushReason`, marker text, messages); `engine/restackcmd.luau` (git edge, modes start/continue/abort); `cmd.restack` in `main.luau` is a few lines; `workread.restackStopped` + `work.luau` answer `work next`.
- **Marker** `<worktree git dir>/zn-restack.state`: written when a run starts (raft, back, start commit, per layer `orig` local tip and `judged`, origin's tip after the run's fetch), rewritten as branches move (`left`, also for layers taken as they are, so `--abort` works after a `--continue`; `pushing <layer> <sha>` before each push and `pushed <layer> <sha>` after it, `red <layer> <sha>` at a red check), `conflict <layer> <own commits>` and `file` lines added at a stop, removed at the end. A crash anywhere leaves `--continue` and `--abort` usable.
- **Walk.** Each layer: tip = local if it holds a commit origin lacks, else origin's. Diverged (both have extra commits): local is taken only if origin's tip is `refs/zn/pushed/<layer>`, the tip this clone itself pushed (written by `start`, `finish` and restack after their push succeeded); otherwise (a fresh clone, a layer someone else pushed, a tip merely fetched or reset to) exit 1 naming both shas and what to do (fetch, rebuild on origin's tip, or ask), nothing changed. No reflog, no pre-fetch tip. Stacked + on origin: skip. Stacked, local ahead: check.sh. Not stacked: `rebase --onto` (rerere off); a rebase or resolution that leaves fewer own commits stops with "emptied ... stop and ask". Every layer runs its check.sh; a red check stops the run, pushes that layer and everything above it never, and keeps the restacked tip on the layer's branch (see Red check).
- **Publishing (per layer; the owner's ruling of 2026-11-22 reversed G1).** A layer is pushed on its own as soon as it is restacked (or its local tip is taken) and its `check.sh` passes, before the next layer is restacked: `git push --force-with-lease=refs/heads/<layer>:<lease> origin <layer>`. A refused push stops the run and names the way on: `./zn restack <R-id> --abort` (it keeps the layers already pushed and puts the others back), then `./zn restack <R-id>`. The lease is the tip this run itself pushed for the layer when it did (a layer pushed, then rebased again after main moved while a conflict waited), else the origin tip the run judged after its fetch (empty: the layer must not exist on origin, never a plain `--force`). Both are kept in the marker so `--continue` uses the same value, never the current remote-tracking ref. A refused push prints only git's reason lines, never its words about the remote, which carry the remote's address. Crash windows: the marker gets `pushing <layer> <sha>` before the push; `--continue`, `--abort` and the next plain restack ask origin (`git ls-remote`) whether that sha landed and, when it did, note it (`refs/zn/pushed`, the `pushed` line, the remote-tracking ref), so a run killed after the push is neither treated as unpushed by `--abort` nor refused as foreign later (test seam: `ZN_RESTACK_KILL=before-push|after-push|after-note` exits the run there; nothing else sets it). `refs/zn/pushed/<layer>` and the marker's `pushed <layer> <sha>` line are written only after that push succeeded. A stop (conflict, red check, emptied commit, refused lease) leaves the layers below it, which passed, pushed, and it and the layers above it not pushed. `restacked` is still emitted once, at the end of a run that moved or pushed anything: it means the raft is restacked, so a run that stops emits nothing, and the run that finishes the stack (a `--continue` or a plain restack) emits it.
- **Red check.** The restacked tip stays on the layer's branch, not pushed (the marker's `red <layer> <sha>`); layers below that passed are pushed, it and those above are not. Nothing is reset: a reset would make the next restack rebase the old tip onto the same layer below and hit the same red check, and `./zn finish` refuses a layer not based on the layer below, so the worker could never fix it. The worker fixes the layer on that tip, runs `./zn finish <issue>`, then `./zn restack` (the tip is local-ahead of origin and `refs/zn/pushed` still equals origin's tip, so it is this clone's own work and is trusted). `work next` answers `restack` with a note that names the fix and `finish` (not "Run ./zn restack") while the branch is still at the red tip; once the worker changed the layer it answers as for any unstacked raft.
- **Exit codes.** 0 success; 1 every refusal; 3 a conflict stop; 75 a layer's check that did not start (the machine's gate queue did not let it: nothing is red, nothing is pushed for that layer or above, the marker keeps `left` with no `red` line, and the next plain restack or `--continue` runs the check again).
- **Where it runs.** `./zn restack` in every form (plain, `--continue`, `--abort`) refuses in the main checkout of a repository with an origin, before any fetch or write, naming `cd "$(./zn worktree <R-id>)" && ./zn restack <R-id>[ --continue| --abort]` (`refuseInMainCheckout` in `cmd.restack`; zz-rules, Worktrees). It runs in the raft's worktree.
- **Start.** A plain restack refuses a rebase in progress (a restack's, naming `--continue` and `--abort`; any other, naming `git rebase --continue` and `git rebase --abort`), then a dirty worktree, before it reads any marker. A marker with no rebase behind it belongs to a run that stopped (a red check, a refused lease, an emptied commit, exit 75, a kill), this raft's or another's: a push it left unrecorded is reconciled first. The marker itself stays until the new run writes its own, which replaces it, so a start that fails before that (a failed fetch, a refusal) leaves the stopped run's record whole (code review 001 F7). The new run's record starts from where it finds each branch, as on main: nothing of the stopped run's `orig` or `pushed` lines is carried (code review 001 F1, F2, F5; G10 withdrawn), so `--abort` after a plain restack goes back to where that restack found each branch and keeps any commit the worker made or resolved in between. Which run's start an abort after several stopped runs should go back to is open to the owner (review-001 F2).
- **Conflict.** The rebase stays in progress on that layer; exit 3; message names layer, files, `--continue`, `--abort` and the layers already pushed. A plain restack then refuses and names both commands. `work next` answers `restack` with the resolve-and-continue note.
- **Continue.** First, before it changes anything (design review 001 F5, code review 001 F3, F4): a layer the run moved (its `left` differs from its `orig`) whose branch is back at its `orig` tip, the tip from before the run, is refused, whatever `refs/zn/pushed/<layer>` holds (before a run pushes a layer that ref is the old tip too). Walking on would rebuild that layer from its old tip and replace what the run left. Every other tip (a hand rebase, an amend, a fix on top, a finished layer, a deleted branch) is the worker's change and goes through the walk as on main. The refusal (exit 1) names, for each such layer, the commit the run left and the commit the branch is at (sha, subject, date) and `git log --oneline <left>..<now>`, and two ways on: first `git branch -f <layer> <left>` (for the branch checked out in this worktree, `git switch --detach && git branch -f <layer> <left> && git switch <layer>`) then `./zn restack <R-id> --continue`, which keeps a resolution staged in the rebase (`git branch -f` works while a rebase is in progress, because the layer is not the branch being rebased); second `./zn restack <R-id> --abort` then `./zn restack <R-id>`, which discards a resolution not yet continued. It never names a reset (G12). Then it refuses naming `unmerged: <file>` and `conflict marker: <file>:<line>` (markers looked for only in the recorded conflicted files), then `GIT_EDITOR=true git rebase --continue` (rerere off), then the walk again (the continued layer is local-ahead: checked; the layers above rebased); one more stop repeats, also a second conflict inside the same layer's rebase. With no rebase in progress it refuses a dirty worktree. `--continue` never fetches: every push is leased on what the run judged after its own fetch, so a layer origin moved since the run started is refused at its push (AC13, AC23), and the way on is `--abort` then a plain restack, which fetches and builds on origin's tip; the refusal says so. The cost: a push someone else made during a stop always ends the run, even a fast-forward the run could have built on (whether to fetch at `--continue` is open to the human, design-review-001 F6).
- **Abort.** Refuses (naming them, changing nothing) a branch that is at none of the shas the run could have left it at (`orig`, `left`, and for a pushed layer its pushed tip), and a dirty worktree when no rebase runs; else aborts the rebase, returns to the start branch (or commit), restores the local branches of the layers this run has not pushed to where the run found them (deletes only ones the run created and did not push, and never the branch the worktree ends on). A layer the run pushed is put to the tip it pushed, whichever branch the worktree ends on (a pushed layer that was rebased again and not pushed goes back to its pushed tip; a pushed layer put back to its tip from before the run goes forward to it, G11; a branch the run created and pushed is kept), because `--abort` never force-pushes origin back; the message names those layers, and every branch the abort moved with the tip it was on and the tip it is on now, so a tip it moved off can be found again (code review 001 F2). The half-moved stack is continuable: a later plain `./zn restack` finds the pushed layers local == origin and stacked, skips them, and restacks the rest from the layer below. Origin then holds the pushed layers on the new base while the layers above still rest on the old commits, the same state any amend of a lower layer leaves, which `./zn done` refuses until restacked.
- **Skills.** zz-execute Phase 5 step 2 and z-work step 3 tell the worker what to do (specs by name via `z-nile/affected`, red check after continue, empty resolution, repeat, unattended = questions.md, never skip/drop/force-push).
