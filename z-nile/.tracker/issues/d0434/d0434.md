# d0434: Restack stops on conflict

## Problem
- `./zn restack <R-id>` aborts the rebase at the first conflict and leaves the layer's branch unchanged, so the worker must rebase the whole layer by hand outside zn.
- A `./zn restack <R-id>` run after a hand rebase that exists only on the local branch takes the layer's tip from `origin`, finds it not stacked, and `git reset --hard`s the local branch to it, discarding the hand rebase.
- When a restack has stopped on a conflict, `./zn work next` does not name continuing it as the raft's action.

Decided with the user (2026-11-21, who resolves): "zn restack conflict shoudl be handled by the ai skill around it". So a conflict during a restack is not a stop for the person: the engine leaves the rebase in progress and names the conflicted files, and the skill the worker follows (zz-execute, through z-work) tells the worker to resolve the conflicts itself, rerun what the resolved files affect, and continue the restack with the one command. Only a conflict the worker cannot resolve with confidence (two sides that both changed the same behaviour on purpose) goes to the person, as a question that names the files and both intents.

## Non-goals
- zn does not resolve conflicted files itself or pick a side for the worker.
- It does not reuse resolutions through git's rerere or any other store of past resolutions.
- A restack run in which no layer conflicts and no layer's local branch holds commits that `origin`'s branch lacks leaves the same branches and pushes as today.
- It does not change when a restack is required or how often main moves during a landing.

## Solution
- When a layer's rebase conflicts, `./zn restack <R-id>` leaves that rebase in progress in the raft's worktree, exits non-zero, and prints the layer, each conflicted file and the exact command that continues.
- After the worker has resolved and staged the conflicted files, one zn command continues the in-progress rebase, runs that layer's `check.sh`, pushes the layer when it passes, and only then restacks the remaining layers, without restarting any layer already rebased in that run.
- Restack takes a layer's tip from the local branch in the raft's worktree whenever that branch holds any commit that `origin`'s branch for the layer lacks, and from `origin` otherwise.
- When the local tip it takes is not based on the current tip of the layer below (for example, a hand rebase onto a main that has since moved, or a layer above one that restack just moved), restack rebases that local tip onto the layer below and never rebases `origin`'s tip for that layer.
- When `origin`'s branch for a layer holds a commit whose change is on neither the local branch nor the layer below, restack exits non-zero, names the layer, and changes no branch for it or any later layer.
- Restack never runs `git reset --hard` on a local branch holding commits that `origin`'s branch lacks.
- Restack skips a layer as "already stacked" only when `origin`'s branch for that layer is itself at the stacked tip.
- When a layer's stacked tip is on the local branch but not on `origin`'s branch, whether from a hand rebase, a rebase restack just made from the local tip, or a continued resolution, restack runs that layer's `check.sh` and pushes the layer when it passes, before it restacks the next layer.
- When that `check.sh` fails, restack exits non-zero, names the layer, pushes nothing for it or any later layer, and leaves the local branch as it is.
- After any restack or continue run that exits zero, `origin`'s branch for every layer of the raft is stacked on the layer below, so `./zn done` does not reply "run ./zn restack".
- A conflict resolution counts as kept once it is a commit on the layer's local branch or is staged in the in-progress rebase, and no restack run removes either without the worker's explicit abort command.
- While a raft's worktree has a restack rebase in progress, `./zn work next` names the continue command as that raft's action.

## Design
Risk reason (risky): it rewrites published layer branches and decides which tip a restack trusts; a wrong choice discards or republishes work.

- **Cause of R0138's reset.** `layergit.layerTip` returns `origin/<layer>` before the local branch. `cmd.restack` took that tip, judged "already stacked" on it, then `checkoutLayer` + `git reset --hard <origin tip>` overwrote the hand-rebased local branch. The rule is now `restackplan.source`: the local tip whenever it holds a commit origin's lacks, else origin's. The only reset left is of a branch that holds nothing origin lacks.
- **Modules.** `engine/restackplan.luau` (pure): `source`, `decide` (none, foreign, skip, publish, rebase), the marker text (`renderState`/`parseState`), `markers` (reads `git diff --check`), the messages. `engine/restackcmd.luau` (git edge): `run(raft, mode, deps)` with modes start, continue, abort. `main.luau` keeps a six-line `cmd.restack`; `workread.luau` reads the marker; `work.luau` answers.
- **Walk.** Every run walks the layers from the bottom: facts per layer (local sha, origin sha, local/origin extra commits, foreign, layer below in tip) go to `decide`. skip: stacked and on origin. publish: stacked, local ahead of origin: run the layer's check.sh, push with `--force-with-lease=refs/heads/<l>:<origin sha>` (the lease the code already used; first push `-u`), then the next layer. rebase: `rebase --onto <below> <own-commits upstream> <layer>`; red check resets the layer to its tip from before. foreign (origin's own commit whose subject is on neither local nor below, only when both sides have extra commits): exit 1 naming the layer, nothing changed for it or later.
- **Conflict state.** A conflicting rebase is left in progress in the raft's worktree, on that layer, exit 3 (0 is success, 1 every refusal). The marker is `<worktree git dir>/zn-restack.state` (`raft`, `back`, `orig <layer> <local sha|->` per layer, `conflict <layer>`). Layers already done are not recorded: every run re-reads them from git, so a crash anywhere re-enters the same walk.
- **Continue.** `./zn restack <R> --continue` needs the marker. While the rebase is in progress it refuses, naming `unmerged: <file>` for each path git lists as unmerged and `conflict marker: <file>:<line>` for each leftover marker (`git diff --check HEAD`). Then `git -c core.editor=true rebase --continue` (another conflict in the same layer stops again, same marker), then the walk: the continued layer is local-ahead so it is checked and pushed, the layers above are rebased on it. `restacked` is emitted once, at the end of a walk that moved something; a conflicted stop emits nothing. A marker with no rebase (a crash after the worker's own `git rebase --continue`) also continues; a plain `restack` then deletes the stale marker and walks.
- **Abort.** `--abort` aborts the rebase, switches to `back`, and puts every layer's local branch on its `orig` sha (deleted when it had none), then removes the marker. Nothing is fetched or pushed.
- **While stopped.** A plain `restack` refuses and names both commands. `./zn work next <R>` reads the marker (`workread.restackStopped`) before looking at layers and answers `restack` with `restackplan.workNote`: resolve the files (listed), run their specs, `--continue`; ask only when both sides changed the same behaviour on purpose.
- **Publishing.** The ticket's Solution wins over "push at the end": each layer is pushed when its check.sh passes, before the next layer is restacked, so a conflict in layer N leaves layers below N pushed. `--abort` restores local branches only; layers pushed earlier stay pushed (see guess G1).
- **Skills.** zz-execute Phase 5 step 2 and a pointer in z-work step 3 say what the worker does on a conflict.

### Scalability
One walk is a few git calls per layer, as before.
### Maintainability
Decisions are pure and spec'd without git; main.luau gains no top-level local.
### Usability
The conflict message prints the layer, each file and both commands; `work next` names the action.

## Acceptance criteria

### Checked
- AC1: When a layer's rebase conflicts, `./zn restack <R-id>` leaves it in progress in the raft's worktree on that layer, exits 3, prints the layer, each conflicted file and the continue and abort commands, pushes nothing and emits no `restacked`.
- AC2: A restack run while one is in progress refuses, says so, names `--continue` and `--abort`, and changes nothing.
- AC3: While a restack is stopped on a conflict, `./zn work next <R-id>` answers `restack`, names the conflicted file and the `--continue` command.
- AC4: `--continue` refuses while a path is unmerged, and while a conflict marker is staged, naming each, and leaves the rebase in progress.
- AC5: After the resolution `--continue` finishes the rebase, pushes it, restacks the layers above on it, leaves trees equal to a by-hand rebase, emits `restacked` once, removes the marker and returns to the starting branch; a following restack says already stacked.
- AC6: `--abort` restores every layer's local branch, origin, the worktree and the starting branch exactly as before the run, and a following `--continue` says no restack is in progress.
- AC7: A layer whose local branch was hand rebased onto the layer below and not pushed keeps its tip; restack pushes it and restacks the layer above it.
- AC8: A restack that stopped on a conflict, whose rebase the worker then continued by hand, is finished by a plain restack that keeps that rebase.
- AC9: When origin's branch for a layer holds a commit whose change is on neither the local branch nor the layer below, restack exits 1 naming the layer and changes no branch of it or of a later layer.
- AC10: When a restacked layer's `check.sh` fails, restack exits 1 naming the layer, pushes nothing for it or later layers and leaves the local branch as it was.
- AC11: zz-execute and z-work tell the worker to resolve a restack conflict itself, run the specs by name, continue with one command, ask only when the owner's side is unclear, and never skip, drop or force-push by hand.
