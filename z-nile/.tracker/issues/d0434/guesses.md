- G1 (design, 2026-11-21): OVERRULED by the owner 2026-11-22. The captured Solution says a layer is pushed when its check.sh passes, before the next layer is restacked; the lead had decided otherwise. Asked "during a restack, are layers pushed one at a time as each passes, or all together once the whole stack is done?", the owner answered verbatim: "1 yes push early, you may push before each review and when ready." Chose: (the lead's choice, overruled) push nothing until every layer was restacked and checked, then one `git push --atomic`; the rule now: each layer is pushed on its own when its check.sh passes, with a lease against the origin tip recorded after the run's fetch, before the next layer is restacked; `refs/zn/pushed/<layer>` is written after each push succeeds; `--abort` restores the layers not yet pushed and leaves the pushed ones (it never force-pushes origin back); a later plain restack goes on from them. Why: the owner's answer above.
- G2 (design, 2026-11-21): When the local branch and origin's branch have both moved (a diverged layer), is origin's tip a rewrite of the local branch or someone else's work? Example: layers are one commit with a fixed subject, and a fetch or a `reset --hard` puts someone else's tip into this clone's remote-tracking ref and even into the local reflog, so neither a subject, a pre-fetch tip nor a reflog says who wrote it. Chose: trust only what this clone pushed itself: zn writes `refs/zn/pushed/<layer>` (the tip it pushed) after every push of a layer it makes (`start`, `finish`, restack's push of each layer, only once the push succeeded), and a diverged origin tip is trusted only when it equals that ref. With no ref (a fresh clone, a layer someone else pushed) the restack stops naming both tips and says to fetch and rebuild on origin's tip, or ask. Why: it is the one record that only this clone's own push can write. Cost: a clone that never pushed the layer must rebuild by hand once (review 001 F1 shows a wider cost, open to the owner). This adds one ref name to what zn writes in a repository (zz-rules, One layer per ticket).
- G3 (design, 2026-11-21): Which exit code does a conflict stop use? Chose: 3. Why: 1 is every refusal and 2 is used by other commands for usage.
- G4 (design, 2026-11-21): Does `--continue` stage a resolved file for the worker? Chose: no; a resolved file left unstaged still counts as unmerged and is refused, naming it. Why: the ticket says "after the worker has resolved and staged".
- G5 (design, 2026-11-24): What does a push of `--continue` lease on, when origin may have moved during the stop (recorded for review 001 F10)? Chose: the origin tip the run judged after its own fetch at the start (or the run's own push, for a layer it already pushed), with no fetch at `--continue`. Why: a lease on a remote-tracking ref that a fetch has just moved protects nothing (lesson zz-arch/fresh-fetch-defeats-force-with-lease). Cost: a push someone else made during a stop always ends the run, even a fast-forward the run could have built on; the way on is `--abort`, then a plain restack (open to the owner as review 001 F6).
- G6 (design, 2026-11-24): When main moves while a conflict waits, does `--continue` rebase again and push again the layers the run already pushed (recorded for review 001 F10)? Chose: yes, so the stack ends on the current main, each push leased on the run's own previous push. Why: freezing the base the run started with ends on a base `./zn done` refuses and costs a second restack. Cost: a pushed layer can be pushed twice in one run.
- G7 (design, 2026-11-24): What happens to a layer whose check.sh is red after the restack moved it (recorded for review 001 F10)? Chose: the restacked tip stays on the local branch, unpushed; the worker fixes it there, runs `./zn finish <issue>`, then a plain restack. Why: a reset would bring back the same red check on the next restack, and `finish` refuses a layer not based on the layer below. Cost: `finish` pushes over whatever origin's layer holds (open to the owner as review 001 F2 and F3).
- G8 (design, 2026-11-24): What does a restack do when a layer's check did not start, because the machine's gate queue did not let it (recorded for review 001 F10)? Chose: exit 75 with nothing red and nothing pushed for that layer or above, a marker kept with no `red` line, and the next plain restack or `--continue` runs the check again (AC30). Why: a check that never ran is neither a pass nor a failure (d0426).
- G9 (design, 2026-11-24): Which pushes write `refs/zn/pushed/<layer>` (recorded for review 001 F10)? Chose: `start`, `finish` and restack's own push of each layer, after the push succeeded; `./zn commit` and `./zn approve` push a layer without writing it. Why: those were the pushes this ticket touched. Cost: a layer whose last push was a `./zn commit` or `./zn approve` is refused as someone else's work after a conflict and `--continue` (open to the owner as review 001 F1).
- G10 (design, 2026-11-24): A plain restack over a stopped run's marker: keep that run's record or refuse (review 001 F6)? Chose: keep it: the stopped run's `orig` for each branch still where it left it, and its `pushed` line for each layer origin still holds at that push. Why: refusing would break the plain restack that AC8, AC26, AC28 and AC30 go on with; keeping is a few lines and makes `--abort` after it true to the first run.
