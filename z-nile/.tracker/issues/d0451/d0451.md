# d0451: Board approval count wrong

## Problem
- This is a defect of f0422 (Tributaries and banded board), which built the board's Flow view and its tributary counts. f0422's captured outcome says the board shows four counts for each tributary, and one of them is "waiting for the owner's approval" (`z-nile/.tracker/issues/f0422/f0422.md` line 39).
- The board's third tributary count holds only open units where the unit or one of its members has a `questions.md`. The board asks the shared rule with `approval = false` (`z-nile/engine/board.luau` lines 1330-1344), so no unit is ever counted as waiting for approval. A live-held unit with no `questions.md` is counted as in flight (`z-nile/engine/tributaries.luau` lines 155-174). Evidence: the read-only audit `z-nile/.tracker/issues/f0450/evidence/audit-B.md` (untracked in f0450's folder on this checkout; an audit of origin/main 3e7b197e3, made 2026-11-24), line 31.
- The chip's tooltip says "waiting for approval" (`z-nile/engine/board.html` line 333), and zz-rules' board row says "waiting for the owner's approval" (`z-nile/skills/zz-rules/SKILL.md` line 90). So the page and the skill promise a count the board does not compute (audit-B.md line 31).
- The real approval count exists only in the app's Themes view (f0437 step 5, `z-nile/engine/themefacts.luau` counts). It comes from the approval facts that the last `./zn approve --queue` wrote, which carry their own time and scope (`z-nile/engine/themewrite.luau` lines 34-47). The app shows "not known yet" when no queue has been read, and warns when the queue was scoped (`z-nile/app/live.js` lines 746-773). So the board and the app show different numbers for the same tributary.
- `./zn approve --queue` writes the approval facts and then remakes only the themes facts, and only in the main checkout (`z-nile/engine/approvewalk.luau` lines 667-708; `refreshThemes` in `z-nile/engine/main.luau` lines 6217-6227). It never rebuilds `.cache/board.html`. Only two commands write that page: `./zn board`, which writes it itself (`z-nile/engine/main.luau` lines 8751-8757), and `./zn sync` in the main checkout, which calls `buildBoard` (lines 652-680), whose one caller is `cmd.sync` (line 2649). A publish does not rebuild the board (the comment at lines 679-680), `cmd.land` (lines 2826-3001) does not either, and zz-rules line 90 says the same. So after a queue run the app has the new approval facts, and the board keeps the page that the last `./zn board` or `./zn sync` built.

## Non-goals
- This idea does not decide whether units waiting on the owner's answer get a count of their own beside the approval count (as the app's `owner` count does), or are shown in one "waiting for you" count that also says how many of its units wait for approval. The owner decides that. Either way, the approval count stays its own number.
- It does not build the approval band at the top of the Flow view that f0422's capture also describes (f0422.md line 40; audit-B.md line 32). That band is an unbuilt outcome of f0422 itself, not part of this defect.
- It does not change where `./zn approve --queue` remakes the themes facts. A queue run outside the main checkout rebuilds neither the themes facts nor the board, as today.
- It does not make a publish or `./zn land` rebuild the board. `./zn board` and `./zn sync` in the main checkout stay the other commands that write it.

## Solution
- For each tributary, the board shows an approval count of its own: the number of its units that the shared rule (`tributaries.classify`) places as waiting for approval. The rule is given each unit's real approval fact, read from the same approval facts file the app's Themes view reads.
- Every time `./zn approve --queue` remakes the themes facts (in the main checkout), it also rebuilds `.cache/board.html` from the same tree and the new approval facts. So reloading the board right after a queue run shows the new approval counts with no other command.
- When the board and the app's Themes view are made from the same tree and the same approval facts file, the board's approval count for every tributary equals the app's `approval` count for it. That still holds right after every `./zn approve --queue` run in the main checkout.
- The board shows the time its approval facts were written, taken from the facts file, as the app does.
- When no approval queue has been read, the board shows each tributary's approval count as not known (never as 0) and names `./zn approve --queue` as the way to get it, as the app does.
- When the last approval queue was scoped, the board states that its approval counts cover only that scope, as the app does.
- No unit where the unit or a member holds a `questions.md` is in the approval count. Each such unit is counted exactly once, as waiting on the owner's answer.
- The board's chip, its tooltip and zz-rules' board row use the same wording for each count, and each wording says what that count counts.
