# d0454: Every layer push records the tip this clone pushed

## Problem
- `./zn commit` (the shared `push()` in `z-nile/engine/main.luau`) and `./zn approve`'s layer push both push a layer without writing `refs/zn/pushed/<layer>`, so that ref falls behind origin's tip.
- When that ref is stale, restack refuses a layer that is rebased or rewritten and not yet pushed, calling it "someone else's work", even though this worktree made and pushed the commit (R0070 layer 2, review-003, 2026-11-25).
- Any of these routes leaves a layer in that state and leads to the refusal: a conflict and then `--continue`, a red check and then a plain restack, a check that did not start (exit 75) and then the rerun, a run killed after its rebase and before its push, and a hand amend or rebase after the push.
- A restack that runs straight through after such a push, with nothing done to the layer by hand since, does not refuse today, because when the check at `z-nile/engine/restackcmd.luau:262` runs, origin's layer holds no commit the local layer lacks.

## Non-goals
- `restackplan.decide`, `restackplan.source` and `restackplan.trusted` keep their current rules.
- Restack does not start trusting a tip because of a fetch, a reset, a reflog entry, a stopped run's `judged` line or the person's word.
- A refusal this change does not prevent is not addressed here: a layer last pushed with plain `git push`, a clone that never pushed the layer, and a worktree refused before this lands. No restack option is added for them, and the refusal message's wording stays as it is.
- The question in d0434 for the owner, about inferring who pushed from other evidence, stays open and is not answered here.

## Solution
- Every zn command that pushes a layer branch (start, finish, restack, `./zn commit` and `./zn approve`) writes `refs/zn/pushed/<layer>` to the pushed sha only after the push exits 0, and leaves the ref alone when the push fails.
- After a `./zn commit` or `./zn approve` push on a layer, restack does not refuse that layer as "someone else's work" on any route in Problem sentence 3; a conflict still needs its hand resolution before `--continue`, and a red check still stops the restack until the layer is fixed.
- Restack's "someone else's work" refusal (`restackcmd.luau:269`) fires only when all three of these hold: the local layer holds a commit origin's lacks, origin's holds a commit the local layer lacks, and origin's tip is not this clone's `refs/zn/pushed/<layer>`; its other refusals (an emptied commit, a strayed layer on `--continue`, a refused push) stay as they are.
- When the local layer holds no commit of its own, restack keeps taking origin's tip whoever pushed it (`restackplan.source`, unchanged).
