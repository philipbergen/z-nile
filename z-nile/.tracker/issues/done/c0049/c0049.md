# c0049: Parallel gate stages

## Problem
`scripts/check.sh` runs every stage serially (stylua, selene, luau-lsp on `src`, luau-lsp on tests and scripts, rojo build, then specs), and `tests/run.luau` runs specs one at a time. CI (`.github/workflows/check.yml`) is a single serial `gate` job. Developers and agents wait for the sum of all stages on every gate run. The first four stages are independent of each other, so they could run concurrently; specs might too. Stage timings haven't been measured yet, so the first step is to find out where the time goes.

Tests and checks run very often, so they must execute as concurrently and as swiftly as possible. That is a standing requirement, not a one-off fix: gate speed has to be monitored continuously and optimised whenever it regresses or a stage becomes a bottleneck.

## Non-goals
- Changing which specs the `--affected` selector picks.
- Splitting CI into multiple jobs (could follow, if local parallelism proves worthwhile).
- Changing what any stage checks.

## Solution
- Time each gate stage first and record the numbers; only parallelise what is worth it.
- Run the independent static stages (format, lint, both type-check passes) concurrently, with per-stage output buffered so logs stay readable, and keep the current fail-the-gate semantics and exit code.
- Evaluate running specs in parallel in `tests/run.luau` (needs spec isolation, e.g. the lifecycle spec's repo clone: see c0006).
- Make this a standing rule in the skills: `.claude/skills/testing/SKILL.md` (and `execute-raft`, where the gate is run) state that tests and checks must run concurrently and swiftly, that gate and stage timings are monitored continuously, and that slow or serial stages are optimised, or filed as a chore, when noticed. Consider having `check.sh` print per-stage timings so the monitoring is cheap.
- The rojo sourcemap must still be generated before the `src` type-check.

## Design

### Measurements (prep, 8-core macOS host)
| stage | time |
|---|---|
| stylua, selene, luau-lsp src, luau-lsp tests+scripts, rojo build (serial) | 0.52 + 0.08 + 1.08 + 0.08 + 0.02 = about 1.8 s |
| the same five, concurrently | 1.3 s |
| `lune run tests/run` (73 spec files, 454 cases) | **27 s** |
| the same files, one `lune run tests/run -- <file>` per file, `xargs -P4` / `-P8` | 10 s / 11-12 s; four repeats at `-P8` all green |

Seven shell-heavy specs (each builds a git fixture under its own `.cache/<name>` and runs `tracker.sh`) take about 27 s of the 31 s per-file sum; the median spec takes 0.02 s. The longest single spec is `tests/acceptance/c0005/worktree.spec.luau` at 9.3 s, so about 10 s is the floor until that spec is split. **The specs are the bottleneck; the static stages are not** (they save about 0.5 s concurrently). Both are done, because the user wants everything concurrent and fast, but the spec runner is the real win.

### Spec runner (`tests/run.luau`)
Flags: `--jobs N` (integer >= 1). Environment: `PICKMAN_JOBS=N`. `--jobs` wins over the environment. Default `min(max(cpus, 2), 8)`, where `cpus` is `sysctl -n hw.ncpu` on Darwin and `nproc` elsewhere (`@lune/system` is not usable here), falling back to 4. An **empty** `PICKMAN_JOBS` means unset. A bad value (`0`, `many`, a missing number after `--jobs`, or a non-integer or `< 1` `PICKMAN_JOBS`) prints `usage: lune run tests/run [--jobs N] [spec files]` plus the offending name (`--jobs` or `PICKMAN_JOBS`) to stderr and exits 2. `--jobs` may appear anywhere among the arguments and combines with no file arguments (every spec) or with a list.

- **In-process path** (unchanged): `jobs == 1` or fewer than 2 files. The existing loop, byte-identical output. This is also what a worker runs.
- **Coordinator path**: `jobs` lanes (`task.spawn` from `@lune/task`) pull the next file from a shared index. Each file is run as `process.exec("lune", { "run", "tests/run", "--", "--jobs", "1", file })` in the same cwd (workers never recurse, and ignore `PICKMAN_JOBS`). A lane records stdout, stderr, exit code and elapsed seconds (`os.clock` is wall time here).
- **Merge**, in sorted file order, never in finish order: parse the worker's last stdout line `^(%d+) passed, (%d+) failed, 1 spec files$` and add its counts; print the rest of its stdout (the `FAIL ...` lines) and its stderr. A worker with no such line is **one failure**, printed as `FAIL <file>: worker exited with code <n>` followed by the last 25 lines of its output. A worker that reported `0 failed` but exited non-zero is also one failure (same message).
- **Output**: a worker's stderr is printed to the coordinator's stderr after that file's stdout. The merged `FAIL` lines, then (**coordinator path only**, so never for `--jobs 1` or a single file) `slowest: <file> <s>s, <file> <s>s, <file> <s>s` (up to 3, slowest first, one decimal), then the unchanged final line `<P> passed, <F> failed, <K> spec files`. Exit 0 iff no failure. Other tooling (`check.sh` files such as c0046's) greps that last line, so its text and position are fixed.

```lua
type Outcome = { file: string, passed: number, failed: number, seconds: number, output: string }
local function jobCount(argv: { string }, env: (string) -> string?): number  -- raises the usage error
local function runWorker(file: string): Outcome
local function merge(outcomes: { Outcome }): (passed: number, failed: number)  -- prints in order
```
(Signatures guide; the spec pins only behaviour.)

### Gate stages (`scripts/lib/par.sh`, `scripts/check.sh`)
`scripts/lib/par.sh` is sourced by `check.sh` and must run under bash 3.2 (macOS `/bin/bash`): indexed arrays, `wait <pid>`, no `wait -n`, no associative arrays, no `$EPOCHREALTIME`.

```
par_start <label> <command> [args...]   # starts the stage in the background now; stdout+stderr go to a temp file
par_wait                                # waits for every started stage; prints each, in start order, as
                                        #   == <label> (<s.s>s)            or   == <label> (<s.s>s, FAILED)
                                        # followed by its output; returns 1 if any stage failed, else 0; resets the batch
```
Each batch keeps its buffers in a fresh `mktemp -d` directory (gates run at once across worktrees and hooks), removed by `par_wait`. Each stage's elapsed time is measured **inside its own background subshell, from just before the command to just after it ends** (never when `par_wait` collects it), using `perl -MTime::HiRes` and falls back to whole seconds from `date +%s` (printed `N.0`) when perl or the module is missing.

`check.sh` flow: the prerequisites that other stages read stay serial and are fast (definitions download, `rojo sourcemap`, Lune typedefs setup). Then `par_start` for the five stages with their **existing labels**:

1. `format (stylua --check)`
2. `lint (selene)`
3. `types (luau-lsp analyze, src with Roblox definitions)`
4. `types (luau-lsp analyze, tests + scripts with Lune definitions)`
5. `build (rojo)`

`par_wait || exit 1`: every static stage has been printed, `GATE PASSED` is not, and the tests never start. Then the unchanged `== tests (<mode>)` stage (the runner now prints `slowest:`), then `gate wall time: <s.s>s` (measured with the same clock from the start of `check.sh` to just before this line), then `GATE PASSED (<mode>)` as the last line. The old `echo ok` after the build is dropped (the stage header carries the time).

**Decision**: the tests do not overlap the static stages. Static stages cost about 1.3 s; overlapping would save at most that, and would run tests on code that fails the static checks and interleave their output. If monitoring ever shows the static block dominating `--affected`, revisit.

### Speed rule in the skills
`.claude/skills/testing/SKILL.md` gets a `## Speed` section (a standing rule, not a one-off):
- tests and checks run very often, so they must run **concurrently** and as swiftly as possible;
- what exists: `par.sh` for stages, `--jobs` and `PICKMAN_JOBS` for specs;
- **monitor continuously**: every gate run prints per-stage times, `slowest:` and the wall time, and the person or agent running it looks at them; a stage or spec that dominates, or a time that creeps up between runs, is a gate defect: **optimise** it now if it is in your Touched modules, otherwise file a chore (`tracker.sh new issue c gate-slow-<what>`), and never add a serial dependency between stages without a reason;
- writing specs for speed: no wall-clock assertions and no fixed sleeps to let something finish (a bounded poll or rendezvous with a timeout is fine), shell-heavy fixtures own a unique `.cache/<name>` (guarded by the isolation spec: a literal `.cache/<dir>` in two spec files under `tests/` fails the gate, a mere mention counts, and `sim` is exempt), no shared mutable state across spec files, prefer in-process Logic specs, and split or stub a spec that takes more than about a second;
- the table of commands gets `--jobs N` / `PICKMAN_JOBS`.

`.claude/skills/execute-raft/SKILL.md`: the final-verification phase tells the executor to record the **gate wall time** and the slowest specs in the Verification log, and to act on a regression (fix or file the chore) per the testing skill.

### Scalability
Lanes are capped at 8 so a big machine does not fork hundreds of Lune processes; each spec file costs one process start (about 20 ms), so 500 spec files add about 10 s of CPU spread over the lanes. New specs add work to the queue, not to a critical path, until one spec is itself the longest (then the `slowest:` line shows it). `.cache` fixture directories are per spec file, so adding specs adds no contention; the isolation guard keeps that true.

### Maintainability
One 40-line bash library and one runner change (about +70 lines), with the in-process path untouched. No per-spec scheduling hints or timing cache (not needed at 10 s versus a 9.3 s floor). The summary line, the stage labels and `GATE PASSED` as the last line are an interface other checks rely on, and the acceptance specs pin them.

### Usability
Same output as before plus `== ... (1.2s)` stage times, a `slowest:` line and a wall-time line. `PICKMAN_JOBS=1` restores the old serial behaviour (for debugging a suspected ordering bug); a failing spec prints exactly the `FAIL` lines it printed before, in sorted order.

## Unknowns & experiments
Run in prep (macOS, Lune 0.10.5, 8 cores):
- **E1** Can every spec run as its own `lune run tests/run -- <file>` process, concurrently, with no shared-state failures? **Pass**: `xargs -P4`/`-P8`, five runs, all 73 files green, 27 s down to 10-12 s.
- **E2** Does `task.spawn` around `process.exec` run children concurrently in Lune? **Pass**: four `sleep 1` children finish in 1 s wall (`require("@lune/task")`; `task` is not a global).
- **E3** Is `@lune/system` usable for the CPU count? **Fail** (`could not jump to alias` in this repo's typedef setup). **Fallback (in Design)**: `sysctl -n hw.ncpu` (verified: 8) or `nproc` (Linux: not run on this host, CI proves it), default 4 on failure.
- **E4** Does the runner accept a fixture spec under `.cache` (a dot directory)? **Pass**.
- **E5** Is `os.clock` wall time in Lune (so a lane can time a child)? **Pass**: 1.0076 s across a 1 s child.
- **E6** Do the five static stages give the same results run concurrently? **Pass**: three repeated concurrent runs, all five exit 0.
- **E7** `perl -MTime::HiRes` exists on the CI image? **Not run** (macOS only). Fallback to whole seconds is in the Design; AC4 accepts `N.0`.
- **E8** `rsync` exists on the CI image (AC5 uses it)? **Not run**; ubuntu-latest ships it. If not, the executor switches AC5's copy to `git ls-files | cpio -pdm`, which is a check.sh edit and so an escalation: say so in the final report.

Mutation check: the rows below are `reasoned`, not `run`. A prototype of the runner and `par.sh` is the implementation itself, so prep did not build one. The acceptance specs were instead run against today's code: 1 of 12 `parallel-runner` cases passes today (the single-spec regression guard), 0 of 8 `par-stages` cases pass, and every `check.sh` criterion except AC3 fails, each on an assertion or a missing file, not a bash error. AC3 (`spec-isolation`) passes today by design: it is a guard on existing behaviour, and its scanner cases kill the two scanner mutants.

**Spec cost** (the new specs must obey the Speed rule too): the rendezvous and sleep cases need bounded waits by nature, so they use 1 s timeouts and 0.6 s sleeps; `parallel-runner` takes about 5 s and the three acceptance specs run as concurrent workers, so they stay under the 9.3 s `c0005` floor and add nothing to the critical path.

**Not checked** (stated, not hidden): the CPU-count default is only checked to give at least 2 lanes; its `sysctl`/`nproc` branches and the cap of 8 are judged by reading and by CI (Linux `nproc`). `PICKMAN_JOBS` leaking in from the caller is neutralised in the specs (`PICKMAN_JOBS=` is set empty for every child run), so the documented rollback `PICKMAN_JOBS=1 scripts/check.sh --full` does not break the promoted specs.

## Regression guard
- The runner's summary line and exit code (c0046's `launch.spec.luau` check and similar `check.sh` greps; `tracker.sh done` and `promote-check` run the runner with explicit file lists, now concurrently).
- Spec failures print `FAIL <file> :: <case>` exactly as before (`parallel-runner :: a failing case ...`).
- A single-spec run is byte-identical (`parallel-runner :: a single spec runs in-process ...`).
- Every existing spec still passes concurrently (AC6, twice, 8 jobs): the shell-heavy ones already own distinct `.cache/<name>` directories, and `spec-isolation` enforces it. `tests/lib/place.luau` already names its build per process, so concurrent place specs do not collide.
- `scripts/hooks/stop.sh` and `post-edit.sh` call `check.sh --affected` and keep working (same exit codes).

## Acceptance criteria

### Checked
- AC1: `tests/run` runs spec files concurrently (up to `--jobs N`, `PICKMAN_JOBS`, default `min(max(cpus,2),8)`), prints failures in sorted order, sums counts across workers, counts a load error or a dead worker as one failure, prints `slowest:` (more than one file only), keeps its final summary line and exit code, and runs a single file in-process.
- AC2: `scripts/lib/par.sh` starts stages immediately and concurrently, prints each stage's output grouped, in start order, under `== <label> (<s.s>s)` (`, FAILED` on failure), returns non-zero if any stage failed after printing all, resets between batches, and runs under bash 3.2.
- AC3: no two spec files share a `.cache/<dir>` fixture directory (`sim` excepted).
- AC4a: `scripts/check.sh` has five `par_start` lines, all before its single `par_wait`.
- AC4: `scripts/check.sh --affected` passes and prints the five static stage headers, each timed, in order, then the tests stage, `gate wall time: <s.s>s`, and `GATE PASSED (affected)` as the last line.
- AC5: with an unformatted file in a copy of the repo, `scripts/check.sh --full` exits non-zero, shows `format ... FAILED` and all the other static stages, and neither runs the tests nor prints `GATE PASSED`.
- AC6: `lune run tests/run -- --jobs 8` passes twice in a row.
- AC7: the testing skill has a `## Speed` section (concurrently, monitor, optimise, `slowest`, file a chore, `par.sh`, `PICKMAN_JOBS`) and the execute-raft skill tells the executor to record the gate wall time.
