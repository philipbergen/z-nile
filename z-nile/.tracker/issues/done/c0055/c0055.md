# c0055: Run setup.sh whole against stub tools

## Problem
`scripts/setup.sh` ends in the only step that runs the full gate in `check.yml` (`scripts/check.sh --full`), and the tools-only mode (`--tools`) skips it. The specs that guard that path read text (`tests/acceptance/c0015/tools.spec.luau`) or run only a slice of the script: R0016's `setup-tools.spec.luau` cuts out the argument check and the lines from the `--tools` test to the gate call and runs them against a stub gate. Code review 003 of R0016 found what a slice cannot see, with mutants that still pass both specs: wrapping the whole stage in `if [[ -z ${CI:-} ]]; then … fi`; `[[ -n ${CI:-} ]] && exec true` before the stage; `exit 256` (the spec's exit allow-list matches the text `exit 2`, but the shell returns 0); deleting `set -euo pipefail` (the spec supplies that line itself, so a red gate would still end with `SETUP OK` and exit 0); an indented `set +e`. Also, the spec leaves 10 temp directories behind per run (no `rm`, no `trap`), a correct `setup.sh` fails the spec if a comment or message contains the word "exit", and the line numbers in its error messages are about doubled. A change that bypasses the gate in CI would go green without running a single spec.

## Non-goals
- Changing `setup.sh`'s behaviour or the `--tools` interface.
- Replacing main's `c0015/tools.spec.luau` (it can stay as the text-level check).

## Solution
A new acceptance spec, `setup-run.spec.luau`, runs the **whole** of `scripts/setup.sh` for real in a sandbox, so a bypass anywhere in the script is caught by what it does, not by its text. `setup.sh` itself does not change: everything it calls can be stubbed from outside (no seam needed, E1). The slice-based `tests/acceptance/c0048/setup-tools.spec.luau` is superseded and removed, which also removes its leaks (temp directories left behind, a false failure on the word "exit" in a comment, doubled line numbers).

## Design
**`tracker/issues/c0055/acceptance/setup-run.spec.luau`** (written in prep; promoted to `tests/acceptance/c0055/` by `done`; 8 cases, about 1.4-3.3 s on macOS):
- **Sandbox** under `.cache/c0055-setup`, built once per spec run: `repo/scripts/setup.sh` is a byte copy of the real `scripts/setup.sh` (it `cd`s to `repo/`, so its `scripts/check.sh` is the stub gate); `bin/` holds the tool names `uname`, `xcode-select`, `git`, `gh`, `curl`, `unzip`, `rojo`, `selene`, `stylua`, `luau-lsp`, `lune` (and `rokit`, per case), every one a symlink to **one** multi-call stub script; `sys/` holds symlinks to the real `bash`, `cat`, `chmod`, `cp`, `dirname`, `env`, `head`, `ln`, `mkdir`, `mktemp`, `rm`; `home/` is an empty `HOME`, recreated per run.
- **One stub, many names**: it logs `<name> <args>` to `calls.log` and acts just enough: `uname` answers from `STUB_OS`/`STUB_ARCH`; `gh release download … -D <dir>` leaves a zip; `unzip … -d <dir>` drops a `rokit` link there; `rokit self-install` links itself into `$HOME/.rokit/bin`; `check.sh` exits with `STUB_GATE_EXIT`; the version-print loop gets `<name> 1.0.0`. One file instead of a dozen because on macOS the first run of newly written executable content is slow (E2).
- **Run**: `<real bash> <repo>/scripts/setup.sh <args>` with `PATH=<bin>:<sys>`, `HOME=<home>`, the `STUB_*` variables, the case's own variables, and **every other controlled variable unset** (the spec launches through the real `env` with `-u NAME` for each one the case doesn't set, as on a runner that doesn't set it; design review 003 F2): all of `CI_ENV`'s keys, `GITHUB_PATH`, `GITHUB_TOKEN`, `PICKMAN_SKIP_GATE`, `SKIP_GATE`, and `BASH_ENV`, `ENV`, `CDPATH`, `GLOBIGNORE` So the spec decides everything `setup.sh` could plausibly key on, wherever the gate runs (CI included), while the rest of the spec's environment, including R0021's fence variables and R0022's browser guard, is inherited. There is no `env -i`: R0021 bans it in specs because it strips those guards (design review 002 F3). No real tool can run: `PATH` has only the stubs and the basics, `HOME` is the sandbox's, and a real `GH_TOKEN` is unset or replaced by `ghs_fake`, so it can't reach the call log.
- **Cases** (each on both `Darwin-arm64` and `Linux-x86_64` where the platform matters):
  1. no argument: exit 0, the log has `check.sh --full` exactly once and as the last call, after `rokit install` and `lune setup`, and stdout has `SETUP OK`;
  2. `--tools`: exit 0, no `check.sh` call, `tools only: gate skipped`, no `SETUP OK`;
  3. on CI (`CI_ENV`: every variable GitHub's variables reference documents as always set (read 2026-10-01, cited in the spec), including `GITHUB_REPOSITORY_ID`, `GITHUB_REPOSITORY_OWNER_ID`, `GITHUB_WORKFLOW_SHA`, `GITHUB_REF_PROTECTED`, `CI`, `GITHUB_ACTIONS`, `RUNNER_OS`, `GITHUB_RUN_ID`, `ImageOS` and the rest, the per-step file variables `GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `GITHUB_STATE`, `GITHUB_EVENT_PATH` pointing into the sandbox, `RUNNER_WORKSPACE`, with `GH_TOKEN=ghs_fake` and `GITHUB_PATH=<file>`), no argument: the gate runs once with `--full`, `SETUP OK`, and the CI branches really ran (`gh api rate_limit` and not `gh auth status`; `rokit authenticate github --token ghs_fake`; `$HOME/.rokit/bin` written to `GITHUB_PATH`);
  4. no variable skips the gate: `CI=1`, `CI=true`, `GITHUB_ACTIONS=true`, `PICKMAN_SKIP_GATE=1`, `SKIP_GATE=1`, and a CI mix with a skip variable, each run the gate once;
  5. a red gate (exit 3) fails setup with exit code 3 and no `SETUP OK`, locally and on CI, on both platforms;
  6. an unknown argument (`--bogus`, `-t`, `tools`, `--full`) exits 2 with `unknown argument` on stderr and an empty log: nothing ran;
  7. a host without rokit downloads `rokit-1.2.0-macos-aarch64.zip` from `rojo-rbx/rokit` v1.2.0, self-installs it into `$HOME/.rokit/bin`, then runs the gate;
  8. the sandbox is removed at the end.
- No text scan of `setup.sh` at all, so comments and messages can say anything.

**`tests/acceptance/c0048/setup-tools.spec.luau`**: deleted by the executor (named on `Overrides:`). Every bypass that a sandboxed run can express is pinned by `setup-run.spec.luau` from the outside, including the five its slice could not see (E3). **Accepted gap** (design review 001 F2): a bypass that probes the host itself rather than the environment (a path such as `/home/runner`, the user id, the date) can't be seen by any sandbox run; the old spec's text rules (`exit` only in known places) caught some of those by text, at the price of its false positives. Decided in prep: no text check is kept; the risk is recorded in R0023's Risks. **Accepted risk** (design review 002 F2, the user's decision 2026-10-01): a `setup.sh` that skips the gate on a CI-only variable outside the snapshot would skip this spec on CI too (it runs inside that gate), and developer machines lack the variable; the snapshot covers GitHub's documented defaults, and such a skip would show in the `setup.sh` diff at code review. No workflow change. **`tracker/issues/done/c0048/check.sh`**: this prep commit already drops it from AC3, which keeps running `tests/acceptance/c0015/tools.spec.luau` (the sequestration check forbids editing any `check.sh` during execution; the spec itself stays in the gate until the raft deletes it, so coverage never lapses). `tests/acceptance/c0015/tools.spec.luau` stays as the cheap text check (non-goal).

No change to `scripts/setup.sh`, `SETUP.md`, the workflows or any skill. No `tracker/architecture.md` change.

### Scalability
21 runs of `setup.sh` per spec run, 1.4-3.3 s in total on macOS (the first run of the freshly written stub is the slow part, E2). Adding a platform or a case adds about 0.05 s per run. The sandbox is one directory, rebuilt per spec run, removed at the end.

### Maintainability
A change to `setup.sh` that calls a new external tool makes the spec fail with "command not found" until the stub learns the name: one line in the stub's `case` and one in `TOOLS`. That is deliberate: the spec must know every tool `setup.sh` runs, or a real one could run. The spec reads `scripts/setup.sh` at run time, so it always tests the current script.

### Usability
Developer-facing: a failure names the case and platform and shows `setup.sh`'s stderr; the call log order is asserted, so "the gate ran before the tools" reads directly from the failing expectation.

## Unknowns & experiments
- **E1 (run in prep, pass)**: can the whole of `setup.sh` run against stubs without editing it? Yes: with the sandbox above, all 8 cases pass against today's `scripts/setup.sh` on macOS (Darwin and Linux branches, both via the `uname` stub). No seam (environment variable for the tools directory) is needed.
- **E2 (run in prep)**: why was a first version, with one stub file per tool written fresh per case, 26 s? Measured: one `setup.sh` run against freshly copied stubs took 2.2 s, then 1.3 s with another fresh copy, then 0.07 s rerun on the same files; the same run outside the sandbox code took 0.08 s. So on macOS the first execution of newly written executable files is what costs (the cause, likely a security scan, and whether it is keyed on file or content, is not established: the design review measured 3.3 s then 1.9 s for two runs of the one-stub spec, whose stub is rewritten each run). One stub script per spec run, symlinked per name, brings the spec to 1.4-3.3 s; on Linux there is no such cost.
- **E3 (mutation check, run)**: 30 mutants of `scripts/setup.sh` (table), each applied to the real script in the prep worktree and restored, each killed by an assertion. They include the five that survived the old slice spec (R0016 code review 003): the stage wrapped in `if [[ -z ${CI:-} ]]`, `[[ -n ${CI:-} ]] && exec true`, `exit 256`, deleting `set -euo pipefail`, an indented `set +e`; the four runner-variable skips from design review 001 (`RUNNER_OS` before the gate and before `lune setup`, `GITHUB_RUN_ID … exec true`, `ImageOS`) the three per-step-file skips from design review 002 (`GITHUB_ENV`, `GITHUB_OUTPUT`, `GITHUB_EVENT_PATH`), and from design review 003 skips on `GITHUB_WORKFLOW_SHA`, `GITHUB_REPOSITORY_ID` and on CI with `GITHUB_TOKEN` unset (`${GITHUB_TOKEN+x}`). The run with `CI=true RUNNER_OS=Linux GH_TOKEN=realtoken` set in the spec's own environment also passes 8/8 (the local cases unset them).
- **E4 (executor's Phase 1)**: does the spec run on Linux (CI)? By reading, yes: every basic it links exists on ubuntu runners, the stubs are `#!/bin/sh`, `env -u` behaves the same in coreutils, and the controlled variables are unset or set by each case, so the runner's own values never decide a case. Not run here. **The executor runs `scripts/ci-verify.sh` right after `start`**: `check.yml`'s dispatch step runs the active raft's sequestered acceptance specs on ubuntu. If it is red, stop and escalate (`BLOCKED:`): the spec is sequestered and must not be edited during execution (design review 001 F3). **Result (2026-10-02, execution Phase 1): pass.** Dispatched run https://github.com/philipbergen/pickman/actions/runs/37021873302 on 4c0596e (the start commit): the active acceptance step ran `setup-run.spec.luau` on ubuntu, `8 passed, 0 failed, 1 spec files`.
