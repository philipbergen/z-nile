# Refute 005: c0116
- F1: fixed: differently from the Recommendation, keeping its reasoning. I tried `refuseDirty("renumber")` first, and it turned 26 cases of three promoted specs red (c0001/tracker-lifecycle, c0052/renumber and c0082/cli). Those run `renumber` on trees with untracked files, as the documented duplicate-copy workflow does with a fresh stub, so it would have narrowed a promoted behaviour for a low finding. So I followed the reviewer's own candidate lesson: "git's view" is two views, and each reader takes the one its commit carries. `gitFolderFiles(dir, tracked)` stays one reader. `keepRecords` (compact, remap, renumber) reads the index (`ls-files -c`), because a rewrite commits only tracked files; the carried move's raft reviews keep `-co --exclude-standard`, because a review may not be committed yet. `gitFolderFiles` is not switched to `-c` for the review check. §1 and AC1 now state the same rule. The rv5 Q5 case is in compact-record.spec: renumber with an untracked work file in a member's folder, land, and `ready` succeeds. M92 (`keepRecords` on the `-co` view, round 4's code) run and killed. The lesson is a note on architecture/one-reader-per-format. consequences: a member that is itself untracked (a fresh stub) hashes empty in `keepRecords`, and is then left as it was; a grouped member is always committed, so this never changes a real record.
