### F1 [medium] `ready` and `keepRecords` hash the working tree, ignored files included, while the record is taken from git: an ignored `acceptance/.DS_Store` makes `ready` refuse a raft nothing redesigned, and the refusal's own recovery cannot clear it
Where: §1 "What the record covers" ("The adapter reads a member's folder from origin/main, from the publish build's tree or from the working tree"); `localFolderFiles` (walks the directory: every file, tracked or not); `cmd.ready` (`now[m.id] = raftplan.recordHash(m.id, localFolderFiles(m.dir))`, outside `moveOnOrigin`'s build); `keepRecords` (its before and after hashes).
Evidence: reproduced (rv4 Q1). A grouped raft R0900 lands with a covering review. In the main checkout `tracker/issues/c0010/acceptance/.DS_Store` appears (Finder; `.DS_Store` is in `.gitignore`, so `git status --porcelain` is empty and `mainCheckoutGuards` passes). `./zn ready R0900`: "R0900: c0010 (9f209e52f27f → e16c61142ffc) changed on origin/main since R0900 grouped it: z-raft drops it (./zn unfold …) or folds it again with a new coherence review". Nothing changed on origin/main. Removing the file, `ready` succeeds. Following the message instead (unfold, fold, a new review) re-records from origin/main, which has no `.DS_Store`, so `ready` refuses again: a loop that costs a review round per turn. `keepRecords` has the same reader: an ignored file in a member's design files in the compact or renumber worktree makes "matched before" false, so the entry is left stale and every later `ready` refuses (or, after the rewrite, the fresh hash includes the file and `ready` refuses later). Reasoned, not run: `ready`'s check runs before `moveOnOrigin`'s build, so a member redesign landing between `pullMain` and the publish passes, while the carried move checks inside its build.
Critique: one record, three readers, and only two of them read the same thing (git blobs). The record's direction is safe here (a false refusal, never a pass), but the message is false and its recovery does not recover. The tempting fix is to skip dot-files, which leaves editor swap files, `*.orig` after a merge, and anything else `.gitignore` covers.
Consequences: reading tracked files only changes what `keepRecords` sees mid-rewrite: `compactLib.apply` moves folders with `git mv` when tracked and `fs.move` otherwise, so the after-hash must read the index's paths with working-tree bytes, not `HEAD`.
Recommendation: one folder reader for the record, over git's view: `ready` computes `now` inside `moveOnOrigin`'s build with `treeFolderFiles(paths, read, dir)`, exactly as the carried move does (this also closes the window after `pullMain`); `keepRecords` lists a folder's files with `git ls-files -- <dir>` (the index, after the rewrite's `git mv`) and reads their bytes; `localFolderFiles` goes, or is that. Say it in §1 ("every hash reads tracked files: origin/main, the publish build, or the index"). Spec cases: an ignored `acceptance/.DS_Store` in the main checkout leaves `ready` succeeding; the same file in the compact worktree leaves the raft readyable after `compact`. Mutant: the working-tree walk (today's code).
Lesson: architecture/one-reader-per-format
