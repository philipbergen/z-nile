### F1 [low] `gitFolderFiles` lists untracked-but-not-ignored files, so a work-in-progress file in a member folder during `renumber` (the one rewrite with no clean-tree guard) leaves the record stale, and `ready` then refuses with a false "changed on origin/main". AC1 says the opposite ("tracked files only")
Where: `gitFolderFiles` (`git ls-files -co --exclude-standard`); `keepRecords`' before-hash; `cmd.renumber` (no `refuseDirty`, unlike `compact` and `remap`); §1 "Every hash reads git's view … tracked and untracked-but-not-ignored files"; AC1 "Every hash reads tracked files only, and an ignored file never changes one".
Evidence: reproduced (rv5 Q5). Raft R0901 over c0030 and c0040 lands with a covering review. In a fresh worktree, an untracked `tracker/issues/c0040/acceptance/wip.spec.luau` is written (not ignored). `./zn renumber c0040` → `c0040 -> c0901`. The file is deleted, the rename is committed and landed. `./zn ready R0901`: "c0901 (efd61a19d243 → 9153e361cba5) changed on origin/main since R0901 grouped it". Nothing was redesigned. Without the file (rv5 control) the same sequence leaves `ready` succeeding. The before-hash included the WIP file, did not match the origin record, and so the entry was not carried through the rename.
Critique: this is a false refusal (the safe side), and it needs a WIP file in another issue's folder during a renumber, so it is low. But the round-4 fix moved the reader to "git's view" and chose the one view (`-co`) that still lets the working tree in. The design states the rule two ways: §1 and the code say `-co`, AC1 says tracked only. One fix is tempting: switch `gitFolderFiles` to `-c`. That breaks the carried move's review check, because z-raft writes the review and then runs the carried move before committing (claims.spec does exactly that).
Consequences: the two callers need different views. The review check needs what the prep commit will carry, so untracked files count. `keepRecords` needs what the rewrite will commit: `git mv` moves tracked files, and the rewrite edits bytes on disk.
Recommendation: `cmd.renumber` calls `refuseDirty("renumber")` as `compact` and `remap` do. That makes all three rewrites start clean, and `-co` then equals `-c` for `keepRecords`, so the reader stays single. Make AC1 match §1: "every hash reads git's view (tracked files, and untracked ones that aren't ignored); an ignored file never changes one; the rewrites refuse an unclean tree". Add a spec case (rv5 Q5) where `renumber` with an untracked file in a member folder is refused, naming the tree. Add a Rules row and the mutant "renumber without refuseDirty".
Lesson: ticket-prep/restated-rules-move-together

Candidate lesson (for the lead, a note on architecture/one-reader-per-format): "git's view" is two views, the index and the working tree as `git add -A` would see it. Choose one per reader for what that reader's commit will carry, and make every rewrite that hashes before and after start from a clean tree.
