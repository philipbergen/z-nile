# Refute 001: c0117 (answers to design-review-001.md)
Prototype: `proto-c0117`, rebased onto `proto-c0116` 94bf674 (simulation 76db711, the edits on top). The user decided F3 on 2026-10-21 ("Bot token, no bypass"), recorded as a `Decided with the user` line in the Problem.

- F1: fixed: the git wrapper decides from git's own resolution, not a parser. `z-nile/bin/git` routes every invocation naming `push`, `send-pack`, `http-push` or `receive-pack`, carrying any `-c`/`--config-env`, or whose command word is an alias (`git config --get alias.<word>`) to `wrap.luau`; `wrap` resolves aliases under the same global options (a shell alias is refused), refuses plumbing, runs `push --dry-run --porcelain` with the same options and arguments (`-q` left out; no `Done` refuses) and decides every update to `refs/heads/main` (`wrapper.decidePush`) against a private fresh fetch (`+refs/heads/main:refs/zn-wrap/main`) and that ref's registry; the local tracking ref is never read. wrapper.spec runs the reviewer's forms for real (16 code-push forms including `--git-dir`, `--work-tree`, `-c alias`, `--config-env`, `heads/main`, a wildcard, `:`, `push.default=matching`, `remote.origin.push`, `send-pack`, a config alias, `--all`, `--mirror`, and the `update-ref` of the tracking ref): every one refused; tracker state and a branch's own name pass. `$ZN_REAL_GIT push` is out of the wrapper's reach by design, and the tripwire catches it (F3). consequences: a push costs a dry run and a fetch (Scalability); the wrapper is now named a convenience layer, the boundary being the credential, the server's protection and the tripwire (§7, zz-rules); rows and mutants M51–M54, M84 (equivalent: a dry run without `--all` fails, which refuses).
- F2: fixed: agents never merge. The dispatcher merges itself with the real gh on the real PATH and the user's credential (§6.9); `authorised/` is gone. The gh wrapper is an allow-list of the skills' commands (`wrapper.GH_ALLOWED`), after skipping gh's global options (`-R`, `--repo`, `--hostname`) and expanding aliases (`gh alias list`; a shell alias refused), and `gh api` allows reads and `POST` to issue and PR comment endpoints only; a GraphQL mutation is a write. wrapper.spec covers each of the reviewer's forms (`-R o/r pr merge`, an alias, GraphQL mutation, `PATCH git/refs/heads/main`, `PUT contents`, `-XPUT …/merge`, `PATCH default_branch`) and walks every `gh` command the skills name against the list. consequences: a gh call costs a Lune start; a skill that names a new gh command must extend the list (the walk case fails until it does); M55–M58.
- F3: fixed by the user's decision (2026-10-21): "Bot token, no bypass". The agent's credential (`credential.luau`: `$ZN_AGENT_TOKEN_FILE`, `~/.config/zn/agent-token` or the keychain item `zn-dispatch-agent`) is the step's `GH_TOKEN`/`GITHUB_TOKEN`, gh reads an empty configuration folder of the step's own, git's credential helpers answer with that token only; no credential, no CLI. The tracker's pushes from inside a step go through the dispatcher's publish broker (`broker.luau`), which pushes tracker state only, with the user's credential. The post-step tripwire (`dispatcher.tripwire`) checks that every commit `main` gained is a broker push or tracker state and that the main checkout moved only along `main`; anything else is exit 5. §8 holds the user's setup steps (the bot account or App with its permissions, storing the token, the ruleset `gh api` call, the check), never run by an agent. What isn't enforceable is said plainly (§5, zz-rules): a same-user process can read the user's own credentials where they live; only a separate OS user would stop it. consequences: the broker is new interface and state (`ZN_PUBLISH_BROKER`, `state.pushed`); `publish.commit` and `land` gain a broker branch; `onGitHub` reads the configured URL; repo-fence gains a reviewed entry for `credential.luau`; spec cases: the agent sees only the agent's token and its own gh folder, no credential starts nothing, a claim reaches `main` through the broker with the tripwire quiet, a real-git code push trips the wire and keeps the spend, the chain stays stopped after it; M59–M64, M77.
- F4: fixed: (a) the launcher is a supervisor with a lifeline: its stdin is a pipe from the dispatcher, and end of file or its own TERM/INT/HUP kills the group; (b) a run's identity is an flock the supervisor holds on `<state>/run.lock` for as long as the group lives (`runner.sameRun`), because `ps` is refused in the specs' jail (E13); `stop` signals a group only while it is still the run's, never a group id that is not a whole number above 1, and otherwise marks it `lost`; (c) a run lock (`<id>/lock`, an flock held by a helper that dies with its dispatcher): a live run refuses a second, and a run left `running` by a dead dispatcher is `lost`, never resumed, until `retry`. control-cli covers the dispatcher killed mid-step (no grandchild left), the lost run and its retry, the refused second run, and a stale state whose group id names a live process, and a group id of 1 with a held lock (both lost, nothing signalled). consequences: new outcome `lost` (the chain stops on it; c0118 shows it); M65–M67; the `kill -- -1` mutant is reasoned, never run (it would signal the whole spec run).
