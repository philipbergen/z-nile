### F1 [high] The home fence's jail case only passes under the macOS jail: promoted, it turns CI's Linux gate red
Where: `acceptance/homes.spec.luau`, "in the jail, a home sentinel the write is refused for leaves the ceiling and every guard as the root's" (lines 160 to 196), and "a symlinked pickman/.cache refuses…" (the `inJail` run, line 152); `.github/workflows/check.yml` (`runs-on: ubuntu-latest`, the gate runs every promoted spec); `tests/lib/fence.luau:524` (`"none (not macOS: environment guards only)"`).
Evidence: the case runs the probe check.sh as `fixture.exec(f.main, "bash", { probe })`, with no env. So it reaches the waiver only if the runner's own `PICKMAN_TEST_JAIL=sandbox-exec` is inherited, and expects `r.ok == true` and "the jail refused". On Linux the runner exports `PICKMAN_TEST_JAIL="none (not macOS: environment guards only)"`. In an accepted outer sandbox on macOS it exports `"outer sandbox …"`. In both cases `pickman_home_fence` takes its refusal branch, and the case fails. I reproduced it in a scratch clone of 632dba2. I passed that run's `r` the Linux value (`env = { PICKMAN_TEST_JAIL = "none (not macOS: environment guards only)" }`), the only change. The result was `FAIL … in the jail, a home sentinel …: No such file or directory` (the check.sh refused before writing `guards.txt`). Its leftover `probe/` folders then failed two later cases ("the main checkout is not clean"), giving 11/14. Unmodified, the same clone passes 14/14. After `./zn done`, `homes.spec` is promoted to `tests/acceptance/c0120/` and runs in CI's `gate` job on ubuntu. So c0120's PR (or the first push after it) is red there, although every local gate on macOS passed. The symlink case's `inJail` run has the mirror defect. On Linux it inherits "none", so it never tests the marker path its comment claims, and W5 ("refusals waived under the jail marker alone") would survive there.
Critique: the waiver's own logic is right. The spec just takes its jail from the machine it runs on, and the prep, the mutation runs and the Verification log were all on macOS. The tempting fix is to skip the case unless `PICKMAN_TEST_JAIL == "sandbox-exec"`. That leaves the waiver and W1b/W3/W4 untested on CI, and on any macOS host that runs specs in an outer sandbox.
Consequences: setting the markers explicitly simulates a jail in an unjailed run on Linux. That is safe here, because everything it touches is the fixture under the run's `.cache`, and `chmod 555` stands in for the kernel's refusal. But `homes.spec` then names `sandbox-exec` in an env table, which the repo-fence scan reviews (its `ALLOWED` entry for this file must cover the new lines). `chmod 555` doesn't stop root, so a root runner would write the sentinel and fail "the jail refused". GitHub's ubuntu runner isn't root, but the case should say so or detect it.
Recommendation: give the case's waived run all three markers explicitly: `env = { PICKMAN_TEST_JAIL = "sandbox-exec", PICKMAN_FENCE_SPECS = "1", PICKMAN_TEST_FENCE = <the fixture's root> }`. Do the same for the symlink case's `inJail` run, so both test the marker path on every OS. Keep the explicit no-marker runs. When `pickman/.cache` is still writable after `chmod 555` (root), fail with a clear message rather than pass vacuously. Extend repo-fence's `ALLOWED` entry for the promoted `homes.spec` to the new marker lines, and rerun E7. Rerun W1b, W3, W4 and W5 with the markers set explicitly, and once with `PICKMAN_TEST_JAIL="none (not macOS: environment guards only)"` in the runner's environment, as Linux would have it, recording the result in the Verification log. Add a Verification-log line that the c0120 specs pass with each value `PICKMAN_TEST_JAIL` takes (`sandbox-exec`, `none (…)`, `outer sandbox (…)`).
Lesson: candidate for the lead (none existing fits): *a spec case that depends on what the runner sets for the host (the jail, its markers, the OS) sets it explicitly, or it passes only where its author ran it. Check: run each case with every value `PICKMAN_TEST_JAIL` takes on CI and in an outer sandbox. Does it still test what its name says?* It belongs in the testing skill's lessons.

### F2 [low] The waiver says "the jail refused" without checking that the jail forbids writes there
Where: §3 step 5 ("That is the jail refusing a write outside the run's `.cache`"); `fence.sh` `pickman_home_fence`.
Evidence: the waiver tests that a jail exists (the three markers), not that `<home>/.cache` lies outside the jail's writable area. Inside the jail, a home whose `.cache` is under `$PICKMAN_TEST_FENCE/.cache` (a fixture) or is the run's own `.cache` (a run started from `pickman/`) is writable. There a failed sentinel write (a full disk, a `mktemp` failure, a jail-refused `rm` of a planted sentinel link) has some other cause. It is waived anyway, with a message that says the jail refused. I found no escape from it: the kernel still refuses writes outside the run's `.cache`, and the hooks are set. So this is the design's sentence being stronger than the code, not a hole.
Recommendation: add the fourth condition the sentence states. Waive only when `<home>/.cache` is neither `$PICKMAN_TEST_FENCE/.cache` nor under it, mirroring c0114's `jailed` test, which compares the same two paths. With F1's explicit `PICKMAN_TEST_FENCE=<fixture root>`, the fixture home is outside that `.cache`, so F1's case still reaches the waiver. Add a case and a mutant: under the markers, with `PICKMAN_TEST_FENCE` set so that the home's `.cache` lies under `$PICKMAN_TEST_FENCE/.cache`, a refused sentinel refuses. Add the line to `cachepaths` if the comparison is new text there.
