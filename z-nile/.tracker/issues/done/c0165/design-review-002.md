### F1 [high] The lifeline dies with the orchestrator's process group, so a killed run's runner lives on and holds the home's lock (repeat of design-review-001 F12)
Where: Design, "`specs.luau run`", **Lifeline**; Rules R38; gate.spec "AC5: a killed owner's spec is taken over" and "AC5: a killed orchestrator's runner dies with it"; capture, **Crash detection** ("takes the row over and runs the spec itself").
Evidence: The supervisor puts only the *runner* in a new group (`if ($pid == 0) { setpgrp(0, 0); ... }`). The supervisor itself stays in the orchestrator's group, so a signal to that group kills the supervisor too, and nothing is left to see `getppid` change. I ran this on the prototype with a probe spec that sleeps 25 s. I started `lune run z-nile/specs -- run --project z-nile -- tests/zzprobe/hang.spec.luau` under `perl -e 'setpgrp(0,0); exec @ARGV'`, as gate.spec's "killed owner" case does, and ran `kill -9 -- -<pgid>`. Four seconds later `ps` still showed `67042 67042 1 lune run tests/run -- tests/zzprobe/hang.spec.luau` and its children, down to `sleep 25`: the runner was orphaned to pid 1. The next `specs run` of the same spec took the row over at once, then printed `waiting for another test run (pid 67043, 68409, 68510) in this checkout to finish` and needed 40 s. With a real suite longer than `PICKMAN_TEST_LOCK_WAIT` (240 s), the takeover's runner fails, so the capture's "runs the spec itself" doesn't hold. Both spec cases miss it:
- the group-kill case asserts only that the takeover finishes in under 60 s, and nested runs take no lock (design-refute-001 F12);
- the orchestrator-only case relies on a fixed 30 s sleep: under load, if the takeover run plus `sleep 5` takes longer than 30 s, the orphan ends on its own and `alive.ok == false` passes even with the lifeline removed.

The worktree's gate.spec, run on the prototype, passed 17/17 and ended with `sweeper: stopped 4 process(es) the specs left running`, which are the orphaned runners of these cases.
Critique: This round's evidence is a second hole in the mechanism round 1 found holed. The supervisor sits in the group it is meant to outlive. The lesson that F12 was harvested into (zz-arch/children-need-a-lifeline) names the robust form: a pipe whose end of file fires however the parent died. The tempting fix is to kill `-<orchestrator pgid>` on exit, but a SIGKILLed orchestrator runs no exit code.
Consequences: If the supervisor leaves the orchestrator's group, a terminal's Ctrl-C reaches only the orchestrator. The supervisor then has to notice the death by its poll, about 0.1 s later, and stop the runner (TERM, 2 s, KILL). A supervisor killed alone by its pid still orphans the runner; say so as what's left. A pipe lifeline needs a writable child stdin, which `process.exec` doesn't give, so it depends on Lune's `process.create`, which then has to be checked on the pinned 0.10.5.
Recommendation: Question the mechanism, then pick one form and state it:
- (a) the supervisor's first statement is `setpgrp(0, 0)`, so it leads a group of its own, and the runner runs in it. It forwards INT, TERM and HUP as now, and polls `getppid`. Or
- (b) a stdin pipe from the orchestrator (`process.create`, if lune 0.10.5 has it): end of file kills the group.

Either way, name what's left (the supervisor killed by pid alone). Change both cases so their result doesn't depend on timing. The hang spec loops while a `hold` file exists, and the case removes that file only after its assertions; this replaces `sleep 30`. Both the group-kill case and the orchestrator-only case then assert that the recorded `hangpid` is gone within 5 s. Use `ps -p`, not `kill -0`, so that "not permitted" can't read as "gone". Update R38 so it covers the group kill, with the mutant "supervisor left in the orchestrator's group". The Lifeline paragraph's "a runner outlives a killed orchestrator by at most about 3 s" must say which kills it covers.
Lesson: zz-arch/children-need-a-lifeline

### F3 [medium] A pass doesn't record whether the run was jailed, so a pass from an unjailed run serves jailed runs of the guard specs whose jailed cases return early
Where: Design, `fingerprint.of` (no jail in the fingerprint), "Usability" / "fallbacks-name-the-modes-they-cover" (claims the outer sandbox always takes "reuse off"); `tests/lib/fence.luau` ~570 (in an outer sandbox, "the only writable protected paths are this checkout and its own git directory").
Evidence: `z-nile/tests/tooling/repo-fence.spec.luau:499` (`if env.PICKMAN_TEST_JAIL ~= "sandbox-exec" then return`), `c0078/jail-signals.spec.luau:14` and `c0076/sweeper.spec.luau:19` pass vacuously when the run isn't jailed. The fence lets an outer-sandbox run write "this checkout". When that checkout is the main checkout (a session there runs a gate or the stop hook), its `.claude/` is writable, so `open` succeeds and those vacuous passes are recorded under the same fingerprint that jailed runs in every worktree then reuse. The Design's "reuse off in an outer sandbox" holds only from a worktree.
Critique: These are the repository guards' own specs. A reused pass skips the one mode in which their assertions run. The tempting fix, "record only jailed (`sandbox-exec`) runs", turns off every gate.spec fixture, because a nested fixture gate runs as `outer sandbox (a fixture of a guarded checkout)` (fence.luau ~717).
Consequences: The orchestrator doesn't know the jail before the runner decides it, so the jail can't go into the fingerprint ahead of time. The runner has to report it.
Recommendation: The runner writes its `PICKMAN_TEST_JAIL` value into the results file. The orchestrator records `passed` rows only from a run whose jail is the host's strongest (`sandbox-exec` on macOS, the unjailed default on Linux), or from a nested run (`PICKMAN_TEST_FENCE` set, which means a fixture's own db). Any other run reads rows but records nothing, and prints `not recorded: <jail>`. Add a Rules row and a results.spec case for the jail field, plus a gate.spec case with a stand-in that reports an outer-sandbox jail and expects no `passed` row. State the rule in "fallbacks-name-the-modes-they-cover".

### F5 [medium] The concurrency cases rest on 3 s and 30 s sleeps, so they flake under load, and a wrong wait can pass them
Where: gate.spec "two concurrent runs" (`slow1`/`slow2` sleep 3), "a waiter whose owner's spec fails" (`slowfail` sleep 3), "a wait on a live owner gives up" (`hang` sleeps 30, `PICKMAN_REUSE_WAIT=2`); E6 (an orchestrator builds its context in 2.3 s and fingerprints in 3.0 s, idle).
Evidence: Each case needs the second orchestrator to read its rows while the first is still inside its spec. The window is the sleep (3 s) against two cold starts of 2.3–3 s each (E6, idle). If the second read comes after the first run recorded:
- "concurrent" sees `reused`, not `waited for pid`, and goes red;
- "waitfail" sees `failed`, decides `run` and runs `slowfail` twice (`count == 1` red);
- in "timeout", the owner's 30 s ends before the waiter, which needs start-up, a 2 s wait and a jailed run, finishes under load, so the row is `passed` and `gaveUp` is nil.

The capture's own numbers say the gate runs at 2.5× its idle time under load (216 s → 500 s+). The reverse also holds: the cases prove the wait only when the timing happens to line up.
Critique: These are timing margins below start-up jitter (zz-test/timing-margins-above-jitter), in a spec that, once promoted, runs in every z-nile gate.
Consequences: Forcing the order needs a signal that the second run has started waiting. That signal is F6's wait line.
Recommendation: Hold each owner's spec on a marker file instead of a sleep. The case releases it only once the second orchestrator's output file shows `waiting for pid` (F6). For "timeout", the owner stays held until after the row is read. Keep only bounded polls (each with its own limit) in the cases.
Lesson: zz-test/timing-margins-above-jitter

### F6 [medium] The orchestrator shows no sign of life: the runner's output is held until it returns, and a wait prints nothing for up to 30 minutes
Where: Design, `specs.luau run` step 3 ("The runner's output is captured and printed when it returns"), step 4 (the wait, `PICKMAN_REUSE_WAIT` default 1800); prototype `execute` (`process.exec` without `stdio = forward`).
Evidence: An `ALL` affected run of z-nile (179 spec files; any `z-nile/` change forces it) prints nothing until the runner ends. `run_specs` streams that output today. A run waiting on another worktree prints nothing at all until the row settles or the wait ends, and 1800 s is three times the 600 s limit on a foreground command in Claude Code. An agent or a person can't tell a hung gate from a busy one.
Critique: zz-arch/waiting-steps-show-liveness. The output is captured only to cut the `FAIL` lines into `detail`.
Consequences: Streaming means `detail` can't be cut from captured stdout. The results file can carry it instead, as each failed case's name and message.
Recommendation: Run the runner with its output forwarded, and build `detail` from the results file (add each failed case's message to the record, and pin that in results.spec). Print `waiting for pid N: <spec>` when a wait starts and again every 60 s. Give the default wait a reason, or lower it below the foreground limit. Add cases: the wait line appears while waiting (F5 uses it), and the runner's `FAIL` line shows in the orchestrator's output before the summary.
Lesson: zz-arch/waiting-steps-show-liveness

### F7 [medium] The wait loop starts two processes per waited spec every second
Where: Design step 4 ("poll the waited rows every second"), `holds` = `fence.holds(fence.alive(pid), start, fence.startOf(pid))`; prototype `fence.alive` (`process.exec("kill", { "-0", pid })`) and `fence.startOf` (`process.exec("perl", …)`).
Evidence: For every waited row still `running`, each poll calls `holds`, which costs one `kill` and one `perl` process. A run waiting on another worktree's `ALL` run of z-nile's 179 spec files (`git ls-files 'z-nile/tests/*.spec.luau' | wc -l`) starts about 358 processes a second, for as long as the owner runs, on a machine already under gate load (c0157). Usually all of those rows share one owner.
Critique: zz-test/count-calls-in-poll-loops: no spec counts the calls, so the cost is invisible until it slows the gates it waits on.
Consequences: none beyond a cache.
Recommendation: Ask `holds` once per distinct `(pid, start)` per poll (and once per distinct owner in step 2). Add a gate.spec case where one owner holds several waited specs, with `perl` (or `ps`) wrapped by a counting stand-in that answers only `STARTED`'s call, and assert the count per poll. Add a Rules row.
Lesson: zz-test/count-calls-in-poll-loops

### F9 [medium] gate.spec takes about 90 s, and once promoted it runs in every z-nile gate
Where: Scalability (no line for the new specs); Test plan (gate.spec carries 17 cases); TOOLING (any `z-nile/` change forces z-nile's full run).

### F10 [low] The learning clone keeps `origin` pointed at the real repository, and its trials are not given the real repository as a protected one
Where: "Learning a missed dependency" step 3 (`git clone -q --no-hardlinks --no-checkout <root> <dir>`), and "Changes stay out of the real repository".
Evidence: `git clone <root>` sets the clone's `origin` to the real repository. The trial runner fences the clone (`protectedPaths`: the clone's common dir, plus `PICKMAN_FENCE_REAL_GIT`, which nothing sets). On Linux, where trials aren't jailed (CI and Linux hosts), a trial spec that pushes to its checkout's `origin` reaches the real repository with no ref guard naming it. On macOS the jail's `deny file-write* (subpath "/")` stops it. No current spec pushes to its checkout's origin, so this is a path only for a faulty spec.
Recommendation: After the clone, `git -C <dir> remote remove origin` (the trials need no remote), and run each trial with `PICKMAN_FENCE_REAL_GIT=<the real common dir>`. In AC8's case, assert that the fixture's own refs are unchanged after learning.
