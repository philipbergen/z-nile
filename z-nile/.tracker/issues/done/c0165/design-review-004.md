### F1 [high] The project-scoped stop hook drops the projects that the forcing rules name: a harness change no longer runs pickman's specs, and a stray old-root file no longer runs the old-roots check
Where: Design, Modules (`scripts/hooks/stop.sh`: "maps changed paths to their homes … old-root `src/` and `tests/` map to `pickman`"); Gate modes table (stop hook row); Scalability ("Design choice (2026-10-31)"); `acceptance/stop-hook.spec.luau` (lines 56–66); R57; Wording (`scripts/check.sh --project "$home" --affected`).
Evidence:
- Today's selector, probed per project: `lune run z-nile/affected -- --project pickman z-nile/tests/lib/t.luau` prints `ALL`. So does `--project pickman z-nile/lib/projects.luau`. `SHARED_FULL` (`z-nile/affected.luau:20–29`) says these "force a full run" of every project, because pickman's specs run on z-nile's runner and harness.
- The designed hook maps `z-nile/lib/x.luau` to `--project z-nile` alone, and stop-hook.spec pins exactly that (`t.expect(stop()).toBe("--project z-nile --affected\n")`). An edit to `z-nile/tests/lib/t.luau` that breaks every pickman spec therefore passes the stop hook. Today the hook runs `scripts/check.sh --affected` with no project, which gives `ALL` for both projects, so it is caught.
- Old roots, probed: `--project pickman src/x.luau` prints nothing, `--project pickman tests/x.luau` prints nothing, and `--project z-nile` prints `ALL` for both, because `OLD_ROOTS` forces z-nile's full run, "whose old-roots spec then fails" (`affected.luau:42–45`). The design maps `src/` and `tests/` to pickman, and stop-hook.spec pins `src/x.luau` → `--project pickman --affected`. That gate selects no spec, so `c0120/old-roots` never runs and a stray `src/x.luau` passes the hook. Today it fails, and the promoted `c0120/ci.spec` says it should ("the old place: gated, and the old-roots check fails there"). Its stub gate logs any arguments, so it stays green, and the regression is hidden.
- A tree from before c0114 (no `z-nile/roots.luau`), which the hook still supports ("this hook runs from the main checkout against any worktree", `stop.sh:24–26`, and `c0114/gate-cover`'s `old` tree): its `scripts/check.sh` rejects `--project` (`*) echo "unknown arg: $1" >&2; exit 2`, at `05b058ea^:scripts/check.sh:18`). The hook then reports "failed; fix before finishing" on every stop. gate-cover's stub accepts any arguments, so this is hidden too.
- No case makes a gate fail when two homes changed. A hook that keeps only the last call's status (pickman red, z-nile green → exit 0) passes stop-hook.spec, whose stub always exits 0, and `c0005/worktree`, which changes one home only.
Critique: The fix for design-review-003 F2 reimplements project selection in the hook by path prefix, beside the selector's own forcing rules, and gets two of the three rule classes wrong. The spec pins the wrong mapping, so a correct implementation would fail AC10. The tempting fix is to add `z-nile/lib/` → both projects and `src/` → z-nile to the hook's prefix table. That is a second copy of `SHARED_FULL`, `TOOLING` and `OLD_ROOTS`, which drifts the next time a rule changes (zz-test/one-rule-one-function).
Consequences: The projects to gate are the homes the changed paths are under, plus every project that `select.forces` names for any changed path (`"all"` → every project; tooling and old roots → z-nile). That needs one reader in the hook, so the hook must run Lune on the session's tree, and a pre-c0114 tree has no `select.luau`. Two sequential `scripts/check.sh` calls also run the static stages twice and share one 300 s timeout. `z-nile/check.sh` already takes repeated `--project` flags, so one call can gate both projects in parallel.
Recommendation:
- Derive the hook's projects from `select.luau`: for example a flag `lune run z-nile/affected -- --gate-projects <changed paths>`, which prints the homes of the paths plus every project `select.forces` names. It reads no `inputs.tsv`, no `*` entries and no db, so a pickman-only edit still names only pickman (the round-3 choice keeps its saving).
- Make one `scripts/check.sh --project <p1> [--project <p2>] --affected` call, so one gate, one exit status and one timeout cover all of them.
- In a tree with no `z-nile/roots.luau`, keep today's unscoped `scripts/check.sh --affected`.
- Update the Wording pin and R57, and rewrite stop-hook.spec's expectations: `z-nile/tests/lib/x.luau` → both projects; `src/x.luau` and `tests/x.luau` → z-nile; a pre-c0114 tree → no `--project`; a stub gate that fails → exit 2.
- Add Rules rows with the mutants "forced projects ignored", "old roots mapped to pickman" and "only the last status counts".
- The hook's command exists today, so run stop-hook.spec against a prototype hook in prep (z-design/prove-specs-pass-on-a-prototype).

### F2 [high] Phase 0's baseline becomes a full gate before the merge, against the captured outcome "The full gate runs only at the merge … Every step before it … runs only the affected specs", with no decision line
Where: Gate modes table (Phase 0 row, `z-nile/check.sh --full --reuse`); Wording (zz-execute Phase 0 step 1, pinned by docs.spec); Problem (capture: "**The full gate runs only at the merge** (`./zn land`, the PR's merge, `done`). Every step before it (the author's iterations, the review, the pre-PR gate) runs only the affected specs."); design-refute-003 F1.
Evidence: `./zn capture c0165` holds the sentence above, and the Problem has no `Scope decision` or `Decided with the user` line about Phase 0. The round-3 answer makes the first step of every raft (zz-execute Phase 0 step 1, today `--full`, `zz-execute/SKILL.md:14`) a full gate. It reuses a matching `full` row when one exists, and otherwise runs every spec (~216 s idle, 500 s+ under load). The reason is sound: an affected baseline on a fresh worktree selects nothing (design-review-003 F1, zz-test/no-vacuous-pass). But the result contradicts a captured outcome, and the round-3 reviewer's recommendation is not a user decision (z-design, **Scope is what was captured**).
Critique: A safety argument doesn't license a scope change. The fix the author will be tempted to make is to call Phase 0 "not a step before the merge". It is one: it runs before the author's iterations.
Consequences: Each option changes what a raft costs or what it can detect. Keeping Phase 0 full costs a full run whenever main's content has no `full` row (any merge after the last `done`, or a tools change). An affected baseline detects nothing. Reading CI's result for `origin/main`'s head costs no local run, but needs `gh` and a network call, and a CI run that hasn't finished yet needs a rule of its own.
Recommendation: escalate to the user: (a) keep `--full --reuse` at Phase 0 (a full gate before the merge, often reused) and record it as `Decided with the user (YYYY-MM-DD)`; (b) Phase 0 reads CI's conclusion for `origin/main`'s head commit (`gh run list --commit <sha>`), refusing on red, waiting or failing closed on pending, and runs no local full gate; or (c) no red-main baseline at Phase 0, so red main is first seen at `done`, where learning's trial (b) reports "fails on the base too". Then pin the chosen wording.
Lesson: z-design/never-narrow-captured-scope

### F3 [medium] A `*` fingerprint and the affected whole-gate digest hold every ref of the shared repository, so any push, fetch or other session's commit invalidates them, and a long `*` run usually can't record its pass
Where: `fingerprint.of` ("one `<ref>\t<commit>` line per ref, sorted"); `workspace.gitState` (`git for-each-ref`, no pattern); Whole-gate reuse ("affected-mode HEAD/ref state when the selection holds a `*` spec"); affected step 3 (R31's re-read "from fresh blob and git-state reads after the run"); R52, R53.
Evidence:
- This checkout has 61 `refs/heads`, 29 `refs/remotes/origin` and one tag, all shared by every worktree. `origin/main` took 114, 221, 15, 17 and 4 commits on 2026-10-25 to 2026-10-31, so the shared refs move every few minutes on a busy day. Every worktree's own commits, `./zn` publishes and `git fetch` move them too.
- The author's pass can't serve the reviewer for any `*` spec, nor for z-nile's whole gate, which always selects the 15 `*` specs. Between the two runs, zz-review code mode has the author push (moving `refs/remotes/origin/<branch>`), and the reviewer runs `./zn sync --fetch` (moving `origin/main`). Both change every `*` fingerprint and the affected digest, though no spec's input and no HEAD changed. The capture's "so the author's pass serves the reviewer" then fails for exactly the slowest specs (`c0120/finished`, 132–754 s).
- R31 makes it worse. A `*` spec whose refs moved while it ran is "released and not recorded". A 132–754 s run in a checkout whose refs move every few minutes therefore often records nothing at all, and the next run starts again.
- The specs' git-state reads are HEAD (clones of HEAD, HEAD history, HEAD's tree: E9's list and design-review-003 F2's own split). The design never shows that a `*` spec reads another worktree's branch or `refs/stash`.
- Only the pure case moves a ref (`select.spec` "HEAD and refs"). A `gitState` that returns `refs = {}` passes every gate case, since none moves a ref without HEAD (zz-test/kill-mutants-where-the-value-is-built).
Critique: The F3 fix chose "every ref" because it's the easy superset, and that defeats reuse where reuse matters most. The tempting fix is to drop refs completely. That loses the specs that do read a ref (if any, for example a spec comparing with `origin/main`).
Consequences: Narrowing needs a way to say which refs a spec reads. That is a new `inputs.tsv` form (or a rule that `*` means blobs plus HEAD), a parser rule with refusals, the digest's git-state extra built from the same set, and R31's re-read reading the same set. A spec that reads an undeclared ref becomes a graph miss of a new kind, which learning can't bisect (it changes files, not refs).
Recommendation:
- Make `*` mean every blob plus `HEAD`.
- Add an explicit `ref:<refname>` input form for the specs that read a named ref. Audit the 15 `*` specs for ref reads and record the search in E9.
- Build the whole-gate digest's git-state extra, and R31's re-read, from the same set.
- Add Rules rows and cases: a ref moved by a fetch or another branch's commit leaves a `*` spec's fingerprint and the affected digest unchanged; a declared ref's movement reruns it; `parseInputs` refuses a malformed `ref:`. Add a gate-level case that moves a declared ref without moving HEAD, which kills the "`gitState` drops refs" mutant.
- State in Scalability what reuse the author→reviewer path gets for `*` specs.

### F5 [medium] R50 (one db read per poll, one liveness check per distinct owner) has no case, though the fixture already proves the seam that would count the calls
Where: Rules and mutants R50 ("(none: a cost, not a result)", reasoned); affected step 4 (waiting); `gatefix.eperm` (a `kill` stand-in on PATH, which `fence.alive`'s `process.exec("kill", …)` resolves, `fence.luau:113`); `PICKMAN_SQLITE3` (the db's binary seam).
Evidence: A waiter on 30 spec files from one owner that checks liveness per spec makes 30 `kill -0` calls and up to 30 `sqlite3` processes a second, for up to 1,800 s (`PICKMAN_REUSE_WAIT`), while z-nile's affected gates select 19 or more files. No case can tell this from the designed loop. The fixture already places a `kill` stand-in that the orchestrator's probe resolves (`gatefix.eperm`), and `PICKMAN_SQLITE3` can name a counting wrapper. zz-test/count-calls-in-poll-loops asks for exactly this case.
Critique: "A cost, not a result" is the reason the lesson rejects. A poll loop's cost is what this lesson counts.
Consequences: A count in a case depends on how long the wait lasts. Bound it by polls, not by wall time: count `kill -0 <owner>` calls per `sqlite3` read during one hold.
Recommendation: Add a gate-wait case: one held owner with three claimed spec files, and a waiter whose PATH has a logging `kill` and whose `PICKMAN_SQLITE3` is a logging wrapper. Assert that the `kill -0 <owner>` count is at most the poll count plus one, not three times it, and that each poll makes one `sqlite3` read. Mark R50 with that case and the mutant "a liveness check per waited spec".
Lesson: zz-test/count-calls-in-poll-loops
