### F1 [high] After a release, the next merge stops: a deleted entry's GET 204 is a hard failure, and the loopback never returns it
Where: `c0172.md:50`–`:52`; `acceptance/cicd.spec.luau:114`–`:132`; prototype `pickman/scripts/lib/lease.luau:230`–`:234` and `:271`–`:276`
Evidence: The design deletes the entry on the way out and creates with `exclusiveCreate` when the entry is absent. Open Cloud's Get Entry prose says a tombstone returns 404, and the same operation's response table lists `204` ("The key is marked as deleted"). Delete Entry "marks the entry as deleted by creating a tombstone"; its parameters are `datastoreName`, `entryKey`, and `scope`. `matchVersion` is on Set Entry, not on Delete. The prototype's `read` treats 404 as absent and every other non-200 as `reading the lease failed with HTTP {status}`. Its delete sends `matchVersion`. Injected HTTP, no network: a GET 204 that includes `roblox-entry-version: tomb` returns `version=nil`, `err=cicd: reading the lease failed with HTTP 204:`, `writes=0`. The spec's fake answers a missing entry with 404, and the 204 it does return is the delete response, after which the next GET is 404. The release case does not acquire again. E7's live call stopped at 403, so a delete-then-get was never recorded.
Critique: The first merge can create, publish, and delete. The next merge reads the tombstone. If that GET is the 204 in the response table, acquire prints the error above and does not publish, and every later merge stops. The tempting fix is to keep treating only 404 as free, because the prose says 404. The response table still lists 204, and the client I ran has no branch for it.
Consequences: A 204 may carry `roblox-entry-version` or not. If it does, the conditional clear is a POST with `matchVersion`, the parameter Set Entry documents. A DELETE that sends `matchVersion` anyway can be ignored (the clear is no longer conditional) or rejected (release fails and the entry stays). `exclusiveCreate` on a tombstone can 412; that attempt has to re-read and replace, or the second merge stops on 412 instead. The scopes that retire E7's 403 are `universe-datastores.objects:read`, `:create`, `:update`, `:delete`, and `universe-datastores.control:create`. `datastore.control:create` is not one of those strings. Until the key has them, the command still stops before publish.
Recommendation: On GET 204, if `roblox-entry-version` is present, POST `matchVersion` of that version with this run's hold; if it is absent, `exclusiveCreate`, and on 412 re-read once and replace. Release clears by that same POST of an expired hold, which is the documented compare-and-swap, and deletes the token file only after that POST succeeds. `cicd.spec` (promoted: the second merge has to keep working) returns 204 with a version header on the GET that follows a clear, and the command publishes. The client measured above fails that case. Replace `datastore.control:create` in the Runtime tests section with the five scope strings.
Lesson: zz-test/seed-every-enumerated-case

### F6 [medium] Both renew calls can be deleted and the success case stays green
Where: `c0172.md:50`; `acceptance/cicd.spec.luau:405`–`:427`; prototype `pickman/scripts/cicd.luau:219` and `:229`; `pickman/scripts/lib/lease.luau:27`
Evidence: The design renews the deadline after the publish and before the lobby suite, for twenty minutes (`Lease.SECONDS = 20 * 60`). Deleting only the two call lines `renewOrStop()` and leaving the function in place left cicd.spec at 18 passed. Restored; both calls are back at those lines. The success case does not read a lease POST body. `OpenCloud.execute` waits up to 120 seconds per script, and there are two runtime scripts. `deploy-beta` pauses 60 seconds on HTTP 409, up to five attempts, per place.
Critique: A command that takes the lease once and never moves `until` passes. Two scripts plus those 409 pauses stay inside twenty minutes, so today's run can finish on the first take. A later script, or a publish that uses the 409 retries and then both suites, crosses `until`. Release without the token is allowed once `until` has passed, so the other merger can clear the entry and publish the same places while the first suites are still in progress.
Consequences: One renew before the lobby suite leaves a game suite that runs first on the original deadline, and the lobby suite on whatever remains. Each suite needs a new `until` at least twenty minutes ahead of the fake's clock, measured from the lease POST body, not from the wall clock. A suite longer than twenty minutes still expires in the middle; the case bounds the gap from that POST to the suite's task-create. The file count from F2 is the suite, so this case does not grow a second list of script names.
Recommendation: `cicd.spec` (promoted: the hold has to keep covering both suites) fails the success case when either suite's first task-create is not preceded by a lease write whose `until` is at least twenty minutes after the time the fake is using. The two-call deletion fails that case. The design sentence is: renew before each suite, for twenty minutes.
