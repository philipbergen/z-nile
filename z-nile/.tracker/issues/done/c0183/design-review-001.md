### F1 [high] AC3 passes a branch whose final design files are wrong, as long as some earlier commit had them right
Where: c0183.md Design item 3 (last bullet but one), AC3; acceptance/designs.spec.luau `versions`/`some`; Rules and mutants, last row.
Evidence: on review branch h1 (from the correct implementation commit), one later commit changed snake's "3 lives" to "5 lives", appended a line to `invaders/.tracker/game-design.md` and deleted `portal/.tracker/architecture.md`. `lune run tests/run -- …/designs.spec.luau` printed `3 passed, 0 failed`. Because the check accepts any historical version, it can't see what the branch delivers. The Rules and mutants table lists the opposite variant ("a wrong first commit fixed by a later one", which should pass) but not this one ("a right first commit broken by a later one", which must fail). The stubs have the same hole: a deleted stub passes.
Critique: the any-version rule fits the promoted spec's job, which is to stay green while later product decisions edit the files. It does not fit AC3's job at `./zn done`, which is to prove that the files the branch delivers are the approved blocks. One check is doing two jobs. The tempting fix is to go back to the prototype's first version (`asAdded`, the oldest commit that added the file). That fails the other way: a wrong first commit fixed later stays red forever, which is why E3 moved away from it.
Consequences: an exact done-time check must not turn into a permanent rule, or the first product decision in `snake/.tracker/game-design.md` reddens the gate (z-design/exact-checks-compare-against-the-merge-base, zz-test/promoted-specs-pin-rules-not-sets). It also must not need a moving reference (F2).
Recommendation: split the two jobs (zz-review/recommendations-pick-spec-or-check):
- **check.sh** (runs at done, then never again) gets an exact check of today's tree. Inside `check "AC3: …"`, compare `shasum -a 256` of each of the nine files (five moved designs and four stubs) in the working tree with digests written into check.sh. This is a cheap read.
- **The promoted spec** keeps the any-version rule, compared against the same pinned digests (see F2).
- Add Rules and mutants rows, and run them: `broken-after` (a correct commit, then a later edit or delete), which must fail AC3 through check.sh while the spec stays green; and the existing E3 variants against both checks.

## Candidate lessons (for the lead; a reviewer writes no lesson file)
- **zz-test: a history-tolerant promoted check is not the done-time check.** Rule: when a promoted spec accepts any past version so that later edits stay green, the exact claim about the delivered tree also goes in check.sh. Why: c0183 design review 001 F1, where a correct commit followed by a broken one passed AC3. Check: "Can a branch that once had the right file and then broke it pass this criterion at `done`?"
- **zz-test: expected text is pinned, not derived from a document.** Rule: a sequestered spec never derives its expected value from a file outside sequestration (the issue document) or from a path a compaction renames; it pins a digest. Why: c0183 design review 001 F2, where editing the block and the file together passed, and a compaction rename made the spec red. Check: "Where does the expected value come from, and can the executor or `./zn compact` change that place?"
- **Tooling (capture as an issue; it is not this design's defect).** `./zn capture c0183` returns the stub first commit e0e09cff, not cda05ea6, whose subject `tracker: new c0183-c0188 …` names the id as part of a range. So a capture batch with a range subject hides the real capture from scope review. Check: "Does `capture` expand an id range in the subject's id list, or mark the answer as weaker?"
