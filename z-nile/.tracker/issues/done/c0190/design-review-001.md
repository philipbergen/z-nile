## Candidate lessons
- z-ticket (or z-design): a batched capture of an approved plan's issue list carries the plan's **Order** into `depends_on`, including edges to issues captured earlier (scaffolding, gates) and from them (a later retirement), because c0190's list carried only the edges between the new issues; check: for each ordering sentence in the source plan, which `depends_on` line enforces it, and which already-captured issue must gain an edge to the new ids in the same land?
- z-ticket: a capture that splits one design among sibling issues names each issue's own sub-sections and its siblings, never "builds exactly what <whole design> says", because c0190's draft gave 18 issues the whole game as captured scope, which no prep can narrow; check: does any captured Problem's pointer cover more than its own outcomes, and does every part of the design have exactly one owner?
- z-design: when a raft's deliverable lands outside its PR (a capture `land`), pin the landed text with a one-time digest in check.sh, because the script that writes it is not sequestered; check: can the executor change what lands (an unsequestered script, a hand edit) and still pass every AC?
