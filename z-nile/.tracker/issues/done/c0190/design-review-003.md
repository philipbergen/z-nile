### F1 [high] S5, I4 and T4 own runtime in their game's place but don't depend on the issue that builds the place; S5 also owns the arena's revive and arena runs without S2
Where: c0190.md Design item 2 (table rows S5, I4, T4; "What the outcomes need"); check.sh `ROWS`; capture.py `I` (S5, I4, T4 `deps`)
Evidence: as landed in the prototype, f0213 (S5) `depends_on: [f0209, f0195, f0197, f0199]` = S1, A1, A2, A3, with the outcome "game over offers the 1 R$ revive (3 lives, keeping score and map; **10 s in an arena while play goes on**); game over returns to the portal" and the part "**Players** (\"Every run, solo or arena, goes to Snake's boards\")". I4 = [I1, A1, A2, A3], T4 = [T1, A1, A2, A3]. The portal design: "The revive product is **bought in each game place**"; P4's Non-goals: "The revive product, bought in each game place: S5, I4 and T4". c0190's own Design: "Each game's place, its server session (…), its arrivals and everything the rules show or sound belong to the view issue, which has the dependencies for them" (S3, I3, T3). None of S5, I4, T4 depends on its view issue, and S5 doesn't depend on S2, which owns the arena session the 10 s offer runs in. So `ready` accepts S5 once S1, A1, A2, A3 are done, with no Snake place, no server session to submit runs from or teleport back from, and no arena; I4 likewise before I3 (and so before Z3 and P4). The portal side gets this right (P2, P3, P4 all depend on P1, which builds the portal's screens), so the games are the inconsistent case.
Critique: this is the third round with a hole in "who runs each game's place" (review 001 F6, review 002 F2), and it is the exact check of lesson split-designs-name-each-owner: "When a gap is answered by handing the part to an existing issue, can that issue do it: do its dependencies … put what it needs (the place, travel, a Beta publish) before it?" The edges are picked by hand per issue in "What the outcomes need", so each fix misses the issues it didn't look at. The tempting fix is to add S3/I3/T3 to the three rows and stop; S5's arena part needs S2 as well.
Consequences: S5 → S3, S2; I4 → I3; T4 → T3. No cycle: S3 → S1, A2–A4; S2 → S3, A2, A3; I3 → I1, I2, A2–A4, P4, Z3; T3 → T1, T2, A2–A4, I3; none reach a scores issue. I4 and T4 then wait for Z3 and P4 (through I3), which the Order allows (it fixes only S1, S2, I1, I2, T1, T2 as early). AC4's digests don't change (`depends_on` is outside the span); AC3's rows do.
Recommendation: question the mechanism, not just the three rows: add one rule to "What the outcomes need", "every issue with an outcome that runs in a place (a screen, a purchase, a submit, a teleport) depends on the issue that builds that place and its session (P1 for the portal, S3, I3, T3 for the games) and on the issue that owns the session it runs in (S2 for the arena)", and walk all 27 rows against it in the table (paste the walk). Then S5 gains S3 and S2, I4 gains I3, T4 gains T3; update capture.py, `ROWS` and the table together; add AC3 mutants "S5 without S3", "S5 without S2" and "I4 without I3" to Rules and mutants and run them.
