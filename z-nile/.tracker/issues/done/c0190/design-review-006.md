### F1 [high] S3 now owns a step that needs Z3's manifest and P1's card, but S3 depends on neither, so it can be readied and done before the step exists
Where: capture.py S3 `outs[3]` ("Publishing the Snake place: … Z3's manifest publishes it from then on; until then the portal's card says \"coming soon\""), S3 `deps` ["S1", "S4", "A2", "A3", "A4"]; c0190.md Design item 2, "Publishing a new game's place"; check.sh `ROWS` S3
Evidence: the closure of S3's `deps` (S1 → c0184; S4 → S1; A2, A3, A4 → c0185) contains neither Z3 nor P1. The same holds for S2 and S5, which reach the portal only through S3. So `ready` accepts S3 while publishing is still pickman's fixed two-place `beta.luau` (SETUP.md: "the deploy publishes `default.project.json` … and `lobby.project.json`"). At that point no manifest entry for `ROBLOX_BETA_SNAKE_PLACE_ID` exists, and no card can say "coming soon". The Observed step S3's outcome names ("Z3's manifest publishes it from then on") can't be performed, and S3's prep would have to invent the publish or stop. I3 and T3 don't have this problem (I3 → P5 → Z3; T3 → I3).
Critique: the round-5 fix gave the publish step to the three view issues without walking their dependencies. This is the check of z-ticket lesson split-designs-name-each-owner: "When a gap is answered by handing the part to an existing issue, can that issue do it: do its dependencies … put what it needs (the place, travel, a Beta publish) before it?" It is also the Design's own rule, "an issue that shows or steers a rule depends on the issue that makes the rule", which S3's new outcome now breaks against Z3 and P1. It is the sixth round with a hole at a place's edge. The tempting fix is to add Z3 to S3 and stop there.
Consequences: S3 → Z3 makes no cycle (Z3 → P2, P4 → A1, A2, A3, P1 → c0185; nothing reaches snake). It puts Snake's view, and so S2 and S5, behind the portal's cards (P1, P2, P4) and the manifest. The other fix is to move the step out of S3 into an issue that already waits for both sides. No snake issue does, and a portal issue can't do it for an issue that comes after it.
Recommendation: question the mechanism, not just the edge. Keeping the step in the view issue needs S3 → Z3, so give S3 Z3 and say why in "What the outcomes need" and in the order table. Then update `ROWS` S3, regenerate S3's digest, and add the AC3 mutant "S3 without Z3" to E4-mutants.sh and Rules and mutants, run on a prototype. If the user would rather keep Snake's view parallel with the portal, that is a scope-order decision. Escalate to the user with the options: (i) S3 → Z3 (Snake waits for the portal's cards and manifest); (ii) give the publish step to a later issue that depends on both S3 and Z3, at the cost of one more edge there and, under F4, a later Snake on Beta.
Lesson: z-ticket/split-designs-name-each-owner
