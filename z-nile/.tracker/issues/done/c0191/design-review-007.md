### F1 [medium] The suite's wall-clock case can't fail for a runner that never stops the command
Where: `acceptance/bounded.spec.luau`, "a command past --time is stopped … (stand-in clock)"; Rules and mutants row "the wall limit stops the command"
Evidence: mutant A (the deadline sets `$timedout`, nothing is signalled) passes all 14 cases. The `sleep 61.1` ends by itself, the runner then exits 124 with the message, and `alive(pid)` is false. The only thing that changes is that the run takes 61 s longer. The row lists only the `exit 1` mutant, and its stand-in form is marked "reasoned, not applied".
Critique: the case is the suite's only guard on "the wall limit stops the command". Its "the command's process gone" assertion is vacuous whenever the command ends by itself before the case looks. The real stop is now only in the one-time proof, so after `done` nothing guards it. The tempting fix is a longer `sleep` (3600). That fails the mutant only by hanging the spec until the runner's limit, which is a slow red and exactly the kind of wait the user ruled out.
Consequences: an elapsed-time assertion uses the wall clock. Its bound must be loose enough not to flake under a loaded gate and much tighter than the sleep.
Recommendation: in that case, record `os.clock()` or `os.time()` before and after `standIn(...)`. Assert that the runner returned in under 10 s (the stop takes a fifth of a second; the sleep is 61.1 s), and assert that before `alive(pid)`. Add mutant A to the row and mark it `run`.

### F2 [medium] runner-cpu and engine-cpu no longer show that the limit is in force, and a cheap stand-in exists
Where: `acceptance/runner-cpu.spec.luau` ("the limit is in force … with a lower caller"), `acceptance/engine-cpu.spec.luau`; Rules rows "every spec process has `ulimit -t`" and "the engine has a CPU limit"

Mutant D (the same in `zn`) passes engine-cpu 2/2. The burner and spinner cases removed in this re-prep were what killed these mutants. They're now only in `proof-limits.luau`, which never runs after `done`.

Consequences: none. The fix spends no CPU: a limit below the jail's 1200 s is observable just by reading `ulimit -t`.
Recommendation: in runner-cpu, add a case `runProbe("77")` with no caller limit and expect `read("limit.txt") == "77"` (verified: the good runner passes it, mutant C fails it). In engine-cpu, add a case whose stub engine prints `process.exec("sh", {"-c", "ulimit -t"}).stdout` under `ZN_ENGINE_CPU=90` with no stand-in, and expect `90`. hooks.spec's pre-bash case already does this for the hook. Add mutants C and D to the two rows.

### F3 [medium] "Runs once" isn't true: every `./zn check c0191` runs both proofs, before and after `done`
Where: check.sh AC1 and AC5 lines and their comments ("runs once", "never promoted as a spec"); Implementation steps preamble ("run once, at step 1 and step 5 … never rerun them in a loop") against steps 2 to 6 ("Verify: AC2 passes", step 4: "`./zn check c0191` runs it"); the decision line ("and then it gets removed")
Evidence: `ac.sh` has no per-AC filter, so every verify step that runs `./zn check c0191` runs both proofs whenever their specs are green. That covers steps 1 to 6, every stream review (zz-review stream mode runs `./zn check <issue>`), every code-review round (code mode item 1), the raft's own check.sh at `done`, and after `done` any rerun. zz-test's "Must run after promotion" requires check.sh to stay runnable, and `A` falls back to `tests/acceptance/c0191`, where the proofs are promoted. So the proof isn't "removed" after it has proved the implementation. It stays one `./zn check c0191` away from anyone, the user included.
Critique: the user's sentence asks for a proof that is used and then removed. The design keeps it as a permanent, re-runnable part of the item's check, and its own text says "once" in four places. The cost is small (about 8 s CPU and 30 s wall per run), but the documents contradict what the files do, and an executor that follows the steps literally will run the proofs about ten times.
Consequences: making the proofs pre-`done` only means check.sh's AC1 and AC5 are weaker after `done` (the spec halves still run), which is the user's stated intent. Deleting the promoted files would also remove the reproducible evidence of a real kill, and that is the user's call.
Recommendation: run each proof only while the sequestered folder exists, e.g. `[[ $A == "$HERE/acceptance" ]] && <proof>`, so after `done` the promoted files are inert and nothing runs them. Say in the AC labels that the proofs run before `done` only. Change steps 2 to 6 to verify through their spec commands (`lune run tests/run -- <spec>`), with one `./zn check c0191` at step 5 and one at the end. Reword "once" to "only before `done`, by `./zn check c0191`". Escalate to the user only whether the inert files must also be deleted after `done` (a chore or `done` support) or may stay as evidence.

### F4 [medium] The unjailed proof is bounded only by the code it tests, and two of its spinners have no bound of their own
Where: check.sh AC1 (`'$ZN_ROOT/zn' run --time 120 -- lune run proof-bounded.luau`); `proof-bounded.luau` "lune spinner" (`while true do end`) and "real CPU limit" (`perl -e '1 while 1'`, twice)
Evidence: the outer bound is `./zn run`, which is the `bounded.pl` under test. The inner bound of each spinner is also that runner (`--cpu 1`, `--time 1`, or the lower caller's `ulimit -t 1` in a `sh -c`, which does bound the second burn). A runner whose `ulimit` and wall stop are both broken (the kind of failure the proof exists to catch) leaves `perl -e '1 while 1'` and the Lune spinner running unjailed. The outer `./zn run` is broken the same way, and the proof runs outside the jail's 1200 s and its sweeper. The other spinners bound themselves (`alarm 20`, `os.clock() < 20`, `< 15`, `(times)[0] < 0.5`).
Critique: that would be a leaked spinner on the user's machine, from the issue whose whole point is no leaked processes, and it would happen exactly when the implementation is wrong.
Consequences: a self-bound must not change the status the case asserts. The CPU limit has to fire well before the self-bound, and the wall-clock case has to end on the wall limit, not on its own clock.
Recommendation: give every spinner its own CPU bound, as the engine and hook spinners already have: `perl -e '1 while (times)[0] < 20'` and `local t = os.clock() while os.clock() - t < 20 do end`. Also put an independent kernel cap in check.sh in front of both proofs: `bash -c "… && ulimit -t 60 && '$ZN_ROOT/zn' run --time 120 -- lune run …"`. `ulimit` is a shell builtin, not the code under test. `bounded.pl` only lowers, so 60 stays and the inner `--cpu 1` still lowers below it. Add the same sentence to the proofs' headers ("bounded independently of the runner under test").

### F5 [low] proof-limits' "no process of it is left" can't fail
Where: `acceptance/proof-limits.luau` `hookHang`, `pgrep -f '{dir}/z-nile/guard-bash'`
Evidence: `pre-bash.sh` `cd`s into its checkout and runs `lune run z-nile/guard-bash` with a relative path. A live entry under the copied hook doesn't match the absolute pattern (probe above), so the check is true whether or not anything is left. The same check was in the old hooks.spec. A relative pattern would instead match every real hook call in a live session, which would make the check flaky.
Recommendation: have the spinning entry first write its Lune pid (`process.exec("sh", {"-c", "echo $PPID"})` to a file in the fixture), then assert `kill -0 <pid>` fails after the hook returns. Have it also print a "started" line and assert it, so a hook that never started the entry (`lune` not found: 127, neither 0 nor 2) can't pass. Do the same for `engineSpin`, which passes vacuously if the stub engine never starts.

### F6 [low] Unlisted mutant: status 152 called a CPU stop whatever the meter says

Evidence: mutant B passes 14/14. The half-allowance control only uses status 1. With a per-process limit, a real SIGXCPU stop means the meter read at least the limit, so 152 at half the allowance is the command's own status by the Design's rule.
Recommendation: run the half-allowance control for both 1 and 152, like the case above it, and add mutant B to the row.

### F7 [low] Proof identity checks and figures disagree with their text
Where: `proof-bounded.luau` header ("`sleep`, `perl` or `lune`") against `cleanup()` (only `sleep` or `perl`, matched as substrings of any command line); `runnersGone()` (`pgrep -f "perl {BOUNDED} --time 60 -- sh -c"`); CPU figures: Test plan "3 s" for proof-bounded (E17 measured 4 s), Affected specs "about seven seconds in all", check.sh "about four seconds" for proof-limits alone
Evidence: `cleanup` would `KILL` a reused pid that now runs any `perl` (for example another session's `./zn run`). The window is milliseconds, so the risk is small, but the identity is weaker than the header claims. `runnersGone` matches any concurrent `./zn run --time 60 -- sh -c …` from the same checkout, which the new hook will make common, and that gives a false FAIL.
Recommendation: tag each command with its unique `sleep` duration (already distinct: 61.1, 62.2, …) or a per-run marker, and have `cleanup` and `runnersGone` match that marker. Make the header match the code. Give one CPU figure (about 8 s in all: about 4 s for each proof) everywhere. Run the final worktree versions of both proofs once on the prototype before landing, since E17 ran the older copies.
