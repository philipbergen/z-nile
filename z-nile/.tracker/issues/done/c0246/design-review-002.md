### F2 [low] Rojo has another spelling of the project file, `*.project.jsonc`, which neither the home rule nor the lister reads, so the Non-goals claim is too strong
Where: Non-goals bullet 2 ("so an unreadable `$path` never reaches `main` in a home"); `home.luau:164` and `graph.luau:348` (`%.project%.json$`).
Evidence: probed through `./zn run`. Rojo 7.7.1 builds `jc.project.jsonc` with `"$path": "../out"` and maps the folder outside (`return 1` is in the output). `rojo build q` on a folder that holds only `default.project.jsonc` builds it too. When both files exist, `.json` wins (`return 9`). `u.Project.JSON`, `v.project.json5` and `w.json` are refused. The home rule's pattern `%.project%.json$` doesn't match `.jsonc`, so a `snake/extra.project.jsonc` that maps `../pickman/src/shared` is never judged, and `graph.placeInputs` never selects on it either. Today's impact is small. The gate builds only `*.project.json` (`z-nile/check.sh:91`), and a home must hold a `default.project.json`, which wins. So only a hand build of the `.jsonc` file follows it.
Critique: the capture's own check asks "does the format allow another spelling of this key". The file has one too, and the design states an absolute it doesn't deliver. The user narrowed this issue to the type or shape of `$path`, so folding the file spelling in silently would widen the scope.
Consequences: refusing `*.project.jsonc` in a home would be a new home-rule line, with its own case and a README clause. Capturing it as a new issue costs nothing now.
Recommendation: escalate to the user, with two options: (a) add one home-rule line to c0246 ("`<file>`: a home holds no `*.project.jsonc`; the gate builds only `*.project.json`"), with a case in `paths.spec` and a README clause; or (b) capture it as a new chore (`./zn new issue c home-rule-refuses-jsonc-projects --project z-nile`). Either way, reword Non-goals bullet 2 to "never reaches `main` in a home's `*.project.json`".
