### F1 [high] Asked a second time, the plain command approves and publishes main's older design while the prep's redesign waits for its pull request
Where: c0369.md Design section 1, the `./zn approve <id>` order ("a waiting worktree ... else a worktree held for main, or held, own and unpushed ... else origin/main when its copy is ready and its approval does not hold ... else, when a pushed, held worktree exists, `<id> is approved in <name>`"); prototype `approveplace.choose`.
Evidence: main holds `design: ready` with no matching approval (every item "prepared before approval", for example c0267 and f0339 today, which have no `approval.md`), and its prep worktree holds a redesign. First run from the main checkout: the prep is waiting, so it records there and pushes `prep-<slug>` (correct). Second run, the same command: the prep is now held, own and *pushed*, which goes in the `pushed` list, so `choose` falls through to `main and main.ready and main.state ~= "holds"` and returns `{ kind = "main", record = true }`. Probe on the prototype's `choose` with `main = {ready, state="none", hash="old"}` and the prep `{ready, state="holds", hash="new"}, pushed = true` printed `main origin/main true`. So the second run makes `.worktree/.approve-<id>`, records an approval of the old design nobody is looking at, and publishes it to origin/main, where `ready` now accepts the old design. The prep PR then carries an `approval.md` that main created separately (an add/add or two-append conflict at its merge: z-design lesson one-file-two-write-channels). The spec's "asked again" case (`approve.spec` "from the main checkout records an unmerged design in its prep worktree ...") has main holding a *draft*, so it never meets this; place.spec's "retries an unpushed approval ..." asserts `pushed` only with a draft main. This is the exact state the re-preps of Q2 create for c0267 and f0339.
Critique: Repeating a command to see where things stand is what people do; the design itself promises "asked again it says where the approval waits" (AC3). The tempting fix is to move the `pushed` check above the main branch in `choose`.
Consequences: then a person who really wants main's older design approved (to ready it before the redesign merges) can no longer do it from anywhere while the prep is open; and the first run already silently prefers the prep over main's unapproved design, which is the capture's "more than one place could be meant" case that the Scope decision of 2026-11-15 assumed had no case left (it counted worktrees, not worktree plus main).
Recommendation: when a read worktree holds a design of its own (waiting, held or pushed), the plain command never records on origin/main: a pushed one prints `<id> is approved in <name>: it counts when its pull request merges` and adds that origin/main holds an older design, unapproved, which the pull request replaces. Add the rule to the Rules and mutants table ("a worktree's own design, approved or not, keeps main's older design from being approved"), a place.spec case (main ready and unapproved, prep held own and pushed, both modes -> `pushed`), an approve.spec case in the branch fixture (main holds a ready, unapproved older design; approve twice from the main checkout; the second run commits nothing on origin/main and makes no `.approve-<id>`), and the mutant "the pushed check comes after main's". Whether a person must be able to approve main's older design while a prep is open is a question for the user (escalate to the user: keep the old design approvable only from inside the scratch/main path with a refusal naming both, or not at all until the prep merges).

### F2 [high] Re-approval during a raft (what `finish`, `done` and zz-execute ask for) is not designed: inside the layer worktree the command pushes the layer branch, and from anywhere else it says the design is already approved
Where: c0369.md Design sections 1 and 3, Checklist "Existing work" and "Restated rules"; `z-nile/skills/zz-execute/SKILL.md:85` ("The human runs `./zn approve <id>` again when the contract changed, then `./zn done`"); `cmd.finish` and `cmd.done` on main (`approval.refusal(".", issue, onMain)` reads the raft checkout's own `approval.md`).

### F5 [medium] The command pushes any branch it records on, creating remote branches for prototypes, and says the approval counts "when its pull request merges" where there is none
