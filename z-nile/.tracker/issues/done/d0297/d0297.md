# d0297: Affected selects sequestered specs

## Problem
lune run z-nile/affected selects a prep branch's own sequestered acceptance specs (<root>/issues/<id>/acceptance/*.spec.luau): 'lune run z-nile/affected -- z-nile/.tracker/issues/c0261/acceptance/docs.spec.luau' prints that file (2026-11-12). So z-nile/check.sh --affected on every prep branch that adds or edits acceptance specs runs them, and they fail by design because the code they pin is not in the prep tree: c0261's prep (#308) 72 failures in its 16 spec files, c0263's prep 84, c0265's prep likewise, nothing else failing. zz-rules Merging now gates a tooling-only PR with --affected on its branch and forbids merging on a red gate, so no prep PR with acceptance specs can merge; zz-test says the gate never runs sequestered specs. What should happen: the gate never runs a sequestered spec (an issue's acceptance/ under a project root), --affected on a prep branch is green when only those changed, and a spec case pins it.

Ruled (user, 2026-11-24): "those defects seem like something was done wrong, or not yet implemented more than the functionality was actually broken, they don't count"

## Non-goals
- Changing what a sequestered spec is, where it lives, or how `check.sh`, `./zn check`, `./zn promote-check` and `./zn done` run it: they name the spec by path and never go through the selector.
- The static stages (`--static`, format, lint, types): a change under a project root already names its project for them, and they already skip `.tracker/**` acceptance specs (`z-nile/check.sh` line 231). Untouched.
- Removing the agents' interim merge rule (memory `prep-gate-sequestered-failures`, "until d0297 lands"): that rule is not in the repository; it lapses by its own words once this issue is in `done/`.
- c0180's stale prep (`preparing` since 2026-11-01, designed against the old graph selector): it is not redesigned here (see Siblings).

## Solution
<!-- The approach in one paragraph. -->
(Added in prep) One pure rule in `sel.affected`: a spec under a project root is never selected, whichever way it reached the selection (the change adds or edits it, or the branch's `current` list names it). The one way in is a new `own` list on the context, which `z-nile/affected.luau` fills only under a new `--own-acceptance` flag, and which only `./zn finish` passes, so that finish keeps recording its own ticket's acceptance specs in the layer's `results.txt` (the trace's test cells cite them). The gate never passes the flag, so the gate never runs a sequestered spec.

## Design

### Reproduction
On `main` today (2026-11-15, this prep's base `de33c578`): `lune run z-nile/affected -- z-nile/.tracker/issues/c0075/acceptance/jail-argv.spec.luau` prints `z-nile/.tracker/issues/c0075/acceptance/jail-argv.spec.luau`, and with `--project z-nile` prints `.tracker/issues/c0075/acceptance/jail-argv.spec.luau`, which `z-nile/check.sh --affected` then runs (`check.sh` lines 297 to 306). The spec cases that fail on `main` for that reason: `acceptance/select.spec.luau` (all four cases: `sel.affected` returns the sequestered paths, `sel.scope` answers `z-nile` instead of `ALL`) and `acceptance/cli.spec.luau` (the prep-branch case prints the branch's sequestered specs; the layer-branch case prints the ticket's own without the flag; the wiring case finds no `--own-acceptance` in `cmd.finish`). Recorded in Unknowns & experiments, E1.

### Expected behaviour
zz-test, "Where acceptance specs live": "They're formatted and linted, but not type-checked or run by the repo gate. Only `check.sh` runs them, by explicit path." z-design step 4: "They fail, because the code doesn't exist yet. Main stays green because the gate doesn't run them." zz-rules, Merging step 2: a tooling-only pull request "is gated by `z-nile/check.sh --affected` on the branch", and a red gate does not merge. This reworks the watch-map selector (#293, "Select specs from a committed watch map", 2026-11-10), whose rule "the specs the change adds or edits" (`watch.select`) was written for specs under `tests/`, and the raft-branch rule that selects a raft's members' acceptance folders (kept from before #296).

### Root cause
`z-nile/lib/watch.luau`, `watch.select`: `for _, p in changed do if string.sub(p, -10) == ".spec.luau" then add(p)`: every changed `*.spec.luau` is selected, wherever it lies. A prep branch adds `<root>/issues/<id>/acceptance/*.spec.luau`, so every one of them is selected. A second way in: `z-nile/affected.luau`, `currentSpecs`, adds `{m.dir}/acceptance` (the ticket's sequestered folder) on a layer branch and every member's on an old raft branch, and `sel.affected` passes that `current` list through unfiltered. `sel.forces` already says "a path under a project root holds tracker documents, which select nothing", but only the static-stage forcing reads it; spec selection never did. No spec caught it: `tests/tooling/watch.spec.luau`'s "the spec a change edits" case and `c0165/select` use `tests/` paths only, and no case changes a path under a project root and expects nothing.

### The fix (pure rule, one adapter flag, one call site)
- `z-nile/lib/select.luau` (pure):
  - `export type Context` gains `own: { string }?`, "sequestered specs the caller names (./zn finish's own ticket, --own-acceptance); no other is kept".
  - `sel.affected(ctx: Context, changed: { string }, only: string?): { string } | "ALL"` (signature unchanged): the specs `watch.select(bindings, changed, ctx.current)` returns are kept only when `projects.rootOf(spec, ctx.rules.roots) == nil`; then every spec in `ctx.own` (typed `local own: { string } = ctx.own or {}`, so the loop type-checks) is added once; then the existing `only` filter and home-relative form apply to all of them. `ctx.rules.roots` is every registered project's root (`pickman/.tracker`, `z-nile/.tracker`, …), so "under a project root" covers an item's `acceptance/` and `proofs/` in `issues/` and `issues/active/`, and any spec in a raft's folder. A spec under `<home>/tests/` (promoted `tests/acceptance/<id>/` included) is unchanged.
  - `sel.scope` passes the gate's view to `sel.affected`: a copy of the context with `own = nil` (`local plain = table.clone(ctx); plain.own = nil`), so a change of only sequestered specs and tracker documents scopes to `ALL` (an empty selection), never a project, whatever context its caller built (design review 001 F6): c0239's rule "a gate scoped to a project is never narrower than the unscoped one" keeps holding.
  - `Context.current`'s comment becomes "the current layer's (or old raft branch's) acceptance specs, when the change includes a source file; sel.affected drops the sequestered ones among them unless `own` names them".
  - `watch.select` itself is unchanged (it has no roots; the rule lives where the roots are).
- `z-nile/affected.luau` (adapter): a new flag `--own-acceptance`, with its own line in the usage block, in the form every usage line has (`--   ... --own-acceptance` padded to the description column, then `-- also the layer's own sequestered acceptance specs (./zn finish` and a continuation line `-- only: it records them in results.txt; the gate never passes it)`; AC4 checks the form, not the wording); after `ctx.current = currentSpecs(files)`, `if ownAcceptance then ctx.own = ctx.current end`. `currentSpecs` is unchanged: on a layer branch it still returns the ticket's promoted and sequestered specs under the same watch rule (every member's on an old raft branch), and on a prep branch it returns nothing (no layer, no raft), so the flag adds nothing there. The header's layer-branch paragraph becomes (design review 001 F6): "On a layer branch (R0010/1/c0010), a change that includes a source file selects that ticket's promoted acceptance specs (tests/acceptance/<id>/) when the ticket has no watch file yet, and only when one of its watch files names the path once the watches exist. On an old raft branch (R####-…), a source change selects that raft's members' promoted ones. A sequestered spec (under a project root: an item's acceptance/ or proofs/) is printed only with --own-acceptance, and then only the current layer's ticket's (every member's on an old raft branch) (d0297): the gate never runs one."
- `z-nile/engine/main.luau`, `cmd.finish`: the selector call becomes `local argv = { "run", "z-nile/affected", "--", "--project", project.name, "--own-acceptance" }`. Nothing else in finish changes. Its `results.txt` therefore lists the same specs as today: the trace (`trace.luau`, `isSpecForIssue`) accepts a test cell citing `<issue-dir>/acceptance/<spec>` only when `results.txt` lists it, and R0103's `trace.md` cites `z-nile/.tracker/issues/active/c0330/acceptance/stub.spec.luau:48 (… recorded green in results.txt)`. Dropping the layer-branch route without the flag would have broken that (E3). AC2's wiring case pins the rule, not the file (design review 001 F3, so c0180's planned split of `main.luau` into one module per command keeps it green): (a) no file a gate, hook or forwarder runs from uses the flag in code; (b) in `z-nile/engine/`, every use lies inside the argv of a `"z-nile/affected"` call (from that string to the `sh.run(`, `sh.stream(` or `process.exec(` that follows) in a file that also writes `results.txt`; (c) there is at least one use. V6 (finish moved into its own engine module) stays green; M15 and M16 (the flag in the dispatcher, bare or in a selector argv) are killed.
- `z-nile/skills/zz-test/SKILL.md`: in the watch-map paragraph, "and, on a layer branch, that ticket's acceptance specs when the change includes a source file its watch names." becomes "and, on a layer branch, that ticket's promoted acceptance specs (`tests/acceptance/<id>/`) when the change includes a source file its watch names." and gains, after it, "It never selects a sequestered spec (a spec under a project root: an item's `acceptance/` or `proofs/`), so a prep branch's own specs never run in the gate (d0297). `./zn finish` alone passes `--own-acceptance`, which adds its layer's own ticket's sequestered specs, so that it records them in the layer's `results.txt`."; "Only `check.sh` runs them, by explicit path." becomes "Only `check.sh` runs them, by explicit path, and `./zn finish`, which records its own ticket's in `results.txt`." (`experiments/prototype.patch` holds both; every docs spec that reads zz-test passed on it, E4.)
- `z-nile/tests/tooling/own-acceptance-callers.spec.luau` and its `own-acceptance-callers.watch.txt` (new, executor-written; the text is in `experiments/prototype.patch`; design review 001 F4): one case, "the files a gate, hook or forwarder runs from never use the flag", the same scan as AC2's part (a) (`git ls-files` of `zn`, `scripts`, `:(glob)z-nile/*.sh`, `:(glob)z-nile/*.luau`, `z-nile/bin`, `z-nile/lib`, `z-nile/scripts`, `.claude`, minus `**/.tracker/**`; `z-nile/affected.luau` aside; a comment is not a use). Its watch file names, sorted, the files that run the selector or hold the hooks: `scripts/affected.luau`, `scripts/hooks/post-edit.sh`, `scripts/hooks/pre-bash.sh`, `scripts/hooks/session-end.sh`, `z-nile/check.sh`, `z-nile/specs.luau`, `zn`. Why: the promoted `d0297/cli.spec` is selected through `tests/acceptance/d0297/watch.txt`, which `./zn finish` writes from the layer's own sources (`affected.luau`, `main.luau`, `select.luau`), so a later change to `z-nile/check.sh` alone would not select it; this spec is selected by exactly those changes (E5 shows `lune run z-nile/affected -- <each>` lists it).

Server authority, Roblox: none (tooling only). The pure/adapter split is the one zz-arch asks for: the rule is in the pure `select.luau` over its inputs (the roots come in `ctx.rules`), the flag is read at the edge (`affected.luau`), and the one caller that needs the exception names it.

### Existing work on the day it lands
- Prep branches (open prep PRs, the dispatcher's prep gates): their `--affected` no longer runs their own or any other item's sequestered specs, so a prep that changed only its folder is green; nothing to migrate.
- Active rafts mid-execution: a layer's `./zn finish` passes the flag, so its `results.txt` is what it was, and a `trace.md` already written keeps passing `./zn trace --check`. A raft's `check.sh` RC0 (`z-nile/check.sh --project <p> --affected`) on a layer branch no longer runs the current ticket's sequestered specs, and loses nothing: the same raft `check.sh` runs every member's `check.sh` next, which runs them by path, and `./zn finish` runs the ticket's `check.sh` (`runCheck`) before its spec run, `./zn done` the raft's.
- Done items: their specs are promoted under `tests/acceptance/<id>/`, which the rule leaves alone.
- No stored data or configuration changes shape.

### Scalability
One `projects.rootOf` per selected spec (a prefix compare per root, five roots today): linear in the selection, no new I/O. The flag adds no file reads (`currentSpecs` already ran).

### Maintainability
The rule is one place (`sel.affected`), so every present and future caller of the selector, the CLI, `sel.scope` and anything that builds a `Context`, gets it; `own` is an explicit, named exception that a reader of the context type sees, and a gate, a hook or a forwarder that starts passing the flag turns `tests/tooling/own-acceptance-callers.spec.luau` red in the `--affected` run of the change that does it (its watch file names those files), as well as the promoted `d0297/cli.spec` in a full run. The `--own-acceptance` name says what it adds and the usage line says who may pass it.

### Usability
A prep author's `z-nile/check.sh --affected` is green when only the prep's own documents and specs changed, so a prep PR with acceptance specs can merge under zz-rules Merging (the captured outcome). A layer's `./zn finish` output and `results.txt` are unchanged. `lune run z-nile/affected -- <a sequestered spec>` printing nothing is the documented behaviour (zz-test), not a silent miss: `./zn check <id>` is how those specs run.
