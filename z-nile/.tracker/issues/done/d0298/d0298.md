## Solution
- An id rewrite (`renumber`, `compact`, `remap`, and `remap`'s scratch merge base) re-records every approval whose last row held before it, judged from the files git tracks: the same row (when and who kept, the new hash and parts), no new row; an approval that did not hold is left as it was. So `ready`, `done` and `land` take a raft after a compaction exactly as they take it when nothing was rewritten.
- `ready` judges a raft's `grouped:` record (and its coherence review's quote) before its members' approvals, from origin/main, so a member redesigned since grouping is named with both record hashes, what z-raft must redo; the carried move's validator still judges the record again on the tree it publishes. `work next` names such a raft the same way (design review 002 F3).
- The spec runner removes a dispatched step's environment before any spec starts: it unsets `fence.STEP_VARS` (the step's run state, the publish broker, the real git and gh, the agent's git token) and drops every `z-nile/bin` entry from PATH (`fence.stepPath`). The gh tokens and gh's configuration were already `fence.sh`'s.
- c0302 makes the clone-fixture specs pass when the checkout is on a stack layer branch, which is where d0298's own raft runs its `check.sh` and `done` (E14).
- c0304 narrows `c0045/workstreams`' two stale cases, and c0266 rewrites `c0114/classified`'s case (and with it `c0116/retired`) to the user's ruling, all three types allowed in z-nile's root; all three are done before d0298 is readied (`depends_on`: c0266, c0302 and c0304, in any order among themselves).
- Every promoted spec passes on main again: z-nile's slow tier and the full gate are green, and the specs that failed only inside a dispatched step pass there too.

Q1 (2026-11-12) is ruled (the Problem's `Scope decision` lines): d0298 stays a defect, and the classified spec is rewritten so that `c`, `f` and `d` are all allowed in z-nile's root. The Problem has each fix land "in the raft that owns the behavior (or the spec's own chore)", and the spec's own chore is c0266, which now quotes the ruling (b667696d). ### 1. Approvals survive id rewrites (`z-nile/engine/approval.luau`, `z-nile/engine/main.luau`)
New in `approval.luau`, pure:
- `approval.partsOf(id: string, files: { [string]: string }, promoted: { [string]: string }?): (contract.Parts?, string?)`: the contract parts from an issue folder's view (`files`: path relative to the folder -> text): `<id>.md`, `check.sh`, `guesses.md` when the folder has one (parsed and passed as `contract.build`'s fourth argument, as `approve` and `ready` hash it since f0399; a file that does not parse is the error `guesses.md: <problem>`), and every `acceptance/**.spec.luau` under its name relative to `acceptance/`; when `files` holds no spec, the `*.spec.luau` files of `promoted` (path relative to the promoted folder) instead. That is `approval.collect`'s rule, and `collect` is rewritten to build the same view from disk (the document, `check.sh`, every `*.spec.luau` under `acceptance/` at any depth, and, only when there is none, every one under the promoted folder at any depth) and call it; it returns the same paths as before, in the same order.
- `approval.standing(text: string, parts: contract.Parts): string`: `"holds"` when `approval.md`'s text parses, has a row, and its last row's hash is `contract.hash(parts)`; `"guesses"` when the last row differs from `parts` only in the `guesses` part (a guess recorded after the approval, which a `ready` outside the dispatcher accepts since f0399); `"stale"` otherwise, a text that does not parse included. It is the one reader of that rule: `readycheck.reason`'s approval branch calls it in place of its inline comparison, and `keepRecords` calls it (design review 002 F1).
- `approval.reseal(text: string, parts: contract.Parts, standing: string): (string?, string?)`: the text with its last row re-recorded, `when` and `who` kept, every earlier row as it was; nil and the parse error when it does not parse. For `"holds"` the row takes `parts`' `contract.hash` and `contract.partHashes`. For `"guesses"` it takes the new hash of every part except `guesses`, and keeps the row's recorded `guesses` part hash and its old `hash` value: the approved guesses text is gone, so no hash of it can be recomputed, and the old value equals no current contract, so `contract.changed` skips its whole-hash shortcut, compares part by part and answers `{"guesses"}`, exactly as before the rewrite. The guess added since stays unapproved: `ready` outside the dispatcher accepts the issue as before, and `done`, `land` and a dispatched `ready` refuse it as before.

In `keepRecords(root, idMap, rewrite)`, before `rewrite()`: for every issue id in `before` (audit's scan), the view is `gitFolderFiles(dir, true)` (the index: what the rewrite commits) and the promoted view `gitFolderFiles(<root>/<projects.promotedDir(reg, itemRoot, id)>, true)`, where `itemRoot` is `projects.rootOf(<the folder, relative to root>, projects.roots(reg))` (`audit.scan`'s entries carry no root), so `projects.promotedDir` stays the one reader of where specs are promoted. The issue is kept, with its standing, when the view holds `approval.md` and `approval.standing(it, partsOf(...))` is not `"stale"`. After `rewrite()`: each kept issue's new id (`idMap[id] or id`), its folder in the new scan, the same two views, and `approval.md` is written with `approval.reseal` and the standing it had before. A rewrite that commits (`compact`, `remap`) commits after `keepRecords` returns, so the carried rows ride in its own commit; `renumber` leaves them in the working tree with its other edits. An approval that did not hold is never touched. Every state is one path: the scan gives backlog, `active/` and `done/` folders alike, and a done issue's specs are read from its promoted folder (the case seeds a backlog and a done issue; an active one differs only in its folder, which the scan supplies).

Why in place and not a new row: `contract.reapprovals` (rows minus one) counts re-approvals in `./zn metrics`; a mechanical rewrite is not a human re-approval, and the row's `who` stays the human who approved. Why the index: a work file in an approved folder (untracked) is not part of what the rewrite commits, so it must not decide whether the approval held (the same reason `keepRecords` hashes grouped records from the index, c0116 review 005 F1).

### 2. `ready` judges the record first (`z-nile/engine/main.luau`, `cmd.ready`)
The validator closure passed to `moveOnOrigin` becomes `local function recordRefusal(paths: { string }, read: (string) -> string?): string?` with the same body (on main since c0369 that body builds the members from `treeFolderFiles` and calls `readycheck.record`). `ready` calls it once, only for a backlog raft whose status is `prepared` (any other raft gets the refusal it gets today, "only a prepared raft is readied" first; design review 002 F2), on origin/main (`git ls-tree -r --name-only origin/main` and `git show origin/main:<path>`: the tree it has just fast-forwarded to), before `readyfacts.reason`, which is where the approval check now lives (`readycheck.reason`, shared with `work next`); it fails with the record's refusal, and otherwise `reason` runs as today. `moveOnOrigin` still gets `recordRefusal` as its validator, so a redesign landing between the pull and the move is caught on the published tree. Messages are unchanged. The record check is not moved into `readycheck.reason`: that module's header keeps the record out of `reason` so an ignored file on disk never changes a hash. Consequence (guess G1): for a raft whose record is broken, the record's message now comes before every other refusal of `ready`, the cheap ones included (an open `questions.md`, an unmet dependency, a design not ready). `work next` gets the same order (guess G2, corrected by design review 002 F3): in `workread.blockFor`, after the not-prepared branch, `readycheck.record(id, front.grouped, members, raftFiles)` runs before `readycheck.reason`, so a redesigned member is named by its record and `work.fixable` treats the raft as any record refusal. The comment in `cmd.ready` and the header of `readycheck.luau` are corrected to say where each command judges the record.

### 3. Spec runs drop a dispatched step's environment (`z-nile/tests/lib/fence.luau`, zz-test)
- `fence.STEP_VARS: { string }` = `ZN_DISPATCH`, `ZN_HEADLESS`, `ZN_DISPATCH_DIR`, `ZN_DISPATCH_HOME`, `ZN_REAL_GIT`, `ZN_REAL_GH`, `ZN_PUBLISH_BROKER`, `ZN_PUBLISH_TOKEN`, `ZN_DISPATCHER_PID`, `ZN_AGENT_GH_TOKEN`, `BASH_MAX_TIMEOUT_MS`: every variable `dispatcher.luau`'s step environment, `credential.agentEnv` and `adapters.STEP_ENV` (merged into the step environment for a runtime; design review 002 F4) set, except those `fence.sh` already handles (`GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK` unset; `GH_CONFIG_DIR`, `GIT_TERMINAL_PROMPT` and the `GIT_CONFIG_*` entries replaced), `GH_PROMPT_DISABLED` (it only turns prompts off) and PATH. It never names `ZN_TOP`, `ZN_CWD` or a `ZN_MEASURE*` variable, which the runner and a fixture's `./zn` read.
- `fence.STEP_HANDLED: { string }` = `PATH`, `GH_PROMPT_DISABLED`, `GH_TOKEN`, `GITHUB_TOKEN`, `GH_CONFIG_DIR`, `GIT_TERMINAL_PROMPT`, `SSH_AUTH_SOCK`, `GIT_CONFIG_*` (a trailing `*` is a prefix): the rest of a step's environment, each handled elsewhere (above). The two lists never share a name.
- One comment at the dispatcher's step environment table (`dispatcher.luau`, above `local env: { [string]: string } = {`), one above `credential.agentEnv` and one above `adapters.STEP_ENV`, each with the sentence "A variable added here goes on fence.STEP_VARS (unset for every spec run) or fence.STEP_HANDLED (d0298)." on one line. They put the three files in the layer's diff, so `./zn finish` writes them into d0298's promoted `watch.txt`, and a later change to any of them selects `stepenv.spec` under `--affected`.
- `fence.stepPath(path: string): string`: PATH without every entry that ends in `/z-nile/bin` (with or without a trailing slash), from any checkout (the dispatcher puts the main checkout's first, and a run starts in a worktree), the rest in order.
- `fence.enter`'s bash line starts `unset PICKMAN_REAP_SWEPT PICKMAN_REAP_CACHE <STEP_VARS>; PATH="$7"; ...` and ends `shift 7`, with `fence.stepPath(process.env.PATH or "")` as its seventh argument. That shell is where every spec process starts (inside the jail when there is one), so the specs and every nested runner inherit the result. The runner's own reads before it (the measuring prelude, the guards' `git` calls) still run in the step's environment; that is the wrapper's job and unchanged.
- `tests/tooling/repo-fence.spec.luau` gains one `ALLOWED` entry, keyed by the path `done` promotes the spec to (the stale-key case accepts an unfinished item's promoted path): `["z-nile/tests/acceptance/d0298/stepenv.spec.luau"] = { GH_CONFIG_DIR = "reads a spec run's gh configuration folder to prove it is fence.sh's empty one", ["credential."] = "calls and reads credential.agentEnv to list a dispatched step's variables" }`. Without it the repository-fence scan (`tests/meta/fence.spec`, in every full gate) fails once the spec is promoted: it bans both names in any spec, and stepenv reads the one and calls the other, setting neither. `check.sh` names no banned word (it injects no `GH_CONFIG_DIR`; E14 caught the first draft doing so).
- zz-test, "Specs never touch the real repository", gains one bullet under "Enforced at run time": a dispatched step's environment, what it carries, that the runner unsets `fence.STEP_VARS` and drops `z-nile/bin` from PATH, that the rest is named in `fence.STEP_HANDLED`, and that a variable added to the step's environment goes on one of the two lists.

### Scalability
The carry adds two `git ls-files` per issue to a rewrite (the before and after views; `gitFolderFiles` already runs one per grouped member). On main's ~300 items a compaction gains about 600 short git calls, seconds, once per compaction; `renumber` and `remap` touch the same scan. `ready` gains one `ls-tree` of origin/main and one `git show` per member and raft file it reads, as its validator already does on the published tree. The scrub is a fixed list of 10 names.

### Maintainability
One reader of an issue's contract (`approval.partsOf`, used by `collect` and `keepRecords`); one reader of whether an approval stands (`approval.standing`, used by `readycheck.reason` and `keepRecords`); one record check used by `ready` twice (`recordRefusal`) and by `work next` (`readycheck.record`). Both step-variable lists sit beside the guard that uses them, and `stepenv.spec`'s first case reads the dispatcher's step environment, `credential.agentEnv` and `adapters.STEP_ENV`, so a variable added there on neither list fails a spec; the comments in the three files make `./zn finish` watch them, so `--affected` runs that case for any later change to any of them (lesson zz-test/specs-read-sources-through-the-selector).

### Usability
Nobody runs a new command. A compaction or renumber no longer silently breaks every approval it touches (today the human would have to re-approve every prepared issue after a compaction). `ready` names what z-raft must redo first. An executor's gate and the post-landing net give the same answers inside a dispatched step as outside it.
