# d0413: Loop scan red on main

## Problem
- Main's full gate is red since f0399 landed (da3de3462, 2026-11-17): `z-nile/tests/meta/scanning-loops.spec.luau` and `z-nile/tests/acceptance/c0193/tree.spec.luau` fail on main.
- The loop scan cannot prove that two `while` loops f0399 added will end, and neither is on the reviewed list in `z-nile/tests/lib/loops.luau`: `z-nile/engine/guesses.luau` line 43 (`while #lines > 0 and lines[#lines] == "" do`) and `z-nile/engine/raftplan.luau` line 104 (`while #out < #issues do`).
- The new `raftplan.luau` loop shifts the file-order match of that file's one listed loop (`while parent[k] ~= k do`), so the scan reports that loop too.
- Every raft's `./zn finish` whose watch map selects either spec is refused (R0113's is).
- `depsFirst` in `raftplan.luau` never returns when two issues in its list share an id.

## Non-goals
- The affected gate's selection is not changed, so this issue does not fix why f0399's own done missed the two specs for those files.
- The raft planner does not reject or report a list with a repeated id, and no caller is changed to prevent one.

## Solution
- Both loops are rewritten as bounded `for` loops that the scan proves end, and `z-nile/tests/lib/loops.luau` gains no entry.
- `guesses.parse` returns the same result as today for every input, trailing empty lines still ignored.
- For every list of issues with distinct ids, the raft planner returns the same dependency order as today, including the ring fallback that takes the lowest id left.
- For a list in which an id repeats, the raft planner returns instead of running forever, and its result holds every entry of the list exactly once.
- Both specs pass on main, and `z-nile/check.sh --full` passes its z-nile stage.

## Design
**Reproduction.** On origin/main (fb69a83a9), `lune run tests/run -- tests/meta/scanning-loops.spec.luau tests/acceptance/c0193/tree.spec.luau` fails both files, naming `z-nile/engine/guesses.luau:43` (`while #lines > 0 and lines[#lines] == "" do`), `z-nile/engine/raftplan.luau:104` (`while #out < #issues do`) and, because the listed entries of a file are matched in file order, `raftplan.luau:291` (`while parent[k] ~= k do`, the one listed loop). `z-nile/check.sh --full` on a clean copy of main: z-nile stage `1283 passed, 2 failed, 211 spec files`, exactly these two (E1). The hang: `raftplan.plan({ f0010, f0010, f0011 }, {})` never returns (E3).

**Expected behaviour.** zz-arch rule 9 (lesson `zz-arch/scanning-loops-advance`, c0193, done): "every loop in the tooling provably advances or is on the reviewed list". f0399 (done, raft R0129) added both loops; it is the work this defect reworks.

**Root cause.** Both loops end only by an argument the scan cannot read: the first by `table.remove` shrinking the list, the second by `#out` growing once per pass. The second's argument is also false for a repeated id: `placed` is keyed by id, so two entries with one id are placed together, `#out` stops one short of `#issues`, and no pass can take anything more. No spec caught the red scan before landing because the affected gate did not select the two scan specs: their watch files name `scan.luau` and the test libraries, not the engine files the specs read (Non-goals: not fixed here; the lesson `zz-execute/run-the-loop-scan-after-adding-a-loop`, written in this prep at `z-nile/skills/zz-execute/lessons/run-the-loop-scan-after-adding-a-loop.md`, covers the gap for the executor).

**The change** (`prototype.patch`, 25 lines added and 16 removed in two files):
1. `z-nile/engine/guesses.luau`, `guesses.parse`: `for at = #lines, 1, -1 do if lines[at] ~= "" then break end; lines[at] = nil end`. A numeric `for` has a fixed number of passes; the result is the list without its trailing empty lines, as before.
2. `z-nile/engine/raftplan.luau`, `depsFirst`: `for _ = 1, #issues do`, one entry taken on each pass. An entry is taken by its place in the list (`taken[at]`), and an id counts as met once any entry carrying it is taken (`met[id]`). The pick on each pass is what it was: the first entry not taken whose listed dependencies are all met (a dependency on itself or on an issue outside the list holds nothing back), else, for a ring, the first entry not taken. For distinct ids `taken` and `met` mark the same entries, so the order is the old one; for a repeated id each entry is taken on its own pass, so every entry is in the result once and the loop ends. Where the entries of a repeated id fall in the order is not specified: the capture asks only that the planner returns and holds each entry once, and an issue may come before a second entry of an id it depends on.
3. `z-nile/tests/lib/loops.luau` is not changed: `raftplan.luau` keeps its one entry, which matches again once the unproven loop before it is gone. The promoted spec pins only the rule (the scan finds no problem in the two files); that the list is unchanged is a `check.sh`-only line against the merge base, so a later issue that changes the list does not turn this issue's promoted spec red (design review F1).

**Siblings.** The scan is the sibling check: with the prototype both scan specs pass, so no other loop in the tooling has this mistake. `guesses.luau` and `raftplan.luau` hold no other `while` or `repeat` loop that f0399 added (`git diff da3de3462^1 da3de3462 -- z-nile/engine | grep -n "^+.*while \|^+.*repeat"` lists these two only).

**Pure and adapter split.** Both functions are pure and stay so. No signature, type or dependency edge changes; `architecture.md` is unchanged.

### Scalability
The planner does the same passes as before (one per issue, each a scan of the list): quadratic in the issues of one type and project, a few dozen at most.

### Maintainability
Two loops fewer for the reviewed list to argue about; the comment on `depsFirst` says why a pass always takes an entry.

### Usability
`./zn finish` and the full gate stop failing on the scan for every raft. `./zn raft-plan` prints the same plan.
