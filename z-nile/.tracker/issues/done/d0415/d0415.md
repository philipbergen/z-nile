# d0415: Refold review refused

## Problem
- In raft mode, `./zn dispatch zz-review <raft> --mode raft` refuses to file a review when the raft folder already has a `design-review-NNN.md`, even when no review there quotes the raft's current `grouped:` record, so a refolded raft of several issues can never be prepared through the dispatcher (seen on R0070, 2026-11-17).
- The refusal at `z-nile/engine/dispatcher.luau:1123` is issued after the reviewer has run to the end, so its tokens (206,361 on R0070) are spent for nothing.
- When filing is refused, the dispatcher deletes the reviewer's `review.md` from the item's state folder, so the findings are lost.
- Both R0070 review runs printed "could not record R0070's design-review row (no row): kept as pending" and no pending row was written, so their spend is on no ledger.

Ruled (user, 2026-11-24), shipped: no: "those defects seem like something was done wrong, or not yet implemented more than the functionality was actually broken, they don't count"

## Non-goals
- The one-round rule in design and code modes, where a second review of the same issue is refused, is not changed.
- The z-raft skill's rule on when a refold owes a new review is not changed.
- The spend of the two R0070 review runs of 2026-11-17 is not back-filled onto a ledger.
- The `review-attempt-N.md` files that a failed attempt leaves, and the deletion of a stale `review.md` at the start of a run, are not changed.

## Solution
- In raft mode the dispatcher files the review as the next `design-review-NNN.md` whenever no review in the raft folder quotes the raft's current `grouped:` record.
- In raft mode the dispatcher still refuses a second review of a `grouped:` record that a review in the raft folder already quotes.
- Every refusal to file a review that can be decided from the folder's state is made before any reviewer CLI is started, and that run spends zero tokens.
- A review the dispatcher cannot file after the reviewer ran is moved to a numbered file in the item's state folder (`review-unfiled-N.md`, N one past the highest already there), which no later run of the same item deletes or overwrites, and the failure message prints that file's path.
- A review run whose design-review row cannot be recorded leaves a pending row holding its tokens and minutes that a later `./zn` spend report shows, or the dispatch exits failed saying the spend is unrecorded.

## Design

### Root cause (verified in the code)
Five defects share one function, `dispatcher.modelStep` (`z-nile/engine/dispatcher.luau`), and the way it lands a review:
1. **Who counts rounds.** `lastRound(dir, prefix)` counts every `design-review-NNN.md` in the folder and `modelStep` refuses when the count is 1 or more (`if last >= 1`). It knows nothing of raft mode: a raft's coherence review is filed under the same `design-review-` prefix as an issue's design round, but a raft is allowed one review per `grouped:` record (z-raft skill, section 4). The record is read by `readycheck.reviewCovers` and `main.luau`'s copy of it, never by the dispatcher.
2. **Where the refusal is decided.** The check sits in the "the dispatcher lands a dispatched review" block, after `modelstep.launch` returned. Nothing before the `for _, spec in tries` loop looks at the folder, so a refusal the folder already decides (the one-round rule of every mode, a covered record) is made after 206,361 tokens were spent.
3. **What deletes `review.md`.** The refusal branch calls `pcall(fs.removeFile, landing)`, and the start of every run clears a stale `{stateDir}/review.md` (line "a stale one from an earlier run is never this run's review"). The state folder is one per item (`{dispatcher.home}/{id}`), so the next dispatch of the same raft deletes whatever a refusal left there.
4. **Why the row is "no row".** `record` calls `publishMeasured`, which appends the buffer line and calls `costrow.plan`. `costrow.plan` (and `buffer.fold`) writes a file only for an id that does not start with `R` (`string.sub(id, 1, 1) ~= "R"`): a raft has no ledger, and `./zn spend <R-id>` shares the row among the raft's members (`spend.attribute`). The dispatcher passed the raft's own id, so `paths` was empty and `publishMeasured` returned `false, "", "no row"`. The row went to `st.pending` (it is in `.cache/dispatch/R0070/state.json`), but `flush` retries it the same way and fails the same way, and nothing prints `st.pending`, so the spend sat on no ledger and in no report. Which worktree the author was in (the rafting worktree) plays no part: the row is written in the `zn-dispatch` worktree. A second loss sits beside it: a review its author started (z-design's and z-raft's reviews under `./zn dispatch`) is a nested run with a state folder of its own, `{ZN_DISPATCH_DIR}/<step>-<mode>-<id>-<n>` (`dispatcher.luau`, `top`), which neither `dispatch status <id>` nor `flush` reads; this machine holds such pending rows for R0094, R0077, R0069, R0072, f0339 and c0359.
5. **Why no spec caught it.** `c0117/dispatch-cli.spec` files one raft review (R0090, no `grouped:`) and one stream second round; no case refolds a raft, no case counts what a refused run spent, and no case dispatches a raft that is on origin/main, so a raft's row was never recorded in any fixture.

### Reproduction
`acceptance/dispatch.spec.luau :: AC1: a refolded raft's review is filed ...`: a raft on origin/main with members c0030 and c0040, a `design-review-001.md` that quotes `[c0030@...]`, and a `grouped:` record `[c0030@..., c0040@...]`. On `main` the reviewer runs to the end and the dispatch fails with "already has design-review-001.md: one round ...". Cases AC2 to AC5 of the same spec fail on `main` for their own reasons (the second run starts the CLI, the review is deleted, the row is not on c0030).

### Expected behaviour
z-raft skill, section 4: "A later fold that changes the grouped record is a new record and needs its own one review", and "the carried move and `ready` refuse a raft of several issues whose reviews quote no record covering the current one". The dispatcher is the one command z-raft names for that review (`./zn dispatch zz-review <R-id> --mode raft`), so it must file it. Rework of: c0117 (the dispatcher, `dispatch-cli.spec`), c0116 (the grouped record and the coherence review).

### The change

**1. One definition of "a review covers the record" (`z-nile/engine/raftplan.luau`).** Two copies exist (`readycheck.reviewCovers`, `main.luau`'s `reviewCovers`). They move here, once:
```
function raftplan.coveringReview(reviews: { [string]: string }, map: { [string]: string }): string?
function raftplan.reviewCovers(reviews: { [string]: string }, map: { [string]: string }): boolean
```
`coveringReview` returns the first (name order) `design-review-NNN.md` whose `Grouped: [...]` line quotes every entry of `map` with the same hash, or nil; an empty `map` is covered by none. `reviewCovers` is `next(map) == nil or coveringReview(...) ~= nil`, the old rule exactly. `readycheck.record` and `main.luau`'s carried-move check call it; the two local copies are deleted (Siblings, below). **Guess (prep) G4**.

**2. Where a review is filed or refused: one pure function (`z-nile/engine/dispatch.luau`).**
```
export type FilingInput = { mode: string?, dir: string, prefix: string, raftId: string,
	reviews: { [string]: string }, grouped: string? }
export type Filing = { number: number?, refusal: string? }
function dispatch.filing(p: FilingInput): Filing
```
`reviews` is name -> text of the folder's files that start with `prefix`. Rules:
- Every mode but raft: the highest `<prefix>NNN.md` is `last`; `last >= 1` is the refusal `"<dir> already has <prefix>NNN.md: one round, then the author answers it; there is no second round"` (the words today's specs pin); otherwise `number = 1`. Unchanged for design, code, final and stream.
- Raft mode, `grouped:` malformed (`raftplan.parseGrouped` problem): refusal `"<R-id>: <problem>: fix it before a review runs"`.
- Raft mode, a non-empty record: `coveringReview` finds a review, so refusal `"<dir> already has <name>, which quotes <R-id>'s current grouped: record: one review per record, then the author answers it; there is no second round of it"`; otherwise `number = last + 1` (the next `design-review-NNN.md`, numbered past every file, never the count).
- Raft mode, no record: one round, like every other mode. **Guess (prep) G1**.

**3. The dispatcher asks it twice (`z-nile/engine/dispatcher.luau`, `modelStep`).** A local `filingNow(l: Landing): dispatch.Filing` reads the folder (`reviewsIn(dir, prefix)` replaces `lastRound`: name -> text of files with the prefix, at the edge) and, in raft mode, the raft document's `grouped:` (`store.readFront("<cwd>/<raft.doc>")`), and calls `dispatch.filing`.
- *Before the reviewer:* right after the stale `review.md` is cleared and before `for _, spec in tries`, when `land` is set, `filingNow(land).refusal` is recorded as a failed attempt with 0 tokens and 0 minutes, printed (`dispatch: <refusal>`), and `tries = {}`: no CLI is started and no model process runs (the agent credential is looked up first, as today, and read nowhere), and the run spends zero tokens. This covers every mode, the one-round rule of design, code, final and stream included (outcome 3 is about every refusal the folder decides).
- *After the reviewer:* the same call, because the folder can change during an 11-minute run (a rival review, the author filing by hand). `number` files `design-review-<number>.md` (note `design-review-NNN`, as before); a refusal is the unfiled case, below.

**4. A review that cannot be filed is kept (`dispatcher.luau`).** If the post-run `filingNow` refuses, or the move into the folder fails (`pcall(fs.move, ...)`), the review is moved to `{stateDir}/review-unfiled-<N>.md`, `N = nextUnfiled(stateDir)` (one past the highest `review-unfiled-<N>.md` there, 1 when none). The attempt's detail is `"<why>; the review is kept at <path>"` (or "could not be kept: it stays at <path>" if even that move fails), so the message in `state.json`, on stderr and in `./zn dispatch status` carries the path. Nothing deletes or overwrites it: the start of a run removes only `{stateDir}/review.md`, `review-attempt-N.md` keeps its own name and rule (a failed attempt's review, unchanged), and `nextUnfiled` never reuses a number. The run still fails and its tokens are still recorded.

**5. A raft's row goes to its members (`dispatcher.luau`, `record`, `publishMeasured`).**
```
Row.members: { string }?            -- a raft's row: the raft's members as the step's own worktree held them
function dispatcher.memberRows(row: Row, members: { string }): { Row }
```
`record` reads `issues:` from the raft document in the step's own worktree (`cwd`, the checkout whose `grouped:` the filing read, so a refold the rafting PR has not merged yet counts) and stores the list on the row, in `state.json` with the pending row, so a later `flush` in another process splits it by the same list. `memberRows` turns a row whose id starts with `R` into one row per member, sorted: the lowest id keeps the tokens, wall, CPU and minutes, every other member gets the same phase, note and model with 0 tokens (so `rowLine` flags them `tokens`, as `./zn spend` does). Any other id keeps its row. All members' lines are buffered, one `costrow.plan` places them, and one commit takes every path (`git add`/`commit --only -- <paths>`). Each member must have a folder in the `zn-dispatch` worktree, or the whole row stays pending naming it (`no folder for <id>`; no partial write across members); a raft row with no `members` is refused with `<R-id> lists no members`. **A pending raft row recorded before this change has no `members` and stays pending**: it is never written, so the two R0070 rows of 2026-11-17 are not back-filled (captured Non-goal). A `prep` or `deliver` row of a raft (z-raft's own step, a run's) goes through the same split with the members its own worktree held. **Guess (prep) G2**.

**6. A row that still cannot be recorded is loud and is found where it is kept (`dispatcher.luau`, `dispatch.luau`, `main.luau`).** `record` keeps appending the row to `st.pending` and now also prints `dispatch: UNRECORDED spend: <id> <phase> <tokens> tokens, <minutes> min, <model>, note "<note>"; ./zn dispatch status <id> lists it`. Pending rows live in more than one place: the item's own `{home}/<id>/state.json` and the state folder of each nested run (`{home}/<parent>/<step>-<mode>-<id>-<n>/state.json`). One edge reader, `statesUnder(dir)`, walks `{home}` and returns every state; everything below uses it:
- `flush` (the start of every run of an item) also takes the pending rows whose `id` is the item's from nested folders whose run is not `running`, writes the ones that are writable, and saves the nested file without them, so a row is written once.
- `dispatcher.pendingReport(home, id?, stateOf?): {string}` returns one line per pending row (of `id` only, when given): `unrecorded spend (<fate>): <id> <phase> <tokens> tokens, <min> min, <model>, note "<note>" [<state.json path>]`. `./zn dispatch status <id>` prints these after its JSON.
- `./zn metrics` prints, after its rework lines, a section `Unrecorded dispatcher spend (this machine only, in no total above; ...)` with `pendingReport(<main checkout>/.cache/dispatch)` (no fate: it has no origin reader; `dispatch status <id>` gives it), so the spend report the capture names shows the row. The ledger totals do not change; a row `flush` has written has left `pending` and is never counted twice.
- Pure, in `dispatch.luau`: `dispatch.rowWritable(id, phase, state, hasMembers): boolean` (a `deliver` row waits for `done`, any other row for `backlog`; `nil` is never; a raft row with no stored members is never) is the one rule `flush` uses, and `dispatch.pendingFate(id, phase, state, hasMembers): string` words it: `written by the next run of <id>`, or `never written: <id> is <state> on origin/main, and a <phase> row waits for <backlog|done>`, `never written while origin/main does not list <id>`, or `never written: <id>'s row was recorded before d0415 and names no members`.
The exit code is unchanged. **Guess (prep) G3**. What the rows that exist on the day this lands do: a non-raft row in the backlog is written by the next run of its item (as before, now also from nested folders); a row whose item left the backlog is shown as `never written` with the state (it is exactly what `flush` always did, now said); a raft row without `members` stays pending and says so through the same fate line: the fate line says so, so `written by the next run` is never printed for a row `flush` will not write.

**7. Documents.** `zz-rules` (Running a model step: a refusal the folder decides is made before the CLI starts; an unfiled review is kept as `review-unfiled-N.md`. Spend: a raft's row is shared among its members; an unrecorded row is shown by `dispatch status`), `zz-review` Output file (one second-review rule: raft mode is one review per `grouped:` record), `z-raft` section 4 and `z-design` step 5.2 (the same sentence where each says a second review is refused).

**Pure/adapter split.** `dispatch.filing`, `raftplan.coveringReview`/`reviewCovers` and `dispatcher.memberRows` are pure over texts and tables (zz-arch rule 4); `reviewsIn`, `nextUnfiled`, `filingNow` and `publishMeasured` do the reading and git at the edge. No new module, no new dependency edge (`dispatch.luau` now requires `raftplan.luau`, a pure leaf that requires only `@lune/serde`), so no `architecture.md` change.

### Scalability
One extra directory read of the item's folder before the reviewer (it is read once more after, as today) and one read of the raft document; the member split adds one `costrow.locate` (one `projects.load` and a few `isDir` checks) per member. Rows and commits do not grow with the items: one commit per review run whatever the number of members.

### Maintainability
The rule "does a review cover this record" and the rule "where does this review go" each have one definition, in a pure module with specs, and the three callers (`ready`, the carried move, the dispatcher) cannot disagree. The next review mode adds a branch to `dispatch.filing`; the next kind of kept file is another `<name>-N.md` family in the state folder.

### Usability
Every refusal names the folder, the file that stops it, the raft and the rule, and says what to do ("fix it before a review runs"); a refused run prints it at once and spends nothing. A lost review prints its path. `./zn dispatch status` shows unrecorded spend where a person looks first.
