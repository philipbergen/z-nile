# d0416: Quiet nested review reported failed

## Problem
- Since commit 2c6197382 (d0415, R0136), `tests/acceptance/c0117/control-cli.spec.luau` :: 'an author waiting on a long nested review stays alive by its heartbeat; a quiet one still stalls' fails at line 421 in the slow tier because a nested review that goes quiet during a dispatched design step is recorded with outcome failed, where it is stalled on the parent c93b49aea.
- Scope decision (user, 2026-11-18): "Fix the test": prep found the engine does what d0415 designed (a second review of an item that already holds `design-review-001.md` is refused before any reviewer starts, a nested one included), and the c0117 case is stale: its quiet half re-reviews c0095 after its first half filed review 001. The engine keeps d0415's rule everywhere; the case is corrected so its quiet half reviews an item with no review yet.
- Scope decision (user, 2026-11-18): "Keep d0416 as a defect": the fix is tracked here although the spec, not the code, is what changes; no chore is filed for it, and this issue edits the promoted spec `tests/acceptance/c0117/control-cli.spec.luau` itself.

## Non-goals
- This fix does not make the other red slow-tier cases pass (`c0116/compact-record`, `c0116/claims` and `c0114/trail-move`, which d0298 owns, and `c0045/workstreams` and `c0114/classified`, which go to c0304 and c0266), and it does not make the spec's waits independent of machine load (c0287).

## Solution
- A nested reviewer that goes quiet is stopped at its own limits and its run state says stalled, so that c0117 case passes in the slow tier, every d0415 acceptance spec still passes (a refolded raft's review is kept and not refused), and the change turns no other slow-tier case red.

## Design
The engine is not changed. `dispatcher.modelStep` (`z-nile/engine/dispatcher.luau`) asks `dispatch.filing` before any CLI starts whether the review it is about to run could be filed; for an item that already holds `design-review-001.md` the answer is the refusal "already has design-review-001.md: one round, then the author answers it; there is no second round", and the run ends `failed` with no tokens spent. d0415 added that check before the start (its outcome 3: no tokens for a review that will be refused), for a direct `./zn dispatch zz-review` and for one an author's step starts (`ZN_DISPATCH_DIR` set) alike. The user confirmed that rule on 2026-11-18 (the Problem's scope decision).

The c0117 case is what is stale. Its first half dispatches `z-design c0095` with a slow nested reviewer, which files `design-review-001.md` in c0095's folder in the reused worktree. Its second half dispatches `z-design c0095` again with a reviewer that goes quiet and expects that reviewer's run to end `stalled`. Since d0415 the second nested review is refused before it starts, so nothing can stall and the newest nested state is `failed`.

The change, all in `z-nile/tests/acceptance/c0117/control-cli.spec.luau` (three hunks, +10/-5, `experiments/prototype.patch`):
- the fixture's setup list gains a second issue for the quiet half, `c0098` (`issue("c0098", "quiet-review")`), with the same limits as c0095 (`.models.toml`: `tool_seconds = 8`, `stall_seconds = 8`);
- the quiet half dispatches `z-design c0098`, reads `dirOf("c0098")`, matches `^zz%-review%-design%-c0098%-(%d+)$` and reads that run's state; its expectation is unchanged: `outcome` is `"stalled"`, and it now also asserts that exactly one nested run exists (`n == 1`), so the case cannot read the author's own state when no reviewer ran (design review 001 F7);
- the first half (c0095: the author stays alive by its heartbeat, `review=0`, `bashmax=7200000`) is untouched, and a comment says why the halves use two issues.
