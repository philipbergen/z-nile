### F1 [high] lost.spec's old-claimant case expects the "taken over" notice from a command that runs after the notice was already given: a correct implementation fails line 320
Where: lost.spec:307-327; Design, Automatic beats ("for each, if origin's stamp for the id differs from the entry's … the entry is deleted and nothing is beaten … when it drops an entry for a changed stamp it says once on stderr `<id>'s claim was taken over (now <stamp>): stop working it`"); review-003 F10.
Evidence: at the time the case starts (`at` = LATE+9·STALE), wt's entries are c0010 (old stamp, epoch LATE+6·STALE, moved forward by the failed attempt in the hung-remote case), c0020 and R0020 (the same). wt2 has just taken over c0010 and R0020. The case's first command is `zn(wt, { "sync" }, at)` (line 310). `sync` is not exempt (it is not `beat`, `run`, `reap` or in `READ_ONLY`, main.luau:5989). So its automatic beat runs first, sees origin's new stamp for c0010 and R0020 (the worktrees share `refs/remotes/origin/main`, which wt2's publish moved, and the entries are 2700 s old, so a fetch happens anyway), deletes both entries and prints the notice on **sync's** stderr. That stderr is never read. Next, `status c0010 prepared` (line 312) is refused correctly. Then `lessons --check` at `at + 2·STALE` (line 318) finds no c0010 entry, so it prints nothing. So `has(told.stderr, "taken over")` (line 320) is false for exactly the implementation the Design describes. A mutant that never prints the notice fails at the same line, so the case cannot tell the two apart. Lines 321-322 then pass trivially: the entry was gone before `told` ran.
Critique: review-003 F10 asked for the notice, and the fix put its assertion on the wrong command. The tempting fix is to make `sync` exempt from the automatic beat. That shrinks "every command" for the sake of a spec, and the next command (`status … prepared`) would print the notice instead.
Consequences: the notice belongs to the first command the old claimant runs after the takeover, whatever that command is. The spec has to read that command's stderr.
Recommendation: assert `taken over` (and the new stamp) on the stderr of `zn(wt, { "sync" }, at)`. Assert that `{wt}/.cache/tracker-beats/c0010` is gone right after it. Keep "no beat of either stamp" and "the next command does not repeat it" on the later `lessons --check` runs (lines 318 and 326). Walk the case again against the Design's order (stamp check before the interval check) before the next round. Lesson: z-design/prove-specs-pass-on-a-prototype (an edge case added in a refute ran against nothing).

### F2 [high] The claim-memory rule turns promoted c0116/claims red, and the Design says `Overrides: none` (repeat of review-003 F1, now confirmed by a run)
Where: Design, Takeover ("Every claim publish (`status <id|R-id> preparing`, the takeover included; `setStatus` today writes the memory for issues only, so it gains the raft case) records the new stamp in `.cache/tracker-claim-<id>`"); Regression guard (`Overrides: none`); Implementation step 1 (the suite run deferred to the executor); z-nile/tests/acceptance/c0116/claims.spec.luau:412-428.
Evidence: c0116/claims, case "a raft move never restamps a prepared member, and release needs the claim or --force", runs `trOk(E, { "status", "R0090", "preparing" })` and then `refused(E, { "release", "R0090" }, "not this checkout's")` (line 421). `release` gives back only a claim this checkout remembers in `.cache/tracker-claim-<id>`, the same file. With the Design's rule, E's `status R0090 preparing` writes that file, so `release` succeeds. My scratch prototype of the rule (two edits to `setStatus`: remember on every `to == "preparing"` publish, refuse the carried move when a remembered stamp differs) gives c0116/claims 20 passed, 1 failed at claims.spec:55 via line 421. c0053's three claim specs and c0117/dispatch stay green. The refute deferred exactly this run to the executor's Phase 1, but a Phase 1 that finds a red promoted spec in a feature issue can only stop: z-design requires a named override, and a chore in `depends_on`, before preparing.
Critique: this is the second round in which the claim memory hits an existing rule. The mechanism is the problem: `.cache/tracker-claim-<id>` already means "this checkout owns the rafting claim" (`release`, `fold`, `recombine`, c0116). The design now also uses it for "the stamp this checkout last claimed" (the user's "refuse"). Those are two facts, and c0116 pins the first one narrowly on purpose: `status R preparing` is not ownership. One tempting fix is to name the override and let `status R preparing` grant release ownership. That changes a c0116 rule nobody asked to change. The other is to write the memory only when a memory already exists. Then an old claimant whose only claim was `status R preparing` remembers nothing, and its carried move passes after a takeover, which contradicts the user's "refuse".
Consequences: a separate record keeps c0116 as it is and gives "refuse" every claim path. The rafting taker then cannot `fold` or `release` without `--force`, which is how any `status R preparing` claimer works today (and Q6's text has to say so).
Recommendation:

- State in the Design what a checkout with no record does (passes) and that a rafting taker's `release` and `fold` need `--force`, as today.
- Run c0116 and c0053 on a prototype of that rule in prep (it is a few lines in `setStatus`) and record the result in Unknowns & experiments.
- Keep `Overrides: none` only if they stay green.
- Add the case review-003 F1 asked for, (3), in the form this choice gives: wt2's `release R0020` after the rafting takeover is refused with "not this checkout's", and its carried `status R0020 prepared` passes.
Lesson: z-design/confirm-overrides-with-a-suite-run, z-design/claim-memory-rules-list-every-claim-path

### F3 [medium] `heartbeat.autoAllowed` is a second reader of the fence's variable: it compares strings exactly, fails open, and has no case at the edge
Where: Design, Automatic beats ("`heartbeat.autoAllowed(env, commonDir)` is false when the engine's git common directory is listed in the fence's `PICKMAN_FENCE_REAL_GIT`"); prototype `autoAllowed`; main.luau:241-273 (`guarded`: "the guards' own script answers, so no variable is named here"); fence.sh `pickman_guarded` (`c=$(cd "$c" && pwd -P)`, both the clean and the caller's resolution, exit 1 counts as guarded); Rules row "a nested `./zn` in a protected checkout never beats … run".
Evidence:
- The engine already asks the question "does a check protect this checkout" through `guarded()`. That function runs fence.sh's own `pickman_guarded`, compares physical paths, checks both git resolutions, and treats every outcome except `unguarded` as guarded (zz-arch rule 7).
- `autoAllowed` reads `PICKMAN_FENCE_REAL_GIT` itself with `dir == commonDir`. The Design never says how `commonDir` is obtained. In the main checkout, `git rev-parse --git-common-dir` prints the relative `.git`, and a symlinked or differently spelled path never compares equal. Every mismatch answers "allowed", which means a fetch and a push to the real origin from inside a check (review-003 F2's path).
- The only case is the pure one. A mutant that never calls `autoAllowed` at the edge, or passes the wrong directory, passes every spec. Review-003 F2's fixture case (a nested `./zn` under a fence that lists the checkout writes no beat) was not added, and its zz-test "Caught only by review" line was neither written nor added to Touched modules.
Critique: zz-arch rule 5 (one reader per format) and rule 7. The fix for a high repository-safety finding is pinned only where it cannot fail.
Consequences: reusing `guarded(true)` costs one `bash` per command. It is already cached per command, and it answers "unguarded" in a fixture (claims publish there today through `publishing()`), so beat.spec and lost.spec still beat.
Recommendation:
- Decide automatic beats (and the outer-command tick) with `not guarded(true)`. Drop `autoAllowed`, or keep it only as a pure mirror documented as matching `pickman_guarded`, with a physical-path case.
- Add a fixture case: in wt, with a due entry, run `zn(wt, { "lessons", "--check" }, due, { PICKMAN_FENCE_REAL_GIT = <the fixture's git common dir, spelled through a symlink or with a trailing `/.`> })`, and assert no new beat ref and no lscalls increment. Give it its own row.
- Write the "Caught only by review" line in the zz-test skill and add `z-nile/skills/zz-test` to Touched modules.
Lesson: zz-arch/one-reader-per-format, zz-arch/compare-canonical-spellings, zz-arch/guard-no-is-explicit

### F4 [medium] "The gate" is listed as a long outer command that beats while it runs, but no process exists to beat it when an agent runs `z-nile/check.sh` directly
