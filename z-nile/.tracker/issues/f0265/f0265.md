# f0265: Work heartbeat

## Problem
An agent working an item pushes a heartbeat every 5 minutes; a stale one marks the item lost, and lost work is picked first

Decided with the user (2026-11-07): "three beats" (the stale limit is 900 s, three beats of 300 s).
Decided with the user (2026-11-07): "ok" (lost work is listed first in `./zn lost` and at the top of `./zn status`; a lost `preparing` claim can be taken over directly; the skills say to take lost work first; the README's Order puts lost before rank; the fuller dispatch refusal stays out unless needed).
Decided with the user (2026-11-07): "heartless" (read as: a claim that has never had a beat is not judged lost; see Assumptions).
Decided with the user (2026-11-07): "a" (a claim with an open pull request, a dispatcher gate or a `questions.md` is parked: never lost, shown `[parked]`).

## Non-goals
- Anything on `main`: a heartbeat never commits a file, never moves `main` and never writes the main checkout (it is a ref, below).
- Ending, giving back or finishing a lost claim by itself: a lost claim is marked and offered first, and a person or a dispatcher acts on it with the commands that exist (`status`, `stop`, `release`, `z-run`).
- Exclusion of a live active raft: a second agent that runs `/z-run` on a raft whose claim is alive is not refused (the user's rule "ownership is documented, not checked", zz-rules, Sync and claim, Whose claim).
- The board (c0118) and `./zn work` (c0253): they will read `./zn lost` and `heartbeat.order`; neither is built here.
- The fuller dispatch refusal (`./zn dispatch <id>` refusing a live claim): out unless needed (the user's "ok").

## Solution
A claim (`preparing-…` on an issue or a raft, `active-…` on a readied raft) is a lease whose proof of life is a **beat**: a git ref on `origin` named `refs/zn/hb/<claim stamp>/<epoch seconds>`, pushed by the agent that works the item every 5 minutes. A beat is a ref to the commit `origin/main` already points at, so it moves no objects, touches no file, creates no branch, never moves `main` and never conflicts with anything. A claim whose newest beat is older than the **stale limit** (900 s) is stale; if the open pull requests do not name the item (nor a dispatcher wait), it is **lost**, and if one does it is **parked** (waiting for a merge or an answer, not worked, not lost). `./zn lost` lists lost claims and `./zn status` marks them and lists them first; a lost `preparing` claim can be taken over by the next `status <id> preparing`; the skills tell whoever picks work to take lost work before anything else.

## Design

### Assumptions to veto, and decisions still pending the user
- **Assumption (Q4 "heartless")**: read as "a claim that never had a beat is never lost". It is shown as `[no beat]` in `./zn status` (visible, not hidden), and `./zn beat <id>` or any `./zn` command in its worktree gives it its first beat. Cost: a claim whose first beat failed (offline claim) is never marked lost until someone beats it, and `[no beat]` is how a person sees it. The other reading ("no beat at all, no heartbeat feature") would drop the feature and is not taken.
- **Pending (Q6, no answer)**: (1) the old claimant's carried `status <id> prepared` is refused once the claim's stamp on origin differs from the one its checkout remembers (`status` names the takeover); (2) a taker continues from the old agent's pushed work branch when one exists (`./zn worktree prep-<slug> --from origin/prep-<slug>`), else starts fresh; a lost rafting claim (`preparing-…` on a raft) is taken over by `status <R-id> preparing` the same way.
- **Pending (Q7, no answer)**: `ZN_NOW` and `ZN_BEAT_EVERY` are honoured only inside a spec run (`PICKMAN_FENCE_SPECS=1`, the runner's marker); a skew above `STALE - INTERVAL` (600 s) between a writer's and a reader's clock can mislabel a claim; the accepted risk is stated here for the user's veto.

### Where a beat lives: the comparison (Q3, the user's suggestion "gh variables, or comments on PRs")
| constraint | ref `refs/zn/hb/…` (chosen) | repository variable | PR comment |
|---|---|---|---|
| no churn or conflict on main, no write to the main checkout | yes | yes | yes |
| a claim with no PR yet (every prep claim precedes its PR) | yes | yes | no: nothing to comment on |
| the dispatched agent's own token | a git push of a ref (U1: unproven for the agent token; fallback: the dispatcher pushes) | writing needs the Actions-variables permission, and `z-nile/bin/gh` refuses any `gh api` write but comments | allowed (comments) |
| one cheap read for all beats | one `ls-remote` (0.65 s), no objects | one `gh api …/actions/variables` (E6: 200, but the 30-variable store also holds the deploy's place ids) | one call per PR (a list of N PRs is N+1 calls) |
| rate and size | none that matters (refs) | rewrites a shared config object every 5 min per agent | 5000/h shared by every `gh` call; comments pile up |
| fits the wrappers and hooks | `git push` outside main passes `decidePush` (E1) | needs an allow-list entry in the wrapper for a config write: widens a guard | allowed |
The ref wins on the one constraint the others cannot meet (claims with no PR) and on rate and guard cost. Variables are repository configuration, shared with the deploy; comments need a PR. This is my choice, for the user to veto.

### The beat (pure module `z-nile/engine/heartbeat.luau`, no I/O, no clock)
```
export type Beat = { stamp: string, epoch: number, ref: string }
export type Claim = { id: string, state: string, stamp: string, match: { string } } -- match: the ids a PR may name (the item, and a raft's members)
export type Verdict = { id: string, state: string, stamp: string, silent: number?, kind: string } -- live | unbeaten | stale | parked | lost
export type Pr = { title: string, head: string }
heartbeat.PREFIX = "refs/zn/hb/"   INTERVAL = 300   STALE = 900   SKEW = 300
heartbeat.refName(stamp, epoch): string
heartbeat.parse(refs: {string}): ({Beat}, {string})                     -- beats, and a problem per malformed ref under the prefix
heartbeat.judge(claims, beats, now, stale?): {Verdict}                  -- live | unbeaten | stale
heartbeat.settle(verdicts, parked: {[string]: boolean}?): {Verdict}     -- stale -> parked | lost; nil (unknown) leaves stale
heartbeat.parkedBy(prs: {Pr}, claims): {[string]: boolean}              -- a PR parks a claim whose match id it names, whole ids only
heartbeat.order(verdicts): {Verdict}                                    -- lost first, longest silent first; the rest in input order
heartbeat.plan(stamp, epoch, beats, claimed, now): { write: string?, delete: {string} }
```
- **Name.** The lease id is the claim stamp. Items that share a stamp (a raft and its members) share its beats; a re-claim has a new stamp, so a dead claim's beats never keep its successor alive. The epoch is in the ref name, so one `ls-remote` reads every beat and no object is fetched. `parse` accepts `^refs/zn/hb/(preparing|active)-<word>-<word>-<word>/<digits>$`; any other ref under the prefix is a problem naming the ref and the rule (zz-arch rule 6).
- **What a claim is** (one definition, used by `beat`'s refusal, `judge`'s list and `plan`'s claimed set): an item whose effective state (`status.effective` with its folder) is `preparing` or `active` and whose stored `status:` carries a stamp. Items in `done/` (about 30 keep `status: active-…`) and `rafts/retired/` are never claims; a derived `preparing` raft with no stored stamp has no lease.
- **Kinds.** `last` is the newest beat of the claim's stamp not dated past `now + SKEW` (such a beat is ignored; one up to `SKEW` ahead reads as `now`). No beat: `unbeaten` (never stale, never lost; shown `[no beat]`). `silent = max(0, now - last)`; `silent > STALE` is `stale`, otherwise `live` (exactly the limit is live). `settle` turns a stale claim into `parked` when `parked[id]`, else `lost`, but only when the parked table was read; `nil` (the pull requests could not be read) leaves it `stale`, shown `[stale?]`: unknown is never lost (zz-arch rule 7).
- **Parked.** A claim is parked when an open PR's title or head branch names one of its `match` ids (whole ids: `c0060` does not match `c00600`), or when a dispatcher run state `.cache/dispatch/<id>/questions.md` exists in the main checkout. A dispatcher stopped at a merge gate has an open PR, so the PR rule covers it. The cheapest reliable source is one `gh pr list --state open --json title,headRefName --limit 200`, made **lazily**, only when some claim is stale (the common `status` costs nothing extra); a failing `gh` makes the list unknown.
- **Order.** `order` is the one definition of "picked first".
- **Plan.** A beat is one atomic push (`git push --atomic origin <sha>:<refName> :<old>…`) of `plan.write` plus deletions: the older beats of the same stamp, and the beats of a stamp no claim holds only when older than `STALE` (a young unclaimed beat may be a claim this checkout has not fetched). `write` is nil when a beat of the same second exists; a newer beat of the stamp is never deleted.

### The engine edge (`z-nile/engine/main.luau`, the one place that reads and writes)
- **`./zn beat <id> [--watch]`**: fetches `origin main` first (so claims and the claimed set are current), refuses (exit 1, naming the item and the rule) an item that is not a claim: `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`, `beat: c0060 is done: no claim to beat`. It pushes `plan`'s write and deletions with the commit `refs/remotes/origin/main` points at; it changes no file, index, HEAD, branch or config, so it runs in the main checkout and in any worktree and publishes nothing to `main`. `--watch` repeats it every `INTERVAL` seconds (fetching each tick) and **refuses unless it runs under `./zn run`** (`ZN_BOUNDED_DEADLINE` set: `beat --watch must run as ./zn run --time 3600 -- ./zn beat <id> --watch`); it exits 0 with a message when the item's stamp on origin changed (claim ended or taken over) or when the next tick would pass the bound; a failed beat is said on stderr and retried at the next tick.
- **Automatic beats.** A beat writes `.cache/tracker-beats/<id>` (`<stamp> <epoch>`) in the checkout that made it. Every `./zn` command except `beat`, `run`, `reap` and `READ_ONLY` ones first reads that folder and, for an entry whose epoch is at least `INTERVAL` old, beats that item (best effort: a failure warns once on stderr and never fails the command). So a session that keeps working keeps its claim alive for as long as it runs any `./zn` command (`commit`, `spend`, `status`, `check`, `dispatch`…), with no loop and no network call inside the interval. First beats: `status <id> preparing`, `status <R-id> preparing`, `new raft`, `fold`, `recombine`, `ready` and a legacy `start` beat right after their publish (they also write the throttle file).
- **`./zn lost`**: one line per lost item, `<id> <state> <minutes>m` (minutes floored), in `heartbeat.order`; a raft's members each get their own line (verdicts are per item, the raft's stamp shared); nothing when none; exit 0. When the beats (`ls-remote`) or the pull requests cannot be read it says `lost: heartbeats unreadable: <message>` / `lost: pull requests unreadable: <message>` on stderr, prints nothing and exits 1. A malformed beat ref is named on stderr (`lost: refs/zn/hb/garbage: not a beat …`) and the rest still judged.
- **`./zn status`** (the list): lost claims first (longest silent first), each `<id> <status> <title> [lost <n>m]`; parked `[parked]`, never beaten `[no beat]`, stale but unconfirmed `[stale?]`; every other line and `status <id>` unchanged. Unreadable beats: the list prints as today with `status: heartbeats unreadable` on stderr.
- **Takeover**: `status <id> preparing` (or `<R-id>`) on a `preparing` claim keeps its refusal text (`<id> is preparing on origin/main: cannot move to preparing`, c0053's) with `; claim alive: last heartbeat <n>m ago, limit <m>m` for a live claim, `; claim parked (an open pull request names it)` for a parked one, `; no heartbeat verdict: <reason>` when anything was unreadable or malformed (naming the ref or git's message), and `; no heartbeat yet` for a claim never beaten. Only an explicit lost verdict allows it (`status.canTakeOver`): it draws a stamp with `freshStamp("preparing")` (checked against `origin/main`, as `ready` does: issue claims drew with `stamp()` before, a 1.4 % chance today that two live claims share a stamp), beats at once, and that beat's `plan` prunes the old claim's beats after the grace. The carried `status <id> prepared` refuses when the stamp on origin differs from the one this checkout remembers: `<id>'s claim was taken over (now <stamp>): …`. An `active` claim is taken over as today (`./zn stop`, `/z-run`).
- **`ZN_NOW`, `ZN_BEAT_EVERY`**: honoured only when `PICKMAN_FENCE_SPECS=1`.
- **The dispatcher** (`z-nile/engine/dispatcher.luau`): while a model step runs, every `INTERVAL` it starts `zn beat <id>` for the item the step works (a raft's id for z-raft and z-run), one child at a time, killed after 60 s (E3: a `process.exec` in a `task.spawn` does not stall the supervising loop). A refusal (no claim yet) is ignored; any other failure is written once per step to the run's stderr. Under `ZN_DISPATCH=1` the step starts no loop (the skills say so).
- **Why not `reap`, the sweeper, or `sync`**: they clean local leftovers; a beat leaves nothing local but the throttle file (ignored, under `.cache`).

### The skills
`zz-rules`: a Heartbeat paragraph (the ref, the limit, parked, `beat`, `lost`, takeover, `ZN_NOW`) and its command table rows, and the main-checkout list ("`beat` writes a ref under `refs/zn/hb/` only"). `z-design` (claim step: start `./zn run --time 3600 -- ./zn beat <id> --watch` in the background unless `ZN_DISPATCH=1`; every `./zn` command beats too; Candidates: take `./zn lost` first, and continue a lost prep from `origin/prep-<slug>`), `z-raft`, `z-run` and `zz-execute` (the same loop for the raft; `z-run` of a lost raft re-adopts it) gain one bullet each. The README's Order says lost work comes before `rank`, its Roadmap gets `work heartbeat | f0265 | exists`, the usage text lists `beat` and `lost`.

### Scalability
`status`/`lost`: one `ls-remote` and, only when a claim is stale, one `gh pr list`. A beat: one fetch, one `ls-remote`, one `git grep`, one push (no objects) per working agent every 5 minutes; throttled locally so frequent `./zn` commands cost nothing. Refs trigger no workflow (`deploy.yml` runs on `main` and pull requests). Origin holds one ref per live claim.
### Maintainability
`heartbeat.luau` is the one reader and writer of the ref format; the lease id is the existing claim stamp; `./zn work` (c0253) calls `settle` and `order`; the limit and interval are constants.
### Usability
Two commands and four markers, each refusal naming the item and the rule; no agent has to remember to beat (claims, any `./zn` command, the dispatcher, the loop).
