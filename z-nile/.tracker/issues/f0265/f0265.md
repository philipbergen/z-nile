# f0265: Work heartbeat

## Problem
An agent working an item pushes a heartbeat every 5 minutes; a stale one marks the item lost, and lost work is picked first

## Non-goals
- Anything on `main`: a heartbeat never commits a file, never moves `main`, and never writes the main checkout (it is a ref, below), so the claims' tracker commits stay the only thing the tiny-push rule allows there.
- Ending, giving back or finishing a lost claim by itself: a lost claim is marked and offered first, and a person or a dispatcher acts on it with the commands that exist (`status`, `stop`, `release`, `z-run`).
- Exclusion of a live active raft: a second agent that runs `/z-run` on a raft whose claim is alive is not refused (the user's rule "ownership is documented, not checked", zz-rules, Sync and claim, Whose claim).
- The board (c0118) and `./zn work` (c0253): they will read `./zn lost` and `heartbeat.order` below; neither is built here.

## Solution
A claim (`preparing-…` on an issue or a raft, `active-…` on a readied raft) is a lease whose proof of life is a **beat**: a git ref on `origin` named `refs/zn/hb/<claim stamp>/<epoch seconds>`, pushed by the agent that works the item every 5 minutes. A beat is a ref to the commit `origin/main` already points at, so it moves no objects, touches no file, creates no branch, never moves `main` and never conflicts with anything. A claim whose newest sign of life (its newest beat, or the moment its claim landed on `main` if it was never beaten) is older than the **stale limit** is **lost**. `./zn lost` lists lost claims and `./zn status` marks them and lists them first; a lost `preparing` claim can be taken over by the next `status <id> preparing`; the skills tell whoever picks work to take lost work before anything else.

## Design

### Open decisions (the user's; the values below are proposals, each one line to change)
- **Q1, the stale limit.** Proposed `heartbeat.STALE = 900` s (15 min: three beats). It is one constant. Shorter (10 min, two beats) finds a dead agent sooner but marks a live one lost when a laptop sleeps for 10 minutes; longer (30 min) never mislabels a live agent and leaves dead work hidden for half an hour.
- **Q2, what "picked first" does today.** Proposed: (a) `./zn lost` and the top of `./zn status` list lost work first, longest silent first (`heartbeat.order`, the order `./zn work` will adopt); (b) a lost `preparing` claim can be taken over without anyone giving it back first; (c) z-design's, z-ready's and z-run's candidate steps say "take `./zn lost` before anything else"; (d) the README's Order says lost work comes before `rank`. Not proposed: the dispatcher or a raft plan picking work by itself (nothing picks without an id until c0253). The alternative is (a) alone, which makes lost work visible and leaves the picking to the person; the other extreme is also making `./zn dispatch <id>` refuse a live claim, which needs a rule for every step.
- **Q3, where a beat lives.** Proposed: a ref on `origin` outside `refs/heads` (this design). Rejected for breaking the captured constraints: a file on `main` (a commit per beat per agent: merge conflicts and CI churn on `main`, the main checkout moved every 5 minutes) and a branch (shows in every branch list, `busy` and the board).
- **Q4, claims that exist the day this lands.** Every `preparing` or `active` claim made before has no beat, so it reads as silent since its landing and is lost at once if older than the stale limit (which is true: nothing proved it alive). Proposed: the executor names every such claim in the PR, and their owners run `./zn beat <id>` (or just keep working: the next commit beats). The alternative is a grandfather rule (a claim with no beat is never lost), which hides every claim whose first beat failed.

### The beat (pure module `z-nile/engine/heartbeat.luau`, no I/O, no clock)
```
export type Beat = { stamp: string, epoch: number, ref: string }
export type Claim = { id: string, state: string, stamp: string, since: number } -- state: preparing | active; since: epoch the claim landed on main
export type Verdict = { id: string, state: string, stamp: string, silent: number, lost: boolean }
heartbeat.PREFIX = "refs/zn/hb/"   heartbeat.INTERVAL = 300   heartbeat.STALE = 900 (Q1)   heartbeat.SKEW = 300
heartbeat.refName(stamp, epoch): string                       -- "refs/zn/hb/<stamp>/<epoch>"
heartbeat.parse(refs: {string}): ({Beat}, {string})           -- beats, and one problem per malformed ref under the prefix
heartbeat.judge(claims, beats, now, stale?): {Verdict}
heartbeat.order(verdicts): {Verdict}                          -- lost first, longest silent first; the rest in input order
heartbeat.plan(stamp, epoch, beats, claimed: {[string]: boolean}): { write: string?, delete: {string} }
```
- **Name.** The claim stamp (`status:` value, `preparing-quiet-copper-falcon`) is already unique on `origin/main` (claims.taken, `status.fresh`), so it is the lease id. Items that share a claim (a raft and its members) share its beats; a re-claim has a new stamp, so a dead claim's beats never keep its successor alive. The epoch is in the name, so **one `git ls-remote origin 'refs/zn/hb/*'` reads every beat, with no object fetched**. `parse` accepts `^refs/zn/hb/(preparing|active)-<word>-<word>-<word>/<digits>$`; any other ref under the prefix is a problem naming the ref and the rule (zz-arch rule 6); refs outside the prefix are ignored.
- **Lost.** `silent = max(0, now - last)`, `last = max(claim.since, newest beat of claim.stamp)`, and `lost = silent > STALE` (exactly the limit is live). A beat dated past `now + SKEW` is ignored, not trusted (a wrong clock must not keep a claim alive for hours), and one up to `SKEW` ahead reads as `now`. A claim nobody beat is silent since `since`, so it turns lost on the same clock. Clocks: the writer's and the reader's wall clocks are compared, so a skew above `STALE - INTERVAL` can mislabel; ntp-grade clocks are assumed (accepted risk: checked against SETUP.md's hosts, which are developer machines with network time).
- **Order.** `order` is the one definition of "picked first": lost before live, longest silent first, ties and live items in input order (stable).
- **Plan.** A beat is one atomic push (`git push --atomic origin <sha>:<refName> :<old>...`) of `plan.write` plus the deletion of `plan.delete`: the older beats of the same stamp, and every beat of a stamp no claim holds (a finished or given-back claim). `write` is nil when a beat of the same second exists; a newer beat of the same stamp (another beater) is never deleted. So origin holds one beat per live claim in steady state, and a crashed beater's leftovers are pruned by the next beat of anyone.

### The engine edge (`z-nile/engine/main.luau`, the one place that reads and writes)
- **`./zn beat <id> [--watch]`**: refuses (exit 1, naming the item and the rule) an item that is not on `origin/main` or whose stored `status:` is not `preparing-…`/`active-…`: `beat: c0020 is new on origin/main: no claim to beat (claim it with ./zn status c0020 preparing)`. Otherwise it reads the claim stamp from `origin/main`, the claimed stamps of all items (one `git grep`), the existing beats (one `ls-remote`), and pushes `plan`'s write and deletes with the commit `origin/main` points at (`refs/remotes/origin/main`, already in this clone's objects, already on origin). It changes no file, index, HEAD, branch or config, so it runs in the main checkout and in any worktree, and publishes nothing to `main` (zz-rules' main-checkout list and the direct-push exception gain "beat writes a ref under `refs/zn/hb/` only"). Retries a lost race once. `--watch` repeats it every `INTERVAL` seconds (`ZN_BEAT_EVERY`, a whole number of seconds, overrides it for specs) until the item's stamp on `origin/main` is no longer the one it started with (claim ended or taken over: it says so and exits 0); a failed beat is said on stderr and retried at the next tick (never silent), and the loop is always started as `./zn run --time <s> -- ./zn beat <id> --watch` so it ends with its bound, with the session, and with `./zn reap`.
- **`./zn lost`**: one line per lost claim, `<id> <state> <minutes>m`, in `heartbeat.order`; nothing when none; exit 0. When the beats or the claim times cannot be read (no origin, `ls-remote` fails, git's message) it says `lost: heartbeats unreadable: <git's message>` on stderr, prints nothing and exits 1: **unknown is never lost** (zz-arch rule 7: the action that follows, a takeover, is the dangerous one, so only an explicit answer lets it through).
- **`./zn status`** (the list): lost claims first (longest silent first), each line `<id> <status> <title> [lost <n>m]`; every other line and `status <id>` are unchanged. If the beats are unreadable the list prints as today, with `status: heartbeats unreadable` on stderr.
- **`status <id> preparing` on a `preparing` claim**: the refusal stays (`<id> is preparing on origin/main: cannot move to preparing`, c0053's text) with `; claim alive: last heartbeat <n>m ago, limit <m>m` appended; when the claim is lost the move is allowed (`status.canMove` gains `takeover`, a boolean the edge passes only from an explicit lost verdict): it writes a fresh stamp, beats at once, and the old claim's beats are pruned by that beat. An `active` claim is taken over as today: `./zn stop <R-id>` (anyone), or `/z-run` on the same raft, whose `beat --watch` revives the same stamp.
- **Claim time (`since`)**: `git log -1 --format=%ct -S"status: <stamp>" origin/main -- <doc path>` (the commit that added the line; E4: 18 ms). One call per claimed item.
- **First beat on every claim path**: `status <id> preparing`, `status <R-id> preparing`, `new raft`, `fold`, `recombine` (the raft's stamp), `ready` and a legacy `start` call `beatQuiet(id)` after their publish: a beat that fails warns on stderr and never fails the command (a claim made offline simply starts silent). `./zn commit` in a raft's worktree beats the raft too (work is happening), so a forgotten loop still leaves a trail.
- **`ZN_NOW`** (epoch seconds) replaces the clock in `lost`, `status`, `beat` and the takeover, for the specs; it is the user's own environment, like `PICKMAN_PUBLISH`.
- **The dispatcher** (`z-nile/engine/dispatcher.luau`): while a model step runs, every `INTERVAL` it starts `zn beat <id>` for the item the step works (a raft's id for z-raft and z-run), as one child at a time, killed after 60 s, its refusal ignored (a `new` item has no claim yet; the step's own claim beats). It runs in the runner's tick as a task (E3: `process.exec` inside `task.spawn` does not stall the supervising loop: 40 ticks in 2 s). Under `ZN_DISPATCH=1` the step itself does not start a loop (the skills say so); an interactive session starts one.
- **Why not `reap`, the sweeper or the main checkout's `sync`**: they clean *local* leftovers (processes, ignored files); a beat leaves nothing local, and its remote leftovers are pruned by the next beat, so none of them changes.

### The skills
`zz-rules` gets a Heartbeat paragraph (the ref, the limit, `beat`, `lost`, takeover, the main-checkout list) and its command table rows; `z-design` (step 1: after the claim start `./zn run --time 14400 -- ./zn beat <id> --watch` in the background, unless `ZN_DISPATCH=1`; Candidates: `./zn lost` first), `z-raft` and `zz-execute`/`z-run` (the same loop for the raft, and `z-run` of a lost raft re-adopts it) and `z-ready` (candidates: lost first) gain one bullet each; the README's Order says lost work comes before `rank`, its Roadmap gets the row `work heartbeat | f0265 | designed`, and the usage text lists `beat` and `lost`.

### Scalability
`status` and `lost`: one `ls-remote` (0.65 s to GitHub, E2) and one 18 ms pickaxe per claimed item, never per item of the tracker; a beat is one `ls-remote`, one `git grep`, one push with no objects, every 5 minutes per working agent: ten agents are two pushes a minute, to refs that trigger no workflow (`deploy.yml` runs on `main` and pull requests only). Origin holds one tiny ref per live claim.
### Maintainability
`heartbeat.luau` is the one reader and writer of the ref format (zz-arch rule 5); the lease id is the existing claim stamp, so nothing new is allocated; `c0253`'s `./zn work` calls `heartbeat.order` and `judge` instead of re-deriving "lost"; the stale limit is one constant.
### Usability
Two new commands and one marker, each with a refusal that names the item and the rule; an agent never has to remember to beat in the common paths (claims, `commit`, the dispatcher beat for it), and the loop is one pasted line.

### Experiments run now
- **E1 (pass)**: a local bare origin takes `git push --atomic origin refs/heads/main:refs/zn/hb/<s>/<new> :refs/zn/hb/<s>/<old>` in 58 ms with no object transfer; `ls-remote 'refs/zn/hb/*'` shows exactly the new ref; `git push --dry-run --porcelain` reports `*` (new) and `-` (deleted) lines whose destinations are not `refs/heads/main`, so `wrapper.decidePush` passes them untouched.
- **E2 (pass)**: the real GitHub origin accepted `refs/zn/hb/probe-f0265/1` and its deletion with the user's credential; `ls-remote` returned it (0.65 s). **Not proven**: the dispatched agent's own fine-grained token may be refused a ref outside `refs/heads` (see Unknowns U1).
- **E3 (pass)**: a `process.exec("sleep 2")` in a `task.spawn` leaves the main loop ticking (40 ticks in 2 s).
- **E4 (pass)**: the pickaxe `git log -1 --format=%ct -S"status: <stamp>" origin/main -- <doc>` answers in 18 ms and returns the claim commit (f0265's own claim).
- **E5 (pass)**: the pure module prototyped in prep and run against `acceptance/heartbeat.spec.luau`: 9 of 9 pass, and 11 mutants each fail on an assertion (below). The prototype is not committed.
