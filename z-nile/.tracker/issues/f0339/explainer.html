f0339: Ticket explainer page

The idea

Before a ticket is built, a person approves its design with ./zn approve <id>. That command saves a fingerprint (a hash) of the design in the ticket's approval.md. Later steps refuse to build a design whose fingerprint changed.

Today the person approves without being shown anything. They must read the long design text on their own.

After this change, each ticket has one web page, explainer.html, written when the ticket is designed. It says in plain words what the idea is. It draws the system before and after. It lists which files change. It gives the good and bad sides of each choice.

./zn approve opens that page in your browser and then asks y/n. Only y or yes saves the approval. Any other answer saves nothing.

Before

The designer writes the ticket. The person runs approve, and it saves the fingerprint at once.

What changes where

  • z-nile/engine/explainer.luau (new): explainer.check(path, html, hash, touched) lists every way a page breaks the expected shape, and explainer.accepts(answer) says whether an answer is a yes. No files are read here.
  • z-nile/engine/main.luau: a new command, ./zn explain <id>, prints the page's path and the hash it must name, then ok or the problems. cmd.approve checks the page, opens it, asks [y/N] at the terminal, and checks again that nothing changed before it saves. approve --publish warns when the page is not on main yet. One new table, pageIO, holds the helpers open (also used by ./zn board), readLine and problems: the file has room for only one more top-level name.
  • z-nile/engine/approval.luau: the "has no approval" refusal adds that the approval first needs the page.
  • z-nile/templates/explainer.html (new): a page of the right shape to copy. Each placeholder is marked zn-fill, and a page that still has one is refused.
  • z-nile/skills/z-design/SKILL.md: the designer writes the page and runs ./zn explain until it says ok.
  • z-nile/skills/zz-rules/SKILL.md: the approve row describes the page and the question; a new explain row.
  • z-nile/skills/zz-review/SKILL.md: the design reviewer reads the page beside the design.
  • z-nile/skills/zz-execute/SKILL.md and z-nile/skills/z-ready/SKILL.md: a re-approval during a raft, and the first approval of an older ticket, start by bringing the page up to date.
  • z-nile/README.md: the approve sentence says the page is shown first.
  • z-nile/tests/tooling/approve.spec.luau and z-nile/tests/tooling/approve-publish.spec.luau: their test tickets get a page, and they type y.
  • z-nile/.tracker/issues/f0339/acceptance: the new tests (the page's shape, the approve flow, the docs).

After

The designer also writes the page. Approve checks it, opens it, and waits for your answer.

Choices

The page is not part of the approved fingerprint

  • Every approval saved today stays valid.
  • Fixing a typo on the page never asks for a new approval.
  • The page could drift from the design. To catch that, the page names the fingerprint it explains, and approve refuses a page that names an old one.

z-nile checks the page's shape, a person checks its words

  • A machine check finds a missing diagram, the same picture twice, a file left off the list, template text left in, or a link to the web.
  • The words and pictures are read by the design reviewer and by you.
  • A page can pass the check and still explain badly; only people catch that.

The page loads nothing from anywhere else and runs no scripts

  • It opens the same offline and years later, with no web fonts or chart libraries.
  • With no scripts at all, nothing on the page can fetch anything behind the check's back.
  • Diagrams are hand-written SVG, not drawn by a diagram tool, and the page can't link to a pull request or even name a web address.

Only y or yes approves; the answer is read from the terminal

  • Pressing Enter, a typo, or a closed terminal saves nothing.
  • A script piping text into the command can't answer for you.
  • Tests have to give the command a real terminal (they use script and yes y).

If the browser can't be opened, approve warns and still asks

  • A machine without a browser opener can still approve; the page's path is printed.
  • Someone could answer without opening the page. The warning tells them to read it first.

Tickets designed earlier need a page before their next approval

  • Every approval from now on comes after an explanation, which is the point.
  • No list of exceptions to keep.
  • 16 designed tickets waiting for approval, and any ticket whose design changes during a raft, each need a page written first (minutes of an agent's work each).
  • A page written at approval time travels in a pull request, not with the approval itself; approve --publish warns until it is on main.
