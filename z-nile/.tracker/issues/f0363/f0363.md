# f0363: Raft follows dependencies

## Problem
- `./zn raft-plan` does not read `depends_on`, so a prepared backlog issue and the same-type, same-project prepared issue it depends on are planned into different rafts and the dependent waits for its dependency to land.
- `./zn raft-plan` starts another raft, skips an issue or refuses a fold when a raft's summed size passes about 1,500 lines, and the z-raft skill and zz-rules state that cap, so a dependency chain cannot be planned as one raft.
- When a dependency is discovered after rafting, nothing names the two issues or a remedy: `./zn raft-plan` says nothing, and `./zn ready` refuses the dependent's raft with a bare refusal.
- One rafting cannot regroup in one pull request, because `./zn recombine` refuses a keeper raft the same rafting already claimed and `./zn fold` refuses an issue the same branch unfolded until that unfold is on origin/main.
- A person who wants a dependent kept apart from its dependency has no way to record that choice, so a re-raft prompt for that pair would be printed on every run.

## Non-goals
- The tooling never re-rafts by itself: every re-raft is a command a person runs.
- No command of this feature moves, changes or prompts about an active raft or its issues.
- No raft holds issues of more than one type or more than one project.
- c0286's grouping of issues the user tied together, d0360's refusal of dependency cycles, d0295's Order check and c0249's rank are unchanged.

## Solution
- `./zn raft-plan` plans two prepared backlog issues of the same type and the same project joined by a `depends_on` edge into one raft with the dependency's layer below the dependent's, for features, defects and chores, and for chains.
- An issue that depends on an issue of another type or another project is not grouped with it, and that dependency must still be done before the raft is readied.
- `./zn raft-plan` no longer starts another raft, skips an issue or refuses a fold because of summed size, the z-raft skill and zz-rules no longer state a cap, and `size:` is still recorded and shown.
- A solo issue is still planned alone, a single raft still takes nothing, and a dependency that is already active or done is not pulled into a raft.
- When `./zn raft-plan` runs and finds a `depends_on` edge between two same-type, same-project prepared issues that sit in different backlog rafts, or one in a raft and one in none, it prints a re-raft prompt that names the two issues, the rafts involved and the command that would put them in one raft.
- When `./zn ready` is asked to ready a raft whose member depends on a same-type, same-project prepared issue outside it, it refuses and prints that same re-raft prompt.
- When `./zn ready` is asked to ready a raft whose member depends on a prepared issue of another type or another project, it refuses, names that dependency, says it must be done first and names no re-raft command.
- A person can record that one dependent stays apart from one dependency, in a place the design names, and `./zn raft-plan` then neither groups that pair nor prints the re-raft prompt for it.
- When `./zn ready` is asked to ready a raft whose dependent is recorded apart from an undone dependency, it refuses, names the dependency, says it must be done first, and names the record and how to remove it.
- In one branch, `./zn recombine` accepts a keeper raft that the same rafting already claimed, and `./zn fold` accepts an issue that the same branch unfolded.
- z-raft with arguments still makes the raft, fold or recombine it is asked for, whatever the dependency edges say.
- The z-raft skill and the zz-rules Rafting section describe dependency grouping, the removed cap, the re-raft prompt and the keep-apart record.
