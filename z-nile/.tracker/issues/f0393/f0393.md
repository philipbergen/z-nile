# f0393: Findings stay in raft

## Problem
- A finding made while designing or delivering a raft (a review finding, a failed step, something noticed in passing) opens a backlog ticket today, so 371 issues were opened against 147 closed and about 60% of all issues cite a raft, a review finding or a one-off incident.
- AGENTS.md and the skills' Lessons sections tell every lead other than a prep or raft lead to capture a new lesson as an issue.

## Non-goals
- A person describing new work to z-ticket still captures a backlog ticket as today.
- The 150 issues already in the backlog are not closed, merged or re-homed by this issue.
- The approval rule for ordinary raft members is unchanged: only an added issue may be approved after its raft's first pull request has merged.

## Solution
- No skill tells an agent to open a backlog ticket, a list entry or a final-report section for a finding: zz-rules "Emergent issues", zz-execute's "Follow-ups filed" report line and the review skills' handling of unfixed findings are changed to match.
- The agent that has the finding decides whether it is worth doing, and for one that is not, it writes a lesson saying not to worry about it.
- A worth-doing fix under a stated size threshold is made in the raft that found it, with no new issue.
- A larger worth-doing finding becomes a new member issue of the raft that found it, designed with recorded guesses, and the agent tells the user it did so.
- The rest of the raft is implemented and its pull request merges without waiting for the added issue's approval.
- A raft with an added member that is unapproved or unimplemented stays in `active/` after that merge, is not done, and the added issue never moves to the backlog.
- After the user approves the added issue, it is implemented on a further pull request of that same raft, and the raft is done only when every member is implemented or the user has rejected the added issue.
- A worth-doing finding made while designing an issue that has no raft yet is added to that issue's own design when it fits the size threshold.
- A larger design-time finding becomes a new issue bound to the issue being designed, so that z-raft always puts both in the same raft and it is never a free backlog ticket.
- A lesson is written straight into the lessons file by whoever learns it, whatever its role, with subagents still reporting to their lead; AGENTS.md and every skill's Lessons section (z-nile's and every project's) say so.
- A tooling (z-nile) ticket is opened only when the user asks for it or when the same failure has happened a second time; a first one-off incident gets a lesson line.
