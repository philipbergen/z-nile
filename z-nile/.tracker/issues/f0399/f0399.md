# f0399: z-work works every ticket

## Problem
- z-work takes only rafts that are ready, so a ticket that is captured, designed or prepared but not yet rafted and readied gets no work from a z-work session.
- Nothing states the order in which z-work would pick among tickets at different steps and with different dependencies.

## Non-goals
- z-work never lands a ticket the human has not approved, however green its gates are.
- This ticket does not change what `./zn dispatch` does, which stays with c0267 and c0252.
- This ticket does not define stacked PR delivery or part landing (c0248), work rank beyond the order above (c0249), or how an added issue waits inside its raft (c0394).

## Solution
- With no raft named, z-work picks any ticket that is not landed and does its next step (design it, fix it, raft it, or implement it), using its best judgement where the ticket leaves a choice open.
- z-work picks in two tiers, and the tier always wins: every ticket with no unmet dependency comes before any ticket that has one.
- Inside a tier, z-work picks the ticket furthest along first (ready raft, then rafted, then prepared, then designed, then captured), so a captured ticket with no dependency is taken before a prepared ticket that depends on an unlanded one.
- A ticket has an unmet dependency when a ticket it depends on has not landed on main.
- z-work starts the second tier only when no ticket in the first tier has a step left that it can do without the human.
- z-work branches a ticket with an unmet dependency off that dependency's branch, not off main.
- z-work puts a ticket and the tickets it depends on in one raft.
- z-work records every guess and assumption it makes in the ticket it made it for, each with what it chose and why.
- A ticket picked up before it was approved may go through every step up to landing, and does not land until the human approves it.
- A ticket with a material change, guess or judgement call pauses after all its gates pass, and continues only on the human's approval.

## Design

Every **Guess (prep)** below is a choice the capture left open, made without the user (the user, 2026-11-16: "make guesses and evidence based assumptions to work through the design without me. I'll review them all before approving"). They are listed again under Unknowns & experiments, G1 to G18, each with its evidence and what the other choice would cost.

Words used below. A **guess** is any choice the worker makes that the approved contract of an issue does not already make: an open question answered, a judgement call, a ruling it would otherwise have asked for. **Guess mode** is a session that takes its actions from `./zn work next` and is not under `./zn dispatch` (`ZN_DISPATCH` unset), or a session the user told to guess. An approval **holds** when the issue's `approval.md` exists and its last row's hash equals the contract's hash now (`approval.verdict`, state `holds`).

Where this sits (**Guess (prep) G1, G2**). f0399 is designed on today's `main`: on `work.luau`'s `./zn work next`, with no dependency on the vision raft (c0248 to c0254) or on c0394. It does not edit their documents. Section 9 says what each of them meets when it is built after f0399.

### 1. Guesses are a file the approval covers

**The file.** `<issue dir>/guesses.md`, one line per guess, oldest first:

```
# guesses
- G1 (design, 2026-11-16): <what was open>. Chose: <what the worker chose>. Why: <the evidence>.
```

The step is `design`, `raft` or `build`. Ids count up from G1 with no gap. A field holds no line break and neither of the marks ` Chose: ` and ` Why: `. A guess is never edited or removed once committed: a guess the worker changes its mind on gets a new line that names the old one.

**`z-nile/engine/guesses.luau`** (new, pure):

```luau
export type Guess = { id: string, step: string, when: string, open: string, chose: string, why: string }
guesses.FILE = "guesses.md"
guesses.STEPS = { "design", "raft", "build" }
-- nil and the problem for a text that is not the header and well-formed lines numbered from G1
function guesses.parse(text: string): ({ Guess }?, string?)
-- the file's new text with one more guess; nil and the problem for an unknown step, an empty field,
-- a field with a line break or a mark, or a `text` that does not parse
function guesses.append(text: string?, step: string, when: string, open: string, chose: string, why: string): (string?, string?)
function guesses.render(list: { Guess }): string
function guesses.has(text: string?, id: string): boolean
```

**`./zn guess <issue-id> --step design|raft|build --open "<…>" --chose "<…>" --why "<…>"`** writes the issue's `guesses.md` in this worktree and prints `<Gn> recorded for <id>: commit it with your work`. It commits nothing (as `./zn idea`), refuses the main checkout (`refuseInMainCheckout`), an id that is not an issue in this checkout, and what `guesses.append` refuses, printing `guess: <its problem>` and leaving the file as it was. An empty option value is an empty field. The date is today's (UTC).

**`./zn guesses <issue-id|R-id> [--check]`** is read-only (it joins `READ_ONLY`). For an issue, or each member of a raft in the raft's order, it prints a head line `<id>: <n> guesses, <approved|not approved|changed since approval (<parts>)>` and then the guess lines as written. An issue with no `guesses.md` prints its head line alone, with `0 guesses`. `--check` prints nothing on stdout, and exits 1 with `<path>: <problem>` on stderr when a `guesses.md` does not parse. It reads this checkout, so the person runs it in the worktree that holds the work.

**The approval covers it.** `contract.build(doc, check, specs, guesses: string?)` gains an optional fourth text. When it is given and not empty, the parts gain one named `guesses` (its normalized text); otherwise the parts are today's, so no existing approval changes. In `contract.order` it sorts after `check.sh` and before the specs. A spec named `guesses` is refused as `design` and `check.sh` are. `approval.collect` reads `<issue dir>/guesses.md` and lists it among the contract's paths (so `approve` refuses an uncommitted one); `readyfacts` and `workread` hand the file to `contract.build` the same way.

So a guess recorded after an approval makes that approval stop holding, and every message that names changed parts names `guesses`. This is what enforces the capture's "pauses after all its gates pass": section 3 lets nothing land without an approval that holds. **Guess (prep) G3.** `guesses.md` is not one of `raftplan.isDesignFile`'s files, so a guess recorded while rafting does not make a raft's `grouped:` record stale.

### 2. A guessed answer under "Open to the human"

Today a refuted finding or an unclosed high stops for the person's `Ruled (user, YYYY-MM-DD):` line. In guess mode the worker answers it with a guess instead:

```
  Guessed (agent, 2026-11-16): G3
```

In a raft's document the guess is named with its issue: `Guessed (agent, 2026-11-16): c0010 G3` (a raft has no approval of its own, so a raft-level guess is recorded in the member it concerns, or in the raft's first member in its order when it concerns the whole raft). A later `Ruled (user, …):` line on the same bullet is the person's ruling as today.

`openlist.luau`:

```luau

function openlist.pending(doc: string): { string }
-- bullets with neither a Ruled line nor a Guessed line
function openlist.waiting(doc: string): { string }

function openlist.guessed(doc: string): { { id: string, issue: string?, guess: string } }
```

`openlist.problem` judges by `waiting`, and its message is unchanged. Who asks what:

| asker | accepts a Guessed bullet | why |
|---|---|---|
| `./zn status <id> preparing` (`idea.designRefusal`, `openlist.pending`) | no | the idea is the person's (G7) |
| the dispatcher (`dispatcher.luau`, `openlist.pending`) | no | dispatch is unchanged (Non-goals) |
| `./zn status <id> prepared`, `./zn ready`, `./zn done`'s review check (`openlist.problem`) | yes | the guess is in a `guesses.md` an approval must cover |

### 3. Approval is checked at the landing, not at ready

Today `ready` refuses a member with no approval or a changed contract (`readycheck.reason`, `approval.reasonOf(…, true)`), `finish` refuses a changed contract, and `done` refuses a changed contract but lets a member with no approval on `origin/main` land. After f0399:

- **ready** asks for no approval. `readycheck.reason` loses that step (it still builds the contract, so a contract that cannot be built still refuses). `ready` writes `lands: approved` into the raft's frontmatter in its one ready commit. `publish.movedEdit` compares a raft document without its `status:`, `lands:` and `on:` lines (section 6), so the move may add them; for an issue document the rule is unchanged.
- **finish**, on a raft with `lands: approved`, does not refuse a member whose approval does not hold. It prints `note: <id> is not approved (<no approval | changed: <parts>>): <R> will wait for ./zn approve <id> before it lands`. On a raft without the line it refuses as today.
- **done**, on a raft with `lands: approved`, refuses unless every member's approval holds in the tree it lands, naming all of them in one message: `<R> waits for approval: <id> (no approval), <id> (changed: guesses, design). The person runs ./zn approve <id> in this worktree; ./zn guesses <R> lists what to review.` On a raft without the line it behaves as today (an approval on `origin/main` must hold, a member with none is left alone), so the six active rafts readied before approvals existed (R0061, R0068, R0070, R0073, R0078, R0084) and every existing fixture that starts a raft without `ready` land as they do now. **Guess (prep) G4.**
- **The whole raft waits** for its last unapproved member: `done` lands all layers or none, as today. **Guess (prep) G5.**
- **approve for an active issue.** The person runs `./zn approve <id>` in the raft's worktree (`./zn worktree <R>`), on the layer checked out there. It commits `approval.md` on that layer, as today's command does in any worktree; nothing about who may run it changes (a terminal on stdin, never under `ZN_DISPATCH`). For an issue in `active/` its last line becomes `It lands with <R>: nothing to publish.`, and `./zn approve <id> --publish` refuses there: `<id> is active in <R>: its approval lands with the raft`. An issue still in the backlog is approved and published as today. **Guess (prep) G6.**
- **A layer stays finished.** `layergit.isPostFinishPath` also accepts `approval.md` and `guesses.md` in any issue's folder (`…/issues/active/<id>/approval.md`, `…/issues/<id>/approval.md`, and the same for `guesses.md`), so the approval commit, and a guess recorded while answering the code review, do not turn a finished layer back into an unfinished one.
- `./zn land` (a capture) is unchanged.

### 4. What `./zn work next` picks with no raft named

`work.luau` (pure). `Input` gains `issues: { IssueFact }?`, and `RaftFact` gains optional fields, so every existing literal still type-checks:

```luau
export type IssueFact = {
	id: string,
	root: string, -- the project's tracker root
	status: string, -- the effective status: new, preparing, prepared, active, done, closed
	raft: string, -- "" when it is in none
	designReady: boolean,
	sized: boolean, -- has a size: z-raft can use
	deps: { string }, -- depends_on
	draftBlock: string, -- "" when z-design's claim gate accepts it (idea.designRefusal), else its reason
}
-- RaftFact, new optional fields:
--   lands: boolean?     the raft document has `lands: approved`
--   on: string?         the raft it is built on (`on: R0100`), nil when none
--   unapproved: { string }?   "<id> (<why>)" for each member whose approval does not hold; read only
--                             once the final review is approved, else nil
--   outside: { string }?      depends_on ids of its members that are not members
export type Decision = { raft: string, layer: string, ticket: string, action: string, why: string } -- unchanged
```

**Unmet dependency.** An issue has one when a `depends_on` id is not in `done/` on `origin/main`; a raft has one when any member has one outside the raft. This is the capture's definition.

**The order** (`work.decide`, no raft named; the count of releases in a row is checked first, as today). The first that exists is the pick; inside one line the lowest id wins (`work.rankKey`, which c0249 replaces):

Tier 1, nothing unmet:
1. **done**: an active raft this author holds whose next action is `done` (it waited for an approval and now has it).
2. **ready**: a backlog raft `ready` would accept (`block == ""`).
3. **rafting**: a backlog issue that is `prepared`, `design: ready`, sized and in no raft.
4. **draft**: a backlog issue that is `new`, in no raft, with `draftBlock == ""`.

Tier 2, something unmet, only when tier 1 has no pick:
5. **ready** `--on <D>`: a backlog raft whose only refusal is its unmet dependencies, when all of them are members of one active raft `D` whose every member has a finished layer (section 6).
6. **rafting**: as 3, when every unmet dependency is `design: ready` (prepared, active or done).
7. **draft**: as 4, when every unmet dependency is `design: ready`.

This is the capture's order: the tier wins, and inside a tier the ticket furthest along is first (a raft to land, a raft to ready, a prepared issue, an issue to design). **Guess (prep) G10, G11.**

What is never picked without being named, each with a reason line (below): an issue that is `preparing` and a raft that is active and not at `done` (another session, or this person's earlier one, may hold it; takeover is c0265's) (**G13**); an issue whose idea was not challenged or has an unruled bullet (**G7**); an issue with no `size:`; anything closed; a c0394 added issue (`waits:` in its frontmatter), which keeps c0394's rule (**G15**).

**The actions' lines.** An issue-level pick has `raft = ""` and `ticket = <id>`, and `work.say` prints `<id>: <action> - <why>` for it (today's `nothing: …` form is only for `none`):

- `draft`: `Design <id> in guess mode (z-design): ./zn status <id> preparing in a prep worktree, record every open choice with ./zn guess, merge the prep pull request when it is green, then ask again.` For tier 2 it adds `It depends on <ids>, not landed: design from their documents, and run prototypes on <branch | their designs: no branch yet>.`
- `rafting`: `<id> is prepared and in no raft. Run z-raft with no argument in guess mode (./zn raft-plan --apply), merge the rafting pull request when it is green, then ask again.`
- `ready`: today's line; for tier 2, `… run ./zn ready <R> --on <D>, then ask again.`
- `wait` (new, from `work.forRaft`, after the final review is approved and the trace passes): `<R> waits for the person: ./zn approve <ids> in its worktree; ./zn guesses <R> lists what to review. Tell the person, then ask again with no raft.` The same action, with `<R> is built on <D>, which has not landed.`, when everything is approved and the raft it is built on is not done.
- `done`, `implement`, `finish`, `restack`, `review`, `trace`, `final-review`, `release`, `end`: unchanged, except that the review line's `Do not guess a ruling.` becomes `Do not guess a ruling under ./zn dispatch; otherwise answer an open ruling with a recorded guess (./zn guess).`

`work.forRaft(r)` gives `wait` where it gives `done` today when `r.unapproved` is not empty, or when `r.on` names a raft that is not done. A raft without `lands` never has `unapproved` filled, so it goes to `done` as today.

**Naming an issue.** `./zn work next <issue-id>` and `./zn work <issue-id>` are accepted (`^[fdc]%d%d%d%d$`). `work.forIssue(i, rafts)`: an issue in a raft gives that raft's action; `new` gives `draft` (or `none` with `draftBlock`); `preparing` gives `draft` with `<id> is being designed: resume its prep worktree`; `prepared` with no raft gives `rafting`. Naming is how a held design is resumed, as naming a raft resumes a held raft.

**When nothing is picked**, the head line stays `nothing to do - no claimable raft[ in <project>]` and the reason lines follow as today. `work.skipped` keeps one line per raft, and `work.skippedIssues(issues, all)` adds one per backlog issue in no raft that was not picked (`issues` is the project's, `all` is every issue, since a dependency may be another project's): `<id>: is being designed (preparing): name it to resume`, `<id>: its idea needs the person (<draftBlock>)`, `<id>: has no size:`, `<id>: depends on <dep>, which is not designed`, `<id>: depends on <dep>, which is in no active raft with every layer finished`. A raft at `wait` prints `<R>: waits for approval: <ids>`. `./zn work queue` prints the same lines. `./zn work status` adds ` waits for approval: <ids>` to the row of a raft at `wait`.

**After a pick.** A `wait` is not a release: the session says what waits and asks again with no raft. A `draft` the worker gives back (section 7) counts as a release, so two in a row stop the session as two blocked rafts do (**G18**).

**Reading the facts** (`workread.collect`). The issue documents of every issue not in `done/` are already in its one `cat-file --batch`; it adds each `new` raftless issue's `idea-review-001.md` to that batch and builds the `IssueFact`s from them (`idea.designRefusal` for `draftBlock`, `raftplan.parseSize` for `sized`). `lands` and `on` come from the raft document it already reads. `unapproved` is read only for an active raft whose final review is approved: one `git ls-tree -r` of the top layer's tip under each member's folder and one `cat-file --batch` for the documents, `check.sh`, specs, `guesses.md` and `approval.md` there, judged by `approval.reasonOf`. The base raft's state (for `on`) is in the facts already.

`dispatch.next` is not changed, and the spec that holds the two decisions to the shared facts still holds: a prepared backlog raft is `ready` here and `z-ready` there (the dispatcher's own approval stop is c0267's).

### 5. z-raft bundles a ticket with what it depends on

`raftplan.Issue` gains `deps: { string }?` (its `depends_on`), filled by `cmd.raft-plan`. `raftplan.plan`:

- **features**: two candidates, or a candidate and an open prepared backlog raft, are also joined when one depends on the other (or on a member of that raft), whether or not their Touched paths overlap.
- **chores and defects**: candidates are placed in dependency order (an issue after the candidates it depends on, lowest id first among the free). An issue that depends on an issue already in a bin goes into that bin; otherwise the first bin that fits, as today.
- **the cap never splits a dependency**: an issue joined to a raft by a dependency is placed there even when the sum passes `raftplan.CAP`. (The user, memory of 2026-11: "stack dependencies in one raft".)
- unchanged: one type and one project per raft, a `solo: true` or over-cap issue is a raft by itself, a `single: true` raft takes nothing, and only a prepared backlog raft is folded into.

So "z-work puts a ticket and the tickets it depends on in one raft" holds for a dependency of the same type and project that is not yet readied. A dependency of another type or project, a solo one, or one already in an active or done raft, stays in its own raft, and the dependent's raft is built on it (section 6). **Guess (prep) G12**, from the user's standing rule "never mix c/f/d" in one raft.

### 6. A raft built on a raft that has not landed

**`./zn ready <R> --on <D>`** readies `R` although members depend on issues that are not done. It accepts when: every dependency of `R`'s members outside `R` is done or a member of `D`; `D` is active on `origin/main`; and every member of `D` has a finished layer (`layergit.layersOf(D)`, `layergit.layerFinished`). It writes `on: <D>` beside `lands: approved` in the ready commit. Refusals, each naming the rule, checked in this order: `--on <D>: <D> is not an active raft`; `--on <D>: nothing in <R> depends on <D>`; `--on <D>: <m> depends on <x>, which is not done and not in <D> (a raft is built on one raft)`; `--on <D>: <D>'s layer for <x> is not finished: <R> can be built on <D> once every layer of <D> is finished` (a member of `D` with no layer yet is not finished). `readycheck.reason` takes the base's members as done for the dependency rule (`Raft.onMembers: { string }?`). Without `--on`, `ready` is today's and removes a stale `on:` line.

**`layergit.raftBase(raft): (string, string)`** is the one place that says what a raft's lowest layer sits on: the tip sha and the pull-request base. With no `on:`, or when the raft `on:` names is in `rafts/done/` on `origin/main`, it is `layergit.mainTip()` and `main`. Otherwise it is the tip and the branch name of the base raft's top layer. Every site that takes `mainTip()` as a raft's base asks it instead: `layergit.startLayer` (layer 1's start point, pull-request base and the `belowBase` of layer 2), `cmd.finish`, `cmd.restack` (both uses), the trace's two walks (`traceProblems`), `cmd.done`'s walk, `workread`'s `stacked`, and `./zn stack`, which prints `built on <D> (<branch>)` above the rows.

- **start, finish, the reviews, the trace** then work on `R` as on any raft: its layer 1 is cut from `D`'s top layer, its pull request is based on that branch, and each diff is `R`'s own. One rule of `start` changes with it: `cmd.start` refuses a member whose `depends_on` outside the raft is not done ("it must be done first"), and for a raft with `on:` it takes the base's members as done, as `ready --on` did.
- **done** refuses while the base has not landed: `<R> is built on <D>, which has not landed: ./zn done <D> first, then ./zn restack <R>`.
- **restack**, once `D` is done, moves `R` onto `main`: `raftBase` now says `main`, and today's rebase (`stack.rebaseUpstream`: the parent of the layer's finish commit, or of its `tracker: start`) carries only `R`'s commits (E1, run). It retargets layer 1's pull request to `main` (`gh pr edit <n> --base main`; a failed edit warns, as the other body edits do). As after any restack today, `work next` then asks again for whatever the rebase made stale (the trace's check, E7) before `done`. While `D` is unlanded and its top layer moved (a fix, a restack), `R` is not stacked and `work next` says `restack`, which rebases `R` onto `D`'s new tip the same way.
- **stop**: `./zn stop <D>` is unchanged and leaves `R` as it is (its branches still exist); `R` then waits (`built on <D>, which has not landed`) until `D` is readied and landed again. `./zn stop <R>` is unchanged, and the `on:` line stays in the document until the next `ready`.
- A chain works: `R` on `D` on `E`. Each is landed in turn.

The prep of an issue with an unmet dependency is a prep worktree from `main` as always (a prep pull request holds only tracker files). Its prototypes and experiments, which need the dependency's code, run in a scratch worktree cut from the dependency's layer branch when it has one. **Guess (prep) G11.**

### 7. The skills

Each skill gains its guess-mode text beside the rule it relaxes; the dispatcher's "Headless" section, identical in four skills and pinned, is not touched.

- **z-work**: step 1 names the actions `draft`, `rafting` and `wait` and that an issue may be named. Step 5 becomes: a human decision is answered with a recorded guess and the work goes on; **blocked** is only the same check failing after a real second attempt, a missing credential, or a choice that would drop or shrink a captured outcome (**G9**: only the user changes scope). Step 6 gains `wait`: tell the person which issues wait and print `./zn guesses <R>`, then ask again with no raft. Step 10's "Left for later" loses nothing but says rank is still c0249's. A new section, **Guess mode**, holds the rules every other skill points to: what a guess is, `./zn guess` at the moment of the choice, the three steps, never guess under `ZN_DISPATCH`, never guess an idea's open line, never guess a scope cut, and the pause before landing.
- **z-design**: a section **Guess mode** before "Headless". A `draft` from `./zn work next`, or the user's say-so, turns it on: every question the skill tells the designer to ask the user becomes `./zn guess <id> --step design` plus a **Guess (prep) Gn** mark at the sentence it decides; an open-list bullet gets a `Guessed (agent, …): Gn` line (step 5.4's "do not guess a ruling" keeps its meaning outside guess mode); the worker does not stop for `./zn approve` (step 5.5) and merges its own green prep pull request (the user started the worker, as under the dispatcher: **G14**); the report lists every guess. A question guess mode may not answer (a scope cut) is written as an open bullet in the document, published by a tracker pull request, and the claim is given back (`./zn status <id> new`): the claim gate then keeps the issue from being picked again until the person rules.
- **z-raft**: guess mode for a coherence review's open bullets (`./zn guess <member> --step raft`, `Guessed (agent, …): <member> Gn`) and for merging its own green rafting pull request; the policy paragraph gains section 5's dependency rule.
- **z-ready**: step 2's approval sentence becomes "an approval is not needed to ready a raft; `done` asks for it"; `--on <D>` and when `work next` offers it.
- **zz-execute**: the stop conditions keep "would drop or shrink an outcome" and say that any other human decision is a recorded guess in guess mode (`--step build`); Phase 4's open rulings may be guessed; Phase 5 ends at `wait` when a member is not approved, with a report line `Waiting for approval: <id> (<n> guesses; <changed parts>) | none`; `./zn approve` for an active issue is run in the raft's worktree.
- **zz-review**: design and code mode read `guesses.md`; a guess with no evidence, or one that drops or shrinks a captured outcome, is a finding.
- **zz-rules**: the `approve`, `ready`, `finish` and `done` rows say where approval is checked; new rows `guess` and `guesses`; `work` gains the issue id; Items gains `guesses.md` and the frontmatter lines `lands:` and `on:`.
- **AGENTS.md** and **z-nile/README.md** (The worker): one sentence each, that with no raft named the worker also designs and rafts, on recorded guesses, and that nothing unapproved lands.

### 8. Edge cases

- No issue facts (`Input.issues == nil`, every existing caller and spec literal): the picks are today's.
- A raft with `lands: approved` and no guess, every member approved before `ready`, nothing changed: no `wait`; it lands as today.
- An approval made on the layer, then a new guess: the approval no longer holds and `wait` comes back, naming `guesses`.
- Two sessions of one person both offered the same `done`, `rafting` or `draft`: the second's `./zn done`, fold or `./zn status <id> preparing` is refused on `origin/main` as today, and it asks again.
- `--on` a raft that is then stopped, or whose layers are rebuilt: covered in section 6.
- A dependency ring between two rafts: neither is in tier 1 and neither base has finished layers, so neither is offered; the reason lines name the dependency.
- A prepared issue whose dependency is a c0394 added issue: treated as any unmet dependency.
- `guesses.md` that does not parse: `approval.collect` fails, so `approve`, `ready`, `finish` and `done` name the file and the problem; `./zn guesses --check` finds it first.
- `./zn guess` on an issue in `done/`: refused (`<id> is done: nothing left to guess`).

### 9. What the prepared tickets meet (not edited by this issue)

### Scalability
`work next` with no raft named makes the git calls it makes today plus blobs in a batch it already runs (one `idea-review-001.md` per `new` raftless issue: 34 today). The approval read of an active raft is two git calls, made only for a raft whose final review is approved (at most a few at a time). The picks are one pass over the issues and one over the rafts, with a dependency lookup by id. `raftplan.plan`'s dependency join is one pass over each candidate's `deps`. `raftBase` is one frontmatter read and, for a raft with `on:`, one `git cat-file -e` on `origin/main` and the base's `layersOf`.

### Maintainability
One reader per thing: `guesses.luau` for the file, `contract.build` for what an approval covers, `openlist` for the three kinds of bullet, `layergit.raftBase` for what a raft sits on, `work.decide` for the order (the skill carries none of it). A new step of the pipeline is one more numbered line in `work.decide` with its `why`. A new thing an approval must cover is one more optional part in `contract.build`.

### Usability
New command line: `guess <issue-id> --step design|raft|build --open <text> --chose <text> --why <text>`, `guesses <issue-id|R-id> [--check]`, `ready <R-id> --on <R-id>`, `work [<R-id>|<issue-id>]` and `work next [--released <n>] [<R-id>|<issue-id>]`. Each joins the usage text; `guesses` joins the read-only set; `guess` joins the commands refused in the main checkout. Every refusal above names the item and the rule. The person's whole part is: read `./zn guesses <R>`, run `./zn approve <id>` for each issue named, and the next `./zn work next` lands the raft.
