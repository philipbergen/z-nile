### F1 [high] The claim publishes the `rounds: on` mark itself, so `origin.restartable` is already false when the claim's new-loop line is checked, and c0161's re-prep is refused at `status prepared` and by the dispatcher
Where: f0417.md **The cut-over** (Writers: "The claim's published commit carries it"; **Where a loop starts**: "the issue is adopted by this claim's mark and its folder already holds one-round-era design reviews … writes `- Loop (tool, <today>): a new design loop from design-review-<next>` in the claiming worktree, carried by the prep pull request"); **Who may write a `## Loops` line** (`origin.restartable` "true when origin/main's copy is unmarked … the callers compute both from origin/main through `roundread`"); Rules row "the claim of a restartable loop … writes the new-loop line" (reasoned).

Every caller of `loopsProblem` (`status prepared`, `dispatch.filingFor`'s caller, `completion.layer`'s caller) runs after the claim and reads origin/main, which by then holds a marked copy. So the adoption branch ("origin/main's copy is unmarked") is never true when it is checked. In that case `restartable` falls back to the loop over origin's files. Probe on the prototype over c0161's real folder (`active/c0161`, seven `changes` rounds, each answered): `rounds.state` gives `kind next, count 7, next 8`, which is neither ended nor cap. `rounds.loopsProblem(doc, doc + "- Loop (tool, …): a new design loop from design-review-008", { highest = { design = 7 }, restartable = false })` returns "## Loops line '- Loop (tool, 2026-11-20): a new design loop from design-review-008' is not on origin/main and no command of the person wrote it". If the line is dropped instead, c0161 gets two rounds before the cap, which is round 3 F4's defect. Yet cli.spec's "a new stub is marked, and a claim marks an older issue on origin" already claims c0030 and runs `status prepared` on it. Seeding that issue with a `design-review-001.md` on origin is the whole fixture.
Critique: a precondition read from origin/main after the command that changed origin/main judges the state the command produced, not the one it started from. The tempting fix is to compute "unmarked" from the claim commit's parent. That ties every caller to finding the claim commit in history (squash merges, renumbering), which is the history read c0260 refused for its own mark ("the mark is read from the issue, never from history").

Cases:
- cli.spec: an older unmarked issue with `design-review-001.md` (`changes`, answered) on origin is claimed. Origin then holds `rounds: on` and `a new design loop from design-review-002`. An approving `design-review-002` in the worktree passes `status prepared`, and the same document without the line is refused.
- marks.spec: the claim's line is accepted; a line with another number, a second line, or a `one more` line is refused.
- rounds.spec: a design line not in `base` is refused whatever `origin` says.

### F2 [high] What makes a loop restartable is computed by no specced function, so a wrong rule passes check.sh; and a cap closed by Guessed lines falls outside it (repeat of design-review-003 F3)
Where: f0417.md **Who may write a `## Loops` line** (`origin.restartable`: "`ended`, or `cap` with every `human` entry ruled … the callers compute both"); rounds.spec "a Loops line counts only when origin holds it, or it is a tool line whose precondition origin holds" (passes `restartable = true|false` as a literal); Rules rows M59 and 443; **At the cap** (guess mode: a design bullet gets a Guessed line and the work goes on); **`rounds.gate`** (Guessed passes for design).
Evidence: round 3 F3 asked for a case where "a ruled cap accepts the claim's line … an unruled cap refuses it". No such case exists. `restartable` is a boolean the spec hands in, and the prototype has no function that computes it (`grep -rn restartable z-nile/engine` in the prototype finds only `loopsProblem`'s parameter). Two wrong implementations pass every case of check.sh:
- `restartable = kind == "ended" or kind == "cap"`. This brings back round 3 F2: an unruled dispute at the cap is escaped by a re-claim.
- `restartable = kind == "ended"`. This brings back round 3 F3: a ruled cap is prepared again with no review.
The Design also says "ruled by the person". In guess mode, a design cap whose leftovers carry Guessed lines passes `rounds.gate`, and the issue is prepared. If that issue is later unfolded and re-claimed for a redesign, the cap is not restartable. The claim writes nothing, `rounds.filing` refuses every round ("cap"), and `rounds.gate` passes on the old Guessed bullets. That is round 3 F3's "redesign prepared with no review", reached through Guessed lines instead of Ruled ones.
Critique: the rule that round 3's F2, F3 and F4 all rest on lives only in prose and in an unwritten caller. Writing "ruled or guessed" into the prose is the tempting fix, and it would still be unpinned.
Consequences: one pure function makes the claim (F1) and any later reader agree. Basing it on `rounds.gate` makes "done with" mean the same thing in both places: ended, or a cap whose entries are ruled or, for design, guessed. A Guessed cap that restarts leaves its old bullets outside the new window. They stay in `guesses.md`, which the person approves before anything lands, so nothing is hidden.
Recommendation: add `rounds.restartable(list, window, doc, marked: boolean): boolean`, pure. It returns true when the issue is unmarked and its folder holds a design round (the adoption), or when `rounds.gate("design", list, window, doc)` is nil. The claim calls it on origin/main's files before its own commit (F1). rounds.spec cases:
- an ended loop: true;
- a cap with its high ruled: true;
- the same cap with the bullet missing or unruled: false;
- a cap with a Guessed bullet: true;
- a dispute in `human` mid-loop (`next`): false;
- an unmarked issue with one `changes` round: true;
- an unmarked issue with no round: false.
Add Rules rows with the mutants "ended only" and "any cap", both run.
