### F1 [high] A `## Loops` line removed from the branch's copy (or missing from a copy not synced) moves the window back, so a redesign or a changed ask passes on the old loop's approval
Where: f0417.md **Who may write a `## Loops` line** ("refuses every `## Loops` line of `doc` that is not in `base`"); **A loop's window** (`rounds.window(doc, stage)` reads the document it is given); **The dispatcher** ("for a code review, `doc` is the layer's issue document (where `resolve retry` writes its `one more code round` line…)"); **The cut-over**, Never removed (only the `rounds: on` mark is protected); prototype `rounds.luau:365-400` (the loop is `for _, line in loopLines(doc)` only); rounds.spec "a Loops line counts only when origin holds it…" (no removal case).
Evidence: an issue's design loop ended at `design-review-002` (approve). Later the issue is re-claimed, and the claim publishes `- Loop (tool, 2026-11-20): a new design loop from design-review-003` (G31). The author redesigns and rewrites the document, and the rewrite leaves out the `## Loops` section. Nothing restores it: the section is tool-written and sits at the end, below everything z-design edits. `status <id> prepared` then calls `rounds.loopsProblem(base, doc, …)`. That function walks only the lines of `doc`, so it returns nil. `rounds.window(doc, "design")` finds no line, so `from = 1`. `rounds.state` reads rounds 001-002 and returns `ended`, `rounds.gate` returns nil, and the redesign is prepared on the approval of the design it replaced. G31 exists to stop exactly that ("So a redesign is never prepared on an approval of the design it replaced"). The same removal works for the other new-loop lines:
- idea, after the ask changed: the old ended idea loop counts, so the changed ask is never challenged;
- design, after `amend-design`'s line or `refuse --to design`'s line: the redesign is never reviewed.

The same gap arises without anyone removing a line. `resolve retry` publishes `one more code round past review-009` to origin/main, but a layer branch parked before the resolve does not hold that line until it is synced. If `doc` is the branch's copy, the person's retry grants nothing and the dispatcher refuses at the cap. If `doc` is origin's copy, the dispatcher and `completion.layer`'s caller read a different copy than `status prepared` does. The Design names neither copy.
Critique: G28 and G31 make origin/main the only judge of which lines count, but the check compares in one direction only. A line origin holds and the branch lacks is as much a branch-written state as a line the branch added. The tempting fix is to add "keep the `## Loops` section" to z-design. That leaves the gate trusting the branch's copy.
Consequences: refusing a missing line also covers the copy that was never synced: the refusal tells the worker to sync before it can go on. Lines are only ever added (no tool removes one), so the refusal never fires on a legitimate edit. Reading the window from origin's copy instead would also work, but it changes `rounds.window`'s inputs at every caller and spec. The refusal leaves them as they are.
Recommendation: `rounds.loopsProblem` also refuses every `## Loops` line of `base` that `doc` does not hold, with the words "<id>: ## Loops line '<line>' is on origin/main but not in this copy: ./zn sync (a Loops line is never removed)". State this beside Never removed, and say that `doc` is the copy each caller reads the window from (the worktree's). Add these cases:
- rounds.spec: `loopsProblem(base, base minus its new design loop line, …)` names the line; `base` with an extra origin line that `doc` holds is nil.
- cli.spec: after c0060's claim, remove the line from the worktree copy and set `design: ready`. `status c0060 prepared` is refused naming the line. With the line restored, it is refused because the next round is `design-review-002`.

Add a Rules row with the mutant "removed lines ignored", run.
