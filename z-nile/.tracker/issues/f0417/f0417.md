# f0417: Rounds to merge ready

## Problem
- Every review at the idea, design and implementation stages stops after one round, and the engine refuses a second ("there is no second round"), though no ticket or owner decision asked for that (PR #292).
- `./zn idea` challenges an idea once and revises once, and c0260's unbuilt design caps the idea loop at 3 challenges where the owner asks for 5.
- z-work never runs the idea stage: it skips a new ticket whose idea needs the person, so it cannot carry an idea to merge ready.
- A human cannot approve an idea or an assumption today: assumptions are free text under "Unknowns & experiments" with no record of their own, and the approved hash names neither them nor the idea's files (the ask, the idea review and its answers).
- The final review reads the full raft and issue documents with their whole trail, and does not check approvals; only `./zn done` does.
- Nothing built sends a refused ticket back to be reworked: c0250's blocked state and `./zn resolve` are unbuilt, and its `review-exhausted` reason presumes several rounds.
- c0161 (active in R0080) cannot be built while reviews are one round.

Decided with the user (2026-11-20): "Review rounds should be toml config" and "toml should have a setting for easy, normal, risky" (the most rounds a review may run is read from TOML: one number per stage (idea, design, implementation) for each of three risk levels, easy, normal and risky. A change that is low risk and easily fixed or reverted gets just a few; one that is complex, large and not easily reverted is allowed more. The numbers are maximums: the skills say so, and say the reviewer is expected to find everything in the first round. The idea cap is configured the same way: "configurable, ideally just one round". This replaces this ticket's fixed 5, 9 and 9, and c0260's cap whatever its number. This ticket owns the rule and overrides every one-round pin, including c0251's AC7, AC11 and AC21, c0306's "only when the newest one is off the review models", and c0166's five-round note, which its Overrides line and depends_on did not name.)

Decided with the user (2026-11-20): "Does the worker wait for approval: No! Optimistically keep working through everything" (the worker never waits for an approval and never sets a ticket aside for one. It records each guess and assumption it makes and keeps building. An unapproved guess or assumption stops one thing only: the ticket cannot go to the final gating review, and waits there for the person's approval. This confirms this ticket's rule over c0253's and c0267's, and names where the wait is: before the final gating review, not only before the landing.)

## Non-goals
- No model assignment changes: `.models.toml` already runs implementation on a lesser model (Sonnet 5.5) than design (Opus 5.5).
- This ticket does not redesign what c0260, c0262, c0250, c0161 or f0399 already design or deliver; it covers only what they leave out or contradict.
- Building before approval (`Lands: approved`) stays as it is; z-work never waits for approval before merge ready.
- No round runs once the reviewer has no open finding: the caps are upper bounds, not required counts.

## Solution
- A review at each stage goes back and forth between the author and a clean adversarial reviewer until the reviewer has no open finding or the cap is reached: 5 rounds for the idea, 9 for the design, 9 for the implementation.
- The idea loop runs up to 5 rounds, each finding going back to the idea agent or the human, and c0260's cap of 3 is changed to 5.
- `./zn work next` runs the idea stage for a new ticket and carries it through design, rafting, ready, build and review to merge ready without waiting for approval.
- Each assumption has a record of its own, and the hash a human approves names the idea's files, every guess and every assumption.
- The last gate is given only the idea, the design and the diff, judges whether the implementation matches the idea, and refuses unless a human has approved the idea, the design, every guess and every assumption.
- A raft lands only once those approvals hold, and a refusal by the human or the last gate returns the ticket to rework through c0250's blocked state, whose `review-exhausted` reason fires when a stage reaches its cap with findings open.
- c0161 is unblocked once the design stage runs more than one round.

### The round rule (S1): `z-nile/engine/rounds.luau`, new, pure (**Guess (prep) G1**, **Guess (prep) G2**, **Guess (prep) G3**, **Guess (prep) G4**, **Guess (prep) G5**)
One module says what a loop is, for all three stages, so the dispatcher, the claim gate, `status prepared`, c0248's layer completion, `work next` and the skills agree.
```lua
export type Stage = "idea" | "design" | "code"
rounds.CAP = { idea = 5, design = 9, code = 9 }
rounds.PREFIX = { idea = { "idea-review-", "idea-refute-" }, design = { "design-review-", "design-refute-" }, code = { "review-", "refute-" } }
export type Finding = { id: string, severity: string, repeatOf: string?, ask: boolean }
export type Round = { n: number, findings: { Finding }, verdict: string?, answers: { [string]: string }?, current: boolean?, interview: number? }
-- answers: finding id -> "fixed" | "refuted" | "deferred" | "revised" | "disputed" | "other"; nil when the round has no refute file
-- current: false when c0248's stamps say a code round reviewed an older patch than the layer's (nil: current)
-- interview: the idea round's `Round: … interview <q> …` count (c0260), nil for other stages
export type Window = { from: number, extra: number }
export type State = { kind: string, count: number, cap: number, last: number, next: number?, human: { string } }
function rounds.marked(doc: string): boolean
function rounds.read(stage: Stage, n: number, review: string, refute: string?): Round
function rounds.window(doc: string, stage: Stage): Window
function rounds.state(stage: Stage, list: { Round }, window: Window, doc: string?): State
function rounds.filing(stage: Stage, list: { Round }, window: Window, doc: string?): { number: number?, refusal: string? }
function rounds.gate(stage: Stage, list: { Round }, window: Window, doc: string): string?
function rounds.loopsProblem(base: string?, doc: string, highest: { [string]: number }, askGrew: boolean): string?
function rounds.restartable(list: { Round }, window: Window, doc: string, adopting: boolean): boolean
```
- **Caps** (G1): `rounds.CAP` is the one place the owner's numbers live; `idea.MAX_ROUNDS` becomes `rounds.CAP.idea` (**The idea loop**). They are constants, not `.models.toml` settings: that file holds models, and "Nothing defaults" there (`z-nile/skills/zz-rules/SKILL.md`, Dispatch); a change of cap is a reviewed pull request either way.
- **`rounds.read`** parses one round with the existing readers: `openlist.findings` and `openlist.answerKind` for design and code (`### F<n> [severity] <claim>`, `- F<n>: fixed|refuted|deferred …`), `idea.parseReview` for the idea's review (`- F<n>: <words>`; severity `unrated`; a finding whose words start `ask:` has `ask = true`, c0260's question for the person) and, for its refute, the file's own `- F<n>: revised|disputed: …` lines (the shape `idea.refuteText` writes; `idea.parseAnswers` reads a model's `## Answers` section, not the file). `repeatOf` is read from a claim that contains `(repeat of <prefix>NNN F<m>)`. `verdict` is the `Verdict:` word (design and code) or the `## Verdict` word (idea). The caller sets `current` for code rounds from c0248's stamps through one function, `roundread.current(review, refute, finishSha, patchId)` (c0248's `Commit:`/`Patch:` reading), which `workread`, `completion.layer`'s caller and `dispatch.filingFor`'s caller all use. For the idea, `interview` is the count c0260's `Round:` line records. Design rounds carry no currency here (**Guess (prep) G27**): a Design edited after an approving round is c0161's design record to catch (**c0161**); f0417's skills say it needs a new round.
- **A loop's window** (G4, G22, G28): the rounds of a stage numbered at or above `window.from`. `rounds.window` reads only the `## Loops` section: the highest NNN of a `a new <stage> loop from <prefix>NNN` line is `from` (with none, 1), and each `one more <stage> round past <prefix>NNN` line whose NNN is at or above `from` adds 1 to `extra`. The cap of the window is `CAP[stage] + extra`.
- **Who may write a `## Loops` line** (**Guess (prep) G28**, its claim rule superseded by **Guess (prep) G31**): a line grants rounds or moves a window, so it counts only when `origin/main` holds it. `rounds.loopsProblem(base, doc, highest, askGrew)` (pure; `base` is origin/main's copy of the document, nil for a new item; `highest` the highest round number of each stage in origin/main's folder) refuses every `## Loops` line of `doc` that is not in `base`, except a `a new idea loop from idea-review-<highest.idea + 1>` line when `askGrew`, and every line of `base` that `doc` lacks ("<id>: ## Loops line '<line>' is on origin/main and not in this copy: ./zn sync"), so a copy that dropped or never synced a line cannot fall back to an older window (the document's `## Ask (verbatim)` holds more `### Message` blocks than `base`'s: the person's new words, c0260's `--record`). Every other writer publishes its line to `origin/main` before anything reads it: the person's `resolve` and `refuse`, and the claim, which publishes its one new-design-loop line in the claim commit itself (below). `status prepared`, `completion.layer`'s caller, `dispatch.filingFor`'s caller and `idea.designRefusal` call it before they read the window, and refuse with its words ("<id>: ## Loops line '<line>' is not on origin/main and no command of the person wrote it").
- **When a loop may restart** (G31, **Guess (prep) G32**): `rounds.restartable(list, window, doc, adopting)` (pure) is true exactly when `rounds.gate` over that stage passes (the loop `ended`, or its cap's leftovers are ruled or, in guess mode, guessed: whatever let the design be prepared lets its redesign start a new loop, so a redesign is never prepared on an old loop's gate); or `adopting` (the claim adds the mark to an issue origin/main holds unmarked) and the folder holds at least one design review. The claim reads origin/main's design rounds and document, decides `restartable` before it publishes anything, and when it is true publishes `- Loop (tool, <today>): a new design loop from design-review-<highest + 1>` under `## Loops` in the same commit as its status line and mark (`publish.claimMarks` accepts exactly that one added line).
- **`rounds.state`** over the window's rounds, newest last (`count` rounds, `last` the newest number); `doc` (when given) is read for the person's rulings through `openlist.sourced` (below):
  1. none in the window: `kind = "none"`, `next` = one past the highest number of the stage in the folder (or `from`).
  2. **ended** (G2): the newest round's verdict is `approve`, it is current (a round with `current == false` is never ended), and, for design and code, every finding of it is answered and none is answered `fixed` (an approving round's low findings answered by a refute keep it final; answered by an edit, they need another round); for the idea, it has no finding at all (c0260's rule: "an approval that still lists a finding does not end the loop"; an approving round whose only findings are asks is `person` until the Interview answers them, then `next`, so the person's answer is itself challenged).
  3. idea only: `count >= cap` → `cap` (c0260: the last challenge is never followed by a revision).
  4. a finding of the newest round that is not an ask has no answer (design and code: no refute line; idea: findings other than asks and no refute file): `answer`.
  5. idea only: the newest round's only findings are asks (whatever its verdict) and the document's `## Interview` holds no more `### Q` questions than the round's `interview` count: `person` (the next round waits for the person's answer; c0260 records that answer, and its ruling, as the next `### Qn`).
  6. `count >= cap`: `cap` (a newest round that is not current adds `<prefix>NNN stale` to `human`: a rebuilt layer at the cap is the person's).
  7. otherwise `next`, `next = last + 1` (a code round that is not current is `next` even when it approved).
  `human` lists, as `<prefix>NNN F<n>`, every finding that must go to the human: in any kind, a finding that repeats an earlier refuted finding (`repeatOf`) and is refuted again (a dispute two reviewers and the author could not settle: G3); in `cap`, also every finding of the newest round that is high (whatever its answer: no reviewer will verify the fix), refuted, deferred or unanswered, and, for the idea, every finding of the last challenge (c0260 F1).
- **`rounds.filing`**: `none` and `next` file `next`; `ended` refuses ("<prefix>NNN approved with no open finding: the loop ended"); `answer` refuses ("answer <prefix>NNN first: every finding fixed or refuted in <refute-prefix>NNN"); `person` refuses ("<prefix>NNN asks the person: <ids>; the next round waits for the answer"); `cap` refuses ("the <stage> cap of <cap> rounds is reached: what is open goes to the person (## Open to the human, ./zn block <id> review-exhausted); only the person's ./zn resolve <id> retry grants another round").
- **`rounds.gate`**: nil when the stage is done with, else the refusal, which names the state and its file: `next` or `none` → "the next round is <prefix>NNN", `answer` and `person` → `rounds.filing`'s words, `cap` (and `ended`) with an entry not answered → "<entries> wait for the person under ## Open to the human". Done with is `ended` or `cap`, with, for design and code, every `human` entry answered by a bullet `openlist.sourced` reads that is ruled or guessed; for the idea, the open list is c0260's (its writer renumbers the leftovers and asks F1.. with no source, and rewrites the list each pass), so the gate asks that `openlist.pending(doc)` is empty: every bullet ruled, a Guessed line never enough (z-work's rule, kept: G11).
- **The bullet grammar** (G5) for design and code is `openlist`'s, the one reader of `## Open to the human`: `openlist.sourced(doc): { { source: string, id: string, ruled: boolean, guessed: boolean } }` reads every bullet `- F<k>: (<prefix>NNN F<n>) …`, and `- F<k>: (<prefix>NNN stale) …` for a stale entry, with its `Ruled (user, …)` and `Guessed (agent, …)` lines; `openlist.pending`, `waiting` and `guessed` keep their behaviour for bullets without a source.
- **Who reviews each round** (G3): a new clean reviewer every round (a fresh subagent, or a fresh `./zn dispatch zz-review` run), never the author and never the previous round's reviewer's context. From round 2 it is given the earlier rounds' review and refute files of the window and, for code, the fix delta (`git diff <the commit that added the previous review-NNN.md>..HEAD`). It rules each refutation: a refutation that holds is dropped on a line `Dropped from <prefix>NNN: F2, F4` under `Inputs:`; one that does not is repeated as a new finding whose claim ends `(repeat of <prefix>NNN F<n>)`, with the new evidence. A repeat the author refutes again goes to the human; later reviewers do not raise it again.
- **`## Open to the human` in a loop** (G5): before a design or code loop ends, only a dispute (above) and a question that would cut scope go there; refutations are the next reviewer's to rule. Every design or code bullet names its source round, `- F1: (design-review-004 F3) <the finding>. Answer: … Decision: …`, numbered F1.. in the document (two rounds' F3 never collide); the idea's bullets are c0260's, as it writes them. ### Edge cases
- No review yet: `none`, the next file is 001 (or one past the highest in the folder, for an older item).
- A round with no findings and `Verdict: changes`: not ended; `answer` has nothing to answer, so `next` (a reviewer that disapproves without a finding is answered by the next reviewer).
- An approving round with an unanswered low finding: `answer`; answered `refuted`: ended; answered `fixed`: `next`.
- A rerun after a crash between the review and the refute: `answer`, never a second review of the same round.
- Extra lines naming a file below `from`: not counted. Two `a new … loop from` lines: the highest wins.
- An idea at the cap with an `ask:`: the ticket waits for the person (never guessed).
- A re-prep of a design whose loop's gate passed (approved, or capped with its leftovers ruled or guessed), or an older issue adopted by the claim: the claim writes `- Loop (tool, …): a new design loop from design-review-<next>`, so the new design is reviewed again; a give-back and re-claim mid-loop continues it.
- An ask in a round that also has other findings: the author answers the others, the next round runs, and the ask stays the person's until ruled; an ask-only round waits (`person`).
- A guess or an assumption recorded after an on-course last review: the view id changes, the last review runs again (`review-again`), and the approval must cover the new contract.
- An unmarked item: filing refuses a second round, and `status prepared` and `done` judge it as before; but an unmarked `new` ticket whose idea is unchallenged (or whose c0260 loop takes its next round) is an `idea` pick of `work next` like a marked one, and `--guess` marks it first (**Guess (prep) G34**): z-work now carries every older unchallenged ticket through the idea stage: on origin/main today (2026-11-19) that is eight new raftless tickets with `idea: unchallenged` (the 23 with no `idea:` key predate the idea stage and stay `draft` picks), each costing up to five `idea-challenge` (Opus 5.5) calls and four `idea` revisions, picked after every `draft` (G12).
- A marked member of a raft whose ready commit has no `Rounds: on` trailer (readied before f0417 landed): `done` applies `lastgate.problem` only under the trailer; the member's approval check stays f0399's.
