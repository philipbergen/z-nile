# f0419: Unblock first work order

## Problem
- `./zn work next` and `./zn work queue` order candidates by lowest id (`work.rankKey`) alone, so a ticket or raft that many other items wait on can be taken after one that nothing waits on.

Decided with the user (2026-11-20): "unblock the most, we want parallelism and progress" (asked whether the rank c0249 gives or f0419's count of what a raft unblocks comes first when the worker picks: the unblock count comes first, then rank, then the lowest ticket number.)

## Non-goals
- This issue does not add or change the `rank:` field or the lost-work rule; those stay c0249's.
- This issue does not change which items are candidates (what `ready` would accept), only the order among them.
- This issue does not change how `depends_on` is written or let it name a raft.
- This issue does not weigh waiting items by size, type or age; each counts as one.

## Solution
- Each candidate gets an unblock count: for an issue, the number of distinct unfinished issues that reach it by following `depends_on` over one or more steps; for a raft, the number of distinct unfinished issues outside the raft that reach any of its member issues the same way, each counted once however many members it waits on, and the raft's own members never count.
- z-work, `./zn work next` and `./zn work queue` put every candidate that needs no further human approval before every candidate that still needs one.
- Within each of those two groups, the candidate with the higher unblock count comes first.
- Today's order (lowest id, `work.rankKey`) decides only between candidates in the same approval group with equal unblock counts.
- Once c0249 lands, its whole order (lost work first, then `rank:`, then lowest id) takes that same tie-break place and is never considered before the approval group and the unblock count.
- `./zn work queue` shows each candidate's approval group and unblock count, so a reader can check the order it lists.
