# f0420: Named raft works until landed

## Problem
- Today `./zn work <R>` stops the session the first time `./zn work next <R>` says `end` or `wait`, which can be well before the raft has landed (for example when a member still needs design or re-prep, the raft needs rafting or readying, or a layer is unfinished).

Scope decision (user, 2026-11-20): "walk the graph, deliver the other rafts first in the order necessary" and "make branches and branch off of those branches" (a named raft is delivered, not stepped: today `z-work <R>` does "one tiny little part of the work" and stops, and ten runs still do not finish it. With a raft named the session keeps going until that raft has landed. When the raft depends on other rafts, the session does not refuse and name them: it shows the dependency graph, delivers those rafts first in the order the graph needs, from the back and as parallel as it can, and then the named raft. A raft with unapproved guesses is not a stop: its work stays on a branch, and the rafts that depend on it are built on branches made from that branch, so one approval session can approve the whole stack and, when every guess was good, every branch just merges. Nothing unapproved goes to the final gating review or to main. This widens this ticket past its captured Non-goal "The session does not take up any other raft": it takes up the rafts the named one depends on, and no others.)

Decided with the user (2026-11-20): "unblock the most, we want parallelism and progress" (the order among workable units, for a named raft and for `./zn work` with no raft named, is what unblocks the most, then rank, then the lowest id. The Non-goal below that `./zn work` with no raft named does not change holds for its loop and its stops, not for its order: f0419 asked for that order and this ticket delivers it as its last build step, so that step needs no further yes from the owner.)

Decided with the user (2026-11-20): "I'm expecting there to be multiple workers from different vendors ready to take tasks from the queue" and "a grok cli does not have opus so it can implement and then let go, b/c another opus enabled client (claude or agent e.g) needs to review, they might take it from there or it goes back in the queue" (several workers run at the same time, one per CLI: for example opencode on a local model for light tasks, claude with Fable for the end review, and grok, agent and kimi beside them, to stretch the budget. The configuration says which model each activity needs, for example implementation on grok-4.7 only and review on Opus only. A worker takes from the queue only an activity its own CLI can deliver, does that one activity, and lets the work go; the next activity is taken by whichever worker can deliver it, the same one if it can, and otherwise it goes back in the queue. So what is queued and claimed is one activity of a ticket or raft, not a whole raft, and no session hands work to another CLI itself. For this ticket: `./zn work next` is asked by a worker that states its CLI, and answers only with an action that CLI can deliver; when the next action of the named raft needs a model this worker lacks, the worker releases that step to the queue and takes another unit of the walk it can do, or waits. The design's lead-and-subagents picture holds within one CLI; across CLIs the hand-off is the queue. The claim, its heartbeat and its takeover (R0100: c0265, c0274, c0275, c0277) and claims between hosts (c0254) are therefore needed by this ticket, not low priority.)

Decided with the user (2026-11-21): "Go, starting with a spike" (asked whether the live layer is built in Go: yes, after a spike that proves atomic claims under a race, a waiter woken within about a second and near-zero idle cost. The live layer is its own ticket, f0424, a small Go daemon. This replaces guess G11 in the Design below (a first build in Luau): build steps 1 to 3 of this ticket need no live layer and go ahead; from step 4 on this ticket calls f0424's contract and builds none of the store, the registration, the heartbeat or the wake signal itself. The contract written in this Design under the live layer is the starting point for f0424's, and where the spike's contract differs, f0424's wins.)

## Non-goals
- `./zn work` with no raft named does not change.
- The session does not take up any other raft, before or after the named one lands or stops.
- No approval is skipped or guessed past: nothing unapproved lands, and the session does not run `./zn approve` itself.
- The session does not idle or poll for the person's approval or answers; it stops, and the person re-runs `./zn work <R>` to resume.

## Solution
- With a raft named, the session keeps taking that raft's next action, whatever its stage, and stops in exactly two cases: the raft has landed on main, or the only remaining next action is one that only the person can clear.
- A person-only stop is a `wait` for `./zn approve`, or a blocked raft that has written `questions.md` and run `./zn stop <R>`.
- When the session stops before the raft has landed, its last message names the raft, the stage it reached, and the exact command or answer the person owes.
- A `wait` that the session can clear itself (a gate, a review or a merge still running) is never a reason to stop: the session holds and then continues.

## Design
A named raft is a *target*, and the work towards it is a queue of *activities*. An activity is one step of one *unit* (an open raft, or an open issue in no raft, as the board's Flow draws them): a design, a review round, a layer, a landing. `./zn work next <R>` answers with the next activity, across R and every open unit R waits on, that unblocks the most and that the asking worker's CLI can deliver. A worker states its CLI, claims that one activity, does it, pushes the result and lets go; the next activity goes to whichever worker can deliver it. Durable outcomes stay in git as today; who is running and what each holds is live state on the machine, behind a small command contract (below). The action words `end` and `wait` are kept, so the pinned specs move as little as possible. **Guess (prep) G1**

**Activities (A).** Each action word `./zn work next` prints (today's, and f0421's rounds) is one activity kind. The config name is what f0421 slice 2's `can(cli, activity, level)` is asked about.

| action word | activity | config name | model | who may take it |
|---|---|---|---|---|
| `draft` | design | design | yes | any worker that `can` |
| `design-review` (round N) | design-review | design-review | yes | never the model the design's release names |
| `design-answer` (answer design-review-NNN) | design-answer | design | yes | the author activity's model, any worker |
| `rafting`, `fix` | rafting, fix | raft, code | yes | any worker that `can` |
| `implement`, `finish` (layer k) | code | code | yes | any worker that `can` |
| `review` (file round N) | code-review | code-review | yes | never the model the code's release names |
| `review` (answer review-NNN) | code-answer | code | yes | the author activity's model |
| `trace` | trace | code | yes | any worker that `can` |
| `final-review` (round N, or its answer) | final-review, final-answer | final, code | yes | never the code's model |
| `ready`, `restack`, `done`, `release` | the same | none | no | any worker, `--cli none` included |
| `wait` (approval, answer), `end`, `none` | none | none | no | owed to the person, or nothing |

`draft` today covers the design and its review in one session; it splits into `draft`, `design-review` and `design-answer`, read with `rounds.next` over the prep branch's `design-review-NNN` and `design-refute-NNN` files, as f0421 does for code. A restack that conflicts turns into `fix`. The model is chosen by the activity at the unit's risk level, never by the worker, and f0421 refuses a config whose writer and reviewer resolve to one model; the "never the model" column is a backstop read from the previous release event.

**The walk (pure, `work.luau`).** `work.decide` with `asked = R` (a raft) does this:
1. R done: `end`. R active with `questions.md`: `release`. Both are unchanged.
2. The units come from `depgraph.units(rafts, issues)`, a new pure function that holds the rule the board uses today (board.luau ~1043; the board then calls it too). A raft waits on the open raft of each outside dependency, or on that dependency itself when it is in no raft. A raftless issue waits the same way. The closure is R plus every unit reachable over `waitsOn`.
3. Each unit in the closure gets one *unit answer*: an activity, `waits on <ids>`, `held by <worker>`, or an owed item. Rules for a raft: the `forRaft` action when active. When it is a backlog raft: `ready` when claimable; `ready --on <bases>` when its only unmet dependencies sit in 1 to 3 active rafts whose layers are all finished (rule 4 below); `fix` when `work.fixable`; `draft` (or its review or answer) for the first member that is not `design: ready`. A raftless issue gets its `issuePick` action with the tiers ignored, or `ready` on the light path. `questions.md`, an idea the person must answer (`draftBlock`), a closed dependency, a changed approved contract, an unapproved member once the final review is approved, and a dependency cycle are owed.
4. The workable units are those whose activity no live worker holds, that this worker `can` deliver, and that the machine's gate cap allows (Parallelism). They are ordered by `depgraph.order(ids, depgraph.unblocks(closure))`. The first one's Decision is returned, with `For R: ` in front of its why when the unit is not R.
5. When nothing is workable: if anything is owed, `wait` lists every owed item as an exact command or file (`./zn approve f0377 (R0093)`, `answer <path>/questions.md`), separated by `; `. Else a unit whose activity no live worker can deliver gives `wait` with `R0093 waits for a worker with code-review/normal (heavy: claude-opus-5-5)`; a unit held by another worker gives `wait` naming it. R backlog with `questions.md` and nothing else owed is `end`, as today.

`--one` (`./zn work next <id> --one`) is today's answer for that one unit (`forRaft` or `forIssue`), still filtered by `can` and the claim. A named issue and every unnamed call stay `--one`. Under `ZN_DISPATCH=1` a named raft is always `--one`.

| situation (R named, not landed) | today | new |
|---|---|---|
| backlog, an outside dependency not done | `none` | the closure's first workable unit's activity |
| backlog, a member not `design: ready` | `none` | `draft`, `design-review` or `design-answer` for that member |
| backlog, ready refuses for a repairable reason | `none` | `fix` (the same text as the unnamed `fix`) |
| backlog, dependencies in active rafts whose layers are finished | `none` | `ready R --on A [--on D]` |
| backlog with `questions.md` | `end` | another unit's activity while one is workable, else `end` |
| active, built, members unapproved | `wait`, "ask again with no raft" | another unit's activity while one is workable, else `wait` listing every `./zn approve` the closure owes |
| active, approved, built on an unlanded raft | `wait` | that base's activity (its `done`, or its owed approval) |
| next activity needs what this CLI lacks | (not asked) | another unit's activity, else `wait` "waits for a worker with X" |
| done / active with questions / unknown id | `end` / `release` / `none` | unchanged |

**The graph.** `./zn work graph <R>` is pure `work.graph(input, workers, R)` over one `workread.collect` and one `live workers`; `./zn work <R>` prints it after the skill. One line per unit, band 0 first, each band in `depgraph.order`, then `now:` and `owed:`:
```
R0099 needs 5 units; 2 can be worked now
band 0  R0091  implement     code/normal          held by grok-8812@mbp  layer 2 f0388
band 0  c0410  draft         design/easy          unblocks 2
band 1  R0093  owed          ./zn approve f0377   unblocks 1
band 1  R0095  waits on c0410
band 2  R0099  waits on R0091, R0093, R0095
now: c0410 (claude, grok, kimi can)
owed: ./zn approve f0377 (R0093)
```

**Building on unapproved work.** Approval gates only the final gating review and the landing, so a unit that waits on approval does not block the units above it. A raft's *bases* are the unlanded rafts that hold its members' outside dependencies, counting direct dependencies only.
- 0 bases: layer 1 starts from `origin/main`, as today. 1 base: `<R>/base` is that raft's top layer plus the tracker-restore commit (`layergit.buildBase`, f0399).
- 2 or 3 bases: `buildBase` detaches at the lowest-id base's top tip, runs `git merge --no-ff --no-edit` with each other base's top tip in id order, then makes the tracker-restore commit (`tracker: base R on A D`). The ready trailer becomes `On: A D` (`readyRecord` reads a list), and `ready` takes `--on` more than once. A conflict is refused at `ready`, naming both rafts, and the walk shows R as `waits on` until one lands. More than 3 bases also waits. **Guess (prep) G2**
- A chain (A unapproved, B on A, C on B and D): C's bases are B and D. There is no depth limit: restacks are mechanical and the walk orders them.
- A base moves: `workread`'s `stacked` also asks that each base's top tip be an ancestor of R's layer 1. R's answer is then `restack`, which rebuilds `<R>/base`; lower rafts restack first because they unblock more. f0423's send-back uses the same restack.
- All approved: each raft runs `done` in band order; `done` already refuses while a base has not landed. After a base lands, the raft above answers `restack` (the landed base drops out), then `done`.

**Light path for an easy raftless ticket.** An issue in no raft that is `design: ready` with `risk: easy` (f0421) goes from designed to done in one pull request: `./zn ready <issue>` creates a `single: true` raft in the same tracker-only claim commit that moves it to `active/` **Guess (prep) G6**; then start, build, finish, restack only if main moved; then `trace` and one final review (final mode) that also reviews the code **Guess (prep) G7**; then approve if it has guesses, and `done`. Skipped: z-raft, `raft-plan`, the rafting PR, and the separate code review. `RaftFact.light` sends `forRaft` from restack straight to trace. Kept: `check.sh`, the RC check, the affected gate at `done`, promotion, `trace --check`, the final verdict, approval and `## Open to the human`.

**The live layer: a process boundary (B, E, F).** Live state is plain data under the main checkout's `.cache/live/`, one machine's, never committed or pushed. The engine reaches it only through `./zn live <op>`: argv in, an exit code and JSON lines out. In this build `livecall.luau` is the only caller and runs the op in process (a second Lune per call costs about a third more, c0070); a later Go binary or daemon serves the same ops and files, and only `livecall` changes to `process.exec`. The contract spec drives `./zn live` by argv only, so it runs unchanged against either.
- `workers/<worker>.json`: `{v, worker, cli, can, host, pid, session, mode, started, heard, stop}`. `worker` is `<cli>-<pid>@<host>` (`.<as>` added for a subagent's `--as`); `can` is the list of `activity/level` pairs `can` gives for that CLI (no `can` yet: every pair for a CLI the config names, mechanical only for `none`); `mode` is `session`, `run` or `plain`; times are epoch seconds. `heard` is the heartbeat; it is not an event.
- `claims/<unit>.json`: `{v, unit, activity, action, step, worker, model, level, since, worktree, stamp, lost}`. One claim per unit: a unit's activities run in order.
- `events.jsonl`, append only: `{v, seq, at, kind, unit, activity, step, worker, cli, model, host, tokens, seconds, ref}`, unknown values `null`. Kinds: `registered`, `gone`, `claimed`, `released`, `given-back`, `lost`, `taken-over`, `design-filed`, `review-filed`, `answer-filed`, `layer-finished`, `restacked`, `readied`, `approved`, `landed`. The live ops emit their own; `finish`, `restack`, `ready`, `approve`, `done` and the review commits emit theirs through `live emit`.
- `wake`: one line `<seq> <epoch>`, replaced on every write here and in `published()` (main.luau, the one place every publish passes). `lock`: the file every write flocks.
- Ops: `register --cli <c> [--as <s>] [--pid <n>] [--mode <m>]`, `beat <w>`, `claim <w> <unit> --activity <a> --action <x> --step <s> [--model <m>]`, `release <w> <unit> [--back] [--tokens <n>] [--seconds <n>] [--ref <sha>]`, `leave <w>`, `stop <w>`, `workers`, `claims`, `emit <kind> <unit> [--field k=v]...`, `events [--since <seq>]`, `wait [--since <seq>] [--timeout <s>]`. Exit 0 done; 1 refused (one JSON line naming why, for a claim the holder); 2 usage; 3 store unreadable; 75 timed out.
- Every write takes the flock on `lock` (`runner.holdLock`, Perl's `flock` as `./zn run` already uses, retried every 50 ms for up to 5 s), reads, decides, writes each file by temp and rename (`sh.writeReplacing`), appends the event, replaces `wake`, then unlocks. A claim is therefore atomic among every process on the machine, and a Go `flock` on the same file interoperates.
- Every op first sweeps: a worker on this host whose pid is gone (`kill -0`) is removed (`gone`) and its claim kept with `lost: true` (`lost`). A worker of another host (once c0254 shares records) is lost when `heard` is older than R0100's 900 s. A live pid keeps its claim however silent; the board shows the silence. **Guess (prep) G10**

Luau now or Go: build this layer first in Luau on Lune behind the contract. **Guess (prep) G11** Lune 0.11.1 has no file-watching API (its 0.10.5 typedefs list none) and no database, but it has what this needs: `fs.metadata` for a one-second stat of `wake`, `task.wait`, `process.exec`, the Perl flock helper and atomic rename, all already used here, and specs, jail and fence stay in one language. Its cost: one-second wake latency, a Lune process (tens of MB, unmeasured) per waiter, and the Perl dependency for the lock. Go's gain: kqueue/inotify events, native flock, one static binary that can later serve a socket or the app. Its cost: a second toolchain on every machine and in CI, a build step `SETUP.md` and the gate must own, zz-arch rules for a new language, and specs that must find the binary inside the jail. E6 to E8 decide: if the stat loop costs over 1% of a core over ten minutes, the race loses a claim, or wake latency exceeds 1.5 s, step 4 is built as a Go `zn-live` serving the same contract instead.

**The claim and the durable guards (B).** The durable claims stay as today: the `ready` commit for a raft, the `preparing` status commit for a design, each made once per unit by its first activity. They gain a `Host: <name>` trailer; a unit whose durable claim names another host is shown as `held on <host>` and never claimed here, until R0100 judges that claim lost and c0274's takeover moves it. Within the host, the live claim decides who holds which activity. The author check (`workread`'s holder) is unchanged: every worker of the host shares its git identity. **Guess (prep) G9**

**R0100.** Its heartbeat is a branch `refs/heads/hb/<claim stamp>` on origin holding one commit (main's tree and tip, subject `hb <stamp> <epoch>`), replaced by a force-with-lease push every 300 s (`heartbeat.INTERVAL`); a claim is stale after 900 s without a beat (`STALE`), parked when an open PR names it, and lost when stale and not parked (c0265). c0274 takes a lost claim over with an atomic branch swap and refuses the old owner by its memory `.cache/tracker-stamp-<id>`; c0275 beats at every claim, every `./zn` command in a worktree and from a background `./zn beat --watch`; c0277 renames the old worktree aside and continues in a numbered copy. R0100 lands first, unchanged: it is approved and built, and nothing here needs it before step 4. This ticket reuses it as the cross-host layer (a claim on main is a host's) and changes three things: taking an activity runs `./zn beat <id> --adopt --stamp <S>` in the activity's worktree, so c0275's beats follow whichever worker holds it; `work wait` and `work run` beat, every 300 s, the stamp of each unit this host released and nobody has taken since, so a hand-off gap never reads lost; and c0277's `--takeover` also accepts a claim the live store marks lost. A dead local worker is found by its pid within a second, not after 900 s.

**Hand-off (C).** An activity is released only when its result is on origin: the worktree it was claimed in has no uncommitted tracked file and nothing ahead of its upstream (`release` refuses otherwise, naming each). On origin at release: a design or answer, the prep branch with its commits; a design-review or code-review round, its `*-review-NNN.md` (or `*-refute-NNN.md`) on the prep branch or the top layer; rafting, fix, ready and done, their publish on main (and `<R>/base` for ready); code, the layer branch `R/k/<issue>` with every commit (finish adds its spend row); restack, the rebuilt layer branches; trace and final review, `trace.md` and `final-review-NNN.md` on the top layer. The next worker runs `./zn worktree <unit>`: on this machine one worktree per unit is reused, fast-forwarded to origin's tip of the branch the activity names (refused when it has diverged); on another machine it is created there. A worker that holds an activity and asks `work next` again gets the same activity until the facts move past it; then it is released and the next answer given. A worker that cannot finish releases with `--back` (a pushed work-in-progress commit is allowed). A lost activity is redone from origin's state: when its worktree is clean the next holder reuses it, otherwise `./zn worktree <unit> --takeover` (c0277) renames it aside and its note lists the unpushed commits and files to take.

**The worker's question (D).** `./zn work next [<R>|<tributary>] [--cli <name>] [--as <s>] [--one]`. The CLI is `--cli`, else `ZN_CLI` (set by `work run` and by wrappers), else `claude` when `sessionread.id()` names a Claude session and `kimi` for a Kimi one, else the nearest ancestor process named in R0100's `heartbeat.SESSIONS` (grok, agent and opencode set no variable this code reads). Otherwise it refuses, naming `--cli`. The pid is that ancestor's (the loop's under `work run`). The first call registers the worker, every call refreshes `heard`, and the answer is claimed before it is printed; when another worker wins the claim the walk runs once more without that unit. `--cli none` is a plain process: it gets only `ready`, `restack`, `done` and `release`. A tributary scope is f0422's filter on the units.

**Waiting (F).** `./zn work wait [<R>|<tributary>] [--cli <name>] [--timeout <s>]` is `work next` that blocks: while the answer is `wait`, it stats `wake` once a second (`fs.metadata`, no process started) and decides again only when `wake` changed; every 60 s (`[workers] remote_seconds` in `.models.toml`) it runs `git ls-remote origin refs/heads/main` and fetches only when the hash changed; every 10 s it sweeps (`live workers`); every 60 s it beats its worker. When the answer is an activity it claims it, prints it and exits 0; at the timeout (default 540 s, at most 3,600, the same bound as `./zn run`) it exits 75; when its worker's pid is gone it exits 1. It is a `./zn` command with its own bound, so AGENTS.md's `./zn run` rule does not apply to it. Idle cost: one stat a second and one `ls-remote` a minute, no model. A session a person opened runs `work wait` as one foreground tool call (540 s keeps it under Claude Code's ten-minute limit) and runs it again on 75, which costs one short turn every nine minutes; a CLI with background notifications may run it in the background.

`./zn work run --cli <name> [<R>|<tributary>] [--sessions <n>] [--once] [--max <n>] [--for <s>]` is the unattended worker: a plain loop with no model that registers n workers (`mode: run`), waits as above, does mechanical activities itself, and for a model activity starts ONE fresh headless session of that CLI in the activity's worktree through `modelstep.launch` (the runner's caps, stall limit and lifeline; the adapter per runtime), with the activity's resolved model, `ZN_WORKER`, `ZN_CLI` and a prompt of the action line plus "z-work, one activity". In that session `work next` answers `end` once the activity is released, so a session never takes a second one. When the session exits the loop releases (or `--back` when the facts did not move, or leaves it lost when the worktree is dirty), writes the measured spend row as the dispatcher does, and emits the event with tokens and seconds. A quota outcome releases `--back` and pauses this worker's model activities for 30 min. It stops at `--for` (default 12 h), on SIGINT or `./zn work stop <worker>` after the activity in flight, and prints a summary: activities done, given back and lost, per unit. c0253 is absorbed here **Guess (prep) G8**: its plain loop that waits with no model (Q6), the cheap supervisor that starts fresh headless sessions (Q3's supervisor, Q8), both ways of running it (Q12), `--cli`, `--once`, `--max`, the stop and the summary, and `done` as the one lander (Q10) are kept; its unit (a raft to merge, Q7), Q3's resumed session per raft and its switch to another CLI on quota (Q9) are replaced by the owner's decision of 2026-11-20 that one activity is claimed and the queue hands off between CLIs.

**Parallelism (G).** With several workers up, parallelism is the workers, each holding one activity. The cap is per machine, because spec runs share the runner's eight lanes: at most `[workers] gate_slots = 3` held activities that run specs or the gate (draft, fix, code, done), of which one `done`. **Guess (prep) G4** A claim past it is refused and the worker gets another kind or `wait`. Reviews, answers, trace, rafting, ready and restack are not capped. A session may still start plain subagents (AGENTS.md) as an option inside one CLI: each registers with `--as`, takes one activity through the queue on the model `work next` names, and returns at its release. The session no longer does lead actions for them, because mechanical activities are queue activities too. **Guess (prep) G3**

**Order among equals.** `work.rankKey` goes. `work.order(ids, input)` is `depgraph.order` over the unblocks of the whole open graph, with c0249's rank as the second key when it lands. `nextClaimable`, `lowestIssue`, the unnamed picks and the walk all use it; without dependencies it is the id, as today. The owner's "unblock the most" decides it, so its step needs no further yes.

**Stops.** The only stops before landing are `end` and a `wait` that only the person can clear; a `wait` for a worker or a held unit is `work wait`, never a stop. The last message is three lines: `R0099 stopped at <R's stage>: <k> of <n> units done`, then each owed item as its exact command or answer (`./zn approve <id>` per member until f0423 lands, then `./zn approve R0099`), then `Then run ./zn work R0099 again.`

**Unchanged from the first design, and the seams (H).** Unchanged: the walk over the closure, `--one`, the graph's bands, up to three bases, the light path, most-unblocks order, the stops. f0421 owns risk, rounds, the config and `can(cli, activity, level) -> boolean` (does this CLI define what that activity names at that level), and the resolved model per activity. f0422 draws the workers panel, the worker on a card and "waiting for a worker with X" from `live workers`, `live events` and pure `work.waitingFor(input, workers) -> {[unit]: string}`, apart from "waiting for your approval". f0423 owns approval, `waiting.of`, send-back and the prep-branch base. R0100 lands first (above). c0254 keeps several hosts: sharing the live records between machines, and spend rows with host, CLI and model.

### Scalability
The walk and the graph are pure, O(units + edges). The live store holds one file per worker and per claim and is read whole per call. New git work: one `merge-base --is-ancestor` per base in `stacked`, one merge per extra base at ready and restack, one `ls-remote` a minute per waiter.
### Maintainability
One unit rule (`depgraph.units`), one order (`work.order`), and one boundary (`livecall`) to the live layer, whose contract spec is the definition a Go build must pass.
