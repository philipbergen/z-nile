# f0421: Risk scaled rounds and models

## Problem
- One review round is enforced for every ticket whatever its risk (`dispatch.filing` refuses a second, and the skills z-design, zz-review, z-raft, zz-execute and zz-rules say so).
- The worker's next action stays on "review" forever after a review said changes, even when every finding is answered, because `workread.reviewState` counts only an approve verdict.
- `.models.toml` gives one model per role whatever the ticket, with fallback lists to other CLIs.
- Only `./zn dispatch` reads `.models.toml`, so no activity in a person-started z-work session gets a configured model.
- Design review takes 43% and design 25% of recorded agent-minutes across done tickets, and nothing lets a low-risk ticket spend less.

Decided with the user (2026-11-20): "Some cli cannot provide heavy or ultra, that's fine, we need to allow CLIs that can't do all the things but can provide some things b/c they are cheap. For example running local qwen3.8 is suitable for xlight and light tasks no problem and does so for free" (a CLI may define only some of the four aliases, and a configuration with such a CLI is valid. The error for a model that cannot be delivered is raised only when an activity is actually given to a CLI that does not define the alias it names. The Solution line that the seed defines all four aliases on every CLI it configures no longer holds for every CLI. Guess (lead), to be ruled in the models slice: the configuration lists the CLIs in an order of preference and an activity goes to the first one that defines its alias, so cheap work goes to the cheap CLI and heavy work to one that has it; that is routing the owner wrote down, not a fallback.)

Decided with the user (2026-11-20): "I'm expecting there to be multiple workers from different vendors ready to take tasks from the queue" and "a grok cli does not have opus so it can implement and then let go, b/c another opus enabled client (claude or agent e.g) needs to review, they might take it from there or it goes back in the queue" (several workers run at the same time, one per CLI: for example opencode on a local model for light tasks, claude with Fable for the end review, and grok, agent and kimi beside them, to stretch the budget. The configuration says which model each activity needs, for example implementation on grok-4.7 only and review on Opus only. A worker takes from the queue only an activity its own CLI can deliver, does that one activity, and lets the work go; the next activity is taken by whichever worker can deliver it, the same one if it can, and otherwise it goes back in the queue. So what is queued and claimed is one activity of a ticket or raft, not a whole raft, and no session hands work to another CLI itself. This settles the lead's guess in the line above: there is no order of preference among CLIs and no routing by a session; each worker filters the queue by what its CLI defines. A CLI that lacks an alias is never an error by itself: the error is only for an activity that no configured CLI can deliver.)

## Non-goals
- No fallback to another CLI or another model when the configured one cannot be delivered.
- No automatic repair of a configuration that gives a writer and its reviewer the same model.
- No change to what a reviewer checks or how findings are written.
- No guarantee that a review settles within its maximum rounds; what happens at the maximum stays with the human.

## Solution
- Each ticket records a risk level (easy, normal or risky), chosen at design from its size, complexity and how easily it is fixed or reverted, and the owner can overrule it.
- TOML sets the maximum review rounds per stage (design, implementation) for each level, and a separate maximum for the idea stage, where the level is not yet known.
- The skills state that these numbers are maximums and that a review should find everything in its first round.
- A review whose findings are all answered counts as settled, so the worker's next action moves past "review".
- TOML defines the aliases xlight, light, heavy and ultra per CLI, each as a model, effort and context.
- TOML gives each activity (design, design review, code, code review), per level, either an alias or a specific model-effort-context.
- The seed is: easy writes design and code with xlight and reviews both with light; normal writes with light and reviews with heavy; risky writes with heavy and reviews with ultra.
- The seed defines the four aliases as four different models on every CLI it configures, so every seeded level gives a writer and its reviewer different models.
- The final gate uses ultra at every level.
- When the configuration is read, any level and stage whose writer and reviewer resolve to the same model name (whatever the effort and context) is refused with an error naming the level, the stage and the model.
- That refusal happens before any activity starts, and no model is ever quietly replaced.
- When the active CLI cannot deliver the model an activity names, that is an error telling the person to switch configuration or CLI.
- The same configuration is read and applied in a person-started z-work session and under `./zn dispatch`.
- This ticket takes over the round rules of f0417, c0418, c0251, c0306 and c0325 and the note in c0166.

## Design
Slice 1 of 2: rounds and settled reviews. Aliases, models per activity and the same-model refusal are slice 2.

**Rule.** The latest round of a review counts, and earlier rounds are history. A review file with no `Verdict:` line and no findings, or a changes verdict and no findings, is malformed: nothing settles it. Approve settles the review. A round that is not approve and not *responded* (every finding has a line in its refute file: fixed with consequences, refuted, or deferred where allowed) waits for the author. A responded round with a high, medium or untagged finding, below the maximum, is followed by the next round, with no rulings: the next round's reviewer accepts or re-raises each refutation. A responded round with only low findings, or at the maximum, is settled once it is also *answered* (what is refuted or still open is listed under `## Open to the human`, qualified by its review file after round 1, and ruled or recorded as a guess); until then the author is asked for exactly that. Nothing goes to the human between rounds. A review that settles at the maximum with serious findings answered says so (`work next`, `./zn rounds`): record it as a guess so the owner sees it at approval. The gates (`./zn done`, `status prepared`) still require what they required; `done` requires *answered* of the latest round. A maximum is not a minimum. `./zn work next`, the dispatcher and `./zn idea` run the loop, and `./zn rounds <id> [--kind design|code|final]` prints the step in one line (`z-nile/engine/roundscmd.luau`, which the dispatcher also reads its step from).

**`rounds.luau` (new, pure).**
- `export type Level = "easy" | "normal" | "risky"`, `export type Stage = "idea" | "design" | "code"`.
- `export type Limits = { idea: number, design: { [Level]: number }, code: { [Level]: number } }`. `rounds.DEFAULT` holds the seed: idea 3, design and code `{ easy = 2, normal = 5, risky = 9 }`.
- `rounds.level(value: string?): (Level?, string?)`: nil or "" gives `normal`, and easy, normal or risky give themselves. Any other value returns nil and `risk is <v>: easy, normal or risky`.
- `rounds.highest(levels: { Level }): Level`: the raft rule, risky > normal > easy, and `normal` for an empty list.
- `rounds.max(l: Limits, stage: Stage, level: Level): number`, where idea ignores the level.
- `export type Round = { number, file, verdict: string?, responded, answered, serious: boolean, seriousCount: number, malformed: string?, open: string? }` (`serious` is true when the review text has a finding rated high or medium, or a finding with no severity tag, read through `openlist.findings`: an untagged finding is unknown, and unknown must not skip a round), `export type Step = { kind: "file" | "answer" | "settled" | "malformed" | "rule", number, max: number, reason: string?, atMaximum: number? }` (`reason` is the sentence of a malformed or rule step; `atMaximum` is the count of serious findings of a review that settled only at the maximum).
- `rounds.verdict(text): string?` is the one `Verdict:` reader (it replaces `workread.verdictOf`).
- `rounds.KINDS = { design = {"design-review-", "design-refute-"}, code = {"review-", "refute-"}, final = {"final-review-", "final-refute-"} }`.
- `rounds.latest(files: { [string]: string }, kind: string, doc: string, isBacklog: (string) -> boolean): Round?` takes the highest-numbered review in `files` (name to text, matched by plain prefix and never by a pattern built from the prefix) and the refute file of the same number ("" when there is none). `responded` is `openlist.unresponded(...) == nil` and `answered` is `openlist.unanswered(...) == nil`. `malformed` is set for a file with no verdict and no findings and no failed Judged criterion ("<file> has no Verdict line and no findings: fix the file or redo the round"), or a non-approve verdict and none ("<file> has a changes verdict and no findings: fix the file or redo the round"). `rounds.laterRule(prevReview, prevRefute)` is the sentence a round above 1 is given (its prompt, and `work next`'s reason): this round only checks the answers, each fix is real and broke nothing in the lines it touched, accept or re-raise each refutation, a new finding only for a defect in those changes or one round 1 could not have seen.
- `rounds.next(latest: Round?, max: number): Step` follows this table.

| latest | verdict | responded | answered | serious | N vs max | kind | number |
|---|---|---|---|---|---|---|---|
| nil | | | | | | file | 1 |
| N | no verdict and no findings, or non-approve and no findings | | | | | malformed | N |
| N | approve | any | any | any | any | settled | N |
| N | not approve (or none) | no | any | any | any | answer | N |
| N | not approve (or none) | yes | any | yes | N < max | file | N+1 |
| N | not approve (or none) | yes | yes | no | any | settled | N |
| N | not approve (or none) | yes | yes | yes | N >= max | settled (`atMaximum` = serious count) | N |
| N | not approve (or none) | yes | no | no, or N >= max | | rule | N |

A finding with no severity tag counts as serious. Rounds are the largest cost in the pipeline, and a round that only re-reads fixed low findings buys nothing.

**Responded and answered.** The body of `main.reviewProblem`, from after its approve check to its end, moves into `openlist` and is split in two. `openlist.unresponded(p)` checks the missing answers, the `consequences:` of a fixed answer and the deferred rules; it is all a round needs for the next one to be filed. `openlist.unanswered(p: { review, refute, doc, reviewName, refuteName: string, isBacklog: (string) -> boolean }): string?` is `unresponded`, then the `openlist.problem` gap (a refuted finding, an unclosed high or a failed Judged criterion needs its ruling or recorded guess), then a verdict that has no findings, or no verdict and no findings (this tightens `done` only for a file that was never a valid review). `isBacklog` replaces its `store.find` call. `reviewProblem` keeps its first lines and calls `unanswered`, so done's words do not change. `designOpen` keeps calling `openlist.problem` (rulings of the latest design review) and is not changed: it does not require refute lines, `status prepared` is no looser than before, and the dispatcher's design step is the stricter reader (it also needs every finding answered before a round counts).

**Open list bullets.** Finding ids restart at F1 in every review file, so a bullet under `## Open to the human` for a round after the first of its kind is qualified by its review file: `- review-002 F1: ...`, `- final-review-002 F1: ...`, `- design-review-003 F2: ...`, `- idea-review-001 F2: ...`. An unqualified `- F1:` is read as the checked kind's round 1 (today's behaviour, which shares an unqualified bullet between `review-001` and `final-review-001`, is kept for round 1 so no document written before this change changes meaning). For round 2 and later only a bullet qualified with that round's file name answers that round's finding. `openlist.pending`, `waiting`, `guessed` and `problem` read the qualified key as one id.

**`[rounds]` in `.models.toml`.**
- `models.parse` accepts a `[rounds]` table and stores it as `layer.rounds`, keyed by the leaf (`idea`, `design.easy`, …).
- Errors, all `{path}: …`:
  - `[rounds] is a table`
  - `rounds.<k> is not a setting (idea, design, code)`
  - `rounds.<stage> is a table of levels (easy, normal, risky)`
  - `rounds.<stage>.<k> is not a level (easy, normal, risky)`
  - `rounds.<key> is a whole number, 1 to 99` (a separate check: no `inf`, NaN or a count nobody means)
- The message for an unknown table becomes `(the file has roles, fallback, dispatch and rounds; skill tables are gone)`.
- `models.rounds(layers: { Layer }): rounds.Limits` starts from `rounds.DEFAULT`, and the closest file replaces only the leaves it sets, so a walk with no `[rounds]` gives the defaults.
- The root `.models.toml` does not get a `[rounds]` table (an older worktree's engine reads main's file and rejects an unknown table); the built-in defaults are the seed, and the parser accepts the table.

**`risk:`** is an issue frontmatter key read through the existing readers. No new reader is added.
- `workread.frontText` already holds `memberFront`.
- `store.readFront` in the dispatcher reads the author's worktree copy.
- `audit.front` validates it. `audit.run` adds an error `risk` naming the document when `rounds.level` returns a problem, and when a raft document carries `risk:`, with the message `a raft's risk is its members' highest`.
- Every use passes the value through `rounds.level`. A raft's level is `rounds.highest` of its members' levels. The idea stage has no level.
- The owner overrules the level by editing the key. z-design proposes it.

**Callers.**
1. `dispatch.filing`: `FilingInput` gains `step: rounds.Step?`. When the mode is design, code or final and `step` is given:
   - `file` returns `{ number = step.number }`.
   - `answer` refuses with `{dir}/{prefix}NNN.md is not answered: answer every finding in its refute file before round N+1`. At the maximum it reads `…: it is round N of M, the last; what stays open goes to the human`.
   - `settled` refuses with `{dir}/{prefix}NNN.md settled the review (approve, or answered at round N of M): there is no further round`.

   Raft mode (its `grouped:` rule), stream mode and a call with no `step` keep today's code and words.

   `dispatcher.filingNow` computes `step` for design, code and final:
   - The files are `reviewsIn` of the review prefix and the refute prefix.
   - The doc is `{cwd}/{item.doc}`.
   - The level is the issue's own, or the highest of a raft's members' read in `cwd`.
   - The limits are `models.rounds(walk(item.dir))`, the pinned main.
   - A bad `risk:` or `[rounds]` raises an error before any CLI starts.
2. `workread.build` and `work.forRaft`:
   - `sideFile` also takes `refute-NNN.md` and `final-refute-NNN.md`.
   - The layer-tip read also takes the raft's own `<R-id>.md`. The raft doc is read in the same order as the side files: the working tree's copy, then the top layer's, then origin/main's.
   - Every `.models.toml` that `models.folders(at.dir)` names joins the one existing `git cat-file --batch` at `origin/main`, and `models.walkAt(dir, readFromBatch, function() return false end)` parses it. Only main's file counts.
   - `codeReview` is "none" (file 1), "open" (answer), "due" (file N+1) or "resolved" (settled). `finalReview` uses the same values, with "approved" for settled.
   - `RaftFact` gains optional fields: `codeRound`, `codeMax`, `finalRound`, `finalMax` (all `number?`) and `roundsProblem` (`string?`, set for a bad risk or a bad `[rounds]`).
3. `./zn idea`: a loop in `cmd.idea` (details under "The idea stage").
4. `./zn done`: through `openlist.unanswered` only (see "One definition of answered").

**What `./zn work next <R>` prints.** The action words do not change, so `RESUMED`, z-work and the specs that read actions keep working. The reason text comes after the action word. "of at most M" is dropped when the max is nil.

**The idea stage.** `cmd.idea` keeps its one command. After the draft it loops:
- `step = rounds.next(latest, models.rounds(layers).idea)`, and it stops unless `step.kind == "file"`.
- It challenges the current prose and writes `idea-review-<NNN>.md`.
- Unless the verdict is approve with no findings, it revises with `idea.answerPrompt(current, findings)`, where `current` replaces `rough` from round 2 on, and writes `idea-refute-<NNN>.md`.
- It records `latest = { number = N, verdict = verdict, answered = true }`.

Only the last round's `idea.openLines` go under `## Open to the human`, because finding ids restart at F1 each round. `idea-review-001.md` always exists, so `designRefusal` and its readers do not change.

### Risks
- Rulings under `## Open to the human` are committed on the layer, not on main. A `work next` that read only origin/main's raft doc would call an answered review open, which is why the doc is read in the same order as the side files.
- Each final round refills `trace.md`. `traceOk` stays tied to the settled final review.
- `designOpen` and `done` do not demand further rounds, so a person can land after an answered round 1 below the maximum. That is by choice, because the numbers are maximums.
- The author's branch sets `risk:`, so it could lower its own maximum. The change shows in the PR diff, and the owner overrules.
- `./zn metrics` and the board count review files, so more rounds show as more rounds and need no change.
- `RaftFact`'s new fields are optional, so promoted `f0399/pick.spec.luau` still type-checks.

## Design, slice 2: aliases and models per activity
Slice 2 of 2. There is no fallback and no routing. Each worker is one CLI. The config says what each activity needs, and a CLI either defines that or does not. A CLI that lacks something is never an error by itself.

**The file.** `models.parse` accepts two new tables beside `[dispatch]` and `[rounds]`. The example below is an excerpt.
- `[clis.<cli>]`, for a CLI in `models.CLIS`, holds any of the aliases `xlight`, `light`, `heavy` and `ultra`. Each is `{ model, effort?, context? }`, and `model` must match the CLI's `MODEL_OF_CLI`. A CLI may define any subset of them. The table also holds `models` (optional: the CLI's other model ids), `runtime` (optional: the default is the CLI's one local runtime), and agent's `max_calls` and `max_minutes`, which stay required as today.
- `[activities.<name>]` holds `max_tokens`, the step's budget and today's role cap. The runner kills a step past it, and a subagent in a session has no cap. The table also holds a setting for `easy`, `normal` and `risky`, or `all`, which a level key overrides. A setting is an alias name or `{ model, effort?, context? }`. On a new-shape walk, every activity needs a setting at every level.
- These activities are set per level: design, design-review, raft, raft-review, code and code-review. These have one setting (`all` only): idea, idea-challenge, final-review and approve. design-answer, code-answer, final-answer, trace and fix use the writer's setting, as f0420's table says. f0420's config name `final` is `final-review`.
- `models.PAIRS` lists each writer and reviewer: idea/idea-challenge, design/design-review, raft/raft-review, code/code-review and code/final-review. raft-review is new, because raft-mode review ran on the writer's own `raft` role.
- `effort` is passed as today: claude `--effort`, grok `--reasoning-effort`, agent `<id>[effort=e]`. kimi has no flag, so on kimi it is advisory. `context` is the context window in tokens. claude-cli honours `context >= 1000000` as `--model <id>[1m]` (E9). Everywhere else, the Agent tool included, it is advisory: `./zn model` prints it and nothing checks it.
- A closer file replaces an alias, a level's setting or a `models` list whole, and `max_tokens` or `runtime` as a single value. `rank` (with `strongest` and `forRaft`), `author` (the pairs replace it), `fallbacks` and a role's `cli` go. The message for an unknown table lists `clis, activities, dispatch and rounds`.

```toml
[clis.claude]
xlight = { model = "claude-haiku-5-5", effort = "low" }
light = { model = "claude-sonnet-5-5", effort = "medium" }
heavy = { model = "claude-opus-5-5", effort = "high" }
ultra = { model = "claude-fable-5-2", effort = "xhigh", context = 1000000 }
[clis.grok]                     # partial: light only, so grok takes no review
```

**The legacy form.** Until step 9, `[roles.*]` and `[fallback.*]` parse as they do today.
- A walk with no `[activities]` in any file is legacy. Each activity, at every level, comes from its role: design-review from design-challenge, raft-review from raft, code from implementation, and the rest by name. The role's `cli` delivers the role's model and effort, and each `fallbacks` CLI delivers its `[fallback.<cli>]` model with the role's effort. `max_tokens` is the role's.
- A legacy walk skips the load-time same-model check, because today's design and design-challenge are both Opus. Its `author` still refuses the author's model at use.
- When any file on the walk has `[activities]`, roles and fallbacks are ignored. Step 9 refuses both tables with `{path}: [roles] and [fallback] are gone: aliases go in [clis.<cli>] and each activity's setting in [activities.<name>]`.

**Resolution (`models.luau`, pure).** `Spec` gains `alias: string?` and `context: number?`.
- `models.config(layers): Config` merges the walk and runs the load checks. Every function below calls it, so a bad file fails before any activity starts.
- `models.resolve(layers, cli, activity, level: rounds.Level?, author: string?): (Spec?, string?)` treats a nil level as `normal`. An alias resolves when the CLI defines it. A specific model resolves, with its own effort and context, when the CLI has it (one of its aliases or its `models` list names it). Otherwise it returns nil and `{cli} does not define {alias}` or `{cli} does not have {model}`. When `models.sameModel(spec.model, author)` it returns nil and `{model} wrote the text: a reviewer never runs on the writer's model`.
- The author is the model that wrote the text. `./zn idea` passes the draft's recorded model, as today. The dispatcher passes the `model` of the item's latest spend row in the writer's phase, or none without one. f0420 passes the model on the writer's release event.
- `models.can(layers, cli, activity, level): boolean` is `resolve(...) ~= nil` with no author.
- `models.canList(layers, cli): { string }` gives every `activity/level` pair that `can` gives, in `ACTIVITIES` order, then easy, normal, risky. A one-setting activity appears at each level, so f0424's `register --can` and f0420's filter match by plain membership.
- `models.need(layers, activity, level): string` gives the alias name or the specific setting's `models.id`, as in `waiting for a worker with code-review/normal (heavy)`.
- `models.sameModel(a, b)` is true when a and b are equal once a trailing `-low`, `-medium`, `-high`, `-xhigh` or `-max` is removed. Ledger ids carry the effort.

**Load errors**, each `{path}: …` naming the closest file: `clis.<k> is not a supported CLI (…)`; `clis.<cli>.<k> is not an alias or setting (xlight, light, heavy, ultra, models, runtime, max_calls, max_minutes)`; `clis.<cli>.<alias> has no model`; `clis.<cli>.<alias>.model is <m>, not a model of cli <cli>`; `activities.<k> is not an activity (…)`; `activities.<a>.<k> is not a level (easy, normal, risky, all)`; `activities.<a>.<k>: <a> has one setting for every level: write all`; `activities.<a>.<lvl> names <v>, which is not an alias (xlight, light, heavy, ultra)`; `activities.<a> has no setting for <lvl>`; `activities.<a> has no max_tokens`; `activities.<a>.<lvl> needs <need> and no CLI in [clis] delivers it`; and `at level <lvl>, <writer> and <reviewer> both resolve to <model> on <cli>: a reviewer never runs on the writer's model` (`at every level` for the idea pair; effort and context are ignored).
