# f0421: Risk scaled rounds and models

## Problem
- One review round is enforced for every ticket whatever its risk (`dispatch.filing` refuses a second, and the skills z-design, zz-review, z-raft, zz-execute and zz-rules say so).
- The worker's next action stays on "review" forever after a review said changes, even when every finding is answered, because `workread.reviewState` counts only an approve verdict.
- `.models.toml` gives one model per role whatever the ticket, with fallback lists to other CLIs.
- Only `./zn dispatch` reads `.models.toml`, so no activity in a person-started z-work session gets a configured model.
- Design review takes 43% and design 25% of recorded agent-minutes across done tickets, and nothing lets a low-risk ticket spend less.

## Non-goals
- No fallback to another CLI or another model when the configured one cannot be delivered.
- No automatic repair of a configuration that gives a writer and its reviewer the same model.
- No change to what a reviewer checks or how findings are written.
- No guarantee that a review settles within its maximum rounds; what happens at the maximum stays with the human.

## Solution
- Each ticket records a risk level (easy, normal or risky), chosen at design from its size, complexity and how easily it is fixed or reverted, and the owner can overrule it.
- TOML sets the maximum review rounds per stage (design, implementation) for each level, and a separate maximum for the idea stage, where the level is not yet known.
- The skills state that these numbers are maximums and that a review should find everything in its first round.
- A review whose findings are all answered counts as settled, so the worker's next action moves past "review".
- TOML defines the aliases xlight, light, heavy and ultra per CLI, each as a model, effort and context.
- TOML gives each activity (design, design review, code, code review), per level, either an alias or a specific model-effort-context.
- The seed is: easy writes design and code with xlight and reviews both with light; normal writes with light and reviews with heavy; risky writes with heavy and reviews with ultra.
- The seed defines the four aliases as four different models on every CLI it configures, so every seeded level gives a writer and its reviewer different models.
- The final gate uses ultra at every level.
- When the configuration is read, any level and stage whose writer and reviewer resolve to the same model name (whatever the effort and context) is refused with an error naming the level, the stage and the model.
- That refusal happens before any activity starts, and no model is ever quietly replaced.
- When the active CLI cannot deliver the model an activity names, that is an error telling the person to switch configuration or CLI.
- The same configuration is read and applied in a person-started z-work session and under `./zn dispatch`.
- This ticket takes over the round rules of f0417, c0418, c0251, c0306 and c0325 and the note in c0166.

## Design
Slice 1 of 2: rounds and settled reviews. Aliases, models per activity and the same-model refusal are slice 2.

**Rule.** The latest round of a review counts, and earlier rounds are history. Approve settles the review. A round that is not approve and not answered waits for the author's answer. If it is answered and below the maximum, the next round is filed. If it is answered at the maximum, it is settled. The gates (`./zn done`, `status prepared`) still require only that the latest round is approve or answered. A maximum is not a minimum. `./zn work next`, the dispatcher and `./zn idea` run the loop.

**`rounds.luau` (new, pure).**
- `export type Level = "easy" | "normal" | "risky"`, `export type Stage = "idea" | "design" | "code"`.
- `export type Limits = { idea: number, design: { [Level]: number }, code: { [Level]: number } }`. `rounds.DEFAULT` holds the seed: idea 3, design and code `{ easy = 2, normal = 5, risky = 9 }`.
- `rounds.level(value: string?): (Level?, string?)`: nil or "" gives `normal`, and easy, normal or risky give themselves. Any other value returns nil and `risk is <v>: easy, normal or risky`.
- `rounds.highest(levels: { Level }): Level`: the raft rule, risky > normal > easy, and `normal` for an empty list.
- `rounds.max(l: Limits, stage: Stage, level: Level): number`, where idea ignores the level.
- `export type Round = { number: number, verdict: string?, answered: boolean }`, `export type Step = { kind: "file" | "answer" | "settled", number: number, max: number }`.
- `rounds.verdict(text): string?` is the one `Verdict:` reader (it replaces `workread.verdictOf`).
- `rounds.KINDS = { design = {"design-review-", "design-refute-"}, code = {"review-", "refute-"}, final = {"final-review-", "final-refute-"} }`.
- `rounds.latest(files: { [string]: string }, kind: string, doc: string, isBacklog: (string) -> boolean): Round?` takes the highest-numbered review in `files` (name to text, matched by plain prefix and never by a pattern built from the prefix) and the refute file of the same number ("" when there is none). `answered` is `openlist.unanswered(...) == nil`.
- `rounds.next(latest: Round?, max: number): Step` follows this table.

| latest | verdict | answered | N vs max | kind | number |
|---|---|---|---|---|---|
| nil | | | | file | 1 |
| N | approve | any | any | settled | N |
| N | not approve (or none) | no | any | answer | N |
| N | not approve (or none) | yes | N < max | file | N+1 |
| N | not approve (or none) | yes | N >= max | settled | N |

**One definition of answered.** The body of `main.reviewProblem`, from after its approve check to its end, moves verbatim into `openlist.unanswered(p: { review, refute, doc, reviewName, refuteName: string, isBacklog: (string) -> boolean }): string?`. That body checks the missing answers, the `consequences:` of a fixed answer, the deferred rules, the `openlist.problem` gap, and a verdict that has no findings. `isBacklog` replaces its `store.find` call. `reviewProblem` keeps its first lines and calls it, so done's words do not change. `designOpen` is unchanged.

**`[rounds]` in `.models.toml`.**
- `models.parse` accepts a `[rounds]` table and stores it as `layer.rounds`, keyed by the leaf (`idea`, `design.easy`, …).
- Errors, all `{path}: …`:
  - `[rounds] is a table`
  - `rounds.<k> is not a setting (idea, design, code)`
  - `rounds.<stage> is a table of levels (easy, normal, risky)`
  - `rounds.<stage>.<k> is not a level (easy, normal, risky)`
  - `rounds.<key> is a whole number, at least 1` (uses `count`)
- The message for an unknown table becomes `(the file has roles, fallback, dispatch and rounds; skill tables are gone)`.
- `models.rounds(layers: { Layer }): rounds.Limits` starts from `rounds.DEFAULT`, and the closest file replaces only the leaves it sets, so a walk with no `[rounds]` gives the defaults.
- The root `.models.toml` gets the seed as `[rounds]`, with `idea = 3`, `design = { easy = 2, normal = 5, risky = 9 }` and `code = { … }` the same.

**`risk:`** is an issue frontmatter key read through the existing readers. No new reader is added.
- `workread.frontText` already holds `memberFront`.
- `store.readFront` in the dispatcher reads the author's worktree copy.
- `audit.front` validates it. `audit.run` adds an error `risk` naming the document when `rounds.level` returns a problem, and when a raft document carries `risk:`, with the message `a raft's risk is its members' highest`.
- Every use passes the value through `rounds.level`. A raft's level is `rounds.highest` of its members' levels. The idea stage has no level.
- The owner overrules the level by editing the key. z-design proposes it.

**Callers.**
1. `dispatch.filing`: `FilingInput` gains `step: rounds.Step?`. When the mode is design, code or final and `step` is given:
   - `file` returns `{ number = step.number }`.
   - `answer` refuses with `{dir}/{prefix}NNN.md is not answered: answer every finding in its refute file before round N+1`. At the maximum it reads `…: it is round N of M, the last; what stays open goes to the human`.
   - `settled` refuses with `{dir}/{prefix}NNN.md settled the review (approve, or answered at round N of M): there is no further round`.

   Raft mode (its `grouped:` rule), stream mode and a call with no `step` keep today's code and words.

   `dispatcher.filingNow` computes `step` for design, code and final:
   - The files are `reviewsIn` of the review prefix and the refute prefix.
   - The doc is `{cwd}/{item.doc}`.
   - The level is the issue's own, or the highest of a raft's members' read in `cwd`.
   - The limits are `models.rounds(walk(item.dir))`, the pinned main.
   - A bad `risk:` or `[rounds]` raises an error before any CLI starts.
2. `workread.build` and `work.forRaft`:
   - `sideFile` also takes `refute-NNN.md` and `final-refute-NNN.md`.
   - The layer-tip read also takes the raft's own `<R-id>.md`. The raft doc is read in the same order as the side files: the working tree's copy, then the top layer's, then origin/main's.
   - Every `.models.toml` that `models.folders(at.dir)` names joins the one existing `git cat-file --batch` at `origin/main`, and `models.walkAt(dir, readFromBatch, function() return false end)` parses it. Only main's file counts.
   - `codeReview` is "none" (file 1), "open" (answer), "due" (file N+1) or "resolved" (settled). `finalReview` uses the same values, with "approved" for settled.
   - `RaftFact` gains optional fields: `codeRound`, `codeMax`, `finalRound`, `finalMax` (all `number?`) and `roundsProblem` (`string?`, set for a bad risk or a bad `[rounds]`).
3. `./zn idea`: a loop in `cmd.idea` (details under "The idea stage").
4. `./zn done`: through `openlist.unanswered` only (see "One definition of answered").

**What `./zn work next <R>` prints.** The action words do not change, so `RESUMED`, z-work and the specs that read actions keep working. The reason text comes after the action word. "of at most M" is dropped when the max is nil.

| state | action | reason text |
|---|---|---|
| `roundsProblem` set | `none` | the problem |
| code none | `review` | `Run code review round 1 of at most M (zz-review code mode; zz-execute Phase 4). Commit review-001.md, then ask again.` |
| code open | `review` | `Answer review-NNN.md in refute-NNN.md (zz-execute Phase 4); anything refuted or an unclosed high goes under ## Open to the human. Commit, then ask again.` At the maximum it adds `This is round N of N, the last.` Today's sentence `Do not guess a ruling under ./zn dispatch; …` is kept. |
| code due | `review` | `review-NNN.md is answered and its verdict is not approve: run code review round N+1 of at most M, commit it, then ask again.` |
| code resolved | | moves on to `trace` |
| final none | `final-review` | today's text |
| final open | `final-review` | as for code, with `final-refute-NNN.md` and Phase 5 |
| final due | `final-review` | `Run final review round N+1 of at most M (zz-execute Phase 5); it refills trace.md.` |
| final approved | | `traceOk` and then `done`, as today |

**The idea stage.** `cmd.idea` keeps its one command. After the draft it loops:
- `step = rounds.next(latest, models.rounds(layers).idea)`, and it stops unless `step.kind == "file"`.
- It challenges the current prose and writes `idea-review-<NNN>.md`.
- Unless the verdict is approve with no findings, it revises with `idea.answerPrompt(current, findings)`, where `current` replaces `rough` from round 2 on, and writes `idea-refute-<NNN>.md`.
- It records `latest = { number = N, verdict = verdict, answered = true }`.

Only the last round's `idea.openLines` go under `## Open to the human`, because finding ids restart at F1 each round. `idea-review-001.md` always exists, so `designRefusal` and its readers do not change.

`rounds.luau` holds the rule, `openlist.unanswered` holds "answered" and `models.rounds` holds the limits. A new review kind joins `rounds.KINDS`.
### Usability
Every refusal names the file, the round and the maximum. The action words do not change.

### Risks
- Rulings under `## Open to the human` are committed on the layer, not on main. A `work next` that read only origin/main's raft doc would call an answered review open, which is why the doc is read in the same order as the side files.
- Each final round refills `trace.md`. `traceOk` stays tied to the settled final review.
- `designOpen` and `done` do not demand further rounds, so a person can land after an answered round 1 below the maximum. That is by choice, because the numbers are maximums.
- The author's branch sets `risk:`, so it could lower its own maximum. The change shows in the PR diff, and the owner overrules.
- `./zn metrics` and the board count review files, so more rounds show as more rounds and need no change.
- `RaftFact`'s new fields are optional, so promoted `f0399/pick.spec.luau` still type-checks.
- In `tests/tooling/idea.spec.luau`, the stub challenger always says revise. Its `ROLES` fixture gains `[rounds]\nidea = 1` so `idea: calls 3` keeps its meaning.
