### F1 [medium] A recorded model is not fixed for the process: a registration under another session id replaces it, with no refusal, and releases the worker's claim as lost
Where: `z-nile/go/internal/live/ops.go:314-318` (the session branch, before the model check) and `320-331`; `z-nile/go/cmd/znlive/opts.go:53-71`; `refute-005.md` F1 ("only a new process changes it").
Evidence: probe. A worker `agy-501@h` registers `gemini-4-neon-high (declared)` and claims `R0050`. The same process registers `gemini-4-argon-high (declared)` with a session id: `map[ok:true ...]`, events appended `[released/lost gone/ registered/]`, no claim left, and the worker now holds `model="gemini-4-argon-high"`. The session's next ordinary call (no session id) is accepted too and swaps it back (`[gone/ registered/]`). The engine sends no `--session`; the `znlive` client takes it from `CLAUDE_CODE_SESSION_ID`, `KIMI_SESSION_ID` or `GROK_SESSION_ID`, while the engine's CLI stays agy because `ZN_CLI` is read first. So `GROK_SESSION_ID=x ZN_MODEL=gemini-4-argon-high ./zn work next` in a Neon session is registered, handed Argon's work, and the Neon claim is given up as lost. By reading: `ZN_WORKER=<any id>` skips `register` altogether (`workerlive.luau:438-441`), and `ZN_WORKER_PID=<another live pid>` makes a second worker, each with the variable's model. A registration that sends the bare spelling of the recorded id turns `declared` off and appends an event (probe: `declared=false` after `"gemini-4-neon-medium"`); the Go test does not look at the flag there.
Critique: the session branch is older than S1a, and round 1 missed it. The fix round then stated the rule as "only a new process changes it", and the design now says the registration fixes the model. For the variable alone that holds. With one more variable it does not, and the first registration's claim is released while its work goes on.
Consequences: keeping the model across a session change of one process is right for claude too (a `/clear` is a new session id on the same process, and claude sends no model). `ZN_WORKER`, `ZN_WORKER_PID` and `./zn live gone` cannot be closed without a reader of the session's model, so the design has to say what the record is: a check of the variable, not a lock.
Recommendation: in `register`, judge the model against the worker of the same process (CLI, pid, start) before the session branch: a different non-empty model is refused whatever the session id, and the kept model and its `declared` flag are carried onto the worker the session change creates. Once `declared` is set for a process it stays set. Go cases: another model under another session id is refused and the claim is still held; the same model under another session id keeps the model; the bare spelling leaves `declared` true. In the design and in AGENTS.md's line, name what the record does not cover (`ZN_WORKER`, `ZN_WORKER_PID`, `ZN_CLI`, `ZN_DISPATCH` and the session variables are the person's and the dispatcher's too), or put that limit to the owner under question 3.
