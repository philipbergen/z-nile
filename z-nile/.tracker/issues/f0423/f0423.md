# f0423: Approval session

## Problem
- `./zn approve <issue-id>` records one ticket's approval and `./zn guesses` prints one ticket's guesses, but no command gathers every ticket in a tributary or raft that waits on approval and walks the owner through each guess.
- A raft whose ticket depends on a ticket in another, unapproved raft starts from `main` rather than from that ticket's layer branch, and a ticket whose guess sits at the idea or design stage has no layer branch for dependent work to build on.
- No command sends a ticket back to the stage that owns a rejected guess (idea, design or code), rebuilds what was built on top of it, or writes a lesson for the changed guess.

## Non-goals
- The layering inside one raft stays as it is: one layer branch per ticket, each built on the one below, landed by one `--no-ff` merge.
- The worker does not wait for approval before it designs, rafts or builds; approval gates only the final gating review and the landing.
- No web page, SPA or separate app is built: the walkthrough is an agent session the command starts.
- c0267's rule and f0339's explanation job are not delivered separately; this ticket replaces both.

## Solution
- `./zn approve <tributary | raft | ticket>` lists every ticket in that scope that waits on approval and starts the owner's AI CLI on a walkthrough that, for each ticket, explains the ticket in plain terms and then each guess: what was open, what was chosen, the alternatives, their pros and cons, and what changing it now costs.
- The walkthrough records each approval per ticket with the existing design, checks and guesses hash, and no raft with an unapproved guess enters its final gating review.
- A raft that depends on a ticket in another, unapproved raft starts its first layer from that ticket's layer branch instead of `main`; when the prerequisite's guess sits at the idea or design stage, that ticket's prep branch is the base, and the dependent layers are restacked onto its layer branch once it exists.
- When every ticket in a chain of dependent rafts is approved, the rafts land from the bottom up, each with its existing `./zn done` merge.
- A change the owner asks for sends the ticket back to the stage that owns the guess, puts it back in the work queue once the change is made, restacks or rebuilds every layer and raft built on top of it, and writes one lesson per changed guess under the step that guessed wrong.

## Design
The walkthrough is an agent session that `./zn approve` starts. The command does the mechanical work: it finds what waits, writes a brief and starts the session. The session explains each ticket and collects rulings, but it never records them. Nothing is recorded until the session has ended and the person types `y` at the command's own prompt, once per ruling. New pieces: `waiting.luau` (the rule), `approverun.luau` (the run folder), `rework.luau` (the `rework.md` format), the command `./zn rework`, and the skill `z-approve`.
### 1. What waits for approval (`z-nile/engine/waiting.luau`, pure)
`waiting.of(f: Fact): Verdict` is the one rule. The approval queue, `work.forRaft`, `./zn done` and f0422's board count all call it, each with facts from the place it already reads. A `Fact` has five fields. `stage` is `draft` while the design is not `ready`, `built` once there is a layer with commits, and `designed` in between. `approval` is `none`, `bad`, or `holds`, `guesses` or `stale` as `approval.standing` reports it, with the changed parts. `guesses` is the guess count. `lands` says the raft was readied with `Lands: approved`. `reworkOpen` and `reworkSince` are defined in section 6. A `Verdict` is `{ state: "waits" | "clear" | "working", why: string }`. The first rule that matches decides it:
1. `stage == draft` or `reworkOpen`: `working`. There is nothing to rule on yet, and the brief lists the ticket as "still being worked".
2. `approval == bad`: `waits`, "approval.md does not parse".
3. `reworkSince`: `waits`, "reworked since approval (W<n>)".
4. `approval` is `guesses` or `stale`: `waits`, "changed: <parts>".
5. `approval == none`, and `guesses > 0` or `lands`: `waits`, "no approval (<n> guesses)".
6. Anything else: `clear`.

`waiting.unit(verdicts)` gives a raft or raftless ticket `waits` if any member waits, else `working` if any member is working, else `clear`. f0422 counts the `waits` units. `waiting.order(units, layers)` sorts by `depgraph.bands`, lowest first, then each raft's members in layer order, then by id. So the bottom of a stack is ruled before anything built on it.
### 2. The command line
```
./zn approve <issue-id> [--check|--publish]               unchanged: records one ticket directly
./zn approve [<R-id>|<tributary>] [--walk <issue-id>]      the walkthrough; add --queue to only write the run and print it
./zn approve --ruling <run> <issue-id> approve
./zn approve --ruling <run> <issue-id> change --stage idea|design|code [--guess G<n>|none] --note "<owner's words>" [--lesson "<rule>" --ask "<question?>"] [--into <skill>/<slug>]
./zn approve --apply <run>                                 asks y/N for each ruling, then records or reworks
./zn rework <issue-id> --stage … --guess … --note … [--lesson … --ask … --into …] | --lessons
```
**Scope.** `R\d+` is that raft plus every raft and raftless ticket it depends on, directly or not, that waits, so a stack is ruled as a whole. `--walk <id>` is that one ticket, and a bare `[fdc]\d+` still records directly, as today. Any other word is a tributary read through f0422's reader, and an unknown name is refused with the list of names. No argument means the folder's project, as `./zn list` reads it. The facts come from `approveplace.load`, the place where `./zn approve <id>` records, so the queue never shows a ticket that recording can't find. `Copy` gains a `guesses` count. Rework facts come from `origin/main`, the only place `rework.md` is published.

**Where each form runs.** The walk form, `--apply`, a bare `<issue-id>`, `--publish` and `rework` without `--lessons` need a terminal, by both the wrapper's `-t 0` test and the engine's `/dev/tty` test. They are refused while `ZN_DISPATCH` or `ZN_APPROVE_SESSION` is set. `--check`, `--queue`, `--ruling` (refused under `ZN_DISPATCH`) and `rework --lessons` need no terminal. The PreToolUse hook (`boundcmd.luau`) refuses an agent's Bash command that runs a terminal-only form of `zn approve` or `zn rework`, directly or through `script`, `expect` or `unbuffer`.
### 3. The run and the session
`approverun.luau` is the one reader and writer of `<main checkout>/.cache/approve/<run>/`, which is ignored. `<run>` is `YYYYMMDDTHHMMSSZ-<4 hex>`. The folder holds four files, `queue.tsv`, `brief.md`, `rulings.tsv` and `applied.tsv` (what `--apply` did with each ruling, so a later `--apply` does not ask twice; written only by `--apply`). The command prunes runs older than 14 days when it makes a new one, never one with a ruling not yet applied. `queue.tsv` also holds the contract's part hashes (to name what changed) and the verdict's reason. The three above are:
- `queue.tsv` has each ticket's id, place, contract hash and verdict.
- `brief.md` has, per ticket in queue order: the title, the stage, why it waits, the doc path, the guesses verbatim with their `Guess (prep) G<n>` places, the rework history, the layer and PR when built, and up to three `ruled` lessons sharing words with the guesses.
- `rulings.tsv` is written only by `--ruling`, which refuses a ticket not in the queue, a second ruling on the same ticket and guess, and an ask with no `?`.

The walk form writes the run, then starts the CLI that `[roles.approve]` in `.models.toml` names, seeded as `model = "claude-opus-5-5"`, `cli = "claude"`. It runs interactively as `claude --model <m> "<opening line>"`, with stdio inherited and `ZN_APPROVE_SESSION=<run>` set. The opening line names the skill, the run and the brief. When the CLI exits, the command runs `--apply <run>` on the same terminal. A CLI the command cannot start interactively is refused, and the refusal names the `--queue` path. That path is also how a person already in an agent session gets a walkthrough. They type `/z-approve R0050`. The session runs `--queue`, walks the tickets and writes rulings, then asks the person to run `./zn approve --apply <run>`. E2 settles whether Claude Code's `!` prefix can run it.
### 4. Why the record stays the person's act
- The session can write only `rulings.tsv`, which is ignored. `--apply` reads `y` from `/dev/tty` once per ruling. Each prompt shows the ticket and the ruling; for a change it also says what happens (for example "R0050 goes back to the backlog"). Any other answer records nothing, and the ruling waits for a later `--apply`.
- An approval is recorded only while the ticket's contract hash equals the one in `queue.tsv`, which is the design that was walked. Otherwise `--apply` refuses the ticket, naming the parts that changed. The row's `who` is `<user.name> (walkthrough <run>)`; the parser is unchanged, and only the printout reads `who`. A rework entry records the run too.
- Guards keep an agent off the record. The real one is the engine: every recording form (the walk form, `--apply`, a bare id, `--publish`) refuses while `ZN_DISPATCH`, `ZN_APPROVE_SESSION` or any agent marker of `agentenv.luau` (`CLAUDECODE`, `AI_AGENT`, `CLAUDE_CODE_SESSION_ID`, `CURSOR_AGENT`, `GROK_SESSION_ID`, `KIMI_SESSION_ID`, `KIMI_CODE_SESSION_ID`) is set, and without a terminal. The wrapper's stdin test and the hook (which refuses the obvious forms, also through `script`, `expect`, `unbuffer`, `./zn run --`, `sh -c 'exec "$@"'` and an `unset`/`env -u` of a marker) come first but are seatbelts, and the skill says the rule. A determined agent that clears its own environment is outside what any of them can stop; the person's `y` at the terminal, once per ruling, is the record.
- What the owner is shown is what the approval records. The brief is read from the place the approval will record (origin/main, or the prep worktree), carries each ticket's Problem, Solution and every guess in full with that place's revision, and the run is refused when this checkout's copy of a waiting ticket differs from it. `--apply` does not trust the folder: it recomputes each ticket's verdict itself, refuses a ticket that does not wait now or whose design is not the one walked, ignores a duplicate ruling, counts "already approved" apart from "approved", and prints, before each question, the title, why it waits, each guess's `Chose:` text and where it records. A change ruling is shown plainly as not carried out and shown again by the next `--apply` until `./zn rework` exists (step 3). The walk form hands its own in-memory queue to `--apply`; a separate `--apply` refuses a folder with no `queue.tsv` in the expected shape.
### 5. The skill `z-nile/skills/z-approve/SKILL.md` (outline)
1. If you were handed no brief, run `./zn approve <scope> --queue`. Read the brief once. Tell the owner how many tickets there are, the order, and why: work that others build on comes first.
2. For each ticket, read `./zn capture <id>` (what was asked), its Design and acceptance criteria, `./zn guesses <id>` and its rework history. If it is built, also read its layer's `git diff --stat` and `gh pr view`. Explain the ticket in at most six plain sentences: the problem, what changes for the owner, and what exists so far.
3. Then take each guess in turn. Cover where it arose, what was open, and one concrete example. Give each option, the chosen one and at least one other, with its pros and cons. Say what changing it now costs: which stage it goes back to, what is rebuilt, and which rafts sit on top. Point out when two guesses pull against each other.
4. Use plain words. Don't use "contract", "layer", "hash" or "restack" without a one-line meaning, and never give an id without its title. Answer questions from the files, by reading code, or by running read-only commands. If you don't know, say so and go look. Never guess an answer.
5. For each ticket ask "approve, change something, or skip?", and act only on an explicit answer. To approve, run `./zn approve --ruling <run> <id> approve`. A skip writes nothing.
6. For a change, restate it in one sentence and agree the stage. The default comes from the guess's step: design and raft go to design, build goes to code.
7. Draft the lesson with the owner: the rule, and the question that would have caught it. Search `./zn lessons --tag ruled <words>` for a lesson to extend with `--into`. Then run `--ruling … change` once per changed guess.
8. Never run another form of `./zn approve`, never run `./zn rework`, and never run anything that fakes a terminal.
9. At the end, list the rulings. If the command started you, tell the owner to exit so the command can ask y/N; otherwise tell them to run `./zn approve --apply <run>`.
10. When every ticket of a stack is ruled approve, say that the stack is clear and what lands it (section 8).
### 6. Rework (`./zn rework`, `z-nile/engine/rework.luau`)
`--apply` runs this for each confirmed change, and a person may run it by hand. Like `./zn approve`, it publishes from a detached scratch worktree `.worktree/.rework-<id>`. It makes one tracker-only commit, `tracker: rework <id> <stage> W<n>`. That commit appends one entry to `<issue dir>/rework.md` and changes at most the document's `status:` and `design:` lines. `publish.luau`'s tracker-only rule allows exactly that, as it allows `close`'s `wont_do:` line. The file is append-only, and its parser refuses a repeated or unknown key:
```
# rework
## W1 (design, 2026-11-20T18:42:00Z, walkthrough 20261120T184000Z-a1b2)
- guess: G2                      (or none)
- rejected: <contract hash>      (code stage: patch <git patch-id --stable of the layer's finish commit>)
- owner: <the owner's words, one line>
- lesson: <rule> / ask: <question?> / into: <skill>/<slug>   (optional, one line each)
```
| stage | refused for | status, design | what goes stale | how it returns to the queue |
|---|---|---|---|---|
| idea | an active member, unless run from the main checkout, where `--apply` first offers `./zn stop <R>` | `new` (`preparing` kept), `draft` | the idea review, the design reviews, the approval | `draft` action, whose text says to run `./zn idea <id> --text "<owner>"` first (E3) |
| design | the same | `new` (`preparing` kept), `draft` | the design reviews (the next round is numbered after them), the approval | `draft` action, taken even inside a backlog raft; z-raft's record check regroups the raft once the ticket is ready |
| code | a ticket with no finished layer | unchanged | the layer's finish, the layers above it (`./zn restack`), `trace.md`, and the layer's code review (a new round, within f0421's maximum) | new `rework` action on that layer: change the code, `./zn finish` again, then `./zn restack <R>` |

Every file is kept, and `guesses.md` stays append-only: the overruled guess stays as written, and the entry records the ruling.

An idea or design entry is open (`reworkOpen`) while the ticket's design on `origin/main` is not `ready`, or while its contract hash there still equals `rejected`. A code entry is open while the layer's finish commit keeps the same patch-id (E4 checks that a restack preserves it). The design is part of the approval hash, so changing a guess or the design ends the old approval. A code-only change leaves the hash as it was, which is why rule 3 (`reworkSince`: the newest entry is later than the last approval row) sends the ticket back to the owner. Whatever is built on top is restacked or rebuilt by f0420's cross-raft restack; this ticket only relies on it.
### 7. The lesson
A ruling that changes a guess must carry `--lesson` and `--ask`, and the rework entry keeps them. The worker who takes the rework is the lead of that prep or raft (zz-arch, Lessons). Its `draft` or `rework` action runs `./zn rework <id> --lessons` in its own worktree. For each guess in the entry that has no lesson yet, it writes `z-nile/skills/<skill>/lessons/<slug>.md`, or with `--into` adds a dated `**Note**` to that lesson. The skill comes from the guess's step: design gives `z-design`, raft gives `z-raft`, build gives `zz-execute`. With no guess it comes from the stage: idea gives `z-ticket`, design gives `z-design`, code gives `zz-execute`. The slug is the title's first six words in kebab case, with `-2` added on a clash. The frontmatter holds `title` (the rule's first sentence), `when` (`build` for zz-execute, `design` otherwise), `tags: [guess, ruled, <step>]` and `check` (the ask). The body is the rule, then `**Why:** <id> G<n> (<step>, <date>) chose "<chose>"; the owner ruled <date> (<run>): "<owner>"`, then `**How to apply:** before a guess like this, ask: <ask>`. The same command adds `- note rework W<n> G<k> overruled by the owner (erred <skill>): <lesson id>` to the issue's `harvest.md`, where `./zn lessons` and the metrics read it. `./zn done` refuses a member whose rework guess has no such note.

The next guess gets better in two ways. z-work's Guess mode, and z-design's and zz-execute's guess lines, say: before `./zn guess`, run `./zn lessons --tag ruled <words>`, follow a lesson that fits, and name it in `--why`. And `./zn guess` prints up to three `ruled` lessons that share words with `--open`.

**An assumption is a guess** (`--open "assumed: …"`). z-design records an unknown that no experiment settles this way. There is no new file and no new step, and f0417's separate record stays parked.
### 8. The final gating review waits; a stack lands
`work.forRaft` returns `wait` just before `final-review` whenever `waiting.unit` says `waits`; today the wait comes only after the final review. The message keeps today's text and adds "or walk them: ./zn approve <R>". `workread` now computes verdicts for every active raft that has a layer, not only for `Lands: approved` rafts whose final review is approved. `./zn done` refuses a member that `waits`. After `--apply`, the command prints a line for each raft in scope whose members are now all `clear`, for example: `R0050, R0060 (built on R0050): approved; ./zn work R0060 takes them through final review and lands them bottom-up`. The landing belongs to f0420. Until f0420 lands, the line names the lowest raft, `./zn work R0050`.
### Seams

### Scalability
A run costs one fetch, then per ticket one `approveplace.load` (4 to 8 git calls) and one `origin/main` read of `rework.md`. `depgraph` is linear, so a 40-ticket tributary is about 300 git calls, a few seconds. `workread` adds one `ls-tree` and one `cat-file` batch per active raft that has a layer. The session's tokens cost the most, and f0421 bounds them.
### Maintainability
A new kind of scope plugs into `cmd.approve`'s resolver, and a new verdict rule goes into `waiting.of` alone. Each format has one reader: `rework.luau` for `rework.md`, `approverun.luau` for the run folder, `lessons.luau` for the harvest notes, and `models.luau` for `[roles.approve]`.

## Acceptance criteria
### Checked
- AC1: for every combination of stage, approval state, guesses, `lands` and the rework facts, `waiting.of` returns the verdict of the first rule (1 to 6) that matches, and `waiting.unit` combines the members' verdicts as section 1 says.
- AC2: `waiting.order` sorts by band, then by layer within a raft, then by id, so the raft a stack is built on comes first.
- AC3: `./zn approve R0050 --queue` lists exactly the waiting tickets of R0050 and of the units below it, in order, with each ticket's hash and guesses in `brief.md`, and writes nothing outside `.cache/approve/<run>/`.
- AC4: `--ruling` writes one row without a terminal, and refuses under `ZN_DISPATCH`, for a ticket not in the queue, for a repeat, and for an ask with no `?`.
