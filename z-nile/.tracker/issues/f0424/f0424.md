# f0424: Live layer daemon

## Problem
- Every claim, release and status change is a git commit pushed to origin/main with retry loops, so two workers on one machine pay a push and a possible retry just to settle who holds what.
- The only record of who carries what is `.cache/work/carriers.tsv`, written by `./zn work next` and read by `./zn work status`; it names the ticket or raft each session holds, but not the worker's CLI, what it can deliver, or the single activity it holds.
- c0265's heartbeat (a heartbeat branch per claim, meant by f0399 to replace `carriers.tsv`) says whether a claim is alive, but not which CLI holds it or what that CLI can deliver.
- A worker that gets `wait` asks again with a model turn, because no waiting process exists.
- Nothing emits an event when a step is recorded, so the board is regenerated on sync and stats are computed on demand from spend rows.

## Non-goals
- The app the daemon serves is a later ticket.
- Porting `./zn` commands to Go is a later ticket.
- A per-project seam for choosing which tests a change needs is a later ticket.
- Replacing git as the store of durable outcomes is out of scope.
- Making claims visible across machines is out of scope: the daemon serves one machine, and c0265's heartbeat branch stays the cross-host signal.

## Solution
- A small daemon written in Go runs on one machine, and every `./zn` command and worker on that machine talks to it through a small language-neutral contract.
- Taking, releasing or heartbeating a claim on one activity of one ticket or raft through the daemon makes no commit and no push.
- A status change that only says "someone holds this" counts as a claim and goes through the daemon, while a status change that records an outcome (a design finished, a review filed, an approval recorded, a raft landed) stays a commit in git as today.
- A claim is atomic: when two workers ask for the same activity at once, exactly one gets it.
- The daemon records each running worker's CLI, what it can deliver, the one activity it holds, its heartbeats and when it is gone; `./zn work status` reads that record in place of `.cache/work/carriers.tsv`.
- Within one machine the daemon's heartbeat is the liveness record that c0265's verdicts (lost, parked) read.
- A waiting worker blocks on the daemon with no model turn and near-zero CPU, and is woken within about a second of a change.
- The daemon records one event for every step forward (an activity claimed or released, a review filed, a layer finished, an approval recorded, a raft landed) with who, what, when, and tokens and seconds when known.
- A reader can follow the event stream live, and the board's workers panel and a live stats view read it.
- The tracker's files in git stay the contract between the daemon and the existing Luau engine.
- The first deliverable is a spike that proves atomic claims under a race, a waiter woken within about a second, and idle cost near zero, before any `./zn` command depends on the daemon.

## Design
The live layer is one Go binary, `znlive`: `znlive serve` is the daemon and every other subcommand is a client. It holds one machine's live state for one repository (who runs, what each holds, the event log) and is never committed or pushed. The spike's three questions are proven (atomic claims, a 6 ms median wake, near-zero idle cost); this design hardens it and wires it in. The tool keeps working without it.

**Where it lives and how it is built (A).**
- One Go module for all of z-nile's Go: `z-nile/go/` (`module znile`, `go 1.24`, standard library only). `cmd/znlive/` holds flags and exit codes; `internal/live/` the state and the ops, pure over requests and events, with no socket or file; `internal/store/` the log, snapshot, rotation and rollup; `internal/wire/` the Unix-socket server and client; `internal/where/` the state directory, socket and binary lookup. A later port adds `cmd/zn` beside it and reuses `internal/`, and one `go vet ./...` and `go test ./...` keep covering it all. **Guess (prep) G1**
- The spike's folder is not kept. Its race tests move into `internal/live` (goroutines) and `cmd/znlive` (processes). Its latency and idle measurements become `cmd/znlive/bench_test.go`, skipped unless `ZN_LIVE_BENCH=1` and run by hand under `./zn run --time 600`.
- One binary per repository: `<main>/.cache/bin/znlive`, built from the main checkout's `z-nile/go/`, whichever worktree calls it. `<main>` is the parent of `git rev-parse --path-format=absolute --git-common-dir`. It is built into a temp file and renamed (`GOCACHE=<main>/.cache/go-build`; the build id, the first 12 hex of the sha256 of the non-test Go sources, `go.mod` and `go env GOVERSION`, is stamped with `-ldflags -X` and kept beside the binary in `<out>.id`). An unchanged id skips the build and the rename, because a replaced binary restarts a running daemon (`z-nile/lib/gobuild.sh`). `ZN_LIVE_ROOT` names another checkout to build from and into (specs use a fixture), and `./zn live build` is the zn script's, not a subcommand of `znlive`. It is built by `./zn live build`, by `./zn live <op>` when it is missing or a `*.go` or `go.mod` under `z-nile/go/` is newer, and by `./zn sync` after its fast-forward. The Luau engine never builds. `ZN_LIVE_BIN` overrides the path: specs set it to the checkout's own build, which the gate makes. **Guess (prep) G2**
- `./zn live <op> [flags]` is handled by the `zn` script itself, as `./zn run` is: it finds or builds the binary and `exec`s it. No Lune starts (a claim and release pair stays near the spike's 4.6 ms) and `main.luau` gains no local. **Guess (prep) G3**
- No Go and no binary: `./zn live <op>` exits 3, saying `live layer unavailable: no Go toolchain and no built znlive (install Go: SETUP.md)`. Everything else still works: emits and pokes are skipped silently, `./zn work status` prints today's `carriers.tsv` lines with the reason on stderr, and the board says "live layer not running". What exit 3 means for f0420's worker commands is f0420's call.
- The gate (`z-nile/check.sh`) gains four stages, run concurrently with the static stages from `z-nile/go/`: `gofmt -l .` (fails on any output), `go vet ./...`, `go test ./...` and the build of `<checkout>/.cache/bin/znlive` (`z-nile/lib/gobuild.sh`). They run with `GOTOOLCHAIN=local`, so an older local Go fails with "Go 1.24 or newer is needed (SETUP.md)" and never downloads a toolchain. The first three run in a full gate, and in an affected or static gate when the change touches `z-nile/go/` (`lune run z-nile/affected -- --touches z-nile/go` prints `yes`, read from the selector's one list of changed paths). The build runs whenever z-nile is picked and `go` is on PATH (about 0.5 s cached), so live specs always find a fresh binary. Without a usable `go` (absent, or older than 1.24), a full gate and a change under `z-nile/go/` fail the gate with one line naming SETUP.md; any other change prints one skip line ("go not found: the Go stages are skipped; the live layer is unavailable on this machine") and passes, and a live spec it selects fails naming `go`. `z-nile/tests/tooling/live-gate.spec.luau` proves both.
- Go tests start their daemons with `--idle-exit 30s`, so a test that dies leaves nothing behind for long. zz-arch's rule 2 becomes "The tooling is Luau on Lune; the live layer is Go in `z-nile/go/`: standard library only, gofmt, vet". SETUP.md lists Go 1.24 or newer.

**One daemon per repository (B).**
- State directory: `<main>/.cache/live/` (mode 0700). It comes from `--dir`, else `ZN_LIVE_DIR`, else the current folder: walk up to the first `.git`. A `.git` folder is the main checkout's. A `gitdir:` file leads through that folder's `commondir` file to the main checkout. Anything else (the fence's sentinel, a bare repository) exits 3. No git process is started per call.
- Socket: `<os.TempDir()>/zl-<uid>-<h>.sock`, where `h` is the first 12 hex of the sha256 of the state directory's real path, or `/tmp/zl-<uid>-<h>.sock` when the first is over 100 bytes. It is made under umask 077 (mode 0600), and its path is written to `<state>/socket`. Clients read that file, so a client with another `TMPDIR` (a sandboxed shell) still finds it. Every request carries `dir` and `proto` (an integer, now 1). A daemon whose own dir or proto differs refuses with exit 3 (its refusal carries `seq`, `events` and `wait` included), so another repository's daemon and an incompatible one never answer. The advice names a command that works: delete the wrong `<state>/socket` pointer for a dir mismatch; wait for the daemon to exit (it does within 10 s of its binary being replaced) or send it SIGTERM for a proto mismatch. A client also refuses a socket file owned by another uid. A refused connection while the socket file exists is retried only while some process holds `<state>/lock` (a shared non-blocking flock tells: `serve` holds it exclusively), so a daemon killed with `kill -9` is refused at once, in milliseconds, and a starting daemon is waited for. Other users are kept out by the 0600 mode and macOS's per-user temp folder.
- Start: the first write op (register, beat, claim, release, gone, stop, emit) auto-starts a daemon when it cannot connect. Read ops (status, workers, claims, events, wait) and `poke` never start one; they exit 3 (no daemon means no waiters to poke). To start, the client flocks `<state>/start.lock` (for at most 2 s) and dials again. If that still fails, it runs `znlive serve` in a new session (setsid) with stdin and stdout closed, stderr appended to `<state>/daemon.log`, and `ZN_BOUNDED_DEADLINE` removed from its environment, then dials every 10 ms for up to 2 s. `serve` gets the client's own `--lost-after`, `--idle-exit`, `--tick-every` and `--check-every` flags when given (specs shorten the daemon's limits this way, never by an environment variable that would leak), and `ZN_LIVE_LOST_AFTER` and `ZN_LIVE_IDLE_EXIT`, when set, reach it through the environment. The variables the bounded runner and the reaper use (`ZN_BOUNDED_*`, `ZN_MEASURE*`, `ZN_RUN_RECORD`) are removed from the daemon's environment, `daemon.log` is moved to `daemon.log.1` at 1 MB, and the daemon is never a reaper target (`znlive` is in neither `TARGETS`, `INTERPRETERS` nor `ORPHANABLE`: E6). `zn live` finds the main checkout from its own `.git` entry with no git process, and rebuilds when a non-test `*.go` or `go.mod` is newer than `<bin>.id` (`gobuild.sh` touches `.id` when the id is unchanged, so an unchanged rebuild is tried once, and never touches the binary); with `ZN_LIVE_BIN` set it never builds. A failed rebuild keeps an existing binary. One instance: `serve` flocks `<state>/lock`, and a loser exits. **Guess (prep) G6**
- Bounded by itself: AGENTS.md exempts `./zn` commands from the `./zn run` rule, and the daemon ends on its own. It exits after `idle_exit` (default 30 min) with no registered worker and no open connection; on `./zn live shutdown` or SIGTERM; and within 10 s of its binary file being replaced, which is the upgrade rule (the next client starts the new build). Every exit writes the snapshot. On shutdown, idle exit and upgrade the listener closes first, waiters and follows are told and cancelled, and requests already in flight finish (each is bounded by its own deadline) before the process exits. A temporary `Accept` error (out of descriptors) is retried with a short backoff and does not end the daemon, and a client retries a refused connection while the socket file exists, inside its 2 s budget, so a full backlog is not reported as "not running".
- A storage failure (disk full, unwritable log) is refused with the word `storage` and exits 3, with one sentence naming the log path: it is the daemon's fault, not a rule the caller broke. A request over 1 MB gets a `usage` reply before the connection closes. A daemon that dies mid-call: the client exits 3 (`live daemon connection lost`). Every op can be repeated safely. Register is idempotent; a claim of a unit the worker already holds answers ok with `again: true`; releasing nothing is refused, naming that. So a caller retries once after exit 3 and reads `claims` again.

**Records (C).** These are JSON objects. Times are epoch seconds with milliseconds (readers show them in PST), and absent values are omitted.
- worker: `id`, `cli`, `can` (a list of `activity/level`, from the caller: the daemon reads no config), `host`, `pid`, `start` (the pid's start time, which catches a reused pid), `session` (`CLAUDE_CODE_SESSION_ID`, `KIMI_SESSION_ID` or the caller's), `mode` (`session`, `run` or `plain`), `started`, `heard`, `state` (`idle`, `working` or `lost`), `stop` (bool), `seen` (the seq of the last reply sent to it).
- claim: `unit`, `activity`, `action`, `step`, `needs`, `model`, `limits` (its classes), `worker`, `since`, plus the caller's `raft`, `project`, `tributary`, `risk` and `round`.
- event: `seq` (from 1, never reused), `at`, `kind` and `host`, then whichever of these apply: `worker`, `cli`, `unit`, `activity`, `raft`, `project`, `tributary`, `risk`, `round`, `model`, `outcome` (`done`, `back`, `failed` or `lost`), `tokens`, `seconds`, `ref` (a commit) and `reason`. The daemon fills `seq`, `at`, `host`, the worker's `cli` and, on `claimed`, `released` and `gone`, the claim's fields. The caller passes everything else: the daemon never learns a project, tributary, raft, risk, round or model by itself. Beats are not events.
- Worker id: the caller makes it, deterministically, so a session finds its id again with no file. It is `<cli>-<pid>@<host>`, plus `.<as>` for a subagent (f0420), where pid is the CLI's own process as f0420 finds it. `register` prints the id and never reads `ZN_WORKER` (a subagent's register would take its parent's id); it uses `--worker`, or builds the id. Every other op takes `--worker`, defaulting to `ZN_WORKER`, which `work run` exports to each session it starts. `--session` defaults from `CLAUDE_CODE_SESSION_ID`, `KIMI_SESSION_ID` or `GROK_SESSION_ID`. Ids and free text are validated: worker, as, unit, activity, cli, session, needs, each `can` entry and each limit class match `^[A-Za-z0-9][A-Za-z0-9._@:/-]{0,127}$` (they reach shell commands, TSV files and HTML); `reason`, `ref`, `action`, `step` and the tags are at most 500 bytes with no control character; a violation is refused `usage` naming the field. A pid below 2 or above the platform's maximum (99999 on macOS, 4194304 elsewhere) is refused `usage`, and so is a pid ps does not know or a zombie (`probe`, exit 3, when ps itself fails): an empty start time would switch the reuse check off. **Guess (prep) G12**

**Operations (D).** Each op is `./zn live <op>` and `znlive <op>`, with flags only. Every reply is one JSON object on one line on stdout, carrying `ok` and `seq` (the newest seq). List ops put their records in one array; `events` prints one event per line. A refusal also goes to stdout, as `{"ok":false,"refused":"<word>",...}` with exit 1, so Luau's `process.exec` and `jq` read it the same way. Every non-zero exit prints one sentence on stderr.

| op | arguments | output, refusals | exits |
|---|---|---|---|
| `register` | `--cli c --pid n [--worker id] [--as s] [--session s] [--mode m] [--can a/l,...]` | `{ok,seq,worker}`; a repeat keeps the claim and appends an event only when a field changed; another `session` on the same id ends the old one first | 0 1 2 3 |
| `beat` | `--worker w` | `{ok,seq,state}`; revives a lost worker; `unknown` | 0 1 3 |
| `claim` | `--worker w --unit u --activity a [--action x] [--step s] [--needs a/l] [--model m] [--limit class=n]... [--raft --project --tributary --risk --round]` | `{ok,seq,claim}`; `held` (with the holder and its activity), `busy`, `cannot`, `cap`, `unknown` | 0 1 2 3 |
| `release` | `--worker w [--unit u] [--outcome done\|back\|failed] [--tokens n] [--seconds n] [--ref sha]` (no outcome records `done`) | `{ok,seq,event}`; `none` | 0 1 3 |
| `gone` / `stop` | `--worker w` | gone: releases (`back`) and removes the worker; stop: sets `stop` and wakes its waiter | 0 1 3 |
| `workers` / `claims` | none | `{ok,seq,workers:[...]}` / `{ok,seq,claims:[...]}` | 0 3 |
| `wait` | `--worker w [--since n] [--timeout s]` (default 540, at most 3600) | the first wake event after `since`, which defaults to the worker's `seen`; `{"ok":false,"refused":"gone"}` at once when its own worker is removed (`gone`, another session under its id, a reaped pid) | 0 1 3 75 |
| `events` | `[--since n] [--kind k] [--follow --timeout s]` | one event per line; `--follow` streams until the timeout | 0 3 75 |
| `poke` | `[--reason r] [--ref sha]` | `{ok,seq}` | 0 3 |
| `emit` | `<kind> [--worker --unit --activity --raft --project --tributary --risk --round --model --outcome --tokens --seconds --ref]` | `{ok,seq,event}`; an op's own kind is a usage error | 0 2 3 |
| `status` | none | `{ok,seq,pid,build,proto,uptime,dir,socket,workers,claims,repaired}` | 0 3 |
| `shutdown` / `serve` | `serve [--dir] [--lost-after s] [--idle-exit s] [--tick-every s] [--check-every s]` | stop the daemon, run it (`./zn live build`, handled by the zn script, builds the binary) | 0 3 |

| exit | meaning | stdout | stderr |
|---|---|---|---|
| 0 | done | the reply | nothing |
| 1 | refused by a rule | `{"ok":false,"refused":...}` | why, naming the holder or the rule |
| 2 | usage | nothing | the usage |
| 3 | unavailable: no binary, not running (read ops), cannot start, connection lost, another repository or proto, a storage failure, the daemon stopping | nothing | which one, and the fix |
| 75 | `wait` or `--follow` timed out | nothing | nothing |

- One claim per unit, whatever its activity, and one per worker. **Guess (prep) G5** A unit's activities (review, answer, the next round) run in order on one worktree, and two at once would race on its branch. `--limit class=n` is f0420's `gate_slots`: the claim is refused `cap` when n held claims already carry that class, checked in the same critical section as the claim. f0420 passes `--limit gate=3` for draft, fix and code, and adds `--limit done=1` for done.
- Wake rule: `wait` returns on the first event after `since` of kind `released`, `gone`, `poke`, `stop` (when it names the waiter) or any emitted kind, that the waiter did not cause itself. A spurious wake is allowed; a missed one is not. A worker's `seen` moves only on replies that show it state (`claims`, `workers`, `status` and a `claim` reply) and on a wait's own return, never on beat, emit, poke, register, release, gone or stop, so the `claims` call behind `work next`'s decision sets the point `wait` starts from and a release between that call and the wait is never swallowed. That closes the spike's gap. A `wait` whose own worker is removed (`gone`, another session registered under its id, its pid reaped) is refused `gone` at once, and any op naming a known lost worker, except `gone` and `stop`, revives it. An open `wait` connection counts as heard.
- Changes to f0420's first contract (f0420 takes these): flags in place of positional arguments; `leave` becomes `gone`; `can` is passed by the caller; the `wake` file and the flock-per-write store give way to the daemon and `poke`; a dead pid's claim is released (event `released` with outcome `lost`) instead of kept with `lost: true`; `--back` becomes `--outcome back`; times are epoch seconds with milliseconds; `wait` takes `--worker`; and exit 3 now means "unavailable". Exits 0, 1, 2 and 75 are kept. **Guess (prep) G10**

**Liveness on one machine (E).** Every 2 s the daemon sends signal 0 to each worker's pid: ESRCH means gone, and EPERM counts as alive. Every 60 s it compares each pid's start time and state: on macOS from the kernel's process table (`sysctl kern.proc.pid`, `internal/where/procs_darwin.go`: no process is started, and it works in the spec jail, which cannot run the setuid `ps`), elsewhere with one `ps -o pid=,stat=,lstart= -p <pids>` call for all of them. A reused pid and a zombie (state `Z`: ended, not yet reaped) are therefore caught on this slower 60 s interval, while a pid that is simply gone is caught within the 2 s tick. A worker whose pid is gone or reused gets `released` (outcome `lost`) when it held a claim, then `gone`. The next worker may then take the unit; what to do with half-done work is f0420's (its takeover reads that event). A worker whose pid lives but which has neither beaten nor held a wait connection for `lost_after` (default 900 s, R0100's stale age) becomes `lost` (event `lost`) and keeps its claim. Any op from it revives it (event `revived`). Silence is measured on the monotonic clock, so a wall-clock jump marks nobody lost, and a tick that arrives much later than its interval (a laptop that slept) gives every worker one fresh interval before it is judged. A live pid keeps its claim however silent: releasing it would hand a half-done unit to a second worker while the first still writes to it. The cost is that a hung session holds its unit until the person ends it, and the board shows that. **Guess (prep) G4** On a restart the pid checks run at once and `heard` is reset to the restart time, so nobody is declared lost before `lost_after` has passed.

**Durability and growth (F).**
- Each event goes to `events.jsonl` in one write(2) before its reply, with no fsync. A daemon crash (`kill -9`) loses nothing. A machine crash loses what the OS had not flushed, which is acceptable: every worker died with the machine, so its claims are moot, durable outcomes are in git, and stats lose seconds. The snapshot, the rotation and the shutdown fsync. **Guess (prep) G7**
- Replay reads `snapshot.json` (seq, workers, claims, `seen`), then the events after its seq. A torn last line is truncated back to the last newline before the first append (`repaired` in `status`); a bad line anywhere else is skipped and counted.
- Rotation: when `events.jsonl` passes 8 MB, or its first event is a day old, the daemon writes the snapshot, renames the file to `events/<first seq>.jsonl` and starts a new one. `events --since` reads closed segments when it needs them. A segment older than 90 days is deleted after its counts are added to `daily.tsv`, one line per PST day, project and kind (`count`, `tokens`, `seconds`), which is kept forever for long trends. **Guess (prep) G8**
- Size: an event is about 300 bytes, and a busy day has at most about 2,000 events (a poke per publish, a claim and release per activity, the step events). That is 0.6 MB a day and 55 MB for 90 days at the high end; `daily.tsv` grows about 2 KB a day.

**Who emits what (G).** `z-nile/engine/livecall.luau` is the one Luau caller: `livecall.run(op, args) -> (code, reply?)`, `emit(kind, fields)`, `poke(reason, ref)` and `snapshot()`. It runs the binary through `process.exec`: `ZN_LIVE_BIN`, else `<main>/.cache/bin/znlive`, where a missing binary costs one stat and returns code 3. It never raises, and the client's connect and reply each time out at 2 s, so an event never blocks or fails a tracker command. `main.luau` requires it inside the functions that use it, so no top-level local is added.

| kind | emitted by | fields the caller passes |
|---|---|---|
| `registered` `claimed` `released` `gone` `lost` `revived` `stop` | the live ops (f0420's `work next`, `work wait` and `work run`) and the daemon | the op's flags |
| `poke` | `published()` in `main.luau`, on every publish | reason (the commit subject), ref |
| `design-started`, `design-filed` | `./zn status <id> preparing`, `./zn status <id> prepared` | unit, project, tributary, risk |
| `review-filed`, `answer-filed` | `./zn commit` when the commit adds a `*review-NNN.md` or a `*refute-NNN.md` | unit, raft, activity, round |
| `layer-finished` | `./zn finish` | unit, raft, round (the layer), ref |
| `restacked`, `readied` | `./zn restack`, `./zn ready` | raft, project, tributary |
| `approved` | `./zn approve` | unit, raft |
| `landed` / `merged` | `./zn done` / `./zn land` (a capture) | raft or unit, project, tributary, ref |
| `spent` | every spend row written: `./zn spend`, the folds in `commit`, `finish`, `done` and `land`, and the dispatcher's rows | unit, activity, model, tokens, seconds |

Stats take their token and second totals from `spent` only. A `released` event's tokens describe that one activity for the workers view and are never added to the totals. **Guess (prep) G11**

**Readers (H).**
- `./zn work status` prints one line per worker from `live workers` and `live claims`: its id, cli, state, the unit and activity it holds and since when (PST), when it was last heard from, and `can`. On exit 3 it prints today's `carriers.tsv` lines, with the reason on stderr.
- `./zn board`: `board.readFacts` puts `livecall.snapshot()` (the workers, the claims and the time taken, or the reason it is unavailable) into the model. The page shows a Workers list headed "snapshot at HH:MM PST", or "live layer not running". f0422's later slice draws the full panel from the same field.
- The app the daemon serves (a later ticket): the daemon gains an HTTP listener on 127.0.0.1. It writes the port and a random token to `<state>/web` (mode 0600), and every request must carry that token. It serves the static page and the event stream as Server-Sent Events: the stream is one-way, an `EventSource` reconnects with `Last-Event-ID` set to the seq, and it needs no dependency. **Guess (prep) G9** Nothing here blocks that: `internal/live` exposes only `Do(Request) Reply` and `Subscribe(since) <-chan Event` and knows no transport, and the spike's hang-up detection on the socket moves into `internal/wire`.

### Scalability
An op is one connection and O(1) map work under one mutex, and `workers` is O(workers). Liveness costs one signal per worker every 2 s and one `ps` a minute. Replay reads the snapshot plus one segment of at most 8 MB. A blocked waiter is one idle process of 5.5 MB using no CPU. A Luau command adds one stat per emit, plus one exec when the binary exists.
### Maintainability
One Go module (`z-nile/go/`) holds all the Go, around one core package with no I/O. `livecall` is the one Luau caller, and `zn`'s `live` case the one shell entry. `livecall` passes the `ZN_LIVE_*` variables to its child explicitly (an edit of `process.env` does not reach a Lune child). A new event kind is one more `emit` call and a row in the table above; a new op is a case in `internal/live` and a row in the ops table.
### Usability
The `zn` usage text gains `live <op>`, and `./zn live` with no op prints the op list. Refusals name the holder, the rule or the fix. In AGENTS.md, the list of ignored files `./zn` writes in the main checkout gains `.cache/bin/` and `.cache/live/`.

## Acceptance criteria

### Checked
- AC1: Of 50 goroutine clients claiming one unit at once, in each of 200 rounds exactly one gets ok and 49 are refused `held`, naming the winner.
- AC2: A claim of another activity on a held unit is refused `held`, naming the holder and its activity. A worker that holds a claim is refused `busy`, a claim past `--limit gate=3` is refused `cap`, and the holder's repeat claim answers ok with `again`.
- AC3: Registering again with the same id and session keeps the claim and appends no event. With another session, the old claim is released (`lost`) and `gone` is appended before `registered`.
- AC4: A worker whose pid ended, or was reused with another start time, is released with outcome `lost` and removed (`released`, then `gone`) within 3 s.
- AC5: A worker whose pid lives but stays silent for `lost_after` becomes `lost` and keeps its claim; its next beat makes it `working` again and appends `revived`.
- AC6: `wait` with no `--since` returns an event appended after the worker's last reply, even one appended before the wait connected. It never returns the waiter's own events, `claimed` or `registered`.
- AC7: After `kill -9` and a restart, the workers, the claims and the next seq are restored, and no worker is lost before `lost_after` has passed since the restart.
- AC8: A log whose last line is torn is truncated to its last newline, `status` reports `repaired: 1`, and the next event is written as a whole line.
- AC9: Rotation at the size limit writes a snapshot and a segment. Replay from them gives the same state as from the whole log, `events --since 1` still returns every event, and a segment past retention leaves its counts in `daily.tsv`.
- AC10: Of 20 `znlive claim` processes started together, in each of 50 rounds exactly one exits 0 and the others exit 1.
- AC11: A second `serve` on one state directory exits and the first keeps answering, and a restart after `kill -9` replaces the stale socket.
- AC12: For a 200-character state directory, the socket path is at most 103 bytes, the socket is mode 0600 and the directory 0700, and a request whose `dir` names another state directory exits 3.
- AC13: A daemon with no worker and no connection exits after `--idle-exit`, and one whose binary file is replaced exits within its check interval; both write the snapshot.
- AC14: Two `./zn live claim` processes for one unit, started together 20 times, give one exit 0 and one exit 1 each time, the second's stdout reading `refused: "held"` with the winner.
- AC15: `./zn live wait --worker A --timeout 10`, started before worker B's release, exits 0 printing that release's seq; `./zn live wait --worker A --timeout 1` with nothing to wake it exits 75.
- AC16: After a registered worker's pid (a fixture `sleep`) is killed, `./zn live claims` no longer lists its claim, `events` holds its `released` (outcome `lost`) and `gone`, and another worker's claim of that unit exits 0.
- AC17: The first write op with no daemon starts one. A read op with no daemon exits 3 and starts none. Then `./zn live status` prints the daemon's pid, build, proto and dir.
- AC18: `./zn live workers` run from a second worktree of the fixture repository answers from the same daemon as one run from its main checkout.
- AC19: With no binary and no `go`, `./zn live claims` exits 3 naming SETUP.md, `./zn work status` exits 0 printing the `carriers.tsv` lines, and `./zn new` and a publish succeed with unchanged output.
- AC20: With a recording fake binary, each command in the Who-emits table calls `emit <kind>` exactly once with the table's fields, and every publish calls `poke` once.
- AC21: With a fake binary that exits 3, every command in that table exits 0 with its usual output.
- AC22: With a daemon, `./zn work status` prints for each worker its id, cli, state, the unit and activity it holds, and its `can`.
- AC23: With a daemon, the page `./zn board` writes holds the workers and claims under "snapshot at" with a PST time; without one it says "live layer not running".
- AC24: `z-nile/check.sh --plan` lists the gofmt, vet and test stages for a change under `z-nile/go/` and none of them for a change elsewhere in z-nile, and lists the build stage for both.
- AC25: zz-arch's layout and rule 2 name `z-nile/go/` as the tooling's Go module, and SETUP.md names the Go toolchain.
