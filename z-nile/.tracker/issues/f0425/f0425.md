# f0425: App approvals view

## Problem
- Before this ticket, no page showed how the owner would work through approvals: the queue, each ticket in plain words, each guess, and the choice to approve or send back.
- No page let a send-back collect the stage the ticket goes back to and the owner's instruction for the worker.
- Neither the mockup nor `z-nile/README.html` used philip-bergen.com's colours and fonts, so the owner had no page in the site's look to judge the app on before f0437 builds any real view.

Decided with the user (2026-11-21): "an optional rich experience where you can visually appealing stay on top of everything (settings, workers, tributaries, rafts, and tickets, stats) there should be a really vibrant stats view that shows you live stats as they are trending for your repo that updates every time a step forward is recorded" and "everything except look at code"; of the approvals mockup: "the mockup looks very good, let's keep building that and the app so we can keep improving on it, we can build the experience for stats and workers" (`mockup/index.html` now has Workers and Stats views beside Approvals, on simulated data, and the app is built on from that mockup).

Decided with the user (2026-11-21, tickets and rafts): "The tickets are an interesting one to mock, one comment on send back there needs to be a mesage collected with instruction and there needs to be a link to open that ticket in an ai cli so I can talk through it. That really goes for all of it, any item on the board including stats should be linkable directly to an AI cli with context so that we can talk about it. How do we model the rafts and tickets?" Three decisions: a send-back collects the stage it goes back to and a required instruction message; every item (ticket, raft, guess, worker, queue entry, stat, event, tributary) has a route and can be opened in an AI CLI with its context (`zn talk <ref>`); the mockup models a ticket as a staged unit of intent (idea, design, rafted, code, review, approval, landed) and a raft as an ordered stack of tickets on one branch and one pull request (`mockup/index.html` now has Tickets and Rafts views).

Decided with the user (2026-11-21, colours): "both mock and html should use the color scheme from philip-bergen.com" and "I like the bright collors on risky/normal and all those things, I just don't really like the pruple". `mockup/index.html` and `z-nile/README.html` now use the site's gold-e scheme (light by default, a warm dark by the theme button) and its fonts (Instrument Serif titles, Geist, Geist Mono); the status and chart colours stay bright, with the purple ones replaced (waiting is lime, series 1 is cobalt).

Decided with the user (2026-11-21, the bundle stage): the stages are seven (idea, design, bundle, code, review, approval, landed); "bundle" was chosen by the lead as the word recognizable without inside knowledge, for the owner to overrule; "raft" stays as the noun for one bundle and is explained in plain words ("a bundle of tickets delivered together") where a page first uses it; whether the noun is renamed is open (c0436).

## Non-goals
- This ticket changes only `z-nile/README.html`'s fonts, colour variables, heading weights and theme default: none of its text, sections or links.
- No view here reads the real tracker or the live daemon: the Approvals, Workers, Stats, Tickets and Rafts views on real data belong to f0437.
- This ticket gives no route or method in the app's server a way to approve or send back, and leaves `TestNoRouteOrMethodCanApprove` in `z-nile/go/internal/web/approvals_test.go` unchanged.
- This ticket does not build `zn talk` or any control that starts it: those belong to f0432, and the mockup's Talk buttons only open a simulated popover.
- This ticket does not build `zn rework` or record lessons: the `zn rework … --stage … --note … --lesson` command the send-back confirmation shows and copies, and its "Also record this as a lesson" box, are simulated, and the command does not exist on main.
- This ticket adds no options field to `guesses.md`: the mockup's options are simulated, and the real view shows only what was open, what was chosen and why (f0437's G15).

## Solution
- `z-nile/.tracker/issues/f0425/mockup/index.html` opens straight from the file and has an Approvals view on simulated data only: a queue, each ticket explained in plain words, and each guess with simulated options and what each option changes.
- The mockup also has Workers, Stats, Tickets and Rafts views, all on simulated data, as the owner decided on 2026-11-21 (PRs #716 and #719): a ticket is shown as a staged unit and a raft as an ordered stack of tickets, and every item has its own `#/` route and a Talk button.
- The mockup's script calls none of `fetch`, `XMLHttpRequest`, `WebSocket` or `EventSource`, so its Approve and Send back controls change only the page's own simulated state and nothing reaches the tracker or the live daemon; its only network requests are the Google Fonts stylesheet and font files.
- The mockup's Send back form lists idea, design and code, disables any stage the ticket has not reached, always has one reached stage selected, and refuses to submit while the instruction is empty or only spaces.
- The mockup uses the site's gold-e colours (light by default, a warm dark from the theme button) and its fonts Instrument Serif, Geist and Geist Mono, loaded from Google Fonts, and none of its status or chart colours is purple or indigo.
- As the owner decided ("both mock and html should use the color scheme from philip-bergen.com"), `z-nile/README.html` uses the same gold-e colours and fonts as the mockup (PR #723, `0b1653326`): it loads Instrument Serif, Geist and Geist Mono from Google Fonts in place of Bricolage Grotesque and IBM Plex, it opens light whatever the OS prefers, and its `#theme` button switches it to the warm dark set.
