# f0427: Zn one go app any repo

## Problem
- zn runs today only as about 37,000 lines of Luau under Lune inside pickman's repository, where it commits its tickets and rafts to that repository's own main branch.
- A repository that knows nothing about zn (first: omarchy, on Omarchy Linux) cannot run the worker, the board, the approval walk or the gate without installing Lune and adopting pickman's layout and tracked files.

## Non-goals
- Putting `.tracker/` in a separate GitHub repository the owner owns, or sharing it between machines, is f0428: here `.tracker/` is local, ignored files on one machine.
- Publishing the board to the world is f0429: here the board is a local file under `.tracker/`.
- Bridging to GitHub issues is f0430.
- Porting every engine command from Luau to Go is not required here.
- Windows is not supported.
- pickman's own repository keeps working as it does today and is not moved to the new layout here.
- Proving the delivery with an AI CLI other than Claude Code is not required here, though no skill file is placed where only Claude Code would find it.
- Installing `git`, `gh` or the AI CLI for the person is not zn's job here.

## Solution
- A person installs one program, `zn`, once, and it runs on Linux and macOS with no Lune, Luau or Rojo installed on the machine or present in the host repository.
- Running `zn init` in a checkout of a repository that knows nothing about zn creates a `.tracker/` directory at the checkout's root and adds `.tracker/` to that checkout's `.git/info/exclude`, changing no tracked file.
- Every ticket, raft, claim, approval record, board file, zn setting and skill file is a file under that `.tracker/` directory, and nowhere else in the host checkout.
- The `zn` program carries every skill the worker follows (z-ticket, z-design, z-raft, z-ready, z-work, z-approve, zz-review and the rest), and `zn init` writes them under `.tracker/skills/`, creating no file or link under `.claude/` or anywhere else outside `.tracker/`.
- `zn work` prints the worker's instructions with the path of each skill file under `.tracker/skills/` that the AI CLI session must read, so the session finds every skill without any skill being registered in the host checkout or the person's home directory.
- Every tracker state change the worker, the board and the approval walk make (capture, design, raft, claiming a raft and moving it to `active/`, stop, approve, done) is written under `.tracker/` and makes no commit, branch or push in the host repository.
- The gate runs the test command named in `.tracker/settings.toml`, and refuses to start with a message naming that file when it names none.
- The only programs a delivery uses besides `zn` are an AI CLI that runs the worker session (first: Claude Code), `git`, `gh`, and whatever the test command in `.tracker/settings.toml` itself calls.
- `zn` refuses to start the worker, with a message naming the missing program, when `git`, `gh` or the AI CLI named in `.tracker/settings.toml` is not installed.
- In an omarchy checkout on Omarchy Linux, after `zn init`, a worker session in Claude Code that follows the skills under `.tracker/skills/` and runs `zn` commands takes one raft through every tracker step: a ticket is captured, designed to prepared, grouped into a raft, readied and claimed, and approved.
- For that same raft in omarchy, the worker then makes the implementation on a branch in a git worktree with `git`, opens its pull request against omarchy's main branch with `gh`, runs the gate on that branch with the test command from `.tracker/settings.toml`, lands the pull request with `gh` once the gate passes, and moves the raft and its ticket to done under `.tracker/`.
- During that delivery in omarchy, the board file under `.tracker/` shows the raft in each state it passes through (backlog, prepared, active, done), and the approval walk presents the ticket and records the owner's ruling under `.tracker/`.
- That omarchy delivery completes with no Lune, Luau or Rojo installed on the machine, and with no zn command failing because a file or layout from pickman's repository is missing.
- After any sequence of zn commands that does not deliver a raft's implementation, `git status` in the host checkout shows no change, and `git log` and `git branch` show no new commit or branch from zn.
- The only commits made in the host repository during a delivery are the code changes of a raft's implementation, on that raft's branch and in the merge of its pull request, containing no path under `.tracker/`, no path under `.claude/` and no zn file.
- The first packaging may carry the Luau engine inside the Go program, as long as the person installs and runs one program and nothing else besides the AI CLI, `git` and `gh`.

## Design
Risk is risky: the whole engine moves behind a new front door, and the one repository the engine has always assumed becomes two.

One Go program, `zn` (`z-nile/go/cmd/zn`), has two halves: today's Luau engine for the tracker, and new Go for the host's code.

**The tracker half is the Luau engine, carried inside the program.** Each release binary embeds its own platform's Lune 0.10.5 and a gzipped tar of `z-nile/{engine,lib,vendor,templates}` with the host skills (about 1 MB). On first run it extracts them to `<os.UserCacheDir()>/zn/<12-hex content id>/`. The extraction goes into a temporary folder, is marked `.ok` and is renamed into place, so a race or a crash never leaves a half copy. Then it `exec`s `lune run <cache>/z-nile/engine/main -- <args>` (E4: a 14 MB binary, 0.77 s cold, 0.14 s warm). Lune is bundled, not downloaded and not required. A download needs the network and GitHub at run time and adds a second way to fail. A prerequisite would break the Solution. The release script checks each Lune zip against a pinned sha256 (`z-nile/go/cmd/zn/lune.sum`) before embedding it (E5).

**The engine runs in the tracker checkout `.tracker/`, never in the host.** `.tracker/` is a git repository shaped like a one-project z-nile repository:
- `z-nile/projects.toml`: one project, named after the host, with root `<name>/.tracker`
- `z-nile/next`, and the items under `<name>/.tracker/{issues,rafts}`
- `skills/`, `settings.toml` and `.models.toml`
- its own committed `.gitignore`: `.cache/`, `.worktree/`, `prompt.md`, `.zn-origin.git/`

Because the engine sees only this repository, its one-repository assumptions hold unchanged: 422 reads of `origin/main`, publish's plumbing push and the claim stamp. The tracker's branch is always `main`, whatever the host's is (omarchy's is `quattro`). In f0427 the tracker's `origin` is a local bare repository, `.tracker/.zn-origin.git`, so publishing and claiming work exactly as they do in pickman's fixtures. f0428 points `origin` at the owner's GitHub repository instead. E6 ran `list`, `board`, `audit` and `new` from an extracted engine in a tree of this shape.

**The code half is new Go.** These commands are the ones where one repository becomes two: `init`, `doctor`, `run`, `worktree`, `gate`, `commit`, `pr`, `land` and `version`. They act on the host checkout with `git` and `gh`, and they change tracker state only through the engine. Every other command goes to the engine. One Go map (`cmd/zn/commands.go`) says which half takes each command, so porting a command later means moving its name to a Go function, proven by the same black-box specs.

**Finding the host and its tracker.** The host is `dirname(git rev-parse --path-format=absolute --git-common-dir)`, from the main checkout or any of its worktrees (E2g), and the tracker is that folder's `.tracker/`. Without a `.tracker/`, every command except `init`, `doctor` and `version` refuses and names `zn init`.

**`zn init` (local).** It refuses outside a git checkout, and in one that holds `z-nile/engine/main.luau`, because pickman keeps its own `./zn`. Then it:
1. appends `.tracker/`, `.worktree/` and `.cache/` to the host's `.git/info/exclude`, each only when missing;
2. runs `git init -b main .tracker`;
3. writes the registry, the counter, `.gitignore`, the skills and `settings.toml`, with the default branch read from `git symbolic-ref refs/remotes/origin/HEAD`;
4. commits, creates the bare `.zn-origin.git` and pushes `main` to it.

**`.tracker/settings.toml`** has one reader, `internal/settings`:
- `[host]`: `name`, `default_branch`, `fork` (f0428) and `land = "pr" | "merge"`
- `[test]`: `command`, run with `bash -c` in the ticket's host worktree, where exit 0 passes
- `[worker]`: `cli = "claude"`
- `[light]`: `protected`

It holds no absolute path and no token, so it can be public (f0428). The gate refuses, naming `.tracker/settings.toml`, when `test.command` is empty.

**Host mode in the engine.** The engine knows it is serving a host from `ZN_HOST=1`, `ZN_ENGINE=<cache dir>` and `ZN_CODE=<host worktree>`. Only the Go program sets them, so pickman's `./zn` keeps all its behaviour. Under `ZN_HOST` the engine:
1. reads `fence.sh`, `ac.sh` and the board's assets from `ZN_ENGINE`, not from the tree (main.luau:300-336, the `ac.sh` line of `templates/issue/check.sh`);
2. lets the commands that publish by plumbing alone run in the tracker's main checkout (main.luau:243-251), because they never touch its working tree: `new`, `status`, `idea`, `guess`, `ready`, `stop`, `approve --publish` and `close`. Work edited by hand (a design, a raft) is done in `.tracker/.worktree/<name>` and goes in with `land`. Under `ZN_HOST`, `land` accepts any branch there, and its gate is `zn audit` (`PICKMAN_LAND_GATE`, main.luau:2755);
3. takes skills and lessons from `<tracker>/skills/` (skills.luau, lessons.luau) and never links `.claude/skills` (`skills` refuses);
4. makes `work` print the host instructions, the z-work skill and the absolute path of every skill file (main.luau:9140);
5. leaves acceptance specs in the ticket's folder at `done` instead of promoting them to `<home>/tests/acceptance` (main.luau:5003-5040);
6. takes the protected paths from `[light] protected`, default `[".github/"]`, instead of pickman's list (light.luau:24-70);
7. refuses `start`, `finish`, `restack`, `commit` and `done`'s merge, naming the Go command that replaces each.

**What stays out of a host.** These are pickman's alone:
- the gate `z-nile/check.sh`: its Luau static stages (:285-293), Rojo builds (:255-300), kernel-zone guard (:41), fence (:155-241) and registry (:75)
- the macOS spec jail (`z-nile/tests/run.luau`)
- `scripts/hooks/*` and `.claude/settings.json`
- `AGENTS.md` and the `.claude/skills/` links
- the `$HOME/.rokit/bin` PATH set in `zn`
- `zn dispatch`, which the Solution's interactive worker does not need

The host's own `AGENTS.md` and `CLAUDE.md` (omarchy has both) are never edited. The host edition of the skills is z-ticket, z-design, z-raft, z-ready, z-work, z-run, z-stop, z-approve, zz-rules, zz-execute, zz-review and zz-stats, plus a short `zz-host-test` that replaces zz-test and zz-arch. Each `./zn ` in their text becomes `zn ` when it is written to disk.

**The code half's commands:**
- `zn worktree <ticket>`: the f0428 fetch, then `.worktree/<ticket>-<slug>` on a new branch from `refs/remotes/origin/<default>`, made with `--no-track`.
- `zn gate`: runs `test.command` there, then the ticket's `check.sh` files from the tracker, with `ZN_CODE` set.
- `zn commit -m`: commits in the host worktree, refusing any staged path under `.tracker`, `.worktree`, `.cache` or `.claude`, then publishes the spend row, which names the host commit, to the tracker.
- `zn pr`: pushes to the fork (to `origin` when `land = "merge"`) and runs `gh pr create`.
- `zn land`: runs only when `land = "merge"` and the gate passed on the PR head. It runs `gh pr merge`, then publishes the raft and its tickets to `done/`.
- `zn doctor`: also the first step of `work`. It checks for `git`, `gh`, `gh auth status` and `worker.cli`, and names whichever is missing.
- `zn run`: the bounded runner, ported to Go (process group, time limit), so no host needs perl for it.

### Scalability
One `exec` per engine command after a single extraction per version. The engine's git calls run against the tracker's small history, never the host's. The Go commands make a fixed number of `git` and `gh` calls per ticket.
### Maintainability
A new host setting goes through `internal/settings` alone. A command moves from the engine to Go by moving one entry in `commands.go`. Host mode lives in one engine module, `hostmode.luau`, that the seven switches above call.
### Usability
`zn` with no arguments prints both halves' commands in one list. Every refusal names the file or program: `.tracker/settings.toml`, `zn init`, the missing `gh`.

### Guesses
Also recorded in `guesses.md`.
- G1, how a binary gets Lune: bundled per platform. The alternative was a download on first run, pinned by checksum. Changing later costs one function in `internal/payload`.
- G2, the tracker's layout: the existing z-nile shape (`z-nile/projects.toml`, `<name>/.tracker/`). The alternative was a flat `issues/` at the root. Changing later costs one `git mv` in the tracker plus `projects.FILE`, `ids.FILE` and `shapeOk`.
- G3, the local tracker's origin: a bare `.tracker/.zn-origin.git`. The alternatives were no origin (offline mode, where `ready` refuses) or a folder under `~/.local/share`. Changing later costs `init` alone.
- G4, perl: the only Perl use, `zn run`, is ported to Go, and the engine's one `sh.run("perl")` is replaced. The alternative was to count perl as part of git (Arch's git depends on it). Changing later is small.
- G5, the host-edition skills: a separate `z-nile/hostskills` folder made from z-nile's skills, plus `zz-host-test`. The alternative was host-aware text inside z-nile's own skills. Merging them later is a text edit.
- G6, omarchy's test command: `test/all`, which is omarchy's own runner and runs `test/cli` and `test/shell`. The owner can change it in `settings.toml`.
- G7, pickman's checkout: the Go `zn` refuses there and points at `./zn`. The alternative was to serve pickman as well, which nothing needs yet.

## Unknowns & experiments
All ran on 2026-11-21 on macOS arm64, each through `./zn run --time <=120 --` in throwaway folders under `.cache/exp/`.
- E3: Does Lune, copied out of rokit, run the engine from a folder outside any z-nile checkout with no `lune` on PATH? Command: `.cache/exp/e3.sh` (it copies `lune` and `z-nile/{engine,lib}` to `.cache/exp/e3/cache`, then runs with `PATH=/usr/bin:/bin`). **Pass**: usage exits 0 in 0.54 s. The engine is 1.8 MB and 81 files.
- E4: Can one Go binary embed Lune and the engine, extract them once and exec them? Command: `.cache/exp/e4/main.go` (go:embed, a content-id cache folder, temp then rename, `syscall.Exec`) built for darwin/arm64 and cross-built for linux/amd64. **Pass**: 14.2 MB, `list` takes 0.77 s cold and 0.14 s warm, `board` 0.25 s warm, and the cache is 17 MB. macOS ran the extracted binary without a quarantine prompt.
- E5: Is there a Lune for Linux, and what does it need? Command: `gh release view v0.10.5 --repo lune-org/lune`, then download and run `file` and `strings`. **Pass**: zips exist for linux x86_64 and aarch64 and macOS x86_64 and aarch64 (about 5 MB each). The Linux binary is glibc-dynamic, needs `GLIBC_2.34`, `libgcc_s` and `libm` (all in Arch base) and is not static. The zip's sha256 is `1fb5dee6a1afa1d300092805c6e660fe06144d29dd68c45cf6956f040667f791`.
- E6: Do tracker commands work from the extracted engine in a tracker-shaped repository holding only `z-nile/projects.toml`, `z-nile/next` and a project root? Command: `.cache/exp/e3.sh`, `e3b.sh`, `e3c.sh` and `e3d.sh`. **Partly**:
  - `list` exits 0, and so does `audit` once `z-nile/next` exists.
  - `board` passes once `z-nile/vendor/marked.umd.js` sits beside the extracted engine, because it is read relative to the module (board.luau:145-153).
  - `new` refuses in the main checkout (the worktree rule, main.luau:243-251). In a worktree it does not publish, because `z-nile/lib/fence.sh` is missing from the tree (main.luau:300-336), and writes the issue locally instead.
  - These are host-mode switches 1 and 2.
- E9, not run: the full delivery on Omarchy Linux. No Linux machine is here, so it is OC1.
- E10, not run: whether Claude Code in omarchy follows skills it is given only as paths, without `.claude/skills`. This is checked by OC1, and the fallback is that `zn work` prints each skill's text inline.
- E11, not run: whether `test/all` runs headless outside omarchy's CI VM. `test.yml` runs it on ubuntu-26.04 with some setup, so the owner checks it on the machine.

## Open to the human
- Q1: Who is the one user? The design assumes the owner, on his own Omarchy machine, signed in to `gh` as himself.
- Q2: Fork and upstream pull requests, or push access? The two tickets disagree. This ticket's Solution has the worker land the pull request against omarchy's main branch with `gh`, but f0428's Non-goals say zn never merges a pull request in the host. As designed, `land = "pr"` (f0428's fork mode, the default) ends the delivery when the pull request is open and the gate has passed, and only `land = "merge"` merges. To meet this ticket's "lands the pull request" literally, the first omarchy run would take the owner's fork as the host, with `origin` set to the fork and `land = "merge"`. Which do you want?
- Q3: Is carrying the Luau engine inside the Go program acceptable as the first packaging? The design embeds it for the tracker commands only, and writes the commands that touch the host in Go from the start (see the recommendation in the PR).
- Q4: Where are the release binaries published? Guess: the GitHub releases of this repository (`philipbergen/z-nile`, public), installed by downloading one file to `~/.local/bin/zn`.
- Q5: Is `test/all` the right gate for omarchy, and does it run outside omarchy's CI VM (E11)?
