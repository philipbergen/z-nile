# f0427: Zn one go app any repo

## Problem
- zn runs today only as about 37,000 lines of Luau under Lune inside pickman's repository, where it commits its tickets and rafts to that repository's own main branch.
- A repository that knows nothing about zn (first: omarchy, on Omarchy Linux) cannot run the worker, the board, the approval walk or the gate without installing Lune and adopting pickman's layout and tracked files.

Decided with the user (2026-11-21, contribution): asked how omarchy is worked, the owner answered "fork and pr". So the host is worked through the owner's fork with pull requests to upstream; a delivery ends at "pull request open, waiting on upstream"; zn never merges upstream. This answers Q2.

Decided with the user (2026-11-21, acceptance specs): asked whether a builder may write the acceptance spec for its own step, the owner answered "it may write it but it has to be reviewed separately". So each step's acceptance spec gets its own review, apart from the code review, before the step merges.

## Non-goals
- Putting `.tracker/` in a separate GitHub repository the owner owns, or sharing it between machines, is f0428: here `.tracker/` is local, ignored files on one machine.
- Publishing the board to the world is f0429: here the board is a local file under `.tracker/`.
- Bridging to GitHub issues is f0430.
- Porting every engine command from Luau to Go is not required here.
- Windows is not supported.
- pickman's own repository keeps working as it does today and is not moved to the new layout here.
- Proving the delivery with an AI CLI other than Claude Code is not required here, though no skill file is placed where only Claude Code would find it.
- Installing `git`, `gh` or the AI CLI for the person is not zn's job here.

## Solution
- A person installs one program, `zn`, once, and it runs on Linux and macOS with no Lune, Luau or Rojo installed on the machine or present in the host repository.
- Running `zn init` in a checkout of a repository that knows nothing about zn creates a `.tracker/` directory at the checkout's root and adds `.tracker/` to that checkout's `.git/info/exclude`, changing no tracked file.
- Every ticket, raft, claim, approval record, board file, zn setting and skill file is a file under that `.tracker/` directory, and nowhere else in the host checkout.
- The `zn` program carries every skill the worker follows (z-ticket, z-design, z-raft, z-ready, z-work, z-approve, zz-review and the rest), and `zn init` writes them under `.tracker/skills/`, creating no file or link under `.claude/` or anywhere else outside `.tracker/`.
- `zn work` prints the worker's instructions with the path of each skill file under `.tracker/skills/` that the AI CLI session must read, so the session finds every skill without any skill being registered in the host checkout or the person's home directory.
- Every tracker state change the worker, the board and the approval walk make (capture, design, raft, claiming a raft and moving it to `active/`, stop, approve, done) is written under `.tracker/` and makes no commit, branch or push in the host repository.
- The gate runs the test command named in `.tracker/settings.toml`, and refuses to start with a message naming that file when it names none.
- The only programs a delivery uses besides `zn` are an AI CLI that runs the worker session (first: Claude Code), `git`, `gh`, and whatever the test command in `.tracker/settings.toml` itself calls.
- `zn` refuses to start the worker, with a message naming the missing program, when `git`, `gh` or the AI CLI named in `.tracker/settings.toml` is not installed.
- In an omarchy checkout on Omarchy Linux, after `zn init`, a worker session in Claude Code that follows the skills under `.tracker/skills/` and runs `zn` commands takes one raft through every tracker step: a ticket is captured, designed to prepared, grouped into a raft, readied and claimed, and approved.
- For that same raft in omarchy, the worker then makes the implementation on a branch in a git worktree with `git`, opens its pull request against omarchy's main branch with `gh`, runs the gate on that branch with the test command from `.tracker/settings.toml`, lands the pull request with `gh` once the gate passes, and moves the raft and its ticket to done under `.tracker/`.
- During that delivery in omarchy, the board file under `.tracker/` shows the raft in each state it passes through (backlog, prepared, active, done), and the approval walk presents the ticket and records the owner's ruling under `.tracker/`.
- That omarchy delivery completes with no Lune, Luau or Rojo installed on the machine, and with no zn command failing because a file or layout from pickman's repository is missing.
- After any sequence of zn commands that does not deliver a raft's implementation, `git status` in the host checkout shows no change, and `git log` and `git branch` show no new commit or branch from zn.
- The only commits made in the host repository during a delivery are the code changes of a raft's implementation, on that raft's branch and in the merge of its pull request, containing no path under `.tracker/`, no path under `.claude/` and no zn file.
- The first packaging may carry the Luau engine inside the Go program, as long as the person installs and runs one program and nothing else besides the AI CLI, `git` and `gh`.

## Design
Risk is risky: the whole engine moves behind a new front door, and the one repository the engine has always assumed becomes two. Review: `design-review-001.md`, answered in `design-refute-001.md`.

One Go program, `zn` (`z-nile/go/cmd/zn`), has two halves. The tracker half is today's Luau engine, carried inside the program and run in the tracker checkout. The host half is new Go, working on the host checkout with `git` and `gh`. One map (`cmd/zn/commands.go`) routes each command name. The host's commands are `init`, `doctor`, `run`, `worktree`, `commit`, `gate`, `pr`, `land`, `live` and `version`. The tracker-side commands with the same verbs are named apart: `zn tracker worktree` and `zn tracker merge`. Every other name goes to the engine, and "land" means only the merge of a raft's implementation.

**1. Packaging.** Each release binary embeds its own platform's Lune 0.10.5, checked at build time against `cmd/zn/lune.sum` (E5). It also embeds a tar of `z-nile/{engine,lib,vendor,templates,roots.luau,affected.luau}` and the generated host skills. On first run it extracts them to `<cache>/zn/<content id>/`.
- `<cache>` is `$XDG_CACHE_HOME`, but only when that is absolute and is a folder the user owns; otherwise it is `~/.cache`.
- Every folder `zn` creates there has mode 0700, and any symlink in the path is refused.
- On every run, the sha256 of the extracted `lune` and of the payload manifest are checked against the embedded values. A mismatch or a missing file re-extracts the payload.
- An exec that fails (for example on a `noexec` mount) refuses with a message naming `ZN_CACHE`, which overrides the folder.

The measured cost is a 14 MB binary, 0.77 s cold and 0.14 s warm (E4).

**2. The tracker checkout matches the engine, so the engine does not change for idea to approval.** The engine always runs inside `.tracker/`, a git repository shaped like a one-project z-nile repository. Its committed files are:
- `z-nile/projects.toml` (one project, root `<name>/.tracker`) and `z-nile/next`
- the items, under `<name>/.tracker/{issues,rafts}`
- `skills/`, `settings.toml` and `.models.toml`
- `.gitignore`

Before every engine call, the front door makes sure of three things:
- Ignored links `z-nile/{engine,lib,vendor,templates,roots.luau,affected.luau}` point into the cache, in the tracker's main checkout and in each tracker worktree. With them in place, `ac.sh`'s `cd`, `lune run z-nile/roots`, the fence, `measure.pl`, `bounded.pl`, `replace-file.pl`, the board's assets and the four `lune` spawns (main.luau:4196, 4222, 5064, 6298) all resolve as they do in pickman.
- `<cache>/bin` comes first on `PATH`. It holds the real `lune`, a `zn` link to this program (so `approvewalk`'s re-run of the engine works), and a `hostname` shim (`exec uname -n`), because Arch base has no `hostname`.
- A standing tracker worktree `.tracker/.worktree/zn` exists, detached at the fetched `origin/main` and refreshed on each call. The commands that publish by plumbing alone (`new`, `status`, `idea`, `guess`, `ready`, `stop`, `approve`, `close`) run there, so the main-checkout refusal (main.luau:243-251) never fires.

E14 published `new` this way with no engine change. The tracker's branch is always `main`, so the engine's 422 reads of `origin/main` stay true whatever the host's default branch is (omarchy's is `quattro`). In f0427 the tracker's `origin` is a bare repository at `$XDG_DATA_HOME/zn/trackers/<host id>.git` (default `~/.local/share`), so deleting `.tracker` loses nothing that was pushed. f0428 points `origin` at GitHub instead.

**3. The front door's duties.** It takes over from the bash `zn` wrapper:
- It sets `ZN_TOP` to the tracker worktree and `ZN_CWD` to the project's folder.
- It lowers `RLIMIT_CPU` to `ZN_ENGINE_CPU` (default 1800 s) and never raises it.
- It reroutes `work` to the host worktree it was called from.
- It runs `approve`'s gate: `zn approve` without `--check`, `--queue`, `--ruling` or `--help` refuses when stdin is not a terminal (an ioctl, so `zn approve </dev/null` refuses), when `ZN_DISPATCH` is set, and when `ZN_APPROVE_SESSION` is set. The engine's own test (main.luau:6146) stays as a second line.
- It forwards `.tracker/.models.toml`'s `[rounds]` and the work profile unchanged, so review-round counts are a setting the owner changes, not code (F24).

**4. Programs.** The first packaging requires `bash`, `perl` and `uuidgen` besides `git`, `gh` and the AI CLI. All three are in Arch base or pulled in by `git`. `perl` is used in about fifteen places, listed in E15. `zn doctor` (and `work` before anything else) checks each one, plus `gh auth status`, and names the one that is missing. `zn run`, the bounded runner, is ported to Go first (section 9), and porting the rest of the perl use is later work. The Solution's sentence on "the only programs" is a scope question (Open to the human).

**5. Host facts: how the engine walks an active raft.** A raft is one host branch, `zn/<R-id>-<slug>`, holding its tickets as layers, where a layer is a commit range. It gets one pull request.
- Before an engine command that reads code state (`work next`, `done --check`, `trace --check`, `approve`, `board`), Go collects the host's facts into one JSON file and passes it as `ZN_HOST_FACTS`. The facts are: the raft branch's tip and base; each layer (ticket, first and last sha, patch-ids); the PR (URL, state, merged, the merge commit, head sha, review decision), read with `gh --repo <upstream>`; and the gate result for the head sha (section 7).
- Under `ZN_HOST`, `workread` (layers at :819-860, `prLookup` at :627-650) and the eight `gh pr` calls read the facts instead of refs and `gh` in the tracker.
- A layer's diff is `git -C <host> diff <first>^..<last>`.
- Reviews, final reviews, traces and the harvest are written in a per-raft tracker worktree, `.tracker/.worktree/<R-id>`, and published by plumbing. A trace cites `<host sha>:<path>:<line>`, which `trace --check` reads with `git -C <host> show`.

**6. Nothing unapproved leaves the machine.** `zn done --check <R-id>` runs the engine's whole refusal list (main.luau:5409-5470: `reviewProblem`, `runCheck`, `guessesKept`, `guessedGap`, `approvalGap`) against the facts. Both `zn land` and a `zn pr` to a repository the `gh` user does not own call it first and stop on any refusal. None of our reviews, traces or guesses are ever posted on an upstream pull request.

**7. Sequestration.** After `ready` publishes, Go publishes `ready_commit: <tracker sha>` in the raft document. `zn gate` and `done --check` read every member's `check.sh` and `acceptance/` from that commit (`git show`, into a temporary folder), never from the working tree. `zn tracker merge`, and the publish guard of the standing worktree, refuse any change to `check.sh`, `acceptance/**` or `approval.md` of a ready or active item. The one exception is the row that `zn approve` itself publishes.

**8. The host check.sh and gate.** A host ticket's `check.sh` is bash. It sources `$ZN_LIB/ac.sh` (set by `zn gate`) and runs its `check "ACn: ..." <command>` lines with the host worktree as its working directory. Its acceptance files are scripts in the ticket's `acceptance/` folder, which the check lines name as `"$A/<name>"`. Template:
```
#!/usr/bin/env bash
source "$ZN_LIB/ac.sh"                    # cds to $ZN_CODE, the host worktree under test
A="$ZN_ACCEPTANCE"                        # the ready commit's acceptance/, extracted by zn gate
check "AC1: test/all passes" bash -c "$ZN_TEST"
check "AC2: <statement>" bash "$A/ac2.sh"
finish
```
`zn gate` works in four steps:
1. It snapshots the host's refs and local config (f0428's E7 helper).
2. It runs `test.command`, then each member's `check.sh`, each through the bounded runner with `[test] seconds` (default 900).
3. It snapshots again, and fails when anything changed outside f0428's allowed list.
4. It publishes `gate: <host sha> pass|fail <date>` to the raft document.

The first time this machine runs a given `test.command`, or a `check.sh` whose hash it has not seen, it asks for one confirmation typed in a terminal. The hash is then kept in `.tracker/.cache/trusted`, which stays on this machine. There is no jail on Linux; the limits are the bounded runner's, the ref snapshot and this confirmation. The skill `zz-host-test` says the same in about 30 lines: what a host `check.sh` holds, that checks change only `$ZN_CODE` and `.cache/`, and that every probe runs through `zn run`.

**9. The bounded runner in Go (`zn run`)** keeps every guarantee of `bounded.pl`:
- `--time` defaults to 60 s, at most 3600; `--cpu` defaults to `--time` and only ever lowers the caller's limit.
- The command runs in a process group of its own, with a watchdog on a pipe only the runner holds, so the group is stopped however the runner dies.
- On the limit, on INT, TERM or HUP, or when the parent is gone, the group gets TERM, then KILL two seconds later. Whatever is left in the group is swept when the command ends.
- Exit codes: the command's own (128+n for a signal), 124 for the wall-clock limit, 125 for the CPU limit (at 90% of the allowance), 123 when the parent is gone, and 2 for a usage refusal.
- Every process carries `ZN_BOUNDED_DEADLINE`. `--report` and the `ZN_MEASURE_*` variables work as today.

**10. Skills, versions and the live layer.** There is one source of skill text: z-nile's skills, with marked blocks `<!-- host -->…<!-- /host -->` and `<!-- pickman -->…<!-- /pickman -->`.
- The build generates the host edition into the payload, keeping host blocks, dropping pickman blocks, and writing `./zn` as `zn`. It fails when the generated edition is stale against its source.
- A manifest lists the shipped skills, so no criterion names a count. No lesson of pickman's ships: the host's lessons folders start empty and fill in the tracker.
- `zn init --upgrade` rewrites `.tracker/skills/` from the binary and records `zn_version` in `settings.toml`. An older binary refuses to run against a tracker that records a newer version, naming that version.
- `zn live` is the live daemon, built into the same binary, with its state in `.tracker/.cache/live`. `where.MainCheckout` gets the tracker checkout from the front door.

**11. Settings (`.tracker/settings.toml`).** It has one reader, `internal/settings`:
- `[host]`: `name`, `default_branch`, `upstream`, `fork`, `land = "pr" | "merge"`, `zn_version`
- `[test]`: `command`, `seconds`
- `[worker]`: `cli`
- `[light]`: `protected`

It holds no absolute path and no token. `zn gate` refuses, naming `.tracker/settings.toml`, when `test.command` is empty.

**12. `zn init` (local)** refuses outside a git checkout, in a checkout that holds `z-nile/engine/main.luau` (pickman keeps its `./zn`), and on the unusual hosts f0428 lists. Then it:
1. appends `.tracker/` and `.worktree/` to `.git/info/exclude`, each only when missing (zn writes nothing in the host's `.cache/`, so f0427 adds no line for it);
2. creates `.tracker` with its seed files;
3. creates and pushes the bare origin;
4. makes the standing worktree.

**Under `ZN_HOST`** (set only by Go, so pickman's `./zn` keeps every behaviour), the engine changes behaviour only, never paths:
- `workread` and the `gh pr` calls read the host facts;
- `done` makes no promotion and no merge, and refuses, naming `zn land`;
- `start`, `finish`, `restack` and `commit` refuse, naming the Go command that replaces each;
- `skills` refuses to link `.claude/skills`;
- `work` prints the absolute path of every manifest skill;
- the watch net (main.luau:2857, 4945), `reap` (macOS only, :8729) and `dispatch` are off;
- the protected paths come from `[light]`.

There are 355 messages that print `./zn`. They stay as they are, and the host skill says that `./zn` in a message means `zn`. Never carried into a host: pickman's gate `z-nile/check.sh`, the macOS spec jail, `scripts/hooks`, `.claude/settings.json`, `AGENTS.md` and the `.claude/skills` links. The host's own `AGENTS.md` and `CLAUDE.md` are never edited.

### Scalability
After the first run, each command costs one exec, one hash of 10 MB and the link checks (a few `lstat`s). The host facts cost one `git log` per raft branch and one `gh pr view`. The engine's git calls run against the tracker's small history.
### Maintainability
A command moves from the engine to Go as one entry in `commands.go`. Host behaviour lives in `hostmode.luau` (its switches) and `internal/hostfacts` (the one writer of the facts file, whose one reader is `workread`). A new external program joins `zn doctor`'s list.
### Usability
`zn` with no arguments prints both halves' commands. Every refusal names the file, the program or the setting to change.

## Open to the human
The design is `design: reviewed`. It stays short of `ready` until these are ruled.
- Q1: Who is the one user? The design assumes the owner, on his own Omarchy machine, signed in to `gh` as himself.
- Q2: How does code reach omarchy: through your fork with pull requests to upstream, or with push access? The design defaults to a fork. On a repository your `gh` account does not own, only you, typing in a terminal, can open the pull request, and the delivery ends in the stage "pull request open, waiting on upstream". On a repository you own, the worker opens and merges it. To meet this ticket's sentence "lands the pull request" literally on the first run, the host would be your own fork. f0428's Non-goals say zn never merges a host pull request, so the two tickets need one answer.
- Q3: Is carrying the Luau engine inside the Go program acceptable as the first packaging? The tracker commands use it unchanged, and the host commands are written in Go from the start.
- Q4: Where are the release binaries published? Guess: GitHub releases of `philipbergen/z-nile` (public), installed by downloading one file to `~/.local/bin/zn`. The alternative is releases in the tracker repository.
- Q5: Which test command gates omarchy work? The choice affects what each gate run costs and what it can break on your machine:
  - (a) `test/all`, omarchy's own runner, which CI runs on ubuntu with some setup. It may not run outside CI (E11).
  - (b) `test/cli` only.
  - (c) `bash -n` over the changed scripts: cheap, but it checks little.
  Whichever you pick, its first run on your machine asks you to confirm it.
- S1 (scope, Solution): "The only programs a delivery uses besides `zn` are an AI CLI …, `git`, `gh`, and whatever the test command … calls." The first packaging also needs `bash`, `perl` and `uuidgen` (E15). All three ship with Arch base or with git, and `zn doctor` checks them. Do you accept the sentence gaining "bash, perl and uuidgen", or must the first release port their uses to Go? The port is about fifteen perl sites (design-review F5).
- S2 (scope, Solution): "Every ticket, raft, claim, approval record, … is a file under that `.tracker/` directory." The local tracker's bare origin now lives in `~/.local/share/zn/trackers/` (F19), so deleting `.tracker` loses nothing that was pushed. It holds copies of the same files. Does that satisfy the sentence, or must it stay inside `.tracker`?
