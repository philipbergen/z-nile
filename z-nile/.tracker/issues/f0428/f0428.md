# f0428: Tracker in its own repo

## Problem
- zn keeps every ticket, raft, design, review, lesson, setting and skill inside the repository it works on, so using it in a host repository the owner does not own (first: omarchy) would add zn files and commits to that repository.
- The owner has no separate public repository that holds the tracker, so the work cannot be showcased without the host repository carrying it.

## Non-goals
- zn does not write the host's `.gitignore`, the user's `core.excludesFile`, or any other tracked or global ignore file.
- zn does not create the owner's fork or add a remote to the host clone, so setup fails with a message when the named remote does not exist.
- zn does not fetch from the fork remote, fetch tags, or fetch any origin branch other than the default branch.
- zn does not pull, merge, rebase or fast-forward the local default branch, so it stays where the owner left it.
- zn does not merge, close or land any pull request in the host repository.
- This ticket does not package zn as the Go app (f0427), publish the board (f0429), or bridge to GitHub issues (f0430).
- This ticket does not support more than one tracker repository per host checkout, or more than one user.
- This ticket does not move pickman's existing in-repository trackers into a separate repository.

## Solution
- One zn setup command, given the address of the owner's tracker repository and the name of an existing remote of the host clone that is the owner's fork, clones the tracker to `.tracker` at the root of the host's main checkout, as its own git repository with its own remote.
- zn reads and writes every ticket, raft, design, review, lesson, setting and skill only inside that tracker checkout, and commits and pushes them only to the tracker repository.
- The setup command appends rules for `.tracker`, `.worktree/` and `.cache/` to the host clone's `.git/info/exclude`, which git never commits or pushes.
- In the host's working tree, zn itself writes only under `.tracker`, `.worktree/` and `.cache/`.
- Before it creates a ticket branch, zn fetches the default branch of the host's origin without tags, and starts the ticket branch from the fetched `refs/remotes/origin/<default branch>` commit, not from the local default branch.
- For each ticket, zn creates one new branch and one worktree under `.worktree/`, and the worker zn runs commits there only the ticket's code changes, so no commit on a ticket branch contains a path under `.tracker`, `.worktree/` or `.cache/`.
- zn pushes a ticket branch only to the fork remote named at setup, and pushes nothing to any other host remote, the host's origin included.
- In the host's `.git`, zn writes only: `info/exclude`; what that fetch writes (`refs/remotes/origin/<default branch>`, `FETCH_HEAD`, the fetched objects and their reflog entries); the registration and per-worktree state of worktrees it creates under `.worktree/`; `refs/heads/<ticket branch>`, its reflog and its upstream settings in `config`; the objects of commits on ticket branches; and `refs/remotes/<fork>/<ticket branch>`, which its push writes.
- zn and its worker make no commit on, and move no ref under `refs/heads/` or `refs/tags/` that zn did not create, the local default branch included.
- The only remote-tracking refs zn moves are `refs/remotes/origin/<default branch>`, by its fetch, and `refs/remotes/<fork>/<ticket branch>`, by its push; a remote-tracking ref is not a host branch in the sentence above.
- Ticket code reaches the host only through a pull request from the fork's ticket branch, which zn opens only when the owner runs a command for it and never merges.
- After setup and after any zn command, `git status` in the host's main checkout and in every worktree lists no `.tracker`, `.worktree` or `.cache` entry, `git diff` in the main checkout shows no change to any tracked file, `.gitignore` included, and `git rev-parse` of the local default branch gives the same commit as before the command.
- Every worktree of the host repository resolves the tracker to the one checkout in the main checkout, so a ticket written from any worktree appears in all of them without a second clone.
- The tracker repository is public on GitHub under the owner's account.

## Design
Risk is risky. This ticket decides what zn may write into a repository the owner does not own, and what it pushes to a public one. A push to the wrong remote, or a local path published, cannot be taken back. This ticket depends on f0427, which provides the Go `zn`, the tracker checkout and host mode.

**Two repositories, one rule each.**
- The host (omarchy) receives only ticket branches, pushed to the fork, and pull requests from them.
- The tracker repository (the owner's, public) receives everything else, as commits pushed straight to its `main`.

No commit goes to both.

**The tracker checkout** is `<host main checkout>/.tracker`. It is a plain `git clone` of the tracker repository with its own `origin`, not a submodule, and it is in no `.gitignore`. It is f0427's tracker with `origin` pointing at GitHub instead of `.zn-origin.git`. Every worktree of the host resolves it as `dirname(git rev-parse --path-format=absolute --git-common-dir)/.tracker` (E2g), so there is one clone per host checkout. One tracker repository may hold several hosts. Each host is a project `<name>/.tracker` in the tracker's `z-nile/projects.toml`, with a `[host.<name>]` table in `settings.toml`, matched to a host checkout by the host's `origin` URL.

**Hiding.** Setup appends `.tracker/`, `.worktree/` and `.cache/` to the host's `.git/info/exclude`, each only when missing. The exclude file of the common directory applies to every linked worktree (E1). `git status`, `git add -A`, `git stash -u` and `git clean -fdx` all skip the nested clone and the worktrees. Only `git clean -ffdx` deletes them (E2): zn never runs it, and the host skill names it as forbidden.

**Claims and publishing** map one to one onto the tracker repository. The claim is still a push to `origin/main`, now the tracker's, and `publish.luau` pushes its plumbing commit there unchanged. Two machines race on that push exactly as two worktrees do today. Tracker-only work never needs a pull request:
- A design or a raft is written in a tracker worktree (`.tracker/.worktree/<name>`).
- It goes in with `zn land`, which merges `origin/main`, runs `zn audit` and pushes.

The board is built from the tracker checkout into `.tracker/.cache/board.html`, and f0429 publishes it from the tracker repository.

**The commands that today commit tracker files and code together** each become one host commit followed by one tracker publish:
- `commit` (main.luau `recordAndCommit`, about :4860-4900, `git add -A` plus spend rows in the item files). The Go `zn commit` commits the code, then publishes the spend row keyed by the host commit's sha. When that publish fails, the next `zn commit` retries it, and the sha key means the row is written only once.
- `done` (main.luau:5387 onward: it merges the top layer, moves the items to `done/` and promotes acceptance specs). The host merge is done by `gh`, either through f0427's `land` or by upstream. The move to `done/` is a tracker publish, and the specs stay in the tracker.
- `new issue` in a raft worktree (:1249), the membership writes (:1420-1433), `fold`, `unfold` and `recombine` (:2161-2423), and `compact`, `renumber` and `remap` (:3636, :3747) are tracker-only. They run in the tracker checkout and touch no host file.
- `start`, `finish` and `restack` (layer branches, :4256) are replaced by one host branch per ticket, made by `zn worktree <ticket>`.

**A ticket's host branch** is `<ticket-id>-<slug>`, for example `f0012-wifi-menu`. `zn worktree <ticket>` runs:
1. `git fetch --no-tags origin refs/heads/<default>:refs/remotes/origin/<default>`
2. `git worktree add --no-track -b <branch> .worktree/<branch> refs/remotes/origin/<default>`

The raft document in the tracker records `branch:`, and after `zn pr` also `pr:` (the URL). The pull request body links the ticket's file in the tracker repository. Host commits carry no trailer and no tracker path. `zn pr <ticket>` pushes `-u <fork> <branch>` and runs `gh pr create --repo <upstream> --head <fork owner>:<branch> --base <default>`. It never pushes to any other remote and never merges. E7 lists every ref and config line these steps write, and they are exactly the Solution's list.

**The fork** is named at setup by its remote. Settings record the fork's URL, and each run resolves the remote whose URL matches, so a second machine may give that remote any name.

**`zn init <tracker-url> --fork <remote>`** is idempotent: each step checks before it writes.
1. It finds the host's main checkout, and refuses in a repository that holds `z-nile/engine/main.luau` (pickman).
2. It refuses, naming the missing remote, when `<remote>` or `origin` is not a remote of the host.
3. It reads origin's default branch with `git ls-remote --symref origin HEAD`, which writes nothing.
4. It appends whichever of the three exclude lines are missing.
5. It sets up `.tracker`:
   - With no `.tracker`, it runs `git clone <url> .tracker`.
   - With an f0427 tracker (its `origin` is `.zn-origin.git`), it pushes `main` to `<url>` when that repository is empty, sets `origin` to `<url>` and deletes `.zn-origin.git`. It refuses when `<url>` already has a `main`.
   - With a tracker whose `origin` is any other URL, it refuses.
6. When no project matches origin's URL, it adds the project and its `[host.<name>]` table (the upstream URL, default branch, fork URL and test command) to the tracker, then commits and pushes to the tracker's `main`. In every case it installs the pre-push hook in `.tracker/.git/hooks/` (see below).
7. It prints the board's path and `zn work`.

**A second machine, or a fresh clone,** clones the host, adds the fork remote and runs the same `zn init <url> --fork <remote>`. Step 5 clones the tracker, and step 6 finds the project by origin's URL and writes nothing.

**What is public, and what is never written there.** Everything committed to the tracker repository is public: tickets, designs, reviews, guesses, approvals, lessons, skills, settings (names, URLs, the test command), the board's sources, and each commit's author name and email. Never written there: absolute paths, the home folder, tokens, session ids and the carriers file. These stay in `.tracker/.cache/` and in `prompt.md`, both ignored by the tracker's committed `.gitignore`.

The pre-push hook (`zn scan-push`, in Go) refuses a push whose new commits add a line containing this machine's `$HOME`, the host checkout's absolute path or a GitHub token prefix (`ghp_`, `gho_`, `ghs_`, `ghu_`, `github_pat_`), and names the file and the line. Prose like `/home/<user>/.config` is allowed, which omarchy's tickets will need. The engine's plumbing push passes through this hook like any other `git push`, because the engine never passes `--no-verify` (E8).

### Scalability
The host fetch takes one ref and no tags. Tracker pushes are as many as today's publishes. The scan reads only the new commits' added lines.
### Maintainability
All host git work is in `internal/host`, one function per allowed write. A new allowed write has to be added there, and its spec, the E7 snapshot test, lists every ref and config line.
### Usability
Every refusal names the remote, the URL or the file. `zn init` prints what it did, step by step, and prints nothing for a step that had nothing to do.

### Guesses
Also recorded in `guesses.md`.
- G1, how tracker-only changes go in: pushed straight to the tracker's `main` (`land` with an audit gate). The alternative was pull requests in the tracker repository. Changing later means `land` opens a pull request instead.
- G2, how a host branch names its ticket: by the branch name and a link in the PR body, with no commit trailer, so upstream sees nothing of zn in history. The alternative was a `Zn-Ticket:` trailer. Changing later is one line in `zn commit`.
- G3, what the scan looks for: only this machine's exact paths and token prefixes, not every `/home/...`. The alternative was a broad path pattern, which would refuse omarchy's normal prose. It can be widened later.
- G4, the fork: recorded by URL and resolved to the remote each run. The alternative was recording the remote's name, which ties the setting to one machine. Changing later is one settings key.
- G5, more than one host per tracker repository: allowed, one project each. The alternative was one tracker repository per host. This needs no change later.
- G6, the user's model: a fork, with pull requests to upstream. The alternative was push access (see Q2). The setting is `land`.

## Unknowns & experiments
All ran on 2026-11-21 through `./zn run --time <=120 --` in fixtures under `.cache/exp/`, with `GIT_CONFIG_GLOBAL=/dev/null`.
- E1: Does the main checkout's `.git/info/exclude` hide `.tracker/`, `.worktree/` and `.cache/` in the main checkout and in a linked worktree? Command: `.cache/exp/e1.sh`. **Pass**: `git status --porcelain` is empty in both, even with `.cache/` and `.tracker/` folders created inside the linked worktree. `git check-ignore -v` from the worktree cites the main checkout's `info/exclude`.
- E2: Does a nested clone at `.tracker` confuse the host? Command: `.cache/exp/e1.sh`.
  - `git worktree add .worktree/t1` works, and `git add -A` stages nothing.
  - `git clean -ndx` lists only `.cache/` (it says `Would skip repository .worktree/t1`), and a real `git clean -fdx` leaves `.tracker` and the worktree in place.
  - `git clean -nffdx` would remove `.tracker/` and `.worktree/`.
  - `git stash -u` has nothing to stash.
  - `git -C .tracker rev-parse --show-toplevel` is `.tracker`.
  - From the worktree, `--git-common-dir` resolves to the main checkout (E2g).
  - **Pass**, with the `-ffdx` caveat.
- E7: What do the fetch, `worktree add --no-track` and a push to the fork write in the host's `.git`? Command: `.cache/exp/e7.sh`, with upstream default branch `quattro`, a tag `v2` and an extra branch `other` on upstream. **Pass**: the before and after `for-each-ref` plus `config --local` differ only in `refs/heads/f0001-hello`, `refs/remotes/origin/quattro`, `refs/remotes/fork/f0001-hello`, and `branch.f0001-hello.remote=fork` and `.merge`. The local `quattro` did not move, `v2` and `origin/other` were not fetched, and the fork received only the ticket branch. One more finding: a relative local remote URL resolves against the worktree, so tests use absolute URLs.
- E8: Does a pre-push hook in the tracker clone see, and refuse, an engine-style plumbing push (`git push origin <sha>:refs/heads/main`) whose commit adds a line with `$HOME`? Command: `.cache/exp/e8.sh`. **Pass**: the push exits 1, and origin's `main` is unchanged. The engine has no `--no-verify` anywhere (`grep -n '"push"' z-nile/engine/*.luau`).
- E12, not run: `gh pr create --head <owner>:<branch>` from a real fork to `basecamp/omarchy`. A design must not open pull requests on GitHub, so this is checked in OC1 with a draft pull request.
- E13, not run: two machines claiming at once. It is the same push race as two worktrees, which pickman's claim specs already cover, so it was not repeated.

### Checked

- AC1: In a fixture host with a bare origin, a bare fork and a bare tracker, `zn init <tracker> --fork fork` clones the tracker to `<main>/.tracker`, whose `origin` is the tracker URL. It appends the three exclude lines once, and a second run changes nothing.

- AC9: A second fixture machine (a fresh host clone with a differently named fork remote) runs `zn init` with the same URL and finds the project, and the tracker's `origin/main` is unchanged.

## Open to the human
- Q1: Who is the one user? The design assumes the owner, with a GitHub account that owns both the fork and the tracker repository.
- Q2: Fork and upstream pull requests, or push access? This ticket assumes a fork (`--fork`, and zn never merges). f0427's Solution has the worker land the pull request. Also, this ticket says zn opens a pull request "only when the owner runs a command for it". As designed, that command is `zn pr`, and the worker session runs it on the owner's behalf. Should `zn pr` instead refuse unless it runs in a terminal the owner types into (like `approve`)?
- Q3: Is carrying the Luau engine inside the Go program first acceptable (f0427 Q3)? This ticket's tracker commands rely on it.
- Q4: What is the tracker repository's name? Guess: `philipbergen/zn-tracker`, public, with `main` as its branch.
- Q5: The tracker's commits publish the git author email configured on the machine. Use GitHub's noreply address in `.tracker`'s local config? Guess: zn sets no identity, and the owner's own git configuration decides.
