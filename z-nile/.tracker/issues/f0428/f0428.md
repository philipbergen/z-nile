# f0428: Tracker in its own repo

## Problem
- zn keeps every ticket, raft, design, review, lesson, setting and skill inside the repository it works on, so using it in a host repository the owner does not own (first: omarchy) would add zn files and commits to that repository.
- The owner has no separate public repository that holds the tracker, so the work cannot be showcased without the host repository carrying it.

Decided with the user (2026-11-21, contribution): "fork and pr": the owner works omarchy through a fork with pull requests to upstream. This answers Q2; the same ruling is on f0427. Each step's acceptance spec is reviewed separately from its code ("it may write it but it has to be reviewed separately").

Decided with the user (2026-11-21, clone layout): asked how the omarchy clone names its remotes, the owner answered "clone layout should be completely irrelevant. All you need is a base directory of omarchy and you pop a .tracker folder in there that you manage via a separate github". So zn asks nothing about remotes: `zn init <tracker-url>` run in the host's base directory is the whole setup, and zn works out by itself which remote is the upstream and which is the owner's fork (from the remotes' addresses and what GitHub says about them), whatever they are named. The `--fork` and `--upstream` options stay only as overrides for a layout zn cannot work out, and zn says so plainly when that happens. This replaces the open question about the clone layout.

Decided with the user (2026-11-22, the tracker repository's name): asked what the tracker repository is called, the owner answered "Every user chooses it on their own, just walk them through how to create an empty repo and then zn can initialize it and put a README and add .tracker/ to .gitignore in the actual repo". So `zn init` with no address prints a short walkthrough and changes nothing; zn never creates the repository or an account, never runs `gh repo create`, never asks for or reads a token; and `zn init <address>` initialises an empty tracker (README, skeleton), pushes it, and keeps `.tracker/` out of the host. This answers Q4 (no default name) and shapes the ignore rule (guess G15).

Decided with the user (2026-11-22, a fork with no upstream remote): fetching the upstream into zn's own ref `refs/zn/upstream/<branch>`, with no remote added, is confirmed ("as built"). S3 and guess G14 are ruled.

Decided with the user (2026-11-22, where the ignore line goes): "I meant to put .tracker in there, we don't have to commit .gitignore". And the owner's description of the layout: "in the base omarchy repo .tracker is ignored, but when you CD into .tracker it's a repo that's its own thing and it has all the tickets and they are in a seaparate rpo". The lead's reading, kept as guess G15: the default is `.git/info/exclude`, which ignores `.tracker` with nothing tracked changed; `--gitignore` writes the tracked file, uncommitted.

Decided with the user (2026-11-22, the host's own tests): asked whether running Omarchy's `test/all` is safe on the live machine, the owner answered "3 I don't know we can test". So, as a constraint for every later step: zn never runs the host's own test suite by itself until that has been tested. Before the first run the lead reads the host's test scripts and reports what they touch (files, network, services, the machine's state).

## Non-goals
- zn does not write the host's `.gitignore`, the user's `core.excludesFile`, or any other tracked or global ignore file.
- zn does not create the owner's fork or add a remote to the host clone, so setup fails with a message when the host has no remote it can use (it never asks for one by name).
- zn does not fetch from the fork remote, fetch tags, or fetch any origin branch other than the default branch.
- zn does not pull, merge, rebase or fast-forward the local default branch, so it stays where the owner left it.
- zn does not merge, close or land any pull request in the host repository.
- This ticket does not package zn as the Go app (f0427), publish the board (f0429), or bridge to GitHub issues (f0430).
- This ticket does not support more than one tracker repository per host checkout, or more than one user.
- This ticket does not move pickman's existing in-repository trackers into a separate repository.

## Solution
- One zn setup command, given only the address of the owner's tracker repository (it works out which remote is the fork), clones the tracker to `.tracker` at the root of the host's main checkout, as its own git repository with its own remote.
- zn reads and writes every ticket, raft, design, review, lesson, setting and skill only inside that tracker checkout, and commits and pushes them only to the tracker repository.
- The setup command appends rules for `.tracker`, `.worktree/` and `.cache/` to the host clone's `.git/info/exclude`, which git never commits or pushes.
- In the host's working tree, zn itself writes only under `.tracker`, `.worktree/` and `.cache/`.
- Before it creates a ticket branch, zn fetches the default branch of the host's origin without tags, and starts the ticket branch from the fetched `refs/remotes/origin/<default branch>` commit, not from the local default branch.
- For each ticket, zn creates one new branch and one worktree under `.worktree/`, and the worker zn runs commits there only the ticket's code changes, so no commit on a ticket branch contains a path under `.tracker`, `.worktree/` or `.cache/`.
- zn pushes a ticket branch only to the fork remote named at setup, and pushes nothing to any other host remote, the host's origin included.
- In the host's `.git`, zn writes only: `info/exclude`; what that fetch writes (`refs/remotes/origin/<default branch>`, `FETCH_HEAD`, the fetched objects and their reflog entries); the registration and per-worktree state of worktrees it creates under `.worktree/`; `refs/heads/<ticket branch>`, its reflog and its upstream settings in `config`; the objects of commits on ticket branches; and `refs/remotes/<fork>/<ticket branch>`, which its push writes.
- zn and its worker make no commit on, and move no ref under `refs/heads/` or `refs/tags/` that zn did not create, the local default branch included.
- The only remote-tracking refs zn moves are `refs/remotes/origin/<default branch>`, by its fetch, and `refs/remotes/<fork>/<ticket branch>`, by its push; a remote-tracking ref is not a host branch in the sentence above.
- Ticket code reaches the host only through a pull request from the fork's ticket branch, which zn opens only when the owner runs a command for it and never merges.
- After setup and after any zn command, `git status` in the host's main checkout and in every worktree lists no `.tracker`, `.worktree` or `.cache` entry, `git diff` in the main checkout shows no change to any tracked file, `.gitignore` included, and `git rev-parse` of the local default branch gives the same commit as before the command.
- Every worktree of the host repository resolves the tracker to the one checkout in the main checkout, so a ticket written from any worktree appears in all of them without a second clone.
- The tracker repository is public on GitHub under the owner's account.

## Design
Risk is risky: this ticket decides what zn may write into a repository the owner does not own, and what it pushes to a public one, and a push to the wrong place cannot be taken back. It depends on f0427, which provides the Go `zn`, the tracker checkout, host facts and sequestration. The design review covered both tickets: `../f0427/design-review-001.md`, answered in `../f0427/design-refute-001.md`.

**Two repositories, one rule each.**
- The host (omarchy) receives one branch per raft, pushed to the fork, and one pull request from it.
- The tracker repository (the owner's, public) receives everything else, as commits pushed straight to its `main`.

No commit goes to both.

**The tracker checkout** is `<host main checkout>/.tracker`, a plain `git clone` of the tracker repository with its own `origin`: not a submodule and in no `.gitignore`. It is f0427's tracker with `origin` pointing at GitHub instead of the bare repository in the data directory. One tracker repository may hold several hosts. Each host is a project `<name>/.tracker` in the tracker's `z-nile/projects.toml`, with a `[host.<name>]` table in `settings.toml`.

**Resolution, from any folder.** `zn` walks up from the working directory:
- A folder whose git top holds `z-nile/projects.toml` and whose main checkout is named `.tracker` is a tracker checkout or worktree. The host is the parent of that main checkout.
- Any other git checkout is a host, at `dirname(git rev-parse --path-format=absolute --git-common-dir)` (E2g), with its tracker at `<host>/.tracker`.

The tracker-side verbs are `zn tracker worktree <name>` (`.tracker/.worktree/<name>`) and `zn tracker merge`: merge `origin/main`, run `zn audit` and f0427's sequestration guard, then push. The host verbs are `zn worktree`, `zn commit`, `zn pr` and `zn land`.

`zn init` refuses hosts where `dirname(common dir)` is wrong, naming the case:
- a submodule (`git rev-parse --show-superproject-working-tree` is not empty);
- a separate git dir (the common dir is not `<top>/.git`);
- a bare repository with worktrees (`core.bare` is true);
- a repository that uses Git LFS (for now: its filters would run during `worktree add`), refused by a later step of `init`.

**Hiding.** Setup appends `.tracker/`, `.worktree/` and `.cache/` to the host's `.git/info/exclude`, each only when missing. The exclude file of the common directory applies to every linked worktree (E1). `git status`, `git add -A`, `git stash -u` and `git clean -fdx` all skip the nested clone and the worktrees. Only `git clean -ffdx` deletes them (E2), and the host skill names it as forbidden.

**Claims and publishing** map one to one onto the tracker repository. The claim is a push to the tracker's `origin/main`, and two machines race on it exactly as two worktrees do today. Design and bundle work is done in a tracker worktree and goes in with `zn tracker merge`; nothing in the tracker needs a pull request. The board is built into `.tracker/.cache/board.html`, and f0429 publishes it from the tracker repository.

**A raft's host branch.** A raft is one branch, `zn/<R-id>-<slug>`, holding its tickets as layers (f0427 section 5). `zn worktree <R-id>` runs:
1. `git fetch --no-tags --refmap= origin +refs/heads/<default>:refs/remotes/origin/<default>`, with the pins named below
2. `git worktree add --no-track -b zn/<R-id>-<slug> .worktree/<R-id> refs/remotes/origin/<default>`

Step 1 builds these in `internal/host` and deviates from the command first designed here in two ways, each for one reason:
- `--refmap=` (empty): a fetch refspec configured on the host's `origin` would otherwise make git update other remote-tracking refs from the same fetch (review P4).
- the refspec is forced (`+`): a force-pushed upstream default branch would otherwise leave the fetch refused and the raft stuck (review P3).

The write-path rule has three sentences. Before every write, zn reads the host's local config (and its per-worktree config when `extensions.worktreeConfig` is on) and refuses, naming the key and its file, unless every key is on the allowlist table in `internal/host` of what a normal clone holds (no `include.*`, no `uploadpack`, `sshCommand`, `filter.*`, `hooksPath` or `worktree`), and every remote URL is https, ssh, file or an absolute path, never a `name::` transport helper. The fetch passes `--upload-pack=git-upload-pack` on its command line, and before `worktree add` zn refuses when any `.gitattributes` of the base commit, or the host's `info/attributes`, selects a `filter=` driver (so a host that adopts Git LFS is refused at every worktree creation). Beyond those, every write runs with `-c` pins that stop what a `-c` can stop: `fetch.prune=false`, `fetch.pruneTags=false`, `submodule.recurse=false`, `gc.auto=0`, `maintenance.auto=false`, `core.fsmonitor=false`, `protocol.ext.allow=never`, `protocol.fd.allow=never` and `core.hooksPath` set to an empty folder under the host's ignored `.cache/`, so no host hook runs; a `-c` pin does not override `remote.<name>.uploadpack`, which is why the allowlist and the command-line option exist. Writes use the user's global and system git config (credentials, proxies, url rewrites live there); reads (the snapshot) pin both to `/dev/null`. Both environments come from an allowlist. Every call is confined to the host's main checkout: `Open` requires git's own top level, git directory and common git directory to be that checkout's, with `.git` the common one, and the hooks folder to be under `<root>/.cache/`.

A raft that depends on an unlanded raft starts from that raft's branch tip and waits in the fork. Once the lower raft lands, `zn worktree --restack` rebases it onto the fetched default. Spend rows are keyed by ticket plus patch-id, so they survive the rebase. The raft document records `branch:` and `pr:` in the tracker. The pull request body links the raft's file in the tracker repository, and the host's commits carry no trailer and no tracker path.

**Pull requests and the end of a delivery.** `zn pr <R-id>` first runs f0427's `done --check`. It pushes `-u <fork remote> <branch>` and runs `gh pr create --repo <upstream> --head <fork owner>:<branch> --base <default>`. On a repository the `gh` account does not own, `zn pr` runs only when stdin is a terminal and neither `ZN_DISPATCH` nor `ZN_APPROVE_SESSION` is set: a person types it, as with `approve`. On the owner's own repository, the worker may run `zn pr` and `zn land`. zn never pushes to any other remote, and never merges a repository it does not own.

The delivery then waits in the named stage "pull request open, waiting on upstream". On every run, `zn work` reads the pull request's state through the host facts:
- merged, by any method including squash (gh's `state: MERGED`, not ancestry): it publishes the raft and its tickets as landed;
- closed without a merge: it frees the claim, as `stop` does;
- changes requested: the raft goes back to code;
- a head sha newer than the approved one: the raft goes back to review.

**Recovery: no local owed state.** Every tracker write is derived again from host facts on the next run, and is idempotent:
- A spend row has the key (ticket, patch-id), and a key already published is skipped.
- `zn land` asks the PR's state first: already merged means it only publishes landed.
- If `ready` wins but the fetch then fails, the raft is claimed and `zn worktree` is simply run again.
- A refusal by the scan exits with 5 and the message "refused by scan: <file>:<line>". It is never retried as a lost push race, which exits 1 and is retried.

**As built (step 2), under the owner's 2026-11-21 ruling that the clone layout is irrelevant, as changed by its code review.** `internal/host` holds:
- Two readers of remote addresses on one shared tokenizer. `CheckAddress` is the safety reader (a transport helper, a leading dash, a scheme other than https, ssh and file, a credential, an unusable host): the write gate (`urlAllowed`) and `CheckHost` ask only this of every remote, so a remote that is safe but oddly shaped (a backup `git@nas:omarchy.git`) blocks no write. `ParseRemote` applies it first, then the identity grammar. https, ssh://, scp-like, absolute-path and file:// forms give `RemoteID{Host, Owner, Repo}`; the host and every path segment are held to a grammar (no `@`, `:`, `%`, spaces or non-ASCII; on github.com exactly owner/repo, so a pasted `/tree/main` is refused); user information on https, a password or token on ssh is `ErrCredential`, and no error ever holds any part of an address. Identities compare by `Key()` (owner and repository lower-cased on a host, as GitHub treats them) and keep the spelled case for display. A local path keeps `/x/r.git` and `/x/r` apart, drops only a trailing `/.git` and resolves symlinks. The port is dropped (a server is its host).
- `(*Repo).Remotes`: each remote's fetch and push identity from the repository's own config. A remote whose address is unsafe carries its `Err` (it names the remote); one that is safe but has no owner/repository carries `NoIdentity`, and `Roles` skips it (naming it when the outcome is not resolved); a push address that is not an address (`DISABLE`, `no_push`) is `PushDisabled`, not broken. Step 1's write refusal accepts it, and no refusal prints a remote's value (its key and "its value is not shown"); git's own stderr is scrubbed of user information.
- `Roles(remotes, lookup, overrides)` with an injected `Lookup` returning `Facts{Parent, CanPush, Owned}`. Remote names never decide. Land mode "merge" needs `Owned`: push access is not ownership, so a maintainer's single upstream remote is need-fork. An owned repository whose contributors' forks are extra remotes is merge. A fork must have a push address that is its fetch repository (`Role.Push` carries it for step 7). Overrides are checked against the lookup: the fork must be pushable, a swapped pair or a fork of a third repository is refused, both given still look up; they win only where the lookup cannot settle the layout. `ErrNotServed` skips a remote the lookup does not serve (named in the reason when the outcome is not resolved); not signed in gives outcome `unknown` (never "not a fork"); any other lookup error is an error. Only a credential or a transport helper refuses the whole result; another unusable remote is skipped. `--fork` alone is checked against the other remotes too: a pushable upstream the user does not own, named as the fork while another remote is the user's fork of it, is refused as swapped.
- A clone of only the owner's fork has a nameless upstream: the result carries `UpstreamURL` (the https address of the parent the lookup returned, which must be on the fork's own host and survive both readers, else the result is a refusal naming the lookup and never the answer) and `UpstreamRef(default)` = `refs/zn/upstream/<default>`; no remote is added and the host's config is not changed. The fetch is step 3. This adds one ref name to the Solution's write list (guess G14, scope question S3).
- `CheckHost(dir)`: read with the program-stopping pins (`core.fsmonitor=false`, hooks off, transport helpers off) on every read, in the scrubbed environment, with git's discovery stopped at the directory's parent. Reasons: not a repository, bare, submodule, not the top level, gitfile (separate git dir or linked worktree), local-config (the step-1 allowlist, so init refuses before it writes anything) and a tracked path under `.tracker`, `.worktree` or `.cache` (case-insensitive when `core.ignorecase` is on). `(*Repo).CheckBase(rev)` does the same for a base commit with `ls-tree`, and `AddWorktree` calls it. No shallow-clone refusal: the design names none and a push from a shallow clone works.

- The engine runs as zn's child in a host, not by exec (`cmd/zn/main.go runInTracker`, `runChild`): zn takes the lock, prepares, runs the engine, then calls `Tracker.Refresh` (Prepare without the fetch), which judges the main the engine published to and only then moves the standing worktree there. With `ZN_FRONT_DOOR=1` the engine's `mergeOrigin` merges nothing, and `status` reads the document it remembers a claim from out of the commit it published (`git show <sha>:<path>`); `rememberClaim` refuses a `.cache` that is a link. I chose zn as the parent over moving `KeepAcrossExec` to just before an exec: with an exec the engine's own children inherit the descriptor whatever zn does, and the parent form is small (one function) and also gives zn the place to filter the engine's output and to refresh after it.

This replaces the design's `--upstream` default of `origin` and the `--fork` requirement of `zn init`: init asks nothing about remotes.

**Remotes.** Settings store each remote as `host` plus `owner/repo`, never as a URL. Each run normalises a remote URL in ssh, scp-like or https form (`git@github.com:o/r.git`, `ssh://git@github.com/o/r`, `https://github.com/o/r.git`) to that pair, and resolves the fork and upstream remotes by it. A URL holding credentials (`https://user:token@…`) is refused and never stored. `gh repo fork` names the fork `origin` and the upstream `upstream`, so zn works out which remote is which from the repositories, whatever the remotes are named; `--upstream` and `--fork` only override it (see As built, step 2).

**`zn init <tracker-url> [--fork <remote>] [--upstream <remote>]`** (the two options are overrides only, replaced by step 2's `Roles`) is idempotent: each step checks before it writes.
1. Resolve the host's main checkout, and refuse pickman and the unusual hosts.
2. Work out the roles (`host.Roles`), refusing, naming the remote, when an override is not a remote or carries credentials, or when the result is ambiguous, refused or unknown.
3. Read the default branch with `git ls-remote --symref <upstream> HEAD`, which writes nothing.
4. Append the missing exclude lines.
5. Set up `.tracker`:
   - With no `.tracker`, clone it.
   - With an f0427 local tracker, push `main` to the URL when that repository is empty, then set `origin` to it. When the URL already has a `main`, refuse.
   - With a tracker whose origin is any other repository, refuse.
6. When no project matches the upstream pair, add the project and its `[host.<name>]` table, then commit and push. Install the scan hooks.
7. Print the board's path and `zn work`.

A second machine, or a fresh clone, runs the same command: step 5 clones and step 6 finds the project. Its fork remote may have any name and any URL form.

**What is public, and the scan.** Everything committed to the tracker is public: tickets, designs, reviews, guesses, approvals, lessons, skills, settings, the board's sources, and each commit's author name and email. Machine-local state stays in `.tracker/.cache/` and in `prompt.md`, both ignored by the tracker's committed `.gitignore`.

`zn scan` (Go) runs at two points: as the tracker's `pre-commit` hook (and inside every plumbing publish before it pushes), and again as `pre-push`. It refuses, naming the file and line, any new commit whose added lines, commit message or file names hold any of:
- this machine's `$HOME`, its host checkout path, `uname -n` or the user name;
- any home path recorded in `.tracker/.cache/seen-homes`, which every machine adds itself to (local, so other machines' paths are caught once seen);
- a GitHub token (`ghp_`, `gho_`, `ghs_`, `ghu_`, `github_pat_`) or a private key header (`-----BEGIN … PRIVATE KEY-----`).

An author email outside the GitHub noreply form gets a warning, not a refusal (Q9). Prose such as `/home/<user>/.config` passes. `zn doctor` fails when the tracker's `core.hooksPath` is set or a hook is missing or not `zn`'s. pickman's tracker prose holds its home path 379 times; moving pickman is a Non-goal, so that does not apply here.

### Scalability
A fetch of one ref with no tags. One push per tracker write, as today. The scan reads only the new commits.
### Maintainability
All host git work is in `internal/host`, one function per allowed write. The E7 snapshot test lists every ref and config line, so a new write must be added there to pass. Remote identity has one reader, `internal/host.RemoteID`.
### Usability
Every refusal names the remote, the URL form, the file or the hook. `zn init` prints each step it took, and nothing for a step that had nothing to do.

## Open to the human
The design is `design: reviewed`. It stays short of `ready` until these are ruled.
- Q1: Who is the one user? The design assumes the owner, with one GitHub account that owns both the fork and the tracker repository.
- Q2: How does code reach omarchy: through your fork with pull requests to upstream, or with push access? It is the same question as f0427's Q2, and it needs one answer for both tickets.
  - Fork (the default): you type `zn pr` yourself, and the delivery waits in "pull request open, waiting on upstream" until the maintainers merge it or close it.
  - Push access: the worker opens and merges the pull request, and this ticket's Non-goal "zn does not merge … any pull request in the host" would have to change.
- Q3: Is carrying the Luau engine inside the Go program acceptable as the first packaging (f0427 Q3)?
- Q4 (RULED 2026-11-22): every user names their own tracker repository; `zn init` with no address walks them through creating an empty one. `main` is its branch.
- Q5: Should tracker changes go straight to the public tracker's `main`? Guess: yes, which is fast, with no pull request for tracker work. The alternative is pull requests in the tracker repository too: slower, but every change gets a reviewable page.
- Q6: What may omarchy's maintainers see? Guess: the branch name `zn/<R-id>-<slug>` and one link to the raft's page in the tracker, in the PR body. The alternatives:
  - nothing at all: a plain branch name and no link;
  - more: a `Zn-Ticket:` trailer in each commit, which puts zn into omarchy's history.
- Q7 (partly answered 2026-11-22: "3 I don't know we can test"; zn does not run the host's own suite by itself until that is tested, see the decision above): Which test command gates omarchy work on your live machine? Same as f0427 Q5.
- Q8: Should the tracker's commits carry your real author email? Guess: zn sets no identity, and the scan warns when the email is not GitHub's noreply form. The alternative is for `zn init` to set the noreply email in `.tracker`'s own config.
- S1 (scope, Solution): "For each ticket, zn creates one new branch and one worktree under `.worktree/`". The sentences that name "ticket branch" (the fetch, the pushes, the `.git` write list, the remote-tracking refs) now apply to one branch per raft, holding its tickets as layers, because you want fewer, meatier pull requests (design-review F7). Do you accept "ticket" becoming "raft" in those sentences? A raft of one ticket is the same as before.
- S3 (RULED 2026-11-22: accepted as built; scope, Solution; guess G14): a host cloned from only the owner's fork has no remote for the upstream, and the owner's ruling is that the layout must not matter. zn fetches the upstream's default branch by the https address of the parent GitHub reports, into the ref `refs/zn/upstream/<default>`, adding no remote and changing no config. That adds one ref name to the Solution's list of what zn writes in the host's `.git`. The alternative is for `init` to refuse with one sentence naming `git remote add upstream <url>`. Do you accept the extra ref name?
- S2 (scope, Solution): "Ticket code reaches the host only through a pull request …, which zn opens only when the owner runs a command for it". The design reads "the owner runs a command" as "a person types `zn pr` in a terminal" on a repository the account does not own. Does that match what you meant?
