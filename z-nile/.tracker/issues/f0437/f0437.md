# f0437: The app on the live daemon

## Problem
- The Approvals, Workers, Stats, Tickets and Rafts views exist only as f0425's mockup with simulated data, and nothing serves any view with the real tracker or the live daemon's real state.
- There is no board view and no settings view in an app at all, real or simulated.
- No view updates when a step forward is recorded, although the live daemon already emits an event for each one (f0424).
- A person can start and watch a worker or a dispatch run only from a terminal of their own, never from an app.

The owner's statement of the intent (2026-11-22), captured at their request ("please capture that, it was great clarity how I just wrote that"): "I am really excited about workers being able to optimistically forge ahead and me just approving or disapproving in the end, automaticaally picking up tickets, maturing idea nd design, rafting them and following the dependencies from the bottom. so that I can just sit with the UI and go through approvals. Moving the multitasking pain to the agents, my time looking linear, working through a theme at a time, a raft at a time, an idea and a design at a time". This is the measure for this ticket: the workers carry the parallel work and never wait on the owner; the owner's time is one linear pass through approvals, a theme, then a raft, then an idea and a design at a time. The same day the owner ranked dead or hung workers low ("manually fixing that is cheap").

## Non-goals
- The app has no view or control for browsing, opening or reading the repository's code files or diffs; code that a run prints in its embedded terminal is not ruled out.
- The command line loses no command and keeps working with the app not running.
- The live daemon's own knowledge of workers, claims and events (f0424) is used as it is, not redesigned.
- The control on every item that starts `zn talk` with that item's context is f0432's deliverable, and this ticket neither builds nor changes it.

## Solution
- One command starts the app, served by the live daemon, and opens it in a browser or window.
- The app shows the real tracker and the real live state in the views approvals, workers, stats, tickets, rafts, the board and settings, with no simulated data left in a delivered view.
- Every view updates by itself when the live daemon records a step forward, without a reload.
- A worker or a dispatch run can be started from the app and watched in an embedded terminal, which shows that run's own output unchanged, including any code the run prints.
- Every item shown in a delivered view has a place where f0432's talk control can sit, and this ticket adds no talk control of its own.
- The app is built view by view from the mockup, each view replacing its simulated data with real data.

### Slim design (step 1: serve the app, Workers live)
- **Opt-in HTTP in the daemon.** `znlive serve --http [--port N] [--page FILE]` (and the new client op `znlive app [--port N] [--page FILE]`) opens an HTTP listener on `127.0.0.1` only (never another interface), on the given port or one the OS picks, and writes `host:port` to `<state>/http` (removed at exit). A daemon that an `emit`/`register` auto-starts passes no `--http`, so it opens no port. `app` auto-starts the daemon (a write op), then asks it over the socket to start serving, and prints `http://127.0.0.1:PORT/`; a second `app` prints the same URL.
- **Package `internal/web`** (pure handler over `*live.Core`; the daemon owns the listener). `GET /` serves the page file read from disk at each request (`z-nile/app/index.html` of the checkout `./zn app` ran in, else the main checkout's; sent to the daemon as the `page` of the `app` op; embedding is a later step). `GET /api/state` returns `{seq, now, workers[], claims[]}` from `Core.Snapshot()`. `GET /api/events` is Server-Sent Events: one `data:` message per event after `Core.Seq()` at connect, woken by `Core.Next` (the same wake-up `wait`/`events --follow` use, no polling), plus a `: ping` comment every 15 s.
- **Same-origin only.** Every request: method GET (else 405); `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (else 403, which also stops DNS rebinding); a present `Origin` must be `http://` plus such a host (else 403); no CORS allow header is ever sent; `Cache-Control: no-store`.
- **Idle exit** counts open HTTP connections like socket connections, so a browser left on the app keeps the daemon up.
- **`./zn app [--open] [znlive-app-flags]`** (wrapper case beside `live`, same build-if-missing and state-folder rules) runs `znlive app` and prints the URL; `--open` also runs `open`/`xdg-open`. `ZN_LIVE_DIR`/`--dir` name the state folder as for `live`.
- **The page** `z-nile/app/index.html` is a copy of the f0425 mockup (kept as the design reference) plus one appended `<script id="live-data">`: over `http:` it fetches `/api/state`, subscribes to `/api/events` (refetch on message; a 15 s refetch keeps "last heard" fresh), and replaces `renderWorkers` with a renderer of the real workers (same cards, state in words, capability chips, elapsed time ticking client-side) and a claims list; no workers: it says so and names `./zn live register --cli <name> --pid <pid>`. A badge in the corner reads "live" on Workers and "simulated" on every other view; from `file://` the badge reads "simulated" everywhere and nothing is fetched.
- **Scalability**: one goroutine per open SSE connection (owner: the HTTP server, ends at disconnect or daemon stop); a state request is one mutex-held copy of the maps. **Maintainability**: later views add one endpoint each in `internal/web` and one renderer override each in the data layer. **Usability**: refusals name the rule (the Host mismatch says which host is accepted).
- **Page rules (review 001 F1, G9).** The daemon, not the client, decides what it serves: absolute clean path; after symlinks a regular file `index.html` (or `live.js` beside it) directly in a folder `z-nile/app`, at most 4 MiB, with one name only (a hard link is refused) and the file opened is the file checked; for the default state folder also inside the main checkout or one of its `.worktree/<name>/`; checked when `app` names a page and again at every read (`O_NOFOLLOW`); a refused swap keeps the current page and the client exits 2 with the rule; a vanished page falls back to the main checkout's; no body or log line sent over HTTP contains a path.
- **Limits (G12)**: 60 s idle timeout, 16 KiB headers, 64 connections, 16 event streams (17th gets 503, the page reopens its stream itself with a growing pause and says why), 10 s write deadline per stream write.
- **Headers (G8)**: CSP, `X-Frame-Options: DENY`, nosniff, no-store; `Sec-Fetch-Site` cross-site or same-site is refused. **View model (G10)**: no host, pid or session in `/api/state` or the events; a public display needs a per-launch token and its own review, and is not designed here.
- **Restart (G11)**: `<state>/http.last` remembers the port; `./zn app` asks for it first. The page names `./zn app` when it cannot reach the daemon.
- **The page**: `z-nile/app/index.html` equals the mockup except its title and one `<script src="live.js">` line (spec `app-copy` fails otherwise); the data layer is `z-nile/app/live.js` with pure renderers (tested by `tests/tooling/app-live.node.js` against a stub page).
- **`check.sh` was written during the build, on the coordinator's instruction, while the design was draft** (it is normally sequestered): the approval walk should raise it.
- **Step 6 note**: the per-launch token must never be stored in the page origin's storage (localStorage, cookies, sessionStorage): another program can take a remembered port and would then read it.
- **Later steps (2 to 6) are listed, not designed.** `design: draft` stays.
- **State file** `<state>/http` is ignored (under `.cache/live`), listed in AGENTS.md with the daemon's state.

### As built, step 4a: the linear Approvals view
- **Facts path.** `./zn approve <scope> --queue` (the read form an agent may run) also writes `<state>/approvals.json` (ZN_LIVE_DIR, else `<main checkout>/.cache/live`; version 1; written atomically; an empty `themes` list when nothing waits) and pokes the daemon. The pure module `engine/approvalfacts.luau` orders it: themes as `tributaries.toml` lists them (then `unsorted`), rafts in queue order (a stack's bottom first), tickets in layer order; only tickets that wait. Per ticket: Problem and Solution, the Design section cut into its `###` parts (each capped at 1,500 characters), every guess (open, chosen, why), the review files with their `Verdict:` word, tokens and minutes from `spend.md` when recorded, the layer branch and pull request when found.
- **Daemon.** `GET /api/approvals` (`internal/web/approvals.go`) reads that file (never a link, at most 8 MiB, version 1) and passes on only the known fields: `{state: ok|absent|unreadable, why, facts}`. Absent or unreadable names the command to run and never a path. Go reads no ticket file. The route table is one map; `web.Routes` is tested against the reviewed set.
- **View.** `live.js` replaces `renderView` over http only: one ticket at a time with "theme 2 of 4, raft 1 of 3, ticket 2 of 5", Previous and Next, keys `j`/right arrow and `k`/left arrow (ignored while typing), an outline at the side to jump, then the idea, the design, each guess as a card, reviews, cost and links. From `file://` the mockup's simulation stays. Absent, unreadable, loading, unreachable and empty (Nothing waits for your approval) states are written.
- **Approving is the person's own act.** The daemon stays GET-only with the reviewed route set; the page has no POST, no form and no request method but GET (a node test fails on one). Approve shows the ruling form bound to the run, `./zn approve --ruling <run> <id> approve` then `./zn approve --apply <run>` (never the bare `./zn approve <id>`, which records at once with no hash check), and Send back shows `./zn approve --ruling <run> <id> change --stage <stage> --note '<message>'` then `./zn approve --apply <run>`, each with a Copy button, for the person's own terminal. The hook that refuses an agent's `./zn approve` is unchanged. See G13.
- **Review fixes (round 1).** The facts carry each ticket's contract hash (the queue row's) and the `scope` of the queue; the page shows the first 12 characters of the hash, `--apply` prints the same 12, and `--apply` refuses a changed contract. A scoped queue shows "showing: R0002 only" and an empty one says "Nothing waits in c0006" (the facts file is still one file that the newest `--queue` overwrites; one file per run with the newest unscoped one shown by default is not done). Text is clipped on a UTF-8 boundary; a failed write removes the old facts file and prints one line. The engine writes facts under `ZN_LIVE=off` or a check marker only to an absolute `ZN_LIVE_DIR`. A named pipe in place of the file no longer hangs the daemon (`O_NONBLOCK`). A raft's tributary wins over its tickets' and themes are keyed by project and name. A PR link with credentials is shown without them and never linked.
- **Residual risk, in plain words.** The page is display only. An agent that can write the facts file can pair a ticket's real contract hash with false text. What protects the owner is the terminal: `--apply`, run by the person in a process an agent does not control, prints the title, the guesses and the contract hash from the tracker itself, asks y/N, and refuses when the contract is not the one queued. The view says so on every ticket ("what you approve is what the terminal shows").
- **Not built.** No talk button (`zn talk` is f0432 and does not exist); `./zn rework` does not exist on main (only the hook names it), so send-back uses the ruling form; a guess has no alternatives field in `guesses.md`; reviews are read from the checkout that ran the command.

#### Decisions

**1. Markdown (decision A), built inside `z-nile/app/live.js`** (pure function in `make(env)`, tested in node with the existing harness; no new file, no new route, no change to `index.html`, so `app-copy` stays byte-checked; G26).
- Input: text. Output: an HTML string built only from a fixed set of elements: `p`, `h3` to `h6` (a `#` heading is shown as `h3`: the page keeps its own `h1` and `h2`), `ul`, `ol`, `li`, `strong`, `em`, `code`, `pre`, `table`, `thead`, `tbody`, `tr`, `th`, `td`, `blockquote`, `hr`, `a`, `br`, and for the diff `ins` and `del`. Attributes: only `href` on `a` (built by the renderer from `#/ticket/`, `#/raft/` or `#/tributary/` plus `encodeURIComponent` of an id it has checked), `class` taken from a fixed list in the renderer, and `colspan`-free tables (no `align`, no `style`). Never an event handler, `style`, `title` from text, `src`, `srcset` or `id`. Everything else is escaped through `env.esc` (`& < > " '`) before it is placed.
- It is two passes over lines (blocks) then characters (inline), never a regular expression with nested quantifiers. Block rules: fenced code (``` and ~~~, an unterminated fence runs to the end of the text and is shown as code), tables (a header row, a delimiter row, then rows; a table with no delimiter row is a paragraph; cells are inline text), lists (`-`, `*`, `+`, `1.`; nesting by indent of 2 spaces or more; each level a new list), block quotes, horizontal rules (`---`, `***`), headings, paragraphs with a hard break on a trailing backslash or two spaces. HTML comments (`<!-- ... -->`) are removed first, an unterminated one is shown as text. A raw html tag in text is escaped and shown as text.
- Inline: `code`, `**bold**`, `*italic*` and `_italic_` (not inside a word), `~~~` is not strikethrough (the page keeps `del` for the diff alone), `[text](address)`, bare addresses and ids.
- **Links.** Outside addresses (`http:`, `https:`, `mailto:`, `javascript:`, `data:`, `file:`, `//host`, anything with a scheme) are never clickable: they are shown as the link text, then the address in a `code`-styled span (clipped at 200 characters with an ellipsis, wrapping), so the person sees where it would go and copies it by hand. An address in the `href` position that is an in-app route or an id (`c0261`, `#/ticket/c0261`) becomes an in-app link only if that unit exists (decision B). No `target`, no `rel` is needed because no outside link exists.
- **Bounds (G27).** (a) Input over 200,000 characters is cut at a character boundary and followed by "text cut here: N more characters in the ticket file". (b) A line over 20,000 characters is shown as plain wrapped text, not inline-parsed. (c) Nesting (list levels and quote levels together) is capped at 8; deeper lines are rendered at level 8. (d) Emphasis delimiters pending per paragraph are capped at 64; the rest are literal. (e) A table has at most 200 rows and 40 columns; the rest are cut with the same cut notice. (f) A work budget of 2,000,000 character steps for one call, counted in the renderer (not a clock): when it runs out the rest of the text is shown escaped in one `pre`, with the notice. (g) At most 20,000 output elements, the same exit. The tests also assert a wall time (250 ms for the 2 MB cases) as a guard, because a budget that is counted wrongly is still a hang.
- **Nothing is trusted twice.** A second pass is not needed: every string goes into the output only through `esc` or as a number, and the real-data test (below) re-parses the output with the page's own DOM parser in node (a tiny allowlist walker over the string) to assert only allowed elements and attributes.
- **Overflow** (fixed already, as the owner says): code blocks scroll inside themselves, tables scroll inside a wrapper `div` of the renderer's making, long tokens wrap (`overflow-wrap:anywhere`), blocks use `min-width:0`. Slice 1 adds a spec on the css rules and an owner look at phone width.
- **Colours and fonts (F).** Only existing tokens. Added text uses `--ok` as a tint with an underline; removed text uses `--back` with a line-through; both also carry a `+`/`−` mark in front of changed lines and the words "added" and "removed" for assistive tech (`ins` and `del` carry `aria-label`-free text, the page adds a visually hidden "added:" and "removed:" label). A script checks every pair for WCAG AA in light and dark (as in step 4a, 0 failures needed; the colour is never the only carrier).

**2. Ids become links (decision B).** One function `linkIds(text, index)` runs on the escaped text pieces of paragraphs, list items, table cells, headings and block quotes, and on the page's own titles (ticket, raft, review names, guess text). An id matches only when it is not preceded or followed by a letter, digit, `_`, `-`, `/`, or a `.` followed by a letter (so `xc0261`, `c02610`, a name inside a path or a URL do not link; `c0261.` at the end of a sentence does). It matches a ticket (`[cfd]` + four digits) or a raft (`R` + four digits) in `index`, the units index (below). Inside a fenced block: never. Inside inline code: only when the code is exactly the id. An id that is not in the index is left as text with a dotted underline and the tooltip text "not in the tracker now (withdrawn, or an example)" (G29). Tributary names: a name from the themes facts links when it is inline code exactly equal to it, when the word before it is `tributary` or `theme`, or when it contains a hyphen and is not part of a longer hyphenated word; the plain words `worker`, `lessons` and `omarchy` therefore never link from prose (G31). The link goes to the detail view's own address (below), so the browser's Back returns to the walk. A unit that is itself waiting for approval links to `#/approvals/<id>` (the walk), not to the detail view (G30).

**3. The units index: one file (decision C; G25).** Compared with the measured numbers:
- **One file `<state>/units.json`** (measured 317 KB with the clips below; 59,826 bytes with no text). Chosen. One write at most per board refresh, skipped when nothing in it changed, one reader in Go with the same guards. The detail view needs it whole anyway (to know which ids exist, for every link in every text).
- **One file per unit**: 460 files (169 with text). Rejected: the file-event daemon on this machine is already overloaded; one land that touches 6 units would write 6 files and a reader would need a directory walk (more guards: names, links, count). And id links need the whole set of ids before any text is shown.
- **The daemon reads the ticket files itself**: rejected. It would make Go a second reader of the tracker format (front matter, states, rafts' members, the contract's section rules), which the daemon so far never is ("Go reads no ticket file"; step 4a and 5 keep it so), and one reader per format is the architecture rule (zz-arch).
- **Shape (version 1, new file, so no existing file changes version; G32).** `{version:1, at, commit, sig, units:[...]}`. Each unit: `{id, kind:"ticket"|"raft", title, project, state:"backlog"|"active"|"done", tributary, themes:[...], raft, members:[...], depends_on:[...], problem, solution, design:[{heading,text}]}`. `problem`, `solution` and `design` are present only for units not done: `problem` and `solution` clipped at 500 characters each, `design` parts clipped so that the unit's design text is 1,500 characters in total (`approvalfacts.clipAt`, on a character boundary; a cut part ends with the page's own "(cut)" mark, a flag `clipped:true` on the unit says that something was cut). A raft holds `members` (ids), a ticket `raft` ("" none). Every list is `list[T]` in Go (a Luau empty list is written as `{}`: lesson an-empty-list-crosses-from-luau-as-an-empty-object); the page treats a missing list as empty. Never a path, never an account name, never the status stamp (it is a worker's claim token), never `spend` (not needed). `at` is the time the content last changed (see below), `commit` the short commit at that change.
- **Written** by `engine/unitswrite.luau` from `themewrite.refresh` (the board refresh, main checkout only, `ZN_LIVE_DIR` rule as `themewrite`): its own `pcall`, never fails the refresh, atomic through `sh.writeReplacing`, never through a link, a failed write leaves the earlier file and says so in one line. **Skip when unchanged**: the file carries `sig`, the sha256 of its body (everything but `at`, `commit` and `sig`); the writer reads the existing file's `sig` (a regular file, at most 8 MiB) and writes nothing, and does not poke the daemon, when it is equal. So the page's "as of" means "unchanged since", which is the safe direction (never newer than the truth). A write pokes the daemon with reason `units`.
- **Read** by `GET /api/units` (`internal/web/units.go`): `{state: ok|absent|unreadable, why, facts}`; Lstat, `O_NOFOLLOW`, `O_NONBLOCK`, regular file, at most 4 MiB (the file is about 320 KB today; 8 MiB is not needed), version 1 only, known fields only, every list on `list[T]`, a unit with a kind or state outside the known words is dropped and counted in `dropped`, no path in any message. An older daemon does not know the route: the page gets 404 and says "this daemon is older than the page: restart it with ./zn app" (never a blank view; G32).
- **The page** joins what it already has: waiting place from `/api/approvals` (ids and the run), stage and holder from `/api/themes` (`units[].ids`), live claims from `/api/state`. Each source carries its own age and the detail view says each.

**4. The detail view (slice 2, read-only).** Routes (the mockup already parses these, so `index.html` is untouched; `live.js` overrides `renderView` for them over http only): `#/ticket/<id>`, `#/raft/<id>`, `#/tributary/<name>`. A ticket: title, id and type chip, project, state word in plain words (backlog, in code, done), where it stands (waiting for approval: link to its place in the walk; in flight, held by whom; as the other facts say, with their ages), its raft and tributary as links, dependencies as links, its idea and design rendered as markdown (clipped; the page says "first N characters; the full text is in the ticket file" and names no path, only the id), and for a done unit the title and place only. A raft: its tickets as a list of links with their states. A tributary: its units (from the themes facts, as the theme row shows) and its purpose. Unknown id or name: "No unit c0999 in the tracker now" and a link home. Back: native hash history. While stepping in the walk the page keeps `#/approvals/<id>` of the current ticket with `history.replaceState` so that Back from a detail lands on the same ticket (E9).

**5. What changed since the last approval (decision D, slice 3; G33 to G36).**
- **What "before" is.** The text at the ticket's last recorded approval: the row's commit found by `git log -S<row hash>`, the five contract inputs at that commit through `approval.partsOf`, and each part **verified**: a part is the earlier text only if its sha256 equals the row's recorded part hash (E2: 11 of 11). A part whose text cannot be found or whose hash differs is `lost`: shown in full, labelled "earlier text not found". A ticket with no `approval.md` is `first`: shown in full, labelled "first approval". An `approval.md` that does not parse is `bad`, said in words.
- **Where the difference is computed: the engine, at `./zn approve --queue`**, beside the approval facts (not by the page). Reasons: only the engine can read git and check the hash of the earlier text; the earlier text of a design is 50 to 110 KB per part (about 1 MB for 11 tickets, E3) against 1 to 3 KB of difference for 7 of the 11; the page then only displays. Cost: the diff pass on the 13 real waiting tickets took 1.7 s for the text recovery in the probe; the line diff is budgeted at 4,000,000 steps per part, and the whole pass at 30 s (a ticket not done by then is `skipped: time`, said on the page). The queue stays correct without it: any failure leaves the approval facts unchanged and only the diff state of that ticket says why.
- **A new file, not a new version of the approval facts (G32).** `<state>/approval-diffs.json`, version 1, served by `GET /api/approval-diffs`. The approval facts stay version 1 and every reader of them is untouched (an old daemon still shows the walk, and says the diffs need a newer daemon; a new daemon with an old facts file works). Written atomically in the same `--queue` call, before the approval facts, in its own `pcall`, never failing the queue; `{}` is written for no changes.
- **Shape.** `{version:1, run, at, tickets:[{id, hash, state, since, parts:[...] , sections, add, del, truncated}]}`:
  - `run` and `hash` are the approval facts' run id and the queue row's contract hash for the same ticket. The page shows a diff only when both equal the approval facts' (`run`, the ticket's `hash`); otherwise it says "the changes were made for another run: run ./zn approve --queue" and shows the ticket without a diff.
  - `state`: `ok` | `first` | `lost` | `bad` | `skipped`; `why` (plain words, no path).
  - `since`: `{when, who, hash12, commit7}` of the last row (the full approval hash is `hash` in the row; the page shows 12 characters as it does for the contract).
  - `parts`: in contract order, `{name, kind:"prose"|"code", status:"changed"|"same"|"added"|"removed"|"lost", add, del, sections:[...]}`. For `design` (kind prose): `sections:[{heading, level, status:"same"|"changed"|"added"|"removed", size, text?, ops?}]`, headings from the `##` and `###` lines of the five sections outside fences, matched by heading text and occurrence; a `same` section carries `size` and `text` clipped to 1,500 characters (to expand it) and no ops. For a code part (`check.sh`, a spec, `guesses` as one line per guess), `sections` is one entry with `ops`.
  - `ops`: the changed section's lines as `[op, text]`, op `" "`, `"-"` or `"+"`, with runs of unchanged lines longer than 6 shortened to 3 lines of context each side and one `["~", n]` for the n elided; a line clipped at 2,000 characters. Both views come from these: the in-place view groups adjacent `-`, `+` lines into paragraphs and does a word diff in the page (a longest-common-subsequence on words, only when the pair is at most 400 words each, else the whole paragraph is shown removed then added); the unified view prints them with `+`, `−` and the `~` as "... N unchanged lines ...".
  - `add`, `del`: true totals for the ticket from the whole diff, even when `truncated`.
  - Caps (G34): 2,000 op lines per part, 4,000 per ticket, 64 KB of ops text per part; past a cap the rest is dropped, `truncated:true` and the counts stay true, and the page says "showing the first N of M changed lines; the rest: `git diff <commit7> -- <part>`" only as words (never a path: it names the part). Real bytes under the caps are measured in E10 against the 1 MB aim.
- **Display.** Per ticket a badge "changed: design, 2 sections, +14 −6 lines" (parts changed, sections changed in the design, true totals), which on click or key `n` jumps to the first change; `N` to the previous one. The page shows the idea and design as now, but with `ins`/`del` marks in place (G35): added words underlined and tinted, removed words struck and tinted, unchanged sections collapsed to their heading with "unchanged (N lines)" and a button to expand them (the clipped text), a switch "in place | unified" per ticket remembered in the page's memory only (not in storage). Code-like parts (check.sh, specs, and guesses.md) open in the unified form and may be switched to nothing else (they have no in-place form). A guess card whose line is `+` shows "new since your approval", a changed one shows its words struck and added. A ticket `first` says "first approval" and shows in full; a `lost` part says what is missing; the badge then says so ("changed: design (earlier text not found)").
- **Honest about the badge.** The part names in the badge come from the hashes (`contract.changed`), the same words the terminal prints; the diff is computed after and must agree. E11 and a spec assert that the set of parts with ops equals `contract.changed`; the engine marks a ticket `bad` (no diff shown, "the changes could not be matched to the approval") when they disagree, so a disagreement is visible, not hidden.

**6. What the page can never do (decision E).** Nothing in this slice adds a button, a form, a request method other than GET, a new write route or a file the daemon writes. What the page shows is a display. The approval stays bound to the contract hash and is recorded only by the owner's own `./zn approve` in a terminal, as step 4a built it. A wrong or stale diff cannot cause a wrong approval because:
1. a diff is shown only with a `run` and a `hash` equal to the approval facts' for that ticket, and the page shows the run, the first 12 characters of the hash and the age of both files (a stale diff is therefore either not shown or labelled with its age);
2. `--apply`, which the owner runs in a terminal the page does not control, prints the title, the guesses and the hash from the tracker itself and refuses a contract that changed since the queue; the diff is an input to nothing;
3. every ticket keeps the sentence "what you approve is what the terminal shows";
4. the part names in the badge come from the hashes, not from the diff text, so a diff that hides a change cannot also hide that a part changed (it can only fail to show what the change was);
5. residual risk, as in step 4a: a program that can write the state folder can write a false diff beside a true hash. The terminal's `--apply` is what protects the owner. Closed by G44: `./zn approve --apply` prints the same one-line count per ticket, computed by the engine from the tracker independently of the page (slice 3).

## Defect: empty lists (2026-11-23)
- Defect: the Approvals view showed "The approval facts cannot be read. the approval facts have an unexpected shape" on real data.
- Cause: the engine writes the facts with Lune's JSON encoder (`approvalfacts.encode`), which writes an empty list as `{}`. The Go reader (`z-nile/go/internal/web/approvals.go`) decoded every list field as a slice, so 7 of 13 tickets (`"guesses":{}`) failed it; an empty `themes`, `rafts`, `tickets`, `design` or `reviews` would too, so "nothing waits" was broken as well.
- Fix: one generic `list[T]` type in the reader takes `{}` as an empty list, refuses a non-empty object, and writes `[]` to the page. Tests: a table over every list field, a facts file with `"themes":{}`, a cross-check fixture copied from the engine's real output (`TestEngineEmptyListFixture`), and a Luau spec that pins what the encoder writes for an empty list (`approval-facts.spec.luau`). Lesson: `zz-arch/lessons/an-empty-list-crosses-from-luau-as-an-empty-object.md`.
