# f0437: The app on the live daemon

## Problem
- The Approvals, Workers, Stats, Tickets and Rafts views exist only as f0425's mockup with simulated data, and nothing serves any view with the real tracker or the live daemon's real state.
- There is no board view and no settings view in an app at all, real or simulated.
- No view updates when a step forward is recorded, although the live daemon already emits an event for each one (f0424).
- A person can start and watch a worker or a dispatch run only from a terminal of their own, never from an app.

The owner's statement of the intent (2026-11-22), captured at their request ("please capture that, it was great clarity how I just wrote that"): "I am really excited about workers being able to optimistically forge ahead and me just approving or disapproving in the end, automaticaally picking up tickets, maturing idea nd design, rafting them and following the dependencies from the bottom. so that I can just sit with the UI and go through approvals. Moving the multitasking pain to the agents, my time looking linear, working through a theme at a time, a raft at a time, an idea and a design at a time". This is the measure for this ticket: the workers carry the parallel work and never wait on the owner; the owner's time is one linear pass through approvals, a theme, then a raft, then an idea and a design at a time. The same day the owner ranked dead or hung workers low ("manually fixing that is cheap").

## Non-goals
- The app has no view or control for browsing, opening or reading the repository's code files or diffs; code that a run prints in its embedded terminal is not ruled out.
- The command line loses no command and keeps working with the app not running.
- The live daemon's own knowledge of workers, claims and events (f0424) is used as it is, not redesigned.
- The control on every item that starts `zn talk` with that item's context is f0432's deliverable, and this ticket neither builds nor changes it.

## Solution
- One command starts the app, served by the live daemon, and opens it in a browser or window.
- The app shows the real tracker and the real live state in the views approvals, workers, stats, tickets, rafts, the board and settings, with no simulated data left in a delivered view.
- Every view updates by itself when the live daemon records a step forward, without a reload.
- A worker or a dispatch run can be started from the app and watched in an embedded terminal, which shows that run's own output unchanged, including any code the run prints.
- Every item shown in a delivered view has a place where f0432's talk control can sit, and this ticket adds no talk control of its own.
- The app is built view by view from the mockup, each view replacing its simulated data with real data.

### Slim design (step 1: serve the app, Workers live)
- **Opt-in HTTP in the daemon.** `znlive serve --http [--port N] [--page FILE]` (and the new client op `znlive app [--port N] [--page FILE]`) opens an HTTP listener on `127.0.0.1` only (never another interface), on the given port or one the OS picks, and writes `host:port` to `<state>/http` (removed at exit). A daemon that an `emit`/`register` auto-starts passes no `--http`, so it opens no port. `app` auto-starts the daemon (a write op), then asks it over the socket to start serving, and prints `http://127.0.0.1:PORT/`; a second `app` prints the same URL.
- **Package `internal/web`** (pure handler over `*live.Core`; the daemon owns the listener). `GET /` serves the page file read from disk at each request (`z-nile/app/index.html` of the checkout `./zn app` ran in, else the main checkout's; sent to the daemon as the `page` of the `app` op; embedding is a later step). `GET /api/state` returns `{seq, now, workers[], claims[]}` from `Core.Snapshot()`. `GET /api/events` is Server-Sent Events: one `data:` message per event after `Core.Seq()` at connect, woken by `Core.Next` (the same wake-up `wait`/`events --follow` use, no polling), plus a `: ping` comment every 15 s.
- **Same-origin only.** Every request: method GET (else 405); `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (else 403, which also stops DNS rebinding); a present `Origin` must be `http://` plus such a host (else 403); no CORS allow header is ever sent; `Cache-Control: no-store`.
- **Idle exit** counts open HTTP connections like socket connections, so a browser left on the app keeps the daemon up.
- **`./zn app [--open] [znlive-app-flags]`** (wrapper case beside `live`, same build-if-missing and state-folder rules) runs `znlive app` and prints the URL; `--open` also runs `open`/`xdg-open`. `ZN_LIVE_DIR`/`--dir` name the state folder as for `live`.
- **The page** `z-nile/app/index.html` is a copy of the f0425 mockup (kept as the design reference) plus one appended `<script id="live-data">`: over `http:` it fetches `/api/state`, subscribes to `/api/events` (refetch on message; a 15 s refetch keeps "last heard" fresh), and replaces `renderWorkers` with a renderer of the real workers (same cards, state in words, capability chips, elapsed time ticking client-side) and a claims list; no workers: it says so and names `./zn live register --cli <name> --pid <pid>`. A badge in the corner reads "live" on Workers and "simulated" on every other view; from `file://` the badge reads "simulated" everywhere and nothing is fetched.
- **Scalability**: one goroutine per open SSE connection (owner: the HTTP server, ends at disconnect or daemon stop); a state request is one mutex-held copy of the maps. **Maintainability**: later views add one endpoint each in `internal/web` and one renderer override each in the data layer. **Usability**: refusals name the rule (the Host mismatch says which host is accepted).
- **Page rules (review 001 F1, G9).** The daemon, not the client, decides what it serves: absolute clean path; after symlinks a regular file `index.html` (or `live.js` beside it) directly in a folder `z-nile/app`, at most 4 MiB, with one name only (a hard link is refused) and the file opened is the file checked; for the default state folder also inside the main checkout or one of its `.worktree/<name>/`; checked when `app` names a page and again at every read (`O_NOFOLLOW`); a refused swap keeps the current page and the client exits 2 with the rule; a vanished page falls back to the main checkout's; no body or log line sent over HTTP contains a path.
- **Limits (G12)**: 60 s idle timeout, 16 KiB headers, 64 connections, 16 event streams (17th gets 503, the page reopens its stream itself with a growing pause and says why), 10 s write deadline per stream write.
- **Headers (G8)**: CSP, `X-Frame-Options: DENY`, nosniff, no-store; `Sec-Fetch-Site` cross-site or same-site is refused. **View model (G10)**: no host, pid or session in `/api/state` or the events; a public display needs a per-launch token and its own review, and is not designed here.
- **Restart (G11)**: `<state>/http.last` remembers the port; `./zn app` asks for it first. The page names `./zn app` when it cannot reach the daemon.
- **The page**: `z-nile/app/index.html` equals the mockup except its title and one `<script src="live.js">` line (spec `app-copy` fails otherwise); the data layer is `z-nile/app/live.js` with pure renderers (tested by `tests/tooling/app-live.node.js` against a stub page).
- **`check.sh` was written during the build, on the coordinator's instruction, while the design was draft** (it is normally sequestered): the approval walk should raise it.
- **Step 6 note**: the per-launch token must never be stored in the page origin's storage (localStorage, cookies, sessionStorage): another program can take a remembered port and would then read it.
- **Later steps (2 to 6) are listed, not designed.** `design: draft` stays.
- **State file** `<state>/http` is ignored (under `.cache/live`), listed in AGENTS.md with the daemon's state.

### Step 6a design: act from the browser (approve, send back, inspect)
**What is true today, in plain words (for the owner).**
1. An approval is one line in a ticket's `approval.md`: a time, a name and a fingerprint of the design. Any program running as you can write that line and commit it.
2. `./zn approve` refuses when it sees an agent's marker or no terminal, and a hook refuses the obvious commands. These are hurdles an agent stops at in ordinary work, not locks: a script file, a new Terminal window or `tmux send-keys` gets past them.
3. After slice 1, once you enrol, an approval counts only when it carries a signature from a key in your Mac's Secure Enclave. The key asks for your fingerprint every time, and no program can make the signature without it.
4. Landing checks every signature and lists each approval with how it was made and whether it is signed. An unsigned approval stops the landing.
5. Until you enrol nothing changes, except that every approval is labelled "unsigned" wherever it is shown.

The owner's ruling (2026-11-22). The lead explained that any local program, an agent included, can reach the app's port, so a plain Approve button could be pressed by an agent in the owner's name; that a real button needs a secret only the owner's browser holds; and that the click must carry the design's fingerprint so the daemon refuses when what is approved is not what was shown. Asked "Agree?", the owner answered: "yes build the button in the approve flow and that functionality can also be used to launch ai with a prompt to inspect a tiekt, raft or theme". The launch is f0432's (its "Launch from the app"). The rule this keeps: approving is the person's own act, and an agent session never records an approval in the owner's name. Review 001 (`design-review-001.md`, verdict: build after these changes) reshaped this design. Each finding is answered where its tag stands, and listed under "Review 001 answers".

**A. Signed approval rows (slice 1: closes F1 and, for approvals, F8, with or without a browser).**
- **The helper.** `z-nile/signer/se-sign.swift` is source in the repository, built on the owner's machine by `./zn signer build` with `swiftc -O` into `~/.local/share/zn/se-sign`, outside the repository. zn downloads nothing. It needs `swiftc`, which comes with the Xcode Command Line Tools (`xcode-select --install`) or with Xcode. **Neither is on a fresh macOS**: the owner installs one first (this machine has Xcode, `swiftc` 6.4.2). `./zn signer build` names that command when `swiftc` is missing.
- **The key.** CryptoKit's `SecureEnclave.P256.Signing.PrivateKey`, created with `SecAccessControlCreateWithFlags(.privateKeyUsage, .biometryCurrentSet)`. Its `dataRepresentation` is a handle that works only inside this Mac's Secure Enclave, and it is stored in `~/.config/zn/se-key` (0600). No Keychain item is made, so no entitlement and no app bundle are needed (E3, as age-plugin-se works). Every signature asks for Touch ID with the reason "Approve <ticket> <hash12> in <repo>", set on the LAContext passed to the signing call. A yes/no LAContext check alone is never used: it proves nothing.
- **What is signed.** One canonical line, `zn-approval v1<TAB><origin URL><TAB><ticket><TAB><contract hash><TAB><when><TAB><path>`, where `<path>` is `terminal` or `browser session N`. The recorder builds the line, `se-sign sign` reads it on stdin and prints a base64 DER signature. That is one touch per ticket and none at landing.
- **The row.** `approval.md` rows gain a fifth tab field, `sig`: `se:<key id>:<signature>`, `sk:<key id>:<signature>` or `unsigned`. An old four-field row reads as unsigned. `contract.parse` and `render` change. The `who` suffix still names the path, for people, but only the signed `<path>` is trusted.
- **Enrolment.** `./zn signer enrol` is a terminal form. It runs `refuseAgent`, and `boundcmd.formAfter` learns the sub-command `signer` (W3). It makes the key with one touch and appends the public key to `z-nile/.tracker/owner-keys.toml` (`[[key]] id, kind = "se"|"sk", public, added`). That file reaches main by its own pull request. The key is also written to `~/.config/zn/owner-keys.pin`. The first key is trusted on first use, and its fingerprint is printed for the owner to keep. Any later key and any revocation must be signed by a key already on origin/main.
- **The pin, outside the repository.** origin/main's history, with GitHub branch protection refusing force pushes (Q7), plus `~/.config/zn/owner-keys.pin`. `./zn land` refuses when the two disagree and prints the fingerprint of every key it relied on.
- **Verification.** It lives in `approval.reasonOf`, the one reader that `ready`, `done`, `land` and `readycheck` already call. Once origin/main's `owner-keys.toml` holds a key, a row counts only when its signature verifies for the current contract hash, the ticket and the repository, against a key valid at its `when`. Otherwise the refusal reads: "c0001's approval is unsigned (or its signature does not verify): run ./zn approve c0001 yourself (one touch)". `znlive verify` checks `se` signatures (Go `crypto/ecdsa`, no touch) and `ssh-keygen -Y verify` checks `sk` ones. Before enrolment, rows count as they do today and are shown as unsigned. The rule is optional now and required once a key is enrolled. No setting turns it off, because an agent could flip a setting: removing the last key needs a signed revocation.
- **Fallback.** An `ed25519-sk` hardware key: `./zn signer enrol --sk`, `ssh-keygen -Y sign`, one touch. This is also the path on Linux. macOS's own OpenSSH may lack the FIDO middleware (E5). Without either, the bar stays as it is today and rows are labelled unsigned.
- **Undo.** None exists today. `./zn approve <id> --revoke` appends a signed `revoked` row, which counts until the ticket's raft lands. After that it is refused: "landed; send it back instead".
- **Landing lists.** `./zn land` prints every approval in the raft: ticket, when, path, and either "signed by <fingerprint>" or "unsigned".

**B. Only embedded pages can act (slice 2: F2, Q3).** The pages that can act are bytes embedded in the binary: go:embed of `z-nile/app/index.html`, `live.js` and `mockup.js`, built from the main checkout. The mockup's inline script moves to `mockup.js`, and `script-src` becomes `'self'` without `'unsafe-inline'` (styles keep it). `SetPage`, the developer's `--page`, ends every session and turns pairing off until the daemon restarts. While it is set, the act routes answer 403 "a developer page is served: actions are off". Left open: an agent that builds a binary from a changed tree and restarts the daemon serves its own page. Signing (A) still closes that for approvals, not for send back or Inspect.

**C. Pairing starts in the terminal (slice 3: F3, F4, F6, W3, Q1).**
- **The check.** `./zn app --act` runs `approvewalk.refuseAgent(ctx, "app --act", "./zn app --act")`, the check `--apply` runs. `boundcmd.formAfter` learns the sub-command `app`, with `--act` as a terminal form, beside `approve` and `rework`.
- **The flow.**
  1. The invocation makes a one-time secret S (32 bytes) and sends its SHA-256 to the daemon in op `act-begin`, which passes the peer check below.
  2. It opens `http://127.0.0.1:PORT/act#S`, with the port the daemon reports over the socket, not `http.last`.
  3. The page takes S from the fragment, clears it with `history.replaceState` and posts it to `POST /api/act/pair`. The daemon spends S (one use, 2 minutes), returns a `pairId` that is kept in page memory, and the page shows a code.
  4. The owner types that code into the same invocation, which reads it from `/dev/tty` and sends op `act-confirm`. The daemon compares it in constant time with the single pairing that invocation began.
  5. The page's `POST /api/act/pair/wait {pairId}` then returns the token, once. Three wrong codes end the invocation.
- **Why it holds.** No pairing starts without a terminal invocation, so `curl` gets nothing. S sits for a moment in `open`'s argv and in the browser history, but it is spent at the first load. An agent that races for it gets a code the owner never sees, and the owner's page says "this link was already used: run ./zn app --act again". A look-alike page on an old port has no code the invocation knows.
- **Peer check (E1, F4).**
  - The daemon takes the peer's audit token (`LOCAL_PEERTOKEN`; `audit_token_to_pid` plus the pid version, so a reused pid does not pass as the peer).
  - It refuses a peer with no controlling terminal.
  - It walks the ancestors while they run as the owner's uid, and refuses any whose environment (`kern.procargs2`) holds an agent marker or z-nile's own names. The Go copy of the list is in `internal/agentenv`, and a spec fails when it differs from `engine/agentenv.luau`.
  - It stops at the first ancestor owned by another uid, such as Terminal's root-owned `login` or launchd: root is not an agent.
  - A same-uid ancestor whose environment cannot be read is refused, by name.
  - Linux: `SO_PEERCRED`, `/proc/<pid>/environ` and the same stopping rule.
- **The token.** It is held only in a variable in `live.js`'s closure: never a cookie (a 127.0.0.1 cookie reaches every port), never storage, a URL or a file. It is sent as `X-ZN-Session` and stored by the daemon only as a hash, compared in constant time. A session ends at daemon restart, at page reload (Q2), at End or `./zn app --act --end`, after 15 idle minutes (F7, Q5) and after 8 hours at most. At most 4 sessions exist at once.
- **Request checks on `/api/act/*`.** POST only (GET and OPTIONS get 405, so no preflight passes). Host and Origin must match exactly. `Sec-Fetch-Site` must be same-origin when present. The body is `application/json`, at most 8 KiB, decoded into a fixed struct with unknown fields refused. No CORS header is ever sent. Framing is refused. The CSP is never loosened.
- **Blocking the owner (F6).** A request without a session is delayed 1 s, with at most 4 waiting. Wrong tokens lock only that token. Nothing locks out a session or the terminal path, so an agent can cost the owner seconds, not access.

**D. What the confirmation shows (slice 4: W1, F7).** It comes from `approve --summary <run> <ticket> --json`, a new read-only form (an agent may run it), built from the tracker at click time:
- the title and the state (waits, or why not)
- the full contract hash and its first 12 characters
- Problem and Solution
- every guess in full (what was open, what was chosen, why)
- a table of the contract's parts (the ticket file's sections, check.sh, each acceptance spec, the guesses), each with its 12-character hash and whether it changed since the last approval row ("new" when there is none)

The full text of a changed part sits behind "show", from the same answer, capped at 64 KiB and cut on a UTF-8 boundary. The page shows it all escaped, under "This is what you approve". The Touch ID prompt names the ticket and the hash12. The browsing view still shows `approvals.json`, which agents can write. The dialog shows the tracker's own text, bound to the hash that is signed. Ticket text is agent-written either way: the signature binds what is approved, not whether it is true.

**E. Approve and send back from the page (slice 5: W2, F5, F7, Q4, Q6).**
- **Walked runs only.** A paired session gathers its own run with `POST /api/act/gather {scope}`: the daemon runs `./zn approve <scope> --queue` and records the run as that session's. Approve is offered only on tickets of a run the session gathered. An agent-made run is shown but cannot be approved from the page.
- **Preview.** A click carries `{run, ticket, hash}`. `POST /api/act/preview` checks that the run is the session's and the hash equals the facts row, then runs `--summary`. It refuses with 409 on another hash or a ticket that no longer waits, and otherwise returns the summary and a 2-minute `previewId`. "Record" sends `POST /api/act/approve {previewId, run, ticket, hash}`, and all four must match. One ticket per confirmation.
- **Recording.** The daemon writes the ruling with `approve --ruling <run> <ticket> approve`, then runs `approve --apply <run> --only <ticket> --grant-stdin`, each as an argv list (no shell), in the main checkout, with its allowlisted environment. A one-time grant `{run, ticket, hash, session}`, valid 60 s, goes on stdin. W2's changes:
  - `--apply`'s re-exec of the recorder passes `--grant-stdin` and writes the grant to the child's stdin instead of `</dev/tty`.
  - The inner `approve <id>` accepts `--grant-stdin` in place of its terminal check (main.luau ~6236) and still refuses every marker.
  - The scratch-worktree re-exec passes stdin through.
  - The process that writes `approval.md` redeems the grant once, through `znlive redeem` (grant on stdin), just before it writes.
  - When a key is enrolled it signs the row, with Touch ID and the path `browser session N`.
  - Under `--grant-stdin` the engine ignores `ZN_LIVE_DIR` and `ZN_LIVE_SOCKDIR` and asks only the main checkout's default daemon (F5). A fake daemon at that address still answers yes, and only the signature closes that.
- **Send back.** `POST /api/act/sendback {run, ticket, hash, stage, note}`. The stage is one of a fixed set; the note is one line of at most 2,000 printable characters, passed as argv to `approve --ruling ... change`. It needs a session but no grant and no signature, because a ruling records nothing.
- **Audit.** The signed `<path>` is the record. The `who` suffix and an `act` event (approve, ticket, session) mirror it.
- **Limits.** One engine call at a time per daemon: `--summary` gets 20 s, `--apply` 120 s.

**F. Inspect (slice 6)** is f0432's "Launch from the app", on the same session and checks.

**G. Not in this step.**
- An embedded terminal in the page: interactive input streamed into a process over HTTP, so step 6 designs it separately.
- A published board (f0429): public, never actions.
- Remote access: loopback only. Pairing is bound to a terminal on this machine, and the signature to this Mac.

**Residual risks, and whether signing closes them (once enrolled).**
- An agent writes `approval.md`, or runs the recorder from a script, a pty, `tmux send-keys`, `osascript` or a new Terminal window (F1, F8): **closed**. An unsigned or forged row does not count at landing.
- An agent drives the paired browser (Claude in Chrome, screen control) and clicks Approve: **closed for approvals**, since screen control cannot give Touch ID. **Open** for send back and Inspect, reduced only by the 15-minute idle end and the "Actions on" banner.
- Script injected through ticket text, a changed `live.js` or binary (F2), a token read from memory, a phished or raced pairing (F3), a fake daemon (F5): **closed for approvals**. For send back and Inspect, reduced by B and C only.
- The owner touches without reading: **open**. The prompt names the ticket and the hash12, and the dialog the changed parts.
- A tampered `se-sign` that names one ticket and signs another: **reduced, not closed**. It can only turn a touch the owner gives at that moment into a different approval. `./zn signer check` compares the helper's SHA-256 with the one printed at enrolment, but a same-user agent can change both.
- A swapped public key: **reduced**. A change to the key list must be signed by a key on origin/main, and `land` compares the outside pin. **Open** against an agent that rewrites main with the owner's GitHub admin rights.
- Blocking the owner (F6): **open**, bounded to seconds. The terminal path always works.
- Before enrolment, or on a machine with neither Touch ID nor a hardware key: today's bar, labelled unsigned.

**H. Test plan (rule :: test :: the mutant it kills).** Specs run with HOME set to a fixture folder and a software P-256 key standing in for the Secure Enclave. That key is reachable only from the spec runner's fixture, and the real helper's path is fixed.
- Once a key is enrolled, an unsigned or four-field row does not count :: `approve-sign.spec` (`ready`, `done` and `land` each refuse and name the command) :: `reasonOf` skips the signature.
- A signature for another ticket, hash, repository, path or key fails :: `approve-sign.spec` :: one payload field left unchecked.
- A key added or revoked without a signature from an enrolled key is refused, and a pin that disagrees refuses `land` :: `owner-keys.spec` :: trust on every use instead of first use.
- A revoke row counts until landing and is refused after it :: `approve-sign.spec` :: revoke ignored, or accepted after landing.
- `land` lists each approval's path and signature state :: `land.spec` case :: the list dropped.
- The helper compiles :: `signer.spec` (`swiftc -parse`, skipped with a message when `swiftc` is missing) :: a syntax break. Real signing: OC1.
- An agent-marked or tty-less `./zn app --act` or `./zn signer enrol` gets nothing :: `app-act.spec` plus `approve-hook.spec` cases :: the `refuseAgent` call dropped; `formAfter` not taught `app` or `signer`.
- The daemon checks the peer itself :: `peer_test.go` (a raw `act-begin` from a child carrying CLAUDECODE, from a child of a marked same-uid parent, with no terminal, through a root-owned ancestor) :: only the client checks; the walk stops at the parent; a root ancestor refused.
- One marker list :: `agentenv-go.spec` :: a name added on one side only.
- Pairing needs a begun S, used once :: `act_test.go` (a pair without S, S reused, S after 2 minutes, a code from another invocation) :: `pair` open to any client.
- `SetPage` ends sessions, turns pairing off, and the act pages are the embedded bytes :: `act_test.go` :: pages read from disk.
- `script-src` has no `'unsafe-inline'` :: `web_test.go` :: the old CSP.
- Every act route needs a session, and the route table stays the reviewed list :: `TestEveryActRouteRefusesWithoutSession` and `TestRoutesAreTheReviewedSet` (method and auth per path) :: a route with no auth; a GET act route.
- Request checks and F6 :: `act_test.go` (a foreign or missing Origin, a wrong Host, a form body, an unknown field, a 9 KiB body, OPTIONS, 50 bad requests that do not lock out a live session) :: each check removed; a global lock.

- A hash mismatch refuses at all three points :: `act_test.go` (click against facts, summary against click) and `approve-grant.spec` (the contract edited between grant and record: `approval.md` unchanged) :: one comparison skipped.
- A grant is single-use, timed and bound, and passes through the re-execs :: `approve-grant.spec` (reused, 61 s old, another ticket or run, made up, CLAUDECODE set, a recorded approval through the scratch worktree) :: not spent; `</dev/tty` left in the re-exec.
