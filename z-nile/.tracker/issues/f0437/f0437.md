# f0437: The app on the live daemon

## Problem
- The Approvals, Workers, Stats, Tickets and Rafts views exist only as f0425's mockup with simulated data, and nothing serves any view with the real tracker or the live daemon's real state.
- There is no board view and no settings view in an app at all, real or simulated.
- No view updates when a step forward is recorded, although the live daemon already emits an event for each one (f0424).
- A person can start and watch a worker or a dispatch run only from a terminal of their own, never from an app.

The owner's statement of the intent (2026-11-22), captured at their request ("please capture that, it was great clarity how I just wrote that"): "I am really excited about workers being able to optimistically forge ahead and me just approving or disapproving in the end, automaticaally picking up tickets, maturing idea nd design, rafting them and following the dependencies from the bottom. so that I can just sit with the UI and go through approvals. Moving the multitasking pain to the agents, my time looking linear, working through a theme at a time, a raft at a time, an idea and a design at a time". This is the measure for this ticket: the workers carry the parallel work and never wait on the owner; the owner's time is one linear pass through approvals, a theme, then a raft, then an idea and a design at a time. The same day the owner ranked dead or hung workers low ("manually fixing that is cheap").

## Non-goals
- The app has no view or control for browsing, opening or reading the repository's code files or diffs; code that a run prints in its embedded terminal is not ruled out.
- The command line loses no command and keeps working with the app not running.
- The live daemon's own knowledge of workers, claims and events (f0424) is used as it is, not redesigned.
- The control on every item that starts `zn talk` with that item's context is f0432's deliverable, and this ticket neither builds nor changes it.

## Solution
- One command starts the app, served by the live daemon, and opens it in a browser or window.
- The app shows the real tracker and the real live state in the views approvals, workers, stats, tickets, rafts, the board and settings, with no simulated data left in a delivered view.
- Every view updates by itself when the live daemon records a step forward, without a reload.
- A worker or a dispatch run can be started from the app and watched in an embedded terminal, which shows that run's own output unchanged, including any code the run prints.
- Every item shown in a delivered view has a place where f0432's talk control can sit, and this ticket adds no talk control of its own.
- The app is built view by view from the mockup, each view replacing its simulated data with real data.

### Slim design (step 1: serve the app, Workers live)
- **Opt-in HTTP in the daemon.** `znlive serve --http [--port N] [--page FILE]` (and the new client op `znlive app [--port N] [--page FILE]`) opens an HTTP listener on `127.0.0.1` only (never another interface), on the given port or one the OS picks, and writes `host:port` to `<state>/http` (removed at exit). A daemon that an `emit`/`register` auto-starts passes no `--http`, so it opens no port. `app` auto-starts the daemon (a write op), then asks it over the socket to start serving, and prints `http://127.0.0.1:PORT/`; a second `app` prints the same URL.
- **Package `internal/web`** (pure handler over `*live.Core`; the daemon owns the listener). `GET /` serves the page file read from disk at each request (`z-nile/app/index.html` of the checkout `./zn app` ran in, else the main checkout's; sent to the daemon as the `page` of the `app` op; embedding is a later step). `GET /api/state` returns `{seq, now, workers[], claims[]}` from `Core.Snapshot()`. `GET /api/events` is Server-Sent Events: one `data:` message per event after `Core.Seq()` at connect, woken by `Core.Next` (the same wake-up `wait`/`events --follow` use, no polling), plus a `: ping` comment every 15 s.
- **Same-origin only.** Every request: method GET (else 405); `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (else 403, which also stops DNS rebinding); a present `Origin` must be `http://` plus such a host (else 403); no CORS allow header is ever sent; `Cache-Control: no-store`.
- **Idle exit** counts open HTTP connections like socket connections, so a browser left on the app keeps the daemon up.
- **`./zn app [--open] [znlive-app-flags]`** (wrapper case beside `live`, same build-if-missing and state-folder rules) runs `znlive app` and prints the URL; `--open` also runs `open`/`xdg-open`. `ZN_LIVE_DIR`/`--dir` name the state folder as for `live`.
- **The page** `z-nile/app/index.html` is a copy of the f0425 mockup (kept as the design reference) plus one appended `<script id="live-data">`: over `http:` it fetches `/api/state`, subscribes to `/api/events` (refetch on message; a 15 s refetch keeps "last heard" fresh), and replaces `renderWorkers` with a renderer of the real workers (same cards, state in words, capability chips, elapsed time ticking client-side) and a claims list; no workers: it says so and names `./zn live register --cli <name> --pid <pid>`. A badge in the corner reads "live" on Workers and "simulated" on every other view; from `file://` the badge reads "simulated" everywhere and nothing is fetched.
- **Scalability**: one goroutine per open SSE connection (owner: the HTTP server, ends at disconnect or daemon stop); a state request is one mutex-held copy of the maps. **Maintainability**: later views add one endpoint each in `internal/web` and one renderer override each in the data layer. **Usability**: refusals name the rule (the Host mismatch says which host is accepted).
- **Page rules (review 001 F1, G9).** The daemon, not the client, decides what it serves: absolute clean path; after symlinks a regular file `index.html` (or `live.js` beside it) directly in a folder `z-nile/app`, at most 4 MiB, with one name only (a hard link is refused) and the file opened is the file checked; for the default state folder also inside the main checkout or one of its `.worktree/<name>/`; checked when `app` names a page and again at every read (`O_NOFOLLOW`); a refused swap keeps the current page and the client exits 2 with the rule; a vanished page falls back to the main checkout's; no body or log line sent over HTTP contains a path.
- **Limits (G12)**: 60 s idle timeout, 16 KiB headers, 64 connections, 16 event streams (17th gets 503, the page reopens its stream itself with a growing pause and says why), 10 s write deadline per stream write.
- **Headers (G8)**: CSP, `X-Frame-Options: DENY`, nosniff, no-store; `Sec-Fetch-Site` cross-site or same-site is refused. **View model (G10)**: no host, pid or session in `/api/state` or the events; a public display needs a per-launch token and its own review, and is not designed here.
- **Restart (G11)**: `<state>/http.last` remembers the port; `./zn app` asks for it first. The page names `./zn app` when it cannot reach the daemon.
- **The page**: `z-nile/app/index.html` equals the mockup except its title and one `<script src="live.js">` line (spec `app-copy` fails otherwise); the data layer is `z-nile/app/live.js` with pure renderers (tested by `tests/tooling/app-live.node.js` against a stub page).
- **`check.sh` was written during the build, on the coordinator's instruction, while the design was draft** (it is normally sequestered): the approval walk should raise it.
- **Step 6 note**: the per-launch token must never be stored in the page origin's storage (localStorage, cookies, sessionStorage): another program can take a remembered port and would then read it.
- **Later steps (2 to 6) are listed, not designed.** `design: draft` stays.
- **State file** `<state>/http` is ignored (under `.cache/live`), listed in AGENTS.md with the daemon's state.

### Step 6a design: act from the browser (approve, send back, inspect)
The owner's ruling (2026-11-22). The lead explained that any local program, an agent included, can reach the app's port, so a plain Approve button could be pressed by an agent in the owner's name; that a real button needs a secret only the owner's browser holds; and that the click must carry the design's fingerprint so the daemon refuses when what is approved is not what was shown. Asked "Agree?", the owner answered: "yes build the button in the approve flow and that functionality can also be used to launch ai with a prompt to inspect a tiekt, raft or theme". The launch is f0432's (its "Launch from the app"), built on the mechanism below. The rule this must keep: approving is the person's own act, and an agent session never records an approval in the owner's name.

**A. The mechanism: a paired browser session.**
- **Where the authority comes from.** Only a terminal the person types in. Pairing is the one act that makes a browser action-capable, and it needs the same check `--apply` needs today: `./zn app --act` runs `approvewalk.refuseAgent(ctx, "app --act", "./zn app --act")` (ZN_DISPATCH, ZN_APPROVE_SESSION, every `agentenv.MARKERS` name, a terminal on stdin), and `boundcmd`'s `terminalForm` treats `app --act` like `approve --apply`, so the hook refuses it to an agent. The daemon's socket can be reached without the engine, so the daemon checks again, on its own: the `pair` op's peer (`LOCAL_PEERPID` on macOS, `SO_PEERCRED` on Linux) and each of its ancestors up to pid 1 must have no marker or own name in their environment (`sysctl kern.procargs2` / `/proc/<pid>/environ`), and the peer must have a controlling terminal. The Go copy of the marker list lives in `internal/agentenv` and a spec fails when it differs from `engine/agentenv.luau`. A daemon whoever started it (an agent's `emit` auto-starts one) serves the views and refuses every action until such a pairing.
- **The flow (code from browser to terminal).** (1) The page's "Pair this browser" sends `POST /api/act/pair`; the daemon makes a pending pairing: a 32-byte `pairId` returned to the page only and a 10-character Crockford code (`7KQ2M-XH4PD`, 50 bits) shown on the page, 5 minutes, at most 3 pending (a 4th gets 429 naming the wait). (2) The owner runs `./zn app --act` in their own terminal, which prints the daemon's address ("pairing the app at http://127.0.0.1:PORT; check your address bar"), reads the code from `/dev/tty` and sends op `pair` with it. A match (constant-time, against each pending) makes browser session N and drops every other pending; 3 wrong codes in 10 minutes drop them all and lock pairing for 10 minutes. (3) The page's `POST /api/act/pair/wait {pairId}` (held up to 25 s, repeated) returns `{session, token}` once: 32 random bytes the daemon keeps only as a SHA-256 hash.
- **Where the token rests.** Only in a variable inside `live.js`'s closure. Never a cookie (a 127.0.0.1 cookie goes to every port, so an agent's server on another port would receive it), never localStorage or sessionStorage (written to the profile on disk), never a URL (history), argv or a file. The code that travels is not a secret: it pairs only the page that holds its `pairId`, so reading it from the screen or the terminal gives nothing.
- **Lifetime.** A session ends at daemon stop or restart (memory only), page reload, the page's End button or `./zn app --act --end` (anyone may end), 30 idle minutes or 8 hours; at most 4 at once (a 5th ends the oldest). A port taken over after a restart receives only dead tokens.
- **Request checks for every `/api/act/*` route.** POST only (GET and OPTIONS get 405, so no preflight passes); Host exact as today; Origin required and exact; `Sec-Fetch-Site` same-origin when present; `Content-Type: application/json`; body at most 8 KiB, decoded with unknown fields refused into the route's fixed struct; header `X-ZN-Session: <token>` (the two pairing routes need `X-ZN-Act: 1` instead); no CORS header ever; more than 20 refused act requests in a minute make every act route answer 429 for 5 minutes (the terminal still works). A cross-site page cannot send the custom header or JSON without a preflight, which fails; a DNS-rebinding page fails the Host check and holds no token; framing is refused (`frame-ancestors 'none'`, `X-Frame-Options`). The CSP is not loosened: `connect-src 'self'` already covers the POSTs.
- **Residual risks, in plain words.**
  - An agent that drives the owner's browser (a Chrome extension such as Claude in Chrome, or screen control) can click Approve in a paired tab, and the daemon cannot tell. Not reduced, except by the idle end and the banner "Actions on: session N" on every view. The owner must accept it, or deny such tools 127.0.0.1 and localhost and press End before letting an agent drive the browser.
  - An agent-written ticket that breaks the page's escaping runs script in the paired page and can use the token. Reduced by escaping tests; closed only by dropping `'unsafe-inline'` from `script-src` (Q3).
  - A process that reads the browser's memory (debugger rights, root) gets the token. Reduced: it is never on disk, and macOS blocks reading a hardened browser's memory without those rights.
  - A same-user process that deliberately evades (scrubs its environment, detaches to launchd, makes a pty; or stops the daemon and answers on its socket) can pair or forge a grant. Not reduced. It is the same bar `./zn approve` has today, which an agent can already pass by opening a new Terminal window (`open -a Terminal x.command`) that has a terminal and no markers. These guards stop an agent's ordinary acts, not a hostile program.
  - An agent can ask the owner to type its own code, or serve a look-alike page on another port. Reduced: the terminal prints the daemon's address and the warning "type only the code your own browser shows on the Approvals page".
  - A malicious page in the same browser: reduced to a browser bug (Origin, Host, the custom header, no CORS, no framing, and the token is in another origin's memory).

**B. Approve and send back from the page.**
- **Confirm shows the engine's text.** The click on Approve carries `{run, ticket, hash}` exactly as shown. `POST /api/act/preview` checks the run and scope equal the facts file's and the hash equals the facts row's, then runs the engine read form `approve --summary <run> <ticket> --json` (new, records nothing, allowed to an agent). It prints what `--apply` prints before its y/N: title, state, full contract hash, every guess's chosen text, and Problem and Solution, all read from the tracker at click time, never from `approvals.json`. The daemon refuses with 409 when that hash is not the clicked one or the ticket no longer waits. The dialog shows that text, escaped, under "This is what will be recorded", plus a 2-minute `previewId`. That answers the forged-facts problem as far as it can be answered: the browsing view still shows agent-writable facts, but the confirmation shows the tracker's own text, bound to the hash that will be recorded. Ticket text is agent-written either way, and the hash binds what is approved, not whether it is true.
- **Recording through the engine.** `POST /api/act/approve {previewId, run, ticket, hash}` (all four must equal the preview's): the daemon writes the ruling with `approve --ruling <run> <ticket> approve` and then runs `approve --apply <run> --only <ticket> --grant-stdin`, with argv elements (no shell), cwd the main checkout, the daemon's allowlisted environment, and on stdin a one-time 32-byte grant `{run, ticket, hash, session}` that is spent in 60 s. The engine passes stdin through every re-exec of the recorder (the scratch worktree of origin/main included). The process that writes `approval.md` redeems the grant once, through `znlive redeem` with the grant on stdin, just before it writes. It records only when run, ticket and the hash it recomputes all equal the grant's; otherwise it fails and writes nothing. `--grant-stdin` takes the place of the terminal check only: markers are still refused, and the hook lists `--grant-stdin` as a terminal form. An agent that runs the form holds no grant, and the daemon never hands one out except to its own child. The daemon does not reimplement approval: no Go source writes `approval.md`.
- **Audit.** The row's `who` reads `Philip Bergen (browser session 3, paired on ttys003, run <run>)`, the way a walkthrough row reads `(walkthrough <run>)`. The daemon emits an event of kind `act` (approve, ticket, session) that the views show.
- **Send back.** `POST /api/act/sendback {run, ticket, hash, stage, note}`: stage from the fixed set, note one line of at most 2,000 printable characters, run through `approve --ruling <run> <ticket> change --stage <s> --note <note>` as argv. That records only a ruling, which an agent may already write, so it needs the session but no grant. When `./zn rework` exists, applying a change takes the grant path.
- **Undo.** There is none today: an approval row is pushed and stays. It stops holding when its contract changes, so a later send-back and change of the design ends it. The dialog says "cannot be undone here".
- **Limits.** One engine call at a time per daemon (`--summary` 20 s, `--apply` 120 s); the page shows "recording…" and the engine's last line.

**C. Launching an AI CLI on an item** is f0432's "Launch from the app": `POST /api/act/talk`, the same session and checks.

**D. Not in this step.** An embedded terminal in the page: it streams interactive input into a process over HTTP, a larger attack surface than three fixed actions, and step 6 needs its own design for it. A published board (f0429): public, never actions. Remote access: loopback only. Pairing is bound to a terminal on this machine, and remote access would need TLS and real accounts.

**F. Open questions (recorded with `./zn guess f0437` once f0437-approvals merges, whose G13 to G15 take the next numbers; until then Q1 to Q6 here).**
- Q1 Which way the code travels. Example: the page shows `7KQ2M-XH4PD` and the owner types it into `./zn app --act`, or the terminal shows it and the owner types it into the page. Recommended: browser to terminal. A code read from the terminal (a tmux pane an agent can capture) could be redeemed first by whoever reads it; one read from the browser pairs only that browser.
- Q2 Does a session survive a reload? Example: the owner presses Cmd-R and must pair again. Recommended: no. Surviving would put the token on disk; the 8-hour end stays either way.
- Q3 Actions stay off until the mockup's inline script moves to a file and `script-src` drops `'unsafe-inline'`. Example: a ticket title that slips past escaping would otherwise run script that approves. Recommended: yes, slice 1.
- Q4 How the click records. Example: the click spends a grant and the engine records (this design), or the click opens a Terminal window running `./zn approve --apply <run> --only <id>` for the owner to press y. Recommended: the grant. Both bars are the same, and only the grant lets the owner stay in the page.
- Q5 Browser-driving agents. Example: Claude in Chrome, allowed on localhost, clicks Approve. Recommended: accept, with the banner and the idle end, and deny such tools 127.0.0.1 and localhost.
- Q6 One confirmation per ticket, or "approve the raft". Example: R0050 has three waiting tickets. Recommended: one per ticket in this step, since each has its own hash; a raft button is a later step.

## Acceptance criteria
