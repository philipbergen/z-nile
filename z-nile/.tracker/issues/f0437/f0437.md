# f0437: The app on the live daemon

## Problem
- The Approvals, Workers, Stats, Tickets and Rafts views exist only as f0425's mockup with simulated data, and nothing serves any view with the real tracker or the live daemon's real state.
- There is no board view and no settings view in an app at all, real or simulated.
- No view updates when a step forward is recorded, although the live daemon already emits an event for each one (f0424).
- A person can start and watch a worker or a dispatch run only from a terminal of their own, never from an app.

The owner's statement of the intent (2026-11-22), captured at their request ("please capture that, it was great clarity how I just wrote that"): "I am really excited about workers being able to optimistically forge ahead and me just approving or disapproving in the end, automaticaally picking up tickets, maturing idea nd design, rafting them and following the dependencies from the bottom. so that I can just sit with the UI and go through approvals. Moving the multitasking pain to the agents, my time looking linear, working through a theme at a time, a raft at a time, an idea and a design at a time". This is the measure for this ticket: the workers carry the parallel work and never wait on the owner; the owner's time is one linear pass through approvals, a theme, then a raft, then an idea and a design at a time. The same day the owner ranked dead or hung workers low ("manually fixing that is cheap").

## Non-goals
- The app has no view or control for browsing, opening or reading the repository's code files or diffs; code that a run prints in its embedded terminal is not ruled out.
- The command line loses no command and keeps working with the app not running.
- The live daemon's own knowledge of workers, claims and events (f0424) is used as it is, not redesigned.
- The control on every item that starts `zn talk` with that item's context is f0432's deliverable, and this ticket neither builds nor changes it.

## Solution
- One command starts the app, served by the live daemon, and opens it in a browser or window.
- The app shows the real tracker and the real live state in the views approvals, workers, stats, tickets, rafts, the board and settings, with no simulated data left in a delivered view.
- Every view updates by itself when the live daemon records a step forward, without a reload.
- A worker or a dispatch run can be started from the app and watched in an embedded terminal, which shows that run's own output unchanged, including any code the run prints.
- Every item shown in a delivered view has a place where f0432's talk control can sit, and this ticket adds no talk control of its own.
- The app is built view by view from the mockup, each view replacing its simulated data with real data.

### Slim design (step 1: serve the app, Workers live)
- **Opt-in HTTP in the daemon.** `znlive serve --http [--port N] [--page FILE]` (and the new client op `znlive app [--port N] [--page FILE]`) opens an HTTP listener on `127.0.0.1` only (never another interface), on the given port or one the OS picks, and writes `host:port` to `<state>/http` (removed at exit). A daemon that an `emit`/`register` auto-starts passes no `--http`, so it opens no port. `app` auto-starts the daemon (a write op), then asks it over the socket to start serving, and prints `http://127.0.0.1:PORT/`; a second `app` prints the same URL.
- **Package `internal/web`** (pure handler over `*live.Core`; the daemon owns the listener). `GET /` serves the page file read from disk at each request (`z-nile/app/index.html` of the checkout `./zn app` ran in, else the main checkout's; sent to the daemon as the `page` of the `app` op; embedding is a later step). `GET /api/state` returns `{seq, now, workers[], claims[]}` from `Core.Snapshot()`. `GET /api/events` is Server-Sent Events: one `data:` message per event after `Core.Seq()` at connect, woken by `Core.Next` (the same wake-up `wait`/`events --follow` use, no polling), plus a `: ping` comment every 15 s.
- **Same-origin only.** Every request: method GET (else 405); `Host` must be `127.0.0.1:PORT` or `localhost:PORT` (else 403, which also stops DNS rebinding); a present `Origin` must be `http://` plus such a host (else 403); no CORS allow header is ever sent; `Cache-Control: no-store`.
- **Idle exit** counts open HTTP connections like socket connections, so a browser left on the app keeps the daemon up.
- **`./zn app [--open] [znlive-app-flags]`** (wrapper case beside `live`, same build-if-missing and state-folder rules) runs `znlive app` and prints the URL; `--open` also runs `open`/`xdg-open`. `ZN_LIVE_DIR`/`--dir` name the state folder as for `live`.
- **The page** `z-nile/app/index.html` is a copy of the f0425 mockup (kept as the design reference) plus one appended `<script id="live-data">`: over `http:` it fetches `/api/state`, subscribes to `/api/events` (refetch on message; a 15 s refetch keeps "last heard" fresh), and replaces `renderWorkers` with a renderer of the real workers (same cards, state in words, capability chips, elapsed time ticking client-side) and a claims list; no workers: it says so and names `./zn live register --cli <name> --pid <pid>`. A badge in the corner reads "live" on Workers and "simulated" on every other view; from `file://` the badge reads "simulated" everywhere and nothing is fetched.
- **Scalability**: one goroutine per open SSE connection (owner: the HTTP server, ends at disconnect or daemon stop); a state request is one mutex-held copy of the maps. **Maintainability**: later views add one endpoint each in `internal/web` and one renderer override each in the data layer. **Usability**: refusals name the rule (the Host mismatch says which host is accepted).
- **Page rules (review 001 F1, G9).** The daemon, not the client, decides what it serves: absolute clean path; after symlinks a regular file `index.html` (or `live.js` beside it) directly in a folder `z-nile/app`, at most 4 MiB, with one name only (a hard link is refused) and the file opened is the file checked; for the default state folder also inside the main checkout or one of its `.worktree/<name>/`; checked when `app` names a page and again at every read (`O_NOFOLLOW`); a refused swap keeps the current page and the client exits 2 with the rule; a vanished page falls back to the main checkout's; no body or log line sent over HTTP contains a path.
- **Limits (G12)**: 60 s idle timeout, 16 KiB headers, 64 connections, 16 event streams (17th gets 503, the page reopens its stream itself with a growing pause and says why), 10 s write deadline per stream write.
- **Headers (G8)**: CSP, `X-Frame-Options: DENY`, nosniff, no-store; `Sec-Fetch-Site` cross-site or same-site is refused. **View model (G10)**: no host, pid or session in `/api/state` or the events; a public display needs a per-launch token and its own review, and is not designed here.
- **Restart (G11)**: `<state>/http.last` remembers the port; `./zn app` asks for it first. The page names `./zn app` when it cannot reach the daemon.
- **The page**: `z-nile/app/index.html` equals the mockup except its title and one `<script src="live.js">` line (spec `app-copy` fails otherwise); the data layer is `z-nile/app/live.js` with pure renderers (tested by `tests/tooling/app-live.node.js` against a stub page).
- **`check.sh` was written during the build, on the coordinator's instruction, while the design was draft** (it is normally sequestered): the approval walk should raise it.
- **Step 6 note**: the per-launch token must never be stored in the page origin's storage (localStorage, cookies, sessionStorage): another program can take a remembered port and would then read it.
- **Later steps (2 to 6) are listed, not designed.** `design: draft` stays.
- **State file** `<state>/http` is ignored (under `.cache/live`), listed in AGENTS.md with the daemon's state.

### Step 6a design: act from the browser (approve, send back, inspect)
**What is true today, in plain words (for the owner).**
1. An approval is one line in a ticket's `approval.md`: a time, a name and a fingerprint of the design. Any program running as you can write that line and commit it.
2. `./zn approve` refuses when it sees an agent's marker or no terminal, and a hook refuses the obvious commands. These are hurdles an agent stops at in ordinary work, not locks: a script file, a new Terminal window or `tmux send-keys` gets past them.
3. After slice 1 you can enrol a passkey: Touch ID on a Mac, a USB security key on any computer, or your phone. From then on each approval carries a signature that needs your touch, made in the app's own page, and no program can make it without you.
4. Landing checks every signature and lists each approval with how it was made and whether it is signed. Once you turn on "signed only", an unsigned approval stops the landing.
5. Until you enrol, nothing changes except that every approval is labelled "unsigned" wherever it is shown.

The owner's ruling (2026-11-22). The lead explained that any local program, an agent included, can reach the app's port, so a plain Approve button could be pressed by an agent in the owner's name; that a real button needs a secret only the owner's browser holds; and that the click must carry the design's fingerprint so the daemon refuses when what is approved is not what was shown. Asked "Agree?", the owner answered: "yes build the button in the approve flow and that functionality can also be used to launch ai with a prompt to inspect a tiekt, raft or theme". The launch is f0432's (its "Launch from the app"). The rule this keeps: approving is the person's own act, and an agent session never records an approval in the owner's name. Review 001 (`design-review-001.md`, verdict: build after these changes) reshaped this design. Each finding is answered where its tag stands and listed under "Review 001 answers".

The owner's ruling on signed approvals (2026-11-22). Asked whether a Touch ID touch per approved ticket was acceptable, the owner answered: "q1 doesnt really travel to other os." The first real host for zn is Omarchy Linux. So the signature is a WebAuthn passkey, which works the same on macOS and Linux, and the Secure Enclave helper is not built (A, "Rejected").

**A. Passkey-signed approval rows (slice 1: closes F1, and F8 for approvals).**
- **What signs.** A WebAuthn credential (a passkey), used only from a small page built into the binary, `sign.html` with `sign.js` (go:embed, `script-src 'self'`, no ticket text rendered, only escaped fields). The page calls `navigator.credentials.get()`, and the browser hands the request to the owner's authenticator: Touch ID on a Mac, a USB or NFC FIDO2 key on any OS, or a phone through the hybrid QR flow (needs Bluetooth on the computer). The daemon and the repository keep only public keys.
- **Origin and RP ID.** The page is served at `http://localhost:<port>`. Browsers treat `http://localhost` and `http://127.0.0.1` as secure contexts, but an RP ID must be a domain, never an IP address. So the app uses the fixed name `localhost`, the RP ID is `localhost`, and `./zn app` prints and opens the `localhost` URL (the Host check already accepts it). The RP ID ignores the port, so a credential outlives a port change. `clientDataJSON.origin` carries the port, and the verifier checks it equals `http://localhost:<pinned port>`. The pinned port is set at enrolment and is the port `./zn app` asks for first (G11). When that port is busy, signing is off and the app says why. Unverified until E3: that Chrome, Firefox and Safari on macOS all accept `localhost` as RP ID over plain http. Safari is the least certain.
- **What is signed.** The challenge is the SHA-256 of one canonical line: `zn-approval v1<TAB><origin URL of the repo><TAB><ticket><TAB><contract hash><TAB><run><TAB><when><TAB><path><TAB><nonce>`. `<path>` is `terminal` or `browser session N`, and `<nonce>` is 16 random bytes from the daemon. The verifier recomputes the line from the row and checks:
  - `clientDataJSON.type` is `webauthn.get`, its `challenge` equals the line's hash, its `origin` is the pinned one, and `crossOrigin` is false
  - `authenticatorData`'s rpIdHash is `SHA-256("localhost")`
  - both the UP (user present) and UV (user verified) flags are set
  - the signature verifies over `authenticatorData || SHA-256(clientDataJSON)` with a pinned credential's public key (ES256 or EdDSA)
- **User verification is required (Q8).** Touch ID gives UV with a fingerprint, a phone gives UV with its unlock, and a FIDO2 key gives UV with its PIN or its own fingerprint. A FIDO2 key with no PIN is asked to set one at enrolment. An old U2F-only key gives presence only and is refused. Presence alone already stops an agent, which cannot touch. UV also stops someone at the desk, and it is what the authenticators above give anyway.
- **The row.** `approval.md` rows gain a fifth tab field, `sig`: `wa:<credential id>:<nonce>:<b64url authenticatorData>.<b64url clientDataJSON>.<b64url signature>`, or `sk:` (fallback, below), or `unsigned`. An old four-field row reads as unsigned. `contract.parse` and `render` change. The `who` suffix names the path, for people. The signed `<path>` is the record.
- **The verifier.** One Go verifier, `znlive verify` (a subcommand that needs no daemon), in the binary zn already builds from repository source with Go. It uses the standard library only (`crypto/ecdsa`, `crypto/ed25519`, plus a small CBOR reader for COSE keys), and the same code runs on macOS and Linux. The engine calls it from `approval.reasonOf`, the one reader `ready`, `done`, `land` and `readycheck` use. When the binary is absent zn builds it. When it cannot (no Go), a signed row reads "unverified (znlive missing)": it counts as unsigned, and under "signed only" it refuses. Never fail open.
- **Enrolment, never by an agent alone.** `./zn signer enrol` is a terminal form: `refuseAgent`, plus `boundcmd.formAfter` learning the sub-command `signer` (W3).
  1. Like pairing (C), it registers a one-time secret with the daemon (peer check) and opens `http://localhost:<port>/enrol#S`.
  2. The page calls `navigator.credentials.create()` (RP ID `localhost`, `userVerification: "required"`, `residentKey: "discouraged"`, attestation `none`) and the owner touches.
  3. The page shows a code, and the owner types it into the same invocation.
  4. The invocation prints the credential's fingerprint and the authenticator's flags. BE/BS say whether the passkey syncs to a cloud account; that is allowed and labelled "synced", because its strength is the account's (Q11).
  5. It appends the key to `z-nile/.tracker/owner-keys.toml` (`[[credential]] id, public (COSE), alg, origin, added, synced`), which reaches main by its own pull request, and to `~/.config/zn/owner-keys.pin`.
  The first credential is trusted on first use. Every later change to `owner-keys.toml` (a new credential, a revocation, the "signed only" policy, a new pinned port) is a row carrying an assertion from a credential already on origin/main, so after the first enrolment an agent cannot add its own key, even a software or virtual authenticator, without the owner's touch.
- **Several authenticators, loss and recovery.** Any pinned credential signs. Enrol two: the laptop's sensor and a backup key or phone. A lost authenticator is revoked by a row signed with another one. When every authenticator is lost, `./zn signer reset` (a terminal form) starts a new first credential. `land` and the app then say "the key list was reset on <date>: trusted on first use again" until the owner removes the notice with a signed row. A reset is the weak moment, and the backup authenticator exists to avoid it.
- **The pin, outside the repository.** On one user account nothing is out of an agent's reach, so the pin is made visible rather than unreachable. The key list's history is on origin/main, where GitHub branch protection refuses force pushes and deletion (Q7, an owner setting). A copy sits in `~/.config/zn/owner-keys.pin`, and `land` refuses when the two disagree. A swap needs both copies changed and main's history rewritten.
- **"Signed only" (Q10).** It is a policy row in `owner-keys.toml`, signed like any other change, so turning it off also needs a touch. Before it is on, an unsigned row counts as it does today and is labelled unsigned everywhere. After it is on, `land`, `ready` and `done` refuse an unsigned row: "c0001's approval is unsigned: approve it again in the app or with ./zn approve c0001 (one touch)". A machine with no authenticator records unsigned rows. They land while "signed only" is off and are refused once it is on.
- **The terminal flow reaches the same bar (Q9).** By default, `./zn approve c0001` (still `refuseAgent`) registers a one-time sign request with the daemon and opens `http://localhost:<port>/sign#S`. The page shows the ticket, its title, the hash12 and the run, then asks for the touch. The assertion comes back over the socket to the waiting invocation, which verifies it and writes the row. This is the default because it needs one credential type, one verifier, and nothing more on a Mac (Touch ID) or on Linux (a USB key or a phone). The fallback, for a machine with no browser, is `ssh-keygen -Y sign` with an `ed25519-sk` key enrolled by `./zn signer enrol --sk`, verified by `ssh-keygen -Y verify`. That needs OpenSSH built with FIDO support. Linux distributions ship it; macOS's own `/usr/bin/ssh-keygen` may not (E5).
- **What the authenticator shows.** Only "localhost" and the account name: never the ticket, the hash or the text. So the link between what the owner read and what is signed rests on the embedded page (B) and on the confirmation content (D) shown just before the touch. The signature proves that the owner touched for this ticket and hash. It does not prove what the owner read.
- **Linux laptops without extra hardware.** Unverified, E6. Chrome and Firefox on Linux generally do not offer the laptop's fingerprint reader (fprintd) as a WebAuthn platform authenticator. What works is a phone through hybrid, which needs Bluetooth on the laptop and is not verified for Firefox on Linux, or a USB key. Chrome's Google Password Manager passkeys (a PIN, no hardware) may exist on Linux. They are synced, weaker, and labelled "synced". Not designed on.
- **Undo.** None exists today. `./zn approve <id> --revoke` appends a revoked row, signed the same way, which counts until the ticket's raft lands. After that it is refused: "landed; send it back instead".
- **Landing lists** every approval in the raft: ticket, when, path, and either "signed by <credential> (device-bound or synced)" or "unsigned".
- **Rejected: a Secure Enclave helper in Swift.** It is macOS only, needs Xcode tools that a fresh Mac lacks, and the owner's first host is Linux ("q1 doesnt really travel to other os.").

**B. Only embedded pages can act (slice 2: F2, Q3).** The pages that can act are bytes embedded in the binary: go:embed of `z-nile/app/index.html`, `live.js` and `mockup.js`, beside slice 1's `sign.html`, `enrol.html` and `sign.js`, built from the main checkout. The mockup's inline script moves to `mockup.js`, and `script-src` becomes `'self'` without `'unsafe-inline'` (styles keep it). `SetPage`, the developer's `--page`, ends every session and turns pairing and signing off until the daemon restarts. While it is set, the act routes answer 403 "a developer page is served: actions are off". Left open: an agent that builds a binary from a changed tree and restarts the daemon serves its own page. It still needs the owner's touch for every approval (A), but it can show one ticket and ask a touch for another (see Residual risks).

**C. Pairing starts in the terminal (slice 3: F3, F4, F6, W3, Q1).**
- **The check.** `./zn app --act` runs `approvewalk.refuseAgent(ctx, "app --act", "./zn app --act")`, the check `--apply` runs. `boundcmd.formAfter` learns the sub-command `app`, with `--act` as a terminal form, beside `approve` and `rework`.
- **The flow.**
  1. The invocation makes a one-time secret S (32 bytes) and sends its SHA-256 to the daemon in op `act-begin`, which passes the peer check below.
  2. It opens `http://localhost:PORT/act#S`, with the port the daemon reports over the socket.
  3. The page takes S from the fragment, clears it with `history.replaceState` and posts it to `POST /api/act/pair`. The daemon spends S (one use, 2 minutes), returns a `pairId` that is kept in page memory, and the page shows a code.
  4. The owner types that code into the same invocation (`/dev/tty`, op `act-confirm`). The daemon compares it in constant time with the single pairing that invocation began.
  5. The page's `POST /api/act/pair/wait {pairId}` returns the session token, once. Three wrong codes end the invocation.
- **Why it holds.** `curl` cannot start a pairing. S sits for a moment in argv and in the browser history, but it is spent at the first load, and an agent that races for it gets a code the owner never sees. A look-alike page has no code the invocation knows. The session only gates send back, Inspect and the approval preview: an approval also needs the touch (A).
- **Peer check (E1, F4).**
  - The daemon takes the peer's audit token (`LOCAL_PEERTOKEN`, then `audit_token_to_pid` with the pid version).
  - It refuses a peer with no controlling terminal.
  - It walks the ancestors while they run as the owner's uid, and refuses any whose environment (`kern.procargs2`) holds an agent marker or z-nile's own names. The Go copy of the list is in `internal/agentenv`, and a spec compares it with `engine/agentenv.luau`.
  - It stops at the first ancestor owned by another uid: root is not an agent.
  - A same-uid ancestor whose environment cannot be read is refused, by name.
  - Linux: `SO_PEERCRED`, `/proc/<pid>/environ` and the same stopping rule.
- **The token.** It is held only in `live.js`'s closure: never a cookie, storage, a URL or a file. It is sent as `X-ZN-Session` and stored by the daemon only as a hash, compared in constant time. A session ends at daemon restart, at reload (Q2), at End or `./zn app --act --end`, after 15 idle minutes (F7, Q5) and after 8 hours at most. At most 4 sessions exist at once.
- **Request checks on `/api/act/*`.** POST only (GET and OPTIONS get 405). Host and Origin must match exactly. `Sec-Fetch-Site` must be same-origin when present. The body is JSON, at most 8 KiB (64 KiB for an assertion), decoded into a fixed struct with unknown fields refused. No CORS header and no framing. The CSP is never loosened.
- **Blocking the owner (F6).** A request without a session is delayed 1 s, with at most 4 waiting. Wrong tokens lock only that token. An agent can cost the owner seconds, not access.

**D. What the confirmation shows (slice 4: W1, F7).** It comes from `approve --summary <run> <ticket> --json`, a new read-only form, built from the tracker at click time:
- the title and the state (waits, or why not)
- the full contract hash and its first 12 characters
- Problem and Solution
- every guess in full (what was open, what was chosen, why)
- a table of the contract's parts (the ticket file's sections, check.sh, each acceptance spec, the guesses), each with its 12-character hash and whether it changed since the last approval row ("new" when there is none)

The full text of a changed part sits behind "show", capped at 64 KiB and cut on a UTF-8 boundary. The page shows it all escaped, under "This is what you approve", directly above the button that asks for the touch. Since the authenticator shows no ticket, this content and B are the whole link between reading and signing. Ticket text is agent-written either way: the signature binds what is approved, not whether it is true.

**E. Approve and send back from the page: the click is the signature (slice 5: W2, F5, F7, Q4, Q6).**
- **Walked runs only.** A paired session gathers its own run with `POST /api/act/gather {scope}` (the daemon runs `./zn approve <scope> --queue` and records the run as that session's). Approve is offered only on tickets of a run the session gathered.
- **Preview.** A click carries `{run, ticket, hash}`. `POST /api/act/preview` checks that the run is the session's and the hash equals the facts row, then runs `--summary`. It refuses with 409 on another hash or a ticket that no longer waits. Otherwise it returns the summary, the canonical line (path `browser session N`, a fresh nonce) and a 2-minute `previewId`. Approval from the page needs an enrolled credential: before enrolment the page offers only the copyable terminal command.
- **Sign.** "Approve with your passkey" calls `navigator.credentials.get({challenge: SHA-256(line), rpId: "localhost", allowCredentials: <pinned ids>, userVerification: "required"})`. The owner touches, and the page posts `POST /api/act/approve {previewId, assertion}`. The daemon checks the assertion against the preview's line with `znlive verify` before going on, which turns a bad touch away early.
- **Record.** The daemon writes the ruling (`approve --ruling <run> <ticket> approve`), then runs `approve --apply <run> --only <ticket> --assertion-stdin` as argv, in the main checkout, with its allowlisted environment, the line and the assertion on stdin. The grant and its redeem of the earlier design are gone, because the assertion is the authority. W2's changes:
  - `--apply`'s re-exec of the recorder passes `--assertion-stdin` and writes stdin through instead of `</dev/tty`.
  - The inner `approve <id>` accepts `--assertion-stdin` in place of its terminal check (main.luau ~6236) and still refuses markers.
  - The scratch-worktree re-exec passes stdin through.
  - The process that writes `approval.md` verifies the assertion against the current contract hash and the pinned credentials, and writes it into the row.
  An agent that runs the form has no assertion. F5's fake daemon is now harmless: nothing the daemon says is trusted, so the environment that picks a daemon does not matter.
- **Send back.** `POST /api/act/sendback {run, ticket, hash, stage, note}`. The stage is one of a fixed set, the note one line of at most 2,000 printable characters, passed as argv to `approve --ruling ... change`. It needs a session and no touch, because a ruling records nothing.
- **Audit.** The signed `<path>` is the record. The `who` suffix and an `act` event mirror it.
- **Limits.** One engine call at a time per daemon: `--summary` gets 20 s, `--apply` 120 s.

**F. Inspect (slice 6)** is f0432's "Launch from the app", on the same session and checks.

**G. Not in this step.**
- An embedded terminal in the page: step 6 designs it separately.
- A published board (f0429): never actions.
- Remote access: loopback only. The RP ID is `localhost`, so a signature can only be made on the machine itself.

**Residual risks under this design.**
- An agent writes `approval.md`, or runs the recorder from a script, a pty, `tmux send-keys`, `osascript` or a new Terminal window (F1, F8): **closed** once "signed only" is on. Before that, its rows show as unsigned.
- An agent drives the browser (Claude in Chrome, screen control): it **can click but cannot touch**, so approvals are closed. Send back and Inspect stay open to it, reduced by the 15-minute idle end and the "Actions on" banner.
- An agent phishes a touch for a different ticket than the one the owner read: a page of its own on `localhost` at another port, a page in a rebuilt binary, or a look-alike shown while the owner expects a prompt. **Reduced, not closed.** The verifier refuses any origin other than the pinned port. The embedded page shows the ticket it signs, and a touch is expected only right after the owner's own click. But the authenticator cannot show the ticket, so a page served on the pinned port while the daemon is down, or by a rebuilt daemon, can still obtain a touch for another ticket. `land` lists every signed approval, and a revoke row undoes one before landing.
- Replay of an assertion: **closed**. The challenge commits to the ticket, contract hash, run, time, path and a nonce. Replayed onto another ticket or hash it fails. Replayed onto the same one it adds nothing, and the verifier refuses a nonce seen twice in one `approval.md`.
- A swapped public key: **reduced**. Every change after the first enrolment needs an existing credential's touch, and `land` compares the outside pin. **Open** at first enrolment and after a reset (trust on first use, loudly labelled), and against an agent that rewrites main with the owner's GitHub admin rights.
- A synced passkey is as strong as its cloud account: **labelled**, the owner's choice (Q11).
- The owner touches without reading: **open**.
- Blocking the owner (F6): **open**, bounded to seconds.
