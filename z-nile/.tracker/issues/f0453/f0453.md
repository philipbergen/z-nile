# f0453: Rework counts shipped defects

## Problem
`./zn metrics` reports Rework = defect / (defect + feature) on all done defects, so a problem found and fixed inside a feature that was still open counts as rework. Today 13 done defects against 48 features give 21.3% by issues, over the 20% target, although ten of the thirteen are tooling defects and several fixed work that was not finished. No unfinished ticket covers this (searched every `.tracker/issues` outside `done/` for "rework": f0446 only describes the figure, d0149 and the others mention it in passing).

Decided with the user (2026-11-24): "I want defects to count only when they ship, we've treated this session as one big body of work and it hasn't really shipped any defects imo"

Asked what "shipped" means, the owner chose "Fixes finished work". Decided with the user (2026-11-24): "Fixes finished work": a defect counts only if the ticket or raft it fixes was already marked done when the defect was found. Problems found and fixed inside a feature that is still open never count.

Ruling on the seven defects with no recorded fix (d0297, d0298, d0333, d0383, d0406, d0410, d0415). Decided with the user (2026-11-24): "those defects seem like something was done wrong, or not yet implemented more than the functionality was actually broken, they don't count"

What should happen: the three rework measures (lines, issues, agent time) are shipped defects / (shipped defects + features); the old all-defects figure stays visible on one line; the defects left out because the work they fix was still open, the defects the owner ruled did not ship, and the defects with neither recorded are each listed.

## Non-goals
- The board's per-period "Defect %" and "Defect time %" (`board.luau`, `chart.luau`, `stats.row` ratios): they are a share of what closed in a period, not the rework figure, and have no `Item.fixes`. Kept as they are (listed in Verification log).
- Recording `fixes:` on open or not-yet-captured defects other than through `./zn new issue d --fixes`.
- Guessing what an old defect fixes: where its Problem does not state it plainly it stays unrecorded and is listed for the owner.
- Chores stay out of the figure, as before.

## Solution
A defect names what it fixes in a frontmatter key `fixes: [<id>, ...]` (issues or rafts). `./zn metrics` counts a defect as shipped when any id it fixes was already done on or before the day the defect was captured (`created:`). A new pure module `z-nile/engine/rework.luau` decides it; `cmd.metrics` reads the facts and prints.

## Design
### What defect tickets carry today
The 13 done defects carry `type`, `raft`, `depends_on`, `emergent`, `created` and prose; no key names the ticket a defect fixes. `depends_on` means "must be done first" (a fix often depends on nothing, and d0412 depends on c0202, the thing it fixes, but d0298 depends on three unrelated tickets), `raft:` names the raft that fixes it, harvest lines are not on the defect. So a new key is needed.

### Key
`fixes: [f0033, R0044]` (ids of issues or rafts, read with `store.readFront` and `store.idList`). `./zn new issue d <slug> --fixes <id>[,<id>...]` writes it (for a defect only; the stub otherwise has no `fixes:` line); an emergent defect (`--raft R`) with no `--fixes` gets `fixes: [R]`, so work found inside open work does not count. z-idea step 3 asks for it. The capture rule (`CAPTURE_KEYS`) lets a capture edit it. `./zn audit` reports an error for a `fixes:` id that names no item (`unknown-fixes`) and for a defect that fixes itself or, not being emergent, its own raft (`self-fixes`); a defect with no `fixes:` is not an audit finding (the old defects would fill every audit with warnings): `./zn metrics` reports it.

### Dates
- Capture date: `created:` (recorded in the file; a defect with none counts as shipped), the local day of the capturing machine.
- Done date of the fixed ticket: no document records it, so `history.read` gives it as `doneDay` (review 001 F2, F3): the local day (the commit's own offset, `%cI`) of the first arrival in `done/` on the first-parent line of `origin/main` (HEAD without it), so it is the day the item reached main, merges and their bound `done/` moves included, and a branch commit days earlier does not count. It keeps the compaction cut of `doneAt`: an id a compaction gave to another item has no day. `history.read` is the one reader; the first fallback (`reworkgit.luau`) was deleted. `closed` and `doneAt` are unchanged, so the board, chart and stats answer as before.
- A fixed ticket that is done now but has no known day (renumbered by a compaction; 76 of 291 done items today) counts, and is listed on its own line: the stricter reading.
- Compared as days: done day <= captured day counts as done first (same day counts: the stricter reading). A defect fixing several ids counts when ANY was done first. A fixed id that is not done was open.
- No readable history (`history.read` nil, as in a shallow clone): every defect that names a fix counts, and the report says so.

### The owner's ruling: `shipped: no`
A defect can carry the owner's ruling that it did not ship in frontmatter `shipped: no`. It is a key of its own, not a value of `fixes:`, because the two answer different questions: `fixes:` is a fact about the work (what the defect repairs, so the date rule can be applied), while `shipped: no` is a judgement only the owner makes ("something was done wrong, or not yet implemented", not broken functionality) that overrides the date rule whatever `fixes:` says, and a defect with a ruling may fix nothing recordable at all.
