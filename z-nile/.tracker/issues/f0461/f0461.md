# f0461: Check design linter

## Problem
- At `2ed28e442`, nothing in the engine checks a normal or risky ticket for these four design mistakes, so only design review rounds catch them. (a) An `ACn` under `### Checked` has no `check "ACn: ..."` line in the ticket's `check.sh`, or such a line has no `ACn` bullet. (b) A `## Test plan` entry `spec :: case` names the ticket's own spec (a bare file name, or a path that starts with `acceptance/`), and that file is missing from the ticket's `acceptance/` folder or has no case with that name. (c) A Regression guard's `Overrides:` line is missing, appears more than once, still holds the template text `<promoted specs`, or names a backticked `tests/acceptance/` path that does not exist at the base. The line also fails when it is not `none` and names no chore id (`c<nnnn>`) outside its backticked paths; only a chore ticket may write `this chore` instead. (d) An `E<n>` entry in `## Unknowns & experiments` has no state, or its state is `run` but it has no backticked command that passes. A command passes when it starts with `./zn run --time <s> --`, is another `./zn` command, ends in `check.sh`, or is `lune run <target>` for a target the bound-command hook lets run bare.
- An entry's state comes from the text inside its first parenthesis, split at commas and colons into trimmed parts. A part that is exactly `not run`, `read`, `reasoned` or `Phase 1`, or that ends in ` Phase 1`, gives that state. A part that is exactly `run` or starts with `run ` gives `run`. With no such part the entry has no state, and with parts that give two different states it has two states. Both fail (d). So `(not run)` is `not run`, `(run in prep: PASS)`, `(pass, run)` and `(mutation check, run)` are `run`, `(executor, Phase 1)` is `Phase 1`, and `(to run in Phase 1)` is `Phase 1` and owes no command.
- For an easy ticket, `./zn ready` already refuses a Regression guard that is not a plain `Overrides: none` (`light.overridesNone`, `z-nile/engine/light.luau:164`, refusal at `:330`). No command checks a normal or risky ticket's `Overrides:` line.
- The lesson `z-design/experiments-record-their-bounded-command` asks a question that (d) answers mechanically once every entry states whether it ran. c0278's E3, the record the lesson came from, opens `(pass, run)`, so (d) fails it if its `./zn run --time 60 -- bash /tmp/c0278-e3.sh` command is removed.

## Non-goals
- `z-design/spec-design-correspondence` does not graduate and its file stays, because its questions are about meaning and check (a) answers none of them. This narrows the rough idea, which graduated both lessons, and needs the user's ruling.
- Check (b) does not judge a Test plan entry that names a spec outside the ticket's own `acceptance/` folder, for example c0252's `tests/tooling/dispatch-texts.spec.luau` or c0137's `tests/acceptance/c0115/absence.spec.luau`.
- Check (d) does not decide which of an entry's other backticked spans are commands, so an entry that holds one passing command passes even if it also quotes a bare one.
- The check does not decide whether a well-formed `Overrides: none` is true for a design that turns a promoted spec red; that stays zz-review item 4's judgement.
- Two commands write `prepared` without going through `./zn status ... prepared`, and neither runs the check. One is `./zn stop` (`stopIssue`, `z-nile/engine/main.luau:7193`, and `cmd.stop`, `:7230`). The other is `./zn release <R-id>` (`cmd.release`, `:2558`), which stamps items whose design is ready back to `prepared` at `:2623`. A ticket can therefore reach `prepared` unchecked when a rafting claim is released, and tickets already prepared, rafted, active or done when this lands are not checked again.
- Pre-code `Rules and mutants` requirements, which c0460 moved to `zz-execute`, do not come back.
- Static linting of `check.sh` paths and sequestration is not built here; it belongs to `c0463`.

## Solution
- `./zn check-design <id>` runs a pure module `z-nile/engine/checkdesign.luau`. Its inputs are the ticket's text, its `check.sh`, the file list and spec text of its `acceptance/` folder, the list of base paths under `tests/acceptance/`, and the registry's project homes. It prints one line for each problem of kinds (a) to (d) and exits 1 when there is any; with none it prints nothing and exits 0. Given a raft id, it checks each member issue and starts every line with that member's id.
- `checkdesign.luau` reads the `Overrides:` line only through `light.luau`. `light.luau` gains one exported function that returns the line's backticked paths and the rest of its text (or `none`, or why the line cannot be read). `light.overridesNone` is rewritten on top of that function, and its existing specs stay green.
- `checkdesign.luau` decides which `lune run` targets pass (d) only through a new export, `boundcmd.isTooling(target: string, homes: { string }): boolean`. It returns `TOOLING[t] == true or` the `homeRunner` test (`<home>/tests/run` for a registered home, `z-nile/engine/boundcmd.luau:213`). `toolingMatch`'s relative-target branch (`:254`) is rewritten to call it. So `lune run arcade/tests/run`, and the same for portal, snake, invaders and asteroids, passes (d) exactly where the hook lets it run bare.
- The `## Unknowns & experiments` comment in `z-nile/templates/issue/doc.md` gives the state rule from the Problem, names the state words (`run`, `not run`, `read`, `reasoned`, `Phase 1`) and says each entry opens with exactly one of them. It also says a `run` entry records its bounded or exempt command, and that a Test plan spec given as a bare file name means the ticket's own `acceptance/` folder.
- Step 3 of z-design's `SKILL.md` gains one sentence: run `./zn check-design <id>` before each design review round starts, and fix every line it prints before the reviewer starts.
- `./zn status <id> prepared` refuses, printing the check's problem lines, while there are any. `./zn status <R-id> prepared` checks every member the move stamps (`z-nile/engine/main.luau:1746`–`1751`), next to `designOpen` at `:1830`, and refuses with the failing member's id. A ticket that is being designed when this lands is checked the next time `./zn status` marks it prepared.
- For a `risk: easy` ticket with a short note, the check runs only (a) and (c). It skips (b) because an easy ticket has no `acceptance/` folder, and (d) because an easy ticket has no experiments.
- `z-design/experiments-record-their-bounded-command` graduates. Its file is deleted, and `z-nile/skills/graduated.tsv` gains a row `graduated: ./zn check-design (d)` that lists every item whose `harvest.md` cites it, so `./zn lessons --check` stays green under c0455.
