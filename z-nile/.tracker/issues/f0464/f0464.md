# f0464: Retire raft PR stage

## Problem
- `./zn ready` refuses a prepared `normal` or `risky` ticket until z-raft has put it in a raft, which takes its own rafting worktree, a raft document (Theme, Order) and a rafting pull request.
- A ticket rafted alone still needs that rafting pull request but gets no coherence review, because z-raft §4 runs one only on a raft of two or more issues, so the step adds a merge cycle that checks nothing beyond the ticket's own design review.
- When `./zn raft-plan` builds a multi-issue raft by default (by folding defects and chores, or by grouping features that share a surface), it adds a rafting pull request and a coherence review round, and it puts the members on one branch, so one member's failing gate or review holds back every other member; the user ruled on 2026-11-27 that this costs more than delivering one ticket per pull request in `depends_on` order.
- A prepared ticket with no raft cannot be readied on a finished but unlanded dependency, because `main.luau` refuses `--on` on the light path ("the light path (ready <issue>) takes no --on and is not for ./zn dispatch"), so the ticket waits for that dependency's landing approval.

## Non-goals
- Stacking under `./zn dispatch`: its `z-ready` step keeps running `ready {id}` with no `--on` (`dispatch.luau:29`), and a dispatched raftless ticket keeps waiting until its `depends_on` have landed.
- Deleting `<root>/rafts/active/R####/` folders, or changing how `trace.md`, `./zn done`, the board and promoted specs use them.
- Re-rafting, unfolding or re-reviewing any multi-issue raft already active or prepared in `.tracker/`.
- Removing the rafting pull request or the coherence review from a multi-issue raft a human asks for.
- Extending `light: true` (and the code review it skips) beyond the `easy` tickets `light.luau` accepts.
- Changing how `work.baseFor` picks a base, or how a stacked branch is retargeted and landed once its base lands.

## Solution
- `./zn ready <issue-id>` readies any prepared `easy`, `normal` or `risky` ticket that has no raft and whose `depends_on` have all landed, by creating its `single: true` raft in the same claim commit; `lightready.luau`, `publish.luau`, `work.luau` and `dispatch.luau` take that path, and `light: true` stays limited to tickets that `light.luau` accepts.
- The light-path refusal in `main.luau` ("takes no --on and is not for ./zn dispatch") is removed, so an issue with no raft can be readied under `./zn dispatch` without `--on`, while the earlier refusal "--on is not for ./zn dispatch" stays as it is.
- Run outside `./zn dispatch`, `./zn ready <issue-id> --on <R-id>` readies a prepared ticket with no raft whose unlanded `depends_on` are all delivered by the finished raft `<R-id>`; its new `single: true` raft records that `--on` and branches from the base `work.baseFor` picks, as for any raft (f0399), so a raftless chain like `f0465` and `c0466` is built on its unlanded dependency.
- `./zn work next` names the action `./zn ready <issue-id> --on <R-id>` for a raftless ticket whose dependency is finished but unlanded, the same way it names `./zn ready <R-id> --on <base>` today for a raft with a finished, unlanded dependency (`work.luau:1366` and `:1900`), and the worker runs it from the main checkout.
- `./zn raft-plan` no longer folds or groups by default, and neither `./zn work` nor `./zn dispatch` starts a rafting step for a prepared ticket, so by default each ticket is delivered on its own branch and pull request in `depends_on` order.
- A raft of two or more issues is made only when a human names its members (`z-raft <ids>`, `./zn fold`, `./zn recombine`), and it still needs its rafting pull request and coherence review before `./zn ready` accepts it.
- Rafts already active or prepared in `.tracker/` are delivered as they are, under the rules that held when they were rafted.

## Design
Decisions this relies on: the user's ruling of 2026-11-27 quoted in the Problem (one ticket per pull request in `depends_on` order costs less than default bundling); the owner's "workers forge ahead, owner approves" (approval is still asked: by `./zn done` outside the dispatcher, by `ready` under it, as f0399 has it). `depends_on: [c0458, c0468]`: c0458 (prepared) rewrites the same `work.luau` branch (`issuePick`'s prepared case, its item 8), removes readycheck's "easy with no design review" refusal and the per-layer code review; this design is written against the code c0458 leaves and changes nothing c0458 changes. c0468 narrows the promoted specs this changes (Regression guard). The design rests on three existing engines that already do most of it: `ready <issue>`'s claim commit (f0420 step 3), `readycheck.reason` (with its `light`, `requireApproval` and `onMembers` inputs) and `work.baseFor` (f0399).

### D1. The one decision: `lightready.check` (`z-nile/engine/lightready.luau`)
`lightready.check(id: string, paths: { string }, read: (string) -> string?, opts: Opts?): Check` stays the one decision whether `./zn ready <issue>` takes a ticket in no raft, and both `ready` and the walk call it (as f0420 made it). It changes from "is it light" to "does ready ready it alone, and is the raft light":
- `export type Opts = { onMembers: { string }?, dispatched: boolean? }`: `onMembers` are the members of the raft `--on` names, taken as done (f0399's rule, as `readycheck` reads it); `dispatched` is ready under `./zn dispatch`.
- `export type Check = { why: string?, light: boolean?, lightWhy: string?, reviewed: boolean?, groupedBy: string? }`: `why` is ready's refusal (nil: it readies the ticket alone); `light` is `light.reason(...) == nil`; `lightWhy` is light.luau's reason when not light.
- The checks before it stay as they are (on origin/main, prepared in the backlog, an empty `raft:` line, not listed by a raft that is not done), and one is added: a `risk:` that `rounds.level` refuses is refused (`{id}: risk is <x>: easy, normal or risky`), because light.luau no longer stands in front of readycheck for it.
- The light rule is still judged with the real dependency states (`depsMet` is "every `depends_on` is done"), so a ticket readied `--on` an unlanded raft is never light; `light: true` stays limited to what `light.luau` accepts.
- The refusal is no longer the light rule: it is `readyfacts.singleFrom(member, "R0000", <raft check.sh template>, { light = light, requireApproval = dispatched, onMembers = onMembers })`, which is `readycheck.reason` on the single raft ready is about to make, exactly as `lightFrom` is today but with the three inputs passed instead of fixed. So the readiness rules of a raft (design ready, a check line, the latest design review settled, a `Level:` line that parses, the contract builds, the guesses parse, an approval that has not gone stale, under the dispatcher an approval that holds, every `depends_on` done or in `onMembers`) hold for a single raft too, and none is duplicated.
- `lightready.claimMessage(raftId: string, issueId: string, how: { dispatched: boolean, on: string?, light: boolean }): string` (new, pure) is the claim commit's message: `tracker: ready <R> <id>`, then the trailers `Lands: approved` (not under the dispatcher, as `ready <R-id>` writes it), `On: <R>` (for `--on`) and `Light: true` (only for a light raft), one per line after a blank line, nothing after the subject when there is none. `layergit.readyRecord` and `workread.holdersOf` already read these trailers from any `tracker: ready <R> ...` commit, so `start`, `done` and the walk treat the raft as any readied raft (an `On:` raft's first layer is cut from `<R>/base`, f0399).
- The header comment says what it decides now.

### D2. `./zn ready <issue-id>` (`z-nile/engine/main.luau`, `cmd.ready`)
- The light-path refusal `"the light path (ready <issue>) takes no --on and is not for ./zn dispatch"` is removed; the earlier `"--on is not for ./zn dispatch"` stays where it is, before any read (Non-goals: no stacking under the dispatcher).
- For an issue whose `raft:` is empty: when `--on <R>` is given, `onMembers = f0399.readyOnMembers(issue, { issue }, onId)` (the existing check that `<R>` is active, every layer finished, and the ticket depends on something in it and on nothing else unlanded; its refusals stay as written, the raft id slot naming the ticket); then `lightready.check(... { onMembers, dispatched })` on origin/main. A refusal fails with `ready: <id> has no raft, and ready does not ready it alone: <why>` and publishes nothing (it names the rule and the item, zz-arch rule 8; "z-raft makes one (./zn raft-plan)" is gone).
- The publish is today's light claim (one tracker-only commit: the raft folder created in `active/`, the ticket moved beside it with the claim stamp and `raft: <R>`, `check.sh` paths rewritten, the counter raise), judged again inside the publish on its own snapshot with the same `Opts`, with three differences: the raft document gets `light: true` only when `check.light`; its Theme is the light text (unchanged) for a light raft and otherwise `"<id> is one ticket in no raft, so ready made this single raft for it in its claim commit (f0464). There is no rafting step: it is built and reviewed as any raft, on its own branch and pull request."`; the message is `lightready.claimMessage(chosen, id, { dispatched, on = onId, light })`.
- Everything after the publish (pull, prompt, `readied <R>`) is unchanged, and `ready <R>` on the raft it made regenerates the prompt as for any active raft.
- `--on`'s usage line is unchanged (`ready <R-id|issue-id> [--on <R-id>]`).

### D3. The publish guard (`z-nile/engine/publish.luau`, `lightClaim`)
The one exception that lets a moved ticket fill an empty `raft:` (rules 1 to 5 in its comment) stays, with rule 2 widened: the raft added in the same publish is `single: true`, lists exactly `[<id>]`, carries the same claim stamp and its `check.sh`, and its `light:` key is either absent or `true` (anything else, `light: false` or an empty value, is refused: `<R> says light: <v>: a single raft ready makes says light: true or nothing`). Whether a raft that says `light: true` really is light is still judged after the build by `lightgit` (an unlit raft that claims light gets the code review the walk asks for, f0420), so the guard does not have to run the light rule. The option keeps its name `lightClaim` (it is the light path's claim generalised; the comment says so), to keep the change to this protected file to the rule line, its message and its comment. This is a change to a guard, which is why the ticket is `risky` (G1).

### D4. What `./zn work next` answers (`z-nile/engine/work.luau`, `z-nile/engine/workread.luau`)
- `IssueFact` gains `readyWhy: string?`: why `ready <issue>` refuses the ticket with its `depends_on` taken as done (nil: it would ready it). `workread` sets it for every prepared, designed ticket in no raft, whatever its level (today only an easy one is judged), by `lightready.check(id, paths, read, { onMembers = <its depends_on> })` on the one origin/main snapshot it already builds once per call; `light` and `lightWhy` come from the same verdict (`lightWhy` is `verdict.lightWhy or verdict.why`). Taking the dependencies as done mirrors a raft's `blockOn` (f0399): whether the ticket waits for them or is built on the raft that delivers them is the walk's to say.
- `issuePick`'s prepared case (as c0458 leaves it, `if i.light == true then "ready" elseif i.sized then "rafting" else "fix"`) becomes: `readyWhy == nil` → `ready`; a `readyWhy` that says `changed since approval` → not picked, reason `ready refuses it: <readyWhy>` (the person approves again, as for a raft, `work.fixable`); any other `readyWhy` → `fix`, whose words become `ready refuses <id>: <readyWhy>. Repair it in guess mode (z-design), merge the pull request when it is green, then ask again.` The issue-level `rafting` action and the `fix` for a missing `size:` are gone (size only fed z-raft's cap). The `groupedBy` case (a raft that is not done lists it) is unchanged: it waits.
- With unmet dependencies, tier 1 still passes the ticket over; tier 2 picks `ready` only when `work.baseForDeps(i.deps, input.rafts, issues)` names a base, and otherwise gives its reason (it waits). `work.baseForDeps(deps: { string }, rafts: { RaftFact }, issues: { IssueFact }): (string?, string?)` is `work.baseFor`'s body moved out unchanged, and `work.baseFor(r, rafts, issues)` becomes `return work.baseForDeps(r.outside or {}, rafts, issues)`, so how a base is picked does not change (Non-goals). `issuePick` and `issueDecision` take the rafts as a new last parameter, which every caller passes (`input.rafts`).
- `issueDecision`'s `ready` words: with a base, `<id> is prepared, in no raft, and depends on <unmet>, delivered by <base>, whose layers are finished. From the main checkout run ./zn ready <id> --on <base>: it makes the single raft for it in its claim commit, built on <base>. Then ask again.`, the same shape as a raft's `./zn ready <R-id> --on <base>` line (`work.luau:1366`, `:1900`); for a light ticket the light text as today; otherwise `<id> is prepared and in no raft: it is delivered alone, on its own branch and pull request, with no rafting step. From the main checkout run ./zn ready <id>: it makes the single raft for it in its claim commit. Then ask again.` The worker runs the line from the main checkout as it runs any ready line (z-work).
- `decide`'s two issue loops ask for `{ "ready", "fix", "resume", "draft" }` instead of `{ "rafting", "fix", "resume", "draft" }`, in the same places, so a ticket to ready is picked where one to raft was; `lowestIssue` matches the action asked and `pickAction` returns it (the light special case folds into the plain match). `ACTIVITY_OF.ready` is already `code`.
- The raft-level `rafting` action (a raft a person named, being grouped, `work-walk-cli`'s `R0120: rafting`) is unchanged.

### D5. The dispatcher's chain (`z-nile/engine/dispatch.luau`, `dispatch.next`)
For a prepared, `design: ready` issue with no raft: an open PR on its `raft-<id>` branch is still the `raft` gate, and a raft the dispatcher wrote in its rafting worktree (`localRaft`) still goes to z-raft, so a chain mid-rafting from before f0464 finishes as it began (Solution: rafts already in flight are delivered as they are). Otherwise the next step is `{ kind = "step", step = "z-ready", target = <id> }`, the existing script step (`./zn ready {id}`, main checkout, no `--on`, `dispatch.luau:29` unchanged). A `z-ready` that ended ok while the issue still has no raft on origin/main stops with exit 1 (`z-ready ended but <id> has no raft on origin/main`), beside the raft's existing check; once readied, the issue's `raft:` is set and the chain follows the raft (existing). A ticket ready refuses (an unlanded dependency, no approval) is a failed step, and the chain stops for `./zn dispatch retry` as it does for a raft today: a dispatched raftless ticket waits for its dependencies (Non-goals). The `raft-plan` and `z-raft` step definitions stay (a person may run them). `dispatcher.luau` needs no change: its `scriptStep` already runs `z-ready` on any id in the main checkout.

### D6. `./zn raft-plan` (`z-nile/engine/main.luau`, `cmd["raft-plan"]`)
With no argument it plans no raft: it prints, for every prepared, `design: ready` issue in the backlog with an empty `raft:` line, in id order, `skip <id>: no default raft (f0464): ./zn ready <id> readies it alone; a raft of several is made only from members a person names (z-raft <ids>)`, and `raft-plan: nothing to raft (no prepared issue without a raft)` when there is none; `--apply` runs nothing (it is still refused in the main checkout). The usage line stays `raft-plan [--apply]`. A raft of two or more issues is made only by `./zn new raft … <ids>`, `./zn fold` and `./zn recombine` (z-raft with arguments), and `ready` still refuses one whose coherence review does not cover its grouping record (`readycheck.record`, unchanged; AC5 pins it).

### Scalability
`ready <issue>` makes the same reads as today's light path (one `git fetch`, one `ls-tree` of origin/main and a `git show` per file read, twice: before the pull and inside the publish), plus, with `--on`, `f0399.readyOnMembers`' layer reads of one raft (as `ready <R> --on` does). `./zn work next` already builds one origin/main snapshot per call; it now judges every prepared raftless ticket on it, not only the easy ones: a few `git show` reads per such ticket (its document, `check.sh`, design reviews, approval, guesses; cached per path), linear in the prepared raftless tickets (20 today across the projects). `raft-plan` reads less (no plan). The dispatcher's chain loses two steps per ticket (`raft-plan`, z-raft: a model session) and one merge gate (the rafting PR), which is the point (Problem).
### Maintainability
One decision (`lightready.check`) still answers "does ready take this ticket alone" for `ready`, the walk and (through them) the dispatcher, and one rule (`light.luau`) still answers "is it light"; readiness is `readycheck.reason` for a single raft as for any raft, so a new readiness rule added there reaches raftless tickets with no extra code. The commit message has one builder whose output the existing trailer readers parse. `work.baseForDeps` is the one base pick for a raft and a ticket. The next kind of unit that is readied alone plugs into `lightready.check`'s `Opts`.
### Usability
`./zn ready <issue>` refusals start `ready: <id> has no raft, and ready does not ready it alone:` and name readycheck's rule (the dependency and its state, the missing check line, the open review, the approval to run). `./zn work next` names the exact command (`./zn ready <id>` or `./zn ready <id> --on <R>`), never a rafting step. `raft-plan`'s skip line names `./zn ready <id>`. No new command, flag or file kind joins an exhaustive list (`ready`, `raft-plan` and `work` are already in the main checkout's list and the read-only set as before).
