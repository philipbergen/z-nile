### F1 [high] The lock change assumes the top process outlives the jail, but the launcher does: a SIGKILLed or TERMed top lets a second run take the lock while the first run's specs still write `.cache` (and promoted `c0058/lock.spec` turns red, not named on Overrides)
Where: c0075 Design, "The run's lock under a pid namespace" ("the top process's own `pid` file is the lock's owner and outlives everything in the jail (the namespace dies with it)"); `tests/lib/fence.luau` `fence.enter` (top `process.exec("perl", launched, …)`) and `REAPER`; `tests/acceptance/c0058/lock.spec.luau` case "a run whose top process was killed keeps the lock while its specs still run".
Evidence: the jail is a child of the launcher (`perl -e REAPER`), and the launcher is a child of the top Lune process. `--die-with-parent` ties bwrap to the launcher, not to the top. Nothing in REAPER watches the top. So `kill -TERM <top>` (exactly what lock.spec does) kills only the top, while the launcher and the whole jail keep running. Today the guarded processes' `pid-N` files keep the lock held. Under the design, every guarded process inside bwrap sees a `pidns` that differs from its own and records nothing. The lock then holds only the dead top's `pid` (and `pidns`, which `lockPids` ignores), so `takeOverIfStale` judges it stale. On Linux CI the inner fixture run is bwrap-jailed (nested, E2), so in lock.spec `meanwhile` takes the lock, runs and passes, and `t.expect(meanwhile.ok).toBe(false)` fails. In real use, two suites then share one checkout's `.cache` fixtures. That is the 2026-09-30 incident this lock exists to prevent. The Overrides line names only `c0058/fence.spec.luau`. AC3 tests only the pure `recordsPid`, so a correct `recordsPid` passes AC3 while the lock is broken.
Critique: the tempting fix is to narrow lock.spec's case on Linux ("orphaned specs are killed with the namespace"). That is false, and it would weaken a guard. The other tempting fix is to drop `pidns` and record jail-namespace pids again, which brings back the false-alive `kill -0 7` problem the design correctly found.
Consequences: whatever process is recorded must be in the host namespace, alive exactly as long as anything in the jail can be, and writable into the lock from outside the jail. The launcher fits all three: bwrap dies with it (`--die-with-parent`, E2 2b), and it runs outside the jail. Its record must survive a top that died, and must go stale once the launcher exits, so the existing "every recorded pid dead, then take over" rule still frees the lock. On macOS the record is harmless: the launcher also outlives the sandbox there.
Recommendation: the launcher records its own pid in the lock. The top passes it the lock path in its own env (e.g. `PICKMAN_REAP_LOCK`, unset for the specs as `PICKMAN_REAP_*` already are), and REAPER writes `<lock>/pid-$$` before it forks. Keep `pidns` and `recordsPid` for the guarded processes. Add to c0075 a Checked case that fails without it: run `fence.REAPER` (as c0079 does) with `PICKMAN_REAP_LOCK` pointing at a fixture lock, and expect `pid-<launcher pid>` while the command runs. Add a Rules row: the mutant "launcher records nothing" fails that case and lock.spec on Linux. With this fix lock.spec needs no override. Say so in Regression guard, and correct the sentence quoted above.

### F2 [high] Promoted `c0078/jail-signals.spec` (and `tests/tooling/sweeper-interlock.spec`) turn red under bwrap: inside a pid namespace, pid 1 is the user's own process, so `fence.alive("1")` is true unjailed too
Where: `tests/acceptance/c0078/jail-signals.spec.luau` "alive counts a refused probe as alive only when jailed…" (`process.env.PICKMAN_TEST_JAIL = "none (unjailed)"; local outside = fence.alive("1")` … `t.expect(outside).toBe(false)`); `tests/tooling/sweeper-interlock.spec.luau` "inside an outer sandbox, a refused liveness probe reads as alive" (`t.expect(none).toBe(false)`); c0075 Overrides; Design "`fence.alive` is unchanged".
Evidence: both specs assume "pid 1 belongs to root: kill -0 is refused it everywhere". With `--unshare-pid`, pid 1 is bubblewrap's own init, running as the invoking user (mapped uid, same kuid). So `kill -0 1` succeeds, `fence.alive` returns true at its first `if r.ok`, and `outside`/`none` come back true. c0078 is promoted and not on Overrides. The design's own text says the `sandbox-exec` gates "stay" and the cases "take their unjailed branches", but this case has no gate.
Critique: an unnamed override of a promoted spec. E4 would find it on CI, and the executor would then edit a promoted spec ad hoc.
Consequences: inside bwrap no process of another user is visible at all, so the "refused, but unconfined, therefore dead" branch can't be reached with a real pid on Linux. Any narrowing needs a different way to make `kill -0` refuse.
Recommendation: name `tests/acceptance/c0078/jail-signals.spec.luau` on Overrides (this is a chore, so no `depends_on`), and specify the narrowed case. `fence.alive` runs `kill` from `PATH`, so a stub `kill` that prints `Operation not permitted` and exits 1, first on `PATH` for that assertion, exercises both branches on every platform, which keeps the case's intent. Do the same in sweeper-interlock. Add both to the Regression guard list.

### F3 [high] `c0058/fence.spec` has two more cases that turn red under nested bwrap, and the Overrides text says only one changes
Where: c0075 Overrides paragraph ("The one case it changes: `a run inside a sandbox says it is not jailed again…`"); `tests/acceptance/c0058/fence.spec.luau` "the guards reach everything the run starts and keep the outer ceiling" and "a run that changed remote or user config fails, even though every case passed".

The inner fixture run is also `bwrap` (nested), so `pickman_fence` sets none either and resets `GIT_CONFIG_KEY_0` to `gc.auto`. ### F4 [high] The bubblewrap jail leaves host Unix-domain sockets connectable, so a spec can hand a write of the real checkout to a daemon (Docker on the GitHub runner, `systemd-run --user`/D-Bus on a developer box)
Where: c0075 Design `fence.jailArgv` (`--ro-bind / /`, nothing hides `/run`); Prep history ("The jail denies the *write*, so how a command names a repository no longer matters"); E1 (no socket probe); testing skill "Handing work to a process outside the jail" (the gate scan flags only `osascript` and `launchctl`).
Evidence: `connect(2)` on a Unix socket needs search access to the path and write permission on the socket inode. A read-only bind mount (`MNT_READONLY`) is checked through `mnt_want_write`, which `connect` never calls, and the `EROFS` permission check covers only regular files, directories and links. So `/run/docker.sock` (`/var/run` links to `/run` on Ubuntu) and `$XDG_RUNTIME_DIR/bus` stay reachable from inside the jail. The user namespace keeps the caller's supplementary group kgids, so the GitHub runner's `docker` group still applies. `--unshare-net` closes abstract sockets only. So a spec that asks the Docker daemon (on CI) or the user's service manager (on a developer box) to run a command gets that command run outside the jail, with the user's normal write access to the checkout. The macOS profile is equally open here (`(allow default)` denies only `network-outbound (remote ip)`), so this is not a regression. But c0075 exists to replace review-only protection with a jail, and this path stays review-only without being listed.
Critique: the tempting fix is a line under "Caught only by review". That is better than nothing, but it leaves the cheapest real escape on CI open, and `docker` appears nowhere in the scan.
Consequences: hiding `/run` needs an empty, read-only tmpfs (`--tmpfs /run --remount-ro /run`). AC1's pinned list ("opens nothing else": no `--tmpfs`) must then change now, because it is sequestered. `$XDG_RUNTIME_DIR` dangles inside (tools tolerate a missing one). DNS is irrelevant with no network. Sockets under `/tmp` (`/tmp/.X11-unix`, `ssh-*` agent sockets) and `~/.docker/run` remain. Either hide `/tmp` the same way, with the run's temp folder bound after it (a later mount covers an earlier one), or list them explicitly. macOS keeps the hole unless the profile also denies `network-outbound (remote unix-socket)` except what specs need, which is a separate issue.
Recommendation: decide in prep, and record the user's decision if it is a trade-off:
1. Add `--tmpfs /run --remount-ro /run` (and decide about `/tmp`) to `jailArgv`, and update `jail-argv.spec` and AC1.
2. Add a `live-jail.spec` probe: connecting to each of `/run/docker.sock` and `$XDG_RUNTIME_DIR/bus` that exists fails. It is harmless: connect, then close.
3. Add an experiment to E1's harness on `ubuntu-latest` proving `docker version` fails inside.
4. Add `docker`, `systemd-run`, `busctl` and `dbus-send` to the testing skill's "Handing work to a process outside the jail", and to the gate scan if no spec needs them.
5. Capture a follow-up issue for the macOS profile.

### F6 [medium] Under nested bwrap, `tests/tooling/fence-leftovers.spec` reads pids from the inner namespace and SIGKILLs those numbers in the outer one, killing unrelated processes of the outer run
Where: `tests/tooling/fence-leftovers.spec.luau` (`bg.pid` and `detached.pid` written by the inner run's spec; `alive(pid)` and `kill -KILL pid` in the outer spec). c0075 E4 lists it only as a "candidate to read first". Also `tests/tooling/repo-fence.spec.luau` "on macOS this run can write nothing…", whose non-macOS branch asserts `PICKMAN_TEST_JAIL` starts with `none`.
Evidence: the copied runner in `.cache/fence-leftovers` now runs in its own nested bwrap, so `echo $!` there writes something like `9`. In the outer jail's namespace pid 9 is some other live process (a worker Lune or its shell). `survived` comes back true, which fails the case, and the cleanup loop then `kill -KILL`s that process, which can fail an unrelated spec file in the same run. On CI that shows up as a flaky, misattributed failure. For repo-fence, the design says the macOS case "keeps its macOS body", but its Linux early-return asserts `none` and fails under `bwrap`.
Critique: E4 would find the red case, but not that its cleanup kills a sibling. The executor may "fix" the symptom elsewhere.
Consequences: a pid is meaningful only together with its namespace. Every spec that hands pids across a nested run needs the namespace too.

- **repo-fence.** Specify that the macOS case's early return becomes a plain `return` when not on macOS, with the Linux sibling doing the checks.
- **Shared sentence.** Put one line for both into "Tests the executor edits".

### F7 [medium] Dropping `--new-session` rests on two unproven claims, and leaves the specs in the launcher's process group, which reaches outside the jail
Where: c0075 Design "No `--new-session`", E5 (reasoned), Rules row "stays in the launcher's process group", raft Risks (TIOCSTI); testing skill "Signals".
Evidence:
1. **The TIOCSTI premise.** "the kernel disables it by default since 6.2": the 6.2 change added `CONFIG_LEGACY_TIOCSTI`, whose upstream default is `y` (legacy behaviour kept). Only distributions that turn it off are safe. Nothing in prep measured `dev.tty.legacy_tiocsti` on a target host. bwrap's `--dev` provides `/dev/tty`, and the specs keep the controlling terminal. So on a host where the sysctl is 1, the residue is input injected into the user's unjailed shell, which is a path to the real repository.
2. **The incompatibility claim.** "It `setsid()`s bwrap out of the process group the launcher signals": as I read bwrap, `--new-session` calls `setsid()` in the sandboxed child, not in the outer bwrap process. If that holds, the outer bwrap stays in the launcher's group, a forwarded INT/TERM/HUP ends it, and `--die-with-parent` then takes the jail down. E1 used `--new-session`, but not in the launcher shape. E2 tested the launcher shape only without it, and its "2c" watchdog step is empty. So the claim is unproven either way.
3. **The group reaches outside the jail.** Without a new session, the specs share a process group with REAPER's watchdog and the outer bwrap process, both outside the pid namespace. Signals sent to the caller's own group are not filtered by pid namespace, so a spec's group-wide signal (a common cleanup idiom) reaches the watchdog and bwrap itself. A STOP to bwrap hangs the run, and a TERM ends the whole run. On macOS the profile refuses signals to the watchdog. E1's signal probe tested only signalling an outside pid by number. The testing skill's "Signals" bullet ("never the runner's top process, its launcher or the watchdog") would be false on Linux, and the Rules table has no signal row.
Critique: the residue was accepted as a user-visible risk on a premise that doesn't hold, and the parity claim for signals is untested.
Consequences: adding `--new-session` changes AC1 and `jail-argv.spec` ("stays in the launcher's process group"), which must happen now, because they are sequestered. Forwarded INT would then end bwrap (a hard stop of the specs) rather than reach them directly. Specs lose the controlling terminal, which none of them should need. Another option is to make REAPER's child call `setsid()` instead of `setpgrp(0,0)`. The group id stays `$pid`, so forwarding and the watchdog keep working, and this also closes the terminal residue on macOS. But it changes c0079's subject, so it needs its own check.
Recommendation: add an experiment on `ubuntu-latest` in the real launcher shape (`fence.REAPER` with the watchdog), with `--new-session` and alternatively with the `setsid` launcher. It has to answer three questions: INT/TERM/HUP stop everything, leaving nothing; SIGKILL of the launcher leaves nothing; a group-wide signal from inside reaches neither the watchdog nor bwrap. Pick the variant that passes and pin it in AC1, the spec and a Rules row. If neither passes, state the residue truthfully: the real `CONFIG_LEGACY_TIOCSTI` default, how to check `dev.tty.legacy_tiocsti` in SETUP.md, and the group-signal reach under "Caught only by review".

### F10 [low] The Linux sibling of repo-fence's jail case can't reuse "the same probes", and the Linux fallback probes miss `/dev/shm`
Where: c0075 "Tests the executor edits" (sibling "with the same probes"); `tests/tooling/repo-fence.spec.luau` macOS case (symlink at the top of `.cache`; `touch -c -r .cache .cache`); Design `escapes()` Linux probes.
