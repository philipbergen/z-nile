# R0099: Provenance

## Theme
Five chores that build one thing, a ticket's provenance, as the user split it: "Split it and prototype first, like c0265", then "one raft, delivered a layer at a time in depends_on order" (c0263, 2026-11-08, quoted by every member). The members are Ticket provenance (c0263, the record: an append-only `provenance.md` per ticket and `./zn provenance record`), Provenance who from git (c0280, `./zn who <id>`), Provenance lifecycle rows (c0282, the lifecycle commands write `unblocked`, `rafted` and `delivered` rows), Design approval gate (c0283, `./zn approve` refused in an agent session and an `approved` row) and Board shows provenance (c0284, the board's item view shows `who`'s entries). The total size is about 2,380 changed lines, over z-raft's cap of about 1,500; the grouping is the user's, by argument, and grouping by argument overrides the cap. The members are layers of one design, so each is delivered as its own layer of one PR (zz-rules, the stack rules), the next building on the previous.

Shared surface (their common Touched paths): `z-nile/engine/provenance.luau` (all four upper layers add to c0263's module), `z-nile/engine/main.luau` (all five), `z-nile/engine/trail.luau` (c0263, c0280, c0284), `z-nile/engine/who.luau` (c0280, c0284), `z-nile/engine/dispatcher.luau` and `z-nile/engine/publish.luau` (c0282; c0263), `z-nile/skills/zz-rules/SKILL.md` and `z-nile/README.md` (all five, one Provenance section and one Provenance line that each layer extends).

User decisions the designs quote, verbatim:
- c0263 (Problem, 2026-11-07): "tickets need authors (whose idea, take it from git, then who approved the design, who unblocked a blocked ticket and so on)."
- Scope decision (user, 2026-11-08), on every member: "Split it and prototype first, like c0265".
- Q1 (2026-11-08), "Derive from git, store only the rest": what git knows is read from history by `./zn who`; only what git cannot tell goes in ONE append-only record per ticket.
- Q3 (2026-11-08), "Land first, define a small record API": c0263 depends on none of c0250, c0260, c0254 or rank; those call `./zn provenance record` when their event happens.
- Q4 (2026-11-08), "Read c0254's spend rows": the worker is read, never stored.
- Q5 (2026-11-08), "Confirm all": rafted is the rafting PR merge, one entry per ticket layer; delivered is the raft PR merge; unblocked is a `status <id> new` after a stop; `release` is not stamped.
- (2026-11-08) "Refuse in any agent session": `./zn approve` is refused in any agent session, "a human ran it must be true, not just reported".
- (2026-11-12) "Restack unites records (Recommended)" and "./zn provenance record (Recommended)" (c0263, R1 and R2).

## Order & dependencies
Delivered a layer at a time, in `depends_on` order, then by id (the user: "one raft, delivered a layer at a time in depends_on order"); `./zn workstreams` runs them one wave each (`parallel: no`).
1. c0263: the record. Every other member builds on its module, the publish rule, the merge and `./zn provenance record`.
2. c0280: `./zn who` and the reader (`trail`, `who`); depends on the record. Second, so that the later layers' rows print through it.
3. c0282: the lifecycle rows, the dispatcher's actors and the rafting gate; depends on the record. Third, because it defines the agent-session variable list first (Whole-raft design) and writes the `rafted` rows that the next layer's `approved` row sits beside.
4. c0283: the approval gate; depends on the record. Fourth, because it adds `AGENT_VARS` as an alias of the third layer's list, and the rafting gate expects a prep PR's `approved` row to be in the record already.
5. c0284: the board; depends on the record and on `who`. Last, so that its board spec compares the board's entries with `who`'s for every row the earlier layers write.

## Cross-raft waits
