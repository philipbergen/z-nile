# R0129: Z work works every ticket

## Theme
One issue, f0399 "z-work works every ticket", grouped alone at the user's request (`/z-raft f399`). Its size is 2,300 lines, over the cap, so `./zn raft-plan` would also make it a raft by itself (f0399, G17: splitting it is the user's call, and the user approved it as one issue on 2026-11-17).

With no raft named, `./zn work next` picks the next step of every ticket (land, resume, ready, repair, raft, size, design), tickets with nothing unmet first. The worker records each choice in the issue's `guesses.md`, the approval covers that file, and approval is checked when a raft lands, not when it is readied. A ticket is rafted with what it depends on, and a raft can be built on an unlanded raft (`./zn ready <R> --on <D>`).

Surface: `z-nile/engine/guesses.luau` (new), `contract.luau`, `approval.luau`, `openlist.luau`, `readycheck.luau`, `readyfacts.luau`, `layergit.luau`, `raftplan.luau`, `work.luau`, `workread.luau`, `main.luau`; the skills z-work, z-design, z-raft, z-ready, zz-execute, zz-review and zz-rules; `z-nile/README.md` and `AGENTS.md`; the tooling specs `readycheck.spec`, `approve.spec` and `approve-publish.spec`.

## Whole-raft design
A raft of one: there is no interface between members. f0399's Design is the whole design, in nine sections: the guesses file and its contract part; the `Guessed` line of the open list; approval checked at landing by the ready commit's trailers (`Lands: approved`, `On: <D>`); the unnamed pick order in two tiers; the dependency join in `raftplan`; a raft built on an unlanded raft by a base commit on `<R>/base`; the skills' Guess mode sections; and what the vision raft's tickets meet when they are built later.

No change to a project's `architecture.md`. `experiments/prototype.patch` in f0399's folder is the reference for the pure modules (`guesses.luau`, `contract.luau`, `openlist.luau`, `raftplan.luau`, `work.luau`): its three pure specs pass on it.

Under `./zn dispatch` nothing changes: `ready` still demands approval there, and the four Headless sections stay identical.

## Experiments phase
Run first, from f0399's Unknowns & experiments (E1 and E2 ran in prep; E6 is reasoned):
- E3: does `./zn trace <R>` ask for a row for `approval.md` or `guesses.md` committed on a layer? Method: `land.spec`'s landing case. Fallback: the trace treats both as it treats an issue document.
- E4: does a `tracker: ready` commit with a body pass every guard on a published commit? Method: `land.spec`'s ready case. Fallback: the guard that reads the message learns the two trailers.
- E5: does `gh pr edit --base main` on layer 1's pull request succeed after the base raft's `done` retargeted its branches? Method: `on.spec` with the fake `gh`. Fallback: a warning, and the person retargets it.
- E7: after `./zn restack <R>` moves a raft from its landed base onto `main`, does `./zn trace <R> --check` still pass? Method: `on.spec`'s last case. No fallback needed: the spec accepts both answers.
- E8: does a branch named `<R>/base` pass `layergit.oldShapeRefusal` and every other reader of a raft's refs? Method: `on.spec`'s start case. Fallback: those readers skip the one name.

The real-git specs (`land.spec`, 18 cases; `on.spec`, 5 cases) have run in prep only up to their first f0399 step, because the commands did not exist. Their Rules and mutants rows are `reasoned`. Run each case as its step is built, and treat a case that cannot pass for any implementation as a finding for the user, never as a spec to edit.

## Risks & rollback
- **The git commands are specified but unproven.** `ready`, `finish`, `done`, `approve` and `--on` were not prototyped (see Experiments phase). This is where a design gap is most likely to show; `land.spec`'s carriers case (AC18) is the least certain.
- **Other rafts touch the same files.** `main.luau`, `work.luau`, `layergit.luau` and the zz-rules and z-work skills are edited by most active z-nile rafts (R0099 and R0100 among them). Expect conflicts at sync; keep both sides and rerun `./zn check f0399`.
- **It changes how every later raft is readied.** From the merge on, a raft readied outside the dispatcher carries `Lands: approved` and is held at `done` until each member's approval holds. Rafts readied before the merge keep today's rule (f0399, G4; AC11 pins it).
- **The vision raft was designed against today's code.** c0248, c0249, c0253 and c0394 meet f0399's changes when they are built (f0399, section 9). Their documents are not edited here; their own z-design reconciles them.
- **Rollback**: revert the raft's merge. A raft readied in between keeps its `Lands:` trailer, which the reverted engine does not read, so it lands by today's rule; a `guesses.md` left in an issue folder is then an unread file.
