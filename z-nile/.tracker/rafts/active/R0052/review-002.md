### F1 [high] (repeat of review-001 F1) The rafting gate still auto-merges a PR that rewrites a sequestered `check.sh`: any raft whose document the PR touches, an active one included, is "own"
Where: `z-nile/engine/dispatcher.luau` `judgePr`, the raft branch: `own[rid] = true` for every path `<root>/rafts/…/<rid>/<rid>.md` in `git diff --name-only base ref`, whether or not that raft exists on main or is active. The doc comment above `judgePr` and zz-rules' Dispatch "The chain" bullet still describe the old rule ("only its own items' files, the raft it adds and that raft's members").
Evidence: `exp2.spec.luau`, built from dispatch-guards' F1 fixture, with two rafts seeded on main: `pickman/.tracker/rafts/active/R0040/` (active) and `pickman/.tracker/rafts/R0041/` (backlog), each with `check.sh` = `bash members-check.sh`. PR #41 is the spec's own merging PR (new raft R0050, the members' `raft:` lines) plus one space added to R0040.md's title and `rafts/active/R0040/check.sh` = `exit 0`. `./zn dispatch c0096` printed `next: merge the raft PR #41`, and the fake gh logged `realgh pr merge 41 --squash --match-head-commit 6e41cd55…`. PR #42 does the same to the backlog raft R0041: `realgh pr merge 42 …`. (Both runs then stop with "merged but origin/main does not show it", because the fake gh doesn't merge. The merge call is the defect.)
Critique: a raft's `check.sh` is its exit criteria (it runs the project gate and every member's `check.sh`). Rewritten to `exit 0`, `./zn done` passes on anything. The PR picks this exemption by touching a document, the same "the PR names its own exemptions" mechanism review-001 found through `issues:`. The fix moved the hole from issues to rafts. The refute believed an existing raft's rewrite would wait for a human, and no case seeds an existing raft. The `items` set (the `only` rule) has the same shape: any raft document the PR touches makes every id in its `issues:` line carry-able, so a PR can rewrite a prepared member's reviewed design document (non-sequestered) by listing it.
Consequences: what a rafting PR may change is a small, known set: a new raft's folder (its document and stub `check.sh`, which pass as a new item without `own`), the members' `raft:` lines, an existing backlog raft's `issues:`/`grouped:` lines (fold, recombine), and `z-nile/next`. Deriving the sets from main (the base) instead of from the PR's own text removes the choice. A recombine or fold that rewrites an existing raft's `check.sh` then waits for a human (exit 4), which is the fail-closed answer review-001 already accepted. An active raft must never be touched by a rafting PR at all.
Recommendation: at the rafting gate pass `own = {}` (a new raft's own files already pass as a new item). Build `items` from rafts that are new or in the backlog on the base, and from members their base document or the issue's own `raft:` names, never from an active or done raft. Refuse any path under an active raft. Make the doc comment and the zz-rules bullet say so. Cases in dispatch-guards (non-sequestered): the two PRs above (active raft, backlog raft) each stop at exit 4 naming the `check.sh`, and the merging PR #34 still merges. Mutant: `own[rid] = true` back, killed.
Lesson: zz-arch/item-rules-scoped-to-their-call

### F2 [medium] The agent's `gh api graphql` still runs a mutation whose text the wrapper can't see: `-F query=@file` and `--input`
Where: `z-nile/engine/wrapper.luau` `apiDecision`: for `graphql` it refuses only when the `query=` field's value contains `mutation`. A `-F query=@q.graphql` value is the file's name, and `--input <file|->` sets `fields` and no query.
Evidence: `exp3.spec.luau` (wrapper-guards' fixture, through `z-nile/bin/gh` with the recording fake gh). `q.graphql` and `body.json` hold `mutation { mergePullRequest(…) }`. Results: `gh api graphql -F query=@q.graphql` → ok, `gh api graphql --input body.json` → ok, and the fake real gh logged both (`gh api graphql -F query=@q.graphql`, `gh api graphql --input body.json`). The inline `-f query=mutation{x}` was refused, as designed.
Critique: `mergePullRequest` merges a PR into `main` with no gate. That is the authority AC4 says the shim never passes ("`gh api` reads and comments"). gh reads `@file`, `@-` and `--input` bodies itself, so a wrapper that judges the argument words can't see them. This is the second hole in the same mechanism (review-001 F4 was an option's value taken for the endpoint). The watermark sees the merge only after the step.
Consequences: refusing what can't be seen may refuse a GraphQL read a skill sends from a file. The acceptance wrapper spec's walk over every gh command the skills name would show that. Reading the file instead means the wrapper reads stdin or files on gh's behalf (and `@-` consumes stdin), which is more surface for little gain.
Recommendation: for `graphql`, fail closed. Refuse `--input` and any field value that starts with `@` (`-F query=@…`, `-F x=@-`), and pass only an inline `query=` with no `mutation`. Add both forms above to wrapper-guards' gh case (refused, the log empty), and keep the inline read passing.
Lesson: zz-arch/guards-decide-from-the-tools-resolution
