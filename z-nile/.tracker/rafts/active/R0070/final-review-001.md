### F1 [medium] Where `lsof` cannot be started, the sweep and `leftovers` end in a stack trace instead of "cannot tell"
Where: z-nile/lib/tmp.luau:349 (`tmp.workingDirs`), reached from tmp.luau:408 (`sweep`) and tmp.luau:626 (`leftovers`); z-nile/check.sh:194; SETUP.md:10-17 (prerequisites)
Evidence: `./zn run --time 60 -- sh -c 'env -u TMPDIR PATH="$HOME/.rokit/bin:/usr/bin:/bin" lune run z-nile/lib/tmpcli -- sweep --dry-run --dir <a folder with a .cache/.tmp>'` (macOS keeps `lsof` in `/usr/sbin`, so this PATH has none) prints `No such file or directory (os error 2)`, then `[Stack Begin]` ... `Script '.../z-nile/lib/tmp', Line 349` ... `Line 408` ... `tmpcli', Line 104` ... `[Stack End]`, and exits 1. `process.exec("lsof", ...)` raises when the program is missing, and `workingDirs` has no `pcall` (`tmp.startOf` has one for perl, tmp.luau:272). No spec starts the real probe without `lsof`: tmp.spec.luau:303 and tmp-review.spec.luau:113 inject a probe that returns nil, and tmp.spec.luau:394 and callers.spec.luau:363 put a stub `lsof` first on PATH.
Critique: The design says "`lsof` unavailable means "cannot tell": nothing swept" (c0194.md:143), that `leftovers` then removes nothing and marks every tree `IN USE?` (c0194.md:150), and counts `lsof` unavailable among the cases that "refuse or sweep nothing" (c0194.md:177). Nothing is removed, so no tree is at risk. What is lost is the message and the listing. SETUP.md supports Linux and does not list `lsof`, and minimal installs and containers do not have it. On such a host every gate start prints eight lines of Lune stack trace that never name `lsof`, `./zn tmp sweep` and `./zn tmp leftovers` exit 1 with the same trace, and the stale trees this chore exists to remove pile up with no line that says why. The tempting fix is a `pcall` that returns nil, and nothing more.
Consequences: With nil, the command line fails at the first folder: one line, `tmp: cannot list the processes' working directories (lsof); nothing swept`, at every gate start on that host, for ever, because check.sh:194 ignores the exit code. That is the right loudness only when the person can act on it, so SETUP.md has to name `lsof`; otherwise the line is noise nobody can clear. `leftovers` then lists every tree as `IN USE?` and removes none. The SessionStart hook stays quiet either way. No `.cache` line is added, so `cachepaths` and `callers.spec`'s scan are not touched.
Recommendation: `tmp.workingDirs` returns nil when `lsof` cannot be started (a `pcall` around the call, as `tmp.startOf` does). SETUP.md's prerequisites table gains `lsof` for Linux ("distro packages"), with the reason. Two cases in `tests/tooling/tmp-review.spec.luau` (not sequestered), both on a PATH that holds lune and the basic tools and no `lsof`: the command line's `sweep --dir <fixture with an aged tree>` exits 1, its stderr is that one `tmp:` line with no `[Stack Begin]`, and the tree is kept; a child Lune calling `tmp.leftovers({ name }, base, tmp.REAL)` gets one line ending `IN USE?` and the tree is kept. No sequestered file changes.

### F2 [low] A FIFO or socket inside a tree makes every sweep print a Lune panic
Where: z-nile/lib/tmp.luau:364-384 (`newest`; the per-child look is lines 373-378); the comment at tmp.luau:417-418
Evidence: A fixture `.cache/.tmp/aaa.A/pipe` made with `mkfifo`, the tree aged four days, then `lune run z-nile/lib/tmpcli -- sweep --dry-run --dir <fixture>` prints `thread 'main' (...) panicked at crates/lune-std-fs/src/metadata.rs:59:13: Encountered unknown filesystem filetype`, then the correct `tmp: would remove ... aaa.A (idle 110 h)` line, and exits 0. With the FIFO removed the panic line is gone and the rest is the same.
Critique: Review 001 F4's fix looks at the entries of `.cache/.tmp` itself with `test`, and the comment says only `test` looks at an entry until it is known to be a folder or a file. One level down, `newest` still hands every direct child of a tree to `fs.metadata`. The `pcall` there catches the panic, so the tree is judged correctly. But Lune prints the panic on stderr first, and the gate shows the sweep's stderr. Sockets are made under `TMPDIR`, which is now `.cache/.tmp`: an ssh control socket folder, `tmux-<uid>`, a Python multiprocessing listener. One such tree makes every gate start in every worktree of the session, and every `./zn tmp sweep` and `leftovers`, print "panicked" until the tree is a day old. It reads as a crash of the gate. tmp-review.spec.luau:129 covers a FIFO directly in `.cache/.tmp`, not one inside a tree. The tempting fix is to ask `test -d` and `test -f` for each child, as the top level does.
Consequences: That is two process starts per direct child of every candidate tree (a clone's top level has about thirty entries), at every gate start. One `find` per tree that lists only folders and regular files costs one start. The "(idle N h)" of the report keeps its meaning as long as the tree's own entry and those children are still looked at.
Recommendation: In `newest`, list the direct children with one `find <path> -mindepth 1 -maxdepth 1 \( -type d -o -type f \)` and hand only those to `fs.metadata`. One case in `tests/tooling/tmp-review.spec.luau`: an aged tree holding a FIFO, the command line's sweep with a stub `lsof`; stderr has the `would remove` line and no "panicked", and the real sweep removes the tree. `leftovers` goes through the same function (tmp.luau:659) and needs no case of its own.
