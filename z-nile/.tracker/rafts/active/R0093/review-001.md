### F1 [high] `retry new` adopts an issue by replacing that issue's own run state, writing into its folder without its lock
Where: z-nile/engine/dispatcher.luau:1088-1106 (`dispatcher.finishCapture`), called from the `retry new` adoption at :2558-2580; the lock `retry` holds is `new`'s only (:2506).
Evidence: I ran a probe spec in a `.cache` fixture with the fake CLIs (deleted after the run). (1) `dispatch new "make one thing"` with a z-ticket that runs `./zn new issue …` and then writes questions.md fails with "z-ticket made c0020 and asked a question: … ./zn dispatch c0020 goes on with the issue". (2) The user does that: `dispatch z-design c0020` leaves `c0020/state.json` with history `z-design:ok`, step `z-design`, mode `step`. (3) `dispatch new "other words"` is refused with "./zn dispatch retry new re-runs it". (4) The user runs that: `retry new` prints "c0020 was made by this capture: its conversation now belongs to it". `c0020/state.json` now holds the slot's state: history `z-ticket:ok,z-ticket:failed`, step `z-ticket`, mode `chain`. The probe's assertion failed: expected "z-design:ok", got "z-ticket:ok,z-ticket:failed". The cause is that `finishCapture` checks only `{dest}/exchange`, then sets `st.dir = dest` and runs `save(st)` with the slot's whole state. That replaces the issue's own history, pending rows (an active item's spend waits there until its merge), worktree, merges and watermark mirror. When c0020's own chain is running in another terminal, the move lands under that live dispatcher. Its in-memory state has `sealed = nil`, so after its step `exchangeRead` sees "added 001-ask.md" and fails the step. Its next save drops the seal, so every later step on c0020 refuses at its start ("the exchange of this run cannot be used") until `--forget-exchange` sets aside the capture's conversation, the record c0260 reads. There is a second defect on the same path. When the dispatcher died after z-ticket made the issue and wrote `questions.md`, the adoption leaves that file waiting in the slot, prints "(your --answer was not taken: nothing waited for it)", and the next `dispatch new` is then refused with "a capture waits for your answer".
Critique: The obvious fix is to refuse the adoption when `{dest}/state.json` exists. That leaves the slot failed with its words, so every later `dispatch new` is refused. The only way on is then `retry new --forget-exchange`, which takes away the conversation the Design (item 8) says belongs to the issue.
Consequences: Merging into the issue's state gives it two writers, the adopting retry and the issue's own dispatcher, so the issue's lock must be taken. A live run must refuse the adoption with nothing moved. The seal must go into the issue's state. That needs no merge with an existing seal, because an issue that has an exchange is already refused. The issue's history, step and mode must stay its own. If the capture's attempts were appended, `exchangeLastStep` would point at z-ticket. In the modelStep success path the issue is new, so the merge changes nothing there, and `lock` is idempotent per process (`holders[dir]`), so the chain's own `lock(st.dir, true)` straight after stays correct.
Recommendation: `finishCapture` first takes `lock(dest, true)`. If another live dispatcher holds it, it returns "<id> is being dispatched: run retry new when it ends" and moves nothing. When `{dest}/state.json` exists, it loads that state and adds only the capture's exchange and its `sealed`, keeping everything else. It saves the slot as finished, as now. It sets a `questions.md` still waiting in the slot aside as `questions-refused-N.md`, as the live path does, and then says the question was set aside rather than that nothing waited. The cases go in an own spec under `z-nile/tests/` (the sequestered specs stay as they are): (a) made-and-asked, then `dispatch z-design <id>`, then `retry new`: the issue's history still holds z-design's attempt, `exchange/` is `001-ask.md`, and a second `dispatch z-design <id>` starts without a "changed since" refusal (the mutant is the old whole-state save); (b) the issue's lock held by a live fake step (`stall`): `retry new` refuses naming the issue, and the slot and the issue's folder are unchanged (the mutant takes no lock); (c) z-ticket makes the issue, writes questions.md and kills its dispatcher: `retry new` adopts the issue, the slot holds no `questions.md`, and a following `dispatch new` runs (the mutant leaves the file). Then rerun the C mutants anchored in `finishCapture` and the adoption (C8, C42, C49, C57) after updating their anchors.
Candidate lesson (zz-arch): a record moved into another item's run folder joins that item's state under that item's lock and never replaces it. Check: what is already at the destination, and who else writes it while you do?

### F2 [medium] A relative `--answer-file` is read from the checkout's root, not from the folder the user ran `./zn` in
Where: z-nile/engine/dispatcher.luau:295-319 (`readAnswer`: `fs.isFile(file[1])` and `fs.readFile(file[1])` as given); `zn` runs `cd "$top"` before the engine starts; z-nile/engine/main.luau:876 (`hereDir`) and :2568 (`callerPath`, c0120) are the existing rule for caller-relative paths.
Evidence: `cd pickman && ../zn dispatch retry c0300 --answer-file answer.md` looks for `<root>/answer.md`. With none there it refuses "--answer-file answer.md is not a regular file", although the file exists where the user stands. With a file of the same name at the root, it stores that file as the user's answer: `cd z-nile && ../zn dispatch retry <id> --answer-file README.md` stores the root README. Every `--answer-file` case in `retry.spec` and `rounds.spec` passes an absolute path, so nothing catches this.
Critique: The obvious fix is to join `hereDir()` to the path inside the dispatcher.
Consequences: `hereDir` lives in `main.luau`, which the dispatcher cannot reach. It is also `""` both at the root and outside the checkout (`zn` sets `rel=""` for a caller outside it), so a relative path given from `/tmp` would still resolve against the root.
Recommendation: In `cmd.dispatch` (main.luau), rewrite a relative `--answer-file` to `<ZN_TOP>/<hereDir()>/<path>` before `dispatcherLib.main` sees it, and leave an absolute path as it is. For a caller outside the checkout, either have `zn` export the caller's physical directory (trusted only when the engine runs in `ZN_TOP`, as `ZN_CWD` is), or refuse a relative path when the caller's folder is unknown. Name the absolute path read in the refusal and on success. Add an own spec case: from a subfolder, a relative `--answer-file` whose name also exists at the root with other text stores the subfolder file's text. The mutant is the unresolved path.
