### F1 [high] A raft that is stopped and readied again sends the next session to its old worktree, where every beat and `done` are refused
Where: R0100.md, Whole-raft design ("The skills and the README": z-run is a shim) and Experiments phase, "z-work and the heartbeat"; c0274.md:70 and :92; the stack's `cmd.stop` (`cm.drop(raft.id)`, main.luau:7936) and `cm.drop`/`cm.file` (lines 427 to 470); `origin/main` z-work step 5 and `work.forRaft`'s `release` and `ready` actions; z-run's `cd "$(./zn worktree <R>)"`; dispatcher.luau:1185 (`worktree(ctx, "raft-{id}")`).
Evidence: z-work, now the main worker, makes stop and ready again its routine block path. Step 5 says "From the main checkout run `./zn stop <R>`". Once the person answers, `./zn work next <R>` prints `ready` ("From the main checkout run ./zn ready R"), then `implement`, and z-run/zz-execute Phase 0 does `cd "$(./zn worktree <R>)"`. Here is that path on the stack:
1. The first session ran `./zn beat <R> --adopt` in `.worktree/<R>`, which wrote `.cache/tracker-stamp-<R>` = S1 in that worktree.
2. `./zn stop <R>` runs in the main checkout. `cm.drop` removes only the cwd's `.cache/tracker-stamp-<R>` (the main checkout's), so the worktree still remembers S1.
3. `./zn ready <R>` publishes a new stamp, S2.
4. c0277's plain lookup returns the family's current member. That is the old `.worktree/<R>`, because nothing discarded it.
5. In that worktree, `heartbeat.holds(S1, S2)` is `taken`. zz-execute's step 2b `./zn beat <R> --adopt` is refused with `<R>'s claim was taken over (now S2)` ("adoption never overrides a remembered different stamp", c0274.md:70), the autobeat drops the claim "with one word, once", and `./zn done <R>` is refused.

The new claim never beats. It reads lost 15 minutes after `ready`, anyone may take it over, and the work can't land. The members' only answer is z-stop step 4 (stack diff): "A lead who stops and re-readies its own raft continues in a numbered copy (`cd "$(./zn worktree --takeover <R-id>)"`)". But the session that readies again later reads z-ready and z-run, not z-stop. Nothing in the `work next` → z-run → zz-execute route says `--takeover`, and zz-execute's own takeover sentence covers only "a raft whose claim was lost", which this one isn't.

The dispatcher fails the same way, and no skill text can fix it. When a person stops a raft and dispatches it again, the z-run step runs in `raft-<id>`. c0275's `dispatchStamp(started, remembered)` prefers the worktree's remembered S1, so every `beat <R> --adopt --stamp S1` is refused, `dispatchOutcome` classifies it `lost`, and the beats stop.

The raft's "z-work and the heartbeat" paragraph lists two things no member delivers, (a) and (b), and misses this one. z-work landed after the members were prepared, which makes this the raft's catch.
Critique: The tempting fix is one more sentence in the z-run shim ("if `--adopt` says taken over, use `--takeover`"). That covers an interactive session that reads it. It doesn't cover the dispatcher's engine-chosen `raft-<id>` path, and it asks an agent to tell "my own old worktree after a stop" apart from "I was taken over" by reading one refusal text that is the same in both cases.
Consequences: The fix that holds is in the engine. When the family's current member remembers a stamp for the item that `origin/main` no longer shows, a plain `./zn worktree <name>` and the dispatcher's `worktree(ctx, …)` must not hand that member out. They must go through c0277's discard of an "already over" claim and return the numbered copy. That keeps "Drop in-place re-adoption", since nothing re-adopts and the old worktree stays refused. It changes c0277's lookup rule (Design, "The lookup is by family"), its AC2 and its Rules rows, so it is a member design change, and z-raft can't make it. Between layer 2 and layer 5 there is no numbered copy at all. c0274 accepted that ("Cost: that path waits on c0277"), but z-work turns it from a rare path into the routine block path, so each layer also needs a stated interim instruction.
Recommendation: Unfold c0277 (`./zn unfold R0100 c0277`; lesson z-raft/rafted-member-changes-stay-in-the-raft) and send it back to z-design. Its plain lookup and the dispatcher's worktree resolution must skip or discard a member whose remembered stamp `origin/main` no longer shows for that item. Spec cases:
- ready → `--adopt` in the worktree → `stop` from main → `ready` → `./zn worktree <R>` prints a numbered copy where `--adopt` succeeds.
- The old worktree is still refused.
- The dispatcher's `claimBeat` after stop and dispatch again beats S2.
- A never-stopped worktree's lookup is unchanged.

Then fold it back and rerun this review. For layers 2 to 4, the raft's z-run shim and zz-execute must say what a session does after it readies a raft it stopped before c0277 lands: z-stop step 4's "start fresh" (remove the worktree). RC3 must pin that phrase. If the author prefers not to unfold, this is the user's call: escalate to the user with the two options (engine routing in c0277; skill text only, which leaves the dispatcher path broken).

### F2 [medium] A discarded z-work session that carries a raft id is sent back into the taker's live copy
