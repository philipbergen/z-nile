### F1 [medium] The publish guard still accepts a status-only edit into `closed-…`, and a move whose new document is closed, neither of which is a close
Where: z-nile/engine/publish.luau:493-501 (the existing-document test) and :309-316 (`validateMoves`)
Evidence: the new test is `if (not before or not after or before ~= after) and closing.guard(existing, c.content) ~= nil then fail`. For a build that sets an existing live document's `status:` to `closed-quiet-copper-falcon` and adds no `wont_do:`, `withoutStatus(existing) == withoutStatus(c.content)`, so the whole condition is false and `closing.guard` never runs. `closing.closedDoc(existing)` is false because the old document is live, so the commit is published. origin/main then holds a closed issue with no reason, which only a later `./zn audit` (`closed-mismatch`) reports. A `ready`-style move is the same: `validateMoves` checks `closedDoc(old)` and then only the `withoutStatus` equality, so a move to `active/` that stamps `closed-…` passes. AC2 says the guard "accepts exactly a close edit (`closing.guard`) and refuses any other edit of an existing document". The Solution says "The publish guard accepts a document edit only when it is exactly a close". No spec case catches this: `readers.spec :: the publish guard refuses a status-only edit of a closed document and a wont_do line without the closed status` covers the reverse half (a `wont_do:` with no closed status) and a status-only edit *of* a closed document, but not a status-only edit *into* closed. Today's `setStatus` can't produce it (`status <id> closed` is refused), so the gap is reached only by a hand-built publish or a later engine bug. Still, the guard exists to catch exactly that, and zz-arch rule 7 says it should.
Critique: the tempting fix is to run `closing.guard` on every edit of an existing document. That would refuse every ordinary status move, because `guard` refuses anything that is not a close.
Consequences: the fix needs a rule for which shape is judged by which test. The status-only path stays for every non-closed target. Any `after` that `closing.closedDoc` holds must pass `closing.guard`. The same rule then applies to `validateMoves` (a moved document may never become closed). Nothing the engine publishes today becomes closed except `close` itself, so no existing command is refused.
Recommendation: in the existing-document test, after the `closedDoc(existing)` refusal: if `closing.closedDoc(c.content)`, require `closing.guard(existing, c.content) == nil` (with the existing "(or be one close: ./zn close)" message). Otherwise keep the status-only test as it is. In `validateMoves`, refuse a moved document whose new content `closing.closedDoc` holds, with the "never published again" reason or a "a move never closes" reason. Add two cases to a non-sequestered spec (for example `tests/tooling/` beside the publish-guard ones; the c0278 acceptance specs are sequestered): a status-only publish of `status: closed-quiet-copper-falcon` on a live document is refused and leaves the tip unchanged, and a move whose new document is stamped `closed-…` is refused.

### F2 [medium] `close`'s dependents grep and `land`'s closed-dependency lookup treat a git failure as "no dependents" and "not closed": both guards fail open
Where: z-nile/engine/main.luau:1849-1866 (`cmd.close` build: `local hits = sh.run("git", args)`, then `string.gmatch(hits.stdout, …)` with `hits.ok`/`hits.code` never read); z-nile/engine/main.luau:2530-2537 (`captureScope`: `if listed.ok and … then … if shown.ok and closing.closedDoc(…)`)
Evidence: `git grep … <rev> -- …` exits 1 for no match, and 128 for an error. For example, `git grep -l -w -e c0266 --and -e '^depends_on:' deadbeefdeadbeef -- z-nile/.tracker/issues/` prints `fatal: unable to resolve revision` and exits 128. Other causes are a missing object in a partial clone, a lock, or a too-long argument list. Either way stdout is empty, so `facts.dependents` stays `{}`, `closing.refusal` passes rule 8, and the close is published even though d0298 depends on it. In `captureScope`, an `ls-tree` or `show` that fails (`ok == false`) skips the id, so the capture lands with a closed issue in its `depends_on`. zz-arch rule 7: "A guard acts only on its one explicit 'no' answer and treats every other outcome as guarded."
Critique: the tempting fix is `if not hits.ok then return "…" end`. That refuses every close with no dependents, because exit 1 is how grep says "no match".
Consequences: the explicit "no" for the grep is `code == 1` with empty stdout; `code == 0` means hits; anything else refuses, naming the id, the base and git's stderr. For land, `ls-tree` exiting 0 with empty output is the explicit "no such backlog document"; a failed `ls-tree`, or a failed `show` of a path `ls-tree` just listed, refuses the land ("cannot read <depDoc> at <base>: …"). Neither changes a refusal text that already exists. The new ones come last (zz-arch/new-refusals-keep-the-old-order).
Recommendation: as in Consequences. Pull the grep-result judgement into a small pure helper, `closing.dependentsFrom(code, stdout)` or a local function, so a spec can cover all three outcomes (0 with hits, 1 empty, 128) without having to make git fail in a fixture. Cover land's lookup the same way: a pure judgement of the `ls-tree`/`show` results with cases for listed-and-closed, not listed, and a failed call.
Lesson: zz-arch/guard-no-is-explicit
