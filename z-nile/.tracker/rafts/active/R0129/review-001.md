### F1 [high] `./zn raft-plan` never passes `depends_on` to the planner, so the dependency bundling does nothing outside the pure spec
Where: `z-nile/engine/main.luau:4505-4521` (`cmd["raft-plan"]` builds each `raftplan.Issue`); `z-nile/engine/raftplan.luau:22-25,89-170,314-345`.
Evidence: the Issue literal in `cmd.raft-plan` sets `id, type, root, state, status, design, raft, size, solo, touched` and no `deps`. `grep -n "raftplan.Issue" z-nile/engine/*.luau` finds that one builder, and nothing else in the engine fills `deps`. Every `(i.deps or {})` in `raftplan.fill`, `depsFirst` and the feature join's `dependsOn` is therefore empty when the real command runs. Example: two prepared features where f0002 depends on f0001 and their Touched modules don't overlap. `./zn raft-plan --apply`, which is the command the `rafting` pick tells the worker to run (`work.luau` issueDecision), still prints two `new raft` lines, as on main. Design section 5 says "`raftplan.Issue` gains `deps: { string }?` (its `depends_on`), filled by `cmd.raft-plan`", and Implementation step 3 says "`cmd.raft-plan` fills it (AC7)". The Solution's outcome "z-work puts a ticket and the tickets it depends on in one raft" is therefore not delivered. AC7 still passes because `plan.spec` calls `raftplan.plan` directly with `deps` set.
Critique: a pure-module acceptance case passes while the command it serves never feeds it. The obvious fix is one line, `deps = store.idList(front.depends_on)`.
Consequences: once deps flow, `raft-plan` changes its output for every prepared issue that has a `depends_on`. A dependency on a done issue, on an issue that is not a candidate, or on an id that doesn't exist must change nothing. `depsFirst` ignores ids that aren't listed, and the feature join only matches names in the other candidate or open raft, so those three cases hold. A dependency of another type or project is in another group and is never joined (G12). A chore past the cap now joins its dependency's bin, which the user's "stack dependencies in one raft" asks for.
Recommendation: fill `deps = store.idList(front.depends_on)` in `cmd.raft-plan`. Then add an ordinary spec under `z-nile/tests/tooling/` (the sequestered `plan.spec` must not be edited) that runs `./zn raft-plan` in a `.cache` fixture and checks three things: two features with no shared Touched path, one depending on the other, come out as one `new raft` line naming both; a chore dependent past `raftplan.CAP` joins its dependency's raft; and a dependency on a done issue leaves the plan as it was. Give it a watch file naming `main.luau` and `raftplan.luau`.

### F3 [medium] No skill carries G18's release rule, so a `fix` that changes nothing is offered without end
Where: f0399.md section 4 "After a pick" and the "Fix it" paragraph, G18; `z-nile/skills/z-work/SKILL.md` steps 5-6 and Guess mode; `z-nile/engine/work.luau` (`Input.released`: "The skill carries it"; `work.fixable`; the `broken` pick in `work.decide`).
Evidence: the design says "A `draft` the worker gives back (section 7) counts as a release" and "the worker counts a `fix` that changed nothing as a release, so two in a row stop the session". The count exists only in the skill (`--released`). `grep -n "release\|changed nothing\|give back" z-nile/skills/z-work/SKILL.md z-nile/skills/z-raft/SKILL.md z-nile/skills/z-design/SKILL.md` finds the old rule ("A release adds one…") and the new "A `wait` is not a release", and nothing about a given-back draft or an empty `fix`. `work.decide` offers the same `fix` for as long as `ready` refuses, for example a raft whose block is an open bullet the worker cannot answer. A worker following the skill as written gets the same line on every call and nothing stops the session.
Critique: the engine's stop is `work.BLOCKED_IN_A_ROW` applied to `--released`, so a rule the skill never states doesn't exist.
Consequences: the same sentence also covers z-design's "give the claim back (`./zn status <id> new`)" for a scope-cut question, which is the given-back draft. Counting it keeps two unanswerable designs in a row from turning into an endless pick-and-give-back loop. A `fix` that did change something (a new coherence round merged) is not a release, and the next `work next` simply moves on.
Recommendation: add to z-work step 6, or to its Guess mode section: "A `draft` you give back (`./zn status <id> new`) and a `fix` that changed nothing each add one to the count you pass as `--released`." Pin that sentence in an ordinary skill-text spec (not the sequestered `docs.spec`).
