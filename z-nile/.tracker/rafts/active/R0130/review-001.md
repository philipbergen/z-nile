### F1 [medium] Run inside a detached worktree that holds a design of its own, approve records on the detached HEAD and then never counts, although zz-rules (pinned by docs.spec) says such a worktree is refused before anything is recorded
Where: z-nile/engine/main.luau:6488 (`if process.env.ZN_APPROVE_IN == top and where ~= "a worktree of origin/main" then`), and the zz-rules approve row ("a worktree on no branch is refused before anything is recorded"), which `acceptance/docs.spec.luau:58` pins
Evidence: I wrote a reviewer probe spec in a fixture under the worktree's `z-nile/.cache/` (since removed). The fixture had a draft c0001 on origin/main and `.worktree/mut-copy` added with `--detach`, holding a committed `design: ready` copy with a design of its own (the shape of the mutation copies and prototypes z-design makes). I ran `yes y | script ... './zn approve c0001'` inside that worktree. It printed `c0001: approving in .worktree/mut-copy`, then `approved c0001 9991e57a… in …/mut-copy`, then `but it does not count yet: … is on no branch, so there is nothing to push. Retry: ./zn approve c0001 --publish`, and exited 1. The tip of the worktree became `tracker: approve c0001` on a detached HEAD. The retry it names, `./zn approve c0001 --publish`, prints the same failure every time. The no-branch refusal only covers a placed run (`ZN_APPROVE_IN == top`). When placement picks the worktree the command runs in, the run continues in-process with `ZN_APPROVE_IN` unset (main.luau:6224, `publishOnly = not chosen.record`), skips the refusal, records, and only the push step finds out there is no branch.
Critique: this breaks the rule the skill states. The retry the command names cannot succeed, and the commit it leaves sits on no branch, so the next checkout drops it. Two fixes will tempt the author. One is to narrow the zz-rules sentence: docs.spec pins that sentence, and the sentence is the safer rule anyway. The other is to set `ZN_APPROVE_IN` for the in-process run as well: that makes the "here" case look placed and changes what `where` prints.
Consequences: if the refusal applies to every recording run with an origin, a prototype or mutation copy on no branch can no longer be approved from inside it. The person gets the existing text (`… is on no branch (a rebase or another operation may be in progress): nothing recorded`) and checks out a branch first. A repository with no origin still records in place, as Design section 2 says, so the condition must keep `hasOrigin()`. The command's own `.worktree/.approve-<id>` is detached by design and must stay exempt. It is exempt through `where` only when the run was placed there, so a person who runs `./zn approve` while standing inside `.approve-<id>` would now be refused, which is acceptable for a folder the command owns. The `--publish` path does not record, so it needs no new rule: it already fails in `pushBranch` on no branch.
Recommendation: change the condition at main.luau:6488 to `if hasOrigin() and where ~= "a worktree of origin/main" then` and keep the refusal text that `approve-raft.spec` pins. Add a case to `z-nile/tests/tooling/approve.spec.luau` (a tooling spec, not sequestered): a detached worktree with a committed ready design of its own, `./zn approve` run inside it, a non-zero exit, `is on no branch` in the output, the tip unchanged and nothing pushed. Check that the case fails with the old condition. Then rerun `./zn check c0369` (approve-raft's no-branch case and approve-main's scratch cases must stay green) and the affected gate. A candidate lesson for zz-execute (a reviewer may not write it): when a skill sentence states a guard for an act without conditions, look at every path that reaches that act (placed, in-process, retried) and check that each one runs the guard. The question: "which call sites reach the guarded write, and does each run the guard?"
