### F1 [high] A new raft's dispatched coherence-review row is never written on its members: it can only be written while the raft is in the backlog on origin, and no flush runs in that window
Where: `z-nile/engine/dispatcher.luau:445` (`publishMeasured` still requires the raft's own folder in the zn-dispatch worktree), `:642-660` (`flush`), `:2033-2050` (the chain's `follow`, no flush); `dispatch.luau:159` (`rowWritable`), `:435` and `:465` (`follow`, then `z-ready`); d0415.md, The change, items 5 and 6; AC5.
Evidence: z-raft section 4 runs the coherence review with `./zn dispatch zz-review <R-id> --mode raft` from the rafting worktree, before the rafting PR lands, so for every new raft origin/main has no folder for it. `record` sends the row to `publishMeasured`, which stops at `costrow.locate(wt, row.id)` with `no folder for R…` and keeps the row pending (the spec's own R0090 case pins exactly that). Under the chain this review is a nested run of the issue's z-raft step, so the row sits in `{home}/<issue>/zz-review-raft-<R>-1/state.json`. Its only writer is `flush`, which takes a nested row only when `row.id == st.id` (line 650), so it needs a top-level run of the raft itself while the raft is in the backlog (`rowWritable`: a non-deliver row waits for `backlog`). The chain never makes one. After the rafting gate merges, `dispatch.next` returns `follow` (the issue is prepared with `raft:` set). The `follow` branch loads and locks the raft's state with no flush. The next action on a prepared backlog raft is `z-ready`, which moves it to active. From then on `rowWritable` is false for good, and `dispatch status <R>` prints `never written: <R> is active on origin/main, and a design-review row waits for backlog`. The issue's next run does not take the row either, because its id is the raft's. The AC5 cases reach a written raft row only for a raft already on origin (R0095, the refold) and for R0091 through a hand-run top-level `./zn dispatch zz-review R0091` while it is in the backlog. So an implementation that writes the refold case and loses every new raft's row passes.
Critique: the loss this issue fixes ("no row", the spend on no ledger) remains for the raft review the dispatcher runs most often: the first coherence review of a new multi-issue raft, which an unattended chain always dispatches. AC5's "a raft's row is recorded on its members instead of being lost" holds only for refolds. The tempting fix is to let `publishMeasured` write a raft row onto its members without the raft's own folder. But the sequestered R0090 and R0091 cases pin that a raft origin does not list keeps its row pending.
Consequences: the row can be written only in the backlog window, so its writer must run inside that window. The chain is the one process that is always there: it merges the rafting PR, or its next run finds it merged, and it then follows into the raft before `z-ready`. A flush there also reaches z-raft's own `prep` row of the raft, kept in the issue's top-level state (F2 gives it members). It writes from the issue's folder that this process has just unlocked (F4: take that lock). A person who readies by hand with `./zn ready <R>` instead of `./zn dispatch <R>` still skips every flush. That path needs a sentence in the skill, not code.

Every row of the raft kept under the home (its nested coherence-review row, z-raft's prep row in the issue's state) is then written while the raft is in the backlog, before `z-ready`. Add one sentence to z-raft section 4 and zz-rules' Spend bullet: a hand-dispatched coherence review's row is written by the next `./zn dispatch <R-id>` while the raft is in the backlog, so readying it through `./zn dispatch <R-id>` writes the row. Add a promoted tooling case (sequestered files untouched). Set up a pending raft row with members in a nested folder under an issue's state, the issue prepared with `raft:` on origin, its raft prepared in the backlog. `./zn dispatch <issue>` follows, the row lands on the lowest member before `z-ready` runs, and the nested `state.json` no longer holds it (mutant: no flush on follow). ### F3 [medium] A member without a folder leaves the lowest member's line in the zn-dispatch buffer, so a retry puts the raft's tokens on that member twice
Where: `z-nile/engine/dispatcher.luau:457-466` (the `publishMeasured` loop), `:468-483` (the failure paths); d0415.md, item 5 ("no partial write across members").
Evidence: the loop appends each member's line with `costrow.append` (to `<zn-dispatch>/.cache/measure.tsv`) before it locates the next member. Take members `[c0030, c0050]` with no folder for c0050 on origin. c0030's line, holding all 123 tokens, is appended. Then `no folder for c0050` returns, and the row stays pending. `costrow.restore` puts back only ledger files, never the buffer. Every later `flush` of the row appends c0030's line again. `buffer.fold` takes every line whose id is in `homes` (`buffer.luau:219-241`) and makes one ledger row per `row` line (`buffer.luau:300-302`). So the run that finally writes the row, or any other dispatcher row for c0030 within the 14 days, puts the 123 tokens on c0030 once per earlier attempt. A failed `git add` or `git commit` (lines 474-483) does the same, now for every member.
Critique: the design promises no partial write across members, and a buffered line is a write. The spend report then overstates the raft's review cost. The tempting fix is to move the `locate` check ahead of the appends, which leaves the add and commit paths as they are.
Consequences: holding the lines out of the buffer until the commit succeeds, or restoring the buffer, must not drop lines that another writer appended meanwhile. `costrow.writeBuffer` already keeps a suffix appended since `bufferPrevious`.
Recommendation: locate every member before appending anything, and refuse `no folder for <id>` with nothing buffered. Keep the rows out of the buffer until the commit succeeds: pass them to `costrow.plan` as `extra` ledger rows, as `cmd.spend` does. Alternatively, on every failure path, rewrite the buffer to `planned.bufferPrevious` plus whatever was appended since. Case: a raft row whose worktree list names a member that origin lacks stays pending. After `advanceMain` adds that member, the next run writes exactly one 123-token row on the lowest member (mutant: append before locate).

### F4 [medium] `statesUnder` walks every folder under the dispatcher's home and rewrites other items' `state.json` without their lock
Where: `z-nile/engine/dispatcher.luau:625-660` (`statesUnder`, `flush`), `:664-685` (`pendingReport`), `:2080` (`runsUnder`); `main.luau:8000` (`cmd.metrics`).
Evidence:
(a) The walk descends into every directory except `gh` and `broker`. That includes a gate judgement's scratch tree `{home}/judge-<n>-<t>-<r>` (an exported tracker plus its `.git`, line 1728). It also follows directory links (`fs.isDir` follows them), which a step can plant in its own state folder (`ZN_DISPATCH_DIR`). If a judgement removes its tree while another item's dispatcher is starting, `fs.readDir` or `loadAt` on the vanished path throws. Nothing guards `flush`, so that run dies at its start, and `dispatch status` and `./zn metrics` die the same way. A link loop makes all three recurse without end.
(b) For every state that is not running, apart from the item's own, `flush` takes the rows whose id is this item's. It then calls `save(other)` whenever it found one, even when it wrote none, and without that item's run lock. Other items' top-level states do hold such rows: the chain's z-raft step records the raft's `prep` row in the issue's state (`d0298/state.json` holds R0096's). `outcome ~= "running"` is not a lock. A chain between steps (judging, merging, following) is alive with the outcome `ok`. If it saves between this load and this save (`follows`, `merged`, its history), the save here throws its update away. A row this flush wrote also comes back with the chain's next save and is written again. The design asked for nested folders of finished runs only ("from nested folders whose run is not `running`").
(c) `runsUnder` already walks the same tree with another descent rule (zz-arch rule 5).
Critique: a read added to the start of every run, and to `status` and `metrics`, can now crash them, and a writer of other items' files runs without their lock. The tempting fix is to add `judge-` to the skip list, which leaves the links and the lock as they are.
Consequences: the sequestered cases need the walk to reach a nested folder under a parent with no `state.json` (c0099), and another item's top-level `state.json` (c0098) for the status line. Nothing in them needs `flush` to write another item's top-level file.
Recommendation: one walker for the run tree, replacing the two rules of `runsUnder` and `statesUnder`. From the home it enters item folders only, never `judge-*`, `gh` or `broker`. Below an item folder it enters only nested run folders named `<step>-<mode>-<id>-<n>`. It enters no entry that is a link (readlink, as zz-arch/writers-under-cache-replace-links says), and it skips a folder or file that vanishes mid-walk (pcall). `flush` rewrites a nested folder only when its run is over, and another item's top-level state only under that item's run lock. It skips a lock another process holds (that item's own run flushes it), and it saves only when it wrote a row. Cases: a `judge-*` tree and a link loop under the home leave `dispatch status` and a run's flush working, and they list the same rows. A lock another process holds on an item leaves its `state.json` unchanged byte for byte.
Lesson: zz-arch/moved-records-join-under-the-owners-lock
Erred: zz-arch
Upstream: z-design
