### F1 [high] A requested rerun crashes once the kicking raft's worktree is removed, so the landing that asked for it is never tested
Where: z-nile/engine/reap.luau:301 (`NET_SCRIPT`: `cd "$1"` and then `./zn run ... ./zn watch-net`, with `$1` the kicking checkout from watchcmd.luau:1131 `rev-parse --show-toplevel`); z-nile/engine/watchcmd.luau:485 (`startStep` runs `{process.env.ZN_TOP}/zn`); watchcmd.luau:461 (`mainDir` runs git with no cwd); watchcmd.luau:1064 (round 2 calls `ensureWorktree` again); zz-execute Phase 6 step 4 (removes the raft's worktree right after the report).
Evidence: the net's lune process, its cwd and its `ZN_TOP` are the kicking worktree, because the `zn` wrapper sets `ZN_TOP` to the checkout whose `zn` ran. Phase 6 step 4 deletes that worktree minutes after the kick, and the design says so itself (§2: "a raft's worktree is deleted minutes after its kick"). Round 1 gets through, because after the marker it uses absolute dirs. A rerun round starts with `ensureWorktree` → `startStep` → `process.exec("<deleted worktree>/zn", ...)`. Lune throws on a missing program ("No such file or directory (os error 2)"; checked with a probe), and a git with no cwd in a deleted folder fails ("fatal: Unable to read current working directory"). The probe reproduces the whole thing in a scratch fixture with this layer's code: a kick from `.worktree/R9999-probe` with the suite held, a second kick from main ("already running ...; a rerun is requested", exit 0), then `git worktree remove --force` of the raft worktree, then release. The first net's log ends `watch-net: a rerun was requested; running again` / `tracker watch-net: No such file or directory (os error 2)` with a stack at `watchcmd:485 startStep` ← `ensureWorktree` ← `runOnce` ← `net`. Its exit file says `1`, `hold/runs` is `start end` (no second run), and `.cache/watch-net/lock` is left behind (`84556 1795132593.755202`): the error is not a `fail()`, so `releaseHeld` never ran. `finishRound` had already removed `rerun`, so the request is gone too. On the real repository this is the usual case for a rerun: raft A kicks and removes its worktree, raft B lands during A's suite and gets "already running" (exit 0, reported as fine), and B's commits wait unseen for the next kick. AC2 ("a rerun request is honoured exactly once") passes only because the lock spec never removes the kicking worktree, and the kick spec's "the log outlives the raft worktree" case removes it only after the net has settled.
Critique: the design moved the net's files out of the raft worktree (F7 of design review 001) but left the net's process living there: its cwd, `ZN_TOP` and the `zn` it runs. The tempting fix is to make NET_SCRIPT `cd` into the main checkout and run the main checkout's `./zn`. That breaks the first run and every run after a change to the net. Phase 6 kicks before step 4's `sync`, so the main checkout still holds the previous engine. On this very landing that engine ignores `--ready`, never writes the marker, and every kick fails at its backstop.
Consequences: after it has started, the net must not depend on the folder it was started from. Every process it starts needs an explicit cwd, and the bounded runner it uses for its steps must live in a folder that outlives the kicker. The net worktree's own `zn` is the version main had at its last rebase, so `zn run`'s flags (`--time`, `--`) must stay compatible across one landing, which they are today. An uncaught Luau error in any round has the same lock-leak path as this one.
Recommendation: (1) `watchcmd.net` reads the main checkout once, at its start, while the kick that started it still waits (`mainDir()`). It passes that path to `ensureWorktree` and never calls `mainDir()` again. (2) `startStep` runs `<netDir>/zn run --time <left> -- git ...` once `<netDir>/zn` exists, which is always true from round 2 on and in round 1 after the worktree is added. It falls back to `ZN_TOP` only for round 1's first fetch and `worktree add`, which run before the kick can return. Every git call in the net gets `cwd` = the net worktree or the main checkout. (3) Wrap the rounds loop in a `pcall` that calls `releaseHeld()` and then re-raises (exit 1), so a crash leaves no lock. (4) Add a tooling spec that is not sequestered, e.g. `tests/tooling/watch-net-rerun.spec.luau` on `netfix`. Case 1: kick from `w.raft` with the hold on, a second kick, `git worktree remove --force w.raft`, release; expect `hold/runs` = "start end start end", the first kick's exit file `0`, and neither `lock` nor `rerun` left. Case 2: a net whose round raises a Luau error (not `fail`) leaves no `lock`. Both cases must fail on be0d3c30e, and case 1 does (the probe). Add a Rules and mutants row for it in the Verification log ("the net outlives the worktree that kicked it").

### F2 [medium] Four rounds share the one `--time 3600` bound, so a long rerun is killed partway, possibly in the middle of a git write in the standing worktree
Where: z-nile/engine/reap.luau:301 (`./zn run --time 3600 -- ./zn watch-net ...` around the whole net); z-nile/engine/watchcmd.luau:1063 (`for round = 1, MAX_ROUNDS`, with `MAX_ROUNDS = 4`); Design §3.
Evidence: each round that has sources runs `check.sh --full` and then `check.sh --slow`. The slow tier alone holds specs of 375 s, 262 s and 260 s (`.cache/slow-main.log`, "slowest:") and 8,402 s of serial time in `tests/slow.tsv`. Two full rounds already take a large part of an hour, and nothing checks the time left before round 2, 3 or 4 starts. At 3600 s, bounded.pl sends TERM and then KILL to the net's group, whatever step it is in: `commitRepair`, `pushMain`'s fetch and rebase, or the slow-tier defect write. A kill inside `git commit` or `git rebase` in `.worktree/watch-net` leaves `index.lock` or a rebase in progress. Then every later net fails at "rebase onto origin/main failed", and repairing that worktree is outside this issue (Non-goals). Before this layer, the net ran one round, so the bound was sized for one round.
Critique: MAX_ROUNDS caps the count but not the time, and the design never checked that four rounds fit inside the bound they share. The tempting fix is to raise `--time`. That moves the cliff without removing it, and it also has to move `NET_MAX_AGE`, which the reaper's exemption depends on.
Consequences: a round that is not started has to leave its request for someone. The next net already deletes a leftover `rerun` when it takes the lock, and that is right, because it runs on a newer main. The net needs to know its own deadline without an inherited variable of the kick's (design review 001 F1).
Recommendation: the net computes its own deadline from its start (`os.time()` at the top of `watchcmd.net`, plus `3600` taken from the same constant `NET_SCRIPT` spells, kept beside it in `reap.luau`, minus a margin). Before each rerun it compares the time left with the wall time of the round it just ran. When the next round would not fit, it leaves `rerun` in place, gives the lock back, and prints `watch-net: a rerun is left for the next kick (<s> s left)`. Make this a pure rule, `watch.again(requested, round, max, lastRound, left)`, with cases: a request with time for a round → again; a request without it → not again and the request kept; no request → not again. Add a Rules and mutants row with the mutant "ignore the time left".

Upstream: zz-review

### F3 [medium] The first real run after landing will push watch-map extensions for a week of commits, and nothing in the raft tells anyone to expect it or check it
Where: z-nile/engine/watchcmd.luau:821 (`applyRepairs`, unchanged; it extends a failing spec's watch file with every suite source in `sincePassed`); `z-nile/watch-passed` = b0c78fb6e (2026-11-12); R0138.md "Risks & rollback"; d0383 Implementation step 4.
Evidence: `git diff --name-only b0c78fb6e origin/main` lists 3,693 paths over 1,038 commits. The last time a net found red after a gap (2026-11-16, b466c3ad0), it pushed d0400 and d0401 straight onto main: 35 sources each, added to `c0172/watch.txt` and `c0246/watch.txt`, among them `zn`, `main.luau` and `tests/lib/loops.luau`. Also, the net runs `check.sh --full` in `.worktree/watch-net`, inside the main checkout, which is the very layout zz-execute Phase 6 keeps the game gate out of ("a clone of the exact head whose parent directories are not a checkout of this repo"). So the first run, which this layer makes possible, will most likely push a "watch-net: extend the map for a missed failure" commit with a week's worth of paths onto main, no review in between. The raft's Risks name only the slow-tier defect, and step 4 asks only for the kick's own line.
Critique: what the net repairs is a Non-goal, so the fix is not mine to prescribe. But reviving a net that has been dead for a week makes this push likely on the first run, and today nobody is told to look. Every spec whose watch file gains `main.luau` or `zn` then runs on almost every tooling change, which slows the gates the user wants fast.
Consequences: limiting the extension to a range is a design change to `applyRepairs`. A check after the run is a reporting change only.
Recommendation: escalate to the user: (a) keep the scope, and extend Implementation step 4 and Phase 6's report for this raft. Cost: one extra report item. (b) Before landing, add to this issue a bound on the repair: no watch-map extension when the range since the last pass exceeds N commits, with a line saying so instead. Cost: a design change, a new pure rule with cases, and a new guess for N. (c) Accept the push without comment, as the Non-goals now read.

### F4 [low] The exemption also switches off the reaper's "past its `./zn run` deadline" rule for everything below a net
Where: z-nile/engine/reap.luau:391 (`underNet` is in the first `continue`, ahead of every rule); Design §4 ("Nothing else is exempt: ... not a `./zn run` orphan").
Evidence: `decide` skips a process below a live net shell before it looks at `ZN_BOUNDED_DEADLINE`. A process in the net's suite that is past its own deadline, with its bounded watchdog gone and its parent alive under the net, is now kept until the net shell ends or is 4,200 s old. Before, it was stopped as "past its ./zn run deadline". In practice the net's `--time 3600` bounds this, but the reaper is the documented backstop for exactly this case.
Critique: the net shell only needs shelter from the orphan rule, which is the only rule its detached shape trips.
Consequences: a net's own live processes carry deadlines in the future, so they are not affected.
Recommendation: apply `underNet` only to the orphan branch (`and not underNet(p, byPid)` beside `ownerless`), and leave the deadline and session rules as they were. Add a pure case to a tooling reaper spec (`tests/tooling/bounded-review.spec.luau` or a new one, not the sequestered spec): a `sleep` below a net shell whose `deadline` is past by more than the grace is listed, while the same `sleep` with a future deadline is not.
Erred: z-design
Upstream: none

### F5 [low] When the net crashes before its marker, the kick prints a stack frame as the reason, with no log path
Where: z-nile/engine/watchcmd.luau:1187 (the `exited` branch prints only `watch.errorLine(log)`).
Evidence: in the F1 probe the net's log ends with stack-trace lines (`.../main:8806: in function <...>`). A Luau error in round 1 before the marker (a `takeLock` file error, a `sh.must` failure) would make that frame the kick's only stderr line, and unlike the `gone` and backstop lines it does not name the log.
Critique: the worker copies that line into the final report, and a frame does not say what failed or where to look.
Consequences: a second line leaves the spec-pinned first line unchanged.
Recommendation: in the `exited` branch, print a second stderr line, `watch-net: log at <path>`. Add a case to the non-sequestered spec of F1: a net that raises before its marker gives a kick whose stderr names the log.

### F6 [low] The guard's take-over lets two waiting nets into the section together
Where: z-nile/engine/watchcmd.luau:991 (`mutexed`: after 100 failed tries, `rmdir` then `mkdir`, and the second `mkdir`'s result is ignored).
Evidence: a net killed inside the section leaves `guard/`. Two nets started within the same 10 s both time out, both `rmdir` and `mkdir`. One `mkdir` fails, but both run the section, both read the stale lock and both write their own. The second write wins, and both nets run a suite in the same worktree, which the lock exists to prevent (F3 of design review 001).
Critique: rare, but it is the one path where the one-net rule fails open.
Consequences: a take-over that must win its `mkdir` needs a bounded retry and a way out.
Recommendation: after the `rmdir`, retry the counted `mkdir` loop once more. If it still fails, exit with `watch-net: cannot take the lock's guard <path>` (through `fail`, exit 1, which the kick reports). No case is needed beyond reading; the existing lock cases must stay green.
Erred: z-design
Upstream: none

### F7 [low] Dead helper and a comment that misstates how the lock is written
Where: z-nile/lib/watch.luau:549 (`watch.waitSeconds`, called nowhere: main.luau parses `--wait` and `--start` with a bare `tonumber`); z-nile/lib/watch.luau:590 (`lockHeld`'s comment: "nothing writes one half-way: it is linked into place whole", although `takeLock` writes it with a plain `fs.writeFile`).
Evidence: `git grep waitSeconds` finds only the definition and the prototype patch. With `--wait -5` the bare `tonumber` gives a loop of zero steps and the message "no word from the net after -5 s".
Critique: `waitSeconds` was evidently meant to validate the flags and never got wired in, and the comment justifies G7 with a fact that is not true.
Consequences: none.
Recommendation: use `watch.waitSeconds(opts["--wait"][1], default)` for both flags in main.luau's two commands, so a bad value falls back to the default. Correct the comment: the lock is written under the guard, and a torn write after a crash counts as free (G7).
