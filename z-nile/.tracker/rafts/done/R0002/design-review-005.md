### F1 [medium] c0044's implementation steps and R0002's "commit the tooling before running `migrate`" can't be followed with `tracker.sh commit`, the only commit command the prompt allows
Where: c0044 Implementation steps 1 to 4; R0002 Order & dependencies item 1 ("Commit the tooling before running `tracker.sh migrate`, and commit the migration separately"); `scripts/tracker/main.luau` `activeRaft` (line 68) and `recordAndCommit` (line 302); `tracker/templates/prompt.md` hard rule 2
Evidence: `tracker.sh commit` calls `recordAndCommit(activeRaft(), …)`, and `activeRaft` calls `store.all("raft")`, which reads every raft document through `store.find`. After step 1 (the new `docIn`), `store.find` raises `… uses the legacy document name; run scripts/tracker.sh migrate` for every directory that still holds a legacy document, and at steps 1 to 3 that is the whole repo, including `tracker/rafts/active/R0002/R0002-worktrees-by-default.md`. So the "Commit." at the end of steps 1, 2 and 3 fails. The reverse order fails too: today's `docIn` matches only `^{id}%-(.+)%.md$`, so if the executor runs `migrate` before changing the store, the old store raises `has no <id>-<slug>.md` on every migrated directory. The store change and the renames must therefore be in the same working tree whenever `tracker.sh commit` runs. That rules out a separate tooling commit before the migration. The prototype runs didn't hit this, because they were never committed (Verification logs: "reverted, never committed").
Critique: a context-free executor that follows steps 1 to 3 hits a tracker error on its first commit. It then either uses plain `git commit`, which breaks hard rule 2 (and c0005's JC1 language), or reorders the steps on its own and ignores the raft doc, or it treats this as a stop condition and escalates. The tempting fix is "commit with plain git until the migration is done", which adds a second exception to hard rule 2 and skips spend recording for those commits.
Consequences: the steps have to be reordered so that every commit sees a store and a document layout that agree. `cmd.migrate` scans directories directly and doesn't depend on the store, so it can land first. `new` must not write `<ID>.md` while the old store is live: an emergent issue filed in that window would be unreadable. The migration can no longer be a separate commit from the store change. The PR is squash-merged anyway, so the only loss is a split in the branch history, and git still records the renames as `R` in that commit.
Recommendation: rewrite c0044's steps.
1. `cmd.migrate` and USAGE, with store, `new` and templates unchanged. Commit with `tracker.sh commit --issue c0044`; the old store still reads the legacy tree.
2. `store.luau` (`docIn`, `find`, slug from frontmatter), `new` (slug validation, `<ID>.md`), `renumber` and the two templates. Then run `scripts/tracker.sh migrate` in the same tree and update the three specs' paths. Commit all of it at once with `tracker.sh commit --issue c0044`.
3. Tracker and ticket-prep skill text, checks, full gate.
In R0002's Order & dependencies item 1, replace the sentence with "the store change and the migration are one commit (the tracker CLI can read only one layout at a time)". Add a sentence that no `tracker.sh new` runs between steps 1 and 2. No spec change is needed.

### F4 [low] A plausible wave mutant, "the last member of the after set decides", survives the promoted spec and is caught only by RC1

Evidence: `for _, a in after do wave = waves[a] + 1 end` over the after set, sorted by id, is a common way to get the maximum wrong. It gives the same output as `1 + max` wherever the member with the highest id also has the highest wave. That holds in every fixture:

Only RC1 separates the two. c0045's after set is c0005 (wave 2) then c0044 (wave 1), so the mutant gives wave 2. RC1 lives in the raft's `check.sh`, which is never promoted, so after R0002 lands no permanent spec guards the formula against this regression.

Consequences: a new fixture raft adds issues and changes the fixture's issue count, but the exact outputs of the existing cases don't change if the new ids come after f0017.
Recommendation: add a raft `R0007` (`mix`) in which a higher-id member of the after set sits in an earlier wave: f0018 (`src/r`), f0019 depending on f0018 (`src/s`), f0020 (`src/t`), and f0021 depending on f0019 and f0020 (`src/u`). Extend the wave row's mutant column with "the last member of the after set decides", run it on the prototype and mark it `run`.
