### F1 [medium] `worktree <name>` resumes a branch that was deleted on origin, because the fetch never prunes stale remote-tracking refs
Where: scripts/tracker/main.luau:611 (`git fetch --quiet origin` in `cmd.worktree`), :623 (`refs/remotes/origin/{branch}` means "resume"), and :641 (`worktree-prune`'s fetch)
Evidence: The repo has `deleteBranchOnMerge: true`, and nobody sets `fetch.prune`. So every merged capture, prep or doc branch leaves an `origin/<name>` ref behind in each clone that fetched while the branch existed. `tracker.sh worktree` fetches on every call, so each clone picks up every in-flight branch. This checkout has one now: `origin/prep-inside-repo` (PR #10, merged; `git ls-remote --heads origin` no longer lists it, and it isn't an ancestor of `origin/main`). I reproduced it in a scratch clone: push `prep-x` with a commit "old prep", delete the branch on origin and locally, then `git fetch`. `scripts/tracker.sh worktree prep-x` then prints `.worktree/prep-x`, the worktree's HEAD is "old prep" (not `origin/main`), and its upstream is the deleted `origin/prep-x`. Reusing a name is realistic: a second prep round of the same raft (`prep-<slug>`, and R0002 itself had two prep PRs), or a repeated `skills-<slug>` or `capture-<slug>`. The agent then works silently on an already-squash-merged base that is missing everything merged since. Its PR carries the old commits again, and a bare `git push` recreates the deleted branch. c0005's AC1 and AC6 ("from origin/main") don't cover this, and no spec case does.
Critique: The design's "the branch exists locally or on origin → resume" is right for a live remote branch, such as the same raft on another host. With an unpruned fetch, though, "on origin" means "ever seen on origin". The tempting fix is to drop origin-only resume, which breaks the documented cross-host resume of a started raft (`R0001-<slug>` on origin, backlog on main).
Consequences: Adding `--prune` keeps cross-host resume, because a live remote branch is never pruned, and it removes stale refs for every other command in every clone. It doesn't cover a stale **local** branch left behind when landing step 4 didn't run: that branch still resumes, by design ("resume after a deleted worktree"), and its upstream then shows as `[gone]`. That case needs a decision: resume silently, warn, or refuse.
Recommendation: Use `git fetch --prune --quiet origin` in `cmd.worktree` and `worktree-prune`. When a local branch is resumed whose configured upstream no longer exists (`git for-each-ref --format='%(upstream:track)' refs/heads/<b>` prints `[gone]`), print a stderr warning naming the branch and the `git branch -D` fix, but still resume, so the documented resume keeps working. Add the author's own spec (tests/tooling, not the sequestered one) with two cases: (1) push a branch, fetch, delete it on origin, then `worktree <same name>` is cut from `origin/main` with no upstream; (2) a live origin-only branch still resumes. Record the change in c0005's Verification log.

### F3 [low] `migrate` can leave a document that its own error message says `migrate` fixes, when `migrate` doesn't fix it
Where: scripts/tracker/main.luau:360-368 (`cmd.migrate`); scripts/tracker/store.luau `find` (the "has no slug:" error)
Evidence: Scratch worktree tests. (a) A legacy `c0084-odd.md` with no frontmatter: `migrate` runs `git mv` to `c0084.md`, then `setFront` raises `has no frontmatter`. That aborts the whole run midway with exit 1, and later directories stay unconverted. A second `migrate` skips c0084 (`<ID>.md` now exists), converts the rest and exits 0. `find c0084` then says `has no slug: in its frontmatter; run scripts/tracker.sh migrate`, but running `migrate` changes nothing. (b) A legacy document with an empty `slug:` line gets the same loop: `readFront` returns `""`, which is truthy, so the slug is left alone. `find` then errors and points at `migrate` again. No real tracker document hits this (all 53 have frontmatter and a valid slug).
Critique: The error message points at a command that can't help, and the rename is committed before the frontmatter write can fail.
Consequences: Making `migrate` also fill a missing or empty `slug:` in an already-named `<ID>.md` needs a slug source, and the filename no longer has one. It is simpler to check first and fail with a precise message.
Recommendation: In `migrate`, read the frontmatter *before* `git mv`. If there is none, report `{dir}: {file} has no frontmatter` as one more ambiguous-style refusal (exit 1 at the end, directory untouched), and continue. Treat an empty `slug:` as absent: set it from the filename. Add both cases to a tooling spec.

### F4 [low] make-issue says to create the worktree in step 6, after step 2 already ran `new`
Where: .claude/skills/make-issue/SKILL.md step 6 ("start with `cd "$(scripts/tracker.sh worktree capture-<slug>)"` *before* step 2")
Evidence: An agent that works through the numbered steps in order runs `scripts/tracker.sh new issue …` (step 2) before it reads the worktree instruction. In a repo with an `origin`, the guard refuses it, so nothing is mutated. In a clone without an `origin` (the guard is off), the issue is created in the main checkout. ticket-prep, by contrast, puts the worktree first in step 1.
Critique: This is a clarity problem, not a JC1 failure, because the rule is stated and the CLI enforces it where it matters.
Consequences: none.
Recommendation: Move the worktree command into a step 0 (or the start of step 2), and keep step 6 for landing.
