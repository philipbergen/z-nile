### F1 [high] AC1's "up to `--jobs N`" passes with unbounded lanes or a hard-coded lane count
Where: parallel-runner.spec.luau (every concurrency case is a two-way rendezvous); c0049.md Rules and mutants, row "Spec files run concurrently, up to `jobs` at a time"; Scalability ("Lanes are capped at 8").
Evidence: In the prototype I replaced `lanes = math.min(jobs, #files)` with `lanes = #files`, which starts one worker per file at once and ignores `N`. Result: `14 passed, 0 failed`. The only cases with more files than jobs (`--jobs 2` with six `ONCE` fixtures) check that each file ran once, not how many ran at a time. A hard-coded `lanes = 2` passes too: no case needs three workers at once. With unbounded lanes, the full suite forks 76 Lune processes, each running git fixtures. That is the scalability trap the Design caps against, and it goes unflagged.
Critique: The listed mutant ("lanes awaited one after another") is the only one killed. The upper bound and the use of N above 2 have no case. The tempting fix is to compare wall times (banned) or to count `ps` processes (racy, host-dependent).
Consequences: A three-way rendezvous decides both deterministically. With `--jobs 2`, fixtures a, b and c each wait for both of the others. a and b start, wait for c and time out. Then c runs, finds both markers and passes, so the result is exactly `1 passed, 2 failed, 3 spec files`. With `--jobs 3`, all three pass. A correct implementation can't start c before a or b finishes, whatever the machine's speed, so neither case is flaky. The timeout case costs 1-2 s (`PICKMAN_RV_TIMEOUT=1`, like the existing serial cases).
Recommendation: Add `at most N specs run at once, and N above 2 is honoured` with the two runs above (`RENDEZVOUS` generalised to a list of others). Add the Rules row "at most `jobs` workers at once" with the mutants "one lane per file" and "hard-coded 2 lanes". Optionally put the rendezvous cases in their own spec file so the about-7 s file runs in a separate lane (round 1's F8 split suggestion).

### F2 [medium] par-stages still doesn't run under `set -euo pipefail` (repeat of review-001 F11), so a row claims a kill that doesn't happen
Where: par-stages.spec.luau `sh()` (`{ "-c", "source scripts/lib/par.sh\n{script}" }`, with no options); c0049.md Rules and mutants, last par row ("all `par-stages` cases (run under `/bin/bash` with those options …)"); design-refute-001 F11 ("fixed: the `par-stages` cases run under `set -euo pipefail`").
Evidence: The spec text is unchanged. I added two bash traps to the prototype: `(( _par_n++ ))` on an unset counter in `par_start`, and `for x in "${_par_files[@]}"` after the reset in `par_wait`. par-stages passed 8/8. The same library under `set -euo pipefail` dies on the first `par_start` with `_par_n: unbound variable`, rc=1. AC4 would catch the `par_start` trap through the real gate. The empty-array-after-reset trap (bash < 4.4 under `set -u`) is never reached by check.sh's single batch, but a second batch or an empty batch would hit it on macOS.
Critique: The refutation records a fix that wasn't made, and the table claims a kill on that basis.
Consequences: The cases already put a failing `par_wait` last or after `||`, and the `[ -e … ] && …` lines are exempt from `-e`, so adding the options changes no outcome for a correct library. A correct library must then avoid `((n++))` and bare empty-array expansion, as the Design already says.
Recommendation: Change `sh()` to `{ "-c", "set -euo pipefail\nsource scripts/lib/par.sh\n{script}" }`. Add a case where `par_wait` on an empty batch returns 0 and prints nothing, followed by a second `par_wait` after a reset. Re-run par-stages against a correct prototype to confirm it stays 8/8 (mine does: the prototype uses `${#arr[@]}` indexing only).

### F3 [medium] The coordinator's output shape is unpinned: repeated worker summaries and an uncapped `slowest:` pass
Where: c0049.md Merge ("print the rest of its stdout (the `FAIL ...` lines)"), Output ("up to 3"), Usability ("a failing spec prints exactly the `FAIL` lines it printed before"); parallel-runner.spec.luau.
Evidence: Prototype mutant `keepsummary` re-prints each worker's whole stdout, including its `1 passed, 0 failed, 1 spec files` line: 14/14 pass. A full-suite run then prints 76 summary-shaped lines before the real one. Nine check.sh files (c0005, c0006, c0007, c0008, c0034, c0038, c0044, c0045, c0046) grep `^[0-9]+ passed, 0 failed, 1 spec files$` anywhere in the output, not on the last line. Today they run single files (in-process), but the first multi-file check written in that style reads a passing worker's line as success. A `slowest:` line listing every file also passes every case and RC1, because only "slow before fast" with two files is checked.
Critique: The summary line is the interface the raft says it keeps fixed, and its uniqueness is part of that interface.
Consequences: A dead worker's last 25 lines may themselves contain a summary (the `c-liar` fixture prints one), so "exactly one summary-shaped line" holds only if the Design says how that tail is printed.
Recommendation: In the Design, state that a dead worker's tail lines are indented by five spaces, like a case's error line, so the only line starting `<P> passed,` is the final one. In the spec, assert in the 3-file failing case and in the 6-file `ONCE` case that exactly one line matches `^%d+ passed, %d+ failed, %d+ spec files$`. In the 6-file case, assert that the `slowest:` line has exactly three `.spec.luau` entries. Add Rules rows for "worker summaries are not re-printed" and "`slowest:` lists at most 3", with the two mutants above.

### F4 [medium] spec-isolation becomes a permanent gate spec with a known false-positive class and an unreadable failure
Where: spec-isolation.spec.luau (`collect` over `tests` and `tracker`; literal `.cache/<dir>` text claims a directory; `t.expect(found).toEqual({})`).
Evidence: (a) Any literal mention claims the directory, even read-only, in a comment, or about another spec. The spec itself has to build its own test strings by concatenation to avoid tripping itself. A future chore whose acceptance spec checks another spec's fixture (c0006, "lifecycle spec clone isolation", is the obvious candidate, about `.cache/tracker-e2e`), or two specs that mention `.cache/check.rbxl`, turns main's gate red the moment its prep lands. That happens even though prep specs under `tracker/` are never run by the gate. (b) When it fires, the message is useless. In my promotion run, a stale copy tripped it and printed `expected deep-equal values, got table: 0x00000007e72866e0`, with no directory and no file names, although `sharedDirs` builds exactly that text.
Critique: The guard is right in spirit (the parallel runner makes shared dirs a real race). But nothing tells the next spec author the rule they must follow to avoid it, and when it fires it doesn't say why.
Consequences: Scanning only `tests/` would move detection to after `tracker.sh done`, where the colliding spec is sequestered and only an escalation can fix it. So keep scanning `tracker/`, and make the rule known instead.
Recommendation: Print the collisions: `t.expect(table.concat(found, "; ")).toBe("")`. In the testing skill's new `## Speed` section, state that literal `.cache/<name>` text in a spec claims that directory, that each spec file owns a unique one, and that a reference to another spec's directory is built by concatenation. Add those words to AC7's grep list (for example `.cache/`), so the rule can't be left out.

### F5 [low] The Speed rule as written forbids what the new specs do (partial repeat of review-001 F8)
Where: c0049.md Speed rule ("writing specs for speed: no sleeping or polling on wall-clock time"); testing skill "Good specs" ("no wall-clock time", the only exception being `sim.bench`); par-stages `quick < 1.5` and `napping >= 2`; parallel-runner `RENDEZVOUS` and `SLEEP1`.
Evidence: design-refute-001 answers that "the Speed rule forbids wall-clock *assertions*, not bounded waits". The Design text wasn't changed and still says "no sleeping or polling", and par-stages asserts on elapsed wall time. These specs become `tests/acceptance/c0049`, the example the next author will copy, and they contradict two written rules.
Recommendation: Word the Speed bullet as the refutation describes: no wall-clock assertions or sleeps, except in specs of concurrency or timing infrastructure, which use bounded rendezvous waits and margins of at least 1 s. Name that as the second timing exception next to `sim.bench` in "Good specs".

### F6 [low] `par.sh`'s temp files aren't required to be unique per run, and parallel worktree gates are routine here
Where: c0049.md Gate stages ("stdout+stderr go to a temp file").
Evidence: The workflow runs several worktree streams at once, plus the stop hook's `check.sh --affected`. A `par.sh` that writes `${TMPDIR:-/tmp}/par-<n>.log` (a natural bash 3.2 choice) passes every par-stages case and AC4/AC5. Two concurrent gates then print each other's stage output under their own headers, or delete each other's logs.
Recommendation: State in the Design that each stage's output and timing files come from `mktemp` (or live under the gate's own repo `.cache`), and that they are removed by `par_wait`. No spec is needed: it's a one-line design rule, and a reviewer can read for it.

Verdict: changes
