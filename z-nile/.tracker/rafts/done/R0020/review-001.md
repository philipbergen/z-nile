### F1 [medium] Emergent issues still take their id from the local tree only, so they collide with ids published on origin, which is the problem c0053 exists to fix
Where: scripts/tracker/main.luau:349 (`store.formatId(prefix, store.nextNumber("issue"))` on the local path); scripts/tracker/store.luau:121 (`store.nextNumber` is unchanged; the raft's module map says "nextNumber delegates")
Evidence: In this worktree the highest local issue is c0060, and origin/main (27feded) already has f0061. `scripts/tracker.sh new issue c foo --raft R0020` here would create `tracker/issues/active/c0670`, which shares number 670 with f0061. If another terminal publishes a `c` issue first, the clash is a same-prefix duplicate. When the raft PR merges, `tracker/issues/c0670/` and `tracker/issues/done/c0670/` both exist on main and `tracker.sh list` fails on the duplicate id. Long rafts and many parallel terminals make this likely.
Critique: The tempting fix is to allocate from the union of local and origin/main ids, which needs only a fetch and `ls-tree`, with no publish. That alone does not hold. The emergent id becomes origin max + 10, which is exactly the id the next published `new issue` in any other terminal will take, because nothing on origin reserves it. The other tempting fix is to publish the stub as a normal backlog `new` item. Then the raft branch's copy in `active/` and origin's copy at the backlog path merge as two directories with one id, and another terminal could claim the issue into a different raft.
Consequences: Reserving the id means publishing something for emergent issues, which changes the design rule "emergent issues are not published". It also needs: a member of an active raft that does not appear in origin's `issues:` list; a give-back (`status <R> prepared`) that must not strand it; and an abandoned raft that leaves an orphaned reservation.
Recommendation: This is a design change, so the author escalates (execute-raft stop condition): the user decides between (a) shipping as is with the gap stated under R0020 Risks and a follow-up chore, or (b) this design. On an `origin`, `new issue --raft <active R>` publishes the stub at the backlog path. The stub carries `raft: <R>`, `emergent: true` and an `active-<stamp>`, so `new raft` refuses it ("already belongs to") and `status` lists it as active. Then the command runs `mergeOrigin()` and `git mv`s the stub into `active/`, the pattern E3 already proved merges cleanly. Offline (`PICKMAN_PUBLISH=0`) it stays local as today. Spec cases: the emergent id is above origin's highest id; a second terminal's `new issue` after it gets the next id; the merged PR leaves one directory per id. Either way, make `store.nextNumber` take the extra ids, or remove that line from the module map, so the design and code agree.

### F2 [medium] The repo-root guard passes when `GIT_DIR` is inherited, so a writing command can still act on, and publish from, another repository
Where: scripts/tracker/main.luau:130 `guardRepoRoot` (compares `git rev-parse --show-toplevel` with `pwd -P`)
Evidence: Scratch run under `$TMPDIR`: repository `A`, plain directory `B`, and `cd B && GIT_DIR=A/.git git rev-parse --show-toplevel` prints `B`, the same as `pwd -P` in `B`. The guard passes, and every git call that follows (`fetch`, `commit-tree`, `push origin`, `merge`, `worktree add`) goes to A and A's origin. git exports `GIT_DIR` to hooks in linked worktrees and during clones (R0021 c0058 E26), and c0058 names "an inherited `GIT_DIR`" as one of the ways a spec reached the real repository. Until R0021 lands, only specs get their environment stripped. A tracker command run from a hook or a script that inherited the variable has no guard.
Critique: The tempting fix is `unset GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE` in `tracker.sh`. R0021's gate scans `scripts/` for those names, so that needs an allowlist entry. It also silently retargets a caller who set `GIT_DIR` on purpose.
Consequences: A refusal is safer than a silent retarget, but any check that names the variables collides with R0021's name scan (c0058's `ALLOWED` table) unless the names are built at run time, as AC9's `check.sh` already does.
Recommendation: In `guardRepoRoot`, for non-read-only commands, also refuse when the repository git resolves (`git rev-parse --absolute-git-dir`) differs from the one discovered without the override variables. Run the second probe through `env -u` with the names built at run time, so R0021's scan needs no entry. Add a commands-spec case: the lost-`.git` fixture run with `GIT_DIR` pointing at the outer repository's `.git`, where every writing command refuses and origin's main is unchanged. If the user prefers to keep R0020 as designed, record the gap under R0020 Risks and hand it to R0021 (c0059 already makes the publisher refuse inside protected repositories). Ask the user before filing anything new.

### F3 [low] A `start` whose push lands but reports failure locks this terminal out of its own claim and deletes the evidence
Where: scripts/tracker/main.luau:868-891 (`mine` is read before the publish; the build skips only `raw == mine`; after a refusal the claim file is removed when `mine == ""`)
Evidence: A first `start` writes `claim` to `.cache/tracker-claim-R`. Attempt 1's push updates origin, but git exits non-zero (the connection drops after the remote accepted the push). Attempt 2 fetches, and the build sees `raw == claim`. That does not equal `mine` (`""`), so the build returns `R is active on origin/main, not prepared`. `publish.commit` fails, the claim file is removed, and origin now says `active-<claim>` with no terminal holding it. A re-run is refused too. The documented property is that a start which died right after its push can be finished.
Critique: The tempting fix is to also skip `raw == claim` in the build. On its own, that makes the in-process retry return `{}`: `r.ok` with no sha, and the restore branch then deletes the file again (because `mine == ""`).
Consequences: The file-keeping rule must become "keep the file when origin holds `claim` or `mine`", not "keep it when a sha came back".
Recommendation: In the build, treat `raw == mine or raw == claim` as ours. After the publish, keep `.cache/tracker-claim-R` set to `claim` when the build saw only our own stamps, restore `mine` when the publish was refused by another terminal's value, and remove it otherwise. Spec case: a `git` wrapper on `PATH` that runs the real push and then exits 1. The next `start` in the same worktree must resume, and another terminal must be refused.
