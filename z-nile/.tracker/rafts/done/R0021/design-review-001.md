### F1 [high] The fence has three verified holes: cwd = `.cache` itself, inherited `GIT_DIR`/`GIT_INDEX_FILE`, and mutating commands at the real root
Where: c0058 Design, "Runner guard" step 3 and "Audit of every check"; prototype `tests/lib/fence.luau:97-109`
Evidence (scratch repo `real/` with `GIT_CEILING_DIRECTORIES=<real>/.cache`, git 2.54):
- With cwd `<real>/.cache` (the ceiling itself, not a folder below it), `git rev-parse --git-dir` printed `<real>/.git`. A ceiling only stops git from moving *up into* a listed directory. Any fixture path built from an empty name (`.cache/` .. "") or a `cd .cache && git …` therefore still reaches the real repository.
- If `GIT_DIR=<real>/.git` is inherited, a fixture that **has its own `.git`** resolves to the real git directory (`git rev-parse --absolute-git-dir` printed `<real>/.git`). An inherited `GIT_INDEX_FILE=<real>/.git/index` made a fixture's `git add f` stage `f` into the real index (`git -C real ls-files --stage` listed it). Git exports these to hooks (githooks(5): "GIT_DIR, GIT_WORK_TREE, etc. are exported"). So a pre-commit or pre-push hook that runs `scripts/check.sh` (the obvious next step for this workflow) or `git rebase -x scripts/check.sh` would point every fixture at the real repository. The runner neither unsets these variables nor refuses to run when they are set. The gate spec only forbids a spec from *naming* them.
- Commands run with `cwd = root` or `git -C <root>` are not fenced at all. c0034 runs `tracker.sh done R9999` and `tracker.sh check c0010` at the real root, and its safety rests on `done`'s own `AC_LIST` refusal, which is code under test. If that guard regresses, a mutating tracker command (`done` pushes and runs `git reset --hard HEAD` on failure) runs against the real repository. Only the narrow tripwire would notice, and only afterwards.
Critique: The audit concludes "That is the hole closed here", but the closed hole is only upward discovery from a folder *below* `.cache`. The tempting fix is to add the three variable names to the gate-spec grep. That polices the spec text, not the environment the runner inherits, and it does nothing for cwd = `.cache` or for the real root.
Consequences: The runner must clean its environment. Lune's `env` option can only add variables, and an empty `GIT_DIR` breaks every git call (verified: `fatal: not a git repository: ''`), so the re-run has to go through `env -u NAME … lune run tests/run`. `env -u` works on macOS and on GNU, and R0014's review already relied on it. Blocking ref writes at the root at runtime (see F2) also needs a git hook path and a cost measurement.
Recommendation:
(1) The top-level re-run strips `GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE GIT_COMMON_DIR GIT_OBJECT_DIRECTORY GIT_ALTERNATE_OBJECT_DIRECTORIES GIT_NAMESPACE GIT_PREFIX` with `env -u`, and the snapshot runs only after they are stripped.
(2) `fence.enter` writes a sentinel file `<checkout>/.cache/.git` containing `gitdir: /nonexistent/pickman-fence`. Verified: git in `.cache` itself then fails with `fatal: not a git repository`, while `.cache/<x>` fixtures with their own repository still work. `.cache` is ignored, so root `git status` is unaffected.
(3) Add c0058 acceptance cases: a probe running git with cwd `<here>/.cache` fails; a top-level run started with `GIT_DIR=<repo>/.git` and `GIT_INDEX_FILE=<repo>/.git/index` leaves a probe fixture (own `git init`) resolving to its own git dir and its own index; and repo-fence case 1 asserts that those variables are unset in the fenced run.
(4) Add Rules-and-mutants rows for each, with the mutants "no `env -u`" and "no sentinel".
(5) Run c0034's real-root tracker calls in a fixture clone, or record this in the testing skill as the single sanctioned exception, with its reason, so the review rule's "any path is high" doesn't fire on it every round. That is a promoted-spec change: name it on an `Overrides:` line (F9).

### F2 [high] Fixture clones of the real checkout keep a push path into it, and nothing fences or detects ref writes
Where: c0058 "Audit" (fixture specs c0001, c0008, c0038, c0006 clone *from* the root); "Runner guard" step 2 (the snapshot has no refs)
Evidence: c0008 and c0038 run `git clone --no-hardlinks <root> <work>` and only *then* `git remote remove origin` (c0038 `deferred.spec.luau`, setup case), so for a while the fixture's `origin` is the real checkout. The runner keeps running later cases after a setup case fails, so if the removal fails, later cases run `tracker.sh` in the fixture, and `tracker.sh` pushes (`main.luau:65`, `:446 push -u origin <branch>`). In scratch, `git push origin HEAD:refs/heads/pushed` from a clone of `real/` created branch `pushed` in `real/`. The ceiling plays no part, because git finds the fixture's own repository. The tripwire doesn't cover `refs/heads`, so a run like this ends green. This is the incident's "fixture branches `collide-a` and `inflight` registered in the real repository" symptom, and the design neither prevents nor detects it.
Critique: The design leaves branches out of the snapshot on purpose ("other sessions' pushes change `branch.*`"), and that is right for config. It leaves ref damage both unguarded and invisible. The tempting fix is to snapshot all of `refs/heads`, but every concurrent `tracker.sh launch`, commit or push in another session would then trip it.
Consequences: Any ref check has to tell fixture refs from legitimate ones. Fixtures commit as `e2e@example.invalid` or `t@example.invalid`, which is a clean discriminator. A runtime ref fence through `core.hooksPath` changes the hook path of every fixture repository too: confirm that no spec relies on fixture hooks, and measure the per-transaction cost.
Recommendation:
(a) `clone.isolated` (and the scan c0006 already has for root clones) makes push impossible from the start: `git clone -c remote.origin.pushurl=/nonexistent/pickman-no-push …`, or the helper removes `origin` itself. Every clone of `root` must go through the helper. That changes promoted specs c0008, c0038, c0001 and c0006, so they go on an `Overrides:` line (F9).
(b) Widen the tripwire with what only an escape can produce: local `user.*` config (the first thing every fixture writes is `git config user.name e2e`) and any `refs/heads/*` whose tip's author email ends in `@example.invalid` (`git for-each-ref --format='%(refname) %(authoremail)' refs/heads`).
(c) Optionally, and as the strongest guard, give the fenced child a ref fence: `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.hooksPath GIT_CONFIG_VALUE_0=<checkout>/tests/lib/git-hooks`, with a `reference-transaction` hook that exits 1 in the `prepared` phase when `git rev-parse --path-format=absolute --git-common-dir` is the real common dir. Verified in scratch: it refused `commit`, `branch`, `switch -c` and `worktree add` in the real repository, and a fixture's own commit still worked. It did **not** stop the local push, because local transport drops `GIT_CONFIG_*`, so (a) is still needed. If adopted, add `GIT_CONFIG_COUNT`, `GIT_CONFIG_PARAMETERS` and `GIT_INDEX_FILE` to the gate-spec name list.
Spec cases: a probe that pushes from a clone of the probe repository into it is refused or fails the run; a probe that creates a branch authored `e2e@example.invalid` in the repository fails the run; a probe that sets `user.email` in the repository fails the run.

### F3 [high] c0058's own acceptance spec rebuilds the incident mechanism, and is exempt from the scan
Where: `tracker/issues/c0058/acceptance/fence.spec.luau:71` (`run()` sets `GIT_CEILING_DIRECTORIES = ""`), probes `remote`, `head`, `nested-worktree` (lines 118-123)
Evidence: Each inner run starts with the outer fence cleared, so its only ceiling is the inner `<repo>/.cache`. The destructive probes run `git remote add escaped`, `git switch -c escaped` and `git worktree add` with `cwd = here`, the fixture root, which is **not** below the inner ceiling. If `.cache/c0058-fence/repo/.git` disappears during the run (a person wiping `.cache` while a background gate runs, a future spec cleaning `.cache`, or R0014's concurrent workers once any spec touches that path), git walks `repo → c0058-fence → <root>/.cache → <root>`. The probes then add a remote to the real repository, switch the real worktree's branch, and register a worktree in it. That is the 2026-09-30 sequence, in the one spec the gate scan exempts.
Critique: The spec clears the ceiling to imitate a person's shell. Clearing only the marker would imitate a top-level run just as well.
Consequences: The "keeps an existing one" case then has to test appending to the outer value rather than `/some/where` alone. Nothing else changes.
Recommendation: `run()` clears only `PICKMAN_TEST_FENCE`, and passes `GIT_CEILING_DIRECTORIES = <inherited>` (or `<inherited>:/some/where` in the "existing value" case). The escape probe keeps its power: without the inner fence, a probe in `repo/.cache/probe/sub` finds the fixture's `repo/.git`, which is below the outer ceiling. Add a guard line to every destructive probe: `assert(git rev-parse --show-toplevel == here)` before acting. Add a rule to the testing skill: no spec may clear the inherited ceiling, the exempt files included.

### F5 [medium] The lock can be lost while its run continues, and stale takeover is racy
Where: c0058 "Runner guard" step 1; prototype `fence.luau:56-85`
Evidence:
- The lock records only the top-level Lune pid, but the specs run in the re-run child and its workers. Verified in scratch: a Lune script blocked in `process.exec` was sent SIGTERM; the parent died and its child process **stayed alive**. A harness timeout, `timeout(1)`, `kill <pid>` or `perl -e 'alarm …; exec'` (the pattern `run-lane-error.spec` already uses) leaves an unlocked orphan suite running. The next run sees a dead pid, takes the lock over, and two suites share the fixtures again: the incident's trigger. The orphan has the marker, so it never runs a tripwire.
- Takeover is check-then-act. Waiters A and B both read the same dead pid; A runs `removeDir` and then `mkdir`, and starts; B's `removeDir` then deletes A's fresh lock, and B's `mkdir` succeeds. Both run.
Critique: The tempting fix is to shorten the window. Neither problem is a window: the first is a lock that names the wrong process, the second is a missing compare-and-swap.
Consequences: Recording the child's pid needs the child to know it holds the lock. It does: it has the marker and the lock dir exists.
Recommendation: The fenced child writes its own pid to `<lock>/child` first thing, and a lock counts as stale only when every pid recorded in it is dead. Take over by atomic `rename(lock, lock.stale.<mypid>)`, which only one waiter can win; the winner then reads the renamed dir's pid, and if it is alive (a fresh lock was stolen) renames it back and keeps waiting. Spec cases: a parent killed with SIGTERM while its child runs, then a new run waits (no takeover); two waiters on one stale lock run one at a time (rendezvous files, no sleeps).

### F6 [medium] The tripwire trips on legitimate work and orders the agent to stop
Where: c0058 "Runner guard" step 2 and "The snapshot is deliberately narrow"; R0021 Risks ("changes only by hand or by an escape")
Evidence: The HEAD label includes `git rev-parse HEAD` of this checkout. An agent that runs the gate in the background (the Speed section asks agents to monitor long runs) and meanwhile commits, pulls or merges `origin/main` in the same worktree moves that sha. The run then fails with `REPOSITORY CHANGED … Stop and report this`, and the execute-raft stop condition halts the raft. `remote.*` also changes legitimately: `gh repo set-default` or a base-repo prompt writes `remote.origin.gh-resolved`, and the user's own repair of `origin` in another session counts too. The Risks section's "changes only by hand" is false for this checkout's HEAD.
Critique: The tempting fix is to drop the sha. That would also drop detection of a fixture committing onto the real branch.
Consequences: The check has to tell a legitimate commit from an escaped one.
Recommendation: Keep the symbolic ref exact. For the sha, fail only when the new HEAD doesn't descend from the old one, or when a new commit (`git log old..new --format=%ae`) has an `@example.invalid` author. Compare `remote.*` without `*.gh-resolved`. Spec cases, inside the probe repository: a probe that commits with a non-fixture identity passes; a probe that commits as `e2e@example.invalid` fails; a probe that runs `git reset --hard HEAD~` fails.

### F7 [medium] Any non-empty `PICKMAN_TEST_FENCE` switches off the lock, the fence and the tripwire
Where: c0058 "A run with the marker … neither locks nor re-runs"; prototype `fence.luau:88-91`
Evidence: `fence.enter` returns as soon as the marker is non-empty. It never checks that `GIT_CEILING_DIRECTORIES` contains `<marker>/.cache` or that `pwd -P` is inside `<marker>`. A marker that leaks into a shell, or into a script that starts a run in another checkout, makes every later targeted run (`tracker.sh check`, `check.sh --affected`, `lune run tests/run -- x`) unfenced and unlocked. `repo-fence` case 1 catches this only in runs that include `repo-fence`, which affected and targeted runs often don't.
Critique: The marker is meant as a cheap "already fenced" proof, but it carries no proof.
Consequences: Nested runs in fixture copies under `<marker>/.cache/...` must still count as nested. They do, because their cwd is under the marker.
Recommendation: Accept the marker only if `pwd -P` is at or below its value and the ceiling list contains `<marker>/.cache`. Otherwise behave as a top-level run and print a one-line note. Case: a run started with `PICKMAN_TEST_FENCE=/bogus` still locks and fences (the escape probe fails to escape, the lock dir appears).

### F10 [medium] The rule's wording promises more than the runner enforces, and the gate itself breaks it
Where: AGENTS.md paragraph and testing-skill section (prototype diff); review skill items 9 and 8
Evidence:
- The testing text makes "every file outside `.cache/`" off limits. But the gate writes `sourcemap.json` at the root (`rojo sourcemap … -o sourcemap.json`), and R0021's own RC0 runs `tracker.sh promote-check`, which writes `tests/acceptance/<id>` into the real tree and removes it afterwards.
- AGENTS.md says the runner "fails any run during which the repository changed". It compares only remote and core config, this checkout's HEAD, and worktrees under `.cache`.
- The review rule makes "any path to the real repository" **high** but doesn't say which paths are enforced and which only reviewers can catch: real-root commands (F1), fixture remotes (F2) and non-git file writes (a stated non-goal).
Critique: A reviewer handed an overclaiming rule either flags the gate itself every round, or trusts the runner for things it doesn't check. The user asked for the rule to be *clear*.
Consequences: The writers the rule allows have to be listed and kept current.
Recommendation: Define the protected object precisely: the shared git directory (config, refs, HEAD, index, worktree registry) plus tracked working-tree files. Name the sanctioned writers (`sourcemap.json`, `.cache/*`, and `promote-check`'s transient copies, or move those copies under `.cache`). Split the section into "enforced by the runner" (each guard, with exactly what it covers) and "only review catches" (cwd at the real root, `-C <root>`, remotes pointing at the root, non-git writes), and point review items 8 and 9 at the second list.

### F11 [low] Lock waits outlast the Stop hook, and some test details are fragile
Where: `.claude/settings.json` Stop hook (`timeout: 300`) vs `PICKMAN_TEST_LOCK_WAIT` default 900; fence spec stale-lock case; R0021 RC1
Evidence:
- When a background suite holds the lock, `scripts/hooks/stop.sh` waits past its 300 s budget and is killed, so the agent stops with no gate result and no message.
- The stale-lock case uses pid `999999`, which can be live on Linux CI (`pid_max` up to 4194304).
- RC1's snapshot omits refs, so it wouldn't see the incident's leaked branches.
Recommendation:
- `stop.sh` exports `PICKMAN_TEST_LOCK_WAIT=240` and turns "gave up" into a blocking message (exit 2) that says another run holds the checkout.
- Get a certainly-dead pid by spawning `sh -c 'echo $$'` and using that pid after it exits.
- Give RC1's snapshot the same fixture-identity ref check as F2(b).
