### F1 [high] (repeat of review-001 F3) c0058's own acceptance spec has already written into the shared repository, because its destructive git calls have no guard of their own
Where: `tracker/issues/c0058/acceptance/fence.spec.luau` lines 295-359: the `during` callbacks, and the restore calls `git(repo, {"config","user.email",…})`, `reset --hard`, `commit-tree`/`update-ref`. These run in the spec process itself, not in a probe. Same for `lock.spec.luau` setup. execute-raft "Tests first" step 2.
Evidence: the shared repository holds exactly what this spec writes, at 07:41-07:42 today, which is before the v2 guards were committed (`f9c7b40`, 07:45:51):
- The `prep-check-isolation` reflog shows `db86c64 commit: dev` at 07:41:38 (author `dev@example.com`) and `a4e746e commit: a fixture commit` at 07:41:59. Both are the spec's line 309-319 and line 331 commands, and both are now ancestors of the commit under review, `7079c9c`. The prep PR would carry them to main.
- `refs/heads/leaked` (`895af14`, message `leaked`, line 347-348) exists in the shared repository.
- The shared `.git/config` has `user.email=e2e@example.invalid` (line 299, or `runnerRepo` line 77). Every commit in every worktree since then is authored as a fixture (F2).

The spec's comment says inner runs are "double-guarded". That holds only once the implementation exists. Each `git(repo, …)` the spec makes itself is protected by nothing but `repo/.git` being present, plus whatever guard the runner executing the spec happens to have. execute-raft requires running the sequestered specs on main's unguarded runner first ("confirm that each one fails"), and then iterating on a half-built `fence.luau`. Any moment where `repo` exists without its `.git` sends these commits, resets and config writes to the checkout: a setup case that failed after `fs.writeDir(dir)` and before `git init` (the runner continues with later cases), or a second copy of the spec re-running `fs.removeDir(base)` + `runnerRepo`. I re-ran the spec on main's runner in a scratch clone of `7079c9c`, and nothing escaped there. So the event needs a missing `.git` as the trigger, which is the incident's own mechanism. The prep record (E6, E10, RC1 "repository unchanged") doesn't mention any of this.
Critique: Review-001 F3 asked for a guard line before every destructive step, and the refute replaced that with "the outer guards stay". The tempting fix again is "run it only with the guard in place". That can't be enforced: the acceptance spec exists to be run before the guard exists.
Consequences: the spec has to be safe by itself, on any runner, including the runner on `main` today. Its helpers then name `GIT_CEILING_DIRECTORIES`, which they may (c0058's specs are exempt from the scan). The `user`/`remote` restore steps must be guarded too, because they are the ones that rewrote the shared identity.
Recommendation:

They also go through a helper `inRepo(dir, args)` that first asserts `git -C dir rev-parse --path-format=absolute --git-common-dir` equals `physical(dir)/.git`, and raises an error without running anything otherwise. No raw `process.exec("git", …)` with `cwd = repo` remains.
(2) Add experiment E12 to Unknowns: on main's runner (no guard), in a scratch clone, run fence.spec with `repo/.git` removed just before the `during` callbacks (a probe that deletes it). The clone's HEAD, refs and config must be unchanged, and the cases fail on their assertions. Add a Rules-and-mutants row "the spec's own writes are fenced", with the mutant "helper skips the check".
(3) Record the 2026-10-01 escape in c0058's Problem section as a second occurrence. Add to R0021 Order & dependencies a precondition that the user decides the repair (F2) before execution. Remove `db86c64` and `a4e746e` from the prep branch before the prep PR. That is a history rewrite of this branch, so it is the user's call; the alternative is a squash merge that drops them.

### F2 [high] The tripwire's only discriminator, `@example.invalid` means "a fixture wrote it", is false in the repository as it is now, so every concurrent commit trips every run
Where: c0058 "Run guards" step 2 (fixture-written refs) and step 4 (HEAD gained fixture commits); R0021 RC1 snapshot; gate spec case 5
Evidence: `git config --local --list` in the shared repository shows `user.email=e2e@example.invalid` (F1). As a result:
- `7079c9c`, `3944ccd`, `406d820`, `56845d0`, `3ae5625`, `f9c7b40` and another session's `dce0940` (prep-publish-state-to-main, R0020) are all authored `e2e@example.invalid`.
- `git for-each-ref` lists `prep-check-isolation`, `prep-publish-state-to-main`, `proto2-c0058` and `leaked` as fixture-written.
- `snapshot()` keys those refs by `refname objectname`. When any session commits on such a branch during a run, a new key appears, and the run ends `REPOSITORY CHANGED … refs written by a fixture appeared`.
- A commit in the running checkout ends with "HEAD gained commits written by a fixture".
- execute-raft's new stop condition then halts the raft. Real escapes become indistinguishable from normal work.
- Nothing in the design notices the bad identity: the tripwire compares only before against after, and the gate spec polices only source files.

This is not a one-off. Any future escape that writes `user.email` (the incident did) silently turns the discriminator off for every session.
Critique: The tempting fix is "the user repairs the config by hand" (a Non-goal). That repairs today and leaves the next escape just as invisible, with every tripwire firing falsely until someone notices.
Consequences: the runner needs a precondition about the repository it protects, checked before any spec runs, and with a message that doesn't invite self-repair (the execute-raft rule).
Recommendation:
(1) `fence.enter` (top-level only, after the lock) fails before running any spec when the shared repository's local config has a `user.email` ending in `@example.invalid`, or has any `user.*` key at all. The project keeps identity in global config, so a local one can only come from a fixture. The message is `REPOSITORY ALREADY CHANGED: … Stop and report`.
(2) Add a case `fence :: a run in a repository whose own identity is a fixture's refuses to start`, with the mutant "no precondition".
(3) R0021 gets an explicit prerequisite: before execution the user removes the local `user.*`, `refs/heads/leaked`, and the two test commits (F1), and decides about the e2e-authored commits already on `prep-publish-state-to-main` and `proto2-c0058`. Otherwise RC1 and the AC3 cases are measured against a broken baseline.
(4) The testing skill's "If the tripwire fires" adds this message.

### F3 [high] (repeat of review-001 F10) The "enforced at run time" list claims more than the ref guard does, and the "caught only by review" list is missing the cases where it falls short
Where: c0058 Environment guards step 3 ("commit, branch, switch, reset, update-ref, worktree add…"); prototype testing skill, "Ref guard … covers commit, branch, switch, reset, worktree add and fetch"; "Caught only by review" list; review skill items 8/9
Evidence (scratch repo with the prototype's hooks injected exactly as `fence.sh` does):
- `git switch other` and `git checkout --detach other` (clean tree) and `git reset --hard other` are each "refused", but the index and working tree were already rewritten to `other` (`f=b`, `g=new` staged) while HEAD stayed on `main`. `git reset --hard HEAD` was "refused" after it had already thrown away the uncommitted change to `f`. The tripwire sees none of this: branch and HEAD are unchanged. In the incident, the agent's next `git add -A && commit` would have committed the fixture branch's tree.
- Not refused at all: `git worktree remove --force ../W` (another worktree and its files deleted), `git worktree prune`, `git remote set-url`, `git branch --set-upstream-to` (`branch.*` is outside the snapshot).
- `git remote rename origin o2` fails with the hook's error, yet the rename **was applied** (`git remote` printed `o2`). `remote remove` and `stash` were stopped cleanly.
- The review list names `reset --hard` and `checkout -- <path>`, but not `switch`/`checkout <branch>`/`merge`/`rebase`/`restore` at the root, `worktree remove|prune|move`, nor `-C <root>` and `--git-dir`. The scan forbids `GIT_DIR` but not its flag form `--git-dir`, which c0008 uses legitimately.
Critique: the user asked for the boundary to be clear. A reviewer reading "switch … enforced" will approve a spec that runs `git switch` at the root, and the result is a silently corrupted worktree with a green run. The tempting fix is to make the hook stricter. No hook runs before checkout rewrites the tree (`post-checkout` and `post-index-change` run after), so the hook can't fix this.
Consequences: the docs must describe the ref guard as damage limitation for refs only. Everything else that a command at the root can do is review-only. AC8 has to pin that wording, or it will drift back.
Recommendation:
- Rewrite the Ref guard bullet as: "refuses the ref update itself. A command that changes files first (switch, checkout, reset --hard, merge, rebase, restore) may already have rewritten the index and working tree, and config writes (remote set-url and rename, `branch.*`, `config`) and worktree registry changes (worktree remove, prune, move) are not refused."
- Add those commands, `git -C <root>`, `--git-dir`/`--work-tree` pointing at the checkout, and `worktree remove|prune|move` to "Caught only by review", in the design, the testing skill and review items 8/9.
- Extend AC8 to grep the review list for `worktree remove` and `switch`.
- Optionally, for detection, let the snapshot also record `git worktree list --porcelain` paths outside `.cache` whose directory still existed at the start. The run then warns, without failing, when one disappears. Concurrent sessions remove worktrees legitimately, which is why this should only warn.

### F4 [medium] The ref guard breaks a legitimate check pattern the audit missed: fetch at the root, as in `scripts/ci-verify.sh`
Where: c0058 Audit, "`check.sh` files: none writes git state"; `tracker/issues/done/c0001/check.sh:12` (`AC3: CI green for this branch's exact HEAD` runs `scripts/ci-verify.sh`, which runs `git fetch -q origin "$branch"`)
Evidence: in scratch, `git fetch -q origin main` under the injected hook exited 128 ("update aborted by the reference-transaction hook"). `refs/remotes/origin/main` stayed stale, and FETCH_HEAD was still written. Under `ac.sh`, ci-verify then dies with "branch … is not on origin; push it first", which is the wrong diagnosis. `tracker.sh check c0001` now fails, and any future "CI green on this HEAD" criterion can't be written.
Critique: The tempting fix is to allow everything under `refs/remotes/*`. That would let `git remote remove origin` through, and that is the incident's worst symptom. The hook stopped it only because it refused the ref deletions.
Consequences: an allowance must keep deletions refused, and must be re-checked against `remote remove` and `remote rename`, both of which delete remote-tracking refs.
Recommendation: choose one of the following and record the decision.
(a) The hook reads its stdin lines (`<old> <new> <ref>`) and allows only creations and updates (new ≠ zero oid) under `refs/remotes/`, refusing every deletion. Add cases: `git fetch` in the probe repository works; `git remote remove origin` in it is still refused **and its config stays**; `fetch --prune` of a deleted branch is refused.
(b) Declare fetch at the root forbidden in checks. Say in the testing skill that CI verification is an Observed criterion, never a `check.sh` line, and note c0001's AC3 as obsolete.
Fix the audit sentence either way.

### F5 [medium] Network remotes and `gh` sit outside every guard and the review list, and the shared origin is on GitHub
Where: `scripts/lib/git-hooks/pre-push` (`*://* | *@*:*) exit 0`); c0058 step 4 "Pushes … to network remotes are untouched"; "Caught only by review" list
Evidence: the shared repository's `remote.origin.url` is `https://github.com/philipbergen/pickman.git`, which every session shares. A fixture that copies that URL (`git remote add origin "$(git -C <root> remote get-url origin)"`), or a c0005-style `pushurl` that fails to set, pushes or deletes real branches. A spec whose fake `gh` didn't land on `PATH` runs the real, authenticated `gh pr ready/edit` (c0008, c0005 depend on fakes). No check legitimately talks to a network remote. Nothing enforces that, and the review list doesn't say it.
Critique: the requirement is that no check can break the shared repository, and its GitHub copy is the one every session pulls from.
Consequences: refusing all network pushes in checks also affects any future e2e that would push. None exists, and one should be a deliberate exception.
Recommendation: when `PICKMAN_FENCE_REAL_GIT` is set, `pre-push` refuses every URL that doesn't resolve to a local directory. `fence.sh` also unsets `GH_TOKEN` and `GITHUB_TOKEN` and sets `GH_CONFIG_DIR=<checkout>/.cache/gh-none`, so a real `gh` in a check is unauthenticated. Add cases: a push to `https://example.invalid/x.git` from a fixture is refused by the hook (exit, no network), and `gh auth status` inside a run fails. Add "network remotes and `gh` against the real repository" to the Protected list.

### F6 [low] Lock and marker leftovers, and stale numbers in R0021
Where: `tests/lib/fence.luau` `takeOverIfStale`, `guarded`, and the re-run `bash -c`; R0021 Risks; `tracker.sh` `withPromotedCopies`
Evidence and fixes:
- **Re-run pid gap**: the re-run child's pid is recorded only once its Lune has started, so a top killed in that window leaves a lock with only dead pids, and a second suite takes it over. Fix: `echo >"$1/.cache/tests-run.lock/pid-$$"` in the `bash -c` before `exec lune`. `exec` keeps `$$`.
- **Takeover mutex without a pid**: a waiter killed between `mkdir <lock>.takeover` and writing its pid leaves a mutex nobody removes, so every later run waits out the full limit while any lock is stale. Fix: treat a mutex with no pid file older than 2 s as dead. Also say in the give-up message which directory to remove.
- **Marker check**: `guarded` accepts any `here` below the marker, and worktrees live below the main checkout (`<main>/.worktree/X`). So a marker and ceiling leaked from a main-checkout run would switch off the lock, fence and tripwire in every worktree. Fix: accept only `here == marker` or `here` under `marker/.cache/`, and add a case.
- **promote-check race**: promote-check copies and removes specs in `tests/acceptance/` outside the lock, so a background run in the same checkout can load or lose them mid-run. Say this in the Allowed writers line, or run the copy under the lock.
- **Stale numbers in R0021**: Risks still says the default wait is 900 s (c0058 says 240), "taken over when its pid is dead" (now: every recorded pid), "changes only by hand or by an escape" (F2 shows otherwise), and that M11 is the deadlock mutant (it is now L-nested).

Verdict: changes
