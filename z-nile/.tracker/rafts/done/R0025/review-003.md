### F1 [medium] stop's new "named the raft but was not claimed" path has no spec case, and the stop-raft skill doesn't describe it
Where: scripts/tracker/main.luau, `cmd.stop`: the readied branch's `else table.insert(left, m.id)`, the legacy branch's `else table.insert(left, m.id)`, and the `warning: … name R but were not claimed with it` line; tests/tooling/ready-members.spec.luau (no case has such a member); .claude/skills/stop-raft/SKILL.md step 2
Evidence: Every member in every case of ready-members.spec is either readied (c0010 and c0020 for R0010) or claimed (c0040 for R0030). None is in the backlog naming an active or claimed raft, so `left` is always empty. Two mutants pass the whole suite:
1. In the readied branch, insert the backlog member into `ids` instead of `left`. Then `moveOnOrigin`'s verify refuses ("c… is prepared on origin/main, not active: nothing to stop"), so `stop R` fails on every run while that issue exists. The raft can't be given back, which is the stranding this mechanism was built to remove.
2. Delete the warning. A member is then silently left out of `stopped R (…)`.
The trigger is ordinary: any issue that names R and reaches origin/main after R was readied, for example a capture landed with `raft: R`. stop-raft step 2 says "moves it and its issues back". It doesn't say which issues, or that some are skipped with a warning. Only the tracker skill's table row says the members are the `raft:` set. Also, in the legacy branch, a member whose effective state is anything other than `active` (`done` included) gets the "not claimed with it" warning, while the readied branch refuses a `done` member. That's a small inconsistency between the two branches.
Critique: The round-2 answer added the `left` path as new behaviour, and its refute says the spec covers "drift both ways". It covers the `issues:` drift both ways, but not this third case, which the new code decides on its own. The tempting fix is one readied case. The legacy branch makes the same decision separately and needs its own case.
Consequences: The cases need a member published after the claim. `trackerfix.elsewhere` already does that, so the fixture needs nothing new. If the legacy branch is made to refuse a `done` member, to match the readied branch, that is a new refusal that needs its own case. Leaving it as a warning is acceptable if the skill says so.
Recommendation: In ready-members.spec add:

### F3 [low] Membership by `raft:` still strands an item whose `raft:` changes on main while it is readied, the residue review-001 named; the claim stamp would identify the claimed set exactly
Where: `cmd.stop` (both branches select by `store.members(raft.id)` on origin/main as it is when stop runs); `cmd.ready` and the legacy `start`, which stamp every claimed item with one `stamp("active")` value
Evidence: The raft R0010 is readied with c0010 and c0020. A PR to main then edits c0020's `raft:` to R0020, where R0020 is a backlog raft. `stop R0010` moves R0010 and c0010 only, and c0020 stays in `active/`. `status c0020 new` refuses ("readied: use tracker.sh stop R0020"), and `stop R0020` refuses because R0020 isn't readied. Only a hand edit gets c0020 out. review-001 F1's Critique already named this residue ("a member whose `raft:` changed while it was readied would still strand"). The tooling's own paths can't cause this drift: `status <id> preparing` refuses items in `active/`. That is why this is low.
Critique: This is the third round to find a gap in raft membership. The `issues:` field and the `raft:` field can both be edited after the claim. The one thing that can't drift is what the claim wrote. `ready` stamps the raft and every moved item with one value. The legacy `start` writes one claim value to the raft and every member.
Consequences: Selecting by stamp means `stop` gives back exactly the items whose `status:` on origin/main equals the raft's `status:` (in `active/` for a readied raft, in the backlog for a legacy one). Items that name the raft but carry another stamp get the F1 warning. Items that carry the stamp but name another raft are moved back and named, which ends the strand. Nothing restamps a readied item before `done`, so the set stays exact. The new rule is "the claim stamp identifies what a claim took", and it needs one spec case: the drift above.
Recommendation: Optional, and the author may defer it as a low finding: select stop's set by the raft's stamp and keep `raft:` only to name items in the warning, adding the drift case above to ready-members.spec. At minimum, have `audit` report an item in `active/` whose `raft:` doesn't name an active raft, so the strand is visible before someone needs `stop`.
