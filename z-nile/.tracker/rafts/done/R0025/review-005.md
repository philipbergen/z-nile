### F1 [medium] (repeat of review-004 F1) `claimStamp`'s uniqueness check is a no-op: `git grep` has no `-x` option, so every call exits 129, which counts as "free", and no claim stamp is ever compared with origin
Where: scripts/tracker/main.luau `claimStamp` (`sh.run("git", { "grep", "-q", "-F", "-x", `status: {v}`, "origin/main", "--", "tracker/" }).ok`); the tracker skill's stop row ("Every claim stamp is new on `origin/main` (redrawn until no item carries it)"); refute-004 F1
Evidence: In this worktree (git 2.54.0, Apple Git-157), `git grep -q -F -x "status: active-plucky-raging-brisk" origin/main -- tracker/` prints `error: unknown switch 'x'` and the usage text, and exits 129. That value is on 7 items on origin/main. The same command without `-x` exits 0. With an absent value it exits 1. With a bad ref it exits 128. `git grep` has `-w` but no `-x`/`--line-regexp`. `sh.run` captures stderr, so the usage error is never shown. `.ok` is false for every value, so `taken` always returns false and `status.fresh` returns the first draw. The behaviour is exactly the pre-fix `stamp("active")`, so review-004 F1's two collisions still happen at the same odds. One of them, a readied raft that draws an active raft's stamp so that `stop R1` moves R2's issues to the backlog, is still a wrong result. The skill text now promises a uniqueness that the code doesn't give. This hid because the predicate treats every non-zero exit, error or not, as "not found". It is the case the round-4 Recommendation asked to pin ("seed a done/ issue whose `status:` is the value…", or at least "a check that `ready` and `start` use it"). Neither exists: `status-fresh.spec` tests only the pure loop. A mutant that replaces `claimStamp()` with `stamp("active")`, or makes `taken` always return false, passes every spec. That mutant is the shipped code.
Critique: The mechanism, "a stamp is the claim's identity", has now had a hole in each of the last two rounds: round 4 found it wasn't unique, and the fix's check doesn't run. The tempting fix is to drop `-x`. That alone keeps the failure mode that hid this one: any git error still reads as "free".
Consequences: The fix needs three things. (1) A correct match. Stamps are `[a-z-]` only, so `git grep -q -E "^status: <v>$"` (or `-F` without `-x`, which errs to "taken" on a substring and only causes a redraw) is safe. (2) A strict reading of the exit code: 0 is taken, 1 is free, anything else fails the claim loudly ("could not check claim stamps on origin/main: <stderr>"). The claim then refuses before any push, the state an operator can retry from. (3) A test that runs the real predicate. Without one the next typo ships the same way. Take the predicate out as a function of the repository (for example `claimTaken(value): boolean` in a module, run in cwd) so a tooling spec can call it in a `.cache` fixture: a value on a done/ item is taken, an absent value is free, and a bad ref throws. In the resumed legacy `start`, `claim = mine` is used without the check. That is right while the raft on origin carries `mine`. With a stale claim file (the raft was given back from another checkout, which removes only that checkout's file), `mine` was free when this file was written but may have been drawn since. Use `mine` only when the raft's origin status equals it, which is review-004 F2's original condition, and otherwise draw a fresh, checked stamp.
Recommendation: Fix (1)-(3) as above. Add the fixture spec for the predicate (taken / free / error), and one sentence in `claimStamp`'s comment on the exit-code contract. Keep the skill sentence only once the spec proves it. This is round 5, so the finding may instead be deferred to a backlog chore under execute-raft Phase 4 step 7. If so, the tracker skill's stop-row sentence "Every claim stamp is new on `origin/main` (redrawn until no item carries it)" is false today and must come out or be qualified before merge, and refute-004 F1's "fixed" answer must be corrected. No sequestered file is involved.
