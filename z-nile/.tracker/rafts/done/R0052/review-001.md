### F1 [high] The rafting gate auto-merges a PR that edits a prepared member's `check.sh`: any issue the PR names in a raft's `issues:` gets the sequestered-file exemption
Where: `z-nile/engine/dispatcher.luau:1173-1201` (`judgePr`: `own` starts as `{ [id] = true }` and gains every member of every raft file the PR touches), `trackerstate.luau` `judge` (`isSequesteredRel(r) and not (opts.own and opts.own[id])`: an `own` item's sequestered files are never judged).
Evidence: in the scratch clone, control-cli's rafting-gate fixture with one changed PR (`expc.spec.luau`, "EXP rafting gate"): PR #31 adds `pickman/.tracker/rafts/R0050/R0050.md` with `issues: [c0096, c0091]`, sets c0096's `raft:` line and replaces c0091's prepared `check.sh` (`lune run tests/run -- pickman/.tracker/issues/c0091/acceptance/a.spec.luau`) with `exit 0`. `./zn dispatch c0096` printed `next: merge the raft PR #31`, and the fake gh's log has `realgh pr merge 31` (`merged? true`). The PR itself chose c0091 as "its own" by listing it; it can as well remove c0091's acceptance specs, or edit the issue's own (c0096's) sequestered files.
Critique: a member of a raft is a prepared issue whose `check.sh` and specs passed its design review and are sequestered from then on (zz-test). A rafting PR never has a reason to change them (z-raft writes the raft's own files and the members' `raft:` lines), so this exemption only ever lets an unattended merge weaken a reviewed acceptance check with no human in the loop, the hole the sequestration rule exists for. The design's sentence ("a rafting PR only its own items' files … never another item's sequestered files") left this open, and the code takes it literally. The tempting fix is to drop the members from `own` but keep the issue `id`: the issue's own reviewed `check.sh` is just as sequestered once prepared.
Consequences: `own` has two jobs today, the `only` rule (which items' files a PR may carry) and the sequestered exemption; separating them means the rafting gate passes a set for `only` and an empty (or rafts-only) set for `own`. A raft the PR *adds* is a new item, so its own `check.sh` and `acceptance/` already pass without `own` (only an item with no file on the base may add them); an existing backlog raft whose `check.sh` a recombine rewrites would then wait for a human (fail closed). The prep gate is unchanged: its `own = { id }` is the issue being prepared, which is right.
Recommendation: in `judgePr`'s raft branch, keep the issue, the rafts and their members for `only`, and pass `own` = the rafts the PR carries at most (never an issue), so every issue's sequestered files are judged per item. Add a control-cli-style case to c0117's specs for the next review to judge it (a code-mode recommendation can't edit the sequestered spec: put it in a new non-sequestered tooling spec, or escalate if it must live in control-cli): a rafting PR that edits a member's `check.sh`, and one that edits the issue's own, each stop at exit 4 naming the file, while the existing "merges: the raft's own document and its member's raft: line" case still merges. Mutant: `own` gains the members again.
Lesson: zz-arch/item-rules-scoped-to-their-call

### F2 [medium] `./zn dispatch retry` skips every start-of-run guard: origin's URL, the watermark gone or set back, and the vetting before a merge
Where: `dispatcher.luau:1542-1573` (`retry` takes the lock and calls `chain`/`oneStep` with the state directly; `guardStart` runs only in `dispatcher.top`, 1617).
Evidence: `expc.spec.luau`, "EXP retry": after `vet` and one clean `dispatch z-design c0010`, `remote.origin.url` set to another bare repo; `dispatch z-design c0010` → exit 5, "origin's URL changed since the last run …" (as designed); then `dispatch retry c0010` → exit 0: `dispatch: z-design c0010 on claude …: ok (done), 123 tokens` and the spend row written, against the new origin, with no URL check. In the chain path the same skip means a gate merge can run before any `vetMain` in that run (`facts` → `judgePr` → `merge`; only a model step vets before it starts).
Critique: §5 says `guardStart` runs "at the start of every run" and a tripwire "stops every later run until the user … runs `./zn dispatch vet`"; `retry` is the command every stop message tells the user (or an agent reading a state file) to run, so it is the likeliest way past exactly the checks that catch a step's between-run tampering (origin repointed, watermark removed or set back). The model step's own `vetMain` still catches an unvetted code commit, which is why the specs stay green.
Consequences: running `guardStart` in `retry` means a retry after a tripwire stays a tripwire until `vet`, which is the design's rule; retry after `lost`, `questions.md` or `failed` is unaffected when main is clean. `guardStart` also sweeps refs and pins origin, which retry then gets too.
Recommendation: route `retry` through the same start as every top-level run (run `dispatcher.guardStart` after taking the lock, stop with exit 5 and the state `tripwire` on a refusal), and add a case: a URL change between runs, then `retry`, exits 5; a code push between runs, then `retry` of a chain whose next action is a gate merge, exits 5 without merging.
Lesson: zz-test/pin-fail-safes-where-they-act

### F3 [medium] The agent's git passes a forced rewind of `main`
Where: `z-nile/engine/wrapper.luau:79-95` (`decidePush` judges only `merge-base..src` and refuses only a deletion; the dry run's `+` flag is ignored).
Evidence: `expw.spec.luau`, "EXP forced rewind", the wrapper spec's fixture: after a tracker-state push moved origin's main to `5f0addbb`, `z-nile/bin/git push --force origin <start>:refs/heads/main` through the shim exited 0 and origin's main is `c036004e` (= start): the commit was dropped. The change from the merge base to the source is empty, so it is "tracker state".
Critique: nothing a step does legitimately rewinds `main` (`publish` uses `--force-with-lease` against its own base, through the broker, never the wrapper). With the user's own token as the agent's credential (G17: the ruleset's `non_fast_forward` rule is bypassed by the admin) this discards other people's commits on `main`; the watermark sees it only afterwards ("rewritten … ./zn dispatch vet"), and vetting it accepts the loss. AC4 claims the wrapper refuses every push that puts anything but tracker state on main "however spelled"; a rewind with a tracker-only tail (`git push -f origin <old main + a tracker commit>:main`) passes the same way.
Consequences: the refusal needs "is the fresh main an ancestor of the source" for every update to `refs/heads/main`, which the wrapper already fetches; `--force-with-lease` forms then pass only as fast-forwards, which is all the tracker needs.
Recommendation: in `wrap.luau`'s check, refuse an update of `main` whose source does not descend from the freshly fetched main ("not a fast-forward of main"), in `decidePush` also refuse flag `+`; add the two forms (a plain rewind, a rewind with a tracker-only commit on top) to a wrapper case run through the shim.

Recommendation: in `apiDecision`, know every value-taking option of `gh api` and skip its value, and refuse any other unknown option rather than guessing; add the two forms above to the gh shim case (refused before the real gh runs, the log empty).
