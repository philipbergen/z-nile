### F1 [high] (repeat of review-002 F1) The rafting gate auto-merges a PR that takes a member out of an active raft by rewriting that issue's `raft:` line, and rewrites its design with it
Where: `z-nile/engine/dispatcher.luau` `judgePr`, the raft branch's second loop: an issue joins `items` when its document **in the PR** (`git show {ref}:{path}`) has `raft:` naming a raft in `rafts`. Nothing reads the issue's base state: its folder (backlog, `active/`, `done/`), its base `raft:` line, or what else the PR changed in it. `store.members` (what a raft's `check.sh` loop and `./zn done` use) is exactly the issues whose `raft:` names the raft.
Evidence: `exp3a.spec.luau`, dispatch-guards' fixture plus one seed on main: `pickman/.tracker/issues/active/c0093/` (prepared stub, `raft: R0040`, a `check.sh`) beside the spec's active raft R0040. After such a merge, R0040's `check.sh` loop (`zn members R0040`) no longer runs c0093's reviewed `check.sh`, and `./zn done R0040` (`main.luau` `cmd.done`, members by `store.members`) passes and moves without it: the active raft's exit criteria are weakened by a non-sequestered line, auto-merged. The same PR shape edits any issue's design in any folder (`done/` included) by naming a raft it adds.
Mutants (on the clone's `dispatcher.luau`, run against `dispatch-guards.spec.luau`, 6/6 passed each, so both survive): MX3 `if named and rafts[named]` → `if named` (an issue naming any raft, an active one included, joins); MX5 the base members of a backlog raft never join `items` (`items[m] = true` removed). No case seeds an issue that names a raft the PR doesn't carry, and none carries a backlog raft's existing member (a recombine).
Critique: this is the third hole in the same mechanism: round 1 the PR's `issues:` line, round 2 the raft documents it touches, now the issue documents it touches. Each fix moved "which items are the PR's" to the next text the PR writes. The refute and the `judgePr` comment say "both derived from the base, never from what the PR itself says"; the join rule isn't. The tempting fix (also refuse paths under `issues/active/` and `issues/done/`) closes this instance and leaves the next: a backlog issue's whole design can still be rewritten by adding a `raft:` line, though z-raft "never edits a member's design" (z-raft §4).
Consequences: what a rafting PR legitimately does to an existing issue is one edit: its front matter's `raft:` line (z-raft's `new raft`, `fold`, `recombine`, `unfold`; `grouped:` hashes the document without `status:` and `raft:` for the same reason). Judging the shape of the change, not just which item it belongs to, removes the choice: the gate then needs the base's `raft:` value and folder of each issue, and the PR's document compared with the base's outside that one line. A recombine (an issue moving between two backlog rafts the PR carries) and an `unfold` (`raft:` emptied) still merge; anything else to an existing issue waits for a human (exit 4, fail closed). `raftOnBase` must know every lifecycle folder `itemOf` knows: it checks `""`, `active/`, `done/`, but `LIFECYCLE` also has `retired/`, so a retired raft reads as "new" and its folder is carry-able.
Recommendation: question the mechanism, not the instance: at the rafting gate judge each existing item's change by its shape, from the base. An existing issue may change only its document, and only in its `raft:` line (the PR's document equals the base's with that line restored), only when it is in the backlog folder on the base, and only from empty or a raft in `rafts` to empty or a raft in `rafts`; an existing backlog raft keeps today's rule (any non-sequestered file); a new raft's folder, `z-nile/next`, and nothing else. Give `raftOnBase` the `retired/` folder (any lifecycle `itemOf` accepts). Update the `judgePr` comment and zz-rules "The chain" bullet (and dispatch-texts' pin) to say so. Cases in dispatch-guards (non-sequestered): PR #51 above stops at exit 4 naming `c0093/c0093.md`; a backlog member's `raft:` line plus a design edit stops at exit 4; an issue whose `raft:` names the active raft R0040 stops (kills MX3); a recombine moving a backlog raft's member into the new raft merges (kills MX5); PR #34 still merges.
Lesson: zz-arch/item-rules-scoped-to-their-call

### F2 [medium] The rafting gate auto-merges a new raft whose `check.sh` is `exit 0`: nothing reviews a single raft's exit criteria
Where: `judgePr` (a new raft's own sequestered files "pass as a new item", `own = {}`); `trackerstate.judge` (`only an item that has no file on the base may add them`); c0117.md:237 ("a rafting PR only its own items' files (the issue, a raft it adds …)").
Evidence: `exp3a.spec.luau`, PR #52 = PR #34 plus `pickman/.tracker/rafts/R0050/check.sh` = `exit 0`: `next: merge the raft PR #52`, `realgh pr merge 52 --squash --match-head-commit 812182a9…`. Every raft's `check.sh` starts as `z-nile/templates/raft/check.sh`: RC0 runs the project's full gate, every member's `check.sh` (`zn members`) and `promote-check`; z-raft only adds RCn checks after the RC0 lines (z-raft §3). With `exit 0`, `./zn done R0050` passes with no member's reviewed checks run.
Critique: a single-issue raft gets no coherence review (z-raft §4: only rafts of two or more), so under `auto_merge = ["raft"]` (G4) no reader, model or human, sees the raft's `check.sh` before it is the exit criterion. The human run gate sees the code PR, whose `./zn done` claims every check passed. Review 002 accepted "a new raft's own files pass as a new item" for the `own` set; that was about the PR choosing exemptions, not about the RC0 lines, which are generated and never the author's to change.
Consequences: requiring the template exactly sends every raft with an RCn check to a human (fail closed; 3 of the 12 backlog and active rafts on main have an RCn check, R0044's among them). Allowing additions means judging shell, which a line like `exit 0` between RC lines defeats; so the narrow rule is: the rendered template's lines through the `promote-check` line, byte for byte, as the file's head, and anything after that waits for a human unless it equals the template's tail.
Recommendation: at the rafting gate, a new raft's `check.sh` must equal `z-nile/templates/raft/check.sh` rendered for its id and project (read from the fresh main, the one renderer `./zn new raft` uses); any other content stops at exit 4 naming the file. Cases in dispatch-guards: PR #52 stops at exit 4; a raft with an RC1 line after the template stops; PR #34 with the rendered template merges.
