### F3 [high] `raftcheck.judge` never returns for a check line with a backslash that is not a line continuation, so the dispatcher hangs at the rafting gate
Where: `z-nile/engine/raftcheck.luau` `word`: in a bare word, `\` ends the word (`return j, nil`) without consuming it; the caller's loop in `judge` sees `\` not followed by `\n`, calls `word(text, j)` at the same index, gets `j` back, and loops forever (`j = nxt`, never advancing).
Evidence: `p2.luau` (the template rendered for R0050, one line added before `finish`, under `perl -e 'alarm 5; exec @ARGV'`): `check "RC1: the log names it" grep -q R0050\.md log.txt` → exit 142 (killed by the alarm after 5 s, no verdict); `check "RC1: x" true \x` → 142; `check "RC1: x" true\ ;exit 0` → 142. `judgePr` calls `raftcheck.judge` on every new raft's `check.sh` (`shapeOf`; dispatch-guards #59 reaches it and merges), so such a raft hangs `./zn dispatch <id>` while it holds the item's lock, until someone kills it.
Critique: an escaped character is ordinary shell in a grep pattern (`\.`), so a well-meant z-raft output hangs the unattended chain, not only an adversarial one. None of raftcheck.spec's cases has a backslash outside a continuation.
Consequences: a fix that consumes `\x` as a literal pair must refuse `\` before a newline inside a word and before `\r`; refusing every backslash but the line-ending continuation is the smaller rule (fail closed: the raft waits for a human).
Recommendation: in `word`, refuse `\` unless it is directly followed by `\n` (and then end the word there, as today); add a progress guard in `judge`'s word loop (`if nxt <= j then return "…" end`) so any later parser slip refuses instead of looping. Cases in raftcheck.spec (refused, each must return): `grep -q R0050\.md log.txt`, `true \x`, `true\ ;exit 0`, `true \` followed by `\r\n`; the existing `continued` case still passes.
