### F2 [medium] The post-merge race is not covered by `vetMain`, which is the refute's reason for not closing it: a merge that lands on a main moved after the judgement is accepted as tracker state
Where: `dispatcher.luau` `merge` (1577–1591: `gh pr merge … --match-head-commit`, then `zn sync`; nothing reads the merge commit); `vetMain` (652–691) runs `trackerstate.checkEach`, which applies only the generic tracker-state rule (`trackerstate.check`), and passes any PR merge (`ctx.prMerged`) whatever it changed; refute-005 F1: "the post-merge judgement of the merge commit (exit 5) … not built, because `vetMain` already judges main's tracker state at every run's start".
Evidence: exp6 Q7: PR #208 edits backlog R0041's document (allowed); the gate judges it against unmoved main and merges (`next: merge the raft PR #208`, merged=true). Main then readies R0041 (`git mv` of R0041 and c0094 into `active/`), and the squash GitHub would make is built on that main (`git merge-tree --write-tree <moved main> <head>` exits 0, committed with the moved main as parent): `rafts/active/R0041/R0041.md` on main now has the PR's `theme: retitled` line. `zn dispatch vet --dry-run` → `f399b033c891 tracker: ready R0041: tracker state` and `016401849682 PR 208 squash: tracker state`, exit 0. Nothing in the dispatcher or the watermark ever notices that an active raft's document changed by an unattended merge, which is review 005 F1's P1 outcome by another door.
Critique: the window is seconds (fetch in `judgePr`, the rest of `facts`, `next`, then `gh pr merge`), but it is the one window the moved rule cannot close by itself, and closing it to detection is one comparison. Stating it as a known limit would be acceptable only if the stated reason were true; it is not: `vetMain` judges whether each commit is tracker state, never the rafting rules.
Consequences: detection after the fact, not prevention (GitHub has no base pin): the merge has happened, so the dispatcher stops and says what to look at; it never reverts. A merge commit whose parent is the judged main is exactly the judged result, so the common case costs one `gh pr view` and one fetch.
Recommendation: after a gate merge, read `mergeCommit` (`gh pr view <n> --json mergeCommit`), fetch it, and require its first parent to equal the main `judgePr` read (keep that sha on the Pr); when it differs, apply the moved rule to `<judged main>..<parent>` against the PR's carried items, and stop with exit 5 (outcome `tripwire`, naming the PR, the items and the commits) when it fires, else continue. Cases: a fake `gh pr merge` that first advances the fixture's main over a carried item (Q7) → exit 5; one that advances it over an unrelated spend row → the chain continues; the plain merge (parent equal) → unchanged. zz-rules' Dispatch does not mention the race today; its "The chain" bullet gains one clause saying the merge commit's parent is checked.
Lesson: zz-arch/merge-gate-checks-what-it-merges
