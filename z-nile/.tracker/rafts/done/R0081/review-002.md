### F1 [high] No failed row and no failed case's result is ever recorded: the F5 "output text" deviation changes what the store holds
Where: `z-nile/specs.luau:256-260` (`if code ~= 0 then … results not recorded`); c0165.md Verification log, "Deviations in output text (review 001 F5)"; Design, `specs.luau run` step 3
Evidence: the Design says "**Only a runner exit of 0 records `passed` rows.** A non-zero exit records only the files its results show failed". The Problem's Scope decision (user, 2026-10-26) says "File level, cases recorded: … record each case's name and result in the db". In the scratch clone a spec with one passing and one failing case, run with a passing spec (`lune run z-nile/specs -- run --project z-nile -- tests/tooling/zz-probe-fail.spec.luau tests/tooling/zz-probe-other.spec.luau`), printed `2 passed, 1 failed, 2 spec files` and `results not recorded: the run exited 1`, and `select spec, state from specs where spec like '%zz-probe%'` returned nothing. A run that exits 0 has every case passing, so with this branch the orchestrator never writes a `failed` row, a failed case, or a `detail`. The schema's `state='failed'`, `detail`, and `decide`'s "a failed row runs" are all unreachable. The Verification log files this under "output text", but it is a change to the store contract that c0238 builds on (Problem: "the second waits for the first's result and uses it").
Critique: an outcome from the user's scope decision, each case's result, now holds only for passes, and the deviation is recorded under the wrong heading, so nobody has decided it. The tempting fix is to record each failed file's rows in the `code ~= 0` branch through `recordMany` as it is.
Consequences: that sends the FAIL text into the one-call batch and into every later read. Probe through `resultsdb.recordMany`: a `detail` holding `\0` fails the whole batch (`sqlite3 failed: Parse error near line 3: near "good": syntax error`), so one spec's message loses every row of the run, the passes included. A `detail` holding `\255\254` records, but every later `rows` read that includes its fingerprint raises (`sqlite3 answered unreadable JSON`). `specs.luau` then turns reuse off for the whole run (and F3 shows that branch also skips the no-record marker). And `recordMany` would then decide `passed` with a copy of `record`'s rule that no spec checks (F2).
Recommendation: implement the Design's rule. With a non-zero exit, under the same `reuseplan.records` and `stands` gates, record a `failed` row, with its cases, for each file the results show failed (`loaded == false` or any case not ok). Never record a pass from that run. Do it after F2's single writer exists. Make the text safe: `rows` must not select `detail`, which the orchestrator never reads. Store `detail` so that any bytes survive or are made harmless (strip NUL and invalid UTF-8, or hex-encode it), and do the same for `gates.summary`, which `gatePassed` reads back as JSON. Cases (unsequestered tooling spec, a fixture through `specs run`): one failing and one passing spec leave exactly one `failed` row, with both case results, and no row for the passing spec. A FAIL text with `\0` and `\255` records its row, and the next run still reuses its other specs. Otherwise escalate to the user to keep the deviation, saying that c0238's waiter must then add failure recording itself.

### F3 [medium] A weak-jail run writes no no-record marker when reuse turned off inside `specs run` (the F1-fix path), so `gate-record` records a whole-gate pass from it
Where: `z-nile/specs.luau:256` (`if db ~= nil and state ~= nil and doc ~= nil then`, which holds the `reuseplan.records` check and the marker write); `:188-194` (the new `pcall`, which sets `db = nil`); `:178-180` (`gitState` nil does the same)
Evidence: in the scratch clone, a `lune` wrapper first on PATH rewrote the results' jail to `outer sandbox (protects the repository)` (gatefix's `weakJail` method). Case A, `PICKMAN_GATE_PID=4242` with the db healthy: `not recorded: outer sandbox (protects the repository)` and `z-nile/.cache/spec-norecord-4242` written. Case B, the same with `PICKMAN_SQLITE3` a stub that exits 5 on any SQL holding `json_group_array` and passes everything else to the real sqlite3: `reuse off: …resultsdb:118: sqlite3 failed: database is locked`, `1 passed`, and no marker. Then `PICKMAN_GATE_PID=4243 lune run z-nile/specs -- gate-record --digest probe-digest --mode affected --projects z-nile --summary <file>` exited 0 and `select key, mode, projects from gates` returned `probe-digest|affected|z-nile`. `gate-record` opens the db itself, so a read that fails once in `run` (a busy timeout, or F1's poisoned row) is not a failure there.
Critique: the Design and AC5 say "a weak-jail run … records no spec or whole-gate row", and "the guard specs' jailed cases return early there". Before the F1 fix a failed `rows` crashed the gate. Now it turns reuse off and also skips the jail decision. The tempting fix is to move only the marker write out of the branch.

Recommendation: decide the run's verdict from the run alone: the runner ran, its results exist, and the exit code, `reuseplan.records(jail)` and `stands`. Then write the marker whenever `records` is false, whatever `db` is, and write rows only when `db` is also open. Unsequestered case (a fixture through `specs run` and `gate-record`, not through the sequestered gatefix): a weak jail plus a sqlite3 stub that fails the rows read writes the marker, and `gate-record` writes no `gates` row.
