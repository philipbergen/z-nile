### F1 [high] A jailed spec makes the unjailed orchestrator run any SQL it likes: `seconds` from a spec-writable worker part file goes into the SQL unquoted
Where: `z-nile/tests/run.luau:291-313` (the coordinator takes `(doc).files[1]` from `<results>.<index>` as it is); `z-nile/specs.luau:314` (`seconds = rec.seconds or 0`); `z-nile/lib/resultsdb.luau:213-215` (`{it.seconds}` interpolated into `upsertSql`)
Evidence: the worker part files sit in the home's `.cache`, which the jail lets every spec write, and a spec sees its own part's path in `PICKMAN_RESULTS`. The coordinator reads every part only after all lanes have finished. In the scratch clone, spec `tests/tooling/zz-a.spec.luau` waited for `…/spec-results-<pid>.json.2` (zz-b's part, written when zz-b ended) and overwrote it with `{"files":[{"file":"tests/tooling/zz-b.spec.luau","loaded":true,"cases":[{"name":"x","ok":true}],"seconds":"0, 0); COMMIT; ATTACH DATABASE '<clone>/PWNED.sqlite' AS p; CREATE TABLE p.t(x); DETACH DATABASE p; BEGIN IMMEDIATE; INSERT INTO specs(fp,home,spec,state,seconds,updated) VALUES ('forged','h','s','passed',1"}]}`. `./zn run --time 300 -- lune run z-nile/specs -- run --project z-nile -- tests/tooling/zz-a.spec.luau tests/tooling/zz-b.spec.luau` printed `2 passed, 0 failed`, rc 0. After it, `ls -la PWNED.sqlite` showed `-rw-r--r-- … 8192 PWNED.sqlite` at the clone's root, outside every `.cache`. `select fp, home, spec, state from specs` returned `forged|h|s|passed`, a passed row the spec chose. So the orchestrator, outside the jail, created a file where the jail forbids writes, and recorded a pass that no run produced. The run's exit is 0, so none of the record gates stop it. In real use the db is the main checkout's `.claude/.znile_tests.sqlite`, and `ATTACH` reaches any path the user can write, the shared `.git` included.
Critique: this is "work handed to processes outside the jail" (zz-test, Specs never touch the real repository), and the orchestrator added it. The Design's premise in `specs.luau`'s header, "the runner's jail denies specs every write outside the home's .cache", stops holding once an unjailed process turns `.cache` content into SQL. The other values are safe: case names and the detail go through `q()`, and `fp`, `home`, `spec` and `now` are the orchestrator's own. The tempting fix is `tonumber(rec.seconds) or 0` in `specs.luau`.
Consequences: that closes this one field. But the mechanism trusts a spec-writable file. A forged part can also rename which file a record belongs to (`file`), and send non-boolean `loaded` or `ok` values, or non-string names, which `clean` and `serde.encode` then meet, and the next field c0238/c0240 add to `Item` would come back unquoted. A single-file (in-process) run shares its Lune module tables with the spec, so its results can be shaped by the spec as well. That case can't be closed from the runner, only by the orchestrator checking what it reads.
Recommendation: treat the results file as untrusted input at the trust boundary, the unjailed orchestrator. (1) In `specs.luau`, accept a record only when `type(rec.file) == "string"` and it equals the `toRun` entry, `type(rec.loaded) == "boolean"`, `cases` is an array of `{name: string, ok: boolean}`, and `seconds` is a finite number ≥ 0. Anything else is a failed result for that file (never recorded as passed). (2) In `resultsdb.upsertSql` (and `pruneSql`), format every number with `string.format("%.6f", n)` after asserting `type(n) == "number" and n == n and math.abs(n) ~= math.huge`, so no caller can put text into the SQL unquoted. (3) In the coordinator, take each part's record only if its `file` is `o.file`. Pin it in an unsequestered tooling case through `specs run` on a fixture: a spec that overwrites a sibling's part with a string `seconds` holding `ATTACH …` leaves no file outside the fixture's `.cache`, writes no row it named, and records the sibling as failed or not at all. Add a direct `recordMany` case with `seconds = "1); DROP TABLE specs; --"` that errors and records nothing. Add a line to zz-test's "Caught only by review" list: an unjailed reader of a file in `.cache` validates every field before it uses it.

### F2 [high] `workspace.blobs` drops every changed symlink that doesn't point at a regular file, so two different trees get one digest and a whole gate is reused after a link is removed
Where: `z-nile/lib/workspace.luau:61-71` (`if fs.isFile(...) then … else blobs[path] = nil -- deleted`), `:88` (`executable()` follows links)
Evidence: `ls-files -m` and `--others` list a symlink as a path. `fs.isFile` follows it, so a link to a directory, or a dangling link, counts as deleted and leaves the map. A link to a file is hashed as the target's content with a `100644`/`100755` mode, never `120000` and its link text. The repository tracks 34 links (`git ls-files -s | grep -c '^120000'`), every one a `.claude/skills/<name>` link to a folder, and `./zn skills --check` (a static stage of the gate, inside the whole-gate report) judges them. A blob-map probe in the clone: unmodified, `.claude/skills/arcade-arch` → `120000 e002573b…`; retargeted to `../../snake/skills/snake-arch` → absent; retargeted to `../../does/not/exist` → absent. End to end in the clone: with an untracked `z-nile/skills/zz-probe/SKILL.md` and its link `.claude/skills/zz-probe`, `lune run z-nile/specs -- digest --mode affected --projects z-nile` printed `d6206c76…`, and `./zn skills --check` said `25 skills, one link each, ok`. After `rm .claude/skills/zz-probe`, the digest was the same `d6206c76…`, and `./zn skills --check` exited 1 (`.claude/skills/zz-probe: missing`). `gate-record --digest <d1>`, then `gate-check --digest <d2>` after the removal, printed `reused: an affected gate passed on this content` and exited 0, so check.sh would print `GATE PASSED (affected)` with a failing stage. The same hole hits every spec fingerprint whose inputs include a link (35 `.claude/` lines in `z-nile/tests/inputs.tsv`, e.g. c0067/ready, c0072/land). Two worktrees sharing the db also share it: a link that is present in one and missing in the other gives one digest.
Critique: the Design's contract is "every file's blob (tracked, modified and untracked)" and "every read fails closed", and AC7 says the workspace reads fail closed. Here a changed tree reads as unchanged, so a stale pass is reused. The tempting fix is `fs.isFile or fs.isDir`.
Consequences: that still hashes a file link's target instead of its text, still can't tell two directory targets apart, and still calls a dangling link deleted. Any lstat-free check (Lune's `fs.metadata` follows links) brings this back for the next path type (a FIFO, a nested repository's folder, which `--others` lists with a trailing `/`).
Recommendation: hash what git would store. For each modified or untracked path, ask `test -L` (or `readlink`) first. For a link, the blob is `120000 <git hash-object --stdin of its readlink text>`. Hash a regular file as now. A path that is neither a link nor a regular file is "deleted" only when `test -e` and `test -L` both say it is absent. Anything else present (a directory from `--others` such as a nested repository, a FIFO) returns nil and a reason, which turns reuse off. Pin it in an unsequestered case on a fixture through `workspace.blobs` and `specs digest`: a tracked link retargeted between two folders changes the digest each time; a dangling link differs from a valid one; an untracked link added and then removed changes the digest; a link to a file differs from a copy of that file; an untracked nested repository turns reuse off.
