### F1 [high] The whole-gate digest leaves out what the selection reads (the merge-base, HEAD's tree), so a gate recorded where a failing spec was not selected is reused where it is
Where: `z-nile/specs.luau` `digestOf` (`baseRef` → `git rev-parse baseRef`, the base *tip*); `z-nile/lib/fingerprint.luau` `digestExtra`; `z-nile/lib/changed.luau:33-37` (selection = `git diff <merge-base>` ∪ `git diff HEAD` ∪ untracked); c0165.md Design, Whole-gate reuse: "`[--base <merge-base sha>]`".
Evidence: two probes. Each is a spec in the scratch clone built on `tests/lib/reusefix.luau` and run with `./zn run --time 300 -- sh -c 'cd …/r5/z-nile && lune run tests/run -- tests/tooling/probe-*.spec.luau'`.
(a) `probe-mb`: extra spec `c` (needs `C`, expects 1). On `work`, `C.luau` is set to `value = 3` and committed. `main` gets a commit with the same tree (`git checkout work -- .`, commit), as a squash or cherry-pick would give it. Output:
```
AFFECTED on main: []
GATE on main ok=true            no specs affected / GATE PASSED (affected)
AFFECTED on work: [tests/unit/c.spec.luau]
GATE on work ok=true            reused: an affected gate passed on this content / GATE PASSED (affected)
GATE --fresh on work ok=false   FAIL tests/unit/c.spec.luau :: runs   (expected 1, got 3)
```
(b) `probe-head`: extra spec `d` (needs `C`, expects 2; red on main, which Phase 0's "No baseline" allows). The gate on `main` selects nothing and is recorded. Then on `work`, commit `C = 2`, and `git checkout main -- pickman/src/C.luau` puts the old text back (`M  pickman/src/C.luau`). The tree, the base tip and the merge-base are all the same as on main. Output: `AFFECTED on work, C put back: [tests/unit/d.spec.luau]`, `GATE on work ok=true` with `reused: …`, then `GATE --fresh on work ok=false` with `FAIL tests/unit/d.spec.luau`.
In both, an affected gate that fails when it runs reports `GATE PASSED (affected)` from a record whose selection was empty.
Critique: the digest's claim is "this gate passed on this content". But an affected gate's result is a function of its selection, and the selection reads two git facts the digest doesn't hold: the merge-base's tree (a) and HEAD's tree (b). The Design named the merge-base sha. The code passes the user's `--base` or the base tip, and the Verification log records no deviation. Even the Design's merge-base would not close (b). Both cases need the whole tree, untracked files included, to be byte-identical at two HEADs. (a) arises when a branch's content lands on main by another commit (a squash of an up-to-date branch, a cherry-pick) and either checkout then runs the gate. (b) arises when a commit is undone in the index or the working tree. The tempting fix is to add `merge-base <sha>` to `digestExtra`, as the Design says. That still fails (b).
Consequences: hashing the selection itself makes the digest follow whatever the selector reads, now and later (c0240 teaches it more), with no list of git facts to keep in step. The selection must be the one check.sh then runs. `digestOf` already calls `select.affected(state.ctx, changed, name)`, the same function `z-nile/affected` uses after the same `forcedAll` (`select.luau:244-245`), from the same `changes.files(base)`. `digest_after` recomputes it, so a run that moves the selection records no gate. AC7's "another base is another gate" stays green: keep `base` in the extra. The selection is per project, so a project with nothing affected adds its line too (an empty list differs from a missing project).
Recommendation: in `digestOf`, add one line per picked project to the extra: `selected <name> ALL`, or `selected <name>` followed by the sorted spec paths, tab-separated. Pass it through `digestExtra` (or an extra argument). Keep `base`, HEAD-for-`*` and the refs. Record the deviation in the Verification log: Design line "`--base <merge-base sha>`" → "the selection itself, which covers the merge-base and HEAD's tree". Pin it in `tests/tooling/reuse-e2e.spec.luau` (unsequestered, the executor's own) with the two probes above as cases: after the gate on `main`, the gate on `work` prints no `reused:` line, runs the selected spec (`ran.log`) and exits non-zero. Each case needs at most 2 gate runs, within the file's budget (reusefix header). Run the mutant "selection line dropped" once and record that both cases go red.

### F2 [medium] A gitlink (submodule) is classed as "now a folder" and dropped, so its commit and its content never reach a digest (repeat of the review-004 F1 mechanism, another path kind)
Where: `z-nile/lib/workspace.luau:86-88` (`blobs[path] = nil -- deleted, or now a folder`); `ls-files -s` keeps `160000 <commit>` only while the submodule is unmoved; `z-nile/skills/zz-arch/lessons/digests-hash-paths-as-git-stores-them.md` ("any other kind of path turn reuse off").
Evidence: in the scratchpad (`probe/outer`, with a submodule `sm` added from `probe/sub`). Clean: `git ls-files -m` lists nothing, and `ls-files -s` gives `160000 98f7026a… sm`. After `git -C sm checkout HEAD~1`, `ls-files -m` lists `sm`. `workspace.blobs` (via `lune run probe-blobs.luau <outer>` under `./zn run`) printed only `.gitmodules` and `f`: `sm` is gone. After a further commit in `sm` (HEAD `30162cc2…`), it printed the same two lines. Two different submodule commits give one blob map. With `sm` back at its recorded commit and an untracked `newfile` inside it, `ls-files -m` and `--others` list nothing, so the map is `sm 160000 98f7026a…` whatever the submodule holds. Today the repository has no gitlink (`git ls-files -s | grep -c '^160000'` → 0), so this is latent.
Critique: the round-4 fix split "neither file nor link" into a nested repository (reuse off) and "now a folder" (deleted). A gitlink is the one tracked path that is a folder whose files never arrive through `--others`, so it falls into the wrong half. The lesson's rule ("any other kind of path turns reuse off") is not what the code does for it. The tempting fix is to hash `git -C <path> rev-parse HEAD` as `160000 <sha>`, which still misses a dirty submodule.
Consequences: turning reuse off for any gitlink means a future submodule disables reuse checkout-wide until someone designs how to hash one. That is the fail-closed choice the Design states ("every read fails closed"), and it costs nothing today.
Recommendation: in `workspace.blobs`, return `nil, "a submodule: <path>; reuse off"` when any `ls-files -s` entry has mode `160000`. Then the `-m` "now a folder" branch can only be a tracked file replaced by a folder. Pin it in `reuse-e2e.spec`'s nested-repository case: `git update-index --add --cacheinfo 160000,<the nested repo's HEAD>,nested`, then commit, then expect `digest() == ""`. Add "a submodule" to the lesson's How to apply.
Lesson: zz-arch/digests-hash-paths-as-git-stores-them

### F3 [low] The reused line drops the time the Design promises
Where: `z-nile/specs.luau` `gateCheckCommand` (`print("reused: an affected gate passed on this content")`); c0165.md Whole-gate reuse ("prints `reused: an affected gate passed on this content at <time>`") and line 190 ("`reused <passed_at>`").
Evidence: `resultsdb.gatePassed` returns `passedAt`, and nothing reads it. The probe's output above reads `reused: an affected gate passed on this content`, with no time.
Critique: a reader of a reused gate can't tell how old the pass is. The Design's two wordings also disagree with each other and with the sequestered specs' substring.
Consequences: appending ` at <ISO time>` keeps the substring check.sh and the specs match.
Recommendation: print ``reused: an affected gate passed on this content at {os.date("!%Y-%m-%dT%H:%M:%SZ", passedAt)}``, and correct line 190's `reused <passed_at>` in the Verification log.
