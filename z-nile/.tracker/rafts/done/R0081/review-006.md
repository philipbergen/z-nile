### F1 [medium] The blob map can't tell a tracked file from an untracked one with the same content, or a link staged as a file from a link, so specs and stages that read git's index are reused after the index changes
Where: `z-nile/lib/workspace.luau` `blobs` (a `--others` path gets `100644|100755 <id>`, the same value as a tracked entry; a `-m` path gets its working-tree mode and id, whatever the index holds); it feeds both `fingerprint.of` (per spec) and `fingerprint.digest` (whole gate). Readers of the index in the gate: `z-nile/tests/acceptance/c0183/registry.spec.luau:62` (`git ls-files --error-unmatch`, declared in `z-nile/tests/inputs.tsv:229-238` by its `.gitkeep` paths) and `z-nile/engine/skills.luau:304` `trackedNonLinks` (`ls-files -s` modes, run by the static stage `./zn skills --check`).
Evidence: all runs are in the scratch clone, with `ZN=<worktree>/zn`.
(a) Per-spec reuse, committed. On a branch `work` (with `refs/remotes/origin/main` set to its base), commit a newline into `arcade/.tracker/issues/active/.gitkeep`. Then `$ZN run --time 300 -- lune run z-nile/specs -- run --project z-nile -- tests/acceptance/c0183/registry.spec.luau` gives `3 passed, 0 failed`. Then `git rm --cached arcade/.tracker/issues/active/.gitkeep` and commit (the file stays on disk, untracked, not ignored). The same command prints `reused tests/acceptance/c0183/registry.spec.luau` / `3 passed, 0 failed, 1 spec files`. Run fresh in the same state (uncommitted), the spec gives `FAIL … registry.spec:64: arcade/.tracker/issues/active/.gitkeep is not tracked` / `2 passed, 1 failed`.
(b) Whole-gate digest, index only. `lune run z-nile/specs -- digest --mode affected --projects z-nile` printed `dee8d2bd…0a96507` with the `.gitkeep` tracked, and the same `dee8d2bd…0a96507` after `git rm --cached` (`git status`: `D ` plus `??`). The selection did not move either (registry was selected in both). So an affected gate recorded in the first state would be reused in the second while registry fails.
(c) A static stage. On the clean branch, the digest is `8cf019a9…c7cb79050` and `./zn skills --check` exits 0. Then `git update-index --cacheinfo 100644,<the link's blob>,.claude/skills/zz-review` (status `TT`). The digest is the same `8cf019a9…c7cb79050`, and `./zn skills --check` prints `.claude/skills/zz-review: tracked as a file (mode 100644), not a link` and exits 1.
Critique: the zz-arch lesson `digests-hash-paths-as-git-stores-them` (extended in this very fix for gitlinks) says to hash a path the way git stores it. Whether a path is in the index, and with what mode, is part of how git stores it, and two readers in the gate depend on it. Case (a) defeats the registry spec in exactly the state it exists to catch. The Design's audit declared registry's reads "by file", assuming the file's blob covers "is it tracked". It doesn't. The Design accepts affected-only forged passes for *undeclared* reads (backstopped by the merge's full gate), which is why this is medium, not high. This read is declared, and both the fingerprint and the whole digest still miss it. The tempting fix is to hash index ids beside working-tree ids. That makes every `git add` of a modified file move every fingerprint, so a gate before `git add -A && git commit` is never reused after it, which costs the reuse its main case.
Consequences: the narrow fix marks only presence and mode. A `git add` of a *new* file then moves the specs that read it once (untracked → tracked), which is cheap. Staging a modified file with the same mode moves nothing, and a commit moves nothing beyond today's HEAD-for-`*`. Every fingerprint and digest changes once when the code lands (a value format change). No db migration is needed: old rows simply stop matching and age out through `prune`.
Recommendation: in `workspace.blobs`, give a `--others` path the value `untracked <mode> <id>`. For a `-m` path whose `ls-files -s` mode differs from the working-tree mode, append ` index <index mode>`. Keep the `-m` id as the working tree's. Pin this in `z-nile/tests/tooling/reuse-e2e.spec.luau` (unsequestered) with three cases: `git rm --cached` of a tracked file left on disk moves `digest()` and a declared spec's fingerprint; `update-index --cacheinfo 100644,<blob>,<link path>` over a tracked link moves `digest()`; `git add` of a modified tracked file (same mode) leaves `digest()` unchanged (the cost guard). Run the mutant "untracked marker dropped" once and record it killed. Add "and whether the path is in the index, with its index mode" to the lesson's How to apply.
Lesson: zz-arch/digests-hash-paths-as-git-stores-them
