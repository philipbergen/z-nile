Where: `z-nile/.tracker/issues/active/c0302/acceptance/watch.txt` (this layer's diff); `acceptance/maintip.spec.luau:40`
Evidence: `./zn finish` wrote the ticket's watch from what the two specs require, since the layer changed no source file (`watchcmd.capture`'s fallback): `z-nile/tests/lib/fixture.luau` and `z-nile/tests/lib/t.luau`. maintip.spec reaches `layergit.mainTip` only through `.cache/c0302-maintip/probe.luau`, whose require is split on purpose (`"req" .. Design review 001 found that the rejected design (mainTip falls back to `HEAD` on a lone layer branch) passes every promoted spec except maintip.spec. A pull request that changes only tooling is gated by `z-nile/check.sh --affected` at `./zn finish`, at `./zn done` and at the merge (zz-rules, Merging, step 2). So that change would land on main with every gate green. The first thing to run maintip.spec would be the watch net, after the merge. The Design states this reach for the scan (`fixtures.spec`, "Where the rule is enforced") but says nothing about maintip.spec, which was added as the guard for exactly that mutant.
Critique: the guard holds inside this raft (RC1 and AC4 at `done`). After the raft it is the one promoted spec standing for Non-goal 1, and it runs only on the paths that never review a mainTip change: the full gate and the net. The tempting fix is a hand edit of `acceptance/watch.txt` to add `z-nile/engine/layergit.luau`. That file is sequestered, `./zn finish` is its only writer (zz-test, Affected selection, Capture), and a reviewer checks it against the derivation, so the edit is not allowed. Other fixes would change maintip.spec (sequestered) or the watch derivation (a tooling file, which RC1 forbids in this raft). None of them can be made in this layer.
Consequences: whichever path is taken, a later `./zn finish` must write the watch, so the fix needs a layer that the tooling's own rules let name `layergit.luau`. Re-preparing c0302 delays R0096 (d0298) and c0340, which wait on this raft, and R0073, c0123, c0248 and c0282, whose checks are red on their layer branches until it lands. Landing as is leaves a window. Until the follow-up lands, a tooling pull request that changes `mainTip` passes every pre-merge gate, and only the net catches it after the merge. When the net does catch it, it repairs the map (the failing spec's watch gains the changed sources) and opens a defect.
Recommendation: escalate to the user (zz-execute stop conditions; the fix needs a sequestered or tooling file), with these options:
(a) Land R0102 as it is. Capture one z-nile chore now: make the watch derivation see what a promoted acceptance spec runs through a probe, for example a declared watch line in the spec that `watchcmd.capture` reads, with c0302's promoted watch rewritten by that tool. Its acceptance would be that `lune run z-nile/affected -- z-nile/engine/layergit.luau` lists `z-nile/tests/acceptance/c0302/maintip.spec.luau`. Record the gap and the chore's id in c0302's Verification log.
(b) `./zn stop R0102` and re-prepare c0302 so that maintip.spec's dependency on `engine/layergit.luau` is one `./zn finish` derives, with the same affected-listing check in prep and again after finish.
(c) Accept the full-gate-and-net reach for maintip.spec, as the Design already does for the scan, with a `Decided with the user` line in the Design.
I recommend (a): it keeps the unblocking raft moving, and it fixes the general case, since any probe-run pin has the same hole.

## Candidate lesson (for the lead to file)
- Rule: when a sequestered spec reaches its subject only in a child process or through a require split to dodge the require scans (a probe), the watch `./zn finish` will write does not name that subject. That watch is the layer's sources, or, when the layer changes none, what the specs require. In prep, on a prototype with the spec and that watch in the promoted layout, check that `lune run z-nile/affected -- <subject>` lists the spec. The Design must say which gate runs the spec otherwise.
- Why: c0302's maintip.spec, the pin design review 001 asked for, watches `fixture.luau` and `t.luau`. A tooling pull request that changes `layergit.mainTip`, which is gated by `--affected` only, never runs it (F1).
- Check: for each promoted spec whose subject runs in a child process, does the selector list it for a change to that subject, given the watch finish will write? Best filed as a note on zz-test/specs-read-sources-through-the-selector, widened to `when: both`.
