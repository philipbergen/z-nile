### F1 [medium] A net kicked from under a `./zn run` is stopped by the reaper once that run's deadline passes: the deadline rule F4 restored reaches the net's own outer `bounded.pl`
Where: z-nile/engine/reap.luau:304 (`NET_SCRIPT`), :386-407 (`decide`: only `reap.isNet(p)` is a whole skip, `sheltered` only guards the orphan branch); z-nile/lib/bounded.pl:108 (only the forked child sets the new `ZN_BOUNDED_DEADLINE`; the waiting parent keeps the environment it was exec'd with); refute-001 F4 ("the net's own shell stays a whole skip while it is young, because it can inherit the kicker's deadline variable").
Evidence: the net's tree is `bash -c NET_SCRIPT ...` (the group shell) → `./zn run --time 3600 -- ./zn watch-net`, whose `zn` execs `perl bounded.pl` → its fork, which sets the net's own deadline and execs the net. That outer perl is a child of the shell and is exec'd with the shell's environment. So when the kick runs under a `./zn run --time N` (a person or agent wrapping `./zn land` or `./zn watch-kick`, or any bounded caller), the outer perl and its watchdog carry the kicker's deadline. Only the processes below the fork carry the net's own. My probe fed `reap.decide` that shape: the shell and pid 501 `perl .../bounded.pl --time 3600 -- ./zn watch-net`, both with `deadline = now - 100`, and pid 503 the net's `lune` with `now + 3000`, all in the main checkout. Output: `TARGETS 501:past its ./zn run deadline by 100s`. `treeOf(501)` is the whole net, so the reaper at the next `./zn sync` or gate start stops the net mid-suite, possibly mid-commit in the standing worktree. Round-1 code skipped this tree whole. The new deadline spec models pid 501 with no deadline, which is not the shape a bounded kicker produces. The perl's cwd is the kicker's checkout (`cd "$1"`), so the case bites at once for a kick from the main checkout (the dispatcher's `zn(ctx.mainRoot(), {"watch-kick"})`, a capture's `./zn land`), and from a raft worktree while that worktree still exists.
Critique: the refute named the inherited variable for the shell and stopped there. The perl directly below the shell inherits it the same way, and the shell's exemption protects nothing once its only child's tree is stopped. The tempting fix is to put `underNet` back in front of the deadline rule. That undoes F4: a stuck process deep in the net's suite would again escape the reaper's documented backstop.
Consequences: the fix must make the kicker's deadline stop at the shell, without sheltering anything below the net's own bound. The shell itself still carries it (its exec-time environment), and the existing `isNet` skip, which is limited by age, stays right for the shell. Removing the variable also matches G12's rule that nothing of the kick reaches the net's suite.
Recommendation: start `reap.NET_SCRIPT` with `unset ZN_BOUNDED_DEADLINE; ` (before `cd "$1"`), so the outer perl, its watchdog and everything below carry only the deadline the net's own `./zn run` sets. The kick and the reaper read the same constant, so recognition holds, and the sequestered reaper spec builds its commands from `reap.NET_SCRIPT` and stays green (re-run it). Add to `tests/tooling/watch-net-reaper-deadline.spec.luau` a case that pins the text (`string.sub(reap.NET_SCRIPT, 1, #"unset ZN_BOUNDED_DEADLINE;")`). Also add a fixture case: kick with `ZN_BOUNDED_DEADLINE=<now - 100>` in the kick's environment, and have the netfix stub suite record `$ZN_BOUNDED_DEADLINE`. Expect a value greater than the kick's start, which proves the suite runs under the net's bound and not the kicker's. The outer perl itself can be judged only outside the jail (ps is refused there). Run the zz-test "detached helpers meet the reaper" experiment once more, as prep's E1 did: a fixture net kicked under `./zn run --time 30`, then `./zn reap --dry-run --root <fixture main>` after 40 s. Record that it lists nothing in the Verification log, and add a Rules and mutants row ("the kicker's deadline does not reach the net").

### F2 [medium] A rerun the net leaves for the next kick is reported nowhere, and with real round lengths it is the usual outcome after a green round
Where: z-nile/engine/watchcmd.luau:1098-1104 (`finishRound` → "left", one line in the holding net's log); z-nile/lib/watch.luau:606-617 (`watch.again`: `left >= lastRound + 300`); watchcmd.luau:1125 (`noPassLine` measures from the pass commit); zz-execute Phase 6 step 1 (`watch-net: already running` is reported as a started net).
Evidence: (1) A rerun fits only when `left >= lastRound + 300`, with `left = 3600 - elapsed`. So after any round longer than (3600 - 300) / 2 = 1650 s, every requested rerun is left. A green round is the full gate plus the slow tier. Full gates in the repo's reports took 270 s to 1096 s, and the slow tier "hit the 3600 s limit on a loaded machine" (c0251.md:660). So a landing made during a green round will in practice be left, not rerun. (2) Nobody is told. The kick that asked printed `watch-net: already running (pid N); a rerun is requested` and exit 0, which Phase 6 reports as the net running. The "left" line lands only in the log of the kick that started the holding net, which no one is reading by then. The no-pass line cannot catch it either. My probe's origin shows round 1's pass commit rebased on top of the landing it never tested (`... the suite passed` above `a source landing`), because `pushMain` rebases onto the new main. So `<pass>..origin/main` excludes that landing, and the pass commit's time is newer than it. The landing is tested only when some later landing kicks. At the end of a working day that can be the next morning, and until then main may be red with nothing saying so, which is the failure d0383 exists to end. (3) The fit prediction also misjudges the common red-then-green order. A round whose fast suite failed runs no slow tier, and a tracker-only round takes seconds. The next round then passes the check and runs fast plus slow past the bound, the kill in the middle of a git write that round 1's F2 was about.
Critique: round 1's recommendation stopped at "leave the request". The tempting fix is to make every rerun a fresh net. That breaks the sequestered AC2 case, which settles the first kick's log and expects `start end start end` and `a rerun was requested` in it.
Consequences: a request that does not fit must still run, under a bound of its own, and AC2's in-process rerun must stay as it is when the round fits. A fresh net started by the ending net has to be one the reaper recognises (`NET_SCRIPT`, `$1` an absolute folder) and one the lock admits (the mutex already handles a kick that takes the lock in between: the fresh net then records a request with it). Chains last only while landings keep requesting.
Recommendation: when `finishRound` would return "left", give the lock back and start a fresh net the way `kick` does (its own kick files in `watch.filesDir(main)`, `bash -c reap.NET_SCRIPT reap.NET_ARGV0 <netDir> ...`, so it runs the standing worktree's `zn`, which is origin/main's engine, under its own 3600 s). Do not wait for its marker. Print `watch-net: the rerun goes to a fresh net, log at <path>` and exit 0. Keep `again` for the in-process decision, and predict with the longest round so far instead of the last, which removes the tracker-only-then-full misjudgement and narrows the red-then-green one. Spec changes: the survives spec's `--limit 1` case expects the first log to name a second log, that second log to settle `0`, `hold/runs` to read `start end start end`, and no `rerun` or `lock` left at the end. Add a pure case to `again` for the longest-round rule. Add a Rules and mutants row ("a rerun that does not fit runs in a fresh net"), and run the mutant "leave it" against the case. If the author prefers to keep "left", the alternative is to escalate to the user: the cost is a landing untested until the next landing, made visible by a line (`watch-net: a rerun waits for the next kick since <time>`) that the kick and the board print while `rerun` exists and no live lock holds.
