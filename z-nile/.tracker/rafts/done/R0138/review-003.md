### F1 [medium] A net kicked from under `./zn run` runs every process under the kicker's CPU limit, which neither the new process group nor the `unset` sheds and the net's own `./zn run --time 3600` cannot raise
Where: z-nile/engine/reap.luau:307-314 (`NET_DETACH`, `NET_SCRIPT`); z-nile/lib/bounded.pl:62-68 and the `exec ... zn_lower_cpu` line (`--cpu` defaults to `--time`, and "a limit cannot be raised again"); z-nile/lib/cpu.sh (`ulimit -t`, which sets the hard limit too); z-nile/tests/tooling/watch-net-bounded.spec.luau (kicks under `--time 60` and `--time 3`); zz-test SKILL.md "The net" ("nothing of the kick reaches the net's own suite"); refute-002 F1.
Evidence: `./zn run --time T` puts `ulimit -t T` (soft and hard) on its command, and every process the kick starts inherits it: `setpgrp` changes the group, not the resource limits, and `unset` changes only the environment. Probe P3: under `./zn run --time 20` the detached shell reports `soft 20 hard 20`, and the net's own `./zn run --time 3600` keeps 20 with its note. Probe P1: in the bounded spec's own fixture, the stub suite inside the net ran under a CPU limit of `60` in the first case and `3` in the second. The spec passes because the stub suite spends no CPU. A real net kicked by `./zn run -- ./zn land` (the default `--time` 60) or by the second case's shape runs its engine, the gate's runner and every spec process under 60 s (or 3 s) of CPU each, where a normal gate gives a spec 1200 s (`PICKMAN_SPEC_CPU`) and the engine 1800 s (`ZN_ENGINE_CPU`). A spec that passes in a normal gate then dies of SIGXCPU in the net, and the net pushes a repair or a `slow-tier-red` defect for a red that main does not have, or the net's engine itself stops at 3 s and the run ends with exit 125 in a log nobody reads. Before round 2 the same kick lost its net to the group kill, so the limit never mattered; the round-2 fix makes this the live case, and the bounded spec, written to prove that case works, cannot see it.
Critique: refute-002 F1 and the new lesson name two things the starter hands down, its environment and its process group, and stop there; the zz-test line now claims nothing of the kick reaches the suite. The tempting fix is `ulimit -t unlimited` at the top of `NET_SCRIPT`. It fails: an unprivileged process cannot raise a hard limit, which `zn_lower_cpu` sets.
Consequences: since the limit cannot be raised from inside, the fix is either to refuse to start a net that would run crippled, or to change how every setter lowers the limit. Refusing means a bounded kicker gets a stderr line and no net (the landing ignores the kick's result but prints its line), which narrows the coordinator's ruling that a net kicked under `./zn run` survives it to kickers whose CPU limit is high enough, so it needs a recorded guess for the user. Lowering only the soft limit in `cpu.sh` (`ulimit -St`) keeps the full scope but changes c0191's "limits only lower" rule for every caller: any process could raise its own soft limit back to the hard one, and the spec jail's 1200 s and the hook's 2 s become soft.
Recommendation: in `watchcmd.kick`, before starting the net, read the hard CPU limit (`sh -c 'ulimit -Ht'`). When it is a number below a floor, the CPU every spec gets in a normal gate (the spec runner's default, `PICKMAN_SPEC_CPU` 1200, from one named constant), do not start the net. Print `watch-net: not started: this command runs under a CPU limit of N s per process, the net needs N2 s: run ./zn watch-kick from a shell without a ./zn run around it` on stderr and return false. In `NET_SCRIPT`, raise the soft limit to the hard one (`ulimit -St "$(ulimit -Ht)" 2>/dev/null;`) so a kicker that lowered only the soft limit does not cripple the net. Record a guess (build) for the user that a kicker below the floor gets no net, with the soft-limit rule of `cpu.sh` as the scope-keeping alternative. Spec changes in watch-net-bounded: both survival cases kick under `./zn run --time <T> --cpu 1800` (the spec runner's own 1200 then holds, which equals the floor) and the stub suite records `ulimit -t`, expected `1200`; a new case kicks under `./zn run --time 60` and expects exit 1, the `not started` line, no `.exit`, no lock and no `hold/started`. Fix the zz-test sentence ("nothing of the kick reaches the net's own suite") and add the CPU limit to the lesson's list of what a detached tree inherits. Add a Rules and mutants row ("a kicker's CPU limit below the floor starts no net") and run the mutant that drops the check.

### F2 [low] A failed hand-off is pinned by no case, and its line says the request stays when the fresh net may already have removed it
Where: z-nile/engine/watchcmd.luau, `net` (the `kicked.ok` false branch: "it stays requested", `handoffFailed`, `process.exit(1)`); `takeLock` (removes `rerun` when it takes the lock); z-nile/tests/tooling/watch-net-handoff.spec.luau (the success case only); refute-002 F2 ("if the hand-off kick fails the net leaves the request and exits 1").
Evidence: mutant M1 (the branch no longer sets `handoffFailed`, so a failed hand-off exits 0) passes the handoff spec, 2 passed, and no other spec names the path. Consequences: none beyond the wording and one case.
Recommendation: say what is known: `watch-net: the rerun could not be handed to a fresh net: <the kick's line>; the next landing's kick runs it`. Pin the branch: either a fixture case in which the hand-off kick fails on a trigger the spec holds on a marker (expecting the first net's exit `1`, the line, and no lock), or, if no trigger fails only the fresh net and not round 1's own push, a pure case on a `watch` helper that turns the hand-off kick's result into the line and the exit code; run M1 against whichever it is.
