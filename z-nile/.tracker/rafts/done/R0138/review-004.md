### F1 [medium] G16 keeps a dispatched step's credential and wrapped git in the net, and with them the net can never push: G16's reason is false, and such a net swallows the reruns of real landings while it runs
Where: guesses.md G16; d0383.md Verification log (code review 003: "a dispatched step's variables and wrapped git (kept on purpose, guess G16; no case)"); zz-test SKILL.md "The net" ("a dispatched step's variables and PATH included, so the net never holds authority its kicker lacked"); z-nile/engine/watchcmd.luau `pushMain` (`git push -q origin HEAD:refs/heads/main`) and `PASSED = "z-nile/watch-passed"`; z-nile/engine/main.luau `land` (the `ZN_PUBLISH_BROKER` branch, then `watchcmd.kick`); z-nile/engine/dispatcher.luau (the step `env`: `PATH = {repo}/z-nile/bin:…`, `ZN_PUBLISH_BROKER`, `cred.agentEnv`); z-nile/engine/credential.luau `agentEnv`; z-nile/engine/wrapper.luau `decidePush`.
Evidence: a dispatched z-ticket step is a normal path (`./zn dispatch "<description>"` picks `z-ticket`, dispatch.luau; z-ticket step 6: "Under the dispatcher, land without asking"). Its `./zn land` pushes through the broker ("inside a dispatched step the agent's credential can't push to main: the dispatcher pushes it (c0117)") and then calls `watchcmd.kick`, whose floor passes (the step runs under the dispatcher's 1800). The net then inherits the step's environment: git's credential helper answers with `ZN_AGENT_GH_TOKEN` (the bot, which cannot push to main), `SSH_AUTH_SOCK` is empty, and `git` on PATH is z-nile/bin's wrapper. The net's pushes are plain `git push origin HEAD:refs/heads/main`, never the broker, and the wrapper passes a push to main only when it "fast-forwards main with tracker state only" (wrapper.luau); `z-nile/watch-passed` and the watch files a repair extends are not under any `root` in projects.toml (`trackerstate.under`), and past the wrapper the bot's token cannot push to main at all. So G16's "Why" ("the net then pushes through the same wrapper and broker as the step that started it") is false: the wrapper refuses every push the net makes and the broker is never asked (and belongs to a dispatcher that ends with its run). Such a net runs the whole fast suite holding the one lock, then fails with `watch-net: could not record the passing commit on main` (or `push rejected twice` for a repair), and never runs the slow tier. A landing that kicks meanwhile gets `already running; a rerun is requested`; the crippled net runs that rerun itself ("again" removes the request) with the same environment, and a hand-off kick is started by the crippled net's own engine and inherits it too. So a real raft's landing can lose its net run to a capture that a dispatcher landed a minute earlier, with only an exit 1 in a log nobody reads.
Critique: G16 weighed the right risk (an unattended step's descendant must not gain the user's credential) but not what the net needs: it pushes non-tracker files to main, which only the user's credential may do. The tempting fix is to strip the step's variables in `NET_SCRIPT` (or in the kick); it fails G16's own test, since the net would then push with the user's keychain credential on an unattended agent's say-so.
Consequences: the net must start with the authority that pushed the landing, and in a dispatched step that is the dispatcher, not the step. Refusing in the kick alone would leave a dispatched capture's landing with no net, which narrows "the net runs after every landing"; so the dispatcher must kick in its stead. The dispatcher's broker push runs in the dispatcher's own environment with the user's credential, the one that put the landing on main, so a kick there holds no authority the landing lacked. A broker push also carries spend and state commits; kicking after each is harmless (one lock, one rerun at most) but noisy, so kicking once after a step whose broker pushed anything, or after a z-ticket step that ended `ok`, is enough.
Recommendation: in `watchcmd.kick`, after the CPU check and before any file, when `ZN_DISPATCH` or `ZN_PUBLISH_BROKER` is set, start no net, print `watch-net: not started: a dispatched step's net could not push to main; the dispatcher starts it after the step` on stderr and return false (`land` already ignores the result). In dispatcher.luau, after a step whose broker pushed at least one commit (`st.pushed` grew), run `zn(ctx.mainRoot(), { "watch-kick" }, true)` as `merge` does. Replace G16 with a build guess for the user stating this, with "strip the step's variables" as the rejected alternative and why. Cases: in watch-net-quick (or bounded), a kick with `ZN_DISPATCH=1` and `ZN_PUBLISH_BROKER` set exits 1 with the line and leaves no `watch.filesDir` folder; a Rules and mutants row ("a dispatched kick starts no net"), with the mutant that drops the check run; for the dispatcher's kick, a case in the dispatcher's existing fixture specs if one already drives a broker push, otherwise a `reasoned` row. Fix the zz-test sentence and the table row.
