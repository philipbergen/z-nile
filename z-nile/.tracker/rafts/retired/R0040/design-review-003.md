### F1 [medium] (repeat of design-review-002 F3) The writer/capture split is still by skill, so a lead in a prep or raft worktree gets two contradictory lesson instructions, and ticket-prep and execute-raft file every non-review lesson in their own folder
Where: c0111.md The skills ("ticket-prep and execute-raft write lesson files…", "Every other skill captures an issue. It never writes a lesson file"); c0111.md Files ("A lesson is one Markdown file … in the folder of the skill whose work it improves"); prototype Lessons sections of testing, architecture, tracker, review (and ticket-prep, execute-raft); execute-raft Phase 2B step 2
Evidence:
- The prep author follows ticket-prep and, for specs, the testing skill (ticket-prep step 4). If the user corrects a spec-writing mistake, testing's Lessons section says "This skill never writes a lesson file itself (its work can't land one) … capture it instead: `scripts/tracker.sh new issue c lesson-<slug>`". ticket-prep's section, which the same agent is also following, says a lesson from "the user corrected you" "goes in `.claude/skills/ticket-prep/lessons/` too, with `from:`". Both apply, and they disagree. The first one's reason is false for this agent: a prep worktree can land the file.
- Following ticket-prep's version puts a testing lesson under `ticket-prep/lessons/`. That contradicts the Files rule above. It also hides the lesson from the agents that need it: streams and code reviewers read `lessons --skill testing`, and the prompt carries only `build`/`both` lessons, while a ticket-prep lesson is usually `design`. execute-raft's section does the same for a raft lead: a build lesson about architecture lands in `execute-raft/lessons/`.
- The review skill's section tells the reader to capture with `tracker.sh new` and, in the next sentence, says a subagent never runs it. Every reader of the review skill in reviewer mode is a subagent, so the first instruction is dead text for its main audience.
- design-review-002 F3 also asked that execute-raft Phase 2B step 2's stream rules say where candidate lessons go, and that the lead's harvest pick them up. The prototype's Phase 2B is unchanged. Only the role sentence in the three skills that streams read covers it, and nothing tells the lead to turn a stream's reported lesson into a file.
Lesson: ticket-prep/instructions-runnable-where-they-run. Its own sharpened `check`, from round 2, says the split "has to be by role, not by skill". The Design still decides writer versus capturer by which skill's text is read, and only the subagent case is by role.
Critique: This is the third round on this mechanism (round-1 F5, round-2 F3), so per the review skill the mechanism should change, not get a third clause. The tempting fix is a fourth sentence in testing, architecture and tracker ("unless you are leading a prep or raft"), which leaves eleven hand-written variants to drift.
Consequences: Deciding by role makes the rule identical in every skill: what an agent may do depends on where it runs and whether it was launched by another agent, not on which skill it is reading. That adds two consequences:
- A lead in a prep or raft worktree writes lesson files under skills outside its Touched modules. Spend splits unclaimed files evenly, so this is harmless, and the files ride the prep commit or the PR like the harvest's.
- The folder a lesson goes in becomes "the skill whose work it improves" in every case, as Files already says, so ticket-prep's and execute-raft's "goes in `<own>/lessons/`" sentence has to go.
Recommendation: Replace the two forms with one role-based paragraph, the same in all eleven Lessons sections apart from the skill name in the read command:
- read `scripts/tracker.sh lessons --skill <s> --full` at the start;
- **a subagent** (stream, reviewer, any agent with a brief) never writes a lesson file or runs `tracker.sh new`, and puts the candidate (rule, why, check question) in its review or final report;
- **the lead of a prep or raft** writes `.claude/skills/<the skill the lesson improves>/lessons/<slug>.md` (with `from:` when it did not come from a review), and commits it with its work;
- **any other lead** (main checkout, capture, metrics) captures it through make-issue with `new issue c lesson-<slug>`.

Put this under The skills in place of the two bullets. Add to execute-raft Phase 2B step 2 that candidate lessons go in the stream's final report, and to Phase 4 step 5 that the lead writes them (with `from:`) alongside the round's harvest. In skill-docs.spec, check that every Lessons section contains the three role clauses (fixed phrases), that none says "never writes a lesson file itself", and that Phase 2B names lessons in the final report. Rows: "a prep or raft lead writes the lesson in the skill it improves" (mutant: ticket-prep's section routes it to `ticket-prep/lessons/`), and "a stream reports candidate lessons" (mutant: the Phase 2B sentence dropped). Add a source for `ticket-prep/instructions-runnable-where-they-run`.
