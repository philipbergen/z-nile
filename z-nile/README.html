AI setup · the tooling behind this repository

z-nile

z-nile takes a one-line idea to a merged, tested pull request. You decide the idea and you approve the result. AI workers carry everything in between. This page is the illustrated guide: why it exists, how it works, and how to use it.

Part 1 · Intention

People decide. Workers deliver.

You have an idea: a feature, a bug fix, a chore. z-nile turns that idea into code on the main branch, with tests, reviews and a record of why. You are asked for two things only: the idea, and an approval. Everything else is done by AI workers, which are AI command-line tools such as Claude, Kimi, Grok or Cursor's agent.

What it is good at

Working code

z-nile is very good at writing code that works and is tested. A ticket is designed first, its tests are written before the code, and the code is reviewed by a fresh reviewer who has never seen the author's chat.

What the work is now

Fast and cheap

The current work is making that same quality quick and inexpensive. Easy tickets get fewer review rounds and lighter models; risky ones get more of both. Cheap models do the building, strong models review.

What you keep

The last word

A worker never waits for you. When it needs a decision, it records a guess and carries on. Nothing that you have not approved reaches the main branch.

Goals

Open on every side

  • Any AI CLI. Today the repository wires in Claude, with Kimi, Grok and Cursor's agent as fallbacks in .models.toml.
  • Any language. The gate is a plain bash script that calls whatever runs the project's tests. This repository's own projects use Luau.
  • Any test suite. The same gate shape: z-nile asks whether it passes and does not care what is inside.

goal Applying z-nile to other languages and CLIs is the aim; this repository is the first test.

Goals

An app for everything but code

An optional rich app is meant to show tickets, rafts, approvals and who is working on what, so that the only thing you ever read as text is code. planned

A clickable mockup exists: open the app mockup (ticket f0425). It is a picture of the plan, not a working app.

Part 2 · High-level mechanics

One ticket, six stages

Every ticket moves down the same river. These six names are the names for a ticket's place going forward: idea, design, code, review, approval, landed. A ticket that leaves the flow without landing is called closed.

1

Idea

/z-ticket

You describe the work. It is captured as a ticket: a feature f, a defect d or a chore c. The text of the idea is the scope no later stage may shrink. Only you narrow scope.

2

Design

/z-design

The worker designs the ticket until any strong worker could build it on the first try. The tests are written here, before any code, and the builder cannot edit them. The ticket also gets a risk level (easy, normal or risky), which you can overrule.

3

Code

/z-work · /z-run

Related tickets are grouped into a raft (/z-raft) and readied (/z-ready). A worker then delivers the raft as a stack, one layer per ticket. Everything happens in a git worktree under .worktree/; the main checkout is never edited.

4

Review

zz-review

A reviewer with a clean context reads the work and numbers its findings. The author answers each one: fixed, refuted with evidence, or deferred. How many rounds are allowed depends on the risk level. The maximums, by default 2, 5 and 9 rounds for easy, normal and risky design reviews.

5

Approval

./zn approve

A worker never waits for you, so it records a guess for every choice the approved design does not already make. You walk through the guesses, one at a time, in a plain terminal. Each ruling is yours. If the design changed after you approved it, the merge is refused until you approve again.

6

Landed

./zn done

The final gate runs once, the stack merges in a single merge, and the ticket moves to its done/ folder. Every review finding has by now become a lesson that later workers search before they act.

The other words

What the rest of the vocabulary means

Items marked planned are designed or captured as tickets and are not built yet.

  • TicketA unit of intent. A feature (f), a defect (d) or a chore (c), each with a number such as c0436. Kept as a folder of Markdown files in git.
  • RaftA unit of delivery: a stack of tickets with one layer each, delivered together and landed in one merge (R0010). A ticket in no raft can be worked on its own; making the light path automatic for easy tickets is planned
  • TributaryA theme that groups rafts and tickets, such as worker or fast-gate. The list lives in z-nile/.tracker/tributaries.toml and ./zn list can show one.
  • WorkerAn AI CLI session that asks ./zn work next for one action, does it and asks again. Several workers, from different vendors, are meant to pull whatever activity each can deliver from one queue. Today a person starts each worker. planned for the pull-by-activity queue across vendors.
  • Risk leveleasy, normal or risky, chosen at design. It sets the most review rounds allowed and which model size does each activity. The sizes are the aliases xlight, light, heavy and ultra; a CLI may define only some of them. ./zn model and ./zn rounds read them. The repository's .models.toml does not define the four aliases yet. planned
  • GuessA worker never waits. It records a guess (./zn guess) and goes on. Guesses are listed with ./zn guesses, and unapproved guesses never reach main. A worker never guesses a scope cut.
  • Approval sessionThe walk-through where you rule on every guess: ./zn approve. It starts a CLI on your terminal, and only your y/N in that terminal records anything.
  • LessonsEvery review finding becomes a lesson, filed under the step that made the mistake. The plan is for every guess you change to become one too. planned ./zn lessons searches them.
  • Gatecheck.sh is plain bash that calls whatever runs the project's tests. --affected while working; --full once at the merge. A guard that refuses to start the gate when the machine's kernel memory is filling (ticket d0426) is planned
  • Live layerA small daemon written in Go that runs on one machine and records who is working on what, with an event for every step forward. ./zn work status reads it. The daemon and its events are built; the app that will show them is planned
  • TrackerNo server and no database. Tickets, rafts, claims and spend rows are files in git. Moving the tracker into its own repository is planned (f0428)
  • OmarchyThe first real trial of z-nile outside this repository: one Go app, the tracker in the owner's own repository, a public board, and a bridge to GitHub issues (f0427 to f0430). planned
  • Work profileOne environment variable that picks a named set of relaxations (fewer rounds, who merges, which gate) and stamps its name on every row it writes (c0433). planned

Part 3 · How to use it

From idea to merge, in seven steps

Run these from the main checkout of the repository. ./zn is the one command everything goes through. ./zn help lists all of it.

  1. Capture an ideaOpen an AI CLI and run /z-ticket, then say what you want in your own words.Stage: idea.
  2. Let a worker run./zn work takes the next thing any ticket needs. ./zn work R0010 delivers that raft and every raft it depends on. In a CLI session, /z-run R0010 does the same.Stages: design, code, review.
  3. See where things are./zn board writes the whole tracker as one HTML page. ./zn work status says who holds what. ./zn work graph R0010 shows a raft and what it waits on. ./zn list active worker lists items in one state and tributary.
  4. Approve./zn approve R0010 (or a ticket id) walks you through every ticket that waits for approval, one guess at a time. Run it yourself, from a plain terminal. An agent never records an approval.Stage: approval.
  5. Check models and rounds./zn model <activity> prints which model runs an activity. ./zn rounds <id> prints where a ticket's reviews stand.
  6. Run unattended, if you want./zn dispatch <id> runs each remaining step headless. It never merges the final pull request, and where it would need an answer it writes questions.md and stops.
  7. Run the gatez-nile/check.sh --affected while you work; z-nile/check.sh --full once, at the merge.Stage: landed.

Each of these commands has a skill that holds its rules: z-ticket, z-design, z-raft, z-ready, z-work, z-run, z-approve and z-stop, in z-nile/skills/. /z-stop R0010 gives a readied raft back.

Where things live

A map of the folders

  • <project>/.tracker/The tickets and rafts of each project: issues/ and rafts/, with active/ and done/ beside them. z-nile's own are in z-nile/.tracker/, with tributaries.toml.
  • z-nile/skills/The rules each step follows, as SKILL.md plus a lessons/ folder. Each project's own skills are in <project>/skills/.
  • z-nile/engine/The code behind ./zn. Strict Luau on Lune.
  • z-nile/go/The live layer daemon, in Go.
  • z-nile/tests/The tooling's own specs. Promoted tests of each ticket are in tests/acceptance/<id>/.
  • z-nile/check.shThe gate. Each project has a check.sh that calls it.
  • .models.tomlWhich model and CLI does each activity, plus the fallback CLIs.
  • AGENTS.mdThe rules every AI CLI reads first, and the table of which skill to read when.
  • z-nile/README.mdThe reference text: the current map of every part.
