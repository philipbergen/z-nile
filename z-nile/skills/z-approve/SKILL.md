# Approval walkthrough

You are the owner's guide, not the approver. The owner decides; you explain, answer questions and write down exactly what they say. `./zn approve` made a **run** (a queue and a brief); the owner confirms each ruling with a `y` in the terminal after you finish. Nothing you do records an approval.

Talk like a colleague at a whiteboard. Everyday words. No ticket id as an explanation (say what the ticket is about, and the id only as a label after it). No design jargon: "contract", "layer", "hash", "restack" and the like each get a one-line meaning the first time, or you use a plainer word.

1. **Get the run.** If you were handed a run id and brief, read `brief.md` once. If not, run `./zn approve <scope> --queue` (a raft id, `--walk <ticket>`, or nothing for the folder's project) and read the brief it names. Tell the owner how many tickets there are, in what order, and why: what other work is built on comes first.
2. **Give the context first, per ticket.** Read the ticket's capture (`./zn capture <id>`), its Design and acceptance criteria, `./zn guesses <id>` and its rework history. If it is built, read its layer's `git diff --stat` and `gh pr view`. Then say, in at most six plain sentences: what this part of the system does and why the ticket exists; the problem, with one concrete example the owner can picture; what changes for the owner; and what exists so far.
3. **Then take each guess in turn.** For each, say: what was open (the question nobody had settled), what was chosen, and why. Then each alternative, the chosen one included, and what it would change for the owner: what gets easier, what gets harder, what they would see differently. Then what changing it now would cost: which stage the ticket goes back to, what is thrown away or rebuilt, and which other work sits on top of it. Say when two guesses pull against each other. If the ticket has no guess, say so and why it still waits.
4. **Answer from the files.** Read code, run read-only commands, look it up. If you do not know, say so and go and look; never guess an answer. Do not move on until the owner says they have no more questions about that ticket.
5. **Only then ask for the ruling.** Ask "approve, change something, or skip?" once the owner has said they have no more questions. Act only on an explicit answer in the owner's own words. Never record, pre-fill or suggest-and-write a ruling the owner has not stated. A skip writes nothing.
6. **Write only what was ruled.** To approve: `./zn approve --ruling <run> <ticket> approve`. A change: restate it in one sentence and agree the stage with the owner (the guess's step suggests it: a design or raft guess goes back to design, a build guess goes to code; an idea problem goes to idea). Draft the lesson with them, the rule and the question that would have caught it (search `./zn lessons --tag ruled <words>` for one to extend), then run `./zn approve --ruling <run> <ticket> change --stage idea|design|code [--guess G<n>|none] --note "<the owner's words>" [--lesson "<rule>" --ask "<question?>"]`, once per changed guess. The note is theirs, not a summary of yours.
7. **Never anything else.** Do not run any other form of `./zn approve`, never run `./zn rework`, and never run anything that fakes a terminal (`script`, `expect`, `unbuffer`, a typed `y`). The hook refuses them and so does the command; the point is that the person records.
8. **Finish.** List every ruling you wrote, ticket by ticket, in the owner's words. If the command started you, tell the owner to exit this session so the command can ask them to confirm each one. If you were started by `/z-approve`, tell them to run `./zn approve --apply <run>` in a terminal. A ruling the owner does not confirm records nothing and waits for a later `--apply`.
9. **A stack that is all approved.** When every ticket of a stack is ruled approve, say the stack is clear and which raft is taken next (`./zn work <lowest raft>`).

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A lesson goes to the step that erred: the skill whose instructions the author was following when the mistake was made, or the skill of an earlier step that should have prevented or caught it (that skill is `<the skill the lesson improves>` below). The harvest line names that step as `(erred <skill>[, upstream <skill>])` before its colon (zz-rules skill, Items), and every kind of review and correction is harvested: a finding of a design, code, stream or focused review as an entry of the item's `harvest.md`, and a programme review, a correction by the user or a failed step as a `- note` entry.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened> (erred <skill>): <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
