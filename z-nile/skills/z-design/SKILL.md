# Design

The goal is an issue that **any strong agent can deliver on the first attempt without asking questions.** z-design designs one issue to `design: ready` and status `prepared`, and does not create a raft: `z-raft` groups prepared issues into rafts afterwards. Time spent here is cheaper than rework. Be thorough.

**Scope is what was captured.** An issue's scope is its title, its Problem and the ideas under its Solution as they stood at capture (`./zn capture <id>` prints that version: the newest commit on `origin/main` whose subject is `tracker: new` followed by a list of ids that includes the item's id at the time, or else the document's first add, marked `(no capture commit: first add)`, across folder moves; an id change is never followed, and the result says so), plus the `Scope decision (user, YYYY-MM-DD)` and `Decided with the user (YYYY-MM-DD)` lines added since. Prep adds the Design and the criteria, and may add detail: it keeps the captured Solution bullets as they are and adds after them. It never rewrites, narrows, defers or drops a captured outcome, and Non-goals fence only what the capture did not ask for. Only the user changes scope: ask them (AskUserQuestion in Claude Code; otherwise stop and report the options and what each costs as your result), then record the answer in the Problem as `Scope decision (user, YYYY-MM-DD): "<their words>"`. A reviewer's recommendation is not a decision, and neither is your own judgement that an outcome is too hard. A scope too big for one raft is split into sequenced rafts, never shrunk. Splitting an issue moves outcomes into new issues captured through z-ticket, and that is the user's call too: the original Problem gains a `Scope decision` line naming the new ids.

## 1. Claim the issue
**Work in a prep worktree** for the whole design (specs, experiments, reviews): `cd "$(./zn worktree prep-<slug>)"`, named by the issue's slug (zz-rules skill, Worktrees). Design reviews run there too, and their files ride in the design PR.

- **Sync first**: `./zn sync` (zz-rules skill, Sync and claim). **Candidates**: `./zn status` (what is `new`, and what others have claimed) and `./zn list backlog`.
- **Claim it**: `./zn status <id> preparing` publishes the claim on `origin/main` at once, and refuses an issue another terminal holds. Give it back with `./zn status <id> new`. An issue already in a raft is redesigned through its raft: the claim refuses it until z-raft takes it out (`./zn unfold <R-id> <id>`). z-design makes no raft: it ends at a prepared issue with no raft, and z-raft groups it later.
- If an issue is missing, create it first with the `z-ticket` skill.

## 2. Product decisions and architecture
`pickman/.tracker/game-design.md` holds the user's product decisions for the game, and it's binding. A design that needs to change a decision stops and asks the user. The issue's Design **quotes the decisions it relies on**, so z-raft can carry them into the raft's Theme and the execution prompt.

Any new dependency edge goes in the project's architecture map (`pickman/.tracker/architecture.md`) now, including the ```` ```deps ```` block.

## 3. Design each issue in detail
First read the checklist for the issue's type, `checklists/<feature|defect|chore>.md` beside this skill (`z-nile/skills/z-design/checklists/`), and answer every item of it in the Design. Then fill every section of the issue template. Requirements:
- **Design**: concrete paths, public types and function signatures, the pure/adapter split, and server authority. Scalability, Maintainability and Usability are answered specifically (see the design checklist of the project's architecture rules: `pickman-arch` for pickman, `zz-arch` for the tooling), not with platitudes.
- **Touched modules**: one backticked path per bullet. Then run `lune run z-nile/affected -- <paths>` and paste its output, plus the new specs, into **Affected specs**.
- **Unknowns & experiments**: list every assumption you can't *prove* from the repo or from docs you've read.
  - Each gets a pass/fail question, a method and a fallback.
  - **Run the cheap ones now** (Lune spikes, `rojo build` probes, doc checks) and record the results. What's left becomes the executor's Phase 1. Run every probe, experiment, loop and background command you start yourself (anything that is not the gate, a check, a `./zn` command or the spec runner) through `./zn run --time <seconds> -- <command>`: it stops at its limit, when it ends and when you do.
- **Regression guard**: name the existing specs and behaviors at risk, and add regression specs to the Test plan.
- **Override check**: promoted specs in `tests/acceptance/` are never edited during execution, so find the conflicts now.
  - For each Touched path, run `lune run z-nile/affected -- <path>` and `grep -rlF -e <path> tests/acceptance`, and read every spec either lists. The selector alone misses specs that read a file as text; neither sees a spec that builds paths or walks a directory, so also skim the `tests/acceptance` folder names for the area. Output `ALL` carries no list (any `scripts/` or config path): use the grep alone for that path, and repeat it with the file's basename.
  - For each promoted spec S whose pinned behavior the issue deliberately changes, name S on an `Overrides:` line in **Regression guard**.
    - A chore changes S in its own raft.
    - Any other type: file a chore c that only has to remove or narrow S (prefer narrowing; if S must go, c also drops the line naming it from the owning item's `check.sh`), so `main` stays green (a spec that asserts behavior `main` doesn't have yet can't land). c names S on its own `Overrides:` line, which satisfies the check for c. The issue's Test plan gets a case that pins the new behavior, its `Overrides:` line names S and c, `depends_on: [c]` goes in its frontmatter, and the raft z-raft puts it in says in its **Order & dependencies** that c must be in `done/` before `start` (z-ready refuses otherwise). A product decision behind the change goes to the user now.
  - If there is none, write `Overrides: none`.
- **Test plan**: `spec file :: case → ACn`.
- **Rules and mutants**: a table with one row per behavioural rule in the Design: `| rule | spec :: case | mutant it kills | checked |`. The mutant is a plausible wrong implementation, and the spec case must fail for it. `checked` is `run` if prep's mutation check ran it, else `reasoned`. When you prototype, fill the table from the mutation check.
- **Acceptance criteria**:
  - **Checked**: nearly all criteria.
  - **Judged**: only with a rubric.
  - **Observed**: minimal Studio steps.
  Push hard to turn Judged and Observed criteria into measurable proxies (see the zz-test skill).
- **Implementation steps**: small, ordered, and each one verifiable.
- **Size and solo** (frontmatter, for z-raft): `size: <n>`, your estimate of the changed lines the executor will count (code, skills and docs; the acceptance specs, `check.sh` and experiments you write here are prep's and not counted). z-raft sums them against its cap of about 1,500 lines, and an issue over it is a raft by itself, never split. `solo: true` only when a recorded user decision says the issue lands as its own raft (a `Decided with the user` line such as "the work lands as sequenced rafts"); z-raft never folds a solo issue with others.

## 4. Write the executable acceptance
- **Issue checks**: `check.sh` for each issue, with one `check "ACn: …"` per Checked criterion.
- **Raft checks** are z-raft's (RCn lines in the raft's `check.sh`). `./zn ready` rewrites only the moved items' own literal paths in their `check.sh` files, so an issue check finds another item with `./zn find <id>`, never a hard-coded backlog path.
- **Write the acceptance specs now** in the issue's `acceptance/` folder (`<root>/issues/<id>/acceptance/`, `./zn find <id>`), as real spec files with the cases that pin the behavior. Require only through aliases, and see the zz-test skill for where these live.
  - They fail, because the code doesn't exist yet. Main stays green because the gate doesn't run them.
  - This is what makes the checks unfakeable and sequestered.
  - They never change the real repository: every command that changes anything runs in a fixture under `.cache/<unique name>` with its own repository, checked before each write, committing as `<name>@example.invalid` (zz-test skill, "Specs never touch the real repository"). Before the guards exist on your branch, or while prototyping them, run them only in a clone under `$TMPDIR`.
- **Verify the wiring**: `./zn check <id>` runs and fails *for the right reasons*: assertion failures or missing modules, not bash errors.
- **Mutation check** (fills the Rules and mutants `checked` column): when you prototype the change in a scratch worktree, apply each row's mutant to the prototype and run the row's spec case, which must fail on an **assertion**, not a syntax or require error. Mark the row `run` and record the outcome in Unknowns & experiments. A row you didn't run (no prototype, or a mutant you couldn't apply) is `reasoned`: say why in Unknowns & experiments, and the reviewer then judges those rows by reading them.
- **Dry-run the promotion**: `./zn promote-check <id>`. The only acceptable failures before implementation are requires of modules the issue will create.

## 5. Adversarial design review (required)
1. **Lessons pass**, before the first round: run `./zn lessons --when design --full`, ask each lesson's `check` of the draft, fix what it finds, and name the lessons that changed the design in the issue's Unknowns & experiments. Then mark the items `design: reviewed` once the author considers them complete. Use `tracker` frontmatter edits.
2. Start a **clean** reviewer, with none of your context: a fresh subagent, given the `zz-review` skill (design mode), the issue's path, and read access to the repo. It writes `design-review-NNN.md` in the issue's folder. A dispatched reviewer writes `review.md` in its state folder instead, and the dispatcher places it there. Run the reviewer on the **review model of the CLI** (the user's rule): Opus through `claude` or `agent`, any grok model at `xhigh` through `grok`, whatever model the author runs on: `./zn dispatch zz-review <id> --mode design` starts it on the CLI and model `.models.toml` names for `zz-review` and records its spend row itself (a headless run always uses it); in an interactive Claude Code session you may instead start a fresh subagent with `model: "opus"`, and don't substitute another model, such as Fable or Sonnet. As soon as a subagent reviewer returns, whatever its verdict (an approving final round costs a run too), `./zn spend <id> --phase design-review --time <reviewer minutes> --tokens <reviewer tokens> --note design-review-NNN` (from the reviewer's usage report).
3. Answer every finding. Before editing, run the **consequence step** on your own fix: what new rules, state, edge cases or user decisions does it bring? Add their Rules and mutants rows and spec cases in the same change, and put any decisions to the user now, all at once.
   - Fix it in the documents, specs or `check.sh`.
   - Or rebut it in `design-refute-NNN.md` (`- F2: refuted: <evidence>` or `- F2: fixed: <what>; consequences: <handled how, or none>`). Once the round is answered, `./zn spend <id> --phase design-review --time <your answering minutes> --note design-refute-NNN`.
   - **Never answer a finding by cutting scope.** If the only fix you see removes, defers or shrinks an outcome the Problem asks for, ask the user before you answer it (under the dispatcher: write the question to `$ZN_DISPATCH_DIR/questions.md` and stop), and write their answer into the Problem as a `Scope decision` line (**Scope is what was captured**, above). Without that line, the answer is a redesign that keeps the outcome.
   - **Harvest the round** as you answer it: add one entry per finding of `design-review-NNN.md` to `harvest.md` in the issue's folder, naming a new lesson, a new source for an existing one (prefer this), or `one-off: <reason>` (format: zz-rules skill, Items). A finding that repeats a lesson the pass should have caught sharpens that lesson's `check`. Then run `./zn lessons --check`, and rerun `./zn promote-check <id>` after the round's spec edits (the test runner does not type-check). The next round's reviewer judges the new lessons; the lessons and the ledger ride in the prep commit.
4. **Rounds: up to 5 rounds, prefer 3.** One rule decides, from the round's `design-review-NNN.md` severities and the diff of your answers:
   - After round 1 or 2, run another round with a new clean reviewer if any high finding was fixed or refuted (a new reviewer rules on a refutation), or answering the round was more than minor (defined below).
   - After round 3 or 4, run the next round only if that round was **major**: it had a **high** finding, or answering it was more than minor.
   - Minor means the answers changed only wording, labels, comments or single assertions, and added no rule, interface, state, spec case, Rules and mutants row or public API change.
   - A re-prep after the user resets an item's scope restarts the count: its first new round is round 1, whatever its file number, and the issue's Unknowns & experiments says which file it starts at.
   - The **final round** is the round after which this rule runs no further round: any round 1 to 4 where it says stop, or round 5, which is always final. A final round holds a high only in round 5, and such a round goes to the user, whatever you answered to it.
5. **Confirm the harvest**: first harvest anything `./zn lessons --uncovered <id>` still lists (rounds written before lessons existed, or a round that slipped), as step 3 says. Then `./zn lessons --uncovered <id>` and `./zn lessons --check` must both pass. Then **check the scope**: compare the issue's document with `./zn capture <id>` (**Scope is what was captured**, above). Its title, Problem and Solution ideas may only have gained detail and decision lines, and every captured outcome has a Design and an acceptance criterion. Anything else goes to the user before `design: ready`.
   When the final round has `Verdict: approve`, or it has no high finding and every finding in it is answered `fixed` or `refuted`, set `design: ready` (a final round with a high, which only round 5 can be, or with an unanswered finding goes to the user instead) on the issue, **then run `./zn status <id> prepared`** (carried: it edits the local document, and refuses unless the issue is `design: ready` and `preparing` on `origin/main`), and only then make the prep commit (`status` needs an origin: with `PICKMAN_PUBLISH=0` or no origin, edit the `status:` line by hand to `prepared-<three words>` instead). Without it the issue keeps its `preparing` stamp and z-raft can't group it. Leave `raft:` empty: z-raft writes it.

## 6. Commit and hand off
- **Commit** the prepared issue, its acceptance specs and architecture changes in the prep worktree as one commit, `tracker: prep c0010 <title>`, then follow Landing a change (zz-rules skill): push, PR, merge, pull the main checkout, remove the worktree. Right after the prep PR is opened, before it merges (so before any raft holding it can be readied), `./zn spend <id> --phase prep --time <your prep minutes, the design-review answering time excluded: that is in the design-review rows>` (once: it counts the prep branch's lines). An issue readied first can no longer take it, and `spend` says so.
  - Ask the user before merging prep they didn't request. Under the dispatcher, don't ask and don't merge: once the PR is open and your spend is recorded, end the step; the dispatcher passes the gate (the user started it).
- **Report**:
  - the issue, its `size:` and whether it is `solo`;
  - the key design decisions;
  - experiment results;
  - review rounds, and what changed because of them;
  - anything left for Observed.
- **Next step**: `/z-raft` (it groups prepared issues), then `/z-ready <R-id>`.

## Headless (under `./zn dispatch`)
When `ZN_DISPATCH=1` is set you run headless and unattended, with the agent's own GitHub credential, and nobody answers a question. Never decide what you would ask the user (a scope change, a final review round that goes to the user, a missing credential): write the questions to `$ZN_DISPATCH_DIR/questions.md`, one `## Q<n>` heading per question with the options and what each costs, and stop. The dispatcher stops the chain there until the user answers and runs `./zn dispatch retry <id>`. `./zn land`, `status`, `spend` and every other `./zn` command that publishes tracker state are allowed: the dispatcher pushes that tracker state to `main` for you. Never `git push` to `main` and never merge a pull request: the dispatcher merges at its gates, your credential can't, and `z-nile/bin/git` and `gh` refuse. Record your spend as this skill says, but without `--tokens` for your own session: the dispatcher records the session's tokens and model. Start every review with `./zn dispatch zz-review <id> --mode <design|raft|code|stream>` (zz-rules skill, Dispatch), and give that one command a two-hour timeout (in Claude Code, the Bash tool's `timeout` of 7200000 ms): a review takes minutes, and the dispatcher keeps it alive by its heartbeat.

## Lessons
Before you start, read this skill's lessons: `./zn lessons --skill z-design --full`. Each is a mistake made before, with the question that catches it.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
