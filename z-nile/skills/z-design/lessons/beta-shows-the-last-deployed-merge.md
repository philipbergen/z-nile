---
title: Beta shows the last ready pull request's merge with main, not main
when: design
tags: [deploy, publish, beta, observed]
check: When the design changes what Beta publishes (a place, a start place, a build), does it say what Beta shows between the raft's pull request leaving draft and its merge, and after the merge while a run started before it is still queued or running? Are the Observed steps placed after a deploy whose merge commit is shown to hold the change (its checkout line's commit and `git show <m>:<file>`), rather than after a log line that does not name the build?
---
The Beta deploy runs for every ready pull request and publishes `refs/pull/<n>/merge`: the pull request merged with `main` as it stood at that pull request's event, not `main` and not the branch's head. So a change to what Beta publishes appears when its own pull request leaves draft, and disappears again whenever another ready pull request deploys before the merge. After the merge, only the runs whose event comes after it carry the change: the `beta-deploy` group runs one deploy at a time and cancels none, so a run queued or still running at the merge publishes its own older merge after it, and the next deploy corrects that.

**Why:** f0209's prep (2026-11-15): making the portal the start place looked like a merge-time switch, but the deploy log of #514 (`git checkout --progress --force refs/remotes/pull/514/merge`, "HEAD is now at be045c7 Merge 2b9a55c4… into af2c07eb…") showed Beta flips between the portal and the lobby while f0209's pull request is ready and others deploy. A rollback, likewise, goes live from its own ready pull request before it merges. f0209 design review 001 F1: the design first said "from the merge on, every deploy publishes the portal", missing the queued run, and its Observed precondition trusted the success line `published the Portal place (<id>)`, which names the place and never its build, so it is met with the lobby out too.

**How to apply:** read a recent deploy run's checkout step (`gh run view <id> --log`) rather than assuming. State the window in the design, both before the merge and for runs queued at it (and put an accepted flip to the user as a Guess). Write Observed steps that start from the most recent completed deploy run: its merge commit `<m>` from the checkout line "HEAD is now at <m> Merge … into …", and `git show <m>:<the manifest>` holding the change. A log line proves only what it names; if the build itself must be logged, that is a change to the deploy and its pinned output, an issue of its own.
