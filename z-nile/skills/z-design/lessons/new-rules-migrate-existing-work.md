---
title: A new rule says how existing work gets through it
when: design
tags: [process, migration, rollout]
check: When this adds a rule, a check or a new data structure, which existing items (prepared, active, mid-prep, done) or stored data fail it on the day it lands, what does the design say they do, and, for a one-time migration, which writers (older builds, old servers, a rollback) still produce the old shape after it ran, and does the new structure pick their data up? When old and new builds share a store at the same time, does the new one write the old shape, so each reads the other's writes? Stored data includes configuration: can a configured producer (a role's fallback or effort in `.models.toml`) still make what the rule refuses? And does a rule about what a change touched hold for a change that only deletes, and was the list of existing work made by a search the design names, so it can be rerun? Was the list of existing work searched in raft documents (a Theme's quoted user decisions) and reviews as well as issue documents, and re-derived on today's origin/main just before the review? When the rule is a whole-file pin (a digest) of files later items will edit, did the search read every in-flight item's documents and experiments patches for those paths (a branch diff cannot see an edit still planned in a document), and does each such item get the exact constraints (re-cut on the real patch, name the pin on its Overrides, the digest rule) with the sending recorded?
---
A new requirement is written for the work that comes after it, but it is checked against everything already in flight. Prepared rafts, active ones and preps open on a branch were made under the old rules and fail the new check the moment it lands, unless the design gives them a path (a migration, a harvest-at-confirm, an exemption, or an order).

**Why:** R0040 design review 5 (F1): the new "confirm the harvest" step would have blocked the three rafts already prepared, whose design reviews had no `harvest.md`. The Risks section said nothing would fail until a later gate. The user chose to have each old raft's executor harvest its own rounds at the confirm step.

c0120 design review 005 F6: when c0120's redesign moved z-nile's home from the root to `z-nile/`, c0115's prep (approved against the first revision) still ran its `check.sh` from the root. A change to a decision other preps were designed against is a new rule for them: name each one and its path (here: re-prepped before c0120 is readied, and a Phase 1 check that every unfinished `check.sh` resolves from its home).

**How to apply:** list the items on `main` and on open branches that the new rule applies to, run the new check against them in prep, and write their path into the design. Where the path is a cost or an ordering, put it to the user.

R0044 design review 1 (F1): the new all-time list of runs was seeded once from the per-player bests, when no list existed. Beta publishes the last ready PR and leaves running servers alone, so builds without the list kept writing per-player bests after the seed, and those runs never reached the list. The fix merged the per-player bests on every write. A one-time migration is only safe when nothing keeps writing the old shape after it.

A rewrite rule written from the cases a sample showed misses the forms the sample didn't: c0115's rule 3 matched only `s=../.claude/skills`, and c0040's `R="$(git … --show-toplevel)/.claude/skills"` stayed broken while the exact check was green (design review 010 F2). Pair the rules with an independent scan that fails on any old form left, and run the before-and-after comparison over every file that names the old thing, not only the ones the rules edited.

c0118 design review 006 F2: c0116 replaced the rafting flow (z-raft plans by `size:` and takes only `prepared` issues), and c0118, prepared under the old flow, was rebased onto it with no `size:` and status `new`. A dependency that replaces the flow is a new rule for every item prepared before it: at the rebase, give the item the new flow's frontmatter and write which command takes it next and whether that command accepts it as it stands.

**Note (c0261 design review 010 F4, F5):** a change of the ledger's format (#294: measured cost, typed minutes now 0, tokens no longer passed) moves every writer and reader of it: the dispatched raft review lost its tokens and the by-model table summed a dead column. Ask: for each place that writes or sums a cost, does it still get a real value after the upstream change?

c0302 design review 001 F2: a design that adds a rule about how fixtures are set up searches the sequestered acceptance specs of unfinished items for the old shape too, not only the promoted specs: c0282's prepared `lifecycle.spec` had the exact defect, and its promotion would have turned the new scan red. Ask: does the search for the old shape cover `*/.tracker/**/acceptance/` outside `done/`, and is each hit run against the new rule?

**Note (c0306's prep, 2026-11-14, design review 001 F6):** `[roles.raft]` runs at effort `high`, so its grok fallback would write a raft review that c0306's rule refuses. The dispatcher would spend a whole review run on a result refused by construction. The user ruled that a review step skips such a try.

**Note** (c0282 re-prep 2026-11-15): c0302's rule that a clone fixture names its branch `main` scans only `z-nile/tests`, so a prepared issue's sequestered spec breaks it only when a raft promotes it (c0282's `lifecycle.spec`, found at R0099's prototype gate). A new rule over specs also scans the open `acceptance/` folders, or names the prepared issues it leaves to fix.

c0286 design review 001 F1: the migration's list of families the user tied came from issue documents only, searched on the prep's base. The newest decision, "rejoin this raft", was quoted only in R0093's Theme, and two landings that morning had moved the members the list described. Search the raft documents too, and redo the search on today's origin/main just before the review.

**Note (c0292 design review 001 F1):** the sweep found the three open prep branches whose folders fail the full gate's format and lint, and the design said "their own merge gates will refuse them". They were dispatched preps, and the dispatcher's prep gate merges on CI green, which runs no gate, so two green, mergeable PRs (#397, #399) would have reached main. For each in-flight item the design says a gate will refuse, name the gate on that item's own merge path (a person's merge, the dispatcher's auto-merge) and check that it runs the failing check; where none does, capture the gap (c0359).

**Note (c0270 design review 001 F2):** a rule on what counts as "another prep" was never run over the 42 items `preparing` on `origin/main`; it counted their own prototype branches and worktrees and PRs that only mention the id. The revision ran it on every one (its E8) and recorded what each resume finds.

**Note (c0301 design review 001 F1, F4):** a rule about what a layer changed is checked against every kind of layer, one that only deletes included: an Overrides chore that removes a promoted spec leaves the ticket no line to cite at the top commit, so the first design refused a stack that lands today. And the existing-work list missed a second active raft with the same rows; name the search that made the list (here, `trace.md` at every layer tip and every active raft on `origin/main`) so the executor reruns it.

**Also:** f0201 design review 001 F3: the arcade's PaidPlay read f0145's `continues` but wrote `revives`, so an old f0145 Pickman server (which outlives a publish) would read none of the arcade's credits and its next write would drop them. When two builds share a store, the new one writes the old shape exactly, and a case pins the stored keys.

**Also:** c0288 design review 001 F6: the Non-goals named the search but listed only part of what it found, leaving out two `proofs/` files. Quote the search's whole result, then say which hits are out of scope and why.

**Note (c0251's prep, 2026-11-15):** fixture configuration counts as existing data. `roleFor("zz-review", "stream")` now resolves to a new `stream-review` role, and `.models.toml` defaults nothing. So every fixture `.models.toml` that runs a stream review fails: five `c0117/dispatch-cli` cases and c0306's `dispatch-review` spec. List the fixtures that run a mode whose role changes, as Overrides.
