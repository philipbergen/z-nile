---
title: Run each sequestered spec against a prototype
when: design
tags: [specs, prototype, acceptance]
check: Has every sequestered case whose module or command already exists been run against a scratch prototype, passing for the intended implementation and failing for its listed mutant, with the result recorded? And has `promote-check` type-checked the specs against a prototype that exports the design's types, rather than against a module that does not exist yet And is the prototype's base still `origin/main` for every file the specs load (the Touched modules and anything a spec reads), with the specs, mutants and gate re-run after any change there, checked as the last step before every approval request, a redesign that reuses a kept `experiments/prototype.patch` included? And has the local full gate on the machine that merges run them on the prototype? And does every later step that says that gate passes match the result that run recorded? And is the prototype committed in the issue folder as `experiments/prototype.patch`, so a prep paused or resumed later can rebase and rerun it? And is no case left unrun because its fixture is slow or awkward to build (a real-git case, a case that changes `HOME`), with every case that was not run named to the human before the approval request?
---
Reading a spec does not show whether a correct implementation can pass it. A sequestered case that contradicts a promoted spec, the publish rules or a command's refusal stops the executor, who may not edit it. Each such case is cheap to run on a scratch patch in prep.

**Why:** R0042 design reviews 002 F9, 003 F9, 004 F2 and 005 F3 each found a sequestered case that no correct implementation could pass: spend on an active item, which the publisher refuses, and an `appendOnly` expectation a promoted c0084 spec forbids. Every Rules and mutants row was `reasoned`, and reading missed the defect four rounds running.

R0012 execution, Phase 3: three strict sequestered specs passed at runtime but failed `promote-check`'s type check against the design's exported types. One declared `phase: string` for the `Phase` union, two read `.intent` and `.dx` off the `Effect` union without narrowing, and one reused `_` across types. Prep's dry run saw only the missing `@logic/Touch` require, which the skill allows, and with the module missing every value was `any`. The user authorized a type-only amendment.

**How to apply:** in a scratch worktree, apply the smallest patch that implements each rule, then run the case, which must pass, and the row's mutant, which must fail on an assertion. Mark the row `run` and record both outcomes in Unknowns & experiments. Keep `reasoned` only for a module that cannot exist yet, and say so. With the prototype's modules in place under `src/` of the scratch worktree, run `promote-check` there too, so strict specs are type-checked against the design's real types.

**Dry-run the promotion where `done` puts the specs.** c0120 (found by c0115's rebase, which simulated c0120 done, 2026-10-21): the gate's type stage ignores `.tracker/`, so six type errors in c0120's acceptance specs (multi-returns inside `t.expect`, an untyped pair) and a stale repo-fence key surfaced only once the specs sat in `z-nile/tests/acceptance/c0120`. Copy the specs to their promoted folder in the prototype, type-check and lint them there, and run the fence allow-list scan (repo-fence) before the prep is ready.
R0044 design review 1 (F3): the prep's mutation check ran 41 mutants and all died, but the reviewer found two more stated rules (a negative score refused, an invalid run table refused) with no mutant, and both survived. List one mutant per Design sentence that states a refusal or a bound, not only per rule you wrote a case for.

R0044 design review 5 (F1): R0034 landed during the prep and changed FlowView and `Flow.Overlay`, two Touched modules. The prototype, specs and mutants had all been proven on the older base, and one sequestered case failed for every correct implementation on the new `main`. Before each review round and before the prep commit, run `git diff <prototype base> origin/main -- <Touched modules and files the specs load>`; if it is not empty, merge, rebase the prototype and re-run everything.

Prove it after the item's own `done` too: simulate the move to `done/` and the promotion, then run the promoted rules that judge finished files. c0115's `check.sh` named `./zn`, `.claude/skills` and `z-nile/check.sh` on lines that ran after `cd "$copy"` or `cd "$ZN_ROOT"`, which c0120's check-paths (a static reader) can't follow, and c0113's AC2 named the deleted `.claude/README.md` literally: both turned c0120's promoted `finished.spec` red only once they were finished (found by c0116's rebase). Anchor such paths at a variable, or use a literal `cd <dir>` the rule reads.

Run the whole item on every experimental patch, not only the spec it was written for. c0115's G14 freeze change was kept as a patch and tried against the two freeze specs; applied at the rebase, its literal mark (an old skill path) turned the item's own absence scan (AC4) red. A patch held for later is proven with `./zn check <id>` on the tree it will join.

Run the `done` command itself too, not only a hand-made move: it leaves its moves and promotions uncommitted while the gate runs, so a spec that clones HEAD and overlays the working tree sees a moved item twice. c0116's retired.spec did, and only a simulated `done` of c0116 (a stub active raft in a scratch clone with no origin) found it.

**Note (c0121 design review 015 F1):** a rule that matches free text people write (PR titles, commit subjects, branch names) is run once against today's real corpus (`gh pr list` output here) before it is specified, and the false matches it finds go into the fixture. c0121's "a title that names the issue" put 4 wrong PRs on 13 real cards; "a title that starts with the issue's id" got all 9 open prep PRs right. Ask: what does this rule say about the last 200 real items, and which of them does it get wrong?

**Note (c0121 design review 016 F1):** the fixture for a rule over free text takes its shapes from the real corpus, not from the cases a review lists: classify the real items by the text around the matched token (a prep PR, a rafting PR naming its raft first, a closed PR, a capture naming several ids, a word that merely contains an id) and put one of each in the fixture, with a state that changes between builds (a worktree added later). Ask: does the fixture hold every shape the corpus has, including closed and raft-first titles?

**Also:** f0399 design review 001 F2 (2026-11-16): an experiment proves only the state it holds. E1 rebased a layer built on another raft with code files only and passed; with the raft's own tracker folders in the tree the design could not work (the layer read its raft as a backlog raft, and the restack would have left the issue in two states). When a design says an existing command "works unchanged" in a new situation, run that command there in a fixture or grep its preconditions; the writer of the sequestered spec found the same gap from the other side, by writing the case.

**Note** (R0129, f0399 executor, 2026-11-17): f0399's prep ran the pure specs on its prototype and left the two real-git specs (`land.spec`, `on.spec`) flagged as never run, with their rows `reasoned`. Five of their 23 cases could not pass for any implementation, and the executor stopped BLOCKED for a ruling on about ten lines. All five were fixture or comparison errors that one run shows:
- two cases expected `work next` to say `wait` from a fixture with a final review and no code review, which `work next` asks for first. A fixture that skips a step has to write that step's record.
- one case ran `./zn` with `HOME` set to a fixture folder, where the pinned `lune` shim cannot start. A fixture that changes `HOME` links `.rokit` into it.
- the same case compared a whole shared file before and after another session's call, though that call rightly adds its own line. Compare the line the rule is about.
- one case compared a trimmed text (read through `fixture.git`) with an untrimmed one. Read both sides through the same helper.
- one case landed a raft after `main` had moved without the `./zn restack` that `done` asks for. A fixture that drives a whole sequence runs every command the engine would ask for in it.
A row marked `reasoned` because the case is slow to set up is where the flaws were. The prototype already existed; running the two files on it took minutes.

**Note (d0415 design review 001 F6):** the prototype's proof is the item's own check and the promoted specs of the area it changes (the dispatcher's, the ready check's), run on the prototype and recorded before the review; an `Overrides: none` line is unproven without it.

**Note** (R0125, 2026-11-17, d0410): c0202's prototype ran every spec and the gates but never `./zn finish`, and finish could not finish a layer that deletes files (its watch capture wrote watch files for the deleted specs). The executor found it at finish, after the build.
