When this issue changes a number another prep quotes (a colour, a size), is it sent to that prep in the same round, the sending recorded, and the worktrees grepped for the old value? And has every in-flight prep's sequestered specs (each `.worktree/prep-*`'s `.tracker/issues/*/acceptance`) been searched for the API this issue changes or removes, since such a spec is an override the day it lands? Does an agreement with another prep's lead appear in that issue's committed documents or specs, with a `depends_on` that fixes the landing order, and for each order the two could land in, which sequestered or promoted specs turn red? And when the change adds a refusal to a command other items' fixtures drive, has the prep itself searched every sequestered spec outside `done/` and every prep worktree for them, rather than leaving the search to execution? And when two preps change the same file, was each landing order merged three-way on a scratch tree, with both issues' acceptance specs run on the result, a behavioural case observing the value the two share (a clean `git apply -3` proves nothing), and the wrong resolution shown to go red? And the other direction: for each prepared or in-flight item whose Touched modules overlap this one's (grep every open item's `### Touched modules` on origin/main, not only the worktrees), have this issue's own sequestered specs been run on that item's prototype merged with this one's, since a type literal, a refusal's words or a command's prompts it changes can turn this issue's specs red, and have that item's specs been run there for the words this issue rewords? And when this design needs to land before another item (it changes code that item deletes or moves), is that order a `depends_on` on the item that must wait, landed where `ready` reads it, and does any prepared design (a parenthesis included) state the opposite order? And when the design builds on approved but unbuilt designs, has every write, state and frontmatter key it adds been walked through each gate, writer and refusal those designs add (a claim's precondition, a land rule's allowed keys, a layer's completion rule, a view's identity), not only the names they export?
