# Make an issue

**Confirm intent first.** When the ticket carries words of the user's (a request, a correction, a problem they point out), restate it before anything is created (no worktree, no `./zn new`): the title, the outcome, who is affected, the non-goals, the Solution ideas, the type (feature, defect or chore) and the project, as you would write them into the Problem, with any overlap `./zn list backlog` shows. The user approves or corrects it, and the stub is made from the approved version. A correction means you restate again. Under `./zn dispatch` (`ZN_DISPATCH=1`), on any CLI, never use plan mode and never only print: ask it the way the dispatcher's prompt tells you to ask the user a question, and stop. Otherwise, in Claude Code, when `EnterPlanMode` is offered (or listed as a deferred tool: load it with ToolSearch) and you are not already in plan mode, call it, write the restatement to the plan file, ending with the line `Next: capture with the z-ticket skill, steps 0 to 6; build nothing.`, and call `ExitPlanMode`: the user's approval is the go-ahead, and a rejection means you ask what to change and restate. Without it, or if the user declines plan mode, or if you are already in plan mode (leave its plan alone), print the restatement and stop until the user answers; a subagent returns the restatement to its lead, which confirms it with the user. A message with several tickets gets one restatement covering all of them, one block per ticket. The restatement adds no design and no scope: it is the user's words, sharpened. A restatement the user has already approved counts, whether they gave it in this conversation or it comes in your brief or in the reply `./zn dispatch retry` hands over. A ticket made only from your own finding (a review finding, a failed step, a graph miss you found) has no words of the user's to check and is filed at once.

0. **Open a capture worktree first**, after the confirmation above and before anything is created: `cd "$(./zn worktree capture-<slug>)"` (zz-rules skill, Worktrees). Everything below runs there, never in the main checkout. Then run `./zn sync`, so you see every item other terminals have created.
0a. **Keep the ask verbatim.** In plan mode the plan file the paragraph above has you write is where the user's words survive the approval that clears the context, so read this step before you call `EnterPlanMode` and write the plan file this way from the start: the user's messages of this request first, verbatim and each dated, under the heading `Ask (verbatim)`, then every restatement you have shown and each reply of the user to it, in order and dated, under the heading `Restatements`, then the current restatement, which still ends with the paragraph's `Next:` line. Copy every message of the user's request exactly as they wrote it (the messages of the request, and any correction they made to the restatement above, each dated; in plan mode take them from the plan file's `Ask (verbatim)` heading, and each restatement with the user's reply from its `Restatements` heading), typos and all, into a record file (**The capture record**, below), one `### Message YYYY-MM-DD` block per message, each inside a fenced block (the fence one backtick longer than the longest run of backticks in the text, at least three), so headings and code in a pasted plan stay as written. Step 2a puts it on the issue as `## Ask (verbatim)`. It is never edited, shortened or "fixed", and `./zn land` refuses a later change that is not an appended message.
0b. **Interview the user.** Every restatement shown above and the user's approval or correction of it is the next `### Qn`, in order (Q1 the first; Question: the restatement as shown; Options: approve | correct; Answer: the user's words, or the reply `./zn dispatch retry` handed over; a correction makes a second restatement and so a Q2; in plan mode they come from the plan file's `Restatements` heading). Then challenge the idea: ask the questions that expose gaps, conflicts, edge cases and unstated assumptions, until you can write each outcome of the Problem without guessing. Ask only what the repository cannot answer (read the tracker, `game-design.md` and the code first), in rounds of at most four questions (Claude Code: AskUserQuestion; another CLI: plain numbered questions), each with the options you propose and what each costs. Cover the classification (step 1), who is affected, what should happen, how "done" is judged, what is out of scope, and any overlap with a backlog issue (`./zn list backlog`: say so and ask whether to merge). Record **every** question, in order, exactly as asked, with the options offered and the user's answer in their own words (an answer of several lines goes in a fenced block after `Answer:`): none is dropped, even one the user waved away. The interview ends when the user says so or you have no open question; Q1 alone is a complete interview.
1. **Classify the work**:
   - **feature** (`f`): new player-facing or developer-facing capability.
   - **defect** (`d`): **product** behavior that's wrong compared with an issue that's already done or with an obvious expectation: a game's, the portal's, the arcade library's, or z-nile's own (its commands, the gate, the guards, the runner, the selector's code; a hole in the watch map is a chore). This is rework, and it's counted against the 20% target, so classify honestly.
   - **chore** (`c`): refactors, infrastructure or upkeep, with no change in behavior. **A spec that is wrong while the code is right is always a chore, even when it's a bug**, for example:
     - a flaky or wrong spec, including a promoted acceptance spec;
     - a test-selector graph miss (a hole in the watch map);
     - a game's own spec or test helper that is broken.
     These never count as rework.
   - **Every root holds all three types** (c0266): z-nile's root (`z-nile/.tracker`) holds its chores, features and defects as a game's root holds the game's. A z-nile command, gate script, guard, hook or workflow that does the wrong thing is a z-nile defect (`--project z-nile`).
2. **Create the shell**: `./zn new issue <f|d|c> <kebab-slug> --project <name> --desc "<one line>"`. The project is `--project`'s when given, else the one whose folder you run `./zn` in (`z-nile/` and below is z-nile's, `pickman/` and below pickman's, c0120); at the checkout's root, or in a folder no project holds, `./zn` refuses and asks for `--project`. Tooling work (the tracker, the gate, the guards, the skills, CI) is `--project z-nile`; the work of a game, the portal or the arcade library is its project's (`--project pickman`, `--project snake`, `--project portal`, `--project arcade`, …: a name in `z-nile/projects.toml`), or a capture run in that project's folder (`pickman/`, `snake/`, …) (zz-rules skill, Projects). This only allocates the id and the stub (`idea: unchallenged`). It does not write the Problem or the Solution. The stub is pushed to `origin/main` at once, so other terminals see the id. The slug is 2–5 words describing the outcome. Under `./zn dispatch`, ask every question before this step: once the stub is on `main` the capture can no longer ask through `questions.md` (the dispatcher fails a z-ticket that made an issue and then asked, and sets the question aside). What you would ask after it (an overlap step 5 finds, a point the idea stage leaves open) goes under `## Open to the human` in the issue, which you land, and you stop: the dispatcher stops the chain on that unruled list, and the user rules in the document and runs `./zn dispatch retry <id>`.
2a. **Keep the record.** Put the record file's blocks on the issue: `./zn idea <id> --record <file>`. It appends the messages to `## Ask (verbatim)` and the questions to `## Interview` (the questions number on from the ones the issue holds), creating the sections before the Design, and changes nothing else. Run it again for every message or question that comes later. `./zn idea` is the only writer of these sections too, and it refuses a Q that skips a number. Step 4 refuses an issue made after the record landed (`capture: required` in its frontmatter) until this is done.
3. **Fill in the frontmatter**: `title`, and `depends_on` (IDs) if you already know them.
4. **Write the idea**: `./zn idea <id> --text "<the rough idea>"`. That command is the only writer of Problem, Solution, Non-goals, `idea-review-001.md` and `idea-refute-001.md`. The `idea` role drafts the outcomes (each bullet one sentence a later claim can find true or false). The `idea-challenge` role challenges once, and the review file is that challenge. An approval with no findings stops there. Otherwise the author answers each finding in the refute (`revised`, or `disputed: <reason>`), and a finding disputed or not answered is left under `## Open to the human`. Do not type those sections yourself. `./zn capture <id>` stays the read-only view of the captured document. Every outcome the idea names is the issue's scope: once it lands, prep may add detail but never narrows, defers or drops an outcome without the user (z-design, **Scope is what was captured**). Everything else is left for `z-design`. Keep `design: draft`. The human rules what is open, then commits the review, the refute and the document and pushes them before design starts.
4a. **Show the idea and its challenge.** Where step 4 says the command challenges once and names `-001`, it now loops: the challenger reviews, the author revises and answers, and the challenger reviews the revised idea again, until it approves or has challenged 5 times (`idea.MAX_ROUNDS`); the last challenge is never followed by a revision, so everything it found, and every question it raised for the user (`- F2: ask: …`), is left under `## Open to the human`. Every pass is its own `idea-review-NNN.md` (and, with findings the author answered, `idea-refute-NNN.md`), numbered on from the last and written when the pass completes. Run `./zn idea` with a Bash timeout of two hours (7200000 ms) in Claude Code: it makes up to ten model calls (a draft, 5 challenges and the 4 revisions between them), each of them up to four tries; under `./zn dispatch` it beats into the step's folder, so the dispatched step is not stalled while a model works. If it stops partway, the passes already written stay and a rerun numbers on. Ask the user each `ask:` question (AskUserQuestion) and record the answer as the next `### Qn` before the next run. Show the user the Problem, Solution and Non-goals that step 4 wrote, the challenger's findings (`idea-review-NNN.md`, which now checks the idea against the Ask and the Interview: nothing dropped, added or bent) with the author's answers (`idea-refute-NNN.md`), and what is left under `## Open to the human`. A change the user asks for is a new message of the Ask (and a question and answer of the Interview when you ask one): record it with step 2a, then run `./zn idea <id>` again, which numbers on (after a first loop of two passes, `idea-review-003.md`) and drops a `Confirmed` line, because the idea changed. The user's ruling on each open point is written under `## Open to the human` as `Ruled (user, YYYY-MM-DD):`, and that line alone lets step 4b confirm: no round follows it. When the user changes or adds to the idea (a new message, an answer that adds an outcome), first record the rulings so far as the next `### Qn` of the Interview (Question: the finding as shown; Answer: their words) with step 2a, because every round rewrites the Problem, Solution, Non-goals and `## Open to the human` whole, and only the Ask and the Interview are kept; then record the change and run `./zn idea <id>` again (a new loop, shown them) before step 4b: `--confirm` binds to the record and the idea the last round judged, and refuses a record that grew since. Step 4 is round 1 (`idea-review-001.md`); a change is the next pass and on, with a loop of its own.
4b. **Have the user confirm it.** Ask the user to confirm the idea as it now stands (Claude Code: AskUserQuestion or plan mode), then run `./zn idea <id> --confirm "<their words>"`. It writes `Confirmed (<who>, YYYY-MM-DD) after round N: "<their words>"` under `## Confirmation`, naming the last round, and refuses while a point is unruled or the record is incomplete. Only the user confirms. Under `./zn dispatch` (`ZN_DISPATCH=1`) nobody answers: do not stop, run `./zn idea <id> --unattended` instead, which writes `Unconfirmed (unattended, YYYY-MM-DD) after round N: …`; `--confirm` is refused there (z-design gets the user to run it in a terminal), a finding the dispatched challenge leaves open does not stop `--unattended` (the user rules it at z-design), and `./zn land` refuses a `Confirmed` line from a dispatched run. z-design asks the user before it designs such a ticket (z-design, Claim the issue).
5. **Duplicates**: look for overlaps with `./zn list backlog`. If there's an overlap, say so and ask whether to merge.
6. **Land it.** Commit in the capture worktree (`git add -A && git commit -m "tracker: new <id> <title>"`), run `./zn land`, and before the worktree is removed record `./zn spend <id> --phase capture` (the tool measures it; do not pass `--time` or `--tokens`), then remove the worktree with the command it prints. No PR: land runs the gate locally and pushes to `main`. Under the dispatcher, land without asking (the user started it); the dispatcher pushes the capture for you. Report the ID and path.

## The capture record
The record is sections of the issue document, after the Solution and before the Design, written only by `./zn idea` (`--record`, `--confirm`, `--unattended`): `## Ask (verbatim)`, `## Interview` and `## Confirmation`. The clean idea is the Problem, Solution and Non-goals step 4 writes, and its review is `idea-review-NNN.md` beside the document. The gate checks the record (`./zn audit`, and the claim for an issue marked `capture: required`, which `./zn new` writes once this record exists; an older issue is never judged). The file step 2a reads holds only the new blocks:

````markdown
## Ask (verbatim)
### Message YYYY-MM-DD
```
<the user's words, exactly>
```

## Interview
### Q1
Question: <exactly as asked>
Options: <the options offered, or "free text">
Answer: <the user's words>
### Q2
...
````

`Options:` may be left out. A ticket you file from your own finding (a lesson, a review finding, a failed step) has no words of the user's: file it with `./zn new issue … --project <name> --filed-by "<source>"` (`lesson:<skill>/<slug>`, `review:<id>/<review file> F<n>` or `agent:<id>/<slug>`), which writes `## Filed by (agent)` and carries no Ask, no Interview and no Confirmation (the user's ruling of 2026-11-13: it still runs step 4, so its outcomes are written and challenged like any ticket's, with no user words to compare against); a user's request is never filed this way. **A stub an agent made without `--filed-by`** cannot be exempted afterwards (only `./zn new issue … --project <name> --filed-by` writes the marker, and `./zn land` refuses any other change to it): recreate it with the flag or capture it as a user ticket. **A marked stub with no record yet** (the claim refuses it and says so) is continued on its id: run steps 0a to 4b against it.

## A capture under the dispatcher
`./zn dispatch new` runs these steps with nobody to answer. The restatement and the user's reply (Q1; c0256's hand-over) and the messages the dispatcher passes are recorded like any other. The rest of the interview is unattended: ask nothing, record `--unattended` at step 4b, land (step 6) and report that the idea is unconfirmed. The points the idea leaves under `## Open to the human` are the user's at z-design, not a stop of this capture: the dispatcher does not stop on the open list of an idea still `Unconfirmed`.

## Headless (under `./zn dispatch`)
When `ZN_DISPATCH=1` is set you run headless and unattended, with the agent's own GitHub credential, and nobody answers a question. Never decide what you would ask the user, and never guess a ruling. A scope change or a missing credential: write the questions to `$ZN_DISPATCH_DIR/questions.md`, one `## Q<n>` heading per question with the options and what each costs, and stop. The dispatcher stops the chain there until the user answers and runs `./zn dispatch retry <id>`. A refutation or an unclosed high is written under `## Open to the human` in the item's document and you stop without ruling on it: the dispatcher stops the chain on that unruled list until the user rules in the document and runs `./zn dispatch retry <id>`. `./zn land`, `status`, `spend` and every other `./zn` command that publishes tracker state are allowed: the dispatcher pushes that tracker state to `main` for you. Never `git push` to `main` and never merge a pull request: the dispatcher merges at its gates, your credential can't, and `z-nile/bin/git` and `gh` refuse. Record your spend as this skill says. Do not pass `--time` or `--tokens`: the dispatcher records the session's wall, CPU, tokens and model. Start every review with `./zn dispatch zz-review <id> --mode <design|raft|code|stream>` (zz-rules skill, Dispatch), and give that one command a two-hour timeout (in Claude Code, the Bash tool's `timeout` of 7200000 ms): a review takes minutes, and the dispatcher keeps it alive by its heartbeat.

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A lesson goes to the step that erred: the skill whose instructions the author was following when the mistake was made, or the skill of an earlier step that should have prevented or caught it (that skill is `<the skill the lesson improves>` below). The harvest line names that step as `(erred <skill>[, upstream <skill>])` before its colon (zz-rules skill, Items), and every kind of review and correction is harvested: a finding of a design, code, stream or focused review as an entry of the item's `harvest.md`, and a programme review, a correction by the user or a failed step as a `- note` entry.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened> (erred <skill>): <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --filed-by "<source>" --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). Pass `--filed-by "<source>"` (quoted: it holds a space for a review finding; `review:<item id>/<review file> F<n>`, `lesson:<skill>/<slug>` or `agent:<item id>/<slug>`) only for a lesson that comes from a finding of yours; one from the user's correction carries their words, so capture it with the z-ticket skill without the flag. The prep that takes the issue writes the file.
