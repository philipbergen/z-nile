# Work the queue

You are the worker. A person opened this session and ran z-work. Ask for one action, do that one thing, ask again. The ordering is `./zn work next`; this skill has none.

1. Run `./zn work next` when no raft was named, or `./zn work next <R>` when one was. A named raft is delivered, with the rafts it depends on: you keep asking until it has landed or only the person can move it, and you never stop at a line that you can act on. While you are carrying a raft, pass its id on every later call. `./zn work <R>` prints the graph of what it waits on, and `./zn work graph <R>` prints it again. A line that starts `For <R>:` is the next action of a raft it waits on, or of an issue it waits on: do it as any other. `./zn work next <R> --one` answers the raft's own next action alone. The line it prints is the one next action: a build, a review, a `draft` (design one issue), `rafting` (group prepared issues), a `ready <issue>` (an easy ticket in no raft takes the light path: `./zn ready <issue>` makes its single raft in one claim commit, no rafting pull request, no separate code review; its final review is its only review, so it reads the code too), a `fix` (repair a raft that needs it) or a `wait` (nothing is ready to take). A held raft or design may be resumed. An issue may be named: `./zn work next <issue-id>` takes that issue's next action. The folder `./zn` is run from chooses the project: from `pickman/` the next raft is a pickman raft, from `z-nile/` a z-nile raft, and the same for each other project. From the checkout root, or from a folder no project holds, it is any project. `./zn work queue` and `./zn work status` use that same folder. Naming a raft still takes that raft, whichever project it is in.
2. Say that line to the person before you do it, and why it is the next action.
3. Do that one action and nothing past it. An action that needs a model (a design, a review, a layer) runs on the one `./zn model <activity> --for <id>` prints: in Claude Code a subagent with its `subagent=` word and `effort=`; on a CLI with no subagents, this session, and only when that model is this session's own. When it exits 1, or the model is not yours, don't do it: print the "waiting for a worker with ..." line the command gave, stop, and tell the person that a worker whose CLI has that model must take it; on exit 2 stop and show the error (AGENTS.md, Subagents). A build follows `z-nile/skills/zz-execute/SKILL.md`. A review follows `z-nile/skills/zz-review/SKILL.md`. Tracker commands follow `z-nile/skills/zz-rules/SKILL.md`. Claiming is `z-nile/skills/z-ready/SKILL.md`. Giving the claim back is `z-nile/skills/z-stop/SKILL.md`. Read the skill the action names. A `restack` line that names conflicted files is yours to resolve (zz-execute, Phase 5 step 2): resolve, run the specs the files select, `./zn restack <R> --continue`; ask the person only when you cannot tell which side the owner wants.
4. At each layer boundary, one line: the ticket, whether its specs are green, and the next `./zn work next` line.
5. A human decision is answered with a recorded guess (Guess mode, below) and the work goes on. Blocked means only: the same check failed after a real second attempt, a missing credential, or a choice that would drop or shrink a captured outcome (only the user changes scope). Then write `questions.md` in the raft folder, one plain question per heading. `./zn commit` it on the layer. From the main checkout run `./zn stop <the raft the line names>` (a `For <R>:` line names a dependency raft). Tell the person, then run `./zn work next <R>` again. Never narrow scope to get green.
6. When a raft was named and the line says `wait` (or `end` for a raft that has not landed), read its text. If it starts `<R> is not landed yet:`, it is the Stops message: nothing can be worked now, and the lines under it are what the person owes, each alone on its own line, a command to paste or a file to answer, with a note after ` # `. Run `./zn guesses <raft>` for the raft each owed approval names, show the Stops message as your last message, and stop. Do not ask again with no raft and do not run `./zn approve` yourself. A `wait` whose text does not start that way is a gate, a review or a merge still running: it clears by itself, so ask again after it can have changed, at most once a minute. A unit given back twice in a row is also a stop: pass the unit you gave back last as `--gave <unit>` beside `--released`, and the message names it. When no raft was named and the line says `wait`, tell the person which issues wait and print `./zn guesses <R>`, then ask again with no raft. A `wait` is not a release: it adds nothing to the count you pass as `--released`. A `draft` you give back (`./zn status <id> new`) and a `fix` that changed nothing each add one to that count, so two in a row stop the session. When the line says end and a raft was named at the start, say so and stop: a landed raft needs no more than that line, and a raft that is not landed (a `questions.md` to answer) ends with the Stops message. When the line says end and no raft was named, this raft is finished: say one line (what landed or was released, and what you take next), then run `./zn work next` with no raft. A release adds one to the count you pass as `--released`. A landing sets that count back to 0. The command stops the session when the count says to; you do not know the number.
7. If the command you just ran fails for a reason that is not this raft (the main checkout is not clean, it cannot fast-forward, fetch failed, there is no origin), stop and tell the person. Do not take another raft.
8. Between rafts, nothing you learned in the last raft is an instruction for the next. Re-read the next raft's prompt and its tickets from git. None of these CLIs gives you a command that clears the session: Claude Code's `/clear` is typed by the person (the program tells the agent to ask them; `claude --help` has no clear command). Kimi's `/clear` and Grok's `/clear` (an alias of `/new`) are typed in the session; neither `kimi --help` nor `grok help` lists a command you can run. Cursor's `agent --help` lists no clear or compact, and this agent has no tool that clears it. Carry on, and re-read.
9. The worker registers itself in the live layer: the first `./zn work` or `./zn work next` of the session does it, and each `./zn work next` after it beats, claims the unit it names and gives it up at the next action, so `./zn work status` and the app show every worker, its CLI and account and what it holds. To tell accounts apart the owner may start each terminal with `ZN_ACCOUNT=<label>` (letters, digits, dot, dash or underscore, at most 32); nothing else is needed (the session's process is found by itself; `ZN_WORKER_PID=<pid>` is per terminal only, for when it cannot be, and never exported to several), and with the layer off the commands answer as they always did. `./zn work queue` prints one line per raft the next action will not take, the first reason only. `./zn work status` prints who holds which raft, which layer, and since when. `./zn finish` and `./zn done` read the session that is running the command and write that row. Claude Code counts each message id once, and only the file `CLAUDE_CODE_SESSION_ID` names in this checkout. Kimi counts a wire only when its `state.json` cwd is this checkout and the CLI named that session; a wire has no per-line time, so the whole file counts. If the session cannot be named, or Kimi's cwd cannot be told, that row says unmeasured. Grok is `~/.grok/sessions` and Cursor's agent is `~/.cursor/projects`; neither has a count on this row today. Do not type a number.
10. Left for later: rank is still c0249 (until then the next raft is the lowest id, and that key is `work.rankKey`), and a live session is told by the live layer (`./zn work status`), the carriers file where there is no layer, until c0265. A blocked status is c0250 (`questions.md` is the only block signal). Heartbeats and taking over a raft someone else holds are c0265. Several hosts are c0254 (the holder is the author of the ready commit). A supervisor that starts a fresh session per raft is a later ticket. The count of releases in a row is yours, because a release commit does not name the session.

## Guess mode
A **guess** is any choice the approved contract of an issue does not already make: an open question answered, a judgement call, a ruling you would otherwise ask for, a deviation while building. Guess mode is a session that takes its actions from `./zn work next` and is not under `./zn dispatch`.
- Record each guess with `./zn guess <issue-id> --step design|raft|build` at the moment you make the choice, not later. Mark it in the document where it decides something (z-design says how).
- Never guess under `./zn dispatch`: there nobody answers, and its Headless section stands.
- Two limits: never guess an idea's open line, and never guess a choice that would drop or shrink a captured outcome. Only the user changes scope.
- Nothing unapproved lands. The person reads `./zn guesses <R-id>` and runs `./zn approve`; `./zn done` checks the approval, so a raft with a member that is not approved ends at `wait`.

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A lesson goes to the step that erred: the skill whose instructions the author was following when the mistake was made, or the skill of an earlier step that should have prevented or caught it (that skill is `<the skill the lesson improves>` below). The harvest line names that step as `(erred <skill>[, upstream <skill>])` before its colon (zz-rules skill, Items), and every kind of review and correction is harvested: a finding of a design, code, stream or focused review as an entry of the item's `harvest.md`, and a programme review, a correction by the user or a failed step as a `- note` entry.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened> (erred <skill>): <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
