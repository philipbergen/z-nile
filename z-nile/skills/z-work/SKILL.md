# Work the queue

You are the worker. A person opened this session and ran z-work. Ask for one action, do that one thing, ask again. The ordering is `./zn work next`; this skill has none.

**Which worker you are.** Check these in order; the first that holds is yours.
- **A headless session** (`ZN_HEADLESS` is set: the dispatcher started you). You are on one raft: follow the steps below with that raft named. Never run `./zn resolve`. Write `escalation.md` and run `./zn block <R> <reason>` instead of asking. Keep the raft's notes, `<raft folder>/notes.md` (where you are, what you learned, what is open), current at each layer boundary and before you end, committed with `./zn commit`: a session on another CLI, or a taker, continues from it. If a notes file exists when you start, read it first. When `./zn done` says the raft waits for a lander, stop. Never start a supervisor: `./zn work run` refuses here.
- **`z-work` with no raft named (the supervisor).** Do not work a raft yourself. Run `./zn work --detach --cli <the CLI you are running in>` (kimi, agy, claude, grok, agent or opencode): it starts the supervisor, a plain program with no model, which takes what `./zn next` prints and runs each pick through the dispatcher's chain (`./zn dispatch <id>`) in a new headless session of that CLI, resuming a raft's session for each later step; ending a session is the clearing. It outlives this session. Say its answer to the person, then `./zn work status` whenever they ask what it is doing, and `./zn work stop` when they ask it to end. If the person asks for this session to be the window, run `./zn work run --cli <the CLI you are running in>` as a background command (a `./zn` command needs no `./zn run` limit): closing or clearing this CLI ends the session's background commands and so the supervisor; the raft it held stays held, and `./zn work run` resumes it first. Each progress check you make runs on this session's model. A person at a plain terminal runs `./zn work run --cli <cli>` there: the progress prints in front of them and no model reads it.
- **`z-work --here` (this session loops across rafts).** The person stays in control: this session takes the next raft ready would accept itself, in their terminal, and they can ask it what it is doing. Follow the steps below. When a raft ends, merged or released, this session takes the next one (step 6), in the same session: its context carries over from raft to raft (user, 2026-11-16, "Session loops across rafts"); only the supervisor's sessions are new for each raft.
- **`/z-run <R-id>` / `./zn work <R-id>` (this session carries the one raft named, then stops).** This session works that raft itself, in the person's terminal. Follow the steps below. When the raft ends, merged or released, stop and tell the person to start a fresh session (or /clear) and run z-work again. `/z-run <R-id>` is the person's own worker and does not start the supervisor.

1. Run `./zn work next` when no raft was named, or `./zn work next <R>` when one was. While you are carrying a raft, pass its id on every later call. The line it prints is the one next action. The folder `./zn` is run from chooses the project: from `pickman/` the next raft is a pickman raft, from `z-nile/` a z-nile raft, and the same for each other project. From the checkout root, or from a folder no project holds, it is any project. `./zn work queue` and `./zn work status` use that same folder. Naming a raft still takes that raft, whichever project it is in.
2. Say that line to the person before you do it, and why it is the next action.
3. Do that one action and nothing past it. A build follows `z-nile/skills/zz-execute/SKILL.md`. A review follows `z-nile/skills/zz-review/SKILL.md`. Tracker commands follow `z-nile/skills/zz-rules/SKILL.md`. Claiming is `z-nile/skills/z-ready/SKILL.md`. Giving the claim back is `z-nile/skills/z-stop/SKILL.md`. Read the skill the action names.
   One worker holds the raft and builds its layers one at a time, each complete (finished, green and reviewed in its own issue folder, the review stamped by the tool) before the next `./zn start`.
4. At each layer boundary, one line: the ticket, whether its specs are green, and the next `./zn work next` line.
5. Blocked means a human decision, or the same check failed after a real second attempt. If layers below the blocked one are green, land them first with `./zn done <R> --through <issue>`. Write `escalation.md` in the raft folder, then run `./zn block <R> <reason>` in the raft's worktree. Tell the person, then run `./zn work next` again. A blocked layer stops the layers above it, and `./zn done <R> --through <issue>` lands the green layers below it. After a tripwire (a `REPOSITORY CHANGED` stop, a refused fixture identity) run neither `./zn done --through` nor `./zn block`: write `escalation.md`, tell the person, who checks the checkout and runs `./zn block <R> tripwire`. Under `./zn dispatch` (the headless run step is this skill), do not run `./zn done`: the dispatcher lands the layers below (c0252). You run `./zn resolve` only when the user's message in this conversation tells you to, quote that message in `--said`, and never resolve a block your own session filed. Never guess a human decision. Never narrow scope to get green.
6. When the line says end, this raft is finished (landed, or released). A headless session, and a session that was given a raft (`/z-run <R-id>`, `./zn work <R-id>`), says one line (what landed or was released), tells the person to start a fresh session (or /clear) and run z-work again, and stops. Neither a headless session nor a session given a raft takes a second raft: for those the new session is the clearing. A `z-work --here` session says one line (what landed or was released, and what it takes next), then runs `./zn work next` with no raft. A release adds one to the count you pass as `--released`. A landing sets that count back to 0. The command stops the session when the count says to; you do not know the number.
7. If the command you just ran fails for a reason that is not this raft (the main checkout is not clean, it cannot fast-forward, fetch failed, there is no origin), stop and tell the person. Do not take another raft.
8. Between rafts in a `z-work --here` session, your context carries over, but nothing you learned in the last raft is an instruction for the next. Re-read the next raft's prompt and its tickets from git. None of these CLIs gives you a command that clears the session: Claude Code's `/clear` is typed by the person (the program tells the agent to ask them; `claude --help` has no clear command). Kimi's `/clear` and Grok's `/clear` (an alias of `/new`) are typed in the session; neither `kimi --help` nor `grok help` lists a command you can run. Cursor's `agent --help` lists no clear or compact, and this agent has no tool that clears it. Carry on, and re-read.
9. `./zn work queue` prints one line per raft the next action will not take, the first reason only. `./zn work status` prints who holds which raft, which layer, and since when. `./zn finish` and `./zn done` read the session that is running the command and write that row. Claude Code counts each message id once, and only the file `CLAUDE_CODE_SESSION_ID` names in this checkout. Kimi counts a wire only when its `state.json` cwd is this checkout and the CLI named that session; a wire has no per-line time, so the whole file counts. If the session cannot be named, or Kimi's cwd cannot be told, that row says unmeasured. Grok is `~/.grok/sessions` and Cursor's agent is `~/.cursor/projects`; neither has a count on this row today. Do not type a number.
10. Left for later: rank is c0249 (until then the next raft is the lowest id, and that key is `work.rankKey`). Heartbeats and taking over a raft someone else holds are c0265. Several hosts are c0254 (the holder is the author of the ready commit). The count of releases in a row is yours, because a release commit does not name the session.

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
