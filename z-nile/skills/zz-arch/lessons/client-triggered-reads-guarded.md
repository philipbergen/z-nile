---
title: A read a client can trigger is guarded in flight and after a leave
when: design
tags: [server, budgets, concurrency, remotes]
check: For each per-player read or cache a client request can start, what happens when the same client asks again, or leaves, while that read is yielding, how many store calls does one client cause in a minute of back-to-back requests (each sent when the last returns), what happens to requests right after a read that failed (is the failure held for a span, or does every request read again), and what does a call made after the player left do? Does a spec model a yielding store, and one that fires requests one after another? And for the writes and broadcasts a client can cause with no store read at all (a wait it joins and leaves, an invite it sends), is each bounded per player per minute, not per wait or per session, with a spec that runs the loop for a minute and counts them? And can a read that began before a write this server made (a grant, a refund) store the older record over the newer one when it returns, and does an action that follows such a write (a purchase's start) depend on a read that may be under way? And does a status read made only to tell the client (a read of the record after a write) come after the state changes that write leads to (a hold released, a decline applied, a screen opened), so an outage that slows the read never delays them?
---
A server read that a client remote can trigger spends a server-wide budget. If its cache entry is written only after the read returns, every request that arrives during the yield starts another read, so one client firing the remote can exhaust the budget for every player. A read that returns after the player left writes an entry that outlives them.

**Why:** R0044 design review 1 (F2): the lobby's "your best" read was cached per player for CACHE_TTL, but the entry was set after `GetAsync`, so five requests during one read made five reads; a read that finished after `PlayerRemoving` left a stale best that a quick rejoin was shown. Synchronous stubs showed neither.

**How to apply:** store an in-flight marker before the yield, skip the read while it is there, and store the result only if the marker is still that read's and the player is still present. Give the spec stub a store call that yields until released, and cover a burst during the read and a leave during the read, each with a mutant.

**An in-flight guard bounds concurrent requests, not repeated ones.** A client that sends its next request as soon as the last call returns costs one store call per round trip, for as long as it likes, and the server's budget is shared: once it runs out, other players' calls fail, and where a failed call is generous (a free game), the spammer hands it to them. f0145 design review 003 F1: twenty CONTINUE asks or START presses one after another made twenty writes or reads. Bound the calls over time as well: answer from what the server last read or wrote (no call when it already knows the answer), drop a request while its answer is pending (a screen open), and allow at most one call per player per few seconds; pin each with a case that sends the requests one after another, not all inside one call.

**Also:** f0201 design review 001 F8: only a successful read was cached, so while the store failed fast every request read again and one client kept the shared budget throttled; a failed read holds its answer for a retry span with no store call. F10: a call made after the player already left (a place that yields first) still spent their free start and made a slot nothing dropped; such calls answer without a store call or a slot, except a give-back owed to them.

**Also:** c0202 design review 001 F4: the library's `Wallet.read` stores what `GetAsync` returned when it returns, after a grant on the same server had already stored the newer record, so a read on joining that spans a purchase hides the play for the cache's 60 s, and the purchase's own START (which read again) was refused as "busy". c0202 starts a play granted on its server without a read; the library's read should not replace a newer record (a per-slot write counter checked before it stores). Spec stubs must return the value the store held when the read began, not when a held read is released, or they cannot show it.

**Writes and broadcasts with no read count too.** f0208 design review 001 F2: joining a 2 PLAYERS line, inviting and cancelling cost the client nothing (its record was cached), yet each loop wrote one MemoryStore entry and broadcast twice; "one invite per wait" bounded nothing, since a wait is free, and a drained experience-wide MemoryStore quota made every pass-map read fail open. The fix is one per-player budget over every write the server makes for that client (a pure rule, `Play.spend`), broadcasts coalesced to once a second, and a case that loops the remotes for a simulated minute and counts both.

**Also:** R0110 code review 001 F1: c0202's note above came true in the library's code. `Wallet`'s record seen kept whichever answer came back last: a read served before a revive grant, or the arrival's claim applied only after its pass read, put back a record with no revive, and `useRevive` (which answers "none held" from that record with no write) refused the revive just bought. Order a cache by the store, not by arrival: each call takes a ticket at its start, and its result is kept only when no other call on that key started or ended while it ran; otherwise forget the entry, so the next request reads or writes. F3: an allowance re-armed by every answer ("down" again within the retry span) bounded the reads but not the writes it allowed, so fifty presses wrote fifty passes; bound the write itself per span, and count the writes in a case that loops the requests.

**Note** (c0202 design review 002 F3, 2026-11-17): on the library, a tell reads the record seen, which costs a store read (up to `Wallet.WAIT_SECONDS`) whenever the library forgot it, after an overlap or a failed write: exactly the outage in which a give-back fails. Placed before `Session.hold(false)` and `Session.decline`, it held END GAME for up to 5 s. Tell last, after every state change the write leads to, and pin it with a case whose read is held.
