# Execute a raft

Input: a raft ID (`R0010`) whose issues are `design: ready`, readied by z-ready and launched by z-code (or handed to you as its prompt).
Output: one layer per ticket. `./zn finish <issue>` makes that layer one commit; `./zn done R0010` lands the stack.

Work through the phases in order and don't skip any. Wherever you are unsure, the zz-rules, zz-arch and zz-test skills, and your project's own skills (`pickman-arch` and `pickman-test` for pickman), are binding.

## Phase 0: Claim (in the first minutes)
1. Work in the raft's worktree: `cd "$(./zn worktree R0010)"` (zz-rules skill, Worktrees), then run `./zn sync` there (a reused worktree may be behind). A new raft worktree is detached at a freshly fetched `origin/main` until `./zn start` checks out the layer. There is no `R####-<slug>` branch. Never switch branches in the main checkout, and run everything below from this directory. Phase 0 runs no gate and reads no CI result: a red `main` first shows at the merge.
2. `./zn start R0010`. It opens the next layer (branch `R0010/1/c0010`, an empty commit, a draft PR on the layer below). You are on one ticket: this layer, the layer below, and this ticket's checks. `./zn finish <issue>` when they are green; `./zn start` again opens the next layer. If it refuses with `run ./zn sync first`, sync and retry.
3. Read the raft document, then every issue document and `check.sh`, in the raft's order.
   - Write down, for yourself, which files each issue touches.

## Phase 1: Experiments (fail fast)
- Run every probe, experiment, loop and background command you start yourself (anything that is not the gate, a check, a `./zn` command or the spec runner) through `./zn run --time <seconds> -- <command>`: it stops at its limit, when it ends and when you do. A `/clear` ends the background commands of the conversation it clears (the SessionEnd hook stops its tool shells).
- For every unknown in the raft's and issues' "Unknowns & experiments" that has no recorded result: run the experiment in the issue's `experiments/` directory, and record the result in the issue document.
- **If an experiment fails:**
  - Switch to the documented fallback, and note that in the issue.
  - If there's no fallback: **stop** and escalate (see Stop conditions).
- Commit: `./zn commit -m "R0010: experiments"`, then post a PR comment listing each experiment and its result. Do not pass `--time` or `--tokens`; the tool measures cost.

## Phase 2: Implement, one issue at a time in the raft's order
For each issue:
1. `./zn focus <issue>`.
2. **Tests first.**
   - Write the specs in the issue's Test plan under `tests/`. These are your own unit, contract and regression specs.
   - The sequestered acceptance specs in `<root>/issues/<id>/acceptance/` (`./zn find <id>`) already exist from prep. Don't modify or move them; `done` promotes them. An easy ticket with a short note has none: its one spec (the note's `Test:`) is written here, in the project's `tests/`, and committed red on its own before the code.
   - Run them and confirm that each one **fails for the expected reason**, not because of a syntax error or a missing file.
3. **Implement** the Design exactly, following the Implementation steps. In an interactive session, run `./zn model code --for <issue>` first and build the layer with a subagent on the model that line names (AGENTS.md, Subagents: on exit 1 print the "waiting for a worker with ..." line the command gave, stop, and tell the person that a worker whose CLI has that model must take it, on exit 2 show the error). A fix of the layer after a review is the same activity (`./zn model fix --for <issue>`).
   - Iterate with `z-nile/check.sh --affected`.
   - Commit at meaningful green steps with `./zn commit -m "<issue>: <what>"`. Do not pass `--time` or `--tokens`.
4. **Finish the issue**: `./zn check <issue>` shows every AC as PASS. Append a Verification log entry, commit it, then `./zn finish <issue>`. That squashes this layer into one commit (`<issue>: <title>`). `./zn start` opens the next layer. Post a PR comment `<issue> done: n/n ACs PASS`.
5. **Deviations**:
   - If the design turns out to be wrong in a small, local way (for example a name or a helper split), adjust it and record the deviation, with the reason, in the issue's Verification log.
   - If it's wrong in a way that changes a public API, a cross-feature dependency or an acceptance criterion, **stop** and escalate.
   - In guess mode every deviation is also recorded with `./zn guess <id> --step build`, so the issue's approval stops holding and the person reads it before it lands (z-work skill, Guess mode).
6. **Emergent problems**: follow "Emergent issues" in the zz-rules skill. Only fix them now if they can't be postponed.

## Phase 2B: Parallel work
Layers replace stream branches. There is no `ws-<issue>` branch and nothing is squashed into a raft branch. Two machines work on different layers of the same raft (`./zn stack <R-id>`). Commits on a layer, whoever made them, become that layer's one commit at `./zn finish <issue>`.

**Candidate lessons are written as they arrive**, on the layer, so finish folds them into that one commit. A subagent puts a candidate in its report: a candidate lesson goes in the final report too. When a report arrives, the lead records a candidate lesson of a report as `- note ws-<issue> (erred <skill>): <lesson ids>` in the raft's `harvest.md` (you name the step the candidate is about), and each time a stream review is committed (`./zn dispatch zz-review <R-id> --mode stream` files one), every finding of it as an entry `- stream-review-<issue>-NNN F<n>: <lesson ids>` (or `one-off: <reason>`), each with its step group `(erred <skill>[, upstream <skill>])` before the colon, copied from the finding's `Erred:` and `Upstream:` lines (run `./zn lessons --check-review <the file>` on each stream review before you commit it; one that fails, or has none, goes back to its reviewer). A new lesson file only when no lesson fits. It commits them on the layer.

1. Finish the layer you are on with `./zn finish <issue>` once its checks are green. `./zn start` opens the next layer.
2. Review that layer in Code mode. The reviewer is given `git diff <layer below>...HEAD` (the first layer: `origin/main...HEAD`).
3. After a fix on a lower layer, `./zn finish` that layer again and `./zn restack <R-id>` before an upper layer is reviewed or `./zn done` lands the stack. The same goes for any other commit on a lower layer after its finish (its review files included): only the top layer may carry commits after its finish commit.

## Phase 3: Whole-raft verification
When the steps below pass, post a PR comment with the RC results.

1. `bash "$(./zn find R0010)/check.sh"`. Every RC line must PASS.
2. Double-check that `z-nile/check.sh --affected` passes as well (every project: the raft's RC0 runs only its own project's gate, c0120), and that `./zn promote-check R0010` passes. It dry-runs the move of the acceptance specs into the project's `tests/acceptance/`. If it fails because of a sequestered spec, stop and escalate now, not at `done`.
3. **Gate speed** moves to Phase 6 step 1: the wall time and the `slowest:` specs of the merge's full gate go in the final report and its PR comment, never into a tracked file.
4. **Sequestration check**: `git fetch origin main && git diff --find-renames=100% --name-status origin/main...HEAD -- 'tracker/**/check.sh' 'tracker/**/acceptance/**' '*/.tracker/**/check.sh' '*/.tracker/**/acceptance/**'` must list nothing except `R100` renames (a raft started the legacy way moves its items on the branch). The three-dot form separates what this branch changed from what `main` brought in, so other terminals' new stubs are not false positives.

## Phase 4: Adversarial code review (a clean reviewer)
The code review is skipped only for a raft whose document says `light: true` and that `./zn work next` still calls light (the light path: one easy ticket readied by `./zn ready <issue>`); its final review then covers the code, and the short note that stands in for the design review of an easy ticket (zz-review, Final mode, Light path; z-design, The easy path). The test of an easy ticket is written with the code, still red first: commit the failing spec before the code. A final review that says `Level: normal` or `Level: risky` sends the ticket through the full design path (`./zn stop <R-id>`, then z-design in full) before it can merge. Every other raft has this phase.
The PR is the visible record of the work. Push and post a PR comment (`gh pr comment --body-file -`) at each step below, so a human watching sees the review start, its findings, and how they were answered. Never hold review state locally. If a push or `gh` call fails, retry once, then carry on and mention the failure in your next comment; don't block on it. `./zn commit` skips the push when there is no upstream, so check that `git status -sb` shows no `ahead`.

1. **Before launching**: commit any pending work with `./zn commit` so the reviewer sees exactly what the PR shows. Run `z-nile/check.sh --affected` and read the whole lint summary (the `errors`/`warnings` lines, never just the last line); a red gate is fixed before a reviewer is launched. Then post the comment `Review NNN started at <short sha> (code mode)`.
2. Start a **clean** reviewer. It has none of your context and gets only these inputs:
   - the `zz-review` skill (code mode);
   - `git diff <layer below>...HEAD` (the first layer: `origin/main...HEAD`; the local `main` isn't kept current);
   - the raft and issue documents and `check.sh` files;
   - read access to the repo.
   In Claude Code, that's a fresh subagent. For other agents, use a new session or context that receives only those inputs.
   Run the reviewer on the model `./zn model code-review --for <R-id>` prints (another model than the one that wrote the code is preferred; its own model is allowed, and the line says `same-model=yes` then, which the review's spend row records; the reviewer is still a clean context, unchanged). `./zn dispatch zz-review <R-id> --mode code` starts it on that model and prints the `./zn commit … --phase code-review --model <id>` line for step 3 (a headless run always uses it). In an interactive session, start the reviewer subagent with that line; when the command exits 1, don't review it yourself: print the "waiting for a worker with ..." line the command gave, stop, and tell the person that a worker whose CLI has that model must take it. Say which model reviewed in the review PR comment. Tell a subagent reviewer to write only `review-NNN.md`: no commits, pushes, PR comments or stray files (a dispatched one writes `review.md` in its state folder, and the dispatcher places it as `review-NNN.md`).
3. The reviewer writes `review-NNN.md` in the raft directory (starting at 001), including a ruling on every Judged criterion. **When the reviewer finishes**, you commit it: `./zn commit -m "R0010: review-NNN" --phase code-review --model <reviewer model>` (this pushes; the model comes from the one `record:` line `./zn dispatch zz-review` printed. Do not pass `--time` or `--tokens`). Then comment with the verdict and the finding count by severity, listing each `F<n> [severity] <claim>`. A dispatched review that fails with "the reviewer wrote no review" still prints its `record:` line: commit that line alone (the commit is its spend row), then rerun the review, which is still the same round.
4. **If the verdict is `approve` with no findings, go to Phase 5**: there is no refute file, and the verdict comment is the record. Otherwise respond in `refute-NNN.md` (the answer runs on the model `./zn model code-answer --for <R-id>` prints), with one line per finding:
   - `- F3: fixed <short sha>: <what changed>; consequences: <what the fix could break or open, and how you checked it, or none>`, or
   - `- F3: refuted: <argument with evidence>`, or
   - `- F3: deferred <id>: <why>`, only for a medium or low finding (a high cannot be deferred).
   Only refute when you can show the reviewer is wrong: a test, a spec, or the design text. Everything else gets fixed. Before each fix, take it one step further, as z-design's consequence step does; `./zn done` refuses a fixed answer without `consequences:`.
5. Commit each fix as you make it (pushed by `./zn commit --phase code-review`). **Harvest the round** as z-design step 5.3 does: one entry per finding of `review-NNN.md` in the raft's `harvest.md`, with its step group (a code review that finds a design hole names `z-design`, not this step, and a finding about something design wrote, the issue document, `check.sh` or a sequestered spec, names `Upstream: z-design`; run `./zn lessons --check-review <the round's file>` on each new review round, and a round that fails, or has no step lines, goes back to its reviewer; any lesson, design ones included; a new one is usually `when: build` or `both`), then `./zn lessons --uncovered R0010`, `./zn lessons --unattributed R0010` and `./zn lessons --check`. Then commit the refute file, the ledger and the lessons the same way. Post a comment `Review NNN addressed`, pasting the refute file's lines.
6. **Then the next round, or the human.** When the verdict is not approve and `./zn work next` names another round, run it from step 1. Round 1 reviews everything. Round N+1 is given the previous round's findings and the answers and checks that each fix is real and introduced nothing new in the lines it touched; it raises a new finding only for a defect in those changes or one it can show round 1 could not have seen: a later round only checks the answers. Between rounds the author answers every finding in the refute file (fixed with consequences, or refuted) and nothing goes to the human: the next round's reviewer accepts or re-raises each refutation. Only at the settling round (approve, only low findings, or the maximum) does anything you refuted, any high finding you could not close (not answered `fixed`), and any Judged criterion ruled fail, go in the raft document under `## Open to the human`, one bullet each: `- F2: <the finding>. Answer: <your answer>. Decision: <what the human must decide>` (a failed Judged criterion uses its `JC<n>` id); a bullet for a round after the first of its kind names its review file (`- review-002 F2: ...`, `- final-review-002 F2: ...`), because finding ids restart at F1 in every review. When the review settled at the maximum with serious findings answered, `./zn work next` says so: record it as a guess (`./zn guess <id> --step build`) so the owner sees it at approval. `./zn rounds <R-id> [--kind code|final]` prints in one line which round is due, what to answer, or that the review settled. The raft can be `done` when that list is empty or every bullet carries `Ruled (user, YYYY-MM-DD): <their decision>`. Do not guess a ruling, except in guess mode, where an open ruling may be answered with `./zn guess <id> --step build`. A medium or low finding you fixed, or deferred to a backlog issue (`- F<n>: deferred <id>: <why>`; `./zn done` accepts that only for a medium or low finding), does not go on the list. Quote every deferred line in the PR comment. Then continue to Phase 5.

## Phase 5: Done
1. Append each issue's final Verification log entry and fill in the raft's "Addressed during execution". Commit with `./zn commit --phase deliver`.
2. If `main` moved, `./zn restack <R-id>` (renumber colliding IDs, rerun `z-nile/check.sh --affected`, commit with `./zn commit --phase deliver`), so the stack is on that main before `done`.
   **A restack that stops on a conflict is yours to resolve, not the person's** (d0434). zn leaves the rebase in progress in the raft's worktree and prints the layer and the conflicted files (exit 3); `./zn work next` names the same action. Each layer is pushed on its own as soon as it is restacked and its check passes, before the next layer is restacked, so a stop leaves the layers below it pushed and it and the layers above it not. Read both sides of each file, resolve it keeping both intents, and `git add` it. Run the specs the resolved files select, by name, not the gate (`lune run z-nile/affected -- <files>` lists them). Then run `./zn restack <R-id> --continue`: it finishes the rebase, checks the layer and restacks the layers above. A later layer may stop again: repeat. If the check goes red after the continue, that layer and the ones above it were not pushed (the layers below it that passed already are) and the restacked tip with your resolution stays on the layer's local branch, unpushed (a plain restack with a red check does the same, and `./zn work next` names this fix, not another restack): fix the layer on that tip, `./zn finish` its issue, then run a plain `./zn restack <R-id>`, which trusts that tip as your own work and goes on from the pushed layers. `./zn restack <R-id> --abort` puts the layers not yet pushed and the worktree back as before the run and leaves the layers it already pushed as pushed (it never moves origin back); a plain `./zn restack <R-id>` then goes on from them. If the resolution empties a commit (its change is already below), or the two sides changed the same behaviour on purpose and you cannot tell which the owner wants, stop and ask, naming the files and both intents: an unattended worker writes `questions.md` and stops as z-work's step for questions says. Never `git rebase --skip`, never drop a commit, never force-push by hand, and never commit an empty one without the owner's answer.
3. **Trace skeleton, then the final review (idea = design = test = code)**: after the last layer is finished and restacked (steps 1 and 2), print the trace skeleton with `./zn trace <R-id>` and commit that skeleton as `trace.md` with `./zn commit`. Then run the final review once on the finished stack (`./zn dispatch zz-review <R-id> --mode final`, or a fresh subagent on the model `./zn model final-review --for <R-id>` prints, in final mode) given the skeleton, the tickets' documents and `git diff origin/main...HEAD`. The reviewer fills `<raft-dir>/trace.md` and writes `final-review-NNN.md` with a verdict and findings; when its verdict is not approve and `./zn work next` names another round, run it. Answer the findings of each round in `final-refute-NNN.md` (on the model `./zn model final-answer --for <R-id>` prints; the trace skeleton and its fixes on `./zn model trace --for <R-id>`) (if a fix changes a layer, `./zn finish` and `./zn restack <R-id>`, and update `trace.md` for the new top-layer commit; anything still open goes under `## Open to the human`). Commit `trace.md` and the final review files with `./zn commit --phase code-review --model <reviewer model>`, after step 1's commit (an issue document committed after the table makes it stale), then verify that `./zn trace <R-id> --check` passes: before the skeleton is committed the check reports the commits after the finish as added before `trace.md`.
4. **Confirm the harvest**: first harvest anything `./zn lessons --uncovered R0010` still lists, as Phase 4 step 5 says. That includes the design reviews of a raft prepped before lessons existed, which are harvested here by you. Give a step to every entry `./zn lessons --unattributed R0010` lists (a raft prepped before steps existed: you judge it, as z-design step 5.3 says). Then `./zn lessons --uncovered R0010`, `./zn lessons --unattributed R0010` and `./zn lessons --check` must pass. Commit with `./zn commit --phase deliver`.
5. `./zn done R0010` lands the stack. It refuses a checkout that is not the published top-layer commit, an unfinished or unstacked layer, a changed contract, a failing or stale `./zn trace <R-id> --check`, and a final review with no `Verdict:` line or whose verdict is not `approve` while an open finding has no human ruling in `## Open to the human`. The binding commit records the final review's `Verdict:` line and `Trace: <done-raft-dir>/trace.md`. The human runs `./zn approve <id>` again when the contract changed, then `./zn done`.
6. Post a PR comment `Ready to merge at <short sha>` (no final report yet). In guess mode, when a member is not approved, Phase 5 ends at `wait` instead: the person reads `./zn guesses <R-id>` and runs `./zn approve <id>` for each member, from anywhere in the checkout (it records in the raft's worktree, on its top layer, and pushes that layer), then `./zn done` lands.

## Phase 6: Merge and clean up
Under `./zn dispatch` (headless) the run ends at Phase 5's `Ready to merge` comment: the merge of the run's PR is a human's gate, and the dispatcher records the run's spend after it. Skip this phase.
1. `./zn done` already landed the stack (one `--no-ff` merge). Do not merge again and do not squash. After the merge, `./zn watch-kick`: it starts the net under `./zn run` in the main checkout's `.worktree/watch-net` and returns once the net has its worktree (a second or two), printing `watch-net: started, log at <absolute path>` or, when a net already runs, `watch-net: already running` (both exit 0). A running net runs your landing again at its end, in a fresh net when its own time is short. Exit 1 and the lines on stderr (the net's last line and `watch-net: log at <path>`) mean the net did not start: put both in the final report; it does not undo the merge, and repairing the net's worktree is not this raft's work. A `watch-net: no pass since <date>` line means main has had source commits for more than a day with no passing net run: report it too. A pull request that changes only tooling is gated by `z-nile/check.sh --affected` on the branch. A pull request that changes a game is gated by the local full gate, `z-nile/check.sh --full`, in a clone of the exact head whose parent directories are not a checkout of this repo, and by `lune run scripts/cicd` there. The PR is mergeable. Record the **gate wall time** and the `slowest:` specs of the merge's gate in the final report and its PR comment. If the merge's gate fails, post a `BLOCKED:` comment naming the failing specs and stop with the PR ready and unmerged; in the raft worktree at the PR head, for each failing spec that `lune run z-nile/affected -- --base $(git merge-base origin/main HEAD)` does not list, file a watch-miss chore (zz-test, Watch miss) and say so in the comment, unless the spec also fails on `origin/main` (then it is a red `main`: say that instead). If another condition can't be met, post a `BLOCKED:` comment and stop; the final report then says BLOCKED. A re-run after main moves is required only when the merged-in commits select a spec for this pull request; tracker-only commits require none (zz-rules, Merging).
2. After the merge and before the final report, `./zn spend R0010 --phase deliver` in the raft's worktree. It commits the row there and publishes it to `origin/main` itself (`published R0010 deliver to origin/main <sha>`): the raft has landed, so no pull request carries the row. If it says it could not publish, nothing was recorded: fix what it names and run it again before the cleanup. If it says the row stays on this branch, the cleanup would lose it: do not clean up, post a `BLOCKED:` comment quoting that line, and stop. Do not pass `--time` or `--tokens`.
3. Write the final report (below), with the merge commit sha. Post it as a comment on the merged PR (`gh pr comment <pr> --body-file -`) *before* cleanup, since cleanup removes your worktree.
4. Follow Landing a change, step 4, in the zz-rules skill, last: the one chained command that updates the root's `main` (`"<root>/zn" sync`, which also rebuilds its board), removes this raft's worktree and deletes the local branch (it removes your own working directory, so nothing runs after it). Post no further commits to the branch. Then give the same report in your reply.

## Stop conditions (escalate; don't improvise)
Stop and report if any of these happen:
- An experiment fails and has no fallback.
- The design is wrong beyond local adjustments.
- Delivering an issue would drop or shrink an outcome its Problem asks for, because the design, a check or a fix requires it. Only the user changes scope. Any other human decision is a recorded guess in guess mode (`./zn guess <id> --step build`), not a stop.
- A `check.sh` or acceptance spec is wrong or can't be satisfied.
- Main is red.
- A tool is missing and `SETUP.md` doesn't fix it.
- The open list under `## Open to the human` still has a bullet with no `Ruled (user, YYYY-MM-DD):`.
- An action would require a secret or credential you don't have.
- A test run prints `REPOSITORY CHANGED` or refuses a fixture identity, or the shared repository's remotes, branches, worktrees or identity look wrong: stop at once, and never repair the shared git configuration yourself (zz-test skill, "Specs never touch the real repository").

To escalate:
1. Commit whatever is green.
2. Push.
3. Leave the PR in **draft**, or, if it's already ready (a `BLOCKED:` stop after `done`), leave it as it is and unmerged.
4. Post a PR comment that starts with `BLOCKED:` and covers what you tried, the evidence, and the decision you need.

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A lesson goes to the step that erred: the skill whose instructions the author was following when the mistake was made, or the skill of an earlier step that should have prevented or caught it (that skill is `<the skill the lesson improves>` below). The harvest line names that step as `(erred <skill>[, upstream <skill>])` before its colon (zz-rules skill, Items), and every kind of review and correction is harvested: a finding of a design, code, stream or focused review as an entry of the item's `harvest.md`, and a programme review, a correction by the user or a failed step as a `- note` entry.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened> (erred <skill>): <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-idea skill). The prep that takes the issue writes the file.
