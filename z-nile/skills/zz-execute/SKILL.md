# Execute a raft

Input: a raft ID (`R0010`) whose issues are `design: ready`, readied by z-ready and launched by z-run (or handed to you as its prompt).
Output: one layer per ticket. `./zn finish <issue>` makes that layer one commit; `./zn done R0010` lands the stack.

Work through the phases in order and don't skip any. Wherever you are unsure, the zz-rules, zz-arch and zz-test skills, and your project's own skills (`pickman-arch` and `pickman-test` for pickman), are binding.

## Phase 0: Claim (in the first minutes)
When the item's folder holds `escalation.md` with a `## Resolution`, read it before you start: it is the human's decision on the last block, unless its `Decision:` is `abort` (that attempt ended: start fresh).
1. Work in the raft's worktree: `cd "$(./zn worktree R0010)"` (zz-rules skill, Worktrees), then run `./zn sync` there (a reused worktree may be behind). A new raft worktree is detached at a freshly fetched `origin/main` until `./zn start` checks out the layer. There is no `R####-<slug>` branch. Never switch branches in the main checkout, and run everything below from this directory. Phase 0 runs no gate and reads no CI result: a red `main` first shows at the merge.
2. `./zn start R0010`. It opens the next layer (branch `R0010/1/c0010`, an empty commit, a draft PR on the layer below). You are on one ticket: this layer, the layer below, and this ticket's checks. `./zn finish <issue>` when they are green; `./zn start` again opens the next layer. If it refuses with `run ./zn sync first`, sync and retry.
3. Read the raft document, then every issue document and `check.sh`, in the raft's order.
   - Write down, for yourself, which files each issue touches.

## Phase 1: Experiments (fail fast)
- Run every probe, experiment, loop and background command you start yourself (anything that is not the gate, a check, a `./zn` command or the spec runner) through `./zn run --time <seconds> -- <command>`: it stops at its limit, when it ends and when you do. A `/clear` ends the background commands of the conversation it clears (the SessionEnd hook stops its tool shells).
- For every unknown in the raft's and issues' "Unknowns & experiments" that has no recorded result: run the experiment in the issue's `experiments/` directory, and record the result in the issue document.
- **If an experiment fails:**
  - Switch to the documented fallback, and note that in the issue.
  - If there's no fallback: **stop** and escalate (see Stop conditions).
- Commit: `./zn commit -m "R0010: experiments"`, then post a PR comment listing each experiment and its result. Do not pass `--time` or `--tokens`; the tool measures cost.

## Phase 2: Implement, one issue at a time in the raft's order
For each issue:
1. `./zn focus <issue>`.
2. **Tests first.**
   - Write the specs in the issue's Test plan under `tests/`. These are your own unit, contract and regression specs.
   - The sequestered acceptance specs in `<root>/issues/<id>/acceptance/` (`./zn find <id>`) already exist from prep. Don't modify or move them; `done` promotes them.
   - Run them and confirm that each one **fails for the expected reason**, not because of a syntax error or a missing file.
3. **Implement** the Design exactly, following the Implementation steps.
   - Iterate with `z-nile/check.sh --affected`.
   - Commit at meaningful green steps with `./zn commit -m "<issue>: <what>"`. Do not pass `--time` or `--tokens`.
4. **Finish the issue**: `./zn check <issue>` shows every AC as PASS. Append a Verification log entry, commit it, then `./zn finish <issue>`. That squashes this layer into one commit (`<issue>: <title>`). `./zn start` opens the next layer. Post a PR comment `<issue> done: n/n ACs PASS`.
4a. **The ticket's final review** (before the next layer starts, and after the layer's own code review): for a ticket marked `final: ticket` (`./zn status <id> prepared` writes it), `./zn work next` says `final-review-ticket` for its finished layer. Run `./zn dispatch zz-review <issue> --mode final`: it starts the reviewer on the `final-review` role in the folder `./zn final <issue> --view` prints (ask, design, contract and the layer's diff, with none of the design reviews, refutes, harvests, pull request comments or worker notes). An agent never starts that reviewer itself: a subagent or CLI it starts carries its checkout's instructions and memory; only a person runs `./zn final <issue> --view` and starts a CLI of their own in that folder. It writes `final-review-NNN.md` in the issue's folder with `Verdict: on-course | off-course`; commit and push it on the layer. On course: the layer is complete and `./zn start` opens the next. Off course by the implementation: `./zn work next` says `rebuild`; harvest each finding into the issue's `harvest.md`, fix the layer, `./zn finish` it again, and the review runs once more. Off course by the design: it says `redesign`; harvest the findings, then the ticket goes back to z-design (copy its `final-review-NNN.md` files into the re-prep's issue folder). A second off-course verdict blocks the ticket for the human (`blocked`): write `escalation.md` in the raft's folder, the first line of its `## Open findings or error` naming the latest `final-review-NNN.md` (the one `./zn final <issue>` names), and run `./zn block <R> review-exhausted --layer <issue>` (an unreadable review: `needs-decision`); the human resolves it with `./zn resolve`. After `approve` or `retry` the raft is `prepared`: it is readied again (z-ready; after an `approve` the person first re-approves the ticket with `./zn approve`), and `./zn work next` goes on; after `amend-design` the ticket has left the raft and is re-prepped as a redesign (copy its `final-review-NNN.md` files first), and the raft is readied again without it; after `abort` nothing is readied (z-stop); after `split` the new issue is captured and the ticket re-prepped. Before a redesign or a block, a raft readied with `layers: reviewed` lands its complete layers below with `./zn done <R> --through <issue>`; a raft without `layers: reviewed` lands whole, so nothing lands first. There is no third review without the human's ruling and no refutation of this one. `./zn final <issue>` prints where the ticket stands.
5. **Deviations**:
   - If the design turns out to be wrong in a small, local way (for example a name or a helper split), adjust it and record the deviation, with the reason, in the issue's Verification log.
   - If it's wrong in a way that changes a public API, a cross-feature dependency or an acceptance criterion, **stop** and escalate.
   - In guess mode every deviation is also recorded with `./zn guess <id> --step build`, so the issue's approval stops holding and the person reads it before it lands (z-work skill, Guess mode).
6. **Emergent problems**: follow "Emergent issues" in the zz-rules skill. Only fix them now if they can't be postponed.

## Phase 2B: Parallel work
Layers replace stream branches. There is no `ws-<issue>` branch and nothing is squashed into a raft branch. One worker holds the raft and builds its layers one at a time, each complete before the next starts; a second machine works on the raft only through a takeover (c0274). `./zn stack <R-id>` shows where the stack stands. A layer may still be built by streams: subagents of the worker committing on the layer it is on. Commits on a layer, whoever made them, become that layer's one commit at `./zn finish <issue>`.

**Candidate lessons are written as they arrive**, on the layer, so finish folds them into that one commit. A subagent puts a candidate in its report: a candidate lesson goes in the final report too. When a report arrives, the lead records a candidate lesson of a report as `- note ws-<issue> (erred <skill>): <lesson ids>` in the raft's `harvest.md` (you name the step the candidate is about), and each time a stream review is committed (`./zn dispatch zz-review <R-id> --mode stream` files one), every finding of it as an entry `- stream-review-<issue>-NNN F<n>: <lesson ids>` (or `one-off: <reason>`), each with its step group `(erred <skill>[, upstream <skill>])` before the colon, copied from the finding's `Erred:` and `Upstream:` lines (run `./zn lessons --check-review <the file>` on each stream review before you commit it; one that fails, or has none, goes back to its reviewer). A new lesson file only when no lesson fits. It commits them on the layer.

1. Finish the layer you are on with `./zn finish <issue>` once its checks are green, then review it (Phase 4). `./zn start` opens the next layer only when this one is complete: finished, green and reviewed.
2. Review that layer in Code mode. The reviewer is given `git diff <layer below>...HEAD` (the first layer: `origin/main...HEAD`).
3. After a fix on a lower layer, `./zn finish` that layer again and `./zn restack <R-id>` before an upper layer is reviewed or `./zn done` lands the stack. The same goes for any other commit on a lower layer after its finish (its review files included): only the top layer may carry commits after its finish commit.

## Phase 3: Whole-raft verification
When the steps below pass, post a PR comment with the RC results.

1. `bash "$(./zn find R0010)/check.sh"`. Every RC line must PASS.
2. Double-check that `z-nile/check.sh --affected` passes as well (every project: the raft's RC0 runs only its own project's gate, c0120), and that `./zn promote-check R0010` passes. It dry-runs the move of the acceptance specs into the project's `tests/acceptance/`. If it fails because of a sequestered spec, stop and escalate now, not at `done`.
3. **Gate speed** moves to Phase 6 step 1: the wall time and the `slowest:` specs of the merge's full gate go in the final report and its PR comment, never into a tracked file.
4. **Sequestration check**: `git fetch origin main && git diff --find-renames=100% --name-status origin/main...HEAD -- 'tracker/**/check.sh' 'tracker/**/acceptance/**' '*/.tracker/**/check.sh' '*/.tracker/**/acceptance/**'` must list nothing except `R100` renames (a raft started the legacy way moves its items on the branch). The three-dot form separates what this branch changed from what `main` brought in, so other terminals' new stubs are not false positives.

## Phase 4: Adversarial code review (a clean reviewer)
Phase 4 runs per layer, after the layer's `./zn finish` and before the next `./zn start`. Its files are `review-NNN.md` and `refute-NNN.md` in the issue's folder (`<root>/issues/active/<id>/`), numbered from 001 per issue. The tool stamps them: `./zn commit` (or the dispatcher, for a dispatched review) writes `Commit: <sha>` and `Patch: <id>` on their first lines from the layer's finish commit, and a reviewer never writes them. A layer is complete when its newest review is settled and current: its stamp names the finish commit or the same patch (a clean restack keeps it), or its refute answers a finding `fixed` for the new commit. `./zn start` and `./zn done` refuse a layer that is not. A layer's open list (`## Open to the human`) is the issue document's, and its harvest is the issue folder's `harvest.md`. A review with `Verdict: approve` and no findings goes to the next layer with nothing more to answer. A review file an old raft keeps in the raft folder still parses.

The PR is the visible record of the work. Push and post a PR comment (`gh pr comment --body-file -`) at each step below, so a human watching sees the review start, its findings, and how they were answered. Never hold review state locally. If a push or `gh` call fails, retry once, then carry on and mention the failure in your next comment; don't block on it. `./zn commit` skips the push when there is no upstream, so check that `git status -sb` shows no `ahead`.

1. **Before launching**: commit any pending work with `./zn commit` so the reviewer sees exactly what the PR shows. Run `z-nile/check.sh --affected` and read the whole lint summary (the `errors`/`warnings` lines, never just the last line); a red gate is fixed before a reviewer is launched. Then post the comment `Review NNN started at <short sha> (code mode)`.
2. Start a **clean** reviewer. It has none of your context and gets only these inputs:
   - the `zz-review` skill (code mode);
   - `git diff <layer below>...HEAD` (the first layer: `origin/main...HEAD`; the local `main` isn't kept current);
   - the raft and issue documents and `check.sh` files;
   - read access to the repo.
   In Claude Code, that's a fresh subagent. For other agents, use a new session or context that receives only those inputs.
   Run the reviewer on the **code-review role** `.models.toml` names, never on the model that wrote the code. On a raft readied with `layers: reviewed`, `./zn dispatch zz-review <issue-id> --mode code` (the layer's issue id) starts it on that role, files the review in the issue's folder and stamps it; on a raft readied without it (R0093 included), `./zn dispatch zz-review <R-id> --mode code` does. Either prints the `./zn commit … --phase code-review --model <id>` line for step 3 (a headless run always uses it). In an interactive session, start the reviewer subagent on that role's model. Say which model reviewed in the review PR comment. Tell a subagent reviewer to write only `review-NNN.md`: no commits, pushes, PR comments or stray files (a dispatched one writes `review.md` in its state folder, and the dispatcher places it as `review-NNN.md`).
3. The reviewer writes `review-NNN.md` in the issue's folder (starting at 001; the tool stamps it), including a ruling on every Judged criterion. **When the reviewer finishes**, you commit it on the layer: `./zn commit -m "c0010: review-NNN" --phase code-review --model <reviewer model>` (this pushes; the model comes from the one `record:` line `./zn dispatch zz-review` printed. Do not pass `--time` or `--tokens`). Then comment with the verdict and the finding count by severity, listing each `F<n> [severity] <claim>`. A dispatched review that fails with "the reviewer wrote no review" still prints its `record:` line: commit that line alone (the commit is its spend row), then rerun the review, which is still the same round.
4. **If the verdict is `approve` with no findings**, there is no refute file, and the verdict comment is the record: on a raft readied with `layers: reviewed` the layer is complete, so go to the next layer's `./zn start` (Phase 5 after the last layer); on a raft readied without it, go to Phase 5. Otherwise respond in `refute-NNN.md`, with one line per finding:
   - `- F3: fixed <short sha>: <what changed>; consequences: <what the fix could break or open, and how you checked it, or none>`, or
   - `- F3: refuted: <argument with evidence>`, or
   - `- F3: deferred <id>: <why>`, only for a medium or low finding (a high cannot be deferred).
   Only refute when you can show the reviewer is wrong: a test, a spec, or the design text. Everything else gets fixed. Before each fix, take it one step further, as z-design's consequence step does; `./zn done` refuses a fixed answer without `consequences:`.
5. Commit each fix as you make it (pushed by `./zn commit --phase code-review`). **Harvest the round** as z-design step 5.3 does: one entry per finding of `review-NNN.md` in the `harvest.md` beside it (the issue folder's on a raft readied with `layers: reviewed`, checked with `./zn lessons --uncovered <issue>`; the raft's otherwise), with its step group (a code review that finds a design hole names `z-design`, not this step, and a finding about something design wrote, the issue document, `check.sh` or a sequestered spec, names `Upstream: z-design`; run `./zn lessons --check-review <the round's file>` on each new review round, and a round that fails, or has no step lines, goes back to its reviewer; any lesson, design ones included; a new one is usually `when: build` or `both`), then `./zn lessons --uncovered R0010`, `./zn lessons --unattributed R0010` and `./zn lessons --check`. Then commit the refute file, the ledger and the lessons the same way. Post a comment `Review NNN addressed`, pasting the refute file's lines.
6. **Then the human.** There is no second reviewer of the same change. A layer's next review round (`review-NNN+1.md`, stamped by the tool) is run only when its newest round is answered (its refute answers every finding, as `done` reads it) and a fix then changed the layer's patch (a final review's finding, a conflicting restack): a refute cannot carry an approve with no findings, or answers that fixed nothing, to a changed patch, so the layer is not complete until that round. `./zn dispatch zz-review <issue-id> --mode code` files it, and refuses it while the newest round is current or not yet answered. After this one revision, anything you refuted, any high finding you could not close (not answered `fixed`), and any Judged criterion ruled fail, goes in the issue document under `## Open to the human` (a final review's, in the raft document), one bullet each: `- F2: <the finding>. Answer: <your answer>. Decision: <what the human must decide>` (a failed Judged criterion uses its `JC<n>` id). The raft can be `done` when that list is empty or every bullet carries `Ruled (user, YYYY-MM-DD): <their decision>`. Do not guess a ruling, except in guess mode, where an open ruling may be answered with `./zn guess <id> --step build`. A medium or low finding you fixed, or deferred to a backlog issue (filed with `./zn new issue … --project <name> --filed-by "review:<raft id>/<review file stem> F<n>"`; `- F<n>: deferred <id>: <why>`; `./zn done` accepts that only for a medium or low finding), does not go on the list. Quote every deferred line in the PR comment. Then continue to Phase 5.

## Phase 5: Done
1. Append each issue's final Verification log entry and fill in the raft's "Addressed during execution". Commit with `./zn commit --phase deliver`.
2. A `main` that moved needs no restack: `./zn finish`, `./zn trace` and `done` judge layer 1 against the commit where it left `main`, and `done` merges the stack onto the newest `main` and runs the gate on that merged tree. If `main` moves again during that gate, `done` merges and gates again by itself, up to nine times. Run `./zn restack <R-id>` only when `done` reports a conflict or a red gate on the merged tree (renumber colliding IDs, rerun `z-nile/check.sh --affected`, commit with `./zn commit --phase deliver`), after a fix on a lower layer, or when `./zn trace` or `done` asks for it on a raft readied `--on` another raft once that raft has landed.
3. **Trace skeleton, then the final review (idea = design = test = code)**: after the last layer is finished, and the layers above any fixed layer are restacked, print the trace skeleton with `./zn trace <R-id>` and commit that skeleton as `trace.md` with `./zn commit`. On a raft readied with `layers: reviewed`, every name in this step is the landing's: the skeleton is `./zn trace <R-id> [--through <issue>]` over the layers this landing binds, committed as `trace-NNN.md`, and the reviewer writes `final-review-NNN.md` (answered in `final-refute-NNN.md`), where NNN is one more than the highest final review on `origin/main`. Then run the final review once on the finished stack (`./zn dispatch zz-review <R-id> --mode final`, or a fresh subagent on the review model of the CLI in final mode) given the skeleton, the tickets' documents and `git diff origin/main...HEAD`. The reviewer fills `<raft-dir>/trace.md` and writes `final-review-001.md` with a verdict and findings. Answer any findings once in `final-refute-001.md` (if a fix changes a layer, `./zn finish` and `./zn restack <R-id>`, and on a raft readied with `layers: reviewed` that layer's next review round, Phase 4 step 6, and update `trace.md` for the new top-layer commit; anything still open goes under `## Open to the human`). Commit `trace.md` and the final review files with `./zn commit --phase code-review --model <reviewer model>`, after step 1's commit (an issue document committed after the table makes it stale), then verify that `./zn trace <R-id> --check` passes: before the skeleton is committed the check reports the commits after the finish as added before `trace.md`.
4. **Confirm the harvest**: first harvest anything `./zn lessons --uncovered R0010` still lists, as Phase 4 step 5 says. That includes the design reviews of a raft prepped before lessons existed, which are harvested here by you. Give a step to every entry `./zn lessons --unattributed R0010` lists (a raft prepped before steps existed: you judge it, as z-design step 5.3 says). Then `./zn lessons --uncovered R0010`, `./zn lessons --unattributed R0010` and `./zn lessons --check` must pass. Commit with `./zn commit --phase deliver`.
5. `./zn done R0010` lands the stack. It refuses a checkout that is not the published top-layer commit, an unfinished or unstacked layer, a changed contract, a failing or stale `./zn trace <R-id> --check`, and a final review with no `Verdict:` line or whose verdict is not `approve` while an open finding has no human ruling in `## Open to the human`. The binding commit records the final review's `Verdict:` line and `Trace: <done-raft-dir>/trace.md`. The human runs `./zn approve <id>` again when the contract changed, then `./zn done`.
6. Run the final review and `./zn done` once per landing. When a layer is blocked, the green layers below it land now: `./zn done R0010 --through <issue>` lands only the layers up to that issue's, after its own final review (`final-review-NNN.md`) and trace (`trace-NNN.md`) over exactly those layers. It moves only those tickets to `done/`, and the raft stays in `active/` until its last layer lands. The raft's `check.sh` runs for the landing's members (`ZN_BIND_MEMBERS`), and its `RC1` and later lines run at the last landing. The lowest layer left is judged against its fork with `main`, like layer 1, so it needs no restack, and its review stays current. A layer that still sits on an older finish of the layer below (a fix made there after it was cut) is refused naming `./zn restack R0010`, which moves only its own commits onto `main`. The layer after them resumes once the blocker is resolved. A raft readied without `layers: reviewed` (one readied before c0248 landed, R0093 included) keeps the rule it was readied under: its code review is the raft's, it has one `trace.md` and one `final-review-NNN.md`, and it lands whole with one `./zn done`, which refuses `--through`.
7. Post a PR comment `Ready to merge at <short sha>` (no final report yet). In guess mode, when a member is not approved, Phase 5 ends at `wait` instead: the person reads `./zn guesses <R-id>` and runs `./zn approve <id>` for each member, from anywhere in the checkout (it records in the raft's worktree, on its top layer, and pushes that layer), then `./zn done` lands.

## Phase 6: Merge and clean up
Under `./zn dispatch` (headless) the run ends at Phase 5's `Ready to merge` comment: the merge of the run's PR is a human's gate, and the dispatcher records the run's spend after it. Skip this phase.
1. `./zn done` already landed the stack (one `--no-ff` merge). Do not merge again and do not squash. After the merge, `./zn watch-kick`: it returns at once, starts the net under `./zn run`, and writes `.cache/watch-net.log` in that checkout. It does not delay the merge, and a failure there does not fail it. A pull request that changes only tooling is gated by `z-nile/check.sh --affected` on the branch. A pull request that changes a game is gated by the local full gate, `z-nile/check.sh --full`, in a clone of the exact head whose parent directories are not a checkout of this repo, and by `lune run scripts/cicd` there. The PR is mergeable. Record the **gate wall time** and the `slowest:` specs of the merge's gate in the final report and its PR comment. If the merge's gate fails, post a `BLOCKED:` comment naming the failing specs and stop with the PR ready and unmerged; in the raft worktree at the PR head, for each failing spec that `lune run z-nile/affected -- --base $(git merge-base origin/main HEAD)` does not list, file a watch-miss chore (zz-test, Watch miss) and say so in the comment, unless the spec also fails on `origin/main` (then it is a red `main`: say that instead). If another condition can't be met, post a `BLOCKED:` comment and stop; the final report then says BLOCKED. A re-run after main moves is required only when the merged-in commits select a spec for this pull request; tracker-only commits require none (zz-rules, Merging).
2. After the merge and before the final report, `./zn spend R0010 --phase deliver`. Do not pass `--time` or `--tokens`.
3. Write the final report (below), with the merge commit sha. Post it as a comment on the merged PR (`gh pr comment <pr> --body-file -`) *before* cleanup, since cleanup removes your worktree.
4. Follow Landing a change, step 4, in the zz-rules skill, last: the one chained command that updates the root's `main` (`"<root>/zn" sync`, which also rebuilds its board), removes this raft's worktree and deletes the local branch (it removes your own working directory, so nothing runs after it). Post no further commits to the branch. Then give the same report in your reply.

## Stop conditions (escalate; don't improvise)
Stop and report if any of these happen:
- An experiment fails and has no fallback.
- The design is wrong beyond local adjustments.
- Delivering an issue would drop or shrink an outcome its Problem asks for, because the design, a check or a fix requires it. Only the user changes scope. Any other human decision is a recorded guess in guess mode (`./zn guess <id> --step build`), not a stop.
- A `check.sh` or acceptance spec is wrong or can't be satisfied.
- Main is red.
- A tool is missing and `SETUP.md` doesn't fix it.
- The open list under `## Open to the human` still has a bullet with no `Ruled (user, YYYY-MM-DD):`.
- An action would require a secret or credential you don't have.
- A test run prints `REPOSITORY CHANGED` or refuses a fixture identity, or the shared repository's remotes, branches, worktrees or identity look wrong: stop at once, and never repair the shared git configuration yourself (zz-test skill, "Specs never touch the real repository").

To escalate:
1. Commit whatever is green.
2. Push.
3. Leave the PR in **draft**, or, if it's already ready (a `BLOCKED:` stop after `done`), leave it as it is and unmerged.
4. Post a PR comment that starts with `BLOCKED:` and covers what you tried, the evidence, and the decision you need.
5. Block the raft: on a raft readied with `layers: reviewed`, land the green layers below the blocked one with `./zn done <R-id> --through <issue>` (a raft readied without it lands whole, so nothing lands before the block), write `escalation.md` in the raft's folder in your worktree (`## Question`, `## What was tried`, `## Open findings or error`, `## Options`: each option starts with one decision, exactly one ends `(recommended)`), and run `./zn block <R-id> <review-exhausted|design-gap|needs-decision|red-gate|quota|tripwire> --layer <issue>`. It files the note on `origin/main` with the `blocked` status, comments `BLOCKED: <reason>: <the question>` on the Layer's PR, and leaves the branches and PRs as they are. Under `./zn dispatch` the same two steps are all there is, except that you do not run `./zn done`: write `escalation.md` and run `./zn block <R-id> <reason> --layer <issue>`, and the dispatcher lands the layers below (c0252) and stops the chain at the blocked raft until the user runs `./zn resolve <R-id> <decision>`. After a tripwire (a `REPOSITORY CHANGED` stop, a refused fixture identity) run neither `./zn done --through` nor `./zn block`: write `escalation.md`, tell the person, who checks the checkout and runs `./zn block <R-id> tripwire`. Under `./zn dispatch`, a finding still open when no further review round may run is `review-exhausted`: copy the bullets verbatim under `## Open findings or error`, block, and after the resolve run `./zn rulings <id>` in your worktree (in guess mode, outside the dispatcher, each open bullet gets a `Guessed` line instead). You run `./zn resolve` only when the user's message in this conversation tells you to, quote that message in `--said`, and never resolve a block your own session filed.

## Final report format
```
R0010: <title>. <MERGED | BLOCKED>
PR: <url>
Merge: <merge commit sha> | not merged: <which condition failed>
Cleanup: done | <what was skipped and why> (if this only becomes known after the report is posted, add a follow-up PR comment)
Criteria: <n>/<n> Checked PASS (./zn done output), Judged: <rulings>
Observed (human, in Studio): <numbered steps from the issues' Observed sections>
Deviations: <issue: what and why> | none
Waiting for approval: <id> (<n> guesses; <changed parts>) | none
Emergent issues: <ids and one line each> | none
Follow-ups filed: <ids> | none
Spend: <raft spend.md totals>
Workstreams: <issue>: <stream review verdict> | sequential   (one line per issue; only when Phase 2B was used)
```

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A lesson goes to the step that erred: the skill whose instructions the author was following when the mistake was made, or the skill of an earlier step that should have prevented or caught it (that skill is `<the skill the lesson improves>` below). The harvest line names that step as `(erred <skill>[, upstream <skill>])` before its colon (zz-rules skill, Items), and every kind of review and correction is harvested: a finding of a design, code, stream or focused review as an entry of the item's `harvest.md`, and a programme review, a correction by the user or a failed step as a `- note` entry.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened> (erred <skill>): <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --filed-by "<source>" --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). Pass `--filed-by "<source>"` (quoted: it holds a space for a review finding; `review:<item id>/<review file> F<n>`, `lesson:<skill>/<slug>` or `agent:<item id>/<slug>`) only for a lesson that comes from a finding of yours; one from the user's correction carries their words, so capture it with the z-ticket skill without the flag. The prep that takes the issue writes the file.
