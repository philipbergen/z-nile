---
title: A trace cell cites the proof of its own claim, not whatever --check accepts
when: build
tags: [trace, final-review, citations]
check: For each test cell of the trace, does the cited line itself name the case or the `check "ACn:` of the row's own claim, and would `./zn trace --check` still pass if that line belonged to another claim? And is a row that is no claim (a lead-in, a "None." section) filled with its doc line and a note saying so, not an invented proof?
---
`./zn trace --check` matches a test cell loosely: a case is found only when its `it("...")` title sits whole on the cited line (or by a `:: <name>` cut at the first comma or semicolon and applied to every reference in the cell), and a `check.sh` reference passes on any command line. So the strongest case for a claim can be uncitable while a line of another criterion passes, and the skeleton derives rows that are no claim (a Problem lead-in ending in a colon, the "None." under Judged and Observed).

**Why:** R0121 final review 001 F1 and F2: the reviewer first cited AC5's `check.sh` line for another row and `--check` accepted it; the cases pinning a bad prefix, bad revives and "revives never rank" open `it(` on their own line with commas in the name, so neighbouring green cases of the same specs were cited instead. The tooling fix was withdrawn by the user on 2026-11-16 (c0301, c0347; zz-review/withdrawn-findings-stay-withdrawn), so the filler of the trace is the author's and reviewer's to keep honest.

**How to apply:** cite a case whose title is whole on the cited line, or `:: <name>` alone in its cell; cite a `check.sh` line only as the row's own `check "ACn: ...` line; fill a non-claim row with its doc line and a note ("not a criterion; the tool derives a claim from it"); and say in the review which proofs the matcher could not cite.

**Note (R0126, final review 001):** a chore that narrows another item's promoted specs has no spec of its own to cite: `./zn trace --check` (`isSpecForIssue` in `z-nile/engine/trace.luau`) refuses a spec under another item's `tests/acceptance/<id>/` as a test cell, and counts those specs as tests, so `## Source files` stays empty. Cite the chore's own `check "ACn:` line that pins or runs the spec, name the narrowed case in the cell's prose, and say below the Source files table which promoted specs the stack changed and the claims each serves. Check: does a test cell cite a spec outside this ticket's own acceptance folder?

**Note (R0117 final review 001, the reviewer's candidate):** the check reads the first `::` in a test cell as the case name for every spec reference in that cell, and cuts the name at the first comma or semicolon. Portal's case names are full of commas and many span lines, so cite a spec line whose `it("…"` name sits on that line and write no `::`, or one `::` naming a case without commas alone beside `check.sh` references; never put `name:digits` text in a note, which the check reads as a file reference.

**Note (R0119 final review 001, the reviewer's candidate):** a chore's own acceptance spec that only reads other specs as text (c0380's `narrowed.spec`) is missing from its ticket's `results.txt`, because its watch names only what the spec requires, so `./zn trace --check` refuses its cases as test cells even though they are the ticket's own. Cite the chore's `check "ACn:` line that runs the spec and name the cases in the cell's prose. A design's Test plan that promises such a spec's cases as the trace's test cell promises a citation the checker will refuse. Check: is the spec a test cell cites listed in that ticket's `results.txt`, and if not, does the cell cite the `check "ACn:` line that runs it?
