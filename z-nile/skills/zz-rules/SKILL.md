# Tracker

All work is tracked in project roots, which are committed. `z-nile/projects.toml` lists the projects, each with the root that holds its issues and rafts: pickman's is `pickman/.tracker/` and z-nile's, the tooling's, is `z-nile/.tracker/`. The arcade's projects keep theirs the same way, `<name>/.tracker/` with the home `<name>/` (c0183: `arcade`, `portal`, `snake`, `invaders`, `asteroids`). A directory it does not list is not a project. Each project also has a home, the folder that holds its root and in which its `check.sh` files and specs run: `pickman/` for pickman (its `src/`, `tests/`, `scripts/` and Rojo projects are there) and `z-nile/` for z-nile (the engine, the gate, and the tooling's specs and harness in `z-nile/tests/`); the repository root belongs to no project (c0120). `./zn check` runs a pickman item's `check.sh` from `pickman/` and a z-nile item's from `z-nile/`, so the paths it names are its project's, and `./zn find` and `members` print paths from the folder you run them in. The folder you run `./zn` in also gives the project (`pickman/` gives pickman, `z-nile/` z-nile; `--project` overrides it). `tracker/` is a retired root (c0120): it holds only the old counter's tombstone, and `./zn audit` and the gate fail if anything else appears there. One counter numbers every project, so a bare id is unique across the repository, and every command that takes an id (`find`, `members`, `status`, `capture`, …) searches every root. The engine, its templates (`z-nile/templates/`), the counter and the compaction map live in `z-nile/` and belong to no project. The command is `./zn` at the repository root (`scripts/tracker.sh` forwards to it until every raft whose sequestered `check.sh` names that path is done). The only way to change tracker state is `./zn`. Don't move tracker directories by hand. Inside a raft, commit with `./zn commit`; capture, prep and doc-only worktrees, which have no active raft, use plain `git add` and `git commit` (see Landing a change). Every change is made in a worktree (see Worktrees).

## Items
| kind | ID | example |
|---|---|---|
| feature issue | `f` + 4 digits | `f0010` |
| defect issue | `d` + 4 digits | `d0020` |
| chore issue | `c` + 4 digits | `c0030` (includes every CI/test/tooling fix, even bugs; see z-ticket) |
| raft (epic) | `R` + 4 digits | `R0010` |

- **Numbering**: `f`, `d` and `c` share one number space; rafts have their own. `z-nile/next` holds the next number of each (`issue <n> <phrase>`, `raft <n> <phrase>`). The first publish after c0114 lands moves the counter there from the old counter file, in its own lease push, and leaves a tombstone in the old file, so an engine from before c0114 refuses to number; until then the old file is the counter. `new`, `new raft`, an emergent issue and `renumber` take the counter, counting by one, and push it raised, with a fresh phrase, in a lease push to `origin/main` (a lost race is retried on the new `main`); a number already in use is always passed. Offline (`PICKMAN_PUBLISH=0`) the local counter is read but never written. A tree without `z-nile/next` (a fixture) keeps the old rule: the next multiple of 10 above the highest number in use.
- **Compaction**: `./zn compact` renumbers every item from 0001, in a fresh worktree cut from `origin/main`, as one local commit to land by pull request; it refuses while another branch changes a project root (`pickman/.tracker/`, `z-nile/.tracker/`) or a project's promoted specs (`z-nile/tests/acceptance/`, `pickman/tests/acceptance/`) (`--force` runs anyway; `./zn busy` lists what holds them: with no paths, exactly the branches `./zn compact` refuses on), and writes the old-to-new map to `z-nile/compaction.txt`. Merge the compaction PR only while `origin/main` still equals the sha in `z-nile/compaction.txt`'s header; if `main` has moved, reset to `origin/main` and compact again (it is deterministic). On each branch that was in flight, run `./zn remap` before merging `origin/main`: it takes the new ids and then merges `origin/main` itself. Never merge it plainly first: nothing detects the mixed tree afterwards. A branch that did merge plainly undoes that merge with `git reset --hard ORIG_HEAD`, then remaps. Any other tree from before the compaction refuses to publish until it merges `origin/main`.
- **Duplicate ids**: `./zn audit` reports every problem in the tree (the gate runs it too). One id in two lifecycle folders blocks most commands: `./zn renumber <directory>` renumbers that copy only: renumber the copy not in `done/` (normally the fresh backlog stub, for example `renumber tracker/issues/c0510`), because a done copy's specs are promoted under its id; a `done/` directory is refused.
- **Legacy layout**: documents used to be named with their slug. `./zn migrate` renames any such document to `<ID>.md` and adds `slug:` to its frontmatter; run it, and commit, after merging a `main` that has the new layout.
- **Conflicts**: two branches that pick the same number now conflict in git, because both write `<ID>/<ID>.md`. Only a `CONFLICT (add/add)` on that path means two items share a number: run `git merge --abort`, `git fetch origin main`, then `./zn renumber <ID>` on your own branch, which gives the item the number one above the highest of its kind in **both** your tree and `origin/main` (`f`, `d` and `c` share one space, rafts have their own), and merge again. `renumber <old> <new>` sets a number by hand. `renumber` rewrites every reference. A content conflict on a document is two edits to one item: resolve it like any merge, and never renumber. A branch from before c0114 that added a file inside a tooling item's folder gets `CONFLICT (file location)` when it merges `origin/main`: git suggests the folder's new place under `z-nile/.tracker/`; accept it (`git add` that path) and never move the folder back. The same holds for a branch from before c0120 that added a file in a pickman item's folder, under `src/` or under a game test folder: accept git's place under `pickman/`, never the old one (the gate's old-roots check fails on it). A branch from before c0115 that added a file inside an old skill folder (`.claude/skills/<old>/`) gets the same conflict: accept git's place under `z-nile/skills/<new>/` or `pickman/skills/<new>/`, never a real folder in `.claude/skills/` (the gate's `./zn skills --check` fails on it).
- **References**: always refer to items by bare ID, never by path. Use `./zn find <id>` to get the current directory.
- **Projects**: the directory gives the project unless `--project` names one. `new issue`, `new raft` and `list` work in `--project <name>`'s project, else in the one whose folder holds the directory you run `./zn` from (`z-nile/` and below is z-nile's, `pickman/` and below pickman's, c0120). At the checkout's root, or in a folder no project holds, the commands that create an item, and so must choose its project (`new issue`, `new raft`), refuse and ask for `--project`; read-only ones read every project there (`list` shows them all), because reading needs no project. There, the work of a game, the portal or the arcade library passes its project (`--project pickman`, `--project snake`, `--project portal`, `--project arcade`, …: a name in `z-nile/projects.toml`) and tooling (the tracker, the gate, the guards, the skills) `--project z-nile`. An emergent issue goes beside its raft, which gives its project. A raft lives in its members' project and never spans two. R0001, finished before c0114, is the one exception: its members stayed with their projects (c0001 in z-nile's, c0002 in pickman's), and `members R0001` still lists both. `.tracker/` is a hidden folder: `rg` and some search tools skip it unless told (`rg --hidden`), so find items with `./zn find` or `git grep`.

Each item is a directory named by its ID:
```
<ID>/<ID>.md            the document (frontmatter incl. slug + sections from z-nile/templates)
<ID>/check.sh           acceptance criteria as executable checks (see the zz-test skill)
<ID>/acceptance/        sequestered acceptance specs (issues); `done` moves them to tests/acceptance/<ID>/
<ID>/experiments/       spikes for unknowns (issues)
<ID>/design-review-NNN.md, design-refute-NNN.md   from z-design, on the issue; z-raft's coherence review, on the raft
<ID>/review-NNN.md, refute-NNN.md                 code review, on the raft
<ID>/final-review-NNN.md, final-refute-NNN.md     final review on the finished stack, on the raft
<ID>/trace.md                                     the final review's idea=design=test=code trace table, on the raft
<ID>/results.txt                                  green specs and case names recorded by `./zn finish`, on the issue
<ID>/spend.md           written by `./zn commit` and `./zn spend`; never edit by hand
<ID>/provenance.md      who decided what: append-only rows, written by `./zn provenance record` and the commands that make an event (c0263); never edit a row
```

- **Skills**: z-nile's skills live in `z-nile/skills/<name>/SKILL.md`, a project's own in `<project>/skills/<name>/SKILL.md` (its name in `z-nile/projects.toml`: `pickman/skills/`). The harnesses find them through `.claude/skills/<name>`, a committed relative link to the real folder (`../../z-nile/skills/<name>`), which `./zn skills` writes and `./zn skills --check` (in the gate) checks: one link per skill, nothing else in `.claude/skills/`. Names are unique across the repository and equal the `name:` in the skill's frontmatter. A project's skill may name one other skill in `extends:`, the skill whose rules it defers to (`snake-arch` extends `pickman-arch`): a raft's prompt inlines it after the project's own skills, and `./zn skills` refuses a name that is no other skill. The `z-` (pipeline) and `zz-` (called from inside a step) prefixes are z-nile's alone: a project's skill is named `<project>-…`, and `./zn skills` refuses any other. Git can't add a path through a link, so every tool, spec, Touched path and edit uses the real folder, never `.claude/skills/<name>/…`.
- **Lessons**: `<skills folder>/<skill>/lessons/<slug>.md` (the skill's real folder, `z-nile/skills/<skill>/` or `<project>/skills/<skill>/`), id `<skill>/<slug>`. Frontmatter `title`, `when` (`design`, `build` or `both`), `tags: [a, b]`, `check` (one question ending in `?`) and optional `from` (only for a source with no item folder to hold a note; each key once); the body says the rule, why, and how to apply it. **`harvest.md`**, in each reviewed item's folder, has one entry per review finding: `- design-review-001 F2: <lesson id>, <lesson id>` or `- review-001 F3: one-off: <reason>`, plus `- note <text>: <lesson ids>` for a source that is not a review finding (a subagent's candidate, a correction by the user, a failed step). A note covers no finding. A lesson's sources are the entries naming it, each once. See `./zn lessons`.

## Worktrees
Every change is made in its own git worktree under `<repo>/.worktree/` and lands by pull request (except tracker state, see Sync and claim). The main checkout stays on `main` and is never edited. Every job runs in a worktree under `<repo>/.worktree/`, never outside the repo directory: no sibling directory next to the repo, and not the harness's own `.claude/worktrees/`. The one exception is Merging's final check and `lune run scripts/cicd` in that clone, a clone outside the repo that is not a worktree.

1. **The main checkout is read-only.** The complete list of commands that may run there:
   - `git fetch`, `./zn sync` (a fast-forward there, which also rebuilds the board), and read-only inspection (`git status|log|diff|show|worktree list`);
   - `git worktree add|remove|prune` and `git branch -D <merged branch>`;
   - `z-nile/setup.sh`, once, when bootstrapping a new machine (SETUP.md);
   - `run` and `reap`, which touch no repository (`./zn run` runs a bounded command, only a command that is itself allowed there; `./zn reap` stops this user's leaked processes);
   - `./zn ready` and `stop`, which publish to `origin/main`, fast-forward it there; `ready` writes the ignored `<root>/rafts/active/<R-id>/prompt.md` beside the raft and `stop` removes it;
   - `./zn dispatch` (Dispatch, below), which runs every step in a worktree of its own and writes only the ignored run state in `.cache/dispatch/`;
   - the read-only tracker commands `list`, `audit`, `find`, `members`, `busy`, `metrics`, `workstreams`, `status` (without a target status), `prompt <R-id>` (it reads a readied raft's prompt and writes nothing), `lessons`, `raft-plan` (without `--apply`), `skills --check` and `capture <id>` (they only read), and `who <id>` (it reads the history and writes nothing), and the worktree commands `worktree` and `worktree-prune`. (`./zn check` runs an item's checks and, for a raft, the full gate, so it runs in a worktree.)
   The tracker enforces part of this: `new`, `renumber`, `migrate`, `start`, `status <id> <to>`, `fold`, `unfold`, `recombine`, `release`, `raft-plan --apply`, `compact`, `remap` and `skills` (without `--check`) refuse to run in the main checkout of a repo that has an `origin`; `ready` and `stop` refuse to run anywhere else.
2. **Every change starts with a worktree**: `cd "$(./zn worktree <target>)"`.

   | work | target | path and branch |
   |---|---|---|
   | executing a raft | `R0010` | `.worktree/R0010`, detached until `./zn start`, then on its layer |
   | capturing an issue (z-ticket) | `capture-<slug>` | `.worktree/capture-<slug>`, the same branch name; lands with `./zn land`, no PR |
   | designing an issue (z-design) | `prep-<slug>`, the issue's slug | `.worktree/prep-<slug>`, the same branch name |
   | rafting (z-raft) | `raft-<slug>` | `.worktree/raft-<slug>`, the same branch name |
   | the dispatcher's own spend rows | `zn-dispatch` | `.worktree/zn-dispatch`, the same branch name; `./zn spend` commits there and pushes nothing |
   | a skill, doc or config edit | `<area>-<slug>`, for example `skills-worktree-rule` | `.worktree/<area>-<slug>`, the same branch name |

   A change to skills, docs or tooling is still tracked work: it has an issue and normally a raft, and is executed in the raft's worktree like any other. Names are lowercase, so a prep worktree is named by the issue's slug and a rafting worktree by a short slug of its own: a new raft's id isn't known until `new raft` has run inside it. Use `./zn worktree`, not the harness's own worktree feature: its directories aren't under `.worktree/`, and `worktree-prune` never sees them (it warns about any worktree outside `.worktree/` and leaves it). A worktree inside the repo also sees the main checkout's `.luaurc` as a parent configuration, so an alias a branch renames can still resolve locally. The final check for a pull request that changes a game is `z-nile/check.sh --full` in a clone of the exact head whose parent directories are not a checkout of this repo. A pull request that changes only tooling (no path under a game home outside that home's `.tracker/`) is gated by `z-nile/check.sh --affected` on the branch.
3. **Starting execution**: the human starts a Claude session in the main checkout (which stays on `main`) and runs `/z-run <R-id>`. The skill reads the raft's prompt (`./zn prompt <R-id> --path`) and `cd`s into `$(./zn worktree <R-id>)`. The hooks follow the session's current directory, so from then on they act in the worktree; subagents get absolute worktree paths, because a subagent's shell resets its working directory on every call. Another agent gets the same text from `./zn prompt <R-id>`.
4. **Prep and rafting merge before execution.** An issue's design PR merges before z-raft groups it, and the rafting PR merges (Landing a change) before `z-ready` runs, so the raft's own worktree branches from an `origin/main` that has the prepped items in their raft. `z-ready` never creates a raft: a raftless issue goes to z-raft.

## Lifecycle: the directory and the status
- **Paths**: `<root>/rafts/retired/<ID>` is a raft `recombine` retired (its review history, never an item to work); `<root>/{issues,rafts}/<ID>` is backlog (`<root>` is the item's project root, `<name>/.tracker` for a project of `z-nile/projects.toml`, such as `pickman/.tracker` or `z-nile/.tracker`), `…/active/<ID>` is in progress, and `…/done/<ID>` is finished. On `main`, `active/` holds the rafts that `ready` has handed out (and their issues), not only the branch you are on: the current raft is the active raft whose branch is the current branch.
- **The design field**: frontmatter `design:` moves `draft` → `reviewed` → `ready`; `z-design` sets an issue's and `z-raft` a raft's.
- **Everything worked is a raft.** A raft has exactly one type (feature, defect or chore), and every member issue must match it. z-design stops at a prepared issue with no raft; z-raft makes every raft, in its rafting worktree, and gives `single: true` only to a raft of one `solo` or over-cap issue (nothing is folded into it); `./zn ready <issue>` refuses a raftless issue, and `prompt` takes only a raft id.
- **One layer per ticket.** A raft is a stack. `R0010/1/c0010` is position 1, issue c0010, based on main; the next layer is based on the one below. Each layer is one branch, one commit (`./zn finish <issue>`) and one pull request. `./zn restack <R-id>` rebases the layers above a change. `./zn done` lands the stack with one `--no-ff` merge.

| step | command | effect |
|---|---|---|
| approve | `./zn approve <issue-id> [--check]` | in the worktree where the design is, with a terminal on stdin, and not while `ZN_DISPATCH` is set. Records a hash of the design sections (Problem, Solution, Design, Acceptance criteria, Test plan), the acceptance specs and `check.sh` in the issue's `approval.md`, and keeps earlier rows. `--check` says whether that hash still holds and which part changed. |
| ready | `./zn ready <R-id\|issue-id>` | main checkout only, on a clean `main`, with an origin (z-ready skill). Checks the raft and every member are `design: ready` with a `check.sh` that has a check, and that every `depends_on` outside the raft is `done`. Refuses a member with no approval, or whose contract hash no longer matches (`./zn approve <id>`); an item prepared before approval is told to take that one-time step. Claims the raft, publishes one tracker-only commit that moves it and its members to `active/` on `origin/main` (every `check.sh` item path rewritten), pulls the main checkout, and writes the ignored `<root>/rafts/active/<R-id>/prompt.md` (it inlines the project's `<root>/architecture.md`, pickman's map; a project without one gets a line saying so). On an active raft it regenerates the prompt and makes no commit. |
| stop | `./zn stop <R-id>` | main checkout only, on a clean `main`, with an origin (z-stop skill). It gives back exactly the issues that carry the raft's own claim stamp (`ready` and `start` stamp the raft and every issue they claim with one `active-…` value); an issue only listed in `issues:`, or one filed naming the raft after the claim, is never touched (the latter is named in a warning). Every claim stamp is new on `origin/main` (redrawn until no item carries it), and a raft with no `active-…` stamp is refused, to be given back by hand. Gives back a readied raft: publishes one tracker-only commit that moves it and its members from `active/` back to the backlog, stamped `prepared-…` (every `check.sh` item path rewritten back), removes `prompt.md`, pulls the main checkout, and names the raft's branch and PR, which it leaves as they are. A raft claimed by the legacy `start` (backlog, status `active`) gets a status-only publish and no move. A member in `done/` refuses. |
| start | `./zn start R0010` | clean tree required. Opens the next layer (`R0010/1/c0010`: an empty `tracker: start` commit, a push, and a **draft** PR based on the layer below, or on main). The next layer waits until `./zn finish` has made the one below a single commit. A readied raft claims and moves nothing. A backlog raft (legacy) still claims and moves to `active/` on that layer branch: members must be `design: ready`, and every `depends_on` outside the raft must be `done` on `origin/main`. If it refuses, merge `origin/main` and retry, never edit `depends_on` to get past it: stop and report. Do this first, so the claim is visible to another machine. |
| worktree | `./zn worktree <R-id\|name>` | creates or reuses `<repo>/.worktree/<R-id\|name>` and prints its path. A raft's worktree is `.worktree/R0010`, detached at a freshly fetched `origin/main` until a layer exists, then on the highest layer. It does not create `R0010-<slug>`. Any other is `.worktree/<name>` on a branch of that name. Refuses a done raft, and a branch that is checked out elsewhere. For a named worktree, `--from <ref>` cuts the new branch from that ref instead of `origin/main`. |
| workstreams | `./zn workstreams <R-id>` | read-only plan. It is not how a raft is built: each issue is a layer, and `./zn finish` makes that layer one commit. Issues in waves from `depends_on` and overlapping Touched modules, and a last line `parallel: yes (wave k: …)` or `parallel: no`. `parallel: yes` means another machine can take another layer (`./zn stack`) |
| board | `./zn board [--out PATH] [-O]` | writes the whole tracker as one self-contained HTML page, `.cache/board.html` by default (gitignored; the main checkout's copy is rebuilt by `./zn board` and by `./zn sync` there (a tracker push does not rebuild it), so reload the tab after a sync; elsewhere regenerate to refresh). One tab per project in `z-nile/projects.toml`, on the left, the first selected (c0118); every view shows the selected project only. It opens on Board: the project's issues as cards in six columns, ticket (`new`), design (`preparing`), raft (`prepared`), ready (readied, in `active/`, and its raft's branch has no commit since that ready), run (its raft's branch `<R-id>-…`, local or on origin, has a commit after its latest ready) or its highest layer (`R0010/1/c0010`), which wins over that slug and done (in `done/`), each raft a band behind its members. Done cards stay for the chosen window, 24 hours by default, from 1 hour to 30 days, counted back from the page's as-of time (HEAD's commit time). A click on a card shows its column, model, spend, dispatcher state, branch and worktree, and its document; PR and checks are live only on the served board (c0121). Under the columns, two charts with their own range (90 days by default, 30 days, 1 year or all history): review rounds by week (the `design-review-NNN.md` and `review-NNN.md` of each raft that landed that week, its members' and those of rafts retired into it, each file once) and review tokens by week and model (spend rows of `design-review` and `code-review`; a row with no model is the unrecorded series). Views Rafts and Issues, each split into Ready, Not ready and Done (a backlog raft is Ready only when its design is ready and its effective status is prepared; a readied raft is Ready; blocked rafts stay listed). A raft's shown type comes from its issues (one type, or mix). A row with a next command has a copy button. Cursor keys, `/` then an id to jump to it, and each item's document and dependencies rendered with the vendored marked. Then it opens the page in the default browser unless `-O` is given (`-O` only writes it, as the specs do; `--open`, the old opt-in, is still accepted and is the default). The board is the local page; GitHub Actions does not build it. Stats (a Stats button, not a third view) charts opened, closed, net, minutes and lines added and removed for the month, quarter and year, by all, feature, defect and chore, plus the defect and chore ratios and mean days in state; Table shows the same numbers with units. Without history (a shallow clone or no git) closed counts and time in state are omitted. |
| busy | `./zn busy [<path>...]` | read-only. Lists what holds the paths: every raft active on `origin/main` (but the current branch's own), every branch, local or on origin, that changes them since it left `origin/main` (compaction's busy-branch check), and every other worktree with uncommitted changes under them; exits 1 when anything does. Without paths it guards what compaction guards (every project root and promoted-spec folder). A move of the tree (c0120: `./zn busy tracker src tests`; c0115: `./zn busy .claude/skills z-nile/skills pickman/skills`) is readied only when it prints nothing. Each move's freeze (`FREEZES` in `z-nile/engine/main.luau`) is on only while every path given lies inside the move's own and `origin/main` still holds the move's mark; then the move's own branches, the branches listed as stacked on them, the ones the user approved by name, any branch holding the move commit, the move's own active raft, and worktrees on those branches, are named on stderr (`ignored for c0115's freeze: ...`) and not counted; without paths, with a path outside the move's, or once the move lands, nothing is exempt |
| capture | `./zn capture <id>` | read-only. Prints `capture <sha> <path> <subject>` and then the item's document as captured: the newest commit on `origin/main` (`HEAD` without one) whose subject is `tracker: new` with the item's id in its leading id list (`tracker: new raft …` and `tracker: scope …` are not captures), or else the document's first add. It reads the item's backlog, `active/` and `done/` folders, under the item's current id only: no id change (a compaction or a `renumber`) is followed. The header line says when the answer is weaker: it ends `(no capture commit: first add)` when no commit is a capture (a renumbered item, or one made before captures had that subject), `(ambiguous: two items held this id at once)` when the id had two copies, and `(history before <sha> not followed: it changed tracker/compaction.txt)` when the item's life starts at a commit that changed the compaction map and its document. A legacy slug-named document counts. Exit 1 for an id with no history |
| who | `./zn who <id>` | read-only, in the main checkout too. Prints the item's history, one line per entry, oldest first: `<when>  <event>  <actor>  <detail>  (git \| record)`. What git knows is read from the history of the item's current life (the same cut as `capture`) and never stored: the `idea` (the author of the capture commit, `human:<name> (from git)`, or `(from git, first add)` when no commit names the item), each status change as `status:<status>` with the author of its `tracker: <id> <status>` commit (a `Co-Authored-By` trailer whose email is no commit author's makes the actor `agent:<model> effort unknown (from git)`), a `tracker: <id> new` commit as `unblocked` (once per commit, and not at all when the same commit appended a record row), `rafted` (who made `raft:` the value it has now and kept it, from `raft:` after each commit of the document), and for a done item `delivered` (the commit that added it under `done/`, its agent trailer read) and `merged` (that commit's author). The record's rows join them, a `rafted` or `delivered` row naming the item's raft taking the place of the git entry, and the worker (host/CLI/model, from the newest `deliver` spend row with a model, else the newest `build` one) joins `delivered` as `worker=`. Writes nothing; an old item needs no record. Exit 1 for an id with no history or a record that does not parse |

## Landing a change
One procedure for every change: a raft, a capture, a prep or an edit.
0. **Sync first.** `./zn sync` in the worktree (a fetch and a merge of `origin/main`).
   - If `main` brought the new document layout, run `./zn migrate` and commit.
   - A `CONFLICT (add/add)` on a tracker document means two items picked the same number: see Conflicts.
   - Then run `./zn list` (it fails on a duplicate id and warns when one number is shared by two prefixes; renumber yours if you can) and `z-nile/check.sh --affected`.
1. **Commit in the worktree**: `./zn commit` inside a raft; plain `git add` and `git commit` elsewhere.
2. **Push and open the PR**: `git push -u origin <branch>`. A raft's PR is opened as a draft by `start`; any other PR is opened ready with `gh pr create`. A capture lands with `./zn land` instead (no PR): it merges `origin/main`, runs the static stages (`z-nile/check.sh --static`) for the projects the capture changed, checks that only the sections, title and `depends_on` of draft backlog issue documents changed, refuses an issue in that diff whose approval no longer matches its contract, pushes one commit to `main` (a lost push retries the push, not the gate) and prints the worktree-removal command. A capture's spend row is committed on the capture branch before `land`, so it is in the tree that push carries.
3. **Merge** a PR only when the conditions under Merging hold. A raft is landed by `./zn done` (one `--no-ff` merge, not a squash) once its review is resolved. Any other PR is merged with `gh pr merge --squash`. A prep the user didn't ask for is not merged without asking, and a capture they didn't ask for is not landed without asking. Under the dispatcher, a step neither asks nor merges: once its PR is open and its spend recorded it ends, and the dispatcher passes the prep and rafting gates itself (the user started it, c0117 G4). (A capture has no PR: `./zn land` in step 2 is its landing.)
4. **After the merge, one chained command, run last**: `"<root>/zn" sync; git -C <root> worktree remove <path> && git -C <root> branch -D <branch>; git -C <root> worktree prune`. `<root>` is the first path in `git worktree list`; `sync` fast-forwards the root and rebuilds its board. When the session works inside the worktree (with z-run it started in the main checkout and `cd`'d into the worktree), removing it removes the session's own directory, so every command after it must use `-C <root>` or absolute paths, and nothing should run after this command: post the final report first. The alternative is to leave removal to `./zn worktree-prune`, run later from the main checkout.

## Merging
The agent that delivered the change merges its own PR once the evidence is in. Don't wait for a human. Merge only when **all** of these hold:
1. **For a raft**, `./zn done` succeeded: the one code review is answered and the raft's `check.sh` passed. The PR is ready, not draft, and has no unresolved `BLOCKED:` comment. The review is already on the PR as a comment (zz-execute Phase 4). A refuted finding, a high finding that was not fixed, or a failed Judged criterion stays open until the raft document's `## Open to the human` records `Ruled (user, YYYY-MM-DD):` for it; `./zn done` refuses before that. A medium or low finding that is fixed, or deferred to a backlog issue, does not block (zz-execute Phase 4 step 6).
2. The gate depends on what the pull request changes. A pull request that changes only tooling (no path under a game home — `pickman`, `arcade`, `portal`, `snake`, `invaders`, `asteroids` — outside `<home>/.tracker/`) is gated by `z-nile/check.sh --affected` on the branch: no clean clone and no Roblox publish. A pull request that changes a game keeps the clean-clone full gate, run by you, outside this repo. `dir=$(mktemp -d)` only when that directory's parent directories are not a checkout of this repo; if `$TMPDIR` is inside this checkout, stop. Then `git clone --no-hardlinks --no-checkout` of this checkout into `$dir`, `git remote remove origin`, and `git checkout --detach` the exact head. Spawn `z-nile/check.sh --full` there with `PICKMAN_FENCE_REAL_GIT` set to the real repository's git directory appended to whatever the process inherited (`${PICKMAN_FENCE_REAL_GIT:+$PICKMAN_FENCE_REAL_GIT:}` plus `git rev-parse --path-format=absolute --git-common-dir` of this checkout). That is the local full gate. That is the verification. A merge does not read GitHub Actions. `./zn done`'s gate in the raft worktree is the raft's own gate and is not this check. A red full gate here is BLOCKED: zz-execute Phase 6 step 1 says what to post and file.
3. When the pull request changes a game: In `$dir/pickman`, on the detached head from step 2 (`git checkout --detach`), `lune run scripts/cicd` passes. Run it as `../zn run --time 1800 -- lune run scripts/cicd` from `$dir/pickman`, where the clone's `zn` is `../zn` (a bare `lune run` of it is refused by the PreToolUse hook: it runs the minutes-long runtime suites). It reads `~/.config/pickman/cicd.toml`, reserves the CICD places, publishes them, and runs both runtime suites. A missing file, a lease held by someone else, a publish failure, or a runtime failure stops the merge. This command is not part of `z-nile/check.sh --full`. A tooling pull request does not run it.
4. `gh pr view <pr> --json mergeable,mergeStateStatus` shows `MERGEABLE` and `CLEAN` (`UNKNOWN` is GitHub still computing it right after `done`: re-poll for up to a minute before deciding); any other state (`BEHIND`, `BLOCKED`, `UNSTABLE`, `DIRTY`) is not mergeable. `done` is preceded by a merge of `origin/main` (zz-execute Phase 5), so this should hold. If `main` moved since, and the merge is a clean one, merge `origin/main` in with `./zn sync` (`./zn commit` needs an active raft, and `done` has moved it). A re-run is required only when `git diff --name-only <the main you gated> <the main you merged>` names a path that selects a spec for this pull request (`lune run z-nile/affected --` those paths). Commits that touch only tracker documents (a project root, or `z-nile/next`) select none and need no re-run. When a re-run is required, a tooling pull request reruns `z-nile/check.sh --affected` on the branch, and a game pull request must rerun `z-nile/check.sh --full` in that clone and `lune run scripts/cicd` (wrapped as in step 3); then push, and repeat this step. If it conflicts, or it needs anything beyond renumbering colliding IDs (`renumber` per Conflicts), post `BLOCKED:` and stop: a finished PR gets no unreviewed code changes.
5. The human hasn't said to hold.

Then `gh pr merge <pr> --squash --subject "<raft>: <title> (#<pr>)" --body $'<summary>\n\n<the Co-Authored-By line from your commit instructions>'` (the `$'...'` form makes the newlines real, so the trailer is a trailer). Get the merge sha with `gh pr view <pr> --json mergeCommit -q .mergeCommit.oid`. Then follow Landing a change, step 4. `main` may have no branch protection (R0063 removed the `gate` check), so these conditions are the only gate: you enforce them. The ruleset c0117 §8 describes (a pull request required, updates restricted to the bypass list, the user the only bypass) is the user's to add, and until then the server stops nothing. The conditions are still yours to check, because your credentials are the admin's; a dispatched agent's are not (Dispatch, the agent credential). Never use `--admin`, and never merge on a red or missing gate for what the pull request changes, a red or missing `lune run scripts/cicd` when the pull request changes a game, an unresolved review, or a stop condition. If any condition can't be met, leave the PR as it is, post a `BLOCKED:` comment saying which, and stop.

Observed criteria (human Studio playtests) do not block the merge. Put them in the final report and PR comment, and file any failure the human finds later as a defect issue.

## The PR is the visible record
The draft PR opened by `start` stays the live log of the raft. Every `./zn commit` pushes. In addition, comment on the PR (`gh pr comment`) when: a review starts (with the sha), a review file lands (verdict and findings by severity), a review is answered (the refute lines), an issue finishes, and on any `BLOCKED:` stop. Never sit on unpushed work, and never leave review files uncommitted. See zz-execute Phase 4.

## Provenance
`provenance.md` (in an issue's or a raft's folder) is the one record of what git cannot tell: a header, the table header and one row per event, `| when | event | actor | detail |`, no row numbers, appended and never edited (`./zn audit` checks it; the file is exactly that grammar and a stray line is an error). The events are `approved`, `unblocked`, `confirmed`, `ranked`, `rafted` and `delivered`. `./zn provenance record <id> unblocked|confirmed|ranked [--actor A] [--detail k=v]` publishes `unblocked`, `confirmed` and `ranked` for a backlog issue or raft (the tickets that make those events call it), `unblocked` only for an active one and nothing for a done one; the other events are written by their own commands in a pull request. The **actor** is `human:<git name>` or `agent:<model> effort <level>`: `--actor`, else `ZN_ACTOR` (the dispatcher sets it), else `agent:unknown effort <CLAUDE_EFFORT>` when `CLAUDECODE`, `AI_AGENT`, `CURSOR_AGENT` (the `agent` CLI), `GROK_SESSION_ID` (the `grok` CLI) or `ZN_DISPATCH` (a dispatched step) is set and non-empty, else the git name. A published append is built from `origin/main`'s file. **Merging.** Two writers (a published row on `main`, a row in your PR) are united by the engine's own merges of `origin/main`: merge with `./zn sync` (the commands that merge for you do the same: `land`, `fold`, `recombine`, `new raft`, every command that publishes, which merges `origin/main` afterwards). `done` merges a stack that sits on main's tip (it refuses an unstacked layer), so that merge never conflicts. `./zn restack` rebases the layers instead of merging and stops on any conflict, a record included: resolve that one by hand in the layer, and let it unite the record, wherever the item's folder moved and however git paired the files: it settles every record either side changed, by the item's id, and puts it beside the item's document. It stops, with nothing left half merged, for a conflict in another file, a record that does not parse, a record both sides changed where a side edited, removed or reordered an old row, an item whose id changed on one side (a `renumber`, or a compaction: run `./zn remap`), a merge that crosses a compaction (a side numbers items differently from the merge base) when a record changed on the other side (run `./zn remap`; on the compaction's own branch, compact again on the current `origin/main`), and an uncommitted change to a record it would have to rewrite (commit or stash it); and it refuses while a merge of a branch `origin/main` does not contain, a cherry-pick, a revert or a rebase is in progress. When it stops on another file, merge by hand: `git merge origin/main`, resolve every conflict except `provenance.md`, `git add` the files, and run `./zn sync` again: it finishes that merge (a merge of `origin/main` or of an older commit of it), merges the newest `origin/main` on top, and unites the records (`origin/main`'s new rows first, then yours, every old row as it was). After a `renumber`, merge that item's record by hand under its new id. `remap` settles the records the same way; when it stops, merge by hand: its merge base is from before the compaction, so `./zn sync` would stop on the compaction, and `remap` refuses a second run. `./zn who <id>` prints an item's history from git and this record (the Commands table); the git entries are read at the time and never stored.

## Spend (best effort, automatic)
Rows are only ever appended. A row has nine columns: when, commit, +lines, -lines, minutes, attribution, phase and tokens, and a tenth, model, once any row of the file records the model that spent its tokens (`--model <id>` on `spend` and `commit`; a file with no such row keeps nine columns, and a row with no model leaves the cell empty). The phase is one of `capture`, `prep`, `design-review`, `build`, `code-review` or `deliver`.
- `capture`: `./zn spend <issue> --phase capture` on the capture branch before `./zn land`, so the row is in the tree land pushes. No lines. The command commits on the branch and pushes nothing.
- `prep`: `./zn spend <issue> --phase prep` once, when the issue's design PR is opened, before anyone readies it. Lines are that branch's own `check.sh`, `acceptance/` and `experiments/` files.
- `design-review`: `./zn spend <issue> --phase design-review` for the reviewer's run and again for the answering time; z-raft's coherence review is `./zn spend <R-id> --phase design-review` (shared among the members). No lines. Design reviews live where they ran (the issue's folder, or the raft's for the coherence review), and `./zn metrics` rolls an issue's up to its raft through `raft:`.
- `build`: `./zn commit` (the default phase). Lines are the staged diff.
- `code-review`: `./zn commit --phase code-review`, including the reviewer's tokens when the harness reports them. Lines are the staged diff.
- `deliver`: `./zn commit --phase deliver`, `done`'s own commit. `./zn spend <R-id> --phase deliver` commits its row on the current branch and pushes nothing, so record it before the merge if it should reach main with that pull request. Lines are the staged diff, or none after the merge.
- **Lines**: the staged diff, excluding every project root, except the `prep` phase above. On the `done` commit, the promoted `tests/acceptance/` specs are also excluded, because they're prep work. Later edits to them, for example a defect fix, do count.
- **Attribution**:
  1. `--issue` flags if given;
  2. otherwise the current focus;
  3. otherwise every issue in the raft.
  With several issues, each file's lines go to the issue whose **Touched modules** lists that path; files nobody claims are split evenly.
- **Minutes**:
  - Do not pass `--time` or `--tokens`. The tool measures the row. A typed number is ignored.
  - Otherwise the wall-clock time since the previous commit, capped at 45 minutes.
  - With several issues, minutes are split in proportion to lines added.
- **Commit often**, at least once per issue and once per review round. Smaller commits mean more accurate attribution.

## Dispatch
`./zn dispatch` runs the pipeline headless and unattended. The rules are `z-nile/engine/dispatch.luau`'s; the stacked model files are `models.luau`'s.
- **What the guards are** (the user's "Keep same user, accept detection", 2026-10-21). Unattended agents run as the user's own OS user. Every guard below (the wrapper, the broker, the tripwire, the watermark and the merge gates) detects honest mistakes and casual misbehaviour; none is a security boundary against a determined agent, which can read the user's credentials, rewrite the watermark or the repository's configuration between runs, or merge with the user's token. Known limits are said where each guard is.
- **Steps.** Model steps: `z-ticket`, `z-design`, `z-raft`, `z-run` and `zz-review` (modes `design`, `raft`, `code`, `stream`). Script steps, which the dispatcher runs itself and never starts a model for: `z-ready` (`./zn ready`), `z-stop` (`./zn stop`), `raft-plan --apply`, `recombine`, `fold`, `release`, `spend` and `zz-stats` (`./zn metrics`). `zz-rules`, `zz-arch`, `zz-test`, `zz-execute` (z-run's protocol) and a project's skills are read inside a step and are never one; any other name is an error.
- **`.models.toml`.** At the repository root, and optionally closer to the work (a project's home, an issue's folder). It stacks like `.gitignore`: a closer file replaces only the keys it sets (`order` whole, each `[dispatch]` setting, each field of each `[<skill>.<cli>]` table). `order` is the CLI priority, top first; the supported CLIs are `claude`, `grok` and `agent` (Cursor), and a table naming any other is an error. Each `[<skill>.<cli>]` has `model`, `rank`, `runtime` and `max_tokens` (and optionally `effort`), and an `agent` table also `max_calls` and `max_minutes`: Cursor's `agent` reports no running token count, so its step stops after `max_calls` model calls (distinct `model_call_id`s, and each turn that carries none) and the spend row takes the result's real total; a stream with three turns in a row and no `model_call_id`, or a line it doesn't know, stops as `cap-unknown` (fail closed); calls are not tokens, so the user tunes it, and an `agent` table without it is an error, never unlimited (the user's "Cap model calls, record real total"); a call count can miss calls, so the step also stops (`cap`) after `max_minutes` of wall time; the runtime belongs to its CLI: `claude-cli`, `grok-cli` and `cursor-cli` (the remote runtimes are c0142's). Nothing defaults: a skill no file names, a missing field, or no file at all is an error naming it. A step about one issue walks to that issue's folder; a step about a raft walks to each member's and takes, per CLI, the stronger spec whole (higher `rank`, then larger `max_tokens`), in the raft's own walk's order; z-ticket walks to the project's home. The `[dispatch]` settings (`auto_merge`, `stall_seconds`, `tool_seconds`) come from the item's own walk; an unset or unreadable `auto_merge` is none. Every file is read as committed on `main` (fetched once per run), never from the working tree: an uncommitted `.models.toml` on the walk is an error, so a new one takes effect once its PR has merged. A `.models.toml` is never tracker state: it changes only by a reviewed PR that a human merges (the broker and the gates refuse it; a step that wants an item-level spec asks in `questions.md`). `zz-review` follows the review rule: Opus (`claude-opus-…`) through `claude` and `agent`, any grok model (`grok-…`) at `effort = "xhigh"` through `grok`; any other is an error.
- **The agent credential** (the user's "Bot token, no bypass"). A model step runs with the agent's own GitHub token (a fine-grained token or a GitHub App's, read from `$ZN_AGENT_TOKEN_FILE`, else `~/.config/zn/agent-token`, else the keychain item `zn-dispatch-agent`); without one no CLI starts. It can push branches and open pull requests and can't merge, bypass `main`'s protection or write protection or rulesets. The step's `GH_TOKEN` and `GITHUB_TOKEN` are that token, gh reads an empty configuration folder of the step's own, and git's credential helpers answer with that token only. Not enforceable: the agent runs as the user, so a process that goes looking can still read the user's own credentials (the keychain, `~/.config/gh`); only a separate OS user would stop that, and the watermark and the server's protection are what catch its use.
- **Tracker state** has one definition (`z-nile/engine/trackerstate.luau`), which the wrapper, the broker, the tripwire, the watermark and the merge gates all use: git's raw diff with renames off (`diff-tree -r --raw --no-renames`), every path under a project root's folder (with the slash) or exactly `z-nile/next`, plain (ASCII, no empty, `.`, `..` or `.git` component), only regular files (no symlink, no submodule), no `.gitattributes`, `.gitmodules` or `.models.toml` in any case, no added path that differs only in case from another; and each item's sequestered files (its `check.sh` and `acceptance/`, in that exact case) judged per item: the same set, each unchanged or, when the item's folder moved, as `paths.rewrite` writes it for that move; only a new item adds them.
- **Tracker state from inside a step.** `./zn`'s pushes to `main` (`publish`, `land`) from inside a step go to the publish broker of the dispatcher that runs the step (a folder of that run's own, `ZN_PUBLISH_BROKER`, its requests bound by a run token): it pushes them with the user's credential, to origin's URL as the run pinned it at its start, only as a fast-forward of a freshly fetched `main`, never forced, and only when every commit is tracker state against its parent (as the watermark judges it). Nothing else in a step is meant to push to `main`.
- **Running a model step.** In the step's worktree (`prep-<slug>`, `raft-<id>`, the raft's own, `capture-zn-<n>`; a review in its author's), with a prompt that names the skill's file and pastes nothing. Search with `./zn lessons <terms>` when you are about to do something a lesson might cover. A supervisor starts the CLI in a process group of its own and holds a lifeline from the dispatcher: when the dispatcher dies, however it died, the group dies with it. The dispatcher kills the group when the running token count passes `max_tokens`, or for `agent` its call count passes `max_calls` or its wall time `max_minutes` (outcome `cap`), when the step prints nothing for `stall_seconds` (`tool_seconds` while a tool call runs) (`stalled`, or `quota` when the CLI's own last words were a wait for quota: a CLI never waits for quota, and the model's words never count), or on `./zn dispatch stop <id>` (`stopped`). A nested step (a review its author waits on as one shell command) writes a heartbeat in its parent's state folder while its CLI prints, and the parent counts a fresh beat as output; claude's maximum for one shell command (`BASH_MAX_TIMEOUT_MS`) is raised to two hours in its step's environment, its default left as it is, and the author passes a two-hour timeout on its review command alone. The nested runner beats once a second while it is alive and within its own limits, not only while its CLI prints, so a beat means "alive and within my limits". It moves down `order` only on quota, which only the CLI's own signals report (claude's rejected rate-limit event, an error result or line, stderr), and past a CLI that is not installed (skipped and named on stderr; none installed fails); any other failure stops, a CLI that is installed but signed out included. The count is input + cache writes + output, cache reads left out, for every CLI.
- **The watermark and the tripwire** (the user's "Persisted watermark", framed by "Keep same user, accept detection"). The dispatcher keeps the last commit of `main` it vetted where a well-behaved step never writes, and detects if it changes: `$ZN_WATERMARK_DIR`, else `$XDG_STATE_HOME/zn-dispatch`, else `~/.local/state/zn-dispatch`, then a folder named for the repository, file `main-seen`, with `origin-url` beside it; and it mirrors it in each item's `state.json`. At the start of every run, before every step and after every step, every commit of `main` since the watermark must be tracker state (as above) or a pull request's merge into `main` on GitHub. The file is shared by every dispatcher of the repository (and `vet`): it only moves forward, under a lock, and another run's advance is never a trip, because within a run the dispatcher vets from its own copy of the watermark, whatever the file says, so a step that deletes or rewrites the file is still caught by what it pushed. A missing watermark at a run's start is never trusted (only `./zn dispatch vet` writes one), one behind the item's mirror stops the next run, a diverged one trips, and so does origin's URL changed since the last run. After a step, origin's configuration (`remote.origin.*`, `url.*`) must be as the run pinned it, the main checkout's tracked and untracked files unchanged, its HEAD moved only forward along `main`. Anything else stops the chain (exit 5, outcome `tripwire`), with the step's spend still recorded, until the user looks, runs `./zn dispatch vet` and then `./zn dispatch retry <id>` (nothing else clears the stop: `vet` alone leaves it; the stop after a gate merge is the same, recorded as the attempt `merge-check`) (`--dry-run` lists each commit's verdict and writes nothing; plain `vet` lists them too). **Known limits:** this detects a late push after the fact, at the next run, and never prevents one; a process left behind can rewrite the watermark, its mirror and the URL file between runs; a merge made with the user's credential (stolen or not) is a pull request's merge and passes; an agent can run `vet` itself. They are the user's, by rule.
- **Spend.** The dispatcher writes each step's measured row (wall, CPU, the adapter's token count, model id) itself: a row in `spend.d/<writer>.tsv` on the `zn-dispatch` branch while the item is in the backlog, a reviewer's row under its review file's name (`design-review-NNN`), a code or stream review's as the `./zn commit … --phase code-review --model <id>` line it prints for the author (the measured row is appended to the author's measure buffer, and that commit folds it), and a run's as pending in `state.json` until the merge, when the next `./zn dispatch <R-id>` writes it as `deliver`. Nobody passes `--time` or `--tokens`. A gate, a spec run and `./zn run` only append to `.cache/measure.tsv`. `./zn commit`, `./zn spend`, `./zn done` and `./zn land` fold the lines for the tickets they commit. A buffer that is never folded (the main checkout, a branch with no ticket) is dropped after 14 days, or when that checkout's `.cache` is deleted.
- **The chain.** `./zn dispatch <id>` (or `new "<description>"`) reads the item's state on `origin/main` after every step and never a model's prose: a new issue goes to z-design; its prep PR is the `prep` gate; a prepared raftless issue gets `raft-plan --apply` in `raft-<id>`, then z-raft; the rafting PR is the `raft` gate; a prepared raft gets `z-ready`; an active raft gets z-run until its PR leaves draft (`./zn done`), and that PR is the `run` gate, always a human's. Only the dispatcher merges: it passes a `prep` or `raft` gate itself, with the real `gh` and the user's credential, when `auto_merge` names it, the PR is green and mergeable, and its head (fetched from `refs/pull/<n>/head` and equal to the head GitHub reports) is the item's own tracker state by the one function, from its merge base with `main` (a prep PR: the issue's own folder, whose sequestered files it may change, and skill lessons; a rafting PR: each item's change judged by its shape against the base, never by what the PR says: an existing backlog issue only its `raft:` line, between empty and a raft the PR carries; an existing backlog raft any file but its sequestered ones; a new raft its backlog folder, its `check.sh` the rendered template's RC0 lines byte for byte, then only `check "RCn: …"` lines and `finish`; nothing of an active, done or retired item) pinned to the head it checked (`gh pr merge --squash --match-head-commit <head>`, so a push to the branch since voids it); otherwise it stops there (exit 4). A rafting PR also needs, beyond that shape: each carried raft keeps its `<id>.md`; an item that main changed since the PR was cut is refused (rebase first: the merge lands on today's main); the id counter is never carried; and the tracker's own readers accept what the merge would make (`git merge-tree` with today's main must not conflict, `audit` must report no error main's does not, and a carried raft's `issues:` and its members' `raft:` lines must agree). The prep gate is held to the same readers (an issue's `raft:` line must be listed by that raft). GitHub pins no base, so after a gate merge the dispatcher compares the merge commit's first parent with the main it judged, and stops with exit 5 when main moved over an item the PR carries; the merge is not undone, and `vetMain` does not judge it. It stops (exit 3) when a step wrote `questions.md` in its state folder (the user answers in that file and runs `./zn dispatch retry <id>`, which keeps it as `answered-<n>.md`), and (exit 1) when a step failed, was lost, or left a finding `./zn lessons --uncovered <id>` still lists after a review step (z-design, z-raft, z-run, zz-review). `--dry-run` prints the next action and the CLIs it would try, and starts nothing and changes no tracker state (a gate's judgement still exports and removes a scratch tree under `.cache/dispatch/`).
- **Run state.** `.cache/dispatch/<id>/state.json` (the step, CLI, runtime, model, the running group and its lock, worktree, start, tokens, outcome, every attempt, the merges and broker pushes, pending rows), `questions.md`, and a folder `<step>-<mode>-<id>-<n>/` of its own for each step a step dispatched (a review from its author): ignored files in the main checkout. One dispatcher per item at a time (an flock that dies with its holder); a step whose dispatcher died is `lost`, never resumed, until `retry`. `./zn dispatch status <id>` prints every run, `stop <id>` kills each running group only while it is still that run (its supervisor still holds the run's lock; never a group id of 1 or less) and marks any other `lost`, `retry <id>` reruns the failed, stopped or lost step on the same order. The board (c0118) reads it.
- **The wrapper.** A model step's PATH starts with `z-nile/bin`, a convenience layer over the credential and the watermark: its `git` decides a push from git's own dry run (aliases, `-c` and refspecs resolved by git) against a private, freshly fetched copy of `main`, refuses anything but tracker state there, and refuses plumbing pushes; its `gh` allows only the skills' commands (no merge, however spelled or aliased) and `gh api` reads and comments. Both are bypassable by an absolute path; the watermark catches what they miss.
- **Inside a check.** A spec or `check.sh` that runs `./zn dispatch` may start only a CLI whose real path is under the checkout's `.cache` (a fake); any other is refused before it starts.

## Sync and claim
Tracker state is shared the moment it changes, not when a PR merges, so parallel terminals see each other's work.
- **Sync first.** Every skill that reads or changes tracker state starts with `./zn sync` (a merge of `origin/main` in a worktree, a fast-forward in the main checkout). Reviewers and stream agents never merge: they run `./zn sync --fetch`, which only updates `origin/main`, so the diff they judge does not move.
- **Statuses** (`status:` in an item's frontmatter): `new -> preparing -> prepared -> active -> done`. `design:` (draft, reviewed, ready) stays the design review's field. A missing `status:` is derived: `done/` is done, `active/` is active, `design: ready` is prepared, a draft item in a raft (or a draft raft) is preparing, anything else is new. `./zn status` lists them from `origin/main`; `status <id>` prints one; `status <id> <to>` moves one, checked against `origin/main`. `done` is only ever set by `./zn done`, and only `ready` (or the legacy `start` of a backlog raft) claims `active`, and `stop` gives a readied raft back.
- **Every write is stamped**: the stored value is `<state>-<three words>` (for example `preparing-quiet-copper-falcon`) and each write uses fresh words, so two terminals making the same move conflict in git instead of merging silently.
- **Published or carried.** These moves are pushed straight to `origin/main` as a tiny commit: `new issue` (the stub, `--desc "<line>"` is its Problem), `new raft` (claims the raft, and its members when they are `new`), `fold` and `recombine` (claim their rafts), `release`, `status <id> preparing|new`, `status <id> prepared` back from `active`, and the claim made by `ready` (or by a legacy `start`). An emergent `new issue --raft <R-id>` and `renumber <id>` without `<new>` push a counter-only commit (the raised `z-nile/next`) and then work locally. The move to `prepared` is **carried by the prep PR**: it only edits the local documents.
- **The direct-push exception.** Everything else lands by pull request. A published change is a tracker-only commit: only `<root>/(issues|rafts)/<ID>/<ID>.md` and `check.sh`, under a root that `origin/main`'s `z-nile/projects.toml` lists (never the working tree's), a `check.sh` only when it is created, an existing document only in its `status:` line (what `status`, `new raft` and `start` publish), an item's `provenance.md`, rows appended only and of the published events (`./zn provenance record`), and `z-nile/next`, whose counters may only go up. An issue's `spend.md` is not pushed by `./zn spend`: the command commits the appended row on the current branch, and the row reaches main with that branch. `publish.commit` still accepts an appended `spend.md` when a tracker commit carries one (a directory move keeps it byte for byte). The one other kind is a whole-directory move by `ready` or `stop`: every file of an item directory moves between the backlog and `active/` of its own root (never `done/`, never to another root), byte for byte, except the document's `status:` line and the item paths in `check.sh`, which `paths.rewrite` changes to the new directory; publish recomputes both and refuses anything else. `./zn land` also pushes a capture's edits to draft backlog issue documents (their sections, `title` and `depends_on`; design stays draft, every other frontmatter line unchanged) after the static stages (`z-nile/check.sh --static`). Designs, reviews, code and acceptance specs never ride it. A commit that skips the deploy for the many tiny pushes is intended: `deploy.yml` ignores every project root (`<root>/**`: `pickman/.tracker/**`, `z-nile/.tracker/**` and the rest, in registry order) and `z-nile/next` on `push`. Adding a project needs its registry entry and its root in that `deploy.yml` list. A project with code also needs its home (z-nile/README.md, A project's home), which the gate checks for every project.
- **Claims.** z-design claims one issue with `./zn status <id> preparing` and gives it back with `status <id> new`. The old prep's `new raft` over `new` issues still claims them with the raft's stamp, and `./zn status <R-id> preparing` claims an existing draft raft with its unprepared members. A raft move (`status <R-id> preparing|new`) never restamps a member that is `prepared` on `origin/main`, and refuses a member another raft holds there. `ready` (and a legacy `start`) refuses a raft unless it and its members are `prepared` on `origin/main`; the claim is made by `ready`, not `start`.
- **Rafting** (z-raft). An issue's raft is its own `raft:` line, edited only in the rafting PR: two PRs that raft one issue edit that one line, so the second cannot merge cleanly, and its sync shows the conflict. The published claim (`new raft` over prepared issues, `fold`, `recombine`, `status <R-id> preparing`) stamps the raft only, with a fresh `preparing-…` value; recombine gives its two rafts one value, and that shared stamp is what lets the carried `status <keeper> prepared` take a member whose `raft:` on `origin/main` still names the other raft. The carried move takes a member that is prepared on `origin/main` as it is, refuses one another raft holds there, and takes a `preparing` member only when it carries the raft's own stamp or a claim this checkout made (`status <id> preparing` here); any other `preparing` member is another terminal's live claim and is refused, naming it. z-design's `status <id> preparing` refuses an issue whose `raft:` names a raft on `origin/main` (z-raft takes it out first with `./zn unfold <R-id> <id>`), and `ready` refuses a raft while a member is `preparing`. A raft's `grouped:` line records a hash of each prepared member's design as z-raft grouped it (its document without `status:` and `raft:`, `check.sh`, `acceptance/`, and its design reviews, refutes and `harvest.md`); the carried move and `ready` refuse a member whose design changed on `origin/main` since (a redesign landed inside the rafting window), a member this rafting grouped with no entry, and a raft of several issues whose coherence reviews quote no `Grouped:` record covering the current one. `compact` and `renumber` re-record every entry that matched before they rewrote its ids, and `remap` does the same. `./zn release <R-id>` is the published give-back. An issue whose `raft:` names a retired or missing raft (audit's `dead-raft` error) is cleared by the command the error names for its state: in the backlog, `./zn unfold <R-id> <id>`, which claims nothing (there is no raft to claim) and rides in the rafting PR; in `active/`, `./zn stop <id>` first (main checkout), which gives that one issue back to the backlog as `stop` gives a member back, and `unfold` after it. An active issue with no `raft:` (`raftless-active`) goes back with `./zn stop <id>` too. A conflict on `raft:` or `depends_on:` (they are adjacent lines) after a sync means rerun z-raft for that issue: take `main`'s line and drop the issue from your raft, or take both edits when it was only `depends_on:`.
- **A failed start.** `start` runs every local check before it claims. If a step after the claim fails (branch push, `gh pr create`), the local state is consistent: finish by hand (`git push -u origin <branch>`, `gh pr create --draft`), or give **your own** claim back with `status <R-id> prepared` (a raft started the legacy way, still in the backlog; a readied raft is given back only by `./zn stop <R-id>`). The same terminal can re-run `start` if it died before moving anything (it remembers the claim in `.cache/tracker-claim-<R-id>`); another terminal is refused.
- **Offline.** `PICKMAN_PUBLISH=0` (or a repository without `origin`) keeps every command local, as it was before. Publishing and every other command that changes a repository first check that git's repository root is the checkout the tracker lives in; read-only commands do not.
- **Giving back a readied raft.** `status` refuses any item in `active/` on `origin/main` ("<id> is readied (in active/): use ./zn stop <R>"); `./zn stop <R-id>` is the way to give back a readied raft, and it also gives back a raft claimed by the legacy `start`.
- **Whose claim.** A claim is not enforced against other terminals' give-backs (`stop` included): `status <R-id> prepared` from `active` (a legacy claim; a readied raft only through `stop`), `status <id> new` and `status <id> preparing` are open to anyone, so use them only for a claim that is yours (the user's decision: ownership is documented, not checked). `release` is the one give-back that checks: it needs the claim this checkout remembers, or `--force`. Never give back a claim you did not make; ask the user.
- **Cutover.** A prep that was open before this landed exists only on its branch, so nothing on `origin/main` knows its raft id or members. Land such preps first, and renumber on a clash (see Conflicts). Do not stamp their members with `status <id> preparing`: a stamped member of a raft that is not on `origin/main` cannot be moved to `prepared` and can never be started.

## Lessons
Search with `./zn lessons <terms>` when you are about to do something a lesson might cover.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
