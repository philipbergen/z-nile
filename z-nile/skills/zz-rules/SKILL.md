# Tracker

All work is tracked in project roots, which are committed. `z-nile/projects.toml` lists the projects, each with the root that holds its issues and rafts: pickman's is `pickman/.tracker/` and z-nile's, the tooling's, is `z-nile/.tracker/`. A directory it does not list is not a project. Each project also has a home, the folder that holds its root and in which its `check.sh` files and specs run: `pickman/` for pickman (its `src/`, `tests/`, `scripts/` and Rojo projects are there) and `z-nile/` for z-nile (the engine, the gate, and the tooling's specs and harness in `z-nile/tests/`); the repository root belongs to no project (c0120). `./zn check` runs a pickman item's `check.sh` from `pickman/` and a z-nile item's from `z-nile/`, so the paths it names are its project's, and `./zn find` and `members` print paths from the folder you run them in. The folder you run `./zn` in also gives the project (`pickman/` gives pickman, `z-nile/` z-nile; `--project` overrides it). `tracker/` is a retired root (c0120): it holds only the old counter's tombstone, and `./zn audit` and the gate fail if anything else appears there. One counter numbers every project, so a bare id is unique across the repository, and every command that takes an id (`find`, `members`, `status`, `capture`, …) searches every root. The engine, its templates (`z-nile/templates/`), the counter and the compaction map live in `z-nile/` and belong to no project. The command is `./zn` at the repository root (`scripts/tracker.sh` forwards to it until every raft whose sequestered `check.sh` names that path is done). The only way to change tracker state is `./zn`. Don't move tracker directories by hand. Inside a raft, commit with `./zn commit`; capture, prep and doc-only worktrees, which have no active raft, use plain `git add` and `git commit` (see Landing a change). Every change is made in a worktree (see Worktrees).

## Items
| kind | ID | example |
|---|---|---|
| feature issue | `f` + 4 digits | `f0010` |
| defect issue | `d` + 4 digits | `d0020` |
| chore issue | `c` + 4 digits | `c0030` (includes every CI/test/tooling fix, even bugs; see z-ticket) |
| raft (epic) | `R` + 4 digits | `R0010` |

- **Numbering**: `f`, `d` and `c` share one number space; rafts have their own. `z-nile/next` holds the next number of each (`issue <n> <phrase>`, `raft <n> <phrase>`). The first publish after c0114 lands moves the counter there from the old counter file, in its own lease push, and leaves a tombstone in the old file, so an engine from before c0114 refuses to number; until then the old file is the counter. `new`, `new raft`, an emergent issue and `renumber` take the counter, counting by one, and push it raised, with a fresh phrase, in a lease push to `origin/main` (a lost race is retried on the new `main`); a number already in use is always passed. Offline (`PICKMAN_PUBLISH=0`) the local counter is read but never written. A tree without `z-nile/next` (a fixture) keeps the old rule: the next multiple of 10 above the highest number in use.
- **Compaction**: `./zn compact` renumbers every item from 0001, in a fresh worktree cut from `origin/main`, as one local commit to land by pull request; it refuses while another branch changes a project root (`pickman/.tracker/`, `z-nile/.tracker/`) or a project's promoted specs (`z-nile/tests/acceptance/`, `pickman/tests/acceptance/`) (`--force` runs anyway; `./zn busy` lists what holds them), and writes the old-to-new map to `z-nile/compaction.txt`. Merge the compaction PR only while `origin/main` still equals the sha in `z-nile/compaction.txt`'s header; if `main` has moved, reset to `origin/main` and compact again (it is deterministic). On each branch that was in flight, run `./zn remap` before merging `origin/main`: it takes the new ids and then merges `origin/main` itself. Never merge it plainly first: nothing detects the mixed tree afterwards. A branch that did merge plainly undoes that merge with `git reset --hard ORIG_HEAD`, then remaps. Any other tree from before the compaction refuses to publish until it merges `origin/main`.
- **Duplicate ids**: `./zn audit` reports every problem in the tree (the gate runs it too). One id in two lifecycle folders blocks most commands: `./zn renumber <directory>` renumbers that copy only: renumber the copy not in `done/` (normally the fresh backlog stub, for example `renumber tracker/issues/c0510`), because a done copy's specs are promoted under its id; a `done/` directory is refused.
- **Legacy layout**: documents used to be named with their slug. `./zn migrate` renames any such document to `<ID>.md` and adds `slug:` to its frontmatter; run it, and commit, after merging a `main` that has the new layout.
- **Conflicts**: two branches that pick the same number now conflict in git, because both write `<ID>/<ID>.md`. Only a `CONFLICT (add/add)` on that path means two items share a number: run `git merge --abort`, `git fetch origin main`, then `./zn renumber <ID>` on your own branch, which gives the item the number one above the highest of its kind in **both** your tree and `origin/main` (`f`, `d` and `c` share one space, rafts have their own), and merge again. `renumber <old> <new>` sets a number by hand. `renumber` rewrites every reference. A content conflict on a document is two edits to one item: resolve it like any merge, and never renumber. A branch from before c0114 that added a file inside a tooling item's folder gets `CONFLICT (file location)` when it merges `origin/main`: git suggests the folder's new place under `z-nile/.tracker/`; accept it (`git add` that path) and never move the folder back. The same holds for a branch from before c0120 that added a file in a pickman item's folder, under `src/` or under a game test folder: accept git's place under `pickman/`, never the old one (the gate's old-roots check fails on it). A branch from before c0115 that added a file inside an old skill folder (`.claude/skills/<old>/`) gets the same conflict: accept git's place under `z-nile/skills/<new>/` or `pickman/skills/<new>/`, never a real folder in `.claude/skills/` (the gate's `./zn skills --check` fails on it).
- **References**: always refer to items by bare ID, never by path. Use `./zn find <id>` to get the current directory.
- **Projects**: the directory gives the project unless `--project` names one. `new issue`, `new raft` and `list` work in `--project <name>`'s project, else in the one whose folder holds the directory you run `./zn` from (`z-nile/` and below is z-nile's, `pickman/` and below pickman's, c0120). At the checkout's root, or in a folder no project holds, the commands that create an item, and so must choose its project (`new issue`, `new raft`), refuse and ask for `--project`; read-only ones read every project there (`list` shows them all), because reading needs no project. There, game work passes `--project pickman` and tooling (the tracker, the gate, the guards, the skills) `--project z-nile`. An emergent issue goes beside its raft, which gives its project. A raft lives in its members' project and never spans two. R0001, finished before c0114, is the one exception: its members stayed with their projects (c0001 in z-nile's, c0002 in pickman's), and `members R0001` still lists both. `.tracker/` is a hidden folder: `rg` and some search tools skip it unless told (`rg --hidden`), so find items with `./zn find` or `git grep`.

Each item is a directory named by its ID:
```
<ID>/<ID>.md            the document (frontmatter incl. slug + sections from z-nile/templates)
<ID>/check.sh           acceptance criteria as executable checks (see the zz-test skill)
<ID>/acceptance/        sequestered acceptance specs (issues); `done` moves them to tests/acceptance/<ID>/
<ID>/experiments/       spikes for unknowns (issues)
<ID>/design-review-NNN.md, design-refute-NNN.md   from z-design, on the issue; z-raft's coherence review, on the raft
<ID>/review-NNN.md, refute-NNN.md                 code review, on the raft
<ID>/spend.md           written by `./zn commit` and `./zn spend`; never edit by hand
```

- **Skills**: z-nile's skills live in `z-nile/skills/<name>/SKILL.md`, a project's own in `<project>/skills/<name>/SKILL.md` (its name in `z-nile/projects.toml`: `pickman/skills/`). The harnesses find them through `.claude/skills/<name>`, a committed relative link to the real folder (`../../z-nile/skills/<name>`), which `./zn skills` writes and `./zn skills --check` (in the gate) checks: one link per skill, nothing else in `.claude/skills/`. Names are unique across the repository and equal the `name:` in the skill's frontmatter. The `z-` (pipeline) and `zz-` (called from inside a step) prefixes are z-nile's alone: a project's skill is named `<project>-…`, and `./zn skills` refuses any other. Git can't add a path through a link, so every tool, spec, Touched path and edit uses the real folder, never `.claude/skills/<name>/…`.
- **Lessons**: `<skills folder>/<skill>/lessons/<slug>.md` (the skill's real folder, `z-nile/skills/<skill>/` or `<project>/skills/<skill>/`), id `<skill>/<slug>`. Frontmatter `title`, `when` (`design`, `build` or `both`), `tags: [a, b]`, `check` (one question ending in `?`) and optional `from` (only for a source with no item folder to hold a note; each key once); the body says the rule, why, and how to apply it. **`harvest.md`**, in each reviewed item's folder, has one entry per review finding: `- design-review-001 F2: <lesson id>, <lesson id>` or `- review-001 F3: one-off: <reason>`, plus `- note <text>: <lesson ids>` for a source that is not a review finding (a subagent's candidate, a correction by the user, a failed step). A note covers no finding. A lesson's sources are the entries naming it, each once. See `./zn lessons`.

## Worktrees
Every change is made in its own git worktree under `<repo>/.worktree/` and lands by pull request (except tracker state, see Sync and claim). The main checkout stays on `main` and is never edited. Every job runs in a worktree under `<repo>/.worktree/`, never outside the repo directory: no sibling directory next to the repo, and not the harness's own `.claude/worktrees/`.

1. **The main checkout is read-only.** The complete list of commands that may run there:
   - `git fetch`, `./zn sync` (a fast-forward there, which also rebuilds the board), and read-only inspection (`git status|log|diff|show|worktree list`);
   - `git worktree add|remove|prune` and `git branch -D <merged branch>`;
   - `z-nile/setup.sh`, once, when bootstrapping a new machine (SETUP.md);
   - `./zn ready` and `stop`, which publish to `origin/main`, fast-forward it there; `ready` writes the ignored `<root>/rafts/active/<R-id>/prompt.md` beside the raft and `stop` removes it;
   - `./zn dispatch` (Dispatch, below), which runs every step in a worktree of its own and writes only the ignored run state in `.cache/dispatch/`;
   - the read-only tracker commands `list`, `audit`, `find`, `members`, `busy`, `metrics`, `workstreams`, `status` (without a target status), `prompt <R-id>` (it reads a readied raft's prompt and writes nothing), `lessons`, `raft-plan` (without `--apply`), `skills --check` and `capture <id>` (they only read), and the worktree commands `worktree` and `worktree-prune`. (`./zn check` runs an item's checks and, for a raft, the full gate, so it runs in a worktree.)
   The tracker enforces part of this: `new`, `renumber`, `migrate`, `start`, `status <id> <to>`, `fold`, `unfold`, `recombine`, `release`, `raft-plan --apply`, `compact`, `remap` and `skills` (without `--check`) refuse to run in the main checkout of a repo that has an `origin`; `ready` and `stop` refuse to run anywhere else.
2. **Every change starts with a worktree**: `cd "$(./zn worktree <target>)"`.

   | work | target | path and branch |
   |---|---|---|
   | executing a raft | `R0010` | `.worktree/R0010`, branch `R0010-<slug>` |
   | capturing an issue (z-ticket) | `capture-<slug>` | `.worktree/capture-<slug>`, the same branch name; lands with `./zn land`, no PR |
   | designing an issue (z-design) | `prep-<slug>`, the issue's slug | `.worktree/prep-<slug>`, the same branch name |
   | rafting (z-raft) | `raft-<slug>` | `.worktree/raft-<slug>`, the same branch name |
   | the dispatcher's own spend rows | `zn-dispatch` | `.worktree/zn-dispatch`, the same branch name; it only publishes |
   | a skill, doc or config edit | `<area>-<slug>`, for example `skills-worktree-rule` | `.worktree/<area>-<slug>`, the same branch name |

   A change to skills, docs or tooling is still tracked work: it has an issue and normally a raft, and is executed in the raft's worktree like any other. Names are lowercase, so a prep worktree is named by the issue's slug and a rafting worktree by a short slug of its own: a new raft's id isn't known until `new raft` has run inside it. Use `./zn worktree`, not the harness's own worktree feature: its directories aren't under `.worktree/`, and `worktree-prune` never sees them (it warns about any worktree outside `.worktree/` and leaves it). A worktree inside the repo also sees the main checkout's `.luaurc` as a parent configuration, so an alias a branch renames can still resolve locally: CI, which checks out the branch alone, is the final check.
3. **Starting execution**: the human starts a Claude session in the main checkout (which stays on `main`) and runs `/z-run <R-id>`. The skill reads the raft's prompt (`./zn prompt <R-id> --path`) and `cd`s into `$(./zn worktree <R-id>)`. The hooks follow the session's current directory, so from then on they act in the worktree; subagents get absolute worktree paths, because a subagent's shell resets its working directory on every call. Another agent gets the same text from `./zn prompt <R-id>`.
4. **Prep and rafting merge before execution.** An issue's design PR merges before z-raft groups it, and the rafting PR merges (Landing a change) before `z-ready` runs, so the raft's own worktree branches from an `origin/main` that has the prepped items in their raft. `z-ready` never creates a raft: a raftless issue goes to z-raft.

## Lifecycle: the directory and the status
- **Paths**: `<root>/rafts/retired/<ID>` is a raft `recombine` retired (its review history, never an item to work); `<root>/{issues,rafts}/<ID>` is backlog (`<root>` is the item's project root, `pickman/.tracker` or `z-nile/.tracker`), `…/active/<ID>` is in progress, and `…/done/<ID>` is finished. On `main`, `active/` holds the rafts that `ready` has handed out (and their issues), not only the branch you are on: the current raft is the active raft whose branch is the current branch.
- **The design field**: frontmatter `design:` moves `draft` → `reviewed` → `ready`; `z-design` sets an issue's and `z-raft` a raft's.
- **Everything worked is a raft.** A raft has exactly one type (feature, defect or chore), and every member issue must match it. z-design stops at a prepared issue with no raft; z-raft makes every raft, in its rafting worktree, and gives `single: true` only to a raft of one `solo` or over-cap issue (nothing is folded into it); `./zn ready <issue>` refuses a raftless issue, and `prompt` takes only a raft id.
- **One raft = one branch (`R0010-<slug>`) = one PR.** In Phase 2B, temporary stream branches (`ws-<issue>`) feed the raft branch and are deleted.

| step | command | effect |
|---|---|---|
| ready | `./zn ready <R-id\|issue-id>` | main checkout only, on a clean `main`, with an origin (z-ready skill). Checks the raft and every member are `design: ready` with a `check.sh` that has a check, and that every `depends_on` outside the raft is `done`. Claims the raft, publishes one tracker-only commit that moves it and its members to `active/` on `origin/main` (every `check.sh` item path rewritten), pulls the main checkout, and writes the ignored `<root>/rafts/active/<R-id>/prompt.md` (it inlines the project's `<root>/architecture.md`, pickman's map; a project without one gets a line saying so). On an active raft it regenerates the prompt and makes no commit. |
| stop | `./zn stop <R-id>` | main checkout only, on a clean `main`, with an origin (z-stop skill). It gives back exactly the issues that carry the raft's own claim stamp (`ready` and `start` stamp the raft and every issue they claim with one `active-…` value); an issue only listed in `issues:`, or one filed naming the raft after the claim, is never touched (the latter is named in a warning). Every claim stamp is new on `origin/main` (redrawn until no item carries it), and a raft with no `active-…` stamp is refused, to be given back by hand. Gives back a readied raft: publishes one tracker-only commit that moves it and its members from `active/` back to the backlog, stamped `prepared-…` (every `check.sh` item path rewritten back), removes `prompt.md`, pulls the main checkout, and names the raft's branch and PR, which it leaves as they are. A raft claimed by the legacy `start` (backlog, status `active`) gets a status-only publish and no move. A member in `done/` refuses. |
| start | `./zn start R0010` | clean tree required. A readied raft (in `active/` on `origin/main`): creates the branch, makes an empty `tracker: start` commit, pushes, and opens a **draft** PR; it claims and moves nothing. A backlog raft (legacy): checks members are `design: ready` and every `depends_on` of a member that isn't a member of the raft is `done` on `origin/main` (an unknown id is refused too); if `start` refuses, merge `origin/main` and retry, never edit `depends_on` or move items to get past it: stop and report. It then claims, creates the branch, moves the raft and its members to `active/`, commits, pushes, and opens a **draft** PR. A worktree made before `ready` is told to `sync` first. Do this first, so the in-progress claim is visible right away. |
| worktree | `./zn worktree <R-id\|name>` | creates or reuses `<repo>/.worktree/<R-id\|name>` on its own branch from a freshly fetched `origin/main` and prints its path. A raft's worktree is `.worktree/R0010` (branch `R0010-<slug>`); any other is `.worktree/<name>`. Refuses a done raft, and a branch that is checked out elsewhere. For a named worktree, `--from <ref>` cuts the new branch from that ref instead of `origin/main` (used for workstream streams: `./zn worktree ws-<issue> --from <raft branch>`). |
| workstreams | `./zn workstreams <R-id>` | read-only plan for parallel execution (zz-execute Phase 2B): issues in waves from `depends_on` and overlapping Touched modules, and a last line `parallel: yes (wave k: …)` or `parallel: no` |
| board | `./zn board [--out PATH] [-O]` | writes the whole tracker as one self-contained HTML page, `.cache/board.html` by default (gitignored; the main checkout's copy is rebuilt after every tracker push to `origin/main` and every `sync` there, so reload the tab; elsewhere regenerate to refresh). Views Rafts and Issues, each split into Ready, Not ready and Done (a backlog raft is Ready only when its design is ready and its effective status is prepared; a readied raft is Ready; blocked rafts stay listed). A raft's shown type comes from its issues (one type, or mix). A row with a next command has a copy button. Cursor keys, `/` then an id to jump to it, and each item's document and dependencies rendered with the vendored marked. Then it opens the page in the default browser unless `-O` is given (`-O` only writes it, as CI and the specs do; `--open`, the old opt-in, is still accepted and is the default). `.github/workflows/board.yml` rebuilds it on every push to `main` and keeps it as the `tracker-board` Actions artifact: `rm -rf .cache/board-ci && gh run download -n tracker-board -D .cache/board-ci` fetches the latest into a fresh directory (gh won't overwrite an existing file, and `.cache/board.html` is the local default). Stats (a Stats button, not a third view) charts opened, closed, net, minutes and lines added and removed for the month, quarter and year, by all, feature, defect and chore, plus the defect and chore ratios and mean days in state; Table shows the same numbers with units. Without history (a shallow clone or no git) closed counts and time in state are omitted. |
| busy | `./zn busy [<path>...]` | read-only. Lists what holds the paths: every raft active on `origin/main` (but the current branch's own), every branch, local or on origin, that changes them since it left `origin/main` (compaction's busy-branch check), and every other worktree with uncommitted changes under them; exits 1 when anything does. Without paths it guards what compaction guards (every project root and promoted-spec folder). A move of the tree (c0120: `./zn busy tracker src tests`) is readied only when it prints nothing |
| capture | `./zn capture <id>` | read-only. Prints `capture <sha> <path> <subject>` and then the item's document as captured: the newest commit on `origin/main` (`HEAD` without one) whose subject is `tracker: new` with the item's id in its leading id list (`tracker: new raft …` and `tracker: scope …` are not captures), or else the document's first add. It reads the item's backlog, `active/` and `done/` folders, under the item's current id only: no id change (a compaction or a `renumber`) is followed. The header line says when the answer is weaker: it ends `(no capture commit: first add)` when no commit is a capture (a renumbered item, or one made before captures had that subject), `(ambiguous: two items held this id at once)` when the id had two copies, and `(history before <sha> not followed: it changed tracker/compaction.txt)` when the item's life starts at a commit that changed the compaction map and its document. A legacy slug-named document counts. Exit 1 for an id with no history |
| lessons | `./zn lessons [--skill <s>]... [--when design\|build] [--tag <t>]... [--full] [<word>...]`, `--tags`, `--check`, `--uncovered [<id>...]` | read-only. Lists the skill lessons (most sources first), shows them in full, lists tags, validates every lesson and `harvest.md` (`--check`, exit 1 on a problem), or lists the review findings no `harvest.md` entry covers (`--uncovered`, exit 1 if any) |
| skills | `./zn skills [--check]` | writes `.claude/skills/` as one relative link per skill folder (`z-nile/skills/*` and every project's `<project>/skills/*`) and removes anything else there, or, with `--check`, writes nothing and exits 1 naming each missing, extra, wrong or non-link entry. Both refuse a skill folder without a `SKILL.md`, a `name:` that differs from its folder, a name two folders share, and a project skill not named `<project>-…`. The gate runs `--check`; `skills` without it refuses in the main checkout of a repository with an origin, like `new` |
| raft-plan | `./zn raft-plan [--apply]` | read-only without `--apply`. Prints z-raft's no-argument plan for every prepared issue with no raft, as the commands that carry it out (`./zn fold <R-id> <ids…>`, `./zn new raft <type> <slug> <ids…> [--single] --project <name>`), and `skip <id>: <why>` for an issue it can't place (no `size:`) or an open raft it won't fold into (a member with no `size:`); `raft-plan: nothing to raft` when there is none. `--apply` runs them in order, in a worktree. The policy is z-raft's (one type and one project per raft, backlog prepared rafts only, defects and chores folded, features by shared surface, the size cap, solo issues alone) |
| fold | `./zn fold <R-id> <issue>...` | in a worktree, on a clean tree. Puts prepared backlog issues with no `raft:` into a prepared backlog raft of their type and project: publishes the raft's claim (its `status:` only; a raft this checkout already claimed is not claimed again), then writes each issue's `raft:` and the raft's `issues:` here and commits. Refuses a solo issue with others, and a raft that is new, being prepared, active or done |
| unfold | `./zn unfold <R-id> <issue>...` | in a worktree, on a clean tree. Takes members out of a backlog raft: claims it as `fold` does, then empties each issue's `raft:`, drops it from `issues:` and `grouped:` here and commits. The route back to z-design for a rafted issue, during a rafting or after it landed |
| recombine | `./zn recombine <keeper> <other> [<issue>...]` | in a worktree, on a clean tree. Moves the named members of the other backlog raft, or all of them, into the keeper (same project and type, both prepared or new, every member prepared). Publishes one fresh `preparing-…` stamp on both rafts (status lines only), then writes the moves here and commits; the other raft is retired only when it ends up empty: its folder moves to `<root>/rafts/retired/<R-id>` in this branch, with `retired: <keeper>`, keeping its reviews, refutes and `harvest.md` (read by `lessons` and `metrics`, never by `find`, the board or the plan) |
| release | `./zn release <R-id> [--force]` | in a worktree. Gives a rafting claim back in one published commit: every backlog item carrying the raft's `preparing-…` stamp on `origin/main` (the raft, recombine's other raft, the issues an old-style `new raft` stamped) goes back to `prepared` when its design there is ready, else `new`. It also gives back the issue claims this checkout remembers for the raft's members (`status <id> preparing` here). Refuses a claim this checkout does not remember (`.cache/tracker-claim-<R-id>`) unless `--force`. This branch's own commits are left as they are |
| prune | `./zn worktree-prune` | removes the worktree and branch of every raft that is in `done/` on `origin/main` (any merge strategy); keeps the rest, never forces, and lists named worktrees |
| focus | `./zn focus f0010` | the following commits are attributed to that issue |
| commit | `./zn commit -m "msg" [--issue f0010]... [--time 25] [--phase build|code-review|deliver] [--tokens <n>]` | `git add -A`, then records spend rows in each issue's `spend.md` and the raft's summary **in the same commit**, adds `Issue:` trailers, and pushes. `--phase` defaults to build; capture, prep and design-review use `./zn spend` |
| spend | `./zn spend <id> --phase capture, prep, design-review or deliver --time <minutes> [--tokens <n>] [--note <text>]` | appends that phase's rows to each issue's `spend.md` on origin/main and changes nothing in this checkout. Refuses inside the main checkout, and refuses an item that is already active |
| done | `./zn done R0010` | requires the latest review round to be resolved (each finding answered `fixed <sha>: <what>; consequences: <what the fix could break, and how that was checked, or none>`, `refuted`, or, for a medium or low finding and only as zz-execute Phase 4 step 7 allows, `deferred <id>: <why>` naming a backlog issue) and the raft's `check.sh` to pass. In this order: promotes acceptance specs to `tests/acceptance/`, moves everything to `done/` (uncommitted), runs the full gate (`z-nile/check.sh --full`) on that tree, marks the PR **ready** before its final push, commits as phase `deliver`, pushes, and appends spend to the PR body. A failing full gate rolls the tree back by itself (fix and re-run `done`). Inside a spec run (a fixture) it skips the full gate, says so, and checks only the promoted specs. If `done` is interrupted (Ctrl-C) during the gate, the tree is left promoted and moved but uncommitted: run `git reset --hard HEAD`, then re-run `done`. Likewise if it fails after marking the PR ready and before its commit: run `git reset --hard HEAD` and re-run `done` (marking ready twice is harmless); if only the push fails, run `git push`, then append `spend.md` to the PR body by hand |

## Landing a change
One procedure for every change: a raft, a capture, a prep or an edit.
0. **Sync first.** `./zn sync` in the worktree (a fetch and a merge of `origin/main`).
   - If `main` brought the new document layout, run `./zn migrate` and commit.
   - A `CONFLICT (add/add)` on a tracker document means two items picked the same number: see Conflicts.
   - Then run `./zn list` (it fails on a duplicate id and warns when one number is shared by two prefixes; renumber yours if you can) and `z-nile/check.sh --full`.
1. **Commit in the worktree**: `./zn commit` inside a raft; plain `git add` and `git commit` elsewhere.
2. **Push and open the PR**: `git push -u origin <branch>`. A raft's PR is opened as a draft by `start`; any other PR is opened ready with `gh pr create`. A capture lands with `./zn land` instead (no PR): it merges `origin/main`, runs `z-nile/check.sh --full` locally, checks that only the sections, title and `depends_on` of draft backlog issue documents changed, pushes one commit to `main` (retrying a lost race) and prints the worktree-removal command.
3. **Merge** a PR only when the conditions under Merging hold, with `gh pr merge --squash`. A raft additionally needs `./zn done` and a resolved review. A prep the user didn't ask for is not merged without asking, and a capture they didn't ask for is not landed without asking. (A capture has no PR: `./zn land` in step 2 is its landing.)
4. **After the merge, one chained command, run last**: `"<root>/zn" sync; git -C <root> worktree remove <path> && git -C <root> branch -D <branch>; git -C <root> worktree prune`. `<root>` is the first path in `git worktree list`; `sync` fast-forwards the root and rebuilds its board. When the session works inside the worktree (with z-run it started in the main checkout and `cd`'d into the worktree), removing it removes the session's own directory, so every command after it must use `-C <root>` or absolute paths, and nothing should run after this command: post the final report first. The alternative is to leave removal to `./zn worktree-prune`, run later from the main checkout.

## Merging
The agent that delivered the change merges its own PR once the evidence is in. Don't wait for a human. Merge only when **all** of these hold:
1. **For a raft**, `./zn done` succeeded: the latest review round is resolved and the raft's `check.sh` passed. The PR is ready, not draft, and has no unresolved `BLOCKED:` comment. The results of the most recent review are already on the PR as a comment (zz-execute Phase 4). Only a *significant* finding in the final round's `review-NNN.md` (any high, or a failed Judged criterion) blocks the merge and engages the human; mediums and lows become follow-up issues (zz-execute Phase 4 step 7).
2. `z-nile/check.sh --full` passes on the final head, run by you.
3. CI is green on the PR's exact head sha. `done` marks the PR ready before its final push, so the push starts the `pull_request` run on the final head (the `ready_for_review` event also starts a run, on the previous head; the poll ignores it because it looks at the final sha). Poll `gh pr view <pr> --json headRefOid,statusCheckRollup` until `headRefOid` equals `git rev-parse HEAD` and the `gate` check is `COMPLETED` with conclusion `SUCCESS`. Any other state is **not** green: a missing `gate`, `IN_PROGRESS`, or `SKIPPED` on the final sha means that sha was pushed while the PR was still a draft, so no run will follow by itself: dispatch one with `z-nile/ci-verify.sh` (below); `FAILURE` is red. If no `gate` run for this sha appears within a few minutes of the push, dispatch one with `z-nile/ci-verify.sh` (it needs HEAD equal to `origin/<branch>`, so push first) and wait. If the dispatched run fails, treat it as red.
   **The `beta` job too.** A PR that is ready for review from this repo also runs `beta`, which publishes the version to Pickman (Beta) and runs the runtime tests, so a merge needs it:
   - A missing `beta` check for the head sha means keep waiting, exactly like a missing `gate`.
   - A `workflow_dispatch` run never satisfies `beta` (it skips it). If no `pull_request` run appears within about 5 minutes of the `ready_for_review` event, re-fire that event with `gh pr ready --undo <pr> && gh pr ready <pr>`; use `ci-verify.sh` only to diagnose `gate`.
   - `beta` must be `COMPLETED` with conclusion `SUCCESS`. Unconfigured publishing ends `SUCCESS` with a warning, which is fine.
   - A red `beta` whose log shows `opencloud: ... failed with HTTP 429` or `HTTP 5xx` (500-599), from publishing, creating the task or polling it, or a publish `HTTP 409` (Roblox busy), is a transient Roblox failure whose retries ran out: rerun that job with `gh run rerun <run-id> --job <job-id>`, at most 3 times, then `BLOCKED:`. Any other red `beta` (HTTP 401, 403, 404 or another 4xx besides publish's 409, or a `FAIL` line without such a status) is a real failure: never rerun it; fix the cause, or post `BLOCKED:` when it isn't in this PR.
   - For a `CANCELLED` `beta`, run `gh run view <run-id> --json jobs`: a `beta` job with no steps was superseded by a newer ready PR (it never started), so rerun it with `gh run rerun <run-id> --job <job-id>` as often as needed until it finishes, but stop with `BLOCKED:` once 60 minutes have passed since the PR became ready, counted from the first ready event (re-firing it does not restart the count). A `beta` job whose steps ran was timed out or cancelled by hand: red. Judge `beta` only by the PR's own `pull_request` runs for the head sha: a `beta` that a dispatched run reports as `SKIPPED` never counts, for or against.
4. `gh pr view <pr> --json mergeable,mergeStateStatus` shows `MERGEABLE` and `CLEAN` (`UNKNOWN` is GitHub still computing it right after `done`: re-poll for up to a minute before deciding); any other state (`BEHIND`, `BLOCKED`, `UNSTABLE`, `DIRTY`) is not mergeable. `done` is preceded by a merge of `origin/main` (zz-execute Phase 5), so this should hold. If `main` moved since, and the merge is a clean one, merge `origin/main` in with plain `git` (`./zn commit` needs an active raft, and `done` has moved it), rerun `check.sh --full`, push, and repeat step 3. If it conflicts, or it needs anything beyond renumbering colliding IDs (`renumber` per Conflicts), post `BLOCKED:` and stop: a finished PR gets no unreviewed code changes.
5. The human hasn't said to hold.

Then `gh pr merge <pr> --squash --subject "<raft>: <title> (#<pr>)" --body $'<summary>\n\n<the Co-Authored-By line from your commit instructions>'` (the `$'...'` form makes the newlines real, so the trailer is a trailer). Get the merge sha with `gh pr view <pr> --json mergeCommit -q .mergeCommit.oid`. Then follow Landing a change, step 4. `main`'s branch protection (a pull request and a green `gate` check, and updates restricted to the bypass list; only the repository admin, the user, bypasses it, for the dispatcher's merges and the tracker's own pushes of tracker state) is the server's half of this gate. The conditions are still yours to check, because your credentials are the admin's; a dispatched agent's are not (Dispatch, the agent credential). Never use `--admin`, and never merge on red or missing CI, an unresolved review, or a stop condition. If any condition can't be met, leave the PR as it is, post a `BLOCKED:` comment saying which, and stop.

Observed criteria (human Studio playtests) do not block the merge. Put them in the final report and PR comment, and file any failure the human finds later as a defect issue.

## The PR is the visible record
The draft PR opened by `start` stays the live log of the raft. Every `./zn commit` pushes. In addition, comment on the PR (`gh pr comment`) when: a review starts (with the sha), a review file lands (verdict and findings by severity), a review is answered (the refute lines), an issue finishes, and on any `BLOCKED:` stop. Never sit on unpushed work, and never leave review files uncommitted. See zz-execute Phase 4.

## Spend (best effort, automatic)
Rows are only ever appended. A row has nine columns: when, commit, +lines, -lines, minutes, attribution, phase and tokens, and a tenth, model, once any row of the file records the model that spent its tokens (`--model <id>` on `spend` and `commit`; a file with no such row keeps nine columns, and a row with no model leaves the cell empty). The phase is one of `capture`, `prep`, `design-review`, `build`, `code-review` or `deliver`.
- `capture`: `./zn spend <issue> --phase capture` after `./zn land`, before the capture worktree is removed. No lines.
- `prep`: `./zn spend <issue> --phase prep` once, when the issue's design PR is opened, before anyone readies it. Lines are that branch's own `check.sh`, `acceptance/` and `experiments/` files.
- `design-review`: `./zn spend <issue> --phase design-review` for the reviewer's run and again for the answering time; z-raft's coherence review is `./zn spend <R-id> --phase design-review` (shared among the members). No lines. Design reviews live where they ran (the issue's folder, or the raft's for the coherence review), and `./zn metrics` rolls an issue's up to its raft through `raft:`.
- `build`: `./zn commit` (the default phase). Lines are the staged diff.
- `code-review`: `./zn commit --phase code-review`, including the reviewer's tokens when the harness reports them. Lines are the staged diff.
- `deliver`: `./zn commit --phase deliver`, `done`'s own commit, and `./zn spend <R-id> --phase deliver` after the merge. Lines are the staged diff, or none after the merge.
- **Lines**: the staged diff, excluding every project root, except the `prep` phase above. On the `done` commit, the promoted `tests/acceptance/` specs are also excluded, because they're prep work. Later edits to them, for example a defect fix, do count.
- **Attribution**:
  1. `--issue` flags if given;
  2. otherwise the current focus;
  3. otherwise every issue in the raft.
  With several issues, each file's lines go to the issue whose **Touched modules** lists that path; files nobody claims are split evenly.
- **Minutes**:
  - `--time <minutes>` when you actually know how long you worked on it. Prefer this.
  - Otherwise the wall-clock time since the previous commit, capped at 45 minutes.
  - With several issues, minutes are split in proportion to lines added.
- **Commit often**, at least once per issue and once per review round. Smaller commits mean more accurate attribution.

## Dispatch
`./zn dispatch` runs the pipeline headless and unattended. The rules are `z-nile/engine/dispatch.luau`'s; the stacked model files are `models.luau`'s.
- **What the guards are** (the user's "Keep same user, accept detection", 2026-10-21). Unattended agents run as the user's own OS user. Every guard below (the wrapper, the broker, the tripwire, the watermark and the merge gates) detects honest mistakes and casual misbehaviour; none is a security boundary against a determined agent, which can read the user's credentials, rewrite the watermark or the repository's configuration between runs, or merge with the user's token. Known limits are said where each guard is.
- **Steps.** Model steps: `z-ticket`, `z-design`, `z-raft`, `z-run` and `zz-review` (modes `design`, `raft`, `code`, `stream`). Script steps, which the dispatcher runs itself and never starts a model for: `z-ready` (`./zn ready`), `z-stop` (`./zn stop`), `raft-plan --apply`, `recombine`, `fold`, `release`, `spend` and `zz-stats` (`./zn metrics`). `zz-rules`, `zz-arch`, `zz-test`, `zz-execute` (z-run's protocol) and a project's skills are read inside a step and are never one; any other name is an error.
- **`.models.toml`.** At the repository root, and optionally closer to the work (a project's home, an issue's folder). It stacks like `.gitignore`: a closer file replaces only the keys it sets (`order` whole, each `[dispatch]` setting, each field of each `[<skill>.<cli>]` table). `order` is the CLI priority, top first; the supported CLIs are `claude`, `grok` and `agent` (Cursor), and a table naming any other is an error. Each `[<skill>.<cli>]` has `model`, `rank`, `runtime` and `max_tokens` (and optionally `effort`), and an `agent` table also `max_calls` and `max_minutes`: Cursor's `agent` reports no running token count, so its step stops after `max_calls` model calls (distinct `model_call_id`s, and each turn that carries none) and the spend row takes the result's real total; a stream with three turns in a row and no `model_call_id`, or a line it doesn't know, stops as `cap-unknown` (fail closed); calls are not tokens, so the user tunes it, and an `agent` table without it is an error, never unlimited (the user's "Cap model calls, record real total"); a call count can miss calls, so the step also stops (`cap`) after `max_minutes` of wall time; the runtime belongs to its CLI: `claude-cli` and `claude-cloud` (`claude --cloud`), `grok-cli` and `grok-bot` (`grok agent headless`), `cursor-cli` and `cursor-app` (`agent worker`). Nothing defaults: a skill no file names, a missing field, or no file at all is an error naming it. A step about one issue walks to that issue's folder; a step about a raft walks to each member's and takes, per CLI, the stronger spec whole (higher `rank`, then larger `max_tokens`), in the raft's own walk's order; z-ticket walks to the project's home. The `[dispatch]` settings (`auto_merge`, `stall_seconds`, `tool_seconds`) come from the item's own walk; an unset or unreadable `auto_merge` is none. Every file is read as committed on `main` (fetched once per run), never from the working tree: an uncommitted `.models.toml` on the walk is an error, so a new one takes effect once its PR has merged. A `.models.toml` is never tracker state: it changes only by a reviewed PR that a human merges (the broker and the gates refuse it; a step that wants an item-level spec asks in `questions.md`). `zz-review` follows the review rule: Opus (`claude-opus-…`) through `claude` and `agent`, `grok-4.7` at `effort = "xhigh"` through `grok`; any other is an error.
- **The agent credential** (the user's "Bot token, no bypass"). A model step runs with the agent's own GitHub token (a fine-grained token or a GitHub App's, read from `$ZN_AGENT_TOKEN_FILE`, else `~/.config/zn/agent-token`, else the keychain item `zn-dispatch-agent`); without one no CLI starts. It can push branches and open pull requests and can't merge, bypass `main`'s protection or write protection or rulesets. The step's `GH_TOKEN` and `GITHUB_TOKEN` are that token, gh reads an empty configuration folder of the step's own, and git's credential helpers answer with that token only. Not enforceable: the agent runs as the user, so a process that goes looking can still read the user's own credentials (the keychain, `~/.config/gh`); only a separate OS user would stop that, and the watermark and the server's protection are what catch its use.
- **Tracker state** has one definition (`z-nile/engine/trackerstate.luau`), which the wrapper, the broker, the tripwire, the watermark and the merge gates all use: git's raw diff with renames off (`diff-tree -r --raw --no-renames`), every path under a project root's folder (with the slash) or exactly `z-nile/next`, plain (ASCII, no empty, `.`, `..` or `.git` component), only regular files (no symlink, no submodule), no `.gitattributes`, `.gitmodules` or `.models.toml` in any case, no added path that differs only in case from another; and each item's sequestered files (its `check.sh` and `acceptance/`, in that exact case) judged per item: the same set, each unchanged or, when the item's folder moved, as `paths.rewrite` writes it for that move; only a new item adds them.
- **Tracker state from inside a step.** `./zn`'s pushes to `main` (`publish`, `land`) from inside a step go to the publish broker of the dispatcher that runs the step (a folder of that run's own, `ZN_PUBLISH_BROKER`, its requests bound by a run token): it pushes them with the user's credential, to origin's URL as the run pinned it at its start, only as a fast-forward of a freshly fetched `main`, never forced, and only when every commit is tracker state against its parent (as the watermark judges it). Nothing else in a step is meant to push to `main`.
- **Running a model step.** In the step's worktree (`prep-<slug>`, `raft-<id>`, the raft's own, `capture-zn-<n>`; a review in its author's), with a prompt that names the skill's file and the `./zn lessons --when <design|build> --full` command and pastes nothing. A supervisor starts the CLI in a process group of its own and holds a lifeline from the dispatcher: when the dispatcher dies, however it died, the group dies with it. The dispatcher kills the group when the running token count passes `max_tokens`, or for `agent` its call count passes `max_calls` or its wall time `max_minutes` (outcome `cap`), when the step prints nothing for `stall_seconds` (`tool_seconds` while a tool call runs) (`stalled`, or `quota` when the CLI's own last words were a wait for quota: a CLI never waits for quota, and the model's words never count), or on `./zn dispatch stop <id>` (`stopped`). A nested step (a review its author waits on as one shell command) writes a heartbeat in its parent's state folder while its CLI prints, and the parent counts a fresh beat as output; claude's maximum for one shell command (`BASH_MAX_TIMEOUT_MS`) is raised to two hours in its step's environment, its default left as it is, and the author passes a two-hour timeout on its review command alone. The nested runner beats once a second while it is alive and within its own limits, not only while its CLI prints, so a beat means "alive and within my limits". It moves down `order` only on quota, which only the CLI's own signals report (claude's rejected rate-limit event, an error result or line, stderr); any other failure stops. The count is input + cache writes + output, cache reads left out, for every CLI.
- **The watermark and the tripwire** (the user's "Persisted watermark", framed by "Keep same user, accept detection"). The dispatcher keeps the last commit of `main` it vetted where a well-behaved step never writes, and detects if it changes: `$ZN_WATERMARK_DIR`, else `$XDG_STATE_HOME/zn-dispatch`, else `~/.local/state/zn-dispatch`, then a folder named for the repository, file `main-seen`, with `origin-url` beside it; and it mirrors it in each item's `state.json`. At the start of every run, before every step and after every step, every commit of `main` since the watermark must be tracker state (as above) or a pull request's merge into `main` on GitHub. The file is shared by every dispatcher of the repository (and `vet`): it only moves forward, under a lock, and another run's advance is never a trip, because within a run the dispatcher vets from its own copy of the watermark, whatever the file says, so a step that deletes or rewrites the file is still caught by what it pushed. A missing watermark at a run's start is never trusted (only `./zn dispatch vet` writes one), one behind the item's mirror stops the next run, a diverged one trips, and so does origin's URL changed since the last run. After a step, origin's configuration (`remote.origin.*`, `url.*`) must be as the run pinned it, the main checkout's tracked and untracked files unchanged, its HEAD moved only forward along `main`. Anything else stops the chain (exit 5, outcome `tripwire`), with the step's spend still recorded, until the user looks and runs `./zn dispatch vet` (`--dry-run` lists each commit's verdict and writes nothing; plain `vet` lists them too). **Known limits:** this detects a late push after the fact, at the next run, and never prevents one; a process left behind can rewrite the watermark, its mirror and the URL file between runs; a merge made with the user's credential (stolen or not) is a pull request's merge and passes; an agent can run `vet` itself. They are the user's, by rule.
- **Spend.** The dispatcher records each step's session tokens and model id (with its effort: `grok-4.7-xhigh`): `spend <id> --phase <the step's phase> --tokens <n> --model <id> --note "dispatch <step>"` from the `zn-dispatch` worktree while the item is in the backlog, a reviewer's row under its review file's name (`design-review-NNN`), a code or stream review's as the `./zn commit … --phase code-review --tokens --model` line it prints for the author, and a run's as pending in `state.json` until the merge, when the next `./zn dispatch <R-id>` writes it as `deliver`. A step under the dispatcher records its own rows without `--tokens` for its session.
- **The chain.** `./zn dispatch <id>` (or `new "<description>"`) reads the item's state on `origin/main` after every step and never a model's prose: a new issue goes to z-design; its prep PR is the `prep` gate; a prepared raftless issue gets `raft-plan --apply` in `raft-<id>`, then z-raft; the rafting PR is the `raft` gate; a prepared raft gets `z-ready`; an active raft gets z-run until its PR leaves draft (`./zn done`), and that PR is the `run` gate, always a human's. Only the dispatcher merges: it passes a `prep` or `raft` gate itself, with the real `gh` and the user's credential, when `auto_merge` names it, the PR is green and mergeable, and its head (fetched from `refs/pull/<n>/head` and equal to the head GitHub reports) is the item's own tracker state by the one function, from its merge base with `main` (a prep PR: the issue's own folder, whose sequestered files it may change, and skill lessons; a rafting PR: only its own items' files, the raft it adds and that raft's members, never another item's sequestered files), pinned to the head it checked (`gh pr merge --squash --match-head-commit <head>`, so a push to the branch since voids it); otherwise it stops there (exit 4). It stops (exit 3) when a step wrote `questions.md` in its state folder (the user answers in that file and runs `./zn dispatch retry <id>`, which keeps it as `answered-<n>.md`), and (exit 1) when a step failed, was lost, or left a finding `./zn lessons --uncovered <id>` still lists after a review step (z-design, z-raft, z-run, zz-review). `--dry-run` prints the next action and the CLIs it would try, and starts and writes nothing.
- **Run state.** `.cache/dispatch/<id>/state.json` (the step, CLI, runtime, model, the running group and its lock, worktree, start, tokens, outcome, every attempt, the merges and broker pushes, pending rows), `questions.md`, and a folder `<step>-<mode>-<id>-<n>/` of its own for each step a step dispatched (a review from its author): ignored files in the main checkout. One dispatcher per item at a time (an flock that dies with its holder); a step whose dispatcher died is `lost`, never resumed, until `retry`. `./zn dispatch status <id>` prints every run, `stop <id>` kills each running group only while it is still that run (its supervisor still holds the run's lock; never a group id of 1 or less) and marks any other `lost`, `retry <id>` reruns the failed, stopped or lost step on the same order. The board (c0118) reads it.
- **The wrapper.** A model step's PATH starts with `z-nile/bin`, a convenience layer over the credential and the watermark: its `git` decides a push from git's own dry run (aliases, `-c` and refspecs resolved by git) against a private, freshly fetched copy of `main`, refuses anything but tracker state there, and refuses plumbing pushes; its `gh` allows only the skills' commands (no merge, however spelled or aliased) and `gh api` reads and comments. Both are bypassable by an absolute path; the watermark catches what they miss.
- **Inside a check.** A spec or `check.sh` that runs `./zn dispatch` may start only a CLI whose real path is under the checkout's `.cache` (a fake); any other is refused before it starts.

## Sync and claim
Tracker state is shared the moment it changes, not when a PR merges, so parallel terminals see each other's work.
- **Sync first.** Every skill that reads or changes tracker state starts with `./zn sync` (a merge of `origin/main` in a worktree, a fast-forward in the main checkout). Reviewers and stream agents never merge: they run `./zn sync --fetch`, which only updates `origin/main`, so the diff they judge does not move.
- **Statuses** (`status:` in an item's frontmatter): `new -> preparing -> prepared -> active -> done`. `design:` (draft, reviewed, ready) stays the design review's field. A missing `status:` is derived: `done/` is done, `active/` is active, `design: ready` is prepared, a draft item in a raft (or a draft raft) is preparing, anything else is new. `./zn status` lists them from `origin/main`; `status <id>` prints one; `status <id> <to>` moves one, checked against `origin/main`. `done` is only ever set by `./zn done`, and only `ready` (or the legacy `start` of a backlog raft) claims `active`, and `stop` gives a readied raft back.
- **Every write is stamped**: the stored value is `<state>-<three words>` (for example `preparing-quiet-copper-falcon`) and each write uses fresh words, so two terminals making the same move conflict in git instead of merging silently.
- **Published or carried.** These moves are pushed straight to `origin/main` as a tiny commit: `new issue` (the stub, `--desc "<line>"` is its Problem), `new raft` (claims the raft, and its members when they are `new`), `fold` and `recombine` (claim their rafts), `release`, `status <id> preparing|new`, `status <id> prepared` back from `active`, and the claim made by `ready` (or by a legacy `start`). An emergent `new issue --raft <R-id>` and `renumber <id>` without `<new>` push a counter-only commit (the raised `z-nile/next`) and then work locally. The move to `prepared` is **carried by the prep PR**: it only edits the local documents.
- **The direct-push exception.** Everything else lands by pull request. A published change is a tracker-only commit: only `<root>/(issues|rafts)/<ID>/<ID>.md` and `check.sh`, under a root that `origin/main`'s `z-nile/projects.toml` lists (never the working tree's), a `check.sh` only when it is created, an existing document only in its `status:` line (what `status`, `new raft` and `start` publish), an issue's `spend.md`, rows appended only (`./zn spend`), and `z-nile/next`, whose counters may only go up. The one other kind is a whole-directory move by `ready` or `stop`: every file of an item directory moves between the backlog and `active/` of its own root (never `done/`, never to another root), byte for byte, except the document's `status:` line and the item paths in `check.sh`, which `paths.rewrite` changes to the new directory; publish recomputes both and refuses anything else. `./zn land` also pushes a capture's edits to draft backlog issue documents (their sections, `title` and `depends_on`; design stays draft, every other frontmatter line unchanged) after a local full gate. Designs, reviews, code and acceptance specs never ride it. A commit that skips CI for the many tiny pushes is intended: `check.yml` ignores `pickman/.tracker/**`, `z-nile/.tracker/**` and `z-nile/next` on `push`, not on `pull_request` (`tracker/**` no more: a push that brings the retired root back runs the gate). CI runs one gate job per project, `gate (<project>)`, and branch protection requires each; adding a project means a registry entry, a CI matrix entry and a new required check (c0120).
- **Claims.** z-design claims one issue with `./zn status <id> preparing` and gives it back with `status <id> new`. The old prep's `new raft` over `new` issues still claims them with the raft's stamp, and `./zn status <R-id> preparing` claims an existing draft raft with its unprepared members. A raft move (`status <R-id> preparing|new`) never restamps a member that is `prepared` on `origin/main`, and refuses a member another raft holds there. `ready` (and a legacy `start`) refuses a raft unless it and its members are `prepared` on `origin/main`; the claim is made by `ready`, not `start`.
- **Rafting** (z-raft). An issue's raft is its own `raft:` line, edited only in the rafting PR: two PRs that raft one issue edit that one line, so the second cannot merge cleanly, and its sync shows the conflict. The published claim (`new raft` over prepared issues, `fold`, `recombine`, `status <R-id> preparing`) stamps the raft only, with a fresh `preparing-…` value; recombine gives its two rafts one value, and that shared stamp is what lets the carried `status <keeper> prepared` take a member whose `raft:` on `origin/main` still names the other raft. The carried move takes a member that is prepared on `origin/main` as it is, refuses one another raft holds there, and takes a `preparing` member only when it carries the raft's own stamp or a claim this checkout made (`status <id> preparing` here); any other `preparing` member is another terminal's live claim and is refused, naming it. z-design's `status <id> preparing` refuses an issue whose `raft:` names a raft on `origin/main` (z-raft takes it out first with `./zn unfold <R-id> <id>`), and `ready` refuses a raft while a member is `preparing`. A raft's `grouped:` line records a hash of each prepared member's design as z-raft grouped it (its document without `status:` and `raft:`, `check.sh`, `acceptance/`, and its design reviews, refutes and `harvest.md`); the carried move and `ready` refuse a member whose design changed on `origin/main` since (a redesign landed inside the rafting window), a member this rafting grouped with no entry, and a raft of several issues whose coherence reviews quote no `Grouped:` record covering the current one. `compact` and `renumber` re-record every entry that matched before they rewrote its ids. `./zn release <R-id>` is the published give-back. A conflict on `raft:` or `depends_on:` (they are adjacent lines) after a sync means rerun z-raft for that issue: take `main`'s line and drop the issue from your raft, or take both edits when it was only `depends_on:`.
- **A failed start.** `start` runs every local check before it claims. If a step after the claim fails (branch push, `gh pr create`), the local state is consistent: finish by hand (`git push -u origin <branch>`, `gh pr create --draft`), or give **your own** claim back with `status <R-id> prepared` (a raft started the legacy way, still in the backlog; a readied raft is given back only by `./zn stop <R-id>`). The same terminal can re-run `start` if it died before moving anything (it remembers the claim in `.cache/tracker-claim-<R-id>`); another terminal is refused.
- **Offline.** `PICKMAN_PUBLISH=0` (or a repository without `origin`) keeps every command local, as it was before. Publishing and every other command that changes a repository first check that git's repository root is the checkout the tracker lives in; read-only commands do not.
- **Giving back a readied raft.** `status` refuses any item in `active/` on `origin/main` ("<id> is readied (in active/): use ./zn stop <R>"); `./zn stop <R-id>` is the way to give back a readied raft, and it also gives back a raft claimed by the legacy `start`.
- **Whose claim.** A claim is not enforced against other terminals' give-backs (`stop` included): `status <R-id> prepared` from `active` (a legacy claim; a readied raft only through `stop`), `status <id> new` and `status <id> preparing` are open to anyone, so use them only for a claim that is yours (the user's decision: ownership is documented, not checked). `release` is the one give-back that checks: it needs the claim this checkout remembers, or `--force`. Never give back a claim you did not make; ask the user.
- **Cutover.** A prep that was open before this landed exists only on its branch, so nothing on `origin/main` knows its raft id or members. Land such preps first, and renumber on a clash (see Conflicts). Do not stamp their members with `status <id> preparing`: a stamped member of a raft that is not on `origin/main` cannot be moved to `prepared` and can never be started.

## Lessons
Before you start, read this skill's lessons: `./zn lessons --skill zz-rules --full`. Each is a mistake made before, with the question that catches it.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.
