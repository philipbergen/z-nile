# Testing (z-nile)

## Running tests
| command | use |
|---|---|
| `z-nile/check.sh` / `--affected` | while iterating: format, lint, types for src (Roblox definitions) and tests/scripts (Lune definitions), rojo build, and **only the affected specs** |
| `z-nile/check.sh --full` | every project's gate, every spec. Used by `land` and `setup.sh`, and by the merge's clean clone |
| `z-nile/check.sh --affected --fresh` | the affected gate without reuse |
| `pickman/check.sh [--full]` / `z-nile/check.sh --project <name>` | one project's gate: its static stages and its specs alone (each project has its own gate; no `--project` runs every project's). A home's `scripts/check.sh` runs that project's gate (c0120): `pickman/scripts/check.sh` pickman's, `z-nile/scripts/check.sh` z-nile's. The local full gate runs every project (`z-nile/check.sh --full` with no `--project`). GitHub Actions does not run it. |
| `z-nile/check.sh --plan` | print what each stage reads for each project, and run nothing |
| `lune run tests/run -- <spec files>` | specific specs, from the project's home: `z-nile/` for z-nile's, `pickman/` for pickman's (`cd pickman && lune run tests/run -- tests/unit/Maze`). The runner refuses any other folder: the repository root belongs to no project |
| `lune run z-nile/affected -- [--base REF] [files…]` | show which specs a change selects (`ALL` = full run) |
| `./zn check <id>` | an item's acceptance checks |
| `lune run tests/run -- --jobs N` / `PICKMAN_JOBS=N` | spec concurrency (default `min(max(cpus,2),8)`; `1` is serial, a bad value exits 2) |

**Gate by step**: the full gate runs once, at the merge; every step before it runs `--affected`, `./zn done` included. `land`, `setup.sh` and the merge's clean clone run `--full` fresh.

| step | gate |
|---|---|
| zz-execute Phase 0 | none (a red `main` first shows at the merge) |
| Phase 2 iterations, stream checks, the raft's RC0, Phase 3, Phase 4 step 1, zz-review code mode, Phase 5 step 2, the pre-PR gate | `--affected` (RC0 scoped `--project <project>`) |
| `./zn done` | `--affected` on the done tree |
| `./zn land`, `setup.sh`, zz-rules Merging steps 2 and 4 (the clean clone) | `--full`, every spec, fresh |
| a red merge gate | BLOCKED: failing specs named, a graph-miss chore for each spec the affected selection did not list |

## Spec layout (`*.spec.luau`)
Each project's specs live under its home and run from it (c0120): z-nile's (the tooling's) under `z-nile/tests/`, pickman's (the game's) under `pickman/tests/`, with each home's `.luaurc` pointing `@tests` at its own `tests/` (and pickman's `@logic`, `@shared` and `@scripts` at pickman's folders). There is no `tests/` at the root. The rows below are relative to the home. The runner, `z-nile/tests/run.luau`, is shared: `pickman/tests/run.luau` runs it from `pickman/`, so a pickman spec's paths, fixtures (`pickman/.cache`) and jail are pickman's, and a z-nile spec's are `z-nile/`'s (`z-nile/.cache`). A spec that needs the repository's other files reads them from the checkout's top (`git rev-parse --show-toplevel`), and writes only under its home's `.cache`. The assertions (`z-nile/tests/lib/t`) and `renamed` are shared too (`pickman/tests/lib/` re-exports them); `sim`, `place`, `fakeengine` and `plain` are pickman's; `place` re-exports the shared harness's (`z-nile/tests/lib/place.luau`, c0185), which reads its script roots from the project file, as every home's `tests/lib/place.luau` does. A project's own tiers (pickman's `tests/unit`, `helper`, `contract`, `integration`, `scenario`, `place` and `runtime`, its `sim`, `place`, `fakeengine` and `plain` helpers) are in that project's own skill: `pickman-test` for pickman. The rows below are those every project has. Every project with a home except z-nile has the same `tests/run.luau`, `tests/lib/t.luau` and `renamed.luau`, `tests/meta/architecture.spec.luau`, `fence.spec.luau` and `home.spec.luau` (z-nile/README.md, A project's home), and the same place tier: `tests/lib/place.luau` and `tests/place/library.spec.luau`, which build the home's place and judge it. A spec that loads the place requires it as `@tests/lib/place`, never the shared file, so the selector knows which home's place it loads.
| dir | tier | may require |
|---|---|---|
| `tests/tooling/` (z-nile's) | the tooling's scripts (`z-nile/`, the root's `scripts/`) | scripts |
| `tests/acceptance/<id>/` | acceptance specs promoted by `./zn done`, in the item's project's home (`pickman/tests/acceptance/<id>` for pickman's, `z-nile/tests/acceptance/<id>` for z-nile's). Never edit these; if one is wrong, file a chore (test fixes are always chores) | anything, via aliases |
| `tests/meta/` | the structural rules: pickman's from the pickman-arch skill (`pickman/tests/meta/`), the tooling's (`z-nile/tests/meta/`) | the graph library |

The assertions are `toBe`, `toEqual` (deep), `toBeNear`, `toBeTruthy` and `toThrow(pattern?)`.

**Good specs**:
- **Deterministic**: no wall-clock time and no unseeded randomness. Pass `dt` and a seeded RNG instead. The one timing exception is `sim.bench` budgets (pickman-test skill, Simulations).
- **One behavior per case**, with a name that states it.
- **Assert on public API results**, never on internals.
- **Survive a compaction** (`./zn compact` renumbers every item): a spec that pins a real tracker item maps its id through `tests/lib/renamed.luau` (`renamed.id("R0010")`), and test data that names a `tests/acceptance/<id>` path spells it in two parts (`"tests/" .. "acceptance/"`), or the compaction rewrites it.
- **Hard to fake.** An acceptance spec must fail for plausible wrong implementations: an off-by-one, a missing edge case, a hard-coded value. Include at least one case that a hard-coded or partial implementation would fail.
- **No browsers.** `tests/run` puts recording `open` and `xdg-open` stubs first on `PATH` for the whole run (workers and nested runners included, through `PICKMAN_OPEN_GUARD`) and fails the run if any is called. Run `./zn board` with `-O`; a spec that tests opening puts its own stubs first on `PATH`. A spec that sets `PATH` for a child prepends to it, never replaces it, or the guard's stubs are lost.

## Affected selection
`z-nile/affected.luau` builds the static require graph of `src/` and `tests/`. It selects every spec whose transitive requires include a changed file.
- **Full run**: changes to the shared runner and harness (`z-nile/tests/run.luau`, `z-nile/tests/lib`), z-nile's libraries (`z-nile/lib/`), `./zn`, the root's `scripts/` or a root config file (`.luaurc`, `rokit.toml`, `selene.toml`, `stylua.toml`) force one of every project; a change to a project's own `tests/lib`, `tests/run.luau`, `tests/meta`, `scripts/`, `.luaurc` or any `*.project.json` (under its home) forces that project's, and any other change under `z-nile/` (the engine, the gate) z-nile's. A change at an old place (the root's `tests/`, `tracker/`, `src/`, the root's project files) forces z-nile's, whose old-roots check then fails. A spec that loads a home's place (it requires the home's `tests/lib/place.luau`) is selected for every change to what the place is built from: the home's project files and every `$path` they map, so a change under `arcade/src/` selects the place specs of every game that maps the library, and the unit specs that require it through `@arcade` follow from their requires. Verify an arcade change against its dependents with `z-nile/check.sh --affected` (every project), not `arcade/check.sh --affected` (the library's own specs). `lune run z-nile/affected -- --project <name>` prints one project's selection, relative to its home.
- **Reliability** depends on the architecture rules: literal requires, and features used only through `init`. `tests/meta` enforces those rules.
- **Reuse**: in an affected run, a spec file whose fingerprint (its own content, everything it can reach, the tools and the gate mode) already passed is skipped and reported `reused <spec>`, and a whole affected gate that passed on the same content is skipped with its stored static report. `--fresh` reuses nothing and `--full` runs every spec. Passes are kept in `.claude/.znile_tests.sqlite`; deleting it only costs reruns.
- **Declared inputs**: a spec that reads files or git state outside its requires declares them in its home's `tests/inputs.tsv`, one `<spec>\t<file, folder/, *, or ref:refs/...>` line each; `*` covers every blob plus HEAD and `ref:` adds one named ref. A path under a project root is allowed only below it, never the root itself or a `spend.md`. A spec that reads the files of every registered project (it loops the registry, itself or through a spec, wrapper or helper it runs) declares `*`, or, when it takes over 2 s idle, a line for each registered project; registering a project adds those lines.
- **Graph miss**: a spec fails under `--full` but wasn't selected for the same diff. That's a selector bug. File it as a chore, since CI and test bugs are always chores: `./zn new issue c affected-graph-miss-… --project z-nile`.

## Acceptance checks (`check.sh`)
Every issue and raft has a `check.sh` that uses `z-nile/lib/ac.sh`:
```bash
HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd -P)" # physical: tests/run strips the physical cwd
source "$(git -C "$HERE" rev-parse --show-toplevel)/z-nile/lib/ac.sh" # cds to the item's project home
A="$HERE/acceptance" # sequestered specs: here before `./zn done`, promoted after it
[[ -d $A ]] || A="$PWD/tests/acceptance/<id>"
check "AC1: ghosts never reverse outside mode changes" lune run tests/run -- "$A/reverse.spec.luau"
check "AC2: Logic stays engine-free" lune run tests/run -- tests/meta/architecture.spec.luau
finish
```
- **Runs from its project's home** (c0120): `ac.sh` changes to the home of the project whose root holds the `check.sh` (`lune run z-nile/roots -- --projects`): `pickman/` for pickman's, `z-nile/` for z-nile's, so `src/…`, `tests/…`, `scripts/…` and git pathspecs mean that project's files. A `check.sh` under a `.tracker/` folder that no project's root holds refuses to run. `$ZN_ROOT` is the repository root (`"$ZN_ROOT/zn" members R0010`, `"$ZN_ROOT/z-nile/check.sh" --full`). The fence is the root's; the specs it starts run in the home's jail.
- **Must run after promotion**: a `check.sh` is re-runnable once `./zn done` has moved its specs, which is what the fallback line is for. `AC_LIST=1 bash <check.sh>` lists a script's checks (`LIST  <label>`) without running them and ends with `n criteria listed (none run)`; `tests/run`, `./zn check` and `./zn done` refuse to run while `AC_LIST` is set.
- Work outside `check` is limited to running a spec through `tests/run` (which list mode refuses), `./zn members` and other cheap reads; everything else goes inside `check`.
- **Every literal path resolves from its home** (a standing rule since c0120's `check-paths` spec is promoted, c0120 code review 005 F7): every literal path an unfinished item's `check.sh` names must exist from its project's home, or lie under the item's (or its raft's members') Touched modules, which the work creates. Otherwise z-nile's gate goes red on the prep's PR. A path a `depends_on` item will create, and is not done yet, is named through `$ZN_ROOT` or created inside `check`. The exempt files are the four restamped ones c0120 lists by blob (R0030, c0083, R0039, c0075); each leaves the list when its re-prep changes its text.
- **One `check` per Checked criterion.** The label starts with the AC number from the document.
- **Exit criteria**: a raft's `check.sh` runs its project's gate (`"$ZN_ROOT/z-nile/check.sh" --project <project> --affected`), then every member's `check.sh`, then the raft's own RCn checks. A project's gate proves that project alone (c0120): A game raft's `done` does not prove z-nile is green; the merger's `z-nile/check.sh --full` does, because it runs every project.
- **Commands**: checks may run any deterministic command, such as a spec, a `lune run` script, `rojo build`, or a `grep` that must match nothing.
- **Where acceptance specs live**: z-design writes them in the issue's `acceptance/` folder (`<root>/issues/<id>/acceptance/*.spec.luau`, under the issue's project root), **not** in `tests/`.
  - They target code that doesn't exist yet, so putting them in `tests/` would turn main red.
  - They're formatted and linted, but not type-checked or run by the repo gate. Only `check.sh` runs them, by explicit path.
  - They must require only through aliases (`@logic/…`, `@tests/…`, `@scripts/…`), never relative paths, because they get moved.
  - Never write literal `require("…")` text inside strings or comments. The graph scanner would treat it as a real require. Build such text by concatenation.
  - `./zn done` **moves** them to `tests/acceptance/<id>/` in the item's project's home (`pickman/tests/acceptance/<id>/` for pickman's, `z-nile/tests/acceptance/<id>/` for z-nile's), where they become permanent regression specs. It then type-checks that project's `tests/`, runs its `tests/meta` and the promoted specs from its home, and **rolls back** if any of that fails.
- **Sequestered**:
  - `check.sh` files and the acceptance specs they name are written in z-design, *before* execution.
  - During execution they must not change. The one exception is a move of the repository's layout that the user decides on, for **finished** items' `check.sh` files only: the move's raft rewrites the paths it breaks in them, so they still resolve from their home (c0114 for its moves, c0120 for the homes), in an edits commit, never a renames-only one, and its sequestration check compares each finished file with its text before the move, rewritten.
  - The code reviewer checks them with `git diff --find-renames=100% --name-status origin/main...HEAD -- 'tracker/**/check.sh' 'tracker/**/acceptance/**' '*/.tracker/**/check.sh' '*/.tracker/**/acceptance/**'`, which must list only `R100` renames (zz-review skill, Code mode item 2).
  - If one is actually wrong, the executor stops and escalates; it doesn't patch it.

## Criteria tiers (in each issue document)
- **Checked**: deterministic and in `check.sh`. Nearly everything belongs here.
- **Judged**: genuinely subjective, with a written rubric. The adversarial code reviewer gives a pass/fail ruling in `review-NNN.md`.
- **Observed**: the minimum set of Studio playtest steps for the human.

If something could be expressed as a measurable proxy, it's not Judged or Observed. For example, "ghost pursuit feels fair" can become "an idle player is caught within 6–12 s across 20 seeds".

## Speed
A standing rule, not a one-off. Tests and checks run very often, so they must run **concurrently** and as swiftly as possible.
- **What exists**: `z-nile/lib/par.sh` runs the independent static stages together (`par_start` / `par_wait`: buffered, timed, reported in start order); `tests/run` runs spec files in concurrent workers (`--jobs N`, `PICKMAN_JOBS`), slowest first by the durations it records in the home's `.cache/spec-durations.tsv` (files with no recorded time first, ties by path; c0154), so a long spec no longer starts late and holds the gate open at the end; the report stays in path order, and a run in-process (`--jobs 1`, one file) neither reads nor writes the record. `PICKMAN_JOBS=1` restores serial runs when you suspect an ordering bug.
- **Monitor continuously**: every gate run prints per-stage times, a `slowest:` line and `gate wall time:`, and whoever runs it looks at them. A stage or spec that dominates, or a time that creeps up between runs, is a gate defect: **optimise** it now if it is in your Touched modules, otherwise file a chore (`./zn new issue c gate-slow-<what> --project z-nile`). Never add a serial dependency between stages without a reason.
- **Writing specs for speed**: no wall-clock assertions and no fixed sleeps to let something finish (a bounded poll or rendezvous with a timeout is fine). Shell-heavy fixtures own a unique `.cache/<name>` (a literal `.cache/<dir>` in two spec files under `tests/` fails the gate, a mere mention counts, and `sim` is exempt). No shared mutable state across spec files. Prefer in-process Logic specs, and split or stub a spec that takes more than about a second. Two suites in one checkout queue on the runner's lock; separate worktrees run in parallel (see "Specs never touch the real repository").

## Specs never touch the real repository
On 2026-09-30 two suites in one worktree deleted each other's fixtures. Fixture git commands then ran in the real repository, removed `origin` for every session, and committed an agent's work onto a fixture branch. While these guards were being built, a spec run against the unguarded runner did it again: it rewrote the shared identity and committed onto a branch. So the repository a check runs in is off limits to every spec, `check.sh` and script a check runs.
- **Protected**: the main checkout, every worktree of it, and the git directory they share (config, refs and branches, HEADs and indexes, the worktree registry, objects, and every file), and the person's own git configuration (`~/.gitconfig`, `~/.config/git`). **Allowed writers**: each project home's `.cache/` (`pickman/.cache/`, `z-nile/.cache/`: fixtures and build output) and the root's `.cache/` (the board, the root fence's sentinel), the gate's `pickman/sourcemap.json`, and the transient copies that `./zn promote-check` makes in each member's project's `<home>/tests/acceptance/` and removes before it exits, and the gate's results db (`.claude/.znile_tests.sqlite` in the main checkout, written by `z-nile/specs` outside the jail). The last three are written by `check.sh` files and the orchestrator, never by specs.
- **Fixtures**: anything a spec changes lives under `.cache/<name>` in its home (`z-nile/.cache/<name>` for z-nile's specs), unique to the spec file, in a repository of its own (`git init`, or a `--no-hardlinks` clone through `@tests/lib/clone`). Fixtures commit as `<name>@example.invalid` (`-c user.name=… -c user.email=…`, or local config in the fixture), and never write an identity anywhere else. Run git and `./zn` in a fixture only through `@tests/lib/fixture` (`fixture.git`, `fixture.exec`): it refuses, before anything runs, a directory that isn't a fixture repository under this run's `.cache` (if the fixture's repository were missing, git would find the real one) and anything that points git elsewhere (`-C`, `--git-dir`, `--work-tree`, or a git-directory variable in `env`). Raw git only for `rev-parse`, `ls-files`, and `init` or `clone` to a named path; no shell strings (`sh -c`), no `process.create`. `retrofit.spec` keeps the twelve older fixture specs on the helper. Written before it and not converted yet: c0510's specs (R0200), and c0640's and c0650's, which check each fixture themselves; convert them when they are next edited. Against the real repository, only read: `rev-parse`, `ls-files`, `ls-tree`, `show`, `log`, `diff`, `cat-file`, `for-each-ref`, and cloning *from* it.
- **Enforced at run time** for every spec, by `tests/run` (`z-nile/tests/lib/fence.luau`, `z-nile/lib/fence.sh`):
  - **Jail (macOS)**: specs run under `sandbox-exec`. The kernel denies every write to the checkout, the main checkout, their shared git directory, every repository an outer guard protects (a copy of the tree under `.cache` runs its own gate), and the person's git configuration, except this checkout's `.cache`. In fact it denies every write outside this checkout's `.cache` (but not the `.cache` entry itself, which must stay a plain folder: the runner and `fence.sh` refuse a symlinked one), the run's own temp folder (a fresh `pickman-run.*` under the shell's temp folder, given to specs as `TMPDIR`, with a `mktemp` that uses it, and removed after the run) and `/dev`. Every other temp folder (`/tmp`, the user temp folder) is closed, because programs outside the jail run and copy files from them. `fence.sh` never deletes recursively. Also closed: the folders above the repository (none can be renamed away, written and renamed back), and the person's home (tools such as the runner itself, shell start-up files, settings, launch agents, which all run later without the jail). It also denies IP networking except loopback, so a spec's `-c protocol.allow=always` reaches nothing while local test servers work; specs also run with no proxy and with `GIT_ALLOW_PROTOCOL=file`. An outer sandbox is accepted only if probes show it closes all of that too. It must still let the root's `.cache` and every project home's `.cache` be written: a run from a home writes the root's sentinel before it enters the jail, and a `check.sh` writes its home's (c0120). It must also let every project home's `.cache` be written (`pickman/.cache` as well as the root's): the home fence waives a refused sentinel only under the runner's own jail, never on an outer sandbox's label, so where an outer sandbox closes a home's `.cache`, a `check.sh` run there (c0034's list mode) refuses, failing closed (c0120). Nothing a spec does can change the repository: git in any form, a plain file write, a missing fixture. A run that can't be jailed refuses to start, before any spec runs, unless it proves by probes that it can't write the repository (an outer sandbox denies it), or that it is a fixture of a jailed outer run (an outer guard's repositories are unwritable from it, and it lies under that checkout's `.cache`; an ancestor in `GIT_CEILING_DIRECTORIES` proves nothing). Runs can't be jailed inside another sandbox, which macOS can't nest, or without `sandbox-exec`. So in a sandboxed agent shell, run specs with that sandbox off. `PICKMAN_TEST_JAIL` says which applies, and the gate's jail case probes the same writes.
    - **Signals**: specs can signal (and probe with `kill -0`) only processes of their own sandbox (`(allow signal (target same-sandbox))`): never the runner's top process, its launcher or the watchdog. `fence.alive` counts a refused probe as alive only where signals are confined: in the jail, and in an outer sandbox (Claude Code's own allows signals only within it).
    - **Symlinks at the top of `.cache`**: specs can't create one there, but can still swap one in for an existing file (c0077 E1). The runner unlinks every link found there (never following it) before the run, after it (in the launcher, after the specs' group is killed, so a Ctrl-C doesn't skip it, and again in the top process), and `z-nile/check.sh` does so at its start, before it writes there. An outer sandbox's link probe uses a fresh random name and counts only `Operation not permitted` as a refusal.
    - **Writers**: every line in `scripts/`, `z-nile/` or a home's `scripts/` that names a `.cache` path is on the reviewed list in `z-nile/tests/lib/cachepaths.luau` (`cachepaths.ALLOWED`), with how it writes safely; the gate fails on an unlisted or stale line. Writers there replace by rename, never write through: `z-nile/lib/replace-file.pl <dest> [<src>]` (a sibling temp file opened `O_CREAT|O_EXCL|O_NOFOLLOW`, then `rename(2)`, which replaces a link of any kind and refuses a real directory), used by `sh.writeReplacing`; `fence.sh`'s sentinel uses an inline `rename(2)`, because fixtures copy `fence.sh` alone. A writer of a whole directory tree (a scratch worktree, say) never works at a fixed name under `.cache`: it uses a fresh `mktemp -d` outside it, as `./zn remap` does. The list covers `scripts/` and `z-nile/` only: a write through a listed variable, or a write from the runner (`tests/lib`), is review's to catch.
    - **Watchdog**: the launcher runs the specs in a process group of their own with a watchdog in it that waits on a pipe only the launcher holds open, so if the launcher dies, however it died, the watchdog stops the specs' group.
    - **Sweeper**: the jail's root is a sweeper (`fence.SWEEPER`): after the specs end it stops every process of the sandbox it can signal, whatever session or group it moved to, except its own ancestors, and says how many. Its interlock refuses to sweep (exit 70) unless a signal to its parent, the launcher (outside the jail, alive until the sweep is done), is refused, so an interrupted run (Ctrl-C) is still swept. Its interlock sweeps only on macOS; an explicit pid (for specs) only inside a jailed spec run; and a test seam (`PICKMAN_SWEEP_ONLY`) that can't be read refuses instead of widening the sweep. A spec can kill the sweeper (same sandbox); the run then fails ("the jail's sweeper was killed"). A spec can also stop it (SIGSTOP): the run then hangs until the launcher is SIGKILLed, which skips the sweep. A SIGKILL of the launcher itself skips the sweep and the launcher's unlink.
    - **pids**: the sweep covers pids up to 99999, macOS's `PID_MAX`.
  - **Fence**: git never looks above `<checkout>/.cache` for a repository, and a sentinel `.cache/.git` makes git fail in `.cache` itself. A fixture whose repository is missing is an error, never the checkout. The same holds for every project home a check runs in (c0120): a spec run from `pickman/` is fenced at `pickman/.cache`, and `ac.sh` fences a home before a `check.sh` runs there with `fence.sh`'s `pickman_home_fence`, in this order (review 002 F1): its `.cache` joins the ceiling (environment only, can't fail); a `.cache` that is a symlink or a file, or a sentinel that is a folder, refuses, in every mode, spec runs and the jail included; the git and spec guards are set whole (the one refusal, no ref-guard hooks, comes before any change, so a refused fence leaves the inherited guards as they were); then the sentinel is written. The sentinel is skipped in exactly one case: its write fails while all three of the runner's jail markers are set (`PICKMAN_TEST_JAIL=sandbox-exec`, `PICKMAN_FENCE_SPECS=1`, `PICKMAN_TEST_FENCE`) and the home's `.cache` lies outside the run's own `.cache`, the one place the jail lets a spec write. The jail then refuses every write there, the fence says so on stderr, and the ceiling and every other guard hold. Any other failed write refuses, spec runs included.
  - **Overrides stripped**: an inherited `GIT_DIR`, `GIT_INDEX_FILE` or the like (git hooks run with them set) is unset before any spec runs. The guards read the repository they protect (`fence.sh`'s `real`, `pickman_guarded`, the runner's tripwire and protected paths) through a clean read, with every such override **and the inherited ceiling** removed for that read only (a ceiling at the checkout's root would hide the checkout from a project home; the specs keep the fence's ceiling). A read that finds no repository refuses, in every mode: it never means "nothing to protect" (c0120 code review 002).
  - **Ref guard**: every git a check runs has a `reference-transaction` hook (`z-nile/lib/git-hooks/`) that refuses any ref update in the real repository. Only a `check.sh` flow started outside any spec run may fetch (create or move refs under `refs/remotes/`). On Linux this is what stops a commit, branch, switch or reset there. It refuses the ref change, but those commands may already have rewritten the index or the working files. The hooks are set only where there is no jail (Linux, `check.sh` files, runs nested inside a jail): under the jail the kernel covers it, and a hook in every fixture commit would cost a slow process start. Where they are set, they then run the repository's own hook of the same name, so a fixture's hooks behave as without the guards.
  - **No network for specs**: a `pre-push` hook refuses pushes into the real repository by any local URL. During spec runs it allows a push only into an existing local repository that isn't protected, so https, ssh, `host:path` and ssh aliases are all refused. With or without hooks, spec runs also allow git no network transport at all (`protocol.allow=never`, local paths and `file://` only), however a URL is spelled or aliased. Specs also get no credentials: `GH_TOKEN` and the like are unset, `GH_CONFIG_DIR` is empty, the git credential helper list is reset (no keychain), and there is no ssh agent and no ssh. A `check.sh` started from inside a spec run keeps these limits.
  - **No publishing from checks**: a tracker command run by a check never publishes tracker state: the publisher asks `pickman_guarded` (`z-nile/lib/fence.sh`), says `not publishing`, and goes on as with `PICKMAN_PUBLISH=0`.
  - **Lock**: one run at a time per checkout and home (`<home>/.cache/tests-run.lock`), because runs share that `.cache`'s fixtures; each home's run has its own `.cache`, lock and jail (c0120), so pickman's may run beside z-nile's. Separate worktrees still run in parallel. A second run prints `waiting for another test run (pid N)` and waits up to `PICKMAN_TEST_LOCK_WAIT` seconds (default 240). A lock is taken over when no process it records still holds it: each is gone, or is a reused pid, whose start id differs from the one recorded with it (a worker's `pid-<n>` holds its id, the top process's is in `start-<pid>`; the id is the kernel's start record, read through perl, inside the jail too, never from the clock). A live pid with no recorded start id (a lock from an older runner) or whose start id can't be read still holds.
  - **Tripwire**: a run refuses to start while the repository's identity is a fixture's. It fails with `REPOSITORY CHANGED`, even when every case passed, if any of these happened during it:
    - remote, core or user config changed (gh's `gh-resolved` aside);
    - this checkout switched branch;
    - its HEAD lost history or gained commits a fixture wrote;
    - a worktree appeared under `.cache`;
    - a ref whose tip a fixture identity wrote appeared.
  - **Gate spec**: `tests/tooling/repo-fence.spec.luau` proves in every gate that the guards are on, the jail included (harmless probe writes outside `.cache` must fail). It scans what runs as a check (the root's `scripts/`, every registered project's home, `z-nile/`'s included, `./zn` and every `check.sh`; a prepared acceptance spec once it is promoted into `tests/`), case-insensitively. It fails if any of them names a way to switch the guards off (`GIT_CEILING_DIRECTORIES`, `GIT_DIR`, `GIT_CONFIG_*`, `core.hooksPath`, `--no-verify`, `sandbox-exec`, `env -i`, `osascript`, `launchctl`, and the network and credential settings `protocol.*allow`, `credential.*`, `extraheader`, `GIT_SSH_COMMAND`, …), or commits as anything but `@example.invalid` (in `user.email` or an `*_EMAIL` variable). Extensionless files (hooks, tools) are read too; the guards themselves (`z-nile/lib/git-hooks/`, `fence.sh`, `fence.luau`) are exempt. A file with a real need to name one (a fixture hook that unsets what git exports to it, the fixture helper that refuses them) gets an entry in the spec's `ALLOWED` table: that file, those names only, and the reason. The review checks every entry.
- **`check.sh` files** get the fence, the override stripping and the ref and push guards through `ac.sh`, but no jail: they legitimately write the checkout (`sourcemap.json`, `promote-check`) The specs they start are jailed.
- **Caught only by review** (the zz-review skill's Repository safety item; each is **high**):
  - **The orchestrator**: `z-nile/specs` runs unjailed and reads back files a jailed spec can write (the results file, the no-record marker): it checks every field and formats every number that reaches SQL, and review checks that no new read-back skips that.
  - **Linux**: specs there are unjailed, so a write to the real checkout's index or files (`git add`, `checkout`, `reset --hard`, `worktree remove`, `remote set-url`, a plain file write) is stopped by nothing. GitHub Actions does not run the specs. The same spec runs on developers' Macs, where the jail stops it.
  - **`check.sh` files' own commands**: anything they run outside `tests/run`, including config writes and network actions.
  - **Handing work to a process outside the jail**: `open`, `osascript`, `launchctl`, or a daemon. The gate scan flags `osascript` and `launchctl`.
  - **Starting a model CLI** (`claude`, `grok`, `agent`): `./zn dispatch` refuses, inside a check, any CLI whose real path is not under the checkout's `.cache` (a spec puts its fakes there), but a spec or `check.sh` that starts one any other way spends real tokens with auto-approve; the CLIs sign in from `~/.claude`, `~/.grok/auth.json` and `~/.cursor`, which the fence does not strip, and off macOS (no jail, so no no-network rule) nothing stops them.
  - **A process that leaves the run's process group** (`setsid`, a double fork into a new session) survives **only where specs aren't jailed** (Linux, a run inside an outer sandbox): there the runner stops only what is left in the specs' group. It then outlives the run and could change files in `.cache` that an unjailed `check.sh` later copies and runs (a copy of the tree under `.cache`). Under the jail the sweeper stops it.
  - **Unjailed runs can signal the runner** (Linux, an outer sandbox): nothing refuses a spec's signal to the top process, the launcher or the watchdog there.
  - **A pid above 99999**: the sweep doesn't reach it, should a future macOS raise `PID_MAX`.
  - **The guards trust their own environment**: a caller that sets `PICKMAN_TEST_JAIL`, `PICKMAN_FENCE_SPECS` and `PICKMAN_TEST_FENCE` as the jail does makes the home fence waive a sentinel it couldn't write (a `.cache` made unwritable outside any jail), and `PICKMAN_FENCE_HOOKS` at a folder of permissive hooks switches the ref guard off (captured as c0123). Nothing in the fence tells a real jail from forged markers (c0120 code review 004 F5): review a check or spec that sets any `PICKMAN_TEST_*` or `PICKMAN_FENCE_*` variable.
  - **AC18 trusts the `origin` it resolves** (c0120): it reads the published main with `git ls-remote origin`, so a swapped `origin` URL, a `url.*.insteadOf` or `GIT_CONFIG_*` in the environment can make any repository's main the reference. Every verdict prints the URL it resolved; check it names the project's GitHub repository (c0120 code review 009 F4).
- **Running specs against unguarded code**: only in a clone under `$TMPDIR`, outside every repository (`git clone --no-hardlinks . "$(mktemp -d)/repo"`). That applies when prototyping the guards themselves, or on a branch from before them. A broken fixture there can only reach the clone.
- **If the tripwire fires**, or the shared remotes, branches, worktrees or identity look wrong: stop, post `BLOCKED:` with the output, and never repair the shared repository yourself. Every worktree and session shares it.

## Hooks (Claude Code only)
- After every `.luau` edit: stylua formats the file and selene lints it.
- Before every Bash or Monitor call (PreToolUse, `scripts/hooks/pre-bash.sh`): an interpreter with no time limit, inline Python that loops or starts an untimed process, a `while`/`until` loop, a follow (`tail -f`, `watch`), a job started with `&` and not waited for, and a background call with anything unbounded in it, are refused, naming the wrapper.
- At the end of a session (SessionEnd, `scripts/hooks/session-end.sh`): `./zn reap --session-end` stops what the session left running.
- On stop: the project-scoped affected gate (`--affected --project <name>`) runs when `z-nile/specs scope` names one project, and the unscoped affected gate runs for every other answer (`ALL`, any other output, a failure, a tree with no `z-nile/specs`; through the old gate path's forwarder, so a worktree from before c0114 still runs its own gate), if a file outside every registry root changed under `src/`, `tests/`, `z-nile/` or the home of a registered project (c0184: `pickman/`, `snake/`, and the rest, from the registry; a registry that does not parse gates every change).

## Lessons
Before you start, read this skill's lessons: `./zn lessons --skill zz-test --full`. Each is a mistake made before, with the question that catches it.

A new lesson (from a review finding, a correction by the user, or a step that failed in a way a rule would have prevented) is handled by your role, not by the skill you are reading:
- **A subagent** (a stream, a reviewer, any agent working from a brief) never writes a lesson file or runs `./zn new`. It puts the candidate (the rule, why, and the question that catches it) in its review or final report.
- **The lead of a prep or raft** writes it in `<skills folder>/<the skill the lesson improves>/lessons/<slug>.md` (the real folder: `z-nile/skills/` for z-nile's skills, `<project>/skills/` for a project's, never through a `.claude/skills/` link, which git can't add through; format: zz-rules skill, Items), and records where it came from in its own `harvest.md`: review findings through the harvest (z-design step 5.3, zz-execute Phase 4 step 5), and anything else (a subagent's candidate, a correction by the user, a failed step) as `- note <what happened>: <lesson ids>`. It adds a note to an existing lesson when one fits, writes a new file only when none does, and commits both with its work.
- **Any other lead** (in the main checkout, a capture, or a metrics report) captures it: `./zn new issue c lesson-<slug> --project z-nile --desc "<skill>: <the rule>, because <what happened>; check: <the question>"` (z-ticket skill). The prep that takes the issue writes the file.

## Bounded commands
Run every probe, experiment, loop and background command you start yourself (anything that is not the gate, a check, a `./zn` command or the spec runner) through `./zn run --time <seconds> -- <command>`: it stops at its limit, when it ends and when you do.
- A `/clear` ends the background commands of the conversation it clears (the SessionEnd hook stops its tool shells).
- A subagent stays open while its background commands run, and a command it started stops at its own `./zn run` limit (at most an hour) or at the session's end; the session-end reaper catches anything left.
- `./zn run [--time S] [--cpu S] -- <command>` (`z-nile/lib/bounded.pl`, which needs `z-nile/lib/cpu.sh` beside it; started before the engine, also callable as `perl <checkout>/z-nile/lib/bounded.pl`): process group, `--time` wall-clock limit (default 60, at most 3600), `--cpu` CPU limit by `ulimit -t` (SIGXCPU; a process that ignores the signal is stopped by the wall-clock limit only; limits only ever lower), TERM then KILL, a watchdog if the runner dies, exit 124 (wall clock), 125 (CPU), 123 (the process that started it is gone), 128+n (a signal).
- **The hook** (`scripts/hooks/pre-bash.sh`, rules in `z-nile/engine/boundcmd.luau`, entry `z-nile/guard-bash.luau`; PreToolUse on `Bash|Monitor`, 10 s timeout, 2 s of CPU) refuses by class and names the exact `<checkout>/zn run` command: a bare `lune run` of anything but the gate's tooling (`TOOLING` in `boundcmd.luau`: a new Lune entry the gate runs joins it; each registered home's `tests/run` counts without an entry, from the registry, c0244), other interpreters, inline Python only when it loops or starts a process with no `timeout=` (a Python file is refused), the `perl alarm` recipe (it leaves the tool child behind), `while`/`until` loops, follows (`tail -f`, `watch`, `gh ... watch`), detachers (`nohup`, `setsid`, `disown`, `at`, `tmux new -d`, `screen -dm`, `launchctl submit`), a `&` job without `wait`, and a background call with anything unbounded in it. It **fails open** (any error exits 0): a seatbelt that can block all work on its own bug is worse than the leak it prevents, and the reaper is the backstop. A **Monitor** command is bounded by its own timeout, so loops and follows pass there; its interpreters and detachers do not. It reads one shell line, not scripts: a script run by name (`bash probe.sh`), `npm`/`make`, other interpreters, `yes` (it ends in a pipe) and spellings a one-line scanner cannot read pass. `Bash(./zn run:*)` is in `permissions.allow` (the user's decision), so **any command wrapped in `./zn run` runs without a permission prompt**; the wrapper's limits are the safeguard, not the prompt.
- **The reaper** (`./zn reap`, `z-nile/engine/reap.luau`) treats a process as a leak only on an explicit yes, in one of three ways: *marked* (a non-system program whose environment carries a `ZN_BOUNDED_DEADLINE` that passed), *orphaned* (a tool program, interpreter, tool shell or `sleep`/`tail`/`gh`/`grep`/`watch` older than 60 s whose ancestors up to launchd are all of that kind), or *session end* (`--session-end`: the ending session's own tool shells, direct children of its `claude` process that source a shell snapshot, with everything below them; MCP servers and the status line are never touched). Scope: the user's processes, working in this repository's checkout and worktrees or its Claude session folders and the runner's temp folders (the session rule goes by ancestry wherever the shell went); never the reaper or its ancestors, a detached `git maintenance` or what runs below it, or an application (macOS's framework `Python` is read as `python3`). Call sites: `--auto` at the start of the gate and `./zn sync` (quiet, does nothing in a check run, never fails), SessionEnd (`scripts/hooks/session-end.sh`, skips `resume`, logs to `${XDG_STATE_HOME:-~/.local/state}/z-nile/reaped.log`), and by hand (`--dry-run` first). Its `ps` calls run with `LC_ALL=C`. macOS only.
- **CPU limits only lower** (`zn_lower_cpu` in `z-nile/lib/cpu.sh`): the spec runner puts `ulimit -t` of `PICKMAN_SPEC_CPU` (default 1200 s) on every spec process, `./zn` puts `ZN_ENGINE_CPU` (default 1800 s) on the engine, the hook entry gets 2 s and the session-end hook 15 s, and `./zn run --cpu` its own; a caller already under a lower limit keeps it. A limit is SIGXCPU only: a process that ignores the signal, or a loop that spends its time in system calls, is not stopped by it, so the wall-clock limit, the watchdog and the reaper are the other lines.
- **What none of this can do:** stop a command the hook cannot read, stop a process that calls `setsid` and is a system binary (the reaper cannot see its environment), or stop a syscall-heavy loop by CPU time alone. A subagent's command stops at its own `./zn run` limit.
